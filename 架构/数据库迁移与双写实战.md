# 数据库迁移与双写实战

> 换数据库/分库分表/上云，最怕"迁移过程中数据错乱、业务中断"。双写 + 校验 + 灰度切读是经典平滑迁移三板斧：先能力对齐，再双写，再校验，最后切流量，全程可回退。

## 1. 迁移流程

```mermaid
flowchart LR
    A[旧库] --> B[增量同步]
    B --> C[新库]
    D[应用双写] --> A
    D --> C
    C --> E[校验对账]
    E --> F[灰度切读]
    F --> G[停旧]
```

## 2. 双写阶段

- 应用同时写旧库与新库（新库可异步）。
- 以旧库为准，新库失败不影响主流程（或反之，按策略）。
- 双写需幂等，避免重复写导致不一致。

## 3. 校验与对账

- **全量校验**：迁移前全量比对，差异归因修复。
- **增量校验**：双写期间定时比对近期数据。
- **抽样+全量**：先抽样快速发现，再全量兜底。

## 4. 灰度切读

- 按用户/流量比例从新库读。
- 异常一键切回旧库。
- 稳定后停双写、下线旧库。

## 5. 常见坑

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 双写不一致 | 数据错 | 对账 + 补偿 |
| 切读回退难 | 影响大 | 流量级回退 |
| 增量丢失 | 漏数据 | CDC 兜底 |
| 性能下降 | 双写慢 | 异步 + 限流 |
| 旧库依赖 | 难下线 | 逐步解耦 |

## 6. 面试题

1. 双写为什么以一方为准？
2. 迁移如何保证数据一致？
3. 灰度切读如何设计？
4. 增量同步用什么？
5. 如何安全下线旧库？

## 7. 小结

平滑迁移 = 能力对齐 + 双写 + 校验对账 + 灰度切读。核心是"每一步都可校验、可回退"，把不可逆操作变成可逆过程。
