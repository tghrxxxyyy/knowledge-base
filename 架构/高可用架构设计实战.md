# 高可用架构设计实战

> 板块：架构 　|　 返回：[README](README.md)
> 覆盖：可用性度量、冗余、故障隔离、弹性、灰度、容灾、典型高可用模式。

## 一、什么是高可用

可用性用「几个 9」衡量：99.9%（年停机 ~8.7h）、99.95%（~4.4h）、99.99%（~52min）、99.999%（~5min）。每多一个 9，成本指数级上升。设计要按业务容忍度定 SLA，不要盲目追高。

> 高可用 = 冗余（不单点） + 故障转移（快速切换） + 降级（保核心） + 容错（出错不崩）。

## 二、冗余与无单点

- **计算无单点**：多实例 + 负载均衡（L4/L7），任一实例挂流量切走。
- **存储无单点**：主从复制、多副本（如 Raft 三副本），写多数派保证不丢。
- **机房无单点**：同城多可用区（AZ）、异地多活/灾备。
- **依赖无单点**：关键依赖（DB/缓存/MQ）自身高可用，避免核心链路依赖脆弱下游。

## 三、负载均衡

- **L4（IP/端口）**：性能好，不解析内容（LVS、硬件）。
- **L7（HTTP）**：按 URL/Header 路由，可做灰度（Nginx、APISIX、Envoy）。
- **算法**：轮询、加权轮询、最小连接、一致性哈希（减缓存击穿）。
- **健康检查**：定期探活，摘除不健康节点。

## 四、故障隔离（熔断/隔离/限流）

- **熔断**：依赖错误率超阈值则切断，快速失败，避免雪崩（Sentinel/Resilience4j）。半开探测恢复。
- **隔离**：线程池隔离、信号量隔离、舱壁模式（bulkhead），一个依赖慢不拖垮全部。
- **限流**：令牌桶/滑动窗口，保护自身（见 [场景设计/限流算法与网关实践](../场景设计/限流算法与网关实践.md)）。
- **超时**：所有远程调用必须设超时，且超时 < 上游超时，避免级联等待。

```java
// Resilience4j 熔断示例（示意）
CircuitBreakerConfig cfg = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .build();
CircuitBreaker cb = CircuitBreaker.of("svc", cfg);
Supplier<String> decorated = CircuitBreaker.decorateSupplier(cb, remoteCall);
```

## 五、降级与兜底

- **降级**：非核心功能在压力下关闭（如推荐关掉、评论只展示不实时排序），保下单/支付核心。
- **兜底数据**：缓存/静态页/默认值，依赖不可用时返回降级内容而非报错。
- **开关**：降级开关集中配置（配置中心），可秒级切换，配合预案演练。

## 六、弹性与自愈

- **弹性伸缩**：基于 CPU/QPS/队列深度自动扩缩容（K8s HPA）。
- **自愈**：健康检查失败自动重启/重建（K8s liveness/readiness）。
- **背压（Backpressure）**：下游慢时上游限流/缓冲，而非无脑转发压垮下游。

## 七、灰度与发布安全

- **蓝绿**：两套环境，流量整体切换，回滚快。
- **金丝雀**：按比例（1%→10%→100%）放量，观察指标，异常即停。
- **灰度维度**：按用户/地域/设备/白名单。
- **可回滚**：每次发布可一键回退，数据库变更向后兼容（先加字段后删）。

## 八、数据高可用

- **主从**：主写从读，主挂切从；注意主从延迟导致读旧数据（关键读走主）。
- **多副本共识**：Raft/Paxos 保证多数派存活即可写（etcd/Consul/TiKV）。
- **备份与恢复**：定期备份 + 演练恢复（备份不可恢复等于没备）。
- **最终一致**：跨库/跨服务用事务消息/Saga，见 [场景设计/支付系统核心设计](../场景设计/支付系统核心设计.md)。

## 九、容灾与多活

- **同城双活**：同城市多 AZ，RTO/RPO 小。
- **异地多活**：跨地域，路由按单元化（用户归属固定单元），避免跨地域强一致。
- **单元化**：把用户流量按维度（用户 ID 取模）封闭在一个单元，单元内自包含，减少跨地域调用。
- **容灾演练**：定期切流演练，避免「预案没用过，真出事不会切」。

## 十、可观测是高可用的眼睛

- 没有监控的高可用是盲飞。指标/日志/链路三支柱，见 [SRE/可观测性三支柱实战](../SRE/可观测性三支柱实战.md)。
- 告警驱动响应，SLO/错误预算量化稳定性，见 [SRE/SLO与错误预算实践](../SRE/SLO与错误预算实践.md)。

## 十一、典型高可用架构示意

```
                 DNS / GSLB（多地域）
                       ↓
               L7 网关（限流/灰度）
            ↓            ↓           ↓
       服务实例A     服务实例B     服务实例C   （多副本 + 熔断隔离）
            ↓            ↓           ↓
       DB 主从(多副本)   Cache 集群   MQ 集群
            ↓
       备份 + 异地容灾
```

## 十二、常见坑

1. 只做主从不做故障转移 → 主挂手动切，停机长。
2. 超时不设或设太大 → 级联阻塞。
3. 降级开关没人敢动 → 预案形同虚设。
4. 蓝绿/金丝雀不做 → 发布即冒险。
5. 备份从不恢复演练 → 真出事恢复失败。
6. 监控有看板无告警 → 故障发现晚。
7. 缓存当源 → 缓存挂数据丢。

## 十三、设计 checklist

- [ ] 每个组件都有冗余且无单点？
- [ ] 关键依赖故障能隔离/熔断？
- [ ] 有降级开关并演练过？
- [ ] 发布可灰度、可回滚？
- [ ] 数据有备份且恢复演练过？
- [ ] 有 SLO 与告警，故障能快速发现？
