# 分布式事务实战

## 〇、本体介绍

**分布式事务**：在多个独立数据库/服务/消息队列之间保证操作的原子性（要么全成功、要么全失败）。分布式事务是**微服务架构最难的课题之一**——CAP 定理决定了完美方案不存在，只有权衡。

**核心矛盾**：
1. **强一致**（2PC）vs **高可用**（BASE）：强一致阻塞，高可用脏读；
2. **性能**（异步/最终一致）vs **正确性**（同步/强一致）：此消彼长；
3. 不同业务场景对一致性要求不同：转账要强一致，点赞可以最终一致。

**核心主线**：2PC → TCC → SAGA → 本地事务表 → 最大努力通知 → 选型决策。

## 一、两阶段提交（2PC）

### 1.1 流程

```mermaid
sequenceDiagram
    participant C as 协调者 Coordinator
    participant P1 as 参与者 A（订单库）
    participant P2 as 参与者 B（库存库）
    C->>P1: Phase1: Prepare（执行但不提交）
    C->>P2: Phase1: Prepare
    P1-->>C: OK（Ready）
    P2-->>C: OK（Ready）
    C->>C: 所有参与者 OK → 决定 Commit
    C->>P1: Phase2: Commit
    C->>P2: Phase2: Commit
    P1-->>C: Ack
    P2-->>C: Ack
    Note over C,P2: 若任一 Prepare 失败 → 全部 Rollback
```

### 1.2 优缺点

| 维度 | 说明 |
|------|------|
| **优点** | 强一致，实现简单 |
| **缺点** | 同步阻塞（Phase1 锁资源）、单点（协调者故障）、Phase2 部分失败不一致 |
| **适用** | 同城短事务、强一致要求、参与者少 |

### 1.3 变体：三阶段提交（3PC）

- 增加 **CanCommit** 阶段（预检查），减少阻塞
- 引入超时机制（参与者超时自动提交/回滚）
- 仍不能完全解决网络分区问题

> 口诀：**"2PC 两阶段，先问后提交；阻塞是命门，强一致代价。"**

## 二、TCC（Try-Confirm-Cancel）

### 2.1 流程

```mermaid
sequenceDiagram
    participant B as 业务方
    participant A as 订单服务
    participant I as 库存服务
    B->>A: Try: 创建订单（状态=PENDING）
    A->>I: Try: 预扣库存（冻结）
    I-->>A: 冻结成功
    A-->>B: Try 成功
    B->>A: Confirm: 确认订单
    A->>I: Confirm: 确认扣减（解冻+扣减）
    I-->>A: 扣减成功
    A-->>B: 订单确认
    Note over B,I: 若 Try 失败 → Cancel: 释放冻结
```

### 2.2 三阶段详解

| 阶段 | 做什么 | 幂等 | 空回滚 | 悬挂 |
|------|--------|------|--------|------|
| **Try** | 资源预检 + 冻结 | ✅ | ❌ 需处理 | ❌ 需处理 |
| **Confirm** | 确认执行 | ✅ | - | - |
| **Cancel** | 释放冻结 | ✅ | ✅ | - |

### 2.3 TCC 异常处理

| 异常 | 处理 |
|------|------|
| **空回滚** | Cancel 先于 Try 到达（网络乱序）：Cancel 发现无冻结记录，记录"已 Cancel"，后续 Try 直接拒绝 |
| **悬挂** | Cancel 执行后 Try 到达：Cancel 标记后，Try 检查标记拒绝 |
| **幂等** | 每个阶段按业务键幂等（Confirm/Cancel 多次调用结果一致） |

### 2.4 TCC 代码示例

```java
// 订单服务 TCC
@LocalTCC
public interface OrderTCC {
    @TwoPhaseBusinessAction(name = "createOrder", commitMethod = "confirm", rollbackMethod = "cancel")
    boolean tryCreateOrder(@BusinessActionContextParameter("orderId") String orderId,
                          @BusinessActionContextParameter("userId") String userId);

    boolean confirm(BusinessActionContext ctx);

    boolean cancel(BusinessActionContext ctx);
}

// Seata TCC 实现
@Service
public class OrderTCCImpl implements OrderTCC {
    public boolean tryCreateAction(String orderId, String userId) {
        // 1. 创建订单（状态 = PENDING）
        orderDao.insert(orderId, userId, OrderStatus.PENDING);
        // 2. 冻结用户余额（freeze 字段）
        accountDao.freeze(userId, orderAmount);
        return true;
    }

    public boolean confirm(BusinessActionContext ctx) {
        String orderId = ctx.getActionContext("orderId");
        // 1. 订单状态 → CONFIRMED
        orderDao.updateStatus(orderId, OrderStatus.CONFIRMED);
        // 2. 解冻并扣减余额
        accountDao.confirmFreeze(userId, amount);
        return true;
    }

    public boolean cancel(BusinessActionContext ctx) {
        String orderId = ctx.getActionContext("orderId");
        // 1. 订单状态 → CANCELLED
        orderDao.updateStatus(orderId, OrderStatus.CANCELLED);
        // 2. 释放冻结余额
        accountDao.unfreeze(userId, amount);
        return true;
    }
}
```

> 口诀：**"Try 冻资源，Confirm 真扣；Cancel 释放，幂等兜底。"**

## 三、SAGA

### 3.1 思路

- 将长事务拆分为**多个本地事务**（T1, T2, T3...）
- 每个本地事务执行后，若失败则执行**补偿事务**（C3, C2, C1...）

```mermaid
sequenceDiagram
    participant B as 业务方
    participant S as SAGA 协调器
    participant DB1 as 订单库
    participant DB2 as 库存库
    participant DB3 as 支付库
    B->>S: T1: 创建订单
    S->>DB1: 订单入库
    S->>DB1: OK
    S->>DB2: T2: 扣减库存
    S->>DB2: OK
    S->>DB3: T3: 扣款
    S->>DB3: 扣款失败！
    S->>DB2: C2: 补偿（回补库存）
    S->>DB1: C1: 补偿（取消订单）
```

### 3.2 编排方式

| 方式 | 思路 | 适用 |
|------|------|------|
| **编排式（Choreography）** | 每个服务完成后发事件，下一个服务消费 | 简单链路 |
| **协调式（Orchestration）** | 中央协调器按序调用各服务 | 复杂链路 |

### 3.3 SAGA vs TCC

| 维度 | SAGA | TCC |
|------|------|-----|
| 一致性 | 最终一致 | 最终一致 |
| 资源锁定 | 不锁定（直接提交） | Try 阶段锁定 |
| 适用 | 长事务、跨多个服务 | 短事务、需要资源预留 |
| 补偿 | 需要补偿事务（逆向操作） | Cancel 释放冻结 |
| 隔离性 | 无隔离（脏读） | 较好（Try 阶段锁定） |

### 3.4 SAGA 编排引擎与隔离性（面试追问）

- **编排引擎**：复杂 SAGA 别手写协调器——**Temporal**（durable execution：步骤持久化、进程崩溃从断点重放）与 **Camunda**（BPMN 可视化编排）是生产标配；「手写状态机 + DB 持久化」也行，但重试/补偿/超时都要自己造轮子；
- **隔离性问题（SAGA 最大短板）**：各步骤直接提交，事务进行中其他请求能读到中间态（脏读）——解法是**语义锁（Semantic Lock）**：业务字段带状态（如订单 `PENDING` 时余额冻结不可消费），中间态对业务语义「不可见」；
- **补偿幂等**：补偿事务与正向事务一样要幂等（重复补偿=多退一笔）；补偿失败要进**死信队列 + 人工干预**，SAGA 不是「自动痊愈」是「可治愈」。<br>
  面试话术：**TCC 用资源冻结换隔离性，SAGA 用补偿换长事务——隔离性需求强选 TCC，步骤多/时间长选 SAGA + 语义锁。**

## 四、本地事务表（Transactional Outbox）

### 4.1 思路

- 业务数据 + 事件数据写入**同一个本地事务**
- 独立进程轮询事件表 → 发 MQ → 消费方处理

```mermaid
sequenceDiagram
    participant S as 订单服务
    participant DB[本地 DB<br/>订单表 + 事件表]
    participant P[事件发布器<br/>轮询]
    participant MQ[Kafka/RocketMQ]
    participant I[库存服务]
    S->>DB: 本地事务: 创建订单 + 插入事件(待发布)
    P->>DB: 轮询待发布事件
    P->>MQ: 发送事件
    P->>DB: 标记已发布
    MQ->>I: 消费事件 → 扣减库存
```

### 4.2 表设计

```sql
CREATE TABLE order_outbox (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    aggregate_id VARCHAR(64) NOT NULL,   -- 订单号
    event_type   VARCHAR(128) NOT NULL,  -- OrderCreated
    payload      JSONB NOT NULL,          -- 事件体
    status       TINYINT DEFAULT 0,      -- 0待发布 1已发布 2失败
    retry_count  INT DEFAULT 0,
    created_at   TIMESTAMP DEFAULT NOW(),
    published_at TIMESTAMP NULL,
    INDEX idx_status_created (status, created_at)
);
```

> 口诀：**"业务事件同事务，轮询发布不丢；消费者幂等处理，最终一致保证。"**

### 4.3 本地事务表 vs RocketMQ 事务消息（面试对比必考题）

| 维度 | 本地事务表 + 轮询 | RocketMQ 事务消息 |
|------|-------------------|-------------------|
| 原理 | 事件同库同事务 + 后台轮询发布 | 半消息（暂不可见）→ 本地事务 → commit/rollback；服务端**回查**兜底 |
| 回查 | 无（靠轮询重试） | 服务端按回查间隔询问本地事务状态（防「本地事务成功但没通知 MQ」） |
| 实现 | 一张表 + 定时任务，无中间件依赖 | 依赖 RocketMQ（版本 ≥ 4.3） |
| 延迟 | 轮询间隔（秒级） | 事务提交后立即可见（毫秒级） |
| 运维 | 无额外组件 | 多一套 MQ 组件 |
| 适用 | 已有轮询基建/无 MQ | 已有 RocketMQ、要低延迟 |

> 面试答案：**两者本质相同（都是「同库同事务 + 可靠投递」），RocketMQ 把「轮询」换成了「半消息 + 回查」，延迟更低；没 RocketMQ 就别为事务消息引入它，本地事务表 + 定时任务完全够用。**

## 五、最大努力通知

### 5.1 思路

- 调用方尽力通知被调用方，但不保证一定成功
- 被调用方提供**查询接口**供调用方核对

### 5.2 流程

```mermaid
sequenceDiagram
    participant C as 调用方（支付）
    participant N as 通知服务
    participant CB as 被调用方（订单）
    C->>N: 发送通知（支付成功）
    N->>CB: HTTP 通知
    CB-->>N: 失败
    N->>N: 重试（1min/5min/30min/2h/...）
    Note over N: 重试 N 次后放弃
    C->>CB: 兜底：查询接口核对
    CB-->>C: 返回最新状态
```

### 5.3 对比

| 方案 | 一致性 | 性能 | 适用 |
|------|--------|------|------|
| **2PC** | 强一致 | 低 | 同城短事务 |
| **TCC** | 最终一致 | 中 | 订单/库存/账户 |
| **SAGA** | 最终一致 | 高 | 长流程/多服务 |
| **本地事务表** | 最终一致 | 高 | 异步事件驱动 |
| **最大努力通知** | 弱一致 | 最高 | 通知/回调 |

## 六、选型决策

```
需要强一致？
  ├── 是 → 2PC（同城）/ TCC（分布式）
  └── 否 → 事务链路长？
              ├── 长 → SAGA
              └── 短 → 需要资源预留？
                        ├── 是 → TCC
                        └── 否 → 异步即可？
                                  ├── 是 → 本地事务表
                                  └── 否 → 最大努力通知
```

| 场景 | 推荐 | 理由 |
|------|------|------|
| 银行转账 | TCC / 2PC | 强一致，不能丢 |
| 电商下单 | TCC / SAGA | 订单→库存→支付，最终一致 |
| 积分发放 | 本地事务表 | 异步，不阻塞主流程 |
| 短信通知 | 最大努力通知 | 尽力即可，可人工补发 |
| 跨系统对账 | SAGA + 对账 | 事后核对修复 |

### 6.1 Seata AT 模式原理（正文对应面试题 11）

Seata 的 **AT（Automatic Transaction）** 模式是「自动化 TCC」：业务代码零侵入，框架自动生成反向 SQL 回滚。

```
TM 开启全局事务 → 生成 XID 透传 →
RM(DataSourceProxy 代理) 执行业务 SQL 时：
  1. 先查 undo_log 所需的前镜像（UPDATE 前的行数据）
  2. 执行业务 SQL，记录后镜像
  3. 同一本地事务内写 undo_log 表
TM 提交/回滚：回滚时读 undo_log，用后镜像-前镜像逆推补偿 SQL 恢复
```

| 关键机制 | 说明 |
|----------|------|
| **DataSourceProxy** | 代理数据源拦截 SQL，自动生成镜像 |
| **undo_log 表** | 每库一张，记录前/后镜像，与业务同事务写入 |
| **全局锁** | 写操作前申请全局锁（防脏写）；锁冲突则重试/等待 |
| **回滚** | 反向 SQL（前镜像 → 原值）恢复；回滚失败进**异常恢复任务**重试 |
| **与 TCC 区别** | AT 自动生成镜像（零侵入），TCC 手写三个方法（灵活但代码多） |

> 面试一句话：**AT = 代理数据源自动记录镜像 + undo_log 同事务落库 + 全局锁防脏写，业务零侵入；代价是额外锁开销与镜像存储，适合「存量系统快速接分布式事务」。**

### 6.2 先问「能不能不用分布式事务」（最高频开放题）

选型之前先答这三问，多数场景可以**避免**分布式事务：

1. **事务边界能否最小化**：把「跨服务事务」变成「单服务本地事务 + 异步通知」——如扣库存不放支付里，支付成功发事件再扣；
2. **顺序能否调整**：先写本地、后补动作（延迟任务/定时补偿）——如订单先落库（本地事务），超时未支付由定时任务关单；
3. **能否用状态机收敛**：把「多个操作」建模成「一个聚合根的状态流转」（见[DDD/战术设计](../DDD/战术设计.md)）——状态机天然可恢复、可对账。

> 结论：**分布式事务是「最后手段」不是「默认方案」——先降级为最终一致 + 对账兜底，兜不住再上 TCC/SAGA。** 面试加分话术：先讲规避，再讲方案。

### 6.3 对账兜底（最终一致的「最后防线」）

任何最终一致方案都必须配套对账，否则「不一致」永远沉默：

- **对账流程**：日终批量核对「本地流水 vs 对方流水」（订单表 vs 支付回调表 / 库存扣减 vs 订单）→ 差异进**差错表** → 自动/人工补偿（补发、冲正、标记人工处理）；
- **对账粒度**：按业务键 + 金额 + 状态三要素比对；流水表要有「唯一性约束 + 幂等键」，对账才有可靠基准；
- **对账触发补偿**：发现差异 → 按差异类型触发补偿动作（SAGA 补跑 / 人工审批补单），补偿动作本身要幂等 + 留痕；
- 完整账务对账设计见[场景设计/钱包与账务系统设计](../场景设计/钱包与账务系统设计：账户、流水与日终对账.md)。

> 一句话：**分布式事务保证「尽力一致」，对账保证「发现不一致」——两者组合才是完整的最终一致。**

## 面试高频问题（18+ 条）

1. **分布式事务有哪些方案？** 2PC、TCC、SAGA、本地事务表、最大努力通知。
2. **2PC 的问题？** 同步阻塞（Phase1 锁资源）、协调者单点、Phase2 部分提交失败。
3. **TCC 的三个阶段？** Try（冻结资源）、Confirm（确认执行）、Cancel（释放冻结）。
4. **TCC 的空回滚是什么？** Cancel 先于 Try 到达（网络乱序），Cancel 记录标记，Try 检查拒绝。
5. **TCC 的悬挂是什么？** Cancel 执行后 Try 到达，Try 检查 Cancel 标记拒绝。
6. **SAGA 和 TCC 的区别？** SAGA 不锁定资源直接提交，需要补偿事务；TCC Try 阶段锁定。
7. **什么是本地事务表（Outbox）？** 业务数据 + 事件数据写同一本地事务，独立进程轮询发布到 MQ。
8. **本地事务表怎么保证不丢？** 事件和订单同事务写入（原子），轮询发布 + 失败重试。
9. **最大努力通知是什么？** 调用方尽力通知，被调用方提供查询接口兜底核对。
10. **怎么选型？** 强一致→2PC/TCC；长链路→SAGA；异步→本地事务表；通知→最大努力。
11. **Seata 支持哪些模式？** AT（自动补偿）、TCC、SAGA、XA。
12. **RocketMQ 事务消息是什么？** 半消息 → 执行本地事务 → 确认/回滚，= 本地事务表的 MQ 实现。
13. **分布式事务中幂等怎么做？** 业务唯一键去重（唯一索引/Redis Set/状态机 CAS）。
14. **BASE 理论是什么？** 基本可用 + 软状态 + 最终一致，是 CAP 中 AP 方案的延伸。
15. **什么是补偿事务？** SAGA 中的逆向操作：如"扣库存"的补偿是"回补库存"。
16. **SAGA 编排式和协调式区别？** 编排式：服务间事件驱动；协调式：中央协调器按序调用。
17. **XA 是什么？** 数据库层面的 2PC 接口（Java JTA），性能差，微服务不推荐。
18. **幂等和事务的关系？** 事务的 Confirm/Cancel/SAGA 补偿都必须幂等（网络重试安全）。
19. **对账在分布式事务中的作用？** 兜底手段：事务执行后定期核对，发现差异自动修复。
