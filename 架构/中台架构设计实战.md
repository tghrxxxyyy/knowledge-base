# 中台架构设计实战

> 板块：架构 　|　 返回：[README](README.md)
> 关联：[微服务拆分与设计原则](微服务拆分与设计原则.md)、[DDD/领域建模与限界上下文实战](../DDD/领域建模与限界上下文实战.md)、[技术选型与决策实战](技术选型与决策实战.md)

中台（Middle Platform）是介于"前台业务"与"后台系统"之间、被多个业务线复用的能力沉淀层。它旨在解决"重复造轮子、业务响应慢、数据孤岛"问题，但同时也有"过度抽象、沟通成本高"的反模式风险。本文从动机、类型、设计原则到落地与反模式系统讲解。

## 一、中台解决的痛点

大公司多业务线（如电商的 C 端、B 端、国际化）常出现：

| 痛点 | 表现 |
|------|------|
| 重复建设 | 每个业务线各做一套用户/支付/商品 |
| 响应慢 | 新业务要从零搭基础设施 |
| 数据孤岛 | 各业务数据口径不一，无法统一分析 |
| 标准不一 | 同类能力多种实现，维护成本高 |

中台思路：把**通用、稳定、可复用**的能力抽出来，作为"能力底座"供前台快速组装。

```
前台（多业务线）：电商C端 / 电商B端 / 国际化 / 新零售
        │  复用
中台（共享能力）：用户中台 / 交易中台 / 商品中台 / 数据中台 / 技术中台
        │  支撑
后台（基础设施）：DB / 中间件 / 运维 / 安全
```

## 二、中台的类型

| 类型 | 提供能力 | 例子 |
|------|---------|------|
| 业务中台 | 业务共性能力 | 用户中心、交易中心、营销中心、商品中心 |
| 数据中台 | 数据汇聚/治理/服务 | 统一数仓、画像、标签、指标平台 |
| 技术中台 | 技术基础设施 | 微服务框架、消息、缓存、DevOps、AI 平台 |
| 组织中台 | 方法论/流程 | 敏捷教练、复用组件库、设计规范 |

> 最常见也最核心的是**业务中台 + 数据中台**。

## 三、业务中台设计

### 3.1 沉淀什么

- **稳定通用**：用户、权限、商品、订单、支付、库存等跨业务通用。
- **可变差异外置**：不同业务的差异用「配置/插件/扩展点」而非分支代码。

### 3.2 能力模型（API / 服务）

```
业务中台 = 领域服务 + 共享数据 + 配置中心 + 扩展点
```

- 每个中台是一个**领域服务中心**（对应 DDD 限界上下文），对外暴露稳定 API。
- 业务线通过调用中台 API + 少量自身定制，快速拼装业务。

### 3.3 扩展点（避免硬编码分支）

- 用 **SPI / 策略模式 / 规则引擎** 让业务差异可插拔。
- 例：营销中台提供"发券"能力，不同业务的发券规则通过配置/插件注入，而非 if(business=='A')。

```java
// 扩展点示例：不同业务不同的风控策略
interface RiskStrategy { boolean check(Order o); }
// 业务A、B 各自实现，中台按 businessType 路由
RiskStrategy s = strategyFactory.get(order.getBizType());
```

## 四、数据中台设计

| 层 | 职责 |
|----|------|
| 采集层 | 业务埋点、日志、DB binlog（CDC）统一接入 |
| 存储层 | 数仓（ODS→DWD→DWS→ADS）、实时（Kafka+Flink） |
| 治理层 | 指标口径统一、数据质量、血缘、主数据管理（MDM） |
| 服务层 | 标签圈人、画像、即席查询、报表 API |

- **统一口径**：同一指标（如"活跃用户"）全公司一个定义，避免各算各的。
- **数据资产化**：把数据变成可复用的"服务/标签"，前台直接调用。

## 五、中台与微服务的区别

| 维度 | 微服务 | 中台 |
|------|--------|------|
| 视角 | 技术/部署拆分 | 业务能力复用 |
| 粒度 | 单个服务 | 一组相关服务的沉淀 |
| 目标 | 独立开发部署 | 多业务线共享 |
| 关系 | 中台由多个微服务组成 | 中台是微服务的"业务聚合层" |

> 中台不是技术架构，而是**组织 + 架构 + 能力的综合体**。没有组织协同，技术上做不出真中台。

## 六、中台落地的关键原则

1. **先有复用需求再抽中台**：别为了"中台"而中台，先出现 2~3 处重复再沉淀（过早抽象害死人）。
2. **稳定内核 + 可变外延**：核心是稳定 API，差异通过配置/插件外置。
3. **API 契约优先**：中台对前台是"服务契约"，版本化管理。
4. **领域驱动划界**：中台边界 = 限界上下文（见 DDD）。
5. **数据口径统一**：数据中台先统一指标定义，再谈平台。
6. **治理与运营**：中台建成后要有团队持续运营（否则腐化）。

## 七、中台的组织保障

- **中台团队**：负责能力沉淀与 SLA，对复用负责。
- **前台团队**：负责业务创新，调用中台快速试错。
- **协作机制**：中台需求来自前台，避免中台自嗨造没人用的能力。
- **度量复用率**：中台价值 = 服务业务线数 × 调用量 − 维护成本。

## 八、中台的反模式

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 过度抽象 | 为不存在的差异做泛化 | 复杂度爆炸、难维护 |
| 中台绑架 | 前台任何需求都过中台 | 响应更慢、沟通成本翻倍 |
| 大泥球中台 | 一个中台包揽一切 | 又回到单体，失去灵活 |
| 中台 KPI 错 | 中台团队考核"做了多少功能" | 造没人用的能力 |
| 伪中台 | 只是改名，无复用 | 换汤不换药 |

> 阿里中台实践后来也反思："中台不是银弹，该拆就拆"。小公司/单业务线做中台往往是过度设计。

## 九、中台 vs 平台 vs 微服务中台化

| 形态 | 说明 |
|------|------|
| 平台 | 提供工具/环境，业务自行搭建（如 AWS） |
| 中台 | 提供可复用业务能力，业务组装（如交易能力） |
| 微服务中台化 | 把多个微服务按领域聚成中台，对外统一 API |

## 十、演进路径

```
单业务系统化 → 多业务重复建设 → 抽取共性(中台) → 能力复用 → 前台快速创新
   ↑                                                   │
   └────────────── 过度膨胀则拆分/瘦身后 ───────────────┘
```

- 早期单业务线：先做好模块化单体/微服务，别急着中台。
- 多业务线出现重复：识别共性，逐步沉淀。
- 成熟后：中台能力产品化，甚至对外输出（如字节/美团的能力中台）。

## 十一、常见坑

1. **没有复用就抽中台** → 过度设计，维护成本 > 收益。
2. **中台做太厚** → 前台任何改动都依赖中台，响应变慢。
3. **领域边界不清** → 中台之间又耦合，回到分布式单体。
4. **数据口径不统一** → 数据中台变成"更多孤岛"。
5. **组织不配套** → 技术做了中台，业务不买账，无人用。
6. **KPI 导向错** → 中台团队堆功能，不重复用率。
7. **一刀切** → 所有业务强制走中台，简单业务也被拖慢。

## 十二、落地清单

- [ ] 确认多业务线确有重复，且复用价值 > 抽象成本。
- [ ] 按 DDD 限界上下文划中台边界（用户/交易/商品/数据）。
- [ ] 设计稳定 API 契约 + 扩展点（配置/插件外置差异）。
- [ ] 数据中台先统一指标口径，再建平台。
- [ ] 配套中台团队 + 前台团队 + 复用率度量。
- [ ] 设"瘦身后"机制，过度膨胀及时拆分。
