# 多级缓存与热点架构实战

缓存是提升系统吞吐、降低延迟、保护数据库的核心手段。
多级缓存通过"本地缓存 + 分布式缓存 + 存储"分层，逐层拦截请求。
本文系统讲解缓存层级、热点Key、穿透/击穿/雪崩、一致性、失效策略与最佳实践。

## 一、为什么要多级缓存

单级缓存存在瓶颈：

- 分布式缓存（如 Redis）仍有网络往返与带宽上限。
- 高并发下热点 Key 集中打到缓存集群，成为单点瓶颈。
- 缓存集群抖动会瞬间把压力传导到数据库。

多级缓存思路：

- 请求先打本地缓存（进程内），命中则零网络开销。
- 本地未命中再打分布式缓存。
- 分布式未命中再回源数据库，并回填各级缓存。

## 二、典型缓存层级

### 2.1 客户端缓存

浏览器/CDN 缓存静态资源与可缓存响应。
通过 Cache-Control、ETag 控制。适合读多写少、变化不频繁的资源。

### 2.2 本地缓存（进程内）

使用 Caffeine、Ehcache、Guava Cache 等。
特点：

- 零网络开销，纳秒级命中。
- 容量有限，受单实例内存限制。
- 多实例间不共享，存在数据不一致窗口。

适用：热点字典、配置、计算结果。

### 2.3 分布式缓存

Redis、Memcached 等集中式缓存。
特点：

- 多实例共享，容量大。
- 有网络开销，毫秒级。
- 可作为统一缓存层，承载大部分读流量。

### 2.4 存储层

数据库、对象存储作为最终数据源。
缓存未命中时回源，回源结果写回缓存。

### 2.5 层级示意

```text
请求 → 客户端/CDN → 本地缓存 → 分布式缓存 → 数据库
        命中返回     命中返回     命中返回     回源并回填
```

## 三、缓存三大经典问题

### 3.1 缓存穿透

现象：查询一个根本不存在的数据，缓存与数据库都没有。
后果：每次请求都打到数据库，恶意攻击可拖垮 DB。

解决方案：

- 缓存空值：对查不到的结果也缓存一个短过期时间的空标记。
- 布隆过滤器：在缓存前用布隆过滤器拦截一定不存在的 Key。
- 参数校验：非法 ID 直接拒绝。

### 3.2 缓存击穿

现象：某个热点 Key 在过期瞬间，大量并发同时打到数据库。
后果：热点 Key 失效引发瞬时回源洪峰。

解决方案：

- 互斥重建：只放一个线程去回源，其他线程等待或返回旧值。
- 逻辑过期：不物理删除，后台异步刷新，读时返回旧值。
- 热点 Key 永不过期 + 主动更新。

### 3.3 缓存雪崩

现象：大量 Key 在同一时间集中失效，或缓存集群宕机。
后果：瞬间回源量暴涨，数据库被打垮。

解决方案：

- 过期时间加随机抖动：避免同时失效。
- 多级缓存：即使分布式层挂了，本地层仍能扛一部分。
- 高可用：缓存集群主从 + 哨兵/集群模式。
- 限流熔断：回源通道做限流，保护数据库。

## 四、热点 Key 问题

### 4.1 热点 Key 的成因

- 爆款商品、热门帖子、大V账号。
- 定时任务集中访问同一批数据。
- 被恶意刷量的对象。

### 4.2 热点 Key 的危害

- 单分片/单节点 CPU、带宽被打满。
- 该 Key 所在节点成为瓶颈，影响同节点其他 Key。

### 4.3 解决方案

- 本地缓存副本：把热点 Key 复制到本地，分散远程访问。
- Key 打散：对热点 Key 做分片（如 key#1、key#2…），分散到不同节点。
- 限流：对单 Key 访问做速率限制。
- 多副本：读取时随机选一个副本，写时广播更新。

## 五、缓存一致性

### 5.1 经典矛盾

缓存与数据库是两份数据，更新时如何保持一致？

### 5.2 先更新数据库，再删缓存（推荐）

步骤：

1. 更新数据库。
2. 删除缓存（不是更新缓存）。

读请求在下次命中时会回源拿到新值。
优点：实现简单、最终一致。
风险：删除缓存失败导致脏数据，可引入重试或 binlog 同步删除。

### 5.3 先删缓存，再更新数据库

步骤：

1. 删除缓存。
2. 更新数据库。

风险：删除缓存后、更新数据库前，若有读请求会回填旧值。
可通过"延迟双删"缓解：更新后再删一次。

### 5.4 读写穿透（Read/Write Through）

由缓存层统一封装读写，业务只和缓存交互。
缓存负责同步落库，一致性更强但实现复杂。

### 5.5 订阅 binlog 异步更新

通过 CDC（如 Canal）订阅数据库变更，异步刷新缓存。
解耦业务代码，降低一致性维护成本。

## 六、失效策略

### 6.1 TTL 过期

给每个 Key 设置过期时间，到期自动失效。
注意：TTL 集中到期会引发雪崩，需加随机抖动。

### 6.2 LRU / LFU 淘汰

内存满时按策略淘汰：

- LRU（最近最少使用）：淘汰最久未访问。
- LFU（最少频率使用）：淘汰访问频次最低。

### 6.3 主动失效

数据变更时主动删除/更新对应缓存，保证及时生效。

## 七、缓存设计反模式

- 缓存大对象：单个 Value 过大撑爆内存与带宽，应拆分。
- 无过期时间：缓存无限增长，内存泄漏。
- 缓存写穿透：每次写都同步双写，性能差，改用删除+异步。
- 把缓存当数据库：缓存可丢，重要数据必须有持久层。

## 八、多级缓存落地建议

- 先确认热点，再决定加哪一级缓存。
- 本地缓存只放真正的热点且可容忍短暂不一致的数据。
- 分布式缓存作为主缓存层，做好高可用。
- 回源通道必须限流、熔断，保护数据库。
- 监控缓存命中率、回源 QPS、各层延迟。

## 九、速记

- 多级缓存：本地 + 分布式 + 存储，逐层拦截。
- 穿透：查不存在 → 布隆/空值；击穿：热点过期 → 互斥重建；雪崩：集中失效 → 抖动过期。
- 一致性首选"先更新库再删缓存"。
- 热点 Key：本地副本、Key 打散、限流。
- 缓存是加速层，不是存储层，不可丢必须可回源。
