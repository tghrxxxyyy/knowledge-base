# 高并发架构与缓存实战

> 本文从"请求从浏览器到数据库"的全链路视角，拆解高并发下的架构手段：静态化、CDN、负载均衡、无状态服务、多级缓存、异步化、数据库优化，以及缓存经典问题与一致性方案。内容基于工程实践，阈值以业务实际为准。

## 1. 高并发的第一性原则

- 尽可能把请求挡在更前面（离用户越近越好）。
- 尽可能减少落到数据库的请求（缓存/聚合）。
- 尽可能让处理无状态、可水平扩展。
- 不可避免的重活用异步削峰。

## 2. 请求链路分层

```
浏览器 → CDN → 四/七层 LB → API网关
   → 无状态 Web → 本地缓存/Redis → 数据库/ES
   ↘ MQ（异步写/削峰）
```

每一层都承担"拦截与加速"。

## 3. 静态化与 CDN

- 静态资源（图片/JS/CSS/页面片段）推 CDN，就近返回。
- 动态内容也可边缘缓存（ESI/边缘函数）。
- 缓存键设计避免命中率过低。
- 版本化文件名便于刷新。

## 4. 负载均衡

- L4（IP/端口）与 L7（HTTP 路径/头）负载。
- 算法：轮询、加权、最少连接、一致性哈希（粘性/缓存命中）。
- 健康检查：摘除故障节点。
- 网关层再做限流/鉴权。

## 5. 无状态服务

- 服务不持有会话状态，状态外置（Redis/DB）。
- 便于水平扩展（加实例即扩容）。
- 会话可放 Redis（session sticky 非必须）。

## 6. 多级缓存

### 6.1 层级

- 浏览器缓存（强缓存/协商缓存）。
- CDN 边缘缓存。
- 应用本地缓存（Caffeine/Guava，防 Redis 抖动）。
- 分布式缓存（Redis）。
- 数据库缓冲池（Buffer Pool）。

### 6.2 读写模式

- **Cache-Aside**：读时查缓存未命中查库并回填；写时更库+删缓存。
- **Read-Through / Write-Through**：缓存层代理 DB 读写。
- **Write-Behind**：异步写库，性能好但可能丢。

### 6.3 一致性

- 先更新 DB，再删除缓存（Cache-Aside 推荐）。
- 延迟双删：删缓存→更库→延迟再删，应对并发读写。
- 更严谨：订阅 binlog（如 Canal）异步更新缓存。

## 7. 缓存三大经典问题

### 7.1 缓存穿透

- 含义：查不存在的数据，缓存与 DB 都没有，每次打 DB。
- 解决：缓存空值（短 TTL）、布隆过滤器拦截。

### 7.2 缓存击穿

- 含义：热点 key 失效瞬间，大量请求同时打到 DB。
- 解决：互斥重建（只放一个线程重建）、逻辑过期（异步刷新）、热点不过期。

### 7.3 缓存雪崩

- 含义：大量 key 同一时间过期，或 Redis 宕机，请求全压 DB。
- 解决：过期时间加随机抖动、多级缓存、Redis 高可用（哨兵/集群）。

## 8. 异步化与 MQ

- 非实时写（日志、积分、通知）入 MQ 异步处理。
- 削峰：突发流量排队，按消费能力处理。
- 解耦：生产者不依赖消费者。
- 注意：消费幂等（见分布式事务章节）。

## 9. 数据库优化

### 9.1 索引

- 高频查询建索引，避免全表扫描。
- 联合索引注意最左前缀。
- 避免索引失效（函数/隐式转换/前导模糊）。

### 9.2 读写分离

- 主写从读，分摊读压力。
- 注意复制延迟导致的"读旧数据"。

### 9.3 分库分表

- 单表过大（千万级+）考虑分片。
- 按 user_id 哈希或范围分片。
- 分片键选择影响查询路由。
- 跨分片查询/事务复杂，能不分就不分。

### 9.4 连接池

- 用连接池（HikariCP 等）复用，避免频繁建连。
- 池大小需调（过大反而上下文切换多）。

## 10. 限流、降级、熔断

- 限流：令牌桶/漏桶，保护系统（见限流章节）。
- 降级：高峰关闭非核心（推荐/评论）。
- 熔断：下游异常快速失败，防雪崩。
- 三者是稳定的三板斧。

## 11. 热点与倾斜

- 热点 key：单 key 高频访问压垮单节点；拆分（key+后缀）、本地缓存、限流。
- 数据倾斜：某分片数据/流量远超其他；重新分片、加盐。
- 大 key/大 value：Redis 大 key 阻塞；拆分/压缩。

## 12. 压测与容量

- 全链路压测找瓶颈（见 SRE 容量章节）。
- 逐步加压到拐点。
- 容量规划 + 弹性扩容。

## 13. 实战：高并发读场景

- CDN + 本地缓存 + Redis + 主从库。
- 读路径：浏览器→CDN→本地→Redis→DB（极少）。
- 热点 key 加随机数分散、互斥重建。

## 14. 实战：高并发写场景

- 入口限流 + 校验。
- Redis 原子预扣/计数。
- MQ 异步落库。
- 批量写入（合并 insert）。
- 分库分表分摊写压力。

## 15. 常见踩坑

1. **先更缓存再更库**：并发下数据错乱；应更库后删缓存。
2. **缓存大 key**：阻塞 Redis；拆分。
3. **本地缓存无上限**：内存溢出；设大小/过期。
4. **读写分离读旧数据**：关键读走主库。
5. **分库分表过早**：运维成本陡增；先优化索引与缓存。
6. **连接池过大**：反而更慢；按实测调。
7. **无降级**：高峰全链路一起挂。
8. **热点单 key**：单节点被打爆；分散+本地缓存。

## 16. 监控指标

- 缓存命中率（低则失效）。
- Redis 内存/命中延迟/大 key。
- DB QPS、慢查询、连接数。
- 接口 P99、错误率。
- MQ 堆积。

## 17. 演进路径

- 先加 Redis 缓存热点。
- 再读写分离、索引优化。
- 加本地缓存、CDN、静态化。
- 异步化削峰。
- 最后才分库分表。

## 18. 小结

高并发架构是"层层拦截、处处缓存、异步削峰、数据库兜底"的组合拳。核心手段：静态化与 CDN 挡在最前，多级缓存减少 DB 压力，无状态服务水平扩展，MQ 异步削峰，限流降级熔断保稳定。缓存的铁律是**先更库后删缓存、防穿透/击穿/雪崩、大 key 必拆**。分库分表是最后手段，别一开始就上。
