# 单体到微服务演进（模块化单体 / 绞杀者模式 / 数据库拆分 / 无状态化改造）

> 「微服务」不是起点，而是**演化的结果**。本篇深入拆解：模块化单体设计、绞杀者模式落地细节、数据库拆分策略、无状态化改造、组织适配康威定律。

---

## 一、为什么不要一上来就微服务

```
分布式铁律：网络不可靠、延迟、分区、最终一致 → 新增成本
运维爆炸：每个服务要独立部署/监控/链路追踪 → 小团队被拖垮
数据一致性变难：原来一个事务 → 现在要 Saga/消息

结论：单体不是原罪，混乱的单体才是。先把单体写「边界清晰」。
```

---

## 二、演进路线（五步）

### 步骤 1：模块化单体（Modular Monolith）

```
在单体内用包/模块划清限界上下文（DDD），模块间只通过明确定义的接口调用，
禁止跨模块直接查表。

好处：规避分布式成本，又攒下清晰边界，为拆分铺路。

实现：
  - 按业务域分包（order/payment/user/inventory）
  - 模块间通过接口调用（不直接依赖实现类）
  - 公共模块抽取到 common/lib
  - ArchUnit 门禁：禁止跨模块依赖
```

### 步骤 2：提取横切/公共能力

```
把认证、日志、通知、文件等抽成公共模块/共享内核，
避免每个模块各写一套。

公共模块：
  认证鉴权：统一认证中心
  日志：统一日志框架
  通知：短信/邮件/推送
  文件：对象存储
  缓存：Redis 工具类
```

### 步骤 3：绞杀者模式（Strangler Fig）拆服务

```
不一次性重写，而是在单体前加一层路由/网关，
把新功能或待拆模块做成独立服务，逐步「绞杀」旧实现。

切流落地细节：
  灰度 1% → 5% → 20% → 50% → 100%（每个阈值停留观察 1~3 天）

  切流控制：网关按用户 ID 哈希 / Header 标签 / 权重切流
  新旧并行校验：同一请求同时打新旧两端，比对结果 diff
  回滚条件预设：错误率 > 0.5% / p99 超 SLO → 即回滚
  影子库校验：新服务数据先落影子表，对账确认一致再转正
  数据迁移窗口：选低峰期（凌晨）迁移大表
  老代码退役：新服务 100% 承接后删除旧实现
```

### 步骤 4：数据库拆分（最难）

```
先逻辑隔离：同一库内按模块分 schema/表，禁止跨模块 JOIN
再物理隔离：把高频/独立演进模块的表迁到独立库，通过 API/事件交互
数据同步：用 CDC（Canal/Debezium）或双写 + 校验

拆分顺序：
  1. 用户表（最独立）
  2. 订单表（高频写）
  3. 商品表（读多写少）
  4. 库存表（写密集）
  5. 日志/流水表（append only）
```

### 步骤 5：按需求独立扩展

```
只有「需要独立扩容/独立技术栈/独立团队 ownership」的模块
才彻底独立成微服务；其余保留模块化单体。

判断标准：
  ✅ 独立变更频繁
  ✅ 资源画像不同（CPU/IO 密集）
  ✅ 团队按域划分 ownership
  ❌ 只是「听说微服务好」
  ❌ 模块间强事务耦合
  ❌ 团队 < 10 人
```

## 三、数据库拆分反模式

| 反模式 | 问题 | 解决 |
|--------|------|------|
| 分布式事务滥用 | 跨服务长事务 | 改 Saga/最终一致 |
| 共享库强耦合 | 拆了服务却还共用一个库 | 按模块独立库 |
| 跨服务 JOIN | 应用层拼 JOIN | API 组合或 CQRS 读模型 |
| 一次性大爆炸迁移 | 停机重写风险极高 | 绞杀者渐进 |

## 四、无状态化改造

### 4.1 状态处理

| 状态 | 拆前现状 | 拆后方案 |
|------|----------|----------|
| 会话 Session | 单体内存 | Redis 集中存储 / JWT 无状态化 |
| 本地缓存 | JVM 内缓存 | 独立缓存服务（Redis/多级缓存） |
| 定时任务 | 单体 cron 全局一份 | 独立任务服务 + 分布式锁 |
| 分布式 ID | 自增主键 | 雪花 ID / 号段模式 |
| 单例/静态变量 | 进程内全局 | 外置为显式依赖（DB/缓存/配置） |

> 原则：**「能被复制出去的进程」才能被拆分**——拆服务前先完成无状态化改造。

### 4.2 模块化单体自己的坑

```
隐式耦合复发：模块间悄悄共享工具类/静态变量/缓存 key → 边界名存实亡
  → 用 ArchUnit 工具门禁

部署单元过大：任何模块发版都重启整个单体 → 变更爆炸半径没缩小
  → 若此痛点强烈，恰恰说明该拆独立服务

一个库的宿命：模块化单体再干净，数据库还是共享的 → 拆库时仍要过第五节的坎

2025 争论的客观答案：
  「模块化单体 vs 微服务」不是二选一
  同一系统可以长期混合（核心交易留单体，扩展热点拆服务）
  Prime Video「从微服务退回单体」证明的是「别为拆而拆」
```

## 五、服务间交互模式选型

| 模式 | 同步/异步 | 适用 | 代价 |
|------|----------|------|------|
| REST/gRPC 同步调用 | 同步 | 实时查询、强依赖 | 链路超时/级联 |
| 消息事件 | 异步 | 解耦、可重放 | 最终一致、去重 |
| 事件溯源 + CQRS | 异步 | 审计/复杂域 | 学习成本高 |
| BFF 聚合层 | 同步 | 客户端编排 | 多一层维护 |

> 选型心法：**查用同步，改发事件**——读链路保实时，写链路保解耦。

## 六、组织侧：康威定律

```
系统结构会复制团队沟通结构。

拆分前：
  确认团队是否已按域划分
  否则「服务边界」与「团队边界」错位，必然返工

拆分后：
  每个服务有明确的 ownership 团队
  团队内自治（技术选型/发布/值班）
```

## 七、拆分实施清单

**拆分前（1~2 周）**
- [ ] 画出现有模块依赖图，找出循环依赖与隐式共享表
- [ ] 用 DDD 限界上下文对齐模块边界
- [ ] 梳理跨模块调用清单，标记「同事务 / 可异步」

**拆分中**
- [ ] 新模块先走「服务内接口 + 事件」双通道
- [ ] 数据库用「双写 + 校验」过渡
- [ ] 每个服务补齐：独立 CI、日志 trace_id、SLO 告警

**拆分后**
- [ ] 旧模块流量归零后删除旧代码/旧表
- [ ] 复盘：跨服务调用是否过多？

**拆完立刻要有的治理配套**
- [ ] 注册中心 + 配置中心
- [ ] API 网关：路由、鉴权、限流统一收口
- [ ] trace_id 全链路透传 + SLO 告警
- [ ] 灰度发布基线 + 回滚预案
- [ ] 契约测试守护服务间接口

## 八、面试高频追问

1. Q：为什么不建议一上来微服务？ A：分布式带来网络/一致性/运维成本，先让单体边界清晰。
2. Q：绞杀者模式是什么？ A：在单体前加路由，把新/待拆模块做成独立服务逐步替代旧实现。
3. Q：数据库怎么拆？ A：先逻辑隔离（分 schema/禁 JOIN），再物理隔离（独立库），CDC 迁移。
4. Q：微服务拆分判断标准？ A：独立变更频繁、资源画像不同、团队按域 ownership 才拆。
5. Q：模块化单体好处？ A：规避分布式成本，又攒下清晰边界，是微服务的安全起点。
6. Q：跨服务 JOIN 怎么解决？ A：API 组合或 CQRS 读模型，不在应用层拼 JOIN。
7. Q：无状态化改造是什么？ A：Session/缓存/定时任务/ID 外置，让服务实例可复制可拆分。
