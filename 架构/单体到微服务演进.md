# 单体到微服务演进（Evolutionary Architecture）

> 本篇是「[系统架构](../架构/系统架构.md)」中「架构决策矩阵」与「演进式架构」的实战展开：如何从**一个能跑的单体**，安全地长成**微服务/模块化单体**，而不是一上来就拆。覆盖拆分顺序、数据库拆分、绞杀者模式与反模式。
>
> 配套：限界上下文见「[DDD/上下文映射](../DDD/上下文映射与子域.md)」，事务一致性见「[系统架构·数据一致性](../架构/系统架构.md)」「[基础知识/分布式系统](../基础知识/分布式系统.md)」。

---

## 〇、本体介绍

「微服务」不是起点，而是**演化的结果**。过早微服务化会引入分布式复杂性（网络、一致性、运维），小团队扛不住。**演进式架构**主张：先让单体内部模块边界清晰，再按需把真正需要独立演进/扩展的模块拆出去。本篇给一条可落地的迁移路线。

---

## 一、为什么不要一上来就微服务

- **分布式铁律**：网络不可靠、延迟、分区、最终一致，全部是新增成本。
- **运维爆炸**：每个服务要独立部署/监控/链路追踪，小团队被拖垮。
- **数据一致性变难**：原来一个事务，现在要 Saga/消息。
- 结论：**单体不是原罪，混乱的单体才是**。先把单体写「边界清晰」。

---

## 二、演进路线（五步）

```mermaid
flowchart LR
    A[混乱单体] --> B[模块化单体]
    B --> C[提取公共能力/中台]
    C --> D[绞杀者拆服务]
    D --> E[按需独立数据库]
    E --> F[微服务/多运行时]
```

### 步骤 1：模块化单体（Modular Monolith）
- 在单体内用**包/模块**划清限界上下文（见 DDD），模块间只通过明确定义的接口调用，**禁止跨模块直接查表**。
- 好处：规避分布式成本，又攒下清晰边界，为拆分铺路。

### 步骤 2：提取横切/公共能力
- 把认证、日志、通知、文件等抽成公共模块/共享内核，避免每个模块各写一套。

### 步骤 3：绞杀者模式（Strangler Fig）拆服务
- 不一次性重写，而是**在单体前加一层路由/网关**，把新功能或待拆模块做成独立服务，逐步「绞杀」旧实现。
- 路由按路径/上下文把流量导向新服务，旧代码逐步下线。

**绞杀者切流落地细节（面试追问最密的部分）**：

```
灰度 1% → 5% → 20% → 50% → 100%（每个阈值停留观察 1~3 天）
```

- **切流控制**：网关按「用户 ID 哈希 / Header 标签 / 权重」切流；切流后**新旧并行校验**（同一请求同时打新旧两端，比对结果 diff）——正确性确认后再放大比例；
- **回滚条件预设**：切流前就定好「错误率 > 0.5% / p99 超 SLO / diff 不一致率 > 阈值」即回滚，回滚只是改路由权重，不涉及代码回退；
- **影子库校验**：新服务的数据写入先落影子表/影子库，跑一段时间对账（行数、金额、状态分布）确认一致再转正；
- **数据迁移窗口**：选低峰期（凌晨）迁移大表；外键改应用层校验；序列/分布式 ID 先换（见[分库分表与数据迁移](../分库分表与数据迁移/)）；
- **老代码退役**：新服务 100% 承接后，**删除**旧实现与旧表（留着 = 双份维护 + 双份出错面），删除是绞杀者的最后一刀。

### 步骤 4：数据库拆分（最难）
- 先**逻辑隔离**：同一库内按模块分 schema/表，禁止跨模块 JOIN。
- 再**物理隔离**：把高频/独立演进模块的表迁到独立库，通过 **API/事件** 而非直接查表交互。
- 数据同步：用 CDC（如 Canal/Debezium）或双写 + 校验，平滑迁移。

### 步骤 5：按需求独立扩展
- 只有「需要独立扩容/独立技术栈/独立团队 ownership」的模块才彻底独立成微服务；其余保留模块化单体。

## 三、拆分的判断标准

| 信号 | 该拆 | 不该拆 |
|------|------|--------|
| 某模块频发变更、独立发版 | ✅ | — |
| 某模块资源画像不同（CPU/IO 密集） | ✅ | — |
| 团队按域划分 ownership | ✅ | — |
| 只是「听说微服务好」 | — | ❌ |
| 模块间强事务耦合 | — | ❌（先解耦再拆） |
| 团队 < 10 人 | — | ❌（运维扛不住） |

---

## 四、数据库拆分反模式

- **分布式事务滥用**：跨服务长事务 → 改 Saga/最终一致。
- **共享库强耦合**：拆了服务却还共用一个库、互查表 → 没真正解耦。
- **跨服务 JOIN**：把 SQL JOIN 搬到应用层拼 → 性能差，应改为 API 组合或 CQRS 读模型。
- **一次性大爆炸迁移**：停机重写风险极高 → 必须绞杀者渐进。

---

## 五、数据与一致性过渡

- **双写期**：新旧库同时写，读仍走旧，校验一致后切读。
- **读模型（CQRS）**：跨域查询用派生读库/ES，避免实时跨服务查。
- **事件驱动**：模块间通过领域事件解耦（见「[DDD/战术设计·领域事件](../DDD/战术设计.md)」）。

## 六、组织侧：康威定律

> 系统结构会复制团队沟通结构。拆分服务前，先确认团队是否已按域划分（see「[DDD 落地·组织适配](../DDD/落地.md)」）。否则「服务边界」与「团队边界」错位，必然返工。

### 7.1 状态处理：拆出去的服务「无状态化改造」

服务拆分时最常卡住的不是代码，而是**状态**——这些「隐形状态」要先外置才能拆：

| 状态 | 拆前现状 | 拆后方案 |
|------|----------|----------|
| 会话 Session | 单体内存 | Redis 集中存储（或 JWT 无状态化） |
| 本地缓存 | JVM 内缓存 | 独立缓存服务（Redis/多级缓存，见[高并发实战](高并发架构实战.md)） |
| 定时任务 | 单体 cron 全局一份 | 独立任务服务 + 分布式锁（保证仅一个实例执行） |
| 分布式 ID | 自增主键 | 雪花 ID/号段模式（见[分库分表与数据迁移](../分库分表与数据迁移/)） |
| 单例/静态变量 | 进程内全局 | 外置为显式依赖（DB/缓存/配置） |

> 原则：**「能被复制出去的进程」才能被拆分**——拆服务前先完成无状态化改造，否则拆完每个实例行为不一致，排查成本翻倍。

### 7.2 模块化单体自己的坑（别从「大泥球」拆成「分布式单体」）

- **隐式耦合复发**：模块间不守「只走接口」，悄悄共享工具类/静态变量/缓存 key → 边界名存实亡（用 ArchUnit 等工具门禁，见[系统架构](系统架构.md)第八节）；
- **部署单元过大**：任何模块发版都重启整个单体 → 变更爆炸半径没缩小，「拆分红利」为零——若此痛点强烈，恰恰说明该拆独立服务；
- **一个库的宿命**：模块化单体再干净，数据库还是共享的——跨模块事务天然存在，拆库时依然要过第五节的坎；
- **2025 争论的客观答案**：「模块化单体 vs 微服务」不是二选一信仰——**同一系统可以长期混合**（核心交易留单体，扩展热点拆服务）；Prime Video 等「从微服务退回单体」的案例证明的是「别为拆而拆」，不是「单体永远对」。

## 八、服务间交互模式选型

| 模式 | 同步/异步 | 适用 | 代价 |
|------|----------|------|------|
| REST/gRPC 同步调用 | 同步 | 实时查询、强依赖 | 链路超时/级联 |
| 消息事件（Kafka/RabbitMQ） | 异步 | 解耦、可重放 | 最终一致、去重 |
| 事件溯源 + CQRS | 异步 | 审计/复杂域 | 学习成本高 |
| BFF 聚合层 | 同步 | 客户端编排 | 多一层维护 |

> 选型心法：**查用同步，改发事件**——读链路保实时，写链路保解耦；同一模块内优先同步，跨模块优先异步（对应「数据库拆分反模式」的解决路径）。

## 九、面试高频追问

1. Q：为什么不建议一上来微服务？ A：分布式带来网络/一致性/运维成本，小团队扛不住；先让单体边界清晰。
2. Q：绞杀者模式是什么？ A：在单体前加路由，把新/待拆模块做成独立服务逐步替代旧实现，而非大爆炸重写。
3. Q：数据库怎么拆？ A：先逻辑隔离（分 schema/表、禁跨模块 JOIN），再物理隔离到独立库，用 API/事件交互，CDC 平滑迁移。
4. Q：微服务拆分判断标准？ A：独立变更频繁、资源画像不同、团队按域 ownership 才拆；强事务耦合/小团队不宜拆。
5. Q：分布式事务怎么处理？ A：优先最终一致（Saga/消息），避免跨服务长事务；强一致场景才用 TCC。
6. Q：康威定律与拆分关系？ A：系统结构复制团队沟通结构，拆服务前先按域划分团队，否则边界错位返工。
7. Q：模块化单体好处？ A：规避分布式成本，又攒下清晰边界，是微服务的安全起点。
8. Q：跨服务 JOIN 怎么解决？ A：改 API 组合或建 CQRS 读模型（派生库/ES），不在应用层拼 JOIN。
