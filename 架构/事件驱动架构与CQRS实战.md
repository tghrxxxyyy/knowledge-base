# 事件驱动架构与 CQRS 实战

> 本文系统讲解事件驱动架构（EDA）与命令查询职责分离（CQRS）的设计原则、实现模式、一致性取舍与踩坑。结合前序架构文档，本文聚焦"用事件串联服务"与"读写模型分离"的工程落地。

## 1. 什么是事件驱动架构

事件驱动架构以"事件（Event）"作为系统间通信的核心媒介：某服务完成一件事后，发布一个"已发生"的事件，其他关心该事件的服务自行订阅并响应。服务间不直接调用，而是通过这些事件解耦。

典型角色：

- **事件生产者（Producer）**：产生并发布事件。
- **事件通道（Broker）**：消息队列（Kafka/RocketMQ/Pulsar）承载事件。
- **事件消费者（Consumer）**：订阅事件并执行业务。

## 2. 事件 vs 命令 vs 消息

- **命令（Command）**："请做某事"，有目的、期望响应（如 CreateOrder）。
- **事件（Event）**："已发生某事"，事实陈述、无响应期望（如 OrderCreated）。
- **消息（Message）**：更泛化的传输单元。

事件驱动强调"事件是过去的事实"，不可变、可追溯，命名用过去式。

## 3. 为什么用事件驱动

### 3.1 解耦

服务只依赖"事件契约"，不依赖对方接口。新增消费者不影响生产者。

### 3.2 可扩展

高峰时通过增加消费者实例横向扩容处理事件。

### 3.3 韧性

生产者不直接等待消费者，消费者宕机可在恢复后继续消费（需持久化）。

### 3.4 审计与溯源

事件天然记录"发生了什么"，可作为审计日志与事件溯源（Event Sourcing）基础。

## 4. 事件驱动的挑战

- **最终一致**：消费者状态滞后，需业务容忍短暂不一致。
- **顺序与重复**：消息可能重复投递（at-least-once），消费必须幂等。
- **调试难**：调用链分散在多个消费者，需链路追踪。
- **事件 schema 演进**：事件结构变化需兼容旧消费者。

## 5. CQRS 概念

CQRS（Command Query Responsibility Segregation）将"写（命令）"与"读（查询）"模型分离：

- **写模型**：聚焦领域行为、一致性、聚合。
- **读模型（投影/Projection）**：为查询优化的扁平化视图。

二者可用不同存储、不同模型，甚至不同服务。

## 6. CQRS 与事件驱动的结合

典型组合：

1. 写侧接收 Command，更新聚合，产生 Domain Event。
2. 事件发布到 Broker。
3. 读侧消费者订阅事件，更新读模型（如物化视图、ES 索引）。
4. 查询直接读读模型，快且不打扰写侧。

这就是"事件驱动 + CQRS"的经典落地：事件驱动负责传播，CQRS 负责读写分离。

## 7. 事件溯源（Event Sourcing）

### 7.1 思想

不存"当前状态"，而存"导致状态变化的全部事件序列"。当前状态 = 从初始状态重放所有事件。

### 7.2 优点

- 完整审计：每一次变化可追溯。
- 可回放：重放事件可重建任意时间点状态，便于调试与临时分析。
- 时间旅行：可"回到过去"看当时状态。

### 7.3 代价

- 状态查询需重放或维护投影（读模型），重放成本高。
- 事件模型演进复杂（旧事件 schema 与新逻辑兼容）。
- 学习曲线陡，非所有业务需要。

### 7.4 适用

金融交易、账本、需要强审计与回放的系统；普通 CRUD 业务上 Event Sourcing 往往过度。

## 8. 一致性保证

### 8.1 至少一次投递

消息队列常见语义，消费者必须幂等（见分布式事务章节的幂等策略）：

- 事件带唯一 ID，消费记录去重。
- 消费动作本身幂等（如 upsert）。
- 用事务消息/本地消息表保证"业务成功 + 事件发出"一致。

### 8.2 顺序

- 同聚合的事件需保序（按聚合 ID 分区），避免乱序导致状态错。
- 跨聚合不强求全局序。

### 8.3 消费滞后

- 监控消费 lag，告警堆积。
- 设计补偿：消费失败进死信队列（DLQ）人工处理。

## 9. 事件 Schema 治理

- **版本化**：事件带 schema 版本，兼容新增字段。
- **契约测试**：生产者与消费者对事件结构做契约校验。
- **演进策略**：新增可选字段、旧字段标记废弃、避免删除/改语义。
- **注册中心**：事件目录，便于发现与治理。

## 10. 落地组件示例

```
[写服务] --Command--> [聚合] --DomainEvent--> [Kafka]
                                                    |
                          ┌─────────────────────────┼──────────────┐
                          ▼                         ▼              ▼
                   [读模型投影A]              [读模型投影B]    [审计/分析]
                   (MySQL 视图)               (Elasticsearch)
                          │                         │
                          ▼                         ▼
                      [查询API]                 [搜索API]
```

## 11. 何时不该用

- 简单 CRUD、团队小、实时性要求强一致：直接同步调用更简单。
- 事件链过深导致难以追踪：应控制事件传播深度。
- 消费幂等难以保证的关键路径：需谨慎设计。

## 12. 与 Saga 的关系

跨服务的长事务可用事件驱动编排 Saga：每步完成后发事件，下一步消费者执行并可能发下一事件，失败则发补偿事件。事件驱动天然适配 Saga 的编排式实现。

## 13. 常见踩坑

1. **消费不幂等**：重复事件导致重复扣款/重复发通知。
2. **事件命名混乱**：既有命令式又有事件式，语义不清；统一用过去式事实命名。
3. **强一致期望落空**：业务假设事件即时可见，实际有 lag，需改交互。
4. **事件过于细碎**：一个操作发十个事件，消费者复杂；应发有业务意义的领域事件。
5. **无死信队列**：消费失败消息丢失或反复阻塞；应 DLQ + 告警。
6. **Schema 破坏性变更**：改字段语义致旧消费者误处理；需版本与契约测试。
7. **过度 Event Sourcing**：普通业务强行事件溯源，复杂度爆炸。

## 14. 实施建议

- 从"有明确业务语义的领域事件"起步（OrderPaid、UserRegistered）。
- 先保证至少一次投递 + 幂等消费。
- 读模型按需投影，查询走读模型。
- 用链路追踪串联跨服务事件流。
- 不盲目 Event Sourcing，先用"事件通知 + CQRS 读模型"过渡。

## 15. 小结

事件驱动 + CQRS 是构建可扩展、解耦系统的强组合：事件传播变化、CQRS 分离读写、事件溯源提供审计与回放。但其代价是最终一致、幂等设计与可观测性要求。落地铁律：**事件用事实过去式命名、消费必须幂等、读模型为查询优化、Schema 必须治理**。简单业务不必强行事件化。
