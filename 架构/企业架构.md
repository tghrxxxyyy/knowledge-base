# 企业架构

> 企业架构（Enterprise Architecture, EA）关注的是**整个企业的业务与技术蓝图**：如何把战略、组织、流程、数据、应用、基础设施串成一张可治理、可演进的网。如果说系统架构管「一个系统怎么造」，企业架构管的是「公司有哪些能力、怎么沉淀、怎么不重复造轮子、怎么管风险」。

**比喻**（来自一线 EA 实践者）：企业架构是技术管理者的「**导航系统**」——看清全局、规划路径、规避风险、提升效率。它不是选择题，而是**组合拳**。

---

## 一、什么是企业架构（与系统架构的区别）

| 维度 | 企业架构 | 系统架构 |
| --- | --- | --- |
| 范围 | 跨系统、跨组织、跨业务线 | 单个系统 |
| 视角 | 战略对齐、能力复用、治理 | 结构、通信、质量属性 |
| 时间 | 数年战略 | 数月~数年 |
| 关键干系人 | CEO/CTO、业务负责人、架构委员会 | 开发团队、Tech Lead |
| 产出 | 蓝图、标准、参考架构、治理流程 | 架构图、ADR、模块边界 |

企业架构的三大价值：**对齐战略与 IT**、**降低重复建设**、**管控转型风险**。

---

## 二、主流企业架构框架

业界有三大「必知」标准，定位互补：

> **TOGAF 告诉你「怎么做」；Zachman 帮你「查是否周全」；ArchiMate 让大家「说同一种语言」**。

### 1. TOGAF（The Open Group Architecture Framework）

- 由 The Open Group 于 1995 年发布，**全球采用最广**的 EA 框架。
- 核心是 **ADM（架构开发方法）**——一个八阶段循环：
  - **A 架构愿景**：定目标、拿高层支持。
  - **B 业务架构**：梳理业务流程，对齐业务目标。
  - **C 信息系统架构**：拆成**数据架构** + **应用架构**。
  - **D 技术架构**：选技术栈、定标准。
  - **E 机会与方案**、**F 迁移规划**、**G 实施治理**、**H 架构变更管理**。
- 配套：内容元模型、架构库（Architecture Repository）、**架构委员会**、Enterprise Continuum（复用参考架构）。
- **第 10 版（2022）** 重大现代化：拆成「基础内容 + 系列指南」，强调**模块化、敏捷、业务架构、安全**，可迭代应用 ADM，不再是「瀑布式重型文档」。
- **适用**：大型企业数字化转型、IT 治理、合规要求高的行业（金融等）。

### 2. Zachman 框架

- John Zachman（IBM）1987 年提出，本质是**本体/分类模型**而非方法。
- **6×6 矩阵**：6 个疑问词（What/How/Where/Who/When/Why）× 6 个干系人视角（规划者→实施者）。
- 不规定「怎么做」，只保证**覆盖完整、不遗漏**（类似元素周期表——保证元素齐全，但不给配方）。
- **适用**：完整性自检、咨询范围界定、教学。

### 3. ArchiMate

- The Open Group 的**开放建模语言**，与 TOGAF 对齐。
- 三层模型：**业务层 / 应用层 / 技术层**，用统一图形符号描述元素与依赖关系。
- 价值在于**可视化沟通**——让业务、开发、架构师用同一套语言对话。
- 开源工具：[archimatetool/archi](https://github.com/archimatetool/archi)（见第十节）。

### 4. 其他常见框架/标准

- **FEAF / DoDAF**：美国联邦 / 国防部体系。
- **Gartner EA 方法论**：偏咨询与能力评估。
- **BIAN**：银行业专用模型。
- **DAMA-DMBoK2**：数据管理知识体系，企业数据架构的基石方法论。

## 三、TOGAF ADM 落地实战（组合拳）

不同规模企业的打法（来自一线经验）：

| 企业规模 | 推荐组合 | 重点 |
| --- | --- | --- |
| 大型（1000+） | TOGAF + ArchiMate | 建完整架构治理体系，先试点后推广 |
| 中型（100–1000） | ArchiMate 为主 + 轻量 TOGAF | 先解最痛的业务流程建模 |
| 小型（<100） | 简化 ArchiMate | 核心系统架构图，避免过度工程 |

**落地成功的四个关键**：
1. **高层支持是前提**（CEO/CTO 背书 + 专门架构团队）。
2. **渐进实施是方法**（从关键领域切入，小步快跑）。
3. **工具支持是保障**（建模工具 + 架构知识库 + 版本管理）。
4. **人才培养是根本**（内部架构师培养 + 最佳实践社区）。

> 经验之谈：不要追求完美；架构是**演进过程**不是一次性项目；沟通比技术更重要；价值导向（每次决策都问「对业务有什么用」）。

## 四、数据中台（Data Middle Platform）

### 概念与由来

「中台」战略由**阿里巴巴**在 2015 年前后提出（「大中台，小前台」），数据中台是其数据侧落地：把分散在各业务线的数据**打通、治理、沉淀为共享资产**，向上支撑前台灵活创新。

- 方法论基座：**OneData**（阿里，统一数据标准/维度/指标）+ DAMA 数据治理理念。
- 能力闭环：**数据集成 → 开发 → 治理 → 资产 → 服务（API/BI）**。
- 与数仓/数据湖的关系：中台是**治理 + 服务层**，湖仓是底层**存储与计算底座**，中台让数据「看得见、找得到、敢用、好用」。

### 代表产品（商业）

- **瓴羊 Dataphin**（阿里云）：源自阿里十余年实践，AI 驱动建模、湖仓一体、50+ 数据源，2025 年获 DAMA 数据治理优秀产品奖。
- **腾讯云 WeData**、**华为云 DataArts Studio**、**网易数帆 EasyData**、**Talend Data Fabric**。

### 开源技术底座（自建中台常用）

| 能力 | 开源项目 |
| --- | --- |
| 元数据 / 数据目录 / 血缘 | [datahub-project/datahub](https://github.com/datahub-project/datahub)（#1 开源 AI 数据目录）、[apache/atlas](https://github.com/apache/atlas)（Hadoop 生态元数据/血缘） |
| 数据集成 / 同步 | [apache/seatunnel](https://github.com/apache/seatunnel)（批流一体集成） |
| 调度 | [apache/dolphinscheduler](https://github.com/apache/dolphinscheduler)（分布式可视化调度） |
| BI 可视化 | [apache/superset](https://github.com/apache/superset) |
| 湖仓格式 | Apache Iceberg / Hudi / Paimon |

> DataHub 可作为数据中台的「元数据层」标杆：以 Kafka 实时更新、构建统一元数据图，提供列级血缘、数据资产地图、数据合同与 AI（MCP）集成，已被 3000+ 组织用于生产。

## 五、业务中台（Business Middle Platform）

### 概念

把**通用业务能力**（用户、商品、订单、支付、营销等）从具体业务中**沉淀为共享服务**，让前台（各业务线/C 端应用）像搭积木一样快速复用，避免「每个业务重造一套」。

- 与微服务的关系：**中台是组织/能力复用的战略，微服务是其技术实现风格之一**。中台更强调「哪些能力该共享、怎么治理」。
- 阿里 COLA 架构：阿里开源的 **COLA（Clean Object-oriented & Layered Architecture，整洁面向对象分层架构）** 是业务中台落地的参考框架——强调以业务为核心、解耦外部依赖、分离业务复杂度与技术复杂度，并提供 archetype 与通用组件（状态机、扩展点、异常处理等），帮助治理混乱的业务应用。详见 [系统架构](系统架构.md) 第十节与 [alibaba/COLA](https://github.com/alibaba/COLA)。

### 风险警示

- **「中台焦虑症」**：不顾业务实际盲目建中台，把不该共享的也抽象，反而拖慢交付。
- 过度抽象、中心化过重会导致「中台变成新瓶颈」。中台应按**真实复用诉求**生长，而非自上而下强制。

## 六、Data Mesh（领域驱动的数据架构）

由 ThoughtWorks 的 **Zhamak Dehghani** 在 2020 年前后提出，被视为数据中台的「去中心化对照面」，常被类比为数据界的**微服务**。

### 四大原则

1. **领域导向的分布式数据所有权**：数据归属离它最近的领域团队，而非集中数据团队。
2. **数据即产品（Data as a Product）**：领域把数据当产品经营，需可发现、可理解、可互操作、安全、可复用。
3. **自助式数据基础设施平台**：平台团队提供「自助建数据产品」的能力（存储、编排、血缘、体验层），领域团队自助产出。
4. **联邦计算治理（Federated Governance）**：全局标准（语义、质量、访问）由各领域共同定义，而非一刀切集中管控。

### 与数据中台对比

| 维度 | 数据中台 | Data Mesh |
| --- | --- | --- |
| 治理形态 | 偏**集中**治理 + 统一服务平台 | 偏**领域自治** + 数据产品 |
| 所有权 | 集中数据团队 | 领域团队 |
| 适用 | 强管控、标准化诉求高的企业 | 多领域、强自治、规模化数据资产 |

两者并非互斥：很多企业在「集中治理 + 领域自治」之间找平衡，DataHub 这类元数据/发现层在两种模式下都是关键拼图。

## 七、企业架构治理

- **架构委员会（Architecture Board）**：决策重大架构方向、做合规评审。
- **架构库与标准**：参考架构、技术选型白名单、API 规范集中管理可复用。
- **ADR**：与企业内各系统共享「决策记录」机制（见[系统架构](系统架构.md)第八节）。
- **架构度量**：架构健康度、技术债务、复用率等指标化，避免「建完无人管」。
- **与敏捷/DevOps 协同**：现代实践多用**轻量 TOGAF**——保留治理原则，把 ADM 迭代化嵌入敏捷交付与云迁移。

### 7.1 ADR 实战（企业级决策记录的完整打法）

ADR（Architecture Decision Record）是治理里**最能立刻落地**的一环：

**模板（一句话背景 + 决策 + 后果）**：

```markdown
# ADR-0023：订单中心引入 Seata 分布式事务

## 背景
订单-库存-支付三服务跨库更新，出现多次金额不一致事故（P1 ×2）。
## 选项
A. 2PC（强一致但阻塞、协调者单点）  
B. TCC（隔离性好但每服务手写三方法，改动大）  
C. Seata AT（零侵入，自动镜像回滚） ✅
## 决策
选 C：存量系统快速接入，业务代码改动最小；接受全局锁带来的吞吐下降。
## 后果
- 正面：接入成本 1 人周；一致性事故归零。
- 负面：写路径 RT +20%；全局锁在大促高并发下需压测验证。
- 复查：大促后评估是否降级为「本地事务表 + 对账」。
```

**治理要点**：
- **编号与存储**：`adr/NNNN-标题.md` 随代码库版本管理（ADR 即代码）；「Accepted / Superseded」状态标记，被替换的 ADR 不删（留历史）；
- **评审节奏**：轻量评审（架构委员会周会 10 分钟过一遍新 ADR）+ 重大决策（跨系统/高成本）走正式评审会；
- **门槛**：凡是「影响多个系统 / 影响数据模型 / 有安全含义」的决策必须 ADR，小决策不进（避免文档债）；
- **闭环**：ADR 与 ArchUnit/架构库联动——决策落代码，代码反哺决策（「规则自动化」见[系统架构](系统架构.md)第八节）。

### 7.2 TOGAF vs 敏捷：正面回答「重文档冲突」

- **冲突本质**：TOGAF 传统 ADM 是「先建模后实施」（瀑布式）；敏捷是「小步迭代」。生搬硬套必然互相拖累；
- **调和姿势（业界共识）**：**裁剪 + 节奏化**——把 ADM 的 A（架构愿景）/B/C/D（业务-信息-技术架构）当作「每个迭代期初的轻量活动」，E/F（机会与迁移）当作「交付积压」，G/H（实施与变更）嵌入 Sprint；文档只产「决策级」产物（愿景、基线、目标、路线图 4 件），不产文档瀑布；
- **SAFe 关系**：规模化敏捷的「企业层（ART 规划、组合管理）」天然是轻量 EA 的执行载体——SAFe 解决「怎么组织」，EA 解决「往哪建」；
- **判断标准**：EA 文档的价值 = 被决策引用次数 / 维护成本——没人引用的文档就是债务，裁剪掉。

## 八、企业架构与 AI（趋势）

- **AI 驱动的数据治理**：如 Dataphin 的 DataAgent，自动盘点数据资产、智能建模、自然语言取数。
- **AIOps / 智能运维**：异常检测、根因分析自动化。
- **Agentic 数据架构**：DataHub 通过 MCP 让 AI Agent 安全获取权威元数据，成为 Agent 时代数据架构的「上下文底座」。
- **架构资产智能化**：用 LLM 辅助生成架构文档、影响分析、合规检查。

### 8.1 AI 时代 EA 转型（2025-2026 完整视角）

- **AI 是新的「架构资产」**：LLM/Agent/RAG 不是项目，是**企业能力层**——EA 要把「AI 能力地图」（哪个域用哪个模型、数据从哪来、权限到哪、成本谁付）纳入架构库与治理（对应[系统架构](系统架构.md)十二节）；
- **ADM 被 AI 增强**：AI 辅助架构愿景生成、基线盘点（扫描代码生成现状架构）、影响分析（改一个系统波及哪些）、合规检查（自动比对架构库标准）——2026 年 EA 工具标配；
- **AI 治理进 EA 治理**：模型准入（选型白名单）、数据权限（RAG 即数据出口，权限同业务系统）、幻觉与评测（SLO 看护）、成本治理（token 预算）都成为架构评审项；
- **组织影响**：平台团队（Platform + AI Infra）与业务架构师（Capability + AI 场景）分工——「AI 架构师」成为新角色，但**决策框架不变**：能力对齐业务、资产可复用、治理管边界。

## 九、架构图怎么画（企业级）

- **ArchiMate 三层图**（业务/应用/技术）：企业级沟通的标准语言，配合 [Archi](https://github.com/archimatetool/archi) 建模。
- **能力地图（Capability Map）**：从业务能力的视角组织企业能力，避免被组织架构带偏。
- **价值流（Value Stream）+ 产品思维**：把「战略→能力→系统」串起来，让架构对齐价值。
