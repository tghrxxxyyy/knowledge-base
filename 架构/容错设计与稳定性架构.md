# 容错设计与稳定性架构

> 本文梳理系统"如何在故障中保持可用"的工程体系：冗余、超时、重试、熔断、限流、降级、隔离、幂等、优雅降级与故障演练。与高并发、SRE 章节互补，本文聚焦"容错模式本身"。内容基于工业实践，参数以业务为准。

## 1. 容错的第一性原理

- 故障必然发生：网络会抖、依赖会挂、机器会坏。
- 目标不是"不出故障"，而是"故障不影响用户或影响可控"。
- 核心思路：冗余 + 隔离 + 快速失败 + 优雅降级。

## 2. 冗余与多副本

- 无状态服务多实例，挂一个还有别的。
- 数据多副本（主从、多 AZ），避免单点。
- 但冗余带来一致性成本（见共识章节）。

## 3. 超时（Timeout）

### 3.1 为什么必须超时

- 无超时的调用会一直阻塞，线程/连接耗尽，故障扩散。
- 下游慢 → 上游线程占满 → 上游也慢 → 雪崩。

### 3.2 设多少

- 基于下游 P99 延迟 + 网络抖动余量。
- 太短误杀正常请求，太长拖累资源。
- 不同时长设不同超时（读/写/连接）。

## 4. 重试（Retry）

### 4.1 何时重试

- 瞬时故障（网络抖、连接断）值得重试。
- 业务错误（参数错、余额不足）不应重试。

### 4.2 正确做法

- 仅对幂等操作重试（见幂等）。
- 指数退避 + 抖动（避免重试风暴）。
- 限制次数与总时长。
- 重试传播：上层重试会放大下游压力，需整体评估。

### 4.3 重试风暴

- 多层服务各自重试 → 请求量指数放大。
- 缓解：退避、限流、熔断、重试预算（如每次只放 10% 重试）。

## 5. 熔断（Circuit Breaker）

### 5.1 状态机

- Closed：正常，统计失败率。
- Open：失败率超阈值，快速失败，不再打下游。
- Half-Open：一段时间后放少量试探，成功则回 Closed，失败回 Open。

### 5.2 作用

- 保护上游线程不被慢下游拖死。
- 给下游恢复时间。
- 与重试配合：熔断打开后停止重试。

### 5.3 阈值

- 失败率（如 50%）、最小请求数、熔断时长、half-open 试探数。
- 需按业务调，避免过灵敏敏震荡。

## 6. 限流（Rate Limit）

### 6.1 算法

- 计数器（固定窗口）：简单但有临界突刺。
- 滑动窗口：更平滑。
- 漏桶：恒定速率流出，整形。
- 令牌桶：允许突发，平均限速（最常用）。

### 6.2 维度

- 用户、IP、接口、租户。
- 分布式限流用 Redis + Lua 原子。

### 6.3 超限处理

- 拒绝（429）、排队、降级。

## 7. 降级（Degrade）

- 关键路径保，非关键关。
- 例：大促关掉推荐/评论，保下单支付。
- 方式：开关配置、功能开关（Feature Flag）、默认兜底值。
- 降级需预案，而非故障临场想。

## 8. 隔离（Bulkhead）

### 8.1 思想

- 像船舱隔离，一处漏水不沉全船。
- 资源隔离防止故障扩散。

### 8.2 手段

- 线程池隔离：不同依赖用不同池，一依赖满不影响其他。
- 信号量隔离：限制并发数。
- 进程/容器隔离：关键服务独立部署。
- 租户隔离：大客户独享资源。

## 9. 幂等（Idempotency）

- 重试/重复请求结果一致，无副作用翻倍。
- 实现：唯一键、去重表、状态机、Token。
- 见分布式事务章节详述。
- 凡是可能被重试/重发的写，必须幂等。

## 10. 优雅降级与兜底

- 缓存挂 → 返回默认/稍后再试，而非全挂。
- 推荐挂 → 返回热门列表。
- 支付渠道挂 → 切备用渠道或排队。
- 原则是"部分可用 > 全不可用"。

## 11. 故障传播与雪崩

### 11.1 雪崩链

- 同步调用链上，一环慢 → 占用上游资源 → 上游慢 → 连锁。
- 同步阻塞是雪崩温床。

### 11.2 阻断

- 异步化（MQ）切断同步链。
- 熔断 + 限流 + 隔离 + 超时 四件套。
- 资源配额防止单依赖耗尽。

## 12. 异地多活与容灾

- 多活：多处同时服务，一地故障切流量（见多集群章节）。
- 单元化：按用户维度分片，故障只影响部分用户。
- RTO/RPO：恢复时间/数据丢失目标。

## 13. 故障演练（Chaos）

- 主动注入故障：杀进程、断网络、增延迟、填磁盘。
- 验证容错是否真有效（而非纸面）。
- 从可控（非高峰、小范围）到真实。
- 配套监控与止血预案。

## 14. 可观测支撑容错

- 没有监控，容错是盲飞。
- 指标：依赖延迟、错误率、熔断状态、限流拒绝数。
- 链路追踪：定位哪环慢/错。
- 告警：超时/熔断/限流触发即告警。

## 15. 设计清单

- 每个外部调用有没有超时？
- 重试是否幂等 + 退避 + 限量？
- 下游是否熔断？
- 关键依赖是否隔离？
- 高峰是否限流降级？
- 重复请求是否幂等？
- 预案是否演练过？

## 16. 常见踩坑

1. **无超时调用**：线程耗尽，雪崩起点。
2. **重试不幂等**：重复扣款/发券。
3. **重试无退避**：重试风暴打垮下游。
4. **熔断阈值乱设**：过灵导致正常流量被拒，过钝不起作用。
5. **限流只限单实例**：分布式下全局超限；需用集中式限流。
6. **降级无预案**：故障才想怎么降，手忙脚乱。
7. **隔离缺失**：一依赖慢拖垮全部。
8. **演练走过场**：从不真注入，预案无效。

## 17. 框架与实现

- 熔断：Resilience4j / Hystrix 思路（Hystrix 已进入维护）。
- 限流：网关层（APISIX/Kong）+ 应用层（Guava RateLimiter / Sentinel）。
- 隔离：线程池/信号量 + 容器资源限制。
- Sentinel：限流/熔断/降级一体，国内常用。

## 18. 与稳定性文化

- 容错是设计出来的，不是救火救出来的。
- 把"失败是常态"作为设计前提。
- 每依赖都假设会挂，问"挂了怎么办"。

## 19. 小结

容错设计是一套"假设会失败"的防御体系：超时防阻塞、重试退避防风暴、熔断快速失败、限流保护自身、降级保核心、隔离防扩散、幂等防重复、演练验真。四件套（超时+重试+熔断+限流）加隔离与降级，是稳定性的基石。记住：同步阻塞是雪崩温床，异步与隔离是扩散阻断器，且所有容错都需可观测与演练兜底。
