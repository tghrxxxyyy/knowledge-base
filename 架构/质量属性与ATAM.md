# 质量属性与 ATAM（Quality Attributes）

> 本篇补全「[系统架构](../架构/系统架构.md)」里被原则带过、却最该系统化掌握的一块：**架构的「非功能需求」如何定义、权衡与评估**。功能需求决定「做什么」，质量属性决定「做得好不好」。
>
> 配套：韧性模式见「[系统架构·韧性](../架构/系统架构.md)」，可观测性见「[云原生/可观测性](../云原生/可观测性.md)」。

---

## 〇、本体介绍

架构师真正的功力，不在画分层图，而在**对质量属性的取舍**：性能、可用、安全、可扩展、可维护性之间永远有冲突（如「强一致」与「高可用」天然矛盾）。本篇给出质量属性的定义框架，以及业界最成熟的评估方法 **ATAM**。

---

## 一、质量属性全景

| 属性 | 含义 | 典型度量 | 常见 tactic |
|------|------|----------|-------------|
| **性能/时延** | 响应时间、吞吐 | RT(p99)、QPS/TPS | 缓存、异步、分片、索引 |
| **可用性** | 持续服务能力 | 几个 9（99.95%） | 冗余、故障转移、限流 |
| **可靠性** | 无故障完成任务 | MTBF/MTTR | 重试、幂等、校验 |
| **可扩展性** | 增资源提能力 | 线性度 | 无状态、水平扩展、分片 |
| **安全性** | 保密/完整/可用 | 漏洞数、合规 | 鉴权、加密、审计、最小权限 |
| **可维护性** | 易修改理解 | 变更成本 | 模块化、清晰边界、测试 |
| **可观测性** | 可监控定位 | 指标/日志/链路覆盖 | Metrics/Log/Trace |
| **可移植性** | 跨环境部署 | 环境耦合度 | 容器化、配置外置 |

---

## 二、质量属性场景（QAS, Quality Attribute Scenario）

评估质量属性不能只说「要快、要稳」，要用**场景六元组**精确描述：

> **刺激源**（谁）→ **刺激**（做什么）→ **制品**（作用对象）→ **环境**（何时）→ **响应**（系统怎么做）→ **响应度量**（指标多少）

例：*"在正常负载下（环境），**1000 并发用户（源）** 提交订单（刺激）到**交易服务（制品）**，系统应在 **p99 < 200ms（度量）** 内返回（响应）*。"

只有能量化的场景，才能指导设计与验收。

---

## 三、质量属性间的冲突与权衡

- **一致性强 vs 可用高**：CAP 下分区时只能选 CP 或 AP（见「[分布式系统](../基础知识/分布式系统.md)」）。
- **安全 vs 性能**：加密/鉴权有开销，需分层（内网轻、外网重）。
- **可维护 vs 性能**：过度抽象降性能，过度优化降可维护，找平衡点。
- **可扩展 vs 简单**：过早微服务化增加运维复杂度。

> 架构决策本质是**在约束下对质量属性排序**，没有银弹。

---

## 四、ATAM（架构权衡分析方法）

ATAM 是 SEI 提出的成熟架构评估方法，核心是**在决策前暴露风险与权衡点**。流程（精简版）：

1. **呈现**：架构师讲业务目标、质量属性优先级、架构方案。
2. **场景驱动**：干系人提出质量属性场景（QAS），排序重要度。
3. **映射 tactic**：每个场景对应哪些架构决策（tactic）能满足。
4. **找敏感点（Sensitivity）**：单个质量属性高度依赖的某个决策（如「可用性依赖数据库主从切换」）。
5. **找权衡点（Trade-off）**：一个决策同时影响多个（常冲突的）质量属性的点（如「分库分表提升扩展性与性能，但牺牲跨分片一致性与查询」）。
6. **风险与短板**：标识未覆盖的高优场景（风险）、当前架构的薄弱点。
7. **产出**：质量属性效用树 + 风险清单 + 权衡点记录，供决策。

```mermaid
flowchart LR
    A[业务目标] --> B[质量属性优先级]
    B --> C[架构方案]
    C --> D[质量场景QAS]
    D --> E[映射tactic]
    E --> F[敏感点/权衡点]
    F --> G[风险清单+决策]
```

## 五、实战：用效用树组织质量属性

把质量属性建成一棵**效用树**（Utility Tree），便于评审：

```
质量属性（根）
├─ 性能
│  ├─ 场景：1000 并发下单 p99<200ms   [重要度 H / 难度 M]
│  └─ 场景：报表导出 < 5s
├─ 可用性
│  ├─ 场景：单节点宕机无感知（99.95%）
│  └─ 场景：发布零停机
└─ 安全
   ├─ 场景：越权访问拦截率 100%
   └─ 场景：敏感数据加密存储
```
每个叶子标注**重要度（H/M/L）**与**实现难度（H/M/L）**，优先保障「高重要+低难度」，重点攻关「高重要+高难度」。

## 六、常见评估陷阱

- 只评估功能，不评估质量属性 → 上线即事故。
- 质量属性无度量 → 无法验收，沦为口号。
- 只列场景不找权衡点 → 决策时仍拍脑袋。
- 干系人缺席 → 优先级失真（业务/运维/安全诉求不同）。

## 面试高频追问

1. Q：质量属性和功能需求区别？ A：功能决定「做什么」，质量属性决定「做得好不好」（快/稳/安全/易改）。
2. Q：质量属性场景六元组？ A：刺激源、刺激、制品、环境、响应、响应度量，用来精确可量化描述需求。
3. Q：敏感点和权衡点区别？ A：敏感点是单个属性高度依赖的决策；权衡点是同时影响多个冲突属性的决策（如分库分表）。
4. Q：ATAM 产出什么？ A：质量属性效用树、风险清单、权衡点记录，辅助架构决策。
5. Q：一致性和可用性怎么权衡？ A：CAP 分区下二选一；按业务选 CP（资金）或 AP（社交），或最终一致折中。
6. Q：为什么说没有银弹架构？ A：质量属性间天然冲突，架构是在约束下对属性排序与取舍。
7. Q：怎么量化「可用性」？ A：用几个 9（99.9%/99.95%/99.99%），对应年停机时长，结合 MTTR 设计冗余与故障转移。
8. Q：质量属性优先级定错了会怎样？ A：把资源投错方向（如过度优化性能却忽视安全），上线暴露短板、返工成本高。

## 七、可用性量化对照表（记牢）

| 可用性 | 年停机 | 月停机 | 典型系统 |
|--------|--------|--------|----------|
| 99% | 87.6 小时 | 7.3 小时 | 内部工具 |
| 99.9% | 8.76 小时 | 43.8 分钟 | 一般业务 |
| 99.95% | 4.38 小时 | 21.9 分钟 | 电商主链路 |
| 99.99% | 52.6 分钟 | 4.38 分钟 | 支付/核心交易 |
| 99.999% | 5.26 分钟 | 26.3 秒 | 电信/交易撮合 |

> 面试谈「可用性」时直接背这张表：目标几个 9 → 年停机预算 → 反推冗余与切换方案（呼应 [SRE·SLO](../SRE与稳定性工程/01-SRE理念与SLI-SLO-ErrorBudget.md) 的错误预算思维）。

## 八、架构评审实操（把 ATAM 用起来）

一次轻量架构评审会（1~2 小时）的议程：

1. **主讲 10 分钟**：业务目标 + 架构图 + 关键决策；
2. **干系人提问**：业务、运维、安全、测试各自视角追问；
3. **现场产出效用树**：列出 top 场景，标重要度/难度；
4. **查敏感点**：每个场景问「哪个决策决定它成败」；
5. **查权衡点**：每个决策问「它牺牲了谁」；
6. **结论**：风险清单 + 决策记录（AD-R）+ 待办责任人。

> 常见收获：发现「没人负责的隐式权衡」（如缓存一致性靠口头约定）、「假设未验证」（如并发量没压测）——这两类正是架构事故的温床。
