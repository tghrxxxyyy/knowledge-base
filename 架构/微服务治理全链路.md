# 微服务治理全链路

## 〇、本体介绍

**微服务治理**：在微服务架构落地的全生命周期中，对服务的注册发现、配置管理、流量管控、容错降级、可观测性、安全认证等进行**统一管控**的能力体系。没有治理的微服务是"分布式单体"——比单体更复杂、更脆弱。

**核心矛盾**：
1. 服务数量爆炸后，**服务间调用关系网状化**，无治理则雪崩；
2. 业务要**快速迭代**（频繁发布）vs 系统要**稳定**（变更风险），需要灰度/回滚能力；
3. 每个服务各自实现治理逻辑导致**重复开发 + 不一致**，需要统一基础设施。

**核心主线**：注册发现 → 配置中心 → API 网关 → 限流熔断 → 分布式追踪 → 安全认证。

## 一、服务注册与发现

### 1.1 架构

```mermaid
graph LR
    P[服务提供者] -->|注册| REG[注册中心: Nacos/Consul/etcd]
    C[服务消费者] -->|订阅| REG
    REG -->|推送/拉取| C
    C -->|负载均衡| P
```

### 1.2 注册中心对比

| 维度 | Nacos | Consul | etcd | Eureka |
|------|-------|--------|------|--------|
| 一致性协议 | Raft/Distro | Raft | Raft | AP（最终一致） |
| 配置管理 | ✅ 内置 | ✅ 需配合 | ❌ 无 | ❌ 无 |
| 健康检查 | TCP/HTTP/MySQL | TCP/HTTP/Script | 心跳 | 心跳 |
| UI 控制台 | ✅ | ✅ | ❌ | ✅ |
| 适用场景 | Java 系、配置+发现 | 多语言、强一致 | K8s 底座 | 已停更，不推荐 |

### 1.3 服务实例元数据

```json
{
  "serviceName": "order-service",
  "instanceId": "192.168.1.10:8080:DEFAULT",
  "ip": "192.168.1.10",
  "port": 8080,
  "weight": 100,
  "healthy": true,
  "metadata": {
    "version": "v2.1.0",
    "region": "cn-east-1",
    "cluster": "gray"
  }
}
```

> 口诀：**"服务启动注册，心跳保活；消费者订阅，负载均衡调；元数据路由，灰度隔离好。"**

### 1.4 云原生时代：注册中心 vs K8s 服务发现（面试最高频）

K8s 里其实有「免费的服务发现」，那还要 Nacos/Consul 吗？取决于**你需不需要应用级元数据**：

| 维度 | K8s 原生（Service + CoreDNS） | 独立注册中心（Nacos/Consul） |
|------|-------------------------------|------------------------------|
| 发现粒度 | 抽象到 Service（负载均衡器），实例透明 | 实例级（IP:port + 权重 + 元数据） |
| 元数据 | 只有标签，无业务元数据 | 版本/灰度/机房/权重，可参与路由 |
| 灰度/金丝雀 | 需要额外配置（Traffic Split/Istio） | 原生按权重/标签路由 |
| 配置管理 | 无（ConfigMap 非动态推送） | 内置动态配置（Nacos 一体） |
| 跨集群 | 弱（联邦复杂） | 多注册中心/多集群容易 |
| 依赖 | 无额外组件 | 多一个高可用组件要运维 |

**选型答案**：
- 纯 K8s + 云原生栈（Go/新项目）→ **K8s Service + Gateway API**，别引入注册中心；
- Java 系微服务（Spring Cloud）、要灰度路由、要动态配置 → **Nacos**（配置 + 发现一体）；
- 已有 K8s 但要用灰度权重路由 → **K8s Service + 网关侧路由**或 Istio，而不是给注册中心硬塞进 K8s；
- Nacos 3.x 已支持 gRPC 直连与 K8s 环境适配，但「注册中心是否值得留」本质是**元数据路由需求**问题。

### 1.5 配置变更灰度与回滚（配置中心的正确用法）

- **灰度标签**：配置带 `env=gray` 标签 → 先推到灰度实例（观察日志/指标）→ 再全量；Nacos 的「灰度推送」即此模型；
- **变更前校验**：配置有 Schema（如 JSON Schema）校验 + 变更预览（diff），防手滑把 `maxPool=100` 改成 `1000`；
- **回滚**：每次变更自动留存版本 + 一键回滚；**回滚后要确认服务已重新加载**（监听回调完成才算生效）；
- **审计**：谁在什么时间改了什么配置 → 事件溯源到人（合规要求）；
- 与[单体到微服务演进](单体到微服务演进.md)的治理配套清单联动：拆完服务第一步就是配齐注册中心 + 配置中心。

## 二、配置中心

### 2.1 核心能力

| 能力 | 说明 |
|------|------|
| **动态配置** | 运行时修改配置无需重启（@RefreshScope / 监听回调） |
| **版本管理** | 配置变更历史 + 回滚能力 |
| **灰度发布** | 按实例/IP/标签灰度推送配置 |
| **环境隔离** | dev/test/prod 多环境独立配置 |
| **加密存储** | 敏感配置（密码/密钥）加密 |

### 2.2 配置优先级

```
启动参数 > 环境变量 > 远程配置中心 > 本地配置文件 > 默认值
```

### 2.3 Nacos 配置示例

```yaml
# Data ID: order-service.yaml, Group: DEFAULT_GROUP
order:
  timeout-minutes: 30
  max-retry: 3
  features:
    new-payment: true        # 功能开关：新支付渠道
    risk-check: true         # 功能开关：风控校验
```

```java
@RefreshScope  // 配置变更自动刷新
@Configuration
public class OrderConfig {
    @Value("${order.timeout-minutes:30}")
    private int timeoutMinutes;

    @Value("${order.features.new-payment:false}")
    private boolean newPaymentEnabled;
}
```

## 三、API 网关

### 3.1 网关职责

```mermaid
graph LR
    CL[客户端] --> GW[API 网关]
    GW -->|路由| S1[订单服务]
    GW -->|路由| S2[用户服务]
    GW -->|路由| S3[支付服务]
    GW -->|统一| AUTH[鉴权]
    GW -->|统一| LIMIT[限流]
    GW -->|统一| LOG[日志]
```

### 3.2 网关对比

| 维度 | Spring Cloud Gateway | Kong | APISIX | Nginx + Lua |
|------|---------------------|------|--------|-------------|
| 语言 | Java | Lua (C) | Lua (C) | C + Lua |
| 性能 | 中 | 高 | 高 | 最高 |
| 插件生态 | 中 | 丰富 | 丰富 | 中 |
| 动态配置 | Nacos 集成 | Admin API | Admin API | 需 reload |
| 适用 | Java 系微服务 | 多语言、高性能 | 多语言、高性能 | 边缘网关 |

### 3.3 关键能力

| 能力 | 做法 |
|------|------|
| **路由** | 路径/Header/参数匹配转发到对应服务 |
| **鉴权** | JWT/OAuth2 统一校验，透传用户身份到下游 |
| **限流** | 令牌桶/漏桶，按 API/用户/服务维度 |
| **灰度** | 按 Header/权重/用户分组路由到不同版本 |
| **协议转换** | HTTP ↔ gRPC，外部 REST ↔ 内部 RPC |

### 3.4 K8s 原生网关：Gateway API 与 Envoy Gateway（2024-2026 新坐标）

传统网关对比表之外，K8s 生态的「网关新标准」：

- **Gateway API**（K8s SIG-Network 标准，取代 Ingress）：`Gateway`（基础设施）与 `HTTPRoute`（路由规则）分离——**路由规则归应用团队、基础设施归平台团队**，天然对齐多团队治理；
- **Envoy Gateway**：基于 Envoy 的 Gateway API 参考实现，直接提供 熔断/限流/重试/灰度 能力，替代「Spring Cloud Gateway 三件套」里的一部分；
- **Istio Gateway + VirtualService**：服务网格网关（与 sidecar 同源），适合「网关 + 网格一体化」；
- **选型结论**：新 K8s 项目网关三选一——**APISIX/Kong（功能全、生态熟）** / **Envoy Gateway（标准向、原生 K8s）** / **Istio（要网格就顺手用）**；Ingress Controller 定位退为「边缘接入」。
- 细节见[云原生/K8s网络深挖](../云原生/K8s网络深挖.md)。

## 四、限流熔断与降级

### 4.1 限流算法

| 算法 | 思路 | 适用 |
|------|------|------|
| **计数器** | 固定窗口内计数 | 简单场景 |
| **滑动窗口** | 多个小窗口滑动 | 避免突刺 |
| **令牌桶** | 匀速产生令牌，请求消耗令牌 | 允许突发 |
| **漏桶** | 请求进入桶，匀速流出 | 严格匀速 |

### 4.2 熔断器状态机

```mermaid
stateDiagram-v2
    CLOSED --> OPEN: 失败率超阈值
    OPEN --> HALF_OPEN: 超时后试探
    HALF_OPEN --> CLOSED: 试探成功
    HALF_OPEN --> OPEN: 试探失败
```

- **CLOSED**：正常请求，统计失败率
- **OPEN**：快速失败（fallback），不调用下游
- **HALF_OPEN**：放少量请求试探，成功→CLOSED，失败→OPEN

### 4.3 降级策略

| 场景 | 降级策略 |
|------|----------|
| 推荐服务超时 | 返回热门推荐（缓存兜底） |
| 支付服务异常 | 关闭在线支付，仅保留货到付款 |
| 风控服务超时 | 放行（宁可漏过不可误杀） |
| 库存服务异常 | 降级为展示"库存紧张"，异步校验 |

> 口诀：**"限流保下游，熔断防雪崩；降级兜底走，功能可牺牲。"**

## 五、分布式追踪

### 5.1 追踪模型

```mermaid
sequenceDiagram
    participant C as 客户端
    participant G as 网关
    participant OS as 订单服务
    participant US as 用户服务
    participant DB as 数据库
    C->>G: GET /orders/123 (traceId=abc)
    G->>OS: 调用 (traceId=abc, span=1)
    OS->>US: 查询用户 (traceId=abc, span=1.1)
    US-->>OS: 返回用户
    OS->>DB: 查订单 (traceId=abc, span=1.2)
    DB-->>OS: 返回订单
    OS-->>G: 返回结果
    G-->>C: 响应
```

### 5.2 核心概念

| 概念 | 说明 |
|------|------|
| **Trace** | 一次完整请求链路（全局唯一 traceId） |
| **Span** | 链路中的一个操作（含开始/结束时间） |
| **Parent Span** | 调用方 Span（构建父子关系） |
| **Annotation** | 关键事件（cs/sr/ss/cr = 客户端发送/接收，服务端接收/发送） |

### 5.3 采样策略

| 策略 | 做法 | 适用 |
|------|------|------|
| **全量采样** | 100% 采集 | 调试阶段、小规模 |
| **概率采样** | 按固定比例（如 10%） | 大规模生产 |
| **尾部采样** | 只采集慢请求/错误请求 | 排障优先 |
| **自适应采样** | 根据 QPS 动态调整 | 推荐 |

### 5.4 可观测性 2025-2026 升级：OTel 统一 + eBPF 零埋点

- **OTel 是地基**：`traceparent`（W3C 上下文传播）跨语言自动透传，OTLP 统一采集，语义约定让指标/日志/Trace 对齐——2025 年起「自带 SDK 手工打点」已被 OTel SDK 自动埋点取代；
- **eBPF 零埋点观测**：Cilium Hubble、DeepFlow、SkyWalking eBPF 探针**不动业务代码**即可拿到服务拓扑、调用链、TCP 指标——适合**存量系统/第三方组件**（数据库、MQ、网关）补盲区；
- **Trace 与 Metrics 联动**：Trace 管「慢在哪一跳」，Metrics 管「趋势与告警」，Log 管「细节」——三者靠 `service.name + trace_id` 关联（OTel 语义约定）；
- **AI 驱动根因分析**：把 Trace/Metrics 喂给 LLM 做根因定位（如「跨 20 跳的调用链自动圈出异常节点」）已是 2026 工具标配；
- **验证手段**：全链路压测（见[测试与代码质量/05-全链路压测](../测试与代码质量/05-性能与负载测试.md)）与混沌工程（见[测试与代码质量/08-混沌工程](../测试与代码质量/08-测试数据Mock服务与混沌工程.md)）是治理效果的「考试」；
- OTel 基础设施细节见[云原生/可观测性](../云原生/可观测性.md)。

### 5.5 服务网格现状（2024-2026 演进：从 Sidecar 到 Ambient）

- **Istio 2024 底回归 CNCF，项目健康度回稳**；2025 起 **Ambient Mesh（Sidecarless，数据面 ztunnel 节点级代理）GA**——数据面每节点一个代理而非每 Pod 一个，**资源开销降 50-90%**，适合「只要东西向安全 + mTLS + 遥测」的中大规模集群；
- **Sidecar 仍在**：需要完整 L7 治理（重试/熔断/流量镜像）时 classic sidecar 更强；两种模式可在同一网格共存（按命名空间选择）；
- **大厂「去 mesh 化」反思**：部分团队因性能损耗/排障复杂度退回「SDK 治理（如 Spring Cloud）+ 网关」——mesh 值不值，取决于你的**服务间安全需求**（多团队多语言强隔离 → mesh；单语言小规模 → SDK 更轻）；
- 落点：**网格不是治理的全部**——注册发现、配置中心、网关、追踪是基础四件套，网格是「安全 + 高级流量治理」的进阶件。详见[云原生/ServiceMesh](../云原生/ServiceMesh.md)。

## 面试高频问题（15+ 条）

1. **微服务治理包括哪些？** 注册发现、配置中心、API 网关、限流熔断降级、分布式追踪、安全认证。
2. **注册中心怎么选？** Nacos（Java 系+配置）、Consul（多语言+强一致）、etcd（K8s 底座）。
3. **配置中心的作用？** 动态修改配置无需重启，支持灰度推送、版本回滚、环境隔离。
4. **API 网关职责？** 路由、鉴权、限流、灰度、协议转换、统一日志。
5. **限流算法有哪些？** 计数器、滑动窗口、令牌桶（允许突发）、漏桶（严格匀速）。
6. **熔断器原理？** 三态机：CLOSED（统计失败率）→ OPEN（快速失败）→ HALF_OPEN（试探）。
7. **降级和熔断的区别？** 熔断是失败后快速失败；降级是主动关闭非核心功能。
8. **分布式追踪怎么实现？** 全局 traceId 透传 + Span 父子关系 + 采样存储（Jaeger/SkyWalking）。
9. **采样策略怎么选？** 全量（调试）、概率（大规模生产）、尾部（排障优先）。
10. **JWT 和 Session 区别？** JWT 无状态不存储；Session 有状态需存储（Redis）。
11. **服务间认证怎么做？** mTLS（零信任）或网关透传 JWT/身份头。
12. **灰度发布怎么实现？** 网关按 Header/权重/用户分组路由到不同版本。
13. **功能开关怎么实现？** 配置中心动态配置 + @RefreshScope 实时生效。
14. **服务雪崩怎么防？** 限流（入口）+ 熔断（调用链）+ 降级（兜底）+ 隔离（线程池）。
15. **Service Mesh 和传统治理的区别？** Mesh 将治理逻辑下沉到 Sidecar，业务代码无侵入。
16. **Nacos 和 Eureka 区别？** Nacos 支持 CP/AP 切换 + 内置配置管理；Eureka 仅 AP 且已停更。
