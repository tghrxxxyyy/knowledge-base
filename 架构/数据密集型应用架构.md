# 数据密集型应用架构

> 板块：架构 　|　 返回：[README](README.md)
> 适用：读写混合、海量数据、复杂查询、实时与离线融合的系统（参考《Designing Data-Intensive Applications》）。

数据密集型应用（与计算密集型相对）的瓶颈在**数据：量、速度、多样性**，以及由此衍生的可靠性、可扩展性与可维护性。本文梳理核心权衡与模式。

## 一、三大设计目标

| 目标 | 含义 | 手段 |
|------|------|------|
| 可靠性（Reliability） | 容错、持久、正确 | 冗余、备份、校验 |
| 可扩展性（Scalability） | 负载增长仍可工作 | 分片、复制、缓存 |
| 可维护性（Maintainability） | 易运维、易演进 | 抽象、可观测、文档 |

## 二、负载特征与度量

- **负载描述**：读写比、QPS、数据量、峰值系数、热点分布。
- **性能指标**：吞吐量、延迟（P50/P99/P999）、资源利用率。
- **取舍**：优化平均值会掩盖长尾（P99 更反映体验）。

## 三、数据模型与存储选型

| 模型 | 代表 | 适用 |
|------|------|------|
| 关系型 | MySQL/PG | 强一致事务、复杂查询 |
| 文档 | MongoDB | 嵌套、schema 灵活 |
| 键值 | Redis | 极简高速访问 |
| 列族 | HBase/Cassandra | 海量写、宽表 |
| 图 | Neo4j | 关系密集 |
| 搜索 | ES | 全文/聚合 |
| 时序 | InfluxDB | 时间序列 |
| 数仓/OLAP | ClickHouse/Doris | 分析 |

> 没有银弹：用**多存储组合（polyglot persistence）**，每类数据选最合适的存储。

## 四、复制（Replication）

- **目的**：冗余、读扩展、就近。
- **单 Leader**：写集中、读可扩展；Leader 故障需选主。
- **多 Leader**：写可多地，但冲突需处理（冲突解决）。
- **无 Leader**：节点对等，写冲突靠后续协调（Dynamo 风格）。
- **同步 vs 异步**：同步强一致但慢；异步快但可能丢/滞后。

## 五、分区/分片（Partitioning）

- **按 key 范围/哈希**：均匀分布。
- **热点**：单一热点 key 落到同一分片 → 加盐/复合 key。
- **再平衡**：扩容时数据重新分布，需平滑（一致性哈希/翻倍扩容）。
- **路由**：请求如何知道数据在哪 → 目录服务或哈希直算。

## 六、事务与一致性

- 单机事务靠 DB；分布式需 2PC/Saga/共识。
- **线性一致 vs 最终一致**：依业务选（见[CAP定理与一致性模型](CAP定理与一致性模型.md)）。
- **脏读/幻读**：隔离级别权衡。

## 七、批处理与流处理

```
数据源 → 批处理(离线,T+1,全量) → 数仓 → BI
数据源 → 流处理(实时,增量) → 实时特征/告警
```

- **批处理**：Spark/Flink Batch，高吞吐、全量。
- **流处理**：Kafka+Flink，低延迟、增量、exactly-once 难。
- **Lambda/Kappa**：批流双算（Lambda）或纯流（Kappa）架构。

## 八、派生数据与不变性

- **派生数据**：缓存、索引、物化视图、搜索索引都是"源数据的派生"，可丢失重建。
- **不变事件源（Event Sourcing）**：存不可变事件流，状态由重放得到，便于溯源与重建。
- 思路：把"可变状态"转为"追加日志 + 派生视图"。

## 九、可观测与演进

- 数据流水线需端到端监控（延迟、积压、错误）。
- Schema 演进：前向/后向兼容，避免破坏消费者（Avro/Protobuf + Schema Registry）。

## 十、常见坑

1. **单存储通吃** → 不合适的数据用错存储；多存储组合。
2. **盲目最终一致** → 钱/库存出错；关键路径保强一致。
3. **热点分片** → 单分片过载；key 加盐/再平衡。
4. **Schema 不兼容** → 上下游断裂；兼容演进 + Registry。
5. **派生数据是真相** → 缓存当源丢数据；源是真相，派生可重建。
6. **忽略长尾延迟** → 平均好看 P99 爆炸；关注分位。
