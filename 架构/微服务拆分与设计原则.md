# 微服务拆分与设计原则

> 板块：架构 　|　 返回：[README](README.md)
> 覆盖：何时微服务、拆分维度、边界与契约、通信、数据自治、服务网格、反模式。

微服务不是银弹，而是用"分布式复杂性"换"开发/部署敏捷性"的权衡。拆得好敏捷翻倍，拆得差变成"分布式单体"更痛苦。本文讲清何时拆、怎么拆、边界与反模式。

## 一、微服务解决的问题

单体（Monolith）在团队/代码规模变大后暴露问题：

- 改动牵一发动全身，编译/测试/发布慢（大泥球）。
- 技术栈绑定，无法局部升级（想换语言/框架牵一发动全身）。
- 扩展只能整体扩，资源浪费（热点模块被迫和冷模块一起扩）。
- 模块边界模糊，代码腐化，新人上手难。

微服务把系统按业务能力拆成可独立开发/部署/扩展的服务，换取：

- **独立部署**：一个服务改了不影响其他（发布频率提升）。
- **独立扩展**：热点服务单独扩容。
- **技术异构**：不同服务可用不同语言/存储。
- **团队自治**：小团队端到端负责。

> **康威定律**：系统架构会反映组织的沟通结构。微服务有效的前提是"小团队独立负责服务"（Two Pizza Team）。组织不调整，光拆服务没用。

## 二、何时该拆（与不该拆）

| 信号 | 该拆 | 不该拆 |
|------|------|--------|
| 团队规模 | 多团队、模块耦合重 | 小团队（<10 人） |
| 变更频率 | 各模块变更频率差异大 | 业务未稳定、边界模糊 |
| 负载 | 不同模块负载差异大需独立伸缩 | 整体负载均匀 |
| 技术 | 需要异构技术栈 | 单一技术栈够用 |
| 阶段 | 领域已清晰 | 还在探索期（先单体） |

- **演进路径**：模块化单体 → 抽出边界清晰的模块 → 逐步服务化（**绞杀者模式 strangler fig**：在新服务里包裹旧功能，逐步替换）。
- **过早微服务是小团队常见灾难**：本该专注业务，却被服务治理、链路追踪、分布式事务耗尽精力。
- 经验：先用「模块化单体 + 清晰模块边界」撑到确实需要拆分时再拆。

## 三、拆分维度

| 维度 | 说明 | 优点 |
|------|------|------|
| 业务能力（Business Capability） | 订单、库存、用户、支付各一服务 | 贴近领域、稳定 |
| DDD 限界上下文 | 按领域划界（见 [DDD/战术设计精要](../DDD/战术设计精要.md)） | 边界与通用语言一致 |
| 变更频率/负载 | 热点模块独立（如秒杀服务） | 便于单独扩容 |
| 数据源 | 按数据归属拆 | 数据自治、解耦 |

- **避免按技术层拆**（如 User-Service 管所有用户表、Order-Service 管所有订单相关）→ 跨服务调用频繁，仍是分布式单体。
- **避免按 CRUD 拆**：一个实体的增删改查分四个服务 → 无端增加网络调用。

## 四、服务边界与契约

- **明确接口契约**：API 定义（OpenAPI / gRPC proto），前后兼容（加字段不删、不改类型、不改语义）。
- **版本治理**：消费者驱动，废弃走 Deprecation 周期，避免强断（如 `/v1` → `/v2` 并存过渡）。
- **团队 ownership**：每个服务一个团队负责（You build it, you run it）。
- **边界清晰**：对外暴露的能力稳定，内部实现可自由重构而不影响消费者。
- **API 网关**：统一入口、认证、限流、路由（见 [技术选型/服务框架与RPC选型](../技术选型/服务框架与RPC选型.md)）。

```protobuf
// 契约优先：gRPC 接口定义即契约
service OrderService {
  rpc CreateOrder(CreateOrderReq) returns (CreateOrderResp);
}
message CreateOrderReq {
  string user_id = 1;
  repeated Item items = 2;
}
```

## 五、通信方式

| 方式 | 协议 | 特点 | 适用 |
|------|------|------|------|
| 同步 | REST / gRPC / GraphQL | 简单、即时、但易成长链 | 必须即时返回的链路 |
| 异步 | MQ（Kafka/RocketMQ） | 解耦、削峰、最终一致 | 非核心、可延迟 |
| 事件驱动 | Event Bus | 松耦合、可扩展 | 状态变更广播 |

- **同步**：REST/gRPC，简单但易形成长调用链；必须配超时 + 熔断（见 [高可用架构设计实战](高可用架构设计实战.md)）。
- **异步**：消息队列解耦、削峰、最终一致（见 [消息队列选型与对比](../技术选型/消息队列选型与对比.md)）。
- **服务发现**：注册中心（Nacos / etcd / Consul / Eureka）+ 客户端/服务端负载均衡。
- **原则**：能异步则异步（解耦、削峰），同步仅用于必须即时返回的链路，且全程带超时/熔断/降级。

```
同步链: A → B → C → D   (任一环慢/挂，链路受影响，需熔断)
异步链: A ──事件──▶ 消费者B (解耦, A不关心B何时处理)
                    └──────▶ 消费者C
```

## 六、数据自治（关键中的关键）

- **每服务自有数据库**（Database per Service），不跨库直接访问（否则回到耦合）。
- 跨服务数据通过 **API 调用** 或 **事件同步**（CQRS 读模型可冗余）。
- 跨服务事务用 **Saga / TCC / 事务消息**保证最终一致（见 [支付系统核心设计](../场景设计/支付系统核心设计.md)、[CAP定理与一致性模型](CAP定理与一致性模型.md)）。
- **共享数据库是反模式**：多服务写同一库 → 隐式耦合，schema 改一处全崩。
- 需要跨服务查询时：用 API 组合（API Composition）或 CQRS 物化视图（异步同步读模型）。

```sql
-- 错误：订单服务直接连用户库
SELECT * FROM user_db.user WHERE id = ?;   -- 跨库耦合！
-- 正确：通过用户服务 API 获取，或订阅用户变更事件维护本地冗余表
```

## 七、服务网格与治理

- 服务间认证、限流、熔断、追踪下沉到 Sidecar（见 [云原生/ServiceMesh深入](../云原生/ServiceMesh深入.md)）。
- 治理要素：注册发现、配置中心、限流降级、链路追踪、灰度路由。
- 把横切关注点从业务代码剥离，业务更纯粹，治理统一。

```
业务容器 + Sidecar(Envoy)
        │ 所有进出流量经 Sidecar
        ▼
   mTLS / 限流 / 熔断 / 重试 / 追踪 统一处理
```

## 八、可观测与交付

- 统一日志/指标/链路，跨服务串联 **trace_id**（见 [SRE/可观测性三支柱实战](../SRE/可观测性三支柱实战.md)）。
- CI/CD + 容器化 + 蓝绿/金丝雀（见 [云原生/GitOps与持续交付](../云原生/GitOps与持续交付.md)）。
- 没有可观测性的微服务 = 黑盒，出问题无从下手。
- 配置中心（Nacos/Apollo）统一管理配置，避免散落。

## 九、分布式单体（反模式）

- **表现**：服务很多，但一次需求要改 5 个服务、共享数据库、强耦合。本质是「没拆对」。
- **成因**：按技术层拆、边界误判、共享库强依赖、数据库共享、团队按层而非按域组织。
- **解法**：重新按领域划界、数据解耦、事件驱动，逐步绞杀旧结构。

| 真微服务 | 分布式单体 |
|---------|-----------|
| 服务可独立部署 | 改一处动全身 |
| 数据自治 | 共享数据库 |
| 团队自治 | 跨团队强协调 |
| 故障隔离 | 一损俱损 |

## 十、常见坑

1. **一上来就微服务** → 小团队被分布式复杂度拖垮（先单体清晰再拆）。
2. **共享数据库** → 服务间隐式耦合，失去独立部署。
3. **链式同步调用无超时** → 雪崩（加熔断/异步）。
4. **分布式事务滥用 2PC** → 性能差、阻塞，改用最终一致（Saga/TCC/事务消息）。
5. **边界不清反复改** → 先 DDD 事件风暴理清领域。
6. **忽略可观测** → 跨服务问题无法定位，排障靠猜。
7. **没有 API 版本治理** → 一改接口全链路崩。
8. **团队按技术层组织** → 和按域拆的服务冲突，沟通成本爆炸。

## 十一、设计原则 checklist

- [ ] 单一职责、高内聚低耦合（按域而非按层）。
- [ ] 数据自治、API 契约稳定、有版本治理。
- [ ] 异步解耦优先、同步带超时/熔断/降级。
- [ ] 独立部署与扩缩容。
- [ ] 团队 ownership（You build it, you run it）。
- [ ] 完善可观测（日志/指标/链路 + trace_id）。
- [ ] 演进式拆分（绞杀者模式），不一步到位。

## 十二、组织与架构的匹配

```
组织（按域的小团队）
   │ 康威定律
   ▼
架构（按域拆的微服务）
   ├─ 订单团队 → 订单服务（自有库）
   ├─ 库存团队 → 库存服务（自有库）
   └─ 用户团队 → 用户服务（自有库）
```

> 架构演进 = 组织演进的一部分。先调组织边界，再调服务边界。
