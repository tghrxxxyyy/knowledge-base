# 微服务拆分与设计原则

> 板块：架构 　|　 返回：[README](README.md)
> 覆盖：何时微服务、拆分维度、边界、通信、数据自治、常见反模式。

微服务不是银弹，而是用"分布式复杂性"换"开发/部署敏捷性"的权衡。拆得好敏捷翻倍，拆得差变成"分布式单体"更痛苦。本文讲清何时拆、怎么拆、边界与反模式。

## 一、微服务解决的问题

单体（Monolith）在团队/代码规模变大后：
- 改动牵一发动全身，编译/测试/发布慢。
- 技术栈绑定，无法局部升级。
- 扩展只能整体扩，资源浪费。
- 模块边界模糊，代码腐化。

微服务把系统按业务能力拆成可独立开发/部署/扩展的服务，换取敏捷与弹性。

> **康威定律**：系统架构会反映组织的沟通结构。微服务有效的前提是"小团队独立负责服务"。

## 二、何时该拆（与不该拆）

- **该拆**：团队多、模块耦合重、不同模块变更频率/负载差异大、需独立伸缩、技术异构需求。
- **不该拆**：早期小团队、业务未稳定、领域边界模糊（先单体清晰再拆）。
- **演进路径**：模块化单体 → 抽出边界清晰的模块 → 逐步服务化（绞杀者模式，strangler fig）。

过早微服务是小团队常见灾难：本该专注业务，却被服务治理、链路追踪、分布式事务耗尽精力。

## 三、拆分维度

- **按业务能力（Business Capability）**：订单、库存、用户、支付各一服务（推荐，贴近领域）。
- **按领域（DDD 限界上下文）**：见 [DDD/战术设计精要](../DDD/战术设计精要.md)。
- **按变更频率/负载**：热点模块独立，便于单独扩容（如秒杀服务）。
- **避免**按技术层拆（User-Service 管所有用户表）→ 仍是分布式单体，跨服务调用频繁。

## 四、服务边界与契约

- **明确接口契约**：API 定义（OpenAPI / gRPC proto），前后兼容（加字段不删、不改类型）。
- **版本治理**：消费者驱动，废弃走 Deprecation 周期，避免强断。
- **团队 ownership**：每个服务一个团队负责（You build it, you run it）。
- **边界清晰**：一个服务对外暴露的能力稳定，内部实现可自由重构。

## 五、通信方式

- **同步**：REST / gRPC，简单但易形成长调用链；必须配超时 + 熔断（见 [架构/高可用架构设计实战](高可用架构设计实战.md)）。
- **异步**：消息队列解耦、削峰、最终一致（见 [技术选型/消息队列选型与对比](../技术选型/消息队列选型与对比.md)）。
- **服务发现**：注册中心（Nacos / etcd / Consul）+ 客户端/服务端负载均衡。
- 选型见 [技术选型/服务框架与RPC选型](../技术选型/服务框架与RPC选型.md)。

原则：**能异步则异步**（解耦、削峰），同步仅用于必须即时返回的链路，且全程带超时/熔断/降级。

## 六、数据自治（关键）

- **每服务自有数据库**，不跨库直接访问（否则回到耦合）。
- 跨服务数据通过 API 或事件同步。
- 跨服务事务用 Saga / TCC / 事务消息保证最终一致（见 [场景设计/支付系统核心设计](../场景设计/支付系统核心设计.md)、[架构/CAP定理与一致性模型](CAP定理与一致性模型.md)）。
- 共享数据别用「同一个库多服务写」→ 隐式耦合，schema 改一处全崩。

## 七、服务网格与治理

- 服务间认证、限流、熔断、追踪下沉到 Sidecar（见 [云原生/ServiceMesh深入](../云原生/ServiceMesh深入.md)）。
- 治理要素：注册发现、配置中心、限流降级、链路追踪。
- 把横切关注点从业务代码剥离，业务更纯粹。

## 八、可观测与交付

- 统一日志/指标/链路，跨服务串联 trace_id（见 [SRE/可观测性三支柱实战](../SRE/可观测性三支柱实战.md)）。
- CI/CD + 容器化 + 蓝绿/金丝雀（见 [云原生/GitOps与持续交付](../云原生/GitOps与持续交付.md)）。
- 没有可观测性的微服务 = 黑盒，出问题无从下手。

## 九、分布式单体（反模式）

- **表现**：服务很多，但一次需求要改 5 个服务、共享数据库、强耦合。本质是「没拆对」。
- **成因**：按技术层拆、边界误判、共享库强依赖、数据库共享。
- **解法**：重新按领域划界、数据解耦、事件驱动，逐步绞杀旧结构。

## 十、常见坑

1. **一上来就微服务** → 小团队被分布式复杂度拖垮。
2. **共享数据库** → 服务间隐式耦合，失去独立部署。
3. **链式同步调用无超时** → 雪崩（加熔断/异步）。
4. **分布式事务滥用 2PC** → 性能差，改用最终一致。
5. **边界不清反复改** → 先 DDD 事件风暴理清领域。
6. **忽略可观测** → 跨服务问题无法定位，排障靠猜。

## 十一、设计原则 checklist

- [ ] 单一职责、高内聚低耦合。
- [ ] 数据自治、API 契约稳定。
- [ ] 异步解耦优先、同步带熔断。
- [ ] 独立部署与扩缩容。
- [ ] 团队 ownership + 可观测。
- [ ] 演进式拆分，不一步到位。
