# DDD 落地与整洁架构实战

> 本文在聚合与领域事件（见 DDD 章节）基础上，讲清 DDD 的工程落地：分层架构、整洁架构（Clean Architecture）、六边形架构、CQRS 与事件溯源结合、以及从"贫血三层"到"领域驱动"的演进路径与常见误区。

## 1. DDD 不是银弹

- DDD 是应对复杂业务领域的建模方法。
- 它不适合所有项目，简单 CRUD 用不上。
- 价值在于：统一语言、清晰边界、可演进的领域模型。
- 过度设计比不设计更危险。

## 2. 统一语言（Ubiquitous Language）

- 业务与研发用同一套术语，避免"翻译损耗"。
- 术语写进代码、文档、对话。
- 例如"订单""履约""对账"必须语义一致。
- 统一语言是 DDD 的起点，也是最难坚持的。

## 3. 分层架构

- 表现层：接口、DTO、参数校验。
- 应用层：用例编排，不含业务规则。
- 领域层：聚合、领域服务、领域事件（核心）。
- 基础设施层：DB、MQ、外部适配。
- 依赖方向：上层依赖下层，领域层不依赖基础设施（靠接口倒置）。

## 4. 整洁架构（Clean Architecture）

- 同心圆：实体 → 用例 → 接口适配 → 框架驱动。
- 依赖规则：外层依赖内层，内层不感知外层。
- 领域与用例在最内，框架/DB 在最外。
- 好处：业务逻辑不绑定 Spring/DB，可测试、可替换。

```
[Entities] ← [Use Cases] ← [Interface Adapters] ← [Frameworks/Drivers]
依赖向内，调用向外（通过接口）
```

## 5. 六边形架构（Ports & Adapters）

- 核心领域是六边形，对外暴露端口（Port）。
- 适配器（Adapter）实现端口，连接外部（DB、HTTP、MQ）。
- 驱动端适配器：Controller 调领域。
- 被驱动端适配器：领域调外部（如发消息的适配器）。
- 与整洁架构思想一致：核心是领域，边界清晰。

## 6. 应用层职责

- 应用服务编排用例：加载聚合 → 调领域行为 → 持久化。
- 不含业务规则（规则在聚合/领域服务）。
- 负责事务边界（一个用例一个事务）。
- 负责发布领域事件。

## 7. 领域服务 vs 聚合

- 聚合根承载"单一聚合内"的一致性。
- 领域服务承载"跨聚合/无状态"的领域逻辑。
- 不要把领域服务当万能筐（避免回到贫血）。
- 能用聚合解决的，不上升领域服务。

## 8. 工厂与仓库

- 工厂：复杂聚合创建（尤其含不变式初始化）。
- 仓库：聚合持久化抽象，按 ID 加载/保存。
- 仓库只存聚合，不暴露内部实体。
- 仓库接口定义在领域层，实现在基础设施层。

## 9. 与 CQRS 结合

- 写侧：聚合 + 领域事件（命令路径）。
- 读侧：投影/查询模型（查询路径）。
- 二者存储可分离（见 CQRS 章节）。
- 适合复杂读多写少、查询多样的系统。

## 10. 与事件溯源结合

- 事件即事实，聚合状态由事件重放得出。
- 事件溯源提供完整审计与回放（见事件驱动章节）。
- 普通业务慎用，金融/账本类更合。

## 11. 从贫血到充血

- 贫血：Entity 只有 getter/setter，逻辑在 Service。
- 充血：行为在聚合，Service 只编排。
- 演进：先把核心聚合找出来，把相关逻辑移入。
- 不必一步到位，渐进重构。

## 12. 限界上下文（Bounded Context）

- 大领域拆成多个上下文，各有统一语言。
- 上下文间用上下文映射（ACL 防腐层、共享内核、客户-供应商）。
- 防腐层（ACL）：隔离外部模型入侵本域。
- 微服务常对应限界上下文边界。

## 13. 战术模式清单

- 实体（有标识、有生命周期）。
- 值对象（无标识、不可变、按属性相等）。
- 聚合（一致性边界）。
- 领域服务（跨聚合逻辑）。
- 领域事件（事实通知）。
- 工厂、仓库、规格（Specification）。

## 14. 建模流程

1. 识别核心域与子域。
2. 定义限界上下文与统一语言。
3. 识别聚合与聚合根。
4. 设计领域事件。
5. 落地分层/整洁架构。
6. 渐进填充领域逻辑。

## 15. 常见误区

1. **全员 DDD**：简单模块硬上，复杂度爆炸。
2. **聚合过大**：一个聚合包一切，事务锁重。
3. **贫血依旧**：DDD 之名行事务脚本之实。
4. **领域层依赖框架**：直接 import Spring，依赖倒置失败。
5. **忽略统一语言**：代码与业务术语脱节。
6. **事件滥用**：每个字段变化都发事件，噪声大。
7. **过度事件溯源**：普通 CRUD 强行溯源，难维护。

## 16. 与微服务关系

- 限界上下文是微服务划分的自然候选。
- 但上下文 ≠ 必须独立部署，可先模块化。
- 分布式带来事务/一致性成本，别过早拆。
- 先单体内清晰上下文，再按需拆服务。

## 17. 测试策略

- 领域层单测最重（纯逻辑、快）。
- 应用层测编排与事务。
- 基础设施层用集成测试（Testcontainers）。
- 领域不依赖框架，单测极易写。

## 18. 落地建议

- 从核心域开始，不追求全覆盖。
- 先统一语言与聚合，再谈架构。
- 保持领域层纯净（无框架依赖）。
- 演进式：贫血→充血，单体→微服务。
- 领域事件驱动跨聚合最终一致。

## 20. 小结

DDD 落地 = 统一语言 + 限界上下文 + 聚合边界 + 整洁/六边形架构 + 事件驱动最终一致。核心是让领域模型承载业务规则、基础设施可替换、依赖向内。铁律：**核心域优先、聚合小且一致、领域层零框架依赖、跨聚合用事件最终一致、简单 CRUD 不必 DDD**。渐进演进胜过一步到位。
