# CAP 定理与一致性模型

> 板块：架构 　|　 返回：[README](README.md)
> 关联：[微服务拆分与设计原则](微服务拆分与设计原则.md)、[一致性协议与分布式共识深度](一致性协议与分布式共识深度.md)、[分布式事务与最终一致性实战](../场景设计/分布式事务与最终一致性实战.md)

CAP 是理解分布式系统的起点，但常被误读为"三选二"。本文讲清 CAP 的真实含义、CP/AP 取舍、一致性强度谱系、Quorum 数学、PACELC 扩展与工程选型，帮助在架构设计时做对一致性决策。

## 一、CAP 是什么

分布式系统在以下三个属性间存在约束（Brewer 2000 提出，Gilbert & Lynch 2002 形式化证明）：

| 字母 | 含义 | 直觉 |
|------|------|------|
| **C** Consistency | 一致性：每次读都拿到最新写（线性一致视角） | 像单副本 |
| **A** Availability | 可用性：每个请求都有（非错误）响应，不保证最新 | 有响应就行 |
| **P** Partition tolerance | 分区容错：网络分区（节点失联）时系统仍能工作 | 不怕断网 |

> **经典结论**：网络分区 P 在分布式系统中几乎必然出现（光缆断、机房隔离、GC 停顿、交换机故障），所以**实际是在 C 与 A 之间二选一**，而非"三选二"。不存在"CA 分布式系统"——所谓 CA 只在理论无分区（单机/强同步主从且从不分区）下成立。

## 二、为什么 P 不可舍弃

- 分布式系统跨网络，网络分区是物理必然（不是"加钱就能消除"）。
- 一旦 P 发生（节点间失联），你**要么**拒绝部分请求（牺牲 A 保 C），**要么**继续响应但可能返回旧值（牺牲 C 保 A）。
- 因此 CAP 的正确读法是：**在出现分区时，系统在 C 和 A 之间权衡**。正常无分区时，两者可兼得。

## 三、CP vs AP 怎么选

| 类型 | 含义 | 代表系统 | 适用 |
|------|------|---------|------|
| **CP** | 分区时保一致、牺牲可用 | ZooKeeper、etcd、HBase、Consul | 配置/锁/选主/金融账务 |
| **AP** | 分区时保可用、牺牲强一致 | Cassandra、DynamoDB、Eureka、Redis 主从 | 购物车、社交、缓存、点赞 |
| **CA** | 理论存在（无分区） | 单机 DB、强同步主从（假设不分区） | 非真正分布式 |

**直觉**：
- 宁可不可用也不能错的 → **CP**（钱、库存、配置、分布式锁）。
- 宁可返回旧值也不能停的 → **AP**（购物车、新闻、点赞、用户画像）。

## 四、BASE 理论（AP 的工程化）

BASE 是对 CAP 中 AP 的妥协与落地，描述"高可用 + 最终一致"的工程哲学：

- **Basically Available**：基本可用（降级、限流，不追求每次都全功能）。
- **Soft state**：软状态，允许中间态（副本间短暂不一致）。
- **Eventually consistent**：最终一致（无新写后，最终所有副本一致）。

> BASE 不是"不要一致"，而是"接受短暂不一致，保证最终收敛"。多数互联网业务是 BASE。

## 五、一致性强度谱系

```
强一致 → 线性一致 → 顺序一致 → 因果一致 → 最终一致 → 弱一致
```

| 级别 | 含义 | 实现/例子 |
|------|------|----------|
| 线性一致 Linearizable | 像单副本，全局实时有序，读必见最新已提交写 | etcd(Raft)、ZooKeeper(接近) |
| 顺序一致 | 所有节点看到相同顺序，但不保证实时 | 某些共识实现 |
| 因果一致 | 有因果关系的操作保序（评论在帖子后） | 社交、CRDT |
| 最终一致 | 无新写后，最终一致（允许延迟窗口） | DNS、MySQL 异步复制、Cassandra |
| 弱一致 | 不保证何时一致 | 缓存 TTL、CDN |

> 设计要选"**够用的最强一致性**"，而非一味追强一致（代价是可用性/性能）。多数业务最终一致即可，只有少数（账务、库存扣减）需强一致。

## 六、如何实现强一致

- **共识算法**：Raft / Paxos，保证日志复制一致（etcd、Consul 基于 Raft）。
- **Quorum（法定人数）**：W + R > N 保证读到最新（见第七节）。
- **租约 Lease**：带期限的授权，避免脑裂（如 leader 租约，租约期内唯一 leader）。
- **两阶段提交 / 严格串行**：单库内强一致；跨库需分布式事务（慎用，性能差）。

## 七、读写 Quorum 数学

- N 副本总数，W 写成功数，R 读成功数。
- **W + R > N** → 强一致读（读集与写集必相交，至少一副本既被写又被读，读到最新）。
- **W + R <= N** → 可能读到旧值（最终一致）。

| N | W | R | 语义 |
|---|---|---|------|
| 3 | 2 | 2 | 强一致（2+2>3） |
| 3 | 1 | 1 | 高可用但最终一致 |
| 5 | 3 | 3 | 强一致、容 2 故障 |
| 5 | 2 | 2 | 高可用、容 2 故障、最终一致 |

取舍：提高 W/R 增强一致但降低可用/增加延迟；降低则相反。常见：(N=3,W=2,R=2) 折中。

## 八、PACELC 扩展（更完整的视角）

CAP 只谈"分区时"的取舍，PACELC 补全了"无分区时"的取舍：

```
分区时(P):  选 A 还是 C  (CAP 部分)
无分区时(E): 选 L(延迟) 还是 C(一致)
```

- 即：无分区时，你在**延迟（L）与一致性（C）**之间权衡。选强一致（如同步复制）会增加延迟。
- 例：DynamoDB 是 PA/EL（分区保可用、平时保低延迟+最终一致）；Bigtable 是 PC/EC（都强一致）。

## 九、时钟与一致

- 物理时钟不可靠（漂移、NTP 误差），不能用于绝对因果判断。
- **逻辑时钟 Lamport**：给事件编号，保"happens-before"偏序。
- **向量时钟 Vector Clock**：能检测并发（无因果关系），用于冲突检测（如 Dynamo）。
- **TrueTime / HLC**：有界偏差的时间服务（Spanner 用 TrueTime 实现外部一致事务）。

## 十、典型中间件定位

| 系统 | 一致性 | 说明 |
|------|--------|------|
| ZooKeeper | 顺序一致（ZAB） | 协调/选主，写全序 |
| etcd | 线性一致（Raft） | 配置/KV/锁 |
| MySQL 主从 | 最终一致 | 异步复制，从库延时 |
| Kafka | 分区内有序 | 流处理语义 |
| Redis 主从 | 最终一致 | 异步复制，缓存 |
| Cassandra | 可调配（ONE/QUORUM/ALL） | 按一致性级别 |

## 十一、实践选型建议

1. **钱/库存/配置**：CP + 强一致（宁可不可用不能错），Raft 类存储。
2. **内容/社交/购物车**：AP + 最终一致（可用优先），用版本/时间戳收敛。
3. **读多写少**：缓存扛读，异步补齐，最终一致。
4. **关键链路选主/配置**：用 Raft 类保证一致性。
5. **跨服务**：用最终一致 + 幂等，避免强一致分布式事务（见 [分布式事务与最终一致](../场景设计/分布式事务与最终一致性实战.md)）。
6. **按操作定级别**：同一系统不同操作可不同级别（如元数据 CP、日志 AP）。

## 十二、常见误区

1. **认为 CAP 是「三选二」静态** → 实际是分区下 C/A 取舍。
2. **把最终一致当不一致** → 最终一致有明确收敛保证，非"永远不一致"。
3. **忽略一致性强度** → 用错存储（把缓存当源、把 AP 库当账务库）。
4. **过度追求强一致** → 牺牲可用性，系统脆弱、易雪崩。
5. **用物理时钟做因果** → 漂移导致乱序判断错误（用逻辑/向量时钟）。
6. **以为 Raft 万能** → Raft 保证日志一致，但应用层仍需处理读一致性（线性读用 ReadIndex/LeaseRead）。
