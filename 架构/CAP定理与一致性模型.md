# CAP 定理与一致性模型

> 板块：架构 　|　 返回：[README](README.md)

CAP 是理解分布式系统的起点，但常被误读为"三选二"。本文讲清 CAP 的真实含义、CP/AP 取舍、一致性强度谱系、Quorum 数学与工程选型，帮助在架构设计时做对一致性决策。

## 一、CAP 是什么

分布式系统在以下三个属性间存在约束：

- **C（Consistency）一致性**：每次读都拿到最新写（线性一致视角）。
- **A（Availability）可用性**：每个请求都有（非错误）响应，不保证是最新值。
- **P（Partition tolerance）分区容错**：网络分区（节点间失联）时系统仍能继续工作。

> 经典结论：网络分区 P 在分布式系统中几乎必然出现（光缆断、机房隔离、GC 停顿），所以**实际是在 C 与 A 之间二选一**，而非"三选二"。CA 只在理论无分区场景（单机/强同步主从）成立。

## 二、CP vs AP 怎么选

| 类型 | 含义 | 代表 | 适用 |
|------|------|------|------|
| CP | 分区时保一致、牺牲可用 | ZooKeeper、etcd、HBase | 配置/锁/金融账务 |
| AP | 分区时保可用、牺牲强一致 | Cassandra、DynamoDB、Eureka | 购物车、社交、缓存 |
| CA | 理论存在（无分区） | 单机/主从强同步 | 非分布式场景 |

直觉：宁可不可用也不能错的（钱、库存、配置）→ CP；宁可返回旧值也不能停的（购物车、点赞、新闻）→ AP。

## 三、BASE 理论（AP 的工程化）

- **Basically Available**：基本可用（降级、限流，不追求每次都全功能）。
- **Soft state**：软状态，允许中间态（副本间短暂不一致）。
- **Eventually consistent**：最终一致（无新写后，最终所有副本一致）。
- BASE 是对 CAP 中 AP 的妥协与落地，是"高可用 + 最终一致"的工程哲学。

## 四、一致性强度谱系

```
强一致 → 线性一致 → 顺序一致 → 因果一致 → 最终一致 → 弱一致
```

- **线性一致（Linearizable）**：像单副本，全局有序，最严格（etcd / Raft 实现）。
- **顺序一致**：所有节点看到相同顺序，但不保证实时。
- **因果一致**：有因果关系的操作保序（如"评论在帖子之后"）。
- **最终一致**：无新写后，最终所有副本一致（允许延迟窗口）。
- **弱一致**：不保证何时一致（如 DNS 缓存 TTL）。

设计要选"够用的最强一致性"，而非一味追强一致（代价是可用性/性能）。

## 五、如何实现强一致

- **共识算法**：Raft / Paxos，保证日志复制一致（etcd、Consul 基于 Raft）。
- **Quorum**：W + R > N（写多数 + 读多数）保证读到最新。
- **两阶段锁/事务**：单库内强一致（超出单库则需分布式事务）。
- **租约（Lease）**：带期限的授权，避免脑裂（如 leader 租约）。

## 六、如何实现最终一致

- **异步复制**：主写后异步同步从。
- **本地消息表 / 事务消息**：保证本地事务与消息原子，消费者最终处理。
- **Saga / TCC**：长事务拆成补偿步骤。
- 见 [场景设计/分布式事务与最终一致] 与 [架构/微服务拆分与设计原则](微服务拆分与设计原则.md)。

## 七、读写 Quorum 数学

- N 副本，W 写成功数，R 读成功数。
- **W + R > N** → 强一致读（读集与写集必相交，读到最新）。
- **W + R <= N** → 可能读到旧值（最终一致）。
- 例：N=3, W=2, R=2 → 强一致；W=1, R=1 → 高可用但最终一致。

取舍：提高 W/R 增强一致但降低可用/增加延迟；降低则相反。

## 八、时钟与一致

- 物理时钟不可靠（漂移），分布式用 **逻辑时钟（Lamport）/ 向量时钟** 定序。
- 新版用 **TrueTime / HLC（混合逻辑时钟）** 做有界偏差的时间服务（如 Spanner）。
- 不要依赖机器时钟做绝对因果判断，除非有 NTP + 边界保护。

## 九、典型中间件定位

| 系统 | 一致性 | 说明 |
|------|--------|------|
| ZooKeeper | 顺序一致（ZAB） | 协调/选主 |
| etcd | 线性一致（Raft） | 配置/KV |
| MySQL 主从 | 最终一致 | 异步复制 |
| Kafka | 分区内有序 | 流处理 |
| Redis 主从 | 最终一致 | 缓存 |

## 十、实践选型建议

1. 钱/库存/配置：CP + 强一致（宁可不可用不能错）。
2. 内容/社交/购物车：AP + 最终一致（可用优先）。
3. 读多写少：缓存扛读，异步补齐。
4. 关键链路：用 Raft 类保证选主与配置一致。
5. 跨服务：用最终一致 + 幂等，避免强一致分布式事务。

## 十一、常见误区

1. 认为 CAP 是「三选二」静态 → 实际是分区下 C/A 取舍。
2. 把最终一致当不一致 → 最终一致有明确收敛保证，非"永远不一致"。
3. 忽略一致性强度 → 用错存储（把缓存当源、把 AP 库当账务库）。
4. 过度追求强一致 → 牺牲可用性，系统脆弱、易雪崩。
5. 用物理时钟做因果 → 漂移导致乱序判断错误。
