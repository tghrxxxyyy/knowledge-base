# CAP 定理与一致性模型

> 板块：架构 　|　 返回：[README](README.md)

## 一、CAP 是什么

分布式系统三个属性不可兼得（网络分区 P 必然存在时，只能在 C 与 A 间选）：

- **C（Consistency）一致性**：每次读都拿到最新写。
- **A（Availability）可用性**：每个请求都有响应（不保证最新）。
- **P（Partition tolerance）分区容错**：网络分区时系统仍能工作。

> 现实：P 几乎必选（网络必故障），所以经典结论是「CP 或 AP 二选一」。

## 二、CP vs AP 怎么选

| 类型 | 含义 | 代表 | 适用 |
|------|------|------|------|
| CP | 分区时保一致、牺牲可用 | ZooKeeper、etcd、HBase | 配置/锁/金融账务 |
| AP | 分区时保可用、牺牲强一致 | Cassandra、DynamoDB、Eureka | 购物车、社交、缓存 |
| CA | 理论存在（无分区） | 单机/主从强同步 | 非分布式场景 |

## 三、BASE 理论（AP 的工程化）

- **Basically Available**：基本可用（降级、限流）。
- **Soft state**：软状态，允许中间态。
- **Eventually consistent**：最终一致。
- BASE 是对 CAP 中 AP 的妥协与落地。

## 四、一致性强度谱系

```
强一致 → 线性一致 → 顺序一致 → 因果一致 → 最终一致 → 弱一致
```

- **线性一致（Linearizable）**：像单副本，全局有序，最严格（etcd/Raft）。
- **顺序一致**：所有节点看到相同顺序，但不保证实时。
- **因果一致**：有因果关系的操作保序。
- **最终一致**：无新写后，最终所有副本一致。

## 五、如何实现强一致

- **共识算法**：Raft / Paxos，保证日志复制一致（etcd、Consul）。
- **Quorum**：W+R > N（写多数+读多数）保证读到最新。
- **两阶段锁/事务**：单库内强一致。

## 六、如何实现最终一致

- **异步复制**：主写后异步同步从。
- **本地消息表 / 事务消息**：保证本地事务与消息原子，消费者最终处理。
- **Saga / TCC**：长事务拆成补偿步骤。
- 见 [场景设计/分布式事务与最终一致]。

## 七、读写 Quorum 数学

- N 副本，W 写成功数，R 读成功数。
- W + R > N → 强一致读（必读到最新）。
- W + R <= N → 可能读到旧值（最终一致）。
- 例：N=3, W=2, R=2 → 强一致；W=1,R=1 → 最终一致但高可用。

## 八、时钟与一致

- 物理时钟不可靠（漂移），分布式用 **逻辑时钟（Lamport）/ 向量时钟** 定序。
- 新版用 **TrueTime / HLC** 做有界偏差的时间服务。

## 九、典型中间件定位

| 系统 | 一致性 | 说明 |
|------|--------|------|
| ZooKeeper | 顺序一致（ZAB） | 协调/选主 |
| etcd | 线性一致（Raft） | 配置/KV |
| MySQL 主从 | 最终一致 | 异步复制 |
| Kafka | 分区内有序 | 流处理 |
| Redis 主从 | 最终一致 | 缓存 |

## 十、实践选型建议

1. 钱/库存/配置：CP + 强一致（宁可不可用不能错）。
2. 内容/社交/购物车：AP + 最终一致（可用优先）。
3. 读多写少：缓存扛读，异步补齐。
4. 关键链路：用 Raft 类保证选主与配置一致。

## 十一、常见误区

1. 认为 CAP 是「三选二」静态 → 实际是分区下 C/A 取舍。
2. 把最终一致当不一致 → 最终一致有明确收敛保证。
3. 忽略一致性强度 → 用错存储（把缓存当源）。
4. 过度追求强一致 → 牺牲可用性，系统脆弱。
