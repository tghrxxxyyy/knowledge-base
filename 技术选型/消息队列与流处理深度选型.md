# 消息队列与流处理深度选型

> 本文深入主流消息中间件的设计取舍：Kafka、RocketMQ、RabbitMQ、Pulsar、ActiveMQ 等的定位、模型、可靠性与适用场景，并给出选型决策框架。内容基于公开设计与工程实践，具体版本特性以官方文档为准。

## 1. 消息队列解决什么

- **异步**：生产者不等消费者，解耦处理时机。
- **解耦**：服务间通过消息通信，不直接依赖。
- **削峰**：突发流量进队列，按消费能力处理。
- **可靠**：消息持久化，防止丢失。

## 2. 核心模型差异

### 2.1 队列模型 vs 发布订阅

- 队列：点对点，一条消息被一个消费者处理。
- 发布订阅：一条消息广播给多个订阅者。
- 现代 MQ 多同时支持（Consumer Group 概念统一）。

### 2.2 消费位点

- 队列维护消费偏移（offset），支持重放。
- 重放能力对排查与补数极重要。

## 3. Kafka

### 3.1 定位

- 高吞吐、持久化、分布式日志。
- 设计目标：海量数据管道与流处理。

### 3.2 核心概念

- Topic / Partition：分区是并行度与顺序单位。
- 顺序：单 partition 内有序。
- 副本：ISR（同步副本）保证不丢。
- 消费组：同组竞争消费，不同组广播。

### 3.3 优点

- 吞吐极高（顺序写盘 + 零拷贝）。
- 持久化 + 可重放。
- 生态广（Connect、Streams、Flink 集成）。

### 3.4 局限

- 延迟非最低（ms 级，非微秒）。
- 运维相对重（分区再均衡、副本管理）。
- 单纯"任务队列"语义不如 RabbitMQ 直观。

### 3.5 适用

- 日志收集、事件流、流处理源、高吞吐解耦。

## 4. RocketMQ

### 4.1 定位

- 阿里开源，金融级可靠，强调事务消息与顺序。
- 国内互联网采用率高。

### 4.2 特性

- 事务消息：半消息 + 回查，保证"本地事务 + 消息发出"一致（见分布式事务章节）。
- 顺序消息：分区顺序 / 全局顺序。
- 延迟消息：分级定时。
- 死信队列：消费失败进 DLQ。

### 4.3 适用

- 电商交易、金融、需要事务消息与顺序保证的场景。

## 5. RabbitMQ

### 5.1 定位

- 基于 AMQP，功能丰富、路由灵活。
- 低延迟、易上手。

### 5.2 特性

- Exchange + Binding 灵活路由（direct/topic/fanout/headers）。
- 多种确认机制。
- 延迟插件支持定时。

### 5.3 局限

- 吞吐相对 Kafka 低（万级 vs 十万级）。
- 海量持久化消息堆积能力弱于 Kafka。

### 5.4 适用

- 任务队列、业务解耦、复杂路由、中小吞吐。

## 6. Pulsar

### 6.1 定位

- 云原生消息平台，计算存储分离。
- 统一队列 + 流。

### 6.2 特性

- 分层架构：Broker（计算） + BookKeeper（存储）。
- 多租户、层级 Topic。
- 支持 Queue 与 Stream 两种订阅。
- 跨地域复制（Geo-replication）。

### 6.3 适用

- 需要多租户、队列流统一、弹性扩展、跨地域的中大型平台。

## 7. ActiveMQ / Artemis

- 老牌 JMS 实现，企业集成场景偶有使用。
- 新项目多转向 Kafka/RocketMQ/Pulsar。

## 8. 可靠性维度

### 8.1 投递语义

- 最多一次（可能丢）。
- 至少一次（可能重复）→ 消费需幂等（最常见）。
- 精确一次（Exactly-Once，Kafka/RocketMQ 支持事务/幂等生产者）。

### 8.2 持久化

- 消息落盘防 broker 宕机丢失。
- 副本机制防单点。

### 8.3 消费幂等

- 任何"至少一次"都必须消费端幂等（去重表/唯一键）。

## 9. 顺序性

- Kafka：单 partition 有序；需顺序则同一 key 进同分区。
- RocketMQ：顺序消息保证。
- RabbitMQ：单队列 FIFO（但 prefetch 并发会乱）。
- 顺序与并行度权衡：强顺序限制吞吐。

## 10. 延迟与吞吐

| 产品 | 吞吐 | 延迟 | 典型场景 |
|---|---|---|---|
| Kafka | 极高 | ms | 日志/流/高吞吐 |
| RocketMQ | 高 | ms | 交易/事务 |
| RabbitMQ | 中 | 低-ms | 任务队列 |
| Pulsar | 高 | ms | 统一队列流 |

## 11. 选型决策框架

1. 是否需事务消息？→ RocketMQ / 支持事务的 Kafka。
2. 是否超高吞吐日志流？→ Kafka。
3. 是否复杂路由任务队列？→ RabbitMQ。
4. 是否多租户/队列流统一/跨地域？→ Pulsar。
5. 是否国内金融交易？→ RocketMQ 常见。

## 12. 运维关注点

- 分区/队列数规划（并行度）。
- 消费滞后（lag）监控告警。
- 磁盘与副本策略。
- 再均衡风暴（Kafka）规避。
- 死信与重试策略。

## 13. 常见踩坑

1. **消费不幂等**：重复消息导致重复发券/扣款。
2. **忽视 lag**：消费跟不上，消息堆积拖垮。
3. **分区过少**：并行度不足，吞吐上不去。
4. **事务消息未回查**：半消息卡住，业务不一致。
5. **用 Kafka 做低延迟任务队列**：延迟与语义不匹配；选 RabbitMQ。
6. **消息体过大**：网络与存储压力；拆分或外链。
7. **无死信处理**：失败消息反复阻塞或丢失。

## 14. 与流处理关系

- Kafka 常作 Flink/Spark 数据源与汇。
- 流处理在 MQ 之上做实时计算（见数据处理章节）。
- MQ 提供"持久化缓冲 + 重放"，是流处理可靠基础。

## 15. 小结

消息队列选型看"语义与场景匹配"：Kafka 胜在吞吐与生态（日志/流），RocketMQ 胜在事务与顺序（交易/金融），RabbitMQ 胜在灵活路由（任务队列），Pulsar 胜在统一队列流与多租户。无论选哪个，**消费必须幂等、监控 lag、规划分区、设死信**，投递语义优先"至少一次 + 幂等消费"。
