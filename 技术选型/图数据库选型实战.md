# 图数据库选型实战

> 当数据核心是"关系"且需要多跳遍历（社交、风控、知识图谱、推荐），关系型数据库的 join 会崩溃，图数据库才是正确选择。本文对比主流图库与选型要点。

## 1. 适用场景

| 场景 | 为什么用图 |
| --- | --- |
| 社交关系 | 多跳好友/二度人脉 |
| 风控反欺诈 | 关系网络识别团伙 |
| 知识图谱 | 实体-关系推理 |
| 推荐 | 基于图的协同 |
| IT 拓扑/血缘 | 依赖影响分析 |

反例：纯 KV 点查、报表聚合——图库不擅长。

## 2. 主流产品

| 产品 | 模型 | 优点 | 注意 |
| --- | --- | --- | --- |
| Neo4j | 属性图 | 成熟、Cypher 友好 | 社区版规模受限 |
| NebulaGraph | 分布式 | 海量、高并发 | 运维门槛 |
| JanusGraph | 可插拔 | 后端灵活 | 依赖外部存储 |
| TigerGraph | 原生分布式 | 实时深图 | 商业为主 |
| ArangoDB | 多模型 | 一库多模 | 图非专精 |

## 3. 数据模型

- **属性图（Property Graph）**：点+边+属性，最主流（Neo4j/Nebula）。
- **RDF**：W3C 标准，语义网，SPARQL 查询。
- **超图**：一条边连多节点，场景少。

## 4. 查询语言

```cypher
// Neo4j Cypher：查二度人脉
MATCH (a:User {id:1})-[:FOLLOW*1..2]->(f:User)
RETURN f.id, count(*) AS depth
```

- Cypher（Neo4j）、nGQL（Nebula）、Gremlin（TinkerPop）各有差异。
- 选型时考虑团队熟悉度与生态。

## 5. 性能指标

- **多跳遍历延迟**：图库强项，关系库弱项。
- **写入吞吐**：分布式图库（Nebula）更高。
- **图算法**：PageRank、社区发现、最短路径是否内置。

## 6. 规模化挑战

- 超大规模图（十亿点、百亿边）需分布式图库。
- 图切分（partition）影响遍历效率——坏切分导致跨机多跳。
- 在线实时图 vs 离线分析图，架构不同。

## 7. 与关系库对比

| 维度 | 关系库 | 图库 |
| --- | --- | --- |
| 多跳查询 | join 爆炸 | O(遍历) |
| 灵活关系 | schema 固定 | 边随意加 |
| 聚合报表 | 强 | 弱 |
| 生态/事务 | 成熟 | 渐成熟 |

## 8. 落地坑点

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 关系库硬做图 | 慢死 | 换图库 |
| 切分差 | 跨机遍历 | 按社区切分 |
| 无索引 | 全图扫 | 建点/边索引 |
| 误用图库 | 报表慢 | 图库+数仓配合 |

## 10. 小结

图数据库 = 关系优先的数据底座。选属性图（Neo4j/Nebula）覆盖多数场景，超大规模选分布式图库并注意切分；报表类仍交给数仓。
