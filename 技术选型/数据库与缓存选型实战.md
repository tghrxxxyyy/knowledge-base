# 数据库与缓存选型实战

> 板块：技术选型 　|　 返回：[README](README.md)

"用什么存数据"是系统设计的第一步，也是最易过度设计的环节。选型不是追新，而是匹配"数据规模、一致性要求、读写比、团队能力"。本文按场景给出现实选型与边界，避免小项目上重武器。

## 一、选型第一原则

先问三个问题：
1. **数据规模与增长曲线**：现在多大？一年后会破亿吗？
2. **一致性要求**：需要强一致事务，还是最终一致可接受？
3. **读写比与访问模式**：读多/写多？点查/范围/聚合？

别一上来就追新，先用**熟、够用、能运维**的方案。过早引入分布式存储，运维与复杂度成本远超收益。

## 二、关系型数据库选型

| 数据库 | 优势 | 适用 |
|--------|------|------|
| MySQL | 生态全、8.0 强、易运维 | 通用 OLTP |
| PostgreSQL | 功能强、扩展多、JSONB | 复杂查询/地理 |
| TiDB | 兼容 MySQL、水平扩展 | 海量且需 SQL |
| Oracle | 企业级强一致 | 大型政企/金融 |

### 2.1 决策要点

- **单表 < 5000 万行、QPS < 1 万**：单库足够，别上分库分表。
- **需要强事务（账务、交易）**：关系型 + 本地事务是首选。
- **需要水平扩展但仍要 SQL**：TiDB / PolarDB 等分布式关系型。
- **复杂查询/地理/JSON 混合**：PostgreSQL 更合适。

## 三、KV / 缓存选型

- **Redis**：内存 KV + 多结构（String/Hash/ZSet/Stream/Geo），缓存/排行榜/分布式锁/消息首选。
- **Memcached**：纯 KV、简单高性能，但功能少、无持久化保障。
- **RocksDB**：嵌入式 LSM KV，本地持久化，常作为存储引擎底层（如 TiDB、Kafka Streams）。

### 3.1 缓存层级

- 本地缓存：Caffeine（进程内，抗读热点，无网络开销）。
- 分布式缓存：Redis（集群）。
- 多级：本地 → Redis → DB，逐级兜底。

## 四、文档 / 搜索

- **MongoDB**：Schema 灵活，迭代快；但事务弱、分析弱、聚合受限。适合内容/配置/日志类。
- **Elasticsearch**：全文检索 + 聚合分析，近实时（见 [场景设计/全文搜索与Elasticsearch实战](../../场景设计/全文搜索与Elasticsearch实战.md)）。
- **ClickHouse**：列存 OLAP，亿级聚合秒级，适合日志/指标分析。

## 五、消息队列选型

| MQ | 特点 | 适用 |
|----|------|------|
| Kafka | 高吞吐、持久、流处理 | 日志/事件流 |
| RocketMQ | 事务消息、低延迟 | 电商交易 |
| Pulsar | 存算分离、多租户 | 云原生 |
| RabbitMQ | 易用、灵活路由 | 中小业务 |

详见 [技术选型/消息队列选型与对比](../技术选型/消息队列选型与对比.md)。

## 六、OLAP 选型

- 实时分析：ClickHouse / Doris（列存、向量化，亚秒级）。
- 离线数仓：Hive / Spark（批处理）。
- 即席查询：Presto / Trino（跨源联邦查询）。

## 七、时序数据库

- **InfluxDB / VictoriaMetrics / Prometheus TSDB**：监控指标、IoT 时序数据存储。
- 特点：高写入、按时间范围高效查询、自动降采样。

## 八、图数据库

- **Neo4j / Nebula**：关系网络、风控反欺诈、推荐关系挖掘。
- 当查询是"多跳关系"（A 的朋友的朋友）时，关系型 JOIN 爆炸，图库更优。

## 九、缓存选型与场景

- **热点读**：Redis 单机/集群，前置 DB。
- **抗读热点**：本地 Caffeine + Redis 多级。
- **分布式锁/限流/排行榜**：Redis 天然契合。
- 注意：缓存是**加速层**，不是源（源在 DB）。

## 十、选型 checklist

1. 数据量 + 增长曲线（决定是否需要分布式）。
2. 一致性强度（强事务 vs 最终一致）。
3. 读写比（读多→缓存、写多→分区/列存）。
4. 团队熟悉度与运维能力（自建集群很重）。
5. 成本（自建 vs 云托管 vs 完全托管）。
6. 延迟与 SLA 要求。

## 十一、常见误区

1. **小项目上分库分表** → 过度设计，维护成本爆炸。
2. **用 Redis 当源数据** → 丢数据风险（它是缓存/索引）。
3. **选 MQ 只看吞吐不看可靠性** → 交易场景丢消息资损。
4. **忽视运维成本** → 自建 ES/Kafka 集群很重，没人运维就崩。
5. **一个数据库打天下** → 用 MySQL 扛分析、用 ES 当主库，都错位。
6. **盲目 NoSQL** → 需要事务/关联时还是关系型稳。
