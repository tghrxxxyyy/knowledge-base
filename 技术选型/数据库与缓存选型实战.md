# 数据库与缓存选型实战

> 板块：技术选型 　|　 返回：[README](README.md)
> 关联：[分库分表与数据迁移/README](../../分库分表/README.md)、[场景设计/缓存经典三问与一致性](../../场景设计/缓存经典三问与一致性.md)、[场景设计/全文搜索与Elasticsearch实战](../../场景设计/全文搜索与Elasticsearch实战.md)、[消息队列选型与对比](消息队列选型与对比.md)

"用什么存数据"是系统设计的第一步，也是最易过度设计的环节。选型不是追新，而是匹配"数据规模、一致性要求、读写比、团队能力"。本文按场景给出现实选型与边界，避免小项目上重武器。

## 一、选型第一原则

先问三个问题：
1. **数据规模与增长曲线**：现在多大？一年后会破亿吗？
2. **一致性要求**：需要强一致事务，还是最终一致可接受？
3. **读写比与访问模式**：读多/写多？点查/范围/聚合/多跳？

> 别一上来就追新，先用**熟、够用、能运维**的方案。过早引入分布式存储，运维与复杂度成本远超收益。多数系统单库 + 缓存能撑很久。

## 二、关系型数据库选型

| 数据库 | 优势 | 适用 |
|--------|------|------|
| MySQL | 生态全、8.0 强、易运维 | 通用 OLTP |
| PostgreSQL | 功能强、扩展多、JSONB、GIS | 复杂查询/地理/混合 |
| TiDB | 兼容 MySQL、水平扩展 | 海量且需 SQL |
| PolarDB/OceanBase | 云原生、存算分离 | 云上高并发 |
| Oracle | 企业级强一致、生态 | 大型政企/金融（贵） |

### 2.1 决策要点

- **单表 < 5000 万行、QPS < 1 万**：单库足够，别上分库分表（见 [分库分表/README](../../分库分表/README.md)）。
- **强事务（账务、交易）**：关系型 + 本地事务是首选（ACID）。
- **水平扩展但仍要 SQL**：TiDB / PolarDB / CockroachDB 等分布式关系型。
- **复杂查询/地理/JSON 混合**：PostgreSQL 更合适（JSONB + PostGIS）。
- **只读副本**：读多写少 → 一主多从，读流量走从库。

## 三、KV / 缓存选型

| 组件 | 特点 | 适用 |
|------|------|------|
| Redis | 内存 KV + 多结构（String/Hash/ZSet/Stream/Geo）、持久化可选 | 缓存/排行榜/锁/消息 |
| Memcached | 纯 KV、简单高性能、多线程 | 纯缓存、无结构需求 |
| RocksDB | 嵌入式 LSM KV，本地持久化 | 存储引擎底层（TiDB、Kafka Streams、Flink State） |
| KeyDB / Dragonfly | Redis 兼容、多线程 | 高并发替代 Redis |

### 3.1 缓存层级

```
请求 → 本地缓存(Caffeine) → 分布式缓存(Redis) → DB
        （进程内、抗读热点）   （集群、共享）
```

- 本地缓存：Caffeine（进程内，抗读热点，无网络开销），适合几乎不变/高频读。
- 分布式缓存：Redis（集群），多实例共享。
- 多级：本地 → Redis → DB，逐级兜底（见 [多级缓存框架](../../场景设计/多级缓存框架.md)）。

## 四、文档 / 搜索

| 引擎 | 特点 | 适用 |
|------|------|------|
| MongoDB | Schema 灵活、迭代快 | 内容/配置/日志类（事务弱） |
| Elasticsearch | 全文检索 + 聚合，近实时 | 搜索/日志分析（见 [全文搜索实战](../../场景设计/全文搜索与Elasticsearch实战.md)） |
| ClickHouse | 列存 OLAP，亿级聚合秒级 | 日志/指标/分析 |
| OpenSearch | ES 开源分支 | AWS 生态 |

- MongoDB 适合**结构多变**的数据（如用户画像标签、设备元数据），但**事务弱、分析弱**，别当分析库。
- ES 是**搜索引擎/索引**，不是主库（写入有延迟、一致性弱）。主数据在 DB，ES 做异构索引。

## 五、消息队列选型

| MQ | 特点 | 适用 |
|----|------|------|
| Kafka | 高吞吐、持久、流处理 | 日志/事件流/大数据 |
| RocketMQ | 事务消息、低延迟 | 电商交易/金融 |
| Pulsar | 存算分离、多租户 | 云原生平台 |
| RabbitMQ | 易用、灵活路由 | 中小业务/任务队列 |

详见 [消息队列选型与对比](消息队列选型与对比.md)。

## 六、OLAP 选型

| 场景 | 选型 |
|------|------|
| 实时分析（亚秒） | ClickHouse / Doris / StarRocks |
| 离线数仓（批） | Hive / Spark / MaxCompute |
| 即席跨源查询 | Presto / Trino |
| 实时数仓 | Flink + 湖仓（Iceberg/Delta） |

- 原则：**OLTP 用关系型，OLAP 用列存**，别用 MySQL 跑亿级 GROUP BY。

## 七、时序数据库

- **InfluxDB / VictoriaMetrics / Prometheus TSDB / TDengine**：监控指标、IoT 时序。
- 特点：高写入、按时间范围高效查询、自动降采样（rollup）、TTL 过期。
- 不适合：需要事务关联的业务数据（用关系型/时序分离）。

## 八、图数据库

- **Neo4j / Nebula Graph / Nebula / TigerGraph**：关系网络、风控反欺诈、推荐关系挖掘。
- 当查询是"多跳关系"（A 的朋友的朋友）时，关系型 JOIN 爆炸，图库更优（遍历边而非 JOIN）。
- 适用：社交图谱、知识图谱、风控关系链。

## 九、向量数据库

- **Milvus / Qdrant / Weaviate / pgvector / Chroma**：Embedding 检索（RAG、相似推荐）。
- 选型看：规模（亿级选 Milvus）、是否要混合检索、与现有栈整合（pgvector 复用 PG）。
- 详见 [存储引擎与数据库内核选型实战](存储引擎与数据库内核选型实战.md)。

## 十、缓存选型与场景

| 场景 | 方案 |
|------|------|
| 热点读 | Redis 单机/集群，前置 DB |
| 抗读热点 | 本地 Caffeine + Redis 多级 |
| 分布式锁/限流/排行榜 | Redis 天然契合（SET NX / INCR / ZADD） |
| 会话/短期状态 | Redis + 过期 |
| 注意 | 缓存是**加速层**，不是源（源在 DB） |

## 十一、选型 checklist

- [ ] 数据量 + 增长曲线（决定是否需要分布式）。
- [ ] 一致性强度（强事务 vs 最终一致）。
- [ ] 读写比（读多→缓存、写多→分区/列存）。
- [ ] 查询模式（点查/范围/聚合/多跳/全文/向量）。
- [ ] 团队熟悉度与运维能力（自建集群很重）。
- [ ] 成本（自建 vs 云托管 vs Serverless）。
- [ ] 延迟与 SLA 要求。

## 十二、常见误区

1. **小项目上分库分表** → 过度设计，维护成本爆炸。
2. **用 Redis 当源数据** → 丢数据风险（它是缓存/索引，需持久化兜底）。
3. **选 MQ 只看吞吐不看可靠性** → 交易场景丢消息资损（需事务/确认）。
4. **忽视运维成本** → 自建 ES/Kafka 集群很重，没人运维就崩。
5. **一个数据库打天下** → 用 MySQL 扛分析、用 ES 当主库，都错位。
6. **盲目 NoSQL** → 需要事务/关联时还是关系型稳。
7. **MongoDB 当分析库** → 聚合弱、慢，该用列存 OLAP。
8. **图库滥用** → 两跳以内 JOIN 也能搞定，别为图而图。
