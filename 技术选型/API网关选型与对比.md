# API 网关选型与对比

> 板块：技术选型 　|　 返回：[README](README.md)
> 关联：[服务框架与RPC选型](服务框架与RPC选型.md)、[消息队列选型与对比](消息队列选型与对比.md)、[云原生/ServiceMesh深入](../../云原生/ServiceMesh深入.md)

API 网关是系统的"统一入口"，承载路由、认证、限流、熔断、灰度、日志等横切能力。选错网关会导致性能瓶颈或能力缺失。本文对比主流网关、核心能力、部署形态与选型建议。

## 一、网关解决什么

没有网关时，客户端直连各服务：地址难管理、认证重复、跨域/限流各做各的、难灰度。网关把这些都收口：

| 能力 | 说明 |
|------|------|
| 路由 | 按路径/域名/Header 转发到后端服务 |
| 认证鉴权 | JWT/OAuth2/API Key 统一校验 |
| 限流熔断 | 入口第一道防线（见 [限流算法](../../场景设计/限流算法与网关实践.md)） |
| 灰度/金丝雀 | 按权重/Header 分流 |
| 协议转换 | REST↔gRPC、HTTP→WebSocket |
| 可观测 | 统一日志、指标、链路 |
| 安全防护 | WAF、防刷、防注入 |

## 二、主流网关对比

| 网关 | 特点 | 适用 |
|------|------|------|
| Nginx | 高性能反向代理，配置简单 | 静态/简单路由、入口 LB |
| Kong | 基于 Nginx+Lua，插件丰富，企业级 | 通用 API 网关 |
| APISIX | 基于 Nginx+etcd，云原生、动态配置、高性能 | 云原生、高动态 |
| Spring Cloud Gateway | Java 生态，与 Spring 集成好 | Java/Spring 微服务 |
| Envoy | 云原生数据面，xDS 驱动 | Service Mesh / 高级流量 |
| Zuul | Netflix，老牌（已弱化） | 旧 Spring Cloud |

### 2.1 关键差异

| 维度 | Nginx | Kong | APISIX | SCG | Envoy |
|------|-------|------|--------|-----|-------|
| 性能 | 极高 | 高 | 极高 | 中 | 高 |
| 动态配置 | 需 reload | 支持 | 强（etcd/watch） | 支持 | xDS 热更新 |
| 插件生态 | 少（需 Lua） | 丰富 | 丰富 | 中等 | 丰富 |
| 语言 | C/Lua | Lua | Lua | Java | C++ |
| 云原生 | 一般 | 好 | 很好 | 一般 | 原生 |

## 三、核心能力详解

### 3.1 动态路由

- 路由规则可热更新（APISIX 用 etcd watch，无需 reload）。
- 支持路径、域名、Header、Cookie、权重多种匹配。

```yaml
# APISIX 路由示例
routes:
  - uri: /api/order/*
    upstream: {nodes: {"order-svc:8080": 1}}
    plugins:
      limit-req: {rate: 100, burst: 50}
      jwt-auth: {}
```

### 3.2 认证鉴权

- 统一在网关做 JWT 校验 / OAuth2 / API Key，后端服务信任网关注入的 `X-User-Id` 等头。
- 避免每个服务各自实现认证。

### 3.3 限流熔断

- 网关层做第一道限流（全局/接口/IP），应用内做纵深。
- 配合熔断（后端异常时网关快速失败或降级）。详见 [稳定性三板斧](../../场景设计/稳定性三板斧：限流-熔断-降级.md)。

### 3.4 灰度发布

- 按权重（v1 90% / v2 10%）或 Header（内部用户走 v2）分流。
- 与 Service Mesh 互补：网关做南北向（外部→内部），Mesh 做东西向（服务间）。

## 四、部署形态

| 形态 | 说明 | 适用 |
|------|------|------|
| 独立网关集群 | 专门网关节点 | 中大型，性能隔离 |
| 边车/Ingress | K8s Ingress（Nginx/APISIX Ingress） | 云原生 |
| Service Mesh | Envoy 做网关（Gateway API） | 已是 Mesh 体系 |

## 五、性能与容量

- 网关是流量咽喉，性能关键：APISIX/Nginx 单实例可扛数万~数十万 QPS。
- 启用 HTTPS 需注意 TLS 握手开销（用会话复用、HTTP/2、硬件加速）。
- 限流/鉴权等插件有开销，按需在关键路由开启。

## 六、选型建议

| 场景 | 推荐 |
|------|------|
| 简单反向代理/静态 | Nginx |
| 通用 API 网关 + 丰富插件 | Kong / APISIX |
| 云原生、动态配置频繁 | APISIX |
| Java/Spring 微服务 | Spring Cloud Gateway（或前面挂 APISIX） |
| 已是/将上 Service Mesh | Envoy / Istio Gateway |
| 超高并发入口 | Nginx/APISIX 前置 |

## 七、常见坑

1. **网关成单点** → 需集群 + 多可用区部署，限流/路由配置高可用。
2. **所有逻辑堆网关** → 网关过重、耦合，应只做横切（业务在后端）。
3. **不做限流** → 网关被打爆拖垮全部服务。
4. **动态配置不生效** → 用需 reload 的方案频繁变更导致抖动（选 APISIX/Envoy 热更新）。
5. **鉴权后透传不安全** → 后端必须校验网关注入头，防伪造。
6. **TLS 性能瓶颈** → 没开会话复用/HTTP2，握手耗 CPU。
7. **链路追踪断在网关** → 网关需注入 trace_id 并透传。
