# OLAP 与实时数仓选型实战

> 本文深入分析型（OLAP）与实时数仓的选型：离线数仓 vs 实时数仓、Lambda/Kappa 架构、主流引擎（ClickHouse/Doris/StarRocks/Spark SQL/Trino）、以及湖仓一体趋势。内容基于公开设计与实践，具体特性以官方为准。

## 1. OLAP 的定位

- OLAP 面向分析查询：聚合、多维、大范围扫描。
- 与 OLTP 互补：OLTP 管交易，OLAP 管分析。
- 特点：读多写少（或批量写）、查询复杂、数据量大。
- 用户：分析师、报表、BI、算法特征。

## 2. 离线数仓（T+1）

- 数据按天批处理，凌晨跑任务出报表。
- 技术栈：Hive/Spark SQL 在 HDFS/对象存储上计算。
- 优点：简单、稳定、成本低、容错好。
- 缺点：延迟高，看不到实时。

## 3. 实时数仓

- 数据秒级/分钟级可见，支持实时监控与决策。
- 技术栈：Flink 计算 + Kafka 传输 + 实时 OLAP 存储。
- 优点：低延迟。
- 缺点：链路复杂、成本较高、排障难。

## 4. Lambda 架构

- 批层（Batch）：全量精确计算（慢但准）。
- 速度层（Speed）：实时近似计算（快但可能不准）。
- 服务层：合并两层结果对外。
- 优点：兼顾准确与实时。
- 缺点：两套逻辑维护成本高（批流代码重复）。

## 5. Kappa 架构

- 一切皆流，只用流处理（Flink）。
- 历史数据靠重放 Kafka 主题重建。
- 优点：一套代码、逻辑统一。
- 缺点：重放成本高、对 Kafka 依赖重、历史超长链路重放慢。

## 6. 湖仓一体（Lakehouse）

- 在廉价存储（对象存储）上构建数仓能力。
- 表格式：Iceberg / Hudi / Delta Lake 提供 ACID、时间旅行、schema 演进。
- 计算引擎（Spark/Trino/Flink）读写统一存储。
- 优点：存算分离、成本低、避免数据孤岛。
- 趋势：现代数仓主流方向。

## 7. ClickHouse

- 列存、向量化执行，单表大宽表聚合极快。
- 写入需批量有序，小批随机写不友好。
- join 能力弱，倾向大宽表反范式。
- 适用：日志、监控、用户行为、实时报表。

## 8. Doris / StarRocks

- MPP 架构，兼具高并发点查与多维分析。
- 支持物化视图、Bitmap 精确去重。
- 适用：多维分析、高并发报表、广告/用户分析。
- StarRocks 在向量化与多表 join 上更强。

## 9. Spark SQL

- 批处理主力，处理海量离线计算。
- 生态成熟，与 Hive/湖仓表格式集成好。
- 不适合低延迟交互查询（起作业慢）。
- 常与实时引擎（Flink）配合。

## 10. Trino / Presto

- 分布式 SQL 查询引擎，跨数据源联邦。
- 不存数据，下推/拉取后汇总。
- 适用：交互式即席查询、跨源查询。
- 对湖仓表格式（Iceberg）支持好。

## 11. 实时 OLAP 选型对比

| 引擎 | 强项 | 弱项 | 适用 |
|---|---|---|---|
| ClickHouse | 大宽表聚合 | join 弱 | 日志/监控 |
| Doris | 多维+高并发 | 超大规模略弱 | 报表/分析 |
| StarRocks | 向量化+多表join | 运维 | 高并发分析 |
| Trino | 联邦即席 | 非存储 | 跨源查询 |

## 12. 数据分层

- ODS：贴源层，原始数据。
- DWD：明细层，清洗后的事实。
- DWS：汇总层，轻度聚合。
- ADS：应用层，面向报表/应用。
- 分层解耦，便于复用与治理。

## 13. 实时链路示例

```
业务库/日志 → CDC(Flink CDC) → Kafka
   → Flink 实时清洗/聚合 → ClickHouse/Doris
   → 实时大屏/告警
离线：业务库 → 同步 → 湖仓( Iceberg ) → Spark 夜算 → 回流
```

## 14. 一致性取舍

- 实时数仓允许短暂不准确（最终一致）。
- 财务/对账类强一致场景仍走离线或对账。
- 实时与离线结果差异需监控并解释。

## 15. 性能优化

- 分区与分桶：减少扫描量。
- 物化视图：预聚合热点查询。
- 索引/排序键：按查询模式设计。
- 数据裁剪：用分区过滤、列裁剪。
- 资源隔离：大查询不挤占小查询。

## 16. 成本治理

- 冷热分层：热数据高性能存储，冷数据廉价归档。
- 存算分离：按需扩计算，存储廉价。
- 生命周期：过期分区自动清理。
- 避免全量重算，用增量。

## 17. 常见踩坑

1. **实时离线两套逻辑**：结果对不齐；用 Kappa/湖仓统一。
2. **ClickHouse 做 join 主战场**：性能差；反范式大宽表。
3. **小批随机写 ClickHouse**：写入阻塞；批量有序。
4. **忽视数据分层**：模型混乱难维护；ODS-DWD-DWS-ADS。
5. **实时当强一致用**：财务误用出差错；对账兜底。
6. **不治理生命周期**：存储爆炸；设 TTL 与归档。
7. **计算存储耦合**：扩缩不灵；走存算分离。

## 18. 演进路径

- 起步：离线 Hive/Spark 报表。
- 实时需求：加 Flink + Kafka + OLAP。
- 统一：湖仓一体（Iceberg + 多引擎）。
- 服务：BI + 即席（Trino）+ 实时大屏。

## 19. 与流处理关系

- Flink 是实时数仓的计算引擎（见数据处理章节）。
- Kafka 是实时数据总线。
- OLAP 是存储与查询端。
- 三者构成实时数仓主干。

## 20. 小结

OLAP 与实时数仓选型围绕"延迟、成本、一致性、join 能力"：离线用 Hive/Spark 稳，实时用 Flink+ClickHouse/Doris，即席/跨源用 Trino，长期趋势是湖仓一体（Iceberg + 存算分离）。铁律：**数据分层解耦、实时允许最终一致、ClickHouse 反范式大宽表、生命周期必治理、流批逻辑尽量统一（Kappa/湖仓）**。
