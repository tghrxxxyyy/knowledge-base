# 时序数据库选型实战

> 板块：技术选型 　|　 返回：[README](README.md)
> 适用：监控指标、IoT 传感器、日志指标、APM、金融行情。

时序数据（Time Series）是按时间顺序产生的高写入、少更新、按时间范围查询的数据。普通关系库在此场景写入与压缩都吃力，TSDB 专门优化。

## 一、时序数据特征

- **写多读少**：持续高频写入（指标/采样）。
- **按时间检索**：几乎都是"某时间段 + 聚合"。
- **不可变追加**：历史一般不改（或降精度归档）。
- **价值随时间衰减**：热数据细粒度，冷数据降采样。

## 二、核心优化技术

| 技术 | 作用 |
|------|------|
| 列式存储 | 同列压缩率高（相同类型+时间序） |
| 数据降采样（Downsampling） | 冷数据按分钟/小时聚合，省空间 |
| 时间分区 | 按天/小时分片，过期自动删 |
| 标签（Tag）索引 | 用低基数列（host/region）高效过滤 |
| 预聚合 | 常用聚合提前算，查询快 |

## 三、主流 TSDB 对比

| 数据库 | 特点 | 适用 |
|--------|------|------|
| InfluxDB | 专为时序、类 SQL、单机/集群 | 监控、IoT |
| Prometheus | 拉模型、PromQL、云原生标配 | 容器/服务监控 |
| TimescaleDB | 基于 PG 的时序插件、SQL 友好 | 已有 PG 栈 |
| ClickHouse | 超强分析、列存、非纯 TSDB | 海量指标+分析 |
| TDengine | 国产、极致压缩、物联网优化 | 工业 IoT |
| VictoriaMetrics | 兼容 Prometheus、省资源 | 大规模监控 |

## 四、Prometheus 生态

```
Exporter(采集) → Prometheus(拉取存储) → PromQL查询 → Grafana展示
                         ↓
                    Alertmanager(告警)
```

- **拉模型**：Prometheus 主动 scrape 目标 `/metrics`。
- **Long-term storage**：本地不适合长期，接 Thanos/Mimir/Cortex 做长期存储。
- **局限**：单机容量有限，超大规模用集群方案。

## 五、选型决策

| 诉求 | 推荐 |
|------|------|
| 容器/K8s 监控 | Prometheus + Grafana + Thanos |
| 已有 PG 栈 | TimescaleDB |
| 工业/IoT 海量 | TDengine / InfluxDB |
| 监控+分析一体 | VictoriaMetrics / ClickHouse |
| 强 SQL  Reporting | TimescaleDB / ClickHouse |

## 六、数据建模

- **Metric + Tags + Timestamp + Value**：如 `cpu_usage{host="web1",region="cn"} 0.8 @ t`。
- **高基数的坑**：Tag 基数爆炸（如 user_id 当 tag）→ 索引膨胀；Tag 用低基数列。
- **降采样链**：原始（秒级）→ 1m 聚合 → 1h 聚合，分层存储。

## 七、写入与留存

- **批量写入**：减少小包开销。
- **留存策略（Retention）**：热 7 天细粒度，冷 1 年降采样，更久归档。
- **压缩**：时序专用编码（delta-of-delta、gorilla）极致压缩。

## 八、与数仓关系

- TSDB 管"实时监控"，数仓管"离线分析"。
- 监控指标也可入湖（Iceberg）做长期分析，与 TSDB 互补。

## 九、常见坑

1. **高基 Tag** → 内存/索引爆炸；Tag 只用低基数字段。
2. **存太久不降采样** → 成本爆炸；分层留存。
3. **Prometheus 当长期存储** → 容量爆；接 Thanos/Mimir。
4. **用 MySQL 存指标** → 写入瓶颈；用 TSDB。
5. **查询全量时间** → 慢；限定范围 + 预聚合。
6. **忽视 cardinality 监控** → 突发膨胀拖垮；监控 series 数。
