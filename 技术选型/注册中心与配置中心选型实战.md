# 注册中心与配置中心选型实战

微服务架构下，注册中心解决"服务在哪"，配置中心解决"参数怎么配"。
两者是基础设施的底座。本文从 CAP、模型、一致性、生态、场景对比主流方案并给出选型建议。

## 一、注册中心的作用

### 1.1 核心职责

- 服务注册：Provider 上线后登记自身地址与元数据。
- 服务发现：Consumer 获取可用 Provider 列表。
- 健康检查：剔除不可用节点。
- 变更通知：节点上下线实时推送。

### 1.2 与负载均衡的关系

注册中心提供节点列表，负载均衡在调用侧选择具体节点。
二者配合实现"动态寻址 + 流量分发"。

## 二、主流注册中心对比

### 2.1 Zookeeper

- 基于 ZAB 协议，强一致（CP）。
- 用临时节点表示服务存活，会话失效自动删除。
- 优点：数据强一致、成熟度高的生态。
- 缺点：在大规模频繁注册场景下写性能与扩展性受限；选举期间不可用。

### 2.2 Eureka

- Netflix 设计，AP 优先，最终一致。
- 自我保护机制：网络分区时不立即剔除节点，宁可保留可能过期的实例。
- 优点：高可用、对网络分区容忍好。
- 缺点：一致性较弱，已停止主动维护。

### 2.3 Nacos

- 阿里开源，同时支持注册中心与配置中心。
- 可切换 CP（Raft）与 AP（Distro）模式。
- 优点：功能全面、中文生态好、易运维。
- 缺点：概念较多，运维复杂度相对高。

### 2.4 Consul

- HashiCorp 出品，CP 取向，基于 Raft。
- 内置 DNS、健康检查、多数据中心。
- 优点：一体化能力强、跨数据中心支持好。
- 缺点：相对重量级。

### 2.5 etcd

- 强一致 KV 存储（Raft），常作为 Kubernetes 的底座。
- 适合作为轻量注册/配置存储。
- 优点：简单、可靠、云原生友好。
- 缺点：需自行构建服务模型与发现逻辑。

## 三、CAP 视角的取舍

- CP 型（ZK/Consul/etcd）：节点列表强一致，但分区/选举时可能短暂不可注册。
- AP 型（Eureka/Nacos-AP）：始终可注册可发现，但可能返回稍旧的节点列表。

经验：多数业务允许短暂"看到旧节点"，更看重"随时可发现"，故 AP 常被接受；
对强一致有硬性要求的场景选 CP 并配合重试/熔断。

## 四、配置中心的作用

### 4.1 核心职责

- 集中管理配置：环境变量、开关、阈值、连接串。
- 动态推送：改配置无需重启应用。
- 环境隔离：dev/test/prod 配置分离。
- 灰度与回滚：按应用/集群/实例维度下发，支持回退。

### 4.2 解决的问题

- 配置散落在代码中、难以统一变更。
- 改一个参数要全量发布。
- 多环境多实例配置混乱。

## 五、主流配置中心对比

### 5.1 Nacos

- 注册 + 配置一体，管理界面友好。
- 支持监听变更、灰度、回滚。

### 5.2 Apollo

- 携程开源，配置管理功能成熟。
- 强调"配置即发布"，有权限、审计、灰度、版本。
- 适合对配置治理要求高的企业。

### 5.3 Spring Cloud Config

- 与 Spring 生态集成好，配置放在 Git 仓库。
- 偏向"配置即代码"，动态刷新需配合消息总线。

### 5.4 自研 / etcd / K8s ConfigMap

- 简单场景可用 K8s ConfigMap + Secret。
- 复杂治理需专门的配置中心。

## 六、选型决策框架

### 6.1 看团队与生态

- 已用 Spring Cloud：Config/Apollo/Nacos 都易集成。
- 已用 Dubbo/阿里系：Nacos 天然契合。
- 强治理诉求：Apollo。
- 云原生/K8s 优先：etcd/ConfigMap/Operator 方案。

### 6.2 看一致性要求

- 必须强一致：ZK/etcd/Consul（CP）。
- 容忍短暂不一致：Eureka/Nacos-AP。

### 6.3 看运维能力

- 希望少运维：托管云服务。
- 有运维团队：自建集群并做好高可用。

### 6.4 看功能诉求

- 只要服务发现：任意注册中心。
- 还要动态配置：选带配置中心的（Nacos/Apollo）。

## 七、高可用部署要点

- 注册/配置中心自身必须集群化，避免单点。
- 客户端缓存：中心不可用时使用本地缓存继续运行。
- 客户端兜底：配置中心不可用时回退到本地默认配置。
- 监控：节点健康、注册数、推送延迟、连接数。

## 八、常见坑

- 注册中心与业务混部，资源争抢。
- 客户端未做本地缓存，中心抖动导致全站不可用。
- 配置变更缺乏灰度，一次改错全量生效。
- 健康检查阈值不合理，频繁误剔除。
- 把大量动态数据塞进注册中心，拖慢其性能。

## 九、速记

- 注册中心：解决"服务在哪"；配置中心：解决"参数怎么配"。
- CP：ZK/etcd/Consul，强一致但分区时可能不可用；AP：Eureka/Nacos-AP，高可用但短暂不一致。
- Nacos 二合一（注册+配置），Apollo 配置治理最强。
- 选型看：生态、一致性、运维、功能诉求。
- 高可用：集群化 + 客户端缓存 + 变更灰度 + 监控。
