# 低代码与 aPaaS 选型实战

> 低代码（Low-Code）与应用平台即服务（aPaaS）用于加速企业内部系统搭建。本文梳理能力维度、开源与商业方案、适用边界与落地风险。

## 1. 低代码能力维度

```mermaid
flowchart LR
    A[表单/模型驱动] --> B[流程引擎]
    B --> C[页面编排]
    C --> D[集成/API]
    D --> E[部署/运维]
```

| 维度 | 说明 |
| --- | --- |
| 数据建模 | 可视化建表、关系 |
| 页面编排 | 拖拽组件、布局 |
| 流程引擎 | 审批、自动化 |
| 集成能力 | 对接 API/数据源 |
| 扩展性 | 自定义代码/插件 |

## 2. 方案分类

| 类型 | 代表 | 适用 |
| --- | --- | --- |
| 开源低代码 | Amis、NocoBase、Appsmith | 自建、可控 |
| 商业低代码 | 钉钉宜搭、简道云、Mendix | 企业快速 |
| aPaaS | 云厂商应用平台 | 云上一体 |
| BPM 平台 | Flowable/Activiti 系 | 流程强 |

## 3. 开源代表

- **Amis（百度）**：JSON 配置驱动前端，适合中后台。
- **NocoBase**：数据模型 + 插件，开源可私有部署。
- **Appsmith**：内部工具快速搭建。
- **ToolJet / Budibase**：轻量内部工具。

## 4. 选型要点

- **核心诉求**：是表单录入、流程审批、还是复杂业务系统？
- **扩展天花板**：低代码能覆盖 80%，剩余 20% 能否写代码补？
- **数据归属**：是否支持私有部署、数据不出域（合规）。
- **厂商锁定**：导出/迁移能力如何？

## 5. 适用边界

✅ 适合：内部审批、CRM 雏形、数据看板、原型。
❌ 不适合：核心交易、极致性能、强定制 UI、算法密集。

> 经验法则：低代码解决"重复造轮子"的 CRUD，复杂逻辑仍需专业开发。

## 6. 落地风险

| 风险 | 现象 | 对策 |
| --- | --- | --- |
| 锁定 | 迁不出 | 选可私有部署 |
| 天花板 | 卡在定制 | 留代码扩展口 |
| 性能 | 大数据慢 | 评估上限 |
| 治理乱 | 多平台碎片化 | 统一平台策略 |

## 7. 与专业开发协作

- 低代码做"壳"与流程，专业代码做"内核"与集成。
- 通过 API 把低代码与现有系统集成。
- 平台提供 SDK/插件机制承接复杂逻辑。

3. 低代码的天花板在哪？

5. 低代码与传统开发如何协作？

## 9. 小结

低代码/aPaaS = 加速内部系统构建的工具，覆盖 80% 通用需求。选型看扩展天花板、私有部署与锁定风险；复杂核心逻辑仍需专业开发，二者以 API 协作。
