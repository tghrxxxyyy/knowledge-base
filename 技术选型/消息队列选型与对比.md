# 消息队列选型与对比

> 板块：技术选型 　|　 返回：[README](README.md)
> 关联：[支付系统核心设计](../场景设计/支付系统核心设计.md)、[消息中间件源码要点](../源码系列/消息中间件源码要点.md)、[服务框架与RPC深度选型](../技术选型/服务框架与RPC深度选型.md)

消息队列（MQ）是分布式系统的"管道"，解决异步、解耦、削峰、可靠传输。但 Kafka、RocketMQ、Pulsar、RabbitMQ 各有侧重，选错会带来吞吐不足或功能缺失。本文从动机、对比、核心概念、可靠性到选型建议系统讲解。

## 一、为什么需要 MQ

| 价值 | 说明 | 例子 |
|------|------|------|
| 异步 | 下单后发消息，积分/通知/风控异步处理，主链路更快 | 下单 50ms 而非 500ms |
| 解耦 | 生产者不依赖消费者实现，只约定消息契约 | 新增消费者不改生产者 |
| 削峰 | 突发流量进队列，消费者匀速消费，保护下游 | 秒杀流量削平 |
| 可靠 | 消息持久化，进程重启不丢 | DB 重启消息不丢 |
| 广播/分发 | 一条消息被多消费者按兴趣消费 | 订单事件 → 积分/物流/风控 |

## 二、主流对比（核心维度）

| 维度 | Kafka | RocketMQ | Pulsar | RabbitMQ |
|------|-------|----------|--------|----------|
| 吞吐 | 极高（十万~百万/s） | 高（十万级） | 极高 | 中（万级） |
| 延迟 | 毫秒~秒 | 毫秒 | 毫秒 | 微秒~毫秒（最低） |
| 事务消息 | 事务 producer（非半消息） | 半消息+回查（成熟） | 支持 | 不强调 |
| 消费模型 | 拉（pull） | 拉/推 | 推（push） | 推 |
| 顺序消息 | 分区内有序 | 队列内有序（成熟） | 分区有序 | 需配置 |
| 典型场景 | 日志/流/大数据 | 交易/金融 | 云原生多租户 | 通用/任务队列 |
| 生态 | 大数据（Flink/Spark） | 阿里系、国内金融 | 云原生 | AMQP 通用 |

### 选型一句话

- **日志/流/大数据** → Kafka
- **交易/金融/电商** → RocketMQ（事务、顺序消息成熟）
- **云原生多租户/存算分离** → Pulsar
- **简单任务队列/低延迟** → RabbitMQ

## 三、RocketMQ 核心

```
Producer → NameServer(路由) → Broker(存消息, 主从) → Consumer Group
                                   ↑
                              Topic / MessageQueue
```

- **Topic / Tag**：Topic 主题，Tag 标签，支持按 Tag 过滤消费（如 `TagA || TagB`）。支持按 tag 消费（用户实践：Spring Boot + RocketMQ 按 tag 消费）。
- **Consumer Group**：消费组，组内竞争（集群模式）、组间广播。
- **Broker / NameServer**：Broker 存消息，NameServer 做路由发现（无状态、去中心化）。
- **事务消息**：半消息 + 回查，保证本地事务与消息一致（见支付/下单场景）。
- **顺序消息**：同一 MessageQueue 内有序，用于订单状态流转（如创建→支付→发货）。
- **延迟/死信**：延迟级别（1s/5s/10s…）、消费失败重试进死信队列（DLQ）。
- **消息回溯**：按时间/offset 重放，便于补数/排查。

```java
// 事务消息：先发半消息，本地事务成功再 commit
TransactionSendResult r = producer.sendMessageInTransaction(msg, null);
// 回查：Broker 未收到 commit/rollback 时回调检查本地事务状态
```

## 四、Kafka 核心

```
Producer → Topic(Partition 多副本) → Consumer Group(Rebalance)
              ↑
          Partition 是并行/扩展单元
```

- **Partition**：分区是并行与扩展单元，同 key 进同分区保序。
- **Consumer Group + Rebalance**：消费者增减触发分区再均衡（再均衡期间消费暂停，需控制）。
- **高吞吐根基**：顺序写盘 + 零拷贝（sendfile）+ PageCache + 批处理。
- **ISR**（In-Sync Replicas）：同步副本集合，保证已提交消息不丢（acks=all + min.insync.replicas）。
- **消费位移**：offset 由消费者提交（手动提交避免丢/重）。

```java
// 同 key 进同分区保序
producer.send(new ProducerRecord<>("order", orderId, payload));
```

## 五、Pulsar 特点

- **存算分离**：BookKeeper 负责存储（分片日志），Broker 无状态计算 → 扩缩容极灵活。
- **多租户**：原生 tenant/namespace 隔离，适合平台化。
- **分层存储**：冷数据下沉到对象存储（S3），降低成本。
- **统一模型**：同时擅长队列（Queue，Shared 订阅）与流（Stream，Exclusive/Failover 订阅）。
- **Geo 复制**：跨地域原生复制。

## 六、RabbitMQ 特点

- 基于 AMQP，Exchange-Binding-Queue 路由灵活（direct/topic/fanout/headers）。
- 延迟低、易上手，适合中小规模任务队列、RPC 式调用。
- 通过 **TTL + 死信队列（DLX）**实现延时/重试。
- 集群用镜像队列（经典）/ Quorum 队列（Raft，更可靠）。

```bash
# 延时消息：消息 TTL 过期后进死信队列
channel.basic_publish(exchange='dlx', routing_key='delay', body=msg,
                      properties=pika.BasicProperties(expiration='5000'))
```

## 七、可靠性保障（端到端）

| 环节 | 手段 |
|------|------|
| 生产端 | ack + 重试；重要场景用事务消息/本地消息表 |
| 服务端 | 副本机制（ISR/多副本/Quorum）、刷盘策略权衡（同步刷盘更可靠但慢） |
| 消费端 | 手动 ack，处理完再提交位移，避免丢；幂等消费避免重复影响 |
| 全链路 | 不丢 ≠ 不重：MQ 一般保证"至少一次"，恰好一次需业务幂等配合 |

- **本地消息表**：业务事务内写消息表，异步任务轮询发送，保证"业务成功必有消息"（最终一致经典方案）。
- **事务消息**：RocketMQ/Kafka 事务 producer 减少自己实现本地消息表的成本。

## 八、幂等消费（必做）

- 消息可能重复（at-least-once）→ 消费逻辑必须幂等。
- 手段：
  - 去重表（消息唯一 ID 入库，唯一索引拦截）；
  - Redis `SETNX` 标记已处理；
  - 状态机（已处理则跳过）；
  - 数据库唯一约束（如订单事件仅插入一次）。

```sql
INSERT INTO consume_log (msg_id, status) VALUES (?, 'DONE')
ON DUPLICATE KEY UPDATE status='DONE';  -- 唯一索引去重
```

## 九、性能与运维

- **批量**发送/消费提升吞吐（Kafka 批处理是关键）。
- **监控积压（lag）**：消费速度 < 生产速度时及时扩容消费者/优化消费逻辑。
- **合理分区数**：Kafka 消费者数 ≤ 分区数，多出的空闲（扩容先加分区）。
- **消息体大小**：过大（>1MB）影响网络/存储，建议压缩或只传 ID 让消费者查。
- **顺序 vs 并行**：顺序消息只能单分区单消费者，吞吐受限，按需使用。

## 十、常见坑

1. **不配消费幂等** → 重复处理（扣款两次、通知多次）。
2. **消费慢不监控不扩容** → 积压，数据延迟严重（lag 告警）。
3. **消息体过大** → 网络/存储压力，序列化慢。
4. **死信队列不用** → 失败消息丢失，无兜底（务必配置 DLQ + 告警）。
5. **顺序消息跨分区** → 乱序，业务错乱（同 key 同分区）。
6. **只看吞吐忽略延迟** → 选了高吞吐但延迟不达标的方案。
7. **自动提交 offset** → 消费失败但 offset 已提交 → 消息丢失。
8. **acks 配置过低** → leader 宕机丢消息（用 acks=all + min.insync.replicas）。
9. **再均衡风暴** → 消费超时导致频繁 rebalance（调大 max.poll.interval）。
10. **消息无限堆积不清理** → 磁盘打满（设 TTL/过期清理）。

## 十一、选型决策表

| 需求 | 首选 | 理由 |
|------|------|------|
| 日志采集、流计算 | Kafka | 吞吐极致、生态全 |
| 金融交易、订单 | RocketMQ | 事务/顺序消息成熟、国内生态 |
| 多租户云平台 | Pulsar | 存算分离、原生多租户 |
| 简单异步、任务队列 | RabbitMQ | 低延迟、易上手 |
| 强一致不丢 | RocketMQ/Pulsar(Quorum) | 副本 + 同步刷盘 |
| 极低延迟 | RabbitMQ | 微秒级 |
