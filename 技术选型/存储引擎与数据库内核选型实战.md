# 存储引擎与数据库内核选型实战

> 本文从"存储引擎内核"视角拆解数据库选型：B+Tree vs LSM-Tree、行存 vs 列存、OLTP vs OLAP、以及典型数据库的存储适配（MySQL/PostgreSQL、RocksDB、ClickHouse、TiDB、Cassandra）。帮助在性能、一致性、成本之间做有依据的取舍。

## 1. 选型先看"读写模型"

数据库选型的第一步不是"哪个最火"，而是回答业务的数据访问特征：

- 读多写少，还是写多读少？
- 事务一致性要求多强？
- 单条点查为主，还是大范围扫描/聚合为主？
- 数据量级别（GB / TB / PB）？
- 是否需要水平扩展？

不同内核结构对这些问题的响应差异巨大。

## 2. B+Tree：传统 OLTP 的基石

### 2.1 结构

B+Tree 是平衡多路树，所有数据存在叶子节点，叶子间用链表串联，非叶子节点只存索引键。高度通常 3–4 层即可索引海量数据。

### 2.2 特性

- **点查极快**：O(log n) 定位，3 次 IO 左右到数据。
- **范围查询友好**：叶子链表顺序遍历，适合 `BETWEEN`、排序。
- **写入有随机 IO**：插入可能触发页分裂、随机写，随机写 SSD 尚可，HDD 较差。
- **原地更新**：更新就地修改页，需 undo/redo 日志保证事务与崩溃恢复。

### 2.3 代表

- MySQL InnoDB、PostgreSQL 默认索引均为 B+Tree（PostgreSQL 用 B-Tree 变体）。
- 适合：订单、账户、交易等强事务、点查+范围混合的 OLTP。

## 3. LSM-Tree：高写入吞吐的选择

### 3.1 结构

LSM-Tree（Log-Structured Merge Tree）把写入先放内存（MemTable），写满后刷成有序的 SSTable 文件，后台 Compaction 合并多层文件。

### 3.2 特性

- **写吞吐极高**：写入是顺序追加（WAL）+ 内存，避免随机写。
- **读需多层**：点查可能查内存+多层文件，用 Bloom Filter 加速跳过无关文件。
- **读放大/写放大/空间放大**：Compaction 带来额外 IO 与空间，需调参（leveled/ tiered）。
- **延迟毛刺**：Compaction 抢占 IO 时可能造成读延迟抖动。

### 3.3 代表

- RocksDB（被 TiDB、Cassandra、Kafka 等大量采用作为底层）。
- Cassandra、HBase 的存储基于 LSM 思想。
- 适合：写多（日志、时序、消息）、能容忍稍高读延迟的场景。

## 4. 行存 vs 列存

### 4.1 行存

- 一行所有列连续存储。
- 点查整行快，适合 OLTP。
- 分析时即使只查一列也要读整行，IO 浪费。

### 4.2 列存

- 同一列的数据连续存储。
- 聚合/扫描某几列极快，且天然高压缩（同列数据类型一致）。
- 点查整行需拼多列，慢。
- 代表：ClickHouse、Vertica、Parquet/ORC 文件格式。

### 4.3 选择

- OLTP → 行存（B+Tree）。
- OLAP / 报表 / 大宽表聚合 → 列存（ClickHouse/Doris）。
- 湖仓 → Parquet/ORC 列存文件 + 计算引擎。

## 5. OLTP 数据库选型

### 5.1 MySQL（InnoDB）

- 成熟、生态广、运维资料多。
- 单实例强一致事务，主从复制（异步/半同步）。
- 水平扩展靠分库分表（sharding）或上分布式数据库。
- 适合：绝大多数互联网业务主库。

### 5.2 PostgreSQL

- 功能更丰富（JSONB、数组、自定义类型、复杂查询优化器）。
- 扩展性强（PostGIS、插件生态）。
- 写吞吐与并发在某些场景优于 MySQL，但默认配置下调优要求高。
- 适合：复杂查询、地理、分析型混合负载。

### 5.3 分布式 OLTP（TiDB 类）

- 兼容 MySQL 协议，自动分片（基于 Region），弹性扩展。
- 底层用 RocksDB（行存）+ TiKV，计算存储分离。
- 适合：数据量超单机、需要水平扩展又想保留 SQL/事务。
- 代价：架构复杂、延迟略高于单机、运维门槛高。

## 6. OLAP 与列式数据库

### 6.1 ClickHouse

- 极致列存分析，向量化执行，单表大宽表聚合极快。
- 写入需批量、有序，小批随机写不友好。
- join 能力弱于传统数仓，倾向大宽表反范式。
- 适合：日志分析、监控、报表、实时数仓。

### 6.2 Doris / StarRocks

- MPP 架构，兼顾高并发点查与多维分析。
- 适合：多维分析、高并发报表、广告/用户行为。

### 6.3 选择要点

- 是否需高并发明细查询？→ StarRocks/Doris。
- 是否超大宽表聚合、写多？→ ClickHouse。
- 是否已有 Hadoop/Spark 生态？→ 配合 Trino/Presto 查询。

## 7. KV 与文档数据库

### 7.1 Redis

- 内存 KV，亚毫秒延迟，多种结构（String/Hash/List/Set/ZSet）。
- 持久化可选（RDB/AOF），多用于缓存、计数器、排行榜、队列。
- 注意：内存贵，数据需有淘汰与降级策略。

### 7.2 文档库（MongoDB）

- 灵活 Schema，JSON 文档，适合结构易变的数据。
- 事务能力已增强，但复杂关联查询弱于关系库。
- 适合：内容、配置、IoT 等 Schema 演进频繁场景。

### 7.3 宽表（Cassandra/HBase）

- 海量写入、多副本、最终一致。
- 适合：时序、消息、海量事件。
- 查询模式受限（需按主键/分区设计），不适合任意维度查询。

## 8. 一致性与隔离级别

- **强一致（线性一致）**：读必见最新写，成本高。
- **因果一致 / 会话一致**：放宽，体验可接受。
- **最终一致**：异步复制，副本滞后。
- 事务隔离：读未提交/已提交/可重复读/串行化，越高越安全但越慢。
- 选型要问：业务能否接受主从延迟导致的"读旧数据"？

## 9. 扩展性维度

- **垂直扩展**：升单机配置，简单但有上限。
- **水平扩展（分片）**：按 key 分片，需解决跨分片事务/查询。
- **读写分离**：主写从读，缓解读压力，注意复制延迟。
- **计算存储分离**：云原生趋势（如 TiDB、Aurora 思路），扩容灵活。

## 10. 成本与运维

- 商业 vs 开源：商业有支持但贵，开源自由但需自建运维。
- 托管 vs 自建：云托管省心但锁定与成本，自建灵活但人力重。
- 隐性成本：备份、监控、扩容、故障恢复的人力。

## 11. 选型决策表

| 场景 | 首选内核/产品 |
|---|---|
| 强事务 OLTP 点查 | MySQL/PostgreSQL (B+Tree) |
| 海量写入/日志/消息 | RocksDB/Cassandra (LSM) |
| 水平扩展 OLTP | TiDB (分布式) |
| 多维分析高并发 | StarRocks/Doris |
| 大宽表聚合 | ClickHouse |
| 缓存/高速 KV | Redis |
| Schema 灵活 | MongoDB |
| 湖仓查询 | Trino + Parquet/ORC |

## 12. 常见误区

1. **用 MySQL 扛分析**：大范围聚合拖垮主库；应分流到 OLAP。
2. **盲目上分布式数据库**：单机够用却引入 TiDB，复杂度与延迟双增。
3. **忽视写入放大**：LSM 的 Compaction 在写入高峰引发抖动，需调参。
4. **列存做点查**：ClickHouse 点查整行慢，应配适当的表引擎/物化视图。
5. **分库分表过早**：业务早期就分片，运维成本陡增；先单机再演进。
6. **读写分离无视延迟**：从库滞后导致用户看到旧数据，关键读走主库。

## 13. 演进路径

- 早期：单机 MySQL/PG，读写分离。
- 增长期：加缓存（Redis）、加从库、冷热分离。
- 海量期：分库分表 或 迁移分布式数据库 / OLAP 分流。
- 分析需求：引入 ClickHouse/Doris + 数据同步链路。

## 14. 小结

数据库选型本质是"内核结构适配访问模式"：B+Tree 擅长点查事务、LSM 擅长写吞吐、列存擅长聚合分析。先量化业务的读写比、一致性、规模、扩展需求，再对应内核选型，避免"唯热门论"和"过早分布式"。多引擎并存（OLTP + 缓存 + OLAP）是现代系统的常态。
