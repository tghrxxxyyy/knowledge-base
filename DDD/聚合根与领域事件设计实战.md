# DDD 聚合根与领域事件设计实战

> 本文聚焦 DDD 中最易误用也最关键的两个概念：聚合（Aggregate）与领域事件（Domain Event），讲清聚合边界划分、聚合根职责、一致性边界、领域事件的设计与发布，以及落地陷阱。内容基于 DDD 经典实践，命名以通用为准。

## 1. 为什么聚合重要

在 DDD 中，实体（Entity）、值对象（Value Object）、聚合（Aggregate）、领域服务（Domain Service）、领域事件（Domain Event）、工厂（Factory）、仓库（Repository）构成领域模型骨架。其中**聚合是一致性边界的基本单元**，划分好坏直接决定系统的正确性、性能与演进难度。

## 2. 聚合的定义

- 聚合是一组**强相关、需保持内部一致**的领域对象簇。
- 每个聚合有且仅有一个**聚合根（Aggregate Root）**，是对外的唯一入口。
- 外部只能通过聚合根操作聚合内部对象，**不能直接引用聚合内的非根实体**。

```text
订单(聚合根)
 ├─ 订单项(实体, 属于订单内部)
 ├─ 收货地址(值对象)
 └─ 金额(值对象)
外部只能 order.addItem(...)，不能直接改某个订单项
```

## 3. 聚合根的职责

- **身份标识**：拥有全局唯一 ID。
- **一致性守卫**：执行业务规则，保证聚合内所有对象始终一致。
- **行为入口**：业务操作以聚合根方法暴露，而非散落 service。
- **不变式（Invariant）维护**：如"订单总额 = 各项之和""库存不为负"。

## 4. 聚合的划分原则

### 4.1 一个事务只修改一个聚合

- 经典原则：**一个事务（ACID）只修改一个聚合**。
- 跨聚合的一致性通过**最终一致**（领域事件）达成，而非同一事务。
- 理由：大聚合 = 大锁 = 低并发；多聚合一事务 = 分布式事务难题。

### 4.2 聚合要小

- 聚合越小，并发越高、边界越清晰。
- 但过小会丢失有用的不变式保护。
- 取舍：以"需要一起保持一致的数据"为界。

### 4.3 避免聚合引用聚合

- 聚合间不持有对象引用，只持有**对方 ID**。
- 通过 ID 在仓库加载，保持聚合独立与边界。

## 5. 聚合内的一致性

聚合根方法内可调用内部实体/值对象完成规则校验：

```java
class Order {
    void addItem(Product p, int qty) {
        if (qty <= 0) throw new IllegalArgumentException("数量必须为正");
        this.items.add(new OrderItem(p.id, qty, p.price));
        this.total = this.total.add(p.price.multiply(qty));
        // 不变式：total 始终等于各项之和
    }
}
```

所有一致性在内存中由聚合根保证，再整体持久化。

## 6. 领域事件

### 6.1 概念

领域事件是"领域中发生的重要事实"，用过去式命名：`OrderPlaced`、`PaymentReceived`、`InventoryLocked`。

- 表示"已经发生"，不可变。
- 承载"跨聚合/跨服务"的信息传播。
- 与事件驱动架构（见相关章节）天然衔接。

### 6.2 何时发事件

- 聚合状态变更后，若有其他聚合/限界上下文需要响应。
- 例：OrderPlaced → 扣库存、发通知、算积分。

### 6.3 事件内容

- 事件应携带**身份与关键数据**（订单 ID、金额、时间）。
- 避免把整个聚合大对象塞进事件（耦合重、体积大）。
- 用最小必要信息，消费者按需再查。

## 7. 事件的发布时机

### 7.1 事务内 vs 事务后

- **事务内发**：与聚合保存同一事务，保证"状态变 + 事件发出"一致（本地消息表/事务消息思想）。
- **事务后发**：先提交，再发；若发失败需补偿/重试。
- 关键：避免"状态已变但事件没发"导致下游不一致。

### 7.2 事件溯源结合

若使用事件溯源，事件本身就是状态来源，发布即追加事件，天然一致。

## 8. 聚合 + 事件的典型流程

```
1. 应用服务加载 Order 聚合（经 Repository）
2. order.place() 修改状态、产生 OrderPlaced 事件
3. 事务内保存聚合 + 持久化事件（本地消息表）
4. 事务提交
5. 事件发布到消息总线
6. 库存聚合消费 → 锁定库存；通知聚合 → 发短信
（各消费者幂等）
```

## 9. 与限界上下文

- 聚合通常位于某个限界上下文内，是上下文内的强一致边界。
- 跨上下文用领域事件（最终一致）解耦，而非聚合直接引用。

## 10. 仓库与工厂

- **Repository**：聚合的持久化抽象，按 ID 加载/保存整个聚合，不暴露内部。
- **Factory**：复杂聚合的创建（尤其涉及不变式初始化），封装创建逻辑。
- 二者让领域层不依赖具体存储框架。

## 11. 常见踩坑

1. **超大聚合**：把一堆实体塞一个聚合，事务锁重、性能差；应拆分。
2. **聚合间对象引用**：直接引用别聚合实体，边界崩塌；只存 ID。
3. **把聚合当数据表**：聚合≠表，一个聚合可能映射多张表，也可能多聚合共表。
4. **事务改多聚合**：一个事务改多个聚合导致分布式事务；改最终一致。
5. **贫血模型**：聚合根只有 getter/setter，逻辑全在 service；应把行为放回聚合。
6. **事件过大**：把整个聚合序列化进事件，耦合重；带最小信息。
7. **事件发漏**：状态变但事件未发，下游不一致；用事务消息/本地表兜底。
8. **事件命名呈命令式**：用 PlaceOrder 而非 OrderPlaced；应用过去式事实。

## 12. 划分实战示例

### 12.1 电商

- 聚合：订单（根）、购物车（根）、商品（根）、用户（根）。
- 订单与购物车分离：下单时从购物车生成订单，二者非同一聚合。
- OrderPlaced → 库存扣减、积分增加（各自聚合，最终一致）。

### 12.2 避免

- 把"用户"和"用户的所有订单"放一个聚合：订单量大会撑爆聚合；用户与订单应是不同聚合，订单持有 userId。

## 13. 与微服务的映射

- 一个微服务可含多个聚合，聚合是微服务内的一致单元。
- 限界上下文常对应微服务边界。
- 聚合的事务边界 ≈ 微服务内本地事务；跨服务必最终一致。

## 14. 落地建议

- 先识别核心域的聚合与根，不追求全量建模。
- 聚合尽量小，事务只改一个聚合。
- 跨聚合用领域事件 + 幂等消费。
- 行为写进聚合根，避免贫血。
- 事件用过去式、带最小信息、事务内可靠发出。

## 15. 小结

聚合是 DDD 的一致性与并发边界：一个事务只改一个聚合，聚合间只持 ID，行为回归聚合根。领域事件承担跨聚合/跨上下文的传播，用"事务内可靠发出 + 最终一致 + 幂等消费"保证整体正确。划分的黄金法则是"小聚合、强边界、事件解耦"，而非把领域对象堆成一个大对象。
