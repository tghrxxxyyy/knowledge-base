# DDD 领域服务与应用服务边界实战

> "这段代码该放领域服务还是应用服务？"是 DDD 实践中最常见的困惑。本文厘清二者的职责边界，并给出判断标准与反模式。

## 1. 三层服务职责

| 层 | 职责 | 是否含业务规则 |
| --- | --- | --- |
| 领域服务（Domain Service） | 跨实体/值对象的无状态业务操作 | 是（领域级） |
| 应用服务（Application Service） | 用例编排、事务、跨聚合协调 | 否（流程级） |
| 基础设施服务 | 技术实现（DB、MQ、邮件） | 否 |

## 2. 领域服务（Domain Service）

当某个业务行为不属于任何一个实体/值对象，而涉及多个领域对象协作时，用领域服务。

```java
// 转账：涉及两个账户，不适合放 Account
class TransferService {
    void transfer(Account from, Account to, Money m){
        from.withdraw(m);
        to.deposit(m);
    }
}
```

- 无状态，操作领域对象。
- 表达领域概念（"转账"是业务动作）。
- 命名体现领域语言。

## 3. 应用服务（Application Service）

负责用例编排，不含业务规则：

```java
class TransferAppService {
    @Transactional
    void transfer(TransferCmd cmd){
        Account from = repo.load(cmd.fromId);
        Account to = repo.load(cmd.toId);
        transferService.transfer(from, to, cmd.money); // 委托领域
        repo.save(from); repo.save(to);
        eventBus.publish(...);  // 跨聚合通知
    }
}
```

- 接收命令（Command）、开事务、调用领域、发事件。
- 不应写 if 判断业务规则（那是领域的事）。

## 4. 判断标准

| 问题 | 放哪 |
| --- | --- |
| 只涉及一个聚合的内部行为 | 聚合根方法 |
| 跨多个聚合的业务规则 | 领域服务 |
| 用例步骤、事务边界 | 应用服务 |
| 调用外部系统/持久化 | 基础设施 |

## 5. 反模式

- **贫血应用服务**：应用层写满 if/计算，领域成空壳。
- **上帝领域服务**：领域服务承担编排，越界。
- **逻辑泄露到 Controller**：业务规则写进接口层。

## 6. 与 CQRS 结合

- 写侧：应用服务编排命令 → 领域处理 → 发事件。
- 读侧：应用服务直接查读模型（查询 handler），不走领域。

## 7. 示例对比

```java
// 错：业务规则在应用层
void placeOrder(cmd){
    if (cmd.items.isEmpty()) throw ...;   // 应属领域
    Order o = new Order(cmd.items);
    repo.save(o);
}

// 对：领域负责规则
class Order {
    Order(List<Item> items){
        if (items.isEmpty()) throw new DomainException("空订单");
        this.items = items;
    }
}
```

## 8. 面试题

1. 领域服务与应用服务区别？
2. 何时用领域服务而非实体方法？
3. 应用服务为何不含业务规则？
4. 贫血模型的成因？
5. 命令（Command）在应用层如何流转？

## 9. 小结

边界口诀：单聚合行为归实体，跨聚合规则归领域服务，流程与事务归应用服务。守住"应用层编排、领域层决策"，才能避免贫血与越界。
