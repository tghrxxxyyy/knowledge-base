# 统一语言与模型驱动设计

> 板块：DDD 　|　 返回：[README](README.md)
> 适用：跨角色协作、需求到代码的准确映射、避免"翻译失真"。

DDD 的第一项实践是**统一语言（Ubiquitous Language）**：让业务专家、产品、开发、测试用**同一套词汇与概念模型**交流，并把它落到代码、文档、图中。它是 DDD 一切的基础——没有统一语言，后续限界上下文、聚合、实体都会走样。

## 一、为什么需要统一语言

- **翻译失真**：业务说"客户下单后锁库存"，开发理解为"减库存"，测试理解为"标记占用"——三者不一致导致缺陷。
- **术语漂移**：同一个"订单"在不同模块含义不同（交易单/物流单/结算单），沟通成本爆炸。
- **代码即文档**：统一语言应体现在类名、方法名、事件名，新人靠读代码就能懂业务。

## 二、统一语言的形成

1. **事件风暴（Event Storming）**：跨角色用便利贴在墙上贴"领域事件"，对齐认知（见[事件风暴实战](事件风暴实战.md)）。
2. **术语表（Glossary）**：维护一份权威词汇表，定义每个术语的精确含义与边界。
3. **落到代码**：实体/值对象/事件的命名直接用语义词（如 `OrderConfirmed`、`InventoryLocked`），拒绝 `doProcess`、`handleData` 之类模糊命名。
4. **持续演进**：语言随业务演化，定期刷新术语表与模型。

## 三、模型驱动设计（Model-Driven Design）

统一语言要落到**模型**：

- **模型反映语言**：语言里的概念（客户、账户、订单）在模型里都有对应构件。
- **绑定实现**：模型不是 PPT 上的图，而是代码里的聚合、实体、领域服务。
- **重构即重构语言**：当发现更好的概念划分，同步更新语言与代码。

```
统一语言(词汇/概念) ──映射──> 领域模型(实体/值对象/聚合/事件) ──实现──> 代码
       ↑                                                          │
       └────────────── 代码命名反哺语言 ──────────────────────────┘
```

## 四、统一语言的落地载体

| 载体 | 作用 |
|------|------|
| 术语表 | 权威定义，避免歧义 |
| 领域事件列表 | 业务发生什么（过去时） |
| 聚合/实体图 | 模型结构 |
| 用户故事 | 用统一语言书写 |
| 代码命名 | 语言的最终体现 |
| 测试/验收标准 | 用语言描述预期 |

## 五、常见反模式

- **开发自创黑话**：用 `EntityA/B`、缩写，业务看不懂，失去统一。
- **PPT 模型 vs 代码两张皮**：图很美，代码是另一套。
- **术语表无人维护**：过时失真，反而误导。
- **跨上下文共用一词不同义**：不区分限界上下文，强行统一导致混乱。

## 六、与限界上下文的关系

- 统一语言是**每个限界上下文内**的统一，而非全公司统一。
- 同一个词在不同上下文可含义不同（"产品"在目录上下文是展示信息，在库存上下文是库存单位），需用**上下文映射**明确边界与翻译（见[上下文映射与子域](上下文映射与子域.md)）。

## 七、实践清单

- [ ] 是否有跨角色认可的事件风暴/术语表？
- [ ] 核心概念在代码里是否有对应命名清晰的构件？
- [ ] 新人能否通过代码+术语表理解业务？
- [ ] 需求评审是否用语义一致的语言？
- [ ] 上下文边界是否清晰，跨域翻译是否定义？

## 八、收益

- **减少返工**：需求到实现失真少，缺陷降。
- **加速沟通**：会议不再为术语吵架。
- **代码即文档**：可维护性提升。
- **模型演进可控**：语言与代码同步演进。
