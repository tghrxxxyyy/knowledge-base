# DDD 领域驱动设计 · 板块导航

> 本板块系统梳理领域驱动设计（Domain-Driven Design）的核心思想、战术构件与战略设计，配合《入门》《落地》两篇叙事，形成从理念到落地的完整闭环。

## 一、要解决的问题

传统「数据建模 → 表结构 → CRUD」的开发方式，在面对复杂业务时会出现：
- 业务规则散落在 Service 层，领域对象退化成「贫血的 getter/setter 容器」；
- 一个需求改动要同时改多张表、多个 Service，修改范围不可控；
- 代码无法反映真实业务语言，开发、测试、业务三方各说各话。

DDD 的核心主张：**用统一语言（Ubiquitous Language）把业务概念沉淀进领域模型，让模型驱动设计、让代码成为模型的忠实表达**。

## 三、推荐学习路径

1. **先建立战略视角**：读《入门》理解「子域 / 限界上下文 / 核心域」，知道「为什么要分」。
2. **再学战术构件**：读《战术设计》，掌握每个领域对象的职责边界与判定规则——这是日常写代码最直接用到的部分。
3. **团队建模协同**：读《落地》的「事件风暴」章节，把它当成一次工作坊的 SOP。
4. **跨上下文协作**：读《上下文映射与子域》，搞清楚上下游团队该怎么「约接口」。
5. **最后对照避坑**：读《反模式与踩坑》，在 Code Review 时作为 checklist。

## 四、与其他板块的关系

- **架构**：DDD 的分层（接口/应用/领域/基础设施）与[架构板块](../架构/系统架构.md)的整洁架构/六边形架构高度契合。
- **设计模式**：仓储（Repository）常配合[工厂方法](../设计模式/创建型/工厂方法模式.md)、防腐层（ACL）本质是[适配器模式](../设计模式/结构型/适配器模式.md)、领域事件驱动常配合[观察者模式](../设计模式/行为型/观察者模式.md)。
- **业务模型**：[业务模型板块](../业务模型/)提供行业语境，是识别子域与核心域的重要输入。
- **源码系列**：落地篇的分层骨架与[Spring](../源码系列/SpringBoot源码.md)、[MyBatis](../源码系列/MyBatis源码.md) 等源码中的分层一脉相承。

## 五、一句话总结

> DDD 不是一套框架，而是一种「让软件结构贴合业务结构」的思维方式：战略上划分边界（限界上下文/子域），战术上用领域对象承载业务规则，工程上用分层与上下文映射控制复杂度。
