# DDD 反模式与踩坑（Anti-Patterns）

> 配套：[战术设计](战术设计.md) · [上下文映射与子域](上下文映射与子域.md) · 返回：[板块导航](README.md)
> 把 DDD 落地中最常见的「形似神不似」陷阱列成清单，作为 Code Review 与方案评审的对照表。

## 〇、本体介绍

DDD 难在「形似容易、神似难」：很多团队引入了实体/聚合/领域事件这些名词，却仍写出贫血、强耦合、难演进的代码。所谓反模式，就是「看起来在实践 DDD、实则背离其初衷」的做法。本文按**模型健康度 / 边界 / 事件 / 协作**四个维度归类。

---

## 一、模型健康度反模式

### 1. 贫血领域模型（Anemic Domain Model）⚠️ 头号反模式
- **表现**：实体只有 getter/setter，所有业务规则在 Service 里；领域对象只是数据容器。
- **危害**：业务逻辑分散、难以测试、模型不表达业务。
- **修正**：把行为搬回聚合/实体（如 `order.pay()` 而非 `orderService.pay(order)`）；Service 只做编排。

### 2. 上帝对象 / 万能聚合（God Aggregate）
- **表现**：一个聚合塞进几十个实体、上千行逻辑（如「用户聚合」包含订单/地址/偏好/积分）。
- **危害**：事务极重、并发冲突多、难维护。
- **修正**：按一致性边界拆小聚合，跨聚合用 ID 关联 + 领域事件最终一致。

### 3. 把基础设施概念带进领域
- **表现**：领域层直接出现 `Long` 主键、JPA 注解、`@Transactional`、DTO、HTTP 概念。
- **危害**：领域被技术框架绑架，无法独立测试与演进。
- **修正**：领域层用强类型 ID 与纯 Java 类型；仓储接口定义在领域层、实现在外层。

## 二、边界与依赖反模式

### 4. 双向依赖 / 循环依赖
- **表现**：聚合 A 持有 B 的引用、B 又持有 A；上下文之间互相调用。
- **危害**：改一处牵全身，无法独立部署与测试。
- **修正**：单向依赖（A→B）；双向关系改为「单向引用 + 领域事件」或引入 ID 而非对象引用。

### 5. 泄漏领域（Leaky Domain）
- **表现**：应用层/接口层直接把实体当 DTO 返回给前端，领域不变量随序列化外泄。
- **危害**：领域模型被前端需求绑架，重构受限。
- **修正**：在应用层用 Assembler/MapStruct 把领域对象转成专用 DTO/读模型。

### 6. 跨聚合强一致事务
- **表现**：一个事务里同时改多个聚合，甚至 `select for update` 锁住多个根。
- **危害**：长事务、死锁、扩展受限。
- **修正**：单事务只改一个聚合；跨聚合通过领域事件 + 消息做最终一致（见[落地·聚合间最终一致](../DDD/落地.md)）。

### 7. 大泥球式上下文
- **表现**：所有模型混在一个上下文，没有边界，改什么都相互影响（参见[上下文映射·大泥球](../DDD/上下文映射与子域.md#9-大泥球big-ball-of-mud)）。
- **修正**：识别限界上下文，新能力用 ACL 隔离，绞杀者模式逐步拆分。

## 三、领域事件反模式

### 8. 过度事件化（Event Happy）
- **表现**：把本该是方法调用的事也发成事件（如「计算总价」也发事件），链路绕、难追踪。
- **危害**：逻辑碎片化、调试地狱、时序依赖隐式。
- **修正**：仅当「解耦跨聚合/跨上下文协作」才用事件；同聚合内的步骤直接方法调用。

### 9. 事件命名/内容错误
- **表现**：命令式命名（`SendEmail`）、事件里塞可变大对象、事件与业务不在同一事务提交。
- **危害**：语义混乱、消费者读到脏数据、事件丢失。
- **修正**：过去时命名（`EmailSent`）、事件不可变快照、事务提交后由仓储/发件箱统一发布。

### 10. 事件丢失 / 重复消费无幂等
- **表现**：发了事件但消费者没收到，或重复投递导致重复业务动作。
- **修正**：用「事务发件箱（Outbox）」保证事件与业务同落库；消费者做幂等（去重表/版本号）。

## 四、协作与组织反模式

### 11. 统一语言只停留在文档
- **表现**： everyone 口头各说各话，代码命名与业务术语不一致。
- **修正**：把统一语言固化进类名/方法名；边界术语冲突时回到事件风暴对齐。

### 12. 用 DDD 套简单 CRUD
- **表现**：一个后台管理页也要拆聚合/上下文/事件。
- **修正**：DDD 适合复杂业务；简单增删改查用事务脚本即可，不必强行 DDD。

### 13. 照搬框架/照搬别人限界上下文
- **表现**：照抄电商的上下文划分到自己金融系统，或让 ORM 框架决定聚合边界。
- **修正**：上下文划分由「你的业务变化原因」决定，而非模板。

## 五、Code Review 速查清单

- [ ] 业务规则是否在实体/聚合内，而非 Service？（防贫血）
- [ ] 一个事务是否只改一个聚合？（防跨聚合强一致）
- [ ] 聚合是否足够小、无双向引用？（防上帝对象/循环依赖）
- [ ] 领域层是否零技术框架注解、用强类型 ID？（防泄漏/耦合）
- [ ] 对外返回的是 DTO 而非实体？（防泄漏领域）
- [ ] 领域事件是否「过去时 + 不可变 + 同事务发布 + 消费幂等」？（防事件反模式）
- [ ] 对接外部是否走了 ACL？（防大泥球污染）
- [ ] 简单 CRUD 是否没必要上 DDD？（防过度设计）

## 面试高频追问

1. Q：什么是贫血领域模型？怎么解决？ A：实体只有数据无行为、逻辑散在 Service；把行为搬回聚合/实体，Service 只编排。
2. Q：大聚合有什么问题？ A：事务重、锁冲突多、难维护；应按一致性边界拆小，跨聚合用事件最终一致。
3. Q：为什么避免跨聚合强一致事务？ A：长事务易死锁、扩展性差；单事务改一个聚合，跨聚合用领域事件最终一致。
4. Q：双向依赖怎么破？ A：改为单向引用+领域事件，或用 ID 而非对象引用，打破循环。
5. Q：领域事件有哪些常见反模式？ A：过度事件化、命令式命名、事件与业务不同事务导致丢失、消费无幂等。
6. Q：事务发件箱（Outbox）解决什么？ A：保证领域事件与业务数据在同一本地事务落库，再由后台投递，避免事件丢失。
7. Q：什么时候不该用 DDD？ A：简单 CRUD/业务逻辑很薄时，事务脚本更直接，强行 DDD 是过度设计。
8. Q：统一语言为什么重要？ A：让开发/测试/业务用同一套术语，代码命名映射业务概念，减少误解与错位。

## 六、反模式自检：症状 → 根因 → 修法速查

| 现象（代码里看到的） | 反模式 | 一步修法 |
|----------------------|--------|----------|
| Service 全是 if/else 业务逻辑 | 贫血模型 | 把判断搬进领域方法（`canRefund()` 挂在订单上） |
| 实体几百行、依赖一堆 | 上帝聚合 | 按一致性边界拆，子域只留 ID 引用 |
| 实体上全是 JPA/JSON 注解 | 基础设施泄漏 | 注解抽到持久化模型，领域对象纯 POJO |
| 改一处触发全模块重新测试 | 大泥球上下文 | 先划限界上下文 + ACL，再绞杀式拆分 |
| 一个方法里锁了 5 张表 | 跨聚合事务 | 拆成「先改主聚合 → 发事件 → 消费者改其他」 |
| 领域事件发了但消费端看不到 | 事件丢失 | 上事务发件箱（Outbox），投递失败重试 |
| 聚合对外暴露 `setXxx` | 封装泄漏 | 收敛为行为方法 + 只读快照，DTO 单独定义 |
| 「只是不想在 Service 里写代码」 | 为 DDD 而 DDD | 回到事务脚本，规则简单时别硬造聚合 |

> 使用方式：**方案评审前用这张表逐项过一遍**，比空谈「要遵循 DDD」可执行得多。
