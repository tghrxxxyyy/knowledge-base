# DDD 战术设计（Tactical Design）

> 配套：[DDD 入门](入门.md) · [DDD 落地](落地.md) · 返回：[板块导航](README.md)
> 战术设计关注「领域模型内部如何由构件组装」，是每个领域对象职责边界的施工手册。

## 〇、本体介绍

战术设计把领域模型拆成一组**职责单一的构件**（building block），让业务规则有确定的归宿，而不是散落在 Service 里。它解决的核心问题是：**「这段逻辑到底该放在哪？」「两个概念是同一事物还是不同事物？」「一致性边界划在哪？」**

经典构件：实体（Entity）、值对象（Value Object）、聚合根（Aggregate Root）、领域服务（Domain Service）、领域事件（Domain Event）、工厂（Factory）、仓储（Repository）、防腐层（ACL）、规格（Specification）、领域异常（Domain Exception）。

---

## 一、实体（Entity）

### 定义
有**连续身份标识**、沿生命周期保持同一性、可变的领域对象。即便属性变了，只要 ID 不变，它仍是「同一个」。

### 判定规则
- 业务关心「它是谁」而非「它长什么样」→ 用实体（如订单、用户、账户）。
- 通过**标识符（ID）**判等，而非字段值。

### 代码要点
```java
class Order {
    private final OrderId id;          // 标识，构造即定，不可变
    private OrderStatus status;
    private Money total;
    // 业务行为放在实体内，而非 Service
    public void pay(Payment payment) {
        if (status != OrderStatus.UNPAID) throw new DomainException("已支付");
        this.status = OrderStatus.PAID;
        this.total = payment.amount();
        // 触发领域事件
        addEvent(new OrderPaidEvent(id, total));
    }
}
```

### 常见坑
- 把数据库主键 `Long id` 直接当领域标识——应在领域层定义**强类型 ID**（如 `OrderId`），避免把基础设施概念泄漏进领域。
- 实体承担过多职责变成「上帝对象」——超出聚合一致性边界的逻辑应下沉到领域服务或拆分聚合。

## 二、值对象（Value Object）

### 定义
**没有身份标识**、通过**属性值**判等、通常**不可变**的对象（如 Money、Address、Coordinate、Period）。

### 判定规则
- 只关心「属性值是否相等」，不关心「是不是同一个」→ 用值对象。
- 金额、区间、规格、颜色、坐标都是典型值对象。

### 代码要点
```java
class Money {                       // 不可变值对象
    private final BigDecimal amount;
    private final Currency currency;
    public Money add(Money other) {
        requireSameCurrency(other);
        return new Money(amount.add(other.amount), currency); // 返回新对象
    }
}
```
- 不可变：所有字段 `final`，修改操作返回新实例。
- 用 `equals/hashCode` 基于值实现（可用 Lombok `@Value`）。

### 实体 vs 值对象（高频对比）
| 维度 | 实体 | 值对象 |
|------|------|--------|
| 身份 | 有 ID，生命周期内同一 | 无 ID，靠值判等 |
| 可变性 | 可变 | 不可变（推荐） |
| 相等 | ID 相等 | 所有属性相等 |
| 示例 | 订单、用户 | 金额、地址、时间段 |

### 常见坑
- 把本该是值对象的「金额/地址」做成可变实体并到处传引用 → 引发隐式共享修改。
- 值对象里混入 ID → 它其实是实体，混淆概念。

## 三、聚合根（Aggregate Root）

### 定义
**聚合（Aggregate）** 是一组相关对象的集合，**聚合根**是聚合的入口与一致性边界的守护者。外部只能引用聚合根，通过它操作整个聚合。

### 设计原则（一致性边界）
1. **只通过根访问内部**：聚合内的非根实体/值对象不对外直接暴露引用。
2. **一次事务只改一个聚合**：跨聚合的一致性用「最终一致」（领域事件 + 消息）而非强一致事务。
3. **聚合要小**：一个聚合尽量小，避免大事务、长锁。

### 代码要点
```java
class Order {                       // 聚合根
    private final OrderId id;
    private List<OrderItem> items; // 内部实体，外部拿不到引用
    public void addItem(Product p, int qty) {
        // 业务不变量在此守护
        if (items.size() >= 50) throw new DomainException("订单项过多");
        items.add(new OrderItem(p.id(), qty, p.price()));
    }
}
// 外部：orderRepository.find(id).addItem(...);  // 不能直接 new OrderItem
```

### 大聚合反模式
- 把「用户 + 他的所有订单 + 订单所有项」做成单一聚合 → 事务极重、并发冲突多。
- 正确做法：用户是一个聚合，订单是另一个聚合，二者通过 ID 关联，跨聚合改动用事件。

## 四、领域服务（Domain Service）

### 定义
当某个业务操作**不属于任何一个实体/值对象**（涉及多个聚合，或需要基础设施能力）时，把它放到无状态、有显式业务含义的**领域服务**中。

### 判定规则
- 操作是「动词/动作」且需要协调多个领域对象 → 领域服务。
- 对象自己能完成的行为 → 放在实体/值对象里（**不要把领域逻辑外泄到应用服务**）。

### 领域服务 vs 应用服务（Application Service）
| | 领域服务 | 应用服务 |
|--|----------|----------|
| 所处层 | 领域层 | 应用层 |
| 职责 | 承载领域规则/跨聚合协调 | 用例编排、事务边界、鉴权、DTO 转换 |
| 能否调仓储 | 可以（谨慎） | 可以 |
| 技术概念 | 不含事务/HTTP 等 | 可含事务/外部调用 |

### 常见坑
- **领域服务膨胀**：把本属于实体的行为错误地放进领域服务 → 又回到贫血模型。
- 领域服务依赖仓储去「拉一堆聚合再算」→ 反思是否该把逻辑移入聚合，或该用领域事件。

## 五、领域事件（Domain Event）

### 定义
表示「领域中已经发生的事」（过去时命名：`OrderPaid`、`UserRegistered`），用于解耦聚合间、模块间甚至服务间的协作。

### 用法
- 聚合内 `addEvent(...)`，事务提交后由基础设施统一发布（保证「事件与业务同事务」）。
- 订阅方异步响应（发邮件、更新读模型、跨服务通知）。

```java
class OrderPaidEvent {
    private final OrderId orderId;
    private final Money amount;
    private final Instant occurredOn;   // 事件发生时间
}
```

### 常见坑
- **事件命名用将来时/命令式**（如 `SendEmail`）——事件应描述「已发生」，命令才描述「要做」。
- 在事件里塞大量可变状态 → 事件应是不可变快照。
- 同一事务里既改库又发同步远程调用 → 应改为「本地落库 + 异步发事件」保证最终一致。

## 六、工厂（Factory）

### 定义
封装**复杂对象的创建**（尤其是聚合根的创建涉及不变量校验、多步装配时），让调用方不必了解构造细节。

### 适用
- 创建逻辑复杂、需要校验不变量、需要依赖其他聚合/服务。
- 重建（从数据库反序列化）与新建共用工厂方法 `reconstitute(...)`。

```java
class OrderFactory {
    public Order create(OrderId id, List<Product> products, Promotion promo) {
        Order o = new Order(id);
        products.forEach(p -> o.addItem(p, 1));
        o.apply(promo);                 // 创建即保证不变量
        return o;
    }
}
```

## 七、仓储（Repository）

### 定义
为**聚合根**提供「类集合」的持久化抽象，屏蔽底层数据库/ORM 细节。仓储面向聚合，不面向任意表。

### 原则
- **一个聚合一个仓储**：`OrderRepository` 而非 `OrderItemRepository`（项随订单一起持久化）。
- 返回**聚合根**，连同其内部的实体/值对象一并加载（或延迟加载，但对外透明）。
- 接口定义在领域层，实现放在基础设施层（依赖倒置）。

```java
interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);            // 包含 insert/update + 发布领域事件
    void delete(OrderId id);
}
```

### 常见坑
- 在领域层直接注入 DAO/Mapper → 破坏分层；应通过仓储接口。
- 仓储里写业务规则 → 仓储只做持久化与装配，规则在聚合/领域服务。

## 八、防腐层（ACL, Anti-Corruption Layer）

### 定义
在**本限界上下文**与**外部系统/遗留系统**之间加一层适配器，把外部模型翻译成自己的领域模型，防止外部概念「腐蚀」本上下文。

### 实现
- 入站：外部 DTO → 领域模型（用[适配器模式](../设计模式/结构型/适配器模式.md)）。
- 出站：领域模型 → 外部命令/查询。

```java
class LegacyOrderAdapter {            // ACL
    public Order toDomain(LegacyOrderDto dto) {
        return Order.reconstitute(new OrderId(dto.getNo()),
                                  Money.of(dto.getAmt()), ...);
    }
}
```

### 常见坑
- 直接把外部 DTO 当领域对象用 → 外部字段语义/命名渗透进领域，耦合爆炸。
- ACL 里写业务规则 → ACL 只做翻译，规则留给领域。

## 九、规格（Specification）

### 定义
把「业务规则/判读条件」封装成可组合、可复用的对象，既可用于校验也可用于查询筛选。

```java
interface Specification<T> {
    boolean isSatisfiedBy(T t);
    default Specification<T> and(Specification<T> o){...}
}
class VipSpecification implements Specification<User> {
    public boolean isSatisfiedBy(User u){ return u.level() >= 3; }
}
```

### 用法
- 复用同一规则于「是否满足优惠」「查询符合条件的用户」，避免规则散落。

## 十、领域异常（Domain Exception）

### 定义
领域层自己定义、表达**业务不合法**的异常类型（区别于技术异常如 `SQLException`、基础设施异常）。

### 原则
- 命名体现业务语义：`OrderCannotBeCancelled`、`InsufficientBalance`、`DuplicateUserName`。
- 不含技术栈细节，让上层据此做友好提示或流程分支。

```java
class OrderCannotBeCancelled extends DomainException {
    public OrderCannotBeCancelled(OrderId id) {
        super("订单 " + id + " 已发货，不可取消");
    }
}
```

## 十一、构件选择速查

| 我想表达… | 用哪个构件 |
|-----------|-----------|
| 有身份、会变、生命周期长的事物 | 实体 |
| 只关心值、不变、可替换 | 值对象 |
| 一组对象的一致性边界入口 | 聚合根 |
| 跨多个对象的业务动作 | 领域服务 |
| 已经发生的业务事实（解耦协作） | 领域事件 |
| 复杂对象创建/重建 | 工厂 |
| 聚合的持久化集合抽象 | 仓储 |
| 隔离外部模型 | 防腐层 |
| 可复用业务规则/筛选 | 规格 |
| 业务不合法的明确表达 | 领域异常 |

## 面试高频追问

1. Q：实体和值对象怎么区分？ A：看「业务是否关心身份」——关心「是谁」用实体（ID 判等），只关心「值相等」用值对象（不可变、值判等）。
2. Q：聚合根解决什么问题？ A：划分一致性边界，规定外部只能通过根访问内部，一次事务只改一个聚合，避免大事务。
3. Q：为什么一个事务只改一个聚合？ A：跨聚合强一致会带来长事务/锁冲突；跨聚合用领域事件做最终一致。
4. Q：领域服务和应用服务区别？ A：领域服务在领域层、承载跨对象业务规则；应用服务在应用层、做用例编排/事务/鉴权/DTO 转换。
5. Q：领域事件命名要注意什么？ A：用过去时表示「已发生」（OrderPaid），不是命令式；事件应不可变快照。
6. Q：防腐层（ACL）的作用？ A：隔离外部/遗留系统的模型，翻译成自己的领域模型，防止外部概念污染本上下文。
7. Q：仓储为什么面向聚合而非表？ A：保证聚合的完整性；项随根一起持久化，外部不感知内部表结构。
8. Q：什么时候该用领域异常？ A：表达业务不合法（如已发货不可取消），区别于技术异常，便于上层友好处理。
