# DDD 战术设计精要（实体 / 值对象 / 聚合 / 仓储 / 领域服务 / 事件）

> 板块：DDD 　|　 返回：[README](README.md)
> 关联：[DDD/领域建模与限界上下文实战](领域建模与限界上下文实战.md)、[DDD/聚合根与领域事件设计实战](聚合根与领域事件设计实战.md)、[DDD/聚合设计深度](聚合设计深度.md)、[DDD/反模式与踩坑](反模式与踩坑.md)

战术设计（Tactical Design）是把战略（限界上下文、通用语言）落地的具体构件与编码模式。它回答：领域对象怎么建模、一致性边界在哪、行为放哪、怎么持久化、聚合间怎么协作。本文拆清每个构件并给出代码与反模式。

## 一、战术设计核心构件

| 构件 | 是什么 | 关键点 |
|------|--------|--------|
| 实体 Entity | 有唯一标识、有生命周期 | ID 不变，属性可变 |
| 值对象 Value Object | 无标识、靠属性定义 | 不可变、可替换、按属性相等 |
| 聚合 Aggregate | 一致性边界 + 根 | 聚合内强一致，聚合间最终一致 |
| 聚合根 Aggregate Root | 聚合的入口 | 外部只通过根访问内部 |
| 领域服务 Domain Service | 跨实体的无状态操作 | 放不进实体的行为 |
| 仓储 Repository | 聚合的持久化抽象 | 面向聚合根，非表 |
| 领域事件 Domain Event | 领域内发生的有意义的事 | 解耦、审计、事件溯源 |
| 工厂 Factory | 复杂对象创建 | 封装创建逻辑 |
| 规格 Specification | 可组合的业务规则 | 复用校验/查询条件 |

## 二、实体 vs 值对象

### 2.1 区分原则

- **实体**：`User(id, name, email)`，id 相同即同一人，即使 name 改了。有连续性、有生命周期。
- **值对象**：`Money(amount, currency)`、`Address(...)`，无 id，两个值相等即相等；不可变，改了就新建一个。

### 2.2 用值对象减少可变性

```java
// 值对象：不可变，equals 基于属性；改了就新建
record Money(BigDecimal amount, Currency currency) {
    Money add(Money o) {
        requireSameCurrency(o);
        return new Money(amount.add(o.amount), currency);
    }
    static Money zero(Currency c) { return new Money(BigDecimal.ZERO, c); }
}
// 实体：有 ID，状态可变
class Order {
    private final OrderId id;          // 标识
    private Money total;                // 值对象
    void addItem(OrderItem item) { ... } // 行为在实体上
}
```

- 用值对象表达地址、金额、时间段、颜色等，减少可变状态，降低 bug。
- 值对象可包含校验（如金额非负），把不变量固化在对象内。

## 三、聚合设计（最难也最关键）

### 3.1 规则

- 一个聚合内部保证**事务一致性**（一个事务只改一个聚合）。
- 聚合根是唯一对外入口，外部不能直接改聚合内非根实体。
- **小聚合原则**：聚合尽量小，避免大聚合锁竞争与级联更新。
- 聚合间通过 **ID** 引用，而非对象引用（避免跨聚合事务）。

```
订单(聚合根) ── 订单项(实体) ── 产品快照(值对象)
              └─ 收货地址(值对象)
```

### 3.2 跨聚合

- 不把「用户」放进「订单」聚合 → 用户是独立聚合，订单只存 userId。
- 跨聚合一致性用**领域事件**（订单创建 → 发 OrderCreated → 库存聚合监听扣减）。

```java
class Order extends AggregateRoot {
    private List<OrderItem> items;
    private OrderStatus status;
    void pay() {
        if (status != CREATED) throw new IllegalStateException();
        status = PAID;
        addEvent(new OrderPaidEvent(id, total));  // 发领域事件
    }
}
```

### 3.3 大聚合反模式

| 错误 | 后果 |
|------|------|
| 把一整棵树放一个聚合 | 事务大、锁多、并发差 |
| 聚合间用对象引用 | 跨聚合加载、隐式耦合 |
| 聚合根暴露内部实体 setter | 绕过不变量，一致性破坏 |

## 四、仓储（Repository）

- 仓储面向**聚合根**，不是 DAO/表。
- 提供 `save(Aggregate)` / `findById(Id)`，隐藏持久化细节（Hibernate/JPA/MyBatis 实现）。
- 应用服务通过仓储获取聚合、调用行为、再保存。

```java
interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);          // 包含发领域事件
    List<Order> findByCustomer(CustomerId id, Pageable p);
}
```

- 一个聚合一个仓储；不要在应用层直接调 DAO 拼装聚合（破坏边界）。

## 五、领域服务 vs 实体行为

- 行为属于某个实体 → 放实体（**富模型**）。
- 行为跨多个实体、无状态、或无自然归属 → 放领域服务。
- 避免「**贫血模型**」（只有 getter/setter，逻辑全在 Service）——领域知识流失、难以测试。

```java
// 坏：贫血
order.status = PAID; orderService.update(order);
// 好：富模型
order.pay();  // 不变量在聚合内保证
```

## 六、领域事件

- 聚合内发生重要变化 → 发领域事件（如 OrderPaid）。
- 事件驱动后续动作，解耦聚合间协作（事件溯源/审计/CQRS 都基于它）。
- 事件本身是不可变值对象，含发生时间、聚合 ID、载荷。

```java
record OrderPaidEvent(OrderId orderId, Money total, Instant occurredAt) implements DomainEvent {}
```

- 发布方式：聚合内 `addEvent` → 仓储 save 时由 Unit of Work 统一发布到消息总线。

## 七、工厂（Factory）

- 复杂对象（尤其聚合）创建逻辑封装进工厂，保证创建即一致（不变量满足）。
- 简单对象可直接构造器；复杂（需加载关联、校验）用工厂方法/独立 Factory。

## 八、规格（Specification）

- 把业务规则（如"信用良好且余额充足"）封装成可组合对象，复用校验与查询。

```java
Specification<Customer> goodCredit = c -> c.creditScore() > 700;
Specification<Customer> enoughBalance = c -> c.balance().greaterThan(min);
if (goodCredit.and(enoughBalance).isSatisfiedBy(customer)) { ... }
```

## 九、应用服务（Application Service）

- 编排用例：开事务 → 取聚合 → 调领域行为 → 保存 → 发事件。
- 应用服务是 DDD 里的「门面/外观」，**不含业务规则细节**（细节在领域层）。
- 一个应用服务方法 ≈ 一个用例。

```java
class PlaceOrderAppService {
    @Transactional
    public OrderId place(PlaceOrderCmd cmd) {
        Customer c = customerRepo.load(cmd.customerId);
        Order o = orderFactory.create(cmd, c);
        o.pay();                       // 领域行为
        orderRepo.save(o);             // 发事件
        return o.id();
    }
}
```

## 十、与分层架构映射

```
接口层(Controller) → 应用层(Application Service) → 领域层(Domain) → 基础设施层(Repo Impl)
```

- 依赖倒置（DIP）：领域层定义仓储接口，基础设施层实现，领域层不反向依赖框架。
- 接口层只做协议转换；领域层是纯业务，不依赖 Spring/DB。

## 十一、常见误区

1. **大聚合** → 事务大、锁多、性能差（用小王合）。
2. **实体贫血** → 逻辑散在 Service，领域知识流失（用富模型）。
3. **仓储当 DAO** → 暴露表细节，破坏聚合边界（面向聚合根）。
4. **聚合间用强一致** → 应事件最终一致。
5. **领域层依赖基础设施** → 应依赖倒置。
6. **滥用领域服务** → 本属实体的行为被挪走（先问"属于哪个实体"）。
7. **领域事件不发/不持久化** → 审计与溯源缺失。

## 十二、落地步骤

1. 事件风暴找实体/聚合/事件（见 [事件风暴实战](事件风暴实战.md)）。
2. 定聚合边界（小聚合、ID 引用）。
3. 写领域行为（富模型）+ 值对象封装不变量。
4. 定义仓储接口（面向聚合根）。
5. 应用服务编排 + 领域事件解耦。
6. 依赖倒置，领域层零框架依赖。
