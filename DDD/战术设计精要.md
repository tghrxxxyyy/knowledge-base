# DDD 战术设计精要（实体/值对象/聚合/仓储）

> 板块：DDD 　|　 返回：[README](README.md)

## 一、战术设计核心构件

| 构件 | 是什么 | 关键点 |
|------|--------|--------|
| 实体 Entity | 有唯一标识、有生命周期 | ID 不变，属性可变 |
| 值对象 Value Object | 无标识、靠属性定义 | 不可变、可替换 |
| 聚合 Aggregate | 一致性边界 + 根 | 聚合内强一致，聚合间最终一致 |
| 聚合根 Aggregate Root | 聚合的入口 | 外部只通过根访问内部 |
| 领域服务 Domain Service | 跨实体的无状态操作 | 放不进实体的行为 |
| 仓储 Repository | 聚合的持久化抽象 | 面向聚合根，非表 |
| 领域事件 Domain Event | 领域内发生的有意义的事 | 解耦、审计、事件溯源 |
| 工厂 Factory | 复杂对象创建 | 封装创建逻辑 |

## 二、实体 vs 值对象

- **实体**：`User(id, name, email)`，id 相同即同一人，即使 name 改了。
- **值对象**：`Money(amount, currency)`，无 id，两个值相等即相等；不可变，改了就新建。
- 用值对象表达地址、金额、时间段等，减少可变状态，降低 bug。

```java
// 值对象：不可变，equals 基于属性
record Money(BigDecimal amount, Currency currency) {
    Money add(Money o) {
        requireSameCurrency(o);
        return new Money(amount.add(o.amount), currency);
    }
}
```

## 三、聚合设计（最难也最关键）

- 一个聚合内部保证**事务一致性**（一个事务只改一个聚合）。
- 聚合根是唯一对外入口，外部不能直接改聚合内非根实体。
- **小聚合原则**：聚合尽量小，避免大聚合锁竞争与级联更新。

```
订单(聚合根) ── 订单项(实体) ── 产品快照(值对象)
              └─ 收货地址(值对象)
```

- 不把「用户」放进「订单」聚合 → 用户是独立聚合，订单只存 userId。
- 跨聚合一致性用领域事件（订单创建 → 发 OrderCreated → 库存聚合监听扣减）。

## 四、仓储（Repository）

- 仓储面向**聚合根**，不是 DAO/表。
- 提供 `save(Aggregate)` / `findById(Id)`，隐藏持久化细节。
- 应用服务通过仓储获取聚合、调用行为、再保存。

```java
interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);
}
```

## 五、领域服务 vs 实体行为

- 行为属于某个实体 → 放实体（富模型）。
- 行为跨多个实体、无状态 → 放领域服务。
- 避免「贫血模型」（只有 getter/setter，逻辑全在 Service）。

## 六、领域事件

- 聚合内发生重要变化 → 发领域事件。
- 事件驱动后续动作，解耦聚合间协作。
- 可落库做事件溯源（Event Sourcing）或至少审计。

## 七、应用服务（Application Service）

- 编排用例：开事务 → 取聚合 → 调领域行为 → 保存 → 发事件。
- 应用服务是 DDD 里的「门面/外观」，不含业务规则细节。
- 见 [结构型/外观模式](../../设计模式/结构型/外观模式.md)。

## 八、与分层架构映射

```
接口层(Controller) → 应用层(Application Service) → 领域层(Domain) → 基础设施层(Repo Impl)
```

- 依赖倒置：领域层定义仓储接口，基础设施层实现（不反向依赖）。

## 九、常见误区

1. 大聚合 → 事务大、锁多、性能差。
2. 实体贫血 → 逻辑散在 Service，领域知识流失。
3. 仓储当 DAO → 暴露表细节，破坏聚合边界。
4. 聚合间用强一致 → 应事件最终一致。
5. 领域层依赖基础设施 → 应依赖倒置。

## 十、落地步骤

1. 事件风暴找实体/聚合/事件。
2. 定聚合边界（小聚合）。
3. 写领域行为（富模型）。
4. 定义仓储接口。
5. 应用服务编排 + 领域事件解耦。
