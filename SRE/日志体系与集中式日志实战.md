# 日志体系与集中式日志实战

> 板块：SRE 　|　 返回：[README](README.md)
> 适用：多实例、多服务的日志采集、检索、告警与审计。

日志是系统行为的"黑匣子"。单机 `tail -f` 在分布式下失效，必须**集中采集、结构化、可检索、可告警**。本文讲清日志规范、采集管道与最佳实践。

## 一、日志的层级

| 级别 | 用途 |
|------|------|
| DEBUG | 调试细节，生产默认关 |
| INFO | 关键流程/业务事件 |
| WARN | 可恢复异常、降级 |
| ERROR | 失败、需关注 |
| FATAL | 致命，服务可能不可用 |

> 原则：ERROR 必须可行动（能据之处理），避免噪声淹没真问题。

## 二、结构化日志

- **拒绝拼字符串**：用 JSON 结构化，便于机器检索。

```json
{"ts":"2026-08-31T10:00:00Z","level":"ERROR","svc":"order","trace_id":"abc","order_id":"o1","msg":"pay failed","err":"timeout"}
```

- 固定字段：时间戳、级别、服务名、trace_id、关键业务 ID。
- 好处：可按任意字段过滤、聚合、关联 trace。

## 三、集中式采集架构（ELK/Loki）

```
应用(文件/ stdout) → 采集Agent(Filebeat/Fluentd/Vector) → 缓冲(Kafka) → 处理/解析 → 存储(ES/Loki) → 检索(Kibana/Grafana)
```

- **采集**：DaemonSet（K8s 每节点一个 Agent）或 Sidecar。
- **缓冲**：Kafka 削峰，防日志洪峰冲垮存储。
- **解析**：提取字段、脱敏（去除密码/手机号）。
- **存储**：ES（全文+聚合强）、Loki（标签索引、成本低）。

## 四、日志规范

- **统一格式**：全公司 JSON 规范，字段命名一致。
- **关键 ID 贯穿**：trace_id、user_id、order_id 随日志输出，便于串联。
- **脱敏**：敏感字段（密码、token、PII）落盘前脱敏/加密。
- **不记大对象**：别把整个请求体/响应体打日志，防爆量与泄露。

## 五、检索与告警

- **检索**：按服务、级别、时间、业务 ID 过滤；全文搜关键字。
- **告警**：错误率突增、关键字（OOM/panic）出现、某接口 ERROR 数超阈值。
- **关联**：从告警下钻到日志，再关联到 trace（见[链路追踪与OpenTelemetry实战](链路追踪与OpenTelemetry实战.md)）。

## 六、生命周期与成本

- **分级存储**：热（最近 7 天，ES 快查）、温（30 天）、冷（归档对象存储）。
- **保留策略**：按合规要求设定（如 90 天），超期自动删。
- **采样**：DEBUG/INFO 高量日志可采样，ERROR 全留。

## 七、与可观测性关系

- 日志（根因细节）+ 指标（宏观趋势）+ 链路（路径）三支柱互补。
- 指标异常 → 下钻日志/trace → 定位根因。

## 八、常见坑

1. **非结构化日志** → 难检索；统一 JSON。
2. **无 trace_id** → 排障断层；全链路注入。
3. **敏感信息落盘** → 合规风险；脱敏。
4. **打全量大对象** → 爆量与泄露；只记关键字段。
5. **采集单点** → 日志丢失；Agent 高可用 + 缓冲。
6. **永久保留** → 成本失控；分级 + 保留期。
7. **ERROR 噪声多** → 真问题被淹；规范级别、可行动才 ERROR。
