# SLO 与错误预算实践

> 板块：SRE 　|　 返回：[README](README.md)

SLO（Service Level Objective）是 SRE 可靠性实践的核心：它用量化目标统一"业务诉求"与"工程投入"，并用"错误预算"把稳定性变成可消耗、可决策的资源。本文从定义、设计、落地到治理系统讲解。

## 一、SLI / SLO / SLA 辨析

### 1.1 SLI（Service Level Indicator）

可测量的服务水平指标，回答"系统现在表现如何"。
常见 SLI：
- 可用性（Availability）：成功请求 / 总请求。
- 延迟（Latency）：请求耗时达标比例（如 P99 < 300ms 的比例）。
- 吞吐量（Throughput）：单位时间处理量。
- 质量（Quality）：如推荐点击率、渲染成功率。
- 正确性（Correctness）：数据一致、计算准确比例。

选 SLI 的原则：**用户能感知、可测量、可归因**。

### 1.2 SLO（Service Level Objective）

对 SLI 设定的目标值，例如"月度可用性 ≥ 99.9%"。SLO 是内部承诺，是可靠性建设的"标尺"。

### 1.3 SLA（Service Level Agreement）

对用户的正式合同，常带违约赔偿条款。SLA 通常比内部 SLO 宽松，预留缓冲。

### 1.4 三者关系

```
用户感知 → SLI 测量 → SLO 内部目标 → SLA 对外承诺
                 ↑
          错误预算 = 100% - SLO
```

## 二、为什么需要错误预算

错误预算（Error Budget）= 1 - SLO。例如 99.9% 可用性意味着：
- 月允许不可用时间 ≈ 43.8 分钟（30 天计）。
- 即"本月最多有 0.1% 的请求可以失败"。

它的价值在于把"稳定性"从模糊口号变成**可消耗资源**，并平衡两个长期冲突的目标：
- 可靠性团队希望系统"别动"。
- 研发团队希望"快速迭代"。

错误预算作为"共同语言"：
- 预算充足 → 大胆发布、做实验。
- 预算烧完 → 冻结非必要变更，先恢复稳定性。

## 三、如何定义好的 SLO

### 3.1 从用户旅程出发

不要对所有接口一刀切。先锁定**关键用户旅程**（如"能下单""能登录""能看视频"），每个旅程定义自己的 SLI/SLO。

### 3.2 明确"失败"的定义

SLI 计算前必须说清"什么算失败"：
- HTTP 5xx？还是含 4xx 中的特定类？
- 延迟超 1s 算失败，还是超 3s？
- 部分降级（返回缓存）算成功还是失败？

定义不清会导致反复扯皮。

### 3.3 目标设定技巧

- 不要设 100%：永远超支、失去意义。
- 基于现状 + 改进空间：起步可略高于当前水平，逐步收紧。
- 分窗口：常用 28 天滚动窗口，避免月初/月末抖动。
- 不同层级不同目标：核心交易 99.95%，内部工具 99.0%。

### 3.4 多窗口多燃烧率

进阶做法：用"燃烧率（burn rate）"告警——
- 短时间快速烧预算（如 1 小时烧掉 2% 预算）立即告警。
- 长时间慢速烧（如 1 天烧 5%）也应告警。
- 避免"预算快没了但没立刻宕机"被忽略。

## 四、错误预算策略（Policy）

### 4.1 预算充足（> 剩余）

- 正常发布节奏。
- 可做有风险但高价值的变更。
- 可做故障演练、混沌工程。

### 4.2 预算告急（接近耗尽）

- 冻结非关键发布（仅放行紧急修复）。
- 触发稳定性专项，复盘根因。
- 暂停实验性特性。

### 4.3 预算耗尽

- 全面冻结发布（change freeze）。
- 成立稳定性作战室，优先恢复。
- 复盘并立项架构改造。

### 4.4 多次烧完

说明 SLO 设定或系统本身有结构性问题：
- 要么 SLO 不现实（下调）。
- 要么架构脆弱（限流/降级/扩容/重构）。

## 五、落地步骤

1. 识别关键旅程，定义 SLI（最好可自动采集）。
2. 设 SLO 目标与窗口。
3. 搭建错误预算看板（剩余预算、燃烧速率）。
4. 配置预算告警（阈值 + 燃烧率）。
5. 制定预算策略并写进团队规范。
6. 定期复盘，调整 SLO 与策略。

## 六、与发布流程结合

- 发布前看预算：告急则走"快速通道审批"或推迟。
- 发布后盯燃烧：新版本若快速烧预算，自动回滚或人工介入。
- 把"预算消耗"作为发布门禁（gate）之一。

## 七、与 OnCall 的关系

- 错误预算告警应升级为事件，进入 OnCall 流程。
- 预算烧完期间的高优告警需立即响应。
- 复盘结论应形成改进项并跟踪闭环。

## 八、常见坑

1. **SLO 设 100%** → 永远超支，指标失去意义。
2. **SLI 定义不清** → 各方对"是否达标"理解不一，扯皮。
3. **预算无动作** → 形同虚设，烧完照样狂发版。
4. **只盯可用性忽略延迟** → 系统"活着但慢"，用户体验崩。
5. **SLO 一刀切** → 核心与非核心同目标，资源错配。
6. **无历史基线** → 拍脑袋定目标，不合理。
7. **告警过噪** → 预算相关告警被淹没，没人看。

## 九、示例：下单服务 SLO

- SLI：下单请求成功率（HTTP 2xx 且 5s 内返回）。
- SLO：月度 ≥ 99.95%（月允许 ~21 分钟不可用）。
- 预算看板：剩余预算 0.04%，燃烧率告警（1h 烧 >1% 即 P1）。
- 策略：预算 < 0.02% 冻结非紧急发布，回滚最近变更复盘。
