# 可观测性三支柱实战（Metrics/Logs/Traces）

> 板块：SRE 　|　 返回：[README](README.md)

## 一、可观测性的目标

系统出问题能「看见、定位、预测」。三支柱：

- **Metrics（指标）**：聚合数值，看趋势与告警（CPU、QPS、错误率）。
- **Logs（日志）**：离散事件，查细节。
- **Traces（链路）**：一次请求跨服务的完整路径，定位慢调用。

## 二、Metrics

- 工具：Prometheus（拉模型）+ Grafana。
- 四大黄金信号：延迟、流量、错误、饱和度。
- RED（请求/错误/时延）或 USE（利用率/饱和度/错误）方法论。

```yaml
# Prometheus 抓取示例
scrape_configs:
  - job_name: api
    static_configs: [{ targets: ["api:8080"] }]
```

## 三、Logs

- 结构化日志（JSON），便于检索。
- 栈：Loki（轻量）/ ELK（重但全）。
- 关键：关联 trace_id，日志可跳链路。

## 四、Traces

- OpenTelemetry 统一采集，导出到 Jaeger/Tempo。
- 自动埋点（拦截器/agent）+ 手动埋点（关键业务段）。
- 看「哪个服务、哪个方法慢」。

## 五、三者关联

- 用统一 `trace_id` / `span_id` 串联：告警（Metrics）→ 下钻链路（Traces）→ 看日志（Logs）。

## 六、告警设计

- 告警要「可行动」，避免狼来了。
- 用 SLO + 错误预算驱动告警。
- 分级：page（立即）/ ticket（工作日）。

## 七、SLO 与错误预算

- SLO = 目标可用性（如 99.9%）。
- 错误预算 = 1 - SLO，烧完则冻结发布。

## 八、常见坑

1. 只装不告警 → 看不见故障。
2. 日志不打 trace_id → 无法关联。
3. 指标太多 → 抓不住重点。
4. 采样率太低 → 漏慢请求。
