# 可观测性三支柱实战（Metrics / Logs / Traces）

> 板块：SRE 　|　 返回：[README](README.md)

可观测性（Observability）回答三个问题：系统**是否**正常（Metrics）、**为什么**异常（Logs）、**哪里**慢（Traces）。三支柱协同才能从"告警"下钻到"根因"。本文从目标、工具、数据模型、关联与告警落地讲解。

## 一、可观测性的目标

当系统出问题，工程团队要能：
- **看见**：实时掌握系统状态。
- **定位**：快速缩小到具体服务/方法/依赖。
- **预测**：从趋势发现容量/劣化风险。

"可观测性"区别于"监控"：监控是看已知指标，可观测性是凭输出推断未知内部状态的能力。

## 二、三大支柱

### 2.1 Metrics（指标）

- 聚合的数值时间序列：CPU、QPS、错误率、延迟分布。
- 优点：轻量、适合趋势与告警。
- 缺点：丢失个体细节（一个 500 错误背后是哪次请求？指标答不了）。
- 工具：Prometheus（拉模型）+ Grafana（可视化）、VictoriaMetrics 等。

### 2.2 Logs（日志）

- 离散的事件记录：某次请求发生了什么、报错堆栈。
- 优点：细节丰富，便于排查根因。
- 缺点：量大、成本高、难直接看趋势。
- 栈：Loki（轻量、与 Prometheus 同源）、ELK（重但全功能）。

### 2.3 Traces（链路追踪）

- 一次请求跨多个服务的完整调用路径，含每段耗时。
- 优点：定位"哪个服务、哪个方法慢/错"。
- 工具：OpenTelemetry（采集标准）+ Jaeger / Tempo（存储展示）。

## 三、核心方法论

### 3.1 四大黄金信号（Google SRE）

- **延迟（Latency）**：请求耗时（区分成功/失败）。
- **流量（Traffic）**：系统承受的负荷（QPS、并发）。
- **错误（Errors）**：失败比例。
- **饱和度（Saturation）**：资源使用接近上限的程度。

### 3.2 RED 与 USE

- **RED**（服务视角）：Rate（请求率）、Errors（错误率）、Duration（时延分布）。
- **USE**（资源视角）：Utilization（利用率）、Saturation（饱和度）、Errors（错误）。

## 四、Prometheus 实战

```yaml
# 抓取配置示例
scrape_configs:
  - job_name: api
    static_configs:
      - targets: ["api:8080"]
```

- 指标类型：Counter（只增）、Gauge（瞬时）、Histogram（分布/分位）、Summary。
- PromQL：率 `rate(http_requests_total[5m])`、分位 `histogram_quantile(0.99, ...)`。
- 告警规则：`error_rate > 0.01` 触发。

## 五、结构化日志

- 用 JSON 结构化（含 level、trace_id、service、timestamp），便于检索与过滤。
- 关键：每条日志带 **trace_id**，使日志可跳转到链路。
- 分级：DEBUG/INFO/WARN/ERROR，生产控制级别与采样，避免爆量。

## 六、链路追踪与 OpenTelemetry

- OpenTelemetry 统一 SDK/协议，采集后导出到 Jaeger/Tempo。
- 自动埋点：框架拦截器/agent 自动生成 span（HTTP、DB、MQ）。
- 手动埋点：关键业务段标注 span，补充业务语义。
- 采样：高流量时按比例采样（如 10%），平衡成本与覆盖。

## 七、三者关联（核心）

统一 `trace_id` / `span_id` 串联：

```
告警（Metrics：错误率突增）
  → 下钻链路（Traces：定位到 payment 服务慢）
    → 看日志（Logs：该 trace_id 下的 DB 超时堆栈）
```

没有关联，三者是孤岛；有了关联，排障时间从小时级降到分钟级。

## 八、告警设计

- **可行动**：收到就要处理，避免"狼来了"。
- **分级**：page（立即响应 P0/P1）/ ticket（工作时间处理 P2/P3）。
- **驱动**：用 SLO + 错误预算触发，而非随意阈值。
- **收敛**：去重、分组、抑制、静默，提升信噪比。

## 九、常见坑

1. **只装不告警** → 看得见故障但没人被通知。
2. **日志不打 trace_id** → 无法关联，排障靠猜。
3. **指标过多无重点** → 盯不过来，关键信号被淹没。
4. **采样率太低** → 漏掉慢请求/偶发错误。
5. **三支柱割裂** → 没有统一 ID，下钻断链。
6. **日志全量不分级** → 成本爆炸、检索困难。
