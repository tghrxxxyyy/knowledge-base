# 故障演练与稳定性保障

> 板块：SRE 　|　 返回：[README](README.md)

稳定性不是"不出故障"，而是"出了故障能快速发现、快速止损、快速恢复"。SRE 用工程化手段（混沌工程、熔断降级、容量压测、应急预案、无指责复盘）把稳定性变成可训练、可度量、可持续改进的能力。本文系统拆解。

## 一、稳定性优先的理念

### 1.1 功能与稳定的关系

新功能带来价值，但一次大故障可能抹掉数月积累的用户信任。
在关键系统上，"不出事"通常比"多一个功能"更重要。

### 1.2 错误是常态

任何复杂系统都会出错：硬件坏、网络抖、依赖挂、发布引入 bug。
目标不是消除错误，而是**限制错误的影响范围与持续时间**。

## 二、混沌工程（Chaos Engineering）

### 2.1 核心思想

主动注入故障，在受控环境下验证系统是否如预期般韧性。
不是"搞破坏"，而是"验证假设"。

### 2.2 经典实验

- 杀进程/杀 Pod：验证自愈与重试。
- 断网络/增加延迟：验证超时、熔断、降级。
- 压满 CPU/内存：验证限流与资源隔离。
- 断开依赖（DB/MQ/缓存）：验证降级路径。

### 2.3 工具与原则

- 工具：Chaos Mesh、Litmus、自研脚本。
- 原则：
  - 从小范围开始（单实例、单可用区）。
  - 有清晰假设（"杀掉一个节点，请求应自动转移"）。
  - 有止损开关（一键回滚实验）。
  - 在生产或类生产环境才有意义（但需谨慎）。

## 三、熔断、降级、限流

### 3.1 熔断（Circuit Breaker）

- 依赖错误率/响应时间超阈值时，暂时"切断"调用，直接快速失败。
- 半开状态探测依赖是否恢复，恢复后闭合。
- 工具：Sentinel、Resilience4j、Hystrix（理念）。
- 防止"一个慢依赖拖垮整个调用链"。

### 3.2 降级（Degradation）

- 关闭非核心功能，保核心链路：如推荐关掉、保下单。
- 静态兜底：返回缓存/默认值/简化结果。
- 降级开关要可动态配置、可灰度、可一键恢复。

### 3.3 限流（Rate Limiting）

- 保护自身不被打垮：令牌桶、漏桶、滑动窗口。
- 多维度：单用户、单 IP、整体 QPS。
- 过载时直接拒绝（快速失败）优于雪崩。

三者配合：**限流防过载 → 熔断防雪崩 → 降级保核心**。

## 四、容量规划与全链路压测

### 4.1 全链路压测

- 用真实流量模型（或影子流量）打通整条链路压测。
- **流量染色 + 影子库/表**：压测数据不污染真实数据。
- 找出各层瓶颈（网关、应用、DB、缓存、MQ）。

### 4.2 容量规划

- 按历史峰值 × 增长系数 × 冗余（如 1.5~2 倍）预留容量。
- 识别单点瓶颈（某服务只有一份实例）。
- 提前扩容预案（大促前压测 + 扩缩容演练）。

## 五、应急预案（Runbook）

### 5.1 每个核心链路要有 runbook

- 现象 → 可能原因 → 止损动作 → 恢复动作。
- 精确到命令/开关/负责人。
- 存储在易检索处（Wiki/知识库/OnCall 平台）。

### 5.2 定期演练

- 预案不演练 = 纸面文章。
- 故障演练中故意触发预案，验证可操作性。
- 发现预案过期（命令错、开关名变）及时修正。

## 六、监控与发现

- 故障早发现 = 损失小。
- 监控要覆盖：基础设施、中间件、应用、业务全链路。
- 关键路径设告警，避免"监控盲区"（如漏了某依赖的健康检查）。
- 真实用户监控（RUM）补充"系统健康但用户侧已坏"的盲区。

## 七、复盘（Postmortem）

### 7.1 无指责（Blameless）

- 聚焦系统与人因，而非"谁犯的错"。
- 追责会让当事人隐瞒信息，错失根因。
- 目标：同样的故障不再因同样原因复发。

### 7.2 复盘结构

- 时间线：从最早异常到恢复，逐事件记录。
- 影响范围：受影响用户/请求/时长/资损。
- 根因：直接原因 + 深层原因（流程/架构/监控缺口）。
- 行动项：具体改进、负责人、期限，必须跟踪闭环。

## 八、常见坑

1. **只压测单接口不压全链路** → 链路某处突发瓶颈没暴露。
2. **降级开关没测过** → 真用时失效，雪崩。
3. **复盘无行动项** → 同样的故障反复发生。
4. **监控盲区** → 故障发现晚，MTTR 拉长。
5. **混沌实验无止损** → 演练变真实事故。
6. **只靠堆机器** → 架构性单点不解决，扩容也救不了。
