# 混沌工程与故障注入实战

> 板块：SRE 　|　 返回：[README](README.md)
> 适用：验证系统韧性、提前暴露脆弱点、建立故障应对信心。

混沌工程不是"故意搞破坏"，而是**用受控的实验主动验证系统在故障下的行为**，把"未知的未知"变成"已知的已知"。Netflix 的 Chaos Monkey 是鼻祖。

## 一、核心原则

1. **先建稳定态假设**：明确"正常时系统长什么样"（如错误率<0.1%、P99<200ms）。
2. **用真实故障**：注入生产级故障（杀节点、断网络、加延迟），而非玩具故障。
3. **最小化爆炸半径**：从小范围、可恢复开始，逐步扩大。
4. **自动化实验**：像测试一样常态化跑，而非一次性。
5. **持续验证**：韧性是动态的，需持续实验。

## 二、典型故障注入

| 故障 | 注入方式 | 验证什么 |
|------|----------|----------|
| 节点宕机 | Kill Pod/进程 | 副本能否接管、有无单点 |
| 网络延迟/丢包 | tc/netem、Istio 故障注入 | 超时/重试/降级是否生效 |
| 依赖不可用 | 熔断下游、返回 500 | 熔断/降级是否保护核心 |
| 资源耗尽 | CPU/内存/磁盘压满 | 限流/驱逐/自愈 |
| 时钟漂移 | 改系统时间 | 时间敏感逻辑 |
| 数据损坏 | 写坏数据 | 校验/恢复 |

## 三、实验流程

```
定义假设 → 设计实验(故障+范围+指标) → 执行(自动注入+监控) → 观察(稳定态是否破坏)
   → 恢复 → 分析(是否符合假设) → 改进(修脆弱点) → 沉淀为回归实验
```

## 四、工具

| 工具 | 能力 |
|------|------|
| Chaos Mesh | K8s 原生，丰富故障类型 |
| Litmus | K8s 混沌，CNCF 项目 |
| Gremlin | 商业，全栈故障注入 |
| Toxiproxy | 网络层延迟/断连 |
| 自研脚本 | Kill/资源压测（简单场景） |

## 五、在 K8s 中的实践

```yaml
# Chaos Mesh 示例：随机杀掉一个 Pod
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: { name: kill-pod }
spec:
  action: pod-kill
  mode: one
  selector: { labelSelectors: { app: order-service } }
  scheduler: { cron: "@every 10m" }
```

- 配合 **就绪探针/自愈**：杀掉后 K8s 自动重建，验证自愈。
- 配合 **熔断/限流**：依赖故障时验证保护是否生效。

## 六、与监控/告警联动

- 实验期间必须有人盯监控（或自动判稳）。
- 若稳定态被破坏（如错误率飙升、核心不可用），立即终止实验（abort）。
- 实验即"演习"，验证告警是否真的会被触发、oncall 是否响应。

## 七、组织与文化

- **游戏日（Game Day）**：团队一起跑故障演练，模拟真实事故。
- **无指责复盘**：实验暴露问题不追责，聚焦系统改进。
- **逐步常态化**：从演练到自动化工单/CI 集成。

## 八、常见误区

1. **在生产乱搞** → 大事故；控制爆炸半径 + 随时可终止。
2. **只注入不看指标** → 不知是否破坏；稳定态假设 + 实时监控。
3. **一次性演练** → 韧性退化；常态化 + 回归。
4. **只测基础设施** → 漏掉应用层；结合业务级故障（依赖返回脏数据）。
5. **无恢复验证** → 不知能否恢复；必须验证自愈。
6. **畏惧混沌** → 隐患留到真故障；小步快跑建立信心。
