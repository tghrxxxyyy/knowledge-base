# 容量规划与全链路压测实战

> 本文聚焦 SRE 体系中"容量"主题：容量评估方法、全链路压测的实施、流量模型构建、限流降级预案、扩容策略与容量基线。内容基于业界公开实践，具体阈值以业务实际为准。

## 1. 容量规划的目标

容量规划回答三个问题：

- 当前系统能扛多少流量（容量上限）？
- 大促/峰值需要多少资源（扩容目标）？
- 哪里是瓶颈（扩容优先级）？

目标是在"成本"与"风险"间平衡：备太多浪费，备太少宕机。

## 2. 容量评估方法

### 2.1 基于历史流量

- 取历史峰值（如去年双十一）并叠加业务增长系数（如 1.5–3 倍）。
- 考虑自然增长 + 活动增量 + 突发预留。

### 2.2 基于单实例容量

- 压测单节点（如单 Pod）在目标延迟下的 QPS 上限。
- 总容量 ≈ 单实例容量 × 实例数 × 安全系数（如 0.7，留余量）。

### 2.3 基于瓶颈资源

- CPU 型：QPS 随核数近似线性。
- IO 型：受磁盘/网络带宽限制。
- 内存型：受堆/缓存大小限制。
- 锁/连接型：受连接池、慢查询影响。

## 3. 全链路压测

### 3.1 为什么"全链路"

单接口压测不能反映真实瓶颈（一条请求串起多个服务，瓶颈常在链路最弱处）。全链路压测在**生产或等比环境**模拟真实流量路径。

### 3.2 影子链路

生产压测需隔离真实数据：用"影子表/影子 Topic/影子标"承载压测流量，避免污染线上数据与用户。

- 影子库表：压测写影子表，读可走真实（只读）或影子。
- 流量标记：请求带 `shadow=true`，中间件路由到影子资源。
- 数据清理：压测后清理影子数据。

### 3.3 流量模型

- **目标 QPS**：按业务预估峰值。
- **读写比**：贴近真实（如 9:1 读多写少）。
- **接口占比**：按线上真实接口分布加权（热门接口占比高）。
- **数据分布**：热点 key、冷数据混合。
- **思考时间**：模拟真实用户行为间隔。

### 3.4 压测执行

- 逐步加压（ramp-up），观察各层指标拐点。
- 记录：QPS、P99 延迟、错误率、资源利用率、慢查询、GC。
- 找到"拐点"（延迟骤升/错误率上升）即容量上限。

## 4. 限流、降级、熔断预案

压测暴露上限后，需有保护手段：

- **限流**：令牌桶/漏桶，保护系统不被打垮（见限流算法章节）。
- **降级**：非核心功能（推荐、评论）在高压时关闭，保核心链路。
- **熔断**：下游异常时快速失败，避免雪崩。
- **排队**：请求入队削峰（如抢购排队）。

预案要提前演练，而非故障时才定。

## 5. 扩容策略

### 5.1 水平 vs 垂直

- **水平扩容**：加实例，适用于无状态服务（最常见）。
- **垂直扩容**：升配置，受单机上限与成本约束。

### 5.2 弹性伸缩

- **HPA（K8s）**：基于 CPU/QPS/自定义指标自动扩缩。
- **定时扩缩**：大促前提前扩容，避免冷启动慢。
- **预测扩容**：基于历史曲线提前准备。

### 5.3 有状态服务的容量

- 数据库扩容难（分库分表、主从、读写分离）。
- 缓存扩容需考虑预热（冷启动命中率低）。
- 消息队列扩容需考虑分区再均衡。

## 6. 容量基线

建立"单接口/单服务"容量基线文档：

- 正常水位：日常 QPS 与资源。
- 预警水位：达到即告警（如 CPU 70%）。
- 极限水位：压测拐点。
- 扩容触发：超过某水位自动/人工扩容。

## 7. 大促备战流程

1. **目标对齐**：业务方给预估峰值与活动节奏。
2. **容量评估**：各服务算所需实例。
3. **全链路压测**：验证并找瓶颈。
4. **优化**：慢 SQL、缓存、扩容、限流参数。
5. **预案评审**：降级/限流/熔断/值班。
6. **演练**：故障注入、切流演练。
7. **值班监控**：实时看板 + 告警。

## 8. 指标与看板

- **流量**：QPS、UV、峰值时刻。
- **资源**：CPU、内存、连接数、带宽。
- **质量**：P99 延迟、错误率、慢请求。
- **依赖**：下游耗时、缓存命中率、DB QPS。
- **业务**：下单成功率、支付成功率。

## 9. 常见踩坑

1. **只压单接口**：忽略链路瓶颈，上线仍崩。
2. **压测数据污染生产**：未用影子链路，脏数据影响真实用户。
3. **容量系数拍脑袋**：无数据支撑，备少了宕机备多了浪费。
4. **无降级预案**：高峰时只能"硬扛"，核心非核心一起挂。
5. **缓存冷启动**：扩容后缓存空，DB 被打爆；需预热。
6. **忽视依赖容量**：自身扩容了，但第三方/DB 没扩，照样瓶颈。
7. **压测不持续**：一次压测定终身，架构变了不重测。

## 10. 工具与生态

- 压测工具：分布式压测框架（如 JMeter 集群、Gatling、k6、自研）。
- 流量录制回放：录制线上真实流量回放。
- 监控：Prometheus/Grafana 实时看板。
- 混沌：配合故障演练验证预案。

## 11. 小结

容量规划是"数据驱动 + 预案兜底"的活：用历史与压测定基线，用全链路压测找瓶颈，用限流降级熔断保底，用弹性扩容应对峰值。核心铁律是——**大促前必须真刀真枪压测与演练，预案写进文档不如演练一遍**。
