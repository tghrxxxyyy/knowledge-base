# 可观测性与监控开源生态再探

> 本文聚焦"可观测性三支柱"（Metrics、Logs、Traces）之外的工程化落地细节，覆盖 Prometheus、Grafana、VictoriaMetrics、Loki、Tempo、Jaeger、OpenTelemetry 等开源项目，重点讲清数据模型、采集链路、存储取舍与告警设计。特性以官方文档为准。

## 1. 可观测性的本质

可观测性（Observability）源于控制论：通过系统的外部输出推断内部状态的能力。工程上用三支柱刻画：

- **Metrics（指标）**：聚合的数值时间序列，回答"系统整体怎样"（QPS、延迟、错误率）。
- **Logs（日志）**：离散的事件记录，回答"某一刻发生了什么"。
- **Traces（链路）**：一次请求跨服务的调用路径，回答"这次慢在哪里"。

三者在"粒度—成本"上权衡：指标最省、日志最贵但最详细、链路居中。生产实践以指标为主、链路定位、日志取证。

## 2. Prometheus：指标的事实标准

### 2.1 数据模型

Prometheus 使用**时间序列**模型：每条序列由 metric name + 一组 label（键值对）唯一标识。样本（sample）是带时间戳的 float64 值。

```
http_requests_total{method="GET",status="200"} 1027 @ 1700000000
```

### 2.2 四种指标类型

- **Counter**：只增不减的累加器（请求数、错误数）。用 `rate()` 求速率。
- **Gauge**：可增可减的瞬时值（内存占用、在途请求数）。
- **Histogram**：把观察值分桶（bucket），统计落入各桶的计数，可算分位数近似（用 `histogram_quantile`）。
- **Summary**：客户端直接计算分位数，精度好但不可聚合。

### 2.3 拉模型（Pull）

Prometheus 主动从 target 的 `/metrics` 抓取（scrape），而非 agent 推送。优点：target 无状态、便于服务发现、抓取失败易察觉。缺点：短生命周期任务需 Pushgateway 中转。

### 2.4 PromQL 核心

- 即时向量：`up{job="api"}`
- 范围向量：`rate(http_requests_total[5m])`
- 聚合：`sum by (status) (rate(...))`
- 分位：`histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))`

### 2.5 局限

- 单机 TSDB，海量序列（高基数 label）下内存与磁盘压力大。
- 不是长期存储方案（默认保留期短），需远程写（remote write）到长期存储。
- 全局视图需 Thanos / VictoriaMetrics / Cortex 等扩展。

## 3. VictoriaMetrics：高性能长期存储

VictoriaMetrics（VM）是 Prometheus 兼容的时序数据库，以高写入吞吐、高压缩比、低内存著称。

- **协议兼容**：可直接作为 Prometheus 的 remote write 后端，或替代 Prometheus 抓取。
- **架构**：单节点版（small）与集群版（vminsert/vmstorage/vmselect）可选。
- **查询**：支持 PromQL（MetricsQL 扩展），兼容 Grafana。
- **优势**：高基数场景优于原生 Prometheus；资源占用低；全球多租户友好。

适用：需要长期保留、大规模指标、降本替换 Prometheus 存储的团队。

## 4. Grafana：可视化与告警统一面板

Grafana 是面板层，连接 Prometheus / VM / Loki / Tempo 等多种数据源，用 Dashboard（JSON）组织图表。

- **Panel**：图表、表格、热力图、状态表。
- **Variables**：模板变量做下拉筛选（如按集群、服务）。
- **Alerting**：统一告警规则（Grafana 8+ 的 unified alerting），支持多数据源、静默、路由到钉钉/飞书/Slack/Webhook。
- **Provisioning**：用配置文件声明数据源与面板，GitOps 化管理。

## 5. Loki：日志的"类 Prometheus"方案

Loki 的设计哲学是"只索引元数据（label），不索引全文"，日志内容按块存储。查询用 LogQL，概念与 PromQL 相似。

- **优点**：存储成本低（类似对象存储），与 Prometheus label 模型一致，运维简单。
- **缺点**：全文检索不如 ES 灵活，复杂日志分析弱。
- **适用**：以"标签过滤 + 关键字"为主的日志场景，与 Prometheus/Grafana 同栈。

## 6. Tempo 与 Jaeger：分布式追踪

### 6.1 OpenTelemetry 先行

OpenTelemetry（OTel）是**厂商中立**的可观测性数据采集标准，提供 SDK（埋点）与 Collector（接收/处理/导出）。它统一了 traces/metrics/logs 的语义约定（如 span 命名、属性 key），是当下事实采集层。

### 6.2 Jaeger

Jaeger 是 CNCF 老牌追踪系统，提供采集（agent/collector）、存储（ES/Cassandra/内存）、UI。适合已有 Jaeger 体系的团队。

### 6.3 Tempo

Tempo 是 Grafana 生态的追踪后端，专注"低成本存储 trace"，与 Loki/Grafana 联动做"指标→链路→日志"跳转。查询走 TraceQL。

### 6.4 链路打通示例

```
请求进入 → OTel SDK 生成 span → Collector → Tempo
                                   ├─ metrics → Prometheus
                                   └─ logs    → Loki
Grafana 中从慢指标下钻到 trace，再跳转相关日志
```

## 7. 告警设计原则

- **黄金信号**：延迟（Latency）、流量（Traffic）、错误（Errors）、饱和度（Saturation）。
- **SLO 驱动**：基于错误预算设告警，而非对每条指标拍阈值。
- **分级**：page（需立即处理）与 ticket（工作时间处理）分离。
- **避免告警疲劳**：合并、去重、静默维护期。
- **可行动**：每条告警都应对应明确处理动作，否则降为仪表盘观察。

## 8. 采样与成本

- **指标**：控制 label 基数（避免把 user_id 当 label）。
- **链路**：全采样成本高，常用头部采样/尾部采样（tail-based）保留错误与慢链路。
- **日志**：结构化（JSON）、分级（debug/info/warn/error）、热冷分层存储。

## 9. 常见踩坑

1. **高基数爆炸**：把无界值（request_id、ip）做 label，导致序列数暴涨拖垮 Prometheus；应放日志而非 label。
2. **histogram 桶设计不当**：桶边界没覆盖真实延迟分布，分位估算失真；应据 SLO 设桶。
3. **Loki 全文检索误用**：想做复杂日志分析却没上 ES，导致查询受限；按场景选型。
4. **告警阈值拍脑袋**：无 SLO 依据，误报/漏报；应基于错误预算。
5. **Trace 上下文丢失**：跨线程/跨进程未传播 context，链路断链；用 OTel 传播器统一。
6. **远程写后端单点**：Prometheus remote write 到单 VM 实例无冗余，需集群化。

## 10. 选型速查

| 需求 | 首选 |
|---|---|
| 指标采集+告警 | Prometheus |
| 长期/大规模指标 | VictoriaMetrics / Thanos |
| 可视化面板 | Grafana |
| 低成本日志 | Loki |
| 强全文日志检索 | Elasticsearch |
| 链路追踪 | Jaeger / Tempo |
| 统一采集埋点 | OpenTelemetry |

## 11. 小结

可观测性不是"装三个系统"就完事，而是围绕"用最低成本最快定位问题"做工程取舍。现代主流栈是 **OpenTelemetry 采集 + Prometheus/VictoriaMetrics 指标 + Loki/Tempo 日志链路 + Grafana 统一展示**，以 SLO 驱动告警。避免高基数与无脑全采样是落地成败关键。
