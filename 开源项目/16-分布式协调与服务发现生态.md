# 分布式协调与服务发现开源生态

> 本文梳理分布式系统中"协调（Coordination）"与"服务发现（Service Discovery）"两大基础能力的主流开源实现，覆盖 ZooKeeper、etcd、Consul、Nacos、CoreDNS 等，重点对比其一致性模型、数据模型、典型用法与适用边界。内容基于各项目的公开设计与工程实践，具体版本特性以官方文档为准。

## 1. 为什么需要协调与服务发现

在单机时代，进程间通过内存变量、锁即可完成同步；进入分布式后，多个节点需要就"谁是主""配置在哪""某个资源是否被占用"达成一致，这就是协调问题。服务发现则解决"上游如何找到下游实例列表并感知其变化"的问题。

二者常常耦合在同一组件里：

- **协调**关注一致性语义：选主（Leader Election）、分布式锁、屏障（Barrier）、成员管理（Group Membership）。
- **服务发现**关注可达性：服务注册（Register）、健康检查（Health Check）、查询（Query）、变更通知（Watch/Notify）。

典型场景：

- 配置中心：把配置放在协调服务中，应用监听变更热更新。
- 注册中心：服务启动时注册自身，下线时注销，消费者拉取/订阅实例列表。
- 分布式锁：在协调服务上创建临时顺序节点实现互斥。
- 选主：多个副本竞选 Leader，失败者变为 Follower 并监听 Leader 变化。

## 2. ZooKeeper：CP 系统的经典代表

### 2.1 定位与数据模型

ZooKeeper 是 Hadoop 生态早期诞生的协调服务，采用 **ZAB（ZooKeeper Atomic Broadcast）** 协议保证日志顺序一致，提供类文件系统的层级命名空间（znode）。

znode 关键属性：

- **持久节点（Persistent）**：创建后一直存在，直到显式删除。
- **临时节点（Ephemeral）**：客户端会话结束即删除，常用于"存活标记"。
- **顺序节点（Sequential）**：创建时自动追加单调递增序号，是分布式锁/选主的基础。
- **临时顺序节点（Ephemeral Sequential）**：上述两者结合，最经典的锁实现方式。

### 2.2 核心机制

**Watcher 一次性订阅**：客户端对节点注册 Watcher，当节点发生变化（数据写、子节点增减）时收到一次通知。注意 Watcher 是一次性的，收到通知后需重新注册，否则会漏掉后续变更。这是 ZooKeeper 客户端常见踩坑点。

**Session 与超时**：客户端与服务器维持会话，定期发送心跳。若会话超时（未收到心跳），其创建的临时节点会被清除，触发依赖这些节点的锁/选主重新选举。

**写流程**：所有写请求由 Leader 处理，先写本地日志，再广播给 Follower，收到多数派（quorum）ACK 后提交并应答客户端。读请求可由任意节点服务，但读到的是该节点本地视图，可能落后——如需强一致读，可调用 `sync()` 后再读。

### 2.3 典型用法：分布式锁

基于临时顺序节点实现：

1. 在 `/locks/resource` 下创建临时顺序节点 `/locks/resource/lock-`。
2. 获取该父节点下所有子节点，按序号排序。
3. 若自己创建的节点序号最小，则获得锁；否则监听前一个序号节点。
4. 释放锁（客户端断开或显式删除节点）后，下一个监听者被唤醒重试。

> 工程提示：Curator 框架的 `InterProcessMutex` 已封装上述逻辑，生产环境建议直接使用，而非手写。

### 2.4 适用与局限

- 优点：语义成熟、生态广、强一致、临时节点天然适合存活检测。
- 局限：Watcher 一次性、客户端需自己处理重连与重试；不适合做大规模 KV 存储或高频写（写走 Leader，存在单点瓶颈）；运维相对重。

## 3. etcd：Kubernetes 背后的协调基石

### 3.1 定位

etcd 是 CoreOS 开源的分布式 KV 存储，使用 **Raft** 一致性算法，是 Kubernetes 的默认后端存储。它更偏向"可靠的小数据 KV"，API 简洁（gRPC + HTTP），watch 机制比 ZooKeeper 更现代。

### 3.2 核心特性

- **Raft 共识**：强 Leader，日志复制，多数派提交，自动选主与成员变更。
- **MVCC + 多版本**：每次写产生新 revision，可基于历史 revision 监听，天然支持"从某版本开始 watch"。
- **Lease（租约）**：客户端申请租约并绑定 key，租约到期未续约则绑定 key 自动删除——等价于 ZooKeeper 的临时节点，用于服务注册存活检测。
- **Watch**：支持前缀、区间、从历史 revision 开始监听，且是持续性的（不像 ZK 一次性）。
- **事务（Txn）**：支持 `If-Then-Else` 条件写，可实现 CAS 语义的分布式锁。
- **compact**：因 MVCC 多版本，需定期压缩历史版本以回收空间。

### 3.3 分布式锁与选主

etcd 官方提供 `concurrency` 库，封装了：

- **Mutex**：基于带租约的 key 与事务竞争，持锁方需定期 `KeepAlive` 续租。
- **Election**：基于带序号的 key 竞选 Leader。

由于 watch 是持续性的且支持 revision，etcd 的客户端逻辑通常比 ZooKeeper 更简单、更不易漏事件。

### 3.4 与 ZooKeeper 对比

| 维度 | ZooKeeper | etcd |
|---|---|---|
| 一致性协议 | ZAB | Raft |
| 数据模型 | 层级 znode | 扁平 KV（支持前缀） |
| Watch | 一次性 | 持续、支持历史 revision |
| 临时节点 | Ephemeral 节点 | Lease 绑定 key |
| 典型用户 | Hadoop/HBase/Dubbo | Kubernetes |
| 运维复杂度 | 中 | 中（K8s 内较成熟） |

## 4. Consul：服务发现 + 配置 + 多数据中心

### 4.1 定位

Consul 由 HashiCorp 出品，主打"服务网格 + 服务发现 + KV 配置 + 多数据中心"。它在一套系统内提供：

- **Service Discovery**：服务注册与健康检查，DNS / HTTP 接口查询。
- **KV Store**：简单 KV，可存配置。
- **Health Checking**：内置多种检查方式（HTTP、TCP、gRPC、脚本）。
- **Multi-Datacenter**：原生支持跨数据中心联邦。
- **Consul Connect / Service Mesh**：基于 sidecar 的 mTLS 与流量控制（已演进为 consul-k8s + Envoy）。

### 4.2 架构

Consul 使用 **Raft** 管理服务端（Server）一致性，客户端（Client）以 gossip 协议（Serf）做成员管理与故障检测，并把请求转发给 Server。Server 间通过 Raft 选主并复制 KV 与目录数据。

多数据中心时，每个数据中心有独立的一致性组，跨中心通过 gossip 与 RPC 只读复制目录信息（不跨中心写 Raft），降低跨地域延迟。

### 4.3 适用场景

- 需要"开箱即用服务发现 + 健康检查 + DNS 查询"的微服务。
- 多活/多数据中心场景，Consul 的跨 DC 能力是亮点。
- 与 Terraform / Vault 同生态的团队。

### 4.4 局限

- 全套较重，若只需 KV 协调，etcd 更轻。
- 历史上 Service Mesh 能力已被 Istio/Linkerd 等分流，定位更偏"发现与配置"。

## 5. Nacos：阿里系的注册中心 + 配置中心

### 5.1 定位

Nacos（Dynamic Naming and Configuration Service）由阿里巴巴开源，核心提供**服务发现**与**动态配置**两大能力，是国内 Spring Cloud Alibaba 生态的事实标准注册/配置中心，兼容 Dubbo、Spring Cloud。

### 5.2 关键能力

- **服务注册发现**：支持 CP（Raft，类注册中心强一致）与 AP（Distro，最终一致）两种模式可切换。临时实例走 AP 保证可用性，持久实例走 CP 保证一致。
- **配置管理**：支持配置灰度、监听变更、命名空间/分组隔离，等价于一个轻量配置中心。
- **健康检查**：客户端心跳 + 服务端探测。
- **DNS 与 CMDB 扩展**：可对接 CMDB 做元数据路由。

### 5.3 设计取舍

Nacos 的"AP/CP 可切换"是其特色：注册中心场景更看重可用性（AP），而配置/元数据场景更看重一致性（CP）。这比"一个协议打天下"更贴合国内大规模微服务实践。

### 5.4 与同类对比

| 项目 | 注册 | 配置 | 一致性 | 生态重心 |
|---|---|---|---|---|
| Nacos | 强 | 强 | AP/CP 可切 | Spring Cloud Alibaba / Dubbo |
| Consul | 强 | 中 | Raft(CP) | 多数据中心 / 全栈 |
| etcd | 弱 | 强(KV) | Raft(CP) | K8s 后端 |
| ZooKeeper | 中 | 弱 | ZAB(CP) | 老牌协调 |

## 6. CoreDNS 与 DNS 服务发现

在 Kubernetes 中，服务发现很大程度通过 **DNS** 完成：kube-dns / CoreDNS 将 `service.namespace.svc.cluster.local` 解析为 ClusterIP 或 Endpoint。

CoreDNS 是插件化 DNS 服务器，支持：

- **kubernetes 插件**：监听 API Server，动态生成服务 DNS 记录。
- **forward 插件**：上游转发。
- **rewrite / template 插件**：改写查询。

DNS 服务发现的优势是**对应用透明**（标准 getaddrinfo），缺点是缓存 TTL 导致变更感知有延迟，通常用于"东西向"服务寻址而非强实时场景。

## 7. 选型决策树

- 已是 Kubernetes 技术栈且需可靠后端 → **etcd**（通常由 K8s 托管，不必自己再建）。
- 需要"注册中心 + 配置中心"二合一、国内生态 → **Nacos**。
- 需要成熟服务发现 + 多数据中心 + 健康检查 → **Consul**。
- 老牌 Hadoop/Dubbo 生态、需要临时节点语义 → **ZooKeeper**。
- 只需轻量 KV 协调、强 watch 语义 → **etcd**。

## 8. 常见踩坑

1. **ZooKeeper Watcher 一次性**：忘记重新注册导致漏事件。务必封装重试或在回调里重新 watch。
2. **etcd 租约未续约**：持锁/注册实例的进程若 GC 停顿过长导致 KeepAlive 失败，key 被删，锁提前释放——需合理设置租约时长并监控。
3. **CAP 误用**：把 CP 注册中心当成"永远可用"，实际上多数派不可用时注册会拒绝写；AP 模式则要容忍列表短暂不一致。
4. **大规模 watch 风暴**：监听根前缀、实例频繁上下线，可能压垮服务端；应做合理的监听粒度和客户端聚合。
5. **脑裂下的双重 Leader**：任何选主实现都要有"任期/epoch"防旧 Leader 继续写，etcd/ZK 已内置，但自研 fencing token 仍需保留。

## 9. 小结

协调与服务发现是分布式系统的"地基"。现代实践趋势是：**Kubernetes 内用 etcd + CoreDNS + EndpointSlice 解决大部分问题；非 K8s 微服务用 Nacos/Consul 做注册与配置；遗留与特定生态保留 ZooKeeper**。选型核心看一致性需求（CP/AP）、生态契合度与运维成本，而非单纯性能数字。
