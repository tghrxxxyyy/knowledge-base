# 系统设计题精解（面试高频）

> 板块：面试备战 　|　 返回：[README](README.md)

系统设计面试不考你背答案，考「拆解问题 + 权衡取舍 + 演进思维」。面试官看的是：**能不能把模糊需求变成清晰架构，并在约束下做合理取舍**。本文给出解题框架、容量估算、经典题索引与失分点。

## 一、标准解题框架

1. **澄清需求**：功能范围、QPS、数据量、延迟要求、读多还是写多、是否要强一致。
2. **估算容量**：用二八定律算存储/带宽/QPS，作为技术选型依据。
3. **画骨架**：核心组件（网关、服务、存储、缓存、MQ）先搭出来。
4. **逐层深入**：每组件选方案，说清为什么，以及瓶颈在哪。
5. **权衡与降级**：CAP 怎么取舍、峰值怎么扛、故障怎么降级。
6. **演进**：从单机到集群，从小规模到大规模，分阶段讲。

> 关键：宁可慢但要问清需求，不要上来就堆技术名词。问需求不是浪费时间，是展现"先理解后动手"的工程素养。

## 二、容量估算速算

| 量 | 估算 |
|----|------|
| 1 亿用户、10% 日活 | 1000 万 DAU |
| 人均 20 次请求/天 | 2 亿次/天 ≈ 2300 QPS 均值 |
| 峰值系数 3 | ~7000 QPS 峰值 |
| 单条记录 1KB | 2 亿条 ≈ 200 GB/天 |

- 存储：算年增量（200GB×365 ≈ 70TB），决定分库分表或冷热分离。
- 带宽：响应 10KB × 7000 QPS ≈ 70 MB/s，决定 CDN/压缩策略。
- 内存：缓存命中率 90% 时，热点数据量决定 Redis 规格。

估算不要求精确，体现量级感即可（量级错一个数量级才是问题）。

### 2.1 常用数量级锚点

- 1 台普通服务器：约 1–2 万 QPS（简单查询）、磁盘顺序写 ~200MB/s、随机写 ~1MB/s。
- 内存访问：~100ns；SSD 随机读：~100µs；网络 RTT 同机房：~0.5ms；跨地域：~30–100ms。
- Redis 单实例：~10 万 QPS；MySQL 单实例写：~2000–5000 TPS（受事务/磁盘约束）。
- 这些锚点用于"拍脑袋"量级估算，面试中比精确更重要。

## 三、经典题索引与要点

- **短链系统**：[场景设计/短链系统设计](../../场景设计/短链系统设计.md)。考察：短码生成（Base62/Snowflake）、存储、301 vs 302、缓存、冲突去重。
- **秒杀系统**：[场景设计/秒杀系统设计与高并发扣减](../../场景设计/秒杀系统设计与高并发扣减.md)。考察：流量分层拦截、Redis 原子扣减、MQ 削峰、防超卖、回滚。
- **Feed 流**：[场景设计/Feed信息流设计](../../场景设计/Feed信息流设计.md)。考察：推模式（写扩散）vs 拉模式（读扩散）、冷热分离、游标分页。
- **限流器**：算法：计数器、滑动窗口、令牌桶、漏桶。分布式限流用 Redis + Lua 或网关层（Sentinel/Kong）。考察：精度 vs 性能、集群一致性。
- **缓存层**：[场景设计/缓存经典三问与一致性](../../场景设计/缓存经典三问与一致性.md)。考察：穿透/击穿/雪崩、一致性、多级缓存。
- **排行榜**：Redis Sorted Set（ZADD/ZRANGE）天然支持；海量用户分片 + 合并，或离线计算 + 缓存。
- **搜索引擎**：倒排索引 + 分词 + TF-IDF/BM25 + 排序，近实时 refresh（见 [场景设计/全文搜索与Elasticsearch实战](../../场景设计/全文搜索与Elasticsearch实战.md)）。
- **分布式 ID**：号段、雪花、UUID、Redis 自增，见 [场景设计/分布式ID生成](../../场景设计/分布式ID生成.md)。
- **延时任务**：时间轮、Redis ZSet、MQ 延迟消息，见 [场景设计/延时任务与定时调度](../../场景设计/延时任务与定时调度.md)。

## 四、高并发通用武器库

- 缓存（Redis）、异步（MQ）、分片（分库分表）、限流（令牌桶）、降级（熔断）、冗余（多副本）。
- 读写分离、CDN、静态化、预热。
- 每条武器都要能说清"解决什么、带来什么代价"。

## 五、数据一致性怎么答

- **强一致**：2PC/事务，性能差，少用（仅账务/锁等）。
- **最终一致**：本地消息表、事务消息、Saga、TCC。
- 见 [场景设计/分布式事务与最终一致] 与 [分库分表]。
- 面试常考："支付成功了，但下游通知失败怎么办？" → 事务消息/本地消息表 + 重试 + 幂等。

## 六、CAP 取舍速答

- 分区必然存在（P 必选），只能 C/A 二选一。
- 钱/库存/配置：CP + 强一致（宁可不可用不能错）。
- 内容/社交/购物车：AP + 最终一致（可用优先）。
- 详见 [架构/CAP定理与一致性模型](../../架构/CAP定理与一致性模型.md)。

## 七、常见失分点

1. **不问需求直接开写** → 方向错，白做。
2. **只讲技术不问规模** → 选型无依据，像背八股。
3. **忽视瓶颈与降级** → 不落地，显得只会画大饼。
4. **背诵流行架构但不懂权衡** → 一问细节就露馅。
5. **不画演进** → 显得只考虑当前，不会规划。
6. **忽略可观测与运维** → 设计方案无法上线。

## 八、加分项（拉开差距）

1. **主动谈 SLO/错误预算**：把"高可用"量化成可用性目标与告警阈值。
2. **给出监控指标**：QPS、P99 延迟、错误率、饱和度（RED/USE 模型）。
3. **讲成本**：不同方案的成本差异（机器数、带宽、存储），体现工程权衡。
4. **谈安全**：鉴权、防刷、限流、数据加密，尤其是对外系统。
5. **画演进路线**：MVP → 水平扩展 → 拆分 → 多活，分阶段可落地。
6. **反问面试官**：确认约束（延迟/成本/团队规模），展现沟通。

## 九、答题话术模板

「这个系统峰值约 X QPS、存储 Y，我先用缓存+分库分表扛量；一致性上选最终一致用事务消息；峰值用 MQ 削峰+限流；故障降级到只读/排队。后续如果量再涨，做 X 演进（如加多级缓存、分片再拆、读写分离）。」

### 9.1 一道题的标准时间分配（45 分钟）

- 0–5 min：澄清需求与约束（不要跳）。
- 5–10 min：容量估算 + 画顶层架构图。
- 10–30 min：逐组件深入（存储/缓存/一致性/高并发各挑重点）。
- 30–40 min：瓶颈、降级、故障、安全。
- 40–45 min：演进路线 + 总结。

## 十、高频追问库（准备时自问自答）

- 如果 Redis 挂了怎么办？（降级、本地缓存、限流拒绝）
- 如果 MQ 堆积怎么办？（消费者扩容、批量消费、丢弃非核心）
- 数据量涨 10 倍怎么改？（分片再拆、冷热分离、归档）
- 如何保证不超卖/不重复扣款？（原子操作 + 数据库兜底 + 幂等）
- 怎么做灰度发布？（金丝雀 + 监控 + 一键回滚）
- 热点 key 怎么处理？（拆分、本地缓存、多副本读）

## 十一、准备建议

- 每个经典题准备"骨架图 + 关键点 + 取舍"三件套。
- 多练容量估算，形成量级直觉。
- 用自己真实项目（如 NL-to-SQL、Workbench）做素材，更易讲深。
- 找同伴互面，用白板/画图讲，逼自己结构化表达。
