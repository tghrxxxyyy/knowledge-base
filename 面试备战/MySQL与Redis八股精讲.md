# Part A · MySQL

## A1 索引：为什么是 B+树

**索引本质**：排好序的、用于快速查找的数据结构。MySQL InnoDB 用 **B+Tree**。

| 候选结构 | 为什么不用 |
|----------|-----------|
| 二叉搜索树 | 有序插入退化为链表，树高不可控 |
| 红黑树 / AVL | 树高仍随数据增长，百万行树高 ~20+，磁盘 IO 多 |
| Hash 索引 | 等值快，但**不支持范围/排序/最左前缀**，冲突退化 |
| B 树（非 +） | 非叶子节点也存 data，单页（16KB）能放的关键字少，树高更高 |
| **B+树 ✅** | 非叶子只存 key+指针，叶子串成**有序双向链表**，树矮、范围查询佳 |

**B+树核心特性**：
- 3 层 B+树可存 **千万级** 数据，查询只需 3 次磁盘 IO；
- 叶子节点存**完整数据行（聚簇索引）**或**主键值（二级索引）**；
- 聚簇索引叶子 = 整行；二级索引叶子 = 主键值，所以"二级索引查非主键列"要**回表**。

**高频考点**：
- **覆盖索引**：查询列都在索引里，无需回表（`EXPLAIN` 的 `Using index`）。
- **最左前缀**：联合索引 `(a,b,c)` 能命中 `a` / `a,b` / `a,b,c`，但不能跳过 `a` 直接用 `b`。
- **索引下推（ICP）**：在存储引擎层就用索引过滤，减少回表（MySQL5.6+）。
- **索引失效**：对列做函数/`or` 非索引列/`like '%x'` 左模糊/`隐式类型转换`。

> **踩坑**：`SELECT *` 几乎必然回表，且无法走覆盖索引；大字段别建索引，用前缀索引 `col(20)`。

## A2 事务隔离与 MVCC

**ACID**：原子性（undo log）、一致性（业务+约束）、隔离性（锁+MVCC）、持久性（redo log）。

**四种隔离级别**（MySQL 默认 **RR 可重复读**）：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| 读未提交 RU | ❌ 可能 | 可能 | 可能 |
| 读已提交 RC | ✅ 避免 | 可能 | 可能 |
| **可重复读 RR** | ✅ | ✅ | ✅(MVCC+间隙锁解决) |
| 串行化 S | ✅ | ✅ | ✅ |

**MVCC（多版本并发控制）原理**：
- 每行有隐藏列 `trx_id`（最后修改事务）、`roll_pointer`（指向 undo log 旧版本）；
- 快照读（普通 `SELECT`）通过 **ReadView** 判断哪个版本对当前事务可见；
- 当前读（`SELECT ... FOR UPDATE` / `UPDATE`）读最新版并加锁。

> **口诀：RR 靠 MVCC 快照读防不可重复读，靠间隙锁防幻读；RC 每次读都生成新 ReadView。**

## A3 锁：行锁 / 间隙锁 / 死锁

- **行锁**：锁索引记录；**没命中索引会升级为表锁**（这是经典坑）。
- **间隙锁（Gap Lock）**：锁住索引区间，防止插入，RR 下解决幻读。
- **Next-Key Lock** = 行锁 + 间隙锁，左开右闭。
- **死锁**：两个事务互相等待对方持有的锁。MySQL 检测到后**回滚代价小的事务**。

> **踩坑**：UPDATE 一个无索引字段 = 全表加行锁，高并发直接锁死；设计 SQL 必须确保 WHERE 走索引。

## A4 Redo / Undo / Binlog 与两阶段提交

| 日志 | 作用 | 层级 |
|------|------|------|
| Redo Log | 崩溃恢复，保证持久性（WAL，先写日志） | InnoDB 引擎层 |
| Undo Log | 回滚 + MVCC 旧版本 | InnoDB 引擎层 |
| Binlog | 主从复制 + 点恢复 | MySQL Server 层 |

**两阶段提交**（保证 redo 与 binlog 一致）：
```
1. prepare：redo 写盘，标记为 prepare
2. 写 binlog 到磁盘
3. commit：redo 标记为 commit
```
崩溃恢复时，若 redo prepare 且 binlog 完整 → 提交；否则回滚。

> **踩坑**：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` 才绝对不丢数据，但性能下降；金融级必须双 1。

## A5 Buffer Pool

- InnoDB 用**缓冲池**缓存数据页/索引页，读写先走内存；
- `LRU` 改进版（分 young/old 区）防止全表扫描污染热点；
- 脏页由后台线程异步刷盘。

> **升华**：MySQL 性能 = 命中 Buffer Pool 的比例。内存比数据小很多时，随机 IO 会爆；加索引、加内存、用 SSD，本质都在提升"内存命中率"。

# Part B · Redis

## B1 五大数据结构与底层编码

| 对外类型 | 底层编码 | 说明 |
|----------|----------|------|
| String | int / embstr / raw | 数字用 int；短字符串 embstr 连续内存 |
| List | quicklist（ziplist+链表） | 3.2+ 用 quicklist |
| Hash | ziplist(小) / hashtable | 元素少且小用压缩列表省内存 |
| Set | intset / hashtable | 全整数且少 → intset |
| ZSet | ziplist(小) / **跳表(skiplist)+dict** | 跳表按分排序，dict 查分值 O(1) |

> **跳表（SkipList）** 是 ZSet 核心：多层索引随机层数，查询/插入 O(log n)，实现比红黑树简单，且**范围查询友好**——这是 ZSet 做排行榜的底层原因。

**高频**：`SDS`（简单动态字符串）比 C 字符串多存 len/free，O(1) 取长度、二进制安全、不溢出。

## B2 持久化：RDB 与 AOF

| 对比 | RDB | AOF |
|------|-----|-----|
| 形式 | 某一刻内存快照 | 追加命令日志 |
| 体积 | 小（压缩二进制） | 大（可重写压缩） |
| 恢复 | 快 | 慢（重放命令） |
| 数据安全 | 可能丢最后一次快照后数据 | `appendfsync=everysec` 最多丢 1s |
| 性能影响 | fork 子进程，大数据集卡顿 | 写放大，但 everysec 折中 |

> **生产建议**：`RDB + AOF 混合`（Redis 4.0+ `aof-use-rdb-preamble`），兼具快恢复与小丢失。

## B3 缓存三大问题

```
        缓存击穿                  缓存穿透                  缓存雪崩
   热点 key 失效瞬间         查不存在的数据           大量 key 同时过期
   海量请求直击 DB          缓存和 DB 都没有          DB 被集中打垮
```

| 问题 | 现象 | 解决方案 |
|------|------|----------|
| **击穿** | 单个热点 key 过期，并发请求全打到 DB | ① 互斥锁（只放一个线程回源）② 逻辑过期（不真删，异步续期）③ 热点 key 不过期 |
| **穿透** | 查 DB 也没有的值，缓存永远不命中 | ① **布隆过滤器**拦非法 key ② 缓存空值（设短 TTL） |
| **雪崩** | 大量 key 同一时刻失效 / Redis 宕机 | ① TTL 加随机抖动 ② 多级缓存 ③ Redis 高可用(集群) + 限流降级 |

> **踩坑**：缓存空值要解决"空值被频繁更新"的同步问题；布隆过滤器有误判率（存在=可能，不存在=一定不）。

## B4 缓存与数据库一致性

**经典三问**：先删缓存还是先更新 DB？
- ❌ 先删缓存再更新 DB：并发读可能把旧值填回缓存；
- ❌ 先更新 DB 再删缓存（Cache-Aside）：极端并发下仍有窗口；
- ✅ 推荐：**先更新 DB，再删缓存**（Cache-Aside），配合**延迟双删 / 订阅 Binlog（Canal）异步删**，几乎所有大厂采用。

> **口诀：读时先缓存后DB，写时先DB后删缓存；强一致上 Canal 订阅 binlog 兜底。**

## B5 分布式锁

**SET NX 加锁（原子）**：
```bash
SET lock:order:1001 <uuid> NX PX 30000   # 不存在才设，30s 自动过期
```
- 必须带**唯一 value（UUID）**，释放时用 Lua 脚本校验 value 再删，防止误删别人的锁；
- 必须设**过期时间**，防死锁；业务超时用**看门狗**自动续期（Redisson 已实现）。

**对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| Redis SET NX | 简单、性能高 | 主从切换可能丢锁（AP）；需 Redlock 才勉强 CP |
| ZooKeeper 临时节点 | 会话断自动释放、强一致 | 性能低于 Redis、依赖 ZK |
| etcd / 数据库乐观锁 | 各有场景 | 数据库锁重，etcd 偏重 |

> **口诀：Redis 锁快但不严（AP），ZK 锁严但重（CP），选哪个看你要可用性还是强一致。**

## B6 内存淘汰与集群

**8 种淘汰策略**（默认 `noeviction` 写满报错）：
- `allkeys-lru` / `volatile-lru`（最近最少用）
- `allkeys-lfu` / `volatile-lfu`（最不经常用，4.0+）
- `allkeys-random` / `volatile-random`
- `volatile-ttl`（快过期先淘汰）

**集群模式**：

| 模式 | 特点 |
|------|------|
| 主从 | 读写分离，主挂需人工/哨兵切 |
| 哨兵(Sentinel) | 自动故障转移，监控+通知 |
| Cluster | 数据分 16384 槽，去中心化，原生分片 |

> **踩坑**：Cluster 下**跨 slot 多 key 操作不支持**（除非 hash tag 绑定）；`-maxmemory` 必须设，否则 OOM 拖垮整机。

## 口诀汇总

> **MySQL：索引选 B+ 树矮 IO 少，聚簇叶子存整行，二级索引要回表；覆盖索引免回表，最左前缀不能跳。**
> **MVCC 靠 ReadView 看版本，RR 防幻读靠间隙锁；redo 持久 undo 回滚 binlog 复制，两阶段提交保一致。**
> **Redis：五大结构底层编码各不同，ZSet 跳表做排行；RDB 快 AOF 全，混合持久化最稳。**
> **缓存三害：击穿锁单线程、穿透布隆拦、雪崩加抖动；一致性先DB后删缓存。**
> **分布式锁 SET NX 带 UUID，Lua 校验才释放；Redis 快 ZK 严。**
