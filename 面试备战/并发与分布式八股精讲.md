# Part A · 并发编程

## A1 线程状态与创建

**6 种状态**（Java 线程，非 OS）：
`NEW → RUNNABLE ⇄ BLOCKED/WAITING/TIMED_WAITING → TERMINATED`

> 注意：Java 没有"RUNNING"态，`RUNNABLE` 包含了"就绪+运行"；`BLOCKED` 专指等 `synchronized` 锁，`WAITING` 是 `wait()/join()` 无参等待。

**创建方式**：① 继承 Thread ② 实现 Runnable ③ 实现 Callable（有返回值+异常）④ 线程池（**生产唯一正确方式**）。

## A2 synchronized 锁升级

JDK6 后 `synchronized` 不再是"重量级锁"代名词，而是**自适应、可升级**：

```mermaid
graph LR
    A[无锁] -->|第一次访问| B[偏向锁<br/>记录线程ID,无竞争]
    B -->|竞争出现| C[轻量级锁<br/>CAS 自旋抢 Mark Word]
    C -->|自旋超限/多竞争| D[重量级锁<br/>OS 互斥,线程阻塞]
```

| 锁 | 适用 | 代价 |
|----|------|------|
| 偏向锁 | 始终一个线程访问 | 几乎零成本，加个线程 ID |
| 轻量级 | 多线程交替，竞争不激烈 | CAS 自旋，占 CPU |
| 重量级 | 高竞争 | 操作系统 mutex，线程阻塞/唤醒（上下文切换重） |

> **踩坑**：`synchronized` 锁的是**对象**（非代码块）；锁实例方法锁 `this`，锁静态方法锁 `Class`。**锁对象别用 String 常量 / 基础类型装箱对象**（全局共享易死锁）。

## A3 volatile 语义

`volatile` 保证两件事：
1. **可见性**：写立即刷主内存，读从主内存取；
2. **有序性**：禁止**指令重排序**（插入内存屏障），典型用于 DCL 单例的 `instance` 字段。

**不保证原子性**——`i++`（读-改-写三步）即便 volatile 也非线程安全，要用 `AtomicInteger` 或锁。

```java
class Singleton {
    private static volatile Singleton instance;   // 必须 volatile 防重排序
    public static Singleton get() {
        if (instance == null) {                    // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null)              // 第二次检查（DCL）
                    instance = new Singleton();
            }
        }
        return instance;
    }
}
```

## A4 线程池

**七大参数**（必须能背）：
```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数（常驻）
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 非核心线程空闲存活
    unit,              // 时间单位
    workQueue,         // 阻塞队列（任务缓冲）
    threadFactory,     // 线程工厂（命名！）
    handler            // 拒绝策略
)
```

**执行流程**：
```
提交任务 → 核心线程未满? 创建核心线程执行
         → 核心满? 入队列
         → 队列满? 创建非核心线程(至maximum)
         → 都满? 触发拒绝策略
```

**四大拒绝策略**：Abort（抛异常，默认） / CallerRuns（调者线程执行） / Discard（静默丢） / DiscardOldest（丢最老）。

> **踩坑（高频死亡题）**：**禁止用 `Executors.newFixedThreadPool()` / `newCachedThreadPool()`**！前者队列无界可能 OOM，后者最大线程 Integer.MAX_VALUE 可能打爆线程数。生产用 `ThreadPoolExecutor` 显式指定队列大小与拒绝策略。

## A5 CAS 与 AQS

**CAS（Compare-And-Swap）**：`compareAndSet(expected, new)`，CPU 原子指令，无锁并发基础。
- **ABA 问题**：值从 A→B→A，CAS 误以为没变。解决：加版本号 `AtomicStampedReference`。
- 自旋开销：高竞争下 CAS 空转耗 CPU。

**AQS（AbstractQueuedSynchronizer）**：JUC 锁的基石（`ReentrantLock`/`Semaphore`/`CountDownLatch`）。
- 维护一个 **state（同步状态）** + **CLH 队列**（阻塞等待线程）；
- `ReentrantLock` 默认**非公平锁**（吞吐高），`fair=true` 才公平（防饥饿但慢）。

> **对比**：`synchronized` 是 JVM 内置管程，简单自动释放；`ReentrantLock` 需 `try/finally` 手动 `unlock`，但支持**可中断、超时、公平、多条件变量**。

## A6 ThreadLocal 内存泄漏

- 每个线程有 `ThreadLocalMap`，key 是 `ThreadLocal` 弱引用，value 是强引用；
- 线程池线程**复用不销毁**，若不再用 ThreadLocal 却不 `remove()`，value 永远挂着 → **内存泄漏**；
- **规范**：`try/finally` 中 `threadLocal.remove()`。

# Part B · 分布式

## B1 CAP 与 BASE

- **CAP**：一致性(C)、可用性(A)、分区容错(P) **三者不可兼得**，网络分区(P)必然存在，所以**CP 或 AP 二选一**。
  - CP：ZooKeeper、etcd、HBase（保一致，牺牲部分可用）
  - AP：Cassandra、Eureka、DNS（保可用，最终一致）
- **BASE**（AP 系统的补偿哲学）：基本可用(Basically)、软状态(Soft)、最终一致(Eventually)。

## B2 一致性模型

| 模型 | 含义 | 例子 |
|------|------|------|
| 强一致 | 写完立刻读到 | ZooKeeper ZAB |
| 顺序一致 | 所有节点看到相同顺序 | — |
| 因果一致 | 有因果关系的操作保序 | — |
| 最终一致 | 无更新后最终一致 | DNS、Redis 主从异步 |

## B3 分布式锁对比

| 方案 | 一致性 | 优点 | 缺点 | 适用 |
|------|--------|------|------|------|
| Redis SET NX | AP | 快、简单 | 主从切换丢锁（需 Redlock） | 高并发、允许极小概率失效 |
| ZooKeeper 临时节点 | CP | 会话断自动释放、可靠 | 性能略低、需 ZK 集群 | 强一致要求 |
| etcd Lease | CP | 租约自动过期、K8s 同款 | 需 etcd | 云原生场景 |
| 数据库唯一索引 | CP | 零依赖 | 性能差、锁释放麻烦 | 低频 |

> **口诀：Redis 锁快但可能丢（AP），ZK/etcd 锁严但重（CP），选哪个看你要可用性还是强一致。**

## B4 分布式 ID

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 简单无中心 | 无序、索引碎片、占空间 |
| 数据库自增 | 简单 | 单点、扩容难 |
| **雪花算法 Snowflake** | 趋势递增、本地生成、64bit | 依赖时钟，时钟回拨会冲突 |
| **号段模式 / Leaf-segment** | DB 批量取号段，性能好 | 依赖 DB（美团 Leaf） |
| Redis INCR | 简单 | 持久化/性能瓶颈 |

> **踩坑**：Snowflake 时钟回拨——解决：① 检测回拨抛异常告警 ② 用 ZooKeeper 记录上次时间 ③ 百度 UidGenerator 用"机器号+时间+序列"降低时钟依赖。

## B5 分布式事务

| 模式 | 原理 | 一致性 | 适用 |
|------|------|--------|------|
| 2PC | 协调者两阶段（准备/提交） | 强一致 | 短事务、低并发（阻塞严重） |
| TCC | Try/Confirm/Cancel 三阶段 | 最终一致 | 高并发、需补偿编码 |
| Saga | 长事务拆本地事务+补偿 | 最终一致 | 长流程（订单→库存→物流） |
| **本地消息表** | 本地事务+消息表，轮询发送 | 最终一致 | 不依赖 MQ 事务 |
| **RocketMQ 事务消息** | Half Message + 回查 | 最终一致 | 已用 RocketMQ 的场景 |

> **口诀：强一致选 2PC（慢），高并发选 TCC/Saga，消息驱动选事务消息/本地消息表；能避免分布式事务就别用。**

深读：[架构/分布式事务实战.md](../架构/分布式事务实战.md) 与 [分库分表与数据迁移/04-分布式事务与一致性.md](../分库分表与数据迁移/04-分布式事务与一致性.md)。

## B6 共识算法 Raft

- 比 Paxos 易理解的共识算法，用于 etcd / Consul / TiKV；
- **三个角色**：Leader / Candidate / Follower；
- **任期(Term)** 单调递增，**日志复制**保证状态机一致；
- Leader 挂 → 超时触发选举（随机退避防脑裂）。

> **升华**：Raft/ZAB 解决"多节点对一件事达成同一结论"，是分布式锁、配置中心、KV 存储的地基。想深读可回到 [基础知识/中间件/ZooKeeper.md](../基础知识/中间件/ZooKeeper.md)。

## 口诀汇总

> **线程六态无 RUNNING；synchronized 锁升级：偏→轻→重，自适应不傻等。**
> **volatile 管可见与有序，不保原子用原子类；DCL 单例必须 volatile。**
> **线程池七大参：核心/最大/空闲/队列/工厂/拒绝；禁用 Executors 无界池。**
> **CAS 无锁防 ABA 加版本；AQS 管 state 与队列，ReentrantLock 非公平最快。**
> **ThreadLocal 用完 remove，不然线程池漏内存。**
> **CAP 三选二必含 P；Redis 锁 AP 快，ZK/etcd 锁 CP 严。**
> **分布式 ID 雪花怕回拨，事务能避就别上；Raft 选主靠任期和日志。**
