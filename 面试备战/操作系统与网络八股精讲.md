## 1. 操作系统基础：进程/线程/协程

**Q：进程、线程、协程区别？**

| 维度 | 进程 | 线程 | 协程（goroutine/虚拟线程） |
|------|------|------|----------------------------|
| 调度 | 操作系统 | 操作系统 | **用户态**（更轻） |
| 资源 | 独立地址空间 | 共享进程地址空间 | 共享线程资源 |
| 切换成本 | 高（换页表/刷TLB） | 中（换栈/寄存器） | 极低（用户态切换） |
| 通信 | IPC（管道/共享内存/消息队列） | 共享内存（需锁） | channel/共享变量 |
| 故障 | 一个崩不影响其他 | 一个崩全进程崩 | 隔离性取决于实现 |

> **踩坑**："线程安全"的本质是**共享可变状态**的并发访问；无共享则无需锁。高并发服务用**线程池 + 协程**（如 Go）而非无节制开线程。

**Q：用户态与内核态？**
- 用户态不能直接操作硬件/内核数据；系统调用（`read/open/fork`）通过**软中断**陷入内核态；
- 频繁的**上下文切换**（线程切换、系统调用）是性能杀手，压测时看 `cs`（context switch）指标。

**Q：进程间通信（IPC）有哪些？**
管道、命名管道(FIFO)、消息队列、共享内存（最快，需配信号量）、信号、Socket（跨机）。

## 2. 内存管理：虚拟内存/分页/缺页

**Q：为什么需要虚拟内存？**
- 每个进程有**独立的连续虚拟地址空间**，屏蔽物理碎片；
- 隔离进程，一个崩不影响其他；支持**按需分页**（用多少加载多少）+ Swap 兜底。

**Q：分页 vs 分段？**
- 分页：物理内存切固定大小**页**（4KB），按页映射，解决外部碎片；
- 分段：按逻辑意义（代码/数据/堆/栈）分变长段；现代系统多用**分页为主、分段为辅**（x86 段仅做权限）。

**Q：页表与地址翻译？**
- 虚拟页号(VPN) → 查页表 → 物理页号(PPN) + 页内偏移；
- 多级页表 + **TLB（快表）** 缓存热点映射，TLB 未命中要 walk 多级页表，慢。

**Q：缺页中断（Page Fault）？**
- **Minor（软缺页）**：页在内存但不在进程页表（如共享库）→ 直接映射，快；
- **Major（硬缺页）**：页不在内存，需从磁盘/Swap 读入 → 慢，是性能瓶颈信号；
- **无效缺页**：访问未映射地址 → `SIGSEGV` 段错误。

**页面置换算法**：FIFO（Belady 异常）、OPT（理想）、**LRU**（最近最少用，近似实现用 Clock 二次机会）、LFU。

> **口诀：虚拟地址独立又隔离，分页映射 TLB 快；缺页分软硬，硬缺页最伤性能。**

## 3. 死锁

**死锁四必要条件（全满足才死锁）**：
1. 互斥（资源独占）
2. 占有并等待（持有一个等另一个）
3. 不可剥夺（资源不能被强抢）
4. 循环等待（A等B、B等A）

**破解方法（破坏任一条件）**：
- **预防**：一次性申请全部资源（破坏"占有等待"）、资源按序申请（破坏"循环等待"）；
- **避免**：银行家算法（预判安全序列，开销大，少用）；
- **检测+恢复**：资源分配图检测环，发现死锁则**终止进程/剥夺资源**（鸵鸟算法：装死，重启解决，很多系统实际采用）。

> **踩坑**：数据库/Java 死锁多因"加锁顺序不一致"。**统一全局加锁顺序**是最实用的预防手段（对应 [并发与分布式八股精讲](并发与分布式八股精讲.md) 的锁章节）。

## 4. IO 模型与零拷贝

**Q：五种 IO 模型？**

| 模型 | 是否阻塞等待数据 | 是否阻塞拷贝 | 典型 |
|------|------------------|--------------|------|
| 阻塞 IO | 是 | 是 | `read()` 默认 |
| 非阻塞 IO | 否（轮询 EAGAIN） | 是 | 忙轮询浪费 CPU |
| **IO 多路复用** | 否（等内核通知） | 是 | **select/poll/epoll** |
| 信号驱动 | 否 | 是 | SIGIO |
| **异步 IO(AIO)** | 否 | 否（内核完成拷贝后通知） | `io_uring` / Windows IOCP |

> **关键区分**："同步/异步"看**数据从内核态拷贝到用户态谁来做**（用户态同步，内核态异步）；"阻塞/非阻塞"看**等数据就绪时线程是否挂起**。epoll 是多路复用（同步非阻塞），io_uring 才是真异步。

**epoll 核心**：红黑树管理监听 fd（增删改 O(log n)），就绪链表存就绪 fd；**ET（边缘触发）** 只通知一次需一次读尽，**LT（水平触发）** 没读完反复通知（安全但低效）。

**零拷贝（高频）**：减少"内核态↔用户态"冗余拷贝
- `mmap`：文件映射到用户空间，省一次拷贝；
- `sendfile`：数据直接从内核页缓存 DMA 到网卡，**不经过用户态**（Kafka/Netty 用）；
- `splice` / `DMA gather`：进一步省内核态内拷贝。

> **口诀：IO 多路复用 select 轮询 poll 数组，epoll 红黑树+就绪链；零拷贝 sendfile 不过户，io_uring 真异步。**

## 5. TCP：握手挥手/拥塞/粘包

**Q：为什么三次握手不是两次？**
- 防止**历史失效连接**（旧 SYN 迟到建立无效连接，浪费资源）；
- 双向确认**初始序列号 ISN**，保证双方收发能力正常。

**Q：为什么四次挥手？TIME_WAIT 是什么？**
- 关闭是**全双工的**，每方向独立关闭：被动方收到 FIN 后先 ACK，等自己数据发完再发 FIN（所以多一次）；
- **TIME_WAIT** 持续 **2MSL**：① 确保被动方收到最终 ACK；② 让本连接的迟到的旧报文在网络中消失，避免污染新连接。

> **踩坑**：高并发短连接服务端出现大量 TIME_WAIT → 端口耗尽。解决：`SO_REUSEADDR`、连接复用（长连接/连接池）、`tcp_tw_reuse`。

**Q：拥塞控制（避免网络雪崩）？**
- 慢启动：cwnd 指数涨到 ssthresh；
- 拥塞避免：线性涨；
- 快重传 + 快恢复：收到 3 个重复 ACK 立即重传，cwnd 减半（不回到 1）；
- 流量控制（滑动窗口）防"发送方压垮接收方"，拥塞控制防"压垮网络"——**两者不同**。

**Q：TCP 粘包/拆包？怎么解决？**
- TCP 是字节流，无消息边界；Nagle 算法、MTU 都会导致粘/拆；
- 解决：① 定长消息 ② 分隔符 ③ **长度字段（header 带 body 长度，最常用）** ④ 序列化协议自带边界（如 Protobuf 帧）。

> **升华**：UDP 无连接、无可靠，但低延迟、支持广播，适合视频/游戏/QUIC；需要可靠时自己在应用层加（如 KCP）。

## 6. HTTP 与 HTTPS

**Q：常见状态码？**
- 2xx 成功（200/201/204）；3xx 重定向（301 永久 / 302 临时 / 304 未改）；4xx 客户端错（400 参数 / 401 未认证 / 403 无权限 / **404 不存在** / 429 限流）；5xx 服务端错（500 / 502 网关错 / 503 不可用 / 504 网关超时）。

**Q：GET vs POST？**
- 语义：GET 取、POST 提交；GET 参数在 URL（有长度/安全问题）、POST 在 body；GET 幂等可缓存，POST 不保证。

**Q：Cookie / Session / Token(JWT)？**
- Cookie：客户端存，每次请求自动带；Session：服务端存会话，靠 Cookie 传 sessionId；
- Token/JWT：服务端**无状态**，签名令牌自带声明，适合分布式/微服务（无需集中存储 Session）。

**Q：HTTPS 怎么保证安全？**
- 非对称加密（RSA/ECDHE）协商出**对称密钥**，后续用对称加密传数据（兼顾安全与性能）；
- **TLS 1.2（ECDHE 握手）**：ClientHello → ServerHello+证书 → 客户端验证书链 → 双方算预备主密钥 → 生成会话密钥（**2-RTT**）；
- **TLS 1.3**：精简到 **1-RTT**（废除 RSA 密钥交换、移除不安全套件），支持 **0-RTT**（重连零往返，但有重放风险）；
- 中间人防护靠 **CA 证书链** + 证书校验（域名/有效期/吊销）。

> **踩坑**：自签证书需手动信任；证书过期是线上 HTTPS 故障高频原因，务必监控到期日。

## 7. HTTP/2 与 HTTP/3（QUIC）

| 版本 | 传输层 | 关键特性 | 仍存在的问题 |
|------|--------|----------|--------------|
| HTTP/1.1 | TCP | 管线化（基本废）、长连接 | **队头阻塞**（一个请求卡住整条连接） |
| **HTTP/2** | TCP | 多路复用（一连接多流）、HPACK 头部压缩、服务端推送 | TCP 层**队头阻塞**（丢包阻塞所有流） |
| **HTTP/3** | **QUIC(UDP)** | 多路流独立、0-RTT/1-RTT、内置 TLS1.3、连接迁移（换 IP 不断） | UDP 可能被中间设备限流 |

**QUIC 为何强**：跑在 UDP 上，每个流独立有序，某流丢包不影响其他流；连接用**连接 ID** 标识，手机切 WiFi（IP 变）不断连（连接迁移）。

> **口诀：HTTP1 队头堵，HTTP2 多路复用仍怕 TCP 丢；HTTP3 上 QUIC，UDP 跑 TLS 不断连。**

## 8. 口诀汇总

> **进程独立线程共享，协程用户态最轻；上下文切换是性能刺客。**
> **虚拟内存分页隔离，TLB 快表省翻译；硬缺页最慢，Swap 是兜底。**
> **死锁四条件，加锁顺序统一破循环。**
> **IO 五模型：阻塞/非阻塞/多路/epoll/异步；零拷贝 sendfile 不过户。**
> **TCP 三握手防旧连，四挥手因全双工；TIME_WAIT 等 2MSL，大量出现要复用。**
> **拥塞控网络，流量控接收，两者不是一回事。**
> **HTTP 状态码 2 成 3 转 4 客 5 服；HTTPS 非对称协商对称密钥，TLS1.3 只要一往返。**
> **HTTP2 多路复用，HTTP3 上 QUIC 不断连。**
