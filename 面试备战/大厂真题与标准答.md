## 一、Java / JVM

**Q1：`volatile` 一定能保证可见性，那它能保证原子性吗？**
- 答：`volatile` 保证**可见性**（写立即刷主存、读从主存取）和**有序性**（禁止指令重排，加内存屏障）；但**不保证原子性**，`i++` 这种"读-改-写"三步在并发下仍会丢更新。
- 对比：要原子用 `AtomicInteger`（CAS）/ `synchronized` / `LongAdder`（高并发分段累加）。
- 升华：DCL 单例的 `instance` 必须 `volatile`，正是为了禁止"分配内存→设引用→初始化"重排导致拿到半初始化对象。

**Q2：`synchronized` 和 `ReentrantLock` 怎么选？**
- 答：`synchronized` 是 JVM 内置管程，**自动释放**、锁升级（偏向→轻量→重量）自适应，简单够用；`ReentrantLock` 需 `try/finally` 手动释放，但支持**可中断、超时获取、公平锁、多条件变量**。
- 踩坑：忘记 `unlock` 会死锁；`synchronized` 拿不到锁时不能中断。
- 升华：多数业务用 `synchronized` 即可；需要精细化控制（如可中断的批量获取多把锁）才上 `ReentrantLock`。

**Q3：线上 Full GC 频繁怎么排查？**
- 答：① `jstat -gcutil` 看 GC 频次与各代占用；② `jmap -histo:live` / `jmap -dump` 抓堆，用 MAT 找**大对象/泄露点**；③ 看 GC 日志（开启 `-Xlog:gc*`）定位是晋升失败还是元空间满；④ Arthas `dashboard`/`heapdump` 在线诊断。
- 常见根因：内存泄漏（ThreadLocal 没 remove、缓存无上限）、堆过小、大对象（一次性加载海量数据）、`Metaspace` 未设上限（动态代理/热部署）。
- 升华：调优是"先定位再调"，不是无脑调 `-Xmx`；G1 下关注 `MaxGCPauseMillis`（软目标）与 mixed GC 是否及时。

## 二、MySQL

**Q4：索引建了但 `EXPLAIN` 没走，为什么？**
- 答：常见原因——对列做了**函数/运算**（`WHERE DATE(create_time)=...`）、**隐式类型转换**（字符串列用数字查）、`LIKE '%x'` 左模糊、`OR` 连了非索引列、优化器认为**全表扫描更快**（数据量小或区分度低）、**最左前缀**断链。
- 踩坑：`SELECT *` + 覆盖索引冲突；`!=`/`NOT IN` 多数情况下放弃索引。
- 升华：用 `EXPLAIN` 看 `type`（const>ref>range>index>ALL）、`key`、`rows`、`Extra`(Using index/Using filesort)。

**Q5：深度分页 `LIMIT 100000,20` 很慢怎么优化？**
- 答：问题在"先读 10 万行再丢"。方案：① **游标分页**（延迟关联）：`WHERE id > 100000 ORDER BY id LIMIT 20`；② **子查询先取 id**：`SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 100000,20) x USING(id)`；③ 业务上限制跳页深度。
- 升华：海量数据下"跳到第 N 页"本身是不合理的产品需求，用"下一页/滚动加载"替代。

**Q6：事务里更新一条没索引的字段会怎样？**
- 答：InnoDB 行锁建立在索引上，**无索引 WHERE 会锁全表（每一行都加锁再释放）**，高并发直接卡死。这是经典生产事故。
- 升华：所有 UPDATE/DELETE 的 WHERE 必须确认走索引（`EXPLAIN` 验证）。

## 三、Redis

**Q7：缓存和数据库一致性怎么保证？**
- 答：推荐 **Cache-Aside**：读时先缓存后 DB；写时**先更新 DB，再删缓存**（删除而非更新，避免并发写覆盖）。极端并发窗口可用**延迟双删**或 **Canal 订阅 binlog 异步删**兜底。
- 踩坑：先删缓存再更 DB，并发读会把旧值填回；强一致场景需 Canal/消息队列保证最终一致。
- 升华：缓存本质是"牺牲强一致换性能"，除非业务强制，否则接受最终一致。

**Q8：热 key / 大 key 怎么处理？**
- 答：**热 key**（某 key QPS 极高）：本地缓存 + 多副本（key 加随机后缀分散）、限流、Redis 集群分片。**大 key**（value 几 MB / 集合百万元素）：拆分（hash 分桶）、分批删除（`UNLINK` 异步删避免阻塞）、定期清理。
- 踩坑：大 key 的 `DEL` 会阻塞单线程；热 key 打挂单分片。

## 四、并发 / 分布式

**Q9：线程池参数怎么定？为什么禁用 `Executors`？**
- 答：核心参数——`corePoolSize`（常驻）、`maximumPoolSize`、`keepAliveTime`、`workQueue`（容量！）、`threadFactory`（命名）、`handler`（拒绝策略）。
- 踩坑：`newFixedThreadPool` 队列**无界**可能 OOM；`newCachedThreadPool` 最大线程 `Integer.MAX_VALUE` 可能打爆线程数。必须 `new ThreadPoolExecutor` 显式指定。
- 升华：IO 密集型 `core ≈ 2*CPU`，CPU 密集型 `core ≈ CPU+1`；队列用有界 + `CallerRunsPolicy` 兜底。

**Q10：分布式锁用 Redis 还是 ZK？**
- 答：**Redis（SET NX + 过期 + Lua 释放 + 看门狗续期）**——性能高、AP 系统，主从切换瞬间可能丢锁（Redlock 缓解）；**ZK 临时节点**——CP、会话断自动释放、强一致，但性能略低、依赖 ZK 集群。
- 升华：选哪个看你要"可用性"还是"强一致"；业务能接受极小概率失效选 Redis，金融强一致选 ZK/etcd。

**Q11：分布式事务怎么选型？**
- 答：**能避免就避免**（同库/最终一致）。强一致短事务用 **2PC**（但阻塞重）；高并发用 **TCC/Saga**（编码补偿）；消息驱动用 **RocketMQ 事务消息 / 本地消息表**（最终一致）。
- 踩坑：2PC 协调者单点、阻塞；TCC 要写三套逻辑（Try/Confirm/Cancel）。

## 五、网络 / 操作系统

**Q12：HTTPS 握手几次？TLS 1.3 改进了什么？**
- 答：TLS 1.2（ECDHE）**2-RTT**：ClientHello→ServerHello+证书→客户端校验+双方算密钥→Finished。TLS 1.3 精简到 **1-RTT**，废除 RSA 密钥交换、移除不安全套件，支持 **0-RTT**（重连零往返，但有重放风险）。
- 升华：安全靠 CA 证书链 + 非对称协商对称密钥（性能权衡）。

**Q13：epoll 为什么快？LT 和 ET 区别？**
- 答：epoll 用**红黑树**管理监听 fd（增删 O(log n)）、**就绪链表**存就绪 fd，只返回就绪的，避免 select/poll 全量轮询。ET（边缘触发）只通知一次需一次读尽（高效但易漏），LT（水平触发）没读完反复通知（安全）。
- 升华：Netty 默认 EPOLL ET + 非阻塞循环读，是高并发网络框架基石。

## 六、消息队列

**Q14：消息重复消费怎么处理？**
- 答：MQ 只保证**至少一次**（at-least-once），重复难免。消费端必须**幂等**：唯一消息 ID + 去重表（Redis `SETNX` / 数据库唯一约束）/ 状态机（已处理则跳过）/ 版本号。
- 升华：幂等是"允许重复、结果唯一"的工程智慧，比追求"恰好一次"更现实。

**Q15：消息积压了怎么办？**
- 答：① 紧急**扩容消费者**（Kafka 加 partition + consumer，RocketMQ 加 consumer）；② 提升单机消费能力（批量拉取、并行处理、去掉慢 IO）；③ 非重要消息**跳过/丢弃**保核心；④ 提前修消费逻辑 bug（死循环/慢 SQL）。
- 踩坑：消费者卡死在外部调用超时，越积压越多——先限流外部依赖。

## 七、场景 / 设计

**Q16：如何保证接口幂等？**
- 答：① 唯一 ID + 去重表（DB 唯一索引/Redis）；② 状态机（已支付不能重复支付）；③ Token 机制（提交前发 token，提交即作废）；④ 乐观锁（version 字段）；⑤ 悲观锁（慎用）。
- 升华：幂等是分布式系统的"安全带"，所有写接口默认要考虑。

**Q17：如何设计一个限流组件？**
- 答：确定维度（IP/用户/接口）、算法（固定窗口/滑动窗口/令牌桶/漏桶）、粒度（单机 vs 分布式 Redis+Lua）。分布式用 Redis `INCR+EXPIRE` 或 Lua 原子计数，网关层（Sentinel/Kong）统一接入。
- 踩坑：固定窗口有"临界突刺"（窗口交界双倍）；令牌桶允许突发更平滑。

**Q18：如何设计一个短链系统？（综合）**
- 见 [场景题与项目深挖](场景题与项目深挖.md) 的"短链"套路：发号（分布式 ID/base62）→ 存储（short_code→long_url）→ 跳转（302，可被 CDN 缓存，便于统计）→ 缓存（热 key 放 Redis）→ 高可用（预生成、主从、限流）。
