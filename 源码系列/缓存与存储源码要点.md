# 缓存与存储源码要点（Redis / MySQL InnoDB）

> 板块：源码系列 　|　 返回：[README](README.md)

本文从工程实现层面梳理两类核心存储的源码级要点：
Redis 的内存模型、数据结构、持久化、过期淘汰、集群；
MySQL InnoDB 的索引、事务、MVCC、Buffer Pool、日志与复制。
内容聚焦"为什么这样设计"与"调优时该看什么"，不追求逐行源码复现。

## 一、Redis 核心实现

### 1.1 单线程与 I/O 多线程

Redis 的核心命令执行是**单线程**的：所有命令在一个事件循环里串行处理。
这带来一个关键好处——**天然避免锁竞争与并发安全问题**，使命令实现简单且原子。

但单线程不等于整系统只有一个线程。从 6.0 起，Redis 引入 I/O 多线程：
- 网络**读/写**（Socket 收发）可以由多个线程并行做。
- 命令的**解析与执行**仍在主线程串行。

这样在万级 QPS 且 VALUE 较大的场景，网络拷贝不再成为瓶颈，而命令执行仍保持无锁简单性。

要点：
- 单线程模型决定了"慢命令"会阻塞整个实例（如 `KEYS *`、大 Hash 的 `HGETALL`）。
- 不要在线上执行 O(N) 且 N 很大的命令，必要时用 `SCAN` 分批。

### 1.2 数据结构与底层编码

Redis 对外提供 String、List、Hash、Set、ZSet 等类型，底层由多种**编码（encoding）**实现，根据数据规模自动切换：

- **SDS（Simple Dynamic String）**：相比 C 字符串，记录了长度（O(1) 求长）、预分配、二进制安全。
- **字典（dict）**：Hash 的默认底层，哈希表 + 链式冲突，触发**渐进式 rehash**（分多次迁移，避免一次性卡顿）。
- **跳表（skiplist）+ 字典**：ZSet 的有序实现，跳表支持范围查询，字典支持按成员 O(1) 查分。
- **ziplist / listpack**：紧凑连续内存结构，用于小 Hash/List/ZSet，省内存；元素过多会转成标准结构。
- **intset**：纯整数 Set 的紧凑编码。

设计启发：
- 大量小字段用 Hash 而非多个独立 Key，可借助 ziplist 节省内存。
- 大 Key（如几百 MB 的 Hash）会导致删除/迁移时阻塞，需拆分或分批。

### 1.3 持久化：RDB 与 AOF

**RDB（快照）**：
- 某一时刻内存数据的二进制快照。
- 通过 `fork()` 子进程写盘，利用写时复制（COW）不阻塞主线程。
- 优点：恢复快、文件紧凑；缺点：两次快照间宕机丢失数据。

**AOF（追加日志）**：
- 记录每条写命令，重启时重放。
- `appendfsync` 策略：always（每次刷盘，最安全最慢）/ everysec（每秒，折中）/ no（交给 OS）。
- AOF 会膨胀，通过 **AOF 重写**（fork 后按当前状态生成最小命令集）压缩。

**混合持久化**（4.0+）：
- AOF 重写时先写一份 RDB 全量，再追加增量 AOF，兼顾恢复速度与数据完整。

### 1.4 过期删除与内存淘汰

**过期删除**两种方式：
- 惰性删除：访问 Key 时才检查是否过期。
- 定期删除：定时随机抽样一批带过期时间的 Key 删除。

仅靠惰性会堆积"已过期但无人访问"的 Key，所以需定期删除兜底。

**内存淘汰（maxmemory-policy）**当内存达上限时触发：
- `noeviction`：不淘汰，写报错（默认）。
- `allkeys-lru` / `volatile-lru`：最近最少使用。
- `allkeys-lfu` / `volatile-lfu`：最不经常使用（4.0+，更准）。
- `allkeys-random` / `volatile-random`：随机。
- `volatile-ttl`：优先淘汰快过期的。

经验：缓存场景用 `allkeys-lru` 或 `allkeys-lfu`；需注意 LFU 的衰减计数配置。

### 1.5 集群与高可用

- **主从复制**：从节点全量同步（RDB）+ 增量命令流。
- **哨兵（Sentinel）**：监控、选主、通知，实现自动故障转移。
- **Cluster**：16384 个槽位（slot），数据按 `CRC16(key) % 16384` 分片。
  - 每个节点负责部分槽，Gossip 协议维护拓扑。
  - 客户端可直连任意节点，节点返回重定向（`MOVED`/`ASK`）。
  - 多 Key 操作若不在同一槽需用 Hash Tag 强制同槽。

### 1.6 线程与阻塞点

典型阻塞源：
- 大 Key 的删除/过期（4.0+ 异步延迟删除 `UNLINK` / `lazyfree`）。
- 同步 AOF `always` 刷盘。
- `fork` 本身在内存大时也会短暂卡顿（页表复制）。

## 二、MySQL InnoDB 核心实现

### 2.1 索引与 B+ 树

InnoDB 使用 **B+ 树**索引：
- 非叶子节点只存键值用于路由，叶子节点存完整数据（聚簇索引）或主键指针（二级索引）。
- 叶子节点用双向链表串联，范围扫描高效。
- 树高通常 3~4 层，千万级数据也能 3~4 次 IO 命中。

**聚簇索引**：主键即数据，行数据按主键顺序存放；因此"主键选短而递增的"能减少页分裂与碎片。

**二级索引**叶子存主键值，回表需再用主键查聚簇索引。

### 2.2 事务与隔离级别

InnoDB 通过 **MVCC + 锁**实现事务：
- **原子性**：undo log 支持回滚。
- **持久性**：redo log 保证崩溃后恢复。
- **隔离性**：MVCC + 锁。
- **一致性**：以上三者共同保证。

隔离级别：
- RU（读未提交）：基本不用。
- RC（读已提交）：每次读生成新 ReadView，解决脏读，有不可重复读。
- RR（可重复读，默认）：事务内首个快照不变，配合 **间隙锁（Next-Key Lock）** 防幻读。
- 串行化：强一致性，性能差。

### 2.3 MVCC 原理

每行记录隐藏字段：`DB_TRX_ID`（最近修改事务ID）、`DB_ROLL_PTR`（回滚指针指向 undo）。
- 读时生成 **ReadView**，依据事务ID 与可见性规则判断哪版数据可见。
- 旧版本存在 **undo log** 链中，读历史版本时沿指针回溯。
- 这就是"快照读"无锁的原因，显著提升并发读性能。

### 2.4 redo / undo / binlog

- **redo log**：物理日志，保证已提交事务不丢（WAL，先写日志再改页）。
  - 循环写，`write pos` 与 `checkpoint` 之间是可写区域。
  - 崩溃恢复时重放 redo。
- **undo log**：逻辑回滚日志，支持事务回滚与 MVCC 历史版本。
- **binlog**：Server 层逻辑日志，用于主从复制与增量备份（CDC 数据源）。
  - 两阶段提交（2PC）保证 redo 与 binlog 一致。

### 2.5 Buffer Pool

- 内存中缓存数据页（16KB/页），减少磁盘 IO。
- LRU 改进版：分 young/old 区，避免全表扫描把热数据冲掉。
- 脏页由后台线程按策略刷盘。

调优点：
- `innodb_buffer_pool_size` 通常设为物理内存 60~80%。
- 监控命中率、脏页比例、刷盘频率。

### 2.6 锁

- **行锁**：基于索引，无索引会升级为表锁。
- **间隙锁 / Next-Key Lock**：RR 下锁住记录及间隙，防幻读，但可能扩大锁范围导致死锁/阻塞。
- **死锁**：InnoDB 检测后回滚代价小的事务。

### 2.7 主从复制

- 基于 binlog：主库写 binlog → 从库 IO 线程拉取 → 从库 SQL 线程重放。
- 异步复制有延迟，半同步降低数据丢失风险。
- CDC 工具（Canal/Debezium）解析 binlog 做数据同步/搜索索引构建。

## 三、Redis 与 MySQL 的协作范式

- **缓存旁路（Cache-Aside）**：读先缓存后库，写先库后删缓存。
- **一致性**：缓存与库双写有窗口，常用"延迟双删"或"订阅 binlog 更新缓存"。
- **防穿透**：空值缓存 / 布隆过滤器。
- **防雪崩**：过期时间加随机抖动。
- **防击穿**：热点 Key 互斥重建或逻辑过期。

## 四、常见坑

1. Redis 大 Key 导致阻塞与迁移失败。
2. 慢命令（KEYS/HGETALL 大集合）拖垮实例。
3. AOF always 在高压下成为瓶颈。
4. MySQL 索引失效（隐式转换、函数包裹、前导模糊）导致全表扫描。
5. RR 下间隙锁范围过大引发并发阻塞。
6. Buffer Pool 过小导致频繁磁盘 IO。
