# ZooKeeper 核心源码要点

> 板块：源码系列 　|　 返回：[README](README.md)
> 关联：[源码系列/README](README.md)、[一致性协议与分布式共识深度](../../架构/一致性协议与分布式共识深度.md)、[CAP定理与一致性模型](../../架构/CAP定理与一致性模型.md)

ZooKeeper 是分布式协调的基石（注册中心、选主、分布式锁、配置管理）。它提供类文件系统的 ZNode 树，保证 **顺序一致（ZAB）** 与高可用。本文拆解数据模型、ZAB 协议、选主、Watcher 与典型用法。

## 一、核心定位与数据模型

- **定位**：分布式协调服务（CP 系统），不是数据库/消息队列。
- **ZNode 树**：类似目录树，每个节点存少量数据（默认 ≤ 1MB）。
- **节点类型**：
  - 持久 / 持久顺序（PERSISTENT / PERSISTENT_SEQUENTIAL）
  - 临时 / 临时顺序（EPHEMERAL / EPHEMERAL_SEQUENTIAL）——临时节点随会话断开自动删除（用于注册/锁）。

```
/
├── /services
│   ├── /order/0000000001   (临时顺序，注册实例)
│   └── /order/0000000002
└── /config/app            (持久，配置)
```

## 二、顺序一致性（ZAB 协议）

ZAB（ZooKeeper Atomic Broadcast）是类 Paxos 的原子广播协议，保证所有事务（写）**全局有序**（zxid 单调递增）。

| 角色 | 职责 |
|------|------|
| Leader | 接收写请求、提案、广播 |
| Follower | 接收提案、投票、参与选主 |
| Observer | 只同步数据、不参与投票（扩展读性能） |

```
Client 写 → Leader 分配 zxid → Proposal 广播 → Follower ACK → 多数派 → Commit → 响应
```

- **zxid**：64 位 = epoch(高32) + counter(低32)，保证顺序与选主时代。
- **写是 CP**：Leader 宕机进入选主，期间不可写（牺牲可用性保一致）。读可从任意节点（可能非最新，要最新需 sync）。

## 三、选主（Leader Election）

- 集群启动或 Leader 失联 → 进入 **LOOKING** 状态，发起选主。
- 基于 **ZAB 选主算法**：比较 (zxid, myid)，优先数据新（zxid 大），其次 myid 大。
- 多数派（quorum = (n+1)/2）同意即当选 → 进入 **LEADING/FOLLOWING**。
- 推荐奇数节点（3/5），容忍 (n-1)/2 故障。

## 四、Watcher 机制（事件通知）

- 客户端可对节点注册 Watcher（`getData`/`exists`/`getChildren` 带 watch）。
- 节点变更（创建/删除/数据改）触发一次性 Watcher 通知（**一次性**，需重新注册）。- 典型用法：监听配置节点、监听子节点变化做服务发现。

```java
// 监听配置变化
zk.getData("/config/app", watchedEvent -> {
    if (watchedEvent.getType()==EventType.NodeDataChanged){
        reloadConfig();                 // 重新加载
        zk.getData("/config/app", this, null);  // 重新注册
    }
}, stat);
```

> 注意 Watcher **一次性**：收到事件后必须重新注册，否则后续变更不通知（常见坑）。

## 五、分布式锁实现

利用**临时顺序节点**实现公平锁：

```
1. 在 /lock 下创建临时顺序节点 /lock/seq-00000001
2. 查 /lock 下所有子节点，若自己是最小序号 → 获锁
3. 否则对前一个（次小）节点注册 Watcher
4. 前一个释放（会话断/删除）→ 被唤醒，重新判断自己是否最小
```

- 优势：公平、防死锁（临时节点会话断自动释放）、惊群小（只 Watch 前一个）。
- 这是 Curator `InterProcessMutex` 的底层原理（推荐直接用 Curator，别手撸）。

## 六、典型使用场景

| 场景 | 用法 |
|------|------|
| 注册中心 | 服务实例建临时节点，消费者 Watch 子节点 |
| 分布式锁 | 临时顺序节点 + Watch 前驱 |
| 选主 | 抢建 /leader 临时节点，谁建上谁是主 |
| 配置管理 | 持久节点存配置，Watch 变更热更新 |
| 分布式队列 | 顺序节点 + 取最小消费 |

## 七、与 etcd / Eureka 对比

| 维度 | ZooKeeper | etcd | Eureka |
|------|-----------|------|--------|
| 一致性 | ZAB（顺序一致） | Raft（线性一致） | 最终一致（AP） |
| 类型 | CP | CP | AP |
| 场景 | 协调/锁/选主 | K8s/配置 | 服务发现 |

> 微服务注册发现若要求"宁可可用"用 Eureka（AP）；若要求强一致协调用 ZK/etcd（CP）。

## 八、常见坑

1. **Watcher 一次性** → 忘记重新注册导致漏通知。
2. **临时节点误用** → 会话超时连接断开，锁/注册节点被删（连接要稳、sessionTimeout 合理）。
3. **节点数据过大** → ZK 设计存小数据，存大对象拖慢同步（应只存指针/路径）。
4. **频繁写同一节点** → ZK 写要广播，非高吞吐写系统（别当 MQ/DB 用）。
5. **奇数节点配置错** → quorum 算错导致脑裂（用 3/5/7）。
6. **客户端不处理断连** → 连接断开后操作抛异常，需重连+会话恢复逻辑。

## 九、最佳实践

- 用 Curator 而非原生 API（封装了重试、锁、选举等）。
- 只存小数据（路径/配置值），大文件放对象存储、ZK 存 key。
- 合理设置 sessionTimeout（太短易误删，太长恢复慢）。
- Observer 扩展读，不增加选主投票负担。
- 监控：连接数、延迟、zxid 落后、节点数。
