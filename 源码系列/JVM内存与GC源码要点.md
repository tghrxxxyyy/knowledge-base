# JVM 内存与 GC 源码要点

> 本文从工程与源码视角梳理 JVM（以 HotSpot 为主）的内存布局、对象分配、垃圾回收算法与主流收集器（Serial/Parallel/CMS/G1/ZGC）的设计要点。内容基于公开的 JVM 实现原理，具体参数与默认行为以对应 JDK 版本官方文档为准。

## 1. JVM 运行时数据区

### 1.1 线程私有

- **程序计数器**：当前线程执行字节码的行号。
- **Java 虚拟机栈**：每方法一栈帧（局部变量、操作数栈、返回地址）；栈深度超限制抛 StackOverflowError。
- **本地方法栈**：Native 方法调用。

### 1.2 线程共享

- **堆（Heap）**：对象实例与数组，GC 主战场。
- **方法区（元空间 Metaspace）**：类元信息、常量、静态变量（JDK8 后元空间在本地内存）。
- **运行时常量池**：字面量与符号引用。

## 2. 堆的分代

- **新生代（Young）**：新对象在此分配，分 Eden + 两个 Survivor（S0/S1）。
- **老年代（Old）**：长生命周期对象、大对象。
- 分代假设：多数对象朝生夕死，故 Minor GC 频繁但快。

## 3. 对象创建与内存布局

### 3.1 分配流程

1. 类加载检查。
2. 计算对象大小，在 Eden 分配（指针碰撞或空闲列表）。
3. 并发分配用 TLAB（线程本地缓冲）减少锁竞争。
4. 初始化零值、设对象头。
5. 执行 <init> 构造。

### 3.2 对象头

- Mark Word：哈希、GC 分代年龄、锁状态。
- 类型指针：指向类元数据。
- 数组额外有长度。

### 3.3 对齐填充

- 对象大小按 8 字节对齐，补齐占位。

## 4. 可达性分析

- GC Roots：虚拟机栈引用、静态变量、常量、JNI 引用。
- 从 Roots 出发可达的对象存活，不可达的待回收。
- 解决了"引用计数"的循环引用问题。

## 5. 垃圾回收算法

### 5.1 标记-清除

- 标记存活，清除死亡。
- 缺点：碎片多、分配慢。

### 5.2 标记-整理

- 标记后把存活对象向一端移动，消除碎片。
- 适合老年代，但移动成本高。

### 5.3 复制算法

- 把存活对象复制到另一半区，原区全清。
- 无碎片、快，但浪费一半空间。
- 新生代用（Eden + 1 Survivor 复制到另 1 Survivor）。

## 6. 分代收集流程

### 6.1 Minor GC

- 仅回收新生代（Eden 满触发）。
- 存活对象复制到 Survivor 或晋升老年代（年龄达阈值/ Survivor 放不下）。
- 速度快，STW 短。

### 6.2 Major / Full GC

- 回收老年代甚至全堆。
- 停顿长，应尽量避免。

### 6.3 晋升

- 年龄计数器到阈值（默认 15）→ 晋升老年代。
- 大对象直接进老年代（避免新生代复制开销）。

## 7. 引用类型

- **强引用**：普通引用，不回收。
- **软引用**：内存不足时回收（缓存）。
- **弱引用**：下次 GC 即回收（WeakHashMap）。
- **虚引用**：仅跟踪回收，无实际引用能力。

## 8. Serial / Parallel 收集器

### 8.1 Serial

- 单线程 GC，简单、适合小应用/客户端。
- 全程 STW。

### 8.2 Parallel（吞吐量优先）

- 多线程 Minor/Major GC，追求高吞吐。
- 适合后台计算型、对停顿不敏感。

## 9. CMS（并发标记清除）

### 9.1 目标

- 降低老年代回收停顿，追求低延迟。

### 9.2 阶段

- 初始标记（STW 短）：标记 Roots 直接关联。
- 并发标记：与业务并发可达性分析。
- 重新标记（STW）：修正并发期间变化。
- 并发清除：清理死亡对象。

### 9.3 缺点

- CPU 敏感（并发占用线程）。
- 浮动垃圾：并发期间新死对象下次清。
- 内存碎片：标记-清除导致，可能触发 Full GC 压缩。

## 10. G1（Garbage First）

### 10.1 设计

- 将堆划分为多个 Region（如 1MB~32MB）。
- 优先回收"垃圾最多"的 Region（Garbage First）。
- 兼顾吞吐与停顿，可设目标停顿时间。

### 10.2 特点

- 逻辑分代但物理不连续。
- 增量并行回收，可预测停顿。
- 并发标记 + 转移（Evacuation）。

### 10.3 适用

- 大堆（数 G 到数十 G）、要求可控停顿的服务端默认选择之一。

## 11. ZGC / Shenandoah（低延迟）

### 11.1 目标

- 亚毫秒级 ~ 十毫秒级停顿，堆大小几乎不影响停顿。

### 11.2 关键技术

- 着色指针（Colored Pointers）：在指针元数据位记录对象状态。
- 读屏障（Load Barrier）：访问对象时修正引用。
- 并发转移：业务线程与 GC 同时移动对象。

### 11.3 代价

- 实现复杂，CPU/内存开销略高。
- 适合超大堆、极低延迟需求（如金融交易）。

## 12. GC 日志与调优

### 12.1 观察指标

- 吞吐（业务时间占比）。
- 停顿时间（STW 长尾）。
- 回收频率、晋升量、老年代增长。

### 12.2 常见参数方向

- 堆大小：-Xms/-Xmx 设一致避免动态扩。
- 新生代比例：影响 Minor 频率。
- 选择收集器：吞吐 → Parallel，低延迟 → G1/ZGC。
- 目标停顿：G1/ZGC 可设 MaxGCPauseMillis。

### 12.3 工具

- jstat：实时 GC 统计。
- jmap：堆转储。
- 可视化：GC 日志分析器。

## 13. 内存溢出与泄漏

### 13.1 OOM 类型

- Java heap space：堆对象过多/泄漏。
- Metaspace：类加载过多（动态代理、热部署）。
- GC overhead limit：GC 耗时占比过高却回收极少。

### 13.2 泄漏排查

- 堆转储对比：找出增长异常的对象类。
- 常见：静态集合长持引用、缓存无淘汰、监听器未注销、ThreadLocal 未 remove。

## 14. 常见踩坑

1. **堆设太小**：频繁 Full GC 甚至 OOM；按业务峰值设。
2. **忽视大对象**：直接进老年代，触发提前回收。
3. **ThreadLocal 不清理**：线程池复用致旧值/泄漏；用完 remove。
4. **用 CMS 在大堆**：碎片 + 并发失败转 Full GC，停顿爆；改 G1/ZGC。
5. **-Xms≠-Xmx**：运行时扩容触发额外 GC。
6. **误以为 GC 无感**：低延迟业务用 Parallel 导致长停顿；选低延迟收集器。

## 15. 选型速查

| 场景 | 收集器 |
|---|---|
| 小应用/客户端 | Serial |
| 高吞吐后台 | Parallel |
| 中堆可控停顿 | G1 |
| 超大堆低延迟 | ZGC / Shenandoah |
| 老系统兼容 | CMS（逐步淘汰） |

## 16. 小结

JVM 内存与 GC 的核心是"分代 + 可达性 + 复制/整理/清除的组合"。理解对象分配（TLAB、Eden、晋升）、可达性分析、以及各收集器的停顿/吞吐取舍，是排查 OOM 与调优的基础。现代服务端主流是 G1（均衡）与 ZGC（极低延迟），选型围绕"堆大小、延迟要求、CPU 预算"三要素，并以 GC 日志持续观测验证。
