# 消息中间件源码要点（Kafka / RocketMQ）

> 板块：源码系列 　|　 返回：[README](README.md)

消息中间件的高吞吐与可靠，本质来自几个共性设计：顺序写盘、PageCache、零拷贝、分区/队列并行、副本与 ACK。
本文以 Kafka 与 RocketMQ 为标本，拆解其核心机制与工程取舍，并补充 Pulsar 对照。

## 一、Kafka 核心机制

### 1.1 顺序写 + 零拷贝

Kafka 的高吞吐根基：
- **顺序写**：所有消息追加到分区日志文件末尾（append-only），磁盘顺序写远快于随机写。
- **零拷贝（sendfile）**：消费时 Broker 用 `sendfile` 把文件内容直接从页缓存拷贝到 Socket，省去内核态↔用户态来回。
- **PageCache**：消息先写页缓存再由后台线程刷盘，读也优先命中页缓存。

### 1.2 分区（Partition）与并行

- 一个 Topic 分为多个 Partition，Partition 是并行与水平扩展单元。
- 同 key 的消息经 `hash(key) % partition` 落到同一分区，**分区内有序**。
- 消费并行度受 Partition 数量约束：消费者数不应超过分区数（多余的消费者空闲）。

### 1.3 ISR 与副本

- 每个 Partition 有 Leader 与若干 Follower。
- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合。
- 消息"已提交"的定义：被 ISR 中所有副本确认。
- Leader 宕机时从 ISR 中选新 Leader，避免丢已提交消息。
- `acks` 参数：`0`（不等待）/ `1`（Leader 落盘）/ `-1/all`（ISR 全确认）。

### 1.4 消费位移（offset）

- 消费者按 offset 拉取，处理完提交 offset。
- 提交方式影响语义：
  - 先处理再提交（可能丢：处理中宕机，offset 未提交，重复消费）。
  - 先提交再处理（可能重复：提交后宕机，已提交未处理）。
- 手动提交 + 业务幂等是常见稳妥组合，实现"至少一次 + 幂等 = 实际恰好一次"。

### 1.5 日志分段与索引

- 分区日志按大小/时间分段（segment），便于清理与查找。
- 每个 segment 有**偏移量索引**与**时间戳索引**，支持按 offset/时间快速定位。

## 二、RocketMQ 核心机制

### 2.1 CommitLog 与 ConsumeQueue

- 所有消息**统一顺序写**到 CommitLog（单一物理队列），保证高写吞吐。
- **ConsumeQueue** 是逻辑队列：每个 Topic+Queue 一个，存消息在 CommitLog 的偏移、大小、tag 哈希。
- 消费时先查 ConsumeQueue 拿到 CommitLog 偏移，再读 CommitLog。

设计权衡：Kafka 按 Partition 多文件，RocketMQ 用单一 CommitLog + 多 ConsumeQueue 索引，二者都服务于"顺序写 + 并行消费"。

### 2.2 事务消息

保证"本地事务"与"消息发送"一致：
1. 发送**半消息**（Half Message，对消费者不可见）。
2. 执行本地事务。
3. 根据本地结果提交或回滚半消息。
4. Broker 对长期无结论的半消息发起**回查**，由生产者确认状态。

这避免了"本地成功但消息没发出"或"消息发出但本地失败"的不一致。

### 2.3 按 Tag 消费

- 消息可打 Tag，消费者通过 `TagA || TagB` 订阅过滤。
- ConsumeQueue 存了 tag 哈希，Broker 可在投递前过滤（但建议消费端再校验，因为哈希可能冲突）。
- 适合"同一 Topic 下不同业务线各取所需"的场景。

### 2.4 刷盘与复制

- 刷盘：同步刷盘（落盘才返回，可靠）/ 异步刷盘（写 PageCache 即返回，快但有丢风险）。
- 复制：同步双写（主备都写成功才返回）/ 异步复制。
- 可靠优先选同步刷盘 + 同步复制，性能优先选异步组合。

### 2.5 延迟消息与死信

- 定时/延迟消息：RocketMQ 用预设延迟级别（18 级）实现，通过内部调度topic 转发。
- 消费失败重试达上限进**死信队列（DLQ）**，供人工排查。

## 三、Pulsar 对照（分层架构）

- **计算存储分离**：Broker 无状态，存储用 BookKeeper（分片日志）。
- 同一 Topic 多个** ledger**，支持多副本写入。
- 分层使扩容更灵活（扩 Broker 不影响存储）。

## 四、共性设计总结

| 机制 | 目的 | Kafka | RocketMQ |
|------|------|-------|----------|
| 顺序写盘 | 高吞吐 | 分区日志 | CommitLog |
| 零拷贝 | 降低消费 CPU/拷贝 | sendfile | sendfile（transientPool） |
| 分区/队列 | 并行 | Partition | Queue |
| 副本/ISR | 不丢已提交 | ISR + acks | 同步双写 |
| 消费语义 | 至少/恰好一次 | offset 提交 | 消费位点 |
| 事务 | 一致性 | 事务 producer | 半消息+回查 |

## 五、消费幂等

中间件一般只保证"至少一次"，**幂等由业务侧保障**：
- 用消息唯一 ID（如业务单号）做去重表 / Redis SETNX。
- 数据库唯一约束兜底。
- 状态机避免重复处理（已处理则跳过）。

## 六、积压处理

- 临时扩容消费者（Kafka 受分区数限制）。
- 提高单条处理效率（批量、异步、批写）。
- 紧急时开"跳过/转移"通道，先保住新消息。
- 定位消费慢根因（锁、慢 SQL、外部依赖）。

## 七、顺序消息

- Kafka：单分区内有序，需把同业务 key 路由到同分区。
- RocketMQ：单 Queue 内有序，用顺序发送 + 单线程消费。
- 全局顺序代价极高，通常只需"局部顺序"（同订单/同用户有序）。

## 八、常见坑

1. 消费逻辑非幂等，导致重复消费数据错乱。
2. 消费者数 > 分区数，多出的消费者空转。
3. 自动提交 offset + 慢处理，崩溃后重复消费。
4. 消息体过大，撑爆网络与内存。
5. 消费超时频繁 rebalance，形成"消费—重平衡"死循环。
6. 事务消息未实现回查，半消息堆积。
