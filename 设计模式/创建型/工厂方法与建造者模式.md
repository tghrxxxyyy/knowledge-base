# 创建型模式：工厂方法、抽象工厂与建造者

> 板块：设计模式 　|　 返回：[README](../../README.md)
> 关联：[设计模式分类](../../设计模式/设计模式分类.md)、[结构型/适配器模式](../../设计模式/结构型/适配器模式.md)、[行为型/策略模式](../../设计模式/行为型/策略模式.md)、[DDD/战术设计精要](../DDD/战术设计精要.md)

创建型模式关注"对象怎么创建"，目标是**解耦对象的创建与使用**，让系统对变化（新产品、复杂构造）更开放。本文聚焦工厂方法、抽象工厂、建造者三种高频模式，对比适用场景与代码。

## 一、为什么需要创建型模式

- 直接 `new` 把"用哪个具体类"硬编码在调用方 → 新增产品要改调用方（违反开闭原则）。
- 复杂对象构造（多参数、多步、不变式）用构造器易出错、难读。
- 创建逻辑（如依赖、配置、池化）散落各处 → 难维护。

> 原则：把"创建"收敛到一个地方（工厂/建造者），调用方只依赖抽象。

## 二、工厂方法（Factory Method）

### 2.1 意图

定义一个创建对象的接口，让子类决定实例化哪一个类。调用方依赖工厂接口而非具体类。

```java
interface Transport { void deliver(); }
class Truck implements Transport { public void deliver(){ System.out.println("卡车"); } }
class Ship  implements Transport { public void deliver(){ System.out.println("轮船"); } }

interface LogisticsFactory { Transport create(); }
class RoadFactory  implements LogisticsFactory { public Transport create(){ return new Truck(); } }
class SeaFactory   implements LogisticsFactory { public Transport create(){ return new Ship(); } }

// 调用方只依赖工厂接口
LogisticsFactory f = new RoadFactory();
Transport t = f.create();   // 无需知道 Truck 的存在
```

### 2.2 适用

- 调用方不知道具体类，只知道抽象产品。
- 希望子类决定创建哪个类（框架扩展点）。
- 与模板方法常结合（父类定流程，子类定创建）。

## 三、抽象工厂（Abstract Factory）

### 3.1 意图

提供一个创建**一系列相关/相互依赖对象**的接口，而无需指定具体类。强调"产品族"（如一套 UI 的按钮+文本框必须同风格）。

```java
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}
class WinFactory implements GUIFactory {
    public Button createButton(){ return new WinButton(); }
    public Checkbox createCheckbox(){ return new WinCheckbox(); }
}
class MacFactory implements GUIFactory {
    public Button createButton(){ return new MacButton(); }
    public Checkbox createCheckbox(){ return new MacCheckbox(); }
}
// 应用只持有 GUIFactory，整族产品风格一致
GUIFactory f = isMac ? new MacFactory() : new WinFactory();
Button b = f.createButton();   // 与 checkbox 同族
```

### 3.2 工厂方法 vs 抽象工厂

| 维度 | 工厂方法 | 抽象工厂 |
|------|---------|---------|
| 创建对象 | 一个产品 | 多个相关产品（产品族） |
| 关注 | 单个创建的延迟决定 | 一系列产品的兼容性 |
| 实现 | 常是抽象工厂的组成部分 | 组合多个工厂方法 |

## 四、建造者（Builder）

### 4.1 意图

将复杂对象的构建与表示分离，同样的构建过程可创建不同的表示；尤其适合**多参数、可选参数多**的对象。

```java
class Computer {
    private final String cpu, ram, disk, gpu;     // 不可变
    private Computer(Builder b){ this.cpu=b.cpu; this.ram=b.ram; this.disk=b.disk; this.gpu=b.gpu; }
    static class Builder {
        String cpu, ram, disk, gpu;
        Builder cpu(String v){ this.cpu=v; return this; }   // 链式
        Builder ram(String v){ this.ram=v; return this; }
        Builder disk(String v){ this.disk=v; return this; }
        Builder gpu(String v){ this.gpu=v; return this; }
        Computer build(){
            if (cpu==null) throw new IllegalStateException("cpu 必填");  // 不变式校验
            return new Computer(this);
        }
    }
}
// 使用：清晰、可读、强制必填
Computer c = new Computer.Builder().cpu("i9").ram("32G").disk("1T").build();
```

### 4.2 适用与注意

- 参数多（尤其可选参数） → 比 telescoping 构造器（多重载）清晰得多。
- 强制不变式：在 `build()` 校验必填/约束。
- 与**产品变种**结合：同一 Builder 可产出不同配置的 Computer。
- 流式 API：Lombok `@Builder`、Kotlin `apply{}`、Go 的 functional option 都是建造者变体。

## 五、三种模式对比

| 模式 | 解决 | 关键词 |
|------|------|--------|
| 工厂方法 | 延迟单个对象的创建决定 | 子类定类 |
| 抽象工厂 | 创建一套相关对象（产品族） | 一致性族 |
| 建造者 | 复杂多步/多参数构造 | 链式、不变式 |

## 六、与 DDD 的关系

- 聚合创建复杂（需加载关联、校验）→ 用**工厂/工厂方法**封装（见 [DDD/战术设计精要](../DDD/战术设计精要.md)）。
- 值对象不可变 + 多参数 → 用**建造者**保证创建即一致。

```java
// DDD 中工厂方法保证聚合创建即有效
class Order {
    static Order create(Customer c, List<Item> items){
        Order o = new Order(c.id, items);
        o.validate();                  // 创建即校验不变量
        return o;
    }
}
```

## 七、常见坑

1. **过度工厂化** → 简单 new 也要工厂，徒增复杂度（简单对象直接 new）。
2. **工厂方法当简单工厂用** → 工厂方法强调"子类决定"，若无需多态别硬套。
3. **抽象工厂产品族爆炸** → 加一个产品要改所有工厂接口（用组合/默认实现缓解）。
4. **建造者不校验** → build() 漏校验导致非法对象（必填放 build 里）。
5. **Builder 非静态内部类持有外部引用** → 内存泄漏（用 static 嵌套类）。
6. **滥用导致类膨胀** → 每个产品一套工厂，类数量激增（权衡必要性与复杂度）。

## 八、选型速查

| 需求 | 选 |
|------|----|
| 调用方不该知道具体类 | 工厂方法 |
| 一套相关对象需风格/版本一致 | 抽象工厂 |
| 对象构造复杂、参数多 | 建造者 |
| 简单对象 | 直接 new（别套模式） |
