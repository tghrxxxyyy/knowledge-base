# 装饰器模式（Decorator）

> 所属分类：**结构型** 　|　 返回：[设计模式分类](../设计模式分类.md)

> **一句话定义**：动态地给一个对象**叠加**职责（增强），且保持同一接口、可多层嵌套——比生成大量子类更灵活。

## 意图

动态地给一个对象添加一些额外的职责；就增加功能而言，装饰器比生成子类更为灵活。装饰器在「运行时」按需包裹，避免继承导致的子类爆炸。

GoF 原话：*Attach additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.*

## 示例代码

```java
interface Coffee { double cost(); String desc(); }
class SimpleCoffee implements Coffee {
    public double cost() { return 10; }
    public String desc() { return "美式"; }
}
abstract class CoffeeDecorator implements Coffee {
    protected Coffee coffee;
    public CoffeeDecorator(Coffee c) { this.coffee = c; }
}
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee c) { super(c); }
    public double cost() { return coffee.cost() + 5; }
    public String desc() { return coffee.desc() + "+奶"; }
}
class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee c) { super(c); }
    public double cost() { return coffee.cost() + 2; }
    public String desc() { return coffee.desc() + "+糖"; }
}
// 使用：new SugarDecorator(new MilkDecorator(new SimpleCoffee())).cost();  // 17
```

> Java IO（`BufferedInputStream`、`DataInputStream`）即此模式的经典应用。

### 深挖：装饰器叠加链与「顺序语义」

```mermaid
graph LR
    A[SimpleCoffee 10] --> B[+Milk 15] --> C[+Sugar 17] --> D[cost=17]
```

- **叠加语义**：外层装饰器调用内层的 `cost()`，形成递归求和——这正是 IO 流 `read()` 逐层委托的模型。
- **顺序敏感**：`new BufferedInputStream(new FileInputStream(...))`——必须先「底层字节流」再「缓冲装饰」；反了则语义错误。
- **与继承对比**：`MilkCoffee`、`SugarCoffee`、`MilkSugarCoffee` 三件套已需 3 个子类，n 种配料组合爆炸 2ⁿ；装饰器只需 n 个装饰器任意组合。

### 深挖：函数式 / 无抽象类的轻量写法

当接口只有单一方法时，可以用「函数包装器」替代继承体系，避免为每个装饰器写一个类：

```java
// 用 Function 风格的包装器，无需为每个增强写一个类
interface Handler { String handle(String input); }

static Handler decorate(Handler target, Handler... enhancers) {
    Handler result = target;
    for (Handler e : enhancers) {
        final Handler prev = result;
        result = input -> e.handle(prev.handle(input)); // 组合增强
    }
    return result;
}
// 日志 + 鉴权 + 业务 三层叠加，零新类
Handler h = decorate(
    input -> "业务:" + input,
    input -> "日志:" + input,
    input -> "鉴权:" + input
);
```

> 现代 Java（函数式接口 + `UnaryOperator`）下，装饰器常退化为「行为组合」，这正是 `Stream` 的 `peek`/`map` 链式增强的思想来源。

### 深挖：装饰器 vs 责任链 vs AOP 的协作边界

| 模式 | 包裹方式 | 每层的职责 | 何时用 |
|------|----------|------------|--------|
| 装饰器 | 层层包裹同一对象 | 每层都处理全部职责并增强 | 功能可任意组合叠加 |
| 责任链 | 节点接力 | 每节点可选处理并决定是否传递 | 请求逐级审批 / 过滤器 |
| AOP 代理 | 切面织入 | 横切关注点（日志/事务/缓存） | 框架级统一增强 |

> 三者常共存：Spring `HandlerInterceptor` 链是责任链，`HttpServletRequestWrapper` 是装饰器，`@Transactional` 是 AOP 代理。理解各自边界才能不乱用。

## 适用场景

- 需要在运行时动态、可组合地为对象增加职责，而不想用大量子类膨胀类层级。
- 典型：IO 流、请求/响应包装、监控埋点、加密/压缩流、缓存层、权限/审计包装。

## 与相似模式区别

- 与**适配器**：装饰器**不改接口**只加功能；适配器为兼容而**改接口**。
- 与**代理**：装饰器强调功能增强且可多层叠加；代理强调对原对象的访问控制（常单层）。
- 与**责任链**：装饰器是「层层包裹同一对象」（每层处理全部职责）；责任链是「节点接力」（每节点可选处理并传递）。

## 不适用场景（反例）

- 只加**一层**功能且永久不变——直接子类继承更简单。
- 装饰后需要**调用具体子类的独特方法**——装饰器基于接口，会丢失具体类型信息（可用原生类型回退或泛型缓解）。
- 装饰链**过长且顺序敏感**——顺序错就出错，应考虑更显式的管线（如 Builder）。
- 增强逻辑会**改变对象的语义身份**（如把 read 改成写）——这不是装饰而是篡改，应重新设计。

## 在 JDK / Spring / 开源中的真实应用

- **JDK IO**：`BufferedInputStream` 装饰 `FileInputStream`、`DataInputStream` 叠加；`BufferedReader`/`LineNumberReader`。
- **集合**：`Collections.unmodifiableList`/`synchronizedList` 包装（装饰器变体）。
- **Servlet**：`HttpServletRequestWrapper`/`HttpServletResponseWrapper` 是装饰器（Filter 里包装请求）。
- **Spring**：`TransactionInterceptor` 链式装饰；`HttpHeaders` 不可变包装。
- **Netty**：`ChannelPipeline` 里的 `ChannelHandler` 通过 `addLast` 层层包裹，是典型的装饰器 + 责任链混合。
- **OkHttp**：`Interceptor` 链用 `RealInterceptorChain` 把每个拦截器包裹起来，形成装饰式调用。

## 实现要点与常见坑

- **保持同一接口**：装饰器与组件实现相同接口，才能无限叠加。
- **顺序敏感**：`new BufferedInputStream(new FileInputStream)` 与反过来（不可）有顺序要求，先具体后缓冲。
- **与代理混淆**：装饰器『增强并透明传递同一接口』可叠加；代理『控制/替代访问』通常只有一层。
- **类型丢失**：装饰后 `instanceof` 具体类会失败，需要特定能力时设计回退或接口暴露。
- **不可变优先**：装饰器通常返回新包装对象而非修改原对象，契合函数式不可变风格，减少并发隐患。
- **调试栈深**：叠加 4 层以上时，异常栈会很长，建议在包装处标记 `toString()` 便于排错。

## 生产实践与重构信号

1. **重构信号**：同一接口出现「A + B 增强」「A + C 增强」「A + B + C 增强」多个组合类 → 换装饰器。
2. **典型落地**：请求/响应包装（Servlet 过滤器）、IO 缓冲、监控埋点（计时/日志装饰器）、加密/压缩流叠加。
3. **与责任链对比**：装饰器是「层层包裹同一对象」；责任链是「节点接力」。功能叠加用装饰器，请求逐级处理用责任链。
4. **保持幂等**：装饰器不要改变原对象的可观察状态，除非语义要求。
5. **限流场景**：把限流装饰器放在最外层，确保下游所有增强都受保护；缓存装饰器放在靠近业务侧以减少重复计算。

## 反模式案例

### 案例：装饰器顺序错导致缓冲失效

```java
// 反模式：缓冲装饰在底层流内部，缓冲形同虚设
InputStream in = new FileInputStream("a.txt");
InputStream buf = new BufferedInputStream(in);   // 正确：先具体后缓冲
// 若写成 new FileInputStream(new BufferedInputStream(...)) 编译都不通过，但
// 在 Filter 链里把"解压"包在"解密"外层却忘记解压需要原始字节流，则解密读取错位
```

**修正**：明确「越底层越靠近被装饰者」，转换类装饰器（解压/解密）必须在其依赖的字节流外层正确排序。

### 案例：装饰器里重复打日志

```java
class LogDecorator implements Handler {
    Handler next;
    public String handle(String i){
        log.info("enter");      // 装饰器自己打
        String r = next.handle(i);
        log.info("exit");
        return r;
    }
}
// 若被装饰者内部也打了同样的日志 → 双倍日志，且无法区分层级
```

**修正**：日志装饰器统一收口，被装饰者不再各自打进入/退出日志，或加 MDC traceId 区分。

## 面试高频追问（30 条）

1. Q：装饰器 vs 继承？ A：装饰器运行期动态叠加功能，避免子类爆炸；继承编译期固定、组合爆炸。
2. Q：装饰器 vs 代理？ A：装饰器增强且可多层叠加、保持接口；代理控制访问，常单层替代原对象。
3. Q：JDK IO 哪里用了装饰器？ A：BufferedInputStream 包装 FileInputStream，可再套 DataInputStream。
4. Q：装饰器顺序重要吗？ A：重要，通常是『被装饰者在内、缓冲/转换在外』。
5. Q：装饰后 instanceof 原类型为何失败？ A：对象是装饰器实例而非原组件，需用接口或回退方法。
6. Q：装饰器缺点？ A：大量小类、装饰顺序易错、调试时调用栈深。
7. Q：装饰器与责任链区别？ A：装饰器层层包裹、每层都处理全部职责（叠加）；责任链每节点可选处理并传递。
8. Q：Collections.synchronizedList 是装饰器吗？ A：是，包装 List 加上同步，接口不变。
9. Q：装饰器能保持对象不可变吗？ A：能，装饰器通常不修改原对象，只包装增强。
10. Q：Servlet 请求包装怎么用？ A：HttpServletRequestWrapper 装饰请求，Filter 中改写参数/头。
11. Q：如何避免装饰器嵌套过深？ A：收敛装饰器数量（≤3 层），或用 builder/管线显式编排。
12. Q：装饰器 vs 模板方法？ A：装饰器运行期动态组合；模板方法编译期固定流程。
13. Q：装饰器里能访问具体类方法吗？ A：不能（基于接口），需要时应在接口上暴露。
14. Q：日志装饰器会有什么坑？ A：重复日志（装饰器自身+原对象都有日志）与性能开销。
15. Q：什么时候装饰器比继承好？ A：功能可无限组合、且组合方式运行时才确定时。
16. Q：装饰器与 AOP 关系？ A：AOP 代理常用来实现装饰器式的横切增强（日志/事务/缓存）。
17. Q：装饰器能装饰类（非接口）吗？ A：可以，但抽象装饰器需继承该类，灵活度低于接口方案。
18. Q：组合多个装饰器有性能问题吗？ A：每层是一次虚方法调用，层数多时有开销，热点路径慎用。
19. Q：装饰器和桥接怎么区分？ A：装饰器是运行时叠加增强；桥接是编译期解耦两个变化维度。
20. Q：装饰器在 Web 框架的应用？ A：Spring 的 HandlerInterceptor、Netty 的 ChannelHandler 链都含装饰器思想。
21. Q：函数式写法能替代类装饰器吗？ A：单方法接口可用 Function 组合替代，零新类；多方法接口仍建议类体系。
22. Q：装饰器如何做缓存？ A：最内层放原始数据，外层放缓存装饰，命中直接返回，避免重复计算。
23. Q：装饰器能用于不可变对象吗？ A：能，每次装饰返回新的包装对象，原对象不变，天然线程安全。
24. Q：OkHttp 拦截器是装饰器吗？ A：是责任链 + 装饰混合，每个 Interceptor 包裹 chain 再调用 proceed。
25. Q：装饰器怎么写单测？ A：对最内层给假对象，逐层验证增强输出与顺序；可用 spy 确认调用次数。
26. Q：装饰器与组合模式区别？ A：装饰器是「单链路包裹增强」；组合是「树形部分-整体聚合」。
27. Q：装饰器可以动态撤销增强吗？ A：运行期把外层摘掉即可（保留内层引用），比继承灵活。
28. Q：为什么 stream 的 map/filter 像装饰器？ A：每个中间操作返回一个新的流包装，叠加形成管线。
29. Q：装饰器在日志场景的最佳实践？ A：统一在最外层收口日志，内部不再重复，配合 MDC 串联链路。
30. Q：装饰器会导致内存泄漏吗？ A：一般不会，但若装饰器持有外部大对象引用且长期缓存，需注意释放。

## 速记口诀

> **「同一接口层层包，功能叠加不用套子类；顺序要记牢，内真实外增强。」**
> 装饰器（叠加增强）≠ 代理（控制访问）≠ 适配器（改接口）。
