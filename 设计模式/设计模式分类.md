# 设计模式

> 本文是设计模式的**总览与分类索引**。GoF 23 种模式已拆分为独立文档（见上方「各模式详细文档」），每个文件内含：意图、结构（类图）、示例代码、适用场景、与相似模式区别。


## 设计模式的分类

### 创建型

- **工厂模式**：简单工厂（if else 去选择）、工厂方法（多个工厂）、抽象工厂（对整个完整对象构建的抽象）。
- **单例模式**：饿汉、饱汉、DCL、内部类、enum。
- **建造者模式**：相比抽象工厂更关注实现的步骤和组合。
- **原型模式**：clone。

### 结构型

- **代理模式**：动态代理解决静态代理代码爆炸问题。
- **适配器模式**
- **桥梁模式**
- **装饰模式**：Java 的 IO。
- **门面模式**：当一个系统过于复杂，拥有大量接口时，可以通过门面模式为外部提供一组简化的高层接口。当需要降低各模块间的耦合度，使代码结构更加清晰时，可以引入门面模式作为模块间的通信中介。当希望控制子系统的访问权限或执行顺序时，通过门面模式可以更好地进行管理和控制。
- **组合模式**：当你想表示对象的部分-整体层次结构时，比如文件系统、组织架构、DOM（文档对象模型）等。当你需要用户以统一的方式处理单个对象和组合对象，并且希望简化客户端代码时。
- **享元模式**：当你的应用中存在大量的相似对象，而这些对象之间大部分状态都可以外部化时。当你想通过共享大量对象来节约内存时。

### 行为型

- **策略模式**
- **观察者模式**
- **责任链模式**：责任树。
- **模板方法模式**
- **状态模式**
- **访问者模式**：查看账单，账单原始数据是不变的，不同的访问者对应展示不同的数据，老板看总的收入支出，财务看税前税后等等。

## 六大设计原则

> 参考文章：[https://zhuanlan.zhihu.com/p/110130347](https://zhuanlan.zhihu.com/p/110130347)

### 单一职责原则（Single Responsibility Principle）

**定义**：应该有且仅有一个原因引起类的变更。

**好处**：

1. 类的复杂性降低，实现什么职责都有清晰明确的定义；
2. 可读性高，复杂性降低，可读性自然就提高了；
3. 可维护性提高，可读性提高了，那自然更容易维护了；
4. 变更引起的风险降低，变更是必不可少的，如果接口的单一职责做得好，一个接口修改只对相应的实现类有影响，对其他的接口无影响，这对系统的扩展性、维护性都有非常大的帮助。

### 开闭原则（Open Closed Principle）

**定义**：开闭原则是指一个软件实体如类、模块和函数应该对扩展开放，对修改关闭。也就是说一个软件实体应该通过扩展来实现变化，而不是通过修改已有的代码来实现变化。

**为什么要用开闭原则**：

1. 开闭原则非常著名，只要是做面向对象编程的，在开发时都会提及开闭原则。
2. 开闭原则是最基础的一个原则，前面介绍的 5 个原则都是开闭原则的具体形态，而开闭原则才是其精神领袖。
3. 开闭原则提高了复用性，以及可维护性。

### 里氏替换原则（Liskov Substitution Principle）

**定义**：就是只要父类能出现的地方，子类就可以出现，而且替换为子类也不会产生任何错误或异常。

### 迪米特法则（Law of Demeter）

又叫“最少知道法则”。

如果一个方法放在本类中，既不增加类间关系，也对本类不产生负面影响，那就放置在本类中。

### 接口隔离原则（Interface Segregation Principle）

接口隔离原则就是客户端不应该依赖它不需要的接口，或者说类间的依赖关系应该建立在最小的接口上。

### 依赖倒置原则（Dependence Inversion Principle）

依赖倒置原则可以减少类间的耦合性，提高系统的稳定性，降低并行开发引起的风险，提高代码的可读性和可维护性。

**使用建议**：

1. 每个类尽量都有接口或抽象类，或者接口和抽象类两者都具备。
2. 变量的表面类型尽量是接口或抽象类。
3. 任何类都不应该从具体类派生。
4. 尽量不要重写基类的方法。如果基类是一个抽象类，而且这个方法已经实现了，子类尽量不要重写。
5. 结合里氏替换原则使用。

**总结**：

1. **单一职责原则**：一个类或接口只承担一个职责。
2. **里氏替换原则**：在继承类时，务必重写（override）父类中所有的方法，尤其需要注意父类的 protected 方法（它们往往是让你重写的），子类尽量不要暴露自己的 public 方法供外界调用。
3. **依赖倒置原则**：高层模块不应该依赖于低层模块，而应该依赖于抽象。抽象不应依赖于细节，细节应依赖于抽象。
4. **接口隔离原则**：不要对外暴露没有实际意义的接口。
5. **迪米特法则**：尽量减少对象之间的交互，从而减小类之间的耦合。
6. **开闭原则**：对软件实体的改动，最好用扩展而非修改的方式。

# SOLID 原则与设计模式关系

SOLID 是设计模式的"价值观"，模式是原则的具体落地。对应关系如下：

| 原则 | 含义 | 典型支撑模式 |
| --- | --- | --- |
| 单一职责 (SRP) | 一个类一个变更原因 | 外观、中介者（收敛职责）、命令（隔离请求） |
| 开闭 (OCP) | 对扩展开放、对修改关闭 | 策略、装饰器、观察者、模板方法、抽象工厂 |
| 里氏替换 (LSP) | 子类可替换父类而不出错 | 策略、状态、装饰器（均依赖抽象替换） |
| 接口隔离 (ISP) | 依赖最小接口 | 适配器、外观、桥接 |
| 依赖倒置 (DIP) | 依赖抽象而非细节 | 工厂方法、抽象工厂、建造者、桥接、观察者 |

> 记忆口诀：模式是"术"，SOLID 是"道"。优先满足原则，再选用模式；不要为用模式而违反原则。GoF 经典建议：**"Favor composition over inheritance（优先使用组合而非继承）"**，多数行为型与结构型模式都体现了这一点。

# 反模式与过度设计

## 常见反模式
- **上帝类（God Class）**：一个类承担过多职责，违反 SRP，难以测试与维护。
- **霰弹式修改（Shotgun Surgery）**：一处需求变更需改动多处，说明职责分散。
- **循环依赖**：模块互相引用，违背 DIP 与迪米特法则。
- **硬编码依赖**：直接 `new` 具体类，无法替换/测试。
- **重复的 if/else 分支**：本可用策略 / 状态 / 责任链消除。

## 过度设计的信号
- 用五六个类解决一个 `if` 能搞定的问题（如给只有一个实现的地方硬上抽象工厂）。
- 提前引入扩展性，但需求半年不变 —— **YAGNI（You Aren't Gonna Need It）**。
- 滥用单例导致全局可变状态、难以并发与测试。
- 为"显得专业"而堆砌模式，反而增加理解成本。

## 实践建议
1. **先朴素实现，再重构引入模式**（三次重复后再抽象）。
2. 优先组合而非继承。
3. 以**可测试性**为标尺：难测试往往意味着耦合过重。
4. 模式服务于业务清晰度，而非相反。

## 设计模式在主流框架中的真实应用

### Spring Framework
- **工厂方法 / 依赖注入**：`BeanFactory`/`ApplicationContext` 是超级工厂，按配置生产 Bean；
- **单例**：Spring 容器中的 Bean 默认单例（容器级，非 GoF 静态单例）；
- **代理 / 装饰器**：AOP 用 JDK 动态代理或 CGLIB 在运行时织入切面（事务、日志）；
- **模板方法**：`JdbcTemplate`、`RestTemplate` 固化"获取连接—执行—释放"流程，可变步骤回调；
- **观察者**：`ApplicationEvent` + `@EventListener` 实现事件通知；
- **策略**：`Resource` 按前缀（`classpath:`/`file:`/`http:`）选不同实现；
- **适配器**：`HandlerAdapter` 让不同 Controller 类型统一被 DispatcherServlet 调用。

### JDK 标准库
- **迭代器**：`java.util.Iterator` / `for-each`；
- **观察者**：`java.util.Observer`/`Observable`（已过时，但语义经典）；
- **策略**：`Comparator` 把比较算法外置；
- **命令**：`Runnable`/`Callable` 把任务封装为对象；
- **工厂方法**：`Executors.newFixedThreadPool()` 等；
- **桥接**：`Collections.synchronizedList()` 在 List 与同步装饰间桥接；
- **原型**：`Object.clone()`；
- **外观**：`java.util.Collections` 聚合大量集合操作。

### Netty
- **责任链**：`ChannelPipeline` 由多个 `ChannelHandler` 串成，入站/出站事件逐站传递；
- **工厂方法**：`ChannelFactory` / `Bootstrap` 创建通道；
- **建造者**：`ServerBootstrap` 链式配置；
- **策略**：`EventLoopGroup` 的 IO 多路复用策略（NIO/Epoll）；
- **观察者**：`ChannelFuture` + `GenericFutureListener` 异步回调。

### MyBatis
- **建造者**：`SqlSessionFactoryBuilder` 解析配置建 `SqlSessionFactory`；
- **工厂方法**：`SqlSessionFactory` 生产 `SqlSession`；
- **代理**：Mapper 接口由 `MapperProxy` 动态代理，方法调用映射为 SQL；
- **桥接**：`Executor` 与 `StatementHandler` 解耦执行与语句构建；
- **模板方法**：`BaseExecutor` 定义 `query` 骨架，子类实现 `doQuery`。

## 模式组合运用案例（策略 + 模板方法 + 工厂）

场景：订单折扣计算，不同活动有不同算法，且计算都遵循"校验—算额—记账"固定流程。

```java
// 模板方法：固定流程
public abstract class DiscountTemplate {
    public final Money calculate(Order o) {
        if (!validate(o)) return Money.ZERO;
        Money m = doCalculate(o);     // 钩子：由策略实现
        bookkeeping(o, m);
        return m;
    }
    protected abstract Money doCalculate(Order o);
    protected boolean validate(Order o) { return o != null; }
    private void bookkeeping(Order o, Money m) { /* 记账 */ }
}
// 策略：多种折扣算法
public class VipDiscount extends DiscountTemplate {
    protected Money doCalculate(Order o) { return o.total().multiply(0.8); }
}
public class FullReduction extends DiscountTemplate {
    protected Money doCalculate(Order o) { return o.total().value() > 200 ? Money.of(20) : Money.ZERO; }
}
// 工厂：按类型产出策略
public class DiscountFactory {
    public DiscountTemplate get(String type) {
        return switch (type) {
            case "vip"  -> new VipDiscount();
            case "full" -> new FullReduction();
            default -> throw new IllegalArgumentException(type);
        };
    }
}
```

组合收益：模板方法固化流程防遗漏，策略让算法可插拔，工厂隐藏创建细节——三者各司其职。

## 重构遗留代码识别模式气味

闻到以下"气味"，就是该引入模式的信号：
- **重复的 if/else 分支**（按类型走不同逻辑）→ 策略 / 状态 / 责任链；
- **new 具体类散落各处** → 工厂 / 抽象工厂 / 依赖注入；
- **方法里一大段 try/catch 包裹同类逻辑** → 装饰器 / 代理（AOP）；
- **对象构建参数爆炸（10+ 参数）** → 建造者；
- **树形结构上反复写递归遍历** → 组合 + 访问者 / 迭代器；
- **大量重复的资源开关代码** → 模板方法；
- **调用第三方接口耦合在业务里** → 适配器 / 防腐层；
- **一个类 1000+ 行、谁都改** → 外观 / 中介者收敛职责。

重构纪律：**先覆盖测试，再小步重构成模式**，每步保持绿灯。

## DDD 与设计模式关系

- 设计模式是**战术实现手段**，DDD 是**战略+战术方法论**；二者互补而非替代；
- DDD 的聚合/实体/值对象常用**工厂**创建、**仓储**持久化、**规格**筛选；
- 跨上下文协作用**领域事件**（观察者/发布订阅）+ **防腐层**（适配器）；
- DDD 强调"把行为放回对象"，天然契合**策略/模板/状态**等"将变化封装进对象"的模式；
- 区别：DDD 关注"业务边界与语言"，设计模式关注"代码结构的复用套路"。高价值域用 DDD + 模式，低价值 CRUD 用简单模式甚至事务脚本即可。
