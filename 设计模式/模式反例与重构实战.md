# 设计模式反例与重构实战

> 模式用错比不用更糟。本文列举常见"反模式"与过度设计，并给出识别信号与重构方向，帮助在"该用"与"滥用"之间找平衡。

## 1. 过度设计（Over-Engineering）

为"将来可能"的需求提前堆抽象。

| 信号 | 说明 |
| --- | --- |
| 抽象层无第二实现 | 只有一个实现的工厂/接口 |
| 配置项从不用 | 万能但无用的开关 |
| 类爆炸 | 每个变体一个类 |

对策：YAGNI（You Aren't Gonna Need It）。先简单实现，在第二个真实需求出现时再抽象。

## 2. 贫血领域模型

```java
// 反例：Entity 只有数据
class Order {
    private List<Item> items;
    // 无行为，逻辑在 OrderService 里
}
class OrderService {
    void calc(Order o){ /* 业务规则在这 */ }
}
```

- 行为散在 service，领域对象成"数据容器"。
- 重构：把与订单相关的计算/状态迁移移入 Order（富领域模型）。

## 3. 上帝类 / 上帝方法

一个类/方法承担过多职责（如 `ApplicationService` 写了所有业务）。

- 信号：文件上千行、改一处影响全局。
- 重构：按聚合/用例拆分，下沉领域逻辑。

## 4. 错误地用 Singleton

```java
// 反例：为"方便"到处用单例全局状态
GlobalConfig.getInstance().getX()  // 隐式依赖，难测试
```

- 问题：隐式依赖、并发态、测试难。
- 重构：通过依赖注入显式传参，单例交给容器管理。

## 5. 滥用继承

"is-a" 关系不成立却用继承，导致脆弱基类。

| 信号 | 说明 |
| --- | --- |
| 子类只 override 一两个方法 | 组合更合适 |
| 父类改了子类崩 | 基类脆弱 |
| 多层深继承 | 难理解 |

重构：用组合（委托）替代继承（策略/装饰器替代子类扩展）。

## 6. 重复的代码拷贝

同一逻辑多份拷贝，改一处漏其他。

- 重构：提取公共方法/工具类，但要区分"真重复"vs"偶然相似"。

## 7. 过深的 if-else 分支

```java
if (type == A) ... else if (type == B) ... else if (type == C) ...
```

- 重构：策略模式 + Map 分发，或状态模式。
- 但简单分支不必硬套模式（KISS）。

## 8. 回调地狱 / 嵌套过深

异步回调层层嵌套，难以阅读。

- 重构：用 Promise/async-await、CompletableFuture、响应式流。

## 9. 识别信号清单

| 信号 | 可能问题 |
| --- | --- |
| 改需求要动很多类 | 耦合高 |
| 单测难写 | 依赖隐式/全局 |
| 类很大 | 职责过多 |
| 大量 switch/if | 缺多态 |
| 重复逻辑 | 未抽象 |

## 10. 重构原则

- 小步快跑，配合测试。
- 先有测试再重构（安全网）。
- 用模式解决"已出现的痛点"，而非预设。

## 11. 面试题

1. 什么是 YAGNI？何时该抽象？
2. 贫血模型如何重构？
3. 继承 vs 组合如何选？
4. 如何识别上帝类？
5. 为什么单例可能是反模式？

## 12. 小结

模式是手段不是目的。反模式的根源多是"为模式而模式"或"忽略职责单一"。原则：YAGNI 防过度、富领域防贫血、组合替脆弱继承、测试护航重构。简单能解决问题就别上模式。
