# eBPF 与可观测性实战

> 板块：云原生 　|　 返回：[README](README.md)
> 适用：内核级可观测、无侵入监控、网络安全、性能分析。

eBPF 让用户态程序**安全地运行在 Linux 内核中**，无需改内核或应用代码，就能观测系统调用、网络、文件、CPU 等一切行为。它是现代云原生可观测与安全的底层革命（Cilium、Pixie、Falco 都基于它）。

## 一、eBPF 是什么

- **本质**：内核中的沙箱虚拟机，运行受限的字节码（验证器保证安全，不会死循环/越界）。
- **挂载点（Hook）**：系统调用、内核函数（kprobe）、用户函数（uprobe）、网络（XDP、TC）、跟踪点。
- **数据通道**：通过 BPF Map 在内核与用户态间高效传递数据（环形缓冲）。
- **价值**：零侵入观测、极低开销、内核级真实数据。

## 二、能做什么

| 领域 | 能力 | 代表工具 |
|------|------|----------|
| 可观测 | 系统调用/网络/延迟追踪 | Pixie、bpftrace |
| 网络 | 高性能负载均衡、网络策略 | Cilium |
| 安全 | 运行时威胁检测 | Falco |
| 性能 | CPU/IO/锁 火焰图 | BCC 工具集 |
| 追踪 | 无侵入分布式追踪 | Pixie（自动注入） |

## 三、可观测性场景

### 3.1 无侵入分布式追踪

- 传统追踪需改代码埋点；eBPF 在内核层捕获 socket/系统调用，自动关联请求，无需应用改造。
- Pixie 即基于 eBPF 实现"零代码改动"的服务拓扑与请求追踪。

### 3.2 网络可观测

- 捕获每个连接的 RTT、重传、丢包、字节数，识别慢连接/异常流量。
- 比应用层指标更底层、更真实。

### 3.3 性能剖析

- 采样 CPU 栈，生成火焰图，定位热点函数（无需重启应用）。
- BCC 的 `profile`/`offcputime` 是经典性能利器。

## 四、网络与安全的代表：Cilium

- **基于 eBPF 的 CNI**：替代 kube-proxy（iptables），用 eBPF 做高性能负载均衡与服务路由。
- **网络策略**：L3/L4/L7 策略，细粒度访问控制。
- **优势**：避免 iptables 规则爆炸，性能高，支持 L7（如按 HTTP 路径）。

## 五、安全检测：Falco

- 用 eBPF 监控系统调用，定义规则检测异常（如容器里起 shell、改敏感文件）。- 运行时安全（runtime security）的重要组成。

## 六、工作原理简示

```
用户态程序(loader) ──加载──> eBPF 字节码 ──验证──> 内核 Hook 点
                                       ↓ (事件)
                                   BPF Map <──> 用户态读取/展示
```

```c
// 简化：追踪 execve 系统调用（bpftrace 一行式）
tracepoint:syscalls:sys_enter_execve { printf("%s %s\n", comm, str(args->filename)); }
```

## 七、局限与门槛

- **内核版本要求**：较新内核（4.x+/5.x 更佳），旧内核能力受限。
- **复杂度**：编写 eBPF 需 C + 内核知识，门槛高；多用现成工具（BCC/Pixie/Cilium）。
- **安全**：验证器保证安全，但不当的 Map 设计仍有风险。
- **可移植**：不同内核版本需 CO-RE（Compile Once Run Everywhere）。

## 八、与传统监控对比

| 维度 | APM/埋点 | eBPF |
|------|----------|------|
| 侵入性 | 需改代码/SDK | 零侵入 |
| 数据层 | 应用层 | 内核层（更真实） |
| 开销 | 中 | 低（内核高效） |
| 门槛 | 低 | 高（需内核知识） |

## 九、常见误区

1. **eBPF 万能** → 不是所有问题都适合；应用层指标仍必要。
2. **忽视内核版本** → 功能不可用；确认内核支持。
3. **自己造轮子** → 复杂度高；优先 BCC/Cilium/Pixie。
4. **忽略安全验证** → 不当 eBPF 有风险；用验证器 + 受控部署。
5. **只追新不设观测** → 老手段（Prometheus）仍基础；eBPF 是补充。
