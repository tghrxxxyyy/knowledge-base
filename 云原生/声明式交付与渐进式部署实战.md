# 声明式交付与渐进式部署实战

> 声明式交付（GitOps）让"期望态"活在 Git，系统自动向期望态收敛；渐进式部署（Argo Rollouts 等）在此基础上加金丝雀、分析门禁，让发布可观测、可暂停、可自动回滚。二者共同把"发布"变成受控工程。

## 1. 声明式交付

```mermaid
flowchart LR
    G[(Git:期望态)] --> C[控制器 Sync]
    C --> K[(集群:实际态)]
    K -->|Drift检测| C
```

- Git 是唯一真相源，任何变更走 PR。
- 控制器持续对比，自动修正漂移。
- 审计天然（谁、何时、改了什么都在 Git）。

## 2. 渐进式部署

| 策略 | 机制 |
| --- | --- |
| 金丝雀 | 按流量比例逐步放量 |
| 蓝绿 | 两套切换 |
| 分析门禁 | 指标达标才继续 |

```yaml
# Rollout 概念
apiVersion: argoproj.io/v1alpha1
kind: Rollout
spec:
  strategy:
    canary:
      steps:
        - setWeight: 10
        - analysis: {template: success-rate}
        - setWeight: 50
        - pause: {duration: 5m}
```

## 3. 分析门禁

- 每个阶段跑分析（错误率、延迟、业务指标）。
- 达标继续，不达标自动中止/回滚。
- 与监控打通，实时取数。

## 4. 常见坑

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 漂移未修 | 配置被改 | 自动 sync |
| 门禁盲 | 异常放行 | 多维指标 |
| 回滚慢 | 影响大 | 自动回滚 |
| Git 冲突 | 丢变更 | PR 流程 |
| 状态不可见 | 不知进度 | 可视化 |

## 5. 面试题

1. 声明式交付为什么可靠？
2. 渐进式部署如何自动决策？
3. 分析门禁看哪些指标？
4. GitOps 与 CI/CD 关系？
5. 漂移如何被发现和修复？

## 6. 小结

声明式交付 + 渐进式部署 = Git 期望态 + 流量分层 + 分析门禁 + 自动回滚。核心是"发布可声明、可观测、可自动撤销"。
