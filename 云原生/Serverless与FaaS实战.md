# Serverless 与 FaaS 实战

Serverless（无服务器）是一种云原生计算范式，开发者无需管理服务器即可运行代码。
FaaS（Function as a Service，函数即服务）是 Serverless 的计算承载形态。
本文从概念、模型、触发器、冷启动、状态、成本、调试与落地场景系统讲解。

## 一、Serverless 的整体认知

### 1.1 什么是 Serverless

Serverless 并非"没有服务器"，而是"无需关心服务器"。
它由两部分组成：

- FaaS：事件驱动的函数计算，按需运行、按调用计费。
- BaaS（Backend as a Service）：托管式后端能力，如对象存储、数据库、消息队列、身份认证。

核心特征：

- 无需管理基础设施：扩容、打补丁、故障恢复由云平台负责。
- 按需计费：只为你真正执行的代码时间付费，空闲不计费。
- 自动弹性：请求到来时自动拉起实例，流量下降时缩容到零。

### 1.2 Serverless 与容器的区别

容器需要你定义副本数、规格、扩缩容策略。
Serverless 把"运行单元"收敛到函数粒度，平台接管调度。

对比维度：

| 维度 | 容器/Pod | FaaS 函数 |
|------|----------|-----------|
| 部署单位 | 镜像 + 配置 | 函数代码 + 配置 |
| 扩缩容 | 按副本数/HPA | 按请求自动、可至零 |
| 计费 | 按实例运行时间 | 按调用次数与执行时长 |
| 启动延迟 | 秒级（镜像拉取） | 冷启动毫秒到秒级 |
| 适用 | 长驻服务 | 短任务、事件驱动 |

### 1.3 典型使用场景

适合 Serverless 的场景：

- 定时任务：每天凌晨跑报表、清理数据。
- 文件处理：对象存储上传后自动转码、缩略图生成。
- Webhook 处理：接收第三方回调并落库。
- 数据管道：消息队列消费、ETL 转换。
- 轻量 API：低频、波动大的接口。

不适合的场景：

- 长连接（WebSocket 长驻）需要常驻进程。
- 超大内存或超长执行时间（超过平台上限）。
- 强状态、高吞吐、低延迟的在线核心链路。

## 二、FaaS 的运行模型

### 2.1 函数结构

一个典型 FaaS 函数包含：

- 入口方法（handler）：接收事件对象与上下文。
- 业务逻辑：纯计算或调用下游服务。
- 返回结果：结构化数据或写入下游。

以伪代码表示：

```text
function handler(event, context):
    # event: 触发事件载荷（如 HTTP 请求体、消息体）
    # context: 运行时上下文（请求ID、剩余时间、函数名）
    data = parse(event)
    result = process(data)
    return result
```

### 2.2 触发器（Trigger）

函数本身不监听端口，由触发器唤起：

- HTTP 触发器：API 网关转发请求。
- 对象存储触发器：文件 Put 事件。
- 消息队列触发器：消费消息。
- 定时触发器（Cron）：周期执行。
- 数据库触发器：数据变更事件。

### 2.3 执行模型：单并发与多并发

不同平台对单实例并发的处理不同：

- 单并发模型：一个实例同一时刻只处理一个请求，请求多了就扩容实例。
- 多并发模型：一个实例可同时处理多个请求（如某些平台的并发度参数）。

多并发能降低实例数、减少冷启动，但要求函数无全局可变状态依赖。

## 三、冷启动问题与优化

### 3.1 冷启动的成因

冷启动指"从零创建一个可执行实例"的过程，包含：

- 调度与分配资源。
- 下载/加载函数代码与依赖。
- 初始化运行时（语言 VM、框架）。
- 执行用户初始化代码（连接池、全局配置）。

与之相对的是热启动：实例已就绪，直接处理请求。

### 3.2 冷启动的影响

冷启动会显著增加首请求的延迟。
对于延迟敏感的在线接口，冷启动可能造成 P99 明显升高。
高频调用的函数通常会保持实例热态，冷启动比例低。

### 3.3 优化手段

常见优化：

- 精简依赖：移除无用包，减小代码体积。
- 延迟初始化：把非必要初始化放到首次调用时按需执行。
- 预热（Provisioned Concurrency）：预先保持一定数量的暖实例。
- 减小包体积：使用分层（layer）拆分公共依赖。
- 选择轻量运行时：如某些脚本语言启动更快。

### 3.4 连接池与冷启动的冲突

冷启动后全局连接池被重建，旧实例的连接在缩容时被回收。
因此不能在函数外持有长期连接并假设它跨调用有效。
推荐在初始化阶段建立连接，并复用同一实例内的连接。

## 四、状态与存储

### 4.1 FaaS 是无状态的

函数实例可能在任意时刻被创建或销毁。
你不能依赖实例本地磁盘或内存来保存会话状态。

正确做法：

- 状态外置到托管存储：对象存储、KV、数据库、缓存。
- 会话信息用 Token 或外部会话存储。
- 临时文件写到平台提供的临时目录，且不能跨调用假设存在。

### 4.2 数据持久化选型

- 结构化数据：云数据库/托管 RDS。
- 键值缓存：托管 Redis。
- 大文件：对象存储。
- 消息：托管 MQ。
- 配置：配置中心或环境变量。

## 五、成本模型

### 5.1 计费构成

典型计费维度：

- 调用次数：每百万次一个计费单位。
- 执行时长：以 GB-秒（内存 × 时间）计。
- 出网流量：跨区或公网流量。
- 附加服务：存储、数据库等按各自计费。

### 5.2 成本优化

- 合理设置内存：内存越大单位时间计费越高，但可能执行更快。
- 减少执行时长：优化算法、减少外部调用。
- 合并小函数：避免过多细粒度调用带来的调用次数费用。
- 异步化：耗时操作转异步，缩短主函数时长。

## 六、调试与可观测

### 6.1 本地调试

- 使用平台提供的本地模拟器运行函数。
- 构造事件样本（event payload）进行单元测试。
- 打印结构化日志，便于在云端检索。

### 6.2 云端日志与监控

需关注：

- 调用次数、错误率、冷启动比例。
- 执行时长分布（P50/P95/P99）。
- 并发实例数。
- 与下游调用的链路追踪。

### 6.3 分布式追踪

函数作为链路的其中一个节点，需要透传 TraceId。
入口处从事件中提取或生成 TraceId，下游调用统一携带。

## 七、常见反模式

### 7.1 把函数写成巨型单体

一个函数承担过多职责，难以维护、难以复用。
应按业务边界拆分，但也不要拆得过碎导致调用链过长。

### 7.2 在_handler_里做重初始化

每次请求都重建连接池、读大文件，性能极差。
初始化应放在实例级（handler 外）。

### 7.3 依赖本地状态

在内存里缓存业务状态并假设下次请求还命中同一实例。
实例随时可能被回收，导致状态不一致。

### 7.4 忽略超时

函数有最大执行时长限制，超时会被强杀。
长任务应拆成多段，或用异步任务编排。

## 八、与编排结合

### 8.1 函数编排（Workflow）

多个函数通过状态机串联：

- 串行：A → B → C。
- 并行分支：同时执行多个函数再汇聚。
- 重试与补偿：失败时按策略重试或回滚。

### 8.2 事件驱动架构

FaaS 天然适配事件驱动：

- 生产者发出事件。
- 事件总线分发。
- 多个函数各自消费、互不阻塞。

## 九、落地建议

- 从非核心、波动性大的任务切入（定时、文件处理）。
- 明确冷启动对业务延迟的容忍度。
- 统一管理函数的超时、内存、并发参数。
- 为函数建立可观测体系（日志/指标/追踪）。
- 将状态与连接全部外置，保持函数无状态。

## 十、速记

- Serverless = FaaS + BaaS，核心是"不关心服务器"。
- 按调用与执行时长计费，空闲为零。
- 冷启动是首请求延迟的主要来源，可预热优化。
- 函数必须无状态，状态外置到托管存储。
- 适合事件驱动、波动大的短任务，不适合长连接核心链路。
