# 可观测性（Observability）

## 〇、本体介绍

**可观测性是什么**：通过系统对外暴露的**三类信号**——指标（Metrics）、日志（Logs）、链路（Traces），在「不重新发版」的前提下，推断系统内部状态、定位问题。它不是「监控」的同义词：监控告诉你「挂了没」，可观测性告诉你「为什么挂、卡在哪」。

**解决什么痛点**：微服务 + 容器后，一次请求横跨十几个服务，靠看单机日志完全抓瞎。可观测性把分散的信号聚合、关联、下钻，把排障从「猜」变成「看」。

**核心概念**：三大支柱（Metrics/Logs/Traces）、RED/USE 方法论、Golden Signals、Prometheus、Grafana、Loki、OpenTelemetry、Exporter、Alertmanager。

**适用场景**：任何生产系统，尤其分布式微服务、云原生。
**不适用场景**：单机脚本、无运维诉求的玩具项目（过度建设）。

---

## 一、可观测性三大支柱

| 支柱 | 回答的问题 | 典型工具 |
|------|-----------|---------|
| Metrics（指标） | 系统整体「健康度」：QPS、错误率、延迟、CPU | Prometheus、VictoriaMetrics |
| Logs（日志） | 某次请求「到底发生了什么」 | Loki、ELK、ClickHouse |
| Traces（链路） | 一次请求「跨服务怎么走的、卡在哪」 | Jaeger、Tempo、OpenTelemetry |

> 三者关系：**Metrics 发现异常 → Traces 定位慢/错的服务 → Logs 看具体原因**。

---

## 二、方法论：RED / USE / Golden Signals

- **RED（请求类服务）**：Rate（请求速率）、Errors（错误率）、Duration（延迟分布）。
- **USE（资源类）**：Utilization（利用率）、Saturation（饱和度）、Errors（错误）。
- **Google Golden Signals**：延迟、流量、错误、饱和度——四个最该盯的。

---

## 三、Prometheus：拉模型时序数据库

- **拉（Pull）模型**：Prometheus 主动按 `scrape_interval` 从各 `Exporter` / 服务 `/metrics` 端点拉指标（区别于 Pushgateway 推模型补边缘场景）。
- **数据模型**：时间序列 = `指标名 + 一组 label（键值对）`，存储为 TSDB。
- **PromQL**：强大查询语言，支持 `rate()`、`histogram_quantile()`（算 P99）、`sum by()` 聚合。
- **Exporter**：把第三方系统指标转成 Prometheus 格式（node_exporter、mysqld_exporter…）。
- **Alertmanager**：告警去重、分组、路由（邮件/钉钉/Webhook）。

> 关联：时序库专题已详述 Prometheus 的 TSDB 视角（见 基础知识/时序库/Prometheus.md）。

---

## 四、Grafana：可视化与告警面板

- 多数据源（Prometheus / Loki / Tempo / MySQL…）统一仪表盘。
- 看板（Dashboard）+ 告警规则，是「看系统」的主界面。

---

## 五、Loki：日志的「类 Prometheus」方案

- 只索引**标签**（不像 ELK 全文本倒排），成本低、与 Prometheus 风格一致。
- 日志与指标共用 label 体系，便于「从指标跳到对应日志」。

---

## 六、Traces 与 OpenTelemetry（OTel）

- **Trace**：一次请求生成 `TraceID`，每跳是一个 `Span`（含起止、耗时、状态），串联成调用树。
- **OpenTelemetry**：**厂商中立**的可观测性数据采集标准（API/SDK/Collector），统一采集 Metrics/Logs/Traces，可导出到任意后端（Jaeger/Tempo/商业 APM），避免厂商锁定。
- **Context Propagation**：跨进程传递 TraceID（HTTP header `traceparent`），是链路贯通的关键。

---

## 七、采样（Sampling）

- 高流量下全量 trace 太贵，需采样：头部采样（Head-based，开头决定）、尾部采样（Tail-based，看完整个 trace 再决定，能保住异常链路）。
- 指标一般全量；日志可按级别/错误采样。

---

## 八、SLO / SLI / 错误预算

- **SLI**（指标，如可用性 99.9%）、**SLO**（目标）、**错误预算**（允许的失败额度）。错误预算耗尽则冻结新功能、先修稳定性——把「可靠性」量化成工程决策。

---

## 九、与 K8s / Mesh 的联动

- K8s 的 Pod 指标（cAdvisor）、Mesh 的 RED 指标天然是 Prometheus 的采集源。
- 服务网格自动注入 trace header，链路开箱即用（见 云原生/ServiceMesh.md）。

---

## 十、与其他板块的关系

- **场景设计 / 问题定位**：可观测性是排障的「眼睛」，问题定位靠它落地。
- **架构 / 系统架构**：可观测性常列为架构非功能需求（与韧性并列）。
- **CI/CD / DevSecOps**：流水线里接质量门禁与可观测性度量（DORA）。
- **源码系列**：应用埋点（Micrometer / OTel SDK）来自业务代码。

---

## 十一、速查表

| 信号 | 工具 | 关键 |
|------|------|------|
| Metrics | Prometheus + Grafana | Pull、PromQL、`histogram_quantile` 算分位 |
| Logs | Loki / ELK | 标签索引、与指标联动 |
| Traces | Jaeger / Tempo + OTel | TraceID/Span、context 传播 |
| 告警 | Alertmanager | 去重/分组/路由 |

## 面试高频问题（20+ 条）

1. **可观测性三大支柱？** Metrics（健康度）、Logs（发生了什么）、Traces（请求怎么走/卡哪）。
2. **监控 vs 可观测性？** 监控告「挂没挂」；可观测性从暴露信号推断「为什么」，且无需发版。
3. **RED 与 USE 区别？** RED 面向请求服务（Rate/Errors/Duration）；USE 面向资源（Utilization/Saturation/Errors）。
4. **Golden Signals 是哪些？** 延迟、流量、错误、饱和度。
5. **Prometheus 为什么是拉模型？** 主动 scrape `/metrics`，简单、易发现、利于联邦；边缘/短任务用 Pushgateway 补。
6. **Prometheus 数据模型？** 指标名 + 多维 label 的时间序列，存 TSDB。
7. **PromQL 算 P99 怎么写？** `histogram_quantile(0.99, sum(rate(http_duration_bucket[5m])) by (le))`。
8. **直方图 vs 摘要（Histogram vs Summary）？** Histogram 存分桶可聚合、算任意分位；Summary 客户端算好分位、不可跨实例聚合。
9. **Exporter 是什么？** 把第三方系统指标转成 Prometheus 格式的中间件（node/mysql exporter）。
10. **Alertmanager 作用？** 告警去重、分组、静默、路由到不同渠道。
11. **Loki 和 ELK 区别？** Loki 只索引 label（省成本、类 Prom 风格）；ELK 全文本倒排（功能强、贵）。
12. **什么是 Trace / Span？** Trace 是一次请求全链路，Span 是其中一跳（含耗时/状态），组成调用树。
13. **OpenTelemetry 是什么？** 厂商中立的可观测性采集标准（API/SDK/Collector），统一三类信号、防锁定。
14. **TraceID 怎么跨服务传递？** 通过 context propagation（HTTP `traceparent` header），保证链路贯通。
15. **为什么要采样？** 全量 trace 成本高；头部/尾部采样在成本与保住异常链路间权衡。
16. **尾部采样 vs 头部采样？** 头部开头决定（简单）；尾部看完整个 trace 再定（能保异常链路，需缓冲）。
17. **SLO / SLI / 错误预算？** SLI 实测指标、SLO 目标、错误预算允许失败额度；耗尽则优先修稳定。
18. **如何定位「慢请求」？** Metrics 发现延迟升高 → Traces 找慢 Span → Logs 看该 Span 详情。
19. **埋点怎么做？** 用 Micrometer（指标）/ OTel SDK（三类信号），框架自动埋或手动埋业务事件。
20. **可观测性在 K8s 里数据源？** cAdvisor（Pod 指标）、kube-state-metrics、Mesh RED 指标、应用 `/metrics`。
21. **MTTR 为什么重要？** 可观测性的终极目标是缩短平均恢复时间；配合告警+面板+链路。
22. **日志太多怎么治理？** 结构化日志（JSON）+ 合理级别 + 按错误采样 + Loki 标签检索，避免全量落盘。
