# 服务网格流量治理实战

> 板块：云原生 　|　 返回：[README](README.md)
> 适用：微服务流量管理、灰度发布、熔断限流、安全通信。

服务网格（Service Mesh）把服务间通信（路由、重试、熔断、mTLS、可观测）从业务代码下沉到**基础设施层（Sidecar 代理）**，让业务专注逻辑。Istio/Envoy 是代表。

## 一、核心架构

```
控制面(Istiod) ──配置下发──> 数据面(每个 Pod 内 Envoy Sidecar)
                                    ↓ 拦截所有进出流量
                         业务容器 <──> Envoy <──> 其他服务
```

- **数据面**：Envoy 代理每个服务的进出流量（iptables/IPVS 透明拦截）。
- **控制面**：Istiod 统一管理配置、证书、服务发现，下发到 Envoy。
- **业务零侵入**：代码不改，治理能力由 Sidecar 提供。

## 二、流量路由（VirtualService）

- **按版本路由**：`v1 90% / v2 10%` 实现金丝雀。
- **按请求路由**：header/路径匹配（如 `/api/v2/*` → 新版本）。
- **故障注入**：路由层注入延迟/错误，配合混沌测试。

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata: { name: reviews }
spec:
  hosts: [ reviews ]
  http:
  - match: [{ headers: { x-canary: { exact: "true" } } }]
    route: [{ destination: { host: reviews, subset: v2 } }]
  - route: [{ destination: { host: reviews, subset: v1 } }]
```

## 三、弹性能力

| 能力 | 配置 | 作用 |
|------|------|------|
| 超时 | timeout | 防止长等待拖垮 |
| 重试 | retries | 瞬时错误自愈 |
| 熔断 | outlierDetection | 剔除不健康实例 |
| 限流 | quota | 保护后端 |

> 注意：重试要配合**幂等**，避免重试放大故障。

## 四、安全：mTLS

- 网格内自动 mTLS（服务间加密 + 身份认证），无需改应用。
- 基于身份的授权策略（如"仅允许 frontend 调 review"）。
- 渐进式：PERMISSIVE（兼容明文）→ STRICT（强制加密）。

## 五、可观测性

- Sidecar 自动生成指标（RED）、访问日志、trace 上下文。
- 与 Prometheus/Grafana/Jaeger 原生集成。
- 免埋点获得全量服务拓扑与黄金信号。

## 六、灰度发布

```
Stable(100%) ──> 注入金丝雀路由 ──> Canary(5%) ──观测──> 扩大/回滚
```

- 比 K8s 原生 RollingUpdate 更细（按流量比例而非实例比例）。
- 结合指标自动分析（如 Argo Rollouts + Istio）。

## 七、适用与权衡

**适合**：多语言微服务、强治理诉求、需细粒度流量控制。
**代价**：
- 资源开销（每 Pod 多一 Sidecar，内存/CPU 增加）。
- 复杂度（运维控制面、排障多一跳）。
- 延迟增加（每跳多两次代理）。

> 不是银弹：小团队/简单服务用网关 + SDK 治理更轻。

## 八、与 API 网关的关系

- **网关**：南北向（外部→内部），鉴权/限流/聚合。
- **网格**：东西向（服务→服务），细粒度治理。
- 二者互补：网关管入口，网格管内部。

## 九、常见坑

1. **Sidecar 资源不设限** → 开销失控；设 request/limit。
2. **重试不幂等** → 放大故障；重试 + 幂等。
3. **mTLS 一刀切 STRICT** → 老服务连不上；先 PERMISSIVE 过渡。
4. **复杂路由难调试** → 多一跳排障难；熟悉 VirtualService/DestinationRule。
5. **忽视延迟** → 每请求多几次代理；评估是否必要。
6. **控制面单点** → 治理全失效；控制面高可用。
