# 检索增强与向量数据库实战进阶

> 本文在基础 RAG 管线之上，深入检索侧与向量库的工程细节：切分策略、混合检索、重排序、向量库选型（Milvus、Qdrant、Weaviate、pgvector、Elasticsearch）、以及生产化陷阱。结合前文 RAG 概述与进阶检索，本文偏"检索与存储"落地。

## 1. 检索质量决定 RAG 上限

RAG 的效果瓶颈往往不在生成模型，而在**检索是否召回了正确片段**。一个常见现象：答案错误是因为检索阶段压根没拿到相关资料，LLM 只能"编造"补位。因此检索侧优化（recall）优先级高于 prompt 微调。

## 2. 文档切分（Chunking）策略

### 2.1 为什么要切分

Embedding 模型对过长文本会截断或平均化语义，导致长文档检索不准；同时 LLM 上下文有限，需把相关片段送入。切分是"语义完整"与"粒度可控"的折中。

### 2.2 常见切分方法

- **固定长度切分**：按 token/字符数切（如 512 token），重叠（overlap）保留上下文。简单但易切断语义。
- **按结构切分**：按标题/段落/表格切，保留层级（Markdown / HTML 解析）。语义更完整。
- **语义切分**：用模型判断句子相似度断点，合并高相关句为一块。
- **父子文档（Parent-Child）**：子块用于精召回，父块用于喂给 LLM，兼顾检索精度与上下文完整。

### 2.3 重叠与大小

切分过大→检索不精确；过小→上下文缺失、碎片多。经验上 256–512 token 配 10–20% 重叠是常见起点，需按文档类型调。

## 3. Embedding 模型与维度

- **维度**：768 / 1024 / 1536 等。维度高表达力强但存储与计算成本上升。
- **中文场景**：优先选在中文语料上训练或对齐的模型（如 bge、m3e 等系列，以官方为准），通用英文模型在中文上可能偏弱。
- **归一化**：多数向量库用余弦相似度，需对向量做 L2 归一化，使点积等价于余弦。

## 4. 混合检索（Hybrid Search）

纯向量检索擅长语义召回，但弱于精确匹配（专有名词、产品编号、错误码）。混合检索结合：

- **向量检索**：语义相似。
- **关键词检索（BM25 / 倒排）**：精确词项匹配。
- **融合**：RRF（Reciprocal Rank Fusion）或加权打分合并结果。

Elasticsearch / Weaviate / Milvus 2.x 等均支持混合检索。实践中混合检索在真实问答上显著优于纯向量。

## 5. 重排序（Re-rank）

检索召回 top-K（如 50）后，用 Cross-Encoder 重排取 top-N（如 5–8）送入 LLM：

- **Bi-Encoder（检索）**：query 与 doc 各自编码，快，但交互弱。
- **Cross-Encoder（重排）**：query+doc 联合编码，精度高，慢。

典型链路：向量/BM25 召回 50 → Cross-Encoder 重排 → 取 top 5 → 生成。这是提升答案相关性的性价比最高的一步。

## 6. 向量数据库选型

### 6.1 Milvus

- 定位：面向大规模向量的专用数据库，支持亿级向量。
- 索引：IVF、HNSW、DiskANN 等；支持标量过滤（metadata filter）。
- 部署：单机（standalone）到分布式（cluster）皆可。
- 适用：超大规模、需要丰富索引与过滤的检索。

### 6.2 Qdrant

- Rust 编写，性能与资源占用平衡好，API 简洁。
- 支持 payload 过滤、量化压缩、本地与云托管。
- 适用：中等规模、追求易用与性价比的团队。

### 6.3 Weaviate

- Go 编写，schema 化，内建向量化模块（可接模型）与混合检索。
- 适用：希望"开箱混合检索 + 语义/关键词融合"的场景。

### 6.4 pgvector

- PostgreSQL 扩展，把向量当列存，复用现有 PG 运维与事务。
- 支持 IVFFlat、HNSW 索引与 SQL 过滤。
- 适用：已有 PG、规模不大、想避免新组件的团队。亿级需谨慎。

### 6.5 Elasticsearch

- 以倒排索引起家，现支持 dense_vector 做向量检索，天然混合检索。
- 适用：已有 ES 栈、需要全文 + 向量统一入口。

| 项目 | 语言 | 规模 | 混合检索 | 运维 |
|---|---|---|---|---|
| Milvus | Go/C++ | 亿级 | 支持 | 中（分布式重） |
| Qdrant | Rust | 千万级 | 支持 | 轻 |
| Weaviate | Go | 千万级 | 内建强 | 中 |
| pgvector | C(扩展) | 百万-千万 | 有限 | 复用 PG |
| Elasticsearch | Java | 大 | 内建 | 重 |

## 7. 索引与相似度

- **HNSW**：基于图的近似最近邻，召回高、查询快，内存占用大（需把图放内存）。
- **IVF（PQ/Flat）**：聚类分桶，内存友好，需调 nprobe 平衡召回与速度。
- **相似度**：内积（IP）、余弦（Cosine）、欧氏（L2）。归一化后内积≈余弦。

## 8. 元数据过滤与多租户

- **过滤**：检索时按 `doc_type`、`时间`、`租户` 过滤，避免跨域召回。
- **多租户隔离**：用 namespace/collection 隔离，或统一集合 + 租户字段过滤（注意权限与越权）。
- **时效性**：文档更新需重算 embedding 并替换/删除旧向量，否则召回过期内容。

## 9. 评测检索质量

- **Recall@K**：相关文档是否在前 K 被召回。
- **命中率（Hit Rate）**：问题对应答案片段是否进入召回集。
- **MRR / NDCG**：排序质量。
- 应建立"问题—期望片段"标注集，离线回归检索改动。

## 10. 生产化陷阱

1. **切分切断语义**：纯固定切分把表格/代码劈成两半，检索失效；应结合结构切分。
2. **向量维度不匹配**：query 与 doc 用不同模型编码，相似度无意义；须统一。
3. **未归一化导致相似度异常**：内积未归一化，长文本向量模长大被高估。
4. **召回 top1 直接喂**：未重排导致噪声片段进上下文；应召回多、重排取精。
5. **索引类型误选**：亿级用 IVF 但 nprobe 过小召回骤降；用 HNSW 又内存爆。
6. **过滤与向量冲突**：强过滤下候选不足，需放松过滤或两阶段。
7. **多租户越权召回**：只靠应用层过滤，向量库层面未隔离，存在越权风险。

## 11. 进阶方向

- **查询改写（Query Rewriting）**：把口语问题改写成检索友好短语，或做多查询扩展。
- **假设性文档嵌入（HyDE）**：先让 LLM 生成"假设答案"再做嵌入检索，提升语义对齐。
- **自查询（Self-Query）**：LLM 从自然语言抽取过滤条件与检索词，驱动结构化过滤。
- **小型化重排**：用蒸馏 Cross-Encoder 降低重排延迟与成本。

## 12. 小结

检索增强的"增强"二字重点在检索工程：切分保语义、混合检索补精确、重排序提相关、向量库按规模选型。把 recall 做扎实，再谈 prompt 与模型，是 RAG 落地最划算的投入产出比。
