# 推理模型成本与取舍

> 对应工程落地视角，与 test-time compute、推理模型评测章节互补。

## 一、背景与挑战

推理模型（o1/R1/QwQ 等）因显式生成长思维链，单次响应的 token 数往往是普通模型的 5–20 倍，带来三重成本：显存占用（KV cache 随序列变长）、算力（生成更多 token）、延迟（用户等待更久）。在客服、实时对话、批量抽取等高并发场景，直接用推理模型可能让单位请求成本飙升、超时率上升，甚至因长上下文撑爆显存而失败。因此落地关键不是「能不能用」，而是「何时用、用多少、怎么省钱」，也就是在准确率、延迟、成本三者间做工程权衡。

## 二、核心原理

成本与「思考预算」强相关。核心取舍逻辑：

- **难度路由**：用轻量路由器判断问题难度，简单题走快模型、难题才走推理模型，避免「杀鸡用牛刀」。
- **思考预算调节**：按任务设 `max_think_tokens`，少思考=快而便宜，多思考=准但贵；部分 API 还支持「思考摘要」以省输出。
- **提前退出 / 早停**：若思维链已给出高置信答案或触发终止标记，可截断思考省 token。
- **蒸馏小模型**：把推理能力蒸馏到 7B/14B，单卡即可高吞吐服务，单位成本骤降。
- **批处理与缓存**：相同前缀的并发请求可共享 KV cache；对重复子问题做结果缓存。

本质是在「准确率-延迟-成本」三角中找 Pareto 最优工作点，而非一味追求最高准确率。

### 工程落地要点

- **分级 SLA**：按业务延迟/成本预算设档位（快模型 / 中预算推理 / 大预算推理），路由据此分流。
- **缓存命中**：相同前缀或相同问题可复用思考/答案缓存，长尾流量成本可降数倍。
- **异步与流式**：推理模型思考慢，前端用流式输出思考片段，避免用户误以为卡死。
- **预算封顶**：对单请求设 token 上限与超时，防止个别难题无限思考拖垮队列。
- **按价值计费**：内部结算用「每正确回答成本」而非「每 token 单价」，更准确反映 ROI。
- **小模型下沉**：高频中等难题优先用蒸馏小模型，仅最难尾部流量上大模型。

## 三、形式化与数学基础

设快模型单位成本 $c_f$、正确率 $a_f$；推理模型成本 $c_r$、正确率 $a_r$，且 $c_r\gg c_f$，$a_r>a_f$ 仅在难分布成立。期望收益差：

$$
\Delta = (a_r - a_f)\cdot v_{\text{task}} - (c_r - c_f)
$$

仅当任务价值 $v_{\text{task}}$ 足够大（难题）时 $\Delta>0$，使用推理模型才划算。思考预算 $B$ 与成本近似线性、与错误率近似幂律：

$$
c(B)\propto B,\qquad \epsilon(B)\approx \epsilon_\infty + k B^{-\alpha}
$$

因此存在拐点预算 $B^*$：超过后准确率提升可忽略，纯浪费。

## 四、代码实现

难度路由 + 思考预算控制（示意）：

```python
def serve(question, router, fast, slow, budget_map):
    hard = router.classify(question)           # 0~1 难度
    if hard < 0.3:
        return fast.generate(question)          # 简单题快答
    budget = budget_map.get(router.topic(question), 4096)
    return slow.generate(question, max_think_tokens=budget)

# 监控：记录每次思考 token 数，超阈值告警并降级
```

|------|--------|------|--------|
| 全用快模型 | 低（难题） | 低 | 低 |
| 全用推理模型 | 高 | 高 | 低 |
| 难度路由 | 高 | 中 | 中 |
| 蒸馏小推理模型 | 中高 | 低 | 中 |

## 六、常见误区

- **推理模型「更聪明所以全能」**：在创意、闲聊、简单抽取上它更贵且未必更好，纯属浪费。
- **不设预算**：放任长思考会拖垮延迟与成本，且难任务上超过拐点后无意义。
- **忽视 KV cache**：长思维链使显存峰值更高，需配套 PagedAttention 等优化，否则 OOM。
- **路由永不误判**：路由本身有误差，误把难题判简单会直接错答，需留兜底重试。
- **只看单价**：还应看「每正确回答的成本」，高单价高命中可能更省。

## 九、演进与趋势

成本优化走向「自适应推理」：模型自己决定思考多深，或用一个 tiny router 实时分流；配合投机解码、KV cache 复用、以及端侧蒸馏小模型，把推理模型的单请求成本压到接近快模型。云厂商也在按 token 分「思考/答案」计费，促使用户精细控制预算。更前沿的是「推理预算调度器」，在延迟-准确率 Pareto 前沿上自动寻优，按 SLA 动态分配算力。

## 十、小结

推理模型成本主要来自长思维链的额外 token，落地应「按需启用」：用难度路由把简单题留给快模型，用思考预算约束难题开销，用蒸馏小模型降单位成本。决策核心是任务价值是否值得多花的算力——在难分布上值得，在通用场景则不划算。监控每正确回答成本，才能找到真正省钱的工作点。
