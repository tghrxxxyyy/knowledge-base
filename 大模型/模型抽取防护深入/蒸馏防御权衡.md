# 蒸馏防御权衡

> 对应 mlabonne/llm-course 模型部署章、开源模型许可实践，与 HuggingFace 模型卡（model card）合规说明。

## 一、背景与挑战

「模型抽取」在技术上指用 API 输出训练替代模型，但在商业上它常与「蒸馏」「微调」「再训练」纠缠不清。一个微妙的现实是：**同样的行为，在开放权重模型上可能是被鼓励的生态使用，在闭源 API 上却是对条款的违反**。防御策略不能一刀切。

更深层的矛盾在于商业模式：完全开放的模型靠生态与社区壮大，过度防御会窒息采用；闭源 API 靠能力稀缺盈利，不防御则价值被稀释。因此防御强度必须与**模型的开放程度、商业目标、风险敞口**逐一匹配，而非追求「最强防御」。

## 二、核心原理

可按「开放度」把模型分为三档，对应不同防御姿态：

- **开放权重（open weights）**：权重公开下载，理论上无法阻止他人用其输出或权重做蒸馏。此时防御重心不在「防」，而在「许可约束 + 生态激励」，例如用社区许可约定禁止超大规模商业蒸馏，并以品牌与生态留住用户。
- **受限 API（gated API）**：提供推理服务但不开放权重，是典型的抽取风险敞口，需限流、监控、扰动、水印全套防御。
- **混合模式**：开放小模型、闭源大模型，或研究用途免费、商业用途受限，防御随档位分级。

权衡的核心是：防御有成本（体验、算力、复杂度），应投入到风险最高、收益最大的环节，而非均匀铺开。

## 三、形式化与数学基础（含 LaTeX）

设模型开放度为 $o\in[0,1]$（$0$ 为完全闭源 API，$1$ 为完全开放权重），风险敞口为 $E(o)\approx 1-o$，防御收益为 $R(d,o)=d\cdot E(o)$，其中 $d$ 为防御投入。同时防御带来体验/成本损失 $C(d)$。

净收益

$$
U(d,o)=d\,(1-o)-C(d)
$$

对 $d$ 求最优，闭源（$o\to0$）时 $d^*$ 较大，开放（$o\to1$）时 $d^*\to0$。这说明**防御投入应随开放度单调递增地下降**，与直觉一致：越封闭越该重防，越开放越该靠生态。

## 四、代码实现（围栏配平）

```python
def defense_policy(model):
    if model.open_weights:
        # 开放权重：靠许可与生态，不堆技术防御
        return {"watermark": False, "rate_limit": "light", "tos": "license"}
    # 闭源 API：全套防御
    return {"watermark": True, "rate_limit": "strict",
            "perturb": True, "monitor": True}

def allowed_usage(license, commercial):
    # 依许可判定蒸馏是否合规，具体条款以官方最新文档为准
    return license.allows_distill and (not commercial or license.allows_commercial)
```

## 五、与其他技术对比

- 与「统一强防御」相比：分层策略避免对开放模型过度投入、对闭源模型投入不足。
- 与「无防御开源」相比：许可约束提供最低限度的边界与追责依据。
- 与纯法律手段相比：技术防御对闭源 API 更直接有效。

## 六、常见误区

- 「开源模型也要防抽取」——权重已公开，技术防御意义有限，应转向许可与生态。
- 「闭源就绝对安全」——API 仍可被查询盗用，必须技术防御。
- 「防御越强越好」——过度防御损害体验与采用，需按风险匹配。
- 「许可能管一切」——许可依赖司法执行力，技术取证仍是兜底。

## 七、与开源书·权威来源对应

- mlabonne/llm-course 在部署与蒸馏章节讨论开放与闭源的取舍。
- HuggingFace model card 模板要求声明许可、用途限制与衍生使用条款。
- 主流开源许可（Apache-2.0、MIT、社区许可等）对再训练/蒸馏的规定各异，具体以官方最新文档为准。
- OWASP LLM Top 10 对 API 暴露面风险有相关指引。

## 八、面试题

- 问：开放与闭源防抽取策略差异？答：开放权重靠许可与生态，闭源 API 靠监控/限流/扰动/水印全套技术防御。
- 问：如何决定防御投入？答：依开放度与风险敞口匹配，闭源重投入、开放轻投入。
- 问：为何开源不宜堆技术防御？答：权重已公开，技术防不住，反而徒增成本伤生态。
- 问：混合模式如何防？答：按档位分级，闭源部分强防、开放部分靠许可与监控。

## 九、演进与趋势

许可本身在演化：「可商用但限制超大规模蒸馏」「按调用量分级」等条款精细化；同时「开源即透明、闭源即防护」的二元正在被混合许可模糊，防御策略随之动态化。合规自动化（调用即校验许可）也在落地。

### 关键要点速查

- 防御投入应随模型开放度反向匹配：越封闭越重防，越开放越靠生态与许可。
- 开放权重模型技术防御意义有限，重心应放在许可约束与社区治理。
- 闭源 API 是典型敞口，需监控、限流、扰动、水印全套防御。
- 分层条款让防护与商业模式对齐，避免一刀切伤生态或留敞口。
- 防御有成本（体验、算力、复杂度），应投到风险敞口最大的环节。
- 混合模式（开放小模型/闭源大模型）需按档位分别设定防御强度。
- 许可依赖司法执行力，技术取证仍是兜底，二者不可互相替代。
- 开源许可对蒸馏的规定各异，具体条款以官方最新文档为准。
- 防御有效性应可度量：用抽取评测验证投入产出，而非凭感觉加防。
- 对闭源 API 可引入「调用信誉分」，高信誉用户放宽、低信誉收紧。

## 十、小结

蒸馏防御的本质是权衡：防御投入应随模型开放度反向匹配，闭源靠技术、开源靠许可与生态，避免无差别过度防御，把资源投到风险敞口最大的环节。
