# 函数调用与工具提示

> 对应 OpenAI Function Calling / Tool Calling 文档与 dair-ai/Prompt-Engineering-Guide「Function Calling」。

## 一、背景与挑战

仅靠自然语言，模型无法可靠地触发确定性的外部操作（查数据库、调 API、算数、发消息）。早期做法是把工具说明写进 prompt，让模型「自由输出 JSON」，但格式不稳定、易错。函数调用（Function/Tool Calling）把可用工具的**结构化 schema（名称、参数、描述）**作为一等公民传给模型，由模型输出**严格符合 schema 的调用请求**，外部执行后把结果回填，模型据此继续生成。它是现代 Agent 工具使用的基础设施。

## 二、核心原理

函数调用是「提示工程 + 协议」的结合：

1. **声明工具**：把每个工具的 JSON Schema（名、描述、参数类型/必填）随请求传给模型（不进普通文本，而走专用 `tools` 字段）；
2. **模型决策**：模型判断是否需要调用及调用哪个、参数如何填，输出结构化 `tool_calls`（而非自然语言）；
3. **外部执行**：宿主程序解析调用、执行函数、拿到结果；
4. **回填续生成**：把 `{role: tool, content: 结果}` 追加回对话，模型基于结果给出最终自然语言回答或继续调用。

与纯文本提示的本质区别：参数被**结构化约束**，几乎不再出现格式解析失败。

## 三、形式化与数学基础

工具集 $\mathcal F=\{f_j\}_{j}$，每个 $f_j$ 有 schema 定义参数空间 $\Theta_j$。模型在上下文 $c$ 下输出调用：

$$a = (j^*, \theta^*),\quad j^*\in\{1..|\mathcal F|\}\cup\{\text{none}\},\ \theta^*\in\Theta_{j^*}.$$

由 schema 保证 $\theta^*$ 的类型/必填合法（模型端或解析端校验）。执行得观察 $o=f_{j^*}(\theta^*)$，更新上下文 $c' = c \oplus (a, o)$，再迭代直至 `finish`。这把 Agent 决策形式化为受 schema 约束的动作选择，等价于带工具的动作空间强化学习。

## 四、代码实现

OpenAI 风格声明与调用（示意，API 以官方最新文档为准）：

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

tools = [{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询城市某日天气",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {"type": "string"},
        "date": {"type": "string", "format": "date"}},
      "required": ["city", "date"]}}}]

r = client.chat.completions.create(
    model="meta-llama/Llama-2-7b-chat-hf",
    messages=[{"role":"user","content":"北京 2026-09-01 天气如何？"}],
    tools=tools)
call = r.choices[0].message.tool_calls[0]     # 结构化调用请求
print(call.function.name, call.function.arguments)
# -> get_weather {"city":"北京","date":"2026-09-01"}
```

## 五、与其他方式对比

| 方式 | 格式稳定性 | 实现 | 适用 |
|------|-----------|------|------|
| 文本提示要 JSON | 低（易错） | 易 | 玩具 |
| Function Calling | 高（schema 约束） | 中 | 生产 Agent |
| ReAct 文本轨迹 | 中 | 中 | 需推理+工具 |
| MCP 协议 | 高（标准化） | 中高 | 多工具生态 |

## 六、常见误区

- **以为描述随便写**：模型靠 `description` 选工具与填参，含糊描述导致选错/参数错。
- **不校验参数**：模型仍可能越界，执行前须按 schema 校验（类型、范围、必填）。
- **忽略失败重试**：工具调用可能超时/报错，需把错误回填让模型换策略。
- **把 tool 结果直接信任**：外部数据需清洗，避免污染后续推理。

## 九、演进与趋势

函数调用走向标准化与生态化：**MCP（Model Context Protocol）**统一工具/数据源接入；**并行工具调用**（一次返回多个调用）；**多轮 agentic 循环**；以及把函数调用与 **RAG、代码执行、浏览器** 组合成通用 Agent。模型侧也在强化「该不该调用、调用哪个」的判断力。

## 十、小结

函数调用（Tool Calling）把工具的 JSON Schema 作为结构化输入传给模型，使模型输出严格合规的调用请求、由外部执行并回填结果，从而可靠地连接大模型与现实操作；相比纯文本要 JSON，schema 约束大幅提升了格式稳定性，是现代 LLM Agent 工具使用的基础机制。
