# 编译与部署流程

> 对应 NVIDIA TensorRT-LLM 官方「Build and Deploy」文档与工程实践。

## 一、背景与挑战

与 vLLM 这类「即时（JIT）执行」框架不同，TensorRT-LLM 走**离线编译（AOT build）**路线：先把模型权重转换成 TRT 专用格式、再编译出高度优化的**引擎（engine）**文件，最后用服务封装部署。这种「编译一次、跑多次」的模式带来极致性能，代价是流程更长、引擎与具体 GPU 架构强绑定，换硬件需重建。

## 二、核心原理

典型四步流程：

1. **下载/准备模型**：从 HF 等获取权重（如 LLaMA、Qwen、Mistral）。
2. **转换检查点**：用 `convert_checkpoint` 把通用权重转成 TRT-LLM 内部格式（含并行切分、量化预处理）。
3. **构建引擎**：`trtllm-build` 选定张量并行度、量化（FP8/INT4）、插件（FlashAttention 等），经图优化+核融合生成 `.engine`。
4. **部署服务**：用 `trtllm-serve`（OpenAI 兼容）或 Triton Inference Server 承载线上流量。

引擎是序列化后的优化计算图 + 权重，加载即用，省去运行时编译开销。

## 三、形式化与数学基础

引擎性能来自编译期对计算的固定化。设模型参数量 $P$，张量并行度 $tp$，则每卡权重：

$$M_w^{\text{card}} = \frac{P \cdot s_{\text{bytes}}}{tp},$$

构建时需保证 $M_w^{\text{card}} + M_{\text{kv}} \le u \cdot M_{\text{gpu}}$。引擎内 GEMM 经分块调度匹配 GPU 的 SM/ Tensor Core 形状，层数、序列长、批上限在构建期部分固定（或设上限），运行时在此范围内高效执行。

## 四、代码实现

转换检查点（以 LLaMA 为例，参数以官方为准）：

```bash
python convert_checkpoint.py \
  --model_dir ./llama-7b \
  --output_dir ./ckpt_trt \
  --dtype float16 --tp_size 1
```

构建引擎：

```bash
trtllm-build --checkpoint_dir ./ckpt_trt \
  --output_dir ./engine \
  --gemm_plugin float16 \
  --tp_size 1
```

启动服务（OpenAI 兼容）：

```bash
trtllm-serve --engine_dir ./engine \
  --host 0.0.0.0 --port 8000
```

## 五、与其他部署方式对比

| 方式 | 编译 | 硬件绑定 | 上手难度 |
|------|------|---------|---------|
| vLLM（JIT） | 否 | 弱 | 低 |
| TRT-LLM（AOT） | 是 | 强 | 中 |
| ONNX+TRT | 是 | 强 | 高 |

## 六、常见误区

- **以为引擎可跨 GPU 架构复用**：引擎内含针对具体 SM 架构（如 sm_90 Hopper）优化的 kernel，换架构（如 A100↔H100）须重建。
- **构建一次用到老**：驱动/CUDA/TRT-LLM 大版本升级后引擎可能不兼容，需重建。
- **忽略转换步**：直接 build 未转换权重会失败，必须先 `convert_checkpoint`。
- **构建参数与部署环境不一致**：构建时设的 `--tp_size`、精度须与部署卡数/驱动匹配，否则加载失败。
- **不固化版本**：TRT-LLM、TensorRT、CUDA 驱动三者版本耦合，升级任一项建议重建并回归测试。

## 九、演进与趋势

TRT-LLM 引入 **LLM API（Python）** 降低上手门槛，支持运行时更灵活的形状；与 Triton 的「多模型、动态批、指标」深度集成；构建缓存与增量编译缩短迭代。跨架构可移植性仍是生态努力方向。

## 十、小结

TRT-LLM 走「转换检查点 → 离线构建引擎 → 服务部署」的 AOT 路线，以编译期优化（核融合、量化、并行）换取极致推理性能；代价是引擎与 GPU 架构强绑定、换硬件须重建，适合追求极限吞吐且硬件固定的生产场景。
