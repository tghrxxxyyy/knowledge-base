# 推理引擎选型

> 对应 vLLM / TensorRT-LLM / SGLang / LMDeploy 等主流推理引擎公开文档与社区基准。

## 一、背景与挑战

开源大模型落地时，面对 vLLM、TensorRT-LLM、SGLang、LMDeploy、llama.cpp 等众多推理引擎，团队常纠结「选哪个」。不同引擎在**性能、易用性、硬件覆盖、定制能力、生态**上各有侧重，没有绝对最优，需结合模型规模、硬件、延迟 SLO、是否需要定制 kernel 与工具链来决策。

## 二、核心原理

选型本质是权衡四个轴：

- **性能上限**：NVIDIA 卡上 TRT-LLM 通常峰值最高（深度核融合+量化），SGLang/vLLM 紧随且迭代快。
- **易用与生态**：vLLM 最易上手、OpenAI 兼容、社区广；SGLang 适合「编程式」复杂推理流。
- **硬件覆盖**：llama.cpp 覆盖 CPU/Metal/各类 GPU；TRT-LLM 聚焦 NVIDIA。
- **定制能力**：需要改 kernel / 接 Triton 生产网关时 TRT-LLM 更强。

## 三、形式化与数学基础

用多目标决策近似：设引擎 $e$ 在吞吐 $T_e$、首延迟 $F_e$、易用 $U_e$、硬件适配 $H_e$ 上打分，综合：

$$\text{Score}(e) = w_T \bar T_e + w_F \bar F_e + w_U \bar U_e + w_H \bar H_e,$$

权重由业务定（如在线服务重 $T,F$，原型验证重 $U$）。注意基准随版本快速变化，应以**当下官方最新文档与自身负载实测**为准。

## 四、代码实现

快速对比验证（vLLM 起服务）：

```bash
python -m vllm.entrypoints.openai.api_server --model <model> --port 8000
```

TRT-LLM 起服务：

```bash
trtllm-serve --engine_dir ./engine --port 8001
```

用同一压测脚本对两端口跑相同 prompts 集合，对比 TTFT/p99 token/s 再决策。

## 五、与其他引擎对比

| 引擎 | 定位 | 优势 | 适用 |
|------|------|------|------|
| vLLM | 通用易用 | 生态广、PagedAttention、OpenAI 兼容 | 大多数场景、快速验证 |
| TRT-LLM | NVIDIA 极致性能 | 核融合/量化/Fast、Triton | 固定硬件、极限吞吐 |
| SGLang | 编程式推理 | RadixAttention 前缀复用 | 复杂提示流、高复用 |
| LMDeploy | 国产友好 | TurboMind 高性能、量化好 | 国内部署、多卡 |
| llama.cpp | 端侧/跨平台 | CPU/GPU/端侧、GGUF | 本地、边缘 |

## 六、常见误区

- **迷信单一基准榜单**：版本迭代快，榜单会过时，须以自身模型+负载实测。
- **为性能牺牲易用导致交付慢**：原型期用 vLLM，规模化再评估 TRT-LLM 更稳妥。
- **忽略硬件**：AMD/Intel 卡上 TRT-LLM 不适用，应看对应后端。
- **只看峰值吞吐**：生产还需考虑显存占用、并发上限、可观测性与运维复杂度，综合才可靠。
- **过早绑定单一引擎**：用抽象封装（统一 OpenAI 接口）降低迁移成本，便于后续 A/B 切换。

## 九、演进与趋势

引擎趋同：vLLM/SGLang 也在做核融合与量化，TRT-LLM 推 Python API 降门槛；**分离式部署**（prefill/decode 拆分）、**多引擎网关**成为大规模方案；国产卡（昇腾、寒武纪）催生对应后端。选型会更看重「可移植 + 可观测 + 易运维」。

## 十、小结

推理引擎选型是性能、易用、硬件、定制的多目标权衡：快速验证用 vLLM，固定 NVIDIA 硬件追求极限吞吐用 TRT-LLM，高前缀复用复杂流用 SGLang，跨平台/端侧用 llama.cpp；最终应以官方最新文档与自身负载实测为准，而非过时榜单。
