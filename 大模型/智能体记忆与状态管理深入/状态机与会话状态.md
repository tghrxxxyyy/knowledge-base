# 状态机与会话状态

> 对应 Yao et al., *ReAct*, ICLR 2023（观测—动作循环）；对话状态跟踪（DST）经典范式，如 MultiWOZ 数据集上的状态跟踪工作。

## 一、背景与挑战

把智能体的一切都塞进自由文本上下文，会导致关键槽位（订单号、金额、确认状态）丢失或被模型改写。
业务流程往往有明确阶段与前置条件，需要显式状态而非让模型「记得」。

## 二、核心原理

- 显式状态对象：把关键槽位与阶段存在程序侧数据结构，模型只读取渲染后的摘要并提出状态变更请求。
- 受限转移：定义状态机的合法转移与前置条件（如未确认不得支付），非法请求被编排层拒绝并回灌原因。
- 幂等与恢复：状态持久化后，会话中断可续跑；重复动作按幂等键去重，避免重复副作用。

## 三、数学形式

状态机为五元组 $M=(S,A,\delta,s_0,F)$，其中转移 $\delta:S\times A\to S$ 只在满足前置谓词 $g(s,a)$ 时定义。

模型输出的动作先经门控 $\mathbb{1}[g(s,a)]$ 过滤，等价于把策略约束在可行集 $A(s)=\{a: g(s,a)\}$ 上。

## 四、代码实现

```python
TRANSITIONS = {("collect", "confirm"): "confirmed",
               ("confirmed", "pay"): "paid"}

def step(state, action, payload):
    key = (state.phase, action)
    if key not in TRANSITIONS:
        return state, f"非法动作 {action}，当前阶段 {state.phase}"
    if action == "pay" and not state.slots.get("amount"):
        return state, "缺少金额槽位，无法支付"
    state.phase = TRANSITIONS[key]; state.slots.update(payload)
    return state, "ok"
```

## 五、与其他对比

- 与纯提示式流程控制：状态机可测试、可回放、可审计；纯提示灵活但不可验证且易被越权指令绕过。
- 与向量记忆：状态是精确结构化事实，记忆是模糊语义回忆，前者做流程控制，后者做个性化与背景补全。

## 六、常见误区

- 让模型自己维护 JSON 状态并每轮重写，累积漂移且无法校验。
- 只在提示里写「未确认不要支付」，把安全约束交给采样概率而非代码。
- 状态不持久化，进程重启或会话切换即丢失，长任务无法续跑。

## 八、面试题

- 为什么关键槽位不能只放在上下文里？答：上下文会被截断、摘要与模型改写，缺乏校验；程序侧状态可校验、可持久化、可审计。
- 状态机与 LLM 如何分工？答：LLM 提出动作与填槽，状态机判定合法性并执行转移，非法请求回灌原因让模型改。

## 九、演进

纯自由对话 → 提示内伪状态 → 显式槽位与状态机 → 持久化与幂等恢复 → 状态驱动的可测试智能体流程。

## 十、小结

会话状态应由代码持有、由状态机约束，模型只负责语义决策，安全约束不能寄托于提示。
