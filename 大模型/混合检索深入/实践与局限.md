# 混合检索实践与局限

> 对应生产落地经验；向量数据库选型与调优实战（文件）衔接。

## 一、背景与挑战

两套索引运维复杂，需权衡收益与成本。

## 二、核心原理

用支持混合的引擎（如 Elasticsearch/Weaviate）或自管两索引；监控各路贡献。

## 三、数学形式

成本 $C = C_{sparse} + C_{dense} + C_{fusion}$；收益 $\Delta Recall$。

## 四、代码实现

```python
# 用现成引擎混合
res = es.search(query={"multi_match":{...}, "knn":{...}})
```

## 五、与其他对比

- 与 长文档切分深入（影响两路质量）衔接。
- 与 查询改写与扩展深入 配合（改写后双路）。

## 六、常见误区

- 过度依赖混合掩盖单路缺陷。
- 两索引未同步更新致不一致。

## 七、与开源书对应

## 八、面试题

- 混合检索代价？答：双索引存储/更新成本+融合开销，需收益覆盖。

## 九、演进

自建双索引 → 引擎内置 → 自适应路由单/双路。

## 十、小结

混合检索收益明确但增运维，宜用现成引擎并监控贡献。
