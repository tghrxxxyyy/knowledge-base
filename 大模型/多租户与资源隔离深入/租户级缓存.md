# 租户级缓存

> 对应 GPTCache 项目与语义缓存（Semantic Cache）多租户实践。

## 一、背景与挑战

LLM 推理昂贵且慢，而真实流量中存在大量相似甚至重复的问题（如「帮我写周报」「解释一下 Transformer」）。缓存命中可省去一次完整推理，显著降本提速。但在多租户场景，缓存若不加区分地共享，租户 A 的提问可能被租户 B 的缓存命中返回，造成隐私泄漏与答案串扰。因此缓存必须与租户边界对齐。

另一挑战是「缓存新鲜度」：知识会更新（如价格、政策），跨租户共享的公共 FAQ 与租户私有的时效数据对 TTL 的要求不同，需要分层 TTL 与失效策略，否则命中率越高、陈旧答案危害越大。同时，语义相似并不等于语义等价——「我们公司退款政策」对两个租户是不同答案，必须靠租户边界区分而非仅靠相似度。

成本视角下，缓存是「用空间换时间、用命中率换钱」：命中率每提升 10 个百分点，推理 GPU 成本可下降接近同比例。但安全视角下，缓存又是攻击面——攻击者可用高频相似查询探测缓存侧信道、或投毒缓存影响其命中结果，因此缓存层也需纳入安全评测，而非仅视为加速组件。设计时应把「租户隔离」「新鲜度」「可审计」作为缓存的三大一等约束。

## 二、核心原理

语义缓存把用户问题做向量化，存入按租户命名空间隔离的向量库；新请求先向量检索历史问答，相似度超过阈值即直接返回缓存答案（命中），否则才走模型。缓存键可包含 `hash(tenant_id + question)` 或显式 namespace。敏感租户可配置「禁用缓存」；跨租户共享需显式策略与授权。还可对缓存做 TTL、命中率统计与计费折减。

实现上需平衡向量检索开销：语义缓存本身要一次向量查询，若命中率不足反而增加延迟。因此常配合精确字符串缓存做「先精确后语义」的两级结构，并异步回填 Embedding，避免缓存路径拖慢主链路。

关键要点：

- 语义缓存把问题向量化，存入按租户命名空间隔离的向量库。
- 命中判定为相似度超过阈值 $\tau$ 即返回缓存答案，省去推理。
- 缓存键应含 tenant_id，敏感租户可配置禁用缓存。
- 两级结构（精确字符串 + 语义）可兼顾命中率与向量检索开销。
- 缓存新鲜度需分层 TTL，公共 FAQ 与私有时效数据策略不同。
- 命中率与答案新鲜度需权衡，且语义相似不等于语义等价。

## 三、形式化与数学基础

定义问题嵌入 $e(q)\in\mathbb{R}^d$，缓存集合 $\mathcal{C}_t$ 属于租户 $t$。命中判定：

$$
\text{hit}(q, t) = \exists\, c\in\mathcal{C}_t:\; \cos(e(q), e(c)) \ge \tau
$$

其中 $\tau$ 为相似度阈值。命中率：

$$
H = \frac{N_{\text{hit}}}{N_{\text{total}}}
$$

成本节省近似 $S \approx H \cdot c_{\text{infer}}$，$c_{\text{infer}}$ 为单次推理成本；折减计费后实际节省为 $S \cdot (1-\delta)$。设语义检索开销 $c_{\text{vec}}$，净节省为 $S - H\cdot c_{\text{vec}}$。

## 四、代码实现

```python
import hashlib

# 租户隔离的语义缓存键
def cache_key(tenant_id, question):
    return hashlib.sha256(f"{tenant_id}::{question}".encode()).hexdigest()

def answer(tenant_id, question, model, sensitive=False):
    if sensitive:                            # 敏感租户禁缓存
        return model.generate(question), "model"
    key = cache_key(tenant_id, question)
    hit = tenant_cache[tenant_id].get(key)   # 仅查本租户命名空间
    if hit:
        return hit, "cache"                  # 命中，零推理
    out = model.generate(question)
    tenant_cache[tenant_id].put(key, out, ttl=3600)
    return out, "model"

# 分层 TTL：公共 FAQ 长、私有短
TTL = {"public": 86400, "private": 600}
```

## 六、常见误区

误区一：缓存提速即可全局共享——跨租户命中即泄漏。误区二：阈值 $\tau$ 设太高——命中率骤降失去意义；太低则答非所问。误区三：缓存永久有效——知识过期会返回陈旧答案。误区四：忽略缓存未命中时的回源压力突增——需限流保护回源。误区五：命中即正确——语义相似不等于语义等价，需业务校验。误区六：语义缓存零开销——向量检索本身有成本。

## 九、演进与趋势

从「精确字符串缓存」到「向量语义缓存」；结合 LLM 重写问题提升命中；把缓存命中纳入计费折减与配额；跨租户授权共享（如公共 FAQ）成为可配置策略，并以分层 TTL 控制新鲜度。缓存与向量库、推理引擎在架构层统一编排，命中与回源形成闭环，并在写入时按租户配额限流。

工程上建议对缓存做可观测：分租户统计命中率、回源率、陈旧命中占比，异常波动（如某租户命中率突降）往往预示注入攻击或后端退化；并把缓存命中纳入配额与计费，使降本与治理同源。当缓存与检索、推理在架构层统一编排，命中与回源形成闭环，多租户降本才真正可持续且安全。

## 十、小结

缓存是降本利器，而租户级隔离是前置条件——以命名空间边界保证命中只发生在本租户域内；辅以分层 TTL、敏感租户禁缓存、回源限流与「精确+语义」两级结构，兼顾安全、速度与新鲜度。
