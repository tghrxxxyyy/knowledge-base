# 数据隔离与隐私

> 对应 OWASP LLM Top 10（LLM06 敏感信息泄露）与向量数据库命名空间隔离实践。

## 一、背景与挑战

多租户 LLM 应用（尤其是 RAG）会读取各租户的私有文档、知识库与对话历史。一旦隔离失效，租户 A 就可能检索或生成出租户 B 的机密，造成数据越界与合规事故。OWASP 将「敏感信息泄露」列为 LLM 应用的十大风险之一（LLM06）。隔离难点在于：数据不仅存于数据库，还流经向量索引、提示拼接、日志、缓存与评测集，任何一环泄漏都会放大为跨租户事故。

更隐蔽的风险是「间接泄露」：模型可能在回答租户 A 时，因训练或检索混入的租户 B 片段而吐出 B 的信息；或缓存命中了其他租户的相似问题而返回错误归属的内容。因此隔离不是「分库」一件事，而是覆盖数据全生命周期的纵深防御工程，且需在合规（GDPR、个人信息保护法）与可用性之间取得平衡。

## 二、核心原理

数据隔离遵循「纵深防御」：存储层按租户命名空间（namespace / schema / 独立集合）物理或逻辑分隔；传输层全程 TLS；检索层在向量库与 SQL 查询中强制注入租户过滤条件（`tenant_id = ?`）；提示拼接层确保上下文只含本租户数据；日志与链路追踪中对 PII（个人可识别信息）脱敏；跨租户共享需显式授权策略。零信任模型下，应默认「无租户上下文即拒绝访问」，把隔离下沉到数据访问层而非依赖业务代码「记得加过滤」。

关键要点：

- 纵深防御覆盖存储/传输/检索/提示/日志/缓存全链路。
- 检索层强制注入 tenant_id 过滤，杜绝跨租户串扰。
- 提示拼接层确保上下文只含本租户数据。
- 日志对 PII 脱敏，跨租户共享需显式授权策略。
- 零信任原则：无租户上下文即拒绝访问。
- 间接泄露（模型吐出他租户信息）同样需评测与审计。

## 三、形式化与数学基础

定义租户上下文 $t\in\mathcal{T}$，数据对象 $d$ 携带标签 $\ell(d)\in\mathcal{T}\cup\{\text{public}\}$。一次检索的合法结果集需满足：

$$
\mathcal{R}(q, t) = \{\, d \in \text{index}(q) \mid \ell(d)=t \;\lor\; \text{grant}(d, t)=\text{true} \,\}
$$

隔离失败率（串扰率）定义为越界返回比例：

$$
\mathcal{L} = \frac{|\{d\in\mathcal{R} \mid \ell(d)\ne t \land \neg\text{grant}\}|}{|\mathcal{R}|}
$$

合规目标为 $\mathcal{L}=0$。此外可定义「间接泄露概率」$\mathcal{P}_{\text{ind}}$ 度量模型吐出他租户信息的条件概率，作为评测项与红线。

## 四、代码实现

```python
# RAG 检索：强制注入租户过滤，杜绝跨租户串扰
def search(tenant_id, query, auth):
    ns = vector_db.namespace(tenant_id)       # 租户独立命名空间
    hits = ns.search(query, top_k=5, filter={"tenant_id": tenant_id})
    return [redact(pii(h.doc), auth) for h in hits]   # 检索 + 脱敏

# 日志脱敏：正则替换邮箱/手机号等 PII
import re
def redact(text, auth):
    if not auth.may_see_pii:
        text = re.sub(r"\b[\w.]+@\w+\.\w+\b", "[EMAIL]", text)
        text = re.sub(r"\b1\d{10}\b", "[PHONE]", text)
    return text

# 零信任拦截：无租户上下文直接拒绝
def guard(req):
    if not req.tenant_id:
        raise Denied("missing tenant context")
```

## 六、常见误区

误区一：只做数据库分库——RAG 的向量索引、缓存、日志同样会泄漏。误区二：靠应用层「记得加过滤」——一旦漏写即越界，应在数据访问层强制注入。误区三：脱敏即匿名——重标识攻击仍可反推个人。误区四：测试数据混入生产租户域——评测集需用合成数据避免真实 PII。误区五：加密等于隔离——加密防外部窃取，不防同库内越权读。误区六：间接泄露可忽略——模型吐字不可控，需输出侧审计。

补充误区：

- 误区六：加密即隔离——加密防外部窃取，不防同库内越权读。
- 误区七：间接泄露可忽略——模型吐字不可控，需输出侧审计与拦截。
- 误区八：测试数据无妨——生产租户域混测同样违反合规。
- 误区九：隔离只防泄露——跨租户串扰还会污染检索与生成质量。

## 九、演进与趋势

从「共享索引 + 应用过滤」走向「向量库原生租户命名空间 + 行级安全策略」；差分隐私与同态加密开始用于极度敏感场景；合成数据用于评测以避免真实 PII 进入红队集。SDK 侧把 tenant 上下文做成一等公民，使过滤与脱敏在数据访问层默认生效，而非散落在业务代码；输出侧增加租户归属审计，拦截间接泄露。

落地时建议以「默认拒绝 + 最小权限」为原则：任何跨租户读取都需显式 grant，所有访问留痕可供租户审计；定期做隔离渗透测试（尝试越权检索他租户文档）并度量 $\mathcal{L}$，把结果纳入发布门禁。多区域部署时还需注意数据驻留（data residency）——某些租户数据依法不得离开特定地理边界，隔离策略必须与合规策略联动。

## 十、小结

数据隔离是隐私合规的底线，必须以纵深防御覆盖存储、检索、提示、日志与缓存全链路，并以 $\mathcal{L}=0$ 为硬目标持续度量；间接泄露与缓存串扰同样需纳入评测视野，零信任是落地抓手。
