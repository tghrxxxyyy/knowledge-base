# SLA 与可用性

> 对应 Google SRE Book（Site Reliability Engineering）与 Kubernetes 多副本高可用实践。

## 一、背景与挑战

企业客户在采购 LLM 服务时，会要求明确的 SLA（服务等级协议），例如「99.9% 月度可用性」「P95 延迟 < 800ms」。没有量化 SLA，故障无法界定责任，也无法驱动工程改进。LLM 服务的可用性尤其难保障：依赖 GPU、权重加载、外部检索（RAG）与多个微服务，任一环节抖动都会传导到终端延迟。

更棘手的是「可用性」在 LLM 场景会被重新定义：一次响应「状态码 200」不代表「结果可用」——可能返回了 refusal、退化为低质量答案或触发了降级。因此 SLA 不能只看 HTTP 层成功率，还要结合业务层质量指标，这比传统 Web 服务复杂。

对客户而言，SLA 还是「信任凭证」：能否签下大客户，常取决于是否提供有赔付条款的 SLA（未达标返还费用或抵扣额度）。因此 SLA 不只是技术指标，更是商务与法务文件，工程团队需为其中的承诺留足余量——通常对内 SLO 严于对外 SLA（如对外 99.9%、对内 99.95%），用缓冲吸收偶发抖动，避免触发赔付。

## 二、核心原理

SLA 由更细的 SLO（服务等级目标）支撑，如可用率、延迟分位、错误率。保障手段是「冗余 + 健康检查 + 故障转移 + 降级」：多副本消除单点；负载均衡做健康检查与流量切换；当主区域异常时切到备用；极端情况下用小模型或缓存兜底（降级）保核心可用。错误预算（error budget）用于权衡发布速度与稳定性——消耗过快则冻结发布。

具体落地时，需在接入层、推理层、依赖层分别设置可用性目标并相乘得到端到端 SLA：若网关 99.95%、推理 99.9%、RAG 检索 99.5%，则链路可用性约为三者之积（约 99.35%），提示单点高可用不足以撑起整体 SLA，必须逐层治理。

关键要点：

- SLA 由更细的 SLO 支撑：可用率、延迟分位、错误率。
- 保障手段是「冗余 + 健康检查 + 故障转移 + 降级」。
- 错误预算（error budget）权衡发布速度与稳定性，消耗过快冻结发布。
- 端到端 SLA 需逐层治理：网关×推理×RAG 可用性相乘。
- 业务可用性需叠加质量门，避免「200 但不可用」假成功。
- 对内 SLO 应严于对外 SLA，用缓冲吸收抖动避免赔付。

## 三、形式化与数学基础

可用性定义为成功请求占比在时间窗内的积分：

$$
A = \frac{1}{T}\int_0^T \mathbb{1}[\text{healthy}(t)]\,dt
$$

99.9% 对应月度不可用约 43 分钟，99.95% 约 22 分钟。错误预算：

$$
B = 1 - \text{SLO}
$$

当消耗过快则冻结发布。延迟 SLO 常用分位：

$$
\Pr(L \le L_{95}) \ge 0.95
$$

业务可用性还需叠加质量门：令 $q(x)$ 为输出质量，则有效可用 $\tilde{A} = A \cdot \Pr(q \ge q_{\min})$。

## 四、代码实现

```python
# 主备切换与降级（示意）
def handle(req):
    if not health_check(primary):
        switch_to(standby)                  # 故障转移
    try:
        return primary.generate(req)
    except OverloadError:
        return small_model_fallback(req)    # 降级兜底

# 错误预算监测
def error_budget_ok(errors, total, slo=0.999):
    return (total - errors) / total >= slo

# 业务质量门（防止 200 但不可用）
def usable(resp):
    return resp.status == 200 and not resp.refused and resp.quality >= 0.6
```

## 六、常见误区

误区一：SLA 只写不测——需定期混沌演练验证可达。误区二：只看平均延迟——P95/P99 才反映长尾体验。误区三：高可用等于堆副本——缺乏健康检查与转移仍会雪崩。误区四：忽视依赖项（RAG、网关）的可用性叠加——链路可用性随环节数指数下降。误区五：200 即成功——需业务质量门把关。

## 九、演进与趋势

从「多副本 + 健康检查」走向「多区域主动-被动/主动-主动」；SLO 被纳入产品契约与计费赔付；AI 驱动的容量预测与自动故障自愈逐步落地。质量 SLO（输出可用性）开始与延迟/错误率 SLO 并列，形成多维服务等级目标。

## 十、小结

SLA 是企业落地 LLM 服务的门槛，需以 SLO、冗余、故障转移与降级共同支撑，并用错误预算持续治理稳定性；同时把业务质量纳入可用性定义，避免「假成功」。
