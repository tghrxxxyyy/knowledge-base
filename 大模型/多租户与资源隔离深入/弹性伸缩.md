# 弹性伸缩

> 对应 Kubernetes HPA 官方文档与 vLLM 动态批处理/扩缩容实践。

## 一、背景与挑战

LLM 推理流量往往呈现明显峰谷：白天高、夜间低，活动期间突发。若按峰值固定部署会浪费大量 GPU 成本，按谷值部署则高峰排队甚至超时。弹性伸缩的目标是在保障延迟 SLA 的前提下，让副本数随负载自动增减，使成本随实际用量走。难点在于 LLM 模型权重大、加载慢（冷启动常以分钟计），盲目缩容又会中断在途请求。

与无状态 Web 服务不同，LLM 推理的有状态性更强：KV cache、连续批处理的在途 batch、已加载的大模型权重都让「扩得快、缩得稳」成为工程难题。若把弹性伸缩简单套用 HPA 的 CPU 指标，会得到完全失灵的策略——因为瓶颈常在显存与带宽而非 CPU。此外，突发流量下「扩容速度跟不上到达速率」会造成瞬时雪崩，需要在容量规划上预留缓冲。

## 二、核心原理

弹性伸缩以「指标驱动」为核心：采集队列长度、在途请求数、P95 延迟、GPU 利用率等指标，与阈值比较后由控制器调增/调减副本。Kubernetes HPA 基于 CPU/自定义指标做水平扩缩；推理层常结合 vLLM 的连续批处理与动态最大 batch。为降低冷启动代价，可预置常驻小池、模型权重预热或使用可秒级拉起的轻量引擎；缩容采用优雅退出（drain），先停止接收新请求、等存量完成再回收。

指标选择直接决定策略成败：队列长度反映积压、在途请求数反映负载、P95 延迟反映体验、GPU 利用率反映饱和。理想做法是多指标融合——以队列长度作为主扩缩信号、P95 作为质量护栏，避免单一指标误判。

关键要点：

- 指标驱动：队列长度/在途/P95/GPU 利用率触发扩缩。
- HPA 基于 CPU/自定义指标，推理层结合连续批处理。
- 冷启动代价高，需常驻小池或权重预热降低不可用窗口。
- 缩容须优雅退出（drain），排空在途请求再回收。
- 多指标融合（队列为主、P95 为护栏）避免单一指标误判。
- 扩容步长需受限，防止一次性扩满击穿数据库等共享依赖。

## 三、形式化与数学基础

设当前副本数 $n$，单副本稳定吞吐为 $\mu$，目标队列长度阈值为 $H$、安全下界为 $L$。触发器：

$$
n \leftarrow \begin{cases}
\min(n+1, n_{\max}) & Q > H \\
\max(n-1, n_{\min}) & Q < L \\
n & \text{otherwise}
\end{cases}
$$

容量需求与延迟约束满足 $\mu\cdot n \ge \lambda$（$\lambda$ 为到达率）。冷却窗口 $T_c$ 防止抖动：

$$
\Delta t_{\text{scale}} \ge T_c
$$

冷启动惩罚 $C_{\text{cold}}$（模型加载耗时）应被纳入扩缩决策，避免「刚扩容又被缩容」的抖动；目标副本数至少为 $\lceil \lambda/\mu \rceil + \text{headroom}$。

## 四、代码实现

```python
# 简单基于队列长度的弹性决策（示意）
def decide(current, queue_len, H=64, L=8, n_min=1, n_max=16):
    if queue_len > H and current < n_max:
        return current + 1                 # 扩容
    if queue_len < L and current > n_min:
        return current - 1                 # 缩容（需优雅退出）
    return current

# 优雅退出：停止接新请求，排空存量
def drain(worker):
    worker.accept_new = False
    while worker.inflight > 0:
        sleep(0.1)
    worker.shutdown()

# 自定义指标暴露给 HPA（如 queue 长度）
def export_metrics():
    return {"llm_queue_len": global_queue.size(), "p95_ms": latency.p95()}

# 扩容预算：避免一次性扩太多击穿其他资源
def bounded_scale(target, current, step=2):
    diff = target - current
    return current + max(-step, min(step, diff))
```

## 五、与其他技术对比

| 策略 | 成本 | 稳定性 | 复杂度 | 冷启动敏感 |
|------|------|--------|--------|------------|
| 固定容量 | 高 | 高 | 低 | 否 |
| 手动扩缩 | 中 | 中 | 中 | 中 |
| 指标自动弹性 | 低-中 | 中（需冷却） | 高 | 高 |
| 预测式弹性 | 低 | 高 | 很高 | 低 |

## 六、常见误区

误区一：缩容即杀进程——会丢弃在途请求导致客户端报错，必须 drain。误区二：只按 CPU 扩缩——LLM 瓶颈常在显存/带宽，CPU 利用率不敏感。误区三：阈值无冷却——指标抖动引发副本频繁震荡。误区四：忽视冷启动——扩容后长时间不可用，反而拉低 SLA。误区五：用平均延迟决策——长尾（P95/P99）才是扩容触发点。误区六：一次性扩满——可能击穿数据库连接池等共享依赖。

## 七、与开源书·权威来源对应

## 九、演进与趋势

从阈值式 HPA 走向「预测式弹性」（基于历史与时间序列提前扩容）；Serverless GPU（如 KServe、Modal）按请求计费、自动缩到零；KV cache 复用与模型分片使副本启动更快。推理引擎开始把「部分权重常驻 + 按需激活」作为弹性前提，进一步压缩冷启动窗口；容量预测与自动故障自愈联动，形成闭环弹性。

## 十、小结

弹性伸缩让 GPU 成本随流量走，但 LLM 的大权重与长冷启动要求指标选择（队列/延迟而非 CPU）、冷却窗口、扩容步长与优雅退出协同设计，并以预测式弹性进一步平滑峰谷。
