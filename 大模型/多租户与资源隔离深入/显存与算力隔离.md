# 显存与算力隔离

> 对应 NVIDIA MIG 官方文档与 vLLM 多租户部署实践。

## 一、背景与挑战

在共享 GPU 集群中，多个租户（团队、客户、业务线）的请求会竞争同一张物理卡的显存与算力。当某个租户突然提交大批量或长上下文推理时，可能占满显存导致他人 OOM，或长期占据 SM 使他人排队延迟飙升，这就是「吵闹的邻居（noisy neighbor）」问题。对 SaaS 化 LLM 服务而言，既要提高硬件利用率、摊薄成本，又必须保证每个租户获得可预期的服务质量，因此显存与算力隔离是平台层不可回避的底座能力。

缺乏隔离还会导致计费失真、故障域扩大与合规风险：一个租户的异常请求可能拖垮整卡，使所有租户 SLA 同时违约；而 GPU 成本高昂，又不能简单地「一租户一卡」。真正的挑战在于，GPU 的资源（显存、算力、L2 缓存、显存带宽、NVLink）是高度耦合的——单纯限制算力无法阻止显存挤占，单纯限制显存也无法阻止带宽争抢，需要分层、分强度的隔离组合。

从经济视角，隔离粒度直接决定 GPU 利用率与成本：切得越细、共享越多，单租户成本越低，但隔离越弱、故障域越大。平台需要在「每卡服务更多租户」与「单租户故障不波及他人」之间做连续权衡，而非二选一。MIG 适合强隔离需求，MPS 与软配额适合成本优先场景，混合编排才能在不同租户间取得帕累托最优。

## 二、核心原理

NVIDIA 提供两套隔离手段：其一是 MIG（Multi-Instance GPU），在 A100/H100 等架构上把一张卡在硬件层面切成多个独立实例，每个实例拥有专属的显存、SM、L2 缓存切片与带宽配额，实例之间物理隔离、互不干扰；其二是 MPS（Multi-Process Service），让多个进程在统一上下文中共享 GPU，通过上下文配额限制单个客户端的算力占比，但显存仍是共享的，隔离强度弱于 MIG。

在调度层，平台用配额（quota）与抢占（preemption）约束每个租户的可并发请求数与最大 batch，推理引擎（如 vLLM、TGI）按租户做队列隔离与令牌桶限流。软隔离依赖调度策略，硬隔离依赖 MIG，实践中常按租户等级混合使用。以 vLLM 为例，其 PagedAttention 本身会复用显存块，多租户共享时需在调度器层做 per-tenant 配额，否则一个租户的长序列会占满 KV cache 块池，饿死他人。

关键要点：

- MIG 硬件切片：专属显存/SM/L2/带宽，实例间物理隔离。
- MPS 共享上下文，显存仍共享，隔离弱于 MIG。
- 调度层用配额与抢占约束并发与最大 batch。
- 推理引擎按租户做队列隔离与令牌桶限流。
- KV cache 配额防单租户占满块池饿死他人。
- 软隔离靠调度，硬隔离靠 MIG，按等级混合使用。

## 三、形式化与数学基础

设 GPU 总算力为 $C$，租户 $i$ 被分配的保证份额为 $\phi_i$，且 $\sum_i \phi_i \le 1$。在时间窗 $T$ 内，租户 $i$ 实际获得算力 $c_i(T)$ 应被下界约束：

$$
c_i(T) \;\ge\; \phi_i \cdot C \cdot (1-\epsilon), \quad \epsilon \text{ 为调度抖动}
$$

MIG 的硬隔离等价于对显存容量 $M$ 做切片 $M_i$，并保证 $\forall i\ne j,\; \text{addr}(M_i)\cap \text{addr}(M_j)=\varnothing$。隔离度的度量可用「跨租户干扰率」：

$$
\mathcal{I} = 1 - \frac{\mathbb{E}[L_{\text{shared}}]}{\mathbb{E}[L_{\text{isolated}}]}
$$

其中 $L$ 为单租户延迟；$\mathcal{I}$ 越接近 0 表示隔离越彻底。带宽隔离类似，定义 $\mathcal{I}_{bw}$ 以显存带宽争抢为对象。

## 四、代码实现

```python
from threading import Semaphore

# 按租户等级分配并发上限（软隔离）
quota = {"free": 2, "pro": 8, "enterprise": 32}
sem = {t: Semaphore(q) for t, q in quota.items()}

def infer(tenant, req):
    sem[tenant].acquire()
    try:
        return engine.generate(req)          # 调用推理引擎
    finally:
        sem[tenant].release()

# 硬隔离：把请求路由到对应 MIG 实例
MIG_PROFILE = {"enterprise": "MIG-1g.10gb", "pro": "MIG-1g.10gb", "free": "MIG-1g.5gb"}

def route(tenant):
    prof = MIG_PROFILE[tenant]
    return mig_device_for(prof)              # 返回该 MIG slice 的 handle

# KV cache 配额：限制单租户可占用块数，防饿死他人
def admit(tenant, need_blocks, kv_pool):
    if kv_pool.used(tenant) + need_blocks > kv_pool.cap(tenant):
        raise AdmissionRejected(tenant)
    return kv_pool.alloc(tenant, need_blocks)
```

## 五、与其他技术对比

| 方案 | 隔离强度 | 利用率 | 故障域 | 适用场景 |
|------|----------|--------|--------|----------|
| 时间片轮转 | 弱 | 高 | 共享 | 非生产、纯成本优先 |
| MPS 共享上下文 | 中 | 高 | 共享 | 同信任域多进程 |
| MIG 硬件切片 | 强 | 中 | 独立 | 多租户 SaaS、合规 |
| 独立物理卡 | 最强 | 低 | 独立 | 金融/政务专属 |

MIG 与 MPS 还可叠加：先用 MIG 切出若干实例，每个实例内再用 MPS 细分层级，兼顾隔离与密度。

## 六、常见误区

误区一：软限制（配额）足够安全——恶意或异常租户可借慢速涨包击穿限额，必须配合硬隔离兜底。误区二：MIG 越多越好——切片过小会限制单租户可跑的模型规模（如 7B 模型需至少 1g.10gb），且管理开销上升。误区三：隔离只管算力——显存碎片与 KV cache 争抢同样致命，需 per-tenant 配额。误区四：抢占无代价——频繁抢占会引入上下文切换与冷启动开销，应在租户等级上设最小保证。误区五：隔离不影响吞吐——MIG 切片会降低单实例可聚合的批大小，峰值利用率下降。

## 九、演进与趋势

从早期「整卡独享」到「时间片共享」，再到 A100 起的 MIG 细粒度硬件切片；云厂商进一步推出按秒计费的 MIG 实例与 GPU 虚拟化（如 MIG + vGPU）。推理引擎正把租户级配额、抢占与连续批处理原生结合，隔离粒度从「卡」走向「请求/上下文」。同时，以 GPU 虚拟化与可抢占调度为代表的技术，让「强隔离 + 高利用率」不再二选一。

## 十、小结

显存与算力隔离是 LLM 平台多租户化的基石：MIG 提供硬件级强隔离，MPS 与调度配额提供灵活软隔离，KV cache 配额补齐显存侧短板。软硬结合、分等级组合，方能在利用率与公平性之间取得平衡。
