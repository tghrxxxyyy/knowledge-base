# 多租户架构

> 对应 Newman《Building Microservices》多租户章与 LiteLLM 多租户路由实践。

## 一、背景与挑战

SaaS 化 LLM 平台需要用一个底座服务众多客户（企业租户、内部团队、个人开发者）。核心矛盾是：共享能极大摊薄 GPU 与运维成本，但会带来数据串扰、资源争抢与合规风险；隔离能保安全，却抬高成本。如何按租户等级在「成本」与「隔离强度」之间权衡，是多租户架构设计的根本命题。

另一个常被忽视的挑战是「 noisy neighbor 的二阶效应」：即便逻辑隔离正确，共享推理引擎的 KV cache、批处理调度仍会互相影响尾延迟。因此架构不仅要回答「数据在哪」，还要回答「算力与延迟预算如何分配」，这两者在平台层需要统一治理。

从组织视角看，隔离策略往往由「合规等级 × 付费等级」共同决定：高合规（金融、医疗）即便付费低也倾向独占或命名空间隔离；低合规高付费可走共享池以降本。平台应把这一映射做成可配置策略，而非硬编码在路由逻辑里，以便随业务与法规变化动态调整，避免每次调整都改代码。

## 二、核心原理

多租户架构沿「隔离梯度」分布：最弱的是纯逻辑隔离（同一进程/库，仅靠 `tenant_id` + 配额区分）；中等是命名空间/集合级隔离；最强是独立实例或独立集群（物理隔离）。平台通常通过路由层识别租户、查表得到其等级与归属资源池，把请求导向共享池或独占池。共享推理用配额、队列与限流防串扰，敏感租户（金融、政务）走独立部署并附加专属密钥与审计。

关键要点：

- 隔离梯度：逻辑隔离 < 命名空间 < 独立实例/集群。
- 路由层识别租户并查表得到等级与资源池归属。
- 共享推理用配额、队列、限流防串扰。
- 敏感租户走独立部署并附加专属密钥与审计。
- 租户身份需贯穿全链路，丢失则下游隔离失效。
- 隔离策略由「合规×付费」共同决定，应可配置而非硬编码。

## 三、形式化与数学基础

设租户等级 $g\in\{\text{shared, namespace, dedicated}\}$，成本函数 $C(g)$ 与隔离度 $\mathcal{S}(g)$ 满足单调：

$$
C(\text{shared}) < C(\text{namespace}) < C(\text{dedicated})
$$
$$
\mathcal{S}(\text{shared}) < \mathcal{S}(\text{namespace}) < \mathcal{S}(\text{dedicated})
$$

路由决策即映射 $r:\mathcal{T}\to \text{Pool}$，满足 $\forall t,\; r(t)\in \text{allowed}(g(t))$。总持有成本把风险折现为成本：

$$
\text{TCO} = \sum_{t} C(g(t)) + \lambda\cdot \sum_t (1-\mathcal{S}(g(t)))
$$

其中第二项惩罚隔离不足带来的风险；$g(t)$ 通常由合规等级与付费等级共同决定。

## 四、代码实现

```python
# 按租户等级路由到不同资源池
def route(tenant):
    tier = lookup_tier(tenant)               # shared / namespace / dedicated
    if tier == "dedicated":
        return isolated_pool(tenant)         # 独占实例
    if tier == "namespace":
        return namespace_pool(tenant)        # 命名空间隔离池
    return shared_pool()                     # 共享池，凭 tenant_id 区分

# LiteLLM 式多租户代理（示意）
def proxy(req, api_key):
    tenant = resolve_tenant(api_key)
    return route(tenant).forward(req, budget=quota(tenant))

# 共享池内按租户配额调度
def schedule(pool, req):
    if not pool.budget[req.tenant].consume(estimate(req)):
        raise RateLimited(req.tenant)
    return pool.dispatch(req)
```

## 五、与其他技术对比

| 模式 | 成本 | 隔离 | 运维复杂度 | 弹性 |
|------|------|------|------------|------|
| 共享池 | 低 | 弱 | 低 | 高 |
| 命名空间 | 中 | 中 | 中 | 中 |
| 独占实例 | 高 | 强 | 高 | 低 |
| 混合（按等级） | 中低 | 可调 | 高 | 中 |

## 六、常见误区

误区一：共享即不安全——逻辑隔离对多数场景足够，过度隔离浪费成本。误区二：一刀切独占——中小租户承担不起。误区三：只在存储层隔离——算力与缓存也要考虑。误区四：忽略计费耦合——隔离必须与配额绑定。误区五：等级静态不变——应按合规变化动态调整路由策略。

## 九、演进与趋势

从「单租户独享」到「逻辑隔离」，再到「按等级混合隔离 + 策略化路由」；平台开始用统一控制面管理租户生命周期、配额与计费，并把隔离粒度细化到请求与上下文。未来趋势是把隔离、配额、计费、SLA 在控制面统一编排，租户等级随合规与付费动态迁移资源池。

在平台工程视角下，多租户正从「部署形态」演化为「产品能力」：租户自助开通、分级 SLA、用量自助看板与配额弹性申请，使底层隔离对上层用户透明，平台只需在控制面声明策略即可。

## 十、小结

多租户架构以隔离梯度换取成本效率，按租户等级混合使用共享与独占资源，并以 TCO 视角把风险折现为成本，是 LLM 服务 SaaS 化的基础。
