# 工具上下文注入

> 对应 LlamaIndex / LangChain 工具调用文档、OpenAI Function Calling 与 Anthropic Tool Use 规范。

## 一、背景与挑战

现代 LLM 通过「工具（tool/function）」连接外部世界：查数据库、调 API、执行代码。要让模型决定何时、如何调用工具，必须把**工具定义**与**工具返回结果**都作为上下文的一部分注入。问题在于：① 工具描述写不好，模型就调不准、调错；② 工具返回结果往往来自不可信外部系统，直接当文本注入会带来注入攻击面；③ 多工具、多轮调用下上下文易混乱、难以解析。工具上下文注入研究的是「如何把工具信息组织得既便于模型决策、又安全可控」。

## 二、核心原理

工具上下文由两部分构成：

- **工具 schema（定义）**：名称、自然语言描述、参数 JSON Schema。这部分是「软提示」——模型据此理解能力边界与调用方式，描述越清晰、参数约束越严格，调用越准确。应写明「何时用、输入输出含义、单位/格式约束」。
- **工具 observation（返回结果）**：工具执行后的输出作为 observation 注入。应标注来源、截断超长输出、对失败给出可读错误，并明确标记为「不可信数据」与系统指令隔离。

工程要点：参数 schema 严格（枚举、类型、必填）减少幻觉；返回结果做结构化与来源标记；失败信息可读（不要只抛原始异常）；必要时对不可信返回做过滤/转义。

工具注入的工程细节决定 Agent 的成败。首先是「描述即提示」：模型只看到你写的 description 来决定是否调用，因此描述要写清「何时该用、输入是什么、输出意味着什么」。常见的失败是描述过短（如「查天气」）导致模型在边界场景误用或漏用，应补充前置条件与不适用场景。其次是「参数 schema 严格化」：用枚举约束取值、用 required 标必填、用类型约束格式，能显著减少「编造参数」「填错字段」类错误。

工具返回结果的注入同样关键。过长结果应截断或先检索再注入（如返回前 2000 字符或最相关片段），避免挤占上下文；失败应返回结构化错误（错误码+可读信息）而非原始堆栈，让模型能自我纠正或改调其它工具。多工具并存时，建议给每次调用与返回都编上序号与来源标记，使模型能清晰区分「工具 A 说……工具 B 说……」，并在后续推理中正确引用。

并行调用是进阶能力：当多个工具互不依赖时，可一次发起多个调用以降时延；但需框架支持并把各结果分别注入。无论串行还是并行，工具上下文注入的底线都是「定义清晰、返回可读、来源可溯、不可信隔离」。

## 三、形式化与数学基础

工具集合 $\mathcal{F}=\{f_1,\dots,f_k\}$，每个工具由描述 $d_i$ 与参数 schema $\sigma_i$ 定义。模型在上下文 $C = [\text{system}, \text{tools}(\mathcal{F}), \text{history}]$ 下生成调用：

$$a_t = \arg\max_a\ P_\theta\big(a \mid C,\ \text{obs}_{<t}\big),\quad a_t = (f_i,\ \text{args}\sim \sigma_i)$$

调用正确性近似取决于描述质量：

$$\text{acc}(a_t) \approx g\big(\,\text{clarity}(d_i),\ \text{strictness}(\sigma_i)\,\big)$$

即描述清晰度 $d_i$ 与 schema 严格度 $\sigma_i$ 越高，错误参数/错误工具的概率越低。返回结果需打标为 untrusted：

$$\text{obs}_i \gets \text{tag}\big(\text{source}=i,\ \text{trust}=\text{untrusted}\big)$$

## 四、代码实现

以 OpenAI 风格函数调用为例：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市当前天气，仅接受城市名",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    },
}]
# 模型返回 tool_calls，执行后将结果作为 observation 注入下一轮
msg = {"role": "tool", "tool_call_id": tc.id,
       "content": json.dumps({"city": "Beijing", "temp_c": 21})}
```

## 五、与其他技术对比

| 维度 | 函数调用 schema | 纯自然语言描述 | 代码执行沙箱 |
|------|---------------|---------------|-------------|
| 解析难度 | 低（结构化） | 高 | 中 |
| 调准率 | 高 | 低 | 高 |
| 安全风险 | 中（需来源标记） | 高 | 需隔离 |

## 六、常见误区

- 工具描述过于简略或含糊，模型不知道何时该用、参数怎么填。
- 把工具返回结果当作可信指令，未隔离标记，给提示注入留口子。
- 返回结果超长未截断，挤占上下文、抬高成本。
- 失败只返回原始堆栈，模型无法自我纠正。

## 九、演进与趋势

从「手写 schema」走向「自动从代码/API 文档生成工具定义」；从「单轮调用」走向「带失败重试、并行调用、结果聚合」的多轮工具编排；并强调工具返回的可信标签与沙箱隔离。

## 十、小结

工具上下文注入把模型从「纯文本生成」连接到「可执行动作」。成败关键在于：用清晰严格的 schema 当软提示提升调准率，用来源标记与隔离把不可信返回关进笼子。这正是 Agent 能力的工程基石。
