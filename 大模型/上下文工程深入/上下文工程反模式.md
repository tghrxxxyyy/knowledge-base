# 上下文工程反模式

> 对应 mlabonne LLM Course、Anthropic 提示工程实践与社区总结的常见错误清单。

## 一、背景与挑战

上下文工程是把「正确的信息，以正确的结构，在正确的时机」放进模型上下文的学问。新手常踩的坑具有高度重复性：这些反模式（anti-pattern）轻则浪费 token，重则让模型行为失控、引入安全风险。把它们系统列清，比罗列「怎么做」更能帮人避坑。本文汇总高频反模式及对应正解。

## 二、核心原理

高频反模式清单：

1. **无脑塞历史**：把所有对话/文档全量塞入，认为越多越好。正解：最小必要原则，按需注入。
2. **系统提示自相矛盾**：两条硬规则冲突且无优先级。正解：显式排优先级、单一职责。
3. **示例格式不一**：few-shot 示例风格/字段参差，模型无所适从。正解：格式严格统一。
4. **把不可信内容当指令**：检索/工具返回未隔离，埋下注入隐患。正解：结构化标记 + 隔离（见上下文隔离与安全）。
5. **忽略成本与时延**：只看质量，上线即贵即慢。正解：质量-成本联合评测。
6. **无评测盲调**：凭感觉改上下文。正解：ablation + 回归测试（见评测上下文质量）。
7. **长提示被忽略**：堆砌导致中间遗忘。正解：精简前置、缓存复用。
8. **上下文结构混乱**：角色/数据/指令混作一团。正解：清晰分区与分隔符。

反模式之所以反复出现，根子在「把上下文当垃圾桶而非接口」：开发者在模型答错时习惯性地「再加一段提示」「再塞几个示例」，而不是回到信息架构层面思考「这一份信息是否必要、结构是否合理、来源是否可信」。这种「堆料式」迭代让上下文越来越胖、越来越乱，最终触发中间遗忘与成本失控。

识别反模式的最好办法是做「上下文审计」：拿到一段上下文，逐块问三问——这块是必要的吗？它的来源可信吗？它与其它块冲突吗？三问中任一答「否」即应重构。例如一段系统提示若同时写「简洁回答」与「详细展开」，立刻判定为规则矛盾；一段检索结果若未带来源标记，立刻判定为不可信未隔离。把这些审计规则沉淀为清单（甚至 CI lint），就能在编写期拦住大多数反模式。

此外，反模式常因「照搬他人提示」滋生：别人的提示贴合其任务分布，直接套用到自己的场景往往水土不服。正确做法是把提示当「参考范式」而非「模板」，依据本任务的评测集改写与验证。

## 三、形式化与数学基础

设上下文组件集合 $C$，反模式可视为引入「噪声/矛盾/不可信指令」的算子 $\eta$：

$$C_{\text{bad}} = \eta(C),\quad \eta \in \{\text{bloat},\ \text{conflict},\ \text{leak-untrusted},\ \text{no-eval}\}$$

健康上下文满足约束：

$$\text{len}(C)\ \text{最小必要},\quad \nexists\, r_i\!\perp r_j\ \text{无优先级},\quad \text{untrusted}(D)\ \text{已隔离}$$

即：长度最小、规则无未决冲突、不可信内容已隔离，且改动经评测。

## 四、代码实现

一个自检清单（伪代码）：

```python
def audit_context(ctx):
    checks = {
        "too_long": len(ctx) > BUDGET,
        "rule_conflict": has_conflict(ctx.rules),
        "untrusted_unmarked": any(d.trust != "untrusted" for d in ctx.data),
        "no_eval": ctx.eval_set is None,
    }
    return [k for k, v in checks.items() if v]   # 返回命中的反模式
```

## 五、与其他技术对比

| 反模式 | 后果 | 正解 |
|--------|------|------|
| 无脑塞历史 | 成本高/注意力稀释 | 最小必要 |
| 规则矛盾 | 行为随机 | 优先级化 |
| 不可信未隔离 | 注入风险 | 标记隔离 |
| 无评测 | 盲调退化 | ablation 回归 |

## 六、常见误区

- 以为「上下文越多越好」，实则边际递减且可能负向。
- 只抄别人提示不改，不符合自己任务分布。
- 一次改多处，无法归因哪处生效（缺 ablation）。
- 把示例当装饰，格式不统一反伤效果。

## 九、演进与趋势

反模式清单正被「上下文 lint 工具」自动化：在 CI 中扫描过长、矛盾、未隔离、缺评测等问题，像代码 linter 一样守护上下文质量。

## 十、小结

上下文工程的反模式高度可枚举：无脑塞、自相矛盾、不可信未隔离、无评测是四大元凶。记住「最小必要、结构化、动态、隔离、评测驱动」，即可避开绝大多数坑。
