# 上下文状态管理

> 对应 LangChain 文档（Memory：ConversationSummaryBufferMemory 等）、mlabonne 的 LLM Course（LLM Engineer 章节）。

## 一、背景与挑战

大模型本身是「无状态」的：每次推理只看到当前传入的 token 序列，不天然记住上一轮说了什么。所谓「状态」，是指让应用在多次交互、多次工具调用之间维持连贯性所需维护的全部信息。当对话只有几轮时，把历史全部塞回上下文即可；但一旦进入 Agent 场景（多轮规划、多工具调用、长任务），状态会迅速膨胀，包含：对话历史、用户画像与长期偏好、工具调用结果、中间计划与子目标、记忆（短期/长期）、以及执行轨迹（trajectory）。核心挑战是——状态若全部塞进上下文，会快速逼近窗口上限、抬高成本、稀释注意力；若全部丢弃，模型又「失忆」。因此需要在「上下文内信息」与「上下文外存储」之间做工程权衡，并定义清晰的状态结构、更新时机、淘汰策略与跨请求持久化方式。

## 二、核心原理

主流做法是把状态与模型上下文分离：状态以结构化形式存于外部（数据库、KV 存储、向量库），只在当前请求时按需把相关片段注入上下文。这带来三点好处：① 上下文长度可控；② 状态可被多会话、多模型共享与审计；③ 敏感状态可做权限隔离。注入策略分三类：

- 全量注入：适用于状态很小（如当前用户 ID、开关标志）。
- 摘要注入：用 LLM 把长历史压缩为结构化摘要再注入（如 ConversationSummaryBufferMemory）。
- 检索注入：把状态写入记忆库，按当前 query 检索相关片段注入（长期记忆）。

此外需定义更新时机（每轮结束写回？工具调用后写回？）、淘汰策略（LRU、按重要性打分、按时间衰减）与冲突合并规则。

在工程落地上，状态管理通常区分两类记忆。工作记忆承载当前任务轨迹，包括最近若干轮对话、当前子目标、待决的工具调用，任务结束即可清空。长期记忆承载跨会话的用户画像、偏好与知识沉淀，写入向量库或 KV 存储并附元数据（来源、时间戳、重要性分），供后续检索式注入。

淘汰策略应结合 LRU 与重要性打分：含实体、约束或决策的轮次高分保留，纯寒暄类低分淘汰。多 Agent 场景还需「共享黑板（blackboard）」机制，让多个子 Agent 读写同一份结构化状态，避免各自维护副本导致不一致。推荐把状态访问封装为统一接口（get/set/search），便于替换底层存储、做权限校验与审计日志，也方便在故障后从外部存储重建上下文。

状态与上下文解耦的另一收益是可观测：因为状态在外部，你能随时检视「模型此刻『记得』了什么」，从而调试幻觉与遗忘，而不必去解析一整段混杂的 prompt。这是状态管理从「技巧」上升为「架构」的分水岭。

## 三、形式化与数学基础

设对话在第 $t$ 轮的状态为 $S_t$，由上一轮状态经事件 $e_t$（用户输入、工具结果、模型动作）更新：

$$S_t = f_\theta(S_{t-1}, e_t)$$

注入上下文的仅为其投影 $I_t = \pi(S_t; q_t)$，其中 $q_t$ 为当前查询，$\pi$ 为检索/摘要/裁剪函数。目标是最小化注入长度同时保留对当前任务必要的语义：

$$\min_{\pi}\ \mathbb{E}_{q_t}\big[\,\text{cost}(I_t)\,\big]\quad \text{s.t.}\quad \text{acc}(I_t) \ge \tau$$

其中 $\text{cost}(I_t)$ 通常为 token 数与时延，$\text{acc}$ 为下游任务准确率，$\tau$ 为可接受下限。

## 四、代码实现

以 LangChain 的摘要缓冲记忆为例，超出 token 阈值的历史会被自动摘要：

```python
from langchain.memory import ConversationSummaryBufferMemory
from langchain.llms import OpenAI

llm = OpenAI()
memory = ConversationSummaryBufferMemory(
    llm=llm,
    max_token_limit=2000,        # 超过则把早期对话压缩为摘要
    return_messages=True,
)
memory.save_context({"input": "我叫小明，在学 RAG"},
                    {"output": "好的，已记住你关注 RAG"})
# 取出注入上下文的消息列表
messages = memory.load_memory_variables({})["history"]
```

对 Agent 场景，更推荐把工具结果写入外部存储，仅注入「最近 N 条轨迹 + 当前子目标」。

## 五、与其他技术对比

| 方案 | 上下文占用 | 持久化 | 适用 |
|------|-----------|--------|------|
| 全量历史注入 | 高 | 无 | 短对话 |
| 滑动窗口 | 中 | 无 | 局部相关 |
| 摘要缓冲 | 低-中 | 可选 | 长对话 |
| 检索式记忆 | 低 | 有（向量库） | Agent/长期 |

## 六、常见误区

- 把所有历史无脑塞入，认为「上下文越多越好」，结果触发中间遗忘与成本爆炸。
- 把不可信的工具返回结果直接当作状态写入并原样注入，带来注入风险。
- 忽略跨请求持久化的 RNG/会话一致性，导致分布式或重放时状态错位。
- 摘要过激丢失关键实体（如用户 ID、订单号），应把关键字段结构化保留而非纯文本摘要。

## 九、演进与趋势

趋势是从「每次重建上下文」走向「持久化、可检索、可演化的状态系统」：长期记忆向量库、分层记忆（工作记忆/情节记忆/语义记忆）、以及把状态管理与上下文压缩、缓存优化联动，形成端到端的状态生命周期管理。

## 十、小结

上下文状态管理的本质是「在成本、窗口、连贯性之间做工程权衡」：用外部存储承载长期状态，用摘要/检索/裁剪做按需注入，并以结构化方式保留关键事实。它是一切长程 Agent 与多轮应用的地基。
