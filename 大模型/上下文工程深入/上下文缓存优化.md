# 上下文缓存优化

> 对应 Anthropic Prompt Caching、OpenAI 提示缓存、vLLM 前缀缓存（prefix caching）与 KV Cache 复用。

## 一、背景与挑战

推理时，长系统提示、固定的知识文档、few-shot 示例等往往**在多次请求间不变**。若每次都重新计算这些前缀的注意力 KV，是巨大浪费。上下文缓存优化的思路是：复用这些稳定前缀的 KV Cache（前缀缓存），并对「相同问题不同表述」做语义缓存省去生成。挑战在于：缓存命中要求前缀**逐 token 完全一致**，而模板里哪怕一个动态变量插到前面，就会破坏整段缓存。因此需在「上下文结构设计」上配合——稳定内容前置、变化内容后置。

## 二、核心原理

两类缓存：

- **前缀缓存（prefix caching / KV cache reuse）**：把共享前缀的 KV 张量缓存，命中后跳过其计算。主流推理引擎（vLLM、TensorRT-LLM、各大厂商 API）均支持。缓存键由前缀 token 序列决定，故要求前缀稳定且置于最前。
- **语义缓存（semantic caching）**：对语义相近的 query 直接返回已生成的答案，跳过一次生成。需 Embedding 判近邻 + 答案复用策略，注意答案可能因上下文不同而不通用。

上下文工程配合点：把不变的系统提示/知识放最前，把用户变量、检索结果等易变内容放最后，最大化前缀命中；并保持模板结构稳定（不要每请求微调前缀格式）。

缓存优化与上下文结构设计是强耦合的：很多团队抱怨「缓存命中率低」，根因往往不是引擎不行，而是模板把易变内容写在了最前面。例如系统提示开头放「当前时间：2026-09-09 10:00」，每次请求都变，前缀缓存整段失效。正确做法是把这类动态字段移到上下文末尾，或抽到工具/变量层、仅在生成时注入，而不进入被缓存的提示文本。

前缀缓存还有一层「层级」值得利用：把跨用户共享的通用知识（如产品说明、API 文档）放在最前作为「全局前缀」，命中率最高；把用户级定制放在中段；把本次 query 放最后。这样不同用户仍能共享最贵的前缀 KV，进一步摊薄成本。语义缓存则适合「高频相似问」场景（如客服 FAQ），但务必设置新鲜度与范围——同一问题在不同用户权限下答案可能不同，盲目复用会泄露或答错。

监控上应记录「缓存命中率 / 省下的 token 占比 / 尾延迟」，把缓存当作一项 SLO 来运营，而非上线即忘。当命中率异常下滑，通常是模板被改动或前置变量泄漏，需回查上下文结构。

## 三、形式化与数学基础

设第 $i$ 次请求上下文 $C_i = [P,\ V_i]$，其中 $P$ 为共享前缀、$V_i$ 为易变后缀。前缀缓存命中时省去前缀计算：

$$\text{FLOPs}_{\text{saved}} = \sum_{l=1}^{L} 2\,|P|\, d_{\text{model}} \quad \text{（前缀各层 KV 免重算）}$$

命中率近似：

$$h = \frac{|\{i: P_i = P_{\text{cached}}\}|}{N}$$

$P_i$ 与缓存前缀逐 token 相等才命中。若把易变内容 $V$ 误插到前缀前，则 $P_i \ne P_{\text{cached}}$，命中率骤降。语义缓存额外定义近邻判定 $\text{sim}(q_i,q_j)\ge\tau$ 即复用答案。

## 四、代码实现

Anthropic 风格提示缓存（标记可缓存断点）：

```python
resp = client.messages.create(
    model="claude-...",
    system=[{
        "type": "text",
        "text": LONG_SYSTEM_PROMPT,     # 稳定前缀
        "cache_control": {"type": "ephemeral"},
    }],
    messages=[{"role": "user", "content": user_input}],  # 易变后置
)
# 后续命中前缀的请求会复用 KV，显著降本提速
```

## 五、与其他技术对比

| 缓存 | 命中条件 | 省什么 | 风险 |
|------|---------|--------|------|
| 前缀缓存 | 前缀逐 token 同 | KV 计算 | 低 |
| 语义缓存 | 语义近邻 | 整次生成 | 答案不通用 |
| 模型权重缓存 | — | 加载 | 无 |

## 六、常见误区

- 把动态变量（时间戳、用户 ID）插到前缀，破坏整段缓存命中。
- 频繁改动系统提示格式，缓存反复失效。
- 语义缓存直接复用答案，忽略上下文差异导致答非所问。
- 只信缓存省成本，未监控命中率与新鲜度。

## 九、演进与趋势

缓存从「手动标记断点」走向「自动前缀检测与跨请求复用」；并和上下文压缩、路由联动：命中缓存可跳过部分路由与检索。长上下文模型下，缓存成为推理成本的控制阀。

## 十、小结

上下文缓存优化的本质是「让不变的前缀只算一次」。工程上把稳定内容前置、易变内容后置、保持模板稳定，即可最大化前缀命中；语义缓存进一步省去重复生成。它是降本提速的工程杠杆。
