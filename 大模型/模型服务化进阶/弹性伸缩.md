# 弹性伸缩

> 对应 KServe / vLLM 生产部署实践与 HuggingFace Text Generation Inference (TGI)  autoscaling 文档。

## 一、背景与挑战

大模型推理服务面临高度波动的流量：白天高峰与夜间低谷的 QPS 可差数十倍，突发活动又会瞬时打满副本。固定副本数要么浪费昂贵的 GPU（低谷空转），要么在高峰丢请求。弹性伸缩（Autoscaling）即根据负载自动扩缩副本数，目标是在「满足延迟 SLA」与「控制 GPU 成本」之间取平衡。大模型场景的特殊性使传统 Web 服务的 HPA（基于 CPU/内存）几乎失效：GPU 利用率与请求排队并不直接对应，且单副本启动要加载数 GB 至数百 GB 权重，冷启动常以分钟计。挑战集中在：如何选取能反映真实压力的扩缩指标、如何压缩冷启动、如何在抢占式（spot）实例被回收时不丢请求。

## 二、核心原理

弹性伸缩由「指标采集 → 决策 → 执行」三环构成：
1. **指标**：优先用队列深度（in-flight 请求数）、GPU 利用率、TTFT（首 token 延迟）、KV Cache 占用率，而非 CPU。
2. **决策**：基于目标值的比例控制器（如 K8s HPA 的 `requests-per-gpu`、KServe 的并发目标）或基于预测（昼夜周期）的提前扩容。
3. **执行**：拉起新 Pod→挂载模型权重→预热→接入负载均衡；缩容则先摘流（drain）再回收。

针对冷启动：用「预热池」（常驻但低功耗的副本占位）或「权重预取缓存」（本地 NVMe 已缓存权重）将加载时间从分钟级压到秒级；spot 实例则需把 checkpoint 放在共享存储并支持断点重载。

## 三、形式化与数学基础

设单副本可稳定服务并发上限为 $C$，目标队列长度 $Q^*$，当前在途请求 $q(t)$。扩容副本数 $N$ 满足：

$$ N = \left\lceil \frac{q(t) + \lambda \cdot \text{TTFT}_{\text{budget}}}{C} \right\rceil $$

其中 $\lambda$ 为到达率。缩容需满足冷却窗口，避免抖动（thrashing）：

$$ \text{scale\_down\_after} = \max(t_{\text{cooldown}},\, k\cdot t_{\text{cold\_start}}) $$

即冷却时间至少覆盖一次冷启动成本，避免「缩了又扩」的振荡。

## 四、代码实现

```yaml
# KServe InferenceService 片段：基于并发的自动扩缩
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 8
    scaleTarget: 16          # 单副本目标并发
    scaleMetric: "concurrency"
    containerConcurrency: 16
    triton:
      storageUri: "gs://models/llama-3-8b"
```

```python
# 自管调度：按队列长度决策（示意）
def desired_replicas(q, target=16, max_r=8):
    return max(1, min(max_r, math.ceil(q / target)))
```

## 五、与其他降本手段对比

| 手段 | 响应速度 | 成本收益 | 复杂度 | 备注 |
|------|----------|----------|--------|------|
| 固定副本 | 即时 | 差（空转） | 低 | 仅稳态流量 |
| 弹性伸缩 | 秒-分级 | 高 | 中 | 需解决冷启动 |
| 多模型路由 | 即时 | 高 | 中 | 降单请求成本 |
| 预热池 | 即时 | 中 | 中 | 牺牲部分空闲省电 |
| Spot 实例 | 分钟级 | 高 | 高 | 需容错重载 |

弹性伸缩常与路由、量化组合：路由先压单请求成本，弹性再压副本总数。

## 六、常见误区

- **用 CPU 利用率做指标**：GPU 推理下 CPU 几乎不动，会严重低估真实压力。
- **冷却窗口过短**：导致副本频繁震荡，冷启动成本反超收益。
- **忽略权重加载时间**：副本「已起」不代表「可服务」，需用就绪探针而非仅进程存活。
- **spot 回收无兜底**：未做 checkpoint 重载会在回收瞬间丢在途请求。

## 九、演进与趋势

- **预测式伸缩**：基于历史周期与业务日历提前扩容，规避冷启动滞后。
- **异构副本**：小模型常驻 + 大模型按需弹，按难度分层供给算力。
- **权重内存映射**：用 mmap/共享内存避免每副本重复加载，进一步压冷启动。
- **Serverless GPU**：按 token 计费的托管推理，将弹性交给平台。

## 十、小结

弹性伸缩是大模型服务降本的关键杠杆，核心是选对反映 GPU 真实压力的扩缩指标、用预热池/权重预取压冷启动、并以足够冷却窗口抑制振荡。它应与路由、量化组合，在 SLA 与 GPU 成本间动态平衡。
