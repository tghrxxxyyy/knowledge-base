# 流式与背压

> 对应 OpenAI Streaming (SSE) 实践、vLLM 流式输出与 HuggingFace TGI 流式 API 文档。

## 一、背景与挑战

用户与大模型交互时，最在意的体感之一是「是否立即开始看到内容」。若等完整回答生成完再一次性返回，几十秒的空白会让人以为系统卡死。流式（Streaming）通过 SSE（Server-Sent Events）或 WebSocket 把 token 边生成边推送给客户端，让首字立即可见、后续逐字涌现。但流式带来新的工程问题：当客户端消费慢（如前端渲染卡顿、网络差）或主动断连时，服务端仍在持续生成并堆积输出，内存与算力被无效占用——这正是背压（backpressure）要解决的。挑战还包括：断连后如何取消生成任务、如何做 token 级超时、多路流如何公平调度、以及流式下如何准确计费与统计。

## 二、核心原理

流式输出的本质是「生产者-消费者」模型，服务端是高速生产者（GPU 逐 token 生成），客户端是慢速、不可靠的消费者。背压机制指：当下游消费不及时，上游应被通知「放慢或暂停」，防止 unbounded 缓冲膨胀。实现要点：
- **断连检测**：通过 HTTP 连接关闭事件（如 `request.is_disconnected()`）立即触发取消，停止后续前向，释放 KV Cache。
- **有界缓冲**：服务端为每个流维护有限长度的发送队列，满则暂停生成或丢弃（依策略）。
- **token 级超时**：单 token 生成/发送超阈值即终止，避免长尾挂死。
- **取消传播**：客户端中止应一路取消到引擎调度层，而非只关 socket。

WebSocket 相比 SSE 支持双向（客户端可中途改指令），但复杂度更高；SSE 单向、基于 HTTP，更易穿透代理，是大模型流式的主流选择。

## 三、形式化与数学基础

设生成速率 $r_g$（token/s），客户端消费速率 $r_c$（token/s），缓冲上限 $B$。若 $r_g>r_c$，缓冲增长：

$$ \frac{d\,\text{buf}}{dt} = r_g - r_c $$

当 $\text{buf}(t) \ge B$ 触发背压，令 $r_g' = \min(r_g, r_c)$，使 $\frac{d\,\text{buf}}{dt}\le 0$。断连时直接置 $r_g'=0$ 并回收资源。背压目标即保证 $\text{buf}(t)\le B$ 恒成立，避免 OOM。

## 四、代码实现

```python
from fastapi import Request
import asyncio

async def stream_generate(prompt, request: Request):
    buf = asyncio.Queue(maxsize=64)        # 有界缓冲=背压边界
    async def producer():
        for tok in engine.generate(prompt):
            await buf.put(tok)             # 满则 await，形成背压
    async def consumer():
        while True:
            if await request.is_disconnected():   # 客户端断连
                return                               # 取消：跳出即停止
            tok = await buf.get()
            yield f"data: {tok}\n\n"
    prod = asyncio.create_task(producer())
    try:
        async for chunk in consumer():
            yield chunk
    finally:
        prod.cancel()                              # 确保生成被取消
```

## 五、传输方式对比

| 方式 | 方向 | 穿透代理 | 复杂度 | 适用 |
|------|------|----------|--------|------|
| SSE | 单向 | 好 | 低 | 主流流式 |
| WebSocket | 双向 | 一般 | 中 | 需中途交互 |
| 长轮询 | 单向 | 好 | 中 | 兼容老客户端 |
| gRPC stream | 双向 | 差 | 高 | 内部服务间 |

## 六、常见误区

- **断连不取消**：只关 socket 但引擎继续生成，浪费算力与显存。
- **无界缓冲**：客户端慢导致服务端内存无限增长，最终 OOM 拖垮整副本。
- **忽略 token 级超时**：个别请求卡在某步，占住调度槽位形成长尾。
- **流式不做计费/统计**：逐 token 输出使传统「按请求」计量失准，需按 token 实时累计。
- **断连后不释放 KV**：取消信号未传到引擎层，显存被死请求占满。

工程上建议把「取消」做成一等信号：网关断连即向调度器发 abort，调度器回收该序列的 KV 块并跳过后续前向，形成端到端资源守恒。

## 七、与开源书·权威来源对应

- OpenAI、Anthropic 等 API 文档定义 SSE `data:` 事件与 `[DONE]` 终止约定。
- vLLM、TGI 的 `stream: true` 输出遵循相同事件格式。
- FastAPI/Starlette 提供 `Request.is_disconnected()` 用于断连取消。

## 九、演进与趋势

- **取消传播标准化**：把 abort 信号贯穿网关→引擎→调度层。
- **自适应节流**：依客户端消费速率动态调节生成节奏。
- **HTTP/2、HTTP/3 多路复用**：降低流式连接开销。
- **边缘流式缓存**：在 CDN 边缘缓冲并转发 token 流。
- **按消费速率自适应节流**：依客户端节奏动态调生成速度，防背压累积。

## 十、小结

流式以 SSE 为主，让首字立现改善体感；背压以有界缓冲 + 断连取消防止慢客户端拖垮服务端。核心是「生产者-消费者」模型下的资源守恒：断连即停、超即止、缓冲有界，方能稳定承载海量并发流。
