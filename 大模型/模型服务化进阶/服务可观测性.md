# 服务可观测性

> 对应 vLLM / TGI 指标暴露（Prometheus）实践与 llm-course (mlabonne) 推理监控章节。

## 一、背景与挑战

大模型推理服务一旦上线，「看不见内部状态」就会变成黑盒：用户抱怨「变慢了」却无法定位是路由、检索还是生成环节；GPU 显存悄悄被长请求占满导致新请求排队；量化模型在某类任务悄悄掉点却无人察觉。可观测性（Observability）通过指标（Metrics）、日志（Logs）、追踪（Traces）三类信号让系统「可被推理」。其挑战在于：大模型推理既有传统服务的吞吐/延迟，又有 token 级特有指标（TTFT、TPOT、KV 命中率、生成长度分布），且一次请求常跨「路由→检索→生成」多阶段，需要端到端链路追踪才能归因。

## 二、核心原理

可观测性三大支柱在大模型场景的具体化：
1. **Metrics（指标）**：用 Prometheus 拉取。关键指标包括请求量（QPS）、延迟分布（P50/P95/P99 的 TTFT 与 TPOT）、错误率（4xx/5xx、生成截断率）、token 吞吐（in/out tokens/s）、GPU 利用率与显存、KV Cache 占用与命中率、队列深度。
2. **Logs（日志）**：结构化记录每次请求的来源、路由决策、模型名、耗时分段、错误信息，便于审计与回溯。
3. **Traces（追踪）**：用 OpenTelemetry 把一次请求在网关、检索器、引擎各段的耗时串联成瀑布图，定位瓶颈段。

告警应围绕 SLA：TTFT/TPOT 越界、错误率突增、KV 命中率骤降、GPU 显存接近上限均触发通知。

## 三、形式化与数学基础

设采样窗口内请求集合 $\mathcal{R}$，第 $i$ 个请求的 TTFT 为 $t_i^{(1)}$、TPOT 为 $t_i^{(2)}$。分位延迟：

$$ P_k = \text{quantile}\big(\{t_i^{(1)}\}_{i\in\mathcal{R}},\ k\big) $$

错误率与「单位成本」用 token 核算：

$$ \text{cost\_per\_1M} = \frac{\text{GPU\$/h} \times \Delta h}{\text{tokens}_{\text{out}} / 10^6} $$

监控目标即把 $P_{95}(t^{(1)})$、$P_{95}(t^{(2)})$ 与错误率约束在 SLA 内，同时让单位成本下行。

## 五、可观测信号对比

| 信号 | 优势 | 局限 | 用于 |
|------|------|------|------|
| Metrics | 低开销、易聚合告警 | 无上下文 | SLA、趋势 |
| Logs | 可回溯细节 | 量大、难检索 | 审计、排障 |
| Traces | 端到端归因 | 有侵入、开销 | 瓶颈定位 |

三者互补：指标发现问题、追踪定位环节、日志还原细节。

## 六、常见误区

- **只监控 QPS 与错误率**：忽略 TTFT/TPOT 会漏掉「能答但极慢」的体验退化。
- **不监控 KV Cache 命中率**：前缀缓存失效时吞吐悄悄下滑却无显式报错。
- **告警阈值静态**：业务峰谷不同，固定阈值易误报/漏报，应按周期基线动态。
- **缺链路追踪**：路由慢、检索慢、生成慢混为一谈，无法归因。

## 七、与开源书·权威来源对应

- vLLM、TGI 原生暴露 `/metrics`（Prometheus 格式）含 TTFT/TPOT/KV 等指标。
- OpenTelemetry 文档给出 LLM 请求追踪的语义约定。
- llm-course (mlabonne) 推理优化章强调 token 级成本核算。
- Grafana 提供现成 LLM 服务看板模板。

## 九、演进与趋势

- **LLM 专用语义约定**：OpenTelemetry 标准化 token、模型、用量等属性。
- **质量可观测**：不仅监控延迟，还在线采样评测生成质量（掉点检测）。
- **因果归因**：从指标异常自动反推到具体阶段/模型版本。
- **成本实时面板**：把 $/1M tokens 做成实时可下钻的业务指标。

## 十、小结

服务可观测性让大模型推理从黑盒变白盒，核心是采集 token 级指标（TTFT/TPOT/KV 命中）、结构化日志与端到端追踪，并围绕 SLA 与单位成本建立动态告警。指标发现问题、追踪定位环节、日志还原细节，三者缺一不可。
