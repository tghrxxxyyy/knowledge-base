# 推理服务架构

> 对应 vLLM / TensorRT-LLM / TGI 部署实践与 HuggingFace 推理优化文档。

## 一、背景与挑战

把训练好的大模型变成「可稳定对外提供每秒数百请求的在线服务」并非简单套一层 API：自回归生成对显存、调度、批处理都有特殊要求，且用户既关心「首个字多快出来」（体感），也关心「每秒能处理多少请求」（成本）。一个生产级推理服务要在吞吐、延迟、成本三者间权衡，并能在流量波动下保持 SLA。典型架构需串联：接入层（负载均衡/鉴权）→ 推理引擎（连续批处理 + 分页 KV Cache）→ KV Cache 与显存管理 → 流式输出。挑战包括长请求占用显存、突发流量排队、多副本一致性、以及可观测性缺失导致无法定位瓶颈。

## 二、核心原理

生产推理服务的标准数据通路为：
1. **网关/负载均衡**：做鉴权、限流、按副本队列深度路由（而非轮询）。
2. **推理引擎**：核心负责连续批处理、PagedAttention 管理 KV、调度 token 步。代表有 vLLM、TensorRT-LLM、TGI、SGLang。
3. **KV Cache 管理层**：以块为单位按需分配显存，支持前缀共享与抢占回收。
4. **输出层**：以 SSE/WebSocket 流式返回，配合背压与取消。

关键 SLO 指标分两类：延迟类（TTFT、TPOT）与效率类（吞吐 req/s、GPU 利用率、$/1M tokens）。架构设计要在二者间取舍——提升 batch 可降单位成本但抬高 TPOT。

## 三、形式化与数学基础

设每步解码 batch 大小为 $B$，每 token 计算量 $F$，GPU 算力 $\tau$（tokens/s 等效），则单步耗时约 $B\cdot F/\tau$。两个核心延迟：
- 首 token 延迟（含 prefill）： $TTFT \approx \frac{L_p\cdot F}{\tau} + q$，其中 $L_p$ 为 prompt 长度、$q$ 为排队等待。
- 每 token 延迟（解码步）： $TPOT \approx \frac{B\cdot F}{\tau}$。

可见 TPOT 随 batch $B$ 上升，故「大 batch 降本」与「低 TPOT」天然冲突，需按业务设上限。

## 四、代码实现

```python
from vllm import LLM, SamplingParams

llm = LLM(model="meta-llama/Llama-3-8b", tensor_parallel_size=2,
          max_num_seqs=256, gpu_memory_utilization=0.9)

params = SamplingParams(temperature=0.7, top_p=0.9, max_tokens=512)

# 引擎内部已做连续批处理；外层只需发起请求
outputs = llm.generate(["请总结以下内容：..."], params)
for o in outputs:
    print(o.outputs[0].text)
```

## 六、常见误区

- **只盯吞吐忽略 TPOT**：高 batch 把单位成本压低，却让用户觉得「卡顿」。
- **用轮询做负载均衡**：副本队列不均时轮询会制造长尾，应按 outstanding 数路由。
- **prefill 与 decode 混步无隔离**：长 prompt 阻塞解码，宜用分块预填充。
- **显存预算拍脑袋**：未给 KV Cache 留余量会在高峰触发淘汰，反而掉速。
- **忽视 prefill/decode 混合代价**：不隔离时长 prompt 拖垮整批解码延迟。
- **不做成本归因**：不把 $/1M tokens 与 GPU 利用率挂钩，难定位降本空间。
- **忽视副本异构**：小模型常驻、大模型按需弹，比全量旗舰更省且更稳。

落地清单：先定 SLA（TTFT/TPOT 上限）→ 选引擎与并行度 → 按 outstanding 路由 → 设 batch 上限保 TPOT → 接前缀缓存与分块预填充 → 用 Prometheus 盯 KV 命中率与单位成本。

## 九、演进与趋势

- **分离式 prefill/decode**：把计算密集的 prefill 与延迟敏感的 decode 部署到不同副本池。
- **前缀/语义缓存**：跨请求共享 KV，复用长 system prompt 与少样本样例。
- ** disaggregated 调度**：KV Cache 跨节点迁移，解耦计算与存储。
- **统一网关标准化**：LiteLLM 等把路由、限流、观测做成接入层基础设施。
- **分离式 prefill/decode 池化**：按负载分别伸缩两类副本，互不拖累。
- **KV 缓存即服务**：把 KV 管理外置，解耦计算与存储资源。
- **按 SLA 自动调 batch**：依 TPOT 预算动态上限 max_num_seqs。

## 十、小结

生产推理服务是「网关 → 引擎 → KV 管理 → 流式输出」的协同系统，核心在吞吐（成本）与延迟（体验）的权衡。选对引擎、按 outstanding 路由、为大 batch 设 TPOT 上限、并配合分块预填充与缓存共享，方能稳定承载高并发。
