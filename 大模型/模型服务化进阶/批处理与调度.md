# 批处理与调度

> 对应 vLLM 连续批处理（continuous batching）与 HuggingFace TGI / Orca 调度实践。

## 一、背景与挑战

自回归生成是逐步产出 token 的过程：一个请求要经历数十至上百次前向。若用传统「静态批处理」（等凑齐一个固定 batch 再统一推理、所有序列等长同步推进），会遇到两个典型问题：一是「短板效应」——batch 中最长的序列决定整批何时结束，短序列早早算完却被迫空等；二是显存浪费——必须为最长序列预分配 padding 与 KV Cache。在大模型高并发场景下，GPU 利用率因此大幅下滑。连续批处理（continuous / in-flight batching）正是为解决该问题而生：它按 token 步动态增删序列，让完成的请求立刻让出位置、新请求随时插入，从而把 GPU 喂满。

## 二、核心原理

连续批处理的关键是把调度粒度从「整个序列」细化到「每一步 token」：
- 每个解码步，调度器从「等待中 + 生成中」的序列池里挑选可运行的序列组成当前步的 batch。
- 某序列生成出 EOS 或达最大长度即退出，其显存（KV Cache 块）立即回收。
- 新到达请求可在任意步加入，无需等当前 batch 结束。
- 为避免长请求「饿死」短请求，需引入优先级或公平调度（如按剩余预算、FCFS+优先级）。

这要求推理引擎的 KV Cache 管理支持「分页/分块」式按需分配，而非预分配整段——这正是 vLLM 的 PagedAttention 所解决的前提。

## 三、形式化与数学基础

设一个静态 batch 含 $n$ 条序列，长度分别为 $l_1,\dots,l_n$，最大长度 $L=\max_i l_i$。静态批处理的有效计算利用率约为：

$$ u_{\text{static}} = \frac{\sum_i l_i}{n \cdot L} \le 1 $$

连续批处理下，短序列退出后其槽位被新序列填补，理论上单步 batch 始终接近满载，利用率趋近：

$$ u_{\text{cont}} \approx \frac{\bar{l}}{\text{slot\_span}} \rightarrow 1 $$

其中 $\bar{l}$ 为平均序列长度。差距越大（序列长度方差越大），连续批处理收益越高。

## 四、代码实现

```python
# 简化调度器：按步动态组 batch（示意）
class Scheduler:
    def step(self, running, waiting, max_tokens):
        batch, used = [], 0
        for seq in sorted(running, key=lambda s: s.priority, reverse=True):
            if used + seq.next_kv_len > max_tokens:
                continue
            batch.append(seq); used += seq.next_kv_len
        for seq in waiting:                    # 新请求随时插入
            if used + seq.next_kv_len <= max_tokens:
                batch.append(seq); waiting.remove(seq); used += seq.next_kv_len
        return batch

# vLLM 实际通过 PagedAttention + block table 管理 KV，见 vllm/config.py
```

## 五、与其他批处理策略对比

| 策略 | 显存利用 | 吞吐 | 尾延迟 | 实现难度 |
|------|----------|------|--------|----------|
| 静态批处理 | 低（padding） | 低 | 高（短板） | 低 |
| 动态批处理（请求级） | 中 | 中 | 中 | 中 |
| 连续批处理（token 级） | 高 | 高 | 低 | 高 |
| 分块预填充（chunked prefill） | 高 | 高 | 低 | 高 |

连续批处理通常配合「分块预填充」以进一步减小 prefill 对解码步的阻塞。

## 六、常见误区

- **以为 batch 越大越好**：超过显存与 KV 预算反而触发淘汰/换页，得不偿失。
- **忽略优先级导致饿死**：纯 FCFS 下长请求会拖垮短请求 P99。
- **把连续批处理等同于动态批处理**：前者调度粒度为 token 步，后者仅为请求级，收益差异显著。
- **未配分页 KV Cache**：连续批处理依赖分块分配，否则仍被预分配束缚。
- **忽视前缀缓存复用**：多请求共享 system prompt 时未复用 KV，等于重复计算。
- **不分块预填充**：长 prompt 整段 prefill 阻塞解码步，抬高 TPOT 长尾。

## 九、演进与趋势

- **分块预填充**：把长 prompt 切成块与解码步交替，平滑延迟曲线。
- **优先级 + SLA 感知调度**：按业务等级与 TTFT 预算动态加权。
- **前缀缓存共享**：多请求共享 system prompt 的 KV 块，进一步提效。
- **离散事件仿真**：用模拟器离线寻优调度超参。
- **抢占式调度**：显存不足时按优先级抢占低优先请求并换出 KV，保障高优 SLA。
- **公平性度量**：用 Jain 指数等量化各请求等待公平度，防长尾饿死。
- **自适应批上限**：依实时显存与 KV 预算动态调 max_num_seqs，而非固定常数。

## 十、小结

连续批处理把调度粒度从序列细化到 token 步，配合分页 KV Cache 动态增删序列，显著消除短板效应、提升 GPU 利用率。落地需兼顾优先级防饿死，并与分块预填充、前缀缓存协同，是高并发推理服务的标配。
