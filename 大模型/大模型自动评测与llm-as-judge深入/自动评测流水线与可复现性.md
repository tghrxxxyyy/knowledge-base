# 自动评测流水线与可复现性

> 对应 Gao et al. 2021 lm-evaluation-harness 与 Zheng et al. 2023《Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena》。

## 一、背景与挑战
评测结论若不可复现，就没有任何决策价值。现实中常见的问题是：同一模型两次评测分数不同、不同团队跑出不同排名、改动很小却分数剧烈波动——这些都属于可复现性缺失。它让「模型是否真的变好了」这一基本问题无法回答。

可复现性的敌人来自多个环节：模型版本未固定（权重或推理服务静默升级）、提示模板不同步、采样温度与随机种子未固化、数据集版本漂移、聚合脚本不一致、以及裁判模型本身随版本变化。任何一个环节松动，结论就失去可比性。

## 二、核心原理
核心思想是「评测即代码」：把数据集、提示模板、裁判配置、采样参数、聚合脚本全部固化为可版本化的配置与代码，放入仓库统一管理。每次评测只允许有一个变量——被评模型。其余一切保持字节级一致。

具体做法包括：为每次评测记录完整的环境指纹（模型标识、数据集哈希、提示哈希、温度、top-p、随机种子、裁判版本、代码 commit）；把评测产物（原始输出、分数、日志）持久化并可 diff；对多次运行报告均值与不确定性而非单次分数；建立定期回归看板，自动对比当前版本与基线的差异并告警。

流水线化的另一价值是「偏差可追踪」：当分数异常波动时，能借助记录快速定位是模型变了、提示变了还是裁判变了。

## 三、形式化与数学基础
把一次评测的运行条件记为配置元组：

$$ \Theta = (model,\ dataset,\ prompt,\ judge,\ T,\ top\text{-}p,\ seed,\ code\text{-}rev) $$

可复现性要求：对两次评测 $r_1, r_2$，若除被评模型外的所有维度相同（$r_1.\Theta_{-model} = r_2.\Theta_{-model}$），则分数差异只归因于模型本身。任何未固定的维度都会污染因果归因。

对同一配置重复运行 $K$ 次得到分数 $\{s_1, \dots, s_K\}$，应报告均值与置信区间。当 $K$ 较大时用正态近似：

$$ \bar{s} \pm z_{1-\alpha/2}\,\frac{\sigma}{\sqrt{K}} $$

其中 $\sigma$ 为样本标准差，$z_{0.975}\approx 1.96$ 对应 95% 置信水平。$K$ 较小时应改用 $t$ 分布临界值。置信区间重叠的两个模型，其分数差异在统计上不可区分，不应轻率地宣称谁更好。

## 四、代码实现
```python
import math
import statistics

# 多次运行：报告均值与 95% 置信半宽
def mean_ci(scores):
    # scores: 同一配置下多次重复运行的分数
    m = statistics.mean(scores)
    if len(scores) < 2:
        return m, float("nan")
    sd = statistics.stdev(scores)          # 样本标准差
    se = sd / math.sqrt(len(scores))
    return m, 1.96 * se                     # 近似 95% 置信半宽
```

## 五、与其他技术对比
| 维度 | 评测流水线（Evaluation-as-Code） | 一次性评测脚本 |
| --- | --- | --- |
| 配置管理 | 版本化、可审计 | 散落、易漂移 |
| 结果可 diff | 是 | 否 |
| 偏差可追踪 | 是 | 难 |
| 复现成本 | 低（一键重跑） | 高（需人工还原环境） |
| 适用 | 持续评测、发布门禁 | 临时探索 |

相比一次性脚本，流水线化能保证偏差可追踪、结果可 diff，代价是需要前期投入工程化建设。对于需要持续迭代的模型团队，这笔投入很快回本。

## 六、常见误区
误区一：「未固定随机种子导致分数漂移」。错，采样温度与种子必须固化，否则差异无法归因。误区二：「把不同温度下的结果混用比较」。错，运行条件不同的评测不可直接比较。误区三：「只报单次结果」。错，应报告多次运行的均值与不确定性。误区四：「置信区间重叠就宣称更好」。错，统计上不可区分，结论无效。误区五：「裁判版本升级后沿用旧基线」。错，裁判变更会系统改变分数，必须重建基线。

## 九、演进与趋势
趋势是评测与模型注册表、数据集注册表深度联动：模型版本、数据集哈希、裁判版本作为一等公民被登记与追踪，评测结果可按任意维度回溯。评测产物从「一个分数」扩展为「可审计的证据包」（原始输出、理由、配置指纹）。同时，持续评测与发布门禁结合，把可复现性从最佳实践变成强制流程。

工程落地的检查清单：

- 配置指纹：每次运行记录模型、数据集哈希、提示哈希、裁判版本与代码版本。
- 产物留存：原始输出、裁判理由与聚合结果一并归档，支持 diff。
- 统计报告：报告均值与置信区间，区间重叠不宣称更优。
- 基线管理：裁判或数据集升级后重建基线，避免新旧混比。
- 自动告警：分数相对基线异常波动时触发通知与复跑。

把「只变被评模型」作为硬约束写入流水线，是保证结论可归因的最有效手段。

## 十、小结
可复现性来自「配置固化 + 统计报告」：把数据集、提示、裁判、采样参数与代码版本全部固定，只让被评模型变化；对多次运行报告均值与置信区间；把结果与配置一并持久化以支持 diff 与归因。它不是锦上添花的工程细节，而是评测结论能否作为决策依据的底线。没有可复现性，再漂亮的分数也只是噪声。
