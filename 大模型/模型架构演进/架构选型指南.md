# 架构选型指南

> 工程决策综合，融合 Vaswani et al. 2017、LLaMA/Touvron 2023、Mamba/Gu & Dao 2023、Mixtral/Jiang 2024 等架构实践。属模型架构演进板块。

## 一、背景与挑战

面对「要做/选一个 LLM 架构」的需求，工程师常被各种噱头迷惑：是上 Transformer 还是上 SSM？要 MoE 还是稠密？要 RoPE 还是 ALiBi？架构选型直接决定**能力上限、训练成本、推理吞吐、长上下文表现与生态成熟度**。本篇给出一个面向工程决策的对照框架，帮助在不同约束下做权衡，而非盲目追新。

## 二、核心原理

选型应围绕四条主轴线展开：
1. **任务性质**：通用对话/创作偏好强能力稠密 Transformer；超长文档/流式处理可考虑 SSM（Mamba 类）；高吞吐且预算有限可考虑 MoE。
2. **序列长度与成本**：Transformer 注意力 $O(T^2)$ 在超长序列下显存爆炸；SSM/线性递归为 $O(T)$ 线性，更省；滑动窗口（Mistral）是折中。
3. **训练 vs 推理预算**：MoE 训练贵但推理激活少；稠密反之。GQA/量化主要影响推理。
4. **生态与成熟度**：Transformer 工具链（FlashAttention、vLLM、各类微调）最成熟，新架构需评估工程风险。

决策不是「谁最强」，而是「在约束下性价比最高」。

## 三、形式化与数学基础

设候选架构 $A$ 在序列长 $T$、维度 $d$、层数 $L$ 下的推理复杂度与显存：

$$
\text{Transformer(MHA)}:\; \text{FLOPs}\sim O(L\,T^2 d),\quad \text{KV}\sim O(L\,T\,h)
$$
$$
\text{SSM(状态空间)}:\; \text{FLOPs}\sim O(L\,T\,d^2),\quad \text{状态}\sim O(L\,d\,N)
$$
$$
\text{MoE}:\; \text{激活参 } \ll \text{总参},\; \text{推理 FLOPs}\sim O(L\,T\,d\cdot s)
$$

其中 $s$ 为专家激活比例，$N$ 为 SSM 状态维。选型即比较在目标 $(T, \text{预算})$ 下：

$$
A^\* = \underset{A}{\arg\min}\; \text{cost}(A) \quad \text{s.t.}\; \text{quality}(A)\ge Q_{\min}
$$

即「满足质量下限的最小成本架构」。

## 四、代码实现（决策表）

```python
def pick_arch(need: dict):
    if need["seq_len"] > 32_000 and need["budget"] == "low":
        return "SSM / 线性递归 (Mamba 类)"
    if need["throughput"] == "high" and need["train_budget"] == "rich":
        return "MoE (Mixtral 类)"
    if need["general"] and need["ecosystem"] == "mature":
        return "Transformer decoder-only + RoPE + GQA"
    return "Transformer (默认)"
```

## 五、与其他技术对比

| 需求 | 首选架构 | 理由 |
|------|---------|------|
| 通用强能力、生态成熟 | Transformer (decoder-only) | 工具链完整 |
| 超长序列、低成本 | Mamba / SSM | 线性复杂度 |
| 高吞吐、预算足 | MoE (Mixtral 类) | 激活少、并行专家 |
| 强外推长上下文 | RoPE + NTK / 滑窗 | 位置编码友好 |
| 端侧小模型 | 小稠密 + 量化 | 部署简单 |

## 六、常见误区

- 认为「新架构一定更好」：Transformer 在生态与质量上仍最稳。
- 忽略推理显存：长上下文下 MHA 的 KV 比参数更致命，GQA/SSM 才解渴。
- MoE 只看到「总参大」却忽略「激活省」，误判成本。
- 脱离团队工程能力选型，新架构踩坑无人填。

## 八、面试题

- 何时该考虑用 SSM 替代 Transformer？关键权衡是什么？
- MoE 的「训练贵、推理省」怎么理解？适合什么团队？
- 长上下文场景下，限制因素更可能是参数还是 KV 缓存？为什么？
- 架构选型应优先看「能力」还是「成本与生态」？

## 九、演进与趋势

架构格局正向「混合」演进：Transformer 主干 + SSM 处理超长、MoE 提效、局部注意力降成本并存（如 Samba 把 Mamba 与 Transformer 融合）。位置编码、注意力稀疏化、以及推理时计算（test-time compute）成为新战场。趋势不是「单一架构取代」，而是「按层/按任务组合异构模块」，并在统一框架（如同化训练栈）下灵活装配。

## 十、小结

架构选型是「在质量下限约束下求最小成本」的工程决策，应围绕任务性质、序列长度、训练/推理预算与生态成熟度四条轴权衡。Transformer（decoder-only + RoPE + GQA）因生态成熟仍是通用首选；超长序列看 SSM、高吞吐看 MoE、强外推看位置编码优化。盲目追新不如匹配约束，未来属于异构组合而非单一取代。
