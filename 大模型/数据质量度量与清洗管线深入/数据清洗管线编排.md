# 数据清洗管线编排

> 对应 HuggingFace datasets（map/filter/缓存与内存映射）、Apache Beam / Dataflow 的大规模数据处理模型，以及 C4（Raffel et al. 2019）、CCNet（Wenzek et al. 2019）、RefinedWeb（Penedo et al. 2023）等公开流水线实践。

## 一、背景与挑战

清洗不是一步，而是十几步的组合：解码与编码归一、语言识别、启发式过滤、去重、质量打分、毒性过滤、隐私遮蔽、分词、打包（packing）与落盘。手工脚本的问题很快暴露：步骤之间有依赖（去重要在质量打分之前还是之后？）、中间结果无法复用（改一个阈值就要重跑全部）、失败后无法续跑、各步淘汰率没有记录因而无法审计、多人协作时配置与代码混在一起难以复现。

工程上的核心诉求因此变成四点：**可重入（幂等）**、**可缓存**、**可并行**、**可观测**。此外还有成本问题：TB 级语料每重跑一次都要花大量机时，所以中间产物必须按内容寻址缓存，使得只改下游步骤时上游不必重算。最后是**顺序的正确性**：顺序不仅影响成本（昂贵步骤应后置），还影响结果（先去重再打分与先打分再去重的保留集合不同）。

## 二、核心原理

把清洗建模为**有向无环图（DAG）**：节点是变换（map/filter/聚合），边是数据依赖。每个节点满足

$$
\text{output}_s = f_s\big( \text{input}_s;\ \theta_s \big)
$$

其中 $\theta_s$ 是该步配置（阈值、模型路径、参数）。节点输出按内容寻址缓存：

$$
\mathrm{key}_s = \mathrm{hash}\big( \mathrm{input\_hash},\ \mathrm{code\_hash}(f_s),\ \mathrm{hash}(\theta_s) \big)
$$

只要三者不变就命中缓存，实现幂等重跑。这是把"脚本"升级为"管线"的关键一步。

**执行顺序的启发式**：
1. 廉价且淘汰率高的步骤前置（编码归一、长度过滤、黑名单），尽快缩减数据规模；
2. 昂贵步骤后置（模型打分、去重），因为输入已变小；
3. 需要全局信息的步骤（跨文档去重）天然成为阶段边界；
4. 语义相互依赖的步骤放在一起（先去重再打分，避免重复文档互相抬高分数）。

**可观测性**：每步记录输入/输出条数、token 数、耗时与淘汰率：

$$
\rho_s = \frac{|\mathrm{input}_s| - |\mathrm{output}_s|}{|\mathrm{input}_s|}
$$

累计保留率为 $\prod_s (1 - \rho_s)$。这些数字既是调试依据，也是合规审计的证据。

**并行模型**：map/filter 类 embarrassingly parallel 步骤按分片并行；全局去重需要 shuffle 与分桶（如 MinHash 分带），按带宽而非 CPU 扩展。

## 三、形式化与数学基础

**吞吐与瓶颈。** 设管线有 $S$ 个步骤，处理 $N$ 条文档，步骤 $s$ 的单条耗时为 $t_s$，并行度为 $P_s$，则该步耗时为

$$
T_s = \frac{N_{s} \, t_s}{P_s} + O_s
$$

其中 $N_s$ 是该步的输入条数，$O_s$ 是固定开销（模型加载、shuffle、落盘）。总耗时

$$
T = \sum_{s=1}^{S} T_s, \qquad \Theta_{\mathrm{e2e}} = \frac{N}{T}
$$

由于 $N_{s+1} = N_s (1 - \rho_s)$，**把高淘汰率的廉价步骤前置**能带来指数级的 $N_s$ 缩减，这是顺序优化的理论依据：

$$
N_S = N_1 \prod_{s=1}^{S-1} (1 - \rho_s)
$$

**Amdahl 与并行上限。** 若某全局步骤（如去重）占比为 $q$ 且难以并行，则加速比上限为

$$
\mathrm{Speedup} \le \frac{1}{q + \frac{1 - q}{P}}
$$

这解释了为什么去重往往成为整条管线的瓶颈。

**成本模型。** 若步骤 $s$ 使用的资源单价为 $c_s$（CPU 核时或 GPU 时），总成本

$$
\mathrm{Cost} = \sum_s c_s \cdot P_s \cdot T_s
$$

优化目标是给定截止时间的成本最小化，通常的解是：GPU 步骤尽量批处理、尽量后置；CPU 步骤高并行。

**幂等与确定性。** 令 $\mathcal{P}$ 为管线，若对任意输入 $X$ 与任意执行次数 $n$ 都有

$$
\mathcal{P}^n(X) = \mathcal{P}(X)
$$

则称其幂等。实现要点是：输出写入临时路径后原子重命名、按内容寻址而非按时间戳命名、所有随机性显式设定种子：

$$
\mathrm{seed}_s = \mathrm{hash}(\mathrm{step\_name}, \mathrm{input\_hash})
$$

**血缘（lineage）。** 每条输出记录保留产生它的输入 ID 与步骤版本集合：

$$
\mathrm{lineage}(d) = \{ (\mathrm{step}_s, \mathrm{ver}_s, \mathrm{cfg\_hash}_s) \}_{s \in \mathrm{path}(d)}
$$

有了血缘，就能回答"这条数据为什么被保留/淘汰"，也可以只重跑受影响的子集。

## 四、代码实现

```python
# 一个最小但可用的 DAG 管线：内容寻址缓存 + 每步淘汰率统计 + 原子写
import hashlib
import json
import os
import time
from dataclasses import dataclass, field

CACHE_DIR = ".pipeline_cache"

@dataclass
class Step:
    name: str
    fn: object                    # 接收 list[dict]，返回 list[dict]
    config: dict = field(default_factory=dict)

def _hash(obj):
    payload = json.dumps(obj, sort_keys=True, ensure_ascii=False, default=str)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:16]

def _atomic_dump(rows, path):
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        for r in rows:
            f.write(json.dumps(r, ensure_ascii=False) + "\n")
    os.replace(tmp, path)         # 原子重命名，保证中断后不留下半截文件

def run_pipeline(rows, steps, verbose=True):
    stats = []
    for st in steps:
        key = _hash({"in": _hash(rows), "cfg": st.config, "name": st.name})
        cache_path = os.path.join(CACHE_DIR, f"{st.name}-{key}.jsonl")
        os.makedirs(CACHE_DIR, exist_ok=True)

        n_in = len(rows)
        t0 = time.time()
        if os.path.exists(cache_path):
            # 命中缓存：直接复用，保证幂等
            with open(cache_path, encoding="utf-8") as f:
                rows = [json.loads(line) for line in f]
            cached = True
        else:
            rows = st.fn(rows, **st.config)
            _atomic_dump(rows, cache_path)
            cached = False
        dt = time.time() - t0

        n_out = len(rows)
        stats.append({
            "step": st.name, "in": n_in, "out": n_out,
            "drop_rate": (n_in - n_out) / max(n_in, 1),
            "seconds": round(dt, 2), "cached": cached,
        })
        if verbose:
            s = stats[-1]
            print(f"{s['step']}: {s['in']} -> {s['out']} "
                  f"(淘汰 {s['drop_rate']:.1%}, {s['seconds']}s, 缓存={s['cached']})")
    return rows, stats
```

```python
# 定义具体步骤：注意顺序——廉价高淘汰的前置，昂贵的后置
def step_normalize(rows):
    import unicodedata
    out = []
    for r in rows:
        r["text"] = unicodedata.normalize("NFKC", r["text"]).strip()
        out.append(r)
    return out

def step_length_filter(rows, min_chars=200, max_chars=200_000):
    return [r for r in rows if min_chars <= len(r["text"]) <= max_chars]

def step_lang_filter(rows, allowed=("zh", "en"), min_conf=0.8):
    # 真实场景替换为 fastText 语言 ID；此处用字段模拟
    return [r for r in rows
            if r.get("lang") in allowed and r.get("lang_conf", 1.0) >= min_conf]

def step_dedup_exact(rows):
    seen, out = set(), []
    for r in rows:
        h = hashlib.sha256(r["text"].encode("utf-8")).hexdigest()
        if h not in seen:
            seen.add(h)
            out.append(r)
    return out

def step_quality_score(rows, min_score=0.3):
    # 昂贵步骤放在最后：此时数据量已被前面的步骤大幅缩减
    return [r for r in rows if r.get("quality", 1.0) >= min_score]

pipeline = [
    Step("normalize", step_normalize, {}),
    Step("length_filter", step_length_filter, {"min_chars": 200}),
    Step("lang_filter", step_lang_filter, {"min_conf": 0.8}),
    Step("dedup_exact", step_dedup_exact, {}),
    Step("quality_score", step_quality_score, {"min_score": 0.3}),
]

clean, stats = run_pipeline(raw_rows, pipeline)
```

```python
from datasets import Dataset

def build(rows):
    ds = Dataset.from_list(rows)
    ds = ds.filter(lambda x: len(x["text"]) >= 200, num_proc=16)
    ds = ds.map(lambda x: {"text": x["text"].strip()}, num_proc=16)
    ds = ds.save_to_disk("clean_corpus")     # 落盘后可直接 load_from_disk
    return ds
```

## 五、与其他技术对比

| 维度 | 线性脚本 | DAG + 缓存编排 | 声明式数据平台（Beam/Spark 一类） |
|------|----------|----------------|-----------------------------------|
| 可重入 | 差（中断即重跑） | 好（按步缓存） | 好 |
| 并行能力 | 需手写 | 中（map/filter 易并行） | 强（自动分片与 shuffle） |
| 全局操作（去重） | 困难 | 需显式设计 | 原生支持 |
| 可观测性 | 靠 print | 结构化统计 | 完整指标与血缘 |
| 迭代成本 | 高 | 低（只重跑受影响步） | 低 |
| 学习与运维成本 | 低 | 中 | 高 |
| 适用规模 | GB 级 | 百 GB ~ TB 级 | TB 以上 |

| 顺序策略 | 总成本 | 风险 |
|----------|--------|------|
| 昂贵步骤前置 | 高 | 无额外风险，只是浪费 |
| 廉价高淘汰步骤前置 | 低 | 需确认前置规则不会误杀 |
| 先去重再打分 | 中 | 重复文档不会互相抬高分数 |
| 先打分再去重 | 中高 | 重复内容易获高分，浪费预算 |

## 六、常见误区

- **步骤顺序随意**：把模型打分放在最前面，会让 90% 的算力花在随后会被丢弃的数据上。
- **没有缓存键或键不完整**：只按文件名缓存，改了阈值却命中旧结果，导致实验不可复现。
- **非原子写**：中断后留下半截文件，被下游当作完整输入，产生难以排查的静默错误。
- **不记录淘汰率**：出现异常（某步淘汰 99%）时无法定位，也无法向合规部门证明处理过程。
- **随机性未定种子**：去重采样或分桶带随机性，导致每次结果不同，无法复现。
- **忽略全局步骤的通信瓶颈**：去重需要 shuffle，网络带宽往往先于 CPU 打满。
- **把配置写死在代码里**：阈值散落各处，无法做配置化实验与版本管理。

## 七、与开源书·权威来源对应

- Raffel et al. 2019《Exploring the Limits of Transfer Learning》（C4）：展示了多步串联清洗的 canonical 流程（去重、语言、长度、脏词）。
- Wenzek et al. 2019《CCNet》：分片 + 困惑度分桶的流水线设计，是"按阶段处理"的典型范例。
- Penedo et al. 2023《The RefinedWeb Dataset》：大规模网页过滤的工程细节与消融，说明每一步的取舍都有实测依据。
- HuggingFace datasets 文档：`map` / `filter` / `save_to_disk` 的缓存机制与内存映射，是单机管线编排的实践基础。
- Apache Beam 编程模型：`PCollection` 与 `PTransform` 的 DAG 抽象，以及"每一步都应有明确输入输出"的工程理念。
- Dean & Ghemawat 2004/2008（MapReduce / Bigtable 相关）：大规模数据处理中"廉价过滤前置、昂贵计算后置"与分而治之的思想源头。
- OWASP LLM Top 10 与数据治理实践：说明管线需要保留处理记录（血缘与淘汰率）以满足审计要求。

## 九、演进与趋势

编排形态从"shell 脚本 + 临时文件"演进到"带缓存的 DAG"，再到"声明式数据平台与血缘追踪"。趋势上，一是**声明式化**：只描述"要什么"，由引擎决定执行计划与并行度；二是**血缘与数据卡片成为标配**，每个数据集附带处理记录、维度分布与许可信息；三是**增量与流式处理**，新数据只需跑受影响分片而非全量重跑；四是**成本可观测**，把每个步骤的机时与碳/费用成本纳入指标；五是**与训练闭环**：管线的配比输出直接对接训练的数据加载器，支持在线调整域权重。

## 十、小结

数据清洗管线化的本质，是把"一次性脚本"变成"可重入、可缓存、可并行、可审计的系统"。四个抓手是：用 DAG 表达依赖、用内容寻址缓存实现幂等、用每步淘汰率实现可观测、用廉价前置昂贵后置的顺序控制成本。落地时先在小样本上跑通全链路并核对每步淘汰率，再放大到全量；所有随机性显式设种子，所有输出原子落盘。
