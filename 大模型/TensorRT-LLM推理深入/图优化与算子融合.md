# 图优化与算子融合

> 对应 NVIDIA/TensorRT-LLM 图优化器，以及 Dao 2022《FlashAttention》、Shazeer 2020《GLU》等算子与激活研究。

## 一、背景与挑战

Transformer 层由大量小算子组成：LayerNorm/RMSNorm、SiLU/GELU、矩阵乘、逐元素偏置与残差加。PyTorch eager 下每个算子单独启动 CUDA kernel，内核启动开销（launch latency）与中间张量显存读写（HBM traffic）主导延迟，尤其对小 batch/短序列。图优化把多个算子融合为单 kernel，搬运到编译期。

挑战：(1) 融合需语义等价；(2) 算子顺序/布局影响可融合性；(3) 过小算子融合收益有限，需启发式决策。

## 二、核心原理

TRT-LLM builder 在构建期做：算子融合（如 RMSNorm+MatMul、GLU 融合、Bias+Add）、常量折叠（把固定子图算成常量）、布局优化（NHWC/张量核心友好格式）、层内/层间融合。融合后单次 kernel 遍历完成多步计算，中间结果留在寄存器/共享内存，减少 HBM 往返。

激活原语如 GLU（门控线性单元）在 LLaMA 等模型中广泛使用：把两个投影门控相乘，是融合重点。注意力则走 FlashAttention 插件（IO 感知、不分块物化）。

构建器的融合决策由「融合可行性加收益启发式」驱动：只有当相邻算子具有相同张量形状与布局、且融合后寄存器/共享内存足够时才会融合。过小或低频算子融合后 kernel 启动省下的时间不如额外编译复杂度，构建器会选择跳过。因此「融合总有益」是误区，真正收益来自减少 HBM 往返而非减少 kernel 数本身。对注意力这类非平凡算子，TRT-LLM 直接用 FlashAttention 插件而非朴素融合，因为它需要在线 softmax 与分块读写，普通 element-wise 融合表达不了。理解哪些该手写 plugin、哪些交给构建器，是性能调优的关键。此外，常量折叠把固定子图（如位置编码的三角函数表）在构建期算成常量并内联，消除运行期重复计算；布局优化把激活排成张量核心友好的形态（如 swizzle），避免运行期 transpose 的额外读写。这些优化叠加，才使 TRT-LLM 在短序列、小 batch 下也能打满算力。

融合的收益本质是提升「算术强度」：把更多 FLOPs 塞进每次 HBM 读写之间，让计算单元不饿肚子。
RMSNorm 与 QKV 投影融合后，归一化结果不必写回显存再读，直接在寄存器里喂给矩阵乘。
GLU 的两个投影与 silu 门控融合，省掉了中间激活张量的物化与两次 kernel 启动。
常量折叠把固定子图（如位置编码的三角函数表）在构建期算成常量并内联，消除运行期重复计算。
布局优化把激活排成张量核心友好的形态（如 swizzle），避免运行期 transpose 的额外读写。
这些优化叠加，使 TRT-LLM 在短序列、小 batch 下也能打满算力，而非被访存拖垮。
对注意力这类非平凡算子，TRT-LLM 直接用 FlashAttention 插件而非朴素融合，因为它需要在线 softmax 与分块读写。
构建器对「是否融合」做收益评估：过小或低频算子融合后省下的启动时间不如额外编译复杂度，会跳过。
因此调优时不应盲目追求融合数量，而应看 Nsight 时间线里是否仍有大量细小 kernel。
理解哪些该手写 plugin、哪些交给构建器，是性能调优的关键能力。
强类型模式下融合更稳定，因为精度契约明确，构建器敢于做跨算子重排。
融合还可能改变浮点累加顺序，FP16 下需与 PyTorch 参考实现对拍，确认误差在可接受范围。

## 三、形式化与数学基础

GLU 门控：

$$\mathrm{GLU}(x) = (xW_1) \otimes \mathrm{silu}(xW_2), \quad \mathrm{silu}(z) = z \otimes \sigma(z)$$

未融合需 2 次 GEMM + 1 次 silu + 1 次逐元素乘，各产生 HBM 读写；融合后在单一 kernel 内流式计算：

$$\text{fused}(x) = \mathrm{MatMul}(x, [W_1;W_2]) \text{ 后门控}$$

算术强度（arithmetic intensity）提升：

$$I = \frac{\text{FLOPs}}{\text{bytes}} \uparrow \Rightarrow \text{更贴近计算受限}$$

RMSNorm 融合：$y = x / \sqrt{\mathrm{mean}(x^2)+\epsilon} \cdot \gamma$，与后续 QKV 投影合并，省一次归约结果的 HBM 写回。

## 四、代码实现

用 functional 层表达可融合原语（概念性）：

```python
import tensorrt_llm.functional as F

# 融合 RMSNorm + QKV 投影（归约与矩阵乘在同一内核完成）
hidden = F.rmsnorm(x, weight=norm_w, eps=1e-6)
qkv = F.matmul(hidden, w_qkv)        # 实际由 builder 进一步融合
# GLU 融合：一步产出门控结果
gate = F.silu(F.matmul(x, w_gate))
up = F.matmul(x, w_up)
h = gate * up
```

注意：融合是否生效取决于 builder 的优化档（builder_flag），开启相应 plugin 才能稳定触发；并非所有组合都可融合。

## 六、常见误区

- 认为融合总有益：过小/低频算子融合收益有限，需构建器启发式决定。
- 忽视精度：融合改变累加顺序，FP16 下可能有微小数值差。
- 过度手动融合：应交给 builder，手写 plugin 易错且难维护。
- 混淆布局优化与融合：二者互补但独立。

## 九、演进与趋势

自动 kernel 生成（CUTLASS、模板库）让融合更通用，支持更多激活与布局；强类型（strongly-typed）构建减少精度歧义。具体以官方最新文档为准。

## 十、小结

图优化与算子融合是 TRT-LLM 性能根基，把 Python/框架开销转移到编译期，靠减少内核启动与 HBM 读写提升算术强度，是低延迟推理的前提。
