LLM 推理成本高，是落地最大门槛。推理优化本质是围绕"算力"与"显存带宽"两个瓶颈做文章。本文拆解成本来源、量化、KV-Cache、批处理、框架选型、投机解码、蒸馏与成本治理，帮助把模型跑得又快又省。

## 一、推理成本从哪来

LLM 推理成本 ≈ 参数量 × 层数 × 序列长度 × (访存 + 计算)。两大瓶颈：

- **计算受限（Compute-bound）**：大 batch、长序列，算力吃满（矩阵乘 GEMM）。
- **访存受限（Memory-bound）**：小 batch、decode 阶段逐 token 生成，瓶颈在显存带宽（每 token 都要把权重从 HBM 读一遍）。

> decode 阶段是典型的 memory-bound：GPU 算力闲置，等着从 HBM 搬运权重。**量化主要解决访存瓶颈**；提升算力利用率靠批处理与并行。

## 二、量化（Quantization）

| 精度 | 比特 | 显存(7B, 含开销) | 相对质量 |
|------|------|--------------|----------|
| FP16 | 16 | ~14 GB | 基准 |
| INT8 | 8 | ~7 GB | 几乎无损 |
| INT4 | 4 | ~3.5 GB | 轻微下降 |
| GPTQ | 4 | ~3.5~4 GB | 校准后接近 FP16 |
| AWQ | 4 | ~3.5~4 GB | 通常优于 GPTQ |

- **GPTQ**：基于二阶信息（Hessian）逐层量化，需校准集（代表性样本），压缩率高。
- **AWQ（Activation-aware Weight Quantization）**：保护"重要权重"（占 1% 的权重决定多数精度），通常比 GPTQ 更稳。
- **KV-Cache 量化**：把 KV 缓存从 FP16 压到 INT8/INT4，长上下文省显存明显（KV 随序列长度线性增长）。
- **GPTQ vs AWQ**：AWQ 更鲁棒、对校准集不敏感；GPTQ 压缩更狠但需好校准集。
- 量化不是越狠越好：过度（2-bit）质量崩塌，需在校准集/任务集上验证指标。

```bash
# 常用工具链
llama.cpp  --quantize q4_K_m model.gguf          # GGUF 量化
python -m awq.entry --model path --w_bit 4       # AWQ 量化
python -m gptq --model path --bits 4 --calib data # GPTQ 量化
```

## 三、KV-Cache 优化

- **PagedAttention（vLLM）**：像操作系统分页一样管理 KV，减少碎片，吞吐提升数倍（KV 块按需分配、可共享）。
- **KV 量化 + 稀疏**：长对话显存大户（KV 随序列长度线性增长）。
- **MQA / GQA**：多查询/分组查询注意力，K/V 头数减少，KV 显存与计算双降（Llama2/3、Mistral 采用 GQA）。
- **Prefix Cache**：多轮对话/共享系统提示时复用前缀 KV，避免重复计算（多数厂商缓存命中打折）。
- 详见 [长上下文与KV-Cache优化](../上下文工程/04-长上下文与KV-Cache优化.md)。

## 四、连续批处理（Continuous Batching）

- 传统 static batching：等 batch 满才推理，短请求被长请求拖住，GPU 利用率低、排队延迟高。
- **连续批处理**：请求完成立即腾出位置，新请求随时插入，GPU 利用率大幅提升（decode 阶段尤其明显）。
- 代表：vLLM、TGI、TensorRT-LLM。这是高并发服务必开能力。
- 配合 **chunked prefill**（prefill 也分块并入批），降低长 prompt 的排队头阻塞。

## 五、推理框架选型

| 框架 | 特点 | 适用 |
|------|------|------|
| vLLM | PagedAttention、连续批处理、吞吐高、生态好 | 通用高并发服务 |
| TensorRT-LLM | NVIDIA 极致优化（融合/量化） | 纯 N 卡生产、追求极致 |
| SGLang | 结构化生成优化（JSON 约束）、RadixAttention | 复杂 Agent/JSON 输出 |
| llama.cpp | CPU/GPU 通吃，GGUF，量化全 | 端侧/本地/消费级 |
| Ollama | 基于 llama.cpp，极简易用 | 本地开发 |
| LMDeploy | Turbomind 引擎，高吞吐 | 企业部署 |

## 六、投机解码（Speculative Decoding）

- 用小草稿模型一次猜多个 token，大模型并行验证，命中则跳过多步。
- **不损失质量**（验证保证与自回归结果一致），延迟可降 2~3 倍。
- 尤其适合大模型自回归慢、草稿模型便宜的场景。
- 变体：**自投机**（同模型浅层）、**Medusa**（多头并行预测）、**EAGLE**（特征级）。

## 七、并行与分布式推理

| 维度 | 方法 | 说明 |
|------|------|------|
| 张量并行 TP | 单层权重切多卡 | 单请求低延迟，通信密集 |
| 流水线并行 PP | 层切多卡 | 大模型，有 bubble |
| 数据并行 DP | 多副本 | 高吞吐，单请求不加速 |
| 序列并行 SP | 长序列切分 | 超长上下文 |

- 单卡放不下大模型 → 张量+流水线并行（如 70B 用 2~4 卡 TP）。
- 通信是瓶颈：NVLink > 网卡；跨机需 InfiniBand。

## 八、蒸馏与小型化

- **知识蒸馏**：大模型教小模型，保留大部分能力（如 DeepSeek 蒸馏系列、DistilBERT）。
- **MoE（混合专家）**：总参大但每 token 激活少，推理便宜（Mixtral、Qwen-MoE、DeepSeek-MoE）。
- **模型剪枝**：去掉冗余连接/头，配合量化进一步压缩（需微调恢复精度）。
- **小模型崛起**：7B/14B 经 SFT + 蒸馏，可覆盖大量业务任务，成本降一个数量级。

## 九、服务化与弹性

- 用 **Triton / Ray Serve / KServe / vLLM server** 做多模型路由、动态批处理、自动扩缩。
- 显存不够时做 **offload**（权重放 CPU/NVMe，按需搬，牺牲延迟换容量）。
- **批处理窗口**（10~50ms）平衡延迟与吞吐：窗口越大吞吐越高、延迟越大。
- 多副本 + 负载均衡，按请求量弹性扩缩（HPA / K8s）。
- **预填充/解码分离**（SplitFuse/DistServe）：prefill 与 decode 异构部署，提升整体吞吐。

## 十、成本治理

- **模型路由**：小任务用 7B/14B，复杂任务才上 70B 或调用闭源（按难度分流）。
- **语义缓存**：相同/相似 prompt 命中缓存（如 GPTCache），省一次推理。
- **请求合并**：批量/流式，减少固定开销。
- **监控**：P99 延迟、每千 token 成本、GPU 利用率、队列长度，设预算告警。
- **量化+缓存+路由**三者叠加，常能把成本降 5~10 倍。

## 十一、常见坑

- **量化过度（2-bit）** → 质量崩塌，需在校准/任务集上验证。
- **忽略 KV-Cache 显存** → 长上下文 OOM（KV 随长度线性增长）。
- **单请求串行（无连续批）** → GPU 利用率低，改连续批处理。
- **不做 Prefix Cache** → 多轮对话重复算系统提示，浪费。
- **盲目上大框架** → 小流量用 Ollama/llama.cpp 更省心。
- **并行通信瓶颈** → 跨机无 IB，TP 反而更慢（评估网络再选并行度）。
- **忽略批处理窗口** → 延迟/吞吐失衡（按 SLA 调窗口）。
