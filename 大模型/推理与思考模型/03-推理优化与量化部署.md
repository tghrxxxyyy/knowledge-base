# 推理优化与量化部署

> 板块：大模型 / 推理与思考模型 　|　 返回：[README](README.md)

LLM 推理成本高，是落地最大门槛。推理优化本质是围绕"算力"与"显存带宽"两个瓶颈做文章。本文拆解成本来源、量化、KV-Cache、批处理、框架选型与成本治理，帮助把模型跑得又快又省。

## 一、推理成本从哪来

LLM 推理成本 ≈ 参数量 × 层数 × 序列长度 × (访存 + 计算)。两大瓶颈：

- **计算受限（Compute-bound）**：大 batch、长序列，算力吃满（矩阵乘）。
- **访存受限（Memory-bound）**：小 batch、decode 阶段逐 token 生成，瓶颈在显存带宽（每 token 都要读一遍权重）。

> decode 阶段是典型的 memory-bound：GPU 算力闲置，等着从 HBM 搬运权重。**量化主要解决访存瓶颈**。

## 二、量化（Quantization）

| 精度 | 比特 | 显存占用(7B) | 质量 |
|------|------|--------------|------|
| FP16 | 16 | 14 GB | 基准 |
| INT8 | 8 | 7 GB | 几乎无损 |
| INT4 | 4 | 3.5 GB | 轻微下降 |
| GPTQ/ AWQ | 4 | 3.5~4 GB | 经校准接近 FP16 |

- **GPTQ**：基于二阶信息逐层量化，需校准集（代表性样本）。
- **AWQ**：激活感知，保护重要权重（占 1% 的权重决定多数精度），通常比 GPTQ 更稳。
- **KV-Cache 量化**：把 KV 缓存从 FP16 压到 INT8/INT4，长上下文省显存明显。
- 量化不是越狠越好：过度（2-bit）质量崩塌，需在校准集上验证任务指标。

```bash
# 常用工具链
llama.cpp  --quantize q4_K_m model.gguf      # GGUF 量化
python -m awq.entry --model path --w_bit 4    # AWQ 量化
```

## 三、KV-Cache 优化

- **PagedAttention（vLLM）**：像操作系统分页一样管理 KV，减少碎片，吞吐提升数倍。
- **KV 量化 + 稀疏**：长对话显存大户（KV 随序列长度线性增长）。
- **MQA / GQA**：多查询/分组查询注意力，K/V 头数减少，KV 显存与计算双降（Llama2/3 采用 GQA）。
- **Prefix Cache**：多轮对话/共享系统提示时复用前缀 KV，避免重复计算。

## 四、连续批处理（Continuous Batching）

- 传统 static batching：等 batch 满才推理，短请求被长请求拖住，GPU 利用率低。
- 连续批处理：请求完成立即腾出位置，新请求随时插入，GPU 利用率大幅提升。
- 代表：vLLM、TGI、TensorRT-LLM。这是高并发服务必开能力。

## 五、推理框架选型

| 框架 | 特点 | 适用 |
|------|------|------|
| vLLM | PagedAttention，吞吐高，生态好 | 通用高并发 |
| TensorRT-LLM | NVIDIA 极致优化 | 纯 N 卡生产 |
| llama.cpp | CPU/GPU 通吃，GGUF | 端侧/本地 |
| Ollama | 基于 llama.cpp，易用 | 本地开发 |
| SGLang | 结构化生成优化 | 复杂 Agent/JSON 输出 |

## 六、投机解码（Speculative Decoding）

- 用小草稿模型一次猜多个 token，大模型并行验证，命中则跳过多步。
- **不损失质量**（验证保证与自回归一致），延迟可降 2~3 倍。
- 尤其适合大模型自回归慢、草稿模型便宜的场景。
- 变体：自投机（同模型浅层）、Medusa（多头并行预测）。

## 七、蒸馏与小型化

- **知识蒸馏**：大模型教小模型，保留大部分能力（如 DeepSeek 蒸馏系列）。
- **MoE（混合专家）**：总参大但每 token 激活少，推理便宜（如 Mixtral、Qwen-MoE）。
- **模型剪枝**：去掉冗余连接，配合量化进一步压缩。

## 八、服务化与弹性

- 用 Triton / Ray Serve / KServe 做多模型路由、动态批处理。
- 显存不够时做 offload（权重放 CPU/NVMe，按需搬）。
- 批处理窗口（10~50ms）平衡延迟与吞吐（窗口越大吞吐越高、延迟越大）。
- 多副本 + 负载均衡，按请求量弹性扩缩。

## 九、成本治理

- 小任务用 7B/14B，复杂任务才上 70B 或调用闭源（routing 按难度分流）。
- 路由（router）避免大材小用（简单分类不用 70B）。
- 缓存：相同/相似 prompt 命中缓存（语义缓存），省一次推理。
- 监控 P99 延迟与每千 token 成本，设预算告警。

## 十、常见坑

- **量化过度（2-bit）** → 质量崩塌，需在校准集上验证。
- **忽略 KV-Cache 显存** → 长上下文 OOM（KV 随长度线性增长）。
- **单请求串行** → GPU 利用率低，改连续批处理。
- **不做 Prefix Cache** → 多轮对话重复算系统提示，浪费。
- **盲目上大框架** → 小流量用 Ollama/llama.cpp 更省心。

## 十一、落地清单

1. 选框架（vLLM 起步，多 N 卡考虑 TRT-LLM）。
2. 量化到 INT4/AWQ 压显存。
3. 开 PagedAttention + 连续批处理。
4. 长上下文开 KV 量化 + Prefix Cache。
5. 加路由 + 缓存 + 成本监控。
