# 流式生成原理

> 官方参考：OpenAI Streaming 指南（platform.openai.com/docs/api-reference/streaming）｜ 仓库：https://github.com/vllm-project/vllm ｜ 入门书：datawhale《llm-universe》部署章 ｜ 规范：HTML SSE 标准（html.spec.whatwg.org/multipage/server-sent-events.html）

## 一、背景与挑战

用过 ChatGPT 的人都熟悉那种“文字一个一个蹦出来”的体验。可如果你自己调 API，默认往往是**一次性返回**：模型把 800 字全部生成完，接口才把整段结果丢给你。于是前端出现这样的惨状——转圈 20 秒，页面毫无反应，用户怀疑是不是死了，甚至点了刷新重发。

问题的本质是：大模型生成是**逐 token 串行**的，一个几百字的回答可能要几秒到几十秒，但用户对“开始动”的耐心只有 1–2 秒（参考首屏响应的 3 秒法则）。挑战有三个：

1. **体感问题**：总耗时一样，但“干等 20 秒”和“1 秒就开始出字”是两种产品。
2. **协议问题**：HTTP 一问一答，怎么在一次请求里“分多次”把数据推给前端？
3. **工程问题**：连接中途断了怎么办？用户点了停止怎么取消后端生成？长答案怎么防止被中间层（反向代理、网关）缓冲住？

流式生成（Streaming）就是对这三个问题的系统性回答。

## 二、核心原理

### 逐 token 产出

模型解码是循环进行的：每步预测出一个 token → 追加到序列 → 再喂回去预测下一个。流式只是把这个循环的**中间结果立刻往外送**，而不是等循环结束。

### SSE：最主流的传输方式

HTTP 无法“推送”，所以借用了长连接 + 分块的思想。目前事实标准是 **SSE（Server-Sent Events，服务器发送事件）**，它基于 HTTP/1.1 的分块传输（Transfer-Encoding: chunked）：

- 响应头是 `Content-Type: text/event-stream`；
- 服务端每生成一个 token，就写一行 `data: {"token":"你"}\n\n`（两个换行是事件分隔符）；
- 每个 `data:` 块是一个独立 chunk，浏览器的 `EventSource` 或 fetch 读取流会逐块触发回调；
- 生成结束时发 `data: [DONE]`，双方关闭连接。

一次请求/一次响应，数据像水管一样持续流出来——这就是“服务器推送事件”的含义。WebSocket 也能做，但它是全双工协议、实现更重；问答场景只需服务器→客户端单向流，SSE 更简单，且天然走 HTTP，容易穿过代理和 CDN。

### 为什么体验更好（打字机效果）

用一个比喻：**流式像是先端上来一盘盘菜，非流式是要等满汉全席全做完才开席**。首字延迟（TTFT, Time To First Token）从“总耗时”降到了“首 token 耗时”，通常只有几百毫秒到一两秒。前端拿到第一个字就开始增量渲染，配合 CSS 的光标闪烁动画，就得到打字机效果——用户在心理上从“等待者”变成了“阅读者”，可感知的等待被阅读时间覆盖掉了。

### 中断与断连

流式还带来一个自然能力：**随时可停**。因为是分块发送，服务端在任意 token 边界都能优雅收尾（保存已生成部分、释放 GPU）。客户端关掉连接（AbortController / 断网）时，服务端通过 `write()` 返回失败感知断连，应当立刻终止解码循环，避免白烧 GPU。反过来，非流式方案想实现“停止生成”，就只能靠超时或硬杀进程，粗暴得多。

## 三、要点形式化

- 体感延迟 ≈ **TTFT（首字延迟）**，而总耗时 ≈ TTFT + 其余 token 生成时间之和。流式改变的是前者，不是后者。
- 吞吐指标 `tokens/s` 不变时，显示速度 = tokens/s，肉眼大约 15–30 字/秒就很流畅。
- 非流式首字延迟 ≈ 总耗时；流式首字延迟 ≈ 首 token 耗时。**流式优化的是延迟感知，不是算力。**

## 四、代码实现（操作步骤）

### 1. 服务端：FastAPI 用 SSE 返回流

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import openai, json

app = FastAPI()

def event_stream(prompt: str):
    # stream=True：SDK 每收到一个 token 就 yield 一次
    resp = openai.ChatCompletion.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        stream=True,
    )
    for chunk in resp:
        delta = chunk["choices"][0]["delta"].get("content", "")
        if delta:
            # SSE 格式：data: xxx\n\n
            yield f"data: {json.dumps({'t': delta}, ensure_ascii=False)}\n\n"
    yield "data: [DONE]\n\n"

@app.post("/chat")
def chat(prompt: str):
    return StreamingResponse(
        event_stream(prompt),
        media_type="text/event-stream",   # 关键：声明为事件流
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

> 中文注释里的两个坑：`X-Accel-Buffering: no` 是为了关掉 nginx 等反代的缓冲，否则数据仍会被攒着一次发出；`no-cache` 防止中间层缓存。

### 2. 客户端：fetch 读取可读流并打字机渲染

```javascript
const res = await fetch("/chat?prompt=你好", { method: "POST" });
const reader = res.body.getReader();        // 拿到可读流
const decoder = new TextDecoder();
const box = document.getElementById("out");

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value);       // 解析每个 data: 块
  for (const line of text.split("\n")) {
    if (line.startsWith("data: ") && line !== "data: [DONE]") {
      box.textContent += JSON.parse(line.slice(6)).t;  // 增量追加
    }
  }
}
```

### 3. 中断：点击“停止”即取消

```javascript
const ctrl = new AbortController();
fetch(url, { signal: ctrl.signal });   // 用户点停止
// ctrl.abort() 会关闭连接，服务端 write 失败后应中止生成
```

## 五、与其他方案对比

| 方案 | 首字延迟 | 实现复杂度 | 中断能力 | 适用场景 |
|------|---------|-----------|---------|---------|
| 一次性返回 | 高（≈总耗时） | 最低 | 差（只能杀请求） | 批处理、离线任务 |
| SSE 流式 | 低 | 中 | 好（关连接即可） | 聊天、写作、客服 |
| WebSocket | 低 | 高（全双工、自定义协议） | 好 | 游戏、语音、双向实时 |
| 轮询 | 中 | 低但浪费 | 一般 | 旧系统兼容 |

绝大多数问答类应用选 **SSE**：够快、够简单、穿透性好。

## 六、常见误区

1. **“流式让生成变快了”**：错。总 token 数和算力不变，总耗时几乎一样，流式只把“体感首字延迟”大幅缩短。
2. **忘了关反向代理缓冲**：本地测试正常，上线后 nginx 把 chunks 攒到结束才发，看起来像“流式失效”。加 `X-Accel-Buffering: no` 并检查代理配置。
3. **一个 chunk 就是一个 token**：不一定。服务端可能合并/拆分（还可能按 UTF-8 字节截断），客户端必须用 `TextDecoder` 处理跨包的多字节中文，否则出现乱码。
4. **流式期间不做错误处理**：中途模型报错、超限怎么办？要在流内发一个 `event: error`，前端据此提示，而不是让用户干等。
5. **认为流式一定省钱**：流式不改变计费 token 数；只有配合“限制 max_tokens、停止生成”才省钱。

## 八、面试题/上手题

1. **SSE 和 WebSocket 的区别，问答场景为什么优先 SSE？** 要点：SSE 基于 HTTP 单向推送、实现简单、易过代理；WebSocket 全双工更重；问答只需服务器下行流。
2. **流式能降低 TTFT 吗？** 要点：能——TTFT 从“整段生成完”变为“首 token 生成完”，这是流式的核心价值；但它不降低总耗时。
3. **为什么 `text/event-stream` 的事件以两个换行结尾？** 要点：SSE 规范用空行分隔事件，客户端据此切分边界。
4. **动手题：用 fetch 把一次流式回答逐字打印在页面上，并加一个“停止”按钮。** 要点：reader.read() 循环、TextDecoder 解码、AbortController 中断。

## 九、演进与趋势

流式本身已相当成熟，但边界在扩展：**一是结构化流式**——边生成边输出 JSON 片段，前端流式渲染表格与图表（如 Vercel AI SDK 的 StreamUI）；**二是语音+文字双流**，TTS 跟随文字增量合成，实现“边想边说”；**三是流式与推理引擎深度协同**——vLLM、SGLang 等把连续批处理（continuous batching）和流式结合，在高并发下仍保证低 TTFT；**四是 token 级计费与超时治理**成为网关标配。入门者的关注点可以放在：把 TTFT 和 tokens/s 两个指标纳入监控，因为它们直接决定产品体感。

## 十、小结

流式生成的全部要义可以压缩成三句话：**模型本来就是一个 token 一个 token 吐的；流式只是把吐出来的过程立刻转发给你；因此首字延迟大降、总耗时不降**。工程上要过三关——服务端用 SSE 分块发送并关掉代理缓冲，客户端用可读流+解码器做增量渲染，再用连接中断实现随时停止。掌握这条链路，你就理解了所有聊天产品“打字机”背后的机制，也踩过了新手最常踩的缓冲与解码坑。
