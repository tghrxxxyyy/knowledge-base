# 检查点聚合与加载

> 对应 Rajbhandari 2020 ZeRO、Zhao 2023 FSDP 与 pytorch/pytorch state_dict 文档。

## 一、背景与挑战
分片检查点（sharded checkpoint）把参数与优化器状态按 rank 切分保存，利于并行写入，但不便于推理、微调或跨框架迁移。
推理与微调通常期望一个完整的、标准的 `state_dict`，能被 `from_pretrained` 或普通 `load_state_dict` 直接消费。
于是需要一个中间步骤：把分散在各分片中的张量按参数名还原为全局布局，拼接成完整权重。这一步就是检查点聚合。
核心挑战在于：分片方式是框架特定的（ZeRO 的扁平化分区、FSDP 的 DTensor 分片），对齐规则不同，聚合逻辑不能通用；聚合过程还受显存与带宽限制，不能简单全部读入。
此外，聚合产物的精度、命名与格式必须与目标加载器的预期一致，否则会出现 key 不匹配或 dtype 不符。

## 二、核心原理
聚合的本质是「按参数名分组 → 按分片元数据排序 → 沿分片维拼接」。每个参数在保存时记录了它在哪些分片、位于分片的哪个区间。
ZeRO-3 把参数扁平化后按 rank 均分，聚合时需要按保存的顺序把各 rank 的扁平分片拼回原始张量，再按参数边界切分命名。
FSDP 用 DTensor 描述分片布局，可通过 `summon_full_params` 在内存中临时还原完整参数，或用分片读取 API 按需加载。
DeepSpeed 提供离线脚本把 ZeRO 检查点重组为 fp32/fp16 的完整 `state_dict`，产物可直接被 `transformers` 等加载。
关键取舍是「离线重组」与「在线按需」：离线重组一次性产出标准权重、简单通用；在线按需省显存、适合超大模型但依赖框架支持。

## 三、形式化与数学基础
设参数张量 $W$ 被切成 $N$ 个分片，聚合即沿分片维拼接：

$$ W = \mathrm{concat}\big(W^{(1)}, W^{(2)}, \dots, W^{(N)},\, \text{axis} = \text{shard}\big) $$

若各 rank 保存的是扁平化后的偏移区间，则需要用参数边界 $[o_i, o_i + s_i)$ 从扁平缓冲中切出：

$$ W_i = \mathrm{flat}[\,o_i : o_i + s_i\,] \;\Rightarrow\; \mathrm{reshape}(W_i, \text{shape}_i) $$

聚合后只保留参数（丢弃优化器状态），检查点体积近似从训练态降为推理态。以混合精度 Adam 为例，训练态常需约 $K\Psi$ 量级（$\Psi$ 为参数个数，$K$ 含梯度、动量、方差等副本），推理态只需约 2 字节/参数：

$$ M_{train} \approx K\Psi \;\gg\; M_{infer} \approx 2\Psi \;(\text{fp16}) $$

因此聚合的另一个收益是体积大幅下降，便于分发与部署。

## 四、代码实现
```python
# DeepSpeed：把 ZeRO 分片检查点重组为标准 fp32 权重
from deepspeed.utils.zero_to_fp32 import (
    convert_zero_checkpoint_to_fp32_state_dict,
)

convert_zero_checkpoint_to_fp32_state_dict(
    "ckpt_z3",                 # 分片检查点目录
    "pytorch_model.bin",       # 输出完整权重
    tag="latest",
)

# 之后可用 transformers 直接加载
from transformers import AutoModelForCausalLM
model = AutoModelForCausalLM.from_pretrained(
    "output_dir", state_dict="pytorch_model.bin"
)

# FSDP：在线聚合完整参数（仅在小模型或必要时使用，注意显存峰值）
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

with FSDP.summon_full_params(model, writeback=False):
    full_state = {k: v.detach().cpu() for k, v in model.state_dict().items()}
```

## 五、与其他技术对比
| 方式 | 产物 | 显存峰值 | 适用 |
|---|---|---|---|
| 离线脚本重组 | 完整 state_dict | 单机 CPU 内存 | 训练后交付、部署 |
| `summon_full_params` | 完整参数视图 | 高（全参入显存） | 小模型、在线检查 |
| 分片读取 API | 按需加载分片 | 低 | 超大模型、续训 |
| 直接加载分片 | 分片态 | 低 | 同框架续训 |
| safetensors 分片 | 标准分片文件 | 低 | 高效分发与加载 |

## 六、常见误区
- 重组后保留优化器状态：推理不需要，通常只取参数，保留会白白增大体积。
- 认为分片可直接 `load_state_dict`：分片格式与标准 state_dict 不同，需先重组或用框架的分片读取 API。
- 名称对齐随意：聚合需按参数名精确匹配，key 不一致会导致加载失败或静默错位。
- 忽视 dtype：聚合常输出 fp32，而部署可能用 fp16/bf16，转换时机与误差需注意。
- 在线聚合时忽略显存峰值：`summon_full_params` 会把完整参数放入显存，大模型上可能 OOM。

## 八、面试题
1. 问：如何从分片检查点得到推理权重？
   答：按参数名与分片元数据重组为完整 fp16/fp32 state_dict，或用框架的分片读取 API。
2. 问：优化器状态去哪了？
   答：推理不需要，通常丢弃，仅保留参数，体积因此大幅下降。
3. 问：离线重组与在线聚合如何取舍？
   答：离线产物通用、简单；在线省显存、适合超大模型，但依赖框架支持。
4. 问：聚合时最容易出错的地方？
   答：参数名对齐、分片维顺序与 dtype 转换，任一错位都会导致权重错误。
5. 问：为什么大模型不适合全量在线聚合？
   答：完整参数会带来显存峰值，超过单卡容量时需按需加载或分块处理。

## 九、演进与趋势
- 格式标准化（如 safetensors）加速加载并提升安全性。
- 分片直读与流式加载避免显式重组步骤，降低内存占用。
- 分布式检查点（DCP）统一分片描述，简化跨并行策略的聚合。
- 具体接口与行为以官方最新文档为准。

## 十、小结
聚合检查点是分片保存与单卡使用之间的桥梁：它按参数名与分片元数据还原全局权重，丢弃优化器状态以获得体积收益。工具链成熟但须注意 key、形状与 dtype 三方面的兼容，否则聚合产物无法被正确加载。
