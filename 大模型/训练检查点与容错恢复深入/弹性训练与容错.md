# 弹性训练与容错

> 对应 pytorch/pytorch Elastic (torchelastic)、Rajbhandari 2020 ZeRO 与 facebookresearch/llama 训练工程经验。

## 一、背景与挑战
千卡级训练往往持续数天甚至数周，节点故障、硬件降级、集群抢占在所难免。故障率随规模上升，长时间不中断几乎不可能。
传统静态训练的容错策略是「故障即全停、从头或从最近检查点整体重跑」，重跑意味着已完成的算力被浪费，成本随故障频率放大。
弹性训练（elastic training）允许成员集合在运行中动态增减：故障节点被替换后，其余节点继续，训练从检查点恢复而非重跑。
核心挑战有三：其一是成员发现与同步，需要在动态变化中维护一致的进程组；其二是状态恢复，优化器状态、学习率调度与数据采样位置都必须精确复位；其三是并行度变化带来的重分片问题。
因此弹性训练是「调度 + 检查点 + 数据管道」的系统协同，而非单一技术。

## 二、核心原理
弹性训练用 rendezvous（会合）机制管理成员集合：每个 worker 在启动时向 rendezvous 后端（如基于 etcd 或共享文件）注册，凑齐最小成员数后建立进程组。
当某个 worker 失效，协调器检测到后解散并重建进程组；若允许更换成员，则等待新成员加入后继续，否则按策略终止作业。
恢复时各 rank 载入最近的检查点，恢复模型参数、优化器状态与学习率调度器的步数，并把数据采样位置复位到对应 epoch/step。
并行度变化会改变分片方式：数据并行 rank 数变了，分片需要重新切分，DeepSpeed/FSDP 提供相应的重分片能力。
这要求检查点格式支持灵活的分片数，否则无法在成员变化后正确恢复。

## 三、形式化与数学基础
单次故障的恢复时间由检查点耗时与加载耗时构成：

$$ t_{recover} = t_{checkpoint} + t_{load} $$

设故障率为 $f$（单位时间期望故障次数）、检查点间隔为 $\Delta t$，则每次故障平均损失的训练步数约为半个间隔，期望浪费时间为：

$$ E[\text{waste}] = f \cdot \frac{\Delta t}{2} \cdot t_{step} $$

同时，频繁检查点本身有开销。若单次保存耗时为 $t_{ckpt}$，则检查点的稳态开销占比为：

$$ \text{overhead} = \frac{t_{ckpt}}{\Delta t} $$

总成本是「故障损失」与「检查点开销」之和，存在最优间隔 $\Delta t^{*}$：

$$ \Delta t^{*} = \arg\min_{\Delta t} \left( f \cdot \frac{\Delta t}{2} \cdot t_{step} + \frac{t_{ckpt}}{\Delta t} \right) $$

对 $\Delta t$ 求导并令其为零，可得 $\Delta t^{*} \propto \sqrt{t_{ckpt} / (f \cdot t_{step})}$——检查点越慢或故障越频繁，间隔应越大。

## 四、代码实现
```bash
# 启动弹性训练（torchrun）：节点数可在 1 到 4 之间弹性变化
# --max_restarts 控制自动重启次数
torchrun \
  --nnodes=1:4 \
  --nproc_per_node=8 \
  --max_restarts=3 \
  --rdzv_backend=c10d \
  --rdzv_endpoint=rdzv-host:29500 \
  train.py
```

```python
import torch.distributed as dist

def train_loop(model, optim, loader, ckpt_interval, start_step=0):
    step = start_step
    for batch in loader:
        if step % ckpt_interval == 0:
            dist.barrier()
            save_sharded(model, optim, step)   # 分片保存，供重启读取
        loss = compute_loss(model, batch)
        loss.backward()
        optim.step()
        optim.zero_grad()
        step += 1
    return step

# 恢复入口：读最近检查点，复位优化器与数据位置
def resume(ckpt_dir):
    state = load_sharded(ckpt_dir)      # 各 rank 读自身分片
    return state["model"], state["optim"], state["step"]
```

## 五、与其他技术对比
| 方案 | 故障处理 | 资源利用 | 实现复杂度 |
|---|---|---|---|
| 静态训练 | 全停重跑 | 低 | 低 |
| 检查点+手动重启 | 从检查点重跑 | 中 | 中 |
| 弹性 rendezvous | 局部替换、继续 | 高 | 高 |
| 抢占式实例+弹性 | 主动让出、自动恢复 | 高（成本低） | 高 |
| 冗余计算 | 影子副本接管 | 中（成本高） | 高 |

静态训练故障即全停；弹性 rendezvous 配合 Kubernetes 重调度可实现自动恢复；DeepSpeed 亦支持弹性 ZeRO 与重分片。

## 六、常见误区
- 认为弹性无需检查点：无检查点无法恢复状态，弹性只能重启不能续训。
- 认为任意成员变动都安全：数据并行 rank 数变化需要重分片，否则分片与参数不对应。
- 认为恢复零丢失：实际会丢失检查点间隔内的步数，需在间隔与开销间权衡。
- 忽视数据管道状态：采样位置未复位会导致数据重复或跳过，影响收敛。
- 过度频繁检查点：保存开销本身可能超过故障损失，间隔需按公式估算而非拍脑袋。

## 八、面试题
1. 问：弹性训练的关键组件是什么？
   答：rendezvous 成员管理加分片检查点，二者缺一不可。
2. 问：恢复的代价是什么？
   答：检查点间隔内的步数损失，以及加载检查点所需时间。
3. 问：检查点间隔如何选？
   答：在故障损失与保存开销之间取平衡，最优间隔约与保存耗时的平方根成正比。
4. 问：成员变化为什么会带来问题？
   答：并行度变化需要重分片，若格式不支持会导致分片与参数错位。
5. 问：弹性训练为什么能降成本？
   答：可结合抢占式实例并局部恢复，避免整体重跑，提高资源利用率。

## 九、演进与趋势
- 与抢占式实例结合降低单位成本，配合优雅退避与快速重连。
- 异步检查点与增量检查点减少恢复开销。
- 自动化容错编排成为大规模训练平台的基础能力。

## 十、小结
弹性训练把「故障等于重跑」变为「故障等于局部恢复」：靠 rendezvous 维护成员集合、靠分片检查点恢复状态、靠重分片适配并行度变化。检查点间隔需要在故障损失与保存开销间权衡，最优值由故障率与保存耗时的关系决定。它是长周期大规模训练的必需能力。
