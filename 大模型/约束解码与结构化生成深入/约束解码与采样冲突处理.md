# 约束解码与采样冲突处理

> 对应 Willard & Louf 2023 constrained decoding; Brown 2020 in-context; Zheng 2023 LLM-as-judge。

## 一、背景与挑战

当模型对某个非法 token 给出极高概率（例如强烈想续写一个不在 Schema 里的词），硬遮罩会把它概率直接压零。这虽然保证了格式，但可能让生成「卡」在不自然处，甚至反复在几个合法 token 间退化重复。问题本质是：约束（格式正确）与采样（语义流畅）可能冲突，需要按任务严格度权衡。

另一类冲突来自采样超参：温度、top-p 与遮罩的交互顺序若处理不当，会让约束失效或分布畸变。因此工程上需要一整套「冲突处理策略」而非单一硬遮罩。

## 二、核心原理

提供三类策略，按严格度递进：

- **硬遮罩（hard mask）**：把所有非法 token 概率置零，保证输出 100% 合法，适合关键格式（JSON 字段、SQL 语法）。
- **软偏置（soft bias）**：给合法 token 加一个对数偏置 $\beta$，不强制置零，允许极端情况下模型逃逸，适合半结构化、创意文本。
- **回退重试（fallback）**：当约束导致退化（如重复、EOS 提前）时，少量重试或更换种子，配合遮罩而非裸重试。

选择原则：格式硬性契约用硬遮罩；需要流畅度的文本用软偏置；回退仅作兜底，不能替代遮罩。

冲突还可能来自「约束与模型先验打架」：模型强烈想续写某词，但该词不在 Schema，硬遮罩强制切走后，后续生成可能语义断裂。此时可用软偏置让模型在约束边界附近仍保留一定流畅度，或对关键字段（id/类型）用硬遮罩、对描述字段用软偏置的分级策略。回退（retry）只应在遮罩导致死状态或明显退化时作为兜底，不能替代遮罩本身。

## 三、形式化与数学基础

软偏置分布定义为把合法指示函数加进 logits：

$$ p'(x) \propto p(x) \cdot \exp\!\big(\beta \cdot \mathbb{1}[x \in A(w)]\big) $$

$\beta \to +\infty$ 时软偏置退化为硬约束；$\beta = 0$ 时退化为无约束。若还要考虑温度 $T$，应先遮罩再缩放：

$$ p'(x_t) = \mathrm{softmax}\!\left( \frac{\mathrm{mask}(\mathbf{z}_{<t}) + \beta \cdot \mathbb{1}_{A(w)}}{T} \right) $$

其中 $\mathrm{mask}(\cdot)$ 把非法 logit 置 $-\infty$。顺序很关键：必须先置零非法 token，再做温度缩放与 softmax，否则非法 token 仍可能获得非零概率。

## 四、代码实现

```python
import torch

def biased_logits(logits, allowed_mask, beta=5.0):
    # allowed_mask: [vocab] bool，True 表示合法
    add = torch.where(allowed_mask, torch.tensor(beta), torch.tensor(-beta))
    return (logits + add).softmax(-1)

def hard_mask_logits(logits, allowed_ids):
    out = torch.full_like(logits, float("-inf"))
    out[allowed_ids] = 0.0
    return (logits + out).softmax(-1)

def decode_with_eta(model, prompt, allowed_fn, beta=5.0, max_len=64):
    ids = model.encode(prompt)
    for _ in range(max_len):
        z = model.logits(ids)[-1]
        # 先硬遮罩兜底，再叠加软偏置提升流畅度
        allowed = allowed_fn(ids)
        if allowed.sum() == 0:            # 死状态：回退
            ids = ids[:-1]
            continue
        probs = biased_logits(z, allowed, beta)
        nxt = int(torch.multinomial(probs, 1))
        ids.append(nxt)
    return model.decode(ids)
```

## 五、与其他技术对比

- 纯硬约束：格式 100% 保证，但可能僵化、退化重复，需配合重复惩罚。
- 纯提示（few-shot）：无格式保证，失败需重试，浪费往返。
- 软偏置：折中，适合半结构化输出，但极端情况下可能逃逸约束。
- 回退裸重试：不配合遮罩时几乎无效，因模型会反复撞同一非法偏好。

## 六、常见误区

误区一：回退重试总能解决冲突——若模型持续偏好某非法 token，裸重试仍会反复撞墙，必须配合遮罩。误区二：温度与遮罩无关——顺序错会让非法 token 复活。误区三：软偏置等于软约束无代价——$\beta$ 太小仍会逃逸，$\beta$ 太大退化为硬遮罩。误区四：硬遮罩必然降质——在合法子集重归一化，影响可控，且常能用重复惩罚缓解退化。

## 八、面试题

1. 约束与采样温度如何交互？温度缩放必须在遮罩之后：先置零非法 token，再做 $z/T$ 与 softmax，保证不越界。
2. 软偏置的 $\beta$ 作用？$\beta$ 越大越接近硬约束，$\beta=0$ 退化无约束，需在保证与流畅间调。
3. 何时用回退？仅作遮罩导致死状态/退化的兜底，不能替代遮罩本身。
4. 硬遮罩为何会退化重复？合法子集过小且含高概率重复 token，需叠加重复惩罚（如出现惩罚）。

生产系统中，约束解码常与「输出校验 + 自愈」结合：约束失败时在 FSM 层局部回退而非整段重试，显著降低延迟。模型原生 JSON mode 与解码期硬约束组成双保险，已成为 Agent 框架（如函数调用）的默认配置。可观测性上，记录「约束触发次数 / 回退次数」是诊断生成质量的重要指标。

## 九、演进与趋势

自适应 $\beta$（按字段严格度分级：关键 id 用硬遮罩、描述字段用软偏置）成为生产实践。结合重复惩罚、出现惩罚与「约束 + 原生 JSON mode」双保险，使结构化输出既零失败又流畅。方向还包括根据模型置信度动态切换硬/软策略。

生产落地：关键字段（类型/id/枚举）用硬遮罩保正确，描述字段用软偏置保流畅，分级处理。
务必先遮罩后做温度缩放，否则非法 token 可能复活。
退化重复时叠加出现惩罚，而非单纯降温度。
回退只在遮罩导致死状态/明显退化时兜底，不能替代遮罩。
记录约束触发与回退计数，作为生成质量监控指标。
软偏置的 β 过大退化为硬遮罩、过小仍逃逸，需按字段调。
约束与模型先验打架时，硬切走可能语义断裂，用软偏置缓解边界。
JSON 结构约束下，字段顺序与必填项由 FSM 严格管，取值合理仍靠提示。
生成卡死（死状态）时删 token 重来比整段重试更省。
出现惩罚（repetition penalty）与约束配合，防合法子集内退化。
模型原生 JSON mode 与约束解码双保险，已成 Agent 默认。
温度与 top-p 在遮罩后仍可用，只作用于合法子集。
多轮对话中约束状态需跨轮保持，避免每轮重建 FSM。
评测约束生成看「首轮可解析率」而非仅仅文本质量。

## 十、小结

约束解码不是非黑即白：硬遮罩保格式、软偏置保流畅、回退兜底。三者的正确组合与「先遮罩后温度」的执行顺序，是把冲突控制在可接受范围内的工程要点。按字段严格度分级约束，是落地最佳实践。
