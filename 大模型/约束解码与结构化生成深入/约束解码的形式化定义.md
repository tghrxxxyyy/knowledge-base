# 约束解码的形式化定义

> 对应 Willard & Louf 2023 constrained decoding; Ouyang 2022 InstructGPT; Zheng 2023 LLM-as-judge。

## 一、背景与挑战

自由生成难以保证输出符合指定格式（JSON、SQL、代码、受控词表），一旦格式错误，下游程序解析即失败，导致 Agent 调用中断或需要昂贵重试。传统「让模型自由生成再 try/except 解析」的失败率随结构复杂度上升而攀升。约束解码（constrained decoding）的思想是：在采样每一步就把 token 限制在「合法续写集合」中，使输出天然可机读，从根源消除格式错误。

挑战在于：如何形式化「合法续写集合」？如何让约束与自回归生成的概率分布兼容而不破坏语义？以及约束的表示（正则、文法、Schema）如何高效编译成可在每一步查询的结构。

## 二、核心原理

把生成过程视为在约束语言 $L$ 上的游走：设当前已生成前缀为 $w_{<t}$，下一步允许的 token 集合由 $w_{<t}$ 与约束（正则/文法/JSON Schema）共同决定，记为 $A(w_{<t})$。解码时对不在此集合的 token 把概率置零（硬约束）或加偏置（软约束），只对合法 token 做 softmax。这样输出序列必然属于 $L$。

约束可分层：词表级遮罩（最细）、前缀树（有限候选）、正则（扁平模式）、上下文无关文法 CFG（嵌套结构）、JSON Schema（API 契约）。越往上表达能力越强，编译与查询成本也越高。

从实现角度，约束集合 $A(w_{<t})$ 的查询必须足够快——每步生成都要查一次，否则吞吐不可接受。常见做法把约束编译成确定性有限状态机（DFA）或下推自动机（PDA），用当前状态 $O(1)$ 得到合法 token 集合；正则、trie、JSON Schema 都可编译为这类自动机，CFG 则需栈结构。编译期与查询期的分离，是约束解码可落地的关键工程抽象。

## 三、形式化与数学基础

令 $A(w_{<t}) \subseteq \mathcal{V}$ 为前缀 $w_{<t}$ 之后合法续写集合，约束分布定义为：

$$ p'(x_t \mid w_{<t}) = \begin{cases} \dfrac{p(x_t \mid w_{<t})}{Z(w_{<t})} & x_t \in A(w_{<t}) \\[6pt] 0 & \text{otherwise} \end{cases} $$

其中归一化项 $Z(w_{<t}) = \sum_{x \in A(w_{<t})} p(x_t \mid w_{<t})$。该式等价于在合法子集上做条件分布 $p(x_t \mid x_t \in A(w_{<t}))$，因此不改变合法 token 间的相对排序，只是把概率质量重新分配。整句概率为各步乘积：

$$ p'(w) = \prod_{t} \frac{p(x_t \mid w_{<t})}{Z(w_{<t})} \quad (w \in L) $$

可见约束解码是「先条件后生成」，而非「先生成后修正」。

## 四、代码实现

```python
import torch

def constrained_logits(logits, allowed_ids):
    # logits: [vocab]；allowed_ids: 合法 token 下标集合
    mask = torch.full_like(logits, float("-inf"))
    mask[allowed_ids] = 0.0
    return (logits + mask).softmax(-1)

def sample_constrained(model, prompt, allowed_fn, max_len=64):
    ids = model.encode(prompt)
    for _ in range(max_len):
        logits = model.logits(ids)[-1]
        allowed = allowed_fn(ids)            # 由前缀推导合法集合
        probs = constrained_logits(logits, allowed)
        nxt = torch.multinomial(probs, 1)
        ids = ids + [int(nxt)]
        if int(nxt) == model.eos_id:
            break
    return model.decode(ids)
```

## 五、与其他技术对比

| 手段 | 是否保证格式 | 是否一次成功 | 语义影响 |
|------|--------------|--------------|----------|
| 后处理校验 + 重试 | 否（依赖运气） | 否 | 无 |
| 提示工程（few-shot） | 否（软约束） | 否 | 无 |
| 约束解码（硬遮罩） | 是 | 是 | 仅合法子集内重归一化 |
| 约束解码（软偏置） | 近似 | 是 | 轻微偏移 |

硬约束解码以「零解析失败」为代价，仅在合法空间内重归一化，对质量影响可控且可预测。

## 六、常见误区

误区一：约束解码会严重降质——它只在合法子集上重归一化，等价于条件分布，对质量影响远小于直觉预期。误区二：约束解码能管取值合理——约束只管结构（括号/字段/类型），不管字段取值是否语义正确，仍需提示说明。误区三：任何约束都能实时编译——歧义文法会状态爆炸，需左因子化。误区四：约束与采样温度无关——温度缩放应在遮罩之后做，先置零非法再 softmax。

## 八、面试题

1. 约束解码如何不影响分布语义？在合法子集上重归一化，等价于条件分布 $p(x_t \mid x_t \in A)$，不改变合法 token 间相对排序。
2. 为什么用 $Z(w_{<t})$ 归一化？保证约束后概率仍合法（和为 1），避免概率崩塌。
3. 硬约束与软偏置取舍？关键格式（JSON 字段）用硬遮罩保正确，创意文本用软偏置保流畅。
4. 约束解码能否用于自回归之外？核心依赖自回归逐步生成，非自回归需改造。

社区正把约束从「逐 token 遮罩」推进到「可组合约束 DSL」：正则、trie、CFG、JSON Schema 统一编译为分词感知自动机，支持混合约束。硬件侧，把约束查询融合进注意力/采样内核进一步降开销。理论侧则关注约束对分布偏差的定量刻画，避免软偏置引入系统性偏好。

## 九、演进与趋势

从正则约束，到上下文无关文法（CFG）引导，再到把 JSON Schema / 类型定义自动编译为有限状态机（FSM）。社区工具（outlines、guidance、vllm guided）把约束编译为分词感知的自动机，避免子词切分越界。趋势是把约束解码与模型原生结构化输出（JSON mode）做成双保险，成为 Agent 与工具调用的工程基石。

## 十、小结

约束解码用「合法集合遮罩」把随机生成约束进可解析空间：形式化上等价于在合法子集的条件分布下采样，从根源消除格式错误。理解 $A(w)$ 与归一化项 $Z$，是掌握从正则到 JSON Schema 各类约束实现的关键。
