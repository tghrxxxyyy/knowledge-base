# 多轮对话管理

> 对应生产聊天应用的会话状态设计；思想参考 OpenAI Chat Completions 消息协议与对话状态管理实践。

## 一、背景与挑战

多轮聊天（客服、助手、角色扮演）需要模型「记住」前文：用户说「它贵吗」中的「它」指上一轮的商品；助理也要保持人设与已达成的事实一致。但上下文窗口有限，长对话会超长、变贵、且远端信息被「遗忘」或稀释。

挑战：(1) 上下文窗口有限，历史无限增长；(2) 长历史稀释注意力（lost in the middle）；(3) 多租户下用户状态必须隔离；(4) 关键信息（偏好、订单号）需可靠保留而非依赖模型记忆；(5) 摘要可能丢失关键约定。

## 二、核心原理

核心是「消息列表 + 上下文压缩」：

- 原始消息栈：system（固定在前）→ user/assistant 交替。system 承载人设与规则，不应被覆盖。
- 截断（滑动窗口）：只保留最近 $k$ 轮，最旧的直接丢弃。
- 摘要压缩：用 LLM 把早期对话压缩为一段摘要，替代原始多轮。
- 检索相关历史：把历史向量化，按需召回与当前问题相关的轮次拼入。
- 结构化状态：把订单号、用户偏好等抽成字段，独立于自由文本持久化。

## 三、形式化与数学基础

设完整历史为 $H=(m_1,\dots,m_T)$，上下文窗口容量 $C$。滑动窗口保留最近 $w$ 条：

$$H_{win} = (m_{T-w+1},\dots,m_T)$$

摘要策略把早期部分压缩为 $\bar m$：

$$\bar m = \text{Summarize}(m_1,\dots,m_{T-w})$$

最终送入模型的上下文：

$$\text{ctx} = [\text{system}] \oplus \bar m \oplus H_{win}$$

检索增强则取 $\text{TopK}_i\,\text{sim}(q, m_i)$ 的相关历史替换或补充 $H_{win}$。

## 四、代码实现

滑动窗口 + 摘要的简化实现（示意）：

```python
def build_context(history, window=10):
    if len(history) <= window:
        return [system_msg] + history
    old, recent = history[:-window], history[-window:]
    summary = llm.invoke("摘要以下对话:\n" + format(old))
    return [system_msg, {"role":"system","content":summary}] + recent
```

结构化状态可与自由文本并行维护：`state = {"user_id":..., "prefs":{...}, "order_no":...}`。

## 五、与其他技术对比

| 策略 | 优点 | 缺点 |
|------|------|------|
| 全量历史 | 完整 | 超窗口、贵 |
| 滑动窗口 | 简单 | 丢早期信息 |
| 摘要压缩 | 保留要义 | 摘要可能失真 |
| 向量检索历史 | 精准 | 实现复杂 |

实务多「滑动窗口 + 摘要」组合，关键事实走结构化状态。

## 六、常见误区

- 把 system 消息插在中间或被历史覆盖，人设/规则失效。
- 只用滑动窗口丢弃早期，导致长程约定（如「之后都用中文」）丢失。
- 多租户共用同一历史缓冲，造成串号/泄露。
- 让模型「凭记忆」记订单号，而非结构化持久化。
- 摘要覆盖整段对话却不保留关键实体，致后续指代断裂。

## 九、演进与趋势

从简单截断到「分层记忆」：短期（窗口）+ 中期（摘要）+ 长期（向量库/数据库）；引入工具调用把事实写入外部存储；用压缩率更高的递归摘要；结合用户画像做个性化上下文装配；以及对长对话做「遗忘曲线」式优先级管理。

## 十、小结

多轮对话管理 = 消息栈 + 上下文压缩 + 结构化状态。用滑动窗口控制长度、摘要保留要义、结构化字段承载关键事实，并在多租户间严格隔离，才能兼顾成本与一致性。
