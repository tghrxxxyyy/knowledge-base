# 提示管理与版本化

> 对应应用工程化实践；思想参考 Prompt Engineering 与「提示工程深入」章节，工具如 LangChain PromptTemplate、PromptLayer。

## 一、背景与挑战

在真实项目里，prompt 不是一次性写在代码里的字符串，而是会随业务、模型、评测结果频繁迭代的「软逻辑」。一段精心调好的 system prompt 可能因一次误改而整体劣化，且难以回滚。把 prompt 当代码管理，是应用可维护、可回归、可协作的前提。

挑战：(1) prompt 散落在代码各处，改一处牵全身；(2) 不知某次改动带来什么效果变化；(3) 多环境（开发/生产）需不同版本；(4) A/B 对比需要同一入口切换；(5) 多人协作易相互覆盖。

## 二、核心原理

把提示模板抽离为独立资源，纳入工程化管理：

- 模板化：用变量占位符（`{question}`、`{context}`）与系统/用户分层，复用与测试。
- 版本化：每次修改留存版本号，支持回滚与差异对比。
- 变量注入：运行时安全填充动态内容（避免拼接注入）。
- 评测绑定：每个版本关联评测结果，变更可验证。
- 多环境治理：按环境/模型选择对应 prompt 版本，支持 A/B。

实现上可用 Git 管理 `.prompt` 文件、配置中心，或 PromptLayer 等托管服务。

## 三、形式化与数学基础

把 prompt 视为带参数的函数：

$$p = P(\theta, \mathbf{v})$$

其中 $\theta$ 为模板结构，$\mathbf{v}$ 为变量集合。版本 $v$ 在评测集上得分为 $S_v$。回滚即选择历史版本 $v^*$：

$$v^* = \arg\max_{v\in \text{history}} S_v$$

A/B 对比则对版本 $a,b$ 比较指标分布，用统计检验判断是否显著差异。版本与评测结果的绑定使每次变更可追溯、可量化。

## 四、代码实现

用模板与配置中心管理（示意）：

```python
from langchain_core.prompts import ChatPromptTemplate

PROMPTS = {
    "v1": ChatPromptTemplate.from_messages(
        [("system","你是助手"),("user","{q}")]),
    "v2": ChatPromptTemplate.from_messages(
        [("system","你是严谨助手，只依据上下文回答"),("user","{q}\n上下文:{ctx}")]),
}
chain = PROMPTS[current_version] | model   # 切换版本仅改 current_version
```

## 五、与其他技术对比

| 实践 | 收益 | 成本 |
|------|------|------|
| 硬编码字符串 | 零基建 | 不可维护 |
| Git 管理模板 | 可回滚 | 需流程 |
| 配置中心 | 热更新 | 需平台 |
| 托管服务 | 可视化/A-B | 外部依赖 |

中小团队从「Git + 模板」起步即可。

## 六、常见误区

- 把 prompt 字符串散落在业务代码，改一处要全局搜。
- 改了 prompt 不跑评测，靠手感判断好坏。
- 变量用字符串拼接而非模板注入，引入注入风险。
- 多环境共用一份 prompt，生产踩坑才回滚。
- 多人同时改同一 prompt 文件，互相覆盖无冲突管理。

## 九、演进与趋势

从静态模板到「可观测 prompt 平台」：版本差异可视化、线上流量回放评测、prompt 与模型/评测集一体化管理；以及把 prompt 优化本身自动化（自动搜索最优模板）。A/B 与灰度成为标准能力。

## 十、小结

提示管理把「调 prompt」从手感活变成工程活。核心是模板化、版本化、变量安全注入、评测绑定，让每一次改动可回滚、可验证、可协作。
