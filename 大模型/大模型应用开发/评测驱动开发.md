# 评测驱动开发 Eval-Driven

> 对应应用质量保障实践；评测思想参考 LLM 评估方法论与「模型评测深入」章节，框架如 Ragas、DeepEval、PromptFoo。

## 一、背景与挑战

大模型应用（RAG、Agent、NL2SQL）的输出具有非确定性：同样的 prompt 在不同模型/温度下结果波动，且「质量」难以用传统单元测试断言。若仅靠开发者手动试几个例子就上线，任何 prompt 或模型切换都可能悄然劣化体验而无人察觉。

挑战：(1) 没有客观度量，改进全凭感觉；(2) 回归风险——一次优化提了 A 却降了 B；(3) 多维度（准确率/忠实度/成本/时延）需要权衡；(4) 业务口径变化，评测集需同步演进；(5) 评测本身可能引入偏差。

## 二、核心原理

评测驱动开发（Eval-Driven Development）把「评测」作为一等公民，与代码同等地位：

1. 建评测集：维护黄金样本（输入 + 期望输出/评分要点），覆盖典型场景、边界与已知失败案例。
2. 自动化跑批：每次 prompt/模型/检索策略变更，自动对评测集推理并打分。
3. 量化决策：用指标（准确率、忠实度、相关性、成本、时延）决定是否发布。
4. 回归门禁：指标低于基线则阻断合并，防止劣化上线。

它与 CI/CD 结合，把「主观试错」变成「可度量、可回归、可对比」的工程流程。

## 三、形式化与数学基础

对评测集 $\mathcal{D}=\{(x_i, y_i^*)\}_{i=1}^{N}$，某版本系统在输入 $x_i$ 上产出 $\hat y_i$，由评分函数 $s$（可为 LLM-judge 或规则）给出得分：

$$\text{Score} = \frac{1}{N}\sum_{i=1}^{N} s(\hat y_i, y_i^*)$$

令版本 $v$ 的得分为 $S_v$，发布门禁为：

$$S_v \ge S_{baseline} - \epsilon \quad \text{且各维度达标}$$

其中 $\epsilon$ 为允许的微小回退阈值。多维度可用向量 $\mathbf{S}_v=(S^{(1)}_v,\dots,S^{(k)}_v)$ 做帕累托比较，避免单指标优化损害其他维度。

## 四、代码实现

用评测框架跑批并对比（示意，以伪代码表达思路）：

```python
from ragas import evaluate
from datasets import Dataset

# 黄金样本：question / answer / contexts / ground_truth
dataset = Dataset.from_dict({...})
result = evaluate(dataset, metrics=[faithfulness, answer_relevancy])
print(result["faithfulness"], result["answer_relevancy"])
# CI 中: if result["faithfulness"] < baseline: fail()
```

也可基于 PromptFoo 做 prompt 多版本 A/B 评测，对比同一组 case 下不同 prompt 的指标差异。

## 五、与其他技术对比

| 方式 | 优点 | 缺点 |
|------|------|------|
| 人工试例 | 快 | 不可回归、主观 |
| 单指标脚本 | 可量化 | 维度单一 |
| 评测驱动 + CI | 防回归、可对比 | 需维护评测集 |
| LLM-judge | 贴近人工 | 有偏差、需校准 |

## 六、常见误区

- 评测集太小或只含「 happy path」，边界与失败案例缺失，指标虚高。
- 用 LLM-judge 当唯一真相，未做人类校准，偏差累积。
- 只看准确率忽略成本/时延，线上不可持续。
- 评测集长期不更新，与真实分布脱节。
- 把评测脚本当一次性工具，未接入发布门禁。

## 八、面试题

- 为什么大模型应用要评测驱动而非人工试几个例子？
- 评测集应该如何覆盖才能避免指标虚高？
- LLM-judge 有什么偏差？如何校准？
- 如何平衡「准确率」与「成本/时延」？

## 九、演进与趋势

从离线评测到「在线评测 + 生产监控」：用真实流量做在线 A/B 与影子评测；评测集用生产失败案例自动反哺；LLM-judge 与人工标注混合校准；把评测门禁嵌入 CI/CD 成为发布硬约束；prompt 版本与评测结果绑定可追溯。

## 十、小结

评测驱动是大模型应用质量护城河。以可回归的黄金评测集 + 自动化跑批 + 多维度门禁，把主观优化变为客观、可对比、防劣化的工程流程，并让 prompt/模型的每次变更都留下可验证的痕迹。
