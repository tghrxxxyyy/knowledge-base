# 连续批处理 Continuous Batching

> 对应 Yu et al., *Orca: A Distributed Serving System for Transformer-Based Generative Models*, 2022（亦见 vLLM 实现）。

## 一、背景与挑战

大模型自回归推理以「请求」为单位服务时，最朴素的做法是**静态批处理（static batching）**：把若干请求凑成一个固定批次，等批次内**最长**的那条序列生成完毕后，才一次性释放整批显存并把结果返回。这带来两个严重问题：

- **木桶效应**：一个短请求会被同批里生成长文本的请求拖住，GPU 在等待期间被迫空转，利用率骤降。
- **显存浪费**：每个请求都按最大长度预留 KV Cache，实际只用很小一部分。

当线上流量请求长短不一、到达时间错落时，静态批处理既拉低吞吐（req/s），又抬高首尾延迟（特别是短请求的排队等待）。连续批处理正是为消除这一矛盾而生。

## 二、核心原理

连续批处理（又称 **in-flight / iteration-level batching**）把调度粒度从「整条序列」下沉到「**每一个生成步（token 步）**」：

1. 在每个解码步，调度器先扫描当前在跑的请求集合；
2. 已完成（生成 EOS 或达最大长度）的请求立即移出并回收其 KV Cache；
3. 新到达的请求在该步即可插入空闲槽位，参与本次前向；
4. 所有未完成的请求拼成一个动态批次，做一次并行前向。

由于不同请求处在各自序列的不同进度，批次构成在每一步都在变化，因此 GPU 几乎始终被填满，无谓空闲大幅减少。它通常与 **PagedAttention** 配合——被移出请求的 KV 页即时释放，供新请求复用。

## 三、形式化与数学基础

设某服务窗口内共处理 $N$ 条请求，第 $i$ 条长度为 $L_i$。静态批处理的完工时间为：

$$T_{\text{static}} = \max_i L_i \times t_{\text{step}},$$

其中 $t_{\text{step}}$ 为单步前向耗时。连续批处理把「按步调度」视为一个在线装箱问题，理想情况下完工时间趋近于各请求长度之和在并行度 $P$ 下的负载：

$$T_{\text{cont}} \approx \frac{\sum_i L_i}{P} \times t_{\text{step}}.$$

吞吐提升比约为 $\frac{\max_i L_i}{\bar L}$（$\bar L$ 为平均长度），长度方差越大收益越显著。设每步可容纳最多 $B$ 条并发请求，则约束为 $|\{i: \text{未完成}\}| \le B$。

## 四、代码实现

以 vLLM 为例，连续批处理由调度器在内部自动完成，用户只需开启服务：

```bash
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-2-7b-chat-hf \
  --max-num-seqs 256 \
  --gpu-memory-utilization 0.9
```

概念上，每步调度的伪代码可写为：

```python
while pending or running:
    finished = [r for r in running if r.done]
    for r in finished:
        free_kv(r); running.remove(r); return_result(r)
    new = admit(pending, capacity=max_batch - len(running))
    running += new; pending -= new
    batch = collate(running)          # 动态拼批
    logits = model.step(batch)        # 一次并行前向
    for r in running:
        r.append(sample(logits[r.slot]))
```

## 五、与其他技术对比

| 维度 | 静态批处理 | 连续批处理 | 连续批处理 + PagedAttention |
|------|-----------|-----------|----------------------------|
| 调度粒度 | 整条序列 | token 步 | token 步 |
| 显存碎片 | 高（预留最大） | 高 | 低（分页按需） |
| 短请求延迟 | 受长请求拖累 | 不被拖累 | 不被拖累 |
| 实现复杂度 | 低 | 中 | 高 |
| 典型引擎 | 早期 HF | Orca / vLLM / TRT-LLM | vLLM |

## 六、常见误区

- **误以为连续批处理会改变输出分布**：它只改「何时算」，不改「怎么算」，输出与逐条串行完全一致。
- **认为 batch 越大越好**：并发上限受显存（KV Cache 总量）约束，过大会触发抢占或 OOM。
- **忽略长尾请求**：个别超长请求会长期占用槽位，需配合最大长度限制或优先级策略。

## 九、演进与趋势

连续批处理已成为生产推理引擎标配。后续演进包括：与**前缀缓存**共用相同提示页以省算力；与**投机解码**结合（草稿步也走动态批）；**抢占式调度**（按优先级换出长请求）；以及在多卡/多节点下与张量并行、流水并行的协同。SGLang 的 RadixAttention 进一步把批内请求的公共前缀做树状复用。

## 十、小结

连续批处理把推理调度从「序列级」降到「token 步级」，通过每步动态进出请求消除木桶效应，是提升 GPU 利用率与吞吐的关键优化；它与 PagedAttention、前缀缓存、投机解码共同构成现代 LLM 服务引擎的吞吐基石，且对最终输出分布无影响。
