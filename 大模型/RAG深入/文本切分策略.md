# 文本切分策略 Chunking

> 对应 Datawhale llm-universe「文档切分」与 mlabonne/llm-course「RAG / Chunking」；切分粒度直接影响检索召回与上下文质量。

## 一、背景与挑战

长文档必须切成「块(chunk)」才能嵌入建索引并被精准检索。切分粒度是 RAG 最容易被低估、却影响最大的超参之一：

- **块太小**：语义不完整，检索到的片段缺乏上下文，LLM 看到「半句话」。
- **块太大**：嵌入向量被平均化而模糊、检索不准，且占用宝贵的上下文窗口。
- **结构破坏**：切错位置会把一个完整语义拆得支离破碎。
- **语言特性**：中文按空格切会切碎语义，应按标点/句式。

此外，切分需尽量保留文档的逻辑结构(标题层级、段落、表格)，否则会把一个完整语义拆得支离破碎，并丢失溯源所需的来源信息。

## 二、核心原理

常见切分策略：

| 策略 | 说明 |
|------|------|
| 固定长度 | 按字符/token 数切，重叠 overlap 防割裂 |
| 递归字符 | 按段落→句子→词递归，保结构 |
| 语义切分 | 按句向量突变(边界)切 |
| 按结构 | Markdown 标题/代码块切 |
| 父子文档 | 小块检索、父块(大块)喂给 LLM |

核心思想是：用较小的块提升「检索精度」，用较大的块(父块)保证「生成上下文完整」，二者通过元数据关联。递归字符切分是通用默认，父子文档是兼顾精度与上下文的最佳实践。

## 三、形式化与数学基础

设文档 $T$ 切成块序列 $C=\{c_1,\dots,c_m\}$，重叠 overlap 保证相邻块共享边界 token：

$$c_i = T[s_i : s_i + L],\quad s_{i+1} = s_i + L - \text{overlap}$$

语义切分则寻找句向量距离突变点作为边界：当 $\|\mathbf{e}_j - \mathbf{e}_{j-1}\|$ 超过阈值时切分。父子文档建立映射 $f: c_{\text{child}} \mapsto c_{\text{parent}}$，检索命中小块后回溯父块，使生成拿到完整上下文。

## 四、代码实现

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n## ", "\n### ", "\n\n", "\n", "。", ""],
)
chunks = splitter.split_documents(docs)

# 父子文档：小块用于检索，父块用于生成(示意)
child = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=20)
parent = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)
```

## 五、与其他技术对比

| 策略 | 精度 | 结构保持 | 适用 |
|------|------|----------|------|
| 固定长度 | 中 | 弱 | 通用 |
| 递归字符 | 中高 | 中 | 多数文本 |
| 语义切分 | 高 | 中 | 长散文 |
| 父子文档 | 高 | 强 | 需完整上下文 |

## 六、常见误区

- 重叠过大导致重复上下文浪费、检索重复命中。
- 忽略语言特性：中文按空格切会切碎语义，应按标点/句式。
- 用单一 chunk_size 适配所有文档类型。
- 切分后丢失来源/标题元数据，使生成无法溯源。
- 把表格从中间切开，破坏结构化信息。

## 九、演进与趋势

从规则切分走向「语义感知 + 结构感知 + 模型感知」的联合切分；也有工作用 LLM 直接生成「自包含检索单元」。检索单元大小正与长上下文窗口、上下文压缩技术协同演化：窗口越大，父块可越大，小块仍可保持检索精度。

## 十、小结

切分是 RAG 质量地基。以「小块检索、大块生成」的父子文档作为默认最佳实践，并结合文档类型与评估指标调优 chunk_size 与 overlap，同时务必保留来源元数据以便溯源。
