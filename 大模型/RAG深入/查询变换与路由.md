# 查询变换与路由

> 对应 mlabonne/llm-course「RAG / Query Transformation」；提升检索召回的工程技巧。

## 一、背景与挑战

用户的原始问题常常不适合直接检索：

- **口语化/模糊**：「那个新出的模型怎么用」缺乏明确实体。
- **多跳/复合**：「A 的作者还写过什么」需先查 A 再查作者。
- **过度具体或抽象**：与索引语料表述不一致，向量空间错配。
- **多源异构**：问题可能该查 FAQ、也可能该查数据库表或知识图谱。

直接拿原始 query 去检索，召回率往往低下。查询变换与路由正是为「让检索器听懂问题」而设计，是低成本的召回提升手段。

## 二、核心原理

用 LLM 在检索前对问题做预处理：

- **Query Rewriting(改写)**：把口语化问题改写为更利于检索的标准问法。
- **Query Expansion(扩展)**：生成多个子查询分别检索再合并，提升多跳覆盖。
- **Step-back Prompting(退一步)**：先问一个更抽象的高层问题，获取背景再答原问。
- **Routing(路由)**：根据问题类型路由到不同知识库/索引(如 FAQ 用向量、结构化数据用 SQL/工具)。

路由本质是一个分类器：先判断「该去哪查」，再做对应检索，避免错库。改写解决表述错配，扩展解决多跳，路由解决多源。

## 三、形式化与数学基础

查询扩展可写为把原查询 $q$ 映射为子查询集合：

$$Q = \{q\} \cup \{q_1,\dots,q_m\},\quad \text{retrieved} = \bigcup_{q_i\in Q} \mathrm{TopK}(D, q_i)$$

最终上下文取各路结果并集或经重排去重。路由则是学习一个映射 $r: q \mapsto \text{index}\in\mathcal{I}$，使检索发生在最合适的索引上，等价于先投影搜索空间再检索。

## 四、代码实现

```python
from langchain_core.prompts import ChatPromptTemplate

rewrite_prompt = ChatPromptTemplate.from_template(
    "把用户问题改写为适合向量检索的标准问法：{question}"
)
rewritten = llm.invoke(rewrite_prompt.format(question=user_q)).content

# 路由：让 LLM 选择索引
route_prompt = "问题属于[向量库/数据库/知识图谱]中的哪类？只回答类别：{question}"
target = llm.invoke(route_prompt.format(question=user_q)).content
```

## 五、与其他技术对比

| 技巧 | 解决 | 额外成本 | 风险 |
|------|------|----------|------|
| 改写 | 口语化错配 | 1 次 LLM | 意图偏移 |
| 扩展 | 多跳覆盖 | 多次检索 | 噪声叠加 |
| 退一步 | 缺背景 | 2 次生成 | 偏题 |
| 路由 | 多源错查 | 1 次分类 | 错库 |

## 六、常见误区

- 扩展子查询过多导致延迟与噪声叠加，反而降低精度。
- 路由分类错误把问题引到错误知识库，比不路由更差。
- 改写引入与用户意图偏差的内容(过度发挥)。
- 忽略对变换结果的缓存，重复计算浪费成本。
- 退一步问题过于抽象，失去检索针对性。

## 九、演进与趋势

查询变换正与 Agentic RAG 融合：模型自主规划「查什么、查几次、何时停」，而不再依赖固定模板。路由也从硬分类走向「软混合检索 + 工具调用」的统一编排，检索前处理成为检索栈的智能入口。

## 十、小结

查询变换与路由让检索器「听懂」真实问题，是提升召回与正确性的低成本高收益手段。改写解口语化、扩展解多跳、路由解多源，三者按场景组合使用，并配合缓存控制成本。
