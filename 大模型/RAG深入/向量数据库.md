# 向量数据库

> 对应 Datawhale llm-universe「向量数据库」与 mlabonne/llm-course「Vector Stores」；存储与高效检索嵌入。

## 一、背景与挑战

嵌入向量规模随文档量线性增长，朴素「遍历全库算相似度」在百万级以上不可行。向量数据库的核心使命是在亿级向量中**毫秒级返回 Top-k 近邻**，同时支持元数据过滤、增删改与持久化。

核心挑战：

- **准确性 vs 速度**：精确检索慢，近似检索有召回损失。
- **内存占用**：高维向量 + 索引结构内存压力大。
- **动态更新**：文档频繁增删时索引需高效维护。
- **过滤与向量联合**：先按元数据筛再近邻，二者如何高效结合。
- **分布式扩展**：超大规模需分片与副本。

## 二、核心原理

向量库核心是**近似最近邻(ANN)** 检索。主流系统与索引算法：

| 系统 | 特点 |
|------|------|
| FAISS | 本地、快、工程化 |
| Milvus | 分布式、生产级 |
| Qdrant | Rust、易用 |
| Chroma | 轻量、原型友好 |
| Weaviate | 混合检索、内置 |
| pgvector | 复用 Postgres |

索引算法：IVF(倒排聚类)、HNSW(可导航小世界图)、PQ(乘积量化压缩)。生产选型要结合规模、内存预算与是否需要混合检索/元数据过滤。

## 三、形式化与数学基础

HNSW 构建多层图：底层含全部节点，上层为下采样，查询从顶层贪心下降：

$$v \leftarrow \arg\min_{u\in \mathrm{neighbors}(v)} \|q-u\|$$

近似复杂度约 $O(\log N)$。IVF 先聚类，仅在与查询最近的若干聚类中心内搜索，量级降为 $O(N^{1/2})$ 级。PQ 把 $d$ 维向量切为 $m$ 段各量化为 $b$ 位，内存从 $d\cdot 4$ 字节压到 $m\cdot b/8$ 字节，以精度换空间。三者在「召回-速度-内存」三角中取舍。

## 四、代码实现

```python
import faiss, numpy as np

idx = faiss.IndexFlatL2(768)          # 精确
# 或 faiss.IndexHNSWFlat(768, 32)     # 近似图索引
idx.add(np.array(vectors, dtype="float32"))
D, I = idx.search(q_vec.astype("float32"), k=5)
```

生产可用 `IndexIVFPQ` 平衡速度与内存；带元数据过滤时可选用支持 `pre-filter` 的向量库(如 Qdrant/Weaviate)。

## 五、与其他技术对比

| 索引 | 召回 | 内存 | 增删 | 适用规模 |
|------|------|------|------|----------|
| Flat(精确) | 100% | 高 | 易 | 小 |
| IVF | 高 | 中 | 中 | 中 |
| HNSW | 高 | 高 | 较慢 | 中-大 |
| IVFPQ | 中 | 低 | 中 | 大 |

## 六、常见误区

- 盲目追求 HNSW 高召回，忽视其内存占用。
- 大规模数据直接用 Flat 精确检索，延迟不可接受。
- 忽略元数据过滤与向量检索的联合实现(部分库需专用过滤语法)。
- 索引参数(聚类数、图度)不调优导致召回骤降。
- 增删频繁场景下用不支持增量更新的索引，重建代价大。

## 九、演进与趋势

向量库从「单一 ANN」走向「混合检索 + 标量/向量联合过滤 + 磁盘驻留(DiskANN)」。云原生、Serverless 化与 GPU 加速索引成为大规模生产标配，并与重排、缓存构成完整检索栈；量化检索(float8/int8)进一步压缩成本。

## 十、小结

向量数据库以 ANN 索引(HNSW/IVF/PQ)在召回、速度、内存间权衡，是 RAG 规模化检索的底座。选型应结合规模、内存预算与是否需要元数据过滤，并调优索引参数；过滤与向量联合是生产常见刚需。
