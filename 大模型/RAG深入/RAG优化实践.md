# RAG 优化实践

> 综合 Datawhale llm-universe 与 mlabonne/llm-course 的工程经验，系统化定位并消除 RAG 瓶颈。

## 一、背景与挑战

RAG 上线后常见的「答非所问、幻觉、遗漏」并非单一原因，而是检索与生成两侧叠加的结果。拍脑袋式调参往往事倍功半。正确做法是先建立评估基线，再用「分层定位 + 对症优化」的工程闭环。

典型症状与归因：

- 正确答案压根没被检索到 → 检索召回问题。
- 检索到了但被稀释在噪声中 → 上下文组织问题。
- 上下文齐全却仍编造 → 生成 prompt 问题。
- 长文档塞满上下文但无用 → 压缩/摘要问题。
- 多源问题查错库 → 路由/过滤问题。
- 高频相似问题反复计算 → 成本问题。

## 二、核心原理

优化遵循「先定位后优化」原则。先通过评估把问题归到具体环节，再针对性施策：

1. **检索召回不足** → 换更强嵌入、加混合检索、查询扩展、增大候选集。
2. **上下文噪声** → 父子文档、重排、收紧 Top-k、元数据过滤。
3. **答案不忠实** → 强化 prompt「仅基于上下文」、加忠实度评估与拒答。
4. **长上下文浪费** → 检索片段压缩/摘要。
5. **元数据维度** → 按时间/来源/权限预筛。
6. **成本浪费** → 高频查询缓存。

关键纪律：**一次只改一个变量**，用评估指标量化改动收益，避免多变量混淆。

## 三、形式化与数学基础

把 RAG 输出质量视为各环节函数的复合：

$$Q_{\text{out}} = G\big(R(D, q), q\big)$$

其中 $R$ 为检索、$G$ 为生成。优化即分别提升对输出贡献最大的环节。评估指标(如 Faithfulness)对环节变化的敏感度，决定优化优先级：

$$\Delta Q \approx \frac{\partial Q}{\partial R}\Delta R + \frac{\partial Q}{\partial G}\Delta G$$

应优先投入边际收益 $\partial Q/\partial \cdot$ 最高的环节，而非盲目换更大模型。

## 五、与其他技术对比

| 优化手段 | 解决 | 代价 | 优先级信号 |
|----------|------|------|------------|
| 混合检索 | 召回不足 | 双路维护 | 召回低时高 |
| 重排 | 噪声稀释 | 推理延迟 | 噪声多时高 |
| 父子文档 | 精度+上下文 | 索引复杂度 | 通用 |
| 缓存 | 成本 | 新鲜度风险 | 高频时高 |

## 六、常见误区

- 一上来就换更大的 LLM，忽视检索召回才是主要瓶颈。
- 把所有片段全塞进上下文，反而稀释注意力。
- 只凭主观感受判断效果，没有量化评估基线。
- 过度优化单点(如 recall 拉满)导致延迟与成本失控。
- 多变量同时改，无法判断哪个改动生效。

## 九、演进与趋势

优化从「人肉调参」走向「自动搜索」：以评估指标为目标函数，自动搜索切分大小、Top-k、重排阈值等超参(类似 RAG 版 AutoML)。Agentic RAG 把「检索-反思-再检索」变成自适应循环，进一步抬升效果上限；在线评估闭环让系统在流量中持续自我优化。

## 十、小结

RAG 优化是分层工程问题。建立评估基线、定位瓶颈环节、对症施策、持续度量，并坚持「单变量对照」纪律，是稳定提升效果的可靠路径。
