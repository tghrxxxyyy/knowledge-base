# 07 部署与上线运维

> Agent 上线只是开始。本章讲容器化部署、私有化 GPU、灰度策略、SLA 保障、故障演练、合规审计、On-call。目标是：**稳定、可回滚、可扩展、合规、有人兜底**。

## 一、部署形态

### 1.1 容器化（K8s）

- Agent 服务、工具层、RAG 服务、网关全部容器化，统一编排。
- **无状态 vs 有状态**：Agent 编排服务尽量无状态（状态外置 DB/工作流引擎）；若用 LangGraph 持久化，状态在外部存储。
- **配置与密钥分离**：ConfigMap + Secret（Vault 注入），不进镜像。

### 1.2 私有化 GPU 部署

- **推理引擎**：vLLM / SGLang / TRT-LLM（高吞吐、连续批处理）。
- **编排**：K8s + 推理 Operator（KServe / Ray Serve / 自研），GPU 资源池化。
- **弹性**：流量的波峰（白天）用 HPA + GPU 共享（MIG/MPS）；闲时缩容省钱。
- **多模型共存**：一个 GPU 节点跑多个小模型，大模型独占，按 QPS 调度。

### 1.3 混合部署

```mermaid
flowchart LR
    EDGE[用户/内网] --> ING[入口网关]
    ING --> AGENT[Agent 服务 Pod(无状态)]
    AGENT --> GW[模型网关]
    GW --> PUB[公有云模型 API]
    GW --> PRI[私有化 vLLM(内网GPU)]
    AGENT --> RAG[RAG 服务]
    RAG --> VEC[(向量库)]
```

- 合规数据走私有化路径；非敏感走公有云，平衡成本与合规。

## 二、灰度与发布策略

| 策略 | 说明 | 适用 |
|------|------|------|
| 金丝雀 | 1–5% 流量先上新版，观测无异常再全量 | 模型/prompt 变更 |
| 影子 | 新旧并行跑，新版本只记录不生效 | 评估新模型效果 |
| 按租户灰度 | 先放内部/友好租户 | 多租户系统 |
| 蓝绿 | 两套环境切流，回滚快 | 大版本 |

> **Prompt/模型变更也要灰度**：模型会漂移，直接全量可能一夜之间质量崩塌。

---

## 三、SLA 与弹性

- **延迟 SLA**：对话类 p95 < 数秒；批量类放宽。超阈值告警。
- **可用性**：多副本 + 健康检查 + 自动重启；网关降级（模型不可用时返回友好提示而非 500）。
- **限流**：入口 + 模型网关双层限流，防单用户打爆。
- **背压**：下游慢（DB/业务系统）时 Agent 排队而非雪崩。

---

## 四、故障演练与韧性

- **混沌测试**：故意杀掉 Agent Pod / 模型网关超时 / 向量库宕机，验证降级与恢复。
- **循环/卡死演练**：注入坏输入让 Agent 循环，验证熔断。
- **数据恢复**：状态外置，演练从 checkpoint 恢复长任务。
- **回滚预案**：prompt/模型/代码任一层出问题，5 分钟内回滚。

---

## 五、监控与告警

- **业务指标**：任务成功率、用户满意度、转人工率。
- **技术指标**：p95 延迟、错误率、GPU 利用率、队列深度。
- **成本指标**：日/周成本、单任务成本、超预算告警。
- **安全指标**：越权尝试、注入拦截、异常工具调用。

---

## 六、合规与审计

- **数据驻留**：合规数据不出域（私有化 + 脱敏，见 04 篇）。
- **审计留痕**：所有运行可回放（见 05 篇 Run Record）。
- **模型备案**：国内生成式 AI 服务按规定备案/登记。
- **定期安全审计**：红队复测、依赖漏洞扫描（OWASP LLM01-10）、权限复核。

---

## 七、On-call 与运维手册

- **On-call 轮值**：Agent 故障有人接（模型供应商宕机、私有 GPU 故障、向量库慢）。
- **Runbook**：常见问题排查（延迟高→看哪层；答非所问→检索还是生成问题；成本突增→哪个租户）。
- **知识沉淀**：每次事故写复盘，更新 eval 用例防止复现。

## 十、典型故障场景与处置 Runbook（Agent 专属）

| 故障现象 | 可能根因 | 处置步骤 | 预防 |
|----------|----------|----------|------|
| 延迟突增 | 模型网关排队 / GPU 满载 / RAG 检索慢 | 看队列深度与 GPU 利用率 → 扩容或降级 | 双层限流 + 背压 |
| 答非所问 | RAG 召回差 / prompt 被污染 / 模型漂移 | 对比 eval 集 → 定位检索 or 生成 | 线上 eval + 影子评测 |
| 循环卡死 | Agent 陷入重复工具调用 | 熔断 + 最大步数兜底 + 重启会话 | 循环检测 |
| 成本突增 | 某租户长上下文 / 重试风暴 | 成本看板定位 → 限流/配额 | 预算告警 + 单租户配额 |
| 越权/注入 | 权限校验缺失 / 提示注入成功 | 先停工具 → 审计回放 → 补校验 | 网关鉴权 + 输出过滤 |
| 模型供应商宕机 | 公有云 API 不可用 | 切私有化路径 / 友好降级提示 | 多供应商路由 + 降级预案 |

> 运维心法：**每个故障都要追问「eval 用例是否已补」**——Agent 事故的根因常能沉淀为回归用例，把「再发生」变成「可验证」。

### 10.1 2025-2026 部署层新变化（AI Infra 前沿）

1. **推理引擎进入「2.0 时代」**：vLLM/SGLang 竞速（speculative decoding、chunked prefill、RadixAttention 前缀复用）之外，**PD 分离（Prefill/Decode Disaggregation）**让 prefill 池与 decode 池独立扩缩（成本降 30-50%，见「训练与部署/05」）；2026 年推理栈出现「引擎无关」化——K8s 上多引擎并存按负载路由；
2. **KV Cache 规模化**：显存大头从权重转移到 KV——「KV 做分层存储（GPU→CPU→NVMe 分级）」与「KV 量化（FP8/INT8/INT4）」成为吞吐的关键杠杆；长上下文场景靠**前缀缓存（Radix/Prompt Cache）**省 90%+ prefill；
3. **模型路由成为常态**：按查询难度自动路由（小模型打底、大模型兜底、推理模型难任务），配合**语义缓存**（相似 query 直接复用答案，见「上下文工程/02」提示缓存）；
4. **多模态/推理模型的部署差异**：推理模型要配 **thinking budget 上限 + 超时兜底**（防无限思考烧钱）；多模态要吃**视觉 token 预算**（见「训练与部署/06」）；
5. **AI 网关标准化**：LiteLLM 类网关 + OTel GenAI semconv 成为标配（成本/延迟/失败率统一观测，见 06 篇）。

> 一句话：**2026 年部署的竞争焦点 = 推理引擎优化（PD 分离/前缀缓存/KV 分层）× 模型路由（难度路由/语义缓存）× 成本观测（token 级计量）三件事。**

## 十一、面试高频追问

1. Q：Agent 部署和传统服务部署最大区别？ A：状态外置（工作流/会话可恢复）+ 模型层也要灰度（会漂移）+ 需要循环/卡死防护（非传统超时能解决）。
2. Q：私有化 GPU 怎么弹性？ A：vLLM 等推理引擎 + K8s Operator 池化 + HPA，MIG/MPS 分卡共享，闲时缩容。
3. Q：模型版本怎么安全上线？ A：影子评估 → 金丝雀 → 全量，每步盯 eval 指标与延迟/成本；随时可回滚到上一版权重。
4. Q：模型网关的价值？ A：统一入口做路由（公有/私有）、限流、降级、成本计量、多供应商容灾——Agent 服务的「流量调度中枢」。
5. Q：怎么证明系统能扛故障？ A：混沌演练（杀 Pod/超时/循环）+ 回滚演练 + 定期复盘，与 SRE 板块的韧性方法论一致。
