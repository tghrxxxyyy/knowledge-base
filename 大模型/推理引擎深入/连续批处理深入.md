# 连续批处理深入

> 对应 llm-course（mlabonne）推理优化章节；vLLM 连续批处理（continuous batching）；相关研究如 Orca（Yu et al., 2022）动态批处理调度（以官方最新文档为准）。

## 一、背景与挑战

推理服务的核心矛盾：GPU 算力强，但请求的「到达时间、长度、结束时刻」都不同。传统静态批处理（static batching）把一批请求凑齐、用最长序列填充（padding）再统一计算：

- 空等：短请求必须等长请求结束才能一起返回，GPU 在等待中闲置。
- 填充浪费：padding token 仍占算力。
- 利用率低：长尾请求拖垮整批吞吐。

连续批处理（continuous / in-flight batching）正是为解决「请求异步进出」而生。

## 二、核心原理

核心思想：在自回归生成的每一步（每个 decoding step），由调度器动态决定「本步哪些序列参与计算」：

1. 就绪即入批：新请求到达随时加入当前步。
2. 完成即退出：某序列生成 EOS 或达 max_len，立刻移出，不阻塞他人。
3. 步级重排：每步重新组批，GPU 始终在跑「当前所有活跃序列」。
4. 与 PagedAttention 配合：KV 按块分配，序列进出不要求连续显存。

调度与内存分配强耦合——新增序列需分配 KV 页，退出序列回收页，避免碎片。

## 三、形式化与数学基础

设时刻 $t$ 活跃序列集合 $A_t$，单步算力正比于 $\sum_{s\in A_t} \text{len}_s$。理想调度使 GPU 占用率

$$ U = \frac{\sum_t \sum_{s\in A_t} c_s}{\sum_t C_{\max}} \to 1 $$

其中 $C_{\max}$ 为单步算力上限，$c_s$ 为序列 $s$ 单步代价。静态批因等待与填充，使部分时刻 $A_t$ 稀疏或含大量 padding；连续批通过「完成即退、到达即进」最大化各时刻 $|A_t|$。

## 四、代码实现

```python
# 连续批处理调度示意（伪代码）
class Scheduler:
    def step(self, running, waiting):
        batch = []
        for seq in running:
            if seq.done:
                self.free(seq)        # 回收 KV 页
            else:
                batch.append(seq)
        # 在显存/配额允许下接纳新请求
        while waiting and self.has_room():
            batch.append(waiting.pop())
        return batch

# 推理循环
while scheduler.active():
    batch = scheduler.step(running, waiting)
    out = model.forward(batch)        # 一步解码
    running, waiting = scheduler.update(out)
```

## 五、与其他技术对比

| 方式 | 组批 | 延迟 | 吞吐 |
|------|------|------|------|
| 静态批 | 固定 | 高（空等） | 低 |
| 连续批 | 步级动态 | 低 | 高 |

连续批以调度复杂度换取 GPU 利用率跃升。

## 六、常见误区

- 批越大越好：盲目增大并发会推高每请求延迟，甚至 OOM。
- 连续批零成本：调度与 KV 分配管理本身有开销，需精细实现。
- 忽视长请求饿死：需公平调度，避免短请求被长请求长期挤占。

## 九、演进与趋势

无批 → 静态批（padding）→ 连续批（步级动态）→ 与抢占式调度、优先级队列结合。趋势是把「序列级调度」做成可插拔策略，并支持 SLA 感知（保证 P99 延迟）。

抢占式调度（preemption）能在高优先级请求到达时挂起长请求、先服务短请求，从而改善 P99，但挂起/恢复需要保存中间激活，带来额外开销。

在实际系统中，连续批常与前缀缓存、KV 量化协同：批内请求共享前缀块、压缩 KV，进一步抬高有效并发上限。

## 十、小结

连续批处理是吞吐引擎的心脏：通过「每步动态组批、完成即退、到达即进」，把 GPU 利用率推到极致。它与 PagedAttention 是当代推理引擎的两大基石。
