# 推理引擎选型

> 对应 llm-course（mlabonne）部署章节；主流引擎官方文档：vLLM、Text Generation Inference (TGI)、TensorRT-LLM、llama.cpp、SGLang（具体能力与版本以官方最新文档为准）。

## 一、背景与挑战

推理引擎决定了「模型上线后的吞吐、延迟、成本与可部署形态」。不同引擎在以下维度差异显著：

- 硬件适配：NVIDIA GPU、AMD、CPU、端侧 NPU。
- 特性支持：连续批、PagedAttention、前缀缓存、量化、投机解码。
- 易用性：Python 生态 vs C++/CUDA 内核。
- 生产成熟度：鉴权、流式、指标、多模型路由。

没有「最快」的通用引擎，只有「最匹配场景」的引擎。

## 二、核心原理

各引擎定位：

- vLLM：高吞吐 Python 引擎，PagedAttention + 连续批，服务端首选。
- TGI（HuggingFace）：生产级、易集成 HF 生态，支持量化与流式。
- TensorRT-LLM：NVIDIA 深度优化，极致低延迟/高吞吐，部署成本高。
- llama.cpp：纯 C++/GGUF，CPU 与端侧、消费级 GPU 友好。
- SGLang：RadixAttention 前缀复用 + 结构化生成，高并发复用场景强。

选型本质是「性能 × 硬件 × 运维复杂度 × 特性」的多目标权衡。落地时建议先用小规模基准（如 ShareGPT 轨迹）在当前硬件上跑通候选引擎，再按 SLA 指标（P99 延迟、峰值吞吐、每 token 成本）排序，而非仅凭社区口碑。对于需要多模型共存或灰度发布的团队，还应考察引擎的「多 LoRA 服务、前缀缓存命中率、量化支持（AWQ/GPTQ/FP8）」等运维特性，这些往往比纯吞吐更能决定长期成本。

## 三、形式化与数学基础

设引擎 $e$ 在硬件 $h$ 上给出指标向量 $(Q_e, L_e^{\text{ttft}}, L_e^{\text{tpot}}, M_e, C_e)$，其中 $Q$ 吞吐、$L$ 延迟、$M$ 显存、$C$ 成本。选型即求解约束优化：

$$ \max_e\; \alpha Q_e - \beta L_e^{\text{p99}} \quad \text{s.t.}\quad M_e \le M_{\text{budget}},\; C_e \le C_{\text{budget}} $$

权重 $\alpha,\beta$ 由业务 SLA 决定（交互场景重 $\beta$，离线批处理重 $\alpha$）。

llm = LLM(model="meta-llama/Llama-3-8B", gpu_memory_utilization=0.9)

# 端侧（llama.cpp，GGUF）

## 五、与其他技术对比

| 引擎 | 强项 | 典型场景 |
|------|------|----------|
| vLLM | 吞吐、生态 | 服务端 API |
| TGI | 生产集成 | HF 生态部署 |
| TensorRT-LLM | NVIDIA 极限性能 | 高并发低延迟 |
| llama.cpp | 端侧/CPU | 本地、手机 |
| SGLang | 前缀复用 | 结构化/高并发 |

## 六、常见误区

- 最快引擎通用：必须匹配硬件与特性集。
- 只看吞吐：交互场景延迟（TTFT/TPOT）更影响体验。
- 忽视运维：C++ 引擎性能高但集成与排障成本上升。
- 忽视量化支持：同模型开/关 AWQ、GPTQ、FP8 时吞吐与显存差异巨大，选型必须实测。

补充视角：引擎选型还应区分「在线服务」与「离线批处理」。在线交互重 P99 延迟与流式体验，常选 vLLM/SGLang；离线批量摘要/抽取重总吞吐与成本，可放宽延迟选 TRT-LLM 批式内核。把场景误配引擎是上线后性能不达预期的最常见根因。

## 九、演进与趋势

原生 HF generate → vLLM（PagedAttention）→ TRT-LLM/SGLang（极致优化）→ 多引擎统一编排（如生产网关按负载路由）。趋势是「开箱即用的高吞吐 + 多硬件后端 + 量化一体」。值得注意，硬件格局正在多元化：AMD ROCm、国产加速卡、以及 CPU/GPU 混合部署，使「引擎 × 硬件」的组合空间扩大，选型时必须以目标硬件的可达性为前提，而非只看 NVIDIA 上的 benchmark 数字。

在异构算力环境下，还应评估引擎对量化格式的生态成熟度：例如 FP8 在 Hopper 架构上有显著收益，但部分引擎的 FP8 路径尚不完善，实测才能定论。

多模型服务场景要关注「模型加载/卸载」与「显存碎片整理」机制，频繁切换模型时，能否快速 reclaim 显存直接决定尾延迟。

对于预算敏感的项目，选型结论往往由「每千 token 成本」而非「峰值吞吐」决定，因此必须把硬件租金计入比较。

## 十、小结

选型决定部署效率上限：以「吞吐/延迟/成本/硬件/特性」五维权衡，没有银弹，只有最匹配业务 SLA 的选择。
