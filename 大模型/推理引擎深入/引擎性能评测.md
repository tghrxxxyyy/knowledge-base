# 引擎性能评测

> 对应 llm-course（mlabonne）部署与评测章节；vLLM / TensorRT-LLM 自带 benchmark 工具；常用评测负载 ShareGPT、Sonnet 对话轨迹（以官方最新文档为准）。

## 一、背景与挑战

选型与容量规划不能拍脑袋：不同推理引擎在相同硬件上吞吐可差数倍。评测目标是从「延迟、吞吐、成本、显存」四维量化比较，但难点在于：

- 负载敏感：不同请求长度/并发下结论可能反转。
- 指标耦合：提高并发提吞吐却推高延迟。
- 可复现难：随机性、批调度、预热都影响结果。

因此需贴近真实流量分布的标准化基准。

## 二、核心原理

评测围绕四个关键指标：

1. TTFT（Time To First Token）：首 token 延迟，反映 prefill 与排队，影响「响应感」。
2. TPOT（Time Per Output Token）：每输出 token 延迟，反映 decode 速度，影响「流式体感」。
3. 吞吐：QPS（请求/秒）或 token/s（总生成速度）。
4. 显存与成本：峰值显存、每千 token 价格。

用真实轨迹（如 ShareGPT 对话）回放，固定并发/速率，统计 P50/P90/P99 分位，再用成本折算性价比。

## 三、形式化与数学基础

设第 $i$ 请求首延迟 $t_i^{\text{ttft}}$、生成 $n_i$ token 总时 $T_i$，则

$$ \text{TPOT}_i = \frac{T_i - t_i^{\text{ttft}}}{n_i} $$

系统吞吐（token/s）：

$$ \Theta = \frac{\sum_i n_i}{\max_j T_j^{\text{end}} - T_0} $$

延迟服务水平（SLA）常以 P99 衡量：

$$ \text{P99} = \text{quantile}_{0.99}(\{t_i^{\text{ttft}}\}) $$

成本效率定义为每美元产出的 token 数 $\eta = \Theta / \text{cost}$。

## 四、代码实现

```python
# 基于轨迹测 TTFT / TPOT（示意）
import time, statistics

def measure(req_fn, trace):
    ttfts, tpots = [], []
    for prompt, n_expected in trace:
        t0 = time.time()
        first = True
        for tok in req_fn(prompt):        # 流式返回
            if first:
                ttfts.append(time.time() - t0)
                t_first = time.time()
                first = False
            last = time.time()
        tpots.append((last - t_first) / max(n_expected, 1))
    return statistics.median(ttfts), statistics.median(tpots)

print(measure(engine.chat, sharegpt_trace))
```

## 五、与其他技术对比

| 维度 | 模型评测 | 引擎评测 |
|------|----------|----------|
| 关注 | 质量/准确率 | 延迟/吞吐/成本 |
| 指标 | 基准分 | TTFT/TPOT/QPS |
| 方法 | 数据集 | 负载回放 |

二者正交：好模型配差引擎仍体验差。

## 六、常见误区

- 单指标定优劣：吞吐高可能以延迟崩坏为代价。
- 用合成均匀负载：真实流量长尾明显，需轨迹回放。
- 忽略预热：冷启动与缓存未建立时数据失真。

## 九、演进与趋势

手测延迟 → 脚本化压测 → 标准轨迹基准（ShareGPT 等）→ SLA 感知评测（P99 + 成本）。趋势是把「延迟分位 + 成本 + 质量」联合成统一选型看板。

## 十、小结

引擎评测驱动理性选型：以 TTFT/TPOT/吞吐/成本四维、用真实轨迹回放并看分位，才能避免「凭感觉」导致的部署翻车。
