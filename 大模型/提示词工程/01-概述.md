# 提示词工程概述

> 提示词工程（Prompt Engineering）是「设计、优化输入指令，以高效利用大语言模型（LLM）解决任务」的学科。它不改变模型权重，只通过输入侧的设计来稳定、可控地拿到更好输出。

## 一、为什么值得学

LLM 的能力上限很高，但**输出质量高度依赖提示词的质量与结构**。同一模型，提示词写得好坏，结果可能天差地别：

- 更准：减少幻觉、跑题、格式错误
- 更稳：在多轮、多输入下保持一致的风格与结构
- 更省：用更短的提示、更少的来回就拿到可用结果，降低 token 成本与延迟

> Anthropic 的一个企业案例：提示工程师结合业务专家的领域知识优化提示词后，客服问答机器人的**准确率提升约 20%**，同时更快上线、成本更低。

## 二、提示词的组成要素

一个完整的提示通常包含以下部分（不必全有，按需组合）：

| 要素 | 作用 | 示例 |
| --- | --- | --- |
| 指令（Instruction） | 告诉模型要做什么 | 「将下面文本总结为 3 条要点」 |
| 上下文（Context） | 背景、约束、领域知识 | 公司规范、数据库 schema、用户画像 |
| 示例（Examples） | 用 few-shot 校准格式/风格 | 给 3 个「输入→输出」样例 |
| 输入（Input） | 本次要处理的具体数据 | 待总结的文章、待分类的评论 |
| 输出格式（Output） | 明确想要的返回结构 | JSON、`###` 分段、表格 |

## 三、两种「学习」范式（对理解少样本很重要）

| 范式 | 含义 | 适用 |
| --- | --- | --- |
| 零样本（Zero-shot） | 不给任何示例，仅靠指令 | 常见、明确的任务 |
| 单样本（One-shot） | 给 1 个示例 | 需要统一风格/约定 |
| 少样本（Few-shot） | 给多个示例 | 复杂格式、边界情况、一致性要求高 |

> 微调（fine-tuning）是另一条路：用成百上千条样本训练模型权重。提示词工程 + 少量示例通常先用，不够再考虑微调。OpenAI 的建议路径即：**先零样本 → 再少样本 → 都不行再微调**。

## 四、核心心法（一句话版）

> 把模型当成「能力很强、但对你业务零背景的新同事」。
> 你交代得越清楚（目标、上下文、格式、边界、示例），它交得越对。

> ⚠️ 不同模型的「脾气」不同：Anthropic（Claude）偏爱 XML 标签结构化、OpenAI 偏好的分隔符是 `###`/`"""`、代码模型偏爱吃「引导词」。**没有跨模型通用的最优提示，务必针对你实际使用的模型做小样本验证。**

## 五、常见反例（Bad vs Good）

提示词没有公式，但有很多「踩坑模板」。下面用反例说明什么叫「模糊指令」——先看反例，再对照正例改。

| 反例 ❌ | 问题 | 正例 ✅ |
| --- | --- | --- |
| 「写得好一点」 | 不可验证、无标准 | 「写成 3 条要点，每条不超过 20 字，面向非技术读者」 |
| 「不要写代码注释」 | 负向指令易遗漏边界 | 「只写必要注释，不解释显而易见的逻辑」 |
| 「总结一下」 | 没说长度 / 角度 | 「用 100 字总结本文的 3 个核心论点」 |
| 一次性塞 10 个技巧 | 互相打架、难排障 | 先最小可用，再评测迭代叠加 |

```text
反例 ❌：帮我改下这个函数，让它更好。
正例 ✅：把下面 Python 函数重构为异步（async/await），
      保持入参出参不变，补充类型注解，并加一句 docstring。
```

> 把反例当「体检表」：写完提示词自查一遍——是否有不可验证的词、是否有负向指令、是否一次堆太多技巧。

## 六、结构化提示模板（生产级）

生产环境（尤其是调用 API 的场景）建议用固定模板 + 变量填充，而不是每次都重新措辞：

```text
<role>    你是一名资深后端架构师，回答要专业、克制、给出取舍。</role>
<task>    评估下面方案在高并发下的风险，并给出 3 条改进建议。</task>
<context> 业务: 日活 1000 万; 已有组件: MySQL 主从、Redis、Kafka。</context>
<input>   【方案内容见下方】</input>
<output>  按「风险 | 原因 | 改进建议」输出三行表格。</output>
```

| 好处 | 说明 |
| --- | --- |
| 可复用 | 变量位（task/input）替换即用 |
| 可评测 | 模板固定后，只改输入做批量验证 |
| 可回滚 | 出问题能定位是模板还是输入导致 |
| 可维护 | 提示词纳入版本管理（Git），随模型迭代更新 |

> Anthropic/OpenAI 官方指南一致强调：**把变量位与固定指令分开**、避免把用户输入直接拼进指令（防注入，见下方安全节）。

## 七、进阶：思维链与角色扮演

| 技巧 | 原理 | 示例 |
| --- | --- | --- |
| 思维链（CoT） | 让模型「先思考再回答」，把推理过程显式写出 | 「请先列出已知条件，再逐步推导」 |
| 少样本 CoT | 给含推理过程的示例，效果强于只给结论示例 | 示例里写清「先…再…所以…」 |
| 角色扮演 | 限定视角与语气，稳定输出风格 | 「你是一名儿科医生」 |
| 温度控制 | 低温度更确定（分类/提取），高温度更发散（创作） | 事实型任务 temperature=0 |

> ⚠️ CoT 提升推理准确率，但**推理过程可能本身是错的**（模型编造逻辑）——生产场景只信「结构化输出 + 程序校验」，不要把模型的中间推理当证据（详见 [推理与思考模型](../推理与思考模型/01-核心原理与训练机制.md)）。
>
> 💡 **推理模型的提示差异**：对 o3/Claude 扩展思考/R1 类模型，**不要显式要求「请逐步思考」**——模型内置思考机制，显式 CoT 反而多余甚至干扰；用 `reasoning_effort` / thinking budget 旋钮控制思考强度即可（详见 [推理与思考模型](../推理与思考模型/02-工程实践与成本治理.md)）。

## 七之二、提示缓存（Prompt Caching）——成本杠杆

系统提示/长示例等**稳定前缀**每次请求都重算输入 token，浪费成本。提示缓存让**命中缓存的前缀 token 按低折扣计费**，同时加快首字延迟：

- **触发条件**：前缀必须 **byte 级完全一致**（前 1024 token 起命中，越长折扣越大），任何改动（甚至末尾换行）导致缓存失效；
- **工程姿势**：把「静态内容（system prompt/示例/工具定义）」放在最前，动态内容（用户输入/RAG 片段）放最后；system prompt 尽量不改版，改版走版本号切换；
- **成本量级**：典型折扣 90%（Anthropic）~50%（OpenAI），命中率 80%+ 的固定前缀场景成本可降 50~70%；
- **推理模型注意**：思考 token 不参与缓存（见推理模块成本篇），别指望思考部分摊薄。

> 详细机制与厂商对比见「[上下文工程/02-核心原理与杠杆.md](../上下文工程/02-核心原理与杠杆.md)」缓存章节与「[RAG/03-评估与最佳实践.md](../RAG/03-评估与最佳实践.md)」。

## 八、提示注入与安全

```
用户输入恶意内容 → 若被拼入指令 → 模型可能泄露 system prompt / 越权操作
```

| 防护手段 | 做法 |
| --- | --- |
| 输入隔离 | 用户输入放入 `<input>` 分隔符，与指令物理隔离 |
| 输出过滤 | 敏感词/指令特征校验后再用 |
| 权限最小化 | 模型能调的工具/API 限到最小范围 |
| 不加信任 | 模型输出一律按「不可信输入」处理（不直接拼 SQL/命令） |

**2025 强化视角**：
- **指令层次（Instruction Hierarchy）**：指令按「系统 > 用户 > 工具输出」分层，低层指令永远不能覆盖高层——OpenAI 官方防线，比单纯分隔符可靠；
- **间接注入**：恶意内容藏进 **RAG 检索到的文档 / 网页 / 工具返回值**（不经用户输入），比直接注入更难防——检索结果与工具输出一律按不可信处理，且标注来源；
- **输出侧防御**：输出编码/重写（如 URL 编码拦截）防止注入指令被下游执行。

## 九、评测与迭代闭环

提示词工程是**迭代工程**，不是一次成型：

```
基线(定义评测集: 50~200 条真实输入+期望输出)
 → 尝试新提示 → 批量跑评测集 → 对比指标(准确率/格式合规率/长度)
 → 保留最优版本 → 回归线上
```

| 评测维度 | 常见指标 |
| --- | --- |
| 正确性 | 准确率、与参考答案相似度（人工/LLM-as-Judge） |
| 格式 | 合法 JSON 比例、字段齐全率 |
| 稳定性 | 同输入多次输出方差 |
| 成本 | 平均 token 数、延迟 P95 |

> 没有评测集的提示词优化 ≈ 没有测试的代码重构：感觉「变好了」不算数，数字才算。
