# 提示词工程概述

> 提示词工程（Prompt Engineering）是「设计、优化输入指令，以高效利用大语言模型（LLM）解决任务」的学科。它不改变模型权重，只通过输入侧的设计来稳定、可控地拿到更好输出。

## 一、为什么值得学

LLM 的能力上限很高，但**输出质量高度依赖提示词的质量与结构**。同一模型，提示词写得好坏，结果可能天差地别：

- 更准：减少幻觉、跑题、格式错误
- 更稳：在多轮、多输入下保持一致的风格与结构
- 更省：用更短的提示、更少的来回就拿到可用结果，降低 token 成本与延迟

> Anthropic 的一个企业案例：提示工程师结合业务专家的领域知识优化提示词后，客服问答机器人的**准确率提升约 20%**，同时更快上线、成本更低。

## 二、提示词的组成要素

一个完整的提示通常包含以下部分（不必全有，按需组合）：

| 要素 | 作用 | 示例 |
| --- | --- | --- |
| 指令（Instruction） | 告诉模型要做什么 | 「将下面文本总结为 3 条要点」 |
| 上下文（Context） | 背景、约束、领域知识 | 公司规范、数据库 schema、用户画像 |
| 示例（Examples） | 用 few-shot 校准格式/风格 | 给 3 个「输入→输出」样例 |
| 输入（Input） | 本次要处理的具体数据 | 待总结的文章、待分类的评论 |
| 输出格式（Output） | 明确想要的返回结构 | JSON、`###` 分段、表格 |

## 三、两种「学习」范式（对理解少样本很重要）

| 范式 | 含义 | 适用 |
| --- | --- | --- |
| 零样本（Zero-shot） | 不给任何示例，仅靠指令 | 常见、明确的任务 |
| 单样本（One-shot） | 给 1 个示例 | 需要统一风格/约定 |
| 少样本（Few-shot） | 给多个示例 | 复杂格式、边界情况、一致性要求高 |

> 微调（fine-tuning）是另一条路：用成百上千条样本训练模型权重。提示词工程 + 少量示例通常先用，不够再考虑微调。OpenAI 的建议路径即：**先零样本 → 再少样本 → 都不行再微调**。

## 四、核心心法（一句话版）

> 把模型当成「能力很强、但对你业务零背景的新同事」。
> 你交代得越清楚（目标、上下文、格式、边界、示例），它交得越对。

> ⚠️ 不同模型的「脾气」不同：Anthropic（Claude）偏爱 XML 标签结构化、OpenAI 偏好的分隔符是 `###`/`"""`、代码模型偏爱吃「引导词」。**没有跨模型通用的最优提示，务必针对你实际使用的模型做小样本验证。**

## 五、常见反例（Bad vs Good）

提示词没有公式，但有很多「踩坑模板」。下面用反例说明什么叫「模糊指令」——先看反例，再对照正例改。

| 反例 ❌ | 问题 | 正例 ✅ |
| --- | --- | --- |
| 「写得好一点」 | 不可验证、无标准 | 「写成 3 条要点，每条不超过 20 字，面向非技术读者」 |
| 「不要写代码注释」 | 负向指令易遗漏边界 | 「只写必要注释，不解释显而易见的逻辑」 |
| 「总结一下」 | 没说长度 / 角度 | 「用 100 字总结本文的 3 个核心论点」 |
| 一次性塞 10 个技巧 | 互相打架、难排障 | 先最小可用，再评测迭代叠加 |

```text
反例 ❌：帮我改下这个函数，让它更好。
正例 ✅：把下面 Python 函数重构为异步（async/await），
      保持入参出参不变，补充类型注解，并加一句 docstring。
```

> 把反例当「体检表」：写完提示词自查一遍——是否有不可验证的词、是否有负向指令、是否一次堆太多技巧。
