# 提示技巧与模式

> 本节按「从基础到进阶」排列常用模式。多数来自 dair-ai/Prompt-Engineering-Guide 与 Anthropic/OpenAI 实践文档。每个模式标注「适用场景」，便于按任务取用。

## 一、基础模式

### 1. 零样本提示（Zero-Shot）
不给示例，直接下指令。适合常见、边界清晰的任务。

```text
把下面这段用户评论分类为：正面 / 负面 / 中性。
评论：{text}
分类：
```

### 2. 少样本提示（Few-Shot / In-Context Learning）
在提示里给若干「输入→输出」样例，让模型照着学格式与风格。示例要**相关、多样、覆盖边界**。

```text
提取下方文本的关键词。
文本1：Stripe 提供 API，开发者可将其集成到网站与移动应用中做支付处理。
关键词1：Stripe, 支付处理, API, 网站, 移动应用
##
文本2：OpenAI 训练了擅长理解与生成文本的前沿语言模型。
关键词2：OpenAI, 语言模型, 文本处理, API
##
文本3：{text}
关键词3：
```

> ⚠️ 示例顺序、数量会影响结果。建议 3–5 个；若模型「照抄」了示例里的意外模式，说明示例不够多样。

## 二、推理增强模式

### 3. 思维链（Chain-of-Thought, CoT）
让模型**先一步步推理再给答案**，显著提升复杂/数学/逻辑题表现。最简单写法：在提示末尾加 `让我们一步步思考。`

```text
问题：操场上有 3 棵树，每棵树上有 4 只鸟，飞走 5 只，还剩几只？
让我们一步步思考。
```

变体：
- **Self-Consistency（自洽）**：采样多条推理路径，取多数答案，比单条 CoT 更稳。
- **Tree of Thoughts（ToT，思维树）**：让模型在每一步生成多个候选并自我评估/剪枝，适合需要搜索与回溯的难题。

### 4. 生成知识提示（Generate Knowledge Prompting）
先让模型「回忆/生成」完成任务所需的知识，再基于这些知识作答，常用于常识/事实类任务。

```text
第一步：列出判断一段文本是否为讽刺所需的关键信号。
第二步：基于上述信号，判断下面这段文本是否为讽刺。
文本：{text}
```

### 5. 草稿本 / 显式思考（Scratchpad）
让模型把「中间思考」写进特定标签（如 `<thinking>`、`<scratchpad>`），用户看不到但能帮助模型算得更准。Anthropic 税务案例中用 `<quotes>` 让模型先抽原文再作答，本质同此思路。

```xml
<scratchpad>
先列出所有候选方案及其权衡，再决定最终答案。
</scratchpad>
```

## 三、工具 / 行动增强模式

### 6. ReAct（推理 + 行动）
交替进行「思考（Thought）→ 行动（Action）→ 观察（Observation）」循环，让模型调用工具（搜索、查库、执行代码）并基于结果继续推理。是构建 Agent 的核心提示范式。

```text
你是一个能使用工具的智能体。每一步输出：
Thought: 我现在需要知道 X
Action: search("X")
Observation: （工具返回）
...循环，直到能回答用户问题。
```

### 7. ART（Automatic Reasoning and Tool-use）
先把任务拆成「推理步骤 + 工具调用」的骨架示例，模型照骨架执行，兼顾推理与工具使用，减少手写编排。

## 四、结构 / 控制模式

### 8. XML 标签结构化（Claude 强相关）
见「02-核心原则」第二节。一句话：用一致、有语义的标签把指令/上下文/示例/输入分开，复杂提示必备。

### 9. 角色设定（Role Prompting）
让模型扮演某领域专家，首轮即更对口。

```text
你是一名资深 MySQL DBA。请评审下面这条慢查询 SQL，
指出索引缺失点并给出改写建议。
SQL：{sql}
```

### 10. 预填充回答（Prefill / 引导开头）
在 assistant 的首个回复里先写半句，把模型「拐」向目标结构。例如想让它输出 JSON，可以先预填 `{`；想让它先引用再作答，可预填 `<quotes>`。

### 11. 链式提示（Chain Prompting）
把一个大任务拆成多个子提示逐步推进，每步输出作为下一步输入。适合：长文写作、多步代码生成、复杂分析。

```text
第1轮：列出本文的 3 个核心论点。
第2轮：针对第1轮的每个论点，各写一个支撑段落。
第3轮：把上面内容整合成一篇 800 字文章，加标题。
```

### 12. 主动提示（Active-Prompt）
对模型「不确定」的样本，人工标注正确推理链，再用这些高质量样本做 few-shot，针对性补强弱点。

### 13. 方向性刺激提示（Directional Stimulus Prompting）
在提示里加一句「希望输出具备某特质」的刺激语（如「简洁」「正式」「有同理心」），用 APE 自动发现最优刺激语。

## 五、模式选型速查

| 你想解决 | 优先尝试 |
| --- | --- |
| 分类 / 抽取 / 格式化 | 少样本（给格式示例） |
| 数学 / 逻辑 / 多步推理 | CoT → 自洽 → ToT |
| 需要查最新/外部信息 | ReAct + 工具 |
| 长文档问答、防幻觉 | 长上下文摆位 + 引用原文（grounding） |
| 稳定风格/领域口吻 | 角色设定 + few-shot |
| 可控结构化输出 | XML 标签 + 预填充 + 输出格式示例 |
| 超长/超复杂任务 | 链式提示分步推进 |

> ⚠️ 模式可以组合：例如「角色设定 + 少样本 + CoT + XML 标签」同框出现非常常见。关键是**先跑通最小可用提示，再用评测小样本迭代**，不要一上来堆满所有技巧。

## 六、Chain-of-Thought / ToT 实战（模板 + 反例）

### CoT 触发

最简单写法：末尾加「请一步步思考」，或显式用 `<scratchpad>` 让模型先写推理再答。

```text
问题：{math / logic}
要求：先把推理过程写进 <thinking>，再给最终答案 <answer>。
```

### Self-Consistency（自洽）

采样 N 条推理路径，取多数答案，比单条 CoT 更稳：

```python
answers = [generate(prompt) for _ in range(5)]
final = max(set(answers), key=answers.count)   # 多数投票
```

### ToT（思维树）

每步生成多个候选并自我评估 / 剪枝，适合需要搜索与回溯的难题：

```text
对每个候选方案打分（1-10），保留 Top-2 进入下一层，
直到得出可行解或达到深度上限。
```

**反例 ❌**：`直接给我答案，别废话。` —— 对数学 / 多步推理题会显著降低准确率，跳过推理易错。

## 七、结构化输出（模板 + 反例）

### 模板

用 JSON + 字段约束 + 预填充 `{` 把模型拐向目标结构：

```json
{
  "summary": "<50字摘要>",
  "tags": ["标签1", "标签2"],
  "confidence": 0.0
}
```

**反例 ❌**：`返回一个包含总结和标签的结果。` —— 模型可能返回散文，无法程序解析。

### 要点

- 预填开头（如 `{` 或 `<quotes>`）把模型引向结构。
- 用 JSON Schema / 函数调用（tool use）强制结构最稳，胜过纯文本约束。
- 复杂任务要求先引用原文再输出（grounding），降低幻觉、便于校验。

## 八、对抗幻觉（模板 + 反例）

### 模板

限定知识边界 + 要求引用 + 未知就明说：

```xml
<instructions>
只基于 <context> 回答。若上下文没有相关信息，
明确回答「我不知道」，禁止编造。
先抽原文到 <quotes>，再写 <answer>。
</instructions>
```

**反例 ❌**：`尽可能回答用户问题。` —— 模型倾向脑补，产生幻觉。

### 补充手段

- 用 RAG 注入事实来源（见 RAG 模块）。
- 用 faithfulness 校验（见 RAG 03）在线拦截编造。
- 关键场景要求给出引用 / 出处，便于人工核查。
- 对事实性强的问题，显式要求「不确定就说是不确定」，比沉默或编造更安全。

## 九、更多推理 / 行动模式（Plan-and-Solve / Reflexion）

### Plan-and-Solve（先规划再执行）
把「先想整体方案再逐步做」显式化：先让模型产出**分步计划**，再按计划逐步执行，避免一上来就钻细节走偏。适合复杂多步任务。

```text
第一步：列出完成 {任务} 的不少于 3 步计划。
第二步：逐步执行计划，每完成一步检查是否偏离目标。
```

### Reflexion（自我反思）
Agent 在任务失败/不满意后，**写一段自然语言「反思」存进记忆**，下一轮尝试时读回，避免重复犯错。是「记忆 + 提示」结合的自我改进闭环。

```text
反思：上一轮我在 X 处假设了 Y，但工具返回证明 Y 错误；
本轮应改为 Z 策略，并先验证再行动。
```

> 💡 与 ReAct 区别：ReAct 是单轮内「思考-行动-观察」；Reflexion 跨轮「失败→反思→改进」，需配合记忆/外部存储。三者常组合：ReAct 执行、Plan-and-Solve 规划、Reflexion 复盘。

## 十、结构化输出进阶（JSON Schema / 函数调用）

纯文本约束结构不稳，工程上优先用「机器强制」：

| 方式 | 做法 | 稳定性 |
| --- | --- | --- |
| 文本 + 预填充 | 给 JSON 模板、`{` 起手 | 中（仍可能跑偏） |
| JSON Schema | 用结构化输出接口传 schema，模型只能填字段 | 高 |
| 函数调用 / Tool Use | 把输出定义为函数参数，模型调函数 | 最高（强类型） |

```python
# OpenAI 结构化输出（JSON Schema 约束）
from pydantic import BaseModel
class Extract(BaseModel):
    summary: str
    tags: list[str]
    confidence: float
completion = client.beta.chat.completions.parse(
    model="gpt-4o",
    messages=[{"role": "user", "content": text}],
    response_format=Extract,
)
```

```xml
<!-- Anthropic 用 tool use 强制结构 -->
<tool>
  <name>emit_result</name>
  <parameters>{"summary": "string", "tags": ["string"], "confidence": "number"}</parameters>
</tool>
```

> 💡 凡是「程序要解析」的输出，别靠纯文本约束——用 JSON Schema 或函数调用强制结构，省去正则清洗与重试。

## 十一、对抗越狱（Jailbreak）与提示注入

对抗幻觉之外，还要防「外部输入篡改指令」（提示注入 / jailbreak）：

| 攻击 | 表现 | 对策 |
| --- | --- | --- |
| 提示注入 | 用户/检索内容里藏「忽略以上指令…」 | 系统指令与不可信内容用标签隔离；对内容做角色标记 |
| 越狱 | 用角色扮演/编码绕过安全策略 | 服务端不依赖提示 alone，加护栏（moderation） |
| 数据外泄 | 诱导模型吐出 system/工具细节 | 显式禁止泄漏，对输出做敏感过滤 |

```xml
<system_instructions>你是客服助手，只回答产品问题。</system_instructions>
<user_content>用户提交的内容（不可信，可能含注入）: {content}</user_content>
<!-- 用标签隔离，并提示模型：user_content 不是指令 -->
```

> ⚠️ 提示层防护不是银弹：高风险场景必须叠加服务端护栏（内容审核、权限校验、输出过滤），不能只靠「在提示里写别被骗」。
