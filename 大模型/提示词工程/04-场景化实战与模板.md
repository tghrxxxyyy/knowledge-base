# 场景化实战与模板

> 把前面的原则落到具体场景：代码生成、RAG、智能体（Agent）、评测迭代，并附可直接套用的模板与避坑清单。

## 一、代码生成

### 技巧
- **引导词**：代码类提示末尾补 `import` / `def` / `SELECT` 等起手式，把模型引向目标语言。
- **拆解任务**：别一次让它「用 TS+Pug+MongoDB 建整个 Express 应用」，拆成「先建 Express+TS+Pug → 加 products 页 → 接数据库」。
- **给上下文**：有意义的函数名、顶部注释、必要的 include/依赖引用，能让模型贴合你的框架与版本。
- **少样本对齐风格**：贴一小段你们项目的真实代码作为样例，模型会跟随既有模式（「垃圾进垃圾出」同样成立）。

### 模板
```text
# 角色
你是一名资深 {语言} 工程师，遵循本仓库既有代码风格。

# 任务
实现函数 {函数名}，要求：{输入} -> {输出}，处理 {边界情况}。

# 约束
- 使用 {框架/库} 的 {版本}
- 不引入额外依赖
- 包含必要的错误处理

# 参考（项目现有风格）
```{语言}
{一段本项目真实代码}
```

# 输出
只输出函数实现，附简短注释。
```

## 二、RAG（检索增强生成）

> 目标：让模型基于「检索到的资料」作答，降低幻觉。

### 技巧（据 dair-ai 与 Anthropic 实践）
- **文档分块（chunking）**要合理，避免把一段语义切两半。
- **把长文档放提示最上方**，查询放最后（见 02 节长上下文摆位）。
- **要求先引用再作答**（grounding）：让模型先输出 `<quotes>` 再写答案，便于核对来源。
- 复杂时可加**查询改写（query transformation）**与**重排（re-ranking）**提升命中。

### 模板
```xml
<instructions>
基于下方 <documents> 回答用户问题。
先抽取相关原文到 <quotes>，再据此写简洁、事实性的回答到 <answer>。
禁止引用文档之外的信息。
</instructions>
<documents>
  <document><source>doc1</source><doc>{检索片段1}</doc></document>
  <document><source>doc2</source><doc>{检索片段2}</doc></document>
</documents>
<input>{用户问题}</input>
```

## 三、智能体 / Agent（以 GPT-5 为例）

来源：https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide/

> 核心矛盾是「主动性（eagerness）」：太积极会乱调工具、太保守会动不动把问题抛回给你。用提示词校准。

### 降低主动性（更快、更省）
- 调低 `reasoning_effort`；
- 在提示里给出明确的「探索边界」与「早停条件」；
- 给模型一个「不确定也可继续」的出口（escape hatch），例如「即使可能不完全准确，也尽快给出答案」；
- 可设固定工具调用预算（如最多 2 次搜索）。

### 提高主动性（更自主、少追问）
```text
你是一个智能体——请持续推进，直到用户问题被彻底解决再结束本轮。
只有在确认问题已解决时才终止。
遇到不确定时不要停下来问用户——自行推断最合理的做法并继续，
事后把你的假设记录给用户。
```

### 安全边界（重要）
明确**安全动作 vs 危险动作**的不确定性阈值：
- 结账/支付类工具：低阈值，必须向用户确认；
- 搜索/只读类工具：高阈值，可大胆调用；
- 删除文件：阈值远低于 grep 搜索。

> 用 Responses API 时，推理状态会在工具调用间保持，Agent 表现更连贯高效。

## 四、评测与迭代（让提示「可改进」）

OpenAI 的优化飞轮：**写评测 → 写提示 → 跑评测 → 看反馈 → 改提示/数据 → 循环**。

- 先建一小批能代表真实输入的测试用例（evals），给基线；
- 用少量测试用例快速迭代提示，看准确率/F1 是否提升；
- 不稳定处用 few-shot、Active-Prompt 补强；
- 仍不够时再考虑微调。

## 五、可直接套用的通用模板

```xml
<role>你是一名{领域}专家。</role>
<instructions>
完成以下任务：{清晰的目标}。
要求：{格式/长度/风格/约束}。
</instructions>
<context>
{必要的背景、数据、领域知识}
</context>
<examples>
  <example><input>...</input><output>...</output></example>
</examples>
<input>{本次具体输入}</input>
<output_format>{期望返回结构，如 JSON / 表格 / 分段}</output_format>
```

## 六、避坑清单 ✅

- [ ] 指令模糊（「写得好一点」）→ 改成可验证的具体要求
- [ ] 只说「不要 XX」→ 改为「要 XX」
- [ ] 示例与真实场景脱节 → 换成贴近业务的样例
- [ ] 把长文档塞在指令后面 → 长文档放最前、查询放最后
- [ ] 一次塞满所有技巧 → 先最小可用，再评测迭代
- [ ] 跨模型直接套用 → 针对你实际用的模型验证（Claude 用 XML、OpenAI 用 `###`/`"""`）
- [ ] 没有评测就「感觉变好了」→ 建小批测试用例做前后对比
- [ ] 依赖模型「自己知道」最新事实 → 用 RAG / 工具补外部知识

> ⚠️ 以上模板与清单均为通用参考，实际效果请以你自己的评测为准；标注的性能数据来自各厂商公开案例。

## 七、Agent 提示范式（模板 + 反例）

Agent 提示的核心是「循环：思考 → 行动 → 观察」，并明确**主动性**与**安全边界**（呼应 03 节 ReAct）。

### ReAct 循环模板

```text
你是一个可使用工具的智能体。每步严格输出：
Thought: <推理当前该做什么>
Action: <工具名>(<参数>)
Observation: <工具返回，由系统填入>
重复直到能回答。最终用 Final Answer 给出结论。
```

### 主动性校准模板（提高自主）

```text
请持续推进直到用户问题彻底解决再结束本轮；
遇不确定不要停下来问，自行推断最合理做法并继续，
事后把假设记录给用户。
```

### 安全边界模板

```text
- 只读 / 搜索类工具：可大胆调用
- 写操作（发消息 / 改文件）：先说明意图再执行
- 高危操作（支付 / 删除 / 外发）：必须向用户确认
```

### 反例 ❌

```text
你是个智能体，去把事情办好。
# 没有循环格式、没有停止条件、没有安全边界
# → 模型易陷入空转，或擅自调用高危工具
```

> 落地要点：用支持推理态保持的接口（如 Responses API），Agent 在工具调用间更连贯；主动性用 `reasoning_effort` 与「探索边界 / 早停条件」校准，别让它在两个极端间横跳。

## 八、评测提示有效性（量化方法）

「感觉变好了」不算数，要量化。三类评测法：

| 方法 | 做法 | 适用 |
| --- | --- | --- |
| 人工 rubric | 定评分维度（准确性/格式/风格），人打分 | 早期、定性 |
| 程序化断言 | 对输出写断言（含关键词/可解析 JSON/正则） | 格式化、可机检 |
| LLM-as-judge | 用强模型按 rubric 给弱模型输出打分 | 规模化、省人力 |

```python
# 程序化评测最小闭环
def eval_prompt(prompt, cases):
    scores = []
    for case in cases:
        out = generate(prompt, case["input"])
        ok = case["check"](out)          # 断言函数
        scores.append(1 if ok else 0)
    return sum(scores) / len(scores)      # 通过率
# 改提示前后跑同一 cases，对比通过率
```

> 💡 评测集要覆盖「典型 + 边界 + 对抗」三类；每次提示改动都跑回归，避免「修一个 bug 引入三个」。

## 九、提示版本管理

提示词是「代码」，应纳入版本管理而非随手改：

| 实践 | 做法 | 收益 |
| --- | --- | --- |
| Git 管理 | 提示模板存 `.md`/`.yaml`，改了就 commit | 可回滚、可 diff |
| 变量化 | 把易变部分抽成 `{变量}`，模板与实例分离 | 一处改全局生效 |
| 评测门禁 | CI 跑评测集，通过率不降才合入 | 防退化 |
| 灰度 | 新提示放量 5%~10% 对比旧版 | 线上安全验证 |
| 元数据 | 记模型版本/日期/负责人 | 溯源与复盘 |

```yaml
# 提示模板示例（变量化 + 版本化）
name: extract_entities
version: 1.3
model: claude-opus-4-8
template: |
  <role>你是一名{role}</role>
  <instructions>{instruction}</instructions>
  <input>{input}</input>
```

> ⚠️ 提示词应与「模型版本」绑定：换模型（如 GPT-4o → GPT-5）后旧提示可能失效，务必重新跑评测再上线。
