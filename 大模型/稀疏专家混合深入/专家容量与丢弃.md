# 专家容量与丢弃

> 对应 Shazeer et al., *Sparsely-Gated MoE*, 2017 与 Fedus et al., *Switch Transformers*, 2022。

## 一、背景与挑战

在稀疏专家混合（MoE）模型中，门控网络把每个 token 路由到少数专家，但 token 在序列与批次中的分布并不均匀：某些热门专家会被大量 token 同时选中，而冷门专家长期空闲。若任由 token 无限制地涌入某个专家，该专家的计算与显存会瞬间被打满，引发算子排队、显存溢出甚至训练崩溃；同时，未被处理的 token 若被直接丢弃，又会造成信息损失，削弱模型质量。这就是「专家容量与丢弃」要解决的问题——在吞吐、显存与质量之间找平衡。

实际工程中，容量设置还受 batch 形状影响：长序列、变长输入、以及某些特殊 token（如特殊符号、分隔符）往往被集中路由，使瞬时峰值远超均值。因此容量必须按「最坏情况峰值」而非「平均值」来估，否则在训练中后期数据分布漂移时丢弃率会突然抬头。

## 二、核心原理

容量（capacity）被定义为每个专家在每个批次中能处理的 token 上限，通常表达为：

$$ capacity = \frac{tokens\_per\_batch}{num\_experts} \times capacity\_factor $$

其中 $capacity\_factor$ 是冗余系数（常见 1.0 到 1.25）。门控选出 top-k 专家后，按位置顺序将 token 填入各专家的输入缓冲区；当某专家已收到 $capacity$ 个 token，后续再被路由到它的 token 即视为「溢出」。溢出 token 有两种典型处置：(1) 直接丢弃（dropped），不参与本次前馈；(2) 残差路由（residual / expert-choice 变体），将其转交共享专家或走残差连接以尽量保留信息。Switch Transformer 采用固定容量加丢弃策略，并结合辅助负载损失来抑制丢弃率。

值得注意，容量是按「设备本地」计算的：在专家并行下，每设备只持有部分专家，其本地容量应为 $capacity / (E/D)$ 经过分片后的实际可容纳量，通信前的 all-to-all 分发要按本地容量裁剪。

## 三、形式化与数学基础

设批次 token 总数为 $T$，专家数为 $E$，每专家容量为 $C$，总容量为 $E \cdot C$。丢弃率定义为：

$$ drop\_rate = \frac{\max(0, T - E \cdot C)}{T} $$

更精细地，对每个专家 $i$ 实际分配到 $a_i$ 个 token，则溢出量：

$$ overflow_i = \max(0, a_i - C) $$

总丢弃 token 数 $D = \sum_i overflow_i$。当 $C < \frac{T}{E}$（即 $capacity\_factor < 1$）时必然丢 token；增大 $C$ 可降丢率，但会增加 padding 与显存浪费（空位需补零）。引入容量后，平均利用率为：

$$ util = \frac{T}{E \cdot C} $$

理想情况 $util \approx 1$，过大则利用率低、padding 多。

## 四、代码实现

```python
# 计算每个专家的容量（带冗余系数）
def compute_capacity(tokens, num_experts, capacity_factor=1.25):
    return int(tokens / num_experts * capacity_factor)

# 按门控结果将 token 填入专家缓冲区，超出容量走残差
def dispatch(x, gate_logits, num_experts, capacity):
    top_idx = gate_logits.topk(1).indices.squeeze(-1)  # 每个 token 的目标专家
    counts = [0] * num_experts
    dispatched = {e: [] for e in range(num_experts)}
    residual = []
    for t in range(x.shape[0]):
        e = int(top_idx[t])
        if counts[e] < capacity:
            dispatched[e].append(x[t])
            counts[e] += 1
        else:
            residual.append(x[t])  # 溢出走残差
    return dispatched, residual

# 监控丢弃率：训练循环里打印 mean overflow
def drop_rate(counts, capacity):
    overflow = sum(max(0, c - capacity) for c in counts)
    total = sum(counts)
    return overflow / max(1, total)
```

## 五、与其他技术对比

| 策略 | 显存占用 | 信息损失 | 实现复杂度 |
| --- | --- | --- | --- |
| 固定容量 + 丢弃 | 低 | 有（丢弃率大于 0） | 低 |
| 残差 / 共享专家补偿 | 中 | 极低 | 中 |
| 动态容量（按负载重分） | 高 | 无 | 高 |
| 无容量限制 | 不可控 | 无 | 低（易溢出） |

可见容量本质是「节流阀」：过小丢信息，过大浪费算力与显存。与负载均衡配合时，辅助损失压低峰值、容量吸收残差，两者共同决定丢弃率。

## 六、常见误区

- 认为容量越大越好：容量过大意味着大量 padding 与空计算，显存与算力被浪费，且无法解决路由本身的不均衡。
- 认为丢弃率可以长期忽略：在长尾数据或突发热点下，丢弃率可能随训练进程漂移，需持续监控。
- 把容量当作全局常量写死：实际应按批次 token 数动态计算，而非硬编码。
- 忽略变长输入的峰值：按均值设容量会在长样本上丢大量 token，应按峰值估。

## 八、面试题

- 专家容量如何设置？答：按批次 token 数、专家数与冗余系数计算，并在监控丢弃率的前提下调 $capacity\_factor$。
- 丢弃 token 有何后果？答：直接损失该 token 的梯度与信息，可能拖累长尾能力，可用残差路由缓解。
- 为何不用无容量？答：单一专家可能瞬时被打满导致显存溢出与训练不稳定。
- 容量与负载均衡什么关系？答：辅助损失降低路由峰值，容量吸收剩余溢出，二者协同控丢弃率。

## 九、演进与趋势

固定容量 → 残差 / 共享专家补偿 → 动态容量与 expert-choice 路由（让专家选择 token，天然均衡）。专家选择机制（如 Google 的 Expert Choice）从根本上规避丢弃，是当前研究热点；另有按设备负载动态重分容量的在线调度方案。

## 十、小结

专家容量与丢弃是 MoE 在「稀疏激活」与「稳定训练」之间的关键阀门：用冗余容量与残差补偿换取吞吐与质量平衡，是工程落地的必选项，且必须按峰值而非均值来设计。
