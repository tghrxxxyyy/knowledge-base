# 成本监控体系

> 对应云原生 FinOps 实践与 LLM 可观测性（OpenLLMetry / OpenTelemetry）。看不见的成本必然失控。

## 一、背景与挑战

大模型应用在成本上有几个特点：同一功能不同输入长度成本差数倍；缓存/重试/并发会放大或节省开销；多模型路由使归因复杂。没有监控时，常见问题包括：某个提示词悄悄吞掉大半预算、失败重试成倍计费、开发/生产混用导致账单混乱。挑战是把成本归因到**功能、团队、用户、模型**四个维度。

## 二、核心原理

成本监控分层：

1. **采集层**：在网关/SDK 拦截每次调用，记录 model、prompt_tokens、completion_tokens、latency、cache_hit、user_id、feature。
2. **归因层**：用 tag/维度把费用分摊到功能与团队；按单价表换算金额。
3. **告警层**：设置预算、日环比、单功能占比阈值。
4. **优化层**：识别 Top-N 昂贵功能，走缓存/小模型/提示压缩。

核心公式：

$$\text{cost}=\sum_i \big(n^p_i \cdot p^{\text{in}}_i + n^c_i \cdot p^{\text{out}}_i\big) - \text{cache\_savings}$$

## 三、形式化与数学基础

设功能 $f$ 在时间窗 $T$ 内的调用集 $S_f$：

$$C_f=\sum_{i\in S_f}\big(t^{\text{in}}_i p^{\text{in}}_{m(i)}+t^{\text{out}}_i p^{\text{out}}_{m(i)}\big)$$

占比与环比：

$$\text{share}_f=\frac{C_f}{\sum_g C_g},\qquad \text{DoD}_f=\frac{C_f(t)-C_f(t-1)}{C_f(t-1)}$$

预警条件（示例）：

$$\text{alert} \iff \text{share}_f > 0.3 \ \lor\ \text{DoD}_f > 0.5$$

## 四、代码实现

在调用侧打点并汇总：

```python
import time
def metered_call(llm, prompt, feature, user):
    t0 = time.time()
    resp = llm.invoke(prompt)
    rec = {
        "feature": feature, "user": user,
        "model": resp.model,
        "in_tok": resp.usage.prompt_tokens,
        "out_tok": resp.usage.completion_tokens,
        "lat_ms": int((time.time() - t0) * 1000),
        "ts": int(time.time()),
    }
    metrics.emit("llm.cost", rec)   # 送入时序库
    return resp
```

再按 `feature` 聚合金额、设阈值告警即可。

| SDK 拦截 | 请求级 | 低 | 高，含上下文 |
| APM 通用监控 | 请求级 | 中 | 缺 token 语义 |

## 六、常见误区

- 只看总账单，不做功能级归因。
- 忽略输入 token：长上下文场景下输入往往是大头。
- 不记录 cache_hit，导致缓存收益无法量化。
- 告警只设总额阈值，等超了才发现是某个功能失控。

## 九、演进与趋势

LLM 可观测性正在标准化（OTel GenAI 语义约定）；「成本即指标」进入 APM 主界面；自动优化闭环（监控 → 路由到更便宜模型）开始落地。

## 十、小结

成本监控的关键是请求级埋点 + 多维归因 + 阈值告警。把成本当一等可观测指标，才能把优化从「拍脑袋」变成「看数据」。
