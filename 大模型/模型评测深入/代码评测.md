# 代码能力评测

> 对应 HumanEval (Chen et al., 2021)、MBPP (Austin et al., 2021)、LiveCodeBench (Jain et al., 2024) 等代码生成基准。

## 一、背景与挑战

代码生成能力是 LLM 最具商业价值的能力之一。但「代码评测」与「文本评测」本质不同：文本可模糊正确，代码必须**可运行且通过测试**。挑战在于：① 需真实执行环境（sandbox）跑测试，成本高且有安全风险；② 公开题库（HumanEval 164 题）易被混入训练集造成数据污染；③ 单次采样通过有运气成分，需多次采样统计；④ 测试覆盖有限，通过测试不等于无 bug。

## 二、核心原理

代码评测范式：给定自然语言问题描述 + 函数签名，模型生成实现，在隐藏测试用例上执行，按通过率计分。核心指标 **pass@k**：从 $n$ 次采样中取 $k$ 个候选，若至少一个全测试通过则视为成功。另有执行率（能否运行不报错）、单元测试覆盖率等辅助指标。

为防污染，LiveCodeBench 等采用「竞赛结束后才入库」的题源，确保评测时模型未见过。

## 三、形式化与数学基础

设模型对一题采样 $n$ 次，其中通过全部测试的次数为 $c$，则 pass@k 的无偏估计（Chen et al.）：

$$
\text{pass@}k = \mathbb{E}\!\left[1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\right]
$$

直观上：当 $k=1$ 测「首次即中」，当 $k$ 增大（如 $k=10$）测「多次尝试命中」，更贴近「带重试的可用率」。整体基准分数常报 pass@1 与 pass@10 两者。

## 四、代码实现

用 `evalplus`（HumanEval+/MBPP+ 增强测试）评测：

```bash
# 安装并评测模型生成的代码
pip install evalplus
evalplus.evaluate \
  --model "bigcode/starcoder2-7b" \
  --dataset humaneval \
  --backend hf \
  --greedy
```

Python 侧自行统计 pass@k（示意）：

```python
import math
def pass_at_k(n, c, k):
    if n - c < k: return 1.0
    return 1.0 - math.comb(n - c, k) / math.comb(n, k)

# 某题采样 n=10，通过 c=7
print("pass@1 =", pass_at_k(10, 7, 1))   # 0.7
print("pass@10=", pass_at_k(10, 7, 10))  # 1.0
```

## 五、与其他技术对比

| 指标 | 含义 | 适用 |
|------|------|------|
| pass@1 | 一次通过率 | 衡量「开箱即用」 |
| pass@k | k 次任一通过 | 衡量「带重试可用性」 |
| 执行率 | 可运行比例 | 基础可用性 |
| 单元测试覆盖 | 覆盖分支 | 质量深度 |

文本指标（BLEU/CodeBLEU）仅作参考，远不如执行验证可靠。

## 六、常见误区

- 「pass@1 高就够」：忽略重试场景，真实 IDE 有多次尝试，pass@k 更实用。
- 「通过测试 = 无 bug」：隐藏测试有限，可能漏掉边界情况。
- 「公开榜分数可信」：HumanEval 等已广泛泄露，需看污染控制版本（如 EvalPlus、LiveCodeBench）。
- 「代码评测只需比字符串」：必须执行，否则无法验证语义正确。

## 九、演进与趋势

从 HumanEval/MBPP（易污染、规模小）到 EvalPlus（增强测试集）、LiveCodeBench（动态防污染、含竞赛题）；评测维度扩展到「调试、编辑、仓库级补全、单元测试生成」。执行环境向安全沙箱（隔离容器、资源限额）标准化，并与 SWE-bench 等「真实 Issue 修复」任务结合，逼近工程落地场景。

## 十、小结

代码评测以「可执行测试通过率」为核心，pass@k 兼顾开箱可用与带重试实用。其难点在 sandbox 安全、数据污染与测试覆盖。权威基准与防污染版本以 HumanEval/EvalPlus/LiveCodeBench 官方为准。
