# 自动化评测框架

> 对应 llm-course「Evaluation」、EleutherAI lm-evaluation-harness、HELM 与 OpenCompass 等开源评测工具。

## 一、背景与挑战

人工评测贵且慢，无法支撑快速迭代与大规模横评。自动化评测框架把「加载模型/API → 构造 prompt → 跑基准 → 解析输出 → 算指标 → 汇总报告」标准化为流水线，使结果可复现、可对比。核心挑战：① 不同模型输出格式不一（思维链、JSON、带解释），答案抽取（answer extraction）易错；② 多后端（本地权重、vLLM、API）接口差异大；③ LLM-as-judge 需固定 rubric 与稳定 prompt；④ 大数据集需并行与缓存以控成本。

## 二、核心原理

典型流水线五段：

1. **加载**：统一抽象 `Model` 接口（HF 本地、OpenAI 兼容 API、vLLM 端点）。
2. **任务构造**：从基准读取样本，套用 few-shot 模板生成 prompt。
3. **推理**：批量请求，支持采样参数与并发。
4. **解析**：正则 / 结构化抽取（如取 `\boxed{}`、最后一行的选项、JSON 字段）。
5. **评分**：调用指标（EM、ROUGE、BERTScore、LLM 裁判）聚合。

框架通常把「任务定义」与「模型后端」解耦，便于横向对比且可插拔。

## 三、形式化与数学基础

评测预算与置信：对 $N$ 题、每题采样 $k$ 次，总调用 $T=Nk$。给定目标误差 $\epsilon$ 与置信 $1-\alpha$，所需样本近似：

$$
N \ge \left(\frac{z_{1-\alpha/2}\,\sigma}{\epsilon}\right)^2
$$

可据历史方差 $\sigma^2$ 反推题量。LLM 裁判打分聚合（多裁判平均）降低单裁判方差：

$$
\hat{s} = \frac{1}{J}\sum_{j=1}^{J} s_j, \quad \text{CI} = \hat{s} \pm t\frac{\hat{\sigma}}{\sqrt{J}}
$$

## 四、代码实现

lm-evaluation-harness 跑基准并导出结果：

```bash
python -m lm_eval \
  --model hf \
  --model_args pretrained=meta-llama/Llama-3-8B \
  --tasks gsm8k,mmlu,truthfulqa \
  --num_fewshot 5 \
  --device cuda:0 \
  --output_path results.json
```

用 OpenCompass Python API 自定义评测并聚合：

```python
from opencompass import OpenCompass
oc = OpenCompass(
    models=["Qwen/Qwen2-7B"],
    datasets=["gsm8k", "mmlu"],
    eval_mode="llm_judge",
)
report = oc.run()
report.aggregate(by="capability").show()
```

## 六、常见误区

- 「框架跑出分数就可靠」：答案抽取错误会系统性高估/低估。
- 「一次运行即可」：采样随机，需多次 + 置信区间。
- 「LLM 裁判无需校准」：需固定 rubric、盲评、人工抽检。
- 「所有任务同一 prompt」：不同基准有专属 few-shot 模板，混用会偏差。

## 九、演进与趋势

框架从「单模型单基准」走向「统一后端 + 多维度聚合 + LLM 裁判 + 防污染动态题源」；与实验追踪（wandb、mlflow）和模型注册表打通，形成「训练—评测—对比」闭环。趋势还包括：可执行评测（代码/数学真实运行）、Agent 轨迹评测、以及成本/时延指标内建，使报告更贴近生产决策。

## 十、小结

自动化评测框架把评测工程化为可复现流水线，关键在统一后端、稳健答案抽取、合理指标与 LLM 裁判校准。主流工具有 lm-evaluation-harness、OpenCompass、HELM，各有侧重。具体用法与任务集以各项目官方文档为准。
