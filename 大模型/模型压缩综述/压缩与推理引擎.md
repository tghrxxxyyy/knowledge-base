# 压缩与推理引擎协同

> 对应 NVIDIA TensorRT-LLM、vLLM 与 AWQ/GPTQ 官方 kernel 文档。

## 一、背景与挑战

模型压缩算法的价值，最终要由推理引擎「跑出来」才算数。一个常见的陷阱是：算法论文宣称把模型压到 4-bit、稀疏度 50%，但通用推理框架不支持对应格式，结果只是「省了显存、没省时延」，甚至因格式转换反而更慢。压缩格式与推理引擎（及其底层 kernel、硬件）是强耦合的——GPTQ/AWQ 需要专门的反量化 kernel，FP8 需要 Ampere 及更新架构的 tensor core，结构化稀疏需要库的支持。因此压缩选型本质是「算法—引擎—硬件」三者协同的系统工程。

## 二、核心原理

选型决策应倒置：先看硬件代际与目标指标（吞吐/时延/显存），再反推可用压缩算法，而非先定算法再找引擎。否则易陷入「论文先进但落地无加速」。压缩收益要在端到端（end-to-end）视角下衡量：吞吐量（tokens/s）、首 token 时延（TTFT）、显存占用、单请求成本。不同压缩手段对应不同的引擎能力：

- **权重量化（INT4/INT8）**：需引擎支持对应反量化 kernel（如 AWQ 的 fused kernel）。
- **FP8/FP6**：依赖 Hopper/Ampere+ 的硬件 tensor core 原生低精度计算。
- **稀疏（2:4）**：需 NVIDIA 结构化稀疏库或专用 kernel。
- **低秩/KV 量化**：框架需支持相应计算路径（如 vLLM 的 KV cache 量化）。

选型时先评估硬件代际与目标指标，再反向选压缩算法，避免「算法先进但引擎不落地」。

## 三、形式化与数学基础

端到端吞吐可建模为各阶段时延之和。设预填充时延 $T_{prefill}$、每 token 解码时延 $T_{decode}$（含反量化开销 $\Delta_q$）：

$$T_{total} = T_{prefill} + L\cdot T_{decode},\quad T_{decode} = T_{compute} + \Delta_q + T_{mem}$$

压缩若只降 $T_{mem}$ 而不降 $\Delta_q$ 或反而增 $\Delta_q$，整体收益有限。理想情况下低比特使 $T_{mem}\downarrow$ 且 $\Delta_q$ 被融合 kernel 摊薄，从而净加速。因此「加速比」应定义为：

$$S = \frac{T_{total}^{FP16}}{T_{total}^{compressed}} > 1$$

## 四、代码实现

```python
# 选型检查：算法是否能被当前引擎/硬件支持（示意）
ENGINE_CAPS = {
    "vllm":      {"int4": True,  "fp8": True,  "sparse24": False},
    "tensorrt":  {"int4": True,  "fp8": True,  "sparse24": True},
    "transformers": {"int4": True, "fp8": False, "sparse24": False},
}

def pick_engine(algo: str, hw: str):
    if algo == "fp8" and hw < "hopper":
        raise ValueError("FP8 需 Hopper 及以上硬件")
    for engine, caps in ENGINE_CAPS.items():
        if caps.get(algo):
            return engine
    raise RuntimeError(f"无引擎支持 {algo}")
```

## 五、与其他技术对比

| 压缩 | 省显存 | 实际加速 | 引擎依赖 |
|------|--------|----------|----------|
| INT8 | 中 | 中 | 广泛 |
| INT4(AWQ) | 高 | 高(需kernel) | 较强 |
| FP8 | 中 | 高(硬件) | Hopper+ |
| 2:4 稀疏 | 高 | 高(库支持) | NVIDIA |

可见「加速」高度依赖引擎与硬件是否对齐。

## 六、常见误区

- 认为「算法压缩 = 实际加速」：必须端到端验证时延与吞吐。
- 忽略反量化开销：不当实现下 kernel 频繁格式转换抵消收益。
- 盲目追最低比特：4-bit 在某些硬件上缺乏原生支持，反而慢。
- 忽视 batch 与 KV cache 影响：压缩权重的收益可能被 KV 瓶颈掩盖。

- 忽视反量化开销：不当实现下 kernel 频繁格式转换抵消收益。

## 九、演进与趋势

- 压缩格式走向「引擎原生」：算法与 kernel 联合设计（co-design）。
- 端到端编译器（如 TorchCompile、Triton）自动生成适配 kernel，降低耦合成本。
- KV cache 量化与分页（PagedAttention）结合，使长上下文下压缩收益更显著。

## 十、小结

压缩与推理引擎是「算法—引擎—硬件」协同体。压缩算法的收益必须通过引擎的专门 kernel 与硬件低精度能力兑现，选型应以端到端吞吐与显存为最终判据，避免停留在参数量或位宽的纸面压缩比。
