# 压缩质量评估

> 对应 perplexity 评测惯例与 lm-evaluation-harness / OpenCompass 等评测框架。

## 一、背景与挑战

压缩不是终点，「压完还能用」才是。但「质量」该用什么衡量，却远非单一指标能回答。仅看困惑度（perplexity）会掩盖任务级退化——某些模型在语言建模指标上几乎无损，却在推理、代码、长尾知识上明显掉点；反之，困惑度微涨也可能因分布偏移造成特定任务崩坏。评估的目标，是建立「精度损失 vs 压缩比 vs 时延/显存」的多维权衡视图，为不同部署场景（云端高并发 / 端侧低资源）提供决策依据。评估还应区分「相对掉点」与「绝对可用」：某些任务从 95% 降到 92% 是相对 3% 但绝对仍可用；而推理任务从 60% 降到 40% 可能直接不可用，需结合任务临界值判断。

## 二、核心原理

评估需覆盖三层：

- **语言建模层**：困惑度（PPL）、bits-per-weight，反映分布保真度。
- **任务能力层**：用标准基准（MMLU、GSM8K、HumanEval 等）测知识、推理、代码，关注相对掉点。
- **系统层**：显存峰值、推理时延、吞吐、单 token 成本。

关键原则是「不要只看困惑度」——困惑度对词表分布敏感但未必对应下游可用性；且要区分「平均掉点」与「极端退化」（worst-case），后者对高风险场景更关键。4-bit 在多数任务接近 FP16，但极敏感任务（如精确算术、长链推理）可能显著掉点。评估还应记录「掉点是否随任务难度单调」等信息，辅助定位压缩损伤来源。

## 三、形式化与数学基础

困惑度定义为交叉熵的指数：

$$\text{PPL} = \exp\left(-\frac{1}{N}\sum_{i=1}^N \log p(x_i\mid x_{<i})\right)$$

压缩质量常用相对退化：

$$\Delta_q = \frac{\text{Metric}_{comp} - \text{Metric}_{ref}}{\text{Metric}_{ref}}$$

压缩比（模型体积）为 $C = \frac{\text{Size}_{ref}}{\text{Size}_{comp}}$。理想 Pareto 前沿是在 $(\Delta_q, C^{-1})$ 平面上越靠近原点越好，时延作为第三轴。常用「等效精度压缩比」描述：达到 $1\%$ 相对掉点内的最大 $C$。

## 四、代码实现

```python
# 计算压缩前后任务指标的相对退化（示意）
def rel_drop(ref: dict, comp: dict) -> dict:
    return {k: (comp[k] - ref[k]) / ref[k] for k in ref}

def pareto_ok(delta_q: float, ratio: float, tol: float = 0.01) -> bool:
    # 在允许掉点 tol 内，压缩比越大越好
    return delta_q >= -tol   # delta_q 为负表示下降

# 困惑度计算
import math
def perplexity(logprobs: list) -> float:
    return math.exp(-sum(logprobs) / len(logprobs))
```

## 五、与其他技术对比

| 评测视角 | 优点 | 局限 |
|----------|------|------|
| 困惑度 | 快、便宜 | 不反映任务 |
| 基准任务 | 贴近能力 | 覆盖有限 |
| 人工评测 | 最真实 | 成本高 |
| 系统指标 | 决定落地 | 与质量正交 |

需组合使用，尤其不能省略任务与系统两层。

## 六、常见误区

- 只报压缩比与困惑度：任务级退化被隐藏。
- 用单一基准代表全部能力：不同任务对量化敏感度差异大。
- 忽略 worst-case：平均无损但个别任务崩坏在部署中致命。
- 不测时延/显存：压缩后推理反而更慢或 OOM。

## 十、小结

压缩质量评估是压缩落地的「验收关」。它要求同时审视语言建模指标、下游任务能力与系统指标，警惕只盯困惑度或压缩比的片面结论，并以 worst-case 与端到端时延作为高风险场景的硬约束。
