# 微调破坏安全对齐

> 对应 Qi et al., *Fine-tuning Aligned Language Models Compromises Safety, Even When Users Do Not Intend To!*, ICLR 2024；Wei et al., *Jailbroken: How Does LLM Safety Training Fail?*, NeurIPS 2023。

## 一、背景与挑战

已经安全对齐的模型，在下游做一次普通的领域微调后，安全拒答能力可能显著退化——即使微调数据完全无害、目的也毫无恶意。这对开放权重模型与微调即服务都是结构性风险：安全属性不是权重里的硬约束，而是一层容易被覆盖的浅层行为倾向。

## 二、核心原理

三条机制。第一，安全行为在参数空间上「浅」：拒答很大程度上由回答开头的少数 token 分布决定，微调改变输出风格与开头分布就足以绕过它。第二，灾难性遗忘：微调目标里没有安全信号，梯度会把与当前任务无关的行为一并挤掉。第三，格式与角色迁移：领域数据往往带固定角色设定与格式，模型学到「在此角色下总是配合」，与安全策略产生冲突。缓解手段相应有三：微调数据中混入固定比例的安全样本（安全重放）、对齐关键参数做冻结或低秩隔离、以及微调后强制过安全回归测试并在系统层加输入输出防护。

## 三、数学形式

把下游微调写成带安全约束的目标：

$$\min_\theta\ \mathcal L_{\text{task}}(\theta)+\lambda_s\,\mathcal L_{\text{safety}}(\theta)+\lambda_k\,\mathrm{KL}\big(\pi_\theta\,\|\,\pi_{\text{aligned}}\big)$$

其中 $\mathcal L_{\text{safety}}$ 为安全样本上的损失（重放），KL 项把模型锚在已对齐分布附近。安全退化程度可用有害顺从率的增量度量：$\Delta\mathrm{HCR}=\mathrm{HCR}(\theta_{\text{ft}})-\mathrm{HCR}(\theta_{\text{aligned}})$，作为上线放行门槛。

## 四、代码实现

```python
import random

def mixed_finetune_batches(task_ds, safety_ds, safety_ratio=0.05):
    # 安全重放：按固定比例把安全样本混入每个训练批，避免遗忘
    n_safe = max(1, int(len(task_ds) * safety_ratio / (1 - safety_ratio)))
    ds = list(task_ds) + list(safety_ds)[:n_safe]
    random.shuffle(ds)
    return ds

def safety_regression_gate(model, base_metrics, harmful, benign_lookalike, tol=0.02):
    m = safety_report(model, harmful, benign_lookalike)
    d_hcr = m["harmful_comply_rate"] - base_metrics["harmful_comply_rate"]
    d_or = m["over_refusal_rate"] - base_metrics["over_refusal_rate"]
    return {"pass": (d_hcr <= tol and d_or <= tol), "delta_hcr": d_hcr, "delta_or": d_or}
```

## 五、与其他对比

- 与 对齐税与能力保持深入：机制同源（遗忘与分布漂移），只是被遗忘的对象是安全行为。
- 与 参数高效微调：LoRA 等方法改动参数少，退化通常更轻，但并不能消除风险，仍需回归测试。
- 与 拒答边界与过度拒答：回归测试必须同时看漏拒与误拒，避免修安全时把误拒推高。

## 六、常见误区

- 认为「我的微调数据无害，所以安全没问题」。公开研究表明无害数据也会导致退化，必须实测。
- 只跑任务指标就上线。安全回归不在常规验证集里，需独立门禁。
- 把安全重放比例设得过高，挤占任务数据、拖累主任务效果；比例应通过小规模扫描确定。

## 八、面试题

- 为什么无害数据微调也会破坏安全？答：安全行为浅且缺乏梯度支持，微调改变开头分布与角色格式即可覆盖它，同时发生灾难性遗忘。
- 如何在微调流水线里防止安全退化？答：混入安全重放样本、加对齐模型的 KL 锚定、并把安全回归测试设为上线门禁。

## 九、演进

假定对齐是持久属性 → 发现下游微调导致退化 → 安全重放与 KL 锚定 → 参数隔离与门禁化回归测试 → 微调即服务的平台级安全约束。

## 十、小结

安全对齐是可被覆盖的浅层属性，任何后续训练都可能抹掉它；把安全样本重放与回归门禁写进流水线，是唯一可靠的工程答案。
