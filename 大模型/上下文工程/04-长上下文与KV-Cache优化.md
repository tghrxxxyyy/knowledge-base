## 一、上下文窗口的真相

模型标称「支持 128K / 200K token」，但工程上必须区分三个概念：

| 概念 | 含义 | 注意 |
|------|------|------|
| 标称窗口 | 厂商宣传的最大 token 数 | 不等于"能用好" |
| 有效窗口 | 模型真正能稳定利用的范围 | 常远小于标称（lost-in-the-middle） |
| 经济窗口 | 成本/延迟可接受的范围 | 由预算与 SLA 决定 |

关键事实：
- **有效上下文 ≠ 标称窗口**：长文中间信息常被「丢失在中间」（Lost in the Middle，论文证实）。
- **成本随长度线性增长**：输入 token 直接计费（许多厂商 input 比 output 便宜但仍显著），且 KV-Cache 占显存。
- **延迟增加**：注意力理论 O(n²)，FlashAttention 优化常数但仍随 n 增长；首个 token 延迟（TTFT）随 prompt 长度明显上升。

> 上下文工程的核心原则：**用最少的 token 装下最相关的信息，而非无脑堆长**。长上下文是能力，不是默认策略。

## 二、KV-Cache 是什么

自回归生成时，每个新 token 都要和之前所有 token 做注意力。为避免重复计算历史 token 的 K、V 矩阵，推理框架把它们缓存下来：

```
输入: [t1 t2 ... tn] → 各 token 算 K,V → 缓存 K_cache, V_cache
生成 t_{n+1}: 只需算 t_{n+1} 的 Q，与缓存的 K,V 做 attention
```

- **显存占用** ≈ 2（K,V） × num_layers × seq_len × hidden_dim × bytes_per_elem。
  - 例：7B 模型（32 层，4096 隐，FP16）单序列 4K 上下文约数百 MB；32K 则数 GB → 并发受限。
- 长对话 / 长文档 = KV-Cache 爆炸的主因（不是模型权重，是激活缓存）。
- 优化方向：减少 seq_len（压缩/裁剪）、降低精度、共享/复用、稀疏化。

## 三、KV-Cache 优化技术

| 技术 | 思路 | 收益 | 代价 |
|------|------|------|------|
| KV 量化 | FP16 → INT8/INT4/FP8 | 显存降 2~4 倍 | 轻微精度损失 |
| PagedAttention | 分页管理 KV，减少碎片（vLLM 首创） | 吞吐提升、显存利用率高 | 实现复杂 |
| MQA / GQA | 多查询/分组共享 KV 头 | KV 量降数倍（如 GQA 降 8x） | 训练需支持 |
| 滑动窗口 | 只保留最近 N token（StreamingLLM） | "无限长"、KV 恒定 | 远处信息丢失 |
| 稀疏注意力 | 只算重要位置（如 Longformer） | 长序列可行 | 需特殊结构 |
| Prefix Cache | 系统提示/公共前缀复用 | 多轮省算力 | 前缀须一致 |
| 投机解码(无关但常并用) | 小模型草稿+大模型验证 | 提速不增 KV | 另算 |

### 3.1 量化细节

- INT8 KV：精度损失小，几乎免费降一半显存。
- INT4/FP8：更激进，需实测质量（长上下文任务对量化更敏感）。
- 多数推理引擎（vLLM、TensorRT-LLM、SGLang）默认支持 KV 量化开关。

### 3.2 PagedAttention 思想

- 传统：每个请求预分配连续最大长度 KV 块 → 大块碎片、利用率低。
- PagedAttention：KV 按固定大小「页」分配，像 OS 虚拟内存，按需分配、可共享、可换出 → 显存利用率从 ~20% 提到 ~90%+，并发数大幅提升。

### 3.3 GQA / MQA

- MHA：每头独立 KV。
- MQA：所有头共享一组 KV → KV 缓存最小，但质量略降。
- GQA：分组共享（如 8 组）→ 平衡显存与质量，Llama 2/3、Mistral 广泛采用。
- 选型：长上下文 + 高并发场景，GQA/MQA 几乎是必选。

## 四、Context 压缩策略

| 策略 | 做法 | 适用 |
|------|------|------|
| 检索式上下文（RAG） | 只把相关片段塞进 prompt | 知识问答、长文档 |
| 摘要压缩 | 早期对话摘要成几行，留最近原文 | 多轮对话 |
| 层级裁剪 | 重要前置、次要后置/丢弃 | 通用 |
| 自动压缩 | LongLLMLingua 用小模型去冗余 token | 长 prompt 前置压缩 |
| 结构化筛选 | 用 schema/关键词先过滤 | 日志/代码检索 |

```python
# 简单上下文裁剪（保留最近 + 关键摘要）
def build_context(history, max_tokens):
    recent = history[-k:]                 # 最近 k 轮原文
    summary = summarize(history[:-k])     # 更早的压缩成摘要
    return fit(summary + recent, max_tokens)

# LongLLMLingua 风格：用小型 prompt 压缩器去冗余
compressed = compressor.compress(prompt, target_ratio=0.5, instructions="保关键信息")
```

## 五、Lost-in-the-Middle 与应对

研究发现：把答案信息放长文中间，模型容易忽略；放开头/结尾召回更好（U 型注意力分布）。

- **重排证据**：把最相关片段放首尾（retrieval rerank 后重排）。
- **分块问答**：先分段检索作答，再汇总，避免一次性塞长文。
- **显式指引**：prompt 里标注「关键信息在下方引用块」「答案必须基于以下材料」。
- **多次重排投票**：从不同顺序多次问答取一致结论，缓解位置偏差。

## 六、多轮对话的缓存复用

- **系统提示（system prompt）每轮相同** → Prefix Cache 复用，省重复计算（多数厂商对 cache 命中打折，如 10%~50% 价）。
- **工具定义、few-shot 示例固定在前缀** → 享受缓存命中。
- **用户历史若不变** → 整段前缀可复用 KV；一旦改动需重算（cache 失效）。
- 实践：把稳定的指令/工具定义放最前，动态内容（用户消息）放最后，最大化前缀命中。

```
[system prompt][tools def][few-shot]  ← 稳定，命中 Prefix Cache
[user turn 1][assistant 1]...[user turn N]  ← 动态，逐轮增长
```

## 七、长文档处理架构

```
用户问 → 检索相关段落(top-k) → 计算各段重要性 → 重排(首尾) → 压缩 → 拼进 ≤窗口
      → 若仍超长：分块并行问答 → 聚合答案（map-reduce 式）
```

- 不要直接把 100 页 PDF 丢进 prompt（贵 + lost-in-middle + 易超窗口）。
- 用 **RAG + 分块问答 + 聚合**，比单次长上下文更稳更省。
- 长文档可结合「章节摘要树」：先摘要各章，再按需展开相关章。

## 八、窗口外推（RoPE 缩放）

- 训练时窗口 4K，想用 32K → 需位置编码外推：NTK-aware RoPI、YaRN、Dynamic NTK。
- 外推会牺牲一定短文本精度，需实测（长窗口模型做短任务可能略差）。
- **优先选原生长窗口模型**（如原生支持 128K/200K 的模型），而非强行外推。
- 外推是"救急"，不是"正品"：能选原生长窗口就别外推。

## 九、成本治理

- 估算成本：`input_tokens × input单价 + output_tokens × output单价`。长上下文任务先压缩再发。
- 高频相同前缀用缓存（多数厂商 cache 命中折扣，见第六节）。
- 监控每轮 token 数，设上限防失控（如单请求 ≤ 32K，超出走 RAG 分块）。
- 缓存策略与厂商对齐：明确哪些前缀可命中、TTL 多久、价格折扣比例。

## 十、评测长上下文能力

| 基准 | 测什么 |
|------|--------|
| Needle-In-A-Haystack | 长文里埋关键信息能否定位（位置敏感度） |
| LongBench | 多任务长上下文综合 |
| L-Eval / ∞Bench | 真实长文档理解 |

- 自测：在长文档不同位置（头/中/尾）埋关键信息，看模型能否定位（验证 lost-in-middle）。
- 按任务定窗口：多数业务 8K~32K 足够，不必盲目上 200K（成本/延迟代价大）。

| 层级 | 动作 |

## 十二、常见坑

1. 把整本文档塞 prompt → 贵且 lost-in-middle。
2. 不压缩多轮历史 → KV 爆显存、成本飙升。
3. 忽略 Prefix Cache → 重复算系统提示（浪费 + 慢）。
4. 强行外推窗口 → 短文本质量下降。
5. 只看标称窗口不看有效窗口 → 长文答非所问。
6. 长上下文不加缓存 → 每轮重复计费，账单爆炸。
7. 重排遗漏 → 关键信息在中间被忽略。
