# 规划评估与可行性

> 对应 Valmeekam et al., *On the Planning Abilities of LLMs (PlanBench)*, NeurIPS 2023；Liu et al., *LLM+P*, 2023（交给外部求解器）。

## 一、背景与挑战

看起来合理的计划常常不可执行：前置条件不满足、动作不存在、顺序违反约束。
严格基准显示语言模型在需要严格状态推演的规划域上正确率有限，因此必须区分「听起来对」和「可验证可行」。

## 二、核心原理

- 静态校验：动作是否在动作空间内、参数是否合法、前置条件是否被前面步骤满足、是否存在环。
- 动态验证：在仿真或干运行环境中执行计划，用状态推演器判定目标是否达成。
- 混合方案：让模型负责把自然语言问题形式化（如生成 PDDL 域与问题），由经典求解器保证最优与可行，模型再把解翻译回自然语言。

## 三、数学形式

计划 $\pi=(a_1..a_T)$ 可行的充要条件是逐步前置条件成立：$\forall t,\ \text{pre}(a_t)\subseteq s_{t-1}$，且 $s_t=(s_{t-1}\setminus \text{del}(a_t))\cup \text{add}(a_t)$。

目标达成为 $G\subseteq s_T$；可行性因此完全可程序化判定，不需要模型自评。

## 四、代码实现

```python
def validate_plan(plan, init_state, actions, goal):
    s = set(init_state)
    for a in plan:
        spec = actions.get(a.name)
        if spec is None or not spec.pre <= s:
            return False, f"步骤 {a.name} 前置条件不满足"
        s = (s - spec.dele) | spec.add
    return goal <= s, "ok" if goal <= s else "目标未达成"
```

## 五、与其他对比

- 与自评式评估：状态推演是客观判定，比让模型说「这个计划可行吗」可靠得多。
- 与端到端任务成功率：成功率是最终指标，但不能定位是规划错、执行错还是工具错；可行性校验提供中间归因。

## 六、常见误区

- 用流畅度或合理性代替可行性判断，导致计划在执行时才暴露问题。
- 只在最后校验，不在生成时约束动作空间，浪费大量采样。
- 忽略资源与时序约束（预算、并发上限、时间窗），仅校验逻辑前置条件。

## 八、面试题

- 为什么规划要用形式化校验？答：可行性由前置条件与状态转移唯一决定，可程序判定，避免依赖不可靠的模型自评。
- LLM+求解器的分工是什么？答：模型做自然语言到形式化域的翻译与结果解释，求解器保证计划可行与最优。

## 九、演进

自由文本计划 → 结构化计划表征 → 静态前置条件校验 → 仿真干运行验证 → 形式化建模加外部求解器。

## 十、小结

规划评估必须客观化：动作空间受限、前置条件可判、必要时把搜索交给专业求解器。
