# 智能体评估

> 对应 AgentBench（Liu et al., 2023）、WebArena / ToolBench 等 Agent 评测基准，以及 METR 的「Agent 任务评估」方法学。属智能体工程深入板块，从工程视角讨论如何评测 Agent。

## 一、背景与挑战

评测一个会调工具、多步决策的 Agent，远比评测单轮问答困难：环境是**有状态、可变的**，同样的动作在不同状态下结果不同；Agent 可能有多种「正确」路径；且失败往往发生在长程交互的某一步。若评测环境不可复现、轨迹不可追踪，就无法归因、无法比较版本、无法上线。核心挑战：如何构建**隔离、可复现、可追踪**的评测，并度量「质量—成本—风险」的联合表现。

## 二、核心原理

Agent 评估分两层：
1. **离线（offline）评估**：用冻结的、脚本化的环境（mock 工具、固定网页/文件）跑固定任务集，保证可复现。指标含任务成功率、步骤效率、工具误用率。
2. **在线（online）/ 影子评估**：在受控真实流量或仿真中运行，观察真实分布下的表现与成本。

关键工程实践：
- **轨迹记录（trajectory logging）**：完整保存每步的 thought/action/observation，便于回放与归因。
- **成本联合度量**：成功率之外记录 token 消耗、时延、调用次数，避免「高成本换高准确率」的伪优。
- **失败分类**：把失败归因为规划错、工具错、解析错、环境错，定位改进点。

## 三、形式化与数学基础

对任务集 $\mathcal{T}$，Agent 策略 $\pi$ 在环境 $\mathcal{E}$ 上定义成功率：

$$
\text{SR}(\pi)=\frac{1}{|\mathcal{T}|}\sum_{\tau\in\mathcal{T}} \mathbb{I}\big[\text{done}(\pi,\mathcal{E},\tau)=\text{success}\big]
$$

联合效用需权衡质量与开销（成本 $C$、时延 $L$）：

$$
U(\pi)=\text{SR}(\pi) - \lambda_c\, \bar{C}(\pi) - \lambda_l\, \bar{L}(\pi)
$$

其中 $\lambda$ 为权重，反映业务对成本/时延的容忍度。可复现要求环境分布固定：$\mathcal{E}$ 在多次评测间保持一致（确定性种子、冻结外部依赖）。

## 四、代码实现

```python
def eval_agent(agent, tasks, env_factory, runs=3):
    rows = []
    for task in tasks:
        scores, costs = [], []
        for r in range(runs):
            env = env_factory(task, seed=r)        # 可复现环境
            traj = agent.run(env, task.goal)        # 带轨迹返回
            scores.append(task.check(traj))         # 成功? 0/1
            costs.append(traj.token_cost)
            log_trajectory(task.id, traj)           # 轨迹存档
        rows.append({"task": task.id, "SR": mean(scores),
                     "cost": mean(costs)})
    return pd.DataFrame(rows)
```

## 五、与其他技术对比

| 评估对象 | 环境 | 可复现 | 主要指标 |
|---------|------|--------|---------|
| 单轮问答 | 无状态 | 易 | 准确率/相似度 |
| RAG | 静态语料 | 易 | 召回/答案正确 |
| Agent | 有状态可变 | 难 | 成功率+成本+轨迹 |
| 人类在环 | 真实 | 难 | 满意度/接管率 |

Agent 评估复杂度最高，因状态与路径多样性。

## 六、常见误区

- 只在「 happy path」上测，忽略异常/注入/超时等边界。
- 用最终答案对错代替轨迹质量，掩盖了高成本绕路。
- 环境未冻结，导致版本间对比失准（「这次变好」可能是环境变了）。
- 不记录完整轨迹，失败后无法定位是哪一步出错。

## 八、面试题

- 为什么 Agent 评测环境需可复现？不可复现会导致什么后果？
- 除成功率外，还应联合度量哪些维度？为何？
- 如何设计「失败归因」体系以指导 Agent 改进？
- 在线影子评估与离线评估分别解决什么问题？

## 九、演进与趋势

Agent 评估正标准化、自动化：出现统一协议（如向 Agent 暴露标准化环境接口）、轨迹回放与差异对比工具；并引入「过程奖励模型」对每步打分，超越终点对错。随自主 Agent 走向生产，评估重点转向「真实世界可靠性」「被劫持后的后果可控性」以及「长程任务的可中断恢复率」。评测集也从静态任务转向对抗性、分布外场景。

## 十、小结

Agent 评估的核心是「隔离、可复现、可追踪」。离线用冻结环境保复现，在线用影子流量看真实分布；指标须把成功率与 token 成本、时延、工具误用率联合度量，并用完整轨迹做失败归因。相比单轮评测，Agent 因有状态与多路径而更难，工程上必须把环境与日志当作一等公民，才能可靠地迭代改进。
