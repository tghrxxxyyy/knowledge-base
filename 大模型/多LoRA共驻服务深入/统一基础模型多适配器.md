# 统一基础模型多适配器

> 对应 Hu et al. 2021「LoRA」、Ouyang et al. 2022「InstructGPT」与 huggingface/peft。

## 一、背景与挑战

多租户环境里，各方需要不同风格或领域的模型：法务要严谨措辞、电商要促销口吻、代码助手要精确语法。若为每个租户硬隔离部署独立模型，资源浪费严重，运维对象爆炸。

统一基座 + 多适配器提供另一条路径：同一份基础权重服务所有请求，行为差异由适配器承担，实现**逻辑隔离**而非物理隔离。挑战在于：如何保证租户间互不串扰、如何路由到正确适配器、以及如何在不牺牲基座稳定性的前提下容纳不断新增的适配器。

## 二、核心原理

- **单一基座**：$W$ 全局共享，只驻留一份。
- **多适配器**：每个租户/任务持有独立的 $(A_a, B_a, s_a)$。
- **路由器**：按请求元数据（tenant、任务标签）或内容分类器选择适配器。
- **前向隔离**：一次前向只结合被选中适配器的增量，其他适配器不参与计算，因此逻辑上互不影响。
- **默认适配器**：可为无适配器的请求提供「零增量」或通用微调版，保证服务完整性。

与「多模型微服务」相比，统一基座的最大价值是**运维与资源成本的数量级下降**。

## 三、形式化与数学基础

适配器条件下的输出为：

$$f(x; a) = Wx + s_a B_a A_a x$$

其中 $a$ 是适配器标识，$s_a = \alpha_a / r_a$。当 $a = \varnothing$（无适配器）时退化为基座：

$$f(x; \varnothing) = Wx$$

因此多适配器本质是「共享参数 + 条件残差」。租户隔离可形式化为：对任意两个租户 $t_1 \ne t_2$，其请求分别绑定 $a_1 \ne a_2$，则

$$f(x_1; a_1) \text{ 的计算路径不包含 } (A_{a_2}, B_{a_2})$$

这保证了逻辑隔离。理论上，若两个适配器对同一输入的输出分布差异大，也可用 KL 散度等度量其行为距离：

$$D_{KL}\big(p(\cdot \mid a_1) \,\|\, p(\cdot \mid a_2)\big)$$

## 四、代码实现

统一基座 + 多适配器路由器。

```python
import torch
from dataclasses import dataclass

@dataclass
class Adapter:
    A: torch.Tensor      # [r, k]
    B: torch.Tensor      # [d, r]
    scale: float

class MultiLoRARouter:
    def __init__(self, W):
        self.W = W                       # 共享基座: [d, k]
        self.adapters = {}               # aid -> Adapter
        self.default = None              # 无适配器时的默认行为

    def register(self, aid, adapter):
        self.adapters[aid] = adapter

    def __call__(self, x, aid=None):
        out = x @ self.W.T
        if aid is not None:
            ad = self.adapters[aid]
            out = out + ad.scale * (x @ ad.A.T) @ ad.B.T
        return out
```

按租户元数据路由到适配器。

```python
def route(req, router, tenant_grants):
    aid = req.adapter or tenant_grants[req.tenant].get("default")
    if aid is not None and aid not in tenant_grants[req.tenant]["allowed"]:
        raise PermissionError("adapter not allowed")
    return router(req.x, aid)
```

## 五、与其他技术对比

| 方案 | 隔离方式 | 每任务额外成本 | 运维复杂度 | 数据泄露风险 |
| --- | --- | --- | --- | --- |
| 每租户独立模型 | 物理隔离 | 一整份模型 | 高 | 最低 |
| 统一基座 + 多适配器 | 逻辑隔离 | $r(d+k)$ | 低 | 低（需鉴权） |
| Prompt/前缀微调 | 逻辑隔离 | 少量前缀 | 低 | 低 |
| 多租户共享单模型 | 无隔离 | 0 | 最低 | 高 |

统一基座方案在成本与隔离间取得较好平衡，但需警惕基座被某个「污染性」适配器影响通用行为。

## 六、常见误区

- 误区一：共享基座会泄露数据。前向只结合请求绑定的增量，不加载他人数据；但必须做鉴权防止越权调用他人适配器。
- 误区二：逻辑隔离不如物理隔离安全。对于多数商业场景逻辑隔离已足够，合规敏感场景才需物理隔离。
- 误区三：基座永不需要更新。基座升级需重新适配所有适配器，是重大运维事件，应规划版本策略。
- 误区四：路由可以随意猜测。错误的适配器选择会产生不符合预期的输出，路由规则应显式、可审计。

## 八、面试题

1. 多适配器如何保证租户隔离？答：请求绑定 `adapter_id`，路由仅加载对应增量，且鉴权限制可用集合。
2. 无适配器请求如何处理？答：走默认适配器或零增量基座。
3. 基座升级的影响？答：所有适配器需基于新基座验证/重训，需版本与灰度策略。
4. 逻辑隔离的边界在哪？答：共享进程与基座，隔离靠路由与鉴权；强合规场景应物理隔离。

## 九、演进与趋势

基座 + 路由已成为「模型即服务」多租户的标准形态。未来方向包括适配器的自动路由（按内容分类选适配器）、适配器组合（叠加多个增量）以及供应链安全（签名与审计）。具体能力以各平台官方文档为准。

## 十、小结

统一基座多适配器以最低边际成本实现多任务/多租户的逻辑隔离。其数学本质是「共享参数 + 条件残差」$f(x;a) = Wx + s_a B_a A_a x$。落地关键在两件事：可靠的路由（选对适配器）与严格的鉴权（防止越权调用）。
