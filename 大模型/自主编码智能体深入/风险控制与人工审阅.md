# 风险控制与人工审阅

> 对应 SWE-bench 与 SWE-agent 报告中的补丁质量讨论；软件工程中的代码评审与 CI 门禁实践。

## 一、背景与挑战

自动生成的补丁可能通过测试却引入安全漏洞、性能退化或不可维护的实现。
在生产仓库中引入自主智能体，必须回答边界（能改什么）、门禁（怎样才算可合）与责任（谁审阅）三个问题。

## 二、核心原理

- 变更边界：限制可修改路径（排除 CI 配置、密钥、迁移脚本、测试目录），大范围重构需人工发起。
- 分级门禁：静态检查与格式化、单元与集成测试、安全扫描、覆盖率不下降、diff 规模阈值，任一不过即阻断。
- 人在回路：智能体产出分支与 PR 而非直接合入主干，评审关注意图匹配与副作用而非语法。

## 三、数学形式

合入风险可写为 $R=\sum_i p_i L_i(1-d_i)$，其中 $d_i$ 是第 $i$ 类缺陷被门禁与评审检出的概率。

多道独立门禁的漏检率近似相乘 $\prod_j(1-d_{ij})$，因此增加异质检查（测试加静态扫描加人工）比强化单一环节更有效。

## 四、代码实现

```python
FORBIDDEN = ("/tests/", ".github/", "migrations/", "secrets")

def gate(patch, repo):
    if any(f.startswith(FORBIDDEN) or FORBIDDEN[3] in f for f in patch.files):
        return False, "触碰受保护路径"
    if patch.changed_lines > 400:
        return False, "diff 过大, 需人工拆分"
    for check in (lint, unit_tests, integration_tests, security_scan):
        ok, msg = check(repo, patch)
        if not ok:
            return False, msg
    return True, "待人工评审"
```

## 五、与其他对比

- 与人工开发流程：门禁与评审要求相同，差别在于智能体产出速度快，必须靠自动化门禁承担第一道过滤。
- 与完全自动合入：仅在低风险场景（依赖升级、格式化、文档）可考虑，且需完善回滚能力。

## 六、常见误区

- 以「测试通过」等同「可合入」，忽视可维护性、安全与性能。
- 允许智能体改动 CI 与测试，等于让被考核者出考题。
- 缺少快速回滚与变更追溯，一旦出问题无法定位是哪次自动变更引入。

## 八、面试题

- 为什么门禁要异质化？答：不同检查的漏检相互独立，漏检率近似相乘，异质组合远优于单点加强。
- 智能体补丁的评审重点是什么？答：意图是否匹配问题、是否引入副作用与安全风险、改动是否最小可维护，而非语法细节。

## 九、演进

自由改动 → 分支加 PR 流程 → 自动门禁（测试、静态、安全）→ 路径与规模边界约束 → 带回滚与审计的渐进自动化。

## 十、小结

自主编码要落地必须配套门禁与人工审阅：限定边界、异质检查、可回滚可追溯。
