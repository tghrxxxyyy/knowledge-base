# 限流与配额

> 对应 OpenAI Rate Limits 官方指南（https://platform.openai.com/docs/guides/rate-limits）、Anthropic Rate limits 文档（https://docs.anthropic.com/en/api/rate-limits）、LiteLLM Proxy（https://github.com/BerriAI/litellm）、Envoy Proxy（https://github.com/envoyproxy/envoy）、uber-go/ratelimit（https://github.com/uber-go/ratelimit）；并见本库「推理服务深入/推理服务架构」「推理服务深入/大模型部署成本模型」篇章。

## 一、背景与挑战

传统 Web 服务的限流以 QPS 为核心假设：请求轻、耗时毫秒级、单次成本近似均匀。LLM 推理服务同时打破了这三个假设。一次 chat 请求可能携带十万 token 上下文并持续生成数十秒，GPU 显存与算力占用随序列长度、并发批大小动态变化，最贵与最便宜的请求成本可差上百倍；多租户共享同一推理池时，一个租户的突发流量会通过连续批处理（continuous batching）的排队效应拉高所有人的 TTFT。因此限流在 LLM 场景中承担三重职责：保护后端（避免批处理器与 KV Cache 过载）、控制账单（防止 token 支出失控）、保障公平（隔离 noisy neighbor）。难点在于：流式生成完成前无法知道真实输出长度，只能用预估值；单一 RPM 维度无法刻画成本差异；多网关实例下计数器存在同步延迟与误差；限得过死又会制造 429 风暴，客户端盲目重试反而把流量放大数倍。

## 二、核心原理

### 2.1 多维配额：RPM / TPM / TPD / 并发

生产网关通常同时叠加四个维度：RPM（每分钟请求数）控制连接建立频率；TPM（每分钟 token 数）对齐真实成本与容量，是 LLM 特有的核心指标；TPD（每日 token 预算）是账单护栏，超支即熔断；并发数（in-flight requests）限制同时占用 GPU 的序列数，直接保护显存。四者取交集，任一维度超额即拒绝。配额按层级继承：组织 → 项目 → API Key → 终端用户（per-end-user，OpenAI 的 rate limit hierarchy 即此模型），子级预算不超过父级，父级还有全局兜底桶。

### 2.2 令牌桶与滑动窗口

令牌桶允许受控突发：以速率 λ 持续补充令牌，桶容量 b 决定最大突发；请求按成本 w（预估 token 数）扣减，不足则拒绝或等待。漏桶则强制匀速出队，平滑但不容突发。滑动窗口类算法（计数窗口、日志窗口、精确度分级窗口）适合"每分钟 N 次"这类产品化配额语义，实现简单、语义直观，但窗口边界处可能容纳两倍突发。工程上常见组合：RPM 用滑动窗口，TPM 与并发用令牌桶/信号量。

### 2.3 准入控制、排队与 429 退避

被拒请求返回 `429 Too Many Requests` 与 `Retry-After` 头（或 `x-ratelimit-reset-*`），客户端按指数退避加抖动重试。服务端可再加一层软限流：接近阈值时降级（限制 max_tokens、切换小模型、截断上下文）而非硬拒。网关层（Kong、Envoy、APIM 或 LiteLLM 这类 LLM 专属代理）负责集中执行配额，推理引擎只关心容量，二者职责分离。

### 2.4 成本护栏

配额是前置闸，成本护栏是后置账：按模型单价把 token 用量折算为美元，设置日/月预算与告警线（如 80% 预警、100% 停用或降级），并对异常账户做风控。这样限流同时是 SLO 工具和财务工具。

## 三、形式化与数学基础

令牌桶状态为桶内余额 $\sigma$，对任意时刻 $t$：

$$\sigma(t) = \min\big(b,\ \sigma(t_0) + \lambda (t - t_0)\big)$$

请求当且仅当成本 $w \le \sigma(t)$ 时被接纳，接纳后 $\sigma \leftarrow \sigma - w$。可见长期通过率上限为 $\lambda$，而瞬时可容忍至多 $b$ 的突发；对 LLM 取 $w = \hat{L}_{out} + L_{in}$（预估输出 + 实际输入）即可把限流变成成本感知的。

滑动窗口计数（近似版）为：

$$C(t) = \sum_{i} \mathbf{1}[\,t_i \ge t - W\,], \quad \text{reject if } C(t) + 1 > N$$

精确滑动日志则维护时间戳队列并淘汰过期项，内存 $O(N)$；分级精度窗口用"当前窗口计数 + 上一窗口权重 $\theta = \frac{t \bmod W}{W}$"逼近：

$$C_\theta = C_{cur} + \theta \cdot C_{prev}$$

并发限制即计数信号量 $n_{inflight} < C_{max}$。多维配额是多个约束的交集：请求合法 $\iff \bigwedge_k (\text{metric}_k \le \text{quota}_k)$。分布式场景下计数器放 Redis，用 Lua 脚本保证"读-判-写"原子性；每键错误率随同步周期 $T$ 增大，实践中以秒级同步换取 $O(1)$ 内存的近似精度。

## 四、代码实现

```python
import threading
import time

class TokenBucket:
    """成本感知令牌桶：按预估 token 数扣费，而非按请求次数。"""

    def __init__(self, rate: float, capacity: float):
        self.rate = rate          # 每秒补充的 token 配额
        self.capacity = capacity  # 桶容量，允许的最大突发
        self.tokens = capacity
        self.ts = time.monotonic()
        self.lock = threading.Lock()

    def allow(self, cost: float) -> bool:
        with self.lock:
            now = time.monotonic()
            # 按流逝时间补充令牌，但不超过桶容量
            self.tokens = min(self.capacity, self.tokens + (now - self.ts) * self.rate)
            self.ts = now
            if self.tokens >= cost:   # 足额才放行
                self.tokens -= cost
                return True
            return False              # 超额：交由上层返回 429


# Redis 滑动窗口计数（Lua 保证原子性），N 为每窗口上限，W 为窗口秒数
SLIDING_WINDOW_LUA = """
local key = KEYS[1]
local now = tonumber(ARGV[1]); local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)  -- 淘汰过期请求
local n = redis.call('ZCARD', key)
if n < limit then
  redis.call('ZADD', key, now, ARGV[4])               -- 记录本次请求
  redis.call('EXPIRE', key, window)
  return 1
end
return 0
"""

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()
bucket = TokenBucket(rate=200, capacity=1000)

@app.middleware("http")
async def rate_limit(request: Request, call_next):
    user = request.headers.get("x-api-key", "anon")
    est = int(request.headers.get("x-est-tokens", "500"))  # 客户端/网关预估输出
    if not bucket.allow(cost=est):
        # 429 必须带 Retry-After，配合指数退避+抖动避免重试风暴
        return JSONResponse(
            {"error": {"type": "rate_limit_exceeded", "message": "配额已用尽，请稍后重试"}},
            status_code=429,
            headers={"Retry-After": "2", "x-ratelimit-remaining-tpm": "0"},
        )
    return await call_next(request)
```

## 六、常见误区

1. **限流只是防爬虫/DDoS**——LLM 场景首要目标是控成本与保 SLO，内部租户突发同样需要限流。
2. **只看 RPM 就够**——十个 100 token 请求与一个 100k 上下文请求对 GPU 的占用完全不同，必须叠加 TPM 与并发维度。
3. **预估输出长度等于真实值**——`max_tokens`、停止符、模型实际生成长度都会偏离预估，需事后按实际用量结算并在下一周期回补配额。
4. **收到 429 立即重试**——固定间隔重试会形成同步风暴；正确做法是指数退避加全抖动（full jitter），并尊重 `Retry-After`。
5. **限流器放在推理引擎里**——引擎应专注调度与批处理，配额执行上移到网关/代理层，才能跨引擎、跨模型统一治理。
6. **硬限流是唯一手段**——接近阈值时先软限流（降 `max_tokens`、限上下文、排队），硬拒只留给完全超支的账户。
7. **计数器必须强一致**——秒级近似一致性对限流足够，追求强一致反而引入高延迟与可用性风险。

## 八、面试题

1. **RPM 与 TPM 各自防什么？如何组合？**
   要点：RPM 控制连接与调度频率，TPM 对齐成本与吞吐；多维取交集，任一超额即 429，另加并发数保护显存。
2. **令牌桶和滑动窗口的区别？LLM 网关分别用在哪？**
   要点：令牌桶按"成本"扣减、允许大小为 $b$ 的突发；滑动窗口语义是"每分钟 N 次"。TPM 用令牌桶，RPM 用滑动窗口，并发用信号量。
3. **客户端收到 429 该怎么处理？服务端为什么还要给 Retry-After？**
   要点：指数退避 + 抖动，读 `Retry-After`；服务端给出恢复时刻可避免客户端盲猜导致的重试同步化。
4. **如何在多网关实例下做到近似准确又便宜的限流？**
   要点：计数器集中在 Redis 并用 Lua 原子化，接受秒级同步误差；或本地桶 + 周期性全局对账（两级限流）。
5. **预估 token 数与实际消耗不一致怎么办？**
   要点：准入按预估扣减，请求完成后按实际用量结算差额，并把欠账计入下一窗口；长期偏差则校准预估模型。
6. **限流和成本护栏（budget cap）的分工？**
   要点：限流管瞬时速率（保护后端），护栏管累计支出（保护账单）；一个决定"多快"，一个决定"最多花多少"。

## 九、演进与趋势

早期是单机固定 QPS 计数；随后演进到 Redis 分布式滑动窗口与令牌桶，解决多实例一致性；再进一步是多维配额（RPM×TPM×TPD×并发）与层级继承的租户体系。当前趋势包括：配额与计费深度耦合（以美元为统一计量单位）、网关内嵌模型感知的软限流与降级路由、基于预测的自适应限流（按队列深度与 TTFT SLO 动态调整阈值），以及把退避协议标准化（429 + `Retry-After` + 剩余量可观测头部），让客户端 SDK 自带背压能力。

## 十、小结

LLM 服务的限流配额是容量、成本、公平三者的共同闸门：用多维配额（RPM/TPM/TPD/并发）刻画真实负载，用令牌桶与滑动窗口实现平滑执行，用层级租户隔离噪声邻居，用 429 与指数退避形成端到端背压，再用预算护栏兜住账单。工程上的关键判断是——限流器要放在网关层、按成本而非次数计量、预估与实际结算闭环；做到这些，稳定性与成本才同时可控。
