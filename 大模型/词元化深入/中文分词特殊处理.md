# 中文分词特殊处理

> 对应 Sennrich 等《Neural Machine Translation of Rare Words with Subword Units》(BPE, 2016)、Kudo & Richardson《SentencePiece》(2018)、Qwen / ChatGLM / Baichuan 等中文友好 tokenizer 的公开技术报告，以及《计算语言学杂志》中关于中日韩无空格分词的综述。

## 一、背景与挑战

英文等语言天然以空格分词，子词算法（BPE / Unigram）在英文上容易学到有界界的词片段（如 `ing`、`tion`）。中文没有词边界，若直接把 UTF-8 字节丢进 BPE，会出现三类典型问题：

1. **切分过碎**：常用词「学习」被拆成「学」「习」甚至字节碎片，序列长度膨胀，注意力计算与 KV Cache 成本按长度平方/线性上升，直接抬高推理费用。
2. **压缩率失衡**：同一语义下，中文被切成的 token 数常是英文的 1.5～3 倍，导致中英混杂 prompt 中文部分「又贵又慢」，也破坏跨语言对齐。
3. **词表浪费与 OOV 风险**：字节级 BPE 的词表被大量单字与无意义字节对占满，真正高频的双字词、三字词、专有名词反而学不进去；极冷门组合回退到单字，语义表示变差。

中文分词质量因此成为**本地化的第一道成本闸门**：它同时影响序列长度（算力）、词表利用效率（模型容量）和下游任务的分词一致性（效果）。

## 二、核心原理

### 2.1 训练语料与预分词

SentencePiece 的 `user_defined_symbols` 可以把词典条目强制作为整体 token；Qwen 系列在 BPE 训练前先做**字与词混合的预切分**：高频词整词保留，低频词回退为字，再在字级别跑 BPE，兼顾「词的整体性」与「未登录词的覆盖」。

关键经验：**中文语料占比必须足够高**。若 BPE 语料 90% 是英文，中文高频词几乎得不到合并预算。主流做法是在预训练语料采样阶段对中文上采样，或分语言训练子词表再合并。

### 2.2 词级 / 字级 / 字节级的权衡

| 方案 | 代表 | 中文序列长度 | 未登录风险 | 词表效率 |
| --- | --- | --- | --- | --- |
| 纯字级 | 早期 char-CNN | 长（一字一 token） | 极低 | 低（词表小但序列长） |
| 词级 + 字回退 | 传统 NLP 分词器 | 短 | 低 | 中（依赖分词器质量） |
| 字节级 BPE | GPT-2/3/4 风格 | 中偏长 | 无（字节兜底） | 中 |
| 字词混合 BPE | Qwen、ChatGLM | 接近词级 | 低 | 高 |

字节级方案的优点是**永不 OOV**：任何 Unicode 文本都能编码。代价是中文在 UTF-8 下一个汉字占 3 字节，若词表没学到整字/词，一个汉字可能吃 2～3 个 token，序列膨胀可达 3 倍。

### 2.3 中文友好的工程手段

- **前缀约束解码（prefix-constrained decoding）**：生成时强制 token 序列始终是一个合法词表前缀，避免半截词。
- **词表扩展（vocab extension）**：在已有英文底座上，用中文语料继续 BPE 合并，新增若干千个中文子词，再冻结词表微调，避免重训 embedding。
- **中英文边界 token**：在中英交界插入显式边界或使用可识别的语言片段，减少「中文英译腔」和混排错切。
- **与分词器无关的规范化**：NFKC 归一化、全角半角统一、繁简归一，防止「ＡＢＣ」与「ABC」被切成不同 token。

## 三、形式化与数学基础

设文本为字符序列 $c_{1:n}$，BPE 学习合并函数集合 $\mathcal{M}$，编码即反复应用最高优先级的合并：

$$ t^* = \arg\max_{m \in \mathcal{M}} \text{score}(m), \quad c_{i:i+|m|} \rightarrow m $$

**压缩率**定义为：

$$ \text{CR} = \frac{\text{字符数}}{\text{token 数}} $$

英文经验 CR 约 3.5～4.5（字符/token），中文若整词切分 CR 可接近 1.0～1.5（汉字/token），碎切时可能降到 0.4～0.7。序列长度近似 $L \approx N / \text{CR}$，而注意力 FLOPs $\propto L^2$，故 CR 减半意味着注意力算力约变为 4 倍。

**词表规模 $V$ 与期望碎片数**存在权衡：$V$ 增大可覆盖更多中文词，但 softmax/采样成本 $\mathcal{O}(V d)$ 上升；大模型通常把 $V$ 控制在 32k～150k，并把增量预算优先分给中文高频合并。

## 四、代码实现

```python
# SentencePiece：训练中文友好 unigram/BPE，强制整词与特殊符号
import sentencepiece as spm
spm.SentencePieceTrainer.train(
    input="zh_corpus.txt",
    model_prefix="zh_spm",
    vocab_size=32000,
    model_type="bpe",                 # 或 "unigram"
    character_coverage=0.9995,        # 中文建议 1.0 附近，避免生僻字被吞
    user_defined_symbols=["[ZH]","[EN]","<s>","</s>"],
    byte_fallback=True,               # 未登录回退字节，保证可逆
    normalization_rule_name="nmt_nfkc",
)

sp = spm.SentencePieceProcessor(model_file="zh_spm.model")
ids = sp.encode("中文大模型分词优化", out_type=int)
print(sp.decode(ids))  # 无损还原
```

```python
# HuggingFace：前缀合法的中文生成约束（示意）
from transformers import LogitsProcessor, LogitsProcessorList

class PrefixLegal(LogitsProcessor):
    def __init__(self, tokenizer, prefix_ids):
        self.tok, self.prefix = tokenizer, prefix_ids
    def __call__(self, input_ids, scores):
        # 只允许延续合法前缀的 token（生产中用 Trie/Aho-Corasick 实现）
        allowed = self.tok.get_prefix_allowed_tokens_fn(input_ids)
        mask = torch.full_like(scores, -float("inf"))
        mask[0, allowed] = 0.0
        return scores + mask
```

排查线上问题时，先用 `tokenizer.tokenize(text)` 打印中文被切成了什么，再对比 `len(text)` 与 `len(ids)` 估算 CR，就能判断「慢和贵」是不是分词造成的。

## 五、与其他技术对比

| 维度 | 字节级 BPE（GPT 风格） | 字词混合（Qwen/ChatGLM） | 纯词级+字回退 |
| --- | --- | --- | --- |
| 中文序列长度 | 偏长 | 短 | 最短 |
| 未登录 | 无 | 极少 | 依赖词典 |
| 训练成本 | 低（无预分词） | 中（需预切） | 高（需分词器） |
| 多语言迁移 | 好 | 中英均衡好 | 词典绑定语言 |
| 与早期词表兼容 | 好 | 需扩展词表 | 差 |

与**传统中文分词器**（jieba/HanLP）的关系：它们仍是很多 RAG 切块、关键词检索的前置步骤；大模型时代 tokenizer 不再承担句法分词，但「切块检索 + LLM 阅读」链路里两者常并存——切块用词级分词保证语义完整，LLM 用子词 tokenizer 保证可训练。

## 六、常见误区

1. **以为 tokenizer 是小模块可以随便换**——换分词器等于换输入分布，必须重训或至少充分微调 embedding，否则性能崩塌。
2. **中文一定比英文省 token**——恰恰相反，同字数下中文 token 数通常更多；优化目标是提高 CR，不是默认省。
3. **词表越大越好**——$V$ 增大线性抬高 logits 成本，且稀释高频词的 embedding 更新次数。
4. **byte_fallback 无成本**——它保命但拖长序列，只应兜底不应成为主路径。
5. **分词只影响 NLP 任务**——长上下文、RAG 召回打分、Agent 工具调用的 JSON 长度全都吃分词，属于系统工程问题。

## 八、面试题

**1. 为何中文大模型需要专门优化分词？**  
要点：无空格导致 BPE 碎切 → 序列变长 → 注意力与 KV Cache 成本平方/线性上升；同时词表被单字占满，语义单元利用不足。优化 CR 直接等于省钱提速。

**2. 字节级 BPE 如何保证中文不出现 OOV？**  
要点：UTF-8 字节本身在词表中（或有 byte 回退），任何汉字都能编码；代价是可能切成 2～3 个 byte token，拉长序列。

**3. 换 tokenizer 为什么必须重训 embedding？**  
要点：token id 语义改变，原有 embedding 矩阵与输出层的对应关系失效，不重训等于向模型输入乱码。

**4. 如何度量一个中文 tokenizer 好坏？**  
要点：压缩率 CR、高频词整词命中率、中英混排边界错误率、下游任务困惑度/生成质量，以及百万 token 语料的端到端延迟。

**5. RAG 切块和 LLM tokenizer 是一回事吗？**  
要点：不是。切块服务检索语义完整性（可按词/句/段），tokenizer 服务模型训练与推理；两者不匹配会导致「检索到但读不顺」。

## 九、演进与趋势

- **无分词模型复兴**：ByT5、CANINE、Llama 3 的 byte-level 探索表明，足够大的模型可以直接吃字节，但效率仍不敌良好子词表；短期子词仍是主流。
- **多模态统一 token**：图像 patch、音频帧与文本子词共用一套词表，中文文本 token 必须为视觉 token 让出 embedding 预算，推动更激进的压缩。
- **长度感知解码与投机解码**：中文 CR 稳定后，投机采样、MTP（多 token 预测）能更准确地估计接受率。
- **动态词表 / vocab pruning**：按领域裁剪低频子词，进一步压缩 $V$，在端侧模型上收益明显。

## 十、小结

中文分词不是「分词器细节」，而是**成本、延迟、效果的共同上游**。实践三板斧：足够高的中文语料占比、字词混合的子词表、上线后持续用 CR 与混排错误率做回归。把它当成数据与系统问题来治理，中文大模型的「贵和慢」才能从源头降下来。
