# 词表与嵌入规模

> 对应 embedding 矩阵与 $V$ 的参数/显存/softmax 工程权衡；参考大模型架构（LLaMA、GPT、Qwen）中的词表设计讨论；与「字节级BPE」「中文分词特殊处理」衔接。词表不是越大越好——它是容量、成本与数据覆盖的三角问题。

## 一、背景与挑战

大模型的输入输出层都与词表大小 $V$ 绑定：

- **输入嵌入**：$E\in\mathbb{R}^{V\times d}$，参数量 $V d$；
- **输出投影**：常再有一份 $d\times V$（或与嵌入共享）；
- **softmax / 采样**：logits 长度 $V$，与 batch 中每 token 的计算 $\mathcal{O}(V d)$。

当 $V=128k$、$d=4096$ 时，仅嵌入就约 5 亿参数；若输出不共享，再翻倍。于是出现一组张力：

1. **词表大** → 压缩率高、序列短、下游算力省，但嵌入贵、低频 token 训不稳；
2. **词表小** → 输出层便宜，但序列膨胀、长上下文成本上升，中文/代码更吃亏；
3. **多语言 + 代码 + 领域词** 都想塞进词表 → 合并预算与采样配比必须设计。

「换词表 = 换 tokenizer」还意味着**兼容成本**：服务端缓存、数据回灌、微调权重都不能随意混用。

## 二、核心原理

### 2.1 参数账与显存账

嵌入参数：$P_{\text{emb}}\approx V d$（输入）。输出层若不共享再加 $V d$。Adam 训练时每个参数还要 $m,v$ 两份状态（fp32 则约 8 字节/参数量级），嵌入梯度与优化器状态可占可观显存。

**输入输出共享（weight tying）**：输出投影用嵌入转置，参数减半，LM 中常见（尤其中小模型）；超大模型也有解绑以提升容量的案例。共享与否影响「词频-表示」耦合，需实验。

### 2.2 词表规模的经验区间

| 规模 | 典型 $V$ | 观察 |
| --- | --- | --- |
| 偏小 | 8k～16k | 序列长，日志成本高 |
| 主流 | 32k～64k | 多语言与英文均衡 |
| 偏大 | 100k～250k | 压缩好，低频与 embedding 预算压力大 |

并非单调越大越好：超过语料覆盖的 token 训练不足，推理时表现为不稳定或长尾幻觉；同时 $V$ 增大对**每 token 的输出层代价**是线性的。

### 2.3 数据侧配合

- 高频语言/领域提高采样占比，保证大 $V$ 里每个 token 有足够曝光；
- 代码、数学、化学式等「内部字节结构强」的文本，适当加大合并；
- 评估用 **tokens-per-byte** 与 **下游 PPL** 双指标，而不是只看 $V$。

## 三、形式化与数学基础

设序列长度 $L$ 与平均压缩率 $\mathrm{CR}$（字符/token）：

$$ L \approx \frac{N_{\text{chars}}}{\mathrm{CR}(V)} $$

注意力代价 $\propto L^2 d$（标准），输出层代价每步 $\propto V d$。扩大 $V$ 提高 $\mathrm{CR}$、降低 $L$，但抬高每步 $V d$——最优点出现在**语料可支撑的压缩增益 ≈ 输出层边际成本**。

粗略参数占比（仅嵌入，不共享输出）：

$$ \rho_{\text{emb}}=\frac{V d}{P_{\text{total}}} $$

当 $\rho_{\text{emb}}$ 过高时，继续加词表会挤占 Transformer 层容量。

## 四、代码实现

```python
import torch
import torch.nn as nn

class TiedLM(nn.Module):
    def __init__(self, V, d):
        super().__init__()
        self.emb = nn.Embedding(V, d)
        self.proj = nn.Linear(d, V, bias=False)
        self.proj.weight = self.emb.weight   # weight tying

class UntiedLM(nn.Module):
    def __init__(self, V, d):
        super().__init__()
        self.emb = nn.Embedding(V, d)
        self.out = nn.Linear(d, V, bias=False)

def emb_params(V, d, tied=True):
    p = V * d
    return p if tied else 2 * p

print(emb_params(128_000, 4096, tied=False) / 1e6, "M params for emb+out")  # ~1048M
```

服务端注意：大 $V$ 的采样 kernel（top-k/top-p）与 fused softmax 要与词表对齐；分片并行（词表并行 softmax）是多卡训练常规。

## 五、与其他技术对比

| 策略 | 优点 | 缺点 |
| --- | --- | --- |
| 小词表 | 输出层便宜 | 序列长、CR 差 |
| 大词表 | 压缩好 | 低频不稳、embedding 贵 |
| 输入输出共享 | 参数省 | 容量可能受限 |
| 输出层分解/自适应 softmax | 降训练成本 | 实现复杂、推理生态少 |
| 词表扩展 + 冻结旧嵌入 | 兼容底座 | 两边分布需调齐 |

## 六、常见误区

1. **$V$ 越大模型越强**——数据不够时低频 token 是负债。
2. **只算嵌入参数就决定 $V$**——还要算优化器状态、输出 softmax、推理采样带宽。
3. **共享权重永远更好**——大模型解绑提升容量的案例很多，需对照实验。
4. **词表可以热更新**——等于换输出层与嵌入，必须整体迁移策略。
5. **CR 涨了成本一定降**——若注意力平方项主导且 $V$ 使输出层成新瓶颈，需全链路算账。

## 八、面试题

**1. 词表增大如何影响训练与推理成本？**  
要点：嵌入/输出参数与 logits 计算随 $V$ 升；同时序列变短降低注意力成本；总成本有最优点，需按负载估计。

**2. 什么是 weight tying？何时用？**  
要点：输出投影与输入嵌入共享权重，参数约减半；中小模型常用，超大模型视容量需求可解绑。

**3. 如何为多语言选 $V$？**  
要点：按语言/领域 token 曝光分配合并预算，保证低资源语言不被英文主导；用 CR 与任务 PPL 共同验证。

**4. 大 $V$ 的工程挑战？**  
要点：fused softmax/采样、词表并行、优化器状态显存、以及服务侧词表版本治理。

**5. 为何不能「只改 tokenizer 不改权重」？**  
要点：token id 语义变化，嵌入与输出行不再对应语言学单元，模型输入分布被破坏。

## 九、演进与趋势

- **更大多语词表**：百 k 级成为常见，配合数据混合课程。
- **输出层优化**：自适应 softmax、logit 池、检索式输出头仍在研究。
- **动态词表/子词剪枝**：按领域收缩低频，降端侧成本。
- **与多模态统一**：文本词表与图像/音频 token 争夺 embedding 预算，推动更紧的文本压缩。

## 十、小结

词表与嵌入规模决定「每个字花多少钱、每层还有多少参数留给注意力」。决策顺序建议：**先定语言与领域覆盖面 → 估 CR 收益 → 算 embedding+softmax+优化器总账 → 再定 $V$ 与是否 tying**。把词表当系统参数而不是超参装饰，才能避免「换分词器引发全链路重训」的事故。
