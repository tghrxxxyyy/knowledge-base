# 移动端推理框架

> 对应 Apple「MLX 文档」；llama.cpp 项目；Microsoft ONNX Runtime 文档；Alibaba MNN/TNN；mlabonne《LLM Course》。

> 端侧推理框架屏蔽 NPU/GPU/CPU 异构差异，提供模型加载、图优化、算子融合与量化内核，是「小模型跑得动、跑得快」的工程基座。选错框架可能让同一模型在设备上慢数倍甚至跑不起来。当前行业呈现 Apple（MLX/Metal）、Google（NNAPI）、高通（Hexagon）各自生态并存的格局，跨平台框架的价值正是抹平这些差异。

## 一、背景与挑战

移动端与桌面端硬件高度异构：Apple 芯片统一内存、安卓 NPU（如骁龙 Hexagon）、GPU（Mali/Adreno）、CPU 各擅胜场。直接调用底层驱动既复杂又不可移植。挑战包括：(1) 后端碎片化——同一模型需为不同芯片写内核；(2) 内存墙——权重与激活的搬运常比计算更耗时；(3) 功耗——推理要兼顾续航，持续推理会引发降频；(4) 精度——低比特内核的数值稳定性；(5) 冷启动——首次加载/图编译耗时影响首响体验；(6) 版本碎片化——同型号不同系统版本支持的算子集不同。

## 二、核心原理

框架通常分三层：前端（解析 GGUF/Safetensors/ONNX 等格式）→ 中间表示 IR（图级优化：算子融合、常量折叠、布局转换）→ 后端（按硬件选择最优内核，如 MLX 走 Apple Metal、llama.cpp 走 CPU/GPU 通用内核、MNN 走 NPU）。关键优化是**算子融合**（把 LayerNorm+MatMul+RoPE 合成一个 kernel，减少读写）与**量化内核**（INT4/NF4 GEMM）。统一内存架构（Apple）让权重零拷贝共享，显著降低延迟；而安卓需通过 NNAPI 抽象各厂商 NPU，兼容性与峰值性能往往折中。后端选择逻辑通常是「能上 NPU 优先 NPU，否则退回 GPU，最后 CPU 兜底」。

## 三、形式化与数学基础

推理受「屋顶线模型」约束。算力上限（Roofline）为：

$$\text{性能} \le \min\!\left( \pi,\; \frac{\beta}{I} \right)$$

其中 $\pi$ 为峰值 FLOPS，$\beta$ 为内存带宽，$I$ 为算术强度（每字节的浮点运算数）。对解码阶段的逐 token 生成，注意力与残差受内存带宽主导（memory-bound），故优化重心在降低权重搬运量，例如 4-bit 量化把 $I$ 提升约 4 倍：

$$I_{\text{4bit}} \approx 4 \times I_{\text{FP16}}$$

单 token 延迟可定性建模为 $t \approx \tfrac{P \cdot b}{\beta} + \tfrac{C}{\pi}$，其中 $P$ 为参数量、$b$ 为每参数比特数、$C$ 为计算量。由此可见，降比特（$b$）对内存受限的解码阶段收益最大；而 prefill 阶段更偏 compute-bound，靠并行内核提速。

## 四、代码实现

以 MLX 在 Apple 芯片上加载并生成文本为例（示意）：

```python
import mlx_lm

model, tokenizer = mlx_lm.load("mlx-community/Qwen2.5-3B-Instruct-4bit")
messages = [{"role": "user", "content": "用一句话解释端侧推理"}]
prompt = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
for resp in mlx_lm.stream_generate(model, tokenizer, prompt=prompt, max_tokens=64):
    print(resp.text, end="", flush=True)
```

llama.cpp 侧则通过 `llama_load_model_from_file` + `llama_decode` 的 C API，或 `llama-cli`/`llama-server` 直接调用，跨平台覆盖 CPU、Metal、CUDA、Vulkan 等后端。工程上建议用 `llama-server` 暴露 OpenAI 兼容接口，方便与上层应用解耦。一个常见加速手段是预编译图（warm-up）并把推理放到独立线程/队列，避免阻塞 UI。若需横向对比，可用 `time` 统计首 token 延迟（TTFT）与吞吐（token/s）作为选型指标。

## 五、与其他技术对比

| 框架 | 平台 | 后端 | 量化 | 典型用途 |
| --- | --- | --- | --- | --- |
| llama.cpp | 跨平台 | CPU/Metal/Vulkan | GGUF 4/5/8bit | 通用本地推理 |
| MLX | Apple | Metal 统一内存 | 原生 | Mac/iOS 最优 |
| MNN/TNN | 移动 | NPU/GPU | INT8/FP16 | 安卓 App 内嵌 |
| ONNX Runtime | 跨平台 | 多 EP | 多种 | 异构部署 |
| Ollama | 桌面 | 基于 llama.cpp | GGUF | 开发体验 |
| WebGPU/WASM | 浏览器 | GPU | 多 | 网页内推理 |

选型口诀：Apple 优先 MLX（统一内存零拷贝），安卓内嵌优先 MNN/TNN 走 NPU，跨平台/桌面开发优先 llama.cpp/Ollama，网页场景看 WebGPU。

## 六、常见误区

- **后端选错**：iOS 强行用通用内核而放弃 MLX/Metal，性能差数倍。
- **精度误配**：训练用 NF4、推理用 INT8，数值偏差累积。
- **线程争用**：推理线程与 UI 线程抢核，导致卡顿；应隔离推理队列。
- **忽视冷启动**：首次模型加载/编译耗时未做加载动画，体验差。
- **盲目追求参数量**：在弱机上硬跑 7B 而非 3B，延迟与发热失控。
- **只看峰值不看持续**：短时跑得快但触发降频，长会话反而更慢。

## 九、演进与趋势

趋势是统一后端抽象（一处定义、多芯片运行）、NPU 原生大模型内核、浏览器内 WebGPU/WASM 推理、以及「推理+服务」一体化（本地 server、函数调用）。随着端侧芯片算力提升，3B~7B 模型在手机上实时运行将成常态，框架之争将收敛到「谁能更好压榨统一内存与 NPU」。同时，推理与训练（LoRA 微调）同框架化也是方向，让端侧个性化成为可能。

工程落地要点：

- 选型先做基准测试，以 TTFT（首 token 延迟）与 token/s 为核心指标，而非只看参数量。
- 推理须放入独立线程/队列并做 warm-up，规避 UI 卡顿与冷启动。
- 功耗需监控降频，长会话应分段并主动让出资源。
- 低比特内核的数值稳定性要在真机上用下游任务验证，而非仅看体积。
- 跨芯片部署应抽象统一后端，避免每款设备各写一套内核。

## 十、小结

移动端推理框架是端侧大模型的工程底座：以 IR+后端抽象屏蔽硬件碎片，以融合与量化内核压榨算力。选型遵循「看硬件生态」——Apple 选 MLX、安卓看 NNAPI/MNN、跨平台用 llama.cpp，并用独立推理线程与 warm-up 规避卡顿、冷启动与降频。
