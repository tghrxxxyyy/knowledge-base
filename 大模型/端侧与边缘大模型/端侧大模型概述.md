# 端侧大模型概述

> 对应 llama.cpp 项目；Apple「MLX 文档」；Ollama 文档；Kaplan et al. (2020) Scaling Laws；mlabonne《LLM Course》。

> 端侧大模型指在手机、PC、车机等本地设备上运行的小参数模型，主打隐私保护、离线可用与低延迟，代价是能力与上下文受限。它回答的不是「能不能跑」，而是「在有限内存下跑多强的模型」。随着 Apple 智能、安卓 AICore 的推进，端侧推理正从极客玩法走向系统级能力。

## 一、背景与挑战

云端大模型带来两项顾虑：数据出端引发隐私风险，网络往返带来延迟且离线不可用。将模型下沉到设备端，可让语音助手、输入法、文档摘要等「数据不离机」。但端侧算力（NPU/CPU）、内存（常 4~12GB 可用）、功耗都远逊云端，直接跑 7B 以上全精度模型不现实，必须用「小模型 + 低比特 + 高效推理」三件套。另一个隐性挑战是生态碎片化：iOS 与安卓、不同芯片代的可用算力差异巨大，需做能力分级与降级。用户预期管理也是难点——端侧能力边界若不明示，极易产生「端侧=云端」的误解。

## 二、核心原理

端侧可行性公式：模型显存占用 ≈ 参数量 × 每参数字节。一个 3B 模型 FP16 需约 6GB，难以在多数手机常驻；量化到 4-bit 后降到约 1.5~2GB，即可装入。因此典型端侧模型为 1B~3B（兼顾能力与内存），配合 4-bit 量化与 KV-cache 精简（如分组查询注意力 GQA），在本地跑基础对话、摘要、改写。更激进的 MoE 路由可让「总参大、激活小」，在内存受限下获得更强表达。为提升体验，常叠加「系统提示 + 本地知识检索（轻量 RAG）」让小模型表现更稳定。

## 三、形式化与数学基础

内存占用近似：

$$M \approx P \times \frac{b}{8} + \text{KV}_{\text{cache}}$$

其中 $P$ 为参数量、$b$ 为量化比特（4/8/16）。对 $P=3\times10^9,\; b=4$：

$$M \approx 3\times10^9 \times \frac{4}{8} \approx 1.5\ \text{GB}$$

解码吞吐受内存带宽主导（见屋顶线模型），单 token 延迟 $t \approx \tfrac{P \cdot b}{\beta}$。上下文越长，KV-cache 越大，故端侧常限制上下文窗口（如 2k~8k）并启用 GQA 降低每 token 的 KV 体量。经验上 4-bit 3B 在 Apple 芯片上可达 20~40 token/s，已能满足对话级延迟；而 1B 模型可做到更低功耗的「常驻唤醒」。

## 四、代码实现

用 Ollama 拉起一个 4-bit 端侧模型并对话（命令行示意）：

```bash
ollama pull qwen2.5:3b-instruct-q4_K_M
ollama run qwen2.5:3b-instruct-q4_K_M "帮我总结这段本地日志"
```

程序中则通过 Ollama 的 HTTP API（`/api/generate`）或 `ollama` Python 包调用，模型常驻本地、请求不出机。若需更低延迟，可改用 llama.cpp 的 `llama-server` 复用同一模型实例，避免每次冷启动加载。移动端则通过 MLX（iOS）或 MNN（安卓）的原生 API 接入，并用 `max_tokens` 与流式输出控制响应节奏。选定模型前建议用 TTFT 与 token/s 做横向基准测试。

## 五、与其他技术对比

| 维度 | 端侧 | 云端 |
| --- | --- | --- |
| 隐私 | 高（数据不离机） | 低 |
| 能力 | 中（1B~3B） | 强（百亿~千亿） |
| 延迟 | 低 | 中（含网络） |
| 离线 | 支持 | 否 |
| 成本 | 一次性硬件 | 按量计费 |
| 可定制 | 高（本地微调） | 中（API 约束） |

## 六、常见误区

- **盲目追大**：在端侧硬上 7B 全精度，内存爆、速度慢；应量化或换更小模型。
- **忽视 KV 膨胀**：长上下文悄悄吃光内存，应限制窗口或用 GQA。
- **高估能力**：把端侧当云端用，复杂推理失败；应端云协同兜底。
- **忽略发热**：持续推理导致降频，需做负载调度与按需唤醒。
- **忽略生态差异**：同一模型在旧安卓机上跑不动，应做能力分级与降级。
- **不管理预期**：未明示能力边界，用户误用导致差评。

## 九、演进与趋势

随 NPU 算力翻倍与统一内存普及，7B 级模型在旗舰手机实时运行可期；端侧多模态（本地语音、图像理解）兴起；MoE 稀疏激活让「小内存跑大模型」成为可能；端云协同成为主流形态。长期看，端侧将从「能跑基础模型」走向「跑得动多模态 Agent」，系统级端侧智能（OS 内置）会进一步降低使用门槛。

工程落地要点：

- 落地前先用内存公式算清账，明确「能装下几 B、留多少 KV 余量」。
- 上下文窗口与 GQA 是延迟与内存的关键旋钮，应优先调。
- 应做能力分级与降级（旧机跑更小模型），并向用户明示能力边界。
- 避免「端侧=云端」的预期错配，用示例说明适用/不适用场景。
- 典型监控指标：TTFT、token/s、常驻内存、功耗与发热。
- 与云端协同兜底，复杂任务自动上云而非硬扛。
- MoE 可在内存受限下获得更强表达，是进阶选型。
- 真机压测优于纸面估算，不同芯片代际差异巨大。
- 电池与发热预算应纳入产品定义，而非上线后补救。
- 系统级集成（OS 内置）比 App 化更易做到常驻与低延迟。
- 量化与蒸馏应联合优化：先蒸馏再量化，避免分段误差累积。
- 端侧模型选型可参考公开基准（如端侧推理榜单），但不盲信纸面指标。
- 功耗与发热应作为上线门槛，而非上线后被动优化。

## 十、小结

端侧大模型 = 小模型（1B~3B）+ 4-bit 量化 + 高效推理。其价值在隐私、离线、低延迟；落地要点是算清内存账、限制上下文、做能力分级与预期管理，并用端云协同兜住能力上限。
