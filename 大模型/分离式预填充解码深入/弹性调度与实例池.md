# 弹性调度与实例池

> 对应 Zhong 2024 DistServe、Kwon 2023 vLLM 与 Kubernetes 自定义伸缩机制。

## 一、背景与挑战
在线推理负载在一天内波动剧烈：白天高峰排队、深夜低谷闲置。固定实例池要么在高峰容量不足、要么在低谷浪费昂贵 GPU。
弹性伸缩（autoscaling）的目标是让容量跟随负载，在满足 SLA 的前提下最小化成本，这是云推理经济性的核心问题。
在分离式架构下，伸缩更复杂：prefill 池与 decode 池的瓶颈不同、伸缩节奏不同，需要独立管理，且两者比例必须协调。
核心挑战有三：其一是冷启动延迟，加载大模型权重需要时间，秒级伸缩在物理上不成立；其二是伸缩震荡，阈值设置不当会反复增减实例；其三是状态问题，被移除的实例上的 KV 与请求需要妥善迁移或重排。
因此弹性调度不只是「加机器」，而是包含扩缩决策、预热、状态迁移与流量再平衡的系统工程。

## 二、核心原理
分离式服务维护两个独立实例池：prefill 池与 decode 池。每个池监控自身队列长度、利用率与 SLA 违规率，独立触发扩缩。
扩容流程：调度器拉起新实例，实例加载权重（或从分片检查点恢复）并完成初始化，随后向路由层注册，开始接收流量。
缩容流程：挑选利用率最低或已排空的实例，先停止接收新请求（优雅下线），等待在途请求完成后再释放资源。
为缓解冷启动，常采用热备实例池、权重缓存或共享存储快速挂载，让新实例能在较短时间内就绪。
两个池的伸缩必须协调：只扩 prefill 会让 decode 排队，只扩 decode 会让 prefill 成为瓶颈，因此需要按比例或按联合指标决策。

## 三、形式化与数学基础
基于队列积压 $Q$ 与阈值的比例式伸缩决策：

$$ \text{scale} = \begin{cases} +1, & Q > H_{high} \\ -1, & Q < H_{low} \\ 0, & \text{otherwise} \end{cases} $$

为避免震荡，引入冷却时间与滞回（hysteresis），即 $H_{high} > H_{low}$。更精细的做法是按所需副本数直接计算。设到达率 $\lambda$、单实例服务率 $\mu$，为满足 SLA 需：

$$ N \ge \left\lceil \frac{\lambda}{\mu} \cdot (1 + m) \right\rceil $$

$m$ 为安全裕度。冷启动使伸缩存在最小响应时间 $T_{cold}$，若负载变化周期短于 $T_{cold}$，则无法跟踪，需依赖预测式伸缩。成本与 SLA 的权衡可写成：

$$ \min_{N_p, N_d} \; c_p N_p + c_d N_d \quad \text{s.t.} \quad \Pr(\text{TPOT} > \text{SLA}) \le \delta $$

即在违约概率不超过 $\delta$ 的约束下最小化两池成本。

## 四、代码实现
```python
import time

class Pool:
    def __init__(self, high, low, cooldown=60.0, min_size=1):
        self.high, self.low = high, low
        self.cooldown = cooldown
        self.min_size = min_size
        self.replicas = []
        self.last_change = 0.0

    def autoscale(self, qlen, now=None):
        now = now or time.time()
        if now - self.last_change < self.cooldown:
            return  # 冷却期内不动作，防止震荡
        if qlen > self.high:
            self.replicas.append(self._spawn())
        elif qlen < self.low and len(self.replicas) > self.min_size:
            victim = min(self.replicas, key=lambda r: r.util)
            victim.drain()          # 优雅下线：停止接收新请求
            self.replicas.remove(victim)
        else:
            return
        self.last_change = now

    def _spawn(self):
        # 从热备池取就绪实例，避免冷启动延迟
        return self.warm_pool.acquire() or self._cold_start()
```

## 五、与其他技术对比
| 方案 | 伸缩粒度 | 响应速度 | 特点 |
|---|---|---|---|
| 整体伸缩 | 全服务 | 慢 | 简单，但无法分别优化两阶段 |
| 分池独立伸缩 | 每池 | 中 | 贴合两阶段异构需求 |
| 预测式伸缩 | 每池 | 快（提前） | 需流量预测模型 |
| 热备池 | 实例 | 最快 | 占用常驻资源，成本高 |
| Serverless 推理 | 请求级 | 冷启动受限 | 按量计费，长尾贵 |

整体伸缩粒度粗，难以匹配 prefill 与 decode 的不同瓶颈；分两池独立伸缩更贴合异构需求，但增加了协调复杂度。

## 六、常见误区
- 认为秒级伸缩无代价：权重加载与冷启动引入数十秒级延迟，必须预热或保留热备。
- 阈值设置过紧：会反复增减实例造成震荡，需冷却时间与滞回区间。
- 忽视两池协调：单池伸缩导致另一池成为瓶颈，整体 SLA 未必改善。
- 缩容时强杀在途请求：应优雅下线，等待请求完成，避免错误率上升。
- 只看利用率不看 SLA：利用率低不等于可缩容，可能正处于需要余量的关键时段。

## 八、面试题
1. 问：冷启动延迟如何缓解？
   答：保留热备实例、缓存权重、共享存储快速挂载，并采用预测式提前扩容。
2. 问：为什么要分两池独立伸缩？
   答：prefill 与 decode 瓶颈不同、伸缩节奏不同，独立伸缩才能贴合各自需求。
3. 问：如何避免伸缩震荡？
   答：设置冷却时间与滞回阈值（高低水位分离），并对指标做平滑。
4. 问：缩容时如何保证不丢请求？
   答：先停止接收新请求，等待在途请求完成后优雅释放实例。
5. 问：预测式伸缩的前提是什么？
   答：负载具有可预测的周期性或趋势，且预测误差在可接受范围内。

## 九、演进与趋势
- 预测式伸缩结合流量预测，提前预热以规避冷启动。
- 与抢占式实例结合降低单位成本，但需更强的容错与迁移能力。
- 两池联合优化与请求级路由协同，形成端到端的成本-SLA 优化。
- 具体策略与收益以官方最新文档与论文为准。

## 十、小结
弹性分池把成本与 SLA 同时优化，是云推理经济性的关键。核心在于独立管理 prefill/decode 两池、用冷却与滞回抑制震荡、以热备与预测缓解冷启动、并用优雅下线保障缩容不丢请求。冷启动的物理约束决定了弹性有下界，预测与预热是突破它的主要手段。
