# 分布式推理部署实践

> 对应 Shoeybi 2019 Megatron-LM、Rasley 2020 DeepSpeed ZeRO 与 Kwon 2023 vLLM。

## 一、背景与挑战
单卡放不下大模型，即便放得下，单请求的显存与算力也难以支撑长上下文。分布式推理成为必需，需要张量并行、流水线并行、专家并行等组合。
推理的并行需求与训练不同：训练强调吞吐与显存摊薄，推理强调单请求延迟与显存占用，配置策略因此有别。
在分离式架构下，prefill 与 decode 的瓶颈不同——prefill 算力密集、decode 带宽密集——两者对并行度的偏好也不一样。
核心挑战是：并行度越高，通信开销越大；不同阶段、不同并行维度对网络带宽与延迟的敏感度不同，配置需要与硬件拓扑协同设计。
此外还要把并行策略映射到分离式两阶段：各阶段内部用集合通信（如 NCCL），跨阶段用 KV 传输衔接，通信路径必须整体规划。

## 二、核心原理
张量并行（TP）把每层的矩阵乘法按列或行切分到多卡，各卡计算结果再通过 all-reduce 合并，适合把单层计算与显存压力摊到多卡。
流水线并行（PP）把不同层分到不同卡，按 micro-batch 流水执行，减少单卡显存但引入流水气泡，适合跨节点扩展。
专家并行（EP）把混合专家（MoE）的不同专家分到不同卡，按 token 路由计算，适合稀疏模型，但路由会带来不均衡与通信。
在分离式部署中，prefill 常用较高 TP/PP 以缩短首 token 计算，decode 更受显存带宽限制，可用较小并行度以减少每步通信。
各并行组内部通过 NCCL 做集合通信，跨 prefill/decode 阶段则通过 KV 缓存传输衔接，两条通信路径的拓扑与带宽要求不同。

## 三、形式化与数学基础
张量并行度 $t$ 时，权重矩阵按维度切分，输出由各分片结果拼接：

$$ Y = \mathrm{concat}(Y_1, \dots, Y_t),\qquad Y_i = X W_i $$

每次前向需要一次 all-reduce 聚合，通信量与 $t$ 及隐藏维 $d$ 相关，近似与层输出规模成正比。单步通信开销可粗略表示为：

$$ T_{comm}^{TP} \approx \frac{2 \cdot (t-1)}{t} \cdot \frac{S_{\text{act}}}{B_{\text{link}}} $$

其中 $S_{\text{act}}$ 为激活字节数、$B_{\text{link}}$ 为链路带宽。$t$ 增大时通信占比上升，超过某点后延迟不降反升。
流水线并行的气泡比例（$p$ 为流水段数、$m$ 为 micro-batch 数）近似为：

$$ \text{bubble} \approx \frac{p - 1}{m + p - 1} $$

增大 $m$ 可摊薄气泡，但受显存限制。分离式下 decode 每步都要通信，带宽敏感，故常选较小 $t$、较大批；prefill 则可容忍更高并行以缩短 TTFT。

## 四、代码实现
```python
# 概念示意：为不同阶段选择不同的并行配置
from dataclasses import dataclass

@dataclass
class ParallelConfig:
    tp: int   # 张量并行度
    pp: int   # 流水线并行度
    ep: int   # 专家并行度

# prefill 侧重算力，可用较高并行缩短首 token 延迟
prefill_cfg = ParallelConfig(tp=8, pp=2, ep=1)
# decode 侧重带宽与显存，减小 TP 以降低每步通信
decode_cfg = ParallelConfig(tp=4, pp=2, ep=1)

def build_engine(model_path, cfg, phase):
    # phase 取 'prefill' 或 'decode'，据此建立对应并行组
    return Engine(model_path, tp=cfg.tp, pp=cfg.pp, ep=cfg.ep, phase=phase)

prefill_engine = build_engine("model", prefill_cfg, "prefill")
decode_engine = build_engine("model", decode_cfg, "decode")
```

## 五、与其他技术对比
| 并行维度 | 切分对象 | 主要收益 | 主要代价 |
|---|---|---|---|
| 张量并行 TP | 层内矩阵 | 降单层延迟与显存 | 每层 all-reduce 通信 |
| 流水线并行 PP | 层间 | 跨节点扩展显存 | 流水气泡 |
| 专家并行 EP | MoE 专家 | 支撑稀疏大模型 | 路由不均衡与通信 |
| 数据并行 DP | 请求/批次 | 提升吞吐 | 权重副本占显存 |
| 序列并行 | 序列维度 | 降长上下文激活 | 通信与实现复杂 |

训练并行强调吞吐与稳定扩展，推理并行强调单请求延迟与显存，配置与调优目标不同，不能直接照搬。

## 六、常见误区
- 把训练并行配置直接套到推理：decode 受带宽限制，TP 过大反而增加通信、抬高每步延迟。
- 忽视阶段差异：prefill 与 decode 用同一并行度，无法分别优化各自的瓶颈。
- 忽略拓扑：跨节点 TP 的 all-reduce 走低速网络会严重拖慢，应把高通信维度放在高带宽域内。
- 只追求显存放下：并行度以满足显存为唯一目标，忽略通信与气泡对延迟的损害。
- 忽视跨阶段 KV 传输：并行组不一致会导致 KV 布局重排，增加额外开销。

## 八、面试题
1. 问：推理中 TP 与 PP 如何取舍？
   答：TP 降单步延迟但增通信；PP 减少通信但增气泡，需依网络带宽与模型规模选择。
2. 问：为什么 decode 阶段不宜用过大的 TP？
   答：decode 每步都需通信，TP 越大 all-reduce 占比越高，延迟不降反升。
3. 问：流水线气泡如何缓解？
   答：增大 micro-batch 数摊薄气泡，但受显存限制，也可用交错调度。
4. 问：分离式下并行配置为何要分阶段设计？
   答：prefill 算力密集、decode 带宽密集，瓶颈不同，最优并行度不同。
5. 问：如何把并行映射到硬件拓扑？
   答：把通信最密集的维度放在 NVLink 等高带宽域内，减少跨节点慢链路通信。

## 十、小结
分布式部署需把并行策略与两阶段架构协同设计：TP 摊薄单层延迟与显存、PP 跨节点扩展、EP 支撑稀疏模型，而分离式要求 prefill 与 decode 各用匹配其瓶颈的并行度。只有兼顾显存、通信与气泡，才能在延迟与吞吐之间取得平衡。
