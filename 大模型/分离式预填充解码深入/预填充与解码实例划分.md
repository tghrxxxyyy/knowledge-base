# 预填充与解码实例划分

> 对应 Patel 2024 Splitwise、Zhong 2024 DistServe 与 Kwon 2023 vLLM。

## 一、背景与挑战
分离式把服务拆成 prefill 池与 decode 池后，紧随其后的工程问题是：两池各需要多少实例？比例如何确定？
请求到达率、prompt 长度分布、输出长度分布共同决定了两阶段的算力需求比例。比例失衡会同时造成排队与闲置。
SLA 是划分的约束条件：prefill 决定首 token 延迟（TTFT），decode 决定逐 token 延迟（TPOT），两者必须同时满足。
核心挑战在于负载是动态的：到达率随时刻变化，prompt 与输出长度分布也可能漂移，静态比例很快会失配。
因此实例划分不是一次性容量规划，而是持续运行的控制问题：需要按实时指标动态调整比例，并在调整中兼顾成本与响应速度。

## 二、核心原理
划分的基本思路是按 SLA 反推各阶段所需并发实例数。prefill 池需保证队列中的请求能在 TTFT 上限内完成首 token。
decode 池需保证同时在解码的序列能在 TPOT 上限内完成每步，因此其规模与「活跃序列数」而非到达率直接相关。
两池的负载特征不同：prefill 的负载与到达率乘以 prompt 长度相关，decode 的负载与活跃序列数乘以输出长度相关。
实践中先用排队论或经验公式估算，再用实测数据校准，最后交给弹性伸缩持续调节。
常用做法是设定两池的目标利用率或目标队列积压，通过闭环控制把实际指标拉回目标区间，实现比例的自适应。

## 三、形式化与数学基础
设请求到达率 $\lambda$、平均 prefill 计算耗时 $T_{prefill}$、TTFT 上限 $SLA_{ttft}$，则所需 prefill 实例数下界为：

$$ N_p \ge \frac{\lambda \cdot T_{prefill}}{SLA_{ttft}} $$

decode 侧，设活跃序列数为 $n_{active}$、单步耗时 $T_{step}$、TPOT 上限 $SLA_{tpot}$，则：

$$ N_d \ge \frac{n_{active} \cdot T_{step}}{SLA_{tpot}} $$

活跃序列数可由到达率与平均输出长度估计（利特尔法则）：

$$ n_{active} \approx \lambda \cdot \bar{L}_{out} \cdot T_{tpot} $$

两池比例随平均 prompt 长度 $\bar{L}_{in}$ 与输出长度 $\bar{L}_{out}$ 变化：

$$ \frac{N_p}{N_d} \propto \frac{\lambda \cdot T_{prefill} / SLA_{ttft}}{n_{active} \cdot T_{step} / SLA_{tpot}} $$

长 prompt 场景提高该比例，长输出场景降低该比例。实际部署还需预留安全裕度并考虑实例异构。

## 四、代码实现
```python
import math

def plan_instances(lam, t_prefill, t_step, n_active,
                   sla_ttft, sla_tpot, margin=0.3):
    # 依 SLA 反推两池所需实例数，margin 为安全裕度
    n_p = math.ceil(lam * t_prefill / sla_ttft * (1 + margin))
    n_d = math.ceil(n_active * t_step / sla_tpot * (1 + margin))
    return max(n_p, 1), max(n_d, 1)

def active_sequences(lam, avg_out_len, tpot):
    # 利特尔法则估计同时解码的序列数
    return lam * avg_out_len * tpot

def rebalance(pools, n_p, n_d):
    # 闭环调整：向目标实例数靠拢，受冷却时间约束
    pools.prefill.scale_to(n_p)
    pools.decode.scale_to(n_d)

lam = 50.0            # 每秒请求数
n_active = active_sequences(lam, avg_out_len=200, tpot=0.05)
np_, nd_ = plan_instances(lam, t_prefill=0.2, t_step=0.01,
                          n_active=n_active, sla_ttft=1.0, sla_tpot=0.1)
print(np_, nd_)
```

## 五、与其他技术对比
| 划分方式 | 依据 | 优点 | 缺点 |
|---|---|---|---|
| 固定比例 | 经验设定 | 简单、可预测 | 负载漂移即失配 |
| 按 SLA 估算 | 排队模型 | 有理论依据 | 依赖参数准确性 |
| 闭环反馈 | 实时指标 | 自适应、抗漂移 | 需调参、可能滞后 |
| 预测式 | 流量预测 | 提前预热 | 预测误差风险 |
| 联合优化 | 成本+SLA | 全局最优 | 实现复杂 |

固定比例实现最简但很快失配；按 SLA 估算给出起点；闭环反馈维持在线平衡；预测式用于规避冷启动。多者常组合：估算定初值，反馈做微调，预测做前瞻。

## 六、常见误区
- 认为实例越多越好：跨实例传输与调度开销随实例数上升，过量实例反而降低效率。
- 用固定比例应对全天：到达率与长度分布随时间变化，比例必须动态调整。
- 只按到达率规划 decode：decode 负载与活跃序列数相关，忽略输出长度会严重低估。
- 忽视安全裕度：按理论下界配置会在抖动时违约，需预留余量。
- 频繁调整比例：调整本身有冷启动与迁移成本，需冷却时间与滞回。

## 八、面试题
1. 问：如何确定 prefill/decode 实例比例？
   答：依到达率、prompt 与输出长度分布及 SLA，用排队模型估算后动态调整。
2. 问：decode 负载由什么决定？
   答：主要由同时活跃的序列数与单步耗时决定，与到达率和输出长度相关。
3. 问：为什么固定比例会失配？
   答：到达率与长度分布随时间漂移，静态比例无法跟踪负载变化。
4. 问：安全裕度的作用？
   答：吸收负载抖动与实例异构带来的波动，降低 SLA 违约概率。
5. 问：利特尔法则在这里怎么用？
   答：用到达率乘平均输出长度与 TPOT 估计同时活跃的序列数，进而推算 decode 规模。

## 十、小结
实例划分本质是按 SLA 做容量规划：prefill 规模与到达率、prompt 长度相关，decode 规模与活跃序列数、输出长度相关，比例应随负载动态调整。正确做法是估算定初值、闭环做微调、预测做前瞻，并预留安全裕度，避免失衡导致的排队与闲置并存。
