# 分离式架构动机与瓶颈

> 对应 Zhong 2024 DistServe、Patel 2024 Splitwise 与 Kwon 2023 vLLM。

## 一、背景与挑战
大模型推理分为两个性质迥异的阶段：prefill 一次处理整个 prompt、计算密集；decode 逐 token 自回归生成、访存密集。
当二者在同一实例上混跑时，prefill 的大矩阵乘会长时间占用计算与显存带宽，使正在进行的 decode 步被拖慢，逐 token 延迟（TPOT）出现剧烈抖动。
更糟的是，TPOT 抖动直接伤害用户体验与 SLA，尤其是对「流式输出稳定」敏感的应用；尾延迟难以通过增加批量来平抑。
核心矛盾在于：两个阶段的资源画像相反——prefill 想要高算力利用，decode 想要高带宽与低延迟——放在一起必然互相干扰。
分离式架构的动机正是把二者物理隔离，让各自在最适合的资源配置下运行，从而稳定 decode 延迟。

## 二、核心原理
分离式把 prefill 与 decode 部署到不同的 GPU 池：prefill 实例专注首 token 计算，decode 实例专注逐 token 生成。
两个阶段通过 KV 缓存传输衔接：prefill 产出 KV，传给 decode 作为后续解码的上下文，从此 decode 不再需要重算 prompt。
这样 prefill 池可以按算力优化（更高并行度、更大批量提高吞吐），decode 池按带宽与延迟优化（较小并行度、更大并发批）。
代价是引入了 KV 跨实例传输，以及更复杂的调度与运维。因此分离式并非无条件更优，需要收益大于代价才划算。
判断依据是干扰的严重程度：prompt 越长、并发越高，耦合下的相互干扰越强，分离的收益越明显。

## 三、形式化与数学基础
耦合部署下，decode 的单步时延被 prefill 干扰：

$$ T_{decode}^{coupled} = T_{comp} + T_{interfere}(\text{prefill}) $$

其中 $T_{interfere}$ 随 prefill 的批量与序列长度增长，是 TPOT 抖动的来源。分离后干扰项被移除，但增加 KV 传输：

$$ T_{decode}^{disagg} \approx T_{comp} + T_{kv\_transfer} $$

分离的净收益要求干扰消除量超过传输开销：

$$ T_{interfere}(\text{prefill}) > T_{kv\_transfer} $$

把 TTFT 与 TPOT 的 SLA 同时纳入，分离式的价值在于改善尾延迟而非平均吞吐：

$$ \min \; \Pr\big(\text{TPOT} > \text{SLA}_{tpot}\big) \quad \text{s.t.} \quad \Pr\big(\text{TTFT} > \text{SLA}_{ttft}\big) \le \delta $$

在长 prompt 场景下，$T_{interfere}$ 显著而 $T_{kv\_transfer}$ 可被重叠隐藏，不等式成立，分离收益明显；短 prompt 下则相反。

## 四、代码实现
```python
def coupled_serve(prompt, model, decode_steps):
    # 同实例：prefill 与 decode 交替，互相干扰
    kv = model.prefill(prompt)
    tokens = []
    for _ in range(decode_steps):
        tok, kv = model.decode_step(kv)
        tokens.append(tok)
    return tokens

def disaggregated_serve(prompt, prefill_engine, decode_engine, net):
    # 分离：prefill 池算首 token 与 KV，decode 池继续生成
    prefill_out = prefill_engine.run(prompt)
    move_kv(prefill_out.kv, decode_engine.addr, net)  # 跨实例传输
    return decode_engine.generate(prefill_out.kv, decode_steps=128)

# 估算分离收益：干扰量 vs 传输开销
def disagg_gain(t_interfere, kv_bytes, net_bw):
    t_transfer = kv_bytes / net_bw
    return t_interfere - t_transfer   # 大于 0 才有净收益
```

## 五、与其他技术对比
| 架构 | 延迟稳定性 | 资源效率 | 复杂度 | 适用场景 |
|---|---|---|---|---|
| 耦合部署 | 低（干扰大） | 中 | 低 | 短 prompt、低并发 |
| 分离部署 | 高 | 高（各取所长） | 高 | 长 prompt、高并发 |
| 分块预填充 | 中 | 中 | 中 | 耦合下的折中 |
| 连续批处理 | 中高 | 高 | 低 | 通用吞吐优化 |
| 优先级调度 | 中 | 中 | 中 | 保护关键请求 |

分块预填充把长 prefill 切成小块与 decode 交错执行，可在耦合模式下缓解干扰；连续批处理提升整体吞吐，二者与分离式正交。

## 六、常见误区
- 认为分离总更快：短 prompt 下传输开销可能抵消甚至超过收益。
- 只看平均吞吐：分离的核心价值在稳定 TPOT 与改善尾延迟，只看均值会误判效果。
- 忽视 KV 体积：长上下文下 KV 传输可能成为新瓶颈，需配合 GQA、量化与异步重叠。
- 忽略运维成本：两池、KV 传输、路由与弹性都增加复杂度，需评估团队能力。
- 把分离当成万能解：耦合加调度优化有时是更经济的方案，应按负载选择。

## 八、面试题
1. 问：分离式主要解决什么指标？
   答：主要压低并稳定 decode 的 TPOT，减少 prefill 对 decode 的干扰。
2. 问：耦合下 TPOT 为何抖动？
   答：prefill 的大矩阵乘占用计算与带宽，使 decode 步被拖慢，时延出现波动。
3. 问：分离的代价是什么？
   答：KV 跨实例传输、更复杂调度与运维，以及两池资源配比问题。
4. 问：什么负载下分离收益最大？
   答：长 prompt、高并发、对尾延迟敏感的场景，干扰强且传输可被隐藏。
5. 问：分离与分块预填充如何选择？
   答：改动成本低时先试分块预填充；干扰与 SLA 压力大时再上分离部署。

## 九、演进与趋势
- 弹性实例池按需扩缩 prefill/decode 比例，成为云推理主流形态。
- KV 压缩、异步传输与拓扑感知放置持续降低分离代价。
- 混合模式与请求级路由让分离按需启用，而非全局强制。
- 具体架构与性能结论以官方最新文档与论文为准。

## 十、小结
分离式通过物理隔离两阶段，把异构瓶颈分别优化，换来稳定低延迟。其动机是消除 prefill 对 decode 的干扰，代价是 KV 传输与运维复杂度。是否采用取决于干扰强度与传输开销的量化对比——长 prompt 高并发时分离占优，短请求低并发时耦合更经济。
