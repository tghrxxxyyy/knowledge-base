# 分离式与混合并发模式

> 对应 Zhong 2024 DistServe、Patel 2024 Splitwise 与 Kwon 2023 vLLM。

## 一、背景与挑战
推理服务有两种基本部署形态：把 prefill（预填充）与 decode（解码）放在同一实例（耦合），或拆到不同实例（分离）。
纯耦合部署实现简单、无跨实例传输，但在大流量与长 prompt 下，prefill 的大矩阵乘会挤占 decode 的带宽，导致逐 token 延迟（TPOT）抖动、尾延迟难控。
纯分离部署把两阶段物理隔离，延迟稳定、可独立扩缩，但对短请求收益有限，还引入 KV 传输与更复杂的运维。
核心挑战在于没有单一最优形态：最优选择取决于流量形态、prompt 长度分布、SLA 严格程度与集群拓扑。
因此现代服务倾向提供多种模式，并按请求特征动态路由，让严格 SLA 的关键请求走分离、普通请求走耦合。

## 二、核心原理
模式一：纯耦合（coupled）。prefill 与 decode 在同一实例内顺序执行，适合小流量、短 prompt、同节点资源充足的场景，运维最简单。
模式二：纯分离（disaggregated）。prefill 实例只做首 token 计算，decode 实例只做逐 token 生成，两者通过 KV 缓存传输衔接，适合大流量且对延迟稳定性要求高的场景。
模式三：混合（hybrid）。网关按请求的 SLA 与特征路由，关键请求走分离流水线，普通请求走耦合流水线，兼顾成本与体验。
路由决策的依据包括：prompt 长度、期望输出长度、请求优先级、当前两池的队列深度与负载。
把模式选择形式化后，它本质是一个带约束的成本最小化问题：在满足 SLA 的前提下最小化单位请求成本。

## 三、形式化与数学基础
设模式 $m$ 的单位请求成本为 $\text{cost}_m$，SLA 违反量为 $\text{violation}_m$，用拉格朗日式权重 $\lambda$ 惩罚违约：

$$ m^{*} = \arg\min_{m \in \{\text{coupled}, \text{disagg}, \text{hybrid}\}} \Big( \text{cost}_m + \lambda \cdot \text{violation}_m(\text{SLA}) \Big) $$

对单请求的路由可用阈值规则近似。设 TTFT 与 TPOT 的 SLA 分别为 $T_{ttft}, T_{tpot}$，分离只有在收益超过传输代价时才划算：

$$ \Delta_{\text{disagg}} = \big(T_{tpot}^{\text{coupled}} - T_{tpot}^{\text{disagg}}\big) - T_{kv\_transfer} > 0 $$

当 prompt 短、KV 体积小且传输快时 $T_{kv\_transfer}$ 很小但收益也小；当 prompt 长、并发高时耦合干扰大，分离收益显著。整体收益还取决于两池的负载比 $r = \lambda_p / \lambda_d$ 与实例配比，配比失配会同时浪费算力并推高排队。

## 四、代码实现
```python
def route(req, pools):
    # 依据 SLA 严格程度与 prompt 特征选择执行模式
    if req.sla_strict or req.prompt_len > pools.long_prompt_threshold:
        return disaggregated_pipeline(req, pools.prefill, pools.decode)
    if pools.prefill.queue_len > pools.prefill.high or \
       pools.decode.queue_len > pools.decode.high:
        # 任一池拥塞时，普通请求改走耦合以保护关键请求
        return coupled_pipeline(req, pools.coupled)
    return coupled_pipeline(req, pools.coupled)

def disaggregated_pipeline(req, prefill_pool, decode_pool):
    prefill_out = prefill_pool.run(req)          # 计算首 token 与 KV
    kv = move_kv(prefill_out.kv, decode_pool)    # 跨实例传输 KV
    return decode_pool.generate(kv, req)         # 逐 token 解码

def coupled_pipeline(req, pool):
    return pool.run(req)                         # 同实例完成两阶段
```

## 五、与其他技术对比
| 模式 | 延迟稳定性 | 运维复杂度 | 传输开销 | 适用场景 |
|---|---|---|---|---|
| 纯耦合 | 低（受干扰） | 低 | 无 | 小流量、短 prompt |
| 纯分离 | 高 | 高 | 有（KV） | 大流量、严 SLA |
| 混合 | 中高 | 中高 | 部分 | 流量形态混合 |
| 连续批处理 | 提升吞吐 | 低 | 无 | 通用优化，与模式正交 |
| 分块预填充 | 缓解干扰 | 中 | 无 | 耦合模式下折中 |

连续批处理（continuous batching，Orca 风格）与分块预填充（chunked prefill）可在耦合模式下缓解干扰，属于与部署模式正交的调度技术。

## 六、常见误区
- 一律上分离：小流量下运维与传输开销得不偿失，短 prompt 收益尤其有限。
- 认为分离一定更快：传输与调度开销可能抵消甚至超过收益，需按负载与 SLA 判断。
- 忽视两池配比：实例比例失配会导致一池排队、另一池闲置，整体体验下降。
- 只优化吞吐不看尾延迟：分离的核心价值在稳定 TPOT 与尾延迟，只看平均吞吐会误判。
- 忽略网关复杂度：混合模式需要成熟的按 SLA 路由与拥塞感知，否则比单模式更难运维。
- 认为模式一旦选定就不变：流量形态随时间变化，模式与配比应通过闭环控制动态调整。

## 八、面试题
1. 问：何时不该用分离式？
   答：短 prompt、低并发、同节点资源充足时，耦合更简单更省成本。
2. 问：混合模式的路由依据是什么？
   答：SLA 严格程度、prompt/输出长度、请求优先级与两池队列深度。
3. 问：分离与连续批处理的关系？
   答：正交。连续批处理提升单实例吞吐，分离改变部署拓扑，二者可同时使用。
4. 问：分离的主要代价是什么？
   答：KV 跨实例传输、更复杂调度与运维、以及两池配比不当带来的资源浪费。
5. 问：如何判断分离是否划算？
   答：比较 TPOT 收益与 KV 传输开销，并结合负载比与实例成本核算。

## 九、演进与趋势
- 自适应路由在请求级动态选模式，成为高级推理网关的标配能力。
- 与弹性实例池结合，按流量形态实时调整两池配比与模式。
- 分块预填充、优先级调度与分离式的组合仍在演进。
- 具体实现与性能结论以官方最新文档与论文为准。

## 十、小结
分离与耦合并非互斥，按 SLA 与流量混合部署最实际。纯耦合胜在简单、纯分离胜在稳定、混合胜在灵活。正确决策依赖对流量形态、传输代价与两池配比的量化判断，而非一刀切地追求某一种模式。
