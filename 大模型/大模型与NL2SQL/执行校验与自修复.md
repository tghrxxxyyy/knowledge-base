# 执行校验与自修复

> 对应提升 SQL 可运行率的工程实践；思想参考 Self-Debugging / ReAct 式自修复与 Spider 的执行准确率评测。

## 一、背景与挑战

LLM 生成的 SQL 常有语法错误（缺括号、错关键字）、语义错误（字段不存在、类型不符、表拼错）、逻辑错误（JOIN 条件缺失）。若不校验直接返回，用户会看到数据库报错或一串错误数据，体验极差。执行校验是自修复闭环的第一道闸。

挑战：(1) 报错信息噪声大，需结构化才能回灌；(2) 危险语句（DROP/UPDATE/DELETE）必须拦截；(3) 多次重试可能陷入死循环；(4) 执行成功不等于结果正确（需合理性检查）；(5) 重试有成本，需设上限。

## 二、核心原理

核心是一个「生成 → 执行 → 诊断 → 修复」的 ReAct 式循环：

1. 在隔离的只读影子库执行预测 SQL；
2. 捕获异常（语法错误、字段未找到、类型不匹配等），转为结构化错误消息；
3. 把 `[原始问题, 上一SQL, 错误]` 回灌模型，要求其修正；
4. 设置最大重试步数，超限则降级返回「无法生成可靠 SQL」或走人工；
5. 执行通过后，对结果做轻量合理性检查（行数、空结果、类型）。

## 三、形式化与数学基础

设第 $k$ 次尝试生成 SQL 为 $\hat y_k$，执行函数返回状态：

$$\text{exec}(\hat y_k) \in \{\text{ok}, \text{err}(m_k)\}$$

其中 $m_k$ 为结构化错误信息。自修复迭代：

$$\hat y_{k+1} = \text{LLM}(q, \mathcal{R}(S,q), \hat y_k, m_k)$$

终止条件为 $\text{exec}(\hat y_k)=\text{ok}$ 或 $k\ge K$（最大步数）。成功率可定义为：

$$P_{\text{fix}} = \frac{1}{N}\sum_i \mathbb{1}[\exists k\le K: \text{exec}(\hat y_{i,k})=\text{ok}]$$

## 四、代码实现

带步数限制与只读约束的校验循环（示意）：

```python
def self_heal(question, schema, max_step=3):
    sql = llm.generate(question + schema)
    for step in range(max_step):
        status, msg = safe_execute(sql, shadow_db, read_only=True)
        if status == "ok":
            return sql
        sql = llm.generate(
            f"问题:{question}\n上一SQL:{sql}\n报错:{msg}\n请修正SQL")
    return None  # 降级：转人工或提示用户
```

## 五、与其他技术对比

| 手段 | 覆盖 | 局限 |
|------|------|------|
| 仅语法检查 | 语法 | 抓不到字段/类型错 |
| 执行校验 | 语法+语义 | 需数据库环境 |
| 执行+自修复 | 可自愈 | 有重试成本 |
| 静态 schema 校验 | 轻量 | 不验证结果 |

生产应以「执行校验 + 自修复」为主，语法检查仅作前置快速失败。

## 六、常见误区

- 不校验直接返回，用户看到数据库报错。
- 允许写操作致数据风险：必须在 DB 层与 SQL 解析层双重禁止非 SELECT。
- 报错原文整段回灌，模型被无关堆栈干扰，应抽取关键 message。
- 无限重试：不设最大步数，可能打满额度或死循环。
- 只看「能否执行」，不检查「结果是否合理」（空结果/行数异常）。

## 九、演进与趋势

从纯文本报错到「错误分类器」：区分语法/模式/执行/逻辑错误并匹配不同修复策略；结合单元测试式断言（用户对结果的描述）做语义校验；引入执行计划代价估计筛掉低效 SQL；与多轮问数联动，让用户参与修正；并把自修复成功率作为评测驱动开发的回归指标。

## 十、小结

执行校验 + 自修复大幅提升 SQL 可用率。关键是隔离只读环境、结构化回灌报错、设最大步数降级，并辅以结果合理性检查，构成生成的最后一道防线。
