# 字典表与关联表映射

> 对应业务库 NL2SQL 专项难点；关系建模思想参考数据库范式与 Spider 的外键标注（Yu et al. 2018）。

## 一、背景与挑战

真实业务库普遍包含两类「隐含知识」：字典表（如 `status` 字段存整数 1/2/3，含义为生效/失效/冻结）与关联表（多对多关系，如 `user_role` 连接用户与角色）。自然语言提问常直接使用业务术语（「看生效的订单」「查管理员用户」），但模型若只看到裸 schema（`status INT`、`user_role` 表），无从知道 1=生效、谁算管理员，从而生成非法或语义错误的 SQL。

挑战：(1) 枚举值映射不在 schema 文本中，模型只能猜；(2) 外键关系需跨表 JOIN，但表名/字段名不提示语义；(3) 同名字段在不同表产生歧义；(4) 字典值会随业务演化（新增状态），映射需可维护。

## 二、核心原理

核心是把「业务语义」显式注入上下文，让模型能翻译术语为 SQL 约束：

- 字典映射表：列出 `字段 → 枚举值 → 业务含义`，如 `orders.status: 1=生效, 2=失效`。
- 外键/关联表：显式给出 `A.id = B.a_id` 关系，提示需要 JOIN。
- 业务术语词典：`「管理员」→ role 表中 name='admin'`。
- 在 prompt 中以「已知关系」区块呈现，或预先用工具把自然语言问句中的术语替换为可查询条件。

## 三、形式化与数学基础

设字典约束为函数 $D(\text{field}, v)=\text{label}$，自然语言词 $w$ 映射到枚举条件：

$$\text{cond}(w) = \bigvee_{v:\, D(\text{field},v)=w} (\text{field} = v)$$

例如「生效订单」$\Rightarrow \text{orders.status}=1$。对外键 $R$ 连接两表 $T_a,T_b$，生成 JOIN 谓词：

$$T_a.\text{id} = T_b.\text{fk} \quad (\text{fk}\in R)$$

模型需在 WHERE/JOIN 中正确实例化这些等式。若枚举缺失，模型可能采样任意值导致结果空集或错误集。

## 四、代码实现

把映射注入为 prompt 上下文（示意）：

```python
context = (
    "【业务术语映射】\n"
    "- 字典 orders.status: 1=生效, 2=失效\n"
    "- 字典 user.type: 1=个人, 2=企业\n"
    "【外键关系】\n"
    "- orders.user_id = user.id\n"
    "- user_role.user_id = user.id, user_role.role_id = role.id\n"
    "【问题】查生效的企业用户"
```

## 五、与其他技术对比

| 策略 | 适用 | 局限 |
|------|------|------|
| 全量 schema + 注释 | 简单库 | 字典/外键仍可能缺 |
| 显式映射表注入 | 字典/关联密集 | 需维护映射 |
| 向量检索召回相关表 | 大库 | 枚举值未必召回 |
| 工具预处理替换术语 | 术语固定 | 需规则/标注 |

实务常「向量检索相关表 + 显式映射表」组合，并对字典字段做值合法性校验。

## 六、常见误区

- 认为把表名给模型就够了，未给枚举含义，模型凭空猜 `status=1` 或乱写值。
- 外键关系缺失，模型不会 JOIN，结果漏数据或产生笛卡尔积。
- 把字典表当普通维表 JOIN 进 SELECT，反而污染结果列。
- 同名字段（如多表都有 `id`/`name`）不限定别名，产生歧义列。
- 字典新增枚举后未同步映射，旧 prompt 把新状态当未知处理。

## 八、面试题

- 为何字典表/关联表必须在上下文显式给出映射？
- 模型不知道 `status=1` 含义时会怎样？如何补救？
- 外键缺失会导致什么典型错误 SQL？
- 多表同名字段如何消歧？
- 字典枚举随业务新增，映射应如何演进？

## 九、演进与趋势

方向包括：自动从数据采样推断枚举分布并生成注释；用数据库 `COMMENT`/数据字典自动抽取映射；把外键元数据纳入向量检索的 schema 描述；结合执行校验回灌「字段值不合法」错误，引导模型使用正确枚举；以及把映射沉淀为可版本化、可回归的「业务语义层」。

## 十、小结

关系/字典表的正确映射是 NL2SQL 准确率的分水岭。把枚举含义与外键关系显式注入上下文，配合执行校验与值合法性校验，才能让模型把业务术语可靠翻译成 SQL 约束，并在业务演进中保持同步。
