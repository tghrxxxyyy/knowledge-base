# Text-to-SQL 评测

> 对应 Yu et al. 2018 (Spider) 评测协议、模型评测深入章节；执行准确率思想参考《Spider: A Large-Scale Human-Labeled Dataset for Text-to-SQL》。

## 一、背景与挑战

Text-to-SQL 的生成结果是 SQL 字符串，但「字符串相似」不等于「语义正确」。两句话法不同但结果一致的 SQL（如 `SELECT a FROM t` 与 `SELECT a FROM t WHERE 1=1`）应视为都对；反之字符串接近但差一个 JOIN 条件就可能返回完全不同结果。因此评测必须面向「执行结果」与「语义成分」，而非表面文本。

挑战：(1) 多表数据库需隔离测试环境；(2) 同一问题存在多种正确 SQL（等价重写）；(3) 需区分错误类型（语法错/模式错/执行错/逻辑错）以指导改进；(4) 不同数据库方言执行结果需一致对齐。

## 二、核心原理

- 执行准确率（Execution Accuracy, EX）：在黄金数据库上运行预测 SQL 与参考 SQL，比较结果表是否一致。这是最贴近真实可用性的指标。
- 成分匹配（Component Matching）：分别比较 SELECT 列、聚合函数、WHERE 条件、JOIN、GROUP BY 等子句是否命中，给出细粒度分数。
- 精确匹配（Exact Match）：字符串完全一致，过严，仅作参考。
- 错误分类：把失败样本按「语法错误/模式错误/执行错误/逻辑错误」打标，定位模型短板。

## 三、形式化与数学基础

对评测集 $\mathcal{D}=\{(q_i, \text{DB}_i, y_i)\}_{i=1}^{N}$，执行准确率定义为：

$$\text{EX} = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\!\left[\text{exec}(y_i, \text{DB}_i) = \text{exec}(\hat y_i, \text{DB}_i)\right]$$

其中 $\text{exec}(\cdot,\cdot)$ 返回查询结果表，$\mathbb{1}[\cdot]$ 为指示函数。成分匹配可对第 $k$ 类子句计算命中率 $P_k = \frac{1}{N}\sum_i \mathbb{1}[c_k(\hat y_i)=c_k(y_i)]$，再取宏平均作为诊断信号。

## 四、代码实现

用隔离库执行并比较结果（示意）：

```python
def execution_accuracy(pred_sql, gold_sql, db_path):
    gold = run_query(gold_sql, db_path)   # 返回排序去重后的结果行
    pred = run_query(pred_sql, db_path)
    return gold == pred                    # 多重集相等判断

# 批量统计
correct = sum(execution_accuracy(p, g, db)
              for p, g, db in zip(preds, golds, dbs))
EX = correct / len(preds)
```

注意：结果比较应忽略行顺序（排序后比较），并对 NULL 做一致处理；预测 SQL 须以只读方式运行于隔离影子库。

## 五、与其他技术对比

| 指标 | 衡量什么 | 优缺点 |
|------|----------|--------|
| 执行准确率 EX | 结果一致性 | 最可靠，但需可执行环境 |
| 成分匹配 | 子句粒度 | 细但忽略等价重写 |
| 精确匹配 | 字符串一致 | 过严，误伤等价 SQL |
| BLEU/编辑距离 | 文本相似 | 与正确性弱相关，不推荐 |

结论：以 EX 为主指标，辅以成分匹配做诊断；错误可按下表分类以便归因。

| 错误类型 | 含义 | 改进方向 |
|----------|------|----------|
| 语法错误 | SQL 不合法 | 语法约束/自修复 |
| 模式错误 | 表/字段选错 | Schema 检索 |
| 执行错误 | 运行报错 | 执行校验 |
| 逻辑错误 | 结果不等价 | 推理/自校验 |

## 六、常见误区

- 用 BLEU 或编辑距离评测 SQL——文本相似度与执行正确性相关性很弱。
- 直接在业务库跑预测 SQL——可能触发写操作或数据泄露，必须用隔离影子库并限制只读。
- 忽略等价 SQL，把 `WHERE 1=1` 之类判错。
- 仅看整体准确率，不按错误类型下钻，无法定位问题。

## 九、演进与趋势

评测从单轮 Spider 走向多轮（SPARC）、跨领域大规模（BIRD 引入数据库值）、真实数据仓库（Spider 2.0 面向复杂分析 SQL）。指标上从单纯 EX 扩展到「效率（查询代价）」「可解释性」「鲁棒性」多维评测；竞赛也引入人类偏好与错误分类报告，并把评测集本身作为防数据泄漏的重点。

## 十、小结

Text-to-SQL 必须以执行级评测（EX）为金标准，配合成分匹配做诊断，并在隔离只读环境中运行，按错误类型下钻归因，唯有如此才能反映生成 SQL 的真实可用性。
