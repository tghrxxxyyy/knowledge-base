# NL2SQL 权限与安全

> 对应大模型安全与对齐实践；权限思想参考数据库行级安全（Row-Level Security）与最小权限原则。

## 一、背景与挑战

把自然语言直接转成 SQL 并连库执行，带来独特的安全风险：用户可能用提问越权访问他人数据（「查一下竞品的客户名单」），模型也可能生成危险语句（误带 UPDATE/DELETE/DROP），或被注入攻击（问题里藏 `; DROP TABLE`）。一旦连上生产库，错误代价极高。

挑战：(1) 越权——不同用户角色可见数据范围不同；(2) 危险写操作——生成 SQL 只能只读；(3) 注入——自然语言可夹带恶意片段；(4) 审计——谁问了什么、生成了什么 SQL 必须可追溯；(5) 敏感字段脱敏——结果中的手机号、身份证需遮蔽。

## 二、核心原理

安全是分层防线，不能只靠 prompt 口头约束：

- 行级权限：在 SQL 自动注入过滤条件（如 `AND tenant_id = :current_user`），或在数据库侧用 RLS 策略强制。
- 只读强制：在数据库账号层授予 SELECT 权限，并在 SQL 解析层拒绝非 SELECT（DML/DDL 全拦）。
- 注入防护：参数化查询、白名单校验表/字段名、解析生成的 SQL 只允许出现 schema 内的标识符。
- 审计与脱敏：记录 (用户, 问题, SQL, 结果摘要)；对结果敏感列做脱敏后返回。

## 三、形式化与数学基础

设当前用户角色 $u$ 的可见行谓词为 $P_u(\text{row})$，则任何生成 SQL 的执行集合应被限制为：

$$\text{exec}(\hat y) \cap \{\text{row} \mid \neg P_u(\text{row})\} = \varnothing$$

即模型输出必须等价于在原始查询上叠加行级约束。设原始生成 SQL 为 $\hat y$，强制改写后执行：

$$\hat y_{\text{safe}} = \hat y \bowtie \sigma_{P_u}(\text{table})$$

其中 $\bowtie$ 表示注入 AND 谓词。危险操作集合 $\mathcal{D}=\{\text{UPDATE, DELETE, DROP, INSERT, TRUNCATE}\}$ 必须满足：

$$\text{stmt}(\hat y) \notin \mathcal{D}$$

## 四、代码实现

执行前做语句类型校验与权限谓词注入（示意）：

```python
import sqlparse

def guard(sql, user):
    stmt = sqlparse.parse(sql)[0].get_type()   # SELECT/UPDATE/...
    if stmt != "SELECT":
        raise PermissionError("仅允许只读查询")
    # 注入行级权限（或依赖数据库 RLS）
    return f"SELECT * FROM ({sql}) _t WHERE tenant_id = {user.tenant_id}"
```

## 五、与其他技术对比

| 防线 | 位置 | 强度 |
|------|------|------|
| prompt 约束 | 模型层 | 弱，可被绕过 |
| SQL 解析拦截 | 应用层 | 中 |
| 账号只读权限 | 数据库层 | 强 |
| 行级安全策略 | 数据库层 | 强且细 |

正确做法：数据库层强制为主，应用层解析为辅，prompt 仅为软提示。

## 六、常见误区

- 仅靠 prompt 说「不要生成危险语句」——模型可被诱导绕过，必须 DB 层强制。
- 忽略行级权限，所有用户看到全量数据，造成越权。
- 不在应用层解析就直接执行，无法拦截注入片段。
- 缺少审计日志，出事无法溯源。
- 脱敏只在展示层做，日志里仍存明文敏感信息。

## 九、演进与趋势

从静态白名单到「策略即代码」：用策略引擎（如 OPA）统一管控；结合数据分类自动脱敏；SQL 生成后做语义级影响分析（会不会触发行数过大、是否跨租户）；与可观测性结合，对异常查询模式实时告警；并把越权拦截率纳入安全评测。

## 十、小结

安全是 NL2SQL 上线红线。以数据库层只读权限与行级安全为硬底线，应用层做语句解析与注入防护，再叠加审计与脱敏，才能放心地把自然语言连到生产库。
