# 多轮对话问数

> 对应对话式数据分析（Conversational Text-to-SQL）；研究参考 SPARC、CoSQL 等多轮 Text-to-SQL 数据集。

## 一、背景与挑战

真实问数场景很少一句话解决：用户先问「上月销售额」，再追问「再按地区拆分」「去掉测试数据」「换成同比」。这类追问往往省略主语、复用上文的过滤与维度，是对话式 BI 的核心交互形态。

挑战：(1) 上下文依赖——追问中的代词、省略需绑定上一轮；(2) 增量改写——多是在上一 SQL 基础上改维度/过滤/排序，而非从头生成；(3) 指代消解——「它」「这个指标」指向前文；(4) 状态一致性——切分维度变了，聚合逻辑也要跟着变；(5) 跨轮累积——多轮叠加后 SQL 可能非常复杂。

## 二、核心原理

两条主流路线：

- 增量改写（推荐）：维护「上一轮 SQL + 关键字段/维度/过滤」作为状态，把追问转化为对上一 SQL 的结构化补丁（加 GROUP BY 维度、改 WHERE、换聚合），再交给模型生成新 SQL。
- 全量重生成：把「对话历史 + 上一结果摘要 + 当前追问」拼成完整 prompt，让模型一次生成新 SQL。实现简单，但长对话易丢信息、成本高。

工程上通常混合：用状态机记录当前查询的「表/维度/度量/过滤」，追问先尝试结构化改写，失败再全量重生成。

## 三、形式化与数学基础

设第 $t$ 轮对话状态为 $S_t = (T_t, D_t, M_t, F_t)$，分别表示表集合、维度、度量、过滤条件。追问 $u_t$ 产生状态转移：

$$S_t = \delta(S_{t-1}, u_t)$$

目标是使生成的 SQL $\hat y_t$ 满足 $\text{exec}(\hat y_t) = \text{exec}(y^*_t)$。增量改写可视为在 AST 层面对上一 SQL 做局部编辑 $\Delta$：

$$\hat y_t = \text{apply}(\hat y_{t-1}, \Delta(u_t))$$

其中 $\Delta$ 可能新增维度（`GROUP BY region`）、追加过滤（`AND is_test=0`）或替换度量（`SUM`→`AVG`）。

## 四、代码实现

维护对话状态并增量改写的简化实现：

```python
state = {"sql": None, "dims": [], "filters": [], "metrics": []}

def ask(question, follow_up=None):
    if follow_up and state["sql"]:
        # 把上一 SQL 与追问一起给模型做增量改写
        prompt = (f"上一SQL: {state['sql']}\n"
                  f"当前维度: {state['dims']}\n"
                  f"追问: {follow_up}\n请返回新SQL")
    else:
        prompt = f"问题: {question}\n{schema_context}"
    sql = llm.generate(prompt)
    state["sql"] = sql
    return safe_execute(sql, shadow_db)
```

## 五、与其他技术对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 每轮从头生成 | 实现简单 | 长对话丢上下文、成本高 |
| 增量改写 | 准确、省 token | 需维护状态机 |
| 历史结果摘要 | 信息紧凑 | 摘要可能丢细节 |
| 向量检索历史轮 | 长对话友好 | 实现复杂 |

## 六、常见误区

- 每轮都把整段对话历史塞进去，超长且噪声大，反而改错维度。
- 不保存上一 SQL，追问无锚点，模型凭记忆重建易错。
- 忽略「去掉测试数据」这类负向过滤，只做加法不做减法。
- 维度切换时未同步聚合函数（如从「总额」误变成「计数」）。
- 把上一轮的结果数字当作事实再次查询，产生矛盾口径。

## 九、演进与趋势

从拼接历史到「查询状态图」：用 AST 差分做精准增量；引入工具调用显式更新维度/过滤；结合执行结果反馈（用户说「不对，要华东」即时修正）；长对话用向量检索召回相关历史轮次而非全量保留；以及把多轮成功率纳入评测驱动开发的回归指标。

## 十、小结

多轮状态管理是问数产品体验关键。维护「上一 SQL + 维度/过滤」状态、优先增量改写、辅以全量重生成兜底，才能在长对话中保持准确与低成本。
