# 协作失败模式与治理

> 对应 Cemri et al., *Why Do Multi-Agent LLM Systems Fail?*, 2025（失败模式分类）；Du et al., ICML 2024。

## 一、背景与挑战

多智能体系统的失败往往不是单个模型能力不足，而是协作机制缺陷：任务规格丢失、角色越权、验证缺位。
把失败归类为可观测模式，才能针对性加护栏而不是盲目加轮数或加角色。

## 二、核心原理

- 规格类失败：需求在角色间传递时被简化或误解，缺少可判定的验收条件。
- 协调类失败：重复劳动、互相等待、越权覆盖他人产出、上下文截断丢失早期约束。
- 验证类失败：没有独立验证者，或验证者与生成者共享同一误差来源，导致集体自信错误。

## 三、数学形式

若每个交接环节保真率为 $q$，$k$ 级链式流水线端到端保真率为 $q^k$，随链长指数衰减。

加入每级验收（检出率 $\alpha$）后近似为 $\prod_{i}\big(q+(1-q)\alpha\big)$，说明质量门比增加角色更能抵抗衰减。

## 四、代码实现

```python
GATES = {"spec": lambda w: has_acceptance_criteria(w),
         "code": lambda w: tests_pass(w),
         "review": lambda w: no_blocking_comment(w)}

def guarded_pipeline(stages, task):
    art = task
    for name, stage in stages:
        art = stage(art)
        if not GATES[name](art):              # 质量门拦截，不让缺陷下传
            art = stage(art, feedback=GATES[name].__doc__)
    return art
```

## 五、与其他对比

- 与单体智能体：单体没有交接损耗但缺乏分工与互检；多智能体收益需扣除协调成本。
- 与软件工程实践：CI 门禁、代码评审、需求验收标准在此几乎可直接移植。

## 六、常见误区

- 出问题就加角色或加轮数，实际是规格与验证缺位，越加越乱。
- 让同一模型既生成又验证同一工件，误差相关导致验证形同虚设。
- 不记录每级工件与决策依据，事后无法定位失败发生在哪一交接点。

## 八、面试题

- 多智能体系统最常见的根因是什么？答：规格不可判定与验证缺位，其次是角色越权与上下文丢失，而非单体模型能力。
- 如何定位失败环节？答：为每级交接记录输入输出工件与质量门结果，做逐级保真率归因。

## 九、演进

无护栏自由协作 → 加日志可观测 → 每级质量门 → 独立验证者与异构裁判 → 失败模式驱动的机制迭代。

## 十、小结

多智能体的可靠性来自机制设计：可判定规格、独立验证、逐级质量门与完整审计。
