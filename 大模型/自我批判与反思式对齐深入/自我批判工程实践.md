# 自我批判工程实践

> 对应 Yao et al. 2022（ReAct）、Bai et al. 2022（Constitutional AI）与 vLLM 高吞吐推理服务实践。

## 一、背景与挑战

自我批判在论文里只需一句「生成后让模型再批判一遍」，但落地时要面对延迟、成本与质量的三角约束：每增加一轮批判，token 消耗与首字延迟大致成倍上升；而一刀切地对所有请求做多轮批判，会把 P99 延迟推高到不可接受。同时还有三个工程难题：批判输出难以解析（模型输出的是散文而非结构化条目）、批判效果难以度量（不知道这轮批判是否真的带来改进）、以及失败模式难以兜底（批判后反而变差、或陷入无限修订）。因此工程实践的核心不是「如何写批判提示」，而是「如何按风险分级、如何控制成本、如何验证收益」。

## 二、核心原理

落地自我批判有五个关键设计：

1. 风险分级：按场景与请求内容判定风险等级，高风险（代码执行、医疗、法律、金融、对外发布内容）启用 2–3 轮批判，中风险 1 轮，低风险（闲聊、简单问答）跳过。分级可由规则、分类器或模型自身打标完成。
2. 轮数与预算控制：设置硬性轮数上限与 token 预算；用早停机制（批判判定无问题即终止）；对长输出采用分段批判而非整篇重来。
3. 结构化批判：要求模型输出固定格式（如 JSON 的条目数组，每条含问题、位置、建议），便于程序解析、统计与展示；解析失败要有降级策略。
4. 验证与回滚：用独立验证器（规则、测试、检索、打分模型）判断修订是否真的更好，未改善则回滚到上一版，防止越改越差。
5. 缓存与异步：对同一内容或相似请求的批判结果做缓存复用；非实时场景走异步批判流水线，把结果用于事后修订或数据回流。

生产系统还应把批判事件全量留痕（触发等级、轮数、改进幅度、耗时），作为调优分级策略与证明有效性的依据。

## 三、形式化与数学基础

设单轮生成成本为 $c_{\text{gen}}$、单轮批判成本为 $c_{\text{crit}}$、轮数为 $k$，则总推理成本近似：

$$ \text{Cost} = c_{\text{gen}} + k \cdot (c_{\text{crit}} + c_{\text{gen}}), \qquad \text{Latency} \approx (1+k) \cdot t_{\text{gen}} + k \cdot t_{\text{crit}} $$

按风险 $r$ 决定轮数 $k(r)$ 后，系统的期望成本为：

$$ \mathbb{E}[\text{Cost}] = \sum_r P(r) \cdot \big(c_{\text{gen}} + k(r)(c_{\text{crit}} + c_{\text{gen}})\big) $$

收益侧，设风险等级 $r$ 下漏放有害内容的代价为 $\alpha_r$，批判把漏放率从 $p_r$ 降至 $p_r'$，则净收益：

$$ \text{Benefit}(r) = \alpha_r (p_r - p_r') - \big(c_{\text{gen}} + k(c_{\text{crit}} + c_{\text{gen}})\big) $$

最优策略是只对 $\text{Benefit} > 0$ 的等级启用批判——这正是风险分级的理论依据。实践中 $\alpha_r$ 与 $p_r$ 难以精确估计，可用离线样本估计改进率 $\Delta_r = p_r - p_r'$，再结合业务容忍度设定 $k(r)$，并随数据积累持续校准。

## 四、代码实现

```python
# 风险自适应批判：分级 + 早停 + 验证回滚 + 留痕
import json
import time

CRITIQUE_SCHEMA = [{"issue": str, "span": str, "suggestion": str}]


def refine_by_risk(model, x, risk, verifier=None, eps=0.02):
    rounds = {"high": 3, "mid": 1, "low": 0}.get(risk, 0)
    y = model.generate(x)
    if rounds == 0:
        return y, {"rounds": 0}

    t0, used = time.time(), 0
    for _ in range(rounds):
        raw = model.generate(
            "按 JSON 数组格式指出问题，每项含 issue/span/suggestion：\n" + y
        )
        try:
            items = json.loads(extract_json(raw))
        except ValueError:
            break                      # 解析失败即降级停止，不强行修订

        if not items:
            break                      # 无问题，早停

        y_new = apply_suggestions(y, items)
        if verifier is not None and verifier(x, y_new) <= verifier(x, y) + eps:
            break                      # 未改善，回滚到上一版
        y = y_new
        used += 1

    log_audit("self_critique", {"risk": risk, "rounds": used,
                                "latency_ms": int((time.time() - t0) * 1000)})
    return y, {"rounds": used}


def apply_suggestions(text, items):
    # 按 span 定位并替换，无法定位的建议丢弃而非误改
    for it in items:
        if it.get("span") in text and it.get("suggestion"):
            text = text.replace(it["span"], it["suggestion"], 1)
    return text
```

## 五、与其他技术对比

- 自我批判 vs 全程 RLHF：批判在推理时更贵（多轮生成）但训练成本极低、可热更；RLHF 训练贵但推理零额外开销。
- 同步批判 vs 异步批判：同步保障当次输出质量但增加延迟；异步不影响体验，适合内容审核与数据回流。
- 全文批判 vs 分段批判：全文语义连贯但成本高；分段并行更快、可控，适合长文档。
- 自批判 vs 外部验证器：自批判覆盖语义与风格，验证器提供客观信号，二者应组合使用。

## 六、常见误区

- 「所有请求同等批判」：低风险请求也被多轮批判，延迟与成本无谓上升。
- 「批判提示无结构」：输出是散文导致无法解析、无法统计，也无法做程序化修订。
- 「只看质量不看收益」：不统计改进率与代价，无法判断某场景是否值得批判。
- 「无回滚机制」：修订后变差也照单全收，反而降低线上质量。

## 七、与开源书·权威来源对应

- Yao et al. 2022（ReAct）：反思驱动动作选择，是批判机制在 Agent 中的典型用法。
- Bai et al. 2022（Constitutional AI）：原则式批判与修订，提供可审计的批判依据。
- vLLM / 高吞吐推理引擎：通过连续批处理与前缀缓存降低多轮批判的边际成本（能力以官方最新文档为准）。
- Zheng et al. 2023（MT-Bench）：提醒用作裁判的模型存在位置与冗长偏好，批判设计需做顺序随机化等校准。

## 九、演进与趋势

自我批判的工程化正走向「自适应、可观测、可复用」：按实时风险信号动态调整轮数与模型规格；用前缀缓存与并行采样压缩多轮开销；把批判过程与结果纳入可观测体系（改进率、回滚率、耗时分布）；并把高频有效的批判—修订对沉淀为偏好数据或蒸馏进小模型，逐步把推理期的成本转移到训练期，形成成本更优的长期方案。

## 十、小结

自我批判落地的关键不在提示词技巧，而在风险分级、预算控制、结构化输出与验证回滚。只有把批判做成可度量、可观测、可关闭的工程模块，才能在生产中稳定产生正向收益。
