# LLMOps 与模型生命周期管理

> 本文梳理大模型从"实验"到"生产"的工程化体系：数据管理、训练/微调流水线、评测、部署、监控、成本治理与版本管理。LLMOps 是 MLOps 在 LLM 时代的延伸，但更强调 prompt/上下文/检索的可迭代性与生成质量的可观测。

## 1. 什么是 LLMOps

LLMOps = 大模型应用的运维工程，覆盖：

- **数据**：训练/微调数据、评测集、知识库。
- **模型**：基座选择、微调、蒸馏、量化。
- **应用层**：Prompt、检索（RAG）、Agent 编排。
- **生产**：部署、推理服务、监控、成本控制、安全。

与传统 MLOps 不同，LLM 应用常"不训练也能上线"（靠 prompt+RAG），因此 prompt 与上下文成为一等公民的可迭代资产。

## 2. 数据管理

### 2.1 训练/微调数据

- **来源**：业务日志、人工标注、合成数据（需防污染与失真）。
- **治理**：去重、去毒、质量打分、版本化（数据集即资产）。
- **格式**：指令—回答对（SFT）、偏好对（RLHF/DPO）。

### 2.2 评测集

- **能力维度**：知识、推理、指令遵循、安全、领域准确。
- **构建**：人工标注 + 自动生成 + 对抗样本。
- **回归**：每次模型/prompt 改动都跑评测集，防回退。

### 2.3 知识库（RAG）

- 文档采集、清洗、切分、向量化、版本追踪。
- 知识更新需重算 embedding 并刷新索引。

## 3. 训练与微调流水线

### 3.1 微调方式

- **SFT（监督微调）**：用指令对调整模型行为风格。
- **RLHF / DPO**：对齐人类偏好，DPO 实现更简单。
- **LoRA / QLoRA**：低秩适配，低成本微调，适配多任务。
- **蒸馏**：大模型教小模型，降推理成本。

### 3.2 流水线要素

- 可复现：固定随机种子、数据版本、超参记录。
- 可追踪：实验管理（loss 曲线、评测指标）。
- 可回滚：模型版本 registry。

## 4. 评测体系

### 4.1 自动指标

- **参考式**：BLEU/ROUGE（文本重叠，弱语义）、BERTScore。
- **模型打分**：用强模型做裁判（LLM-as-Judge），需防偏置。
- **任务式**：代码执行通过率、工具调用正确率。

### 4.2 人工评测

- 抽样人工打分（相关性、事实性、安全性）。
- 红队测试：主动攻击找漏洞（越狱、泄露、偏见）。

### 4.3 持续评测

- 把评测集接入 CI，prompt/模型变动自动回归。

## 5. 部署与推理服务

### 5.1 服务形态

- **在线推理**：低延迟 API（OpenAI 兼容接口风格）。
- **批量推理**：离线大批量处理。
- **边缘/私有**：本地化部署满足合规。

### 5.2 推理优化

- **KV Cache**：缓存注意力键值，降重复计算。
- **批处理（continuous batching）**：合并多请求提升吞吐。
- **量化**：INT8/INT4 降显存与提速，权衡精度。
- **投机解码 / 并行**：提升生成速度。

### 5.3 服务组件

- 网关层：限流、鉴权、路由（多模型/多版本）。
- 编排层：prompt 模板、RAG 检索、Agent 循环。
- 可观测：token 用量、延迟、错误、质量采样。

## 6. 监控与质量可观测

- **技术指标**：QPS、P99 延迟、错误率、GPU 利用率。
- **质量指标**：幻觉率（抽样评估）、拒答率、用户反馈（👍/👎）。
- **成本指标**：token 消耗、单位请求成本。
- **漂移检测**：输入分布变化、知识时效性。

## 7. 成本治理

- **模型分层**：简单任务用小/便宜模型，复杂任务才用大模型。
- **缓存**：相同/相似 query 命中缓存（语义缓存）。
- **压缩上下文**：裁剪无关历史、摘要长对话。
- **预算与告警**：设每日 token 预算与异常告警。

## 8. 版本与配置管理

- **Prompt 版本**：prompt 作为代码，Git 管理 + 灰度。
- **模型版本**：registry 管理基座/微调版本，支持回滚。
- **配置即代码**：检索参数、温度、top_p 等纳入版本。

## 9. 安全与合规

- **数据合规**：训练/推理数据脱敏，满足法规。
- **内容安全**：输出过滤、拒答违规请求。
- **权限**：Agent 工具最小权限，敏感动作人工审核。
- **审计**：留痕请求与决策链路，便于追溯。

## 10. 常见踩坑

1. **评测集不更新**：线上问题无法在评测暴露，需持续补充。
2. **prompt 无版本**：改动凭感觉，回退困难；应 Git 管理+灰度。
3. **只盯准确率忽视成本**：大模型滥用拖垮预算；需分层+缓存。
4. **幻觉无监控**：上线后无人抽样质量，问题滞后发现。
5. **知识库陈旧**：文档更新未刷新向量，答非所问；需同步管线。
6. **过度依赖自动指标**：BLEU 高但体验差，需人工+模型裁判结合。

## 11. 工具生态映射

- 实验/训练：训练框架、实验追踪（如 MLflow 类思路）。
- 评测：评测集 + 裁判模型 + 红队。
- 服务：推理框架 + 网关。
- 可观测：指标/日志/链路（见可观测性章节）。

## 12. 小结

LLMOps 的核心是把"模型能力"转化为"稳定、可控、可观测、低成本的生产服务"。它不只是训练，更大量的工作在前端的 prompt/上下文管理与后端的监控/成本治理。建立评测闭环与版本管理，是 LLM 应用能否长期健康运行的分水岭。
