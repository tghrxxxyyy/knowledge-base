# 多后端推理与加速

> 对应 Gao et al. 2021 lm-evaluation-harness 多后端抽象与 Kwon et al. 2023 vLLM（PagedAttention）；参考 HuggingFace Transformers。

## 一、背景与挑战

大规模评测（千级样本 × 多任务 × 多 shot）在单卡上推理耗时巨大，往往以小时甚至天计，成为研发迭代的瓶颈。同时不同团队偏好不同推理栈：有的用 HuggingFace `transformers` 的 `generate`，有的用 vLLM 的高吞吐服务，有的用本地 `llama.cpp`。若评测框架绑定单一后端，既无法利用更高效的服务，也难以保证「评测环境 = 线上环境」的一致性。harness 通过抽象 `generate`/`loglikelihood` 接口对接多后端，实现批量、连续批解码与加速，同时把「切换后端」变成配置项而非重写。

挑战在于：不同后端默认采样参数、分词、padding 行为不同，可能悄悄改变分数，需在后端切换时严格对齐配置。

## 二、核心原理

harness 把模型推理抽象为统一接口：

1. `loglikelihood`：给定上下文与候选，返回对数似然（多选/perplexity 路线）。
2. `generate_until`：给定提示，自回归生成至停止条件（生成式问答路线）。
3. `loglikelihood_rolling`：长文本困惑度滚动计算。

后端（vLLM、HF、本地）各自实现这些接口。vLLM 凭 PagedAttention 的 KV cache 分页管理与连续批处理（continuous batching），在批量评测中显著提升吞吐；HF 胜在通用与易调试；本地引擎胜在轻量。harness 通过批处理与请求合并把 N 个样本组织成高效批。

实践中还应关注后端一致性：先在锚定样本（anchor set）上验证各后端输出对齐，再用于正式评测；否则引擎差异会污染模型对比。投机解码、前缀缓存等加速手段若改变采样行为，必须记入实验指纹。批大小 $B$ 的选择需兼顾吞吐与显存，过大反而因 OOM 或排队导致实际吞吐下降，应通过扫描确定最优 $B$；对生成式任务，停止条件（max_tokens、eos）也须跨后端统一，否则长度差异会显著影响指标。

补充实践要点：
- 评测前用锚定样本校准后端，分离引擎噪声与模型差异。
- 记录每次运行的完整采样参数，纳入实验指纹。
- 对长文本任务关注上下文截断行为是否跨后端一致。

## 三、形式化与数学基础（含 LaTeX）

吞吐近似为批大小与生成长度之积除以总时长：

$$
\text{throughput}\approx \frac{B\cdot L_{\text{gen}}}{T}
$$

其中 $B$ 为批大小，$L_{\text{gen}}$ 为平均生成长度，$T$ 为总耗时。连续批处理下有效批大小随时间变化，平均利用率：

$$
\bar B=\frac{1}{T}\int_0^T B(t)\,dt
$$

vLLM 的 PagedAttention 把 KV cache 显存碎片导致的闲置降至最低，使 $\bar B$ 接近硬件上限，从而吞吐优于静态批处理。注意吞吐提升不改变单样本分布，但采样参数偏差会改变分数。

## 四、代码实现

```python
# 选择后端并批量评测（结构示意）
def run_eval(model, tasks, backend="vllm"):
    engine = load_backend(backend)        # vllm / hf / local
    engine.set_sampling(temperature=0.0, top_p=1.0)   # 与论文对齐
    results = []
    for task in tasks:
        for batch in chunk(task.samples, B):
            results += engine.generate_until(batch)
    return results
```

## 五、与其他技术对比

- vLLM：PagedAttention + 连续批处理，吞吐最高，适合千级样本评测与线上一致。
- HF transformers：通用、易调试，但默认吞吐低于 vLLM，适合小规模/研究。
- 本地引擎（llama.cpp）：低资源、量化友好，适合端侧模型评测。
- 取舍：性能 vs 一致性 vs 易用，需按场景选后端并锁定参数。

## 六、常见误区

- 「后端切换不影响分数」：采样参数、分词、padding 差异会导致分数漂移，必须对齐。
- 「只追求吞吐忽略对齐」：加速若以偏差为代价，评测结论失真。
- 「temperature 非零跑基准」：多数基准要求贪心（temp=0），否则方差大不可比。
- 「忽略 KV cache 复用边界」：跨样本共享需谨慎，避免污染。

## 九、演进与趋势

评测与服务共用同一推理栈（同后端、同参数）以保证一致性；投机解码、前缀缓存进一步加速；分布式评测把任务切分到多卡/多机，缩短迭代周期。

落地要点：
- 加速手段若改变采样行为，必须同步记录进实验指纹，否则丧失可比性。
- 连续批处理的高吞吐建立在稳定请求流上，突发流量需预留队列，避免排队污染 TTFT 度量。
- 前缀缓存对共享系统提示/少样本模板收益显著，应在成本归因中正确折减。
未来方向是按任务优先级动态调度后端资源，以评测结果反推服务侧瓶颈，形成「测—服」一体化的性能闭环。

## 十、小结

多后端推理与加速通过统一接口对接 vLLM/HF/本地引擎，用连续批处理与 PagedAttention 提升评测吞吐，并在成本与保真间平衡。其权威基础是 Gao 2021 与 Kwon 2023，落地关键是切换后端时严格对齐采样参数以保证分数可比。
