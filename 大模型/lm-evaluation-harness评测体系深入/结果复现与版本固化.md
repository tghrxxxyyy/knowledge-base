# 结果复现与版本固化

> 对应 Gao et al. 2021 lm-evaluation-harness（EleutherAI）复现实践与官方版本/配置固化建议。

## 一、背景与挑战

同一模型在不同时间、不同环境跑出不同分数，是评测领域广受诟病的问题。原因五花八门：harness 版本升级改了模板、模型权重文件被替换（同一名字不同哈希）、采样参数或随机数种子未固定、依赖库（tokenizers、transformers）版本漂移、后端默认行为变化。这些都会让「我的复现比原论文低 2 个点」变得无法解释，也削弱结论的可信度与可质疑性。结果复现的核心，是把一次评测变成「可重跑、可审计、可比对」的实验指纹。

挑战在于：指纹需覆盖所有影响分数的变量，且要在易用（不增加太多负担）与完备（不遗漏隐藏依赖）间平衡。

## 二、核心原理

可复现评测需固化以下维度并一并记录：

1. harness 版本：git commit 或发布版本号，模板/聚合逻辑依赖它。
2. 模型标识：不仅记模型名，更记权重哈希（或具体 checkpoint 路径/commit）。
3. 配置哈希：任务名、num_fewshot、模板版本、采样参数（temp/top_p/top_k/seed）。
4. 依赖环境：transformers、tokenizers、vLLM 等库的版本（可由环境锁文件得出）。
5. 随机数种子：few-shot 抽样与采样若随机，必须固定。

把上述拼成实验指纹 $F$，与分数一同存档，使任何第三方都能在等价环境下重跑并核对。

## 三、形式化与数学基础（含 LaTeX）

实验指纹定义为各影响因子的级联哈希：

$$
F=H\big(\text{harness}\Vert \text{model\_hash}\Vert \text{config}\Vert \text{seed}\Vert \text{deps}\big)
$$

其中 $H$ 为密码学哈希（如 SHA-256），$\Vert$ 表示拼接。两条评测记录可比当且仅当：

$$
F_1 = F_2 \implies \text{分数差异仅来自偶然/实现}
$$

反之若 $F_1\neq F_2$，差异可能来自任一未对齐因子，需逐项 diff。对分数本身也可附加置信区间：

$$
\text{score}\pm z\cdot\text{stderr}
$$

使「差异是否显著」有统计判据。

## 四、代码实现

```python
# 生成实验指纹（结构示意）
import hashlib, json

def fingerprint(cfg):
    # cfg: {harness, model_hash, config, seed, deps}
    payload = json.dumps(cfg, sort_keys=True).encode()
    return hashlib.sha256(payload).hexdigest()[:16]

# 与分数一并持久化
record = {"fingerprint": fingerprint(cfg), "scores": results, "config": cfg}
save(record)                       # 归档供第三方重跑核对
```

## 五、与其他技术对比

- 口头描述（「用 vLLM 跑的」）：不可审计、不可质疑、不可复现。
- 指纹化：把隐式依赖显式化，使结果可审计、可质疑、可复现。
- 与 CI 结合：每次模型/任务变更自动跑带指纹的评测，历史分数可逐版对比。

## 六、常见误区

- 「只记录模型名不记录权重哈希」：同名权重可能被覆盖/微调，指纹失真。
- 「忽略依赖库版本」：tokenizers 升级可能改变切分，分数漂移。
- 「忘记固定 seed」：few-shot 抽样随机导致不可重跑。
- 「只存总分不存原始样本结果」：无法做后续细粒度 diff 与错误分析。

## 九、演进与趋势

评测结果上链与可验证缓存成为趋势：分数附带可验证指纹，第三方不必重跑即可校验；环境用容器/锁定文件固化；「评测即实验」的规范使论文结论更易被社区复核。

落地建议：把指纹生成做成评测命令的默认输出，而非事后补记；将原始样本级结果一并归档，便于后续做细粒度 diff 与错误分析。只有把复现当成工程纪律，评测结论才经得起推敲。指纹应随论文/报告一并发布，而非仅留存内部。

## 十、小结

结果复现与版本固化通过把 harness 版本、权重哈希、配置、种子与依赖编码为实验指纹，使评测从「一次性实验」升级为「可审计工程」。其权威基础是 Gao 2021 复现实践，落地关键是广度（覆盖所有隐式依赖）与归档（指纹+原始结果+配置一并保存）。
