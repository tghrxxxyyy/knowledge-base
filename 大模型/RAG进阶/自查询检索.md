# 自查询检索 Self-Query

> 对应 LlamaIndex / LangChain「Self-Query Retriever」；结构化元数据过滤 + 语义检索。

## 一、背景与挑战

用户问题常隐含过滤条件：「2024 年的财报」「价格低于 100 的型号」「研发部写的文档」。纯语义检索只看文本相似度，会忽略这些**结构化约束**，返回一堆语义相近但不满足条件的文档。

若知识库带着丰富元数据(时间、类型、作者、部门、标签)，就应当让检索「既按语义找、又按条件筛」——这就是自查询检索(Self-Query)。它把自然语言问题翻译成「语义查询 + 结构化过滤器」两部分。

## 二、核心原理

用 LLM 把自然语言问题分解为两部分：

1. **语义查询(semantic part)**：需要向量检索的核心意图。
2. **结构化过滤器(metadata filter)**：可映射到元数据 schema 的比较表达式(=、>、<、in、contains…)。

执行顺序：先按过滤器在元数据上做硬筛选缩小候选，再做语义检索，二者取交/并集。这样既保证条件满足，又保留语义召回。

```
问题 → LLM 解析 → {语义查询, 过滤器} → 元数据过滤 → 向量检索 → 结果
```

关键是给 LLM 一份**清晰的元数据 schema**(字段名、类型、含义)，否则解析出的字段对不上索引。

## 三、形式化与数学基础

设元数据过滤器为谓词 $F(m)$，语义相关集合为 $R(q)$。自查询检索结果为：

$$\text{result} = \{d : F(d.\text{meta}) \text{ 且 } d \in \mathrm{TopK}(R(q)) \}$$

等价于先投影 $\tilde D=\{d\mid F(d.\text{meta})\}$ 再在子集上做向量检索，显著缩小搜索空间、提升精度。过滤器可组合为合取/析取树：$F = F_1 \land F_2$ 或 $F_1 \lor F_2$，覆盖复杂条件。

## 四、代码实现

```python
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain_community.vectorstores import Chroma

metadata_field_info = [
    {"name": "year", "type": "integer", "description": "发布年份"},
    {"name": "dept", "type": "string", "description": "部门"},
]
retriever = SelfQueryRetriever.from_llm(
    llm, vectordb, "文档库", metadata_field_info, verbose=True
)
docs = retriever.invoke("研发部 2024 年关于成本的文档")
```

## 五、与其他技术对比

| 检索方式 | 元数据 | 语义 | 适用 |
|----------|--------|------|------|
| 纯向量 | 否 | 是 | 无结构条件 |
| 纯过滤 | 是 | 否 | 强条件 |
| 自查询 | 是 | 是 | 条件+语义 |

## 六、常见误区

- 元数据 schema 设计不清，LLM 解析出的字段名对不上。
- 不加校验直接执行 LLM 生成的过滤器，易出错或注入。
- 过滤器过严导致候选为空，应设兜底(放宽/忽略过滤)。
- 把过滤也丢给语义检索，精度与可控性都差。
- 元数据本身缺失/脏，过滤器无从生效。

## 九、演进与趋势

自查询与「自然语言转查询(Text-to-SQL/Search)」融合，从向量库扩展到数据库、知识图谱的统一路由。过滤器生成正走向「带 schema 校验的结构化输出」(如 function calling / JSON schema)，降低解析错误与注入风险，并支持自动兜底策略。

## 十、小结

自查询检索把自然语言拆为「语义查询 + 结构化过滤器」，先按元数据硬筛再语义检索，兼顾条件满足与语义召回。清晰的元数据 schema 与输出校验是其稳定生效的关键，过滤器落空时需有兜底逻辑。
