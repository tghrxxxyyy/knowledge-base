# 检索后处理

> 对应 LlamaIndex「Postprocessing」与 RAG 工程最佳实践；检索召回的片段需后处理再进上下文。

## 一、背景与挑战

向量检索(及重排)返回 Top-k 片段后，直接拼进 prompt 往往并不理想：片段间可能重复、含低相关噪声、或超出上下文预算。检索后处理(Post-retrieval Processing)是在「拿到候选」与「喂给 LLM」之间的必要清洗与组织环节，决定最终进入上下文的质量。

典型问题：

- 多路/多跳检索结果重复冗余。
- 重排后仍夹带低相关片段稀释注意力。
- 片段过长超出上下文窗口或抬高成本。
- 缺少引用标记，难以溯源与可观测。
- 最优相关片段排在上下文两端，被长上下文模型「中间遗忘」。

## 二、核心原理

后处理管线通常是串联的若干变换：

```
候选集 → 去重(dedup) → 相关性过滤(阈值) → 压缩/摘要 → 排序与引用标注 → 拼上下文
```

- **去重**：同文档多片段或跨路重复合并。
- **过滤**：按重排分数/相关性阈值剔除边缘片段。
- **压缩**：用 LLM 抽取与问题相关的句子(Contextual Compression)。
- **引用标注**：为每段绑定来源，便于生成时引用与可追溯。
- **重排序**：`LongContextReorder` 把最相关片段放上下文中部，缓解中间遗忘。

LlamaIndex 把这些都抽象为 Node Postprocessor，可组合串联。

## 三、形式化与数学基础

设重排后候选集 $C=\{(d_i, s_i)\}_{i=1}^{k}$，过滤保留 $s_i\ge \tau$ 者；去重用相似度 $\mathrm{sim}(d_i,d_j)>\delta$ 合并。压缩可视为抽取映射：

$$c'_i = \mathrm{Compress}(d_i, q)$$

目标是最小化进入上下文的 token 数 $T=\sum_i |c'_i|$，同时最大化保留的相关信息量 $I(c'_i; q)$，即：

$$\max\ I - \lambda T$$

其中 $\lambda$ 为成本-信息权衡系数，体现「省 token 但以不丢关键信息为界」。

## 四、代码实现

```python
from llama_index.core.postprocessor import SimilarityPostprocessor, LongContextReorder

# 过滤低分 + 长上下文重排序(把最相关放中间)
postprocessors = [
    SimilarityPostprocessor(similarity_cutoff=0.75),
    LongContextReorder(),
]
nodes = retriever.retrieve(query)
for p in postprocessors:
    nodes = p.postprocess_nodes(nodes)
```

`ContextualCompressionRetriever` 可把压缩器(如 LLMChainExtractor)直接挂在检索器后，自动抽取相关句子。

## 五、与其他技术对比

| 后处理手段 | 解决 | 代价 |
|------------|------|------|
| 去重 | 冗余 | 低 |
| 阈值过滤 | 噪声 | 可能误删 |
| 压缩 | 超长 | 1 次 LLM |
| 重排序 | 顺序 | 低 |

## 六、常见误区

- 阈值定过高误删正确但表达不同的片段。
- 压缩过度丢失关键证据，导致生成无据。
- 忽略引用标注，使答案不可溯源、难调试。
- 把后处理当万能，掩盖检索召回这一根本问题。
- 未处理「中间遗忘」，最相关片段被排在长上下文两端。

## 九、演进与趋势

后处理正与重排融合为「可学习、端到端可微」的上下文选择器；也有工作让 LLM 在生成前先「决定用哪些片段、丢弃哪些」，把后处理变成生成过程的一部分。`LongContextReorder` 这类针对长上下文模型弱点的重排策略会越来越重要。

## 十、小结

检索后处理是「候选 → 上下文」的精炼关卡：去重、过滤、压缩、标注引用、顺序重排五步提升最终上下文质量。它是低成本高收益环节，但前提是检索召回本身已达标，否则后处理无米之炊。
