# 抢占式调度

> 对应 Agrawal et al., *Sarathi-Serve: Quasi-Preemptive Scheduling*, 2023；与 优先级调度深入 / 服务框架深入 衔接。

## 一、背景与挑战

高优先请求到达时，低优先长请求正在占用 GPU，需抢占以免 SLA 违约。

## 二、核心原理

以 chunk（decode 步组）为单位准抢占：保存低优先 KV，插入高优先请求，结束后再恢复，降低抢占粒度。

## 三、数学形式

抢占额外开销 $\Delta = \text{save}(KV)+\text{restore}(KV)$；准抢占使 $\Delta\ll$ 整请求重跑。

## 四、代码实现

```python
if high_prio_arrived and can_preempt(cur):
    save_kv(cur); suspend(cur)
    run(high); restore(cur)
```

## 五、与其他对比

- 与 分页注意力PagedAttention（KV 易保存/恢复）依赖。
- 与 优先级调度总览（抢占是手段）衔接。

## 六、常见误区

- 抢占粒度太粗（整请求）开销大。
- 频繁抢占致吞吐下降、上下文切换多。

## 八、面试题

- 为何要准抢占而非重跑？答：保存/恢复 KV 比重算整请求便宜得多，降级延迟可控。

## 九、演进

无抢占 → 整请求抢占 → chunk 级准抢占。

## 十、小结

抢占式调度保障高优先 SLA，依赖细粒度 KV 保存与恢复。
