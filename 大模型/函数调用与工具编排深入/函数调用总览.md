# 函数调用与工具编排总览

> 对应 Schick et al., *Toolformer*, NeurIPS 2023；Yao et al., *ReAct*, ICLR 2023；Qin et al., *ToolLLM*, ICLR 2024。

## 一、背景与挑战

纯参数化模型的知识固化在权重里、无法执行副作用动作（查库、下单、跑代码），且算术与实时信息是其系统性弱项。
函数调用（tool use）把「决定调什么、传什么参数」交给模型，把「实际执行」交给确定性外部系统，从而把不可靠的生成转成可验证的执行。

## 二、核心原理

- 工具被描述为结构化签名（名称、自然语言用途、参数 JSON Schema），进入提示的工具清单；模型输出的是一次调用意图而非最终答案。
- 运行时（orchestrator）解析调用、执行、把结果作为新的观测回填上下文，模型据此继续推理，形成 思考→调用→观测 的循环。
- 关键分界：模型负责语义决策与参数填充，编排器负责校验、执行、重试、超时与权限，二者边界越清晰系统越稳。

## 三、数学形式

一次交互可写成受工具增广的自回归分解：$P(y\mid x)=\sum_{a,o}P(a\mid x)\,P(o\mid a)\,P(y\mid x,a,o)$，其中 $a$ 是调用（含参数），$o$ 是环境返回的观测，$P(o\mid a)$ 由外部系统而非模型决定。

多步时轨迹 $\tau=(a_1,o_1,\dots,a_T,o_T)$ 的似然为 $\prod_{t}P_\theta(a_t\mid x,\tau_{<t})$，工具只改变条件而不参与梯度（除非做工具增广训练）。

## 四、代码实现

```python
def run_agent(llm, tools, question, max_steps=6):
    msgs = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        out = llm(msgs, tools=[t.schema for t in tools])
        if not out.tool_calls:
            return out.content
        for call in out.tool_calls:
            obs = tools[call.name].run(**call.arguments)
            msgs.append({"role": "tool", "name": call.name, "content": str(obs)})
    return "达到步数上限"
```

## 五、与其他对比

- 与 RAG：RAG 是只读单一检索工具的特例；函数调用泛化到可写、可计算、可交互的动作空间。
- 与 规划与任务分解深入：规划决定「做哪些子任务」，函数调用决定「每步用哪个工具」，前者是策略层后者是执行层。

## 六、常见误区

- 把工具描述写成开发者注释而非面向模型的用途说明，导致选错工具——描述文本本身就是提示工程的一部分。
- 让模型自由拼接原始 SQL 或 shell 命令而不做参数化与白名单，等价于把注入风险交给采样过程。
- 假设模型输出的参数一定合法；必须先用 Schema 校验再执行，校验失败要把错误文本回灌让模型自纠。

## 八、面试题

- 为什么函数调用能改善算术与时效性问题？答：把不可靠的隐式计算/记忆外置为确定性执行，模型只需正确表达意图，误差不再随位数或时间累积。
- 编排器应该承担哪些职责？答：Schema 校验、权限与配额、超时与重试、结果截断与脱敏、审计日志，这些都不应依赖模型自觉。

## 九、演进

提示内伪工具（解析文本命令）→ 训练内嵌工具调用（Toolformer）→ 结构化函数调用接口 → 多工具编排与工具图谱 → 面向长任务的智能体运行时。

## 十、小结

函数调用把语言模型从「回答者」变成「决策者」，价值在于模型负责语义、系统负责保证，编排层的工程严谨度决定上限。
