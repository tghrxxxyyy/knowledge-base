# 工具检索与选择

> 对应 Qin et al., *ToolLLM/ToolBench*, ICLR 2024；Patil et al., *Gorilla*, 2023（大规模 API 检索式调用）。

## 一、背景与挑战

工具数量从个位数增长到成百上千后，无法把全部签名塞进上下文：既超长又引发选择困难与幻觉调用。
需要先检索出候选工具子集，再让模型在小集合内选择，这与 RAG 的召回—精排范式同构。

## 二、核心原理

- 工具文档（名称、用途、参数、示例调用）作为可检索文档建索引，用查询意图召回 top-k 候选注入提示。
- 分层选择：先选工具族/服务，再选具体接口，缩小每层的决策空间，减少近义接口混淆。
- 用调用成功率与结果有用性做在线反馈，更新工具描述或检索权重，形成可迭代的工具目录治理。

## 三、数学形式

检索阶段取 $T_k=\text{TopK}_{t\in T}\ \text{sim}(E(q),E(d_t))$；选择阶段模型在候选内建立分布 $P_\theta(t\mid q,T_k)$。

端到端正确率上界受召回率约束：$\text{Acc}\le \text{Recall@}k$，因此召回缺失是不可恢复的错误来源。

## 四、代码实现

```python
def select_tool(llm, q, index, k=8):
    cands = index.search(embed(q), k=k)          # 工具文档召回
    listing = "\n".join(f"{c.name}: {c.desc}" for c in cands)
    choice = llm(f"可用工具:\n{listing}\n\n任务: {q}\n只输出工具名")
    return next((c for c in cands if c.name == choice.strip()), None)
```

## 五、与其他对比

- 与全量工具注入：全量简单但受上下文与注意力稀释限制；检索式可扩展但引入召回风险。
- 与工具内化训练（Toolformer）：内化对固定小工具集高效，检索式对开放大工具集更可持续。

## 六、常见误区

- 工具描述由接口文档直接复制，充满内部术语，检索相似度与模型判断双双变差。
- 只按名称做词法匹配，忽略同义表达（下单/购买/提交订单），需混合稀疏与稠密检索。
- 候选 k 设得过大反而降低准确率：选项越多越容易被表面相似的接口带偏。

## 八、面试题

- 工具检索与文档检索有何不同？答：工具文档短、结构化、近义接口多，需要强调参数语义与可执行前置条件，并可用调用日志做反馈。
- 如何降低近义接口选错率？答：分层选择、在描述中显式写出「不适用场景」、并对易混对做少样本对比示例。

## 九、演进

固定少量工具 → 全量注入 → 检索式候选 → 分层与图结构工具目录 → 基于调用反馈的自动描述优化。

## 十、小结

工具规模化后选择问题退化为检索问题，召回率决定上限，描述质量决定精度。
