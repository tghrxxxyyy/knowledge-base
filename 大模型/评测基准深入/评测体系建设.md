# 评测体系建设

> 对应 EleutherAI *lm-evaluation-harness*、Stanford *HELM*（Liang et al., 2022）、Shanghai AI Lab *OpenCompass*（2023）；参考 LangChain / LlamaIndex 评估模块。

## 一、背景与挑战

公开榜单（MMLU、Arena 等）只能反映模型「通用能力」，无法直接回答「这个模型能否落地我业务」。企业级评测需要工程化体系：把公开基准、内部业务样本、持续回归串成流水线，做到每次迭代可量化、可对比、可门控。挑战在于：业务样本稀缺且标注贵、评测结果易波动、多基准聚合口径不一、以及如何在 CI 中自动拦截劣化。

## 二、核心原理

评测体系遵循「构建 → 跑分 → 报告 → 门控」闭环：(1) **构建**：维护三层数据集——公开基准（广度）、内部业务集（真实需求，最关键）、对抗/回归集（防回退）；(2) **自动化跑分**：用统一框架（lm-eval/OpenCompass）批量执行，固定随机种子与 prompt 模板；(3) **报告对比**：生成版本间 diff 看板；(4) **门控发布**：设定阈值，关键指标下降超 $\delta$ 则阻断发布。底层还需样本版本化、模型缓存与结果可复现。

## 三、形式化与数学基础

设版本 $v$ 在指标 $m$ 上得分 $s_m^{(v)}$，门控规则：

$$\text{pass} = \bigwedge_m \big(s_m^{(v)} \ge s_m^{(v_0)} - \delta_m\big)$$

其中 $v_0$ 为基线版本，$\delta_m$ 为允许最大回退（通常 0，关键指标）。统计显著性用 Bootstrap 估计置信区间：

$$\hat{\sigma}_m = \text{std}\!\left(\frac{1}{B}\sum_{b=1}^{B} \text{Acc}(\mathcal{D}_b^{(m)})\right)$$

仅当差异超出置信区间才判定「真实变化」，避免噪声误报。多基准聚合可按权重求加权总分 $S=\sum_m w_m s_m$。

## 四、代码实现

```python
from lm_eval import simple_evaluate
from lm_eval.models.huggingface import HFLM

model = HFLM(pretrained="my-model-v2")
res = simple_evaluate(
    model, tasks=["mmlu", "gsm8k", "my_business_set"],
    num_fewshot=0,
)
scores = {k: v["acc"] for k, v in res["results"].items()}

baseline = {"mmlu": 0.65, "gsm8k": 0.70, "my_business_set": 0.82}
for k in scores:
    if scores[k] < baseline[k] - 0.01:     # 回退 >1% 阻断
        raise SystemExit(f"REGRESSION on {k}: {scores[k]}")
```

结合 git tag 与 CI，每次合并自动跑该脚本并贴报告。

## 六、常见误区

- 只用公开基准：无法反映业务真实表现，公开集与线上分布差异大。
- 无随机种子/固定模板：结果不可复现、对比失真。
- 忽略置信区间：噪声波动误判为回归/提升。
- 门控阈值过松：劣化悄悄上线。

## 八、面试题

1. 为何公开基准不能替代业务内部评测？答：分布差异大，公开高分不代表线上任务好。
2. 如何避免噪声误报？答：固定种子 + Bootstrap 置信区间，差异超出区间才判变化。
3. 门控发布怎么设？答：基线版本关键指标设允许回退阈值，超则阻断。

## 九、演进与趋势

评测从「跑分」走向「持续评估平台」：与数据版本、模型注册、在线监控打通；引入 LLM-as-judge 自动评业务生成质量，并对接 RAG/Agent 轨迹评测，形成离线-在线一体化质量门。

## 十、小结

工程化评测体系是模型能否安全上线的守门人。三层数据集 + 统一框架 + 门控发布，把「模型变好/变坏」从主观感受变成可量化、可复现、可拦截的客观决策。
