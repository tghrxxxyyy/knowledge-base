# LLM 应用架构模式

> 对应 llm-course (mlabonne) 与 LangChain / LlamaIndex 官方文档。

## 一、背景与挑战

传统软件系统的输入、输出、执行路径高度确定，可用固定接口契约与单元测试覆盖。大模型应用则引入三类不确定性：第一，模型输出是非确定性的，相同输入在不同温度、不同推理引擎下可能得到不同结果；第二，单次推理时延从毫秒级跃升到百毫秒至数秒级，且对输入长度呈超线性增长；第三，成本以 token 计而非调用次数计，长上下文与多轮工具调用会迅速放大开销。为满足业务准确性，生产系统普遍叠加检索增强（RAG）、工具调用（Function Calling）、多智能体协作、人在回路（Human-in-the-loop）等机制。这些都使得「把模型接进服务」远远不够，必须建立一套从原型到生产的分层架构与治理闭环。

## 二、核心原理

业界通常把 LLM 应用拆成五层，自顶向下职责清晰、可独立演进：

- **接入层（Gateway）**：负责鉴权、限流、请求校验、协议转换（REST / gRPC / WebSocket），是稳定与安全的边界。
- **编排层（Orchestration）**：以 Chain、Agent、Workflow 形式串联提示组装、检索、工具调用、后处理；要求可控、可观测、可重试。
- **模型层（Model / Inference）**：托管推理服务（vLLM、TGI、TensorRT-LLM 等），提供高可用、弹性扩缩与连续批处理。
- **数据层（Data）**：向量数据库、文档存储、KV 缓存、结果缓存，决定知识新鲜度与命中率。
- **观测层（Observability）**：日志、追踪、指标、评测，贯穿其余四层，支撑灰度与持续优化。

分层的核心思想是「关注点分离」：把易变的部分（提示词、检索策略、工具）与稳定的部分（网关、鉴权、推理引擎）解耦，使 prompt 与检索逻辑的迭代不触发整体重发布。

一个常见反模式是「贫血架构」：把所有逻辑塞进一个巨大的 prompt 与单条调用，看似简单，却牺牲了可观测、可重试与可降级能力。生产级设计应让每一层都可独立替换与测试——例如检索策略可 A/B、模型层可热切换、观测层可关闭而不影响主链路。

## 三、形式化与数学基础

一次端到端请求可视为一个有向无环图（DAG）上的求值过程。设请求 $r$ 经过 $k$ 个处理节点 $v_1,\dots,v_k$，节点 $v_i$ 的输出为 $h_i$，则：

$$
h_i = f_i\big(h_{j_1},\dots,h_{j_{m_i}};\ \theta_i\big),\quad (j_1,\dots,j_{m_i}) \in \text{Parents}(i)
$$

端到端成本与时延分别可累加为：

$$
C(r) = \sum_{i=1}^{k} c_i(r), \qquad T(r) = \max_{\text{paths}} \sum_{i \in \text{path}} t_i(r)
$$

其中 $c_i$ 为节点 $i$ 的 token/调用费用，$t_i$ 为其时延。注意时延取「关键路径」最大值（并行节点）而非简单求和，这正是编排层需要异步与并发调度的数学依据。

## 四、代码实现

下面用 LlamaIndex 风格展示一个最小「检索 + 生成」编排：

```python
from llama_index.core import VectorStoreIndex, Document
from llama_index.llms.openai import OpenAI

docs = [Document(text="公司报销政策：单笔差旅不超过 5000 元。")]
index = VectorStoreIndex.from_documents(docs)
llm = OpenAI(model="gpt-4o-mini")

query_engine = index.as_query_engine(llm=llm, similarity_top_k=3)
# 编排层：检索 → 拼装上下文 → 生成
response = query_engine.query("出差住宿最多能报多少？")
print(response.response)
```

生产环境会把 `query_engine` 包进接入层（FastAPI + 限流中间件），并把每一步耗时上报观测层。

## 五、与其他技术对比

| 维度 | 传统微服务 | LLM 应用架构 |
|------|-----------|--------------|
| 输出确定性 | 高 | 低（需评测兜底） |
| 成本计量 | 调用次数 / CPU | token 数 / GPU 时 |
| 核心组件 | 数据库、缓存 | 向量库、推理引擎 |
| 失败模式 | 异常、超时 | 幻觉、越界、降级 |
| 关键治理 | 熔断、重试 | 评测、灰度、护栏 |

## 六、常见误区

- 把 Prompt 硬编码在业务代码里，导致提示词迭代必须发版。正确做法是把提示词与检索配置外置为可热更新的资源。
- 认为「加一层 Agent 就能解决一切」，忽视编排复杂度与可观测性，结果线上无法定位哪一步出错。
- 只压测单请求时延，忽略关键路径并发与长上下文下的显存/排队放大效应。

## 九、演进与趋势

架构正从「手工 Chain」走向「声明式 Workflow + 托管 Agent 运行时」：模型厂商提供原生工具调用与结构化输出，编排层下沉为轻量调度；向量检索与推理引擎融合（如带前缀缓存的推理服务），观测与评测逐步标准化（OpenTelemetry + 评测集）。多智能体协作催生「Agent 通信协议」与「共享记忆层」。

落地时还需配套组织机制：提示词与检索配置的版本管理、回滚预案、以及「评测集驱动」的迭代节奏，才能让上述分层架构真正可持续演进。

## 十、小结

LLM 应用架构的本质，是在「不确定性的模型」之上叠加确定性的工程体系：以分层隔离变化、以观测兜底质量、以缓存与路由控制成本。从原型到生产，关键不在「接上模型」，而在建立可迭代、可评测、可降级的工程闭环。
