# 推理服务高可用

> 对应 vLLM 官方文档与 HuggingFace Text Generation Inference 文档。

## 一、背景与挑战

GPU 推理昂贵且时延波动大：单副本故障即意味着服务中断；流量突增时，若不加约束地接收请求，会触发显存溢出（OOM）或请求堆积雪崩。另一方面，用户体验由尾延迟（p99）而非平均时延决定——一个被长序列拖慢的批处理可能让多数用户等待。高可用的目标是在不浪费 GPU 的前提下，保证可用性与可预期的尾延迟。

## 二、核心原理

生产推理服务通常组合以下手段：

- **多副本 + 负载均衡**：消除单点，分散流量。
- **健康检查**：就绪/存活探针，避免把请求发到未就绪或已劣化的副本。
- **自动扩缩容**：按队列长度或 GPU 利用率增减副本。
- **请求排队**：用有界队列削峰，超出容量的请求快速失败而非拖垮整体。
- **连续批处理（continuous batching）**：把陆续到达的请求动态拼批，提升吞吐。
- **KV Cache 分页管理**：防止自回归生成中的显存碎片与 OOM。

## 三、形式化与数学基础

在批大小 $B$、每步耗时 $t$ 的近似下，吞吐为：

$$
\text{TH} = \frac{B}{t}\ \text{(tokens/s)}
$$

把请求到达建模为到达率 $\lambda$、服务率 $\mu$，则平均排队等待（M/M/1 直觉）：

$$
W \approx \frac{\lambda}{\mu - \lambda}
$$

必须保证 $\mu > \lambda$，否则队列无界增长。尾延迟往往由批内最长序列决定，因此批策略直接影响 p99。

## 四、代码实现

以 vLLM 部署配合 K8s 探针为例（示意）：

```yaml
# 简化示意：vLLM 部署 + 探针
resources:
  limits:
    nvidia.com/gpu: 1

  httpGet:
    path: /health
    port: 8000
readinessProbe:
  httpGet:
    path: /health
    port: 8000
```

客户端侧则应使用带超时的有界队列，避免无限等待：

```python
import requests
try:
    r = requests.post(URL, json=payload, timeout=30)
    r.raise_for_status()
except requests.Timeout:
    # 触发降级或重试
    pass
```

## 五、与其他技术对比

| 方案 | 可用性 | 吞吐 | GPU 成本 | 尾延迟 |
|------|--------|------|----------|--------|
| 单副本 | 低 | 低 | 低 | 不稳定 |
| 多副本+LB | 高 | 中 | 中 | 较稳 |
| 多副本+自动扩缩 | 高 | 高 | 弹性 | 可控 |

## 六、常见误区

- 为「保险」过度预留 GPU，造成成本浪费。
- 只看平均时延，忽视 p99 尾延迟对体验的影响。
- 不设请求队列上限，客户端超时风暴反压击垮服务。

## 九、演进与趋势

方向包括 prefill 与 decode 解耦部署、KV Cache 卸载到 CPU/SSD、serverless GPU 推理、基于 S-LoRA 的多租户复用，以及感知硬件拓扑的调度器。

## 十、小结

LLM 推理高可用 = 副本冗余 + 智能批处理 + 有界队列 + 弹性扩缩，并以尾延迟与 GPU 成本为双约束调优。它不是堆硬件，而是用工程手段在「不崩」与「不贵」之间找平衡。
