# 限流与降级

> 对应 vLLM 文档与稳定性工程实践（以官方最新文档为准）。

## 一、背景与挑战

LLM 推理慢且贵：单次请求占用 GPU 显存与算力数秒，且并发受限于显存与批处理能力。
若放任流量涌入，少量长请求即可占满资源，导致整体队列膨胀、超时雪崩，甚至 OOM 让服务崩溃。
限流与降级是用「主动拒绝/退让」换取「系统不垮、多数用户可用」的稳定性手段。

## 二、核心原理

- **限流（Rate Limiting）**：令牌桶 / 漏桶 / 并发上限，约束单位时间请求数或同时在途请求数。LLM 场景更应限「并发」与「在途 token」，因瓶颈在显存而非 QPS。
- **排队（Queueing）**：有界队列削峰，超容量快速失败（429）而非无限等待。
- **超时（Timeout）**：避免单请求长时间挂起占用资源。
- **降级（Fallback）**：主模型不可用或过载时，回退到小模型 / 模板 / 缓存答案；失败路径仍须保证不返回有害内容。

## 三、形式化与数学基础

令牌桶以速率 $r$ 补充、容量 $C$ 为上限，时刻 $t$ 可用令牌 $T(t)$ 满足：

$$
T(t) = \min\!\big(C,\ T(t-\Delta t) + r\cdot\Delta t\big)
$$

请求消耗 $1$（或按 token 计费消耗 $k$）令牌，不足则拒绝。
并发上限 $M$ 约束同时在途请求数，使显存占用有界：

$$
\sum_{i \in \text{inflight}} \text{VRAM}_i \le \text{GPU\_CAP}
$$

降级触发可由错误率 $e$ 或队列长度 $q$ 超过阈值决定，形成「限流→排队→超时→降级」的递进防护。

## 四、代码实现

以令牌桶限流中间件（FastAPI 风格）示意：

```python
import time

class TokenBucket:
    def __init__(self, rate: float, capacity: float):
        self.rate, self.cap, self.tokens = rate, capacity, capacity
        self.last = time.time()
    def allow(self) -> bool:
        now = time.time()
        self.tokens = min(self.cap, self.tokens + self.rate * (now - self.last))
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

bucket = TokenBucket(rate=5.0, capacity=20.0)  # 每秒 5 个，突发 20
```

## 五、与其他技术对比

| 手段 | 作用 | 代价 |
|------|------|------|
| 令牌桶限流 | 平滑流量 | 突发被拒 |
| 并发上限 | 护显存 | 超出排队/失败 |
| 超时 | 防挂起 | 早失败 |
| 降级 | 保可用 | 质量下降 |

## 六、常见误区

- 用 QPS 限流 LLM，却忽略「在途 token / 显存」才是真正瓶颈。
- 降级回退到无护栏的小模型，可能返回有害或越界内容。
- 队列无限长，客户端超时反而造成重复请求放大压力。
- 只限入口不限推理引擎，导致引擎侧仍被压垮。

## 九、演进与趋势

自适应限流（按 GPU 实时负载动态调阈值）、按请求优先级与预算调度、与降级链路的自动编排，以及把「护栏（guardrail）」纳入降级默认路径。
云原生场景下，限流常与网关、服务网格联动，做到多层防护。
进阶做法是「自适应限流」：不再用固定令牌桶速率，而是实时读取 GPU 利用率、队列长度与 p99 时延，动态收紧或放宽并发上限。

## 十、小结

一个常被忽视的细节是「重试风暴」：客户端在超时后盲目重试，会把瞬时过载放大成持续性过载。
正确做法是在客户端实现带退避（exponential backoff + jitter）的重试，并尊重服务端返回的 429 与 Retry-After 头。
服务端与客户端协同限流，才能构成完整防护：服务端护显存、客户端护自身与对端，二者缺一不可。
限流与降级是 LLM 服务的稳定性底座：以并发/在途 token 为约束护住显存，以有界队列与超时防止雪崩，以安全降级保证「不垮且不失守」。
