## 一、为什么评测是刚需

模型能力肉眼难测，没有评测就没有迭代方向。评测回答三个问题：

- **能力**：知识、推理、代码、数学到什么水平？
- **安全**：会不会输出有害/偏见/泄密内容？
- **对齐**：是否符合人类意图与价值观？

## 二、能力评测维度

| 维度 | 代表基准 | 说明 |
|------|----------|------|
| 通用知识 | MMLU | 57 学科多选 |
| 推理 | GSM8K / BBH | 数学/综合推理 |
| 代码 | HumanEval / MBPP | 函数级代码生成 |
| 中文 | C-Eval / CMMLU | 中文知识与学科 |
| 长上下文 | LongBench | 长文理解 |
| 指令遵循 | IFEval | 格式/约束遵循 |

## 三、评测方法

- **基准测试**：标准数据集跑分（自动化）。
- **LLM-as-Judge**：用强模型给回答打分（高效但有偏）。
- **人工评测**：难例抽检，最可靠但贵。
- **A/B 对比**：新旧版本在同源样本上对比胜率。

## 四、红队（Red Teaming）

红队是主动攻击模型，找漏洞：

- **越狱（Jailbreak）**：用角色扮演/编码/拆分绕过安全护栏。
- **提示注入**：在工具返回里藏恶意指令（"忽略之前所有指令"）。
- **数据泄露**：诱导输出训练数据/系统提示/密钥。
- **偏见歧视**：测试性别/种族/地域刻板印象。
- **幻觉诱导**：问编造事实看是否一本正经胡说。

## 五、常见攻击与防御

| 攻击 | 防御 |
|------|------|
| 越狱提示 | 系统提示强化 + 输入过滤 + 输出审核 |
| 提示注入 | 工具内容标记隔离 + 最小权限 |
| 数据泄露 | 训练去重 + 输出过滤 + 敏感信息正则 |
| 多轮套话 | 跨轮次一致性检测 |

## 六、评测集建设

- 自建业务评测集（≥500 条）覆盖真实场景。
- 分层：简单/中等/困难，按难度看退化。
- 定期回归，防止优化一项崩另一项（能力遗忘）。

## 七、指标体系

- **准确率 / 通过率**：客观题。
- **胜率（Win Rate）**：对比评测。
- **有害率**：安全维度。
- **拒答率**：过度拒答也需关注（可用性）。
- **成本/延迟**：工程可行性。

## 八、评测平台

- 开源：lm-evaluation-harness、OpenCompass、HELM。
- 自建：把评测集 + 自动判分 + 看板串起来。

## 九、常见坑

- 只跑公开榜 → 不代表业务效果。
- 用被测模型当 judge → 自我偏好偏置。
- 忽视安全评测 → 上线翻车。
- 不回归 → 微调后能力悄悄退化。

## 十、落地清单

1. 建业务评测集（能力 + 安全）。
2. 接自动化评测流水线。
3. 红队定期攻防。
4. 每次迭代跑回归 + 看板。
5. 设上线门槛（能力不降 + 安全达标）。
