> LLM 评测难在多维、主观、动态。本篇深入拆解：评测数据集构建、LLM-as-Judge 工程化、Agent/RAG 专项评测、评测驱动开发（Eval-Driven Dev）。

---

## 一、为什么 LLM 评测如此之难

传统 ML 评测简单：分类看 Accuracy、回归看 MSE、推荐看 AUC。LLM 不行，因为三个结构性困难：

| 困境 | 说明 |
|------|------|
| **多维性** | 能力维度 = {知识, 推理, 代码, 数学, 创意, 安全, 指令遵循, …}，单一指标无法捕捉全貌 |
| **主观性** | 「好回答」本身主观；人类标注员间一致性（Cohen's κ）仅 **≈0.4–0.7** |
| **动态性** | 模型频繁更新、基准公开后被训进数据（污染）、易过拟合 → Goodhart 定律 |

> Goodhart 定律：「当一个指标成为目标，它就不再是好指标」。

## 二、三大评测方法

### 2.1 静态基准（Static Benchmarks）

标准化题集，可量化、可复现、快速筛选；缺点：易污染、易 gaming、单分数片面。

代表：MMLU、GSM8K、HumanEval、GPQA、SWE-bench、LiveBench、Hella's Last Exam。

### 2.2 人类偏好评估（Human Preference）

以人类真实偏好为核心。最可信但最贵、难规模化。代表：**LMSYS Chatbot Arena**——匿名 pairwise 对比、Elo 排名（约 499 万票 / 296 模型）。

局限：用户群体偏差、成本/可扩展性、隐式偏见。

### 2.3 LLM-as-Judge（模型评模型）

用 LLM 按自定义标准打分。**GPT-4 级 judge 与人类标注员一致性 >80%**，成本仅为人类的 **500–5000×**，是企业最实用的自动化方案。

```mermaid
flowchart LR
    P[原始 prompt] --> S[LLM 系统输出]
    S --> J[LLM Judge + 评分 rubric]
    J --> SC[分数 0-1 / 胜者]
    SC --> DASH[看板 / 回归]
```

## 三、评测数据集构建（深入）

### 3.1 数据集来源

| 来源 | 特点 | 适用 |
|------|------|------|
| 公开基准 | 标准、可对比 | 横向比较 |
| 私有领域题 | 你的真实分布 | 生产回归 |
| 生产日志采样 | 真实请求（脱敏） | 最贴近实际 |
| 合成数据 | 可控、可扩充 | 覆盖边界 |
| 人工标注 | 质量最高 | 校准/金标准 |

### 3.2 数据集设计原则

```
覆盖性：
  正常场景（80%）：常见提问
  边界场景（10%）：长文本/多轮/模糊提问
  失败场景（10%）：历史出错的 case（回归）

金标准（Golden Set）：
  人工标注的期望答案
  用于：Judge 校准、人工抽检

动态更新：
  每周从生产日志采样新 case
  人工 review 后加入测试集
  版本化（Git 管理）
```

### 3.3 防污染设计

```
私有题（防训练污染）：
  公司内部数据/新生成的题
  不公开

动态题：
  定期更新（过期作废）
  与模型训练集隔离

结果验证：
  高分模型抽查真实输出（防 gaming）
```

## 四、LLM-as-Judge 工程化（深入）

### 4.1 两种类型

| 类型 | 输出 | 适用 |
|------|------|------|
| **Single-output** | 对单条输出打定量分 | 答案相关性、忠实度、正确性 |
| **Pairwise** | 选「赢家」（不输出分） | 类 Arena 的 A/B 对比 |

### 4.2 G-Eval：最常用自定义 Judge

G-Eval 思路：用 LLM 定义**评估标准（rubric）+ CoT 自评**，输出 0–1 分数。常见指标：
- **Answer Relevancy**（是否切题）
- **Faithfulness**（是否忠实事实、不幻觉）
- **Correctness / Helpfulness / Bias**

```python
from deepeval import evaluate
from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCase

metric = GEval(
    name="coherence",
    criteria="评判摘要对原文是否连贯",
    evaluation_params=["input", "actual_output"],
)
test_case = LLMTestCase(input=article, actual_output=summary)
evaluate([test_case], [metric])
```

### 4.3 Rubric 设计

```
好 Rubric 特征：
  具体可观察（"包含关键数字"而非"回答准确"）
  分档明确（0~1 的每档描述）
  与业务目标对齐（客服场景看"解决问题率"）

Rubric 模板：
  0.0~0.2：完全错误/不相关
  0.3~0.5：部分正确，缺关键点
  0.6~0.8：正确，有瑕疵
  0.9~1.0：完全正确且高质量
```

### 4.4 提升 Judge 可靠性的技巧

- **CoT 提示**：先写评判理由再打分；
- **In-context learning**：给 1–2 个打分示例校准尺度；
- **Swap position**（pairwise 必做）：两条输出左右互换各评一次，消除位置偏差；
- **独立更强 judge**：别用被测同模型当 judge；
- **人类校准**：上线前与人类标注对齐，目标 >80% 一致。

### 4.5 常见偏差与破解

| 偏差 | 表现 | 破解 |
|------|------|------|
| 位置偏差 | pairwise 固定左赢 | 换位置各评一次 |
| 自我偏好 | 偏好同家族模型 | 用独立 judge |
| 长度偏差 | 越长越被当好 | rubric 强调质量非长度 |
| 权威偏差 | 自信表述被当对 | 要求引用/验证 |
| 冗余偏差 | 重复内容被当好 | rubric 明确禁止冗余 |

### 4.6 Judge 成本控制

```
分层 judge：
  简单任务 → 小模型 judge（便宜）
  复杂任务 → 大模型 judge

批量评估：
  合并多条 case 一次评估（降低调用次数）
  按批次缓存结果

抽样评估：
  全量跑小模型 + 抽样跑大模型对比
  大模型只复核低置信结果
```

## 五、Agent / RAG 专项评测

### 5.1 RAG 评测（RAGAS 四指标）

| 指标 | 回答的问题 |
|------|-----------|
| Faithfulness | 答案是否忠实于检索上下文 |
| Answer Relevancy | 答案是否切题 |
| Context Precision | 检索到的上下文是否相关 |
| Context Recall | 是否检索到所有相关上下文 |

### 5.2 Agent 评测

```
Agent 评测维度：
  任务完成率：目标是否达成（主指标）
  工具调用正确性：调用是否准确/参数是否正确
  效率：步数/轮数是否合理
  安全性：是否越权/误操作
  鲁棒性：异常输入/工具失败时的表现

评测方法：
  端到端（任务级）：跑完整任务 → 检查结果
  分步（轨迹级）：每步工具调用评分
  仿真环境：模拟用户/工具（Sandbox）
```

### 5.3 工具调用评测

```
正确性：
  工具名选择是否正确
  参数填充是否正确（类型/必填）
  返回值使用是否正确

误用检测：
  是否调用无关工具
  是否遗漏关键工具
  是否绕过权限工具
```

## 六、评测驱动开发（Eval-Driven Dev）

### 6.1 流程

```
1. 写 case（先于实现：TDD 思想）
2. 跑基线（当前模型/系统得分）
3. 修改（提示词/工具/RAG）
4. 重跑对比（同 case 集）
5. 达标放行 / 掉点回滚
```

### 6.2 回归门禁

```
每次变更必跑：
  提示词改动
  RAG 检索改动（切块/重排/模型）
  Agent 工具/编排改动
  模型升级/切换

门禁规则：
  关键指标掉点 > 2% → 阻断发布
  新 case 加入 → 验证不破坏旧 case
  结果存档（可回放）
```

### 6.3 评测数据管理

```
版本化：case 集 Git 管理（变更记录）
标签：按业务域/难度/类型分类
所有权：业务方认领 case 更新
淘汰：过期/重复 case 定期清理
```

## 七、自动化 Eval 流水线

```
任务测试集(私有/领域) → 批量跑 LLM 系统 → Judge 打分(LLM-as-Judge) 
   → 指标聚合(准确率/忠实度/相关性) → 看板/回归对比 → 告警/人工抽审
```

关键组件：
- **数据集版本化**：任务特异 cases + 领域基准 + 私有题（防污染）；
- **持续评测**（OpenAI Evals 哲学）：开发全程记录好 case，尽量自动化，用人类反馈校准；
- **可复现**：用 lm-eval-harness 等标准实现跨模型一致比较；
- **回归门禁**：每次改动跑 eval 前后对比，掉点即拦。

## 八、推理模型怎么评（2025 评测最大盲区）

长思考（CoT）模型的评测必须回答四个问题：

1. **Judge 看什么**：主流做法**只评最终答案**（思考 token 不对外、不可见，且各厂商 CoT 格式不同）；
2. **思考预算不归一**：必须**固定 thinking budget（reasoning effort）对比**，并额外报「每正确 1 题的 token 成本」；
3. **口径统一**：明确 pass@1 还是多数投票/自洽——多数投票分数更高但成本翻倍，报告时分开；
4. **采样与温度**：报告分数时标注温度与采样数，否则不可复现。

> 一句话：**评推理模型 = 固定思考预算 + 只评最终答案 + 口径统一（pass@1 vs 多数投票）+ 报 token 成本。**

## 九、生产三层防线

```
第一层：任务特异测试集（你的真实分布，私有/动态题）
第二层：领域基准（GPQA / SWE-bench / 行业题）
第三层：线上 A/B + 人类抽检（关键路径必加）
```

- 静态基准给广度基线，领域基准给区分度，人类/A-B 兜底高风险；
- 动态/私有题防 gaming（基准公开易被训进数据）。

## 十、小结

- 评测难在多维、主观、动态；需多方法组合。
- LLM-as-Judge 是当前生产主流（单/双两型 + G-Eval），但必须人类校准、防偏差。
- 把评测做成自动化流水线 + 回归看板，RAG/Agent 改动必跑。
- 三层防线（私有集 / 领域基准 / 线上 A-B）覆盖广度与高风险。
- Agent/RAG 专项评测：RAGAS 四指标 + 任务完成率 + 工具调用正确性。
- **评测驱动开发**：case 先行、回归门禁、掉点回滚。
