# 推理算力估算

> 对应 Shazeer, 2019；NVIDIA 推理优化实践；LLM 服务成本模型.

## 一、背景与挑战

部署时需估算每请求的延迟与算力，以定 batch、显存与单价；推理仅前向，结构不同于训练。

## 二、核心原理

每生成 token 前向约 $2N$ FLOPs；自回归逐 token 生成，prefill 阶段处理整 prompt（含注意力 $O(n^2)$），decode 阶段逐 token。

## 三、数学形式

生成 $T$ token 约 $2NT$ FLOPs；prefill $2N\times n_{prompt}$；decode 受内存带宽主导（每 token 读一次权 $N$ 参数）。

## 四、代码实现

```python
def infer_flops(params, prompt_len, gen_len):
    return 2*params*(prompt_len + gen_len)
latency ≈ 2*params*bytes / bandwidth      # decode 受带宽
```

## 五、与其他对比

- 与 训练算力估算（6ND、含反向）对照：推理仅前向。
- 与 连续批处理深入（提升 GPU 利用率）衔接。

## 六、常见误区

- 以为算力主导 decode（实为内存带宽主导）。
- 忽略 prefill 与 decode 成本结构不同。

## 八、面试题

- 为何 decode 受带宽而非算力？答：每 token 需读全量权重一次，瓶颈在显存带宽而非计算吞吐。

## 九、演进

逐 token 朴素 → 连续批处理 → 投机/蒸馏降算力。

## 十、小结

推理算力估算要区分 prefill/decode，decode 受带宽主导，是服务成本核心。
