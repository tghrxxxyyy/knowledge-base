# 指令数据集与格式化

> 对应 rasbt/LLMs-from-scratch 第7章、Alpaca / ShareGPT 指令数据格式。

## 一、背景与挑战

SFT 效果上限由数据质量决定。原始指令数据多为 JSON 结构化字段（instruction / input / output，或对话多轮 messages），必须序列化为模型可训练的单条 token 流，并正确标注"哪段算 loss"。难点：其一，**模板一致性**，训练与推理必须用同一对话模板，否则分布错位；其二，**loss mask 构造**，prompt 部分置 `-100`，仅 response 算梯度；其三，**特殊 token**，BOS/EOS/分隔符需拼对，否则解码错乱；其四，**多轮拼接**，对话历史要按角色交错排布；其五**长度截断**，超长样本需按策略截断（优先保留最新轮）且不破坏 mask 对齐；其六**模板泄漏与污染**，训练模板字符串若出现在评测题里会虚高分数，需去污染。

## 二、核心原理

通用流程：

1. **读取结构化样本**：Alpaca 用 `instruction+input+output` 三段；ShareGPT 用 `messages` 角色列表。
2. **套用模板拼接**：把字段按固定模板渲染成单一字符串，角色用特殊标记（如 `### Instruction:`、`<|user|>`）分隔。
3. **tokenize 并构造 labels**：先对整串编码，再把 prompt 区域标签置 `-100`，仅保留 output/assistant 段。
4. **补 EOS**：response 末尾加结束符，告知模型"答完"。
5. **截断对齐**：超长时从左侧裁掉最旧轮次，并同步裁 labels 保持一一对应。

## 三、形式化与数学基础

设拼接后 token 序列为 $x_{1:T}$，prompt 覆盖区间 $\mathcal{P}$、回答覆盖 $\mathcal{A}=[1,T]\setminus\mathcal{P}$。标签：

$$\ell_t = \begin{cases} -100, & t\in\mathcal{P} \\ x_t, & t\in\mathcal{A} \end{cases}$$

损失仅对 $\mathcal{A}$ 求和（见「指令微调实现」）。多轮对话则每轮 assistant 段都纳入 $\mathcal{A}$，user 段纳入 $\mathcal{P}$，保证模型只学"如何答"而非"如何问"。序列长度约束 $T\le T_{\max}$，超出需截断且保持 $\ell$ 与 $x$ 索引一致。去污染要求训练集与评测集在模板与 n-gram 上低重叠。

## 四、代码实现

```python
def build_sample(tok, instruction, inp, output):
    if inp:                                       # Alpaca 含 input
        prompt = f"### Instruction:\n{instruction}\n### Input:\n{inp}\n### Response:\n"
    else:
        prompt = f"### Instruction:\n{instruction}\n### Response:\n"
    full = tok(prompt + output + tok.eos_token, return_tensors="pt")
    ids = full["input_ids"][0]
    labels = torch.full_like(ids, -100)
    p_len = len(tok(prompt)["input_ids"])        # prompt 长度
    o_ids = tok(output)["input_ids"]
    labels[p_len: p_len + len(o_ids)] = ids[p_len: p_len + len(o_ids)]
    return {"input_ids": ids, "labels": labels}   # output 段参与 loss

# ShareGPT 多轮：逐轮拼 user/assistant，仅 assistant 段置真实 label
def build_chat(tok, messages):
    ids, labels = [], []
    for role, text in messages:
        seg = tok(f"<|{role}|>:{text}")
        ids += seg; labels += (seg if role == "assistant" else [-100]*len(seg))
    return ids + [tok.eos_token_id], labels + [tok.eos_token_id]
```

## 六、常见误区

- **训练/推理模板不同**：格式错位，回答前缀错乱。
- **prompt 也进 loss**：模型学复述问题。
- **漏 EOS**：生成不终止。
- **特殊 token 与 tokenizer 不匹配**：解码出乱码。
- **截断破坏对齐**：裁 input 未同步裁 labels，索引错位致 loss 算错。
- **忽略去污染**：训练模板串泄漏进评测，指标虚高。

## 九、演进与趋势

从人工 Alpaca 走向"自指令（self-instruct）"自动扩量；从单模板走向"聊天模板标准化"（ChatML / Jinja 模板随 tokenizer 绑定，如 HuggingFace `tokenizer.apply_chat_template`）；指令去污染与质量筛选（如 LIMA 的"少而精"）成为关键工程；合成数据配比研究（如Mixin）提升多样性，并配合 n-gram 去重避免评测泄漏。

## 十、小结

指令数据格式化的本质是把结构化样本变成"带掩码的单流"。模板一致 + prompt 掩码 + EOS 收尾 + 截断对齐 + 去污染，是 SFT 数据管线的五件小事，却直接决定微调成败与评测可信度。
