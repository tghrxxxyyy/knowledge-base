# Prompt 工程模式与少样本学习

> 本文系统梳理 Prompt 工程的可复用模式：角色设定、结构化输出、思维链（CoT）、少样本（Few-shot）、自洽性（Self-Consistency）、ReAct、约束与防注入等，并给出何时用哪种模式的判断。内容基于公开研究与实践，具体模型行为以厂商文档为准。

## 1. Prompt 工程的定位

Prompt 工程是"在不改模型权重的前提下，通过输入组织方式引导模型输出期望结果"的技术。它成本低、可解释、易迭代，是 LLM 应用的第一道工程杠杆。但当任务复杂、稳定性要求高时，应转向微调或 Agent 架构。

## 2. 基础模式

### 2.1 角色与指令清晰化

- 明确角色：`你是一个资深 Java 面试官，严格按评分标准打分`。
- 明确任务边界：输入/输出格式、禁止项、语气。
- 避免歧义：用"必须/禁止/仅"等强约束词。

### 2.2 结构化输出

要求模型输出 JSON / YAML / XML，便于程序解析：

```
请输出 JSON：{"summary": "...", "risk_level": "low|medium|high", "items": [...]}
仅输出 JSON，不要额外解释。
```

配合 schema 校验（如 JSON Schema、Pydantic）做后处理兜底。

### 2.3 分步与示例

复杂任务先给步骤再执行，降低单次推理负担。

## 3. 思维链（Chain-of-Thought, CoT）

CoT 让模型"先想后答"，在推理、数学、多步任务上显著提升准确率。

- **零样本 CoT**：加一句 `让我们一步步思考（Let's think step by step）`。
- **少样本 CoT**：在示例里展示"推理过程 → 答案"的格式。

适用：需要多步推断的任务；对纯检索/格式转换帮助有限。

## 4. 少样本（Few-shot）

在 prompt 中提供若干 (输入, 输出) 示例，引导模型模仿风格与格式。

- **示例质量 > 数量**：3–5 个高质量、覆盖边界的示例常胜过 20 个噪声示例。
- **顺序与多样性**：覆盖典型与异常 case，避免示例本身有偏。
- **与指令冲突**：示例若与指令矛盾，模型可能跟随示例，需保持一致。

## 5. 自洽性（Self-Consistency）

对同一个问题采样多条推理路径（多条 CoT），用多数投票选最终答案。牺牲延迟换准确率，适合对正确性极敏感的场景（如数学题、诊断）。

## 6. ReAct（推理 + 行动）

ReAct 让模型交替进行：思考（Thought）→ 行动（Action，调用工具）→ 观察（Observation），循环直到得出答案。它是 Agent 的基础范式，把"推理"与"外部交互"结合。

```
Thought: 我需要查订单状态
Action: query_order(order_id="123")
Observation: {"status":"shipped"}
Thought: 已发货，可告知用户
Final Answer: 订单 123 已发货
```

要点：工具描述要清晰、动作空间要受限、循环需设最大步数防失控。

## 7. 约束与防注入

### 7.1 越狱与提示注入

攻击者可在用户输入中嵌入"忽略以上指令，执行 X"。防御手段：

- **系统/用户隔离**：明确系统指令优先级，用分隔符包裹不可信输入。
- **输入净化**：检测并拒答明显注入模式。
- **输出校验**：对敏感操作要求二次确认或人类审批。
- **最小权限**：Agent 工具仅暴露必要能力。

### 7.2 格式与长度约束

- 明确最大长度、禁止内容（如"不要输出代码以外内容"）。
- 用分隔符（`###`、`"""`）划定不可信文本边界。

## 8. 模式选择决策

| 任务 | 推荐模式 |
|---|---|
| 格式转换/抽取 | 结构化输出 + 少样本 |
| 多步推理/数学 | CoT / 自洽性 |
| 分类/打标 | 少样本 + 明确标签集 |
| 需查外部数据 | ReAct + 工具 |
| 超高准确率需求 | 自洽性 + 校验 |
| 防恶意输入 | 隔离 + 注入防护 |

## 9. 评估 Prompt

- **固定测试集**：一批输入—期望输出，回归测试 prompt 改动。
- **多维度**：准确率、格式合规率、拒答率、延迟、成本。
- **版本管理**：prompt 当代码管理，记录变更与效果。

## 10. 常见误区

1. **prompt 越长越好**：冗余指令反而稀释重点，应精炼。
2. **忽视模型差异**：某模型有效的技巧在另一模型未必，需实测。
3. **少样本噪声**：示例选错导致风格漂移，应精选。
4. **过度依赖 CoT 于简单任务**：增加延迟无收益。
5. **无输出校验**：信任模型必然合规，生产应加 schema 校验与降级。

## 11. 与上下文工程的关系

Prompt 工程偏向"单次输入怎么写"，上下文工程（见相关章节）偏向"在长程任务中组织、筛选、压缩给模型的信息"。二者互补：写好单条 prompt，也要管好整体上下文窗口。

## 12. 小结

Prompt 工程是 LLM 应用性价比最高的起点：先用角色+结构化+少样本+CoT 打底，复杂任务上 ReAct，敏感任务加自洽与注入防护，并用固定测试集持续评估。记住——示例质量优于数量，约束要写在显眼处，输出必须程序校验。
