# 日志与追溯

> 对应 OWASP Top 10 for LLM Applications（敏感信息泄露等风险项）、NIST AI RMF 与国内生成式 AI 服务安全基本要求中的留痕审计条款（以官方最新文档为准）。

## 一、背景与挑战

大模型服务上线后必然面对用户投诉、安全事件与监管调阅。当出现违规输出、隐私泄露或错误决策时，团队必须还原「谁、在何时、用哪个模型版本、输入了什么、检索了什么、得到了什么输出」。核心挑战有四：一是请求量大，全量留痕带来存储与成本压力；二是日志中常含用户隐私（PII），明文落盘违反数据保护要求；三是网关、编排、检索、推理、插件多服务调用需要跨系统关联；四是日志本身若可被篡改，便失去取证与定责价值。因此追溯体系必须在完整性、隐私性与成本之间取平衡。

## 二、核心原理

可追溯体系围绕一条「审计轨迹」展开。最小记录字段通常包括：唯一请求/会话标识（trace id）、脱敏后的用户或租户标识、时间戳、模型名称与版本（含权重哈希或快照 id）、提示模板 id 与变量、检索来源（RAG 场景的文档 id 与片段）、最终输出、过滤与拦截动作、判定理由、延迟与 token 用量。

工作流为：

1. 网关生成 trace id 并通过请求头向下游透传，保证跨服务可关联；各阶段以结构化事件（JSON）上报，字段统一 schema 并版本化。
2. 写入前做脱敏：PII 哈希或令牌化，正文按最小必要原则截断或分级存储。
3. 存储采用只追加（append-only）+ 哈希链，保证不可篡改且可验证。
4. 提供按 trace id、用户、模型的检索与导出接口，并设置留存期与访问权限。

关键设计原则是「可关联、可验证、最小化」：能还原链路，能证明未被改动，同时不持有不必要的敏感信息。

## 三、形式化与数学基础

定义可追溯覆盖率：全部事件中可被唯一 trace id 完整还原的比例。

$$ T = \frac{|\{\,e \in E : \text{traceable}(e)\,\}|}{|E|} $$

留痕可建模为成本—合规权衡。设单请求存储成本为 $c_s$，留存期为 $L$ 天，日均请求量 $Q$，采样率为 $\rho$，则存储成本：

$$ \text{Cost} = c_s \cdot Q \cdot L \cdot \rho $$

分层采样可在保持覆盖率的同时降本：对高风险请求取 $\rho=1$，对普通请求按比例采样。为降低 PII 风险，对标识施加单向脱敏函数 $h(\cdot)$，使明文不可从日志恢复：

$$ \text{log}_i = (\text{trace}_i,\ h(\text{uid}_i),\ \text{ts}_i,\ \text{model}_i,\ \text{out}_i) $$

完整性由哈希链保证，第 $i$ 条记录摘要依赖前一条；任一历史记录被修改，其后所有摘要校验失败，篡改即可被发现：

$$ H_i = \text{SHA256}\big(\text{rec}_i \,\|\, H_{i-1}\big), \quad H_0 = \text{seed} $$

## 四、代码实现

```python
# 审计日志：结构化事件 + 脱敏标识 + 哈希链 + 分级采样
import hashlib, json, time


class AuditLog:
    def __init__(self, store, seed="0" * 64):
        self.store = store          # 只追加存储（WORM / 对象存储 + 版本控制）
        self.prev = seed

    def _digest(self, payload: str) -> str:
        return hashlib.sha256(payload.encode("utf-8")).hexdigest()

    def _anonymize(self, uid: str) -> str:
        # 加盐哈希：同一用户在同一 salt 下可关联，但不可反推明文
        return self._digest("salt:" + uid)[:16]

    def append(self, trace_id, uid, model, prompt, output, risk="normal"):
        rec = {
            "ts": int(time.time()), "trace_id": trace_id, "model": model,
            "uid_anon": self._anonymize(uid), "prompt": prompt, "output": output,
            "risk": risk, "prev": self.prev,
        }
        rec["hash"] = self._digest(json.dumps(rec, sort_keys=True))
        self.prev = rec["hash"]
        self.store.write(rec)
        return rec["hash"]

    def verify(self, records) -> bool:
        # 重算哈希链，任一条被改动都会导致后续校验失败
        prev = "0" * 64
        for r in records:
            body = {k: v for k, v in r.items() if k != "hash"}
            body["prev"] = prev
            if r["hash"] != self._digest(json.dumps(body, sort_keys=True)):
                return False
            prev = r["hash"]
        return True


# 分级采样：高风险全留，普通请求按比例抽样
def should_log(risk, sample_rate=0.05):
    import random
    return risk == "high" or random.random() < sample_rate
```

## 五、与其他技术对比

- 无日志 vs 全量明文日志：前者无法定责，后者制造隐私与合规风险，需折中治理。
- 日志（logging）vs 可观测性（observability）：日志是追溯的事实载体，metrics/tracing 关注运行健康，二者互补而非替代。
- 明文日志 vs 哈希链日志：明文易被篡改且泄露 PII，哈希链提供完整性证明。
- 中心化存储 vs 只追加对象存储：后者配合版本控制与写入权限收敛，抗篡改能力更强。

## 六、常见误区

- 「有日志就合规」：若记录明文 PII 或日志可被后台修改，反而制造新的合规与安全风险。
- 「全量永久留存」：不考虑成本与最小化原则，既浪费也扩大泄露面。
- 「只记输出不记输入」：无法还原越狱与提示注入路径；不记模型快照与提示模板版本，则无法定位问题来源。

## 七、与开源书·权威来源对应

- OWASP Top 10 for LLM Applications：敏感信息泄露等风险项明确要求控制训练数据与 PII 逸出。
- NIST AI RMF：将可追溯性（traceability）与文档化列为治理关键属性。
- 国内《生成式人工智能服务安全基本要求》：要求服务具备日志留痕与审计能力（以最新发布版本为准）。
- LangChain / LlamaIndex：提供回调与追踪机制，可作为结构化事件采集的参考实现。

## 九、演进与趋势

追溯体系正从「被动文本日志」演进为「结构化、隐私增强、可验证」的审计基础设施：用差分隐私或 k-匿名降低重识别风险；用 Merkle 树或外部公证增强不可篡改性；把日志与模型版本、数据集版本、提示模板版本联动，形成完整的数据—模型—输出溯源（provenance）；并逐步把合规审计接口标准化，便于监管与第三方核查。

## 十、小结

日志与追溯是责任认定、安全复盘与监管配合的锚点。做好脱敏、不可篡改与跨系统关联，才能做到「出事查得清、平时不泄露」。
