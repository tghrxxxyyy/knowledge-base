# 合规评测

> 对应 OWASP Top 10 for LLM Applications、NIST AI RMF 与国内《生成式人工智能服务安全基本要求》（具体条款以官方最新文档为准）。

## 一、背景与挑战

生成式大模型服务面向公众提供前，需要以可验证的方式证明其输出满足所在法域的法律法规与公序良俗。难点在于：合规不是单一指标，而是覆盖违法不良信息、拒答正确性、标识覆盖率、可追溯性、公平性等多维度的综合要求；监管细则、标准与行业口径会持续更新，难以用一次性测试固化；模型本身并不真正「理解」合规边界，越狱与提示注入可以绕过表层约束；此外评测本身存在刷分风险（Goodhart 定律），一旦固定题库被针对性优化，分数就不再代表真实安全水位。因此合规评测必须做到持续、可复现、可审计。

## 二、核心原理

合规评测本质是一套「风险维度 × 评测样本 × 判定规则 × 汇总口径」的工程体系：

1. 风险维度拆解：把监管要求拆成可判定的子类，如暴恐、色情、歧视、侵权、虚假信息、隐私泄露等，每类给出明确判定标准与示例。
2. 样本集构造：三类样本缺一不可——有害请求（期望拒答或安全改写）、边界请求（期望谨慎回答）、正常请求（用于测误拒率）。题目需难度分层并保留留出集，避免题库泄露后被刷分。
3. 自动化判定：规则命中、分类模型打分、LLM-as-judge 三者融合；判定结果需输出理由，便于复核。
4. 一致性校准：定期用人工标注集计算自动化判定与人类的一致性（如 Cohen's kappa），一致性下降说明裁判口径漂移。
5. 汇总与门禁：按维度加权汇总，设置发布门禁；每次模型/提示/策略变更触发回归。评测既是「打分」，更是「定位薄弱环节」的诊断工具：分数下降要能追溯到具体维度与样本。

## 三、形式化与数学基础

设风险维度集合为 $K$，第 $k$ 维的正确判定数为 $C_k$、样本数为 $N_k$，则该维度得分：

$$ s_k = \frac{C_k}{N_k} $$

整体合规得分按维度重要性加权：

$$ C_{\text{total}} = \sum_{k \in K} w_k \cdot s_k, \quad \sum_{k} w_k = 1 $$

拒答能力必须双向报告。应拒答召回与误拒率分别为：

$$ R = \frac{|\{\text{应拒且正确拒答}\}|}{|\{\text{应拒答}\}|}, \qquad F = \frac{|\{\text{应答但被拒}\}|}{|\{\text{正常请求}\}|} $$

由于样本量有限，得分应同时给出置信区间（小样本下可用 Wilson 区间），避免小样本上的高分假象。最终决策宜采用代价加权，而非单纯看通过率：

$$ \text{Cost} = \alpha \cdot N_{\text{miss}} + \beta \cdot N_{\text{false}} $$

其中 $\alpha$ 为漏放代价（通常远大于 $\beta$），调阈值等价于在该目标下选工作点。

## 四、代码实现

```python
# 合规评测：维度得分 + 拒答召回/误拒率 + Wilson 置信区间
from collections import defaultdict


def wilson_ci(hit, total, z=1.96):
    # 小样本下比正态近似更稳健的区间估计（Wilson 区间）
    p = hit / max(total, 1)
    denom = 1 + z * z / total
    center = (p + z * z / (2 * total)) / denom
    margin = z / denom * (p * (1 - p) / total + z * z / (4 * total * total)) ** 0.5
    return (max(0.0, center - margin), min(1.0, center + margin))


def run_compliance_eval(samples, generate, judge, weights):
    # samples: [{prompt, risk, expect}]，expect 取值 refuse / rewrite / answer
    stats = defaultdict(lambda: {"hit": 0, "total": 0})
    should_refuse = refuse_ok = 0
    normal = false_refuse = 0
    for s in samples:
        out = generate(s["prompt"])
        res = judge(s["prompt"], out, s["expect"])  # {correct: bool, refused: bool}
        stats[s["risk"]]["total"] += 1
        stats[s["risk"]]["hit"] += int(res["correct"])
        if s["expect"] == "refuse":
            should_refuse += 1
            refuse_ok += int(res["refused"] and res["correct"])
        else:
            normal += 1
            false_refuse += int(res["refused"])

    report = {
        "by_risk": {k: {"score": v["hit"] / v["total"],
                        "ci": wilson_ci(v["hit"], v["total"])} for k, v in stats.items()},
        "recall": refuse_ok / max(should_refuse, 1),      # 应拒答召回
        "false_refuse": false_refuse / max(normal, 1),    # 误拒率（可用性损伤）
    }
    report["total_score"] = sum(
        weights.get(k, 1.0) * v["score"] for k, v in report["by_risk"].items())
    return report


# 发布门禁：任一分项低于阈值即拦截上线（第二返回值为薄弱维度清单）
def gate(report, min_score=0.95, max_false_refuse=0.03):
    weak = [k for k, v in report["by_risk"].items() if v["score"] < min_score]
    return (not weak) and report["false_refuse"] <= max_false_refuse, weak
```

## 五、与其他技术对比

- 能力评测 vs 合规评测：前者衡量「有多聪明」，后者衡量「有多守规矩」，目标正交，需分别建设且不可互相替代。
- 单点安全测试 vs 体系化合规评测：单点测试容易被刷分，体系化强调维度覆盖、留出集与可审计流程。
- 自动化评测 vs 人工评测：自动化可规模化、可回归；人工处理边界语义与价值权衡；二者用一致性指标互相校准。自评快但缺乏独立视角，关键上线节点通常需要独立或可审计的评估流程。

## 六、常见误区

- 「自测过关即合规」：自评缺乏独立性，监管通常要求可审计流程与留存证据。
- 「只报通过率」：不披露误拒率会掩盖可用性损伤，必须双向报告。
- 「一次评测定终身」：模型迭代、越狱新手法与监管更新都会改变合规状态。
- 「题库固定不变」：固定题库会被针对性优化，必须定期轮换并保留未公开留出集；加权总分还会掩盖个别维度的严重短板，门禁应按分项设置。

## 七、与开源书·权威来源对应

- OWASP Top 10 for LLM Applications：列出 LLM 应用面临的安全与合规风险类别与防护要点。
- NIST AI Risk Management Framework：把可测量性、可追溯性列为治理关键属性。
- 国内《生成式人工智能服务安全基本要求》与 EleutherAI lm-evaluation-harness、llm-course（mlabonne）：分别提供官方评测维度参考与可复用的评测框架、基准索引（法规以最新发布版本为准）。

## 九、演进与趋势

合规评测正从「静态红队集 + 人工报告」走向「自动化红队生成 + 持续回归 + 监管对齐」：用强模型自动构造对抗样本扩大覆盖；把合规指标纳入 CI/CD 作为发布门禁；评测对象从纯文本扩展到图文音视频与 Agent 工具调用链路；同时探索用策略即代码（policy-as-code）表达合规规则，使判定逻辑可版本化、可审计。

## 十、小结

合规评测把抽象的「安全合规」转化为可量化、可回归、可审计的维度得分与证据链，是生成式 AI 服务上线的前提，也是产品迭代中必须长期守护的底线。
