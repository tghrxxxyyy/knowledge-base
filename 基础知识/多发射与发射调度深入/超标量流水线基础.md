# 超标量流水线基础

> 对应 Hennessy & Patterson《Computer Architecture》第 3、4 章（ILP 与超标量）/ Bryant & O'Hallaron《CSAPP》第 4 章 / Fisher 1983 "Very Long Instruction Word Architectures and the ELI-512"。

## 一、背景与挑战

经典五级流水线每周期只能取指、译码、发射各一条指令，IPC 上界为 1。但硬件资源天然可以并行：多个 ALU、访存单元与浮点单元同时空闲，指令流中也存在大量互不相关的指令。**超标量（superscalar）** 就是让前端每周期取指并发射多条指令，把 IPC 推向 2、4 乃至更高。

难点不在「多放几个 ALU」，而在三个配套问题：**取指带宽**（变长指令集在解码前不知指令边界，需要长度解码器并行工作）、**相关检测**（多条指令同拍发射前必须两两判断 RAW/WAR/WAW 与结构相关，检测逻辑随宽度平方级增长）、**动态与静态的分工**（哪些并行性由硬件在运行期挖掘，哪些由编译器显式给出）。

## 二、核心原理

超标量核心的前端到后端流水大致为：取指（多路）→ 长度解码/预译码 → 译码 → 重命名 → 发射队列 → 功能单元（多组）→ 提交。每一级都可能成为宽度限制：

- **取指**：受 I-cache 行宽与分支目标对齐影响，跨越缓存行边界的取指块会被拆成两次访问。
- **解码**：x86 的典型做法是「每周期若干条指令，且其中至多一条复杂指令（可微码化）」，这个不对称约束直接限制实际发射宽度。uop cache（译码结果缓存）绕开长度解码，显著提高可稳定发射的 uop 数。
- **宏融合/微融合**：比较加分支可融合成一个 uop（宏融合），加载加算术可融合（微融合），减少 uop 数从而缓解宽度压力。
- **重命名与发射**：宽度受物理寄存器分配带宽与发射队列端口数限制。
- **执行与提交**：受功能单元数量、端口配置与 ROB 提交宽度限制；访存宽度通常最窄。

这些限制叠加的结果是**实际 IPC 远低于发射宽度**：一个 4 宽的核心在真实负载上长期处于 1~2 的区间是常态。

## 三、形式化与数学基础

理想情况下，超标量核心的 IPC 上界为

$$
\text{IPC} \le \min\left(W_{fetch},\ W_{decode},\ W_{rename},\ W_{issue},\ W_{commit},\ \text{ILP}_{\text{prog}}\right)
$$

其中 $\text{ILP}_{\text{prog}}$ 是程序固有可并行度，由数据依赖链决定。用依赖图的关键路径长度 $L_{\text{crit}}$ 与总指令数 $N$ 可给出上界 $\text{IPC} \le N / L_{\text{crit}}$：若一段代码有 1000 条指令但关键路径 500 拍，则 IPC 不超过 2，无论发射宽度多大。

再考虑以 uop 为单位的宽度约束。设平均每条指令被解码为 $\mu$ 个 uop，则指令级 IPC 为

$$
\text{IPC} = \frac{W_{uop}}{\mu}
$$

这是理解「CISC 的重命名宽度常按 uop 计」的关键：$\mu$ 越大等效指令吞吐越低，而宏融合与微融合本质上就是在降低 $\mu$。若前端每周期只能提供 $W_f$ 个 uop、后端能执行 $W_b$ 个，而某负载前端受限的比例为 $\beta$，则即使把后端加宽到无穷，加速比也只有 $1/(\beta/W_f)$——这解释了「只加 ALU 不扩前端」为何常常收效甚微。

## 四、代码实现

```c
/* 用依赖图估计 IPC 上界：关键路径长度 vs 总指令数 */
#include <stdio.h>
#define N 9

typedef struct { int lat, p1, p2; } insn_t;   /* 延迟与前驱（最多两个） */

/* 计算每条指令的最早完成时刻，最大值即关键路径长度 */
int critical_path(const insn_t *g, int n, int *finish) {
    int best = 0;
    for (int i = 0; i < n; i++) {
        int start = 0;
        if (g[i].p1 >= 0 && finish[g[i].p1] > start) start = finish[g[i].p1];
        if (g[i].p2 >= 0 && finish[g[i].p2] > start) start = finish[g[i].p2];
        finish[i] = start + g[i].lat;
        if (finish[i] > best) best = finish[i];
    }
    return best;
}

int main(void) {
    /* 前 5 条构成串行依赖链（含一次 4 拍加载），后 3 条彼此独立 */
    insn_t g[N] = {
        {4, -1, -1}, {1, 0, -1}, {1, 1, -1}, {1, 2, -1}, {1, 3, -1},
        {3, -1, -1}, {3, -1, -1}, {3, -1, -1}, {3, -1, -1}
    };
    int finish[N];
    int L = critical_path(g, N, finish);
    printf("insns=%d crit_path=%d cycles, IPC upper bound=%.2f\n",
           N, L, (double)N / L);
    return 0;
}
```

输出提示：关键路径为 9 拍、IPC 上界 1.0，即便硬件宽度为 4 也无法超过。若把 4 拍加载缩短或打断依赖链，上界才会上升——这正是「先改算法与数据布局、再谈微架构」的量化依据。

## 五、与其他技术对比

| 架构 | 并行性来源 | 硬件复杂度 | 二进制可移植性 | 典型 IPC 特征 |
| --- | --- | --- | --- | --- |
| 标量流水 | 流水线重叠 | 低 | 好 | IPC ≤ 1 |
| 超标量（按序） | 硬件多发射 + 编译器排序 | 中 | 好 | 受限于相关，通常 1~2 |
| 超标量（乱序） | 硬件多发射 + 动态调度 | 高 | 好 | 可显著高于 1，受窗口限制 |
| VLIW / EPIC | 编译器显式打包 | 低（硬件） | 差（绑定微架构） | 调度成功时高，失败时崩塌 |
| SMT | 多线程共享发射宽度 | 中 | 好 | 提高总吞吐，单线程略降 |
| SIMD/向量 | 数据级并行 | 低 | 好 | 数据并行负载上远超标量 |

## 六、常见误区

- 「发射宽度等于 IPC」：相关、缺失、端口与前端带宽会把实际 IPC 拉低到远小于宽度。
- 「超标量一定快于标量」：宽度小、命中率低的负载上，前端复杂度开销可能抵消收益。
- 「只关注后端而忽略取指与解码」：x86 变长指令的解码约束常是实际宽度的真实上限，uop cache 命中率比 ALU 数量更关键。
- 「VLIW 是过时技术」：在延迟固定、编译器可完全掌握的领域（DSP、网络处理、加速器）它依然高效。
- 「提高 IPC 就等于提高性能」：还需看频率、功耗与内存带宽，IPC 与频率常相互制约。

## 八、面试题

1. **超标量与流水线宽度有什么区别？** 要点：流水线宽度是同时处于不同阶段的指令数（重叠），超标量是每周期**发射**多条指令的能力（并行）。
2. **限制 ILP 的主要因素有哪些？** 要点：真数据依赖链（关键路径）、名字相关（靠重命名缓解）、分支、结构相关与内存延迟。
3. **为什么 x86 的实际发射宽度常低于标称宽度？** 要点：变长指令需长度解码，解码规则含「每周期至多一条复杂指令」等不对称约束；uop cache 命中可绕开该限制。
4. **宏融合与微融合的作用？** 要点：把多条指令合并成更少 uop，降低平均 uop 数 $\mu$，在固定 uop 宽度下提高指令吞吐。
5. **为什么先优化算法再谈超标量？** 要点：关键路径长度与 uop 数由算法与数据布局决定，硬件只能在这些上界之内发挥作用。

## 九、演进与趋势

多发射宽度从 2 路走向 4~6 路后在通用核心上趋于稳定，因为从相关性检测到寄存器堆端口再到功耗，宽度带来的收益被成本迅速吞掉。提升转向三处：前端（uop cache、融合、更好的预测与解耦取指）、调度（更大窗口与分布式队列）、并行层次（SMT 提高利用率、SIMD 扩大数据并行、多核替代单核加宽）。异构计算把「延迟容忍型」并行交给 GPU 或专用加速器，使超标量核心更专注于单线程延迟敏感的通用代码。

## 十、小结

超标量通过每周期多发射提升 ILP，但真正的上界由**程序固有并行度、前端取指解码带宽、相关性检测能力与资源端口**共同决定，实际 IPC 往往只有发射宽度的一半甚至更低。判断一场优化是否值得，先算关键路径与 uop 数，再看硬件宽度是否真的成为约束。
