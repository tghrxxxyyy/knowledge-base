# 乱序发射与寄存器重命名

> 对应 Hennessy & Patterson《Computer Architecture》ILP 章节 / Tomasulo 1967 / Smith & Pleszkun 1988 "Implementing Precise Interrupts in Pipelined Processors" / Intel SDM 与 ARM ARM 的寄存器模型。

## 一、背景与挑战

程序里存在大量**名字相关**（伪相关）：两条指令写同一架构寄存器构成 WAW，一写一读同一寄存器构成 WAR。它们不是数据依赖——值并没有真正流动——只因复用了有限的 16/32 个架构寄存器名，按序发射的处理器就必须让它们串行。

在窗口很大的乱序核心里这个约束是致命的：即使前后指令毫无关系，也会被 WAR/WAW 卡住，可提取的 ILP 被寄存器的**名字**而非数据流限制。第二个挑战是精确异常：乱序完成意味着结果到达顺序与程序序不同，一旦中间指令触发异常或分支误预测，必须能把状态回滚到「该指令之前」的一致快照。

## 二、核心原理

寄存器重命名的核心是**把名字与存储解耦**：架构寄存器（逻辑名）映射到物理寄存器堆（PRF，通常上百项）。每条写架构寄存器的指令分配一个新物理寄存器，之后所有读该架构寄存器的指令都引用这个新物理寄存器。于是：

- **WAR 消失**：后来的写用新物理寄存器，不会覆盖前面读还在用的旧物理寄存器。
- **WAW 消失**：两个写各占不同物理寄存器，只有最后提交者成为架构可见值。
- **RAW 保留**：它是真实数据流，通过物理寄存器的生产者—消费者关系维持。

核心数据结构是**重命名映射表**（RAT），每项是一个物理寄存器编号：`RAT[逻辑寄存器] -> 物理寄存器`。两条实现路线：

1. **PRF + RAT（显式重命名）**：物理寄存器堆是唯一真值来源，架构寄存器只是名字映射，提交时更新「架构可见映射」。
2. **ROB 内重命名**：以 ROB 表项编号充当物理寄存器号，值随指令保存在 ROB 中，提交时写回架构寄存器堆；省掉独立 PRF，但读操作数需从 ROB 前递。

恢复机制有三种流派：**快照（检查点）**分支处保存整个 RAT 副本；**历史缓冲**记录被覆盖的映射以便回滚；**走查**从 ROB 重建映射，慢但存储最省。现代高频核心多用「每分支一个检查点 + 提交时释放」的混合方案。

另有两个正交收益：**MOV 消除**（寄存器移动在重命名阶段直接把目标映射到源物理寄存器，不产生微操作）与**零惯用语消除**（如 `xor r1, r1`），二者都是实测中显著的加速来源。

## 三、形式化与数学基础

架构寄存器集合 $L$（$|L| = 32$），物理寄存器集合 $P$（$|P| \gg |L|$），重命名是满射 $\rho: L \to P$。指令写下 $\ell$ 时被赋予新物理寄存器 $p_{new}$，并令 $\rho(\ell) \leftarrow p_{new}$；旧值只有在**所有**读过它的指令都已提交后才可回收。

物理寄存器数量的下界由在途指令数决定：若窗口为 $W$、每周期最多提交 $n$ 个架构寄存器，则

$$
|P| \gtrsim |L| + W_{\text{inflight}}
$$

即「架构寄存器数 + 窗口内未提交的写操作数」。这解释了为什么窗口扩大必然要求 PRF 扩大——否则空闲池耗尽会引发**重命名停顿**，此时窗口未满也无法取新指令。

寄存器生命周期可形式化为区间 $[alloc, free]$：$alloc$ 是重命名周期，$free$ 是「最后一个消费者提交且它不再是架构可见映射」的周期。活跃物理寄存器数即这些区间的最大重叠数，也就是所需的 PRF 容量。

## 四、代码实现

```c
/* 简化重命名器：空闲池 + 映射表 + 分支检查点 */
#include <stdint.h>
#include <string.h>
#define N_LOGICAL 32
#define N_PHYS    192
#define N_CKPT    8

static int16_t free_pool[N_PHYS];
static int     free_top;
static int16_t arch_rat[N_LOGICAL];      /* 已提交的架构可见映射 */
static int16_t spec_rat[N_LOGICAL];      /* 推测中的映射 */
static int16_t ckpt[N_CKPT][N_LOGICAL];

static int16_t alloc_phys(void) {
    return free_top > 0 ? free_pool[--free_top] : -1;   /* -1：空闲池耗尽 */
}

/* 为一条写逻辑寄存器 rd 的指令做重命名；失败返回 -1（重命名停顿） */
int16_t rename_dst(int rd) {
    if (rd < 0) return 0;                /* 无目标寄存器（如 store） */
    int16_t p = alloc_phys();
    if (p < 0) return -1;
    spec_rat[rd] = p;                    /* 新映射，WAR/WAW 随之消失 */
    return p;
}

static void make_checkpoint(int slot) {  /* 分支处保存快照 */
    memcpy(ckpt[slot], spec_rat, sizeof(spec_rat));
}

static void restore_checkpoint(int slot) {  /* 误预测时回滚映射 */
    memcpy(spec_rat, ckpt[slot], sizeof(spec_rat));
    /* 实际还需释放错误路径上已分配的物理寄存器，否则永久泄漏 */
}

static void commit_mapping(int rd) {     /* 提交时推进映射并回收旧物理寄存器 */
    if (rd < 0) return;
    int16_t old = arch_rat[rd];
    arch_rat[rd] = spec_rat[rd];
    if (old >= 0) free_pool[free_top++] = old;
}
```

实现要点：物理寄存器编号位宽要覆盖 PRF 容量；空闲池恢复必须与检查点配合；MOV 消除需同时维护「该映射的来源」信息，以便恢复时重建正确标签。

## 五、与其他技术对比

| 方案 | 消除 WAR | 消除 WAW | 值存放位置 | 恢复机制 | 代表 |
| --- | --- | --- | --- | --- | --- |
| 记分牌 | 部分（靠等待） | 否 | 架构寄存器堆 | 无需 | CDC 6600 |
| Tomasulo（保留站） | 是 | 是 | 保留站 + 寄存器 | 需附加机制 | IBM 360/91 |
| PRF + RAT | 是 | 是 | 物理寄存器堆 | 检查点/历史缓冲 | 现代主流 |
| ROB 内重命名 | 是 | 是 | ROB 表项 | ROB 天然有序 | 部分低功耗实现 |

与「直接增加架构寄存器数量」相比：后者需改指令编码与 ABI、破坏兼容，而重命名是纯微架构的、对软件透明。

## 六、常见误区

- 「重命名改变程序语义」：它只改实现映射，任何时刻架构可见值都与顺序执行一致。
- 「物理寄存器无限」：PRF 有限，空闲池耗尽引发重命名停顿，常被计入前端或后端空闲。
- 「重命名能消除所有停顿」：RAW 与结构相关（功能单元、端口）依然存在。
- 「MOV 消除一定无损」：被消除的 MOV 不写物理寄存器，若恢复逻辑依赖它作为值来源，需额外记录来源映射。
- 「重命名只影响整数」：向量/浮点寄存器同样重命名，且位宽大、端口多，对 PRF 面积与带宽压力更大。

## 八、面试题

1. **重命名如何消除 WAR？** 要点：后来的写分配新物理寄存器，不再覆盖前面读还在使用的旧物理寄存器。
2. **物理寄存器何时回收？** 要点：当它不再是架构可见映射且所有读过它的在途指令都已提交后，归还空闲池。
3. **有 Tomasulo 为什么还需要 ROB？** 要点：Tomasulo 允许乱序完成，但精确异常与按序提交需要 ROB 提供程序序与回滚边界。
4. **空闲池耗尽会造成什么？** 要点：重命名停顿——前端无法取新指令，窗口利用率下降，性能计数表现为前端空闲或后端停顿。
5. **MOV 消除为何能显著提速？** 要点：寄存器移动在重命名阶段被消解为零微操作，减轻执行与提交压力。

## 九、演进与趋势

趋势是把重命名从集中式大表推向**分布式与分段**：按整数/浮点/向量分区，或用「架构映射 + 重排缓冲」的混合方案降低索引延迟与端口冲突。值推测方向出现内存重命名（store-to-load 值转发）与基于值预测的重命名。安全约束带来新考量：重命名状态属微架构状态，误预测路径上的映射残留可能被侧信道利用，恢复必须彻底回滚。长期看，重命名是「窗口继续扩大」路线的主要面积与延迟瓶颈之一。

## 十、小结

寄存器重命名把架构寄存器的名字与物理存储解耦，用一张映射表和一块更大的物理寄存器堆一次性消除 WAR 与 WAW，是乱序执行的支柱。关键约束是空闲池容量与恢复机制：池太小会重命名停顿，恢复太慢会让误预测代价失控。
