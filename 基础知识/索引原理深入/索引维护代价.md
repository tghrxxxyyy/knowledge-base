# 索引维护代价

> 对应 Silberschatz《Database System Concepts》11 章，以及 DDIA 索引维护讨论。

## 一、背景与挑战
索引提升读，却在每个 INSERT/UPDATE/DELETE 上增加写放大：每多一个索引，写路径就多一次 B+ 树修改。过多索引拖慢写入并占空间。

## 二、核心原理
写操作对每行触发：聚簇索引更新 + 每个二级索引更新（可能分裂页、维护可见性）。删除产生墓碑与版本链。统计信息也需周期刷新。

## 三、形式化 / 数学基础
写代价 $W = W_{clu} + \sum_i W_{idx_i}$。每个 B+ 树插入期望 $O(\log_b N)$ 页访问，并可能触发页分裂（额外 I/O）。索引数 $k$ 使写放大近似线性于 $k$。

## 四、代码实现
```sql
-- 写多读少表，控制索引数量
CREATE TABLE events (
  id BIGINT PRIMARY KEY,
  uid BIGINT,
  ts TIMESTAMP
  -- 仅建必需索引，避免每个查询列都建
);
```

## 五、与其他技术对比
| 索引数 | 读 | 写 | 空间 |
|--------|----|----|------|
| 少 | 慢 | 快 | 小 |
| 多 | 快 | 慢 | 大 |

## 六、常见误区
1. 索引零成本——每个写都付维护费。
2. 删数据索引自动瘦身——通常仅标记，需重建。
3. 只读副本也要同样索引——可按查询模式差异化。

## 九、演进与趋势
列式/列存用不同索引策略；增量统计与在线重建（如 pg_repack）降低维护窗口。

## 十、小结
索引维护代价随数量线性增长，设计时应按真实读写比裁剪，避免无谓写放大。
