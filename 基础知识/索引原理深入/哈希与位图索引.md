# 哈希与位图索引

> 对应 Silberschatz《Database System Concepts》11.3 Hash Index 与 11.5 Bitmap Index，以及数据仓库索引实践。

## 一、背景与挑战
B+ 树擅长范围查询但点查有 $\log$ 开销；低基数列用 B+ 树效率低。哈希索引优化点查，位图索引优化多列低基数的 OLAP 过滤。

## 二、核心原理
哈希索引用哈希函数把键映射到桶，点查 $O(1)$ 但无序、不支持范围。位图索引为每个不同值维护一个 bitmap，多条件 AND/OR 用位运算（与/或）快速求交，适合只读或低频更新的数仓。

## 三、形式化 / 数学基础
哈希：定位 $h(k) \bmod B$ 桶。位图查询：`result = bitmap[v1] AND bitmap[v2]`，位运算代价 $O(N_{rows}/word\_size)$。位图适合 $NDV \ll N$ 的列。

## 四、代码实现
```sql
-- PostgreSQL 位图索引（实际为建 btree 后自动位图扫描，或 BRIN）
CREATE INDEX idx_gender ON people USING bitmap (gender);  -- 示意
SELECT * FROM people WHERE gender='F' AND city='BJ';      -- 位图 AND
```

## 五、与其他技术对比
| 索引 | 点查 | 范围 | 适合场景 |
|------|------|------|----------|
| B+ 树 | O(log) | 优 | OLTP |
| 哈希 | O(1) | 无 | 点查 |
| 位图 | 中 | 位运算 | OLAP 低基 |

## 六、常见误区
1. 哈希索引能范围查——不能。
2. 位图索引适合高基数列——位数组巨大且更新昂贵。
3. 位图索引更新快——位翻转代价高，适合读多写少。

## 九、演进与趋势
BRIN（块范围索引）以极小空间服务有序大表的粗过滤；近似位图与压缩位图（Roaring Bitmap）在 OLAP 普及。

## 十、小结
哈希索引换点查速度、位图索引换多低基列交并效率；按读写特征与基数选型。
