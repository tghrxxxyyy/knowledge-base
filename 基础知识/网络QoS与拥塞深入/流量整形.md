# 流量整形

> 对应 Kurose & Ross《Computer Networking: A Top-Down Approach》流量整形与管制的相关章节；RFC 2475（DiffServ 架构中的 traffic conditioning）；RFC 2697（srTCM）/ RFC 2698（trTCM）。

## 一、背景与挑战
上游应用的发送天然是突发的：一次请求可能触发一次批量写入，一次文件传输会以内存拷贝的速度涌向网卡。若把突发直接交给网络，会同时伤害三方：中间的浅缓冲交换机会丢弃突发尾部，接收端因乱序与重传放慢确认，本机发送队列则反复在「空」与「满」之间切换，时延抖动显著。

流量整形（traffic shaping）的目标是把发送速率约束在一条目标曲线附近，把突发「削峰填谷」：超出即时额度的部分不丢弃，而是排队延迟发出。它的对立面是管制（policing）：超规即丢（或降级重标记）。两者常被混用，但在缓冲与语义上完全不同。

## 二、核心原理
整形位于出口，拥有发送队列，因此可以实现「延迟而不丢」；管制通常位于入口或信任边界，设备侧无法为每个流提供足够缓冲，因此选择丢包或降级标记。两者共享同一套度量模型——令牌桶或漏桶（详见「令牌桶与漏桶」）。

整形的关键实现要素有三个：其一，速率曲线由桶参数决定（平均速率、突发额度）；其二，队列必须有界，否则整形会退化成无界缓冲并制造 bufferbloat；其三，调度必须"守时"——不能在某一刻把积攒的额度一次性发出去，否则整形退化为突发透传。

在 Linux 中，整形由排队规则（qdisc）承担，典型的令牌桶整形器是 `tbf`，分层限速用 `htb`（层级令牌桶，支持子类借用父类未用额度）。需要注意的是 qdisc 只作用于**出口**：入口方向的整形需要借助 IFB 等中间设备把流量重定向到一个虚拟出口再整形，否则只能做管制（丢包）。

## 三、形式化与数学基础
令牌桶对发送量施加的约束可以写成：对任意时间区间 $[t, t+\tau]$，累计发送字节数 $A$ 满足
$$A(\tau) \le r\cdot\tau + b$$
其中 $r$ 为令牌生成速率（平均速率上界），$b$ 为桶容量（突发额度）。直观解释：区间内可用令牌不超过「初始最多 $b$ 个」加上「期间新生成 $r\tau$ 个」。

漏桶视角下队列动态（入速率 $in(t)$、漏出速率 $r$、容量 $b$）：
$$\frac{dQ}{dt} = \begin{cases} in(t) - r, & Q > 0 \\ \max(0,\, in(t) - r), & Q = 0 \end{cases}, \qquad \text{若 } Q > b \text{ 则丢弃}$$
整形引入的排队时延由当前积压决定：
$$d_{queue} \approx \frac{Q(t)}{r}$$
一次大小 $B$ 的突发在最坏情况下被摊开的时间为
$$t_{spread} \approx \frac{B - b}{r} \quad (B > b)$$
这正是「整形以增加时延换取平滑」的量化表达：突发越大、桶越小，等待越久。

## 四、代码实现
用 `tc` 做出口整形：先限速，再叠加一个分层结构以支持优先级。
```bash
# 出口整形：平均 10mbit、突发 32kbit、队列延迟上限 50ms
tc qdisc add dev eth0 root handle 1: tbf rate 10mbit burst 32kbit latency 50ms

# 分层限速：父类保证 100mbit 上限 1gbit，子类按权重借用
tc qdisc add dev eth0 root handle 1: htb default 30
tc class add dev eth0 parent 1:  classid 1:1  htb rate 100mbit ceil 1gbit
tc class add dev eth0 parent 1:1 classid 1:10 htb rate 50mbit  ceil 100mbit prio 1
tc class add dev eth0 parent 1:1 classid 1:20 htb rate 30mbit  ceil 100mbit prio 2
tc filter add dev eth0 protocol ip parent 1:0 prio 1 u32 \
  match ip dport 443 0xffff flowid 1:10
```
用户态实现整形的核心是「按额度睡眠」而不是「立刻发完」：
```python
import time

class Shaper:
    # 令牌桶整形：先凑额度再发送，超出部分排队等待
    def __init__(self, rate_bps, burst_bytes):
        self.rate, self.burst = rate_bps, burst_bytes
        self.tokens, self.ts = burst_bytes, time.monotonic()

    def send(self, nbytes):
        while True:
            now = time.monotonic()
            self.tokens = min(self.burst, self.tokens + (now - self.ts) * self.rate)
            self.ts = now
            if self.tokens >= nbytes:
                self.tokens -= nbytes
                return 0.0                     # 无需等待
            deficit = nbytes - self.tokens
            time.sleep(deficit / self.rate)    # 关键：延迟而非丢弃
```

## 五、与其他技术对比
| 维度 | 整形 Shaping | 管制 Policing |
| --- | --- | --- |
| 超规处理 | 缓存并延迟发送 | 丢弃或降级重标记 |
| 缓冲需求 | 需要（出口队列） | 不需要 |
| 对上层影响 | 增加排队时延、不丢包 | 引发重传与吞吐抖动 |
| 部署位置 | 出口（发送侧） | 入口、边界、互连点 |
| 典型工具 | `tc tbf`、`tc htb`、CAKE | `tc policer`、边界标记器 |

| 模型 | 突发语义 | 输出特性 | 典型用途 |
| --- | --- | --- | --- |
| 令牌桶 | 允许突发至桶容量 | 平均受限、瞬时可变 | 限速 + 突发 |
| 漏桶 | 不允许突发（超出即丢/排队） | 严格平滑 | 恒定码率输出、整形出口 |
| 分层令牌桶 | 子类可借用父类额度 | 分层保证 + 统计复用 | 多租户限速 |

## 六、常见误区
- 认为整形与管制是一回事。前者缓存并延迟，后者丢弃或降级，对上层协议的影响完全不同。
- 认为整形不会丢包。队列是有限的，桶与队列同时溢出时仍然会丢；整形只是把「丢」推迟到更极端的情况。
- 认为整形能提升吞吐。它不增加链路容量，只是重新分配发送时刻；在拥塞链路上甚至可能因为增加时延而降低有效吞吐。
- 忽略突发参数的作用。只设置 rate 而不理解 burst/latency，实际曲线会偏离预期：桶太小则平滑过度、吞吐上不去，桶太大则几乎不整形。
- 以为 `tc` 能对入口流量整形。出口 qdisc 才是整形，入口要先重定向到 IFB 才能整形，否则实际执行的是管制。
- 在浅缓冲链路上做激进整形。端到端时延由「本地排队 + 链路排队」共同决定，本地整形引入的时延可能抵消其对上游丢包的缓解。

## 七、与开源书·权威来源对应
- Kurose & Ross《Computer Networking: A Top-Down Approach》：多媒体网络章节给出漏桶/令牌桶整形的经典图示与公式，是 shaping 与 policing 区分的标准来源。
- RFC 2475：DiffServ 架构中定义 traffic conditioning（计量、标记、整形、丢弃）的组成，说明整形在网络边界的位置。
- RFC 2697（srTCM）与 RFC 2698（trTCM）：单速率与双速率三色标记器的标准定义，是令牌桶参数语义的权威依据。
- Tanenbaum《Computer Networks》：QoS 与拥塞控制章节讨论漏桶、令牌桶与调度对突发的影响。
- Stevens《TCP/IP Illustrated》第 1 卷：拥塞窗口与发送队列行为，帮助理解整形为何能改善重传与抖动表现。

## 八、面试题
1. 整形与管制的区别？要点：整形缓存并延迟发送（出口、不丢或推迟丢），管制丢弃或降级（入口、需要即时决策）。
2. 令牌桶参数如何影响实际曲线？要点：rate 决定平均速率上界，burst 决定可瞬时发送的额度，latency 约束队列停留时间。
3. 为什么整形会增加时延？要点：为平滑突发而排队，排队时延约等于积压量除以整形速率。
4. 为什么 `tc` 只能整出口流量？要点：只有发送侧具备可控队列与时序，入口侧无法决定上游发送时刻，只能丢弃或标记。
5. HTB 相比单一令牌桶解决了什么？要点：分层额度与借用机制，在保证各级最小值的同时允许统计复用空闲带宽。
6. 整形与 AQM 如何配合？要点：AQM 管理队列的丢弃时机以控制时延，整形控制入队/发送速率；两者共同决定时延与丢包分布。

## 九、演进与趋势
方向是从「固定参数限速」走向「时延友好的主动队列管理 + 整形」的组合：AQM（如 CoDel）控制驻留时延，FQ-CoDel/CAKE 则在队列层面做公平调度与整形，抑制 bufferbloat。云网络侧强调分层限速与容器粒度配额（cgroup 与 qdisc 结合）、以及基于可编程数据面的精细计量。与 L4S 的配合让整形不再需要依赖大缓冲来吸收突发。具体实现与参数以官方最新文档为准。

## 十、小结
流量整形用出口队列与令牌桶把突发改造成符合合约的平滑流，代价是排队时延。它与管制互补：整形用于自己能控制的发送侧，管制用于无法控制上游的入口与边界。工程上的关键不是「限到多少」，而是速率、突发额度与队列时延三者的联合设定。
