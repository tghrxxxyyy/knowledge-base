# 令牌桶与漏桶

> 对应 RFC 2697（srTCM：单速率三色标记器）；RFC 2698（trTCM：双速率三色标记器）；RFC 4115（面向 DiffServ 的三色标记器）；Kurose & Ross《Computer Networking: A Top-Down Approach》流量整形章节。

## 一、背景与挑战
限速看起来很简单：说好 10Mbps 就发 10Mbps。但真实流量是突发的——一次内存拷贝会把几十个包几乎同时推入网卡队列，一次批量写入产生毫秒级速率尖峰。严格按平均速率逐包发送会无谓丢弃突发；完全放任突发，则下游的浅缓冲交换机会替你丢。

因此需要一个既能约束长期平均速率、又能容忍合理突发的模型。令牌桶与漏桶是两种互补的经典答案：前者允许突发但约束平均，后者严格平滑输出。理解它们的差别，本质是理解「突发在哪里被吸收、被谁吸收」。

## 二、核心原理
**令牌桶（token bucket）**：桶以恒定速率 $r$ 累积令牌、容量为 $b$。每个包需取走与自身字节数相等的令牌才能发送。桶空时包要么等待（整形语义），要么被丢弃/降级（管制语义）。平均速率不超过 $r$，瞬时最多发送 $b$ 字节的突发。

**漏桶（leaky bucket）**：输入可突发进入缓存，输出以恒定速率 $r$ 漏出，缓存容量 $b$，溢出则丢弃或标记。输出曲线严格平滑，没有任何突发。

关键差别在于突发吸收器是谁：令牌桶靠**令牌本身**（允许发送时刻的快慢不等），漏桶靠**队列**（把突发摊到时间轴）。因此令牌桶适合「限速但保留脉冲」的业务，漏桶适合「必须恒定输出」的业务。

**三色标记器**把令牌桶推广为合规性分级。srTCM 用两个桶（CBS 承诺突发、EBS 超额突发）与一个速率（CIR），把包分为绿/黄/红；trTCM 用两个速率（PIR 峰值、CIR 承诺）与两个桶（PBS、CBS），先检查峰值再检查承诺。颜色决定后续丢弃与调度的优先级。

## 三、形式化与数学基础
令牌桶约束（最核心的式子）：对任意区间 $[t, t+\tau]$，累计发送字节数 $A$ 满足
$$A(\tau) \le r\,\tau + b$$
推导要点：区间内可用令牌不超过「起始时桶中最多 $b$ 个」加上「区间内新生成 $r\tau$ 个」。这解释了为何「长期平均 $\le r$」与「瞬时突发 $\le b$」能同时成立。

桶的微分形式（$T(t)$ 为令牌数）：
$$\frac{dT}{dt} = r, \qquad 0 \le T(t) \le b, \qquad \text{发包时 } T \mathrel{-}= L_{pkt}$$
漏桶队列动态（入速率 $in(t)$、漏出速率 $r$、容量 $b$、队列长 $Q(t)$）：
$$\frac{dQ}{dt} = \begin{cases} in(t) - r, & Q(t) > 0 \\ \max(0,\, in(t)-r), & Q(t) = 0 \end{cases}, \qquad Q(t) > b \Rightarrow \text{溢出丢弃/标记}$$
srTCM 着色规则（$C$ 与 $E$ 为两桶剩余令牌、$L$ 为包长）：若 $C \ge L$ 置绿并 $C \mathrel{-}= L$；否则若 $E \ge L$ 置黄并 $E \mathrel{-}= L$；否则置红。trTCM 先判峰值桶：$P < L$ 直接置红，再判承诺桶定绿/黄。

## 四、代码实现
两种模型的用户态实现。区别很直观：令牌桶在额度不足时等待或拒绝，漏桶总是以固定节奏输出。
```python
import time
from collections import deque

class TokenBucket:
    # 限平均、容突发：按经过时间补桶，避免定时器累积误差
    def __init__(self, rate_bps, burst_bytes):
        self.rate, self.cap = rate_bps, burst_bytes
        self.tokens, self.ts = burst_bytes, time.monotonic()

    def try_take(self, nbytes):
        now = time.monotonic()
        self.tokens = min(self.cap, self.tokens + (now - self.ts) * self.rate)
        self.ts = now
        if self.tokens >= nbytes:
            self.tokens -= nbytes
            return True
        return False

    def take_blocking(self, nbytes):
        while not self.try_take(nbytes):
            time.sleep(1e-4)               # 整形：排队等待额度

class LeakyBucket:
    # 严格恒定输出：积压的包按固定节奏漏出，超容量直接丢
    def __init__(self, rate_bps, capacity_bytes):
        self.rate, self.cap = rate_bps, capacity_bytes
        self.q, self.bytes_queued, self.next_time = deque(), 0, time.monotonic()

    def push(self, pkt):
        if self.bytes_queued + len(pkt) > self.cap:
            return False                    # 溢出丢弃
        self.q.append(pkt)
        self.bytes_queued += len(pkt)
        return True

    def pop(self):
        if not self.q:
            return None
        now = time.monotonic()
        if now < self.next_time:
            time.sleep(self.next_time - now)   # 关键：把突发摊到时间轴
        pkt = self.q.popleft()
        self.bytes_queued -= len(pkt)
        self.next_time = max(now, self.next_time) + len(pkt) / self.rate
        return pkt
```
要验证不变量 $A(\tau) \le r\tau + b$，只需记录每次发送的 (时间, 字节数)，对每个窗口起点累加发送量，检查「累计 $-\ (r \cdot \text{窗口} + b)$」是否始终不大于 0。

## 五、与其他技术对比
| 维度 | 令牌桶 | 漏桶 | 固定窗口计数 |
| --- | --- | --- | --- |
| 突发语义 | 允许突发至桶容量 | 不允许突发（平滑输出） | 窗口内可一次用尽 |
| 平均速率约束 | 严格 $r$ | 严格 $r$ | 跨窗口可翻倍 |
| 状态量 | 令牌数 + 时间戳 | 队列 + 时间戳 | 计数器 |
| 典型用途 | API 限流、流量整形 | 恒定码率输出 | 简单限流 |

| 标记器 | 速率参数 | 桶参数 | 颜色判定顺序 | 典型场景 |
| --- | --- | --- | --- | --- |
| srTCM | CIR | CBS、EBS | 先承诺后超额 | 单速率合约计量 |
| trTCM | PIR、CIR | PBS、CBS | 先峰值后承诺 | 双速率合约、突发上界 |
| RFC 4115 型 | PIR、CIR | PBS、CBS | 峰值桶只判红，承诺桶定黄绿 | DiffServ 边界计量 |

## 六、常见误区
- 认为令牌桶不允许突发。桶容量 $b$ 就是突发额度，$b$ 越大允许的瞬时突发越大。
- 认为漏桶能加速。漏桶只把输出平滑到不超过 $r$，多余部分不会被压缩进更短时间。
- 认为两者等价。突发语义相反：令牌桶让突发按额度通过，漏桶让突发摊开通过。
- 忘记令牌桶需要时间戳。只用「每秒补 $r$ 个令牌」的定时器实现会在调度抖动下产生系统性偏差。
- 忽略队列溢出。整形侧的队列有界，桶满队满仍会丢包，「整形不丢包」是错误印象。

## 七、与开源书·权威来源对应
- RFC 2697：srTCM 的正式定义，给出 CBS/EBS 双桶着色规则与参数语义。
- RFC 2698：trTCM 的正式定义，说明 PIR/PBS 与 CIR/CBS 的双速率判定顺序。
- RFC 4115：面向 DiffServ 的三色标记器变体，细化峰值桶只用于判红的处理方式。
- Kurose & Ross《Computer Networking: A Top-Down Approach》：流量整形章节用漏桶与令牌桶解释「平均速率约束 + 突发容忍」的组合。
- Tanenbaum《Computer Networks》：QoS 与拥塞控制章节讨论令牌桶参数对突发的影响与调度配合。

## 八、面试题
1. 令牌桶与漏桶的核心区别？要点：令牌桶用令牌额度允许突发通过（限平均），漏桶用队列把突发摊到时间轴上（严格平滑）。
2. 为什么限流常用令牌桶？要点：既限制平均速率又保留合理突发，符合接入侧真实流量特征，实现只需令牌数与时间戳。
3. 桶容量 $b$ 的物理含义？要点：允许的最大瞬时突发字节数；$b$ 越大脉冲越强，$b$ 越小输出越平滑。
4. 为什么按时间戳补桶而不是用定时器？要点：定时器受调度抖动影响会累积偏差，按时间差计算令牌可保持长期速率准确。

## 九、演进与趋势
工程主流是对令牌桶做层次化封装：HTB 用父子类构成限速树，父类额度可被子类借用，在保证最低速率的同时复用空闲带宽；CAKE 类实现把整形与公平队列、AQM 结合，直接面向低时延目标。云侧趋势是分布式限速（令牌额度按实例切分或集中协调），以及在网关与服务网格层做多级配额。具体实现与参数以官方最新文档为准。

## 十、小结
令牌桶与漏桶是同一件事的两种取向：都约束长期平均速率，区别在于突发是被「额度放行」还是被「队列摊开」。理解了 $A(\tau) \le r\tau + b$ 这个不变量，就能看懂所有整形器的参数取舍；而三色标记器不过是把单个令牌桶扩展成多维合规性判定。
