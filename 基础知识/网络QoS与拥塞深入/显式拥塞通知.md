# 显式拥塞通知

> 对应 RFC 3168（The Addition of Explicit Congestion Notification to IP）；RFC 9330 / RFC 9331（L4S 架构与 ECT(1) 语义）；Kurose & Ross《Computer Networking: A Top-Down Approach》拥塞控制章节。

## 一、背景与挑战
传统 TCP 把丢包当作拥塞信号：路由器队列溢出，丢一个包，发送端才意识到网络拥塞并降低速率。这套机制的问题是信号产生得太晚——丢包发生时队列已经满了，排队时延已经很高；而且信号的成本很高：丢包触发重传、可能伴随超时，吞吐出现明显抖动。

bufferbloat 现象把问题放大到极致：当链路缓冲区远大于带宽时延积，队列会长期保持高水位，丢包信号出现前的时延可能达到数百毫秒。此时「不丢包」反而是坏消息，因为时延已经被严重污染。

显式拥塞通知（ECN）的思路是：让路由器在队列将满时**标记**而不是**丢弃**，把拥塞信号提前、无损地传给端系统。

## 二、核心原理
ECN 借用 IP 首部中的两个比特（IPv4 的 ToS 字节低 2 位，IPv6 的 Traffic Class 低 2 位，即原 ECN 域）。四种取值对应四种语义：`00` 表示不支持 ECN（Not-ECT），`10` = ECT(0)，`01` = ECT(1)，`11` = CE（Congestion Experienced）。

工作流程分四步。其一，端系统协商：TCP 在连接建立时通过在 SYN 中同时置 ECE 与 CWR 表示「我支持 ECN」，对端在 SYN-ACK 中回同样的标志表示双向启用。其二，发送端把数据包的 ECN 域置为 ECT(0) 或 ECT(1)。其三，支持 ECN 的路由器在队列超过阈值（由 AQM 算法决定）时，把 ECT 包改写成 CE，而不是丢弃；不支持 ECN 的路由器通常不改动或清零。其四，接收端在 ACK 中置 ECE 把拥塞信号回声给发送端；发送端收到后降低发送速率并置 CWR（Congestion Window Reduced）告知接收端「已响应」。

关键细节：ECN 是**端到端**信号，中间设备只做标记不做响应；CE 只在数据包上标记，ACK 上的 ECE 是接收端的回声；若接收端不回声（旧栈不支持），发送端不会降速，ECN 就退化为无效标记。此外，重传包、ICMP 等不应携带 ECT，避免把非拥塞流量计入信号。

## 三、形式化与数学基础
ECN 编码（两位二进制）：
$$Not\text{-}ECT = 00_2,\quad ECT(1) = 01_2,\quad ECT(0) = 10_2,\quad CE = 11_2$$
标记规则：若到达包为 $ECT(0)$ 或 $ECT(1)$ 且队列判定为拥塞，则置为 $CE$；否则不改动。设平均队列长度为 $\bar q$、最小阈值 $min_{th}$、最大阈值 $max_{th}$，则标记概率可取（RED 风格）
$$P_{mark} = \begin{cases} 0, & \bar q < min_{th} \\ \frac{\bar q - min_{th}}{max_{th} - min_{th}}, & min_{th} \le \bar q \le max_{th} \\ 1, & \bar q > max_{th} \end{cases}$$
AIMD 发送端对 CE 的响应（每个 RTT 最多一次，避免过度降低）：
$$cwnd \leftarrow \frac{cwnd}{2}, \qquad \text{并置 } CWR$$
经典 DCTCP 用指数平滑估计 CE 比例 $\alpha$，并把降窗与比例挂钩：
$$\alpha \leftarrow (1-g)\,\alpha + g\,F, \qquad cwnd \leftarrow cwnd\cdot\left(1 - \frac{\alpha}{2}\right)$$
其中 $F$ 是本窗口内被标记包的比例、$g$ 是平滑系数。这与 Reno 的「无条件减半」形成对比：标记比例小则轻微降速，标记比例大则接近减半。L4S 则依赖 ECT(1) 与更激进的 AQM（如 DualPI2），把队列时延压到很低，使发送端可以频繁微调速率（可扩展拥塞控制）。

## 四、代码实现
路由器侧标记与端侧响应的核心逻辑（示意）：
```c
#define ECN_NOT_ECT 0x0
#define ECN_ECT1    0x1
#define ECN_ECT0    0x2
#define ECN_CE      0x3

/* 出队前调用：AQM 决定是否标记 */
void ecn_mark(struct sk_buff *skb, struct queue_state *qs) {
    uint8_t ecn = ip_ecn_get(skb);
    if (ecn != ECN_ECT0 && ecn != ECN_ECT1) return;   /* 非 ECN 流不标记 */
    if (qs->avg_len > qs->mark_thresh) {              /* 队列超阈值 */
        ip_ecn_set(skb, ECN_CE);                      /* 标记代替丢弃 */
        qs->ce_marks++;
    }
}

/* 发送端：收到携带 ECE 的 ACK */
void on_ack(struct tcp_sock *tp, struct sk_buff *ack) {
    if (!(tcp_flag(ack) & TCP_FLAG_ECE)) { tp->ce_seen = 0; return; }
    if (tp->ce_seen) return;                          /* 每个 RTT 只减一次 */
    tp->snd_cwnd = tp->snd_cwnd / 2;
    tp->ce_seen = 1;
    tcp_set_flag(ack, TCP_FLAG_CWR);                  /* 通知对端已响应 */
}
```
观测与开关（Linux 侧示意，具体名称以实现为准）：
```bash
sysctl net.ipv4.tcp_ecn            # 0 关闭 / 1 主动请求 / 2 被动接受
ss -tin state established         # 输出中可见 ecn 标记与 cwnd 相关字段
```

## 五、与其他技术对比
| 维度 | 丢包信号（经典 Reno） | ECN + ECT(0) | L4S（ECT(1) + DualPI2） |
| --- | --- | --- | --- |
| 信号形式 | 丢包 | 无损标记 | 无损标记（高频、可扩展） |
| 信号时机 | 队列溢出后 | 队列将满时 | 极浅阈值、近乎一有排队即标 |
| 时延影响 | 排队时延高 | 明显改善 | 目标为低排队时延 |
| 公平性假设 | Reno 友好 | 与 Reno 友好流共存 | 需要独立队列/双队列调度 |
| 部署门槛 | 无 | 端 + 路由器均支持 | 端、路由器、AQM 同步升级 |
| 主要风险 | 吞吐抖动、重传 | ECN 被中间设备清零/改写 | 与传统流互相干扰 |

## 六、常见误区
- 认为 ECN 是「不丢包」。ECN 只把**可提前感知**的拥塞用标记表达，队列彻底溢出时仍会丢包。
- 认为开了 ECN 就一定更快。若接收端不回声 ECE，或路径上有设备清掉 ECN 域（ECN bleaching），信号根本传不到发送端。
- 认为所有业务同等受益。时延敏感且缓冲深的路径受益最大；短连接、小流量对 ECN 不敏感。
- 把 ECN 与 AQM 混为一谈。AQM 决定「何时标记/丢弃」，ECN 只是「标记」这种动作的信号载体，二者是策略与机制的关系。
- 忽略重传与 ICMP 的 ECT 设置。非拥塞流量带上 ECT 会污染拥塞估计。
- 认为 L4S 只是「换个 ECT 值」。L4S 要求 AQM（双队列）与发送端算法同时支持，否则会与传统流互相伤害。

## 七、与开源书·权威来源对应
- RFC 3168：ECN 的 IP 位定义、TCP 协商（SYN/ECE+CWR）、ECE/CWR 语义与路由器标记规则，是本主题的第一手规范。
- RFC 9330 / RFC 9331：L4S 架构与 ECT(1) 的使用约定，说明低时延可扩展拥塞控制的分工。
- Kurose & Ross《Computer Networking: A Top-Down Approach》：拥塞控制与 AQM 章节给出 ECN 与丢包信号的对比框架。
- Stevens《TCP/IP Illustrated》第 1 卷：TCP 首部标志位与窗口调整的可视化讲解，便于理解 ECE/CWR 的交互。
- RFC 8311：讨论放宽 ECN 实验的限制，说明「ECN 被中间设备破坏」这类部署现实问题。

## 八、面试题
1. ECN 的 IP 位有哪些取值与含义？要点：`00` 非 ECT、`10` ECT(0)、`01` ECT(1)、`11` CE；路由器只把 ECT 标为 CE。
2. ECN 如何减少 bufferbloat？要点：把拥塞信号从「溢出丢包」提前到「队列将满」，发送端在时延恶化前降速，队列水位与驻留时延随之下降。
3. ECE 与 CWR 分别由谁设置、作用是什么？要点：接收端在 ACK 上置 ECE 回声拥塞；发送端降低 cwnd 后置 CWR 表示已响应，避免重复降速。
4. 为什么 ECN 需要 SYN 阶段协商？要点：确保双向都理解标记语义，避免旧实现把 CE 当成异常或不回声造成误判。
5. L4S 与经典 ECN 的关键区别？要点：用 ECT(1) 标识低时延流、配合双队列 AQM 与可扩展拥塞控制实现高频微调，需要端到端同步支持。

## 九、演进与趋势
趋势是把 ECN 从「可选的拥塞提示」推进为「低时延传输的基础设施」：L4S 通过 ECT(1) 与双队列 AQM 把排队时延压到很低，使发送端可以持续微调速率；同时，更精确的 ECN 反馈（如按字节计数而非按包回声）在标准化进程中推进，数据中心场景的 DCTCP 思路也被更广泛地借鉴。部署侧的主要障碍仍是中间设备对 ECN 域的破坏与端栈版本差异。具体规范与开关以官方最新文档为准。

## 十、小结
ECN 把拥塞信号从「有损、滞后」改成「无损、提前」，本质是用两个比特换取端到端可感知的队列压力。它不消灭丢包，也不增加带宽，真正收益在于让发送端在时延恶化之前主动降速；而 L4S 把这条路走到极致，代价是对端、路由器与 AQM 的协同要求更高。
