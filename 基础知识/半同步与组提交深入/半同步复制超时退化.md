# 半同步复制超时退化

> 对应 MySQL 官方文档「Semisynchronous Replication」超时行为，参考运维实践。

## 一、背景与挑战
半同步要求至少一个从库确认。若从库网络抖动或宕机，主库不能无限等待，否则写入全部阻塞。超时机制用于在一致性与可用性间动态切换。

## 二、核心原理
参数 `rpl_semi_sync_master_timeout`（默认 10000ms）控制主库等待从库确认的时长。超时后主库自动退化（降级）为异步复制，继续接受写入；从库恢复并追上后，主库可自动升回半同步。这一退化保证高可用，但期间可能丢失未确认的已提交事务。

## 三、形式化与数学基础
退化条件：
$$ wait\_time > timeout \Rightarrow mode \leftarrow async $$
恢复条件：从库 ACK 到达且 `rpl_semi_sync_master_enabled=1`：
$$ mode \leftarrow semi $$
可用性相对异步不降级，一致性在该窗口内弱化。

## 四、代码实现
```sql
SET GLOBAL rpl_semi_sync_master_timeout = 2000;
-- 监控是否退化
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';  -- ON/OFF
```

## 五、与其他技术对比
Raft 类系统无「退化」概念，而是切换 leader 或阻塞写入以维持多数派，牺牲可用性保一致。MySQL 半同步退化更偏可用性优先。

## 六、常见误区
认为半同步开启就永远不丢——超时退化窗口内等同于异步。认为超时越短越安全——过短会频繁退化，反而失去半同步意义。

## 七、与开源书/权威来源对应
MySQL 官方「Semisynchronous Replication」timeout 段落；DDIA 第3章可用性讨论。

## 八、面试题
问：半同步从库宕机主库会怎样？答：等待超时后降级为异步，继续写入；恢复后自动升回。问：如何监控？答：Rpl_semi_sync_master_status 状态变量。

## 九、演进与趋势
多源半同步（多个从库确认其一即可）与加权确认提升鲁棒性。

## 十、小结
超时退化让半同步在故障下保可用，代价是短暂的一致性松弛，须被监控与理解。
