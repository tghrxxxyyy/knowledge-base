# 半同步复制超时退化

> 对应 MySQL 官方 Semisynchronous Replication 文档与 Kleppmann《Designing Data-Intensive Applications》的可用性讨论。

## 一、背景与挑战

半同步复制的承诺是：主库提交一个事务后，至少等待一个从库确认已收到该事务的日志，才向客户端返回成功。相比异步复制，它显著降低了「主库宕机导致已提交事务丢失」的概率。

但严格等待会引入新的风险：若唯一的从库网络抖动、负载过高或宕机，主库将无限等待，所有写入被阻塞，可用性直接归零。工程上必须有退路——这就是**超时退化（timeout fallback）**机制：等待超过阈值后，主库自动降级为异步模式继续服务。

## 二、核心原理

半同步复制由插件实现（`rpl_semi_sync_master` / `rpl_semi_sync_slave`）。主库在事务提交时：

1. 先写本地 redo/binlog（本地提交的准备动作）；
2. 等待至少一个从库返回 ACK，确认已收到该事务的 binlog；
3. 在超时时间内收到 ACK → 向客户端返回成功，保持半同步状态；
4. 等待超过 `rpl_semi_sync_master_timeout`（常见默认 10000ms）→ 自动切换为异步模式，继续接受写入。

当从库恢复、重新接通并追赶上之后，主库会自动升回半同步。这一「降级—恢复」闭环保证了高可用，但代价明确：**在降级窗口内，已提交事务等同于异步复制，存在丢失风险**。

需要注意：半同步要求从库「确认收到」，不同配置下确认的持久化程度不同（收到即 ACK 还是落盘后 ACK），直接影响丢数据的边界。

## 三、形式化与数学基础

设主库等待从库 ACK 的时间为 $w$，超时阈值为 $\tau$，当前复制模式为 $M \in \{\text{semi}, \text{async}\}$。退化规则：

$$
w > \tau \Rightarrow M \leftarrow \text{async}
$$

恢复规则（从库 ACK 到达且插件已启用）：

$$
\text{ack}_i \land \text{enabled} \Rightarrow M \leftarrow \text{semi}
$$

可用性视角：设从库可用概率为 $p$，异步模式下主库写入成功概率近似为 1（不依赖从库），半同步模式下为：

$$
P(\text{success}) = 1 - (1-p)^{k}\quad (k \text{ 为需确认的从库数，退化前})
$$

超时机制把上式在 $p \to 0$ 时的行为从「失败」改为「降级」：

$$
\lim_{p \to 0} P(\text{write}) = 1\ (\text{async}),\qquad \text{但一致性弱化为最终一致}
$$

丢数据窗口即降级持续时间：设退化开始于 $t_0$、恢复于 $t_1$，则该窗口为 $[t_0, t_1]$，期间已提交但未到达从库的事务在主库故障时会丢失。窗口长度与超时阈值 $\tau$ 正相关：

$$
\text{loss window} \approx (t_1 - t_0) \ge \tau
$$

## 四、代码实现

```sql
-- 启用半同步插件（从库同理启用 rpl_semi_sync_slave）
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';

SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 2000;   -- 单位 ms

-- 监控是否发生退化：ON = 半同步，OFF = 已退化为异步
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';
SHOW STATUS LIKE 'Rpl_semi_sync_master_yes_tx';    -- 半同步成功次数
SHOW STATUS LIKE 'Rpl_semi_sync_master_no_tx';     -- 退化（未等 ACK）次数
SHOW STATUS LIKE 'Rpl_semi_sync_master_wait_sessions';

-- 查看相关变量
SHOW VARIABLES LIKE 'rpl_semi_sync%';
```

运维要点：把 `Rpl_semi_sync_master_no_tx` 的增长纳入告警，它直接反映「有多少事务在退化窗口内提交」；同时监控从库的追赶进度与延迟。

## 五、与其他技术对比

| 机制 | 从库故障时的行为 | 一致性 | 可用性 | 丢数据风险 |
| --- | --- | --- | --- | --- |
| 异步复制 | 不受影响 | 最终一致 | 高 | 主库故障可丢未同步事务 |
| 半同步（不退化） | 主库写入阻塞 | 较强 | 低 | 不丢（若配置落盘 ACK） |
| 半同步（超时退化） | 降级为异步继续写 | 窗口内弱化 | 高 | 窗口内可能丢 |
| 全同步 | 阻塞直至全部确认 | 强 | 最低 | 不丢 |
| Raft/Paxos 多数派 | 切换 leader 或阻塞 | 强（多数派） | 中高 | 多数派内不丢 |

MySQL 半同步的退化更偏「可用性优先」；Raft 类系统没有「退化」概念，而是通过换 leader 或拒绝写入来维持多数派一致性，属于「一致性优先」。

## 六、常见误区

- **认为开启半同步就永不丢数据**：超时退化窗口内等同于异步，仍可能丢。
- **认为超时越短越安全**：过短会频繁退化，半同步形同虚设，应结合网络质量设定。
- **不监控退化状态**：`Rpl_semi_sync_master_status` 长期为 OFF 意味着保护已失效却不自知。
- **忽略 ACK 的持久化语义**：从库「收到即 ACK」还是「落盘才 ACK」决定丢数据的边界。
- **只部署一个从库**：单从库故障即触发退化，多从库可提升鲁棒性。
- **把退化当故障处理**：退化是设计内的保护机制，无需告警为故障，但应记录与统计。

## 七、与开源书·权威来源对应

MySQL 官方 Semisynchronous Replication 文档说明了插件安装、状态变量与 `rpl_semi_sync_master_timeout` 的行为；Kleppmann《Designing Data-Intensive Applications》讨论了同步/异步复制的可用性与一致性权衡；MySQL 官方文档对 ACK 时机与 `rpl_semi_sync_master_wait_point` 等参数有详细说明。具体默认值与参数语义以 MySQL 官方最新文档为准。

## 八、面试题

- **问：半同步从库宕机，主库会怎样？** 答：等待至超时后降级为异步，继续接受写入；从库恢复后自动升回半同步。
- **问：如何监控是否发生了退化？** 答：查看 `Rpl_semi_sync_master_status`（ON/OFF）与 `no_tx` 计数。
- **问：超时阈值设长设短各有什么影响？** 答：长则窗口内更可能丢但更少退化；短则频繁退化，保护弱但可用性高。
- **问：退化期间的数据会丢吗？** 答：若主库在此窗口内故障，未确认到达从库的已提交事务会丢失。

## 九、演进与趋势

改进方向包括：多源半同步（多个从库确认其一即可）提升鲁棒性；加权确认与按需确认（`AFTER_SYNC`/`AFTER_COMMIT`）细化持久化语义；以及用组复制（Group Replication）或共识协议替代半同步，让「多数派确认」成为默认，减少退化带来的不一致窗口。云托管数据库则把退化事件纳入可观测指标，便于运维判断风险。

## 十、小结

超时退化让半同步在故障下保持可用：主库不会因从库不可达而阻塞写入，代价是降级窗口内的一致性松弛与潜在丢数据。正确做法是配置合理的超时、监控 `status` 与 `no_tx`、并理解 ACK 的持久化语义，从而在可用性与数据安全之间做出明确取舍。
