# 主从复制同步模式

> 对应 MySQL 官方文档「Replication」与 DDIA 第3章复制章节，参考 DeCandia 2007 最终一致性背景。

## 一、背景与挑战
主从复制中，主库提交后多久、以何种保证把变更传到从库，决定了一致性与可用性的取舍。同步、异步、半同步三种模式各有适用场景。

## 二、核心原理
异步复制：主提交即返回，从库后台追赶，可能丢最近事务但性能最好。全同步：等所有从库确认才提交，强一致但延迟高、可用性差。半同步：等至少一个从库确认收到（不要求已应用）即提交，折中一致与性能。

## 三、形式化与数学基础
设从库确认时延 $d_i$，提交时延：
$$ T_{async} = T_{local} $$
$$ T_{semi} = T_{local} + \min_i d_i $$
$$ T_{sync} = T_{local} + \max_i d_i $$
一致强度递增、性能递减。

## 四、代码实现
```sql
-- MySQL 半同步
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_timeout = 1000;  -- ms
```

## 五、与其他技术对比
PostgreSQL 同步复制用 `synchronous_standby_names` 指定需确认的从库，语义类似半同步（收到流即确认）。分布式共识（Raft）将「多数派确认」形式化，比主从半同步更严谨。

## 六、常见误区
认为半同步=不丢数据——它只保证日志到达从库内存，从库宕机仍可能丢（除非也已落盘且配置得当）。认为同步复制一定强一致——需配合其他机制防脑裂。

## 七、与开源书/权威来源对应
MySQL 官方「Semisynchronous Replication」；DDIA 第3章「Synchronous vs Asynchronous」。

## 八、面试题
问：半同步保证什么？答：至少一个从库收到 binlog（内存/磁盘依配置），降低丢数据概率但不绝对。问：超时后退化为？答：异步，保障可用性但失去半同步保护。

## 九、演进与趋势
多副本多数派确认（Raft/Paxos）、地域级同步组成为云数据库默认，半同步逐步被更严谨共识替代。

## 十、小结
复制模式是延迟与一致性的权衡旋钮，半同步是单机主从下的实用折中。
