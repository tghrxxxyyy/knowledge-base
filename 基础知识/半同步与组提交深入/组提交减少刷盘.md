# 组提交减少刷盘

> 对应 MySQL InnoDB 官方 Group Commit 文档与 Gray & Reuter《Transaction Processing》中关于提交代价的论述。

## 一、背景与挑战

事务的持久性要求提交时把日志刷入持久存储（fsync）。但 fsync 的代价极高：机械盘需要等待寻道与旋转，SSD 也会引入写放大与延迟。若每个事务都独立 fsync 一次，高并发下吞吐会被磁盘同步开销牢牢卡住。

组提交（group commit）要解决的就是这个矛盾：把多个并发事务的刷盘动作合并为一次 fsync，让一次磁盘同步持久化多个事务，从而在保持持久性的同时大幅提升吞吐。

## 二、核心原理

InnoDB 的 redo 组提交通常分为三个阶段：

- **flush**：把各事务的日志写入 redo 缓冲区，形成待持久化的队列；
- **sync**：把这一批日志一次性 fsync 到磁盘；
- **commit**：按顺序标记各事务提交，事务对客户端可见。

MySQL 的 binlog 同样支持组提交，按事务提交顺序成组刷盘。由于内部两阶段提交需要协调 redo 与 binlog，两个日志各自的组提交需要保持一致顺序——这被称为「binlog 组提交 + redo 组提交」的协同。

关键点在于：组提交不改变单个事务的持久性语义（配置为 1 时，返回成功即已落盘），只是把多个事务的同步开销摊薄到一批上。批越大，单事务平均 fsync 成本越低，但等待组形成的时间也会增加，因而存在延迟与吞吐的权衡。

## 三、形式化与数学基础

设并发事务数为 $N$，无组提交时每个事务独立 fsync：

$$
F_{\text{naive}} = N
$$

采用组提交、平均批大小为 $B$ 时：

$$
F_{\text{group}} = \left\lceil \frac{N}{B} \right\rceil
$$

fsync 次数的下降带来吞吐提升，近似：

$$
\frac{T_{\text{group}}}{T_{\text{naive}}} \approx \frac{N}{N/B} = B
$$

设单次 fsync 耗时为 $t_f$、单事务处理耗时为 $t_c$，则无组提交时单事务平均延迟约为：

$$
L_{\text{naive}} \approx t_c + t_f
$$

组提交下，事务平均分摊 fsync 成本，但需等待同批事务聚合，平均延迟为：

$$
L_{\text{group}} \approx t_c + \frac{t_f}{B} + w_{\text{batch}}
$$

其中 $w_{\text{batch}}$ 为等待组形成的时长。可见 $B$ 越大吞吐越高，但 $w_{\text{batch}}$ 会增大尾延迟，需按业务 SLA 调整（如限制最大批等待时间）。

## 四、代码实现

```sql
-- 查看与持久化、组提交相关的关键配置
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';  -- 1 最安全
SHOW VARIABLES LIKE 'sync_binlog';                     -- 1 每事务刷 binlog
SHOW VARIABLES LIKE 'binlog_group_commit_sync_delay';  -- 延迟多少微秒再同步（攒批）
SHOW VARIABLES LIKE 'binlog_group_commit_sync_no_delay_count';
-- 达到指定事务数即不再延迟，立即同步

-- 适度增大延迟可提升批大小与吞吐（以少量延迟换取吞吐）
-- SET GLOBAL binlog_group_commit_sync_delay = 1000;          -- 1ms
-- SET GLOBAL binlog_group_commit_sync_no_delay_count = 10;

-- 监控提交相关状态
SHOW STATUS LIKE 'Binlog_commits';
SHOW STATUS LIKE 'Binlog_group_commits';   -- 组提交次数
```

若 `Binlog_group_commits` 远小于 `Binlog_commits`，说明成组效果良好。

## 五、与其他技术对比

| 系统/机制 | 组提交实现 | 持久化语义 | 调节手段 |
| --- | --- | --- | --- |
| MySQL InnoDB redo | 三阶段 flush/sync/commit | `flush_log_at_trx_commit=1` 不丢 | 批量刷盘 |
| MySQL binlog | 按提交顺序成组 | `sync_binlog=1` 不丢 | `sync_delay` 等 |
| PostgreSQL WAL | WAL writer 共享 fsync | `synchronous_commit=on` 不丢 | `commit_delay`、`commit_siblings` |
| LSM 引擎 WAL | 批量 fsync 写前日志 | 可配置 | 批大小与间隔 |
| 分布式共识日志 | 批量 append + 批量复制 | 多数派持久化 | 批大小与流水线 |

组提交是几乎所有写入型系统的共性优化：它把「每次提交一次同步」变成「每批提交一次同步」，是持久化与吞吐之间的标准折中。

## 六、常见误区

- **认为 `sync_binlog=1` 必然很慢**：组提交会把同步代价摊到批次，实际吞吐通常可接受。
- **认为组提交无风险**：在非严格配置下，极端崩溃可能丢失整批「已返回成功但未落盘」的事务。
- **盲目增大 `sync_delay`**：批变大、吞吐上升，但尾延迟显著增加，可能违反 SLA。
- **把组提交当异步**：配置为 1 时事务返回前本批已 fsync，语义仍是持久化，只是批量化。
- **忽略 binlog 与 redo 的顺序**：二者需要一致的提交顺序，否则破坏内部 2PC 的一致性。
- **只调参不看指标**：应结合 `Binlog_group_commits` 与实际延迟分布评估效果。

## 七、与开源书·权威来源对应

MySQL InnoDB 与 Binary Log 官方文档描述了组提交的阶段划分与相关参数；Gray & Reuter《Transaction Processing》讨论了提交与持久化的代价模型；PostgreSQL 官方文档的 WAL 与 `commit_delay` 说明提供了同类机制的对照。具体参数名、默认值与语义以各数据库官方最新文档为准。

## 八、面试题

- **问：组提交如何提升吞吐？** 答：把多个事务的 fsync 合并为一次，降低磁盘同步次数，从而摊销单事务持久化成本。
- **问：内部 2PC 中组提交在哪？** 答：redo 与 binlog 各自成组，在内部两阶段提交的协调下都需要保持顺序一致。
- **问：组提交会增加延迟吗？** 答：会引入等待成组的时长，属于吞吐与尾延迟的权衡。
- **问：如何确认组提交生效？** 答：比较 `Binlog_group_commits` 与 `Binlog_commits`，前者显著小于后者即有效。

## 九、演进与趋势

组提交正与硬件演进协同：NVMe 多队列让批量同步更高效，更细粒度的提交分组可按设备队列并行；数据库侧引入「提交时间窗」自适应调整批大小；分布式系统中则与流水线复制、批量共识结合，进一步压低每次提交的同步开销。

## 十、小结

组提交以批量 fsync 摊薄持久化成本，是高并发写入不可或缺的优化：它把 $N$ 次同步降为 $\lceil N/B \rceil$ 次，近似线性提升吞吐，代价是引入等待成组的延迟。理解这一权衡并合理配置，才能在保持持久性的同时获得可接受的吞吐与延迟。
