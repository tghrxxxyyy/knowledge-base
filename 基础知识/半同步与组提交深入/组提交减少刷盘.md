# 组提交减少刷盘

> 对应 MySQL InnoDB 官方文档「Group Commit」与 Gray 等事务提交理论，参考 DDIA 第3章。

## 一、背景与挑战
每个事务提交都 fsync 一次 redo/binlog 代价极高（磁盘旋转/SSD 写放大约束）。组提交把多个并发事务的刷盘合并为一次 fsync，是高频写入的命脉优化。

## 二、核心原理
InnoDB 的 redo 组提交分三阶段：flush（写日志到缓冲）、sync（一批一起 fsync）、commit（标记事务提交）。MySQL 的 binlog 也有组提交（按事务提交顺序成组）。两阶段结合（binlog 组提交 + redo 组提交）使一次 fsync 可持久化多个事务的日志。

## 三、形式化与数学基础
无组提交时 N 个并发事务 fsync 次数：
$$ F_{naive} = N $$
组提交（每批大小 $B$）后：
$$ F_{group} = \lceil N / B \rceil $$
fsync 次数随批次显著下降，吞吐近似线性提升。

## 四、代码实现
```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';  -- 1 最安全
SHOW VARIABLES LIKE 'sync_binlog';  -- 1 每事务刷 binlog
-- 二者=1 时依赖组提交保吞吐
```

## 五、与其他技术对比
PostgreSQL 的 WAL 也有组提交（多个后端共享一次 fsync via WAL writer）。LSM-tree 的 WAL 同样批量 fsync。这是几乎所有写入型系统的共性优化。

## 六、常见误区
认为 `sync_binlog=1` 必然很慢——组提交把代价摊到批次。认为组提交无风险——极端崩溃可能丢失整批已返回成功但未落盘的事务（取决于配置）。

## 七、与开源书/权威来源对应
InnoDB 官方「Group Commit」文档；Gray 关于事务提交与 fsync 代价的论述；DDIA 第3章。

## 八、面试题
问：组提交如何提升吞吐？答：合并多个事务的 fsync 为一次，降低磁盘同步次数。问：两阶段提交中组提交在哪？答：redo 与 binlog 各自成组，XA 协调下都受益。

## 九、演进与趋势
更细粒度的提交分组、与 NVMe 多队列协同，进一步压低 fsync 开销。

## 十、小结
组提交以批量 fsync 摊薄持久化成本，是高并发写入不可或缺的优化。
