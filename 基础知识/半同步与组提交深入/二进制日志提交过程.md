# 二进制日志提交过程

> 对应 MySQL 官方 Binary Log 文档与 Kleppmann《Designing Data-Intensive Applications》对 2PC 的讨论。

## 一、背景与挑战

MySQL 的持久化依赖两套日志：InnoDB 的 **redo log**（物理日志，保证崩溃恢复）与 Server 层的 **binlog**（逻辑日志，保证主从复制与时间点恢复）。一个事务的提交必须让二者状态一致，否则崩溃恢复后可能出现「redo 已提交但 binlog 没有」或反之，导致主从数据不一致。

这不是理论问题：若 binlog 记录了某事务而 redo 未提交，从库会应用一个主库并不存在的事务；若 redo 已提交而 binlog 缺失，从库则永久丢失该事务。两种都会造成主从不一致。

## 二、核心原理

MySQL 在内部用两阶段提交协调 redo 与 binlog：

1. **prepare 阶段**：InnoDB 写 redo log 并标记该事务为 `prepare`，同时把事务的 XID 写入 redo；
2. **写 binlog**：事务的变更按提交顺序写入 binlog，并在 binlog 中记录相同的 XID；
3. **commit 阶段**：InnoDB 在 redo 中写入 `commit` 标记，事务正式提交。

崩溃恢复时的判定规则非常清晰：

- 若 redo 中有该事务的 `prepare`，且 binlog 中能找到对应 XID 的完整记录 → **提交**；
- 若 redo 中有 `prepare`，但 binlog 中找不到对应记录 → **回滚**。

由此保证核心不变量：**binlog 中存在的事务，redo 必然已提交**。这正是主从一致性的根基——从库只重放 binlog，而 binlog 里的事务在主库上一定是已提交的。

## 三、形式化与数学基础

记事务 $T$ 的状态为 $\text{prepare}(T)$、$\text{binlog\_complete}(T)$、$\text{redo\_committed}(T)$。核心一致性不变量为：

$$
\text{binlog\_complete}(T) \Rightarrow \text{redo\_committed}(T)
$$

崩溃恢复的判定规则：

$$
\text{prepare}(T) \land \text{binlog\_complete}(T) \Rightarrow \text{commit}(T)
$$

$$
\text{prepare}(T) \land \lnot \text{binlog\_complete}(T) \Rightarrow \text{rollback}(T)
$$

两个关键配置项决定持久化强度：

- `innodb_flush_log_at_trx_commit = 1`：每次提交将 redo 刷盘（最安全）；
- `sync_binlog = 1`：每次提交将 binlog 刷盘。

当二者均为 1 时，单个事务的提交在崩溃后不会丢失，但会产生两次昂贵的 fsync——这正是组提交（group commit）要摊薄的成本。设窗口内并发事务数为 $N$、组提交批大小为 $B$，则 fsync 次数由 $N$ 降为：

$$
F_{\text{group}} = \left\lceil \frac{N}{B} \right\rceil
$$

```sql

SHOW VARIABLES LIKE 'sync_binlog';                    -- 1 = 每事务刷盘
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; -- 1 = 每事务刷盘

-- 查看当前 binlog 文件与位点
SHOW MASTER STATUS;
SHOW BINARY LOGS;

-- 查看 InnoDB 事务状态（含 prepare 状态的事务）

-- 基于 binlog 的时间点恢复（示意）

```

## 五、与其他技术对比

| 系统 | 日志体系 | 是否需内部 2PC | 恢复与复制一致性 |
| --- | --- | --- | --- |
| MySQL（InnoDB + binlog） | 双日志（redo + binlog） | 是 | 靠 XID 关联保证 |
| PostgreSQL | 单日志（WAL） | 否 | WAL 同时承载恢复与复制 |
| 多数 NewSQL（Raft） | 共识日志 | 否 | 多数派提交即一致 |
| LSM 存储引擎 | WAL + 内存表 | 否（单日志） | WAL 单点决定 |

PostgreSQL 用单一 WAL 同时承担恢复与流复制，从架构上避免了 MySQL 的双日志协调问题；MySQL 的双日志源于其插件式存储引擎历史，是架构耦合的产物，也因此保留了两阶段提交的逻辑。

## 六、常见误区

- **认为 binlog 只服务复制**：它同时是内部 2PC 与崩溃恢复一致性的关键参与者。
- **认为 prepare 即提交**：prepare 阶段事务尚未对外可见，需 commit 标记完成。
- **配置 `sync_binlog=0` 却要求不丢**：该配置下 binlog 由操作系统决定刷盘，崩溃可能丢事务。
- **忽略 XID 的作用**：没有 XID 关联，恢复时无法判断 binlog 是否包含该事务。
- **把 binlog 当 redo 用**：binlog 是逻辑日志，粒度为语句/行变更，不能替代物理 redo。
- **以为崩溃恢复一定能自动完成**：极端情况仍可能需人工核对 binlog 与 redo。

## 七、与开源书·权威来源对应

MySQL 官方 Binary Log 与 Internal XA/两阶段提交文档详细描述了提交流程与恢复判定；Kleppmann《Designing Data-Intensive Applications》讨论了两阶段提交的语义与容错；MySQL 源码与 InnoDB 文档说明了 redo 的 prepare/commit 标记机制。具体配置项与默认值以 MySQL 官方最新文档为准。

## 八、面试题

- **问：崩溃恢复如何决定 prepare 事务提交还是回滚？** 答：看 binlog 是否完整记录了该事务（通过 XID 关联），是则提交，否则回滚。
- **问：为什么需要两套日志？** 答：redo 保证崩溃恢复（物理），binlog 保证复制与时间点恢复（逻辑），职责不同。
- **问：核心一致性不变量是什么？** 答：binlog 中存在的事务，redo 必然已提交。
- **问：与 PostgreSQL 的差异？** 答：PostgreSQL 单一 WAL 兼顾恢复与复制，无需内部 2PC。

## 九、演进与趋势

云原生数据库正重构这一机制：部分系统用统一日志（shared log）替代 redo + binlog 的双日志协调，从架构上消除 2PC 的复杂性；也有实现把 binlog 下沉到存储层，让复制与恢复共享同一份日志。总体方向是「用单一日志源降低协调成本」，同时保持崩溃恢复与复制的一致性。

## 十、小结

binlog 的提交过程本质是用内部两阶段提交协调 redo 与 binlog：prepare 写 redo，随后写 binlog，最后提交 redo。恢复时依据 binlog 是否完整决定提交或回滚，从而保证「binlog 有则 redo 必提交」这一核心不变量，这是 MySQL 复制可靠与崩溃恢复正确的根基。
