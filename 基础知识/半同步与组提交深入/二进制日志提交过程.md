# 二进制日志提交过程

> 对应 MySQL 官方文档「Binary Logging」与「Two-Phase Commit」在 binlog + redo 中的实现，参考 DDIA 第3章。

## 一、背景与挑战
MySQL 同时有 InnoDB redo（物理，保崩溃恢复）与 binlog（逻辑，保复制）。一个事务的「提交」必须让二者一致，否则恢复后主库与 binlog 状态矛盾，复制出错。

## 二、核心原理
内部采用两阶段提交（2PC）协调 redo 与 binlog：阶段一（prepare）InnoDB 写 redo 并标记 prepare；阶段二先写 binlog，再写 redo 的 commit 标记。崩溃恢复时，若 redo 处于 prepare 且 binlog 完整，则提交；若 binlog 缺失，则回滚。这样就保证「binlog 有则 redo 必提交」。

## 三、形式化与数学基础
一致性不变量：
$$ binlog\_has(T) \Rightarrow redo\_committed(T) $$
恢复判定：
$$ if\ prepare(T)\ and\ binlog\_complete(T): commit(T) $$
$$ if\ prepare(T)\ and\ \neg binlog\_complete(T): rollback(T) $$

## 四、代码实现
```sql
-- 控制 binlog 刷盘
SET GLOBAL sync_binlog = 1;
-- 查看两阶段状态（内部）
SHOW ENGINE INNODB STATUS;  -- TRANSACTIONS 段
```

## 五、与其他技术对比
PostgreSQL 单日志体系（WAL 既管恢复又管复制）无需此类 2PC；MySQL 因历史上是插件式存储引擎 + 独立 binlog 才需协调，是架构耦合的产物。

## 六、常见误区
认为 binlog 只是复制用——它也是 XA 2PC 与崩溃恢复一致性的关键。认为 prepare 即提交——prepare 阶段事务尚未对外可见，需 commit 标记完成。

## 七、与开源书/权威来源对应
MySQL 官方「Binary Log」与「Internal XA」文档；DDIA 第3章对 2PC 的讨论。

## 八、面试题
问：崩溃恢复如何决定 prepare 事务提交还是回滚？答：看 binlog 是否完整记录了该事务，是则提交，否则回滚。

## 九、演进与趋势
binlog 与 redo 的协调在云原生存储下被重构，部分系统用统一日志避免 2PC 复杂性。

## 十、小结
binlog 提交借 2PC 与 redo 协调，保证崩溃后主从状态一致，是 MySQL 复制可靠的根基。
