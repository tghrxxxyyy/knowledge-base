# 反序列化漏洞

> 对应不安全的反序列化（Insecure Deserialization）与对象注入。

## 一、背景与挑战
把不可信数据反序列化为对象时，攻击者可构造恶意对象图，触发危险方法（Java readObject、PHP POP 链、Python pickle），导致 RCE/提权。

## 二、核心原理
- 语言原生序列化（Java ObjectInputStream、PHP unserialize、Python pickle）在反序列化时自动调用魔术方法/构造函数。
- 利用：构造 gadget chain（一串可串联调用）最终执行命令。
- 防御：不反序列化不可信数据；用 JSON 等纯数据格式；签名校验来源。
- 类型白名单：限制可实例化的类。

## 三、形式化 / 数学基础
- 危险来自反序列化即执行语义：$deserialize(x) \to \text{side-effect}$，而非纯数据重建。
- Gadget chain：存在方法序列 $m_1\circ\cdots\circ m_k$ 使输入可控点到达 sink（`Runtime.exec`）。
- 完整性：若 $verify(sig, x)$ 失败则拒绝，防篡改构造。
- 白名单类集 $C_{allow}$，反序列化仅允许 $c \in C_{allow}$。

## 四、代码实现
```python
# 错误：反序列化不可信 pickle（可执行的任意代码）
import pickle
obj = pickle.loads(user_data)        # 危险！
# 正确：用纯数据格式 + 校验
import json
data = json.loads(user_data)         # 仅数据，无行为
# 对敏感载荷加签名
if not hmac.compare_digest(sig, sign(user_data, key)): raise ValueError
```

## 五、与其他技术对比
- 原生序列化 vs JSON：前者带行为危险，后者纯数据安全。
- 黑名单类 vs 白名单：白名单更可靠。
- 输入校验 vs 签名：签名保证来源可信更强。

## 六、常见误区
- 认为"只是数据"而反序列化不可信输入。
- 用黑名单禁个别危险类（gadget 众多难穷举）。
- 在缓存/会话中直接存反序列化对象并对外暴露。

## 九、演进与趋势
默认禁止危险反序列化；Schema 校验（Protobuf/JSON Schema）；内存安全语言减少利用链。

## 十、小结
不安全反序列化因对象重建即执行而危险，须以纯数据格式、签名校验与类白名单替代原生反序列化。
