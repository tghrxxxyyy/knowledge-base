# 崩溃恢复

> 对应 Silberschatz《Database System Concepts》第 17 章 Recovery System，以及 ARIES 论文（Mohan et al., ACM 1992）。

## 一、背景与挑战
数据库可能因断电、进程崩溃而处于不一致状态：已提交事务的修改可能未落盘，未提交事务的修改可能已部分落盘。恢复子系统必须保证原子性与持久性。

## 二、核心原理
基于 WAL（预写日志）：任何页修改先写日志再改页。恢复分三阶段：Analysis（确定哪些事务活跃、哪些页脏）、Redo（重放所有已提交与未提交修改到崩溃前状态）、Undo（回滚未提交事务）。

## 三、形式化 / 数学基础
日志记录含 `<T, P, old, new, LSN, prevLSN>`。检查点减少 Redo 起点。恢复正确性依赖：先 Redo 再 Undo，且 Undo 自身也写日志（CLR）以支持重复恢复。

## 四、代码实现
```python
def recover(log, dirty_pages):
    analysis(log)                 # 构建待重做/撤销集合
    for rec in log.from_checkpoint():
        if rec.lsn >= dirty_pages.get(rec.page, -1):
            apply(rec.new)        # REDO
    for txn in active_txns:
        for rec in reverse_log(txn):
            apply(rec.old)        # UNDO, 写 CLR
```

## 五、与其他技术对比
| 方案 | 特点 |
|------|------|
| 影子分页 | 无重做但空间复制开销大 |
| WAL+ARIES | 细粒度、支持模糊检查点 |
| 物理日志 | 记录页偏移，紧凑 |

## 六、常见误区
1. 只 Undo 不 Redo——会丢失已提交数据。
2. 先 Undo 后 Redo——破坏日志顺序导致错误。
3. 检查点=完全落盘——现代用模糊检查点。

## 九、演进与趋势
分布式下引入 Paxos/Raft 复制日志，将单机 ARIES 扩展到多副本一致恢复（如 Spanner、CockroachDB）。

## 十、小结
崩溃恢复以 WAL 与 ARIES 三阶段为核心，保证 ACID 中的 A 与 D；检查点控制恢复时间窗口。
