# 聚簇与非聚簇索引

> 对应 Silberschatz《Database System Concepts》11.2 Indexing，以及 CMU 15-445 Lecture 6 Clustered Index。

## 一、背景与挑战
同一张表常有多种查询访问模式（按主键、按姓名）。如何让不同查询都高效？索引的物理组织方式（聚簇 vs 非聚簇）决定了一次索引查找后还需多少额外 I/O。

## 二、核心原理
聚簇索引（clustered）的叶子结点直接存放整行数据，表数据按索引键物理排序，每表仅一个。非聚簇索引（secondary）叶子存索引键与指向聚簇键（或行指针）的引用，需一次回表（bookmark lookup）。

## 三、形式化 / 数学基础
回表代价近似：$C = h_{sec} \cdot T_{disk} + k \cdot h_{clu} \cdot T_{disk}$，其中 $k$ 为命中行数。覆盖索引可令 $k=0$ 省去回表。

## 四、代码实现
```sql
-- MySQL InnoDB：主键即聚簇索引
CREATE TABLE t (
  id INT PRIMARY KEY,            -- 聚簇
  name VARCHAR(64),
  KEY idx_name (name)            -- 非聚簇，叶子存 (name, id)
);
-- 覆盖索引：无需回表
SELECT id FROM t WHERE name = 'a';
```

## 五、与其他技术对比
| 类型 | 数据位置 | 数量 | 回表 |
|------|----------|------|------|
| 聚簇 | 叶子结点 | 1 | 否 |
| 非聚簇 | 引用主键 | 多 | 是 |

## 六、常见误区
1. 非聚簇索引一定慢——覆盖索引可避免回表。
2. 聚簇索引可建多个——错，物理顺序唯一。
3. UUID 主键好——随机插入导致页分裂与碎片。

## 九、演进与趋势
列式存储与覆盖索引（Included columns）让非聚簇索引尽量自带列；Oracle 的 IOT、InnoDB 聚簇设计持续演进以减少随机回表。

## 十、小结
聚簇索引决定行物理顺序，非聚簇索引靠回表取数据；覆盖索引是消除回表代价的关键优化手段。
