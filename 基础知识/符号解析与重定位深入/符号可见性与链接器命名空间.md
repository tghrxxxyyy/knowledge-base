# 符号可见性与链接器命名空间

> 对应 Levine《Linkers and Loaders》第 6 章；CSAPP 第 7 章；并参考 ELF gABI 关于 `STV_*` 可见性与 glibc `dlmopen`/`dlinfo` 文档。

## 一、背景与挑战

大型程序由众多库组成，全局符号平面命名易冲突（如多个库都定义 `log`、`debug`、`init`）。

需要控制哪些符号对外可见、哪些仅模块内部使用，否则会出现「符号拦截（symbol interposition）」：一个库的函数被另一个库的同名强符号意外覆盖。

可见性控制还影响性能：隐藏符号可避免 GOT/PLT 间接与运行时符号查找。

链接器命名空间（如 `dlmopen` 的 `LM_ID`）把一组库隔离在独立符号域，让同名符号互不干扰，典型用于插件沙箱。

## 二、核心原理

ELF 符号绑定字段区分 `STB_LOCAL` / `STB_GLOBAL` / `STB_WEAK`；可见性 `st_other` 的 `STV_*` 进一步约束跨对象可见性：

`STV_DEFAULT`（按默认规则可被拦截/导出）、`STV_HIDDEN`（仅本模块/DSO 可见，不进动态符号表）、`STV_PROTECTED`（本模块内直接绑定，外部仍可见但不可预占）、`STV_INTERNAL`（实现定义）。

`-fvisibility=hidden` 把默认可见性翻转为 hidden，再用 `__attribute__((visibility("default")))` 显式导出 API。

`dlmopen(lmid, path, flag)` 在指定命名空间加载，符号查找限于该命名空间，实现强隔离。

## 三、形式化与数学基础

导出符号集（进入 `.dynsym` 且可被外部绑定）：

$$E = \{ s \mid bind(s)\neq LOCAL \land vis(s)=default \}$$

隐藏后调用开销下降，因为省去 GOT/PLT 间接与符号查找：

$$cost_{hidden} < cost_{global}$$

且预占（preemption）被禁止：hidden/protected 符号地址在链接期确定，可被直接调用或内联。

## 四、代码实现

```c
// 隐藏符号，仅本 DSO 可见
__attribute__((visibility("hidden"))) int internal_counter;

// 默认导出（显式，配合 -fvisibility=hidden）
__attribute__((visibility("default"))) void api(void) { ... }

// 命名空间隔离：在独立 lmid 加载插件，避免与主程序符号冲突
void *h = dlmopen(LM_ID_NEWLM, "plugin.so", RTLD_LOCAL);
```

`objdump -T` 查看动态符号表（仅 `default` 强/弱符号出现），`readelf -s` 看完整 `.symtab` 含 hidden。

## 五、与其他技术对比

| 可见性 | 进 dynsym | 可被预占 | 调用开销 |
| --- | --- | --- | --- |
| default | 是 | 是 | GOT/PLT |
| hidden | 否 | 否 | 直接 |
| protected | 是（x86 特殊） | 否（本模块） | 直接 |
| static（文件内） | 否 | 否 | 直接 |

全局默认可见便于插件扩展但膨胀 dynsym、增加冲突面；hidden 默认（fvisibility=hidden）更安全紧凑，需显式导出 API。

## 六、常见误区

1. `static` 仅文件内可见，仍需配合 visibility 才能避免进 dynsym：跨文件但需隐藏的符号要用 `visibility("hidden")`。
2. 误以为 hidden 符号绝对不可外部调用：仍可由地址直接调用，只是不在符号表，外部无法按名解析。
3. 命名空间隔离不隔离内存：仅隔离符号查找域，模块仍共享同一地址空间。
4. 误以为 protected 在 x86 等同 hidden：x86 上 protected 仍可能被外部以 GOT 访问，语义与架构相关，曾引发一致性问题。
5. 误以为 `-fvisibility=hidden` 影响符号冲突检测：它只改变动态可见性，静态链接的强/弱决议不变。
6. 误以为导出集越小越好而无视 ABI：隐藏后外部无法按名调用，须用版本脚本固定稳定 API 面。

## 七、与开源书·权威来源对应

- Levine《Linkers and Loaders》第 6 章讲符号作用域与可见性。
- glibc 手册 `dlmopen`/`dlinfo` 描述链接器命名空间 `lmid` 的隔离语义。
- ELF gABI 定义 `STV_DEFAULT/HIDDEN/PROTECTED/INTERNAL` 的精确规则。
- CSAPP 第 7 章铺垫全局符号与库冲突背景。
- `readelf -d` 可查看 `DF_1_*` 标志与 `SONAME`，验证命名空间/可见性配置是否生效。

## 八、面试题

1. `static` 与 `hidden visibility` 区别？要点：static 文件内；hidden 跨文件但不在 dynsym，外部不能按名绑定。
2. 为何要隐藏符号？要点：缩小 dynsym、减少冲突、允许直接调用/内联、提升安全。
3. 命名空间（`dlmopen`）用途？要点：把插件加载到独立符号域，避免与主程序同名符号互相预占。
4. protected visibility 的陷阱？要点：x86 上语义与架构相关，外部仍可能经 GOT 访问。

## 九、演进与趋势

- 符号版本脚本（version script，`__attribute__((alias))`+`*.ver`）配合 hidden 默认，成为库 ABI 稳定的标准做法。
- `IFUNC` 与可见性交互：解析函数需 default 可见以被 `ld.so` 绑定。
- `DF_1_NODELETE`/`DF_1_GLOBAL` 标志细化命名空间全局可见性。

## 十、小结

可见性控制把全局平面名空间收敛为受控导出面：hidden 默认 + default 显式导出是库工程化的基石，而 `dlmopen` 命名空间在运行时提供更强隔离，二者共同抑制符号冲突与预占。
