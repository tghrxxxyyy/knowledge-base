# 代码评审效能提升

> 对应 McConnell《Code Complete》。

## 一、背景与挑战
评审若体量过大、反馈迟缓或流于形式，既拖慢交付又抓不住真正问题，沦为盖章流程。

## 二、核心原理
控制单 PR 规模（小批量更易审）、设定响应 SLA、聚焦设计而非风格（风格交给 lint）、用模板引导评论，提升评审 throughput 与 defect 捕获率。

## 三、形式化与数学基础
缺陷密度随 PR 规模超线性增长：defects ∝ size^1.5。拆分小 PR 使每单位评审可发现缺陷概率更高，即 review_yield 提升。

## 四、代码实现
```text
PR 模板：
- 变更目的：(一句话)
- 影响范围：(服务/接口)
- 自测：(如何验证)
# 规则：单 PR < 400 行，超时 1 工作日提醒
```

## 五、与其他技术对比
相比无评审，规范评审显著降低缺陷泄漏；但过度评审（每人必批）拖慢流动，需平衡。

## 六、常见误区
- 评审变成找缩进/命名等 lint 能管的事。
- PR 巨大导致 reviewer 草草通过。

## 七、与开源书/权威来源对应
《Code Complete》以实证研究说明正式评审比测试更具缺陷发现性价比。

## 八、面试题
为什么小 PR 评审质量更高？评审应关注哪些层面？

## 九、演进与趋势
AI 预评审处理风格与明显缺陷，让人聚焦设计权衡。

## 十、小结
高效评审靠小批量、快反馈、分层关注，把人的注意力留给真正重要的判断。
