# 代码评审效能提升

> 对应 Steve McConnell《Code Complete》代码评审实证研究、现代 PR 评审（Pull Request）实践。

## 一、背景与挑战

代码评审（Code Review）是缺陷进入主干前的关键闸门，但若体量过大、反馈迟缓或流于形式，既拖慢交付又抓不住真正问题，沦为「盖章流程」。典型痛点：

- 巨型 PR：一次性改上千行，reviewer 难以深入，草草通过。
- 反馈慢：评审排队数天，打断开发者心流、拉长周期。
- 关注错层：评审者纠缠缩进/命名，忽视设计权衡。
- 形式化：所有人 Approve 但无人真正负责。

核心挑战是让评审「既快又准」，把人的注意力留给真正重要的判断。

## 二、核心原理

高效评审依赖几条原则：

1. 小批量：单 PR 控制在可审规模（如 < 400 行），缺陷更易被发现。
2. 响应 SLA：设定评审时效（如 1 个工作日），避免阻塞流动。
3. 分层关注：风格交给 lint/ formatter，人聚焦设计、边界、安全。
4. 模板引导：PR 模板强制写清目的、影响、自测，降低 reviewer 认知成本。
5. 自动化预审：CI 跑测试/静态扫描，AI 预评审处理明显问题。

目标是提升评审吞吐（throughput）与缺陷捕获率（defect yield），而非追求 100% 覆盖。

## 三、形式化与数学基础

实证表明缺陷密度随 PR 规模超线性增长（近似幂律）：

$$ \text{defects} \propto \text{size}^{\,1.5} $$

拆分小 PR 使单位评审可发现缺陷概率（review yield）提升。设单 PR 发现缺陷概率为 $p$，整体捕获率随拆分增加：

$$ Y = 1 - \prod_{k}(1 - p_k),\quad \sum \text{size}_k = \text{size}_{\text{total}} $$

小批量令每个 $p_k$ 更高，整体 $Y$ 上升，且评审耗时近似线性而非超线性。

## 四、代码实现

```text
# PR 模板（约束上下文，降低评审成本）
变更目的：(一句话说明为什么)
影响范围：(服务 / 接口 / 数据表)
自测方式：(如何验证，含测试命令)
风险点：(已知边界 / 回滚方案)

# 评审规则（写入仓库约定）
# - 单 PR 规模 < 400 行（除生成代码/批量重构）
# - 超时 1 个工作日自动提醒 owner
# - 风格类问题交给 lint，评审不重复指出
# - 关注设计权衡、错误处理、安全，而非缩进
```

```python
# 用脚本在 CI 中拦截超大 PR
def check_pr_size(patch_lines, limit=400):
    if patch_lines > limit:
        warn("PR 过大，建议拆分为多个小 PR 以利评审")
    return patch_lines <= limit
```

## 五、与其他技术对比

| 维度 | 无评审 | 规范评审 | 过度评审 |
| --- | --- | --- | --- |
| 缺陷泄漏 | 高 | 低 | 低 |
| 流动 | 快但脆 | 平衡 | 拖慢 |
| 成本 | 事后贵 | 适中 | 人耗高 |
| 关注点 | 无 | 设计/安全 | 形式/全批 |

## 六、常见误区

- 「评审 = 找缩进/命名」：这些是 lint 能管的，浪费人的注意力。
- 「PR 巨大也能审」：reviewer 易疲劳草过，漏掉真问题。
- 「人人必批才过关」：强制造就形式化，责任分散。
- 「AI 预审可替代人」：AI 处理明显项，设计权衡仍需人。

## 九、演进与趋势

从「邮件/会议评审」到「PR 异步评审」再到「AI 预评审 + 人聚焦设计」；趋势是把评审 SLA、规模阈值、缺陷逃逸率纳入效能度量，并用 AI 自动标注明显缺陷。

## 十、小结

高效评审靠小批量、快反馈、分层关注：把风格交给工具，把人的注意力留给设计与安全。在「快」与「准」之间取得平衡，才能让评审成为真正有效的质量闸门而非流动瓶颈。
