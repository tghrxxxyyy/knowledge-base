# 网络命名空间基础

> 对应 Linux man namespaces(7) / network_namespaces(7) / clone(2) / unshare(2)。

## 一、背景与挑战

同一份内核要同时服务成百上千个租户或容器，而每个租户都需要"自己的"网卡列表、路由表、iptables 规则、端口空间与 `/proc/net` 视图。若共用一套网络栈，端口冲突、路由互相干扰、规则互相覆盖将不可避免。

网络命名空间（netns）就是这个"网络栈实例"的隔离单元：内核中的网络相关全局变量被拆成按命名空间持有的结构，进程通过 task 结构中的指针指向其中一个实例。理解 netns 的关键是理解**哪些状态被隔离、哪些仍然共享**。

## 二、核心原理

被 netns 隔离的对象包括：

- 网络设备（含 loopback）与它们的配置；
- 路由表与策略路由规则（`ip rule`）、邻居表（ARP/ND）；
- netfilter 规则集（iptables/nftables）与连接跟踪表；
- 套接字绑定关系与协议控制块（因此各 ns 中同一端口互不冲突）；
- `/proc/net/*`、`/sys/class/net/*` 的呈现内容。

共享的则是：内核代码、物理网卡硬件（同一块网卡在同一时刻只能属于一个 ns，除非用 macvlan/ipvlan 派生虚拟接口）、以及底层的 conntrack 内存池等资源上限。

创建方式有三条：

- `clone(CLONE_NEWNET)`：子进程带一个全新 netns 出生；
- `unshare(CLONE_NEWNET)`：当前进程脱离原 netns；
- `setns(fd, CLONE_NEWNET)`：加入已存在的 netns（详见 API 一节）。

新建 netns 中**只有 loopback 且状态为 down**，必须显式 `ip link set lo up`，否则连 `127.0.0.1` 都不可达——这是最常见的排障起点。

## 三、形式化与数学基础

把隔离维度写成集合：

$$NetNS = \{\, ifaces,\ routes,\ rules,\ nft,\ sockets,\ /proc_{net} \,\}$$

进程 $p$ 绑定到命名空间 $n$ 可表示为 $p.ns_{net} = n$；套接字创建时取其创建者的 $ns_{net}$：

$$socket(p) \in p.ns_{net}$$

隔离性可表达为端口唯一性仅在命名空间内成立：

$$\forall a,b:\ a.ns_{net} \neq b.ns_{net} \Rightarrow port(a) \text{ 与 } port(b) \text{ 不冲突}$$

命名空间对象的生命周期由**引用计数**决定：被进程引用、被打开的 nsfs 文件引用、或被 bind mount 引用时保持存活；全部引用消失后内核释放该实例。这解释了为什么 `ip netns add` 能"持久化"一个 netns——`/var/run/netns/<name>` 是一次 bind mount，本身构成引用。

## 四、代码实现

```bash
# 命令行：创建、配置并查看 netns
ip netns add ns1
ip netns exec ns1 ip link set lo up            # 必须！默认 lo 是 down
ip netns exec ns1 ip addr add 10.0.0.2/24 dev veth0
ip netns exec ns1 ip route add default via 10.0.0.1
ip netns list
ip netns pids ns1                               # 找出属于该 ns 的进程
ip -n ns1 link show
```

```c
/* C：创建新 netns 并让子进程在其中运行 */
#define _GNU_SOURCE
#include <sched.h>
#include <unistd.h>

char stack[1 << 20];
int child(void *arg) {
    /* 此处已在新的 netns 中；仅 lo 存在且 down */
    execl("/bin/sh", "sh", (char *)NULL);
    return 1;
}
int main(void) {
    int pid = clone(child, stack + sizeof(stack),
                    CLONE_NEWNET | SIGCHLD, NULL);
    waitpid(pid, NULL, 0);
    return 0;
}
```

注意 `clone` 的栈指针必须指向缓冲区**末尾**（栈向下增长），这是 `clone(2)` 最常被写错的地方。

## 五、与其他技术对比

| 维度 | netns | VLAN（802.1Q） | VR（虚拟路由实例） |
| --- | --- | --- | --- |
| 隔离层次 | 整个网络栈实例 | 二层标签划分 | 三层路由表实例 |
| 隔离粒度 | 接口/路由/规则/端口全隔离 | 仅共享广播域被切分 | 仅路由表隔离 |
| 端口空间 | 独立 | 共享 | 共享 |
| 是否需特权 | 需要相应 capability | 需网络管理权限 | 需网络管理权限 |
| 典型用途 | 容器、CI 沙箱、网络测试 | 数据中心二层隔离 | 多租户路由器 |

同类还有 UTS、PID、mount、user、IPC、cgroup 命名空间，分别隔离主机名、进程号、挂载点、UID/GID 映射、SysV IPC 与资源视图；容器就是若干命名空间的组合。

## 六、常见误区

1. **以为新建 netns 自动有网络**：只有 down 状态的 lo，必须手动配置。
2. **混淆 netns 与 VLAN**：前者是独立协议栈实例（三层可见），后者是同一栈内的二层划分。
3. **以为 netns 与进程一一对应**：多个进程可共享同一 netns，一个进程也可通过多个 fd 引用不同 netns。
4. **忘记 netns 生命周期**：没有进程与挂载引用后 netns 会被销毁，容器退出后 `ip netns list` 中凭空消失即源于此。
5. **忽略 capability 与 user ns 的关系**：在 user namespace 内获得 CAP_SYS_ADMIN 才能创建 netns，rootless 容器依赖这一机制。

## 八、面试题

1. **netns 隔离了什么？** 要点：接口、路由/规则、netfilter 与 conntrack、套接字端口空间、`/proc/net` 与 `/sys/class/net` 视图。
2. **新建 netns 后为什么 ping 不通 127.0.0.1？** 要点：loopback 存在但默认 down，需 `ip link set lo up`。
3. **容器为什么用 netns？** 要点：在不引入独立内核的前提下，为每个容器提供独立的端口空间与网络配置能力。
4. **netns 何时被销毁？** 要点：引用计数归零时——进程退出、fd 关闭且 bind mount 卸载之后。
5. **一个进程能属于多个 netns 吗？** 要点：同一线程同一时刻只属于一个（由 task 指向），但一个进程可打开多个 netns 的 fd，用于操作或后续加入。

## 九、演进与趋势

netns 已从容器基础设施扩展为通用的网络实验与隔离工具：CI 中用它做网络故障注入，eBPF 程序可绑定到具体 netns 做细粒度可观测与策略。内核侧持续推进与 user namespace 的组合（rootless 场景）、netns 内 eBPF 与 cgroup 钩子的协同，以及与 Kubernetes CNI 生态的对接，使"一个 netns = 一个可编程网络域"成为事实标准。

## 十、小结

netns 把内核中原本全局的网络状态结构化为可多实例持有的对象，为容器提供了独立、可配置、可回收的网络栈。掌握"隔离了什么、共享了什么、引用计数决定生命周期、lo 默认 down"这四点，就具备了容器网络排障的基本视角。
