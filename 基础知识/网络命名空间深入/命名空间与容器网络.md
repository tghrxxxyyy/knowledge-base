# 命名空间与容器网络

> 对应 OCI Runtime Spec 与 opencontainers/runc 实现；Docker/CNI 官方文档；Kerrisk《The Linux Programming Interface》命名空间章节。

## 一、背景与挑战

容器不是虚拟机：没有独立内核，没有硬件虚拟化，而是**一组命名空间加 cgroup 约束下的普通进程**。这让容器的启动成本极低，但也意味着网络隔离必须由运行时有意识地构造——内核只提供 netns 这个原语，不提供"容器网络"。

于是产生了分层设计：运行时负责创建 netns 并把接口接好，CNI 插件负责 IP 分配与网络拓扑，kube-proxy 或 eBPF 负责服务发现与负载均衡。理解容器网络，本质是理解这三层各自做了什么、边界在哪里。

## 二、核心原理

一次容器启动的网络动作可分为：

1. `runc` 依据 OCI 配置调用 `clone(CLONE_NEWNET | CLONE_NEWPID | CLONE_NEWUTS | ...)` 创建带新 netns 的进程；
2. 运行时不直接配置网卡，而是把 netns 路径交给 **CNI 插件**（通常为 `/proc/<pid>/ns/net` 或 `/var/run/netns/<name>`）；
3. bridge 插件创建 veth pair，一端移入容器 ns 并重命名为 `eth0`，另一端接宿主网桥；IPAM 插件（如 host-local）分配 IP 与网关；
4. 容器内写入默认路由（指向网桥地址）；宿主侧由 `portmap` 插件签发 DNAT 规则，由 MASQUERADE 完成出网。

**sandbox（pause）容器**的设计要点是：让一个几乎不消耗资源的进程持有 netns，这样应用容器重启时网络配置（IP、veth、规则）保持不变。

网络模式则由"共享哪个 netns"决定：

- `host`：与宿主共用 netns，无隔离、无 NAT 开销、端口直接占用宿主；
- `bridge`（默认）：独立 netns + 桥接 + NAT；
- `none`：独立 netns 但不接线；
- `container:<id>`：与另一容器共享 netns（K8s Pod 内多容器即此模式）；
- overlay：跨主机大二层，由 CNI 网络插件实现。

## 三、形式化与数学基础

容器出网的地址转换可写成：

$$(10.0.0.2{:}1234) \xrightarrow{POSTROUTING,\,MASQUERADE} (host\_ip{:}rand)$$

回包由 conntrack 逆映射回 $(10.0.0.2, 1234)$。独立 netns 带来的直接收益是端口空间解耦：

$$port_A = port_B \nRightarrow conflict,\qquad \text{当 } ns_A \neq ns_B$$

Pod 网络模型可形式化为"每个 Pod 一个 IP、Pod 间无需 NAT 即可互达"：

$$\forall p,q \in Pods:\ reachable(p,q) \;\text{（三层直连，无 NAT）}$$

而 Service 则是叠加在 Pod 网络之上的一层虚拟 IP 映射，其实现在 iptables 模式下规则数随端点数量近似线性增长（

$$|rules| \approx O(|Service| \times |Endpoints|)$$

），这正是大规模集群中转向 IPVS 或 eBPF 的动因。

## 四、代码实现

```c
/* 运行时创建带新网络的容器进程（简化示意） */
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <unistd.h>

char stack[1 << 20];

int child(void *arg) {
    /* 已在新 netns/PID/UTS 中；等待父进程配置 veth 后 exec */
    execl("/usr/bin/pause", "pause", (char *)NULL);
    return 1;
}

int main(void) {
    int flags = CLONE_NEWNET | CLONE_NEWPID | CLONE_NEWUTS | SIGCHLD;
    int pid = clone(child, stack + sizeof(stack), flags, NULL);
    printf("%d\n", pid);                    /* 把 pid 交给 CNI 插件 */
    return 0;
}
```

```bash
# CNI bridge 插件等价的手工拓扑

nsenter -t <container-pid> -n ip route add default via 10.244.1.1
ip link set veth-host master cni0
```

## 五、与其他技术对比

| 维度 | host 模式 | bridge 模式 | overlay 模式 | macvlan 模式 |
| --- | --- | --- | --- | --- |
| 隔离性 | 无 | 强（独立 netns）| 强 | 强 |
| 性能 | 最好（无 NAT/桥） | 中（桥 + NAT） | 中低（封装） | 好（绕过宿主栈）|
| 端口冲突 | 与宿主冲突 | 独立 | 独立 | 独立 |
| 跨主机 | 依赖宿主拓扑 | 需 overlay 或路由 | 原生支持 | 依赖底层二层可达 |
| 典型场景 | 高性能网格代理、监控 | 单机默认 | 多机集群 | 低延迟直连 |

## 六、常见误区

1. **把网络慢归咎于 netns**：netns 本身开销很小，主要成本在 NAT/conntrack、veth 拷贝与封装。
2. **以为容器有独立内核**：共享宿主内核，因此内核版本与模块是所有容器的共同约束。
3. **忽略 pause 容器的意义**：它持有 netns，删掉它会导致 Pod 网络被销毁。
4. **把 Pod IP 当成可持久标识**：Pod 重建后 IP 常变化，稳定寻址应依赖 Service/DNS。
5. **以为 Service 是真实可达地址**：Service IP 是虚拟地址，只在节点上的规则/程序中有意义，集群外不可直接路由。

## 八、面试题

1. **容器网络如何隔离？** 要点：每个容器一个 netns，配以 veth 接入宿主桥，端口与路由彼此独立。
2. **NAT 出网原理？** 要点：容器流量经桥到宿主，POSTROUTING 做 MASQUERADE，回包按 conntrack 逆映射。
3. **host 与 bridge 模式的区别？** 要点：host 共享宿主 netns、无 NAT 开销但端口冲突；bridge 独立 netns、需 NAT 与转发。
4. **为什么 Pod 内多容器能共享网络？** 要点：它们的容器进程加入同一个 netns（由 pause 容器持有），因此共享 IP 与端口空间。
5. **Service 在大规模集群为什么从 iptables 转向 IPVS/eBPF？** 要点：iptables 规则数随 Service×Endpoint 线性增长导致更新与匹配成本上升。

## 九、演进与趋势

CNI 插件化让跨主机网络可替换（Calico/Flannel/Cilium 等）；kube-proxy 从 iptables 转向 IPVS 再到 eBPF 数据路径，减少规则膨胀与一次 netfilter 遍历；容器运行时侧，Pod 沙箱由 CRI 抽象、与 CNI 解耦。未来方向包括：基于 eBPF 的统一数据面与可观测、基于硬件卸载（DPU/SmartNIC）的封装与策略加速，以及 IPv6/双栈下更简化的寻址模型。

## 十、小结

容器网络是"内核 netns 原语 + 运行时接线 + CNI/Service 控制面"三层协作的产物：netns 提供隔离，veth/bridge/NAT 提供连通，CNI 与服务代理提供编排与寻址。理解每层的职责边界与开销来源，才能在性能与连通性问题上快速定位。
