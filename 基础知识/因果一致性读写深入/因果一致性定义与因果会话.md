# 因果一致性定义与因果会话

> 对应 Vogels 2009「Eventually Consistent」；Lamport 1978「Time, Clocks, and the Ordering of Events」；Gilbert & Lynch 2002；Kleppmann《Designing Data-Intensive Applications》第9章。

## 一、背景与挑战

强一致（线性一致）代价高，需要跨节点协调；最终一致又可能让用户在「读自己写」时看到旧值。因果一致性是介于二者的模型：它保证有因果关系的操作按序对所有节点可见，而无因果关系的并发操作可任意交错。这样既避免了最刺眼的反直觉现象（读不到自己刚写的数据、评论早于原帖），又能在网络分区时保持可用。挑战在于：需要一套不依赖全局时钟的因果序定义，以及把这些保证落到「会话」这一工程概念上——因为跨请求的因果上下文若不被保存，保证就会在两次请求之间丢失。

## 二、核心原理

因果一致性要求：若操作 $A$ 因果先于 $B$（$B$ 读取 $A$ 的写入，或 $A$、$B$ 属于同一进程的顺序操作），则所有副本必须先看到 $A$ 再看到 $B$。由此衍生四个常被一起提出的会话保证：读己之写（Read Your Writes）、单调读（Monotonic Reads）、单调写（Monotonic Writes）、写后读（Writes Follow Reads）。它们各自是因果一致的特例，工程上常通过让客户端携带「已见版本向量」并把它附加到后续请求来实现——这就是因果会话（causal session）。因果会话的上下文可以完全放在客户端，服务端无需维护全局会话表，因此天然适合无状态的 HTTP/RPC 接口与多副本负载均衡。

## 三、形式化与数学基础

定义因果序 $\to$ 为满足以下两条的最小自反传递关系：

$$ a \prec_p b \Rightarrow a \to b \quad (\text{同一进程内的顺序操作}) $$
$$ \text{若 } b \text{ 读 } a \text{ 的写，则 } a \to b \quad (\text{读写依赖}) $$

一致性保证：对任意副本视图 $V$，若 $a \to b$ 且 $a \in V$，则必有 $b \in V$，即 $V$ 对 $\to$ 下闭（因果闭包）。用向量时钟表达，则为 $\text{VC}(a) < \text{VC}(b)$ 时禁止倒序可见。层级关系为：

$$ \text{Linearizable} \Rightarrow \text{Sequential} \Rightarrow \text{Causal} \Rightarrow \text{Eventual} $$

从右向左强度递增、约束递增、可用性递减；因果一致正是「保留可用性同时消除因果违例」的分界点。

## 四、代码实现

```python
# 因果会话：客户端携带已见版本向量，服务端据此过滤可见版本
class CausalSession:
    def __init__(self, nid, n):
        self.nid, self.seen = nid, [0] * n

    def on_read(self, key, result_vc, value):
        # 把读到的版本并入已见，形成因果链
        self.seen = [max(x, y) for x, y in zip(self.seen, result_vc)]
        return value

    def on_write(self, key, value):
        # 写请求附上已见向量：服务端须保证这些依赖先可见
        return {"key": key, "value": value, "deps": list(self.seen)}

def visible(item_vc, session_seen):
    # 因果闭包检查：依赖未满足则不可见
    return all(x <= y for x, y in zip(item_vc, session_seen))
```

会话对象把「因果上下文」变成显式状态，从而让无状态的 HTTP/API 也能承载因果保证；客户端需保证把 `seen` 一致地附加到每一次读写请求上。

## 五、与其他技术对比

| 维度 | 最终一致 | 因果一致 | 顺序一致 | 线性一致 |
| --- | --- | --- | --- | --- |
| 排序要求 | 无 | 尊重因果序 | 单一全局序 | 单一全局实时序 |
| 并发写交错 | 任意 | 任意 | 全局统一 | 全局统一 |
| 读己之写 | 不保证 | 保证 | 保证 | 保证 |
| 分区下可用（AP） | 是 | 是 | 否 | 否 |
| 元数据成本 | 无 | 中（依赖向量） | 高 | 高 |
| 典型系统 | Dynamo 默认 | COPS、Riak、MongoDB 会话 | 部分分布式日志 | Spanner、etcd |

## 六、常见误区

1. 认为因果一致等于线性一致：并发写可任意交错，不保证全局单一序。
2. 以为最终一致天然包含因果：纯最终一致可能违反读己之写（读不同副本时）。
3. 混淆单调读与因果一致：单调读是因果一致的一个特例（同一会话不时光倒流）。
4. 把「会话」当作服务端存储：因果会话的上下文可由客户端携带，服务端无需全局表。
5. 忽略依赖向量的传播：任一跳丢失依赖，后续整条因果链都失效。
6. 认为四个会话保证彼此等价：它们刻画不同维度，实现手段与代价各不相同。

## 七、与开源书·权威来源对应

- Vogels 2009「Eventually Consistent」系统列出最终一致的各类会话保证。
- Lamport 1978 给出 happens-before 偏序，是因果序的定义来源。
- Gilbert & Lynch 2002 形式化 CAP，说明因果一致在分区下的可用性优势。
- Kleppmann《Designing Data-Intensive Applications》第9章梳理一致性层级与因果先于关系。
- 具体系统支持的会话保证，以官方最新文档为准。

## 八、面试题

1. 因果一致与最终一致的本质差别？——前者保证因果相关操作按序可见，后者只保证无新写后收敛。
2. 读己之写如何实现？——客户端携带已见版本（或粘性路由），读请求要求不早于该版本。
3. 为什么因果一致能在分区下保持可用？——它不要求全局单一序，只需因果闭包，AP 复制即可满足。
4. 因果序 $\to$ 的两条来源是什么？——同进程顺序操作、以及写后读的读写依赖。
5. 单调读与因果一致的关系？——单调读是因果一致的特例，保证同一会话读到的版本不回退。

## 九、演进与趋势

因果一致正在成为「可用且合理」的默认选择，被 COPS、Riak、以及多家云数据库以「会话一致性」形式提供。趋势包括：把依赖元数据内建于 SDK 与代理层、与 CRDT 结合实现无协调合并，以及在边缘场景下用因果会话替代昂贵的强一致读。具体支持范围以官方最新文档为准。

值得注意的是，因果会话的元数据体积会随会话长度增长，因此生产系统通常会为会话设置上限，并在超过阈值时通过重放或重新同步来收缩依赖。

这与向量的「紧凑化」问题同源：本质是在不确定的因果历史上，寻找一个有界的可比较摘要。

## 十、小结

因果一致性在可用性与合理性之间取得平衡，核心是保证因果闭包可见；而「因果会话」把抽象的偏序保证落到可携带的客户端上下文上，是它能在工程中大规模落地的关键。
