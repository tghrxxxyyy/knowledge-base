# COPS系统因果写

> 对应 Lloyd et al. 2011「Don't Settle for Eventual: Scalable Causal Consistency for Wide-Area Storage」（COPS）；Kleppmann《Designing Data-Intensive Applications》第9章；Lamport 1978。

## 一、背景与挑战

COPS 是首批在地理分布式 KV 存储上同时提供「因果一致 + 读己之写 + 单调读」并保持高可用的系统。其难点在于：写操作跨数据中心异步复制时，如何在不引入全局同步的前提下保证因果顺序。若副本应用了新版本却缺失其因果前驱，读端就会看到「悬空」状态（评论存在但原帖缺失）。COPS 的核心思路是让每个写携带显式的依赖集，并在目标副本按依赖顺序应用，把「顺序问题」转化为「依赖是否已满足」的局部判定。代价是写路径必须额外记录并传播依赖元数据，且依赖链越长、跨区收敛越慢。

## 二、核心原理

COPS 为集群划分若干分区，每个分区由一个本地数据中心内的一个节点组管理，所有分区共享一个中心化的顺序服务（用于分配严格递增的版本号）。写路径：客户端 `put` 先在本地数据中心的对应分区提交，提交时记录该写在本地已见到的版本作为依赖集；随后异步复制到其他数据中心的分区，复制时先检查依赖副本是否可见，不可见则暂存等待。读路径：`get` 在本地分区返回当前可见版本；`get_transaction`（COPS-GT）返回一个包含依赖信息的快照，供后续读做因果检查。两种写模式：非保守模式写立即确认、依赖稍后满足；保守模式（COPS with transactions）等待依赖在目标可见后才确认，代价是更高延迟。

## 三、形式化与数学基础

所有写与其依赖构成有向无环图 $G = (V, E)$，边 $u \to v$ 表示 $v$ 依赖 $u$（$v$ 的依赖集中含 $u$）。复制调度必须保证每个 $v$ 的所有前驱在其之前应用，即按拓扑序应用：

$$ \forall (u, v) \in E:\; apply(u) \prec apply(v) $$

由于 $G$ 无环（版本号严格递增，$u$ 的版本号必小于 $v$），拓扑序存在且可由「入度归零」算法在线构造。依赖集大小上界为写路径读到的 key 数量，记为 $|D|$，复制检查成本为 $O(|D|)$，与全局分区数无关，这是 COPS 可扩展性的来源。若把依赖集视为向量时钟的一种稀疏表示，则「应用前检查依赖」等价于「要求目标副本的版本向量逐分量不小于该写的依赖向量」。

## 四、代码实现

```python
# 复制端：按依赖拓扑序应用写，前驱未到则暂存等待
from collections import deque

def apply_in_order(writes, store, pending):
    indeg = {w.id: len(w.deps) for w in writes}
    ready = deque(w for w in writes if indeg[w.id] == 0)
    while ready:
        w = ready.popleft()
        store.put(w)
        for child in w.children:            # 依赖 w 的后继
            indeg[child.id] -= 1
            if indeg[child.id] == 0:
                ready.append(child)
    # 仍有入度者说明前驱未到，暂存待补
    for w in writes:
        if indeg[w.id] > 0:
            pending[w.id] = w

def replicate(w, deps_visible, store, pending):
    if not deps_visible(w.deps, store):     # 依赖不可见 -> 不落地
        pending[w.id] = w
        return
    store.put(w)                            # 依赖已满足，安全应用
```

关键约束：落地前必须验证依赖可见，否则会破坏因果闭环，读端将暴露悬空状态。暂存的写需要超时与重试机制，避免因单个前驱丢失而永久滞留。

## 六、常见误区

1. 认为 COPS 是线性一致：它是因果一致，并发写可任意交错，不保证全局单一序。
2. 忽略依赖传播成本：跨区写延迟随依赖链长度增加，读到的版本越新、带出的依赖越多。
3. 混淆 causal 与 conservative 模式：后者在依赖满足后才确认写，提供更强的事务性因果。
4. 认为依赖可以只记单个 key：依赖必须覆盖写时读到的全部版本，否则因果链断裂。
5. 把拓扑序当作固定顺序：拓扑序不唯一，只要求「前驱先于后继」这一偏序约束。
6. 忽略暂存写的清理：前驱长时间不到会占用内存，需超时淘汰或向上游重拉。

## 八、面试题

1. COPS 如何保证副本不悬空？——写携带依赖集，复制端按拓扑序应用，前驱必先于后继落地。
2. 为什么依赖检查只需 $O(|D|)$？——检查范围限于写自身携带的依赖集，与集群规模无关。
3. COPS 的写为什么可以异步确认？——非保守模式下依赖由复制端异步满足，读端通过检查避免违例。
4. COPS 与 Spanner 的核心取舍差异？——前者保可用性与确定性因果，后者用时间同步换取外部一致性。
5. 保守模式带来什么好处与代价？——好处是事务性因果保证；代价是写延迟升高、吞吐下降。

## 九、演进与趋势

COPS 的依赖跟踪与因果复制思想已融入现代多活数据库、边缘 KV 与 CRDT 框架，常以「依赖广播 + 无协调合并」的组合出现。趋势是把依赖元数据下沉到存储引擎与 SDK，并通过压缩依赖集降低跨区开销。具体实现以官方最新文档为准。

另一个方向是把「因果一致」与「可调一致性」结合：同一集群内按 key 或按请求选择强度，让热路径保持低延迟、关键路径获得更强保证。

这类分级设计的关键在于统一版本表示，使同一份元数据可以在不同强度之间复用。

## 十、小结

COPS 用显式依赖集与拓扑序复制，在可用性与因果正确性之间取得实用平衡，证明弱一致性模型也能提供「逻辑合理」的用户体验，是后续因果一致系统的原型。
