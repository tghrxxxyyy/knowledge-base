# 因果一致性读实现

> 对应 COPS 论文（Lloyd et al. 2011）与 Vogels 2009。

## 一、背景与挑战
在最终一致存储上实现「因果读」：客户端读到某版本后，后续读必须看到该版本及其因果祖先，不能看到「来自未来」的、因果未闭合的状态。否则用户会看到矛盾（如看到评论却看不到原帖）。

## 二、核心原理
每次写返回一个依赖向量（causal dependency metadata）。客户端在后续请求中携带来保证读取满足因果闭包。副本在返回数据前检查：所返回状态是否包含客户端依赖的所有版本，否则等待或重定向。

## 三、形式化与数学基础
设客户端依赖集 \\(D\\)，副本状态 \\(S\\)，则允许返回当且仅当 \\(D\subseteq causal(S)\\)（D 是 S 因果闭包的子集）。形式化为偏序上的下闭包检查。

## 四、代码实现
```python
def can_serve(client_deps, store_version):
    for node, ver in client_deps.items():
        if store_version.get(node, 0) < ver:
            return False
    return True
```

## 五、与其他技术对比
线性一致读需共识或 Raft 读路径；因果读只需元数据检查，延迟更低、可用性更高；COPS 即此思路。

## 六、常见误区
1. 以为因果读保证全局最新：只保证因果闭合，不保证看到他人并发写。
2. 忽略依赖向量膨胀：长会话依赖需压缩。
3. 在跨数据中心忘记传递依赖：断链导致因果违例。

## 七、与开源书/权威来源对应
COPS 系统论文给出因果读协议；Vogels 2009 定义读己之写等会话保证。

## 八、面试题
问：因果读与线性读区别？
答：因果读只要求因果闭包可见，线性读要求读取最新全局值。

## 九、演进与趋势
将依赖跟踪内建于存储引擎与客户端 SDK，降低使用门槛。

## 十、小结
因果读通过依赖向量保证不读「矛盾状态」，是可用因果系统的关键读路径。
