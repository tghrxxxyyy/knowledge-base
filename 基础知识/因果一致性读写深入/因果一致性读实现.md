# 因果一致性读实现

> 对应 Lloyd et al. 2011「Don't Settle for Eventual: Scalable Causal Consistency for Wide-Area Storage」（COPS）；Vogels 2009「Eventually Consistent」；Kleppmann《Designing Data-Intensive Applications》第9章。

## 一、背景与挑战

在最终一致的 KV 存储上实现「因果读」：客户端读到某版本后，后续读必须看到该版本及其全部因果祖先，不能看到因果未闭合的「来自未来」的状态，否则用户会看到矛盾（如看到评论却看不到原帖）。难点在于：副本各自异步接收更新，任意时刻可能只应用了依赖 DAG 的一部分；读请求要在不引入全局同步的前提下，判断本地状态是否已满足客户端的因果依赖，不满足则等待、重定向或阻塞。这要求读路径携带依赖元数据，并在副本侧做闭包检查。此外，依赖元数据必须随客户端的读操作持续累积，否则跨多次请求的因果链会断裂。

## 二、核心原理

每次写提交时由协调节点计算一个「依赖集」（通常是一组 key 版本号或向量时钟），记录该写因果依赖的先前版本。客户端在会话中累积已见版本，后续读请求带上该依赖集。副本收到读请求后检查：本地状态是否已应用客户端依赖的全部版本；若否，则按策略等待（阻塞读）或转发到已满足的副本。写路径可选两种模式：非保守（写先落地、依赖异步满足，读端检查）与保守（写等待其依赖在目标副本可见后才确认），后者提供更强的因果事务保证。COPS 还提供 `get_transaction`：返回一个带依赖信息的快照，供后续读继续做因果检查，从而在客户端侧维持一条连续的因果上下文。

## 三、形式化与数学基础

设客户端依赖集 $D$（key 到版本号的映射），副本状态 $S$ 给出每个 key 的可见版本 $S[k]$，允许返回当且仅当：

$$ \forall k \in dom(D):\; S[k] \ge D[k] $$

等价表述是 $D \subseteq causal(S)$，即 $D$ 落在 $S$ 的因果闭包内。因果闭包定义为沿 happens-before 边的下闭包：

$$ causal(S) = \{ v' \mid \exists v \in S,\; v' \to v \} $$

因果一致性的读保证即：若 $w \to r$ 且 $w$ 属于 $D$，则任何服务 $r$ 的副本视图都必须包含 $w$。检查复杂度为 $O(|D|)$，与全局节点数无关，这是因果读延迟低于线性读的根本原因。

## 四、代码实现

```python
# 副本侧因果读：依赖闭包检查 + 等待重试
import time

def can_serve(client_deps, store_version):
    for k, ver in client_deps.items():
        if store_version.get(k, 0) < ver:      # 本地尚未应用该依赖
            return False
    return True

def causal_read(key, client_deps, store, deadline=1.0):
    t0 = time.monotonic()
    while True:
        if can_serve(client_deps, store.version_map()):
            item = store.get(key)
            # 返回时把「新读到的版本」并入依赖，形成因果链
            client_deps[key] = max(client_deps.get(key, 0), item.version)
            return item
        if time.monotonic() - t0 > deadline:
            raise TimeoutError("deps not satisfied, try another replica")
        time.sleep(0.002)                        # 或直接转发到远端副本
```

等待策略的选择是工程权衡：阻塞读延迟低但占用连接；转发读能快速返回但增加跨域流量；若依赖长期无法满足，还需考虑降级为「返回可读版本并提示陈旧度」。

## 五、与其他技术对比

| 维度 | 最终一致读（任意副本） | 因果读 | 会话单调读 | 线性一致读 |
| --- | --- | --- | --- | --- |
| 元数据需求 | 无 | 依赖集/向量时钟 | 每会话位置 | 无（但要共识） |
| 是否读己之写 | 不保证 | 保证 | 保证 | 保证 |
| 是否全局最新 | 否 | 否（只保因果） | 否 | 是 |
| 读延迟 | 最低 | 低 | 低 | 高（需协调） |
| 分区下可用性 | 高 | 高（AP） | 高 | 低（CP） |
| 实现复杂度 | 低 | 中（依赖传播） | 低 | 高 |

## 六、常见误区

1. 以为因果读保证全局最新：它只保证因果闭合，不保证看到他人并发写的最新值。
2. 忽略依赖集膨胀：长会话累积大量依赖，需要压缩、合并或定期重置。
3. 跨数据中心忘记传递依赖：断链会让远端副本误判可见性，造成因果违例。
4. 只检查「读的 key」而忽略传递依赖：依赖应包含写时读到的所有版本，而非单一 key。
5. 把等待无限延长：必须有超时与转发策略，否则单个慢副本会拖垮读可用性。
6. 认为 `get` 与 `get_transaction` 等价：后者携带依赖信息，是维持因果上下文的必要手段。

## 八、面试题

1. 因果读与线性读的区别？——因果读只要求因果闭包可见，线性读要求读到全局最新的提交。
2. 副本如何判断能否服务一次因果读？——检查客户端依赖集是否被本地版本映射逐项覆盖。
3. 为什么因果读延迟通常低于线性读？——只需本地元数据检查，无需跨节点共识或多数派确认。
4. 依赖集为什么会膨胀，如何处理？——长会话累积写依赖；可压缩向量、合并区间或定期重置。
5. COPS 的保守模式与普通模式有何差异？——保守模式在依赖可见后才确认写，提供事务性因果保证但延迟更高。

## 九、演进与趋势

趋势是把依赖跟踪内建到存储引擎与客户端 SDK，让开发者无需手写元数据；并把因果读与 CRDT 合并结合，形成「因果广播 + 无协调合并」的组合。跨区域部署上，依赖压缩与部分可见性优化是关键方向。具体能力以官方最新文档为准。

另一条路线是把因果读的判定前移到客户端 SDK：由 SDK 维护依赖集并选择「满足依赖的最近副本」，把等待逻辑从服务端移出，减少连接占用。

这类设计的关键是让 SDK 与服务端对版本号语义达成一致，否则依赖比较会因版本表示差异而误判。

## 十、小结

因果读通过依赖集与因果闭包检查，在不引入全局同步的前提下保证读到「逻辑合理」的状态，是可用因果系统的关键读路径；其工程难点集中在依赖的传播、压缩与等待/转发策略。
