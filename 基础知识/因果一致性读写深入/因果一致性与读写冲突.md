# 因果一致性与读写冲突

> 对应 Shapiro et al. 2011「Conflict-free Replicated Data Types」；Lamport 1978「Time, Clocks, and the Ordering of Events」；Kleppmann《Designing Data-Intensive Applications》第9章。

## 一、背景与挑战

分布式副本允许并发写，冲突不可避免。线性一致用全局串行化消解冲突，代价是跨节点协调与高延迟；因果一致放宽为「只要求因果相关的写按序可见」，于是必须显式回答另一个问题：两个互相不可见的并发写如何合并？如果合并策略不确定、不满足结合律或不幂等，副本会永久发散。核心挑战是把「冲突检测」（由因果序判定）与「冲突消解」（由合并函数执行）彻底分离，并让合并对乱序投递、重传、重复投递都稳健。此外，副本间的后台同步（anti-entropy）还要能以有限带宽发现并补齐差异。

## 二、核心原理

对因果相关的更新按因果序应用；对并发更新应用合并函数 $\sqcup$，要求所有副本对同一组并发更新产生相同结果。典型策略：LWW（Last-Writer-Wins）以「时间戳 + 节点 id」做确定性 tie-break；G-Counter 对每个节点分量取 max 后求和；OR-Set 用「添加标签集合减去删除标签集合」实现可交换增删；PN-Counter 由一对 G-Counter 表达增减。合并必须绑定在「状态」而非「操作」上，才能在乱序与重复投递下收敛。CRDT 分两类：基于状态的 CvRDT（合并即半格 join，可容忍消息丢失后由 anti-entropy 补齐）与基于操作的 CmRDT（广播操作，要求可靠因果投递）。后台同步常用 Merkle 树比对摘要，只传输差异子树。

## 三、形式化与数学基础

设 $\sqcup$ 为合并算子，收敛要求 $(S, \sqcup)$ 构成 join 半格：

$$ a \sqcup b = b \sqcup a \quad (\text{交换律}) $$
$$ (a \sqcup b) \sqcup c = a \sqcup (b \sqcup c) \quad (\text{结合律}) $$
$$ a \sqcup a = a \quad (\text{幂等律}) $$

交换律保证投递顺序无关，结合律保证分组无关，幂等律保证重复投递无害，三者合起来给出「任意投递顺序结果一致」。CvRDT 还要求合并单调不减 $a \sqsubseteq a \sqcup b$ 且状态空间有界，从而任意合并序列收敛到最小上界。并发由 happens-before 偏序定义：若 $a \not\to b$ 且 $b \not\to a$，则 $a \parallel b$，交由 $\sqcup$ 处理。

## 四、代码实现

```python
# CvRDT 两个实例：LWW 寄存器与 G-Counter
class LWW:
    def __init__(self):
        self.ts, self.node, self.val = 0, "", None
    def write(self, val, ts, node):
        self.ts, self.node, self.val = ts, node, val
    def merge(self, other):
        # 时间戳大者胜；相等时以 node id 确定性 tie-break，禁止读时钟/随机数
        if (other.ts, other.node) > (self.ts, self.node):
            self.ts, self.node, self.val = other.ts, other.node, other.val

class GCounter:                       # 只增计数器，每个副本一个分量
    def __init__(self, n):
        self.v = [0] * n
    def inc(self, i):
        self.v[i] += 1
    def merge(self, other):
        self.v = [max(x, y) for x, y in zip(self.v, other.v)]
    def value(self):
        return sum(self.v)            # 收敛后各副本读数一致

def sync(a, b):                       # 双向合并，anti-entropy 的基本动作
    a.merge(b); b.merge(a)
```

`merge` 必须是纯确定性的状态合并：一旦引入本地时钟或随机数，LWW 的结果就依赖副本，收敛性被破坏。

## 五、与其他技术对比

| 维度 | 悲观锁/2PC | 纯因果一致（无合并） | CRDT（因果 + 合并） | 线性一致 |
| --- | --- | --- | --- | --- |
| 并发写处理 | 拒绝并发 | 允许但需外部合并 | 允许且自动合并 | 全局串行化 |
| 分区下可用性 | 低（需多数派） | 高 | 高 | 低（CP） |
| 收敛保证 | 靠锁保证一致 | 依赖应用合并 | 代数保证收敛 | 强一致 |
| 写入延迟 | 高（同步） | 低 | 低 | 高（共识） |
| 元数据成本 | 低 | 中（依赖向量） | 中高（状态/墓碑） | 低 |
| 典型场景 | 银行转账 | 会话因果读 | 协作编辑、离线优先 | 配置中心 |

## 六、常见误区

1. 认为因果一致自动解决并发冲突：它只规定因果相关的顺序，并发仍必须有合并策略，否则发散。
2. 认为 LWW 总是正确：并发写中「时间戳较小」的一方被静默丢弃，业务语义可能不允许。
3. 合并非幂等：重复投递会让计数翻倍，副本再也无法收敛。
4. 用本地墙上时钟做时间戳：时钟漂移使 LWW 结果依赖副本，破坏确定性。
5. 混淆 CvRDT 与 CmRDT 的前提：CmRDT 依赖可靠因果广播，丢消息即发散。
6. 忽略墓碑膨胀：删除操作需长期保留标记，状态体积会随删除次数单调增长。

## 八、面试题

1. CRDT 收敛的三个代数性质是什么？——交换律、结合律、幂等律。
2. 因果一致与 CRDT 是什么关系？——前者定义「何时必须有序」，后者定义「并发如何合并」，互补。
3. LWW 的主要缺陷？——静默丢更新，且依赖时钟，必须用确定性 tie-break。
4. 为什么合并必须幂等？——否则重传会使状态漂移，副本无法收敛。
5. CvRDT 与 CmRDT 的差别？——前者合并状态、容忍乱序；后者广播操作、依赖因果可靠投递。

## 九、演进与趋势

CRDT 已成为 local-first 与协作编辑的核心（Automerge、Yjs 等）。演进方向包括 delta-state CRDT 压缩同步开销、减少墓碑与状态膨胀、以及把因果广播与合并解耦以支撑大规模部署。具体能力以官方最新文档为准。

另一个方向是把合并语义与访问控制、审计结合：在保留收敛性的同时记录「谁合并了什么」，以支撑需要可追溯性的合规场景。

## 十、小结

因果一致解决「有序」问题，CRDT 用满足交换/结合/幂等的合并解决「并发合并」问题，二者互补构成无协调收敛的理论与工程基础。
