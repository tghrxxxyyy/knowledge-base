# 构建缓存与增量构建

> 对应 Humble & Farley 2010（Continuous Delivery）与 Bazel/构建系统内容寻址思想。

## 一、背景与挑战
大型仓库全量构建耗时长，重复编译未变更模块浪费算力，拖慢 CI 反馈、降低提交频率，进而削弱 CI 的价值。核心矛盾：大多数提交只改少数文件，却触发整仓重建。构建缓存与增量构建通过「跳过未变更工作」消除这种浪费，是规模化 CI 的必备优化。

在单体仓库（monorepo）与超大型服务中，一次全量构建可能数十分钟，若不优化，开发者每次推送都要等半天才知道结果，CI 形同虚设。缓存与增量是让 CI「快得愿意高频使用」的关键。

需要强调：缓存与增量的首要目标不是「快」，而是「快且正确」。一个错误的缓存命中比不缓存危害更大——它会让 CI 静默地验证错误产物。

## 二、核心原理
通过内容寻址缓存（对源文件、依赖、编译器标志计算哈希）复用已有产物；增量构建只重新编译「受变更影响的编译单元及其下游」。判定影响范围的依据是模块依赖图：变更集合的传递闭包才是需重建集合。

缓存可分级——本地（快但不共享）与远程（跨机器共享，接近本地体验）。命中条件必须是「所有输入完全一致」，任何遗漏都会导致脏缓存。

因此，缓存键的设计是核心工程问题：它必须覆盖源、依赖、参数、工具链等全部影响产物的因素。

## 三、形式化与数学基础
设模块依赖图 $G=(V,E)$，变更集合 $C$。需重建集合：

$$ V' = C \cup \{ v \mid \exists u \in C,\ \text{path}(u \to v) \text{ 在 } G \text{ 中} \} $$

即变更节点及其所有下游。缓存命中条件：输入（源哈希、依赖哈希、编译参数、工具链版本）完全一致，则跳过编译直接取缓存产物。

$$ \text{hit}(a) \iff \text{hash}(\text{src}, \text{deps}, \text{flags}, \text{toolchain}) = \text{cacheKey} $$

内容寻址要求产物可仅由输入确定，故禁止把时间戳等非确定性信息写入产物。若任一输入 $i$ 改变（$\text{hash}(i) \neq \text{hash}'(i)$），则对应产物失效、触发重建。

## 四、代码实现
```bash
# Bazel 风格：输入哈希命中则复用远程缓存
bazel build //service:all --remote_cache=grpc://cache:9090

# 本地依赖缓存（npm）
npm ci --prefer-offline

# Gradle 构建缓存开启
./gradlew build --build-cache

# 命中判断（示意）：
# key = hash(sources + deps + flags + toolchain)
```

Bazel 的 action cache 以「输入文件集合的 Merkle 树哈希」为键；Gradle 的 build cache、Rust 的 sccache、C++ 的 ccache 同理。远程缓存需注意「缓存污染」：不同机器若工具链略有差异，缓存键必须包含工具链指纹，否则会取出不兼容产物。

## 五、与其他技术对比

| 方式 | 速度 | 正确性风险 | 共享 |
| --- | --- | --- | --- |
| 全量构建 | 慢 | 低 | 否 |
| 增量构建 | 快 | 依赖推导错则漏编 | 否 |
| 本地缓存 | 快 | 键错则脏 | 否 |
| 远程缓存 | 最快 | 键错则脏 | 是 |
| 可重现构建 | 快且可验证 | 最低 | 是 |

增量构建省时但需正确推导依赖；远程缓存跨机器共享、接近本地体验，但缓存键必须包含全部输入。二者常叠加：先增量确定受影响集，再对每个集查远程缓存。

## 六、常见误区
- 误区一：缓存键未含环境变量。导致「相同源码不同结果」的脏缓存。
- 误区二：把时间戳写入产物。破坏内容寻址，缓存永不命中。
- 误区三：增量构建万能。宏/全局配置变更需触发更广重建，依赖图要准确。
- 误区四：缓存无限保留。应设保留策略，避免存储膨胀与陈旧产物。
- 误区五：缓存命中即正确。若工具链版本未进缓存键，可能取到旧工具链产物。
- 误区六：远程缓存天然可信。跨团队共享时需命名空间隔离，防止不同分支互相污染。
- 误区七：只优化编译、忽略测试。测试结果同样可缓存，但需保证测试输入完整。

## 七、与开源书·权威来源对应
Humble & Farley 2010 强调「只构建一次」并全程复用同一产物，避免构建不一致。Bazel（Google）把内容寻址与依赖图增量构建工程化；ccache 等是编译缓存实践。

Kleppmann《DDIA》在「数据与代码」章也强调可重现构建。Reproducible Builds 项目进一步要求字节级一致，使缓存正确性可被独立验证。具体工具行为以官方最新文档为准。

## 八、面试题
- 问：如何设计缓存键保证正确？答：包含源哈希、依赖哈希、编译参数、工具链版本，排除非确定信息。
- 问：增量构建如何处理宏/配置变更？答：把宏/全局配置作为依赖图的额外边，触发下游重建。
- 问：本地与远程缓存取舍？答：本地快不共享，远程共享但需网络，常组合使用。
- 问：时间戳为何破坏缓存？答：每次构建时间不同使哈希变化，缓存永远失效。
- 问：如何防缓存污染？答：缓存键纳入工具链指纹与全部输入，必要时命名空间隔离。
- 问：测试结果能否缓存？答：可以，但需保证测试输入（代码、依赖、环境）完整纳入键。
- 问：增量构建依赖什么？答：准确的模块依赖图，否则会漏编下游。

## 九、演进与趋势
远程构建缓存与构建网格（Build Farm）让 CI 节点共享结果，接近本地体验；「可重现构建（reproducible builds）」消除环境差异使缓存更可靠；云原生构建（如 BuildKit 缓存层）把缓存下沉到镜像构建层。

缓存命中率正成为 CI 性能的核心 SLO，与构建时长一起被持续监控。相关实践以官方最新文档为准。

从工程度量看，除命中率外还应关注「缓存体积」「失效频率」「跨节点命中占比」，它们共同决定远程缓存的真实收益。

从正确性看，建议为缓存实现「可关闭开关」：一旦怀疑脏缓存，能一键回退到全量构建，快速排除干扰。

从团队协作看，远程缓存应做命名空间隔离（按分支或按项目），避免实验性分支的产物污染主干缓存。

从构建脚本看，应避免在构建过程中做不可复现的操作（如读系统时间、随机数、外部网络），否则会持续击穿缓存。

## 十、小结
缓存与增量构建用「哈希 + 依赖图」消除重复工作，是规模化 CI 的必备优化；正确性是前提——缓存键必须覆盖全部输入，且产物须内容可寻址。把缓存命中率与构建时长纳入可观测，是持续保持 CI 高速的工程纪律。
