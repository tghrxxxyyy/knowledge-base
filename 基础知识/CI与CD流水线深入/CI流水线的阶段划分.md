# CI流水线的阶段划分

> 对应 Humble & Farley 2010（Continuous Delivery）与 Fowler《Refactoring》持续集成实践。

## 一、背景与挑战
代码合入主干后若缺乏自动化验证，缺陷会累积到发布前集中爆发，形成「集成地狱」。CI（持续集成）的目标是把「集成痛苦」提前、高频地发生：每次提交都触发一次构建与验证，让问题尽早暴露。阶段化是 CI 的核心组织方式——把验证拆成有序、可中断的环节，任一环节失败即整体失败，保证主干始终处于「可发布」状态。

历史上，团队常把集成推迟到「功能都写完」才做，结果合并冲突与隐藏缺陷集中爆发，修复成本指数级上升。CI 通过「每日多次、甚至每次提交」的集成，把成本摊薄到每次小变更，这正是其价值所在。

阶段划分的质量直接决定反馈速度：一个设计糟糕的流水线会让开发者等很久才拿到结果，从而降低提交频率，反过来削弱 CI 的意义。

## 二、核心原理
典型 CI 流水线顺序为：代码检出 $\to$ 依赖安装 $\to$ 静态检查（lint/类型） $\to$ 编译/构建 $\to$ 单元测试 $\to$ 集成测试 $\to$ 产物归档。每个阶段是「质量闸门」：上游失败则下游不执行，从而「快速失败（fail fast）」，把反馈时延降到最低。

阶段间应解耦、可独立复跑；产物在构建阶段产出后由后续阶段复用，避免重复构建。原则是「一次构建、处处验证」。把「快而广」的检查（lint、单测）放在最前，把「慢而窄」的检查（端到端、性能）放在最后，是缩短平均反馈时间的关键排序。

此外，阶段应尽量「幂等」：重复执行同一阶段不产生副作用，这样失败重试才是安全的。

## 三、形式化与数学基础
设阶段序列 $P = [p_1, \dots, p_n]$，每阶段有通过谓词 $\text{ok}(p_i)$。流水线成功等价于：

$$ \bigwedge_{i=1}^{n} \text{ok}(p_i) = \text{true} $$

失败及早返回：若第 $k$ 阶段失败，则反馈时延约 $\sum_{i=1}^{k} t(p_i)$，远小于跑完全部。

理想情况下各阶段可并行（如单元与集成测试在独立 Agent 并发），整体时延由最长路径决定（关键路径），故阶段划分也影响总反馈速度。若阶段间有依赖，可建模为 DAG，并行度受关键路径限制。设关键路径长度 $L$，则流水线最短完成时间为 $L$，优化目标即缩短 $L$。

## 四、代码实现
```yaml
stages:
  - build
  - test
  - package

build:
  stage: build
  script:
    - ./gradlew compileJava        # 编译失败立即中断
test:
  stage: test
  needs: ["build"]
  script:
    - ./gradlew test               # 单测是质量门禁
package:
  stage: package
  needs: ["test"]
  script:
    - ./gradlew assemble           # 产出不可变制品
```

GitLab CI 的 `needs` 字段即表达阶段间 DAG 依赖，允许 `test` 在 `build` 完成后立即并行于其他无关阶段。Jenkins、GitHub Actions 等也有类似 stage/needs 机制。把「快而广的单测」放在「慢而窄的端到端」之前，能最快拦截大部分回归。

## 五、与其他技术对比

| 方式 | 环境 | 产物 | 终点 |
| --- | --- | --- | --- |
| 本地手工构建 | 不一致 | 易漂移 | 不可靠 |
| CI 自动化 | 一致 | 不可变 | 可部署 |
| CI + CD | 含自动发布 | 不可变 | 生产运行 |
| GitOps | 声明式 | 不可变 | 持续对齐 |

相比本地手工构建，CI 提供一致环境与不可变产物；相比 CD，CI 止步于「可部署」，不自动发布到生产。CI 是 CD 的前提：没有可靠的 CI，自动化发布只会在不可信的构建上加速出错。

## 六、常见误区
- 误区一：提交后长时间不触发构建。失去快速反馈意义，CI 价值在于「高频」。
- 误区二：流水线里跑不稳定端到端测试。制造假红、阻断合入，应隔离为可重试门禁。
- 误区三：阶段间传递源码而非制品。重复构建导致环境不一致与漂移。
- 误区四：CI 等同「跑测试」。CI 还包括静态检查、构建、制品归档等质量屏障。
- 误区五：阶段越多越好。过多串行阶段拉长关键路径，应把可并行的尽量并行。
- 误区六：所有检查都串行执行。可并行的阶段应并行，否则关键路径被人为拉长。
- 误区七：失败后继续跑完全部阶段。快速失败才能把反馈时延降到最低。

## 七、与开源书·权威来源对应
Humble & Farley 2010 提出「每次提交都应触发一次构建」，并强调自动化是部署流水线的基石。Fowler 的「Continuous Integration」一文定义每日多次合入与自动化构建的实践。Kleppmann《DDIA》讨论自动化验证的思路。

Accelerate 把「主干开发 + CI」列为高效能团队关键指标，并指出部署频率与前置时间由 CI/CD 成熟度决定。具体实践细节以原文与官方最新文档为准。

## 八、面试题
- 问：CI 与 CD 区别？答：CI 止于可部署，CD 自动化发布到生产。
- 问：为何测试要分层？答：单测快而多、端到端慢而少，分层兼顾速度与覆盖。
- 问：如何缩短反馈时间？答：并行阶段、缓存依赖、失败快速返回、隔离不稳定测试。
- 问：为何要一次构建？答：保证后续环境验证的是同一个产物，杜绝漂移。
- 问：阶段顺序有何讲究？答：快而广的检查前置，慢而窄的后置，缩短平均反馈时延。
- 问：为何阶段要幂等？答：失败重试安全，不会产生重复副作用。
- 问：关键路径如何影响流水线？答：流水线最短完成时间等于关键路径长度，优化需从它入手。

## 九、演进与趋势
向预提交（pre-commit）/预合并检查演进，结合 Bazel 等增量构建与远程缓存进一步提速；「可观测的流水线」把每阶段时延、失败率可视化；合并队列（merge queue）在合入前自动排队验证，避免主干被破坏。

AI 辅助的「失败归因」也开始进入 CI，自动定位是测试、依赖还是环境导致红。相关工具与实践以官方最新文档为准。

此外，流水线的「可复现性」也日益重要：同一提交在不同时间、不同 Agent 上跑出的结果应一致，否则红绿结论本身都不可信。

## 十、小结
CI 用自动化验证把集成风险前置，阶段化与快速失败是其设计核心；一次构建、处处验证，保证主干始终可发布。理解阶段作为「质量闸门」与 DAG 关键路径的关系，是设计高效流水线的出发点。
