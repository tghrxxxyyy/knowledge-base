# CI流水线的阶段划分

> 对应 Humble & Farley 2010 (Continuous Delivery)。

## 一、背景与挑战
代码合入后若缺乏自动化验证，缺陷会累积到发布前集中爆发。CI 的目标是把集成痛苦提前并高频发生。

## 二、核心原理
一次典型的 CI 流水线分为：检出 -> 依赖安装 -> 静态检查 -> 编译/构建 -> 单元测试 -> 集成测试 -> 产物归档。任一阶段失败即中断，保证主干始终可发布。

## 三、形式化与数学基础
设阶段序列 P = [p1..pn]，每阶段有通过谓词 ok(pi)。流水线成功等价于 AND_i ok(pi) == true。失败及早返回降低反馈时延。

## 四、代码实现
```yaml
stages:
  - build
  - test
build:
  stage: build
  script:
    - ./gradlew compileJava   # 编译失败立即中断
test:
  stage: test
  script:
    - ./gradlew test          # 单测是质量门禁
```

## 五、与其他技术对比
相比本地手工构建，CI 提供一致环境与不可变产物；相比 CD，CI 止步于"可部署"，不自动发布。

## 六、常见误区
- 提交后长时间不触发构建，失去快速反馈意义。
- 在流水线里跑不稳定的端到端测试，制造假红阻断合入。

## 七、与开源书/权威来源对应
Humble & Farley 2010 提出"每次提交都应触发一次构建"，并强调自动化是部署流水线的基石。

## 八、面试题
CI 与 CD 的区别？为什么测试要分层？如何缩短流水线反馈时间？

## 九、演进与趋势
向预提交（pre-commit）与远程缓存演进，结合 Bazel 等增量构建进一步提速。

## 十、小结
CI 用自动化验证把集成风险前置，阶段化与快速失败是其设计核心。
