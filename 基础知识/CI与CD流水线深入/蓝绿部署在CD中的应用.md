# 蓝绿部署在CD中的应用

> 对应 Humble & Farley 2010（Continuous Delivery）与 Newman《Building Microservices》零停机发布。

## 一、背景与挑战
原地升级（in-place）常导致服务短暂不可用，且一旦新版本有缺陷，回退成本高、恢复慢。对可用性敏感的服务，需要「近乎零停机的切换」与「一键回滚」能力。蓝绿部署（blue-green）正是为此设计的经典发布模式：用冗余环境换取切换与回滚的确定性。

它的核心经济学是「用资源换风险可控」：多维护一套等同容量的环境，换来的是「发布不再是一场赌博」——出问题只需把流量拨回旧版本，秒级而非分钟级恢复。对电商大促、金融交易等不可中断业务，这种冗余是值得的。

需要清醒认识其代价：双倍资源、双份运维、以及对数据层兼容性的严格要求。蓝绿不是「免费的零停机」，而是一种明确的资源换稳定性交易。

## 二、核心原理
同时维护两套等价环境：蓝（当前生产流量）与绿（新版本，已部署但未接流量）。绿环境经过充分验证（冒烟、健康检查）后，通过路由/负载均衡「一次性」把流量切到绿；若异常，立即把流量切回蓝，实现快速回滚。切换是原子性的流量重定向，而非逐实例替换，因此用户几乎无感知，回滚也只需改路由。

成功的关键在「切换前验证」：绿环境必须先通过健康检查、冒烟测试、甚至影子流量验证，才能承接全量流量；否则「一键切换」会变成「一键故障」。

另一个要点是「会话与状态」：无状态服务切换最干净；有状态或强会话亲和的场景需要额外处理会话迁移或粘性策略。

## 三、形式化与数学基础
设流量分配权重 $w_{blue}, w_{green}$ 且 $w_{blue} + w_{green} = 1$。蓝绿切换即令 $w_{green}=1$ 的原子操作；回滚即重置为 $w_{blue}=1$。

$$ \text{switch}: (w_{blue}, w_{green}) \to (0, 1),\quad \text{rollback}: \to (1, 0) $$

若要做渐进，可令 $w_{green}$ 从 0 线性增至 1（此时已接近金丝雀），但经典蓝绿是「全有或全无」。关键在于两套环境共享同一数据库/存储，因此切换对数据层透明。若做加权切换，本质是蓝绿与金丝雀的混合，需保证新旧版本对数据格式兼容。

## 四、代码实现
```bash
# 切换入口流量到 green 池（K8s Service selector 切换）
kubectl patch svc/app -p '{"spec":{"selector":{"version":"green"}}}'
# 异常时回退
kubectl patch svc/app -p '{"spec":{"selector":{"version":"blue"}}}'
# 验证绿环境健康后再切
kubectl rollout status deploy/app-green

# 数据库侧：先做向后兼容的扩展式迁移
# 1) 新增字段（新旧都能读）  2) 切换流量  3) 再删除旧字段
```

在 Istio 等服务网格中，可通过 `VirtualService` 的权重路由实现更细粒度切换；在云厂商负载均衡（ALB/NLB）上则通过目标组（target group）切换。无论哪种，关键是「切换动作幂等、可瞬时回滚」。

## 五、与其他技术对比

| 方式 | 资源 | 回滚 | 灰度 | 复杂度 |
| --- | --- | --- | --- | --- |
| 滚动更新 | 少 | 中 | 渐进 | 低 |
| 蓝绿 | 双倍 | 快（切路由） | 否（全切） | 中 |
| 金丝雀 | 部分 | 快 | 小流量 | 高 |
| 影子流量 | 额外 | 不涉用户 | 只验证 | 中 |
| 特性开关 | 无 | 快（关开关） | 按用户 | 低 |

蓝绿切换更彻底、回滚更快，但需双倍资源；金丝雀做小流量灰度、风险更低但实现更复杂。实践常组合：先蓝绿占住新版本，再在绿内做金丝雀灰度，最后全量。

## 六、常见误区
- 误区一：忽略数据库兼容性。蓝绿两版对 schema 假设不同会导致切换失败，需「向后兼容迁移」（先加字段、再切、后删旧）。
- 误区二：未先对绿环境做充分冒烟就切流。应验证健康再切。
- 误区三：蓝绿等于无需回滚预案。仍要准备回滚与数据回填方案。
- 误区四：蓝绿浪费资源不可接受。可用「缩容蓝/共享节点」缓解。
- 误区五：蓝绿适合所有服务。有状态、强本地会话的服务切换需额外处理会话亲和。
- 误区六：切换后立即销毁蓝环境。应保留一段时间作为回滚兜底，确认稳定后再回收。
- 误区七：切换只改应用层。DNS 缓存、客户端长连接、CDN 都可能让「切换」不彻底，需一并考虑。

## 七、与开源书·权威来源对应
Humble & Farley 2010 把蓝绿部署作为零停机发布的基础模式之一；Newman《Building Microservices》讨论其在微服务下的数据库兼容处理；Kleppmann《DDIA》在部署策略部分涉及蓝绿与滚动。

Kubernetes Service/Ingress 是常见路由切换载体。expand/contract 迁移模式（先扩展 schema 兼容新旧、再收缩）是蓝绿在数据库侧的标配配合。具体实现以官方最新文档为准。

## 八、面试题
- 问：蓝绿与金丝雀如何选择？答：要快速全切回滚用蓝绿；要小流量验证用金丝雀。
- 问：蓝绿对数据库迁移要求？答：需向后兼容的增量迁移，避免两版 schema 冲突。
- 问：回滚为什么快？答：只改路由权重，瞬时切回蓝。
- 问：如何减少双倍资源？答：用共享节点池、或切流期间临时扩容绿、验证后回收蓝。
- 问：蓝绿如何处理会话？答：优先无状态；有状态需会话迁移或粘性策略。
- 问：何时不能立即销毁旧环境？答：需保留作为回滚兜底，确认稳定后再回收。
- 问：expand/contract 是什么？答：先扩展 schema 兼容新旧、切换流量、再收缩删除旧结构。

## 九、演进与趋势
与服务网格（Istio/Linkerd）结合，蓝绿可按请求元数据（用户、版本头）精准切换；GitOps 把蓝绿状态声明在 Git，由控制器对齐。数据库方面「扩展式迁移（expand/contract）」成为标配以解耦部署与数据变更。

影子流量（shadow）也常与蓝绿配合：把生产流量复制一份打到绿环境验证，却不返回给用户。相关实践以官方最新文档为准。

从流量切换的「彻底性」看，长连接与客户端缓存会让「切路由」并不立即生效：WebSocket 会保持旧连接，DNS 有 TTL，CDN 有缓存，需要配合主动断连与缓存刷新策略。

从数据回滚看，若新版本已写入不兼容数据，单纯切回蓝环境可能不足以恢复，必须提前设计「前滚修复」或数据回填方案。

从成本优化看，可采用「蓝缩容、绿全量」的不对称配置：稳态时只保留一套全量，切换时临时扩容，兼顾成本与安全。

从验证深度看，切换前可先做「只读灰度」：让部分内部用户访问绿环境，验证功能与性能后再全量切换。

从自动化程度看，把「部署绿、验证、切流、观察、回收蓝」编排成一条可重试流水线，能显著降低人工误操作。

从组织协作看，蓝绿发布需要研发、运维、测试对「何时切、切多少、何时回滚」有统一判定标准。

从可观测性看，切换前后应对比关键指标（错误率、延迟、饱和度），并设置自动回滚阈值，让异常在用户感知前被发现。

## 十、小结
蓝绿部署用冗余环境换取切换与回滚的确定性，是零停机发布的经典方案；落地须重视数据库兼容与切换前的健康检查。它和金丝雀、影子流量共同构成现代「低风险发布」工具箱，资源代价换来的是业务连续性的硬保障。
