# 制品管理与版本溯源

> 对应 Humble & Farley 2010（Continuous Delivery）与 Newman《Building Microservices》依赖与制品治理。

## 一、背景与挑战
同一份代码在不同环境、不同机器上重新构建，可能产出不同结果（依赖漂移、时间戳、环境差异），导致「开发能跑、生产崩」。必须保证「一次构建、处处部署」：构建一次得到不可变制品，后续所有环境都部署这同一个制品，杜绝环境间行为差异，并能从生产问题反向追溯到确切的源码提交。

「可重现构建（reproducible build）」是这一原则的延伸：给定同一份源码与构建环境，任何时候构建出的制品字节级一致。它既是溯源的基础，也是供应链安全的前提。

反过来看，若允许「在生产重新编译」，等于放弃了所有一致性保证：你无法证明生产上跑的到底是哪份代码，也无法保证两份「同版本」制品真的相同。

## 二、核心原理
CI 产出不可变制品（容器镜像、jar、wheel、npm 包），存入制品库（如 Nexus、Artifactory、Harbor）并附元数据：git sha、构建号、依赖树、构建时间。部署只「拉取制品」，严禁在目标环境重新编译。

制品以内容寻址或唯一坐标标识，引用精确到 digest 而非浮动的 `latest`，从而任意时刻都能复现与回滚。容器镜像的 digest 是内容摘要，天然满足「同一 digest 必为同一字节」。

「不可变」是硬约束：一旦发布某版本，不允许原地覆盖，只能追加新版本。这样历史版本长期可回溯、可审计。

## 三、形式化与数学基础
制品 $a$ 具唯一坐标 $(\text{group}, \text{name}, \text{version}, \text{buildNo})$ 或更严格的内容摘要

$$ \text{digest} = \text{sha256}(\text{artifact}) $$

溯源链为：$\text{deploy}(a) \to \text{build}(b) \to \text{commit}(c)$，反向可定位任意生产问题到源码提交 $c$。不可变性要求：一旦发布，$a$ 不可被覆盖（只可追加新版本），保证历史版本长期可回滚与审计。

若制品带签名，还可建立 $\text{verify}(a, \text{sig}) \to \text{provenance}$ 的信任链，把「这个制品确实由这条流水线、从这次提交构建」变成可验证的事实。

## 四、代码实现
```bash
# 打标签并推送不可变镜像（带构建号）
docker build -t registry/app:1.4.2-${CI_BUILD_ID} .
docker push registry/app:1.4.2-${CI_BUILD_ID}

# 取 digest 并部署，引用精确 digest 而非 latest
DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' \
  registry/app:1.4.2-${CI_BUILD_ID})
kubectl set image deploy/app app=registry/app@${DIGEST}

# 附加元数据（git sha、构建号）便于溯源
kubectl annotate deploy/app \
  git.sha="${CI_COMMIT_SHA}" build.id="${CI_BUILD_ID}" --overwrite
```

除镜像外，jar/wheel 应发布到对应制品库并锁定版本；前端静态资源应带 content-hash 文件名以利用 CDN 缓存。所有制品的元数据（构建者、时间、来源 commit、依赖 SBOM）应一并入库，供审计查询。

## 五、与其他技术对比

| 方式 | 一致性 | 可回滚 | 溯源 |
| --- | --- | --- | --- |
| 源码部署 | 差（重编译漂移） | 难 | 弱 |
| 制品（latest） | 中 | 难（浮动） | 中 |
| 制品（digest） | 强 | 易 | 强 |
| 制品 + 签名 + SBOM | 强 | 易 | 强（可验证） |
| 可重现构建 | 最强（字节一致） | 易 | 最强 |

相比直接传源码部署，制品可复用且环境一致；相比 latest 标签，带 digest 的引用杜绝漂移。digest 还让多副本确保拉到「完全相同」的字节，避免「同标签不同内容」的诡异故障。

## 六、常见误区
- 误区一：使用 latest 标签。无法回滚到确定版本，且多副本可能拉到不同镜像。
- 误区二：制品库无保留策略。故障后找不到历史版本，审计失败。
- 误区三：在生产环境重新编译。破坏「一次构建」原则，引入环境差异。
- 误区四：制品不含元数据。缺少 git sha 则无法溯源到提交。
- 误区五：制品不可变即安全。不可变防篡改但需配合签名/校验，否则仍可被替换。
- 误区六：digest 与 tag 等价。tag 可变、digest 不可变，只有 digest 能保证拉取内容确定。
- 误区七：SBOM 只对合规有用。它也是漏洞响应时快速定位受影响制品的依据。

## 七、与开源书·权威来源对应
Humble & Farley 2010 反复强调「二进制复用」与「一次构建」，是可追溯发布的基石；Newman《Building Microservices》讨论依赖与制品治理。

SLSA 框架与 SBOM（软件物料清单）把制品元数据标准化，支撑供应链安全。cosign/Notary 提供制品签名，Sigstore 提供透明日志，使溯源链可验证。具体规范与工具版本以官方最新文档为准。

## 八、面试题
- 问：为何不能在生产重新编译？答：破坏一致性，引入环境漂移。
- 问：latest 标签风险？答：浮动、不可回滚、可能各副本不一致。
- 问：如何证明生产跑某次提交？答：制品元数据含 git sha，部署引用精确 digest。
- 问：SBOM 的作用？答：列出制品的全部依赖与版本，支撑合规与安全审计。
- 问：制品为何要签名？答：建立来源可信，防止被替换或投毒。
- 问：digest 与 tag 区别？答：tag 是可变的别名，digest 是内容摘要、不可变。
- 问：可重现构建解决什么？答：同源码同环境产出字节一致制品，使缓存与溯源更可靠。

## 九、演进与趋势
SBOM 成为制品元数据标配，支撑供应链安全与合规审计；签名制品（cosign/Notary）保证来源可信；构建 provenance（构建来源证明）与 SLSA 级别让溯源从「sha」深入到「构建环境与步骤」。

可重现构建（如 Reproducible Builds 项目）进一步要求字节级一致，使「同样源码 $=$ 同样制品」可被第三方验证。相关标准以官方最新文档为准。

从成本角度看，制品库需要容量规划与生命周期策略：热版本常驻、冷版本转低频存储、超期版本按合规要求归档，避免存储无限膨胀。

从安全角度看，「软件物料清单 + 签名 + 来源证明」三件套正在成为标配：分别回答「用了什么」「是谁构建的」「如何构建的」三个问题。

从流程角度看，制品晋级应「一次构建、多环境复用」：同一 digest 依次进入测试、预发、生产，任何一环都不允许重新构建。

从排障角度看，把制品元数据与部署记录、日志、追踪关联，可在事故时快速回答「这次故障对应哪次提交、哪个依赖升级」。

## 十、小结
制品管理用不可变与可溯源把「构建」和「部署」解耦，是可靠发布的底座；引用精确 digest、附全量元数据，才能做到任意回滚与问题溯源。在软件供应链攻击频发的当下，签名与 SBOM 让制品治理从「工程便利」升级为「安全刚需」。
