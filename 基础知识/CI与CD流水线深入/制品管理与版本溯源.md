# 制品管理与版本溯源

> 对应 Humble & Farley 2010 (Continuous Delivery)。

## 一、背景与挑战
同一份代码在不同环境构建出不同产物，会导致"开发能跑生产崩"。需要保证一次构建、处处部署。

## 二、核心原理
CI 产出不可变制品（镜像、jar、wheel），存入制品库并附元数据（git sha、构建号、依赖树）。部署只拉取制品，禁止在目标环境重新编译。

## 三、形式化与数学基础
制品 a 具唯一坐标 (group, name, version, buildNo)。溯源链：deploy(a) -> build(b) -> commit(c)。可反向定位任意生产问题到源码提交。

## 四、代码实现
```bash
# 打标签并推送不可变镜像
docker build -t registry/app:1.4.2-${CI_BUILD_ID} .
docker push registry/app:1.4.2-${CI_BUILD_ID}
# 部署引用精确 digest 而非 latest
kubectl set image deploy/app app=registry/app@sha256:...
```

## 五、与其他技术对比
相比直接传源码部署，制品可复用且环境一致；相比 latest 标签，带 digest 的引用杜绝漂移。

## 六、常见误区
- 使用 latest 标签，无法回滚到确定版本。
- 制品库无保留策略，故障后找不到历史版本。

## 七、与开源书/权威来源对应
Humble & Farley 2010 反复强调"二进制复用"与"一次构建"，这是可追溯发布的基石。

## 八、面试题
为什么不能在生产环境重新编译？latest 标签的风险？如何证明生产跑的是某次提交？

## 九、演进与趋势
SBOM（软件物料清单）成为制品元数据标配，支撑供应链安全与合规审计。

## 十、小结
制品管理用不可变与可溯源把"构建"和"部署"解耦，是可靠发布的底座。
