# 脑裂与Quorum

> 对应 Gifford 1979（Weighted Voting for Replicated Data，quorum 概念）与 Gilbert & Lynch 2002（CAP）。

## 一、背景与挑战
如何在不依赖全局锁的情况下，保证「任意两次写至少有一份公共副本参与」，从而让分区下的少数派无法成写、天然阻止双主？Quorum（法定多数）机制用「写需 W 票、读需 R 票、且 W+R>N」的集合相交性质回答这个问题。它既是 CP 系统防脑裂的数学基础，也是读写一致性（read-your-writes 等）的可配置手段。

Gifford 1979 的加权投票是最早的系统化表述：把每个副本赋予权重，写/读分别需要超过半数总权重，从而把「成员数」泛化为「权重和」，适配异构、跨地域部署。现代 Raft/Paxos 的「日志复制需多数」本质上就是 quorum 的特例（W=R=(N/2)+1）。

Quorum 的另一重要价值是「延迟可调」：写只需 W 个副本确认即可返回，无需等全部副本。这使系统在部分副本慢或跨地域时仍能保持可接受的写延迟，代价是读时必须联系 R 个副本并取最新版本（因为最快的副本可能不是最新的）。

## 二、核心原理
把 N 个副本看作带投票权的集合：
- 写成功需获得至少 W 个副本确认。
- 读需联系至少 R 个副本并取最新。
- 约束 $W + R > N$：任意一次读与任意一次写必有至少一个公共副本，读必能看见最近写。
分区时，任何一侧副本数若不足 W（取 $W > N/2$）就无法完成写，双主被阻止。调小 W、R 可换更高可用但更弱一致性。读一致性级别（one/quorum/all）本质上就是调 R；写一致性级别就是调 W。

读的「取最新」需要版本信息支撑：单纯联系 R 个副本、返回第一个响应是不够的，必须比较各副本的版本号（或向量时钟）并选出最新者。若某个本应持有最新值的副本恰好未能响应（因故障或网络），而 W 恰好满足但不覆盖它，就可能读到旧值——这正是「W+R>N」的必要性所在。

还需注意 quorum 与「顺序」的关系：quorum 保证「读能看到之前的写」，但不自动保证「所有节点看到的写顺序相同」。后者需要额外的机制（如把写请求串行化到某个 leader，或用日志序号统一排序）。Raft/Paxos 通过「日志索引 + 多数确认」同时获得这两点。

## 三、形式化与数学基础
核心不等式：
$$W + R > N$$
当网络分为两半，至多一侧副本数 $\ge \lceil (N+1)/2 \rceil$，另一侧 $< N/2$。取 $W = \lfloor N/2 \rfloor + 1$ 则少数派永远凑不齐 W，故防脑裂。读写可见性：读集合 $R$ 与写集合 $W$ 交集非空，故最近写所在副本必被读覆盖。加权投票下以权重和替代计数，约束改为 $W_w + R_w > \text{总权重}$。更强地，若要保证 read-your-writes 与单调读，需 $R + W > N$ 且读需见到自己写的那份副本。

交集大小的精确下界：$|Q_R \cap Q_W| \ge R + W - N \ge 1$。这个数字不依赖于具体的读写请求，只依赖配置，因此「任意读必能覆盖任意最近写」是配置层面的保证，而非概率性的。

偶数 N 的处理需精确：若 $N = 4$、$W = R = 3$，则 $W + R = 6 > 4$ 成立，且 $W = 3 > 4/2 = 2$ 也成立，故仍能防脑裂。但此时任一节点故障都会使可用副本只剩 3 个，若再故障一个就无法成写。因此奇数 N 的优势在于「容错效率」：$N=3$ 容忍 1 故障、$N=5$ 容忍 2 故障，而 $N=4$ 只容忍 1 故障。

## 四、代码实现
```python
# 法定多数配置与判定
def safe_quorum(N):
    W = N // 2 + 1          # 写需严格过半
    R = N - W + 1           # 满足 W+R>N
    return W, R

def write_ok(acks, W):
    return acks >= W

def read_sees_latest(contacted, last_writers, R, W):
    # 读集合与最新写集合必相交（因 R+W>N）
    return len(set(contacted) & set(last_writers)) >= 1

# 加权版本
def weighted_write_ok(live_weights, total, W_w):
    return sum(live_weights) > total / 2
```

读路径需按版本择新，而非取首个响应：

```python
def read_latest(self, keys, R):
    responses = self.broadcast_read(keys, timeout=self.t)
    if len(responses) < R:
        raise NotEnoughReplicas()          # 未达读 quorum，拒绝返回
    # 从 R 个响应中选出版本号最大者，保证读到最近写
    return max(responses, key=lambda r: r.version).value
```

## 六、常见误区
1. 设 $W+R \le N$。此时读可能错过最新写，破坏读写一致性。
2. 偶数 N 下取 W=N/2。平分两侧都能凑齐 W，双主仍可发生，须 W>N/2 或加权重。
3. 把 quorum 当 fencing 用。quorum 防「成写」，但防不了「陈旧主带旧权限继续发写」——仍需 fencing 兜底。
4. 以为 W 越大越安全。W 大则写可用性差、延迟高，是 C 与 A 的权衡而非免费午餐。
5. 以为读只需联系 R 个副本、取第一个响应。必须比较版本号取最新，否则可能返回旧值。
6. 以为 quorum 能保证「全体看到的顺序一致」。它只保证读写可见性，顺序一致需额外的日志机制。
7. 忽略「读修复」的存在。为提升后续读的命中率，系统常在读时把最新值回写到旧副本。

## 八、面试题
1. 为什么 $W+R>N$ 能保证读到最新写？
   要点：读集合与写集合必有交集，最新写所在副本被读覆盖。
2. 偶数节点如何防脑裂？W 该取多少？
   要点：取 $W > N/2$（奇数化），或引入权重使两侧不可能同时过半。
3. quorum 能完全替代 fencing 吗？
   要点：不能，quorum 防成写，fencing 防陈旧主带旧权限写。
4. 加权 quorum 相比简单多数有何优势？
   要点：可把跨地域/异构副本按权重配置，避免弱副本拖累又防脑裂。
5. 读 quorum 为什么必须比较版本号？
   要点：R 个响应可能有不同版本，取首个响应可能读到旧值。
6. 容忍 f 个故障至少需要多少副本？
   要点：$N \ge 2f+1$，因为写 quorum 必须能覆盖所有可达故障集。

## 九、演进与趋势
动态 quorum 在分区修复时临时调整 W/R 以快速恢复可用；分级 quorum（如 Azure 的「云 + 区域」两层投票）提升跨地域容灾；Raft/Paxos 用「日志复制需多数」等价实现 quorum 语义；leader 租约与 quorum 结合降低提交延迟。

工程上的另一方向是「弹性 quorum」：在保证 $W+R>N$ 的前提下，按负载动态选择 W 与 R（如读多写少时降低 R），从而在一致性与延迟之间按业务实时权衡。

## 十、小结
Quorum 用集合相交性质从数学上阻止脑裂双写，是强一致复制的基石。正确配置 $W+R>N$ 且 $W>N/2$，才能在分区下既防双主又保证读可见最新；但它防不了陈旧主带旧权限写，需与 fencing 配合。牢记「读需择版本、写需达 W 票」两条实现要点，才能真正把 quorum 用对。
