# 脑裂的检测与恢复

> 对应 Kleppmann DDIA 第8章（split-brain recovery）与 DeCandia et al. 2007（Dynamo 冲突合并）。

## 一、背景与挑战
脑裂发生后，被分区隔开的两侧可能各自接受了写，分区恢复时两套历史出现分歧。若处理不当，轻则覆盖一侧更新（丢写），重则两版数据反复覆盖、永不正合。恢复策略取决于系统的一致性定位：CP 系统倾向于「少数派回滚」，AP 系统倾向于「保留两侧、合并收敛」。无论哪种，前提都是「陈旧主已被隔离」，否则恢复期间它仍在写，会让合并永远无法收敛。

真实场景中，脑裂恢复往往伴随运维压力：DBA 要在「保一致」与「保数据」间权衡，错误操作（如直接把一侧 rsync 到另一侧）会扩大损失。理解 CP/AP 两种恢复范式的本质差异，是设计高可用存储与正确运维的前提。生产事故表明，恢复阶段若未先隔离旧主，往往出现「合并-被旧主覆盖-再合并」的死循环，因此隔离是恢复的必要前置条件。

## 二、核心原理
恢复分三步：
1. 检测分歧：以版本向量/向量时钟比较两侧对同一 key 的版本，找出被支配（可丢弃）与并发（需合并）的版本。
2. 隔离陈旧主：通过 fencing token 或存储层写锁，确保陈旧主无法再写（见 Fencing 文档）。
3. 按一致性模型收敛：CP 丢弃少数派未提交写、从多数派全量/增量同步；AP 保留并发 sibling，由应用层或 CRDT 合并。
关键在于：合并函数必须满足交换律、结合律、幂等，使多次重试结果一致。若不满足幂等，网络重传会让合并重复执行、产生错误状态。隔离与合并的顺序不能颠倒：先合并再隔离，旧主仍会污染结果。

分歧检测还有一个易被忽略的细节：判定「支配」必须使用能表达因果的版本信息（版本向量、向量时钟或带因果元数据的 HLC），单纯的时间戳不足以区分「并发」与「先后」。若用本地墙上时钟做比较，时钟回拨或漂移会让两条并发写被误判为有序，从而静默丢弃一侧更新——这是「看起来恢复了，实际丢了数据」的典型事故形态。

## 三、形式化与数学基础
对 key 的两版本 $(V_a, data_a)$、$(V_b, data_b)$：
- 若 $V_a$ dominates $V_b$：丢弃 b，保留 a。
- 若并发：$\forall$ 副本最终状态须为 $merge(data_a, data_b)$，且合并须满足：
$$merge(a,b)=merge(b,a),\quad merge(a,merge(b,c))=merge(merge(a,b),c)$$
$$merge(a,a)=a$$
这些性质保证 AP 系统在任意顺序传播下都能收敛到同一状态（CRDT 的语义基础）。CP 系统则直接令最终状态为多数派已提交状态 $S_{majority}$，少数派未提交写被丢弃（可能丢写但保强一致）。两种范式共享「先检测分歧」这一步，差异只在「如何收敛」。

这三条性质分别对应三个工程后果：交换律保证消息到达顺序不影响结果；结合律保证分批次合并与一次性合并等价（因而可增量收敛）；幂等性保证重传不改变结果。三者合起来构成「半格（join-semilattice）」结构——只要合并操作是某个半格上的上确界，收敛性就自动成立。这解释了为什么 G-Counter 取逐分量最大值、G-Set 取并集都是天然 CRDT：它们的合并就是半格的 join。

## 四、代码实现
```python
# 分区的合并：保留并发 sibling，合并收敛
def reconcile_versions(versions):
    # versions: [(clock, data)]
    result = []
    for vc, data in versions:
        dominated = any(dominates(o, vc) for o, _ in versions if o is not vc)
        if not dominated:
            result.append((vc, data))    # 只保留未被任何版本支配的（即极大元）
    # 对保留的并发版本做应用层/CRDT 合并
    if len(result) > 1:
        merged = merge_all([d for _, d in result])
        return merged
    return result[0][1]

# 幂等合并示例：集合并集（满足交换/结合/幂等）
def merge_all(datas):
    out = set()
    for d in datas:
        out |= d                          # 并集：天然满足三大代数律
    return out

# 反例：求和合并不幂等（重传会累加两次），须改为「取较大计数」或带版本去重
def bad_merge(datas):
    return sum(datas)                     # 重放同一条数据会导致重复计数

def good_counter_merge(datas):
    n = max(len(d) for d in datas) if datas else 0
    return n                              # 计数类取 max（半格 join），幂等
```

`reconcile_versions` 中 `if o is not vc` 的判断是为了避免把版本与自身比较（自支配恒成立与否取决于偏序是否严格）。若写成 `o == vc` 而版本对象未实现相等语义，可能把两个内容相同但独立的版本误判为「被支配」，从而漏掉一个应保留的并发分支。

## 五、与其他技术对比
| 维度 | CP 回滚 | AP 合并 | 手工修复 | 共识强一致 |
| --- | --- | --- | --- | --- |
| 丢写风险 | 少数派写丢失 | 不丢（保留） | 取决于人 | 无（多数提交） |
| 自动化 | 高 | 中（需 merge） | 低 | 高 |
| 运维成本 | 中 | 低 | 高 | 低 |
| 一致性 | 强 | 最终 | 不定 | 线性 |
| 恢复耗时 | 与落后量相关 | 与冲突量相关 | 不可预估 | 短暂 |
| 对应用的要求 | 可接受丢写 | 需可合并数据类型 | 需人工判断 | 无需特殊处理 |

CP 回滚实现简单且结果确定，代价是明确丢弃少数派未提交写；AP 合并保数据完整但要求应用能定义合理的合并语义；共识强一致从协议层杜绝脑裂，是「最省心的恢复」——其代价体现在正常路径的性能与可用性上，而非恢复阶段。

## 六、常见误区
1. 恢复时直接用一侧覆盖另一侧。这会静默丢写，正确做法是先比较支配关系。
2. 未在恢复前完成 fencing。陈旧主继续写会让恢复永远不收敛，甚至再次脑裂。
3. 合并函数不满足幂等。网络重传会重复合并，产生错误状态。
4. 以为恢复是「瞬时的」。大对象/大量 key 的合并可能耗时很长，期间仍需保持隔离。
5. 以为 CP 回滚一定能保数据。少数派未提交的写在 CP 下被主动丢弃，是「保一致弃数据」。
6. 用墙上时钟判断版本先后。时钟漂移会让并发写被误判为有序，导致静默丢写。
7. 认为所有数据类型都能自动合并。计数、集合等有天然 merge，而「账户余额」这类需要业务语义的类型必须谨慎定义。
8. 忽略恢复期的读语义。合并尚未完成时对外服务可能读到中间态，需明确降级策略或短暂停写。

## 八、面试题
1. 脑裂恢复时 CP 与 AP 策略有何本质差异？
   要点：CP 回滚少数派、保强一致；AP 保留并发写、合并收敛。
2. 为什么恢复前必须对旧主 fencing？
   要点：否则旧主继续写，合并无法收敛、可能二次脑裂。
3. 合并函数需满足哪些代数性质？为什么？
   要点：交换、结合、幂等，保证任意传播顺序收敛一致。
4. 若合并不满足幂等会发生什么？
   要点：重传导致重复合并，最终状态依赖到达顺序，破坏收敛性。
5. CP 与 AP 在「数据保全」上如何取舍？
   要点：CP 保一致可能丢少数派未提交写；AP 保数据但需合并、可能读到中间态。
6. 为什么不能用墙上时钟判定版本先后？
   要点：时钟可漂移与回拨，会把并发误判为有序，从而静默丢弃一侧更新。
7. 合并的代数性质对应什么数学结构？
   要点：构成半格（join-semilattice），上确界即 merge，收敛性由半格性质保证。

## 九、演进与趋势
CRDT 把「合并」固化进数据类型，使 AP 恢复成为纯状态传播、无需应用层逻辑；Raft/Paxos 的「仅多数派提交」从协议层杜绝脑裂；云厂商把 fencing 下沉到存储卷写令牌，进一步简化应用。现代系统倾向于「协议防脑裂 + CRDT 自动恢复」双保险，把恢复从「人工决策」变为「自动收敛」。

另一条趋势是「可逆的自动恢复」：在合并前先做快照与冲突审计，使自动收敛的结果可回溯、可解释，避免「机器悄悄丢了数据」。这类设计在金融等对数据血缘要求严格的领域尤为重要。具体能力以各系统官方最新文档为准。

## 十、小结
脑裂恢复的核心是「先隔离旧主，再按一致性模型合并或回滚」。CP 走回滚、AP 走合并，二者都依赖版本向量判定分歧，并以幂等合并保证收敛。隔离是恢复的前置条件，不可与合并颠倒，否则陈旧主会持续污染恢复结果。

三条执行要诀：判定分歧用因果版本而非时钟（识别要准）、fencing 先行（前提要稳）、merge 必须是半格 join（收敛要保）。三者齐备，脑裂恢复才能从「人工排障」变为「确定性过程」。
