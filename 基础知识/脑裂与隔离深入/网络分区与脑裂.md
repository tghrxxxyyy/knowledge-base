# 网络分区与脑裂

> 对应 Gilbert & Lynch 2002（CAP 定理证明，网络分区下的一致/可用取舍）与 Brewer 2000（CAP 猜想）。

## 一、背景与挑战
网络分区（network partition）指通信故障把一组节点割裂成互不连通的子集。它是脑裂（split-brain）的直接诱因：原本单一集群的两侧都以为对方失联，于是各自选主/接写。CAP 定理告诉我们，在分区（P）不可避免的真实异步网络中，一致性（C）与可用性（A）不可兼得——这从根本上决定了脑裂期间系统该「拒绝写」还是「允许分歧」。

需要澄清一个常见误解：CAP 不是「三选二」的静态配置，而是「当分区发生时，C 与 A 必舍其一」。无分区时系统完全可以同时做到 C 与 A。因此现代系统设计重点不是「逃避 CAP」，而是「在分区发生时如何取舍，以及无分区时如何两全」。

分区的形态比想象中丰富：除了「链路断开」，还包括单向可达（A 能发给 B，B 发不回 A）、高延迟（消息最终能到但超出超时阈值）、以及「部分进程崩溃」。后者虽是进程故障而非网络故障，但对其他节点而言表现与分区无异——从系统外部看，二者都表现为「某些节点失联」。因此工程上的容错机制通常不区分故障类型，而统一按「失联即需仲裁」处理。

## 二、核心原理
- CP 系统：分区时拒绝少数派的写，保证全局一致，但少数派不可写（牺牲可用性 A）。由于写被集中到多数派，不会形成双主，脑裂被「预防」。
- AP 系统：分区时两侧都可读写，保证可用，但产生分歧历史，脑裂成为必然，需靠冲突解决而非阻止。
- 现实系统多在请求级做「可调一致性」（tunable consistency）：关键写走 quorum 强一致，非关键写走最终一致。这样既在关键路径保 C，又在普通路径保 A。

网络分区本身有多种形态：单链路断开（两点不可达）、多数派裂脑（一侧 > N/2）、对称/非对称分区（一侧能发、另一侧收不到）。不同形态对 quorum 的影响不同，恢复策略也不同。

「少数派不可用」的具体含义需精确理解：CP 系统并非让少数派节点崩溃，而是让它们无法完成「写」这类需要多数确认的操作。少数派通常仍可提供读（可能读到旧值）或返回明确错误，这取决于具体实现。「返回错误」优于「静默挂起」——它让上游能快速失败转移。

## 三、形式化与数学基础
Gilbert & Lynch 对 CAP 的严格证明：在异步网络模型下，若系统保证一致性（对任意两个不相交操作序列返回一致值）且可用性（每个未崩溃节点最终响应），则当发生分区（存在两节点间消息可任意延迟）时，二者无法同时满足。可表述为：
$$\text{Partition } P \implies \neg(C \land A)$$
即 $C + A$ 至多取其一。选择 C 意味着少数派请求失败（防脑裂）；选择 A 意味着允许脑裂。PACELC 进一步补充：无分区（PAC 不触发）时，系统还要在延迟 L 与一致性 C 间取舍（E），即「else Latency or Consistency」。

证明的关键一步是「不可区分性论证」：在异步网络下，一个节点无法区分「对端崩溃」与「消息被无限延迟」。若它在无法确认对端时仍执行本地写并返回成功（保 A），则当对端也如此行事时，两侧返回的值必然冲突（违反 C）；若它拒绝对外服务（保 C），则不满足「每个未崩溃节点最终响应」（违反 A）。这一论证不依赖具体实现，因此 CAP 是「模型层面的不可能性」。

可用性与延迟的定量权衡：若要保证线性一致读，通常需至少一轮 quorum 通信，故读延迟下界约为一个 RTT；若允许读旧值，则可本地读，延迟降至接近零。这条取舍线在 PACELC 中被显式表达。

## 四、代码实现
```python
# 分区下策略选择：CP 仅多数派可写
def on_partition(side_size, N, mode):
    if mode == "CP":
        return side_size > N / 2      # 仅多数派允许写入
    return True                        # AP：两侧均可用

# 可用性衡量：少数派在 CP 下不可用
def available_in_cp(side_size, N):
    return side_size > N / 2

# 可调一致性：关键写需 quorum
def write_with_level(level, acks, W):
    if level == "strong":
        return acks >= W
    return acks >= 1   # 最终一致：单副本确认即可
```

在 CP 系统中，「少数派返回明确错误」优于「静默等待」：

```python
def cp_write(self, replicas_alive):
    if len(replicas_alive) <= self.N / 2:
        raise NotEnoughReplicas(   # 快速失败，便于上游切换
            f"only {len(replicas_alive)} of {self.N} replicas reachable")
    return self.replicate_to_quorum(replicas_alive)
```

## 五、与其他技术对比
| 维度 | CP 系统 | AP 系统 | CA（理论） | 可调一致 |
| --- | --- | --- | --- | --- |
| 分区时写 | 仅多数派 | 两侧均可 | 假设无分区 | 按请求 |
| 脑裂 | 被预防 | 必然发生 | 不适用 | 混合 |
| 合并成本 | 低（回滚） | 高（合并） | 无 | 视级别 |
| 典型 | ZK, etcd | Dynamo, Riak | 单库 | Cassandra |
| 读延迟 | 至少一 RTT | 可本地读 | 低 | 按级别 |
| 写延迟 | 需多数确认 | 单副本即可 | 低 | 按级别 |

需要纠正一个流行但不严谨的表述：「CA 系统」在分布式语境中其实只有单机或「假设永不分区的集群」。任何真正跨网络部署的多副本系统，只要分区可能发生，就必然要在 C 与 A 之间取舍。

## 六、常见误区
1. 以为「CAP 三选二」可静态固定。实际上 C/A 是「分区发生时」的取舍；无分区时两者可兼得。
2. 忽略 AP 系统脑裂后的合并成本。可用性换来的分歧需要应用层/CRDT 解决。
3. 以为增加副本数能消除脑裂。副本再多，奇数平分或协调失败仍可能脑裂。
4. 以为分区都是「干净两半」。非对称分区下两侧感知不同，quorum 判断更复杂。
5. 以为高延迟不算分区。消息若超出超时阈值，对系统而言与断开无异，同样触发脑裂行为。
6. 以为 CAP 只约束写。读同样受影响：保线性一致读需协调，保低延迟读则可能读到旧值。
7. 忽略「失败模式」设计：CP 系统的少数派应返回明确错误而非静默阻塞，否则会造成上游超时雪崩。

## 八、面试题
1. CAP 为什么说分区下 C 与 A 不可兼得？
   要点：异步网络 + 分区下，保一致就要拒少数派写（损可用），保可用就要允分歧（损一致）。
2. CP 与 AP 在脑裂时行为有何不同？
   要点：CP 拒少数派写、防双主；AP 两侧写、需事后合并。
3. 为什么真实系统几乎都是 CP 或 AP 而非 CA？
   要点：分布式系统分区不可避免，CA 只在单点/无分区假设下成立。
4. PACELC 在 CAP 之外补充了什么？
   要点：无分区时还要在延迟 L 与一致性 C 间取舍。
5. 高延迟为何也算分区？
   要点：异步模型下节点无法区分「慢」与「断」，超时即等价于失联。
6. CP 系统少数派应当如何表现？
   要点：快速返回明确错误（fail fast），而非静默阻塞，以免上游超时放大故障。

## 九、演进与趋势
「可调一致性」让单系统在请求级选择 C 或 A；PACELC 在 CAP 之外补充「无分区时延迟 vs 一致性」的取舍；共识算法（Raft/Paxos）把 CP 的强一致实现标准化；多活数据中心推动「CRDT + quorum」的混合，让 AP 也能渐进收敛到强一致。

另一趋势是「按数据分级的容错」：同一系统内，账户余额这类关键数据走 CP，点赞数这类可合并数据走 AP，从而在整体上同时获得合理的一致性体验与可用性。这也呼应了 PACELC 的「按请求取舍」思想。

## 十、小结
网络分区是脑裂的源头，CAP 定理从数学上框定了分区下「保一致或保可用」的取舍。CP 预防脑裂、AP 接受并解决脑裂——这是一切分布式容错设计的前提，而 PACELC 提醒我们无分区时仍有 L/C 的权衡。掌握「不可区分性」这一证明内核，就能理解为什么 CAP 是模型层面的事实而非实现缺陷。
