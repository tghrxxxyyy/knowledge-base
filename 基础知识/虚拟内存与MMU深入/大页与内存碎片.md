# 大页与内存碎片

> 对应 CSAPP 中文笔记 https://github.com/Hansimov/csapp 第9章；OSTEP；Linux 内核文档《HugeTLB / HugePages》与《Transparent Hugepage》。

## 一、背景与挑战

4KB 页在超大内存工作集下迅速成为瓶颈。现代服务器几百 GB 内存，若按 4KB 页管理，活跃页数可达数千万；即便 L2 TLB 有 1536 项，覆盖也只有 6MB，数据库缓冲池、JVM 堆、AI 训练张量随便一热就是几十 GB，TLB 抖动让有效访问时间翻倍。另一方面，大页（2MB、1GB）需要连续物理页框，随着系统长时间运行，内存被切碎，即使空闲总量足够也常常分配失败。

这就形成两难：用大页提升 TLB 覆盖、缩短页表遍历（2MB 页在 PD 级终止，少走两级），却要付出内部碎片、内存占用放大、分配碎片化、以及回收/压缩停顿的代价。透明大页（THP）试图自动合并小页，但合并本身要扫描页表、迁移页面，可能造成延迟毛刺，数据库圈甚至有「关 THP」的老经验。工程上必须理解何时该开大页、如何预留、如何观测碎片。

本主题是虚拟内存工程化的高价值内容：它把页表结构、TLB、伙伴系统（buddy allocator）、内存规整（compaction）串起来，也是面试区分「知道概念」和「做过系统调优」的典型题。真实系统里，大页策略要和业务形态对齐：数据库缓冲池适合显式预留 2MB/1GB 页，容器集群可能偏向 THP + 监控，HPC 作业启动时一次性 `mlock` 大页以保证确定性。

理解碎片比背命令更重要。分配器面对的是「空闲总量够、连续块不够」的尴尬局面，伙伴系统靠合并邻居维持 $2^k$ 连续块，但长期运行、随机大小的分配最终仍会打碎内存。compaction 通过迁移页面搬出空洞，却引入停顿；因此延迟敏感服务常显式关闭 THP，或改为 `madvise` 精细控制。定量上，用覆盖公式与内部碎片公式做取舍，远比「听说大页快」可靠。

## 二、核心原理

**大页形态**：x86-64 支持 4KB、2MB、1GB。2MB 页在 PD 级表项 `PS=1` 直接给出 PFN；1GB 页在 PDPT 级。PTE 数量大幅下降：覆盖 1GB 内存，4KB 页需 262144 个 PTE，2MB 页需 512 个，1GB 页只要 1 个。

**TLB 覆盖提升**：$Coverage = N_{entries} \times PageSize$。同样 64 项，4KB 覆盖 256KB，2MB 覆盖 128MB，1GB 覆盖 64GB。随机访问命中率近似 $\min(1, C/W)$，大页直接把 $C$ 放大几个数量级。

**内部碎片**：程序实际用 $U$ 字节，分配到 $k$ 个大页，浪费 $k\cdot PageSize - U$。平均浪费约半页；对大量中等尺寸对象，若各自独占大页则浪费惊人。所以大页适合「真正大而连续」的工作集，不适合海量小对象。

**外部碎片与分配**：2MB 页需要 512 个连续 4KB 物理页。伙伴系统靠合并相邻块维持连续性，但长期运行后仍可能碎片。Linux 提供：

- **显式 HugeTLB**：`echo N > /proc/sys/vm/nr_hugepages` 预留，或 `mmap(MAP_HUGETLB)`；确定性好，适合数据库。
- **透明大页 THP**：内核在缺页时尝试 `khugepaged` 合并，运行中迁移页面形成大页；便利但有停顿与内存占用波动，可通过 `/sys/kernel/mm/transparent_hugepage/enabled` 调成 `madvise` 或 `never`。

**页表遍历缩短**：大页使 walk 提前终止，$t_{walk}$ 降低约 $2/4$（省两级访存），在 TLB 缺失时仍更快。

**边界条件**：COW 时大页可能被拆成 4KB（split_huge_page），共享库多的进程收益下降；NUMA 跨节点大页分配更难；内存回收时大页回收粒度粗，可能放大冷热干扰。

**碎片的两层含义**：外部碎片指空闲内存不连续，大页分配因此失败；内部碎片指页内未用满，按 2MB 页装 100KB 对象会浪费大量内存。两者往往此消彼长——页越小外部碎片越易管理、内部碎片越少，但 TLB 覆盖越差。工程上常用「大页给大缓冲、小页给小对象」的分层策略，而不是全局一刀切。

**THP 的运行时行为**：`khugepaged` 后台线程扫描可合并区间，缺页路径也可能直接建大页；内存紧张时又会 split 回 4KB。监控 `AnonHugePages`、`thp_fault_alloc`、`thp_collapse_alloc` 与延迟分位数，才能判断 THP 是在帮忙还是在添乱。

## 三、形式化与数学基础

设 TLB 项数 $N$，页大小 $P$，工作集页数 $W = \lceil M / P \rceil$（$M$ 为活跃内存）。理想 LRU 下随机访问命中率近似：

$$h \approx \min\left(1, \frac{N\cdot P}{M}\right)$$

**例**：$M=1GB$，$N=64$  
- 4KB：$N P = 256KB$，$h \approx 0.00025$  
- 2MB：$N P = 128MB$，$h \approx 0.125$  
- 1GB：$N P = 64GB$，$h \approx 1$  

配合 $EAT = t_{hit} + (1-h)t_{walk}$，命中率提升直接降低有效延迟。

碎片量化：分配 $U$ 字节到大页大小 $P_H$：

$$InternalFrag = \left\lceil \frac{U}{P_H} \right\rceil P_H - U \in [0, P_H)$$

碎片化程度可用「最大可分配连续块」与「空闲总量」比值描述。令 $F$ 为空闲率，$L_{max}$ 为最大连续块，则大页分配成功概率随 $L_{max}$ 衰减；Linux compaction 通过迁移页面把 $L_{max}$ 抬高，代价是 CPU 与延迟抖动。

内存密度权衡：大页数量 $k = \lceil U/P_H\rceil$，占用 $k P_H$。若对象尺寸分布方差大，应使用 slab/对象池而把大页只给真正的大缓冲。

## 四、代码实现

用 Python 模拟「4KB vs 2MB 页」的 TLB 覆盖与内部碎片，并给出 Linux 查看命令：

```python
import math


def tlb_coverage(entries: int, page_size: int) -> int:
    return entries * page_size


def hit_rate_approx(working_set: int, entries: int, page_size: int) -> float:
    return min(1.0, tlb_coverage(entries, page_size) / working_set)


def internal_frag(used: int, page_size: int) -> int:
    return math.ceil(used / page_size) * page_size - used if used else 0


def compare_pages(working_set=1 << 30, tlb_entries=64):
    print(f"working_set={working_set/2**30:.2f} GiB, TLB entries={tlb_entries}")
    for name, ps in [("4KiB", 4096), ("2MiB", 2 << 20), ("1GiB", 1 << 30)]:
        cov = tlb_coverage(tlb_entries, ps)
        h = hit_rate_approx(working_set, tlb_entries, ps)
        print(f"  {name:5s} coverage={cov/2**20:8.2f} MiB  h~{h:.6f}")
    print("frag for 10.5MB payload in 2MiB pages:", internal_frag(int(10.5 * 2**20), 2 << 20), "bytes")
    print("frag for 10MB payload in 2MiB pages:", internal_frag(10 << 20, 2 << 20), "bytes")
    print("frag for 9MB payload in 2MiB pages:", internal_frag(9 << 20, 2 << 20), "bytes")


if __name__ == "__main__":
    compare_pages()
```

系统侧观测与启用（需 root，仅示意）：

```bash
grep -i huge /proc/meminfo
# HugePages_Total / HugePages_Free / Hugepagesize
cat /sys/kernel/mm/transparent_hugepage/enabled
# 预留 2MB 大页
# echo 512 > /proc/sys/vm/nr_hugepages
# 程序内: mmap(..., MAP_HUGETLB | MAP_HUGE_2MB)
```

预期输出：4KiB 覆盖 0.25MiB、$h$ 极小；2MiB 覆盖 128MiB；1GiB 覆盖远超工作集。碎片示例：10MB 恰为 5 个 2MB 页浪费 0；10.5MB 浪费 1.5MB；9MB 浪费 1MB——大页的浪费取决于载荷与页大小的余数关系。

## 五、与其他技术对比

| 方案 | TLB 覆盖 | 内部碎片 | 分配难度 | 延迟确定性 |
|------|----------|----------|----------|------------|
| 4KB 标准页 | 小 | 小（平均半页） | 低 | 高 |
| 2MB 大页 | 大（512×） | 中 | 中 | 中（THP 有停顿） |
| 1GB 大页 | 极大 | 大 | 高 | 高（显式预留） |
| THP 自动 | 动态 | 中 | 自动但可抖动 | 波动 |
| 显式 HugeTLB | 可控 | 中 | 需预留 | 高 |

与「对象池/slab」对比：slab 解决小对象分配效率，大页解决地址转换与页表压力，二者正交，常一起用（内核 slab 页仍是 4KB，但缓存了对象）。与「mlock 全锁定」对比：mlock 防换出但不自动用大页；两者叠加可给实时任务最稳定的内存行为，代价是弹性下降。

与「压缩内存（zswap/zram）」对比：压缩提高有效容量，却不减少 TLB 项数；大页提高转换效率，却不增加容量。内存子系统的问题常常需要多个工具组合，而不是单点银弹。

## 六、常见误区

1. **「大页总是更快」**——小工作集 TLB 本不缺，大页只增加浪费；某些负载 THP 合并/拆分反而引入毛刺。应测量 `perf` 与延迟分位数再决定。
2. **「开 THP 就等于用上 2MB 页」**——THP 是尽力而为，碎片或内存紧张时会拆分；`AnonHugePages` 变小说明没用上。
3. **「内部碎片可以忽略」**——对海量 32KB 小缓存若按 2MB 页分配，浪费近 99%；大页应给大缓冲区。
4. **「nr_hugepages 设置越大越好」**——预留页不能被普通分配使用，设太多挤压系统内存，可能触发 OOM；应按工作集预留并监控 `HugePages_Free`。
5. **「大页不影响缺页」**——大页首次缺页要分配/合并连续页，可能更慢；COW 写时会 split，语义与 4KB 不完全一致。

## 八、面试题

1. **大页的收益与代价各是什么？**  
   参考答案：收益是提高 TLB 覆盖、减少 walk 级数、减少 PTE 数量；代价是内部碎片、连续物理分配难度、THP 停顿与内存回收粒度变粗。

2. **为什么数据库偏好显式大页而非 THP？**  
   参考答案：需要延迟确定性；THP 合并/拆分会造成尾延迟毛刺。预留 HugeTLB 后内存布局稳定，性能可预测。

3. **TLB 64 项，覆盖 1GB 工作集，4KB 与 2MB 页命中率大概多少？**  
   参考答案：$h \approx N P / M$。4KB：$64\times 4KB/1GB \approx 0.00025$；2MB：$64\times 2MB/1GB = 0.125$。差数百倍。

4. **如何查看与启用大页？**  
   参考答案：`/proc/meminfo` 的 HugePages_*，`/sys/kernel/mm/transparent_hugepage/enabled`，`mmap(MAP_HUGETLB)` 或 `echo N > /proc/sys/vm/nr_hugepages`。

## 九、演进与趋势

趋势是「多页尺寸并存 + 自适应」：CPU TLB 同时缓存 4K/2M/1G；内核根据负载自动提升/拆分 THP（`madvise` 精细控制）；1GB 页在数据库与 JVM 堆中成为标配；CXL 内存池与持久内存继续用大页降低远端访问的转换开销；GPU/HBM 通过 IOMMU 映射大页。学术与工业界还在研究「页大小分层」（sub-page、flexible page size）与基于 PMU 的自动调参。理解碎片与覆盖的数学关系，才能在这些新机制前做出正确配置，而不是盲目追新。

## 十、小结

大页用更大的映射粒度换取 TLB 覆盖与更短的页表遍历，却引入内部碎片与连续分配难题；THP 降低使用门槛但带来延迟波动。正确的工程姿态是：量化工作集与覆盖，选择显式或透明大页，监控 HugePages 与延迟分位，在 TLB 效率与内存密度之间取得可测量的平衡。
