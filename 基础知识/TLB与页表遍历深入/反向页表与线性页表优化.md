# 反向页表与线性页表优化

> 对应 Tanenbaum & Bos《Modern Operating Systems》内存管理章；Stallings《Computer Organization and Architecture》；IBM Power ISA（Hashed Page Table）。

## 一、背景与挑战

正向多级页表以虚拟地址为索引，"每个进程一套"，空间随进程数与映射量增长。在 64 位地址空间下虽然稀疏，但成百上千个进程叠加后，页表本身的内存占用与缓存污染仍相当可观。

反向页表（inverted page table, IPT）翻转索引方向：以**物理页框**为索引，全系统只有一张表，表项数等于物理页数，与进程数、虚拟地址空间大小都无关。代价是失去了"一次索引"的能力——必须由虚拟地址反查。

## 二、核心原理

IPT 表项记录"哪个虚拟地址映射到这个物理框"：

$$\text{IPT}[pfn] = \langle pid,\ vpn_{tag},\ \text{权限位} \rangle$$

由于虚拟地址空间远大于物理内存，多个 VA 竞争同一表项，因此必须用**哈希**把它折叠到有限表项中，冲突用链式或开放寻址解决，这就是 hashed page table。IBM Power 的 HTAB 是经典实现：以虚拟页号参与哈希，得到页表项组（PTEG），每组容纳固定数量的页表项（PTE），组内线性查找；TLB 未命中时由硬件走这一段哈希查找。

Linux 中的"反向映射"（rmap / `anon_vma`、`address_space.i_mmap`）是另一个概念：它解决的是"给定一个物理页，找出所有映射它的 PTE"，用于页换出、迁移与 unmap，本身并不是反向页表，但共享同一个思路——维护反向索引以避免全表扫描。

## 三、形式化与数学基础

表大小只与物理内存有关：

$$|IPT| = N_{phys\_pages} = \frac{M_{RAM}}{PageSize}$$

以哈希实现时，查找代价取决于负载因子与链长。对链地址法，成功查找的期望探测次数近似为

$$E[\text{probes}] \approx 1 + \frac{\lambda}{2},\qquad \lambda = \frac{n}{m}$$

其中 $n$ 为已映射页数、$m$ 为表项数。当物理内存接近满载（$\lambda \to 1$）时，链长增长，查找与插入成本上升；而正向多级页表的查找次数恒为级数（最坏 4 次），与负载无关。这构成了两者最本质的权衡：**空间可预测 vs. 时间可预测**。Power 的 HTAB 用"每组固定项数 + 硬件并行比较"把组内查找压成一次访存来缓解该问题。

## 四、代码实现

```c
/* 哈希反向页表（开放寻址示意） */
struct ipt_e { unsigned long va_tag; int pid; unsigned long pfn; int used; };
static struct ipt_e ipt[MAX_PFN];

static unsigned hash(unsigned long va, int pid) {
    return (unsigned)((va >> 12) ^ ((unsigned long)pid * 0x9E3779B97F4A7C15UL)) % MAX_PFN;
}

long ipt_lookup(unsigned long va, int pid) {
    unsigned h = hash(va, pid);
    while (ipt[h].used) {
        if (ipt[h].va_tag == (va >> 12) && ipt[h].pid == pid)
            return (long)h;                       /* 返回 pfn */
        h = (h + 1) % MAX_PFN;                    /* 探测下一槽 */
    }
    return -1;                                    /* 未映射 */
}
/* 冲突多时，插入也要沿同一探测序列找空槽 */
```

工程上还需处理"固定项数不足"的情况：Power 的 HTAB 在组满时触发哈希页表溢出处理，体现为性能下降而非功能错误。

## 五、与其他技术对比

| 维度 | 正向多级页表 | 反向/哈希页表 | Linux 反向映射（rmap）|
| --- | --- | --- | --- |
| 索引方向 | VA → PA | PFN 定位，记 VA | PA → 所有 PTE |
| 表大小 | 随进程与映射量 | 随物理页数 | 随映射关系 |
| 查找代价 | 固定级数 | 依赖哈希负载 | 遍历映射链 |
| 多进程开销 | 每进程一套 | 全局共享 | 全局共享 |
| 典型实现 | x86、ARMv8 | IBM Power HTAB、IA-64 VHPT | Linux 页回收/迁移 |

## 六、常见误区

1. **以为反向页表能直接由 VA 得 PA**：必须哈希反查并解决冲突，最坏情况代价高于多级遍历。
2. **以为它取代 TLB**：二者互补——TLB 缓存热映射，IPT 是后备结构，未命中仍要走一次查找。
3. **把 Linux rmap 当成反向页表**：rmap 是"物理页 → 映射它的 PTE 集合"的辅助索引，页表本身仍是正向多级结构。
4. **忽略共享内存的语义**：一个物理框可被多个 VA/进程映射，IPT 需按共享链表或标识共享页，而非简单一对一。
5. **忽视大页**：大页会改变哈希粒度与表项占用，需专门处理。

## 八、面试题

1. **反向页表为什么在 64 位系统更省内存？** 要点：表项数由物理页数决定，与虚拟地址空间和进程数无关。
2. **反向页表的性能代价？** 要点：失去直接索引能力，需哈希查找并处理冲突，负载高时探测次数上升。
3. **Linux 的 rmap 解决什么问题？** 要点：给定物理页快速找到所有映射它的 PTE，用于换出、迁移与 unmap 时的 TLB 失效。
4. **为什么 Power 用哈希页表而 x86 不用？** 要点：架构设计取向不同——Power 强调物理内存受限下的页表空间可控，x86 强调查找时间可预测与硬件实现简单。
5. **反向页表如何表示共享页？** 要点：需为同一物理框维护多个（pid, va）映射记录或指针链表，不能简单一对一。

## 九、演进与趋势

在虚拟化环境中，嵌套页表（EPT/NPT）让"两级地址翻译"成为常态，反向着眼于"空间可预测"的思路在新架构中仍有体现。同时，大规模内存系统（CXL 扩展内存、分层内存）需要按物理位置管理元数据，反向索引的价值回升。Linux 侧则在正向多级页表上叠加更多反向辅助结构（rmap、页表页回收、`pte_offset` 优化）来替代整体翻转索引方向。

## 十、小结

反向页表以"物理页为索引"翻转了映射视角，把表大小与虚拟地址空间解耦，适合物理内存受限、进程众多的场景；代价是查找从"固定级数"变成"依赖负载的哈希探测"。它与正向多级页表、TLB、Linux rmap 各自解决不同侧面的问题，理解其取舍比记住结论更重要。
