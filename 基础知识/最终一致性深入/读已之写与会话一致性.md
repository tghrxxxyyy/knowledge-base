# 读已之写与会话一致性

> 对应 Terry et al. 1994《Session Guarantees for Weakly Consistent Replicated Data》、Vogels 2009《Eventually Consistent》（client-centric guarantees）、Kleppmann《Designing Data-Intensive Applications》第 5 章，以及 Terry et al. 1995《Managing Update Conflicts in Bayou》。

## 一、背景与挑战

纯最终一致会带来一类非常刺眼的体验问题：用户刚提交表单、刚发完消息、刚更新头像，刷新却看到旧内容。系统在技术上是「正确的」（分歧最终会收敛），但用户会认为系统坏了，甚至重复提交导致重复订单。根源在于最终一致的保证是「系统级」的，而用户感知是「会话级」的：同一用户短时间内的一系列操作构成一个逻辑会话，只要会话内部的因果与顺序关系被破坏，体验就崩坏。因此需要在最终一致底座之上提供一组以客户端（会话）为单位的一致性保证，把「用户视角下必须成立」的几条性质显式建模。

## 二、核心原理

Terry 等人提出四类会话保证，它们共同构成 client-centric consistency 的核心。

读己之写（Read-Your-Writes）：进程读到的数据必须包含它自己之前的写。客户端在写成功后记录一个「写标记」（版本号或时间戳），后续读请求携带该标记，服务端保证返回不早于该标记的数据。

单调读（Monotonic Reads）：同一进程后续的读不会看到比之前读到的更旧的数据，即读到的数据版本单调不减。客户端记录上次读到的版本，后续读要求副本至少达到该版本。

单调写（Monotonic Writes）：同一进程的写按调用顺序在所有副本上生效，不会「后发先至」。靠固定路由到同一副本，或携带顺序号按因果投递实现。

写随读（Writes-Follow-Reads）：同一进程的写必须在它所依赖的那些读所对应的更新之后生效，保证「读—改—写」序列不会因副本滞后导致基于旧值的写覆盖新值（丢失更新）。

四条保证的组合常被称为「会话一致」。直观实现路径是「会话粘性 + 版本追踪」：把同一会话的请求固定路由到特定副本（sticky session），副本自身按序应用更新，于是单调性与读己之写自然成立。但粘性路由在副本故障或负载均衡时会被破坏，因此更稳健的做法是携带版本令牌并做条件性路由或等待。

实现的关键机制有三种：版本令牌（客户端保存服务端返回的版本号，后续请求携带它，服务端拒绝或等待不满足条件的副本）；条件路由（代理层按令牌选择至少达到该版本的副本）；写路径固化（客户端把同一键的写路由到同一副本以避免多写乱序）。

边界必须强调：这些保证都是「单客户端视角」的，跨设备、跨浏览器、跨会话一律不保证；用户换设备登录看到旧数据是符合语义的。此外，读己之写只保证「自己的写」可见，不保证「他人的写」，也不保证读到全局最新值。

## 三、形式化与数学基础

把会话 $S$ 视为一个客户端进程发起的操作序列，$\text{ver}(r)$ 表示读操作 $r$ 返回的版本，$\text{ver}(w)$ 表示写操作 $w$ 产生的版本。四条保证可形式化如下：

$$ \text{读己之写}:\quad w \to_{S} r \implies \text{ver}(r) \ge \text{ver}(w) $$

$$ \text{单调读}:\quad r_1 \to_{S} r_2 \implies \text{ver}(r_2) \ge \text{ver}(r_1) $$

$$ \text{单调写}:\quad w_1 \to_{S} w_2 \implies \text{ver}(w_2) \ge \text{ver}(w_1) \ \wedge\ \text{各副本生效顺序一致} $$

$$ \text{写随读}:\quad r \to_{S} w \implies \text{ver}(w) \ge \text{ver}(r) $$

用版本向量表达实现条件更直接：设客户端保存令牌 $T = (v_1, \dots, v_n)$，其中 $v_i$ 是会话在副本 $i$ 上已知的最高版本。读请求要求目标副本 $j$ 满足

$$ \forall i:\ T[i] \le \text{localver}_j[i] \quad (\text{否则等待或改路由}) $$

这就是「令牌驱动的一致性读」的形式化，也是现代多数据中心数据库实现会话一致的方式。若采用等待而非重路由，最坏等待时间为 $T_{wait} \le T_{repl} + T_{retry}$，其中 $T_{repl}$ 是副本间复制延迟。这解释了会话一致的成本：它不消耗协调开销，但会消耗时间——用户可能为一个「保证看到自己写」的读多等几十毫秒。

## 四、代码实现

带令牌的读己之写实现（客户端保存写标记，读时校验）：

```python
class SessionClient:
    def __init__(self, replicas):
        self.replicas = replicas
        self.wt = None      # 写标记：最近一次写产生的版本
        self.rt = None      # 读标记：最近一次读到的版本，用于单调读

    def write(self, key, value):
        resp = self.replicas[0].put_versioned(key, value)
        self.wt = resp.version
        return resp.version

    def read(self, key):
        # 同时要求：不早于自己的写（wt），不早于上次读（rt）
        need = max_token(self.wt, self.rt)
        for rep in self.replicas:
            if covers(rep.local_version(key), need):
                v = rep.get(key)
                self.rt = rep.local_version(key)   # 更新读标记，保证单调读
                return v
        raise StaleReplicaUnavailable("no replica reached required version")
```

写随读必须携带读标记，确保写建立在它读到的状态之上：

```python
def read_modify_write(client, key, fn):
    cur = client.read(key)                      # 可能等待到满足保证的版本
    return client.write_with_cas(key, fn(cur), base=client.rt)
```

运维侧观察会话一致相关指标：

```bash
nodetool tpstats                     # 副本滞后与请求队列
nodetool netstats                    # 跨区复制延迟（等待时间的主要来源）
```

注意 `covers` 必须比较版本向量而非单一标量，否则跨键、跨副本的令牌校验会失效——这是实现中最常见的错误。

## 五、与其他技术对比

| 保证 | 覆盖范围 | 解决的问题 | 实现成本 | 失败时的现象 |
| --- | --- | --- | --- | --- |
| 线性一致 | 全局所有客户端 | 读一定最新 | 高（共识） | 分区时不可用 |
| 因果一致 | 全局，按因果序 | 顺序悖论（先见果后见因） | 中高（因果元数据） | 元数据膨胀 |
| 读己之写 | 单会话 | 提交后看不到自己的写 | 低（写标记） | 需要等待或重路由 |
| 单调读 | 单会话 | 数据「倒退」出现 | 低（读标记） | 需固定副本或等待 |
| 单调写 | 单会话 | 自己的写乱序生效 | 低（顺序号/固定路由） | 需固定路由 |
| 写随读 | 单会话 | 读改写导致丢失更新 | 中（CAS + 读标记） | 需条件写支持 |
| 纯最终一致 | 无 | 无 | 无 | 上述问题都可能出现 |

权衡主线是「保证范围与成本的对立」：范围越大（从会话到全局），需要的协调或元数据越多，可用性与延迟代价越高。client-centric 保证的价值恰恰在于用极低成本覆盖了绝大多数令用户不满的场景——因为用户的不满是「以自己为中心」的。

## 六、常见误区

1. 认为读己之写等于全局强一致。它只保证「自己的写」对自己的读可见，不保证看到他人更新，也不保证读到全局最新值。
2. 认为可以跨设备跨会话生效。这些保证以会话（进程）为单位，换设备、换浏览器、会话超时后一律不适用。
3. 认为会话一致不需要额外成本。它虽不需要共识，但需要携带令牌、条件路由与可能的等待重试，会带来可观的长尾延迟。
4. 只用标量版本实现令牌校验。跨副本、跨键场景必须用版本向量或可比较的因果令牌，标量无法表达偏序，会漏判。
5. 忽略写随读的必要性。不保证写随读时，用户「读到旧值后修改再写回」会把旧值固化，造成丢失更新，比读到旧值更严重。
6. 认为固定路由（sticky session）足够。副本故障或重平衡会破坏粘性，必须有令牌机制兜底。

## 七、与开源书·权威来源对应

- Terry et al. 1994：四条会话保证的原始定义与形式化，是 client-centric 一致性研究的起点。
- Terry et al. 1995《Managing Update Conflicts in Bayou》：弱一致复制系统中冲突检测与处理的经典实践。
- Vogels 2009《Eventually Consistent》：把会话保证纳入最终一致模型并命名为 client-centric guarantees。
- Kleppmann《Designing Data-Intensive Applications》第 5 章：复制滞后现象（读己之写、单调读、一致前缀读）的系统性讨论。
- DeCandia et al. 2007：Dynamo 的实践背景，说明无主架构下会话保证为何必要。
- Azure Cosmos DB / DynamoDB 文档：session token 与可调一致性在工业系统中的落地形式。

## 八、面试题

1. 什么是读己之写，如何实现？
   要点：进程能读到自己之前的写；实现是写成功后记录版本令牌（写标记），后续读携带该标记，服务端只返回不早于该标记的副本，否则重路由或等待。

2. 会话一致与其他 client-centric 保证是什么关系？
   要点：会话一致通常指四条保证（读己之写、单调读、单调写、写随读）的组合；它们都以会话为单位，可单独提供也可叠加。

3. 单调读和线性一致有什么区别？
   要点：单调读只保证同一会话的读版本不倒退，允许落后于最新；线性一致要求任何读都反映最近一次成功写，强得多也贵得多。

4. 为什么需要写随读？
   要点：防止「读旧值—修改—写回」把旧值固化造成丢失更新；写必须建立在它读到的状态之上，因此需要 CAS 或携带读标记的条件写。

5. 固定路由为什么不够？
   要点：副本故障、扩容缩容或负载重平衡都会破坏粘性，导致请求落到落后副本；必须有版本令牌机制作为兜底保证。

## 九、演进与趋势

趋势一是令牌机制的标准化：多区域数据库把 session token 作为一等公民返回给客户端，客户端只需原样回传即可获得会话一致，把复杂度从应用移到 SDK。趋势二是把 client-centric 保证下沉到代理与协议层：服务网格或数据库代理可自动追踪令牌并完成条件路由，应用代码无需感知。趋势三是与因果一致融合：会话保证是因果一致的局部化形式，用因果关系图或混合逻辑时钟可同时提供全局因果序与会话级保证，以较少元数据覆盖更多顺序需求。趋势四是与 CRDT 协同：CRDT 保证合并确定性，却无法解决「看到自己写」的体验问题，两者常叠加使用。

## 十、小结

读己之写与其他一致性保证的不同之处在于，它以客户端会话为单位，用极低成本解决了最终一致中最刺眼的体验问题。四条会话保证分别对应「看不到自己写」「数据倒退」「自己的写乱序」「读改写丢失更新」四类现实故障，实现上依赖写标记、读标记、令牌校验与条件路由。必须牢记两条边界：它只覆盖单会话，跨设备跨会话无效；它需要携带元数据并可能等待，因而会带来可观的长尾延迟，不能当作免费午餐。
