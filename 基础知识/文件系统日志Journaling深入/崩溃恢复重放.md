> 对应 Silberschatz《Operating System Concepts》「Recovery」与 Linux 内核 ext4 恢复逻辑。

## 一、背景与挑战
系统崩溃后重启，文件系统可能处于「部分事务已写、部分未写」。需要一种确定、可重复、且快速的流程，把系统恢复到一致状态，而不依赖缓慢的全盘 fsck。

## 二、核心原理
挂载时，JBD2 扫描日志：从最后干净检查点开始，按顺序读取事务。对每个事务：若有有效提交块（校验和通过），则重放其描述的数据/元数据到主结构；若遇到无提交块或校验失败的事务，则停止（之后的都视为未完成并丢弃）。重放幂等，可安全重复。

## 三、形式化与数学基础
设日志事务序列 T_1..T_n，恢复处理前缀 T_1..T_k 其中：
```
k = max i 满足 (commit(T_i) 存在 且 checksum(T_i) 有效)
```
对 i<=k 重放 apply(T_i)；对 i>k 丢弃。因 apply 幂等：
```
apply(apply(T_i)) == apply(T_i)
```
故重复重放（如因多次挂载）不会破坏一致性。

## 四、代码实现
```c
// fs/jbd2/recovery.c（简化）
int journal_recover(journal_t *journal)
{
    err = do_one_pass(journal, &info, PASS_SCAN);    // 找最后有效提交
    err = do_one_pass(journal, &info, PASS_REPLAY);  // 重放已提交
    err = do_one_pass(journal, &info, PASS_REVOKE);   // 处理撤销块
    return err;
}
// PASS_REPLAY 中：读描述块 -> 校验 -> 写回主区
```

## 五、与其他技术对比
- 全盘 fsck：正确但 O(容量)，慢。
- 日志重放：O(飞行中事务)，快。
- COW 文件系统：靠「原子切换根指针」而非重放，崩溃即停在上一一致快照。

## 六、常见误区
- 误区：重放会重做已完成的正常写。已 checkpoint 的日志槽被回收，不会被再次处理。
- 误区：恢复总能修复一切。日志只保证元数据一致，应用层写事务语义需应用自己保证。

## 九、演进与趋势
ext4 fast_commit 让恢复只需重放少量增量记录；日志校验和使恢复更稳健；与 e2fsprogs 的离线检查形成「在线快恢复 + 离线深检查」双层防护。

## 十、小结
崩溃恢复重放以「扫描有效提交、幂等重放、丢弃未完成」的确定流程，把恢复时间从与容量相关降到与飞行事务相关。
