# 组播地址与组播组模型

> 对应 RFC 1112（Host Extensions for IP Multicasting, IGMPv1）与 RFC 4607（Source-Specific Multicast, SSM）。

## 一、背景与挑战

一对多、多对多通信（直播、视频会议、状态同步）若用单播，源需为每个接收者复制一份报文，带宽随接收者数线性膨胀；若用广播（255.255.255.255），则打扰网段内所有主机、且无法跨子网、不区分是否真需要。IP 组播以「组」抽象让接收者按需加入，网络只在有接收者的分支上复制转发，从源头到第一跳路由器只发一份，效率最高。其前提是统一的地址模型与成员管理协议——没有一致的组地址约定，路由器无从建立转发状态，组播无从落地。

## 二、核心原理

IPv4 组播地址属 D 类，范围 `224.0.0.0/4`（即 `224.0.0.0`–`239.255.255.255`）。其中 `224.0.0.0/24` 为本地链路保留（link-local）：`224.0.0.1` 表示子网内所有主机、`224.0.0.2` 所有路由器、`224.0.0.5/.6` 为 OSPF 等。接收主机通过 IGMP 向直连路由器发送 Report 加入某组，路由器据此在转发平面上建立组播状态；任意源发往组地址的报文，网络按「(*, G) 或 (S, G)」状态按需复制。D 类地址只能作目的地址，不能作源地址。管理范围 `239.0.0.0/8` 为私有组播（类似 RFC 1918 私网），可企业内部复用而不与公网冲突。组播组是「逻辑标识」，靠 (S,G) 区分具体流，不保证全局唯一。

## 三、形式化与数学基础

组播转发状态以「组/源」对表示：

$$ (*, G):\ \text{任意源到组 }G\text{（ASM 共享树）} $$
$$ (S, G):\ \text{特定源 }S\text{ 到组 }G\text{（源树，SSM 用）} $$

组地址范围约束：

$$ 224.0.0.0 \le addr \le 239.255.255.255,\quad addr\in\text{D 类} $$
$$ 232.0.0.0/8\ \text{保留给 SSM};\quad 239.0.0.0/8\ \text{为管理范围} $$

复制点（replication point）是转发树的分支点：每个分支仅在有成员时才向下转发一份，使总带宽 $\approx$ 源到各接收者最短路径之和（优于单播的 $N$ 倍）。形式化地，对 $N$ 个接收者：单播总带宽 $B_{uni}=N\cdot B_{pkt}$，组播总带宽 $B_{mc}=\sum_{e\in tree}B_{pkt}\le N\cdot B_{pkt}$，且通常远小于 $N$ 倍。

## 四、代码实现

```python
# Linux 加入组播组（Python，IPv4）
import socket, struct
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
# mreq = {组地址(4B), 接口地址(4B)}
mreq = struct.pack('4s4s',
                   socket.inet_aton('224.0.0.251'),
                   socket.inet_aton('0.0.0.0'))
s.setsockopt(socket.IPPROTO_IP, socket.IP_ADD_MEMBERSHIP, mreq)
s.bind(('', 5353))   # 监听组播端口
```

查看主机已加入的组：

```bash
ip maddr show
cat /proc/net/igmp
```

IPv6 组播地址 `FF00::/8` 结构更清晰：高 8 位 `FF` + flag + scope（如 `FF02::1` 链路本地所有节点），寻址语义内建，无需 D 类那样的位映射技巧。

## 五、与其他技术对比

| 方式 | 带宽 | 跨子网 | 打扰无关主机 |
| --- | --- | --- | --- |
| 单播 | $N$ 倍源带宽 | 是 | 否 |
| 广播 | 网段内一次 | 否 | 是（泛洪） |
| 组播 | 沿树复制，最优 | 是（需路由协议） | 否（仅成员） |

广播打扰所有主机且受限网段；单播重复发送浪费源带宽；组播仅发给加入者，但需 PIM/MBGP 等维护转发树与跨域。代价是运维复杂度显著更高，且公网默认多不支持。应用层组播（覆盖网）则在无网络层支持时以端到端方式模拟。

## 六、常见误区

1. 认为组播地址可当源地址——D 类仅作目的地址，源必须是单播地址。
2. 以为组播能跨公网任意传播——实际需 PIM/MBGP 等维护，多数运营商默认不限或限速。
3. 混淆 `224.0.0.1`（所有主机）与 `224.0.0.2`（所有路由器）——前者用于主机发现，后者用于路由器协议。
4. 以为加入组就一定能收到——还需路由层建立 (S,G) 状态、RPF 检查通过。
5. 以为 D 类地址全球唯一——组播组地址是「逻辑组标识」而非「位置」，靠 (S,G) 区分流，不保证全局唯一。
6. 以为 link-local 组（224.0.0.0/24）可路由——它们 TTL=1，仅本地链路，不会被路由器转发。

## 七、与开源书·权威来源对应

- RFC 1112（Deering 1989）：定义主机组播扩展与 IGMPv1，奠定 D 类地址与组成员模型。
- RFC 4607（Holbrook & Cain 2006）：定义 SSM，限定 `232.0.0.0/8` 与 (S,G) 模型。
- Tanenbaum《Computer Networks》ch5：组播寻址与成员管理。
- Kurose & Ross《Computer Networking》ch4：IP 组播与 IGMP 入门。
- RFC 1918 / RFC 2365：私网/管理范围地址背景。
- RFC 4291：IPv6 组播地址结构（FF00::/8）。

## 八、面试题

1. `224.0.0.1` 与 `224.0.0.2` 区别？
   要点：前者=子网内所有主机，后者=所有路由器；常用于邻居发现类协议。
2. 为什么组播比单播省带宽？
   要点：源到第一跳只发一份，网络在树分支点复制，总带宽≈各接收者最短路径和，而非 $N$ 倍。
3. 管理范围 `239/8` 的用途？
   要点：企业私用组播，类似 RFC 1918，可跨站点复用而不冲突公网。
4. 为什么 D 类不能作源地址？
   要点：组播语义是「发往一组接收者」，源必须是唯一可路由的单播地址，否则回程路径无法建立。
5. IPv6 组播地址结构为何更清晰？
   要点：`FF` 前缀 + flag + scope 字段内建，无需 D 类的低位映射技巧，寻址语义自解释。

## 九、演进与趋势

SSM（RFC 4607）简化模型、收指定源；IPv6 组播（`FF00::/8`）内建且地址结构更清晰（含 scope/flag 字段）；BIER（RFC 8279）探索无状态比特索引转发，免去显式建树；SDN 用控制器集中算树替代分布式协议。应用层组播（覆盖网）在无网络层支持时以端到端方式模拟，但带宽效率低于网络层。组播在数据中心因运维复杂常让位于 REPLICATE-IN-SOFTWARE。

## 十、小结

IP 组播以 D 类地址与「组」概念实现高效一对多分发：IGMP 管理主机成员关系、(S,G)/(*,G) 刻画转发状态，是流媒体与状态同步的基础技术。理解地址范围与组模型，是排错与正确部署组播的前提——而「组地址是逻辑标识、靠 (S,G) 区分流」这一点，是避开配置误区的关键。记住：组播省的是「源到各接收者」的带宽，前提是路由层建树与 RPF 正确。
