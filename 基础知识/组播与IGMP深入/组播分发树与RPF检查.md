# 组播分发树与RPF检查

> 对应 RFC 4601（PIM-SM）与 RFC 3973（PIM-DM），以及 Tanenbaum《Computer Networks》组播转发基础（RPF）。

## 一、背景与挑战

单播转发按「目的地址」查转发表找路；组播转发方向相反——它要按「来源」逆向建树并避免环路。若不对入接口做约束，组播报文会在网络中无限循环、形成组播风暴，占用全部带宽。反向路径转发（Reverse Path Forwarding, RPF）是防环与正确建树的核心机制：它用「单播路由表中到达源的接口」作为唯一合法的入接口，保证组播流只沿「朝向源」的方向进入网络，自然形成无环分发树。绝大多数组播故障（收不到流、收到重复流）的根因都落在 RPF 或成员状态上，理解 RPF 是排错组播的第一把钥匙。

## 二、核心原理

RPF 检查：当路由器从某接口收到 $(S,G)$ 报文时，查单播路由表（含静态 `mrroute`）得到「到达源 $S$ 的最佳出接口」，即 RPF 接口。若收到报文的入接口正是该 RPF 接口，则接受并向下游（出接口列表 OIL）转发；否则丢弃。这样每个 (S,G) 流只在「源到各接收者的最短路径树（SPT）」上传播，loop-free。OIL 由下游的 Join 状态（(*,G) 或 (S,G)）决定——只有确有成员的分支才在 OIL 中。RPF 失败常见于非对称路由（去程与回程路径不同）或缺少到源的路由，需用静态 `mrroute` 修正。注意 RPF 基于「到源」而非「到组」，因此同一组内不同源走不同树，互不干扰。断言（Assert）机制则在多路由器连同一网段时选一个转发者，避免重复转发。

## 三、形式化与数学基础

RPF 判定（按源 $S$ 的反向接口）：

$$ accept(pkt,\ in\_if) \iff in\_if = RPF\_interface(S) $$

其中 $RPF\_interface(S)$ 由单播 FIB（含静态组播路由）查得。出接口列表由加入状态决定：

$$ OIL(G)=\{\,p\mid p\text{ 有 }(*,G)\text{ 或 }(S,G)\text{ 下游状态}\,\} $$

转发规则：接受 iff RPF 通过，且向 $OIL\setminus\{in\_if\}$ 复制转发。该规则等价于「沿以 $S$ 为根的最短路径树下行」，故无环（树结构天然无环）。若到源有多条等价路径，RPF 取「管理距离最小、度量最小」者；静态 `mrroute` 可覆盖，处理非对称场景：

$$ RPF\_interface(S) = \text{argmin}_{i} metric_i(S) \quad (\text{可被静态覆盖}) $$

该定义保证：任何非 RPF 接口进入的报文都是「绕远路」的副本，必丢弃，从而消除风暴。

## 四、代码实现

```python
# 概念性 RPF 检查
def rpf_check(src, in_if, unicast_fib):
    return in_if == unicast_fib.rpf_interface(src)

# 组播转发：RPF 通过才向出接口列表复制
def mcast_forward(pkt, in_if, oil, fib):
    if not rpf_check(pkt.src, in_if, fib):
        return DROP                    # 非 RPF 接口，丢弃（防环）
    for out in oil:
        if out != in_if:
            send(pkt, out)
```

Linux 查看组播路由与 RPF 状态：

```bash
ip mroute show        # 内核组播路由表（含 IIF/OIL）
# 用 pimd / smcroute 维护，或用 ip route add ... multicast 修正 RPF
```

## 五、与其他技术对比

| 转发 | 依据 | 方向 | 防环 |
| --- | --- | --- | --- |
| 单播 | 目的 FIB | 朝目的 | 靠路由无环 |
| 组播 RPF | 源 RPF 接口 | 朝源（反向） | 靠树结构无环 |
| 无 RPF | 目的 | — | 易风暴 |

单播依据目的 FIB，组播 RPF 依据源 RPF 接口，方向性相反。RPF 失败常源于非对称路由或缺少到源的路由。断言（Assert）与 BFD 联动则加快 RPF 接口失效时的收敛。SSM 下 RPF 同样适用，只是 (S,G) 由接收者显式指定。

## 六、常见误区

1. 以为组播靠目的地址路由——实际靠「源 RPF 接口」，目的地址只决定组，不决定路径。
2. 以为 RPF 失败一定是配置错——也可能是非对称路径（如去程走 A、回程走 B），需静态 `mrroute`。
3. 混淆 IIF（入接口，须为 RPF 接口）与 OIL（出接口列表）——二者分别由 RPF 与 Join 状态决定。
4. 以为 RPF 只在 PIM-SM 用——DVMRP/PIM-DM/SM 都依赖 RPF 防环，是基础机制。
5. 以为 RPF 接口即「收到包的接口」——必须是「到源最短路径的反向接口」，否则丢弃。
6. 忽略等价多路径——多条等度量路径时 RPF 接口选择需与单播转发一致，否则抖动。

## 七、与开源书·权威来源对应

- RFC 4601 / RFC 3973：PIM-SM / PIM-DM 均规定 RPF 用于建树与防环，是协议正确性的基石。
- Tanenbaum《Computer Networks》ch5：以「反向路径转发」直观说明组播无环分发树原理。
- RFC 4760（MBGP）：为组播维护独立 RPF 拓扑（区别于单播拓扑），处理非对称场景。
- RFC 2189（DVMRP）：早期距离矢量组播路由，同样以 RPF 防环。
- Kurose & Ross《Computer Networking》ch4：组播转发与 RPF 入门。

## 八、面试题

1. RPF 检查失败会怎样？
   要点：报文被丢弃，接收者收不到组播；常见原因是到源的回程路径与入接口不一致（非对称路由）。
2. 为什么 RPF 能防环？
   要点：只允许从「到源最短路径的反向接口」进入，流自然沿 SPT 下行，树结构无环，不会回头。
3. RPF 接口从哪来？
   要点：查单播路由表（或静态 mrroute）得到到达源 S 的最佳出接口，即 RPF 接口。
4. 同一组多个源如何处理？
   要点：每个 (S,G) 独立建树、独立 RPF，不同源走不同 SPT，互不干扰。
5. 等价多路径下 RPF 为何可能抖？
   要点：若单播转发与 RPF 接口选择策略不一致，路径切换会导致 RPF 失败，需统一选路。

## 九、演进与趋势

MBGP（RFC 4760）为组播维护独立 RPF 拓扑，缓解非对称路由；BIER（RFC 8279）以无状态比特索引转发弱化传统树与 RPF 依赖，降低状态与建树开销；SDN 用控制器集中下发 RPF/树状态，简化运维。断言（Assert）与 BFD 联动则加快 RPF 接口失效时的收敛。RPF 检查正从「单播 FIB 派生」走向「独立组播拓扑」，以适应复杂网络。

## 十、小结

RPF 以「按源反向」检查入接口，是组播无环转发与建树的基础。理解「RPF 接口来自单播 FIB、OIL 来自 Join 状态」这一对关系，才能排查组播不通与环路问题——绝大多数组播故障，根因都在 RPF 或成员状态。记住：组播「朝源」而非「朝目的」，这是与单播最反直觉也最关键的区别，也是所有组播排错的起点。
