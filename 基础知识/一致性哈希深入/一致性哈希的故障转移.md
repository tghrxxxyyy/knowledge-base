# 一致性哈希的故障转移

> 对应 DeCandia et al. 2007（Dynamo hinted handoff 与故障转移）与 Kleppmann DDIA 第5章（复制）。

## 一、背景与挑战

一致性哈希回答的是「key 归谁管」，但它从不承诺「这台机器永远活着」。生产集群里节点宕机是常态而非异常：磁盘损坏、内核 panic、云主机被回收、网络交换机割接、滚动升级重启。若每个 key 只有一份数据、只在一台机器上，那么任意一次宕机都会造成数据不可用，甚至永久丢失。把一致性哈希直接当成高可用方案，是分布式系统里最危险的误用之一。

真正的挑战是：**在节点可能临时消失的前提下，继续提供读写，并在节点回来后收敛回正确状态**。这要求一套与哈希环配合的复制与故障转移机制：副本放在哪里、宕机时写到哪里、恢复后怎么归还、长期故障怎么永久重分片、网络分区时会不会产生「两个都认为自己是 owner」的分裂脑。

Dynamo 的回答是一整套组合拳：环上的 preference list 决定副本位置，sloppy quorum + hinted handoff 保证「节点临时宕机时写不丢」，反熵（anti-entropy，Merkle 树）修复长期偏差，成员探测与临时所有权处理分区恢复。这套设计的核心哲学是**可用性优先**：宁可临时写到错误的节点，也不要拒绝写入。理解它，也就理解了 AP 系统的工程底色。面试中常见追问是「节点宕机后数据怎么办」「hinted handoff 的风险」「和 Raft 故障转移的差别」。

## 二、核心原理

**1. 副本链（preference list）**。对每个 key，沿环顺时针取 $R$ 个不同物理节点作为副本（$R$ 通常 3）。第一个是协调者，其余是备份。必须**跨物理机去重**——同一台机器的多个 vnode 不算多副本；还应尽量跨机架/可用区，避免整机架断电导致副本同时消失。

**2. 故障时顺延**。若 preference list 中某节点宕机，写入与读取顺延到列表中下一个健康节点。关键是：**顺延的目标是「临时托管」，不是「永久接管」**。永久接管会带来恢复后数据归属混乱，以及故障期间热点全部压到一台邻居身上。

**3. Hinted handoff（提示移交）**。临时接收方会记下一条「hint」：这份数据本应属于节点 $X$。当 $X$ 恢复，接收方把数据异步回传给 $X$，然后删除 hint。这样故障恢复后系统自动收敛，无需人工搬运。Hint 可以持久化在本地磁盘，防止接收方自己也宕机。

**4. Sloppy quorum（松散法定人数）**。在故障期间，读写不要求达到严格 $R$ 个「正确」副本，只要求 $N$ 个「可用」节点中拿到足够确认（常见 $W+R > N$）。这保证写入不被单点宕机阻塞，代价是故障期间读到的可能是临时节点上的旧数据或 hint 数据，最终一致。

**5. 反熵与成员传播**。节点恢复后除了 handoff，还需要定期用 Merkle 树对比副本差异并修复；成员变更（节点加入/离开/永久故障）通过 gossip 传播，避免「幽灵节点」长期占环。

不变量要点：**正常情况下**每个 key 在 preference list 的 $R$ 个节点上有完整副本；**故障情况下**副本暂时缺失，但写入落到了 hint 节点，不会丢；**恢复后**最终每个 key 回到 preference list 的 $R$ 个节点。系统允许可变的「可用性」，但不允许静默丢数据。

## 三、形式化与数学基础

**不可用概率**。设单节点可用率 $p$（例如 0.99），副本数 $R$，若故障独立，则 key 完全不可用的概率为
$$
P_{\text{down}} = (1-p)^R.
$$
当 $p = 0.99$，$R = 3$ 时 $P_{\text{down}} = 10^{-6}$。这就是为什么 Dynamo 默认 $R=3$。注意独立性假设在机架级故障下不成立，因此 preference list 要跨故障域。

**读写一致性条件**。设 $N$ 为顺延可达节点数，$W$ 为写确认数，$R_r$ 为读副本数。若要求「读能覆盖最近一次写」，需要
$$
W + R_r > N.
$$
典型配置 $N=3, W=2, R_r=2$。故障时 $N$ 可能临时变大（顺延到第 4、5 个节点），此时 $W+R_r > N$ 不一定成立，系统退化为最终一致，靠 handoff/反熵收敛。

**handoff 回传压力**。节点 $X$ 宕机时长 $T$，其写入速率为 $\lambda$，则 hint 积压约 $\lambda T$。$X$ 恢复后要在 $T_{\text{handoff}}$ 内回传完，回传带宽需
$$
B > \frac{\lambda T}{T_{\text{handoff}}}.
$$
若 $X$ 长期宕机导致 hint 过多，正确策略是放弃 handoff、改为全量反熵或重新分片（rebuild），否则接收方与恢复方都被拖垮。

**失败独立性与 $R$ 的边际收益**。当节点故障不是独立事件（同一机架、同一交换机）时，$(1-p)^R$ 低估风险。更稳妥的模型是按故障域 $D$ 计算：若同域故障相关，则有效 $R$ 是「跨域副本数」而不是总副本数。

## 四、代码实现

下面给出「环 + preference list + 健康顺延 + hinted handoff 队列」的最小可运行模型。重点看故障时写入如何落到 hint 节点，以及恢复后如何回传。

```python
import hashlib
from bisect import bisect_left
from collections import defaultdict, deque


def md5_int(data) -> int:
    if not isinstance(data, bytes):
        data = str(data).encode()
    return int.from_bytes(hashlib.md5(data).digest()[:8], "big")


class FailoverRing:
    def __init__(self, nodes, v=10, R=3):
        self.R = R
        self._pts, self._owner = [], {}
        for n in nodes:
            for i in range(v):
                p = md5_int(f"{n}#{i}")
                idx = bisect_left(self._pts, p)
                self._pts.insert(idx, p)
                self._owner[p] = n
        self.healthy = set(nodes)
        self.data = defaultdict(dict)      # node -> {key: value}
        self.hints = defaultdict(deque)    # intended_node -> [(key, val, holder)]

    def preference_list(self, key, extra=10):
        """顺时针取 R 个不同物理节点；extra 用于故障顺延。"""
        h = md5_int(key)
        start = bisect_left(self._pts, h)
        if start == len(self._pts):
            start = 0
        seen, lst = set(), []
        for k in range(len(self._pts)):
            node = self._owner[self._pts[(start + k) % len(self._pts)]]
            if node not in seen:
                seen.add(node)
                lst.append(node)
                if len(lst) >= self.R + extra:
                    break
        return lst

    def write(self, key, value):
        """写 R 个副本；宕机节点顺延并记录 hint。"""
        lst = self.preference_list(key)
        written = 0
        for i, node in enumerate(lst):
            if written >= self.R:
                break
            if node in self.healthy:
                self.data[node][key] = value
                written += 1
            else:
                # 找一个健康节点临时托管，hint 记下本应给谁
                holder = next((n for n in lst if n in self.healthy), None)
                if holder:
                    self.hints[node].append((key, value, holder))
                    self.data[holder][key] = value
                    written += 1
        return written

    def read(self, key):
        for node in self.preference_list(key):
            if node in self.healthy and key in self.data[node]:
                return self.data[node][key]
        return None

    def mark_down(self, node):
        self.healthy.discard(node)

    def mark_up(self, node):
        self.healthy.add(node)
        self._run_handoff(node)

    def _run_handoff(self, node):
        """节点恢复：把 hint 中属于它的数据回传。"""
        q = self.hints.get(node, deque())
        while q:
            key, value, holder = q.popleft()
            self.data[node][key] = value
            self.data[holder].pop(key, None)   # 临时副本撤掉
        print(f"handoff done for {node}")


if __name__ == "__main__":
    ring = FailoverRing(["A", "B", "C", "D", "E"], R=3)
    ring.write("user:1", "v1")
    print("read before fail:", ring.read("user:1"))

    ring.mark_down("B")
    ring.write("user:1", "v2")
    print("read during fail:", ring.read("user:1"))

    ring.mark_up("B")
    print("read after recovery:", ring.read("user:1"))
```

这段代码演示了三段生命周期：正常写入 → $B$ 宕机后写入被顺延并记 hint → $B$ 恢复后 handoff 归还。生产实现还要加：hint 持久化、回传限速、Merkle 树反熵、gossip 成员管理。

## 五、与其他技术对比

| 机制 | 一致性模型 | 故障时行为 | 恢复方式 | 适用 |
| --- | --- | --- | --- | --- |
| Dynamo hint + sloppy quorum | 最终一致 | 写顺延到邻居 | handoff + 反熵 | 高可用 K/V |
| Raft/Paxos 故障转移 | 强一致 | 新 leader 选举 | 日志复制收敛 | 配置、金融账本 |
| 主备同步复制 | 强/半同步 | 切主 | 从库追日志 | 传统数据库 |
| 只读副本 + 人工切换 | 读己之写可能丢 | 降级只读 | DBA 介入 | OLTP 读写分离 |

Raft 强一致但故障时可能不可用（选主期间）；Dynamo 优先可用，允许读到旧值。两者不是优劣，而是 CAP 侧重点不同。

## 六、常见误区

1. **hint 无限积压导致接收方过载**。节点长期宕机时 hint 会越积越多，临时节点磁盘被打满。必须设置阈值：超限则停止 hint，转为反熵重建或标记永久故障重新分片。
2. **把临时托管当成永久归属**。恢复后不归还数据，导致环上数据分布漂移、某节点长期超载，副本策略失效。
3. **忽略故障域相关性**。把三个副本放在同一机架，$(1-p)^3$ 的计算自欺欺人。preference list 必须显式跨机架。
4. **网络分区产生多份「临时 owner」**。分区两侧都顺延写入，合并后冲突。必须用向量时钟/版本向量或 CRDT 解决冲突，否则会丢更新。
5. **handoff 无优先级、无限速**。恢复瞬间大量回传打满网络，影响在线请求。应限速、优先热点 key、并支持后台执行。

## 八、面试题

**1. 节点宕机后 key 如何继续可用？**
preference list 中后续健康节点顺延服务，写入可落到 hint 节点并记录归属，读写都不被单点阻塞。

**2. hinted handoff 有什么风险？**
hint 积压导致接收方过载；网络分区时产生多份临时副本；无持久化时接收方宕机会丢 hint。需要阈值、限速、冲突解决与反熵兜底。

**3. 与 Raft 故障转移的本质区别？**
Raft 用选举保证强一致，故障期间可能短暂不可用；Dynamo 用 sloopy quorum + handoff 优先可用，接受最终一致。

**4. 副本数 $R$ 怎么选？**
$P_{\text{down}} = (1-p)^R$，按 SLA 反推；$R=3$ 是常用点。还要跨故障域，并考虑 $W+R_r>N$ 的读写代价。

## 九、演进与趋势

现代系统在 Dynamo 骨架上持续加固：Cassandra 将 hint 持久化到本地并支持 handoff 限速；ScyllaDB 用更高效的 repair 调度替代纯反熵；CockroachDB / TiKV 把 Raft 与一致性哈希分片结合，用强一致副本组解决冲突，再用 Range 迁移做 rebalance。CRDT 越来越多地替代「hint + 事后合并」，让临时副本天然可交换合并。云原生运维把「故障转移」变成控制器闭环：探活、自动隔离、限速补数据、健康后自动回迁。未来方向包括跨区域故障域感知的 placement、基于 Merkle 的增量 repair、以及在 Serverless 库存算力下的「冷节点低成本托管」。

## 十、小结

一致性哈希给出归属，故障转移机制给出韧性：preference list 把副本铺在环上，sloppy quorum + hinted handoff 让节点宕机时写入不丢、服务不停，反熵与成员传播保证恢复后收敛。它是 AP 系统的经典范式——用最终一致换持续可用，代价则由 hint、冲突解决与修复机制来偿还。
