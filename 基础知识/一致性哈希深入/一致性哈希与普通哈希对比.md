# 一致性哈希与普通哈希对比

> 对应 Karger et al. 1997（Consistent Hashing）与 Kleppmann DDIA 第6章（数据分区）。

## 一、背景与挑战

几乎所有后端系统都会在某个时刻面对同一道选择题：key 到机器的映射该怎么算？最朴素的答案是取模哈希 `idx = hash(key) % N`。它在教科书第一章、在缓存分片、在数据库分库分表、在消息队列分区分配里无处不在。当 $N$ 从设计之初就固定（例如永远 8 台缓存机），取模哈希几乎无可挑剔：一次除法得到结果，映射均匀，客户端与服务端各自计算即可，无需任何中心化元数据。

问题出现在 $N$ 不再固定的那一刻。互联网业务的流量是变化的，集群必须跟着伸缩：大促前扩容、流量回落后缩容、某台机器故障要摘除、硬件换代要把老机型下线。每一次 $N$ 变化，取模哈希的输出都会整体改变——这不是「少部分 key 换机器」，而是「绝大多数 key 换机器」。在 100 台机器的集群上加一台，99% 的缓存同时失效，后端数据库瞬间被击穿；在分库分表场景，意味着几乎全量数据的 rehash 与搬迁，迁移窗口内服务要么停写、要么面对分裂脑。普通哈希的缺陷不在于「算错」，而在于**它对拓扑变化过于敏感**：任何一个节点的进退都会扰动全局映射。

一致性哈希与普通哈希的对比，本质上是「静态拓扑下的最优解」与「动态拓扑下的最优解」之争。面试中这组对比常被追问到公式层面：迁移量差多少、负载是否一样均匀、查询开销谁更大。把这三件事说清楚，才算真正理解了为什么 Dynamo、Cassandra、Redis Cluster 都弃用了朴素取模。

## 二、核心原理

**普通取模哈希**的规则是一行：`idx = h(key) % N`。它的优点是绝对简单、$O(1)$ 查询、在 $h$ 均匀时负载也均匀。它的缺点是**全局耦合**：$N$ 作为除数出现在每一个 key 的计算中，$N$ 一变，所有余数都可能变。数学上看，`hash % N` 与 `hash % (N+1)` 几乎是两套互不相关的映射，唯一的重合是那些恰好在两种模下余数相同的 key。

**一致性哈希**把除数从公式里拿掉：key 与节点都映射到固定的大空间（环），key 归属顺时针最近的节点。节点集合变化时，公式不变，变的只是环上的点集。于是映射的变化被限制在「新节点/消失节点附近的那段弧」里，其余 key 的归属保持不变。这就是「一致性」的真正含义：**哈希函数与空间固定，拓扑局部扰动只引起映射的局部变化**。

两者的差别可以浓缩为三个维度：

1. **迁移量**：取模近乎全量；一致性哈希约 $1/N$。
2. **负载均匀度**：取模在理想哈希下比「无 vnode 的一致性哈希」更均匀；一致性哈希需要虚拟节点才能追平。
3. **元数据与复杂度**：取模无状态；一致性哈希需要维护环（或环的缓存副本），查询略贵。

因此对比不是「谁碾压谁」，而是「场景对了没有」。固定拓扑、小规模、要求极致简单时取模更好；弹性伸缩、大规模、经常加减机器时一致性哈希更好。

## 三、形式化与数学基础

设 key 总数 $K$，节点数从 $N$ 变为 $N+1$。

**取模哈希的迁移期望**。对均匀独立的哈希值 $X = h(k)$，新旧映射一致要求 $X \bmod N = X \bmod (N+1)$。当 $N$ 与 $N+1$ 互质（几乎总是），由中国剩余定理的密度可知，满足条件的 $X$ 占比约为 $\frac{1}{N(N+1)}$。因此需要迁移的 key 数约为
$$
K_{\text{mod}} \approx K \left(1 - \frac{1}{N(N+1)}\right) \approx K.
$$
等价的直观说法：每个 key 在新节点数下的落点独立均匀，保持原位的概率约 $\frac{1}{N+1}$，于是迁移量约 $K \cdot \frac{N}{N+1}$。

**一致性哈希的迁移期望**。新节点接管一段弧，弧长期望占环的 $\frac{1}{N+1}$，故
$$
K_{\text{ch}} \approx \frac{K}{N+1}.
$$
**迁移比**为
$$
\frac{K_{\text{ch}}}{K_{\text{mod}}} \approx \frac{1}{N},
$$
即节点越多，一致性哈希的优势越大。当 $N = 10$ 时约 10 倍差距，$N = 100$ 时约 100 倍。

**负载方差对比**。取模下若 $h$ 理想均匀，节点负载近似二项分布，相对标准差约 $\sqrt{\frac{1}{K/N}} = \sqrt{\frac{N}{K}}$，当 $K \gg N$ 时很小。一致性哈希（无 vnode）的区间长度服从碎棍分布，单节点负载方差约为
$$
\operatorname{Var}(\text{load}) = K^2 \cdot \operatorname{Var}(L_i) \approx \frac{K^2}{N^3},
$$
相对标准差约 $\frac{1}{\sqrt{N}}$，在 $N$ 小时非常难看。引入每个节点 $v$ 个虚拟节点后，相当于把点数变为 $vN$，相对标准差降为约 $\frac{1}{\sqrt{vN}}$，工程上取 $v \ge 100$ 即可压到 10% 以内。

**Jump Consistent Hash** 提供了第三个参照点：只允许「追加节点」时，用
$$
\delta = \frac{1}{N+1}, \quad \text{以概率 } \delta \text{ 迁移}
$$
的递归算法可在 $O(\ln N)$ 时间内得到几乎完美的均匀映射，迁移恰为 $\frac{K}{N+1}$。它牺牲了「删除节点」的对称性，换来比环更均匀的分布。

## 四、代码实现

下面用同一组 key 实测三种映射在扩容时的迁移量，并实现一个简化版一致性哈希环做对照。

```python
import hashlib
import random
from bisect import bisect_left, insort


def md5_int(s) -> int:
    if not isinstance(s, bytes):
        s = str(s).encode()
    return int.from_bytes(hashlib.md5(s).digest()[:8], "big")


def moved_by_mod(keys, n_before, n_after):
    """普通取模哈希：统计节点数变化后有多少 key 换了归属。"""
    moved = 0
    for k in keys:
        if md5_int(k) % n_before != md5_int(k) % n_after:
            moved += 1
    return moved


class SimpleRing:
    """无虚拟节点的一致性哈希环，用于对比迁移量。"""

    def __init__(self, nodes):
        self.pts, self.ring = [], {}
        for n in nodes:
            p = md5_int(n)
            insort(self.pts, p)
            self.ring[p] = n

    def get(self, key):
        h = md5_int(key)
        i = bisect_left(self.pts, h)
        if i == len(self.pts):
            i = 0
        return self.ring[self.pts[i]]


def moved_by_ring(keys, nodes_before, nodes_after):
    r1, r2 = SimpleRing(nodes_before), SimpleRing(nodes_after)
    return sum(1 for k in keys if r1.get(k) != r2.get(k))


if __name__ == "__main__":
    random.seed(42)
    keys = [f"user:{i}" for i in range(10000)]
    N = 20

    nodes_before = [f"node-{i}" for i in range(N)]
    nodes_after = nodes_before + ["node-20"]

    m_mod = moved_by_mod(keys, N, N + 1)
    m_ring = moved_by_ring(keys, nodes_before, nodes_after)

    print(f"普通取模迁移: {m_mod}/{len(keys)}  ({m_mod / len(keys):.2%})")
    print(f"一致性哈希迁移: {m_ring}/{len(keys)}  ({m_ring / len(keys):.2%})")
    print(f"理论: 取模≈{N / (N + 1):.2%}, 一致性≈{1 / (N + 1):.2%}")
```

典型输出会显示：取模迁移约 95%，一致性哈希迁移约 5%，与理论值 $\frac{N}{N+1}$ 和 $\frac{1}{N+1}$ 吻合。若把虚拟节点加进环（每节点 100 个），迁移比例仍约 5%，但负载更均匀。注意实验里用 `md5_int` 保证跨进程稳定，若换成 `hash()`，对比结果在不同运行之间都可能漂移。

## 五、与其他技术对比

| 维度 | 取模哈希 | 一致性哈希 + vnode | 跳跃一致性哈希 | Maglev 查找表 |
| --- | --- | --- | --- | --- |
| 扩容迁移 | $\approx 100\%$ | $\approx 1/N$ | $\approx 1/N$ | 表重建，近似全量重算 |
| 查询开销 | $O(1)$ | $O(\log vN)$ | $O(\ln N)$ | $O(1)$ |
| 负载均匀 | 好 | 好（需足够 vnode） | 极好 | 很好 |
| 支持删节点 | 是 | 是 | 否（只加） | 是（重算表） |
| 元数据 | 无 | 环或成员列表 | 只需 $N$ | 整张查找表 |
| 典型用途 | 固定分库 | Dynamo/Cassandra | Google 缓存 | 负载均衡后端 |

取舍很清晰：**拓扑越稳定，越该选简单方案**。若集群三个月不变，取模的简洁性就是优势；若每天都在扩容，一致性哈希的局部性就是生存能力。跳跃哈希是「只加不删」约束下的最优解；Maglev 用内存换确定性，适合每个 LB 节点独立决策的场景。

## 六、常见误区

1. **在完全固定的集群上强行上一致性哈希**。引入环、虚拟节点、额外查找开销，却换不来任何迁移收益，属于过度设计。正确做法是先判断拓扑变化频率。
2. **混用两种哈希导致路由不一致**。例如客户端用一致性哈希、服务端用 `hash % N` 做校验，或扩容时新老节点计算方式不同，会出现「写进去读不到」的灵异现象。同一套映射必须全局唯一。
3. **只比迁移量，不比负载**。一致性哈希无 vnode 时负载方差远大于取模，若不引入虚拟节点，迁移量的优势可能被「单机被打爆」抵消。
4. **认为一致性哈希「零迁移」**。任何改变归属的扩容都有迁移，一致性哈希只是把迁移从 $O(K)$ 降到 $O(K/N)$，并不是免除。
5. **迁移量公式套错场景**。$\frac{1}{N}$ 是单节点增删的期望；一次替换（一进一出）或一次批量缩容，要按实际接管弧的总和计算，不能简单乘。

## 八、面试题

**1. 什么场景该用取模而不是一致性哈希？**
节点集合长期固定、变更频率极低、要求 $O(1)$ 无元数据查询时。例如单机房固定 8 个分片、变更需走停机窗口的批处理集群。

**2. 请写出两种哈希在 $N \to N+1$ 时的迁移量公式。**
取模约 $K\cdot\frac{N}{N+1}$，一致性哈希约 $\frac{K}{N+1}$，比例约 $N:1$。

**3. 一致性哈希负载一定更均衡吗？**
不一定。无虚拟节点时方差约 $\frac{K^2}{N^3}$，可能比取模差很多；需 vnode 或加权才能均衡。

**4. 如果不允许任何数据迁移，还有办法扩容吗？**
有两类近似做法：只加缓存层、数据层不动（缓存弹性）；或用双写/影子分片做平滑切流，但严格零迁移意味着新节点不接数据，扩容失去意义。

## 九、演进与趋势

现代系统很少「二选一」，而是按约束融合：Redis Cluster 用 16384 个固定槽位（本质是取模到大常数，再由槽位到节点的映射动态调整），把「key 映射」与「拓扑变更」解耦，迁移只发生在槽位搬迁时；Kubernetes 的一致性哈希负载均衡注解、Envoy 的 ring hash LB、gRPC 的一致性哈希选择器，都在客户端缓存环以降低查询开销。算法层，Jump Hash、AnchorHash、Multi-Probe 一致性哈希（减少 vnode 内存）持续优化均匀度与内存；工程层，「加权 vnode + 自动 rebalance + 后台限速迁移」已成为 Cassandra、TiKV 等系统的标配。可以预见，云原生弹性扩缩容越普遍，一致性哈希家族的重要性只会继续上升。

## 十、小结

普通取模哈希在静态拓扑下简洁高效，却在 $N$ 变化时把映射全局打碎；一致性哈希用环形局部性把迁移从 $O(K)$ 降到 $O(K/N)$，代价是负载方差与稍高的查询开销。两者不是替代关系而是场景分工：稳定性换简洁，弹性换局部性，虚拟节点与跳跃哈希则在各自约束下把权衡推向更优。
