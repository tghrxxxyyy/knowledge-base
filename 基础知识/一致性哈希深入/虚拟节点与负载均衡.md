# 虚拟节点与负载均衡

> 对应 DeCandia et al. 2007（Dynamo 论文，virtual nodes 章节）与 Karger et al. 1997（一致性哈希原文）。

## 一、背景与挑战

一致性哈希解决的是「扩缩容时迁移要少」，但把方案直接推上生产后，工程团队会立刻撞上另一堵墙：**负载不均**。当集群只有 5 台机器、每台在环上占一个点时，环被切成 5 段长度随机的弧。哈希均匀只保证「点的位置均匀」，不保证「弧长相等」。极端情况下，某台机器可能碰巧接管了 40% 的环，扛着 40% 的流量与磁盘，而它的邻居只分到 8%。这台「热点节点」会先磁盘打满、再 CPU 打满，最终拖垮整个集群的尾延迟——而集群平均利用率其实并不高。

另一个现实问题是**异构硬件**。机房里的机器从来不是同构的：老机型 8 核 2TB，新机型 32 核 16TB，混部时若每台机器都只占环上一个点、都算一个「完整节点」，小机器会被数据压垮，大机器则大量算力闲置。我们需要一种机制，既能把弧长的随机波动抹平，又能表达「这台机器该多扛一点」。

虚拟节点（Virtual Node，简称 vnode）就是为这两个问题而生的。Dynamo 论文明确用它来「让每台物理节点以多个点出现在环上，从而获得更均匀的负载分布，并以 vnode 数量表达机器容量差异」。在现代 Cassandra、Riak、Ketama、Redis Cluster 的实现里，vnode 都是标配。面试中「虚拟节点的作用」是高频题，期望答案不是一句「负载均衡」，而是「用 $v$ 把区间方差压下来 + 用 $v_i$ 表达权重」。

## 二、核心原理

虚拟节点的做法是：**每台物理节点不再对应环上一个点，而是对应 $v$ 个（通常 100～200）随机分布的点**。这 $v$ 个点各自作为「虚拟节点」出现在环上，被顺时针规则分配一段弧；查询时先定位到虚拟节点，再把结果映射回它所属的物理节点。

这里的关键不变量是：

1. **物理节点的负载 = 它名下所有 vnode 区间长度之和**。于是物理节点的负载从「一段随机弧长」变成「$v$ 段随机弧长之和」，方差按 $1/v$ 缩小。
2. **key 的路由路径是两跳**：`key → 环上位置 → 最近的 vnode → 物理节点`。对外接口不变，内部多一层间接。
3. **迁移仍然局部**：物理节点加入时新增 $v$ 个点，它接管的是这 $v$ 个点各自前方的一小段弧；离开时同理。迁移总量期望仍是 $\frac{K}{N}$，只是切成 $v$ 小份，对单台接收方更平滑，避免「一次涌入全部搬迁数据」。

为什么 $v$ 个随机点能均衡？直觉是大数定律：$v$ 段独立（近似）弧长求和，相对波动被 $\sqrt{v}$ 稀释。$v=1$ 时相对标准差约 $1/\sqrt{N}$；$v=100$、$N=10$ 时相当于 1000 个点在环上，相对标准差降到约 3%，进入工程可接受区间。

虚拟节点还带来两个次生好处：**故障隔离更平滑**（一台机器宕机，它散落的 $v$ 段弧被各自邻居接管，而不是某一台机器被撑爆）；**异构权重有了自然表达**（权重大的机器分配更多 vnode，见下一篇）。代价是环上元数据变大、二分查找的 $\log(vN)$ 略增，但 $vN$ 在几千量级时完全可以忽略。

## 三、形式化与数学基础

设物理节点数 $N$，每节点虚拟节点数 $v$，环上总点数 $M = vN$。把环归一化为 $[0,1)$，$M$ 个均匀点把它切成 $M$ 段弧。

**单段弧长分布**。第 $i$ 段弧长 $L_i$ 的期望与方差为
$$
\mathbb{E}[L_i] = \frac{1}{M}, \qquad \operatorname{Var}(L_i) = \frac{M-1}{M^2(M+1)} \approx \frac{1}{M^3}.
$$

**物理节点负载**。节点 $j$ 的负载 $B_j = \sum_{i \in S_j} L_i$，其中 $|S_j| = v$。若近似认为各段弧长独立，
$$
\mathbb{E}[B_j] = \frac{v}{M} = \frac{1}{N}, \qquad \operatorname{Var}(B_j) \approx v \cdot \frac{1}{M^3} = \frac{1}{v^2 N^3}.
$$
相对标准差（变异系数）为
$$
\frac{\sqrt{\operatorname{Var}(B_j)}}{\mathbb{E}[B_j]} \approx \frac{1/\!(vN)^{3/2}}{1/N} = \frac{1}{\sqrt{vN}} = \frac{1}{\sqrt{M}}.
$$
即**相对波动只与环上总点数 $M=vN$ 有关**，约为 $1/\sqrt{M}$。工程经验值：

| $v$（$N=10$） | $M$ | 相对标准差 |
| --- | --- | --- |
| 1 | 10 | ~32% |
| 10 | 100 | ~10% |
| 100 | 1000 | ~3.2% |
| 200 | 2000 | ~2.2% |

Dynamo 的前身实现常用每节点约 100～200 个 vnode；Ketama（memcached 客户端）默认每物理节点约 160 个虚拟点。要让「最忙节点负载不超过平均的 1.1 倍」这类目标，通常需要 $M$ 达到数千。

**迁移量不变**。节点加入新增 $v$ 个点，接管弧长期望 $\frac{v}{M+ v} = \frac{1}{N+1}$，仍为 $O(K/N)$。但迁移被切成 $v$ 小份，同时被 $v$ 个邻居分摊，瞬时网络压力更均匀。

**查询开销**。有序数组二分 $O(\log M) = O(\log N + \log v)$；客户端缓存全环时可降为 $O(1)$ 或 $O(\log v)$（对每个 key 只查一次）。

## 四、代码实现

下面实现带虚拟节点的环，并用 20000 个 key 实测负载分布，对比 $v=1$ 与 $v=100$。

```python
import hashlib
from bisect import bisect_left, insort
from collections import Counter


def md5_int(data) -> int:
    if not isinstance(data, bytes):
        data = str(data).encode()
    return int.from_bytes(hashlib.md5(data).digest()[:8], "big")


class VNodeRing:
    def __init__(self, v=100):
        self.v = v
        self._pts = []          # 有序虚拟点
        self._owner = {}        # 虚拟点 -> 物理节点

    def add(self, node_id, vnodes=None):
        v = vnodes if vnodes is not None else self.v
        for i in range(v):
            p = md5_int(f"{node_id}#{i}")
            while p in self._owner:          # 极小概率碰撞：换扰动串重试
                p = md5_int(f"{node_id}#{i}#retry{p}")
            insort(self._pts, p)
            self._owner[p] = node_id

    def remove(self, node_id):
        victims = [p for p, n in self._owner.items() if n == node_id]
        for p in victims:
            del self._owner[p]
            idx = bisect_left(self._pts, p)
            if idx < len(self._pts) and self._pts[idx] == p:
                self._pts.pop(idx)

    def get(self, key):
        h = md5_int(key)
        i = bisect_left(self._pts, h)
        if i == len(self._pts):
            i = 0
        return self._owner[self._pts[i]]


def load_stats(ring, keys):
    cnt = Counter(ring.get(k) for k in keys)
    n = len(cnt)
    avg = len(keys) / n
    var = sum((c - avg) ** 2 for c in cnt.values()) / n
    std = var ** 0.5
    return cnt, avg, std / avg          # 变异系数


if __name__ == "__main__":
    keys = [f"key:{i}" for i in range(20000)]
    nodes = [f"node-{i}" for i in range(10)]

    for v in (1, 20, 100):
        ring = VNodeRing(v=v)
        for n in nodes:
            ring.add(n)
        cnt, avg, cv = load_stats(ring, keys)
        mx, mn = max(cnt.values()), min(cnt.values())
        print(f"v={v:3d}  avg={avg:.0f}  min={mn}  max={mx}  CV={cv:.2%}")
```

预期输出：$v=1$ 时最忙节点可能是平均的 1.5～2 倍；$v=100$ 时最忙/最闲被压到 1.1 倍以内，CV 降到约 2%～4%。这直观验证了 $\mathrm{CV} \approx 1/\sqrt{vN}$ 的结论。

## 五、与其他技术对比

| 方案 | 负载均匀度 | 迁移平滑度 | 表达异构权重 | 元数据开销 |
| --- | --- | --- | --- | --- |
| 单点一致性哈希 | 差（CV~1/√N） | 一次大迁移 | 不支持 | 最小 |
| 虚拟节点 v=100+ | 好（CV~1/√vN） | 分摊到多邻居 | 用 vnode 数 | 中等 |
| 加权区间（显式） | 精确 | 可控 | 精确 | 需要配额计算 |
| 取模哈希 | 好 | 全量迁移 | 难 | 无 |
| 一致性随机树（论文方案） | 好 | 局部 | 复杂 | 树结构 |

虚拟节点的定位是「用最简单的随机化 + 复制，同时换回均衡、平滑迁移与权重表达」，因此在 Dynamo 生态中胜出。显式区间划分更精确但实现复杂；取模不支持弹性。

## 六、常见误区

1. **$v$ 设得太小**。$v=10$、$N=10$ 时 CV 仍有 10%，生产环境不够；至少应保证 $vN \ge 500$，热点敏感场景取 $v \ge 100$。
2. **$v$ 设得太大**。$v=10000$ 时元数据与查找开销上升，且增删节点会产生大量细碎迁移日志，收益边际递减。$v=100\sim200$ 通常是甜点。
3. **虚拟点生成方式不随机**。用 `hash(node + monotonic_id)` 且哈希有偏时，vnode 会聚在环的一段，形成更大热点。应使用稳定且分布良好的 Murmur/xxHash/MD5。
4. **把 vnode 数当权重却忘了重新平衡**。机器扩容后继续用旧 vnode 数，新机器「名义上加了」实际没接多少负载。
5. **误以为 vnode 能代替副本**。vnode 只是分区手段；数据冗余需要独立的副本链/preference list，一台物理机上的多个 vnode 不是多个故障域。

## 八、面试题

**1. 虚拟节点数 $v$ 如何影响负载均衡？**
相对标准差约 $1/\sqrt{vN}$，$v$ 增大均衡度提升但元数据与迁移粒度变细；通常取每物理节点 100～200。

**2. 为什么 vnode 能让迁移更「平滑」？**
迁移量期望仍是 $K/N$，但被拆成 $v$ 段，分别由 $v$ 个邻居供给，单机网络与 IO 峰值降低。

**3. 异构机器如何用 vnode 表达权重？**
按容量比例分配 vnode 数：32TB 机器给 4 倍于 8TB 机器的 vnode，其期望负载占比即为权重占比。

**4. vnode 与副本数是一回事吗？**
不是。vnode 解决分区均衡；副本数解决可用性与持久性。同一物理节点的多个 vnode 应视为一个故障域。

## 九、演进与趋势

在工程侧，Cassandra 默认每节点 256 个 vnode（可配），并提供 `nodetool status` 观察真实负载偏斜；Redis Cluster 用 16384 个槽位（等价于固定高分辨率的 vnode）做槽到节点的再分配；TiKV 与 CockroachDB 把 Range 切分与一致性哈希结合，用自动分裂代替手工 vnode。算法侧，**Multi-Probe 一致性哈希**（Google 2015）用多个探测点减少所需 vnode 内存；**AnchorHash**、**DX Hash** 等新结构追求「少 vnode、好均衡」。云原生场景还出现「按 CPU/内存实时反馈动态调整 vnode 权重」的控制器，把静态配置变成闭环调优。虚拟节点的思想也被借用到 P2P 网络、CDN 边缘调度与游戏房间分配中。

## 十、小结

虚拟节点用「一机多点」同时攻下负载方差、迁移平滑度与异构权重三个问题：相对波动被压到约 $1/\sqrt{vN}$，迁移仍为 $O(K/N)$ 但被多邻居分摊，vnode 数即权重旋钮。它是一致性哈希从「正确」走向「可用」的关键一跃，也是几乎所有现代分布式分区系统的默认组件。
