# 一致性哈希原理

> 对应 Karger et al. 1997（Consistent Hashing and Random Trees, MIT）与 Kleppmann DDIA 第6章（分区与副本）。

## 一、背景与挑战

在分布式系统中，数据分片几乎是绕不开的问题：客户端给出 key，系统必须快速确定这个 key 由哪台机器负责。最直观的做法是取模哈希 `hash(key) % N`。当节点集合固定、永不变化时，这个方案几乎完美——计算常数时间、映射均匀、无需额外元数据。然而真实的存储集群几乎从不静止：机器会因扩容加入、因故障或退役离开、因运维从机架 A 迁到机架 B。每次 $N$ 变化，取模映射就整体崩塌，绝大多数 key 的归属被重新洗牌，引发全量数据迁移。在一个 PB 级集群里，哪怕只是加一台机器，也可能意味着数十 TB 的无谓拷贝，网络被打满、请求延迟飙升、在线服务抖动。

更深层的矛盾在于：我们需要的其实只是「局部稳定」——加一台机器，最好只迁移 $\frac{1}{N}$ 的数据；剩下 $\frac{N-1}{N}$ 的数据纹丝不动。Karger 等人在 1997 年提出的一致性哈希（Consistent Hashing）正是为这一目标设计的。它把节点和 key 映射到同一个环形空间上，key 顺时针归属到最近的节点，于是节点增删只影响环上相邻的区间。注意「一致性」在这里不是指数据一致性（如 CAP 中的 C），而是指「哈希映射随拓扑变化保持稳定」。理解这一点是理解全文的前提。

在工程与面试语境中，一致性哈希是分布式系统章节的必考项：Dynamo、Cassandra、Riak、Redis Cluster、Ketama、负载均衡器、CDN 调度、分布式缓存客户端都建立在它之上。面试官通常希望你能说清环模型、虚拟节点、以及「为什么迁移量是 $\frac{1}{N}$ 而不是 $\frac{N-1}{N}$」这三个层次，而不是背诵「一致性哈希可以减少数据迁移」这句空话。

## 二、核心原理

一致性哈希的核心构件是**哈希环**。取一个足够大的哈希空间，例如 $[0, 2^{32})$ 或 $[0, 2^{64})$，把它首尾相接看成一个圆环。所有节点和所有 key 都通过同一个哈希函数（通常选均匀、低碰撞的 MurmurHash、xxHash 或 SHA-1 截断）映射到环上的某个点。

路由规则非常简单：给定 key $k$，计算 $h(k)$ 在环上的位置，**沿顺时针方向行走，遇到的第一个节点就是 $k$ 的归属节点**。若顺时针绕了一圈都找不到节点，则视为系统空，拒绝服务或触发扩容。这条「顺时针后继」规则是整个算法的灵魂——它保证了每个节点只负责环上的一段连续弧，而这段弧的起点是自己、终点是顺时针邻居。

不变量（Invariant）是理解正确性的关键：

1. **区间不变量**：任意时刻，每个节点拥有环上一段半开半闭区间 $(\text{pred}(n), n]$，其中 $\text{pred}(n)$ 是逆时针前驱。key 落在该区间内当且仅当它属于 $n$。区间之间互不重叠、并集覆盖整环。
2. **局部性不变量**：当节点 $n$ 加入环时，它只会「接管」前驱 $\text{pred}(n)$ 原本区间的一部分——即 $(\text{pred}(n), n]$ 这段；其他节点的区间端点不变，因而它们持有的 key 一个都不用迁移。
3. **离开时对称**：节点 $n$ 离开时，它的区间被前驱完整接管，其他区间同样不动。

边界条件必须显式处理：环为空时 `get` 不能无限循环或返回 None 让调用方崩溃；只有一个节点时它负责全环；哈希碰撞（两个节点映射到同一点）需要确定性的 tie-break（例如比较节点 ID）或链式存储。实现上通常用有序结构（平衡树、排序数组 + 二分）保存环上所有点，查询是 $O(\log N)$。

为什么「顺时针第一个」就对了？因为它是唯一一种把「全局环」划分成「连续区间」且增删节点只撕裂一段区间的方式。若改为「顺时针最近的两个节点投票」或「按距离最近」，区间不再连续，增删会同时扰动多个区间的边界，局部性不变量立刻失效。环形 + 后继，这两点共同构成了正确性。

## 三、形式化与数学基础

设环长 $M = 2^{32}$（实际只关心相对顺序，$M$ 的具体值可取任意充分大的数），节点数 $N$，key 总数 $K$。

**取模哈希的迁移量**。当节点数由 $N$ 变为 $N+1$ 时，映射 $h(k) \bmod N$ 变为 $h(k) \bmod (N+1)$。对于均匀随机的 $h(k)$，一个 key 保持不变的充要条件是它在两个模下落在同一编号。可以证明（或用随机变量直觉）大约只有 $\frac{1}{N(N+1)}$ 量级的 key 映射不变，换言之约
$$
K \cdot \frac{N}{N+1}
$$
个 key 需要迁移。极端地，$N \to N+1$ 时几乎所有数据搬家。

**一致性哈希的迁移量**。节点 $n$ 加入时，接管的是一段弧。若哈希均匀，各节点区间长度是同分布的随机变量，期望相等，于是新节点接管的 key 数期望为
$$
\mathbb{E}[\Delta] = \frac{K}{N+1} \approx \frac{K}{N}.
$$
更精确地，加入第 $N+1$ 个节点时迁移比例约为 $\frac{1}{N+1}$，离开时约为 $\frac{1}{N}$。相比取模的 $1 - \frac{1}{N+1}$，差距约 $N$ 倍。当 $N=100$、$K=10^9$ 时，取模要动约 $9.9\times 10^8$ 个 key，一致性哈希只动约 $10^7$ 个。

**负载方差的初步分析**。把 $N$ 个节点看成把环切成 $N$ 段，等价于 $N-1$ 个均匀切点把 $[0,1]$ 圆周分成 $N$ 段。这是经典的「碎棍问题」（broken stick）：第 $i$ 段长度 $L_i$ 满足 $\mathbb{E}[L_i] = \frac{1}{N}$，而
$$
\operatorname{Var}(L_i) = \frac{N-1}{N^2(N+1)} \approx \frac{1}{N^3}.
$$
单节点负载的标准差约为 $\frac{1}{\sqrt{N}}$ 量级；换算到 key 数，节点负载的标准差约 $\frac{K}{\sqrt{N}}$，相对波动高达 $1/\sqrt{N}$。当 $N$ 较小时极不均衡——这正是后续虚拟节点要解决的问题。这里先记住：一致性哈希解决的是**迁移局部性**，负载均衡要靠额外机制。

## 四、代码实现

下面是无虚拟节点的一致性哈希环完整实现。使用 `bisect` 在排序数组上做顺时针后继查询，支持增删节点与 key 查找。

```python
import bisect
import hashlib


def _hash(data) -> int:
    """稳定哈希：用 md5 取前 8 字节，避免 Python 内置 hash 的随机性。"""
    if not isinstance(data, bytes):
        data = str(data).encode("utf-8")
    digest = hashlib.md5(data).digest()
    return int.from_bytes(digest[:8], "big")


class ConsistentHashRing:
    def __init__(self):
        self._points = []       # 有序的环上点
        self._ring = {}         # point -> node_id

    def add(self, node_id) -> None:
        p = _hash(node_id)
        if p in self._ring:
            raise ValueError(f"hash collision on node {node_id}")
        bisect.insort(self._points, p)
        self._ring[p] = node_id

    def remove(self, node_id) -> None:
        p = _hash(node_id)
        self._ring.pop(p, None)
        idx = bisect.bisect_left(self._points, p)
        if idx < len(self._points) and self._points[idx] == p:
            self._points.pop(idx)

    def get(self, key):
        if not self._points:
            raise RuntimeError("empty ring")
        h = _hash(key)
        idx = bisect.bisect_left(self._points, h)   # 顺时针第一个 >= h 的点
        if idx == len(self._points):
            idx = 0                                  # 绕回环起点
        return self._ring[self._points[idx]]

    def nodes(self):
        return list(self._ring.values())


if __name__ == "__main__":
    ring = ConsistentHashRing()
    for n in ["nodeA", "nodeB", "nodeC"]:
        ring.add(n)

    keys = [f"key{i}" for i in range(20)]
    before = {k: ring.get(k) for k in keys}

    ring.add("nodeD")                              # 扩容一台
    after = {k: ring.get(k) for k in keys}

    moved = sum(1 for k in keys if before[k] != after[k])
    print(f"moved {moved}/{len(keys)} keys after adding nodeD")
    for k in keys:
        print(k, before[k], "->", after[k])
```

运行这段代码可以看到：加入 `nodeD` 后只有少数 key 换了归属，其余保持不变。若换成 `hash(key) % 4` 与 `% 5` 对比，迁移比例会高得多。代码中有三个值得留意的细节：其一，用 `md5` 而不是 `hash()`，因为 CPython 的字符串哈希带 `PYTHONHASHSEED` 随机化，跨进程不稳定；其二，`bisect_left` 返回的下标越界时绕回 0，对应「顺时针走完一圈」；其三，删除节点后必须同步维护 `_points` 与 `_ring` 两个结构，否则环会留下孤儿点。

## 五、与其他技术对比

| 方案 | 扩缩容迁移量 | 查询复杂度 | 负载均衡 | 典型场景 |
| --- | --- | --- | --- | --- |
| 取模哈希 | $\Theta(K)$ | $O(1)$ | 均匀 | 固定节点数、无扩容 |
| 一致性哈希（无 vnode） | $\Theta(K/N)$ | $O(\log N)$ | 方差较大 | 小规模、演示 |
| 一致性哈希 + 虚拟节点 | $\Theta(K/N)$ | $O(\log vN)$ | 良好 | Dynamo / Cassandra |
| 跳跃一致性哈希 Jump Hash | $\Theta(K/N)$ | $O(\ln N)$ | 极均匀 | 只加不删的缓存 |
| Maglev | $O(K)$（重建表） | $O(1)$ | 很均匀 | 负载均衡器后端 |
| 范围分区 / 分配表 | 手工迁移 | $O(1)$ 或 $O(\log)$ | 可控 | Bigtable / HBase |

取模哈希胜在简单与常数时间；一致性哈希胜在迁移局部性；Jump Hash 把「只允许加机器」的约束用到极致，得到近乎完美的均匀度；Maglev 用一张查找表换 $O(1)$ 查询与良好均匀度，但节点变更需重算整表。范围分区把控制权交给人工或自动 split，适合有序扫描，而不适合纯 K/V 定位。选型的核心问题是：**节点变化频率、数据量、是否要求有序、能否接受中心化的元数据服务**。

## 六、常见误区

1. **把「一致性哈希」的「一致性」当成 CAP 的一致性**。这会导致讨论走向强一致/最终一致的岔路。这里的 consistency 指映射的稳定性（consistent naming），与副本一致性正交。
2. **认为一致性哈希天然负载均衡**。不加虚拟节点时，$N=3$ 就可能出现某节点管一半环的情况。负载均衡来自 vnode 或加权，不来自环本身。
3. **用语言内置 `hash()` 做环哈希**。Python/Java 的 `hashCode`、Go 的 `map` 迭代顺序在进程间不一致，重启后路由全乱，数据「找不到」。必须用稳定的 Murmur/xxHash/SHA 系列。
4. **查询实现用线性扫描**。`for p in sorted_points: if p >= h: return` 虽正确但 $O(N)$，环上点上千时延迟不可接受。应当用二分或平衡树。
5. **忽略哈希碰撞与同点节点**。两个节点落到同一 hash 值时，后加入的会覆盖先加入的，造成节点「失踪」、负载悄悄偏斜。需要显式检测碰撞并加扰动（例如追加序号再哈希）。

## 八、面试题

**1. 一致性哈希相比取模哈希，迁移量减少了多少？请给出量级。**
节点由 $N$ 增至 $N+1$ 时，取模约 $1-\frac{1}{N+1}$ 的 key 迁移，一致性哈希约 $\frac{1}{N+1}$ 迁移，差距约 $N$ 倍；两者都可写成 $O(K/N)$ 与 $O(K)$ 的对比。

**2. 为什么 key 要顺时针找第一个节点，而不是找距离最近的节点？**
顺时针后继把环切成连续区间，保证增删节点只撕裂一段区间；「最近」会切碎区间，一次变更影响多个节点，破坏局部性不变量。

**3. 只有一致性哈希就够了吗？还需要什么？**
不够。还需要虚拟节点（或加权 vnode）压负载方差，需要副本策略（preference list）保证可用性，需要稳定哈希函数与元数据同步机制。

**4. 查询复杂度是多少？如何优化到 $O(1)$？**
有序数组二分是 $O(\log N)$；可用一致性哈希预先计算的查找表（Maglev）或在客户端缓存整环副本达到均摊 $O(1)$。

## 九、演进与趋势

一致性哈希诞生后沿着三条路线演进。其一是**均匀度**：虚拟节点（Ketama、Dynamo）把方差压到可接受范围；跳跃一致性哈希（Lamping & Veach, 2014）在「只加不删」场景用 $O(\ln N)$ 计算得到接近完美的均匀分布，被 Google 的分布式缓存采用。其二是**确定性查找表**：Google Maglev（2016）为每个负载均衡器生成一致性查找表，节点变更时表局部重算，兼顾 $O(1)$ 查询与低扰动，广泛用于现代 LB。其三是**工程落地**：Cassandra 的 `NetworkTopologyStrategy` + vnode、Redis Cluster 的 16384 槽位（本质是固定粒度哈希环）、Ketama 的 160 个 vnode/节点、Kubernetes 对有状态负载的分片调度，都可以看作环模型的变体。云原生时代，服务网格与多租户缓存让「虚拟节点数」「权重再平衡」成为可动态调参的运维旋钮，一致性哈希从论文技巧变成了基础设施的默认组件。

## 十、小结

一致性哈希用一条环、一条顺时针后继规则，把「扩缩容导致全量迁移」的世界改写为「只动局部」的世界：区间不变量保证正确性，局部性不变量把迁移量从 $O(K)$ 压到 $O(K/N)$。它本身不解决负载方差与可用性，需要虚拟节点、加权与副本链配合，但正是这一干净的核心，使它成为 Dynamo 以降几乎所有动态分区系统的理论基石。
