# 文件描述符表与打开文件表

> 对应 Kerrisk《The Linux Programming Interface》第 5 章文件 I/O 与 Bryant & O'Hallaron《CSAPP》第 10 章系统级 I/O。

## 一、背景与挑战
进程调用 `open` 返回的小整数"文件描述符"是什么？为什么父子进程、dup 之后的描述符共享或独立？必须厘清三层级结构：进程级描述符表、系统级打开文件表、文件系统 inode。

## 二、核心原理
每个进程有独立的 `files_struct`，其 `fd` 数组下标即 fd，指向内核"打开文件表"(`struct file`) 的一项。`file` 记录当前偏移、打开模式、引用计数 `f_count`，并指向底层 `inode`。多个 fd 可指向同一 `file`（dup、fork 继承），也可指向同一 inode 的不同 `file`（各自独立偏移）。

## 三、形式化与数学基础
设进程 $P$ 的描述符表 $D_P$，打开文件表项 $O$，inode $I$。关系为：
$$D_P[fd] = O,\quad O.offset \in \mathbb{N},\quad O.inode = I$$
fork 时 $D_{child}[fd] = O$ 且 $O.f\_count \mathrel{+}= 1$；dup 同理；两个独立 `open` 产生两个 $O$ 但可能同一 $I$。

## 四、代码实现
```c
// fork/exec 后父子共享同一打开文件表项，偏移同步
int fd = open("log", O_WRONLY|O_APPEND);
pid_t pid = fork();
write(fd, "x", 1);   // 父子任一写入都推进同一 O.offset
// 欲独立偏移须各自 open
int fd2 = open("log", O_WRONLY|O_APPEND);
```

## 五、与其他技术对比
相较 Windows HANDLE，fd 是整数索引更轻量；相较 stdio 的 `FILE*`，fd 是内核态句柄，`FILE*` 还带用户态缓冲区（`fopen` 默认全缓冲）。

## 六、常见误区
误以为 dup 后两个 fd 偏移独立：其实共享 `file`。误以为 `O_APPEND` 用 `lseek` 可绕过：内核在写时原子定位到末尾。误以为关闭 fd 即删除文件：只减 `f_count`，归零才释放 `file`。

## 七、与开源书/权威来源对应
CSAPP 10.5 用 shell 重定向讲 fd 0/1/2 与 dup2；Kerrisk 第 5 章详述三表结构与 `fcntl`。

## 八、面试题
问：fork 后父子同时写同一 fd，会不会交错了？答：共享偏移且 `write` 在小数据量下原子，输出交错但各自完整；大块 `write` 可能撕裂。问：重定向如何实现？

## 九、演进与趋势
io_uring 引入内核态环形提交队列，绕过逐次 fd 系统调用；close_range 批量关闭 fd 提升安全清理效率。

## 十、小结
理解"进程描述符表→打开文件表→inode"三级结构，才能正确推理偏移共享、继承与 dup 语义。
