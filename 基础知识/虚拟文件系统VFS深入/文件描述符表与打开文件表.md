# 文件描述符表与打开文件表

> 对应 Kerrisk《The Linux Programming Interface》第 5 章「深入探究文件 I/O」，以及 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 10 章「系统级 I/O」。

## 一、背景与挑战
`open` 返回一个非负小整数，程序称其为「文件描述符」（fd）。真正难回答的是语义问题：为什么 `fork` 之后父子进程写同一个 fd 会共享偏移？为什么 `dup` 出的两个 fd 也共享偏移，但两次独立 `open` 却不共享？为什么 `fcntl` 设置 `O_NONBLOCK` 会影响所有副本，而 `FD_CLOEXEC` 只影响一个？
回答这些问题必须区分三个层次：**进程级描述符表**、**系统级打开文件表**、**文件系统的 inode**。混淆这三层是 Unix I/O 相关 bug 的主要来源，例如误以为重定向只需 `dup2` 而忽略 `O_APPEND` 的原子性，或误以为 `close` 会立刻释放磁盘空间。

## 二、核心原理
**第一层：进程级描述符表。** 每个进程有 `struct files_struct`，其中 `fdtable` 包含一个 `struct file *` 指针数组，fd 就是这个数组的下标。`fdtable` 支持动态扩容（`expand_fdtable`），上限由 `RLIMIT_NOFILE`（`ulimit -n`）约束。`FD_CLOEXEC` 标志位存在这一层的 `close_on_exec` 位图中，因此它属于「描述符」，不属于「打开的文件」。`clone(CLONE_FILES)` 创建的线程共享同一 `files_struct`。
**第二层：打开文件表（`struct file`，即 open file description）。** 它记录 `f_count`（原子引用计数）、`f_pos`（当前偏移，决定「共享与否」）、`f_flags`（状态标志如 `O_NONBLOCK`/`O_APPEND`，被所有副本共享）、`f_mode`（读写模式，打开后不可改）、`f_op`（`file_operations` 函数表，VFS 多态分派点）、`f_path`（`struct path`，含 `vfsmount` 与 dentry）、`f_inode`。
**第三层：inode。** 描述文件本体（权限、大小、时间戳、数据块位置）。多个 `struct file` 可指向同一 inode（多次 `open`、硬链接），各自维护独立偏移但共享文件数据与元数据。
由此得到三条推论：一是 `fork` 复制 `fdtable` 的指针并把 `f_count` 加一，父子共享 `f_pos` 与 `f_flags`；二是 `dup`/`dup2`/`dup3` 只复制指针并加计数，因此共享偏移与标志，而 `FD_CLOEXEC` 需单独设置；三是两次独立 `open` 得到两个不同的 `struct file`，偏移互不影响。
`O_APPEND` 需要特别注意：内核在 `write` 路径中强制把写入位置设为文件末尾，因此它**不能被 `lseek` 绕过**，并保证了追加写入的原子性——这正是多进程写同一日志文件应使用 `O_APPEND` 而非「`lseek` 到末尾再写」的原因。
`close` 只把 `f_count` 减一，只有归零时才调用 `f_op->flush` 并释放 `struct file`。`unlink` 减少的是 `i_nlink`；若仍有 `struct file` 引用该 inode，数据块不回收，`df` 会显示空间未释放。

## 三、形式化与数学基础
设进程 $P$ 的描述符表为 $D_P$，打开文件表项为 $O$，inode 为 $I$：

$$ D_P[fd] = O,\qquad O.f\_pos \in \mathbb{Z}_{\ge 0},\qquad O.f\_inode = I $$

`fork` 与 `dup` 统一为「共享同一 $O$ 并递增引用计数」：

$$ fork: D_{P'}[fd] = D_P[fd] = O,\qquad O.f\_count \leftarrow O.f\_count + 1 $$
$$ dup(fd_1, fd_2): D[fd_2] \leftarrow D[fd_1],\qquad D[fd_1].f\_count \leftarrow +1 $$

两次独立打开则为一对多：

$$ open(p) = O_1,\; open(p) = O_2 \Rightarrow O_1 \ne O_2,\; O_1.f\_inode = O_2.f\_inode = I $$

于是「是否共享偏移」的判据极为简洁：

$$ \text{共享偏移}(a, b) \iff D[a] = D[b] $$

`close` 的引用计数语义为 $O.f\_count \leftarrow O.f\_count - 1$，当且仅当 $O.f\_count = 0$ 时执行 $flush(O) \land free(O)$。

## 四、代码实现
```c
#include <fcntl.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC | O_APPEND, 0644);
    if (fd < 0) return 1;

    if (fork() == 0) {
        write(fd, "child\n", 6);      /* 与父进程共享 f_pos 与 O_APPEND */
        _exit(0);
    }
    write(fd, "parent\n", 7);
    wait(NULL);
    close(fd);                        /* 仅递减 f_count */
    return 0;
}
```

最容易混淆的是「文件状态标志」与「描述符标志」的区别：

```c
int fd = open("f", O_RDWR);
int d = dup(fd);                      /* 与 fd 共享同一 struct file */

/* 文件状态标志：影响所有副本，fd 与 d 同时变为非阻塞 */
fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);

/* 描述符标志：只影响单个 fd */
fcntl(d, F_SETFD, fcntl(d, F_GETFD) | FD_CLOEXEC);

/* 原子打开并设置 O_CLOEXEC/O_NONBLOCK，避免多线程下的泄漏窗口 */
int fd2 = open("g", O_RDWR | O_CLOEXEC | O_NONBLOCK);

/* 重定向只操作描述符表这一层：dup2 会先关闭 oldfd 再复制 */
int out = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(out, STDOUT_FILENO);
close(out);                           /* 描述符 1 仍持有该引用 */
```

批量关闭可用 `close_range(first, last, flags)`，比循环 `close` 更快，且 `CLOSE_RANGE_CLOEXEC` 支持「先全部标记再关闭」的安全清理模式。

## 五、与其他技术对比
| 维度 | Linux fd | Windows HANDLE | C 的 `FILE *` | `struct file` | inode |
| --- | --- | --- | --- | --- | --- |
| 本质 | `fdtable` 数组下标 | 内核对象句柄（可继承） | 用户态结构体指针 | 内核打开文件项 | 文件系统元数据 |
| 偏移存放 | 不适用（查表） | 内核对象内 | `FILE` 内的偏移与缓冲 | `f_pos` | 无 |
| 用户态缓冲 | 无 | 无 | 有（默认全缓冲） | 无 | 无 |
| 复制语义 | `dup` 共享偏移与标志 | `DuplicateHandle` 共享 | 无等价物 | 引用计数 +1 | 由 `i_count` 管理 |
| 与 `epoll`/`io_uring` | 原生支持 | IOCP（模型不同） | 需 `fileno` 转换 | 不适用 | 不适用 |

fd 相对 `FILE *` 的关键优势是「无用户态缓冲」，因此可安全地与 `epoll`、`sendfile`、`splice`、`io_uring` 组合。`FILE *` 的缓冲区会让 `fork` 后的重复输出（父子各自 flush 同一缓冲）成为经典坑点，这正是「`fork` 前 `fflush`」这条纪律的来源。

## 六、常见误区
- **以为 `dup` 后两个 fd 偏移独立**：它们指向同一 `struct file`，共享 `f_pos` 与 `f_flags`。
- **以为 `O_APPEND` 可以用 `lseek` 绕过**：内核在 `write` 时强制定位到末尾，正确定位与原子性由内核保证。
- **以为 `close` 会删除文件或释放空间**：`close` 只递减引用计数；删除由 `unlink` 完成，空间在最后一个引用消失后回收。
- **以为 `fd` 就是文件编号**：`fd` 只是进程内数组下标，同一文件在不同进程中可以是不同 `fd`，同一 `fd` 在不同时刻可指向不同 `struct file`。
- **在多线程程序中用 `fcntl` 逐个设置 `CLOEXEC`**：`open` 与 `fcntl` 之间存在窗口，另一线程可能恰好 `fork`+`exec` 泄漏 fd；应使用 `O_CLOEXEC` 原子打开。

## 八、面试题
1. **`fork` 后父子同时写同一 fd，输出会交错吗？**
   要点：共享偏移，写入位置统一推进；小块 `write`（小于 `PIPE_BUF`）是原子的，顺序取决于调度但不撕裂；大块写入可能交错。
2. **shell 的 `>` 重定向是怎么实现的？**
   要点：父进程 `open` 得到 fd，`dup2(fd, 1)` 让描述符 1 指向该 `struct file`，再 `close` 原 fd，然后 `exec`；子进程只继承描述符表。
3. **为什么日志追加推荐 `O_APPEND` 而不是自己 `lseek`？**
   要点：内核在 `write` 时原子定位到末尾，多进程并发不会互相覆盖；用户态 `lseek`+`write` 存在竞态窗口。
4. **删除文件后 `df` 显示空间未释放的原因？**
   要点：仍有进程持有该 inode 的 `struct file` 引用，`i_nlink` 已为 0 但引用计数非零，数据块待最后一个引用关闭后回收。
5. **`FD_CLOEXEC` 与 `O_CLOEXEC` 有何区别？**
   要点：前者是描述符标志，只能通过 `fcntl(F_SETFD)` 设置；后者是 `open` 的原子标志，避免「打开后设置前被 `exec` 继承」的泄漏窗口。

## 九、演进与趋势
fd 模型本身稳定，但围绕它的接口持续演进：`close_range` 提供批量、原子友好的关闭；`io_uring` 用内核态环形队列提交 I/O 并支持注册固定文件，消除重复查表；`pidfd` 用 fd 表达进程引用，与统一的 fd 事件模型一致；`openat2` 通过 `struct open_how` 提供可扩展的打开参数（含 `RESOLVE_*` 路径约束）。容器与沙箱场景更关注描述符泄漏防护，`O_CLOEXEC` 已成为新代码的默认选择。

## 十、小结
「进程描述符表 → 打开文件表 → inode」三级结构是理解 Unix I/O 的钥匙：`fd` 是进程内下标，`struct file` 承载共享的偏移与状态标志，inode 承载文件本体。共享偏移当且仅当两个 fd 指向同一 `struct file`：`dup` 与 `fork` 共享，独立 `open` 不共享；`fcntl(F_SETFL)` 影响所有副本，`FD_CLOEXEC` 只影响单个描述符。掌握这三条规则，就能正确推理重定向、日志追加、引用计数与「删除后空间未释放」等绝大多数 fd 相关问题。
