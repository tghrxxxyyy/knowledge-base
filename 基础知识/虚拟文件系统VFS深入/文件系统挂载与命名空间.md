# 文件系统挂载与命名空间

> 对应 Kerrisk《The Linux Programming Interface》第 14 章「文件系统」，以及 Love《Linux Kernel Development》第 13 章中关于挂载与 `super_block` 的说明。

## 一、背景与挑战
Unix 的核心理念是「单一树形命名空间」：所有文件都可从 `/` 出发用一条路径访问。但物理上存在多块磁盘、多个分区、网络文件系统与内存文件系统。「挂载」（mount）把某个文件系统的根「嫁接」到已有目录上，原目录内容被隐藏，`/` 之下的路径继续可用。
容器时代带来第二层需求：同一台机器上多个容器需要看到**不同**的文件系统视图——容器 A 的 `/proc` 只显示自己的进程，容器 B 的 `/` 是它自己的镜像根。于是挂载不再只有一棵全局树，而必须支持**每命名空间的挂载树副本**，即挂载命名空间（mount namespace）；随之引入的新复杂度是挂载事件的**传播**（一个命名空间里的 `mount` 是否影响其他命名空间）。

## 二、核心原理
内核用 `struct mount`（历史上称 `vfsmount`）描述一次挂载：`mnt_parent`（父挂载）、`mnt_mountpoint`（父树中被遮盖的挂载点 dentry）、`mnt_root`（本次挂载的文件系统根 dentry）、`mnt_ns`（所属命名空间）、`mnt_flags`（如 `MS_RDONLY`、`MS_NOSUID`、`MS_NODEV`、`MS_NOEXEC`）、`mnt_list`/`mnt_child`/`mnt_sibling`（构成挂载树与命名空间链表）。`mount --bind` 只是把现有子树再挂一次（`mnt_root` 指向已有 dentry），`MS_REC` 使操作递归到子树内所有挂载。`mount_hashtable` 以「父 mount + mountpoint dentry」为键，路径解析遇到带 `DCACHE_MOUNTED` 的 dentry 时查表跨越挂载点。
命名空间由 `struct mnt_namespace` 表示。`clone(CLONE_NEWNS)` 或 `unshare(CLONE_NEWNS)` 创建新命名空间，内核通过 `copy_mnt_ns` **复制**父命名空间的挂载树结构——同一批 `struct mount` 被多个命名空间共享，因此它自带引用计数并可通过 `mnt_list` 挂在多个命名空间的链表上。这就是「初始视图相同、后续变更可隔离」的实现基础。
**挂载传播**是容器场景最易出错的部分。每对父子挂载之间有若干传播类型：`MS_SHARED` 属于某个共享对等组（peer group），组内任一成员发生挂载/卸载都会传播到组内所有成员并向下传播；`MS_PRIVATE` 既不接收也不发送；`MS_SLAVE` 接收来自对等组的事件但本地事件不外传（单向）；`MS_UNBINDABLE` 既不可共享也禁止 bind 挂载。`mount --make-rshared /` 与 `mount --make-rslave /` 分别递归设置，systemd 用 `Propagation=` 管理默认行为，容器运行时通常先把新命名空间的 `/` 设为 private 或 slave，避免挂载泄漏到宿主。
**`pivot_root` 与 `chroot` 的关键区别**：`chroot` 只改进程的 `fs_struct->root` 指针，不改变挂载树——进程仍可见全局挂载，且可通过 `/proc/<pid>/root`、已打开的 fd 或 chroot 前的 cwd 逃逸。`pivot_root(new_root, put_old)` 则把当前挂载树整体换根：新根成为 `/`，旧根挂到 `put_old` 下，配合 `umount` 移除旧根后进程的挂载视图彻底改变。容器运行时用 `unshare(CLONE_NEWNS)` + `pivot_root` 实现文件系统隔离。
**卸载**失败最常见的原因是引用非零：仍有进程持有该挂载内某个 `struct file`、进程 cwd 位于其中、或存在子挂载。此时返回 `EBUSY`（这是保护性错误），或用 `MNT_DETACH` 惰性卸载——先把挂载从树中摘除，待最后一个引用消失再真正释放。

## 三、形式化与数学基础
设根命名空间的挂载树为 $M_0$，第 $i$ 个 clone 得到 $M_i$（初始时结构同构并共享同一批 `struct mount`）。路径解析按当前进程的命名空间进行：

$$ lookup(p, M_i) \ne lookup(p, M_0)\quad \text{当 } p \text{ 的某个前缀在两树中指向不同挂载} $$

挂载点跨越可写成（$H$ 为以 $(parent, dentry)$ 为键的挂载哈希表）：

$$ resolve(d) = \begin{cases} mnt\_root(H[p][d]) & (p,d) \in H \\ d & \text{否则} \end{cases} $$

共享对等组 $G = \{g_1, \dots, g_n\}$ 内的事件 $e$ 传播为

$$ propagate(e) = \bigcup_{g \in G} e|_{g} \;\cup\; \bigcup_{g \in G,\, c \in children(g)} propagate(e|_{c}) $$

`MS_SLAVE` 只保留接收方向，`MS_PRIVATE` 使传播集合为空。卸载的可行性条件为

$$ umount(m)\ \text{成功} \iff refcount(m) = 0 \;\land\; \left|children(m)\right| = 0 $$

否则返回 `EBUSY`，或需以 `MNT_DETACH` 惰性摘除。

## 四、代码实现
```c
#define _GNU_SOURCE
#include <sched.h>
#include <sys/mount.h>
#include <unistd.h>

int setup_container_fs(const char *newroot) {
    /* 1. 独立挂载命名空间 */
    if (unshare(CLONE_NEWNS) == -1) return -1;

    /* 2. 默认 __shared__ 会把挂载事件传播到宿主，先改为 private */
    if (mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL) == -1) return -1;

    /* 3. 递归 bind 新根，使 /proc、/sys 等子挂载一并带上 */
    if (mount(newroot, newroot, NULL, MS_BIND | MS_REC, NULL) == -1) return -1;

    /* 4. pivot_root：新根成为 /，旧根挂到 newroot/.oldroot */
    char oldroot[256];
    /* 用 snprintf 拼出 newroot 下的 .oldroot 路径 */
    if (pivot_root(newroot, oldroot) == -1) return -1;

    /* 5. 卸载旧根并切到新的 / */
    if (chdir("/") == -1) return -1;
    if (umount2("/.oldroot", MNT_DETACH) == -1) return -1;

    /* 6. 以受限标志挂载 proc：容器内必备的三个安全标志 */
    return mount("proc", "/proc", "proc",
                 MS_NOSUID | MS_NOEXEC | MS_NODEV, NULL);
}
```

```bash
# 查看传播类型与挂载树关系（第三列是父挂载 id，标有 shared:X / master:Y）
cat /proc/self/mountinfo | head -20

mount --make-rslave /          # 递归 slave：接收宿主事件但不回传（容器默认行为）
umount -l /mnt/busy            # 惰性卸载：立即摘除，待引用归零后释放
mount --rbind /src /dst        # 递归绑定挂载
```

## 五、与其他技术对比
| 维度 | `chroot` | 挂载命名空间 | 完整容器 | bind 挂载 | overlayfs |
| --- | --- | --- | --- | --- | --- |
| 改变根目录 | 是 | 是（配合 `pivot_root`） | 是 | 否（复用子树） | 否 |
| 改变挂载视图 | 否 | 是（每命名空间独立） | 是 | 否 | 否 |
| 是否可见其他挂载 | 是（仍见全局） | 否（隔离后不可见） | 否 | 是 | 是（作为下层） |
| 所需特权 | `CAP_SYS_CHROOT` | `CAP_SYS_ADMIN`（用户命名空间内可放宽） | 组合 | 同左 | 同左 |
| 可逃逸性 | 可（相对路径、仍见外部挂载） | 低（配合 `pivot_root`） | 低 | 不适用 | 不适用 |

`chroot` 的问题不在于「被绕过」这一单一技巧，而在于它只改一个指针：进程仍能通过 `/proc/1/root`、已打开的描述符或 chroot 前建立的工作目录逃逸。挂载命名空间则从根上删除「外部路径可达」这一前提，这正是「容器 = 命名空间 + cgroups + 安全模块」而非「容器 = chroot」的原因。

## 六、常见误区
- **以为 `chroot` 等于容器隔离**：它只改根目录，挂载视图、PID 视图、网络视图全部共享，且存在多种逃逸路径。
- **以为 `umount` 总会成功**：忙挂载（有进程打开文件、cwd 在其中、存在子挂载）返回 `EBUSY`；应找到持有者或用 `MNT_DETACH`。
- **以为挂载只影响本进程**：默认传播是 `MS_SHARED`，在共享对等组内会传播到其他命名空间；容器必须先设为 private/slave。
- **以为 clone 出的命名空间完全独立**：初始视图是**复制**同一批 `struct mount`（引用计数共享），只有一侧执行挂载/卸载后才产生分歧；`MS_SLAVE` 正是为表达这种半独立关系而存在。
- **以为 `pivot_root` 与 `chroot` 可随意互换**：`pivot_root` 要求新根是一个挂载点且与旧根不在同一挂载上（否则 `EINVAL`），并改变整个命名空间的根。
- **以为命名空间能隔离设备访问**：它只隔离路径视图；隔离设备需 cgroup 设备控制器与 `MS_NODEV` 等标志配合。

## 八、面试题
1. **容器如何用挂载命名空间实现根文件系统隔离？**
   要点：`unshare(CLONE_NEWNS)` 建立私有挂载树 → 递归 `MS_PRIVATE`/`MS_SLAVE` 防止传播 → 递归 bind 新根 → `pivot_root` 换根 → `MNT_DETACH` 卸载旧根 → 以 `MS_NOSUID|MS_NOEXEC|MS_NODEV` 挂载 `proc`。
2. **`MS_SHARED`、`MS_SLAVE`、`MS_PRIVATE` 的区别？**
   要点：shared 双向传播（对等组内互见），slave 单向接收（可见宿主变更但不回传），private 完全隔离；容器通常用 slave 或 private。
3. **为什么 `umount` 会返回 `EBUSY`？**
   要点：挂载或其后代仍被引用——有进程持有其中的 `struct file`、cwd 位于其中、或存在子挂载；可定位持有者或用 `MNT_DETACH`。
4. **`/proc/self/mountinfo` 中的父子 id 与传播标记说明了什么？**
   要点：每行一个挂载，`parent id` 表示挂载树中的父节点，`shared:X` 表示属于共享对等组 X，`master:Y` 表示它是 Y 的从属；据此可还原挂载树与传播拓扑。
5. **`chroot` 为什么不足以做隔离？**
   要点：只改 `fs_struct->root`，挂载树与 PID/网络视图不变；已打开 fd、`/proc/<pid>/root`、chroot 前的 cwd 都可能成为逃逸路径。

## 九、演进与趋势
挂载命名空间已成为容器与 systemd 的基石：systemd 用 `Propagation=` 与 `BindPaths=` 声明服务视图，runc/crun 用 `pivot_root` 与 `MS_*` 标志构造根，Kubernetes 的 volume 挂载叠加 `bind` 与 `overlayfs`。技术演进集中在三处：**新挂载 API**（`fsopen`/`fsconfig`/`fsmount`/`move_mount`/`open_tree`）把「创建文件系统实例」与「挂载到某处」分离，支持以 fd 传递与原子移动；**idmapped mounts** 让同一挂载树在不同用户命名空间下呈现不同属主映射，消除大量按容器复制挂载的必要；**挂载属性原子设置**（`mount_setattr`）与 `statmount`/`listmount` 等只读查询接口提升可观测性。长期看，「路径视图 + 命名空间 + 传播拓扑」三层模型会稳定保留。

## 十、小结
挂载把多棵异构文件系统树拼成单一逻辑树，`struct mount` 的 `mnt_parent`/`mnt_mountpoint`/`mnt_root` 构成挂载树，挂载哈希表支撑路径跨越。挂载命名空间让这棵树可被进程级复制，通过 `MS_SHARED`/`MS_SLAVE`/`MS_PRIVATE` 精确控制事件传播方向；配合 `unshare` 与 `pivot_root`，进程即可获得与宿主彻底隔离的文件系统视图。三条最实用的结论：容器场景必须先禁用默认共享传播、`umount` 的 `EBUSY` 是引用计数保护、`chroot` 不等于隔离。
