# 文件系统挂载与命名空间

> 对应 Kerrisk《The Linux Programming Interface》第 14 章与 Love《Linux Kernel Development》第 13 章挂载机制。

## 一、背景与挑战
单棵树 `/` 如何容纳多个物理设备与网络文件系统？`mount` 将一块文件系统"嫁接"到已有目录（挂载点），实现统一命名空间。容器又要求每个容器看到不同的挂载树，于是引入挂载命名空间。

## 二、核心原理
`mount` 把新文件系统的 root `dentry` 挂到父树某目录上，原目录内容被隐藏。`mount` 结构体记录 `mnt_parent`、`mnt_mountpoint`、`mnt_root` 形成挂载树。CLONE_NEWNS 创建的挂载命名空间让进程拥有独立挂载树副本，容器借此隔离 `/proc`、`/sys` 等。

## 三、形式化与数学基础
设根命名空间挂载树为 $M_0$，clone 得 $M_i$。查找路径 $p$ 时按当前进程的 `nsproxy->mnt_ns` 解析：
$$lookup(p, M_i) \ne lookup(p, M_0)\quad \text{当 } p \text{ 在两树中被不同挂载}$$
共享/从属（shared/slave）挂载传播控制变更是否跨命名空间可见。

## 四、代码实现
```c
// 进入容器前为子进程建立独立挂载命名空间
unshare(CLONE_NEWNS);
mount("proc", "/proc", "proc", MS_NOSUID|MS_NOEXEC|MS_NODEV, NULL);
// pivot_root 切换根，使容器只见自身根
```

## 五、与其他技术对比
绑定挂载（bind mount）复用同一子树到多处；overlayfs 叠加密集层做容器镜像；相较 chroot，挂载命名空间更彻底且可叠加多挂载点。

## 六、常见误区
误以为 chroot 等于容器隔离：chroot 只改根目录，仍能看到全局挂载与 PID。误以为 `umount` 总成功：忙挂载（引用非零）返回 EBUSY。误以为挂载对全局可见：shared 传播才是默认。

## 七、与开源书/权威来源对应
Kerrisk 第 14 章覆盖 `mount`/`umount`/`mount namespaces`；OSTEP 容器章讲 `clone(CLONE_NEWNS)`。

## 八、面试题
问：容器如何用 mount namespace 实现根文件系统隔离？答：CLONE_NEWNS + pivot_root。问：shared 与 slave 挂载区别？

## 九、演进与趋势
挂载命名空间是容器技术基石之一，与 pid/network/user namespace 组合实现轻量隔离；systemd 用 `Propagation` 管理发行版挂载传播。

## 十、小结
挂载将异构文件系统拼成统一树，挂载命名空间让该树可被进程级复制，是容器文件系统视图隔离的根本。
