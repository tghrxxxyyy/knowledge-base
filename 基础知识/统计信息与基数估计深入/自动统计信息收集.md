# 自动统计信息收集

> 对应 PostgreSQL autovacuum/auto-analyze 与 MySQL `innodb_stats_auto_recalc`，参考官方运维文档。

## 一、背景与挑战

统计信息会随数据变更而陈旧，依赖人工 `ANALYZE` 容易遗忘，尤其在批量加载、大事务、突发写入之后。自动收集机制在表变更达到阈值时自动触发，保持统计新鲜，降低运维负担。

但自动收集并非「万能且实时」，理解其触发逻辑与滞后窗口，对关键负载仍必要。误以为「开了自动就万事大吉」，常是大批量导入后计划退化的根因，也是运维最容易踩的坑。

## 二、核心原理

**PostgreSQL** 的 auto-analyze 由 autovacuum 守护进程负责：当表变更行数超过阈值即启动分析。触发阈值：

$$ \Delta rows \ge autovacuum\_analyze\_threshold + autovacuum\_analyze\_scale\_factor \cdot reltuples $$

其中 `reltuples` 为当前估计行数。可针对单表调整 `autovacuum_analyze_scale_factor` 与阈值，热门表可调低以更频繁刷新。

**MySQL InnoDB** 在 `innodb_stats_auto_recalc = ON` 时，当表约 10% 行发生变化后，异步更新持久统计（写入 `mysql.innodb_index_stats`）。异步重算避免阻塞写入，但存在统计滞后窗口——刚导入完数据，统计可能尚未刷新。

PostgreSQL 还可配置 `log_autovacuum_min_duration` 观察分析是否真的触发，便于确认自动收集按预期工作。

## 三、形式化与数学基础

通用触发条件：

$$ \Delta rows \ge \max(threshold, scale\_factor \cdot N) $$

$N$ 为当前估计行数。小表因 $N$ 小，阈值容易被突破，更频繁分析；大表需更大绝对变更才触发。异步重算意味着统计反映「触发时刻附近」的快照，存在时间滞后：

$$ t_{stale} = t_{change} + t_{lag} $$

在 $t_{lag}$ 窗口内查询仍用旧统计。若批量导入在阈值触发前结束并被查询，便会命中陈旧统计，这正是导入后即查变慢的典型成因。

## 四、代码实现

```sql
-- PostgreSQL 查看 / 调整自动分析
SHOW autovacuum_analyze_threshold;
SHOW autovacuum_analyze_scale_factor;
ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.05);

-- MySQL 查看自动重算
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';

-- 批量导入后手动刷新（弥补滞后）
ANALYZE TABLE orders;
```

## 五、与其他技术对比

| 系统 | 触发 | 是否异步 | 备注 |
| --- | --- | --- | --- |
| PostgreSQL | 变更超阈值 | 是（autovacuum） | 可单表调参 |
| MySQL InnoDB | 约 10% 变更 | 是 | 持久统计 |
| Oracle | 自动作业 + 直方图自动构建 | 是 | 更细粒度 |
| 列式系统 | 加载时同步构建 | 否 | 弱化后台需求 |

Oracle 有更细粒度的自动统计与直方图自动构建；列式系统常在加载时同步构建列统计，几乎不需要后台异步收集，从根本上消解滞后窗口。

## 六、常见误区

- 认为自动收集永远及时：大批量加载后可能有滞后窗口，需手动 `ANALYZE`。
- 认为自动收集零开销：仍消耗 IO 与 CPU，密集写入时可能叠加压力。
- 认为阈值越低越好：过低导致频繁分析，反而拖累写入吞吐。
- 认为自动分析会锁表：现代实现多为采样且允许并发，但仍建议避开峰值。

## 八、面试题

- 批量导入后为何要手动 ANALYZE？答：自动收集有滞后阈值，导入期间可能未触发或未完成。
- PostgreSQL 触发公式？答：`threshold + scale_factor * reltuples` 的变更行数。
- 自动收集有开销吗？答：有，IO/CPU 消耗，需在新鲜度与写入吞吐间权衡。
- 如何验证自动分析真的发生？答：查 `pg_stat_user_tables.last_analyze` 或 `log_autovacuum_min_duration` 日志。

## 九、演进与趋势

增量 / 在线统计更新、基于变更流（binlog/WAL）的实时统计，减少滞后与全表扫描开销；学习型统计自动决定采样率与桶数，按列重要度差异化收集，把算力集中在倾斜与高频列。

配置自动收集时，一个常被忽略的点是「大表反而更迟钝」：因为触发公式含 `scale_factor * N`，大表的绝对变更阈值很高，需要海量写入才触发，期间计划可能已退化很久。对核心大表应单独调低 `scale_factor` 或 `threshold`。

与之相对，小表很容易频繁触发分析，若表每秒都在小幅变动，会自动分析刷个不停，反而浪费 IO。这类表可考虑关闭自动分析、改为定时任务在低谷期执行，把抖动平滑掉。

监控上建议同时看两类信号：一是 `pg_stat_user_tables.last_analyze` 距现在多久（新鲜度），二是统计估计与实际的偏差（质量）。只盯新鲜度会误判——分析是执行了，但采样或分布问题仍可能让估计失真。

最后，自动收集与分析是「修统计」，不是「修计划」。若某查询长期对统计不敏感（如优化器缺等价变换），再频繁 ANALYZE 也无济于事，那时该考虑的是重写 SQL 或加索引，而非调统计参数。

## 十、小结

自动收集降低运维负担，但理解其触发阈值、滞后窗口与开销，对关键批量负载仍不可或缺；必要时手动 `ANALYZE` 兜底，尤其在批量加载后立即刷新，可避免计划退化，是稳定性能的最低成本保险。
