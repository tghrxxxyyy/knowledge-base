# 自动统计信息收集

> 对应 PostgreSQL autovacuum/auto-analyze 与 MySQL `innodb_stats_auto_recalc`，参考官方运维文档。

## 一、背景与挑战
统计信息会随数据变更而陈旧。依赖人工 ANALYZE 易遗忘，尤其在批量加载后。自动收集在变更达到阈值时触发，保持统计新鲜。

## 二、核心原理
PostgreSQL 的 auto-analyze 由 autovacuum 进程在表变更行数超过 `analyze_scale_factor * reltuples + analyze_threshold` 时启动。MySQL InnoDB 在 `innodb_stats_auto_recalc=ON` 时，当表约 10% 行变化后异步更新持久统计。

## 三、形式化与数学基础
触发条件：
$$ \Delta rows \ge \max(threshold, scale\_factor \cdot N) $$
$N$ 为当前估计行数。异步重算避免阻塞写入，但存在统计滞后窗口。

## 四、代码实现
```sql
-- PostgreSQL 查看/调整
SHOW autovacuum_analyze_threshold;
ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.05);
-- MySQL
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
```

## 五、与其他技术对比
Oracle 有更细粒度的自动统计与直方图自动构建（auto job）。列式与分析型系统常在加载时同步构建列统计，弱化后台自动收集需求。

## 六、常见误区
认为自动收集永远及时——大批量加载后可能存在滞后窗口，需手动 ANALYZE。认为自动收集零开销——仍消耗 IO 与 CPU。

## 七、与开源书/权威来源对应
PostgreSQL 文档「Automatic Vacuuming」；MySQL 文档「InnoDB Statistics」。

## 八、面试题
问：批量导入后为何要手动 ANALYZE？答：自动收集有滞后阈值，导入期间可能未触发或未完成。

## 九、演进与趋势
增量/在线统计更新、基于变更流的实时统计，减少滞后与开销。

## 十、小结
自动收集降低运维负担，但理解其触发阈值与滞后对关键负载仍必要。
