# 统计信息过期与计划退化

> 对应 PostgreSQL / MySQL 官方文档关于统计陈旧的影响与 DDIA 第3章，参考运维经验。

## 一、背景与挑战
数据分布随业务演化，而过期统计使优化器基于旧画像做决策，原本优的计划逐渐退化，表现为「昨天还快、今天变慢」的经典现象。

## 二、核心原理
当表行数暴涨、新增热点值（如促销商品）、或数据从均匀变倾斜，旧直方图与 distinct 数失效。优化器仍按旧选择性选小表驱动、走索引，实际却应走顺序扫或换连接顺序。

## 三、形式化与数学基础
真实选择性 $sel_{real}$ 与估计 $sel_{est}$ 偏差：
$$ \epsilon = \frac{|sel_{real} - sel_{est}|}{sel_{real}} $$
$\epsilon$ 大时估计基数失真，带动扫描方式与连接顺序错位，代价差可放大为数量级。

## 四、代码实现
```sql
-- 对比估计与实际
EXPLAIN ANALYZE SELECT * FROM orders WHERE status='shipped';
-- 若估计 rows 与 actual rows 差很大，考虑 ANALYZE
ANALYZE orders;
```

## 五、与其他技术对比
自适应查询（SQL Server、Oracle）在首执发现偏差后后续重优化，部分缓解过期统计影响。静态优化器则完全依赖统计新鲜度。

## 六、常见误区
认为计划退化=SQL 写错——常是统计过期。认为加索引解决一切——根因在估计偏差时加索引无效。

## 七、与开源书/权威来源对应
PostgreSQL 文档「Updating Planner Statistics」；DDIA 第3章存储与检索章节。

## 八、面试题
问：查询突然变慢第一排查什么？答：看 EXPLAIN 估计行数与实际差距，判断是否统计过期，执行 ANALYZE。

## 九、演进与趋势
反馈式优化（feedback-driven）依据执行反馈自动修正统计与计划，是商业库与科研热点。

## 十、小结
统计过期是计划退化的头号隐形原因，监控估计偏差与定期 ANALYZE 是防线。
