# 统计信息过期与计划退化

> 对应 PostgreSQL / MySQL 官方文档关于统计陈旧的影响，参考 Kleppmann《DDIA》第3章。

## 一、背景与挑战

数据分布随业务持续演化：行数暴涨、出现新热点值（如促销商品 ID）、或从均匀变为倾斜。而统计信息是某一时刻的「快照」，会随之陈旧。当优化器仍基于旧画像决策，原本优的计划逐渐退化，于是出现经典现象——「昨天还快，今天变慢」。

这是生产中最隐蔽、最高频的性能问题之一，因为其表象与「SQL 写错」「索引缺失」高度相似，极易被误判，浪费大量排查时间。

## 二、核心原理

统计过期后，优化器对谓词选择性的估计偏离真实。例如某 `status` 列旧统计显示各值均匀，实际新增热点值占 90%；优化器仍按「选 1/10」选索引回表，实际却要回表 90% 的行，远不如直接顺序扫描。

又或连接顺序按旧 distinct 数安排，实际某一侧暴涨导致中间结果膨胀为数量级，拖垮整条 SQL。计划退化往往不是突变，而是随数据漂移逐步劣化，难以第一时间察觉，常在业务高峰暴露。

## 三、形式化与数学基础

真实选择性 $sel_{real}$ 与估计 $sel_{est}$ 的相对偏差：

$$ \epsilon = \frac{|sel_{real} - sel_{est}|}{sel_{real}} $$

$\epsilon$ 大时估计基数失真，带动扫描方式（索引 vs 顺序扫）与连接顺序错位。代价模型下，单表扫描代价约：

$$ Cost \approx sel \cdot N \cdot c_{random} + (1-sel) \cdot N \cdot c_{seq} $$

当 $sel$ 估计偏低，优化器低估随机 IO 而误选索引；实际高选择性使其退化为海量随机读，延迟飙升。连接代价同理被中间结果放大：

$$ Cost_{join} \propto card(left) \cdot card(right) / sel_{join} $$

基数误差在多层连接中指数级放大。

## 四、代码实现

```sql
-- 对比估计与实际行数，判断是否统计过期
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'shipped';
-- 若计划的 rows（估计）与 actual rows（实际）差很大，执行 ANALYZE

ANALYZE orders;                 -- 刷新统计
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 200;

-- 定期巡检：对比 pg_stat_user_tables.n_live_tup 与统计估算
SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE relname = 'orders';
```

## 五、与其他技术对比

| 优化器 | 应对过期 | 特点 |
| --- | --- | --- |
| 静态（多数开源） | 依赖统计新鲜度 | 过期即退化 |
| 自适应（SQL Server/Oracle） | 首执发现偏差后重优化 | 缓解但未根除 |
| 反馈驱动 | 依据执行反馈修正 | 前沿方向 |

自适应查询在首执发现估计偏差后，后续执行自动重优化，部分缓解过期影响；但首次执行仍可能慢，且依赖运行时反馈闭环。

## 六、常见误区

- 认为计划退化 = SQL 写错：更常见是统计过期导致估计偏差。
- 认为加索引解决一切：根因在选择性估计偏差时，加索引无效甚至更慢。
- 认为自动收集足够：大批量加载后自动收集有滞后窗口，需手动 `ANALYZE`。
- 认为实际行数略多无妨：基数误差会在连接中被放大，小偏差可引发大退化。

## 八、面试题

- 查询突然变慢第一排查什么？答：看 `EXPLAIN ANALYZE` 估计行数与实际差距，判断是否统计过期，再 `ANALYZE`。
- 热点值导致什么问题？答：旧统计均匀假设下误选索引，实际高选择性退化为海量随机读。
- 如何防退化？答：监控估计偏差、定期 / 批量后 `ANALYZE`、用自适应或反馈优化。
- 连接中基数误差为何更严重？答：多层连接使中间结果基数误差被连乘放大，指数级劣化。

一个常被忽视的关联是：计划退化与「统计新鲜度」并非线性关系。数据小幅漂移时计划可能不变（优化器容差内），一旦越过拐点会突然劣化，呈现「平时好好的、某天崩了」的断崖式表现，这正是统计过期最棘手之处。

因此监控应设「相对偏差」阈值而非「绝对时间」阈值：只要估计/实际偏差超比例就告警，比「距上次 ANALYZE 多久」更能提前发现问题，也避免了无谓的频繁分析。

补充一句：计划退化往往不是优化器「变笨」，而是它手里拿的是过期地图；定期刷新地图、或在关键时刻手动重绘，比反复怀疑优化器本身更有效。

## 九、演进与趋势

反馈式优化（feedback-driven）依据执行反馈自动修正统计与计划；自动统计增量更新与变更流实时统计，减少滞后窗口；学习型基数估计直接预测真实选择性，弱化对静态统计的依赖，从「周期性快照」走向「在线自适应」。

定位计划退化时，可遵循一个固定流程：先用 `EXPLAIN ANALYZE` 找出估计与实际偏差最大的那一步；再 `EXPLAIN` 无 `ANALYZE` 看优化器的输入估计；二者差异即指向统计问题。若偏差集中在某列，多半是该列分布漂移或采样漏采。

需要警惕的还有「隐性退化」：计划没变、但数据变了，原本索引扫描仍被选中，只是实际回表行数暴增。这类问题不会报错，只在延迟上悄悄体现，最适合用慢查询日志 + 计划基线比对来发现。

在写入高峰后（如大促、批量灌数），务必把 `ANALYZE` 写进收尾脚本，而不是等自动收集「可能」触发。把这一步制度化，能消除一大类偶发慢查询。

从架构层面，对极其敏感的核心查询，可考虑用查询提示（hint）或绑定执行计划暂时兜底，但治本仍在于让统计跟上数据；提示只是过渡手段，长期应回到统计与反馈优化。

## 十、小结

统计过期是计划退化的头号隐形原因；监控估计偏差、在批量变更后及时 `ANALYZE`，是稳定性能的第一道防线，也是区分「真慢」与「统计假象」的关键手段，更是性能排查的起点动作。
