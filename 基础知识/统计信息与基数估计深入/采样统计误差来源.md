# 采样统计误差来源

> 对应 PostgreSQL 文档「Default Statistics Target」与 Garcia-Molina《Database Systems》第12章采样估计，参考 Silberschatz 第14章。

## 一、背景与挑战

为降低 `ANALYZE` 的开销，数据库通常基于**随机抽样**而非全表扫描来构建统计信息（直方图、MCV、distinct 数等）。采样天然带来估计方差，在小表、倾斜数据或数据快速漂移时误差尤其明显，而这些误差会直接传导到优化器的基数估计，进而选出坏的执行计划。

理解误差来源是正确调参与解读 `EXPLAIN` 的前提，也是判断「该不该相信计划」的依据。很多「明明有索引却走全表」的诡异计划，根因正是统计采样误差。

## 二、核心原理

采样率由 `default_statistics_target`（PostgreSQL，控制直方图桶数与采样页数）或类似参数决定。误差来自多条路径：采样行数不足导致方差大；数据倾斜使稀有值被漏采（rare value 在样本里为 0，但实际存在）；数据分布随时间漂移使旧统计失真；并发写入使采样瞬间的数据不一致。

PostgreSQL 按表大小自动确定采样页数（近似固定页数，小表近乎全扫），桶数与采样精度随之变化；MySQL 用固定采样页数，二者都以「少量样本估整体」为代价换速度。采样页是随机选的，因此结果有随机性，重复 ANALYZE 可能得到不同统计。

## 三、形式化与数学基础

对比例 $p$ 的二项估计，标准误：

$$ SE = \sqrt{ \frac{p(1-p)}{n} } $$

$n$ 为采样行数。可见稀有值（小 $p$）或采样不足（小 $n$）时误差显著放大。直方图桶数 $k$ 增大可降低量化误差，但提高采样需求与存储。

对稀有值存在性估计，漏采概率约：

$$ P(miss) = (1 - p)^n \approx e^{-pn} $$

当 $pn \ll 1$ 时极易漏采，这正是长尾值估计失准的根源。方差与样本量成反比，故增大采样页数是降误差最直接手段，但成本随 $n$ 线性上升。

## 四、代码实现

```sql
-- PostgreSQL：提高单列采样精度
ALTER TABLE orders ALTER COLUMN amount SET STATISTICS 500;  -- 桶数上限
SET default_statistics_target = 1000;                        -- 全局目标
ANALYZE orders;                                              -- 重新采样

-- 查看某列统计（含直方图/MCV 摘要）
SELECT * FROM pg_stats WHERE tablename = 'orders';

-- MySQL：调整持久统计采样页数
-- SET GLOBAL innodb_stats_persistent_sample_pages = 200;
-- ANALYZE TABLE orders;
```

## 五、与其他技术对比

| 系统 | 采样控制 | 特点 |
| --- | --- | --- |
| PostgreSQL | `default_statistics_target` | 按表大小定采样页数 |
| MySQL InnoDB | `innodb_stats_persistent_sample_pages` | 固定采样页数 |
| 列式存储 | 区块级精确统计 | 写入时维护，弱化采样误差 |

列式 / 分析型系统常在写入时维护区块级精确统计，规避随机采样误差，因此少有「采样方差」问题，但牺牲了部分写入灵活性。

## 六、常见误区

- 认为统计一定准：采样天然有误差，尤其是稀有值与倾斜列。
- 认为调高目标零成本：更慢的 `ANALYZE` 与更大的统计存储，且仍有漂移风险。
- 认为大表误差小就够用：稀有值漏采概率与总体大小无关，只取决于 $pn$。
- 认为一次 ANALYZE 永久有效：数据漂移会使统计逐渐失效，需周期刷新或触发自动收集。

## 八、面试题

- 小表统计反而不准怎么解？答：提高 `statistics target` 或强制更大采样；小表 PostgreSQL 本就近似全扫。
- 稀有值为何容易漏？答：漏采概率约 $e^{-pn}$，样本覆盖不足时稀有值样本为 0。
- 采样误差如何度量？答：二项标准误 $SE=\sqrt{p(1-p)/n}$，随样本量下降。
- 何时该手动 ANALYZE？答：批量加载 / 大事务后，自动收集滞后窗口内应手动刷新。

从排障流程看，当某查询计划突然变坏且怀疑是统计问题，第一步应是看该列 `pg_stats` 中的 `n_distinct`、直方图与 MCV 是否匹配实际数据；若 MCV 里没有真实存在的高频值，几乎可以断定是采样漏采或统计过期，而非优化器「算错」。

此外，不要把「采样误差」与「统计过期」混为一谈：前者是构建方式固有的方差，调大采样可缓解；后者是时间维度的失真，必须刷新统计。二者治法不同，诊断时先区分，才能对症下药。

补充一句：采样误差不是「 bug 」而是「 trade-off 」的显性化——它提醒我们统计只是近似，优化器 outputs 本就是估计；把估计当精确值，才是真正的误区。

## 九、演进与趋势

自适应采样、增量统计随写入追加更新、以及基于 Sketch（如 HyperLogLog 估 distinct）的近似统计，减少全表 `ANALYZE` 频率与误差；学习型采样率自动决定每列应采多少行，把算力花在倾斜列上。

实践中，判断「统计是否够准」最实用的办法是看 `EXPLAIN ANALYZE` 里估计行数与实际行数的比值：偏差超过一个数量级通常就是采样或分布问题，而非 SQL 本身。

对于明显倾斜的列（如金额、时长、状态码），建议单独提高其 `statistics target`，因为这类列的稀有值与长尾正是最易被采样遗漏、也最影响计划的部分。

需要区分两类误差：采样方差（每次 ANALYZE 结果抖动）与系统偏差（统计结构本身表达不了分布，如相关列）。前者靠增大采样缓解，后者必须引入直方图或 MCV 才能根治，调大采样无济于事。

最后，列式 / 向量化引擎常维护 min/max/null_count 之类的区块级精确统计，配合 zone map 即可跳过无关数据块；这与行存基于随机采样的思路互补，理解二者差异有助于在 HTAP 场景下正确归因性能问题。

## 十、小结

采样统计是开销与精度的权衡：理解标准误、稀有值漏采与分布漂移，才能正确调参并合理解读执行计划偏差，避免把「估计误差」误判为「SQL 写错」，也知道何时该增大采样或手动刷新。
