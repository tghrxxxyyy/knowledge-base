# 重定位表与ELF重定位项

> 对应 Levine《Linkers and Loaders》第 7 章；Bryant & O'Hallaron《CSAPP》第 7.6 节；ELF 规范。

## 一、背景与挑战

编译器生成代码时未知外部符号（函数/全局变量）的最终地址，只能在指令操作数处填 0 并留下「重定位记录」，由链接器（静态）或加载器/动态链接器（动态）事后补值。重定位项是连接「代码位置」与「符号地址」的元数据，理解其结构才能解释为何 PIE/共享库能加载到任意地址。若重定位类型用错（如对非 PIE 用 PC32），会产生绑定到固定地址、ASLR 失效甚至运行时崩溃的问题。

另一层挑战是「加数（addend）的隐式性」：早期 REL 格式把加数编码在指令里（例如 PC 相对调用把 `-4` 写进指令操作数），链接器必须先解码指令才能取出加数，既低效又依赖 ISA 细节；RELA 把加数独立成字段，一举解决可移植性与可调试性问题，这也是 x86-64「几乎全用 RELA」的直接原因。

## 二、核心原理

ELF 每个需重定位的节附一张 `.rela.text`（带加数 addend）或 `.rel.text`（无独立加数，加数编码在指令里）。每项含：偏移 `r_offset`（节内位置）、信息 `r_info`（高 32 位符号索引 + 低 32 位类型）、加数 `r_addend`（REL 无此字段）。常见类型：`R_X86_64_PC32`（32 位相对）、`R_X86_64_64`（64 位绝对）、`R_X86_64_GLOB_DAT`（GOT 项填充）、`R_X86_64_JUMP_SLOT`（PLT 项）、`R_X86_64_RELATIVE`（基址相对，用于 PIE 内数据指针）。链接器与加载器按类型套用不同公式回填。

按「是否查符号表」还可把重定位分为两类：需要查符号的（PC32、64、GLOB_DAT、JUMP_SLOT）与无需查符号的（RELATIVE、IRELATIVE）。后者只依赖加载基址 $B$，因此可在加载期以极低成本批量处理，是 PIE 启动性能的重要优化点。

## 三、形式化与数学基础

对 `R_X86_64_PC32`，最终写入值：

$$value=S+A-P$$

其中 $S$ 为符号运行时地址，$A$ 为加数（常量偏移，PC 相对调用常带 $-4$ 修正指令长度），$P$ 为重定位位置自身地址。相对跳转因此与加载基址无关。绝对重定位 `R_X86_64_64` 写 $S+A$，依赖固定基址（非 PIE）。`R_X86_64_RELATIVE` 写 $B+A$（$B$ 为加载基址），用于 PIE 内「指向自身数据」的指针，无需查符号。

| 类型 | 公式 | 是否查符号 | 依赖基址 |
| --- | --- | --- | --- |
| R_X86_64_PC32 | $S+A-P$ | 是 | 否 |
| R_X86_64_64 | $S+A$ | 是 | 是 |
| R_X86_64_GLOB_DAT | $S$ | 是 | 否 |
| R_X86_64_JUMP_SLOT | $S$ | 是 | 否 |
| R_X86_64_RELATIVE | $B+A$ | 否 | 否（含 $B$） |
| R_X86_64_IRELATIVE | $f(B+A)$ | 否（调用解析函数） | 否 |

注意 PC32 的溢出边界：当 $|S+A-P|>2^{31}-1$ 时 32 位字段无法容纳，链接器报 `relocation truncated to fit`。

## 四、代码实现

```c
// 应用一条重定位（x86-64，REL 风格）
void apply_reloc(Elf64_Rela *r, uint64_t S, uint64_t base) {
    uint64_t P = base + r->r_offset;            // 重定位位置地址
    int64_t v = (int64_t)(S + r->r_addend - P); // S + A - P
    *(int32_t *)P = (int32_t)v;                 // 写入 32 位相对偏移
}
// RELA 相比 REL：加数独立存于 r_addend，便于链接器静态计算
```

动态链接器在加载期对 `JUMP_SLOT`/`GLOB_DAT` 项填真实地址，惰性绑定时 `JUMP_SLOT` 先指向 PLT 残桩，解析后再回填。

```c
// 无需查符号的重定位：只依赖加载基址，可批量快速处理
void apply_relative(Elf64_Rela *r, uint64_t base) {
    uint64_t P = base + r->r_offset;
    *(uint64_t *)P = base + r->r_addend;   // RELATIVE：B + A
}
// 链接器可把连续的 RELATIVE 项归组，加载期顺序扫描、零哈希查找
```

## 五、与其他技术对比

| 类型 | 公式 | 依赖基址 | 用途 |
| --- | --- | --- | --- |
| R_X86_64_PC32 | S+A-P | 否（相对） | 函数调用、近跳转 |
| R_X86_64_64 | S+A | 是（绝对） | 绝对指针、非 PIE |
| R_X86_64_GLOB_DAT | S | 否 | GOT 项填充 |
| R_X86_64_RELATIVE | B+A | 否 | PIE 内自身指针 |

PC 相对重定位使代码可加载到任意地址，是 PIE 与共享库的基础；绝对重定位则把代码钉死在固定地址。

| 格式 | 加数位置 | 优点 | 采用架构 |
| --- | --- | --- | --- |
| REL `.rel.*` | 编码在指令中 | 项更小 | 32 位 ARM/x86 |
| RELA `.rela.*` | 独立 `r_addend` | 可移植、易调试 | x86-64/AArch64 |

## 六、常见误区

1. 把 addend 当成 0——PC 相对调用常带 `-4` 修正指令长度（下一条指令地址）。
2. 误以为重定位只在链接期——加载动态库、PLT 惰性绑定时也要重做。
3. 32 位相对溢出（距离超过 2GiB）只在大型可执行文件/库才暴露，表现为运行时崩溃。
4. 误以为 REL 与 RELA 等价——RELA 把加数独立存储，便于链接器静态计算、查看更清晰，现代 x86-64 几乎全用 RELA。
5. 误以为 `r_offset` 是虚拟地址——它是「相对所属节的偏移」，加载期还需加上段的映射基址。
6. 误以为 `RELATIVE` 也要查符号表——它只用 $B+A$，因此加载期可批量无哈希处理，是 PIE 优化重点。

## 八、面试题

1. `S+A-P` 各含义？答：S 符号地址、A 加数、P 重定位位置地址；PC32 用相对距离，与基址无关。
2. PC32 与 64 绝对区别？答：前者相对、可重定位；后者绝对、依赖固定基址（非 PIE 才用）。
3. 为何 PIE 必须相对重定位？答：PIE 基址随机（ASLR），代码必须自相对寻址，不能用绝对地址。
4. `R_X86_64_RELATIVE` 用于什么？答：PIE 内指向自身数据的指针，填 $B+A$，无需查符号表。
5. PC32 的 addend 为何常是 `-4`？答：x86 相对跳转以「下一条指令地址」为基准，而重定位以「当前指令地址」为基准，差 4 字节。
6. `relocation truncated to fit` 因何产生？答：32 位相对字段无法容纳大于约 2GiB 的符号距离，需改模型或拆分模块。

## 九、演进与趋势

RELA 取代 REL（加数独立字段，链接器更易计算）；RISC-V 引入 PC 相对与 GOT 混合类型；`R_X86_64_REX_GOTPCRELX` 等让链接器把 GOT 访问优化为直接 RIP 相对，减少间接。链接器还用「重定位压缩」（如 `DT_RELACOUNT`）加速加载期处理。

更进一步的方向是「减少重定位量」：`-fno-plt` 让调用直接经 GOT 而非 PLT，减少跳板；`-Wl,-z,pack-relative-relocs`（DT_RELR）用差分编码压缩连续的 RELATIVE 项，可使大型二进制的相对重定位表体积显著下降；`-fvisibility=hidden` 则从源头消除跨模块重定位需求。加载器侧也引入并行重定位处理，把加载期 CPU 开销分摊到多核。

## 十、小结

重定位项是位置修正的元数据，PC 相对公式 `S+A-P` 是地址无关的根基。理解它才能解释 PIE、共享库与加载期绑定的底层机制。实务中建议形成两条直觉：其一，重定位公式的每一项都有明确角色，读 `readelf -r` 时应能直接推算出最终写入值；其二，重定位类型的选择决定了「能否随机加载」和「加载期开销多大」，因此它与安全（ASLR）和启动性能直接挂钩。
