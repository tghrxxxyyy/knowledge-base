# 静态链接与符号合并机制

> 对应 Bryant & O'Hallaron《CSAPP》第 7 章；Levine《Linkers and Loaders》第 4 章。

## 一、背景与挑战

多个可重定位目标文件（`.o`）各自拥有独立的符号表、代码段与数据段，且地址在链接前未知。链接器必须把它们合并成单一可执行镜像，核心难点有三：相同名字的符号来自不同翻译单元、强弱语义不同（同名函数只能一个定义）、地址需合并后统一重排。若处理不当，会出现 multiple definition、undefined reference 或静默选用错误定义。真实工程里还涉及 C++ 模板实例化产生的「重复强符号」（COMDAT）、以及静态库间的循环依赖，使决议更复杂。

第四个难点是「重定位与决议的耦合」：决议结果（某符号最终绑定到哪个定义）直接决定重定位要填入什么值，因此链接器必须先完成全局符号决议，才能回填重定位；而决议又依赖「哪些 `.o` 被抽入」，形成「抽取 → 决议 → 再抽取」的迭代。理解这一依赖环，才能解释链接顺序为何如此敏感。

## 二、核心原理

链接器按命令行顺序读取 `.o` 与静态库（`.a`），将同名节（`.text`/`.data`/`.bss`）拼接成连续区域，构建全局符号表。对全局符号做决议（resolution）：从所有定义中选一个绑定到所有引用。强弱符号规则：强符号（函数、已初始化全局变量）全局只能有一个定义，重复即报错；弱符号（未初始化全局，COMMON）允许多个，链接器任选其一（若存在强符号则强优先）。静态库按「需要才抽取」原则：只把当前未定义符号所需的 `.o` 加入，且命令行顺序决定抽取先后，不回头。C++ 的 COMDAT（如 `.gnu.linkonce`）让模板/内联的重复定义可被合并而非报错。

现代编译器默认 `-fno-common`，把未初始化全局改为强符号放入 `.bss`，避免「同名未初始化变量被静默合并」这一历史陷阱；如需旧行为可显式 `-fcommon`。

## 三、形式化与数学基础

合并后符号表规模满足：

$$|\Sigma|=\sum_i |sym_i|-|\text{重复弱符号}|$$

其中 $\Sigma$ 为最终符号集合。节在镜像中的虚拟偏移由累加布局决定：$off_k=\sum_{j<k}align\_up(size_j, align_j)$。符号决议可看作偏函数 $resolve(name)\mapsto def$，强符号优先于弱符号；COMDAT 组以「首次定义胜出」合并。链接通常分两遍（two-pass）：第一遍收集所有符号与节尺寸、定布局，第二遍真正回填重定位。

| 符号类别 | 定义位置 | 可否多定义 | 决议规则 |
| --- | --- | --- | --- |
| 强全局 | 函数/已初始化全局 | 否 | 重复即报错 |
| 弱符号（COMMON） | 未初始化全局（`-fcommon`） | 是 | 有强则强优先，否则任选 |
| `__attribute__((weak))` | 显式声明 | 是 | 强定义可覆盖 |
| 局部（static） | 文件内 | 是（互不冲突） | 不参与全局决议 |

## 四、代码实现

```c
// 伪代码：节拼接与符号布局
typedef struct { char *name; uint64_t addr, size, align; } Section;
unsigned off = 0;
for (Section *s = secs; s; s = s->next) {
    s->addr = base + off;                 // 分配虚拟地址
    off += align_up(s->size, s->align);   // 按对齐累加
}
// 符号决议：强覆盖弱
for (Symbol *sym in all_symbols)
    if (is_strong(sym)) global[sym->name] = sym;   // 重复强符号 -> 报错
    else if (!global[sym->name]) global[sym->name] = sym;  // 弱兜底
```

静态库抽取还需维护「未决引用集合」，每抽到 `.o` 就消解其中导出的符号，并可能引入新未决引用——故顺序敏感。

```c
// 静态库抽取算法（伪代码）
U = {};                       // 未决引用集合
for (obj in inputs) {
    if (obj.is_archive_member && !obj.defines_any(U)) continue;  // 不需要则不抽
    add(obj);                 // 抽入
    U = (U ∪ obj.undefs) \ obj.defs;   // 消解已定义，加入新未决
}
// 结束后若 U 非空 -> undefined reference
```

## 五、与其他技术对比

| 方式 | 体积 | 启动 | 库更新 | 内存共享 |
| --- | --- | --- | --- | --- |
| 静态链接 | 大 | 快（无加载绑定） | 需重链 | 不可共享 |
| 动态链接 | 小 | 略慢（GOT/PLT 绑定） | 替换 .so 即可 | 可共享物理页 |

静态链接把代码固化为单一镜像，部署简单、启动快，但体积大、库修复需重新链接整个程序。

| 去重机制 | 作用 | 说明 |
| --- | --- | --- |
| COMDAT 组 | 合并模板/内联重复定义 | 以组为单位保留一份 |
| `--gc-sections` | 删除未引用节 | 需配合 `-ffunction-sections` |
| LTO | 跨 TU 内联与死代码消除 | 链接期重做优化 |
| `--start-group` | 解决 `.a` 循环依赖 | 反复扫描，链接变慢 |

## 六、常见误区

1. 认为未初始化全局变量是强符号——实际是弱符号，落入 COMMON，多定义时链接器任选其一，可能掩盖 bug。
2. 以为链接顺序无关——静态库按命令行顺序抽取，符号在前未被引用则后续不再回头补抽，顺序错会 undefined reference。
3. 重复定义强符号却期望明确报错位置——实际仅报 `multiple definition`，不指出哪个 TU 优先。
4. 误以为静态库顺序无关可用 `--start-group` 万能解——`--start-group` 能解循环依赖但显著拖慢链接。
5. 误以为 `static` 函数也会冲突——局部符号不参与全局决议，各 TU 可同名。
6. 误以为 `-fcommon` 是默认行为——现代 GCC 默认 `-fno-common`，旧的「同名未初始化变量静默合并」已不是默认。

## 八、面试题

1. 为什么会出现 `multiple definition`？答：两个强符号（如两处定义同名非 static 函数/已初始化全局）冲突，链接器无法确定用哪个。
2. 强弱符号如何决议？答：强符号优先，多个强符号报错；弱符号（未初始化全局）允许多个，存在强符号则强覆盖弱，否则任选。
3. 静态库链接顺序为何重要？答：`.a` 按需抽取 `.o`，顺序错会导致后出现的库所需符号在前已无法回头抽取。
4. COMDAT 解决什么问题？答：让 C++ 模板/内联的重复强定义合并而非报 multiple definition。
5. `--start-group` 为何能解循环依赖？答：让链接器在同一组内反复扫描直到不再有新的符号被消解。
6. `-fno-common` 为何成为默认？答：把未初始化全局改为强符号，避免两个 TU 同名变量被静默合并导致的隐蔽错误。

## 九、演进与趋势

现代链接器（lld、gold）采用并行节合并与增量链接；LTO（Link-Time Optimization）在链接期重做整个程序的内联与常量传播，模糊了编译与链接边界；`-fvisibility` 控制符号导出面，减小动态符号表。调试信息（DWARF）也在链接期做去重与压缩。

另一条主线是「减小产物与加速链接」：`--gc-sections` + `-ffunction-sections` 擦除死代码；`-Wl,--icf=all` 做相同代码折叠；增量链接（Incremental Linking）把重链接成本降到只处理变更部分。符号决议本身也在演化——lld 在大型工程中用哈希表与并行决议替代单遍线性扫描，使「链接时间」不再是构建链的瓶颈。

## 十、小结

静态链接的本质是符号决议加节布局，强弱符号语义与命令行顺序决定正确性。理解它才能解释链接期各类报错与「为何某些定义被静默选用」。实践中给出两条硬性建议：一是保持命令行「使用者在前、被用者在后」的依赖顺序，必要时才用 `--start-group`；二是统一使用 `-fno-common` 并对跨 TU 的全局符号加前缀或隐藏可见性，把「静默选用」的空间压缩到最小。
