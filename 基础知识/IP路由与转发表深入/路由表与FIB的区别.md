# 路由表与FIB的区别

> 对应 RFC 3222（Terminology for Forwarding Information Base (FIB) based Router Performance）、Kurose & Ross《Computer Networking: A Top-Down Approach》第 5 章（控制平面与数据平面）、RFC 4271（BGP-4）、RFC 2328（OSPFv2），以及 Linux 内核 `fib_lookup` 与 `ip-route(8)` 文档。

## 一、背景与挑战

路由器内部存在两个功能截然不同的平面：控制平面负责「决定怎么走」，数据平面负责「真的把包送出去」。前者需要完整、可分析、可回滚的路由信息全集，包含备选路径、策略属性、未激活候选；后者只需要「对每个目的，当前唯一有效的下一跳与出接口」，且必须在纳秒级完成查表。把这两类需求塞进同一个数据结构会同时伤害双方：控制平面需要的丰富性与可更新性会拖慢转发，转发需要的紧凑与快速会限制策略表达。因此工程上把它们分离为路由信息库（RIB, Routing Information Base）与转发信息库（FIB, Forwarding Information Base）。挑战在于：如何保证 RIB 到 FIB 的映射正确且及时，如何在收敛过程中避免瞬时不一致导致黑洞，以及如何在不同硬件架构下把映射代价控制在可接受范围。

## 二、核心原理

RIB 是控制平面的全部路由信息集合，来源包括：动态协议进程（BGP、OSPF、IS-IS）学习到的路由、管理员配置的静态路由、内核根据接口地址自动生成的直连路由、以及重分发引入的路由。RIB 的特点是可以对同一目的存在多条候选，每条候选带有来源、管理距离、度量、路径属性等元数据。RIB 是「多值」的。

FIB 是数据平面实际用于转发的信息库，特点是对每个目的前缀只保留一条被选定的活动路由，并预计算好转发所需的全部信息：下一跳地址、出接口、二层封装（如 MAC 重写）、以及 ECMP 下一跳组。FIB 是「单值且预计算」的。

映射过程称为「路由选择」或「最佳路径选择」：对每个目的前缀，在 RIB 中按管理距离优先、再按度量比较，选出唯一优胜者，然后连同其下一跳信息一起安装到 FIB。这个过程在主控路由器上由控制平面完成，之后通过内部通道（路由器内部总线、PCIe、或管理协议）下发到线卡的转发引擎，通常表现为编程 TCAM 或 SRAM 表项。

Linux 主机上的情况稍有不同：RIB 与 FIB 同在内核，但逻辑上依然分离。`ip route` 看到的是 RIB 视图（`main` 表及其它表），而 `fib_lookup()` 使用的是一棵经过压缩与预计算的 trie（`fib_trie`），并附带 `fib_nh`（next hop）等预计算结构。当路由发生变化（如链路 down、动态协议通告），内核先更新 RIB，再刷新 FIB 与相关缓存，中间存在一个短暂的不一致窗口。

## 三、形式化与数学基础

设 RIB 为从目的前缀到候选路由集合的映射：

$$ RIB : \text{Prefix} \to \mathcal{P}\!\left(\text{Route}\right) $$

其中 $\mathcal{P}$ 表示幂集。最佳路径选择函数在每条候选上定义一个全序键，通常为字典序：

$$ \text{key}(r) = \left( AD(r),\ \text{metric}(r),\ \dots \right) $$

按 key 升序（管理距离越小越优，度量越小越优）取最小者：

$$ \text{best}(d) = \arg\min_{r \in RIB(d)} \text{key}(r) $$

FIB 即为该映射的像：

$$ FIB = \left\{ \left( d,\ \text{next}(d) \right) \;\middle|\; d \in \text{Prefix},\ \text{next}(d) = \text{best}(d) \right\} $$

注意 $|FIB| \le |RIB|$ 的势关系：RIB 到同一目的可有多条，而 FIB 每目的一条。在多路径场景下，FIB 的条目可以承载一个下一跳集合 $N(d)$，此时转发再做哈希选择：

$$ \text{nexthop}(pkt) = N(d)\left[\, h(pkt) \bmod |N(d)| \,\right] $$

收敛一致性问题可形式化：设 RIB 在 $t_0$ 更新，FIB 在 $t_0 + \delta$ 完成安装，则区间 $[t_0, t_0+\delta]$ 内存在不一致，若该前缀是活跃流量的关键路径，就会出现丢包或环路。减少 $\delta$ 是快速重路由（FRR）的核心目标。

## 四、代码实现

观察 Linux 中 RIB 与 FIB 的不同视图：

```bash
# RIB 视图：全部候选与所有表
ip route show
ip route show table all

# FIB 视角：某个具体目的地址的实际查找结果
ip route get 1.1.1.1

# 内核 FIB trie 的层级结构（压缩后的转发结构）
cat /proc/net/fib_trie | head -30

# 传统简化转发表（仅主表的部分信息）
cat /proc/net/route
```

BGP 路由的典型 RIB 输出中，同目的可能有多行，只有被标记为最优（`>`）的那条才会进入 FIB：

```text
B>  10.20.0.0/16 [20/0] via 192.168.1.1, eth0, 00:12:34
B   10.20.0.0/16 [200/0] via 192.168.2.1, eth1, 00:10:00
```

上面第一条进入 FIB，第二条仅存在于 RIB 作为候选；若第一条撤消，第二条会被重新选出并安装，这正是 RIB 与 FIB 分离带来的收敛与备份能力。

面向 FIB 的性能排查关注三个指标：表项数量、安装延迟（从 RIB 变更到 FIB 生效）、以及 FIB 查找速率。它们分别对应容量、收敛与吞吐三个维度。

## 五、与其他技术对比

| 维度 | RIB（路由表） | FIB（转发表） | 硬件流表（OpenFlow） |
| --- | --- | --- | --- |
| 所在平面 | 控制平面 | 数据平面 | 数据平面（控制器下发） |
| 条目语义 | 多候选、含策略元数据 | 每目的唯一最优 | 匹配域 + 动作 |
| 更新频率 | 高（协议通告驱动） | 中（随最佳路径变化） | 低到中（控制器驱动） |
| 查找要求 | 无需线速 | 必须线速 | 必须线速 |
| 存储介质 | 内存/磁盘 | SRAM/TCAM/专用芯片 | TCAM/SRAM 流水线 |
| 一致性窗口 | 不适用 | 相对 RIB 有短暂滞后 | 相对控制器意图有滞后 |
| 典型规模 | 全部候选 | 活动子集 | 按策略裁剪 |

权衡主线是「完整性与速度的对立」。RIB 追求表达完备以便正确决策与回滚；FIB 追求紧凑与预计算以便线速转发；硬件流表把表达力提升到任意匹配域但把状态管理交给控制器，引入控制通道依赖。

## 六、常见误区

1. 认为改了路由表转发立即生效。某些平台 FIB 编程存在延迟，尤其在分布式路由器下线卡编程较慢时更明显，需要确认安装完成。
2. 认为 FIB 包含全部路由。FIB 只含被选定的活动路由；未激活候选、被策略压制的路由只存在于 RIB。
3. 把 `ip route show` 当作转发结果的权威。它是 RIB 视图，某地址的实际命中需用 `ip route get` 确认。
4. 忽略 RIB 到 FIB 安装期间的不一致窗口。收敛期间可能出现短暂黑洞或环路，关键业务需考虑 FRR 或收敛优化。
5. 认为 RIB 与 FIB 必须同机。分布式路由器中 RIB 在主控卡、FIB 在线卡，二者通过内部通道同步，通道故障会导致转发与控制不一致。
6. 混淆 RIB 的「最优」与转发的「最长前缀」。最优路径选择发生在前缀粒度内，而 LPM 选择哪个前缀参与转发，是两件不同的事。

## 七、与开源书·权威来源对应

- RFC 3222：明确给出 RIB 与 FIB 的术语定义与基于 FIB 的路由器性能术语框架。
- Kurose & Ross《Computer Networking: A Top-Down Approach》第 5 章：控制平面与数据平面的划分，以及「路由选择」与「转发」的区分。
- Tanenbaum & Wetherall《Computer Networks》：路由表组织与转发过程。
- RFC 4271（BGP-4）与 RFC 2328（OSPFv2）：RIB 的两大主要来源协议及其决策过程。
- Linux 内核 `fib_lookup` 与 `ip-route(8)`：Linux 中 RIB/FIB 的实现与观察方式。
- McKeown et al. 2008（OpenFlow）：把 RIB 逻辑上收到控制器、FIB 留在交换机的先例。

## 八、面试题

1. 为什么 RIB 和 FIB 要分开？
   要点：RIB 保存全部策略与备选以便收敛计算与回滚，FIB 只保留预计算的最优结果以提升查表速度与硬件下发效率；分离让二者各自优化。

2. RIB 到 FIB 的映射依据是什么？
   要点：对每个目的前缀按管理距离优先、度量次优（再按路径属性）选出唯一优胜者，并预计算下一跳与二层封装后安装。

3. RIB 与 FIB 的大小关系如何？
   要点：$|FIB| \le |RIB|$，因为同一目的可有多条候选而 FIB 每目的只保留一条（多路径时表现为一个下一跳组）。

4. RIB/FIB 分离带来什么新问题？
   要点：安装延迟造成的不一致窗口可能在收敛期间产生黑洞或环路，需要快速重路由、优雅重启等机制缓解。

5. 分布式路由器中二者如何部署？
   要点：RIB 位于主控卡承担全部计算，FIB 由主控下发到各线卡的转发芯片，通道故障会造成控制与转发状态脱节。

## 九、演进与趋势

演进有两条主线。一是控制的集中化：SDN 把 RIB 逻辑上收到控制器，交换机只保留 FIB 与流表，用全局视角获得更好的策略一致性与流量工程能力；OpenFlow 与 P4 提供可编程的下发接口。二是数据的本地化与智能化：为了降低控制器依赖，出现「控制器下发意图 + 本地快速重路由」的分层设计，以及在网卡/DPU 上卸载 FIB 查找以减轻 CPU。同时 IPv6 使 FIB 规模更大、前缀更长，推动更紧凑的表结构与更高效的安装协议（如更细粒度的增量更新与批量编程）。此外，可编程数据平面允许在同一流表中表达多种匹配类型，使 FIB 的概念从「纯目的前缀表」扩展为「多级匹配-动作流水线的第一级」。

## 十、小结

RIB 是控制平面的全量候选集合，携带策略与备选，追求表达完备；FIB 是数据平面的最优活动集合，预计算好转发所需的一切，追求线速查表。二者的分离是路由器架构的基本设计，用一致性窗口这一代价换来了策略完整性与转发性能的双赢。实践中必须牢记三点：FIB 是 RIB 的子集、`ip route show` 是 RIB 视图而非转发结果、以及 RIB 变更到 FIB 生效之间存在需要关注的安装延迟。
