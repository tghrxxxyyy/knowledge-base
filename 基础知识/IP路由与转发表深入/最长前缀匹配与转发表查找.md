# 最长前缀匹配与转发表查找

> 对应 RFC 4632（Classless Inter-domain Routing, CIDR）、RFC 791（Internet Protocol）、Tanenbaum & Wetherall《Computer Networks》第 5 章（网络层）、Kurose & Ross《Computer Networking: A Top-Down Approach》转发章节。

## 一、背景与挑战

IP 转发时，一个目的地址可能同时匹配路由表中的多条前缀：例如同时命中 `10.0.0.0/8`、`10.1.0.0/16` 和 `10.1.2.0/24`。若随意选择其中一条，流量就会走向错误的方向——更具体的路由往往代表更精确的策略（专线、特殊出口、内部子网），被聚合前缀抢走会导致策略失效甚至黑洞。因此转发规则被明确定义为「最长前缀匹配」（Longest Prefix Match, LPM）：在所有匹配的前缀中，选择掩码位数最多的那一条。这个看似简单的规则带来三重挑战：一是必须高效地在变长前缀集合中求出最具体匹配，而非首个匹配；二是表规模持续增长到百万级，查找必须保持线速；三是更新（BGP 通告与撤消）必须能在不中断转发的前提下完成。

## 二、核心原理

路由表由（前缀，掩码长度，下一跳）三元组构成，本质是一棵以地址位为路径的隐式树：每个前缀对应树中一个节点，前缀长度就是节点深度。LPM 的目标是找到包含目的地址的所有路径节点中最深的那个。默认路由 `0.0.0.0/0` 对应树根，是所有路径的公共前缀，因此它是天然的兜底项，而不是优先级最高的项——这是一个极常见的方向性误解。

转发时，路由器先对目的地址做 LPM，得到下一跳与出接口，再据此封装二层帧发出。若查表失败（无任何前缀匹配）且没有默认路由，报文被丢弃并可能回送 ICMP 目的不可达。

CIDR 是 LPM 存在的制度前提。在 CIDR 之前，地址按 A/B/C 类划分，前缀长度固定，转发只需按类别取固定位数比较，甚至可以用哈希精确匹配；引入变长前缀后，精确匹配不再可行，必须做前缀匹配并按长度选优。这一变化催生了整个「地址查找算法」研究领域，也推动硬件从哈希表转向 trie 与 TCAM。

## 三、形式化与数学基础

设候选前缀集合 $P = \{(p_i, l_i)\}$，其中 $p_i$ 是长度为 $l_i$（$0 \le l_i \le W$）的前缀，目的地址为 $d$，地址位宽 $W$。匹配判定为：

$$ \text{match}(p_i, l_i, d) \iff \left( d \gg (W - l_i) \right) = \left( p_i \gg (W - l_i) \right) $$

等价地，用掩码 $M(l) = \underbrace{1\cdots1}_{l}\underbrace{0\cdots0}_{W-l}$ 表达为：

$$ (d \;\&\; M(l_i)) = p_i $$

最优（最具体）匹配为：

$$ p^* = \arg\max_{i:\ \text{match}(p_i, l_i, d)} l_i $$

LPM 的树视图给出一个有用性质：沿地址位逐位下降时，遇到的每个「前缀节点」都是候选，最终必须选深度最大的那个。因此算法设计的关键是「如何在下降过程中不遗漏更深候选」，这直接决定了为什么简单地在第一个命中处返回是错的。

若把前缀集映射到长度为 $W$ 的位串全集的划分，则对地址 $d$，命中最深前缀等价于对 $d$ 的每个 $l$ 计算 $d$ 的前 $l$ 位是否在前缀表中出现，取最大的 $l$：

$$ l^* = \max\left\{ l \;\middle|\; \text{prefix}_l(d) \in \mathcal{L} \right\} $$

朴素实现需要检查所有 $W+1$ 个长度层，这是线性代价的来源；多比特 trie 与 TCAM 都是为了压缩这一过程。

## 四、代码实现

朴素 LPM（清晰但线性，仅用于理解语义）：

```python
def mask(l):
    return 0xFFFFFFFF << (32 - l) & 0xFFFFFFFF if l > 0 else 0

def lpm(routes, dst):
    # routes: [(prefix, plen, nexthop), ...]
    best = None
    for prefix, plen, nh in routes:
        if (dst & mask(plen)) == (prefix & mask(plen)):
            if best is None or plen > best[0]:
                best = (plen, nh)
    return best[1] if best else None
```

内核与用户态验证：

```bash
# 查看全部路由（RIB 视图）
ip route show

# 查询某目的地址最终会命中哪条路由（触发 FIB 查找）
ip route get 8.8.8.8

# 带源地址与入接口的查找，用于验证策略交互
ip route get 8.8.8.8 from 10.0.0.5 iif eth0

# 查看内核压缩 trie 结构与层级
cat /proc/net/fib_trie | head -30
```

`ip route get` 的输出会明确给出 `via`、`dev`、以及是否经过某张非主表，这是判断 LPM 结果的唯一可靠方式，比肉眼比对 `ip route show` 的输出更准确。

## 五、与其他技术对比

| 匹配类型 | 结构 | 匹配语义 | 更新代价 | 典型用途 |
| --- | --- | --- | --- | --- |
| 精确匹配（exact） | 哈希表 | 全字段相等 | 低 | MAC 表、ARP 缓存、连接跟踪 |
| 最长前缀匹配（LPM） | trie / TCAM | 最长掩码匹配 | 中到高 | IPv4/IPv6 路由表 |
| 三元匹配（ternary） | TCAM | 0/1/don't-care | 高 | ACL、流分类、LPM |
| 范围匹配（range） | TCAM / 专用结构 | 区间比较 | 高 | 端口范围、策略 |
| 通配位匹配 | 掩码哈希 | 按掩码比较 | 低 | 简单流表 |

核心差异在于「匹配的唯一性」。精确匹配可以靠哈希常数时间完成，因为只有一个候选；LPM 存在多个候选且必须选最具体的，无法用哈希直接表达，必须维护序关系，因此结构必然更复杂、更新更贵。

## 六、常见误区

1. 认为路由表按书写顺序匹配首条命中的条目。转发只看前缀长度，与配置顺序、表内排列完全无关。
2. 认为默认路由优先级最高。`0.0.0.0/0` 掩码最短，是最后兜底的规则，任何更具体前缀命中都会覆盖它。
3. 认为掩码可以任意（非连续）。标准 LPM 要求掩码为连续的前导 1，非连续掩码由 AC 列表用三元匹配表达，不属于 LPM。
4. 混淆「匹配」与「选优」两步。同时命中多条是常态，错误在于没有按最长前缀选优，而不是匹配本身出错。
5. 用 `ip route show` 的输出去推断转发结果。它展示的是全部候选，而非某地址的实际命中项，应使用 `ip route get`。
6. 忽略源地址与入接口对查找的影响。存在策略路由或多张表时，仅按目的地址推断结果会得出错误结论。

## 七、与开源书·权威来源对应

- RFC 4632：CIDR 的定义、前缀聚合与「最具体匹配优先」的转发语义。
- RFC 791：IP 协议本体与转发基本规则，理解默认路由兜底语义的基础。
- Tanenbaum & Wetherall《Computer Networks》第 5 章：网络层转发与路由表组织。
- Kurose & Ross《Computer Networking: A Top-Down Approach》：转发与路由选择的区别、最长前缀匹配的说明。

## 八、面试题

1. 目的地址同时匹配 /24 和 /16，应选哪条？
   要点：选 /24。掩码更长表示更具体、更精确的策略，这就是最长前缀匹配原则，与配置顺序无关。

2. 默认路由在 LPM 中的位置如何理解？
   要点：`0.0.0.0/0` 掩码长度为零，是所有地址的公共前缀，因此只在没有任何更具体前缀命中时才生效，是兜底而非优先。

3. 为什么 LPM 不能用哈希表实现？
   要点：哈希只支持精确匹配，无法表达「命中多个候选并选最具体」的序关系；必须用保持前缀层次的结构（trie/TCAM）或分层查找。

4. 为什么说「先匹配到就返回」是错的？
   要点：地址可能同时匹配多条前缀，先遇到的可能不是最长的那条（若按地址位递减遍历，浅前缀先出现），必须持续下降到没有更深匹配为止。

5. 掩码必须连续吗？
   要点：标准 LPM 要求掩码为连续前导 1；非连续掩码由三元匹配（TCAM/ACL）表达，属于通用匹配而非 LPM。

## 九、演进与趋势

表规模增长是长期驱动力：IPv4 全球路由表已远超数十万条，IPv6 前缀长度翻倍且数量持续上升，这推动 LPM 结构从简单二叉 trie 演进到多比特 trie、LC-trie、二分搜索与位图混合方案，硬件则从纯 SRAM 算法走向流水线化 SRAM trie 与 TCAM 并行匹配。另一条主线是匹配语义的扩展：SRv6 把转发语义从「目的前缀」扩展到段路由标签序列，使路径信息可携带在报文中；可编程数据平面（P4/RMT）让 LPM 与其他匹配类型共存于同一流水线，支持一条流水线上同时做目的前缀、五元组与 ACL 匹配。可以预见，LPM 仍将是转发面最核心的匹配操作，但其实现会持续向「压缩 + 流水 + 分区」方向发展。

## 十、小结

最长前缀匹配是 IP 转发的核心查表规则：在所有与目的地址匹配的前缀中选掩码最长的那一条，保证最具体路由优先于聚合路由，默认路由则作为最后兜底。理解「匹配」与「选优」是两个独立步骤、理解掩码长度与具体性的对应关系、并习惯用 `ip route get` 而非 `ip route show` 验证结果，是排查路由选择问题的三项基本功。
