# 路由查找算法与硬件转发

> 对应 Ruiz-Sanchez, Biersack & Dabbous 2001《Survey and Taxonomy of IP Address Lookup Algorithms》、Srinivasan & Varghese 1999（Controlled Prefix Expansion）、Waldvogel et al. 1997（Scalable High Speed IP Routing Lookups）、Morrison 1968（PATRICIA）、RFC 4632（CIDR）。

## 一、背景与挑战

核心路由器的转发面要在每条链路上以线速完成最长前缀匹配（LPM）：在数十万到上百万条变长前缀中，找出与目的地址匹配且掩码最长的那一条。三个约束同时施压：查表延迟必须小于一个最小包时间，存储必须容纳持续增长的 IPv6 表（128 位前缀使深度翻倍），更新必须承受 BGP 撤消/通告的突发。软件算法与硬件结构的选择，本质是在「查找延迟、存储占用、更新复杂度」之间的三角权衡。

## 二、核心原理

软件侧的主流思路是把变长前缀的比较转化为对地址位串的遍历。基本二叉 trie 每层检查一位，深度等于地址位数（IPv4 为 32）；Patricia trie 合并只有单个孩子的节点并把「跳过位数」记录在节点中，深度降到与不同分支数成正比。多比特 trie（controlled prefix expansion）每次检查 $k$ 位，把变长前缀展开成若干定长前缀副本，使每层是 $2^k$ 路分支，深度降到约 $\lceil 32/k \rceil$，代价是前缀被复制多份。LC-trie 对路径与层级同时压缩，是 Linux `fib_trie` 的基础。

硬件侧的主流是 TCAM（Ternary Content Addressable Memory）：每个单元能存 0、1 或 don't-care，整表并行比较，一个时钟周期得到全部匹配结果，再用优先级编码器选出最长前缀。它把「多步遍历」变成「一步并行匹配」，代价是单元面积约为 SRAM 的数十倍、整表翻转导致功耗极高、容量受限，且更新需移位或预留空位。介于两者之间的是基于 SRAM 的流水线 trie 与可编程交换机的匹配-动作流水线。

理解 LPM 的复杂度来源是关键：难点不在「比较」，而在多条同时匹配时选出最具体的那一条，这要求结构本身保持前缀之间的序关系。

## 三、形式化与数学基础

设地址位宽 $W$（IPv4 为 32，IPv6 为 128），每步检查 $k$ 位，则多比特 trie 最大深度与存储膨胀因子为：

$$ D = \left\lceil \frac{W}{k} \right\rceil, \qquad \text{factor} \approx 2^{k} $$

这是选择 $k$ 的核心矛盾：$k$ 越大查表越快，但存储膨胀指数上升。工程上常用 $k=4$ 到 $8$，并对稀疏层使用不等步长。

TCAM 的并行匹配条件为，对表项 $i$ 的（key，mask）与目的地址 $d$：

$$ \text{match}_i = \left( (d \;\&\; \text{mask}_i) = (\text{key}_i \;\&\; \text{mask}_i) \right) $$

最终按优先级编码器给出最长匹配：

$$ p^* = \arg\max_{i:\ \text{match}_i} |\text{prefix}_i| $$

管道化 SRAM trie 的查表时间为 $T \approx D \cdot T_{stage}$，与表规模无关但随级数增长；TCAM 为 $T \approx T_{parallel} + T_{encoder}$，与表项数近似无关，这正是它被用于核心设备的根本原因。

## 四、代码实现

概念性的多比特 trie 查表（`step` 为每层检查位数）：

```python
class Node:
    __slots__ = ("children", "best")
    def __init__(self):
        self.children = {}
        self.best = None      # 该路径上已遇到的最长前缀的下一跳

def lookup(root, addr, step=8):
    node, best, shift = root, root.best, 32 - step
    while shift >= 0 and node is not None:
        bits = (addr >> shift) & ((1 << step) - 1)
        node = node.children.get(bits)
        if node is not None and node.best is not None:
            best = node.best        # 越深前缀越长，直接覆盖
        shift -= step
    return best
```

观察真实实现——Linux 内核按层级压缩后的 trie：

```bash
cat /proc/net/fib_trie | head -40    # 缩进表示层级，/32 标注叶节点前缀长度
ip route get 8.8.8.8                 # 查看某地址的实际查找结果
```

`/proc/net/fib_trie` 的缩进结构是理解「路径压缩如何在真实实现中落地」的直观素材。

## 五、与其他技术对比

| 结构 | 查表延迟 | 存储占用 | 更新代价 | 功耗 | 典型部署 |
| --- | --- | --- | --- | --- | --- |
| 二叉 trie | 与 $W$ 成正比 | 中 | 低 | 低 | 早期软件实现 |
| Patricia / LC-trie | 与分支数相关 | 较小 | 中 | 低 | 通用软件转发 |
| 多比特 trie | 与 $W/k$ 成正比 | 膨胀 $2^k$ 倍 | 中 | 低 | 高吞吐软件转发 |
| 管道化 SRAM trie | 与级数成正比，可流水 | 中 | 中 | 中 | NPU、可编程交换 |
| TCAM | 近似常数（单周期） | 极小容量、极贵 | 高 | 极高 | 核心路由器 |

选择原则：软件转发靠算法在通用 CPU 上取得可接受吞吐；硬件转发靠结构与并行度换线速。TCAM 为速度牺牲容量、功耗与更新灵活性，SRAM 算法结构为容量与更新灵活性牺牲部分速度。

## 六、常见误区

1. 认为软件路由一定慢。多核 CPU 配合压缩 trie、批处理与 SIMD 位操作可达很高转发率，中小规模场景完全够用。
2. 认为 TCAM 无所不能。表项数受限、功耗极高，更新频繁时显著降速，IPv6 前缀会迅速吃满容量。
3. 混淆「前缀长度」与「树深度」。压缩后二者不成正比，深度由分支结构决定。
4. 忘记更新路径的代价。BGP 抖动带来的批量更新可能比查找本身更影响稳定性。
5. 认为多比特 trie 没有代价。存储膨胀是实打实的，$k$ 增大时内存可能翻数倍，影响缓存命中率。
6. 忽略 IPv6 的维度变化。位宽从 32 到 128，二叉 trie 深度翻四倍，TCAM 宽度与功耗大幅上升。

## 八、面试题

1. TCAM 为什么能单周期完成最长前缀匹配？
   要点：所有表项并行比较，don't-care 位由掩码实现，匹配结果经优先级编码器按前缀长度选最长，无需逐层遍历。

2. 多比特 trie 中步长 $k$ 如何取舍？
   要点：$k$ 增大使深度 $\lceil W/k \rceil$ 减小（更快），但存储膨胀约 $2^k$ 倍并降低缓存友好性，常用 4~8 并按层稀疏度调整。

3. Patricia trie 相比普通二叉 trie 改进在哪里？
   要点：合并单分支路径并记录跳过位数，使深度与分支数相关而非与地址位数相关，显著降低平均访问次数。

4. 为什么路由器要区分控制平面与转发平面的查找结构？
   要点：控制平面维护全量候选并承担策略计算；转发平面只需最优活动集合，用更紧凑、更快但不易更新的结构实现线速查表。

5. IPv6 对查找结构带来什么挑战？
   要点：前缀宽度从 32 位增到 128 位，树深度与 TCAM 宽度大幅增加；表规模更大、更新更频繁，需要更强的压缩与分区策略。

## 九、演进与趋势

软件侧的趋势是把算法与内存层次协同优化：压缩 trie 配合大页、预取与批处理，用 SIMD 做多位并行比较，用 Bloom filter 预过滤无效访问。硬件侧的趋势是可编程数据平面：P4 与 RMT 让匹配-动作表可按业务定义并保持线速，智能网卡与 DPU 把 FIB 卸载到网卡侧减轻 CPU。另一条主线是匹配类型的融合：现实转发常需「五元组精确匹配 + 目的前缀 LPM + ACL 三元匹配」组合，因此结构上倾向多级流水线，每级做一类匹配。长期看，TCAM 因功耗与容量限制会更多退守到小规模高优先级表，大规模 LPM 由 SRAM 算法结构与流水线硬件承担。

## 十、小结

路由查找的本质是在变长前缀集合中快速选出最长匹配。软件以压缩 trie（Patricia/LC-trie/多比特 trie）在延迟、存储与更新之间取得平衡，硬件以 TCAM 用面积与功耗换取近乎常数的查表时间。理解深度 $D=\lceil W/k \rceil$ 与膨胀因子 $2^k$ 的取舍，以及 TCAM 的并行匹配加优先级编码原理，是评估任何转发方案性能与成本的共同基础。
