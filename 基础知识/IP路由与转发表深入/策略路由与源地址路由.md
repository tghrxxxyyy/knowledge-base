# 策略路由与源地址路由

> 对应 RFC 1102（Policy Routing in Internet Protocols）、RFC 791（Internet Protocol）、Linux `ip-rule(8)`/`ip-route(8)` 手册、Linux Advanced Routing & Traffic Control HOWTO（LARTC），以及 McKeown et al. 2008（OpenFlow）。

## 一、背景与挑战

普通 IP 转发只依据目的地址查一张表，这种「目的决定一切」的模型在多宿主主机、多出口企业网、按业务分流的 VPN 场景下立刻失效：同一个目的地址，来自内网 A 的流量应该走电信出口，来自内网 B 的应该走联通；访问内网资源的流量走隧道，访问公网的流量走本地直连。这些需求无法用单一目的路由表表达。更深层的挑战是：一旦允许按多维度条件选路，就必须处理随之而来的问题——规则之间的优先级如何定义、规则数量增长后查表开销如何控制、正向与反向路径如何保持对称、以及缓存一致性如何维护（早期内核的路由缓存会让新加的规则看似不生效）。

## 二、核心原理

Linux 的策略路由由两部分组成：规则库（Routing Policy Database, RPDB）与多张路由表。内核转发时的顺序是：先遍历 RPDB 中的规则，找到第一条匹配当前报文的规则，取出它指向的路由表号；再到该表中按目的地址做最长前缀匹配。这与传统模型的关键区别在于「选表」被提前了，而且选表的依据可以是源地址、入接口、fwmark 标记、TOS/DSCP、甚至 uid/gid 等。

规则有三类动作：查某张表（`lookup TABLE`）、直接返回不可达（`unreachable`）、直接丢弃（`blackhole`/`prohibit`）。默认规则通常包含 `local`（本地地址表）、`main`（主表）和 `default`（兜底）。优先级由 `pref` 数值决定，数值越小越先被检查，管理员可以用插入位置（`pref`）精确控制顺序。

选表的条件组合构成策略的表达力。`from` 匹配源前缀，`iif` 匹配入接口，`fwmark` 匹配由 netfilter 打上的标记（这使 iptables/nftables 的分类结果可以驱动路由选择），`tos` 匹配 TOS/DSCP。将这些条件组合，就能实现「来自某网段 + 特定标记的流量走 VPN 表，其余走主表」这类典型需求。

与之配套的是规则生效时机与缓存问题：现代内核（较新版本）已移除按流缓存的路由缓存，改为更精细的 per-CPU 或 nexthop 缓存，因此新增规则通常立即生效；但在仍带路由缓存的内核上，必须显式刷新缓存，否则旧流仍按旧规则转发，看起来像「配置没生效」。

## 三、形式化与数学基础

RPDB 是一个按优先级全序排列的规则集 $R = \{r_1 \prec r_2 \prec \dots \prec r_m\}$，其中 $\prec$ 表示优先级（pref 越小越靠前）。每条规则 $r_i$ 包含选择器谓词 $S_i$ 与目标表 $T_i$（或终结动作）。转发决策可形式化为：

$$ k = \min\left\{ i \;\middle|\; S_i(pkt) = \text{true} \right\} $$

$$ \text{nexthop}(pkt) = \text{FIB}_{T_k}.\text{LPM}(dst) $$

若 $k$ 不存在，则回落到默认规则（通常指向 default 表）。注意 $S_i$ 是合取谓词，例如：

$$ S_i(pkt) = \left[ src \in P_i \right] \wedge \left[ iif = I_i \right] \wedge \left[ fwmark = M_i \right] $$

匹配开销随规则条数线性增长，因此实践中的优化方向是把最常用的规则放在最前、用 fwmark 把复杂判断一次性算好，从而避免在数据路径上重复多次前缀比较。规则条数为 $m$、平均前缀比较代价为 $c$ 时，单包选表开销近似为：

$$ T_{policy} \approx \sum_{i \le k} \left( c_{S_i} \right) + T_{LPM} $$

这也是「规则越多越慢」的定量来源，通常规则数控制在数十条以内。

## 四、代码实现

源地址策略路由：来自 192.168.10.0/24 的流量走另一张表，该表默认指向隧道：

```bash
# 1. 建规则：按源地址指向表 100
ip rule add from 192.168.10.0/24 table 100 pref 1000

# 2. 在表 100 中配置默认路由
ip route add default via 10.0.0.1 dev tun0 table 100

# 3. 表 100 中若需访问本地内网，另加一条直连路由
ip route add 192.168.0.0/16 dev eth1 table 100

# 4. 查看规则与表
ip rule show
ip route show table 100

# 5. 触发一次查找，确认命中哪条规则
ip route get 8.8.8.8 from 192.168.10.10 iif eth1
```

基于 fwmark 的策略路由（由 netfilter 分类后驱动）：

```bash
# 用 nftables 给特定流量打标记（0x1 表示走 VPN）
nft add table inet mangle
nft add chain inet mangle prerouting '{ type filter hook prerouting priority mangle; }'
nft add rule inet mangle prerouting ip daddr 10.0.0.0/8 meta mark set 0x1

# 按标记选择表 200
ip rule add fwmark 0x1 table 200 pref 2000
ip route add default via 10.0.0.1 dev tun0 table 200
```

清理与排查：

```bash
ip rule del from 192.168.10.0/24 table 100
ip route flush cache          # 老旧内核需要，现代内核通常无路由缓存
```

## 五、与其他技术对比

| 机制 | 匹配维度 | 表达力 | 查表开销 | 状态维护 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| 普通目的路由 | 目的前缀 | 弱 | 一次 LPM | 无 | 单出口主机、常规转发 |
| RPDB 策略路由 | 源/接口/fwmark/TOS | 中强 | 规则遍历 + LPM | 无 | 多宿主、分流、VPN |
| netfilter + mark | 任意五元组与状态 | 强 | 规则链匹配 | 连接跟踪 | 分类与标记 |
| eBPF/XDP | 可编程、任意字段 | 很强 | 取决于程序 | 可维护 map | 高性能分流与负载均衡 |
| SDN 集中控制 | 全局策略 | 很强 | 硬件流表 | 控制器 + 交换机状态 | 云网络、数据中心 |

核心权衡是「表达力与数据路径开销」。普通路由开销最低但维度单一；策略路由用规则遍历换来多维度；netfilter 与 eBPF 把表达能力推到最强（可编程），代价是程序复杂度、状态维护与性能调优成本。实际系统常把三者叠加：eBPF/netfilter 做分类与标记，RPDB 做选表，多张表做具体转发。

## 六、常见误区

1. 认为 `ip rule` 本身就完成转发。规则只负责「选哪张表」，真正的下一跳仍来自该表的 LPM 结果；表里没有路由就依然不可达。
2. 配置后不刷新缓存导致看似不生效。带路由缓存的旧内核中，已建立的流不会重新走规则遍历，需 `ip route flush cache`。
3. 忽略反向路径。只配了出向策略而没配入向或对端回程路径，会形成单向通而反向丢包，通常被误判为防火墙问题。
4. 规则顺序颠倒导致策略失效。`pref` 越小越先检查，若把宽泛规则放在前面，后面的精细规则永远不会命中。
5. 认为 fwmark 是普通字段。fwmark 由内核内部产生（netfilter、socket 选项或 eBPF），用户配置必须与打标记的地方严格一致，否则规则永远不会命中。
6. 规则条数无节制增长。规则遍历是线性开销，几十条以上就要考虑用 fwmark 归并或用 eBPF 重写。

## 七、与开源书·权威来源对应

- RFC 1102（1989）：策略路由的概念框架，讨论如何按策略而非仅按目的选路。
- RFC 791：IP 转发的基本模型，是理解「目的路由」基线的前提。
- Linux `ip-rule(8)` 与 `ip-route(8)` 手册：RPDB 的规则语义、动作类型与表号约定。
- Linux Advanced Routing & Traffic Control HOWTO：多表、标记与分流的实战配置范式。
- McKeown et al. 2008（OpenFlow）：把策略集中到控制器的思想来源。
- Cilium/eBPF 文档（BPF 与 XDP Reference Guide）：可编程数据路径替代部分 RPDB 能力的实践参考。

## 八、面试题

1. 如何让来自内网 A 的流量走电信、内网 B 的流量走联通？
   要点：用两条 `ip rule` 分别按源地址指向两张路由表，各表配置不同的默认网关；注意规则 pref 顺序与反向路径。

2. `ip rule` 与 `ip route` 的分工是什么？
   要点：rule 负责按多维条件选择「用哪张表」，route 负责在该表内按目的地址做最长前缀匹配；两者是先后两级决策。

3. fwmark 策略路由的典型用法与前提是什么？
   要点：先用 netfilter 或 socket 选项给报文打标记，再用 `ip rule add fwmark` 按标记选表；前提是打标记与匹配标记的值必须严格一致。

4. 为什么加了规则却感觉不生效？
   要点：旧内核有路由缓存，已建立的流不再重新遍历规则，需刷新缓存；也可能是规则顺序被宽泛规则提前命中。

5. 策略路由与 SDN 的关系？
   要点：两者都突破「仅按目的转发」的限制；策略路由把决策留在本机内核，SDN 把决策集中到控制器下发流表，后者全局视角更强但依赖控制器可用性。

## 九、演进与趋势

演进的主线是把策略决策从「规则遍历」迁移到「可编程数据路径」。eBPF 与 XDP 允许在内核态、甚至在驱动收包最早阶段执行自定义逻辑，直接读取任意头部字段、维护 map 状态并输出转发决策，性能与表达力远高于 RPDB；这使得传统策略路由在前沿场景中逐渐成为兜底机制。同时，云厂商用 VPC 路由表与安全组在租户级别实现策略，SDN 控制器统一编排；容器网络则用 CNI 插件把策略下沉到 veth 与 eBPF 程序。可以预期的长期格局是：分类与标记由 eBPF/netfilter 承担，选表由 RPDB 承担，精细转发与隔离由可编程数据平面承担，三者分层协作而非互相取代。

## 十、小结

策略路由以规则库 RPDB 按源地址、入接口、fwmark、TOS 等多维条件选择路由表，突破了「仅按目的地址查表」的限制，是多宿主、多出口分流与 VPN 分流的核心手段。实现时必须同时关注四件事：规则优先级顺序、表内路由是否完备、反向路径是否对称、以及缓存是否刷新。理解 rule 与 route 的两级分工，是排障时最快定位问题的方法。
