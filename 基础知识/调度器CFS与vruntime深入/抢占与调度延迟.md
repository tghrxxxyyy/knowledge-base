> 对应 Linux 内核 Documentation（scheduler/）与 Intel SDM 卷3 的「任务切换」背景。

## 一、背景与挑战
一个高优先级/被唤醒的任务应尽快运行，但内核代码可能处于不可抢占区段。挑战是界定「何时可以抢占」，在保证内核数据一致性的前提下把调度延迟降到最低。

## 二、核心原理
Linux 支持自愿抢占（cond_resched）与可抢占内核（PREEMPT）。在 CFS 中，唤醒新任务时若其 vruntime 显著小于当前任务，标记 TIF_NEED_RESCHED；在返回用户态/内核抢占点时检查该标志并调用 schedule 完成切换。抢占延迟取决于最长不可抢占区段与 tick 粒度。实时（PREEMPT_RT）进一步把自旋锁改为可睡眠锁，缩短不可抢占窗口。

## 三、形式化与数学基础
调度延迟 L 的上界近似：
```
L <= max(不可抢占区段时长) + tick_granularity + ctx_switch_cost
```
唤醒抢占条件（简化）：
```
if (wakee->vruntime + wakeup_granularity < curr->vruntime)
    set_tsk_need_resched(curr)
```
wakeup_granularity 防止过于频繁的微小抢占（thrashing）。

## 四、代码实现
```c
// kernel/sched/core.c（简化）
static void check_preempt_wakeup(struct rq *rq, struct task_struct *p)
{
    if (wakeup_preempt_entity(se_of(p), &curr->se) == 1) {
        resched_curr(rq);     // 设 TIF_NEED_RESCHED
    }
}
// 返回用户态/抢占点
if (test_thread_flag(TIF_NEED_RESCHED))
    schedule();               // 实际切换
```

## 五、与其他技术对比
- 非抢占内核：延迟高、实现简单。
- PREEMPT（自愿+可抢占）：通用桌面/服务器折中。
- PREEMPT_RT：接近硬实时，锁可抢占。
- 协作式：仅自愿让出，延迟最不可控。

## 六、常见误区
- 误区：PREEMPT 让任何时刻都可切换。仍有关中断区段与原子上下文不可抢占。
- 误区：调度延迟只由 tick 决定。不可抢占区段往往贡献更大。

## 九、演进与趋势
从 2.4 非抢占到 2.6 可抢占；PREEMPT_RT 主线化（6.x 起逐步合并）使实时抢占成为通用能力；EAS 在移动端按能效触发唤醒。

## 十、小结
抢占机制在「内核一致性」与「低调度延迟」间平衡，TIF_NEED_RESCHED 标记 + 抢占点检查是现代 Linux 响应式调度的关键。
