# MPTCP 拥塞控制耦合

> 对应 RFC 6356《Coupled Congestion Control for Multipath Transport Protocols》与 RFC 8684 第 3.4 节相关要求，背景可参考 Kleppmann《Designing Data-Intensive Applications》关于资源公平的讨论。

## 一、背景与挑战
MPTCP 最诱人也最危险的特性是「多路径」。如果让每条子流各自独立地跑标准拥塞控制，会出问题：设想瓶颈链路是共享的，一条 MPTCP 连接开了 $n$ 条子流都经过它，那么这条连接就会像 $n$ 条竞争流一样抢占带宽，比单路径 TCP 多占数倍份额。

后果有两层：

- 公平性破坏：合规的 TCP 流被 MPTCP 挤压，网络退化为「谁开多路径谁占优」，损害整体效率。
- 拥塞加剧：多占的带宽并非来自空余容量，而是从别的流手里抢来，整体吞吐不升反降，甚至引发更多丢包。

因此必须把各子流的拥塞窗口「耦合」起来，使 MPTCP 在共享瓶颈上的行为大体等价于一条正常 TCP 流，同时仍能利用真正空闲的路径。

## 二、核心原理
耦合拥塞控制的核心思想是：子流本地调整，但受一个全局约束。

- 每条子流仍按其自身的 RTT 与丢包事件调整本地 cwnd，从而适配各自路径的特性。
- 引入耦合因子 $\alpha_i$，决定子流 $i$ 在拥塞避免阶段的增长权重。
- $\alpha_i$ 由全局吞吐目标与各子流的 RTT/吞吐份额共同推导，使所有子流的聚合响应等效于单路径 TCP。
- 结果：RTT 小、质量好的路径获得更多增长（更快派发数据），RTT 大、质量差的路径增长受限，但整体不超额占用瓶颈。

RFC 6356 给出的正是这套「Linked Increases Algorithm」（LIA）框架，RFC 8684 在多路径拥塞控制章节引用并约束其行为。直觉上，它类似把「多条流」虚拟成「一条流」来做公平竞争。

## 三、形式化与数学基础
定义子流 $i$ 的瞬时吞吐为：

$$ w_i = \frac{cwnd_i}{RTT_i},\qquad W = \sum_{j=1}^{n} w_j $$

耦合目标可表述为：在共享瓶颈上，聚合吞吐应大体不劣于、也不显著优于一条等效单流。RFC 6356 的做法是在拥塞避免阶段令每条子流每 RTT 的窗口增量为：

$$ \Delta cwnd_i = \frac{\alpha_i \cdot MSS^2}{cwnd_i} $$

其中 $\alpha_i$ 由全体子流的吞吐与 RTT 推导，其取值使下式成立：

$$ \sum_{i=1}^{n} \alpha_i \cdot \frac{1}{w_i} \ \propto\ \text{（单流等效增量）} $$

$\alpha_i$ 的精确表达式与推导以 RFC 6356 官方文本为准；其定性行为是：吞吐份额 $w_i/W$ 越大的子流权重越高，RTT 越大的子流增长越受抑制。

拥塞事件到来时，子流按各自算法（如类 Reno/CUBIC 的响应）减小窗口，但任何一条子流发生丢包都会向「连接级」反馈，避免其他子流继续无约束增长。韧性上，整体可用带宽满足：

$$ BW_{total} \le \sum_{i=1}^{n} BW_i $$

而在共享瓶颈处，聚合份额被约束在约一条流的量级，这正是耦合的意义。

## 四、代码实现
以下为简化示意，用于说明耦合思想；生产实现（如 Linux 内核的 mptcp 拥塞控制）应以内核源码与 RFC 6356 为准。

```python
# 简化耦合示意：按吞吐份额与 RTT 分配增长权重
def coupled_increase(subflows, mss=1460):
    for s in subflows:
        w = s.cwnd / s.rtt            # 子流吞吐
        totals = sum(x.cwnd / x.rtt for x in subflows)

        if totals <= 0:
            continue
        # 份额越大、RTT 越小，权重越高（简化形式）
        share = w / totals
        alpha = share

        # 拥塞避免：每 RTT 增量 alpha * MSS^2 / cwnd
        inc = (alpha * mss * mss) / max(s.cwnd, mss)
        s.cwnd += min(inc, s.cwnd)    # 限制单步增量，避免突变
```

```python
# 丢包时：任一子流拥塞都向连接级反馈，避免其他子流盲目增长
def on_loss(subflows, s):
    s.cwnd = max(s.cwnd * 0.5, mss_min)   # 子流本地退避
    for other in subflows:
        if other is not s:
            other.cwnd = min(other.cwnd, other.cwnd * 0.9)  # 轻度抑制
```

真实的 LIA 需要精确计算 $\alpha_i$、处理 RTT 测量平滑、并区分超时与重复 ACK 等场景，实现复杂度远高于上述示意。

## 五、与其他技术对比

| 维度 | MPTCP 耦合拥塞控制 | 各子流独立拥塞控制 | 单路径 TCP（CUBIC 等） |
| --- | --- | --- | --- |
| 共享瓶颈公平性 | 好，近似单流 | 差，多占带宽 | 基准 |
| 多路径聚合收益 | 有，且不损害他人 | 有，但以不公平换 | 无 |
| 实现复杂度 | 高，需跨子流协调 | 低 | 中 |
| RTT 异构适配 | 支持，按 RTT 加权 | 支持但无协调 | 单 RTT |
| 部署要求 | 两端均实现 | 各自实现即可 | 通用 |

耦合是 MPTCP 能从「实验室技巧」走向「可部署协议」的必要条件：没有它，多路径传输会沦为对网络的滥用。

## 六、常见误区
- 误区一：MPTCP 一定更快。在共享瓶颈上受耦合约束，未必成倍提升，甚至可能持平。
- 误区二：耦合等于各子流均分窗口。实际按 RTT 与吞吐份额加权，权重并不相等。
- 误区三：公平性只靠一端。需要两端都实现耦合算法，否则约束不成立。
- 误区四：子流丢包只影响该子流。耦合算法会向连接级反馈，影响整体增长。
- 误区五：$\alpha_i$ 是固定常数。它随 RTT 与吞吐份额动态变化。

## 七、与开源书·权威来源对应
- RFC 6356 定义了 MPTCP 的耦合拥塞控制框架与 LIA，是本节的第一手来源。
- RFC 8684 在多路径拥塞控制章节引用 RFC 6356 的要求，规范 MPTCP v1 的实现约束。

## 九、演进与趋势
- 面向异构路径（Wi-Fi + 5G）的研究在改进耦合粒度，力求聚合收益最大化同时不损害共享瓶颈上的其他流。
- Linux 内核默认提供耦合式拥塞控制，并允许按场景选择不同算法。
- 与调度器协同：拥塞控制决定「能发多少」，调度器决定「从哪条子流发」，二者共同影响体验。
- 面向低时延与高带宽场景的改进仍在持续，具体进展以官方标准与实现文档为准。

## 十、小结
MPTCP 通过耦合各子流的拥塞窗口，在获得多路径聚合收益的同时，把对共享瓶颈的占用约束在近似单流的量级，从而兼顾效率与公平。耦合因子 $\alpha_i$ 随 RTT 与吞吐份额动态变化，具体公式以 RFC 6356 为准。耦合是 MPTCP 可实际部署、而非沦为网络滥用的必要条件。
