# 并发编程深入实战（JMM / volatile / CAS / 锁体系 / AQS / 线程池 / 并发容器 / CompletableFuture）

> Java 并发编程 =「**线程模型 + 内存可见性 + 原子性 + 同步机制 + 并发工具 + 调试排障**」。
> 本篇从「概览」升级为「深入实战 + 面试全景」：先讲清最底层的 **JMM 与 happens-before**（一切可见性/有序性的根），再依次展开 volatile、CAS 与原子类、synchronized 与显式锁、AQS、并发工具类、线程池、ThreadLocal、并发容器、伪共享，最后落地 CompletableFuture / ForkJoin / 调试工具 / 并发 Bug 复现，并附实战口诀。

## 一、并发三大问题与心智模型

```text
并发编程要同时解决三个问题：
┌──────────┬───────────────────────────────┬──────────────────────────┐
│ 问题     │ 含义                          │ 典型手段                │
├──────────┼───────────────────────────────┼──────────────────────────┤
│ 原子性   │ 一个或多个操作要么全做要么全不做 │ 锁 / CAS / 原子类       │
│ 可见性   │ 一个线程的修改对其他线程立即可见 │ volatile / 锁 / happens-before │
│ 有序性   │ 程序执行顺序与代码顺序一致      │ volatile / 锁 / 内存屏障│
└──────────┴───────────────────────────────┴──────────────────────────┘
```

> **口诀**：原子看操作、可见看刷新、有序看重排；锁三者全包，volatile 只包可见+有序。

### 1.1 线程状态（JVM 层面）

```text
NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED

RUNNABLE 包含 Ready 和 Running（JVM 不区分，由 OS 调度）
BLOCKED   ：等待进入 synchronized 监视器锁（Monitor Enter）
WAITING   ：wait() / join() / LockSupport.park()（无超时，需被显式唤醒）
TIMED_WAITING：sleep() / wait(timeout) / parkNanos / join(timeout)
```

> **排查要点**：大量线程 `BLOCKED` 多半是锁竞争激烈或死锁；大量 `WAITING` 多半是线程池满 + 任务堆积或下游阻塞。

## 二、JMM（Java 内存模型）与 happens-before

> JMM 不是 JVM 内存结构（堆/栈/方法区），而是**多线程下变量读写可见性的抽象规范**。它定义了线程工作内存（Working Memory，类比 CPU 缓存）与主内存（Main Memory，类比主存）的交互规则。

### 2.1 核心规则

```text
1. 所有变量存在主内存；每个线程有私有的工作内存（拷贝副本）。
2. 线程只能操作自己工作内存中的副本，不能直接读写主内存外的变量。
3. 线程间变量传递必须经主内存（A 改→刷主存→B 从主存读）。
```

### 2.2 happens-before（可见性与有序性的唯一判据）

> 若操作 A **happens-before** 操作 B，则 A 的结果对 B **可见**，且 A 看似在 B 之前执行。

```text
happens-before 八大规则：
1) 程序次序：同一线程内，前面的操作 hb 后面的操作。
2) 管程锁定：unlock(hb)lock 同一把锁。
3) volatile 变量：对 volatile 变量的写 hb 后续对该变量的读。
4) 线程启动：Thread.start() hb 该线程的任何动作。
5) 线程终止：线程中所有动作 hb 其他线程检测到它结束（join 返回）。
6) 中断：interrupt() hb 被中断线程检测到中断。
7) 传递性：A hb B 且 B hb C ⇒ A hb C。
8) 对象终结：构造器结束 hb finalize()。
```

> **关键认知**：happens-before 不要求时间先后，只保证**可见性与顺序约束**。没有 hb 关系的两个线程操作，JVM 可自由重排。

### 2.3 重排序与 as-if-serial

```text
- 编译器/CPU 为优化会重排指令（编译器重排、指令级并行、内存系统重排）。
- as-if-serial：单线程内，重排后执行结果与顺序执行一致（所以单线程"无感"）。
- 但多线程下重排会破坏正确性 —— 必须用 volatile/锁/原子类建立 hb 关系来约束。
```

## 三、volatile：轻量级同步（可见性 + 有序性）

### 3.1 语义

```text
volatile 的两大保证（不保证原子性）：
1) 可见性：写操作立即刷主存，读操作从主存取，跳过工作内存副本。
2) 禁止重排序：在 volatile 读写处插入内存屏障（LoadLoad / StoreStore / LoadStore / StoreLoad）。
```

```java
// 典型用法：状态开关、双重检查锁的单例
class Singleton {
    private static volatile Singleton instance;
    static Singleton get() {
        if (instance == null) {               // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null)          // 第二次检查（必须）
                    instance = new Singleton(); // volatile 防止"半初始化对象"逸出
            }
        }
        return instance;
    }
}
```

### 3.2 经典坑：volatile 不保证原子性

```java
private static volatile int count = 0;
// 100 个线程各 count++ 一万次，结果远小于 1000000
// 原因：count++ 是「读-改-写」三步，volatile 只保证每一步的可见性，不保证三步整体原子
// 修复：AtomicInteger / synchronized / LongAdder
```

> **口诀**：volatile 管"看得到、不乱排"，管不了"一起做"。计数/累加请用原子类或锁。

## 四、CAS 与原子类（无锁原子性）

### 4.1 CAS 原理

```text
CAS(内存地址 V, 期望值 A, 新值 B)：
  if (V == A) { V = B; return true; }
  else { return false; }   // 由 CPU 指令（cmpxchg）保证原子
```

```java
// AtomicInteger 核心
public final int incrementAndGet() {
    return U.getAndAddInt(this, VALUE, 1) + 1; // 底层循环 CAS 直到成功
}
```

### 4.2 ABA 问题与解决

```text
ABA：值从 A→B→A，CAS 误以为没变而过检。
解决：加版本号/戳 —— AtomicStampedReference<V>(初始值, 初始戳)
```

```java
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);
int[] stamp = new int[1];
Integer cur = ref.get(stamp);          // cur=100, stamp[0]=0
ref.compareAndSet(cur, 200, stamp[0], stamp[0] + 1);
```

### 4.3 原子类家族

| 类 | 用途 |
|----|------|
| `AtomicInteger/Long/Boolean` | 基础原子整数 |
| `AtomicReference<V>` | 原子对象引用 |
| `AtomicStampedReference` / `AtomicMarkableReference` | 带版本戳，解决 ABA |
| `AtomicIntegerFieldUpdater` | 原子更新已有类的 volatile 字段（避免改对象结构） |
| `LongAdder` / `DoubleAdder` | **高并发计数**（分段 Cell，减少 CAS 竞争，空间换时间） |
| `LongAccumulator` | 自定义累加函数 |

> **选型**：低并发用 `AtomicLong`；高并发计数（如 QPS 统计）用 `LongAdder`，性能可差数倍。

## 五、synchronized 与显式锁体系

### 5.1 synchronized 锁升级（JDK 8+，64 位 Mark Word）

```text
无锁 → 偏向锁 → 轻量级锁 → 重量级锁

偏向锁    ：单线程反复进入，Mark Word 记录线程 ID，几乎零成本。
轻量级锁  ：有竞争但未激烈，CAS 自旋尝试获取（偏向锁撤销后升级）。
重量级锁  ：竞争激烈，线程进 Monitor 等待队列（OS 互斥量，涉及用户态↔内核态切换）。
```

```text
优化手段（JVM 自动）：
- 锁消除：JIT 发现不可能逃逸，直接去掉锁（如 StringBuffer 局部变量）。
- 锁粗化：把循环内多次加锁合并成一次。
- 适应性自旋：根据上次自旋成功率动态调整自旋次数。
```

### 5.2 synchronized vs ReentrantLock

| 维度 | synchronized | ReentrantLock |
|------|--------------|---------------|
| 获取方式 | 关键字，自动释放 | `lock()/unlock()`（finally 释放） |
| 可中断 | 不可 | `lockInterruptibly()` |
| 公平锁 | 非公平（不可改） | 可指定公平/非公平 |
| 尝试获取 | 无 | `tryLock(timeout)` |
| 条件变量 | 单 wait/notify | 多 `Condition`（精准唤醒） |
| 性能 | JDK 6 后大幅优化，接近 | 高竞争下更灵活 |

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
try { /* 临界区 */ } finally { lock.unlock(); }  // 必须 finally，否则死锁
```

### 5.3 读写锁与 StampedLock（读多写少场景）

```java
// ReentrantReadWriteLock：读共享、写独占
ReadWriteLock rw = new ReentrantReadWriteLock();
rw.readLock().lock();   try { /* 并发读 */ } finally { rw.readLock().unlock(); }
rw.writeLock().lock();  try { /* 独占写 */ } finally { rw.writeLock().unlock(); }

// StampedLock：乐观读（无锁），写时才校验戳
StampedLock sl = new StampedLock();
long stamp = sl.tryOptimisticRead();
int v = data;
if (!sl.validate(stamp)) {        // 期间被写，乐观读失效
    stamp = sl.readLock();         // 退化成悲观读锁
    try { v = data; } finally { sl.unlockRead(stamp); }
}
```

> **注意**：`StampedLock` 不支持重入，且 `readLock()` 获取后若发生中断会抛异常——读多写极少用乐观读，性能优于读写锁。

### 5.4 死锁：四条件与排查

```text
死锁四必要条件（缺一不可）：互斥、持有等待、不可剥夺、循环等待。
预防：
- 按固定全局顺序加锁（破坏循环等待）；
- 使用 tryLock(timeout) 超时退出；
- 减少锁粒度 / 用并发容器替代。
```

```bash
# 排查死锁
jstack <pid> | grep -A 20 "deadlock"   # 直接定位死锁线程与持锁
```

## 六、AQS（AbstractQueuedSynchronizer）

### 6.1 核心结构

```text
AQS = volatile int state + CLH 双向等待队列 + 一个独占/共享模式

state     ：同步状态（0/1 = 独占锁占用；>1 = 重入次数；信号量 = 剩余许可）
CLH 队列 ：竞争失败的线程封装成 Node 入队，FIFO，自旋/阻塞等待
```

### 6.2 获取与释放（独占模式）

```text
acquire(arg):
  1. tryAcquire(arg) 成功 ⇒ 直接获得
  2. 失败 ⇒ addWaiter 入队尾部（CAS）
  3. 队列中线程 acquireQueued：自旋 CAS 抢占 head，失败则 park 阻塞
release(arg):
  1. tryRelease 修改 state
  2. unparkSuccessor：唤醒后继节点线程
```

### 6.3 基于 AQS 的实现

| 同步器 | state 含义 | 模式 |
|--------|-----------|------|
| `ReentrantLock` | 重入次数 | 独占 |
| `Semaphore` | 剩余许可数 | 共享 |
| `CountDownLatch` | 剩余计数 | 共享 |
| `ReentrantReadWriteLock` | 高 16 位读计数 / 低 16 位写计数 | 混合 |

```text
条件变量 Condition：await()/signal() 基于 AQS 的等待队列，实现精准唤醒（替代 wait/notify）。
```

## 七、并发工具类（同步器）

| 工具 | 语义 | 典型场景 |
|------|------|----------|
| `CountDownLatch` | 计数到 0 放行（一次性） | 主线程等所有子任务完成 |
| `CyclicBarrier` | 所有线程到齐再继续（可重用） | 多线程分阶段计算 |
| `Semaphore` | 控制并发许可数 | 限流、连接池 |
| `Phaser` | 可动态注册的分阶段屏障 | 复杂多阶段任务 |
| `Exchanger` | 两线程交换数据 | 遗传算法、管道 |

```java
// CountDownLatch 示例
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) new Thread(() -> { doWork(); latch.countDown(); }).start();
latch.await();   // 等 3 个完成
```

## 八、线程池：原理、参数与调优

### 8.1 七大参数

```java
new ThreadPoolExecutor(
    corePoolSize,      // 核心线程数（常驻）
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 空闲非核心线程存活时间
    unit,              // 时间单位
    workQueue,         // 任务队列（ArrayBlockingQueue/LinkedBlockingQueue/SynchronousQueue）
    threadFactory,     // 线程工厂（命名、 daemon）
    handler            // 拒绝策略
);
```

### 8.2 拒绝策略

| 策略 | 行为 |
|------|------|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` |
| `CallerRunsPolicy` | 由提交线程自己执行（天然限流，保护系统） |
| `DiscardPolicy` | 静默丢弃 |
| `DiscardOldestPolicy` | 丢弃队列最旧任务，重试提交 |

### 8.3 线程数计算（经验公式）

```text
CPU 密集型：线程数 ≈ Ncpu + 1
IO 密集型 ：线程数 ≈ Ncpu × (1 + 阻塞系数)   （阻塞系数 0.8~0.9 ⇒ 2N~10N）
精确：线程数 = Ncpu × (1 + 阻塞时间/计算时间)
```

> **禁用 `Executors` 快捷工厂**：`newFixedThreadPool`/`newCachedThreadPool` 用无界队列或无限线程，易导致 OOM。务必手动 `ThreadPoolExecutor` + 有界队列 + 合理拒绝策略。

### 8.4 常见坑与监控

```text
- 任务抛异常被吞：submit() 异常藏在 Future，execute() 才进 UncaughtExceptionHandler。
- 上下文切换成本：线程数过多反而因频繁切换而变慢。
- ThreadLocal 用完不 remove ⇒ 线程复用导致串数据（见第九节）。
- 监控：通过 ThreadPoolExecutor 的 getActiveCount/getQueue().size() 暴露到 /metrics。
```

## 九、ThreadLocal：线程封闭与内存泄漏

### 9.1 原理

```text
每个 Thread 持有 ThreadLocalMap（key=ThreadLocal 弱引用，value=业务值）。
get/set 实际读写当前线程的 Map。实现线程间数据隔离（如用户信息、traceId）。
```

### 9.2 内存泄漏根因

```text
ThreadLocalMap 的 key 是弱引用 ⇒ GC 后 key 变 null，但 value 是强引用仍占用。
若线程长期存活（线程池），value 永远无法回收 ⇒ 泄漏。
修复：务必 try-finally 中 remove()。
```

```java
private static final ThreadLocal<User> CTX = new ThreadLocal<>();
try { CTX.set(user); doBiz(); } finally { CTX.remove(); }   // 必须 remove
```

### 9.3 跨线程传递

```text
InheritableThreadLocal：子线程继承父线程值（仅 new Thread 时复制一次）。
线程池场景失效（线程是复用的）⇒ 用阿里 TransmittableThreadLocal（TTL）做装饰传递。
```

## 十、并发容器（JUC 集合）

### 10.1 ConcurrentHashMap（1.8）

```text
1.7：分段锁 Segment（16 段）独立加锁。
1.8：Node 数组 + 链表/红黑树，CAS + synchronized 锁定单个桶头节点（更细粒度）。
- sizeCtl：负数表示初始化/扩容中；正数表示阈值。
- 扩容：多线程协助迁移（ForwardingNode 标记已迁移桶）。
- counterCell：分段计数，避免 size() 争用。
```

### 10.2 阻塞队列（线程池/生产者消费者基石）

| 队列 | 特点 |
|------|------|
| `ArrayBlockingQueue` | 有界、数组、可选公平 |
| `LinkedBlockingQueue` | 默认无界链表（建议显式有界） |
| `SynchronousQueue` | 不存储元素，直接交接（CachedThreadPool 用） |
| `PriorityBlockingQueue` | 优先级无界 |
| `DelayQueue` | 延迟到期才能取（定时任务） |

### 10.3 其他

```text
- CopyOnWriteArrayList：写时复制，读无锁，适合读多写极少（监听器列表）。
- ConcurrentLinkedQueue：无锁 CAS 队列（高并发无界）。
- 跳表 ConcurrentSkipListMap/Set：有序并发，替代 TreeMap。
```

## 十一、伪共享（False Sharing）

```text
CPU 缓存以缓存行（64 字节）为单位。两个无关 volatile 变量在同一缓存行，
一核修改 ⇒ 整行失效 ⇒ 另一核被迫重新加载 ⇒ 性能骤降（看似无关却互相拖累）。
```

```java
// JDK 8+ 用 @Contended（需 -XX:-RestrictContended）
@sun.misc.Contended
class PaddedCounter { volatile long value; }

// 或手动填充（兼容性好）
class Counter { volatile long value; long p1,p2,p3,p4,p5,p6,p7; }  // 占位填满缓存行
```

> LongAdder 内部 `Cell[]` 正是用填充规避伪共享，这也是它高并发优于 AtomicLong 的原因之一。

## 十二、CompletableFuture 异步编排

### 12.1 核心 API

```java
CompletableFuture.supplyAsync(() -> queryA(), exec)        // 异步有返回值
    .thenApplyAsync(r -> transform(r), exec)                // 转换
    .thenComposeAsync(f -> queryB(f), exec)                // 扁平化（避免嵌套 Future）
    .thenCombine(CompletableFuture.supplyAsync(() -> queryC()), (a, b) -> merge(a, b));

CompletableFuture.anyOf(f1, f2, f3);   // 任一完成
CompletableFuture.allOf(f1, f2, f3).thenRun(() -> done());
```

### 12.2 异常处理与线程池

```java
future.exceptionally(ex -> fallback)              // 异常兜底
      .handle((r, ex) -> ex != null ? fallback : r);  // 统一处理

// 务必传自定义线程池！否则默认 ForkJoinPool.commonPool，IO 任务会拖垮全局
CompletableFuture.supplyAsync(task, bizExecutor);
```

## 十三、ForkJoinPool 分治框架

### 13.1 工作窃取（Work-Stealing）

```text
每个线程有双端队列；自己从队头取任务，空闲线程从别人队尾"窃取"任务。
适合递归分治：大任务 split 成子任务，子任务再 split，直到可计算。
```

### 13.2 使用与陷阱

```java
class SumTask extends RecursiveTask<Long> {
    protected Long compute() {
        if (end - start <= THRESHOLD) return directSum();
        SumTask left = new SumTask(start, mid), right = new SumTask(mid, end);
        left.fork(); long r = right.compute(); long l = left.join();
        return l + r;
    }
}
```

```text
陷阱：
- 不要在 ForkJoinPool 中执行阻塞 IO（会饿死其他任务）。
- 并行流 parallelStream() 用 commonPool，需限流（自定义 ForkJoinPool 包裹）。
```

## 十五、并发 Bug 复现与修复

### 15.1 常见并发 Bug 模式

```text
1) 竞态条件：if-then-act 非原子（如"不存在则创建"用 synchronized 或 putIfAbsent）。
2) 可见性缺失：共享变量未 volatile/锁，值不刷新。
3) 死锁/活锁：加锁顺序不一致 / 相互礼让。
4) 饥饿：低优先级线程长期拿不到锁。
5) 对象逸出：构造器中 this 泄露（内部类/线程可见到半初始化对象）。
6) 发布未同步集合：HashMap 并发写导致死循环（用 ConcurrentHashMap）。
```

## 十六、锁的底层实现原理

### mutex 源码结构

```go
// runtime/sema.go
type mutex struct {
    state int32  // 锁状态
    sema  uint32 // 信号量
}

// 锁状态：
// mutexLocked    = 1 << 0  // 已锁定
// mutexStarving  = 1 << 1  // 饥饿模式
// mutexWoken     = 1 << 2  // 唤醒标志
// mutexCopied    = 1 << 3  // 已复制（检查是否有 goroutine 等待）
```

### mutex 加锁流程

```
正常模式（Normal Mode）：
  1. CAS 尝试获取锁（state 0 → mutexLocked）
     成功 → 获取锁，返回
  2. 失败 → 自旋 4 次（多次 CAS 尝试）
     检查：GOMAXPROCS > 1 && 已有 goroutine 持锁
     自旋成功 → 获取锁，返回
  3. 自旋失败 → 将当前 goroutine 挂入等待队列（waiter）
     修改 state：mutexLocked | mutexWoken
     调用 gopark() 挂起
  4. 被唤醒 → 自旋获取锁
     成功 → 获取锁，返回
  5. 获取失败 → 加入队尾，继续等待

饥饿模式（Starving Mode）：
  条件：等待时间 > 1ms
  特性：
    1. 锁直接传递给队首 waiter（唤醒者）
    2. 新请求者不自旋，直接挂入队尾
    3. 保证 FIFO 公平性
    4. 当等待队列为空或等待时间 < 1ms 时，退化为正常模式

切换条件：
  正常 → 饥饿：waiter 等待时间 > 1ms
  饥饿 → 正常：队列为空或等待时间 < 1ms
```

### sync.Pool 实现原理

```go
// runtime/sync_pool.go
type Pool struct {
    noCopy noCopy

    local     unsafe.Pointer // local fixed-size per-P pool
    localSize uintptr        // size of the local array

    victim     unsafe.Pointer // 从上一轮 GC 中回收的对象
    victimSize uintptr

    New func() any  // 创建新对象的函数
}

// 每个 P 有本地池（无锁）
type poolLocal struct {
    poolLocalInternal
    pad [128 - unsafe.Sizeof(poolLocalInternal{})%128]byte
}

type poolLocalInternal struct {
    private any  // 私有对象（无锁访问）
    shared  poolChain  // 共享队列（本地 P 无锁，其他 P 有锁）
}
```

```
Pool 工作流程：
  Get:
    1. 当前 P 的 private 有对象 → 直接返回（无锁）
    2. 当前 P 的 shared 有对象 → pop（无锁）
    3. 其他 P 的 shared 有对象 → steal（有锁）
    4. victim 中有对象 → 获取
    5. 都没有 → 调用 New 创建

  Put:
    1. 当前 P 的 private 为空 → 放入 private（无锁）
    2. 当前 P 的 private 有对象 → 放入 shared 头部（无锁）

  GC 清理：
    每次 GC 将 Pool 中的对象移到 victim
    下一次 GC 将 victim 清空
```

## 十七、WaitGroup 源码分析

### WaitGroup 内部实现

```go
// sync/waitgroup.go
type WaitGroup struct {
    noCopy noCopy
    state1 [3]uint64  // [sema, counter, waiter_count]
}

// state1 布局：
// 低 32 位：counter（计数器）
// 高 32 位：waiter_count（等待者数量）
// sema：信号量（用于阻塞/唤醒）
```

### WaitGroup 操作流程

```
Add(delta):
  1. 原子操作 state + delta
  2. 检查 counter 是否 >= 0
     < 0 → panic（Add 负数超过 Wait 的值）
  3. 如果 counter 变为 0 且有 waiter
     唤醒所有 waiter

Done():
  Add(-1)  // counter 减 1

Wait():
  1. 检查 counter 是否为 0
     是 → 直接返回
  2. 原子操作 waiter_count + 1
  3. 调用 gopark() 挂起
  4. 被唤醒（counter 变为 0）
  5. 返回

关键实现：
  - counter 和 waiter_count 打包在一个 uint64 中
  - 用原子操作保证线程安全
  - sema 用于阻塞/唤醒 goroutine
```

## 十八、Context 与取消传播

### Context 取消传播实现

```go
// context/context.go
type cancelCtx struct {
    Context
    mu       sync.Mutex
    done     atomic.Value  // chan struct{}
    children map[cancelCtx]struct{}
    err      error
    cause    error
}

type timerCtx struct {
    cancelCtx
    timer    *time.Timer
    deadline time.Time
}
```

### 取消传播流程

```
WithCancel(parent):
  1. 创建 cancelCtx，parent 指向 parent
  2. 将 cancelCtx 加入 parent.children
  3. 返回 cancelCtx 和 cancel 函数

调用 cancel():
  1. 设置 err = Canceled
  2. 关闭 done channel（close(ch)）
  3. 从 parent.children 中移除自己
  4. 遍历 children，递归调用 cancel()
  5. 停止定时器（如果是 timerCtx）

WithTimeout(parent, timeout):
  1. 创建 timerCtx
  2. 计算 deadline = now + timeout
  3. 启动定时器，到期后调用 cancel()
  4. 返回 timerCtx 和 cancel 函数

取消传播：
  context.Background()
    └── WithCancel() [ctx1, cancel1]
        └── WithTimeout() [ctx2, cancel2]
            └── WithCancel() [ctx3, cancel3]

  调用 cancel1() → ctx1, ctx2, ctx3 全部取消
  调用 cancel2() → ctx2, ctx3 取消，ctx1 不受影响
```

## 二十、并发模式与最佳实践

### 常见并发模式

```go
// 模式 1：Worker Pool（工作池）
func workerPool(jobs <-chan Job, results chan<- Result, workers int) {
    var wg sync.WaitGroup
    for i := 0; i < workers; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs {
                results <- process(job)
            }
        }()
    }
    wg.Wait()
    close(results)
}

// 模式 2：Fan-out / Fan-in
func fanOut(input <-chan int, workers int) []<-chan int {
    channels := make([]<-chan int, workers)
    for i := 0; i < workers; i++ {
        channels[i] = worker(input)
    }
    return channels
}

func fanIn(channels ...<-chan int) <-chan int {
    var wg sync.WaitGroup
    merged := make(chan int)
    for _, ch := range channels {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for v := range ch {
                merged <- v
            }
        }()
    }
    go func() {
        wg.Wait()
        close(merged)
    }()
    return merged
}

// 模式 3：Pipeline（管道）
func pipeline(input <-chan int) <-chan int {
    stage1 := func(in <-chan int) <-chan int {
        out := make(chan int)
        go func() {
            for v := range in {
                out <- v * 2
            }
            close(out)
        }()
        return out
    }

    stage2 := func(in <-chan int) <-chan int {
        out := make(chan int)
        go func() {
            for v := range in {
                out <- v + 1
            }
            close(out)
        }()
        return out
    }

    return stage2(stage1(input))
}

// 模式 4：Throttle（限流）
func throttle(ch <-chan int, rate int) <-chan int {
    out := make(chan int)
    limiter := time.NewTicker(time.Second / time.Duration(rate))
    go func() {
        defer limiter.Stop()
        defer close(out)
        for v := range ch {
            <-limiter.C
            out <- v
        }
    }()
    return out
}
```

## JMM Happens-Before 规则详解

### 八大规则

```
Happens-Before 8 大规则：

1. 程序顺序规则（Program Order）
   同一线程内，前面的操作 happens-before 后面的操作

2. 监视器锁规则（Monitor Lock）
   unlock happens-before lock（同一个锁）

3. volatile 变量规则（Volatile Variable）
   volatile 写 happens-before volatile 读

4. 线程启动规则（Thread Start）
   Thread.start() happens-before 该线程的每个操作

5. 线程终止规则（Thread Termination）
   线程的所有操作 happens-before Thread.join() 返回

6. 中断规则（Interruption）
   调用 interrupt happens-before 检测到中断

7. 终结器规则（Finalizer）
   对象构造函数 happens-before finalize() 开始

8. 传递性规则（Transitivity）
   A hb B, B hb C → A hb C
```

## CAS 与原子类深度解析

```
CAS 工作原理：

  Compare-And-Swap：
    ├── 比较内存值与预期值
    ├── 相等则更新为新值
    └── 不相等则重试（自旋）

  ABA 问题：
    ├── 值从 A → B → A，CAS 误认为未修改
    └── 解决：AtomicStampedRef（版本号）

  自旋开销：
    ├── 竞争激烈时 CPU 空转
    └── 解决：LongAdder（分段累加）
```

```java
// AtomicInteger 使用
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();  // CAS 自旋更新
counter.compareAndSet(5, 10);  // CAS

// AtomicStampedRef 解决 ABA
AtomicStampedRef<Integer> ref = new AtomicStampedRef<>(0, 0);
int stamp = ref.getStamp();
ref.compareAndSet(0, 1, stamp, stamp + 1);

LongAdder adder = new LongAdder();
adder.increment();  // 内部分段，减少竞争
```

### JMM happens-before 八规则详解

```java
// 1. 程序顺序规则：单个线程内，前面的操作 happens-before 后面的操作
int a = 1;  // 操作1
int b = 2;  // 操作2
// 操作1 happens-before 操作2

// 2. 监视器锁规则：unlock happens-before 同一个锁的 lock
synchronized (lock) {
    // 操作3
}
// 操作3 happens-before 下一个线程的 lock 操作

// 3. volatile 变量规则：volatile 写 happens-before 后续的 volatile 读
volatile int flag = 0;
// 线程A: flag = 1;  // volatile 写
// 线程B: if (flag == 1) { ... }  // volatile 读

// 4. 线程启动规则：Thread.start() happens-before 被启动线程的每个操作
Thread t = new Thread(() -> {
    // 操作4
});
t.start();  // start() happens-before 操作4

// 5. 线程终止规则：线程的所有操作 happens-before Thread.join() 返回
t.join();  // 线程所有操作 happens-before join() 返回

// 6. 线程中断规则：interrupt() happens-before 被中断线程检测到中断
thread.interrupt();  // interrupt() happens-before 检测到中断

// 7. 终结器规则：构造函数 happens-before finalize() 开始
// 8. 传递性：如果 A happens-before B，B happens-before C，则 A happens-before C
```

### 无锁算法（Lock-Free）

```java
// 1. CAS实现无锁栈
public class LockFreeStack<T> {
    private final AtomicReference<Node<T>> top = new AtomicReference<>();
    
    public void push(T value) {
        Node<T> oldTop = top.get();
        Node<T> newTop = new Node<>(value, oldTop);
        while (!top.compareAndSet(oldTop, newTop)) {
            oldTop = top.get();
            newTop = new Node<>(value, oldTop);
        }
    }
    
    public T pop() {
        Node<T> oldTop = top.get();
        Node<T> newTop = oldTop == null ? null : oldTop.next;
        while (!top.compareAndSet(oldTop, newTop)) {
            oldTop = top.get();
            newTop = oldTop == null ? null : oldTop.next;
        }
        return oldTop == null ? null : oldTop.value;
    }
}

// 2. ABA问题解决
public class ABAFix<T> {
    private final AtomicStampedRef<T> ref = new AtomicStampedRef<>(null, 0);
    
    public void update(T expected, T newValue) {
        int[] stampHolder = new int[1];
        T value = ref.get(stampHolder);
        int stamp = stampHolder[0];
        
        if (value == expected) {
            if (ref.compareAndSet(expected, newValue, stamp, stamp + 1)) {
                return;
            }
        }
        // 重试逻辑
    }
}
```

| 版本号 | AtomicStampedRef | 解决ABA但复杂 |
| LongAdder | 分段累加 | 高并发累加优化 |

### 生产者-消费者与读写锁模式

```java
// 1. 生产者-消费者（BlockingQueue）
public class ProducerConsumer {
    private final BlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000);
    
    // 生产者
    public void produce() {
        while (true) {
            Task task = createTask();
            queue.put(task);  // 队列满时阻塞
        }
    }
    
    // 消费者
    public void consume() {
        while (true) {
            Task task = queue.take();  // 队列空时阻塞
            process(task);
        }
    }
}

// 2. 读写锁（ReadWriteLock）
public class ReadWriteLockExample {
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    private final Map<String, Object> cache = new HashMap<>();
    
    // 读操作（共享锁）
    public Object read(String key) {
        lock.readLock().lock();
        try {
            return cache.get(key);
        } finally {
            lock.readLock().unlock();
        }
    }
    
    // 写操作（排他锁）
    public void write(String key, Object value) {
        lock.writeLock().lock();
        try {
            cache.put(key, value);
        } finally {
            lock.writeLock().unlock();
        }
    }
}

// 3. StampedLock（乐观读+悲观写）
public class StampedLockExample {
    private final StampedLock lock = new StampedLock();
    private double x, y;
    
    // 乐观读（无锁）
    public double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead();
        double currentX = x, currentY = y;
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();  // 降级为悲观读
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.sqrt(currentX * currentX + currentY * currentY);
    }
    
    // 写操作
    public void move(double deltaX, double deltaY) {
        long stamp = lock.writeLock();
        try {
            x += deltaX;
            y += deltaY;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}
```

| StampedLock | 乐观读+悲观写 | 高并发读 |
| Condition | 条件等待 | 复杂同步 |
