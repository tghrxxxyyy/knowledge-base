# 重构节奏

> 对应 Martin Fowler《Refactoring》「Refactoring, Testing, and Legacy」、Robert C. Martin 务实工程观，及 CS-Notes。

## 一、背景与挑战

重构若与功能开发长期分离，会演化成「重构大项目」——积压的债务越堆越多，最终与主线冲突、难以 review、无人敢动。团队常在「先赶功能、后专门重构」的循环里反复，结果是技术债务利息越滚越大。核心问题：如何把重构融入日常，使其不再成为需要「专门立项」的负担？

## 二、核心原理

核心是**持续重构（continuous refactoring）**，与童子军法则（Boy-Scout Rule）一致：让代码比你来时更干净。具体节奏：

- **小步合入**：每次提交顺手做一点重构，不单独开长命分支。
- **与 CI 协同**：小步合入主干，借助持续集成快速发现回归，可随时回滚。
- **两顶帽子（Two Hats）**：同一时段内要么加功能、要么重构，不混为一谈，保持行为边界清晰。
- **债务预算**：把「重构增量」与「新增复杂度」挂钩，使债务增长受控。

这与「重构 sprint」相对立——专项重构易与特性冲突、review 困难、易半途而废。

实践上，团队可把「顺手重构」写进 Definition of Done：每个 PR 至少消除一个坏味道或抽出一处可复用逻辑；并用 15 分钟时间盒（time-box）约束改动范围，避免小重构滑成大改动。CI 中可对新增复杂度设趋势门禁（如关键函数圈复杂度不升、重复率不增），把节奏从「个人自觉」升级为「工程约束」。同时要和发布节奏协调：版本冻结或封板期应暂停结构性重构，避免在稳定分支引入回归。衡量节奏是否健康，可观察「坏味道新增 vs 消除」的净值曲线——长期为负才说明债务真正下降，而非被新功能不断掩盖。对大型遗留模块，还可设定「每周技术债偿还时间块」，把持续重构制度化，而不是寄望于一次性的清理项目。

## 三、形式化与数学基础

设每次提交带来的新增复杂度（复杂度增量）为 Δc，同时偿还的债务（重构削减）为 Δr。为控制债务增长，团队约定系数 α，要求：

$$
\Delta r \ge \alpha \cdot \Delta c, \quad \alpha \in (0,1]
$$

即每新增一份复杂度，至少偿还 α 比例的债务。当 α=1 表示「随借随还」，债务不增。在 CI 频率 f 下，单位时间最大可承受复杂度增速被 f 与单步可验证性约束：步子越大，回归检测越滞后，实际可行的 α 越低。

## 四、代码实现

```bash
# 每次 PR 顺手小重构，不单独开重构分支
git commit -m "feat: add coupon; extract calc_total()"

# pre-commit 自动做基础重构（lint/format），把噪音前置
# .pre-commit-config.yaml 示意
#  - repo: https://github.com/pre-commit/pre-commit-hooks
#    hooks: [trailing-whitespace, end-of-file-fixer]
```

```python
# 在加功能时顺手抽出可复用函数（两顶帽子之一）
def calc_total(items, coupon=None):   # 提取自原内联逻辑
    subtotal = sum(i.price * i.qty for i in items)
    return subtotal - (coupon.value if coupon else 0)
```

## 五、与其他技术对比

- **重构 sprint（专项）**：集中清理但易与特性冲突、难 review、易中断。
- **持续小步重构**：与特性并行、随时可回滚、债务可控。
- **完全不重构**：短期快，长期被熵增拖垮。
- **长期特性分支重构**：合并冲突风险高，背离 Trunk-Based Development。

## 六、常见误区

- **误区一：把重构藏在大特性里不说明**——review 者无法区分功能与结构改动。
- **误区二：在没有测试的分支长期重构**——等价性无法验证，风险累积。
- **误区三：等「有空」再重构**——「有空」永不到来，债务持续复利。
- **误区四：重构 sprint 能解决一切**——专项清理后很快又被新需求侵蚀。

## 八、面试题

- 为什么不建议专门安排重构 sprint？如何把重构融入日常？
- 两顶帽子原则是什么？为什么功能与重构要分开？
- 如何用债务预算（α）约束复杂度增长？
- 持续集成在重构节奏中扮演什么角色？

把持续重构落到团队日常，可参考以下实践清单：

- 把「消除一个坏味道」写进每个 PR 的 Definition of Done，而非留待专门项目。
- 用 15 分钟时间盒约束单次重构范围，避免小改动滑成大重写。
- 在 CI 中加入复杂度与重复率趋势门禁，让债务可见、可阻断。
- 版本冻结 / 封板期暂停结构性重构，稳定优先。
- 对大型遗留模块设固定「技术债偿还时间块」，制度化而非靠自觉。
- 配合 pre-commit 自动 lint / format，把基础整洁前置到提交前。

这些实践的共同目标是：让重构成为低摩擦的日常习惯，而不是令人畏惧的周期性大工程。衡量节奏是否健康，可长期观察「坏味道新增 vs 消除」的净值曲线，持续为负才算债务真正下降。

## 九、演进与趋势

pre-commit 钩子把 lint/format 等基础重构前置，降低人工负担；自动化重构（LSP）让小步更易执行；可观测的「代码健康度」指标（复杂度趋势、坏味道数）让重构节奏可度量、可治理。具体实践以团队工程规范为准。

## 十、小结

小步、常做、随 CI，让重构成为习惯而非项目。用债务预算约束复杂度增速，使代码健康度在持续交付中稳步提升。
