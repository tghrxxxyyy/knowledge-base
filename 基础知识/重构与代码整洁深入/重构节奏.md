# 重构节奏

> 对应 Fowler《Refactoring》"Refactoring, Testing, and Legacy"、Martin 务实观。

## 一、背景与挑战
重构若与功能开发长期分离，会产生"重构大项目"积压并引发冲突。需要把重构融入日常。

## 二、核心原理
持续重构（Boy-Scout Rule：让代码比你来时更干净）优于周期性大重构；与持续集成结合，小步合入主干。

## 三、形式化 / 数学基础
若每次提交增量重构量 $\Delta r$ 与新增复杂度 $\Delta c$ 满足 $\Delta r \ge \alpha \Delta c$（$\alpha$ 为团队约定），则债务增长受控。

## 四、代码实现
```bash
# 每次 PR 顺手小重构，不单独开重构分支
git commit -m "feat: add coupon; extract calc_total()"
```

## 五、与其他技术对比
与"重构 sprint"相对立：专项重构易与特性冲突、难 review。与 CI 协同保证小步可回滚。

## 六、常见误区
误区：把重构藏在大特性里不说明。误区：在没有测试的分支长期重构。

## 七、与开源书 / 权威来源对应
Fowler, M.《Refactoring》"Refactoring and Testing"；Martin, R. C.《Clean Code》；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"为什么不建议专门安排重构 sprint？如何把重构融入日常？"

## 九、演进与趋势
预提交钩子（pre-commit）自动 lint/format，把基础重构前置。

## 十、小结
小步、常做、随 CI，让重构成为习惯而非项目。
