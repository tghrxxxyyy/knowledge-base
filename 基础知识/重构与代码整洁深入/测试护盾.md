# 测试护盾

> 对应 Martin Fowler《Refactoring》「Testing」、Kent Beck《Test-Driven Development: By Example》，及 CS-Notes。

## 一、背景与挑战

没有测试网，重构如同走钢丝——你改了结构，却无法证明行为未变。测试套件就是允许安全重构的「护盾」，提供快速反馈：任何破坏等价性的改动都会立刻被红灯捕获。挑战在于：护盾并非「有就行」，其质量（覆盖什么、断言什么）决定了它能挡住多少回归；盲目追求高行覆盖率却写弱断言，会营造虚假安全感。

## 二、核心原理

重构前应先有覆盖关键行为的测试。经典结构是**测试金字塔**：大量单元测试（快、隔离）、少量集成测试、极少端到端测试。TDD 把测试变为设计工具，遵循「红—绿—重构」循环：先写失败测试定义期望行为，再实现使其通过，最后在绿灯下安全重构。

护盾的「强度」不只看行数，更看它能否抓住行为变化。两个关键实践：

- **表征测试（characterization test）**：锁定当前（哪怕是错的）行为，防止重构意外改变它（见遗留代码处理）。
- **突变测试（mutation testing）**：故意注入小改动（突变），看测试能否发现，衡量护盾真实灵敏度。

在遗留系统或无测试项目中，护盾可从「表征测试」起步（见遗留代码处理章节）：先钉住当前行为，再逐步补正确性测试。另一个常见陷阱是「脆弱测试」——断言了实现细节（如具体私有方法调用、浮点精确值），导致任何无害重构都触发红灯，反而劝退重构。好的测试应断言「可观察行为」而非「实现路径」，让护盾既灵敏又不扰民。同时，护盾本身也要被测试：断言写错（永远为真）的测试比没有测试更危险，因为它提供虚假的安全感。

## 三、形式化与数学基础

覆盖率指标：行覆盖 $C_{line}=\frac{被执行行}{总行}$，分支覆盖 $C_{branch}=\frac{覆盖分支}{总分支}$。但覆盖率衡量「被执行」，不衡量「被断言」。更本质的护盾强度用突变存活率：

$$
M = \frac{\text{未被测试捕获的突变数}}{\text{总突变数}}
$$

$M$ 越低，护盾越可靠。一个强护盾应满足 $M \to 0$。注意：突变测试计算成本高，常抽样或增量运行。

行为等价验证可表达为：对测试集 T，重构前后应满足：

$$
\forall t \in T,\ outcome_{before}(t) = outcome_{after}(t)
$$

测试套件即对该全称命题的有限近似证明。

## 四、代码实现

```python
# 重构前后断言不变：护盾的核心价值
def calc_outstanding(invoice) -> float:
    return sum(i.amount for i in invoice.items)

def test_calc_outstanding():
    inv = Invoice(items=[Item(10), Item(20)])
    # 无论内部如何重构，该断言必须仍成立
    assert calc_outstanding(inv) == 30
```

## 五、与其他技术对比

- **调试驱动开发（DDD）**：先写代码后调试，无护盾、回归靠运气。
- **TDD**：先写失败测试，测试即规格，重构安全网天然存在。
- **类型系统**：防一类「形状错误」，但不防「行为错误」，与测试互补。
- **仅端到端测试**：覆盖真实但慢、脆弱，难定位问题，需金字塔平衡。

## 六、常见误区

- **误区一：追求 100% 行覆盖**——覆盖不等于断言，行覆盖高也可能全是弱断言。
- **误区二：重构后不跑全量测试**——只跑局部等于主动放弃护盾。
- **误区三：测试只为通过**——应断言行为，而非「期望当前输出」。
- **误区四：护盾越厚越好**——维护成本随测试量上升，需取舍关键路径。

## 八、面试题

- 为什么重构前需要测试？突变测试是什么，为什么比覆盖率更本质？
- 测试金字塔是什么？为何端到端测试应最少？
- TDD 的「红—绿—重构」循环如何支撑安全重构？
- 高行覆盖率却仍出回归，问题在哪？

把护盾真正用起来，需要工程化而非一次性编写：将测试接入 CI 在每次提交运行，对核心路径设覆盖率下限与突变存活率门禁，未达标则阻断合并。对于历史无测试模块，采用「表征测试先行、正确性测试渐增」的渐进策略，避免一次性补测试导致的脆弱断言泛滥。测试也应自身被守护——用「变异测试」定期验证断言有效性，剔除永远为真的假测试，保证护盾真实灵敏。

## 九、演进与趋势

AI 生成测试、Property-Based Testing、基于覆盖引导的测试补全不断提升护盾密度；突变测试逐步融入 CI 做「护盾强度门禁」。具体工具能力以官方最新版本为准。

一个实用建议：为重构相关代码编写「表征 + 行为」双层测试——表征测试守护现状不被无意改变，行为测试守护正确语义；二者分离，既能放心重构又不掩盖既有 bug。当测试变红时，先判断是「行为真的坏了」还是「断言过紧」，再决定修代码还是修测试。把测试当作会进化的规格，而非一次性产物，护盾才能随系统长期有效。

## 十、小结

测试套件是重构的安全网，但其价值在于「断言质量」与「突变灵敏度」，而非覆盖率数字。把测试当作可执行的规格，重构才真正无惧。
