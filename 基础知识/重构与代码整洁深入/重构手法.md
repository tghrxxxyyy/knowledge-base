# 重构手法

> 对应 Martin Fowler《Refactoring: Improving the Design of Existing Code》Refactoring Catalog，及 CS-Notes（CyC2018）。

## 一、背景与挑战

重构是在**不改变外部可观察行为**的前提下改善代码内部结构。它的对立面是「大爆炸式重写」——一次性推倒重来，风险高、回报不确定。软件熵增定律告诉我们：不持续整理，代码结构会随需求叠加而腐化。重构的价值在于用「小步、可验证」的手法，把腐化过程逆转，又不引入功能回归。

挑战在于：如何保证「行为不变」？如何把庞大改动拆成安全的小步？如何在没有测试的情况下依然能重构？

## 二、核心原理

Fowler 把每个重构定义为「名称 + 动机 + 做法 + 示例」的结构化操作，形成可复用的手法目录（catalog）。常用核心手法：

- **Extract Method / Extract Variable**：抽离子逻辑，提升复用与命名表达。
- **Rename**：用更准确的名字揭示意图（最常用、最安全）。
- **Move Method / Move Field**：把职责放到它真正依赖的数据附近。
- **Replace Conditional with Polymorphism**：用多态消除复杂分支。
- **Introduce Parameter Object**：聚合参数，降低耦合。
- **Replace Temp with Query**：去除易变的中间变量。

关键纪律：每做一小步就运行测试，确保行为等价；不要一次叠加多个重构，否则回归无法归因。

值得注意的是，手法目录不是「越多越好」，而是「动机驱动」：先嗅到坏味道，再查目录找对应手法，而非为了用手法而改代码。Fowler 还强调「两顶帽子」：同一时段内要么加功能（行为变、测试红→绿），要么重构（行为不变、测试恒绿），不要混做，否则无法判断测试失败是功能问题还是重构引入。现代 IDE 的重构菜单本质上就是 catalog 的自动化版，但理解其背后的等价性逻辑，才能在自动化失败时手动兜底，也才敢在缺乏工具支持的语言里安全重构。

## 三、形式化与数学基础

重构保证「行为等价」。设原始函数 f_before，经变换 T 得到 f_after，对全部输入 x 有：

$$
\forall x,\ f_{before}(x) = f_{after}\big(T_{adapt}(x)\big)
$$

其中 T_adapt 是输入适配（如调用签名变化）。每一步后运行测试套件验证该等价性，等价于用测试集近似「全输入域」的等价证明。若测试套件覆盖关键行为，则小步重构的回归风险被约束在测试盲区之内。

## 四、代码实现

```python
# Extract Method：把计算逻辑抽出独立函数
def print_owing(invoice):
    # 反例：计算散落在打印流程中
    outstanding = 0
    for i in invoice.items:
        outstanding += i.amount
    print("name:", invoice.customer)
    print("amount:", outstanding)

# 重构后
def calc_outstanding(invoice) -> float:     # 抽出单一职责
    return sum(i.amount for i in invoice.items)

def print_owing(invoice):
    print("name:", invoice.customer)
    print("amount:", calc_outstanding(invoice))
```

## 五、与其他技术对比

- **重写（rewrite）**：改变行为或技术栈，风险高、周期长；重构则保证行为不变。
- **性能优化**：可能改变结构但目标不同（为了快），有时与可读性冲突。
- **单纯格式化**：只改样式不改善设计，是重构的「子集」而非全部。
- **大特性顺带改结构**：未以小步验证，易引入隐性回归。

## 六、常见误区

- **误区一：不写测试就重构**——失去安全网，等价于走钢丝。
- **误区二：一次做多个重构**——回归发生时无法定位是哪一步。
- **误区三：重构改了行为**——已越界成重写，需明确区分。
- **误区四：追求目录全用**——手法是工具，动机驱动才是关键。

## 八、面试题

- Extract Method 的步骤？如何保证重构不改变行为？
- Rename 为何是最安全的重构？
- 重构与重写的本质区别？
- 没有测试时能不能重构？应怎么办？

在团队层面落地手法目录，关键是「先识别、后查表、再小步」：评审时把坏味道与对应手法写进评论，让知识在 PR 中沉淀。自动化重构工具（IDE 的 Safe Rename、Extract，以及基于 LSP 的批量重命名）能显著降低人工出错，但工具只负责「等价变换」，是否该做、做到哪一步仍需人判断。建议把常用手法做成团队速查卡（cheat sheet），配合代码评审 checklist，使重构从「个人手艺」变为「团队共识」。

## 九、演进与趋势

现代 IDE 与语言服务器（LSP）已内置 Safe Rename、Extract、Inline 等自动化重构，降低人工出错；静态分析可自动推荐坏味道并给出重构候选。AI 辅助重构正在兴起，但「行为等价」验证仍依赖测试套件。具体工具能力以官方文档为准。

实践中一个常被忽视的纪律是「提交即重构」：每完成一个小功能，顺手用 Extract / Rename 把新代码整理到位，比事后统一清理更易坚持。当手法涉及跨文件移动（Move Method / Move Field），务必先在测试保护下小步验证，再扩大范围。记住手法是手段不是目的——若某个重构让代码更难懂，即使「符合 catalog」也应停止，重新评估动机是否真实存在。

## 十、小结

以测试为安全网，用小步、结构化的手法目录持续改善设计。重构不是一次性的英雄壮举，而是日常的工程纪律。
