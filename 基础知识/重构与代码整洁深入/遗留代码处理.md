# 遗留代码处理

> 对应 Michael Feathers《Working Effectively with Legacy Code》，及 CS-Notes（CyC2018）。

## 一、背景与挑战

Feathers 对遗留代码的定义直击要害：**「没有测试的代码」**。它不是「老代码」的同义词，而是「无法安全改动」的代码。直接改易碎——任何修改都可能引发看不见的回归，而你没有护盾发现它。挑战在于：如何在没有测试、依赖缠绕、行为不明确的前提下，安全地注入测试并逐步改善结构？

典型困境：想加个功能，却发现改一处会牵动多处；想写测试，却发现类 HardCode 了时间、数据库、网络等依赖，无法在隔离环境实例化。

## 二、核心原理

Feathers 提出「遗留代码改动算法」，顺序不可颠倒：

1. **识别改动点**：明确要改的类和函数。
2. **找测试点**：找到能观察行为的最小 seam。
3. **打破依赖**：通过子类化、接口提取、参数注入，把难以控制的依赖替换为可 Fake 的版本。
4. **写表征测试（characterization test）**：先锁定当前（哪怕是错误的）实际行为，断言「现在它就是这样」，防止重构意外改变它。
5. **再重构 / 加功能**：在绿灯护盾下安全地改。

核心是「先缝测试、锁行为，再改善结构」，与绿地开发「先测试后实现」相反——遗留代码先要「把行为钉住」。

## 三、形式化与数学基础

**接缝（seam）**：程序中的一个点，其旁的行为可以在**不修改该点代码**的前提下被替换。设依赖 D 经接缝 S 注入，则测试可传入假依赖 $D_{fake}$：

$$
call(S, D_{fake}) \quad \text{而非} \quad call(S, D_{real})
$$

表征测试锁定行为：设当前实现 f 对输入 x 输出 y（无论 y 是否「正确」），表征测试断言：

$$
\forall x \in Sample,\ test(x) = y = f(x)
$$

其后任何重构若改变了 y，测试即红灯——从而暴露等价性被破坏。注意：表征测试保护「现状」，不保护「正确性」，正确性测试需另写。

## 四、代码实现

```python
# 用子类覆盖受保护方法以隔离依赖（打破依赖）
class LegacyService:
    def get_time(self):
        return datetime.now()     # 难测：依赖真实时间

class FixedTimeService(LegacyService):
    def get_time(self):
        return FIXED_TIME        # 便于 characterization test

# 表征测试：先锁定当前行为
def test_legacy_behavior():
    svc = FixedTimeService()
    assert svc.process() == CAPTURED_CURRENT_OUTPUT   # 钉住现状
```

```python
# 用依赖注入制造接缝
def process(order, clock=datetime.now):   # clock 即接缝
    if clock() > DEADLINE:
        return "late"
```

## 五、与其他技术对比

- **绿地重构**：已有测试，直接按目录重构。
- **遗留代码处理**：优先「锁行为」而非「改善结构」，差异在起手式。
- **直接大改**：无护盾，回归风险失控。
- **测试替身（test double）技术**：子类化、mock、fake 都是制造 seam 的手段，与遗留处理强相关。

## 六、常见误区

- **误区一：先大改结构再加测试**——顺序反了，没护盾就动结构极危险。
- **误区二：凭印象假设旧行为**——旧代码行为常出人意料，必须 characterization 实测锁定。
- **误区三：表征测试变正确测试**——它只保护现状，正确性需额外验证。
- **误区四：所有代码都值得测**——优先锁高频变更 / 高风险路径，控制投入。

## 九、演进与趋势

可观测性（tracing、影子流量）辅助推断旧行为，降低 characterization 成本；增量重构工具与 AI 辅助生成表征测试，使老代码现代化更快。具体实践以团队工程规范为准。

## 十、小结

遗留代码不是「老」，而是「无测试」。先缝测试、锁行为，再渐进重构——这是把脆弱老代码变成可演进资产的唯一稳妥路径。
