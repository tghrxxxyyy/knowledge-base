# 命名与函数

> 对应 Robert C. Martin《Clean Code》第 2 章「Meaningful Names」、第 3 章「Functions」，及 CS-Notes（CyC2018）。

## 一、背景与挑战

命名与函数结构是代码可读性最直接的载体。糟糕的命名迫使读者反查上下文才能理解意图，长函数掩盖逻辑、增加认知负担，混乱的参数列表则容易引发调用错误。在大型协作项目中，命名问题会随代码膨胀被持续放大——阅读代码的时间远高于编写，糟糕命名实质上是在向每一位后续维护者征收「理解税」。

具体挑战包括：缩写泛滥导致语义丢失、布尔参数隐式切换行为、函数承担了过多职责难以测试、命令与查询混杂破坏可预期性。

## 二、核心原理

**命名**应遵循「揭示意图而非描述实现」：名字要回答「为什么存在、做什么、怎么用」，而非「它是什么类型或怎么存」。好的命名可替代大量注释。原则：

- 名副其实：名字与职责一致，无需再看实现。
- 避免误导：不用易混淆词（如 `accountList` 实际不是 List）。
- 做有意义区分：`a1/a2` 不如 `source/target`。
- 使用读得出、可搜索的名字；单字母仅限短作用域循环变量。

**函数**应：短小（Martin 建议不超过一屏、约 20 行内）、只做一件事（single responsibility）、参数尽量少（理想 0–2 个，最多 3 个）、无副作用（命令与查询分离）。一个大函数应被拆为多个单一意图的小函数，靠命名表达流程，而非靠注释解释。

## 三、形式化与数学基础

函数纯度可用其副作用集合度量。设 f 修改的状态集合为：

$$
SideEffects(f) = \{ s \mid f\ \text{修改}\ s \}
$$

理想纯函数满足 $SideEffects(f)=\emptyset$，其输出仅由输入决定，便于推理、并行与测试。参数个数影响调用组合复杂度，以排列视角看，k 个参数的可能误用组合随 k 增长而上升，故应聚合为对象（Introduce Parameter Object）以控制 k。

可测性边界：一个函数若副作用集非空且不可注入，则其行为难以在隔离环境下验证，这正是「依赖注入」存在的理由。

## 四、代码实现

```python
# 反例：命名模糊且带隐藏副作用
def get(d):          # 含义不清，且修改了状态
    d["x"] += 1
    return d["x"]

# 正例：意图清晰、单一职责
class Counter:
    def __init__(self) -> None:
        self.value = 0

    def increment(self) -> int:   # 命令：改变状态
        self.value += 1
        return self.value

    def snapshot(self) -> int:    # 查询：只读取，无副作用
        return self.value
```

```python
# 避免用布尔参数切换行为，应拆为两个函数
def save(user, as_draft: bool): ...      # 反例
def save_published(user): ...            # 正例
def save_draft(user): ...               # 正例
```

## 五、与其他技术对比

- **匈牙利命名等旧规**：强调类型前缀，现代语言有类型推导，可读性优先于类型暗示。
- **函数式编程**：与 Clean Code 共享「小而纯」理念，但 FP 更彻底地禁止副作用。
- **过长函数 + 注释**：用注释弥补结构混乱，本质是把不该有的复杂度转嫁给读者。
- **过度缩写**：短期少打字，长期高理解成本。

## 六、常见误区

- **误区一：用缩写节省字符**——IDE 自动补全已消除打字成本，可读性更值钱。
- **误区二：布尔参数切换行为**——调用点看不出语义，应拆两个函数。
- **误区三：函数稍长无所谓**——超过一屏后，理解成本非线性上升。
- **误区四：命令查询合一**——`deleteFile` 既删又返回是否存在，调用方易误用。

## 八、面试题

- 什么是命令查询分离（CQRS 思想在单函数层面的体现）？为什么函数参数不宜过多？
- 如何判断一个函数「只做一件事」？
- 布尔参数有什么问题？如何重构？
- 好名字的标准是什么？缩写何时可接受？

## 九、演进与趋势

类型推导（TypeScript、Rust、Kotlin）部分替代了命名中对类型的暗示，使名字更聚焦意图；LSP 的 rename 重构让重命名几乎零成本，鼓励「先写后改」地优化命名；AI 辅助命名建议也在降低命名负担，但意图判断仍靠人。

## 十、小结

好命名即好文档，小函数聚焦单一意图。把「揭示意图」作为命名与函数设计的北极星，能显著降低团队的长期理解成本。
