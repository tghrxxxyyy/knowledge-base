# 日志文件系统

> 对应 OSTEP 第 42 章“崩溃一致性”与 ext3/ext4 `fs/jbd2`。

## 一、背景与挑战
写文件涉及多个元数据更新（位图、inode、数据块）分散在磁盘。若中途崩溃，会留下不一致状态。日志（journal）通过“先写日志、再提交”保证原子性。

## 二、核心原理
- 写前日志（write-ahead logging）：先把待写事务写入日志区并提交标记，再写回主结构。
- 崩溃恢复时重放（replay）或撤销未完成事务。
- ext4 支持 data=ordered/journal/writeback 三种日志模式。

## 三、形式化 / 数学基础
事务提交协议：
1. 写数据到日志（含 checksum）；
2. 写 commit 记录；
3. 检查点（checkpoint）刷回主元数据。
恢复：扫描日志，遇 commit 且 checksum 合法则重放，否则丢弃。

## 四、代码实现
提交事务（示意）：

```c
void jbd_commit(transaction *t) {
    write_to_journal(t->buffers);   /* 1. 写数据 */
    write_commit_record(t);         /* 2. 写提交标记(含checksum) */
    fsync_journal();                /* 保证落盘 */
    checkpoint_to_fs(t);            /* 3. 回写主结构 */
}
```

## 五、与其他技术对比
无日志（ext2）崩溃后需 `fsck` 全量扫描；日志以小额日志写代价换快速一致恢复；copy-on-write 文件系统在另一维度解决一致性（见下篇）。

## 六、常见误区
- 认为日志=不丢数据：仅保元数据/有序一致性，不保证已写未提交内容。
- 忽略日志模式差异（ordered 最常用）。
- 混淆 journal 与 writeback 持久性语义。

## 九、演进与趋势
ext4 引入 `fast_commit` 缩短日志延迟；元数据校验和（metadata_csum）防静默损坏。

## 十、小结
日志文件系统以 WAL 把多步写聚成可重放事务，用小额日志写换取崩溃后快速一致恢复。
