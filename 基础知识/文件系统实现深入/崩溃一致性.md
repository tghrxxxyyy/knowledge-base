# 崩溃一致性

> 对应 OSTEP 第 41-42 章“崩溃一致性”与文件系统恢复。

## 一、背景与挑战
文件系统更新往往跨多个磁盘写（如创建文件要写位图、inode、目录项）。崩溃可能发生在任意两步之间，留下不一致。需要机制保证“要么全做、要么不做”。

## 二、核心原理
- 顺序约束：经典方案按“数据→inode→位图→目录项”顺序，使任意崩溃点都可被 `fsck` 修复。
- 日志（见上篇）与 CoW（见上篇）是两大现代方案。
- fsck 在挂载时检查并修复不一致（代价高）。

## 三、形式化 / 数学基础
把更新看作事务 $T=\\{w_1,w_2,\\dots,w_k\\}$。一致性不变量 $I$ 要求 $\\bigwedge$ 有关联关系成立。崩溃恢复须使系统处于 $I$ 为真状态：日志重放补全 $T$，或 fsck 依顺序规则修正。

## 四、代码实现
失败原子重命名（原子替换文件）：

```c
/* 先写临时文件, 再 rename 原子提交 */
fd = open("f.tmp", O_WRONLY|O_CREAT, 0644);
write(fd, data, len); fsync(fd); close(fd);
rename("f.tmp", "f");   /* 原子: 崩溃时要么旧f要么新f */
fsync(dirfd);
```

## 五、与其他技术对比
`fsck` 全量扫描慢且可能丢数据；日志快速重放；CoW 指针切换最干净。应用层“写临时+rename+fsync”是隔离崩溃的通用技巧。

## 六、常见误区
- 认为 `write` 返回即持久：需 `fsync` + 目录 fsync 才真正落盘。
- 忽略磁盘易失写缓存导致 reorder。
- 以为 ext4 默认就丢不了数据：取决于日志模式。

## 九、演进与趋势
`fsck` 被日志/CoW 大幅弱化；多副本（ZFS mirror）与端到端校验进一步抵抗静默损坏。

## 十、小结
崩溃一致性保证多步更新的原子可见：顺序写+fsck、WAL 日志、CoW 指针切换三层演进，应用层可用“临时文件+rename+fsync”获得原子提交。
