# 令牌刷新与撤销

> 对应 RFC 6749（OAuth 2.0，§1.5 刷新令牌）；RFC 7519（JWT）；RFC 9700（Security BCP）；OWASP 会话管理指南。

## 一、背景与挑战

`access_token` 若长期有效，一旦泄露攻击窗口就很长；但若过短（如几分钟），用户又要频繁重新登录，体验差。OAuth 用「短时 `access_token` + 长时 `refresh_token`」的组合化解这对矛盾：`access_token` 短命以缩小泄露窗口，`refresh_token` 长命用于静默换新。然而 `refresh_token` 本身却成了「长期可用」的高价值目标——它一旦被盗，攻击者可长期冒充用户。因此「刷新」必须以「可被撤销/侦测重用」为设计前提，否则从「缓解泄露」退化为「扩大泄露」。

## 二、核心原理

标准做法是**刷新轮换（refresh token rotation）**：每次用 `refresh_token` 换新 `access_token` 时，授权服务器同时签发一个全新的 `refresh_token` 并使旧的作废。客户端只保留「当前最新」的 refresh。安全收益来自一个不变量——同一个 `refresh_token` 不应被使用两次。一旦服务器检测到「某个已作废/旧的 refresh 被再次提交」，即可判定发生了泄露（攻击者与原客户端各自持有一份），此时**吊销整个令牌族（token family）**：把所有由该 refresh 派生的 access 与 refresh 一并作废，迫使重新登录。

此外 `access_token` 常配合「滑动过期」与「绝对过期」两套时钟：滑动过期在每次活动后顺延，提升用户体验；绝对过期（如 30 天）作为硬上限，保证无论如何都要重新认证，避免「永久在线」。「注销/撤销」则通过服务端维护的吊销列表（或把 refresh 标记无效）实现——关键在于吊销动作必须对后续所有派生令牌生效，而非只废当前 access。

从存储视角，refresh 必须「sender-constrained」（绑定到客户端）：要么存于 `HttpOnly`+`Secure`+`SameSite` Cookie 使其不进 JS 可控范围，要么绑定到 TLS 客户端证书 / DPoP 密钥，使即使被人截获也无法被第三方使用。把 refresh 明文放进 `localStorage` 是 XSS 场景下最常见、也最致命的失误。

还需注意并发场景：多个标签页或并行请求可能同时刷新，导致「客户端自己触发了重用侦测」而误吊销。工程上通常引入「同一 refresh 的短暂宽限期（grace window）」或让客户端串行化刷新，把「真实攻击」与「自身并发」区分开。

## 三、形式化与数学基础

令牌生命周期约束：

$$ t_{access} \ll t_{refresh} $$

轮换安全不变量：若 refresh $r_k$ 已被使用并轮换为 $r_{k+1}$，则任何后续出现的 $r_k$ 提交即视为泄露：

$$ reuse(r_k) \;\Rightarrow\; revoke\big(family(r_k)\big) $$

其中 $family(r_k)$ 为「由同一初始 refresh 衍生的全部令牌」。对 JWT 这类无状态 `access_token`，吊销无法靠「删服务端记录」实现，需额外机制：黑名单（短寿命、与 exp 同窗口）、版本号/族 ID（`jti` + 服务端记录该族是否已吊销），或把敏感操作要求重新认证。

把「误判率」纳入考虑：设正常并发导致的重复提交概率为 $p_c$，真实攻击导致的重复提交概率为 $p_a$。宽限期把 $p_c$ 压低的同时也会给攻击者一个窗口，因此宽限期 $g$ 的选择是一个显式权衡：

$$g \downarrow \Rightarrow p_c \uparrow\ (\text{误吊销}), \qquad g \uparrow \Rightarrow \text{攻击窗口} \uparrow$$

实践中 $g$ 通常取「秒级」，与本系统单次刷新耗时同量级。

## 四、代码实现

下面给出刷新并轮换、侦测重用即吊销的简化逻辑：

```python
def refresh(rt):
    fam = store.get_family(rt)
    if rt != fam.current:            # 非当前最新 → 检测到重用/旧令牌
        if within_grace(rt, fam):    # 宽限期内视为并发，非攻击
            return {"access_token": issue_access(fam.user),
                    "refresh_token": fam.current}
        fam.revoke_all()             # 吊销整族，迫使用户重新登录
        return 403
    new_rt = fam.rotate()            # 签发新 refresh，作废旧 rt
    new_at = issue_access(fam.user)  # 签发新 access
    return {"access_token": new_at, "refresh_token": new_rt}
```

```python
# JWT 兜底吊销：族 ID + 版本号，服务端只需记录被吊销的族
def verify_access(at, jwt_key, revoked):
    claims = jwt.decode(at, jwt_key, algorithms=["EdDSA"])
    # 无状态校验之外，检查该族是否已被吊销（黑名单按族而非按 token）
    if claims["fam"] in revoked:      # 族级黑名单，条目数远小于逐 token
        return False
    if claims["ver"] != store.current_version(claims["fam"]):
        return False                  # 版本不匹配 → 已轮换失效
    return True
```

按族（而非逐个 token）维护吊销记录，可让黑名单规模从「与令牌数同阶」降到「与活跃族数同阶」，是分布式场景下的关键优化。

## 五、与其他技术对比

| 方案 | 吊销成本 | 泄露影响 | 适用 |
| --- | --- | --- | --- |
| 短 access + 长 refresh（不轮换） | 中 | 大（refresh 长期可用） | 不推荐 |
| 刷新轮换 + 重用侦测 | 低 | 小（侦测即吊销整族） | 推荐 |
| 无状态 JWT + 黑名单 | 中（需共享存储） | 取决于黑名单覆盖 | 分布式 |
| Sender-constrained（DPoP/mTLS） | 低 | 极小（令牌不可被第三方使用） | 高安全场景 |

短 `access` + 刷新比「长 `access`」安全；服务端黑名单与「轮换 + 重用侦测」各有成本——前者适合无状态 JWT 的兜底吊销，后者从根源降低 refresh 被盗价值。

## 六、常见误区

误区一：`refresh_token` 长期不变没关系。错——不变意味着一旦拖库即长期失陷，轮换是缩小窗口的关键。

误区二：前端把 refresh 存 localStorage。错——XSS 即可窃取，应优先存于 `HttpOnly`、`Secure`、`SameSite` Cookie 或服务端会话。

误区三：忽略轮换导致「一钥永逸」。错——不轮换等于把长期凭证静态暴露，违背刷新设计的初衷。

误区四：JWT 无法吊销所以不用管。错——可用族 ID/黑名单/`jti` 机制兜底，绝非零信任的借口。

误区五：重用侦测一定准确。错——客户端并发刷新会触发误报，需宽限期或请求串行化来区分。

误区六：注销只需删本地令牌。错——若不使服务端记录失效，被盗的 refresh 仍可继续换取新 access。

## 七、与开源书·权威来源对应

- RFC 6749 §1.5 定义 `refresh_token` 的用途、保密要求与撤销语义。
- RFC 9700（Security BCP）建议 refresh 轮换与绑定（sender-constrained）令牌。
- OWASP 会话管理备忘强调令牌的最短寿命、安全存储与吊销能力。
- RFC 9449（DPoP）定义用客户端密钥绑定令牌的具体机制，是 sender-constrained 的标准化方案。
- 图解网络（xiaolincoder/hello-http）对刷新流程有图解。

## 八、面试题

1. 为何用「短 access + 长 refresh」？要点：缩小 access 泄露窗口、又避免频繁重新登录。
2. 轮换如何侦测泄露？要点：同一 refresh 被用两次即判泄露，吊销整族令牌。
3. JWT 如何吊销？要点：族 ID/黑名单/`jti` + 服务端记录，或要求重新认证敏感操作。
4. refresh 应存哪？要点：`HttpOnly`+`Secure`+`SameSite` Cookie 或服务端会话，避免 XSS 可窃的 localStorage。
5. 如何区分「攻击重用」与「客户端并发」？要点：宽限期或请求串行化；同一族短时间内多次提交按并发处理，超窗口则判攻击。
6. 为什么按族吊销比逐 token 吊销更可行？要点：族数量远小于 token 数量，且族级黑名单天然覆盖所有派生的 access 与 refresh，避免漏网。

## 九、演进与趋势

DPoP（RFC 9449）与 Token Binding 把令牌与客户端密钥/TLS 绑定，使被盗令牌也无法被他人重放；「绑定 cookie 的刷新」（refresh in secure cookie）降低前端暴露；续期令牌（bound token）与「撤销即失效」的短寿命设计持续压缩攻击窗口。

另一趋势是「令牌寿命进一步缩短 + 自动轮换」：当 access 寿命缩到分钟级、refresh 也频繁轮换时，黑名单窗口随之缩小，甚至可以在多数场景下放弃服务端黑名单，仅靠寿命与版本号实现等效吊销。这一取舍取决于业务的实时性要求与存储成本，应以官方最新规范与安全指南为准。

## 十、小结

刷新令牌以「轮换 + 短命 access」在体验与安全间平衡，**轮换侦测重用是吊销泄露的关键不变量**——同一 refresh 二次出现即判失陷并吊销整族。配合安全存储与 JWT 兜底吊销机制，构成现代令牌生命周期管理的核心；而并发误报与宽限期设计，是把该机制真正落地时必须处理的工程细节。
