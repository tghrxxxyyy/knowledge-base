# 快速恢复与拥塞窗口

> 对应 RFC 5681 快速恢复算法（Reno 式）与 xiaolincoder/hello-http 拥塞控制说明。

## 一、背景与挑战
丢包通常意味着网络出现拥塞，发送方必须降速。但「快速重传」已通过重复 ACK 证明：网络仍能交付后续段，说明拥塞并不严重、管道并未完全断流。此时若像超时那样把 cwnd 直接降到 1 进入慢启动，会过度反应、白白浪费已建立的吞吐。快速恢复（fast recovery）的目标，就是在丢包后「平滑降速」而非「断崖式重启」，既响应拥塞又维持管道充盈。

这在长肥管道（高带宽时延积，BDP）下尤为重要：慢启动从 1 涨回原 cwnd 需要数十个 RTT，期间带宽几乎闲置；快速恢复则把 cwnd 维持在半数附近，恢复快得多。因此快速恢复是高速网络吞吐的守护者，也是 Reno 相对 Tahoe 的核心改进。

它的哲学可以概括为「区分轻重」：超时代表「连确认都收不到」，是重信号，必须重罚；重复 ACK 代表「部分数据仍在流动」，是轻信号，只需轻罚。AIMD 家族正是建立在这种信号分级之上。

## 二、核心原理
Reno 式快速恢复在收到第 3 个重复 ACK、触发快速重传的同时进入：先把 ssthresh 设为当前 flight 的一半（至少 $2\cdot\text{SMSS}$），再把 cwnd 设为 ssthresh $+\,3\cdot\text{SMSS}$——这 3 个 MSS 是为「已经离开网络、被接收方缓存的 3 个重复 ACK 所对应的段」预留的「在途额度」。此后每再收到一个重复 ACK，cwnd 临时 $+1$ 个 MSS（即「拥塞窗口膨胀」），让发送方在恢复期间仍能继续发新数据、保持管道不满。

直到收到一个「覆盖全部已发数据」的新 ACK（new ACK），才把 cwnd 收敛回 ssthresh，退出快速恢复、进入拥塞避免。这个「临时膨胀」不是随心所欲：它精确补偿了接收端已缓存但发送端尚不知情的段，使「发送端估计的在途量」与「网络实际在途量」大致对齐。

理解这一点很关键：快速恢复并非「不做降速」，而是「把降速做得刚好」。它把窗口从 cwnd 降到约一半，同时用膨胀项抵消误判带来的空洞，使吞吐平滑过渡。

## 三、形式化与数学基础
进入快速恢复时：

$$ \text{ssthresh} = \max\left(\frac{\text{cwnd}}{2},\, 2\cdot \text{MSS}\right),\quad \text{cwnd} = \text{ssthresh} + 3\cdot \text{MSS} $$

每收到一个重复 ACK：$\text{cwnd} \leftarrow \text{cwnd} + \text{MSS}$（临时膨胀）。收到 new ACK（确认了快速重传时点之后的所有数据）：$\text{cwnd} = \text{ssthresh}$，状态切到拥塞避免（CONG_AVOID）。拥塞避免阶段每收到一个 RTT 的 new ACK，cwnd $+=$ MSS（加法增大，AIMD 的「增」）。

注意膨胀只在「仍有重复 ACK 到来」期间存在，new ACK 一到即回落，不会无限增长——因为 new ACK 意味着所有在途段都已确认，无需再为「离网段」保留额度。整个 AIMD（加法增大、乘法减小）在数学上保证多个流收敛到公平共享点，这是其被长期沿用的理论依据。

## 四、代码实现
```python
MSS = 1460
SLOW_START, FAST_RECOVERY, CONG_AVOID = 0, 1, 2

def on_dup_ack(seq):
    global cwnd, ssthresh, state, dup_count
    if state == SLOW_START and dup_count == 3:
        ssthresh = max(cwnd // 2, 2 * MSS)
        cwnd = ssthresh + 3 * MSS      # 为 3 个离网段留额度
        retransmit(seq)
        state = FAST_RECOVERY
    elif state == FAST_RECOVERY:
        cwnd += MSS                    # 每 dup ack 临时膨胀

def on_new_ack():
    global cwnd, state
    if state == FAST_RECOVERY:
        cwnd = ssthresh                # 收敛回 ssthresh
        state = CONG_AVOID

def on_timeout():
    global cwnd, ssthresh, state
    ssthresh = max(flight // 2, 2 * MSS)
    cwnd = MSS                         # 超时：回到慢启动
    state = SLOW_START
```

上述是 Reno 经典版；Linux 实际实现中还有「PRR（Proportional Rate Reduction）」算法，它在快速恢复期间更平滑地降速，避免窗口在恢复中过度膨胀，已被 RFC 6937 标准化并作为 Linux 默认。PRR 的核心思想是「按已确认比例线性放出新数据」，比 Reno 的「每 dup ACK +1」更可控，尤其在多段丢失时更稳。

## 五、与其他技术对比

| 算法 | 丢包后 cwnd | 是否进慢启动 | 恢复速度 |
| --- | --- | --- | --- |
| Tahoe | 降到 1 | 是 | 慢 |
| Reno（快速恢复） | 半速 + 临时膨胀 | 否 | 快 |
| NewReno | 半速，逐段部分确认 | 否 | 较快（多丢更好） |
| CUBIC | 半速附近，按三次函数增 | 否 | 高速网络更优 |
| BBR | 不依赖丢包信号 | 否 | 绕开丢包 |

Tahoe 对任何丢包都退慢启动，过度保守；Reno 引入快速恢复避免该反应；NewReno 通过「部分确认」增强多段丢失场景；CUBIC/BBR 进一步适配高 BDP 网络。BBR 完全用带宽/RTT 模型，不再把丢包当作拥塞唯一信号，因此根本不经过「快速恢复」这一基于丢包的语义，而是独立调控 pacing rate。

## 六、常见误区
- 误区一：快速恢复后 cwnd 立即回 1。那是超时/慢启动行为；快速恢复是半速。
- 误区二：窗口膨胀会无限增长。仅持续到收到 new ACK，随即回落到 ssthresh。
- 误区三：加法增大太慢。在长肥管道（高 BDP）下确实偏慢，这正是 CUBIC/BBR 的动机。
- 误区四：快速恢复能处理多段丢失。Reno 式快速恢复对单段丢失有效，多段丢失会反复触发、效率下降，需 SACK/FACK/RACK 增强。
- 误区五：快速恢复是独立算法。它必须与快速重传配套，单独「恢复」没有意义，二者是同一机制的两种动作。
- 误区六：快速恢复会改变拥塞避免的加性增长。它只影响恢复期的窗口调度，退出后仍回到标准加性增长。
- 误区七：ssthresh 减半即最终窗口。它只是进入时的目标，恢复期窗口会临时高于它。

## 七、与开源书·权威来源对应
RFC 5681 第 3.2 节严格定义快速重传与快速恢复（Reno 式）的状态机与 cwnd 公式。xiaolincoder/hello-http 用图示展示 cwnd 在快速恢复期间的膨胀与收敛。Kurose & Ross《Computer Networking》在 TCP 拥塞控制章描述 AIMD（加法增大、乘法减小）。RFC 6937（PRR）描述了更现代的恢复降速策略。Linux 的 `tcp_cong.c` 实现 Reno，CUBIC 为默认，PRR 在 `net/ipv4/tcp_cong.c` 与 `tcp_input.c` 中实现。

具体实现细节与默认算法随内核版本演进，阅读源码时以对应版本的官方文档为准。

## 八、面试题
- 问：快速恢复中 cwnd 怎么变？答：进入时设 ssthresh$+3$MSS，每 dup ACK $+$MSS，new ACK 后回到 ssthresh。
- 问：为何临时膨胀？答：为已离网的 3 个段保留在途额度，维持管道不满。
- 问：ssthresh 怎么设？答：$\max(\text{cwnd}/2, 2\cdot\text{MSS})$，即乘法减小的一半。
- 问：Reno 与 Tahoe 区别？答：Reno 丢包后快速恢复而非慢启动。
- 问：PRR 是什么？答：Linux 默认的比例降速恢复算法，比 Reno 膨胀更平滑。
- 问：快速恢复与拥塞避免如何衔接？答：收到 new ACK 后 cwnd 回到 ssthresh，状态切到拥塞避免。
- 问：为何快速恢复不适用于超时？答：超时缺乏「仍在交付」的证据，必须按重信号处理，回到慢启动。

## 九、演进与趋势
现代 Linux 默认拥塞控制已从 Reno 演进到 CUBIC，后者在快速恢复之外用三次函数更激进、对 BDP 敏感地恢复窗口；BBR 则完全绕过「丢包 $=$ 拥塞」假设，用带宽/RTT 模型驱动。但快速恢复的「半速 + 临时膨胀」语义在各类算法中仍被广泛保留，是 AIMD 家族的核心环节，并被 PRR 改良得更平滑。

未来演进方向是在多段丢失场景下用更精确的 scoreboard 替代「$+3$MSS」的启发式，并与 pacing、ECN 等机制协同。相关算法与默认配置以官方最新文档为准。

## 十、小结
快速恢复在丢包后以「半速 + 临时膨胀」平滑降速并维持管道充盈，避免了 Tahoe 的过度慢启动，是 Reno 式 AIMD 中兼顾「响应拥塞」与「保持吞吐」的关键。理解它与快速重传、拥塞避免的衔接，以及 PRR 对膨胀的改良，是读懂 TCP 拥塞控制状态机的核心。
