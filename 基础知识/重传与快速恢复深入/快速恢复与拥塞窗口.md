# 快速恢复与拥塞窗口

> 对应 RFC 5681 快速恢复算法（含 Reno 式）与 xiaolincoder/hello-http 的拥塞控制说明。

## 一、背景与挑战
丢包代表网络可能拥塞，必须降速；但「快速重传」已表明网络还能交付后续段，不应像超时那样剧烈降到 1。快速恢复的目标是在丢包后平滑降速、维持管道充盈。

## 二、核心原理
进入快速恢复时：ssthresh 设为当前 flight 的一半（至少 2·SMSS），cwnd 设为 ssthresh + 3·SMSS（为已离网的 3 个段留余量）。此后每收到一个重复 ACK，cwnd 临时 +1 个 SMSS（「拥塞窗口膨胀」），让发送方继续发新数据以维持吞吐。收到新数据的 ACK 后，cwnd 收敛回 ssthresh，退出快速恢复进入拥塞避免。

## 三、形式化与数学基础
进入：ssthresh = max(cwnd/2, 2·MSS)；cwnd = ssthresh + 3·MSS。
每 dup ACK：cwnd += MSS（临时）。
退出（新 ACK 覆盖全部飞行数据）：cwnd = ssthresh；state = CONG_AVOID。
拥塞避免阶段：每 RTT 使 cwnd += MSS（加法增大）。

## 四、代码实现
```python
def fast_recovery():
    ssthresh = max(cwnd//2, 2*MSS)
    cwnd = ssthresh + 3*MSS
    # 每 dup ack:
    cwnd += MSS
    # 新数据 ack:
    cwnd = ssthresh
```

## 五、与其他技术对比
Tahoe 在任一直失（含快速重传触发）都退到慢启动，Reno 引入快速恢复避免该过度反应；CUBIC 用三次函数替代线性拥塞避免以适配高速网络；BBR 则完全绕过 cwnd 式的丢包信号。

## 六、常见误区
误区一：快速恢复后 cwnd 立即回 1——那是超时/慢启动。误区二：膨胀会无限增长——仅持续到收到新 ACK。误区三：加法增大太慢——在长肥管道下确实偏慢，这正是 CUBIC/BBR 动机。

## 七、与开源书/权威来源对应
RFC 5681 第 3.2（快速恢复）为权威；xiaolincoder/hello-http 图示状态机；Kurose & Ross 描述 AIMD。

## 九、演进与趋势
CUBIC 在快速恢复外采用了更激进、对 BDP 敏感的窗口增长；Linux 默认拥塞控制已从 Reno 演进到 CUBIC，快速恢复语义仍保留。

## 十、小结
快速恢复在丢包后以「半速 + 临时膨胀」平滑降速并维持管道，是 AIMD 中避免恢复过激的关键环节。
