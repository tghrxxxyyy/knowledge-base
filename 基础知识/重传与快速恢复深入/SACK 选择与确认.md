# SACK 选择与确认

> 对应 RFC 2018（SACK 选项）与 RFC 6675（SACK 重传算法），以及 xiaolincoder/hello-http。

## 一、背景与挑战
标准 TCP 的累积 ACK 只能确认「连续字节流的前缀」：若序号 1~1000 已收、1001~1100 丢失、1101~2000 已收，接收方只能 ACK 到 1000，发送方无从得知 1101~2000 其实已安全到达。当多个不连续段同时丢失时，发送方只能「盲目重传」所有未确认段，造成大量无效重传、吞吐骤降。选择性确认（SACK）让接收方汇报「已收到但不连续」的块，发送方据此精准重传真正丢失的段。

这个问题在长肥管道和高丢包率链路（如卫星、跨洋）上尤其致命：多段同时丢失时，无 SACK 的恢复几乎退化成逐段超时，吞吐可下降一个数量级。SACK 是把「多丢」从灾难变成「可管理」的关键，也是后续 FACK、RACK 的信息基础。

换句话说，累积 ACK 回答的是「连续到哪里」，SACK 回答的是「除此之外还收到了哪些」。信息量的差异，正是「盲重传」与「精准重传」的分水岭。

## 二、核心原理
接收方在 TCP 选项里携带若干 SACK 块，每块是 $[left, right)$ 字节范围，报告已收但超出累积 ACK 的「洞外数据」。发送方维护一张「记分板（scoreboard）」记录哪些段已确认（含 SACK 覆盖的），重传时只覆盖「既未被累积 ACK、也未被 SACK 覆盖」的未确认区间。这样多段丢失时只重传空洞段，避免对已达段重传，显著提升多丢场景吞吐。

D-SACK（RFC 2883）扩展 SACK，用第一个块报告「重复接收」的段，帮助发送方检测虚假重传与 ACK 丢失。当发送方看到 D-SACK，就能意识到「我重传的段其实对端早就收到了」，从而避免把 RTO 估计得过大或反复无谓重传。

SACK 与「累积 ACK 必须保留」的关系不能颠倒：接收方仍须先发出累积 ACK，再附带 SACK 选项；SACK 是补充，不是替代。

## 三、形式化与数学基础
设 SACK 块集合为有序不重叠区间 $B = \{[l_i, r_i)\}$，累积 ACK 序号为 $a$。未确认区间：

$$ U = [a,\; \text{send\_high}) \setminus \left(\bigcup B\right) $$

重传只需覆盖 $U$ 中的段。RFC 6675 的 pipe 算法估算「在途未确认且未被判丢失」的字节数 pipe，发送方仅在 $\text{pipe} < \text{cwnd}$ 时才可发新/重传数据，从而既利用 SACK 信息又不冲破拥塞窗口。scoreboard 持续更新：每收到 SACK 即把对应区间标记为「已确认」。

pipe 的核心思想是「按已离网但未确认的数据量控制发送」，比单纯 cwnd 更精细——它防止在已确认数据上「重复发送」，相当于用 SACK 信息修正了 cwnd 的有效含义。这也解释了为何同一 cwnd 下，启用 SACK 后实际发送量可以更接近链路容量。

## 四、代码实现
```c
/* 接收方：在 TCP 选项里回报已收但不连续的块（内核伪代码） */
skb_put_sack(skb, start_seq, end_seq);   /* 加入一个 SACK 块 */

/* 发送方：仅重传未被 SACK 覆盖的未确认段 */
for (seg in unacked_queue) {
    if (!covered_by_sack(seg) &&
        !recently_retransmitted(seg)) {
        retransmit(seg);                 /* 精准重传空洞 */
    }
}
```

Linux 内核中，`tcp_sacktag_write_queue` 负责解析入站 SACK 并更新 scoreboard，`tcp_mark_lost_retrans` 与 `tcp_time_to_recover` 据此决定哪些段标记丢失。实际实现还结合 FACK/RACK 计算更稳妥的丢失判据，并为每个 skb 维护 `sacked` 标志位记录其被 SACK 覆盖的状态，避免每次全量扫描。

## 五、与其他技术对比

| 机制 | 能告知的信息 | 重传精度 |
| --- | --- | --- |
| 累积 ACK | 仅连续前缀 | 盲（只能猜） |
| SACK | 洞外已收块 | 精准（知空洞） |
| D-SACK | 重复接收块 | 检测虚假重传 |
| RACK | 时间序丢失 | 乱序/尾部更鲁棒 |
| FACK | 前向确认点到序号距离 | 减少伪重传 |

无 SACK 时发送方只能靠 dup ACK 猜测；SACK 把「猜」变「知」。D-SACK 进一步让发送方意识到「自己重传了其实对方已收到的段」，从而下调 RTO 或避免误判。RACK 在 SACK 之上补时间维度，专门处理尾部丢失与严重乱序；FACK 则用前向确认点判断重排距离。

## 六、常见误区
- 误区一：SACK 替代累积 ACK。不，累积 ACK 始终是基础，SACK 只是补充，接收方仍须先发累积 ACK。
- 误区二：SACK 块越多越好。TCP 选项空间有限（通常 40 字节），最多约 3 个 SACK 块（每块 8 字节 + 2 字节 kind/len）。
- 误区三：SACK 自动开启。需通信两端都支持并在握手时隐含可用，任一方不支持则只用累积 ACK。
- 误区四：有 SACK 就无需快速重传。SACK 提供信息，但触发重传仍需 dup ACK / RACK 等机制配合。
- 误区五：SACK 能解决尾部丢失。尾部单段丢失无后续段产生 SACK，仍需 RACK/TLP 补救。
- 误区六：SACK 块必须有序。RFC 允许乱序，接收方应尽量按序排列但发送方不应假设有序。
- 误区七：SACK 可以携带任意多信息。受选项长度硬约束，超出的已收区间只能靠「更新已有块」间接表达。

## 七、与开源书·权威来源对应
RFC 2018 定义 SACK 选项格式；RFC 2883 定义 D-SACK；RFC 6675 定义基于 SACK 的丢失恢复与 pipe 算法；Linux `net/ipv4/tcp_input.c` 实现 scoreboard。xiaolincoder/hello-http 展示多段丢失下的 SACK 恢复；Kurose & Ross 在可靠传输章讨论选择性重传（SR），指出 SR 与 Go-Back-N 的本质区别正是「选择性重传」——SACK 正是 SR 在 TCP 中的落地。

具体选项编码与内核实现随版本演进，细节以对应 RFC 与官方文档为准。

## 八、面试题
- 问：SACK 与累积 ACK 区别？答：累积 ACK 只确认连续前缀，SACK 额外报告不连续已收块。
- 问：D-SACK 用途？答：报告重复接收，检测虚假重传与 ACK 丢失。
- 问：为何 SACK 块数有限？答：TCP 选项空间有限，最多约 3 块。
- 问：SACK 如何提升多丢吞吐？答：只重传真正空洞段，避免无效重传。
- 问：pipe 算法作用？答：按在途未确认量控制发送，避免冲破拥塞窗口。
- 问：SACK 与快速重传谁触发谁？答：SACK 提供信息，重传仍由 dup ACK/RACK 等机制触发。
- 问：SACK 能否解决尾部丢失？答：不能，需 RACK/TLP 等时间序或探测机制补足。

## 九、演进与趋势
RACK（RFC 8985）与 SACK 协同：SACK 提供精确「哪些已收」信息，RACK 用「发送时间序」处理重排与尾部丢失，弥补 SACK 在「尾部单段丢失、无后续段触发 SACK」时的盲区。Linux 默认启用 SACK（除非与某些不兼容中间件通信需关闭）。

随着 QUIC 普及，SACK 思想被 ACK 帧的「缺失范围」机制继承，但 QUIC 天然带时间信息，更接近 RACK 语义。相关实现与默认行为以官方最新文档为准。

从编码角度看，每个 SACK 块占 8 字节（左边界 4 字节 + 右边界 4 字节），加上选项的 kind/len 共 2 字节；40 字节的 TCP 选项空间除去时间戳（通常 10 字节）后，实际能容纳的块数相当有限，这也是接收端必须「择优报告」的原因。

启用 PAWS/时间戳后选项空间进一步紧张，实战中 SACK 往往只能报 2~3 个块；接收端应优先报告最靠前的空洞之后的数据，以最大化发送端可判定的信息量。

部分老旧防火墙或负载均衡会剥离、重写未知 TCP 选项，导致 SACK 在单侧生效或被静默丢弃；排查时可用抓包确认双方是否真的都在携带 SACK 选项。

ECN 让拥塞在丢包前被显式标记，SACK 则让丢包后的恢复更精准，二者一「防」一「治」，共同提升高 BDP 链路的有效吞吐。

部署上，优先确保两端使用较新内核，避免在存在老中间盒的路径上强依赖 SACK；在数据中心内部可放心启用，在跨广域链路上应保留「无 SACK 也能工作」的降级路径。

## 十、小结
SACK 通过选择性确认让发送方精准重传，是多段丢失场景维持高吞吐的核心机制；配合 RFC 6675 的 scoreboard 与 pipe 算法实现高效恢复，D-SACK 则增强对虚假重传的感知。它是现代 TCP 可靠性与高性能的基石之一，也是从「盲目重传」走向「精准恢复」的分水岭。
