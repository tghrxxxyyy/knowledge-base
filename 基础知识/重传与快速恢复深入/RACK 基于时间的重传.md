# RACK 基于时间的重传

> 对应 RFC 8985（RACK：Time-Based Loss Detection）与 Google RACK 文档，结合 xiaolincoder/hello-http。

## 一、背景与挑战
传统「3 个重复 ACK」与序号距离判断（FACK）在两类场景下失灵：一是严重乱序（路径重排使段大幅错位），易误判丢包造成伪重传；二是尾部丢失（最后一个段丢了，没有后续段来产生 dup ACK / SACK），只能苦等 RTO。RACK（Recent ACKnowledgment）改用「时间」作为丢失判据：若某段发出后，比它更晚发出的段都已确认，而它仍未确认，则判定它丢失。这天然适配乱序与尾部丢失。

在移动网络、Wi-Fi 等乱序普遍的环境中，RACK 带来的收益尤其明显：它把「乱序误判」与「尾部超时」两大痛点同时缓解，是近年 Linux 内核最实用的传输层改进之一，也是 BBR 等现代拥塞控制得以稳定工作的前提。

RACK 的洞察很朴素却深刻：丢包的本质不是「序号落后」，而是「在合理时间内没有被确认」。既然时间才是最自然的维度，就应该用时间来判断。

## 二、核心原理
RACK 维护一个按「发送时间」排序的已发送段序列。每当收到一个 ACK/SACK 确认了某个「相对较新发送」的段，就把所有「发送时间早于该段、却仍未确认」的段标记为丢失——但仅当它们已超过可配置的 RACK 重排序窗口（允许一定重排时间）时才标记。

这样：乱序时只要在窗口内、晚发段先到不会误杀早发段；尾部丢失时，只要后续某段（或探测段）被确认、而尾段迟迟未确认，超时窗口一到即判定丢失，无需等 3 个 dup ACK。

RACK 还区分「原始发送时间」与「重传时间」：对重传段使用重传时刻作为时间戳，避免把重传误当新证据。这是早期时间序方案容易踩的坑，也是 RFC 8985 明确规定的细节。

## 三、形式化与数学基础
设段 $x$ 的发送时刻为 $t_x$，最新被确认的段 $y$ 有发送时刻 $t_y \ge t_x$。若

$$ t_{\text{now}} - t_x > \text{RACK\_reorder\_window} \quad \text{且 } x \text{ 仍未确认} $$

则标记 $x$ 丢失。RACK_reorder_window 通常取 $k\cdot\text{RTT}$（$k\approx1$），并随观测到的重排情况自适应放大（如测量到历史上最大的重排延迟）。该判据本质是「以发送时刻排序的偏序」替代「以序号排序」，因此对乱序鲁棒。

更进一步，RACK 维护的重排窗口是对「网络最坏重排」的在线估计：窗口越大越保守（不易误判但发现慢），越小越激进。自适应机制让它在乱序轻微时收紧、乱序严重时放宽，兼顾准确与及时。

## 四、代码实现
```python
RACK_MIN_RTT = 0.001  # 秒，示意

def on_ack(seq, t_send, now):
    global rack_window
    for seg in sent_segments_older_than(t_send):
        if not seg.acked and (now - seg.t_send) > rack_window:
            mark_lost(seg)          # 时间序判定丢失
    maybe_retransmit()              # 重传被标记段

# TLP：尾部丢包时在 RTO 前发一个探测段，制造一个「新确认」
# send_probe_segment()
```

Linux 中 `tcp_rack_mark_lost` 遍历 skb 队列，按 `skb->skb_mstamp_ns`（发送时间）与最新被确认段的时间差判定。RACK 与 TLP 协同：TLP 在尾部丢失时发出探测段，该段被确认后即为更早的尾段提供「时间序证据」，从而在 RTO 之前完成判定。

探测段通常用已确认过的数据或凑一个字节，不破坏语义。

## 五、与其他技术对比

| 判据 | 维度 | 乱序敏感度 | 尾部丢失 |
| --- | --- | --- | --- |
| 3 dup ACK | 计数 | 高（易误判） | 无法处理 |
| FACK | 序号距离 | 高 | 部分 |
| RACK | 发送时间 | 低（窗口容忍） | 能处理 |
| TLP | 探测 | — | 强 |
| SACK | 确认范围 | 低（信息辅助） | 不能 |

RACK 是「时间序」、最贴近真实传播与排队；TLP 常与 RACK 配合，在尾部丢包时主动发探测避免等 RTO。相比计数/distance 判据，RACK 把「时间」作为第一性证据，更符合网络本质——丢包本就是「在合理时间内未确认」，时间本就是最自然的判据。

## 六、常见误区
- 误区一：RACK 完全不用 dup ACK。实现仍常把 dup ACK 作为快速触发之一，只是不再唯独依赖计数。
- 误区二：时间窗口固定。会据重排观测自适应放大，避免把正常重排误判为丢包。
- 误区三：RACK 替代超时。超时仍是最终兜底，RACK 只是更早更准地提前判定。
- 误区四：RACK 只用于重传。它也改善「重传计时」与「cwnd 恢复」的时机判断。
- 误区五：RACK 与 SACK 互斥。二者互补：SACK 给「哪些已收」，RACK 给「何时判丢」。
- 误区六：重传段与原始段同等对待。RACK 需用重传时间戳，否则判定会出错。
- 误区七：窗口越大越安全。窗口过大会延迟发现丢包，需在准确与及时间权衡。

## 七、与开源书·权威来源对应
RFC 8985 是 RACK 的权威规范；Google 的 RACK 设计文档阐述动机与算法；xiaolincoder/hello-http 在重传章提及；Linux 4.9+ 默认启用 RACK 与 TLP。Mathis 等的 FACK 论文是序号距离判据的前身。Linux `net/ipv4/tcp_recovery.c` 实现 RACK 状态机，与 `tcp_input.c` 的 SACK 处理共同构成默认恢复路径。

具体默认参数与实现细节随内核版本演进，以对应 RFC 与官方文档为准。

## 八、面试题
- 问：RACK 为何用时间而非计数？答：乱序与尾部丢失下计数/dup ACK 失灵，时间序更贴近真实传播。
- 问：如何避免乱序误判？答：设 RACK 重排序窗口容忍一定重排延迟，窗口内不标记丢失。
- 问：与 TLP 关系？答：TLP 发探测段制造新确认，帮助 RACK 在尾部丢失时及时判定。
- 问：尾部丢失怎么处理？答：靠后续段/探测段的确认触发时间序判定，不必等 RTO。
- 问：RACK 窗口如何自适应？答：跟踪历史最大重排延迟，动态放大以容忍正常乱序。
- 问：RACK 与 SACK 如何分工？答：SACK 报告已收范围，RACK 决定何时判定丢失。
- 问：重传段为何要用独立时间戳？答：避免把重传时刻误当原始发送时刻而错判。

## 九、演进与趋势
RACK 已是 Linux 默认丢失检测机制，与 SACK、TLP 协同，逐步取代纯 Reno 式 3-dupACK 判断，显著提升真实网络（尤其移动、高乱序）下的恢复性能。后续工作把 RACK 与 BBR 的传输模型进一步整合，使丢失检测与带宽探测共享同一时间视图。

随着 QUIC 普及，时间序判定成为主流，RACK 的思想被直接吸收进 QUIC 的丢包检测。相关演进以官方最新文档为准。

在发送侧，RACK 与 pacing 的配合也很关键：判定丢失后会集中重传若干段，若不配合 pacing，爆发式重传可能瞬时打满链路并引发二次拥塞。

RACK 与 FACK 的分工可以这样理解：FACK 提供「序号距离」证据，RACK 提供「时间」证据，二者在现代内核中并存、互为补充，而非一个取代另一个。

与 QUIC 对照，QUIC 的丢包检测默认就采用「时间阈值 + 乱序阈值」，与 RACK 思想同源，区别在于状态机可收敛到用户态、便于快速迭代与部署。

调参上，重排窗口过小会误判、过大会延迟恢复，通常取 1 个 RTT 量级并随观测自适应；具体默认值以内核版本为准，不建议手工写死。

## 十、小结
RACK 以「晚发段已确认而早发段未确认」的时间序判据检测丢失，对乱序与尾部丢失更鲁棒，是现代 TCP 丢失恢复的核心，常配合 TLP 在 RTO 前完成恢复。它是从「序号视角」转向「时间视角」的标志性演进，也是理解现代传输层为何比经典教科书 TCP 更 resilient 的钥匙。
