# 两阶段提交

> 对应 Bernstein & Newcomer《Principles of Transaction Processing》，以及 Garcia-Molina《Database Systems》分布式事务章。

## 一、背景与挑战
跨多个资源管理器（数据库/服务）的事务需保证原子提交：要么全部提交，要么全部回滚。单库本地事务协议不够，需要协调者统一决策。

## 二、核心原理
2PC 分两阶段：准备阶段（协调者询问各参与者能否提交，参与者写 undo/redo 并锁定资源后投票 Yes/No）；提交阶段（全 Yes 则发 commit，否则 abort）。参与者在投 Yes 后进入不确定状态，须阻塞等待最终指令。

## 三、形式化 / 数学基础
协调者决策：$commit \iff \forall p_i, vote_i = Yes$。一旦发出 commit 记录，必须完成（即使崩溃也要重发）。参与者投 Yes 即承诺可提交（已持久化 prepare 日志）。

## 四、代码实现
```python
def coordinator(prepare_votes):
    if all(v == 'YES' for v in prepare_votes):
        log('commit'); broadcast('COMMIT')
    else:
        log('abort'); broadcast('ABORT')
# 参与者投 YES 前必须 fsync prepare 日志
```

## 五、与其他技术对比
| 协议 | 阻塞 | 容错 |
|------|------|------|
| 1PC | 无 | 无原子性 |
| 2PC | 有（不确定态） | 协调者单点 |
| 3PC | 减少 | 仍有限 |

## 六、常见误区
1. 2PC 不会阻塞——协调者崩溃且参与者不确定时会阻塞。
2. 2PC 完全容错——协调者单点 + 数据不一致风险（脑裂）。
3. 准备阶段就提交——须等全局决定。

## 九、演进与趋势
用 Paxos/Raft 复制协调者日志消除单点；TCC/Saga 用业务补偿替代强阻塞协议。

## 十、小结
2PC 以两阶段实现跨资源原子提交，代价是不确定态下的阻塞与协调者单点，是分布式事务的经典但受限方案。
