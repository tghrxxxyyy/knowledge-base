# 检查点频率对性能影响

> 对应 MySQL InnoDB 与 PostgreSQL 官方文档中 checkpoint 调优章节，参考 DDIA 第3章持久化讨论。

## 一、背景与挑战
检查点频率是吞吐与恢复时间的跷跷板：频繁检查点缩短恢复但增加写放大与 IO 竞争；稀少检查点反之。需要依据业务对恢复时间目标（RTO）的容忍度调优。

## 二、核心原理
每次检查点推进都触发脏页刷盘与日志 fsync。频率 $f$ 提高意味着单位时间刷盘量上升，挤占前台 IO 与 CPU。但恢复时需重放日志量下降，RTO 改善。

## 三、形式化与数学基础
设写负载 $W$（页/秒），检查点间隔 $T = 1/f$，恢复日志量约 $L \approx W \cdot T$。吞吐损失随 $f$ 上升：
$$ Penalty(f) \propto f $$
RTO 随 $f$ 下降：
$$ RTO \propto \frac{1}{f} $$
二者需权衡。

## 四、代码实现
```sql
-- MySQL：控制刷盘节奏
SET GLOBAL innodb_max_dirty_pages_pct = 75;
-- PostgreSQL：延长检查点间隔
ALTER SYSTEM SET checkpoint_timeout = '15min';
```

## 五、与其他技术对比
云原生数据库常把持久化下推到分布式存储，本地检查点频率对恢复影响被稀释。单机引擎则对频率敏感得多。

## 六、常见误区
盲目调高 `max_dirty_pages_pct` 以求性能，结果崩溃恢复极慢。认为检查点频率只影响恢复，忽略其对前台 IO 的实时抢占。

## 七、与开源书/权威来源对应
MySQL 官方「InnoDB Checkpoint」、PostgreSQL「WAL Configuration」文档；DDIA 第3章。

## 八、面试题
问：OLTP 与 OLAP 检查点策略差异？答：OLTP 偏平滑避免尖峰，OLAP 批量可容忍周期性大检查点。

## 九、演进与趋势
基于负载预测的弹性检查点，在空闲时多做、高峰时少做，是运维自动化方向。

## 十、小结
检查点频率是性能与 RTO 的平衡旋钮，结合脏页比例与 IO 能力调优是关键。
