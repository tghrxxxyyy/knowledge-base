# 全量检查点与增量检查点

> 对应 PostgreSQL 官方文档「WAL Configuration」与 checkpoint 机制，参考 Silberschatz 第17章。

## 一、背景与挑战

全量检查点（sharp / full checkpoint）在触发时强制把缓冲池所有脏页刷盘，使恢复极快——因为检查点后几乎无需 Redo。但代价是巨大的 IO 尖峰：瞬间大量刷盘阻塞前台、造成延迟毛刺，甚至把存储打满。增量检查点（fuzzy / incremental checkpoint）把应刷脏页均匀摊到整个检查点周期内，平抑负载，却因「检查点时仍有未刷脏页」使恢复略慢。

挑战在于：如何在「恢复快」与「IO 平滑」之间取到可运维的折中，且不引入不可控的突发刷盘。

## 二、核心原理

- **全量检查点**：触发即把全部脏页刷回，写一条 checkpoint 记录标记「此刻物理一致」。恢复从检查点起几乎零 Redo。代价是尖峰，且大库上刷盘可能远超 `checkpoint_timeout` 允许窗口。
- **增量检查点**：以 PostgreSQL 为典型，后台按 `checkpoint_completion_target` 把应刷脏页均匀分摊到两次检查点之间（如 target=0.9 表示用 90% 间隔完成刷盘），既避免尖峰，又不至于拖到下次检查点才完成。InnoDB 的 fuzzy checkpoint 也是持续增量推进脏页 LSN，而非一次性全刷。

本质区别在「刷盘节奏」：全量=脉冲式，增量=恒流式。现代引擎几乎都走增量/模糊路线，因为全量尖峰对 SLA 不可接受。

InnoDB 的 fuzzy checkpoint 本质是「持续增量推进脏页 LSN」：后台线程不断把最老脏页刷盘，使 redo_lsn 前移，而非触发时一次性全刷。PostgreSQL 则用 checkpoint_completion_target 把应刷脏页均匀摊到间隔内。二者都把「尖峰」拆成「恒流」，代价是检查点时仍有少量未刷脏页，恢复略慢但可控。

## 三、形式化与数学基础

设检查点间隔 $T$，需刷脏页数 $D$，平摊刷盘速率：

$$ r = \frac{D}{T \cdot \mathrm{target}} $$

$\mathrm{target}$ 越接近 1，刷盘越平滑（峰值越低）但越接近下次检查点才完成；$\mathrm{target}$ 小则前期猛刷、后期空闲，仍有局部尖峰。IO 尖峰高度近似：

$$ \mathrm{spike} \propto \frac{D}{T \cdot \mathrm{target}} - W $$

其中 $W$ 为正常写负载；当平摊速率逼近 $W$ 时尖峰最小。增量检查点使恢复区间约等于 $W \cdot T \cdot (1-\mathrm{target})$ 的残余脏页对应日志量，故 target 高 → 恢复略慢但平滑。

## 四、代码实现

```sql
-- PostgreSQL 调优检查点平滑度（以官方最新文档为准）
SHOW checkpoint_timeout;             -- 最大检查点间隔，默认 5min
SHOW checkpoint_completion_target;  -- 刷盘在间隔内均匀程度，默认 0.9
ALTER SYSTEM SET checkpoint_completion_target = 0.9;
ALTER SYSTEM SET checkpoint_timeout = '15min';
CHECKPOINT;                          -- 触发一次立即全量检查点（运维用）

-- 观察检查点频率与刷盘统计
SELECT * FROM pg_stat_bgwriter;
```

## 五、与其他技术对比

| 类型 | 恢复速度 | IO 平滑 | 适用 |
|------|----------|----------|------|
| 全量检查点 | 最快 | 差（尖峰） | 小库、离线 |
| 增量/模糊 | 较快 | 好 | 主流 OLTP |
| LSM 引擎 | 中 | 好（天然顺序） | 写多读少 |

早期系统全量检查点造成明显停顿；现代引擎几乎都走增量/模糊路线。列式与 LSM 引擎因写入模型不同，检查点开销本就较低（不可变段 / SSTable）。

## 六、常见误区

误区一：`checkpoint_timeout` 越长越好——恢复时间随之增长（恢复区间 ∝ 间隔）。误区二：增量检查点不会造成 IO 压力——突发脏页（大事务、批量导入）仍可能短期集中刷盘。误区三：全量检查点已淘汰——运维手动 `CHECKPOINT`、逻辑备份前后仍用之。误区四：target 越接近 1 越优——过犹不及，若刷盘跟不上写负载，仍会在间隔末堆积。

## 八、面试题

1. 调大 `checkpoint_timeout` 利弊？减少检查点频率省 IO，但崩溃恢复需重放更久日志（RTO 升）。
2. `checkpoint_completion_target` 作用？控制两次检查点间刷盘的均匀程度，高值平滑、低值可能尖峰。
3. 全量 vs 增量本质？刷盘节奏：脉冲式 vs 恒流式；恢复速度与 IO 平滑反向权衡。
4. 大事务为何让增量检查点失效？单事务产生大量脏页，超出平摊速率，被迫短期集中刷盘。

自适应检查点按负载实时调间隔与速率，空闲多做、高峰少做，是运维自动化方向。云数据库结合存储层快照做更细粒度持久化点，把「全量/增量」选择从静态参数变为运行时调度。Serverless 场景按计费粒度暂停/恢复检查点，平衡成本与恢复目标。

## 十、小结

全量简单恢复快但抖，增量平滑但恢复慢。现代引擎以模糊/增量检查点折中，通过 `checkpoint_completion_target` 等参数把刷盘摊平。理解「恢复区间 ∝ 间隔」与「尖峰 ∝ 平摊速率 - 写负载」，是检查点调优的核心。
