# 脏页链表与刷盘调度

> 对应 MySQL InnoDB 官方文档「Buffer Pool」与「Dirty Page Flushing」，参考 DDIA 第3章 B-Trees 与缓冲管理。

## 一、背景与挑战
缓冲池修改的页成为脏页，必须定时刷回磁盘以满足持久性与检查点要求。刷盘过快占用 IO，过慢则在崩溃时 Redo 量过大或在内存压力下被迫同步刷盘，造成抖动。

## 二、核心原理
InnoDB 维护脏页链表（flush list），按最早修改的 LSN 排序。后台有 page cleaner 线程周期性刷盘。刷盘策略受 `innodb_max_dirty_pages_pct` 与目标 LSN 推进速度控制，采用「邻居写」批量刷相邻脏页以减少随机 IO。

## 三、形式化与数学基础
设脏页比例 $p = \frac{D}{B}$，$B$ 为缓冲页数，$D$ 为脏页数。当
$$ p > p_{max} $$
触发积极刷盘；平滑刷盘速率 $r$ 与 $(p - p_{target})$ 成正比，形成反馈控制。

## 四、代码实现
```sql
SHOW VARIABLES LIKE 'innodb_max_dirty_pages_pct';
SHOW VARIABLES LIKE 'innodb_flush_neighbors';
-- 观察刷盘
SHOW STATUS LIKE 'Innodb_buffer_pool_wait_free';
```

## 五、与其他技术对比
PostgreSQL 的 bgwriter 与 checkpoint 配合刷脏，机制类似但参数体系不同（如 `bgwriter_lru_maxpages`）。LSM-tree（O'Neil 1996）无原地更新脏页概念，改为顺序写 SSTable，规避随机刷盘。

## 六、常见误区
认为脏页不刷就丢失——有 WAL 保证，崩溃后可 Redo 重建。认为 SSD 下刷盘调度不重要，实际仍会影响写放大与寿命。

## 七、与开源书/权威来源对应
MySQL 官方 Reference Manual「InnoDB Buffer Pool」章节；DDIA 第3章讨论缓冲与持久化权衡。

## 八、面试题
问：脏页为什么不立即刷盘？答：聚合随机写为顺序、利用缓冲提升读命中。问：脏页比例过高后果？答：检查点推进慢、崩溃恢复长、内存压力爆。

## 九、演进与趋势
机器学习预测刷盘时机、与存储层协同的写入整形（write shaping）降低写放大，是存储引擎研究方向。

## 十、小结
脏页刷盘是吞吐与恢复成本的平衡艺术，靠脏页链表与反馈式调度平滑进行。
