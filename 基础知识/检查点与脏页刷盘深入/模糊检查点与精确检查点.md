# 模糊检查点与精确检查点

> 对应 Mohan 1992 ARIES 论文中的 Fuzzy Checkpointing 与 Gray 1978 系统恢复理论，参考 Silberschatz 第17章 Recovery。

## 一、背景与挑战

检查点（checkpoint）记录「某一时刻数据库的一致状态」，用于缩短崩溃恢复时需要重放的日志长度。若没有检查点，恢复要从日志开头全量重放，对运行数月的大库不可接受。但「如何在不停机的情况下记录一致状态」是核心难题：精确检查点要求暂停所有写入以保证一致性快照，代价高、造成业务停顿；模糊检查点（fuzzy checkpoint）允许在写活动进行时记录，成为现代引擎主流。

挑战在于：模糊检查点记录的是「进行中」的现场，恢复时如何据此正确恢复到一致状态？活跃事务与脏页信息如何配合日志完成 Redo/Undo？

## 二、核心原理

- **精确检查点（quiescent / sharp checkpoint）**：先暂停（或等待）所有进行中事务与写入，把缓冲区所有脏页刷盘，再写一条检查点记录标记「此刻数据库完全一致」，恢复可直接从该状态开始，无需重放此前日志。优点简单；缺点停写窗口长，高并发系统不可接受。
- **模糊检查点（fuzzy checkpoint）**：不要求数据库静止，仅记录检查点开始/结束时刻的活跃事务列表与脏页表（dirty page table），真正刷脏由后台线程异步完成。恢复时从检查点记录出发，先 Redo 把库恢复到崩溃前瞬间，再 Undo 未提交事务，从而达成一致性。

模糊检查点的精髓是「记录现场」与「刷脏」解耦：检查点记录的是时间点 $T$ 的快照元数据，而非强制该时刻物理一致。

恢复协议上，模糊检查点并不保证「记录时刻物理一致」，而是记录「进行中现场」：活跃事务表 + 脏页表 + redo_lsn。崩溃恢复时从这些元数据出发，先 Redo（重复历史）把库恢复到崩溃前瞬间，再 Undo 未提交事务达成一致。因此检查点记录本身不刷全部数据页，真正的刷脏由后台 page cleaner 异步完成，二者解耦是可用性的关键。

## 三、形式化与数学基础

恢复需重放的日志量近似：

$$ L_{\mathrm{redo}} = L_{\mathrm{total}} - L_{\mathrm{before\_ckpt}} $$

模糊检查点使 $L_{\mathrm{before\_ckpt}}$ 接近最近一次稳定点，从而 $L_{\mathrm{redo}}$ 显著降低，且不引入停写窗口。设检查点记录时刻为 $t_c$，活跃事务集 $T_{act}$、脏页集 $D_c$，恢复起点 LSN 为：

$$ LSN_{\mathrm{redo}} = \min\{ \mathrm{LSN}(p) \mid p \in D_c \} $$

即从检查点时最早脏页的 LSN 开始重放（见「崩溃恢复中的 Redo 起点」）。

## 四、代码实现

```c
/* 伪代码：模糊检查点（以官方最新文档为准） */
void begin_checkpoint() {
    log_write(CHECKPOINT_START);          // 在 WAL 写入开始记录
}

void write_checkpoint_record() {
    ckpt_t rec;
    rec.active_txns = copy_active_transactions();   // 活跃事务表快照
    rec.dirty_pages = copy_dirty_page_table();      // 脏页表快照
    rec.redo_lsn    = min_dirty_page_lsn();         // 重做起点
    log_write(CHECKPOINT_END, rec);                 // 不阻塞新事务
}

void end_checkpoint() {
    /* 仅标记完成，刷脏由 page_cleaner 异步进行 */
}
```

## 五、与其他技术对比

| 类型 | 是否停写 | 恢复速度 | 适用 |
|------|----------|----------|------|
| 精确（静止）检查点 | 是 | 最快 | 小库、离线 |
| 模糊检查点 | 否 | 快（需 Redo+Undo） | 主流 OLTP |
| 增量检查点 | 否 | 中 | 平抑 IO（见「全量/增量」） |

早期系统常用 quiescent 检查点，简单但造成停顿。模糊检查点将「记录」与「刷脏」解耦，是现代引擎（PostgreSQL、InnoDB）标配，配合 REDO 日志完成恢复。

## 六、常见误区

误区一：检查点就是把所有数据刷盘——模糊检查点只是记录现场信息，真正刷脏由后台刷盘线程异步完成。误区二：检查点越频繁恢复越快——但频繁检查点增加 IO 负担与写放大，需权衡（见「检查点频率对性能影响」）。误区三：模糊检查点记录的状态可直接用——它需结合 WAL 的 Redo/Undo 才达成一致。误区四：检查点后旧日志可立即删——需确认 `redo_lsn` 之后都保留。

## 八、面试题

1. 为什么用模糊检查点？避免停写窗口、降低恢复时间同时不阻塞业务；以「记录现场 + 异步刷脏」替代「强制静止」。
2. 恢复时模糊检查点怎么用？从检查点记录的活跃事务表与脏页表出发，先 Redo（重复历史）再 Undo 未提交事务。
3. 精确 vs 模糊的本质差异？前者要求物理一致快照、停写；后者记录进行中现场、不停写。
4. 模糊检查点为何还需要脏页表？用于确定 Redo 起点（最早脏页 LSN），避免全日志重放。

云原生数据库把检查点语义下推到分布式存储层，本地检查点更多用于加速本地重放而非持久性本身。共识日志（Raft/Paxos）使检查点在副本间一致推进，主从恢复路径统一。存储计算分离后，脏页刷盘与检查点的「IO 成本」转由共享存储承担，本地调参维度减少。

## 九、演进与趋势

增量检查点（如增量记录脏页位图、持续推进 `redo_lsn`）进一步平摊检查点开销，避免单次大量刷盘造成的 IO 尖峰（见「全量检查点与增量检查点」）。云原生与分布式存储把检查点语义下推，本地恢复路径被稀释。NVM 等非易失介质也在改变检查点的「刷盘」含义。

落地：现代引擎默认模糊/增量检查点，无需追求精确检查点的停写。
检查点记录只记现场（活跃事务表 + 脏页表 + redo_lsn），刷脏异步。
恢复从检查点出发先 Redo 后 Undo，二者缺一不可。
调优关注 checkpoint 间隔与脏页比例，而非手动全量刷盘。
云原生下检查点语义下推，本地更多用于加速重放。
精确检查点仅适合小库/离线/逻辑备份前后。
模糊检查点不保证记录时刻物理一致，而是记录进行中现场。
活跃事务表用于恢复时区分已提交/未提交。
脏页表用于确定 Redo 起点（最早脏页 LSN）。
InnoDB/PG 均走模糊路线，配合 WAL 完成恢复。
检查点频率与脏页比例共同决定实际刷盘节奏。
运维手动 CHECKPOINT 用于备份前一致性快照。
恢复时间随检查点间隔增长，需按 RTO 设。
监控 checkpoint 耗时与恢复区间，评估可用性。

## 十、小结

模糊检查点通过「记录现场而非强制静止」兼顾恢复速度与可用性，是 WAL 体系的关键一环。理解其「活跃事务表 + 脏页表 + Redo/Undo」的恢复协议，是掌握现代数据库崩溃恢复的基础。
