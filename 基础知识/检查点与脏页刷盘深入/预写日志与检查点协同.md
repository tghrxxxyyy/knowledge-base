# 预写日志与检查点协同

> 对应 Gray 1978 与 Mohan 1992 ARIES 的 WAL 原则，参考 Silberschatz 第17章。

## 一、背景与挑战

持久性要求「先写日志再改数据页」：若先改页再写日志，崩溃可能留下已改页却无日志记录，恢复无法重建。预写日志（WAL, Write-Ahead Logging）就是这个规则。但 WAL 单独不足以缩短恢复——日志会无限增长。检查点必须与 WAL 协同，在日志中标记一个安全的恢复起点，使恢复从「最后一个完整检查点之后」开始，而非日志开头。

挑战在于：检查点推进必须保证「其记录的 Redo 起点之前的所有修改都已持久」，否则从该起点恢复会漏数据。二者若协同出错（如检查点记录早于实际刷盘进度），恢复会不一致。

## 二、核心原理

WAL 规则：任何缓冲页的修改必须先有对应日志记录落盘（fsync 日志），才能修改内存页甚至刷盘数据页。检查点在日志中写入一条 checkpoint 记录，包含当时的已刷脏页 LSN 上限、活跃事务表与脏页表。恢复时从最后一个完整 checkpoint 记录的 `redo_lsn` 之后开始 Redo，避免全日志扫描。

二者协同关键点：检查点不能「宣告」一个尚未真正持久的点。`checkpoint_lsn` 必须 $\ge$ 当时最早未刷盘脏页的 LSN，即保证检查点之前的所有修改已落盘或将被 Redo 覆盖。

协同的硬约束是 checkpoint_lsn ≥ redo_lsn：检查点记录不能「宣告」一个尚未真正持久的点，否则从该点恢复会漏掉已提交但未刷盘的修改。WAL 的持久性由「提交前日志 fsync」保证，group commit 把多个事务的 fsync 合并摊薄代价。崩溃时即便数据页落后，也能靠日志 Redo 完整重建已提交状态。

## 三、形式化与数学基础

定义 `redo_lsn` 为最早未刷盘脏页对应的 LSN。检查点推进保证：

$$ \mathrm{checkpoint\_lsn} \ge \mathrm{redo\_lsn} $$

恢复只需从 $\max(\mathrm{checkpoint\_lsn}, \text{日志起点})$ 开始重放，重放区间长度：

$$ L_{\mathrm{replay}} = LSN_{\mathrm{end}} - \mathrm{checkpoint\_lsn} $$

该区间随检查点推进而缩短。WAL 的持久性保证可写为：对任意已提交事务 $T$，其提交记录在返回成功前已 fsync，故 $LSN(T.\mathrm{commit}) \le LSN_{\mathrm{end}}$，必被重放覆盖。

## 四、代码实现

```c
/* 伪代码：WAL 提交（以官方最新文档为准） */
void wal_commit(transaction_t *txn) {
    log_record_t r;
    r.lsn     = next_lsn();
    r.page_id = txn->dirty_pages;
    r.before  = snapshot_before(txn);
    r.after   = snapshot_after(txn);
    write_log_record(r);
    fsync(log_file);          // 先持久化日志
    modify_buffer_page(r);    // 再改内存页（可滞后刷盘）
}

void checkpoint() {
    ckpt_lsn = current_redo_lsn();   // 必须 >= 最早未刷脏页 LSN
    write_checkpoint_record(ckpt_lsn, active_txns, dirty_pages);
    fsync(log_file);
}
```

## 五、与其他技术对比

| 机制 | 检查点角色 | 恢复路径 |
|------|------------|----------|
| ARIES + WAL | 标记 Redo 起点 | 从 checkpoint 后 Redo |
| LSM-tree | manifest 标记有效 SSTable | 加载 manifest |
| 影子分页 | 提交即切换指针 | 切回旧页 |

ARIES 的 WAL + 模糊检查点是关系库事实标准。LSM-tree 用顺序追加的 WAL + SSTable 合并，检查点概念弱化为 manifest 文件标记有效 SSTable 集合，逻辑更简单。

## 六、常见误区

误区一：检查点后旧日志可立即删除——需确认其覆盖的脏页都已刷盘且后续无依赖（redo_lsn 已前移）。误区二：fsync 日志很慢不可接受——group commit 把多个事务的 fsync 合并，摊薄代价。误区三：WAL 只管持久性不管恢复速度——检查点正是为缩短恢复而存在。误区四：先改页再补日志也行——崩溃会留无据可查的修改，破坏一致性。

## 八、面试题

1. WAL 为什么能保证持久性？提交前日志落盘，崩溃后靠日志 Redo 重建已提交修改；先写日志后改页是铁律。
2. 检查点与 WAL 关系？检查点记录 Redo 起点，缩短恢复路径；其 LSN 必须不早于实际刷盘进度。
3. group commit 作用？合并多个事务的日志 fsync，降低单次 fsync 的吞吐损失。
4. 为何检查点不能随便删旧日志？redo_lsn 之前可能仍有未刷盘脏页依赖这些日志。

分布式 WAL 把单点日志提升为复制组共识日志，检查点协同需在多数派副本一致。NVM 使 fsync 代价骤降，WAL 的「先写日志」边界变得模糊，可能出现「日志即数据」的存储结构。可观测上，日志写入延迟与检查点推进速度的解耦监控，是诊断恢复风险的关键。

## 九、演进与趋势

非易失内存（NVM）使 WAL 的 fsync 语义改变，可能出现无锁日志或「日志即数据」；分布式 WAL（如基于 Raft/Paxos 的共识日志）把单点 WAL 推广到复制组，检查点协同需在副本间一致。云存储下推使本地 WAL 更多用于本地重放加速。

## 十、小结

WAL 与检查点共同构成崩溃恢复基石：WAL 用「先写日志」保证不丢，检查点用「Redo 起点」缩短恢复。二者通过 `checkpoint_lsn ≥ redo_lsn` 的协同约束，实现正确且高效的崩溃恢复。
