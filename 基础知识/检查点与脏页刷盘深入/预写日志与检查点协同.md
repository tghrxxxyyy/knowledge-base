# 预写日志与检查点协同

> 对应 Gray 1978 与 Mohan 1992 ARIES 的 WAL 原则，参考 Silberschatz 第17章。

## 一、背景与挑战
持久性要求「先写日志再改数据页」。检查点必须与 WAL 协同，使恢复从日志中一个安全的起点开始，否则可能重放不完整或重复。

## 二、核心原理
WAL 规则：任何缓冲页的修改必须先有对应日志记录落盘。检查点在日志中写入 checkpoint 记录，包含当时的已刷脏页 LSN 上限与活跃事务。恢复从最后一个完整 checkpoint 之后开始 Redo。

## 三、形式化与数学基础
定义 `redo_lsn` 为最早未刷盘脏页对应的 LSN。检查点推进保证：
$$ checkpoint\_lsn \ge redo\_lsn $$
恢复只需从 $max(checkpoint\_lsn, 日志起点)$ 开始重放，避免全日志扫描。

## 四、代码实现
```c
// 伪代码：WAL 提交
write_log_record(lsn, page_id, before, after);
fsync(log_file);          // 先持久化日志
modify_buffer_page(page); // 再改内存页
```

## 五、与其他技术对比
ARIES 的 WAL + 模糊检查点是关系库事实标准。LSM-tree 则用顺序追加的 WAL + SSTable 合并，检查点概念弱化为 manifest 文件标记有效 SSTable 集合。

## 六、常见误区
认为检查点后旧日志可立即删除——需确认其覆盖的脏页都已刷盘且后续无依赖。认为 fsync 日志很慢不可接受，实际上 group commit 可摊薄该代价。

## 七、与开源书/权威来源对应
Mohan 1992 ARIES 论文；Silberschatz《Database System Concepts》17.2「Log-Based Recovery」。

## 八、面试题
问：WAL 为什么能保证持久性？答：提交前日志落盘，崩溃后靠日志 Redo 重建已提交修改。问：检查点与 WAL 关系？答：检查点记录 Redo 起点，缩短恢复路径。

## 九、演进与趋势
非易失内存（NVM）使 WAL 的 fsync 语义改变，可能出现无锁日志；分布式 WAL（如 consensus 日志）将单点 WAL 推广到复制组。

## 十、小结
WAL 与检查点共同构成崩溃恢复基石，前者保证不丢，后者缩短恢复。
