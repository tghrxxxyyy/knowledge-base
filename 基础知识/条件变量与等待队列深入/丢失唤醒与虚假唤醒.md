# 丢失唤醒与虚假唤醒

> 对应 Lamport 1978 与 Linux 内核 Documentation。

## 一、背景与挑战
并发等待最隐蔽的两类错误：丢失唤醒（唤醒发生在等待之前，等待者永远睡去）与虚假唤醒（被唤醒但谓词仍未满足）。二者都源于对「等待与通知时序」与「谓词重查」的处理不当。

## 二、核心原理
丢失唤醒源于非原子地「检查谓词—睡眠」，若在检查后、睡眠前发生状态改变并 signal，唤醒就丢失。正确做法是把检查与 wait 原子化（条件变量保证）。虚假唤醒是系统允许 wait 无故返回，必须用 while 重查谓词来容忍。

## 三、形式化与数学基础
丢失唤醒对应竞态：

$$ \text{check } \neg P \;\to\; (\text{set } P,\ \text{signal}) \;\to\; \text{wait (永远睡)} $$

原子 wait 消除该间隙。虚假唤醒要求：

$$ \text{upon return from wait}: \text{re-evaluate } P $$

只有 $P$ 真才继续，否则重新 wait。

## 四、代码实现
错误与正确对比：

```c
// 错误：可能丢失唤醒
if (!ready) pthread_cond_wait(&cv, &m);  // 用 if

// 正确：while 重查，容忍虚假唤醒与竞争
while (!ready) pthread_cond_wait(&cv, &m);
```

内核等待队列也用类似 while 谓词循环。

## 五、与其他技术对比
信号量因计数不会丢失唤醒（V 累积），但无谓词语义；条件变量必须配合 while；completion 因单调计数避免丢失。三者对唤醒语义的处理不同。

## 六、常见误区
认为只要先 signal 就安全，非原子检查仍会丢；认为虚假唤醒罕见可忽略，规范上必须处理；认为 broadcast 比 signal 更安全可省 while，实则仍需重查。

## 七、与开源书/权威来源对应
Lamport 1978 给出并发事件次序的形式化，帮助理解丢失唤醒；Linux waitqueue 文档强调谓词循环；Silberschatz 讨论条件变量陷阱。

## 八、面试题
丢失唤醒如何发生；为何 while 而非 if；虚假唤醒来源；completion 为何不怕丢失。

## 九、演进与趋势
形式化验证工具（如 TLA+）用于证明无丢失唤醒；futex 与内核等待队列提供底层保障。

## 十、小结
丢失唤醒靠原子 wait 消除，虚假唤醒靠 while 重查容忍，二者是正确实现等待通知的两条铁律。
