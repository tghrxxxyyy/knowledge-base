# 拥塞信号

> 对应 RFC 3168（ECN）；RFC 5681（丢包信号）；Stevens《TCP/IP Illustrated》卷1；Kurose & Ross《Computer Networking》第3章。

## 一、背景与挑战

拥塞控制的核心动作是「感知到网络过载后降速」，因此「用什么信号判断过载」直接决定控制的及时性与代价。最传统、最可靠的是丢包（隐式信号）：队列溢出丢弃报文，发送方通过超时或 3-dup-ACK 推断拥塞。但丢包的代价很高——被丢弃的报文本身已占用带宽与计算，且信号严重滞后（要等到队列填满才出现），还会引入重传。为此 RFC 3168 引入显式拥塞通知（ECN），让路由器在「队列将满未满」时就用标记代替丢弃，使发送方在损失发生之前就降速。如何设计、协商与处理这两类信号，是该主题的关键。

## 二、核心原理

端点可依赖两类拥塞信号：

1. 丢包 / 3-dup-ACK：强信号。触发乘性减（`ssthresh` 减半、`cwnd` 下降），是「兜底」信号，任何实现都必须处理。
2. ECN：无损信号。发送方在 IP 头用 ECT(0)/ECT(1) 标记「本连接支持 ECN」，支持 ECN 的转发设备发现队列超过阈值时把这两位改写成 CE（Congestion Experienced）。接收方在回传的 TCP ACK 中置 ECE 位回声该标记，发送方见 ECE 后减半 `cwnd` 并置 CWR 位通知接收方「我已降速，停止回声」，避免同一次拥塞被重复计入。

ECN 的协商发生在三次握手：SYN 中置 ECE+CWR 表示「本端支持 ECN」，对端在 SYN-ACK 中回 ECE 确认，之后数据段才能使用 ECT 标记。若任一方不支持，则退化为纯丢包模式。

## 三、形式化与数学基础

IP 头 ToS 字节低 2 位构成 ECN 字段：

$$ \text{ECT/CE} \in \{00=\text{Non-ECT},\ 10=\text{ECT(0)},\ 01=\text{ECT(1)},\ 11=\text{CE}\} $$

TCP 头标志位：ECE（Echo Congestion Experienced，位 0x40）、CWR（Congestion Window Reduced，位 0x80）。

处理流程可形式化为：

$$ \text{转发设备：} ECT \neq 00 \land q > threshold \;\Rightarrow\; \text{CE}=11 $$
$$ \text{接收方：} 见 CE \;\Rightarrow\; ACK.\text{ECE}=1 $$
$$ \text{发送方：} 见 ECE \land \neg 已减半 \;\Rightarrow\; cwnd \leftarrow \max(cwnd/2,\ 2\cdot SMSS),\ ACK.\text{CWR}=1 $$

注意 ECN 标记触发的是与 3-dup-ACK 相同的「乘性减」反应，区别在于它无损、提前，且不引发重传。

## 四、代码实现

下面给出 ECN 收发两端核心位操作的简化逻辑：

```c
// 转发设备（概念）：队列超阈值且有 ECT 时标记 CE
if ((ip->tos & 0x03) != 0x00 && queue_len > ECN_THRESHOLD) {
    ip->tos = (ip->tos & 0xFC) | 0x03;   // 置 CE
}

// 接收方：把 CE 回声到下一个 ACK
if ((ip->tos & 0x03) == 0x03) {
    tcp->flags |= TCP_ECE;                // 回声拥塞经历
}

// 发送方：见 ECE 则降速并回 CWR
if (tcp->flags & TCP_ECE) {
    cwnd = max(cwnd / 2, 2 * SMSS);       // 乘性减
    tcp->flags |= TCP_CWR;                // 通知对端停止回声
}
```

## 五、与其他技术对比

| 信号 | 性质 | 及时性 | 是否丢包 | 公平性影响 |
| --- | --- | --- | --- | --- |
| 丢包/3-dup-ACK | 硬、滞后 | 低 | 是 | 标准 |
| ECN 标记 | 软、提前 | 高 | 否 | 与丢包一致 |
| 延迟类（Vegas） | 前瞻 | 高 | 否 | 与丢包流混合时易饿死 |

基于延迟的信号（如 TCP Vegas 用 RTT 上升趋势）比 ECN 更前瞻，但与基于丢包的流共享瓶颈时往往因「提前降速」而被后者挤占带宽，存在公平性难题。ECN 则保持与丢包信号相同的反应幅度，避免了这一问题。

## 六、常见误区

误区一：ECN 标记意味着报文会被丢弃。错——ECN 的全部意义就是用「标记」替代「丢弃」，使拥塞被感知但不损失数据。

误区二：ECN 关闭时网络就无法做拥塞控制。错——丢包信号始终是兜底，ECN 只是增强。

误区三：只有路由器能设置 CE。对——只有支持 ECN 的转发设备会在拥塞时改写 CE，端主机在发送时只设 ECT、不自行置 CE。

误区四：ECE 与 CWR 作用相同。错——ECE 是接收方「回声」拥塞、发送方「读取」降速；CWR 是发送方「告知已降速、请停止回声」，二者方向相反、缺一不可。

## 七、与开源书·权威来源对应

- RFC 3168 完整定义 ECN 的 IP/TCP 位、握手协商与处理状态机。
- RFC 5681 规定丢包（超时与 3-dup-ACK）作为拥塞信号的降速逻辑。
- Stevens《TCP/IP Illustrated》卷1 第21章用实测报文讲解 3-dup-ACK 的触发条件。
- Kurose & Ross《Computer Networking》第3章将 ECN 作为「网络辅助拥塞控制」范例。

## 八、面试题

1. ECN 为什么能减少重传与吞吐抖动？要点：提前、无损地提示拥塞，发送方在丢包前降速。
2. ECE 与 CWR 各自作用？要点：ECE 回声拥塞、驱动降速；CWR 通知对端已降速、停止回声。
3. ECN 协商失败会怎样？要点：退化为纯丢包模式，仍由 RFC 5681 控制。
4. 为什么 ECN 的反应幅度与丢包一致？要点：避免延迟类算法那样的公平性问题，保持与 Reno 兼容。

## 九、演进与趋势

L4S（RFC 9330/9331）将 ECN 语义扩展为「低时延可扩展拥塞信号」，用两种 ECT 码点区分「经典」与「低时延」流，配合 DCTCP、BBR 等把排队时延从毫秒级压到亚毫秒级，特别适合数据中心与实时应用。此外，AccECN（RFC 8511）扩展 ECN 回声能力，使接收方能更精确地反馈拥塞经历的次数。

## 十、小结

拥塞信号是拥塞控制的「感知器官」：丢包/3-dup-ACK 是滞后但可靠的硬信号，ECN 是提前且无损的软信号，二者驱动相同的乘性减反应。理解 IP/TCP 中 ECT、CE、ECE、CWR 四位的协作，是掌握现代 TCP 为何能在高吞吐下仍保持低排队时延的关键。
