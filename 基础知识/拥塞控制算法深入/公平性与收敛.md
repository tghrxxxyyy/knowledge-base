# 公平性与收敛

> 对应 Chiu & Jain 1989《Analysis of the Increase and Decrease Algorithms for Congestion Avoidance》；RFC 5681；Kurose & Ross《Computer Networking》第3章。

## 一、背景与挑战

当多条 TCP 流共享同一瓶颈链路时，协议必须满足两个性质：一是「公平」——带宽分配不能让某条流长期饿死；二是「收敛」——无论初始窗口如何，系统状态都应从任意起点演化到唯一的均衡点，否则会出现持续震荡或某流被挤出。公平性与收敛性因此是评价一切拥塞控制算法的两个独立维度：一个算法可能收敛很快但不公平（如 MIMD 下小流被大流压制），也可能公平但收敛极慢（拖慢整体利用率）。理解这套评价体系，才能判断 AIMD、CUBIC、BBR 各自优劣的根因。

还需明确「公平」的口径：是字节公平、连接数公平，还是按 RTT/权重的比例公平？不同口径会给出完全不同的结论——例如大量短连接的应用在「连接数公平」下会占优，而在「按源 IP 公平」下被抑制。讨论公平性前先确定口径，否则结论无从比较。

## 二、核心原理

公平性度量最常用 Jain 公平性指数：给定 $n$ 条流的吞吐量 $x_i$，定义为 $(\sum x_i)^2 / (n\sum x_i^2)$，取值 $(0,1]$，值为 1 表示完全均分。它的优点是对「绝对差距」不敏感、对「相对差距」敏感，且对流的条数尺度不变。

收敛性则考察多流博弈的动力学：AIMD 被 Chiu & Jain 证明在「效用函数最大化」框架下能收敛到比例公平（proportionally fair）点——即满足 $\sum \log x_i$ 最大化的分配。直观上，加法增保证「空闲容量会被逐步分掉」（效率），乘法减保证「某流退场后其余流能平滑补位、且占优流被快速拉回」（公平）。

值得注意的是，收敛性说的是「均衡点存在且可达」，并不保证「到达速度快」或「途中不震荡」。因此在评价算法时，除了看最终是否公平，还要看「收敛时间」与「超调幅度」——这两者决定了实际用户体验。

## 三、形式化与数学基础

Jain 公平性指数：

$$ f(x_1,\dots,x_n) = \frac{\left(\sum_{i=1}^{n} x_i\right)^2}{n\sum_{i=1}^{n} x_i^2} \in (0,1] $$

当所有 $x_i$ 相等时取 1；当一条流独占总带宽、其余为 0 时趋于 $1/n$。

两人 AIMD 收敛分析：设瓶颈容量 $C$，两流速率 $x,y$ 满足 $x+y=C$。每次「加性增」使二者各 $+a$，每次「乘性减」（因子 $\beta=1/2$）使二者各 $\times\beta$。两次减操作之间差距 $d=x-y$ 会被拉开再被压缩，Chiu-Jain 证明在加/减幅度配置对称时，$d$ 随迭代按 $1/2$ 衰减并趋于 0。

比例公平解：最大化 $\sum_i \log x_i$ 在 $\sum x_i=C$ 约束下的 Karush–Kuhn–Tucker 条件给出 $x_i$ 全部相等（等 RTT、等权重情形），即等分瓶颈带宽。

收敛速度可由差距的几何衰减刻画：$d_{k+1} \approx \beta\, d_k$，即 $d_k \approx \beta^k d_0$。因此 $\beta$ 越小（减得越狠）收敛越快，但稳态利用率越低——这是「收敛速度 vs 利用率」的显式权衡。

## 四、代码实现

下面用一段 Python 计算 Jain 指数，以及模拟两流 AIMD 的收敛过程：

```python
def jain(xs):
    s = sum(xs)
    return s * s / (len(xs) * sum(x * x for x in xs))

def aimd_pair(capacity, beta=0.5, steps=200):
    x, y = capacity * 0.1, capacity * 0.9   # 不公平的初值
    for _ in range(steps):
        # 加性增
        if x + y < capacity:
            x += 1; y += 1
        else:
            # 乘性减：模拟一次丢包
            x *= beta; y *= beta
    return x, y, jain([x, y])

print(jain([10, 10]))        # 1.0
print(jain([18, 2]))         # 约 0.68

# 观察收敛速度与 beta 的关系：beta 越小，差距衰减越快但稳态利用率越低
for beta in (0.9, 0.7, 0.5, 0.3):
    xs, ys, f = aimd_pair(100, beta=beta, steps=300)
    print(beta, round(f, 3))   # 公平性随 beta 减小而改善
```

注意 `jain` 的返回值不能单独用来评判「好」：若两条流都很小（$\sum x_i$ 远低于容量），指数仍可能接近 1，因此必须与「链路利用率」一起看。

## 五、与其他技术对比

| 算法 | 公平性 | 收敛性 | 备注 |
| --- | --- | --- | --- |
| AIMD（Reno） | 比例公平 | 收敛到等分 | RTT 小流占优 |
| MIMD | 差（易震荡） | 不收敛 | 乘法增放大差距 |
| AIAD | 差 | 不稳定 | 加增加减无法收敛 |
| BBR | 与 Reno 混合时偏占优 | 模型式稳定 | 不属 AIMD 家族 |
| FQ/公平排队 | 近完美 | 网络层保证 | 调度而非端点 |

AIMD 在公平与收敛间取得平衡；但 RTT 公平性（RTT 小的流窗口涨得快、抢占更多带宽）是其固有缺陷。BBR 与 Reno 共享瓶颈时被认为更占优，引发「公平性」争议，BBR v2 因此引入与 Reno 兼容的公平性折中。

## 六、常见误区

误区一：TCP 天生完全公平。错——存在 RTT 偏置与启动时间偏置（先启动的流已占带宽），并非严格等分。

误区二：公平就是每流绝对等分。错——比例公平考虑权重与 RTT，加权公平队列允许不同权重。

误区三：Jain 指数等于 1 就一定最优。错——还要看链路利用率，等分但总吞吐很低也不是好结果。

误区四：收敛到均衡点意味着永不震荡。错——实际网络流量时变，均衡点是动态跟随的，短期波动始终存在。

误区五：换个算法就能消除不公平。错——端点算法的公平性最终受网络层调度（队列、标记）制约，端网协同才有效。

误区六：公平性指标口径不重要。错——字节公平、连接公平与加权公平结论差异巨大，讨论前必须明确口径。

## 七、与开源书·权威来源对应

- Chiu & Jain 1989 用「增加/减少算法」的相图（increase/decrease plot）严格证明 AIMD 收敛且公平，是该领域的奠基性论文。
- RFC 5681 的 AIMD 规则是该理论在 TCP 中的落地。
- Kurose & Ross《Computer Networking》第3章用 Jain 指数与公平性曲线直观讲解多流交互。
- CS-Notes 对公平性指数有通俗归纳。

## 八、面试题

1. 什么是 Jain 公平性指数？取值范围与含义？要点：$(\sum x_i)^2/(n\sum x_i^2)$，1 为完全公平，$(0,1]$。
2. 为什么 RTT 小的 TCP 流占优？要点：拥塞避免每 RTT 加 1 MSS，RTT 小者单位时间涨得快，抢占带宽。
3. 为什么 AIMD 能收敛到公平点？要点：加性增补满空闲、乘性减快速拉回占优流，对称配置下差距按 $1/2$ 衰减。
4. MIMD 为何不公平？要点：乘法增放大已有差距，强者恒强、弱者饿死。
5. 收敛速度与利用率如何取舍？要点：减得越狠（$\beta$ 越小）差距衰减越快、收敛更快，但稳态窗口越低、利用率越差。
6. 公平性为何不能只看端点算法？要点：队列调度、标记与优先级等网络层机制会直接改变实际分配，端网协同才决定最终公平性。

## 九、演进与趋势

在网络层，FQ-CoDel、pacing 与公平队列（如 DRR）用调度而非端点算法保证公平，与端点拥塞控制协同。BBR v2 显式建模与 Reno 的公平性折中，试图缓解「模型式算法抢占丢包式算法」的问题。近年还有基于「 max-min 公平」与「utility maximization」的显式拥塞控制（如 XCP、RCP）研究，把收敛点直接写入网络信令。

在数据中心场景，「公平性」的诉求正在从「吞吐等分」转向「低延迟 + 尾部延迟」。这带来了新的评价维度：除了 Jain 指数，还需看 P99 延迟与队列占用，因为「吞吐公平但延迟极不公平」同样会破坏多租户体验。

## 十、小结

公平性用 Jain 指数量化、收敛性由 AIMD 的加增乘减动力学保证，二者共同定义了拥塞控制的「好」。但现实中存在 RTT 偏置与算法间不公平，提示我们公平性不仅是端点问题，也依赖网络层调度与算法协同；而明确公平性口径、并把收敛速度与利用率一并纳入评价，才是判断算法优劣的完整视角。
