# 现代变体

> 对应 RFC 9438（CUBIC）；RFC 9413（TCP 演进综述）；RFC 5681（Reno 基线）；Stevens《TCP/IP Illustrated》卷1。

## 一、背景与挑战

标准 Reno 在大带宽-时延积（BDP）链路下暴露出明显短板：拥塞避免阶段「每 RTT 才加 1 个 MSS」，窗口从 $W$ 涨到 $2W$（丢包后减半再涨回）需要约 $W$ 个 RTT，而 $W$ 与 BDP 成正比——千兆长肥管道上这可能要几十秒，链路利用率长期不足。此外不同场景诉求不同：数据中心要低尾延迟，卫星/无线链路要抗高丢包与乱序，移动网络要抗带宽剧变。于是围绕 Reno 框架出现了一批「现代变体」，在保持 TCP 友好性的同时针对特定瓶颈优化。

## 二、核心原理

现代变体大致可归为几类思路：

- 时钟驱动凹函数（CUBIC）：不再按 RTT 线性增，而是以「距离上次丢包的时间」为自变量，用三次函数逼近上次丢包前的窗口，使高 BDP 下增长更快、接近公平点更平缓。
- 二分搜索（BIC）：把窗口搜索区间对半分，快速逼近又不震荡，CUBIC 的前身。
- 延迟预测（Vegas）：用 RTT 的实际上升量估计「多余在途数据」，提前降速，属于 delay-based。
- 带宽估计（Westwood/Westwood+）：用 ACK 到达速率估计瓶颈带宽，据此设定丢包后的 `ssthresh`，抗无线丢包误判。
- 时间重传（RACK）：用「已成功确认的数据的时间序」而非「重复 ACK 计数」检测丢包，对乱序/重排更鲁棒（已成 Linux 默认）。

这些变体都是对「何时增、增多少、丢包后减到哪」的重新设计，而非推翻 TCP 语义。

## 三、形式化与数学基础

CUBIC 的窗口随「距离上次降窗的经过时间 $t$」变化：

$$ cwnd(t) = C \cdot (t - K)^3 + W_{last} $$

其中 $W_{last}$ 为上次丢包前的窗口，$K$ 是使窗口回到 $W_{last}$ 所需时间：

$$ K = \sqrt[3]{\frac{W_{last} \cdot (1 - \beta)}{C}}, \quad \beta \approx 0.7 $$

$\beta$ 即乘性减因子（CUBIC 默认 0.7 而非 0.5）。当 $t < K$ 时函数在窗口低于 $W_{last}$ 的凹段快速爬升；当 $t > K$ 时在凸段平缓探索更高带宽，兼顾「恢复快」与「不冲垮网络」。

Vegas 的延迟判据：

$$ \text{expected} = BtlBw \cdot RTT_{min}, \quad \text{diff} = BtlBw \cdot (RTT - RTT_{min}) $$

以 `diff` 落在预设门限区间来加/减窗口，提前于丢包降速。

## 四、代码实现

下面给出 CUBIC 窗口计算的简化实现（示意）：

```c
// CUBIC 简化实现
#define CUBIC_C   0.4
#define BETA      0.7

long long cubic_cwnd(long long w_last, long long t_ms) {
    // t_ms：距上次丢包的毫秒数；K 用毫秒单位近似
    long long K = cbrt(w_last * (1 - BETA) / CUBIC_C);
    long long delta = t_ms - K;
    long long cwnd = CUBIC_C * delta * delta * delta + w_last;
    return cwnd < 1 ? 1 : cwnd;
}
```

## 五、与其他技术对比

| 变体 | 核心思想 | 适用场景 | 主要短板 |
| --- | --- | --- | --- |
| Reno | AIMD 线性增 | 小 BDP、通用 | 大 BDP 收敛慢 |
| CUBIC | 时钟驱动三次函数 | 大 BDP、长肥管道（Linux 默认） | 仍丢包驱动、bufferbloat |
| BBR | BtlBw×RTTprop 模型 | 高吞吐低时延 | 与 Reno 公平性争议 |
| Vegas | 延迟预测 | 低丢包网络 | 混合场景易饿死 |
| DCTCP | ECN 驱动降窗 | 数据中心 | 依赖 ECN 部署 |

数据中心常选 DCTCP/BBR 压尾延迟；广域网大 BDP 用 CUBIC/BBR；无线/卫星链路偏好 Westwood 类带宽估计。

## 六、常见误区

误区一：新算法一定全面优于 Reno。错——取决于 RTT、BDP、丢包率，短肥或低丢包场景下差异很小，甚至 Reno 更稳。

误区二：CUBIC 是 Reno 的线性增。错——它是三次函数、以时间为自变量，与 Reno 的「每 RTT +1」本质不同。

误区三：BBR 属于 Reno 家族。错——BBR 是模型式、非 AIMD，不依赖丢包主信号。

误区四：变体越多越好。错——多算法混跑会放大公平性问题，部署时需统一策略。

## 七、与开源书·权威来源对应

- RFC 9438 是 CUBIC 的正式标准，给出窗口函数与参数取值。
- RFC 9413 综述 TCP 拥塞控制的演进与开放问题。
- RFC 5681 定义 Reno 基线，是所有变体的比较基准。
- Stevens《TCP/IP Illustrated》卷1 讲解各变体的报文行为。
- CS-Notes 对 CUBIC/BBR 有通俗对照。

## 八、面试题

1. Linux 默认拥塞控制是什么？要点：CUBIC（TCP 默认），BBR 需手动开启。
2. CUBIC 相比 Reno 优势？要点：以时间而非 RTT 驱动、三次函数使大 BDP 下收敛更快、逼近公平点更平缓。
3. 为什么 Vegas 在混合网络中易饿死？要点：提前降速让基于丢包的流抢占带宽。
4. DCTCP 适合什么场景？要点：数据中心，借 ECN 实现低时延、高吞吐的群体公平。

## 九、演进与趋势

BBR v2 在保持模型式优势的同时引入公平性折中；L4S（RFC 9330/9331）为低时延场景重构 ECN 语义；基于机器学习的拥塞控制（Aurora、Remy）尝试用离线训练替代手工增益曲线。此外，QUIC 将拥塞控制从内核上移到用户态，使新算法（如 BBR）的迭代不再依赖操作系统升级。

## 十、小结

现代变体（CUBIC、BBR、Vegas、DCTCP 等）在 Reno 的 AIMD 骨架上，针对大 BDP、低时延、高丢包等异质网络分别优化，是拥塞控制工程演进的主线。理解各自的「增/减律」与适用边界，比记住某个算法更重要。
