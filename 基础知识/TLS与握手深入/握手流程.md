# 握手流程

> 对应 RFC 8446（TLS 1.3 握手协议）§4；RFC 5246（TLS 1.2）；Kurose & Ross《Computer Networks》第 8 章「安全」一节；Stevens《TCP/IP Illustrated》卷 1 第 17 章。

## 一、背景与挑战

TLS 握手的目标是在一个可能被中间人监听、篡改的信道上，让通信双方协商出一组只有彼此知道的对称密钥，同时完成对端身份认证，并尽量压缩往返次数（RTT）。TLS 1.2 与 1.3 在握手结构上有本质差异：1.2 依赖 RSA 或 DH 密钥交换、大量明文握手消息、2-RTT 全握手；1.3 默认仅 ephemeral 密钥交换、把除 ClientHello/ServerHello 之外的握手消息全部加密，并支持 1-RTT 与 0-RTT。

握手还要处理会话恢复（session id / session ticket / PSK）、协议降级保护（downgrade protection）以及密码套件与版本协商。核心矛盾是「安全强度」与「连接建立延迟/成本」的权衡，移动网络与短连接（如 HTTP/3 短流）场景对此尤为敏感，每一次多余的 RTT 都可能带来数十毫秒的体感延迟。对延迟敏感的服务而言，握手本身往往比单条记录加密更影响首字节时间（TTFB）。

## 二、核心原理

TLS 1.3 的 1-RTT 全握手流程：客户端发送 ClientHello，携带 supported_versions、supported_groups、key_share（自己的临时公钥）、cipher_suites、signature_algorithms 等扩展。服务器回复 ServerHello（选定参数与自己的 key_share），随后立即发送被 handshake 密钥加密的 EncryptedExtensions、Certificate、CertificateVerify、Finished。

客户端在收到 ServerHello 后即可用协商出的握手密钥解密后续消息，验证证书链与签名，然后发送自己的 Finished（用 client handshake 密钥对全部握手转录做 MAC）。所有握手消息都进入 Transcript-Hash，被 CertificateVerify 签名与 Finished 的 MAC 覆盖，从而抵抗篡改。相较之下，1.2 需要 ClientKeyExchange 显式传输密钥材料，且 ChangeCipherSpec 是独立记录，整个握手更长且更多明文，中间人可观测更多握手元数据。

若服务器不支持客户端提供的 key_share 群，则回 HelloRetryRequest（HRR）让客户端补发正确群的公钥，这会增加一次往返但保证协商成功。HRR 本身也经过完整性保护，防止被降级利用。

## 三、形式化与数学基础

密钥调度基于 HKDF 两阶段（Extract 再 Expand）：

$$handshake\_secret = HKDF\_Extract(0,\ shared\_secret)$$

$$client\_hs = HKDF\_Expand(handshake\_secret,\ \text{tls13 c hs traffic},\ hashLen)$$

$$server\_hs = HKDF\_Expand(handshake\_secret,\ \text{tls13 s hs traffic},\ hashLen)$$

完成握手后再派生 master_secret 与 application traffic secret。Finished 的验证数据定义为：

$$verify\_data = HMAC(traffic\_secret,\ TranscriptHash(HandshakeContext))$$

其中 TranscriptHash 是截至本消息前所有握手消息的哈希，任何中间篡改都会改变哈希，使 HMAC 校验失败，从而提供完整性绑定。注意 1.3 中 CertificateVerify 的签名还额外覆盖一个固定字符串前缀（「TLS 1.3, server CertificateVerify」），防止签名被跨上下文重放。降级保护也通过把 server/client 的随机值中嵌入版本指纹，使 downgrade 企图可被双方检测。

## 四、代码实现

```c
// 简化的 1-RTT 握手消息序列（伪代码）
enum { CH, SH, EE, CT, CV, SF, CF };        // 各握手消息类型
send(client, ClientHello{ key_share, groups, versions });
recv(server, ServerHello{ key_share });
shared = ecdhe_derive(client_priv, server_pub);
hs_secret = HKDF_Extract(ZERO, shared);
client_hs = derive_secret(hs_secret, "c hs traffic");
server_hs = derive_secret(hs_secret, "s hs traffic");
// 此后用 server_hs 解密后续握手消息
recv(server, decrypt(server_hs, EE, CT, CV, Finished));
assert(hmac_verify(server_hs, transcript, Finished.verify_data));
send(client, Finished{ hmac(client_hs, transcript) });
// 切到 application traffic secret 收发应用数据
// 若遇到 HRR，则重发带对应 key_share 的 ClientHello
```

```c
// PSK 会话恢复（0-RTT 或 1-RTT resumption）的简化序列
send(client, ClientHello{ pre_shared_key = ticket, key_share? });
recv(server, ServerHello{ pre_shared_key = ticket });
psk = lookup(ticket);                       // 从会话缓存取 PSK
early_sec = HKDF_Extract(0, psk);          // 不依赖新 ECDHE
// 0-RTT 时还可直接用 psk 派生 early traffic 密钥发送 early data
```

## 五、与其他技术对比

| 维度 | TLS 1.2 全握手 | TLS 1.3 1-RTT | DTLS 1.3 |
| 往返次数 | 2 RTT | 1 RTT | 1 RTT（基于 UDP） |
| 密钥交换 | RSA/DHE/ECDHE | 仅 DHE/ECDHE（ephemeral） | 同 1.3 |
| 握手加密 | 仅 Finished 之后 | 除 ClientHello/ServerHello 外全加密 | 同 1.3 |
| 抗降级 | 有（但较弱） | 强（downgrade 纳入签名） | 同 1.3 |
| 传输层 | TCP | TCP | UDP（需重传/无状态 Cookie） |

DTLS 面向不可靠传输，因此要在记录层之上自行处理丢包重传与抗重放（显式序列号 + 滑动窗口），握手消息也需重传定时器，这与 TCP 上 TLS 依赖传输层可靠性的假设不同。

## 六、常见误区

误区一：TLS 握手一定 2 RTT。错，1.3 通常 1-RTT、可 0-RTT。误区二：Finished 只是确认信号。错，它用 HMAC 绑定全部握手消息转录，是防篡改的关键锚点。误区三：1.3 仍有 ClientKeyExchange。错，1.3 已移除该消息，密钥材料来自 key_share 扩展。误区四：会话恢复（PSK）无需任何握手。错，PSK 恢复仍需一次 Finished 交换以确认双方持有同一 PSK，否则无法建立流量密钥。误区五：HRR 表示握手失败。错，HRR 是正常的协商往返，用于让客户端补发服务器支持的群公钥。误区六：加密握手消息就不会被分析。错，ClientHello/ServerHello 仍明文，SNI、ALPN 等元数据可被观测，需 ECH 进一步隐藏。

## 七、与开源书·权威来源对应

- RFC 8446 §4「Handshake Protocol」定义消息序列与密钥调度；§4.4 规定 CertificateVerify 与 Finished 的 TranscriptHash 计算方式，并明确签名前缀防重放。
- RFC 5246 §7 描述 1.2 的两阶段握手与 ClientKeyExchange 字段，可与 1.3 对照理解演进。
- Kurose & Ross《Computer Networks》第 8 章「Secure TCP connections」给出握手直觉与密码学背景，可与协议细节互补。
- Bryant & O'Hallaron《CSAPP》从应用视角说明 HTTPS 协议栈，便于建立整体认知。
- Stevens《TCP/IP Illustrated》卷 1 给出 TLS 在 TCP 之上承载的封包结构。

## 八、面试题

1. TLS 1.3 全握手需要几 RTT？ServerHello 之后服务器为什么能立即发送加密的 Certificate？要点：1.3 用 key_share 在 ServerHello 阶段就完成 ECDHE，从而立刻派生 handshake 密钥，后续消息即可加密。
2. Finished 消息为什么能防止中间人篡改握手？要点：HMAC 覆盖全部 TranscriptHash；任何篡改都会改变哈希导致校验失败。
3. 为什么 TLS 1.3 的 handshake 消息大多加密而 1.2 不是？要点：减少明文指纹、抵抗主动干预、为后续 ECH 加密 SNI 打基础。
4. HRR 的作用是什么？要点：当客户端 key_share 群服务器不支持时，让客户端补发正确群公钥，保证协商成功且不牺牲前向安全。
5. 降级保护如何实现？要点：在客户端/服务器随机值中嵌入版本指纹，握手哈希纳入签名，任何 downgrade 企图都会被检测。

## 九、演进与趋势

0-RTT 与 PSK 会话恢复进一步降低延迟；Encrypted Client Hello（ECH，原 ESNI）把 ClientHello 的明文 SNI 也加密，抵御基于域名的审查与指纹；后量子密钥交换（ML-KEM / Kyber，hybrid 模式）正以「classical + PQ」双密钥形式并入 1.3 握手。QUIC 把 TLS 1.3 握手直接内嵌到传输层，实现建连同时完成加密协商，进一步压缩首字节时间，并借助连接 ID 支持无缝迁移。未来握手还可能引入证书压缩与握手合并以进一步节省字节。

## 十、小结

TLS 握手在「不安全的信道」上用非对称协商加上密钥派生建立「只有双方知道的对称密钥」，并完成身份认证。TLS 1.3 通过 ECDHE 默认获得前向安全、压缩到 1-RTT、加密大部分握手消息，并把 Finished 的 HMAC 作为防篡改锚点，是现代安全通信的标准建连流程。理解握手序列、密钥调度与降级保护，是排查连接失败、性能瓶颈与中间人攻击的基础。
