# 密钥交换

> 对应 RFC 8446（TLS 1.3 Key Exchange）§4.2.8；RFC 7919（frozen groups）/ RFC 5869（HKDF）；Diffie & Hellman 1976 原始论文。

## 一、背景与挑战

通信双方需在一个被监听的公开信道上协商出「只有彼此知道」的共享秘密，用于后续对称加密（AEAD）。早期 TLS 1.2 允许用服务器 RSA 公钥直接加密预主密钥（key transport），这虽简单但一旦服务器长期私钥泄露，所有历史流量都可被解密——缺乏前向安全。现代 TLS 强制 (EC)DHE（ephemeral Diffie-Hellman），即每次会话使用一次性临时密钥对，从而在长期密钥泄露情形下仍保护历史通信。

另一挑战是群参数安全：自定义的 DH 群可能隐含弱结构（如平滑素数）被特定数论攻击破解，因此标准倾向于固定、经过审查的群。此外，协商出的共享秘密只是「原始字节」，必须经过密钥派生才能用于不同用途（握手密钥、应用密钥、IV），否则密钥复用会带来可区分性风险。

在工程实践中，密钥交换还必须与证书体系协同：客户端用证书验证服务器身份，再用 (EC)DHE 协商出只有双方知道的秘密，二者结合才同时获得「认证」与「机密性」。遗漏任一方都会产生可被利用的漏洞。

## 二、核心原理

双方各自生成临时公私钥，仅交换公钥，再各自用「自己的私钥 × 对端公钥」算出同一个共享秘密 $S$。私钥从不在网络中传输，网络上只出现公钥。TLS 1.3 把静态 RSA 密钥传输、静态 DH 全部移除，只保留 DHE 与 ECDHE（以及稍后的 PSK 恢复与后量子混合）。

协商在 key_share 扩展中完成，supported_groups 声明支持的曲线/群（如 x25519、secp256r1、ffdhe2048），服务器若不支持客户端所给群则会回 HelloRetryRequest。ECDHE 在同等安全强度下密钥更短、运算更快，已成为事实标准，且 x25519 的 Montgomery ladder 天然恒定时间，降低了侧信道风险。曲线实现还需防止无效点（small subgroup）攻击，故需校验对端公钥的合法性。

## 三、形式化与数学基础

有限域 DH：

$$A = g^a \bmod p,\quad B = g^b \bmod p,\quad S = B^a = A^b = g^{ab} \bmod p$$

椭圆曲线（ECDHE，点乘记为 $[k]P$）：

$$A = [a]G,\quad B = [b]G,\quad S = [ab]G$$

安全性归约到离散对数 / 椭圆曲线离散对数问题（ECDLP）。密钥派生（TLS 1.3）以共享秘密为输入密钥材料：

$$IKM = S;\quad derived = HKDF\_Extract(0,\ IKM)$$

随后经多轮 Expand 得到握手与流量密钥，避免把原始 $S$ 直接用作对称密钥。曲线选择直接影响抗量子前的经典安全强度：x25519 约 128-bit 经典安全，secp256r1 同量级但实现更易出常数时间问题。

## 四、代码实现

```python
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

# 客户端：生成临时密钥对并导出公钥字节
cli_priv = ec.generate_private_key(ec.X25519())
cli_pub  = cli_priv.public_key().public_bytes_raw()   # 放入 key_share

# 收到服务器公钥 peer_raw 后
peer_pub = ec.X25519PublicKey.from_public_bytes(peer_raw)
shared   = cli_priv.exchange(ec.ECDH(), peer_pub)     # = [ab]G，从不经网络传输
# TLS 1.3 进一步用 HKDF-Extract(0, shared) 得到握手密钥材料
hk = HKDF(algorithm=hashes.SHA256(), length=32, salt=None, info=b"tls13 derived")
derived = hk.derive(shared)
```

```python
# 群参数校验（固定群优于自定义群）：拒绝未知或弱群
assert peer_group in (ec.X25519, ec.SECP256R1, ffdhe2048)
# 校验对端公钥为曲线上合法点，防无效点/小子群攻击
assert peer_pub.public_numbers().is_on_curve()
# 临时密钥应在握手完成后显式释放，避免持久化削弱前向安全
del cli_priv
```

## 五、与其他技术对比

| 维度 | RSA 密钥传输 | 静态 (EC)DH | ECDHE（临时） |
| 前向安全 | 无 | 无 | 有 |
| 私钥是否传输 | 否（用对方公钥加密） | 否 | 否 |
| 长期密钥泄露影响 | 可解密历史 | 可解密历史 | 仅影响该临时密钥 |
| TLS 1.3 支持 | 已移除 | 已移除 | 默认 |

RSA 密钥传输还把「认证」与「密钥协商」耦合在证书私钥上，一旦该私钥用于解密流量就失去机密性隔离；ECDHE 则把认证（证书签名）与机密性（临时密钥）解耦。

## 六、常见误区

误区一：密钥交换把「密钥」传给对方。错，双方各自独立算出共享秘密，私钥从不传输。误区二：DHE 比 ECDHE 更安全。错，在等价安全强度下 ECDHE 用更短密钥、更快且更易做常量时间实现。误区三：前向安全由证书保障。错，它由「每次会话的 ephemeral 临时密钥」保障，证书私钥泄露不会泄漏临时密钥。误区四：共享秘密 $S$ 可直接当对称密钥用。错，必须经 HKDF 派生出相互独立的握手/应用流量密钥，避免密钥复用与可区分性风险。误区五：群参数随便选。错，弱群（平滑素数、小子群）可被破坏性攻击，应使用 RFC 7919 固定群或标准曲线。误区六：ECDHE 自动恒定时间。错，曲线实现需显式保证，否则标量乘法可能泄漏私钥比特。

## 七、与开源书·权威来源对应

- RFC 8446 §4.2.8 定义 key_share / supported_groups；§7.4 描述完整密钥调度与密钥用途分离。
- RFC 5869 定义 HKDF（Extract + Expand 两阶段），是 TLS 1.3 密钥派生的核心，保证即使 $S$ 部分可预测也能得到强随机密钥。
- RFC 7919 给出固定的 ffdhe 群参数，避免部署方自选弱群。
- Kurose & Ross《Computer Networks》第 8 章给出 Diffie-Hellman 的直觉与安全性论证。
- Diffie & Hellman 1976 原始论文是临时密钥协商的理论源头。

## 八、面试题

1. ECDHE 为什么天然具备前向安全？要点：临时密钥用后即弃，长期密钥（证书私钥）不参与共享秘密计算，泄露也无从反推历史会话。
2. TLS 1.3 为什么彻底移除 RSA 密钥传输？要点：它无前向安全，且不利于 PFS 与 0-RTT 的统一定义。
3. 共享秘密 $S$ 能直接用作 AES 密钥吗？要点：不能，需经 HKDF 派生并分离不同用途的密钥，否则存在密钥复用与可区分性风险。
4. 为何标准推荐固定群（如 ffdhe2048）而非自定义群？要点：避免隐含弱结构被数论攻击，且便于实现与审计。

## 九、演进与趋势

后量子密钥交换（ML-KEM / Kyber）以「X25519 + ML-KEM」hybrid 模式并入 TLS 1.3，使单次握手同时抵抗经典与量子攻击；曲线层面 x25519 因恒定时间、无参数歧义已成主流，secp256r1 仍常见于合规场景。固定群参数（RFC 7919）与可验证随机曲线进一步降低弱参数风险，而密钥协商与认证的解耦也让轮换证书不影响机密性。实现侧还强调把临时私钥锁定在内存、禁用换页，防止冷启动泄露。

## 十、小结

密钥交换在非对称框架上让双方各自算出同一个共享秘密，TLS 1.3 用 ephemeral 的 ECDHE 默认获得前向安全，并经 HKDF 派生出分层流量密钥，是 TLS 机密性与 PFS 的根基。它把「认证」与「机密性」解耦，使长期密钥泄露的爆炸半径被限制在单台服务器，而非全部历史流量。正确实现还需校验对端公钥合法性与选用固定群，避免协议层之外的侧信道与小子群风险。
