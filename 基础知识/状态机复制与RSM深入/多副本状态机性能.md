# 多副本状态机性能

> 对应 Ongaro & Ousterhout 2014（Raft）与 DDIA 第9章性能讨论。

## 一、背景与挑战
RSM 为一致性付出性能代价：每条命令需多数派网络往返、磁盘 fsync、串行 apply。如何在保一致前提下提升吞吐与降低延迟，是工程核心。

## 二、核心原理
优化维度：① 批处理（Pipeline）多条命令一次 RPC；② 并行磁盘写与网络；③ 只读请求走「租约读或线性一致读」避免全共识；④ 流水线复制（不阻塞等前条提交）；⑤ 多 Raft group 分片。

## 三、形式化与数学基础
吞吐近似 \\(T \approx \frac{batch\_size}{RTT + disk\_latency}\\)。降低 RTT 占比（批处理或流水线）线性提升吞吐；只读读路径延迟可由共识 \\(O(RTT)\\) 降到本地 \\(O(1)\\)（租约内）。

## 四、代码实现
```python
# 批量提案
def propose_batch(cmds):
    entries = [log.append(c) for c in cmds]   # 一次性多条
    replicate_async(entries)                   # 流水线
    return wait_majority(entries)
```

## 五、与其他技术对比
单机状态机无网络开销但无容错；RSM 多副本换容错；异步主从延迟低但可能丢或乱序。Multi-Paxos 与 Raft 在性能上接近，差异在工程清晰度。

## 六、常见误区
1. 每条命令一次往返：吞吐受限，应批处理。
2. 所有读都走共识：只读可走租约读。
3. 串行 apply 成为瓶颈却未分片：用多 group 横向扩展。

## 七、与开源书/权威来源对应
Raft 论文讨论批处理与流水线；6.824 实验测 RSM 吞吐；TiKV 用 multi-raft 分片。

## 八、面试题
问：如何降低 RSM 读延迟？
答：用租约读或 Raft ReadIndex，避免每条读走完整共识。

## 九、演进与趋势
无领导（leaderless）共识与并行 Raft 进一步提升横向性能。

## 十、小结
RSM 性能靠批处理、流水线、租约读与分片，在一致与速度间取舍优化。
