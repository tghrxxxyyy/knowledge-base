# 多副本状态机性能

> 对应 Ongaro & Ousterhout 2014（Raft）与 Ongaro 博士论文中的只读与批处理讨论；Chandra, Griesemer & Redstone 2007（Paxos Made Live）；Kleppmann《DDIA》第 9 章；Corbett et al. 2012（Spanner）。

## 一、背景与挑战
RSM 为一致性付出明确的性能代价：**每条命令都需要一次以上网络往返、一次多数派持久化、再按序 apply**。在跨机房部署时，RTT 可能是毫秒级甚至数十毫秒，若每条命令都独立走一轮，吞吐会被 RTT 死死按住；在单机房内，磁盘 fsync 与串行 apply 又可能成为新的瓶颈。

优化难点在于：其一，**一致性与延迟的耦合**——同步复制必须等待多数派落盘，无法通过简单并发绕过；其二，**串行 apply 的瓶颈**——为保持确定性必须按 index 顺序执行，单机 FSM 的执行线程成为上限；其三，**读路径的误用**——若所有读都走完整共识，读吞吐同样被共识吞吐限制，而实际上大量读可以走更廉价的路径；其四，**负载倾斜**——单 Raft 组内热点 key 会让整个组受限，需要分片但不能破坏跨分片事务的语义。理解「哪一段开销是必须的、哪一段是可优化的」，是性能工程的核心。

## 二、核心原理
主要优化维度可归为四类。**第一，批处理（batching）**：把多条客户端命令合并成一次网络往返与一次 fsync，用更大的单位摊薄固定开销；代价是引入「等待凑批」的额外延迟，需要在批大小与延迟间取折中（常见做法是有上限的微批或 Nagle 式合并）。

**第二，流水线（pipelining）**：领导者不必等前一条命令提交完成就可以继续发送后续日志项，使网络与磁盘的时间重叠，把「串行等待」变成「重叠流水」。

**第三，只读路径优化**：线性一致的读有两种常见廉价实现——**ReadIndex**（领导者先确认自己仍持有多数派支持，取一个读索引，等本地 apply 追到该索引后返回）与**租约读（lease read）**（领导者依靠一段时间内不会出现新领导者的时钟假设，直接本地读）。二者把读延迟从「一次共识往返」降到「本地 apply 追上」甚至「本地读」，而 follower read 通过向领导者询问安全读点，把读扩展到从节点。

**第四，分片（sharding）**：用多个相互独立的共识组（multi-raft / multi-group）横向扩展，每个组独立选主与复制；代价是跨组分片事务需要两阶段提交或类似协调，且组成员数过多会放大选主与心跳开销。

此外还有**组提交与并行落盘**（多个日志项并行 fsync 后统一确认）、**快照与日志压缩**降低重启重放时间、以及**客户端侧批量与去重缓存**减少重复命令。所有这些都必须在「不破坏确定性 apply 与提交规则」的前提下进行。

## 三、形式化与数学基础
把单条命令的延迟拆分为固定项与可摊薄项。设网络单程为 $RTT$、磁盘 fsync 为 $D$、批大小为 $b$，则单命令的平均写入延迟近似为
$$ L \approx \frac{RTT + D + C_{apply}}{b} + L_{queue} $$
而吞吐近似为
$$ T \approx \frac{b}{RTT + D + C_{apply}} $$
这解释了为什么批处理对吞吐是**线性提升**，代价只是队列延迟 $L_{queue}$ 上升。若要满足延迟目标 $L_{SLO}$，则可用的最大批大小为
$$ b_{max} = \frac{RTT + D + C_{apply}}{L_{SLO} - L_{queue}} $$
流水线下延迟改为「最后一项的延迟」而非「所有项之和」：
$$ L_{pipe} \approx RTT + D + b \cdot C_{apply} $$
即网络与磁盘只付一次，apply 仍随批线性增长——因此**串行 apply 常常成为流水线的最终瓶颈**。只读优化方面，走完整共识的读延迟为 $O(RTT)$，而 ReadIndex 为 $O(\max(0, t_{apply} - t_{commit}))$（通常接近 0），租约读在租约有效期内为 $O(1)$ 本地访问，但引入了时钟漂移安全性假设 $\Delta < \tau_{lease} - \epsilon$。分片后的总吞吐近似线性叠加但受协调成本约束：
$$ T_{total} = \sum_{g=1}^{G} T_g - \Gamma(G) $$
其中 $\Gamma(G)$ 为跨组协调、心跳与元数据管理的开销增量，随组数增长而增长，故组数并非越多越好。

## 四、代码实现
批处理与流水线复制的接口抽象：
```python
class Replicator:
    def __init__(self, transport, log, batch_max=128, flush_interval=0.002):
        self.transport = transport      # 网络发送
        self.log = log                  # 持久化日志
        self.batch_max = batch_max
        self.flush_interval = flush_interval

    def propose_batch(self, cmds):
        entries = [self.log.append(c) for c in cmds]        # 一次性追加多条
        self.transport.replicate_async(entries)             # 流水线：不阻塞等待
        return self.wait_majority(entries[-1].index)         # 只等最后一条的多数派

    def wait_majority(self, index):
        # 组提交：等待多数派已确认到达该 index（隐含前序项也已确认）
        return self.transport.await_commit(index)
```

ReadIndex 与租约读的实现要点（示意）：
```python
def read_index(leader, ctx):
    if not leader.step_down_if_stale():        # ① 确认仍是领导者（心跳多数派回应）
        raise NotLeader()
    idx = leader.commit_index()                # ② 取当前提交索引作为安全读点
    leader.wait_applied(idx)                   # ③ 等本地 FSM 追到该索引
    return leader.fsm.query()                  # ④ 此时本地读满足线性一致
```

分片与跨分片事务（示意）：
```python
def route(key, groups):
    return groups[hash(key) % len(groups)]     # 一致哈希定位到某个共识组

def cross_shard_txn(coordinator, shards, prepare, commit):
    # 两阶段提交：任一分片失败则整体回滚，注意协调者自身也需容错
    votes = [s.propose(prepare) for s in shards]
    if all(votes):
        for s in shards:
            s.propose(commit)
        return "committed"
    for s in shards:
        s.propose("abort")
    return "aborted"
```

## 六、常见误区
1. **「每条命令一次往返无所谓」**——错。跨机房 RTT 是硬上限，必须靠批处理与流水线把固定开销摊薄，否则吞吐与 RTT 成反比。
2. **「所有读都走共识更安全」**——方向安全但不必要。读可走 ReadIndex 或租约读，既不牺牲线性一致，又把延迟从 $O(RTT)$ 降到接近本地。
3. **「批越大越好」**——错。批越大吞吐越高但延迟与队列积压越严重，需按 SLO 计算可用批上限，并对慢客户端做隔离。
4. **「加了副本就能提升吞吐」**——错。同步副本增加的是写入应答数与 RTT 敏感度；提升写吞吐要靠分片（多组）而非单组加副本。
5. **「串行 apply 不是瓶颈」**——错。流水线把网络与磁盘只付一次后，apply 随批线性增长，往往成为真正的天花板；需要优化 FSM 执行或用多组分摊。

## 八、面试题
1. **如何降低 RSM 的读延迟？** 要点：ReadIndex（确认领导权后取读点并等待 apply 追上）或租约读（租约内本地读），把 $O(RTT)$ 降到接近本地；需注意时钟假设与租约失效回退。
2. **批处理为什么能线性提升吞吐？** 要点：$T \approx b/(RTT + D + C_{apply})$，固定开销被 $b$ 摊薄；代价是等待凑批带来的队列延迟。
3. **流水线提升的是什么？** 要点：让网络与磁盘时间重叠，只付一次 RTT/D，但 apply 仍随批线性增长，故 FSM 执行常成为瓶颈。
4. **单组加副本能提升写吞吐吗？** 要点：不能。副本增加容错与应答数，写吞吐仍受单组串行与 RTT 限制，需用多组分片扩展。
5. **分片越多越好吗？** 要点：不是。跨组协调、心跳与元数据开销随组数增长，存在最优区间；热点还需要动态再平衡。

## 九、演进与趋势
工程方向一是把共识做成**可组合的库**（如各类 Raft 库）并对接批量提交、异步 IO 与共享日志，让吞吐接近硬件极限。方向二是**分片自动化**：multi-raft 配合调度器做负载感知的副本迁移与分裂合并，把「加机器就加吞吐」变成常态。方向三是**读扩展**：follower read、非领导者只读副本与缓存层协同，把读压力从领导者卸载。方向四是**确定性数据库**（固定事务顺序的确定性执行）以减少协调与锁开销，并探索并行 apply 的可行边界。硬件层面，持久内存、RDMA 与更低延迟网络持续抬高共识的性能上限，具体实现与参数**以官方最新文档与论文为准**。

## 十、小结
RSM 的性能优化围绕一条主线：**固定开销是 RTT 与 fsync，可优化的是「每条命令付几次」**。批处理把多次摊成一次，流水线让网络与磁盘重叠，只读走 ReadIndex 或租约读绕开共识，分片把单组上限变成多组叠加。优化过程中最容易被忽略的是串行 apply——当网络与磁盘不再是瓶颈时，按 index 顺序执行 FSM 就成了新的天花板。理解这些量之间的关系（$T \approx b/(RTT+D+C_{apply})$），才能在延迟与吞吐之间做出有依据的取舍。
