# RSM基本定义与确定性

> 对应 Lamport 1978（Time, Clocks, and the Ordering of Events）；Schneider 1990（State Machine Approach）；Ongaro & Ousterhout 2014（Raft）。

## 一、背景与挑战
如何让多台机器表现得像一台始终可用的机器？状态机复制（Replicated State Machine, RSM）给出的答案是：**所有副本从同一初始状态出发、以相同顺序执行相同命令，则必然得到相同状态**。这个结论一旦成立，复制问题就被分解为两个更清晰的问题——「如何让日志顺序一致」交给共识算法，「如何保证执行结果相同」交给确定性设计。

前提正是「命令执行确定性」。这也是 RSM 最容易被低估的约束：现实中导致副本分叉的原因往往不是共识崩了，而是状态转移函数里出现了**未定义行为或不可复现的输入**——读取本地时间、使用随机数、依赖哈希表遍历顺序、依赖浮点运算的平台差异、依赖未排序的并发更新、调用外部不可控服务（如支付网关返回的随机单据号）。一旦这些进入状态转移，即使日志完全一致，副本状态也会发散，而且通常**不会立刻报错**，而是在某个后续操作上才表现为诡异的不一致或崩溃。

## 二、核心原理
RSM 的核心是一个确定性转移函数：给定相同状态 $S$ 与命令 $C$，$\delta(S,C)$ 在任意副本上产生相同结果。只要日志（命令序列）在副本间一致有序，各副本独立重放即可得到一致状态，**无需互相拷贝状态**——这正是 RSM 相比「状态传输」方案在带宽上更优的原因：传输的是命令（通常很小），而不是整个状态。

要让这套机制真正工作，还需若干配套设计。**命令必须是自包含的**：所有非确定因素（时间戳、随机种子、唯一 ID）必须由领导者一次性确定并写入命令体内，而不是在 apply 时各副本各自生成。**客户端交互必须幂等**：重试会带来重复命令，需用请求 ID 与去重表保证同一条命令只生效一次。**执行必须按 index 严格递增**：不能为了并行而乱序 apply，除非能证明这些命令的转移可交换。**外部副作用必须延后或去重**：向客户端发送回复、写外部存储等动作应由领导者统一执行，或通过去重机制保证不重复。此外，**状态必须可序列化**：快照用于恢复与给落后副本传输，因此状态中不能包含无法持久化的句柄（如文件描述符、连接对象）。

## 三、形式化与数学基础
定义状态转移函数
$$ \delta: \mathrm{State} \times \mathrm{Command} \to \mathrm{State} $$
若各副本日志一致，即 $\vec{C} = (C_1, \dots, C_n)$ 在所有副本上相同，则
$$ S_n = \delta(\dots \delta(\delta(S_0, C_1), C_2) \dots, C_n) $$
对所有副本相同。把重复应用写成闭包形式：
$$ S_n = \delta^{*}(S_0, \vec{C}) $$
**确定性要求**可形式化为：若两个副本的输入相同，则输出必然相同，
$$ \forall a,b:\ (\mathrm{state}_a = \mathrm{state}_b) \wedge (C_a = C_b) \Rightarrow \delta(\mathrm{state}_a, C_a) = \delta(\mathrm{state}_b, C_b) $$
违反该式即出现分叉，即存在某个命令使 $\mathrm{state}_a \neq \mathrm{state}_b$，且该差异会在后续应用中持续放大。工程上的常用手段是「把非确定性输入显式化」：将 $\delta$ 改写为纯函数
$$ \delta(S, C) = \delta_{pure}(S, C, \xi), \qquad \xi \in \mathrm{Command} $$
其中 $\xi$ 是时间戳、随机数等全部非确定参数，且由领导者在**提案时**确定后写入 $C$。这样 $\delta_{pure}$ 就只依赖 $(S, C)$，确定性条件转化为「$\delta_{pure}$ 实现中不存在全局可变状态与外部调用」。此外，模拟类应用常要求**状态收敛的可观测性**：定义状态指纹
$$ \mathrm{FP}(S) = H(\mathrm{canonical}(S)) $$
各副本可周期性比对 $\mathrm{FP}$，以便尽早发现分叉而不是等到故障时才暴露。

## 四、代码实现
一个正确与错误写法并存的最小 RSM：
```python
import time, random, hashlib, json

class RSM:
    def __init__(self):
        self.state = {}

    # 错误：apply 里读时钟/随机数，破坏确定性
    def apply_bad(self, cmd):
        if cmd["op"] == "SET":
            self.state[cmd["key"]] = cmd["val"]
            self.state["_ts:" + cmd["key"]] = time.time()     # 非确定
        elif cmd["op"] == "TOKEN":
            self.state["token"] = random.randint(0, 10**9)    # 非确定
        elif cmd["op"] == "KEYS":
            return list(self.state.keys())                    # 遍历序可能变化

    # 正确：所有非确定输入在提案时确定并写入命令
    def apply(self, cmd):
        if cmd["op"] == "SET":
            self.state[cmd["key"]] = cmd["val"]
            self.state["_ts:" + cmd["key"]] = cmd["ts"]       # 由领导者写入
        elif cmd["op"] == "TOKEN":
            self.state["token"] = cmd["token"]                # 由领导者生成
        elif cmd["op"] == "DELETE":
            self.state.pop(cmd["key"], None)
        elif cmd["op"] == "INC":
            self.state[cmd["key"]] = self.state.get(cmd["key"], 0) + cmd["val"]
        return None

def fingerprint(state):
    # 规范化序列化：键排序后再哈希，避免遍历序引入差异
    canon = json.dumps(state, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canon.encode()).hexdigest()
```

确定性地枚举状态，避免依赖语言默认遍历序，同时保证状态可序列化（不含连接、文件句柄等对象）：`sorted(k for k in state if not k.startswith("_"))`。

幂等去重把重试变成无害：
```python
class Dedup:
    def __init__(self):
        self.seen = {}
    def once(self, request_id, apply_fn, cmd):
        if request_id in self.seen:
            return self.seen[request_id]          # 返回缓存结果，不重复执行
        result = apply_fn(cmd)
        self.seen[request_id] = result
        return result
```

## 六、常见误区
1. **「用随机数/时间参与状态转移没关系」**——错。这是副本分叉的头号原因；必须把非确定输入在提案时固化进命令。
2. **「依赖 map 遍历序只是风格问题」**——错。不同实现或不同版本的语言运行时遍历序可能不同，跨语言场景更容易暴雷；必须显式排序。
3. **「日志一致就等于状态一致」**——错。日志一致只是必要条件，还需 $\delta$ 确定性且 apply 严格按序；否则日志相同状态仍可能发散。
4. **「浮点计算结果各平台一致」**——错。编译器优化、FPU 设置、库版本差异都可能导致末位不同，进而放大为不一致；敏感场景应使用定点数或整数。
5. **「快照随便序列化即可」**——错。快照必须覆盖全部影响状态的字段且可反序列化；含句柄、连接或未持久化的临时结构会导致恢复后行为不同。

## 七、与开源书·权威来源对应
- Lamport 1978：以逻辑时钟刻画「先后」，为「全序一致」提供理论语言，是 RSM 顺序问题的理论基础。
- Schneider 1990：状态机方法的经典论文，正式给出 RSM 定义、确定性前提与容错条件。
- Ongaro & Ousterhout 2014（Raft）：把 RSM 作为核心抽象，明确日志与状态机之间的接口。
- Fischer, Lynch & Paterson 1985：FLP 不可能性，说明「顺序一致」为何需要部分同步假设才能终止。
- Herlihy & Shavit《The Art of Multiprocessor Programming》：并发对象的确定性顺序与线性一致性讨论。
- Kleppmann《Designing Data-Intensive Applications》第 9 章：把 RSM 与共识、幂等、去重的工程细节串起来。
- Tanenbaum《Modern Operating Systems》：进程与线程状态模型，理解「同输入同输出」的底层含义。

## 八、面试题
1. **RSM 为何要求确定性？** 要点：只有确定性转移才能保证「同序命令到同状态」；否则副本会在同一日志上分叉。
2. **如何处理时间戳和随机数？** 要点：由领导者（提案方）生成并写入命令体，apply 时只读取命令中的值，把非确定性输入显式化为命令的一部分。
3. **日志一致是否足够？** 要点：不够。还需确定性 $\delta$、严格按 index 顺序 apply、以及幂等去重与快照可序列化。
4. **如何检测副本已经分叉？** 要点：周期性对规范化状态做哈希得到指纹并各副本比对；早发现可以把损失限制在较小范围。
5. **RSM 与状态传输的取舍？** 要点：RSM 传命令、带宽小、对确定性要求强；状态传输传差异、对确定性无要求但带宽可能很大，且难以支持频繁写入。

## 九、演进与趋势
确定性正在从「软件约定」变成「框架能力」：把非确定输入（时钟、随机、ID 生成）收敛到领导者并由框架注入，而业务代码只写纯函数式的 apply，是主流工程化的做法。与此同时，**确定性数据库**（固定事务顺序的确定性执行）把整个事务调度做成确定性状态机，从而简化复制、减少锁与协调开销，代价是需要预知读集或做额外分析。另一方向是**并行 apply**：在能证明命令间可交换的前提下（如按 key 分区的独立更新）并行执行以突破串行瓶颈，但这要求对确定性边界做更精细的形式化论证。相关实现取舍**以官方最新文档与论文为准**。

## 十、小结
RSM 以「同序 + 确定性」换取多副本一致：共识负责把日志顺序定下来，确定性转移函数负责把日志变成相同状态。工程上真正致命的问题几乎都出在确定性上——时间、随机、遍历序、浮点、并发、外部调用都会让副本悄悄分叉。正确做法是把所有非确定输入在提案时固化进命令，让 apply 成为纯函数，并配合幂等去重、状态指纹与可序列化快照来守住边界。
