# 状态机复制容错边界

> 对应 Schneider 1990（RSM）；Lamport 1998（Paxos）；Gilbert & Lynch 2002（CAP）；Lamport, Shostak & Pease 1982（Byzantine Generals）；Castro & Liskov 1999（PBFT）。

## 一、背景与挑战
RSM 能容忍多少故障？什么时候系统会不可用？这些问题的答案由**故障模型**与**副本数**共同决定，而不是由「用了 Raft」这一事实决定。规划集群规模、容量与可用性目标时，必须先明确边界，否则会出现「以为三副本很安全，实际上容错能力为零」这类致命误判。

边界问题包含几个正交维度：其一，**故障类型**——崩溃-恢复（crash-recovery，节点只是停止响应，之后可能带着持久化状态回来）还是拜占庭（任意错误行为，包括发假消息、选择性沉默、串谋）；其二，**是否需要区分「停止服务」与「返回错误结果」**——前者是安全性的可用性代价，后者是安全性被破坏，两者严重程度完全不同；其三，**网络假设**——同步、异步还是部分同步，直接决定能否给出有界的响应时间；其四，**成员集合是否静态**——动态成员变更期间的容错下界会暂时收紧。此外还有「故障域」的现实问题：三副本若放在同一机架或同一可用区，仍可能被单次断电或单次网络分区同时打掉。

## 二、核心原理
崩溃故障模型下，多数派是全部机制的核心。设总副本数为 $N$，容错数为 $f$：
$$ N = 2f + 1 $$
因为任一次决策需要 $\lceil N/2 \rceil + 1 = f+1$ 个副本应答，而故障最多 $f$ 个，剩余 $N - f = f+1$ 个正确副本足以构成多数派。这同时保证了任意两个多数派必然相交（交集至少含一个正确副本），从而不可能对同一日志位置决定不同值——这是**安全性的几何基础**。

拜占庭故障模型下，要求
$$ N = 3f + 1 $$
直觉是：故障节点可能说谎，因此不能只靠「多数」理解为一票，必须让正确节点数量足以覆盖故障节点可能制造的假信息。PBFT 类算法正是按此下界设计，并需要额外的视图切换与消息认证（MAC / 签名）来约束谎报。

可用性侧，RSM 在「凑不齐多数派」时会**停止接受写入**，表现为 CP 系统：宁可不可用，也不返回不一致结果。与之相对，主从异步复制在多数副本不可达时仍可能继续在主上写入，代价是主挂时会丢失未同步的已确认数据。**CAP** 指出在发生网络分区时必须在一致性（C）与可用性（P 意义上的可用）之间取舍，**PACELC** 进一步指出即使没有分区，也仍要在延迟（L）与一致性（C）之间取舍——因为跨地域同步复制必然付出延迟。

## 三、形式化与数学基础
多数派相交性质是安全性的形式化表述。对任意两个集合 $Q_1, Q_2 \subseteq \{1,\dots,N\}$，若
$$ |Q_1| > N/2 \ \wedge\ |Q_2| > N/2 \ \Rightarrow\ Q_1 \cap Q_2 \neq \varnothing $$
则同一时刻不可能存在两个互斥的决策多数派。代入 $N = 2f+1$ 可得写入所需应答数
$$ q = \left\lceil \frac{N}{2} \right\rceil + 1 = f + 1 $$
故障 $f$ 个后仍剩余 $N - f = f+1 = q$ 个正确副本，恰好可继续决策；故障 $f+1$ 个则 $N - (f+1) = f < q$，写入停摆。可用性因此是副本数的阶梯函数：
$$ \mathrm{Available}(N, f_{fail}) = \mathbb{1}\big[\,f_{fail} \le \lfloor (N-1)/2 \rfloor\,\big] $$
若把每个副本的独立可用度设为 $a$，则「至少 $q$ 个可用」的概率为
$$ A_{sys} = \sum_{k=q}^{N} \binom{N}{k} a^{k}(1-a)^{N-k} $$
该式解释了为什么三副本（$q=2$）在 $a=0.99$ 时系统可用度约为 $99.97\%$，看似很高但**故障是相关的**——同机架、同电源、同交换机故障会让独立性假设失效，因此必须做故障域隔离（跨机架、跨可用区）。拜占庭下界 $N = 3f+1$ 同样可由「正确节点必须能在收到 $f$ 个谎报后仍分辨真相」推出。

## 四、代码实现
用代码把边界关系具体化：
```python
def quorum_size(n):
    return n // 2 + 1

def can_tolerate(n, f):
    return f <= (n - 1) // 2

# 崩溃故障：3 副本容 1，5 副本容 2，4 副本仍只容 1（偶数副本无额外收益）
assert quorum_size(3) == 2 and can_tolerate(3, 1)
assert quorum_size(5) == 3 and can_tolerate(5, 2)
assert can_tolerate(4, 1) and not can_tolerate(4, 2)   # 4 副本容错与 3 副本相同

# 拜占庭故障：需要 3f+1
def byzantine_min(f):
    return 3 * f + 1

assert byzantine_min(1) == 4 and byzantine_min(2) == 7
```

可用性估算与故障域检查（示意）：
```python
from math import comb

def availability(n, a):
    q = quorum_size(n)
    return sum(comb(n, k) * a**k * (1 - a)**(n - k) for k in range(q, n + 1))

print(round(availability(3, 0.99), 6), round(availability(5, 0.99), 6))
# 三副本约 0.99970，五副本约 0.99999（假设故障相互独立）

def check_fault_domains(replicas, min_domains=3):
    # replicas: [{"id": ..., "az": ..., "rack": ...}]
    zones = {r["az"] for r in replicas}
    if len(zones) < min_domains:
        return f"风险：仅跨 {len(zones)} 个可用区，相关性故障可能同时打掉多数派"
    return "故障域分布符合要求"
```

成员变更的安全约束（示意）：
```python
# 一次变更只改一个成员时，安全所需多数派在变更瞬间不得重叠冲突
def safe_step(old_set, new_set):
    assert len(old_set ^ new_set) == 2, "一次只增删一个成员"
    q_old, q_new = quorum_size(len(old_set)), quorum_size(len(new_set))
    return q_old, q_new        # 过渡期需按更严格的多数派要求推进
```

## 六、常见误区
1. **「2 副本可容 1 个故障」**——错。2 副本需要 2 票才能决策，任一挂即无多数派，写入停摆；3 副本才是容 1 的最小配置。
2. **「副本越多越安全」**——需要区分概念。增加副本提高容错上限，但也增加写入应答数与延迟；且偶数为 4 副本的容错与 3 副本相同，性价比低。
3. **「有共识就不会脑裂」**——错。脑裂的避免不是靠算法本身，而是靠**必须获得多数派才能决策**这一约束；若配置成「单节点也可提交」就等价于放弃安全性。
4. **「拜占庭场景用 2f+1 够」**——错。需要 $3f+1$，且需消息认证与视图切换机制，成本显著更高。
5. **「三副本一定安全」**——错。若三副本处于同一故障域（同机架、同交换机、同电源），一次物理故障可以同时带走多数派，容错形同虚设。

## 八、面试题
1. **为何 $2f+1$ 能容忍 $f$ 个崩溃？** 要点：写入需 $\lceil N/2 \rceil + 1$ 应答；故障 $f$ 个后剩 $f+1$ 个正确副本，仍可构成多数派；任意两多数派必相交，保证不冲突。
2. **为什么 2 副本不能容 1 个故障？** 要点：$N=2$ 时多数派为 2，任一节点失效即无法凑齐，写入直接停摆。
3. **拜占庭为什么需要 $3f+1$？** 要点：故障节点可能说谎，正确节点必须多到能在 $f$ 个错误信息中自证真相；同时需认证与多轮投票。
4. **失去多数派时系统应如何表现？** 要点：停止接受写入（CP），返回失败而不是返回可能不一致的结果；只读也需谨慎，可能需要对领导者身份的确认。
5. **三副本跨同一机架有什么风险？** 要点：故障域重叠使失败相关，单次物理事件可打掉多数派；应按可用区/机架分散并做容量预留。

## 九、演进与趋势
成员管理从静态配置走向**在线变更**（joint consensus、一次改一个成员），让容错边界可在运行中调整，同时配套自动再平衡与扩缩容。地理分布上，跨区域共识付出高延迟，因此出现「分区内共识 + 跨区异步」的分层结构，或把强一致限制在关键元数据、把数据面放宽为可调一致性。容错模型上，**拜占庭容错在联盟链与多方协作场景**重新受到重视，优化方向是降低通信复杂度（从平方级降到线性级）与减少轮次。云环境下，可用性计算必须从「独立概率」升级为「相关性故障建模」，并配合反亲和与故障注入演练验证边界。具体参数与下界推导**以官方最新文档与原始论文为准**。

## 十、小结
RSM 的容错边界由故障模型与多数派几何共同决定：崩溃故障需 $2f+1$ 副本容忍 $f$ 个，拜占庭故障需 $3f+1$，写入需多数派应答，失去多数派即停写（CP）。可用性是副本数的阶梯函数，而非线性增长——2 副本与 4 副本都不带来预期的额外容错，且故障相关性会使理论可用性大幅缩水。真正可靠的容错设计，是「正确的副本数 + 明确的故障模型 + 隔离的故障域 + 演练验证」四者的组合。
