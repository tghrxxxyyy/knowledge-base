# 确定性状态机与命令日志

> 对应 Schneider 1990（State Machine Approach）；Ongaro & Ousterhout 2014（Raft 的日志复制与日志匹配性质）；Cachin, Guerraoui & Rodrigues《Introduction to Reliable and Secure Distributed Programming》。

## 一、背景与挑战
RSM 选择复制「操作」而不是「结果」，因此需要一份**有序、持久、一致**的命令日志作为真相源。这条路线带来三个必须同时满足的挑战：其一，**命令必须可序列化**——命令在执行前要被编码为字节序列并跨版本、跨语言传递，因此不能含歧义（如同一字段既可为字符串又可为数字）、不能含指针或本地句柄；其二，**日志必须容错**——不丢、不重、不乱序，即使领导者切换、磁盘故障、网络分区；其三，**重放必须确定**——同一条日志在任何副本、任何时刻重放都得到相同状态，这就要求命令内容自包含且 apply 严格按 index 递增。

另一个容易被忽视的挑战是**日志的长期可维护性**。日志是真相源，意味着格式变更（新增命令类型、字段）必须向后兼容，否则老副本无法重放新日志；同时也意味着日志不能无限增长，必须配合快照与截断。设计不好会在「升级」与「恢复」两个环节集中暴露。

## 二、核心原理
基本流程是：**领导者将客户端命令追加到本地日志，通过共识复制到多数派，提交后各副本按顺序 apply**。每条日志项通常包含三元组 `(term, index, command)`：`index` 给出唯一位置，`term` 记录产生它的任期（用于选举与一致性判断），`command` 是序列化后的操作。

关键的工程规则有六条。**第一，apply 严格按 index 递增**，不得跳号或乱序，因为确定性依赖顺序。**第二，提交与 apply 分离**：提交（committed）表示多数派已持久化、不可回退；apply 表示已应用到 FSM，`last_applied <= commit_index` 是必须维持的不变式。**第三，领导者只能提交当前任期的项**（通过提交一条当前任期的空日志项来间接提交旧任期项），否则可能提交了后来被覆盖的项。**第四，日志匹配性质**：若两副本在某个 index 的 term 相同，则该 index 及其之前的所有日志项完全相同；这是判断日志是否可通过追加恢复一致的依据。**第五，冲突处理是截断而非合并**：当领导者发现跟随者本地存在冲突项时，跟随者删除从冲突点起的本地日志再接收领导者的项，因为日志是「权威顺序」而非「多源合并」。**第六，客户端交互需幂等**：重试导致重复命令必须靠请求 ID 去重。

## 三、形式化与数学基础
日志是带元数据的有序序列：
$$ L = \big[(t_1, i_1, c_1),\ (t_2, i_2, c_2),\ \dots\big],\qquad i_k = k $$
共识保证「提交即一致」：若副本 $a, b$ 都对 index $k$ 提交，则
$$ \mathrm{committed}_a(k) \wedge \mathrm{committed}_b(k) \Rightarrow L_a[1..k] = L_b[1..k] $$
**日志匹配性质**可写成蕴含式：
$$ \forall a,b,k:\ \mathrm{term}_a(k) = \mathrm{term}_b(k) = \tau \Rightarrow L_a[1..k] = L_b[1..k] $$
它是「用下一条的 term 判断前一条是否一致」的依据：若两日志在 index $k$ 的 term 相同，则 index $k$ 之前完全相同。由该性质可推出**领导者完整性**：若某条日志项在某个 index 被提交，则此后每个领导者在该 index 都持有相同项。apply 函数按序应用：
$$ S_k = \delta(S_{k-1}, c_k),\qquad k = 1, 2, \dots, \mathrm{commit\_index} $$
不变式可表述为
$$ \mathrm{last\_applied} \le \mathrm{commit\_index} \le \mathrm{last\_log\_index} $$
此外，领导者选举限制（只有日志足够新的节点才能当选）保证「已提交的项不会因领导者更换而丢失」，这在形式上要求候选人持有集群中「最完整」的日志前缀。

## 四、代码实现
日志项结构与按序 apply：
```python
from dataclasses import dataclass

@dataclass
class Entry:
    term: int
    index: int
    command: bytes        # 已序列化，自包含，不含本地句柄

class StateMachine:
    def __init__(self):
        self.last_applied = 0
        self.state = {}

    def apply_committed(self, log, commit_index):
        while self.last_applied < commit_index:
            nxt = self.last_applied + 1
            entry = log[nxt]                     # 必须存在且为连续序号
            assert entry.index == nxt, "日志出现空洞或乱序"
            self.state = self.delta(self.state, entry.command)
            self.last_applied = nxt              # 先算新状态再推进游标

    def delta(self, state, command):
        cmd = decode(command)                    # 解码必须确定性
        if cmd["op"] == "SET":
            state[cmd["key"]] = cmd["value"]
        elif cmd["op"] == "DEL":
            state.pop(cmd["key"], None)
        return state
```

```python
def advance_commit_index(leader, match_indexes):
    # 统计各 index 的复制份数，取满足多数派的最大 index
    n = len(match_indexes)
    majority = n // 2 + 1
    candidates = sorted(match_indexes, reverse=True)
    for idx in candidates:
        if sum(1 for m in match_indexes if m >= idx) >= majority:
            if leader.log[idx].term == leader.current_term:   # 只提交当前任期的项
                leader.commit_index = idx
            return
```

## 六、常见误区
1. **「乱序 apply 能提升性能」**——仅在能证明可交换时成立。默认禁止乱序，因为确定性依赖顺序；跨 key 的独立更新可分区并行，但需显式论证。
2. **「客户端重试没关系」**——错。重试会造成重复命令，必须用请求 ID 去重；否则计数类操作会被重复累加。
3. **「日志项里带本地时间戳更真实」**——错。时间戳必须由领导者确定后写入命令，跟随者只读取命令中的值，否则重放会产生不同结果。
4. **「日志冲突可以智能合并」**——错。Raft 类日志是权威顺序而非多源合并：冲突时应截断跟随者的本地尾部再追加领导者的项。
5. **「日志项格式可以随意变更」**——错。日志是长期真相源，格式变更必须向后兼容（新增字段可忽略、类型不改变），否则升级与恢复时会失败。

## 八、面试题
1. **日志匹配性质是什么？** 要点：若两副本在某个 index、term 相同，则该 index 及其之前的日志项完全相同；这是判断日志是否一致的判据。
2. **提交与 apply 的区别？** 要点：提交表示多数派已持久化、不可回退；apply 表示已应用到 FSM。不变式是 last_applied ≤ commit_index。
3. **为什么领导者只能提交当前任期的项？** 要点：直接提交旧任期项可能在自身未胜选的情况下误判已提交，通过提交当前任期项可间接安全地提交之前的项。
4. **发现跟随者日志冲突如何处理？** 要点：回退寻找匹配点，从冲突点截断本地日志再追加领导者的项；不做合并。
5. **命令为什么必须自包含？** 要点：重放时不得依赖本地时间、随机数与外部状态，所有非确定输入必须在提案时写入命令体。

## 九、演进与趋势
工程实践上，日志格式正走向更明确的**版本化与向后兼容约定**（如带 schema 的序列化格式），以支撑长期存储与跨版本升级。部署形态上，共享日志（shared log）与「日志即服务」把日志抽象成独立基础设施，使多个状态机可以消费同一条日志。压缩方面，快照 + 日志截断已是标配，增量快照与基于存储引擎 checkpoint 的方案进一步降低开销。并行 apply 与可交换命令识别，则是突破串行执行瓶颈的研究与工程热点。相关格式与接口约定**以官方最新文档为准**。

## 十、小结
命令日志是 RSM 的「真相源」：共识保证它在所有副本上一致有序，确定性 apply 保证状态收敛。围绕它有一整套不可省略的工程规则——按 index 递增应用、提交与 apply 分离、只提交当前任期项、冲突即截断、命令自包含、客户端幂等去重、格式向后兼容。这些规则的共同目标是让「重放」这件事在任何时候、任何副本上都能得到完全相同的结果。
