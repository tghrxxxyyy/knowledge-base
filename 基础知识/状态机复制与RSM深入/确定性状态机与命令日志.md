# 确定性状态机与命令日志

> 对应 Ongaro & Ousterhout 2014（Raft）与 6.824 课程。

## 一、背景与挑战
把「操作」而非「结果」复制到各副本，需要一份有序、持久、一致的命令日志。挑战在于：命令必须可序列化（无歧义）、日志必须容错（不丢、不重、不乱序），且重放必须确定。

## 二、核心原理
Leader 将客户端命令追加到本地日志，通过共识复制到多数派，提交后各副本按顺序 apply。每条日志项含 (term, index, command)。apply 时严格按 index 递增，保证确定性。

## 三、形式化与数学基础
日志是一序列 \\(L = [(t_1,i_1,c_1),\dots]\\)，共识保证：若副本 \\(a,b\\) 在 index \\(k\\) 提交，则 \\(L_a[1..k]=L_b[1..k]\\)（日志匹配性质）。apply 函数 \\(\delta\\) 按 index 顺序应用 \\(c_k\\)。

## 四、代码实现
```python
def apply_committed(log, sm, commit_index):
    while sm.last_applied < commit_index:
        sm.last_applied += 1
        entry = log[sm.last_applied]
        sm.apply(entry.cmd)   # 严格按序
```

## 五、与其他技术对比
命令日志复制 vs 状态差异复制（如 rsync）：前者保证因果与确定性，后者省带宽但需比对。WAL 是单机命令日志，RSM 将其推广到多机共识。

## 六、常见误区
1. 乱序 apply 提升性能：破坏确定性，禁止。
2. 把客户端响应依赖 apply 顺序外的状态：必须按 commit 顺序。
3. 日志项含非确定性内容（如时间戳）：应在命令内显式携带。

## 七、与开源书/权威来源对应
Raft 论文「Replicated State Machine」一节；6.824 Lab2/3 实现日志复制与 apply。

## 八、面试题
问：日志匹配性质是什么？
答：若两日志在某一 index 的 term 相同，则它们该 index 之前的所有日志项完全相同。

## 九、演进与趋势
将命令日志接入确定性执行引擎（如确定性调度）实现水平扩展。

## 十、小结
命令日志是 RSM 的「真相源」，共识保证其一致，确定性 apply 保证状态收敛。
