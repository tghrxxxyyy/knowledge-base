# 幂等性定义与数学基础

> 对应 Gray 1978《Notes on Data Base Operating Systems》幂等事务与可重启操作；Kleppmann《Designing Data-Intensive Applications》第 11 章流处理与幂等 sink；HTTP 语义规范（RFC 7231）方法幂等定义。

## 一、背景与挑战

网络不可靠导致客户端超时重试，同一请求可能被投递多次。若服务端操作非幂等（如「余额减 10」），重复执行会产生错误结果。幂等设计让「执行一次」与「执行多次」效果相同，是构建可靠分布式系统的基石。挑战在于：如何为任意副作用操作定义稳定的「幂等键」，并在并发、崩溃、部分失败时仍能保持一致——这既是工程问题，也有清晰的数学结构。

工程上的难点集中在三处：其一，幂等键的生成必须稳定且全局唯一，客户端重试时要复用同一键，否则去重形同虚设；其二，「记忆」必须与业务副作用原子地绑定，否则崩溃窗口内会出现「记忆已写但业务未做」或反之；其三，并发重复请求需要原子占位（唯一约束或 CAS），仅靠「先查后写」在竞争下必然漏判。

## 二、核心原理

数学上，操作 $f$ 幂等当且仅当 $f(f(x)) = f(x)$。在分布式服务中，这意味着携带相同「幂等键」的重复请求，第二次及以后应被识别并跳过实际副作用，或重放相同结果。实现上通常把「已处理请求」的记忆外置（缓存/数据库/令牌），以稳定键索引；对读取型操作（GET）天然幂等，对写入型则需显式去重。在代数视角下，幂等操作是**状态转移幺半群中的单位元性质**：多次复合与单次复合结果相同。注意「幂等」不等于「无副作用」——它允许副作用发生一次，但不允许发生多次。

三种主流的落地形态：一是「唯一约束」型，直接让数据库主键/唯一索引承担去重，插入冲突即代表重复；二是「状态机」型，为请求定义状态（待处理/已完成），只允许从待处理推进一次，天然幂等；三是「令牌」型，服务端先向客户端发放一次性令牌，消费即作废。三者可以叠加使用，可靠性依次递增但复杂度也递增。

## 三、形式化与数学基础

设状态转移函数 $S' = apply(S, req)$，对重复请求 $req$（同键）满足：

$$
apply(apply(S, req), req) = apply(S, req)
$$

即二次应用不改变结果。等价地，该操作在状态空间上是**幂等映射**。更一般地，对键集合 $K$ 与记忆集 $seen \subseteq K$：

$$
\forall k \in K:\ apply^{(n)}_k(S) = apply_k(S),\quad n \ge 1
$$

若操作还满足交换律（如「设为某值」），则多个并发重复请求可任意交错而结果一致；若不满足（如「加 10」），则必须靠去重保证只执行一次。HTTP 语义中 GET/PUT/DELETE 被规定为幂等，POST 默认不幂等（每次可能创建新资源）。

可以把「幂等 + 可交换」的组合刻画得更精确：若操作集合 $\{apply_k\}$ 满足对任意 $k_1 \ne k_2$ 有 $apply_{k_1} \circ apply_{k_2} = apply_{k_2} \circ apply_{k_1}$，且每个 $apply_k$ 幂等，则该集合在复合下构成一个**半格**，任意到达顺序与重复次数都收敛到同一状态。这就是 CRDT 与幂等消息处理的共同代数基础。反之，若只有幂等而无交换律，则必须保证同一键的请求按序处理（如分区内单线程），否则「先加后减」与「先减后加」虽各自幂等，交叉执行仍可能产生不同结果。

## 四、代码实现

```python
# 最简幂等：用记忆集去重（示意，生产应外置持久存储）
def transfer(req_id, from_, to_, amount, seen):
    if req_id in seen:                 # 已处理
        return seen[req_id]            # 返回原结果，不再执行副作用
    result = do_transfer(from_, to_, amount)
    seen[req_id] = result              # 记忆结果
    return result
```

```python
# 生产级：唯一约束 + 同事务写业务，靠主键冲突实现原子去重
def transfer_atomic(conn, req_id, from_, to_, amount):
    with conn.transaction():
        try:
            conn.execute("INSERT INTO idem(req_id, status) VALUES(?, 'pending')",
                         (req_id,))          # 冲突则抛唯一约束异常
        except UniqueViolation:
            row = conn.execute("SELECT status, result FROM idem WHERE req_id = ?",
                               (req_id,)).fetchone()
            if row.status == 'done':
                return row.result        # 已完成，直接复述结果
            raise RetryLater()           # 仍在处理中，让调用方稍后重试
        result = do_transfer(conn, from_, to_, amount)   # 业务副作用
        conn.execute("UPDATE idem SET status='done', result=? WHERE req_id=?",
                     (result, req_id))   # 与业务同事务提交，原子生效
        return result
```

`INSERT` 唯一约束而非「先 SELECT 再 INSERT」是关键：前者由数据库保证原子性，后者在并发下两个请求可能同时通过检查，双双执行业务操作。此外，「pending」状态的引入解决了「第一次请求仍在执行时第二个请求到达」的场景——此时不能返回成功（业务未完成）也不能重复执行，只能让调用方重试。

## 五、与其他技术对比

| 维度 | 事务回滚 | 幂等 | at-least-once + 幂等 | 一次性令牌 | 状态机去重 |
|------|----------|------|----------------------|------------|------------|
| 处理对象 | 失败撤销 | 重复执行 | 重复投递 | 重复调用 | 重复调用 |
| 适用 | 失败场景 | 重试场景 | 消息队列 | 支付/下单 | 长流程 |
| 关键 | ACID | 稳定键 + 记忆 | 必须配幂等 | 令牌一次性 | 状态单向推进 |
| 并发安全性 | 由锁保证 | 依赖原子占位 | 依赖存储约束 | 高 | 高 |
| 存储成本 | 无 | 需记忆表 | 需记忆表 | 需令牌表 | 需状态表 |

at-most-once 靠不重试规避重复；at-least-once 必须配合幂等才能安全；exactly-once 在分布式中通常由「at-least-once + 幂等」实现。一次性令牌与状态机去重本质上都是「唯一约束」的变体，区别在于去重信息的组织方式与生命周期。

## 六、常见误区

1. 认为重试天然安全：非幂等操作重试会放大副作用。
2. 只在客户端去重：服务端仍需，因多客户端或不同重试路径。
3. 用请求内容而非稳定键判重：相同业务语义应有同一键，否则漏去重。
4. 混淆「幂等」与「无副作用」：幂等允许发生一次，关键是「不多于一次」。
5. 误以为 GET 永远安全幂等：带副作用的 GET（如计数）违反了语义约定，应改 POST/PUT。
6. 把「可交换」当成「幂等」：加法可交换但非幂等，必须显式去重。
7. 用「先查后写」代替原子占位：并发下两个请求可能同时通过检查，双双执行。
8. 幂等键由服务端生成：客户端重试时会拿到新键，去重完全失效；键必须由调用方生成并随重试复用。

## 七、与开源书·权威来源对应

- Gray 1978：讨论「幂等事务」与可重启（restartable）操作。
- Kleppmann《DDIA》第 11 章：强调流处理需幂等 sink 以达端到端精确一次。

## 八、面试题

1. HTTP 中哪些方法幂等？答：GET、PUT、DELETE 语义上幂等；POST 默认不幂等。
2. 如何给非幂等操作加幂等？答：引入稳定幂等键 + 持久记忆（唯一约束/原子占位），重复请求跳过副作用。
3. exactly-once 真能实现吗？答：分布式中通常由 at-least-once 投递 + 幂等消费近似实现，非物理精确一次。
4. 幂等与可交换有何区别？答：幂等是「重复执行等价单次」，可交换是「顺序无关」；「加 10」可交换但非幂等。
5. 幂等记忆应放哪？答：放跨进程持久存储（DB/Redis），不能仅存进程内存，否则重启/扩副本失效。
6. 为什么必须用唯一约束而非「先查后写」？答：查询与写入之间存在竞争窗口，只有数据库层的原子约束才能保证并发下仅一次成功。
7. 幂等键该由谁生成？答：由调用方生成并随重试复用；服务端生成会让每次重试得到新键，去重失效。

## 九、演进与趋势

云厂商把「幂等键」作为 API 标准字段（支付、订单创建等），框架层自动去重；结合事务消息与 WAL 把幂等记录与业务写绑定，减少手写分支。具体以官方最新文档为准。

另一条演进线是把幂等能力上升为平台原语：请求网关统一分配并校验幂等键，业务代码无须感知；存储层提供「条件写（compare-and-set）」为上层提供原子去重基础。趋势是让开发者「默认获得幂等」，而不必在每个接口重复实现同一套模式。

## 十、小结

幂等是「重试安全」的数学保证，靠稳定键加状态记忆实现。它把不可靠网络下的重复投递转化为可接受的「重复但等价」结果，是可靠系统的第一性原理之一。

落地三要素：键由调用方生成且重试复用（键要稳）、记忆与副作用同事务（原子性）、并发去重靠唯一约束而非查询（无竞争窗口）。三者齐备，幂等才真正成立。
