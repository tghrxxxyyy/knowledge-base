# 幂等与分布式事务

> 对应 Gray 1978《Notes on Data Base Operating Systems》幂等事务；Kleppmann《Designing Data-Intensive Applications》第 9、12 章分布式事务与共识；Hector Garcia-Molina 等《Database Systems: The Complete Book》Saga 章节。

## 一、背景与挑战

两阶段提交（2PC）等分布式事务保证原子性，但协调者故障会阻塞；Saga 等补偿式事务用「反向操作」回滚。幂等在二者中都很关键：重试子事务、重放日志、崩溃恢复都要求子操作可安全重复。否则一次重试就可能重复扣款或重复补偿，把「恢复」变成「二次破坏」。挑战在于：如何让每一笔子操作和它的补偿都天然幂等。

## 二、核心原理

在 Saga 中，每个本地事务与其补偿事务都应幂等，这样故障恢复重放时不会重复扣款或重复补偿。2PC 的 `prepare`/`commit` 若需重试，也依赖参与者对重复 `commit` 的幂等响应（即「已提交则直接回 ACK」）。实现上，每个子步骤用「事务 ID + 步骤 ID」作为幂等键，执行前先查是否已 done；补偿同理用「是否已 compensated」判重。TCC（Try-Confirm-Cancel）把三阶段显式化：Try 预留资源，Confirm/Cancel 必须幂等，使重试安全。

## 三、形式化与数学基础

补偿应满足幂等且语义回滚：

$$
comp(comp(S)) = comp(S),\quad comp(apply(S, T)) = S
$$

即补偿自身幂等，且对已完成事务的补偿回到原状态。重试算子 $R$（重放某步）满足：

$$
R(R(x)) = R(x)
$$

2PC 中参与者对重复 `commit` 的请求：

$$
commit(k):\ \text{if } state(k) = COMMITTED \to return\ ACK\ \text{else}\ commit
$$

保证协调者重试不会双提交。

## 四、代码实现

```python
# Saga 步骤与补偿均幂等（示意）
def saga_step(tx_id, op):
    if done(tx_id, op):
        return result_of(tx_id, op)     # 幂等：已执行直接返回
    r = execute(op)
    mark_done(tx_id, op, r)             # 记录完成
    return r

def compensate(tx_id, op):
    if compensated(tx_id, op):
        return                         # 幂等：已补偿直接返回
    undo(op)
    mark_compensated(tx_id, op)
```

```python
# 2PC 参与者对重复 commit 的幂等响应
def on_commit(txn_id):
    if log.contains(txn_id, COMMITTED):
        return ACK                     # 已提交，直接确认
    apply_commit(txn_id)
```

## 五、与其他技术对比

| 维度 | 2PC | Saga | TCC |
|------|-----|------|-----|
| 一致性 | 强（阻塞） | 最终一致 | 最终一致 |
| 可用性 | 低（协调者阻塞） | 高 | 高 |
| 幂等需求 | commit 重试幂等 | 补偿幂等 | Confirm/Cancel 幂等 |

幂等是这三种方案下重试安全的共同前提。

## 六、常见误区

1. 认为 Saga 自动安全：补偿非幂等会导致重复反向操作（如重复退款）。
2. 2PC 协调者重试 commit 不考虑幂等：参与者需容忍重复 commit，否则双提交。
3. 把「发消息」当可回滚：应转「可取消或可确认」的 TCC 模式，或事务消息。
4. 忽略子步骤幂等键：没有稳定键就无法判「已执行」，重试必重复副作用。
5. 以为补偿总能精确回滚：跨服务补偿可能部分失败，需重试与对账兜底。

## 八、面试题

1. 为何 Saga 补偿必须幂等？答：故障恢复会重放补偿，非幂等补偿会重复撤销造成状态错误（如重复退款）。
2. 2PC 中重复 commit 如何处理？答：参与者记录已提交日志，重复 commit 直接回 ACK，避免双提交。
3. TCC 与 Saga 的幂等差异？答：TCC 把 Confirm/Cancel 显式设计为幂等三阶段，Saga 则靠补偿幂等+重试。

## 九、演进与趋势

TCC 把幂等内置于三阶段，配合事务消息落地；基于日志/事件溯源（event sourcing）的模型让每步天然可追溯与幂等重放；服务网格层提供事务上下文传播。具体以官方最新文档为准。

## 十、小结

无论 2PC、Saga 还是 TCC，子操作与补偿的幂等是故障重试安全的前提。它把「分布式事务的脆弱性」关进「重复无害」的笼子里，是构建可靠跨服务流程的底层保障。
