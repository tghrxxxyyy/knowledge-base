# 消息队列去重与 at-least-once

> 对应 Kleppmann《Designing Data-Intensive Applications》第 11 章流处理；Kafka 官方文档 idempotent producer 与 transactions（EOS）；Apache Flink 检查点与两阶段提交。

## 一、背景与挑战

Kafka 等系统默认提供 at-least-once 投递：消息可能因生产者重试、broker 故障、消费者重平衡后重放而**重复**。消费者若做「非幂等副作用」（写库、发钱、调下游），重复消费即灾难。必须在消费端配合幂等，或借助生产者/事务机制从源头抑制重复。核心难点是：重复可能发生在生产端（同条消息写两遍）、传输端（重试）、消费端（offset 提交滞后被重放），每一处都要有应对。可见去重是端到端问题，而非单点能解决。

另一个必须正视的事实是：at-most-once（可能丢）与 exactly-once（协议层的强保证）在纯网络语义下都难以独立达成。业界所称的「精确一次」本质上是「至少一次投递 + 幂等处理」的组合，是语义层面的等价，而非物理层面的「只传一次」。承认这一点，才能正确选择在链路的哪一段投入去重成本。

## 二、核心原理

两条去重路径：① **生产者端幂等**——Kafka 的 `enable.idempotence` 给每个 producer 分配 PID，消息带单调递增序列号，broker 维护每分区 `last_seq`，仅接受 `seq = last_seq+1`，丢弃重复，从而保证**分区内无重复**（但跨分区仍可能重排）；② **消费者端幂等**——用「处理位移 + 业务幂等键」确保同一消息多次消费效果一致。常用「消费位移与业务写在同一事务」实现精确一次（EOS）：消费到消息→在事务内写业务+提交 offset→事务提交，崩溃恢复时要么都生效要么都回滚。Kafka 的 EOS 还引入 `transactional.id` 与事务协调器，跨分区原子提交，使「消费-转换-生产」成一体。

生产者幂等的边界需要说清：`PID + seq` 只覆盖「同一 producer 会话内的同一分区」，因此 producer 重启会获得新 PID，跨会话的重试仍可能重复；同时序列号是分区维度而非主题维度，故跨分区无去重能力。消费者侧的幂等键选取也有讲究：必须选「业务上真正唯一」的标识（如订单号、请求 ID），而不是消息 offset 或时间戳——后者在重平衡或重放后都不稳定。

## 三、形式化与数学基础

生产者序列号约束（分区内有序且无重）：

$$
\forall m:\ seq(m) = last\_seq_{partition} + 1 \Rightarrow accept;\quad seq(m) \le last\_seq \Rightarrow drop
$$

消费者侧幂等：设消息 $m$ 有业务键 $k(m)$，处理映射 $h$，重复消费需满足：

$$
h(h(state, m), m) = h(state, m)
$$

即重复应用同一消息不改变状态——这正是流处理中「幂等 sink」的数学要求。端到端精确一次 = at-least-once 投递 + 幂等 sink + 事务性位移提交。

用「有向无环幂等」可以更准确地刻画组合场景：若处理函数 $h$ 幂等且满足交换律（对无依赖消息 $m_1, m_2$ 有 $h(h(s,m_1),m_2) = h(h(s,m_2),m_1)$），则乱序重放也安全；若只有幂等而无交换律（如消息带状态增量），则必须依赖分区内有序投递，否则顺序颠倒会使结果错误。这解释了为什么「幂等键 + 分区有序」是常见组合：分区保序解决顺序问题，幂等键解决重复问题，两者互补。此外，事务性位移提交的原子性可用「两阶段提交」表述：准备阶段写业务并预提交 offset，提交阶段由协调器统一决策，从而在崩溃点前后保持「业务写与位移」同生共死。

## 四、代码实现

```python
# Kafka 消费者：用幂等键去重（示意）
def on_message(msg):
    if msg.key in processed_cache:
        return                        # 已处理，跳过副作用
    with db.transaction():
        db.write(business(msg))       # 业务副作用
        db.mark_offset(msg.topic_partition, msg.offset)  # 同事务提交位移
    processed_cache.add(msg.key)      # 事务提交成功后再更新缓存
```

```python
# 生产者开启幂等（配置示意，非代码逻辑）
# props: enable.idempotence=true, acks=all, retries>0
# broker 依 PID+seq 去重，分区内保证无重复
# 跨分区精确一次需开启事务：transactional.id + 事务协调器
# 注意：producer 重启会更换 PID，跨会话重试仍可能重复，须配合业务幂等键
```

两处细节决定成败：`processed_cache.add` 必须放在事务提交之后，若在事务内更新而事务回滚，缓存会「记住」一次并未生效的处理，导致真正的消息被跳过；`business(msg)` 本身也必须可重入——即同一事务内的重复执行不应产生叠加副作用，否则事务重试时仍会出错。

## 五、与其他技术对比

| 维度 | at-most-once | at-least-once | at-least-once + 幂等 | 事务 EOS |
|------|--------------|---------------|----------------------|----------|
| 可能丢 | 是 | 否 | 否 | 否 |
| 可能重 | 否 | 是 | 实际无副作用重复 | 无 |
| 实现成本 | 最低 | 低 | 中（需幂等） | 高（事务） |
| 额外延迟 | 无 | 无 | 需幂等存储查询 | 事务协调 RTT |
| 典型场景 | 指标采集 | 日志收集 | 订单/支付写入 | 流式 ETL |

at-least-once + 幂等 == 实际精确一次；Kafka 事务性 EOS 把位移与写绑定到同一事务。at-most-once 适合「丢了也无所谓」的监控类数据；at-least-once + 幂等是绝大多数业务系统的性价比最优解；事务 EOS 用于对跨分区原子性有硬要求的流水线。

## 六、常见误区

1. 认为 at-least-once 不会重复：正因可能重复才需幂等。
2. 消费位移提交与业务写不在同一事务：可能重复（先提交 offset 后崩溃）或丢失（先写后崩溃未提交）。
3. 用消息 offset 当业务幂等键：重平衡后 offset 语义不稳，且同键不同内容会错位。
4. 以为生产者幂等能跨分区：PID+seq 仅保证单分区内无重，跨分区顺序/去重需额外机制。
5. 把「处理成功」与「offset 提交」割裂：二者不一致是重复/丢失的根源。
6. 以为开启 EOS 就零成本：事务协调器引入额外 RTT 与延迟，吞吐下降。
7. 幂等键选得过粗或过细：过粗会误判「不同业务请求」为重复而丢消息，过细则无法拦截真正的重复。
8. 认为业务写幂等就够了：若下游调用（如发短信、调第三方支付）不幂等，重复消费仍会造成外部可见的副作用。

## 八、面试题

1. at-least-once 如何实现精确一次？答：配合幂等消费（或事务性位移+写），使重复处理无副作用。
2. Kafka 生产者幂等原理？答：PID + 单调序列号，broker 丢弃 `seq<=last_seq` 的重复，保证分区内无重。
3. 位移与业务写为何要同事务？答：否则二者任一步崩溃都会造成重复消费或消息丢失。
4. EOS 的代价？答：事务协调器增加延迟与复杂度，吞吐低于非事务生产，需按业务权衡。
5. 为什么消息 offset 不能当幂等键？答：重平衡或重放后同一条业务消息可能换 offset，且 offset 不表达业务唯一性。
6. 幂等与「可交换」如何配合？答：幂等解决重复，交换律解决乱序；无交换律时须靠分区内有序投递保序。

## 九、演进与趋势

Flink 等引擎内建 exactly-once checkpoint 与两阶段提交 sink；Kafka 事务 API 让「消费-处理-生产」成原子。具体能力以官方最新文档为准。

同时，越来越多元系统把幂等能力下沉到存储层：如分布式数据库的「唯一约束 + upsert」直接承担去重职责，使上层消费者无需自建幂等表；流处理引擎则通过「状态 + 检查点」在框架内保证算子幂等。趋势是把重复治理从「每个应用各写一遍」变为「平台统一提供」。

## 十、小结

队列层的重复是常态，消费端幂等加事务位移是精确一次的关键。它把「消息可能来两遍」这一事实，转化为「来两遍也无妨」的工程性质。

落地清单三条：选业务唯一键作幂等键（不用 offset）、把位移提交与业务写放进同一事务、缓存更新必须在事务提交之后。做到这三点，at-least-once 即可在业务语义上等价于精确一次。
