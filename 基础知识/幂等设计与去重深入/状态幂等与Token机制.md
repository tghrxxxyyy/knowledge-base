# 状态幂等与Token机制

> 对应常见支付或订单系统设计与 DDIA 第11章。

## 一、背景与挑战
无状态服务也可做幂等，但需把「已处理状态」外置。Token（一次性令牌）机制让客户端先领令牌、再携令牌下单，服务端校验令牌消费一次即失效，天然防重。挑战是令牌的发放、校验、过期与并发消费。

## 二、核心原理
客户端请求令牌（如 `POST /token` 返回 UUID），下单时带令牌。服务端以令牌为唯一键原子消费（CAS），成功后作废。未消费令牌可过期回收。状态机记录「订单状态」，重复支付请求在「已支付」态直接返回。

## 三、形式化与数学基础
令牌消费是原子操作 \\(consume(t): \text{if } state(t)=\text{FREE} \to state(t)=\text{USED}; \text{return OK else FAIL}\\)。等价于 test-and-set，保证令牌至多生效一次。

## 四、代码实现
```python
def pay(token, order):
    if not redis.set(token, "USED", nx=True, ex=600):
        return get_order(order)   # 已用，幂等返回
    do_pay(order)
    return order
```

## 五、与其他技术对比
幂等键由客户端生成（易碰撞需规范），令牌由服务端发放（可控、可过期）；二者可结合：令牌即服务端托管的幂等键。

## 六、常见误区
1. 令牌不过期：被截获后可长期重放（应设短 TTL）。
2. 令牌与订单未绑定：可能被用于其他订单。
3. 多实例下令牌存储非原子：需用共享原子存储。

## 七、与开源书/权威来源对应
DDIA 第11章讲幂等与状态；主流支付网关（Stripe或PayPal）采用 Token 防重。

## 八、面试题
问：一次性令牌如何防重放？
答：服务端原子消费令牌，消费一次即作废，重复用同一令牌直接拒绝或返回原结果。

## 九、演进与趋势
把令牌写入 WAL 或 DB 与业务操作同事务，强化持久幂等。

## 十、小结
Token 机制是服务端托管的幂等键，发放-消费-过期三段式保证安全去重。
