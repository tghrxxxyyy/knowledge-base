# 状态幂等与 Token 机制

> 对应 Kleppmann《Designing Data-Intensive Applications》第 11 章幂等与状态；主流支付网关（Stripe / PayPal）的一次性令牌（token）防重设计；Gray 1978 可重启操作。

## 一、背景与挑战

无状态服务也可做幂等，但需把「已处理状态」外置。Token（一次性令牌）机制让客户端先领令牌、再携令牌下单，服务端校验令牌「消费一次即失效」，天然防重。难点在于：令牌的发放、校验、过期与并发消费都必须原子，否则可被重放或重复消费；且令牌应与具体订单绑定，避免被挪作他用。此外还要考虑令牌泄露后的吊销与刷新策略。

令牌机制的另一层价值是「责任划分」：幂等键由客户端生成时，服务端无法判断键是否被恶意复用；而令牌由服务端签发，服务端掌握其生命周期，因此可以把「防重放」从「信任客户端的约定」升级为「由服务端强制的约束」。这种控制权的转移，是令牌相比普通幂等键的本质优势。

## 二、核心原理

客户端先请求令牌（如 `POST /token` 返回 UUID），下单时带上令牌。服务端以令牌为唯一键做**原子消费（CAS）**：成功则将令牌置为 `USED` 并执行业务；失败（已被用）则返回原订单或拒绝。未消费令牌可过期回收。订单侧再用状态机记录「待支付/已支付/已取消」，重复支付请求在「已支付」态直接返回，双重保证。这样即便客户端重放同一令牌，也只会生效一次。令牌还可分级：短期支付令牌、长期刷新令牌，前者泄露窗口小，后者用于换发前者。

两层防护的分工值得强调：令牌层解决「同一请求被提交多次」（重放与重试），状态机层解决「令牌不同但业务上重复」（例如用户刷新页面拿到新令牌却再次点击支付）。只做令牌而不做状态机检查，会漏掉后一种；只做状态机而不做令牌，则在「首次请求处理中、第二次请求到达」时会重复扣款。两者叠加才覆盖完整的重复场景。

## 三、形式化与数学基础

令牌消费是原子操作，等价于 test-and-set：

$$
consume(t):\ \text{if } state(t) = FREE \to state(t) := USED;\ return\ OK\ \text{else}\ FAIL
$$

该操作保证令牌**至多生效一次**。结合订单状态机 $S \in \{INIT, PAID, CANCEL\}$，重复请求满足：

$$
pay(t, o):\ \text{if } S(o)=PAID \to return\ existing;\ \text{else if } consume(t)=OK \to do\_pay(o)
$$

即无论重试多少次，结果集合一致。

可以证明该组合满足「至多一次副作用」：设 $n$ 次重复请求中，命中的令牌消费成功次数为 $c$。由 CAS 的原子性，同一 $t$ 的 $c \le 1$；即使客户端使用多个不同令牌 $t_1..t_m$，状态机检查 $S(o) = PAID$ 也会在首次成功后拦截其余请求，故总副作用次数 $\le 1$。这两条性质在逻辑上互补，任一条单独都不足以保证「至多一次」。此外，令牌的 TTL 引入了一个隐含前提：业务处理必须在 TTL 内完成，否则令牌已过期而业务仍在执行，此时若客户端重试会拿到新令牌并再次触发业务——因此 TTL 必须显著大于业务处理时间的上界。

## 四、代码实现

```python
# 一次性令牌：原子消费即作废（示意）
def pay(token, order):
    if not redis.set(token, "USED", nx=True, ex=600):
        return get_order(order)        # 已用，幂等返回原结果
    if order_state(order) == "PAID":
        return get_order(order)        # 订单已支付，直接返回
    do_pay(order)                      # 真正扣款
    return order
```

```python
# 令牌应与订单绑定，防止跨订单重放
def pay_bound(token, order, uid):
    key = f"{token}:{order}:{uid}"     # 复合键，杜绝挪作他用
    if not redis.set(key, "USED", nx=True, ex=600):
        return get_order(order)
    do_pay(order)
```

```python
# 生产级改进：令牌消费与业务写在同一事务，避免「已消费但未扣款」
def pay_durable(conn, token, order, uid):
    with conn.transaction():
        row = conn.execute(
            "UPDATE tokens SET state='USED' WHERE token=? AND state='FREE'",
            (token,)).rowcount
        if row == 0:                      # 未占用成功：令牌已用或不存在
            return get_order(conn, order)
        if order_state(conn, order) == "PAID":
            return get_order(conn, order)
        do_pay(conn, order)               # 与令牌状态同事务提交，原子生效
        return get_order(conn, order)
```

`redis.set(..., nx=True)` 的 `nx`（not-exists）与 SQL 中的 `WHERE state='FREE'` 是同一语义的两种表达：都要求「检查与置位」不可分割。若换成 `if not exists(tok): set(tok)`，两个并发请求可能同时通过 exists 检查，导致双花——这正是「必须原子 CAS」的直观反例。

## 五、与其他技术对比

| 维度 | 幂等键（客户端生成） | 令牌（服务端发放） | 唯一约束 | 状态机去重 |
|------|----------------------|--------------------|----------|------------|
| 键来源 | 客户端，易碰撞需规范 | 服务端，可控可过期 | 数据库 | 服务端 |
| 防重放 | 依赖键稳定 | 消费即废，强防重放 | 仅防重复插入 | 依状态判定 |
| 复杂度 | 中 | 中（多一次领令牌） | 低 | 中 |
| 额外 RTT | 无 | 需先领令牌 | 无 | 无 |
| 抗恶意复用 | 弱 | 强（绑定+吊销） | 弱 | 中 |

二者可结合：令牌即服务端托管的幂等键。若系统无法承受「先领令牌」的额外往返，可直接使用客户端幂等键并配合唯一约束；若安全要求高（支付、资金类），令牌的绑定与吊销能力则是不可替代的。

## 六、常见误区

1. 令牌不过期：被截获后可长期重放，应设短 TTL（如数分钟）。
2. 令牌与订单未绑定：可能被用于其他订单，需复合键约束。
3. 多实例下令牌存储非原子：需用共享原子存储（Redis/DB），不能只存本地内存。
4. 以为令牌发放后即可用：需校验令牌状态与归属，防止伪造/越权。
5. 忽略并发消费竞态：必须原子 CAS，否则双花。
6. 把刷新令牌当支付令牌用：刷新令牌应只用于换发短期令牌，不应直接用于业务防重。
7. TTL 短于业务处理时间（令牌过期而业务仍在执行，客户端重试会拿到新令牌并重复触发业务）；令牌消费与业务写若不在同一事务，还会出现「令牌已消费但扣款失败」的死结，用户既扣不了款也用不了令牌。

## 七、与开源书·权威来源对应

- Kleppmann《DDIA》第 11 章：幂等与状态、端到端去重。
- Stripe / PayPal 文档：以一次性 token 防重复扣款与重放。
- Gray 1978：可重启操作与幂等事务的早期论述。
- RFC 6749：OAuth 2.0 中授权码与令牌的一次性使用语义，是同类机制在协议层的体现。

## 八、面试题

1. 一次性令牌如何防重放？答：服务端原子消费令牌，消费一次即作废，重复用同一令牌直接拒绝或返回原结果。
2. 为何令牌要与订单绑定？答：防止令牌被挪到别的订单重放，复合键限定作用域。
3. 令牌过期长短如何取舍？答：太短用户体验差（来不及支付），太长重放窗口大；按业务风险设短 TTL 并配合状态机。
4. 令牌泄露如何处置？答：提供吊销接口使其立即失效，并依靠短 TTL 与订单绑定缩小影响面。
5. 为什么令牌消费与业务必须同事务？答：否则会出现「令牌已消费但业务未执行」的中间态，此时重试被拒、业务永远无法完成。
6. 令牌与幂等键的关系？答：令牌是服务端托管的幂等键，额外提供绑定、过期与吊销能力，控制权从客户端转移到服务端。

## 九、演进与趋势

把令牌写入 WAL 或 DB 与业务操作同事务，强化持久幂等；前端通过一次性表单 token 防重复提交，后端通过 opaque token 防 API 重放，二者在网关层统一。另一条趋势是「无感令牌」：由网关或服务网格自动为每个请求注入并校验幂等标识，业务代码完全无须改动，把幂等从「每个接口都要记得实现」变为「平台默认提供」。具体以官方最新文档为准。

## 十、小结

Token 机制是服务端托管的幂等键，发放-消费-过期三段式保证安全去重。它把「防重放」从约定升级为原子操作，是支付等高可靠系统的标准实践。三条实现要点：消费必须原子（CAS 而非先查后写）、令牌必须绑定作用域（复合键防止跨订单复用）、令牌状态与业务写必须同事务（避免中间态卡死）；三者齐备，令牌机制才能在并发与崩溃下都成立。
