# 数据库唯一约束与去重

> 对应 Gray 1978 与 DDIA 第7章（事务与约束）。

## 一、背景与挑战
在数据库层做去重最可靠：利用唯一索引让重复插入失败，从而保证「同一业务实体只创建一次」。难点是冲突处理与跨表一致性，以及高并发下的死锁或重试。

## 二、核心原理
为业务唯一键（如订单号）建 UNIQUE 索引。首次插入成功即「占有」该键；重复插入触发唯一冲突（如 SQL 23505、MySQL 1062），应用捕获后转为「返回已有记录」而非报错。

## 三、形式化与数学基础
唯一约束是关系代数上的函数依赖：键 \\(k\\) 决定唯一元组。并发插入 \\(k\\) 时，数据库用锁或 MVCC 保证至多一行提交，其余回滚，形成天然的 test-and-set。

## 四、代码实现
```python
try:
    cur.execute("INSERT INTO orders(id, payload) VALUES (%s,%s)", (order_id, p))
except UniqueViolation:
    cur.execute("SELECT * FROM orders WHERE id=%s", (order_id,))
    return cur.fetchone()   # 幂等返回已有
```

## 五、与其他技术对比
应用层去重依赖缓存一致性，可能漏；DB 唯一约束是持久化强保证。但 DB 约束无法跨库去重，需结合分布式锁。

## 六、常见误区
1. 先 SELECT 再 INSERT 判重：竞态下仍可能重复，须靠约束。
2. 捕获异常后不补偿：应返回已有结果以达幂等。
3. 长事务持唯一锁：易死锁，应短事务。

## 七、与开源书/权威来源对应
Gray 1978 讨论约束与并发；DDIA 第7章讲弱隔离下的异常与约束。

## 八、面试题
问：先查后插为何不保证唯一？
答：两步间有竞态窗口，并发可同时通过查询后插入，必须靠唯一约束兜底。

## 九、演进与趋势
分布式数据库用全局索引或分片键实现跨节点唯一，配合 2PC 或 calcite 层校验。

## 十、小结
唯一约束是数据库层幂等去重的基石，应用需正确捕获冲突并补偿。
