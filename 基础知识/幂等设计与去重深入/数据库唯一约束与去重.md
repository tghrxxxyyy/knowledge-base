# 数据库唯一约束与去重

> 对应 Gray 1978《Notes on Data Base Operating Systems》；Kleppmann《Designing Data-Intensive Applications》第 7 章弱隔离与约束；SQL 标准 UNIQUE 约束语义。

## 一、背景与挑战

在数据库层做去重最可靠：利用唯一索引让重复插入失败，从而保证「同一业务实体只创建一次」。难点在于：冲突要被正确捕获并转为「返回已有记录」而非报错；高并发下可能有死锁或重试风暴；且单库唯一约束无法跨库/跨分片去重。它适合「创建类」幂等（如按订单号创建），但不适合「累加类」操作（扣款需配合条件更新）。理解约束的底层加锁/MVCC 行为，才能写出既正确又高性能的去重逻辑。

另一个关键区分是「去重」与「互斥」的目标不同：去重只要求同一键最终只有一行，允许插入失败的调用方自行重试；互斥则要求同一时刻仅一个持有者，通常需要锁或条件更新。用唯一约束实现去重是顺手的，用它实现互斥则容易出现「插入失败即视为未获得锁」的误用。明确目标后，才能选对原语。

## 二、核心原理

为业务唯一键（如订单号、用户邮箱）建 UNIQUE 索引。首次插入成功即「占有」该键；重复插入触发唯一冲突（PostgreSQL 23505、MySQL 1062、SQL Server 2601 等），应用捕获后转为「返回已有记录」而非抛错。底层实现依赖索引上的行锁或 MVCC：并发插入同一键时，数据库保证**至多一行**提交，其余回滚，形成天然的 test-and-set。注意这与「先 SELECT 再 INSERT」不同——后者两步间有竞态窗口。对于「存在则更新」语义，可用 `INSERT ... ON CONFLICT DO UPDATE`（UPSERT），把判重与写入原子化。

底层机制值得展开：在 B+ 树索引上，插入同一键的两个事务会在索引页上产生冲突，一个获得锁并写入，另一个等待或回滚（取决于隔离级别与配置）。在 MVCC 实现（如 PostgreSQL）中，唯一性检查会检查「已提交版本」与「同时未提交但已占用该键的事务」，因此即使在可重复读隔离级别下也能正确拒绝并发重复插入。这也带来一个副作用：并发冲突会短暂阻塞，在高冲突场景下形成串行化点，需要考虑分区或预分配来分散热点。

## 三、形式化与数学基础

唯一约束对应关系代数上的函数依赖：键 $k$ 决定唯一元组。并发插入 $k$ 时，数据库用锁或 MVCC 保证至多一行提交：

$$
\forall t_1 \neq t_2:\ insert(k, t_1) \land insert(k, t_2) \Rightarrow \text{恰好一个 commit}
$$

形式化为原子谓词：

$$
insert\text{-}if\text{-}absent(k):\ \bigl(\nexists row(k)\bigr) \xrightarrow{atomic} \bigl(insert(k)\bigr)
$$

这正是数据库层的 test-and-set，隔离级别需至少达到防止丢失更新的级别（如 REPEATABLE READ / SERIALIZABLE 或显式兜底唯一索引）。

从并发控制理论看，唯一约束的作用是排除一类特定的写偏斜（write skew）：它使得「两个事务各自检查后都写入」这一非法历史不再可能被提交。这与串行化隔离所保证的「历史等价于某串行执行」是同一目标，但唯一约束只针对键唯一性这一条谓词「局部地」实现，代价远低于全库串行化。代价的代价是：它只覆盖单库单索引的键，跨表、跨分片的唯一性无法由它承担。

## 四、代码实现

```python
# 捕获唯一冲突，幂等返回已有记录（示意）
try:
    cur.execute(
        "INSERT INTO orders(id, payload) VALUES (%s, %s)",
        (order_id, p),
    )
    conn.commit()
    return fetch_new(order_id)
except UniqueViolation:               # 23505 / 1062 等
    conn.rollback()                   # 必须先回滚，否则事务处于失败状态
    cur.execute("SELECT * FROM orders WHERE id=%s", (order_id,))
    return cur.fetchone()             # 幂等：返回已存在的记录
```

```sql
-- 更稳妥：INSERT ... ON CONFLICT DO NOTHING / UPDATE（PostgreSQL）
INSERT INTO orders(id, payload) VALUES (%s, %s)
ON CONFLICT (id) DO NOTHING;

-- 若需「存在则更新」：只更新业务允许变更的列，避免覆盖并发合法写
INSERT INTO orders(id, payload) VALUES (%s, %s)
ON CONFLICT (id) DO UPDATE SET payload = EXCLUDED.payload
WHERE orders.state = 'INIT';          -- 条件更新：已推进的订单不被回退
```

第二段 SQL 中的 `WHERE` 是避免「UPSERT 覆盖并发合法变更」的关键：若无条件 `DO UPDATE`，一个迟到的重试可能把已支付订单的 payload 覆盖回初始值，造成数据回退。加上状态条件后，UPSERT 只在其允许的状态下生效，兼顾原子性与安全性。

## 五、与其他技术对比

| 维度 | 应用层去重 | DB 唯一约束 | 分布式锁 | 全局索引/分片键 |
|------|-----------|--------------|----------|-----------------|
| 可靠性 | 依赖缓存一致性，可能漏 | 持久化强保证 | 中（依赖锁服务） | 高 |
| 作用范围 | 单进程/缓存 | 单库 | 跨节点 | 跨库 |
| 成本 | 低 | 低（索引） | 中 | 高（索引与协调） |
| 并发表现 | 快但不准 | 冲突时串行化 | 有锁超时风险 | 带宽与延迟上升 |

DB 约束无法跨库去重，需结合分片键或全局索引。选择原则是：单库内优先用唯一约束（最简单最可靠）；跨库时若业务允许「最终去重」，可先本地插入再异步合并；若必须强唯一，则需要全局索引或预先分配全局 ID 的策略。

## 六、常见误区

1. 先 SELECT 再 INSERT 判重：竞态下仍可能同时通过查询后插入，必须靠约束。
2. 捕获异常后不补偿：应返回已有结果以达幂等，否则调用方看到错误。
3. 长事务持唯一锁：易死锁，应短事务并快速提交。
4. 以为唯一约束能防所有重复：仅防同一索引键，跨索引/跨表仍需额外机制。
5. 在 nullable 列上建唯一索引：NULL 不视为相等，多个 NULL 都可插入，需 NOT NULL。
6. 滥用 UPSERT 无条件更新：可能覆盖并发写入的合法变更，应只更新特定列。
7. 捕获冲突后忘记显式回滚：在多数数据库中事务会进入失败态，后续语句全部报错。
8. 用复合索引顺序不当：唯一约束在 $(a, b)$ 上只保证「两列组合唯一」，若要 `a` 单独唯一须另建索引。

## 八、面试题

1. 先查后插为何不保证唯一？答：两步间有竞态窗口，并发可同时通过查询后插入，必须靠唯一约束兜底。
2. 唯一冲突该如何处理才幂等？答：捕获后回滚并返回已有记录，而非抛错给调用方。
3. 唯一约束与分布式 ID 如何配合？答：用全局唯一业务 ID 作约束键，是本库内去重的最简可靠方式。
4. UPSERT 与捕获冲突孰优？答：UPSERT 把判重与写入原子化、代码更简洁，但需谨慎避免覆盖合法更新。
5. NULL 值为何会破坏唯一性？答：SQL 中 NULL 与 NULL 不相等，故多个 NULL 被视为互不冲突，可重复插入。
6. 唯一约束的实现依赖什么？答：索引上的行锁或 MVCC 唯一性检查，数据库据此保证并发插入中至多一行提交。

## 九、演进与趋势

分布式数据库用全局索引或分片键实现跨节点唯一，配合 2PC 或校准层校验；也出现把唯一约束与业务逻辑合并为「UPSERT / MERGE」原语，减少应用层分支。具体以官方最新文档为准。

另一条趋势是把唯一性检查下沉到存储引擎的批量接口：一次提交多行时，引擎在批内与批间统一判重，避免应用层逐行异常处理的性能损耗。这类优化对高吞吐导入场景（日志、事件、指标）尤其重要，因为它把「异常驱动的控制流」换成「批量结果反馈」。

## 十、小结

唯一约束是数据库层幂等去重的基石，应用需正确捕获冲突并补偿返回。它把 test-and-set 下沉到存储引擎，提供了最强的单库持久保证。

三条实践要点：用约束而非查询判重（消除竞态窗口）、冲突后回滚并返回已有记录（保证幂等语义）、跨库唯一须另设机制（约束的作用域仅限单库单索引）。
