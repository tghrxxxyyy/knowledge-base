# 幂等键设计与实现

> 对应 DDIA 第11章与常见支付或订单系统实践。

## 一、背景与挑战
幂等键（idempotency key）是去重的核心。键设计不当会导致「本应不同的请求被误合并」或「本应合并的被分开」。需兼顾全局唯一、语义稳定、可过期。

## 二、核心原理
客户端生成 UUID 或业务单号作为幂等键，随请求传入；服务端以键为索引记录「已处理结果」。复杂度在于：并发同键请求需串行化（如用分布式锁或唯一约束），且记录需有 TTL 防止无限增长。

## 三、形式化与数学基础
设键空间 \\(K\\)，映射 \\(R: K\to Result\\)。正确性要求：对任意 \\(k\in K\\)，首次写 \\(R(k)\\) 后，所有后续同 \\(k\\) 读返回同一值。并发写需满足原子 test-and-set。

## 四、代码实现
```python
import uuid, redis
r = redis.Redis()

def handle(req_id, payload):
    # 原子占位
    if not r.set(req_id, "PROCESSING", nx=True, ex=3600):
        return r.get(req_id)   # 已有结果或在处理
    try:
        res = do_work(payload)
        r.set(req_id, res, ex=3600)
        return res
    except Exception:
        r.delete(req_id)
        raise
```

## 五、与其他技术对比
前端去重仅靠客户端，不可靠；服务端唯一约束提供强保证但仅限 DB；Redis 原子键适合跨服务。Kafka 的 producer id 加序列号提供「精确一次」语义另辟蹊径。

## 六、常见误区
1. 用时间戳当键：并发同毫秒会冲突或遗漏。
2. 键永久不失效：存储膨胀。
3. 处理中状态未清理：异常导致永久卡死。

## 七、与开源书/权威来源对应
DDIA 第11章讲幂等消费者；Stripe 等公开文档以幂等键为 API 标准。

## 八、面试题
问：并发同幂等键如何处理？
答：用分布式锁或原子占位（SET NX）串行化，处理中异常需清理占位。

## 九、演进与趋势
服务网格或 API 网关内建幂等中间件，业务无感知。

## 十、小结
幂等键是去重的句柄，设计要点是唯一、稳定、可过期、并发安全。
