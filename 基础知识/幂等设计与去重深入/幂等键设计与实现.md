# 幂等键设计与实现

> 对应 Kleppmann《Designing Data-Intensive Applications》第 11 章「Stream Processing」幂等消费者；Stripe 公开 API 文档的 Idempotency-Key 设计；Gray 1978《Notes on Data Base Operating Systems》可重启操作。

## 一、背景与挑战

网络不可靠导致客户端超时重试，同一请求可能被投递多次；若服务端操作非幂等（如「创建订单」「扣款」），重复执行会产生重复记录或重复扣钱。幂等键（idempotency key）是去重的核心句柄：设计不当会导致「本应不同的请求被误合并」或「本应合并的被分开」。难点在于：键须全局唯一、语义稳定、可过期，且对并发同键请求要能正确串行化，处理中的状态在异常时要能清理，否则会永久卡死。

## 二、核心原理

典型做法是：客户端在发起请求时生成一个稳定且唯一的键（UUID、业务单号、或「用户 ID + 动作 + 业务对象 ID」的复合），随请求头/字段传入；服务端以该键为索引记录「已处理结果」。并发同键请求需串行化（分布式锁或唯一约束保证「首写获胜」），且记录需有 TTL 防止无限增长。关键三态：`PROCESSING`（处理中）、`DONE`（已完成，存结果）、`FAILED`（失败，可重试）。只有首写成功者真正执行业务，其余同键请求要么返回已有结果，要么（处理中）等待/快速失败。键的生成策略直接决定安全性：UUID 简单但与原业务语义无关，业务复合键更利于排查与对账。

实例推演（创建订单）：
- 客户端用 `Idempotency-Key: ord-20240915-uuid` 发起创建订单请求。
- 首次到达：SET NX 占位为 PROCESSING，执行建单，写 DONE 并附带订单号。
- 网络超时，客户端用同一键重试：占位已存在，直接返回 DONE 中的订单号，不再建单。
- 若首写执行中途崩溃：异常清理占位，重试可重新执行，不会因 PROCESSING 残留而永久失败。

## 三、形式化与数学基础

设键空间 $K$，结果映射 $R: K \to Result \cup \{PROCESSING, FAILED\}$。正确性要求：对任意 $k \in K$，首次成功写入 $R(k)$ 后，所有后续同 $k$ 的读返回同一值。并发写需满足原子 test-and-set：

$$
\bigl(R(k) = \emptyset\bigr) \xrightarrow{atomic} \bigl(R(k) := PROCESSING\bigr)
$$

幂等性即状态转移的等幂：

$$
apply(apply(S, req), req) = apply(S, req)
$$

即二次应用不改变已确定结果。

## 四、代码实现

```python
# 幂等键：原子占位 + 处理中状态 + 异常清理（示意）
import uuid, redis

r = redis.Redis()

def handle(req_id, payload):
    # 原子占位：仅当键不存在时写入 PROCESSING，并设过期
    if not r.set(req_id, "PROCESSING", nx=True, ex=3600):
        return r.get(req_id)          # 已有结果或处理中，直接返回
    try:
        res = do_work(payload)
        r.set(req_id, res, ex=3600)   # 标记完成并存储结果
        return res
    except Exception:
        r.delete(req_id)              # 清理占位，允许安全重试
        raise
```

## 五、与其他技术对比

| 维度 | 客户端去重 | 服务端唯一约束 | Redis 原子键 | Kafka pid+seq |
|------|-----------|----------------|--------------|----------------|
| 可靠性 | 低（多端不可控） | 强（持久化） | 中高（依赖 Redis 可用） | 强（分区内顺序） |
| 作用范围 | 单端 | 单库 | 跨服务 | 单分区 |
| 复杂度 | 低 | 低 | 中 | 高 |
| 适用错误 | 客户端重发 | 重复插入 | 重复请求 | 消息重发 |

Kafka 的 producer id + 序列号提供「精确一次」语义，是另一种从源头消除重复的思路。

## 六、常见误区

1. 用时间戳当键：并发同毫秒会冲突或遗漏，且时钟回拨更危险。
2. 键永久不失效：存储无限膨胀，应设合理 TTL。
3. 处理中状态未清理：异常后键永久 `PROCESSING`，后续同键永久卡死。
4. 用请求体哈希当键：相同语义不同非关键字段（如时间戳）会导致本应合并的被分开。
5. 忽略部分失败：业务执行一半失败时未回滚占位，造成状态不一致。
6. 用纯随机 UUID 而丢弃业务可追溯性：排查对账时难以关联原订单。
7. 以为占位成功即业务成功：占位只保证串行化，业务结果仍需正确写回 DONE。

## 八、面试题

1. 并发同幂等键如何处理？答：用分布式锁或原子占位（SET NX）串行化，处理中异常需清理占位以允许重试。
2. 幂等键该如何设计？答：稳定唯一、与业务语义绑定、可过期；避免时间戳/随机碰撞，必要时用复合业务键。
3. 处理中状态为何要清理？答：否则异常会令该键永久卡在 PROCESSING，后续合法重试全部被吞。
4. UUID 与业务复合键如何取舍？答：UUID 实现简单；复合业务键利于排查对账，但须保证稳定不变。
5. 占位与实际结果如何区分？答：三态 PROCESSING/DONE/FAILED 分开存，占位成功只代表拿到执行权，结果须写 DONE。

## 九、演进与趋势

服务网格或 API 网关内建幂等中间件，业务无感知；结合 WAL/事务把幂等记录与业务操作写入同一事务，强化持久一致性。具体 API 形态以各厂商官方最新文档为准。

## 十、小结

幂等键是去重的句柄，设计要点是唯一、稳定、可过期、并发安全、可清理。它把「重试安全」从业务代码里抽离成一个可复用的基础设施契约。
