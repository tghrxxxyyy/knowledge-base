# 分布式事务

> 对应 Newman《Building Microservices》「Distributed Transactions」章节；Pat Helland「Life beyond Distributed Transactions」(CIDR 2007)；相关模式见 Enterprise Integration Patterns。

## 一、背景与挑战

跨多个微服务的写操作，无法再用单机数据库事务保证 ACID。经典的两阶段提交（2PC）在微服务中几乎不可用：

- 阻塞：协调者等待所有参与者，期间持有锁，吞吐骤降。
- 可用性差：任一参与者或协调者宕机，整个事务挂起。
- 跨库耦合：要求所有服务用同一事务协议，违背去中心化。

因此微服务普遍放弃强一致，转向「最终一致 + 可恢复」的设计哲学。

## 二、核心原理

主流最终一致方案：

1. Saga 模式：把跨服务操作拆成一组本地事务 $T_1,\dots,T_n$，每步成功后发事件触发下一步；某步失败则逆序执行补偿事务 $C_i$ 回滚已完成步骤。分「编排式（orchestration，中央协调器）」与「协同式（choreography，事件驱动各自响应）」。
2. TCC（Try-Confirm-Cancel）：业务层三阶段，Try 预留资源、Confirm 提交、Cancel 释放，更细粒度但侵入强。
3. 事件驱动 + 消息队列：本地事务与发消息借助事务消息/Outbox 保证原子。

核心思想：「接受暂时的不一致，保证最终可恢复」，并用幂等保证重复投递安全。

## 三、形式化与数学基础

Saga 为事务序列 $T_1,T_2,\dots,T_n$，每 $T_i$ 关联补偿 $C_i$。若第 $k$ 步失败，逆序执行补偿：

$$ T_1 \to T_2 \to \cdots \to T_k\;\text{fail} \;\Rightarrow\; C_k \to C_{k-1} \to \cdots \to C_1 $$

系统最终满足「全成功」或「全补偿抵消」，即

$$ \text{state} = \begin{cases} \sum T_i & \text{成功}\\ \sum C_{\text{done}} & \text{回滚} \end{cases} $$

幂等要求：补偿 $C_i$ 重复执行结果不变，即 $C_i(C_i(s)) = C_i(s)$，以容忍消息重投。

## 四、代码实现

```python
# 编排式 Saga：本地事务成功发事件，失败发补偿（示意）
def create_order_saga():
    try:
        reserve_inventory()          # T1 本地事务
        publish("inventory.reserved")
        charge_payment()             # T2 本地事务
        publish("payment.charged")
    except PaymentError:
        # 逆序补偿
        release_inventory()          # C1
        publish("inventory.released")
        raise

# 补偿必须幂等：用去重表避免重复回滚
def release_inventory(idempotency_key):
    if seen(idempotency_key):
        return
    mark_seen(idempotency_key)
    do_release()
```

## 五、与其他技术对比

| 方案 | 一致性 | 可用性 | 侵入 | 复杂度 |
|------|--------|--------|------|--------|
| 2PC | 强 | 低（阻塞） | 中 | 低 |
| Saga | 最终 | 高 | 中 | 中 |
| TCC | 最终 | 高 | 高 | 高 |
| 事务消息/Outbox | 最终 | 高 | 低 | 低 |

2PC 强一致但阻塞；Saga 高可用但需补偿；TCC 更细但改造重。

## 六、常见误区

- 微服务里强求 2PC：可用性崩坏，违背去中心化。
- 补偿不幂等：消息重投导致重复回滚、状态错乱。
- 忽略空补偿/防悬挂：网络乱序下需处理「先收到 Cancel 后收到 Try」。
- 把 Saga 当免费 ACID：最终一致意味着查询可能看到中间态，业务需容忍。

## 九、演进与趋势

2PC → Saga/事件驱动 → 事务消息（RocketMQ half-message）→ Outbox + CDC（变更数据捕获，将本地写与事件原子落地再异步投递）→ 工作流引擎（Temporal/Cadence）以代码表达持久化 Saga。趋势是「把分布式事务变成可观测、可恢复的工作流」。

## 十、小结

分布式事务在微服务中不可用 2PC 求强一致，转而用 Saga/消息驱动 + 补偿换可用性，并以幂等和 Outbox 保证最终一致与可恢复。关键是接受中间态、显式设计补偿路径。
