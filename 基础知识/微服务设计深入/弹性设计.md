# 弹性设计

> 对应 Newman《Building Microservices》「Resilience」章节；Microsoft「Designing Resilient Systems」；Netflix 韧性工程实践（如 Hystrix 思想）。

## 一、背景与挑战

分布式系统中故障是常态而非异常：下游超时、瞬时网络抖动、依赖雪崩、硬件故障都会发生。若不做弹性设计，局部故障会沿调用链放大，导致整个系统不可用。核心挑战：

- 级联失败：一个慢依赖拖垮调用方线程池，进而传染上游。
- 瞬时故障被误判为永久：抖动触发不必要失败。
- 重试放大：盲目重试把瞬时压力变成持续风暴。
- 资源耗尽：连接池/线程被长期占用。

弹性设计的目的是「在部分失效时仍能提供降级但可用的服务」。

## 二、核心原理

一组互补的弹性模式：

1. 超时（Timeout）：给每次调用设上限，避免无限等待占满资源。
2. 重试（Retry）+ 退避（Backoff）：对瞬时故障重试，指数退避 + jitter 避免同时重试。
3. 熔断（Circuit Breaker）：失败率超阈值则「开路」，快速失败并给下游喘息，半开态试探恢复。
4. 舱壁隔离（Bulkhead）：把资源按服务/调用方隔离成「舱」，单舱故障不淹没全局。
5. 限流（Rate Limit）：保护自身不被过载，丢弃超额请求。
6. 降级（Fallback）：依赖不可用时返回缓存/默认值/简化结果，保核心链路。

这些模式组合使用，按「故障类型 × 业务容忍度」取舍。

## 三、形式化与数学基础

熔断器三态机：Closed（正常）、Open（开路）、Half-Open（半开）。以滑动窗口统计失败率

$$ f = \frac{\text{fail}}{\text{total}} $$

当 $f > f_{\text{threshold}}$ 且样本数 $n \ge n_{\min}$，转 Open 并启动冷却计时 $t_{\text{cool}}$；冷却结束后转 Half-Open，放行少量探测请求，成功则回 Closed，失败则重回 Open。重试退避间隔

$$ t_k = \min(t_{\max},\, t_0 \cdot r^k) + \text{jitter} $$

jitter 为随机扰动，打散重试洪峰。

## 四、代码实现

```python
# 简化版熔断 + 重试逻辑（示意）
class CircuitBreaker:
    def __init__(self, threshold=0.5, cooldown=10):
        self.threshold = threshold
        self.cooldown = cooldown
        self.failures = 0
        self.open_until = 0

    def call(self, fn):
        if time.time() < self.open_until:
            return self.fallback()          # 开路，快速失败
        try:
            r = fn()
            self.failures = max(0, self.failures - 1)
            return r
        except Exception:
            self.failures += 1
            if self.failures / WINDOW > self.threshold:
                self.open_until = time.time() + self.cooldown
            raise
```

## 五、与其他技术对比

| 模式 | 解决 | 副作用 |
|------|------|--------|
| 重试 | 瞬时故障 | 加剧拥塞（需退避+jitter） |
| 熔断 | 级联失败 | 可能误杀健康依赖 |
| 舱壁 | 爆炸半径 | 资源利用率略降 |
| 限流 | 过载 | 拒绝部分请求 |

重试解决瞬时问题但需配退避；舱壁隔离优于全局共享池，限制故障蔓延。

## 六、常见误区

- 无退避盲目重试：制造重试风暴，把抖动变成持续故障。
- 超时过长：线程/连接被占满，资源耗尽。
- 忽视 jitter：大量客户端同步重试触发「惊群」。
- 把熔断当银弹：半开探测阈值需调参，否则误判。

## 九、演进与趋势

从手动 try-catch → 库级模式（Hystrix）→ Sidecar 统一治理（Service Mesh）→ 混沌工程主动注入故障验证弹性 → 自适应限流（按实时负载动态调参，借鉴 TCP Vegas 思路）。趋势是「弹性内建到基础设施 + 主动验证」。

## 十、小结

弹性设计以「超时、重试、熔断、隔离、限流、降级」组合拳抵御故障传播：核心不是杜绝故障，而是在部分失效时保住核心链路、限制爆炸半径、给下游恢复空间。
