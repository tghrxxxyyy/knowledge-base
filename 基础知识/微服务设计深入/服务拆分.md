# 服务拆分

> 对应 Newman《Building Microservices》第2章「Decomposing the Monolith」；Evans《Domain-Driven Design》限界上下文（Bounded Context）；康威定律（Conway's Law）。

## 一、背景与挑战

系统规模增长后，单体应用出现：编译慢、部署耦合、一个 bug 全站宕机、团队互相阻塞。拆分为微服务能获得独立部署与扩展能力，但拆错了代价更大——最常见失败是「分布式单体」：服务虽多，却因强耦合无法独立开发部署，反而更复杂。核心挑战：

- 边界难定：业务边界模糊，切得太粗仍是单体，太细则通信爆炸。
- 数据耦合：拆分后还共享数据库，等于没拆。
- 组织对齐：团队结构与系统结构不匹配（康威定律的反向作用）。

## 二、核心原理

拆分的核心准则是「围绕业务能力（Business Capability）或限界上下文切分」，而非按技术层（controller/service/dao）。关键属性：

- 高内聚：服务内职责相关、变更同源。
- 低耦合：服务间仅通过稳定 API/事件交互。
- 独立部署：每个服务可单独发布、独立扩缩。
- 独立数据：每服务自有数据库，杜绝跨库 JOIN。
- 围绕小团队：两披萨团队，对齐康威定律（组织结构≈系统结构）。

常见策略：先识别限界上下文（订单、库存、支付），再据耦合强度逐步抽取，避免一次性大爆炸拆分。落地时常用「绞杀者模式（Strangler Fig）」：在单体前加一层路由/网关，新功能以独立服务实现，旧功能逐步迁移，最终旧单体被「绞杀」下线。它能把拆分风险控制在每次小步变更中，配合特性开关实现灰度。值得注意的是，拆分不是终点而是一致性契约的开始——服务间 API 需显式版本化，避免消费方被隐性破坏。

## 三、形式化与数学基础

把系统视为服务集合 $S=\{s_1,\dots,s_n\}$。定义服务 $i,j$ 间耦合由调用频率 $c_{ij}$ 与共享数据量 $s_{ij}$ 衡量。理想切分最小化跨服务耦合、最大化服务内聚：

$$ \min_{\text{partition}}\; \sum_{i\ne j} (c_{ij} + s_{ij}) $$

同时令单服务内聚度（如模块间调用密度）最大。可用社区发现（如 Louvain）对调用图聚类得到初版边界。康威定律可形式化为：系统通信结构 $\mathcal{C}$ 会收敛于组织沟通结构 $\mathcal{O}$，即 $\mathcal{C}\approx \mathcal{O}$。

## 四、代码实现

```yaml
# 按限界上下文划分服务与独立仓库（示意）
services:
  order-service:       # 订单上下文：自有 order_db
    repo: github.com/org/order-svc
    db: order_db
  inventory-service:   # 库存上下文：自有 inv_db
    repo: github.com/org/inventory-svc
    db: inv_db
  payment-service:     # 支付上下文：自有 pay_db
    repo: github.com/org/payment-svc
    db: pay_db
# 服务间仅通过 API/事件交互，禁止跨库访问
```

## 五、与其他技术对比

| 形态 | 部署 | 耦合 | 适用 |
|------|------|------|------|
| 模块化单体 | 单部署 | 中 | 早期/小团队 |
| 微服务 | 独立 | 低 | 规模大/多团队 |
| 分布式单体 | 伪独立 | 高 | 应避免 |

微服务牺牲一致性/运维成本换取独立部署；与 Service Mesh 配合降低通信治理成本。

## 六、常见误区

- 按技术层而非业务拆分：得到分布式单体，毫无收益。
- 过早微服务化：早期流量小、边界未稳，单体更划算（Majestic Monolith 回潮）。
- 共享数据库假装拆分：跨库访问使服务无法独立演进。
- 粒度过细：服务数爆炸，通信与运维成本反超收益。
- 忽视团队边界：拆出的服务没有对应小团队负责，最终又回到少数人对整体负责。

进一步说，拆分粒度应与「组织沟通成本」同频：当新增一个服务带来的沟通开销超过它省下的协作成本时，就该停止继续细分。这也是康威定律的反向应用——不是技术决定组织，而是组织能力决定了能有效维护的服务数量上限。

## 九、演进与趋势

从大单体 → 模块化单体（临时过渡）→ 微服务（按限界上下文）→ 平台工程（Internal Developer Platform）降低微服务运维门槛。趋势是「演进式拆分」：先单体后按需抽服务，并辅以服务网格与 IDP 控制复杂度。同时也要警惕「微服务教条」：当团队规模小、业务边界未稳定时，强行拆分反而拖累交付，「模块化单体 + 清晰模块边界」往往是更务实的起点，待真正出现多团队并行演进信号再拆分不迟。

拆分后的接口治理同样关键：服务间契约（如 OpenAPI、Protobuf IDL）应纳入版本管理，破坏性变更要走兼容流程，避免「一个服务改了，全链路编译失败」。

当服务数增长，本地开发也需配套：契约测试、服务桩（stub）、本地编排脚本能把「分布式复杂度」挡在开发者体验之外。

组织层面，每个服务应有明确的单一责任人（owner）与清晰的 SLA，权责不清是微服务退化为「分布式大泥球」的前兆。

## 十、小结

服务拆分以「业务边界而非技术层」为唯一准绳：高内聚、低耦合、独立数据与部署，并主动对齐组织结构（康威定律），避免分布式单体这一最常见陷阱。
