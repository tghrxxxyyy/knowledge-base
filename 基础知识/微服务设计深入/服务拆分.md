# 服务拆分

> 对应 Newman《Building Microservices》第2章、DDD 限界上下文。

## 一、背景与挑战
单体应用随规模变大，编译慢、部署耦合、团队阻塞。拆分微服务需确定边界，避免分布式单体。

## 二、核心原理
以业务能力（Business Capability）或限界上下文为边界拆分；高内聚、低耦合；每个服务独立部署、独立数据存储、围绕小团队（康威定律）。

## 三、形式化 / 数学基础
耦合度量：服务 $i,j$ 间调用频率 $c_{ij}$ 与共享数据 $s_{ij}$。理想切分使 $\sum_{i\ne j}(c_{ij}+s_{ij})$ 最小，同时单服务内聚度最大。

## 四、代码实现
```yaml
# 按限界上下文划分仓库与服务
services:
  - order-service     # 订单上下文
  - inventory-service # 库存上下文
  - payment-service   # 支付上下文
```

## 五、与其他技术对比
与模块化单体相比，微服务牺牲一致性换取独立部署；与服务网格结合降低通信成本。

## 六、常见误区
误区：按技术层（controller/service/dao）而非业务拆分，得到分布式单体。误区：过早微服务化。

## 七、与开源书 / 权威来源对应
Newman, S.《Building Microservices》第2章；Evans《Domain-Driven Design》；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"如何决定微服务边界？分布式单体是什么？"

## 九、演进与趋势
平台工程（Internal Developer Platform）降低微服务运维门槛；模块单体回潮（如 Majestic Monolith）提示按需拆分。

## 十、小结
以业务边界而非技术层切分，避免分布式单体。
