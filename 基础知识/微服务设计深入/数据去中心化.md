# 数据去中心化

> 对应 Newman《Building Microservices》第5章「Data」；Pat Helland「Data on the Outside vs. Data on the Inside」；Dehghani《Data Mesh》相关思想。

## 一、背景与挑战

微服务强调「独立部署」，而最破坏独立性的就是「共享数据库」：一旦多个服务读写同一库，任一服务改表结构都会牵连其他服务，等于把所有人绑回单体。痛点：

- 隐式耦合：表结构成为服务间的强契约。
- 无法独立演进：DDL 变更需跨团队协调。
- 事务诱惑：跨服务直接 JOIN/事务，牺牲可用性。
- 技术绑定：所有服务被迫用同一存储技术。

数据去中心化主张「每个服务拥有并私有自己的数据」。

## 二、核心原理

三条核心原则：

1. 数据库每服务私有（Database per Service）：服务独享数据存储，其他服务只能通过其 API 访问，不得直连其库。
2. 通过 API/事件同步：跨服务所需数据由 owner 服务暴露接口，或以事件异步复制，杜绝直连。
3. 最终一致性：放弃跨服务的强一致事务，接受「短暂不一致、最终收敛」，用补偿/Saga 处理失败。

配合 CQRS：写服务持有权威数据，查询侧维护只读副本/物化视图，缓解跨服务查询压力。进阶是「数据网格（Data Mesh）」：把领域数据当作产品，由领域团队负责其质量与契约。实践中的关键细节是「事件溯源（Event Sourcing）」：不存当前状态而存状态变更事件序列，任何时刻的状态可由重放事件得到，这天然适合跨服务异步复制与审计。但事件溯源也带来「事件 schema 演进」与「重放性能」挑战，通常需要定期快照（snapshot）平衡二者。

## 三、形式化与数学基础

一致性谱：强一致要求线性化（Linearizable），任意操作可见顺序与真实时间一致，代价高（需同步复制）；最终一致满足：经过有限时间 $T$ 后，所有副本收敛到同一值：

$$ \forall t > T,\; \forall i,j:\; replica_i(t) = replica_j(t) $$

用版本向量（Version Vector）$VV = (v_1,\dots,v_n)$ 记录各节点因果计数，检测更新因果顺序：若 $VV_a < VV_b$（逐分量 $\le$ 且至少一个 $<$），则 $a$ 因果先于 $b$。冲突通过最后写入胜出（LWW）或业务合并解决。

## 四、代码实现

```sql
-- 每服务独立 schema，互不可见（示意）
-- order-service.order_db / payment-service.pay_db
CREATE TABLE order_service.orders (id BIGINT, status VARCHAR(20));
-- 跨域数据通过事件异步复制，禁止跨库 JOIN
-- 查询侧物化视图（只读副本）
CREATE MATERIALIZED VIEW order_payment_view AS
  SELECT o.id, o.status, p.amount
  FROM order_events o JOIN payment_events p
  ON o.id = p.order_id;
```

## 五、与其他技术对比

| 方案 | 独立性 | 一致性 | 复杂度 |
|------|--------|--------|--------|
| 共享数据库 | 低 | 强 | 低 |
| 每服务私有库 | 高 | 最终 | 中 |
| + CQRS | 高 | 读写分离 | 高 |
| 数据网格 | 最高 | 产品化治理 | 高 |

私有库独立性高但需处理冗余与一致性；CQRS 缓解查询痛点。

## 六、常见误区

- 同库不同 schema 假装去中心化：仍共享存储，DDL 互相影响。
- 跨服务直接 JOIN：绕过 API 重新耦合，破坏独立部署。
- 强求跨服务 ACID：应改最终一致 + 补偿。
- 忽视数据契约：事件结构需版本化，避免消费方断裂。
- 误以为无需备份：每服务私有库更分散，备份与灾难恢复策略必须下沉到每个服务。

需要强调的是，去中心化不等于「无治理」。相反，它把治理成本从「隐式共享」转移到了「显式契约与平台能力」：数据目录、schema 注册中心、跨域事件总线，都是去中心化后必须补齐的基础设施，否则会演变成「分布式数据沼泽」。

## 九、演进与趋势

共享库 → 每服务私有库 → CQRS/事件同步 → 数据网格（领域数据产品化、自助式治理）。趋势是把「数据所有权」与「数据契约」作为一等公民，用平台能力降低去中心化的运维负担。另一条值得关注的路径是「主数据管理（MDM）+ 领域数据产品」：跨域仍需一致的主实体（如用户、商品）由专门的权威服务以契约形式对外提供，其余服务只持有本地投影，从而在去中心化与全局一致性之间取得务实平衡。

工程上，去中心化落地常与「数据库迁移」绑定：旧单体拆库时常用双写+比对+切换的灰度策略，先让新服务读自己库、旧服务仍写共享库，验证一致后再关闭双写。

此外，跨服务数据查询不应每次都实时聚合，可借助变更数据捕获（CDC）把源数据增量同步到只读分析库，用空间换查询时间，这是 CQRS 读模型的常见实现。

最后要提醒，去中心化不是「各管各的」，而是「各自负责、统一契约」，缺少 schema 注册与数据目录，分散的库会退化为更难治理的数据孤岛。

## 十、小结

数据去中心化用「数据库私有化 + API/事件同步 + 最终一致」换取部署独立，是微服务区别于单体的关键。代价是必须接受最终一致并用补偿/Saga 兜底，同时以数据契约约束跨域交互。
