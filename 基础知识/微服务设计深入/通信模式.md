# 通信模式

> 对应 Newman《Building Microservices》第4章、Fowler 关于 API 的文章。

## 一、背景与挑战
服务间需通信，但同步调用链过长会导致延迟累积与故障传播；需根据场景选择协议与模式。

## 二、核心原理
同步（REST/gRPC）适合请求-响应；异步（消息队列、事件总线）解耦生产者消费者；API Gateway 聚合边缘调用；Backends for Frontends（BFF）按客户端裁剪。

## 三、形式化 / 数学基础
同步链路延迟 $L=\sum_{k} l_k$，故障传播概率随跳数上升。异步将调用方与被调用方解耦：生产者 $P$ 仅依赖 broker，不依赖消费者可用性。

## 四、代码实现
```go
// gRPC 一元调用
resp, err := client.GetOrder(ctx, &pb.GetOrderReq{Id: id})
// 异步发布事件
broker.Publish("order.created", payload)
```

## 五、与其他技术对比
RPC（gRPC）强类型高性能；REST 易调试；消息队列提升弹性但引入最终一致性与运维复杂度。

## 六、常见误区
误区：所有调用都用同步 REST，造成扇入雪崩。误区：在同步链里混用事务。

## 七、与开源书 / 权威来源对应
Newman, S.《Building Microservices》第4章；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"同步与异步通信如何取舍？BFF 解决什么问题？"

## 九、演进与趋势
gRPC-Web、GraphQL Federation、AsyncAPI 标准化异步契约。

## 十、小结
按一致性/延迟/解耦需求匹配通信模式。
