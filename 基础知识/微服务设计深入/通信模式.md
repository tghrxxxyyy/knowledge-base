# 通信模式

> 对应 Newman《Building Microservices》第4章「Inter-process Communication」；Fowler 关于 API Gateway、RPC 与异步消息的文章；相关实践见 CS-Notes。

## 一、背景与挑战

微服务把单体拆成多个独立部署的进程，进程间必须通信才能协作。但通信方式直接决定系统的延迟、可用性、一致性与运维复杂度。典型挑战：

- 延迟累积：同步调用链过长，每跳叠加网络与处理耗时。
- 故障传播：下游超时/雪崩沿调用链向上游传导。
- 耦合风险：服务间协议/数据格式强绑定，一方变更波及全网。
- 一致性难题：跨服务数据无法用单机事务保证。

因此必须按「一致性要求、延迟敏感度、解耦需求」选择通信模式。

## 二、核心原理

主流通信模式分两类：

1. 同步（请求-响应）：调用方阻塞等待结果。
   - REST/HTTP：易调试、生态广，文本协议开销略高。
   - gRPC：基于 HTTP/2 + Protobuf，强类型、低延迟、支持流式与双向通信。
   - 适用：需要即时结果、强一致读写的场景。
2. 异步（消息驱动）：调用方发完即返，由 broker 投递。
   - 消息队列（Kafka/RabbitMQ）：解耦生产者与消费者，支持削峰、重放。
   - 事件总线/Event Sourcing：以事件为唯一事实来源，便于审计与重建。
   - 适用：耗时任务、跨团队解耦、最终一致场景。

横切模式：API Gateway 在边缘聚合/路由请求，Backend for Frontends（BFF）按客户端（Web/App）裁剪接口，避免「一个通用 API 适配所有端」的臃肿。

## 三、形式化与数学基础

同步链路若有 $n$ 跳，每跳延迟 $l_k$（含网络 $n_k$ 与处理 $p_k$），总延迟

$$ L = \sum_{k=1}^{n} (n_k + p_k) $$

故障传播：若每跳独立可用率为 $a_k$，链路整体可用率

$$ A = \prod_{k=1}^{n} a_k $$

跳数越多 $A$ 越低。异步将调用方仅依赖 broker 可用率 $a_b$，与消费者可用率解耦：

$$ A_{\text{async}} = a_{\text{caller}} \cdot a_b $$

生产者不再受消费者故障牵连，爆炸半径被限制。

## 四、代码实现

```go
// gRPC 一元调用（同步、强类型）
resp, err := client.GetOrder(ctx, &pb.GetOrderReq{Id: id})
if err != nil {
    return fmt.Errorf("get order failed: %w", err)
}
// 异步发布事件到 broker（解耦）
broker.Publish("order.created", payload)

// BFF：按客户端裁剪字段后聚合返回
func MobileOrderHandler(w http.ResponseWriter, r *http.Request) {
    order := fetchOrder(id)              // 调用内部服务
    render(w, trimForMobile(order))      // 仅返回移动端所需字段
}
```

## 五、与其他技术对比

| 模式 | 一致性 | 延迟 | 耦合 | 适用 |
|------|--------|------|------|------|
| REST | 即时 | 中 | 低 | 通用、易调试 |
| gRPC | 即时 | 低 | 中 | 内部高性能 |
| 消息队列 | 最终 | 高 | 极低 | 解耦、削峰 |
| API Gateway/BFF | - | - | 降 | 边缘聚合 |

RPC 高性能但强耦合 IDL；REST 易用但文本开销；消息队列换弹性但引入最终一致与运维负担。

## 六、常见误区

- 所有调用都同步 REST：长调用链造成扇入雪崩与延迟叠加。
- 在同步链里混用事务：跨服务无法回滚，应通过补偿/Saga。
- 忽视超时与重试：无超时会被下游拖死，盲目重试放大故障。
- 一个 API 适配所有端：导致移动端拉取冗余字段，宜用 BFF。

## 九、演进与趋势

从单一 REST → gRPC 内部高性能调用 → 异步消息/Event Sourcing 解耦 → GraphQL Federation 聚合多服务数据 → AsyncAPI 标准化异步契约。趋势是把「同步即时」与「异步弹性」按场景组合，并用 Service Mesh 统一治理横切关注点。

## 十、小结

通信模式没有银弹：以一致性/延迟/解耦三需求为锚，同步选 gRPC/REST、异步选消息队列，配合 API Gateway 与 BFF 在边缘收敛复杂度，并按故障域主动隔离爆炸半径。
