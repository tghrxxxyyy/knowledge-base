# 服务网格

> 对应 Buoyant 提出的 Service Mesh 概念、Istio/Linkerd 实践。

## 一、背景与挑战
把熔断、重试、mTLS、观测等横切关注点写进每个服务，导致重复且与业务耦合。

## 二、核心原理
服务网格以 sidecar 代理（如 Envoy）拦截服务间流量，将通信治理下沉到基础设施层，业务代码无感知。控制面（Istio）下发策略，数据面执行。

## 三、形式化 / 数学基础
每个服务实例旁部署 proxy $P_i$，流量 $S_i \to P_i \to P_j \to S_j$。策略函数 $policy(traffic)$ 在 $P$ 上统一执行，业务层 $S$ 维持纯粹。

## 四、代码实现
```yaml
# Istio VirtualService 配置重试与熔断（业务代码零改动）
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  http:
  - retries: { attempts: 3, perTryTimeout: 2s }
```

## 五、与其他技术对比
与 SDK/库方案（如 Hystrix）相比，mesh 语言无关、升级不停机；代价是运维复杂度与延迟跳数。

## 六、常见误区
误区：小团队也上全量 mesh，运维成本超过收益。误区：忽视 sidecar 资源开销。

## 七、与开源书 / 权威来源对应
Newman, S.《Building Microservices》"Service Mesh" 相关章节；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"服务网格解决了什么？与 SDK 方案对比？"

## 九、演进与趋势
eBPF 把部分 mesh 能力移出 sidecar，降低开销（如 Cilium）。

## 十、小结
把通信治理下沉到 sidecar，解耦业务与基础设施。
