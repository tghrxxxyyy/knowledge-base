# 服务网格

> 对应 Buoyant 提出的 Service Mesh 概念（William Morgan）；Istio / Linkerd 官方实践；Envoy 数据面代理。Newman《Building Microservices》相关章节。

## 一、背景与挑战

微服务把「熔断、重试、mTLS、流量观测、限流」等横切关注点写进每个服务，带来两个问题：

- 重复实现：每语种、每服务各自写一套，代码冗余。
- 业务耦合：治理逻辑与业务混在一起，升级需改业务代码、全量发版。
- 多语言障碍：用 SDK（如 Hystrix）会把技术栈锁死在某一语言。

服务网格（Service Mesh）的目标是「把这些通信治理下沉到基础设施层」，让业务代码保持纯粹。

## 二、核心原理

服务网格由两层构成：

1. 数据面（Data Plane）：每个服务实例旁部署一个轻量代理（sidecar，如 Envoy），拦截进出流量。所有服务间调用实际都走「服务 → 本机 sidecar → 对端 sidecar → 服务」。
2. 控制面（Control Plane）：统一下发路由、重试、熔断、mTLS、遥测等策略到所有 sidecar，无需改业务代码。

业务只需「发普通请求」，治理在 sidecar 透明完成。流量治理、加密、观测都被标准化、集中化管理。

## 三、形式化与数学基础

设服务实例 $S_i$ 旁部署代理 $P_i$，一次跨服务调用路径为

$$ S_i \xrightarrow{\text{localhost}} P_i \xrightarrow{\text{network}} P_j \xrightarrow{\text{localhost}} S_j $$

策略函数 $policy(\cdot)$ 在 $P_i,P_j$ 上统一执行（重试、熔断、mTLS）。定义代理引入的额外延迟 $\delta$（本地回环 + 加解密），若原网络延迟为 $L$，则

$$ L' = L + 2\delta $$

由于 $\delta$ 为本地回环级微秒开销，对多数场景可忽略，但高频小包调用需权衡。业务层 $S$ 维持纯粹，治理复杂度被隔离到 $P$。

## 四、代码实现

```yaml
# Istio VirtualService：重试 + 熔断，业务代码零改动
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: order-route
spec:
  hosts: ["order-service"]
  http:
  - route:
    - destination: { host: order-service }
    retries:
      attempts: 3            # 重试次数
      perTryTimeout: 2s      # 单次尝试超时
      retryOn: 5xx,gateway-error
    timeout: 5s
```

## 五、与其他技术对比

| 方案 | 语言无关 | 升级成本 | 延迟 | 运维 |
|------|----------|----------|------|------|
| SDK（Hystrix） | 否 | 高（改业务） | 低 | 低 |
| Service Mesh | 是 | 低（改配置） | 略增 | 高 |
| 无治理 | - | - | 最低 | 无 |

Mesh 以运维复杂度与延迟跳数换取「语言无关 + 不停机升级」。

## 六、常见误区

- 小团队也上全量 mesh：运维成本（控制面、sidecar 资源、排障）可能超过收益。
- 忽视 sidecar 开销：每实例多占 CPU/内存，需合理设资源配额。
- 以为 mesh 解决一切：业务逻辑的正确性不在 mesh 范畴。
- 跳过 mTLS 配置：零信任要求服务间默认加密。

## 九、演进与趋势

库/SDK 治理 → Sidecar 数据面（Envoy）→ 成熟控制面（Istio/Linkerd）→ eBPF 把部分能力移出 sidecar（如 Cilium），降低延迟与资源开销。趋势是「无 sidecar 或轻 sidecar」的下一代 mesh，兼顾治理与性能。

控制面的选型也影响体验：Istio 功能全但组件重，Linkerd 更轻量，Cilium 基于 eBPF 甚至无需 sidecar，团队应据运维能力取舍。

落地时建议「先可观测、后治理」：先把流量指标与追踪接好，再用渐进式规则开启重试/熔断，避免一上来全量策略导致排障困难。

## 十、小结

服务网格把通信治理下沉到 sidecar，以「语言无关 + 配置驱动 + 不停机升级」解耦业务与基础设施；代价是运维与延迟开销，需按团队规模与复杂度审慎选型。
