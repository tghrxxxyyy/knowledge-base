# CI/CD · 03 构建与制品管理

> **口诀：构建要可重现，制品要不可变——同一次提交，任何时间、任何机器，跑出同一个包。**

本篇覆盖流水线中段：代码怎么变成可运行的产物。先讲构建工具与"增量/可重现"两大原则，再讲制品的定义、分类、仓库与晋级，最后深入 Docker 镜像构建（多阶段、缓存、瘦身）与镜像仓库、依赖供应链（SBOM 先给概念）。

## 一、构建（Build）：从源码到可运行物

构建是把人类可读的源码 + 依赖，转换成机器可执行的产物（字节码/二进制/包/镜像）的过程。它在 CI 中每次提交触发，是"质量门禁"的第一道关。

### 1.1 主流构建工具一览

| 语言/生态 | 构建工具 | 依赖管理 | 增量/缓存机制 |
|-----------|---------|---------|--------------|
| Java | Maven、Gradle | pom.xml / build.gradle | Gradle 增量编译、构建缓存 |
| JavaScript | npm、yarn、pnpm | package.json + lock | pnpm 硬链接 + 内容寻址存储 |
| Go | Go module（`go build`） | go.mod / go.sum | 编译缓存 `$GOCACHE` |
| Python | setuptools、poetry、uv | pyproject.toml / poetry.lock | uv 极速解析与缓存 |
| Rust | Cargo | Cargo.toml / Cargo.lock | 增量编译 + sccache |

### 1.2 Maven 生命周期与增量

Maven 把构建固化为标准生命周期：`validate → compile → test → package → verify → install → deploy`。Gradle 在此基础上提供**增量编译（只重编受影响的源文件）**与**构建缓存（本地/远程缓存任务输出）**，大型项目提速显著。

```bash
# Maven：跳过测试快速打包（仅示例，CI 不应跳过测试）
mvn -DskipTests package

# Gradle：启用构建缓存与并行
gradle build --build-cache --parallel
```

### 1.3 npm / pnpm 依赖一致性

`package-lock.json` 锁定依赖树，保证可重现。pnpm 用**内容寻址存储 + 硬链接**，节省磁盘且严格隔离，避免"幽灵依赖"。

```bash
npm ci            # 严格按 lock 安装（CI 推荐，比 npm install 干净）
pnpm install --frozen-lockfile
```

### 1.4 Go module 可重现构建

```bash
go mod tidy       # 整理依赖
go build -trimpath -ldflags="-buildid= -mod=readonly" -o app .   # 去路径/去 buildid 以可重现
```

> `-trimpath` 去掉绝对路径，`-buildid=` 置空，是保证 Go 二进制可重现的关键。

### 1.5 Python：wheel 与 uv

现代 Python 分发用 **wheel（`.whl`）** 预编译格式取代源码包，安装无需现场编译。依赖用 `uv`（2024 起流行的极速解析器）或 `poetry` 锁版本。

```bash
uv sync --frozen          # 按 uv.lock 精确安装
python -m build           # 产出 sdist + wheel
```

## 二、两大原则：增量构建与可重现性

### 2.1 增量构建与缓存（避免全量重建）

每次都全量重建既慢又费资源。关键手段：

- **输入指纹缓存**：以源文件/依赖哈希为 key，命中的任务直接取缓存产物。
- **分层缓存**：Docker 层、Maven `~/.m2`、npm `node_modules`、Go `GOCACHE` 挂载到 CI 缓存卷。
- **远程缓存**：Gradle Build Cache、Bazel Remote Cache、sccache（Rust），让团队共享编译结果。

```mermaid
flowchart LR
    SRC[源码+依赖 哈希] --> HASH{缓存命中?}
    HASH -->|是| REUSE[复用缓存产物]
    HASH -->|否| BUILD[执行构建]
    BUILD --> STORE[存入缓存]
    REUSE --> OUT[产出]
    STORE --> OUT
```

> **口诀：缓存的本质是"用哈希换时间"——输入没变，就别重算。**

⚠️ **生产踩坑**：
- 缓存键（cache key）设计不当会导致"缓存永不命中"或"命中了旧错结果"。务必把依赖清单（lock 文件）纳入 key。
- `mvn install` 把快照装进本地仓库会污染其他构建，CI 应用 `package`/`verify` 而非 `install`。

### 2.2 可重现构建（Reproducible Builds）

指**同一次源码，在任何时间、任何机器、任何环境下，产出字节级一致的产物**。价值：供应链可信、可验证、可审计（与第 13 篇 SBOM/签名呼应）。

实现要点：

| 干扰源 | 对策 |
|--------|------|
| 绝对路径/时间戳 | 去除（Go `-trimpath`、Jar `reproducible`、zip 忽略 mtime） |
| 非确定性排序 | 固定文件遍历/映射顺序 |
| 嵌入 git 版本 | 改为外部注入而非编译期写入 |
| 依赖漂移 | 锁文件 + 私有仓库固定源 |

## 三、制品（Artifact）：构建的产物

### 3.1 定义与分类

制品是构建产出的、可部署/可消费的**不可变单元**。一旦发布，不应被修改，只能发新版本。

| 类型 | 例子 | 典型仓库 |
|------|------|---------|
| JVM 包 | `.jar` / `.war` | Nexus、Artifactory |
| Python 包 | `.whl` / `.tar.gz` | PyPI、Artifactory |
| Node 包 | `.tgz`（npm pack） | npm、GitLab Package |
| 容器镜像 | `.tar` / OCI 镜像 | Harbor、ECR、GCR |
|  chart | Helm `.tgz` | Harbor（OCI）、ChartMuseum |
| 二进制 | Go 编译可执行、静态库 | Nexus |

### 3.2 制品仓库：集中管理 + 晋级

制品仓库把"构建产出"与"部署消费"解耦，并提供版本、权限、漏洞库、晋级（promotion）。

| 仓库 | 特点 |
|------|------|
| Sonatype Nexus | 多格式（maven/npm/docker/...）、轻量易部署 |
| JFrog Artifactory | 企业级、统一元数据、晋级流水线、Xray 扫描 |
| GitHub Packages | 与 GitHub 一体，按仓库管理 |
| GitLab Package Registry | 与 GitLab CI 一体 |

制品**晋级（promotion）**示例：snapshot → release candidate → production。

```mermaid
flowchart LR
    CI[CI 构建] --> SNAP[(snapshot 仓)]
    SNAP --> RC{测试通过?}
    RC -->|是| REL[(release 仓)]
    REL --> PROD{审批通过?}
    PROD -->|是| PRD[(production 仓)]
```

> **口诀：制品只升不降、只加不改——发布的版本永不可变，回滚靠旧版本而非改旧包。**

⚠️ **生产踩坑**：把同一版本号重新上传覆盖（mutable artifact）是严重反模式，会导致"明明没改代码，生产行为却变了"，且无法审计。仓库应开启 immutable 策略。

## 四、Docker 镜像构建

### 4.1 docker build 基础与缓存层

Docker 镜像由**只读层**叠加而成。每条 `RUN`/`COPY`/`ADD` 产生一层；构建时若上层未变则复用缓存。因此**把易变的步骤（COPY 源码）放后面、稳定的（装依赖）放前面**，能最大化缓存命中。

```dockerfile
# 不佳：源码一改，依赖重装
COPY . .
RUN npm install

# 较佳：先拷依赖清单装依赖（命中缓存），再拷源码
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
```

### 4.2 多阶段构建（Multi-stage）

用一个"构建阶段"编译，再把产物拷进极小的"运行阶段"镜像，最终镜像不含编译器与源码，体积小、攻击面低。

```dockerfile
# ---- 构建阶段 ----
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -o /app/server .

# ---- 运行阶段 ----
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
```

```mermaid
flowchart TB
    subgraph B[构建阶段 builder]
    B1[golang:1.22 基础镜像] --> B2[go mod download 依赖层]
    B2 --> B3[COPY 源码 + go build]
    B3 --> B4[产出 /app/server 二进制]
    end
    subgraph R[运行阶段 distroless]
    R1[distroless/static 极小基础] --> R2[COPY --from=builder 二进制]
    R2 --> R3[最终镜像 ~10MB 无 shell/无源码]
    end
    B4 -.COPY --from.-> R2
```

### 4.3 BuildKit 与构建加速

BuildKit（现代 Docker 默认构建引擎）支持：**并行阶段构建**、**远程/内联缓存导出**、**secret 挂载（不进镜像）**、**--mount=type=cache 依赖缓存**。

```bash
# 导出缓存供下一次复用（CI 关键）
docker buildx build --cache-to=type=registry,ref=myrepo/cache:build-cache \
                    --cache-from=type=registry,ref=myrepo/cache:build-cache \
                    -t myrepo/app:1.0 --push .
```

### 4.4 镜像瘦身与 .dockerignore

- 用 **distroless / alpine** 基础镜像；alpine 约 5MB，distroless 仅含运行时与 CA 证书，无 shell（更安全但调试难）。
- **`.dockerignore`** 排除 `.git`、`node_modules`、本地缓存等，避免无谓上下文传输与误拷。

```text
# .dockerignore
.git
node_modules
*.log
Dockerfile
.dockerignore
```

### 4.5 镜像分层策略小结

| 策略 | 效果 |
|------|------|
| 依赖层前置 | 提高缓存命中 |
| 多阶段构建 | 大幅缩小最终镜像 |
| distroless/alpine | 减体积、降攻击面 |
| BuildKit cache mount | 加速依赖安装 |
| `.dockerignore` | 减小构建上下文 |

> **口诀：镜像不是"能跑就行"，而是"越小越纯越安全"。**

⚠️ **生产踩坑**：
- `latest` 标签是反模式——不可溯源、不可回滚。必须用不可变标签（git sha / 语义版本）。
- 把密钥 `COPY` 进镜像或用 `ENV` 写死，会随镜像泄露。用 BuildKit `--secret` 或运行时注入。
- 基础镜像不锁定 digest，今天构建和明天构建可能拉到不同基础层，破坏可重现性。建议钉 digest（`@sha256:...`）。

## 六、依赖与供应链：SBOM 先给概念

### 6.1 依赖锁文件是底线

所有生态都应提交 lock 文件（`go.sum`/`package-lock.json`/`poetry.lock`/`Cargo.lock`），保证 CI 与本地、今天与明天拉到**完全一致**的依赖树。

### 6.2 SBOM（软件物料清单）概念

SBOM（Software Bill of Materials）是"软件由哪些组件构成"的清单（如 CycloneDX / SPDX 格式），用于：

- 漏洞爆发后**秒级定位**受影响版本（如 Log4Shell）。
- 合规与审计。
- 与镜像签名共同构成供应链信任链。

```bash
# 用 Syft 生成 SBOM（示例）
syft packages myrepo/app:1.0 -o cyclonedx-json > sbom.json
```

> **口诀：没有 SBOM，你根本不知道自己部署了什么——出了事只能全网盲猜。**

⚠️ 深入（SBOM 生成、签名、准入控制、依赖投毒防护）留待 [13-安全与供应链安全](13-可观测性DORA度量与DevSecOps.md)。

- [ ] 选对构建工具，开启增量/缓存（Gradle、BuildKit、sccache）。

## 二十三、Maven 依赖仲裁机制与冲突排查

### 13.1 依赖仲裁规则

```
Maven 依赖调解（Dependency Mediation）：
  ① 最短路径优先（Nearest Definition）
     A → B → C → D(v1)   路径长度 3
     A → E → D(v2)       路径长度 2
     → 选 D(v2)

  ② 最先声明优先（First Declaration）
     路径相同时，pom.xml 中先声明的依赖胜出

  ③ 依赖范围（Scope）影响优先级
     runtime > compile > provided > system
```

### 13.2 冲突排查工具

```bash
# Maven 依赖树（最常用）
mvn dependency:tree -Dverbose | grep "omitted for conflict"
# 输出示例：
# [INFO] +- org.apache.hadoop:hadoop-common:jar:3.3.4:compile
# [INFO] |  \- (com.google.guava:guava:jar:27.0-jre:compile - omitted for conflict with 30.1-jre)

# Maven 依赖分析
mvn dependency:analyze
# Used undeclared: 使用了但未声明（需加到 pom）
# Unused declared: 声明了但未使用（可移除）

# Gradle 依赖分析
./gradlew dependencies --configuration runtimeClasspath
# > +--- com.google.guava:guava:30.1-jre
# > |    \--- com.google.guava:failureaccess:1.0.1 (coco)

# 依赖收敛检查
mvn enforcer:enforce -Drules=dependencyConvergence
```

### 13.3 Gradle 依赖仲裁

```
Gradle 依赖调解规则：
  ① 最高版本优先（与 Maven 不同！）
     A 依赖 guava:27
     B 依赖 guava:30
     → 选 guava:30

  ② 最先声明（版本相同时）
     pomo.xml / build.gradle 中先声明的胜出

  ③ 强制版本（推荐显式指定）
     implementation('com.google.guava:guava:31.1-jre')
     // 或全局强制
     configurations.all {
         resolutionStrategy.force 'com.google.guava:guava:31.1-jre'
     }

  ④ 拒绝冲突版本
     configurations.all {
         resolutionStrategy {
             failOnVersionConflict()
         }
     }
```

| 维度 | Maven | Gradle |
|------|-------|--------|
| 默认策略 | 最短路径 → 最先声明 | 最高版本 → 最先声明 |
| 强制版本 | `<dependencyManagement>` | `resolutionStrategy.force` |
| 排除依赖 | `<exclusions>` | `exclude group` |
| BOM 管理 | `<dependencyManagement>` + import | `platform()` / `enforcedPlatform()` |

> **口诀**：Maven 看路径远近，Gradle 看版本高低——两者规则不同，迁项目时最容易踩坑。

## 二十四、Gradle 构建缓存原理与远程缓存

### 14.1 本地缓存原理

```
Gradle 本地缓存：
  路径：~/.gradle/caches/
  ├── build-cache-1/    # 本地构建缓存（任务级）
  ├── transforms-3/     # 依赖转换缓存
  ├── modules-2/        # 依赖 JAR 缓存
  └── executionHistory/ # 任务执行历史

缓存键计算：
  输入指纹 = f(源文件哈希, 依赖哈希, 类路径哈希, JVM 参数)
  → 输入不变 → 缓存命中 → 跳过执行

任务级增量：
  inputs（输入文件）→ 增量分析 → 只重编受影响的源文件
  outputs（输出目录）→ 哈希比对 → 命中则复用
```

### 14.2 远程缓存（Build Cache）

```mermaid
flowchart LR
    A[开发者A 执行构建] -->|任务输出| CACHE[(远程缓存)] 
    CACHE -->|缓存命中| B[开发者B 执行相同任务]
    B -->|跳过执行| C[直接复用缓存产物]
```

| 缓存类型 | 说明 | 适用 |
|----------|------|------|
| local | 本地磁盘缓存 | 开发机 |
| remote HTTP | HTTP 服务端缓存 | 团队共享 |
| remote S3 | S3 兼容存储 | 云上部署 |
| Develocity | Gradle Enterprise 云缓存 | 企业级 |

```bash
# 启用远程缓存
./gradlew build --build-cache \
  -Dgradle.cache.remote.url=https://cache.example.com \
  -Dgradle.cache.remote.username=$USER \
  -Dgradle.cache.remote.password=$TOKEN

# settings.gradle.kts 配置
buildCache {
    local { enabled = true }
    remote<HttpBuildCache> {
        url = uri("https://cache.example.com/")
        isPush = true  // 是否允许推送
        credentials {
            username = System.getenv("CACHE_USER") ?: ""
            password = System.getenv("CACHE_PASS") ?: ""
        }
    }
}
```

### 14.3 缓存失效策略

```
缓存失效条件（任一命中即失效）：
  ① 源文件内容变化（非时间戳，是内容哈希）
  ② 依赖版本变化（lock 文件变化）
  ③ JVM/工具版本变化
  ④ 系统属性/环境变量变化
  ⑤ 构建脚本（build.gradle）变化

防缓存错乱：
  必须用内容哈希作为缓存键（Gradle 已内置）
  不要用时间戳（可重现构建原则）
  CI 环境与本地环境用相同缓存 key（锁文件一致）
```

> **口诀**：缓存的本质是"输入哈希 → 输出复用"——锁文件变了缓存必须失效，否则"缓存命中但结果错"比慢更可怕。

## 二十五、制品晋级流程详解

### 15.1 晋级状态机

```mermaid
flowchart TB
    BUILD[CI 构建] --> SNAP[(SNAPSHOT 仓)]
    SNAP --> TEST{自动化测试通过?}
    TEST -->|否| FAIL[阻断通知]
    TEST -->|是| RC[(Release Candidate 仓)]
    RC --> STAGING{部署到 Staging?}
    STAGING -->|冒烟/压测通过| GATE{人工审批?}
    STAGING -->|失败| ROLLBACK[回滚 RC]
    GATE -->|通过| PROD[(Production 仓)]
    GATE -->|拒绝| REJECT[退回 RC]
    PROD --> DEPLOY[部署到生产]
```

### 15.2 各阶段门禁

| 晋级阶段 | 门禁条件 | 典型配置 |
|----------|----------|----------|
| snapshot → RC | 单元测试 100% 通过 + 静态扫描 0 Blocker | Maven release plugin |
| RC → staging | 集成测试 + 安全扫描 + 构建可重现验证 | Jenkins/GitLab CI |
| staging → prod | 压测通过 + 人工审批 + 变更工单 | ServiceNow/Jira |

```bash
# Maven release 全流程
mvn release:prepare    # 版本号 + Git Tag + 提交
mvn release:perform    # 部署到 release 仓库

# Gradle release（使用 release 插件）
./gradlew release -Prelease.stage=RC -Prelease.version=1.2.3-rc.1
```

### 15.3 制品不可变性保障

```
不可变制品（Immutable Artifact）原则：
  ① 已发布的版本号禁止覆盖（开启仓库 immutable 策略）
  ② SNAPSHOT 版本可变（仅开发期允许）
  ③ 镜像标签用 git SHA 或语义版本（禁止 latest）
  ④ 回滚 = 部署旧版本（不是改旧包）
```

## 二十六、SBOM 三格式深度对比

### 16.1 三种主流 SBOM 格式

| 维度 | SPDX | CycloneDX | SWID |
|------|------|-----------|------|
| 发起方 | Linux Foundation | OWASP | ISO/IEC 19770-2 |
| 格式 | RDF/XML/JSON/YAML | JSON/XML | XML |
| 覆盖范围 | 软件包 + 许可证 + 安全 | 软件包 + 漏洞 + 许可证 + 供应链 | 软件资产标识 |
| 漏洞关联 | 弱（需外挂扫描） | 强（原生 CVE 链接） | 无 |
| 许可证管理 | 强（License List） | 中 | 弱 |
| 适用场景 | 开源合规/审计 | DevSecOps/漏洞管理 | 软件资产盘点 |
| 工具支持 | Syft/FOSSA/Black Duck | Syft/Trivy/CDXGen | Microsoft/SAP |
| 标准化 | ISO/IEC 5962:2021 | OWASP 标准 | ISO 19770-2 |

### 16.2 SBOM 生成实战

```bash
# SPDX 格式
syft packages myapp:latest -o spdx-json > sbom.spdx.json

# CycloneDX 格式（推荐，漏洞关联最好）
syft packages myapp:latest -o cyclonedx-json > sbom.cdx.json

# Trivy 同时生成 SBOM + 扫描漏洞
trivy image --format cyclonedx --output sbom.json myapp:1.0
trivy sbom sbom.json --severity HIGH,CRITICAL

# SBOM 验证
cosign verify-attestation --type spdxjson sbom.spdx.json
```

### 16.3 SBOM 在流水线中的位置

```mermaid
flowchart LR
    A[源码] --> B[构建]
    B --> C[SBOM 生成]
    C --> D[漏洞扫描]
    D --> E{高危 CVE?}
    E -->|是| F[阻断发布]
    E -->|否| G[签名]
    G --> H[存入制品仓]
    H --> I[部署门禁验签]
```

> **口诀**：SBOM = 软件的"成分表"——没有它你不知道部署了什么，出了漏洞只能全网盲猜。CycloneDX 是 DevSecOps 首选。

### 17.3 漏洞管理流程

```mermaid
flowchart TB
    SCAN[漏洞扫描] --> NEW{新发现漏洞?}

    NEW -->|是| SEV{严重程度?}
    SEV -->|CRITICAL| FIX[立即修复/阻断发布]
```

| 漏洞等级 | 修复 SLA | 处置策略 |
|----------|----------|----------|

### 18.1 可复现性干扰源与对策

| 干扰源 | 症状 | 对策 | 工具 |
|--------|------|------|------|
| 系统时间 | 产物含时间戳 | `SOURCE_DATE_EPOCH=0` | 所有语言 |

| 非确定性打包 | zip/tar 内文件顺序随机 | 固定打包顺序（Go 默认确定性） | 构建工具 |
| Git 元数据 | commit hash 嵌入产物 | 外部注入，不编译期写入 | CI 注入 |

## 十一、构建缓存：本地缓存与远程缓存

缓存是加速 CI 的第一杠杆。**本地缓存**随 agent 复用；**远程缓存**（Build Cache）跨 agent / 跨流水线共享，命中即跳过编译。

| 工具 | 远程缓存 | 适用 |
|------|----------|------|
| Gradle Build Cache | `--build-cache` + 远程缓存节点 | JVM |
| Bazel Remote Cache | `remote_cache` | 多语言 |
| Docker BuildKit | `cache-to/from=type=registry` | 镜像 |
| GitHub Actions | `actions/cache` / `type=gha` | 通用 |

```bash
# Gradle 开启远程构建缓存
./gradlew build --build-cache \
  -Dgradle.cache.remote.url=https://cache.corp.com \
  -Dgradle.cache.remote.username=$USER -Dgradle.cache.remote.password=$TOKEN
```

```dockerfile
# BuildKit 远程缓存（推到镜像仓库，跨 runner 共享层）
# 构建命令：docker buildx build \
#   --cache-to=type=registry,ref=registry/app:cache \
#   --cache-from=type=registry,ref=registry/app:cache .
```

> 注意：缓存失效策略要稳——依赖变更必须使缓存失效，否则"缓存命中但构建错误"比慢更可怕。用锁文件 hash 作为缓存 key。

## 十二、Reproducible Build（可重现构建）

同输入必产同字节输出，杜绝"我机器上是好的"：

- **去时间戳**：不把构建时间写入产物（`SOURCE_DATE_EPOCH`）。
- **去绝对路径**：用相对路径，避免 `/home/ci/...` 泄漏。
- **锁依赖**：`package-lock.json` / `go.sum` / `pom.xml` 锁版本。
- **排序**：资源打包顺序固定（zip/tar 确定性排序）。
- **工具**：Go 原生 reproducible；Java 用 `reproducible-builds` 插件；Docker 用 `buildkit` + 固定 base。

```bash
export SOURCE_DATE_EPOCH=0
go build -trimpath -ldflags="-buildid=" -o app .   # -trimpath 去除路径
```

## 十四、制品签名与验签

用 cosign（sigstore）对镜像/制品签名，部署前验签，阻断未签名产物上线：

```bash
# 签名（Keyless 模式，由 Fulcio 签发短期证书）

# 生成 SBOM 证明并签名

# 部署前验签

  --certificate-identity-regexp '.*@corp.com' \
  --certificate-oidc-issuer 'https://oauth.corp.com'
```

## 十六、Docker 多阶段构建进阶

### 16.1 跨阶段文件复制

多阶段构建的核心是 `COPY --from=<stage>`，可以在阶段间传递任意文件：

```dockerfile

FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server .

FROM builder AS tester
RUN go test ./... -v            # 测试阶段复用构建产物

ENTRYPOINT ["/server"]
```

`--mount=type=cache` 让依赖安装目录跨构建持久化，即使依赖文件变化也不会全量重装：

```dockerfile
RUN --mount=type=cache,target=/root/.m2/repository \
    mvn -B clean package -DskipTests

RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

### 16.3 Secrets 安全注入

```dockerfile
# 不进镜像、不进日志的 secret 挂载
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci

# 构建命令
docker build --secret id=npmrc,src=.npmrc .
```

## 二十二、依赖供应链安全

### 22.1 依赖投毒防护

```
常见攻击向量：
  ① typosquatting（仿冒包名，如 lodash-es vs lodashe）
  ② dependency confusion（私有包名泄露，公共仓库同名包投毒）
  ③ 维护者账号被盗，上传恶意版本

防护措施：
  ① 锁文件 + 哈希校验（npm ci --prefer-offline）
  ② 私有仓库优先（scope 拦截）
  ③ 依赖来源审计（`npm audit`、`go vet`、`pip audit`）
  ④ 签名验证（npm provenance、Go checksum database）
```

### 22.2 供应链安全成熟度

| 级别 | 能力 | 对应实践 |
|------|------|----------|
| L1 | 基础 | 锁文件提交、CI 扫描 |
| L2 | 可审计 | SBOM 生成 + 制品签名 |
| L3 | 可验证 | 签名验签 + 准入控制 |
| L4 | 零信任 | SLSA 框架 + 可重现构建 + 供应链溯源 |

> 口诀：**供应链安全 = 锁文件 + SBOM + 签名 + 扫描 + 准入——缺一环都可能被投毒**。

## 二十一、Maven 依赖仲裁机制（最短路径/最先声明）冲突排查

### 21.1 Maven 依赖仲裁规则

```text
Maven 依赖冲突解决（两个规则）：
  1. 最短路径优先（Depth-First）
     A → B → C → D(1.0)
     A → E → D(2.0)
     结果：选择 D(1.0)（路径更短）

  2. 先声明优先（Declaration Order）
     同深度时，pom.xml 中先声明的依赖胜出
     <dependencies>
       <dependency>A</dependency>  <!-- 先声明 -->
       <dependency>B</dependency>
     </dependencies>
```

### 21.2 依赖冲突排查工具

```bash
# 查看依赖树
mvn dependency:tree

# 查看冲突依赖
mvn dependency:tree -Dverbose -Dincludes=commons-lang

# Maven Enforcer 插件
mvn enforcer:enforce -Drules=dependencyConvergence

# 排除冲突依赖
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>3.12.0</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

### 21.3 依赖冲突排查流程

```mermaid
flowchart TD
    A[构建报 ClassNotFoundException/NoSuchMethodError] --> B[mvn dependency:tree]
    B --> C{存在多个版本?}
    C -->|是| D[检查最短路径/声明顺序]
    D --> E[exclusion 排除或 dependencyManagement 统一版本]
    C -->|否| F[检查类路径是否正确]
    E --> G[重新构建验证]
```

## 二十二、Gradle 构建缓存原理（Task Input Snapshot → Content Hash）

### 22.1 Gradle 缓存机制

```text
Gradle Build Cache 原理：
  1. Task Input Snapshot：记录 task 的所有输入（源码、依赖、参数、环境）
  2. Content Hash：对输入计算 SHA-256 哈希
  3. 缓存查找：哈希匹配则复用缓存输出
  4. 缓存存储：task 执行后将输出存入缓存

缓存层次：
  本地缓存：~/.gradle/caches/build-cache-1/
  远程缓存：HTTP/S3/GCS 仓库
```

### 22.2 缓存配置

```groovy
// settings.gradle
buildCache {
    local {
        enabled = true
        directory = new File(rootDir, '.gradle/build-cache')
    }
    remote(HttpBuildCache) {
        url = 'https://cache.example.com/'
        credentials {
            username = 'user'
            password = 'password'
        }
        push = System.getenv('CI') != null  // 仅 CI 推送
    }
}
```

### 22.3 远程缓存配置

```yaml
# GitLab CI: Gradle 远程缓存
build:
  stage: build
  cache:
    key:
      files:
        - gradle.lockfile
    paths:
      - .gradle/caches
      - .gradle/wrapper
  script:
    - ./gradlew build --build-cache
```

## 二十六、构建可复现性要点（Reproducible Builds）

### 26.1 可复现构建原则

| 原则 | 做法 | 工具 |
|------|------|------|
| 固定依赖版本 | lock 文件锁定 | package-lock.json/go.sum |
| 固定基础镜像 | digest 引用 | `FROM image@sha256:abc...` |
| 去时间戳 | 产物不含时间信息 | `SOURCE_DATE_EPOCH` |
| 去路径依赖 | 绝对路径不影响产物 | `-trimpath`（Go） |
| 固定环境变量 | 环境变量不影响编译结果 | `LC_ALL=C` |
| 固定编译器版本 | 指定编译器版本 | `.tool-versions` |

### 26.2 可复现构建验证

```bash
# 验证构建可复现性
# 构建两次，对比产物 digest
docker build -t myapp:v1 .
SHA1=$(docker inspect --format='{{index .RepoDigests 0}}' myapp:v1)

# 清理后重新构建
docker system prune -f
docker build -t myapp:v1 .
SHA2=$(docker inspect --format='{{index .RepoDigests 0}}' myapp:v1)

# 对比 digest
[ "$SHA1" = "$SHA2" ] && echo "可复现" || echo "不可复现"
```

## 三十、Maven 依赖仲裁与版本冲突解决

### 依赖仲裁机制

| 规则 | 说明 | 示例 |
|------|------|------|
| 距离优先 | 路径最短者优先 | A→B→C→D(1.0) vs A→D(2.0) → 选 2.0 |
| 声明优先 | pom.xml 中先声明者优先 | 同距离时先写的 dependency 生效 |
| 覆盖仲裁 | `<dependencyManagement>` 强制锁定 | 统一锁定 Spring 版本 |
| exclusions | 排除传递依赖 | `excludes: log4j` |

```xml
<!-- 全局版本锁定 -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.google.guava</groupId>
      <artifactId>guava</artifactId>
      <version>32.1.3-jre</version>
    </dependency>
  </dependencies>
</dependencyManagement>
```

### Gradle 构建缓存策略

```
Gradle 缓存层级：
  本地缓存：~/.gradle/caches（开发者机器）
  远程缓存：Gradle Build Cache / Nexus（团队共享）
  增量编译：只编译变更的类

缓存命中条件：
  1. 输入不变（源码+依赖+任务配置）
  2. 任务标注 @CacheableTask
  3. 输出路径一致

配置示例：
  buildCache {
    local { enabled = true }
    remote {
      url = 'https://cache.example.com'
      push = true  // 仅 CI 可写
    }
  }
```

| 缓存类型 | 命中率目标 | 实现方式 |
|----------|-----------|---------|
| 依赖缓存 | >95% | 固定版本 + lock 文件 |
| 构建缓存 | >80% | @CacheableTask + 远程缓存 |
| Docker 层缓存 | >90% | 多阶段构建 + BuildKit |
| 测试缓存 | >70% | 只跑变更测试类 |
