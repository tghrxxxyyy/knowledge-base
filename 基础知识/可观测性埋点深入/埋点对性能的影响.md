# 埋点对性能的影响

> 对应 Kleppmann《Designing Data-Intensive Applications》关于批处理与流处理的吞吐-开销权衡，以及《Site Reliability Engineering》（Google SRE）的可观测性成本实践。

## 一、背景与挑战
可观测性本身也要消耗资源。如果埋点在业务主流程里同步执行序列化、加锁与网络发送，它就从「观测者」变成了「参与者」：每次请求都要额外付出这些开销，最终表现为延迟上升、CPU 占用增加，甚至在高并发下引发反压，让采集故障演变成业务故障。

实践中常见的三种伤害路径：

- 延迟增加：同步上报把网络往返加进关键路径，尾延迟被显著放大。
- 资源争抢：序列化、锁竞争与内存分配抢占业务线程与内存带宽。
- 故障传播：采集端不可用时，埋点抛异常或阻塞，直接导致业务请求失败。

因此核心命题是：把开销移出关键路径，并保证采集故障绝不影响业务。

## 二、核心原理
降低埋点开销的手段可归纳为五条。

- 异步化：主线程只做「入队」，序列化与发送交给后台线程/协程。
- 批处理：攒够一批再发，把每条的网络与系统调用开销摊薄。
- 采样：按概率或级别丢弃低价值数据，从源头减少工作量。
- 无锁与原子化：指标累加用原子操作而非互斥锁，减少竞争。
- 熔断与隔离：队列有界，满时丢弃并计数，绝不阻塞生产者；采集异常被捕获并降级。

一个有界队列是这套设计的核心：它在内存上限与背压之间划出边界。队列满时选择「丢弃并计数」而非「阻塞等待」，才能保证业务优先级高于观测。

## 三、形式化与数学基础
同步埋点的请求延迟为二者之和：

$$ T_{sync} = T_{biz} + T_{instr} $$

其中 $T_{instr}$ 含序列化 $T_{ser}$ 与网络发送 $T_{net}$，高 P99 场景下 $T_{net}$ 的尾部分布尤其危险。改为异步批处理后，主线程只承担入队操作 $T_{enq}$，通常为常数级：

$$ T_{async} \approx T_{biz} + T_{enq},\quad T_{enq} \ll T_{instr} $$

代价转移到后台吞吐与内存缓冲。设队列上限 $B$、单条记录大小 $s$，峰值内存为：

$$ mem_{max} = B \cdot s $$

后台处理速率必须不小于生产速率，否则队列积压直至触顶：

$$ \lambda_{produce} \le \mu_{consume} $$

当 $\lambda > \mu$ 时，队列在 $t = B / (\lambda - \mu)$ 内填满，之后按策略丢弃。批处理的摊销效果为：设批大小 $b$、单条网络开销 $c$，则单条摊销成本为：

$$ c_{eff} = c_{net} + \frac{c_{batch}}{b} $$

$b$ 越大摊销越明显，但缓冲延迟与内存也随之上升，需按 SLO 取平衡。指标累加的原子操作在无竞争时近似常数开销，远低于加锁的临界区串行化。

## 四、代码实现
主线程只入队，后台批量导出。

```python
import queue, threading

q = queue.Queue(maxsize=10000)   # 有界队列，防止内存无上限增长

def on_request(record):
    try:
        q.put_nowait(record)     # 主线程几乎零等待
    except queue.Full:
        dropped.inc()            # 满则丢弃并计数，绝不阻塞业务

def worker():
    while True:
        batch = []
        # 攒批：最多等 1 秒或攒够 512 条
        try:
            batch.append(q.get(timeout=1.0))
            while len(batch) < 512:
                batch.append(q.get_nowait())
        except queue.Empty:
            pass
        if batch:
            try:
                exporter.export(batch)   # 采集异常不影响业务
            except Exception:
                export_errors.inc()

threading.Thread(target=worker, daemon=True).start()
```

指标用原子操作累加，采样在最前端执行以省下后续开销。

```c
/* 原子自增，无锁竞争 */
__atomic_fetch_add(&http_requests_total, 1, __ATOMIC_RELAXED);

/* 尽早返回：低级别日志若不被采样，零后续开销 */
if (level < WARN && !sampled()) return;
```

## 五、与其他技术对比

| 方案 | 业务延迟影响 | 数据完整性 | 资源成本 | 复杂度 |
| --- | --- | --- | --- | --- |
| 同步上报 | 高，进入关键路径 | 高 | 中 | 低 |
| 异步 + 批处理 | 低 | 高（队列有界时有损） | 内存与后台 CPU | 中 |
| 异步 + 采样 | 低 | 中，按概率丢 | 低 | 中 |
| eBPF 无侵入 | 很低 | 高 | 内核态开销可控 | 高 |

选型原则是：核心链路优先保证业务延迟，用异步 + 批处理；数据完整性要求极高的审计场景可退回同步或加长缓冲。

## 六、常见误区
- 埋点异常未隔离：采集失败抛出到业务栈，一个 SDK bug 拖垮整个服务。

- eBPF 与运行时内建埋点：进一步降低对业务代码的侵入与开销。

## 十、小结
埋点必须异步化与隔离：主线程只入队，序列化与上报交给后台，用有界队列与丢弃策略保证永不阻塞业务。开销从关键路径转移到后台，用批处理摊薄网络成本，用采样从源头减量。目标是「既看得见，又不拖慢业务」。
