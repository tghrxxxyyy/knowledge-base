# 日志结构化与采样

> 对应 OpenTelemetry Logs 数据模型与语义约定、《Site Reliability Engineering》（Google SRE）中关于日志与采样的实践章节。

## 一、背景与挑战
日志是最古老也最通用的可观测手段，但传统做法有两个硬伤。

第一是难以机器消费。以自由文本拼装的日志，如「user 42 paid 99.9 at 12:03」，要提取字段只能靠脆弱的正则，字段增删或措辞变化就会让解析规则失效。

第二是成本失控。高流量系统每秒产生海量日志，全量长期保存的费用往往超过业务服务器本身；而其中大部分是重复的健康请求日志，真正关键的只有错误与异常路径。若不加以采样与分级，关键信息会被淹没在噪音里，排查时反而更难。

结构化与采样正是针对这两点：用固定 schema 让机器可解析，用分级采样把成本压到可接受区间。

## 二、核心原理
结构化日志的核心，是把「一句话」换成「一条记录」：每条日志是一个带字段的对象，通常以 JSON 或 logfmt 编码，包含时间戳、级别、消息、以及若干业务字段。字段名遵循统一约定（如 trace_id、span_id、service.name），才能与追踪、指标关联。

采样则回答「哪些日志值得留下」。常见策略包括：

- 按级别采样：ERROR/FATAL 全采，INFO/DEBUG 按概率采。
- 按速率采样：同一模式每秒最多保留 N 条，抑制突发重复。
- 错误优先：任何带异常、非 2xx 的日志无条件保留。
- 按 trace 一致性采样：与追踪的采样决策对齐，保证「被采样的请求其日志也完整」。

一条重要原则是：采样只能丢弃「可再生的噪音」，绝不能丢弃定位问题所需的上下文。日志与追踪共享 trace_id/span_id，才能从告警跳到日志再跳到调用链。

## 三、形式化与数学基础
设日志流为 $L$，采样函数 $s: L \to \{0,1\}$，保留集合为：

$$ retained = \{\, l \in L \mid s(l) = 1 \,\} $$

若采样的保留概率为 $p$，则保留量的期望与方差为：

$$ \mathbb{E}[|retained|] = p\,|L|,\qquad \mathrm{Var} = |L|\,p(1-p) $$

分级采样可写成分段函数：设日志级别为 $\ell$，阈值以上全采、以下按概率采：

$$ p(\ell) = \begin{cases} 1.0, & \ell \ge ERROR \\ p_{info}, & \ell = INFO \\ p_{debug}, & \ell = DEBUG \end{cases} $$

采样带来的代价是估计偏差：若用采样后的错误率 $\hat{r}$ 估计真实错误率，则需按 $p$ 还原：

$$ \hat{r}_{true} \approx \frac{r_{sampled}}{p} $$

这就是为什么「采样率」本身必须是可观测的元数据——否则看到的分位数与错误率都会被系统性扭曲。信息论视角下，日志的熵越低（越重复），可压缩与可采样的空间越大。

## 四、代码实现
以结构化方式输出日志，并附加追踪上下文。

```python
import logging, json

log = logging.getLogger("checkout")

def log_event(event, level="info", **fields):
    # 结构化输出，避免字符串拼接
    record = {"event": event, "service": "checkout", **fields}
    getattr(log, level)(json.dumps(record, ensure_ascii=False))

log_event("pay.ok", order_id=oid, amount=99.9, ms=12)
```

按级别与概率采样，且错误全采：

```python
import random

def should_emit(level, p_info=0.1, p_debug=0.01):
    # 错误日志无条件保留，健康路径按概率采样
    if level in ("ERROR", "FATAL"):
        return True
    if level == "INFO":
        return random.random() < p_info
    return random.random() < p_debug

def emit(level, log):
    if should_emit(level):
        sink.write(log)          # 保留 trace_id 等关联字段
```

与追踪对齐时，应在日志字段中带上 trace_id 与 span_id，使日志可被 Trace 视图反向检索。

## 五、与其他技术对比

| 维度 | 结构化日志 | 非结构化文本日志 | 指标 | 追踪 |
| --- | --- | --- | --- | --- |
| 机器可解析 | 强 | 弱，依赖正则 | 强 | 强 |
| 字段灵活度 | 高 | 高但难检索 | 低 | 中 |
| 成本 | 中高，可采样 | 高 | 低 | 高 |
| 关联能力 | 依赖 trace_id | 弱 | 依赖标签 | 自带因果 |
| 典型用途 | 明细排查、审计 | 临时调试 | 趋势告警 | 链路定位 |

三者协同：指标发现异常，追踪定位链路，日志解释细节。

## 六、常见误区
- 在热路径拼接大对象并序列化：JSON 编码与字符串拼接都在主线程，直接增加延迟。
- 采样把上下文一起丢掉：只保留消息不保留 trace_id，导致无法与追踪关联。
- 采样率不记录：事后无法还原真实错误率与分位数，得出结论失真。
- 把敏感信息写入日志：手机号、token、卡号落盘，带来合规风险。
- 级别滥用：全用 INFO 打日志，导致分级采样形同虚设。
- 时间戳本地化不一致：跨时区服务未统一为 UTC，排序与关联出错。

## 九、演进与趋势
- 日志、指标、追踪共享同一上下文（trace_id/span_id），告警可直达 trace 与日志。
- OpenTelemetry Collector 统一做日志的批处理、脱敏与路由，降低对业务进程的侵入。
- 日志解析前移到采集端，端侧即完成结构化，减少后端解析成本。

## 十、小结
结构化让日志可被机器消费，采样让成本可控。二者的组合必须以「错误优先、上下文完整」为底线：错误与异常路径全采，健康路径按概率采，采样率作为元数据保留。日志、指标、追踪三者的上下文打通，才是现代可观测性的完整形态。
