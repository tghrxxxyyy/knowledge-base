# 指标埋点的维度设计

> 对应 OpenTelemetry Metrics 语义约定、Prometheus 数据模型，以及 Tom Wilkie 的 RED 方法与 Brendan Gregg 的 USE 方法。

## 一、背景与挑战
只上报一个全局总数，就像只拿到一张体检总评：知道「有问题」，却说不清问题出在哪个服务、哪个接口、哪个地域。指标必须携带维度（标签）才能下钻切片，否则可观测性会退化成黑盒。

但维度不是越多越好。时序数据库对每个「标签取值组合」都维护一条独立时间序列，若把 user_id、request_id 这类高基数字段当标签，序列数量会随流量线性甚至指数膨胀，最终拖垮存储、拖慢查询。维度设计的本质，是在「诊断能力」与「基数成本」之间做权衡。

## 二、核心原理
一条指标样本由三部分构成：指标名、数值、以及一组标签（key=value）。理解以下几个要点即可把握设计准则。

- 语义稳定的维度：service、endpoint、method、status、region 这类取值集合有限且长期稳定的字段，是理想维度。
- 低基数优先：一个维度的取值个数应可控，避免把业务主键（uid、order_id、trace_id）当标签。
- 命名统一：同一含义在跨服务间要用同一套语义约定，否则维度无法关联聚合。
- 指标类型匹配语义：计数器（Counter）只增不减用于请求数、错误数；直方图（Histogram）用于延迟分布；可增减的用 UpDownCounter；瞬时值用 Gauge。
- 聚合可加性：Counter 与 Histogram 满足可加性，便于在任意维度上求和；Gauge 通常不可加。

RED 方法关注请求侧：Rate（速率）、Errors（错误）、Duration（耗时）。USE 方法关注资源侧：Utilization（利用率）、Saturation（饱和度）、Errors（错误）。两者互补，一个面向服务、一个面向资源。

## 三、形式化与数学基础
一条指标可形式化为三元组：

$$ m = (name,\ value,\ \{k_1{:}v_1,\ \dots,\ k_n{:}v_n\}) $$

设维度 $k_i$ 的取值个数为 $|D_i|$，则理论时间序列数为各维度基数的乘积：

$$ S = \prod_{i=1}^{n} |D_i| $$

这就是基数爆炸的来源：即便每个维度只取 20 个值，5 个维度相乘也有 $20^5 = 3.2\times10^6$ 条序列。工程上常要求 $S$ 保持在一个可管理量级（具体阈值以各时序库官方文档为准）。

计数器在一次统计窗口 $[t_0, t_1]$ 上的速率定义为：

$$ rate = \frac{\Delta C}{\Delta t},\quad \Delta C = C(t_1) - C(t_0) $$

直方图用一组桶边界把观测值分箱，第 $j$ 个桶的占比近似为其累积分布：

$$ P(X \le b_j) \approx \frac{c_j}{\sum_k c_k} $$

据此可估算分位数（如 P95/P99），而无需保留原始样本，代价是精度受桶粒度限制。

## 四、代码实现
OpenTelemetry 中以带维度的方式记录计数与直方图。

```python
from opentelemetry import metrics

meter = metrics.get_meter("checkout")

# 计数器：只增，适合请求数、错误数
orders = meter.create_counter(
    "http.server.requests", unit="{request}",
)
# 直方图：适合延迟分布
latency = meter.create_histogram(
    "http.server.duration", unit="ms",
)

def handle(method, route, status, ms):
    # 维度保持低基数：method/route/status 取值有限
    attrs = {"http.method": method, "http.route": route,
             "http.status_code": status}
    orders.add(1, attrs)
    latency.record(ms, attrs)
```

避免反例：

```python
# 反例：把高基数主键当维度，序列数随用户数爆炸
orders.add(1, {"user_id": uid})      # 数以百万计的新序列

# 正例：改用有限枚举，必要时用日志/追踪补细节
orders.add(1, {"user_tier": "gold"})
```

延迟直方图配置桶边界时要覆盖业务关心的区间，过粗会丢失尾延迟信息，过细则增加序列与存储成本。

## 五、与其他技术对比

| 方案 | 存储成本 | 聚合速度 | 下钻能力 | 适用场景 |
| --- | --- | --- | --- | --- |
| 带低基数维度的指标 | 低 | 快 | 中 | 趋势、容量、告警 |
| 高基数指标 | 很高 | 慢 | 高 | 慎用，常被时序库限制 |
| 结构化日志 | 中高 | 慢 | 很高 | 明细排查、审计 |
| 分布式追踪 | 高 | 慢 | 高 | 单请求链路定位 |

结论是分工：用低基数指标做「发现」，用日志与追踪做「解释」，不要把高基数细节硬塞进指标。

## 六、常见误区
- 把 user_id / request_id / trace_id 当标签，导致基数爆炸，属于最典型事故。
- 维度命名各写各的，service 与 svc、method 与 http.method 混用，跨服务无法聚合。
- 只埋总量不埋维度，事后想下钻时发现没有数据，只能回滚重发布。
- 指标类型选错：用 Gauge 统计累计请求数，重启归零、无法求速率。
- 维度取值不受控：把 URL 原始路径（含 id）直接当 route，等价于高基数。
- 忽略单位与语义约定，导致跨团队数据不可比。

## 七、与开源书·权威来源对应
- OpenTelemetry Metrics 语义约定给出了 HTTP、RPC、数据库等领域的标准维度名。
- Prometheus 官方文档系统解释了标签、时间序列与基数问题，并给出 best practices。
- Tom Wilkie 提出的 RED 方法（Rate/Errors/Duration）面向请求侧监控。
- Brendan Gregg 提出的 USE 方法（Utilization/Saturation/Errors）面向资源侧监控。
- 《Site Reliability Engineering》（Google SRE）讨论了 SLO 与指标的关系。

## 九、演进与趋势
- 自动埋点（Auto-Instrumentation）：框架层透明采集标准指标，减少手工遗漏。
- Exemplar 与指标-追踪联动：让聚合曲线可一键跳到具体样本。
- OpenTelemetry 语义约定持续标准化，跨厂商可比性增强。
- 在时序侧引入更高效的基数治理与降采样策略，缓解高基数压力。

## 十、小结
埋点维度决定可观测性的下钻能力。设计铁律是「低基数、语义一致、类型匹配」：用有限枚举维度支撑聚合与告警，把高基数细节交给日志与追踪。指标负责发现异常，维度负责定位范围，两者配合才能既看得见又说得清。
