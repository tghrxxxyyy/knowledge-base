# 滚动更新与回滚策略

> 对应 Kim et al. 2016《Accelerate》与《The DevOps Handbook》中关于缩短恢复时间（MTTR）与渐进式部署的论述，以及 Kubernetes 滚动更新实践。

## 一、背景与挑战

一次性替换所有实例会中断服务（容量骤降或短暂停机）；而回滚若缓慢会放大故障影响面、延长 MTTR。滚动更新在「资源占用」与「可用性」之间折中，是多数无状态服务的默认策略。

挑战：(1) 批次过大导致瞬时容量不足、健康检查失败连锁雪崩；(2) 新旧版本并存期间的兼容（见数据兼容）；(3) 回滚时若已推进多批，需逐批倒回或快速拉旧副本；(4) 就绪探针配置不当导致流量打到未就绪实例。

## 二、核心原理

滚动更新（rolling update）逐批以新实例替换旧实例，维持整体容量不低于阈值；每批先启动新实例、等其就绪并通过探针后再摘下等价数量的旧实例（maxSurge/maxUnavailable 控制节奏）。回滚则反向逐步恢复旧版，或借助保留的可用旧副本/镜像快速拉起。

Kubernetes Deployment 用 `strategy.rollingUpdate` 表达：maxSurge 允许超出期望的实例数，maxUnavailable 允许不可用的实例数，二者共同决定每批步长与容量底线。

maxSurge 与 maxUnavailable 的取舍体现容量与资源的权衡：设 maxSurge>0 允许临时多起实例，容量不跌但需要额外资源；设 maxUnavailable>0 允许部分实例先下线，省资源但容量短时下降。常见做法是镜像式滚动（maxSurge=N, maxUnavailable=0）保证零容量损失，资源紧张时再放开 maxUnavailable。优雅下线（graceful shutdown）决定回滚是否在途请求被切断：preStop 钩子应先从负载均衡摘流量（drain），再等待 in-flight 请求完成，最后进程退出；readinessProbe 失败即停止接新流。若只配置 liveness 而不配 readiness，Kubelet 可能在进程仍处理请求时误杀，造成 5xx 突增。回滚本身有两种形态：其一是 rollout undo 反向滚动（逐批换回旧镜像），其二是保留旧 ReplicaSet 直接切回（类蓝绿）。若发布已推进多批且数据层不兼容，回滚需与数据 contract 配合（见回滚的原子性）。把 MTTR 作为首要指标，优于追求零缺陷。实践中建议为关键服务设定「滚动最长时长」与「探活失败阈值」，超过即自动暂停并告警，防止半 finished 状态长时间拖累容量。

滚动过程中应监控错误率与延迟，异常时自动暂停（pause）而非继续推进。

与就绪探针配合的流量摘除，应在实例真正就绪前绝不接流，防止请求打到空实例。

## 三、形式化与数学基础

设实例数 $N$，批次大小 $b=\max(\text{maxSurge}+\text{maxUnavailable})$。滚动完成需步数：

$$k = \left\lceil \frac{N}{b} \right\rceil$$

每步保证在线实例 $\ge N - b$（最坏情况），需满足容量约束：

$$N - b \ge N \cdot (1 - \epsilon_{\mathrm{cap}})$$

即 $b \le N \cdot \epsilon_{\mathrm{cap}}$（$\epsilon_{\mathrm{cap}}$ 为可容忍容量损失比例）。回滚步数同理，但若保留旧镜像可瞬时切换路由（类蓝绿）。

## 四、代码实现

```bash
# 触发滚动更新
kubectl set image deploy/app app=img:v2 --record
# 观察节奏与可用度
kubectl rollout status deploy/app
# 异常时回滚到上一版本（基于 revision 历史）
kubectl rollout undo deploy/app
# 查看历史以精确回退
kubectl rollout history deploy/app
```

注意：需配置合理的 readinessProbe 与 preStop 钩子（先摘流量再下线），否则请求会打到未就绪或正在退出的实例。

## 五、与其他技术对比

| 策略 | 资源 | 切换彻底 | 回退速度 | 容量 |
|------|------|----------|----------|------|
| 蓝绿 | 双倍 | 彻底 | 快 | 稳 |
| 滚动 | 省 | 渐进 | 中 | 波动 |
| 重建 | 低 | 中断 | 慢 | 跌 |

## 六、常见误区

- 批次过大导致瞬时容量不足、健康检查失败连锁。
- 回滚时数据库 schema 已变更，旧代码不兼容（见数据兼容）。
- 忽略 preStop 优雅下线：在途请求被切断。
- 用 liveness 替代 readiness：探针语义混用导致误杀。

## 九、演进与趋势

结合就绪探针与流量摘除（如 Istio 的 drain），实现「先停流量再下线」的平滑滚动；与渐进式交付（Argo Rollouts）结合，把滚动与金丝雀分析统一。具体以官方最新文档为准。

滚动更新与回滚的本质是用可控节奏换取可用性与资源的平衡。
把 MTTR 作为首要 SLO，滚动策略的一切参数都应服务于缩短恢复时间。
配合健康探针与流量摘除，滚动可做到用户无感的平滑变更。

## 十、小结

滚动更新在资源与可用性间折中，回滚策略必须和数据演进一并设计。配合探针、优雅下线与前向兼容 schema，才能把 MTTR 压到最低。
