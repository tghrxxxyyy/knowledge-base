# 滚动更新与回滚策略

> 对应 Kim et al. 2016 (Accelerate / The DevOps Handbook)。

## 一、背景与挑战
一次性替换所有实例会中断服务，而回滚若缓慢会放大故障影响面。

## 二、核心原理
滚动更新逐批以新实例替换旧实例，维持整体容量；回滚则反向逐步恢复旧版，或借助可用旧副本快速拉起。

## 三、形式化与数学基础
设实例数 N，批次大小 b。滚动完成需 ceil(N/b) 步。每步保证在线实例 >= N - b，从而容量不跌破阈值。

## 四、代码实现
```bash
kubectl set image deploy/app app=img:v2 --record
# 控制节奏与可用度
kubectl rollout status deploy/app
# 异常回滚到上一版本
kubectl rollout undo deploy/app
```

## 五、与其他技术对比
相比蓝绿（双倍资源），滚动更省资源但切换不彻底；回滚速度通常慢于蓝绿的一次路由切换。

## 六、常见误区
- 批次过大导致瞬时容量不足、健康检查失败连锁。
- 回滚时数据库 schema 已变更，旧代码不兼容。

## 七、与开源书/权威来源对应
The DevOps Handbook 强调缩短恢复时间（MTTR）比追求零缺陷更重要。

## 八、面试题
滚动更新如何保证容量？回滚时数据兼容性如何处理？

## 九、演进与趋势
结合就绪探针与流量摘除，实现"先停流量再下线"的平滑滚动。

## 十、小结
滚动更新在资源与可用性间折中，回滚策略必须和数据演进一并设计。
