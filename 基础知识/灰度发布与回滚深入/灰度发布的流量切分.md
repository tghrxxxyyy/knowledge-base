# 灰度发布的流量切分

> 对应 Kim et al. 2016《Accelerate》与《The DevOps Handbook》中渐进式交付（progressive delivery）原则，以及 Istio/Envoy 流量治理实践。

## 一、背景与挑战

新版本直接全量上线风险高：一旦有缺陷，影响面是 100% 用户，故障恢复成本随暴露时间指数上升。理想做法是在真实流量下小范围验证，确认无碍再逐步放大。这就是灰度（canary / progressive rollout）的核心动机。

挑战：(1) 切分维度选错会让同一用户在不同请求落到不同版本，造成状态错乱与体验不一致；(2) 比例长期停在低值不推进，失去统计意义；(3) 晋级条件靠人工拍板，反应慢且不一致；(4) 多版本并存下的可观测性。

## 二、核心原理

灰度按某个稳定维度（用户 ID、地域、设备、请求头、账户等级）把部分流量导入新版本，其余留在稳定版。常用做法是哈希该维度得到稳定分桶，使同一用户始终命中同一版本。切分比例从 1% → 5% → 25% → 50% → 100% 平滑推进，每一步都依赖监控指标（错误率、延迟、业务转化）决定是否晋级。

流量切分本质是「路由层决策」，与功能开关（代码路径）不同：它作用于部署版本而非代码分支。底层可由网关/Service Mesh 的权重路由或一致性哈希实现。

切分维度的选择直接决定灰度质量：用用户 ID 哈希能保证同一用户始终命中同一版本，避免购物车、登录态跨版本错乱。
除用户 ID 外，也可按设备类型、地域、账户等级切分，但要确保维度稳定且能映射到分桶。
随机权重（非哈希）适合无状态只读场景，而有状态会话必须哈希，否则体验断裂。
晋级节奏应「慢开始、快结束」：早期小比例多观察，确认稳定后加速放大，缩短整体暴露窗口。
每步晋级的判据需量化（错误率、延迟、业务转化），由金丝雀分析驱动而非人工拍板。
若某步指标异常，应自动暂停并缩回上一比例，而非硬推到 100%。
灰度还应与发布门禁结合：只有前一比例通过健康窗，才允许进入下一比例。
对关键业务，灰度比例可与功能开关联动，先放量再开能力，进一步隔离风险。
灰度期间建议保留旧版本实例（不立即缩容），以便异常时秒级切回。
监控上需区分「新版本自身指标」与「整体指标」，避免被稳定版稀释而漏判。
多区域部署时，建议逐区域灰度，先在非核心区域验证再扩到核心区域。
灰度的终态是 100% 后旧版本下线，但下线前应保留足够回退证据（镜像、配置版本）。

## 三、形式化与数学基础

设总流量归一为 1，版本 $v$ 的流量占比为 $r_v$，且 $\sum_v r_v = 1$。灰度过程是一序列占比：

$$r_{v_2}: 0.01 \to 0.05 \to 0.25 \to 0.50 \to 1.0$$

每一步晋级需满足监控指标在阈值内：

$$\forall m \in M,\; \mathrm{metric}_m(\text{canary}) \le \tau_m \Rightarrow \text{promote}$$

为保证用户体验一致，要求分桶函数 $h(u)$ 稳定：

$$\mathrm{version}(u) = v_2 \text{ 当 } h(u) \bmod 100 < r_{v_2}\cdot 100 \text{，否则 } v_1$$

即对用户 ID 取模，低于当前百分比的进新版本，且 $h$ 不随请求变化。

## 四、代码实现

Istio VirtualService 按权重分流（概念配置）：

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: app-route
spec:
  hosts: ["app.example.com"]
  http:
    - route:
        - destination: { host: app, subset: v1 }   # 稳定版
          weight: 90
        - destination: { host: app, subset: v2 }   # 灰度版
          weight: 10
```

若按用户一致性哈希（而非随机权重），用 DestinationRule 的 consistentHash 指向同一 subset。注意：weight 之和必须为 100，且需配套的就绪探针与指标采集才能驱动自动晋级。

## 五、与其他技术对比

| 策略 | 切换方式 | 风险 | 资源 | 回退 |
|------|----------|------|------|------|
| 全量 | 一次性 | 高 | 省 | 慢 |
| 蓝绿 | 路由切换 | 中 | 双倍 | 快 |
| 灰度 | 比例渐进 | 低 | 省 | 中 |
| 功能开关 | 代码路径 | 低 | 省 | 秒级 |

## 六、常见误区

- 切分维度选择不当：用随机权重而非用户哈希，导致用户跨请求版本跳变、购物车/会话错乱。
- 灰度比例长期停在低值不推进：样本不足，统计无意义。
- 只看成功率不看业务指标：错误率正常但转化率下滑被忽略。
- 忘记回退路径：晋级自动化但回滚仍需人工。

## 九、演进与趋势

与 Feature Flag 结合可按用户属性做更精细的渐进式交付；与自动金丝雀分析（如 Flagger、Argo Rollouts）结合实现指标驱动晋级；与服务网格细粒度路由结合支持按请求头/地域精准投放。具体以官方最新文档为准。

## 十、小结

灰度用可控流量暴露问题，切分维度的稳定性与晋级条件的量化共同决定其安全边界。它是渐进式交付的基础实践，应与可观测性和自动分析闭环配合。
