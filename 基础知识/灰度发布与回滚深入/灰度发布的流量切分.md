# 灰度发布的流量切分

> 对应 Kim et al. 2016 (Accelerate / The DevOps Handbook)。

## 一、背景与挑战
新版本直接全量上线风险高，一旦有缺陷影响面大。需要在真实流量下小范围验证再逐步放大。

## 二、核心原理
按维度（用户 ID、地域、设备、请求头）把部分流量导入新版本，其余留在稳定版。切分粒度从 1% 到 100% 平滑推进，全程可观测。

## 三、形式化与数学基础
设总流量 1，版本 v 占比 r_v。灰度过程为序列 r_v: 0.01 -> 0.1 -> 0.5 -> 1.0，每步满足监控指标在阈值内才晋级。

## 四、代码实现
```yaml
# Istio VirtualService 按权重分流
http:
  - route:
    - destination: { host: app, subset: v1 }
      weight: 90
    - destination: { host: app, subset: v2 }
      weight: 10
```

## 五、与其他技术对比
相比蓝绿（全或无），灰度更平滑、风险更低；相比功能开关，它作用于部署版本而非代码路径。

## 六、常见误区
- 切分维度选择不当，使同一用户在不同请求落到不同版本，造成状态错乱。
- 灰度比例长期停在低值不推进，失去验证意义。

## 七、与开源书/权威来源对应
The DevOps Handbook 把小批量、循序渐进作为降低风险的核心原则；Accelerate 强调可恢复性优于预防。

## 八、面试题
灰度按用户 ID 哈希有什么好处？如何保证同一用户体验一致？

## 九、演进与趋势
与 Feature Flag 结合，可按用户属性做更精细的渐进式交付。

## 十、小结
灰度用可控流量暴露问题，切分维度与晋级条件决定其安全边界。
