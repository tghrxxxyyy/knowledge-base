# 金丝雀分析的指标判定

> 对应 Humble & Farley 2010《Continuous Delivery》中自动化验收测试驱动发布决策，以及 Argo/Flagger 金丝雀分析实践。

## 一、背景与挑战

金丝雀发布把少量流量导向新版本，但「何时算安全」不能靠拍脑袋。人工观察慢、不一致、容易漏掉隐性劣化（如延迟升而成功率不变）。需要量化判定晋级或回滚。

挑战：(1) 样本量小导致指标波动大，易误判；(2) 多指标冲突（错误率正常但 P99 飙升）；(3) 基线本身在漂移，固定阈值失效；(4) 业务指标（转化、留存）滞后于技术指标。

## 二、核心原理

采集金丝雀与基线版的对比指标：错误率、延迟 P99/P95、吞吐量、CPU/内存、业务转化率等。用统计方法判断是否显著劣化，自动决策晋级或回退。常见做法是「对比同一时段两版指标」，结合置信区间避免抖动误判，再由控制器（Flagger / Argo Rollouts）执行路由切换。

分析可分两类：(1) 阈值型——超阈值即失败；(2) 对比型（A/B 统计检验）——用 t 检验/卡方判断差异显著性。

样本量设计是分析可靠性的前提：错误率本身低频，若金丝雀只接 1% 流量，要检出相对 20% 的错误率上升需要足够请求数，否则置信区间过宽、判定无意义。实践中常按「最小可检测效应（MDE）」反推所需流量与时长，并在流量不足时延长观察而非草率晋级。多维指标的聚合也需谨慎：简单的「任一超阈即失败」易因单指标抖动误回滚；更稳的做法是加权健康分，并对每个指标做「相对基线」的统计检验（如 Mann-Whitney 检验延迟分布），只有显著劣化才计入。业务指标（转化、留存）通常滞后且噪声大，宜作为「人工确认」项而非自动回滚触发项。基线漂移是固定阈值的死穴：大促或故障期间基线本身异常，固定阈值会误报。改进是用「同期对比」——同一时段金丝雀与稳定版对比，或用历史同段预测自适应基线，只在偏离自适应基线显著时才告警。自动晋级还需设「观察窗口」与「晋升步长」，避免一夜之间从 1% 跳到 100%。

## 三、形式化与数学基础

设基线错误率 $e_b$，金丝雀错误率 $e_c$，相对阈值 $\delta$。判定：

$$\frac{e_c - e_b}{e_b} > \delta \Rightarrow \text{rollback}$$

延迟用相对提升或绝对阈值；为避免小样本抖动，需样本量 $n$ 满足最小统计功效，且用置信区间 $[L,U]$：

$$\text{若 } U_{e_c} > \tau \text{ 或 } \frac{\bar e_c}{\bar e_b} > 1+\delta \text{ 在 } 95\% \text{ CI 下显著} \Rightarrow \text{回滚}$$

多维指标可加权聚合为健康分 $H = \sum_k w_k \cdot \mathrm{norm}(m_k)$，低于门限即失败。

## 四、代码实现

Flagger 金丝雀分析（概念配置）：

```yaml
analysis:
  interval: 1m
  threshold: 5            # 连续 5 次分析失败才回滚
  metrics:
    - name: error-rate
      threshold: 1        # 错误率超过 1% 即失败
    - name: latency-p99
      threshold: 500      # P99 超过 500ms 即失败
  webhooks:
    - name: approve
      url: http://approval/svc
```

注意：threshold（连续失败次数）用于抗抖动；指标需由 Prometheus 等采集且与金丝雀实例正确关联，否则误判。

## 六、常见误区

- 仅用成功率忽略延迟：用户体感已变差却仍在晋级。
- 样本量过小：指标波动大，一次尖刺就误回滚。
- 固定阈值不随基线漂移：大促期基线本就高，误判。
- 只看技术指标忽略业务：转化掉了没发现。

## 九、演进与趋势

引入机器学习做异常检测，从固定阈值走向自适应基线（如基于历史同段预测）；多维指标用加权健康分与因果归因结合。具体以官方最新文档为准。

## 十、小结

金丝雀分析把发布决策建立在对比指标之上，是渐进式交付的闭环大脑。它需兼顾样本量、多指标与基线漂移，并以连续判定抗抖动。
