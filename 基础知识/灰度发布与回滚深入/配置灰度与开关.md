# 配置灰度与开关

> 对应 Fowler 2002/2003 (Patterns of Enterprise Application Architecture)。

## 一、背景与挑战
即使代码全量上线，也可能因配置错误（限流阈值、开关）引发故障。配置需要像代码一样可灰度、可回退。

## 二、核心原理
将配置从代码中剥离到配置中心，支持按环境、集群、实例维度下发不同值；危险配置先小范围生效，异常时秒级回退。

## 三、形式化与数学基础
配置 c 作用域为集合 S。灰度即 c 先在 S_small 生效，再扩展到 S_all。回退即把 c 还原为 c_prev，且不依赖重新部署。

## 四、代码实现
```java
// 从配置中心动态读取，无需重启
int limit = config.getInt("rate.limit", 1000);
if (qps > limit) reject();
// 动态调整：把 limit 改为 500 立即在灰度集群生效
```

## 五、与其他技术对比
相比改代码发版，配置灰度秒级生效；相比 Feature Flag，它偏运维参数而非功能路径。

## 六、常见误区
- 配置缺乏类型与校验，错误值导致启动即崩溃。
- 多数据中心配置不一致，引发区域差异故障。

## 七、与开源书/权威来源对应
Fowler PoEAA 将配置外置作为企业应用的基础实践。

## 八、面试题
配置中心与启动参数如何配合？配置变更如何做灰度与回滚？

## 九、演进与趋势
配置即代码（GitOps）+ 配置校验流水线，把配置变更纳入评审与审计。

## 十、小结
配置灰度让运维参数具备发布级别的可控性，是降低变更风险的低成本手段。
