# 回滚的原子性与数据兼容

> 对应 Humble & Farley 2010《Continuous Delivery》中关于数据库变更可回滚性的论述，以及扩展/收缩（expand/contract）迁移模式。

## 一、背景与挑战

回滚不只是把代码退回去，还可能涉及数据库 schema、缓存结构、消息格式。最危险的场景：新版本写入了旧版本不认识的 schema 或数据形状，回滚后旧代码读到不兼容数据直接报错，回滚「失败」反而放大故障。

挑战：(1) 删列/改类型使旧代码失效；(2) 缓存中新旧格式混存；(3) 消息队列中残留新格式事件被旧消费者处理；(4) 回滚演练不足，真实故障时才发现退路不通。

## 二、核心原理

采用可回滚的变更策略：schema 变更前向兼容（先加字段不改旧、不删旧），应用支持新旧版本并行运行；必要时提供补偿迁移而非简单丢弃。核心原则是「演进可进退」：每一步变更都能独立前进或后退。

标准模式是扩展/收缩（expand/contract）：先扩展（expand，双写、加字段、新旧兼容），稳定后收缩（contract，删旧）。回滚只发生在 expand 阶段，此时新旧都兼容，安全。

expand/contract 的「扩展」阶段具体做法是双写与双读：新字段加为可空后，写路径同时写旧列与新列，读路径先读新列、新列缺失时回退旧列。这样无论流量在旧版还是新版，读写都不报错。待确认所有写路径都已上新、且监控无旧列缺失异常后，再进入「收缩」阶段删除旧列。契约层面的兼容同样重要：若服务间用消息队列，事件 schema 也应向前兼容——新增字段设为可选、不删不改已有字段语义；消费方用「忽略未知字段」的解析策略。否则旧消费者读到新格式事件仍会失败，回滚窗口内消息成为隐患。演练是把「可回滚」从假设变事实的关键：发布流程应包含回滚演练（failure drill），故意在 expand 阶段触发回滚，验证旧版本读新数据不报错、监控无异常。许多团队只测「前进」不测「后退」，结果真实故障时才发现 contract 不兼容。把回滚纳入发布门禁，与前进同等对待，才能在事故来临时真正做到秒级退路。此外，缓存层的兼容性常被忽略：旧版本写入的缓存 key/value 格式若被新版改变，回滚后读缓存也会出错，应一并对缓存做前向兼容或带版本号隔离。

回滚演练应记录在 runbook，明确每一步验证点与中止条件。

## 三、形式化与数学基础

设版本 $v$ 能读写数据形态 $D(v)$。可回滚要求 $v_{\mathrm{new}}$ 写出的数据 $D(\mathrm{new})$ 仍能被 $v_{\mathrm{old}}$ 读取（向后兼容）：

$$D(\mathrm{new}) \subseteq \mathrm{readable}(v_{\mathrm{old}})$$

即新版本只「新增可选字段」、不强制旧版本理解、不改既有字段语义。双写阶段：

$$\text{write}(x):\; \text{old\_schema}(x) \land \text{new\_schema}(x)$$

保证任一版本读都不报错。contract 阶段确认无旧版本后再删旧字段。

## 四、代码实现

```sql
-- 可回滚的扩展：先加可空列，旧代码忽略它
ALTER TABLE orders ADD COLUMN note VARCHAR(255) NULL;
-- 新版本开始写入 note；旧版本仍只读旧列，不报错
-- 稳定后（确认无旧版本）再收缩：
-- ALTER TABLE orders DROP COLUMN legacy_field;
```

注意：避免在回滚窗口内执行 DROP/重命名/改类型；破坏性变更必须排在 contract 阶段且确认旧版本已下线。

## 五、与其他技术对比

| 策略 | 风险 | 复杂度 | 适用 |
|------|------|--------|------|
| 代码+数据一起回滚 | 高 | 低 | 小系统 |
| 前向兼容变更 | 低 | 中 | 主流 |
| 双写+补偿 | 低 | 高 | 强一致 |

## 六、常见误区

- 删除列或改列类型后再回滚：旧代码直接报错。
- 假设回滚总能成功：未演练导致真实故障时卡住。
- 只测前进不测后退：contract 阶段才发现不兼容。
- 忽略缓存/消息格式：数据层兼容但缓存击穿。

## 七、与开源书·权威来源对应

- Humble & Farley 2010《Continuous Delivery》——数据库变更最难回滚，需单独设计。
- 扩展/收缩（parallel change）模式——Martin Fowler 提出的演进式迁移。
- 蓝绿部署文献——数据层共享时的兼容处理。

## 九、演进与趋势

展开/折叠（expand/contract）成为标准；结合在线 schema 变更工具（如 gh-ost、pt-osc）实现无锁迁移；数据契约（data contract）与版本化事件让消息格式也可进退。具体以官方最新文档为准。

数据兼容是回滚能否成功的最终裁判，许多回滚失败都源于忽略 schema。
把 expand/contract 写入发布规范，可系统性消除这类隐性故障。
每次发布都应明确回答：旧版本读新数据会报错吗？若不会，退路才成立。
数据契约的版本号应随代码版本同步演进，便于追溯与回退对齐。

## 十、小结

回滚的难点在数据与契约兼容，发布前必须明确「退路」是否成立。前向兼容 + 双写 + 演练是把回滚从「赌运气」变成「可验证」的关键。
