# 堆管理与空闲链表

> 对应 Arpaci-Dusseau《Operating Systems: Three Easy Pieces》第 16–17 章（Free Space Management / Memory API）、Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 9.9 章动态内存分配、Silberschatz《Operating System Concepts》内存管理章。

## 一、背景与挑战
用户态堆必须先从内核批量要内存（`brk`/`sbrk` 或 `mmap`），再自行切分、复用、回收。这带来三重约束：分配要快（常在热路径上）、内存占用要低（不能为每个请求向内核要一页）、碎片要可控（长尾碎片会让大块分配失败，尽管总空闲量足够）。空闲链表就是对「哪些块可用」这一信息的组织方式。

## 二、核心原理
三种块组织形态：
1. **隐式空闲链表**：不维护额外指针，靠块头记录大小，通过「当前地址 + 大小」跳到下一块。查找需线性扫描全部块（含已分配块）。
2. **显式空闲链表**：在空闲块载荷区存前驱／后继指针，把所有空闲块串成双向链表。查找只在空闲块中进行，代价是每块需额外指针空间。
3. **分离空闲链表**：按大小类别维护多个链表（如 2 的幂次桶）。分配时先查合适桶，近似 $O(1)$；释放时按大小归桶。

块结构与边界标记：每块含头部（大小与分配位）与可选的脚部。带脚部的好处是能从当前块向前合并——读取前一块末尾的脚部即可知道其大小与是否空闲。分配位通常复用大小字段的低位（对齐保证低位为 0）；最小块需容纳头部与两个空闲链表指针，否则空闲块无法串链。

分配策略：
- **首次适配**：从头扫到第一个够大的块。快，但易在低地址累积小碎片。
- **下一次适配**：从上次位置继续扫。分配更均匀，碎片率通常更高。
- **最佳适配**：选最接近请求大小的块。剩余碎片小，但扫描成本高且易产生大量微小碎片。
- **分离适配**：按桶查找，工程上最常用（glibc malloc、jemalloc、tcmalloc 均属此类思路）。

释放与对齐：释放时若相邻块空闲则合并（coalesce）以防外部碎片累积；合并需向前向后双向检查，向前依赖脚部、向后依赖「地址 + 大小」。请求大小需向上对齐到 `alignof(max_align_t)`（x86-64 通常 16 字节）；若空闲块明显大于请求则分割，余量过小则整块给出。

## 三、形式化与数学基础
设堆容量 $H$、空闲字节总量 $F$、最大连续空闲块 $M$，外部碎片率：

$$\mathrm{ext\_frag} = \frac{F - M}{H}$$

当它接近 1 时，尽管大量内存空闲，稍大的请求仍会失败——这就是「内存充足却分配失败」的成因。内部碎片来自对齐与最小块约束：

$$\mathrm{bsize}(r) = \mathrm{align}(r + \mathrm{HDR}),\qquad \mathrm{int\_frag}(r) = \mathrm{bsize}(r) - r - \mathrm{HDR}$$

峰值利用率是分配器的核心指标，其中 $L(t)$ 为活跃字节数：

$$U_{peak} = \max_t \frac{L(t)}{H(t)}$$

合并的正确性条件：设当前块 $B$、前块 $P$、后块 $N$，

$$\mathrm{size}(B') = \mathrm{size}(B) + [\mathrm{free}(P)]\mathrm{size}(P) + [\mathrm{free}(N)]\mathrm{size}(N)$$

合并后必须更新后块的脚部，否则链表结构损坏，后续合并会读到错误大小。

## 四、代码实现
```c
#include <stddef.h>

/* 带边界标记的隐式空闲链表（简化示意，非生产可用） */
#define ALIGN   16
#define HDR     (sizeof(block_hdr))
#define MINBLK  (ALIGN * 2)

typedef struct block_hdr {
    size_t size;      /* 低 3 位保留，bit0 = 是否已分配 */
    size_t prevsize;  /* 脚部：使前向合并可行 */
} block_hdr;

#define BLK_SIZE(h) ((h)->size & ~(size_t)7)
#define IS_ALLOC(h) ((h)->size & (size_t)1)
#define PAYLOAD(h)  ((void *)((char *)(h) + HDR))
#define NEXT(h)     ((block_hdr *)((char *)(h) + BLK_SIZE(h)))

/* 首次适配 + 分割：余量不足最小块时整块给出，避免产生无法复用的碎片 */
void *my_malloc(block_hdr *heap_start, char *heap_end, size_t req) {
    size_t need = (req + HDR + ALIGN - 1) & ~(size_t)(ALIGN - 1);
    if (need < MINBLK) need = MINBLK;
    for (block_hdr *b = heap_start; (char *)b < heap_end; b = NEXT(b)) {
        if (IS_ALLOC(b) || BLK_SIZE(b) < need) continue;
        if (BLK_SIZE(b) - need >= MINBLK) {
            block_hdr *rest = (block_hdr *)((char *)b + need);
            rest->size = BLK_SIZE(b) - need;
            rest->prevsize = need;
            NEXT(rest)->prevsize = BLK_SIZE(rest);   /* 修正后块脚部 */
            b->size = need | 1;
        } else {
            b->size |= 1;
        }
        return PAYLOAD(b);
    }
    return NULL;                      /* 真实实现应向内核扩展堆 */
}
```

## 五、与其他技术对比

| 维度 | 隐式空闲链表 | 显式空闲链表 | 分离空闲链表 | 伙伴系统 |
|---|---|---|---|---|
| 查找成本 | $O(\text{块数})$ | $O(\text{空闲块数})$ | 近似 $O(1)$ | $O(\log H)$ |
| 每块额外空间 | 头部（+脚部） | 头部 + 两个指针 | 头部 + 桶内指针 | 位图 |
| 外部碎片 | 中 | 中 | 低 | 中，但合并确定 |
| 合并方式 | 边界标记 | 需维护链表一致 | 依赖块头信息 | 天然按 2 的幂合并 |
| 实现复杂度 | 低 | 中 | 高 | 中 |
| 代表实现 | 教学实现 | 早期分配器 | glibc/jemalloc/tcmalloc 思路 | 内核页级分配 |

## 六、常见误区
误区一：忘记对齐导致未定义行为。返回未对齐指针会让 `double`、`long long` 与 SIMD 访问出错。
误区二：释放后不合并。外部碎片快速累积，表现为「内存充足却分配失败」。
误区三：越界写覆盖头部。堆溢出破坏块大小字段，导致后续 `free` 走到非法地址，是最经典的堆利用入口。
误区四：认为 `free` 会缩小进程内存占用。`free` 通常只把块还给分配器，是否归还内核取决于策略与堆顶情况。

## 八、面试题
1. 首次适配与最佳适配的区别与取舍？
   要点：首次适配快、低地址易碎；最佳适配剩余碎片最小但扫描成本高且易产生微小碎片。
2. 为什么合并（coalesce）重要？
   要点：不合并会累积外部碎片，最终出现大量空闲但无连续大块的失败场景。
3. 内部碎片与外部碎片的区别？
   要点：内部碎片是分配块大于请求（对齐、最小块约束造成）；外部碎片是空闲总量足够但不连续。
4. 边界标记（boundary tag）解决什么问题？
   要点：靠脚部存储前块大小，使向前合并成为 $O(1)$，无需全堆扫描。

## 九、演进与趋势
现代通用分配器以「线程本地缓存 + 大小分级 + 分片 arena」为核心，把锁竞争降到最低并显著改善多核可扩展性。安全强化方面，分配器普遍加入元数据校验、隔离空闲链表、随机化分配与更严格的 `free` 合法性检查，以提高堆漏洞利用难度。内核侧从 slab 演进到 slub 等实现，用更少元数据与更好的 NUMA 局部性支撑高并发。具体实现与默认策略以各分配器官方最新文档为准。

## 十、小结
堆分配器的核心是「用空闲链表组织可用空间、用分配策略选块、用合并与分割控制碎片」这三件事的权衡。隐式链表简单但慢，显式链表利用载荷存指针，分离链表用分桶换取近似常数时间，是工业实现的共同方向。工程上牢记三条不变式：返回指针必须对齐、块头必须准确、相邻空闲块必须合并——破坏任何一条，都会从性能下降演变为内存漏洞。
