# 流量控制

> 对应 RFC 9293 第 3 章、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 17 章、Tanenbaum《Computer Networks》第 6 章。

## 一、背景与挑战
发送方可能以远超接收方处理能力（或接收缓冲）的速率发包，导致接收方应用来不及读取、缓冲区溢出而丢包。流量控制（flow control）保证发送方不淹没接收方，解决「端到端速率匹配」。注意它只关心「接收方能不能收」，与「网络能不能传」（拥塞控制）是两件事——混淆二者是常见错误。

若没有流量控制，高速发送方会把慢速接收方的内存迅速打满，随后只能靠丢包让发送方「撞墙」式减速，效率极低且不公平。

流量控制之所以必要，根源在于「端系统处理能力可能远低于网络带宽」：在数据中心内部，网络可以轻松跑满 100 Gbps，但应用层若在做复杂计算或同步写入磁盘，其消费速率可能只有几 Gbps。没有窗口通告，缓冲区溢出与丢包不可避免，且丢包会被拥塞控制误判为「网络拥塞」，进一步降低发送速率——一个越慢越严重的恶性循环。

## 二、核心原理
接收方在每个 ACK 中通告接收窗口 `rwnd`（剩余可用缓冲区大小）。发送窗口受 $\min(cwnd, rwnd)$ 约束：`rwnd=0` 时发送方停止发数据（仅允许发 1 字节探测段以打破死锁）。随着接收方应用读取数据、腾出缓冲，后续 ACK 携带更大的 rwnd，发送窗口重新打开。

这是典型的「反馈闭环」：接收方用窗口大小实时调速，发送方据此节流。窗口是「还能发多少字节」的声明，而非「速率」声明，因此需配合 ACK 节奏形成平滑控制。

通告窗口的更新是「搭便车（piggyback）」的：接收方在发送 ACK 时顺带填写当前剩余空间，不额外发包。若接收方长期没有数据要发（纯 ACK），则会按期发送独立的窗口更新段。这两条路径共同保证 rwnd 信息持续流动。

接收方还必须在「通告窗口」与「实际可用空间」之间保持一致：若通告后发现应用尚未读取，窗口不能缩小（TCP 不允许「窗口回缩」），否则会与已发出的数据产生歧义。因此接收方通常只在空间增加时才通告增长，这也是 Clark 算法自然成立的原因。

## 三、形式化与数学基础
接收方通告窗口：

$$ rwnd_t = R_{buf} - (R_{recv} - R_{acked}) $$

即缓冲区容量减去「已收但未交付给应用」的字节数。发送窗口：

$$ W_{send} = \min(cwnd,\; rwnd) $$

零窗口探测：当 $rwnd=0$ 时，发送方每约一个 RTO 或一个固定间隔（约 1 分钟，以实现为准）发 1 字节数据段，迫使接收方回含新 rwnd 的 ACK，打破「双方都在等对方」的死锁。

零窗口探测的间隔通常采用指数退避，避免在网络长时间拥塞时持续发探测段。这与重传退避同源，目的是让「对端一直不开窗」的异常连接最终被自动清理（持续失败后内核可终止连接）。

Silly Window Syndrome 的定量描述：若接收方每次只通告 $\delta$ 字节窗口、发送方每次只发一个小段，头部开销（TCP+IP 约 40 字节）相对有效载荷的比例为 $40/(40+\delta)$，当 $\delta$ 很小时有效带宽利用率趋近于 $0$。因此需要「窗口至少增长 MSS 或半个缓冲」的下界约束。

## 四、代码实现
```java
// 接收方：每次读取后重新计算并通告窗口
int free = recvBuffer.capacity() - recvBuffer.occupied();
int rwnd = Math.max(0, free);
tcpHeader.setWindow(rwnd);   // 携带在每一个 ACK 中发给发送方
```
```c
// 发送方：受 rwnd 约束，rwnd=0 时仅允许零窗口探测段
if (snd_una + min(cwnd, rwnd) <= snd_nxt) {
    send_probe();   // 仅发 1 字节探测
}
```

接收方侧的 Clark 算法（避免通告过小窗口）：

```c
/* 仅在可腾出至少 MSS 或半个缓冲时才通告窗口增长 */
int new_free = buf_capacity - buf_occupied;
if (new_free >= MSS || new_free >= buf_capacity / 2) {
    advertise_window(new_free);      /* 增长通告 */
} else {
    advertise_window(0);             /* 保持零窗口，避免小窗口低效 */
}
```

## 五、与其他技术对比
| 维度 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 目标 | 不淹没接收方缓冲 | 不压垮网络中间链路 |
| 信号来源 | 接收方 rwnd | 丢包/延迟（cwnd 试探） |
| 作用范围 | 端到端（单连接） | 多点（网络路径） |
| 机制 | 窗口通告 | 慢启动/拥塞避免/AIMD |
| 失效后果 | 接收方缓冲区溢出丢包 | 网络拥塞崩溃 |
| 调整速度 | 随应用读取实时变化 | 按 RTT 量级探测 |

二者通过 $\min(cwnd, rwnd)$ 共同决定实际发送窗口，缺一不可：只控流会导致网络拥塞，只控拥塞会让接收方溢出。

值得补充的是 QUIC 的层次化流控：它同时维护「连接级窗口」与「流级窗口」，单流被阻塞不影响其他流，这解决了 TCP 单字节流中「一个慢消费者拖住整条连接」的问题。HTTP/2 在应用层也做了类似的事，但受制于 TCP 的单窗口，效果不如 QUIC 彻底。

## 六、常见误区
误区一：流量控制防止网络拥塞——错，那是拥塞控制的职责。误区二：rwnd=0 后连接永久挂起——错，有零窗口探测保活。

误区三：Silly Window Syndrome（SWS）只在发送方——错，接收方也可能：若每次仅读取极小字节并通告极小 rwnd，会陷入「小窗口低效」，Clark 算法（接收方仅当可腾出至少 MSS 或半缓冲时才通告增长）解决。误区四：rwnd 越大越好——过大会加剧 bufferbloat。

误区五：以为接收窗口可以随意缩小。TCP 不允许窗口回缩（避免与已发送数据歧义），只能保持或增大。误区六：以为 `SO_RCVBUF` 设置多大多大就真的生效。内核存在最小值、最大值与自动调优机制，实际值可能是被 clamp 后的结果（以官方文档为准）。误区七：把流量控制当成「速率限制」。窗口是「在途字节数上限」，配合 RTT 才体现为速率，二者不等价。

## 八、面试题
1. 流量控制与拥塞控制的区别？答：前者针对接收方缓冲（端到端速率匹配），后者针对网络链路（避免拥塞崩溃）；实际窗口取二者最小值。
2. 什么是零窗口死锁，如何打破？答：接收方 rwnd=0 且后续 ACK 丢失，发送方一直等待。打破靠零窗口探测段定期探活，逼对端回新 rwnd。
3. 什么是 Silly Window Syndrome？答：收/发双方因通告/发送极小窗口导致的低效，靠 Clark 算法与 Nagle 机制缓解。
4. Nagle 与流量控制关系？答：Nagle 避免发小包（发送方侧），与接收方 SWS 缓解互补，共同减少小窗口低效。
5. 为什么接收窗口不能缩小？答：缩小窗口会与「已通告窗口内发送的数据」产生歧义，接收方可能被迫丢弃已合法发出的数据。
6. 为什么 `SO_RCVBUF` 调大不一定生效？答：内核有上下限与自动调优，实际值可能被 clamp；且过大缓冲会加剧 bufferbloat。

## 九、演进与趋势
自动缓冲区调优（autotuning）动态调整 socket 缓冲区与 rwnd，使其随 measured BDP 自适应，避免手动设 `SO_RCVBUF` 过小。接收端 offload（如 LRO/GRO）减轻 CPU，但需注意不过度缓存放大 bufferbloat。

QUIC 在流级做流控、连接级做整体流控，粒度更细，单流 rwnd=0 不影响其他流——这是相对 TCP 单窗口的重要改进。随着 L4S 等低延迟队列管理机制的推广，「拥塞信号」与「流控信号」的分离也更被重视，目标是同时实现高吞吐与低排队延迟。

## 十、小结
流量控制用 rwnd 通告让发送方不超过接收能力，是 $\min(cwnd, rwnd)$ 中的 rwnd 分量；零窗口探测与 Clark 算法分别解决死锁与 SWS，是端到端速率匹配的关键。理解「窗口是容量声明而非速率声明」「窗口不可回缩」这两点，是正确实现与调优流控的基础。
