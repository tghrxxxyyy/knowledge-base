# 滑动窗口

> 对应 Tanenbaum《Computer Networks》第 6 章、RFC 9293 第 3 章、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 17 章。

## 一、背景与挑战
停-等协议（stop-and-wait）每发一帧等一个 ACK，信道利用率仅 $1/(1+2a)$，其中 $a = RTT/(L/R)$ 为归一化时延带宽比。在高 BDP（带宽时延积）链路上 $a$ 很大，利用率趋近于零。滑动窗口让发送方在未被确认前连续发送多个段，从而「填满管道」，把利用率提升到接近 100%。

TCP 的发送窗口同时承载流控（接收方能力）与拥塞控制（网络能力）两重语义，是 TCP 性能的核心旋钮。

滑动窗口的价值可用一个直观例子说明：一条 1 Gbps、RTT 100 ms 的链路，BDP 约 12.5 MB。若窗口只有 64 KB，则每次只能「在途」64 KB，等效吞吐约 $64\text{ KB} / 0.1\text{ s} = 5.1\text{ Mbps}$——不到链路能力的 1%。这解释了为什么窗口缩放与自动调优是现代 TCP 性能的关键。

## 二、核心原理
发送窗口上界由接收方通告的接收窗口 `rwnd` 与拥塞窗口 `cwnd` 共同决定：

$$ \text{发送窗口} = \min(cwnd,\; rwnd) $$

窗口内的字节分为「已发送已确认 / 已发送未确认 / 可发送未发送 / 不可发送」四段。每收到一个 ACK，窗口左侧（`snd_una`）右移，右侧按 min(cwnd, rwnd) 推进，故称「滑动」。

接收方用同样机制维护接收窗口，仅交付按序到达的数据给应用，失序段缓存等待缺口补齐。窗口滑动意味着「已确认的部分腾出空间，可发新数据」。

窗口「不缩回」是一条硬约束：接收方一旦通告了某窗口，就不能再缩小它（因为发送方可能已经按旧窗口发出了数据）。因此接收方在缓冲被占满时只能通告 0，等应用腾出空间后再通告增长——这正是 Clark 算法存在的原因。

窗口的另一重作用是「批量确认」：一个 ACK 可以同时确认多个段（累计确认），因此窗口越大，单位数据所需的 ACK 越少，反向链路的开销也越低。这在高 BDP 链路（如卫星链路）上尤为明显：若每段都回一个 ACK，反向链路带宽会被 ACK 占满。

## 三、形式化与数学基础
可用窗口（usable window）：

$$ W_{use} = \min(cwnd,\; rwnd) - (S_{next} - S_{una}) $$

管道容量（BDP）：

$$ BDP = B \cdot RTT $$

理想窗口至少为 BDP 才能跑满带宽；若窗口 $< BDP$，链路未被填满。窗口缩放选项（RFC 7323）：

$$ rwnd_{advertised} = rwnd_{field} \cdot 2^{scale},\quad scale \in [0,14] $$

使 16 位 rwnd 字段最大可表达约 1 GB（受 14 位缩放上限约束）。

窗口与吞吐的定量关系可写成：

$$ \text{Throughput} \le \frac{W}{RTT} $$

其中 $W$ 为有效窗口。要在 BDP 为 $B \cdot RTT$ 的链路上跑满带宽 $B$，必须 $W \ge B \cdot RTT$。这一不等式是窗口调优的「唯一公式」：所有调参（扩缓冲、开缩放、用连接池）都是为了让 $W$ 不小于 BDP。

窗口缩放因子必须在 SYN 握手中协商且只协商一次（RFC 7323），因此「连接已建立后才想扩大窗口」是不可能的——必须重建连接。这是排查「大 BDP 链路吞吐上不去」时要先确认缩放是否生效的原因。

## 四、代码实现
```go
type Sender struct {
    base uint32 // 最早未确认序号 snd_una
    next uint32 // 下一个待发序号 snd_nxt
    win  uint32 // 发送窗口 = min(cwnd, rwnd)
}
func (s *Sender) canSend() bool {
    // 已发送未确认长度必须小于窗口
    return s.next - s.base < s.win
}
// 收到 ACK：base 右移，窗口左沿滑动
func (s *Sender) onAck(ack uint32) {
    if ack > s.base {
        s.base = ack
    }
}
```

## 五、与其他技术对比
滑动窗口是「字节流」层面的流控/拥塞窗口抽象；数据链路层的 Go-Back-N 与 Selective Repeat 以「帧号」为窗口单位，通常无拥塞窗口概念。Go-Back-N 丢一帧重传其后所有帧，Selective Repeat 仅重传丢失帧——TCP 借助 SACK 更接近 Selective Repeat 语义。

QUIC 的流与连接级窗口分离，流级窗口不阻塞其他流，避免了 TCP 单字节流队头阻塞。

| 维度 | 停-等 | Go-Back-N | Selective Repeat | TCP 滑动窗口 |
| --- | --- | --- | --- | --- |
| 窗口单位 | 1 帧 | 帧号 | 帧号 | 字节 |
| 利用率 | $1/(1+2a)$ | 高 | 高 | 高 |
| 丢包恢复 | 重传该帧 | 重传其后全部 | 仅重传丢失帧 | 快速重传 + SACK |
| 拥塞控制 | 无 | 无 | 无 | 有（cwnd） |
| 接收缓冲压力 | 最小 | 中 | 大（需乱序缓存） | 大 |

## 六、常见误区
误区一：窗口单位是「报文段个数」——错，TCP 窗口按字节计。误区二：rwnd 越大越好——错，过大会加剧 bufferbloat（排队延迟飙升）。

误区三：窗口不滑动直到超时——错，每收到 ACK 即滑动。误区四：16 位 rwnd 最大 65535 字节足够——错，高 BDP 链路需窗口缩放（RFC 7323）才能跑满。误区五：cwnd 与 rwnd 可独立无限增大——实际取二者最小值。

误区六：以为窗口缩放可以在连接中途协商。它只在 SYN 中协商一次，建立后无法改变。误区七：忽略「接收窗口不可回缩」。接收方若缩小已通告的窗口，会与已发出的数据产生歧义。

## 八、面试题
1. 发送窗口由谁决定？答：$\min(cwnd, rwnd)$，cwnd 来自拥塞控制，rwnd 来自接收方通告。
2. 窗口缩放解决什么问题？答：16 位 rwnd 字段最大 65535 字节不足以匹配高 BDP 链路，缩放位（0–14）把它扩到约 1 GB。
3. 为什么停-等在高 BDP 链路差？答：窗口=1 个段，利用率 $1/(1+2a)$，a 大时趋近 0。
4. 接收窗口为 0 后还能收到数据吗？答：可收 1 字节零窗口探测段与带 URG 的数据，但不能发普通数据。
5. 窗口与吞吐的定量关系是什么？答：$\text{Throughput} \le W / RTT$，要跑满带宽需 $W \ge BDP$。
6. 为什么窗口缩放必须在握手时协商？答：缩放因子只在 SYN 中交换一次，建立后无法更改，若未协商则窗口上限固定在 64 KB。

## 九、演进与趋势
自动调优（autotuning）让 socket 缓冲区随 measured BDP 自适应，避免手动设 `SO_RCVBUF`/`SO_SNDBUF`；MPTCP 维护每子流窗口并做耦合拥塞控制。

QUIC 把窗口分为流级与连接级，单流阻塞不影响其他流。窗口缩放已成为现代内核默认启用，配合 autotuning 几乎无需人工干预即可跑满高 BDP 链路。此外，L4S 等低延迟队列管理机制试图在保持高吞吐的同时抑制排队延迟，与「大窗口」的 bufferbloat 副作用形成互补。

## 十、小结
滑动窗口用 $\min(cwnd, rwnd)$ 同时实现流控与拥塞控制，配合窗口缩放才能在现代高带宽链路跑满吞吐；理解 BDP 与窗口关系是网络性能调优的基础。牢记「窗口按字节计」「不可回缩」「缩放须握手协商」这三条，可以快速定位绝大多数吞吐异常。
