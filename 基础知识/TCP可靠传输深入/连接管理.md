# 连接管理

> 对应 RFC 9293（TCP 状态机）、RFC 6528（ISN 生成）、RFC 7413（TFO）、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 18 章。

## 一、背景与挑战
TCP 面向连接，通信前需建立端到端状态（序列号、窗口、选项），结束后需优雅释放并防止旧报文干扰新连接。连接管理定义了建立、释放与异常处理的完整状态机，是 TCP 可靠性的前提。状态机必须正确处理正常三次握手、四次挥手，以及 SYN Flood、半打开、同时打开/关闭等异常，否则会出现资源耗尽或数据串扰。

理解状态机也有助于排查「连接卡在 SYN_RECV」「CLOSE_WAIT 堆积」等线上问题，这些往往指向应用未调用 close/accept 或被动关闭方未接收 FIN。

连接管理的另一面是「资源核算」：每条连接在内核里对应 `struct sock`（百余字节到数 KB 不等，含收发缓冲与选项），加上半连接项 `request_sock` 与 TIME_WAIT 轻量结构 `inet_timewait_sock`。因此连接数上限不只由端口决定，还受内存、`file-max`、`somaxconn` 与 `tcp_max_syn_backlog` 共同约束。生产事故中「连接泄漏」与「握手风暴」是两类不同病因：前者是 ESTABLISHED/CLOSE_WAIT 单调增长，后者是 SYN_RECV 尖峰。

## 二、核心原理
三次握手建立连接：SYN（seq=ISN_A）→ SYN+ACK（seq=ISN_B, ack=ISN_A+1）→ ACK（ack=ISN_B+1）。双方由此同步 ISN 并协商窗口规模、SACK、时间戳等选项。四次挥手释放：FIN → ACK → FIN → ACK；因 TCP 是全双工，每个方向独立关闭，故需两侧各发一个 FIN。

主动关闭方发完最后 ACK 后进入 TIME_WAIT 等待 2MSL，保证最后 ACK 可达且旧报文消亡。被动关闭方在收齐对端 FIN 与 ACK 后直接回到 CLOSED。谁先发 FIN，谁就承担 TIME_WAIT。

RFC 9293 定义 11 个状态：CLOSED、LISTEN、SYN_SENT、SYN_RCVD、ESTABLISHED、FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、CLOSING、LAST_ACK、TIME_WAIT。选项协商只发生在 SYN 段（除 SACK 允许在握手后单独协商）：MSS 在 SYN 中声明可接收的最大段长，窗口缩放（Window Scale）一旦协商成功便对整条连接生效且不可再改，SACK Permitted 决定是否允许收发 SACK 块，Timestamps 同时用于 RTT 测量与 PAWS。若对端不支持某选项，本端必须退化为默认行为，这也是「旧设备互操作」坑的来源。

三次握手通常还要考虑同时打开（双方几乎同时发 SYN，各自进入 SYN_SENT 并互回 SYN+ACK，最终双方均成为 ESTABLISHED）与同时关闭（双方同时发 FIN，状态经 FIN_WAIT_1 → CLOSING → TIME_WAIT，故四次挥手实际只有三次报文）。这些路径在状态机中必须被完整实现，否则会出现「罕见路径死锁」。

## 三、形式化与数学基础
状态转移关键路径：

$$ CLOSED \xrightarrow{SYN} SYN\_SENT \xrightarrow{SYN,ACK} ESTABLISHED $$
$$ ESTABLISHED \xrightarrow{FIN} FIN\_WAIT\_1 \xrightarrow{ACK} FIN\_WAIT\_2 \xrightarrow{FIN} TIME\_WAIT $$

TIME_WAIT 持续时间：

$$ T_{TIME\_WAIT} = 2 \cdot MSL $$

Linux 固定为 60 秒（`TCP_TIMEWAIT_LEN`）。同时打开（simultaneous open）与同时关闭有独立转移路径（见单独文档）。SYN Cookie 把半连接状态编码进序列号，使服务端在收到第三次 ACK 前不分配 `request_sock`，从而无状态抵御 SYN Flood。

RFC 6528 要求 ISN 不可预测，其推荐形式为 $ISN = M + F(localip, localport, remoteip, remoteport, K)$，其中 $M$ 是每 4 微秒递增一次的计时器，$K$ 为服务端私钥，$F$ 为密码学哈希。这样即使攻击者观测到某个四元组的 ISN，也无法预测其他四元组的 ISN。SYN Cookie 的序列号则由四元组、时间戳与 MSS 经哈希生成，服务端在第三次 ACK 中重新计算并比对，代价是无法在握手中携带 SACK 等需要状态协商的选项（若对端要求这些选项，Cookie 模式下会被省略）。

半连接队列的溢出概率可用排队模型粗略估算：若 SYN 到达率为 $\lambda$、处理（含超时重传窗口）时间为 $T_{syn}$，则稳态下队列占用近似 $\lambda T_{syn}$，一旦超过 `tcp_max_syn_backlog` 即开始丢弃新 SYN。这也解释了为何「短时突然的大量正常连接」与「攻击」在指标上难以区分。

## 四、代码实现
```c
// 典型阻塞服务端：完成三次握手后 accept 返回
int s = socket(AF_INET, SOCK_STREAM, 0);
bind(s, (struct sockaddr *)&addr, sizeof(addr));
listen(s, 128);                  // 设置全连接队列 backlog（内核取 min(backlog, somaxconn)）
int c = accept(s, NULL, NULL);   // 阻塞至三次握手完成，取出全连接队列中的 sock
// ... 读写 ...
close(c);                        // 触发四次挥手（本端为被动/主动关闭方之一）
```

客户端 `connect()` 内部完成 SYN→SYN+ACK→ACK 并在返回时连接已 ESTABLISHED。注意 `accept` 只是从全连接队列取走已完成握手的 sock，不负责握手本身；因此「应用长时间不 accept」会导致全连接队列溢出，而非握手失败。

全双工关闭需区分两个 API：

```c
shutdown(c, SHUT_WR);   // 发送 FIN，本端进入 FIN_WAIT_1，但仍可继续读对端数据
close(c);               // 减引用计数，引用为 0 时才真正发 FIN/RST 并释放 fd
```

半关闭（half-close）常用于「客户端发完请求后 shutdown(SHUT_WR)，等对端把响应发完再 close」的协议，可避免两端互相等待造成死锁。而 `close` 在 fd 被 `dup` 或多线程共享时并不会立即发 FIN，这是「明明 close 了却没看到 FIN」的常见原因。

## 五、与其他技术对比
UDP 无连接管理，无握手/挥手、无 TIME_WAIT，简单但不可靠。QUIC 在 UDP 之上自建连接（含 0-RTT/1-RTT 与 TLS 1.3 合并协商），关闭语义类似「建立/释放」但用连接 ID 解耦四元组。

SCTP 用四路握手 + cookie 抵御 SYN Flood，且支持多流（multistreaming）避免队头阻塞。TCP 的单一字节流在丢包时会队头阻塞，是 QUIC 改进的重点。

| 维度 | TCP | QUIC | SCTP | UDP |
| --- | --- | --- | --- | --- |
| 建立握手 | 三次（1 RTT） | 1-RTT / 0-RTT | 四路 + cookie | 无 |
| 连接标识 | 四元组 | 连接 ID | 关联（vtag） | 四元组 |
| TIME_WAIT | 有（2MSL） | 无（连接 ID 解耦） | 弱化（T-bit） | 无 |
| 队头阻塞 | 单流整体阻塞 | 仅单流内阻塞 | 多流独立 | 无（应用自担） |
| 加密 | 可选（TLS 叠加） | 内建（TLS 1.3） | 可选（DTLS） | 无 |

## 六、常见误区
误区一：两次握手即可——错，无法确认客户端的接收能力，且易遭旧 SYN 误导建立无效连接。误区二：TIME_WAIT 是 bug——错，它保证最后 ACK 可达并让旧报文消亡。

误区三：服务器不会进 TIME_WAIT——错，谁主动 close 谁进。误区四：accept 前连接没建立——错，accept 只是从全连接队列取走已完成三次握手的 sock。误区五：FIN 关闭双向——错，FIN 只关闭本端到对端的方向，另一方向仍可发数据。

误区六：`close()` 一定立即发 FIN——错，存在 fd 引用计数与 `SO_LINGER` 影响，被 dup 的 fd 全部关闭后才真正关闭。误区七：LISTEN 套接字上的 backlog 就是并发上限——错，它只限制「已完成握手、尚未 accept」的排队数，与并发连接总数无关。误区八：只要加机器就能解决 CLOSE_WAIT 堆积——错，CLOSE_WAIT 是应用未 close 的结果，与容量无关。

## 八、面试题
1. 为什么是三次握手？答：同步双方 ISN、确认双向收发能力，并抵御旧 SYN 造成的半开连接。
2. 为什么 TIME_WAIT 是 2MSL？答：覆盖最后 ACK 的往返与对端 FIN 重传，并让迟到旧报文彻底消亡。
3. 大量 TIME_WAIT 如何缓解？答：SO_REUSEADDR / tcp_tw_reuse（出向）+ 时间戳、扩大端口范围、用连接池；服务端优先被动关闭。
4. CLOSE_WAIT 堆积说明什么？答：被动关闭方已收到 FIN 并回 ACK，但应用未调用 close，常见于应用层漏关连接。
5. FIN_WAIT_2 会长期停留吗？答：会，若对端一直不发 FIN，本端将长期处于 FIN_WAIT_2；内核有 `tcp_fin_timeout` 兜底回收孤儿连接。
6. shutdown(SHUT_WR) 与 close 的区别？答：前者发 FIN 并保持半关闭（仍可读），后者按引用计数释放 fd、最终发 FIN 或 RST。
7. 为什么 SYN Cookie 要牺牲部分选项？答：它把状态编码进序列号，服务端不保存 `request_sock`，故无法在 SYN+ACK 中携带需要状态的选项（如窗口缩放）。

## 九、演进与趋势
TCP Fast Open（RFC 7413）在 SYN 携带数据以削减一次 RTT，但安全考量使其在公网默认受限、需 cookie 验证。SYN Cookie 已成为标准实践以无状态抵御 SYN 洪泛。

MPTCP（RFC 8684）把单连接扩展到多子流，连接管理涉及子流的建立/移除。随着 QUIC 普及，部分场景的连接管理语义迁移到用户态传输层，握手与加密合并进一步降低延迟，连接迁移与 0-RTT 成为新常态，同时也带来「重放攻击」等新的安全约束，需要服务端做幂等保护。

## 十、小结
三次握手建立、四次挥手释放、TIME_WAIT 保安全，是 TCP 面向连接语义的落地；理解状态机、队列上限与 SYN Cookie，是排查连接问题与抗攻击的基础。掌握 11 个状态与两个队列的关系，几乎可以把所有「建连失败/连接堆积」类线上问题定位到具体环节。
