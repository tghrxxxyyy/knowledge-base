# 超时重传

> 对应 RFC 6298（RTO 计算）、RFC 9293 第 3 章、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 21 章。

## 一、背景与挑战
报文可能丢失、乱序或延迟。发送方必须判定「多久没收到 ACK 就算丢」，过短会误重传浪费带宽，过长则恢复慢、尾延迟高。超时重传是可靠性的最后兜底机制：当快速重传（依赖 dup ACK）因 ACK 丢失或尾部丢包而无法触发时，只能靠定时器。

其难点在于 RTO 必须随网络 RTT 动态变化，又不能对抖动过度敏感——这是 TCP 在「及时性」与「稳定性」之间的经典权衡。

从可靠性角度看，超时重传是「完备性」的唯一保证：无论丢包模式多么恶劣（连续多个 ACK 丢失、尾部丢包、网络长时间中断），只要定时器还在跑，发送方最终一定会重传。相比之下快速重传是「性能优化」——它加速恢复，但无法覆盖所有丢包情形。二者在职责上不可互替。

## 二、核心原理
发送方为每个未确认段（或最早未确认段）维护一个重传定时器；超时则重传并采用指数退避（binary exponential backoff），即下一次超时间隔翻倍，避免在网络持续恶化时雪崩式重传。RTO 由对 RTT 的测量与方差估计动态计算，而非固定值。

重传后，由于无法判断回到的 ACK 对应原始段还是重传段（二义性），重传段的 RTT 不参与采样（Karn 算法）。这样避免「重传段被当正常段测速」而污染估计。

Karn 算法有一个重要补充：若使用时间戳选项（RFC 7323），则每个 ACK 都携带对应段的时间戳，重传二义性被彻底消除，此时**可以**对重传段采样 RTT。因此现代内核在启用时间戳后会对重传段也做 RTT 估计，使 RTO 收敛更快。

「单一重传定时器」的设计也值得说明：TCP 只为最早未确认段（`snd_una`）设一个定时器，而非每段一个。理由是「累计确认」语义下，最早未确认段被确认即意味着它之前全部被确认，因此只需盯住这一个「最老」的段即可；这也使定时器数量与连接数无关，实现简洁。

## 三、形式化与数学基础
RFC 6298 算法。设第 $i$ 个采样 RTT 为 $M_i$：首样本：

$$ SRTT = M_1,\qquad RTTVAR = M_1/2 $$

后续样本：

$$ RTTVAR = (1-\beta)RTTVAR + \beta|SRTT - M_i|,\quad \beta = 1/4 $$
$$ SRTT = (1-\alpha)SRTT + \alpha M_i,\quad \alpha = 1/8 $$
$$ RTO = SRTT + 4\cdot RTTVAR,\quad \text{且 } RTO \ge 1\text{s} $$

重传后定时器翻倍（指数退避）：

$$ RTO' = 2\cdot RTO $$

上限通常钳制在 $60\text{s}$ 量级（以官方最新文档为准）。需注意 SRTT/RTTVAR 更新用指数加权滑动平均（EWMA），对突发抖动平滑。

EWMA 的语义解释：$\alpha = 1/8$ 意味着新样本只占 12.5% 权重，等效「记忆」约 8 个样本；$\beta = 1/4$ 使方差估计对变化更敏感。因此 SRTT 平滑、RTTVAR 灵敏，二者配合使 RTO 既能跟随长期趋势、又能对抖动快速反应。

「4 倍方差」的统计含义：若 RTT 近似正态分布，$SRTT + 4\,RTTVAR$ 对应约 4 个标准差的上界，理论上覆盖 99.99% 的样本，故误超时概率极低。这正是选择系数 4 而非 1 或 2 的原因。

```python
SRTT = RTTVAR = None

def on_sample(m):
    global SRTT, RTTVAR
    if SRTT is None:
        SRTT, RTTVAR = m, m / 2.0

        RTTVAR = 0.75 * RTTVAR + 0.25 * abs(SRTT - m)
```

```python
def on_ack(ack_seq, is_retransmitted, ts_echo=None):
    if is_retransmitted and ts_echo is None:
        return None            # 无时间戳：重传段不可采样（Karn 算法）
    if ts_echo is not None:
        return now() - ts_echo  # 有时间戳：二义性消除，可安全采样
```

## 五、与其他技术对比
超时重传是「消极」兜底（要等很久才触发，常数百毫秒到秒级）；快速重传依靠重复 ACK 主动探测丢包，恢复快得多（约一个 RTT）。二者互补：没有超时，长期丢 ACK 或尾部丢包会卡死；没有快重传，恢复太慢、吞吐骤降。

超时更偏向正确性（一定能最终恢复），快重传更偏向性能。实践中绝大多数丢包由快重传处理，超时只在「连 dup ACK 都没有」时登场。

| 维度 | 超时重传 | 快速重传 | TLP（RFC 8985） | RACK |
| --- | --- | --- | --- | --- |
| 触发条件 | 定时器到期 | 3 个 dup ACK | RTO 前发探测段 | 时间差判定 |
| 恢复时延 | RTO 量级 | 约 1 RTT | 约 1 PTO | 约 1 RTT |
| 覆盖丢包类型 | 全部（兜底） | 中段丢包 | 尾部 1–2 个丢包 | 乱序/丢包 |
| 是否依赖 ACK | 否 | 是 | 否 | 是（时间戳） |

## 六、常见误区
误区一：每次重传都重新采样 RTT——错，Karn 算法规定重传的段不参与 RTT 采样，避免二义性污染估计。误区二：RTO 等于平均 RTT——错，还要加 4 倍抖动（RTTVAR），否则抖动稍大就频繁误超时。

误区三：RTO 越小越好——错，过小导致大量伪重传，浪费带宽且可能加剧拥塞。误区四：定时器对所有未确认段各设一个——实际通常只对最早未确认段（`snd_una`）设单一重传定时器。误区五：退避只在第一次重传——实际每次连续超时都翻倍直到上限。

误区六：以为 Karn 算法永远禁止对重传段采样。启用时间戳后二义性消除，可以采样。误区七：忽略 RTO 下限的工程意义。$1\text{s}$ 下限避免了极短 RTO 在微秒级抖动下疯狂误重传。

## 八、面试题
1. 为什么 RTO 要加 $4\times RTTVAR$ 而非等于 SRTT？答：吸收 RTT 抖动，避免频繁误重传；纯均值对抖动无缓冲。
2. Karn 算法解决了什么？答：重传段的 RTT 采样二义性（无法判断 ACK 对应原始还是重传段），故重传期间不更新 SRTT/RTTVAR。
3. 指数退避的作用？答：网络恶化时逐步拉长重传间隔，防止重传风暴加剧拥塞。
4. 为什么 RTO 有 1 秒下限？答：避免极短 RTO 在极小 RTT 抖动下疯狂误重传，RFC 6298 规定下限 1s。
5. 有了时间戳后 Karn 算法还需要吗？答：时间戳消除了二义性，故可对重传段采样；但在无时间戳时仍是必须的。
6. 为什么只用一个重传定时器？答：累计确认语义下，最早未确认段被确认即意味着其前全部被确认，只需盯住最老段。

## 九、演进与趋势
Tail Loss Probe（TLP，RFC 8985）在 RTO 到期前发送一个探测段（携带最新数据或重传尾部），用一次轻量重传快速恢复尾部 1–2 个丢包，显著降低尾延迟。RACK（RFC 8985）用时间戳做基于时间的重排检测，弥补 dup ACK 不足时的恢复盲区。

两者共同把「靠超时兜底」的占比降到极低，使现代 TCP 在保持正确性的同时尾延迟可控。数据中心内部（低 RTT、低抖动）还出现了「每包定时器」等更激进的方案，但受 CPU 开销限制，主流仍以「单一定时器 + 快速恢复」为骨架。

## 十、小结
超时重传靠 RFC 6298 的 SRTT/RTTVAR 估算动态 RTO 并指数退避，是可靠性的最终兜底；Karn 算法避免采样二义性，TLP/RACK 则是现代内核对其恢复慢问题的补充。理解「单一定时器 + EWMA 估计 + 指数退避」这三件套，就掌握了 TCP 在不确定网络中「既不频繁误判、又能最终恢复」的设计精髓。
