# 序号与确认机制

> 对应 Kurose & Ross《Computer Networking: A Top-Down Approach》第 3 章；RFC 9293。

## 一、背景与挑战
IP 是不可靠、无连接、尽力而为的数据报服务，既不保证交付也不保证顺序。TCP 在 IP 之上构建可靠字节流，必须解决丢包、乱序、重复三大问题。序号与确认（ACK）是可靠性的第一块基石。

## 二、核心原理
TCP 把应用数据看作无结构字节流，每个字节分配一个 32 位序号（sequence number）。报文段首部的 `seq` 填该段首个数据字节的序号；确认号 `ack` 采用累计确认（cumulative ACK），表示“所有小于 ack 的字节均已按序收到，期望从 ack 开始接收”。初始序号 ISN 随机生成（RFC 6528），以防御序列号预测与旧连接残留报文混淆。

## 三、形式化 / 数学基础
发送方已发送未确认区间为 `[U, S)`，下一段 `seq = S`，段长 `L`，发送后 `S += L`。
累计确认：$ack = \min\{ b \mid \text{所有序号} < b \text{的字节均已按序到达} \}$。
RTT 估计（RFC 6298）：$SRTT = (1-\alpha)SRTT + \alpha \cdot RTT\ (\alpha=1/8)$；$RTTVAR = (1-\beta)RTTVAR + \beta|SRTT-RTT|\ (\beta=1/4)$；$RTO = SRTT + 4\cdot RTTVAR$。

## 四、代码实现
```c
// RFC 9293 TCP 首部（简化，网络字节序）
struct tcphdr {
    uint16_t sport, dport;
    uint32_t seq;   // 序号
    uint32_t ack;   // 确认号（ACK 标志置位时有效）
    uint8_t  off;
    uint8_t  flags; // SYN/FIN/ACK/RST...
    uint16_t rwnd;  // 接收窗口
    uint16_t csum, urp;
};
```

## 五、与其他技术对比
累计 ACK 实现简单、对乱序鲁棒，但只能告知“第一个缺口”而不能精确告知丢的是哪些段。选择确认 SACK（RFC 2018）用 TCP 选项携带多个 `[left,right)` 区间，弥补该缺陷，适合高 BDP 链路。

## 六、常见误区
误区一：序号是“第几个报文段”。错，它是字节偏移。误区二：ACK 是已收到的最后一个字节序号。错，ACK 是期望的下一个字节（已收字节数 +1）。误区三：ISN 从 0 开始。错，ISN 随机以防御攻击。

## 八、面试题
1. 为什么 ISN 要随机？2. 累计确认与 SACK 区别？3. 收到 1–100、201–300，ACK 回什么？答：101（缺口前第一个未收字节）。

## 九、演进与趋势
多路径 TCP（MPTCP，RFC 8684）每个子流有独立序号空间，并引入 Data Sequence Number（DSN）做跨子流重排；TCP Timestamps（RFC 7323）辅助更精确 RTT 测量。

## 十、小结
序号标识字节位置、累计 ACK 确认连续前缀，配合 ISN 随机化与 RTT 估计，构成 TCP 可靠传输基石；SACK 与 Timestamps 是重要增强。
