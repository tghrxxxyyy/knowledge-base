# 序号与确认机制

> 对应 RFC 9293（现行 TCP 规范）第 3 章、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 24 章。

## 一、背景与挑战
IP 是不可靠、无连接、尽力而为的数据报服务，既不保证交付也不保证顺序。TCP 在 IP 之上构建可靠字节流，必须解决丢包、乱序、重复三大问题。序号（Sequence Number）与确认（ACK）是可靠性的第一块基石：发送方用序号标记每个字节在流中的位置，接收方用确认号告知「期望收到的下一个字节」，从而让发送方判断哪些数据已安全到达、哪些需要重传。

没有序号/确认，TCP 就无法区分「丢包」与「延迟」、无法在乱序时重组。它也是后续流量控制（rwnd）、拥塞控制（cwnd）与重传机制的计数基准。

TCP 的序号只对「数据字节 + SYN + FIN」计数，这一设计使序号天然等价于「流内偏移」，从而让接收方能用一个数字表达整段前缀的接收状态。这也意味着序号空间是**环形**的（模 $2^{32}$），比较序号必须用「模运算下的先后」，而不能用无符号整数直接比大小——这是实现 TCP 时最容易出错的地方之一。

## 二、核心原理
TCP 把应用数据看作无结构字节流，每个字节分配一个 32 位序号。报文段首部的 `seq` 填该段首个数据字节的序号；确认号 `ack` 采用累计确认（cumulative ACK），表示「所有小于 ack 的字节均已按序收到，期望从 ack 开始接收」。

初始序号 ISN 随机生成（RFC 6528），以防御序列号预测攻击与旧连接残留报文混淆。SYN 与 FIN 各消耗一个序号（占据一个字节的虚拟位置），因此纯 ACK 不消耗序号。接收方通常延迟确认（delayed ACK，约 200ms 内合并）以减少段数，但每两个数据段或超时即需确认，避免发送方误判丢包。

延迟确认与 Nagle 算法同时启用时会产生「交互式卡顿」：Nagle 等 ACK 才发下一小段，而延迟 ACK 在等更多数据才回 ACK，双方互相等待直到 200ms 定时器到期。这是「小包延迟高」的经典成因，通常通过 `TCP_NODELAY` 或合并写解决。

序号比较必须用环形语义：定义「a 在 b 之前」为 $(int32)(a-b) < 0$。若直接用无符号比较，在序号绕回处会得出完全错误的结论，导致接收方把新数据当旧数据丢弃（或反之）。

## 三、形式化与数学基础
发送方已发送未确认区间为 $[U, S)$，下一段 `seq = S`，段长 $L$，发送后 $S \mathrel{+}= L$。累计确认：

$$ ack = \min\{ b \mid \text{所有序号} < b \text{ 的字节均已按序到达} \} $$

即 ACK 指向「第一个缺口前的下一个字节」。RTT 估计（RFC 6298）：

$$ SRTT = (1-\alpha)SRTT + \alpha \cdot RTT,\quad \alpha = 1/8 $$
$$ RTTVAR = (1-\beta)RTTVAR + \beta|SRTT - RTT|,\quad \beta = 1/4 $$
$$ RTO = SRTT + 4 \cdot RTTVAR,\quad RTO \ge 1\text{s} $$

序号空间为 32 位，约 4 GB 数据后绕回，PAWS（RFC 7323）用时间戳防止绕回误判。

环形比较的形式化：设序号空间 $M = 2^{32}$，定义 $a \prec b \iff 0 < (b - a) \bmod M < M/2$。该关系仅在「两序号相距小于 $M/2$」时可靠，这也解释了为什么窗口大小必须小于 $M/2$——否则无法区分「很旧的数据」与「很新的数据」。窗口缩放上限（缩放因子最大 14，即窗口最大 $2^{30}$）正是为满足这一约束而设。

## 四、代码实现
```c
// RFC 9293 TCP 首部（简化，网络字节序）
struct tcphdr {
    uint16_t sport, dport;
    uint32_t seq;    // 序号：本段首字节在流中的位置
    uint32_t ack;    // 确认号：ACK 标志置位时有效
    uint8_t  off;    // 数据偏移（首部长度，单位 4 字节）
    uint8_t  flags;  // SYN/FIN/ACK/RST/PSH...
    uint16_t rwnd;   // 接收窗口
    uint16_t csum, urp;
};
```

发送方维护 `snd_una`（最早未确认）、`snd_nxt`（下一个待发），二者之差即已发送未确认字节数。`rcv_nxt` 为接收方期望的下一字节。

环形序号的正确比较方式：

```c
// 判断 a 是否在 b 之前（TCP 环形序号语义）
static inline int seq_before(uint32_t a, uint32_t b)
{
    return (int32_t)(a - b) < 0;   // 有符号差值，自动处理绕回
}
// 接收方判定段是否可接受：落在 [rcv_nxt, rcv_nxt + rcv_wnd) 内
static inline int seq_acceptable(uint32_t seq, uint32_t rcv_nxt, uint32_t rcv_wnd)
{
    return (int32_t)(seq - rcv_nxt) >= 0 &&
           (int32_t)(seq - rcv_nxt) < (int32_t)rcv_wnd;
}
```

## 五、与其他技术对比
累计 ACK 实现简单、对乱序鲁棒，但只能告知「第一个缺口」，不能精确告知丢了哪些段。选择确认 SACK（RFC 2018）用 TCP 选项携带多个 $[left,right)$ 区间，弥补该缺陷，适合高 BDP（带宽时延积）链路上的多段丢失。

与之相对，Go-Back-N 在链路层用单个确认号，选择性重传（Selective Repeat）更接近 SACK 思想；TCP 因字节流语义选择累计 ACK + 可选 SACK 的组合。QUIC（RFC 9000）则用基于包的帧确认（ACK Frame），可精细表达多个已收包区间。

| 机制 | 确认粒度 | 缺口信息 | 重传效率 | 典型场景 |
| --- | --- | --- | --- | --- |
| 累计 ACK | 字节前缀 | 仅第一个缺口 | 多段丢失时差 | TCP 基础 |
| 累计 ACK + SACK | 字节前缀 + 区间 | 多个已收区间 | 高 | 高 BDP 链路 |
| Go-Back-N | 帧号 | 仅下一个期望帧 | 低（回退重传） | 链路层教学 |
| Selective Repeat | 帧号 + 位图 | 逐帧 | 高 | 链路层协议 |
| QUIC ACK Frame | 包号 + 区间 | 多个已收包 | 高 | 用户态传输 |

## 六、常见误区
误区一：序号是「第几个报文段」。错，它是字节偏移（流中的第几个字节）。误区二：ACK 是已收到的最后一个字节序号。错，ACK 是期望的下一个字节（已收字节数 +1）。

误区三：ISN 从 0 开始。错，ISN 随机以防御攻击与旧报文混淆。误区四：纯 ACK 消耗序号。错，只有携带数据的段、SYN、FIN 消耗序号。误区五：累计 ACK 能定位所有丢失段。错，只能定位第一个缺口，需 SACK 补充。

误区六：用无符号比较判断序号先后。错，必须用环形（有符号差值）语义，否则绕回处判断相反。误区七：空 ACK 段可以随意重复发送而无需考虑序号。错，纯 ACK 段虽不消耗序号，但若序号字段填错会被对端视为不可接受段而回 RST。

## 八、面试题
1. 为什么 ISN 要随机？答：防序列号预测攻击，并避免旧连接残留报文被新连接（同四元组）误收。
2. 累计确认与 SACK 区别？答：累计 ACK 只报第一个缺口；SACK 通过选项补充报多个已收区间，减少不必要的重传。
3. 收到 1–100、201–300，ACK 回什么？答：101（缺口前的第一个未收字节），201 之后的数据虽到但累计 ACK 无法表达。
4. SYN 消耗序号吗？答：消耗，SYN 占据一个序号，故握手后数据从 ISN+1 起算。
5. 为什么窗口大小必须小于序号空间的一半？答：否则无法用环形比较区分「很旧」与「很新」的段，会出现误收旧数据。
6. 延迟确认与 Nagle 同时开启会怎样？答：互相等待，交互式请求出现固定量级延迟（约 200ms），需 `TCP_NODELAY` 或合并写。

## 九、演进与趋势
多路径 TCP（MPTCP，RFC 8684）每个子流有独立序号空间，并引入 Data Sequence Number（DSN）做跨子流重排；TCP Timestamps（RFC 7323）辅助更精确 RTT 测量与 PAWS。

随着 QUIC（RFC 9000）兴起，其确认机制改为基于包的帧确认，支持乱序包的精细确认，与 TCP 累计 ACK 形成对照；这对视频/游戏等乱序敏感场景更友好。由于 QUIC 序号严格单调且不可重复使用（即使重传也用新包号），它天然避免了 TCP 序号复用带来的「重传二义性」问题。

## 十、小结
序号标识字节位置、累计 ACK 确认连续前缀，配合 ISN 随机化与 RTT 估计，构成 TCP 可靠传输基石；SACK 与 Timestamps 是重要增强，分别补足多段丢失定位与 RTT 测量精度。掌握「序号是字节偏移、ACK 是期望下一位」与「环形比较」这两条，是正确实现与调试 TCP 的前提。
