# 快速重传与快速恢复

> 对应 RFC 5681（TCP 拥塞控制）；Kurose & Ross 第 3 章。

## 一、背景与挑战
仅靠超时重传恢复丢包平均要等一个 RTO（常达数百毫秒），太慢。若接收方每收到一个失序段就回重复 ACK（dup ACK），发送方可据此在超时前主动重传。

## 二、核心原理
当发送方收到 3 个重复 ACK（即第 4 个相同 ACK），判定首个未确认段丢失，立即重传（fast retransmit），不必等超时。随后进入快速恢复：不把 cwnd 降到 1，而是减半并谨慎探测。

## 三、形式化 / 数学基础
Reno 行为（RFC 5681）：
检测到 3 个 dup ACK：$ssthresh = \max(cwnd/2,\ 2\cdot SMSS)$；$cwnd = ssthresh + 3\cdot SMSS$（每收到 1 个 dup ACK 加 1 SMSS，计入已离网段）；新数据被 ACK 时 $cwnd = ssthresh$ 进入拥塞避免。

## 四、代码实现
```c
if (dupack_count == 3 && !in_fast_recovery) {
    ssthresh = max(cwnd / 2, 2 * SMSS);
    cwnd = ssthresh + 3 * SMSS;   // 快速重传 + 进入快速恢复
    retransmit(head_of_queue);
}
```

## 五、与其他技术对比
Tahoe 在丢包时 cwnd 直接回到 1（慢启动），恢复慢；Reno 引入快速恢复保留部分窗口。SACK 增强的快速重传可一次重传多个丢失段，而非每 3 dup ACK 才一个。

## 六、常见误区
误区一：收到 3 个 dup ACK 就重传所有未确认段。错，只重传第一个缺口段。误区二：快速恢复会重置 ssthresh。错，ssthresh 已在进入时设置。误区三：dup ACK 一定代表丢包。错，也可能只是乱序。

## 九、演进与趋势
CUBIC（RFC 9438）用凹函数逼近 ssthresh，对大 BDP 友好；SACK + 丢包重排（RACK，RFC 8985）用时间而非计数判断重传。

## 十、小结
3 个 dup ACK 触发快速重传，快速恢复让 cwnd 减半而非归零，是 TCP 高效恢复丢包的核心。
