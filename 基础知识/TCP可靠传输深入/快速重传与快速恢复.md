# 快速重传与快速恢复

> 对应 RFC 5681（TCP 拥塞控制）、RFC 6675（SACK 重传）、Kurose & Ross《Computer Networking》第 3 章、Stevens《TCP/IP Illustrated》卷一第 21 章。

## 一、背景与挑战
仅靠超时重传恢复丢包，平均要等一个 RTO（常达数百毫秒），对交互与短流极不友好。若接收方每收到一个失序段就回重复 ACK（duplicate ACK，dup ACK），发送方可据此在超时前主动重传，从而把丢包恢复时间从「RTO 量级」降到「一个 RTT 量级」。快速重传（fast retransmit）与快速恢复（fast recovery）正是利用 dup ACK 的机制。

它属于拥塞控制的一部分：丢包被解释为「网络可能拥塞」，因此重传的同时要降窗，但又不能像慢启动那样把吞吐打回原形。

「3 个 dup ACK」这一阈值的选择有着直接的工程含义：若某段只丢失一个，且其后至少三个段成功到达并被缓存，接收方就会发出三个重复 ACK。反过来，若丢失发生在窗口尾部（后面没有足够的段到达），就无法凑齐三个 dup ACK，只能靠超时兜底——这正是「尾部丢包（tail loss）」必须引入 TLP/RACK 的原因。

## 二、核心原理
当发送方收到 3 个重复 ACK（即第 4 个相同 ACK，确认号不变但非重传触发），判定首个未确认段丢失，立即重传该段（fast retransmit），不必等超时。随后进入快速恢复：不把 cwnd 降到 1（像慢启动那样），而是减半并谨慎探测，以保留部分吞吐。

注意：dup ACK 也可能仅由正常乱序引起（通常 1–2 个），因此取 3 个作为阈值以容忍少量乱序、避免误重传。只有持续 3 个相同 dup ACK 才强烈暗示「首个段确实丢了」。

NewReno 对「一个窗口内多个丢包」做了改进：在快速恢复期间，只有「部分确认（partial ACK，确认号前进了但未覆盖全部在途数据）」时才判断还有丢包，并对新确认点重传，同时保持恢复状态，直到「完整确认（full ACK）」才退出恢复。这避免了 Reno 每个丢包都要重新触发一次快速恢复、导致 cwnd 反复减半。

SACK（RFC 2018/6675）则用「计分板（scoreboard）」直接记录哪些字节已收，从而可以一次重传多个已知丢失段，并按「管道中估计的在途量」决定还能重传多少，不必依赖 dup ACK 数量。

## 三、形式化与数学基础
Reno 行为（RFC 5681）：检测到 3 个 dup ACK 时

$$ ssthresh = \max(cwnd/2,\; 2\cdot SMSS) $$
$$ cwnd = ssthresh + 3\cdot SMSS $$

（每收到一个 dup ACK 把 cwnd 加 1 个 SMSS，计入已离网、在途的段）；当新数据被 ACK 时，$cwnd = ssthresh$，进入拥塞避免（线性增）。拥塞避免阶段：

$$ cwnd \mathrel{+}= SMSS \cdot SMSS / cwnd \quad \text{每收到一个 ACK} $$

恢复时间对比可用下式直观体现：超时恢复约需 $\text{RTO} \approx SRTT + 4\cdot RTTVAR$，而快速重传只需约 $1\sim 2$ 个 RTT（含检测与重传到达）。在高 BDP 链路上，RTO 常达数百毫秒，而 RTT 可能只有几十毫秒，差距可达一个数量级。

SACK 下的「计分板」判定重传量的形式化思路：设已收区间集合为 $S$，最高已收序号为 $H$，则「估计在途字节数」$\text{pipe} \approx (H - snd\_una) - |S|$，允许新重传量不超过 $cwnd - \text{pipe}$。这使 SACK 能在一次恢复中重传多个丢失段，而不必每 3 个 dup ACK 才前进一段。

## 四、代码实现
```c
// 简化自拥塞控制状态机
if (dupack_count >= 3 && !in_fast_recovery) {
    ssthresh = max(cwnd / 2, 2 * SMSS);
    cwnd = ssthresh + 3 * SMSS;        // 快速重传 + 进入快速恢复
    retransmit(head_of_queue);         // 仅重传第一个缺口段
    in_fast_recovery = true;
}
// 之后每来一个 dup ACK：cwnd += SMSS（膨胀窗口，反映在途段）
```

带 SACK 时（RFC 6675）按「计分」（scoreboard）一次重传多个丢失段，而非每 3 个 dup ACK 才一个。这显著改善多段丢失时的恢复效率。

NewReno 的部分确认处理示意：

```c
// 部分确认：确认号前进但未覆盖恢复前的最高序号
if (in_fast_recovery && ack > snd_una && ack < recover) {
    partial_acks++;
    retransmit(first_unacked_segment());   // 重传新暴露的缺口，保持恢复态
    cwnd = ssthresh + 3 * SMSS - partial_acks * SMSS;  // 避免窗口虚高
} else if (ack >= recover) {
    in_fast_recovery = false;              // 完整确认，退出恢复
    cwnd = ssthresh;
}
```

## 五、与其他技术对比
| 算法 | 丢包时 cwnd | 恢复速度 | 特点 |
| --- | --- | --- | --- |
| Tahoe | 回到 1（慢启动） | 慢 | 早期版本，无快速恢复 |
| Reno | 减半（ssthresh） | 较快 | 引入快速恢复 |
| NewReno | 减半 + 部分确认处理 | 快 | 单窗口多丢包不重复减半 |
| SACK/NewReno | 减半 + 多段重传 | 更快 | 处理多段丢失 |
| CUBIC | 凹函数逼近 ssthresh | 大 BDP 友好 | RFC 9438 |
| BBR | 建模 BDP，不以丢包为唯一信号 | 高吞吐低排队 | 基于带宽与 RTT 模型 |

Reno 比 Tahoe 保留更多窗口；SACK 增强后可一次重传多个丢失段，而非每 3 dup ACK 才一个。CUBIC 与 BBR 则跳出「丢包即拥塞」的范式：CUBIC 用三次函数曲线在大 BDP 下更快恢复窗口，BBR 直接测量瓶颈带宽与最小 RTT，避免把随机丢包误判为拥塞。

## 六、常见误区
误区一：收到 3 个 dup ACK 就重传所有未确认段——错，只重传第一个缺口段（Reno）；SACK 才按计分重传多个。误区二：快速恢复会重置 ssthresh——错，ssthresh 在进入时已设置。

误区三：dup ACK 一定代表丢包——错，也可能只是乱序（故阈值取 3）。误区四：快速恢复期间窗口无限增长——错，新数据 ACK 到来后 cwnd 回落到 ssthresh 进入拥塞避免。误区五：以为快速重传能替代超时——它只处理「有 dup ACK」的丢包，尾部丢包仍需超时/Tail Loss Probe。

误区六：以为「重传后立即再发新数据」总是安全的——若重传段与在途段一起涌入，可能加重拥塞，需受 cwnd 约束。误区七：混淆「部分确认」与「重复 ACK」——前者确认号前进（说明有数据到达），后者确认号不变（说明只有失序段到达）。

## 八、面试题
1. 为什么是 3 个 dup ACK 而非 1 个？答：容忍正常乱序（通常 1–2 个 dup ACK 由乱序引起），避免误重传。阈值过大则恢复延迟、过小则误触发。
2. Reno 与 Tahoe 区别？答：Tahoe 丢包后 cwnd 回 1；Reno 引入快速恢复，cwnd 减半而非归零，恢复更快。
3. 快速恢复期间 cwnd 如何变化？答：每来一个 dup ACK 加 1 SMSS（反映在途段），新数据被 ACK 后回落到 ssthresh 进入拥塞避免。
4. SACK 下快速重传有何不同？答：按 scoreboard 一次重传多个丢失段，不必等每 3 个 dup ACK。
5. 为什么尾部丢包无法快速重传？答：后面没有足够数据触发 3 个 dup ACK，只能靠 RTO 或 TLP/RACK 探测。
6. NewReno 解决了 Reno 的什么问题？答：单窗口多丢包时 Reno 会重复减半，NewReno 用部分确认一次恢复多个缺口。

## 九、演进与趋势
CUBIC（RFC 9438）用凹函数逼近 ssthresh，对大 BDP 链路友好；SACK + 基于时间的重排检测（RACK，RFC 8985）用时间而非计数判断重传，解决 dup ACK 不足时的恢复慢问题。

Tail Loss Probe（TLP，RFC 8985）在 RTO 前发探测段快速恢复尾部丢包。这些机制共同把「靠超时兜底」的占比降到极低，是现代高吞吐 TCP 的关键。

## 十、小结
3 个 dup ACK 触发快速重传，快速恢复让 cwnd 减半而非归零，是 TCP 高效恢复丢包的核心；SACK、NewReno、CUBIC、RACK、TLP 是在此基础上的现代增强。理解「dup ACK 是乱序与丢包的共同信号，故需阈值与时间双重判据」，就理解了 TCP 丢包恢复设计的全部张力。
