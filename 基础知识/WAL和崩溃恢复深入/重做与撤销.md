# 重做与撤销

> 对应 Silberschatz《Database System Concepts》17.3 Recovery Algorithms，以及 ARIES Redo/Undo。

## 一、背景与挑战
崩溃后，已提交事务可能未落盘（需重做），未提交事务可能已部分落盘（需撤销）。两者必须正确区分并执行。

## 二、核心原理
Redo：从检查点重放所有日志记录的 new 值，把数据库恢复到崩溃瞬间状态（含未提交修改）。Undo：对崩溃时仍活跃的事务，按日志逆序用 old 值回滚，每步写 CLR 以防重复恢复时再次 undo。

## 三、形式化 / 数学基础
重做条件：日志记录 LSN $\ge$ 页的 `pageLSN`（即该页尚未包含此修改）。撤销沿事务的 prevLSN 链反向遍历：`undo(T) = replay old in reverse(prevLSN order)`。

## 四、代码实现
```python
def redo_pass(log, start):
    for rec in log.from_lsn(start):
        if rec.lsn >= page_lsn(rec.page):
            apply(rec.new)
def undo_pass(txn):
    rec = last_of(txn)
    while rec and not rec.is_clr:
        apply(rec.old)              # 写补偿日志
        rec = log.by_lsn(rec.prev)
```

## 五、与其他技术对比
| 操作 | 方向 | 对象 |
|------|------|------|
| Redo | 正向 | 已提交+未提交 |
| Undo | 反向 | 未提交 |

## 六、常见误区
1. 只 undo——丢失已提交数据。
2. 重做所有日志——应只重做未落盘部分。
3. undo 不用记日志——ARIES 用 CLR 保证幂等。

## 九、演进与趋势
逻辑日志（如 MySQL binlog row 格式）与物理日志结合，使 redo/undo 也能跨存储引擎与副本重放。

## 十、小结
Redo 恢复已持久化的提交结果，Undo 清除未完成修改；CLR 让 undo 可安全重复执行。
