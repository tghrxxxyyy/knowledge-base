# 预写日志

> 对应 Silberschatz《Database System Concepts》17.2 Log Structure，以及 ARIES 论文（Mohan et al. 1992）。

## 一、背景与挑战
若先改页再写日志，崩溃可能丢失已提交修改或留下未提交修改。WAL（Write-Ahead Logging）规定修改页前必须先持久化对应日志。

## 二、核心原理
WAL 原则：事务提交前，其所有修改的日志记录（含 undo/redo 信息）必须先 fsync 到日志；缓冲池页可延迟写盘。日志是顺序写，远快于随机改页。

## 三、形式化 / 数学基础
提交协议：
1. 写 redo/undo 记录到日志缓冲区
2. `fsync(log)` 成功后才返回 commit 给客户端
3. 之后页面可异步刷盘
用 LSN（Log Sequence Number）单调标识每条记录，页头存 `pageLSN` 表示本页最新修改。

## 四、代码实现
```c
void commit(Transaction *t) {
    log_write(t->last_rec);          // 追加日志
    fsync(log_fd);                   // 关键：先于返回
    t->state = COMMITTED;
}
```

## 五、与其他技术对比
| 方法 | 提交代价 | 恢复 |
|------|----------|------|
| 直写页 | 高（随机） | 简单 |
| WAL | 低（顺序） | 需 redo/undo |
| 影子分页 | 中 | 无日志 |

## 六、常见误区
1. WAL 只记 redo——也需 undo 信息回滚未提交。
2. 日志写盘即可——必须 fsync 才算持久。
3. 页面可随意延迟——但有脏页上限。

## 九、演进与趋势
Group Commit 批量 fsync 提升吞吐；分布式下 WAL 复制（同步/异步）实现副本一致。

## 十、小结
WAL 用顺序日志换随机写，以 fsync 为持久性边界，是一切崩溃恢复的基础。
