# 复制日志

> 对应 Kleppmann《DDIA》第 5 章 Replication，以及 MySQL binlog / PostgreSQL streaming replication。

## 一、背景与挑战
单实例有可用性与持久性上限。复制把日志发送到副本，提升读扩展与容灾，但需保证副本与主机一致、故障切换不丢数据。

## 二、核心原理
主库将 WAL/binlog 流推（或备拉）到从库重放。三种模式：同步（等副本确认）、异步（可能丢最后事务）、半同步（多数确认）。基于日志的复制天然支持物理复制（重放同页）与逻辑复制（按行事件）。

## 三、形式化 / 数学基础
复制滞后 $lag = T_{apply\_replica} - T_{commit\_primary}$。同步复制保证 $lag=0$ 但增加提交延迟；异步牺牲持久性换延迟。RPO 异步下可能为非零。

## 四、代码实现
```sql
-- MySQL 半同步复制
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';
SET GLOBAL rpl_semi_sync_master_enabled = 1;
-- 主库提交会等至少一个从库接收 binlog
```

## 五、与其他技术对比
| 模式 | 持久性 | 延迟 | 可用 |
|------|--------|------|------|
| 同步 | 强 | 高 | 受副本影响 |
| 异步 | 弱 | 低 | 高 |
| 半同步 | 中 | 中 | 中 |

## 六、常见误区
1. 异步复制不丢数据——故障可能丢未传日志。
2. 副本永远最新——存在复制滞后。
3. 复制=备份——副本同样会执行误删。

## 九、演进与趋势
共识复制（Raft/Paxos，如 TiDB、CockroachDB）把复制与一致性统一，自动选主与无丢失切换。

## 十、小结
复制日志把单机 WAL 延伸到多副本，同步/异步/半同步在一致性与延迟间权衡；是可用性与容灾的基础。
