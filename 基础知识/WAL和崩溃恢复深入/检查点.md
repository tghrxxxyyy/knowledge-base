# 检查点

> 对应 Silberschatz《Database System Concepts》17.4 Checkpoints，以及 ARIES 模糊检查点。

## 一、背景与挑战
若每次恢复都从日志头重放，时间随运行线性增长。检查点定期记录恢复起点，缩短恢复窗口，但需不阻塞正常处理。

## 二、核心原理
检查点记录此刻所有活跃事务与脏页表，并标记日志位置。模糊检查点（fuzzy）允许在打点期间继续修改，不要求所有脏页立即落盘，恢复时从该点之后的日志开始 redo。

## 三、形式化 / 数学基础
恢复起点 $LSN_{start\_ckpt}$ 记录于日志； Analysis 从最近完成的检查点开始。恢复时间 $\approx$ 自上次检查点以来的日志量，与总日志长度无关。

## 四、代码实现
```python
def checkpoint():
    begin = log_append(("<BEGIN CKPT>", active_txns(), dirty_pages()))
    flush_all_dirty_pages()           # 模糊检查点可省略此步
    log_append(("<END CKPT>", begin))
```

## 五、与其他技术对比
| 类型 | 阻塞 | 恢复起点 |
|------|------|----------|
| 一致检查点 | 是 | 精确 |
| 模糊检查点 | 否 | 稍早，需 redo 补全 |

## 六、常见误区
1. 检查点=落盘全部数据——模糊检查点不必。
2. 检查点越频繁越好——频繁打点增加写负载。
3. 恢复从检查点即可——还需 Analysis 修正。

## 九、演进与趋势
增量检查点与并行刷脏（MySQL page cleaner）降低检查点抖动；云库用存储层快照替代部分检查点。

## 十、小结
检查点锚定恢复起点以控制恢复时长，模糊检查点在性能与可恢复性间取得平衡。
