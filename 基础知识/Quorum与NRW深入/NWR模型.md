# NWR 模型

> 对应 DeCandia et al. 2007《Dynamo: Amazon's Highly Available Key-value Store》（N/R/W 参数字化）；Kleppmann《Designing Data-Intensive Applications》第 5 章 replication；Gilbert & Lynch 2002 CAP。

## 一、背景与挑战

复制系统要在一致性、可用性、延迟之间取舍。Dynamo 把复制参数化为 $(N, R, W)$：$N$ 为副本总数，$R$ 为读所需确认的副本数，$W$ 为写所需确认的副本数。通过请求级调参，同一系统可在「强一致」与「最终一致」之间灵活滑动，而不必为不同业务部署不同集群。难点在于：如何选参既满足一致性语义，又不牺牲可用性与延迟，还要保证足够的耐久性（durability）。此外还要处理并发写造成的版本冲突与后台修复。

## 二、核心原理

- $N$：每个对象的副本总数（典型为 3）。
- $W$：一次写需获得确认写入的副本数。
- $R$：一次读需查询并比较的副本数。
- 关键不等式：**$W + R > N$** 时，任意读集合与最近写集合必有交集，从而读到最新值，称为强一致读；若 $W + R \le N$，读可能完全避开最新写，属最终一致。
- $W$ 与 $R$ 还可独立调节延迟与可用性：$W=1$ 写快但耐久弱，$R=1$ 读快但可能旧。
- 例：$N=3$ 时，$(W,R)=(2,2)$ 强一致且容忍 1 副本故障；$(1,1)$ 最低延迟但任副本陈旧即可能读到旧值。

实例推演（设 $N=3, W=2, R=2$）：
- 写操作向 3 个副本广播，待其中 2 个返回确认即成功（满足 $W=2$）。
- 读操作向 3 个副本取版本，比较其中 2 个（$R=2$），必有 1 个落在刚才写入的 2 副本内，故见到最新值。
- 若此时 1 个副本宕机，写仍可达 2/3、读仍可比较 2/3，服务不中断且强一致。
- 若改为 $(1,1)$，写仅 1 副本确认后即返回，读仅看 1 副本，二者可能完全避开同一副本，读到旧值。

## 三、形式化与数学基础

单个副本独立故障率为 $p$（且假设独立），则写确认数 $\ge W$ 的概率（即可耐久性下界）：

$$
P_{ok} = \sum_{k=W}^{N} \binom{N}{k} (1-p)^k p^{N-k}
$$

数据完全丢失的概率为 $P_{loss} = \sum_{k=0}^{W-1}\binom{N}{k}(1-p)^k p^{N-k}$。提高 $W$ 增大写延迟但降低丢失概率。读一致条件仍为 $W+R>N$；在 $N=3$ 下，$(W,R)=(2,2)$ 强一致，$(1,1)$ 最终一致。

## 四、代码实现

```python
# 依据 N/R/W 判定一致级别与耐久性（示意）
from math import comb

def consistency_level(N, R, W):
    return "strong" if R + W > N else "eventual"

def durability(N, W, p):
    return sum(comb(N, k) * (1 - p)**k * p**(N - k)
               for k in range(W, N + 1))

print(consistency_level(3, 2, 2))   # strong
print(durability(3, 2, 0.01))       # 至少 2 副本存活的概率
```

```python
# 读取时比对 R 个副本并顺便做 read-repair（示意）
def read_repair(replicas, key, R):
    picked = sorted(replicas, key=lambda r: r.ver, reverse=True)[:R]
    latest = max(picked, key=lambda r: r.ver)
    for r in picked:                 # 把最新值写回陈旧副本
        if r.ver < latest.ver:
            r.write(key, latest.val, latest.ver)
    return latest
```

## 五、与其他技术对比

| 维度 | 固定主从同步 | NWR 可调 | Paxos/RAFT | 读写性能 |
|------|--------------|----------|------------|----------|
| 一致性 | 由拓扑固定 | 请求级可调 | 线性一致 | 取决于 R/W |
| 可用性 | 依赖主 | 可调 R/W 取舍 | 多数派存活即可 | W/R 小则快 |
| 复杂度 | 低 | 中（需协调 R/W） | 高 | 中 |

NWR 不保证线性一致，仅保证「读到最新」的顺序/因果视图；真正线性一致需共识协议。

## 六、常见误区

1. 把 $N=3, W=1, R=1$ 当强一致：实际 $W+R=2 \not> 3$，是最终一致。
2. $N$ 小于期望容错数：例如想容忍 2 副本故障需 $N\ge 3$ 且 $W\ge 2$。
3. 以为调大 $W$ 只影响一致不影响耐久：它同时提升耐久与写延迟。
4. 忽略 read-repair：最终一致下需后台比对副本修复，否则陈旧值可能长期存在。
5. 把 NWR 当线性一致：它不提供跨 key 的全局顺序。
6. 误以为 $W=N$ 一定最好：写需全部副本确认，任一慢/故障副本都拖垮写延迟与可用性。
7. 忽略版本冲突：并发写可能都满足各自 quorum，需向量时钟/版本号检测并合并。
8. 以为 $(1,1)$ 不可用：它只是最终一致，仍可写可读，只是不保证见到最新。

## 八、面试题

1. $N=3, W=2, R=2$ 是一致还是最终一致？答：强一致，因 $W+R=4>3$，读必与最近写相交。
2. 如何提高写的耐久性？答：提高 $W$（如 2→3），但写延迟与不可用风险上升。
3. $(W=1,R=1)$ 意味着什么？答：最终一致，读写都快但可能读到旧值、易丢写。
4. NWR 能保证线性一致吗？答：不能，仅保证读到最新值，无全局顺序。
5. 为何最终一致仍需 read-repair？答：否则陈旧副本长期不被纠正，读到的旧值窗口被不必要地拉长。
6. 想容忍 2 副本故障该怎么设？答：需 $N\ge 3$ 且 $W\ge 2$（如 $N=3$ 时最多容忍 1；容忍 2 须 $N\ge 5,W\ge 3$）。

## 九、演进与趋势

按数据重要度动态设 N/R/W（冷热分层）；与 CRDT、read-repair、hinted handoff 结合，在 AP 系统中逼近更强语义。具体以官方最新文档为准。

## 十、小结

NWR 把一致性与可用性变成可调旋钮：用 $W+R>N$ 保证强一致读，用较小 $W/R$ 换低延迟与高可用。它是 AP 系统的灵活性来源，也是理解现代 KV 存储一致性的钥匙。
