# Quorum 与 CAP

> 对应 Gilbert & Lynch 2002（CAP 定理证明）；Brewer 2000（CAP 猜想）；Gifford 1979（quorum 起源）。

## 一、背景与挑战

Quorum 看似能「既要一致又要可用」，但 CAP 定理指出：在**网络分区（P）不可避免**的前提下，一致性（C）与可用性（A）不可兼得。理解 quorum 在 CAP 中的定位，才能避免「用 quorum 绕过 CAP」的误解。实际上，quorum 只是把分区下的 C/A 取舍**参数化**到 $(R,W)$ 上，而非消除它。正确认知这一点，是设计复制系统一致性的起点。

还需要澄清 CAP 中「C」与「A」的严格含义：C 指线性一致（linearizability），而非「各副本最终相同」；A 指每个非故障节点都必须在有限时间内响应，而非「系统整体还能工作」。二者定义都极其严格，因此现实系统往往既不满足严格 C 也不满足严格 A，而是落在中间地带——CAP 是边界定理，不是设计手册。

## 二、核心原理

- **无分区时**：quorum 可同时达成 C 与 A（多数派存活即可读写且强一致）。
- **发生分区时**：若坚持 $W+R>N$（强一致），则处于少数派的副本既写不成（$<W$）也读不到最新（$<R$），系统对该部分牺牲可用性以保一致——即 **CP**。
- 若放宽参数使两侧都能写（例如各自本地 $W_{local}+R_{local}>N_{local}$ 但跨侧不相交），则保 A 但产生分歧，需事后合并——即 **AP**。
- 关键：quorum 的参数是「取舍点」的旋钮，分区下无论怎么选都落在 CP 或 AP，无法两全。

实例推演（$N=5$，分区成 3|2）：
- 取 $W=R=3$：仅 3 副本一侧可达法定，2 副本一侧写不成也读不到最新 -> 表现为 CP（少数派不可用）。
- 取 $W=R=2$：每侧各自 2 副本即达法定，两侧均可独立读写 -> 表现为 AP，但分区期间产生分歧，恢复后需合并。
- 取 $W=3,R=1$：写仅 3 侧可行（CP 写），读两侧皆可（AP 读），是混合取舍。

旋转旋钮的连续效果值得体会：随着 $W$ 从 1 增到 $N$，系统从「写极快但读需扫全部」逐步转向「写极慢但读一次即可」。因此 $(R,W)$ 不只是 C/A 开关，更是读写延迟与吞吐的分配器——这是 quorum 在工程上比「CP/AP 二选一」有用得多的原因。

## 三、形式化与数学基础

设分区把 $N$ 个副本分为两侧，大小 $a$ 与 $b$（$a+b=N$，$a\ge b$）。若 $W > b$ 且 $R > b$，则大小为 $b$ 的少数侧既无法满足写法定也无法满足读法定，故该侧不可用——系统表现为 **CP**。反之若两侧各自 $W_{side} + R_{side} > a$（或 $>b$），两侧皆可独立读写，表现为 **AP**：

$$
CP \iff (W > b) \land (R > b),\quad AP \iff (W \le b) \lor (R \le b \text{ 且对侧对称})
$$

即 quorum 参数决定分区下的 C/A 取舍：法定数越过较小侧的大小，就进入 CP；否则进入 AP。

把条件改写为「临界侧大小」更便于选参：设可容忍的最大少数侧为 $b$，则要让系统在该分区下保持 CP（少数侧不可用而多数侧安全），只需 $W > b$ 与 $R > b$；反之若希望两侧都能服务（AP），需 $W \le b$ 且 $R \le b$。工程上常用 $N=3, W=R=2$ 的方案：此时 $b=1$（3 分区分成 2|1），$W=R=2 > 1$，故少数侧不可用而多数侧强一致——这就是「三副本多数派」的由来。值得注意的是，$N$ 为偶数时容忍度并不更好：$N=4$ 时多数派需 3，与 $N=3$ 的容忍故障数相同，却多消耗一个副本，故生产实践普遍偏好奇数副本。

## 四、代码实现

```python
# 分区下：某侧是否可写/可读（示意）
def side_behavior(side_size, other_size, N, W, R):
    can_write = side_size >= W          # 本侧达写法定
    can_read  = side_size >= R          # 本侧达读法定
    if can_write and can_read:
        return "AP (本侧可独立读写，可能产生分歧)"
    return "CP (本侧牺牲可用以保一致)"

# 例：N=5, 分区 3|2，W=R=3 -> 2 的那侧不可写不可读 -> CP
print(side_behavior(2, 3, 5, 3, 3))
```

```python
print(side_behavior(2, 3, 5, 3, 1))   # 混合取舍：W=3,R=1 时写 CP、读 AP

# 通用分析：枚举所有可能的 2-分区（少数侧 1..N//2），逐个判定 CP/AP
def analyze(N, W, R):
    return [(N - b, b,
             "CP" if (W > b and R > b) else
             "AP" if (W <= b and R <= b) else "混合")
            for b in range(1, N // 2 + 1)]
# analyze(5,3,3) -> 全部 CP；analyze(5,2,2) -> 全部 AP
```

`analyze` 的实用价值在于：它把「选 $W$/$R$」从直觉变成可枚举的验证。工程选参时应列出所有可能的少数侧大小（$1$ 到 $\lfloor N/2 \rfloor$），确认在最坏分区下系统的行为仍符合业务预期；若出现「混合」行，则须明确哪一侧可读写、哪一侧停服，避免上线后才发现语义不符合预期。

## 五、与其他技术对比

| 维度 | 2PC | Quorum (CP 模式) | Gossip (AP) | 取舍本质 |
|------|-----|-------------------|-------------|----------|
| 分区行为 | 整体不可用 | 少数派不可用 | 两侧皆可写 | — |
| 一致模型 | 强（线性） | 强（多数派） | 最终一致 | — |
| 取舍 | 选 C 弃 A | 选 C 弃少数派 A | 选 A 弃强 C | C vs A |
| 协调开销 | 高（需协调者） | 中（法定数） | 低（异步扩散） | — |
| 恢复成本 | 中 | 低 | 高（需合并分歧） | — |

quorum 不突破 CAP，只是让取舍在请求级可调。相较 2PC，quorum 无需中心协调者且不会因单点故障整体不可用；相较 gossip，quorum 用协调开销换来了更强的读一致性保证。

## 六、常见误区

1. 以为 quorum 能绕过 CAP：分区下仍必须在 C/A 间选边。
2. 把「多数派可读写」当成全局线性一致：仍需版本/ fencing 才线性。
3. 以为调大 $N$ 就两全：分区下法定阈值相对大小决定 CP/AP，与 $N$ 绝对值无直接关系。
4. 忽略分区恢复后的冲突：AP 模式分区期间两侧写入需合并（冲突解决）。
5. 把可用性的「多数派」等同于「一致性」：多数派只保证法定相交，不保证无分歧写入。
6. 误以为 CP 模式永远强一致：若 $W,R$ 在多数派内达成但版本未全局单调，仍可能非严格线性。
7. 忽略混合模式：W/R 不对称时可一边 CP 一边 AP，需整体评估语义。
8. 认为偶数副本更稳：$N$ 为偶数时容忍故障数不增，多数派门槛却更高，纯属浪费资源。
9. 把 CAP 当成「三选二」：P 是客观存在的环境属性而非可选项，真正的选择只在 C 与 A 之间。

## 八、面试题

1. quorum 是否违反 CAP？答：不违反，分区下仍须选 C 或 A，quorum 只是把取舍参数化。
2. 分区下 quorum 如何表现为 CP 或 AP？答：法定数越过较小分区大小则少数派不可用（CP）；否则两侧各自可写（AP）。
3. 为何无分区时 quorum 既 C 又 A？答：多数派存活即可达成强一致法定，且服务可用。
4. 分区恢复后 AP 系统怎么办？答：需冲突解决/合并（向量时钟或 CRDT），否则两侧写入分歧残留。
5. W/R 不对称时有何语义？答：可能写 CP、读 AP，需按业务分别评估一致性保证。
6. 为何生产系统偏好奇数副本？答：偶数副本不增加故障容忍度，却抬高多数派门槛，浪费资源且降低可用性。
7. 调大 $N$ 能提升一致性吗？答：不能直接提升；一致性由 $W+R>N$ 与版本机制保证，$N$ 只影响容错与开销。

## 九、演进与趋势

可调一致性在请求级暴露 CAP 取舍（如 Cassandra 的 CONSISTENCY 级别），让应用按操作自决 CP/AP；与 CRDT 结合使 AP 侧写入可无冲突合并，降低分歧成本。具体以官方最新文档为准。

另一条趋势是「PACELC 视角」的普及：除分区（P）时在 C/A 间取舍外，无分区（E）时还需在延迟（L）与一致性（C）间取舍。PACELC 把讨论从「分区时的极端选择」扩展到「日常运行时的代价」，更贴近真实系统的设计权衡——例如强一致读必然带来额外的往返或等待，这正是延迟与一致性的日常取舍。

## 十、小结

Quorum 不突破 CAP，而是把分区下的 C/A 取舍参数化到 $(R,W)$。理解这一点，才能在「什么场景该强一致、什么场景该保可用」上做出正确工程决策。

三条实践要点：先枚举最坏分区并验证 CP/AP 行为（不靠直觉）、偏好奇数副本（效率最优）、牢记分区只是极端情形而日常还有 PACELC 的延迟取舍。
