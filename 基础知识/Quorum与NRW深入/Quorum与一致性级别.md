# Quorum 与一致性级别

> 对应 Kleppmann《Designing Data-Intensive Applications》第 5 章（replication & consistency models）；Gilbert & Lynch 2002（CAP）；Vogels 2009《Eventually Consistent》。

## 一、背景与挑战

不同业务对一致性要求天差地别：金融转账需要强一致，社交 feed 流可接受最终一致。Quorum 的 $(R,W)$ 选择直接映射到这些级别，但「quorum 读」并不自动等于「线性一致」或「因果一致」——它只保证读到最新写，不提供跨对象的全局顺序。理解 quorum 能支撑哪一层一致性，是正确选参的前提，否则会出现「以为强一致实则最终一致」的隐性 bug。这要求设计者厘清一致性强弱谱系。

谱系越往上，代价越陡：最终一致几乎免费，因果一致需要跟踪依赖，线性一致需要全局协调或时钟基础设施。因此选型的第一问不是「哪种最强」，而是「业务真正需要哪一层」——多数业务实际只需要「单调读 + 会话一致」，达到线性一致往往是过度设计。

## 二、核心原理

- **强一致**：要求 $W+R>N$，读必见最新写；若进一步要求线性一致，还需全局单调版本号/时间戳与 fencing，使「后写必覆盖前读」。
- **最终一致**：$W+R\le N$，可能读到旧值，但系统保证若无新写，副本终将收敛（Vogels 2009）。
- $W$ 与 $R$ 各自可调：例如 $W=N$ 保证写已落到全副本（强耐久）但写慢；$R=1$ 读快但可能陈旧。
- 一致性级别是**谱系**而非二元：线性 > 顺序 > 因果 > 单调读 > 最终一致，quorum 主要服务于其中的「读最新」片段。

实例推演：
- 金融扣款取 $(W=N,R=N)$ 或至少 $(W+R>N)$ 强一致，宁可慢也要正确。
- 社交 feed 取 $(1,1)$ 最终一致，用户短暂看到旧内容无碍，但延迟与可用最佳。
- 若只把 $R$ 调大而不调 $W$，仍可能读到未达 $W$ 的旧写入，须二者同时满足 $W+R>N$。

把「单对象读到最新」升级为「因果一致」需要额外的依赖信息：单读最新的 quorum 无法阻止「先看到回复、再看到原帖消失」这类因果倒置。因此因果一致系统会在元数据中携带版本向量或依赖集合，读时据此过滤掉违反因果的版本——这就是 quorum 参数的「能力边界」：它只控制「多少次交集」，不携带「谁依赖谁」的信息。

## 三、形式化与数学基础

设读延迟 $L_R \propto R$，写延迟 $L_W \propto W$。系统可用度（近似，副本独立存活率 $q$）：

$$
A \approx 1 - P(\text{存活副本} < \min(W, R))
= 1 - \sum_{k=0}^{\min(W,R)-1} \binom{N}{k} (1-q)^k q^{N-k}
$$

故降低 $W/R$ 提升可用但削弱一致保证；提高则反之。线性一致还需：对任意两个操作 $a,b$，若 $a$ 在 $b$ 开始前完成，则全局顺序中 $a$ 先于 $b$——quorum 本身不保证这点。

上式还揭示了一个反直觉的结论：可用度由 $\min(W,R)$ 而非 $W$ 或 $R$ 单独决定。因此把 $W$ 提高到 $N$ 但保持 $R=1$ 时，可用度仍由 $R=1$ 主导（几乎不受影响）；而把 $R$ 也提到 $N$，则任一副本故障都会让读失败，可用度急剧下降。这解释了为什么不建议追求 $W=R=N$：它对可用性的打击是双重的，而一致性收益并不比 $W+R>N$ 的方案更高。

## 四、代码实现

```python
# 一致性级别 -> (W, R) 参数选择（示意）
def pick(N, level):
    if level == "linear" or level == "strong":
        w = N // 2 + 1
        return w, N - w + 1        # 保证 W + R > N
    if level == "durable_write":
        return N, 1                # 写全副本，读快
    return 1, 1                    # 最终一致，最快

# 单调读：记录上次读到的版本，之后只读 >= 该版本的副本
def monotonic_read(replicas, last_ver, R):
    candidates = [r for r in replicas if r.ver >= last_ver]
    return max(candidates[:R], key=lambda r: r.ver)

# 可用度估算：由 min(W,R) 决定，而非 W 或 R 单独
from math import comb
def availability(N, W, R, q):
    k = min(W, R)
    fail = sum(comb(N, i) * (1 - q) ** i * q ** (N - i) for i in range(k))
    return 1 - fail

# availability(5, 3, 3, 0.99) ≈ 0.99997；availability(5, 3, 1, 0.99) 同样 ≈ 0.99997
```

最后一行注释说明了「可用度由 $\min(W,R)$ 决定」这一结论的直接体现：把 $R$ 从 3 降到 1 并不会提升可用度，因为瓶颈在 $W=3$。反过来，若业务希望进一步提升可用性，必须同时降低 $W$ 与 $R$，代价则是一致性保证的相应削弱。

## 五、与其他技术对比

| 维度 | Quorum 强一致 | 线性一致存储 | 因果一致 | 最终一致 |
|------|---------------|--------------|----------|----------|
| 读到最新 | 是（W+R>N） | 是 | 跨因果依赖 | 延迟窗口后 |
| 全局顺序 | 否 | 是 | 仅因果序 | 否 |
| 实现成本 | 中 | 高（共识） | 中（向量时钟） | 低 |
| 典型场景 | 配置/库存 | 账户余额 | 评论线程 | feed/计数 |
| 需额外机制 | 版本 + fencing | 共识/时钟 | 版本向量 | read-repair |

quorum 不保证线性/因果，仅保证「单对象读到最新」。因此凡是涉及「多个对象之间的顺序」的场景（如余额与流水必须一致），单纯调 $W/R$ 不够，必须引入共识或事务机制。

## 六、常见误区

1. 以为 quorum 读就是线性一致——还需全局序与 fencing。
2. 盲目追求 $W=N$ 导致写不可用：任一副本故障写即失败。
3. 混淆单调读与强一致：单调读只保证不回退，不保证见到最新。
4. 以为 $R$ 大就一致性高：还需 $W+R>N$ 且写已达成 quorum。
5. 把最终一致当「不一致」：它有收敛保证（Vogels），只是有延迟窗口。
6. 忽略读修复时机：最终一致依赖 read-repair/anti-entropy 主动传播，否则收敛很慢。
7. 只调 R 不调 W 求强一致：必须二者同时越过边界，单改 R 无效。
8. 认为可用度只受 W 影响：实际由 $\min(W,R)$ 决定，$R$ 过低同样会成为瓶颈。
9. 以为 quorum 能提供跨对象顺序：它只作用于单个 key，多 key 间顺序需额外机制。

## 八、面试题

1. quorum 能保证线性一致吗？答：不能，仅保证单对象读到最新写；线性一致还需全局顺序与 fencing。
2. 如何为不同业务选 R/W？答：金融用 $W+R>N$ 强一致；feed 用 $(1,1)$ 最终一致；需耐久时提高 $W$。
3. 单调读是什么？答：记录上次读版本，后续只读不早于该版本的副本，避免读到回退的旧值。
4. 为何 $W=N$ 危险？答：写需全部副本确认，任一副本慢或故障都拖垮写可用性与延迟。
5. 最终一致靠什么收敛？答：read-repair 与后台 anti-entropy 主动比对传播最新值。
6. 调大 R 一定能强一致吗？答：不能，还需 $W+R>N$ 且写已达成 W 法定。
7. 可用度由什么决定？答：由 $\min(W,R)$ 决定；仅降低 R 而 W 仍是瓶颈时不提升可用性。
8. 多个 key 之间的顺序如何保证？答：quorum 无能为力，需共识、事务或版本依赖（因果一致）机制。

## 九、演进与趋势

客户端一致性（如 Cassandra 的 ONE/QUORUM/ALL、DynamoDB 的 ConsistentRead）把级别暴露给调用方；与 CRDT/向量时钟结合，在 AP 系统里提供更强收敛保证。具体以官方最新文档为准。

另一条趋势是「按操作选级别」的精细化：同一系统内，写订单用 QUORUM、读推荐列表用 ONE、写审计日志用 ALL，把一致性成本精确匹配到每个操作的价值上。这比「给整个系统定一个级别」更符合实际业务，但要求开发者对每个接口的语义有清晰认识。

## 十、小结

Quorum 是一致性级别的可调底座：用 $W+R>N$ 支撑强一致读，用较小参数支撑最终一致。但它只覆盖「读到最新」这一片段，完整的线性/因果一致还需额外机制。

三条选型要点：先明确业务所需的最弱可接受级别（避免过度设计）、确认可用度瓶颈在 $\min(W,R)$（不能只调一侧）、跨对象顺序必须另设机制（quorum 只管单 key）。
