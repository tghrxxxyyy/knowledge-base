# 文档评审与CI集成

> 对应 reStructuredText / MkDocs / Sphinx docs-as-code。

## 一、背景与挑战
文档靠自觉维护容易走样，错别字、断链、格式混乱无人发现，直到读者投诉。

## 二、核心原理
文档变更走与代码相同的 PR 评审；CI 自动执行拼写检查、链接校验、格式规范与构建，门禁不通过则不可合并。

## 三、形式化与数学基础
评审门禁 gate(doc_pr) = lint(d) && linkcheck(d) && build(d)。三者全真才允许 merge，把质量卡在合入前。

## 四、代码实现
```yaml
doc-ci:
  script:
    - mkdocs build --strict        # 断链即失败
    - write-good --parse *.md      # 可读性检查
    - markdownlint docs/
```

## 五、与其他技术对比
相比发布后人工校对，CI 前置拦截成本最低；相比代码 CI，文档 CI 更重内容与链接健康。

## 六、常见误区
- 校验太严（如强制句子长度）引发抵触，应聚焦客观错误。
- 只对新增文件校验，旧文档继续腐化。

## 七、与开源书/权威来源对应
docs-as-code 实践强调把文档纳入与代码同等的工程纪律。

## 八、面试题
文档 CI 应校验哪些维度？评审文档与评审代码有何不同？

## 九、演进与趋势
AI 辅助评审标记含糊表述与缺失示例，提升文档质量下限。

## 十、小结
文档评审与 CI 把质量控制前移，是文档即代码落地不可或缺的一环。
