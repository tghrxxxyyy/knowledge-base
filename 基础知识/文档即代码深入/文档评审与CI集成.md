# 文档评审与CI集成

> 对应 Anne Gentle《Docs Like Code》与 mkdocs build --strict、Vale、markdownlint 等文档工具链的官方文档。

## 一、背景与挑战
文档靠个人自觉维护，必然走样：错别字无人纠正、链接悄悄失效、格式各行其是、示例与代码脱节。问题往往在读者投诉时才被发现，而此时错误已经传播了数月。根因在于文档缺乏与代码同等的工程纪律——代码有评审、有测试、有门禁，文档却常常直接提交。

另一重挑战是「质量的主观性」：什么是好文档难以量化，若把主观偏好写成硬性门禁，会引发团队抵触，反而降低协作效率。因此文档 CI 的设计要点是：只管可客观判定的问题（死链、拼写、构建失败、格式规范），把风格偏好交给指南而非门禁。

## 二、核心原理
文档评审与 CI 的核心是把文档变更纳入与代码相同的流程：变更走 Pull Request、由人评审内容、由 CI 自动校验可自动化的部分，全部通过才允许合并。

评审关注「人该管的」：准确性（技术描述是否正确）、完整性（是否覆盖读者所需）、结构（是否易检索理解）。CI 关注「机器该管的」：拼写与术语一致性、内部与外部链接是否有效、构建是否成功、格式是否符合规范、代码块语法是否合法、是否触碰禁用词表。

关键设计原则：门禁只拦客观错误；对警告分级（error 阻断合并、warning 仅提示）；对历史文档分阶段治理，避免「一上来全库红」。

## 三、形式化与数学基础
把一次文档 PR 的质量门禁记为布尔断言：

$$ \text{gate}(doc\_pr) = \text{lint}(d) \wedge \text{linkcheck}(d) \wedge \text{build}(d) \wedge \text{spell}(d) $$

只有当四项全部为真（$\wedge$ 为逻辑与）时，合并才被允许。这是「合入前拦截」，其成本远低于发布后返工。

进一步可把校验结果按严重度分级，定义阻断集合：

$$ F_{block} = \{\, e \in E \mid \text{severity}(e) = \text{error} \,\} $$

要求 $|F_{block}| = 0$ 才通过，而 warning 级问题允许存在但计入技术债看板。这样既守住底线，又给治理留出渐进空间。链接检查可形式化为对文档引用的邻接集合 $L(d)$ 逐个做可达性验证，任一不可达即为一条 error。

## 四、代码实现
```yaml
# CI 配置示意：文档门禁
doc-ci:
  stage: test
  script:
    - mkdocs build --strict          # 构建失败或存在断链即报错退出
    - markdownlint 'docs/**/*.md'    # 格式规范检查
    - vale docs/                     # 术语、风格与可读性检查
    - lychee --offline 'docs/**/*.md'  # 文档内链接可达性
  rules:
    - changes:
        - docs/**/*
```

```bash
# 本地预检，减少 CI 往返
mkdocs build --strict
markdownlint docs/ || true
vale --minAlertLevel=error docs/
```

`--strict` 的行为、检查器的规则集与配置文件名以各工具官方文档为准；规则应显式版本化，避免上游更新导致门禁「莫名其妙」地变红。

## 五、与其他技术对比
| 方式 | 发现问题时机 | 成本 | 能发现的问题 |
| --- | --- | --- | --- |
| 发布后人工校对 | 最晚 | 最高 | 随机、不系统 |
| 发布前人工评审 | 较晚 | 高 | 内容与结构问题 |
| CI 自动校验 | 合入前 | 低 | 死链、拼写、格式、构建 |
| 编辑器实时提示 | 编写时 | 最低 | 拼写与格式 |

CI 前置拦截成本最低且最系统，但它只覆盖可自动化的问题；内容准确性与读者适配仍需人工评审。二者结合才完整。相比代码 CI，文档 CI 更偏重内容健康（链接、术语、可读性）而非逻辑正确性。

## 六、常见误区
误区一：「校验越严越好」。错，强制句长、禁用被动语态等主观规则会引发抵触，应聚焦客观错误。误区二：「只对新增文件校验」。错，旧文档会持续腐化，需分阶段全量治理。误区三：「链接检查只在联网时跑」。错，内网或离线环境应有离线校验策略，避免门禁时红时绿。误区四：「规则集不固定版本」。错，上游更新会让门禁行为漂移。误区五：「CI 通过就等于文档合格」。错，机器只管格式与链接，内容质量仍需人评审。

## 七、与开源书·权威来源对应
- Anne Gentle《Docs Like Code》：docs-as-code 的代表性实践著作，主张文档应享有与代码同等的工程流程。
- MkDocs 官方文档：`mkdocs build --strict` 等构建与校验能力。
- Vale 官方文档：基于规则的散文风格与术语检查。
- markdownlint 官方文档：Markdown 格式规范与规则集。
- Google 开源项目文档风格指南：术语与写作风格的权威参考，具体条目以官方最新版本为准。

## 九、演进与趋势
AI 辅助评审正在成为新一层：自动标记含糊表述、缺失示例、术语不一致与可能过期的段落，把 reviewer 的注意力引向真正需要判断的地方，从而抬高文档质量的下限。同时，链接与拼写检查向「语义级」演进（如检测过期的 API 用法）。趋势不是用 AI 取代门禁，而是「机器守客观底线、AI 提示可疑点、人来下最终判断」。

一套可落地的文档 CI 清单：

- 构建：mkdocs build --strict 或 sphinx-build -W，断链即失败。
- 格式：markdownlint 校验标题层级、列表缩进与空行规范。
- 拼写与术语：codespell、vale 检查拼写与受控词表。
- 链接：内链与外链可达性检查，离线场景使用缓存或白名单。
- 示例：文档中的代码片段纳入测试运行。
- 门禁分级：error 阻断合并，warning 进入技术债看板。

评审时人工应重点确认：

- 技术描述是否与当前实现一致（CI 无法判断）。
- 是否覆盖读者完成任务所需的最少信息。
- 结构是否便于检索，长文是否有清晰导航。
- 破坏性变更是否给出迁移说明。

## 十、小结
文档评审与 CI 把质量控制前移到合入之前，是文档即代码落地的关键一环。它的设计哲学是分工：机器负责客观、可枚举的检查（构建、链接、格式、拼写），人负责准确性与读者适配。只拦客观错误、对警告分级、对历史分阶段治理，才能在守住质量底线的同时不制造协作摩擦。
