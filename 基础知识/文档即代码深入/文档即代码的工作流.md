# 文档即代码的工作流

> 对应 reStructuredText / MkDocs / Sphinx docs-as-code。

## 一、背景与挑战
文档散落在 Wiki、脑图与口头沟通中，与代码脱节、易过期，且修改无评审、无历史。

## 二、核心原理
把文档当作源码：存于同一仓库，用 Markdown/rST 编写，经 PR 评审、CI 校验、自动构建发布，版本与代码对齐。

## 三、形式化与数学基础
文档 d 与代码 c 同处版本树 V。每次提交产生 (c, d) 的联合差异 Δ；CI 校验 doc-lint(Δ.d) 保证不破损、链接有效。

## 四、代码实现
```bash
# 文档随代码提交，CI 校验链接与拼写
mkdocs build --strict     # 断链即失败
# 合并后自动部署到站点
mkdocs gh-deploy
```

## 五、与其他技术对比
相比传统 Wiki，文档即代码有评审与历史；相比纯注释，它面向读者、更完整。代价是需要构建流程。

## 六、常见误区
- 文档与代码放不同仓库，版本仍脱节。
- 只建不校验，死链与过期内容累积。

## 七、与开源书/权威来源对应
MkDocs/Sphinx 官方均将"源文件 + 构建"作为 docs-as-code 的核心范式。

## 八、面试题
文档即代码相比 Wiki 的优势？CI 能为文档做什么？

## 九、演进与趋势
文档与 OpenAPI、类型定义联动，实现接口文档自动同步。

## 十、小结
文档即代码用工程化手段保证文档可评审、可验证、可发布，是知识不腐化的关键。
