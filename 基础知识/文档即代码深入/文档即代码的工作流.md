# 文档即代码的工作流

> 对应 Anne Gentle《Docs Like Code》与 MkDocs、Sphinx 官方文档中的 docs-as-code 范式。

## 一、背景与挑战
在传统协作方式下，文档散落在 Wiki、脑图、聊天记录和口头沟通中：与代码脱节、极易过期、修改无评审、历史不可追溯、版本与代码对不上。读者看到的是「某个时间点的快照」，无法确认它描述的是哪个版本的软件。当代码快速迭代时，文档迅速沦为「过期的承诺」。

问题的根源不在于写作能力，而在于流程：文档没有进入软件的工程生命周期。文档即代码（docs-as-code）要解决的，就是把文档当作源码来管理——与代码同仓库、同流程、同工具链。

## 二、核心原理
文档即代码的核心主张：文档不是交付物的附属品，而是与代码并列的源文件。其工作流包含几个关键约定：

- 同仓：文档与代码放在同一仓库，避免版本脱节。
- 同格式：用纯文本标记语言（Markdown 或 reStructuredText）编写，便于 diff、合并与代码审查。
- 同流程：文档变更走 Pull Request，经人工评审 + CI 校验后合并。
- 同发布：合并后由 CI 自动构建为站点或其它格式并部署。
- 可追溯：文档的历史即版本历史，任意版本可回溯对应代码。

这套约定把「文档质量」从个人自觉，变成流程保障的必然结果。

## 三、形式化与数学基础
把文档 $d$ 与代码 $c$ 视为同处一个版本树 $V$ 中的两个受管对象。每次提交产生联合差异：

$$ \Delta = (\Delta c,\ \Delta d) $$

文档门禁要求对文档部分的差异执行校验函数并通过：

$$ \text{doc-lint}(\Delta d) = \text{true} $$

从而在合入前拦截断链、拼写与格式破损。发布环节可抽象为一个纯函数，把源文件集合映射为站点产物：

$$ \text{build}: (\text{source files},\ \text{nav}) \to \text{site} $$

由于构建是确定性的纯映射，同样的源必然得到同样的产物，这为「可复现的文档发布」提供了基础。文档与代码的对齐关系可记为 $\text{doc}(v) \leftrightarrow \text{code}(v)$，即每个文档版本对应一个代码版本。

## 四、代码实现
```bash
# 本地预览：边写边看
mkdocs serve

# 构建并严格校验（断链即失败），用于 CI
mkdocs build --strict

# 合并后自动发布到站点
mkdocs gh-deploy
```

```yaml
# CI 流水线示意：文档随代码提交即校验并发布
docs:
  script:
    - mkdocs build --strict        # 构建与断链校验
    - markdownlint 'docs/**/*.md'  # 格式规范
  deploy:
    script:
      - mkdocs gh-deploy --force   # 发布到 Pages
    only:
      - main
```

具体命令与参数以 MkDocs、Sphinx 及各 CI 平台的官方文档为准。

## 五、与其他技术对比
| 维度 | 文档即代码（Git + 纯文本） | 传统 Wiki | 代码内注释 | 商业 CMS |
| --- | --- | --- | --- | --- |
| 版本历史 | 强（git） | 弱/中 | 强 | 中 |
| 评审流程 | 有（PR） | 无/弱 | 有 | 一般无 |
| 与代码对齐 | 强 | 弱 | 天然 | 弱 |
| 面向读者 | 是 | 是 | 否 | 是 |
| 门槛 | 需构建流程 | 低 | 低 | 低 |

相比 Wiki，文档即代码有评审与可追溯的历史；相比代码注释，它面向读者、结构更完整；代价是需要维护一套构建与发布流程。对中小项目，这套流程的收益通常远超成本。

## 六、常见误区
误区一：「文档与代码放不同仓库」。错，版本仍会脱节，失去对齐的基础。误区二：「只建站点不校验」。错，死链与过期内容会持续累积。误区三：「文档即代码等于用 Markdown」。错，格式只是表象，核心是评审、校验、发布一体化的流程。误区四：「把全部内容塞进仓库」。错，需与代码相关的文档入仓，纯营销内容可另置。误区五：「合并即完成」。错，还应触发自动构建与发布，使文档真正到达读者。

## 九、演进与趋势
趋势之一是文档与接口定义联动：从 OpenAPI、类型定义、Schema 自动生成并同步 API 文档，实现「一处定义、多处一致」。趋势之二是文档质量的可观测化：把断链率、过期率、示例失败率纳入看板持续跟踪。趋势之三是 AI 辅助写作与评审，把重复劳动交给模型，把判断留给作者与评审者。

最小可行落地方案：

- 文档与代码同仓，使用 Markdown 编写。
- 引入静态站点生成器与一次 CI 构建。
- 文档变更走 PR，合并后自动发布。
- 每周固定一次死链与示例巡检。

## 十、小结
文档即代码用工程化手段保证文档可评审、可验证、可发布、可追溯，是让知识不腐化的关键机制。它的精髓不在 Markdown 或某个工具，而在于把文档纳入软件的完整生命周期：与代码同仓、走同一套 PR 与 CI、由流水线自动构建发布。当流程保证了「对齐」与「校验」，文档与代码脱节这一顽疾才被系统性地根治。
