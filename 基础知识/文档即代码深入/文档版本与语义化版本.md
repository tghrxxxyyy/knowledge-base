# 文档版本与语义化版本

> 对应 Semantic Versioning 2.0.0（semver.org）与 Conventional Commits 规范。

## 一、背景与挑战
软件有版本，文档也必须随之有版本。读者可能仍在使用旧版本软件，若文档站点永远只呈现最新版，就会造成严重误导：他们按新文档操作旧软件，得到的是错误结果。文档版本与软件版本一旦错位，文档就从「帮助」变成「陷阱」。

挑战在于两条并行的需求：既要为历史版本保留可访问的文档（归档），又要让大多数用户默认看到当前稳定版的文档。同时，版本号本身需要承载「这次升级会不会破坏我的用法」这一关键信息，否则用户无法判断升级风险。

## 二、核心原理
采用语义化版本（Semantic Versioning，SemVer）标记每次发布，格式为 `MAJOR.MINOR.PATCH`，并约定递增规则：

- MAJOR：做了不兼容的 API 变更时递增，其余位归零。
- MINOR：以向后兼容的方式新增功能时递增，PATCH 归零。
- PATCH：做了向后兼容的问题修正时递增。

文档站点据此按版本归档：每个 MAJOR.MINOR 组合对应一套可访问的文档分支，站点提供版本切换器；`stable`（或 `latest`）指针指向当前稳定的推荐版本。破坏性变更必须在文档中显著标注迁移说明，MINOR/PATCH 则在对应版本分支内维护。

版本号的可读性是整套机制的基石：用户只看版本号就能判断升级是否需要改代码。

## 三、形式化与数学基础
版本号可表示为三元组：

$$ V = (x,\ y,\ z), \quad x = \text{MAJOR},\ y = \text{MINOR},\ z = \text{PATCH} $$

递增规则的序关系可形式化为：给定变更集合 $C$，若 $C$ 含不兼容变更（breaking change），则 $x \leftarrow x+1,\ y \leftarrow 0,\ z \leftarrow 0$；否则若 $C$ 含向后兼容的新功能，则 $y \leftarrow y+1,\ z \leftarrow 0$；否则 $z \leftarrow z+1$。

文档与代码的对齐关系记为：

$$ \text{doc}(v) \longleftrightarrow \text{code}(v) $$

即文档版本 $v$ 必须与代码版本 $v$ 精确对应。预发布与构建元数据可扩展为 $x.y.z\text{-}pre\text{+}build$，其比较规则以 SemVer 规范为准。维护成本的权衡体现为归档粒度：归档到 MINOR 可显著减少分支数量，同时仍能覆盖不兼容边界。

## 四、代码实现
```text
docs/
  v1.0/            # 1.x 文档分支，PATCH 修复也在此维护
    index.md
  v2.0/            # 含不兼容变更的文档
    index.md
    migration.md   # 迁移指南，必须显著入口
  stable -> v2.0   # 站点默认指向当前稳定版
```

```yaml
# 站点版本配置示意（以主题插件为准）
extra:
  version:
    provider: mike
    default: stable
```

```bash
# 发布新版本文档：切分支 + 构建 + 部署
mike deploy --push --update-aliases 2.1 stable
```

具体命令与版本插件能力以所用主题与工具的官方文档为准。

## 五、与其他技术对比
| 方案 | 兼容性可读性 | 归档能力 | 用户升级判断 | 维护成本 |
| --- | --- | --- | --- | --- |
| 语义化版本 | 强（号即语义） | 按版本分支 | 一眼可判 | 中 |
| 自由编号（如 v1, v2, v3） | 弱 | 有 | 需读文档 | 低 |
| 日期版本（YYYY.MM） | 无 | 有 | 无法判断兼容性 | 低 |
| 单版文档（只留最新） | 无 | 无 | 旧用户被误导 | 最低 |

相比单版文档，多版归档兼顾历史用户；相比自由编号，SemVer 让兼容性可一眼判断。代价是需要维护分支与迁移指南。

## 六、常见误区
误区一：「破坏性改动只升 PATCH」。错，这会误导用户，应升 MAJOR 并给出迁移指南。误区二：「文档版本与代码版本长期错位」。错，二者必须一一对应，否则读者无从判断。误区三：「归档到每个 PATCH」。错，成本过高且收益有限，通常归档到 MINOR。误区四：「stable 指针手工维护」。错，应随发布自动更新，避免指向过期版本。误区五：「迁移说明可有可无」。错，MAJOR 升级的迁移指南是文档的核心交付物之一。

## 九、演进与趋势
趋势是文档站点内置版本切换器并自动关联代码 tag，使「文档版本 = 代码版本」成为流水线的自动结果而非人工纪律。配合 Conventional Commits 与自动化发布，版本号、变更日志与文档归档可由提交信息驱动，减少人为疏漏。另一方向是把迁移指南结构化（可检索、可对照旧新用法），让 MAJOR 升级的体验更平滑。

发布检查清单：

- 版本号是否按变更类型正确递增（破坏性变更必须升 MAJOR）。
- 是否为 MAJOR 升级撰写迁移指南并置于显著入口。
- 是否为该版本创建文档分支并更新站点版本切换器。
- stable 指针是否指向正确的稳定版本。
- 变更日志是否与版本号、文档同步更新。

## 十、小结
语义化版本为文档与代码提供统一的演进坐标：版本号本身承载兼容性语义，多版归档保障各代用户都能读到与其软件相匹配的文档。它把「用户如何判断升级风险」这一体验问题，转化为版本号的纪律问题。配以自动化的站点版本切换与迁移指南，文档版本管理才能既准确又不增加太多维护负担。
