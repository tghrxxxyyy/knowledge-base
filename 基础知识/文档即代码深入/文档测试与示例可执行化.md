# 文档测试与示例可执行化

> 对应 Python doctest 官方文档与 Sphinx doctest 扩展文档。

## 一、背景与挑战
文档里的代码示例会随接口演进悄然失效：函数改了参数，示例没改；返回值结构变了，输出没更新；依赖升级了，示例跑不通。读者照着文档抄，却得到报错，对文档的信任迅速崩塌。更糟的是，这类问题不会被常规单元测试发现——因为示例不在测试覆盖范围内。

文档腐化的本质是「真相有多个副本」：代码是真相，示例是真相的转述。任何转述都会过期。可执行化要做的，是把示例从「转述」变回「真相的验证者」——让示例本身成为可运行、可断言的测试单元。

## 二、核心原理
核心思想是「文档中的示例就是测试用例」。doctest 风格下，示例以交互式会话形式书写，工具执行输入、捕获输出，并与文档中声明的期望输出比对；一致则通过，不一致即失败。CI 在每次提交时运行全部示例，保证示例与实现始终同步。

Sphinx 的 doctest 扩展进一步把散布在文档中的代码片段统一收集、执行并报告结果，使「文档构建」本身成为一次测试。实践要点包括：示例要自包含、可重复、无外部依赖；对不确定输出（时间、随机、路径）做规范化或打桩；对需要网络或数据库的示例提供 fixture 或跳过标记。

这带来一个良性约束：写文档时必须真正跑一遍示例，示例因此天然准确。

## 三、形式化与数学基础
设文档示例 $e$ 有输入 $i$ 与期望输出 $o$。doctest 执行 $e$ 得到实际输出 $o'$，断言：

$$ o' = o $$

全部示例构成集合 $E$，CI 失败的示例集合为：

$$ F = \{\, e \in E \mid o'(e) \neq o(e) \,\} $$

可执行化的目标是维持 $F = \emptyset$。对含不确定输出的示例，引入规范化函数 $\phi$ 后比较 $\phi(o') = \phi(o)$，例如把时间戳、内存地址、临时路径替换为占位符，从而在保留验证价值的同时消除伪失败。

覆盖率视角下，可定义「示例覆盖的公开接口比例」作为文档健康度指标，但它衡量的是示例广度，不等于正确性，应与 $F$ 的实时状态共同解读。

## 四、代码实现
```python
def add(a, b):
    # 示例即测试：doctest 会执行下列交互并比对输出
    # >>> add(1, 2)
    # 3
    # >>> add(-1, 1)
    # 0
    return a + b

# 运行方式：
#   python -m doctest -v example.py
# 或在 pytest 中启用 --doctest-modules
```

```python
# 含不确定输出时：规范化后再断言
import re

def normalize(text):
    text = re.sub(r"\d{4}-\d{2}-\d{2}", "<DATE>", text)
    text = re.sub(r"0x[0-9a-fA-F]+", "<ADDR>", text)
    return text
```

```text
# 示例可执行化的工程约定
- 示例自包含：不依赖网络、时间、外部文件或未声明的状态
- 需要环境时用 fixture/容器提供，或标记为跳过
- 输出中的易变部分先规范化再比对
- CI 全量运行示例，失败即阻断合并
```

## 五、与其他技术对比
| 方式 | 是否验证正确性 | 读者视角 | 覆盖范围 | 维护成本 |
| --- | --- | --- | --- | --- |
| 纯文字描述 | 否 | 好懂 | 广 | 低但易腐化 |
| doctest 示例 | 是 | 贴近读者 | 示例级 | 中（随接口更新） |
| 独立单元测试 | 是 | 不对读者可见 | 代码级 | 中 |
| 可执行 Notebook | 是 | 交互性强 | 示例到分析 | 高 |

相比纯描述，可执行示例自带验证；相比独立测试用例，它更贴近读者真实使用姿势，但覆盖应限于示例级——不该把文档测试当作完整回归测试的替代品。

## 六、常见误区
误区一：「示例依赖外部状态（时间、网络），结果不确定导致误失败」。错，应打桩或规范化，否则门禁会被噪声淹没。误区二：「只写不跑，失去执行化意义」。错，不运行的示例和普通文字没有区别。误区三：「把文档测试当成完整测试套件」。错，它只覆盖示例，不保证边界与异常路径。误区四：「输出里包含地址/时间却直接比对」。错，会造成伪失败。误区五：「示例太复杂也没关系」。错，示例越复杂越难维护，应保持最小可读。

## 九、演进与趋势
趋势是文档与交互式环境联动：可执行 Notebook、在线 Playground、以及在文档页面直接运行示例的能力，让「读文档」与「跑代码」合并。另一方向是自动生成示例（由类型与签名推导最小用法），再用可执行化保证其不腐。无论形态如何变化，核心不变——让示例成为可运行、可验证的活证据。

落地时可遵循的最小清单：

- 每个公开 API 至少有一个可运行示例。
- 示例不依赖网络、时间与未声明的外部状态。
- 不确定输出先规范化再比对。
- CI 全量运行示例，失败即阻断合并。
- 示例保持最小可读，复杂逻辑交给测试用例。

## 十、小结
文档测试把示例从易腐化的转述，变成随 CI 每次提交都接受验证的活证据。它的价值在于用工程手段消除「文档与代码不一致」这一系统性风险：只要示例必须通过测试，它就不可能悄悄过期。代价是示例必须自包含、可规范化、易维护——这恰恰也是好示例本就该有的品质。
