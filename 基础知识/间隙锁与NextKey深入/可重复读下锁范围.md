# 可重复读下锁范围

> 对应 MySQL InnoDB 官方文档 RR 隔离级别锁行为，参考 DDIA 与 cmu-db/15445-course 并发控制。

## 一、背景与挑战
在 RR 下，一条看似简单的查询实际加锁的范围往往超出直觉——不仅是命中的行，还包括其前后间隙与扫描路径上的 Next-Key 锁。理解「锁到底覆盖到哪」对诊断阻塞与死锁至关重要。

## 二、核心原理
RR 下，当前读（锁定读/更新/删除）对遍历到的每一条索引记录加 Next-Key Lock（左开右闭）。若使用唯一索引等值且命中，降级为仅记录锁；若为主键范围扫描，则扫描区间内所有记录及其左间隙均被锁。未命中区间两端也可能被锁，以阻止区间外插入移入。

## 三、形式化与数学基础
对谓词 $P$ 命中的索引键集合 $K_P$，锁范围：
$$ L = \bigcup_{k \in K_P} (prev(k), k] \;\cup\; boundary\_gaps $$
即所有命中记录的 Next-Key 区间并上扫描边界间隙。非唯一索引下 $K_P$ 含重复键，锁范围相应扩大。

## 四、代码实现
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
DELETE FROM t WHERE k >= 50;   -- 锁 [50, +\infty) 相关 Next-Key 区间
-- 另一事务 INSERT k=49 可能被左边界间隙锁阻塞
COMMIT;
```

## 五、与其他技术对比
READ COMMITTED 下 InnoDB 基本退化为记录锁、关闭间隙锁（除外键/唯一检查），锁范围远小但允许幻读。PostgreSQL 的 RR 不靠锁而靠快照，锁范围仅限真正冲突行。

## 六、常见误区
认为 RR 只锁查询返回的行——实际锁的是扫描路径上所有被访问记录及间隙。认为改隔离级别无影响——RC 与 RR 锁范围差异巨大，直接影响并发与死锁率。

## 七、与开源书/权威来源对应
InnoDB 官方「InnoDB Locking」与「Transaction Isolation Levels」；cmu-db/15445-course。

## 八、面试题
问：RR 下 DELETE 范围会锁哪些？答：扫描路径上所有命中记录的 Next-Key 锁及边界间隙。问：RC 为何锁更少？答：禁间隙锁，仅锁实际命中的记录。

## 九、演进与趋势
谓词锁/区间锁更精确表达「条件区间」，有望替代粗粒度 Next-Key，降低 RR 下的过度封锁。

## 十、小结
RR 的锁范围由扫描路径与 Next-Key 共同决定，远超「命中行」直觉，调优隔离级别需权衡并发与幻读。
