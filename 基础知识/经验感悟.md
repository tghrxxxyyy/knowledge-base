# 经验感悟

## 使用并发工具类库的感悟

一是，只知道使用并发工具，但并不清楚当前线程的来龙去脉，解决多线程问题却不了解线程。比如，使用 ThreadLocal 来缓存数据，以为 ThreadLocal 在线程之间做了隔离不会有线程安全问题，没想到线程重用导致数据串了。请务必记得，在业务逻辑结束之前清理 ThreadLocal 中的数据。

二是，误以为使用了并发工具就可以解决一切线程安全问题，期望通过把线程不安全的类替换为线程安全的类来一键解决问题。比如，认为使用了 ConcurrentHashMap 就可以解决线程安全问题，没对复合逻辑加锁导致业务逻辑错误。如果你希望在一整段业务逻辑中，对容器的操作都保持整体一致性的话，需要加锁处理。

三是，没有充分了解并发工具的特性，还是按照老方式使用新工具导致无法发挥其性能。比如，使用了 ConcurrentHashMap，但没有充分利用其提供的基于 CAS 安全的方法，还是使用锁的方式来实现逻辑。你可以阅读一下 [ConcurrentHashMap 的文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ConcurrentHashMap.html)，看一下相关原子性操作 API 是否可以满足业务需求，如果可以则优先考虑使用。

四是，没有了解清楚工具的适用场景，在不合适的场景下使用了错误的工具导致性能更差。比如，没有理解 CopyOnWriteArrayList 的适用场景，把它用在了读写均衡或者大量写操作的场景下，导致性能问题。对于这种场景，你可以考虑使用普通的 List。

其实，这四类坑之所以容易踩到，原因可以归结为，我们在使用并发工具的时候，并没有充分理解其可能存在的问题、适用场景等。所以最后，我还要和你分享两点建议：

1. 一定要认真阅读官方文档（比如 Oracle JDK 文档）。充分阅读官方文档，理解工具的适用场景及其 API 的用法，并做一些小实验。了解之后再去使用，就可以避免大部分坑。
2. 如果你的代码运行在多线程环境下，那么就会有并发问题，并发问题不那么容易重现，可能需要使用压力测试模拟并发场景，来发现其中的 Bug 或性能问题。

## 更多工程经验感悟

五是，过度信任“本地能跑”。本地环境与生产在并发量、数据量、网络、时钟、依赖可用性上完全不同。任何核心改动都应上预发/灰度，并以压测和真实流量验证，而不是“本地 OK 就发布”。

六是，忽视日志与可观测性。没有 traceId、没有关键路径埋点，线上出问题只能盲猜。应当在设计阶段就考虑日志分级、链路追踪（TraceId 透传）、指标（QPS/RT/错误率）和告警，让系统“可被观测”。

七，把异常吞掉（catch 空处理）。异常被静默吞下后，问题被掩盖，排查时毫无线索。至少要打日志，业务异常应向上抛或由统一异常处理器处理，关键路径异常要有监控告警。

八，数据库是稀缺资源，别滥用。在循环里查库、在事务里调远程接口、用 `SELECT *` 取大量无用字段、不加索引的慢 SQL，都会把 DB 拖垮。应当批量、缓存、异步，给高频查询加索引。

九，没有兜底与降级。强依赖第三方时，一旦下游抖动，上游跟着雪崩。重要链路要有超时、重试（带退避与幂等）、熔断、降级返回值或默认逻辑，保证“部分失败不影响整体”。

十，技术债不会自己消失。临时方案、复制粘贴、绕过正道的 hack，都会在未来成倍反噬。应当小步重构、补齐测试、在合适时机偿还，而不是等系统腐化到无法维护。

十一，写代码先想“怎么测”。可测试的设计（依赖注入、纯函数、清晰边界）比事后补测试轻松得多；单元测试覆盖核心逻辑，集成测试覆盖关键链路。

十二，沟通与评审胜过个人英雄主义。复杂方案先写设计文档、拉人评审，往往能提前发现盲区；Code Review 既防 bug 也传播知识，是团队最重要的质量门禁之一。

## 更多工程经验感悟（第二轮）

十三，**先测量再优化**。场景：曾把某接口从串行改并行、引入线程池，自以为提速，结果压测发现瓶颈在一条慢 SQL，并行反而打爆 DB 连接池。教训：优化前先用火焰图/APM/EXPLAIN 定位热点，用数据指路，别凭直觉动刀；多数系统瓶颈在 IO 与锁，而非算法。

十四，**警惕共享可变状态**。场景：用 `static Map` 当缓存，多实例部署后数据不一致；用普通 `HashMap` 在并发读写下出现死循环（JDK 7 头插法）。教训：跨请求/跨线程共享的状态默认就是隐患，优先不可变对象、线程封闭、`ConcurrentHashMap`、原子类；能不共享就不共享。

十五，**可观测性优先**。场景：线上偶发超时，却只有"接口慢"的笼统告警，没有 traceId、没有 RT 分布、没有依赖耗时，排查耗了一整天。教训：设计阶段就埋好日志分级、链路追踪（TraceId 透传）、指标（QPS/RT/错误率）和告警，让系统"可被观测"，故障定位从盲猜变秒级。

十六，**技术债要显性化**。场景：为赶工期用硬编码表名 + 复制粘贴绕过了正道，半年后无人敢动这段代码，改一处崩三处。教训：技术债不是不能欠，但要写进文档/卡片、标注 TODO 与偿还时机，定期排期清理；隐形的债会复利膨胀。

十七，**改动必须有回滚预案**。场景：一次配置变更导致全量流量打到新逻辑，错误率飙升，却只能"再发一版修复"，恢复花了 20 分钟。教训：任何线上变更（代码/配置/数据）都要想好"怎么撤"——开关（Feature Flag）、灰度、配置回退、数据备份，保证一键回滚。

十八，**配置与密钥不要硬编码**。场景：测试库密码写死在代码里被提交，密钥泄露只好全量轮换；环境差异靠改代码发布，事故频发。教训：配置外置（`application.yml`/配置中心），密钥走 KMS/环境变量/密钥管理，敏感信息绝不入仓。

十九，**容量规划与压测不能省**。场景：大促前没压测，峰值一来缓存击穿 + DB 被打满，服务雪崩。教训：核心链路上线前做容量评估与全链路压测，估算 QPS/连接数/内存，留好余量；对突发流量有扩容与限流预案。

二十，**关注依赖版本与供应链**。场景：升级一个间接依赖后，传递引入了不兼容版本，启动即报 `NoSuchMethodError`；或某开源库爆出 CVE 却长期未升级。教训：锁定关键依赖版本，定期 `dependency-check`/SCA 扫描，升级前看 changelog 与破坏性变更。

二十一，**关注"慢路径"与边缘 Case**。场景：主流程测试充分，却漏了"空列表/超长输入/并发首次"等分支，线上在这些边界崩了。教训：写代码时把非法输入、空值、超大值、并发首访当成一等公民覆盖；单测与异常用例比happy path 更重要。

二十二，**不要过度设计（YAGNI）**。场景：为"未来可能的多租户"提前做了三层抽象，结果项目一年没用上，反而增加理解成本与 bug 面。教训：只解决当下真实需求，抽象等到第三次出现相似逻辑（三次法则）再提炼；奥卡姆剃刀同样适用于代码。

二十三，**数据库结构变更要在线且可回滚**。场景：`ALTER` 大表锁表 10 分钟，写入全部阻塞；想回退却只能再锁一次。教训：大表用 Online DDL（`ALGORITHM=INPLACE, LOCK=NONE`）或 gh-ost/pt-osc 灰度；变更前向后再兼容（先加字段后删旧），保证可回退。

二十四，**写文档是工程能力的一部分**。场景：核心模块只有作者懂，作者休假时线上出问题无人能救；评审靠口述，决策无据可查。教训：关键设计写设计文档（背景/方案/权衡/回滚），接口写清楚契约；好文档让系统可被接手、决策可追溯，是团队杠杆。

二十五，**给关键路径设评审清单**。场景：每次上线凭记忆检查，总漏项（漏加索引、漏配告警、漏开开关）。教训：沉淀一份上线/设计评审清单（Checklist），覆盖监控、回滚、容量、安全、数据兼容，发布前逐项打勾，把个人经验变成团队流程。

## 第二轮补充：更多工程经验（二十六 ~ 三十八）

二十六，**监控要有"黄金指标"**。场景：监控面板堆了上百张图，告警却从没配，真出事没人收到。教训：每个核心服务盯 4 个黄金指标——延迟（RT/P99）、流量（QPS）、错误率、饱和度（CPU/连接/队列）；告警基于 SLO 触发，而非"有图就行"。

二十七，**别让定时任务成暗雷**。场景：一个 cron 每天凌晨批量跑，某天数据量翻倍跑了 3 小时，撞上早高峰把 DB 拖垮。教训：批处理要限速、分片、错峰；加超时与失败告警；大任务用分布式调度（XXL-JOB/ElasticJob）分片，别单机裸跑。

二十八，**幂等是写接口的底线**。场景：客户端超时重试导致重复下单、重复扣款。教训：写接口默认按业务唯一键幂等（去重表/状态机），尤其支付、下单、通知类；永远别假设"调用方不会重试"。

二十九，**日志要能重建现场**。场景：线上报错只有一行 `NullPointerException`，没有上下文（谁、什么参数、哪个租户）。教训：日志带关键业务标识（userId/orderId/traceId）与入参摘要；敏感信息脱敏；错误日志要有"够定位"的上下文。

三十，**谨慎使用分布式锁**。场景：用 Redis 锁没设超时，持锁实例 GC 长停顿，锁过期后别的实例进入，出现双写。教训：锁必须有过期兜底；缩短锁内耗时；能走数据库唯一约束/乐观锁就别用分布式锁；Redlock 依赖时钟假设有争议。

三十一，**配置变更也要灰度**。场景：一键把全局超时从 3s 改成 30s，下游被积压请求打满。教训：配置同样要灰度 + 监控，改动可快速回退；影响面大的配置用动态推送 + 小流量验证后再全量。

三十二，**容量要留余量**。场景：连接池设 20，流量翻倍后大量请求等连接超时。教训：连接池/线程池/队列按峰值 × 冗余设置；压测验证；关键资源有熔断与降级，别让一个资源耗尽拖垮全局。

三十三，**别只信"测试环境通过了"**。场景：测试库数据量小、并发低，SQL 走得好好的，上生产因数据倾斜走全表扫，直接慢查询告警。教训：性能验证要用接近生产的量与分布；关注"数据倾斜/热点"而非平均值。

三十四，**降级开关要默认可关**。场景：新接入的推荐服务抖了，却没有开关，只能发版摘掉，恢复慢。教训：非核心依赖加 Feature Flag/降级开关，默认可一键关；核心链路不依赖不稳定旁路。

三十五，**数据迁移要可校验**。场景：老表迁新表，跑完才发现漏了部分历史数据，且无法比对。教训：迁移前后做行数/校验和/抽样比对；双写过渡期比对一致性；保留回退窗口，确认无误再删旧数据。

三十六，**错误要可观测可聚合**。场景：异常散在各处日志，统计错误率无从谈起。教训：统一异常体系 + 结构化日志（JSON）+ 错误码；关键错误上报监控，能按错误码聚合、按维度下钻。

三十七，**所有依赖都要设超时**。场景：调下游没超时，下游卡住，上游线程全阻塞，连锁雪崩。教训：所有远程调用、DB、缓存都设合理超时（连接 + 读）；超时值要匹配下游 SLA，不是越大越好。

三十八，**复盘写"根因"而非"背锅"**。场景：事故复盘写成"某某粗心"，同样问题三个月后重演。教训：用 5 Whys 找系统根因（流程缺失/缺监控/缺校验），改系统而非改人；把教训沉淀进 Checklist 防止复发。

## 第三轮补充：更多工程经验（三十九 ~ 五十二）

三十九，**压测要贴真实分布**。场景：压测用均匀随机 ID，线上却是少数热点用户，缓存命中率天差地别。教训：压测数据要模拟真实分布（幂律/热点），否则结论误导决策。
四十，**警惕缓存击穿式热点**。场景：明星商品缓存过期瞬间，百万请求同时回源 DB。教训：热点 key 用互斥锁重建 / 逻辑过期异步刷新 / 多级缓存。
四十一，**异步不是银弹**。场景：为提速把同步改异步，链路变长、排障难、消息堆积。教训：异步用于解耦/削峰，核心写链路慎异步，且保证可追踪。
四十二，**数据库迁移要灰度双写**。场景：直接切新表，字段映射错还无法回退。教训：双写 + 比对 + 灰度读新，确认后切读，最后停旧写。
四十三，**API 要版本与兼容**。场景：改了入参结构，老客户端全挂。教训：API 版本化（/v1）、向后兼容、废弃走公告期。
四十四，**密钥定期轮换**。场景：一个密钥泄露，无法快速替换，只能全量重启。教训：密钥经 KMS、支持热轮换，绝不硬编码。
四十五，**关注 GC 对延迟的影响**。场景：秒杀时 Full GC 卡 1s，超时率飙升。教训：监控 GC 停顿，选 ZGC/G1，给足堆，避免大对象。
四十六，**文档比想象重要**。场景：方案只有口头共识，执行中各做各的。教训：重要决策落文档，减少信息差与返工。
四十七，**留好逃生通道**。场景：灰度出问题，却只能全量回滚。教训：支持按比例/按标签回滚，灰度可控可逆。
四十八，**学习靠真实项目**。场景：光学不练，过目即忘。教训：在真实项目里用新技术，踩坑才内化。
四十九，**别忽视慢查询的隐性成本**。场景：一条慢 SQL 占满连接，拖垮整个服务。教训：慢查询治理常态化，设阈值告警，定期 review 执行计划。
五十，**限流要作用在正确位置**。场景：只对入口限流，内部批量任务把下游打挂。教训：限流覆盖入口与关键依赖调用，按资源而非只按 QPS。
五十一，**降级要默认内置而非事后**。场景：依赖抖动，临时加开关来不及。教训：非核心依赖开关默认内置，演练降级路径，别等故障现做。
五十二，**可测试性也是架构质量**。场景：核心逻辑耦合静态调用，单测要起整个容器。教训：依赖注入、纯函数、清晰边界，让核心逻辑可单测，测试才敢写、敢跑。

## 第四轮补充：更多工程经验（五十三 ~ 六十四）

五十三，**慢接口要设超时与降级**。场景：一个下游慢，调用方线程池满，连锁雪崩。教训：所有外部调用设超时 + 熔断，慢接口有降级返回值。
五十四，**数据库连接池要监控**。场景：池耗尽，新请求一直等连接，接口全超时。教训：监控活跃/空闲连接与等待数；池大小按峰值设，配超时与告警。
五十五，**避免分布式大事务**。场景：跨服务 `@Transactional` 不生效还以为安全，实则各自提交、部分成功。教训：跨服务用最终一致（消息/补偿），别依赖本地事务。
五十六，**日志级别要合理**。场景：生产开 DEBUG，磁盘写满，服务挂。教训：默认 INFO，DEBUG 按需动态开；大流量日志异步 + 采样。
五十七，**重视依赖兼容性**。场景：两库传递依赖版本冲突，启动 `NoSuchMethodError`。教训：显式锁定关键版本，依赖树定期梳理；升级看 changelog。
五十八，**防重放与防刷**。场景：下单接口被脚本刷，库存被薅。教训：关键写接口加幂等 + 频控 + 风控；参数做合法性校验。
五十九，**数据加密别自己造**。场景：自写"加密"实则易逆，泄露出事。教训：用标准算法（AES-GCM）+ 成熟库 + 密钥管理，别自创密码学。
六十，**关注慢启动与预热**。场景：刚发布实例 JVM 未预热，RT 高被摘流量。教训：灰度小流量预热；JVM 用 AOT/预热脚本，避免冷启动雪崩。
六十一，**评审要覆盖数据兼容**。场景：改字段类型没考虑旧数据，迁移后查询报错。教训：变更评审含数据兼容/迁移脚本/回退；新旧并存过渡。
六十二，**保持简洁**。场景：为炫技写复杂实现，别人看不懂也不敢改，bug 藏深。教训：代码以"能被接手"为美，复杂处加注释与测试，KISS 原则。
六十三，**监控告警要可行动**。场景：告警狂响却不知如何处理，最终被忽略。教训：告警带"谁来处理 + 怎么处理"的 runbook，无行动指引的告警不如不告警。
六十四，**把稳定性当成功能**。场景：只排期业务需求，稳定性永远"以后再说"，直到出大事故。教训：稳定性是需求的一部分，容量/容灾/演练要有专门排期与 owner。

## 第五轮补充：更多工程经验（六十五 ~ 七十七）

六十五，**缓存与 DB 一致性别强求**。场景：为强一致引入分布式事务锁缓存，性能崩。教训：用"短暂不一致 + 补偿"（Cache-Aside + binlog 删缓存），业务容忍秒级延迟。
六十六，**限流阈值要压测得出**。场景：拍脑袋设 1000 QPS，实际 300 就挂。教训：阈值来自压测与历史水位，配自动调控；过低误杀、过高无效。
六十七，**重视冷数据与归档**。场景：单表 10 亿行，查询全慢。教训：冷热分离、定期归档到历史表/数仓；索引也随数据膨胀。
六十八，**配置要有默认值与校验**。场景：缺配置项启动失败，或配错值静默异常。教训：配置给合理默认，启动时校验（端口范围、必填项），fail-fast。
六十九，**幂等键要稳定**。场景：用请求 ID 做幂等，重试时 ID 变了，去重失效。教训：幂等键用业务唯一标识（订单号），而非每次随机 ID。
七十，**异步任务要可观测**。场景：定时任务卡死无人知，数据几天没更新。教训：异步/定时任务有心跳、最后成功时间、失败告警，关键任务有 SLA。
七十一，**避免 BigDecimal 精度坑**。场景：用 double 算金额，出现 0.1+0.2≠0.3。教训：金额用 BigDecimal（String 构造）/ 分单位 long，禁 float/double 做钱。
七十二，**重视环境一致性**。场景：测试能跑、生产因 JDK/OS/参数差异崩。教训：环境尽量一致（容器化），差异显式管理，上线前类生产验证。
七十三，**日志别打敏感信息**。场景：日志打印身份证/密码，被审计出问题。教训：脱敏（掩码），密钥/令牌绝不入日志，遵守合规。
七十四，**关注锁竞争**。场景：一处 synchronized 大块，并发上不去。教训：缩小锁粒度、用并发容器/无锁；JFR/arthas 看锁竞争。
七十五，**数据库别用 SELECT ***。场景：查了大字段拖慢查询、占带宽。教训：只取所需列，大字段拆表/独立查询。
七十六，**重试要带退避与上限**。场景：下游抖动用固定间隔猛重试，把下游打挂。教训：指数退避 + 抖动 + 最大重试次数 + 死信。
七十七，**保持好奇心**。场景：只守一亩三分地，技术停滞。教训：定期看新版本/论文/别人系统，保持对"更好做法"的敏感。

## 第六轮补充：更多工程经验（七十八 ~ 八十七）

七十八，**可观测性先于功能**。场景：新功能上线时埋头写业务，忘了埋 traceId、指标与告警；上线三天后接口偶发变慢，毫无数据，全员盲猜一整天。教训：功能代码写完只是"能跑"，可观测性（日志分级 + 链路追踪 + 指标 + 告警）才是"敢上线"的前提；把埋点当验收项，没监控的功能不算完成。

七十九，**技术债显性化**。场景：为赶工期硬编码表名 + 复制粘贴绕过正道，半年后无人敢动这段代码，改一处崩三处。教训：债可以欠，但必须写进卡片/文档、标 TODO 与偿还时机、排期清理；隐形的债会复利膨胀，显性的债才是可控杠杆。

八十，**评审 Checklist 比个人记忆可靠**。场景：每次上线凭记忆检查，总漏项（漏加索引、漏配告警、漏开开关）。教训：沉淀一份上线/设计评审清单，覆盖监控、回滚、容量、安全、数据兼容，发布前逐项打勾；把个人经验变成团队可复用的流程，质量不再依赖"谁记得"。

八十一，**先测量再优化**。场景：把某接口从串行改并行、引入线程池，自以为提速，结果压测发现瓶颈在一条慢 SQL，并行反而打爆 DB 连接池。教训：优化前用火焰图/APM/EXPLAIN 定位热点，用数据指路；多数系统瓶颈在 IO 与锁而非算法，凭直觉动刀常优化不重要的 1%。

八十二，**警惕共享可变状态**。场景：用 `static Map` 当缓存，多实例部署后数据不一致；用普通 `HashMap` 并发读写出现死循环（JDK 7 头插法）。教训：跨请求/跨线程的共享状态默认是隐患，优先不可变对象、线程封闭、`ConcurrentHashMap`、原子类；能不共享就不共享。

八十三，**灰度发布黄金法则**。场景：一键全量发布新逻辑，错误率瞬间飙升，只能"再发一版修复"，恢复花了 20 分钟。教训：任何变更走小流量灰度（按用户/比例/标签），监控核心指标无异常再逐步放量；支持按比例回滚，绝不"全或无"；核心开关 + 可观测指标是灰度的两翼。

八十四，**Oncall 心智模型**。场景：半夜告警狂响，值班人慌乱重启、乱改配置，把小问题搞大。教训：Oncall 先"止血再定位"——确认影响面、有无回滚开关、是否先限流降级；建立"告警→影响评估→预案→回滚→根因"的标准动作；把排障手册（runbook）写进文档而非靠记忆，平时演练而非事故现学。

八十五，**文档即契约**。场景：服务间靠口头约定字段含义，对方改了枚举值没通知，调用方解析错乱、资损数小时。教训：接口/协议文档是跨团队契约，定义字段、取值、兼容性承诺与变更流程；改契约走评审 + 公告期，下游有过渡；文档过时比没文档更危险，设 owner 定期维护。

八十六，**不要过早抽象**。场景：为"未来可能的多租户"提前做三层抽象，结果一年没用上，反而增加理解成本与 bug 面。教训：只解决当下真实需求，抽象等到第三次出现相似逻辑（三次法则）再提炼；奥卡姆剃刀适用于代码——YAGNI（You Aren't Gonna Need It）省下的复杂度就是稳定性。

八十七，**容量规划反直觉**。场景：按平均 QPS 配了连接池与线程池，峰值一来资源耗尽、全链路超时，但平均水位明明很低。教训：容量按峰值 × 冗余规划，而非均值；关注长尾（P99）与突发，留 30%~50% 余量；压测用真实分布（含热点），并对单资源耗尽有熔断/限流/降级，避免一个资源拖垮全局。

## 第七轮补充：更多工程经验（八十八 ~ 九十七，充实版）

八十八，**自动化一切可重复**。场景：每次发布手动跑脚本、改配置、核对清单，人一多就出纰漏，一次漏执行迁移脚本导致字段缺失。教训：凡重复超过三次的操作都应脚本化/平台化（CI/CD、发布流水线、数据校验）；手动步骤越少，人为失误越少；把"人肉 SOP"变成"系统强制"，质量不依赖个人状态。

八十九，**测试金字塔别倒置**。场景：单测几乎为零，却投入大量精力写 UI 端到端测试，结果测试慢、脆、难维护，反而没人跑。教训：多数测试应在底层（单测快而多），集成适中，端到端少而精；把核心逻辑做成可单测的纯函数/清晰边界，测试才敢写敢跑；倒置的金字塔会拖垮交付速度。

九十，**安全左移**。场景：上线前才做安全扫描，发现硬编码密钥与 SQL 拼接，回改成本高、发布延期。教训：安全在需求与编码阶段就介入——输入校验、参数化查询、密钥管理、依赖 CVE 扫描进 CI；SAST/SCA 自动化卡点，别等上线前或出事后再补；安全是功能属性不是附加项。

九十一，**依赖要设边界（防腐层）**。场景：直接调用第三方 SDK 的模型贯穿业务代码，对方一升级改了字段，全项目编译失败、连带改几十处。教训：用防腐层（ACL）把外部模型隔离在边界，内部只依赖自己的领域模型；外部变更被挡在一处，降低耦合与爆炸半径；接口契约由你定义，而非被依赖绑架。

九十二，**沟通慢即是快**。场景：需求没对齐就开干，做了一半发现理解相反，返工一周。教训：开工前用一页文档/半小时对齐"目标与权衡"，省下数倍返工；异步沟通结论先行、带上下文；把模糊的口头共识落到文档，信息差才是最大的隐性成本。

九十三，**数据驱动决策而非拍脑袋**。场景：凭"感觉"把超时从 3s 调到 30s，下游被积压请求打满；又凭"感觉"回退，反复折磨。教训：任何参数/策略调整基于监控与压测数据（RT 分布、饱和度、错误率），有基线有对比；用 A/B 或灰度验证假设，别用直觉替代证据。

九十四，**故障演练（混沌工程）**。场景：从没演练过主从切换，真故障时没人敢切，怕切坏。教训：定期注入故障（杀节点、断网络、打满 CPU）验证系统韧性，把"不敢操作"变成"演练过有 SOP"；韧性是练出来的，不是设计出来的；演练暴露的弱点比线上事故便宜得多。

九十五，**评审关注意图而非形式**。场景：Code Review 只挑命名和格式，逻辑漏洞没人问，上线即崩。教训：评审多问"如果失败了会怎样""边界考虑了吗""为什么这么做"，而非只改 typo；新人暴露的盲区是团队知识库缺口；一条讲"为什么"的评论胜过十条格式纠正。

九十六，**关注业务指标而非仅技术指标**。场景：系统 RT、QPS 漂亮，但转化率和下单量跌了，技术团队一无所知。教训：工程师要懂业务结果（北极星指标），技术指标好不等于业务好；可观测性既包含系统指标也包含业务埋点；技术决策最终要对业务结果负责。

九十七，**保持系统简单（减依赖）**。场景：为小需求引入一个新中间件，运维、监控、排障成本翻倍，用的功能却只有 10%。教训：每加一个依赖/组件都要算总账（部署、监控、升级、人员学习）；能用现有能力解决的就不引新武器；系统的复杂度是负债，少即是多。

## 第八轮补充：更多工程经验（九十八 ~ 一百零七，再充实）

九十八，**把"为什么"写进代码**。场景：一行诡异的 `if (type == 7)` 没人懂，半年后有人"优化"删掉，线上立刻出错。教训：非常规逻辑旁写注释说明背景与代价（不是复述代码，是说为什么）；关键决策链接收设计文档链接；让后人敢改而非只敢绕。

九十九，**环境一致性是隐性成本**。场景：测试能跑、生产因 JDK/OS/参数差异崩；本地 Mac 跑得好，Linux 容器报错。教训：用容器/ IaC 统一环境，差异显式管理；上线前做类生产验证；别让"在我机器上是好的"成为交付标准。

一百，**慢查询治理要常态化**。场景：一条慢 SQL 占满连接，拖垮整个服务，告警却只在超时后才响。教训：设慢查询阈值告警、定期 review 执行计划、加索引/拆大字段；把治理当日常而非救火；单条慢 SQL 是系统性风险点。

一百零一，**幂等与重试要成对出现**。场景：下游抖动用固定间隔猛重试，把下游打挂，且重复下单。教训：写接口默认幂等（去重表/状态机/业务唯一键），重试带指数退避 + 抖动 + 上限 + 死信；永远假设调用方会重试。

一百零二，**变更要小步可验证**。场景：一次性大改发布，出问题时定位与回滚都难，恢复以小时计。教训：变更拆小、单点可验证、配开关与灰度；小步快跑比大爆炸发布安全；每次变更都能说清"这步改了什么、怎么验证、怎么撤"。

一百零三，**监控告警要可行动**。场景：告警狂响却无人知如何处理，最终被忽略，真事故时没人响应。教训：告警带 runbook（谁处理 + 怎么处理），无行动指引的告警不如不告警；基于 SLO，而非"有图就行"；降噪比加图重要。

一百零四，**文档是契约也是记忆外挂**。场景：核心模块只作者懂，他休假时线上出问题无人能救；三个月后自己也不记得为何这么设计。教训：关键设计落文档（背景/方案/权衡/回滚），接口写清契约与变更流程；文档让系统可接手、决策可追溯。

一百零五，**给关键路径设评审清单**。场景：每次上线凭记忆检查，总漏项（漏加索引、漏配告警、漏开开关）。教训：沉淀上线/设计 Checklist，覆盖监控、回滚、容量、安全、数据兼容，发布前逐项打勾；把个人经验变团队流程。

一百零六，**技术债分良性与恶性**。场景：为抢窗口借债验证市场，事后按计划偿还，是良性杠杆；复制粘贴扩散、无人认领的，是恶性债。教训：债要显性化（写进卡片/文档、标偿还时机）+ 定期还（每迭代留 10%~20%）；把债当资产负债表管理。

一百零七，**保持好奇心是长期复利**。场景：只守一亩三分地，技术停滞，遇到新架构无从下手。教训：定期看新版本/论文/别人系统，在真实项目里用新技术踩坑内化；热情来自"能把复杂变简单"的掌控感，而非追逐热点。
