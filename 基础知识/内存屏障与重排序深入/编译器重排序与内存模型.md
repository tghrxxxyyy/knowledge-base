# 编译器重排序与内存模型

> 对应 Lamport 1979「How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs」；ISO C11/C++ 内存模型规范。

## 一、背景与挑战

编译器为优化（寄存器提升、指令调度、公共子表达式消除、死存储消除）可对无数据依赖的访存重排、合并甚至消除。单线程下经 as-if-serial 保证「可观察行为不变」，但多线程下这会破坏线程间同步协议：比如把「写数据」重排到「写发布标志」之后，使另一线程看到标志却读到未初始化数据。理解编译期重排是写正确并发的第一步。典型场景：双重检查锁定（DCLP）若不用 atomic，编译器可能把对象指针赋值重排到构造函数完成之前，导致其他线程拿到未构造完的对象。

更棘手的是：编译期重排是「源码级静态改写」，一次编译即固化进二进制，不随运行环境变化。因此它比 CPU 重排更「稳定地错」——一旦被优化出来，在所有同版本编译产物上都必然发生，而调试器单步执行看到的仍是源码语义，观测与实际的鸿沟极难察觉。

## 二、核心原理

编译期重排受 as-if-serial 约束：单线程程序的可观察行为（外部可观测的 I/O 与 volatile 访问）不变。但跨线程的同步必须靠原子操作与内存序（acquire/release/seq_cst）或显式屏障来约束——它们既阻止编译器重排，也作为「不能跨此点移动访存」的提示。普通变量（非 atomic）编译器可自由重排/缓存到寄存器。C++ 内存模型用 happens-before 关系刻画哪些写必然对哪些读可见。要注意：编译器的重排发生在「生成机器码」阶段，与 CPU 执行期重排相互独立、叠加发生。

需要辨析三类「顺序」：编译器的 `memory_order` 约束（阻止指令调度跨点移动）、编译器屏障（`asm volatile("" ::: "memory")`）、以及硬件屏障。语言原子同时覆盖前两者（并隐含或显式生成第三者的等价物），而 volatile 只覆盖「不缓存、不消除该变量」这一条弱约束，不提供任何跨线程顺序。

## 三、形式化与数学基础

happens-before（$\text{hb}$）是程序次序（$\text{po}$）与同步次序（$\text{sw}$，synchronizes-with）的传递闭包：

$$a\ \text{hb}\ b \iff a\ \text{po}\ b \ \lor\ a\ \text{sw}\ b \ \lor\ \exists c: a\ \text{hb}\ c \land c\ \text{hb}\ b$$

若写 $W\ \text{sw}\ R$（如 release 存后被 acquire 读），则 $W$ 之前的所有写 $\text{hb}$ $R$ 之后的所有读，保证可见性。缺乏该边则读可能看到任意旧值，且构成 data race（未定义行为）。

关键推论：**任何一对「对同一非原子对象的并发访问，其中至少一个是写」，若无 hb 边即为 data race**，程序行为完全未定义——不是「读到旧值」这么温和，而是编译器与 CPU 可以任意处置。这正是 C++ 与 Java 的关键差别：Java 给出确定的「允许值集合」，C++ 则直接判为 UB，因此「碰巧能跑」不能作为正确性证据。

## 四、代码实现

```c
// 编译器可能重排普通写
int data = 0;
int flag = 0;
// 线程1（生产者）
data = 42;
flag = 1;            // 普通变量：编译器可能重排为 flag=1; data=42
// 应使用原子 + release 防止重排
#include <atomic>
std::atomic<int> flag_a{0};
data = 42;
flag_a.store(1, std::memory_order_release);   // 之前写不会被移到此之后
```

注意：即使 CPU 不乱序，编译器也可能在生成代码阶段打乱顺序。用 `std::atomic` 且非 relaxed 才能同时约束编译器与 CPU。

```c
// 编译器屏障：只约束编译器，不生成任何机器指令
#define compiler_barrier() asm volatile("" ::: "memory")
data = 42;
compiler_barrier();      // 阻止编译器把 data 写移到此后
flag = 1;                // 但 CPU 仍可能重排这两条普通访存
```

二者差别要牢记：`compiler_barrier()` 在 x86 上生成的机器码与「什么都不写」相同，只对编译期有效；要同时约束 CPU，必须使用 `std::atomic` 或真实硬件屏障。

## 五、与其他技术对比

| 重排来源 | 发生阶段 | 约束手段 | 典型风险 |
| --- | --- | --- | --- |
| 编译器 | 生成机器码 | 原子/内存序/volatile | 标志发布过早 |
| CPU | 执行期 | 硬件屏障 | 弱模型可见性错乱 |

二者独立但都受内存模型约束，需「双重防护」：既用 atomic 阻止编译器，又靠底层屏障（由 atomic 隐含或显式）约束 CPU。

| 约束手段 | 阻止编译器重排 | 阻止 CPU 重排 | 保证原子性 | 建立 hb |
| --- | --- | --- | --- | --- |
| `volatile` | 部分（仅该变量） | 否 | 否 | 否 |
| `compiler_barrier()` | 是（全局） | 否 | 否 | 否 |
| `relaxed atomic` | 是（该原子） | 是 | 是 | 否 |
| `acq/rel atomic` | 是 | 是 | 是 | 是（配对时） |

## 六、常见误区

1. 误认为 `volatile` 提供原子性与顺序保证——它仅阻止编译器对该变量的优化（缓存/消除），不建立跨线程 happens-before，也不阻止 CPU 重排。
2. 误认为「加锁就万事大吉」但锁外发布数据——锁保护临界区，锁外的标志发布仍需 release/acquire。
3. 误认为编译期重排不存在——`-O2` 下大量重排真实发生，是并发 bug 的隐形来源。
4. 误认为 relaxed 原子能防重排——relaxed 仅保证原子性，不建立同步边，仍可能被重排到其它访问之外。
5. 误以为 `-O0` 调试没问题就等于正确——优化等级变化会改变重排结果，`-O0` 通过不代表 `-O2` 通过。
6. 误以为 data race 只是「读到旧值」——在 C++ 中它属于未定义行为，编译器可做任意变换。

## 七、与开源书·权威来源对应

- C++ 国际标准「Memory Model」章节定义 happens-before、data race 与 memory_order。
- Lamport 1979 原始论文定义顺序一致性（SC），为语言内存模型提供理论起点。
- Boehm & Adve 2008「Foundations of the C++ Concurrency Memory Model」解释为何需要语言级模型。
- Drepper《What Every Programmer Should Know About Memory》第 3 节解释编译期优化与缓存对并发的影响。

## 八、面试题

1. `volatile` 能替代互斥吗？答：不能。它不保证原子、不阻止 CPU 重排、不建立跨线程 happens-before。
2. 编译器重排与 CPU 重排有何不同？答：前者在生成代码阶段，后者在执行期；都需内存模型约束，atomic 同时覆盖两者。
3. 没有 happens-before 边的两次访问会怎样？答：构成 data race，行为是未定义的（UB），可能读到撕裂值。
4. 双重检查锁定为什么需要 atomic？答：否则对象指针赋值可能被重排到构造完成前，其他线程拿到未构造完的对象。
5. `compiler_barrier()` 为何在 x86 上不产生任何机器指令？答：它只向编译器声明「内存可能被修改」，禁用寄存器缓存与指令移动，硬件层无对应操作。
6. 为什么 Java 的 data race 与 C++ 的处理不同？答：Java 通过 volatile/同步给出确定的允许值集合（JMM），C++ 直接判为 UB，因此对代码要求更严。

## 九、演进与趋势

语言级内存模型（C11/C++11、Rust `Atomic*`、Java `volatile`/`Atomic*`）把「顺序/松弛/获取/释放/顺序一致」抽象出来，开发者写内存序而非手写屏障，编译器与目标架构负责落地，显著减少移植错误。同时，编译器的「并发感知优化」更严格地遵守模型，避免引入新的重排 bug。

新进展还有两条主线：其一是形式化验证，用 herd7/rc11 等工具对 litmus test 建模，检查编译器是否引入「模型之外」的重排；其二是 C++20/23 引入 `atomic_ref`、`atomic::wait/notify` 等设施，把原子语义扩展到既存对象与无锁等待场景。Rust 则以 `Send`/`Sync` 类型系统在编译期拒绝可疑的共享，把部分内存模型约束前移到类型检查。

## 十、小结

编译器重排是优化的副产物，理解 as-if-serial 与 happens-before 才能写出正确的并发代码：用 atomic 表达同步意图，而非依赖「源码看起来有序」。切记「编译器重排」与「CPU 重排」是两套独立机制，必须用同一套语言级原子同时覆盖；任何在 `-O2` 下靠时序侥幸成立的并发代码，本质上都是未定义行为。
