# 经典消息传递模式

> 对应 Boehm 内存模型论文；Herlihy & Shavit《The Art of Multiprocessor Programming》第 1 章。

## 一、背景与挑战

两个线程通过「数据 + 标志」通信是最基本的并发模式：生产者写入数据后把标志置位，消费者轮询标志、看到置位后读取数据。若缺少正确同步，接收方可能读到「标志已置但数据未写」的中间态，造成断言失败或数据损坏。该模式是锁、队列、管道、无锁 ring buffer 的共同地基。它的难点在于：标志的置位与数据的写入之间必须存在跨线程可见的顺序保证，而这点在弱模型上并非默认成立。

这一模式还揭示了并发的「最小完备单元」：只要「数据发布 + 标志通知」被正确处理，就能在其上叠加缓冲区、批量传输、多级流水等结构。反之，任何更高层的并发原语只要内部漏了这一对同步，都会在压力下暴露同类错误，且往往表现为「低频、随机、无法复现」。

## 二、核心原理

生产者写数据后，以 release 语义置标志；消费者以 acquire 语义读标志，若看到置位，则「release 之前的所有写」对消费者「acquire 之后的所有读」可见。这种「发布-订阅」把数据可见性显式同步，无需互斥，比共享锁更轻量。关键在于：标志的 release 与 acquire 之间建立 happens-before 边，使数据传递成立。若消费者用普通读、生产者用普通写，则既无编译器约束也无 CPU 约束，标志与数据各自的可见时机完全独立。

在具体实现上，有三处必须同时正确：其一，标志本身必须是原子类型，否则编译器可把它缓存进寄存器使轮询永不退出；其二，两侧内存序必须配对（release/acquire），保证数据传递；其三，数据本身在发布前不可被其他线程访问，避免出现「边写边读」的半成品。

## 三、形式化与数学基础

单标志发布协议依赖如下不变式：

$$\text{load}(flag)\ \text{acquire}\ \land\ \text{see}(flag=1) \implies \text{store}(data)\ \text{before}\ \text{store}(flag)\ \text{release}$$

即：若消费者 acquire 读到 `flag==1`，则生产者 release 之前的 `data` 写必然已完成且可见。若违反（如缺 release/acquire 或编译器把两写重排），可见性无序，断言可失败。该不变式正是 happens-before 链 $data\_write\ \text{hb}\ flag\_store\ \text{sw}\ flag\_load\ \text{hb}\ data\_read$ 的体现。

| 生产者写序 | 消费者读序 | 数据可见性 |
| --- | --- | --- |
| relaxed 写数据 + release 写标志 | acquire 读标志 | 保证 |
| relaxed 写数据 + relaxed 写标志 | acquire 读标志 | 不保证 |
| release 写数据 + release 写标志 | relaxed 读标志 | 不保证 |

## 四、代码实现

```c
#include <atomic>
std::atomic<bool> ready{false};
int payload = 0;
// 生产者线程
void producer() {
    payload = 100;                                  // 写数据
    ready.store(true, std::memory_order_release);   // 发布（之前写不被后移）
}
// 消费者线程
void consumer() {
    while (!ready.load(std::memory_order_acquire))  // acquire 读
        ;   // 自旋等待
    assert(payload == 100);   // 安全：数据已可见
}
```

注意：若 `payload` 本身是 atomic 但用 relaxed 读写，仍无法建立与 `ready` 的 happens-before 链，断言仍可能失败——必须用 release/acquire 配对。

```c
// 扩展为一写多读：一次 release 发布，多个 acquire 各自建立同步边
std::atomic<bool> ready{false};
int payload = 0;
void producer()   { payload = 100; ready.store(true, std::memory_order_release); }
void consumer_i() { while (!ready.load(std::memory_order_acquire)) ; use(payload); }
// 每个消费者都与同一次 release 配对成功，各自获得完整的可见性保证
```

## 五、与其他技术对比

| 模式 | 同步成本 | 语义 | 适用 |
| --- | --- | --- | --- |
| 消息传递（标志+序） | 低（无锁） | 一写多读/发布 | 发布-订阅、SPSC |
| 互斥锁 | 中（可能睡眠） | 通用临界区 | 任意共享状态 |
| 事务内存 | 低-中 | 多变量原子 | 低冲突临界区 |

消息传递最轻量但只表达「发布」语义，复杂共享状态仍需互斥或事务。

| 场景 | 推荐手段 | 原因 |
| --- | --- | --- |
| 单生产者单消费者 | release/acquire + 环形缓冲 | 无竞争，零系统调用 |
| 多生产者 | CAS 抢槽位 + release 发布 | 需协调写入位置 |
| 多消费者 | seq_cst 或计数原子 | 需精确「谁消费了哪项」 |

## 六、常见误区

1. 误认为 `while(!ready)` 轮询不需要屏障——轮询本身必须用 acquire 读才能建立 happens-before，否则编译/CPU 可能把 `payload` 读提升到循环前或永久缓存旧值。
2. 误认为 `bool` 普通变量够用——普通 `bool` 既可能被编译器缓存到寄存器，又无顺序语义。
3. 误认为一个标志能传递多个独立变量——需保证所有数据写在 release 前，且消费者在 acquire 后读全部。
4. 误认为把 payload 也设为 atomic 就够——若用 relaxed，仍无 happens-before 链，断言可失败。
5. 误认为「标志先写、数据后写」也行——那消费者可能看到标志却读到旧数据；发布顺序必须是「先数据、后标志」。
6. 误以为「自旋等待」会消耗大量 CPU 就应换成睡眠——在低延迟场景自旋更快，仅在长等待时用 futex/条件变量退化为睡眠。

## 七、与开源书·权威来源对应

- Herlihy & Shavit《The Art of Multiprocessor Programming》第 1 章以该模式为并发编程基石，贯穿全书无锁结构。
- C++ 标准内存模型示例直接采用「flag + payload」的发布-订阅。
- Boehm 等人的内存模型论文论证该模式在弱模型下的正确性条件。
- Drepper《What Every Programmer Should Know About Memory》讨论该模式在 NUMA 下的可见性延迟。

## 八、面试题

1. 若去掉 release/acquire 会怎样？答：ARM 上消费者可能看到 `ready==true` 却读到 `payload` 旧值（0），断言失败；x86 上多数情况碰巧正确反而掩盖 bug。
2. 为什么用 `atomic<bool>` 而非普通 `bool`？答：保证不被编译器缓存、且有内存序语义建立 happens-before。
3. 如何扩展为一写多读？答：release 写一次、多个 acquire 读；多写则需更强同步（如 seq_cst 或 RCU）。
4. payload 用 atomic relaxed 为何不够？答：relaxed 不建立同步边，与 ready 之间无 happens-before 链，可见性仍乱。
5. 发布顺序为什么必须「先数据后标志」？答：消费者以标志为「数据就绪」的凭证，若标志先可见，凭证失效。
6. 自旋等待如何避免浪费 CPU？答：短等待自旋，长等待退化为 futex/条件变量；也可加 `pause`/`yield` 降低总线压力。

## 九、演进与趋势

无锁 SPSC 环形队列即该模式的工程化：配合内存序与缓存行对齐（避免 false sharing）实现高性能线程间通信；多生产者/多消费者则引入 seq_cst 或 CAS。Rust 的 `crossbeam` 等库把该模式封装为安全 API。C++20 的 `std::atomic_ref` 还允许对非 atomic 对象施加原子语义。

硬件与语言层面的新趋势也在降低该模式的门槛：C++20 `atomic::wait/notify` 让消费者可以「睡等」而非忙等，同时保持内存序语义；ARMv8.1 的 `LDAPR`（弱化 acquire）在共享只读数据场景下进一步降本；内核侧的 RCU 则把「发布-订阅」扩展到「读多写少」的极致，用宽限期代替每次读的原子开销。

## 十、小结

消息传递用「标志 + 内存序」把数据可见性显式同步，是构建一切高层并发原语的地基。其正确性完全建立在 release/acquire 建立的 happens-before 边上。工程要点可归结为三句话：数据先写、标志后放；标志用 release、读标志用 acquire；一处漏配即全体失效。
