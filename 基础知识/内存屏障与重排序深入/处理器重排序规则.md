# 处理器重排序规则

> 对应 Intel SDM 卷3「Memory Ordering」章节；ARMv8 架构参考手册 Barrier 章节。

## 一、背景与挑战

现代 CPU 为提升流水线吞吐与隐藏访存延迟，在遵守内存模型的前提下允许对访存指令重排序。不同架构的内存模型强弱差异巨大：x86 属于强序的 TSO（Total Store Order），ARM/POWER 属于弱内存模型。若程序依赖「源码顺序即执行顺序」的直觉，移植到弱模型 CPU 常因缺失屏障而失效。可移植并发代码必须建立在抽象内存模型之上，而非具体硬件行为。还要注意的是，处理器重排只影响「跨线程的可见性顺序」，单线程可观察行为永远符合程序序——这正是它难以调试的根源：bug 只在多核交叉执行时偶现。

另一层微妙之处在于「重排」并非真的在执行单元里交换指令顺序，而多由缓冲结构造成：store buffer、load buffer、写合并缓冲、预取器等让「完成」与「可见」解耦。理解这一点才能明白为什么屏障指令是必要的——它约束的是「可见时刻」，而非指令发射顺序。

## 二、核心原理

x86-TSO 是「处理器一致性（processor consistency）」的变体，仅允许一种重排：较早的 store 与较晚的 load 重排（store→load），原因是 store 先进入写缓冲（store buffer）异步刷出，而 load 可先去缓存取最新值。其余顺序（store→store、load→load、load→store、以及同地址的所有顺序）均保持。ARMv8 弱模型允许更多：写写、读读、读写、写读（除数据/地址依赖与控制依赖外）在屏障前均可重排，需显式 DMB 约束。依赖关系（如 `a = *p; b = a;` 中 b 依赖 a 的值）不会被重排，因为 CPU 能识别真数据依赖。

补充两点常见细节：其一，x86 的 store 若命中 L1 且一致，其「可见」很快，因此 store→load 重排在单核高频场景中未必被观察到，但语义上允许；其二，x86 保证「store-load 之前的 store 对同核后续 load 可见」（store forwarding），故 `mov [x],1; mov eax,[x]` 同核必读到 1——这条规则常被误读为「x86 是全序」。

## 三、形式化与数学基础

x86-TSO 允许的重排关系（程序次序 $\prec_{po}$ 下被放松者）：

$$S_a \prec_{po} L_b \Rightarrow L_b \text{ 可能在 } S_a \text{ 全局可见之前完成}$$

即 load 可越过更早的 store 先观测到外部值。ARM 在 $a,b$ 间无屏障时，除地址/数据依赖外任意两者都可重排，可用偏序 $\prec_{model}$ 描述每架构「被保留的序」集合。形式化地，每个架构定义一个保留序 $\prec_{model}\subseteq \prec_{po}$，重排即允许不保持 $\prec_{po}$ 中不在 $\prec_{model}$ 里的边。

| 架构 | 保留序集合 $\prec_{model}$ |
| --- | --- |
| SC | 全部 $\prec_{po}$ |
| x86-TSO | $\prec_{po}\setminus\{\text{store}\to\text{load}\}$ |
| ARMv8 | 依赖边 + 屏障分隔的边 |

## 四、代码实现

```asm
; x86：store 进写缓冲，load 可能先完成
    mov DWORD [x], 1     ; store x（暂存写缓冲）
    mov eax, [y]         ; load y 可能先观测到 y 的最新外部值
; 经典 Dekker 测试在 x86 上此对通常保持，store->load 才被放松
```

在 ARM 上，类似代码需显式屏障才能复现 x86 的保证：

```asm
    str w0, [x]          ; store x
    dmb ish              ; 防止 str x 与 ldr y 重排
    ldr w1, [y]          ; load y
```

若缺 `dmb ish`，其他核可能看到 `y` 的旧值同时本核已写 `x`，破坏对称协议。

```asm
; x86 上真正的 store->load 序列需要 MFENCE 才能保证全局顺序
    mov DWORD [x], 1
    mfence               ; 排空写缓冲，确保 store x 全局可见后才执行 load y
    mov eax, [y]
```

注意 `sfence` 只排序 store（对 store→load 无效），`lfence` 主要排序 load 并常用于推测屏障，只有 `mfence` 同时约束两个方向。

## 五、与其他技术对比

| 架构 | 模型强度 | 允许的主要重排 | 屏障需求 | 编程难度 |
| --- | --- | --- | --- | --- |
| x86 (TSO) | 强 | 仅 store→load | 少（MFENCE/SFENCE） | 低 |
| ARMv8 | 弱 | 读读/写写/读写/写读 | 多（DMB 按域/方向） | 高 |
| POWER | 弱 | 类似 ARM 更弱 | 多 | 高 |
| RISC-V | 弱（RVWMO） | 按 fence 位掩码放松 | 中（fence 语义正交） | 中 |

x86 接近直观、易编程；ARM/POWER 性能高但需更多屏障/原子，这正是 C++ 抽象内存模型存在的意义。

## 六、常见误区

1. 误认为所有 CPU 都像 x86——把 x86 上「碰巧正确」的代码移植到 ARM 常因缺失屏障而失效。
2. 误认为「单线程看顺序」等于「全局看顺序」——重排只影响跨线程可见性，单线程可观察行为不变。
3. 误认为加一条 barrier 就够——弱模型下需按方向与共享域（inner shareable/outer shareable）选正确屏障。
4. 误认为数据依赖不会被重排——真数据依赖确实不被重排，但「地址依赖」在部分弱模型（早期 Alpha）也需屏障，ARMv8 已保证地址依赖。
5. 误认为 `sfence` 能替代 `mfence`——`sfence` 只排序 store，无法阻止 store 越过后续 load，防不住 store→load。
6. 误认为同地址访问也可重排——同地址的访存顺序在任何主流模型中都保持，否则会破坏单核语义。

## 七、与开源书·权威来源对应

- Intel SDM 卷3「Memory Ordering」表列出 x86 各类重排与保证（含写直读、同地址顺序等）。
- ARMv8 架构参考手册「Barrier Litmus Tests」给出可重排/不可重排的示例与 DMB 语义。
- Hennessy & Patterson《Computer Architecture》讲解写缓冲与 TSO 起源。
- Drepper《What Every Programmer Should Know About Memory》量化写缓冲对可见延迟的影响。

## 八、面试题

1. x86 允许哪种重排？答：仅 store→load 重排（store 进写缓冲、load 可先观测外部值），其余在 TSO 下保持。
2. 为什么弱模型性能更高？答：更少的顺序约束让流水线与写缓冲更自由，隐藏访存延迟。
3. 依赖源码顺序写并发有何风险？答：在弱模型上缺失屏障会导致跨线程可见性错乱，且难以复现。
4. 写缓冲（store buffer）为何导致 store→load 重排？答：store 先缓冲、异步刷出，而后续 load 可能从缓存取到更新的外部值，于是「后读」早于「前写」对外可见。
5. 为何同核 `mov [x],1; mov eax,[x]` 一定读到 1？答：store forwarding 让本核 load 直接从写缓冲取值，保证同地址顺序。
6. `mfence`、`sfence`、`lfence` 各约束什么？答：MFENCE 双向全序，SFENCE 只排序 store，LFENCE 只排序 load 并兼作推测屏障。

## 九、演进与趋势

RISC-V 定义自己的弱内存模型 RVWMO；各架构正把屏障语义统一到语言级原子（C11/C++ memory_order），源码写一次、编译器按目标架构插入对应屏障，降低移植负担。同时，CPU 厂商在微架构层用「内存依赖预测」减少重排造成的停顿，但对外仍遵守模型。

安全侧也在重塑这一领域：Spectre 之后，`lfence` 从单纯排序指令升级为「推测屏障」，被广泛用作阻断跨漏洞推测的原语；AMD 引入 `lfence` 序列化语义的强化说明；ARM 增加 `CSDB`（Consumption of Speculative Data Barrier）用于抑制推测侧信道。由此可见，重排规则不再只是性能话题，也是安全边界的一部分。

## 十、小结

处理器重排规则由内存模型规定，x86 与 ARM 差异巨大：x86 仅放松 store→load，ARM 几乎全部可重排。跨平台并发必须依赖抽象内存模型而非具体硬件经验。工程上记住三条：用 `std::atomic` 表达意图而非猜硬件；发布-订阅结构两侧成对同步；任何「实测通过」都不能替代对模型的分析。
