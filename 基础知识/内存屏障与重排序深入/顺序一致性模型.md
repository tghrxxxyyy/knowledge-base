# 顺序一致性模型

> 对应 Lamport 1979「How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs」；Hennessy & Patterson《Computer Architecture》。

## 一、背景与挑战

顺序一致性（Sequential Consistency, SC）是最易理解、最直观的内存模型：所有处理器的操作似乎按某种单一全局顺序执行，且每个处理器内部的程序次序在该全局顺序中保持。程序员无需考虑重排。但 SC 严重限制硬件优化（禁止写缓冲、禁止重排），真实多核 CPU 都不严格遵守，于是需要更弱但高效的模型，并在需要时「重建」SC 片段。SC 也是验证并发算法正确性的「黄金参照」：许多算法（Dekker、Peterson）先证明在 SC 下正确，再讨论如何在弱模型上补足屏障。

SC 的核心价值是「定义而非实现」：它给出一把衡量所有弱模型的标尺，让我们能精确说出「TSO 比 SC 弱在哪」「acquire/release 重建了 SC 的哪一部分」。缺少这把标尺，讨论「这段代码是否安全」就会陷入「在我机器上没问题」的经验主义。

## 二、核心原理

SC 要求程序执行的结果等价于所有处理器操作的一个交错（interleaving），且每个核自身的程序次序在该交错中保持。实现 SC 需禁止所有重排并让写即时全局可见，代价极高。实际硬件采用 TSO/弱模型，再用屏障或原子（seq_cst）在关键路径上重建 SC 所需保证，而非全局强制。通俗地说：SC 像「所有人排队依次操作」，弱模型像「各干各的、偶尔对一下账」，性能高但需要显式对账点。

注意「可组合性」这一重要推论：SC 是唯一能让「局部正确」自动推导出「组合正确」的模型。若每个组件在 SC 下满足其规约，则任意组合仍满足。正因如此，为组件编写规约时通常默认 SC 语义，再把实现映射到弱模型——这也是「顺序一致库」概念的由来。

## 三、形式化与数学基础

存在全序 $\prec$ 满足：

1. 若 $a\ \text{po}\ b$（同一处理器），则 $a\prec b$；
2. 每个处理器的读返回按 $\prec$ 的「最近」写入值。

则称该执行满足 SC。即所有处理器的操作被「串成一条线」，且线内保留各自程序序。注意 SC 不指定具体交错，只要求存在某一种。可证：任何满足 SC 的执行，其每个线程的局部视图都与「某全局串行顺序」一致。

与线性一致性（linearizability）的区别值得细分：线性一致性还要求「实时序」$\prec_{rt}$ 被尊重（若操作 A 在真实时间上先完成，则 A 必须先于 B），而 SC 只要求存在某个与程序序相容的全序，允许「读到已完成的旧值」。因此线性一致 $\subset$ SC 约束的实时部分更强，而 SC 对程序序的要求更强。二者不可互相蕴含，但都可用于刻画并发正确性。

## 四、代码实现

```python
# 概念性：检查一个执行是否满足 SC（穷举交错）
def is_SC(execution):
    for interleaving in all_program_order_respecting_orders(execution):
        if values_consistent_with(interleaving):
            return True     # 存在一种 SC 交错解释本次执行
    return False
```

真实硬件不会穷举，而是用「禁止重排 + 即时可见」隐式满足该条件。在软件层，可用 `std::atomic` 的 seq_cst 在关键读写上重建 SC 片段，代价是全屏障。

```c
// 用 seq_cst 在两个变量间重建 SC：经典 Dekker 互斥雏形
std::atomic<int> x{0}, y{0};
// 线程 A
x.store(1, std::memory_order_seq_cst);
int ry = y.load(std::memory_order_seq_cst);
// 线程 B
y.store(1, std::memory_order_seq_cst);
int rx = x.load(std::memory_order_seq_cst);
// 结论：rx==0 && ry==0 不可能同时成立（seq_cst 提供单一全序）
```

若把两个原子都改为 relaxed，则 `rx==0 && ry==0` 是可能的——这正是 SC 与弱序的可观测区别。

## 五、与其他技术对比

| 模型 | 强度 | 性能 | 编程难度 | 典型硬件 |
| --- | --- | --- | --- | --- |
| SC | 最强 | 差 | 最低 | 理论模型 |
| TSO (x86) | 中 | 中 | 低 | x86 |
| 弱模型 (ARM) | 弱 | 高 | 高 | ARM/POWER |
| 线性一致 | 部分更强 | — | 中 | 分布式系统 |

Dekker、Peterson 等算法在 SC 下正确，在弱模型下需加屏障或改用原子。线性一致性常见于分布式共识与共享寄存器规约，SC 更贴近多核硬件的「程序序」直觉。

## 六、常见误区

1. 误认为多核硬件默认提供 SC——多数架构为性能放弃 SC，需用屏障/原子重建所需保证。
2. 误认为 SC 保证「最新值」——SC 保证的是「存在一致交错」，不保证实时性。
3. 误认为软件锁能弥补硬件弱序——锁的正确性本身依赖底层内存序，弱模型下锁实现也要屏障。
4. 误认为 seq_cst 全局免费——seq_cst 需全屏障并在多核间协调单一顺序，开销最大。
5. 误把 SC 与线性一致混为一谈——后者额外要求尊重实时顺序，前者只要求尊重程序序。
6. 误以为 SC 下「读旧值」是 bug——SC 允许读到尚未被「本线程可见」的旧值，只要全序自洽。

## 七、与开源书·权威来源对应

- Lamport 1979 原始论文首次定义 SC 并给出 formal 条件。
- Hennessy & Patterson《Computer Architecture》以 SC 为起点讲解 TSO 与写缓冲的由来。
- 操作系统教材（如 OSTEP）常以 SC 作为讨论并发正确性的基准。
- Herlihy & Shavit《The Art of Multiprocessor Programming》用 SC 定义寄存器规约与无锁算法正确性。

## 八、面试题

1. 为何实际 CPU 不用 SC？答：SC 禁止写缓冲与重排，会严重限制流水线、降低写吞吐，性能损失大。
2. SC 下 Dekker 算法为何正确？答：SC 保证两线程的读写存在一致交错，不会都「看不到对方写」。
3. 如何在弱模型上获得 SC？答：对关键访问用 seq_cst 原子或显式全屏障，重建全局单一顺序片段。
4. SC 与 TSO 的关系？答：TSO 是 SC 的弱化：仅放松 store→load，其余保持，故 x86 比纯 SC 略快但接近直观。
5. SC 与线性一致性差别？答：线性一致额外要求尊重实时完成顺序，SC 只要求存在尊重程序序的全序。
6. 为什么说 SC「可组合」？答：SC 下满足规约的组件任意组合仍满足规约，弱模型无此性质，需显式同步点。

## 九、演进与趋势

现代做法是在弱模型上用语言级原子（seq_cst）「模拟」SC 所需片段，而非全局强制 SC。硬件提供「弱默认 + 强同步点」的折中，把性能留给无竞争路径。研究上还有「限定范围 SC（location consistency）」等中间模型，在局部保序、全局放松。

语言侧亦在收窄缺口：C++ 原子提供 `atomic_thread_fence(memory_order_seq_cst)` 作为「局部 SC 栅栏」，Java 用 volatile 建立全序片段，Rust 复用 C++ 模型。工具侧则出现 litmus test 驱动的一致性验证框架（如 herd7），用可执行测试反推硬件究竟保留了哪些序——这把「SC 是标尺」的理念落到了工程实践中。

## 十、小结

顺序一致性是最强、最直观的模型，但性能成本使其无法在硬件层直接实现。理解 SC 方能把握「为何需要屏障」与「语言内存序到底重建了什么」。它以「存在一个尊重程序序的全局交错」为唯一要求，既简单到可作为正确性证明的基准，又强到足以支撑可组合性推理——这正是它历经数十年仍是并发理论核心坐标的原因。
