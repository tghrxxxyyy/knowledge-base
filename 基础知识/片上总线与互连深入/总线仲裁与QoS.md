# 总线仲裁与 QoS

> 对应 ARM AMBA 规范的 QoS 扩展与 AXI 互联约定，以及 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》互连章节；AMBA QoS 的具体位宽与语义以 ARM 官方规范为准。

## 一、背景与挑战

多个主设备（CPU 簇、DMA、GPU/NPU、显示控制器、网络引擎）共享互连资源。若采用朴素轮询，高优先级或实时流量会被大量低优先级流量稀释，表现为延迟抖动甚至饿死；若采用纯固定优先级，低优先级流量可能长期得不到服务。仲裁器与 QoS 机制的任务，就是把这团「无序竞争」转化为可预测的带宽与延迟分配。

真正的难点在于两类需求同时存在：一是带宽型流量（DMA 大块搬运）追求吞吐、容忍延迟；二是延迟敏感型流量（CPU 取指/取数、显示扫描、实时音频）追求延迟上界，吞吐反倒次要。单一策略无法同时满足，必须引入分级、加权与限速的组合机制。此外 QoS 必须与缓存一致性、DRAM 调度协同：互连只保证「到达内存控制器之前」的服务质量，若内存控制器侧不做优先级区分，端到端延迟仍可能失控。

## 二、核心原理

常见仲裁策略：

- 固定优先级（fixed priority）：实现最简、延迟确定，但低优先级可被饿死。
- 轮询（round-robin, RR）：维护指针循环授权，公平但无带宽保证，且对突发不友好。
- 加权轮询（WRR）：按权重分配服务次数，提供比例带宽保证。
- 信用制/令牌桶（credit / token bucket）：以令牌消耗与重填速率控制长期带宽与突发上限。
- 彩票（lottery）与赤字轮询（DRR）：在变长事务下更精确地实现加权公平。
- 分层仲裁（hierarchical arbitration）：先簇内仲裁再簇间仲裁，减少仲裁器输入端数，天然支持「簇级保底 + 簇内加权」。

AXI 生态中的 QoS 通常体现为一个附带在事务上的优先级/类别字段（如 AxQOS，位宽以规范为准），由主设备标注、互联读取并据此选择事务。仅靠标注并不足够，互联还需具备「限速」能力，防止某主设备用高优先级标注霸占总线。因此实际 QoS 方案一般是「优先级 + 速率限制 + 超时老化」三件套：优先级提供区分度，速率限制提供上限，老化（aging）防止长期饥饿。

在交叉开关或 NoC 路由器中，仲裁按输出端口独立进行，还要处理头阻塞（head-of-line blocking）：常用虚拟输出队列（VOQ）把每个输入端针对不同输出的队列分开，再用矩阵仲裁器或轮询在各输入之间选择。

## 三、形式化与数学基础

加权轮询下主设备 $i$ 获得的长期带宽比例：

$$BW_i = \frac{w_i}{\sum_j w_j} \times BW_{total}$$

信用制/令牌桶的连续时间模型（$c_i$ 为令牌数，$r_i$ 为重填速率，$u_i$ 为使用速率）：

$$\frac{d c_i}{dt} = r_i - u_i, \qquad 0 \le c_i \le c_i^{max}$$

该模型同时限定了长期平均速率（$r_i$）与最大突发量（$c_i^{max}$），这正是实时流量所需的「双参数整形」。

排队等待时间可借助 M/D/1 或 M/M/1 近似刻画。以服务率 $\mu$、到达率 $\lambda$ 为例，平均排队延迟：

$$W_q = \frac{\rho}{2\mu(1-\rho)}, \qquad \rho = \frac{\lambda}{\mu}$$

当 $\rho \to 1$ 时延迟非线性发散，这解释了为什么「利用率跑到 90% 以上」的系统延迟会急剧恶化——仲裁策略能重分配等待，但无法消除资源不足的本质。

公平性可用 Jain 公平指数衡量（$x_i$ 为各主设备实际获得的服务量，$n$ 为主设备数）：

$$J = \frac{\left(\sum_{i=1}^{n} x_i\right)^2}{n \sum_{i=1}^{n} x_i^2}$$

$J = 1$ 表示完全公平，$J = 1/n$ 表示被单一主设备独占。工程上还需给出最坏情况的延迟上界（worst-case latency bound）：对固定优先级仲裁，低优先级事务的等待时间上界是所有更高优先级事务的「最大突发之和」加上当前进行中事务的剩余时间，这一界是硬实时系统可调度性分析的基础。

## 四、代码实现

```c
/* 加权轮询（WRR）：按权重发放信用，用尽后整体重置
   特点：实现简单、比例带宽可控；缺点是重置点可能造成瞬时抖动 */
#define N 4
static const int w[N]      = {4, 2, 1, 1};
static int       credit[N] = {4, 2, 1, 1};

int wrr_pick(const int req[N]) {
    for (int i = 0; i < N; i++)
        if (req[i] && credit[i] > 0) { credit[i]--; return i; }
    for (int i = 0; i < N; i++) credit[i] = w[i];   /* 一轮结束，重置 */
    for (int i = 0; i < N; i++)
        if (req[i] && credit[i] > 0) { credit[i]--; return i; }
    return -1;                                       /* 无请求 */
}

/* 轮询 + 老化：既保证公平，又给长期未获服务者提升优先级，
   防止「持续高优先级流量」造成饿死 */
int rr_aging_pick(const int req[N], int *rr_ptr, int wait[N]) {
    int best = -1, best_wait = 0;
    for (int i = 0; i < N; i++) {
        if (!req[i]) continue;
        wait[i]++;
        int aged = (wait[i] > AGE_THRESHOLD);        /* 超时者提权 */
        if (aged && (best < 0 || wait[i] > best_wait)) { best = i; best_wait = wait[i]; }
    }
    if (best >= 0) { wait[best] = 0; *rr_ptr = (best + 1) % N; return best; }
    for (int k = 0; k < N; k++) {                    /* 常规轮询 */
        int i = (*rr_ptr + k) % N;
        if (req[i]) { wait[i] = 0; *rr_ptr = (i + 1) % N; return i; }
    }
    return -1;
}

/* 令牌桶限速：把长期速率与最大突发分开控制 */
static int tb_allow(int *tokens, int rate, int cap, int cost) {
    *tokens += rate;                                 /* 每周期重填 */
    if (*tokens > cap) *tokens = cap;                /* 突发上限 */
    if (*tokens >= cost) { *tokens -= cost; return 1; }
    return 0;                                        /* 超速，暂缓 */
}
```

## 五、与其他技术对比

| 策略 | 公平性 | 带宽保证 | 延迟上界 | 实现复杂度 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 固定优先级 | 差 | 无 | 可解析 | 极低 | 硬实时、单一关键流 |
| 轮询 RR | 好 | 无 | 弱 | 低 | 对等流量 |
| 加权轮询 WRR | 好 | 比例保证 | 中等 | 低 | 混合负载通用 |
| 赤字轮询 DRR | 很好 | 比例保证 | 中等 | 中 | 变长事务 |
| 令牌桶 + 优先级 | 可调 | 强（双参数） | 强 | 中高 | 实时 + 带宽混合 |
| 分层仲裁 | 好 | 分级保证 | 强 | 高 | 多簇 SoC、NoC |

## 六、常见误区

1. 认为公平即最优：实时流量需要的是延迟上界而非平均公平，纯轮询会让显示/音频出现抖动。
2. 认为标了 QoS 就自动生效：需要互联真正读取该字段并配套限速，否则高优先级标注会被滥用。
3. 认为仲裁只影响延迟不影响正确性：一致性协议依赖消息有序与及时性，长期饥饿可导致协议级活锁。
4. 忽略变长事务的影响：按「事务数」公平在变长突发下并不等于按「字节数」公平，需用 DRR 或按字节加权。
5. 只在互连层做 QoS：内存控制器、L2 与缓存替换策略同样需要优先级感知，否则端到端延迟不可控。
6. 忽视重置点的抖动：WRR 的信用重置会在边界产生突发，可能击穿下游缓冲。

## 八、面试题

1. 问：信用制如何同时防饥饿又限带宽？答：令牌耗尽即停止服务（限上限），重填速率决定长期配额（限均值），二者共同界定平均速率与最大突发。
2. 问：固定优先级仲裁的缺陷与补救？答：低优先级可能饿死；补救方式是引入老化（等待超时提权）或分层为「高优先级限速 + 低优先级保底」。
3. 问：为什么按事务数加权不等于按带宽加权？答：变长突发下每笔事务携带字节数不同，需按字节记账（如 DRR 用赤字累加字节数）才能给出真实的带宽比例。
4. 问：头阻塞如何解决？答：为每个输出端口维护独立的虚拟输出队列（VOQ），再用矩阵仲裁器在各输入间选择，使被阻塞的包不再堵住同输入的其他包。
5. 问：如何给实时流量一个延迟上界？答：限制高优先级事务的最大突发与最大长度，低优先级等待时间上界即为「更高优先级事务最大突发之和 + 当前事务剩余服务时间」。

## 九、演进与趋势

- 硬件 QoS 监控与软件协同：把互连带宽计数器暴露给操作系统/运行时，用于 DVFS 调节与带宽隔离（如按核或按 VM 限速）。
- 精细粒度隔离：从「按主设备」演进到「按进程/虚拟机/容器」的带宽与延迟隔离（与 PASID、SMMU 配合）。
- NoC 化 QoS：以虚通道与按类流控替代集中仲裁，QoS 从「谁先上总线」变为「谁能注入网络、注入多少」。
- 与一致性协同：一致性流量（失效、转发）需要专用优先级与保留带宽，避免被大块 DMA 淹没。
- 可预测性优先：面向自动驾驶、工业控制等场景，追求有界延迟（bounded latency）而非平均性能。

## 十、小结

仲裁与 QoS 把「谁先用总线」从无序竞争变为可预测的资源分配：优先级提供区分度，加权/信用提供带宽保证与上限，老化防止饥饿，分层结构控制仲裁器规模。它的边界也必须看清——仲裁只能重分配等待，无法突破带宽与排队论给的上限；真正的端到端 QoS 需要互连、缓存与内存控制器全链路共同配合。
