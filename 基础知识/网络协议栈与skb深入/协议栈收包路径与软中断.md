# 协议栈收包路径与软中断

> 对应《Linux 内核网络栈》收包路径与 NAPI 机制，xiaolincoder/hello-http 网络收包流程，及 Kurose & Ross《计算机网络》。

## 一、背景与挑战

网卡收到帧后，如何高效、低延迟地送达用户进程？

若直接在硬件中断上下文里做全部协议处理，高流量下 CPU 会被中断「打满」，系统卡死。

Linux 采用「硬中断 + 软中断（softirq）」两段式模型，并在高负载下用 NAPI 轮询，平衡延迟与吞吐。

核心挑战在于三点：

- 在「单包低延迟」与「高吞吐不饿死其他任务」之间找平衡。
- 在千兆 / 万兆以上速率下，逐包中断不可扩展。
- 需要充分利用多核，避免单核成为瓶颈。

## 二、核心原理

收包主路径如下：

1. **DMA 写入**：网卡把帧通过 DMA 写入内核环形缓冲区（ring buffer），无需 CPU 逐字节拷贝。
2. **硬中断（top half）**：网卡触发硬件中断，处理程序只做最少工作——标记有包到达、屏蔽中断、触发 `NET_RX_SOFTIRQ` 软中断。
3. **软中断处理（bottom half）**：在软中断上下文调用网卡 `poll` 函数（NAPI），**批量**收包，每包构建 `sk_buff` 并沿协议栈上送：链路层 → IP 层 → 传输层 → socket 接收队列。
4. **唤醒用户进程**：数据入 socket 队列后，唤醒阻塞在 `recv` 的进程，由它将数据拷贝到用户态。

NAPI 的关键在于：空闲时回退到中断触发，有包时切换到轮询，避免每包一次中断。

## 三、形式化与数学基础

硬中断仅做 $O(1)$ 标记，收包主体在软中断，可被多 CPU 并行（RPS/RFS 把流分发到稳定 CPU）。

NAPI 每轮 `poll` 有预算（budget，默认 `weight=64`）限制处理包数：

$$
\text{每轮处理包数} \le weight
$$

超过预算则让出 CPU、重新调度，避免软中断长时间占用、starve 其他任务。

单核理想吞吐需满足：软中断处理总时长 < 包到达间隔累积，否则需 RPS 把流散到多核。

ksoftirqd 是软中断的兜底内核线程，仅在软中断积压过重时运行。

## 四、代码实现

```c
/* 软中断注册（内核 net/core/dev.c 示意） */
open_softirq(NET_RX_SOFTIRQ, net_rx_action);

/* NAPI poll 概要（驱动侧） */
static int my_poll(struct napi_struct *napi, int budget)
{
    int work = 0;
    struct sk_buff *skb;
    while (work < budget && (skb = poll_one(dev)) != NULL) {
        netif_receive_skb(skb);   /* 上送协议栈 */
        work++;
    }
    if (work < budget)
        napi_complete(napi);      /* 收完，重新使能中断 */
    return work;
}
```

## 五、与其他技术对比

- **传统每包中断（NAPI 之前）**：千兆以上吞吐 CPU 被打满，扩展性差。
- **NAPI 中断 + 轮询混合**：借鉴 polling 高效，又保留空闲低延迟。
- **DPDK 用户态轮询**：完全旁路内核、零拷贝轮询，极致吞吐但牺牲通用性与内核生态。
- **busy-poll（SO_BUSY_POLL）**：应用层主动轮询，降低单包延迟但占 CPU。

## 六、常见误区

- **误区一：软中断是线程**——它是可延迟执行上下文，非独立线程；ksoftirqd 才是兜底线程。
- **误区二：NAPI 永远轮询**——空闲时回退到中断触发，省 CPU。
- **误区三：多核自动分流**——需 RPS/RFS 把流绑到稳定 CPU，否则 Cache 抖动。
- **误区四：硬中断里能随便做事**——硬中断应极短，重活交给软中断。

## 九、演进与趋势

**XDP（eXpress Data Path）** 在驱动更早阶段用 eBPF 处理包，进一步降低收包路径开销。

per-CPU 队列、总线轮询与多队列网卡（RSS）持续演进，把收包并行度推到极限。

在多队列网卡上，收包并行度还依赖 RSS 把不同流哈希到不同队列 / CPU，使每队列的 NAPI 软中断在独立核上运行，避免单核瓶颈。

配合 RPS/RFS 可在软件层进一步校正分发，使「流 → CPU → 应用」三者亲和一致，最大化 Cache 局部性。

当软中断仍成为瓶颈时，XDP 在驱动层用 eBPF 对包做早期分类、丢弃或转发，把热点处理从协议栈后半段前移，是近年高 PPS 场景的主流优化路径。

## 十、小结

收包走「硬中断触发 + 软中断 / NAPI 批处理 + 协议栈上送」路径。

分层 skb 流转与软中断机制兼顾了低延迟与高吞吐，是现代网卡驱动的核心设计。

收包路径的可观测性同样关键：可用 `cat /proc/net/softnet_stat` 查看每 CPU 的软中断收包与丢包计数，`/proc/interrupts` 看中断亲和，`ethtool -S` 看网卡队列统计。

常见故障信号包括某 CPU 软中断占比持续高位（单队列瓶颈）、`softnet_stat` 的 `dropped` 增长（backlog 溢出）、网卡中断未分散到多核（亲和未设）。

排障时按「硬中断 → 软中断 → NAPI poll → 协议栈」逐层下钻，是网络性能问题定位的基本方法论。
