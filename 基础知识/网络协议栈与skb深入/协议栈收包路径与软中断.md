# 协议栈收包路径与软中断

> 对应《Linux 内核网络栈》收包路径与 xiaolincoder/hello-http 的网络收包流程，及 NAPI 机制。

## 一、背景与挑战
网卡收到帧后如何送达应用？直接在中硬件中断里处理大流量会拖慢系统，Linux 采用「硬中断 + 软中断（softirq）」两段式，并在高负载下用 NAPI 轮询，平衡延迟与吞吐。

## 二、核心原理
网卡 DMA 把帧写入环形缓冲区并触发硬中断，中断处理程序仅做最少工作（如标记）、随后触发 NET_RX_SOFTIRQ 软中断。软中断上下文调用网卡 poll 函数（NAPI）批处理收包，构建 skb 并沿协议栈上送：链路层 -> IP 层 -> 传输层 -> socket 接收队列，最终唤醒用户进程。

## 三、形式化与数学基础
硬中断仅做 O(1) 标记，收包主体在软中断，可被多 CPU 并行（RPS/RFS 分发）。NAPI 预算每轮 poll 最多 weight（默认 64）个包，超过则让出 CPU 再调度，避免软中断饿死其他任务。

## 四、代码实现
```c
/* 软中断注册（内核） */
open_softirq(NET_RX_SOFTIRQ, net_rx_action);
/* NAPI poll 概要 */
while ((skb = poll_one(dev)) && budget--) {
    netif_receive_skb(skb);  /* 上送协议栈 */
}
```

## 五、与其他技术对比
传统每包中断（NAPI 前）在千兆以上吞吐下 CPU 被打满；NAPI 的「中断 + 轮询」混合借鉴了 polling 的高效。DPDK 则完全旁路内核、用户态轮询，极致但牺牲通用性。

## 六、常见误区
误区一：软中断就是线程——它是内核可延迟执行上下文，非独立线程（ksoftirqd 是兜底线程）。误区二：NAPI 永远轮询——空闲时回退到中断触发。误区三：多核下无需分流——需 RPS/RFS 把流绑到稳定 CPU。

## 七、与开源书/权威来源对应
内核 net/core/dev.c 实现 NAPI 与 softirq；xiaolincoder/hello-http 给出收包时序图；Kurose & Ross 描述层次化协议处理。

## 八、面试题
为什么分硬中断与软中断？NAPI 解决了什么？ksoftirqd 何时运行？RPS/RFS 作用？

## 九、演进与趋势
XDP（eXpress Data Path）在驱动更早阶段用 eBPF 处理包，进一步降低收包路径开销；总线轮询与 per-CPU 队列持续演进。

## 十、小结
收包走「硬中断触发 + 软中断/NAPI 批处理 + 协议栈上送」路径，分层 skb 流转与软中断机制兼顾了低延迟与高吞吐。
