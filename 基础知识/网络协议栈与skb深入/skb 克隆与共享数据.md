# skb 克隆与共享数据

> 对应 Linux 内核 skbuff 的克隆 / 共享语义，xiaolincoder/hello-http 关于 skb 复用的说明，及《Linux 内核设计与实现》。

## 一、背景与挑战

同一数据包常需被多个消费者处理：多播要把一份报文发给多个接收者，抓包（tcpdump / AF_PACKET）要同时看到原始帧，重定向与桥接也要「另发一份」。若每份都完整拷贝数据，在高吞吐下代价极高。Linux skb 提供**克隆（clone）**与**共享（share）**机制：让多个 skb 结构体引用同一数据区，仅在真正写入时才拷贝（**写时复制，Copy-on-Write**）。挑战在于：如何安全地共享、何时分离、以及如何用引用计数防止泄漏。

## 二、核心原理

核心操作：

- **`skb_clone`**：创建一个新 skb 头（结构体），但**共享同一数据缓冲区**，通过数据区引用计数 `dataref` 记录持有者数量。头本身复制成本低（$O(1)$）。
- **`skb_shared(skb)`**：判断当前数据区是否被多方引用（引用计数 > 1）。
- **写时复制**：当某方要修改数据（如 `skb_put` 追加、改写内容）且数据区被共享时，调用 `skb_copy` 或 `pskb_expand_head` 分离出独立缓冲，再写入，避免影响其他持有者。
- **释放**：每释放一个 skb 引用，数据区引用计数减一，归零才真正释放数据区。

由此，只读场景零拷贝，只有「真正写入」才付出拷贝成本。

典型应用还包括抓包路径：AF_PACKET 通过 `ETH_P_ALL` 接收克隆的 skb，用户态 tcpdump 看到的是共享数据区副本，原始报文继续上送协议栈，互不干扰。重定向（redirect）与桥转发也依赖克隆：一份报文被复制给多个出口，各自独立处理。理解引用计数的生命周期至关重要——任何 `skb_clone` 必须配对 `kfree_skb`，否则数据区永不释放，表现为内存随流量缓慢泄漏。生产排查 skb 泄漏时，常借助 `skb:traced_*` 或 `kmem` 相关 tracepoint 观察分配 / 释放是否配对。

## 三、形式化与数学基础

设数据区引用计数为 $r$。操作语义：

- clone：$r \leftarrow r + 1$（共享同一区）。
- 释放：$r \leftarrow r - 1$；当 $r = 0$ 时释放数据区。

写入时若 $r > 1$，先拷贝分离（成本 $O(L)$，$L$ 为数据长度）再写；若 $r = 1$ 直接写（成本仅修改量）。克隆头成本 $O(1)$，远低于全量拷贝 $O(L)$。因此多消费者场景总体成本：

$$
Cost \approx O(1)\cdot N_{clone} + \mathbb{1}[write]\cdot O(L)
$$

即只读多播几乎不拷贝，仅首个写入者承担一次分离成本。

## 四、代码实现

```c
/* 克隆：新 skb 头共享数据区 */
struct sk_buff *c = skb_clone(skb, GFP_ATOMIC);

/* 写入前检查是否共享，必要时写时复制 */
if (skb_shared(skb)) {
    struct sk_buff *new = skb_copy(skb, GFP_ATOMIC);
    kfree_skb(skb);
    skb = new;          /* 持有独立缓冲后再修改 */
}
skb_put(skb, 4);        /* 追加 4 字节，安全写入 */
```

## 五、与其他技术对比

- **BSD mbuf「mbuf + cluster」**：同样用引用计数共享簇（cluster），思想同源。
- **skb_clone vs skb_copy**：前者只复制头、共享数据（快）；后者复制头 + 数据（独立、慢）。
- **用户态零拷贝（sendfile / splice）**：避免内核 ↔ 用户间拷贝，与 skb 共享同属「减少拷贝」谱系。
- **DPDK mbuf `refcnt`**：用户态实现类似克隆语义。

## 六、常见误区

- **误区一：克隆后改一处全变**——未做写时复制确实会，故修改前必须确保独占（`skb_shared` 检查）。
- **误区二：克隆等于拷贝**——仅头复制、数据共享，成本低。
- **误区三：引用计数不会泄漏**——任一处未 `kfree_skb` 都会泄漏数据区。
- **误区四：克隆 skb 可随意改**——共享数据区只读安全，写必须分离。

## 八、面试题

- skb_clone 与 skb_copy 区别？各自成本？
- 写时复制何时触发？为何需要？
- 引用计数如何防止数据区泄漏？
- 多播为何用克隆而非拷贝？

调试 skb 共享问题时，可借助 `dropwatch`、`skb:kfree_skb` tracepoint 观察释放路径，确认引用计数是否如期归零；在 eBPF 程序里操作 skb 时，需谨记它可能在多个钩子间被克隆，直接写入共享数据区会影响其他消费者。内核后续引入的「skb 碎片页引用（page pool）」进一步降低了分配 / 释放成本，使高频克隆场景下缓冲复用更高效。理解「克隆头 + 共享页」的二层结构，是排查零拷贝链路异常的基础。

## 九、演进与趋势

skb 的 `frags`（分页数据）使零拷贝收发更精细；配合 XDP 的「原地修改」模式，克隆语义在 eBPF 程序中仍需谨慎处理（避免误改共享区）。具体机制随内核版本演进，以官方源码为准。

性能上，克隆的优势在「只读多消费者」场景最明显：多播、抓包、策略镜像都可零拷贝复制 skb 头而共享数据区，仅首个写入者承担一次分离拷贝。因此在设计数据面时，应尽量让中间处理环节保持只读、把写操作集中到确定唯一的出口，从而最大化克隆带来的零拷贝收益，并避免频繁触发 `skb_copy` 造成隐性复制开销。

## 十、小结

skb 克隆以「共享数据 + 引用计数 + 写时复制」实现高效多消费者，是报文多路处理（抓包、多播、重定向）零拷贝的基础。代价仅在真正写入时发生，且由引用计数严格管理生命周期。
