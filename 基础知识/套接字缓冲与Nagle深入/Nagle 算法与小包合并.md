# Nagle 算法与小包合并

> 对应 RFC 896（Nagle 算法）与 xiaolincoder/hello-http 关于 Nagle 与延迟的说明。

## 一、背景与挑战
早期 telnet 等交互应用每敲一键就发一个仅 1 字节的 TCP 段，造成大量小包、极低有效载荷比（「糊涂窗口」式浪费）。Nagle 算法旨在把多个小写合并成较大段再发，减少小包数量。

## 二、核心原理
Nagle 规则：若存在「已发送但未确认的数据」（即还有在途小段），则新数据先在发送缓冲区积攒，直到：要么积累了足够数据（达到 MSS），要么之前的小段被 ACK（管道清空）才发送。这样一次只让一个未确认小段在途，后续数据被合并，显著降低小包率。

## 三、形式化与数学基础
令 outstanding = (存在已发未确认段)。发送条件：if not outstanding: 发送；else: 仅当 data_len >= MSS 或 PSH 标志才发送，否则缓存。效果：在途未确认段数 <= 1（小段意义下），小包发送速率被 ACK 节奏限制，等价于「每个 RTT 最多一个新小段」。

## 四、代码实现
```c
if (outstanding_bytes == 0) {
    send_now();
} else if (data_len >= MSS || user_push) {
    send_now();      /* 攒够或显式 PSH */
} else {
    buffer_and_wait_ack();   /* Nagle 合并 */
}
```

## 五、与其他技术对比
Nagle 解决「发送侧小包过多」；而接收侧的「糊涂窗口综合征（SWS）」避免接收方通告过小窗口。两者常配合使用。禁用 Nagle（TCP_NODELAY）则每 write 立即发包，适合低延迟交互但牺牲带宽效率。

## 六、常见误区
误区一：Nagle 会合并任意数据——只在有未确认小段时暂缓，聚满 MSS 或 ACK 回来即发。误区二：Nagle 导致大延迟一定不好——对批量传输有益，对实时交互有害。误区三：Nagle 与延迟确认无关——二者叠加会放大交互延迟（经典「写-等ACK-再写」卡顿）。

## 七、与开源书/权威来源对应
RFC 896 定义 Nagle；xiaolincoder/hello-http 解释其与延迟确认的交互；Kurose & Ross 在 TCP 章提及小包问题。

## 九、演进与趋势
现代高吞吐网络下，应用多批量写或启用 TCP_NODELAY + 合理缓冲；Nagle 在默认开启状态下仍守护着大量遗留交互协议，避免小包洪泛。

## 十、小结
Nagle 算法通过「在途仅留一个未确认小段」合并小写，降低小包率，但会与延迟确认叠加放大交互延迟，需按场景权衡开关。
