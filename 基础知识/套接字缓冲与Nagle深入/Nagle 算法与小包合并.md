# Nagle 算法与小包合并

> 对应 RFC 896（Nagle 算法）与 xiaolincoder/hello-http 关于 Nagle 与延迟确认的说明。

## 一、背景与挑战

早期 telnet 等交互应用每敲一键就发一个仅 1 字节的 TCP 段，造成大量小包、极低有效载荷比（「糊涂窗口」式浪费）。Nagle 算法旨在把多个小写合并成较大段再发，减少小包数量。

但在延迟敏感的交互场景，Nagle 与延迟确认叠加会放大人为延迟，因此理解其取舍至关重要。Nagle 的本质是「机会主义批量」：它不禁止发送，而是把「还有未确认小段时的新数据」暂存，等管道清空或攒够 MSS 再发，从而在保序的前提下把多个小写粘成少个大包。

代价是交互首个后续小段要等一个 RTT 的确认，这正是与延迟确认冲突的根源——两道防线在同一小包上互相等待。现代高吞吐网络下，应用多批量写或启用 TCP_NODELAY + 应用层批量（pipeline）来兼顾。Nagle 在默认开启状态下仍守护着大量遗留交互协议，避免小包洪泛。

## 二、核心原理

Nagle 规则：若存在「已发送但未确认的数据」（即还有在途小段），则新数据先在发送缓冲区积攒，直到满足任一条件才发：①之前的小段被 ACK（管道清空）；②积累数据达到 MSS；③应用显式 PSH。这样在途未确认小段数不超过 1，后续数据被合并，显著降低小包率。它只作用于「有未确认小段」时的暂缓，而非无条件延迟。

实践中常用 `TCP_NODELAY` 在应用框架层默认开启以规避交互延迟，同时用应用层批量（pipeline/batching）弥补小包率——把多次小写在用户态合并成一个大 write，既享受 Nagle 的省包收益，又不被其延迟拖累。这是比单纯关 Nagle 更优的工程折中。

关键要点：

- Nagle 是「机会主义批量」，仅在存在未确认小段时暂缓，而非无条件延迟。
- 触发发送的三条件：管道空 / 攒够 MSS / 应用显式 PSH。
- 在途未确认小段数 $\le 1$，等价于每个 RTT 最多一个新小段。
- 与延迟确认叠加会放大交互延迟，是经典的「写-等 ACK-再写」死锁。
- 应用层批量（pipeline）比单纯关 Nagle 更优：兼顾省包与低延迟。
- 部分内核对本地回环自动豁免 Nagle，回环测试未必反映真实行为。

## 三、形式化与数学基础

令 $\text{outstanding}$ 表示存在已发未确认段。发送判定：

$$
\text{send now} \iff \neg\text{outstanding} \;\lor\; (\text{data\_len} \ge \text{MSS}) \;\lor\; \text{PSH}
$$

否则 $\text{buffer\_and\_wait\_ack}$。效果：小段意义下在途未确认段数 $\le 1$，小包发送速率被 ACK 节奏限制，等价于「每个 RTT 最多一个新小段」。因此交互一次「写两段」的额外延迟约一个 RTT（等首段 ACK）。

## 四、代码实现

```c
/* 发送侧 Nagle 判定（概览） */
void try_send(buffer buf) {
    if (outstanding_bytes == 0) {
        send_now(buf);                      // 管道空，立即发
    } else if (buf.len >= MSS || user_push) {
        send_now(buf);                      // 攒够 MSS 或显式 PSH
    } else {
        buffer_and_wait_ack(buf);           // Nagle 合并，等 ACK
    }
}
```

## 五、与其他技术对比

| 机制 | 作用 | 小包率 | 交互延迟 | 适用 |
|------|------|--------|----------|------|
| Nagle（默认开） | 发送侧合并小写 | 低 | 高（交互） | 批量/遗留协议 |
| TCP_NODELAY | 关闭 Nagle | 高 | 低 | 实时交互 |
| TCP_CORK | 主动攒大包 | 低 | 高 | HTTP 头体合并 |
| SWS avoidance | 接收侧防小窗口 | — | — | 配合 Nagle |

## 六、常见误区

误区一：Nagle 会合并任意数据——只在有未确认小段时暂缓，聚满 MSS 或 ACK 回来即发。

误区二：Nagle 导致大延迟一定不好——对批量传输有益，对实时交互有害。

误区三：Nagle 与延迟确认无关——二者叠加会放大交互延迟（经典「写-等 ACK-再写」卡顿）。

误区四：关 Nagle 永远更快——小包过多降低整体吞吐，且低速链路上反而抬高带宽占用。

误区五：Nagle 解决所有小包问题——它只管发送侧，接收侧糊涂窗口综合征需 SWS avoidance 配合。

补充误区：

- 误区六：现代网络不需要 Nagle——批量与遗留协议仍显著受益。
- 误区七：NODELAY 是性能银弹——需配合应用层批量才最优。
- 误区八：Nagle 影响吞吐上限——它影响延迟，吞吐由窗口/拥塞决定。
- 误区九：关 Nagle 必然降带宽占用——不当关闭在低带宽下反而抬高占用。

## 七、与开源书·权威来源对应

RFC 896 定义 Nagle；xiaolincoder/hello-http 解释其与延迟确认的交互；Kurose & Ross 在 TCP 章提及小包问题；Linux tcp(7) 的 TCP_NODELAY/TCP_CORK 提供开关；本仓库「延迟确认与交互式流量」「TCP_NODELAY 与禁用 Nagle」配套讨论同一机制的双向视角。

判断是否需要 Nagle 的核心是看流量形态：纯批量（文件传输、训练日志）可保留默认以省带宽；请求-响应交替的在线服务应评估关闭。可用 `ss -o` 观察 retransmit 与 rtt，结合应用延迟百分位决定，而非一刀切。

## 九、演进与趋势

现代高吞吐网络下，应用多批量写或启用 TCP_NODELAY + 应用层批量（pipeline）来兼顾；Nagle 在默认开启状态下仍守护着大量遗留交互协议，避免小包洪泛；部分内核对本地回环自动豁免 Nagle。

HTTP/2、gRPC 等多路复用协议在帧层做批量，使应用无需直接操心 Nagle；QUIC 则完全在用户态实现可靠传输，从协议层消解内核 Nagle 的取舍矛盾。

## 十、小结

Nagle 算法通过「在途仅留一个未确认小段」合并小写、降低小包率，但会与延迟确认叠加放大交互延迟，需按场景权衡开关，并以应用层批量配合，而非简单地全局禁用。
