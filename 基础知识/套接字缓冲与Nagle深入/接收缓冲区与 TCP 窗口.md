# 接收缓冲区与 TCP 窗口

> 对应 RFC 793 窗口字段、RFC 7323 窗口缩放与 xiaolincoder/hello-http 的接收缓冲说明。

## 一、背景与挑战

TCP 用「接收窗口（rwnd）」告知对端自己还能收多少数据，防止发送方淹没接收方。rwnd 直接由接收缓冲区剩余空间决定。窗口过小会限制吞吐（尤其长肥管道 BDP 大时），窗口缩放则解决 16 位窗口上限（最大 65535 字节）不足的问题。

窗口的本质是「流控信用」：接收方用 rwnd 告诉发送方「你还能发多少」，发送方据此在已发未确认量上自我约束。它与拥塞窗口 cwnd 共同构成发送上限，二者取小。理解这一点对排查「带宽够却跑不满」至关重要——往往卡在 rwnd（接收缓冲太小）或 cwnd（拥塞谨慎），而非链路本身。

## 二、核心原理

接收方在每次 ACK 中通告 $\text{rwnd} = \text{接收缓冲剩余}$（受 SO_RCVBUF 限制）。发送方保证「已发未确认」不超过 rwnd。RFC 7323 的窗口缩放（WSOPT）在握手时协商一个移位因子 $wscale\in[0,14]$，使窗口最大可达约 1 GB，适配高 BDP 网络。接收缓冲不足会直接「缩小窗口」形成流控背压，迫使发送方降速。

在容器与虚拟化环境，接收缓冲还受 cgroup 网络限制与虚拟网卡队列影响；跨主机长肥管道务必同时打开窗口缩放与足够的 tcp_rmem.max，否则 16 位窗口上限会把吞吐锁死在约 64KB/RTT。NUMA 与网卡多队列（RSS）也间接影响接收侧处理能力，进而体现在 rwnd 上。

关键要点：

- rwnd 直接由接收缓冲剩余空间决定，是端到端流控的闸门。
- 发送方有效窗口为 $\min(\text{cwnd}, \text{rwnd})$，二者取小才是真实发送上限。
- WSOPT 解决 16 位窗口上限，长肥管道必须开启才能跑满吞吐。
- 本端应用消费过慢会塌缩 rwnd，形成流控背压迫使发送方降速。
- 容器/cgroup 会限制接收缓冲，跨主机需足够大的 tcp_rmem.max。
- SWS avoidance 避免通告过小窗口造成糊涂窗口综合征。

## 三、形式化与数学基础

通告窗口：

$$
\text{rwnd} = \text{RCV\_BUF} - \text{已收未读}
$$

发送方有效窗口：

$$
W_{\text{eff}} = \min(\text{cwnd}, \text{rwnd})
$$

开启缩放后，报文 window 字段值 $w$ 对应的实际窗口为 $w \ll wscale$。为避免「小窗口傻等」，TCP 用糊涂窗口综合征（SWS）avoidance：仅当窗口增长到足够大（通常 $\ge \text{MSS}$ 或半缓冲）才通告/发送。

## 四、代码实现

```bash
# 握手启用窗口缩放（wscale=7 表示 <<7，最大约 1GB）
sysctl -w net.ipv4.tcp_window_scaling=1
```
```c
int rcv = 4 << 20;  /* 4 MB 接收缓冲 */
setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &rcv, sizeof rcv);
/* 实际窗口受 min(SO_RCVBUF*2, tcp_rmem.max) 与 rwnd 共同约束 */
```

## 五、与其他技术对比

| 协议/机制 | 流控窗口 | 最小单位 | 特点 |
|-----------|----------|----------|------|
| TCP 窗口 | 端到端单连接 | 字节 | 受 RCV_BUF + WSOPT 约束 |
| TCP + WSOPT | 放大到 ~1GB | 字节 << wscale | 适配长肥管道 |
| UDP | 无 | — | 溢出即丢包 |
| QUIC 流控 | 流 + 连接两级 | 字节 | 比 TCP 更细粒度 |

## 六、常见误区

误区一：窗口越大越好——受 RCV_BUF 与对端 cwnd 共同限制，且过大增加内存与重传成本。

误区二：16 位窗口够用——长肥管道下必须 WSOPT，否则吞吐被锁死。

误区三：窗口只由对端控制——本端应用读取速度直接决定剩余空间，消费慢则窗口塌缩。

误区四：调大 SO_RCVBUF 一定提速——还受 tcp_rmem.max 与对端约束，且过大增加内存压力。

误区五：窗口与拥塞无关——cwnd 才是网络拥塞约束，二者取小才是真实发送上限。

补充误区：

- 误区六：只看 tcp_rmem 不关心应用消费——消费慢才是窗口塌缩根因。
- 误区七：窗口缩放下线即故障——属正常背压，应配流控而非告警。
- 误区八：WSOPT 可中途变更——需在握手协商，无法运行时开启。
- 误区九：接收窗口等同吞吐——最终上限由 min(cwnd, rwnd) 决定。

## 七、与开源书·权威来源对应

RFC 793 定义窗口；RFC 7323 窗口缩放；man socket(7) 的 SO_RCVBUF；xiaolincoder/hello-http 图示窗口；Kurose & Ross 讨论流控；Linux ip-sysctl 的 tcp_rmem。排障窗口相关问题时，`ss -ti` 可直接看到 rwnd、cwnd、rtt 与 retransmit；若 rwnd 长期为 0 或很小，优先检查 SO_RCVBUF 与 tcp_rmem 是否被压低，以及应用消费是否过慢。

## 九、演进与趋势

自动调优（tcp_rmem）按 BDP 动态扩缩接收缓冲；Linux 支持接收缓冲的 forward RTT 感知以适配高带宽延迟网络；QUIC 把流级与连接级窗口分离，避免单流占满整连接。云环境的智能网卡（NIC offload）还能在硬件层做窗口与拥塞协同，进一步释放长肥管道潜力。

## 十、小结

接收缓冲区大小直接映射为 TCP 接收窗口，是端到端流控的闸门；窗口缩放让高 BDP 网络也能获得足够吞吐，配合 autotuning 接近最优，但需警惕应用消费过慢导致的窗口塌缩。
