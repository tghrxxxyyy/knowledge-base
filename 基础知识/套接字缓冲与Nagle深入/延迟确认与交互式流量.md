# 延迟确认与交互式流量

> 对应 RFC 1122 关于延迟确认（Delayed ACK）的规定与 xiaolincoder/hello-http 的相关说明。

## 一、背景与挑战
TCP 中纯 ACK 不带数据却占用一个包。为减少 ACK 数量，接收方可「延迟确认」：收到数据后不立即回 ACK，而是等一小段时间，期望顺带把 ACK 捎带（piggyback）在反向数据流上，或合并多个段的确认。

## 二、核心原理
RFC 1122 规定接收方至多延迟一个 RTT（典型 40–200ms，Linux 默认约 40ms），且每收到第二个全尺寸段必须立即确认（防止发送方误以为丢包）。延迟确认与 Nagle 相遇时会出现「写小段→等 ACK→再写」的相互等待，造成交互延迟（经典「ACK 延迟死锁」现象）。

## 三、形式化与数学基础
延迟确认计时器 T_dack ≈ min(RTT, 200ms)。触发立即 ACK 的条件：收到第 2 个 MSS 段，或计时器到期，或需发送反向数据（捎带）。与 Nagle 叠加时，发送方因 outstanding 小段暂缓、接收方因延迟 ACK 暂缓回确认，双方各等对方，延迟约 T_dack。

## 四、代码实现
```c
/* 接收端（概览） */
on_data():
    if (second_full_segment) || (timer_expired):
        send_ack_now()
    else:
        start_delayed_ack_timer()   # 期望捎带或合并
```

## 五、与其他技术对比
TCP 快速确认（quickack）模式可临时关闭延迟确认以加速特定交互；QUIC 的 ACK 帧频率与合并策略不同且多在应用数据帧上捎带。延迟确认是接收侧优化，Nagle 是发送侧优化，二者目标都是减少小包但会互相牵制。

## 六、常见误区
误区一：延迟确认总有害——对批量吞吐有增益（减少 ACK 数）。误区二：可无限延迟——有上限且第二全段即确认。误区三：只影响接收方——其效果直接卡住启用 Nagle 的发送方。

## 七、与开源书/权威来源对应
RFC 1122 第 4.2.3.2 节延迟确认；xiaolincoder/hello-http 解释与 Nagle 的交互；Kurose & Ross 讨论捎带确认。

## 八、面试题
延迟确认为何减少 ACK？与 Nagle 如何冲突？第二全段为何立即 ACK？quickack 是什么？

## 九、演进与趋势
现代内核提供 tcp_delack_min 等可调参数，并能在检测到交互模式时自动切换快速确认；MPTCP 下各子流也各有延迟确认逻辑。

## 十、小结
延迟确认通过合并/捎带 ACK 减少小包，但与 Nagle 叠加会放大交互延迟，理解二者交互是调优实时流量的关键。
