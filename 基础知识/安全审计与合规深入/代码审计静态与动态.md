# 代码审计静态与动态

> 对应 OWASP Code Review Guide；OWASP Top 10；Livshits & Lam（USENIX 2005，静态分析找安全漏洞）；Brian Chess & Jacob West《Secure Programming with Static Analysis》。

## 一、背景与挑战
漏洞的根因大多在代码逻辑：SQL/命令注入、越权访问（IDOR）、整数溢出、反序列化、密码学误用、竞态导致的状态绕过。这些问题在运行时测试中未必能被触发，但在代码里通常是可识别的「危险模式 + 污点传播」。于是形成三类互补手段：**SAST**（静态应用安全测试，不运行程序即分析源码/字节码）、**DAST**（动态，运行中从外部探测）、**IAST**（运行时插桩，在程序内部观测真实数据流）。

挑战在于：其一，**精确性与可扩展性的矛盾**——全路径敏感、上下文敏感分析是昂贵的，工程上必须做近似；其二，**误报与漏报的取舍**——SAST 规则宽则误报爆炸、窄则漏掉变体，误报率过高直接导致开发者忽略告警；其三，**逻辑漏洞难以静态刻画**——越权往往不是语法模式而是「缺少归属校验」，需要人工审计与规格化断言；其四，**依赖与配置不在源码里**——第三方库与运行配置需要 SCA 与基线检查配合。

## 二、核心原理
SAST 的基本流程是：解析源码为 AST，构建控制流图（CFG）与调用图（CG），再做**污点分析（taint analysis）**——把用户输入等不可信数据标为 source，把危险操作标为 sink，沿数据流检查是否存在「未经净化即到达 sink」的路径。在此基础上还有值集分析、指针分析（如 Andersen 风格）与区间分析（查整数溢出）。规则通常以 AST 模式 + 数据流条件表达，因此同一条规则能覆盖 `+` 拼接、`format!`、模板插值等多种写法。

DAST 从外部以黑盒方式发请求，观察响应与副作用，覆盖真实配置与运行时行为，但对「未暴露的代码路径」无能为力且定位到行级困难。IAST 通过 agent 插桩采集真实的调用栈与参数快照，把运行时看到的污点流回填到静态地图上，从而大幅降低误报。人工审计的作用不是替代工具，而是补上工具不擅长的部分：鉴权模型是否自洽、密码学使用是否正确（模式、IV、密钥管理）、业务规则是否可被绕过、以及信任边界在哪里。

## 三、形式化与数学基础
污点分析可形式化为可达性判定。设程序点集合 $P$，数据流关系 $\Rightarrow$，若存在路径
$$ s \xrightarrow{\ \text{no sanitize}\ } t,\qquad s \in \mathrm{Source},\ t \in \mathrm{Sink} $$
则报告为污点漏洞。带净化的表述为
$$ \mathrm{Reach}(t) \Leftarrow \exists s \in \mathrm{Source}:\ s \rightsquigarrow t \wedge \neg \mathrm{Sanitized}(s \rightsquigarrow t) $$
分析精度可用格（lattice）上的不动点迭代刻画：给定抽象域 $D$ 与单调转移函数 $f$，最少不动点
$$ \mu f = \bigsqcup_{n \ge 0} f^{n}(\bot) $$
即上下文敏感度越高（$k$-CFA、对象敏感、路径敏感）越精确，但复杂度随之上升——这是「精度—代价」曲线的形式化来源。检测质量的常用度量：
$$ \mathrm{Precision} = \frac{TP}{TP+FP},\qquad \mathrm{Recall} = \frac{TP}{TP+FN} $$
工程上通常要求把 Precision 保持在高位（减少噪声），用多种分析手段叠加来补偿 Recall。可达性对风险排序同样有效：$P(\text{exploitable}) \approx \mathrm{Reach}_s \cdot \mathrm{Exposed}$。

## 四、代码实现
危险与安全的对照（SAST 会标记前者）：
```python
# 危险：字符串拼接构造查询，污点直达 sink
def get_user_bad(uid):
    return db.query("SELECT * FROM users WHERE id = " + uid)

# 危险：命令注入
def ping_bad(host):
    return os.system("ping -c 1 " + host)

# 安全：参数化查询，输入与语句分离
def get_user_ok(uid):
    return db.execute("SELECT * FROM users WHERE id = %s", (uid,))

# 安全：参数数组，不经过 shell
def ping_ok(host):
    return subprocess.run(["ping", "-c", "1", host], check=True,
                          capture_output=True, shell=False)
```

一个极简的污点传播原型（示意）：
```python
SOURCES = {"request.args", "request.form", "request.json", "input"}
SINKS = {"db.query", "os.system", "eval", "exec", "subprocess.run"}
SANITIZERS = {"escape", "int", "quote", "validate_uuid"}

def scan(fn):
    findings = []
    tainted = set()
    for node in fn.ast.walk():                 # 伪 AST 遍历
        if node.is_call() and node.qualname in SOURCES:
            tainted.add(node.result_var)
        elif node.is_call() and node.qualname in SANITIZERS:
            tainted.discard(node.arg_var)      # 净化后取消污点
        elif node.is_call() and node.qualname in SINKS:
            if any(a in tainted for a in node.arg_vars):
                findings.append((node.lineno, node.qualname, node.arg_vars))
    return findings
```

CI 中的组合用法（工具以官方文档为准）：
```bash
# SAST：提交时快速门禁
bandit -r src/ -f json -o sast.json
# SCA：依赖漏洞
pip-audit --format json > sca.json
# DAST：部署后用基线扫描验证
zap-baseline.py -t https://staging.example.com -r dast.html
```

## 五、与其他技术对比
| 维度 | SAST | DAST | IAST | 人工代码审计 | SCA |
| --- | --- | --- | --- | --- | --- |
| 运行要求 | 不需要 | 需要可运行目标 | 需要运行 + 插桩 | 不需要 | 不需要 |
| 覆盖范围 | 源码全部路径（近似） | 仅可达接口 | 被实际执行的路径 | 依赖审计者经验 | 第三方依赖 |
| 定位精度 | 行级 | 端级（URL/参数） | 行级 + 调用栈 | 行级且含语义 | 组件/版本级 |
| 误报率 | 高 | 低 | 中低 | 低（但受限于人） | 中（可达性缺失易高估） |
| 发现逻辑越权 | 弱 | 中 | 弱 | 强 | 不适用 |
| 最佳时机 | 编码与提交 | 测试与预发 | 集成测试 | 设计评审与专项 | 构建与上线 |

## 六、常见误区
1. **「靠 SAST 工具就够了」**——错。规则覆盖不了业务逻辑越权与密码学误用，误报若不治理会被开发者整体忽略。
2. **「参数化查询万能」**——错。它防的是注入类，不防 IDOR、不防参数被篡改后的越权，仍需服务端归属校验。
3. **「忽略依赖代码审计」**——错。大量真实事件来自第三方组件，SBOM 与 SCA 是必要补充。
4. **「DAST 扫不到就没问题」**——错。黑盒无法穷尽路径，尤其内部鉴权分支与并发竞态。
5. **「审计一次即长期有效」**——错。代码持续变化，需把扫描接入 CI 做增量门禁并跟踪修复闭环。

## 七、与开源书·权威来源对应
- OWASP Code Review Guide：代码审计的实操清单与常见缺陷模式。
- OWASP Top 10：把风险归类（注入、访问控制失效、加密失败等），指导审计优先级。
- Livshits & Lam（USENIX 2005）：把静态分析用于 Java 应用安全漏洞发现的经典工作，污点分析的重要参考。

## 八、面试题
1. **SAST 与 DAST 区别？** 要点：是否运行、覆盖范围、定位精度与误报率不同；SAST 早且全但噪声大，DAST 真实但晚且覆盖受限，常与 IAST 组合。
2. **污点分析的原理？** 要点：标 source 与 sink，沿数据流判定是否存在「未经净化可达」的路径；精度取决于上下文/路径敏感度与净化建模。
3. **参数化查询为什么能防注入？** 要点：把数据与语句结构分离，输入不再参与语法构造，因此无法改写查询结构。
4. **为什么 SAST 发现不了越权？** 要点：越权是缺少归属校验的语义问题，不表现为危险函数调用，需人工审计与规格化断言。
5. **如何治理 SAST 误报？** 要点：分级规则、基线豁免与到期复审、只对新增代码设门禁，让 noise 不淹没真问题。

## 九、演进与趋势
静态分析正从语法模式走向语义与跨函数、跨服务的全局分析，并与制品签名、SBOM 结合形成供应链可信链条。IAST/RASP 在运行时提供更精确的观测与阻断，eBPF 类技术让运行时审计的侵入性下降。AI 辅助审计在告警聚类、修复建议与变体识别上开始发挥作用，但需要以人工复核与可解释规则兜底。工程实践上，主流方向是「左移 + 门禁 + 闭环」：把 SAST/SCA 放进提交与构建阶段，把 DAST/IAST 放进集成与预发，并用修复 SLA 与逃逸复盘驱动规则迭代。相关工具能力与规则集**以官方最新文档为准**。

## 十、小结
代码审计的本质是在「代码即攻击面」的前提下，用 SAST 做早期全量筛查、用 IAST/DAST 做运行时验证、用人工审计补齐逻辑与密码学语义，并以 SCA 覆盖第三方依赖。污点分析是注入类漏洞的核心方法，其精度—代价曲线决定了工程上必须做多手段叠加与误报治理。真正有效的组织不是买了工具，而是把审计能力嵌入研发流程，让每一处信任边界上的输入都经过明确校验。
