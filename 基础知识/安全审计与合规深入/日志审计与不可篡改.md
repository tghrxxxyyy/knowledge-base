# 日志审计与不可篡改

> 对应 RFC 5424（Syslog 协议）；RFC 5848（签名 Syslog 消息）；OWASP Logging Cheat Sheet；Crosby & Wallach（USENIX Security 2009，防篡改日志数据结构）；RFC 6962（Certificate Transparency）。

## 一、背景与挑战
安全事件的事后回溯几乎完全依赖日志：攻击者何时进入、用了什么凭据、动了哪些数据，都靠日志拼出时间线。但攻击者也清楚这一点，所以「清日志」是后渗透的标准动作之一——删除系统日志、篡改应用日志、关闭审计服务。若日志本身不可信，取证结论就毫无价值，合规要求（留存、可审计）也无法满足。

难点在于四点：其一，**完整性与可验证性**——需要一种机制让任何篡改都能被检测出来，且检测不依赖「日志所在的同一台被攻陷的机器」；其二，**时序正确性**——跨主机时钟不同步会让因果颠倒，必须统一时间基准并记录偏移；其三，**内容取舍**——记太少无法回溯，记太多则成本高且可能把明文口令、令牌、个人敏感信息写入日志而违反合规；其四，**可用性**——日志系统本身也会被攻击波及，需要集中化与冗余，同时集中化又扩大了传输与存储的暴露面。

## 二、核心原理
审计日志的**记录范围**应聚焦安全相关事件：认证成功与失败、授权决策（尤其拒绝）、权限与配置变更、敏感数据访问、密钥与凭据操作、管理性操作、以及日志系统自身的启停。**只追加（append-only）** 是基本约束——日志不允许原地修改或删除，只能追加新条目。

**哈希链（hash chain）** 提供防篡改的轻量方案：每条记录连同前一条的哈希一起计算本条哈希，任何中间修改都会导致其后所有哈希失配。但哈希链对「截断尾部」无能为力——攻击者删掉最后若干条后，剩余链仍自洽。因此更完整的方案使用**Merkle 树 / 哈希树**（Merkle 1987）：叶节点是记录哈希，内部节点是子节点哈希的哈希，根哈希被周期性签名或对外发布（如 RFC 6962 的 Certificate Transparency 用「签名树头 + 一致性证明」让日志可被公众监督）。这样既能做**包含证明**（某记录确实在日志中）也能做**一致性证明**（新版日志确实扩展了旧版而非重写），还能抵抗尾部截断。

另一层是**集中化与独立留存**：把日志实时转发到与业务隔离的存储（SIEM / 对象存储的 WORM 桶），使攻击者在业务主机上的删除操作无法影响已转发的副本。传输本身需加密与认证，避免被截获或注入。同时用时间同步（NTP）加「记录本地时钟与源时钟」来支撑事后校正。

## 三、形式化与数学基础
哈希链的定义为
$$ h_i = H(h_{i-1} \| \mathrm{entry}_i),\qquad h_0 = \mathrm{GENESIS} $$
篡改 $e_k$ 会使其后所有 $h_j\ (j \ge k)$ 失配，在碰撞抗性的假设下被检测出的概率趋近 1。其弱点是尾部截断：删除尾部 $m$ 条后，前 $n-m$ 条链仍完全自洽，故必须外部锚定。Merkle 树把 $n$ 条记录组织成深度 $\lceil \log_2 n \rceil$ 的二叉树，叶为 $L_i = H(\mathrm{entry}_i)$，内部节点为
$$ N_{a,b} = H(N_{a,m} \| N_{m+1,b}) $$
根 $R$ 被签名并对外发布。**包含证明**只含 $O(\log n)$ 个兄弟节点哈希，验证者用其重算根并比对签名：
$$ \mathrm{Verify}\big(L_i,\ \mathrm{proof}_i,\ R\big) = 1 \iff \mathrm{root}(L_i, \mathrm{proof}_i) = R $$
**一致性证明**保证新根 $R'$ 是旧根 $R$ 的扩展而非替换，代价同为对数规模。用 $H$ 的抗碰撞优势 $\mathrm{Adv}^{coll}_{H}$ 界定，日志被检出篡改的概率至少为 $1-\mathrm{Adv}^{coll}_{H}$。留存容量可用「事件率 × 条目大小 × 保留窗口」估算：
$$ \mathrm{Storage} = r \cdot \bar{s} \cdot T_{retention} $$
其中 $r$ 为每秒事件数、$\bar{s}$ 为平均条目大小；该式直接决定热/温/冷分层与采样策略。

## 四、代码实现
哈希链追加与校验（示意）：
```python
import hashlib

class HashChainLog:
    def __init__(self):
        self.entries = []                                  # [(entry, h)]
        self.head = hashlib.sha256(b"GENESIS").digest()

    def append(self, entry: bytes):
        h = hashlib.sha256(self.head + b"|" + entry).digest()
        self.entries.append((entry, h))
        self.head = h
        return h
```

Merkle 根与包含证明（示意）：
```python
def merkle_root(leaves):
    level = [hashlib.sha256(x).digest() for x in leaves]
    while len(level) > 1:
        if len(level) % 2:
            level.append(level[-1])                        # 奇数个则复制末节点
        level = [hashlib.sha256(level[i] + level[i + 1]).digest()
                 for i in range(0, len(level), 2)]
    return level[0]

def inclusion_proof(leaves, idx):
    level = [hashlib.sha256(x).digest() for x in leaves]
    proof, i = [], idx
    while len(level) > 1:
        if len(level) % 2:
            level.append(level[-1])
        proof.append(level[i ^ 1])
        level = [hashlib.sha256(level[j] + level[j + 1]).digest()
                 for j in range(0, len(level), 2)]
        i //= 2
    return proof                                           # 用于重算根并比对签名
```

集中化与 WORM 留存（示意，命令与参数以各平台官方文档为准）：
```bash
# 只追加转发，业务主机本地删除不影响已转发副本
journalctl -f -o json | logger -n siem.internal -P 6514 -T   # 走 TLS 的 syslog
```

## 五、与其他技术对比
| 维度 | 本地文本日志 | 集中 SIEM | 哈希链日志 | Merkle 签名日志 | 区块链式账本 |
| --- | --- | --- | --- | --- | --- |
| 防篡改能力 | 无 | 依赖平台权限 | 中（抗中间修改） | 强（含包含/一致性证明） | 强 |
| 抗尾部截断 | 无 | 弱 | 弱（需外部锚定） | 强 | 强 |
| 校验成本 | 不适用 | 查询成本高 | 全量重算 $O(n)$ | 单条证明 $O(\log n)$ | 高 |
| 是否需外部锚定 | 不需要 | 不需要 | 需要 | 根签名/公示 | 共识网络 |
| 主要用途 | 排障 | 关联告警与合规 | 审计基线 | 可被第三方验证的审计 | 多方互不信任场景 |

## 六、常见误区
1. **「记了口令便于排障」**——错。明文口令/令牌/完整卡号写入日志直接违反合规，且日志一旦泄露等于凭据泄露；应脱敏或仅记哈希与掩码。
2. **「只记成功不记失败」**——错。认证与授权的失败事件正是暴力破解与探测的信号，缺失会让检测彻底失明。
3. **「有时钟就有时序」**——错。各主机时钟漂移会导致因果颠倒；应统一时间源并记录偏移以便校正。
4. **「哈希链就无法篡改」**——不完整。哈希链挡不住尾部截断与整段丢弃，必须用根哈希对外签名或公示来做锚定。
5. **「日志留在本机足够」**——错。攻击者通常先清日志；实时转发到隔离的只追加存储是底线要求。

## 七、与开源书·权威来源对应
- RFC 5424：Syslog 协议与消息格式，日志传输的结构化基础。
- RFC 5848：签名 Syslog 消息，为日志传输提供来源认证与完整性。
- OWASP Logging Cheat Sheet：应记录哪些事件、不该记录什么、以及日志安全的实践清单。
- Crosby & Wallach（USENIX Security 2009）：防篡改日志数据结构，哈希链与树形方案的系统论述。

- RFC 6962：Certificate Transparency，签名树头与一致性证明的工程范例。
- Tanenbaum《Modern Operating Systems》：文件系统时间戳与只追加语义的背景知识。

## 八、面试题
1. **哈希链如何防篡改？为什么还不够？** 要点：每条锚定前一条哈希，中间修改导致后续全部失配；但挡不住尾部截断，需用根哈希签名或对外公示做外部锚定。
2. **哪些事件必须记？** 要点：认证与授权（含失败）、权限与配置变更、敏感数据访问、凭据与密钥操作、管理操作、日志系统自身状态。
3. **为什么不记明文口令？** 要点：违反合规与最小必要原则，日志泄露即凭据泄露；应以脱敏、掩码或哈希代替。
4. **Merkle 树相比哈希链的优势？** 要点：包含证明与一致性证明均为对数规模，且能抵抗尾部截断与历史重写，适合被第三方验证。
5. **多主机日志如何保证时序正确？** 要点：统一 NTP 时间源、记录本地与参考时间差、在分析阶段按偏移校正后再合并时间线。

## 九、演进与趋势
可观测性技术让审计数据与追踪、指标同源，事件回溯更完整，但也带来数据量与隐私治理压力。防篡改从「哈希链 + 集中留存」演进为「签名根 + 对外公示 + 第三方可验证」，以支撑跨组织审计。采集侧，eBPF 提供内核级、低侵入的系统调用与网络审计，弥补应用日志易被绕过的短板。隐私侧，机密日志（密文存储 + 可验证查询）与聚合式审计在合规敏感场景开始落地。标准与实现细节**以官方最新文档为准**。

## 十、小结
审计日志是取证与合规的地基，其价值取决于三点：**记录范围是否覆盖关键安全事件**（含失败与变更）、**时序是否可信**（统一时钟并保留偏移）、**完整性是否可验证**（哈希链抵抗中间篡改、Merkle 签名根抵抗尾部截断与重写）。再叠加隔离的集中留存，才能让攻击者「删日志」这一动作失去意义。日志的另一个同等重要的约束是「不该记的绝不记」——不记录明文凭据与超范围个人数据，是合规与安全共同的底线。
