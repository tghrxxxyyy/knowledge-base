# 合规框架概览

> 对应 GB/T 22239-2019（网络安全等级保护基本要求）；GDPR（EU 2016/679）；PCI DSS；ISO/IEC 27001；NIST CSF；OWASP Top 10。

## 一、背景与挑战
安全合规不是可选项而是法定义务与商业门槛：处理欧盟个人数据须满足 GDPR，受理银行卡须满足 PCI DSS，国内关键信息基础设施与重要系统须通过网络安全等级保护测评，面向海外客户常还需 ISO/IEC 27001 或 SOC 2 证明。不合规的后果既有监管罚款，也有业务停摆（无法过审、无法上线、无法续约）。

真正的挑战不在于「要不要合规」，而在于三点：其一，**框架碎片化**——不同地区、行业的控制项命名与颗粒度不同，同一技术措施要映射到多套条款；其二，**时点快照 vs 持续状态**——认证测评是某个时间点的抽样结论，而系统每天都在变化，如何把合规变成持续能力而非一次考试；其三，**合规不等于安全**——通过审计只说明「有控制项且可举证」，不代表没有漏洞。因此需要把框架条款翻译为可执行、可观测、可自动校验的工程控制。

## 二、核心原理
各框架的共性是把「安全目标」分解为**控制域（control domain）**与**控制项（control item）**，再要求组织提供**制度、实现、证据**三层证明：有书面策略、有技术落地、有可被第三方核验的记录。缺任一层，在审计中都会成为发现项。

等保以**分级**为主线：按受侵害客体与影响程度定级，级别越高要求越严，覆盖安全物理环境、通信网络、区域边界、计算环境、管理中心等层面，技术与管理并重，且需定期测评与整改。GDPR 以**数据主体权利**为主线：合法基础与同意、最小化与目的限制、可携与删除（被遗忘权）、数据保护影响评估与泄露通报，并强调默认隐私（privacy by design/default）。PCI DSS 以**持卡人数据环境（CDE）**为主线：加密存储与传输、最小留存、访问控制与最小权限、日志与监控、定期测试。

落地方法是**控制项映射（control mapping）**：把一条法规要求拆解为若干技术控制（如「加密持卡人数据」→ 传输 TLS、静态加密、密钥管理、字段脱敏），再绑定到具体实现与检测手段；同一实现可同时满足多套框架，从而避免「一个要求做一遍」。

## 三、形式化与数学基础
设框架 $F$ 的控制项集合为 $C_F$，组织已实现且可举证的控制集合为 $R$。覆盖率与缺口定义为
$$ \mathrm{Coverage}(F) = \frac{|R \cap C_F|}{|C_F|},\qquad \mathrm{Gap}(F) = C_F \setminus R $$
缺口越大，说明制度或实现存在空洞，需按风险优先级补齐；而同一控制被打上越多框架标签，映射复用收益越高。等保级别越高控制项越多，可抽象为随级别 $L$ 递增的需求函数：
$$ N(L) = N_0 \cdot (1+\alpha)^{L-1},\quad \alpha > 0 $$
罚款与风险通常以上限形式约束。GDPR 的行政罚款上限形式为
$$ \mathrm{Fine} \le \max(20\ \mathrm{M\ EUR},\ 4\%\ \text{年度全球营业额}) $$
（具体档位以法规文本与监管裁量为准）。风险视角下，单一控制的价值可用风险降低量刻画：
$$ \Delta \mathrm{Risk} = \sum_{t \in T} P(t)\cdot I(t)\cdot g(c_t) $$
其中 $P(t)$ 为威胁发生概率、$I(t)$ 为影响、$g(c_t)\in[0,1]$ 为该控制对威胁的缓解度。合规决策因此应优先覆盖高 $\Delta \mathrm{Risk}$ 且被多框架共同引用的控制项——这正是「映射复用」的收益来源。此外，证据本身应可验证：
$$ \mathrm{Evidence}(c) = (\text{书面制度},\ \text{技术实现},\ \text{可核验记录}),\quad \text{三者缺一即降级} $$

## 四、代码实现
把多框架要求收敛为一张统一的控制基线，再据此生成检查与证据：
```python
# 控制基线：一条控制同时打上多个框架的标签，实现映射复用
CONTROLS = {
    "encrypt_card_at_rest":  {"frameworks": ["PCI DSS"],        "evidence": "kms-key-id + 表级加密配置"},
    "encrypt_in_transit":    {"frameworks": ["PCI DSS", "GDPR", "等保"], "evidence": "TLS 配置扫描报告"},
    "rbac_least_privilege":  {"frameworks": ["等保", "ISO27001"], "evidence": "IAM 策略快照 + 定期评审记录"},
    "consent_management":    {"frameworks": ["GDPR"],            "evidence": "同意记录与撤回链路"},
    "audit_log_retention":   {"frameworks": ["等保", "PCI DSS", "ISO27001"], "evidence": "日志留存策略 + 完整性校验"},
    "vuln_management":       {"frameworks": ["PCI DSS", "ISO27001"], "evidence": "扫描报告 + 修复工单闭环"},
}

def gap_report(implemented, framework):
    need = {k for k, v in CONTROLS.items() if framework in v["frameworks"]}
    return sorted(need - set(implemented))

print(gap_report(implemented=["encrypt_in_transit", "rbac_least_privilege"], framework="GDPR"))
# ['consent_management', 'encrypt_card_at_rest']
```

持续合规的典型做法是把该基线与 IaC/云配置扫描挂钩，每次变更自动评估：
```bash
# 用策略即代码检查基础设施是否符合基线（工具示例，以官方文档为准）
conftest test --policy policies/ infra/*.tf
```

## 六、常见误区
1. **「通过认证即安全」**——错。认证是时点抽样结论，漏洞与配置漂移照样存在；需用持续监控补足。
2. **「只做文档不落地控制」**——错。制度、实现、证据三层缺一不可，文档与实际不符在审计中属高风险发现。
3. **「一套框架一套做法」**——错。应做控制映射复用，否则维护成本线性叠加且互相矛盾。
4. **「合规只属于安全团队」**——错。研发、运维、法务、业务都承担控制落地责任，尤其隐私要求在需求与设计阶段就要介入。
5. **「通过等保就不用管 GDPR 或 PCI DSS」**——错。不同框架的目标对象不同（系统整体 / 个人数据 / 卡数据），控制项不能互相替代，只能互相复用证据。
6. **「跨境数据照搬本地做法」**——错。数据出境、本地化与传输合法性规则差异大，需结合法规文本与官方指引单独评估。

## 七、与开源书·权威来源对应
- GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》：等保 2.0 的分级与技术要求来源。
- GDPR 法规文本（EU 2016/679）：数据主体权利、合法基础与罚则的原始条款。
- PCI DSS 标准文档：持卡人数据环境的技术与管理要求，版本演进以官方最新文档为准。
- ISO/IEC 27001 与 ISO/IEC 27002：信息安全管理体系与控制措施集。
- NIST Cybersecurity Framework：识别、保护、检测、响应、恢复的功能框架。
- NIST SP 800-53：控制目录，常作为多框架映射的公共参照词汇表。
- OWASP Top 10：把常见 Web 风险映射到合规控制项（如访问控制失效、易受攻击组件）。
- Ross Anderson《Security Engineering》：从工程与组织角度讨论安全与合规的关系。

## 八、面试题
1. **等保分级的逻辑是什么？** 要点：按受侵害客体与影响程度定级，级别越高技术与管控要求越严，需定期测评整改。
2. **GDPR 的核心权利有哪些？** 要点：知情与访问、更正、删除（被遗忘）、可携、反对自动化决策、撤回同意；并配套泄露通报与 DPIA。
3. **PCI DSS 对持卡人数据的关键要求？** 要点：加密存储与传输、最小留存、访问控制与最小权限、日志监控、定期测试与漏洞管理。
4. **合规能否等于安全？** 要点：不能。合规是底线与可举证性，安全性还需威胁建模、测试与持续运营。
5. **如何减少多框架的重复工作？** 要点：建立统一控制基线并做多框架映射，一条控制绑定一份证据，以策略即代码做持续校验。

## 九、演进与趋势
趋势一是**持续合规（Continuous Compliance）**：把控制项转成策略即代码，在 CI/CD 与云配置变更时自动评估，取代年度一次性审计。趋势二是**隐私工程左移**：数据映射、最小化与同意管理进入需求与设计阶段，敏感数据发现与脱敏成为平台能力。趋势三是**供应链与证据链**：SBOM、构件签名与来源证明被多框架引用，用来证明「组件可信」。趋势四是**跨境与本地化规则的动态调整**，需要建立法规跟踪与影响评估机制。各框架条款与版本会持续更新，落地时**以官方最新文档与监管指引为准**。

## 十、小结
合规框架以分级、行业或权利模型规定安全底线，通过控制域、控制项与证据三层要求把法规翻译成工程措施。等保重分级测评，GDPR 重数据主体权利，PCI DSS 重持卡人数据环境，ISO 27001 重管理体系，NIST CSF 提供功能视角。工程上最有效的做法是建立统一控制基线做多框架映射，并以策略即代码把合规变成持续能力——因为合规是底线而非安全的上限，只有把控制真正落到系统里，认证才有意义。
