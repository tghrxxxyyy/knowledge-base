# 渗透测试方法论

> 对应 OWASP Web Security Testing Guide（WSTG）；OWASP Top 10；PTES；NIST SP 800-115；MITRE ATT&CK。

## 一、背景与挑战
防御措施是否真的有效，只能用攻击视角来验证。渗透测试的价值在于用结构化的方法发现**真实可利用**的漏洞链，而不是丢一个扫描器跑出几百条告警。它同时是一件高度敏感、受法律约束的活动：未经书面授权对系统发起测试，即使技术上是「只读探测」，也可能构成违法。

因此挑战集中在四个方面：其一，**授权与边界**——必须明确目标范围、时间窗、允许的技术（是否允许社工、是否允许 DoS 类验证）与紧急联系人；其二，**深度与风险的平衡**——深入利用可能造成业务中断或数据污染，需要约定「只证明可达，不实际破坏」；其三，**覆盖完整性**——测试人员容易陷入某一类漏洞的细节而遗漏整条攻击面，需要方法论与清单驱动；其四，**报告的可执行性**——漏洞描述必须给出复现步骤、影响与修复建议，否则修复方无从下手。

## 二、核心原理
主流方法论把过程划分为若干个阶段。**PTES** 的经典划分是：前期交互与授权约定 → 情报搜集（被动/主动侦察）→ 威胁建模 → 漏洞分析 → 漏洞利用 → 后渗透（提权、横向移动、持久化、凭据获取）→ 报告。**OWASP WSTG** 则从 Web 应用视角给出覆盖检查项：信息收集与配置管理、身份认证、会话管理、授权、输入校验（注入）、错误处理与密码学、业务逻辑、客户端测试、API 测试等。

关键思想是**以攻击面为单位组织测试**，并区分三种证据强度：观测型（如版本泄露）、验证型（如可复现的逻辑绕过）、利用型（取得 shell 或读到他人数据）。测试者需要建立攻击图（attack graph）：节点是资产与权限，边是可利用的漏洞路径，目标是最短路径到达关键资产。这与防御方的威胁建模互为镜像——防御方画攻击面，攻击方沿攻击面找最短路径。

## 三、形式化与数学基础
设端点为攻击面集合，风险按影响与可能性加权：
$$ A = \bigcup_{e \in E} \mathrm{endpoints}(e),\qquad \mathrm{Risk} = \sum_{e \in A} \mathrm{Impact}(e)\cdot \mathrm{Likelihood}(e) $$
测试覆盖度可度量为
$$ \mathrm{Coverage} = \frac{|\{\,e \in A \mid \mathrm{tested}(e)\,\}|}{|A|} $$
但更重要的是**路径覆盖**：由于漏洞常以链式出现，单点覆盖无法反映风险，攻击图上的最短可利用路径更贴近真实威胁：
$$ L^{*} = \min_{p \in \mathrm{Paths}(s \to t)} \ \sum_{v \in p} c(v),\qquad c(v) = -\log P(\mathrm{exploit}(v)) $$
即把「可利用难度」取对数后求和，路径代价越小越可能被真实攻击者采用，应优先修复该路径上的瓶颈节点。此外，修复收益可用阻断收益表示：
$$ \mathrm{Block}(v) = \sum_{p \ni v} \frac{1}{P(\text{选择 } p)} $$
即被最多可行路径共用的节点，修复它收益最大——这解释了为什么「统一鉴权中间件」的修复优先级往往高于逐点打补丁。

## 四、代码实现
授权范围内的自动化辅助（仅对自有目标运行，须有书面授权与时间窗）：
```bash
# 服务与版本识别：明确资产与暴露面
nmap -sV -Pn --top-ports 1000 target.internal

# Web 内容与参数发现：为后续测试列出端点
ffuf -u https://test.target/FUZZ -w wordlist.txt -mc 200,301,302,403

# 基线扫描作为起点，而非结论
zap-baseline.py -t https://test.target -r report.html
```

用脚本把「发现端点 → 分类 → 生成检查清单」串起来（示意）：
```python
# 从抓包/站点地图导出端点，按认证态与参数化程度分组，决定测试策略
def plan(endpoints, authed_prefixes=("/admin", "/api/me")):
    buckets = {"unauth": [], "authed": [], "state_changing": []}
    for e in endpoints:
        if e.method in ("POST", "PUT", "PATCH", "DELETE"):
            buckets["state_changing"].append(e)
        if e.path.startswith(authed_prefixes):
            buckets["authed"].append(e)
        else:
            buckets["unauth"].append(e)
    # 授权类测试优先覆盖 authed 桶：水平/垂直越权
    return buckets
```

验证一个越权假设（示意，仅用于自有环境）：
```bash
# 用 A 用户令牌访问 B 用户资源，观察是否返回 200 与数据
curl -s -H "Authorization: Bearer $TOKEN_A" \
     https://test.target/api/me/orders/$ORDER_ID_OF_B -o resp.json
grep -q '"order_id"' resp.json && echo "疑似水平越权，需人工确认影响"
```

## 六、常见误区
1. **「没有书面授权也能测」**——错。授权必须覆盖 IP/域名范围、测试类型与时间窗，越界即违法；生产环境的破坏性验证尤其需要单独许可。
2. **「扫描器结果就是渗透测试结论」**——错。扫描只是发现线索，缺少人工验证与链式利用分析，误报与漏报并存。
3. **「只看技术漏洞，忽略业务逻辑」**——错。优惠券叠加、越权改价、状态机绕过等逻辑缺陷往往影响更大且工具无法发现。
4. **「报告只列漏洞不给修复方案」**——错。可执行的复现步骤、影响评估与修复建议才是报告的核心价值。
5. **「一次测试长期有效」**——错。功能与架构持续变化，应把测试与回归纳入发版节奏，并对已修漏洞做复测。

## 七、与开源书·权威来源对应
- OWASP WSTG：Web 应用测试的完整检查项与方法，按测试类别组织。
- OWASP Top 10：风险分类与优先级依据（如 A01 访问控制失效、A03 注入）。
- PTES（Penetration Testing Execution Standard）：阶段划分与授权约定的行业事实标准。
- NIST SP 800-115：信息安全测试与评估的技术指南，含方法论与报告要求。
- MITRE ATT&CK：攻击战术与技术知识库，用于组织对抗视角与检测覆盖分析。
- Stevens《TCP/IP Illustrated》与《UNIX Network Programming》：理解网络服务与协议细节的基础。
- Ross Anderson《Security Engineering》：把攻击与防御放回真实系统与组织语境。

## 八、面试题
1. **渗透测试的典型阶段？** 要点：授权与范围 → 情报搜集 → 威胁建模 → 漏洞分析与利用 → 后渗透 → 报告与复测。
2. **WSTG 覆盖哪些方面？** 要点：配置、认证、会话、授权、输入校验/注入、密码学、错误处理、业务逻辑、客户端与 API。
3. **为什么必须书面授权？** 要点：测试行为与攻击在技术上难区分，法律与业务连续性风险需事先约定边界、时间窗与免责条款。
4. **如何判断漏洞优先级？** 要点：结合可复现性、可达性、影响面与攻击图最短路径，优先修复被多路径共用的瓶颈节点。
5. **渗透测试与红蓝对抗差别？** 要点：前者时点、目标明确、产出漏洞清单；后者持续、含检测与响应评估，产出是能力改进结论。

## 九、演进与趋势
攻击面从传统 Web 扩展到 API、移动端、云配置、容器与 CI/CD 流水线，测试方法随之加入云元数据、IaC 与供应链环节。自动化侧，持续渗透（continuous pentest）与攻击图驱动扫描开始与资产平台联动，把「项目制」变成「常态化」。红蓝对抗与紫队协作强调把攻击发现转化为**检测规则与响应流程**的改进。合规侧，渗透测试已成为多项标准（如持卡人数据环境要求）的显式条款，推动测试过程与报告也需被规范化留存。工具与框架的具体能力**以官方最新文档为准**。

## 十、小结
渗透测试是以攻击视角验证防御的结构化工程：从授权与情报搜集开始，经威胁建模、漏洞分析与利用，到后渗透与可执行报告。OWASP WSTG 与 PTES 提供覆盖清单与流程骨架，MITRE ATT&CK 提供对抗视角。其成败不取决于用了多少工具，而取决于是否在授权边界内、以攻击图为纲、把真实的漏洞链可复现地证明出来，并推动修复闭环。
