# 中止原因与回退路径

> 对应 Intel SDM 卷3 TSX 中止原因编码；ARM TME 规范（TSTART 返回码）。

## 一、背景与挑战

事务中止来源多样且不可预测：容量超限、数据冲突、页表/TLB 事件、中断、系统调用、I/O 等。健壮的 HTM 代码必须为每种中止提供回退（fallback）——否则一旦中止就数据不一致或死循环。理解中止原因编码是设计自适应策略的前提。实际工程中，绝大多数中止来自「容量」与「数据冲突」两类，特权事件（中断/系统调用）虽少但每次都会强制中止，必须据此选择是否重试。

此外要意识到「中止原因是诊断信号」：若生产中容量中止占比高，说明临界区应缩小或迁移到锁路径；若冲突中止占主导，说明数据争用激烈或存在伪共享。把中止原因纳入监控，是调优 HTM 代码的第一手依据。

## 二、核心原理

中止时硬件丢弃事务内所有写（回滚到 `XBEGIN` 前状态），并把中止原因写入 EAX 的位图（RTM）或状态寄存器（TME）。常见位：`EXPLICIT`（主动 XABORT）、`RETRY`（可重试冲突）、`CONFLICT`（数据冲突）、`CAPACITY`（容量超限）、`DEBUG`（断点）、`NESTED`。软件据此选择：可重试的中止（冲突）限次重试；不可重试的（容量、特权事件）直接降级到锁。特别地，`XABORT` 可携带自定义状态字节（4-7 位），用于区分「业务主动中止」与「硬件冲突中止」，从而走不同回退。

需要注意位图是「关于原因的建议而非保证」：不同微架构填充的位可能不同，且部分位可同时置位。因此回退判断应基于「是否包含可重试位」的保守逻辑，而非「等于某个精确值」。

## 三、形式化与数学基础

设中止原因集合 $\mathcal{A}=\{cap, conflict, interrupt, syscall, \dots\}$。回退策略可形式化为：

$$Policy(a)=\begin{cases} retry & a=conflict \land tries<T\\ lock\_path & \text{otherwise} \end{cases}$$

其中 $T$ 为最大重试次数，防「持续冲突死循环」。自适应变体把 $T$ 改为基于历史中止率 $\alpha$ 的动态阈值：当 $\alpha$ 超过阈值则跳过事务直接走锁。注意容量中止（cap）重试必败，应直接降级，否则浪费 $T$ 次无谓重试。

| 中止原因 | 可重试 | 建议动作 |
| --- | --- | --- |
| CONFLICT / RETRY | 是 | 限次重试，可加退避 |
| CAPACITY | 否 | 直接降级到锁路径 |
| EXPLICIT（自定义） | 视业务 | 按状态码分流 |
| DEBUG / 断点 | 否 | 降级（调试场景） |
| 中断 / 页错误 | 否 | 降级重试下一次 |

## 四、代码实现

```c
#define XABORT_CONFLICT  (1u << 1)
#define XABORT_CAPACITY  (1u << 2)
#define XABORT_EXPLICIT  (1u << 0)

for (int t = 0; t < MAX_RETRY; t++) {
    unsigned status = _xbegin();
    if (status == _XBEGIN_STARTED) {   // 事务开始
        critical_section();
        _xend();
        return;                        // 提交成功
    }
    // 非冲突类（容量/特权/页表）直接降级，重试无意义
    if (!(status & XABORT_CONFLICT))
        break;
}
lock_critical_section();              // 回退路径
```

更精细的做法：统计近 $N$ 次中止中 cap 占比，高于阈值则永久禁用事务路径，避免反复进入必败事务。

```c
// 自适应回退：按历史中止率决定是否还进入事务
static int aborts, attempts;
static int use_txn = 1;                      // 事务路径开关
void do_work(void) {
    if (use_txn) {
        attempts++;
        unsigned st = _xbegin();
        if (st == _XBEGIN_STARTED) { critical_section(); _xend(); return; }
        aborts++;
        if (aborts * 4 > attempts)           // 中止率 > 25% 则关闭事务路径
            use_txn = 0;
    }
    lock_critical_section();                 // 稳定回退
}
```

## 五、与其他技术对比

- 「乐观重试」适合冲突稀疏：多数时候一次提交，重试开销小。
- 「立即锁兜底」适合高冲突：跳过事务直接加锁，避免反复中止浪费。
- 「自适应混合」统计中止率动态切换，平衡二者但实现复杂，是运行时（如 glibc/HyTM 库）的常见做法。

对比维度：重试消耗 CPU 但无上下文切换；锁兜底引入可能的睡眠与调度，但保证最终完成。

| 策略 | 中止率高时 | 中止率低时 | 实现复杂度 |
| --- | --- | --- | --- |
| 固定限次重试 | 浪费重试 | 最优 | 低 |
| 立即降级 | 最优 | 错过事务收益 | 低 |
| 自适应切换 | 接近立即降级 | 接近限次重试 | 高 |

## 六、常见误区

1. 误认为无限重试最优——遇持续性冲突会死循环烧 CPU，必须限次并降级。
2. 误认为所有中止都值得重试——容量/系统调用类中止重试必失败，应直接走锁。
3. 误认为回退路径可以被忽略——回退是正确性的最后保障，必须覆盖全部中止原因。
4. 误认为中止率可忽略——在虚拟化或多插槽 NUMA 下，跨核冲突与迁移会让中止率显著偏高。
5. 误以为重试次数是「架构固定」的——`MAX_RETRY` 是软件参数，需按中止率实测调优。
6. 误以为中止后必须从零重做——若业务允许，可在回退路径复用事务内已完成的只读计算，减少重复工作。

## 七、与开源书·权威来源对应

- Intel SDM 列出 `XBEGIN` 后 EAX 中止原因位图的具体含义与保留位。
- ARM TME 规范中 `TSTART` 返回非零错误码（如 `ETMFAILURE`）用于类似回退决策。
- HyTM 研究论文讨论「事务优先、锁兜底」的正确性证明。
- Herlihy & Shavit 以事务内存与无锁结构的正确定义提供理论对照。

## 八、面试题

1. 为何系统调用会让事务中止？答：系统调用可能切换地址空间、访问不可缓存资源、触发特权事件，破坏事务隔离假设，硬件只能中止。
2. 容量中止与冲突中止重试策略有何不同？答：冲突中止可限次重试，容量中止重试必败，应直接降级锁。
3. 自适应回退如何决定走事务还是锁？答：统计近期中止率 $\alpha$，超阈值则跳过事务直接走锁路径。
4. `XABORT` 自定义位有何用？答：携带业务状态字节区分主动中止与硬件冲突，分别走不同回退分支。
5. 中止原因位图能否用于精确判断？答：不宜，位含义随微架构可能不同且可叠加，应做保守的「包含即可重试位」判断。
6. 在虚拟化环境中为何中止更频繁？答：vCPU 迁移、物理核切换与跨 NUMA 访问会频繁使监视失效，导致额外中止。

## 九、演进与趋势

运行时自适应（统计中止率决定走事务还是锁）成为最佳实践；TSX 在部分 CPU 被禁用削弱了 HTM 的可用性，推动回退逻辑更重视纯锁/无锁路径。ARM TME 也提供类似中止编码，使 HyTM 思路跨架构通用。部分库还引入「中止率指数退避」避免重试风暴。

更高层的抽象也在出现：一些运行时把「事务路径」与「降级路径」统一封装为可插拔策略，由调度器按 CPU 能力与负载动态选择；性能剖析工具（如 Intel VTune）开始直接暴露「按中止原因分类的统计」，使「为什么这段代码总是中止」从猜测变为可测量。这标志着 HTM 调优正从经验驱动转向数据驱动。

## 十、小结

HTM 的实用性取决于健壮的回退路径：识别中止原因、限次重试、最终降级到锁。把中止当「正常事件」而非「异常」来设计，是写好 HTM 代码的关键。工程落地的完整闭环是：按原因分流 → 限次重试 + 退避 → 自适应开关 → 把中止原因纳入监控，从而在冲突稀疏时吃到并发收益、在持续冲突时稳定退化为锁。
