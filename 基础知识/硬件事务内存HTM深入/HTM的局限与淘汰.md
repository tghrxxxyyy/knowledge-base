# HTM的局限与淘汰

> 对应 Intel 各代 erratum 与 2019 年后 TSX 禁用公告；Herlihy & Shavit《The Art of Multiprocessor Programming》。

## 一、背景与挑战

HTM 理论优美——用硬件自动做冲突检测与回滚，省去手写锁。但真实落地受四类约束困扰：容量（事务能覆盖的缓存行有限）、中止（冲突/特权事件频繁）、安全（推测执行状态成为侧信道）、实现复杂度（与虚拟内存/中断/系统调用交互）。Intel 多次因 erratum 与侧信道风险禁用 TSX，工业界采用极其谨慎，HTM 始终未能成为主流同步原语。这也反映在生态上：主流语言与运行时（glibc、JVM）对 HTM 仅作「可选加速」，从不作为默认路径。

另一层困难来自「事务的原语粒度」：HTM 只保证内存访问的原子性，不提供跨 I/O、跨系统调用的原子语义。任何一次 `write()`、`mmap()`、页错误或缺页，都会把事务变成「不可完成」，逼程序员把临界区切成「纯内存部分 + 非事务部分」，代码复杂度反而上升。

## 二、核心原理

HTM 的根本局限来自「把写集/读集放进缓存」这一实现选择：事务大小一旦超过缓存写集容量（或触发缓存行换出、页表写、TLB 失效）就立即中止；中断、系统调用、`WBINVD` 等特权事件同样强制中止。更隐蔽的是，事务的推测执行状态（如哪个地址在写集）可被同核/跨核通过计时等手段观测，成为微架构侧信道，迫使厂商在安全性与功能间取舍——当微码修复成本高于收益，直接关闭 TSX。另外，虚拟化下 HTM 行为更复杂：宿主机调度、vCPU 迁移都可能造成大量虚假中止。

中止可分三类：容量中止（写集/读集超限）、冲突中止（另一核访问了本事务的读/写集）、以及「非冲突类内部中止」（interrupt、页表写、CPUID 等，TSX 中报告为 `TX_ABORT` 的特定 status code）。只有冲突中止有重试价值，其余重试通常徒劳，正确的回退策略必须区分这几类，而不是无脑重试。

## 三、形式化与数学基础

中止概率随冲突率 $c$ 与事务访存规模 $s$（以缓存行计）增长。在独立冲突假设下：

$$P(abort) \approx 1-(1-c)^{s}$$

大事务（$s$ 大）、高冲突（$c$ 大）时该值迅速逼近 1，使 HTM 退化为「频繁中止→频繁回退锁」的纯开销。工程上常以「中止率 $\alpha$」作为是否值得用 HTM 的判据：$\alpha$ 超过阈值即整体降级到纯锁路径。若把单事务期望成本记为 $C_{txn}+P_{abort}\cdot C_{fallback}$，则当 $P_{abort}$ 高时总期望成本高于纯锁。

进一步可得「HTM 仅在满足下式时优于纯锁」的判据：

$$C_{txn} + P_{abort}\cdot(C_{fallback}+C_{txn}) < C_{lock}$$

即回退代价 $C_{fallback}$ 必须远小于 $C_{lock}$，且 $P_{abort}$ 必须足够低。当回退路径本身也要走一遍锁临界区，双重开销会让 HTM 的期望成本反超纯锁——这正是「高中止率下 HTM 反而更慢」的数学来源。

## 四、代码实现

```c
// 运行时检测 TSX 是否可用并决定策略
#include <cpuid.h>
int tsx_available(void) {
    unsigned a, b, c, d;
    if (__get_cpuid_count(7, 0, &a, &b, &c, &d))
        if (!(b & (1 << 11))) return 0;   // RTM 位不存在
    // 进一步检查 IA32_ARCH_CAPABILITIES / MSR 是否禁用
    if (tsx_disabled_by_ucode()) return 0;
    return 1;
}
// 主路径：可用走事务，否则直接锁
void critical(void) {
    if (tsx_available()) rtm_try();
    else lock_critical();
}
```

```c
// 区分中止类型：仅冲突类才重试，容量/内部类立即回退到锁
enum { ABORT_CONFLICT, ABORT_CAPACITY, ABORT_INTERNAL };
int rtm_try_once(void) {
    unsigned st;
    if ((st = _xbegin()) == _XBEGIN_STARTED) {
        do_work();
        _xend();
        return ABORT_CONFLICT;      // 成功
    }
    if (st & _XABORT_CONFLICT) return ABORT_CONFLICT;
    if (st & _XABORT_CAPACITY) return ABORT_CAPACITY;
    return ABORT_INTERNAL;          // 含 _XABORT_EXPLICIT / 超时
}
```

注意：即使 `CPUID` 报告 RTM 可用，运行期仍可能因 MSR（IA32_TSX_CTRL）被设为禁用而让 `XBEGIN` 立即中止，故运行期探测与回退都不可省。

## 五、与其他技术对比

| 方案 | 容量限制 | 可移植性 | 中止风险 | 工程成熟度 |
| --- | --- | --- | --- | --- |
| HTM（TSX/TME） | 受缓存限制 | 差（仅特定 CPU） | 高 | 被厂商禁用 |
| 无锁 CAS/LL-SC | 无 | 好 | 重试但稳定 | 高 |
| 成熟锁（futex/mutex） | 无 | 好 | 无 | 极高 |
| 语言级 STM | 无（软件实现） | 好 | 无（但开销大） | 一般 |

结论：HTM 在多数通用场景收益不稳定、可移植性差，逐渐被更可控的无锁/锁方案取代。

## 六、常见误区

1. 误认为 HTM 是「未来主流」——现实中部署受安全与正确性顾虑限制，多数服务器 CPU 已默认关闭 RTM。
2. 误认为容量超限很罕见——只要临界区跨越几十个以上写缓存行或触碰页表，就极易触发。
3. 误认为回退锁能完全掩盖中止——高中止率下回退锁反而成为瓶颈，且回退路径本身要正确实现。
4. 误认为检测 RTM 位即可——运行期 MSR 仍可能禁用，必须同时处理运行期立即中止。
5. 误认为所有中止都可以重试——容量与内部中止重试无意义，盲目重试只是把开销放大若干倍。
6. 误认为 HTM 能替代锁——它通常只能保护「纯内存」临界区，任何系统调用都必须移出事务。

## 七、与开源书·权威来源对应

- Intel 安全公告与微码更新说明（如相关 erratum 文档）列出 TSX 被禁用的具体型号与 MSR 控制位。
- 研究论文（如各类「TSX Aborts」分析）量化容量、冲突、页表事件导致的各类中止占比。
- Herlihy & Shavit 讨论 TM 在真实硬件上的工程代价与局限。
- Herlihy & Shavit 关于 LL/SC 与 CAS 的可等待性（wait-freedom）讨论，可用来说明「硬件原子原语为何更保守但更可用」。

## 八、面试题

1. 为何 TSX 被厂商禁用？答：微码/硬件 erratum 与侧信道风险，使厂商选择关闭 RTM/HLE 以避免错误暴露与安全漏洞，修复成本高于收益。
2. 容量超限时发生了什么？答：写集/读集超出缓存可记录范围，事务立即中止并回退到锁路径。
3. 为什么 HTM 不适合大临界区？答：事务规模 $s$ 越大中止概率越高，且大临界区更易触碰页表/系统调用等强制中止事件。
4. 虚拟化为何加剧 HTM 中止？答：vCPU 迁移、宿主机抢占都会造成大量虚假中止，使中止率失真升高。
5. HTM 与无锁 CAS 的本质取舍？答：HTM 提供「多地址原子 + 自动回滚」的易用语义，但受容量与中止限制；CAS 无容量限制且可移植，但需人工设计 ABA/可等待性。
6. 如何设计一个稳健的 HTM 回退路径？答：按中止类型分类，仅冲突类有限次重试，其余立即走锁；回退路径必须与事务路径语义等价且可被重复执行。

## 九、演进与趋势

研究转向更受限但可靠的「受控事务」（如把事务限制在特定 NUMA 域）与语言级 STM。x86 上 HTM 退居「可选加速」而非依赖特性；ARM 的 TME 同样面临容量与侧信道质疑。整体趋势是用无锁算法 + 语言级原子语义解决绝大多数并发问题，而非依赖硬件事务。

另一条路线是「硬件事务 + 软件运行时协同」：由运行时在检测到高中止率后动态关闭 HTM 路径（自适应算法），使 HTM 只在真正获益的负载上启用。这类自适应策略已成为 HTM 在工业界唯一被接受的形态。

## 十、小结

HTM 证明了事务内存在硬件上可行，但容量、中止、安全三重局限使其未能成为主流。回退到锁/无锁仍是稳健选择；把 HTM 当作「性能锦上添花、正确性靠锁兜底」的定位最为务实。实现上务必按中止类型分类处理，并以官方最新 erratum 与 MSR 文档为准。
