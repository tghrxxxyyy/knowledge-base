# 冲突检测与版本管理

> 对应 Herlihy & Moss 1993 与各类 HTM 冲突检测方案（eager/lazy）；Herlihy & Shavit《The Art of Multiprocessor Programming》。

## 一、背景与挑战

HTM 必须判断两个并发事务是否冲突。冲突检测时机与版本管理机制直接决定中止频率、回滚成本与可扩展性。核心矛盾是：检测得越早，浪费越少但干扰越多；检测得越晚，干扰小但可能做大量无效工作后才发现冲突。此外，检测精度也影响正确性——漏检冲突会破坏隔离性，误检（false conflict）则白白中止。

第三个维度常被忽略：回滚的「代价不对称」。事务可能已执行大量计算才发现冲突，此时回滚重试的成本远高于「早发现」；而 eager 检测虽能早停，却会打断其他正在推进的事务，把损失转嫁给邻居。因此检测策略实际上在「浪费自己的计算」与「干扰他人的计算」之间做分配。

## 二、核心原理

eager（急切）检测：事务写某地址时立即检查他人读集是否含该地址，命中则立即中止其中一方（通常中止后到者）。lazy（惰性）检测：提交阶段才比较读集/写集与全局版本，冲突则回滚。硬件 HTM 多借缓存一致性（MESI）自然实现——当某核写一行，相干消息会让持有该行只读副本（在他人读集）的核发现冲突。版本管理用缓存行元数据（读/写位、版本号）支撑「谁读过、谁写过」。注意 eager 在「写发生时」中止后到者，可能造成活锁（两事务反复互相中止），需用随机退避或优先级化解。

还原/回滚的实现方式是两者的第二个分水岭：eager 常配合「undo log」（写前先记旧值，回滚时逆序恢复），lazy 常配合「redo log」（写暂存于私有缓冲，提交时一次生效）。undo 需要在写时额外开销、redo 需要在读时到私有缓冲查找，二者代价位置不同。

## 三、形式化与数学基础

设地址 $a$ 有版本 $v(a)$，事务 $T$ 在开始时对每个读地址记录 $v_{seen}(a)$。提交时校验读集未被修改：

$$\forall a\in R_T:\; v_{read}(a)=v_{current}(a)$$

写集则在提交瞬间原子应用并自增版本：$v(a)\leftarrow v(a)+1,\ \forall a\in W_T$。若该不变式在提交点被破坏（某 $a\in R_T$ 版本已变），则中止。eager 把「版本变化发现」提前到写发生时，lazy 推迟到提交。版本号位宽有限，长运行需考虑回绕处理（通常以 GC 或足够位宽规避）。

| 方案 | 冲突发现点 | 所需日志 | 回滚成本 | 主要风险 |
| --- | --- | --- | --- | --- |
| eager/undo | 写发生 | undo log | 中（逆序恢复） | 活锁、干扰多 |
| lazy/redo | 提交 | redo log | 高（做完才知） | 浪费计算 |
| 混合 | 写 + 提交双向 | undo + redo | 中 | 实现复杂 |

## 四、代码实现

```c
// 惰性检测提交示意（软件版）
int commit(Txn *t) {
    // 验证：读集中每个地址版本未变
    for (int i = 0; i < t->nr_read; i++)
        if (version[t->read[i].addr] != t->read[i].seen)
            return ABORT;
    // 提交：写集刷入并自增版本
    for (int i = 0; i < t->nr_write; i++) {
        mem[t->write[i].addr] = t->write[i].val;
        version[t->write[i].addr]++;
    }
    return OK;
}
```

硬件版本管理不显式存「版本号」，而是借缓存行状态位（如 MESI 的「被他人读」标记）隐式判定：当事务提交时若该行已被他人修改，则读集失效，等价于点对点的版本校验。

```c
// eager 检测：写发生时立即校验他人读集（含 undo 记录以便回滚）
int write_eager(Txn *t, addr_t a, val_t v) {
    if (shared_read_by_other(t, a)) {   // 冲突：他人已读过 a
        rollback(t);                    // 用 undo log 逆序恢复
        return ABORT;
    }
    undo_log_push(t, a, mem[a]);        // 记录旧值，供回滚
    mem[a] = v;                         // 就地写入（写可见）
    t->write_set_add(a);
    return OK;
}
```

## 五、与其他技术对比

| 检测方式 | 失败时机 | 浪费 | 干扰 | 典型实现 |
| --- | --- | --- | --- | --- |
| eager | 写发生时 | 少（早停） | 多（频繁中止对方） | 部分 STM |
| lazy | 提交时 | 多（做完才知） | 少 | 基于缓存一致性的 HTM |

硬件多用 lazy 式（借 MESI 相干消息在写传播时发现读冲突），因为不需要显式轮询。

| 冲突表示 | 精度 | 存储 | 说明 |
| --- | --- | --- | --- |
| 精确集合（地址表） | 精确 | 大 | 无虚假冲突 |
| 签名（位数组哈希） | 近似 | 小 | 有虚假冲突 |
| 缓存行状态位 | 精确到行 | 极小 | 行内共享即视为冲突 |

## 六、常见误区

1. 误认为冲突检测免费——它依赖缓存行元数据与一致性流量，高冲突下开销显著。
2. 误认为 eager 一定更好——早失败虽省工作，但频繁中止他人会拖垮整体吞吐，且可能活锁。
3. 误认为版本号无限——版本回绕（wrap-around）在长运行系统中需以足够位宽或 GC 处理。
4. 误认为硬件无版本管理——HTM 以缓存行状态位隐式实现等价校验，并非「无版本」。
5. 误以为冲突检测粒度是「变量」——硬件粒度是缓存行，两个变量落在同一行会被判为冲突（false sharing 型冲突）。
6. 误以为签名冲突就必然中止——签名是近似表示，可能把不相交的读写集误判为冲突，需权衡位数组大小。

## 七、与开源书·权威来源对应

- Herlihy & Moss 描述基于缓存的冲突检测，奠定 HTM 硬件路线。
- 后续 LogTM（日志化 TM）、SigTM（签名 TM）等工作改进版本/签名管理，降低硬件存储。
- Herlihy & Shavit 把 TM 冲突检测与无锁算法正确性关联讨论。
- Intel SDM TSX 章节给出 RTM/HLE 中止原因与冲突处理的实现约束。

## 八、面试题

1. 为何用缓存一致性做冲突检测？答：MESI 本就广播写，硬件可借相干消息自然发现「他人读了我写的行」这类读冲突，零额外探测。
2. eager 与 lazy 的本质区别？答：冲突发现时机——写时发生 vs 提交时，权衡浪费与干扰。
3. 版本号作用？答：提交时比对读集版本，未变则证明读期间无他人写，保证隔离性。
4. eager 为何可能活锁？答：两事务反复在写发生时互相中止对方，需退避/优先级化解。
5. 为何「同缓存行的两个无关变量」也会冲突？答：硬件检测粒度是缓存行而非变量，行内任一字节被写即视为整行冲突。
6. 签名式检测的取舍是什么？答：以位数组近似读写集，大幅省存储，但存在虚假冲突（把不相交集合判为冲突而多中止）。

## 九、演进与趋势

签名式冲突检测（signature）以位数组近似读/写集，降低硬件存储但引入误判（false conflict，把不相交集合判为冲突而多中止）。研究也探索「可见性位 + 版本」混合、以及把冲突检测卸载到目录（directory）以减少广播。eager 的活锁问题催生了「中止优先级」硬件扩展。

软件侧的对应技术也在成熟：STM（软件事务内存）用「全局版本时钟 + 读写集校验」实现 lazy 检测，用「所有权记录 + 争用管理器」实现 eager 的变体；数据库领域则把同样思想表达为 MVCC（多版本并发控制）——读不阻塞写、写不阻塞读，靠版本可见性规则判定提交是否可行。可见「版本 + 冲突检测」是跨层次的通用模式。

## 十、小结

冲突检测是 HTM 核心，eager/lazy 与版本管理决定其性能曲线，常借缓存一致性天然实现。理解「何时发现冲突、如何记录版本」才能解释 HTM 的中止行为。实践中还需记住检测的物理粒度是缓存行：把共享热点数据结构做缓存行对齐与填充（padding），往往比调整事务逻辑更能降低中止率。
