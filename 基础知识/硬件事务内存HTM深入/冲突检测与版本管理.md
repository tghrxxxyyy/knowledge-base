# 冲突检测与版本管理

> 对应 Herlihy & Moss 1993 与各类 HTM 冲突检测方案（eager/lazy）。

## 一、背景与挑战
HTM 需判断两事务是否冲突。冲突检测可在写发生时立即检查（eager），或在提交时检查（lazy），二者对延迟、回滚成本与可扩展性有不同权衡。

## 二、核心原理
eager 检测：事务写时立即检查他人读集是否含该地址，命中则立即中止一方。lazy 检测：提交阶段比较读集/写集与全局版本，冲突则回滚。版本管理用缓存行元数据（如读/写位、版本号）支撑。

## 三、形式化与数学基础
设地址 $a$ 有版本 $v(a)$。事务 $T$ 提交时校验：
$$\forall a\in R_T:\; v_{read}(a) = v_{current}(a)$$
即读期间未被修改；写集则在提交瞬间原子应用并自增版本。

## 四、代码实现
```c
// 延迟检测提交示意
int commit(Txn t){
    for (a in t.read_set)
        if (version[a] != t.seen_version[a]) return ABORT;
    for (a in t.write_set) {
        version[a]++; mem[a] = t.newval[a];
    }
    return OK;
}
```

## 五、与其他技术对比
eager 早失败、少浪费但中止频繁打扰；lazy 提交时才知、浪费多但干扰小。硬件多用基于缓存一致性的 lazy 式（冲突在相干消息时检测）。

## 六、常见误区
误认为冲突检测免费。它依赖缓存行元数据与一致性流量，高冲突下开销显著。

## 七、与开源书/权威来源对应
Herlihy & Moss 描述基于缓存的冲突检测；后续 LogTM、SigTM 等工作改进版本/签名管理。

## 八、面试题
问：为何用缓存一致性做冲突检测？答：MESI 本就广播写，硬件可借相干消息自然发现「他人读了我写的行」这类冲突。

## 九、演进与趋势
签名式冲突检测（signature）以位数组近似读/写集，降低硬件存储，但引入误判（false conflict）。

## 十、小结
冲突检测是 HTM 核心，lazy/eager 与版本管理决定其性能曲线，常借缓存一致性天然实现。
