# 事务内存基本概念

> 对应 Herlihy & Moss《Transactional Memory: Architectural Support for Lock-Free Data Structures》(1993)；Herlihy & Shavit《The Art of Multiprocessor Programming》。

## 一、背景与挑战

多核时代下，用锁保护共享数据面临三大顽疾：其一，死锁——多个线程以不同顺序获取多把锁时互相等待；其二，优先级反转——高优先级线程被持锁的低优先级线程阻塞；其三，并发度低——粗粒度锁把本无冲突的访问也串行化。事务内存（Transactional Memory, TM）借用了数据库事务的思想：把一段临界区标记为「事务」，乐观地假设无冲突地执行，提交时若无冲突则整体生效（原子性、隔离性），一旦检测到冲突就中止（abort）并回滚重试。这种方式让程序员以「我这段代码要么整体发生、要么不发生」的直观心智写并发，而不必精算锁的顺序与粒度。其代价是：需要硬件或运行时拦截每次访存，且对不可事务化的操作（I/O、系统调用）无能为力，必须配合回退路径。

## 二、核心原理

事务在执行期间对内存的读、写分别记录到读集（read-set）与写集（write-set）。硬件/运行时拦截每次访存，把地址与值记入集合，但写操作通常先写入一个「影子/缓冲」区域，并不立即对其它线程可见。到达提交点时，系统检查是否有其它事务与自己冲突：若没有，则把写集原子地刷入内存并提交；若有，则丢弃本次所有写、恢复寄存器与内存状态、从开头（或某回退点）重试。与数据库事务不同，内存事务一般没有持久化（Durability）需求，回滚代价极低，且事务预期非常短（保护几个缓存行级别的临界区）。此外还有「嵌套事务（nested transaction）」概念：内层事务提交后并入外层，外层中止则整条链回滚；HTM 中常用「扁平事务（flat）」或「闭嵌套（closed nesting）」以屏蔽可恢复的中间中止。

## 三、形式化与数学基础

把事务记为 $T$，其读集 $R_T$、写集 $W_T$ 为地址集合。两并发事务 $T_i,T_j$ 冲突当且仅当它们的读写集相交：

$$Conflict(T_i,T_j) \iff (R_i\cap W_j)\cup(W_i\cap R_j)\cup(W_i\cap W_j)\neq \emptyset$$

无冲突的事务可线性化（linearizable）为任意交错顺序并安全并发提交。若把事务集合记为 $\mathcal{T}$，则可提交性等价于存在一种全序 $\prec$ 使得相邻事务互不冲突。冲突检测的本质就是把并发执行约束到「无冲突交错」这一偏序上，这与 Lamport 1979 的顺序一致性（SC）一脉相承。更进一步，若引入时间戳/版本，则可把冲突判定归约为「读集版本是否仍等于提交时快照」的验证问题。

## 四、代码实现

软件事务内存（STM）的核心是一个被拦截的临界区，下面用伪代码展示提交时对冲突的检查：

```c
// 软件事务内存（STM）提交伪代码
typedef struct { addr_t *read_set; addr_t *write_set; } Txn;

int txn_commit(Txn *t) {
    // 检查读集中每个地址是否被他人改写（验证阶段）
    for (int i = 0; i < t->nr_read; i++) {
        if (*t->read_set[i].addr != t->read_set[i].snapshot)
            return ABORT;            // 读被改，中止
    }
    // 写集刷入（提交阶段，需全局锁或原子切换）
    for (int i = 0; i < t->nr_write; i++)
        *t->write_set[i].addr = t->write_set[i].val;
    return COMMIT;
}
```

工程上更鲁棒的做法是结合「全局版本时钟 + 局部写缓冲」，提交时比较时钟而非逐地址比较，并用 try/retry 包裹：

```c
// 带回退的 STM 使用模式
for (int i = 0; i < MAX_RETRY; i++) {
    Txn t = txn_begin();
    do_work(&t);                 // 读记入 R_T，写写入本地缓冲
    if (txn_commit(&t) == COMMIT) break;
}
lock_path();                     // 事务始终失败时的兜底
```

硬件事务（HTM）把读/写集放进缓存行元数据，由缓存一致性协议自动完成上述检查，软件只需用 `XBEGIN/XEND` 包裹临界区即可。

## 五、与其他技术对比

| 维度 | 锁（互斥） | 无锁（CAS/LL-SC） | 事务内存 |
| --- | --- | --- | --- |
| 并发模型 | 悲观互斥 | 乐观无阻塞 | 乐观回滚 |
| 死锁风险 | 有 | 无 | 无（但可能活锁/中止风暴） |
| 编程复杂度 | 高（锁序） | 高（算法难写） | 低（临界区直写） |
| 高冲突下 | 串行但稳定 | 重试但稳定 | 频繁中止，吞吐崩塌 |
| 适用场景 | 通用 | 单变量、短临界 | 低中冲突、多变量临界区 |

可见 TM 在低中冲突下并发度显著更高、代码更直观，但在高争用场景会因「中止风暴」反而比锁更慢。因此实践中 TM 通常作为「乐观快路径」，锁作为「悲观兜底」。

## 六、常见误区

1. 误认为事务内存永远优于锁——高争用场景下中止风暴使吞吐崩塌，且事务有容量与系统调用限制，并非银弹。
2. 误认为事务能替代所有同步——I/O、系统调用、跨进程共享内存通常不可事务化，必须走回退路径。
3. 误认为回滚是「免费」的——虽然内存回滚廉价，但事务内若产生外部可见副作用（如打印、网络发送）则无法撤销，即「语义中止」陷阱。
4. 误认为隔离意味着性能无代价——冲突检测依赖缓存行元数据与一致性流量，也有硬件开销。
5. 误认为事务一定比无锁简单——当写集需跨多个不相邻缓存行、且需保证全序时，无锁结构可能反而更可控。

## 七、与开源书·权威来源对应

- Herlihy & Moss 1993 原始论文提出以缓存行元数据实现 HTM 的硬件支持，奠定读写集与冲突检测思路。
- Herlihy & Shavit《The Art of Multiprocessor Programming》系统讲解 STM 与无锁数据结构的关系。
- Shavit & Touitou 1997 提出 Software Transactional Memory（STM），使 TM 不必依赖硬件。
- Lamport 1979 顺序一致性论文为「无冲突交错」提供理论底座。
- C++ Transactional Memory 技术规范（已撤回 TS）曾探索语言级 `atomic`/`synchronized` 语法。

## 八、面试题

1. 事务内存与数据库事务的异同？答：都讲 ACID 中的 A（原子）/I（隔离），但内存事务无持久化（D，除非 NVM），无 Undo 日志（靠缓存回滚），中止代价低，用于短临界区。
2. 为什么高冲突下 TM 反而慢？答：每次冲突都整体回滚重试，冲突率 $c$ 高时中止概率 $1-(1-c)^s$ 迅速逼近 1，退化为频繁回退。
3. 一个事务里调用了 `printf`，中止会发生什么？答：`printf` 已产生终端输出这一外部副作用无法撤销，属于语义中止陷阱，必须将此类操作移出事务或走回退路径。
4. 读写集冲突分别指什么？答：读集被他人写称「读冲突」，写集被他人读/写称「写冲突」。
5. 嵌套事务如何回滚？答：闭嵌套中内层提交并入外层，外层中止整条链回滚；开嵌套（open）则内层提交即对外可见，需谨慎使用。

## 九、演进与趋势

HTM 与 STM 的混合（HyTM）结合二者优点：硬件事务做快路径、软件事务/锁做慢路径兜底。研究上还出现了基于「签名（signature）」的近似冲突检测，以位数组压缩读/写集以降低硬件存储，代价是引入误判（false conflict）。语言层面上，C++ 事务性内存技术规格虽被撤回，但 Rust、Java 等社区仍在探索更安全的语法糖。随着 Intel TSX 在部分型号被微码禁用，工业界对「把 TM 当硬依赖」趋于谨慎，更多把它作为可选加速而非基础设施。

## 十、小结

事务内存用「乐观、冲突回滚」取代锁，简化了并发编程的心智模型，其正确性根植于读写集冲突检测与无冲突交错的全序约束。但它依赖低冲突假设、受容量与系统调用限制，且对外部副作用无能为力——理解这些边界，才能把它用对地方。
