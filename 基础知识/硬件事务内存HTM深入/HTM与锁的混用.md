# HTM与锁的混用

> 对应 Intel《TSX Best Practices》；各类 HyTM（混合事务内存）研究（如 Dalessandro et al.）。

## 一、背景与挑战

纯 HTM 难覆盖所有情况：大临界区超容量、含系统调用/I/O、或跨进程共享内存均不可事务化。纯锁则放弃 HTM 的并发收益。实践中采用 HyTM（混合事务内存）：事务包裹临界区，失败则降级为传统锁，兼顾性能与正确性。这正是 Intel HLE 的设计哲学。更进一步的工程实践还会加入「统计自适应」——当事务路径持续失败时直接跳过，不再进入必败事务。

还有一层隐蔽风险：事务路径与锁路径保护的必须是**同一组内存位置**，且回退时不能出现「事务内已读、锁内未重读」的情况。若两路径的读写集合不一致，降级后可能基于过期读做出决策，产生仅在「事务恰好失败」时才出现的竞态——这类 bug 极难复现。

## 二、核心原理

HLE 的 `XACQUIRE`/`XRELEASE` 通过在锁变量上做「锁消除」实现：若事务成功提交，锁从未真正获取（其它线程可见它未被持有，可并发进入）；若中止，硬件自动「按原锁语义」获取并持有锁，互斥不变。这样遗留代码几乎零改动即可受益。RTM 则可在 `XBEGIN` 失败时显式调用原锁函数兜底，逻辑等价于「事务优先、锁兜底」。需要强调的是：回退路径使用的「锁」必须与事务保护的「同一临界区」语义一致，否则降级后会出现新的竞态。

两者的实现差异也要清楚：HLE 是「指令前缀」式，无需改控制流，事务边界由锁获取/释放隐式界定；RTM 是「显式区域」式，用 `XBEGIN/XEND` 框出边界，可用 `XABORT` 主动中止并携带状态码。HLE 更易改造既有代码，RTM 更灵活（可控制边界位置与中止原因），代价是需要显式写回退分支。

## 三、形式化与数学基础

设锁获取为 `L.acq()`。HLE 语义可写为：

$$XACQUIRE(L.acq) \Rightarrow \begin{cases} \text{若事务提交，} L \text{ 从未被持有}\\ \text{若中止，} L \text{ 实际被获取} \end{cases}$$

无论走哪条路径，互斥不变量 $\neg(\exists t_1\neq t_2: held(L,t_1)\land held(L,t_2))$ 都成立，故 HyTM 正确性可归约为锁的正确性。进一步，若事务路径成功概率 $p$ 高，则平均持锁时间远短于纯锁，吞吐提升正比于 $p$。

| 路径 | 是否持有锁 | 可并发 | 正确性依据 |
| --- | --- | --- | --- |
| 事务提交 | 否 | 是 | 全序 + 冲突检测 |
| 事务中止 | 是 | 否 | 与纯锁完全同构 |
| 回退加锁 | 是 | 否 | 普通互斥 |

## 四、代码实现

```asm
; HLE 包裹自旋锁（x86-64）
    xacquire lock bts [lockvar], 0   ; 尝试锁消除
.spin:
    jc .spin                         ; 被他人真正持有则自旋
    ; ---- 临界区 ----
    mov eax, [shared]
    add eax, 1
    mov [shared], eax
    ; ----
    xrelease lock btr [lockvar], 0   ; 提交事务 / 实际释放
```

失败时硬件按普通 `lock bts` 执行自旋等待，二进制在新旧 CPU 上均正确。RTM 写法则是 `xbegin .abort ... xend` 后接 `lock` 兜底，二者逻辑等价、性能曲线不同。

```c
// RTM 版本：事务优先、锁兜底（含重试上限）
#include <immintrin.h>
for (int t = 0; t < MAX_RETRY; t++) {
    unsigned st = _xbegin();
    if (st == _XBEGIN_STARTED) {          // 进入事务
        if (lock_is_held()) _xabort(1);   // 有人持锁则立刻中止，避免无效工作
        critical_section();
        _xend();                          // 提交
        return;
    }
    if (!(st & _XABORT_RETRY)) break;      // 不可重试类中止，直接降级
}
pthread_mutex_lock(&m);                    // 兜底：与事务保护同一临界区
critical_section();
pthread_mutex_unlock(&m);
```

## 五、与其他技术对比

| 方案 | 并发（无冲突） | 鲁棒性 | 实现成本 | 可移植性 |
| --- | --- | --- | --- | --- |
| 纯锁 | 低（串行） | 高 | 低 | 好 |
| 纯 HTM | 高 | 低（易中止） | 中 | 差 |
| HyTM | 高 | 高（锁兜底） | 中 | 差（依赖 TSX） |

HyTM 最实用，但强绑定特定硬件。

| 变体 | 事务边界 | 中止控制 | 改造量 |
| --- | --- | --- | --- |
| HLE | 由锁操作隐式界定 | 不能主动中止 | 极小 |
| RTM | 显式 `XBEGIN/XEND` | 可 `XABORT` 带码 | 中 |
| STM（软件） | 显式 | 完全可控 | 大 |

## 六、常见误区

1. 误认为加 `XACQUIRE` 就保证无锁——事务仍可能中止并实际获取锁，且锁内不能含不可事务化操作。
2. 误认为 HLE 提升单线程性能——它只在多竞争下有利，无冲突时与锁持平。
3. 误认为 HyTM 可完全替代锁设计——回退路径仍需正确实现，否则降级后死锁。
4. 误认为降级锁可用不同实现——回退锁必须与原锁语义一致，混用会造成隐蔽竞态。
5. 误以为 `xacquire/xrelease` 是独立指令——它们是前缀，必须附着在 `lock` 指令上，单独出现无意义。
6. 误以为中止后一切自动回滚——内存写会被回滚，但**寄存器与外部副作用（如 I/O）不会**，因此事务内不得有不可撤销的副作用。

## 八、面试题

1. HLE 如何向后兼容？答：`XACQUIRE` 在旧 CPU 上被忽略、按普通锁执行，新 CPU 上做锁消除，同一二进制两者正确。
2. HyTM 为何能保持互斥？答：无论事务提交（锁未持有）还是中止（锁实际获取），互斥不变量都成立，正确性归约到锁。
3. 什么操作不能放进 HLE 事务？答：系统调用、I/O、跨进程共享内存、超容量的大临界区。
4. 自适应 HyTM 如何避免重试风暴？答：统计中止率，超阈值则跳过事务直接走锁。
5. 事务内能否有 I/O 副作用？答：不宜。内存写可回滚，但已发出的 I/O 无法撤销，会导致「中止也产生了效果」的不一致。
6. HLE 与 RTM 的核心差异？答：HLE 是前缀式、隐式边界、零改造；RTM 是区域式、显式边界、可控中止与原因。

## 九、演进与趋势

随 TSX 在部分型号被微码禁用，HyTM 的实用性受挫，社区更关注可移植的 STM/无锁方案；但「事务优先、锁兜底」的设计模式仍被无锁库借鉴（如先 try 无锁再 fallback 加锁）。研究方向的 HTM 也尝试把「事务路径」做成可热插拔，运行时按 CPU 能力切换。

工程上的替代路径同样值得关注：不依赖硬件事务的「乐观并发」可用版本号 + 提交时校验（如读写锁升级、seqlock、乐观快照）实现类似效果；持久内存（PMEM）领域则把「事务」概念扩展到「崩溃一致性」，用日志与刷写屏障（`clwb`/`sfence`）模拟事务语义。可见「事务内存」的思想正在以不同形态延续。

## 十、小结

HTM 与锁混用（HyTM）是工程现实：事务优先、锁兜底，兼顾性能与鲁棒性。理解「锁消除」的两条路径如何都维护互斥，是用好 HLE 的关键。落地时务必确认三件事：回退锁与事务保护同一临界区、事务内无不可撤销副作用、以及存在统计自适应以防持续失败时反复进入必败事务。
