# 连接重置RST的产生与处理

> 对应 RFC 9293（原 RFC 793）第 3.4 节复位、RFC 1122 第 4.2.2.12 节、Stevens《TCP/IP Illustrated》卷一第 18 章。

## 一、背景与挑战
RST 段用于异常的即时连接终止，它不进入正常四次挥手，而是直接丢弃缓冲并通知应用层「连接被重置」。RST 常用于端口无监听、半打开连接探测、以及防御性拒绝。理解 RST 的触发条件对排查「connection reset by peer」至关重要——因为同一句报错可能来自对端崩溃、应用主动 abort、防火墙注入或序列号不匹配，定位方式截然不同。

与 FIN 的优雅语义不同，RST 意味着「我不想也不打算和你继续」，接收方应立即放弃该连接，已缓冲但未读的数据也会丢失。因此 RST 是一把双刃剑：既是合法的错误通知，也常被中间盒用作策略执行手段。

RST 的另一层复杂性在于「谁发出的」。抓包只能看到 RST 从某跳到达，无法直接判断是端系统还是中间设备。常见判据包括：RST 的 TTL 与前后文的 TTL 是否一致（不一致说明来自别的设备）、RST 的序列号是否为 0/异常、以及 RST 出现在三次握手前还是数据阶段。这些经验规则不能替代证据，但可大幅缩小排查范围。

## 二、核心原理
当报文到达一个不存在的套接字（如目标端口无进程监听），内核回送 RST。半打开连接（一端已崩溃重启，另一端仍维持 ESTABLISHED）在收到对端数据时会因序列号不在期望窗口内而收到或发送 RST。应用可设置 `SO_LINGER` 且 `l_onoff=1, l_linger=0` 以发送 RST 而非 FIN 关闭。

此外，收到非预期 SYN（如早已关闭端口又来 SYN）或校验失败的段，也会触发 RST。RST 段本身不带数据、不要求确认，接收方一收到即终止连接，不进入任何 TIME_WAIT 式的等待。

RFC 9293 对「何时发 RST」给出精确条件，核心是三条：一是到达的段不匹配任何连接（含目标端口无监听）；二是段落在 CLOSED 状态的连接上（回 RST）；三是连接处于非同步状态（SYN_SENT/SYN_RCVD）而收到不可接受的段。此外，RFC 规定「携带 RST 的段不得再以 RST 响应」，否则两端会互相回击形成 RST 风暴。

应用层还有两条常见的 RST 来源：一是收到数据后调用 `close` 但接收缓冲仍有未读数据，内核可能直接发 RST 而非 FIN（表示「这些数据我不要了」）；二是 `SO_LINGER` 设为 0 时主动 close。前者解释了「对端说收到 RST，但我们明明只是 close」的现象。

## 三、形式化与数学基础
RST 判定常依赖序列号是否落在接收窗口内。对于处于 SYN_RCVD 的套接字，若收到 ACK 但确认号不合法：

$$ ack \neq (snt\_isn + 1) \;\Rightarrow\; \text{发送 RST} $$

半打开连接探测中，若收到的段 seq 不在期望窗口 $[rcv\_nxt,\; rcv\_nxt + rcv\_wnd)$ 内，则回 RST：

$$ seq \notin [rcv\_nxt,\ rcv\_nxt + rcv\_wnd) \;\Rightarrow\; \text{发送 RST} $$

RFC 793 还规定：若段携带 RST 标志则忽略之（RST 不被 RST 响应），避免复位风暴；且 RST 不消耗序列号。

更完整地，当连接处于已同步状态（ESTABLISHED/FIN_WAIT 等）时，判定条件为「段可接受性」：段必须落在接收窗口内（允许零长窗口段的边界情形），且若是 ACK 段则确认号须在合理范围 $(snd\_una, snd\_nxt]$ 内。任一不满足，直接回 RST 并终止连接，而不做「静默丢弃」——这一点与「纯乱序」不同：乱序段落在窗口内会被缓存，只有真正落在窗口外才回 RST。因此「半打开」之所以引发 RST，是因为对端重启后 `rcv_nxt` 归零，我们的序号显得「远在未来」。

## 四、代码实现
Linux 在 `tcp_v4_do_rcv` 中检测到无对应 sock 时回 RST：

```c
// 简化自 net/ipv4/tcp_ipv4.c
if (sk->sk_state == TCP_CLOSE)
    return tcp_v4_send_reset(sk, skb);
```

应用层强制 RST 关闭（linger 为 0）：

```c
struct linger l = { .l_onoff = 1, .l_linger = 0 };
setsockopt(fd, SOL_SOCKET, SO_LINGER, &l, sizeof(l));
close(fd);   // 发送 RST 而非 FIN
```

需注意：linger=0 的 RST 会让对端丢失未读数据，应仅在明确放弃连接时使用。

另一种产生 RST 的常见写法是「收到少量数据就 close」：

```c
/* 若接收缓冲仍有未读数据，close 时内核会发 RST 而非 FIN */
char buf[64];
recv(fd, buf, sizeof(buf), MSG_PEEK);   // 只窥视未读完
close(fd);                              // 剩余数据被丢弃 -> RST
```

要避免这种情况，应先 `shutdown(fd, SHUT_WR)` 等待对端把剩余数据发完并正常关闭，或把接收缓冲读空后再 close。

## 五、与其他技术对比
RST 是立即终止，FIN 是优雅半关闭（仍可收完对端已发数据）；UDP 无 RST 概念，不可达端口直接丢弃并返回 ICMP 端口不可达。SCTP 的 ABORT 块语义类似 RST，但携带原因码便于诊断。

QUIC 用 CONNECTION_CLOSE 帧，区分应用层关闭与传输层错误，且对端可选择性忽略某些错误。相较之下，TCP 的 RST 信息量极少，几乎只表达「重置」，诊断需结合抓包。

| 维度 | TCP RST | TCP FIN | SCTP ABORT | QUIC CONNECTION_CLOSE |
| --- | --- | --- | --- | --- |
| 语义 | 立即丢弃、异常终止 | 优雅半关闭 | 立即终止 | 区分应用/传输错误 |
| 携带原因 | 无 | 无 | 有原因码 | 有错误码与原因串 |
| 未读数据 | 丢弃 | 可继续读 | 丢弃 | 丢弃 |
| 是否可忽略 | 不可 | 不可 | 不可 | 部分错误可忽略 |

## 六、常见误区
误区一：收到 RST 后还能继续收发数据——实际连接已被废弃，读写会失败。误区二：认为 RST 一定代表对端崩溃——也可能是应用主动 abort 或中间盒（防火墙、负载均衡）注入。

误区三：以为 RST 一定带数据——RST 段通常不携带数据，仅用于通知。误区四：忽视 RST 也可能由 TIME_WAIT assassination（收到合法 RST 提前结束 TIME_WAIT）引起，需时间戳保护。误区五：把 ECONNRESET 与 ETIMEDOUT 混为一谈——前者多因 RST，后者多因无响应。

误区六：以为 keepalive 一定能探出坏连接——keepalive 探测失败时才发 RST，且默认周期很长（以官方文档为准）。误区七：以为 RST 会先生效再通知应用——内核会立即终止连接并把错误码交给阻塞的读写调用，已入缓存的待发数据被丢弃。

## 八、面试题
1. 为什么连接一方崩溃重启后，另一方发数据会收到 RST？答：崩溃方重启后无原连接状态，收到带数据的段序列号不在窗口内，按 RFC 793 回 RST 终止半打开连接。
2. `SO_LINGER` 设 0 与默认 close 有何不同？答：默认 close 发 FIN 走优雅关闭；linger=0 发 RST 立即丢弃缓冲，对端可能丢失未读数据。
3. 为何 TIME_WAIT 收到 RST 不立即消失？答：为防止旧报文串扰，标准规定 TIME_WAIT 对 RST 的处理受 PAWS 与时间戳约束，普通 RST 不提前结束。
4. 如何判断 RST 来自中间盒？答：比对 RST 与其上下文的 TTL/源 MAC 是否一致，观察是否在握手前或固定阈值出现，并做端到端两侧抓包对比。
5. 端口无监听时为何回 RST 而非静默丢弃？答：静默丢弃会让发起方一直重试直到超时；回 RST 能尽快告知「此端口不可达」，同时 RFC 1122 明确要求这样做。
6. 为什么「RST 不被 RST 响应」很重要？答：否则两端在各收到 RST 后又互相回 RST，形成无限风暴。

## 九、演进与趋势
现代中间盒（防火墙、负载均衡、代理）常主动注入 RST 以实现连接限速或策略拒绝，这使「connection reset」成因更趋复杂，需要结合抓包区分是端系统还是中间盒行为。同时，TLS 与加密隧道的普及使得被动 RST 注入难以区分于真实中断，诊断更依赖端到端日志。

在服务网格中，sidecar 常以 RST 或 FIN 代为关闭后端连接，需结合 tracing 还原真实关闭方，避免误判业务异常。可以预期，未来传输协议（如 QUIC）会用更结构化的关闭原因替代「仅有 RST」的模糊语义。

## 十、小结
RST 是 TCP 用于异常即时终止的机制，触发于无监听端口、半打开连接、显式 abort 与策略拒绝。定位 RST 需结合序列号、连接状态与抓包综合判断，不能简单归因于对端崩溃。理解「RST 不被 RST 响应」「RST 不消耗序列号」「有未读数据时 close 可能发 RST」这三条细节，是准确诊断的一半。
