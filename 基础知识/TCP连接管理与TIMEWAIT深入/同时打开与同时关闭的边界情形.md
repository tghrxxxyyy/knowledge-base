# 同时打开与同时关闭的边界情形

> 对应 RFC 9293（原 RFC 793）第 3.4 节与附录状态机、Kurose & Ross《Computer Networking: A Top-Down Approach》第 3 章、Stevens《TCP/IP Illustrated》卷一 18.8、Tanenbaum《Computer Networks》传输层章节。

## 一、背景与挑战
标准三次握手隐含一个不对称假设：存在主动打开方（client）与被动打开方（server），前者发 SYN，后者从 LISTEN 出发回 SYN+ACK。但 TCP 规范从未规定两端必须扮演不同角色——状态机本身是**对称**的，两个对等端完全可能在同一时刻各自主动打开，或在已建立连接上几乎同时发起关闭。

这两类边界情形会打破实现与运维的默认假设：
- 若状态机只按「收到 SYN 即在 LISTEN 回复」编写，同时打开的纯 SYN 会被当作错误丢弃或触发 RST；
- 若关闭路径只按「FIN 之后必是 ACK」编写，同时关闭中的 FIN 会被误判为乱序或重复报文。

在 P2P 直连、NAT 穿透、中间件心跳重连等场景中，对称建连并不罕见。理解它们既能解释「两端 connect 都成功却不走标准三次握手」的现象，也能定位一类难以复现的连接异常。

## 二、核心原理
**同时打开（simultaneous open）**。双方都调用 connect 进入 SYN_SENT 并各自发出 SYN（无 ACK）。当一方处于 SYN_SENT 收到对方的**纯 SYN**（`SYN=1, ACK=0`）而非预期的 SYN+ACK 时，不返回 RST，而是迁移到 SYN_RCVD，回送 SYN+ACK。随后各自收到对方的 SYN+ACK 并回 ACK，双双进入 ESTABLISHED。最终只建立**一条**连接，共交换 4 个报文段（普通握手 3 个）。

**同时关闭（simultaneous close）**。双方均处于 ESTABLISHED 并各自发送 FIN，进入 FIN_WAIT_1。当收到对方的是 FIN（而非期望的 ACK）时，说明双方都在关闭：本端 ACK 掉对方 FIN 后进入 CLOSING，等待对方对本端 FIN 的 ACK。待 ACK 到达后进入 TIME_WAIT，经历 2MSL 后回到 CLOSED。关键点：**双方都会进入 TIME_WAIT**，而不是通常的「先关方独占 TIME_WAIT」。

## 三、形式化与数学基础
两类场景的报文段数量对比：

$$ N_{seg}^{normal} = 3,\qquad N_{seg}^{simopen} = 4 $$

同时关闭的迁移链，其中触发条件是「收到对端 FIN 而非 ACK」：

$$ ESTAB \xrightarrow{FIN} FIN\_WAIT\_1 \xrightarrow{FIN} CLOSING \xrightarrow{ACK} TIME\_WAIT $$

用发送事件 $s_i$ 与接收事件 $r_j$ 表示时序，同时关闭的充要条件是双方都在看到对方 FIN 之前已发出自己的 FIN：

$$ s_1(FIN) \prec r_2(FIN) \;\wedge\; s_2(FIN) \prec r_1(FIN) $$

反之若 $r_2(FIN) \prec s_1(FIN)$，则退化为普通顺序关闭（一方 FIN_WAIT_2、另一方 CLOSE_WAIT），只有先关方经历 TIME_WAIT。可见同时关闭的判定本质是**时序竞争**，而非状态机新分支。TIME_WAIT 时长取 $2 \times MSL$，MSL 的具体取值以各实现官方最新文档为准（Linux 固定不可配置，其他系统可按 RFC 建议设定）。

## 四、代码实现
Linux 在 `tcp_rcv_synsent_state_process` 中区分「纯 SYN」与「SYN+ACK」，前者走同时打开分支：

```c
/* 简化自 net/ipv4/tcp_input.c，示意思路，非逐行源码 */
if (th->syn) {
    if (th->ack) {
        /* 正常路径：SYN+ACK，握手完成，进入 ESTABLISHED */
        tcp_set_state(sk, TCP_ESTABLISHED);
    } else {
        /* 同时打开：对端也在主动打开，回送 SYN+ACK */
        tcp_set_state(sk, TCP_SYN_RECV);
        tcp_send_synack(sk);
    }
}
```

同时关闭无需专门代码分支：FIN_WAIT_1 收到 FIN 的转移（进入 CLOSING）本就存在于 TCP 状态机中，两条关闭路径共享重传定时器与 TIME_WAIT 超时处理，唯一差别是「进入 TIME_WAIT 的端数」从 1 变为 2。

```text
FIN_WAIT_1 收到 ACK       -> FIN_WAIT_2
FIN_WAIT_1 收到 FIN       -> CLOSING     （同时关闭起点）
FIN_WAIT_1 收到 FIN + ACK -> TIME_WAIT
CLOSING   收到 ACK        -> TIME_WAIT
```

## 五、与其他技术对比
| 维度 | TCP | SCTP | QUIC |
| --- | --- | --- | --- |
| 对称建连支持 | 有（同时打开，4 段） | 原生（INIT/INIT-ACK 对称） | 由连接状态机处理 |
| 同时关闭语义 | 双方 TIME_WAIT | SHUTDOWN 握手 | 连接 ID + 显式关闭 |
| 连接标识 | 四元组 | 四元组 + Verification Tag | Connection ID |
| 队头阻塞 | 有（单一字节流） | 缓解（多流） | 无（多流独立） |
| 防火墙友好度 | 入向 SYN 常被丢弃 | 部署较少 | 基于 UDP 较易穿透 |

TCP 的同时打开在实践中少见且易被安全设备拦截；SCTP 因四路握手与 Cookie 机制天然对称；QUIC 用连接 ID 与 UDP 封装，从根本上回避了「谁是客户端」的四元组绑定。

## 六、常见误区
误区一：以为同时打开会建立两条连接。实际只建立一条，只是多花一个报文段（4 段而非 3 段）。

误区二：以为同时关闭只需一方进入 TIME_WAIT。双方都发过 FIN 且都需 2MSL 吸收迟到报文，故**两方都进 TIME_WAIT**，连接资源占用翻倍。

误区三：以为「两端同时 connect 就必然同时打开」。触发条件是双方都处于 SYN_SENT 且都未在 LISTEN；若一方已在 LISTEN，收到的 SYN 走标准三次握手，退化为普通建连。

误区四：以为防火墙一定友好放行。多数中间设备默认丢弃无主动状态的入向 SYN，同时打开因而失败，工程上常需回退到「一方先侦听」的拓扑。

误区五：把 CLOSING 与 LAST_ACK 混淆。CLOSING 从 FIN_WAIT_1 收到 FIN 进入，是对称关闭特有；LAST_ACK 是 CLOSE_WAIT 后发出 FIN 的被动关闭路径。

## 八、面试题
1. **同时打开需要几个报文段？** 4 个。双方各自发出 SYN 且互不以 SYN+ACK 回应，需要额外一次「SYN+ACK / ACK」交换，故比标准握手多一段。
2. **同时关闭与正常关闭的状态机差异？** 正常关闭在 FIN_WAIT_1 收到 ACK 后进 FIN_WAIT_2，仅先关方 TIME_WAIT；同时关闭在 FIN_WAIT_1 收到 FIN 后进 CLOSING，双方各自 TIME_WAIT。
3. **为什么现实中很少见到同时打开？** 典型服务端处于 LISTEN，收到 SYN 直接走标准握手；只有两端都主动 connect 才触发，且常与丢弃入向 SYN 的防火墙策略冲突。
4. **为什么同时关闭必须先经 CLOSING 而不能直接 TIME_WAIT？** 收到对方 FIN 并不等于对方确认了本端 FIN；必须等对方对本端 FIN 的 ACK 到达，才能确保双方 FIN 均被确认。

## 九、演进与趋势
现代 P2P 与 NAT 穿透场景中，TCP 同时打开配合 `SO_REUSEADDR` 可支持对等连接，但防火墙拦截入向 SYN 使其可靠性不足，实践中更多借助 UDP 打洞（STUN/TURN，RFC 5389/8656）或 QUIC。多路径 TCP（MPTCP，RFC 8684）各子流仍遵循类似建连与关闭语义，由主连接协调。QUIC 以 Connection ID 标识连接、用 UDP 封装，天然规避四元组绑定与同时打开的尴尬，其具体的重连与 0-RTT 语义以官方最新 RFC 为准。

## 十、小结
同时打开与同时关闭是 TCP 对称状态机的两个边界分支：前者以 4 段握手建立单条连接，后者以 CLOSING 与双方 TIME_WAIT 保证迟到报文被吸收。它们揭示了「客户端/服务端」只是角色约定而非协议约束，理解它们对分析非常规连接失败、评估防火墙策略与设计 P2P 穿透方案都有实际价值。
