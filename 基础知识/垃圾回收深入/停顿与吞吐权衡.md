# 停顿与吞吐权衡

> 对应 Jones《GC Handbook》第 9 章 与 CS-Notes。

## 一、背景与挑战
GC 设计本质是吞吐（总工作时间）与停顿（单次最大暂停）的权衡：更并发降停顿但通常降总吞吐并增内存；更 STW 反是。挑战：按场景选策略（延迟敏感 vs 吞吐敏感）。

## 二、核心原理
吞吐 = 应用时间 / (应用+GC) 时间。停顿 = 单次 STW 最长。并发度↑→停顿↓但屏障/同步成本↑→吞吐↓；空间换时间：更大堆降 GC 频率但增延迟风险。

## 三、形式化 / 数学基础
设 mutator 速率 $\mu$，collector 速率 $\lambda$。并发时吞吐上限 $\mu/(\mu+\lambda)$ 受 collector 占用的 CPU 比例影响。
暂停时间 $P$ 与回收窗口成反比：分代/并发把 $P$ 从 $O(|H|)$ 降到 $O(\text{存活小块})$。

## 四、代码实现
```python
# 策略示意：根据 SLA 选 GC
if latency_sla_ms < 10:
    use("ZGC")     # 并发转移，亚毫秒
else:
    use("Parallel") # STW，吞吐优先
```

## 五、与其他技术对比
- Parallel/STW：吞吐最高、停顿长（批处理友好）。
- CMS/G1：平衡。
- ZGC/Shenandoah：停顿极低、吞吐略损（交互/服务友好）。

## 六、常见误区
1. 以为并发 GC 一定吞吐更好（其实常略低）。
2. 只调堆大小不调 GC 算法。
3. 把吞吐当延迟（高吞吐也可能偶发长暂停）。
