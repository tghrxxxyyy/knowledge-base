# 自旋锁与阻塞锁权衡

> 对应 OSTEP（Remzi 等）《Operating Systems: Three Easy Pieces》锁章节、Tanenbaum《Modern Operating Systems》同步原语、Bryant & O'Hallaron《CSAPP》第 12 章、Herlihy & Shavit《The Art of Multiprocessor Programming》。

## 一、背景与挑战
临界区极短时，线程挂起与唤醒的上下文切换开销（典型数微秒量级，含 TLB 与调度器开销）可能远超锁持有时间本身。选错锁类型会造成两种浪费：自旋锁在等待期间空转烧掉整颗核；阻塞锁为极短临界区付出两次上下文切换的代价。核心问题是——等待锁期间是**忙等**还是**让出 CPU**？答案取决于临界区长度、核数、以及等待者是否处于不可睡眠上下文（中断、软中断、持有自旋锁时）。

## 二、核心原理
自旋锁在获取失败时忙等（busy-wait），不触发上下文切换，获取即返回、无调度延迟；适合多核且临界区远短于切换成本的场景。阻塞锁（互斥量）在失败时把线程挂入内核等待队列并让出 CPU，适合长临界区或单核环境。

混合方案「自适应互斥锁」（adaptive mutex）先自旋若干次再阻塞：若锁在极短时间内释放，自旋零切换胜出；若持有者被换出或临界区很长，则及时睡眠避免浪费。现代运行时普遍采用该策略：
- **Go runtime**：`sync.Mutex` 正常模式先自旋（受 `GOMAXPROCS` 与 P 数量约束）后进入 `semacquire` 睡眠；
- **JVM**：偏向锁 / 轻量级锁（CAS 自旋）/ 重量级锁（内核 mutex）三级升级（具体策略随 JDK 版本演进，以官方最新文档为准）；
- **Linux futex**：用户态先 CAS，失败才 `FUTEX_WAIT` 进内核，把「阻塞」成本下沉到真正发生竞争时。

不可睡眠约束同样关键：内核中断上下文中只能使用自旋锁，因为中断上下文没有可调度的任务结构，无法睡眠。

## 三、形式化与数学基础
设临界区时间 $C$、上下文切换总开销 $S$（换出 + 换入 + 调度）、唤醒开销 $S_{wake}$、自旋轮数 $k$、每轮自旋耗时 $c$。自旋等待的期望时间近似为：

$$ T_{spin} \approx \sum_{i=1}^{k} c \cdot \mathbb{1}[\text{未获得}] \;\;,\qquad \text{获得前总耗时} \sim O(kc) $$

阻塞路径至少付出两次切换：

$$ T_{block} = S_{out} + C + S_{wake} $$

判据为：

$$ T_{spin} < T_{block} \iff k \cdot c < S_{out} + S_{wake} $$

即当「预计自旋到锁释放的时间」小于「切换往返成本」时自旋更优。单核且不关闭抢占时，持锁线程随时可能被换出，$k$ 无上界，$T_{spin} \to \infty$：自旋几乎必然劣于阻塞，甚至永久空转。这正是内核在单 CPU 配置下把 `spin_lock` 编译为空操作（仅关抢占）的原因——互斥性改由「关抢占」保证，而非忙等。

## 四、代码实现
最简 TAS 自旋锁，注意需 acquire/release 语义保证临界区内外不发生重排：

```c
/* 极简 TAS 自旋锁（C11 atomic） */
#include <stdatomic.h>

atomic_int lock = 0;

static inline void acquire(void) {
    while (atomic_exchange_explicit(&lock, 1, memory_order_acquire))
        ;                       /* 忙等：交换成功即持有 */
}

static inline void release(void) {
    atomic_store_explicit(&lock, 0, memory_order_release);
}
```

测试并测试（TTAS）在失败后先用普通读探测，可减少缓存一致性流量：

```c
static inline void acquire_ttas(void) {
    for (;;) {
        while (atomic_load_explicit(&lock, memory_order_relaxed))
            ;                   /* 只读探测，不写缓存行 */
        if (!atomic_exchange_explicit(&lock, 1, memory_order_acquire))
            return;
    }
}
```

阻塞锁（`pthread_mutex`）在获取失败时由内核将线程挂入等待队列，唤醒时不占用 CPU；代价是两次系统调用与调度延迟。

## 五、与其他技术对比
| 类型 | 等待方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 自旋锁 | 忙等 | 零切换、延迟极低 | 占 CPU、单核危险 |
| 阻塞锁 | 睡眠 | 不占 CPU、省电 | 切换开销、唤醒延迟 |
| 自适应 | 先旋后睡 | 兼顾短长临界区 | 阈值需调、实现复杂 |
| 读写锁 | 按读写区分 | 读并行 | 写者可能饥饿 |
| 无锁 CAS | 原子重试 | 无阻塞、无死锁 | ABA、重试活锁 |

读写锁在只读为主时更优；无锁结构彻底避免锁但把复杂度转移到内存序与回收；自旋与阻塞的抉择则几乎完全由临界区时长与核数决定。

## 六、常见误区
误区一：认为单核上自旋锁「偶尔可用」。除非关闭抢占且持有者不会被换出，否则自旋方可能永远等不到 CPU，属于必然错误而非概率问题。

误区二：长临界区也选自旋，等于自我 DoS——白烧一整颗核的算力，还抬高功耗与缓存争用。

误区三：手写 `while (flag);` 当自旋锁。普通变量读不具原子性与内存序保证，编译器还可能把循环优化掉；必须用原子读或原子交换。

误区四：忽略内存屏障。原子操作默认带序（或需显式指定 `acquire`/`release`），而裸读裸写会让临界区内的访问越界重排到锁外，产生可见性 bug。

误区五：以为「自旋锁不会阻塞」。自旋锁虽不调度，但在高争用下退化为长时间空转，对实时性有害；内核因此引入排队自旋锁。

## 八、面试题
1. **何时用自旋锁？** 多核、临界区极短、不能容忍调度延迟（中断处理、调度器内部），且持有者不会被换出。
2. **为何单核自旋危险？** 持有者需要 CPU 才能释放锁，若未关抢占则可能被换出，自旋方在唯一核心上空转，永远等不到。
3. **TAS 与 CAS 的区别？** TAS 无条件置位并返回旧值，用于实现锁；CAS 仅在值等于期望时才写入，可在循环中重试，是无锁算法的基础原语。
4. **为什么 TTAS 优于 TAS？** 失败路径只做普通读，不写缓存行，避免了每个等待者反复使其他核失效的缓存一致性风暴。

## 九、演进与趋势
排队自旋锁（MCS、CLH 以及 Linux 的 qspinlock）让等待者排成链表、各自旋于自己的节点，把缓存一致性流量从 $O(P^2)$ 降到 $O(P)$。futex 把阻塞能力下沉到内核，仅在真正竞争时进入系统调用，是用户态锁库的基石。应用层通常无需手写自旋：Rust 与 C++ 的 `std::mutex` 已内置自适应实现，Linux 内核则用 `spin_lock`/`mutex` 严格区分上下文。面向低延迟场景还出现混合锁（自旋 + 内核等待）与 NUMA 感知锁。

## 十、小结
锁类型的选择由两个变量决定：临界区长度与可用核数。短小多核选自旋或自适应，长久单核选阻塞，不可睡眠上下文只能用自旋。无论哪种，内存序与可见性都不能省略——这是自旋锁从「看起来对」到「真的对」之间最容易失守的一环。
