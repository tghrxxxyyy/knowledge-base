# 死锁与优先级反转

> 对应 Tanenbaum《Modern Operating Systems》死锁章节、OSTEP（Remzi 等）死锁与优先级反转案例、Bryant & O'Hallaron《CSAPP》第 12 章、Lamport 1978（面包店算法）、Silberschatz《Operating System Concepts》死锁章节。

## 一、背景与挑战
多线程按不同顺序获取多把锁会形成循环等待（circular wait）：所有线程都在等彼此释放锁，系统永久停滞。死锁的麻烦在于它并非「更慢」，而是**永不推进**，且往往在压力测试或生产环境偶发，本地难以复现。

另一类更隐蔽的问题是优先级反转（priority inversion）：高优先级线程被持有锁的低优先级线程阻塞，而中优先级线程抢占了低优先级线程，间接「插队」到高优先级线程之前，使高优先级任务被无限期推迟。著名的火星探路者（Mars Pathfinder）任务就因未启用优先级继承而发生看门狗复位。二者的共同点是破坏并发的可靠性，但成因与解法完全不同：死锁靠资源获取策略预防，优先级反转靠调度协议消除。

## 二、核心原理
**死锁四个必要条件（Coffman 等）**：
1. 互斥（mutual exclusion）：资源一次只能被一个线程持有；
2. 持有并等待（hold and wait）：持有资源的同时等待新资源；
3. 不可抢占（no preemption）：资源不能被强制剥夺；
4. 循环等待（circular wait）：存在等待环 $T_1 \to T_2 \to \cdots \to T_n \to T_1$。

破坏任意一条即可防止死锁。工程上最可行的是破坏第 4 条（统一加锁顺序），其次是破坏第 2 条（一次性申请全部资源或使用无等待设计）。

**优先级反转**发生在缺少优先级继承协议时，典型的三方链条为：低优先级线程 $L$ 持锁 → 高优先级线程 $H$ 等待该锁 → 中优先级线程 $M$ 抢占 $L$ 并长时间运行，使 $H$ 的等待时间被 $M$ 拉长。解法是：
- **优先级继承（priority inheritance, PI）**：持锁的 $L$ 临时继承等待者中的最高优先级，使 $M$ 无法抢占，锁尽快释放；
- **优先级天花板（priority ceiling）**：锁的优先级设为所有可能使用者的最高值，线程一旦持有即被提权，可静态分析从而预防死锁。

## 三、形式化与数学基础
**资源分配图**。顶点为线程与资源，请求边与分配边构成有向图。环路是死锁的必要条件；在「每类资源仅一个实例」时环路也是充分条件；多实例时环路只是必要，需进一步判定。

**安全状态与银行家算法**。设 $Alloc_i$、$Need_i$、$Work$，若存在线程序列 $\langle P_1,\dots,P_n\rangle$ 使：

$$ \forall i:\; Need_{P_i} \le Work,\qquad Work \leftarrow Work + Alloc_{P_i} $$

则当前状态安全（$Work$ 单调不减）。若找不到这样的序列则可能进入死锁。银行家算法要求预先知道每线程的最大需求，现实中难以获得，故工程上以「预防」为主。

**优先级反转的延迟界**。在无 PI 时，$H$ 的等待时间上界不可控，因为它取决于 $M$ 的执行时长；启用 PI 后，$H$ 的阻塞时间受**优先级天花板协议**限制为至多一次（或按嵌套层数计）临界区时长：

$$ W_H \le \sum_{k=1}^{m} C_k^{cs} $$

其中 $C_k^{cs}$ 为被继承链上各级临界区时长。这是实时系统中可分析性（analyzability）的来源，也是 RTOS 必须内置该协议的原因。

## 四、代码实现
破坏循环等待的最直接手段是强制统一的加锁顺序：

```c
/* 统一按对象 id 升序加锁，破除循环等待 */
void transfer(Account *a, Account *b, int amt) {
    Account *first  = (a->id < b->id) ? a : b;
    Account *second = (a->id < b->id) ? b : a;

    lock(&first->lk);
    lock(&second->lk);
    /* 临界区：原子完成两账户更新，避免中间态被观察 */
    first->bal  -= amt;
    second->bal += amt;
    unlock(&second->lk);
    unlock(&first->lk);
}
```

若无法统一顺序（如对象由外部传入且顺序未知），可用 `trylock` 加回退打破死锁等待：

```c
if (!trylock(&first->lk)) return RETRY;
if (!trylock(&second->lk)) {
    unlock(&first->lk);       /* 回退并让出，避免持有并等待 */
    return RETRY;             /* 调用方加随机退避后重试 */
}
```

优先级继承需显式配置（`PTHREAD_PRIO_INHERIT`），否则内核不会自动提权；实时系统还常用优先级天花板互斥量。

## 五、与其他技术对比
| 现象 | 本质 | 典型解法 | 可分析性 |
| --- | --- | --- | --- |
| 死锁 | 循环等待，永久停滞 | 统一锁序 / trylock 回退 / 银行家 | 静态可判定（部分场景） |
| 活锁 | 反复退让、不前进 | 随机退避 / 打破对称 | 概率性 |
| 饥饿 | 长期得不到资源 | 公平队列 / 老化 | 可给界 |
| 优先级反转 | 高优先级被低优先级者间接拖住 | 优先级继承 / 天花板 | PI 后可给界 |

优先级反转介于死锁（永远不动）与普通调度延迟之间——系统在推进，但关键任务的时延不可控；因此它靠**协议**而非算法消除。

## 六、常见误区
误区一：加超时即可根治死锁。超时只是缓解（退避重试），高竞争下会退化为活锁，且无法保证关键路径；它是兜底而非根治。

误区二：忽视嵌套锁顺序。只要两线程以相反顺序获取同一对资源，就可能死锁——即便每处代码局部看都「只加两把锁」。

误区三：以为优先级继承自动生效。多数系统需显式配置（如 `PTHREAD_PRIO_INHERIT`），否则反转原样重现；继承还只作用于互斥量，信号量与其他同步原语未必支持。

误区四：以为单把锁不会死锁。单锁无法构成循环等待，但同一线程重复获取非递归锁会**自死锁**。

误区五：只关注锁而忽略其他等待关系。条件变量误用、线程 join 环、协程 await 环、甚至异步任务依赖环同样构成循环等待。

## 七、与开源书·权威来源对应
- **Tanenbaum《Modern Operating Systems》**：死锁四条件、资源分配图与银行家算法的标准讲授。
- **Silberschatz《Operating System Concepts》**：死锁预防/避免/检测与恢复的系统化分类。
- **OSTEP（Remzi 等）死锁章节**：以实例演示死锁，并复述 Mars Pathfinder 的优先级反转案例。
- **Lamport 1978（面包店算法）**：无死锁的软件互斥方案，用取号顺序替代显式锁序。
- **Bryant & O'Hallaron《CSAPP》第 12 章**：Pthreads 死锁示例与并发陷阱。

## 八、面试题
1. **死锁的四个必要条件？** 互斥、持有并等待、不可抢占、循环等待；破坏任一即可避免死锁。
2. **如何破坏循环等待？** 所有线程按全局固定顺序（如按地址、id 或锁层次的层级编号）获取多把锁。
3. **优先级继承的原理？** 持有锁的低优先级线程临时继承等待者中的最高优先级，使中优先级线程无法插队，从而让锁尽快释放、反转消失。
4. **死锁 vs 活锁 vs 饥饿？** 死锁是全员停滞；活锁是持续动作但不推进（如互相退让）；饥饿是某线程长期得不到资源但系统整体在推进。
5. **如何在线检测死锁？** 用锁序检查工具（`lockdep`）或动态分析（ThreadSanitizer 的锁序报告）在运行期发现不一致的加锁顺序。

## 九、演进与趋势
内核的 `lockdep` 与用户态 TSan 把「锁序」变成可自动检查的性质；futex 支持优先级继承（`FUTEX_LOCK_PI`），把 PI 下沉到内核，是 RT-Linux 的关键组件。静态锁序分析在编译期预防死锁，对大型代码库尤其有价值。实时系统中优先级天花板协议已成标配，配合可抢占内核满足可预测时延。另一条路线是尽量避免共享：用消息传递、actor 模型或所有权类型系统（Rust）让数据竞争与死锁在编译期被排除。

## 十、小结
死锁与优先级反转都是并发可靠性的核心议题，但对策不同：死锁靠统一锁序、trylock 回退与资源策略**预防**（运行时检测成本高且为时已晚），优先级反转靠优先级继承或天花板协议**消除**。工程实践中「预防 + 工具检测」的组合，远比依赖运行时死锁检测更可靠。
