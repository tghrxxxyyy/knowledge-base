# 锁粒度与锁分解

> 对应 OSTEP（Remzi 等）《Operating Systems: Three Easy Pieces》锁章节、Bryant & O'Hallaron《CSAPP》第 12 章、Herlihy & Shavit《The Art of Multiprocessor Programming》第 1/9 章、Silberschatz《Operating System Concepts》同步章节。

## 一、背景与挑战
粗粒度全局锁把对象的所有操作串行化：高并发下吞吐被单锁限制，临界区再短也没有并行度。当哈希表、链表、计数器数组被多线程高频访问时，锁竞争成为扩展性瓶颈，表现为「加核不加性能」甚至随核数增加而退化。

锁分解（lock splitting / lock striping）通过把一把全局锁拆成多把子锁（按分片、桶或字段），让不同子分片上的操作并行执行，从而提升多核吞吐。但粒度并非越细越好：更细的粒度带来更多锁对象（内存与缓存行开销）、更高的死锁风险（跨分片操作需多锁）、以及跨分片不变式难以维护的问题。

## 二、核心原理
锁分解的本质是**按被保护数据的访问模式切分临界区**，使锁的冲突域与数据的分区对齐。常见形态：

- **分片锁（striping/sharding）**：键 $k$ 映射到分片 $k \bmod N$，每个分片一把锁。不同分片的 `put`/`get` 完全并行；
- **桶锁（bucket lock）**：哈希表每个桶（或桶组）一把锁，是分片锁在哈希结构上的具体化；
- **字段锁（field-level locking）**：为结构的独立字段分别加锁，仅在不变式不跨字段时安全；
- **层次锁（hierarchical locking）**：读写路径自上而下加锁（树结构）、自下而上释放，用锁层次替代全局锁。

粒度选择的核心权衡是：并发度、锁开销、跨分片操作的成本、以及正确性论证难度。粗粒度无并行但简单；细粒度并行高但需为多锁设计全局顺序（死锁预防）与一致读语义。

## 三、形式化与数学基础
把原本串行的部分视为比例 $f$ 的工作量，拆成 $N_{locks}$ 个可并行分片后，理想加速比（Amdahl 形式）：

$$ S(N_{locks}) = \frac{1}{(1-f) + f/N_{locks}} $$

当 $N_{locks} \to \infty$ 时，$S \to 1/(1-f)$，即被阿姆达尔定律的串行部分封顶。实际中还要计入锁操作自身开销：设单次加解锁成本 $c$、每秒到达的操作数 $\lambda$，分片上的有效利用率 $\rho = \lambda c / N_{locks}$，则平均队列等待近似为：

$$ W_q \approx \frac{\rho}{1-\rho} \cdot c $$

可见 $N_{locks}$ 增大使 $\rho$ 下降、等待迅速变小；但当 $N_{locks}$ 超过实际争用的分片数后，边际收益递减，而每次操作仍需两次原子指令与潜在缓存行传输（参见伪共享文档），总收益趋零甚至转负。

## 四、代码实现
分片锁哈希表的简化实现，注意跨分片操作必须固定全局加锁顺序：

```c
/* 分片锁：每个分片一把锁，避免全局锁串行化 */
#include <stdatomic.h>
#define SHARDS 16

typedef struct { atomic_int lk; int slot[64]; } shard_t;
shard_t table[SHARDS];

static void lock_shard(shard_t *s) {
    while (atomic_exchange_explicit(&s->lk, 1, memory_order_acquire))
        ;                                   /* TAS 自旋，仅锁本分片 */
}

void put(int key, int val) {
    shard_t *s = &table[key % SHARDS];
    lock_shard(s);
    s->slot[(key / SHARDS) % 64] = val;
    atomic_store_explicit(&s->lk, 0, memory_order_release);
}

/* 跨分片迁移：按分片下标升序加锁，杜绝循环等待 */
void move(int key, int dst_shard) {
    int a = key % SHARDS, b = dst_shard;
    if (a > b) { int t = a; a = b; b = t; }
    lock_shard(&table[a]);
    lock_shard(&table[b]);                  /* 与 a != b 时保证顺序 */
    /* ... 搬运并维护总量不变式 ... */
    atomic_store(&table[b].lk, 0);
    atomic_store(&table[a].lk, 0);
}
```

分解后若仍有全局不变式（如总元素数），需用原子累加或专门的汇总锁，而不能靠分片锁隐式维护。

## 五、与其他技术对比
| 策略 | 并行度 | 复杂度 | 跨分片一致性 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全局锁 | 低 | 低 | 天然成立 | 低并发、结构简单 |
| 分片锁 | 中高 | 中 | 需全局序/两阶段 | 哈希表、计数器 |
| 字段锁 | 高 | 高 | 不变式可分解 | 字段独立、读多写少 |
| 无锁（CAS） | 高 | 很高 | 靠原子原语 | 高竞争、低延迟 |

分片锁比全局锁并行度高、比无锁更易证正确，代价是跨分片事务需要额外全局顺序或两阶段锁；字段锁能榨取更高并行度，但对数据布局与不变式的要求最苛刻。

## 六、常见误区
误区一：分片数越多越好。受阿姆达尔上限与缓存行争用限制，过多分片增加内存与伪共享，且每次操作仍需原子指令，收益会饱和甚至反降。

误区二：以为分片锁自动保护跨分片事务。跨分片操作需固定全局顺序获取多把锁（或两阶段锁），否则可能死锁或读到中间态。

误区三：把锁放在栈上或函数局部变量中。锁必须是被多线程共享的同一对象，局部锁无法同步任何东西，编译器还允许完全消除它。

误区四：忽略全局不变式。即便分片独立，涉及总量、最大值的操作仍需原子或汇总锁，否则分解会破坏语义。

误区五：以为分解只对「大锁」有意义。即便单锁，若临界区包含可分离的独立操作（如先更新统计再更新索引），拆成语义独立的两把锁也能降低冲突域。

## 八、面试题
1. **锁分解如何提升吞吐？** 减小不同线程临界区的交集，让不同分片真正并行；收益受阿姆达尔定律约束，争用越集中在少数分片、收益越明显。
2. **分片数如何选？** 权衡争用热度、内存与伪共享，通常取 CPU 核数的若干倍并实测：以竞争率（`perf` 中的锁争用计数）与吞吐曲线拐点决定。
3. **跨分片操作怎么办？** 按固定全局顺序（如分片下标升序）获取多把锁，或用两阶段锁；必要时引入全局汇总锁或原子变量维护不变式。
4. **锁分解与锁粗化（coarsening）矛盾吗？** 不矛盾。分解用于降低真实争用；粗化（如合并相邻临界区、用批量锁减少加解锁次数）用于降低锁操作开销，两者针对不同瓶颈，需分别测量后选择。

## 九、演进与趋势
无锁分片（并发哈希表的分段 CAS）、读写分片锁、RCU 读侧无锁进一步降低读路径竞争；硬件事务内存（HTM/TSX）提供细粒度原子但生态受限且已有多起安全退役案例。数据库领域把 latch（保护内存结构，短临界区、可分解）与 lock（保护事务语义，跨行持久）分层，是锁分解思想的成熟工程化。NUMA 架构下还需注意分片与节点亲和性，避免跨节点访问抵消分解收益。

## 十、小结
锁粒度是并发度与复杂度的直接权衡，分片是把原子锁拆成可并行锁的最实用手段。但必须同步处理三件事：跨分片操作的全局锁序、全局不变式的维护、以及缓存行层的布局影响。盲目细化既不安全也不更快，正确做法是测量争用分布后再决定分片。
