# 锁粒度与锁分解

> 对应 remzi-arpacidusse/ostep-code (GitHub) / 《CSAPP》并发章节。

## 一、背景与挑战
粗粒度全局锁把所有操作串行化，高并发下吞吐被单锁限制。锁竞争成为扩展性瓶颈，须通过细化粒度提升并行度。

## 二、核心原理
锁分解(lock splitting)把全局锁拆为多个子锁(如按分片/桶)，不同分片可并行。粒度越细并发越高，但死锁风险与复杂度上升，且细到每元素锁内存开销大。

## 三、形式化与数学基础
理想并行加速受锁覆盖比例限制(Amdahl 类)：
$$ S = \frac{1}{(1-f) + f/N_{locks}} $$
$f$ 为被锁保护串行部分比例，$N_{locks}$ 可并行锁数，增大 $N_{locks}$ 提升上限。

## 四、代码实现
```c
// 分片锁：哈希桶各自加锁，避免全局锁
#include <stdatomic.h>
#define SHARDS 16
atomic_int locks[SHARDS];
int table[SHARDS][1024];
void put(int key, int val) {
    int s = key % SHARDS;
    while (atomic_exchange(&locks[s], 1)) ;   // 仅锁本分片
    table[s][key/SHARDS] = val;
    atomic_store(&locks[s], 0);
}
```

## 五、与其他技术对比
锁分解增加并行但需处理跨分片操作(两阶段锁)。相比无锁，分解更易正确但仍有竞争。

## 六、常见误区
过度细化导致死锁与缓存行争用。误以为分片锁能保护跨分片事务，需额外全局序。

## 七、与开源书/权威来源对应
OSTEP 锁章节讨论锁开销；cmu-db/15445 中哈希表/latch 用分片降低竞争。

## 八、面试题
锁分解如何提升吞吐？分片数如何选？跨分片操作怎么办？

## 九、演进与趋势
无锁分片、读写分片锁、RCU 读侧无锁；硬件事务内存(TM)实验性提供细粒度原子。

## 十、小结
锁粒度在并发度与复杂度间权衡，分片是最实用的分解手段，但需正视跨分片一致性。
