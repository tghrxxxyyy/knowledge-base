# 缓存行与锁的伪共享

> 对应 Bryant & O'Hallaron《CSAPP》第 6 章（存储器层次与缓存一致性）、Herlihy & Shavit《The Art of Multiprocessor Programming》第 1 章、OSTEP 锁章节、Love《Linux Kernel Development》（per-CPU 变量）、Intel SDM Vol.3（缓存与内存排序）。

## 一、背景与挑战
多个锁变量或计数器若挤在同一缓存行（cache line，x86 上典型为 64 字节），即便各线程操作的是逻辑上完全不同的对象，硬件缓存一致性协议仍会把整行在核间反复失效。这就是伪共享（false sharing）：线程并未真正竞争同一把锁，却因共享缓存行而互相拖慢。

它的危害具有欺骗性——性能曲线上表现得像「锁很慢」，但换更高级的锁算法毫无改善，因为根因是**内存布局**而非锁算法。典型症状包括：加核后吞吐不升反降、`perf` 显示大量缓存行回退（HITM）、把锁变量单独隔离后性能突然恢复。

## 二、核心原理
现代多核通过 MESI（Modified / Exclusive / Shared / Invalid）及其扩展（MOESI、MESIF）维护缓存一致。核 $i$ 要写入某个变量时，若该行不处于 Modified/Exclusive 态，必须先取得独占权，即发起 Read For Ownership（RFO）：把整行从其他核的缓存中抢来并置为独占，同时使其他核的副本变为 Invalid。

关键在于：**一致性的粒度是缓存行，不是变量**。两个线程分别写同行内的不同变量时，每次写都会让对方的副本失效，对方下次访问又需重新取整行，形成来回迁移的「乒乓」与 RFO 风暴。伪共享与真共享的区别：
- **真共享**：两个线程访问同一变量/同一锁，存在真实冲突，需要原子操作或互斥；
- **伪共享**：访问的是不同变量，硬件层面却因同处一行而冲突，本可完全并行。

解决手段是让热变量彼此隔离到不同缓存行（padding + 对齐），或让每个核/线程操作自己的本地副本（per-CPU / per-thread 局部化，最后汇总）。

## 三、形式化与数学基础
设 $k$ 个热变量同处一行，各自写频率为 $f_i$。在 MESI 下每次写都需 RFO，其他核的副本失效，行迁移次数上界为：

$$ RFO_{rate} \approx \sum_{i=1}^{k} f_i = k\bar{f} $$

经填充使各变量独占一行后，不同地址落在不同行，写操作不再互相失效：

$$ \lfloor addr_i / L \rfloor \neq \lfloor addr_j / L \rfloor \;(i \neq j) \;\Longrightarrow\; RFO_{rate} \to \bar{f} $$

其中 $L$ 为缓存行大小。行迁移的直接代价是总线/互连往返延迟 $\tau_{coh}$（跨核对同一行的传输通常远大于本地 L1 命中延迟），伪共享下的额外开销近似为：

$$ \Delta T \approx (k-1)\,\bar{f}\,\tau_{coh} \cdot t_{op} $$

可见开销随同一行上的热变量数近似线性增长——这正是「把 8 个计数器放一起」比「分散到 8 行」慢数倍的原因。填充本身有成本：以 $L$ 字节粒度浪费内存，且可能降低缓存利用率；对齐要求变量地址为行大小整数倍（否则变量跨行反而会引发两次失效）。

## 四、代码实现
为每个锁预留独占缓存行，或用显式填充与对齐：

```c
/* 每锁独占缓存行，避免相邻锁伪共享 */
#include <stdatomic.h>
#include <stddef.h>

#define CL 64   /* 典型缓存行；可移植写法见下方说明 */

typedef struct {
    atomic_int lk;
    char pad[CL - sizeof(atomic_int)];   /* 填充到整行 */
} __attribute__((aligned(CL))) padded_lock;

padded_lock locks[8];   /* 数组步长 = 行大小，每元素独占一行 */

void work(int id) {
    while (atomic_exchange_explicit(&locks[id].lk, 1, memory_order_acquire))
        ;                               /* 仅本行失效，不牵连邻锁 */
    /* 临界区 */
    atomic_store_explicit(&locks[id].lk, 0, memory_order_release);
}
```

C++17 提供 `std::hardware_destructive_interference_size` 标准化该行大小，避免硬编码 64；Linux 内核用 `____cacheline_aligned` 与 `____cacheline_internodealigned_in_smp` 宏。另一个更彻底的思路是 per-CPU 计数：每个核只更新自己的变量，汇总时再求和。

```text
per-CPU 计数（伪代码）
  for each cpu c:
      count[c] += 1            # 无跨核写，无行迁移
  total = sum(count[:])        # 仅在读取统计时汇总
```

## 五、与其他技术对比
| 问题 | 根因 | 解法 | 消除方式 |
| --- | --- | --- | --- |
| 真共享（锁竞争） | 逻辑上同一资源 | 减小临界区 / 锁分解 / 无锁 | 降低冲突概率 |
| 伪共享 | 布局同处一行 | padding / 对齐 / per-CPU | 物理隔离，彻底消除 |
| 缓存行乒乓 | 同一变量跨核高频读写 | 本地化 + 批量同步 | 降低跨核通信频率 |
| NUMA 远端访问 | 内存与本核不同节点 | 亲和绑定 / 本地分配 | 减少跨节点流量 |

伪共享是纯布局问题，与锁算法无关；正因如此它才能被「物理隔离」彻底消除，而真共享只能被降低。CAS 无锁计数器同样受伪共享影响——原子操作保证的是操作不可分割，而不是不产生缓存行迁移。

## 六、常见误区
误区一：换更高级的锁算法就能解决。根因在内存布局，算法层无能为力；先做填充验证，再谈算法优化。

误区二：`atomic` 变量天然免疫伪共享。原子性只保证操作不可分割，缓存行照样在核间迁移，甚至因 RFO 更频繁。

误区三：填充 64 字节可在任意平台通用。行大小因架构而异（不同 ARM、Power 实现各有取值），应以 `hardware_destructive_interference_size` 或实测为准。

误区四：只关注锁变量。高频更新的计数器、每线程统计、引用计数、无锁队列的头尾指针（head 与 tail 同处一行）同样会伪共享，需要一并处理。

误区五：填充越大越好。过度填充浪费缓存容量与内存带宽，且若变量跨越两个缓存行会引发两次失效，反而更慢。

## 八、面试题
1. **锁也会伪共享吗？** 会。多个锁变量同处一行时，任一次加锁写都会使其他核的副本失效，表现为无谓的 RFO 风暴与吞吐塌陷。
2. **如何定位伪共享？** 用 `perf c2c`（cache-to-cache）查看哪些缓存行存在跨核 HITM，或做填充前后对比实验；也可通过采集 `L1-dcache-load-misses` 等事件推断。
3. **为什么填充通常是 64 字节？** x86-64 的缓存行典型为 64 字节；可移植做法是使用 `hardware_destructive_interference_size`（C++17）或运行时探测。
4. **伪共享与真共享的处理策略有何本质区别？** 伪共享可通过布局改变物理隔离从而**彻底消除**，真共享只能通过减小临界区、分解锁或改用无锁结构来**降低冲突概率**。

## 九、演进与趋势
C++17 的 `hardware_destructive_interference_size` / `constructive_interference_size` 把填充大小标准化，避免硬编码；`perf c2c` 让伪共享可视化定位普及。内核与高性能库广泛使用 `cacheline_aligned` 宏，无锁队列普遍把 head/tail 分开到独立行。NUMA 与多路系统上，伪共享常与跨节点访问延迟叠加，需要同时考虑数据亲和性与布局。异构计算（CPU-GPU 共享内存）则引入了更复杂的一致性粒度问题，具体行为以各平台官方文档为准。

## 十、小结
锁变量同缓存行会触发无谓的 RFO 迁移，使「无冲突的锁」也表现糟糕；填充隔离与 per-CPU 局部化是最直接的修复，定位依靠 `perf c2c`。牢记根因是内存布局而非锁算法——高频计数器、每线程统计与无锁结构的头尾指针同样需要警惕伪共享。
