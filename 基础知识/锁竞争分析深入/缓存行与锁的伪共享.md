# 缓存行与锁的伪共享

> 对应 《CSAPP》第6章 / remzi-arpacidusse/ostep-code (GitHub)。

## 一、背景与挑战
多个锁变量若挤在同一缓存行，频繁获取/释放不同锁的线程会互相失效该行，产生伪共享，使锁扩展性与性能骤降。

## 二、核心原理
同 SUBDIR 1 所述，MESI 下对某核写锁变量令他核该行失效。即便各线程锁不同逻辑对象，硬件只认缓存行，于是 RFO 风暴出现。

## 三、形式化与数学基础
设 $k$ 个热锁同处一行，写频率 $f$：
$$ \text{RFO}_{rate} \approx k \cdot f $$
填充使各锁独占行：地址满足 $\lfloor addr_i/64\rfloor$ 互异，RFO 降为 $f$。

## 四、代码实现
```c
// 每锁独占缓存行，避免与邻锁伪共享
#include <stdatomic.h>
#define CL 64
typedef struct { atomic_int l; char pad[CL - sizeof(atomic_int)]; } cl_lock;
cl_lock locks[8];   // 每个独立缓存行
void work(int id) {
    while (atomic_exchange(&locks[id].l, 1)) ;
    // 临界区
    atomic_store(&locks[id].l, 0);
}
```

## 五、与其他技术对比
锁伪共享是布局问题，与锁算法无关；CAS 无锁也受伪共享(计数器)影响。解决同靠填充。

## 六、常见误区
认为换更高级锁算法能解——根因是布局。忽略 `atomic` 变量同样按缓存行对齐才有效。

## 七、与开源书/权威来源对应

## 八、面试题

## 九、演进与趋势
`std::hardware_destructive_interference_size`(C++17)标准化；perf c2c 工具可视化伪共享。

## 十、小结
锁变量同缓存行会触发无谓 RFO，填充隔离是最直接修复，定位靠 c2c/perf。
