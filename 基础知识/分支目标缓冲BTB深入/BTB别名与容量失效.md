# BTB别名与容量失效

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第3章（分支预测与 cache 失效分类）；Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第4章。

## 一、背景与挑战

BTB（Branch Target Buffer）是一张以分支指令地址为键、目标地址为值的关联缓存。为降低硬件开销，BTB 几乎都用哈希索引而非全相联，容量也有限。这就带来两类经典失效，与 cache 的失效分类同构：

- 别名失效（alias / conflict miss）：两个不同分支指令被哈希到同一 set，相互驱逐，导致命中率下降，即使总容量远未用满。
- 容量失效（capacity miss）：程序分支工作集超过 BTB 总条目，无论如何替换都放不下，必然换入换出。

二者表现都是 BTB 命中率下降、误预测上升，但根因不同，优化手段也截然相反——前者靠提高相联度或改进哈希，后者只能增大容量。理解区分二者是 BTB 微架构调优的第一步。

还有第三类「强制失效（compulsory miss）」：分支第一次执行时 BTB 必然未命中，这属于冷启动不可避免的代价，只能靠预取或更激进的预测（如静态预测）部分缓解，不应与别名/容量失效混为一谈。

## 二、核心原理

典型 BTB 结构：以 `(pc 的部分位 hash) mod sets` 作为 set 索引，每个 set 内多路（associativity $a$）存放 `tag + target + 预测信息`。查找时先定位 set，再在该 set 内逐路比对 tag，全不匹配则为未命中。

- 别名：不同 PC $p_a, p_b$ 经哈希落入同一 set，且替换策略（如 LRU）把先到的条目驱逐。结果是一个分支的条目「踩掉」了另一个，二者命中率都受损，但 BTB 总占用可能很低。
- 容量失效：活跃分支总数 $|W| > C$（总容量），任何替换策略都无法避免部分条目被反复驱逐，与哈希无关。

诊断上：若增大 BTB 容量命中率明显上升但改成组相联无效，多半是容量失效；若增大相联度/改哈希有效而加容量无效，多半是别名失效。

还有一个隐含因素：**替换策略**会让「同一工作集」在不同策略下表现迥异。LRU 对循环式访问（工作集略大于容量）会产生「抖动」——每次访问都恰好淘汰下一次要用的项，导致命中率接近 0，这是别名与容量的混合表现，也是随机/伪 LRU 替换常被采用的原因。

## 三、形式化与数学基础

设索引位宽 $s$，相联度 $a$，则总容量：

$$ C = 2^s \cdot a $$

对 PC 集合 $W$（工作集），若：

$$ |W| > C \quad \Rightarrow \quad \text{必存在容量失效} $$

别名失效则取决于哈希函数 $h$ 与替换策略：若存在 $p_a \neq p_b$ 使 $h(p_a)=h(p_b)$ 且二者在替换轮转中相互驱逐，则产生冲突别名。理想哈希应使 $h$ 近似均匀，且不同 PC 落入同一 set 的概率约为 $1/2^s$，与 cache 的冲突概率分析完全一致。

对「工作集略大于容量 + LRU」的循环访问，命中率可近似为 0（每次访问都替换掉即将用到的那一项），这一退化被称为「LRU 抖动」，其形式化条件是访问序列的复用距离恒大于容量 $C$。

## 四、代码实现

下面给出「直接映射 BTB」的最小建模，它最易出现别名：

```c
// 简化的直接映射 BTB（易别名）
#define SETS 1024
typedef struct { uint64_t tag; uint64_t target; int valid; } Entry;
Entry btb[SETS];

int idx(uint64_t pc) { return (pc >> 2) & (SETS - 1); }  // 低位移位哈希

Entry* btb_lookup(uint64_t pc) {
    int i = idx(pc);
    if (btb[i].valid && btb[i].tag == pc) return &btb[i];
    return NULL;   // 未命中（可能是真冷启动，也可能是被别名驱逐）
}
```

注意：直接映射下，任何两个低 12 位相同的分支都会争用同一表项，别名是结构性必然。

```c
// 组相联 + 历史混入哈希：降低别名并区分不同上下文
int idx2(uint64_t pc, uint64_t ghr) {
    // 把历史低位移入索引，使同一 PC 在不同上下文下映射到不同 set
    return (int)(((pc >> 2) ^ (ghr & 0x3ff)) & (SETS - 1));
}
// 若同一 set 仍有多个同 PC 条目（不同历史），用 tag 内的历史位区分
```

把历史混入索引是「用上下文维度换别名损失」的典型手法：它让同一分支在不同调用上下文中使用不同表项，正是现代条件/间接预测器降低冲突的核心思路。

## 五、与其他技术对比

| 结构 | 别名程度 | 硬件代价 | 访问延迟 |
| --- | --- | --- | --- |
| 直接映射 | 严重 | 最低 | 最快（单端口） |
| 组相联 | 较轻 | 较高（多端口/比较器） | 略慢 |
| 全相联 | 无别名 | 最高 | 最慢 |
| 分层 BTB（L0+L1） | 热分支几乎无别名 | 中高 | 命中快/未命中慢 |

组相联在别名与代价间折中；软件侧也可通过链接时布局（把热分支分散到不同低地址位）缓解别名，而不改硬件。

## 六、常见误区

误区一：加大 BTB 总能提升性能。错——若工作集不大，额外容量只是面积与功耗浪费；且更大的多端口 BTB 会拖慢取指关键路径，反而可能降频。

误区二：命中率下降就是容量不够。错——很可能是别名（冲突）失效，此时加容量无效，改相联度或哈希才有效。

误区三：BTB 未命中一定误预测。错——未命中时默认顺序取指（not taken），对不跳转的分支反而是「正确」的，只有实际 taken 的分支未命中才损失。

误区四：把强制失效也算作可优化项。错——首次执行必然未命中，属于不可避免的冷启动成本，应与其他失效分开评估。

误区五：LRU 总是最好的替换策略。错——在工作集略大于容量的循环访问下，LRU 会抖动到近乎全失效，此时随机或伪 LRU 反而更稳。

## 七、与开源书·权威来源对应

- Hennessy & Patterson 第3章在讲解 cache 失效（强制/容量/冲突）的同时，把同样的分类框架用于 BTB 与分支目标缓存，指明别名与容量是两类独立失效。
- CSAPP 第4章讨论程序控制流与取指，是理解 BTB 命中/失效现象的软件视角。
- 现代 CPU 微架构手册（如 Intel Optimization Manual）给出 BTB 容量/相联度的实测参数与布局建议。
- Seznec 关于带 tag 与历史索引预测器的研究，展示了「用上下文化解别名」的标准做法。

## 八、面试题

1. 如何区分 BTB 的别名失效与容量失效？要点：别名是不同分支争同一 set（加相联度/改哈希有效）；容量是整体条目不足（加容量有效）。
2. 直接映射 BTB 为什么别名严重？要点：低地址位相同的分支必然落入同一表项，结构性冲突。
3. BTB 未命中一定有害吗？要点：不一定，顺序取指对不跳转分支恰好正确。
4. 为什么把历史混入索引能降低别名？要点：让同一分支在不同上下文中使用不同表项，把「同索引」的概率分散到多个 set。
5. LRU 抖动是什么？要点：工作集略大于容量时，每次访问恰好淘汰下一项要用的条目，命中率退化为接近 0。
6. 强制失效能消除吗？要点：不能完全消除，属冷启动固有成本；只能靠预取、静态预测或提前训练部分缓解。

## 九、演进与趋势

现代采用分层 BTB（小快 L0 + 大慢 L1/L2），用 L0 覆盖热分支、L1/L2 兜容量，兼顾延迟与容量；并引入上下文相关哈希（把全局/局部历史混入索引）减少别名。部分设计按分支类型（条件/间接/返回）分设独立预测器，降低单结构压力。

另一方向是「软硬协同」：链接器与运行时把热分支的地址分布纳入考量（如避免大量热分支落在同一索引段），或通过 PGO（profile-guided optimization）把分支布局调整得对预测器更友好。这类手段不增加硬件成本，却能在特定工作负载上显著降低别名。

## 十、小结

BTB 失效与 cache 失效同构：容量失效是「放不下」、别名失效是「被踩掉」、强制失效是「第一次必然没有」。优化前者靠加容量、后者靠提高相联度或改进哈希，强制失效只能缓解不能消除。先诊断、再对症，是 BTB 微架构调优的基本原则；而替换策略与哈希设计，往往比单纯扩容更能改变实际命中率。
