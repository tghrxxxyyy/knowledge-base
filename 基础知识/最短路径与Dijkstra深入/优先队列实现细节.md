# 优先队列实现细节

> 对应 Cormen 等《CLRS》第 24 章（Dijkstra 中优先队列与 decrease-key）与 Sedgewick《Algorithms》。

## 一、背景与挑战
Dijkstra 的性能与正确性都系于优先队列实现，尤其是「如何处理距离被更新的过期条目」。当通过某条更短路径松弛一个已入队的顶点，标准二叉堆不支持高效的 decrease-key（需知道元素下标）。工程上普遍用「懒删除（lazy deletion）」：直接把新距离作为新条目压入堆，弹出时若发现它是过期副本就跳过。这一取舍决定了实现的简洁度与堆的实际规模。

优先队列的选择还会影响空间与时间：二叉堆实现简单但 decrease-key 难；斐波那契堆理论摊还更优但常数大、实现复杂；索引堆（IndexPQ）显式支持 decrease-key 且适合稠密图。理解这些权衡，才能在具体负载下选对结构。

另一个常被低估的问题是「稳定性与可复现性」：当多个顶点 dist 相同时，弹出顺序取决于堆的内部实现，可能导致不同的最短路树（虽然距离都正确）。在需要确定性输出的场景（测试、可复现实验）中，必须用「(dist, node) 元组排序」或索引堆来固定顺序，而不能依赖堆的偶然行为。

## 二、核心原理
堆中存放 $(dist, node)$ 元组。松弛成功时，不更新旧条目，而是压入 $(new\_dist, node)$ 新副本。弹出时比较弹出的 dist 与当前已知 dist[node]：若 $d > dist[node]$，说明是更早、更大的过期副本，直接丢弃；否则它是当前最优、予以处理。这样每个 $(node, 更优距离)$ 各占一个堆项，过期项无害地停留在堆中直到被弹出跳过。

懒删除的正确性：过期副本永不会被当作「当前最优」处理，因为弹到它时 dist[node] 已是更小值，比较必然跳过。它多占堆空间，但不影响结果正确性，是用空间换实现简单。

decrease-key 的本质需求是「改变已在堆中的元素的键值并恢复堆序」。它需要两个能力：定位元素当前在数组中的位置（反向索引 map）、以及执行上浮（sift-up）或下沉（sift-down）。二叉堆天然只支持「从根方向的下沉」与「从叶方向的上浮」，而 decrease-key 只需上浮（键变小），因此实现并不困难——难点在于「如何知道元素在哪」。

生产代码中还有一种折中做法：用「可索引的堆」（数组 + position 映射），但只在松弛次数相对较少时使用；若松弛爆炸（稠密图），反向索引维护成本可能超过收益。

## 三、形式化与数学基础
懒删除下，每个节点最多入堆「出度」次（每次有更短路径就压一次），总堆操作：
$$O(E \log E) = O(E \log V)$$
若堆支持真正的 decrease-key（如斐波那契堆），每个节点只调整一次，复杂度可降至 $O(V \log V + E)$ 的摊还界。但二叉堆的 decrease-key 需维护反向索引（位置表）定位元素，实现复杂且常数大，故工程多用懒删除。索引堆则维护「节点→堆下标」的反向映射，使 decrease-key 为 $O(\log V)$，是稠密图 Dijkstra 的优选。

各方案复杂度对照的推导要点：二叉堆建堆 $O(V)$ 且每次操作 $O(\log V)$；斐波那契堆的 insert 与 decrease-key 摊还 $O(1)$、extract-min 摊还 $O(\log V)$，因此总界为 $O(V\log V + E)$（这是它成为 Dijkstra 理论最优的原因）；配对堆的摊还界与之相同但实践更简单，路网实测常优于斐波那契堆。

堆中元素总数的上界 $E+1$ 值得强调：它保证懒删除的空间开销是 $O(E)$ 而非指数级，这是它被工程广泛接受的根本原因。

## 四、代码实现
```python
import heapq
# 懒删除：松弛时压入新副本，弹出跳过过期项
def relax(pq, dist, u, v, w):
    if dist[u] + w < dist[v]:
        dist[v] = dist[u] + w
        heapq.heappush(pq, (dist[v], v))   # 旧副本弹出时自然跳过

def dijkstra(graph, src):
    dist = [float("inf")] * len(graph)
    dist[src] = 0
    pq = [(0, src)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist[u]:
            continue                      # 过期副本
        for v, w in graph[u]:
            relax(pq, dist, u, v, w)
```

索引堆的 decrease-key 骨架（含反向索引）：

```python
class IndexPQ:
    def __init__(self, n):
        self.pos = [-1] * n      # 节点 -> 堆数组下标，-1 表示不在堆中
        self.heap = []           # 堆数组，元素为节点编号
        self.key = [float("inf")] * n
    def _swap(self, i, j):
        self.heap[i], self.heap[j] = self.heap[j], self.heap[i]
        self.pos[self.heap[i]] = i
        self.pos[self.heap[j]] = j
    def decrease_key(self, node, new_key):
        assert new_key < self.key[node]
        self.key[node] = new_key
        i = self.pos[node]
        while i > 0 and self.key[self.heap[i]] < self.key[self.heap[(i - 1) // 2]]:
            self._swap(i, (i - 1) // 2)      # 上浮恢复堆序
            i = (i - 1) // 2
```

## 六、常见误区
1. 忘记跳过过期副本。弹出后不比较 $d > dist[u]$ 会用旧距离继续松弛，得到错误结果。
2. 元组第二键不可比较导致崩溃。存入 $(dist, node)$ 时 node 需可比较（整数安全），否则 Python 会比较到 node 引发 TypeError。
3. 以为 decrease-key 总是更快。二叉堆上定位元素代价高，常不如懒删除实在。
4. 以为堆项多就是 bug。懒删除天然产生过期项，只要弹出时跳过即正确。
5. 误以为懒删除会改变算法结果。它只影响效率，dist 数组的最终值与非懒删除版本完全一致。
6. 忽略「入堆前应先比较」的时机。若在松弛前不比较、直接入堆，堆规模会膨胀到 $O(E)$ 都撑不住（每条边都可能无条件入堆）。
7. 在并发环境下忽略堆的线程安全。懒删除的堆在并发松弛下需加锁或改用局部堆合并策略。

## 八、面试题
1. decrease-key 与懒删除如何取舍？
   要点：懒删除实现简单、堆更大；decrease-key 需位置索引、理论更优但常数高。
2. 为什么堆里存 (dist, node) 而非仅 dist？
   要点：需知道弹出的是哪个节点，且第二键保证比较安全。
3. 斐波那契堆在 Dijkstra 上的理论优势？
   要点：decrease-key 摊还 $O(1)$，总界 $O(V\log V+E)$，但常数大、工程少用。
4. 索引堆相比懒删除的优势？
   要点：decrease-key 为 $O(\log V)$、堆规模可控，适配稠密图。
5. 懒删除会影响结果的确定性吗？
   要点：不影响距离正确性；但相同距离时的弹出顺序依赖元组比较，需第二键固定才能确定性输出。
6. 堆中最多有多少元素？
   要点：$O(E)$，每条边最多触发一次成功松弛入堆。

## 九、演进与趋势
索引堆（支持随机访问与 decrease-key）在稠密图更优；配对堆在路网 Dijkstra 表现好；并行 Dijkstra（如 Δ-stepping）把堆操作分桶以并行化；Dial 桶队列在整数权下达 $O(V+E)$，是理论最优实践版。

工程上的另一方向是「批处理松弛」：把同一轮松弛产生的多个更新合并后再统一调整堆，减少堆操作次数；这在 GPU/多核实现中尤其有效，因为可以牺牲部分确定性换取吞吐。

## 十、小结
优先队列的懒删除是 Dijkstra 工程实现的关键：用「压入新副本 + 弹出跳过过期项」替代困难的 decrease-key，实现简单且正确性由比较保证，是 $O(E\log V)$ 标准实现的基石。稠密图可升级到索引堆获得更稳的 decrease-key。理解「堆大小是 $O(E)$」「第二键提供确定性」这两点，是用好优先队列的前提。
