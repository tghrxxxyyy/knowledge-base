# 近实时搜索与段合并

> 对应 Chang et al. 2006（SSTable/compaction 思想映射），以及 Vonng/ddia 第 3 章（不可变段与合并）。

## 一、背景与挑战
全文索引需“写入后很快可读”（近实时），又要控制文件数与碎片。借鉴 LSM/SSTable 思路：索引由多个不可变段（segment）组成，后台合并段以控制数量并清理删除。

## 二、核心原理
新文档写入内存缓冲，定期刷为一个不可变段（含自有倒排与词典）。查询并发查所有段再合并结果。后台 merger 将若干小段归并为大段并根据删除列表（.del）剔除已删文档，维持段数可控、查询更快。

## 三、形式化与数学基础
查询需合并 $k$ 个段，复杂度：
$$ Cost = \sum_{i=1}^{k} lookup(seg_i) $$
段数控制目标：
$$ k \le K_{max} \implies \text{归并触发} $$
合并后删除回收：
$$ Size_{after} = Size_{before} - \sum deleted\_postings $$

## 四、代码实现
```python
# 多段查询合并（仅示意）
def search_segments(segs, term):
    hits = []
    for s in segs:                      # 并发查各段
        hits.extend(s.postings(term))
    return merge_and_score(hits)        # 合并并打分
```

## 五、与其他技术对比
单大索引写入需重建、不可近实时；多段不可变 + 合并兼具近实时与高效。与 LSM compaction 异曲同工（SSTable 思想）。

## 六、常见误区
1) 认为段越多越好——查询需合并过多段变慢。
2) 忽略 .del 延迟清理导致膨胀。
3) 误以为刷新即立即可查——需 reopen reader。
