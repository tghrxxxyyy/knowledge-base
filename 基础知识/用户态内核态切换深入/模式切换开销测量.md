# 模式切换开销测量

> 对应 Bryant & O'Hallaron《CSAPP》第 8 章与 Kerrisk《The Linux Programming Interface》第 3 章。

## 一、背景与挑战
每次系统调用都付模式切换固定成本。高 IOPS/网络服务中，频繁小调用（如 gettimeofday）的陷入开销可能超过实际工作。精确测量有助于判断能否批处理或用 vDSO。

## 二、核心原理
用 `clock_gettime(CLOCK_MONOTONIC)`（本身走 vDSO 几乎零陷入）为计时节拍，循环 N 次空 `getpid()`（必陷入）求均值；或与 `rdtsc` 周期计数交叉验证。开销源于寄存器保存、页表/TLB 部分刷新与返回路径。

## 三、形式化与数学基础
单次成本估计：
$$\hat c = \frac{1}{N}\sum_{i=1}^{N}(t_{i+1}-t_i) - t_{loop\_overhead}$$
现代 x86 `syscall` 约 50-200 ns 级，受 KPTI、Spectre 缓解影响波动。相对纯函数调用（~1 ns）高 1-2 个数量级。

## 四、代码实现
```c
struct timespec a, b;
long sum = 0;
for (int i = 0; i < 1000000; i++) {
    clock_gettime(CLOCK_MONOTONIC, &a);
    getpid();                       // 必陷入内核
    clock_gettime(CLOCK_MONOTONIC, &b);
    sum += (b.tv_nsec - a.tv_nsec);
}
printf("avg ns/ syscall ~ %ld\n", sum / 1000000);
```

## 五、与其他技术对比
vDSO 调用（gettimeofday）无陷入近零成本；io_uring 提交批处理把多次调用合并减陷入；相较用户态函数调用开销显著。

## 六、常见误区
误以为所有 syscall 同速：IO 阻塞类远大于纯模式切换。误以为测量不受缓解影响：KPTI/Spectre 增开销。误以为循环测量无噪声：需绑核与预热。

## 七、与开源书/权威来源对应
CSAPP 8.1 系统调用成本；Kerrisk 第 3 章 timing 注意事项。

## 八、面试题
问：为什么批量 syscall（io_uring）更快？答：减少陷入次数与模式切换固定成本。问：vDSO 为何快？

## 九、演进与趋势
`syscall` 用户态批量（io_uring）、`pidfd` 减少 stat；硬件缓解（IBPB/IBRS）持续优化开销。

## 十、小结
模式切换有固定几十纳秒成本，测量与批处理/vDSO 是降其影响的工程手段。
