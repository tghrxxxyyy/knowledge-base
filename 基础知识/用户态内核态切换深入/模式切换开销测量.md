# 模式切换开销测量

> 对应 Bryant & O'Hallaron《CSAPP》第 8 章 Exceptional Control Flow 与 Kerrisk《The Linux Programming Interface》第 3 章；并参考 Drepper《What Every Programmer Should Know About Memory》关于 `rdtsc` 的章节与内核文档 `Documentation/admin-guide/pm/`。

## 一、背景与挑战

每次系统调用都付出模式切换的固定成本：保存/恢复寄存器、切换栈、可能的页表/TLB 部分失效与返回路径。

在高 IOPS、高频计时（如 `gettimeofday`）或 RPC 密集型服务中，频繁小调用（尤其是本可批处理的工作）的陷入开销可能超过实际业务工作。

精确测量有助于判断「能否用 vDSO、能否批处理、或能否合并到 io_uring」，从而决定优化方向，而非凭直觉优化。

若测量方法本身引入偏差，会得出完全相反的结论，例如把 vDSO 路径误当成陷入路径，或把循环开销算进 syscall。

## 二、核心原理

测量要用「自身几乎零陷入」的时钟做节拍，否则计时会把测量工具的开销混进来。

`clock_gettime(CLOCK_MONOTONIC)` 在 vDSO 路径下走用户态 `rdtsc`，不陷入，适合做基准。

方法是循环 N 次：在两次 `clock_gettime` 之间插入一个「必陷入」的调用（如 `getpid()`，它需读 `task_struct`），用差值均值估算单次陷入成本。

或用 `rdtsc`/`rdtscp` 直接数周期，并与 `clock_gettime` 结果交叉验证。

开销来源主要是寄存器保存/恢复、`CR3`/`TLB` 影响（KPTI 下需切页表）、以及返回路径的 `SWAPGS`/IBRS 等缓解指令。

为减少噪声，应绑核（`sched_setaffinity`）、关闭 CPU 频率调节、预热后测量，且取多次运行的中位数而非单次。

## 三、形式化与数学基础

单次陷入成本估计（扣除测量循环自身开销）：

$$\hat c = \frac{1}{N}\sum_{i=1}^{N}(t_{i+1}-t_i) - t_{loop}$$

现代 x86 `syscall` 纯模式切换约 50–200 ns 量级，且随 KPTI、Spectre 缓解（IBRS/IBPB、RETPOLINE）显著波动。

相对纯函数调用（约 1 ns 级）高 1–2 个数量级。

以周期计：

$$c_{cycles} \approx \frac{N_{mem\_op}\cdot lat_{mem} + N_{insn}}{f_{cpu}}$$

其中 $N_{mem\_op}$ 为模式切换路径中的访存次数，其延迟受 TLB 状态支配。

若测量在 KPTI 开启下进行，还需计入 `CR3` 写与用户/内核页表切换的 TLB 失效。

## 四、代码实现

```c
// 估算单次必陷系统调用开销（getpid 必陷入内核读 task_struct）
#include <time.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    struct timespec a, b;
    long sum = 0;
    const int N = 1000000;
    for (int i = 0; i < N; i++) {
        clock_gettime(CLOCK_MONOTONIC, &a);   // vDSO，几乎零陷入
        getpid();                              // 必陷入内核
        clock_gettime(CLOCK_MONOTONIC, &b);
        sum += (b.tv_sec - a.tv_sec) * 1000000000L
             + (b.tv_nsec - a.tv_nsec);
    }
    printf("avg ns/syscall ~ %ld\n", sum / N);
    return 0;
}
```

更精确可用 `rdtscp` 替代 `clock_gettime` 直接数周期，并用 `CPU_ZERO`/`sched_setaffinity` 绑核消除迁移噪声。

`RDTSC` 不带序列化可能偏小，而 `RDTSCP` 带伪序列化更接近真实；注意 `clock_gettime` 本身虽不陷入，仍执行若干指令构成 $t_{loop}$。

## 五、与其他技术对比

| 路径 | 是否陷入 | 典型成本 |
| --- | --- | --- |
| 用户态函数调用 | 否 | ~1 ns |
| vDSO 调用（gettimeofday） | 否 | ~10 ns |
| 普通 syscall（getpid） | 是 | 50–200 ns |
| io_uring 批量提交 | 分摊到多次 | 远低于逐次 |

vDSO 把只读调用移回用户态几乎零成本；io_uring 提交批处理把多次调用合并，减少陷入次数与模式切换固定成本。

## 六、常见误区

1. 误以为所有 syscall 速度相同：阻塞类 I/O（等网络/磁盘）远大于纯模式切换成本。
2. 误以为测量不受缓解影响：KPTI/Spectre 缓解会让同一机器上成本随内核版本波动。
3. 误以为循环测量无噪声：需绑核、预热、避开 CPU 频率跳变（用 `taskset` 与 `cpupower frequency-set`）。
4. 误以为成本只来自指令：TLB/缓存冷启动与 `CR3` 切换占比可观。
5. 误以为 `RDTSC` 与墙上时钟一一对应：TSC 频率与 `CLOCK_MONOTONIC` 倍率需经内核校准，否则换算偏差。

## 八、面试题

1. 为什么批量 syscall（io_uring）更快？要点：减少陷入次数与每次模式切换的固定成本，把提交/完成队列化。
2. 为什么用 `clock_gettime` 而非 `gettimeofday` 做计时？要点：前者是 vDSO 单调时钟，精度高且不回拨，测量开销更低。
3. 什么因素会让测得的开销偏大或偏小？要点：绑核、频率、缓解开关、循环开销扣除、TSC 序列化。
4. 如何用 `perf` 交叉验证？要点：`perf stat -e syscalls:sys_enter -e cycles` 看次数与周期，与基准对照。

## 九、演进与趋势

- `syscall` 用户态批量（io_uring）、`pidfd` 减少 stat 类陷入。
- 硬件缓解（IBPB/IBRS、eIBRS）持续优化开销；AMD 的 `SNP`/Intel 的 `TME` 也影响陷路。
- 用户态轮询（busy-poll）与 `io_uring` 的 `IORING_SETUP_SQPOLL` 进一步把陷入降到最低。

## 十、小结

模式切换存在固定的几十纳秒级成本，测量须用零陷入时钟做基准并扣除循环开销。

批处理、vDSO 与 io_uring 是降低其影响的工程手段，而 KPTI/Spectre 缓解是成本随版本波动的主要来源。

任何优化决策都应以可复现的测量为据，而非经验假设。
