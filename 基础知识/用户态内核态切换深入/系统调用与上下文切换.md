# 系统调用与上下文切换

> 对应 Bryant & O'Hallaron《CSAPP》第 8 章 System-Level I/O 与 Kerrisk《The Linux Programming Interface》第 3 章 System Calls；并参考 Love《Linux Kernel Development》第 4 章 Process Scheduling 与 Stevens《UNIX Network Programming》卷 1 关于阻塞语义的论述。

## 一、背景与挑战

用户程序运行在 Ring 3 无特权，要读文件、建进程、收发网络包等特权操作，都必须经系统调用陷入内核（Ring 0）。

这里有两层容易被混淆的开销：模式切换（register/stack 在用户态与内核态间切换）与进程上下文切换（调度器换出当前进程，刷新页表与寄存器，切到另一进程）。

理解二者区别，是分析性能、理解阻塞语义与并发模型的关键，也是回答「为什么频繁 syscall 慢」「为什么异步 I/O 更优」的基础。

混淆二者常导致错误的优化方向——例如把可批处理的陷入误当成必须消除的调度。

## 二、核心原理

用户态执行 `syscall` 指令（x86-64）切换特权级到内核，硬件保存用户现场并跳到 `entry_SYSCALL_64`；内核把用户寄存器存入内核栈 `pt_regs`，据 `rax` 中的系统调用号查 `sys_call_table` 分派到处理函数（如 `sys_read`、`sys_write`）。

处理若不需等待则直接完成，经 `sysret` 返回用户态——这仅是模式切换。

若内核在等待 I/O、锁或显式 `schedule()` 时阻塞，调度器会切换到其他进程，发生进程上下文切换，额外刷新页表（`CR3`）、冷缓存，代价大得多。

返回用户态后若 `TIF_NEED_RESCHED` 置位，还会在返回路径上先调用调度器。

注意：vCPU 在虚拟机中还可能从「系统调用 → 客户内核」继续陷入到「宿主机」，叠加 VM-exit 成本。

## 三、形式化与数学基础

模式切换成本 $C_{mode}$ 约等于几十到数百 ns（保存/恢复寄存器 + TLB 部分失效）。进程切换额外成本 $C_{ctx}$ 远大于 $C_{mode}$（刷新页表、缓存冷、可能写回脏状态）。

总开销：

$$T_{sys} = C_{mode} + (blocked\ ?\ C_{ctx} + wait : 0)$$

其中 $C_{ctx}$ 在现代 CPU 上常为数微秒到数十微秒，且受工作集大小与缓存热度强烈影响。

唤醒另一进程还需 $C_{wake}$。

若系统调用触发缺页（`brk`/`mmap` 后），还会叠加 page fault 路径成本。

## 四、代码实现

```c
// 直接发起系统调用，观察陷入；等价于 glibc 的 open/read/write 底层
#include <unistd.h>
#include <sys/syscall.h>

long ret = syscall(SYS_write, 1, "hi\n", 3);
// 或内联汇编精确控制寄存器（x86-64 调用约定）
asm volatile(
    "syscall"
    : "=a"(ret)
    : "a"(1), "D"(1), "S"(buf), "d"(3)
    : "rcx", "r11", "memory");
// 若 write 阻塞（如管道满），内核调用 schedule() 触发进程上下文切换
```

glibc 的 `write` 在内部已经封装了上述 `syscall` 指令与 errno 处理，应用层通常无需手写；`strace` 可观测每次陷入与返回码，区分「陷入次数」与「上下文切换次数」。

## 五、与其他技术对比

| 维度 | 函数调用 | 系统调用 | 进程上下文切换 |
| --- | --- | --- | --- |
| 特权级 | 同（Ring 3） | 跨（3→0） | 跨且换进程 |
| 地址空间 | 同 | 同进程内核 | 换页表 |
| 检查/审计 | 无 | 有 | 有 |
| 典型成本 | ~1 ns | 50–200 ns | 数 µs |

系统调用是受控同步陷入；vDSO 把部分调用移回用户态省陷入；进程上下文切换是调度器行为，与「是否系统调用」无必然联系，但阻塞型系统调用会触发它。

相较 `vfork`/`clone`，`fork` 的写时复制页表本身也构成一次昂贵的上下文建立。

## 六、常见误区

1. 误以为系统调用必切换进程：仅模式切换，只有内核阻塞才切换进程。
2. 误以为系统调用号跨内核版本稳定：会随架构/版本变化，应用必须走 libc 而非硬编码号。
3. 误以为用户可直接执行特权指令：会触发 #GP 异常并被内核杀进程。
4. 误以为 `syscall` 后立即可见：返回前内核可能先处理信号与重调度（`resched`）。
5. 误以为上下文切换只在 syscall 时发生：定时器中断、抢占点同样会触发。
6. 误以为零拷贝就零陷入：零拷贝减少数据搬运，但 `ioctl`/`splice` 仍需陷入与权限检查。

## 七、与开源书·权威来源对应

- CSAPP 8.1 把系统调用归入异常控制流，并对比函数调用与 syscall 的成本。

## 八、面试题

1. 系统调用和函数调用的区别？要点：跨特权级、进内核、有参数/权限检查与安全审计、伴随模式切换。
2. 何时发生进程上下文切换？要点：内核阻塞（等 I/O/锁）或 `need_resched` 置位时由调度器切换。
3. 为什么频繁 syscall 比频繁函数调用慢？要点：模式切换固定成本 + 可能的 TLB 失效与缓解指令。
4. `vmstat`/`cs` 列与 syscall 计数的关系？要点：cs 是上下文切换（含自愿/非自愿），与陷入次数不是同一指标。
5. 为什么 `io_uring` 能减少上下文切换？要点：提交/完成走共享环，多数路径免去陷入与阻塞等待。

## 九、演进与趋势

- `syscall` 指令取代旧 `int 0x80`/`sysenter`；vDSO/vsyscall 加速 `gettimeofday`。
- io_uring 用共享环形队列把「提交+完成」移出 syscall 快路径，batch 减少陷入。
- 用户态调度（如 `sched_ext`、用户态线程库）把部分上下文切换从内核下沉到用户态进一步降开销；eBPF 可在不陷入前提下观察系统调用。

## 十、小结

系统调用是用户态请求内核服务的唯一受控通道；模式切换是隔离与性能的权衡点，而进程上下文切换是内核调度的结果，二者不可混为一谈。

优化时应先区分「陷入成本」与「阻塞等待成本」，再决定用批处理、vDSO 还是异步 I/O。
