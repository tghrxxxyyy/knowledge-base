# 系统调用与上下文切换

> 对应 Bryant & O'Hallaron《CSAPP》第 8 章系统级 I/O 与 Kerrisk《The Linux Programming Interface》第 3 章。

## 一、背景与挑战
用户程序运行在 Ring 3 无特权，需读文件、建进程等特权操作必须经系统调用陷入内核（Ring 0）。这涉及模式切换（register/stack 切换）与可能的进程上下文切换，是性能与隔离的核心。

## 二、核心原理
用户态执行 `syscall` 指令（x86-64）切换特权级到内核，保存用户寄存器到内核栈，据 syscall 号查 `sys_call_table` 分派处理函数，完成后 `sysret` 返回。若内核阻塞（如等 I/O），则调度器切换至其他进程（进程上下文切换，额外换页表/寄存器）。

## 三、形式化与数学基础
模式切换成本 $C_{mode} \approx$ 几十到数百 ns（保存/恢复寄存器 + TLB 部分失效）。进程切换额外 $C_{ctx} \gg C_{mode}$（刷新页表、缓存冷）。总开销：
$$T_{sys} = C_{mode} + (blocked? C_{ctx} + wait : 0)$$

## 四、代码实现
```c
// 直接 syscall 而非库函数，观察陷入
long ret = syscall(SYS_write, 1, "hi\n", 3);
// 或内联汇编
asm volatile("syscall" : : "rax"(1), "rdi"(1), "rsi"(buf), "rdx"(3));
```

## 五、与其他技术对比
系统调用 vs 函数调用：前者跨特权级、经内核、有检查；后者同地址空间直接跳。相较中断，syscall 是受控同步陷入。vDSO 把部分调用移回用户态省陷入。

## 六、常见误区
误以为系统调用必切换进程：仅模式切换，阻塞才切换进程。误以为 syscall 号跨版本稳定：可能变，应走 libc。误以为用户可直接执行特权指令：会 #GP 异常。

## 七、与开源书/权威来源对应
CSAPP 8.1 系统调用与异常；Kerrisk 第 3 章系统调用约定；OSTEP 陷入机制。

## 八、面试题
问：系统调用和函数调用区别？答：跨特权级、进内核、有安全审计与模式切换。问：何时发生进程切换？

## 九、演进与趋势
`syscall` 指令取代旧 `int 0x80`；vDSO/ vsyscall 加速 gettimeofday；io_uring 批量减少陷入。

## 十、小结
系统调用是用户态请求内核服务的唯一受控通道，模式切换是隔离与性能的权衡点。
