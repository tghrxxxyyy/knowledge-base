# 用户态与内核态栈

> 对应 Bovet & Cesati《Understanding the Linux Kernel》第 3 章 Processes 与 Bryant & O'Hallaron《CSAPP》第 8 章 Exceptional Control Flow；并参考 Love《Linux Kernel Development》第 3 章 Process Management 与内核文档 `Documentation/x86/kernel-stacks.rst`。

## 一、背景与挑战

用户态与内核态各有独立栈。内核栈固定且很小（x86-64 通常 16 KiB，由 `THREAD_SIZE` 决定，早期为 8 KiB），每个线程（task）独占一份。

它不能借用用户栈，因为用户内存不可信：可能被恶意改写、可能被换出（swap），也可能在陷入时正处于不一致状态。

陷入内核时必须正确切到内核栈并完整保存用户现场，返回时再恢复并切回用户栈；任何切换差错都会导致内核读到污染数据或返回后用户态崩溃。

栈隔离同时是特权级安全与内核稳定性的根基，也是实现信号、ptrace、seccomp 等机制的前提。

## 二、核心原理

每个 `task_struct` 通过 `task->stack` 指向其内核栈底（栈向下增长）。进入内核（syscall/中断/异常）由硬件与 `swapgs` 配合切换：硬件从 TSS 取出内核栈指针，内核桩把用户 `rsp` 暂存到 `pt_regs` 并把 `rsp` 指向内核栈顶。

随后 `SAVE_ALL` 把通用寄存器压入内核栈，形成 `struct pt_regs`；其顶部是硬件压入的返回上下文（ss/rsp/rflags/cs/rip），其下是通用寄存器区。

返回路径（`restore_regs_and_return_to_usermode`）从 `pt_regs` 恢复用户寄存器，再用 `sysret`/`iret` 切回用户栈。用户栈大且可增长（受 `RLIMIT_STACK` 约束），但内核绝不依赖它执行特权代码。

早期 `thread_info` 直接嵌在栈底；x86-64 已将其移入 `task_struct`，仅保留 `stack` 指针用于回溯。

## 三、形式化与数学基础

栈切换可写为：

$$on\_enter:\ ksp = task.thread.sp;\ save(user\_regs)\rightarrow kstack$$

$$on\_exit:\ restore(user\_regs);\ usp = pt\_regs.sp$$

内核栈容量 $S_k$（如 16 KiB）须容纳当前调用深度、被中断的上下文以及中断嵌套层数，超出即栈溢出触发 `stack-overflow` 检测或 #DF，期望满足 $depth_{max}\cdot frame_{avg} < S_k - guard$。

在 `CONFIG_VMAP_STACK` 下，内核栈用 vmalloc 区域映射，紧邻一个不可访问的 guard page，溢出会立即页故障而非静默破坏相邻内存。

## 四、代码实现

```asm
# x86-64 进入内核：把用户栈指针保存到内核 pt_regs，切到内核栈
swapgs
mov    %rsp, %gs:pcpu_old_rsp     # 暂存用户 rsp 到 per-CPU
mov    %gs:pcpu_kernel_rsp, %rsp  # 切到内核栈顶
sub    $PT_REGS_SIZE, %rsp        # 预留 pt_regs
SAVE_ALL                          # 此后 C 函数全程使用内核栈
# ... 调用 do_syscall_64 等
# 返回时：
RESTORE_ALL
mov    %gs:pcpu_old_rsp, %rsp     # 切回用户 rsp
swapgs
sysretq
```

C 侧可用 `task_stack_page(current)` 取栈底，`object_is_on_stack()` 判断地址是否落在当前内核栈范围，调试器据此回溯 `pt_regs`；`in_task_stack()` 则用于区分进程栈与中断栈。

## 五、与其他技术对比

| 维度 | 用户栈 | 内核栈 | 中断栈（独立） |
| --- | --- | --- | --- |
| 大小 | 大、可增长 | 固定 8/16 KiB | 固定、每 CPU |
| 是否可信 | 否 | 是 | 是 |
| 增长方式 | mmap 扩展 | 不支持 | 不支持 |
| 越界后果 | SIGSEGV | panic/页故障 | panic |

相较协程栈，内核栈由调度器与陷入路径严格管理；部分架构（x86）对设备中断使用独立中断栈（或 IST 栈），防止深度嵌套耗尽进程内核栈。ARM64 则依赖 `vmap` 栈与 `stackprotector` 实现类似保护。

## 六、常见误区

1. 误以为内核能用用户栈：用户内存不可信且可能已被换出，特权代码绝不能依赖它。
2. 误以为内核栈可无限大：固定且小，深递归或超大栈帧（`char buf[8192]`）极易溢出。
3. 误以为栈切换只在进程切换时发生：每次陷入（含中断）都会切到内核栈。
4. 误以为 `thread_info` 总在栈底：x86-64 已把 `thread_info` 移入 `task_struct`，仅保留 `stack` 指针回溯。
5. 误以为内核栈溢出只是数据错误：实际会踩到 guard page 触发明确页故障，便于诊断而非静默 corruption。
6. 误以为用户栈增长无需代价：超出 `RLIMIT_STACK` 或撞到 mmap 区会触发 SIGSEGV。

## 八、面试题

1. 为什么内核不能共用用户栈？要点：用户内存不可信、可能被恶意修改或换出，特权代码须有隔离的执行栈。
2. 内核栈多大、为什么不能增长？要点：固定 8/16 KiB，由 `THREAD_SIZE` 决定，硬件在陷入时直接切换，不支持动态扩展。
3. 中断嵌套如何不耗尽内核栈？要点：独立中断栈/IST 栈承载嵌套，进程内核栈只承载一次陷入上下文。
4. guard page 如何防溢出？要点：`CONFIG_VMAP_STACK` 在栈底映射不可访问页，越界即页故障而非破坏邻居。

## 九、演进与趋势

- 独立中断栈与 per-CPU 栈减少深度嵌套风险；virtio 等驱动使用专属栈。
- `CONFIG_VMAP_STACK` 用 vmalloc 映射内核栈并附加 guard page，溢出即页故障而非静默 corruption。
- KASAN/KMSAN 可检测内核栈越界与未初始化读取；`CONFIG_SCHED_STACK_END_CHECK` 在栈末端放哨兵检测溢出。

## 十、小结

用户/内核双栈隔离保证特权代码不依赖不可信用户内存，是特权级安全与系统稳定性的根基。

陷入时正确的栈切换与 `pt_regs` 保存让切换对用户态透明，而 guard page 与工具链把栈溢出从隐蔽 bug 变成可诊断故障。

设计内核代码时应始终警惕固定尺寸内核栈的预算约束，避免在陷入路径分配大栈帧。
