# 健康检查

> 对应负载均衡健康检查实践；RFC 5789（PATCH 探测）思路。

## 一、背景与挑战
后端实例会宕机、僵死或过载。LB 必须及时把异常节点摘出、恢复后加回，否则把流量导到坏节点或浪费容量。

## 二、核心原理
健康检查分主动与被动。主动：LB 周期性 TCP 连接、HTTP GET /healthz、ICMP ping。被动：观察转发失败率/延迟。判定通常“连续 N 次失败标记 down、连续 M 次成功标记 up”，避免抖动误判。

## 三、形式化 / 数学基础
状态机：$UP \xrightarrow{N\ 连失} DOWN \xrightarrow{M\ 连成} UP$。
探测间隔 $I$、超时 $T$（$T < I$），窗口内失败计数 $f$；标记 down 当 $f \ge N$。
熔断（circuit breaker）：错误率超阈值 $e_{max}$ 触发 OPEN，冷却后半开探测。

## 四、代码实现
```go
func check(addr string) bool {
    conn, err := net.DialTimeout("tcp", addr, 2*time.Second)
    if err != nil { return false }
    defer conn.Close()
    return true   // L4 探活
}
// HTTP 探活：GET /healthz 期望 200
```

## 五、与其他技术对比
主动探测独立、及时但消耗资源；被动探测零额外流量但滞后。对比服务注册中心心跳（见会话保持外的服务发现）。

## 六、常见误区
误区一：ping 通即健康。错，进程可能僵死但网络通。误区二：一次失败就摘。错，应连续失败避免抖动。误区三：健康检查越频繁越好。错，过频压垮后端与 LB。
