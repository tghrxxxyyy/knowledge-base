# 健康检查

> 对应 RFC 1122（Internet 主机需求，可达性与故障语义）、RFC 9110（HTTP 语义，200/503/`Retry-After`）、Google《Site Reliability Engineering》，以及 Envoy/HAProxy 官方文档中的 outlier detection 与 panic threshold。

## 一、背景与挑战

后端实例会以多种方式失效：进程崩溃（连接被拒）、僵死（socket 存在但不处理请求）、过载（响应极慢但成功）、依赖不可用（自身健康却无法服务）。负载均衡器必须及时摘除异常节点、恢复后加回，否则要么把流量导向坏节点，要么长期浪费容量。难点在于准确性与时效性互相冲突：判定太激进会被网络抖动误导并引发连锁过载，太保守则让用户持续遇到错误；探测太频繁会把探针本身变成负载，恢复太快又会把刚重启的实例再次打挂。

## 二、核心原理

**主动探测（active）**：LB 或控制面按固定间隔发探针，形式包括 TCP 建连、TLS 握手、HTTP GET 专用路径、自定义命令。确定性强、可校验语义健康，但增加流量，且探针路径与真实业务路径不同时会出现「探针通过而业务失败」。**被动探测（passive / outlier detection）**：不额外发流量，观察真实请求的失败率、超时率、5xx 比例。零额外开销且覆盖真实路径，但只有有流量时才有效，冷实例失效无法察觉。

工程上两者结合：主动探测负责存活与恢复确认，被动观测负责快速剔除「探针健康但真实请求失败」的节点。判定逻辑是带**滞回（hysteresis）**的状态机：连续 $N$ 次失败标记 `DOWN` 并摘除；连续 $M$ 次成功标记 `UP` 并放回，通常先给少量流量（慢启动）；摘除后保留低频探测以便感知恢复；短时间内反复上下线时启用**抖动抑制（flap damping）**，延长冷却期避免振荡消耗整个集群容量。

## 三、形式化与数学基础

状态机可写作 $UP \xrightarrow{N\ \text{连失}} DOWN \xrightarrow{M\ \text{连成}} UP$。最坏检测延迟（从真实故障到被摘除）为

$$D_{detect} = N\cdot I + T,\qquad T < I\ \text{（超时必须小于间隔，避免探测堆积）}$$

**误摘概率**：若单次探测因抖动失败的概率为 $p$，连续 $N$ 次都失败的概率为 $p^N$。取 $N=3$、$p=1\%$ 时约 $10^{-6}$，说明连续失败阈值是廉价而有效的降噪手段。

**探测开销**：实例数为 $n$、间隔为 $I$ 时，探针速率为 $R = n/I$ 次/秒，且 LB 需为每个实例维护状态机与定时器，因此间隔不能一味缩小。在摘除窗口 $D_{detect}$ 内坏节点仍会失败或被重试，故降低 $D_{detect}$（减小 $I$ 或 $N$）直接减少错误量，但代价是误摘风险与探测开销上升。

## 四、代码实现

```go
// 主动探测：第 1 层做 TCP 可达性，第 2 层做应用层语义检查
func probe(addr string, timeout time.Duration) error {
    ctx, cancel := context.WithTimeout(context.Background(), timeout)
    defer cancel()

    var d net.Dialer
    conn, err := d.DialContext(ctx, "tcp", addr)   // 层 1：能否建连
    if err != nil {
        return err                                 // 不可达
    }
    conn.Close()

    // 层 2：GET /healthz 期望 200，非 2xx/3xx 视为不健康
    // 探针必须无副作用，且不得依赖缓存或慢速外部依赖
    return httpCheck(ctx, "http://"+addr+"/healthz")
}
```

带滞回的状态机则用「连续失败 $N$ 次下线、连续成功 $M$ 次上线」实现，并把真实请求的连续 5xx 与超时接入同一状态机；Envoy 的 outlier detection 还支持基于成功率与标准差的统计化判定，具体语义以官方文档为准。

## 六、常见误区

- **「ping 通或 TCP 能连就健康」**：进程可能僵死、线程池耗尽、依赖不可达，必须做应用层语义检查。
- **「一次失败就摘除」**：网络抖动会造成误摘与流量重分配，进而连锁过载；应设连续失败阈值。
- **「健康检查越频繁越好」**：探针速率 $R = n/I$，过频会同时压垮后端与 LB，且超时必须小于间隔。
- **「恢复后立即满负载」**：刚恢复的实例缓存冷、连接池空，立即打满会再次崩溃，需慢启动逐步加权。
- **「健康检查可以替代重试」**：检查只能降低打到坏节点的概率，客户端仍需超时、重试与幂等设计。
- **「不健康节点直接摘掉就好」**：若多数节点不健康，全部摘除等于全站不可用，应设 panic 阈值在极端情况下继续转发。

## 七、与开源书·权威来源对应

- **RFC 1122**：Internet 主机的可达性与故障语义，是「什么算不可达」的基础定义。
- **RFC 9110**：`200 OK`、`503 Service Unavailable` 与 `Retry-After` 的语义，健康探针与状态码判定的规范依据。
- **Google《Site Reliability Engineering》**：过载处理、健康检查与避免级联故障的工程经验（以官方在线版本为准）。
- **Fowler, *CircuitBreaker*（martinfowler.com）**：熔断器 Closed/Open/Half-Open 状态机的经典表述。
- **Envoy / HAProxy / Kubernetes 官方文档**：health checking、outlier detection、panic threshold、`observe`、`agent-check` 与 liveness/readiness 探针语义，以官方最新文档为准。

## 八、面试题

**Q1：为什么需要连续失败次数阈值？**
要点：单次探测可能因抖动或瞬时过载失败，连续 $N$ 次同时失败的概率约为 $p^N$，可把误摘率降到可忽略。

**Q2：主动探测与被动探测如何配合？**
要点：主动负责冷实例与恢复确认，被动负责发现「探针健康但真实请求失败」，二者合并到同一状态机。

**Q3：检测延迟如何计算，为什么恢复后要慢启动？**
要点：$D_{detect} = N\cdot I + T$，即连续失败次数乘探测间隔再加单次超时，且超时必须小于间隔；慢启动是因为刚恢复实例缓存冷、连接池未预热，立即满负载会被再次打挂。

**Q4：大部分节点都不健康时怎么办？readiness 与 liveness 有什么区别？**
要点：设 panic/紧急阈值，在健康比例过低时仍向后端转发以避免全站不可用；readiness 决定是否纳入流量（失败则摘除但不重启），liveness 决定是否重启容器（失败说明进程无法自愈）。

## 九、演进与趋势

- **多维健康融合**：把延迟分位数、错误率、饱和度等黄金指标纳入判定，而非只看二值可达性；Kubernetes 的 liveness/readiness/startup 探针已成为跨平台约定。
- **网格内统一健康视图**：sidecar 汇总被动健康数据并上报控制面，实现全局一致的健康判定，并结合慢启动让恢复节点按时间或成功率逐步提升权重。
- **内核态观测与容量联动**：用 eBPF 以更低开销完成连接级被动探测，并在摘除坏节点后联动自动扩缩容，避免剩余节点过载。

## 十、小结

健康检查用主动探测与被动观测结合、以带滞回的状态机决定节点上下线，是负载均衡可用性的保障。三个关键参数是连续失败阈值 $N$、探测间隔 $I$ 与超时 $T$，直接决定检测延迟与误摘率；配套手段包括抖动抑制、慢启动与 panic 阈值。健康检查只能降低故障暴露面，不能替代超时、重试、幂等与容量规划。
