# 会话保持

> 对应 RFC 6265（HTTP State Management Mechanism）、RFC 3022（传统 IP NAT）与 Karger et al. 1997 *Consistent Hashing and Random Trees*（STOC）。

## 一、背景与挑战

有状态应用（购物车、登录会话、上传分片）希望同一用户的请求落到同一后端，否则会「会话丢失、要求重新登录」或状态错乱。会话保持（sticky session / session affinity）即为满足这一约束而引入。

它带来结构性矛盾：**亲和度越高，负载越不均衡**。新节点上线后拿不到任何存量会话，扩容失效；某后端承载过多被「黏」住的会话时，其故障影响面也成倍放大。同时最常用的源 IP 亲和在现代网络中并不可靠：NAT 让成千上万用户共享出口 IP（RFC 3022），移动网络切换会改变客户端地址，IPv6 隐私地址（RFC 4941）也会周期性轮换。

## 二、核心原理

四种常见手段：

1. **源 IP 哈希**：$backend = H(srcIP) \bmod N$。零配置、对客户端透明，但 NAT 后大量用户被映射到同一后端，且客户端换 IP 即丢亲和。
2. **Cookie 注入**：均衡器在首次响应插入 `Set-Cookie: SRV=node3`，后续请求据此路由，并对客户端隐藏后端标识。
3. **Cookie 透传/改写**：沿用应用自己的会话 Cookie（如 `JSESSIONID`），均衡器只读取其值做路由，需要应用与均衡器约定编码方式。
4. **基于业务键的一致性哈希**：用用户 ID、租户 ID、设备 ID 等稳定标识做键，节点增减仅影响相邻区间，迁移量最小。

关键设计原则是**状态外置**：把会话数据放入 Redis/数据库等共享存储，使后端无状态。此时亲和退化为性能优化（提高缓存命中、减少跨节点读取），而非正确性前提——节点挂掉最多让用户多读一次共享存储，不会丢会话。

## 三、形式化与数学基础

绑定函数可写作 $backend = H(k)$，其中 $k \in \{srcIP, sessionID, userID, tenantID\}$，目标是在时间窗口 $W$ 内对同一 $k$ 恒定映射，同时满足负载均衡约束。

**取模的迁移代价**：节点数 $N \to N+1$ 时，键被重新映射的比例为

$$\frac{N}{N+1} \approx 1 - \frac{1}{N+1}$$

几乎全部会话丢失。改用一致性哈希后迁移比例降为 $\dfrac{1}{N+1}$，只影响环上相邻区间。**源 IP 亲和的实际偏差**：若某出口 IP 对应 $m$ 个用户、总用户数为 $U$、后端数为 $N$，则该后端获得的会话份额约为 $m/U$ 而非 $1/N$，方差随 NAT 规模上升，热点后端可能远超平均负载。

## 四、代码实现

```nginx
# 源 IP 亲和（最简单，NAT 下最不均衡）
upstream app_ip { ip_hash; server 10.0.1.10; server 10.0.1.11; }

# Cookie 亲和：均衡器注入并维护后端标识
upstream app_cookie {
    server 10.0.1.10;
    server 10.0.1.11;
    sticky cookie srv_id expires=1h httponly secure path=/;
}

# 一致性哈希：按业务键绑定，节点增减仅影响相邻区间
upstream app_chash {
    hash $cookie_user_id consistent;
    server 10.0.1.10;
    server 10.0.1.11;
}
```

```python
# 应用侧：把会话状态外置，使后端真正无状态
def login(uid, sid_store, token_store):
    token = token_store.new(uid)                            # 随机、不可猜测
    sid_store.setex(b"sid:" + token, 1800, encode(uid))     # TTL 30 分钟
    return token

def handle(token, sid_store):
    uid = sid_store.get(b"sid:" + token)
    if uid is None:
        return 401                                          # 会话过期或被驱逐
    sid_store.expire(b"sid:" + token, 1800)                 # 滑动过期
    return 200
```

Cookie 属性必须齐全：`Secure`、`HttpOnly`、`SameSite`，并在服务端防会话固定与 CSRF。

## 五、与其他技术对比

| 维度 | 源 IP 哈希 | Cookie 注入 | 一致性哈希（业务键） | 外置状态 + 无亲和 | 服务端会话复制 |
| --- | --- | --- | --- | --- | --- |
| 客户端透明性 | 完全透明 | 需接受新 Cookie | 完全透明 | 透明 | 透明 |
| NAT 下均衡性 | 差 | 好 | 好 | 好 | 好 |
| 节点故障影响 | 该 IP 用户重登录 | 该 Cookie 重映射 | 仅相邻区间受影响 | 无状态丢失 | 依赖复制延迟 |
| 扩容迁移量 | 几乎全量 | 几乎全量 | $1/(N+1)$ | 无 | 需同步新节点 |
| 主要风险 | 热点、换 IP | 客户端禁 Cookie | 键选择不当 | 存储成为依赖 | 内存放大、一致性 |

## 六、常见误区

- **「有了会话保持就不会丢状态」**：节点宕机时本地会话仍会丢失；会话保持只保证正常情况下落在同一节点，不提供持久性。
- **「源 IP 亲和一定准确」**：NAT 后多用户同 IP、移动网络切换、IPv6 隐私地址轮换都会破坏该假设。
- **「亲和时间越长越好」**：过期时间越长，新节点参与度越差，故障时受影响用户越多，滚动发布越容易造成大面积登出。
- **「一致性哈希能替代负载均衡」**：它只决定归属，不感知实时负载；热点键仍需靠虚拟节点或有界负载缓解。

## 七、与开源书·权威来源对应

- **RFC 6265**：Cookie 的语义与安全属性，是 Cookie 亲和与安全加固的规范基础（后续修订以官方最新版本为准）。
- **RFC 3022**：传统 IP NAT，说明源 IP 亲和在现代网络中为何不可靠。
- **RFC 4941**：IPv6 隐私地址，解释客户端地址会周期性变化。
- **Karger et al. 1997（STOC）**：一致性哈希，节点增减时最小化重映射。
- **Kurose & Ross《Computer Networking: A Top-Down Approach》**：HTTP 无状态语义与 Cookie 的引入动机。
- **Google《Site Reliability Engineering》**：有状态服务的运维实践与外部化状态的动机（以官方在线版本为准）。

## 八、面试题

**Q1：会话保持的代价是什么？**
要点：牺牲均衡度与弹性——新增节点难以分担存量会话，节点故障会造成该节点全部会话丢失，热点用户可能压垮单节点。

**Q2：如何既保持亲和又保证高可用？**
要点：把会话状态外置到 Redis/共享存储，亲和降级为性能优化；任选后端均可处理请求，节点故障只影响缓存命中率。

**Q3：为什么源 IP 亲和不可靠？**
要点：NAT 使大量用户共享出口 IP，移动网络与 IPv6 隐私地址会改变客户端地址，导致映射漂移或热点。

**Q4：会话 Cookie 必须带哪些属性？**
要点：`Secure`、`HttpOnly`、`SameSite`，并在服务端使用高强度随机 ID、防会话固定与 CSRF。

**Q5：一致性哈希相比取模好在哪？**
要点：扩容时迁移比例从 $N/(N+1)$ 降到 $1/(N+1)$，只影响环上相邻区间，避免大面积缓存击穿与会话丢失。

## 九、演进与趋势

- **无状态化成为主流**：JWT 等自包含凭证（RFC 7519）让服务端不存会话，代价是撤销困难，需短 TTL 配合黑名单。
- **服务网格里的流量亲和**：Envoy 等数据面支持基于 Cookie/Header 的亲和与一致性哈希，策略由控制面统一下发。
- **优雅下线（drain）**：节点退出前停止接受新会话、等待存量会话迁移或过期，配合注册中心摘除减少强制登出。
- **多活与就近接入**：会话存储跨地域复制，一致性由存储层而非亲和承担。
- **无 Cookie 方案**：移动端与服务间调用更多使用 token 与 mTLS 身份，弱化 Cookie 亲和的必要性。

## 十、小结

会话保持用源 IP、Cookie 或一致性哈希把用户黏到后端，解决有状态应用的短期一致性问题，但以均衡性、弹性与故障域为代价。最佳实践是**把状态外置、让后端无状态**：此时亲和只用于提高缓存命中率，节点故障不再意味着会话丢失。任何方案都要正视 NAT、地址漂移与热点用户这三类现实约束。
