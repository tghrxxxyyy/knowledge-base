# 会话保持

> 对应负载均衡会话亲和（Session Affinity）实践。

## 一、背景与挑战
有状态应用（购物车、登录会话）希望同一用户请求落到同一后端，否则会话丢失需重新登录或状态错乱。但过度亲和又损害均衡。

## 二、核心原理
会话保持（Sticky / Affinity）让同一客户端的请求黏到同一后端。手段：基于源 IP 哈希、注入 Cookie（如 Nginx sticky）、基于一致性哈希的 key（用户 ID）。后端应把状态外置（Redis）以降低亲和依赖。

## 三、形式化 / 数学基础
绑定函数：$backend = H(client\_id)$ 或 $backend = map[session\_cookie]$。
目标：在窗口 W 内同一 client_id 恒定映射；节点故障时重映射（可能丢失本地状态）。

## 四、代码实现
```nginx
upstream app {
    ip_hash;                 # 基于源 IP 亲和
    server 10.0.1.10;
    server 10.0.1.11;
}
# 或 cookie 亲和
upstream app { sticky cookie srv_id expires=1h; ... }
```

## 五、与其他技术对比
会话保持提升有状态体验但牺牲部分均衡与可扩展性；无状态 + 集中缓存（Redis）可从根上免除亲和需求，是更优架构。

## 六、常见误区
误区一：有了会话保持就无需共享存储。错，节点挂掉仍丢状态。误区二：源 IP 亲和一定准。错，NAT 后多用户同 IP 或 IPv6 前缀变化。误区三：亲和越久越好。错，阻碍新节点分担。

## 八、面试题
1. 会话保持的代价？2. 如何既保持又高可用？答：外置状态到 Redis。

## 九、演进与趋势
服务网格用 consistent hashing + 外部会话存储替代传统 sticky；无状态化是趋势。

## 十、小结
会话保持用 IP/Cookie/哈希把用户黏到后端，但最佳实践是外置状态实现无状态扩展。
