# 四层与七层负载均衡

> 对应 Zhang & Jin 2000 *Linux Virtual Server for Scalable Network Services*（Ottawa Linux Symposium）、Eisenbud et al. 2016 *Maglev*（NSDI），以及 RFC 791/793/9110。

## 一、背景与挑战

流量必须分发到多后端。四层（L4）只看 IP 与端口，转发快但无法理解内容；七层（L7）能解析 HTTP 等协议做智能路由，但需要完整处理报文，开销更大。二者不是替代关系而是分层协作：L4 解决「如何把海量连接分到一组机器」，L7 解决「一条连接里的请求该如何按内容路由」。

真正的工程难点在于：L4 的三种转发模式对网络拓扑有不同要求，选错会导致回包路径断裂或端口耗尽；L7 终止 TLS 后客户端真实信息丢失，需要额外机制传递；HTTP/2 与 HTTP/3 的多路复用让「连接级均衡」失效——一条连接可能承载数千请求，后续请求不再经过均衡器。

## 二、核心原理

**L4 的三种模式**（以 LVS 分类为参照）：

- **NAT**：均衡器改写目的 IP（必要时也改端口），后端回包必须再经均衡器做反向改写，故请求与响应都过均衡器，是双向瓶颈，但后端无需配置。
- **Tunnel（IP 封装）**：均衡器把原始报文封装进新 IP 报文发给后端，后端解封装后直接回给客户端；响应不经过均衡器，但后端需支持 IP 隧道。
- **DSR（Direct Server Return）**：只改二层目的 MAC、保持目的 IP 不变；后端把 VIP 配在本地（通常在 `lo` 或抑制 ARP 的接口），以 VIP 为源地址直接回包。吞吐最高，但要求同二层网络，且后端看不到真实源 IP。

**L7 的关键能力**：终止 TCP/TLS 后按 Host、路径、Header、Cookie 路由，支持改写、压缩、缓存、WAF、限流。代价是维持完整连接状态与协议解析状态机，内存与 CPU 成本远高于 L4。NAT 模式还需维护连接跟踪表，表项数正比于并发连接数。

## 三、形式化与数学基础

L4 的决策元组是五元组：

$$key = (srcIP, srcPort, dstIP, dstPort, proto)$$

同一五元组的报文必须哈希到同一后端，否则 TCP 因乱序错配而崩溃。L7 的决策依赖应用层字段：$route = f(method, host, path, headers)$。

**NAT 的端口约束**：设均衡器有 $n$ 个出口 IP、可用端口区间为 $P$，则并发连接上界为 $C_{max} = n\cdot P$，这正是高并发 NAT 网关需要大量出口 IP 的原因。**DSR 的带宽收益**：均衡器承担的流量从

$$B_{NAT} = B_{in} + B_{out}\quad\text{降为}\quad B_{DSR} = B_{in}$$

对「请求小、响应大」的场景（视频、下载、图床），收益可达数倍。

## 四、代码实现

```nginx
# 七层：按 Host 与路径分流，并保留客户端真实信息
upstream api { server 10.0.1.10:8080; server 10.0.1.11:8080; }
server {
    listen 443 ssl;
    server_name api.example.com;
    location /v1/ {
        proxy_pass http://api;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# 四层：stream 模块按端口转发，不做协议解析
stream {
    upstream mysql_backend { server 10.0.2.10:3306; }
    server {
        listen 3306;
        proxy_pass mysql_backend;
        proxy_protocol on;   # 向后端传递原始源/目的地址
    }
}
```

`proxy_protocol`（PROXY protocol）是 L4 传递真实源地址的标准手段：在连接建立后、业务数据之前插入地址信息，需后端显式支持。

## 六、常见误区

- **「L7 一定慢到不能用」**：现代实现（Envoy、Nginx、HAProxy）在常见配置下可接近线速，瓶颈通常在于 TLS 握手与连接管理。
- **「L4 不能做会话保持」**：可以基于源 IP 或五元组哈希粘连，只是粒度粗、无法感知应用语义。
- **「反向代理就是负载均衡」**：反向代理侧重「代表后端接收请求」（可能只有一个后端），负载均衡侧重「在多个后端间分发」。
- **「DSR 一定最优」**：它要求同二层、需后端配 VIP、丢失真实源 IP，在容器与 Overlay 网络中难以落地。
- **「HTTP/2 下 L7 均衡仍然有效」**：连接级均衡对长连接失效，需要请求级均衡或限制单连接并发 stream 数。
- **「NAT 模式不用管端口耗尽」**：大规模 NAT 场景下源端口是稀缺资源，必须规划出口 IP 池。

## 八、面试题

**Q1：L4 与 L7 负载均衡的核心区别？**
要点：L4 只看五元组、不解析载荷、性能高但无内容感知；L7 终止并可修改应用协议，支持按 Host/路径/Header 路由、改写、WAF、压缩。

**Q2：DSR 模式为什么回包不经均衡器？**
要点：目的 IP 未被改写，后端以 VIP 为源地址直接把响应发给客户端，均衡器只负责入向的二层转发，从而卸载出向带宽。

**Q3：NAT 模式的瓶颈在哪？**
要点：请求与响应都经过均衡器形成双向带宽压力，且需要连接跟踪表与足够的出口端口/IP 空间。

**Q4：L7 如何把真实源 IP 传给后端？**
要点：注入 `X-Forwarded-For`/`X-Real-IP`（应用层）或使用 PROXY protocol（四层），二者都需要后端配合解析。

**Q5：长连接下 L7 均衡为什么会失效？**
要点：多路复用让一条连接承载大量请求，只有建连时经过均衡器，后续请求绕过它；解法是请求级均衡。

## 九、演进与趋势

- **eBPF/XDP 内核态转发**：在网卡驱动层完成 L4 均衡与 NAT，绕过协议栈，降低尾延迟与 CPU 占用。
- **服务网格数据面**：sidecar 把 L7 能力（重试、熔断、mTLS、路由）下沉到每个工作负载旁，策略由控制面统一下发。
- **Maglev 类一致性哈希**：以查表替代逐次哈希，兼顾均衡度、最小扰动与极低查找开销。
- **HTTP/3 与 QUIC**：传输层在用户态实现，均衡器还需处理连接迁移与 0-RTT。
- **DPU/智能网卡卸载**：把 L4 转发与 TLS 卸载移到硬件，释放主机 CPU。

## 十、小结

L4 按五元组转发、追求极致性能与最小状态，L7 解析应用协议、提供内容路由与治理能力，二者按场景组合：入口用 L4 做集群级高吞吐分发，业务层用 L7 做精细路由与策略。选择关键不在「哪个更快」，而在是否需要内容感知、回包路径是否可接受、以及真实源 IP 与 TLS 终止位置这些约束。
