# 服务发现

> 对应服务发现模式；Consul/etcd/ZooKeeper 实践；RFC 2782（SRV）。

## 一、背景与挑战
动态环境中后端实例频繁上下线、IP 变化，硬编码地址不可行。服务发现让调用方自动获知“当前有哪些可用实例及地址”。

## 二、核心原理
两类模式：客户端发现（client 查注册中心拿实例列表并自行 LB）与服务端发现（经 LB/网关查）。注册中心（etcd/Consul/ZK）存服务→实例映射，实例通过心跳或租约（lease）维持存活；DNS SRV 也是轻量发现机制。

## 三、形式化 / 数学基础
租约：$lease\_TTL$，实例须每 $< TTL$ 续租，否则 $expire \rightarrow 从注册表摘除$。
一致性：etcd/ZK 用 Raft/Zab 保证注册表强一致（多数派写入）。
健康检查联动：注册中心标记 unhealthy → 从可返回列表移除。

## 四、代码实现
```go
// etcd 注册（租约）
lease, _ := client.Grant(ctx, 10) // 10s TTL
client.Put(ctx, "svc/user/10.0.1.10:8080", "up", clientv3.WithLease(lease.ID))
// 续租保活
keep, _ := client.KeepAlive(ctx, lease.ID)
```

## 五、与其他技术对比
客户端发现（如 gRPC 内置 resolver + 一致性哈希）延迟低、去中心 LB；服务端发现（经网关）对客户端透明。对比静态配置与 DNS 轮询（弱一致、慢）。

## 六、常见误区
误区一：服务发现等于 DNS。错，DNS 是特例且弱一致。误区二：注册即用、无需续租。错，需心跳/租约防僵尸。误区三：发现中心挂了全站挂。错，应缓存快照 + 本地兜底。

## 十、小结
服务发现用注册中心 + 租约/心跳动态维护实例列表，是弹性微服务的基础设施。
