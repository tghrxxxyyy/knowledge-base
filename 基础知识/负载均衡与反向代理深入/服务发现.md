# 服务发现

> 对应 RFC 2782（DNS SRV 记录）、Ongaro & Ousterhout 2014 *In Search of an Understandable Consensus Algorithm*（Raft）与 Kurose & Ross《Computer Networking: A Top-Down Approach》。

## 一、背景与挑战

动态环境中实例频繁上下线、IP 由调度器分配，硬编码地址必然失效。服务发现要回答「此刻有哪些可用实例、地址是什么」，并在**故障与网络分区并存**时给出不误导的答案。它有内在矛盾：注册表越强一致，写入越慢、越难跨地域；心跳只证明「进程还在跑」，不证明业务可用；集中式注册中心自身会成为新的单点，因此调用方必须有本地缓存与兜底。

## 二、核心原理

两种基本范式：

- **客户端发现**：客户端向注册中心查询实例列表，自行负载均衡与重试（gRPC 内置 resolver、Eureka 客户端）。路径最短、少一跳，但每种语言都要实现一套发现与均衡逻辑。
- **服务端发现**：客户端只访问稳定入口（VIP、LB、网关），由入口查询注册中心并转发（Kubernetes Service、IPVS、云 LB、Envoy xDS）。对客户端透明，但入口成为容量与故障焦点。

实例通过两种机制维持存活：**心跳**（周期上报，超时未收到即摘除）与**租约**（申请带 TTL 的租约并持续续约，到期自动过期，etcd 的 lease 是典型）。此外 DNS SRV（RFC 2782）也是合法载体，它把「服务、协议、域名」映射到「优先级、权重、端口、目标主机」，自带优先级与权重，但受缓存 TTL 约束且无法表达健康状态与元数据。

## 三、形式化与数学基础

租约模型下，设 TTL 为 $L$、续约周期为 $p$（需 $p \ll L$），实例停止续约后最坏摘除延迟满足

$$D_{detect} \le L + \varepsilon,\qquad \varepsilon = \text{注册中心检测与传播延迟}$$

etcd 基于 Raft、ZooKeeper 基于 Zab，均为多数派写入的强一致协议：集群规模 $N = 2f+1$ 时可容忍 $f$ 个节点故障，写请求需 $N_{quorum} = \lfloor N/2 \rfloor + 1$ 个节点确认。若客户端缓存快照并接受陈旧读，则在陈旧窗口 $\Delta t$ 内读到已下线实例的概率随故障率 $\lambda$ 上升：

$$P_{stale} \approx 1 - e^{-\lambda \cdot \Delta t}$$

这正是「缓存 + 快速失败重试」比「每次强一致查询」更常用的原因。

## 四、代码实现

```go
// etcd 注册：申请租约、挂载键并持续保活
cli, _ := clientv3.New(clientv3.Config{Endpoints: endpoints})
ctx := context.Background()

lease, err := cli.Grant(ctx, 10)                 // TTL 10s
if err != nil { return err }
_, err = cli.Put(ctx, "svc/user/10.0.1.10:8080", `{"weight":100}`,
    clientv3.WithLease(lease.ID))                // 键随租约过期而消失
if err != nil { return err }

kaCh, err := cli.KeepAlive(ctx, lease.ID)        // 临近过期时自动续约
if err != nil { return err }
for ka := range kaCh {
    if ka.TTL == 0 {                             // 续约失败，需重新注册
        return errors.New("lease expired")
    }
}
```

```bash
# DNS SRV 发现：优先级 10、权重 60、端口 8080
_service._proto.example.com. 60 IN SRV 10 60 8080 app1.example.com.
```

## 六、常见误区

- **「服务发现就是 DNS」**：DNS 只是载体之一，弱一致、受 TTL 约束、无法表达健康状态，不适合高频变更场景。
- **「注册完就一直可用」**：没有租约或心跳，进程被 `SIGKILL` 后注册表会永远保留僵尸条目。
- **「发现中心挂了全站就挂」**：正确设计是客户端持有快照、注册中心不可用时继续使用，并配合本地健康检查兜底。
- **「探活等于可用」**：TCP 能连不等于业务健康，应提供能校验关键依赖的语义化探针。
- **「注册表越强一致越好」**：跨地域强一致会带来写延迟与分区可用性问题；通常只需读路径可用、写路径最终一致。

## 七、与开源书·权威来源对应

- **RFC 2782**：DNS SRV 记录的优先级与权重语义，是「用 DNS 做发现」的规范基础。
- **Ongaro & Ousterhout 2014（USENIX ATC）**：Raft，etcd/Consul 等注册中心的一致性内核。
- **Hunt et al. 2010（USENIX ATC）**：ZooKeeper 的 wait-free 协调原语与顺序保证。
- **Kurose & Ross《Computer Networking: A Top-Down Approach》**：DNS 与协议分层章节，解释 SRV 与缓存 TTL 的代价。
- **Gilbert & Lynch 2002（SIGACT News）**：CAP 的形式化证明，是「可用性 vs 陈旧窗口」取舍的依据。

## 八、面试题

**Q1：客户端发现与服务端发现的区别与取舍？**
要点：前者无额外跳、路径最短，但每种语言都要实现；后者对客户端透明，但引入入口热点与一跳延迟。由团队技术栈统一程度决定。

**Q2：注册中心为什么要租约/心跳？**
要点：进程可能崩溃、被强杀或遭遇网络分区，无法优雅注销；TTL 使条目自动过期，避免僵尸实例被长期调度。

**Q3：发现中心不可用时怎么办？**
要点：客户端缓存实例快照、允许陈旧读、本地健康检查加退避重试；核心是让发现系统不成为数据路径的关键依赖。

**Q4：为什么 DNS 不适合高频变更？**
要点：多级缓存与 TTL 下限导致传播延迟不可控，且 SRV 不携带健康状态与元数据。

## 九、演进与趋势

- **Kubernetes 原生发现**：Endpoints/EndpointSlice 由控制器按 Pod 就绪状态维护，`Service` 提供稳定虚拟 IP，发现成为平台能力。
- **xDS 与数据面下沉**：服务网格把发现、均衡、熔断统一下发到 sidecar/eBPF 数据面，客户端代码与协议解耦。
- **多集群与拓扑感知**：基于延迟探测与区域标签做就近路由，优先同区、跨区兜底。
- **声明式与可观测性**：发现结果与健康状态直接暴露为指标，配合分布式追踪定位「选错实例」类问题。

## 十、小结

服务发现用注册中心加租约/心跳动态维护实例列表，本质是一致性、可用性与变更延迟三者的取舍。工程要点是：写路径强一致但不进入数据关键路径，读路径允许缓存与陈旧并配合快速失败，健康状态必须语义化而非仅靠 TCP 可达。
