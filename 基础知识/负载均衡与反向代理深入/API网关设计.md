# API网关设计

> 对应 Richardson《Microservices Patterns》、RFC 9110（HTTP 语义）、RFC 6749（OAuth 2.0）、RFC 7519（JWT）与 RFC 2697/2698（单速率/双速率三色标记，令牌桶的规范表述）。

## 一、背景与挑战

微服务拆细之后，客户端若直连每个服务会面临一串问题：地址暴露（内部拓扑泄漏）、协议异构（REST、gRPC、WebSocket 并存）、认证重复（每个服务都要实现一套鉴权）、限流无法统一、可观测性碎片化。API 网关把这些横切关注点收敛到统一入口，同时带来三个新问题：它成了单点，必须自身高可用与可水平扩展，否则「统一入口」等于「统一故障」；它进入每个请求的关键路径，每加一个插件就叠加一次延迟；它容易演变成业务编排器，一旦承担业务逻辑，就会随业务变更频繁发布，稳定性与迭代速度同时受损。

## 二、核心原理

网关的骨架只有两部分：**路由表**与**插件链**。

**路由匹配**：以 $(method, host, path, headers)$ 为输入，按优先级与最长前缀匹配到目标服务。工程要点是匹配必须**确定性且可预测**（相同输入永远得到同一结果），并支持路由冲突检测与显式优先级，避免新增路由意外劫持旧流量。

**插件链（middleware pipeline）**：请求按序穿过认证、限流、路由改写、熔断、日志等插件，响应逆序穿回。每个插件应满足三个约束：无阻塞（不执行同步 IO 或重计算）、失败语义明确（拒绝还是放行）、自带指标。核心能力清单包括：认证授权（JWT、OAuth 2.0、mTLS、API Key）、限流配额（令牌桶/漏桶，按租户或路由维度）、熔断隔离、协议转换（HTTP/JSON ↔ gRPC/Protobuf、WebSocket 升级、HTTP/1.1 ↔ HTTP/2）、请求聚合与裁剪（BFF 模式）、可观测性与安全（访问日志、Trace 头透传、WAF、体积限制）。

**南北向与东西向**：网关通常指客户端到集群的南北向流量；集群内部的服务间流量（东西向）由服务网格的 sidecar 承担。两者能力高度重合，因此现代架构倾向统一数据面、分别下发策略。

## 三、形式化与数学基础

**路由匹配**可用优先级函数刻画。设路由 $r$ 的匹配长度为 $|prefix(r)|$、显式优先级为 $p_r$，则 $r^{*} = \arg\max_{r \in \mathcal{R}(req)} (p_r, |prefix(r)|)$，即先比显式优先级、再比最长前缀，保证结果确定。

**令牌桶限流**：桶容量 $b$、令牌补充速率 $r$，时刻 $t$ 的可用令牌数为 $tokens(t) = \min(b,\ tokens(t_0) + r\cdot(t-t_0))$。请求到达时若 $tokens \ge 1$ 则放行并减 1，否则拒绝（通常返回 429）。$r$ 决定长期平均速率，$b$ 决定可容忍的突发量。分布式场景下各网关实例独立计数会让实际总速率约为 $r \times$ 实例数，需要中心化计数或按份额切分配额。（令牌桶的规范化表述见 RFC 2697/2698 的三色标记算法。）

**插件链延迟**：设链上 $k$ 个插件、各自新增延迟 $d_i$，端到端延迟为 $L = L_{downstream} + \sum_{i=1}^{k} d_i$。即使单个 $d_i$ 很小，$k$ 较大时也会显著抬高尾延迟。**可用性级联**：若每个插件自身可用性为 $a$，整条链的可用性上界为

$$A_{chain} = \prod_{i=1}^{k} a_i$$

这解释了「插件越多越不可靠」的数学依据，也说明非关键插件（日志、指标）必须失败不阻断。

## 四、代码实现

```yaml
# 路由表 + 插件链（伪配置，字段语义参照主流网关）
routes:
  - name: user-api
    match: { method: [GET, POST], path_prefix: /v1/user/ }  # 最长前缀匹配
    upstream: user-svc:8080
    plugins:
      - jwt-auth: { issuer: "https://idp.example.com", jwks_ttl: 300 }
      - rate-limit: { rate: 100, burst: 200, key: "$tenant_id" }
      - circuit-breaker: { error_rate: 0.5, window: 10, half_open: 5 }
      - access-log: { sample: 0.01 }        # 非关键插件，失败不阻断
  - name: order-grpc
    match: { path_prefix: /v1/order/ }
    upstream: order-svc:50051
    plugins:
      - oauth2-introspect: {}
      - grpc-transcode: { proto: "order.proto" }   # JSON <-> gRPC
```

```c
/* 令牌桶限流核心（单实例视角，无锁近似） */
typedef struct { double tokens, rate, burst, last; } bucket_t;

bool allow(bucket_t *b, double now) {
    b->tokens += (now - b->last) * b->rate;          /* 按时间补充 */
    if (b->tokens > b->burst) b->tokens = b->burst;  /* 桶容量上界 */
    b->last = now;
    if (b->tokens < 1.0) return false;               /* 拒绝，返回 429 */
    b->tokens -= 1.0;
    return true;
}
```

分布式限流需要把计数放到共享存储或用配额切分：每个实例最多消耗 $r/k$，代价是突发能力下降且热点分配不均。

## 五、与其他技术对比

| 维度 | API 网关 | 反向代理 | 服务网格 sidecar | BFF | ESB |
| --- | --- | --- | --- | --- | --- |
| 主要位置 | 南北向集群入口 | 单服务前置 | 东西向每实例旁 | 面向特定客户端 | 企业集成总线 |
| 核心职责 | 路由 + 横切策略 | 转发、TLS 终止 | 服务间通信治理 | 按客户端聚合裁剪 | 协议转换与编排 |
| 是否含业务逻辑 | 应尽量无 | 无 | 无 | 有（客户端适配） | 大量（编排） |
| 扩展方式 | 插件/Wasm 热加载 | 模块或配置 | 控制面下发 | 独立服务 | 重量级适配器 |
| 故障半径 | 全集群入口 | 单服务 | 单实例调用 | 单客户端类型 | 全企业 |
| 典型实现 | Envoy、Kong、APISIX | Nginx、HAProxy | Envoy、Linkerd | 各类定制服务 | 传统中间件 |

## 六、常见误区

- **「网关能解决一切」**：它也是瓶颈与单点，必须自身多副本、就近部署，并具备独立于业务的容量规划。
- **「网关里放业务逻辑很方便」**：业务一旦进网关，就要随业务变更频繁发布入口组件，风险半径覆盖全站；业务应下沉到服务，网关只做横切。
- **「网关就是 ESB」**：ESB 侧重企业级协议适配与集中编排，重量级且中心化；网关是轻量的流量入口，不做业务编排。
- **「插件越多能力越强」**：链上每加一个插件都叠加延迟与失败概率，$A_{chain} = \prod a_i$；非关键插件必须可降级。
- **「限流配置了就是全局生效」**：多副本下各实例独立计数会使实际速率成倍放大，需要中心化计数或配额切分。
- **「熔断与重试可以随便叠加」**：重试会放大下游压力，若所有客户端同时重试，会把局部故障放大为全网雪崩，必须配合退避、抖动与重试预算。

## 七、与开源书·权威来源对应

- **Richardson《Microservices Patterns》**：API 网关、BFF 与微服务横切关注点的模式化描述。
- **Fowler《Microservices》与 Gateway 相关文章（martinfowler.com）**：网关的定位与「不要放业务逻辑」的告诫。
- **RFC 9110**：HTTP 语义（方法、状态码、条件请求、缓存），是网关改写与转发规则的规范基础。
- **RFC 6749 / RFC 7519**：OAuth 2.0 与 JWT，网关鉴权插件的实现依据；**RFC 8446** 则是入口 TLS 终止与 mTLS 的协议基础。
- **RFC 2697 / RFC 2698**：单速率与双速率三色标记，令牌桶/漏桶限流的规范化表述；**RFC 6585** 定义 `429 Too Many Requests` 与 `Retry-After`。
- **Envoy / Kong / APISIX 官方文档与 OpenAPI Specification**：路由匹配、插件模型、Wasm 扩展与接口契约的权威说明，以官方最新文档为准。

## 八、面试题

**Q1：网关与反向代理的区别？**
要点：反向代理侧重「代表后端接收请求」并做转发与 TLS 终止；网关在此之上提供认证、限流、熔断、协议转换等横切策略与统一入口治理。

**Q2：为什么网关不应承载重业务逻辑？**
要点：业务变更会迫使入口组件频繁发布，故障半径覆盖全站；网关需保持无状态、低延迟、高稳定，业务逻辑应下沉到服务或 BFF。

**Q3：网关限流在多副本下如何保持全局准确？**
要点：中心化计数（Redis/共享存储）或按实例切分配额；前者准确但增加一次网络往返，后者近似但可能突发不均。

**Q4：插件链为什么会影响可用性？重试为什么可能引发雪崩？**
要点：链式调用的可用性是各环节可用性的乘积 $A_{chain}=\prod a_i$，故日志、指标类插件必须失败不阻断；重试会成倍放大下游流量，若客户端同时重试且无退避，局部过载会扩散为全网故障，需要重试预算、指数退避与抖动。

**Q5：BFF 与网关的关系？**
要点：BFF 是网关的按客户端特化形态，为不同终端定制聚合与裁剪；它更靠近业务，通常作为独立服务而非网关插件实现。

## 九、演进与趋势

- **数据面统一与 Wasm 插件**：网关与 sidecar 共用同一数据面（如 Envoy）与控制面协议（xDS）；用 WebAssembly 承载插件逻辑，实现语言无关、沙箱隔离与热加载，避免为改插件而重启网关。
- **eBPF 卸载与契约驱动**：把鉴权、限流的前置判断下沉到内核态；以 OpenAPI/Protobuf 为单一事实来源自动生成路由、校验与文档，减少手工配置漂移。
- **零信任与 AI 流量治理**：mTLS 与短期凭证成为默认，网关承担身份转换而非自定义鉴权；面向 LLM 推理的网关还需处理配额、成本核算、令牌级限流与流式响应（以各厂商最新文档为准）。

## 十、小结

API 网关把路由与认证、限流、熔断、协议转换、可观测性等横切关注点收敛为统一南北向入口，其骨架是「路由表 + 插件链」。设计的核心权衡是：入口越统一、能力越集中，单点风险与延迟叠加越严重，因此必须坚持无状态多副本、非关键插件可降级、业务逻辑下沉，并用契约驱动与统一下发控制面来降低配置漂移。
