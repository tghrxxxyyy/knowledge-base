# 冲突解决

> 对应 Kleppmann《DDIA》第 5 章 Conflict Resolution，及 Shapiro et al. CRDT 论文。

## 一、背景与挑战
多主/无主复制中并发写会产生冲突(同一 key 的不同值)。必须在“可接受的延迟与复杂度”下决定最终值，且保证各副本收敛。

## 二、核心原理
冲突解决策略：
- LWW(最后写入获胜)：按时间戳选最新；简单但可能静默丢更新。
- 应用层合并：返回多版本给客户端，由业务逻辑合并后回写。
- 因果合并：用向量时钟识别并发，对并发值做合并。
- CRDT(无冲突复制数据类型)：数据结构设计使并发更新可交换、结合、幂等，自动收敛(如 G-Counter、OR-Set、PN-Counter)。
- 版本向量(Version Vectors)：判断副本间是“因果前序”还是“并发”。

## 三、形式化 / 数学基础
CRDT 收敛要求：合并操作满足交换律 merge(a,b)=merge(b,a)、结合律、幂等性。
例 G-Counter：每个副本 i 维护计数 c_i，合并为逐分量 max，总值为 Σ c_i；增量只改本地分量，故并发增量可无损相加。
OR-Set：用 (element, unique_tag) 标记，添加加 tag，删除移除对应 tag；合并保留所有未删除 tag，保证加/删并发不丢。

## 四、代码实现
```python
# G-Counter: 可交换、结合、幂等的计数器
class GCounter:
    def __init__(self, n): self.c = [0]*n
    def inc(self, i, d=1): self.c[i] += d
    def merge(self, other):
        self.c = [max(a,b) for a,b in zip(self.c, other.c)]
    def value(self): return sum(self.c)
```

## 五、与其他技术对比
- LWW 简单但有损；CRDT 无损但需数据结构支持。
- 应用层合并最灵活但最重。

## 六、常见误区
- 误区：LWW 总能选出“正确”值。它丢弃并发更新。
- 误区：普通集合可自动合并。需 OR-Set 等 CRDT 才不丢并发加/删。

## 九、演进与趋势
CRDT 成为本地优先协作软件(如协作编辑器、边缘数据库)的主流冲突解决方案。

## 十、小结
冲突解决在一致性与可用性间取舍：LWW 简单有损，CRDT 无损自动收敛，应用层合并最灵活，应按场景选择。
