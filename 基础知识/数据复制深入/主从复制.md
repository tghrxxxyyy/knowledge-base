# 主从复制

> 对应 Kleppmann《DDIA》第 5 章 Replication(单领导者)。

## 一、背景与挑战
把数据复制到多节点以提升可用性与读吞吐。最简单可靠的是单主(single-leader)复制：一个节点处理写，其他副本异步/同步跟随。

## 二、核心原理
- Leader 接收所有写，按日志(如 WAL/binlog)顺序发给 Follower。
- Follower 重放日志，保持与 Leader 相同顺序。
- 同步复制：Leader 等至少一个 Follower 确认才返回(强但慢)；异步复制：Leader 立即返回(快但可能丢未同步写)。
- 半同步(semi-sync)：折中，等少数派确认。
故障切换：Leader 宕机后从 Follower 中选举新 Leader。

## 三、形式化 / 数学基础
同步复制安全：写 w 在返回客户端时已持久于多数派(或指定同步副本)，故不丢。
异步风险：Leader 在复制前崩溃会丢失已确认给客户端的写(若 Leader 被误判死亡而新 Leader 无该写)。
复制滞后(replication lag)：异步下读从 Follower 可能看到旧值，定义滞后 = now - last_applied_time。

## 四、代码实现
```sql
-- PostgreSQL 流复制(异步)
ALTER SYSTEM SET synchronous_commit = off;
-- 半同步：至少一个同步备库
ALTER SYSTEM SET synchronous_standby_names = 'standby1';
```
```python
# 应用层主从：写主、读从(带滞后感知)
def write(leader, sql): leader.execute(sql)        # 主
def read(slave, sql): return slave.execute(sql)    # 从，可能滞后
```

## 五、与其他技术对比
- 单主：一致简单，但写成为瓶颈、Leader 故障需切换。
- 多主/无主：写可分散，但冲突处理更复杂。

## 六、常见误区
- 误区：异步复制下读从库总是新。有滞后窗口。
- 误区：同步复制一定不丢。若同步副本也同时挂则不行，需多数派。

## 十、小结
主从复制以单写者简化一致性，代价是写瓶颈与滞后；同步/异步的选择本质是 C 与 A/L 的权衡。
