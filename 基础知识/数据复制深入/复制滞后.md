# 复制滞后

> 对应 Kleppmann《DDIA》第 5 章“Replication Lag”。

## 一、背景与挑战
异步复制下，Follower 永远略微落后于 Leader，这个“滞后”会带来一系列可见的不一致现象，需在应用层或协议层处理。

## 二、核心原理
滞后来源：网络延迟、副本负载、全量重放开销。
典型不一致：
- 读己之写(Read-your-writes)缺失：用户写后从滞后从库读，看不到自己的写。
- 单调读(Monotonic read)缺失：用户先后两次读，第二次反而更旧(因路由到不同滞后从库)。
- 因果读(Consistent prefix)缺失：看到子事件却看不到父事件。
缓解：同步某些关键读、粘性路由、follower 读需追上指定位点、或读主。

## 三、形式化 / 数学基础
设 Leader 在时刻 t_w 应用写 w，Follower i 在 t_i 应用。滞后 L_i = t_i - t_w。
在窗口 [t_w, t_w + max(L_i)] 内，从 Follower 读可能返回 w 之前的值。
读己之写要求：返回给用户的结果版本 >= 该用户最近写入版本(用会话级位点/版本跟踪)。

## 四、代码实现
```python
# 用会话位点保证读己之写
class Session:
    def __init__(self): self.last_write_ver = 0
    def write(self, v):
        self.last_write_ver = leader.write(v)
    def read(self):
        return follower.read_wait_until(self.last_write_ver)  # 等从库追上
```

## 五、与其他技术对比
- 同步复制无滞后但慢；异步有滞后但快。
- 可调一致：对关键路径用 QUORUM/同步，其余用异步。

## 六、常见误区
- 误区：滞后可忽略。高写入/弱网下可达秒级甚至分钟级。
- 误区：所有读都应走主。会丧失读扩展收益。

## 九、演进与趋势
基于位点/版本的读(如 MySQL GTID、Postgres LSN 等待)让应用精确控制“读到哪”。

## 十、小结
复制滞后是异步复制的必然代价，通过会话位点、粘性路由与一致性级别可在体验与性能间平衡。
