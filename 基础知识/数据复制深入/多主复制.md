# 多主复制

> 对应 Kleppmann《DDIA》第 5 章 Multi-Leader Replication。

## 一、背景与挑战
单主的写集中在一点，跨地域场景延迟高。多主(multi-leader)允许多个节点都可写，各自接受写再相互复制，降低写延迟并提升可用性，但引入写冲突。

## 二、核心原理
- 每个 Leader 既是写入口也是其他 Leader 的 Follower。
- 写在本节点应用后异步传播到其他 Leader。
- 冲突处理：最后写入获胜(LWW, 按时间戳)、应用层合并、或 CRDT 自动合并。
- 适用：跨数据中心、离线优先(如日历/联系人同步)、协作编辑。

## 三、形式化 / 数学基础
每个写带 (replica_id, version) 或向量时钟。
LWW 决策：比较 (timestamp, replica_id)，大者胜；但时钟不可靠时可能丢更新。
正确收敛需交换并发写并应用可交换/结合的合并函数(CRDT)：merge(a,b)=merge(b,a)，保证各副本收敛到同值。

## 四、代码实现
```python
# 多主合并：向量时钟检测并发，CRDT 合并
def merge_write(local, remote):
    if concurrent(local.vec, remote.vec):
        return crdt_merge(local.val, remote.val)  # 可交换合并
    return max_by_vec(local, remote)              # 非并发取较新
```

## 五、与其他技术对比
- 优点：写本地、低延迟、某 Leader 宕机仍可写。
- 缺点：冲突解决复杂，一致性弱于单主。

## 六、常见误区
- 误区：多主一定比单主好。冲突与运维复杂度显著增加。
- 误区：LWW 安全。时钟偏差下会静默丢更新。

## 九、演进与趋势
CRDT 让多主在无中心冲突解决下自动收敛，推动本地优先软件发展。

## 十、小结
多主复制用“可接受写冲突”换取低延迟与高可用，适合跨地域与离线场景，但需可靠的冲突解决机制。
