# 超标量与超长指令字

> 对应 Hennessy & Patterson 第3章；CSAPP 中文笔记 https://github.com/Hansimov/csapp 。

## 一、背景与挑战

经典流水每拍发射一条指令，受 ILP 限制。超标量(Superscalar)每拍发多条，VLIW 由编译器打包并行指令字，目标都是挖掘指令级并行。

## 二、核心原理

超标量：硬件动态检测多指令间无冲突并行发射（如 4-wide）。VLIW：指令字含多个 slot，编译器静态调度并保证 slot 间无依赖；硬件简单但依赖编译器质量与二进制兼容。

## 三、形式化 / 数学基础

每拍可完成指令数 $IPC$ 受宽度 $W$ 与可用并行度限制：

$$IPC_{actual} \le \min(W, ILP_{available})$$

净吞吐正比于有效 $IPC$。

## 四、代码实现

```c
// 循环展开提升可并行度（编译器常做）
for (int i = 0; i < n; i += 4) {
    a[i]   = b[i]   + c[i];
    a[i+1] = b[i+1] + c[i+1];
    a[i+2] = b[i+2] + c[i+1];
    a[i+3] = b[i+3] + c[i+3];
}
```

## 五、与其他技术对比

- 超标量靠硬件动态调度，兼容旧二进制；VLIW 靠编译器，硬件省面积但跨代不兼容。
- EPIC(Itanium) 是 VLIW 的失败尝试，因编译器难预测内存延迟。

## 六、常见误区

- 误以为发射宽度等于 IPC：受依赖与缓存缺失限制。
- 误以为 VLIW 不需硬件调度：仍需处理长延迟操作占位。

## 八、面试题

- 超标量与 VLIW 区别？答：前者硬件动态发射，后者编译器静态打包。
- 为何 EPIC 不成功？答：编译器难以静态隐藏内存与分支延迟。

## 九、演进与趋势

宽发射(5-6 wide)配大乱序窗口成为主流；VLIW 在 DSP/GPU 领域存活。

## 十、小结

并行发射挖掘 ILP，关键在于依赖分析与延迟隐藏，而非单纯增加宽度。
