# 幂等重试与客户端实现

> 对应 Kleppmann《Designing Data-Intensive Applications》容错与重试章节，及 RFC 9110 幂等方法定义。

## 一、背景与挑战

网络不可靠：请求可能因超时、连接重置、DNS 抖动而「结果未知」。客户端必须重试才能提高成功率，但盲目重试非幂等写操作会带来重复下单、重复扣款、重复发消息等严重问题。

难点在于区分两类失败：**确定失败**（连接未建立、明确被拒）与**不确定失败**（请求已发出但未收到响应）。后者才是「可能已生效、也可能未生效」的危险区，重试策略必须建立在其上。

## 二、核心原理

- **仅对幂等请求安全重试**：GET/PUT/DELETE，或带 `Idempotency-Key` 的 POST。
- **按失败类型决策**：
  - 连接未建立（connect 失败）：请求未到达服务端，可立即重试。
  - 已连接但超时（无响应）：结果未知，只重试幂等操作，或用幂等键让服务端去重。
  - 明确 4xx（非 408/429）：不可重试，属于请求本身问题。
  - 5xx 与 408/429：可退避重试，配合幂等保证。
- **退避策略**：指数退避 + 抖动（jitter），避免所有客户端同步重试造成「重试风暴」。
- **幂等键**：客户端为同一业务操作生成稳定唯一键，服务端据此去重并缓存首次结果。

## 三、形式化与数学基础

指数退避延迟：

$$t_i = \min\left(T_{max},\ base \cdot 2^{i}\right) \cdot \left(1 \pm jitter\right)$$

加抖动的目的：若 $n$ 个客户端无抖动地同步退避，重试负载呈脉冲式叠加；引入均匀抖动后，期望同时到达数为：

$$\mathbb{E}[\text{concurrent}] \approx \frac{n \cdot t_{retry}}{T_{window}} \ll n$$

重试放大系数（考虑每层重试）需被限流约束：

$$\beta = 1 + r + r^2 + \cdots + r^{k} = \frac{1 - r^{k+1}}{1 - r}$$

幂等保证下，重复应用的副作用不变：

$$apply^{(n)}(R) = apply^{(1)}(R)$$

## 四、代码实现

带指数退避与抖动的重试封装。

```python
import random
import time

class TransientError(Exception):
    pass

def retry(fn, tries: int = 5, base: float = 0.1, cap: float = 10.0):
    last = None
    for i in range(tries):
        try:
            return fn()
        except TransientError as e:      # 仅对可重试错误重试
            last = e
            if i == tries - 1:
                break
            delay = min(cap, base * (2 ** i))
            time.sleep(delay * (0.5 + random.random()))   # 抖动
    raise last
```

用幂等键让 POST 可安全重试。

```python
import uuid, requests

def create_order(payload, session: requests.Session):
    key = str(uuid.uuid4())              # 同一业务操作只生成一次，重试复用
    headers = {"Idempotency-Key": key}
    return retry(lambda: _post(session, "/orders", payload, headers))

def _post(session, url, payload, headers):
    resp = session.post(url, json=payload, headers=headers, timeout=5)
    if resp.status_code >= 500 or resp.status_code in (408, 429):
        raise TransientError(resp.status_code)
    resp.raise_for_status()
    return resp.json()
```

## 五、与其他技术对比

| 层次 | 机制 | 解决的问题 | 是否感知应用语义 |
| --- | --- | --- | --- |
| TCP | 超时重传 | 字节可靠传输 | 否 |
| HTTP 客户端 | 重试策略 | 请求级失败恢复 | 是（需幂等） |
| 服务网格 | 重试 + 熔断 | 基础设施级容错 | 部分 |
| 消息队列 | 至少一次 + 消费幂等 | 端到端消息处理 | 是 |

TCP 重传解决链路丢包，不解决「应用层操作是否重复」；因此即便 TCP 可靠，应用层仍可能收到重复请求（如超时后客户端重发）。

## 六、常见误区

- 误区一：超时一律重试。非幂等写在超时后重试可能重复执行。
- 误区二：重试次数越多越可靠。会放大故障（重试风暴），必须配合退避与熔断。
- 误区三：幂等键可随意生成。必须在同一业务操作内稳定且唯一；每次重试生成新键就失去了去重意义。
- 误区四：服务端收到幂等键就万事大吉。还需保证「首次执行结果」被持久化，且并发同键请求被正确处理（如唯一约束或锁）。

## 八、面试题

1. 如何安全重试 POST？答：使用 `Idempotency-Key`，由服务端去重并返回首次结果。
2. 指数退避为何要加抖动？答：避免多个客户端同步重试形成脉冲负载。
3. 什么故障该重试、什么不该？答：连接未建立与 5xx/408/429 可退避重试，明确 4xx（非 408/429）不重试；`Idempotency-Key` 由同一业务操作生成一次稳定唯一键，重试复用以供服务端去重。

## 九、演进与趋势

服务网格（如 Envoy）在代理层提供重试、超时与熔断策略；主流 API 平台广泛采用 `Idempotency-Key` 显式保证写幂等，成为标准实践。同时「重试预算」与自适应限流被用于抑制重试放大，具体参数以各产品官方文档为准。

## 十、小结

重试必须建立在幂等或去重之上，配合指数退避与抖动、限流与熔断，才能在网络波动下既保证可靠性，又不把局部故障放大成系统性雪崩。理解「确定失败 vs 不确定失败」是设计重试策略的起点。
