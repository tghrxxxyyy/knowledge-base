# 幂等重试与客户端实现

> 对应 Kleppmann《DDIA》「容错与重试」章节与 RFC 9110 关于幂等方法的说明，结合 xiaolincoder/hello-http。

## 一、背景与挑战
网络不可靠，请求可能因超时、连接中断而需要重试。但盲目重试非幂等写操作会导致重复下单、重复扣款。设计安全的重试机制必须区分操作幂等性与失败类型。

## 二、核心原理
仅对幂等请求（GET/PUT/DELETE 或带幂等键的 POST）在「不确定结果」时安全重试。对于「连接未建立」的失败可立即重试；对于「已发出但未收到响应」的超时，应仅重试幂等操作或使用 Idempotency-Key 由服务端去重。退避策略（指数退避 + 抖动）避免重试风暴。

## 三、形式化与数学基础
指数退避延迟 t_i = min(T_max, base · 2^i) · (1 ± jitter)。重试成功概率随次数上升，但重试放大系数 β = (1 + Σ r^i) 需被限流控制，避免雪崩。幂等保证下副作用 S 不变：apply_n(幂等请求) = apply_1。

## 四、代码实现
```python
import random, time
def retry(fn, tries=5):
    for i in range(tries):
        try:
            return fn()
        except TransientError:
            time.sleep(min(10, 0.1 * 2**i) * (0.5 + random.random()))
    raise
```

## 五、与其他技术对比
TCP 自身有重传但解决的是字节可靠而非应用语义；HTTP 重试位于应用层，须考虑幂等。消息队列（Kafka）以「至少一次 + 消费幂等」实现端到端正确，与 HTTP 幂等重试思想一致。

## 六、常见误区
误区一：超时一律重试——非幂等写可能重复。误区二：重试越多越可靠——会引发重试风暴。误区三：Idempotency-Key 由客户端随便生成——须在同一业务操作内稳定唯一。

## 七、与开源书/权威来源对应
Kleppmann《DDIA》第 11 章讨论幂等与重试；RFC 9110 定义幂等方法；xiaolincoder/hello-http 提及客户端重试实践；Stripe 等以 Idempotency-Key 头提供写幂等。

## 八、面试题
如何安全重试 POST？指数退避为何加抖动？什么故障该重试什么不该？Idempotency-Key 怎么用？

## 九、演进与趋势
服务网格（如 Envoy）在代理层提供重试与熔断策略；OpenAI/Stripe 等 API 广泛采用 Idempotency-Key 显式保证写幂等，成为业界标准实践。

## 十、小结
重试必须建立在幂等或去重之上，配合退避与限流，才能在网络波动下既保证可靠又不放大故障。
