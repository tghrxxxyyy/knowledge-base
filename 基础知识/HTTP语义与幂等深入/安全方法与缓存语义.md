# 安全方法与缓存语义

> 对应 RFC 9110 关于安全方法与缓存以及 Kurose & Ross 应用层 HTTP 缓存的讨论。

## 一、背景与挑战
GET 等安全方法不改变服务器状态，因此可以被代理与浏览器缓存、被预取、被重放而不产生副作用。理解安全方法与缓存的关联，对性能优化与正确性都至关重要。

## 二、核心原理
安全方法（GET、HEAD、OPTIONS、TRACE）语义上只读。缓存代理可对 GET 响应按 Cache-Control、Expires、ETag 等头部做存储与条件校验。非安全方法（POST、PUT、DELETE）默认不可被共享缓存缓存其响应（除非显式指定 Cache-Control）。

## 三、形式化与数学基础
令缓存命中率 h，则源站请求数 ≈ (1-h)·Q。安全方法可缓存使 h 显著上升；新鲜度由 max-age 或 (Date, Expires) 决定：fresh 当 now < Date + max_age。条件请求用 If-None-Match 校验，命中返回 304 省带宽。

## 四、代码实现
```http
HTTP/1.1 200 OK
Cache-Control: max-age=3600
ETag: "abc123"
```
```http
GET /r HTTP/1.1
If-None-Match: "abc123"
# 未变则 304 Not Modified
```

## 五、与其他技术对比
CDN 本质是分布式的 GET 缓存层；而 POST 表单提交通常绕过缓存。GraphQL 多用 POST 单端点，需额外设计缓存键（如按 query 哈希），与 REST 的 GET 缓存天然性不同。

## 六、常见误区
误区一：HEAD 没有缓存价值——HEAD 可用来探测资源存在与元信息。误区二：POST 绝不缓存——带 Cache-Control 时可。误区三：安全方法一定快——仍受带宽与序列化约束。

## 七、与开源书/权威来源对应
RFC 9110 第 9.2 节定义 safe 方法；xiaolincoder/hello-http 讨论缓存头；Kurose & Ross 在 HTTP 章节介绍条件 GET 与代理缓存。

## 八、面试题

## 九、演进与趋势
HTTP/3 不改变缓存语义；边缘计算与 stale-while-revalidate 等指令让缓存策略更精细；部分框架开始对只读 POST 显式声明可缓存。

## 十、小结
安全方法因其只读语义天然可缓存，配合 ETag/If-None-Match 等条件请求可实现高效且一致的内容分发。
