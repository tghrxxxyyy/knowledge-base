# 安全方法与缓存语义

> 对应 RFC 9110 第 9.2 节安全方法与 RFC 9111《HTTP Caching》，并参考 Kurose & Ross 应用层缓存讨论。

## 一、背景与挑战

GET 等安全方法不改变服务器状态，因此可以被浏览器、代理与 CDN 缓存，也可以被预取、被安全重放而不产生副作用。这种「只读」特性是 Web 可扩展性的根基：一次源站生成，千万次边缘命中。

但安全与缓存并非自动绑定——缓存与否还取决于响应头。理解二者的关联，对性能优化与正确性同样重要，因为错误地把非安全方法当作可缓存，会造成「删除后仍命中」这类严重不一致。

## 二、核心原理

- **安全方法**：GET、HEAD、OPTIONS、TRACE，语义上只读。
- **可缓存性由响应头决定**：`Cache-Control`、`Expires`、`ETag`、`Last-Modified`、`Vary` 等。
- **GET 响应**默认可被共享缓存存储与复用；**HEAD 响应**可缓存其头部元信息；**OPTIONS/TRACE** 通常不被缓存。
- **非安全方法**（POST、PUT、DELETE、PATCH）的响应默认不被共享缓存缓存，除非显式给出 `Cache-Control`。POST 响应在少数实现中可被缓存以便重放，但语义受限。
- **条件校验**：缓存过期后用 `If-None-Match` 向源站校验，命中返回 304，省去重传 body。

## 三、形式化与数学基础

设请求到达率为 $Q$，缓存命中率为 $h$，则源站请求数近似为：

$$Q_{origin} \approx (1 - h) \cdot Q$$

安全方法可缓存使 $h$ 显著上升，从而降低源站负载。新鲜度由 `max-age` 或 `(Date, Expires)` 决定：

$$fresh \iff now < Date + max\_age$$

若已过期则进入校验阶段，校验命中（304）的带宽成本约为：

$$BW_{304} \approx size(headers) \ll size(headers) + size(body) = BW_{200}$$

`Vary` 头把缓存键从 URL 扩展到若干请求头，即：

$$key = (URL,\ \{h : h \in Vary\})$$

## 四、代码实现

源站为 GET 响应设置缓存与校验头。

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=3600
ETag: "abc123"
Vary: Accept-Encoding
Content-Type: application/json

{"id": 1, "name": "demo"}
```

客户端在缓存过期后发起条件请求。

```http
GET /resource HTTP/1.1
Host: example.com
If-None-Match: "abc123"
```

源站若版本未变，返回无 body 的 304，客户端沿用本地副本。

```http
HTTP/1.1 304 Not Modified
ETag: "abc123"
Cache-Control: public, max-age=3600
```

服务端设置缓存头的常见方式（以框架中间件为例）。

```python
@app.after_request
def add_cache_headers(resp):
    if request.method in ("GET", "HEAD") and resp.status_code == 200:
        resp.headers["Cache-Control"] = "public, max-age=60"
    else:
        resp.headers["Cache-Control"] = "no-store"   # 非安全方法默认不缓存
    return resp
```

## 五、与其他技术对比

| 维度 | REST + GET 缓存 | GraphQL（单端点 POST） | CDN |
| --- | --- | --- | --- |
| 默认可缓存 | 是（GET） | 否（POST） | 是（面向 GET） |
| 缓存键 | URL（+Vary） | 需按 query 哈希自定义 | URL + 边缘规则 |
| 失效控制 | Cache-Control/ETag | 应用层自定义 | purge/invalidate API |
| 语义天然性 | 高 | 低 | 高 |

CDN 本质是分布式的 GET 缓存层；GraphQL 需要额外的缓存键设计（如持久化查询 + 哈希）。

## 六、常见误区

- 误区一：HEAD 没有缓存价值。HEAD 可缓存元信息，用于探测资源存在性与大小。
- 误区二：POST 绝不缓存。显式 `Cache-Control` 下可缓存其响应，但需谨慎对待重放语义。
- 误区三：安全方法一定快。仍受带宽、序列化与源站计算约束，缓存未命中时照样慢。
- 误区四：缓存只看 max-age。还需考虑 `Vary`、`private`/`public`、`no-store` 等的组合语义。

## 八、面试题

1. 哪些是安全方法？答：GET、HEAD、OPTIONS、TRACE。
2. 为什么安全方法可被缓存？答：只读语义使其可安全重放，重复使用不改变服务器状态。
3. 304 的作用？答：告知客户端缓存仍新鲜，省去重传 body。
4. `Cache-Control` 与 `Expires` 的区别？答：前者相对时间且优先级更高，后者是绝对时间、受时钟影响。

## 九、演进与趋势

HTTP/2、HTTP/3 不改变缓存语义；边缘计算与 `stale-while-revalidate`、`stale-if-error` 等指令让缓存策略更精细。部分框架开始为只读的 POST 显式声明可缓存，但需业务确认语义安全。

## 十、小结

安全方法因其只读语义天然适合缓存，配合 ETag/If-None-Match 等条件请求，可实现高效且一致的内容分发。关键判据是：方法是否只读，以及响应头是否显式允许缓存。
