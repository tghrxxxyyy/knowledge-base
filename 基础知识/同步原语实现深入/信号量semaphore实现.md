# 信号量semaphore实现

> 对应 Bryant & O'Hallaron《CSAPP》第 12 章；Love《Linux Kernel Development》第 10 章。

## 一、背景与挑战

互斥只保护单一临界区，而需限制并发访问数量（如连接池上限、生产者消费者缓冲）或跨进程同步时，需信号量：一个计数值 + P/V 原子操作。信号量以「许可计数」抽象了限流与事件通知，是比互斥更通用的同步原语。

其复杂性在于「计数」与「等待队列」必须作为一个整体被原子维护。若把「减计数」与「入队睡眠」分成两步，两个线程可能同时看到 $s=1$、都进入临界区；若把「加计数」与「唤醒」分开，可能出现「唤醒了但许可已被别人拿走」的虚假唤醒，导致被唤醒者再次睡下，反复往返浪费 CPU。正确性全部落在这一对原子的边界上。

## 二、核心原理

`sem_wait`（P）：原子减计数，若 $<0$ 则睡眠入等待队列；`sem_post`（V）：原子加计数，若有等待者则唤醒一个。计数初值即许可数，可用于限流（N 个资源）或事件通知（0/1 二值）。P/V 必须在内部锁保护下完成，确保「计数变更」与「队列操作」不被打断，避免丢失唤醒（V 在释放等待队列锁内完成）。

语义上还要区分「模型两种」：Dijkstra 定义的经典信号量中计数可为负，负值的绝对值即等待线程数；POSIX 与 Linux 实现通常把「计数」与「等待者数」分离记录，效果一致但可观测字段不同。二值信号量（$N=1$）可当互斥用，但它不记录持有者，因此不能实现「仅持有者可释放」这一约束，也无法做优先级继承。

## 三、形式化与数学基础

不变量：

$$0 \le permits \le N,\quad 临界并发数 \le N$$

P/V 操作：

$$P:\ s=s-1;\ if\ s<0\ sleep$$
$$V:\ s=s+1;\ if\ s\le 0\ wake$$

正确加锁保证无丢失唤醒（V 在持有等待队列锁时执行 wake）。二值信号量（$N=1$）即互斥语义。

| 场景 | 初值 | 语义 |
| --- | --- | --- |
| 互斥 | 1 | 二值信号量，进入/离开 |
| 限流（N 资源） | N | 同时最多 N 个持有者 |
| 事件通知 | 0 | V 置位、P 等待事件 |
| 生产者消费者 | 空槽数 / 满槽数 | 两个信号量配对 |

## 四、代码实现

```c
sem_t sem; sem_init(&sem, 0, 4);   // 最多 4 个并发
void worker(void) {
    sem_wait(&sem);                 // P：申请许可
    use_resource();
    sem_post(&sem);                 // V：归还许可
}
// 二值信号量即互斥
sem_t m; sem_init(&m, 0, 1);
```

POSIX 信号量 `sem_wait` 底层亦结合 futex 优化无冲突快路径。

```c
// 生产者-消费者：用两个信号量表达「空槽」与「满槽」
sem_t empty, full;                 // empty 初值 = 缓冲容量，full 初值 = 0
sem_init(&empty, 0, CAP); sem_init(&full, 0, 0);
void producer(void) {
    sem_wait(&empty);              // 等空槽
    put(buf, item);
    sem_post(&full);               // 通知有数据
}
void consumer(void) {
    sem_wait(&full);               // 等数据
    item = get(buf);
    sem_post(&empty);              // 归还空槽
}
// 注意：P 的顺序在「需同时等待多个条件」时会影响死锁可能性
```

## 五、与其他技术对比

| 原语 | 能否计数 | 跨进程 | 自带谓词 | 易错点 |
| --- | --- | --- | --- | --- |
| 信号量 | 能 | 命名 sem 可 | 是（计数） | 忘记 V 永久阻塞 |
| 互斥锁 | 否 | 通常同进程 | 否 | 重入死锁 |
| 条件变量 | 否 | 同进程 | 需自维护 | 漏 while 重查 |

信号量可计数、可跨进程；互斥锁不可计数、通常同进程。相较条件变量，信号量自带计数不需额外谓词。易误用（忘记 V 永久阻塞）。

| 实现形态 | 位置 | 特点 |
| --- | --- | --- |
| POSIX 匿名 `sem_init` | 进程内 | 快、可不落盘 |
| POSIX 命名 `sem_open` | `/dev/shm` | 可跨进程 |
| System V `semop` | 内核 | 支持一次操作多个信号量 |
| 内核 `struct semaphore` | 内核 | 可睡眠，用于不可自旋处 |

## 六、常见误区

1. 误以为信号量等于互斥锁——信号量可计数、可跨进程（命名 sem），互斥锁仅互斥。
2. 误以为 P 一定睡——计数 $>0$ 时直接过，仅当无许可才睡眠。
3. 误以为 `sem_post` 在信号上下文安全——取决于具体实现，内核 `up()` 通常可，但用户态需查文档。
4. 误以为二值信号量能替代互斥锁——它不记录持有者，无法保证「谁能释放」，也无法做优先级继承。
5. 误以为 V 可以随意多调用——过量的 V 会让计数超出初值，等于凭空发放许可，破坏限流语义。
6. 误以为 POSIX 信号量可被 `fork` 后共享——匿名信号量在 `fork` 后为两份副本；跨进程须用 `sem_open` 或共享内存中的 `pshared=1` 实例。

## 八、面试题

1. 用信号量如何实现互斥？答：初值 1 的二值信号量，P 进入临界区、V 离开，保证同时只有一个线程进入。
2. P/V 为何必须原子？答：计数变更与队列操作必须整体完成，否则两线程可能同时看到 $s=1$ 都进入、或 V 唤醒丢失。
3. 信号量与条件变量本质区别？答：信号量自带计数与「许可」语义，条件变量需外部谓词 + 互斥配合。
4. 生产者消费者为何需要两个信号量？答：一个表达「可用空槽数」、一个表达「可用数据数」，分别约束生产与消费的阻塞条件。
5. 二值信号量为何不能替代 mutex？答：它不记录持有者，任何线程都能 V，无法保证互斥的「仅持有者释放」语义。
6. 忘记 `sem_post` 的后果？答：许可永久泄漏，后续等待者可能永不被唤醒（永久阻塞）。

## 九、演进与趋势

`sem_wait` 结合 futex 优化无冲突快路径；读优先/写优先信号量用于读写场景；内核 `struct semaphore` 用于不可自旋的睡眠同步；user-space 信号量库（如 libatomic_ops）提供无系统调用近似。

实践中的趋势是「减少裸信号量、强化语义封装」：语言运行时的通道（Go channel）、`BlockingQueue`（Java）、有界 mpsc（Rust）都把「计数 + 阻塞」封装为更高层抽象，避免手动 P/V 配对出错；内核侧则用完成量（completion）、`mutex`、`rwsem` 等更专用原语取代通用信号量，以表达更强的语义约束（如所有者语义、可中断等待）。

## 十、小结

信号量以计数 + 原子 P/V 提供限流与同步原语，是经典并发控制工具。理解「计数即许可、P/V 配对」方能避免永久阻塞与丢失唤醒。工程上宜遵守三条纪律：每次 P 必有对应 V（含异常路径）、不滥用 V 越过初值上限、跨进程场景务必使用共享可见的信号量实例而非 `fork` 出来的副本。
