# 条件变量与生产者消费者

> 对应 Bryant & O'Hallaron《CSAPP》第 12 章；Kerrisk《The Linux Programming Interface》第 30 章；OSTEP 同步章。

## 一、背景与挑战

仅用互斥锁无法表达「条件不满足就等待」——若用互斥 + 忙等轮询，会空转浪费 CPU 且可能优先级反转。条件变量（condvar）配合互斥，让线程在谓词不满足时原子地释放锁并睡眠，被唤醒后再重新检查，是生产者消费者、线程池、阻塞队列的核心同步原语。它解决的是「丢失唤醒（lost wakeup）」问题：若先发信号再等待，信号已发出而等待者尚未入睡，便会永久睡死——condvar 用「原子释锁+入睡」消除这个窗口。

另一个动机是「避免优先级反转与忙等浪费」：忙等不仅烧 CPU，还会在单核或超售环境下让需要运行的线程拿不到时间片，形成活锁式退化；睡眠等待则把 CPU 让给真正能推进工作的线程。

## 二、核心原理

`pthread_cond_wait` 原子地完成「释放互斥 + 睡眠」，醒来时重新获取互斥；`pthread_cond_signal` 唤醒至少一个等待者，`pthread_cond_broadcast` 唤醒全部。关键纪律：对谓词（如队列非空）的读写必须在同一互斥保护下进行；wait 前持锁，wait 返回后仍持锁。必须用 `while` 而非 `if` 重查谓词——抵御虚假唤醒（spurious wakeup）与多个消费者被 broadcast 唤醒后的惊群。condvar 自身不存储任何状态，它只是「等/醒」的机制，谓词状态由你自己的共享变量维护。

「原子释锁 + 入睡」之所以关键，是因为它把两个动作合并为一个不可分割的步骤。若分成两步（先解锁再睡眠），中间就会出现「信号已发但线程未睡」的窗口，导致永久睡眠——这正是 condvar 必须由系统调用（配合 futex）提供而无法用纯用户态变量模拟的根源。

## 三、形式化与数学基础

管程（monitor）不变量：

$$hold(mutex)\ \land\ pred\ \text{在锁内检查}$$

唤醒协议（单生产者单消费者）：
$$producer:\ lock;\ buf.push(x);\ signal;\ unlock$$
$$consumer:\ lock;\ while(empty)\ wait(mutex);\ x=buf.pop();\ unlock$$

`while` 而非 `if` 抵御虚假唤醒与多消费者抢空，保证醒来后谓词仍成立才继续。形式上，`wait` 把线程加入条件队列并释放 `mutex`，`signal` 把队列中一线程移回就绪队列（仍持锁时调用），二者均在 `mutex` 保护下，避免丢失唤醒。

正确性可用两个不变式刻画：一是「谓词只能在持锁时被修改」，二是「等待必须发生在谓词检查之后且在同一次持锁周期内」。任何破坏其一的设计（如无锁修改谓词、先 signal 后 wait）都会引入丢失唤醒或数据竞争。

## 四、代码实现

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;
queue_t q;
// 生产者
void producer(int x) {
    pthread_mutex_lock(&m);
    queue_push(&q, x);
    pthread_cond_signal(&c);     // 锁内改谓词并通知
    pthread_mutex_unlock(&m);
}
// 消费者
void *consumer(void *arg) {
    for (;;) {
        pthread_mutex_lock(&m);
        while (queue_empty(&q))                 // while 防虚假唤醒/惊群
            pthread_cond_wait(&c, &m);          // 原子释锁并睡
        int x = queue_pop(&q);
        pthread_mutex_unlock(&m);
        consume(x);
    }
}
```

```c
// 带超时的等待：避免永久阻塞，便于优雅退出
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
ts.tv_sec += 1;                                  // 1 秒超时
int rc = pthread_cond_timedwait(&c, &m, &ts);
if (rc == ETIMEDOUT) { /* 检查退出标志，决定是否继续等 */ }
```

多生产者时建议用 `pthread_cond_broadcast` 或在 push 后 signal，避免单 signal 只唤醒一个而多个新元素无人消费的情况（虽 while 重查可自愈，但吞吐略降）。可改用 `pthread_cond_timedwait` 加超时防止永久阻塞。

## 五、与其他技术对比

| 原语 | 是否睡眠 | 是否需谓词 | 适用 |
| --- | --- | --- | --- |
| 条件变量 | 是 | 是（while 检查） | 通用阻塞同步 |
| 信号量 | 是 | 否（自带计数） | 限流/计数同步 |
| 自旋+条件 | 否（忙等） | 是 | 极短等待 |
| 屏障（barrier） | 是 | 否（固定参与者） | 阶段同步 |

条件变量需配互斥与谓词；信号量可替代但易漏唤醒。相较 RCU，condvar 用于通用同步而非读多写少。

## 六、常见误区

1. 误以为 `if` 判断够——虚假唤醒致错，多消费者 broadcast 时也需 while 重查。
2. 误以为 `signal` 前需持锁——标准允许不在锁内 signal，但常见做法在锁内改谓词并 signal，避免丢失唤醒。
3. 误以为 condvar 自带状态——它无内存，只负责「等/醒」，谓词状态须自己用共享变量维护。
4. 误以为 `wait` 返回即谓词成立——可能被广播或虚假唤醒，必须重查。
5. 误以为 signal 一定唤醒正确线程——只保证唤醒一个，不保证是哪个，故谓词须对「任一被唤醒者」都成立。
6. 误以为 signal 一定要用 broadcast——broadcast 会引发惊群，除非确有多个等待者可被同一事件满足，否则优先 signal。

## 八、面试题

1. 为什么 `cond_wait` 要用 `while` 而非 `if`？答：防虚假唤醒、多消费者被 broadcast 唤醒后抢空，醒来后必须重查谓词。
2. `signal` 何时调用？答：在持锁改完谓词后调用，确保等待者醒来时谓词可能已满足，避免丢失唤醒。
3. 丢失唤醒是什么？答：若先 `signal` 后等待者 `wait`，信号已发完，等待者永久睡死——故必须先持锁检查再 wait。
4. 为何 condvar 必须与 mutex 配合？答：谓词检查与等待需原子，mutex 提供临界区，wait 内部原子释锁入睡。
5. condvar 与信号量如何选择？答：condvar 用于「等待条件成立」，需自管谓词；信号量用于「计数与限流」，自带计数但语义较粗。
6. 为什么 condvar 无法用纯用户态变量实现？答：它需要「释锁与入睡」的原子性，必须借助内核的等待队列（如 futex）才能消除丢唤醒窗口。

## 九、演进与趋势

`pthread_cond_clockwait` 支持指定时钟的超时；底层用 futex 使快路径（无竞争）更省；C++ `std::condition_variable` 提供 RAII 封装；「状态 + condvar」模式演进为更高层的 `std::future`/channel。Rust 的 `condvar` 还强制与 `MutexGuard` 绑定，防止忘记持锁。

另一个方向是把「谓词 + 等待」的模式提升为语言级抽象：通道（channel）、消息队列、异步运行时的唤醒器等，把易错的手写 while/wait 隐藏在库内。但底层语义仍是同一套——理解 condvar 的丢唤醒与假唤醒，仍是排查上层抽象疑难问题的必要基础。

## 十、小结

条件变量以「锁内谓词 + 等待/唤醒」实现高效阻塞同步，是生产者消费者模型的标准解法。`while` 重查与锁内 signal 是正确性的两根支柱，而超时等待与 signal/broadcast 的选择则决定了系统的健壮性与吞吐。
