# 异常处理与栈展开机制

> 对应 System V AMD64 ABI（DWARF / `.eh_frame` unwind 规范）；Itanium C++ ABI 异常条款；libunwind 实现；GCC `-fexceptions` 文档。

## 一、背景与挑战

抛出异常时，运行时必须沿调用链**回退多帧**，为每一帧恢复寄存器状态、执行局部对象的析构（cleanup），并最终把控制流交到匹配的 `catch` 处理器。难点在于：栈帧千差万别（优化后甚至没有帧指针），运行时无法靠「猜」还原每一帧。因此需要一份**机器可读的元数据**，精确描述「在函数的任意指令点，如何恢复调用者的寄存器」，这就是 unwind 信息。没有它，异常机制无从谈起。

难点还在于「任意指令点」这一要求：同一个函数在执行过程中，栈帧布局会随指令推进而变化（例如序言中逐步 push、尾声逐步 pop，中间还可能有 `sub rsp` 调整）。因此 unwind 元数据不是「每函数一条」，而是「按 PC 区间分段」——这正是 FDE 内部由多条 CFI 指令构成、并覆盖不同地址范围的原因。

## 二、核心原理

编译器为每个函数生成 `.eh_frame` 段，其内部的 FDE（Frame Description Entry）基于 DWARF CFI（Call Frame Information）规则，记录本帧如何在任意 PC 点恢复 caller 的 rsp/rbp/rip 及被保存寄存器。抛出异常时，libunwind（或语言运行时的等效实现）从当前上下文出发，反复执行「查 FDE → 按 CFI 指令恢复上一帧寄存器 → 检查着陆区（landing pad）是否匹配 catch 类型」的循环，直到找到处理器；若一路 unwind 到栈底仍无匹配，则调用 `std::terminate`。C++ 的**零开销异常（zero-cost exception）**指：正常路径不付出查询代价，仅在真正抛出时才走 unwind 表。异常表本身占用空间，但不影响正常指令的执行速度。

「两阶段展开（two-phase unwinding）」是 C++ 异常语义的关键机制：第一阶段只做「查找」，沿栈向上扫描，判断是否存在能处理该异常的帧，但**不执行**任何 cleanup；只有确认找到处理器后，第二阶段才真正展开并执行各帧的析构与 cleanup。这样设计是为了避免「先析构再发现没人接、于是 terminate」的尴尬——若只有一阶段，就可能出现「已释放资源却无法恢复」的情况。

## 三、形式化与数学基础

栈展开是一串状态转移，每步由 CFI 指令驱动：

$$
state_{i+1} = unwind(CFI_i, state_i)
$$

每一步恢复 $\{rsp, rbp, rip\}$ 到调用者视角，并用 LSDA（Language-Specific Data Area）里的类型表判定当前帧是否含匹配 `catch`：

$$
match \iff type(T_{thrown}) \in CatchSet(landing\_pad_i)
$$

若匹配则停止并跳转到对应 landing pad；否则继续，直至终止（`std::terminate`）。CFI 以「相对上一帧的偏移增量」表达，因此 unwind 只需局部推理，无需全局重算。

「增量表达」这一点是性能关键：设第 $i$ 帧的 CFA（Canonical Frame Address）为 $CFA_i$，CFI 只需给出 $\Delta_i = CFA_{i-1} - CFA_i$ 之类的相对量，因而每步的计算都是常数时间的局部运算，总复杂度与帧数 $n$ 成线性关系 $O(n)$。若元数据采用绝对地址表达，则每帧都需重定位与全局符号解析，unwind 会退化为「每次抛出都要扫全表」的高开销操作。

## 四、代码实现

```c
/* libunwind 风格的手动走查（示意） */
#include <libunwind.h>

void walk(void) {
    unw_cursor_t cur;
    unw_context_t uc;
    unw_getcontext(&uc);
    unw_init_local(&cur, &uc);
    do {
        unw_step(&cur);              /* 退一帧，按 FDE 恢复寄存器 */
    } while (!matches_handler(&cur)); /* 直到找到匹配 catch 的着陆区 */
    /* 由运行时跳转到 landing pad 执行 cleanup / catch */
}
```

```c
/* 析构函数在展开途中的安全性：绝不可让析构再抛异常 */
struct Guard {
    ~Guard() {
        /* 必须确保此处不会抛异常；若抛，第二次异常会导致 terminate */
        release_resource_noexcept();
    }
};

/* 反例（不要这样做）：析构中可能抛出 */
struct BadGuard {
    ~BadGuard() { /* 可能 throw */ risky_close(); }
};
```

这一段强调了「展开期间异常」这条硬规则：当异常正在传播、逐帧执行析构时，若某个析构函数再次抛出异常，运行时无法同时处理两个异常，只能直接 `terminate`。因此 C++ 的惯例是让析构函数（以及 cleanup 路径上的代码）隐含 `noexcept`——这不是风格偏好，而是展开机制的结构性要求。与之对照，C++ 的 `try { throw ... } catch (...)` 之所以能「跳进」某个帧，正是因为第一阶段已用 LSDA 确认该帧存在匹配的 landing pad。

## 五、与其他技术对比

| 类型安全 | 无 | 有（按类型匹配） | 有 | 依 payload 类型 |

## 六、常见误区

1. 以为异常「不耗性能」——unwind 表占用二进制空间，抛出时走查代价高，热路径应避免抛出。
2. 析构在栈展开中**必然**被调用，资源泄漏要靠 RAII 而非裸指针管理。
3. 用 `strip --strip-unwind` 或 `-fno-exceptions` 剥离 unwind 信息后，抛出会在 unwind 时崩溃。
4. 误以为 `catch(...)` 能捕获一切——栈展开本身的错误（如析构抛异常）会直接 `terminate`。
5. 以为 unwind 能跨语言边界——C 函数无异常处理表，C++ 异常穿过 C 栈帧时依赖其 unwind 表仍能工作，但 C 代码本身不能 `throw`。
6. 认为两阶段展开是多余开销：它正是为了避免「先析构才发现无人捕获」的不可恢复状态。
7. 在析构函数中抛出异常：展开期间二次异常会立即 terminate，是常见崩溃根因。
8. 忽略优化对 CFI 的影响：编译器内联、尾调用、`-fomit-frame-pointer` 都会改变帧结构，CFI 必须随之更新，否则 unwind 走错帧。

## 八、面试题

1. 栈展开如何工作？答：运行时按 `.eh_frame` 的 CFI 指令逐帧恢复 caller 的寄存器，并用 LSDA 判定是否匹配 catch，匹配则跳转 landing pad。
2. `.eh_frame` 的作用？答：以 DWARF CFI 描述每个函数在任意 PC 点如何恢复上一帧的寄存器，是 unwind 的地图。
3. 「零开销异常」含义？答：正常执行路径不付出异常查询成本，代价仅在真正抛出异常、执行 unwind 时才产生。
4. 为何不能剥离 unwind 信息？答：异常抛出时依赖它逐帧恢复，缺失会导致 unwind 失败并 terminate。
5. 什么是两阶段展开？答：第一阶段沿栈查找匹配处理器（不执行 cleanup），确认后再在第二阶段展开并执行析构。
6. 为什么析构函数不能抛异常？答：展开期间已有异常在传播，二次异常无法并存，运行时会直接调用 terminate。

## 九、演进与趋势

macOS 采用 compact unwind 格式加速查表；Windows 使用完全不同的 `UNWIND_INFO` / `.pdata` 体系；Rust 的 `panic` unwind 复用类似的 CFI 机制但更强调 `abort` 与 `unwind` 两种策略。未来方向包括更紧凑的 unwind 编码与面向安全的 CFI 集成。具体实现细节以官方最新文档为准。

值得注意的是，unwind 机制与前面讨论的返回地址保护存在交汇：影子栈在展开时必须同步更新，否则「正常展开」会被硬件误判为攻击。同理，异常展开与协程、async/await 等机制的交互也需要统一的栈管理协议。

## 十、小结

异常处理依赖 CFI 元数据做栈展开，把控制流从抛出点安全回退到匹配的 `catch` 处理器，并在途中正确析构每个栈帧的对象。它用「正常路径零开销、异常路径可暂停」的折中，换来了结构化错误处理的能力——代价是二进制中必须保留精确的 unwind 地图。

三条实践要点：热路径避免抛异常（走查代价高）、析构与 cleanup 路径必须不抛（否则 terminate）、任何剥离或压缩都可能破坏 unwind（需谨慎）。
