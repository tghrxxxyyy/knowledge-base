# 栈帧布局与返回地址保护

> 对应 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 3.7、3.10 节；System V AMD64 ABI；GCC 文档 `-fstack-protector` / `-fcf-protection` 选项；Intel CET 规范。

## 一、背景与挑战

返回地址是栈上最敏感的数据：函数返回时处理器从 `[rsp]`（或 `[rbp+8]`）取出它跳回调用者，一旦该值被篡改，控制流即被劫持。经典的栈溢出攻击正是利用 `strcpy` 之类不检查长度的函数，把局部缓冲区写穿、覆盖返回地址，使其指向注入的 shellcode。ABI 既要约定帧布局让调用/返回可预测，又要提供机制在运行时检测并阻断这类篡改。现代攻击还引入了「信息泄露 + 部分覆盖 + 绕过 ASLR」的组合，单一防护已不足以应对。

防护与攻击的对抗本质上是一场「信息不对称」博弈：防护方希望攻击者不知道金丝雀值、不知道地址布局；攻击方则通过格式化串漏洞、越界读等手段窃取这些信息。因此防护设计必须假设「信息可能泄露」，并在此基础上提供即使信息泄露也无法绕过的机制——影子栈正是这一思路的产物。

## 二、核心原理

开启帧指针时，栈帧布局为：返回地址在 `[rbp+8]`，保存的旧 rbp 在 `[rbp]`，局部变量在 `[rbp-...]` 向下生长。两套主流防护叠加提供纵深防御：其一是**栈金丝雀（stack canary）**，编译器在返回地址之前插入一个随机值（Linux 上取自 `fs:0x28`，即 TLS 中的 stack canary 槽），函数尾声比对，若被改则调用 `__stack_chk_fail` 终止；其二是**影子栈（shadow stack）**，把「真正的」返回地址另存于一块受保护（硬件只读/受限写）的内存页，每次 `ret` 时比对栈上与影子栈的值，不符则陷入异常（#CP）。二者互补：canary 廉价但可被信息泄露绕过，影子栈强但需硬件与编译协同，且对老二进制兼容性需特殊处理。在开启 `-fomit-frame-pointer` 优化的函数里，rbp 被挪作通用寄存器，返回地址直接位于当前 `rsp` 处，但 canary 与影子栈的防护逻辑不变。

金丝雀的设计细节值得注意：其最低字节通常被置为 `0x00`（即所谓「terminator canary」）。这不是安全需要，而是功能需要——因为溢出攻击常用 `strcpy` 等字符串函数，`0x00` 会终止写入，从而让攻击者无法在不破坏金丝雀的情况下继续覆盖后面的返回地址。这一细节体现了「对抗真实攻击手法」而非「对抗抽象攻击模型」的设计哲学。

## 三、形式化与数学基础

金丝雀校验在返回前执行：

$$
\text{if } *(rbp - cansize) \neq canary_{rand} \Rightarrow \_\_stack\_chk\_fail()
$$

影子栈返回校验：

$$
\text{if } shadow[sp] \neq code[retaddr] \Rightarrow \#CP\ \text{(Control Protection fault)}
$$

其中影子栈由硬件以 `WRSS` 等指令受限写入，普通数据写入（包括被劫持的 `mov`）无法改到它，因此即便栈指针被篡改也无法伪造影子栈内容。两者独立判断，构成纵深防御，任一发现异常即终止进程。

从概率角度可以量化金丝雀的强度：若金丝雀为 $n$ 字节（排除固定 `0x00` 后约 $8n-8$ 位随机），则盲猜测中金丝雀的正确概率约为 $2^{-(8n-8)}$。以 8 字节金丝雀为例，排除末位 0 后约 56 位随机，盲猜成功率低于 $10^{-16}$——因此金丝雀的安全性完全依赖「值不被泄露」而非「值难猜」。这解释了为什么「一次泄露 + 一次写入」的组合就足以绕过它，也说明为何影子栈这种「不依赖保密性」的机制更根本。

## 四、代码实现

```asm
# 开启 -fstack-protector 的函数尾声（x86-64）
mov   rax, fs:0x28       ; 取本线程随机金丝雀
mov   [rbp-8], rax       ; 存于返回地址之前
...                      ; 函数体（可能溢出 [rbp-8] 之上的缓冲）
mov   rdx, [rbp-8]
xor   rdx, fs:0x28       ; 与原始值异或比较
jne   __stack_chk_fail   ; 不等则说明被覆盖
leave
ret
```

```asm
# 启用 CET 影子栈的函数入口/出口（示意）
endbr64                 ; 合法间接分支入口标记
push  rbp
...                     ; 返回地址同时写入普通栈与影子栈
pop   rbp
endbr64                 ; （示意）ret 时硬件比对两处返回地址
ret
```

```asm
# 影子栈的另一用途：setjmp/longjmp 与异常展开时同步恢复
# 展开到某帧时，硬件会用影子栈中的值覆盖普通栈上的返回地址，
# 从而保证「即使普通栈被篡改，返回仍回到函数真正调用者的下一句」
restore_shadow_sp:      ; 示意：把 shadow sp 与普通 rsp 对齐
incsspq 1               ; 弹出 1 项影子栈条目（栈收缩）
ret
```

第三段展示了影子栈在非攻击场景下的价值：异常展开、`longjmp` 等操作需要「跨帧跳转」，此时正确的返回地址应以影子栈为准。这也意味着影子栈与 C++ 异常、协程、信号处理等机制存在交互，实现时必须统一协调，否则会出现「正常程序被误判为攻击」或反之的问题。

## 五、与其他技术对比

| 维度 | 栈金丝雀 | 影子栈 (CET) | ASLR | CFI（前向边） |
|------|----------|--------------|------|---------------|
| 防护目标 | 检测返回地址被改 | 阻止返回地址被改 | 提高地址不可预测性 | 限制合法跳转目标 |
| 开销 | 每函数几条指令 | 硬件读写 + 比对 | 几乎无运行开销 | 依实现而定 |
| 绕过风险 | 金丝雀泄露后可重放 | 需同时攻破硬件保护 | 信息泄露可削弱 | 依粒度而定 |
| 兼容性 | 通用 | 需 CPU/内核支持 | 通用 | 需重编译 |
| 对抗什么 | 栈溢出写 | 返回地址篡改 | 代码复用攻击 | 任意跳转劫持 |

## 六、常见误区

1. 以为 `-fstack-protector` 覆盖所有函数——默认仅对**含字符数组**的函数插桩，可用 `-fstack-protector-strong` / `-all` 扩大范围。
2. 忽略金丝雀来源 `fs:0x28` 是**每线程**随机的，同一进程内多线程值不同。
3. 关闭保护编译历史代码会复活漏洞；剥离 unwind/保护信息可能使防护失效。
4. 误以为 ASLR 单独足以防劫持——它只增加难度，仍需 canary/影子栈做运行时检测。
5. 以为影子栈开启后旧二进制自动受保护——需重编译并内核支持，且需处理「Legacy 栈与影子栈同步」的边界情况。
6. 以为 `-fomit-frame-pointer` 会破坏防护——返回地址仍在栈顶，canary/影子栈机制与之无关。
7. 认为金丝雀能防所有溢出：它只保护返回地址，覆盖局部变量、函数指针、GOT 表等仍可造成危害。
8. 忽略防护与异常/协程的交互：影子栈需与 unwind 机制协同，否则正常展开可能触发 #CP。

## 八、面试题

1. 金丝雀如何防溢出？答：在返回地址前放随机值，函数返回前校验，被改则中止，阻止跳到恶意地址。
2. 影子栈的原理与局限？答：真返回地址存于受保护页，`ret` 比对；强但需硬件/内核支持，且旧代码需重编译。
3. 为何返回地址如此危险？答：它直接决定控制流去向，覆盖它即可劫持执行路径。
4. `-fstack-protector` 默认对哪些函数生效？答：仅含字符/聚合数组、可能被溢出的函数，故高安全场景应改用 `-strong`。
5. 金丝雀末字节为何常为 0？答：使字符串类溢出函数在该字节处终止写入，攻击者无法在保留金丝雀的前提下继续覆盖返回地址。
6. 金丝雀与影子栈的防护逻辑有何本质区别？答：金丝雀是「检测」（依赖值保密），影子栈是「阻断」（依赖硬件保护），后者在信息泄露后仍有效。

## 九、演进与趋势

Intel CET 提供硬件影子栈与间接分支追踪（IBT），在 ret / 间接跳转/调用处强制校验；Linux 内核自 5.x 起逐步支持用户态影子栈。编译器侧把 `-fcf-protection` 与 canary 结合，形成「检测 + 阻断」双重控制流完整性（CFI）体系，并向更细粒度的前向边 CFI 与细粒度 CFI 演进。具体支持范围以官方最新文档为准。

另一条趋势是把防护扩展到硬件层面的隔离机制：如内存标签（MTE、MPK）为指针附加标签并校验，从根源上阻止越界与类型混淆；这些机制若与影子栈同时部署，可使「控制流劫持」与「数据越界」两条主要攻击路径同时受限。

## 十、小结

返回地址是栈上最敏感的数据。栈金丝雀以廉价插桩做「篡改检测」，硬件影子栈以受保护内存做「篡改阻断」，二者在 ABI 与 ISA 层面共同构成控制流防护的基石。理解帧布局与这些机制，是分析安全漏洞与加固程序的基础。

三条实践结论：防护需分层（检测 + 阻断 + 随机化缺一不可）、默认选项往往不足（生产应显式开启 strong/full 级别）、防护与语言运行时需协同（异常、协程、长跳转都要正确配合）。
