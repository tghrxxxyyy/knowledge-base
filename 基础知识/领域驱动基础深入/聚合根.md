# 聚合根

> 对应 Evans《Domain-Driven Design》第 6 章 Aggregate，以及 Vernon《Implementing DDD》中聚合设计准则。

## 一、背景与挑战

领域对象互相引用形成网状图，事务边界与一致性边界不清，导致：并发修改同一图的不同部分产生冲突；级联更新失控（改 A 顺带改了一大片）；一个「保存」触发整库写。

挑战：(1) 一致性边界该划在哪；(2) 外部如何安全地引用内部对象；(3) 事务该多大；(4) 聚合过大导致锁竞争、过小导致不变量无法维护。

## 二、核心原理

聚合（Aggregate）是一组相关对象的边界，聚合根（Aggregate Root）是外部唯一可引用的入口。对聚合的修改必须通过根进行，根负责维护内部不变量（invariant）。一个事务只修改一个聚合——跨聚合的一致性通过最终一致（领域事件）达成，而非单事务强一致。

设计准则：尽量小的聚合（仅包含必须共同一致的对象）；通过身份引用其他聚合，而非对象引用。这样并发度高、事务短、边界清晰。

划定聚合边界的经验法则：第一，只把「必须一起保持一致的 objects」放进同一聚合，其余用 ID 引用；第二，聚合根应是「业务上天然是一个整体」的概念（如订单与其条目），而非技术便利；第三，避免双向关联，聚合内子对象不反向持有根以外的引用，根也不持有其他聚合的对象引用。聚合过小的反例是「每个实体独立聚合」——这会丧失不变量保护，跨实体的业务规则无处安放；过大的反例是「一个聚合包含半个领域」——任何修改都锁一大片，并发与性能崩溃。理想的聚合小到能保住不变量、大到不频繁跨聚合协作。聚合与仓储一一对应：一个聚合根一个仓储，子实体不经过自身仓储暴露。这与「事务只改一个聚合」共同构成 DDD 的并发与一致性基石，也是事件溯源中「每次操作产生事件」的单位。一个实用信号是：如果两个对象总是被一起修改、一起加载，它们大概率应属同一聚合；如果常独立变化，就应该拆开。

## 三、形式化与数学基础

聚合 $A = (root, \{child\})$。一致性规则：对 $A$ 的任何操作 $op$，结束后不变量成立：

$$\forall op,\; invariant(A) = \mathrm{true} \quad \text{操作后}$$

跨聚合一致性通过事件最终达成，不在单事务内强一致：

$$state_{downstream}(t+\Delta) = handle(event(op(A)))$$

其中 $\Delta$ 为有限延迟，发布方事务不等待下游。这把「强一致事务边界」收缩到单个聚合。

## 四、代码实现

```python
class Order:                      # 聚合根
    def __init__(self):
        self.items = []
        self.status = "NEW"

    def add_item(self, product, qty: int) -> None:
        # 根维护不变量：总量上限
        if self.total_qty() + qty > MAX_ITEMS:
            raise BusinessError("超出订单上限")
        self.items.append(OrderLine(product, qty))

    def total_qty(self) -> int:
        return sum(line.qty for line in self.items)
```

注意：`OrderLine` 作为子实体只能经 `Order` 访问；外部不得直接持有并修改 `OrderLine`，否则绕过不变量。

## 五、与其他技术对比

| 方案 | 一致性边界 | 事务 | 并发 |
|------|------------|------|------|
| 一个表一个事务 | 表 | 大 | 低 |
| 聚合 | 聚合 | 单聚合 | 高 |
| 实体直引 | 无 | 混乱 | 低 |

## 六、常见误区

- 聚合设计过大（近乎全表）：锁竞争、事务漫长。
- 让外部直接引用聚合内子实体：绕过根，破坏不变量。
- 跨聚合用同一事务强一致：违背「一事务一聚合」，扩展性差。
- 用对象引用而非 ID 引用其他聚合：边界泄漏。

## 九、演进与趋势

事件溯源（Event Sourcing）常与聚合根配合，以事件流重建状态、天然保证不变量时序；聚合设计方法论（如 Vernon 的「两步法」）进一步降低边界错误。具体以官方最新实践为准。

## 十、小结

聚合根是一致性边界入口，事务只跨一个聚合。通过根维护不变量、用 ID 引用他聚合并以事件达成最终一致，是 DDD 并发与一致性的核心权衡。
