# 领域事件

> 对应 Evans《Domain-Driven Design》中 Domain Events 模式，以及 Vernon《Implementing DDD》对领域事件的补充。

## 一、背景与挑战

领域中的重要事实（订单已支付、库存已扣减、账户已冻结）需要通知其他上下文或触发后续流程，但若在领域对象里直接调用其他服务，会破坏领域纯净、引入耦合，且让发布方承担下游成败。

挑战：(1) 跨聚合/跨上下文协作如何解耦；(2) 领域对象不应依赖消息中间件；(3) 事件与命令语义混淆；(4) 「发布事件」与「本地事务」如何原子（避免状态已改但事件丢失）。

## 二、核心原理

领域事件是对「已经发生的事实」的命名表达，命名用过去时（OrderPaid、InventoryDeducted）。领域层只在聚合上产生事件（挂到事件列表），由应用层或订阅方负责发布与响应，从而解耦跨聚合/跨上下文协作。

事件表「已发生」，与命令（Command，表「意图」）相对。发布方不等待下游，下游通过最终一致收敛。这样既保持领域纯净，又支持响应式流程编排。

领域事件的命名应使用过去时且为事实陈述：OrderPaid、InventoryDeducted、AccountFrozen，而非 PayOrder（命令式）。
事件应携带足够的不可变快照（聚合 ID、关键数值、发生时间），使订阅方无需回查即可处理。
但不宜把整个聚合塞进 payload，避免体积过大与耦合，通常带 ID 加必要字段即可。
事件的发布时机在聚合状态提交之后，由应用层从聚合取出 events 列表统一投递到总线。
这保证「状态已持久化」与「事件最终被投递」的衔接，配合 Outbox 可做到原子。
订阅方处理事件应满足幂等：同一事件可能因重试到达多次，处理需可重复且不产生副作用。
跨上下文协作通过事件解耦：订单上下文发布 OrderPaid，库存、积分、通知上下文各自订阅，互不知晓。
这与命令（Command）相对：命令表意图、需调用方等待结果；事件表已发生、发布方不等待下游。
消息队列是事件的技术传输层，但事件本身是领域概念，不应把 MQ 细节泄漏进领域层。
事件溯源（Event Sourcing）把事件流作为唯一事实来源，状态由重放事件重建，与聚合根天然契合。
事件 schema 应向前兼容，新增字段可选，避免旧消费者在回滚窗口内解析失败。
常见反模式是「事件里调外部服务」或在事件命名上混淆命令语义，都会破坏解耦与纯净。

## 三、形式化与数学基础

事件结构化为元组：

$$e = (type, occurredAt, payload, aggregateId)$$

订阅处理满足最终一致：

$$handle(e) \text{ 在有限延迟 } \Delta \text{ 后使下游状态收敛}$$

且事件发布不影响发布方事务的提交语义：发布方只需保证「状态已提交且事件最终会被投递」。

## 四、代码实现

```python
from dataclasses import dataclass

@dataclass
class OrderPaid:
    order_id: str
    amount: int

class Order:
    def __init__(self, oid: str):
        self.id = oid
        self.status = "NEW"
        self.events = []

    def pay(self) -> None:
        self.status = "PAID"
        # 产生领域事件，不直接调外部服务
        self.events.append(OrderPaid(self.id, self.total))

# 应用层：提交聚合后统一发布事件
def handle_payment(order: Order, repo) -> None:
    order.pay()
    repo.save(order)
    publish(order.events)   # 由基础设施投递到消息总线
```

注意：领域层只「产生」事件，投递由应用/基础设施负责；避免在 `pay` 内直接发副作用。

| 领域事件 Event | 过去 | 事实 | 发布方不等待 |

## 六、常见误区

- 把事件当命令：命名用将来时、含意图（如 `PayOrder`），混淆语义。
- 在事件发布前就调用外部副作用：破坏领域纯净与事务边界。
- 忽略事件丢失：未用 Outbox 等模式保证「状态+事件」原子。
- 事件 payload 过大或含可变引用：应只带不可变快照标识。

## 九、演进与趋势

Outbox 模式（事务内写消息表，后台投递）保证原子；事件总线标准化与 schema 演进（版本化事件）成为大规模系统的标配；与事件溯源结合可完整回放领域历史。具体以官方最新实践为准。

## 十、小结

用过去时事件解耦上下文，发布与处理最终一致。领域层只产生事件、不投递副作用，配合 Outbox 保证原子性，是响应式领域协作的核心机制。
