# 实体与值对象

> 对应 Evans《Domain-Driven Design》第 5 章 Entity 与 Value Object。

## 一、背景与挑战

领域建模时混淆「有身份」与「有属性」的对象，会导致：用值比较却依赖 ID（同一属性被当成不同对象），或用 ID 比较却只需属性相等（无谓维护身份）。这会引发正确性与性能问题，也让并发与缓存更复杂。

挑战：(1) 何时该用身份、何时该用属性，边界不清；(2) 值对象被做成可变会破坏语义与线程安全；(3) 过度使用实体带来身份管理负担。

## 二、核心原理

实体（Entity）由身份（ID）定义：生命周期内属性可变但身份不变，相等性按 ID。典型如订单、用户、账户。

值对象（Value Object）由属性定义：不可变、无身份，相等性按属性值，可自由替换与共享。典型如金额、地址、坐标、时间段。把本应值对象的建模为实体是常见错误。

两者共同构成领域模型的基石；值对象越多，领域越简单、越安全（天然不可变、可组合、可测试）。

值对象的不可变带来引用透明：可在多处安全共享同一实例，无需防御性拷贝，天然线程安全。
因此集合、缓存、并发场景里，凡是「按属性相等」的概念都应优先建模为值对象。
金额、地址、坐标、时间段、颜色、度量（带单位的量）都是典型值对象，常带自我校验（如金额不为负）。
值对象内部可实现组合操作（如 Money.add 返回新 Money），保持不可变语义，调用方无副作用。
实体则需谨慎管理身份生命周期：身份在创建时分配（UUID 或业务键），之后不变，即便属性全改仍是同一对象。
数据库主键是持久化概念，领域身份应独立于存储，便于在内存、测试、多存储间迁移。
当两实体属性相同但身份不同，它们应判为不等；当身份相同属性不同，应判为相等——这是实体与值对象的根本分界。
贫血模型常把所有对象做成「只有 getter/setter 的实体」，把逻辑塞进 Service，导致值对象的不可变优势丧失。
语言层支持（Java record、Kotlin data class、Python dataclass(frozen)、C# record）让值对象声明简洁且默认不可变。
建模时可先假设「它是值对象」，只有当确实需要身份与生命周期时才提升为实体，默认倾向值对象。
值对象也可作为实体的属性或集合元素，构成领域模型的主体，实体只承担身份与边界职责。

## 三、形式化与数学基础

实体相等（按身份）：

$$e_1 = e_2 \iff id(e_1) = id(e_2)$$

值对象相等（按属性）：

$$v_1 = v_2 \iff \bigwedge_{a \in attrs} a(v_1) = a(v_2)$$

值对象满足不可变约束：构造后任意属性 $a$ 不可改，$v.a$ 为常量。由此值对象可安全共享（引用透明），且 $v_1 = v_2$ 时可互换而不影响行为。

## 四、代码实现

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Money:           # 值对象：不可变、按属性相等
    amount: int
    currency: str

    def add(self, other: "Money") -> "Money":
        # 返回新值对象而非修改自身
        return Money(self.amount + other.amount, self.currency)

class Order:           # 实体：按 id 相等
    def __init__(self, order_id: str):
        self.id = order_id
    def __eq__(self, o) -> bool:
        return isinstance(o, Order) and o.id == self.id
    def __hash__(self) -> int:
        return hash(self.id)
```

注意：`frozen=True` 强制不可变；实体必须实现 `__eq__`/`__hash__` 基于 ID，避免 ORM/集合误判。

## 五、与其他技术对比

| 对象 | 相等性 | 可变性 | 身份 | 示例 |
|------|--------|--------|------|------|
| 实体 | ID | 可变 | 有 | 订单、用户 |
| 值对象 | 属性 | 不可变 | 无 | 金额、地址 |
| DTO | 结构 | 可变 | 无 | 传输结构 |
| ORM 行 | 主键 | 可变 | 有 | 表记录 |

## 六、常见误区

- 把本应是值对象的金额/地址建模成实体：徒增身份管理。
- 值对象里放可变字段破坏语义与线程安全。
- 用数据库主键当领域身份：主键是持久化概念，领域身份应独立于存储。
- 值对象持有实体引用：值对象应保持简单、自包含。

## 九、演进与趋势

语言层不可变类型（Java record、Kotlin data class、Python dataclass frozen、C# record）让值对象建模更自然；值对象的「基于属性相等 + 不可变」正成为默认最佳实践。具体以官方最新实践为准。

## 十、小结

以「身份 vs 属性」区分实体与值对象，多用值对象降低复杂度。值对象不可变、按属性相等，是构建正确、可测试领域模型的关键。
