# 仓储模式

> 对应 Evans《Domain-Driven Design》第 6 章 Repository，以及 Fowler《Patterns of Enterprise Application Architecture》中 Repository 模式。

## 一、背景与挑战

领域层若直接写 SQL 或依赖具体 ORM，会把持久化细节混入业务规则，导致：代码纠缠难读、业务逻辑无法脱离数据库单测、替换技术栈成本高。更进一步，领域对象以「行/表」视角暴露，破坏了聚合边界。

挑战：(1) 领域层不应感知存储介质（关系库、文档库、内存、缓存）；(2) 查询应表达领域意图而非 SQL；(3) 测试时要能替换成内存实现；(4) 与聚合根边界保持一致，避免返回脱离根的零散实体。

## 二、核心原理

仓储（Repository）为聚合提供「集合式」抽象：领域层以 `add / find / remove` 这类面向集合的语义操作聚合，不关心底层是关系库、文档库还是内存。它位于领域层与基础设施层之间，向上对领域暴露领域接口，向下委托持久化实现。

关键约束：仓储面向聚合根，而非面向表；一次 `find` 返回的是完整聚合（含其子实体与值对象），保证不变量（invariant）一致。仓储接口定义在领域层，实现放在基础设施层（依赖倒置）。

仓储的接口应只暴露聚合级操作，避免泄漏查询细节：find_by_id 返回完整聚合，find_by_spec 返回集合而非分页 DTO。
复杂查询（多条件、联表）不应塞进写侧仓储，而应走 CQRS 的读模型或专用查询对象。
内存实现是仓储的重要价值：单测中注入内存版，领域逻辑可脱离数据库独立验证，测试飞快且稳定。
持久化实现（如 SQLAlchemy、MongoDB driver）放在基础设施层，通过依赖注入传入应用层。
仓储内部可用 Unit of Work 模式批量提交，把多次 save 合并为一次事务，减少往返。
对聚合的删除，仓储应保证级联一致性：删根即删其下所有子实体，避免孤儿数据。
乐观锁（version 字段）常放在仓储 save 中，检测并发修改冲突，防止丢失更新。
事件发布也常与仓储配合：save 后从聚合取出领域事件统一发布（见领域事件）。
命名上建议按聚合根命名（OrderRepository），而非按表（OrdersDao），强化领域语义。
仓储不应包含业务规则，规则在聚合根内；仓储只负责「按身份存取聚合」。
多数据源场景下，一个聚合根可能跨库，此时仓储需协调多存储的事务边界（常借助 Saga）。
测试仓储实现应覆盖边界：空结果、并发写、乐观锁冲突，确保行为契约稳定。

## 三、形式化与数学基础

把仓储 $R$ 视作聚合集合 $A$ 上的抽象容器，满足集合语义：

$$R.add(a) \Rightarrow R.find(a.id) = a$$
$$R.remove(a) \Rightarrow R.find(a.id) = \bot$$

它隔离了领域模型 $Domain$ 与持久化映射 $M: Domain \to Persistence$。从类型看，仓储是满足以下签名的抽象：

$$R: \mathrm{Id} \to A \cup \{\bot\}, \quad R.\mathrm{save}: A \to \mathrm{void}$$

换言之，仓储对外只暴露「按身份取聚合」与「保存聚合」，隐藏了 join、ORM session、缓存失效等细节。

## 四、代码实现

```python
from abc import ABC, abstractmethod

class OrderRepository(ABC):
    @abstractmethod
    def save(self, order: "Order") -> None: ...
    @abstractmethod
    def find_by_id(self, oid: str) -> "Order | None": ...
    @abstractmethod
    def remove(self, order: "Order") -> None: ...

# 领域服务仅依赖抽象，不依赖任何具体存储
def place_order(repo: OrderRepository, order: "Order") -> None:
    # 业务规则在 Order 内，repo 只负责持久化
    repo.save(order)
```

注意：仓储实现（如 SQLAlchemy/MySQL）放在基础设施层，通过依赖注入传入；单测可注入内存实现，实现领域层独立测试。

## 五、与其他技术对比

| 模式 | 中心 | 关注 | 领域纯净度 |
|------|------|------|------------|
| DAO | 表/行 | 数据访问 | 低 |
| Active Record | 行 | 行即对象 | 低 |
| Repository | 聚合 | 集合语义 | 高 |
| Data Mapper | 对象 | 映射 | 中 |

## 六、常见误区

- 在仓储里写领域逻辑：仓储只做持久化，业务规则应在聚合根内。
- 返回脱离聚合根的零散实体：破坏边界，外界可绕过不变量。
- 把仓储当万能查询器：复杂报表查询应交由 CQRS 的读模型，而非污染写侧仓储。
- 一个实体一个仓储：应按聚合根而非每个实体建仓储。

## 九、演进与趋势

Specification 模式与仓储结合表达可组合查询；CQRS 下读写模型分离，写侧用领域仓储、读侧用专用读模型；事件溯源下仓储退化为事件流存储。具体以官方最新实践为准。

## 十、小结

仓储把持久化抽象为聚合集合，保护领域纯净、可测试、可替换。它只面向聚合根、只暴露集合语义，是连接领域与基础设施的受控边界。
