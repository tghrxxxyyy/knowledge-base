# 仓储模式

> 对应 Evans《Domain-Driven Design》第6章、Fowler《Patterns of Enterprise Application Architecture》。

## 一、背景与挑战
领域层直接写 SQL 或依赖 ORM 会污染业务逻辑、难以测试，且把持久化细节混入领域。

## 二、核心原理
仓储（Repository）为聚合提供集合式抽象：领域层以 `add/find/remove` 操作聚合，不关心底层是关系库、文档库还是内存。它位于领域与基础设施之间。

## 三、形式化 / 数学基础
仓储 $R$ 满足集合语义：$R.add(a) \Rightarrow R.find(a.id)=a$；$R.remove(a) \Rightarrow R.find(a.id)=\bot$。它隔离了 $Domain$ 与 $Persistence$ 的映射 $M$。

## 四、代码实现
```python
class OrderRepository(ABC):
    @abstractmethod
    def save(self, order: Order): ...
    @abstractmethod
    def find_by_id(self, oid: str) -> Order: ...

# 领域服务仅依赖抽象
def place(repo, order):
    repo.save(order)
```

## 五、与其他技术对比
与 DAO（数据访问对象）相比，Repository 以聚合/领域为中心，DAO 以表为中心。与 Active Record 相比，领域更纯净。

## 六、常见误区
误区：在仓储里写领域逻辑。误区：返回脱离聚合根的零散实体，破坏边界。

## 九、演进与趋势
Specification 模式与仓储结合表达查询；CQRS 下读写仓储分离。

## 十、小结
仓储把持久化抽象为聚合集合，保护领域纯净。
