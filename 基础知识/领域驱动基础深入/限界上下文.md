# 限界上下文

> 对应 Evans《Domain-Driven Design》第2章、第14章。

## 一、背景与挑战
同一词汇在不同部门含义不同（"客户"在销售与物流中属性不同），共享一个大模型会导致概念冲突与耦合一团。

## 二、核心原理
限界上下文（Bounded Context）是领域模型的显式边界，边界内术语有唯一、无歧义的定义（通用语言 Ubiquitous Language）。上下文间通过上下文映射（Context Map）的防腐层（ACL）等模式交互。

## 三、形式化 / 数学基础
设上下文 $C_i$ 含模型 $M_i$ 与术语集 $T_i$。在 $C_i$ 内映射 $meaning:C_i\times T_i\to concept$ 唯一。跨上下文转换由 ACL 提供 $translate: M_j\to M_i$。

## 四、代码实现
```python
# 销售上下文的 Customer 与物流上下文的 Customer 各自独立建模
# 通过防腐层转换，避免互相污染
class ShippingACL:
    def to_shipping_customer(self, c: SalesCustomer) -> ShipCustomer:
        return ShipCustomer(id=c.id, address=c.delivery_address)
```

## 五、与其他技术对比
与"统一企业数据模型"相反，DDD 接受多模型并存，用边界与映射管理差异。与微服务边界高度吻合。

## 六、常见误区
误区：强行统一全公司一词一义。误区：上下文过大，重蹈大泥球。
