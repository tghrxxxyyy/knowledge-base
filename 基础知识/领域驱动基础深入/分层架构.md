# 分层架构

> 对应 Evans《Domain-Driven Design》第 4 章 Layered Architecture，以及 Fowler 关于分层与依赖倒置的讨论。

## 一、背景与挑战

代码混层（UI 里写 SQL、领域里发 HTTP）使依赖方向混乱：技术细节渗入核心业务，核心逻辑无法独立测试，替换技术栈要动全身。大型系统尤其需要显式的职责边界。

挑战：(1) 依赖方向易反向（领域层引用基础设施）；(2) 应用层被塞进业务规则变成「胖应用」；(3) 各层职责模糊导致重复；(4) 跨层调用失控，难以推理。

## 二、核心原理

经典四层（自上而下）：用户界面层（表现/接口）→ 应用层（用例编排，薄，无业务规则）→ 领域层（核心逻辑、聚合、领域事件、领域服务）→ 基础设施层（持久化、消息、外部调用）。

关键原则：依赖指向领域层。领域层不依赖任何外层；基础设施层实现领域层定义的抽象接口（依赖倒置 DIP）。应用层只编排、不承载领域规则。

应用层应是「薄编排」：它协调仓储、领域服务与外部系统完成用例，本身不含业务规则。
若应用层开始写 if 判断业务分支，说明逻辑应下沉到领域对象或领域服务。
领域服务（Domain Service）用于「无自然归属对象」的行为，如跨多个聚合的计算、需要外部依赖的领域逻辑。
但它不应成为所有逻辑的垃圾桶，能用实体/值对象表达的规则优先放在对象内。
基础设施层实现领域定义的接口，方向是向内依赖；领域层永不 import 具体技术实现。
一个判断标准：把基础设施（数据库、HTTP 客户端）全部替换为假实现，领域与应层仍能编译运行。
用户界面层只负责表示与输入校验，不写业务；展示模型（DTO/ViewModel）与领域模型应分离，避免泄漏。
分层间的防腐层也很重要：调用外部系统时通过 ACL 转换，防止外部模型侵蚀领域。
六边形架构与整洁架构是 DDD 分层的等价表达，区别在图形化视角与端口/适配器术语。
实践中可在领域层标记「纯 Python/Java」，用编译或测试强制其不依赖外层，守住依赖向内。
分层不是越多越好，过小团队可用「领域 + 应用 + 基础设施」三段，避免过度分层带来的样板代码。
跨层调用应单向，禁止循环依赖与反向调用，可用架构测试（如 dependency-cruiser）自动守护。

## 三、形式化与数学基础

依赖方向约束：

$$UI \to App \to Domain \leftarrow Infra$$

即外层依赖内层，内层（Domain）对外层零依赖：

$$Dependencies(Domain) = \emptyset \quad \text{（相对外层）}$$

由 DIP 反转基础设施依赖：领域定义接口 $I$，基础设施提供实现 $I'$，运行时注入，编译期依赖仍指向领域。

## 四、代码实现

```python
# 领域层定义抽象接口
class OrderRepository(ABC):
    @abstractmethod
    def save(self, o: "Order") -> None: ...

# 基础设施层实现该接口（依赖倒置）
class SqlOrderRepo(OrderRepository):
    def save(self, o: "Order") -> None:
        # 具体 ORM/SQL 逻辑在这里
        ...

# 应用层只编排领域与仓储抽象，不接触持久化细节
def place_order(repo: OrderRepository, order: "Order") -> None:
    repo.save(order)
```

注意：领域层不得 `import` 基础设施模块；若需要，应通过领域定义的接口（端口）回调，由外层注入实现。

## 五、与其他技术对比

| 架构 | 核心层 | 依赖方向 | 特点 |
|------|--------|----------|------|
| 传统三层 | 业务层 | 表现→业务→数据 | 业务与数据耦合 |
| DDD 四层 | 领域层 | 向内 | 领域显式独立 |
| 六边形 | 领域 | 端口向内 | 等价但视角不同 |
| 整洁架构 | 实体/用例 | 同心圆向内 | 更图形化 |

## 六、常见误区

- 应用层塞进业务规则变成「胖应用」：业务应下沉到领域。
- 领域层反向 import 基础设施：违反依赖向内。
- 把基础设施细节（SQL）写进应用层：应用层应只编排。
- 滥用「服务」：贫血模型下逻辑全堆在 Service，领域沦为数据载体。

## 九、演进与趋势

整洁架构/六边形架构进一步把依赖规则图形化，边界用端口与适配器表达；CQRS 在应用层之上拆分读写，缓解单模型负担。具体以官方最新实践为准。

## 十、小结

领域层居中、依赖向内，分层隔离技术细节。配合 DIP，领域保持纯净且可测试，是 DDD 落地的骨架。
