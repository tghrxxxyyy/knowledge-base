# 分层架构

> 对应 Evans《Domain-Driven Design》第4章、Fowler 分层讨论。

## 一、背景与挑战
代码混层（UI 里写 SQL、领域里发 HTTP）使依赖方向混乱，难以测试与替换技术栈。

## 二、核心原理
经典四层：用户界面层 → 应用层（用例编排，薄）→ 领域层（核心逻辑、聚合、领域事件）→ 基础设施层（持久化、消息）。依赖指向领域层（配合 DIP）。

## 三、形式化 / 数学基础
依赖方向：$UI \to App \to Domain \leftarrow Infra$。领域层不依赖任何外层，满足 $Dependencies(Domain)=\emptyset$（相对外层），由 DIP 反转基础设施依赖。

## 四、代码实现
```python
# 依赖：infra 实现 domain 定义的接口
class SqlOrderRepo(OrderRepository):  # infra 实现 domain 抽象
    def save(self, o): ...
# app 层仅调用 domain 与 repo 抽象
```

## 五、与其他技术对比
与"传统三层（表现/业务/数据）"相比，DDD 把业务核心显式独立为领域层；与六边形架构等价但视角不同。

## 六、常见误区
误区：应用层塞进业务规则变成"胖应用"。误区：领域层反向 import 基础设施。

## 七、与开源书 / 权威来源对应
Evans, E.《Domain-Driven Design》第4章；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"DDD 分层各层职责？为什么领域层不依赖基础设施？"

## 九、演进与趋势
整洁架构/六边形架构进一步把依赖规则图形化，边界用端口与适配器。

## 十、小结
领域层居中、依赖向内，分层隔离技术细节。
