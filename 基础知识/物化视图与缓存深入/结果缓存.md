# 结果缓存

> 对应应用层缓存模式（Cache-Aside 等），以及 DDIA 中文第 10 章 缓存。

## 一、背景与挑战
数据库直接承受重复读压力会成瓶颈。在应用层缓存查询结果（而非整页）可按业务键精准加速，但需处理一致性、穿透、击穿、雪崩。

## 二、核心原理
常见模式 Cache-Aside：读时查缓存，未命中查库并回填；写时更新 DB 并删缓存（或双写）。需应对：缓存穿透（查不存在 key，用空值/布隆）、击穿（热点 key 失效并发回源，用互斥/逻辑过期）、雪崩（批量失效，用随机 TTL）。

## 三、形式化 / 数学基础
命中率 $h$；穿透率 $p$ 使无效回源；$T_{avg} = h \cdot T_{cache} + (1-h)(T_{db} + T_{cache\_write})$。缓存一致性窗口 = 写后到删缓存间的延迟。

## 四、代码实现
```python
def get_user(uid):
    v = redis.get(f"u:{uid}")
    if v is None:
        v = db.query("SELECT * FROM users WHERE id=?", uid)
        if v: redis.setex(f"u:{uid}", 300, serialize(v))
        else: redis.setex(f"u:{uid}:nil", 60, "1")  # 防穿透
    return v
```

## 五、与其他技术对比
| 模式 | 读路径 | 一致性 |
|------|--------|--------|
| Cache-Aside | 应用管 | 最终 |
| Read-Through | 缓存管 | 最终 |
| Write-Through | 同步写 | 较强 |

## 六、常见误区
1. 删缓存一定及时——并发下可能脏读。
2. 缓存不会错——失效前是旧数据。
3. 永不失效——内存爆炸与雪崩。

## 九、演进与趋势
本地+分布式多级缓存、缓存与 CDC（如 Debezium）联动自动失效，降低一致性窗口。

## 十、小结
结果缓存以业务键加速读，关键在工程化应对穿透/击穿/雪崩与一致性，是数据库前的第一道性能防线。
