# 查询缓存

> 对应 MySQL 查询缓存（已弃用）历史，以及 PostgreSQL 计划/结果缓存讨论，DDIA 缓存章。

## 一、背景与挑战
相同查询反复执行浪费算力。缓存查询结果可秒回，但失效（invalidation）与内存管理是难题；任何基表变更都需令相关缓存失效。

## 二、核心原理
查询缓存以 SQL 文本（含参数）为键、结果集为值。命中直接返回；失效策略：表级失效（任一相关表变更即清）、TTL、或精确依赖跟踪（开销大）。

## 三、形式化 / 数学基础
命中率 $h = hit/(hit+miss)$。收益 $B = h \cdot (T_{compute} - T_{cache\_get})$。写多场景 $h$ 趋近 0，缓存反而因失效扫描拖慢——正是 MySQL 弃用查询缓存原因。

## 四、代码实现
```python
cache = {}
def query(sql):
    if sql in cache:
        return cache[sql]            # 命中
    res = db.execute(sql)
    cache[sql] = res                 # 写缓存（需失效机制）
    return res
```

## 五、与其他技术对比
| 缓存 | 粒度 | 失效 | 适用 |
|------|------|------|------|
| 查询缓存 | SQL | 表级 | 读多写少 |
| 缓冲池 | 页 | LRU | 通用 |
| 结果缓存 | 业务键 | 业务 | 特定 |

## 六、常见误区
1. 查询缓存总提速——写多反而变慢。
2. 缓存键用 SQL 文本足够——参数化与大小写需归一。
3. 缓存无需失效—— stale 数据错误。

## 九、演进与趋势
转向应用层/中间件缓存（如 Redis 缓存聚合结果）、数据库内计划缓存与 prepared statement 缓存。

## 十、小结
查询缓存以 SQL 为键加速重复查询，但写密集下失效开销使其得不偿失，现代多转向更精细的缓存层。
