# 放大攻击

> 对应 RFC 5358（Preventing Use of Recursive Nameservers in Reflector Attacks）、RFC 2827（BCP38 网络入口过滤）与 US-CERT 关于反射放大攻击的告警。

## 一、背景与挑战
某些基于 UDP 的协议具备「请求小而响应大」的特性，且无需握手即可伪造源 IP。攻击者用受害者 IP 作为源地址向大量开放服务器发送小请求，这些服务器便把庞大的响应发往受害者，形成「反射放大」。攻击者只需极小的上行带宽，就能撬动远超自身容量的流量打向受害者。

这种攻击的隐蔽性在于：流量来自大量看似无辜的第三方服务器，受害者难以直接溯源，也无法简单封禁——封禁意味着切断真实用户对这些公共服务的访问。开放递归 DNS 解析器、NTP monlist、SSDP、SNMP、Memcached 等都曾是被滥用的重灾区。

## 二、核心原理
反射放大依赖三个条件同时成立：协议基于 UDP（可伪造源）、请求与响应存在非对称放大、服务器对任意来源开放。放大因子定义为：

$$ A = \frac{\text{size}(response)}{\text{size}(request)} $$

不同协议的放大因子差异巨大，从个位数到数万倍不等，具体数值随协议实现与查询类型变化，不宜当作固定常数。攻击者控制 $N$ 个反射器，每个以速率 $rate_{req}$ 收请求、以 $rate_{resp}$ 回响应，则受害者承受的总带宽约为：

$$ \lambda_{victim} \approx N \cdot rate_{resp} = N \cdot A \cdot rate_{req} $$

而攻击者实际发出的流量仅为 $\lambda_{victim}/A$。

防御的根本在于拆除前提条件：关闭开放递归与可放大服务（限制查询来源）、实施 BCP38 入口过滤阻止源 IP 伪造、对响应做速率限制。

## 三、形式化与数学基础
设每个反射器的响应大小为 $S_{resp}$、请求大小为 $S_{req}$，则放大因子 $A = S_{resp}/S_{req}$。若攻击者以总上行带宽 $B_{up}$ 发请求，则受害者处承受的流量下界为 $A \cdot B_{up}$。

源地址伪造能否成功，取决于攻击者所在网络是否实施入口过滤。BCP38（RFC 2827）要求边缘网络丢弃「源地址不属于本网段」的报文，一旦普遍部署，反射器收到的请求源地址即为真实地址，攻击便无法定向到受害者。这解释了为何 BCP38 是治本之策，却因跨域协同困难而普及缓慢。

## 四、代码实现
```bash
# DNS：关闭开放递归，只允许内部查询（named.conf 片段）
# options { recursion no; allow-query { internal_nets; }; };

# NTP：关闭 monlist 等可被放大的查询
ntpdc -c "restrict default nomodify notrap nopeer noquery"

# 主机侧：对 UDP 响应做速率限制（示意）
iptables -A OUTPUT -p udp --sport 53 -m limit --limit 50/s -j ACCEPT
iptables -A OUTPUT -p udp --sport 53 -j DROP
```

配置语法随软件版本而异，实际部署需参照对应服务与发行版的官方文档。运营商侧则应启用 uRPF（单播反向路径转发）或 ACL 实现 BCP38 入口过滤。

## 五、与其他技术对比
| 维度 | 反射放大攻击 | 直接僵尸网络洪泛 |
| --- | --- | --- |
| 是否需控制肉鸡 | 否，借公共服务 | 是，需感染大量主机 |
| 源 IP 特征 | 伪造为受害者 | 真实肉鸡地址 |
| 放大效应 | 有，因子可达极大 | 无，1:1 输出 |
| 溯源难度 | 高，流量来自第三方 | 相对可追 |
| 关键防御 | 关闭开放服务 + BCP38 | 清洗、黑名单、任播 |

放大攻击「借力打力」，单位攻击成本更低、峰值更高；但它对特定协议与开放服务的依赖也更明显，一旦全球范围完成治理，其威力会显著下降。

从攻防视角看，反射放大之所以高效，在于它同时做到了「放大」与「隐蔽」：

- 放大：请求与响应的非对称使攻击者以小博大。
- 隐蔽：流量来自大量无辜第三方，溯源困难。
- 廉价：无需控制肉鸡，借公开服务即可发动。
- 突发：可在极短时间内把峰值推到链路上限。

治理需要供给侧与需求侧同时发力：

- 供给侧（服务运营方）：默认拒绝外部查询、做响应速率限制、绑定监听地址。
- 需求侧（网络运营方）：部署 BCP38 入口过滤，阻断伪造源地址出网。
- 受害侧（被攻击方）：保留上游清洗与黑洞通道，作为无法治理他人服务时的兜底。

一个常被忽略的事实是：治理的收益具有外部性——你关闭了自己的开放服务，受益者可能是素不相识的第三方。这正是源地址验证类协同治理难以快速普及的原因，也是受害侧仍需自备兜底能力的理由。

评估自身暴露面的快速自查清单：

- 对外是否运行 DNS、NTP、Memcached、SSDP、SNMP、LDAP 等 UDP 服务？
- 这些服务是否允许任意来源查询？
- 响应大小是否远大于请求？
- 出口是否允许伪造源地址（BCP38 未部署）？
- 是否有针对异常响应速率的监控与限速？

## 六、常见误区
误区一：「TCP 也能被放大」。错，TCP 需要三次握手、难以伪造源地址，且无天然的请求响应不对称，不是反射放大的载体。误区二：「关掉 DNS 递归就安全了」。错，NTP、SSDP、Memcached、SNMP、LDAP 等同样可被滥用。误区三：「放大攻击必须有僵尸网络」。错，借助公开服务器即可，无需肉鸡。误区四：「只要自己不开放就行」。错，别人开放的服务照样能把响应打向你的 IP，需要上游过滤与清洗兜底。

## 九、演进与趋势
Memcached 反射曾把攻击峰值推到 Tbps 量级，推动行业默认关闭危险服务并加强响应限速。趋势上，一方面协议实现默认收紧（递归 DNS 默认拒绝外部查询、Memcached 默认仅监听本地），另一方面攻击者转向新暴露面（游戏协议、物联网设备、云上错配置的 UDP 服务）。源地址验证与响应速率限制正在成为 UDP 服务的默认工程要求。

## 十、小结
放大攻击利用无状态 UDP 的小请求大响应特性，以极小代价撬动巨大流量。防御逻辑清晰——关闭开放服务、做 BCP38 源地址过滤、加响应限速——难点在于跨组织协同与存量服务的治理。理解放大因子与反射器数量这两项关键变量，就能定量评估暴露风险并排定加固优先级。
