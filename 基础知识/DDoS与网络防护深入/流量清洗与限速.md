# 流量清洗与限速

> 对应 RFC 2697（srTCM 单速率三色标记）、RFC 2698（trTCM）与 RFC 2827（BCP38 入口过滤）。

## 一、背景与挑战
真实攻击流量往往混杂在正常流量之中：同一批 IP 既在发攻击包，也在发合法请求；同一协议端口既是业务入口，也是攻击载体。粗暴地全量丢弃会误伤用户，全量放行则后端被打垮。工程上需要两件互补的工具——「识别并剥离恶意部分的清洗」与「约束异常速率的限速」。

清洗解决「像不像攻击」的问题，限速解决「太多太快」的问题。二者常被混为一谈，但技术路径完全不同：清洗依赖指纹、行为分析与协议解析，限速只看速率是否越过配置阈值。

## 二、核心原理
流量清洗的流程是：检测到异常后，通过 BGP 引流或策略路由，把去往目标的前缀流量引到清洗中心；清洗中心基于特征指纹（如放大攻击的响应特征、SYN 洪泛的半连接模式）、行为基线、协议合规性检查过滤掉攻击流量；干净流量再回注到目标网络。清洗中心的带宽容量与检测精度是核心指标。

限速（policing）则在边界用令牌桶丢弃超出承诺速率的流量，简单、低成本、可即时生效。整形（shaping）与之相对，通过缓存把突发平滑后发出，不丢包但引入延迟与缓冲需求。清洗偏「精准」，限速偏「粗暴但兜底」，二者常叠加：先限速削峰，再清洗剥离。

## 三、形式化与数学基础
设检测丢弃率为 $d_{detect}$，则清洗后残余到达目标的速率约为：

$$ \lambda_{clean} = \lambda_{legit} + \lambda_{attack}\,(1 - d_{detect}) $$

$d_{detect}$ 无法达到 1，因此总存在残余攻击；同时若检测误伤合法流量，会额外损失可用性，故真实目标是在控制误杀率的前提下最大化 $d_{detect}$。

令牌桶（srTCM，RFC 2697）用三个参数描述：承诺速率 $CIR$、承诺突发 $CBS$、超额突发 $EBS$。桶内令牌以 $CIR$ 补充，报文按长度消耗令牌：令牌充足则标记为绿（放行），不足则标记为黄或红（降级或丢弃）。单速率双色桶的判定可写作：到达速率 $\lambda \le CIR$ 时基本放行，突发受 $CBS$ 约束，长期均值被压到 $CIR$ 附近。

## 四、代码实现
```bash
# 边界限速：令牌桶整形/管制（tbf）
tc qdisc add dev eth0 root tbf rate 1gbit burst 32kbit latency 10ms

# 按目的端口做精细限速示意
tc qdisc add dev eth0 root handle 1: htb default 30
tc class add dev eth0 parent 1: classid 1:1 htb rate 1gbit

# 主机防火墙：对新建连接做速率限制
iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW \
  -m limit --limit 200/s --limit-burst 400 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -m conntrack --ctstate NEW -j DROP
```

清洗侧的引流通常是 BGP 通告或策略路由，属于网络设备配置范畴，具体命令依厂商而定。限速参数需要结合业务基线反复调优，配置过严会造成正常突发被误伤。

## 五、与其他技术对比
| 维度 | 流量清洗 | 速率限制（Policing） | 流量整形（Shaping） |
| --- | --- | --- | --- |
| 判据 | 内容/行为特征 | 速率阈值 | 速率阈值 |
| 处理方式 | 剥离攻击后回注 | 超限丢弃 | 缓存后平滑发送 |
| 对合法流量 | 尽量保留 | 突发可能被误伤 | 不丢包但增延迟 |
| 成本 | 高（带宽+设备） | 低 | 中（需缓冲） |
| 适用 | 可识别的攻击 | 兜底削峰 | 对抖动敏感的业务 |

清洗保可用性但成本高、有误杀；限速成本低但无内容识别能力；整形不丢包却引入延迟。三者按业务敏感度组合使用。

落地清洗体系时，几个工程指标决定它是否真的有用：

- 清洗容量：能否承接峰值攻击带宽，不足则自身成为新瓶颈。
- 引流与回注时延：引流慢意味着攻击已造成伤害，回注路径需避免二次拥塞。
- 检测准确率：漏杀让攻击穿透，误杀伤害体验，二者需分别度量并报告。
- 回注策略：按目的、按源或按隧道回注，影响路径可控性与可观测性。
- 可观测性：清洗前后流量、丢弃原因分布与残余流量必须可查。

限速的工程要点同样容易被忽视：

- 桶参数需按业务基线设定，承诺速率过低会导致常态化误伤。
- 区分「每源」与「聚合」限速：前者防单点滥用，后者防分布式低速聚合。
- 对 TCP 而言，丢包会触发重传与退避，粗暴限速可能放大抖动，必要时改用整形。
- 与白名单结合，保证关键调用方不被限速波及。
- 监控被丢弃流量，区分「攻击被拦」与「正常被误伤」。

一个实用的分层做法是「先粗后细」：边界先用令牌桶削掉明显的异常峰值，把流量压到清洗中心可处理的量级；清洗中心再做基于特征与行为的精细过滤。这样既控制了清洗成本，又提升了整体残余流量的可预测性。

监控与复盘建议：

- 记录清洗前后的流量曲线，量化实际拦截效果。
- 分类统计丢弃原因，识别误杀与固有短板。
- 对照攻击峰值与清洗容量，评估是否需要扩容或改进引流。

## 六、常见误区
误区一：「清洗能 100% 区分攻击与正常」。错，检测天然存在漏杀与误杀，需持续调优并接受残余风险。误区二：「限速等于清洗」。错，限速只看速率，对伪装成正常速率的慢速攻击无效。误区三：「限速不会影响正常用户」。错，配置过严时正常突发流量同样被丢，需按业务基线设定。误区四：「整形和限速是一回事」。错，整形不丢包、以延迟换平滑；限速直接丢弃、以丢包换保护。

## 九、演进与趋势
清洗侧引入机器学习的行为分析，把判据从静态指纹扩展到流量基线与实体行为画像，提升对低速、分布式攻击的识别率。部署形态上，任播与边缘计算推动「近源清洗」，把过滤点前移到离攻击源更近、带宽更充裕的位置。限速侧则从粗粒度接口限速走向基于 eBPF 的细粒度、低开销实现。整体趋势是「检测更智能、处置更靠边」。

## 十、小结
流量清洗以内容与行为判据剥离攻击、尽量保留合法流量，限速以速率阈值约束异常、低成本兜底，整形以延迟换平滑。三者不是替代关系而是分层组合：在带宽充足处清洗、在边界削峰、对敏感业务整形。理解各自的能力边界与代价，才能在保可用性与保网络之间做出正确的取舍。
