# 黑洞路由

> 对应 RFC 3882（Configuring BGP to Block Denial-of-Service Attacks）与 RFC 5635（Remote Triggered Black Hole Filtering，RTBH）。

## 一、背景与挑战
当攻击规模超过清洗能力、或攻击源极度分散以至于无法区分攻击与合法流量时，继续让流量抵达目标会拖垮整个接入网段甚至上游链路。此时最后的手段是：把去往受害 IP 的流量「丢弃到虚空」，主动牺牲该 IP 的可用性，以保全网络其余部分的稳定。

黑洞路由是典型的「断尾求生」——它不是缓解攻击的常规手段，而是故障隔离与保护性降级的兜底机制。理解它的关键，是接受一个前提：在被黑洞的时间窗口内，该地址就是不可达的，不论流量合法与否。

## 二、核心原理
黑洞路由有两种落地形态。其一是本地静态黑洞：在路由器上把受害者前缀指向 null0（丢弃接口），去往该前缀的报文在本机被直接丢弃。其二是基于 BGP 的黑洞：通过 BGP 把受害者前缀连同「黑洞社区」属性通告给上游 AS，使上游网络也对去往该前缀的流量做丢弃，从而在更靠近源的位置止住流量。

两种形态的差别在于丢弃发生的「位置」：本地黑洞只能挡住已经到达你网络边界的流量，上游链路仍被占满；BGP 黑洞让上游提前丢弃，可保护你与上游之间的链路带宽，但需要与运营商约定社区值（社区语义是运营商策略，非全球统一标准）。

## 三、形式化与数学基础
把路由决策记为函数 $R(dst)$，返回下一跳。黑洞等价于对匹配前缀 $P$ 的流量强制：

$$ R(dst) = \text{null0}, \quad \forall dst \in P $$

本地黑洞下，合法流量 $\lambda_{legit}$ 与攻击流量 $\lambda_{attack}$ 一并被丢弃：

$$ \lambda_{served} = 0 $$

即受害者完全不可达。BGP 黑洞则把该决策通过路由通告传播到上游 AS：

$$ prefix\ P\ \xrightarrow{\ \text{BGP}\ } \ COMMUNITY(blackhole) $$

上游据此对 $P$ 执行丢弃，丢弃范围通常以特定的社区值限定到指定 ASN 或特定粒度，避免全网误伤。可用性折损以「不可达时长 × 受影响业务价值」衡量，因此黑洞通常配合自动触发阈值与最短持续时长使用。

## 四、代码实现
```bash
# Linux 主机侧静态黑洞路由
ip route add blackhole 192.0.2.0/24

# Cisco 风格：向 null0 指路
# ip route 192.0.2.0 255.255.255.0 Null0

# BGP 通告黑洞社区（示意，社区值以运营商约定为准）
# route-map RTBH permit 10
#   set community 65535:666
# router bgp 64500
#   network 192.0.2.0 mask 255.255.255.0 route-map RTBH
```

社区值、RTBH 触发方式（手动/自动）、以及是否支持「目的前缀 + 源前缀」精细化黑洞，均取决于运营商策略，落地前须与上游确认。

## 五、与其他技术对比
| 维度 | 黑洞路由 | 流量清洗 | 速率限制 |
| --- | --- | --- | --- |
| 对合法流量的影响 | 全部丢弃 | 尽量保留 | 超阈值部分丢弃 |
| 是否保住目标可用性 | 否，目标不可达 | 是 | 部分保留 |
| 部署位置 | 本地/上游 BGP | 清洗中心 | 边界/主机 |
| 适用场景 | 超大规模、无法区分 | 有指纹可识别 | 异常速率 |
| 代价 | 服务中断 | 成本与误杀 | 误伤正常突发 |

黑洞与清洗往往组合使用：攻击在清洗能力内则清洗，超出阈值或清洗失效则自动切黑洞兜底，攻击回落后再解除。

生产落地时，黑洞策略通常与一组「护栏」配套，避免被误触发或长期生效：

- 触发阈值：基于带宽、pps 或业务错误率设定，并区分「告警」与「自动黑洞」两档。
- 最短持续时长：避免攻击波动导致黑洞频繁通断，造成业务抖动。
- 自动解除：攻击回落并稳定一段时间后自动撤销通告。
- 影响面评估：黑洞前确认该前缀承载的业务与用户规模，必要时先通知业务方。
- 可观测性：记录每次黑洞的触发原因、时间、影响范围与解除时间。
- 演练验证：定期模拟触发，确认通告路径与解除流程真正可用。

BGP 黑洞的社区值并非全球统一标准，而是各运营商自行约定的「方言」，这意味着：

- 同一社区值在不同运营商处可能含义不同，甚至被忽略。
- 多上游场景需逐一确认支持的社区值与通告粒度。
- 精细化黑洞（按源前缀、按服务）的支持程度差异很大。

因此，落地前必须与上游完成「社区语义对齐」，并在演练中验证通告确实生效——配置正确并不等于上游真的执行了丢弃。

## 六、常见误区
误区一：「黑洞能缓解攻击又不掉线」。错，被黑洞的前缀完全不可达，任何访问都会失败。误区二：「黑洞只丢攻击流量」。错，它按目的前缀整体丢弃，合法流量一起牺牲。误区三：「黑洞应作为首选」。错，它是最后兜底，首选应是清洗与限速。误区四：「配了 BGP 社区就全网生效」。错，社区语义由运营商自定义，需逐家约定，未约定的上游不会执行。

## 九、演进与趋势
运营实践正走向更精细的黑洞：从「整前缀丢弃」演进到按五元组、源 ASN 或特定服务的定向丢弃，减少误伤。自动化方面，DDoS 防护平台把黑洞接入攻击检测流水线，超过阈值即触发 RTBH 并在攻击回落后自动解除。同时，任播与近源清洗在一定程度上减少了对黑洞的依赖，但极端场景下黑洞仍是不可替代的兜底。

## 十、小结
黑洞路由以牺牲目标 IP 可用性为代价，换取网络其余部分的稳定，是超大规模 DDoS 下的最后兜底手段。它的技术实现简单，难点在于「何时触发、通告给谁、如何解除」的运营决策。把它与清洗、限速编排成有序的降级链条，才是负责任的做法。
