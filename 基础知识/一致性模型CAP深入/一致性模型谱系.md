# 一致性模型谱系

> 对应 Kleppmann《Designing Data-Intensive Applications》第 9 章一致性模型层级。

## 一、背景与挑战
不同业务对“读到什么”的要求差异巨大：金融账务要强一致，社交动态可容忍短暂不一致。一致性模型定义了“系统允许返回哪些旧值”的契约，是上层正确性的基础。

## 二、核心原理
一致性模型按强度从强到弱构成谱系：
线性一致性(Linearizable) > 顺序一致性(Sequential) > 因果一致性(Causal) > 会话一致性(Session) > 单调读/单调写 > 最终一致性(Eventually Consistent) > 弱一致性。
越强的模型实现代价越高(延迟、协调成本)。

## 三、形式化 / 数学基础
- 线性一致性：存在全局实时序 <_real，且操作 op 在其区间 [start, end] 内某点原子生效，对所有进程可见顺序与 <_real 一致。
- 顺序一致性：存在合法全序满足每个进程的程序序，但不要求与实时一致。
- 因果一致性：偏序“happens-before”(a->b)必须被所有进程保持；并发写可乱序。

## 四、代码实现
```python
# 单调读：记录本会话见过的最大版本号，只接受 >= 它的读
class MonotonicReadClient:
    def __init__(self):
        self.seen = 0
    def read(self, store):
        v, ver = store.read()
        if ver >= self.seen:
            self.seen = ver
            return v
        return self.last  # 拒绝回退
```

## 五、与其他技术对比
- 线性一致需全局原子序，代价高；因果一致只排序因果相关事件，可水平扩展。
- 最终一致是 AP 系统的常见选择，但需应用层处理临时不一致。

## 六、常见误区
- 误区：最终一致等于“随便返回”。其实要求收敛(所有副本最终相同)。
- 误区：因果一致包含线性一致。其实因果一致弱于线性一致(不保证实时序)。

## 九、演进与趋势
云数据库(如 Spanner, CockroachDB)通过 TrueTime / 混合逻辑时钟逼近线性一致；弱一致模型向“可调一致性(tunable consistency)”发展。

## 十、小结
一致性模型是一致性强度的谱系，选择取决于业务对正确性与可用性的容忍度；理解各层级契约是设计分布式系统的前提。
