# 统计信息缺失导致的坏计划

> 对应 PostgreSQL 官方文档「Statistics Used by the Planner」与 MySQL 官方文档「Optimizer Statistics」，参考 DDIA 第3章。

## 一、背景与挑战
优化器所有代价估算都依赖统计信息（表行数、列基数、数据分布、索引唯一性）。若统计信息缺失或过期，优化器会基于错误假设选择极差计划，典型如选错连接顺序、放弃索引走全表。

## 二、核心原理
统计信息由 `ANALYZE`（PostgreSQL）或 `ANALYZE TABLE`（MySQL）/自动统计收集线程维护。缺失时优化器或退回默认常量估计（如假设选择性 1/1000），或基于极小的默认行数做判断，导致计划与实际数据严重不符。

## 三、形式化与数学基础
选择性估计依赖基数 $N$ 与 distinct 值数 $D$：
$$ sel = \frac{1}{D}, \quad est\_rows = N \cdot sel $$
当 $N$ 被默认成极小值（如 1000）而真实为 $10^8$，估计行数偏差达 $10^5$ 倍，直接误导扫描方式选择。

## 四、代码实现
```sql
-- PostgreSQL 手动更新统计
ANALYZE verbose orders;
-- 查看统计
SELECT reltuples, relpages FROM pg_class WHERE relname = 'orders';
```
MySQL 中 `SHOW TABLE STATUS` 或 `information_schema.STATISTICS` 观察。

## 五、与其他技术对比
列式存储（Abadi 等）在写入时即维护丰富的区块级统计（min/max），谓词下推可跳过整块，对统计依赖更天然。行存更依赖独立的 ANALYZE 作业。

## 六、常见误区
认为刚导入的大表立即可被优化器正确认识——往往需手动 ANALYZE。认为自动统计收集一定及时，批量加载后它可能尚未触发。

## 七、与开源书/权威来源对应
PostgreSQL 文档「Statistics Used by the Planner」明确列出默认统计与目标；DDIA 第3章「Storage and Retrieval」提及索引与统计对查询计划的影响。

## 八、面试题
问：新导入千万行后为啥查询变慢？答：可能统计信息没更新，优化器错误估算走了全表。问：怎么排查？答：看 EXPLAIN 的估计行数与真实差距，执行 ANALYZE 后对比。

## 九、演进与趋势
自动统计收集结合变更阈值触发、增量统计、甚至机器学习预测基数（如 learned cardinality）正在成为研究方向与部分商业库特性。

## 十、小结
坏计划的根因常是统计信息缺失或过期，及时 ANALYZE 与监控估计偏差是基本功。
