# 执行计划缓存与重新解析

> 对应 MySQL 官方文档 Query Cache（历史）与 Prepared Statements，以及 Oracle library cache 概念，参考 Silberschatz 第14章。

## 一、背景与挑战
硬解析（hard parse）需做词法分析、语法校验、语义检查、重写、优化器代价计算，代价高昂。高并发短查询下重复解析会成为瓶颈，计划缓存由此而生。

## 二、核心原理
数据库将 SQL 文本（或参数化后的指纹）映射到已生成的计划，存入共享计划缓存。后续相同 SQL 直接取出计划执行，跳过优化阶段，称为软解析（soft parse）。绑定变量（prepared statement）使不同参数复用同一计划。

## 三、形式化与数学基础
设单次硬解析代价 $C_{hard}$，软解析代价 $C_{soft} \ll C_{hard}$，命中率 $h$ 下平均代价：
$$ C_{avg} = h \cdot C_{soft} + (1 - h) \cdot C_{hard} $$
提升 $h$ 即降低平均代价。缓存淘汰常用 LRU。

## 四、代码实现
```sql
-- 使用预处理语句复用计划
PREPARE stmt FROM 'SELECT * FROM users WHERE id = ?';
SET @a = 5; EXECUTE stmt USING @a;
```
PostgreSQL 的 `PREPARE`/`EXECUTE` 与计划缓存（`plan_cache_mode`）类似。

## 五、与其他技术对比
Oracle 的 shared pool / library cache 是成熟计划缓存；MySQL 早期 Query Cache 缓存的是查询结果而非计划，且因失效粒度过粗在 8.0 被移除。PostgreSQL 默认对 prepared statement 缓存计划。

## 六、常见误区
认为计划缓存永远有益。统计信息变化后旧计划可能变差，需要失效重算。认为绑定变量万能，对数据倾斜列使用绑定变量可能得到不具代表性的通用计划（bind variable peeking 问题）。

## 七、与开源书/权威来源对应
Silberschatz《Database System Concepts》14.1 节查询处理概述；MySQL 官方文档「Server-Side Prepared Statements」。

## 八、面试题
问：为什么要用绑定变量？答：减少硬解析、防 SQL 注入、提升缓存命中。问：MySQL 8.0 为何移除 Query Cache？答：失效频繁、锁争用高、收益低。

## 九、演进与趋势
自适应计划（如 Oracle Adaptive Plans、SQL Server 的 deferred compilation）在首执后据运行时统计调整后续计划，缓解缓存过期与参数嗅探问题。

## 十、小结
计划缓存以软解析替代硬解析降低开销，但需配合统计信息更新与自适应机制防止计划退化。
