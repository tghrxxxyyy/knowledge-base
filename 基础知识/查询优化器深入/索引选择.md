# 索引选择

> 对应 Silberschatz《Database System Concepts》11 章与 13.6 物理设计，以及 Database Tuning 经典方法。

## 一、背景与挑战
索引加速查询但拖慢写入并占空间。应该为哪些列建索引、建什么类型，是物理设计难题。

## 二、核心原理
依据查询负载（谓词列、连接列、排序列）与列基数选索引。高选择性、常出现在 WHERE/JOIN/ORDER BY 的列优先。复合索引遵循最左前缀。写多读少表应少建。

## 三、形式化 / 数学基础
建索引收益 $B = \sum_{q \in workload} freq(q) \cdot (Cost_{no\_idx}(q) - Cost_{idx}(q))$，成本 $C = write\_overhead + space$。当 $B > C$ 时值得。最左前缀：复合索引 $(a,b,c)$ 可服务 $(a)$、$(a,b)$、$(a,b,c)$ 前缀查询。

## 四、代码实现
```sql
-- 仅为高频过滤列建复合索引
CREATE INDEX idx_orders_user_status
  ON orders (user_id, status);   -- 命中 WHERE user_id=? AND status=?
```

## 五、与其他技术对比
| 列特征 | 是否建索引 | 理由 |
|--------|------------|------|
| 高基数字段 | 是 | 选择性好 |
| 低基数字段 | 谨慎 | 位图更合适 |
| 常更新列 | 否 | 维护代价高 |

## 六、常见误区
1. 索引越多越好——写放大与空间上升。
2. 建了就能用——需符合最左前缀。
3. 函数列无法索引——可用函数索引。

## 九、演进与趋势

## 十、小结
索引选择是收益-成本权衡；依据查询模式与列选择性，复合索引最左前缀是必须遵守的规则。
