# 查询计划

> 对应 Silberschatz《Database System Concepts》第 13 章 Query Processing，以及 CMU 15-445 Lecture 12-13 Query Planning。

## 一、背景与挑战
同一条 SQL 可生成指数级等价执行计划，性能可差几个数量级。优化器需在有限时间内挑出代价最低的计划。

## 二、核心原理
查询处理分：解析→逻辑计划（关系代数）→代数重写→物理计划（选择算子实现如 hash/sort-merge join）→代价估算→选最优。计划以树表示，叶子是表扫描，内部是连接/聚合等。

## 三、形式化 / 数学基础
逻辑计划表示为关系代数表达式：
$$\pi_{name}(\sigma_{age>30}(R \bowtie_{R.id=S.rid} S))$$
计划枚举在连接顺序上有 $(2n-2)!/(n-1)!$ 种（左深树）可能。

## 四、代码实现
```sql
EXPLAIN
SELECT o.id FROM orders o JOIN users u ON o.uid=u.id WHERE u.city='BJ';
-- 输出：Hash Join / Seq Scan on users / Index Scan on orders
```

## 五、与其他技术对比
| 计划形状 | 搜索空间 | 优化难度 |
|----------|----------|----------|
| 左深树 | 小 | 易 |
| 右深树 | 中 | 中 |
| 浓密树（bushy） | 大 | 难 |

## 六、常见误区
1. 优化器永远选对——统计信息过期会选错。
2. EXPLAIN 显示实际执行——需 EXPLAIN ANALYZE。
3. 索引一定被用——小表全扫更快。

## 九、演进与趋势
自适应查询执行（如 PolarDB、CockroachDB）在运行中途根据真实基数调整计划；学习型优化器（Bao、Neo）用 ML 选计划。

## 十、小结
查询计划是从 SQL 到算子树的核心产物，计划质量取决于枚举策略与代价估算精度。
