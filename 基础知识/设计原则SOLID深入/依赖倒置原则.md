# 依赖倒置原则

> 对应 Martin《Clean Architecture》"Stable Abstractions"、GoF。

## 一、背景与挑战
高层业务直接依赖低层模块（如数据库、框架）时，低层变化会层层传导，导致业务代码难以测试与复用。

## 二、核心原理
DIP（Dependency Inversion Principle）：高层模块不应依赖低层模块，二者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象。即面向接口编程。

## 三、形式化 / 数学基础
依赖方向反转：传统 $High \rightarrow Low$，DIP 要求 $High \rightarrow Abstraction \leftarrow Low$。稳定度 $S$ 与抽象度 $A$ 应满足 $S \approx A$（见稳定抽象原则），使易变细节位于低抽象、低稳定侧。

## 四、代码实现
```python
from abc import ABC, abstractmethod
class Repository(ABC):
    @abstractmethod
    def save(self, e): ...
class Service:
    def __init__(self, repo: Repository):  # 依赖抽象
        self.repo = repo
```

## 五、与其他技术对比
DIP 常通过依赖注入（DI）落地；与 OCP 协同：抽象稳定，细节可替换。注意 DIP 不等同于"依赖注入框架"。

## 六、常见误区
误区：认为"只要用了接口就是 DIP"，但若抽象由低层定义且高层仍受控于低层，则未倒置。抽象应属于高层策略。

## 九、演进与趋势
六边形架构、整洁架构都把 DIP 作为核心：所有跨越边界的依赖都指向内侧抽象。

## 十、小结
让依赖箭头指向稳定的抽象，而非易变的实现。
