# 依赖倒置原则

> 对应 Martin《Clean Architecture》「The Dependency Inversion Principle」、Martin《Agile Software Development》与 GoF《Design Patterns》。

## 一、背景与挑战

当高层业务逻辑直接依赖低层实现（数据库、Web 框架、消息队列）时，低层的任何变化都会沿依赖链向上传导：换一个数据库就要改业务代码，测试业务逻辑必须启动真实数据库。系统变得僵硬、难以测试、难以复用。

依赖倒置原则（Dependency Inversion Principle, DIP）通过**反转依赖方向**解决这个问题：让高层与低层都依赖抽象，且抽象由高层拥有。

## 二、核心原理

DIP 的两条规则：

1. 高层模块不应依赖低层模块，二者都应依赖抽象。
2. 抽象不应依赖细节，细节应依赖抽象。

关键洞见是「谁拥有抽象」：接口应定义在高层策略一侧（因为它代表高层需要什么），由低层实现去适配。这与「先有接口还是先有实现」的直觉相反，故名「倒置」。

落地手段常是依赖注入（DI）：由外部（容器或构造函数）把具体实现传入，而非在内部 `new`。但 DIP ≠ DI 框架——手动传参同样满足 DIP。

## 三、形式化与数学基础

传统依赖方向为高层指向低层：

$$High \rightarrow Low$$

DIP 要求依赖箭头指向抽象，实现反向指向抽象：

$$High \rightarrow Abstraction \leftarrow Low$$

按 Robert Martin 的稳定抽象原则（SAP），组件稳定度 $I$ 与抽象度 $A$ 应满足 $I \approx A$：

$$I = \frac{Ce}{Ca + Ce}, \quad A = \frac{N_a}{N_c}$$

其中 $Ca$ 为入依赖数、$Ce$ 为出依赖数、$N_a$ 为抽象类数、$N_c$ 为类总数。稳定组件（$I$ 小）应更抽象（$A$ 大），易变细节应位于低抽象、低稳定侧。

## 四、代码实现

高层服务依赖抽象接口，而不依赖具体数据库。

```python
from abc import ABC, abstractmethod
from typing import List

class OrderRepository(ABC):          # 抽象由高层定义
    @abstractmethod
    def save(self, order) -> None: ...
    @abstractmethod
    def find(self, order_id: str): ...

class OrderService:                  # 高层业务
    def __init__(self, repo: OrderRepository):   # 依赖抽象
        self.repo = repo

    def place(self, order) -> None:
        self.repo.save(order)        # 只与抽象交互

class PostgresOrderRepo(OrderRepository):        # 低层细节实现抽象
    def save(self, order) -> None:
        pass                         # 写入 Postgres
    def find(self, order_id: str):
        return None

class InMemoryOrderRepo(OrderRepository):        # 测试替身
    def __init__(self):
        self.store = {}
    def save(self, order) -> None:
        self.store[order.id] = order
    def find(self, order_id: str):
        return self.store.get(order_id)
```

测试时传入 `InMemoryOrderRepo`，无需真实数据库；生产时传入 `PostgresOrderRepo`。

## 五、与其他技术对比

| 概念 | 含义 | 与 DIP 的关系 |
| --- | --- | --- |
| DIP | 依赖抽象，抽象属于高层 | 原则 |
| 依赖注入（DI） | 由外部提供依赖 | 落地手段之一 |
| 控制反转（IoC） | 控制权交给框架 | 更宽泛的机制 |
| 服务定位器 | 主动查询依赖 | 与 DIP 精神相悖（隐式依赖） |

注意：使用了接口不代表满足 DIP。若抽象由低层定义、高层仍被低层「牵着走」，则未真正倒置。

## 六、常见误区

- 误区一：用了接口就是 DIP。抽象归属才是关键，抽象应属于高层策略。
- 误区二：DIP 等于依赖注入框架。构造函数传参、工厂、甚至闭包都能实现 DIP。
- 误区三：所有依赖都要倒置。对稳定的标准库或纯函数，倒置只会增加间接层。
- 误区四：抽象越早越好。在真实变化点出现前过度抽象，会带来不必要的复杂度（见「原则权衡」）。

## 八、面试题

1. DIP 与依赖注入的关系？答：DIP 是原则，DI 是常见落地手段，二者不等价。
2. 抽象应由谁拥有？答：由高层策略拥有，低层实现去适配。
3. DIP 如何提升可测试性？答：可注入测试替身，隔离外部依赖。
4. 什么情况下不需要 DIP？答：依赖稳定且无替换需求时，倒置是多余复杂度。

## 九、演进与趋势

六边形架构、整洁架构、洋葱架构都把 DIP 作为核心：所有跨越边界的依赖都指向内侧的抽象。微服务与插件化架构中，端口-适配器（Ports & Adapters）是 DIP 的典型形态。

## 十、小结

DIP 的实质是「让依赖箭头指向稳定的抽象，并由高层拥有抽象」。它使业务逻辑独立于数据库、框架与传输细节，从而更易测试、复用与演进。判断是否倒置，只需问：如果要换掉低层实现，需要改动高层吗？
