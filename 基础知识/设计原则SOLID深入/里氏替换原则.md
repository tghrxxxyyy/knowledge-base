# 里氏替换原则

> 对应 Liskov 1987「Data Abstraction and Hierarchy」、Meyer《Object-Oriented Software Construction》与 Martin《Clean Architecture》。

## 一、背景与挑战

当子类覆写父类方法后，若调用方依赖父类契约却得到意外行为，系统会埋下隐蔽缺陷。最经典的例子是「正方形继承长方形」：从数学上看正方形是长方形，但从行为上看，正方形无法独立改变宽与高，因此破坏了调用方的假设。

问题根源在于：**「是一个（is-a）」的直觉分类并不等于「可替换（behaves-as）」**。LSP 把关注点从继承结构转移到行为契约。

## 二、核心原理

里氏替换原则（Liskov Substitution Principle, LSP）：子类型必须能够替换其基类型，且使用基类型的程序在替换后行为不被破坏。

它约束三层含义：

1. **签名兼容**：方法可被调用（多数语言已由类型系统保证）。
2. **前置条件不增强**：子类不能要求比父类更多的输入约束。
3. **后置条件不削弱**：子类不能给出比父类更弱的保证。
4. **不变量保持**：父类的不变量在子类中必须继续成立。
5. **历史约束**：子类不应引入父类未声明、且会破坏调用方假设的副作用。

关键判据是「行为契约」，而非「继承关系本身」。

## 三、形式化与数学基础

按 Bertrand Meyer 的契约式设计（Design by Contract），设父类方法 $m_{base}$ 与子类覆写 $m_{sub}$，前置条件 $pre$、后置条件 $post$、不变量 $inv$：

$$pre_{base}(x) \Rightarrow pre_{sub}(x)$$

即子类前置条件不能强于父类（调用方按父类调用的输入必须仍被接受）；以及：

$$post_{sub}(x) \Rightarrow post_{base}(x)$$

即子类后置条件不能弱于父类（子类必须至少兑现父类的承诺）。不变量约束为：

$$inv_{base} \Rightarrow inv_{sub}$$

综合起来，替换安全的条件是：

$$\forall x:\ \big(pre_{base}(x) \land \text{子类执行 } m_{sub}\big) \Rightarrow post_{base}(x) \land inv_{base}$$

## 四、代码实现

反例：企鹅继承鸟却无法飞行，破坏了「所有鸟会飞」的假设。

```python
class Bird:
    def fly(self) -> None:
        raise NotImplementedError

class Penguin(Bird):
    def fly(self) -> None:
        raise RuntimeError("penguins cannot fly")   # 破坏 LSP
```

正例：把「会飞」抽象为独立能力，只让真正会飞的类型实现它。

```python
from abc import ABC, abstractmethod

class Bird(ABC):
    @abstractmethod
    def move(self) -> str: ...

class FlyingBird(Bird):
    def move(self) -> str:
        return "fly"

    def fly(self) -> str:
        return "fly high"

class Penguin(Bird):
    def move(self) -> str:
        return "swim"                # 满足 Bird.move 的契约
```

另一个典型修复：把可变的长方形与不可变的正方形拆开，或都改为不可变类型。

## 五、与其他技术对比

| 概念 | 关注点 | 与 LSP 的关系 |
| --- | --- | --- |
| LSP | 行为契约可替换 | 本体 |
| 结构化子类型（鸭子类型） | 有对应方法即可用 | 更弱，不保证契约 |
| 契约式设计（DbC） | 前置/后置/不变量 | 为 LSP 提供形式基础 |
| OCP | 扩展而不改旧码 | 以 LSP 为前提 |

LSP 是 OCP 得以成立的前提：只有子类可替换，才能安全地对扩展关闭。

## 六、常见误区

- 误区一：编译通过即满足替换。类型系统保证签名，不保证行为契约（异常、不变量、性能语义）。
- 误区二：is-a 就应继承。正方形/长方形、栈/列表都是「集合关系成立但行为不成立」的经典反例。
- 误区三：LSP 只针对类继承。接口实现、多态分派、甚至函数指针替换同样适用。
- 误区四：覆写时抛出新异常无害。若父类不抛该异常，调用方未处理，替换即失败。

## 七、与开源书·权威来源对应

## 八、面试题

1. 为什么「正方形继承长方形」违反 LSP？答：调用方依赖「可独立修改宽高」的契约，正方形无法满足。
2. 如何判断子类是否可替换？答：检查前置条件是否增强、后置条件是否削弱、不变量与异常是否兼容。
3. LSP 与鸭子类型的关系？答：鸭子类型只看方法存在，LSP 更强调行为契约。
4. 如何避免 LSP 违例？答：优先组合而非继承，用能力接口（如 FlyingBird）替代宽泛基类。

## 九、演进与趋势

现代语言以不可变类型、代数数据类型（ADT）、基于 trait/接口的组合降低 LSP 违例风险；契约式设计与属性测试（property-based testing）可自动发现契约破坏。核心思想不变：替换性由行为契约定义。

## 十、小结

LSP 的本质是「行为可替换」，由前置条件、后置条件、不变量共同定义，而非继承结构。判断一个设计是否满足 LSP，最实用的方法是问：调用方对基类行为的每一个假设，子类是否都成立？
