# 开闭原则

> 对应 Meyer《Object-Oriented Software Construction》提出的开闭原则与 Martin《Clean Architecture》组件原则。

## 一、背景与挑战

需求持续变化，但频繁修改已上线、已测试的稳定代码会引入缺陷，也让回归测试成本不断攀升。理想状态下，新增一种业务规则不应要求修改已有类，而应通过「增加新代码」来完成。

开闭原则（Open-Closed Principle, OCP）正是回答这个问题：让系统**对扩展开放、对修改关闭**。难点在于如何找到那个「不变量」——锁定它，让变化通过扩展进入。

## 二、核心原理

OCP 的表述：软件实体（类、模块、函数）应当对扩展开放，对修改关闭。

实现机制是**抽象 + 多态**：

1. 识别变化维度，把稳定契约抽象为接口或抽象类。
2. 让调用方只依赖抽象，不依赖具体实现。
3. 新增行为时，实现一个新类即可，调用方代码不变。

表达式：客户端依赖接口 $I$，具体实现 $\{C_1, C_2, \dots\}$ 可无限扩展；新增 $C_{n+1}$ 不触碰客户端。典型模式包括策略、工厂、模板方法、观察者。

关键是抽象要放在**真正的变化点**上，而非猜测的变化点上。

## 三、形式化与数学基础

设模块 $M$ 处理行为集合 $B$。当新增行为 $b_{new}$ 时，理想情况下被修改的代码规模应尽量小：

$$extension(M, b_{new}) = M \cup \{M_{new}\}, \quad M_{old}\ \text{unchanged}$$

即改动量 $|M_{changed}| \to |M_{new}|$，而已有部分保持不变。借助依赖倒置，$M_{old}$ 只依赖抽象 $A$：

$$M_{old} \rightarrow A \leftarrow M_{new}$$

扩展的代价与「变化点是否已被抽象覆盖」相关。若抽象覆盖了变化维度，则新增行为成本为常数：

$$Cost(add\ b) = O(1)$$

若未抽象，则每次变化都要修改核心逻辑，成本随行为数线性增长 $O(n)$。OCP 的价值就是把 $O(n)$ 的修改成本降到 $O(1)$ 的扩展成本。

## 四、代码实现

以折扣策略为例，新增折扣无需改动调用方。

```java
public interface Discount {
    double apply(double price);
}

public class NoDiscount implements Discount {
    public double apply(double price) { return price; }
}

public class VipDiscount implements Discount {
    public double apply(double price) { return price * 0.9; }
}

public class Checkout {
    private final Discount discount;
    public Checkout(Discount discount) { this.discount = discount; }

    public double total(double price) {
        return discount.apply(price);        // 依赖抽象，行为可扩展
    }
}
```

新增会员折扣时，只需新增一个实现类，`Checkout` 完全不动。

```java
public class MemberDiscount implements Discount {
    public double apply(double price) { return price * 0.95; }
}
```

## 五、与其他技术对比

| 概念 | 关注点 | 与 OCP 的关系 |
| --- | --- | --- |
| OCP | 扩展开放、修改关闭 | 本体 |
| SRP | 变化原因单一 | 划定抽象边界 |
| DIP | 依赖抽象 | 提供实现手段 |
| GoF 策略/工厂 | 封装可替换行为 | 常见落地模式 |
| YAGNI | 不提前实现 | 约束 OCP 的过度使用 |

OCP 依赖抽象，而滥用抽象会导致复杂度上升。SRP 定边界、OCP 定演化方式、DIP 提供方向，三者协同。

## 六、常见误区

- 误区一：为每一个可能的变化预先抽象，造成过度设计。应在真实变化点出现后再引入抽象。
- 误区二：认为必须完全「零修改」。现实中接口升级、配置调整难以完全避免，OCP 是方向而非绝对。
- 误区三：只有继承才能开闭。策略、组合、函数式传入高阶函数同样实现 OCP。
- 误区四：抽象层级越高越好。抽象若不稳定，反而把变化扩散到所有实现。

## 七、与开源书·权威来源对应

- Meyer, B.《Object-Oriented Software Construction》，OCP 的原始提出。
- Martin, R. C.《Clean Architecture》「The Open-Closed Principle」。
- Gamma, E. et al.《Design Patterns》，策略、工厂方法、模板方法。
- Fowler, M.《Refactoring》，以重构让抽象「长出来」。

## 八、面试题

1. 如何在项目中落地 OCP？答：识别变化维度，抽象为接口，让调用方依赖抽象，新增行为走实现类。
2. 什么情况下不应应用 OCP？答：变化尚未发生或极少发生，提前抽象只增复杂度。
3. OCP 与 DIP 的关系？答：DIP 是达成 OCP 的主要手段（依赖抽象使扩展成为可能）。
4. 如何避免 OCP 导致的抽象泄漏？答：抽象应表达稳定契约，避免把实现细节暴露进接口。

## 九、演进与趋势

插件化架构、SPI（Service Provider Interface）、Feature Toggle 都是 OCP 在运行期/部署期的延续：通过配置与注册机制扩展行为，而不重新编译核心。微内核与事件驱动架构也以 OCP 为设计哲学。

## 十、小结

OCP 用抽象锁定稳定契约、用扩展接纳变化，把修改成本从 $O(n)$ 降到 $O(1)$。落地要点是：抽象只加在真实变化点上，避免为想象中的未来买单——这也是它与 YAGNI 之间需要持续权衡的原因。
