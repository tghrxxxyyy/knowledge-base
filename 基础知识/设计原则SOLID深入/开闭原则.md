# 开闭原则

> 对应 Martin《Clean Architecture》组件原则、Bertrand Meyer 提出。

## 一、背景与挑战
需求持续变化，但频繁修改已上线、已测试的稳定代码会引入缺陷。需要让系统对扩展开放、对修改封闭。

## 二、核心原理
OCP（Open-Closed Principle）：软件实体（类、模块、函数）应当对扩展开放，对修改关闭。通过抽象与多态，新增行为时仅增加新代码，不改旧代码。

## 三、形式化 / 数学基础
设模块 $M$ 处理行为集合 $B$。当新增 $b_{new}$，理想情况下 $|M_{changed}|$ 应尽量小：
$$extension(M, b_{new}) = M \cup \{M_{new}\},\quad M_{old}\ unchanged$$
依赖倒置与策略模式使 $M_{old}$ 仅依赖抽象 $A$。

## 四、代码实现
```java
interface Discount { double apply(double p); }
class NoDiscount implements Discount { public double apply(double p){return p;} }
class VipDiscount implements Discount { public double apply(double p){return p*0.9;} }
// 新增 MemberDiscount 时无需改动调用方代码
```

## 五、与其他技术对比
OCP 依赖抽象，而滥用抽象会导致"抽象泄漏"与复杂度上升。与 SRP 配合：SRP 定边界，OCP 定演化方式。

## 六、常见误区
误区：为每一个可能的变化预先抽象，造成过度设计。应在"真实变化点"出现后再引入抽象（见重构节奏）。

## 七、与开源书 / 权威来源对应

## 八、面试题
"如何在项目中落地开闭原则？什么情况下不应该应用它？"

## 九、演进与趋势
插件化架构、SPI、Feature Toggle 都是 OCP 在运行期/部署期的延续。

## 十、小结
用抽象锁定稳定契约，用扩展接纳变化，但避免过度抽象。
