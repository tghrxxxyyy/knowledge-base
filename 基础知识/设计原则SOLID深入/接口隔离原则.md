# 接口隔离原则

> 对应 Martin《Clean Architecture》「Interface Segregation Principle」与 GoF 客户端特定接口思想。

## 一、背景与挑战

一个「胖接口」把许多不相关的方法捆在一起，强制实现类提供它不需要的方法（常见做法是抛 `UnsupportedOperationException`），也强制调用方依赖它不使用的部分。结果是耦合面变大：接口任何一处变更，所有实现类与调用方都要重新编译、测试、部署。

接口隔离原则（Interface Segregation Principle, ISP）主张：把接口按客户端需要切小，谁用哪些方法就依赖哪些接口。

## 二、核心原理

ISP 的表述：客户端不应被迫依赖它不使用的方法。

具体含义：

- **按客户端分组**：为不同的客户端角色定义各自的接口，而非一个通用大接口。
- **小而专**：每个接口围绕一组内聚的、被同一类客户端使用的方法。
- **避免接口污染**：不要让某个客户端的变更波及无关客户端。

常见落地形态是「角色接口（Role Interface）」：接口代表「在某个协作关系中扮演的角色」，而非「对象的全部能力」。注意 ISP 关注的是**调用方依赖面**，而 SRP 关注的是**实现变化原因**。

## 三、形式化与数学基础

设胖接口 $I$ 的方法集为 $M$，客户端 $C$ 实际只使用子集 $M_C \subset M$。ISP 要求存在接口 $I_C$ 使：

$$M(I_C) = M_C, \quad C \text{ 仅依赖 } I_C$$

于是客户端 $C$ 的依赖面从 $|M|$ 降为 $|M_C|$。定义耦合度：

$$Dep(C) = \sum_{i} |M(I_i)|$$

ISP 的目标是最小化每个客户端的 $Dep(C)$。接口变更的影响面也随之缩小：修改 $I_C$ 只影响使用 $M_C$ 的客户端，而非全部 $|M|$ 使用者。

若把接口粒度记为 $g$（每个接口的平均方法数），存在权衡：$g$ 过大会造成被迫依赖，$g$ 过小会造成接口数量爆炸与组合成本，其最优值同样由「变更隔离收益 vs 组合复杂度」的边际平衡决定。

## 四、代码实现

反例：一体化的多功能设备接口。

```java
interface MultiFunctionDevice {
    void print(String doc);
    void scan(String doc);
    void fax(String doc);
}
```

正例：按能力拆分为小接口，各设备只实现所需。

```java
interface Printer {
    void print(String doc);
}

interface Scanner {
    void scan(String doc);
}

class SimplePrinter implements Printer {
    public void print(String doc) {
        // 仅实现打印
    }
}

class AllInOne implements Printer, Scanner {
    public void print(String doc) { /* ... */ }
    public void scan(String doc) { /* ... */ }
}
```

调用方只依赖它真正使用的能力。

```java
class DocumentService {
    private final Printer printer;      // 只依赖 Printer，不关心 scan/fax
    DocumentService(Printer printer) { this.printer = printer; }

    void render(String doc) { printer.print(doc); }
}
```

## 五、与其他技术对比

| 原则 | 关注点 | 拆分依据 |
| --- | --- | --- |
| ISP | 客户端依赖面 | 按客户端/角色 |
| SRP | 实现变化原因 | 按 actor |
| OCP | 扩展而不改旧码 | 按变化维度 |
| 角色接口 | 协作关系中的能力 | 按使用场景 |

ISP 与 SRP 相似（都反对「大而全」），但 ISP 站在调用方视角，SRP 站在实现方视角。

## 六、常见误区

- 误区一：接口越碎越好，导致接口爆炸。应按真实客户端分组，而非每个方法一个接口。
- 误区二：ISP 就是 SRP。二者视角不同：ISP 看依赖，SRP 看变化原因。
- 误区三：单实现接口没意义。只要有多个客户端或需要考虑变更隔离，专接口就有价值。
- 误区四：只在语言层拆分。文档、API 边界、模块依赖也应遵循 ISP 思想。

## 八、面试题

1. ISP 与 SRP 的区别？答：ISP 关注客户端依赖面，SRP 关注实现的变化原因。
2. 何时该拆分接口？答：当不同客户端使用不同方法子集、或接口变更会波及无关客户端时。
3. 拆分过度的代价与语言新特性的影响？答：拆分过度会导致接口数量爆炸、组合与文档成本上升；默认方法/trait 缓和了接口膨胀，但客户端视角依然有效。

## 九、演进与趋势

语言层面的默认方法（default method）、trait、协议扩展缓和了「加方法就得改所有实现」的痛点，但并未消除 ISP 的核心关切：不要让客户端依赖它不需要的东西。微服务与 API 网关设计中，ISP 思想体现为按消费者划分的细粒度 API。

## 十、小结

ISP 的核心是「按客户端而非实现者切分接口」，从而缩小依赖面与变更影响范围。判断一个接口是否违反 ISP，只需问：是否存在某个客户端被迫依赖它从不调用的方法？若有，就该拆。
