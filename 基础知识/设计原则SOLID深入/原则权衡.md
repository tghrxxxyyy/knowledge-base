# 原则权衡

> 对应 Martin《Clean Architecture》组件聚合张力、Clean Code 务实态度。

## 一、背景与挑战
SOLID 五原则并非总是同向：强抽象提升灵活性的同时增加间接层与认知成本，盲目追求会损害可维护性。

## 二、核心原理
原则之间存在张力：SRP 与 DIP 可能增加文件数；ISP 与 OCP 需要前瞻抽象。应在"当前真实变化率"与"可理解性"之间权衡，避免教条式应用。

## 三、形式化 / 数学基础
以成本建模：总维护成本 $C = C_{change} + C_{complexity}$。抽象降低 $C_{change}$ 但抬高 $C_{complexity}$。最优抽象度使 $\frac{dC}{da}=0$，即边际收益等于边际成本。

## 四、代码实现
```python
# 当变化尚未出现，简单过程式函数更优
def checkout(cart):  # 暂不需要 Discount 抽象
    total = sum(i.price for i in cart)
    return total
# 待出现第二种折扣策略时再重构为策略模式
```

## 五、与其他技术对比
与 YAGNI（You Aren't Gonna Need It）互补：不为臆测变化提前抽象。与 KISS 共同约束复杂度。

## 六、常见误区
误区：把 SOLID 当硬性清单逐条满足。误区：用原则互相攻击而非讨论成本收益。

## 九、演进与趋势
领域驱动与整洁架构提供分层视角，使原则在架构边界处应用、在内部保持简单。

## 十、小结
原则服务可维护性，权衡依据真实变化率与复杂度成本。
