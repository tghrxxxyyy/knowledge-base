# 原则权衡

> 对应 Martin《Clean Architecture》组件内聚与耦合章节，以及 Fowler《Refactoring》的务实重构节奏。

## 一、背景与挑战

SOLID 五原则并非总是同向：强化抽象提升灵活性的同时增加间接层与认知成本；为满足接口隔离而细分接口，可能带来接口爆炸；为满足开闭而预留扩展点，可能变成臆测式设计。

把 SOLID 当成必须逐条满足的硬性清单，结果往往是过度设计——系统比需求更复杂，维护者反而更难理解。原则的目的是服务可维护性，而不是自我实现。

## 二、核心原理

原则之间存在真实张力：

- **SRP 与 DIP**：为倒置依赖而引入抽象，会新增文件与跳转层级，抬升复杂度。
- **ISP 与 OCP**：接口切得越细，扩展越灵活，但客户端要组合更多接口。
- **OCP 与 YAGNI**：为「可能的变化」提前抽象，与「不实现不需要的功能」直接冲突。

正确的做法是：**在真实变化率与可理解性之间权衡**，让抽象的出现由实际变化驱动，而非由想象驱动。

## 三、形式化与数学基础

以成本建模。设抽象度为 $a$（可理解为抽象层数与接口粒度），总维护成本由「变更成本」与「复杂度成本」组成：

$$C(a) = C_{change}(a) + C_{complexity}(a)$$

其中 $C_{change}$ 随抽象度上升而下降（变化被局部化），$C_{complexity}$ 随抽象度上升而上升（更多间接层）。最优抽象度满足一阶条件：

$$\frac{dC}{da} = 0 \quad\Longrightarrow\quad -\frac{dC_{change}}{da} = \frac{dC_{complexity}}{da}$$

即**边际收益等于边际成本**。若当前变化率低，$dC_{change}/da$ 很小，最优点 $a^*$ 靠近零（少抽象）；变化率升高时，$a^*$ 右移（值得抽象）。

用期望变化率 $\lambda$ 表达更直观：只有当

$$\lambda \cdot \Delta C_{change} > \Delta C_{complexity}$$

时，引入抽象才划算。

## 四、代码实现

变化尚未出现时，简单过程式实现更优；出现第二种策略后再重构。

```python
# 阶段一：只有一种计价方式，直接写清晰
def checkout(cart) -> float:
    return sum(item.price for item in cart)
```

```python
# 阶段二：出现会员折扣、活动折扣等多种策略，此时才引入抽象
from abc import ABC, abstractmethod

class Pricing(ABC):
    @abstractmethod
    def total(self, cart) -> float: ...

class RegularPricing(Pricing):
    def total(self, cart) -> float:
        return sum(i.price for i in cart)

class VipPricing(Pricing):
    def total(self, cart) -> float:
        return sum(i.price for i in cart) * 0.9

def checkout(cart, pricing: Pricing) -> float:
    return pricing.total(cart)
```

重构的典型节奏：先让代码工作且清晰，当同一处因相同原因反复变化时，再抽象。这与 Fowler《Refactoring》中「坏味道驱动重构」一致。

## 五、与其他技术对比

| 原则 | 主张 | 潜在冲突 |
| --- | --- | --- |
| SOLID（尤其 OCP/DIP） | 面向变化抽象 | 与 YAGNI 冲突 |
| YAGNI | 不实现不需要的 | 与前瞻性扩展冲突 |
| KISS | 保持简单 | 与过度分层冲突 |
| DRY | 消除重复 | 与「错误抽象比重复更糟」冲突 |

这些不是彼此否定的教条，而是需要按上下文权衡的力。DRY 尤其要警惕：过早消除「看起来相似」的代码，可能产生耦合不同变化原因的坏抽象。

## 六、常见误区

- 误区一：把 SOLID 当硬性清单逐条满足。原则是启发式，不是验收标准。
- 误区二：用原则互相攻击。「你不满足 OCP」若忽略真实变化率，就是教条。
- 误区三：DRY 高于一切。重复有时优于错误抽象（三次法则：出现三次再抽象）。
- 误区四：抽象总是有益。抽象是负债也是资产，取决于它能被复用的次数。

## 八、面试题

1. 什么时候不应应用开闭原则？答：真实变化尚未出现时，提前抽象是过度设计。
2. 如何向团队解释过度设计？答：用变更成本与复杂度成本的边际权衡说明收益不足。
3. DRY 与「错误抽象」如何取舍？答：遵循三次法则，先观察是否因同一原因重复变化。
4. SOLID 冲突时如何决策？答：以真实变化率与可理解性为依据，而非原则优先级。

## 九、演进与趋势

领域驱动设计与整洁/六边形架构提供分层视角：在架构边界处应用抽象（DIP、OCP），在领域内部保持简单直接。测试驱动与持续重构让抽象由真实需求「长出来」，而非预先设计出来。

## 十、小结

原则服务可维护性而非相反。权衡的依据是「真实变化率」与「复杂度成本」：当 $-\frac{dC_{change}}{da} = \frac{dC_{complexity}}{da}$ 时达到最优抽象度。实践中坚持「先简单、按坏味道重构」，比背诵 SOLID 清单更能产生好设计。
