# 单一职责原则

> 对应 Martin《Clean Code》第 10 章「Classes」与 Martin《Agile Software Development, Principles, Patterns, and Practices》中 SRP 章节。

## 一、背景与挑战

一个类承担过多职责时，修改一个功能会波及看似无关的功能：改持久化逻辑不小心破坏了业务计算，加日志字段却引发序列化回归。这类代码难以测试（要构造大量依赖）、难以并行开发（多人改同一文件冲突不断）。

典型症状是「上帝类」：一个类同时包含业务计算、数据持久化、日志、序列化与校验。

## 二、核心原理

单一职责原则（Single Responsibility Principle, SRP）：一个模块（类/函数）应该有且仅有一个导致其变化的原因（one reason to change）。

关键升级：Robert Martin 后来强调，变化原因来自**角色（actor）**。每个 actor 对应一组内聚的需求，若一个类要同时满足多个 actor 的需求，这些需求的变化会互相牵制。

因此 SRP 的判据不是「功能数量」或「代码行数」，而是：**这个类会被几类不同的利益相关者要求修改？** 只有一个 actor 时，即使方法很多也可能内聚；有多个 actor 时，即使方法很少也应拆分。

## 三、形式化与数学基础

设类 $c$ 的职责集合为 $R(c) = \{r_1, r_2, \dots, r_n\}$，每个职责对应 actor $a_i$。若存在 $r_i, r_j$ 属于不同 actor，且二者对代码的修改会相互耦合（修改一个易影响另一个），则应拆分：

$$\exists i \ne j:\ a_i \ne a_j \ \land\ \frac{\partial c}{\partial r_i} \not\perp \frac{\partial c}{\partial r_j} \ \Longrightarrow\ \text{split}(c)$$

内聚度可量化为方法对字段的引用集中度：

$$Cohesion = \frac{\text{被多个方法共同引用的字段数}}{\text{字段总数}}$$

低内聚往往提示职责过多。另一种度量是 LCOM（Lack of Cohesion of Methods），值越大越不内聚。

## 四、代码实现

反例：一个类既管业务计算又管持久化。

```python
class Report:
    def calculate(self, data):
        return {"total": sum(data)}

    def save_to_db(self, report):
        pass        # 持久化职责：数据库结构变化会波及本类
```

正例：按 actor 拆分，计算与持久化各有唯一变化原因。

```python
class ReportCalculator:
    def calculate(self, data):
        return {"total": sum(data)}


class ReportRepository:
    def save(self, report):
        pass        # 只有存储格式变化时才需修改


class ReportService:
    def __init__(self, calc: ReportCalculator, repo: ReportRepository):
        self.calc = calc
        self.repo = repo

    def generate(self, data):
        report = self.calc.calculate(data)
        self.repo.save(report)
        return report
```

这样财务改计算规则只动 `ReportCalculator`，DBA 改表结构只动 `ReportRepository`。

## 五、与其他技术对比

| 概念 | 关注点 | 粒度 |
| --- | --- | --- |
| SRP | 变化原因（actor） | 类/模块/函数 |
| 高内聚低耦合 | 模块内部关联与模块间依赖 | 通用设计原则 |
| 关注点分离（SoC） | 不同关注点独立 | 架构层 |
| ISP | 客户端依赖面 | 接口 |

SRP 与「高内聚」是同一思想的不同粒度表述；SoC 更偏架构。SRP 的独特之处在于聚焦「变化原因」。

## 六、常见误区

- 误区一：按功能数量拆分，导致过度碎片化。判据是 actor，不是方法数量。
- 误区二：把所有 setter 当一个职责。应看它们服务于哪个 actor。
- 误区三：SRP 意味着每个类只能有一个方法。方法可以很多，只要它们因同一原因变化。
- 误区四：拆分越细越好。过度拆分会增加跳转与装配成本，需权衡（见「原则权衡」）。

## 八、面试题

1. SRP 中的单一职责指什么？答：一个变化原因/一个 actor，而非一个功能。
2. 如何判断一个类职责过多？答：看它是否被多类 actor 要求修改、内聚度是否低。
3. SRP 与高内聚的区别？答：高内聚是度量，SRP 是判据（变化原因）。
4. 拆分到什么程度停止？答：当每个模块只有一个 actor 触发变化，且拆分收益不再超过成本时。

## 九、演进与趋势

微服务语境下，SRP 上升到服务级：每个服务对应一个业务能力，由单一团队（actor）拥有。这与领域驱动设计的限界上下文互补——限界上下文界定模型边界，SRP 界定变化归属。

## 十、小结

SRP 的判据是「变化原因/actor」，而非代码行数或方法数。以 actor 为唯一标准拆分，能有效降低回归风险与耦合；但也要警惕过度碎片化，把拆分收益与复杂度成本放在一起权衡。
