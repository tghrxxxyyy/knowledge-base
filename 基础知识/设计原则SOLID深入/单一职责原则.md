# 单一职责原则

> 对应 Martin《Clean Code》第10章、Martin《Agile Software Development》SRP。

## 一、背景与挑战
一个类承担过多职责时，修改一个功能会影响看似无关的功能，导致回归风险高、测试困难、并行开发冲突。典型症状：一个类同时包含业务计算、持久化与日志。

## 二、核心原理
SRP（Single Responsibility Principle）：一个模块（类/函数）应该有且仅有一个导致其变化的原因（one reason to change）。变化原因来自不同角色（actor），每个 actor 对应一组内聚的需求。

## 三、形式化 / 数学基础
职责集合 $R(c)=\{r_1,r_2,\dots,r_n\}$。若 $r_i$ 与 $r_j$ 对应不同 actor，且 $\frac{\partial c}{\partial r_i}$ 与 $\frac{\partial c}{\partial r_j}$ 互相耦合，则应拆分。内聚度可量化为 $Cohesion=\frac{相关字段引用数}{方法数}$，低内聚提示职责过多。

## 四、代码实现
```python
# 反例：一个类既管业务又管持久化
class Report:
    def calculate(self, data): ...
    def save_to_db(self, data): ...

# 正例：按 actor 拆分
class ReportCalculator:
    def calculate(self, data): ...

class ReportRepository:
    def save(self, report): ...
```

## 五、与其他技术对比
与"高内聚低耦合"是同一思想的不同粒度表述；关注点分离（SoC）更偏架构层。SRP 聚焦"变化原因"，而非"功能数量"。

## 六、常见误区
误区一：按功能数量而非变化原因拆分，导致过度碎片化。误区二：把所有 setter 当一个职责。正确判据是 actor 而非方法数。

## 九、演进与趋势
微服务语境下 SRP 上升到服务级（每个服务一个业务能力），与领域驱动设计的限界上下文互补。

## 十、小结
以"变化原因/actor"为唯一判据拆分，降低回归与耦合。
