# 信号机制与信号处理函数

> 对应 Kerrisk《The Linux Programming Interface》第 20 章信号与 Bryant & O'Hallaron《CSAPP》第 8 章异常控制流。

## 一、背景与挑战
信号是内核向进程异步通知事件的软件中断：如 `Ctrl-C`(SIGINT)、子进程退出(SIGCHLD)、非法指令(SIGILL)。进程需注册处理器或采用默认动作，否则可能被终止。

## 二、核心原理
每个进程有信号掩码与挂起集。内核或进程用 `kill`/`raise` 发信号，若未被阻塞则"递送"（deliver）：执行 `sa_handler` 或默认动作（终止/忽略/停止）。处理函数运行于进程上下文、打断正常执行流，类似软中断。

## 三、形式化与数学基础
递送条件：
$$deliver(s) \iff s \notin blocked \land s \in pending$$
未决信号通常只计一次（标准信号不排队），实时信号（`SIGRTMIN+`）按队列保序。处理期间自动阻塞该信号以防重入（除非 `SA_NODEFER`）。

## 四、代码实现
```c
void handler(int sig) { write(1, "got\n", 4); }
int main(void) {
    signal(SIGINT, handler);     // 或 sigaction 更安全
    while (1) pause();           // 等待信号
    return 0;
}
```

## 五、与其他技术对比
信号异步类似硬件中断但运行于进程、可阻塞；相较管道/共享内存等 IPC，信号带宽极低仅作通知。相较异常（同步），信号多为异步（除 SIGSEGV 等同步信号）。

## 六、常见误区
误以为信号处理里能调任意 libc 函数：只能调 async-signal-safe 函数（如 `write`），禁 `printf`/`malloc`。误以为标准信号会排队：不排队只置位。误以为 `signal()` 可移植：语义随实现变，应用 `sigaction`。

## 七、与开源书/权威来源对应
Kerrisk 第 20-21 章信号与 async-signal-safe；CSAPP 8.5 异常控制流与信号。

## 八、面试题
问：信号处理函数为什么不能用 printf？答：非 async-signal-safe，可能死锁。问：SIGKILL 能捕获吗？

## 九、演进与趋势
`signalfd` 把信号转文件描述符，便于事件循环（epoll）统一处理；实时信号提供可靠排队。

## 十、小结
信号是异步软件中断，理解递送/阻塞与 async-signal-safe 约束是编写健壮 Unix 程序的基础。
