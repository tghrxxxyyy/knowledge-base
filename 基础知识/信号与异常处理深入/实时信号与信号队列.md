# 实时信号与信号队列

> 对应 Kerrisk《The Linux Programming Interface》第 22 章「信号：高级特性」，以及 POSIX 实时扩展中关于排队信号与 `sigqueue` 的规定。

## 一、背景与挑战
标准信号（1–31）有三个结构性缺陷：**不排队**（同一信号多次产生只保留一次）、**不携带数据**、**无优先级**。对「必须可靠送达且需要携带参数」的场景——实时音视频控制消息、用户态代理模拟硬件中断、异步 I/O 完成通知——标准信号完全不够用。
POSIX 实时扩展引入实时信号（`SIGRTMIN` 至 `SIGRTMAX`）补齐这三点：可排队、按序递送、可通过 `sigqueue` 附带一个 `sigval`。代价是每个排队信号需要分配内核对象，因此存在配额，配额耗尽时投递会失败——这本身就是必须处理的边界情况。

## 二、核心原理
实时信号的排队由内核 `sigqueue` 结构承载：发送时 `__send_signal_locked` 为信号分配节点并挂到目标线程的队列；若无配额则发送失败并返回 `EAGAIN`。标准信号走位图路径（`sigset_t pending`），置位即合并。
递送顺序有明确定义：**先按信号号升序，同号内按入队顺序（FIFO）**。这常被误解为「纯 FIFO」——实际上 `SIGRTMIN+1` 会优先于 `SIGRTMIN+2`，即使后者先到。glibc 把 `SIGRTMIN` 之后的若干编号保留给 pthread 内部使用（线程取消、`setxid` 等），因此应用应通过 `__libc_current_sigrtmin()`/`__libc_current_sigrtmax()` 获取可用范围，或使用 `SIGRTMIN + n`（n 取足够大的固定偏移）。
`sigqueue(pid, sig, value)` 与 `kill` 的差别除了携带数据，还在于 `si_code = SI_QUEUE`（`kill` 为 `SI_USER`）。处理器必须用三参数形式（`SA_SIGINFO`）才能取到数据，即 $data = info\text{->}si\_value.sival\_int$（或 `sival_ptr`）。`sival_ptr` 只是**指针的数值**，跨进程传递时对端无法解引用（地址空间不同），实践中应使用整数编码、共享内存偏移或 fd 传递。
实时信号也是唯一能与内核侧排队语义配合的通知机制：POSIX 定时器（`timer_create`）的 `SIGEV_SIGNAL` 模式在每次超时时投递信号，`siginfo_t` 中带 `si_overrun`（超限计数）与 `si_timerid`，使应用能检测「处理速度跟不上定时频率」。接收侧除异步处理器外，还可用 `sigwaitinfo`/`sigtimedwait` **同步**收取：从 pending 队列取出一个信号并返回 `siginfo_t`，不进入处理器上下文，因而天然规避 async-signal-safe 限制；这与 `signalfd` 互补——后者通过 fd 可加入 `epoll`。

## 三、形式化与数学基础
设某实时信号的队列为 $Q_s$，容量受配额约束：

$$ \left|Q_s\right| \le Q_{limit} - \sum_{s' \in RT} \left|Q_{s'}\right| $$

其中 $Q_{limit}$ 由 `RLIMIT_SIGPENDING`（每个真实用户 ID 的未决信号上限）决定，超出时投递返回 `EAGAIN`。递送顺序是字典序：

$$ (s_1, seq_1) \prec (s_2, seq_2) \iff s_1 < s_2 \;\lor\; \left(s_1 = s_2 \;\land\; seq_1 < seq_2\right) $$

与标准信号对比：

$$ \left|Q_s\right| \in \{0,1\}\;\; (s \in [1,31]), \qquad \left|Q_s\right| \ge 0\;\; (s \in \text{SIGRT}) $$

被阻塞时信号只累积不丢弃：$s \in blocked \Rightarrow Q_s \leftarrow Q_s \cup \{(s, seq)\}$。解除阻塞后队列中的 $n$ 个同号实时信号**全部**按序递送，这才是「可靠」的准确含义；标准信号在任何情况下只递送一次。

## 四、代码实现
```c
#include <signal.h>
#include <string.h>
#include <unistd.h>

/* 发送端：可靠投递并附带数据 */
void send_with_payload(pid_t pid, int payload) {
    union sigval v;
    v.sival_int = payload;
    if (sigqueue(pid, SIGRTMIN + 1, v) == -1) {
        /* EAGAIN: 配额耗尽；EINVAL: 信号号非法；EPERM: 权限不足 */
    }
}

/* 接收端：异步处理器形式，必须使用 SA_SIGINFO */
static void rt_handler(int sig, siginfo_t *info, void *uc) {
    (void)sig; (void)uc;
    char buf[96];
    int n = snprintf(buf, sizeof(buf), "value=%d overrun=%d\n",
                     info->si_value.sival_int, info->si_overrun);
    if (n > 0) { ssize_t w = write(STDOUT_FILENO, buf, (size_t)n); (void)w; }
}

int setup_rt(int signo) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = rt_handler;
    sa.sa_flags = SA_SIGINFO;          /* 必需，否则取不到 si_value */
    sigemptyset(&sa.sa_mask);
    sigaddset(&sa.sa_mask, signo);
    return sigaction(signo, &sa, NULL);
}
```

推荐做法是把重活放到普通上下文，用 `sigwaitinfo` 或 `signalfd` 消费：

```c
#include <errno.h>
void drain_rt(int signo) {
    siginfo_t info;
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, signo);
    for (;;) {
        if (sigwaitinfo(&set, &info) == -1) {
            if (errno == EINTR) continue;      /* 被其他信号打断，重试 */
            break;
        }
        handle(info.si_value.sival_int);       /* 普通上下文：可 malloc、可加锁 */
    }
}

/* POSIX 定时器：可观察超限计数，sival_ptr 在进程内可安全解引用 */
struct sigevent sev;
memset(&sev, 0, sizeof(sev));
sev.sigev_notify = SIGEV_SIGNAL;
sev.sigev_signo = SIGRTMIN + 2;
sev.sigev_value.sival_ptr = &job;
timer_create(CLOCK_MONOTONIC, &sev, &tid);
```

## 五、与其他技术对比
| 维度 | 标准信号 | 实时信号 | `signalfd` | `eventfd` | `pipe` |
| --- | --- | --- | --- | --- | --- |
| 是否排队 | 否（位图，会合并） | 是（链表） | 是（取决于被监听信号） | 是（64 位计数） | 是（内核缓冲区） |
| 携带数据 | 否 | `sigval`（8 字节） | `signalfd_siginfo` 结构 | 8 字节整数 | 任意字节流 |
| 顺序保证 | 无 | 信号号升序 + FIFO | 同实时信号 | 计数语义 | FIFO |
| 递送上下文 | 打断任意指令 | 打断任意指令 | 用户主动 `read` | 用户主动 `read` | 用户主动 `read` |
| 可加入 `epoll` | 否 | 否 | 是 | 是 | 是 |
| 典型用途 | 终止、控制、异常 | 可靠通知 + 参数 | 事件循环统一收信号 | 事件计数 | 数据通道 |

核心权衡是：信号更轻量（无需缓冲区、可定向到线程）但带宽极低（每次最多 8 字节，且要付出内核对象分配与调度开销）；管道/`socketpair` 带宽高但需要额外的 fd 生命周期管理、且无法定向到线程。`eventfd` 只做计数，多次 `write` 会累加，`read` 时无法区分次数，因此不适合「每次事件都要处理」的语义。

## 六、常见误区
- **以为所有信号都排队**：只有 `SIGRTMIN`–`SIGRTMAX` 排队；用 `SIGUSR1` 做事件计数必然丢事件。
- **以为实时信号可以无限排队**：受 `RLIMIT_SIGPENDING` 约束，超额时 `sigqueue` 返回 `EAGAIN`，不检查就会静默丢事件。
- **以为递送顺序是纯 FIFO**：实际是「信号号升序优先，同号内 FIFO」；需要严格时序应只用一个实时信号号。
- **以为 `sival_ptr` 跨进程可用**：它只是一个数值，对端地址空间不同，解引用必然错误。
- **在处理器里做重活**：实时信号可能高频到达，处理器中任何非安全操作都会放大风险；推荐「处理器只置标志或只 `write`，主循环用 `sigwaitinfo`/`signalfd` 消费」。

## 八、面试题
1. **标准信号为什么会丢事件？**
   要点：pending 是位图，多次产生同一信号只保留一次；要计数或严格送达必须用实时信号、自管道或 `eventfd`。
2. **实时信号如何携带数据？跨进程传指针可行吗？**
   要点：`sigqueue` 传 `union sigval`，处理器通过 `si_value` 读取，`si_code == SI_QUEUE`；指针仅为数值，跨进程不可解引用，需整数编码、共享内存偏移或 `SCM_RIGHTS`。
3. **`RLIMIT_SIGPENDING` 会带来什么后果？**
   要点：每个真实 UID 的未决信号总量受限，超额时 `sigqueue` 返回 `EAGAIN`；不检查会静默丢事件，也可能影响同 UID 下其他进程的信号投递能力。
4. **`SIGRTMIN` 可以直接用吗？**
   要点：glibc 保留了其后若干编号给 pthread 内部，应用应使用 `__libc_current_sigrtmin()` 计算的起点或 `SIGRTMIN + n`（n 足够大）。
5. **`sigwaitinfo` 与信号处理器如何取舍？**
   要点：`sigwaitinfo` 在普通上下文运行，无 async-signal-safe 限制、可分配内存与加锁，适合事件循环；处理器适合需要立即打断当前执行的场景。同一信号不宜混用两种方式。

## 九、演进与趋势
实时信号的两个限制——递送必须打断指令、每次仅 8 字节——使接收侧逐渐被事件化接口取代：`signalfd` 把排队信号变成可 `read` 的结构化数据并可加入 `epoll`，`eventfd`/`timerfd` 提供无处理器的事件与定时能力，`pidfd` 与 `io_uring` 进一步从上层消除「信号 + 回调」模式。当前主流组合是发送侧仍用实时信号（可定向到线程、开销低），接收侧统一用 `signalfd` 或 `sigwaitinfo` 消费；极高频通知则下沉到共享内存环形队列加 `eventfd` 唤醒。

## 十、小结
实时信号用「排队 + 优先级 + 附带 `sigval`」补齐标准信号的三个缺陷：$|Q_s| \ge 0$ 取代 $|Q_s| \in \{0,1\}$，字典型序取代无序合并，`si_value` 取代单一信号号。代价是配额约束（超额返回 `EAGAIN`）、仍需 async-signal-safe 的处理器上下文、以及 `sival_ptr` 跨进程不可解的陷阱。最佳实践是：实时信号做可靠投递与线程定向，`sigwaitinfo`/`signalfd` 在普通上下文或事件循环中消费，把异步处理器压缩到最小。
