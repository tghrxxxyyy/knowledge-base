# 同步信号与致命信号

> 对应 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 8 章异常与信号的映射，以及 Kerrisk《The Linux Programming Interface》第 20 章默认动作与 `siginfo_t`。

## 一、背景与挑战
「信号是异步的」只是近似说法。`SIGSEGV`、`SIGFPE`、`SIGILL`、`SIGBUS`、`SIGTRAP`、`SIGSYS` 都由**进程自身的某条指令**同步触发：访问非法地址、除以零、执行非法操作码、访问未对齐或不可用的内存对象、命中断点、被 seccomp 拦截的系统调用。它们与引发异常的指令严格对应，递送给触发异常的那个线程。
另一类是**致命信号**：`SIGKILL` 与 `SIGSTOP` 不可捕获、不可忽略、不可阻塞，是内核保留的最终控制手段。理解这两类的差别，决定崩溃现场能否被正确诊断，也决定「捕获后重试」的思路在何种情况下必然失败。

## 二、核心原理
同步信号由 CPU 异常经内核路径转换而来：`#PF` → `SIGSEGV` 或 `SIGBUS`，`#DE`/`#MF` → `SIGFPE`，`#UD`/特权指令 → `SIGILL`，`#BP`/`#DB` → `SIGTRAP`，seccomp 拦截 → `SIGSYS`。内核用 `force_sig_fault` 构造 `siginfo_t`：`si_signo`（信号号）、`si_code`（细化原因，如 `SEGV_MAPERR` 表示地址无映射、`SEGV_ACCERR` 表示映射存在但权限不符、`SEGV_PKUERR` 表示保护键违例）、`si_addr`（出错虚拟地址，`FPE`/`ILL` 类通常是引发异常的指令地址）；`si_code > 0` 表示内核产生，`< 0` 表示来自用户（`SI_USER`/`SI_QUEUE`）。
`SIGFPE` 细分 `FPE_INTDIV`/`FPE_INTOVF`/`FPE_FLTDIV`/`FPE_FLTOVF`/`FPE_FLTUND`/`FPE_FLTINV`/`FPE_FLTRES`/`FPE_FLTSUB`；`SIGILL` 细分 `ILL_ILLOPC`/`ILL_PRVOPC`/`ILL_ILLADR`/`ILL_BADSTK`；`SIGBUS` 细分 `BUS_ADRALN`（对齐错误）、`BUS_ADRERR`（物理地址不存在，如 `mmap` 越出文件末尾）、`BUS_OBJERR`。
默认动作分 `Term`/`Core`/`Stop`/`Ign`/`Cont`。`SIGSEGV`、`SIGBUS`、`SIGFPE`、`SIGILL`、`SIGABRT`、`SIGQUIT`、`SIGTRAP`、`SIGSYS` 默认为 `Core`，既终止又留下可回溯的内存镜像。core 受 `RLIMIT_CORE`（`ulimit -c`）限制，并可用 `/proc/sys/kernel/core_pattern` 重定向到管道（如 `|/usr/lib/systemd/systemd-coredump`）交给用户态收集器。
实现层面必须记住：**处理器若正常返回，内核会重新执行引发异常的那条指令**。若处理器未修复故障（补映射、改权限），同一指令再次异常，形成「信号—返回—再异常」循环——这正是「捕获 `SIGSEGV` 后什么都不做直接返回」表现为挂死或反复进入处理器的原因。

## 三、形式化与数学基础
同步信号的投递目标确定，就是产生异常的线程：

$$ target(s_{sync}) = current\_thread,\qquad siginfo.si\_addr = fault\_va $$

异步进程级信号则可投给任一未阻塞它的线程：

$$ target(s_{async}) \in \left\{t \;\middle|\; s \notin blocked(t)\right\} $$

默认动作取值域为 $A(s) \in \{Term, Core, Stop, Ign, Cont\}$，其中 $A(s) = Core$ 对 $s \in \{SIGSEGV, SIGBUS, SIGFPE, SIGILL, SIGTRAP, SIGABRT, SIGSYS\}$ 成立，而 $A(SIGKILL)$、$A(SIGSTOP)$ 不可覆盖。
「处理器返回后重试」可写成：设故障指令地址为 $\alpha$、映射函数为 $\mu$，若处理器返回时 $\mu' = \mu$，则必然再次异常：

$$ \mu' = \mu \Rightarrow \text{重新执行 } \alpha \Rightarrow \text{再次触发同类异常} $$

只有 $\mu' \ne \mu$（映射被修复）或处理器不返回（`_exit`、`siglongjmp`）时循环才被打破。core 的可获取性为 $core\ generated \iff RLIMIT\_CORE > 0 \land A(s) = Core$。

## 四、代码实现
```c
#include <signal.h>
#include <string.h>
#include <unistd.h>

static void on_segv(int sig, siginfo_t *si, void *uc) {
    (void)sig; (void)uc;
    /* 严格的异步信号安全只允许 write 常量串；此处用 snprintf 仅为可读性 */
    char buf[160];
    int n = snprintf(buf, sizeof(buf), "SIGSEGV at %p code=%d\n",
                     si->si_addr, si->si_code);
    if (n > 0) { ssize_t w = write(STDERR_FILENO, buf, (size_t)n); (void)w; }
    _exit(128 + SIGSEGV);        /* 必须直接退出：返回会导致故障指令重试 */
}

int main(void) {
    struct sigaction sa;
    memset(&sa, 0, sizeof(sa));
    sa.sa_sigaction = on_segv;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK;   /* 配合 sigaltstack 应对栈溢出 */
    sigemptyset(&sa.sa_mask);
    sigaction(SIGSEGV, &sa, NULL);
    sigaction(SIGBUS,  &sa, NULL);

    volatile int *p = (int *)0x1;
    *p = 42;                     /* si_addr ≈ 0x1，si_code = SEGV_MAPERR */
    return 0;
}
```

栈溢出场景必须注册备用信号栈，否则处理器压栈即再次故障：

```c
static char altstack[SIGSTKSZ];
stack_t ss;
memset(&ss, 0, sizeof(ss));
ss.ss_sp = altstack;
ss.ss_size = sizeof(altstack);
ss.ss_flags = 0;
sigaltstack(&ss, NULL);          /* 之后带 SA_ONSTACK 的处理器运行在此栈上 */
/* si_code == FPE_INTDIV 表示整数除零，这类故障无法“修复”，应尽快退出；
 * 访问 mmap 映射中跨越文件末尾的页得到 SIGBUS，且 si_code = BUS_ADRERR */
```

## 五、与其他技术对比
| 维度 | 同步信号 | 异步信号 | 致命信号 | C++ 异常 | Go panic |
| --- | --- | --- | --- | --- | --- |
| 触发来源 | 当前线程的指令 | 外部 `kill` 或内核事件 | 外部或内核 | 显式 `throw` | 显式 `panic` |
| 投递目标 | 触发线程，唯一 | 任一未阻塞线程 | 任意目标进程 | 当前线程 | 当前 goroutine |
| 能否屏蔽 | 技术可屏蔽但危险 | 可以 | `SIGKILL`/`SIGSTOP` 不可 | 不适用 | 不适用 |
| 能否忽略 | 可注册但重试语义受限 | 可以 | 不可 | 可被 catch 吞掉 | 可被 recover 吞掉 |
| 携带诊断信息 | `si_addr` + 精确 `si_code` | 多为 `SI_USER` | 无 | 栈回溯 | 栈回溯 |
| 可恢复性 | 需修复映射，通常无解 | 可自由恢复 | 不可恢复 | 可恢复 | 可恢复 |

与普通 IPC 相比，同步信号的独特价值是**携带精确故障地址与原因码**且不依赖任何通信设施——本质上是「内核把硬件异常的事实告知进程」。与 try/catch 相比，信号没有栈展开，处理器运行在故障现场之上，几乎无法安全地继续执行。

## 六、常见误区
- **以为 `SIGSEGV` 处理器返回就能继续运行**：内核会重试故障指令，形成无限循环；必须修复映射、`_exit` 或 `siglongjmp`。
- **以为捕获即可忽略**：部分故障（硬件校验错误、`SEGV_PKUERR` 保护键违例、栈破坏）根本无法恢复，忽略只会掩盖真实错误。
- **以为 core 一定会生成**：受 `RLIMIT_CORE`、`core_pattern`（可指向管道或 `/dev/null`）、容器限制共同约束，容器中常被显式关闭。
- **以为 `SIGBUS` 与 `SIGSEGV` 可互换理解**：`SIGBUS` 常意味着「地址合法但对象不可用」（映射越界、对齐错误、介质错误），修复思路完全不同。
- **忘记 `SA_ONSTACK` + `sigaltstack`**：栈溢出导致的 `SIGSEGV` 在默认栈上无法运行处理器，表现为无声终止或反复异常。

## 八、面试题
1. **为什么 `SIGSEGV` 被称为同步信号？**
   要点：由当前线程执行某条指令（访问非法地址）同步产生，与指令一一对应，且只递送给该线程；`SIGINT`、`SIGTERM` 等来自外部，属异步。
2. **core 文件如何产生，可能被哪些因素抑制？**
   要点：默认动作为 `Core` 的信号触发内核转储；受 `RLIMIT_CORE`、`core_pattern`、磁盘空间与容器安全策略影响，可重定向到管道。
3. **捕获 `SIGSEGV` 后为什么不能简单返回？**
   要点：内核恢复上下文后重新执行故障指令，映射未修复则再次异常；必须修复地址空间、`_exit` 或 `siglongjmp`。
4. **`si_code` 与 `si_addr` 在崩溃诊断中怎么用？**
   要点：`si_code > 0` 表示内核产生，`SEGV_MAPERR`/`SEGV_ACCERR`/`BUS_ADRERR` 给出原因类别；`si_addr` 与 `/proc/<pid>/maps` 对照可判断是野指针、越界还是权限问题。
5. **为什么要给 `SIGSEGV` 处理器注册备用信号栈？**
   要点：栈溢出时默认栈已不可用，压栈会再次故障；`sigaltstack` + `SA_ONSTACK` 让处理器在独立栈上运行，才能记录有效现场。

## 九、演进与趋势
内核与工具链持续丰富同步信号的信息量：`siginfo_t` 增加 `SEGV_PKUERR`（Intel 保护键）、`SIGSYS` 携带触发的系统调用号与 seccomp 动作，使沙箱违规可精确归因。core 机制走向「管道化 + 集中收集」，`systemd-coredump`/`coredumpctl` 把崩溃现场转为结构化数据。语言运行时（如 Go）自行捕获同步信号并打印栈，`SA_ONSTACK` 成为标准配置。只要硬件异常存在，同步信号就是内核向用户暴露故障事实的唯一通用通道。

## 十、小结
同步信号把 CPU 异常暴露为进程级通知，携带 `si_addr` 与精确 `si_code`，只投递给故障线程，且处理器返回会导致故障指令重试，因此几乎不存在「安全恢复」路径。致命信号（`SIGKILL`/`SIGSTOP`）由内核保留，不可捕获与阻塞。工程上的正确做法是：为同步信号注册 `SA_SIGINFO | SA_ONSTACK` 处理器并配 `sigaltstack`，收集最小诊断信息后立即终止，同时保证 core 转储链路可用。
