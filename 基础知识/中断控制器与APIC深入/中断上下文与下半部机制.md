# 中断上下文与下半部机制

> 对应 Linux 内核 Documentation 与 Silberschatz《Operating System Concepts》。

## 一、背景与挑战
中断处理若做太多工作会抬高延迟、丢失后续中断。内核把处理分为上半部（硬件相关、尽快完成、不可睡眠）与下半部（推迟的、可较长运行的工作）。

## 二、核心原理
上半部在关中断或最低必要中断屏蔽下跑，做应答与数据搬运。下半部机制包括 softirq（静态、每 CPU、不可睡眠，用于网络与块设备）、tasklet（基于 softirq、串行化同一 tasklet）、工作队列（运行在进程上下文、可睡眠）。选择取决于是否需睡眠与并发要求。

## 三、形式化与数学基础
用两阶段延迟建模：

$$ L_{total} = L_{top} + L_{bottom} $$

上半部应满足硬实时期望：

$$ L_{top} \ll T_{irq\_gap} $$

其中 $T_{irq\_gap}$ 为可容忍的中断间隔。下半部若在进程上下文，则受调度延迟支配。

## 四、代码实现
tasklet 与工作队列示例：

```c
void my_bh(unsigned long data) { /* 不可睡眠 */ }

DECLARE_TASKLET(my_tasklet, my_bh, 0);

// 上半部中调度
tasklet_schedule(&my_tasklet);

// 或需睡眠时
static void wq_func(struct work_struct *w) { /* 可睡眠 */ }
static DECLARE_WORK(my_wq, wq_func);
schedule_work(&my_wq);
```

## 五、与其他技术对比
softirq 并发度高但编写难；tasklet 自动串行化更易用；工作队列可睡眠但开销大、延迟高。Windows 的 DPC 与 Linux 的 softirq 概念类似，但 API 不同。

## 六、常见误区
认为中断上下文可以调用可能睡眠的函数（如 mutex、kmalloc(GFP_KERNEL)），实际会死锁或出错；认为 tasklet 可并行于同类型 tasklet，实际它串行化；混淆 softirq 与线程化 IRQ。

## 七、与开源书/权威来源对应
Linux 内核 Documentation/interrupts.rst 与 softirq.rst 为权威；Silberschatz《Operating System Concepts》讨论中断与调度；Corbet《Linux Device Drivers》有经典章节。

## 八、面试题
上半部与下半部划分原则；为何中断上下文不能睡眠；softirq/tasklet/workqueue 取舍；线程化 IRQ 的好处。

## 九、演进与趋势
线程化中断（request_threaded_irq）让更多处理跑在可抢占线程；中断亲和与 NAPI 降低高吞吐网络的中断开销。

## 十、小结
把中断处理拆分为不可睡眠的上半部与可延后的下半部，是平衡中断延迟与系统吞吐的关键设计，多种下半部机制按是否可睡眠与并发需求取舍。
