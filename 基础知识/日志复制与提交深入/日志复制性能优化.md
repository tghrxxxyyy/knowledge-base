# 日志复制性能优化

> 对应 Ongaro & Ousterhout 2014（Raft）与 DDIA 第9章性能讨论。

## 一、背景与挑战
每条命令走「Leader 写盘加多数派网络加 fsync 加 apply」路径，延迟与吞吐受限于最慢环节。工程上需在不破坏安全前提下压榨性能。

## 二、核心原理
优化手段：① 批处理（一次 RPC 带多条日志）；② 流水线（不等前条提交即发下条）；③ 异步或并行磁盘 fsync 与网络；④ 组提交（group commit）摊薄 fsync；⑤ 只读走 ReadIndex 或租约读绕开复制。

## 三、形式化与数学基础
吞吐 \\(T \approx \frac{batch}{RTT + fsync}\\)。流水线把串行 \\(n\times RTT\\) 降为 \\(RTT + (n-1)\times proc\\)；组提交使每次 fsync 摊销到 B 条，有效 fsync 延迟降为 \\(fsync/B\\)。

## 四、代码实现
```python
# 组提交：攒一批再 fsync
def group_commit(buffer, threshold, timeout):
    if len(buffer) >= threshold or elapsed() > timeout:
        fsync(buffer)              # 一次刷盘
        replicate_async(buffer)     # 流水线发出
        buffer.clear()
```

## 五、与其他技术对比
无批处理或流水线的 Raft 延迟高；Zab 的类似优化；EPaxos 通过去 Leader 提升并行度但实现复杂。优化须在「持久性或一致性」边界内。

## 六、常见误区
1. 为性能关 fsync：崩溃可能丢已确认日志，违反持久性。
2. 流水线但乱序提交：须按 index 顺序推进 commit。
3. 只读也走共识：应用租约读降低延迟。

## 七、与开源书/权威来源对应
Raft 论文讨论批处理与流水线；etcd 或 TiKV 工程实践大量优化；6.824 测吞吐。

## 八、面试题
问：组提交如何提升吞吐？
答：把多次 fsync 合并为一次，使每条日志摊薄的刷盘成本降为 fsync/B。

## 九、演进与趋势
RDMA 或用户态网络降低 RTT；WAL 与 RocksDB 深度整合减少拷贝。

## 十、小结
日志复制性能靠批处理、流水线、组提交与租约读，在保安全前提下逼近物理极限。
