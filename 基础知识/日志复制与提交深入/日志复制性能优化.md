# 日志复制性能优化

> 对应 Ongaro & Ousterhout 2014（Raft）与 Kleppmann《Designing Data-Intensive Applications》第 9 章性能讨论。

## 一、背景与挑战

每条命令的写路径是「Leader 本地落盘 + 多数派网络往返 + fsync + apply 状态机」，延迟受最慢环节（磁盘 fsync、网络 RTT）钳制，吞吐受单线程串行复制限制。在 etcd/TiKV 这类系统中，一次写常需亚毫秒到数毫秒，而 fsync 本身就可能占数百微秒。工程上必须在不破坏持久性与一致性的前提下压榨性能：批处理、流水线、组提交、异步刷盘、租约读等都是围绕「摊薄 fsync」「隐藏 RTT」「减少不必要共识」三条主线展开。

需要认清「哪些开销是固定成本、哪些是可摊薄的边际成本」。RPC 建立、fsync 提交、线程唤醒属于固定成本，与批大小无关，因此最容易通过批量化摊薄；而字节拷贝、CRC 校验、序列化属于边际成本，只能通过减少数据量或使用零拷贝来降低。优化的第一原则是先测出瓶颈归属（用延迟分解而非猜测），再对症下药——把时间花在非瓶颈环节的优化上，收益恒为零。

## 二、核心原理

主要优化手段：① 批处理（一次 AppendEntries 携带多条日志，摊薄 RPC 与 fsync 固定开销）；② 流水线（不等前条被确认即发出后续，使网络与磁盘并行）；③ 组提交（group commit）把多个写攒一批后单次 fsync；④ 异步/并行磁盘与网络，把 fsync 从关键路径移出；⑤ 只读走 ReadIndex 或租约读，绕开整个复制路径。注意流水线仍须按 index 顺序推进 `commitIndex`，不得乱序提交——性能优化的边界永远是「崩溃后已提交项仍完整可 apply」。

几条机制细节值得展开。流水线的正确做法是维护「在途窗口」：Leader 记录已发送未确认的最大 index，收到确认后推进可发送边界，遇到失败则回退重发。批处理的触发策略通常是「大小阈值 + 超时阈值」双条件——纯等阈值会在低负载时无限等待，纯等超时会在高负载时批太小，二者结合才能同时兼顾吞吐与尾延迟。租约读的本质是把「每次都问多数派」替换为「Leader 在租约期内自认为合法主」，其安全性依赖时钟漂移上界 $\epsilon$ 与租约时长 $L$ 满足 $L > \epsilon$ 之类的约束，因此对 NTP 质量与容器时钟隔离有硬要求。

## 三、形式化与数学基础

吞吐近似：

$$T \approx \frac{batch}{RTT + fsync_{eff}},\quad fsync_{eff} = \frac{fsync}{B}$$

其中 $B$ 为组提交每批条数。流水线把串行 $n \times RTT$ 降为 $RTT + (n-1)\times proc$，使网络等待被计算覆盖。设单条延迟 $L = RTT + fsync$，批大小 $b$ 与组大小 $B$ 共同把每条有效成本压到 $L/(b\cdot B)$ 量级（理想下）。但尾延迟随 batch/timeout 增大而上升，需权衡。

更精细的模型要区分吞吐与尾延迟两个目标。设触发超时为 $t$、到达率为 $\lambda$，则期望批大小 $b \approx \max(b_{min}, \lambda t)$，尾延迟增加量约为 $t$（最坏情况等待满超时）。因此存在「吞吐—尾延迟」的帕累托前沿，工程上常用分位数目标（如 P99）来选取工作点，而非单纯最大化吞吐。流水线带来的并行度也不是无限的：在途窗口受「崩溃后需重放的数据量」与内存占用约束，窗口过大时恢复时间线性增长，形成「稳态吞吐」与「恢复时间」的又一组权衡。

## 四、代码实现

```python
def group_commit(buffer, threshold, timeout):
    # 攒一批再统一 fsync，把随机写合并为顺序段
    if len(buffer) >= threshold or elapsed() > timeout:
        fsync(buffer)                 # 一次刷盘，摊薄到整批
        replicate_async(buffer)        # 流水线并发发给 Follower
        buffer.clear()

def pipeline_send(entries, next_index, window):
    # 不等 ack，连续发送多个 batch，但在途量受 window 限制
    for batch in chunk(entries, BATCH):
        while inflight() >= window:    # 背压：防止缓冲无限膨胀
            wait_for_ack()
        send_append(next_index, batch)
        next_index += len(batch)

def on_ack(match_index, follower_id):
    # 严格按 index 单调推进，绝不因收到更大 index 而跳过中间空洞
    match_idx[follower_id] = max(match_idx[follower_id], match_index)
    advance_commit_index_match_majority()   # 只在多数派连续覆盖时推进

# 异步刷盘：fsync 不阻塞主写线程，由后台线程完成
def async_fsync(log_segment, ack_callback):
    def worker():
        os.fsync(log_segment.fd)      # 真正落盘
        ack_callback()                # 落盘完成后才允许回 ACK 给客户端
    spawn(worker)

# 只读快路径：ReadIndex，不写日志也不复制
def linearizable_read(leader):
    idx = leader.commit_index
    if not has_quorum_heartbeat_ack(leader, idx):  # 确认自己仍是主
        return None
    while leader.applied_index < idx:
        wait()                        # 等本地状态机追平读点
    return leader.state_machine.read()
```

其中 `advance_commit_index_match_majority` 是性能与安全的交汇点：只有当多数派的 `matchIndex` **连续**覆盖到某个 index 时，才能推进提交点。若允许「按最大 index 跳跃推进」，就会把中间尚未复制的空洞误标为已提交，崩溃恢复后状态机将缺少条目。

## 五、与其他技术对比

| 优化 | 收益 | 风险 | 适用负载 | 对尾延迟影响 |
| --- | --- | --- | --- | --- |
| 批处理 | 降 RPC 与 fsync 次数 | 增加尾延迟 | 高吞吐写 | 中等上升 |
| 流水线 | 隐藏 RTT | 需保序提交、占更多缓冲 | 长 RTT 广域 | 略降 |
| 组提交 | 摊薄 fsync | 缓冲内已确认写需 WAL 兜底 | 小写高并发 | 中等上升 |
| 异步 fsync | 移出关键路径 | 回 ACK 时机必须严谨 | 写密集 | 下降 |
| 租约读 | 读免共识 | 依赖时钟，漂移致双主 | 读多写少 | 显著下降 |
| ReadIndex | 免写日志的线性读 | 需一次心跳确认主身份 | 读多写少 | 略降 |

无批/流水线的朴素 Raft 延迟高；Zab 采用类似优化；EPaxos 去 Leader 提升并行度但实现复杂。所有优化须在「持久性/一致性」边界内，不能为了快而牺牲已提交不丢。

## 六、常见误区

1. 为性能关 fsync：崩溃可能丢已确认日志，违反持久性；正确做法是组提交而非关闭持久化。
2. 流水线但乱序提交：必须按 index 单调推进 `commitIndex`，否则状态机 apply 顺序错乱。
3. 只读也走共识：应用租约读/ReadIndex 降低延迟，盲目共识浪费吞吐。
4. 批次越大越好：过大批次抬升尾延迟并增大缓冲占用，需配合超时触发。
5. 异步 fsync 即安全：若未等 fsync 完成就向客户端回 ACK，崩溃会丢已确认写，须 WAL 先落盘再应答。
6. 用 `os.fsync` 的返回当作已持久化：部分文件系统与存储设备存在缓存，必要时需正确的写屏障/目录 fsync，否则元数据可能未落盘；流水线窗口也须设上限并做背压，否则慢 Follower 会让 Leader 缓冲无界增长。

## 八、面试题

1. 问：组提交如何提升吞吐？
   答：把多次 fsync 合并为一次顺序写，使每条日志摊薄的刷盘成本降为 $fsync/B$，磁盘寻道/刷新次数大幅下降。
2. 问：流水线为何不能乱序提交？
   答：状态机必须按日志 index 顺序 apply；乱序提交会跳过未确认前缀，导致已 apply 状态依赖尚未达成多数派的条目。
3. 问：租约读的前提与风险？
   答：前提是时钟漂移可控、租约内无新 Leader；风险是时钟回拨/漂移造成双主，读到过期数据。
4. 问：异步 fsync 与客户端 ACK 的顺序？
   答：必须先 WAL 落盘（fsync 完成）再向客户端回 ACK，否则崩溃丢已确认写；异步只用于「已确认后的后续处理」。
5. 问：批处理的触发条件为什么需要超时？
   答：只有大小阈值时，低负载下永远凑不满一批，写会被无限延迟；超时保证低负载也能及时提交。流水线窗口同理须设上限——窗口即「崩溃后需重放的未确认数据量」，无上限会让内存与恢复时间失控，故需背压。

## 九、演进与趋势

RDMA 与用户态网络（DPDK/io_uring）降低 RTT 与 syscall 开销；WAL 与 RocksDB 深度整合减少内存拷贝；可移植的「复制组」抽象（如 TiKV 的 multi-raft）把优化下沉到存储层。更新的方向还包括 NVM 持久内存把 fsync 从毫秒级降到微秒级，以及并行提交 / 无序共识（如 EPaxos 类）在冲突稀疏负载上绕开单主瓶颈。

但更大的风险是引入了额外的抽象层与故障域，因此该路线更适合已有成熟共识库的中大型团队。具体实现以各项目官方最新文档为准。

## 十、小结

日志复制性能靠批处理、流水线、组提交与租约读，在不破坏安全不变式的前提下逼近物理极限。所有优化的检验标准只有一个：崩溃恢复后，已提交项依然完整、顺序一致、可被 apply——快必须以「不丢、不乱」为边界。性能工程的全部智慧，都在于在这个边界内把硬件带宽吃满。实践顺序宜为：先做端到端延迟分解定位瓶颈，再用组提交与批处理摊薄固定成本，然后加流水线隐藏 RTT，最后才考虑租约读等一致性弱化手段；每一步都要用崩溃恢复测试验证边界未被突破。
