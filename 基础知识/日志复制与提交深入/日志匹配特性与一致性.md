# 日志匹配特性与一致性

> 对应 Ongaro & Ousterhout 2014（Raft）与 Lamport 1998（Paxos 安全性）。

## 一、背景与挑战

多副本日志会因 Leader 切换、网络分区而分歧。设想副本 A 提交了 index 5，但新 Leader B 的日志在 index 5 是另一条命令——若直接让 B 覆盖 A，则 A 已 apply 的状态被悄悄抹掉，破坏持久性。日志匹配特性（Log Matching Property）与 Leader 完整性（Leader Completeness）是保证「已提交项永远不丢、且不冲突」的数学基石，也是 Raft 安全性证明的两个核心引理。缺少它们，复制系统会在故障恢复时产生不可解释的状态回滚。

挑战的难点在于这是「并发 + 非确定性」环境下的全局性质：每个副本只看到局部信息，网络可丢包重排，节点可随时崩溃重启，而需要保证的却是跨越全部历史与全部副本的强不变量。因此不能依赖运行时观察来判安全，只能构造一组局部可检验的规则（prev 检查、选举限制），再用归纳法把局部规则升华成全局定理。

## 二、核心原理

两条引理共同支撑安全性：① 日志匹配——若两日志在 index $i$ 的 term 相同，则它们 $1..i$ 的前缀完全一致（由 AppendEntries 的 prev 检查归纳得到）；② Leader 完整性——任何在 term $T$ 被选出的 Leader，其日志必包含所有已在 term $< T$ 提交的条目。二者结合推出：一旦某项被提交，任何未来 Leader 的日志都含该项，因此后续覆盖只会追加、不会抹除已提交项。直观地说，term 是「谁拥有权威」的单调递增凭证，completeness 保证权威副本必含全部已确认历史。

两条引理的证明结构值得记住。日志匹配用对 index 的归纳：基础情形（$i=1$）由 term 首次出现的唯一性给出；归纳步依赖 AppendEntries 的一致性检查——Leader 只有在 Follower 的 `prevLogIndex/prevLogTerm` 与自己匹配时才允许追加，这保证了新追加项的前缀必然已一致，因此「term 相同 ⇒ 前缀相同」可沿 index 逐项传递。Leader 完整性的证明是反证：假设存在 term $T$ 的 Leader 缺少某已提交项 $e$，考虑提交 $e$ 的多数派 $Q$ 与选出该 Leader 的多数派 $Q'$，二者必有交集节点 $v$；$v$ 既已持久化 $e$（不投落后候选），又投给了该 Leader，由选举限制该 Leader 日志必不落后于 $v$，矛盾。

## 三、形式化与数学基础

日志匹配可写为：若 $L_p[i].term = L_q[i].term$，则 $\forall j\le i,\ L_p[j] = L_q[j]$。Leader 完整性形式化如下，设 $e$ 为任一已提交项：

$$\forall\ candidate\ c\ elected\ at\ term\ T,\quad e \in c.log$$

选举限制（候选人日志不落后于任一投票者）是它成立的前提：投票者只把票投给 `lastTerm` 更高、或同 term 时 `lastIndex` 不更短的候选。由此可证 Raft 满足「持久性」：已 apply 的状态永不被回滚。严格证明用反证：假设存在最早被覆盖的已提交项，则由 completeness 新 Leader 必含它，由日志匹配覆盖会保持一致，矛盾。

选举可用「日志新旧全序」表述：定义 $(lastTerm, lastIndex)$ 的字典序 $\preceq$，投票规则即为「只投给 $\succeq$ 自身日志的候选」。该序是全序且良基的，因而每次选举后 Leader 的日志在全体节点中取到「当前已知最大值」。再叠加 Quorum 交叠（任意两个多数派必相交），就得到「最大值必然包含全部已提交项」这一结论。这三步——全序、交叠、选举限制——构成了 Raft 安全性的完整骨架，缺任一步论证即断。

## 四、代码实现

```python
def last_term_index(log):
    # 返回日志最后一项的 (term, index)，空日志返回 (0, 0)
    return (log[-1].term, len(log)) if log else (0, 0)

def election_eligible(cand_log, voter_log):
    # 选举限制：候选人日志必须「不落后」于投票者
    c_term, c_idx = last_term_index(cand_log)
    v_term, v_idx = last_term_index(voter_log)
    if c_term != v_term:
        return c_term > v_term          # term 高者胜
    return c_idx >= v_idx                # 同 term 比长度

def log_match(L, R, i):
    return L[i].term == R[i].term        # 锚点 term 相同即前缀一致

def append_consistent(log, prev_idx, prev_term, entries):
    # AppendEntries 的 prev 检查：只在锚点匹配时才追加
    if prev_idx > len(log):
        return False                     # 锚点在本地不存在，Follower 需回退
    if prev_idx > 0 and log[prev_idx].term != prev_term:
        return False                     # term 不符，拒绝并指示回退
    log[prev_idx + 1:] = entries         # 前缀已一致，安全覆盖后缀
    return True

# 安全检查：提交前确认该 index 项已被当前 term 覆盖且多数派持有
def safe_to_commit(log, index, match_indexes, peers, current_term):
    if log[index].term != current_term:
        return False                     # 旧 term 项不可直接提交
    return count_ge(match_indexes, index) > len(peers) // 2
```

`append_consistent` 的关键在于：检查通过后执行的是一次「覆盖」而非「追加」。正因为锚点已确认一致，覆盖只可能触及不匹配的后缀，前缀（含全部已提交项）在结构上不可能被改变——这就是日志匹配引理在代码里的直接体现。

## 五、与其他技术对比

| 维度 | Raft | Paxos | Zab | VR |
| --- | --- | --- | --- | --- |
| 安全保证 | 日志匹配 + 选举限制 | chosen 值不可变 | 前缀一致 + 有序广播 | view 同步 + 全序 |
| 表述方式 | 落到日志/任期，可归纳 | 抽象「多数派已接受」 | epoch（zxid）单调 | view number 单调 |
| 锚点定位 | prevLogIndex/Term | 实例号 + 提案号 | zxid 前缀 | view + op number |
| 可验证性 | 易做 Coq/TLA+ 形式化 | 同样安全但论证更绕 | 有形式化工作 | 有形式化工作 |
| 教学友好度 | 高 | 中 | 中 | 中 |

二者安全性等价：Raft 的 Leader 完整性等价于 Paxos「一旦 chosen 即不变」，只是把抽象约束具体化到选举与日志前缀上，便于工程与教学。Paxos 的优雅在于极简，Raft 的优雅在于可验证。Zab 与 VR 则通过「单调递增的逻辑序号 + 新 Leader 同步阶段」达到同样效果，代价是引入了与 Raft 不同的故障恢复流程。

## 六、常见误区

1. 任期高就能当选：还需日志至少不落后于投票者，否则可能丢已提交项（违背 completeness）。
2. 冲突项保留不动：Raft 强制 Follower 覆盖以达一致，保留即发散。
3. 提交后还能被截断：安全性保证已提交项永不被覆盖，截断只针对未提交后缀。
4. 日志匹配适用于任意两日志：它只在「存在共同 index 且 term 相同」的锚点处成立，仍需 prev 检查定位该锚点。
5. 认为两个不同 term 的 index 可共存：同一 index 在不同日志可有不同 term，匹配性质靠 term 而非 index 判定一致。
6. 把「多数派持有」当成「已提交」：多数派复制只是必要非充分条件，还须该条属于当前 term，否则存在被覆盖的可能。
7. 认为选举限制是「优化」：它是安全性前提，去掉后仍能选出 Leader，但会选出落后副本并丢数据。
8. 混淆持久性与一致性：持久性说「已确认的不丢」，一致性说「所有读看到同一顺序」，二者由不同机制保证，不可互相推导。

## 八、面试题

1. 问：日志匹配如何保证不丢已提交项？
   答：Leader 完整性确保新 Leader 含所有已提交项，日志匹配确保这些项不会被后续覆盖；二者构成「已提交 = 永久安全」的闭环。
2. 问：为何选举要比较日志长度而非只看 term？
   答：term 只反映最新活动，长度反映已复制进度；同 term 下更长的日志更可能含已提交项，避免选出落后的 Leader。
3. 问：能否用日志匹配证明 Exactly-Once？
   答：不能。日志匹配只保证顺序一致，幂等/去重需状态机层用 clientId+seq 实现，否则重试会重复 apply。
4. 问：日志匹配为什么依赖 prevLogTerm 而非 prevLogIndex？
   答：index 可重复出现在不同 term，term 才是该项「归属任期」的唯一标识，靠 term 比对才能判定前缀真的相同。
5. 问：Leader 完整性的证明关键在哪一步？
   答：在 Quorum 交叠——提交多数派与选举多数派必有交集节点，该节点的不投票落后行为把「已提交」与「新 Leader 含此项」刚性绑定。
6. 问：Follower 收到不一致的 AppendEntries 应如何响应？
   答：返回失败并附带冲突信息（期望的前一项 term/index），Leader 据此回退 `nextIndex` 重试，而非 Follower 自行截断。

## 九、演进与趋势

将日志匹配性质做机器辅助证明成为热点：如「Verdi」「Raft Refloated」用 Coq 校验 Raft 安全不变量；工业界把日志匹配推广到可证明安全的复制库（如用 TLA+ 建模 etcd 的 Raft 并跑模型检查）。形式化方法正从「论文证明」走向「出厂即验证」。

另一条演进线是「按需一致性」：在跨地域复制中，弱化全序以降低延迟（如 EPaxos 利用交换律并发提交无冲突命令），但所有变体都必须保留「已提交不可变」这一最小内核。换言之，可以放松顺序，不能放松不变量。具体实现细节以各项目官方最新文档与论文为准。

## 十、小结

日志匹配与 Leader 完整性是 Raft 安全的两根支柱。前者保证前缀可被确定性对齐，后者保证已提交项随任何新 Leader 一起存活。理解这两点，就理解了为什么 Raft 在混乱的故障场景下仍能守住「已提交即永久」这一不变式——这不是工程技巧，而是被归纳法证明的数学结论。

一句话总结其分工：日志匹配解决「如何判定两个副本在何处开始分歧」（定位问题），Leader 完整性解决「分歧处谁的内容必须保留」（裁决问题）。定位准确加裁决公正，正是复制日志得以在故障中收敛的原因。
