# 日志匹配特性与一致性

> 对应 Ongaro & Ousterhout 2014（Raft）与 Lamport 1998（Paxos 安全性）。

## 一、背景与挑战
多副本日志可能因 Leader 切换、网络分区而分歧。若不经过严格对齐，apply 会发散。日志匹配特性（Log Matching）是保证「已提交项永远不丢、且不冲突」的数学基石。

## 二、核心原理
两条引理：① 若两日志在 index i 的 term 相同，则它们 i 之前完全相同（归纳自 append 的 prev 检查）；② Leader 完整性——被选出的 Leader 含所有已提交项。二者共同保证安全性：一旦某项提交，任何未来 Leader 都有它。

## 三、形式化与数学基础
形式化归纳：AppendEntries 带 (prevLogIndex, prevLogTerm)，follower 拒绝不匹配，故接受即保证前缀一致。Leader 完整性由选举限制（候选人日志须不落后于选民）保证：
\\[
\forall committed\ entry\ e,\ candidate.log \text{ contains } e
\\]

## 四、代码实现
```python
def election_eligible(candidate_log, voter_log, last_idx, last_term):
    # 候选人日志不能比选民旧
    if candidate_log[-1].term != last_term:
        return candidate_log[-1].term > last_term
    return len(candidate_log)-1 >= last_idx
```

## 五、与其他技术对比
Paxos 用「 chosen 值不变」保证安全，表述更抽象；Raft 把同样保证落到「日志匹配加选举限制」，更易验证。二者安全性等价。

## 六、常见误区
1. 认为任期高就能当选：还需日志至少不落后。
2. 冲突项保留不动：Raft 强制覆盖以达一致。
3. 提交后还能被截断：安全性保证已提交项永不被覆盖。

## 七、与开源书/权威来源对应
Raft 论文「Safety」一节证明日志匹配与 Leader 完整性；Lamport 1998 给出 Paxos 安全性；6.824 强调此性质。

## 八、面试题
问：日志匹配如何保证不丢已提交？
答：Leader 完整性确保新 Leader 含所有已提交项，日志匹配确保这些项不会被后续覆盖。

## 九、演进与趋势
将日志匹配性质形式化验证（如 Coq 证明 Raft 安全）成为研究热点。

## 十、小结
日志匹配与 Leader 完整性是 Raft 安全的两根支柱，确保已提交日志永不被篡改或丢失。
