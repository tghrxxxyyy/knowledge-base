# 字节序基本概念

> 对应 Cohen 1981《On Holy Wars and a Plea for Peace》与 Bryant & O'Hallaron《CSAPP》第 2 章。

## 一、背景与挑战

多字节整数在内存中按字节存放的顺序有两种约定：**小端**（little-endian，低位字节在低地址）与**大端**（big-endian，高位字节在低地址）。二者只差一个方向，却足以让同一段字节被解释成完全不同的数值。

当数据跨架构、跨网络或跨语言传输时，若收发双方对字节序的假设不一致，就会出现「数值莫名其妙」的 bug：端口号差 256 倍、长度字段指向错误位置、图像颜色通道错乱。历史上这被称为「字节序圣战」（Cohen 1981 语），至今在系统编程中仍是必须明确的约定。

## 二、核心原理

以 32 位值 `0x01020304` 为例，其四个字节在内存中的排列为：

- **小端**：`04 03 02 01`（低地址存放在最低有效字节），见于 x86、多数 ARM 默认配置；
- **大端**：`01 02 03 04`（低地址存放在最高有效字节），见于网络字节序、部分 RISC 与 Power 架构。

小端的优势在于：低位运算与类型扩展（如 32 位转 64 位）无需移动已有字节，地址不变；大端的优势在于：数值从左到右即从高到低，符合人类阅读习惯，且与网络传输的自然顺序一致。二者没有绝对优劣，关键在于**协议双方约定一致**。

判断本机字节序的做法是：把一个多字节常量存入变量，读取其首字节，若等于最低字节则为小端。

## 三、形式化与数学基础

设整数 $V = \sum_{i=0}^{n-1} b_i \cdot 256^{i}$，其中 $b_0$ 为最低有效字节，$b_{n-1}$ 为最高有效字节。在地址基 $A$ 处，内存布局为：

$$
\text{mem}[A+i] = \begin{cases} b_i, & \text{little-endian} \\ b_{n-1-i}, & \text{big-endian} \end{cases}
$$

两种序互为字节级反转：

$$
\text{mem}_{\text{BE}}[i] = \text{mem}_{\text{LE}}[n-1-i]
$$

以 $V = 0\text{x}01020304$（$b_0=04, b_1=03, b_2=02, b_3=01$）代入 $n=4$ 即得上述字节序列。需要强调的是，字节序只决定**字节**的排列，不影响字节内部的位序：

$$
\text{bit order within a byte}:\ b_i = \sum_{j=0}^{7} \text{bit}_j \cdot 2^{j}\quad \text{（与字节序无关）}
$$

## 四、代码实现

```c
#include <stdio.h>
#include <stdint.h>

int main(void) {
    // 1) 观察多字节整数的字节排列
    uint32_t v = 0x01020304u;
    unsigned char *p = (unsigned char *)&v;
    printf("%02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);

    // 2) 运行时判断本机字节序
    uint16_t t = 0x0001u;
    if (*(unsigned char *)&t == 0x01) {
        printf("little-endian\n");
    } else {
        printf("big-endian\n");
    }

    // 3) 编译期判断（C99 及以上，利用联合体常量表达式）
    union { uint16_t u; unsigned char c[2]; } probe = { .u = 0x0001u };
    printf("first byte = 0x%02x\n", probe.c[0]);
    return 0;
}
```

## 五、与其他技术对比

| 维度 | 小端（LE） | 大端（BE） |
| --- | --- | --- |
| 低地址存放 | 最低有效字节 | 最高有效字节 |
| 典型平台 | x86、多数 ARM | 网络序、部分 RISC/Power |
| 类型扩展 | 地址不变，便于低位运算 | 需移动字节 |
| 人类可读性 | 逆序，不易直读 | 与书写顺序一致 |
| 网络传输 | 需转换（`hton*`） | 天然一致 |
| 适用建议 | 本机计算主流 | 协议/持久化约定 |

## 六、常见误区

- **误认为字节序影响位序**：字节序只决定字节存放顺序，字节内部的位顺序不受影响。
- **以为单字节数据也受影响**：字节序仅针对多字节类型，`char`/`uint8_t` 无此问题。
- **把「网络字节序」当成主机内存布局**：它只是传输约定，主机内部仍是本机序。
- **假设所有 ARM 都是小端**：ARM 支持可配置字节序，虽以 LE 为主，但不能想当然。
- **忽略文件格式约定**：如 BMP、PNG 等格式规定了自己的字节序，读取时必须按格式转换。
- **用 `memcpy` 跨机传结构体**：同时踩中字节序与结构体填充两个问题。

## 七、与开源书·权威来源对应

Cohen 1981《On Holy Wars and a Plea for Peace》以幽默而严谨的方式提出 endian 概念并主张明确约定，是字节序讨论的经典文献；Bryant & O'Hallaron《CSAPP》第 2 章用图示对比大小端的内存布局；Tanenbaum《Computer Networks》从协议设计角度解释为何需要统一的网络字节序。具体平台行为以目标架构官方最新文档为准。

## 八、面试题

- **问：如何判断本机字节序？** 答：放一个多字节常量，读其首字节：等于最低字节即小端，等于最高字节即大端。
- **问：字节序会影响位序吗？** 答：不会。它只决定字节的存放顺序，字节内位顺序由硬件与约定单独决定。
- **问：为什么网络选大端？** 答：历史约定与可读性，早期网络主机多为大端，统一后便于实现。
- **问：小端有什么实际优势？** 答：低位在低地址，便于低位运算、类型扩展与地址复用，是主流计算平台的选择。

## 九、演进与趋势

硬件层面，ARM 等支持 BE8/LE 等多种配置，但软件生态以 LE 为主，跨序问题更多由序列化层规避。Protobuf、Cap'n Proto、FlatBuffers 等通过显式编码或定长小端约定，让应用几乎不必关心字节序。趋势是把「字节序」从应用代码上移到格式标准与工具链。

## 十、小结

字节序是「字节在内存中的排列约定」，小端低位在前、大端高位在前，仅影响多字节类型的字节顺序。理解它，能避免跨平台与网络数据的错读；实践中应显式约定并在边界处转换，而不是依赖「本机就是这样」的假设。
