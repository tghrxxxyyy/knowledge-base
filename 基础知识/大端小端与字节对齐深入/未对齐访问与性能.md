# 未对齐访问与性能

> 对应 Intel SDM（Intel 64 and IA-32 Architectures Software Developer's Manual）与 ARM Architecture Reference Manual（ARMv8-A 对齐要求）。

## 一、背景与挑战

「未对齐访问」指访问地址不是访问大小的整数倍，例如用 4 字节指令读取地址 `0x1003`。这类访问在不同架构上行为差异极大：x86 通常允许但可能变慢；ARM 传统上要求严格对齐，未对齐访问可能触发异常或由硬件模拟。

更深的影响在并发与性能：未对齐访问可能跨缓存行，被拆成两次内存操作，从而失去原子性、产生撕裂读；在 SIMD 与多线程场景中，这既是性能问题也是正确性问题。

## 二、核心原理

**x86 侧**：大多数普通访存指令支持未对齐访问，硬件自动拆分为多次总线操作。但仍有例外：部分 SIMD 指令（如早期的 `movdqa`）要求对齐；`LOCK` 前缀的原子操作对未对齐地址行为受限。

**ARM 侧**：ARMv8-A 放宽了对普通访存的未对齐支持，但对原子、独占访问（exclusive）与多字节访问仍有严格对齐要求，未对齐的原子操作往往直接未定义。

**性能机理**：CPU 以缓存行为单位（通常 64 字节）与内存交互。未对齐访问若跨越缓存行边界，需要两次行访问，吞吐下降；若同时跨页，代价更高。对齐访问则落在单行、可由单条微指令完成。

因此，编译器会主动插入填充、优化结构体布局，并假定开发者不做未对齐访问；一旦人为构造（如强制指针转换），就进入未定义行为区。

## 三、形式化与数学基础

设访问地址为 $a$、大小为 $s$、要求的对齐为 $k$（通常 $k = s$）。未对齐度定义为：

$$
u = a \bmod k,\qquad \text{未对齐} \iff u \neq 0
$$

设缓存行大小为 $L = 64$（字节），访问跨越的行数为：

$$
n_{\text{lines}} = \left\lceil \frac{(a \bmod L) + s}{L} \right\rceil
$$

- 对齐访问（如 $a \bmod 64 = 0$、$s = 8$）：$n_{\text{lines}} = 1$；
- 跨越边界的未对齐访问（如 $a \bmod 64 = 60$、$s = 8$）：$n_{\text{lines}} = 2$。

这解释了对齐访问的性能优势：单行访问可一次完成，且能被硬件原子地处理（当 $s$ 不超过缓存行且不跨界时）。撕裂读的判据是：若写方与读方各自拆分为多次操作，读方可能观测到新旧混合值。

## 四、代码实现

```c
#include <stdint.h>
#include <string.h>

// 可移植的未对齐读取：手动逐字节拼装，避免架构异常
static inline uint32_t rd_unaligned(const void *p) {
    const unsigned char *b = (const unsigned char *)p;
    return (uint32_t)b[0] | ((uint32_t)b[1] << 8) |
           ((uint32_t)b[2] << 16) | ((uint32_t)b[3] << 24);
}

// 显式告知编译器允许未对齐：GCC/Clang 会生成安全的指令序列
static inline uint32_t rd_packed(const void *p) {
    uint32_t v;
    memcpy(&v, p, sizeof(v));   // 编译器将其优化为单条对齐/未对齐指令
    return v;
}

// 对齐版本：编译器可放心使用宽指令
static inline uint32_t rd_aligned(const uint32_t *p) {
    return *p;
}
```

在需要兼容严格对齐架构时，优先使用 `memcpy`（编译器懂其语义并生成最优序列），而非强制指针转换解引用。

## 五、与其他技术对比

| 行为 | 对齐访问 | 未对齐访问（x86） | 未对齐访问（严格架构） |
| --- | --- | --- | --- |
| 是否合法 | 合法 | 多数合法，部分指令非法 | 可能触发异常/未定义 |
| 访存次数 | 1 次 | 可能 2 次（跨行） | 由硬件模拟或异常处理 |
| 原子性 | 单行内可原子 | 不可靠，可能撕裂 | 不保证 |
| 性能 | 最优 | 下降 | 显著下降或崩溃 |
| 编译器假设 | 成立 | 进入 UB，优化可能出错 | 进入 UB |

## 六、常见误区

- **认为 x86 上未对齐完全无害**：虽不报错，但性能下降、失去原子性，且部分 SIMD/原子指令仍非法。
- **用指针强制转换规避对齐**：这是未定义行为，编译器可能在优化时做出错误假设。
- **忽略缓存行边界**：对齐到 4/8 字节不等于不跨 64 字节行，热点数据仍可能跨界。
- **在多线程中用未对齐共享变量**：可能撕裂读，必须使用对齐的原子类型或加锁。
- **滥用 packed 结构体**：把原本对齐的字段变成未对齐访问，得不偿失。
- **忘记 SIMD 对齐要求**：向量化访问通常要求 16/32/64 字节对齐，未对齐需走慢路径。

## 七、与开源书·权威来源对应

Intel SDM 详细描述各指令在未对齐地址下的行为，以及对原子性与性能的影响；ARM Architecture Reference Manual（ARMv8-A）规定对齐要求与未对齐访问的异常/模拟语义；Bryant & O'Hallaron《CSAPP》第 3 章讨论对齐访问的效率与结构体布局的关系。具体指令级行为以各架构官方最新文档为准。

## 八、面试题

- **问：为何多线程下未对齐读危险？** 答：可能被并发写拆成两次访存，读到新旧混合值，且原子指令对未对齐地址不可用。
- **问：x86 与 ARM 在未对齐访问上的差异？** 答：x86 大多允许但可能变慢；ARM 传统上更严格，ARMv8 放宽普通访存但仍约束原子与多字节访问。
- **问：如何安全地读未对齐数据？** 答：用 `memcpy` 或逐字节拼装，避免指针强制转换解引用。
- **问：未对齐访问为何可能变慢？** 答：跨越缓存行需两次行访问，跨越页边界代价更高。

## 九、演进与趋势

编译器与运行时提供了更强的检测与保障：UBSan 的 `alignment` 检查可在开发期捕获未对齐访问；`atomic_ref`、`std::atomic` 要求对象正确对齐；SIMD 生态（如 AVX-512）提供对齐与未对齐两套指令，由编译器与自动向量化选择。趋势是让「对齐」从依赖程序员纪律，逐步转为工具链与类型系统的强制约束。

## 十、小结

未对齐访问是「可移植性与性能」的双重陷阱：在 x86 上可能只是变慢并失去原子性，在严格对齐架构上则可能直接异常。理解各架构行为，优先使用 `memcpy` 与正确对齐的类型，并在并发场景坚持对齐访问，才能写出安全且高效的代码。
