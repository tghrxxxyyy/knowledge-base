# 网络字节序转换

> 对应 RFC 791（IPv4）与 RFC 793（TCP）及 Stevens《UNIX Network Programming》中的字节序规定。

## 一、背景与挑战

TCP/IP 协议族规定：所有多字节整数字段在网络上以**大端**（big-endian）传输，即最高有效字节先发，这也被称为「网络字节序（network byte order）」。而主流主机（x86、ARM）多是小端，若直接把本机内存里的整数发出去，接收方按大端解析会得到完全错误的值。

以端口 8080（0x1F90）为例，小端内存是 `90 1F`，若原样发送则被对端理解成 0x901F = 36895。这类错误常见于手写协议、裸 socket 编程或二进制格式解析，后果是隐蔽而严重的：端口、长度字段、IP 地址全部错位。

## 二、核心原理

标准库提供四个转换函数，成对覆盖 16/32 位：

- `htons` / `htonl`：host to network，short(16) 与 long(32)，发送前调用；
- `ntohs` / `ntohl`：network to host，接收后调用。

在大端主机上这些函数通常是**空操作**（no-op），在小端主机上执行字节翻转。因此代码应始终调用它们，而非依赖「本机就是大端」的假设，这样才能在异构集群中可移植。

处理 IP 地址时，还有更语义化的接口：`inet_pton`（文本 → 二进制网络序）与 `inet_ntop`（二进制 → 文本）。它们自动处理字节序与点分十进制解析，优于手工拆分字符串再 htonl。

## 三、形式化与数学基础

设 16 位值 $V$，其大端表示的高、低字节为 $b_1, b_0$，则 $V = b_1 \cdot 256 + b_0$。小端主机需交换两字节：

$$
V_{\text{net}} = \text{swap16}(V) = b_0 + b_1 \cdot 256 = ((V \,\&\, 0\text{xFF}) \ll 8) \mid ((V \gg 8) \,\&\, 0\text{xFF})
$$

对 32 位值同理，按 4 字节整体逆序：

$$
\text{swap32}(V) = \text{bswap}\big(V,\ 4\big)
$$

并用恒等式校验其自反性（翻转两次还原）：

$$
\text{swap16}(\text{swap16}(V)) = V,\qquad \text{swap32}(\text{swap32}(V)) = V
$$

判断本机字节序可用联合体或指针读首字节：

$$
\text{little-endian} \iff \text{mem}[0] = b_0
$$

## 四、代码实现

```c
#include <arpa/inet.h>   // htons/htonl/inet_pton
#include <stdint.h>
#include <stdio.h>

int main(void) {
    uint16_t port = htons(8080);          // 主机序 -> 网络序
    uint32_t ip   = htonl(0x0A000001);    // 10.0.0.1 网络序存放
    printf("port bytes: %02x %02x\n",
           ((unsigned char*)&port)[0], ((unsigned char*)&port)[1]);

    // 文本 IP -> 网络序二进制，自动处理字节序
    struct in_addr addr;
    if (inet_pton(AF_INET, "10.0.0.1", &addr) != 1) {
        return 1;
    }
    printf("network order: %08x\n", ntohl(addr.s_addr));

    // 接收方向：网络序 -> 主机序
    uint16_t host_port = ntohs(port);
    printf("host port: %u\n", host_port);
    return 0;
}
```

## 五、与其他技术对比

| 方案 | 可移植性 | 易错点 | 适用场景 |
| --- | --- | --- | --- |
| `htons`/`htonl` 等标准函数 | 高 | 需成对调用，勿混用 16/32 位 | 通用协议字段 |
| 手工位移实现 | 高但需自测 | 位运算写错、符号扩展 | 无标准库的嵌入式环境 |
| `inet_pton`/`inet_ntop` | 高 | 返回值为 0/1/-1，需检查 | IP 地址文本与二进制互转 |
| 直接 `memcpy` 发送结构体 | 低 | 字节序 + 填充双重错误 | 严禁用于跨机通信 |
| 访问器 `__bswap_16`/`__builtin_bswap32` | 高 | 需确认底层字节序 | 性能敏感的内核/驱动 |

## 六、常见误区

- **误以为字符串 IP 需要字节序转换**：`"10.0.0.1"` 是文本，转成二进制时才涉及字节序，`inet_pton` 已正确处理。
- **发送时忘了转换**：本机能通、跨机失败，是典型的字节序 bug。
- **16/32 位函数混用**：对 uint16 调用 `htonl` 会读取越界字节，产生错误值。
- **对结构体整体 `memcpy`**：同时踩中字节序与结构体填充两个坑，跨平台必然出错。
- **认为「网络字节序」等于「大端内存」**：它只是逻辑约定，主机内部仍是本机序。
- **忽略长度前缀**：协议中长度字段也须转换，否则对端读不到正确边界。

## 七、与开源书·权威来源对应

RFC 791（Internet Protocol）与 RFC 793（Transmission Control Protocol）明确规定了首部字段使用网络字节序（大端）；Stevens《UNIX Network Programming》详细讲解 `htons`/`htonl` 与 `inet_pton` 的用法与陷阱；Tanenbaum《Computer Networks》从协议设计角度解释统一字节序的必要性。具体接口语义以各系统官方最新文档为准。

## 八、面试题

- **问：为什么网络统一用大端？** 答：历史约定与可读性，早期网络主机多为大端，沿用成标准，实现只需按约定转换即可。
- **问：`htons` 在大端主机上做什么？** 答：通常为空操作，但代码仍应调用以保证可移植。
- **问：如何判断本机字节序？** 答：取多字节整数的首地址字节，等于最低字节即小端，等于最高字节即大端。
- **问：`inet_pton` 与 `htonl` 的关系？** 答：前者做文本到二进制的解析（已输出网络序），后者做主机序到网络序的数值转换。

## 九、演进与趋势

上层序列化（JSON、Protobuf、Cap'n Proto）多采用显式编码或定长小端加变长整数，绕开了裸字节序问题，让应用层几乎不必手写转换。但底层协议、硬件寄存器与二进制文件格式仍严格依赖字节序约定，`htons` 一类接口依然是网络编程的基本功。

## 十、小结

网络字节序统一为大端，主机序到网络序的转换必须由标准函数完成，不能靠假设。正确做法是：发送前 `hton*`、接收后 `ntoh*`、IP 用 `inet_pton`/`inet_ntop`、绝不直接 `memcpy` 结构体。掌握这一细节，是跨平台网络通信正确性的基础。
