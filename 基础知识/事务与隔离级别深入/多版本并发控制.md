# 多版本并发控制

> 对应 Bernstein & Goodman MVCC 综述，以及 DDIA 中文第 7 章、MySQL InnoDB MVCC。

## 一、背景与挑战
传统锁让读写互相阻塞。MVCC 通过保留数据的多个版本，让读访问旧版本、写创建新版本，从而读不加锁、读写不阻塞。

## 二、核心原理
每行带系统版本号（或事务 ID）标记创建/过期版本。读事务按自身快照选择可见版本；写事务创建新版本并链接旧版本（版本链）。清理（vacuum/purge）回收不再被任何快照需要的版本。

## 三、形式化 / 数学基础
可见性谓词（InnoDB 风格）：对事务 $T$（读视图 up_limit_id），版本 $v$ 可见当 $v.creat_trx < up\_limit\_id$ 且 $v.del_trx$ 为空或 $\ge up\_limit\_id$。即未被本快照之后事务删除。

## 四、代码实现
```c
// 简化可见性判断
int visible(Version *v, uint64_t snap) {
    if (v->creat_trx >= snap) return 0;        // 本快照后创建
    if (v->del_trx && v->del_trx < snap) return 0; // 本快照前已删
    return 1;
}
```

## 五、与其他技术对比
| 方案 | 读写阻塞 | 版本存储 | 清理 |
|------|----------|----------|------|
| 锁 | 阻塞 | 无 | 无 |
| MVCC | 不阻塞 | 多版本 | 需 vacuum |
| SI | 不阻塞 | 多版本 | 需 vacuum |

## 六、常见误区
1. MVCC 无锁——写写仍需冲突处理。
2. 版本无限保留——需定期 purge，否则膨胀。
3. 长事务无害——会阻止旧版本回收。

## 九、演进与趋势
将版本回收下推到存储层（如 Aurora）、用 undo 日志链与可见性视图优化，降低 vacuum 开销。

## 十、小结
MVCC 以空间换并发，靠版本链与可见性规则实现无锁读；版本清理是运维重点。
