# 异步与同步快照

> 对应 Chandy & Lamport 1985（异步无中断快照）；Tanenbaum《Distributed Systems: Principles and Paradigms》故障恢复章节；Carbone et al. 2015（Apache Flink 异步屏障快照）。

## 一、背景与挑战

快照可在「停止整个世界」的同步方式下进行，也可在不中断处理的异步方式下进行。二者在一致性保证与系统可用性上差异巨大：同步简单但造成停顿（STW），异步复杂但保留吞吐。选择取决于系统对可用性、一致性与开销的容忍度。一个关键洞察是：一致性的「代价」在不同方案间是此消彼长的——同步把代价集中为停顿，异步把代价摊薄为缓冲与协调。

工程上还要区分「快照」与「检查点」两种用途：快照用于读一致性视图或故障恢复起点，检查点则强调可回滚的持久化点。前者对一致性要求更高，后者对恢复速度要求更高；同一系统可能同时需要两者，因而快照模型的选择还必须与恢复流程、日志保留策略协同设计。

## 二、核心原理

- 同步快照：协调者暂停所有进程，依次记录各自状态，再恢复。因所有进程同时静止，所得状态天然一致（相当于全局时钟冻结）。简单、易证，但期间系统不可用、延迟尖刺，不适合长尾敏感的服务。
- 异步快照：用 marker / barrier 在不停止处理的前提下记录一致 cut。进程照常处理消息，仅旁路抄送状态；无全局停顿，但需缓冲「先到通道数据」以保证对齐，带来额外内存/延迟开销。本质是「用缓冲换不停顿」。

异步快照的核心机制可拆成三步：其一，协调者在某时刻向所有进程注入 marker（或 barrier）；其二，进程首次收到 marker 时立即记录自身状态，并把 marker 沿所有出边转发；其三，进程在等待某条入边上的 marker 期间，把该通道上先到的业务消息缓冲起来，直到 marker 到达后再按序处理。这样得到的每个进程「记录状态 + 各入通道缓冲」的组合，恰好构成一个一致 cut。与同步快照的关键区别是：异步快照的「瞬时性」是逻辑上的而非物理上的——各进程记录时刻在真实时间上错开，但通过通道缓冲记账，逻辑上等价于某一时刻的全局静止。

## 三、形式化与数学基础

同步快照延迟约 $O(\sum state)$ 且期间吞吐为 0；异步快照把开销摊薄到处理中，吞吐近似不降，但需额外缓冲 $B$ 满足：

$$B \le \sum channel\_inflight$$

即缓冲所有「已收未处理、或对齐中」的在途消息。设同步停顿 $P_{sync}$，异步额外缓冲延迟 $L_{async}$，权衡为：当 $P_{sync} \gg L_{async}$ 且状态大时，异步更优。精确地说，异步快照的完成时间受最慢对齐路径约束，而非全量停顿。

用 cut 的定义可以更精确地刻画一致性：全局状态 $S = (S_1, \dots, S_N)$ 与通道状态 $C_{ij}$ 构成一致快照，当且仅当不存在「被记录为已发送但未被记录为已接收」的消息丢失或重复——形式化地说，对任意消息 $m$，若 $send(m) \in S_i$ 且 $receive(m) \notin S_j$，则 $m \in C_{ij}$。这正是 marker 协议的记账目标。完成时间方面，若快照传播沿最长有向路径需要 $D$ 跳、每跳延迟 $\ell$，则异步快照总时延近似 $D \cdot \ell + \max_i \tau_i$（$\tau_i$ 为进程 $i$ 记录自身状态的时间），与全系统状态总量无关——这是异步方案可扩展性的数学根源。

## 四、代码实现

```python
# 同步快照（伪代码）：协调者驱动
def sync_snapshot(procs):
    for p in procs:
        p.pause()                      # 暂停所有进程
    states = [p.snapshot() for p in procs]   # 全局静止后依次记录
    for p in procs:
        p.resume()                     # 恢复处理
    return states                      # 天然一致，无需通道缓冲

# 异步快照：各进程独立记录，由 marker 界定 cut（Chandy-Lamport 思路）
class AsyncProc:
    def __init__(self, inbound):
        self.recorded, self.state = False, None
        self.buffers = {c: [] for c in inbound}   # 每条入通道缓冲

    def on_business_msg(self, ch, msg):
        if self.recorded and msg.marker_pending(ch):
            self.buffers[ch].append(msg)   # 对齐期：先到消息入缓冲
        else:
            self.apply(msg)                # 平时：正常处理

    def on_marker_trigger(self, ch):
        if not self.recorded:              # 首次收到 marker
            self.state, self.recorded = self.snapshot(), True
            for out in self.out_channels:
                out.send(MARKER)           # 沿所有出边转发 marker
        else:
            self.buffers[ch].close()       # 该通道对齐完成

# 协调者等待所有进程回报完成
def coordinator(procs):
    for p in procs:
        p.inject(MARKER)                   # 或由某一进程作为发起者
    wait_until(all(p.snapshot_done() for p in procs))
```

实现上有两处易错：其一，marker 必须与业务消息走同一通道并保持队内顺序，否则会「越过」先发消息导致漏记；其二，进程首次收到 marker 就要立刻转发，不能等到记录完所有通道，否则快照传播会被拖慢，与异步的初衷相悖。

## 五、与其他技术对比

| 维度 | 同步快照 | 异步快照（对齐） | 非对齐快照 |
| --- | --- | --- | --- |
| 系统可用性 | 中断 | 不中断 | 不中断 |
| 一致性 | 天然一致 | 需对齐/缓冲保证 | 需额外记账恢复 |
| 额外内存 | 无 | 在途消息缓冲 | 极小 |
| 适用规模 | 小/可停顿 | 大/流式 | 强反压/超大状态 |
| 实现复杂度 | 低 | 中 | 中高 |
| 恢复代价 | 低 | 低 | 略高（需重放通道状态） |

同步简单但大规模不可行；Flink 等流系统选异步（ABS）以保 Exactly-Once。数据库 checkpoint 多类似异步（后台刷盘 + WAL）。二者不是优劣，而是场景选择。非对齐快照是对齐方案的进一步变体：它放弃「等待对齐」，直接记录通道中的在途数据量，用恢复期的重放换取检查点期的零阻塞，适合反压严重、对齐迟迟无法完成的场景。

## 六、常见误区

1. 认为异步快照一定更快：对齐期间缓冲与反压可能使特定检查点更慢，是权衡非绝对优势。
2. 同步快照在大规模下完全不可行：对配置小、可短暂停顿的系统仍可接受（如单节点状态导出、测试环境）。
3. 忽略异步的缓冲上限：在途消息无界增长会 OOM，需背压或 unaligned checkpoint 兜底。
4. 混用两种语义：同系统须统一快照模型，否则恢复点不一致，无法正确回放。
5. 认为同步快照一定一致：若暂停顺序有漏洞（先 resume 部分再 pause 其他），仍可能不一致，需严格「全停→全记→全恢复」。
6. 把 marker 当普通消息处理：marker 必须保序且被优先识别，否则会被业务逻辑消费掉，导致 cut 无法闭合；此外还须注意输入源可重放性与「快照完成 ≠ 数据已落盘」，否则恢复时会缺数据。

## 七、与开源书·权威来源对应

- Chandy & Lamport 1985 给出异步无中断快照的理论基础，证明 marker 驱动可得一致 cut。
- Tanenbaum《Distributed Systems》故障恢复章节对比 STW 与异步检查点，讨论恢复时间目标（RTO）。
- Carbone et al. 2015 描述 Flink 异步屏障快照（ABS）的工程实现与 Exactly-Once 保证。
- Coulouris 等《Distributed Systems: Concepts and Design》从全局状态与一致 cut 角度补充讨论。

## 八、面试题

1. 问：异步快照如何避免全局停顿？
   答：用 marker/barrier 界定一致 cut，各进程独立旁路记录状态，正常消息处理不中断，仅额外缓冲对齐期数据。
2. 问：何时同步快照仍可接受？
   答：状态小、可容忍短暂停顿（如单节点导出、测试环境、低频配置类快照）时，同步更简单且易证一致。
3. 问：异步快照的额外开销来自哪？
   答：对齐期缓冲先到通道数据、状态异步刷盘的 I/O 与内存占用，以及 barrier 传播协调成本。
4. 问：同步 vs 异步的权衡本质？
   答：把一致性代价从「集中停顿」摊薄为「分布式缓冲+协调」，换来可用性但增加实现复杂度与内存峰值。
5. 问：marker 为什么必须与业务消息同通道保序？
   答：若 marker 可越过先发消息，该消息就不会被记入通道缓冲，导致 cut 丢失消息、快照不一致。

## 九、演进与趋势

增量快照只记录状态差降低异步开销；unaligned checkpoint（Flink）在反压下放弃严格对齐，改用通道状态记录（回到 CL 思路）缓解瓶颈；与持久化分层存储结合降低刷盘成本。研究还探索「分级快照」（热/冷数据不同频率）。

同时，快照与共识日志的结合日益紧密：把快照视为日志的压缩点，用「日志 + 快照」共同支撑恢复，既控制了日志长度，又缩短了重放时间；其核心是保证「快照点与日志序号严格对应」，否则恢复会读到跨越不一致边界的组合状态。具体机制以各系统官方最新文档为准。

## 十、小结

异步快照以少量缓冲换无中断，是现代流/存储系统的首选；同步快照以简单与天然一致换取可用性代价。二者并非优劣之分，而是「可用性 vs 复杂度」的取舍——理解这点才能为具体系统选对快照模型。没有银弹，只有适配场景的工程选择。决策要点三条：状态小且可停→同步；状态大且需在线→异步对齐；反压严重导致对齐全阻塞→非对齐；选错其一的后果是恢复点不一致或吞吐被拖垮。
