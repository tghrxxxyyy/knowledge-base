# 快照的通道状态

> 对应 Chandy & Lamport 1985（Distributed Snapshots: Determining Global States of a Distributed System，channel state recording）；MIT 6.824 Lab 3 对通道状态的实现要求；Coulouris《Distributed Systems》。

## 一、背景与挑战

全局快照不止包含各进程（节点）的本地状态，还包含「在途消息」——即快照边界处仍在通道上传输、尚未被接收方计入的消息。只拍进程状态、漏掉在途消息，会得到自相矛盾（幽灵消息或丢失消息）的全局视图。例如进程 A 快照记「已发 m 给 B」，但 B 的快照在 m 到达前已拍——若 m 不被记入通道状态，则全局状态里 m 凭空消失。通道状态记录的就是这条边界上「发出但未达」的消息集合。

这个问题的本质是「分布式系统没有全局时钟，也没有瞬时全局状态」。任何快照都是在不同时刻对各个进程的采样，必须额外记录「采样时刻之间跨边界的传输」，才能拼出一个逻辑上自洽的全局状态。通道状态就是这份「补丁」。

另一个实践困难是「在途消息可能很多」：高吞吐通道上，一毫秒内可能有成千上万条消息在传输，逐条记录会带来巨大开销。因此工程实现（见演进节）会用「序列号区间」等紧凑表示替代逐条记录。

## 二、核心原理

在 Chandy-Lamport 算法中，进程开始记录自身状态后，到对应通道的 marker 到达前，所有收到的应用消息都记入该通道状态；marker 到达即关闭该通道的记录。最终某通道 $C(p\to q)$ 的状态 = 「在快照前由 $p$ 发出、在快照后才被 $q$ 收到」的消息集合。记录动作对应用层透明：应用消息照常投递与处理，只是同时被旁路抄送进快照缓冲。关键：通道状态是「接收方视角」在入边侧记录的，每个有向通道独立。

按「谁负责记录」划分，CL 算法有三种等价视角：发起者记录自身状态后沿出边发 marker；接收者收到 marker 前把入边消息记为通道状态；发起者也可能通过「先发 marker 再继续发送数据」的方式，让其出边由下游记录。三种视角得到的结果完全一致，实现时按方便选择即可。

需要强调「记录与投递并行」：属于通道状态的消息既要被记录，也要照常投递给应用（否则会改变程序行为）。因此实现上通常采用「写日志 + 正常处理」双写路径，而不是「拦截后不投递」。这是 CL 算法能「不停止系统」的关键。

## 三、形式化与数学基础

对通道 $C(p\to q)$，记 $M_{pre}$ 为 marker 前由 $p$ 发出的消息，$M_{post}$ 为 marker 后发出的。通道状态为：

$$S_C = \{\, m \in M_{pre} \mid r_m\ \text{发生在快照记录之后}\,\}$$

即 $m$ 已发出但接收事件落在接收方快照之后。该集合保证全局状态因果闭合：若 $m$ 影响了发送方快照后的状态，则其效果由通道状态代偿，使 cut 一致。形式化上 $S_C$ 正是「跨 cut 进入」的消息集合（见《快照的局限与演进》）。

一致性条件可表述为：全局状态 $S = (S_{p_1}, \dots, S_{p_n}, S_{C_1}, \dots, S_{C_m})$ 是一致的，当且仅当不存在「消息被接收但不在任何通道状态中」的情形，也不存在「消息既在通道状态中又被计入接收方状态」的情形。前者会导致消息凭空出现（幽灵消息），后者导致消息重复计数。

用 cut 的语言：一致 cut 要求「若接收事件在 cut 内，则对应的发送事件也必须在 cut 内」。通道状态 $S_C$ 正是那些「发送在 cut 内、接收在 cut 外」的消息，它把这一违反条件补齐，使整体满足一致性。

## 四、代码实现

```python
# 通道状态记录（进程侧）
def on_msg(self, ch, msg, snap):
    if snap.recording and not snap.channel_closed[ch]:
        snap.channel[ch].append(msg)   # marker 到达前，记入在途消息
    else:
        self.deliver(msg)               # 正常投递应用层
    if msg is MARKER:
        snap.channel_closed[ch] = True  # marker 到达即关闭记录

# 收齐判定：所有入边 marker 到达后，本进程快照完成
def snapshot_done(self, snap):
    return all(snap.channel_closed[c] for c in self.in_channels)
```

用序列号区间紧凑表示通道状态（高吞吐场景）：

```python
class ChannelState:
    # 只记录"已发未达"的序列号区间，避免逐条存储消息体
    def record(self, lo, hi):
        self.ranges.append((lo, hi))
    def merge(self):
        # 合并重叠/相邻区间，得到最简表示
        self.ranges.sort()
        merged = []
        for lo, hi in self.ranges:
            if merged and lo <= merged[-1][1] + 1:
                merged[-1] = (merged[-1][0], max(merged[-1][1], hi))
            else:
                merged.append((lo, hi))
        self.ranges = merged
```

## 五、与其他技术对比

| 记录对象 | 是否含在途消息 | 一致性 | 主要用途 |
| --- | --- | --- | --- |
| 仅进程状态 | 否 | 可能丢失在途消息 | 不完整，不可用于恢复 |
| CL 通道状态 | 是 | 一致 cut | 全局逻辑视图、恢复 |
| 数据库 WAL | 记录已落盘日志 | 非在途概念 | 崩溃恢复 |
| Flink 对齐缓冲 | 是（隐式） | 一致 cut | 流式检查点 |
| 序列号区间 | 是（紧凑） | 一致 cut | 高吞吐通道 |

仅记录进程状态会丢在途消息；数据库 WAL 记录的是已持久化日志而非传输中消息，语义不同——WAL 用于崩溃恢复，CL 通道状态用于全局逻辑视图，二者目的不同不可混用。

## 六、常见误区

1. 把 marker 当普通消息处理：marker 不应进入通道状态，也不可被应用消费，须旁路识别。
2. 在 marker 到达后仍写入通道状态：会使通道状态多算已到达的消息，破坏一致性。
3. 忽略通道方向：每个有向通道独立记录，入边与出边的「在途」定义相反（出边是「已发」，入边是「未达」）。
4. 假设通道自动保序：CL 要求 FIFO，非 FIFO 需序列号辅助（见《快照的局限与演进》）。
5. 认为通道状态一定非空：若 marker 前无在途消息，通道状态为空集合，这是合法且常见的情况。
6. 以为记录后可以不投递消息：只记不投会改变程序行为，必须在记录的同时正常投递。
7. 忽略「重复记录」风险：若同一消息既被计入通道状态又被接收方状态包含，会造成重复计数，需按 marker 边界严格区分。

## 七、与开源书·权威来源对应

- Chandy & Lamport 1985 论文精确定义 channel state 为「marker 前发出、marker 后到达」的消息集，并证明集齐后全局状态一致。
- MIT 6.824 Lab 3 明确要求实现通道状态记录作为一致快照的一部分，测试常构造特定消息时序验证。
- Coulouris《Distributed Systems》第 14 章用图示说明通道状态与 cut 的关系，区分有向通道的入/出边。
- Kleppmann《DDIA》第 11 章：流处理状态与恢复中的「一致性边界」讨论。

## 八、面试题

1. 问：通道状态记录何时开始、何时结束？
   答：进程首次收到某通道 marker 即开始记录该通道入边的在途消息，该通道 marker 再次到达（或本进程向该出边发过 marker 后收到回边 marker）即关闭。
2. 问：为什么在途消息必须被记录？
   答：否则一致 cut 条件被破坏——发送方快照「已发」与接收方快照「未收」无法对账，恢复出的全局状态自相矛盾（消息丢失或重复）。
3. 问：通道状态为空是否合法？
   答：合法；当 marker 到达前该通道无在途消息时，通道状态为空集合，不影响一致性。
4. 问：为什么记录通道状态时消息仍要正常投递？
   答：CL 的目标是不停止系统；只记不投会改变程序行为，只投不记则快照不一致。
5. 问：为什么通道状态必须由接收方（入边侧）记录？
   答：因为「是否已到达」只有接收方能判断，发送方无法知道消息是否仍在途中。

## 九、演进与趋势

对无锁/高吞吐通道可用序列号区间表示状态（如「$[lo, hi]$ 已发未达」），避免逐条存储；流系统用异步屏障快照把通道状态转为对齐缓冲（见《快照在Flink中的应用》）。研究还探索「近似通道状态」以换取更低开销。

在工程实现上，还有一种「用持久化消息队列代替通道状态」的做法：如果通道本身是可靠的持久队列（如 Kafka），那么「队列中的未消费偏移」天然就是通道状态，只需在快照中记录消费位点，无需逐条复制消息。这把通道状态的记录成本降到了 $O(1)$ 每个通道。

## 十、小结

通道状态是快照一致性的关键拼图，记录的是「边界在途消息」而非全部消息。正确理解「marker 前发出、marker 后到达」这一判据，就掌握了 Chandy-Lamport 为什么能在不停止系统的前提下得到因果闭合的全局视图。漏掉通道状态，是整个算法唯一会系统性出错的地方；而把通道状态用序列号区间或消费位点紧凑表示，则是它从理论走向高吞吐工程的关键一步。
