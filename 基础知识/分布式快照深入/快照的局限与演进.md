# 快照的局限与演进

> 对应 Chandy & Lamport 1985（假设 FIFO 通道与可靠消息）；Fischer, Lynch & Paterson 1985（FLP 不可判定性背景）；Apache Flink 文档（Incremental Checkpoint）。

## 一、背景与挑战

经典 Chandy-Lamport 算法建在两个假设上：通道 FIFO 且消息可靠。但真实系统有非 FIFO 通道、消息丢失/重排序、算子动态扩缩容（rebalance）、以及超大规模下全量快照成本过高的问题。直接套用原算法会得到不一致或不可行的快照，必须扩展或另寻路径。理解局限，才能把理论快照落地为可用的容错机制。

这四个局限的性质并不相同：非 FIFO 与不可靠通道破坏的是「正确性」（快照本身会不一致），动态拓扑破坏的是「完整性」（cut 覆盖不到全部通道），而大规模破坏的是「可行性」（正确但太慢太贵）。因此应对手段也分两类——前两者必须修复协议，后两者可以靠工程优化缓解。

## 二、核心原理

- 非 FIFO 通道：需为每条消息带序列号，按发送序号集合判定「在途」，而不能仅靠 marker 前后的时间序。
- 动态拓扑：节点加入/离开需重新协调 marker 集合，新节点从加入点起参与快照，离节点须先结算其通道状态。
- 大规模系统：全量快照状态大、频率受限，转向增量/分区快照，只记录与上一次的差异。
- 通道不可靠：消息可能丢失，需用确认/重传或更高层可靠信道兜底，否则通道状态记录不全。

动态拓扑的处理有一个易被忽略的细节：节点「离开」必须与快照协调配合——若节点在快照进行中退出，其尚未结算的通道状态会永久丢失。因此实现上通常要求先禁止拓扑变更、等待当前快照完成，或让退出节点在离开前主动上报其通道状态。这类「变更与快照互斥」的设计，是分布式系统协调开销的重要来源。

## 三、形式化与数学基础

非 FIFO 下，通道状态必须用发送序号集合表示以保证因果可重建：

$$S_C = \{\, seq_i \mid msg_i\ sent\ before\ marker,\ not\ yet\ received\,\}$$

增量快照只记录状态差 $\Delta S$，恢复时：

$$S_t = S_{t-1} \oplus \Delta S$$

其中 $\oplus$ 为状态合并算子（覆盖/合并）。这要求基线 $S_{t-1}$ 持久可用，否则无法重建。增量把每次成本从 $O(|S|)$ 降为 $O(|\Delta S|)$。设全量成本 $C_{full}$、增量成本 $C_{inc}$，当 $C_{inc} \ll C_{full}$ 且快照频繁时收益显著。

增量方案还引入了一个新的失败模式：基线链。若快照 $S_t$ 依赖 $S_{t-1}$、$S_{t-1}$ 又依赖 $S_{t-2}$……则恢复时间随链长线性增长，且链上任一环节损坏都会导致整条链不可用。因此工程上必须「定期打全量锚点」（compaction），把链长限制在常数范围内——这是增量收益与恢复可靠性之间的必要折中。

## 四、代码实现

```python
# 增量快照合并（恢复时）
def apply_delta(base, delta):
    s = dict(base)                  # 复制基线
    for k, dv in delta.items():
        if dv is TOMBSTONE:
            s.pop(k, None)          # 删除
        else:
            s[k] = dv               # 覆盖/新增
    return s

# 非 FIFO 通道状态用序号集合记录
def record_channel(ch, msg, marker_seq):
    if msg.seq < marker_seq[ch]:
        ch.inflight.add(msg.seq)    # marker 前发出且未达
    # marker 后到达的 seq 从 inflight 移除

# 动态扩容：rebalance 后新分区入边纳入 marker 协调
def on_rebalance(new_partitions, snap):
    for p in new_partitions:
        snap.channel_closed[p.in_ch] = False   # 开始记录新通道

# 恢复：沿基线链回放，链过长时须先做全量锚点（compaction）
def restore(base_snapshot, deltas):
    s = base_snapshot
    for d in deltas:                # 按时间顺序应用差异
        s = apply_delta(s, d)
    return s
```

`record_channel` 中的 `msg.seq < marker_seq[ch]` 判定是非 FIFO 场景的核心：它不再依赖「消息到达的先后」，而是比较「消息本身的序号」与「marker 携带的序号」，从而在乱序通道下仍能正确判定哪些消息处于「已发未收」状态。这也是「用序号替代时间序」这一思路的具体体现。

## 五、与其他技术对比

| 方案 | 空间 | 基线依赖 | 恢复代价 | 适用 |
| --- | --- | --- | --- | --- |
| 全量 CL | 大 | 无 | $O(1)$（直接装载） | 小规模、低频 |
| 增量快照 | 小 | 需持久基线 | $O(\text{链长})$ | 大规模、高频 |
| 逻辑复制（CDC） | 极小 | 无 | 需重放全量历史 | 关注变更流 |
| 非对齐快照 | 小 | 无 | 需重放通道状态 | 强反压场景 |

全量 CL 简单但开销随状态增长；增量省空间但需基线完整；逻辑复制关注「变更流」而非「全局状态」，目标不同，不能互相替代。非对齐快照则以「恢复期多做事」换取「检查点期不阻塞」，是针对反压场景的专门优化。

## 六、常见误区

1. 在非 FIFO 通道直接套用 CL：时间序不可靠，必须用序列号界定在途，否则通道状态错乱。
2. 增量基线丢失导致无法恢复：必须保证基线 $S_{t-1}$ 持久且可达，定期做全量锚点。
3. 动态扩容时漏记新通道：rebalance 后新分区的入边须纳入 marker 协调，否则 cut 不完整。
4. 认为快照零开销：即便异步，对齐缓冲与刷盘仍有成本，需与吞吐权衡。
5. 忽略不可靠通道的丢失：消息丢失会使通道状态缺项，需可靠信道或确认机制兜底。
6. 无限延长增量链：链越长恢复越慢、单点损坏影响越大，必须定期 compaction。
7. 认为拓扑变更可与快照并行：离开节点的未结算通道会永久丢失，二者需互斥协调。
8. 把「快照成功」等同于「可恢复」：恢复还依赖状态机可重放、外部副作用可补偿等前提。

## 七、与开源书·权威来源对应

- Chandy & Lamport 1985 的假设明确为 FIFO 通道，是其正确性的隐含前提，论文也指出非 FIFO 需扩展。
- Fischer, Lynch & Paterson 1985（FLP）说明异步系统无故障下共识不可判定，提示快照/协调的底层限制。
- Apache Flink Docs: Incremental Checkpoint 描述基于 RocksDB 状态后端的增量机制（只存变更的 SST 文件）。
- Coulouris《Distributed Systems》：动态组成员与一致性的系统层讨论。

## 八、面试题

1. 问：CL 算法对通道有何假设？违反会怎样？
   答：假设 FIFO 且可靠；非 FIFO 下 marker 前后无法界定在途消息，必须用序列号补救，否则通道状态不一致。
2. 问：增量快照如何减少开销？
   答：只记录状态差 $\Delta S$，恢复时与基线合并，每次成本正比于变更量而非全量。
3. 问：为何增量需要基线？
   答：没有基线无法重建完整状态；基线须持久，并定期全量锚定以防链过长或丢失。
4. 问：动态扩容下如何保持快照一致？
   答：rebalance 后把新分区的入边纳入 marker 协调，旧分区结算其通道状态，保证 cut 覆盖全部活动通道。
5. 问：为什么必须定期做全量锚点？
   答：否则增量链无限增长，恢复时间线性上升，且链上任意一环损坏都导致整体不可恢复；非对齐快照则以「放弃检查点期对齐等待、改在恢复期重放」换取检查点不阻塞。

## 九、演进与趋势

与 CRDT/状态机复制结合做「持续一致性快照」，把快照从周期事件变为连续可查询状态；流式系统用 unaligned checkpoint 缓解反压下对齐瓶颈（见《异步与同步快照》《快照在Flink中的应用》）。研究还关注「分层快照」（内存+磁盘分级）以降低频率限制。

另一条演进线是把快照与「可验证恢复」结合：每次快照生成完整性摘要（校验和或哈希），恢复前先校验，避免用一个静默损坏的快照恢复出错误状态。这在长时间运行的流式系统中尤为必要，因为「损坏的快照」比「没有快照」更危险。

## 十、小结

Chandy-Lamport 是快照的理论基石，但其 FIFO/可靠假设与现实有 Gap。工程上需针对非 FIFO、动态拓扑、规模做扩展：序列号补非 FIFO、增量降开销、异步对齐换无中断。理论之美在于简洁，工程之难在于把简洁适配到不完美的真实系统——这正是从算法到系统的距离。

三条实践要点：正确性问题必须改协议（非 FIFO 与不可靠通道）、可行性问题可靠优化（增量与异步对齐）、拓扑变更必须与快照互斥协调（否则 cut 不完整）。
