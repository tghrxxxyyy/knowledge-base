# 持久化与断电保护

> 对应 Remzi Arpaci-Dusseau《OSTEP》持久化章节（Crash Consistency, Journaling）；Silberschatz《Database System Concepts》事务与恢复；Intel SDM 与 NVDIMM/持久内存相关规范（公开定性）。

## 一、背景与挑战

存储栈里到处都是缓存：CPU store buffer、多级缓存、SSD 的 DRAM 映射表与写缓存、磁盘写缓存、操作系统页缓存。这些缓存提升性能，却都易失——断电或崩溃时，尚未刷到持久介质的数据会消失。数据库「事务已提交」、文件 `write()` 返回成功，都不等于数据已落到 NAND/盘片。若掉电发生在错误时刻，可能出现：日志写了一半、数据页部分更新、inode 与数据块不一致。

朴素做法一是「每次都同步写」：`write` 后立刻 `fsync`/刷盘，每次提交都等介质确认。正确但极慢，尤其是 HDD 随机 fsync 可达毫秒级，OLTP 吞吐会掉几个数量级。二是「从不刷」：性能好，但崩溃后无法保证任何已确认写入存活，数据库不能接受。工程上需要一套持久化协议：用日志（WAL）把随机写变顺序刷、用屏障定义提交点、用硬件断电保护（PLP）让写缓存在掉电时仍能落地。

持久化语义（durable、fsync、O_SYNC、fdatasync、原子写）是数据库、文件系统、分布式存储面试的高频题，也是实际丢数据事故的高发区。

## 二、核心原理

**持久性（durability）**：一旦对调用者宣称「写已持久」，该写在后续崩溃/掉电后必须可恢复。边界通常定义为「fsync/barrier 返回后」。

**刷盘与屏障**：
- `write()`：通常只进页缓存（page cache），返回快但未持久。
- `fsync(fd)` / `fdatasync`：把该文件的数据与必要元数据刷到持久介质（或设备缓存且设备保证掉电安全）后返回。
- `O_SYNC`/`O_DSYNC`：每次 write 隐式刷，语义强但慢。
- `sync`/`syncfs`：全局刷。
- 存储协议层：FUA（Force Unit Access）、Flush/Barrier 命令，让设备不把数据停在易失写缓存。

**预写日志（WAL, Write-Ahead Log）**：修改数据页之前，先把「日志记录」（redo/undo）顺序写入日志区并强制持久（log flush），然后才允许覆盖数据页。崩溃恢复时重放已提交事务的日志，或撤销未提交事务。核心规则：

$$\text{Commit} \Rightarrow \text{Persist}(L) \text{ 先于 } \text{Persist}(D)$$

即日志必须先于数据持久。WAL 把随机小写合并为顺序日志写，既提高吞吐又保证原子性与持久性。

**断电保护（PLP, Power Loss Protection）**：企业级 SSD/RAID 卡带超级电容。正常时电容充电；掉电瞬间，电容能量足够把设备 DRAM 中的写缓存刷到 NAND。这样「设备缓存写回」路径也可以安全地被 fsync 依赖（设备宣称掉电安全）。消费级盘常无 PLP，fsync 必须等真实 NAND 编程。

**原子性与顺序**：单扇区/原子写指令（atomic write unit）减少「撕裂写」；日志、检查点（checkpoint）与影子分页（shadow paging）是文件系统与数据库常用模式。分布式系统还涉及 quorum 复制与跨副本确认（如 Raft log、Ceph PG）。

**不变量**：
1. 任何对调用者可见的「持久成功」都必须对应介质上的完整记录（或 PLP 保护的缓存）。
2. 日志记录在数据页之前到达持久域。
3. 恢复算法幂等：重放/回滚可重复执行。
4. 元数据（inode、目录、映射）与数据的持久顺序要一致（否则出现文件大小已更新但数据块还是旧值）。

## 三、形式化与数学基础

**崩溃一致性状态**：设数据状态为 $D$，日志为 $L$，合法持久状态集合 $\mathcal{S}$。崩溃恢复函数 $R$ 必须满足：

$$\forall t,\ R(\text{state}(t)) \in \mathcal{S}$$

即任何崩溃点恢复后都落在一致状态（原子性）。WAL 通过「先持久 $L$ 再改 $D$」保证：若 $L$ 未持久则事务未提交可丢弃；若 $L$ 已持久则恢复时重放到 $D$。

**提交延迟模型**：同步提交一次事务需要至少一次顺序日志刷：

$$T_{commit} \approx T_{log\_append} + T_{flush}$$

其中 $T_{flush}$ 对 HDD 可达 1–10ms，对 SATA SSD 数百微秒，对带 PLP 的 NVMe 可到数十微秒。若每事务都 fsync，吞吐上界 $ \approx 1/T_{flush}$。组提交（group commit）把 $n$ 个事务合并一次 flush：

$$T_{commit}' \approx \frac{T_{flush}}{n} + T_{queue}$$

**fsync 的持久条件**（简化）：

$$\text{fsync 返回} \Rightarrow \text{Data} \in \text{PersistentDomain} \lor \text{Data} \in \text{PLPCache}$$

其中 PLPCache 表示设备保证掉电后可回写。若设备不守信（谎称缓存安全），就会丢数据——这是「掉电保护」硬件的意义。

**WAL 写放大与检查点**：设事务平均日志长度 $l$、数据页更新 $p$、检查点间隔 $C$，则持久写流量约：

$$W \approx T_x \cdot l + \frac{T_x \cdot p}{C}$$

检查点间隔 $C$ 越大，恢复时间越长、日志空间越大；越小则额外刷数据页越勤。典型权衡：恢复时间目标 RTO 决定 $C$。

## 四、代码实现

下面演示 WAL 的提交/恢复语义：先写日志并 `flush`（模拟持久化），再改数据；崩溃模拟后用日志重放，保证已提交事务不丢、未提交不生效。

```python
"""WAL 持久化与崩溃恢复模拟"""
import io


class WALStore:
    def __init__(self):
        self.data = {}          # 模拟数据页
        self.log = []           # 日志记录（已持久部分）
        self.log_disk = io.StringIO()  # 模拟日志持久介质
        self.commited = set()

    def _persist_log(self, record: str):
        """顺序追加日志并强制持久（等价 fsync 日志区）"""
        self.log_disk.write(record + "\n")
        self.log_disk.flush()
        self.log.append(record)

    def commit(self, txid: int, updates: dict):
        # 1) 先写 redo 日志并持久
        rec = f"BEGIN {txid}\n" + "".join(
            f"SET {k}={v}\n" for k, v in updates.items()
        ) + f"COMMIT {txid}"
        self._persist_log(rec)
        # 2) 日志已持久，才允许改数据（可稍后 checkpoint）
        self.data.update(updates)
        self.commited.add(txid)

    def crash_after_log(self, txid: int, updates: dict):
        """崩溃发生在日志已持久、数据未改之前"""
        rec = f"BEGIN {txid}\n" + "".join(
            f"SET {k}={v}\n" for k, v in updates.items()
        ) + f"COMMIT {txid}"
        self._persist_log(rec)
        # 崩溃：数据未更新
        return "crash_before_data"

    def recover(self):
        """重放日志中已提交事务（幂等）"""
        text = self.log_disk.getvalue().splitlines()
        pending = {}
        committed = {}
        tx = None
        for line in text:
            if line.startswith("BEGIN"):
                tx = line.split()[1]
                pending[tx] = {}
            elif line.startswith("SET") and tx:
                k, v = line.split()[1].split("=")
                pending[tx][k] = v
            elif line.startswith("COMMIT"):
                committed[line.split()[1]] = pending[tx]
                tx = None
        for t, upd in committed.items():
            self.data.update(upd)
            self.commited.add(t)
        return sorted(committed)

    def read_log_disk(self):
        return self.log_disk.getvalue()


if __name__ == "__main__":
    s = WALStore()
    s.commit(1, {"balance_a": "90", "balance_b": "110"})
    print("after commit1 data =", s.data)

    # 事务2：日志已持久但数据未改时崩溃
    s.crash_after_log(2, {"balance_a": "40", "balance_b": "160"})
    print("crash: data =", s.data, "（应仍是事务1后的值）")

    # 恢复：重放已提交日志
    recovered = s.recover()
    print("recovered tx =", recovered, "data =", s.data)
    assert s.data["balance_a"] == "40"
    assert s.data["balance_b"] == "160"
    print("WAL recovery OK: 已提交事务不丢，未提交未半吊子生效")
```

运行结果：事务 1 提交后数据已更新；事务 2 崩溃时数据仍为旧值；恢复后重放日志，事务 2 的更新生效。这正是 WAL 的正确性：日志先持久，恢复可重放。

## 五、与其他技术对比

| 维度 | 每次 fsync | WAL+组提交 | 带 PLP 的写缓存 | 无任何刷盘 |
|------|-----------|------------|-----------------|-----------|
| 崩溃安全 | 强 | 强（日志持久） | 强（设备级） | 无 |
| 性能 | 差 | 好 | 好 | 最快 |
| 硬件依赖 | 介质即可 | 介质即可 | 电容/超级电容 | — |
| 典型 | 简单日志文件 | 数据库、文件系统 | 企业 SSD、RAID | 缓存/可丢失数据 |

取舍：WAL 用顺序日志换随机写安全；PLP 用硬件成本换设备缓存安全；fsync 是软件必须正确使用的接口。分布式再叠加复制与 quorum，把「单机持久」扩展为「多副本持久」。

## 六、常见误区

1. **「write 返回了数据就安全」**——错。write 通常只进页缓存，掉电即丢；必须 fsync/fdatasync 或 O_SYNC，并确认设备缓存掉电安全。
2. **「有 SSD 写缓存就一定持久」**——错。消费级 SSD 的 DRAM/易失缓存掉电会丢；需要 PLP 或禁用写缓存（hdparm -W0）或依赖 FUA/Flush。
3. **「日志写了就等于数据写了」**——WAL 只保证「日志先持久」，数据页可稍后 checkpoint；恢复依赖重放。若不重放或日志被截断，仍会丢数据。
4. **「fdatasync 比 fsync 弱到可忽略」**——fdatasync 只刷数据与必要元数据（如文件大小），通常更快；但若改了与数据无关的元数据（时间戳），语义有差异，选错会导致恢复不完整。
5. **「数据库提交一次就是一次盘写」**——组提交、缓存、复制延迟都会让「逻辑提交」与「物理持久」解耦；需要理解 commit 路径上的 flush 点。

## 八、面试题

**1. 为什么需要 fsync？**
答：write 只把数据放进页缓存，掉电会丢。fsync 强制把数据（及必要元数据）刷到持久介质或 PLP 保护的设备缓存，fsync 返回后崩溃仍可恢复，满足持久性。

**2. PLP（掉电保护）的作用是什么？**
答：超级电容在掉电时为设备 DRAM 写缓存供电，把未落盘的数据刷到 NAND，使设备写缓存路径也能被当作持久，既保性能又保安全。

**3. WAL 的核心规则是什么？**
答：修改数据页之前，必须先把对应的日志记录顺序写入并强制持久。崩溃恢复时重放已提交事务的日志、撤销未提交事务，保证原子性与持久性。

**4. 组提交为什么能提升吞吐？**
答：把多个事务的 log flush 合并为一次持久化，摊薄 $T_{flush}$；在 fsync 很慢的介质上吞吐近似提升 $n$ 倍，代价是单事务延迟略增。

## 九、演进与趋势

持久内存（NVDIMM、CXL Type-3）提供字节可寻址持久域，`clwb`/`sfence` 与 PMDK（libpmemobj）把「持久化」变成编程模型一等公民，WAL 可更轻量（如每事务 8B 原子标志）。原子写指令与「幂等 DMA」减少撕裂。分布式存储用 quorum、链式复制与对象版本（S3、Ceph）扩展持久语义；云盘后端多副本+PLP。文件系统侧，ext4/XFS 的 data=ordered/journal、F2FS、NOVA（持久内存日志文件系统）持续演进。可观测性：blktrace、iostat 的 flush/fsync 延迟、数据库 checkpoint 指标。硬件侧，NVMe 的 FUA/Flush、ZNS 持久化边界、以及「近内存持久化」是活跃方向。

## 十、小结

持久化要求「宣称持久的数据崩溃后仍在」，手段包括 fsync/屏障、WAL 日志先行、设备 PLP 与恢复算法。fsync 保证软件侧落盘点，WAL 用顺序日志换原子与高效提交，PLP 用硬件换设备缓存安全。把持久域边界、提交点与恢复幂等想清楚，才能避免丢数据事故。
