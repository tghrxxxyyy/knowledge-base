# 分支误判代价与流水线冲刷

> 对应 Bryant & O'Hallaron《CSAPP》第 4 章（处理器体系结构）第 4.5.3 节 / Hennessy & Patterson《Computer Architecture》分支预测与 CPI 章节 / Intel 优化手册性能计数事件（`BR_MISP_RETIRED.*`）。

## 一、背景与挑战

流水线靠重叠连续指令的阶段来提升吞吐：取指、译码、重命名、发射、执行、访存、写回。条件分支的**方向**要到执行阶段才能确定，而取指必须在此前决定下一条的地址。若不做预测，前端每遇分支就要停顿到方向解析，停顿深度等于「分支解析级 − 取指级」，几十条流水线槽位被浪费。

因此现代核心一律猜。猜对零代价，猜错则已投机进入流水线的指令全部作废：前端重新取指，后端丢弃未提交结果，恢复重命名映射，把正确的指令重新走一遍。代价随「前端深度 + 恢复逻辑延迟 + 重新填充前端的时间」增长。

难点在于这是**结构的**而非局部的代价：它与流水线深度、BTB 命中、I-cache 命中、重命名恢复机制、乃至发射队列中已占用槽位的清理都相关，调优时不能只看误预测率这一个数字。

## 二、核心原理

投机执行的实现依赖乱序核心的三个构件：

1. **重排序缓冲（ROB）**：指令按程序序进入 ROB，乱序执行但按序提交。推测的结果先写入物理寄存器/存储缓冲，只有提交时才成为架构状态。
2. **重命名映射**：误预测恢复时，把映射表回退到分支处的检查点（快照或提交即释放的方案），使后续按错误路径分配的物理寄存器可回收。
3. **分支检查点**：分支解析出真实方向后，与预测方向比对。不一致时，从 ROB 中裁剪掉该分支之后的所有微操作，向取指单元发出重定向（redirect）信号。

冲刷（flush）的动作至少包括：清空 ROB 中分支之后的条目、清空发射队列中的对应条目、释放其占用的物理寄存器、恢复 RAT、清空前端已预译码的指令缓冲、以正确 PC 重新取指。代价不只是「浪费的周期数」，还包含**再次填充流水线所依赖的 I-cache、BTB、uop cache 的冷启动**。

## 三、形式化与数学基础

误预测代价近似为流水线深度与重填时间之和：

$$
C_{mispred} \approx D_{frontend} + L_{redirect} + B_{refill}
$$

$D_{frontend}$ 是前端级数（从重定向到第一条正确指令进入执行），$L_{redirect}$ 是检测与恢复逻辑的延迟，$B_{refill}$ 是重新填满发射队列所需的周期。实际处理器上这是十余到二十余周期的量级，具体数值取决于微架构，以官方优化手册为准。

对整体性能的贡献可用 CPI 分解刻画：

$$
CPI_{eff} = CPI_{base} + f_{br}\cdot(1-p)\cdot C_{mispred} + f_{ld}\cdot m\cdot C_{miss}
$$

其中 $f_{br}$ 是每指令分支数，$p$ 是预测准确率，$f_{ld}$ 是每指令加载数，$m$ 是缺失率。该式说明优化优先级：当 $f_{br}(1-p)C_{mispred}$ 与 $f_{ld}\,m\,C_{miss}$ 同阶时，两个方向都要抓。

对循环型分支，误预测只发生在循环退出的一次，摊薄后每迭代代价约为

$$
\frac{C_{mispred}}{N_{iter}} \to 0 \quad (N_{iter} \to \infty)
$$

这解释了「内层循环的分支几乎免费、而随机数据依赖分支极贵」的现象。反之，若分支方向由输入数据随机决定（如 `if (data[i] > threshold)` 且数据随机），准确率趋近 $1/2$，代价全额计入。

## 四、代码实现

```c
// 同一份代码，数据分布决定误预测率与总耗时
#include <stdio.h>
#include <stdlib.h>

/* 已排序：分支方向几乎恒定，预测器命中率高 */
static long count_sorted(const int *a, int n, int key) {
    long c = 0;
    for (int i = 0; i < n; i++)
        if (a[i] > key) c++;            /* 前段恒 false，后段恒 true */
    return c;
}

/* 随机分布：方向不可预测，每次迭代约一半概率误预测 */
static long count_random(const int *a, int n, int key) {
    long c = 0;
    for (int i = 0; i < n; i++)
        if (a[i] > key) c++;
    return c;
}

/* 无分支改写：用比较结果做算术，消除方向预测 */
static long count_branchless(const int *a, int n, int key) {
    long c = 0;
    for (int i = 0; i < n; i++)
        c += (a[i] > key);              /* 编译器通常生成 setcc/add，无跳转 */
    return c;
}
```

第三种写法把控制依赖转成数据依赖，对不可预测分支通常更稳，但对可预测分支反而多算了算术。另外注意 `c += (a[i] > key)` 会引入一条从比较到累加的依赖链，在乱序宽度不足时会限制 ILP；实际应同时观测 IPC 与误预测计数（如 `perf stat -e branch-misses,instructions`）。

## 五、与其他技术对比

| 事件 | 触发频率 | 恢复机制 | 典型代价 | 可控手段 |
| --- | --- | --- | --- | --- |
| 分支误预测 | 每几十条指令 | 前端重定向 + ROB 裁剪 | 十余到二十余周期 | 更准预测器、无分支化、PGO |
| 缓存缺失 | 每数百条指令 | 停顿等待填充 | 数十到数百周期 | 预取、分块、数据布局 |
| 异常/中断 | 极低 | 精确异常，保存现场 | 上千周期 | 批处理、向量化 |
| 内存消歧失败 | 与访存密度相关 | 重放加载 | 数周期 | 别名分析、软件预取 |

与异常恢复对比：两者都需回滚，但误预测由硬件在流水线内完成且极为频繁，异常则走微码或体系结构路径，代价高但罕见。

## 六、常见误区

- 「流水线越深越快」：深度提高频率上限，但误预测代价近似线性增长，分支密集负载可能净亏。
- 「只看误预测率」：一个 5% 误预测率的热循环若每迭代都有分支，与 1% 的冷代码相比，绝对损失可能更大。
- 「预测器准就够了」：BTB 缺失导致的取指气泡、uop cache 未命中也会造成与冲刷同量级的停顿。
- 「把所有分支都无分支化」：对高可预测分支，条件传送会引入额外依赖与寄存器压力，得不偿失。
- 「误预测只是浪费几个周期」：被冲刷的路径可能已发起投机访存，污染缓存状态（这也正是 Spectre 的基础）。

## 八、面试题

1. **误预测代价为何与流水线深度相关？** 要点：代价等于被冲刷的流水线级数加上重填时间；深度越大，进入流水线后被作废的指令越多。
2. **投机执行如何回滚？** 要点：ROB 按序提交，未提交结果不算架构状态；误预测时裁剪 ROB 中后续条目、释放物理寄存器、恢复重命名映射、重定向前端。
3. **为什么排序后的数组会让循环快很多？** 要点：分支方向变得高度局部化，2-bit 计数器或 TAGE 能稳定预测；随机数据使准确率趋近 1/2。
4. **`perf` 上如何定位误预测问题？** 要点：看 `branch-misses` 与 `branches` 之比、结合 `instructions` 算 IPC，并配合源码级采样定位具体热分支。
5. **有无办法让冲刷更便宜？** 要点：更小的检查点恢复粒度、分支检查点复用、前端解耦（取指不被后端阻塞）、提前解析分支。

## 九、演进与趋势

前端设计从「深流水线」转向「更准预测 + 更短重定向」：TAGE 类预测器把准确率推向极限，检查点（checkpoint）与快速恢复逻辑缩短重定向延迟，解耦前端让取指独立于后端停顿。同时无分支化在编译器侧被 PGO 驱动（依据剖面自动在分支与条件传送间选择），SIMD/向量化则在更粗粒度上消除分支。长期看，前端瓶颈正从「预测不准」转向「取指带宽与解码宽度」，这也是 uop cache 与融合解码存在的原因。

## 十、小结

误预测代价等于被冲刷的流水线级数加重填时间，是深流水线时代最直接也最容易被忽视的性能杠杆。优化顺序应是：先消除热点不可预测分支（算法/数据布局/无分支化），再依赖预测器与 PGO，最后才考虑微架构级的重定向优化。
