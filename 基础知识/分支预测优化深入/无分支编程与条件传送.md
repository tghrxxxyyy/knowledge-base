# 无分支编程与条件传送

> 对应 Bryant & O'Hallaron《CSAPP》第 3 章 3.6.4/3.6.5（条件传送与 `cmov`）/ Hennessy & Patterson《Computer Architecture》/ Agner Fog 微架构手册中条件传送的延迟与依赖讨论。

## 一、背景与挑战

当条件分支方向不可预测时，误预测代价（十余到二十余周期）往往远高于「把两路都算出来再选一个」的算术代价。于是编译器与手写代码都有动机消除控制依赖：用**条件传送**（conditional move）或位运算掩码把「跳或不跳」变成「选哪个值」。

x86 提供 `CMOVcc`（按标志位条件移动）与 `SETcc`（按标志位写字节），AArch64 提供 `CSEL`/`CSINC` 等条件选择，GPU 提供线程级谓词执行。它们的共同点是：**只有数据依赖，没有控制依赖**，因此不经过分支预测器，也不产生流水线冲刷。

代价是：无条件多算一路、多占一个目的寄存器，并引入「两路源都需就绪」的数据依赖结构。若分支本身高度可预测，这些额外开销就是纯浪费。

## 二、核心原理

条件传送的语义是 `dst = cond ? a : b`。硬件实现上它是一条 ALU/移动类微操作，读标志位作为 select 信号，**两路输入都必须就绪才写回**。由此产生三个特性：

- **优点**：消除分支预测风险与前端重定向，方向随机时表现稳定。
- **依赖代价**：即使 `cond` 早已确定，也必须等两路源就绪。若其中一路来自长延迟链（缓存缺失的加载），CMOV 会把该延迟拉进关键路径；分支版本则可只走真正需要的那一路。
- **副作用**：CMOV 的内存操作数**总是被读取**。因此 `x ? *p : 0` 不能安全地编译成 CMOV——即使条件为假，加载仍可能触发缺页异常，破坏 C 的短路语义。
- **寄存器压力**：两路同时活跃，活跃区间变长，可能引发更多溢出。

无分支编程的一般技巧是位运算：由比较结果生成全 0 或全 1 的掩码，再用 `and`/`or`/`xor` 组合两路。

## 三、形式化与数学基础

以 32 位无分支取最大值为例，定义掩码

$$
mask = \operatorname{sar}(a-b,\ 31)
$$

算术右移把符号位铺满：$a<b$ 时为全 1，否则为全 0。于是

$$
r = (a \mathbin{\&} \lnot mask) \mid (b \mathbin{\&} mask)
$$

当 $a<b$ 时 $mask = 0\text{xFFFFFFFF}$ 得 $r=b$，否则 $r=a$。严格说该式依赖补码减法的行为，极端溢出时符号位不可靠，健壮写法应使用比较加 `cmov`。

更一般的谓词化选择可写成

$$
r = b + (a-b)\cdot[\text{cond}], \qquad [\text{cond}] \in \{0,1\}
$$

这与 SIMD 的 `blend`/`select` 及 GPU 谓词执行同构。

何时该用可量化：设分支误预测率 $q$、误预测代价 $C_m$、两路都算的额外代价 $C_e$，则无分支化有利当且仅当

$$
q \cdot C_m > C_e
$$

由于 $C_m$ 是十余到二十余周期量级而 $C_e$ 通常只有 1~3 周期，只要 $q$ 高于约 5%~15% 就划算。这也解释了编译器为何只在剖面显示分支不可预测时才生成 CMOV。

## 四、代码实现

```c
#include <stdint.h>
#include <stdio.h>

/* 掩码版无分支最大值：算术右移把符号位铺满 */
int32_t max_mask(int32_t a, int32_t b) {
    int32_t mask = (a - b) >> 31;                 /* 负 -> 全 1 */
    return (a & ~mask) | (b & mask);
}

/* 语义清晰的形式，编译器常自行转为 cmov */
int32_t max_cmov(int32_t a, int32_t b) {
    return (a > b) ? a : b;
}

/* 无分支绝对值：INT32_MIN 的溢出属未定义行为，生产代码应用无符号技巧 */
uint32_t abs_nb(int32_t x) {
    int32_t mask = x >> 31;
    return (uint32_t)((x ^ mask) - mask);
}

/* 逐元素剪裁：向量化后整条循环无分支，生成 minss/maxss 类指令 */
void clamp_vec(const float *in, float *out, size_t n, float lo, float hi) {
    for (size_t i = 0; i < n; i++) {
        float v = in[i];
        v = v < lo ? lo : v;
        out[i] = v > hi ? hi : v;
    }
}
```

工程提示：用 `gcc -O2 -S` 观察是否真的生成 `cmov`；用 `__builtin_expect` 或 `[[likely]]` 告知编译器的分支倾向，帮助它在分支与 CMOV 间正确取舍；对指针解引用要格外小心，无分支化会引入本不存在的访存。

## 五、与其他技术对比

| 方案 | 依赖类型 | 可预测分支 | 不可预测分支 | 副作用风险 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 普通条件分支 | 控制依赖 | 最优（近零代价） | 差（冲刷） | 无（不执行不访存） | 大概率方向、冷路径 |
| CMOV / CSEL | 数据依赖 | 一般（多算一路） | 好且稳定 | 内存操作数恒被读取 | 小分支、随机方向 |
| 位运算掩码 | 数据依赖 | 一般 | 好 | 算术溢出风险 | 整数选择、饱和运算 |
| SIMD select | 数据依赖（向量级） | 不适用 | 最优（整块无分支） | 掩码加载需谨慎 | 数组、图像、信号处理 |
| GPU 谓词执行 | 数据依赖 | 不适用 | warp 内一致时好 | 无 | warp 内分支一致 |

## 六、常见误区

- 「无分支一定更快」：分支可预测时多算一路纯属浪费，还可能因寄存器压力变慢。
- 「`?:` 会短路所以安全」：C 的 `?:` 确实短路，但生成 CMOV 后**丧失短路性**，对可能失效的指针或越界下标不能依赖编译器保证。
- 「CMOV 延迟等同于普通 move」：它需两路源都就绪且读写标志位，延迟与依赖结构都不同。
- 「算术右移总能得到掩码」：C 中负数右移是实现定义行为，应使用无符号类型加显式转换或编译器内置函数保证可移植性。

## 八、面试题

1. **什么时候 CMOV 优于分支？** 要点：分支方向不可预测（误判率显著高于额外计算占比）且两路计算廉价时，依据是剖面与源码级误预测计数。
2. **无分支 max 的掩码原理？** 要点：算术右移符号位得到全 0/全 1 掩码，用 `and`/`or` 按位选择；注意减法溢出与右移实现定义问题。
3. **什么情况下无分支会更慢？** 要点：分支高度可预测、某一计算路径很长或可能触发异常、寄存器压力导致额外溢出。
4. **为什么 `x ? *p : 0` 不能安全编译成 CMOV？** 要点：CMOV 的内存操作数无条件读取，`p` 无效时会触发本不该发生的访存异常。
5. **SIMD 与标量无分支的关系？** 要点：SIMD 用掩码选择实现向量级谓词化，消除逐元素分支，前提是数据可向量化且控制流能表示为选择。

## 九、演进与趋势

硬件层长期并存两条路线：x86 靠 `CMOVcc`，ARM64 靠 `CSEL` 家族与少量真正的条件执行，GPU 靠 warp 级谓词。编译器层面，PGO 让「分支还是 CMOV」的取舍从静态启发式变成数据驱动；向量化则把无分支化提升到整块粒度。安全方向上存在反向拉扯：无分支代码会缩短投机窗口，但也可能因额外访存而扩大 gadget 面，因此推测加载加固与无分支化需要联合考虑。

## 十、小结

无分支编程把控制依赖转成数据依赖，用「多算一路」换取「消除预测风险」，在分支不可预测且计算廉价时收益显著。它的三个约束是两路源都必须就绪、内存操作数恒被读取、寄存器压力上升；是否采用应基于剖面而非直觉。
