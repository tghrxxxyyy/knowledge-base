# 租约机制原理

> 对应 Gray & Lamport 2006（The Byzantine Generals in the lease: breaking the tie with time）与 Burrows 2006（Chubby: a lock service for loosely-coupled distributed systems）。

## 一、背景与挑战

分布式系统中，资源常被多个客户端并发访问——典型如「谁是当前主节点」「谁能写某分片」。要让某客户端在一段时间内独占访问，又不能依赖全局同步时钟（不存在严格同步的全局时钟），还要避免「客户端崩溃后锁永远不释放」的死锁。分布式锁用心跳/超时维持，但网络分区下极易出现「双主」或「永久挂起」。租约（lease）用「带超时的授权」把「谁有权」转化为各节点本地可判定的超时问题，从根上规避死锁，成为缓存一致、选主与协调服务的基石。其安全性不依赖互斥算法的复杂协议，而依赖一个简单事实：时间有界。

## 二、核心原理

服务端在授予客户端一段有效期 $[t, t+T]$（从授予方时钟计）的租约，期间客户端被视为合法持有者、可独占相应权利（如写某资源、作为 primary）。客户端必须在到期前主动续租（renew）；若到期未续，服务端视租约失效，可将权利授予他人。租约的本质是把「协调权归属」问题转化为「本地超时判断」——持有方只需看自己本地时钟是否仍在区间内，无需每次操作都问服务端。授予方通过保守地设定边界（考虑时钟漂移、网络最大延迟、处理时间）保证不会在旧持有者仍自认有效时把权利发给新者。续租本身是幂等的：只要旧租约未过期，新的续租请求把 `expire` 顺延即可。租约把「互斥」从「需要共识」降级为「需要计时」，这是其优雅之处。

## 三、形式化与数学基础

设授予方时钟漂移率上界 $\rho$，网络单程最大延迟 $d$，授予租约时长 $T$，处理时间 $\epsilon$。为避免双主，安全条件要求旧持有者在最坏情况下早于新持有者生效的时间被 $T$ 覆盖：

$$ T > \frac{d}{1-\rho}+\epsilon $$

即租约时长必须超过「时钟可能超前的最大偏差 + 最大网络延迟 + 处理」。若不满足，旧持有者凭本地偏快时钟自认有效、同时新持有者已被授权，出现双主。服务端通常以比客户端超时节律更保守的边界设 $T$。续租时新租约从确认续租的时刻起重新计算 $T$，若续租请求在旧租约到期前到达则无缝延续：

$$ expire_{new} = now_{grant} + T,\quad \text{要求 } now_{grant} < expire_{old} $$

该式保证权利不会「真空」也不会「重叠」（在时钟边界内）。

## 四、代码实现

```python
class Lease:
    def __init__(self, ttl):
        self.ttl = ttl          # T
        self.owner = None
        self.expire = 0         # 授予方视角下的到期时间戳

    # 授予 / 续租：仅当旧租约已到期才放行
    def grant(self, who, now):
        if now < self.expire:
            return False        # 仍被旧持有者占据
        self.owner = who
        self.expire = now + self.ttl
        return True

# 持有方本地判断是否仍有效（用单调时钟，避免被调快）
def still_valid(start_monotonic, ttl):
    return (time.monotonic() - start_monotonic) < ttl
```

## 五、与其他技术对比

| 机制 | 崩溃安全 | 语义 | 时钟依赖 |
| --- | --- | --- | --- |
| 分布式锁（无租约） | 容易死锁 | 互斥 | 低 |
| 心跳保活 | 分区下误判 | 存活 | 中 |
| 租约（lease） | 超时自动释放，无死锁 | 限时授权 | 需保守时钟边界 |

租约不怕客户端崩溃后死锁——超时自动释放；相比心跳，它显式授权且可缓存结果、减少协调流量。相比「基于超时的互斥」，租约把「权利有效期」与「故障检测」解耦，使故障检测可更保守而不影响权利释放的及时性。Raft/Paxos 的 leader 任期本质上也是一种租约，任期号即 fencing。

## 六、常见误区

1. 认为租约永不丢失——时钟漂移/被调快可造成双主（见时钟偏移篇），需配合 fencing token。
2. 把租约时长设得过短——频繁续租引发「续租风暴」，反而增加服务端负载与故障概率。
3. 以为续租一定能成功——服务端在旧租约到期后才接受新申请，若旧者一直续，新者可能长期拿不到。
4. 混淆「租约有效」与「操作成功」——租约只管权利归属，不保证操作本身不冲突（需 fencing）。
5. 以为租约可无限续——多数系统对新持有者的公平性或租约总数设限，避免饿死。
6. 把租约当「强一致锁」——它只保证时间界内的限时授权，不替代状态机共识。

## 七、与开源书·权威来源对应

- Gray & Lamport 2006：从「用时间打破平局」角度给出租约安全性的形式化证明，是租约理论的奠基文献。
- Burrows 2006（Chubby）：把租约用作锁服务的核心——master 持租约对外服务，过期重选。
- Kleppmann《Designing Data-Intensive Applications》ch8：以缓存一致与选主为例直观讲解租约。
- Coulouris《Distributed Systems》：在故障检测与互斥章节讨论基于超时的授权。
- Vogels 2009（Eventually Consistent）：讨论租约在最终一致系统中的角色。

## 八、面试题

1. 租约相比分布式锁好在哪里？
   要点：客户端崩溃后租约超时自动释放，不会死锁；权利归属本地可判定，减少协调。
2. 时钟漂移如何破坏租约安全性？
   要点：持有方本地时钟偏快会提前自认仍有效，若服务端已授权他人则双主；需用保守 $T$ 与 fencing 防御。
3. 续租失败会发生什么？
   要点：旧租约到期后服务端可授权他人，旧持有者权利失效，需停止写并重新申请。
4. 为什么服务端要保守设 $T$？
   要点：必须覆盖最坏时钟偏差+网络延迟+处理，否则旧持有者偏快时与新持有者权利重叠。
5. 租约与共识（Raft term）有何共通？
   要点：leader 任期即一种租约，任期号单调递增充当 fencing，过期则重新选举。

## 九、演进与趋势

在云原生中，租约常与「领导者选举库」（如 etcd clientv3）绑定，应用无需自己实现超时逻辑。租约时长可随工作负载自适应：长任务用长租约，短任务用短租约。

- 把租约与分布式屏障（barrier）结合，可协调多节点阶段推进而无需中心锁。
- 多租户下需对租约总数限流，防止单一客户端占用全部授权配额造成饿死。
- 共识即租约：Raft/Paxos 的 leader 任期天然是带 fencing 的租约，任期号即防护。

现代实践把租约与 fencing token 结合（防御脑裂写），并演化为会话租约（ZooKeeper 会话超时近似租约）、层级租约（父派生子）、带 CAS 版本防重放等可组合形态；租约服务化（etcd Lease API）使授权统一管控。Serverless 场景出现「极短租约 + 自动续期」以适配弹性实例。把租约与可信执行环境（TEE）结合，可提供更紧的双主窗口。

## 十、小结

租约以时间边界换取「无死锁的独占访问」，把协调权归属转化为本地超时判断，是缓存一致、选主与分布式锁的基础。其安全性根植于「保守的时长边界 + 单调时钟 + fencing」三位一体——脱离任一层，都会埋下双主或死锁的隐患。记住：租约不是锁，而是「限时授权」。
