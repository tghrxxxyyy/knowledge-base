# 心跳与租约对比

> 对应 Gray & Lamport 2006（The Byzantine Generals in the lease）与 Coulouris《Distributed Systems: Concepts and Design》故障检测章节。

## 一、背景与挑战

心跳（heartbeat）与租约（lease）都用于表达「我还活着 / 我仍有权」，但二者语义层级不同：心跳是「存活信号」，回答「进程是否还在」；租约是「带期限的权利凭证」，回答「谁当前被授权」。把二者混为一谈是分布式设计的常见错误——仅用心跳做主从切换，旧主在网络抖动恢复后仍会写数据形成脑裂；仅用租约不做存活检测，又无法及时感知崩溃以触发切换。理解语义差异才能正确组合二者，界定「何时怀疑」与「何时权利真正失效」两个不同时间点，缺一不可。

## 二、核心原理

心跳：从节点周期性向主/协调者发送 ping（或协调者主动 probe），超时（连续若干轮无应答）即认为失联。它偏向「故障检测」，驱动「该不该切换」。租约：服务端主动授予一段有效期权利，持有方在期内独占，到期未续则权利回收。它偏向「权利界定」，驱动「谁当前合法」。二者常配合：心跳/故障检测决定「何时认为持有方失联」，租约决定「失联后权利何时真正释放」——释放发生在租约自然到期，而非检测判定的那一刻，从而保证安全窗口。即：检测判失败 ≠ 权利失效，权利失效永远由租约到期定。心跳是「软信号」，租约是「硬边界」。

## 三、形式化与数学基础

心跳检测时延上界（连续 $k$ 轮、周期 $T_{hb}$、最大延迟 $d$）：

$$ T_{detect} \le k\cdot T_{hb} + d $$

租约安全窗口 = 租约时长减去「最坏检测上界」，须为正以防止双主：

$$ T_{safe} = T_{lease} - T_{detect\_bound} > 0 $$

即租约必须长于检测上界。若 $T_{safe}\le 0$，检测已判失败但租约未到期，旧持有者仍合法，此时切换会与其并发写。注意：心跳只影响「何时怀疑」，不决定「何时权利失效」——后者永远由租约到期定。更一般地，权利失效时刻为随机量，其上界即 $grant\_time+T_{lease}$，与检测完全解耦。该不等式是安全切换的设计红线。

## 四、代码实现

```python
# 心跳：基于最后收到 ping 的时间判断是否存活
def is_alive(last_beat, now, hb_period, d_max):
    return (now - last_beat) <= (hb_period + d_max)

# 租约：基于授予时刻 + 时长判断是否仍有权
def has_right(grant_time, ttl, now):
    return now < (grant_time + ttl)
```

## 五、与其他技术对比

| 维度 | 心跳 | 租约 |
| --- | --- | --- |
| 语义 | 存活（liveness） | 授权（right） |
| 谁驱动 | 被监控方发 ping | 授权方发 grant |
| 失败后果 | 误判假死 → 误切换 | 时钟漂移 → 双主 |
| 与切换 | 触发切换意图 | 界定切换安全点 |
| 消息量 | 每周期一次 ping | 仅续租时交互 |

心跳管「死活」，租约管「权利」，二者互补而非替代。心跳频繁但只在检测层；租约稀疏但决定权利边界。把二者融合（续租即心跳）是常见简化。

## 六、常见误区

1. 仅用心跳做选主——主崩溃后旧主在网络恢复瞬间仍写数据，造成脑裂；必须等租约到期或用 fencing。
2. 租约与心跳超时设置不匹配——$T_{lease} < T_{detect}$ 时切换与合法权利重叠。
3. 以为「收到心跳 = 有权利」——存活不代表授权未过期，授权由租约定。
4. 以为「租约未到期 = 进程健康」——租约只管时间，不反映进程是否真能服务。
5. 忽略 fencing——即便 $T_{safe}>0$，时钟偏移仍可能击穿，fencing 是最后防线。
6. 以为心跳失败即立即切换——切换需等租约到期或 fencing 生效，否则违反安全窗口。
7. 忽略监控指标割裂——存活（心跳）与授权（租约）常由不同面板观测，排障时需关联二者时间戳。
8. 以为二者可互相替代——心跳发现故障快但无授权语义，租约界定权利但感知慢，必须配合使用。

## 八、面试题

1. 为什么光用心跳不能安全做主从切换？
   要点：心跳只判死活，不界定权利失效时刻；旧主在恢复瞬间仍可能写，需租约到期或 fencing 兜底。
2. 租约与心跳如何配合才安全？
   要点：检测判失联后，等租约自然到期再切换（$T_{lease}>T_{detect}$），或配合 fencing 立即切换。
3. $T_{safe}\le 0$ 会怎样？
   要点：检测已判失败但租约未到期，新旧主权利重叠，出现双主/脑裂写。
4. 收到心跳能否证明仍有权？
   要点：不能，存活与授权是两个维度；授权由租约到期界定，心跳只说明进程应答。
5. 续租为何可同时充当心跳？
   要点：续租周期性发生，失败即暴露失联，天然兼具存活检测与权利延续。
6. 监控中如何关联心跳与租约？
   要点：二者时间戳需对齐，存活丢失但租约未到期时系统应进入「等待切换」而非立即动作。

## 九、演进与趋势

在 Kubernetes 等编排系统中，租约（Lease 对象）与心跳（节点状态上报）并存：心跳供调度感知，租约供控制面互斥。把「续租即心跳」统一后，控制面消息量显著下降。

- 多副本服务的健康探针（readiness/liveness）本质是轻量心跳，需与租约边界对齐。
- 边缘/弱网场景优先用心跳快速感知，再用租约兜底权利，避免频繁切换。
- 共识层把心跳与任期合并：leader 心跳即租约续期，任期号充当全局 fencing。

用租约替代长连接保活，降低控制面消息量；把心跳下沉为「租约续租」本身（续租即心跳），统一存活与授权信号；会话租约（ZK）把二者融合为单一超时语义。Raft 中心跳（leader 维持权威）即兼具「存活+租约续期」双重角色，任期号天然 fencing。基于 gossip 的故障检测与租约结合，在大规模集群更省带宽。

## 十、小结

心跳管「死活」，租约管「权利」，二者互补而非替代。安全切换的不等式 $T_{lease}>T_{detect}$ 把故障检测与权利释放缝合成一体——脱离对方孤立设计任一方，都会埋下脑裂或误杀的隐患。牢记：检测决定「何时怀疑」，租约决定「何时权利真正失效」，这是两个必须区分且联动的时间点。
