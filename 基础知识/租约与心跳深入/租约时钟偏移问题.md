# 租约时钟偏移问题

> 对应 Gray & Lamport 2006（The Byzantine Generals in the lease: breaking the tie with time）与 Lamport 1978（Time, Clocks, and the Ordering of Events in a Distributed System）。

## 一、背景与挑战

租约的安全性建立在「持有方本地时钟不会比授予方超前太多」这一假设上。但真实节点的时钟并非完美同步：NTP 步进调整、人为 `date` 修改、虚拟机迁移暂停后时钟跳变、甚至时钟芯片漂移，都会让持有方认为「租约还有效」而实际授予方已过期并把权利给了别人。这种「双写」（stale write）是租约最隐蔽的破坏方式——它不依赖网络分区，仅靠时钟偏移即可发生，且难以被常规监控发现。时钟偏移因此被视为租约部署的头号风险。

## 二、核心原理

租约有效期由授予方时间定义（如 `expire = grant_time + T`），但持有方用本地时钟判断自己是否仍有效（`now_local < expire_local`）。若持有方时钟被调快 $\delta$，它在授予方视角已过期时仍自认有效，继续写数据，与新持有者形成双写。缓解手段有三层：(1) 用单调时钟（monotonic clock，不受 wall-clock 步进影响）给租约计时，避免被 `ntpdate` 跳变击穿；(2) 限制最大可容忍漂移、用保守 $T$ 覆盖最坏偏差；(3) 引入 fencing token——每次授权递增一个令牌，存储层只接受「令牌大于已见最大令牌」的写，使陈旧持有者的写被拒绝。三层中 fencing 是最后、也最可靠的防线，它把安全性从「时间」升级为「单调序号」，不依赖任何时钟假设。

## 三、形式化与数学基础

设双方时钟偏差上界为 $\delta$（持有方可比授予方早/晚最多 $\delta$），最大网络延迟 $d_{max}$，处理 $\epsilon$。最坏情况下持有方比授予方「早认为有效」的时间即 $\delta$。安全条件变为：

$$ T_{lease} > \delta + d_{max} + \epsilon $$

若 $T_{lease}$ 不覆盖 $\delta$，则存在窗口：授予方已视租约过期并授权他人，持有方仍凭偏快时钟自认有效。fencing token 进一步把安全性从「时间」转为「单调序号」：设授予序号 $t$，陈旧持有者持 $t' < t$，存储层维护已接受最大序号 $t_{max}$，仅当 $t > t_{max}$ 才接受写：

$$ accept(write, t) \iff t > t_{max};\quad t_{max}\leftarrow\max(t_{max}, t) $$

注意 fencing 不依赖时钟，因此可彻底消除时钟偏移导致的双写——这正是它作为「最终防线」的价值。即使 $\delta\to\infty$，fencing 仍保证正确性。

## 四、代码实现

```python
import time

# 用单调时钟计时，避免 wall-clock 被调快击穿
_start = time.monotonic()
def still_valid(elapsed_since_start, ttl):
    return (time.monotonic() - _start) < ttl

# 存储层用 fencing token 拒绝陈旧写
class Store:
    def __init__(self): self.max_token = 0
    def write(self, data, token):
        if token <= self.max_token:
            raise StaleWrite("token 不新，拒绝陈旧写")
        self.max_token = token
        self.apply(data)
```

## 五、与其他技术对比

| 计时方式 | 抗步进 | 表达超时 | 用于租约 |
| --- | --- | --- | --- |
| wall-clock（墙上时钟） | 否 | 是 | 危险，被调快击穿 |
| monotonic clock | 是 | 是（相对） | 推荐 |
| 逻辑时钟（Lamport） | 是 | 否 | 不能直接表达超时 |
| HLC（混合逻辑时钟） | 是 | 是（近似真实时间） | 新兴 |

逻辑时钟不测真实时间，无法直接表达「超时」；NTP 仍可能有 step，需配合 fencing。HLC 兼顾顺序与真实时间边界，是跨地域租约的去 NTP 严格同步方向。单调时钟解决「被调快」，但不解决「两台机器起点不同」的绝对偏差，仍需保守 $T$ 或 fencing。

## 六、常见误区

1. 用 wall-clock 判断租约，被 `ntpdate`/人工调快跳变击穿——必须用单调时钟。
2. 认为 fencing token 可完全替代租约时长设计——fencing 是最后防线，但租约时长仍决定不可用的上界与切换频率。
3. 以为时钟「大致同步」就安全——长尾漂移 + 大 $T$ 的保守不足，仍会偶发双写。
4. 混淆「本地有效」与「全局有效」——本地判有效不代表他人已视其失效。
5. 以为 fencing token 全局唯一即可——需在存储层持久化 `max_token`，否则重启后失效，陈旧写可重入。
6. 忽略虚拟机/容器暂停恢复——暂停期间 wall-clock 可能大幅跳变，单调时钟也可能被宿主机调整。

## 七、与开源书·权威来源对应

- Gray & Lamport 2006：证明租约安全性依赖时钟偏差上界，给出双主窗口的形式化分析。

- Vogels 2009：讨论时钟偏差在最终一致系统中的现实影响。

## 八、面试题

1. 时钟被调快如何破坏租约？
   要点：持有方凭偏快时钟自认有效、继续写，而授予方已过期并授权他人 → 双写。
2. 为什么还需要 fencing token？
   要点：时间边界总有最坏偏差，fencing 用单调序号让存储层拒绝陈旧写，彻底消除双写。
3. 单调时钟解决了什么、没解决什么？
   要点：解决 wall-clock 步进击穿；但不解决「两台机器单调时钟起点不同」的绝对偏差，仍需保守 $T$ 或 fencing。
4. fencing token 为何要持久化？
   要点：重启后 `max_token` 归零会让陈旧持有者写的旧 token 又被接受，失去防护意义。
5. HLC 相比单调时钟好在哪？
   要点：HLC 兼顾事件顺序与近似真实时间边界，适合跨地域无需严格 NTP 的租约。

## 九、演进与趋势

混合逻辑时钟（HLC）在无需严格 NTP 的跨地域部署中提供近似真实时间边界，正被广泛采用。把 fencing token 与一致性快照结合，可同时防御双写与读旧数据。

- 虚拟机迁移的时钟暂停需由监控代理显式上报，触发租约主动失效而非靠超时。
- 可信时间源（如 PTP/PTM）降低时钟偏差上界 $\delta$，允许更紧的租约边界。
- 把单调计时放入 TEE，使租约有效期不被宿主机或 hypervisor 篡改，收紧双主窗口。

混合逻辑时钟（HLC）兼顾「事件顺序」与「真实时间边界」，使跨地域租约可不依赖 NTP 严格同步；fencing token 服务化（如 etcd 的 `lease_id` + `revision`）成为标准防护；可信执行环境（TEE）提供受保护单调计时，进一步收紧双主窗口。Raft 的 `term` 与 `log index` 组合即一种分布式 fencing，天然抵御时钟偏移。把时钟监控纳入 SLO 告警，可提前发现漂移风险。

## 十、小结

租约依赖时间边界，而时钟偏移（尤其墙钟被调快）是其最隐蔽的破坏源。稳健方案需「单调时钟计时 + 保守时长覆盖最坏偏差 + fencing token 兜底」三重保障——其中 fencing 把安全性从「时间」升级为「单调序号」，是防御双写的最终防线，不依赖任何时钟假设。记住：fencing 是底线，永远不要只靠时钟。
