# 租约的演进与趋势

> 对应 Gray & Lamport 2006（The Byzantine Generals in the lease）与 Hunt et al. 2010（ZooKeeper: wait-free coordination for Internet-scale systems, USENIX ATC）。

## 一、背景与挑战

经典租约解决「单资源、单持有者」的限时独占，适用于选主、缓存一致等场景。但云原生与大规模系统提出更精细的诉求：跨地域多服务共享授权、父权利撤销需级联回收子权利、写冲突需防重放、控制面需降低保活消息量。简单超时授权已不够，催生了可组合、带防护、服务化的租约形态。租约从「一个超时令牌」演化为一套授权原语集，以应对复杂的协调与容错需求。

## 二、核心原理

现代租约演化为一组可组合原语：(1) 会话租约（ZooKeeper 会话超时近似租约）——客户端与协调者建立会话，会话内所有临时节点/锁随会话失效自动清理；(2) fencing token——每次授权递增序号，存储层只接受更新序号的写，挡住陈旧持有者；(3) 层级租约（父派生子）——父租约约束子租约有效期 $T_c\le T_p$，撤销父即级联回收全部子权利；(4) 带 CAS/版本的租约——用条件写（compare-and-set）防重放与并发覆盖。这些形态把「限时授权」升级为「可组合、带证明的授权」。租约不再是孤立机制，而是与共识、会话、层级命名空间深度集成。

## 三、形式化与数学基础

层级租约中，父租约有效期 $T_p$ 约束子租约：

$$ \forall\,c:\ T_c \le T_p $$

保证撤销父租约可级联回收全部子权利（子必先于父过期）。fencing token 的单调序号 $t$ 使存储层只接受严格递增写：

$$ accept(w,t)\iff t>t_{max};\quad t_{max}\leftarrow\max(t_{max},t) $$

带 CAS 的租约把「续租」建模为条件更新：仅当 `lease.version == expected` 时写入新 `expire`，拒绝并发覆盖与重放。会话租约等价于「隐式层级」——会话是父，其下临时资源是子，会话失效即级联清理。层级正确性可形式化为：若父在时刻 $t$ 失效，则所有 $T_c\le T_p$ 的子必在 $t$ 前已过期，无残留。

## 四、代码实现

```python
# fencing token 防御陈旧写
class GuardedStore:
    def __init__(self): self.max_token = 0
    def write(self, data, token, last_token):
        if token <= self.max_token:
            raise StaleWrite("陈旧持有者，拒绝")
        self.max_token = token
        self.apply(data)

# 层级租约：子租约不得超过父
def grant_child(parent_expire, child_ttl, now):
    child_expire = now + child_ttl
    if child_expire > parent_expire:
        raise ValueError("子租约不可超过父")
    return child_expire
```

## 五、与其他技术对比

| 形态 | 解决的问题 | 代价 |
| --- | --- | --- |
| 原生租约 | 单资源独占 | 双主风险（需 fencing） |
| 会话租约 | 临时资源自动清理 | 需维持会话心跳 |
| 层级租约 | 级联回收 | 父失效波及子 |
| fencing 租约 | 防陈旧写 | 存储层需校验 |

对比原生锁：fencing 解决「锁释放后陈旧持有者写」；对比心跳保活：会话租约更省消息。每种形态解决一类具体问题，生产中常组合使用——例如「会话租约 + fencing + 层级」三层叠加。

## 六、常见误区

1. 以为有 lease 就不需要 fencing——时钟偏移/脑裂仍可致双写，fencing 是必需防线。
2. 层级租约撤销未级联——只撤父不校验子，子权利残留造成越权。
3. 把租约时长设得过长求省心——故障切换与不一致窗口被拉长。
4. 以为 fencing token 全局唯一即可——需在存储层持久化 `max_token`，否则重启后失效。
5. 把会话租约当永久锁——会话超时即失效，不能假设「拿到就一直有」。
6. 忽略 CAS 续租的并发——多客户端同时续租需版本校验，否则互相覆盖。

## 八、面试题

1. fencing token 为什么比单纯租约更稳？
   要点：租约依赖时间边界（有漂移风险），fencing 用单调序号让存储层拒绝陈旧写，彻底防双写。
2. 层级租约撤销为何必须级联？
   要点：父失效时子若仍有效，会残留越权；要求 $T_c\le T_p$ 保证子必先过期。
3. 会话租约与心跳的关系？
   要点：续租即心跳，会话超时（近似租约）触发临时资源清理，统一存活与授权。
4. CAS 续租防什么？
   要点：防并发覆盖与重放，确保只有当前持有者能顺延租约。
5. 为什么云原生需要组合租约？
   要点：跨地域、多服务、层级资源需级联回收与防护，单一超时授权不够。

## 九、演进与趋势

服务网格（service mesh）把租约用于连接级授权，sidecar 间用短租约限权，降低横向移动风险。共识即租约：Raft/Paxos 的 leader 任期天然是带 fencing 的租约。

- 机密计算（TEE）提供抗篡改单调计时，收紧双主窗口至微秒级。
- 层级租约与 K8s 资源树结合，权限随资源删除自动级联回收，无需手动撤销。
- 多租户下需对租约总数限流，防止单一客户端占用全部授权配额。

租约服务化（etcd Lease API、Consul Session）使任意系统复用统一授权；与共识（Raft/Paxos）深度结合，租约成为「leader 任期（term/epoch）」的天然体现；可信执行环境提供抗篡改单调计时，进一步收紧双主窗口；Serverless 场景下出现「极短租约 + 自动续期」以适配弹性实例。层级租约与命名空间（如 K8s）结合，使权限回收随资源树自动传播。

## 十、小结

租约从「简单超时授权」演进为「可组合、带防护、服务化」的授权原语：会话租约管生命周期、fencing 管防双写、层级租约管级联回收、CAS 管防重放。理解这些形态，才能在云原生系统中正确、安全地使用租约——记住：现代租约从不单打独斗，而是以「层级+防护+会话」的组合出现。
