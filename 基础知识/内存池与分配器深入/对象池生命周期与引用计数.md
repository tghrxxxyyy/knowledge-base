# 对象池生命周期与引用计数

> 对应 Silberschatz《Operating System Concepts》与 Tanenbaum《Modern Operating Systems》。

## 一、背景与挑战
池化对象被多处共享时，需明确何时可回收，过早释放导致悬空、过晚释放导致泄漏。引用计数提供自动确定生命周期的手段。

## 二、核心原理
每个池对象带引用计数，获取时增一、释放时减一，归零即归还对象池（或真正释放）。原子计数保证并发正确。结合对象池，回收不再依赖全局 GC，而是即时确定。

## 三、形式化与数学基础
计数 $C \ge 0$。操作：

$$ \text{get}: C \gets C+1 $$
$$ \text{put}: C \gets C-1;\ \text{if } C=0 \text{ then recycle} $$

不变量：

$$ C = \text{当前持有引用数} $$

归零意味无活跃引用，可安全回收。

## 四、代码实现
带计数的池对象：

```c
typedef struct {
    int refcount;
    void *data;
    node_t node;          // 挂入对象池自由链表
} pooled_t;

void obj_get(pooled_t *o) {
    __atomic_add_fetch(&o->refcount, 1, __ATOMIC_ACQ_REL);
}
void obj_put(pooled_t *o) {
    if (__atomic_sub_fetch(&o->refcount, 1, __ATOMIC_ACQ_REL) == 0)
        pool_free(o);     // 归还对象池
}
```

## 五、与其他技术对比
手动 free 易错；GC 自动但有停顿；引用计数即时但无法处理循环引用（需弱引用或 GC 兜底）；对象池+计数组合在小对象高频场景高效。

## 六、常见误区
认为引用计数解决循环引用，实际需弱引用或定期扫描；忽略原子操作性能；在中断上下文用可能睡眠的回收路径。

## 七、与开源书/权威来源对应
Silberschatz 讨论引用计数与 GC；Tanenbaum 对比分配策略；Linux kref 是内核引用计数实现。

## 八、面试题
引用计数如何决定回收；循环引用问题；为何需原子；与 GC 区别。

## 九、演进与趋势
kref/refcount_t 在内核标准化；用户态使用 hazard pointers 替代部分 RCU/计数场景。

## 十、小结
对象池配合引用计数可在无 GC 的环境下即时、确定地回收共享对象，代价是需正确处理计数与循环引用。
