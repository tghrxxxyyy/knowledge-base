# 重排序缓冲ROB

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》乱序提交与精确异常章（第 3 章）与 CSAPP 第 4 章。

## 一、背景与挑战
乱序执行能提升 ILP，但程序语义要求「对外可见的状态变化按程序序发生」，否则异常（如除零、缺页）会发生在错误的上下文，且并发线程会看到乱序的中间状态。重排序缓冲（ROB, Reorder Buffer）记录已发射未提交指令，按程序序「提交（retire）」其结果到架构状态，从而实现「乱序执行、按序提交」，并支持精确异常（precise exception）。

没有 ROB，乱序执行会破坏「精确异常」这一基本要求：发生异常时，处理器必须能回到「异常指令处、其之前全完成、之后全未生效」的状态，否则恢复后的程序行为错误。ROB 正是实现这一点的硬件结构。

ROB 还承担「恢复锚点」的角色：误预测或异常发生时，需要知道「哪些指令已合法提交、哪些必须丢弃」。ROB 头指针即「架构状态边界」，头指针与误预测指令之间的所有项都是必须丢弃的推测结果。没有这个边界信息，硬件无法判断回滚到哪里。

## 二、核心原理
指令译码后入 ROB 尾部，携带 PC、目标架构寄存器/内存地址、分配到的物理寄存器、完成标记、异常标记。执行完在 ROB 内标记 done；ROB 头部（最老）连续完成的指令按序提交：写回 ARF 或提交 store 到内存（经 store buffer）。遇到异常时，丢弃异常点之后所有指令并恢复映射，使处理器状态仿佛「在异常指令处精确停止」。

ROB 还承担「顺序内存提交」：store 在提交前只进入 store buffer，提交时才真正写内存，保证其他核看到的内存写入顺序与程序序一致，这是 TSO（total store order）内存模型的基础。

提交逻辑的一条重要规则是「头部阻塞」：只有 ROB 头部那一条（或前若干条）完成后才能提交，即使后面的指令已经完成也不能越过。因此一条长延迟指令停在头部会阻塞整个提交过程，但由于其后的指令仍可继续乱序执行，这一阻塞通常不会立即影响吞吐——它只是延后了「对外的可见性」。

ROB 项的字段设计也体现了「精确异常」的需求：项中必须有「异常标记」与「异常码」，而不是在执行时就抛异常。原因是在推测路径上抛异常是错误的（该路径可能被丢弃），必须延后到提交点才真正触发。这一「延迟异常」的设计是精确异常的关键机制。

## 三、形式化与数学基础
提交宽度 $R$，窗口大小 $S$（ROB 项数），指令在窗内平均延迟 $L$。可重叠执行的指令数约 $S/L$，则：
$$IPC \approx \min\left(R,\; \frac{S}{L}\right)$$
ROB 大小 $S$ 决定可探索的 ILP 窗口：过小则后续指令无法早入窗、限制调度；过大则恢复延迟与面积上升。精确异常要求：提交点之前的所有指令效果已生效、之后全无，ROB 头部位置即「架构状态边界」。误预测时从头部到误预测点之间的指令全部丢弃，恢复 RAT/FreeList 到检查点。

Little 定律给出了 ROB 大小的直观解释：若平均指令延迟为 $L$ 个周期、希望维持 $IPC = I$，则在途指令数需满足
$$ S \ge I \cdot L $$
例如希望 IPC 达到 4 且平均延迟（含访存与功能单元）为 20 周期，则 ROB 至少需约 80 项；考虑长尾（cache miss 数百周期）后，实际设计普遍取 200 项以上。

误预测恢复成本也可由 ROB 大小刻画：误预测点位于 ROB 尾部附近时，需丢弃约 $S$ 条指令的推测状态，恢复代价约与 $S$ 成正比。这与「大 ROB 提升性能但放大误预测惩罚」的经典权衡完全一致。

## 四、代码实现
```c
// 循环 ROB：按序提交
struct rob_e { int pc; int dst; int phys; int done; int exc; };
struct rob_e rob[192]; int head, tail;
void retire() {
    while (rob[head].done && !rob[head].exc) {
        commit(rob[head].dst, rob[head].phys);   // 按序提交到 ARF
        head = (head + 1) % 192;
    }
    if (rob[head].exc) {
        flush_after(head);    // 丢弃异常点之后所有指令，恢复映射
    }
}
// store 提交：经 store buffer 按序写内存
void commit_store(rob_e *e) {
    if (e->is_store) store_buffer_write(e->addr, e->data);
}
```

「延迟异常」的实现方式：

```c
/* 执行阶段只记录异常码，不立即触发，避免污染推测路径 */
void execute_and_mark(int idx) {
    rob[idx].done = 1;
    rob[idx].exc  = detected_exception();   // 仅标记，不抛
}
/* 只有提交到头部时才真正进入异常处理 */
void retire_check(int idx) {
    if (rob[head].exc) handle_exception(rob[head].exc);
}
```

## 五、与其他技术对比
| 维度 | ROB + 按序提交 | 纯 Tomasulo（无 ROB） | store buffer | 顺序流水线 |
| --- | --- | --- | --- | --- |
| 提交约束 | 按程序序 | 无 | 推测存储排队 | 按序 |
| 精确异常 | 支持 | 不支持 | 配合 ROB | 天然 |
| 内存可见 | 提交时 | 立即 | 提交时 | 立即 |
| 恢复难度 | 中（需检查点） | 无法恢复 | 低 | 无需恢复 |
| 结构复杂度 | 高 | 中 | 低 | 低 |
ROB 与 store buffer 配合：store 在提交前只入 store buffer，提交时才真正写内存，保证「乱序执行、按序可见」。

需要区分 ROB 与 store buffer 的职责：ROB 管「指令级」的按序提交与异常精确；store buffer 管「访存级」的暂存与转发（load 若命中 store buffer 中的较新 store，可直接转发，无需等其提交）。二者配合才能同时实现「精确异常」与「内存顺序」。

## 六、常见误区
1. 误以为乱序执行即乱序可见。提交才生效，提交前仅内部状态变化。
2. 误以为 ROB 越大越好。面积、唤醒/提交逻辑延迟随项数上升，恢复更慢。
3. 混淆「完成」与「提交」。done 仅表示执行完，提交需头部连续 done 才行。
4. 以为异常只来自算术。缺页、写保护、断点等都可能触发，ROB 必须能统一处理。
5. 以为 ROB 头部阻塞会立即拖慢吞吐。其后指令仍可乱序执行，阻塞只延后可见性，直到 ROB 被填满才真正停摆。
6. 以为异常可以在执行时立即抛出。推测路径上的异常必须延迟到提交，否则会误报。
7. 忽略「提交时才能写内存」对性能的影响。这使 store 的对外可见被延后，但换来正确性，是 TSO 的核心。

## 八、面试题
1. ROB 如何实现精确异常？
   要点：仅提交到异常点之前的指令，异常点之后全部丢弃并恢复映射。
2. ROB 大小如何影响性能？
   要点：窗口越大可探索 ILP 越多，但面积/恢复延迟上升。
3. store 何时真正写内存？
   要点：指令提交时，经 store buffer 按序写，保证内存可见顺序。
4. ROB 与 store buffer 如何配合保证内存语义？
   要点：store 提交前只在 buffer，提交时按序写，对外可见顺序=程序序（TSO）。
5. 为什么异常要延迟到提交才触发？
   要点：推测路径上的异常可能是「假异常」，立即触发会错误中断程序。
6. ROB 大小与 IPC 的定量关系？
   要点：由 Little 定律 $S \ge IPC \times L$，窗口必须覆盖平均延迟乘以目标 IPC。

## 九、演进与趋势
大 ROB（200+ 项）配合分支预测恢复检查点；与重命名映射检查点协同缩短误预测惩罚；store buffer 与 ROB 解耦提升访存并行；非阻塞提交（speculative retire）在研究中。现代高性能核的 ROB 已达数百项，是单线程性能的关键资源。

另一趋势是「异构 ROB」：把访存类指令与算术类指令的提交路径部分解耦，使长延迟 load 不长时间占住提交口。也有研究探索把 ROB 与调度队列合并（统一结构）以省面积，但需解决唤醒与提交的时序耦合问题。

## 十、小结
ROB 是乱序处理器正确性的守门人：用「顺序提交」把性能（乱序执行）与正确性（按序可见、精确异常）统一起来。其大小与恢复机制直接决定可探索的 ILP 窗口与误预测惩罚，也是内存一致性模型的硬件支撑。记住「提交才可见」「异常延迟到提交」「头部阻塞不等于吞吐停摆」这三条，就掌握了 ROB 的行为要点。
