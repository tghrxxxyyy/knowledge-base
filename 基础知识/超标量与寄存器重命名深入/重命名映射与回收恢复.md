# 重命名映射与回收恢复

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》寄存器重命名与推测恢复章（第 3 章）与 Intel P6/ARM 微架构。

## 一、背景与挑战
分支误预测、异常或中断时，处理器必须撤销推测执行，把架构寄存器映射表（RAT）与空闲物理寄存器表（FreeList）恢复到某个一致状态。若恢复慢，误预测惩罚（pipeline flush 深度）增大；若映射表与 FreeList 不一致，会出现物理寄存器泄漏（越来越少可用）或被错误复用（数据损坏）。恢复机制是乱序处理器鲁棒性的核心。

现代 CPU 每周期重命名多条指令、推测执行上百条，任何一次误预测都要精确撤销所有这些状态。恢复的正确性直接决定程序是否会在并发/异常下产生错误结果，是「正确性」而非「性能」问题。

恢复机制的设计还受「恢复频率」影响：分支密度高的代码（如解析器、解释器中常见的 switch/间接跳转）误预测率可能达百分之几，若每次恢复都要重建整张映射表，性能损失会非常显著。因此恢复速度与恢复频率共同决定了检查点机制的收益。

## 二、核心原理
三类主流恢复技术：
1. 检查点（checkpoint）：分支/推测点时快照整张映射表与 FreeList，误预测时直接恢复最近检查点。恢复快，但占存储（多份副本）。
2. 未来文件（future file / architectural recovery）：按程序序提交时逐步建立可恢复态，误预测时从已提交态重建。省存储但恢复慢。
3. 提交回收（retire/commit）：指令按序提交时把旧物理寄存器归还 FreeList，活跃推测态随之收缩。
现代多用「检查点 + 提交回收」混合：用检查点加速误预测恢复，用提交回收常态释放物理寄存器。检查点常只打在分支指令处，且环形缓冲有限个，避免存储爆炸。

检查点环形缓冲的工程语义：硬件维护 $C$ 个检查点槽（如 4~8 个），分支被重命名时占用一个槽；当槽用尽，最老的分支不再打检查点（其后的误预测需从 ROB 头部重建）。这与「分支密集中检查点不够用」的性能问题直接相关，是微架构调参的常见权衡点。

另一个易被忽视的细节：恢复不仅涉及 RAT 与 FreeList，还涉及「分支预测器状态」（如全局历史寄存器、RAS 栈指针）。误预测时这些也必须回退，否则后续预测会基于错误的（未来路径的）历史，产生「预测器污染」，导致误预测率在恢复后一段时间内异常升高。

## 三、形式化与数学基础
恢复延迟由检查点间隔决定。设分支在 ROB 位置 $k$，每 $c$ 条指令建一个检查点（环形缓冲 NCP 个），最坏恢复需回退到上一个检查点并重建中间映射：
$$RecoverDelay \le c \times IssueWidth$$
FreeList 的不变式：其包含的空闲物理寄存器 = 全部物理寄存器 − 所有「未提交且已分配」的物理寄存器。误预测恢复时必须把「推测分配出去、尚未提交」的物理寄存器全部归还，否则会泄漏。映射表（RAT）记录「架构寄存器 → 最新物理寄存器」，恢复时须回退到检查点处的 RAT 快照，使后续重取指令重映射到正确物理寄存器。

FreeList 不变式可写成守恒式：设 $P$ 为物理寄存器总数、$\text{Alloc}_{spec}$ 为未提交已分配数、$\text{Alloc}_{arch}$ 为当前架构态占用数，则
$$ |\text{FreeList}| = P - \text{Alloc}_{spec} - \text{Alloc}_{arch} $$
恢复到检查点 $cp$ 时，$\text{Alloc}_{spec}$ 应回退为检查点记录的值，多出的部分（本次推测新分配的）必须全部归还 FreeList。任何一侧（RAT 或 FreeList）回退不完整，都会破坏该守恒式。

误预测惩罚的近似模型：若检查点间隔为 $c$ 条指令、误预测率为 $m$，则平均每指令的惩罚约
$$ \text{Penalty} \approx m \cdot (c \cdot \text{IssueWidth} + \text{RefetchLatency}) $$
降低 $c$（更密检查点）可减小惩罚但增加存储与端口压力，这是典型的「面积换性能」权衡点。

## 四、代码实现
```c
// 分支时打检查点，误预测时恢复
void checkpoint(int cp) {
    save_map[cp]  = copy_map(arch_map);     // 快照映射表
    save_free[cp] = copy_free(free_list);   // 快照空闲表
}
void recover(int cp) {
    arch_map  = save_map[cp];                // 恢复架构->物理映射
    free_list = save_free[cp];              // 恢复空闲表（含所有推测分配项）
    fp = free_list_head;
    // 此后被误预测的指令重取，物理寄存器不再泄漏
}
// 提交回收：常态归还旧物理寄存器
void commit(int dst_arch, int phys) {
    free_list[fp++] = arch_map[dst_arch];   // 旧物理寄存器归还
    arch_map[dst_arch] = phys;              // 新映射生效
}
```

还需一并恢复分支预测器状态，否则会「预测器污染」：

```c
void recover_predictor(int cp) {
    ghr = save_ghr[cp];          // 全局历史寄存器回退
    ras_sp = save_ras_sp[cp];    // 返回地址栈指针回退
    // 部分实现还需回退局部分支历史表、ITTAGE 等相关状态
}
```

## 五、与其他技术对比
| 维度 | 检查点 | 未来文件 | 提交回收 | 混合 |
| --- | --- | --- | --- | --- |
| 恢复速度 | 快 | 慢 | 持续 | 快 |
| 存储开销 | 高（多副本） | 低 | 低 | 中 |
| 适用 | 误预测 | 提交点 | 常态释放 | 主流 |
| 恢复粒度 | 最近检查点 | 已提交态 | 逐条 | 检查点+逐条 |
| 硬件复杂度 | 中（多份 RAT） | 低 | 低 | 高 |

未来文件的思路是「维护一份总是正确的架构态副本」：提交时同步更新该副本，误预测时直接把它复制回工作 RAT，无需检查点。它省去多份快照，但每次恢复要复制整张表，恢复慢、且对高频误预测不友好。RISC 与 CISC 的主流实现最终都选了「少量检查点 + 提交回收」。

## 六、常见误区
1. 误以为只有提交才回收物理寄存器。提交确实回收，但误预测时若只恢复 map 不恢复 FreeList，会泄漏物理寄存器。
2. 以为 FreeList 含已分配项。FreeList 只含空闲物理寄存器，已分配的在映射表中。
3. 检查点过密。每指令都打检查点存储爆炸，需按策略（关键分支）稀疏化。
4. 以为恢复只是清 ROB。还需同步映射表、FreeList、与分支预测器状态。
5. 以为误预测恢复可以「懒着做」。不恢复会导致后续指令读到推测值或被错误映射，是可复现的数据损坏。
6. 忽略异常路径的恢复。异常（缺页、除零）也需精确恢复，机制与分支误预测共享但触发点不同。
7. 以为检查点只需存 RAT。FreeList 的状态同样必须快照，否则回收时机错乱。

## 八、面试题
1. 为何误预测要同时恢复 map 和 FreeList？
   要点：二者必须一致，否则物理寄存器泄漏或被误复用、数据损坏。
2. 检查点恢复与提交回收如何配合？
   要点：检查点加速误预测恢复，提交回收常态归还物理寄存器。
3. FreeList 不变式是什么？
   要点：空闲项 = 全部物理寄存器 − 未提交已分配项 − 架构态占用项。
4. 为何检查点不能每条指令都打？
   要点：存储随检查点数量线性增长，需稀疏化（如仅分支处）控制开销。
5. 为什么还要恢复分支预测器状态？
   要点：否则后续预测基于错误路径的历史，造成预测器污染、误预测率升高。
6. 异常与分支误预测的恢复有何异同？
   要点：机制相似（都需要回退到一致态），但异常是「精确点」恢复而非「丢弃推测路径」，语义上保留异常前的全部效果。

## 九、演进与趋势
影子映射（shadow map）减少检查点存储；混合检查点（仅关键分支打点）降低开销；与 ROB 提交协同的「渐进回收」提升吞吐；物理寄存器堆容量成为宽发射设计的关键参数。ARM/Intel 均用「检查点 + 提交回收」混合方案，检查点环形缓冲大小是微架构调参重点。

新方向包括：把检查点做成「增量快照」（只记录与前一检查点的差异）以进一步省面积；以及在 SMT 下按线程独立维护检查点，避免线程间干扰。

## 十、小结
映射与回收是推测执行的「撤销机制」：检查点提供快恢复、提交回收常态释放物理寄存器。二者一致性直接决定误预测惩罚与寄存器安全，是乱序处理器鲁棒性的核心，任何不一致都会引发难以复现的数据损坏。牢记 FreeList 守恒式与「预测器状态也要回退」这两条，是把恢复做对的关键。
