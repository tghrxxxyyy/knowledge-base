# 寄存器重命名原理

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》寄存器重命名章（第 3 章）与 Bryant & O'Hallaron《CSAPP》。

## 一、背景与挑战
程序二进制只有有限架构寄存器（x86 整数 16 个、ARM 32 个、浮点更多）。这造成两类「伪相关」：写后写（WAW，两条写同一架构寄存器）与读后写（WAR，读旧值却被新写覆盖）。它们并非真正的数据依赖，却因共用同一个架构名而强制串行，限制 ILP。寄存器重命名把架构寄存器映射到更大的物理寄存器堆（PRF，常 100+ 项），消除伪相关，仅保留真相关（RAW）。

这是现代乱序执行能发挥并行度的前提：没有重命名，一段「先写 r1、再读 r1、再写 r1」的代码会因名字冲突被强制串行；重命名后三次操作可绑定到不同物理寄存器并行推进（在安全前提下）。

需要强调「名字」与「值」的分离：架构寄存器是给程序员看的名字，物理寄存器是承载值的容器。重命名的本质是一次「改名（renaming）」，把复用同一名字的不同值分派到不同容器，从而让硬件的相关判定只依赖数据流而非名字复用。这一视角也解释了为什么 SMT（同时多线程）需要重命名：多个线程的架构寄存器名字相同，必须靠各自映射表隔离，否则会互相污染。

## 二、核心原理
维护架构寄存器文件（ARF）到物理寄存器（PRF）的映射表（RAT）。每条写指令分配一个新物理寄存器，读指令绑定当前映射的物理源。指令执行完在 ROB 内标记完成，按序提交时把新映射写入 ARF、把旧物理寄存器归还 FreeList。回滚（误预测）时恢复映射表（见回收恢复文档）。这样两条写同一架构寄存器的指令可写到不同物理寄存器，并行执行。

注意分配时机：现代实现常在「重命名/分发」时分配物理寄存器并记录「旧物理寄存器」，提交时再归还旧寄存器，使推测执行期间物理寄存器可被安全占用，回滚时由检查点统一回收。

一次重命名的完整流程可拆成四步：读源（查 RAT 把架构源映射为物理源，若源正在被上一条指令写则改绑其目标物理号）→ 分配目标物理寄存器 → 更新 RAT（写目标架构寄存器的新映射）→ 记录旧映射（供提交时归还）。注意「源映射」有一种优化：若源正是同周期前面某指令的目标，可直接转发其新分配物理号，避免读 RAT 中尚未更新的旧映射，这就是同一周期内依赖链不被打断的关键（「同周期转发」/ bypass）。

对于 x0/零寄存器这类恒零寄存器，通常不参与重命名（无目标可写），硬件可省下该项。条件码/标志位寄存器（x86 EFLAGS）的处理也需专门设计：现代实现把标志位拆成若干微架构寄存器（如 CF/OF/ZF/SF）分别重命名，否则标志位会成为重命名瓶颈。

## 三、形式化与数学基础
设物理寄存器数 $P$，架构寄存器数 $A$。可消除的伪相关上界受两者与 ROB 窗口约束：
$$Independent = \min(P - A,\; ROB_{size})$$
当 $P$ 足够大，WAW/WAR 不再阻塞，仅 RAW（真相关，由数据流决定）约束并行。重命名也可消除「写后读（RAW 的良性重叠）」对架构名的争用，使循环展开、软件流水更易发挥 ILP。真相关 RAW 不受重命名影响，因为程序语义要求「读必须见到最新写」——这是数据流决定的硬约束。

从图论角度看，重命名把「依赖图」从「名字相关图」细化为「值相关图」：原图中凡共用架构名的节点两两有边（含伪边），重命名后仅保留真实数据流边。设原图边数为 $E_{name}$、真相关边数为 $E_{true}$，则可并行空间从 $E_{true}$ 决定，与 $A$ 无关。

物理寄存器数的下界可由「在途指令数」估算：若窗口内有 $W$ 条指令、其中约 $r$ 比例产生目标，则在各目标寄存器同时存活期间至少需 $rW$ 个物理寄存器，再加架构寄存器对应的一份「当前值」共 $A$ 个，故经验上取 $P \gtrsim A + rW$，才能避免重命名因 FreeList 空而停塞。这也是宽窗口处理器 PRF 动辄 200+ 项的原因。

## 四、代码实现
```c
// 重命名映射表与自由表（简化）
int map[32];            // 架构 -> 物理
int free_list[128]; int fp = 128;
int alloc_phys() { return free_list[--fp]; }   // 取空闲物理寄存器（空则停塞）

void rename(int dst_arch, int *new_p) {
    *new_p = alloc_phys();                      // 仅为目标分配新物理寄存器
}
void commit(int dst_arch, int phys) {
    free_list[fp++] = map[dst_arch];            // 旧物理寄存器归还
    map[dst_arch]  = phys;                      // 新映射生效（写 ARF）
}
```

注意上述简化版在提交时才归还旧寄存器，推测执行期间旧物理寄存器一直被占用——这保证了「误预测回滚时仍能找回旧值」。真实实现还需维护「旧映射」的检查点，见重命名回收恢复文档。

源操作数的映射读取示意：

```c
// 读源：查表得到物理源；若上一条指令刚写该架构寄存器则直接转发其目标
int read_src(int arch) {
    return map[arch];       // 当前最新物理寄存器号（含同周期转发后的结果）
}
```

## 五、与其他技术对比
| 维度 | Tomasulo（RS 内嵌） | 物理寄存器堆 PRF | 编译器分配 |
| --- | --- | --- | --- |
| 操作数存储 | 在保留站 | 集中 PRF | 静态 |
| 面积 | 较大（多份拷贝） | 省（单份） | — |
| 唤醒 | 标签广播 | 同一机制 | — |
| 时机 | 运行时 | 运行时 | 编译期 |
| 推测支持 | 需额外机制 | 天然（配合检查点） | 无 |
| 伪相关消除 | 隐式 | 显式映射表 | 静态改名 |
现代实现多用 PRF：结果写入统一堆，保留站只存「物理寄存器号 + 就绪位」，省面积。

编译器侧的「寄存器分配」与硬件重命名目标一致（解同名冲突），但前者是静态且必须在编译期确定、受 ABI 约束；后者是动态的，且能覆盖分支预测带来的推测路径。二者并不互斥：编译器多做展开/分配可减少重命名压力，而硬件重命名弥补编译器无法预知的运行时行为。

## 六、常见误区
1. 误以为重命名消除所有相关。只消除 WAW/WAR 伪相关，RAW 真相关仍在、约束并行。
2. 误以为架构寄存器数决定并行度。决定上限的是物理寄存器数、ROB 窗口与真相关数据流。
3. 以为 FreeList 大小无所谓。物理寄存器不足会 stall 重命名，成为吞吐瓶颈。
4. 以为重命名只影响整数寄存器。浮点/向量寄存器的重命名同样重要，且 PRF 常分整数/浮点两个堆。
5. 以为重命名会改变程序语义。它只改「值存放位置」，提交后的架构状态与顺序执行完全一致。
6. 以为映射表无需检查点。误预测必须回滚，否则后续指令会读到推测值（需配合检查点/未来文件）。
7. 忽略标志位/条件码的重命名瓶颈。若只把 EFLAGS 当一个整体寄存器，标志位写会串行化大量指令。

## 八、面试题
1. WAW 与 WAR 为何是伪相关？
   要点：仅因共用有限架构名，重命名到不同物理寄存器后可并行。
2. 重命名能消除 RAW 吗？为什么？
   要点：不能，RAW 是真数据依赖，由程序语义决定，必须等待。
3. 物理寄存器不足会怎样？
   要点：FreeList 空，重命名停塞，前端停滞直到提交回收。
4. 重命名与编译器寄存器分配的关系？
   要点：二者解耦同名冲突的思路相同，编译器是静态、硬件重命名是动态且覆盖推测执行。
5. 为什么需要「旧映射」记录？
   要点：提交时须归还旧物理寄存器、误预测时须回退映射，二者都依赖历史映射信息。
6. 条件码如何重命名？
   要点：拆分为多个微架构标志寄存器分别重命名，减少标志位造成的串行。
7. 重命名宽度为何不是越宽越好？
   要点：映射表读写端口、FreeList 分配逻辑、转发网络复杂度随宽度平方级上升。

## 九、演进与趋势
重命名与 ROB/FreeList 协同支持推测恢复（checkpoint）；物理寄存器堆容量、重命名宽度成为设计参数；与 SMT（同时多线程）结合时每线程共享 PRF 需更精细分配；寄存器堆读端口数也成瓶颈（每周期需读多个源）。Apple/Intel 的宽核把 PRF 做到 200+ 项。

进一步趋势包括：更激进的「同周期转发网络」以缩短重命名到发射的延迟；把物理寄存器堆做成多体（banked）以支持更多读端口；以及在 SMT 下按线程配额划分 PRF，防止单线程耗尽资源导致另一线程饿死。

## 十、小结
寄存器重命名通过「架构名 → 物理寄存器」解耦，把 ILP 从有限架构寄存器数量的枷锁中解放出来，仅保留真相关约束。它是现代乱序超标量处理器发挥并行度的基石技术，与 ROB、FreeList、检查点共同构成推测执行的正确性骨架。理解重命名，就理解了乱序执行「为什么能快、又为什么不会错」的核心。
