# 指令选择树覆盖

> 对应 Aho, Sethi & Ullman《Compilers: Principles, Techniques, and Tools》第 8 章（代码生成 / 树覆盖）。

## 一、背景与挑战

编译器后端要把与机器无关的 IR（如表达式树）映射到目标指令序列。一条 CISC 指令常等价于多步 RTL 操作——例如 x86 的 `lea rax, [rbx+rcx*4+8]` 同时做了加法、移位与基址偏移，等价于三条 RISC 指令。如何以「最少、最快」的指令覆盖 IR 树，是指令选择（instruction selection）的核心。覆盖得不好会生成冗余指令，覆盖得过贪可能违反寄存器约束或触发隐藏的副作用。

这一阶段处于「类型/语义已确定、寄存器尚未分配」的中间位置，因此有两点硬约束：其一，指令选择必须在寄存器分配之前完成，但选出的瓦片会反过来决定寄存器压力，两种决策相互耦合；其二，IR 中的内存访问带有别名与副作用，覆盖时不能把它们当作纯函数算子随意重排，否则会破坏程序的可见行为。

## 二、核心原理

把 IR 表示为树，把每条目标指令建模为带代价的「瓦片（tile）」——一段可覆盖树局部的模式。动态规划在树上做最优覆盖：对每个节点计算「被各瓦片覆盖」的最小代价，自底向上选出全局最优瓦片集合。复杂寻址模式（如 x86 的 `[base+index*scale+disp]`）作为大瓦片可一次覆盖多层 IR，显著减少指令数。最终覆盖即一组瓦片根，其并集等于整棵树。关键：代价表必须反映真实成本，而非简单「指令数最少」。

算法分两个阶段。第一阶段是标注（labeling），自底向上为每个节点记录「覆盖以它为根的子树的最小代价及其所选瓦片」；第二阶段是发射（covering），自顶向下依据已记录的瓦片展开，递归处理每个瓦片的子节点。两阶段划分的好处是标注只需一次线性遍历（配合模式匹配），发射阶段不再做代价比较，因而总开销可控。当存在「一条瓦片覆盖整棵大树」与「多条小瓦片拼接」两种方案时，DP 会精确比较两者代价并选优——这正是贪心无法保证而 DP 能保证的地方。

## 三、形式化与数学基础

节点 $n$ 的最小代价：

$$C(n) = \min_{tile\ t\ covers\ n} \left( cost(t) + \sum_{c\in children(t)} C(c) \right)$$

覆盖为瓦片根的集合，使总代价 $\sum cost(t)$ 最小。这是经典的最优子结构问题，时间复杂度 $O(|nodes| \times |tiles|)$。注意 $cost(t)$ 未必等于指令数——某些 CISC 指令单条慢于多条 RISC，代价表需反映真实延迟/面积。完美覆盖还需满足寄存器约束：瓦片要求的寄存器类必须可分配。

最优子结构的成立依赖一个前提：瓦片的覆盖边界必须与子树的根对齐。若允许瓦片「跨过」节点边界（如把一个节点的子树上提、另一个下移），则子问题不再独立，DP 的正确性失效。这正是树覆盖相对通用图重写的本质局限。此外，代价模型可写成加权和 $cost(t) = \alpha \cdot latency(t) + \beta \cdot size(t) + \gamma \cdot regs(t)$，通过调节 $\alpha,\beta,\gamma$ 适配不同的优化目标（速度优先或体积优先）；若目标函数含「寄存器压力」这类非线性项，则它不再可分解，DP 只能近似求解，工程上多采用「先按延迟/体积选，再在分配阶段修正」。

## 四、代码实现

```python
def label(n, tiles_by_op, memo):
    # 自底向上标注：每个节点被各瓦片覆盖的最小代价
    if n in memo:
        return memo[n]
    best_cost, best_tile = INF, None
    for tile in tiles_by_op.get(n.op, []):
        if not tile.matches(n):          # 模式匹配：形状与类型都要对上
            continue
        child_cost = 0
        for slot, c in zip(tile.children, n.children):
            child_cost += label(c, tiles_by_op, memo)
            if child_cost >= best_cost:  # 剪枝：已不优则无需继续
                break
        c_total = tile.cost + child_cost
        if c_total < best_cost:
            best_cost, best_tile = c_total, tile
    memo[n] = (best_cost, best_tile)
    return best_cost

def cover(n, memo):
    # 依据标注结果自顶向下发射瓦片对应的指令
    _, tile = memo[n]
    emit(tile.code, operands_of(n))
    for c in tile.children_of(n):
        cover(c, memo)

# 代价示例：复杂寻址瓦片比「add+shift+add」组合更优
TILE_COST = {"ADD": 1, "SHIFT": 1, "LEA_COMPLEX": 1, "MOV": 1, "LOAD": 4}
# 说明：LOAD 代价设为 4 体现「访问内存远贵于寄存器运算」，
# 若按指令数计为 1，优化器会倾向于多生成 load 而少做寄存器复用
```

`label` 中的剪枝与 `memo` 都是工程必需：剪枝避免在明显不优的分支上继续递归，`memo` 保证每个节点只标注一次（否则公共子树会被重复计算，退化为指数复杂度）。

## 五、与其他技术对比

| 方法 | 适用 | 最优性 | 灵活度 | 编译时延 |
| --- | --- | --- | --- | --- |
| 树覆盖 + DP | 表达式树 | 局部最优可证 | 中 | 低 |
| DAG 覆盖 | 含公共子表达式 | 更优 | 中 | 中 |
| PEG/规则重写（LLVM） | 任意模式 | 难证最优 | 高 | 中 |
| 贪心最大匹配 | 简单 IR | 无保证 | 低 | 最低 |
| 超优化（superopt） | 基本块级 | 依赖搜索范围 | 极高 | 高 |

树覆盖适合纯表达式；DAG 覆盖处理公共子表达式更优（避免重复覆盖同一子表达式）；LLVM 的 SelectionDAG 用表驱动模式匹配，更灵活但难以证明全局最优，需配合后续窥孔优化。贪心最大匹配实现最简单，但当大瓦片的收益会被周围代价抵消时就会选错，因此工业实现几乎都采用 DP 或规则重写。

## 六、常见误区

1. 贪心选最大瓦片未必全局最优：大瓦片可能抬高周围代价，DP 才是正解。
2. 忽略瓦片代价差异：某些 CISC 指令慢于多条 RISC，按「指令数最少」选会错。
3. 漏掉约束（寄存器类/早期裁剪）：覆盖出的指令可能无法分配寄存器，导致后续 spill。
4. 把内存操作当普通节点：load/store 有别名与副作用，需单独建模，否则覆盖破坏内存序。
5. 认为覆盖越细越安全：过细覆盖产生大量 MOV，寄存器压力上升，反而更慢。
6. 忘记 memo 化导致重复标注：公共子树会被反复计算，小图也会指数级变慢。
7. 忽略类型合法化：某些目标指令要求特定类型或需要插入转换节点，未合法化就匹配会生成非法代码。
8. 认为代价表一劳永逸：不同微架构的最优代价不同，需按目标 CPU 分别标定。

## 七、与开源书·权威来源对应

- Aho 等《Compilers》第 8 章给出树覆盖与动态规划算法（原称「代码生成器生成器」思路），并证明最优子结构。
- Appel《Modern Compiler Implementation》第 9 章用类似 DP 讲解指令选择，配合 DAG 化。
- Muchnick《Advanced Compiler Design and Implementation》系统讨论指令选择与模式匹配的实现细节。
- LLVM 后端 SelectionDAG / GlobalISel 是工业级实现参考，展示模式表与类型合法化。

## 八、面试题

1. 问：指令选择为何用树覆盖？动态规划作用？
   答：IR 表达式天然成树，瓦片覆盖有最优子结构，DP 可对每个节点算最小代价，保证整树代价最小。
2. 问：复杂寻址模式为什么作为大瓦片？
   答：一次覆盖多层 IR（加法+移位+基址），减少指令数与寄存器压力，但代价表要反映其真实成本。
3. 问：树覆盖能否处理公共子表达式？
   答：纯树不能（会重复覆盖），需先转 DAG 或在后端 CSE 阶段处理，否则同一子表达式生成多份。
4. 问：为何代价表不能只用指令数？
   答：不同指令延迟/吞吐不同，微架构上「一条慢指令」可能不如「两条快指令」，代价须贴近硬件。
5. 问：为什么最优子结构在树覆盖里成立？
   答：瓦片边界与子树根对齐，使每个子树的代价独立可加；若允许瓦片跨越边界，子问题耦合，DP 即失效。
6. 问：标注阶段为何需要 memo 化？
   答：公共子树会被多个父节点引用，不记忆化则同一子问题重复求解，复杂度从线性退化为指数。

## 九、演进与趋势

MLIR 用声明式重写规则表达指令选择，把模式与代价解耦；GlobalISel 在更粗粒度并行降低编译时延；基于 ML 的代价建模开始替代手写代价表，据实测吞吐选覆盖。后端正从「手写模式表」走向「数据驱动选择」。

同时，指令选择与调度、寄存器分配的边界正在变得模糊：部分新架构支持「选择时即考虑发射槽与寄存器类」的联合优化，用更大搜索空间换取更优代码；代价是编译时间上升，因此多用于 JIT 或热点函数的离线编译路径。具体行为以各编译器官方最新文档为准。

## 十、小结

指令选择本质是带代价的最优树覆盖：把机器无关的 IR 映射到最少且最快的目标指令集合。DP 保证了「局部最优→全局最优」的可证性，而代价表的准确性决定了覆盖是否真的快——这是编译器后端从「能跑」到「跑得快」的关卡。选错代价表，再聪明的覆盖也会生成慢代码。

记忆框架：输入是树、武器是瓦片、准则是代价、方法是自底向上 DP、产物是覆盖集。理解这五个要素，就能把指令选择与其他后端问题（调度、分配）清晰区分开。
