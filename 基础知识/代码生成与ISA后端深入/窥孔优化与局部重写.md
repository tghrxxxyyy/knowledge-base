# 窥孔优化与局部重写

> 对应 Aho, Sethi & Ullman《Compilers》第 8 章；Appel《Modern Compiler Implementation》第 8 章。

## 一、背景与挑战

即便经过前面的各阶段优化，相邻指令序列仍常残留冗余：连续 load 同一地址、乘 2 可改移位、`jmp L1; L1: jmp L2` 的跳转链、无用的 `add 0` 等。这些冗余在高层 IR 看不见——只有落到目标指令层才暴露。窥孔优化（peephole optimization）在一个滑动小窗口（数条相邻指令）上做等价重写，是代码发射前的最后打磨，专门吃掉这类「低垂果实」。

难点在于「等价」二字的代价。机器指令不是纯函数：它们会隐式改写标志位（x86 的 NZCV）、可能触发异常或段错误、可能与其他指令共享寄存器别名。因此一条在代数上显然的化简（`x+0 → x`）在机器层也可能不合法——若后续指令依赖 `add` 产生的标志位，删掉它就改变了程序行为。窥孔规则的正确性门槛，比它的实现难度高得多。

## 二、核心原理

窥孔优化在滑动窗口上应用等价重写规则：消去死 store、合并常量、折叠跳转链（`jmp L1; L1: jmp L2 → jmp L2`）、代数化简（`x+0→x`、`x*2→x<<1`）、强度削减。规则保持语义，可多趟迭代直至到达不动点（fixpoint）。它通常在目标指令层进行，因此能捕获高层 IR 看不到的机器相关冗余（如标志位、寻址模式、特定指令对的组合）。

规则集通常按「模式长度」组织：单指令规则（自搬移 `mov a,a`、`add 0`）、双指令规则（跳转链、load 后立即 store 同一地址、比较后紧跟条件跳转）、三指令及以上规则（连续地址的 load-store 合并为块拷贝）。窗口大小一般取 2–5 条指令，窗口越大可表达的规则越多，但匹配成本与规则数量组合爆炸也越严重，因此工业实现多在「表驱动 + 有限长度」之间取平衡。

## 三、形式化与数学基础

重写系统对指令序列 $s$ 应用规则 $r: pattern \to replacement$，保持语义等价：

$$\forall s.\ sem(s) = sem(apply(r,s))$$

迭代得到不动点 $s^* = fixpoint(\{r_i\})(s_0)$，且因每条规则不增长度（或替换后不再触发反向规则），有 $|s^*| \le |s_0|$。正确性前提是规则保持可观测行为与异常/标志位语义。形式化上，重写系统是终止的（无长度增长的规则保证停机）。

严格来说，终止性来自一个良基度量（well-founded measure）：若每条规则都使序列长度严格减小，或使某种「字典序度量」（如指令总长度、再按指令序号）严格下降，则系统必停机，且抵达的不动点唯一性由「无反向规则」保证。若规则集中同时含 `x*2 → x<<1` 与 `x<<1 → x*2`，系统就会在两个形态间振荡而永不停机——这是设计规则集时必须排除的循环。另一个常被忽视的前提是「异常顺序」：若被删除的指令可能抛异常（如除零、空指针解引用），则删除会改变可观测行为，因此此类指令必须被视为有副作用而不可消除。

## 四、代码实现

```python
def peephole(insns, max_rounds=100):
    changed = True
    rounds = 0
    while changed and rounds < max_rounds:   # 迭代至不动点（含上限保护）
        changed = False
        rounds += 1
        i = 0
        while i < len(insns) - 1:
            a = insns[i]
            b = insns[i+1]
            # 前提：a 写入的标志位未被后续指令使用（has_live_flags 检查）
            if a.op == 'add' and a.imm == 0 and not has_live_flags(a):
                del insns[i]; changed = True     # x + 0 消去
            elif a.op == 'jmp' and b.label == a.target:
                a.target = b.target; changed = True   # 跳转链折叠
            elif a.op == 'mul' and a.imm == 2 and a.unsigned:
                a.op, a.imm = 'shl', 1; changed = True  # 强度削减（须无符号）
            elif a.op == 'mov' and a.src == a.dst:
                del insns[i]; changed = True     # 自搬移消去
            elif a.op == 'load' and b.op == 'load' and a.addr == b.addr:
                b.op, b.args = 'mov', [a.dst]    # 复用已加载值
                changed = True
            i += 1
    return insns
```

三处守卫值得注意：`has_live_flags` 保证删除 `add` 不会破坏标志位消费者；`a.unsigned` 保证强度削减在有符号溢出语义下安全（有符号 `x*2` 溢出是未定义/陷入行为，与 `shl` 不同）；`max_rounds` 防止规则集意外含循环时无限迭代——把「理论上必然停机」变成「实践上一定停机」的工程保险。

## 五、与其他技术对比

| 优化 | 范围 | 典型收益 | 是否需数据流分析 | 风险 |
| --- | --- | --- | --- | --- |
| 窥孔 | 局部相邻指令 | 消除冗余、强度削减 | 否（局部即可） | 低（规则受控） |
| 全局 CSE/DCE | 跨基本块 | 去公共子表达式、死代码 | 是 | 中 |
| 循环优化 | 循环层 | 提升迭代吞吐 | 是（含依赖分析） | 高 |
| 指令调度 | 基本块/全局 | 隐藏延迟、提升发射率 | 是 | 中 |
| 寄存器分配 | 全函数 | 决定最终指令数与溢出 | 是 | 高 |

窥孔是局部、廉价的收尾优化；全局 CSE/DCE 处理跨块，二者互补，常在代码发射前做最后清理。窥孔的优势是「不需要数据流分析」，规则匹配即可，因此成本低、易验证；但它也因此无法发现跨块的等价性，例如同一地址在两个分支中各自 load 一次。

## 六、常见误区

1. 规则不保持语义（如忽略标志位副作用 `add` 改写 ZF）致错误：须用未使用的标志或 `lea` 替代。
2. 单趟不够：改写后可能暴露新匹配，需迭代至不动点。
3. 在含不可达假设处折叠破坏异常语义：如把可能抛异常指令移过可见副作用。
4. 盲目强度削减：`x*2` 改 `shl` 在溢出行为上与有符号乘法未必等价，需类型保证无溢出。
5. 把窥孔当万能优化：它只处理局部模式，跨块冗余必须靠全局 pass。
6. 规则集含循环导致不收敛：如同时存在 `x*2 → x<<1` 与 `x<<1 → x*2`，必须在设计时排除。
7. 忘记删除影响标签或跳转目标：删掉某条指令后，指向它的标签/跳转必须同步修正，否则生成悬空跳转。
8. 在寄存器分配前做机器相关窥孔：此时物理寄存器尚未确定，部分模式无法匹配，通常需在分配后再做一轮。

## 八、面试题

1. 问：窥孔优化常见规则？为何需迭代？
   答：常见有代数化简、跳转链折叠、强度削减、死 store 消去；改写后可能暴露新匹配，需迭代到不动点才稳定。
2. 问：与全局优化区别？
   答：窥孔只看局部相邻窗口、规则简单、开销低；全局优化需数据流/控制流分析，覆盖跨块冗余。
3. 问：如何保证窥孔不破坏语义？
   答：规则必须保持可观测行为与标志位/异常语义，必要时用不影响标志的指令形式（如用 lea 替代 add）。
4. 问：为什么窥孔放在后端而非中端？
   答：很多冗余（标志、寻址模式、指令对）只有落到目标指令才可见，中端 IR 无法表达。
5. 问：重写系统为什么一定停机？
   答：需存在良基度量（如序列长度）在每次重写后严格下降；若规则集含反向规则则可能振荡，须在设计时排除。
6. 问：强度削减 `x*2 → x<<1` 什么时候不合法？
   答：有符号乘法溢出时行为与移位不同，若类型不能保证无溢出则不可替换。

## 九、演进与趋势

基于模式匹配的表驱动窥孔、结合 MLIR 重写引擎把规则声明与执行解耦；后端用 target 描述自动生成窥孔规则，减少手写错误。近年还把窥孔与指令选择融合，在 SelectionDAG 阶段就做 combine，减少发射后再扫一遍的成本。

另一趋势是把窥孔往「可验证」方向推进：将规则与形式化语义一起给出，用 SMT 求解器自动证明替换的等价性，从而把规则正确性从人工审查变为机器检查。这类方法能显著降低「规则写错导致静默错误代码」的风险，代价是规则表达能力受限。具体工具与能力以各项目官方最新文档为准。

## 十、小结

窥孔优化以小窗口等价重写做最后打磨，稳健地消除邻近冗余指令。它不追求大跨度优化，却以极低风险吃掉发射前残留的低垂果实——是「正确性优先」的局部改写艺术的典型代表。一个成熟的编译器后端，往往在窥孔 pass 里藏着大量针对特定微架构的精雕细琢。

三条实践准则：规则宁少勿错（一条错误规则可能污染全部输出）、迭代设上限（防止规则集意外振荡）、先做分配后做机器相关窥孔（否则模式匹配不全）。做到这三点，窥孔收益稳定而风险可控。
