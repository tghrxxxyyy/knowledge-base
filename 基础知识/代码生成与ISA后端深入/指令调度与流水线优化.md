# 指令调度与流水线优化

> 对应 Aho, Sethi & Ullman《Compilers: Principles, Techniques, and Tools》第 8 章；Appel《Modern Compiler Implementation》第 13 章；Hennessy & Patterson《Computer Architecture》。

## 一、背景与挑战

现代 CPU 多发射、深流水线，简单按程序序发射会因数据冒险（RAW/WAW/WAR）、结构冒险（功能单元争用）或控制冒险（分支）而停顿。考虑 `a = load x; b = a + 1; c = load y; d = c * 2`——若 `load x` 到 `a+1` 有 3 周期延迟，朴素发射会让后续空等。指令调度的目标是在不改变程序语义的前提下重排指令，把无关指令（`c = load y`）填入延迟槽、拉开依赖距离，从而提升指令级并行（ILP）。它通常发生在寄存器分配之后、发射之前，是后端性能的关键一环。

调度与寄存器分配之间存在真实的张力：调度为了填充延迟槽会拉长活跃区间，从而提高寄存器压力；压力过高则引发 spill，而 spill 又引入新的 load/store 与依赖，可能抵消调度的全部收益。因此现代后端普遍采用「压力感知调度」——在关键路径优先的同时，对会显著增加活跃变量的移动施加惩罚。

## 二、核心原理

基于依赖 DAG 的列表调度（list scheduling）：以指令为节点，以数据/控制/资源依赖为边。每个周期从「就绪列表」（所有前驱已调度）中选指令发射，须满足延迟约束（如 load 到使用需 3 周期、乘法需多周期）与功能单元占用。启发式常用「关键路径优先」：优先发射位于最长路径上的指令，以压缩关键路径长度。调度可在基本块内（局部）或跨块（trace / 超块 / 软件流水）进行。注意调度只重排「偏序」，绝不改变数据依赖的先后——这是正确性的底线。

三类依赖的消除难度不同：RAW（真依赖）不可消除，只能靠拉开距离或插入无关指令隐藏；WAR 与 WAW 属伪依赖，可通过寄存器重命名消除（硬件 RAT 或软件重命名）；资源依赖（同一功能单元争用）则靠错开发射周期解决。因此调度的实质工作是「在真依赖构成的关键路径之外，尽可能多地塞入可并行的独立工作」。

## 三、形式化与数学基础

调度长度下界由关键路径决定：

$$len \ge \max_{path}\ \sum_{i\in path} delay(i)$$

节点 $n$ 的就绪时间满足 $rdy(n)=\max_{p\in pred(n)} (rdy(p)+latency(p\to n))$。优先发射 $rdy$ 早且处于关键路径的指令。资源约束可建模为每周期功能单元容量矩阵 $U[u][c] \le cap_u$，列生成/整数规划可求最优，但工程上用启发式近似。最优调度本身是 NP-hard，故实际编译器都退而求「足够好」。

除关键路径下界外，还有两个常用下界：一是「资源下界」，即总工作量除以并行功能单元数 $\lceil \sum_i delay(i) / \sum_u cap_u \rceil$；二是「关键路径下界」如上式。实际调度长度不小于两者最大值，因此计算这两个下界即可快速判断当前调度结果离最优有多远——若结果已等于下界，就无须继续优化，这是工程上极有价值的终止判据。

## 四、代码实现

```python
def list_schedule(nodes, latency, units):
    cycle = 0
    scheduled = set()
    while len(scheduled) < len(nodes):
        ready = [n for n in nodes
                 if n not in scheduled
                 and all(p in scheduled for p in preds(n))]
        # 关键路径优先：剩余最长路径长的先发；pressure 高者降权
        ready.sort(key=lambda x: -(critical_len(x) - PRESSURE_PENALTY * x.live_growth))
        for n in ready:
            if units[n.unit].free(cycle, latency[n]):
                schedule(n, cycle)
                units[n.unit].occupy(cycle, latency[n])
                scheduled.add(n)
        cycle += 1
    return cycle

# critical_len：从该节点到 DAG 出口的最长剩余延迟（可用 DP 记忆化）
def critical_len(n, memo={}):
    if n in memo:
        return memo[n]
    memo[n] = max((latency[n] + critical_len(c, memo) for c in succs(n)), default=0)
    return memo[n]

# 寄存器重命名：消除 WAR/WAW 伪依赖，让更多指令进入就绪列表
def rename(insns):
    ver = {}                              # 架构寄存器 -> 当前版本号
    for ins in insns:
        ins.srcs = [ver.get(r, 0) for r in ins.srcs]   # 读旧版本
        ver[ins.dst] = ver.get(ins.dst, 0) + 1         # 写新版本
        ins.dst_ver = ver[ins.dst]
    return insns
```

`critical_len` 必须用记忆化，否则在共享子节点较多的 DAG 上会重复遍历导致指数开销。`rename` 的作用是消除伪依赖：重命名后同一架构寄存器的不同版本互不干扰，WAW/WAR 边从依赖图中消失，就绪列表规模随之扩大——这正是「调度的自由度来自重命名」的具体体现。

## 五、与其他技术对比

| 维度 | 局部调度 | 全局调度 | 软件流水 | 硬件乱序 |
| --- | --- | --- | --- | --- |
| 范围 | 基本块内 | 跨块/trace | 循环迭代间 | 运行时动态窗口 |
| 收益 | 有限 | 大 | 循环高吞吐 | 适应运行时不确定性 |
| 风险 | 低 | 需异常/语义安全 | 需模调度 | 面积功耗高 |
| 编译期成本 | 低 | 中 | 高 | 无（运行时成本） |
| 对缓存缺失的适应 | 无 | 无 | 无 | 有 |

局部调度简单但受块边界限制；全局调度收益大但要处理控制依赖（谓词执行或 guarded move）与异常安全（不能把可能抛异常的指令移到可见副作用之前）；软件流水用模调度让循环的多次迭代重叠执行。硬件乱序执行能吸收运行时不确定性（如缓存缺失），但静态调度仍能显著减少 ROB 压力与发射期停顿，二者是互补而非替代。

## 六、常见误区

1. 调度违反控制依赖致结果错误：跨块移动需守卫或谓词化。
2. 忽略 WAW/WAR 后需重排或重命名寄存器避免伪依赖。
3. 过度依赖静态调度：乱序执行 CPU 可部分吸收，但调度仍能减少 ROB 压力。
4. 把 store 移到 load 之前破坏内存语义：需别名分析证明不冲突，否则可能丢失 store-load 顺序。
5. 认为关键路径优先总是最优：资源冲突时可能不如「早清空长依赖链」的局部策略。
6. 忽略寄存器压力导致 spill：调度拉长活跃区间，若不加惩罚会引发溢出，反噬收益。
7. 把可能陷入的指令跨块移动：如除法、空指针解引用，移动后会改变异常的可观测时机。
8. 认为软件流水无启动开销：模调度需要 prologue/epilogue，短循环上开销可能超过收益。

## 八、面试题

1. 问：列表调度如何工作？关键路径作用？
   答：按依赖 DAG 每周期从就绪列表选指令发射，关键路径优先可压缩最长路径，从而确定调度长度下界。
2. 问：为何需要寄存器重命名配合调度？
   答：消除 WAW/WAR 伪依赖，让真正无关的指令能并行调度，提升 ILP。
3. 问：静态调度与硬件乱序执行的关系？
   答：互补；静态调度减少译码/发射期停顿，硬件在运行时吸收剩余依赖与缓存不确定性。
4. 问：为什么最优指令调度是 NP-hard？
   答：资源约束下的调度等价于经典调度问题，需搜索指令-周期分配满足依赖与功能单元容量，组合爆炸。
5. 问：如何判断调度结果是否已足够好？
   答：计算关键路径下界与资源下界并取最大；若调度长度等于该值即已最优，可提前终止优化。
6. 问：调度与寄存器分配为何存在冲突？
   答：填充延迟槽会拉长活跃区间、提高寄存器压力，压力过高引发 spill，故需压力感知调度。

## 九、演进与趋势

机器学习调度器（如基于真实硬件反馈的 ML 模型）据实测延迟与端口争用调序，超越手写启发式；LLVM 的 MachineScheduler 支持 per-target 的 DAG 调度策略，结合寄存器压力感知避免调度恶化分配。近年还出现「机器学习 cost model」替代静态延迟表。

另一趋势是「调度与分配联合优化」：不再把两者当作顺序执行的独立 pass，而是在统一框架内交替决策，以逼近联合最优。这类方案的理论收益明显，代价是编译时间上升，因此多用于 JIT 热点或对性能极敏感的离线构建。具体实现以各编译器官方最新文档为准。

## 十、小结

指令调度用依赖 DAG 与延迟/资源约束重排指令，把流水线空隙压到最小。它的本质是在「语义不变」前提下重排偏序，而关键路径优先是逼近最优调度的实用启发式——调度质量直接决定能否喂饱多发射流水线的吞吐。编译器后端一半的性能，往往就藏在这「看似只是挪动几行指令」的步骤里。三条实践准则：先重命名消除伪依赖再调度（扩大自由度）、把异常与内存语义作为不可逾越的约束（保证正确性）、用压力惩罚抑制 spill（避免收益反噬）。
