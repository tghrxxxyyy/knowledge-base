# 向量数据库生态深入（混合检索 / RAG 工程 / 生产部署 / 成本优化 / 多租户）

> 向量数据库 = 存「高维向量」并按「相似度」检索的数据库。本篇深入拆解：混合检索策略、RAG 全链路工程、生产部署最佳实践、成本优化、多租户架构。

---

## 一、核心概念

| 术语 | 含义 |
|------|------|
| Embedding | 文本/图片映射为 N 维浮点向量（如 1024 维） |
| 相似度度量 | 余弦（语义）、欧氏（空间距离）、内积（归一化后≈余弦） |
| ANN | 近似最近邻（召回率×查询速度权衡） |
| Top-K | 返回最相似的 K 个结果 |

## 二、索引算法深入

### 2.1 HNSW（分层可导航小世界）

```
每层一张图：层越高节点越少（跳得快）
查询: 顶层贪婪搜索 → 逐层下钻到第 0 层精搜索

参数：
  M（每节点邻居数）：越大召回越高，内存越大
  efConstruction（建索引质量）：越大索引质量越好，构建越慢
  efSearch（查询质量）：越大召回越高，查询越慢

优缺点：
  ✅ 查询延迟稳定低、召回率高
  ❌ 全部驻留内存，亿级向量需要大内存机器
```

### 2.2 IVF（倒排文件）

```
先用 k-means 聚类成 N 个桶（如 1024 桶）
查询时只查最近的几个桶（如 10 个）

参数：
  nlist（桶数量）：越大分桶越细，查询越快，构建越慢
  nprobe（查询桶数）：越大召回越高，查询越慢

优缺点：
  ✅ 内存占用小（可 + PQ 压缩）
  ❌ 桶边界可能漏召回
```

### 2.3 PQ（乘积量化）

```
把 N 维向量切成 m 段，每段用 k-means 聚类成子码本
用「码字 ID」代替原始浮点 → 内存降 8~64 倍

原理：
  原始向量：1024 维 × 4B = 4KB
  PQ：1024/8 = 128 段 × 1B = 128B（压缩 32 倍）

代价：精度损失
  → 用「先粗索引（IVF/HNSW）+ 再 PQ 精排 + 重算原始距离」恢复精度
```

## 三、混合检索（Hybrid Search）

### 3.1 为什么需要混合

```
纯向量检索的问题：
  专有名词（如"IP 地址 192.168.1.1"）→ 向量语义匹配不准
  编号/代码（如"SKU-20260819"）→ 向量无法精确匹配

混合检索 = 向量（语义）+ 关键词（BM25 精确词命）双路

流程：
  Query → 向量检索 Top-100 + BM25 检索 Top-100
  → 融合（RRF / 加权平均）→ Top-10 返回
```

### 3.2 RRF（Reciprocal Rank Fusion）

```
RRF = 基于排名的融合（不依赖分数绝对值）

score(d) = Σ 1/(k + rank_i(d))  其中 k=60（常数）

优点：
  不需要归一化分数（向量和 BM25 分数尺度不同）
  简单有效
```

### 3.3 元数据过滤

```
检索流程：
  1. 先按元数据过滤（如知识域=Java、时间=2026）
  2. 再在过滤后的子集中做向量检索
  3. 返回 Top-K

好处：
  缩小搜索空间（从亿级→百万级）
  权限隔离（用户只能检索授权数据）
  提升召回质量
```

## 四、RAG 全链路工程

### 4.1 切块策略

| 策略 | 说明 | 适用 |
|------|------|------|
| 固定大小 | 按 token/字符数切 | 简单场景 |
| 语义切块 | 按语义边界切（段落/章节） | 文档/知识库 |
| 递归切块 | 先大块再小块（parent-child） | 需要上下文的场景 |
| 滑动窗口 | 有重叠的切块 | 需要连贯性的场景 |

### 4.2 切块参数

```
块大小：500~1000 token（太大检索不准，太小上下文碎片化）
重叠：50~100 token（保持上下文连贯）

推荐：
  技术文档：500 token，重叠 50
  法律合同：1000 token，重叠 100
  FAQ：200 token，无重叠
```

### 4.3 重排（Rerank）

```
召回 Top-100 → 用重排模型精排取 Top-5

重排模型：
  Cross-Encoder（精度最高，但慢）
  ColBERT（平衡精度和速度）
  Cohere Rerank（API 调用）

效果：精度提升 10~30%
```

### 4.4 增量更新

```
文档更新 → 新向量写入 + 旧向量删除（按 doc_id）

流程：
  1. 文档变更 → 重新切块 + Embedding
  2. 新向量写入向量库
  3. 旧向量按 doc_id 删除
  4. 索引重建（或增量更新）

注意：
  避免索引膨胀（只更新变化的块）
  版本管理（保留历史版本用于审计）
```

## 五、六大产品对比

| 产品 | 形态 | 核心特点 | 适合 |
|------|------|----------|------|
| **Milvus** | 分布式向量数据库 | 存算分离、亿级向量、多种索引 | 大规模生产 RAG |
| **Qdrant** | Rust 向量库 | 过滤能力强、快、Docker 一键 | 中小规模、过滤多 |
| **Weaviate** | Go 向量库 | 内建模块、GraphQL | 快速原型 |
| **Chroma** | 嵌入式 Python | 本地方便 | 原型验证 |
| **FAISS** | 索引库（非数据库） | 算法最全最快 | 算法/离线 |
| **pgvector** | PG 扩展 | SQL 向量列 | 已有 PG、量不大 |

### 5.1 选型决策

```
已有 PG 且量不大 → pgvector（零新组件）
生产级 RAG 亿级向量 → Milvus
过滤条件多且快 → Qdrant
纯算法实验 → FAISS
原型验证 → Chroma
多租户 → Milvus（原生支持）
```

## 六、成本优化

| 策略 | 说明 | 省多少 |
|------|------|--------|
| PQ 压缩 | 向量压缩 8~64 倍 | 80%+ 内存 |
| 磁盘索引 | IVF + 磁盘存储 | 50%+ 内存 |
| 分层存储 | 热数据内存 + 冷数据磁盘 | 30%+ |
| 按量付费 | Milvus Cloud / Qdrant Cloud | 按实际使用 |
| 副本数调整 | 冷数据减少副本 | 30%+ |

### 6.1 内存估算

```
1 亿向量 × 1024 维 × 4B ≈ 400GB（原始值）
+ HNSW 图结构 ≈ 100GB
+ 索引元数据 ≈ 20GB
总计 ≈ 520GB

优化后（PQ 压缩）：
  1 亿 × 128B（PQ）≈ 12.8GB
  + 图结构 ≈ 100GB
  总计 ≈ 113GB
```

## 七、多租户架构

### 7.1 方案对比

| 方案 | 原理 | 适用 |
|------|------|------|
| 独立集合 | 每租户一个 Collection | 强隔离 |
| 元数据过滤 | 共享 Collection + tenant_id 字段 | 中小规模 |
| 混合 | 热租户独立，冷租户共享 | 混合负载 |

### 7.2 元数据过滤方案

```
写入时：
  vector = {...embedding..., "tenant_id": "t_001"}

查询时：
  过滤条件：tenant_id = "t_001"
  向量检索：在过滤后的子集中做 ANN

Milvus 实现：
  collection.create_index("embedding", index_params)
  collection.search(query, "embedding", 
                    expr="tenant_id == 't_001'",
                    limit=10)
```

## 八、常见误区

| 误区 | 真相 |
|------|------|
| 向量库 = 语义库 | 相似度不代表"答案正确"，检索质量取决于切块与模型 |
| HNSW 万能 | 亿级向量内存需求巨大，需要 PQ + 磁盘索引 |
| 维度越高越准 | 768/1024 是常用档，超高维收益递减 |
| 只上向量不做过滤 | 权限场景必须标量过滤，否则越权 |
