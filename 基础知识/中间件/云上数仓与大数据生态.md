# 云上数仓与大数据生态（数据仓库 / 数据湖 / 流计算 / BI）

> 云上大数据把「集群运维」换成「按量付费查询」：数仓（Redshift/BigQuery）、湖仓（Snowflake/Databricks）、流计算（托管 Flink）、编排（Airflow 托管）。本篇逐个讲「解决的问题 → 原理 → 特性 → 选型关注点」。

---

## 一、云数仓：Redshift / BigQuery / MaxCompute / 云数仓

### 1.1 Redshift（AWS）—— 经典 MPP 数仓

**解决的问题**：TB~PB 级分析查询，自己搭数仓集群（选型/扩容/运维）太累。

**原理**：MPP 列式存储 + 节点集群（Leader + Compute Node），数据按分布键切片，查询并行执行；列压缩 + 排序键（Sort Key）+ 分布键（Dist Key）决定查询性能。

**特性**：弹性扩容/缩容、Redshift Spectrum（直接查 S3 数据湖，免加载）、RA3 存储分离、自动优化（AUTO 表排序）。

**选型关注点**：集群是「预留容量」——空闲也付费（可暂停节省）；查询模式固定 → 性能好；临时分析多 → Snowflake/BigQuery 按量更划算。

### 1.2 BigQuery（GCP）—— Serverless 数仓代表作

**解决的问题**：不想管任何集群，SQL 直接查，按扫描字节付费。

**原理**：列式 + 分布式执行引擎（Dremel），存储与计算完全分离，查询自动并行；分区/聚类裁剪扫描量。

**特性**：零运维、按查询扫描量计费、实时分析（BigQuery Streaming）、与 GCP 生态（Pub/Sub/Dataflow）原生打通、ML（BigQuery ML 内置模型）。

**选型关注点**：适合「查询频率低、扫描量可预测」的 BI/分析；高频小查询反而不省（按量计费）；跨云用是短板（数据在 GCP）。

### 1.3 国内：MaxCompute（阿里）/ 云数仓 TCHouse（腾讯）/ AnalyticDB

- **MaxCompute**：阿里云数仓（类 BigQuery），SQL + 生态强，离线批处理主力；
- **AnalyticDB（ADB）**：分析型数据库（MySQL 协议、向量检索），偏实时分析/交互查询；
- **腾讯云数仓**：类 Redshift 的 MPP，配套 TCHouse 生态。

**选型关注点**：国内合规 + 数据在阿里云 → MaxCompute；需要 MySQL 兼容的实时分析 → ADB；实时分析优先 → 云 ClickHouse / Doris（见「[ClickHouse](./ClickHouse.md)」）。

## 二、湖仓一体与 SaaS 数仓：Snowflake / Databricks

### 2.1 Snowflake —— 云中立 SaaS 数仓

**解决的问题**：数仓的「存储、计算、服务」三件事全托管，且**多公有云可用**（AWS/Azure/GCP），不锁一家。

**原理**：存算分离三层——存储层（云对象存储）、计算层（虚拟仓库，可独立扩缩容与暂停）、服务层（元数据/优化器）；多集群共享同一份数据（Multi-Cluster Shared Data）。

**特性**：按秒计费（查询才花钱）、虚拟仓库隔离负载、时间旅行（可查历史版本数据）、外部表（直接查 S3 数据）、数据市场。

**选型关注点**：多云/跨云战略 → Snowflake（云中立）；团队已在某云 → 原生 Redshift/BigQuery 通常更便宜；Snowflake 贵在「弹性与零运维」溢价。

### 2.2 Databricks —— 湖仓一体（Lakehouse）

**解决的问题**：数据湖（低成本存原始数据）与数仓（高性能分析）割裂，Databricks 把两者合一。

**原理**：Delta Lake（事务表格式：ACID + 时间旅行 + 索引）+ Spark 引擎 + 统一管理；数据存在云对象存储，Spark 计算层弹性伸缩。

**特性**：Delta/Parquet 表格式、SQL + DataFrame + ML（MLflow）、流批一体（Structured Streaming）、跨云部署。

**选型关注点**：数据科学/ML + 分析混合负载 → Databricks；纯 SQL BI → 数仓更合适；Delta Lake 开源（可与 Spark 自建组合）。

## 三、托管流计算：Dataflow / 云 Flink / Kinesis Analytics

| 服务 | 厂商 | 关键点 |
|------|------|--------|
| Dataflow | GCP | 托管 Apache Beam，自动扩缩容，Exactly-once |
| Managed Flink（云 Flink） | 阿里/腾讯 | 开源 Flink 托管，SQL/DataStream，Kafka→Flink→数仓链路 |
| Kinesis Data Analytics | AWS | SQL/Java 分析 Kinesis 流，轻量 |
| Stream Analytics | Azure | 类 SQL 流处理，与 Event Hubs 集成 |

**原理**：流引擎（Flink/Beam）托管化——状态管理、checkpoint、窗口、背压由平台兜底，开发者只写作业。

**选型关注点**：阿里云生态 + 实时链路 → 云 Flink（国内主流）；GCP → Dataflow；AWS → Kinesis Analytics（轻量）或 MSK + 自建 Flink。

## 四、托管编排与调度：Airflow / Step Functions / 云工作流

- **托管 Airflow**（AWS MWAA / GCP Composer / 阿里云）：DAG 调度开箱即用，省集群运维；
- **Step Functions**（AWS）：状态机编排（重试/超时/并行分支），与 Lambda/SQS 组合成无服务编排；
- **云工作流/DataWorks**（阿里）：DataWorks 是数据开发全流程（调度 + 血缘 + 治理），国内数据工程标配。

**选型关注点**：数据任务编排 → 托管 Airflow / DataWorks（血缘治理好）；应用流程编排 → Step Functions/云工作流（轻量状态机）。

## 五、选型速查（云上大数据全景）

| 需求 | 首选 | 备选 |
|------|------|------|
| 离线数仓（国内合规） | MaxCompute / 云数仓 | Redshift（海外） |
| Serverless 按量查询 | BigQuery | Snowflake |
| 多云/弹性 BI | Snowflake | BigQuery |
| 数据湖 + 分析 + ML | Databricks（Lakehouse） | EMR + 自建 Delta |
| 实时流处理 | 云 Flink（国内）/ Dataflow（GCP） | Kinesis Analytics |
| 查询 S3 数据湖 | Redshift Spectrum / Athena | BigQuery 外部表 |
| 任务编排 | DataWorks / 托管 Airflow | Step Functions |
| 交互式 BI 查询 | AnalyticDB / 云 ClickHouse | — |

> 补充：**Serverless 查询（Athena）**：不建任何集群，SQL 直接查对象存储（按扫描量计费）——临时/低频分析的性价比之王。
