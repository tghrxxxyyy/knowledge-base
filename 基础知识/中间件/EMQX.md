# EMQX（IoT 消息中间件 / 大规模 MQTT Broker）

> EMQX 是**全球领先的开源 MQTT 消息服务器**（Erlang/OTP 构建），单集群可支撑**亿级设备连接、百万级消息吞吐**，以「MQTT 协议全版本 + 规则引擎（数据桥接）+ 分布式集群」成为 IoT 平台消息层的首选。相比自研 MQTT Broker、VerneMQ（功能少）、Mosquitto（轻量单机）、云 IoT Hub（厂商锁定），EMQX 以「**大规模、高可用、易扩展、多云部署**」独树一帜。本篇按「解决的问题 → 原理 → 特性 → 选型关注点」拆解。

---

## 一、要解决的问题

| 痛点 | 说明 |
|------|------|
| 海量设备连接 | 百万级设备长连接，普通 Broker 连接数撑不住 |
| 弱网环境 | 设备网络不稳定，需自动重连/会话恢复 |
| 消息不可达 | 设备离线时消息需持久化（QoS + 保留消息） |
| 数据接入下游 | 设备数据要转发到 Kafka/MySQL/ES 等系统 |
| 设备管理 | 连接状态/上下线事件/认证需要统一管理 |

> 核心认知：**EMQX = IoT 设备的「消息汇聚中心」**——设备（MQTT）进，业务系统（Kafka/MySQL/HTTP）出，中间是规则引擎做转换分流。

## 二、核心原理

### 2.1 架构

```
设备层：MQTT（Android/iOS/嵌入式/网关） + MQTT-SN/CoAP/LwM2M
  └── EMQX Cluster（Erlang/OTP 分布式）
      ├── 连接层（百万级长连接，无状态水平扩展）
      ├── 会话层（QoS 0/1/2、离线消息、遗嘱消息、保留消息）
      ├── 路由层（主题树匹配，全节点共享路由表）
      └── 规则引擎（SQL 式规则 → 数据桥接）
          ├── Kafka / Pulsar / RabbitMQ（消息转发）
          ├── MySQL / PostgreSQL / TDengine / InfluxDB（落库）
          ├── ES / ClickHouse（分析）
          └── Webhook / HTTP API（业务对接）
```

### 2.2 集群原理（Erlang 分布式）

- **全连接网状 + 路由表广播**：每个节点持有全集群主题路由，任意节点收发消息都可达（对比分区模型，EMQX 是「无分区全局路由」）；
- **水平扩展**：加节点即可提升连接数（连接不互斥），节点故障自动摘除；
- **共享订阅**：同一主题多个订阅者分摊消息（负载均衡，类似消费者组）。

### 2.3 路由机制深入（消息如何跨节点到达）

```
设备 A 连在节点 1，订阅者 B 连在节点 2：
  设备 A 发布到主题 "dev/1/telemetry"
  → 节点 1 查全局路由表（主题树）
  → 找到节点 2 有订阅者 → 转发到节点 2
  → 节点 2 投递给订阅者 B

路由表维护：
  每个节点维护"主题 → 哪些节点有订阅"的路由树
  订阅变化 → 广播增量更新（全节点最终一致）
  主题树压缩（前缀合并）→ 路由表内存可控（千万级主题）

性能关键：
  消息只在"有订阅的节点"间转发（不做全广播）
  高扇出主题（大量订阅者）→ 路由表热点 → 用共享订阅分散
```

### 2.4 MQTT 核心机制落地

| 机制 | EMQX 实现 |
|------|-----------|
| QoS 0/1/2 | 完整支持（QoS2 四段握手） |
| 保留消息 | 主题级保留（新订阅即收最新值） |
| 遗嘱消息 | 设备异常断开自动发布遗嘱（上下线感知） |
| 会话恢复 | Clean Session/Persistent Session（离线期间消息累积） |
| 认证鉴权 | 内置密码认证 + JWT + HTTP 认证 + ACL |
| 心跳/超时 | 自动处理半开连接（协议级探测） |
| 共享订阅 | 多订阅者分摊（`$share/group/topic`） |
| 延迟发布 | 主题级延迟（延迟发布消息） |
| MQTT 5.0 | 增强认证、主题别名、消息过期、User Properties |

### 2.5 QoS 与消息不丢深入

```
QoS 0：尽力而为（最快，可能丢）——遥测非关键数据
QoS 1：至少一次（ack 确认，可能重复）——默认推荐
QoS 2：恰好一次（四段握手：PUBLISH→PUBREC→PUBREL→PUBCOMP）——关键指令

消息不丢的关键（QoS 1/2 语义）：
  发布端：QoS1 未收到 PUBACK → 重发（MQTT 3.1.1 语义）
  Broker 端：离线消息在持久会话里累积（会话保留期配置）
  订阅端：QoS 由订阅 QoS 决定（min(发布 QoS, 订阅 QoS)）

⚠️ 设备弱网建议：
  QoS1 + Persistent Session（离线补发）
  避免 QoS2（四段握手开销大，弱网吞吐更低）
  客户端必须处理重复消息（幂等）
```

### 2.6 规则引擎（数据桥接，核心差异化）

```sql
-- 示例：设备数据落库 + 转发 Kafka 一条规则完成
SELECT
  clientid, payload.temp as temp, payload.humidity as humidity,
  payload.ts
FROM "devices/+/telemetry"
WHERE payload.temp > 40            -- 条件过滤（告警场景）
DO
  INSERT INTO `temperature_alarm` ...    -- 落库
  SEND TO kafka_topic               -- 转发 Kafka
  CALL webhook_alarm(...)           -- 触发 Webhook
```

**选型关注点**：规则引擎让「设备数据 → 业务系统」零代码/低代码打通——不用写消费者程序，是 EMQX 比裸 MQTT Broker 值钱的核心。

### 2.7 规则引擎执行链路

```
消息进入（设备发布）
  → 匹配规则（FROM 主题模式）
  → SELECT 字段提取/转换（payload 解析 JSON/二进制）
  → WHERE 条件过滤（只处理感兴趣的数据）
  → DO 动作执行（可多个动作并行）
      ├── 写入 SQL 数据库（INSERT 语句）
      ├── 转发到 Kafka/其他 MQTT/Webhook
      ├── 调用 REST API（业务系统）
      └── 重新发布（规则内部流转）

执行语义：
  动作失败 → 重试（可配置）→ 失败消息进队列
  高性能：单规则单消息处理开销极低（毫秒级）
```

## 三、核心特性

| 特性 | 说明 |
|------|------|
| 海量连接 | 单集群千万级连接（MQTT over TCP/SSL/WS） |
| 多协议 | MQTT 3.1/3.1.1/5.0 + MQTT-SN + CoAP + LwM2M + WebSocket |
| 高可用 | 集群无单点、自动故障转移、消息不丢 |
| 规则引擎 | SQL 式规则 + 20+ 数据桥接（Kafka/DB/ES/Webhook） |
| 离线消息 | 会话持久化（内存/数据库） |
| 安全 | TLS/mTLS + 认证（内置/JWT/HTTP）+ ACL |
| 可观测 | Dashboard + Prometheus + 链路追踪（OTel） |
| 运维 | Dashboard 管理台 + REST API + 集群热升级 |
| 云原生 | K8s Operator 部署、多云镜像（开源版/企业版） |

## 四、EMQX vs VerneMQ vs Mosquitto vs 云 IoT Hub

| 维度 | EMQX | VerneMQ | Mosquitto | 云 IoT Hub（阿里/华为/AWS） |
|------|------|---------|-----------|---------------------------|
| 语言 | Erlang | Erlang | C | 托管 |
| 扩展性 | 强（无分区集群） | 中 | 弱（单机） | 托管弹性 |
| 功能 | 全（规则引擎） | 中 | 基础 | 全 + 云生态 |
| 规则引擎/桥接 | 强 | 弱 | 无 | 云服务集成 |
| 运维成本 | 中（自建） | 中 | 低 | 零（托管） |
| 厂商锁定 | 无 | 无 | 无 | 有 |
| 适用 | 大规模 IoT 平台 | 中型 IoT | 原型/小规模 | 云上快速交付 |

**选型关注点**：
- 大规模/生产 IoT 平台 → **EMQX**（功能全 + 可扩展 + 无锁定）；
- 小规模/原型 → **Mosquitto**（几分钟部署）；
- 云上快速交付 → **云 IoT Hub**（接受锁定）；
- 极简需求 → VerneMQ 少用。

## 五、生产实践

### 5.1 关键配置

| 配置 | 建议 |
|------|------|
| 集群节点 | ≥3（奇数），同机房内网互通 |
| 连接数规划 | 按峰值 ×1.5 预留（连接不互斥，可扩容） |
| 消息保留 | QoS1 + 会话持久化 + 按需开保留消息 |
| 认证 | 生产必开（JWT/HTTP 认证），禁止匿名 |
| 规则引擎 | 拆多条规则（落库/告警/转发分离），防止规则内阻塞 |
| 监控 | Dashboard + Prometheus + 上下线事件告警 |
| 会话超时 | 弱网设备配长会话保留期（如 24h），防频繁重建 |

### 5.2 容量规划

```
连接数：单节点万~百万级（取决于内存），集群线性扩展
  → 每连接约消耗 50~200KB 内存（TCP + MQTT 会话）

消息吞吐：单节点 10万+/秒 级别（受规则引擎/持久化影响）
  → 无规则引擎直通最快

磁盘规划：
  离线消息（会话队列）：持久会话 × QoS1 消息
  桥接失败积压：规则引擎 action 队列
  → 按"峰值离线消息量"规划磁盘

网络规划：
  设备上行流量 + 规则引擎下行流量（转发到 Kafka/DB）
  跨节点路由流量（订阅者分布广时）
```

### 5.3 常见坑

- **QoS2 滥用**：设备侧尽量 QoS1（QoS2 四段握手开销大，弱网更差）；
- **订阅主题爆炸**：主题名设计规范（`产品/设备/属性`），否则路由表膨胀；
- **遗嘱消息导致误告警**：上下线抖动时遗嘱频繁触发 → 配置会话恢复 + 去抖；
- **规则引擎阻塞**：桥接 Kafka 不可用时会积压 → 设置队列 + 重试 + 告警；
- **弱网重连风暴**：设备断网集体重连（基站恢复）→ 连接突增 → 集群扩容量 + 连接限速；
- **大 payload**：单条消息过大（>1MB）拖垮吞吐 → 限制 + 拆分。

### 5.4 安全加固

```
① TLS/mTLS：设备证书双向认证（设备端证书绑定）
② 认证：
  密码认证（内置 MySQL/Redis 存储）
  JWT 认证（对接业务鉴权系统）
  HTTP 认证（灵活，对接任意）
③ ACL：主题级访问控制（每设备只能访问自己的主题：dev/{clientid}/#）
④ 协议限制：最大报文大小、最大连接数/租户
⑤ 审计：设备上下线/认证失败日志
```

### 5.5 典型架构（数据链路）

```
设备 → MQTT → EMQX 集群
  ├── 规则引擎 → Kafka（大数据管道，离线分析）
  ├── 规则引擎 → TDengine/InfluxDB（时序存储，监控大屏）
  ├── 规则引擎 → MySQL/PostgreSQL（业务落库，订单/告警）
  ├── 规则引擎 → Webhook（实时业务通知）
  └── 下行：设备命令（topic 下发）→ 设备执行
```

## 六、选型速查

| 需求 | 首选 | 备选 |
|------|------|------|
| 大规模 IoT 平台 | EMQX | 云 IoT Hub |
| 原型/小规模 | Mosquitto | EMQX（单机） |
| 多云/避免锁定 | EMQX | VerneMQ |
| 与 Kafka/DB 打通 | EMQX 规则引擎 | 自研消费者 |
| 云上快速交付 | 云 IoT Hub | EMQX on 云 VM |
| 强安全合规 | EMQX 企业版（mTLS/审计） | 云 IoT Hub |

### 6.1 决策树

```
设备规模 < 1 万 + 原型 → Mosquitto
生产 IoT + 数据要进下游系统 → EMQX（规则引擎）
云上托管快速交付 → 云 IoT Hub（接受锁定）
需要高级特性（桥接/审计/多云）→ EMQX 企业版
```
