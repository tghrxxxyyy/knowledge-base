# 云上数据库与缓存生态深入（多地域部署 / 读写分离 / 迁移路径 / 成本优化）

> 云上数据库 = 开源引擎托管化 + 存算分离弹性化 + 专属 NoSQL。本篇深入拆解：多地域部署方案、读写分离策略、迁移路径规划、成本优化实战。

---

## 一、托管关系库

### 1.1 RDS / Cloud SQL

```
原理：开源 MySQL/PG 的托管化（同引擎、同协议）
  主从复制 + 自动故障转移 + 定时备份 + 只读副本

特性：
  高可用：多可用区主从，故障秒级切换
  只读副本：读扩展（RDS 最多 15 个）
  自动备份 + 时间点恢复（PITR）
  参数组统一管理、慢日志/审计
```

### 1.2 云原生弹性关系库

| 服务 | 厂商 | 引擎 | 亮点 |
|------|------|------|------|
| Aurora | AWS | MySQL/PG | 15 读副本、存储自动扩容 |
| PolarDB | 阿里云 | MySQL/PG/Oracle | 兼容国产替换 |
| AlloyDB | GCP | PG | 列存加速分析 |
| Spanner | GCP | 自研 SQL | 全球分布式强一致 |

```
存算分离原理：
  存储层：分布式日志复制（6 副本，3 AZ）
  计算层：写主 + N 读副本（副本只读存储）
  写入：日志复制到 6 副本后返回成功
  读取：直接读存储层（一致性强）
```

## 二、多地域部署方案

### 2.1 方案对比

| 方案 | 原理 | 适用 |
|------|------|------|
| 主从跨地域 | 主在 Region A，从在 Region B | 读扩展 + 灾备 |
| 多主复制 | 两个 Region 都可写 | 全球多活 |
| Spanner | 全球分布式强一致 | 强一致多活 |
| 代理层 | 代理路由读写到不同 Region | 灵活 |

### 2.2 Aurora Global Database

```
Aurora Global Database：
  主集群在 Region A
  只读副本在 Region B（跨地域复制延迟 < 1s）
  故障转移：Region A 挂了，Region B 提升为写

适用：
  全球读扩展（多 Region 读副本）
  灾备（RPO < 1s，RTO < 1min）
```

### 2.3 多地域读写分离

```
读写分离策略：
  写：路由到主 Region
  读：路由到最近的只读副本（本地优先）

实现方式：
  应用层：配置多个数据源，读写分开
  代理层：ProxySQL / RDS Proxy 自动路由
  DNS 层：GeoDNS 按地域路由
```

## 三、读写分离策略

### 3.1 代理模式

```
ProxySQL / RDS Proxy / PgBouncer：
  应用连接代理 → 代理自动路由写到主、读到从

优点：
  应用无感知（透明代理）
  连接池复用（减少连接数）
  自动故障转移

缺点：
  增加一跳延迟（通常 < 1ms）
  代理本身高可用
```

### 3.2 主从延迟处理

| 策略 | 说明 |
|------|------|
| 强制读主 | 关键读（如支付后查询）强制走主 |
| 延迟检测 | 检查 Seconds_Behind_Master，超阈值读主 |
| 半同步复制 | 至少 1 个从库确认后才返回成功 |
| GTID 等待 | 等待从库同步到指定 GTID 后再读 |

### 3.3 连接池配置

```
连接池大小：
  最小连接数：CPU 核数 × 2 + 磁盘数
  最大连接数：最小连接数 × 2

超时设置：
  连接超时：3s
  空闲超时：600s
  最大存活时间：1800s

PgBouncer 配置：
  pool_mode = transaction（事务级连接池，推荐）
  default_pool_size = 20
  max_client_conn = 1000
```

## 四、迁移路径规划

### 4.1 评估阶段（1~2 周）

```
1. 梳理现有数据库清单
2. 评估各服务的迁移复杂度
3. 确定迁移优先级（低风险→高风险）
4. 工具评估（DMS/数据传输服务）
```

### 4.2 试点阶段（2~4 周）

```
1. 选一个非核心服务试点
2. 验证协议兼容性（MySQL/PG）
3. 测试性能和可靠性
4. 验证备份恢复
```

### 4.3 批量迁移（4~8 周）

```
1. 按优先级批量迁移
2. 双跑验证（新旧并行）
3. 切换流量
4. 监控稳定性
```

### 4.4 清理阶段（1~2 周）

```
1. 下线旧实例
2. 清理旧数据
3. 复盘总结
```

## 五、托管 NoSQL

### 5.1 DynamoDB

```
DynamoDB = 托管 KV 数据库（AWS 代表作）
  分区键 + 排序键设计（单表设计思想）
  按 RCU/WCU 计费

特性：
  按需/预置容量模式
  全局表（多区域多写）
  流（Stream → Lambda）
  TTL
  事务 API
  PartiQL（SQL 兼容查询）
```

### 5.2 Cosmos DB

```
Cosmos DB = 多模型 + 多 API + 全球多写
  支持：Mongo/SQL/Cassandra/Gremlin/Table
  全球多写强一致（独一份）
  成本：贵

适用：
  全球多活多模型
  需要强一致
  不差钱
```

## 六、托管缓存

### 6.1 ElastiCache / MemoryDB / 云 Redis

| 服务 | 厂商 | 关键点 |
|------|------|--------|
| ElastiCache | AWS | Redis/Memcached，多 AZ 故障转移 |
| MemoryDB | AWS | Redis 兼容 + 持久化强一致（贵） |
| Azure Cache | Azure | Redis 托管，企业版含模块 |
| Memorystore | GCP | Redis/Memcached |
| 云 Redis | 国内 | 兼容 Redis 协议，读写分离/集群版 |

### 6.2 选型

```
纯缓存（可丢）→ 任意托管 Redis（便宜档）
缓存数据不能丢 → MemoryDB 或云 Redis 持久化版
大 key/热 key → 治理方法与自建一致
```

## 七、成本优化

| 策略 | 做法 | 省多少 |
|------|------|--------|
| 预留实例 | 承诺 1~3 年 | 30~60% |
| 弹性伸缩 | 按负载自动扩缩 | 20~40% |
| 冷热分层 | 热 SSD + 冷 HDD/归档 | 50~80% |
| 只读副本 | 读扩展（按需） | 30~50% |
| 连接池 | PgBouncer/Pgpool | 减少连接数 |
| Serverless | 按量付费（低频） | 60~90% |
