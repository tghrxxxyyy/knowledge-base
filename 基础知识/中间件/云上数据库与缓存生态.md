# 云上数据库与缓存生态（托管关系库 / NoSQL / 缓存）

> 云厂商把数据库做成托管服务：自动备份、高可用、弹性、免运维，且按引擎分档（兼容开源 vs 自研高性能）。本篇按类别拆解：托管关系库、云原生弹性关系库、托管 NoSQL（文档/KV）、托管缓存，每个讲「解决的问题 → 原理 → 特性 → 选型关注点」。

---

## 一、托管关系库：RDS / Cloud SQL / 云数据库 RDS

**解决的问题**：MySQL/PostgreSQL 的备份、主从、升级、监控全都自己搞——托管后开箱即用。

**原理**：即开源 MySQL/PG 的托管化（同引擎、同协议），主从复制 + 自动故障转移 + 定时备份 + 只读副本。

**特性**（各云一致）：
- 高可用：多可用区主从，故障秒级切换；
- 只读副本：读扩展（RDS 最多 15 个，PolarDB 更多）；
- 自动备份 + 时间点恢复（PITR）；
- 参数组统一管理、慢日志/审计、SSL/TLS。

**选型关注点**：
- 想完全兼容开源生态 → RDS/Cloud SQL（零迁移成本）；
- 读多写少、要弹性 → 加只读副本或直接上 Aurora/PolarDB；
- 省钱：按实例规格 + 存储计费，闲时低配 + 弹性升配。

---

## 二、云原生弹性关系库：Aurora / PolarDB / AlloyDB / Spanner

**解决的问题**：RDS 的瓶颈是「单实例上限」——Aurora 系用**存算分离**把存储做成共享层，计算节点秒级扩缩，存储自动扩容到 128TB 且多副本。

**原理**：存储与计算分离（存储层分布式日志复制，计算节点共享同一份存储）；写主节点 + N 读副本（副本间不复制数据、只读存储）；写入日志复制到 6 副本（3 AZ）。

| 服务 | 厂商 | 引擎兼容 | 亮点 |
|------|------|----------|------|
| Aurora | AWS | MySQL/PostgreSQL | 15 读副本、存储自动扩容、Serverless 档 |
| PolarDB | 阿里云 | MySQL/PostgreSQL/Oracle | 兼容国产数据库替换场景、列存索引 |
| AlloyDB | GCP | PostgreSQL | 列存加速分析、AI 特性 |
| Cloud Spanner | GCP | 自研 SQL | 全球分布式强一致（NewSQL 天花板） |

**特性**：秒级弹性、跨可用区高可用、存储与计算独立计费、快照即克隆（开发环境秒建库）。

**选型关注点**：
- 读多写少 + 大促弹性 → Aurora/PolarDB（性价比最高）；
- 全球多活强一致 → Spanner（贵，但独一份）；
- 已有 TiDB 自建 → 不必换，云托管 TiDB 也有（如 TiDB Cloud）。

## 三、托管 NoSQL：文档（MongoDB）与 KV（DynamoDB）

### 3.1 托管 MongoDB：DocumentDB / 云 MongoDB / Cosmos DB

- **DocumentDB**（AWS）：MongoDB 兼容（3.6/4.0 API），存储与计算分离（同 Aurora 架构），吞吐弹性；
- **云 MongoDB**（阿里/腾讯）：开源 MongoDB 托管，副本集/分片集群、备份、监控；
- **Cosmos DB**（Azure）：多模型（文档/图/列/键值）+ 多 API（Mongo/SQL/Cassandra/Gremlin）+ **全球多写强一致**，分布式存储之王但贵。

**选型关注点**：要 MongoDB 生态与工具 → DocumentDB/云 MongoDB；要全球多活多模型 → Cosmos DB；注意 DocumentDB 非 100% 兼容（部分聚合/索引差异，迁移前验证）。

### 3.2 DynamoDB —— 托管 KV 数据库（AWS 代表作）

**解决的问题**：需要「单表存亿级 KV、毫秒级访问、无限伸缩」的存储，不想运维任何集群。

**原理**：分区键 + 排序键设计（单表设计思想），数据自动按分区键哈希分布到分区，按容量单位（RCU/WCU）计费。

**特性**：按需/预置两种容量模式、自动扩缩、全局表（多区域多写）、流（Stream → Lambda）、TTL、事务 API、PartiQL（SQL 兼容查询）。

**选型关注点**：
- 高吞吐 + 弹性强 → DynamoDB（省心）；但**查询模型受限**（必须按分区键），复杂查询要设计单表；
- 需要灵活 SQL → Aurora/云数据库更合适；
- 成本：按 RCU/WCU 计量，读多写少的场景便宜，扫描查询贵。

## 四、托管缓存：ElastiCache / MemoryDB / 云 Redis / Memorystore

**解决的问题**：Redis 集群的部署、哨兵、故障转移、备份自己运维——托管后拿来即用。

| 服务 | 厂商 | 关键点 |
|------|------|--------|
| ElastiCache | AWS | Redis/Memcached 两种引擎，多 AZ 自动故障转移，集群模式（分片） |
| MemoryDB | AWS | Redis 兼容 + **持久化强一致**（多副本日志），贵但可用作「内存数据库」而非纯缓存 |
| Azure Cache for Redis | Azure | Redis 托管，企业版含模块（Bloom/TimeSeries） |
| Memorystore | GCP | Redis/Memcached 托管，VPC 内连接 |
| 云 Redis（阿里/腾讯） | 国内 | 兼容 Redis 协议，读写分离、集群版、持久化备份 |

**选型关注点**：
- 纯缓存（可丢）→ 任意托管 Redis（便宜档）；
- 缓存数据不能丢（会话/计数器）→ MemoryDB 或云 Redis 持久化版；
- 大 key/热 key：托管版同样存在，治理方法与自建一致（见「基础知识/redis知识」）。

## 五、托管对象存储（S3 协议是事实标准）

- **S3**（AWS）/ **OSS**（阿里）/ **COS**（腾讯）/ **Cloud Storage**（GCP）——本质都是对象存储 + S3 兼容 API；
- 解决：海量非结构化文件（图片/视频/备份/日志），11 个 9 持久性；
- 特性：生命周期管理（冷热分层）、版本控制、静态网站托管、预签名 URL、事件通知（触发函数）；
- 选型关注点：**协议兼容（S3 API）几乎零迁移成本**；冷数据用归档档省 80%+ 成本；私有部署用 MinIO（见「[对象存储 MinIO/OSS](./对象存储MinIO-OSS.md)」）。

## 六、选型速查

| 需求 | 首选 | 备选 |
|------|------|------|
| 标准 CRUD + 兼容开源 | RDS / Cloud SQL / 云 RDS | Aurora（读多时） |
| 大促弹性 + 读多写少 | Aurora / PolarDB | 云数据库 Proxy + 只读副本 |
| 亿级 KV + 高吞吐 | DynamoDB | 云 Redis（数据不大时） |
| 文档/灵活 Schema | DocumentDB / 云 MongoDB | Cosmos DB（全球多活） |
| 全球多活强一致 | Spanner / Cosmos DB | — |
| 缓存（可丢） | ElastiCache / 云 Redis | Memorystore |
| 缓存（不可丢） | MemoryDB / 云 Redis 持久化 | — |
| 图片/文件/备份 | S3 / OSS / COS | MinIO（私有） |
