# Ceph（分布式存储 / 统一存储平台）

> Ceph 是 **SUSE 主导的开源分布式存储系统**，以「**一套集群同时提供对象存储（RADOS Gateway/S3）、块存储（RBD）、文件存储（CephFS）**」著称，底层是去中心化的 **RADOS**（可靠的自动分布式对象存储）+ CRUSH 数据分布算法。相比 MinIO（纯对象存储）、HDFS（大数据文件系统）、GlusterFS（文件存储）、云存储（S3/EBS 托管），Ceph 以「**统一存储 + 自愈 + 无单点 + 软件定义**」成为私有云/开源基础设施的存储底座。本篇按「解决的问题 → 原理 → 特性 → 选型关注点」拆解。

---

## 一、要解决的问题

| 痛点 | 说明 |
|------|------|
| 存储种类割裂 | 对象/块/文件三套系统分别建设，管理成本高 |
| 硬件绑定 | 商业存储（EMC/NetApp）贵且绑定硬件 |
| 扩容困难 | 存储扩容要停机/换柜，规模受限 |
| 单点风险 | 集中存储控制器故障 = 数据不可用 |
| 数据可靠性 | 磁盘损坏需要自动修复（自愈） |

> 核心认知：**Ceph = 「软件定义的统一存储」**——普通 x86 服务器 + 千兆网络就能组成一个自我修复的存储集群，一套底座出三种接口（S3/RBD/CephFS）。

---

## 二、核心原理

### 2.1 架构

```
应用层：S3/OSS（RGW 对象）/ 虚拟机磁盘（RBD 块）/ 文件（CephFS）

服务层：
  ├── RADOS Gateway（RGW）：S3/Swift 兼容对象存储网关
  ├── RBD：块设备（KVM/CephFS 虚拟机磁盘、K8s PVC）
  ├── CephFS：POSIX 文件系统（多活元数据服务器）

核心层（RADOS）：
  ├── OSD（Object Storage Daemon）：每磁盘一个，存数据 + 复制 + 自愈
  ├── MON（Monitor）：维护集群地图（Cluster Map），选举/一致性（Paxos）
  ├── MGR（Manager）：监控/调度/均衡（Prometheus 指标、Balancer）
  └── CRUSH 算法：数据分布（无需查表，确定性计算）

硬件：普通 x86 + SSD/NVMe（OSD journal）+ 万兆网
```

### 2.2 CRUSH 数据分布（核心算法）

```
对象 ID → hash → PG（Placement Group）→ CRUSH 映射（按集群地图确定性计算）
  → 选定 OSD 组合（如 3 副本）：数据分布均匀 + 故障域感知（机架/机房）
```

**与 HDFS 对比**：HDFS 用 NameNode 集中记录数据位置；Ceph **无中心查询**——客户端自己用 CRUSH 算出数据在哪，这也是 Ceph 无单点、可水平扩展的根源。

**选型关注点**：CRUSH 让 Ceph 扩容/故障时**只迁移受影响 PG**（局部重均衡），不像一致性哈希全量迁移——大规模扩展友好。

### 2.3 数据可靠性

- **副本/纠删码**：默认 3 副本（或 EC 2+1 省空间，如 8+3）；
- **自愈**：OSD 故障 → PG 自动在健康 OSD 重建副本；
- **Scrub**：定期数据校验（对比副本哈希，防静默损坏）；
- **故障域**：副本分布跨机架/机房（容忍机架级故障）；
- **一致性**：MON 用 Paxos 保证集群地图一致。

### 2.4 三种接口的落地

| 接口 | 组件 | 典型场景 |
|------|------|----------|
| 对象（S3） | RGW | 备份/归档/媒体存储（兼容 S3 协议） |
| 块（RBD） | RBD | 虚拟机磁盘、K8s PVC（OpenStack/K8s 存储类） |
| 文件（CephFS） | CephFS | 共享目录、大数据计算共享存储 |

**选型关注点**：一套集群三种接口是 Ceph 最大卖点——但**别为了「统一」把不合适的负载硬塞进来**（如高并发小文件 IO 并不适合 Ceph）。

## 三、核心特性

| 特性 | 说明 |
|------|------|
| 统一存储 | 对象 + 块 + 文件一套集群 |
| 无单点 | 去中心化（CRUSH + Paxos），全部组件可水平扩展 |
| 自愈 | 磁盘故障自动重建副本 |
| 软件定义 | 普通硬件组建，成本低 |
| 弹性扩展 | 在线加 OSD，容量/性能线性增长 |
| S3 兼容 | RGW 兼容 S3 API（生态直接复用） |
| K8s/OpenStack | 成熟 CSI/Cinder 驱动（云原生存储类） |
| 生态 | 被 OpenStack/K8s/云厂商（OpenShift/私有云）广泛集成 |

## 四、Ceph vs MinIO vs HDFS vs GlusterFS

| 维度 | Ceph | MinIO | HDFS | GlusterFS |
|------|------|-------|------|-----------|
| 类型 | 统一（对象+块+文件） | 对象 | 文件（大数据） | 文件 |
| 一致性 | 强（CRUSH 副本） | 强 | 强 | 强 |
| 去中心化 | 强（CRUSH） | 中（需控制面） | 弱（NameNode） | 中 |
| 自愈 | 强（自动重建） | 有（纠删码） | 有（副本恢复） | 弱 |
| 性能 | 中（元数据开销） | 高（小规模） | 高吞吐 | 中 |
| 部署复杂度 | 高 | 低 | 中 | 低 |
| 适用 | 私有云存储底座 | 轻量对象存储 | 大数据批处理 | 文件共享 |

**选型关注点**：
- 私有云/统一存储/生产底座 → **Ceph**；
- 轻量对象存储/快速落地 → **MinIO**；
- 大数据计算存储 → **HDFS**（与 Spark/MapReduce 深度耦合）；
- 简单文件共享 → **GlusterFS/NFS**。

## 五、生产实践

### 5.1 关键配置

| 配置 | 建议 |
|------|------|
| 副本策略 | 默认 3 副本；容量敏感用 EC（纠删码） |
| OSD 数量 | ≥10 个起步（PG 分布才均匀），PG 数按 OSD 数计算 |
| 网络 | 集群网络/公网分离，万兆起步（复制流量大） |
| 故障域 | 副本跨机架（`crush-failure-domain=rack`） |
| 快照 | RBD 快照/克隆（虚拟机备份） |
| 监控 | MGR Prometheus 指标 + Dashboard（OSD 健康/延迟） |
| 告警 | OSD down / PG 不一致 / 容量水位 |

### 5.2 常见坑

- **PG 数量规划错误**：PG 太多 → 内存/CPU 浪费；太少 → 分布不均（OSD 数×100 参考）；
- **网络不足**：复制流量是写入流量的 2~3 倍，千兆网是瓶颈；
- **小文件性能**：高并发小文件 IO（如日志/图片热点）不适合 Ceph → 对象场景用 MinIO 或上缓存层；
- **集群不健康时别操作**：PG 有异常就先修复（扩容/删池都受影响）；
- **版本升级**：Ceph 升级必须按官方顺序（跨大版本需先停）。
