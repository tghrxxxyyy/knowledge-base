# 协调者故障

> 对应 2PC/3PC 故障恢复研究与 Gray 关于事务系统的论述。

## 一、背景与挑战
协调者是 2PC 的中枢，其崩溃或网络隔离会直接威胁原子性与可用性。理解协调者故障的各类场景与恢复机制，是构建可靠分布式事务的关键。

## 二、核心原理
故障场景：
- 阶段一前崩溃：所有参与者未 prepare，可直接 abort。
- 阶段一后、阶段二前崩溃：参与者已 prepared 持锁，需协调者恢复后下发决定；恢复前阻塞。
- 阶段二发送中崩溃：部分已 commit，部分未知；恢复日志若记录了“已决定 commit”，则通知未决者提交。
恢复机制：协调者把“全局决定”先持久化到稳定存储，再发指令；重启后据日志重发。若日志未落盘即崩溃，则决定未知 -> 只能询问参与者或阻塞。

## 三、形式化 / 数学基础
协调者恢复不变量：一旦写入“decision = commit”日志，则必须保证所有参与者最终提交(即使原消息丢失，也要重发/查询)。
决策不确定性窗口：从“收到首个 yes”到“decision 日志落盘”之间崩溃，决定未知，参与者只能等待/打探。
协议安全性依赖：decision 日志在发 commit 指令前持久化(Write-Ahead)。

## 四、代码实现
```python
def coordinator_recover(log):
    decision = log.read_decision(tx)   # 从稳定存储读
    if decision is None:
        return "UNKNOWN"               # 需询问参与者
    for p in participants:
        p.resend(decision)             # 重发最终指令
    return decision
```

## 五、与其他技术对比
- 3PC 用 PreCommit 降低“决定未知”窗口但仍需假设。
- 共识方案：把“决定”本身通过 Raft 复制，协调者无单点，天然容错。

## 六、常见误区
- 误区：协调者重启总能知道决定。若决定未落盘则不知。
- 误区：新协调者随意重发。重发必须基于已持久化的同一决定，不能重新投票。

## 九、演进与趋势
“用 Raft 复制事务协调状态”让协调者无状态/可随时切换，是 Spanner 等系统的做法。

## 十、小结
协调者故障把 2PC 的阻塞与不确定性暴露无遗；决策日志先落盘、重启重发，或改用共识复制协调状态，是可行的缓解路径。
