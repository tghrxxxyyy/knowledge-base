# 两阶段提交

> 对应 Birman & Lynch《Atomic Broadcast》(背景) 与 Gray《Notes on Data Base Operating Systems》(1978) 提出的 2PC。

## 一、背景与挑战
单机事务靠日志与锁保证 ACID。跨多个数据库/资源管理器(XA)时，需要协议让所有参与者“要么全提交、要么全回滚”，2PC 是最经典的阻塞式原子提交协议。

## 二、核心原理
角色：协调者(Coordinator) + 若干参与者(Participants)。
阶段一 准备(Voting)：
1. 协调者发 prepare 给所有参与者。
2. 参与者写 undo/redo 日志，锁定资源，若可提交则回 yes，否则回 no，并进入“待决(prepared)”状态(不释放锁)。
阶段二 提交/中止(Commit)：
3. 协调者若收齐 yes，发 commit；否则发 abort。
4. 参与者执行后释放锁，回 ack。
关键：参与者在 prepared 后必须能提交或中止，直到收到协调者最终指令(通过日志保证可恢复)。

## 三、形式化 / 数学基础
原子性不变量：不存在参与者子集提交、另一子集中止的最终状态。
提交条件：协调者仅在所有参与者投 yes 后才进入 commit；任何 no/超时 -> abort。
参与者 prepared 状态持久化，保证重启后仍可按协调者最终决定执行(即使协调者消息丢失，也需询问/等待)。

## 四、代码实现
```python
def coordinator_prepare(parts, tx):
    votes = [p.prepare(tx) for p in parts]   # 写日志并锁资源
    if all(votes):
        for p in parts: p.commit(tx)         # 阶段二
        return "COMMITTED"
    else:
        for p in parts: p.abort(tx)
        return "ABORTED"
```

## 五、与其他技术对比
- 2PC 保证强原子性，但阻塞且协调者单点。
- 相比 Saga：Saga 用补偿而非锁，非阻塞但只最终一致。

## 六、常见误区
- 误区：2PC 不会阻塞。参与者在 prepared 后等协调者，协调者挂则永久阻塞(锁不释放)。
- 误区：2PC 能自动容错。需配合超时与恢复日志，否则卡死。

## 九、演进与趋势
XA 事务在微服务中因阻塞与长事务问题被 Saga/TCC 取代；但数据库内核仍大量使用 2PC 做内部提交。

## 十、小结
2PC 以“准备+提交”两阶段实现跨资源原子提交，强一致但阻塞且依赖协调者，是分布式事务的经典基石。
