# 2PC 阻塞与超时

> 对应 Gray《Notes on Database Operating Systems》(1978) 关于 2PC 阻塞问题的分析。

## 一、背景与挑战
2PC 的最大缺陷是“阻塞”：在关键阶段若协调者崩溃或网络分区，参与者卡在 prepared 状态，持有锁不放，事务无法推进，系统可用性受损。

## 二、核心原理
阻塞发生点：
- 阶段二协调者发出 commit 前崩溃：部分参与者已提交，部分仍在 prepared，且不知道决定 -> 必须等待协调者恢复(否则可能错误 abort 造成不一致)。
- 若协调者用“先持久化决定日志再发指令”可被恢复，但恢复前参与者仍阻塞。
超时处理：参与者超时未收到阶段二指令，不能单方面 abort(因他人可能已提交)，只能：
  (a) 阻塞等待协调者恢复；或
  (b) 发起“终止协议/查询”向其他参与者打听决定(若有人已提交则提交，全为 prepared 才可 abort)。
这正体现 2PC 无法在非阻塞下解决协调者故障。

## 三、形式化 / 数学基础
F 个协调者/参与者故障时，2PC 在 1 个协调者 + F 参与者配置下仍可能阻塞；理论上需 3PC 或共识才能避免阻塞(但无法同时满足同步假设外的完全非阻塞)。
不可单边决策：参与者在不知全局决定时，abort 可能与已 commit 冲突 -> 破坏原子性。

## 四、代码实现
```python
def participant_on_timeout(prepared, peers):
    # 不能单方面 abort，需打听他人状态
    decisions = [p.ask_decision() for p in peers]
    if any(d == "COMMITTED" for d in decisions):
        return "COMMIT"          # 跟随已提交
    if all(d == "PREPARED" for d in decisions):
        return "ABORT"           # 无人提交才可中止
    return "BLOCK"               # 仍不确定，继续等
```

## 五、与其他技术对比
- 3PC 通过引入预提交阶段与超时推进，减少阻塞(但需同步时钟假设)。
- Paxos/Raft 做原子提交(如 Spanner)从根本避免协调者单点阻塞。

## 六、常见误区
- 误区：参与者超时可自行 abort。可能与其他已提交者冲突。
- 误区：2PC 在任意故障下都能进展。关键阶段会阻塞。

## 九、演进与趋势
用共识(Raft/Paxos)做原子提交(如 Spanner)消除协调者阻塞；3PC 作为理论上的非阻塞近似。

## 十、小结
2PC 的阻塞源于“协调者故障下参与者无法安全单边决策”，这是其协议结构的根本限制，催生了 3PC 与共识方案。
