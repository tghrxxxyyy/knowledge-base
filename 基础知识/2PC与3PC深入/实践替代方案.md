# 2PC 实践替代方案

> 对应 Kleppmann《DDIA》第 9 章“Distributed Transactions and Consensus”及微服务事务实践。

## 一、背景与挑战
2PC 阻塞、协调者单点、长事务锁资源，难以适配高并发与微服务。实践中常以“最终一致 + 补偿”或“共识”替代强原子提交。

## 二、核心原理
替代方案：
- Saga：把长事务拆为一系列本地事务，每步有补偿(compensation)；失败则反向执行补偿，达到最终一致(非隔离)。
- TCC(Try-Confirm-Cancel)：Try 预留资源，Confirm 提交或 Cancel 释放，业务层实现三动作。
- 基于消息队列：本地事务 + 可靠事件(事务消息/Outbox)，消费者幂等处理。
- 共识提交：用 Raft/Paxos 复制提交决定，避免协调者单点(如 Spanner TrueTime + 2PC 但协调状态复制)。
选择：强一致短事务用 2PC；长事务/跨服务用 Saga/TCC + 幂等。

## 三、形式化 / 数学基础
Saga 正确性与“可补偿性”相关：每个正向步骤 s_i 有逆 c_i，失败序列执行 c_{n-1}...c_1 恢复。
隔离性缺失：Saga 默认无隔离，需用“语义锁/交换式更新”减少脏读/丢失更新。
幂等：消息消费必须幂等(用去重表/版本)以容忍重投。

## 四、代码实现
```python
# Saga 编排(简化)
def saga(steps):
    done = []
    for s in steps:
        if not s.action():
            for c in reversed(done): c.compensate()  # 补偿回滚
            return False
        done.append(s)
    return True
```

## 五、与其他技术对比
- 2PC：强一致、阻塞、短事务。
- Saga/TCC：非阻塞、最终一致、适合长事务与跨服务。
- 共识提交：强一致且容错，但实现复杂。

## 六、常见误区
- 误区：Saga 等于 ACID 事务。它只保证最终一致，无隔离。
- 误区：消息队列自动幂等。需应用层去重。

## 九、演进与趋势
Saga 编排框架、TCC 框架与 CDC 驱动的可靠事件成为微服务事务主流。

## 十、小结
实践中以 Saga/TCC/消息队列(最终一致+补偿)或共识提交替代 2PC，在可用性与一致性间取得更适合分布式服务的平衡。
