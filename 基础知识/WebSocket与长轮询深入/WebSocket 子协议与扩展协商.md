# WebSocket 子协议与扩展协商

> 对应 RFC 6455 第 1.9/9 节子协议与扩展协商与 xiaolincoder/hello-http 协商说明。

## 一、背景与挑战
WebSocket 只提供「双向消息传输管道」，不规定消息的语义格式。若客户端与服务端对「消息里是什么」没有约定，应用层无法解析。为了让双方就消息格式达成一致（如 JSON-RPC、STOMP、MQTT），需要在握手阶段协商「子协议（subprotocol）」；而「扩展（extension）」用于可选能力（如 per-message 压缩）。协商失败不应悄无声息地建立一条「双方各说各话」的连接。

子协议的本质是「应用层内容类型协商」：就像 HTTP 用 Content-Type 约定媒体类型，WebSocket 用子协议约定消息格式，使同一个连接上的双方对「如何解析 payload」达成共识。

没有协商机制的后果很现实：客户端发二进制、服务端按文本解析，或双方对字段命名理解不同，都会造成难以定位的「静默错误」。把语义协商显式化，是分布式协议设计的基本功。

## 二、核心原理
客户端在握手请求中通过 `Sec-WebSocket-Protocol` 提供候选子协议列表（逗号分隔）；服务端从中「选一个」回显在同一头部，表示就采用该子协议。扩展通过 `Sec-WebSocket-Extensions` 协商，可带参数键值对（如 `permessage-deflate; client_max_window_bits=10`）。

若客户端列的子协议服务端一个都不支持，服务端可省略该头部（连接仍建立但无子协议约定）或直接返回 400。扩展未协商则不使用，是可选的。客户端必须能处理「服务端不返回任何子协议」的情形，并据此决定是继续还是报错。

协商发生在握手阶段、一次性完成；握手之后不再改变。这意味着协议版本演进必须靠「新增子协议名」而非「在连接中途切换」。

## 三、形式化与数学基础
协商是集合交集运算：设客户端候选集 $S_c$、服务端支持集 $S_s$。服务端选 $s \in S_c \cap S_s$ 返回；若交集为空则协商失败（不返回该头部或 400）。

$$ s = \text{choose}(S_c \cap S_s),\quad \text{失败当且仅当 } S_c \cap S_s = \varnothing $$

扩展则是带参能力声明，可表示为键值对集合 $E = \{(k_i, v_i)\}$，双方就每个扩展的可选参数达成一致才启用。子协议与扩展正交：子协议管「消息语义」，扩展管「传输增强」。注意子协议是「单选」，扩展可「多选」，二者语义空间不同。

当扩展参数是数值时（如窗口位数），通常取双方支持的更小值，即 $\min(v_c, v_s)$，以兼容较弱一方。

扩展协商还有一个容易被忽略的点：permessage-deflate 同时提供「无上下文接管」与「有上下文接管」两种模式，前者每条消息独立压缩、省内存但压缩率低，后者跨消息复用压缩上下文、压缩率高但状态更复杂。

某些客户端只声明扩展名而不带参数，此时服务端应使用自己支持的默认参数回显，并在两端都能处理该默认值时启用。

子协议名是大小写敏感的（RFC 规定为 token），实现中不应做大小写归一化，否则可能与对端不匹配。

## 四、代码实现
```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Protocol: chat, superchat
Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits=10
Sec-WebSocket-Version: 13
```
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Protocol: chat
Sec-WebSocket-Extensions: permessage-deflate
```

服务端若不支持任一候选子协议，按 RFC 应返回 400 并在响应中列出自己支持的项；客户端据此向用户报错而非静默连接。扩展参数（如 window_bits）需双方取交集（取较小值）以避免解压失败。

## 五、与其他技术对比

| 机制 | 层级 | 作用 | 可否多选 |
| --- | --- | --- | --- |
| HTTP Accept/Content-Type | 表示层 | 媒体类型协商 | 否（单类型） |
| WS 子协议 | 应用语义 | 消息格式约定 | 服务端只选一个 |
| WS 扩展 | 传输增强 | 压缩等 | 可多个 |
| gRPC Content-Type | 应用语义 | 标识 proto 服务 | 单服务 |
| SSE | 应用语义 | 事件流格式 | 否 |

HTTP 内容协商用于媒体类型；WS 子协议用于应用消息格式，层级不同。gRPC 用 HTTP/2 的 Content-Type 标识 proto 服务，思路类似但机制不同——gRPC 还绑定了特定的帧编码（length-prefixed），而 WS 子协议只约定「消息如何解析」。

## 六、常见误区
- 误区一：子协议影响传输。它只约定应用语义，不改变帧格式。
- 误区二：可协商多个子协议。服务器只能选一个返回，连接只用那一个。
- 误区三：扩展必选。扩展可选，未协商则不使用；客户端必须能处理「无扩展」情形。
- 误区四：Version 13 以下可用。RFC 6455 规定版本 13，旧版本应被拒。
- 误区五：子协议自动校验消息。它只是约定，不强制校验消息是否符合该格式，解析错误仍由应用层处理。
- 误区六：扩展参数可各自取最大值。窗口位数等参数须取交集（较小值），否则解压会失败。
- 误区七：服务端可以静默忽略不支持的子协议。应显式拒绝或省略头部，让客户端可感知。

## 七、与开源书·权威来源对应
RFC 6455 第 1.9 与第 9 节定义子协议与扩展；xiaolincoder/hello-http 给双子协议示例；Kleppmann《DDIA》讨论接口/协议版本兼容；MDN 文档列出常见子协议（如 `graphql-ws`、`wamp`）。`socket.io` 等库在子协议之上还定义自己的私有握手元数据，但底层仍遵循 RFC 协商框架。

具体子协议注册与浏览器支持情况以权威文档与官方最新说明为准。

## 八、面试题
- 问：子协议与扩展区别？答：子协议约定消息语义，扩展增强传输（如压缩）。
- 问：协商失败会怎样？答：可省头部（无约定）或返回 400，连接建立与否取决于服务端。
- 问：为何子协议只选一个？答：一条连接只有一种消息格式，避免解析歧义。
- 问：permessage-deflate 是什么？答：基于 deflate 的每消息压缩扩展，减小文本体积。
- 问：扩展参数如何协商？答：取双方支持的交集（如 window_bits 取较小值）。
- 问：服务端不支持客户端候选子协议时可否静默？答：不建议，应显式拒绝或省略并让客户端可判断。
- 问：握手后还能协商吗？答：不能，协商在握手阶段一次性完成。

## 九、演进与趋势
基于 WebSocket 的子协议生态（WAMP、Socket.IO 自有协议、graphql-ws）持续演进；压缩扩展 permessage-deflate 已成主流以减小文本消息体积。HTTP/3 上 WebSocket 通过 CONNECT 扩展承载，子协议/扩展语义保持不变。

浏览器还要求安全上下文（HTTPS）下才能使用 wss，推动子协议层也向安全默认演进。相关规范与实现以官方最新文档为准。

## 十、小结
子协议与扩展在握手阶段完成能力协商：子协议约定消息语义、扩展增强传输能力，二者让 WebSocket 从「裸管道」变为可扩展的应用传输层。理解「子协议单选、扩展多选、与 HTTP 内容协商同构」的关系，有助于设计可互操作、可演进的实时协议。
