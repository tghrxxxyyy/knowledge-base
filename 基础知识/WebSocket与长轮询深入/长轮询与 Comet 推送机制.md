# 长轮询与 Comet 推送机制

> 对应 Kurose & Ross《Computer Networking》关于 HTTP 持久连接与 xiaolincoder/hello-http 中推送方案的对比。

## 一、背景与挑战
在 WebSocket 普及前，网页需要服务端主动推送（如聊天、行情）。受 HTTP 请求-响应模型限制，只能由客户端发起请求。Comet 是一类「服务端推」的 hack 技术，长轮询是其中最稳健的一种。

## 二、核心原理
长轮询：客户端发起 HTTP 请求，服务器不立即响应，而是hold 住连接直到有数据可发或超时，才返回响应；客户端收到后立即再发起下一次请求，从而形成「持久近似」的通道。相比普通轮询（固定间隔频繁空请求）显著减少无效请求。

## 三、形式化与数学基础
设普通轮询间隔为 T，平均无谓请求占比为 (T - t_data)/T，其中 t_data 为有数据的响应占比。长轮询把空轮询压缩到几乎为零，仅在有事件或超时（典型 30–60s）时才完成一次往返，请求数降至 O(事件数 + 超时次数)。

## 四、代码实现
```python
# 服务端伪代码：阻塞直到有消息或超时
def long_poll():
    msg = wait_for_message(timeout=30)
    return Response(msg or "{}", status=200)
# 客户端收到即重连
fetch("/poll").then(reconnect)
```

## 五、与其他技术对比
与普通轮询相比省带宽、低延迟；与 WebSocket 相比，长轮询仍受 HTTP 头部开销与每次重建请求限制，且单向为主。SSE 是标准的服务端单向推送，比长轮询更轻量。

## 六、常见误区
误区一：长轮询会一直占用一个线程——阻塞式实现确实会，需用异步/事件驱动（如 epoll）避免线程耗尽。误区二：长轮询等于 WebSocket——两者协议模型不同。误区三：超时即失败——超时是正常重连信号。

## 九、演进与趋势
随着 HTTP/2 多路复用与 WebSocket/SSE 成熟，纯长轮询新项目已较少，但在受限环境（仅标准 HTTP 代理）中仍有价值。

## 十、小结
长轮询通过「服务器hold 请求直到有数据」逼近服务端推送，是 WebSocket 之前的实用方案，代价是 HTTP 头部与连接重建开销。
