# 长轮询与 Comet 推送机制

> 对应 Kurose & Ross《Computer Networking》HTTP 持久连接与 xiaolincoder/hello-http 推送方案对比。

## 一、背景与挑战
在 WebSocket 普及前，网页需要服务端主动推送（聊天、行情、通知）。但 HTTP 是请求-响应模型，只能由客户端发起。Comet 是一类「服务端推」的 hack 技术统称，长轮询（long-polling）是其中最稳健、兼容性最好的一种。它要解决的核心矛盾：在不改变 HTTP 语义、不依赖特殊协议的前提下，逼近「服务端能主动、及时地通知客户端」。

Comet 还包括 iframe 流、XHR 流等变体，但长轮询因「每个请求终会结束、易于穿越代理」而成为生产首选。它是对「HTTP 无推送」这一限制的务实妥协，而非理想方案。

这也是一个经典的工程案例：在协议不支持的条件下，用「时间维度的巧妙占用」换取新的能力，代价是连接与资源的持续消耗。

## 二、核心原理
长轮询流程：客户端发起一个 HTTP 请求，服务端不立即响应，而是「hold 住」连接，直到有数据可发或达到超时，才返回响应并关闭该请求；客户端一收到响应（或超时被关闭），立即发起下一次请求，如此循环，形成「近似持久」的通道。

相比普通轮询（固定间隔频繁发空请求），长轮询把「无效空请求」压缩到几乎为零：仅在有事件或超时（典型 30~60s）时才完成一次往返，因此请求数降至 $O(\text{事件数} + \text{超时次数})$。

服务端侧的关键是用事件驱动模型而非阻塞线程：否则每个挂起请求占用一个线程，连接一多就耗尽资源。这也是长轮询必须与异步框架一起使用的原因。

## 三、形式化与数学基础
设普通轮询间隔为 $T$，平均有数据响应的占比为 $p$，则空轮询占比 $(1-p)$，单位时间内无效请求约 $(1-p)/T$。长轮询把空往返压到仅由超时触发，请求频率约

$$ f_{\text{long}} \approx \frac{1}{\max(t_{data},\, T_{timeout})} $$

$t_{data}$ 为平均事件间隔。期望带宽节省接近 $(1-p)$ 比例的轮询开销。代价是每次请求仍带 HTTP 头部（含 Cookie），且需重建连接（HTTP/1.1 可复用 TCP 但仍是新请求）。若事件突发密集，长轮询会退化为「一连串短请求」，此时优势减弱。

另一个约束来自中间设备：NAT/代理的空闲超时记为 $T_{idle}$，应保证 $T_{timeout} < T_{idle}$，否则连接会在服务端主动返回前被静默切断。

在负载均衡下，长轮询的「hold」会长期占用一个后端连接，需确保 LB 的空闲超时大于服务端 hold 超时，否则 LB 会先断开，导致客户端频繁重连、服务端空转。

与连接数相关的还有「连接复用」：HTTP/1.1 keep-alive 可让重连复用同一 TCP，而 HTTP/2 多路复用下长轮询的并发挂起请求会共享一条连接，需注意流数量上限。

## 四、代码实现
```python
import asyncio, json

# 服务端伪代码：异步等待事件或超时
async def long_poll(request):
    try:
        msg = await asyncio.wait_for(wait_for_message(), timeout=30)
    except asyncio.TimeoutError:
        return Response("{}", status=200)      # 超时，客户端重连
    return Response(json.dumps(msg), status=200)

# 客户端：收到即重连，形成持久通道
async def loop():
    while True:
        resp = await fetch("/poll")
        handle(await resp.json())
```

生产实现应使用异步框架（如 asyncio、Tornado、Node 事件循环）以单线程支撑大量挂起请求；数据库可用「列表/通道」（如 Redis pub/sub、PostgreSQL NOTIFY）解耦「事件产生」与「请求 hold」。

超时应略小于客户端/代理的 idle 超时，避免连接被中间件静默切断。

## 五、与其他技术对比

| 方案 | 延迟 | 带宽 | 方向 | 限制 |
| --- | --- | --- | --- | --- |
| 普通轮询 | 高（$\le T$） | 差（多空请求） | 单向 | 简单 |
| 长轮询 | 低 | 好 | 单向 | HTTP 头部/重建 |
| SSE | 低 | 好 | 单向 | 仅 GET 流 |
| WebSocket | 最低 | 最好 | 双向 | 需协议升级 |
| HTTP/2 Server Push | 低 | 好 | 服务端推资源 | 不推送应用事件 |

长轮询比普通轮询省带宽、低延迟；与 WebSocket 比，仍受 HTTP 头部与每次重建请求限制，且主要单向。SSE 是标准单向推送，比长轮询更轻量（单连接常驻、无重建）。

## 六、常见误区
- 误区一：长轮询一直占用一个线程。阻塞式实现确实会耗尽线程，须用异步/事件驱动（epoll、asyncio）避免。
- 误区二：长轮询等于 WebSocket。两者协议模型不同，长轮询仍是 HTTP 请求-响应。
- 误区三：超时即失败。超时是正常「重连信号」，应被客户端当作继续轮询的触发。
- 误区四：长轮询能双向。严格说请求方向与推送方向相反，双向需客户端另发请求。
- 误区五：hold 越久越好。过久会被代理/NAT 切断，应与超时、心跳配合。
- 误区六：服务端可无限 hold。必须有超时，否则连接泄漏、资源无法回收。
- 误区七：长轮询无需去重。重连瞬间可能重复投递，需要消息 ID 做幂等。

## 七、与开源书·权威来源对应
xiaolincoder/hello-http 对比轮询/长轮询/WebSocket；Kleppmann《DDIA》讨论轮询与流处理；Kurose & Ross 介绍 HTTP 持久连接如何支撑长请求；HTTP/1.1 的「持久连接 + 分块传输」是长轮询的底层支撑。

## 八、面试题
- 问：长轮询与普通轮询区别？答：长轮询 hold 请求直到有数据/超时，几乎无空请求。
- 问：为何需要超时？答：避免服务端无限 hold、连接泄漏，且让客户端周期性重连保持健康。
- 问：长轮询的服务器资源问题？答：阻塞实现耗线程，需异步事件驱动。
- 问：何时选长轮询而非 WebSocket？答：受限于仅标准 HTTP 代理、无法升级协议的环境。
- 问：长轮询如何解耦事件？答：用 Redis 通道/消息队列连接事件源与挂起请求。
- 问：超时应如何取值？答：略小于中间设备的空闲超时，避免被静默切断。
- 问：重连会不会丢消息？答：设计不当会重复或丢失，需消息 ID 与游标做幂等与续传。

## 九、演进与趋势
随着 HTTP/2 多路复用与 WebSocket/SSE 成熟，纯长轮询在新项目中已较少；但在受限环境（仅标准 HTTP 代理、企业防火墙不允许 Upgrade）仍有价值。SSE 常作为单向推送的轻量替代。

现代浏览器与边缘网络（CDN）对长连接的友好度提升，也使 WebSocket/SSE 成为默认推荐。相关方案选择以官方最新文档与具体网络环境为准。

## 十、小结
长轮询通过「服务器 hold 请求直到有数据」逼近服务端推送，是 WebSocket 之前的实用方案，代价是 HTTP 头部与连接重建开销，需用异步架构避免线程耗尽。理解它与轮询、SSE、WebSocket 的取舍，是选型实时通信方案的基础。
