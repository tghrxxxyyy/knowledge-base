# WebSocket 心跳与连接保活

> 对应 RFC 6455 第 5.5 节 ping/pong 控制帧与 xiaolincoder/hello-http 连接管理建议。

## 一、背景与挑战
长连接会经过 NAT、代理、负载均衡器等中间设备，这些设备常对「空闲连接」设超时（如 NAT 表项 30s~几分钟），到期即静默丢弃，导致一端以为连接还在、另一端已无表项（「半开连接」）。应用层需要心跳探测对端存活，避免向已死连接发送数据、或堆积半开连接耗尽资源。WebSocket 本身没有「连接保活」的强制机制，需应用层用控制帧实现。

若不心跳，最典型的故障是「夜晚空闲后早上第一条消息发不出去」——因为中间 NAT 表项早已过期，报文被无声丢弃。心跳正是为了持续「刷新」这些中间状态。

半开连接还会造成更隐蔽的问题：服务端以为客户端在线，继续为它维护会话与内存，长期累积导致资源泄漏。

## 二、核心原理
WebSocket 定义 ping（opcode 0x9）与 pong（opcode 0xA）控制帧。一方发送 ping，对端「必须尽快」回 pong，且 pong 的载荷原样回显 ping 的载荷。应用层常定时（如每 30s）发 ping，若在连续 k 个周期内未收到 pong，则判定连接失效并主动关闭。

也可依赖 TCP keepalive 作为更底层补充，但 TCP keepalive 默认关闭且周期长，不适合应用级快速失败。因此「应用层心跳」与「TCP keepalive」应各司其职：前者负责快速探活与业务级判断，后者负责更底层的内核级兜底。

服务端通常比客户端更适合主动发 ping，因为它需要管理大量连接、及时回收失效会话。

## 三、形式化与数学基础
设心跳间隔 $T_h$，允许连续丢失次数 $k$，则判定死连接的超时

$$ T_{dead} \approx k\cdot T_h $$

保活带宽开销为每 $T_h$ 一个控制帧，载荷通常 $\le 125$ 字节，带宽成本为 $O(1/T_h)$。合理取值需在「尽早发现死连接」与「不过度占用带宽/电量」间权衡：移动网络下 $T_h$ 常取 30~60s，且可随网络类型自适应。

若中间设备空闲超时为 $T_{idle}$，应保证 $T_h < T_{idle}$，否则心跳来不及刷新表项。一个保守做法是取 $T_h \approx T_{idle}/2$，留出抖动余量。

心跳设计还应考虑「双向」：客户端与服务端都可发 ping，但通常约定由一侧主导，避免两侧同时探测造成 pong 风暴。

判定死亡的另一个信号是「发送失败」：当底层 write 报错或长时间无 ACK，也应主动关闭并进入重连流程，而不只依赖 pong 超时。

## 四、代码实现
```python
import asyncio

async def heartbeat(ws, interval=30, max_miss=3):
    misses = 0
    while True:
        try:
            await ws.ping()                       # 发 ping
            await asyncio.wait_for(ws.recv_pong(), timeout=interval)
            misses = 0
        except Exception:
            misses += 1
            if misses >= max_miss:
                await ws.close()                  # 判定失效，关闭
                break
        await asyncio.sleep(interval)
```

注意：浏览器实现的 WebSocket 在客户端会自动响应 pong，但「发 ping」需应用层或库主动做；服务端主动 ping 更常见。另需注意 ping/pong 是控制帧，不计入应用消息，应用层不应把 pong 当作业务数据。

在服务端批量管理连接时，建议把「最后收到任意帧的时间」与心跳状态一并维护，便于快速定位是网络抖动还是对端进程卡死。

## 五、与其他技术对比

| 保活机制 | 层级 | 周期 | 及时性 |
| --- | --- | --- | --- |
| TCP keepalive | 传输层 | 默认长（常 2h） | 差 |
| WS ping/pong | 应用协议层 | 可配（秒级） | 好 |
| HTTP 长轮询重连 | 应用层 | 超时驱动 | 中 |
| 应用层业务心跳 | 应用层 | 可配 | 好（含业务状态） |
| QUIC PING 帧 | 传输层 | 可配 | 好 |

TCP keepalive 默认关闭且探测周期长，不适合应用级快速失败；WS ping/pong 位于协议层，及时且可携带应用状态。相比长轮询靠超时重建，WebSocket 心跳是「带确认」的活体探测，更可靠。

## 六、常见误区
- 误区一：ping 必须由客户端发。任一方都可发，服务端也可主动探活。
- 误区二：pong 可延迟。RFC 要求尽快回复（控制帧优先）。
- 误区三：心跳能探测应用卡死。只能探测连接存活，不保证业务逻辑健康（需应用层健康检查）。
- 误区四：心跳越频越好。过频浪费带宽与移动电量，且可能被中间设备误判为攻击。
- 误区五：pong 是业务消息。pong 是协议控制帧，不应被业务层消费。
- 误区六：心跳可以替代重连逻辑。判活只是第一步，还需指数退避重连与状态恢复。
- 误区七：只发 ping 不等 pong。必须等待 pong 或超时计数，否则无法判断对端是否存活。

## 七、与开源书·权威来源对应
RFC 6455 第 5.5.2/5.5.3 节规定 ping/pong 行为；xiaolincoder/hello-http 讨论代理超时；Kleppmann《DDIA》提及故障检测与超时（如 Φ-accrual 等）；MDN 文档说明浏览器对控制帧的处理。

Nginx 的 `proxy_read_timeout` / websocket 配置即针对此类空闲超时，需与心跳间隔匹配。具体配置项与默认值以官方最新文档为准。

## 八、面试题
- 问：ping/pong 作用？答：应用层探测连接存活，及时发现半开/死连接。
- 问：为何不能只靠 TCP keepalive？答：默认关且周期长，无法快速失败。
- 问：心跳间隔如何取舍？答：权衡及时性与开销，移动网络常 30~60s 并自适应，且须小于中间设备空闲超时。
- 问：半开连接是什么？答：一端以为连接还在、另一端表项已丢，发数据丢失。
- 问：心跳能替代健康检查吗？答：不能，只探连接不探业务逻辑。
- 问：为什么服务端发 ping 更常见？答：服务端需管理大量连接并及时回收失效会话。
- 问：pong 载荷有什么约定？答：应原样回显 ping 的载荷，便于匹配请求与响应。

## 九、演进与趋势
移动网络下「自适应心跳」（按网络类型/信号调整间隔）被广泛采用以省电；QUIC 的 PING 帧与 CONNECTION_CLOSE 提供传输层保活能力；服务网格（如 Envoy）也在 sidecar 层做连接健康检查，与应用心跳互补。

部分平台用「应用层最后收到消息时间」代替固定心跳，进一步省电。相关机制以官方最新文档为准。

## 十、小结
WebSocket 用心跳 ping/pong 在应用层维持连接存活、快速发现断连，是长连接服务稳定运行的必要机制；需配合合理的间隔与丢失容忍，且不能替代应用层健康检查。把心跳间隔设为小于中间设备空闲超时，是避免「夜间静默断连」的关键配置。
