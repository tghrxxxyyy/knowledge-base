# WebSocket 数据帧与掩码处理

> 对应 RFC 6455 第 5 节数据帧格式与 xiaolincoder/hello-http 的帧解析说明。

## 一、背景与挑战
握手后双方以二进制帧通信。帧格式需支持分片、多种数据类型（文本/二进制/控制帧）以及防缓存投毒的掩码。正确理解帧结构是编写兼容客户端/服务端的前提。

## 二、核心原理
帧首字节含 FIN（是否为消息最后分片）、opcode（0x1 文本、0x2 二进制、0x8 关闭、0x9 ping、0xA pong 等）。次字节最高位 MASK 表示是否掩码，后 7 位为载荷长度（126/127 时后续扩展为 16/64 位）。客户端发往服务端的帧必须掩码，掩码由 4 字节随机值 XOR 载荷得到，服务端收到后按相同掩码还原。

## 三、形式化与数学基础
设载荷字节为 P[i]，掩码键为 M[0..3]，还原公式 P'[i] = P[i] XOR M[i mod 4]。帧长度字段 L 的取值：L <= 125 直接用；L == 126 表示后续 2 字节无符号整数为长度；L == 127 表示后续 8 字节。

## 四、代码实现
```python
def unmask(payload, mask):
    return bytes(payload[i] ^ mask[i % 4] for i in range(len(payload)))
```

## 五、与其他技术对比
HTTP/2 用二进制帧但自带流多路复用与 HPACK 头部压缩，WebSocket 帧更简单且面向单条全双工消息流。SSE 直接发送文本事件，无需掩码。

## 六、常见误区
误区一：服务端也必须掩码——规范只要求客户端发服务端时掩码，服务端发客户端不掩码。误区二：opcode 决定整个消息类型——仅首片 opcode 有效，后续分片 opcode 为 0（continuation）。误区三：长度字段永远 1 字节——大消息需用 126/127 扩展。

## 七、与开源书/权威来源对应
RFC 6455 第 5.2/5.3 节定义帧格式与掩码动机（防止缓存投毒攻击）；xiaolincoder/hello-http 展示抓包帧结构；Kurose & Ross 在应用层介绍协议封装概念。

## 八、面试题

## 九、演进与趋势
因 WebSockets 常与 HTTP/2 共存，浏览器在 HTTP/2 连接上仍复用 WebSocket 的语义；未来在 HTTP/3/QUIC 上的承载方式继续标准化。

## 十、小结
WebSocket 帧以 FIN/opcode/长度/掩码描述消息，客户端发服务端强制掩码以防缓存污染，分片机制支持大消息流式传输。
