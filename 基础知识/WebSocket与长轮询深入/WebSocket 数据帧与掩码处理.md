# WebSocket 数据帧与掩码处理

> 对应 RFC 6455 第 5 节数据帧格式与 xiaolincoder/hello-http 帧解析说明。

## 一、背景与挑战
握手成功后，双方不再交换 HTTP 报文，而是以二进制「帧（frame）」通信。帧结构需支持：消息分片（大消息拆多帧）、多种数据类型（文本/二进制/控制帧）、以及防缓存投毒的掩码。正确理解帧结构是编写兼容客户端/服务端、以及排查粘包/分片问题的前提。

很多自研 WebSocket 网关的 bug 源于对帧字段（FIN、opcode、长度扩展、掩码）解析不完整，例如忽略 126/127 长度扩展导致大消息截断，或错误要求服务端掩码导致客户端断连。逐字段吃透是正确实现的关键。

另一个常见问题是没处理「粘包/半包」：TCP 是字节流，一次 recv 可能拿到半个帧或多个帧，必须自己按长度字段切分并缓存残包。

## 二、核心原理
帧首字节含 FIN（是否为消息最后分片）与 opcode（0x1 文本、0x2 二进制、0x8 关闭、0x9 ping、0xA pong 等）。次字节最高位 MASK 表示是否掩码，后 7 位为载荷长度：$\le 125$ 直接用；126 表示后续 2 字节为 16 位无符号长度；127 表示后续 8 字节为 64 位长度。

客户端发往服务端的帧必须掩码：掩码由 4 字节随机值 XOR 载荷得到，服务端收到后按相同掩码还原。服务端发客户端不掩码。若服务端收到未掩码的客户端帧（或客户端收到被掩码的服务端帧），按 RFC 应关闭连接。

分片时仅首片 opcode 有效（如 0x1），后续分片 opcode $=0$（continuation），FIN 仅在最后一片置 1；控制帧不得分片。

## 三、形式化与数学基础
设载荷字节为 $P[i]$，掩码键为 $M[0..3]$，还原公式：

$$ P'[i] = P[i] \oplus M[i \bmod 4] $$

帧长度字段 $L$ 取值：$L \le 125$ 直接为长度；$L = 126$ 则后续 2 字节无符号整数为长度；$L = 127$ 则后续 8 字节。掩码的动机（RFC 6455 附录）是防止恶意网页通过代理缓存污染：若浏览器发未掩码帧，攻击者可构造被代理缓存的「伪造响应」。

掩码键由客户端随机生成，每次发送独立，保证不可预测。注意掩码不提供任何机密性——密钥随帧明文传输，真正的机密性依赖 wss/TLS。

## 四、代码实现
```python
def unmask(payload, mask):
    # 还原被掩码的载荷：逐字节异或 4 字节掩码键
    return bytes(payload[i] ^ mask[i % 4] for i in range(len(payload)))

def parse_frame(buf):
    fin = (buf[0] & 0x80) != 0
    opcode = buf[0] & 0x0F
    masked = (buf[1] & 0x80) != 0
    length = buf[1] & 0x7F
    off = 2
    if length == 126:
        length = int.from_bytes(buf[2:4], "big")
        off = 4
    elif length == 127:
        length = int.from_bytes(buf[2:10], "big")
        off = 10
    mask = buf[off:off + 4] if masked else None
    body = buf[off + (4 if masked else 0): off + (4 if masked else 0) + length]
    if masked:
        body = unmask(body, mask)
    return fin, opcode, length, body
```

解析时还需处理 RSV1-3 位（用于扩展协商，如 permessage-deflate 用 RSV1）、以及控制帧（ping/pong/close）不允许分片、且载荷 $\le 125$ 字节等约束，违反应关闭连接。

在流式解析器中，应把「已读但不足一帧」的字节缓存到缓冲区，凑齐后再解析，避免半包误判。

## 五、与其他技术对比

| 协议 | 帧 | 多路 | 掩码 | 压缩 |
| --- | --- | --- | --- | --- |
| WebSocket | 简单帧 | 否（应用层自建） | 客户端→服务端强制 | permessage-deflate |
| HTTP/2 | 二进制帧 | 是（流 ID） | 否 | HPACK |
| SSE | 文本事件 | — | 否 | — |
| QUIC | 多类型帧 | 是（流） | 否 | 可选无序 |

HTTP/2 用二进制帧且自带流多路复用与 HPACK 头部压缩；WebSocket 帧更简单、面向单条全双工流；SSE 直接发送文本事件，无需掩码。WebSocket 帧的简洁性是以「无内建多路/无内建压缩」为代价，由扩展与应用层补足。

## 六、常见误区
- 误区一：服务端也必须掩码。规范只要求客户端发服务端时掩码，服务端发客户端不掩码（且服务端若发掩码帧，RFC 6455 要求客户端关闭连接）。
- 误区二：opcode 决定整个消息类型。仅首片 opcode 有效，后续分片 opcode 为 0。
- 误区三：长度字段永远 1 字节。大消息需 126/127 扩展。
- 误区四：掩码用于加密。掩码只是异或、密钥明文传输，不提供任何机密性（机密性靠 wss/TLS）。
- 误区五：控制帧可分片。RFC 规定 ping/pong/close 不得分片，且载荷不超过 125 字节。
- 误区六：一次 recv 等于一帧。TCP 是字节流，必须自行切分并处理半包/粘包。
- 误区七：RSV 位可以忽略。使用扩展时 RSV 位有确定含义，误判会导致解压或解析失败。

## 七、与开源书·权威来源对应
RFC 6455 第 5.2/5.3 节定义帧格式与掩码动机（防止缓存投毒）；xiaolincoder/hello-http 展示抓包帧结构；Kurose & Ross 在应用层介绍协议封装；MDN 给出逐字节解析示例。

主流库（如 `websockets`、`ws`）的帧编解码实现均严格遵循上述字段布局，可作为参考；具体实现细节以官方最新文档为准。

## 八、面试题
- 问：WebSocket 掩码作用？答：防缓存投毒攻击，非加密。
- 问：FIN 与分片如何配合？答：仅最后一片 FIN$=1$，中间片 opcode$=0$ 续传。
- 问：ping/pong 控制帧用途？答：保活与探活，控制帧可插入数据帧间。
- 问：为何浏览器强制掩码？答：防止网页通过代理制造被缓存的伪造响应。
- 问：126/127 长度字段含义？答：126→后续 2 字节长度，127→后续 8 字节长度。
- 问：如何处理粘包/半包？答：按长度字段切分，缓存不足一帧的残余字节。
- 问：RSV 位何时有意义？答：协商了相应扩展时（如 permessage-deflate 用 RSV1），否则应为 0。

## 九、演进与趋势
WebSocket 常与 HTTP/2 共存，浏览器在 HTTP/2 连接上复用 WebSocket 语义；HTTP/3/QUIC 上的承载方式继续标准化（CONNECT 扩展）。permessage-deflate 压缩扩展已广泛支持以减小文本载荷，并结合 RSV1 位协商。

帧格式本身稳定，演进主要在扩展与安全约束（如强制安全上下文）。相关规范以官方最新文档为准。

## 十、小结
WebSocket 帧以 FIN/opcode/长度/掩码描述消息，客户端发服务端强制掩码以防缓存污染，分片机制支持大消息流式传输；理解帧结构是互操作实现的基础。掌握 126/127 长度扩展、分片续传与控制帧约束，是写出健壮 WebSocket 解析器的前提。
