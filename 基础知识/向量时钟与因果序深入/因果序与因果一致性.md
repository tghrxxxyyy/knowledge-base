# 因果序与因果一致性

> 对应 Lamport 1978（happened-before 与因果）与 Shapiro 2011（CRDTs，因果一致复制）以及 Kleppmann DDIA 第5章。

## 一、背景与挑战
强一致（线性一致）要求所有读看到同一全局最新写，代价是每次操作都要跨副本共识，可用性与延迟受限。最终一致只保证「无新写后全体收敛」，却可能让人读到违反直觉的状态：例如先看到一条评论的回复，却还没看到被回复的原帖——这破坏了因果（causal）关系。因果一致性（Causal Consistency）介于二者之间：它不强求全局最新，但保证所有副本以相同的顺序尊重「有因果依赖的操作」，从而杜绝「看见结果却看不见原因」的异常。

更形式地说，因果一致只要求「有因果关系的操作按因果序可见」，并发操作则允许任意（但全局一致）的排序。这比线性一致弱、比纯最终一致强，是在「可用性优先」与「用户可接受的语义」之间被广泛采用的中间点，也是 COPS、Bayou、CRDT 复制系统的共同基础。真实系统如社交feed、协同编辑都依赖因果一致来保证「不乱序」。

因果一致还有一个重要的工程优势：它**不需要等待全局共识**。因果依赖信息随操作（消息）携带，副本只需在本地判断「依赖是否齐备」即可决定是否应用，无需跨节点协调。因此因果一致既能避免「看果不见因」的荒谬，又保留了分区可用性（AP 语义），是「弱一致但语义合理」的最佳落点。

## 二、核心原理
因果序（causal order）由 happened-before 关系「$\to$」定义：
- 若进程先写 x 后读 x 再写 y，则这些操作间存在因果边。
- 若操作 a 影响了 b（b 读取了 a 的结果，或 a、b 同进程且 a 在前），则要求每个副本必须先应用 a 再应用 b。
- 两个无因果关系的（并发）操作可以任意排序，只要所有副本采用同一顺序。
判定工具正是向量时钟：维护每个操作的因果历史向量，应用前检查依赖已就位。需要区分「因果一致」与更弱的「读己之写」「单调读」等会话级保证——因果一致蕴含这些，但不止于此。

happened-before 的三条规则需完整掌握：同一进程内 a 先于 b 则 $a \to b$；消息发送先于其接收；关系具有传递性。任何不满足该关系的两操作即「并发」，系统对它们的顺序不作因果要求。

因果一致的两个层次：一是**因果序（causal order）**，即应用顺序尊重 happened-before；二是**因果收敛**，即并发操作最终在所有副本上收敛到同一状态。仅有序而无收敛会留下永久分歧；仅有收敛而无序会出现「看见回复却看不到原帖」。二者叠加才是工程可用的因果一致系统。

## 三、形式化与数学基础
对操作 op，其因果依赖历史记为向量 $V_{op}$。副本本地已应用向量为 $L$。操作可应用（causally ready）当且仅当：
$$\forall j: V_{op}[j] \le L[j]$$
即 op 的所有因果前驱都已在本地应用。两个并发操作 $op_1, op_2$ 满足 $V_{op_1}$ 与 $V_{op_2}$ 互不 dominates，副本可任意选定其一先应用，但一旦选定，所有副本须一致（如按全局唯一 id 定序）。因果一致可形式化为：对任意因果相关操作对，所有进程看到的应用顺序相同。并发操作则要求收敛到同一最终状态（最终一致的一部分），即系统同时具备「因果序」与「最终收敛」两属性。

与线性一致的强度关系可这样定位：线性一致 $\Rightarrow$ 顺序一致 $\Rightarrow$ 因果一致 $\Rightarrow$ 最终一致。因果一致所需的通信量为 $O(1)$ 每条操作（仅携带向量元数据），而线性一致需每操作一轮 quorum 通信，这是其可用性与延迟优势的根源。

因果「就绪」检查的代价是可能长时间缓冲：若某依赖永远不到达（例如依赖的产生者已经下线且数据丢失），操作会一直挂起。工程上需设定超时或提供「反熵」机制补齐缺失依赖。

## 四、代码实现
```python
# 因果就绪检查：依赖未到齐则缓冲
def try_apply(op, local, buffer):
    if all(op.deps[j] <= local[j] for j in range(len(local))):
        apply(op)
        local[op.node] = max(local[op.node], op.clock)
        return True
    buffer.append(op)  # 暂缓，等依赖到达
    return False

# 并发操作全局定序（避免副本间不一致）
def total_order(op1, op2):
    # 按 (node, clock) 唯一序破平，保证所有副本一致
    return (op1.node, op1.clock) < (op2.node, op2.clock)
```

依赖到达后应重新扫描缓冲，把「由新到达操作解锁」的待处理操作一并应用（连锁解锁）：

```python
def on_apply(self, op, local, buffer):
    try_apply(op, local, buffer)
    progressed = True
    while progressed:                       # 反复扫描，直到本轮无新进展
        progressed = False
        for b in list(buffer):
            if all(b.deps[j] <= local[j] for j in range(len(local))):
                apply(b)
                local[b.node] = max(local[b.node], b.clock)
                buffer.remove(b)
                progressed = True           # 解锁了新的操作，需再扫一轮
```

## 五、与其他技术对比
| 维度 | 线性一致 | 因果一致 | 最终一致 | 顺序一致 |
| --- | --- | --- | --- | --- |
| 读到全局最新 | 是 | 否 | 否 | 否 |
| 不违反因果 | 是 | 是 | 不一定 | 是（按某全序） |
| 跨副本共识需求 | 强 | 弱 | 无 | 中 |
| 可用性/延迟 | 差 | 中 | 好 | 中 |
| 每操作通信开销 | 一轮 quorum | $O(1)$ 元数据 | $O(1)$ | 需全序广播 |
| 可实现于分区两侧 | 否 | 是 | 是 | 否（需全序） |

## 六、常见误区
1. 把「最终一致」与「违反因果」等同。其实可构造因果一致的最终一致系统（如 COPS、CRDT 复制），二者并不矛盾。
2. 把因果一致当成「读己之写」。读己之写是更弱的会话保证，因果一致蕴含它但不止于此。
3. 以为向量时钟一装就有因果一致。还需在应用层缓冲未就绪操作、并保证并发操作全局定序。
4. 以为因果一致能消除写冲突。它只保证因果顺序，并发写的合并仍需版本向量/CRDT。
5. 以为因果一致等于顺序一致。顺序一致要求存在某全序尊重程序序，比因果一致更强且更难实现。
6. 忽略「依赖永不满足」的风险。缺失依赖会导致操作无限缓冲，需超时或反熵兜底。
7. 忽略元数据的传播成本。因果历史随操作传播，长期运行的系统需做剪枝（否则元数据无界增长）。

## 八、面试题
1. 因果一致相比线性一致弱在哪、强在哪？
   要点：不保证全局最新（弱），但保证不违反因果且不要求共识（强可用）。
2. 如何用向量时钟维护因果一致？
   要点：每个操作带因果历史向量，副本仅在依赖齐备时应用，并发操作按全局序定序。
3. 因果一致能否避免写冲突？与冲突检测的关系？
   要点：不消除并发写冲突，只保证因果顺序；并发写的合并仍需版本向量/CRDT。
4. 因果一致与读己之写谁的保证更强？
   要点：因果一致更强，它蕴含读己之写、单调读等会话保证。
5. 因果一致与最终一致如何共存？
   要点：因果一致在最终一致之上加「因果序约束」，二者叠加即「因果一致 + 收敛」。
6. 因果依赖永远不到达会怎样？
   要点：操作会被无限缓冲；需超时触发反熵补齐，或按策略放弃该操作。

## 九、演进与趋势
CRDT 把「因果合并」变成确定、无冲突的本地操作，副本间只需传播状态、无需协调（Shapiro 2011）。后续研究如 SwiftCloud、AntidoteDB 把因果一致与事务结合；无冲突复制从「最终一致」走向「强最终一致 + 因果序」的工程标准，成为边缘协同、离线优先应用的基础。因果一致也被用于「冲突无关复制数据类型」（CRDT）的理论保证中。

近年另一趋势是「因果一致的元数据压缩」：用点状版本向量（Dotted Version Vectors）或混合逻辑时钟（HLC）替代完整向量，把每条操作的元数据从 $O(N)$ 降到 $O(活跃节点数)$，使因果一致在千级节点规模下也变得可落地。

## 十、小结
因果一致性在以可用性为先的分布式系统中提供了「合理」的弱一致保证：它不强求全局最新，却杜绝了违反因果的异常。向量时钟与 CRDT 让因果一致可被高效实现，是最终一致存储走向可用的关键一步，也是多数真实业务能接受的一致性上界，避免了线性一致的高昂共识代价。理解它在一致性层级中的位置（强于最终一致、弱于顺序一致），是做出正确架构选型的前提。
