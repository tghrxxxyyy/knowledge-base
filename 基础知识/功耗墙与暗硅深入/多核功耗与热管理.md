# 多核功耗与热管理

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》热与功耗章；Intel RAPL（Running Average Power Limit）与 DTS 文档；Linux thermal framework 文档。

## 一、背景与挑战

多核芯片上局部高功耗会产生**热密度热点（hot spot）**，一旦结温超过安全上限就会触发降频（thermal throttling）甚至永久损伤。难点在于功耗是**空间分布**问题：即使芯片平均温度安全，单个核心的高密度热点仍可能触顶。因此多核热管理需要在温度、功耗、性能之间联合优化，并通过任务调度把热负载摊匀。这涉及硬件传感器、固件控制环与操作系统调度器的协同。

另一个关键特征是「多时间尺度耦合」：热扩散的时间常数在毫秒到秒量级，而指令级功耗波动在纳秒量级，调度决策在毫秒量级，散热环境（风扇、机房空调）在秒到分钟量级。因此热管理必须分层设计——硬件快速限流、调度器中期均衡、运维层面长期规划，任何单层都无法独立解决问题。

## 二、核心原理

热力学上用**热阻模型**描述：温升 $\Delta T = P \cdot R_{th}$（$R_{th}$ 为结到环境的热阻）。芯片内置数字温度传感器（DTS）阵列实时监测各区域温度，电源管理控制器（如 Intel 的 RAPL、AMD 的 APM）按功耗/热预算调节。RAPL 通常划分多个**功率域**（package、core、uncore、dram），分别施加功率上限。操作系统层面做**热感知调度（thermal-aware scheduling）**：把任务从热核迁移到冷核、用 DVFS 给热核降频、用时钟/电源门控关掉空闲核。控制目标是「在预算内尽量均衡」，避免任一核心长期过热。

三层防护的触发顺序值得说明：首先是硬件 RAPL 在毫秒级限制功率（防止瞬时超限）；若温度仍上升，硬件直接触发温度降频（thermtrip 前的保护）；操作系统调度器则在更长时间尺度上做负载迁移与频率分配，避免「持续在边缘运行」。这种「快慢分层」的设计，使得单点故障（如某个传感器失灵）不会立即导致损伤。

## 三、形式化与数学基础

稳态结温：

$$
T_{j} = T_{amb} + P \cdot R_{th}
$$

热时间常数描述升温过程：

$$
\tau = R_{th} C_{th},\quad T(t) = T_{ss}\left(1 - e^{-t/\tau}\right)
$$

多核调度的优化目标（最小化最热核心温度，受总功耗预算约束）：

$$
\min_{load} \max_i T_i \quad s.t.\quad \sum_i P_i \le P_{budget}
$$

这本质是一个带盒约束的负载均衡问题；由于 $T_i$ 与 $P_i$ 非线性（含漏电正反馈），实践中多用启发式。TDP（Thermal Design Power）是散热器设计参考的持续功率，并非瞬时峰值，二者常被混淆。

该优化问题有一个重要的结构性难点：目标是「最小化最大值」（min-max），而非「最小化总和」。这意味着把负载从热核迁到冷核的收益取决于两核的温差——温差大时迁移收益显著，温差小时迁移只增加开销却几乎不改善峰值温度。因此实际调度器通常设置「温差阈值」作为迁移触发条件，这既是性能考虑，也是避免任务抖动（thrashing）的必要设计。

## 四、代码实现

```c
/* 温度感知调度：把任务从最热核迁到最冷核（示意） */
void thermal_balance(int temp[4], int load[4]) {
    int hot = argmax(temp);
    int cold = argmin(temp);
    if (temp[hot] - temp[cold] > THRESH) {   /* 温差阈值：抑制抖动 */
        int move = load[hot] / 2;     /* 迁移一半负载以摊匀热 */
        move_task(hot, cold, move);
        set_freq(hot, lower_freq());  /* 同时给热核降频 */
    }
}
```

```c
/* RAPL 功率域限流示意（伪接口） */
rapl_set_limit(DOMAIN_PACKAGE, 65_W);  /* 整包不超过 65W */
rapl_set_limit(DOMAIN_DRAM,    15_W);  /* 内存子域单独限 */

/* 更细的 RAPL 用法：区分「持续预算」与「瞬时突发」
   - 长期功率上限（PL1）：稳态平均功率，对齐散热能力
   - 短时功率上限（PL2）：允许短时间高于 PL1 以吸收突发
   二者组合使芯片在负载波动下既有突发性能又不超热设计 */
rapl_set_limit(DOMAIN_PACKAGE, 65_W);   /* PL1：持续 */
rapl_set_limit_burst(DOMAIN_PACKAGE, 95_W, 30_ms);  /* PL2：突发 30ms */
```

第二段引出了 PL1/PL2 这对概念：只设单一上限会迫使芯片在突发负载下过早降频，损失响应性；而允许无限突发又会突破散热能力。因此硬件通常提供「持续上限 + 短时上限 + 时间窗」三元组，把「瞬时性能」与「长期热安全」解耦。

## 五、与其他技术对比

| 维度 | 仅 DVFS | 热感知调度 | RAPL/硬件闭环 | 液冷/封装散热 |
|------|---------|------------|----------------|----------------|
| 控制对象 | 全局功率 | 空间温度分布 | 功率/能量预算 | 热阻 $R_{th}$ |
| 响应速度 | 中 | 慢（调度周期） | 快（硬件 ms 级） | 极慢（物理改造） |
| 解决热点 | 否（只降总量） | 是（迁移均衡） | 是（限功率） | 是（降低温升） |
| 成本 | 低 | 中 | 低（已内置） | 高 |

三者协同（RAPL 限预算 + 调度均衡 + DVFS 调频）才能既保安全又保性能；而改进封装与散热（即降低热阻 $R_{th}$）是从根源上提高可用功率上限的手段，代价是硬件成本。

## 六、常见误区

1. 误以为降频只因功耗：实际常为**温度**触顶，是热而非功率直接触发。
2. 误以为平均温度安全即可：局部热点仍会触发 per-core 降频，整体性能受损。
3. 忽略热时间常数——瞬时峰值可能已损伤，而平均读数正常。
4. 误以为关核一定省电：频繁开关电源域的恢复开销可能抵消收益。
5. 混淆 TDP 与实际功耗：TDP 是散热设计参考，瞬时功率可短暂超过。
6. 认为调度器能单独解决热点：调度周期（毫秒）远慢于热扩散，必须配合硬件毫秒级限流。
7. 忽略漏电的温度正反馈：高温增大漏电、漏电又升温，可能触发连锁降频。
8. 以为只要不超 TDP 就绝对安全：瞬时电流冲击与电压跌落同样可能造成可靠性问题。

## 八、面试题

1. 为何热管理需空间均衡？答：局部热点触顶降频，即便平均温度安全也会拉低整体性能，需把负载从热核迁到冷核。
2. 热阻模型表达什么？答：$\Delta T = P \cdot R_{th}$，结温随功耗线性上升，故限功耗即限温。
3. RAPL 作用？答：硬件级按功耗/能量预算实时调节（分功率域），比操作系统调度环更快，作为第一道保护。
4. TDP 是功耗上限吗？答：不是，它是散热设计参考的持续功率，瞬时峰值可超出。
5. PL1 与 PL2 有何区别？答：PL1 是长期持续功率上限（对齐散热能力），PL2 是短时突发上限，二者配合兼顾响应性与热安全。
6. 迁移任务为何要设温差阈值？答：目标是最小化最热核温度，温差小时迁移收益微薄却增加开销与抖动，故需阈值触发。

## 九、演进与趋势

趋势是**芯片内温度传感器阵列 + 片上 AI 预测热模型**，实现每核/每域毫秒级精细调控；并与 DVFS、异构调度统一为「功率-热-性能」联合优化框架。具体接口与能力以官方最新文档为准。

另一条趋势是从「芯片级热管理」扩展到「机架/机房级协同」：数据中心把服务器功率上限与制冷能力联动调度，在整体电费与散热约束下追求集群级最优，而非单机最优。这类跨层优化能显著提升整体能效，但要求软硬件与运维体系深度配合。

## 十、小结

热管理是把「功耗预算」空间化的工程，决定了多核可持续性能。它把物理热学（热阻、时间常数）与操作系统调度结合，在保安全的前提下最大化吞吐——是后功耗墙时代不可或缺的系统层能力。

三条要点：热点是空间问题而非总量问题（需迁移均衡）、控制必须分层（硬件毫秒级 + 调度毫秒以上）、TDP 是设计参考而非硬上限（勿混淆概念）。
