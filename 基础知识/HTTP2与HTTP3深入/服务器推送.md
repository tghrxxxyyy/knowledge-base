# 服务器推送

> 对应 RFC 9113（HTTP/2 Server Push）。

## 一、背景与挑战
浏览器解析 HTML 后才发现子资源（CSS/JS/图片），需再发请求，引入额外 RTT。服务器推送让服务端“预测”并主动下发关联资源，减少往返。

## 二、核心原理
服务端发 PUSH_PROMISE 帧，携带承诺的流 ID 与请求头，告知客户端“我将推送此资源”。随后在该流上发响应。客户端可发 RST_STREAM 拒收，避免浪费。

## 三、形式化 / 数学基础
PUSH_PROMISE 帧：$Type=0x5$，含 $Promised\ Stream\ ID(31bit)$ 与请求头块片段。
推送流 ID 须为客户端已发起流的“后续偶数/奇数”规则：服务端只能用奇数（客户端发起）流 ID 中服务端承诺的；承诺流 ID 由服务端在已用最大 ID 基础上按规则分配。

## 四、代码实现
```go
// 服务端：推送 style.css 前先发 PUSH_PROMISE
conn.writePushPromise(promisedID, ":path", "/style.css")
conn.writeHeaders(promisedID, 200, headers)
conn.writeData(promisedID, cssBytes)
// 客户端不想收：
conn.writeRSTStream(promisedID, CANCEL)
```

## 五、与其他技术对比
服务器推送 vs 预加载（<link rel=preload>）：预加载仍由客户端发请求，推送由服务端主动发。推送易过度推送、与缓存/多路复用交互复杂，实践中常不如精细的 preload + 多路复用。

## 六、常见误区
误区一：推送一定能提速。错，盲目推送会占带宽、与浏览器缓存冲突。误区二：推送需客户端先请求该资源。错，正是“无需请求”。误区三：HTTP/3 也强推。错，HTTP/3 已弱化/弃用推送（RFC 9114 未定义 PUSH）。

## 九、演进与趋势
HTTP/3 不再标准化推送，转向 preload、103 Early Hints（RFC 8297）等更可控手段。

## 十、小结
服务器推送用 PUSH_PROMISE 主动下发子资源，意图省 RTT，但因缓存与带宽权衡在实践中受限。
