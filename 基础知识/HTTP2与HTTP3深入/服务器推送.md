# 服务器推送

> 对应 RFC 9113（HTTP/2 Server Push）。

## 一、背景与挑战
浏览器解析 HTML 后才发现子资源（CSS/JS/图片），需再发请求，引入额外 RTT；若服务器能「预测」页面依赖并主动下发，便可省去这次往返。HTTP/2 的服务器推送（Server Push）即为此设计：服务端在客户端请求主文档的同时，主动把关联资源「推」过去。但推送是一把双刃剑——盲目推送会浪费带宽、与浏览器 HTTP 缓存冲突，且撤销成本高，因此实践中必须适度且可被客户端拒绝。

更现实的考量是：服务端并不知道客户端缓存里已有什么（除非客户端主动告诉它）。这正是 Cache Digest 提案想解决的，但它最终因复杂度未普及。于是推送常退化为「推客户端大概率没有的资源」，命中率难以保证。

## 二、核心原理
服务端通过 **PUSH_PROMISE** 帧（类型 0x5）发起推送：它携带一个「承诺的流 ID（Promised Stream ID）」与请求头块片段（请求头，不含 body），告知客户端「我将为你推送这个资源」。随后服务端在该承诺流上发送 HEADERS（响应头）与 DATA（响应体）。客户端若已有该资源（强缓存命中）或不想接收，可发送 RST_STREAM（码 REFUSED_STREAM 或 CANCEL）拒收，避免浪费。

注意：被推送的流是服务端发起，因此承诺流 ID 为**偶数**（客户端发起为奇数），且 PUSH_PROMISE 必须关联一个已存在的客户端请求流，以便客户端理解推送的因果。推送还受 `SETTINGS_ENABLE_PUSH`（默认 1，置 0 则禁用）约束，以及 `MAX_CONCURRENT_STREAMS` 限制并发推送数。

## 三、形式化与数学基础
PUSH_PROMISE 帧头部为：

$$ Type=0x5,\quad PromisedStreamID(31bit) \parallel RequestHeaderBlockFragment $$

其行为约束可抽象为：若客户端在收到 PUSH_PROMISE 前已存在对同一资源 $R$ 的本地强缓存副本 $C(R)$，则接受收益 $B\approx 0$，而拒收可省去下行带宽 $W_R$：

$$ accept = \begin{cases} false, & C(R)\ \text{命中（省 } W_R \text{）}\\ true, & \neg C(R) \land requestable(R) \end{cases} $$

此外推送受 `MAX_CONCURRENT_STREAMS` 约束并发数；被拒收时服务端应停止发送对应流的数据，且不应计入成功推送统计。过度推送会挤占真正需要的流带宽，故应设推送速率上限。

## 四、代码实现
```go
// 伪代码：服务端推送 style.css（先于主文档响应发送 PUSH_PROMISE）
func pushResource(w http2ResponseWriter, path string) {
    w.Push(path, &PushOptions{            // 内部发送 PUSH_PROMISE
        Method: "GET",
        Header: http.Header{":authority": {"example.com"}},
    })
    w.Write(cssBytes)                     // 之后在承诺流上发送真实响应
}

// 客户端不想收：发送 RST_STREAM 拒收
conn.Write(Frame{StreamID: promisedID, Type: 0x3, Payload: u32(CANCEL)})
```

```go
// 伪代码：客户端按缓存命中去重，避免接受冗余推送
func onPushPromise(p *PushPromise) {
    if cache.Fresh(p.Path) {              // 强缓存已命中
        conn.Write(Frame{StreamID: p.PromisedID, Type: 0x3, Payload: u32(REFUSED_STREAM)})
        return
    }
    acceptStream(p.PromisedID)            // 接受并在本流接收响应
}

// 伪代码：服务端限制并发推送，避免挤占关键流
func maybePush(s Session, candidates []string) {
    for _, c := range candidates {
        if s.PushedCount() >= maxPush { break } // 速率上限
        s.Push(c)
    }
}
```

## 五、与其他技术对比
| 维度 | 服务器推送 | 103 Early Hints | `<link rel=preload>` |
| --- | --- | --- | --- |
| 谁发起请求 | 服务端主动 | 服务端提示 | 客户端发起 |
| 与缓存冲突 | 易冲突 | 无（仅提示） | 客户端自己管 |
| 可控性 | 差 | 好 | 好 |
| 协议层支持 | HTTP/2 帧 | HTTP 状态 | HTML 标签 |

服务器推送 vs 预加载：预加载仍由客户端发请求，推送由服务端代发；但推送因缓存不可见而常过度，精细的 preload + 多路复用往往更可控。Early Hints 只提示「稍后会有这些资源」，不强制占用流，是更温和的折中。

## 六、常见误区
- 误区：推送一定能提速。错，盲目推送会占带宽、与浏览器缓存冲突，甚至挤占真正需要的资源。
- 误区：推送需客户端先请求该资源。错，正是「无需请求」地主动下发，但须关联一个客户端请求流作上下文。
- 误区：HTTP/3 也强推。错，HTTP/3（RFC 9114）未定义 Server Push，官方已弱化/弃用该机制。
- 误区：推送资源自动进客户端缓存。错，客户端可拒收，且缓存策略仍由响应头决定。
- 误区：服务端无法感知拒收。错，客户端 RST_STREAM 会通知服务端停止发送。
- 误区：推送越多越好。错，并发推送受 MAX_CONCURRENT_STREAMS 限制，过量会拖慢主文档。

## 八、面试题
1. PUSH_PROMISE 的作用是什么？为何要在发响应前发它？（预告将推送的资源，让客户端有机会提前 RST_STREAM 拒收。）
2. 推送流 ID 的奇偶规则？（服务端发起为偶数；客户端发起为奇数。）
3. 为什么服务器推送在实践中用得少？（缓存不可见、易过度推送、与多路复用 + preload 相比收益有限。）
4. 客户端如何拒绝推送？（发送 RST_STREAM，码 REFUSED_STREAM/CANCEL。）
5. 推送受哪些 SETTINGS 约束？（ENABLE_PUSH 与 MAX_CONCURRENT_STREAMS。）

## 九、演进与趋势
HTTP/3 不再标准化 Server Push，行业转向 103 Early Hints、`<link rel=preload>`、优先级（Priority）信令等更可观测、可取消的手段。Chrome 等实现已默认关闭或移除推送，标志其从「协议特性」退场；服务端缓存摘要（Cache Digest）曾试图让推送变聪明，但也因复杂度未普及。未来的方向是「服务端只发提示，客户端决定拉取」，把缓存可见性交还给客户端。

## 十、小结
服务器推送用 PUSH_PROMISE 主动下发子资源，意图省 RTT，但因缓存不可见、撤销成本高、易过度推送，在实践中受限，最终被更轻量的提示机制取代。工程上应优先评估 preload + 多路复用的性价比，再决定是否启用推送。
