# 队头阻塞对比

> 对应 RFC 9113（HTTP/2）；RFC 9000（QUIC）；RFC 9114（HTTP/3）。

## 一、背景与挑战
「队头阻塞」（Head-of-Line blocking, HOL）指队首的堵塞拖慢整队后续项。HTTP 体系里 HOL 出现在不同层级，且解法迥异，常被混为一谈：应用层（HTTP/1.1 请求串行）、传输层（HTTP/2 over TCP 的字节流）、流级（HTTP/3 仍单流内有序）。

厘清层级是理解 Web 性能演进的主线，也是定位「为何一个慢请求拖垮整页」类问题的关键。很多线上「偶发卡顿」本质就是某一层 HOL 发作，而非应用逻辑问题。

值得一提的是，HOL 并非 HTTP 独有：TCP 自身的按序交付、帧中继/ATM 网络、乃至消息队列都会出现同类现象。比较不同协议的 HOL 边界，是网络性能分析的基本功。

## 二、核心原理
- **HTTP/1.1 应用层 HOL**：在单个 TCP 连接上，响应必须按请求顺序返回，慢响应阻塞其后所有请求；浏览器用多连接缓解，但受并发上限与连接开销制约。
- **HTTP/2 over TCP 传输层 HOL**：多路复用消除了应用层 HOL，但所有流共享一条 TCP 字节流；TCP 要求按序交付，任一报文丢失会冻结整条连接上所有流的重排，造成「一个丢包，全连接停顿」。
- **HTTP/3/QUIC 流级隔离**：QUIC 每条流是独立可靠有序信道，丢包只影响本流，其余流照常前进；但单流内部仍是有序可靠，故流内 HOL 依旧存在。

理解这三层的关键是把「有序交付」的边界画对：HTTP/1.1 是整个响应序列有序；HTTP/2 是整条 TCP 字节流有序；HTTP/3 退到「单条 QUIC 流」有序。边界越小，阻塞影响面越小。

## 三、形式化与数学基础
设连接含 $n$ 个并发流，单段在途丢包概率为 $p$。HTTP/2 下整连接因任一在途段丢失而停顿的概率约：

$$ P_{H2\_stall} \approx 1-(1-p)^{k},\quad k=\text{在途段数} $$

而 HTTP/3 单流停顿概率为 $p$，其余 $n-1$ 流不受影响。恢复时延对比：

$$ T_{TCP} \approx RTO\ (\text{整连接冻结});\quad T_{QUIC} \approx RTO\ (\text{仅单流冻结，其余流继续}) $$

可见 QUIC 把「停顿影响面」从 $O(n)$ 降到 $O(1)$ 流。当 $n$ 很大（一个页面数十个资源）且 $p$ 不大时，HTTP/2 几乎必然周期性全连接停顿，而 HTTP/3 仅个别流受影响。若采用多路径 QUIC 且单路径丢包独立，整体停顿概率进一步降为各路径乘积。

## 四、代码实现
```text
HTTP/1.1 单连接:
  [req1 ==> resp1][req2 ==> resp2]   # resp1 慢 => req2 排队等待

HTTP/2 over TCP（单连接多流）:
  流1▢ 流2▢ 流3▢  (共用一条 TCP 字节流)
  丢一个 TCP 段 => 整连接重排阻塞 => 所有流暂停

HTTP/3 over QUIC（每流独立）:
  QUIC流1▢  QUIC流2▢  QUIC流3▢  (各自可靠有序)
  流2 丢包 => 仅流2 等待重传，流1/流3 继续
```

```text
TCP 字节流视角（为何整连接冻结）：
  byte0 byte1 byte2(丢失) byte3 byte4 ...
  => 接收端缓存 byte3/byte4 但应用不可读，直到 byte2 重传到达
  => 所有依赖该连接的 HTTP/2 流都被卡住
```

```text
实测观测建议（定位是哪层 HOL）：
  应用层：单个流内请求/响应耗时分布（HAR  waterfall）
  传输层：tcpdump 看是否「一个丢包后整连接 RTT 拉升」
  QUIC 层：per-stream 丢包/重传计数，确认仅单流停顿
```

## 五、与其他技术对比
| 层级 | 机制 | 阻塞范围 | 解法 |
| --- | --- | --- | --- |
| 应用层（HTTP/1.1） | 请求串行响应 | 单连接全部请求 | 多路复用（HTTP/2） |
| 传输层（HTTP/2/TCP） | 字节流按序交付 | 整连接所有流 | 流级可靠（HTTP/3） |
| 流内部（HTTP/3） | 单流有序 | 仅该流 | 业务层分块/多流并发 |

WebSocket 在单 TCP 上也受 TCP HOL 影响；gRPC 流、SSE 同理。多路径 QUIC 进一步在多条路径间分担，降低单路径丢包影响。注意：HTTP/2 的「多连接」并行并不能消除 TCP HOL，只是把概率摊薄到多条连接。

## 六、常见误区
- 误区：HTTP/2 多路复用解决了一切 HOL。错，TCP 层仍在，单丢包冻结全连接。
- 误区：TCP 不会 HOL。错，丢包重传会阻塞整连接字节流，后续无关字节也被卡住。
- 误区：HTTP/3 完全无 HOL。错，单流内有序可靠，流内丢包仍阻塞该流。
- 误区：多开 TCP 连接就能根治 TCP HOL。错，每条连接仍各自有 HOL，且开销大。
- 误区：队头阻塞只影响吞吐不影响延迟。错，它会直接抬升首字节与尾字节延迟。
- 误区：丢包率低就无需关心 HOL。错，高并发下即使 1% 丢包，全连接停顿也频繁发生。

## 八、面试题
1. HTTP/2 还有哪种 HOL 没解决？（TCP 层：丢包触发整连接字节流重排阻塞。）
2. HTTP/3 怎么消除传输层 HOL？（每流独立可靠有序，丢包只影响对应流。）
3. 为什么单流内仍有 HOL？（流本身要求有序交付，丢包须等重传。）
4. 多开 TCP 连接能否根治？（不能，每条连接各自有 HOL，且开销大。）
5. 多路径 QUIC 如何进一步缓解？（多条路径分担，单路径丢包不影响整体。）

## 九、演进与趋势
多路径 QUIC（Multipath QUIC）在多条网络路径间分担流量，单路径丢包不再影响整体；同时 HTTP/3 的优先级信令（RFC 9218）让重要流优先重传，进一步缓解「关键流被次要流拖累」的体验问题。未来「流内分块 + 多流并发」将成为应用层规避流内 HOL 的默认范式；传输层也可能探索「部分可靠」流（允许丢弃而非重传）以彻底消除实时场景的 HOL。CDN 与浏览器正把 HOL 指标纳入核心 Web 指标观测。从工程角度看，最务实的优化往往是「减少单连接上的流数」与「把大 body 切成可独立解码的块」，从而降低单次 HOL 的暴露面。

## 十、小结
队头阻塞分应用层与传输层：HTTP/2 解前者、HTTP/3/QUIC 再解后者（流级隔离），是 Web 性能演进主线；但单流内有序的 HOL 属应用设计范畴，需靠多流并发与优先级解决。排查线上卡顿时，应先判断 HOL 发生在哪一层，再对症选协议或拓扑。协议选择不是终点，业务层的并发与优先级设计同样关键。

在 QUIC 多路径普及后，单路径丢包对整体的影响进一步下降，但应用层仍需避免把关键与次要请求混在同一条流里，否则流内 HOL 仍会拖垮关键请求。
