# SLO与错误预算

> 对应 Beyer 2016《Site Reliability Engineering》(Google) 与 Kim et al. 2016《Accelerate》。

## 一、背景与挑战

「追求 100% 可用」既不经济也不可行：多一个九意味着指数级的成本增长，而用户往往感知不到 99.99% 与 99.999% 的差别。团队真正需要的是一个可量化的平衡点，在「可靠」与「快速迭代」之间做明确取舍。

更现实的困境是：稳定性与交付速度常被当成对立目标，产品团队想多发版，运维团队想求稳，双方缺乏共同语言。SLO 与错误预算（error budget）正是把这一争论转化为可计算的账本。

## 二、核心原理

三个层次要分清：SLI 是实际测量的指标（如成功率），SLO 是目标值（如 99.9%），SLA 是对客户的承诺（通常含赔偿条款，目标低于内部 SLO）。

错误预算 = $1 - \text{SLO}$，即在统计窗口内允许的失败额度。它的作用是把可靠性变成一种「可消耗资源」：

- 预算充足时，团队可放心发布新功能、做风险实验；
- 预算耗尽时，冻结非必要变更，把工程资源转向稳定性修复；
- 预算消耗速度（burn rate）比绝对剩余更能反映风险，可用于告警。

实践要点是选对 SLI：应贴近用户体验（如「请求成功率」「端到端延迟」），而非内部技术指标（如 CPU 使用率）。窗口通常用滚动 28 天或 30 天，兼顾统计显著性与响应灵敏度。

## 三、形式化与数学基础

设窗口内请求总数为 $N$、失败数为 $F$，则实际可用性：

$$
A = 1 - \frac{F}{N}
$$

错误预算的绝对额度与剩余量：

$$
B_{\text{total}} = (1 - \text{SLO}) \cdot N,\qquad B_{\text{left}} = B_{\text{total}} - F = (\text{SLO} - A) \cdot N
$$

当 $B_{\text{left}} \le 0$ 时触发发布冻结。燃烧率定义为预算消耗速度相对理想速度的倍数：

$$
\text{BR} = \frac{F / N}{1 - \text{SLO}}
$$

在消耗全部预算的前提下，预算耗尽所需时间为窗口的 $1/\text{BR}$。多窗口告警常用「长窗口 + 短窗口」组合：长窗口确认持续性问题，短窗口捕捉突发，降低误报与漏报。例如「1 小时 BR > 14.4」约等于 2 天耗尽一个 28 天窗口的预算。

## 四、代码实现

```python
# 基于滚动窗口的错误预算与燃烧率计算
SLO = 0.999
WINDOW_REQUESTS = 1_000_000
allowed = int((1 - SLO) * WINDOW_REQUESTS)      # 允许失败数

def budget_state(total, failed):
    left = allowed - failed
    availability = 1 - failed / total
    burn_rate = (failed / total) / (1 - SLO)
    return {
        "availability": round(availability, 6),
        "budget_left": left,
        "burn_rate": round(burn_rate, 2),
        "freeze": left <= 0,
    }

state = budget_state(WINDOW_REQUESTS, actual_failures)
if state["freeze"]:
    freeze_noncritical_deploys()                 # 冻结非必要发布
if state["burn_rate"] > 14.4:
    page_oncall("error budget burning fast")     # 高燃烧率告警
```

## 五、与其他技术对比

| 机制 | 关注点 | 是否连接交付节奏 | 典型用途 |
| --- | --- | --- | --- |
| SLI 监控 | 当前指标数值 | 否 | 看板与趋势 |
| 阈值告警 | 是否越过固定线 | 否 | 单点异常通知 |
| SLO + 错误预算 | 目标与额度消耗 | 是，驱动发布决策 | 稳定性与迭代的权衡 |
| SLA | 对外承诺与赔偿 | 间接 | 合同与合规 |
| 燃烧率告警 | 消耗速度 | 是，触发冻结 | 灵敏的预算保护 |

## 六、常见误区

- **SLO 定得过高**：预算形同虚设，团队永远不敢发布，失去本意。
- **只看月度聚合**：掩盖短时严重超标，用户实际体验已受损。
- **SLI 选得不对**：用内部指标而非用户可感知指标，导致 SLO 与实际体验脱节。
- **预算耗尽仍强行发布**：破坏规则的严肃性，SLO 沦为摆设。
- **把预算当 KPI 考核**：会诱导「藏数据」而非改系统。

## 七、与开源书·权威来源对应

Beyer 2016《Site Reliability Engineering》(Google) 系统提出 SLI/SLO/SLA 体系与错误预算、燃烧率告警；Kim et al. 2016《Accelerate》用实证数据说明可靠性实践与交付绩效正相关，反驳「稳定与速度对立」；《The DevOps Handbook》将错误预算作为风险权衡的落地机制。具体窗口与阈值建议以各组织官方最新实践为准。

## 八、面试题

- **问：错误预算耗尽后该怎么做？** 答：冻结非必要变更，优先修复稳定性；并复盘预算消耗的根因。
- **问：SLO 与 SLI 的关系？** 答：SLI 是测量值，SLO 是该测量值的目标，错误预算由两者之差导出。
- **问：为什么用燃烧率而不只看剩余预算？** 答：剩余量是静态的，燃烧率能提前预警「即将耗尽」，更灵敏。
- **问：如何选 SLI？** 答：选贴近用户体验、可稳定测量、且团队能影响的指标，如成功率与端到端延迟。

## 九、演进与趋势

多窗口多燃烧率告警已成为云原生 SRE 的标配；SLO 平台正把「定义—测量—冻结—复盘」自动化，并与发布系统联动实现「预算不足即阻断」。另一趋势是按用户旅程或关键业务流定义分层 SLO，把有限预算优先保护最重要的路径。

## 十、小结

SLO 与错误预算把抽象的「可靠性」变成可度量、可消耗、可决策的资源：SLI 回答「现在多可靠」，SLO 回答「要多可靠」，错误预算回答「还能冒多大风险」。它用一本共同的账，终结了稳定与速度的对立争论。
