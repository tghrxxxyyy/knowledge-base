# 多因素认证原理

> 对应 RFC 6238（TOTP）；RFC 4226（HOTP）；NIST SP 800-63B（Digital Identity Guidelines）；OWASP Authentication Cheat Sheet；FIDO2/WebAuthn（W3C）规范；Saltzer & Schroeder 1975。

## 一、背景与挑战

单因子认证（仅口令）面对钓鱼、撞库、爆破时非常脆弱：口令可被诱导输入、可在别站泄露后被批量重放。多因素认证（MFA）要求用户提供跨类别的两个及以上凭证，使单一因子泄露不再足以冒用身份。挑战在于：因子的「类别独立性」必须真实成立（两个口令不是两因子）；验证流程要抵抗重放（同一验证码不能二次使用）；用户体验与恢复流程（设备丢失、无手机）不能因安全而不可用；此外推送式 MFA 会遭遇「MFA 疲劳」攻击——反复轰炸弹窗等待用户误点批准。

## 二、核心原理

三类因子：知识因子（Something you know，如口令、PIN）、持有因子（Something you have，如手机、硬件令牌）、固有因子（Something you are，如指纹、人脸）。MFA 要求跨类组合。TOTP 基于共享密钥与时间窗口生成一次性码：客户端与服务端共享密钥 $K$，按时间步长 $T$ 计算并取低位数字，双方在窗口内可对齐。为容忍时钟漂移，验证通常接受当前步及前后各一步。HOTP 则是基于计数器的同族方案，每用一次计数递增，需要双方计数器严格同步。FIDO/WebAuthn 换用公钥模型：注册时生成密钥对，私钥留在认证器（不可导出），登录时用私钥签名挑战值，服务端用公钥验证——因其绑定源站域名，天然抗钓鱼，且服务器侧不存任何可被复用的共享秘密。

## 三、形式化与数学基础

设两个独立因子的破解概率分别为 $p_1, p_2$，组合后的破解概率为：

$$ P_{break} = p_1 \times p_2 $$

独立性是乘积成立的前提：若两因子相关（如手机短信与手机号），则不能简单相乘。TOTP 的码由键控消息认证码经动态截断得出：

$$ code = DT(HMAC\text{-}SHA1(K, \lfloor (t - T_0)/T \rfloor)) \bmod 10^{d} $$

其中 $t$ 为当前 Unix 时间，$T=30$ 秒，$d=6$，$DT(\cdot)$ 为动态截断：取末字节低 4 位为偏移 $o$，取 $HMAC[o..o+3]$ 的 31 位大端整数再对 $10^d$ 取模。由于时间步前进后 $c = \lfloor t/T \rfloor$ 必增大，旧码在新时间步不再匹配，从而天然抗重放；但同一时间步内的重复使用需要服务端额外记录已消费的步数来拦截。

## 四、代码实现

```python
# TOTP 生成（简化实现，协议见 RFC 6238；生产建议用 pyotp）
import hmac, hashlib, time, struct

def totp(secret: bytes, t=None, step=30, digits=6) -> str:
    t = int(time.time()) if t is None else int(t)
    counter = t // step
    msg = struct.pack(">Q", counter)              # 8 字节大端计数器
    mac = hmac.new(secret, msg, hashlib.sha1).digest()
    offset = mac[-1] & 0x0F                       # 动态截断偏移
    code = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(code % (10 ** digits)).zfill(digits)

def verify(secret, user_code, used_steps, window=1):
    now = int(time.time())
    # 接受当前步及前后各一步，容忍时钟漂移；服务端需记录已用码防重放
    for w in range(-window, window + 1):
        step = now // 30 + w
        if step in used_steps:                    # 该时间步已消费，拒绝重放
            continue
        if hmac.compare_digest(totp(secret, step * 30), user_code):
            used_steps.add(step)
            return True
    return False
```

生产实现还需：限制尝试次数（防在线爆破）、把共享密钥加密存储、以及在注册时用二维码安全地分发种子。

## 五、与其他技术对比

| 维度 | 短信 OTP | TOTP | 推送 MFA | FIDO2/WebAuthn |
| --- | --- | --- | --- | --- |
| 因子类别 | 持有（依赖运营商） | 持有 | 持有 | 持有 + 可选固有 |
| 抗钓鱼 | 弱（可转发的实时钓鱼） | 弱（可代填） | 弱（疲劳攻击） | 强（绑定源站域名） |
| 抗 SIM 交换 | 差 | 好 | 好 | 好 |
| 服务端存储 | 手机号 | 共享密钥 | 共享密钥 | 仅公钥 |
| 离线可用 | 否 | 是 | 否 | 是 |
| 体验/成本 | 低门槛 | 中（需 App） | 中 | 较高（需认证器） |

## 六、常见误区

1. 把「两个口令」当两因子：同属知识因子，不构成多因素。
2. 把短信视为强因子：SIM 交换、号码转移与实时转发钓鱼都能绕过。
3. 忽略重放防护：TOTP 在同一窗口内可被重复使用，服务端需记录已消费的时间步。
4. 忽视 MFA 疲劳：无限次推送会让用户误点「批准」，应限速、标注来源并要求数字匹配。
5. 忘记恢复路径的安全设计：恢复码若弱化，会成为绕过 MFA 的后门。
6. 认为 MFA 与 SSO 互斥：二者正交，SAML/OIDC 的 IdP 登录也应在认证环节强制 MFA。
7. 忽略时钟漂移：客户端时钟偏差过大会使所有码都验证失败，需提供对时引导或扩大窗口。

## 七、与开源书·权威来源对应

- RFC 6238 定义 TOTP 的时间步、动态截断与验证窗口，是本章算法依据。
- RFC 4226 定义 HOTP，TOTP 在其计数型基础上引入时间。
- NIST SP 800-63B 给出认证器保证等级的规范要求与对短信因子的限制性建议。
- OWASP Authentication Cheat Sheet 汇总 MFA 实现与防重放要点。
- FIDO2/WebAuthn 规范定义公钥式无口令认证的抗钓鱼模型。
- 具体参数与合规口径以官方最新版本为准。

## 八、面试题

1. 三类因子分别是什么？——知识（知道什么）、持有（拥有什么）、固有（是什么）。
2. TOTP 为什么能抗重放？——时间步单调前进，同一码在新时间步不再匹配。
3. FIDO/WebAuthn 的核心优势？——私钥不外泄、公钥绑定源站、服务端无共享秘密，抗钓鱼与抗拖库。
4. MFA 疲劳攻击如何缓解？——限制推送频率、展示来源上下文、要求数字匹配、异常时强制改用其他因子。
5. 为什么两个口令不算 MFA？——同属知识因子，破解概率不构成乘积下降。

## 九、演进与趋势

Passkey（基于 WebAuthn 的可同步凭证）正在把「持有因子」与用户设备体验结合，降低 MFA 的摩擦。自适应风险认证（结合设备指纹、行为特征与地理位置动态调整验证强度）与零信任结合，实现「该严则严、该宽则宽」。具体支持范围以官方最新文档为准。

## 十、小结

MFA 以跨类因子的乘积效应显著降低账号被冒用的概率；TOTP 实现简单但需防重放，短信因子弱化明显，而 FIDO/WebAuthn 以公钥模型提供了抗钓鱼的最强保障，是当前认证演进的主方向。
