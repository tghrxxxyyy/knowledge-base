# 口令存储与慢哈希

> 对应 OWASP Password Storage Cheat Sheet；RFC 9106（Argon2）；NIST SP 800-63B（Digital Identity Guidelines）；Provos & Mazières 1999（bcrypt）；Bovet & Cesati《Understanding the Linux Kernel》（crypt(3) 与影子口令背景）。

## 一、背景与挑战

口令库一旦泄露，若存储为明文或使用快速哈希（MD5/SHA-1/SHA-256 裸用），攻击者可用 GPU 离线暴力破解，速度可达每秒数十亿次猜测。防御思路是人为提高「单次验证」的成本，使离线爆破在经济与时间上不可行。挑战在于：成本提升必须对合法用户可接受（登录延迟几十到几百毫秒），且必须抵抗彩虹表（预计算）、抵抗 GPU/ASIC 并行、并支持随硬件进步平滑升级参数。此外还要正确处理「相同口令不同用户哈希不同」与「验证过程不泄露信息（常数时间比较）」两个细节。

## 二、核心原理

两大机制：加盐（salt）与慢哈希（key stretching）。每个用户使用独立的随机盐，使同一口令产生不同哈希，从而使预计算彩虹表失效、且无法批量比对用户之间是否同口令。慢哈希（bcrypt/scrypt/Argon2）通过可调参数（迭代轮数、内存占用、并行度）刻意拖慢计算；其中 scrypt 与 Argon2 是「内存硬」（memory-hard）的，强制占用大量内存，从而限制 GPU/ASIC 因内存带宽与容量不足而获得的并行优势。Argon2 是 2015 年 Password Hashing Competition 的获胜算法，Argon2id 混合了数据依赖与数据无关两种寻址，兼顾抗侧信道与抗 GPU。参数选择的原则是：在目标硬件上单次验证耗时落在可接受区间，并随硬件升级上调参数、在用户下次登录时透明重算。

## 三、形式化与数学基础

离线爆破的总代价可建模为：

$$ Cost = N_{users} \times 2^{H} \times t_{hash} + C_{memory} $$

其中 $N_{users}$ 为库中账户数，$H$ 为口令熵（比特），$t_{hash}$ 为单次哈希耗时，$C_{memory}$ 为内存硬算法带来的额外限制。慢哈希把 $t_{hash}$ 从微秒（快速哈希）提升到数十毫秒量级，即提高约 $10^4$ 倍，直接抬升爆破成本；内存硬进一步压低攻击者的并行度 $k$，整体吞吐约与可用内存带宽成正比。盐的作用是把「同口令取同哈希」的批量攻击降级为逐账户攻击：

$$ P(\text{彩虹表命中}) \xrightarrow{salt} \approx 0, \qquad \text{攻击复杂度} \propto N_{users} $$

验证必须使用常数时间比较，否则会泄露「前缀匹配长度」构成时序侧信道。

## 四、代码实现

```python
# 使用 Argon2id（需 argon2-cffi）；参数按目标硬件调优
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher(
    time_cost=3,        # 迭代轮数：越大越慢
    memory_cost=65536,  # 内存开销（KiB）≈64 MiB，抗 GPU 并行
    parallelism=4,      # 并行度，通常取核数
)

def register(password: str) -> str:
    return ph.hash(password)            # 自动生成随机盐，并编码参数与盐入哈希串

def login(stored: str, password: str) -> bool:
    try:
        ph.verify(stored, password)     # 内部使用常数时间比较
        if ph.check_needs_rehash(stored):
            stored = ph.hash(password)  # 参数升级后透明重算并回写
        return True
    except VerifyMismatchError:
        return False
```

`argon2` 的哈希串自带版本、参数与盐，便于逐条记录平滑升级。

## 六、常见误区

1. 自定义哈希（如「MD5+SHA1+拼接」）：混淆不等于强度，缺少盐与慢化仍可被爆破。
2. 使用固定盐或全局盐：等于没有盐，彩虹表与批量比对依然成立。
3. 用快速哈希存口令：单次微秒级使 GPU 每秒可试数十亿次，形同明文。
4. 参数长期不升级：硬件进步会逐年削弱既有参数的有效性。
5. 用 `==` 比较哈希：非常数时间比较泄露前缀信息，形成时序侧信道。
6. 认为加 pepper 可替代加盐：pepper 是全局密钥（存于应用侧），泄露后价值有限，只是纵深防御补充。

## 八、面试题

1. 为什么必须加盐？——使同口令产生不同哈希，破坏彩虹表与跨账户批量比对。
2. 慢哈希的目的是什么？——把 $t_{hash}$ 提高几个数量级，直接抬升离线爆破成本。
3. bcrypt 与 Argon2 的关键差异？——Argon2 是内存硬且可调并行度，抗 GPU/ASIC 更强，并支持 Argon2id 抗侧信道。
4. 为什么用常数时间比较？——避免通过响应时间泄露哈希前缀，构成侧信道。
5. 参数应如何演进？——在可接受延迟内取上限，随硬件升级上调，并在用户下次登录时透明重算。

## 九、演进与趋势

Argon2id 已成为多数场景的默认推荐；云与合规环境常叠加 HSM/KMS 管理的 pepper 作为纵深防御。同时，无口令方案（Passkey/WebAuthn）从源头减少口令依赖，把风险从「如何存口令」转移到「如何保护公钥凭证」。具体推荐以官方最新文档为准。

## 十、小结

口令必须用「每用户随机盐 + 慢哈希（首选 Argon2id）」存储，把离线爆破成本提高到不现实，同时做好参数可升级与常数时间比较。它是口令库泄露后的最后一道防线。
