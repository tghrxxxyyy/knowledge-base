# 单点登录基础

> 对应 RFC 6749（OAuth 2.0 授权框架）；RFC 7519（JWT）；OpenID Connect Core 1.0；SAML 2.0 规范；OWASP Authentication Cheat Sheet。

## 一、背景与挑战

多系统各自维护账号，既造成糟糕的登录体验（重复注册、重复输入口令），也让统一注销与审计变得不可能。单点登录（SSO）让用户在一次认证后访问多个相互信任的应用。挑战有三：其一，如何让应用在不接触用户口令的前提下信任「用户已认证」——这需要由可信身份提供方（IdP）签发、应用（SP/RP）可验证的断言；其二，如何防止断言被伪造或重放——需要签名、时效与受众校验；其三，如何做到单点注销——全局会话的失效要能传导到所有下游会话，而这在纯无状态令牌下有天然困难。

## 二、核心原理

用户向 IdP 完成认证，IdP 签发断言或令牌，各应用信任该断言而免除二次登录。三条主流技术路线：SAML 2.0 以 XML 断言承载属性，企业级集成常见，但报文重、解析复杂；OIDC（OpenID Connect）在 OAuth 2.0 之上增加身份层，用 JWT 形式的 ID Token 表达用户身份，轻量且对移动端友好；CAS 用一次性票据（ticket）换取会话，协议简单。核心机制是「联合身份」：应用只依赖 IdP 的公钥或共享密钥验证签名，并校验 `iss`（签发者）、`aud`（受众）、`exp`（过期）等声明，从而把认证责任集中到 IdP。单点注销通常依靠 IdP 向各 RP 推送 back-channel 通知，或依赖短时效令牌加定期重验来收敛。

## 三、形式化与数学基础

SSO 的信任链可表示为认证与断言的两段式转移：

$$ User \xrightarrow{auth} IdP \xrightarrow{assertion} SP $$

应用侧接受断言的充要条件为签名、受众、时效三者同时成立：

$$ Valid = Verify(sig_{IdP}, assertion, cert_{IdP}) \land (aud = self) \land (now < exp) $$

其中签名验证基于 IdP 公钥 $pk_{IdP}$：$Verify(pk_{IdP}, m, \sigma)$ 为真当且仅当 $\sigma$ 是 $m$ 在 $sk_{IdP}$ 下的合法签名。若断言为 JWT，则签名覆盖 `base64url(header) + "." + base64url(payload)`，任意字段被篡改都会导致验证失败。安全强度还依赖票据熵与有效期：一次性票据的猜测成功概率为 $2^{-H}$，$H$ 为熵位数。此外，`nonce` 与 `state` 用于防重放与防 CSRF，是授权码流程的必备参数。

## 四、代码实现

```python
# 校验 OIDC 的 ID Token：签名 + 受众 + 签发者 + 时效（需 PyJWT）
import jwt
from jwt import PyJWKClient

jwks = PyJWKClient("https://idp.example.com/.well-known/jwks.json")
id_token = "..."                               # 来自 OIDC 回调的 id_token

signing_key = jwks.get_signing_key_from_jwt(id_token).key
claims = jwt.decode(
    id_token,
    signing_key,
    algorithms=["RS256"],                      # 白名单，禁止 alg=none
    audience="my_client_id",                   # 校验 aud
    issuer="https://idp.example.com",          # 校验 iss
    options={"require": ["exp", "iat", "sub"]},
)
user_id = claims["sub"]                        # 验证通过即信任该身份
```

四个必须显式处理的点：算法白名单（防 `alg=none` 与算法混淆）、受众（防令牌被其他应用复用）、签发者（防伪造 IdP）、以及 `nonce`/`state` 比对（防重放与请求伪造）。

## 五、与其他技术对比

| 维度 | SAML 2.0 | OIDC | CAS | 直接本地登录 |
| --- | --- | --- | --- | --- |
| 令牌载体 | XML 断言 | JWT（ID Token） | 票据字符串 | 服务端会话 |
| 签名/加密封装 | XML DSig/Enc | JWS/JWE | 可选 | 不适用 |
| 移动端友好度 | 较低 | 高 | 中 | 高 |
| 属性传递 | 强（断言属性） | 中（claims） | 弱 | 无 |
| 单点注销 | 有规范 | 有（含 RP-Initiated） | 有 | 不适用 |
| 集成复杂度 | 高 | 中 | 低 | 最低 |

## 六、常见误区

1. 把 OAuth 2.0 当认证协议：OAuth 只解决「授权访问资源」，身份语义由 OIDC 的 ID Token 提供。
2. 不校验算法：允许 `alg=none` 或接受对称/非对称混淆算法会导致签名验证被绕过。
3. 忽略受众校验：ID Token 被其他客户端复用即构成越权。
4. 认为 IdP 被攻破影响有限：IdP 是整个信任链的根，一旦失守所有下游应用同时沦陷。
5. 忽略单点注销：只做单点登录会让本地会话在全局注销后继续残留。
6. 把 access token 当身份凭证：它面向资源服务器，语义与受众都与 ID Token 不同。

## 七、与开源书·权威来源对应

- RFC 6749 定义 OAuth 2.0 授权框架，是 OIDC 的协议底座。
- OpenID Connect Core 1.0 定义 ID Token、UserInfo 端点与身份声明。
- SAML 2.0 规范定义企业级 XML 断言与联合身份。
- RFC 7519 定义 JWT 结构，是 ID Token 的编码格式。
- OWASP Authentication Cheat Sheet 给出联合身份与令牌校验的实践要点。
- 具体参数与端点以各规范官方最新版本为准。

## 八、面试题

1. SSO 的基本原理？——用户向 IdP 认证一次，IdP 签发断言，各应用验证断言后建立本地会话。
2. OAuth 与 OIDC 的区别？——OAuth 管授权（访问令牌），OIDC 在其上加身份层（ID Token）。
3. 为什么必须校验 `aud` 与 `iss`？——防止令牌被其他应用复用或由伪造 IdP 签发。
4. IdP 成为单点故障如何缓解？——IdP 高可用部署、多 IdP 联邦、以及对下游的降级登录预案。
5. 单点注销为什么难？——下游会话各自独立，需靠 back-channel/front-channel 通知或短令牌时效收敛。

## 九、演进与趋势

方向包括：以 WebAuthn/Passkey 替代口令提升 IdP 自身安全性；FedCM 把浏览器中介的联合登录标准化以减少第三方 Cookie 依赖；去中心化身份（DID）与可验证凭证探索免中心 IdP 的信任模型。具体支持情况以官方最新文档为准。

落地层面还有一个常被低估的细节：JWKS 的缓存与轮换。IdP 轮换签名密钥时，验证方若长期缓存旧公钥，会在轮换窗口内出现验证失败或误接受，因此需要按缓存策略与 `kid` 正确选择密钥。

同理，断言的有效期与时钟偏差容忍度也需要在双方之间显式约定。

## 十、小结

SSO 通过可信 IdP 的签名断言实现「一次登录、多系统访问」，SAML、OIDC、CAS 是三条主流路线，其中 OIDC + JWT 因其轻量与移动友好成为现代默认选择；而 IdP 的安全性决定了整个信任体系的上限。
