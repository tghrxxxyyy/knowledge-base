# 最小权限与认证授权边界

> 对应 Saltzer & Schroeder 1975「The Protection of Information in Computer Systems」；OWASP Top 10 A01（Broken Access Control）；OWASP Authorization Cheat Sheet；NIST SP 800-162（ABAC 指南）。

## 一、背景与挑战

认证（AuthN：你是谁）与授权（AuthZ：你能做什么）常被混为一谈，边界不清直接导致越权：只验证「已登录」而不验证「是否有权访问该对象」。最典型的形态是 IDOR（Insecure Direct Object Reference）——把 `GET /orders/1234` 中的 ID 改成 `1235` 即可读到他人订单，因为后端只检查会话有效性，未检查归属。挑战有三：其一，认证与授权是两道独立关卡，任何一道被省略都会失守；其二，授权必须对每个对象「完全仲裁」，不能用「会话有效」笼统代替；其三，权限判断必须放在服务端可信边界内，前端隐藏按钮不构成任何保护。

## 二、核心原理

认证产出身份声明（用户是谁、以何种强度认证），授权基于该身份与策略决定某次访问是否放行。Saltzer & Schroeder 的最小权限原则要求：主体只应获得完成当前任务所必需的最小权限，且默认拒绝（fail-safe defaults）。工程落实上有三条要点：完全仲裁（每次访问都重新判定，不依赖上一次结果或缓存的身份结论）、对象级授权（把资源归属或 ACL 纳入判定，而不只是路由级角色）、服务端强制（所有判定在服务端完成，前端仅作体验优化）。纵深防御上，认证授权还应与网络分区、数据加密、审计日志分层配合——单点失守不应导致整体失守。

## 三、形式化与数学基础

把请求抽象为三元组 $(u, obj, act)$，放行条件为认证与授权同时成立：

$$ allow(u, obj, act) \iff AuthN(u) \land Policy(u, obj, act) = Permit $$

默认拒绝意味着策略缺省取 `Deny`：

$$ Policy(u, obj, act) = Deny \quad \text{当策略未显式匹配时} $$

IDOR 漏洞可精确刻画为策略函数丢失对象维度，即 $Policy(u, obj, act) \equiv Policy(u, act)$，于是 $\forall obj$ 同一判定，对象隔离失效。最小权限则是对权限集合的约束：主体 $u$ 的授权集 $P(u)$ 应满足 $P(u) \subseteq Need(u)$，其中 $Need(u)$ 为完成其职责所必需的最小集合。

## 四、代码实现

```python
# 对象级授权：每次请求都做归属检查，防 IDOR
def delete_doc(user, doc_id):
    if not user.authenticated:          # 关卡一：认证
        return 401, "unauthenticated"
    doc = db.get(doc_id)
    if doc is None:
        return 404, "not found"
    if doc.owner_id != user.id and not user.has_role("admin"):
        return 403, "forbidden"         # 关卡二：对象级授权
    db.delete(doc)
    audit.log(user.id, "delete", doc_id)
    return 200, "ok"

def list_docs(user):
    # 查询层也要收窄：不要把全部数据取出后再过滤
    return db.query("SELECT * FROM docs WHERE owner_id = ?", user.id)
```

两个易错点：先查后判会产生 TOCTOU 竞态，建议在同一次查询中带上归属条件；列表接口同样要做授权，否则「能列就能看」。

## 五、与其他技术对比

| 维度 | 仅认证 | 路由级角色检查 | 对象级授权 | 属性/策略授权 |
| --- | --- | --- | --- | --- |
| 检查粒度 | 会话有效性 | 接口/路径 | 单个资源实例 | 主体+资源+环境 |
| 能否防 IDOR | 不能 | 不能 | 能 | 能 |
| 实现复杂度 | 低 | 低 | 中 | 高 |
| 策略可表达性 | 无 | 粗（角色） | 中（归属/ACL） | 强（动态上下文） |
| 典型风险 | 全面越权 | 水平越权 | 需防 TOCTOU | 策略配置错误 |
| 适用场景 | 内部低敏接口 | 后台管理 | 多租户业务 | 零信任/合规场景 |

## 六、常见误区

1. 登录即信任后续所有操作：把「已认证」当作「已授权」，导致全面越权。
2. 只做路由级检查：有 `read:doc` 权限并不意味着能读**任意**用户的 doc。
3. 把前端隐藏按钮当授权：攻击者可直接调用接口，服务端必须独立校验。
4. 先查后判导致 TOCTOU：检查与操作之间存在窗口，应合并为原子条件查询。
5. 列表接口漏授权：批量接口常被当作「只读」而省略归属过滤，实际是最常见泄露点。
6. 默认放行：策略未匹配时返回 `Permit`，一旦新增资源类型即自动暴露。
7. 只在应用层设防：数据库账号、对象存储桶、消息队列同样需要最小权限配置。

## 七、与开源书·权威来源对应

- Saltzer & Schroeder 1975 提出最小权限、默认拒绝、完全仲裁等经典安全原则。
- OWASP Top 10 A01 把「失效的访问控制」列为 Web 应用首要风险。
- OWASP Authorization Cheat Sheet 给出对象级授权、默认拒绝与避免 IDOR 的实践建议。
- NIST SP 800-162 系统化 ABAC，说明策略判定的属性模型。
- 具体合规要求以各标准官方最新版本为准。

## 八、面试题

1. 认证与授权的区别？——认证确认身份，授权决定该身份可对哪些对象做哪些操作。
2. 什么是 IDOR？——通过篡改对象标识访问未授权资源，根因是缺少对象级授权。
3. 为什么必须做对象级授权？——路由级角色无法表达归属关系，水平越权由此产生。
4. 完全仲裁的含义？——每次访问都独立判定，不因「之前通过」而跳过检查。
5. 默认拒绝为什么重要？——新资源上线时若策略缺失，默认放行会立即造成暴露。

## 九、演进与趋势

方向是「策略即代码」：把授权策略外置为可测试、可版本化的声明式规则（如 OPA/Rego），配合零信任在每次请求重判。细粒度属性授权（ReBAC/图权限）用于表达共享、委派等复杂关系。具体实现与规范以官方最新文档为准。

与之配套的是「授权可观测性」：把每次判定结果与命中策略记录下来，才能在生产环境定位「为什么这次请求被拒绝」或「为什么越权成功了」。

缺少可观测性时，策略会退化为不可验证的隐式规则，这正是访问控制失效类漏洞长期居高的原因之一。

因此在设计阶段就应明确：每条策略依赖哪些属性、缺省结论是什么、以及属性缺失时如何降级为拒绝。

## 十、小结

认证与授权必须严格分离，且授权要对每个对象在服务端完全仲裁、默认拒绝。对象级检查是防越权的关键，最小权限原则应贯穿权限模型设计、接口实现与运维配置的全过程。
