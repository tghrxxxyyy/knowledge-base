# 迁移中读写路由

> 对应 DeCandia 等 2007 (Dynamo)、Kleppmann《DDIA》第 5/6 章、Lamport 1978 (Logical Clocks) 与 Coulouris《Distributed Systems》第 18 章。

## 一、背景与挑战

分区迁移是一个有持续时间的过程。在这段时间里，同一个分区的数据同时存在于源节点与目标节点，而客户端、网关、协调者必须为每个请求给出一个明确的路由决策。路由错了会表现为三类症状：

- **读到旧值**：写已落在目标，读却走了源；
- **写入消失**：写落在源而源副本在切换后被清理；
- **瞬时不可用**：切换瞬间路由表未更新，请求打到已不再负责该分区的节点并直接被拒。

难点在于路由信息本身是**分布式状态**：如果把它放在中心节点，同一次切换的所有决策就有了统一来源，但中心成为延迟与可用性瓶颈；如果缓存在客户端，就可能出现「部分客户端已切、部分未切」的脑裂式路由。因此路由设计必须在**一致性、延迟与可用性**之间做选择，而选择的前提是弄清楚数据以哪一侧为权威。

## 二、核心原理

### 两种权威模型，决定了完全不同的读写策略

**模型 A：源为权威（source-primary / 日志转发）。** 所有写先落到源节点，源再把日志转发到目标。此时：

$$ \text{read}(P) \ \text{总是可以从 } src \ \text{安全读取} $$

因为源的写入序列是全局最新的，目标是它的回放副本。**读不需要合并**，只需要确保在切换之前读都走源。这是最简单也最易正确实现的模型，缺点是源在切换前是单点（若源故障且日志未复制，未转发的写会丢）。

**模型 B：双权威（dual-primary / 双写）。** 迁移期间写同时应用到源与目标（或在切换临界窗口内双写）。此时两侧可能有不同的写入历史：

$$ \text{read}(P) = \text{merge}\left( \text{get}(src),\ \text{get}(dst) \right) $$

必须依据版本信息（版本号、向量时钟、LWW 时间戳）选择或合并。模型 B 的写延迟更高、需要冲突解决，但能在源故障时继续服务。

**很多实现事故的根源是把两者混用**：写按模型 B 双写，读却只走源；或写只走源，读却两边扇出后用了错误的合并规则，把旧值当成新值返回。

### 路由表的表示与状态机

路由信息是「分区 → 位置集合」的映射，并带一个状态：

$$ R: P \to 2^{Nodes}, \qquad R_{normal}(P) = \left\{ owner \right\}, \qquad R_{mig}(P) = \left\{ src,\ dst \right\} $$

状态取值通常为 `SERVING(src)`、`MIGRATING(src → dst)`、`SERVING(dst)`。状态机只在两个方向迁移：`SERVING(src) → MIGRATING → SERVING(dst)`，不存在从 `MIGRATING` 直接跳到「两侧都不服务」的转换——否则会产生不可用窗口。

### 路由的分发与版本化

三种分发方式与相应的正确性手段：

| 方式 | 路由来源 | 陈旧风险 | 纠错机制 |
| --- | --- | --- | --- |
| 客户端表（smart client） | 本地缓存 + 订阅变更 | 有（缓存 TTL 内） | 服务端返回新版本号/重定向 |
| 中心代理 | 代理查询配置中心 | 低（可在请求时查） | 配置中心强一致读 |
| 服务端重定向 | 由服务端告知 | 有（客户端未更新） | `MOVED`（永久）/`ASK`（本次）语义区分 |

关键机制是**路由版本号（epoch / generation）**：路由表每次变更递增一个单调版本，客户端把版本号随请求（或随心跳）携带。

- 若服务端发现自己领先，返回新版本并让客户端刷新（"stale route" 纠正）；
- 若服务端发现自己落后（客户端更新的版本它不知道），拒绝服务并让客户端回退——这防止了「客户端超前于元数据」的脑裂。

Redis Cluster 的 `MOVED` 与 `ASK` 正是这一思想的极简实现：`MOVED` 表示槽已永久迁移，客户端可更新缓存；`ASK` 表示槽正在迁移、本次请去目标但**不要**更新缓存，因为其他键可能还在源上。

### 切换后的「落伍请求」（straggler）

切换是即时的，但网络上存在两类在途请求：

1. 客户端用旧路由发出的请求，在切换后才到达源节点；
2. 源节点已返回但客户端尚未收到、并被重试到目标节点的请求。

处理策略有三种，实际系统常组合使用：

- **重定向**：源节点拒绝并返回「已迁移，请去目标」+ 新 epoch。最简单，但客户端需要一次额外往返。
- **转发（forwarding）**：源节点把请求透明转发给目标。客户端无感知，但源必须保留转发能力一段时间（增加了切换后的复杂度）。
- **宽限期双服务（grace period）**：源在切换后一段时间内继续服务读请求。对读安全（源数据在清理前仍完整），对写则必须保证不会与目标产生分歧——通常只允许宽限读、不允许宽限写。

### 读写与一致性等级的配合

若分区是多副本（Dynamo 风格），迁移期间还要叠加法定人数语义。设每侧副本数为 $n$、写仲裁 $w$、读仲裁 $r$，则读到最新写需 $w + r > n$。迁移期间两侧都有副本时，需把读写集合的并集纳入仲裁计算：

$$ \left| W_{src} \cup W_{dst} \right| + \left| R_{src} \cup R_{dst} \right| > n_{total} $$

否则会出现「写成功但读不到」的经典问题。实践中为避免复杂化，通常让一侧（源）承担全部仲裁职责，另一侧只作为副本追赶，直到切换。

## 三、形式化与数学基础

**读合并的正确性条件。** 用版本函数 $v: Value \to \mathbb{N}$（或向量时钟 $\mathbb{V}$）表示新鲜度，读合并返回：

$$ \text{read}(P) = v^{-1}\left( \max \left\{ v(x) \ \middle|\ x \in \text{get}(src) \cup \text{get}(dst) \right\} \right) $$

对单值数据，这要求版本号**单调且无歧义**（同一逻辑写产生同一版本）。对向量时钟，若两侧版本不可比（并发写），则必须由业务规则决定（合并、让客户端解决、或按 LWW）。

**不丢写的充分条件。** 设切换时刻为 $t_{co}$，切换时源的写入日志位置为 $L_{co}$，目标已应用位置为 $L_{dst}(t_{co})$。则迁移不丢写的充分条件是：

$$ L_{dst}\left( t_{co} \right) \ge L_{co} $$

即「切换点之前产生的所有写都已到达目标」。这是切换必须等待追赶完成的数学依据。

**陈旧路由的暴露窗口。** 设客户端路由缓存 TTL 为 $T_{ttl}$，元数据变更传播延迟为 $T_{prop}$，则客户端可能使用陈旧路由的最长时间为：

$$ T_{stale} \le T_{ttl} + T_{prop} $$

该窗口内的请求必须由服务端侧的机制（epoch 比较、重定向、转发）兜住，不能寄希望于客户端及时更新。这是「路由必须带版本、服务端必须能做陈旧检测」的根本原因。

**重定向的额外时延。** 客户端受重定向时的额外往返为：

$$ \Delta T = 2 \cdot \frac{RTT}{2} = RTT $$

即多一个完整往返。若陈旧比例高、请求量又大，这部分开销会显著影响尾延迟——因此**用主动推送（订阅变更）减少重定向比例，比优化重定向本身更有效**。

**线性化与非线性化的界限。** 若迁移期间接受有界陈旧（读到最多滞后 $\Delta$ 的数据），则路由表可以放最终一致的配置中心；若要求线性化（任何读都能看到之前的写），则路由版本必须参与共识，且每次切换是一次线性化点：

$$ \text{cut-over} \in \text{LinearizationPoints} $$

工程上大多数系统选择前者（接受迁移窗口内的有界陈旧），只有强一致分片数据库（基于 Raft 派生的系统）选择后者。

## 四、代码实现

路由表结构与带 epoch 的读取路径（模型 A：源为权威，读只走源）：

```python
class RoutingTable:
    def __init__(self):
        self.epoch = 0
        self.table = {}          # partition -> dict(state, src, dst, owner)

    def begin_migration(self, p, src, dst):
        self.table[p] = {"state": "MIGRATING", "src": src, "dst": dst}
        self.epoch += 1

    def finish_migration(self, p, dst):
        self.table[p] = {"state": "SERVING", "owner": dst}
        self.epoch += 1

    def read_target(self, p):
        """模型 A：源始终持有最新数据，读一律走源，无需合并。"""
        info = self.table[p]
        return info["src"] if info["state"] == "MIGRATING" else info["owner"]
```

模型 B（双写）下的读写路径，带版本合并与陈旧路由检测：

```python
def route_read(p, client_epoch, routing, nodes):
    if client_epoch < routing.epoch:
        # 服务端领先：告知新版本，客户端应刷新后重试
        raise StaleRoute(routing.epoch)

    info = routing.table[p]
    if info["state"] == "MIGRATING":
        # 双写模型：两侧都可能更新，需按版本合并取最新
        a = nodes[info["src"]].get(p)
        b = nodes[info["dst"]].get(p)
        return merge_by_version(a, b)
    return nodes[info["owner"]].get(p)


def route_write(p, value, routing, nodes):
    info = routing.table[p]
    if info["state"] == "MIGRATING":
        # 双写：两边都必须成功；失败由上层重试（写操作必须幂等）
        ok = nodes[info["src"]].put(p, value) and nodes[info["dst"]].put(p, value)
        if not ok:
            raise WriteFailure(p)
        return
    nodes[info["owner"]].put(p, value)


def merge_by_version(a, b):
    if a is None:
        return b
    if b is None:
        return a
    return a if a.version >= b.version else b    # 取版本较新者
```

切换后的落伍请求处理：源节点拒绝并携带新 epoch，或选择透明转发：

```python
def handle_at_source(p, req, routing, nodes):
    info = routing.table[p]
    if info.get("state") == "SERVING" and info.get("owner") != self_node:
        if FORWARDING_ENABLED and req.is_read:
            # 宽限期内透明转发，客户端无感；写不转发以免产生分歧
            return nodes[info["owner"]].forward(req)
        # 默认：返回新 epoch，让客户端刷新路由后重试
        raise Redirect(owner=info["owner"], epoch=routing.epoch)
    return self.execute(req)
```

把路由表放进共识存储，使切换成为一次线性化写入：

```python
def cut_over(p, dst, meta_store, routing):
    # 单次 compare-and-set：只有当前版本匹配才提交，保证切换是原子的
    prev = meta_store.get_version("/routing/%d" % p)
    meta_store.cas(
        key="/routing/%d" % p,
        expect_version=prev,
        value={"state": "SERVING", "owner": dst},
    )
    routing.reload(p)          # 所有路由方在下一次读取时看到同一版本
```

版本号随心跳/请求携带，用于双向陈旧检测：

```python
def on_client_hello(peer_epoch, routing):
    if peer_epoch < routing.epoch:
        return Reply(kind="UPDATE", epoch=routing.epoch, table=routing.table)
    if peer_epoch > routing.epoch:
        # 客户端比本节点更新：本节点元数据落后，拒绝服务以免给出错误路由
        return Reply(kind="RETREAT", epoch=routing.epoch)
    return Reply(kind="OK", epoch=routing.epoch)
```

## 五、与其他技术对比

| 维度 | 源为权威 + 日志转发 | 双写 + 版本合并 | 客户端表 + 重定向 | 中心代理路由 | 共识内路由（Raft 配置变更） |
| --- | --- | --- | --- | --- | --- |
| 读是否需要合并 | 否（恒定走源） | 是（按版本） | 否 | 否 | 否 |
| 写路径开销 | 低（单写 + 转发） | 高（双写） | 低 | 低 | 中（复制） |
| 源故障可写性 | 不可写（除非日志已复制） | 可写 | 同左 | 同左 | 可写（多数派） |
| 陈旧路由风险 | 有 | 有 | 有（缓存 TTL 内） | 低 | 无（线性化） |
| 纠错机制 | epoch 比较 + 重定向/转发 | epoch + 版本合并 | `MOVED`/`ASK` 语义 | 代理重查 | 配置提交即生效 |
| 额外时延 | 切换后可能有 1 RTT | 写延迟升高 | 陈旧时 +1 RTT | 代理多一跳 | 复制延迟 |
| 实现复杂度 | 中 | 高（冲突解决） | 低（客户端） | 中 | 高（需共识层） |
| 典型系统 | Kafka 副本迁移、日志系统 | 多主 KV | Redis Cluster | 各类代理网关 | TiKV、CockroachDB |

核心判断依据是「谁持有权威版本」。若能在迁移期确定性地让一侧权威（源或目标），读写路由就退化为「查表 + 陈旧检测」；若必须两侧同时接受写（为了可用性），就必须引入版本合并，并接受冲突解决带来的复杂度与延迟。

## 六、常见误区

- **迁移中只读源，但写已双写。** 若目标已开始接收一部分路由的写，只读源就会漏掉这些写，出现读回退。
- **写只写目标。** 源上的旧数据未同步到目标、且切换前仍有请求读源，会造成数据回退与丢失。
- **路由表非原子更新。** 多客户端各自轮询配置会形成脑裂式路由，表现为间歇性陈旧读，极难排查。
- **只做单向陈旧检测。** 只让服务端纠正落后的客户端，而不拒绝「超前于元数据」的客户端，会在元数据回滚或分区恢复后产生错误路由。
- **切换后不处理落伍请求。** 没有重定向/转发机制时，在途请求会直接失败，表现为切换瞬间的错误率尖峰。
- **宽限期内允许写。** 宽限读是安全的（源数据在清理前完整），但宽限写会与目标产生分歧，必须禁止。
- **忽略路由缓存的 TTL 效应。** 缓存时间越长，陈旧窗口越大；必须在服务端兜底，而不是假设客户端会及时刷新。
- **在多副本场景忽略仲裁集合变化。** 迁移期两侧副本并存时若不扩大读写集合，会破坏 $w + r > n$ 的读己之写保证。

## 八、面试题

1. **迁移期间写为什么可能必须双写？**
   要点：切换前请求可能被路由到源或目标（取决于客户端缓存状态），若写只落一侧，另一侧就会缺失更新；双写（或日志转发）保证两侧都能收到全部写，待追上后再切。

2. **模型 A（源为权威）为什么读不需要合并？**
   要点：所有写先落源，目标是源的回放副本，因此源始终持有最新数据；只要读都走源，就不存在版本歧义。代价是源在切换前是单点。

3. **路由表为什么必须带版本号？**
   要点：用于双向陈旧检测——服务端可纠正落后的客户端，也能拒绝超前于元数据的客户端（防止元数据回滚或恢复后给出错误路由）。

4. **切换瞬间的在途请求怎么处理？**
   要点：三种手段——重定向（源拒绝并给出新 epoch）、透明转发（源把读转发到目标）、宽限期双服务（只允许宽限读）。三者常组合使用。

5. **为什么宽限期只能读不能写？**
   要点：源在清理前数据完整，读是安全的；写会同时落到源与目标而产生分歧，且切换后源不再是权威，宽限写会引入无法合并的冲突。

## 九、演进与趋势

最主要的方向是**把路由元数据放进共识系统**。etcd/ZooKeeper 保存路由表，使每次切换成为一次线性化写入，从根上消除「脑裂式路由」；Raft 系统更进一步，把迁移直接表达为配置变更，让「切换点」就是一次日志提交，读写路由由协议自动保证一致。代价是路由读取需要经过共识层（通常通过 watch 缓存与本地副本缓解），且分区数量受元数据规模约束。

第二个方向是**减少路由的粒度与频次**。固定分区数方案让 `key → partition` 永不变，路由表只在 `partition → node` 维度变化，规模从「键级」降到「分区级」；配合 epoch 增量推送（只推送变更的分区），客户端刷新成本大幅降低。

第三个方向是**客户端库的标准化**。越来越多的系统提供官方 smart client，内建路由缓存、epoch 校验、重定向重试与请求合并，把「迁移中读写路由」的正确性从「每个业务自行实现」收敛为「库保证」。Kubernetes 生态中的 service mesh 也在做类似的事：把路由与故障转移下沉到 sidecar，业务只看到稳定的服务名。总体趋势是**让路由正确性成为基础设施属性，而非应用开发者的负担**。

## 十、小结

迁移中读写路由的正确性取决于两个决定：**哪一侧是权威**，以及**路由如何分发与版本化**。若源为权威（日志转发），读只需恒定走源、无需合并，实现最简；若必须双写（双权威），则必须引入版本比较与合并规则，并接受更高的写延迟与冲突复杂度。

无论哪种模型，都必须具备三项兜底能力：切换前确认目标已追到切换点（不丢写）、路由带单调 epoch 并做双向陈旧检测（不出错路由）、切换后能处理落伍请求（重定向/转发/宽限读）。把路由表放进共识系统、或把迁移表达为 Raft 配置变更，是把这三项能力从「各自实现」升级为「协议保证」的最可靠路径。
