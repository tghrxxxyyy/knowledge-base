# 一致性哈希与虚拟节点

> 对应 Karger 等 1997 (Consistent Hashing and Random Trees)、DeCandia 等 2007 (Dynamo)、Thaler & Ravishankar 1998 (Rendezvous Hashing) 与 Kleppmann《DDIA》第 6 章。

## 一、背景与挑战

设想用 `hash(key) mod N` 把数据分到 $N$ 个节点。当 $N$ 变为 $N+1$ 时，对几乎每个 key 都有：

$$ h(key) \bmod N \neq h(key) \bmod (N+1) $$

平均只有 $1/(N+1)$ 的 key 恰好保持不变，因此**几乎所有数据都要重新分配**。对缓存系统这意味着缓存集体失效（雪崩）；对存储系统意味着全量搬迁（不可完成的任务）。

问题的根源在于：`mod N` 把「key 到位置的映射」与「节点数量」耦合在一起。任何改变节点数的操作都会改写整个映射表。

一致性哈希（Consistent Hashing，Karger 等 1997）的洞见是把「位置」从「节点的编号」中解耦出来：先把节点映射到一个固定的地址空间（哈希环），再把 key 映射到同一空间并规定「顺时针遇到的第一个节点即归属」。这样节点数变化只影响环上的一段局部区间，其余 key 的归属纹丝不动。

但原版一致性哈希有一个实用缺陷：节点少时，每个节点占有的环上区间长度差异很大，负载可能相差数倍。虚拟节点（virtual node，vnode）正是为此而引入：让每个物理节点在环上占多个位置，从而把「一段大区间」拆成「多个小区间」，让随机性抹平不均衡。

## 二、核心原理

### 环结构与归属规则

取一个哈希空间 $[0, 2^{32})$ 并首尾相连成环。对每个节点 $n$ 计算 $h(n)$ 落在环上；对每个 key $k$ 计算 $h(k)$，从 $h(k)$ 出发顺时针找到第一个节点：

$$ owner(k) = \arg\min_{n} \left\{ h(n) \ \middle|\ h(n) \ge h(k) \right\} \quad (\text{若无则回绕到最小}) $$

**节点加入**时，它在环上落点顺时针相邻的区间（原属于后继节点）被切走一半给新节点；**节点退出**时，它占的区间整体交给后继节点。两者的影响范围都是局部的，与 $N$ 无关。

### 虚拟节点

每个物理节点注册 $V$ 个哈希位置：

$$ \text{positions}(n) = \left\{ h\left( n \mathbin{\|} \#i \right) \ \middle|\ i = 0, \dots, V-1 \right\} $$

于是每个物理节点在环上占有 $V$ 段小区间。$V$ 越大：

- 负载越均衡（随机切分粒度的方差下降）；
- 迁移粒度越细（新节点从多个旧节点各偷一小段，而不是抢走一整段）；
- 元数据与内存成本越高（环上有 $NV$ 个位置）。

Dynamo 与 Cassandra 都采用 vnode 结构，并把 $V$ 作为可调参数以适配不同规模的集群。

### 带权虚拟节点（异构硬件）

若新机型容量是旧机型的两倍，可让它注册 $2V$ 个 vnode，使期望负载与其容量成正比：

$$ V(n) = V_0 \cdot \frac{\text{capacity}(n)}{\text{capacity}_{base}} $$

这把「均衡」从「等量」推广到「等比」，是混部集群中的标准做法。

### 多副本放置

有副本因子 $R$ 时，从 $h(k)$ 出发顺时针依次取 $R$ 个**互不相同的物理节点**作为副本位置（Dynamo 称为 preference list）。关键约束是必须**跳过同一物理节点**的其他 vnode，否则多个副本会落在同一台机器上，失去容错意义；进一步还应结合机架/可用区反亲和，避免同机架故障带走全部副本。

## 三、形式化与数学基础

**迁移量界。** 从 $N$ 个节点扩展到 $N+1$ 个，只有被新节点覆盖的区间需要迁移，期望迁移比例为：

$$ \frac{K}{N+1} $$

而 `mod N` 方案为 $K \cdot (1 - \frac{1}{N+1}) \approx K$。设 $N = 100$，一致性哈希迁移约 1% 的数据，`mod N` 迁移约 99%——相差两个数量级。

**负载偏离界。** 每个 vnode 占有的环上区间长度在期望上相同，因此单个 vnode 的负载均值为 $1/(NV)$。所有 vnode 的实际长度为独立同分布随机变量，最大值的偏离量级为：

$$ L_{vnode}^{max} = \frac{1}{NV} \left( 1 + O\!\left( \sqrt{\frac{\log (NV)}{1}} \right) \right) $$

聚合到物理节点（每节点 $V$ 段）后，最大负载相对平均值的偏离为：

$$ \left| L_{max} - \frac{K}{N} \right| = O\!\left( \frac{K}{N} \sqrt{\frac{\log V}{V}} \right) $$

它给出了两条实用结论：**偏离随 $\sqrt{\log V / V}$ 递减**（收益递减，$V$ 从 100 提到 1000 只改善约 3 倍），以及**当 $V = O(\log N)$ 时最大负载与平均值之比有常数上界**（以高概率）。因此工程上取 $V$ 为数百量级通常已经足够，继续增大只会线性增加内存与查找开销。

**查找复杂度。** 把 $NV$ 个位置存成有序数组后二分查找：

$$ T_{locate} = O\left( \log (NV) \right), \qquad M_{ring} = O(NV) $$

若改用 rendezvous（HRW）哈希，内存为 $O(1)$ 但每次查找需计算 $N$ 次哈希（$O(N)$）；Jump Consistent Hash 则是 $O(\ln N)$ 时间、$O(1)$ 内存，但只支持桶数量的单调变化。三者的选择取决于「节点集合变化是否任意」与「查找频率」。

**哈希函数的要求。** 环上位置的均匀性直接决定均衡质量，因此哈希函数必须雪崩性好、分布均匀（MD5、SHA-1、murmur3、xxhash 均可用）。更重要的是：**key 与节点必须使用同一个哈希函数、同一个哈希空间**。混用不同函数会让「顺时针查找」失去意义，是最常见也最隐蔽的实现错误。

## 四、代码实现

完整的一致性哈希环，含虚拟节点、二分查找与多副本放置：

```python
import bisect, hashlib

def h(s: str) -> int:
    """统一的哈希函数：key 与节点必须共用同一个，映射到 32 位空间。"""
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:4], "big")

class ConsistentHashRing:
    def __init__(self, nodes=(), vnodes=256, replicas=3):
        self.vnodes = vnodes
        self.replicas = replicas
        self._pos = []           # 有序的 vnode 位置
        self._owner = {}         # position -> (physical_node, vnode_index)
        for n in nodes:
            self.add(n)

    def _vpos(self, node: str, i: int) -> int:
        return h("%s#%d" % (node, i))       # 同一物理节点的第 i 个虚拟节点

    def add(self, node: str):
        for i in range(self.vnodes):
            p = self._vpos(node, i)
            self._pos.append(p)
            self._owner[p] = (node, i)
        self._pos.sort()

    def remove(self, node: str):
        for i in range(self.vnodes):
            p = self._vpos(node, i)
            self._owner.pop(p, None)
        self._pos = [p for p in self._pos if p in self._owner]

    def _iter_nodes(self, key: str):
        """从 key 的位置顺时针遍历 vnode，按物理节点去重。"""
        if not self._pos:
            return
        idx = bisect.bisect_left(self._pos, h(key))
        seen = set()
        n = len(self._pos)
        for step in range(n):
            node, _ = self._owner[self._pos[(idx + step) % n]]
            if node not in seen:
                seen.add(node)
                yield node
                if len(seen) >= self.replicas + 1:
                    return

    def locate(self, key: str) -> str:
        return next(iter(self._iter_nodes(key)))

    def replicas_for(self, key: str):
        """返回 R 个互不相同的物理节点，跳过同节点的其他 vnode。"""
        out, seen = [], set()
        for node in self._iter_nodes(key):
            if node not in seen:
                seen.add(node)
                out.append(node)
            if len(out) == self.replicas:
                break
        return out
```

查看一个 key 的归属与副本、以及节点增减对归属的影响：

```python
ring = ConsistentHashRing(["node-a", "node-b", "node-c"], vnodes=128, replicas=2)

for key in ["user:1001", "user:1002", "order:88"]:
    print(key, "->", ring.locate(key), ring.replicas_for(key))

# 统计加入新节点后需要迁移的 key 比例（应接近 1/(N+1)）
before = {k: ring.locate(k) for k in ("k%d" % i for i in range(20000))}
ring.add("node-d")
after = {k: ring.locate(k) for k in before}
moved = sum(1 for k in before if before[k] != after[k])
print("moved ratio = %.3f (expect ≈ %.3f)" % (moved / len(before), 1 / 4))
```

带权虚拟节点（容量翻倍的节点获得双倍 vnode）：

```python
def add_weighted(ring: ConsistentHashRing, node: str, weight: float):
    n = max(1, int(ring.vnodes * weight))
    for i in range(n):
        p = ring._vpos("%s:w%.1f" % (node, weight), i)
        ring._pos.append(p)
        ring._owner[p] = (node, i)      # 归属仍记录为物理节点
    ring._pos.sort()
```

对比：rendezvous（HRW）哈希，无需环结构，迁移性质相同：

```python
def hrw_locate(key: str, nodes):
    """对每个节点计算 h(key, node)，取最大者。节点增删只影响被增减节点服务的 key。"""
    return max(nodes, key=lambda n: h("%s@%s" % (key, n)))
```

## 五、与其他技术对比

| 维度 | `hash mod N` | 一致性哈希 + vnode | Rendezvous (HRW) | Jump Consistent Hash | 固定分区数（哈希槽） |
| --- | --- | --- | --- | --- | --- |
| 增删节点迁移量 | $\approx K$ | $K/(N+1)$ | $K/(N+1)$ | 桶数变化时约 $K/2$ | $K/(N+1)$（按分区） |
| 查找复杂度 | $O(1)$ | $O(\log (NV))$ | $O(N)$ | $O(\ln N)$ | $O(1)$ |
| 额外内存 | $O(1)$ | $O(NV)$ | $O(1)$ | $O(1)$ | $O(P)$ |
| 负载均衡手段 | 无（依赖均匀哈希） | 增加 $V$ | 增加节点数 | 天然均匀 | 增加 $P$ + 分配算法 |
| 支持任意增删 | 是（但代价极高） | 是 | 是 | 否（仅桶数变化） | 是 |
| 带权支持 | 难 | 易（权 = vnode 数） | 中（加权随机） | 否 | 易（按权重分配分区数） |
| 典型系统 | 早期缓存/DB 分库 | Dynamo、Cassandra | 部分 LB、CDN | 部分分片后端 | Kafka、Redis Cluster |

选择建议：**节点集合任意变化且需要带权与多副本**时选一致性哈希；**查找成本敏感且节点数不大**时选 rendezvous；**只按固定桶数扩容**的无状态分片可用 jump hash；**需要精确控制数据位置（机架感知、手动指派）**时选固定分区数方案。

## 六、常见误区

- **不使用虚拟节点。** 物理节点少时（例如 5 台），单节点负载可能相差数倍，是最常见的实现缺陷。
- **认为一致性哈希绝对均衡。** 只有 $V$ 足够大时才近似均衡；$V$ 小或节点数少时偏离可能显著。
- **key 与节点使用不同哈希函数或不同空间。** 环的「顺时针」语义随即失效，表现为「数据能存但读不到」。
- **多副本时不跳过同一物理节点的其他 vnode。** 会把多个副本放到同一台机器，容错能力名存实亡。
- **忽略机架/可用区反亲和。** 环上相邻的物理节点可能在同一机架，一次机架故障即丢失全部副本。
- **$V$ 取得过大。** 内存与查找成本线性上升，而均衡收益按 $\sqrt{\log V/V}$ 递减，收益极小。
- **加入节点后不做数据搬迁就以为生效。** 环只决定「新数据去哪」，已存在的旧数据必须由迁移流程搬过去，否则会造成长期的双份数据与不一致。
- **环上位置不经持久化。** 重启后若 vnode 位置重新计算且哈希函数/种子变化，整个映射会改变，导致全量错位。

## 七、与开源书·权威来源对应

- Karger 等 1997《Consistent Hashing and Random Trees: Distributed Caching Protocols for Relieving Hot Spots on the World Wide Web》：一致性哈希的提出，含「增删节点只影响相邻区间」的性质与虚拟节点的均衡分析。
- DeCandia 等 2007《Dynamo: Amazon's Highly Available Key-value Store》：vnode、preference list、协调者与仲裁读写的工程实现。
- Thaler & Ravishankar 1998《Using Name-Based Mappings to Increase Hit Rates》：Rendezvous（HRW）哈希，提供无环结构的最小迁移映射。
- Lamping & Veach 2014《A Fast, Minimal Memory, Consistent Hash Algorithm》：Jump Consistent Hash 的 $O(\ln N)$ 无状态算法。
- Kleppmann《DDIA》第 6 章：分区策略、倾斜与「不要用 mod N」的系统性论证。
- Coulouris 等《Distributed Systems》：分布式数据分布与可扩展性框架。
- Redis Cluster 官方规范：以 16384 个哈希槽替代连续环的生产级取舍。

## 八、面试题

1. **一致性哈希为什么能减少迁移？**
   要点：key 与节点映射到同一固定哈希空间，归属由「顺时针第一个节点」决定。节点增删只改变环上相邻区间，其余 key 归属不变，迁移量约 $K/(N+1)$。

2. **虚拟节点解决了什么问题？**
   要点：把每个物理节点的一大段区间拆成 $V$ 个小段，降低负载方差（偏离随 $\sqrt{\log V/V}$ 下降），并使新节点能从多个旧节点均匀偷取区间，迁移更平滑。

3. **一致性哈希的查找复杂度与内存开销是多少？**
   要点：环上有 $NV$ 个位置，用有序数组二分查找为 $O(\log(NV))$，内存 $O(NV)$。若不想付出内存，可用 rendezvous 哈希（$O(1)$ 内存、$O(N)$ 时间）或 Jump hash（$O(1)$ 内存、$O(\ln N)$ 时间，但仅支持桶数变化）。

4. **多副本如何放置？**
   要点：从 key 位置顺时针走，依次取 $R$ 个互不相同的物理节点（跳过同节点其他 vnode），并结合机架/可用区反亲和，保证故障域隔离。

5. **为什么 key 与节点必须用同一哈希函数？**
   要点：环的归属依赖两者在同一数值空间中的相对位置；若函数或空间不同，比较无意义，会出现路由错位，属于隐蔽严重的实现错误。

## 九、演进与趋势

一致性哈希的已知短板是「负载上界是概率性的」：虽然期望均衡良好，但极端情况下仍可能出现单个节点负担显著偏高的「重尾」。为此出现了**有界负载一致性哈希（consistent hashing with bounded loads）**：在保持最小迁移性质的同时，对每个节点设定容量上界，超出的 key 溢出到环上的下一个节点。这使最坏情况负载被显式约束，代价是牺牲部分「最小迁移」的严格性。Google 的若干大规模系统采用了这一变体。

另一条演进路线是**用更简单的无环算法替代环**。Rendezvous 哈希在缓存与负载均衡器场景中广泛使用，因为它无需维护环、天然支持权重扩展；Jump Consistent Hash 则在对「桶数单调增长」有保证的分片后端中提供了完美均匀且极低开销的方案。它们的共同特点是「把一致性哈希的结论（最小迁移）与实现结构解耦」。

在系统层面，固定分区数（哈希槽）方案因其「迁移粒度可控、支持机架感知与手动指派」的优势，在需要运维可控性的场景中反而更主流（Redis Cluster 的 16384 槽、Kafka 的分区）。因此现实中的选择往往不是「用不用一致性哈希」，而是**「用结构化的环，还是用两层映射的固定分区」**——前者胜在优雅与自动，后者胜在可控与可观测。未来的方向是把两者的优点结合：结构自动、上界显式、迁移可编排。

## 十、小结

一致性哈希用「先映射到固定空间，再按顺时针归属」的巧妙设计，把节点数量变化的影响限制在环上的局部区间，使扩容迁移量从近全量降到 $K/(N+1)$。虚拟节点通过把每个物理节点拆成 $V$ 个环上位置，显著改善了负载均衡（偏离按 $\sqrt{\log V/V}$ 递减），并使迁移粒度更细、支持带权与多副本放置。

实现上必须牢记三条：key 与节点共用同一哈希函数与空间；多副本要跳过同物理节点的其他 vnode 并考虑机架反亲和；环位置需持久化以免重启后映射漂移。替代方案（rendezvous、jump hash、固定分区数）各有适用面，选择取决于节点集合是否任意变化、查找成本敏感度与运维可控性要求。
