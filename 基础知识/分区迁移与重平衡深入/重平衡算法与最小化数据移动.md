# 重平衡算法与最小化数据移动

> 对应 Karger 等 1997 (Consistent Hashing)、DeCandia 等 2007 (Dynamo)、Lamping & Veach 2014 (Jump Consistent Hash)、Thaler & Ravishankar 1998 (Rendezvous Hashing) 与 Kleppmann《DDIA》第 6 章。

## 一、背景与挑战

集群规模会变化：扩容、缩容、故障替换、机房迁移。任何一次成员变更都要求把一部分数据从旧节点搬到新节点，这个过程称为重平衡（rebalancing）。它面临三个互相冲突的目标：

- **均衡**：迁移后各节点负载尽量接近（否则热点节点仍会拖慢整体）；
- **最小迁移**：搬运量与迁移时间尽量小（迁移占用网络与磁盘 IO，直接影响线上延迟与可用性）；
- **持续可用**：迁移过程中读写不能中断，不能丢数据。

朴素方案（例如 `hash(key) mod N`）在 $N$ 变化时会把几乎所有 key 重新映射，导致全量搬迁——这既不可接受也无法在合理时间内完成。因此重平衡算法的核心问题是：**是否存在一种映射结构，使得成员变更只需移动恰好必要的那部分数据？** 答案是肯定的，路线有两条：结构化的一致性哈希，与无环的 rendezvous/jump 类哈希。

## 二、核心原理

### 路线一：一致性哈希 + 虚拟节点

把节点与 key 都映射到同一个哈希环 $[0, 2^{32})$，key 归属于顺时针方向的第一个节点。新增节点只从环上相邻位置「偷取」一段区间，其余 key 的归属不变，因此迁移量正比于 $1/(N+1)$ 而非 $1$。

单纯的一致性哈希在节点少时分布不均（区间大小方差大），引入虚拟节点后每个物理节点在环上占 $V$ 个位置，把「一个大区间」拆成「$V$ 个小区间」，均衡度随 $V$ 提升。Dynamo 与 Cassandra 都采用这一结构，并把 $V$ 作为可调参数。

### 路线二：固定分区数（partition-based）

Dynamo 之前的多数系统采用另一种更易运维的结构：**分区数量远大于节点数且固定不变**。例如初始化时就创建 $P = 1024$ 个分区，key 通过 `hash(key) mod P` 映射到分区，分区再分配给节点。

关键在于**两层映射解耦**：`key → partition` 的映射永不变化，成员变更只改变 `partition → node` 的映射，因此迁移的粒度是「整个分区」。新增一个节点时，从每个现有节点各取走一部分分区，也能做到均衡且迁移量约为 $P/(N+1)$ 个分区。Cassandra 与 Kafka 采用这种思路（Kafka 的分区重分配即此模型）。

DDIA 第 6 章总结得很好：**不要用 `hash mod N`，因为它把「key 到分区的映射」和「分区到节点的映射」耦合在一起，导致成员变更必须重映射所有 key。**

### 路线三：无环哈希（rendezvous / jump）

两类无需维护环结构的算法：

- **Rendezvous（最高随机权重，HRW）**：对每个 key 与每个节点计算 $h(key, node)$，选值最大者。节点集合变化时，只有原本由被移除节点服务的 key 会重新选择，迁移量同样为 $1/(N+1)$。优点是实现极简、无需虚拟节点；缺点是每个 key 需计算 $N$ 次哈希，$N$ 大时成本高。
- **Jump Consistent Hash**：用一段紧凑的循环在 $O(\ln N)$ 时间内确定性地把 key 映射到 $[0, N)$ 中的桶，无需存储、分布完全均匀，但**只支持桶数量变化**（不支持任意节点增删，只能按序号扩容）。适合分片数单调增长的后端存储。

### 主动均衡与贪心迁移

上述方法解决「结构上最少移动」，但不解决「实际负载不均」——因为数据大小、访问热度并非均匀，且节点可能异构。因此还需要**主动均衡器**：周期性计算各节点负载，反复挑选「最重节点」与「最轻节点」，把一个分区从前者迁到后者，直到负载差小于阈值。

工程上的三个约束决定了它能否落地：迁移**并发度**（同时迁移多少个分区）、迁移**速率上限**（每节点带宽配额）、以及**滞回阈值**（避免在阈值附近来回抖动）。

## 三、形式化与数学基础

设总 key 数为 $K$，节点数为 $N$，每节点平均持有 $K/N$。

**新增一个节点时的最小迁移量。** 新节点最终应持有 $K/(N+1)$，这些数据只能来自原有节点，因此：

$$ M_{N \to N+1} = \frac{K}{N+1} $$

且每个旧节点平均贡献：

$$ m_{per\ node} = \frac{K}{N(N+1)} $$

**移除一个节点时：** 该节点全部数据需重新分配，故 $M_{N \to N-1} = K/N$（比扩容更贵，这也是「缩容比扩容更危险」的定量原因）。

作为对照，`hash(key) mod N` 的迁移量为：当 $N \to N+1$ 时，key $k$ 保持归属不变的概率为 $\frac{1}{N+1}$，故：

$$ M_{mod} = K \left( 1 - \frac{1}{N+1} \right) \approx K $$

即几乎全量搬迁，与一致性哈希的 $K/(N+1)$ 相差 $O(N)$ 倍。

**虚拟节点数的均衡界。** 设每物理节点 $V$ 个虚拟节点，最大负载相对平均值的偏离量级为：

$$ \left| L_{max} - \frac{K}{N} \right| = O\!\left( \frac{K}{N} \sqrt{\frac{\log V}{V}} \right) $$

即 $V$ 越大越均衡，但收益按 $\sqrt{\log V / V}$ 递减——把 $V$ 从 100 提到 1000 只带来约 3 倍改善，而维护成本（内存中的环、每次查找的二分）线性上升。工程上取数百量级通常足够。

**贪心均衡的收敛性。** 设负载向量 $L = (L_1, \dots, L_N)$，定义不均衡度：

$$ \Delta(L) = \max_i L_i - \min_i L_i $$

每轮选择使 $\Delta$ 下降最多的 $(partition, target)$ 对执行迁移。由于分区大小有下界，算法在有限步内达到 $\Delta < \tau$（阈值）的稳定状态；但若阈值取得过小，小分区的往复迁移会造成抖动，因此需要滞回：

$$ \text{migrate} \iff \Delta > \tau_{high}, \qquad \text{stop} \iff \Delta < \tau_{low}, \qquad \tau_{low} < \tau_{high} $$

## 四、代码实现

一致性哈希环与「新节点偷取区间」的核心逻辑（简化示意）：

```python
import bisect, hashlib

def h(s: str) -> int:
    return int(hashlib.md5(s.encode()).hexdigest()[:8], 16)

class Ring:
    def __init__(self, nodes, vnodes=256):
        self.vnodes = vnodes
        self.positions = []          # 有序的虚拟节点哈希位置
        self.owner = {}              # position -> node
        for n in nodes:
            self.add(n)

    def add(self, node):
        for i in range(self.vnodes):
            p = h("%s#%d" % (node, i))
            self.positions.append(p)
            self.owner[p] = node
        self.positions.sort()

    def locate(self, key):
        p = h(key)
        idx = bisect.bisect_left(self.positions, p)   # 顺时针找第一个
        if idx == len(self.positions):
            idx = 0                                    # 回绕
        return self.owner[self.positions[idx]]
```

固定分区数模型：成员变更只改 `partition -> node`，`key -> partition` 不变，因此可精确控制迁移粒度：

```python
NUM_PARTITIONS = 1024      # 固定且远大于节点数

def partition_of(key: str) -> int:
    return h(key) % NUM_PARTITIONS      # 永不随成员变化

def build_assignment(nodes):
    # 目标：均分分区，且相对上次分配尽量少动
    n = len(nodes)
    base, extra = divmod(NUM_PARTITIONS, n)
    assign = {}
    cursor = 0
    for i, node in enumerate(nodes):
        cnt = base + (1 if i < extra else 0)
        for p in range(cursor, cursor + cnt):
            assign[p] = node
        cursor += cnt
    return assign
```

Jump Consistent Hash（无状态、$O(\ln N)$、完美均匀，仅支持桶数变化）：

```python
def jump_hash(key: int, num_buckets: int) -> int:
    # 与 Lamping & Veach 的算法结构一致：以 64 位运算实现
    b, j = -1, 0
    while j < num_buckets:
        b = j
        key = (key * 2862933555777941757 + 1) & 0xFFFFFFFFFFFFFFFF
        j = int((b + 1) * (float(1 << 31) / float((key >> 33) + 1)))
    return b
```

带滞回与速率限制的贪心均衡器：

```python
def rebalance(nodes, partitions, tau_high, tau_low, max_inflight):
    """每轮迁移一个分区，直到不均衡度低于低阈值；滞回避免抖动。"""
    moved = 0
    inflight = 0
    while True:
        loads = {n.id: n.load for n in nodes}
        delta = max(loads.values()) - min(loads.values())
        if delta <= tau_low:
            break                            # 已足够均衡，停止
        if delta <= tau_high:
            break                            # 落入滞回带：不再继续迁移
        if inflight >= max_inflight:
            break                            # 迁移并发已达上限，等下一轮
        heavy = max(nodes, key=lambda n: n.load)
        light = min(nodes, key=lambda n: n.load)
        p = heavy.pick_heaviest_partition()  # 选收益最大的待迁分区
        if p is None:
            break
        start_migration(p, src=heavy, dst=light)
        moved += p.size
        inflight += 1
    return moved
```

## 五、与其他技术对比

| 维度 | 一致性哈希 + vnode | 固定分区数 | Rendezvous (HRW) | Jump Consistent Hash | 范围分区 |
| --- | --- | --- | --- | --- | --- |
| 迁移量（$N \to N+1$） | $K/(N+1)$ | $K/(N+1)$ | $K/(N+1)$ | 桶数翻倍时约 $K/2$ | 视分裂策略，可精确控制 |
| 每 key 查找成本 | $O(\log(NV))$ 二分 | $O(1)$ | $O(N)$ | $O(\ln N)$ | $O(\log N)$ 树查找 |
| 额外内存 | 环（$NV$ 项） | 分区表（$P$ 项） | 无 | 无 | 边界表 |
| 支持任意节点增删 | 是 | 是 | 是 | 否（仅桶数变化） | 是 |
| 可控性 | 中（靠 $V$） | 高（分区可精确指派） | 低 | 低 | 高（可手动挪热点段） |
| 典型系统 | Dynamo、Cassandra | Kafka、Elasticsearch | 部分 LB / 缓存 | 部分分片后端 | HBase、TiKV、RocksDB 层 |
| 主要难点 | 环维护与均衡度 | 分区数需预估 | 计算成本随 $N$ 增长 | 不支持缩容 | 热点段需人工干预 |

选择依据：需要**精确控制数据位置**（如同步迁移、机架感知、异构硬件）时选固定分区数或范围分区；需要**动态成员且实现简单**时选一致性哈希；连接层无状态分片（如负载均衡器选后端）可用 rendezvous 或 jump。

## 六、常见误区

- **一次性全量重排。** 迁移风暴会占满网络与磁盘，导致线上延迟飙升甚至雪崩。应增量分批、限速、限并发。
- **忽视迁移成本只看均衡度。** 为消除 5% 的负载差而搬运数百 GB 数据不划算；应把迁移代价纳入目标函数。
- **阈值过低导致抖动。** 在阈值附近反复迁移，既消耗资源又让路由表持续变动。必须设置滞回带。
- **用 `hash(key) mod N` 做分片。** 成员一变即全量搬迁，是最常见也最致命的设计错误。
- **分区数取得太小。** 若 $P \approx N$，单节点故障会让负载无法均分（只能整体接管），且迁移粒度太粗。工程上常取 $P$ 为节点数的数十到数百倍。
- **忽略缩容比扩容更贵。** 缩容要搬走整个节点的数据（$K/N$），而扩容只需 $K/(N+1)$；下线节点前应先把数据主动迁出。
- **认为一致性哈希天然均衡。** 只有虚拟节点足够多时才近似均衡；物理节点少且 $V$ 小时偏差可能达数倍。

## 七、与开源书·权威来源对应

- Karger 等 1997《Consistent Hashing and Random Trees》：一致性哈希的提出与「成员变更只影响相邻区间」的性质证明。
- DeCandia 等 2007《Dynamo: Amazon's Highly Available Key-value Store》：虚拟节点、分区分配与主动再平衡的工程实践。
- Lamping & Veach 2014《A Fast, Minimal Memory, Consistent Hash Algorithm》：Jump Consistent Hash 的 $O(\ln N)$ 无状态算法。
- Thaler & Ravishankar 1998《Using Name-Based Mappings to Increase Hit Rates》：Rendezvous（HRW）哈希，说明其最小迁移性质。
- Kleppmann《DDIA》第 6 章：分区再平衡策略（固定分区数、动态分区、按节点比例）与成本分析。
- Kleppmann《DDIA》第 5 章：复制与分区交互，理解迁移期间的读写路由前提。
- Coulouris 等《Distributed Systems》：数据分布与可扩展性的一般性讨论。

## 八、面试题

1. **如何最小化扩缩容时的数据移动？**
   要点：用一致性哈希使只有相邻区间移动，迁移量约 $K/(N+1)$；或用固定分区数解耦两层映射，按分区粒度迁移；也可用 rendezvous/jump 哈希。关键是避免 `mod N`。

2. **为什么 `hash(key) mod N` 不可用？**
   要点：成员变更会改变几乎所有 key 的映射，迁移量近似全量 $K$，与一致性哈希的 $K/(N+1)$ 相差 $O(N)$ 倍。

3. **固定分区数方案的优势是什么？**
   要点：把 `key → partition` 与 `partition → node` 解耦，前者永不变，成员变更只改后者，迁移粒度是整个分区，运维可控且便于机架感知与手动指派。

4. **虚拟节点为什么能改善均衡？**
   要点：把每个物理节点的「一个大区间」拆成 $V$ 个小区间，随机化程度提高，最大负载偏离随 $\sqrt{\log V/V}$ 下降；但收益递减，$V$ 取数百量级通常足够。

5. **主动均衡器如何避免抖动？**
   要点：设置滞回双阈值（超过高阈值才迁，低于低阈值才停）、限制并发迁移数与每节点带宽配额，并把迁移代价纳入决策而非只看负载差。

## 九、演进与趋势

重平衡的演进方向是把「事后补救」变成「事前规划」。基于历史负载与业务增长的预测性再平衡（在热点形成前预先把分区迁到空闲节点）比纯反应式更平滑；结合异构硬件权重的带权虚拟节点让新旧机型混部时也能均衡；在云环境中，节点生命周期短、弹性伸缩频繁，重平衡从「偶发运维操作」变成了「持续后台过程」，因此限速与优先级（迁移流量标记为低优先级）成为必要能力。

另一个明显趋势是**把迁移纳入共识**。Raft 的成员变更（joint consensus）与分片共识（如 Multi-Raft）把「数据迁移」表达为日志复制的一部分，使迁移过程具备明确的一致性语义与原子切换点，避免了状态机分裂。TiKV、CockroachDB 等系统即采用这一路线，代价是分区数量受共识开销约束。

在存储引擎层面，分区的物理迁移正被更多「共享存储 + 元数据切换」的方案替代：数据不再搬移，只改指向（如存算分离架构下的对象存储引用），把重平衡的代价从「搬字节」降为「改元数据」。这可能是未来最具颠覆性的方向。

## 十、小结

重平衡的本质是在均衡、迁移成本与可用性之间做三角权衡。最小化数据移动的基础是撤销 `mod N`，改用一致性哈希（配虚拟节点）、固定分区数或 rendezvous/jump 类无环哈希，其共同性质是成员变更只移动 $K/(N+1)$ 量级的数据。

结构解决「最少移动」，主动均衡器解决「实际不均」；后者必须配套滞回阈值、并发上限与速率限制，否则会把再平衡变成新的故障源。工程实践中最稳的组合是「固定分区数或带权 vnode 提供结构基础 + 带滞回的贪心迁移器做负载修正 + 共识协议保证切换原子」。
