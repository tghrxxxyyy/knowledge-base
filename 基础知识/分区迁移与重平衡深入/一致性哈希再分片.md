# 一致性哈希再分片

> 对应 Karger 等 1997 (Consistent Hashing)、DeCandia 等 2007 (Dynamo)、Lim 等 2014 (Redis Cluster) 与 Kleppmann《DDIA》第 6 章。

## 一、背景与挑战

一致性哈希解决了「节点增减时迁移量最小」的问题，但它隐含一个假设：**分区（分片）的数量与节点数量同阶**。一旦改为「分区数远大于节点数」的两层结构，问题就从「节点如何分配区间」变成了「分区本身如何增删与搬迁」，这就是再分片（resharding）。

再分片的出现有几类现实动因：

- **初始分区数预估不足**：单分区数据或吞吐超过单节点能力，必须把一个分区分裂成多个；
- **分区数过多**：大量小分区带来元数据与心跳开销，需要合并；
- **分片键或分布策略变更**：例如从 `hash(key)` 改为 `hash(user_id)`，边界全部重划；
- **异构硬件与地域策略**：需要更细的迁移粒度以适配权重。

再分片的难点不同于一般迁移：它改变了**边界本身**，因此 `key → partition` 的映射会发生变化。如何在映射变化的同时保持线上可用、不丢数据、且不产生大规模重映射，是本文的核心。

## 二、核心原理

### 两种再分片模型

**模型一：预分片 + 固定边界（pre-sharding）。** 在集群初始化时就创建远多于节点数的分区（例如 1024 个），并约定分区数量**永不改变**。此时：

$$ key \to partition: \text{固定}, \qquad partition \to node: \text{可变} $$

再分片退化为「分区重新指派」，即普通迁移，不存在边界变化问题。Kafka、TiKV 早期的多数系统、以及各类「固定分片数」方案都属此类。它的代价是分区数必须一次预估得当——过少则单分区成为瓶颈，过多则元数据膨胀。

**模型二：动态边界（split / merge）。** 分区边界可运行时变化：当某分区超过大小阈值就分裂（split），当相邻小分区过多就合并（merge）。范围分区系统普遍采用此法：HBase 的 region、TiKV 的 region、MongoDB 的 chunk 都支持分裂，部分支持合并（如 TiKV 的 Region Merge、HBase 的 merge API）。

分裂的核心机制是**用两个新分区替换一个旧分区**，且这是元数据层面的原子替换：

$$ P \longrightarrow \left\{ P_{left},\ P_{right} \right\} $$

分裂本身通常在源节点本地完成（把数据文件或索引按新边界切开），因此几乎不需要网络传输，代价远低于跨节点搬迁。这也是范围分区在「数据量增长」场景下优于哈希分区的原因。

### 三种切流方式

边界或归属变化后，客户端如何找到正确的节点？常见三种：

**重定向（redirect）。** 服务端返回一个「请去 X」的响应，客户端重试。Redis Cluster 用 `MOVED`（槽已永久迁移）与 `ASK`（槽正在迁移中，本次请去 X 但别更新本地缓存）区分两种语义。灵活性高，但多一次往返。

**代理转发（proxy）。** 客户端只连代理，由代理查表并转发。客户端简单、适合多语言；代理成为延迟与容量瓶颈。

**客户端表 + 变更通知（smart client）。** 客户端缓存路由表，由集群通过心跳或配置订阅推送变更。延迟最低，但客户端实现复杂、需要处理版本不一致。

三者常组合使用：正常走客户端表，表过期时用重定向纠正。

### 一致性哈希与哈希槽的取舍

Redis Cluster 把键空间划分为 **16384 个哈希槽**（slot），键归属由 `CRC16(key) mod 16384` 决定，槽再分配给节点。为什么是 16384 而不是更大？一个广为引用的理由是：集群节点间心跳需要携带「本节点负责哪些槽」的位图，16384 位 = 2KB，而 65536 位需要 8KB——在心跳中携带 8KB 位图会显著增加带宽，而 16384 个槽已足以支撑千级节点的均衡粒度。这说明**槽数的选择是均衡度与元数据开销的权衡**，而非纯数学问题。

槽级迁移的一个硬约束是：涉及多键的操作（`MULTI/EXEC`、`MSET`、集合运算）要求所有键在同一槽，因此常用 **hash tag**（如 `user:{1000}:name` 中花括号内内容）强制把相关键映射到同一槽，代价是牺牲分布均匀性。

## 三、形式化与数学基础

**虚拟节点带来的迁移粒度。** 设每物理节点有 $V$ 个虚拟节点，新增第 $N+1$ 个节点后，理想情况下每个旧节点让出 $V/(N+1)$ 个虚拟节点区间：

$$ \Delta V_{per\ node} = \frac{V}{N+1}, \qquad \Delta K_{total} = \frac{K}{N+1} $$

$V$ 越大，单次让出的区间越小，迁移越平滑、单批影响越小。

**预分片的分区数与均衡质量。** 设 $P$ 个分区随机分配到 $N$ 个节点（球入箱模型，球数 $P/N$ 每箱），最大负载的期望上界为：

$$ L_{max} \approx \frac{P}{N} + \sqrt{2 \cdot \frac{P}{N} \ln N} $$

因此相对不均衡度为：

$$ \frac{L_{max} - P/N}{P/N} \approx \sqrt{\frac{2 N \ln N}{P}} $$

要在 $N = 100$ 时把不均衡度控制在 10% 以内，需要 $P \gtrsim 2 \times 100 \times \ln 100 / 0.01 \approx 9 \times 10^{4}$——这远超实际取值。原因在于上述分析假设**纯随机分配**；实际系统用轮转 + 贪心（把分区按大小降序轮流分配）可以接近完美均衡，因此 $P = 10N \sim 100N$ 已足够。这也说明：**分区数的选择必须结合分配算法，单纯加大 $P$ 并不高效。**

**再分片的额外开销。** 改变 `key → partition` 映射（如分区数从 $P$ 增到 $P'$）会导致大量键重映射。设映射不变的概率为 $P/P'$（对均匀哈希），则重映射比例为：

$$ \rho = 1 - \frac{\min(P, P')}{\max(P, P')} $$

当 $P' = 2P$ 时 $\rho = 50\%$，即**一半数据需要搬迁**。这就是「分区数一经确定就尽量不要改」的定量依据，也是 Kafka 增加分区数会改变既有键归属的原因（其默认分区器对键做 `murmur2(key) & (numPartitions-1)`，分区数变化即映射变化，破坏原有的按 key 有序性保证）。

**分裂的代价对比。** 分裂在本地完成，只需重写元数据与（可能的）索引：

$$ C_{split} = O\left( \text{元数据} \right) + O\left( \text{本地索引重建} \right) $$

而跨节点搬迁需要传输数据本身 $C_{move} = O(S)$（$S$ 为分区大小）。二者相差数量级，因此**范围分区系统的扩容策略是「先分裂、再搬迁」**：先让热点分区变小从而可被搬迁，再执行迁移。

## 四、代码实现

Redis Cluster 风格的槽级迁移（`MIGRATING`/`IMPORTING`/`ASK` 三态协作）：

```python
class SlotOwner:
    # 源节点侧：把槽标记为 MIGRATING，逐个键搬迁到目标
    def migrate_slot(self, slot, target):
        self.slots[slot].state = "MIGRATING"
        self.slots[slot].target = target

        while True:
            keys = self.keys_in_slot(slot, limit=100)
            if not keys:
                break
            for k in keys:
                # 先搬运单键，再在本地删除；两步之间命令按 MIGRATE 语义原子处理
                self.send_migrate(k, target)
                self.delete_if_unchanged(k)
            time.sleep(0.01)          # 限速，避免阻塞正常请求

        # 迁移完成：向集群广播新的槽归属（一次配置变更）
        self.cluster.broadcast_slot_owner(slot, target)

    # 请求处理：本节点不拥有该槽时如何响应
    def handle(self, cmd):
        slot = crc16(cmd.key) % 16384
        owner = self.cluster.slot_owner(slot)
        if owner is self:
            if self.slots[slot].state == "MIGRATING" and not self.exists(cmd.key):
                # 键可能已迁走：让客户端去目标节点，但不要更新本地缓存
                return Reply("ASK", self.slots[slot].target)
            return self.execute(cmd)
        return Reply("MOVED", owner)      # 槽已永久归属他人，客户端可更新缓存
```

目标节点侧需要把槽标记为 `IMPORTING`，并只对带 `ASKING` 前缀的请求放行：

```python
class SlotImporter:
    def handle(self, cmd, asking: bool):
        slot = crc16(cmd.key) % 16384
        st = self.slots[slot]
        if st.state == "IMPORTING" and asking:
            # 仅当客户端先发 ASKING 才服务该槽的键，避免误服务尚未迁完的槽
            return self.execute(cmd)
        owner = self.cluster.slot_owner(slot)
        if owner is not self:
            return Reply("MOVED", owner)
        return self.execute(cmd)
```

预分片模型的再分片：只重指派分区，`key → partition` 不变：

```python
PARTITIONS = 1024        # 一经确定不再改变

def partition_of(key: str) -> int:
    return crc32(key) % PARTITIONS          # 永不随成员变化

def rebalance_assignment(partitions, nodes):
    """把分区按大小降序轮流分配，比纯随机更均衡（LPT 启发式）。"""
    load = {n.id: 0 for n in nodes}
    assign = {}
    for p in sorted(partitions, key=lambda x: -x.size):
        target = min(nodes, key=lambda n: load[n.id])   # 选当前最轻的节点
        assign[p.id] = target.id
        load[target.id] += p.size
    return assign
```

范围分区的分裂（元数据原子替换，数据本地切开）：

```python
def split_region(region, split_key):
    """把一个 region 按 split_key 切成两个，并原子更新元数据。"""
    assert region.start < split_key < region.end

    left = Region(start=region.start, end=split_key)
    right = Region(start=split_key, end=region.end)

    # 本地切分存储：左半留在原位，右半写入新目录（无需跨节点传输）
    move_keys(source=region, dst=left, predicate=lambda k: k < split_key)
    move_keys(source=region, dst=right, predicate=lambda k: k >= split_key)

    # 元数据层以单次事务把 region 替换为 {left, right}
    meta_store.replace(region.id, [left.id, right.id])
    return left, right
```

## 五、与其他技术对比

| 维度 | 预分片（固定分区数） | 哈希槽（Redis Cluster） | 范围分区分裂/合并 | 一致性哈希 + vnode | 全量重哈希 |
| --- | --- | --- | --- | --- | --- |
| 边界是否可变 | 否 | 槽数固定、归属可变 | 是（split/merge） | 区间随 vnode 变化 | 随路由数变化 |
| key 重映射风险 | 无 | 无（槽数固定） | 局部（仅边界处） | 无 | 高（$1 - P/P'$） |
| 迁移粒度 | 一个分区 | 一个槽（16384 之一） | 一个 region | 若干 vnode | 全量 |
| 分裂代价 | 不涉及 | 不涉及 | 本地，极低 | 不涉及 | 极高 |
| 元数据规模 | $P$ 项 | 16384 位的位图 + 归属表 | region 边界表 | $NV$ 项环 | 路由表 |
| 支持缩容 | 是（重指派） | 是（槽回迁） | 是（合并） | 是 | 是 |
| 典型系统 | Kafka、Elasticsearch | Redis Cluster | HBase、TiKV、MongoDB | Dynamo、Cassandra | 早期 `mod N` 方案 |

关键认识：**「再分片」有两种截然不同的含义**。若采用预分片/哈希槽，则分区数固定，再分片只是「归属重指派」，代价可控（$K/(N+1)$）；若允许边界动态变化（分裂），则每次变化只影响边界附近的数据，代价更低但仍需处理跨节点搬迁与元数据原子性。真正的灾难是**改变分区总数**（如 `mod P` 变成 `mod 2P`），会造成 50% 以上的键重映射。

## 六、常见误区

- **一次性大区间迁移。** 把整个节点的数据一次搬走会冲击网络与磁盘；应细化为 vnode/分区/槽粒度，分批限速。
- **虚拟节点数或分区数过少。** 粒度粗导致分布不均与迁移不平滑；Redis 选择 16384 个槽正是为了在元数据开销可控的前提下提供足够粒度。
- **再分片期间不限制速率。** 搬运流量与线上业务争抢资源，会把再平衡变成性能事故。
- **认为增加 Kafka 分区数无副作用。** 分区数变化会改变键到分区的映射，破坏既有键的按序处理，且分区数不能减少（只能通过建新 Topic + 迁移实现）。
- **忽略多键操作的槽约束。** Redis Cluster 中 `MULTI/EXEC`、集合运算要求键同槽，需用 hash tag 强制同槽，代价是分布不均。
- **分裂后忘记更新元数据。** 数据切开了但边界表未更新，会导致路由到错误的分区，出现「数据存在但读不到」。
- **合并小分区时忽略历史版本。** 合并需保证两侧数据在同一逻辑时间线上，否则会覆盖新值。

## 八、面试题

1. **虚拟节点如何改善再分片？**
   要点：把迁移粒度从「整节点区间」降到「小 vnode 区间」，新节点从多个旧节点均匀偷取，负载平滑转移，单批影响小。

2. **为什么 Redis Cluster 用 16384 个槽而不是 65536？**
   要点：槽归属位图需随心跳交换，16384 位 = 2KB 而 65536 位 = 8KB；16384 已足够提供均衡粒度，是均衡度与心跳带宽的权衡。

3. **预分片方案为什么能避免键重映射？**
   要点：`key → partition` 用固定分区数计算，永不变化；成员变更只改 `partition → node`，迁移粒度是整分区，因此键的归属不受影响。

4. **范围分区为什么可以「先分裂再搬迁」？**
   要点：分裂在本地完成，只重写元数据与本地索引，成本远低于网络传输；把大分区切小后，单次迁移的数据量与影响面都降低。

5. **增加 Kafka 分区数有什么风险？**
   要点：键到分区的映射依赖分区数，增加会改变既有键的归属，破坏按 key 的有序性；且分区数不能减少，调整需新建 Topic 并迁移数据。

## 九、演进与趋势

再分片的方向之一是**让边界变化变得廉价**。范围分区系统把「分裂」做成微秒级的元数据操作，配合本地数据切分，使扩容的第一步几乎无成本；TiKV 与 HBase 进一步支持 Region Merge，让「分区过多」也能收敛回来。这形成了完整的弹性闭环：数据增长 → 分裂 → 迁走热点；数据减少 → 合并 → 释放元数据。

第二个方向是**减少需要重映射的场景**。存算分离让数据与计算分离，分区边界变化不再必然引起数据搬移；一致性哈希的变体（如 rendezvous、jump hash）在无状态分片层提供了更简单的「无边界」方案，适合连接层与缓存层。

第三个方向是**自动化的槽/分区管理**。Redis Cluster 的槽迁移、Kafka 的 partition reassignment、TiKV 的 PD 调度器都在把「选哪些分区迁移、迁移多少、限速多少」交给调度器，并暴露进度与落后量指标。未来更依赖基于实时负载的预测性调度，而不是阈值触发的被动响应。

## 十、小结

再分片的本质是「改变分区边界或归属」。若采用预分片或哈希槽模型，分区数固定，再分片退化为归属重指派，迁移量约 $K/(N+1)$ 且无键重映射；若采用范围分区，则通过 split/merge 在本地廉价地调整边界，再配合跨节点搬迁。真正的禁忌是改变分区总数（如 `mod P` 变 `mod 2P`），会造成 50% 以上数据的重映射。

工程上要记住三点：粒度要细（靠 vnode/槽/分区数足够大）、迁移要限速分批、元数据变更必须原子。Redis 的 16384 槽与 `MOVED`/`ASK` 三态协作、Kafka 的分区不可减少、HBase/TiKV 的本地分裂，都是在这些约束下的成熟答案。
