# 分区迁移触发与流程

> 对应 DeCandia 等 2007 (Dynamo)、Kleppmann《DDIA》第 6 章、Ongaro & Ousterhout 2014 (Raft 成员变更) 与 Coulouris《Distributed Systems》第 18 章。

## 一、背景与挑战

分区迁移与重平衡算法是同一问题的两面：算法决定「应该把哪个分区搬到哪里」，流程决定「怎么搬才不丢数据、不停服」。后者往往更难，因为它要在数据面持续接受读写的同时完成状态搬迁，且必须能容忍迁移过程中任意节点、任意时刻的故障。

核心矛盾在于：**迁移是一个有时间跨度的过程，而路由必须始终是一个明确的答案。** 如果迁移期间路由只指向源节点，则已切到目标节点的读会读到旧数据；如果只指向目标节点，则未同步完的数据会丢失。任何忽略这一矛盾的实现都会在迁移窗口内出现「读到旧值」「写入消失」「部分读成功部分失败」等难以复现的错误。

因此迁移流程的设计目标可以概括为：**在迁移窗口内保证不丢写、允许读收敛、并在结束时以原子操作完成切换。**

## 二、核心原理

### 触发来源

迁移不会无缘无故发生，常见触发源有四类：

1. **成员变更**：扩容（新节点加入需数据）、缩容（下线节点需迁出）、故障替换（副本重建）。这是最主要来源。
2. **负载倾斜**：监控到某节点 CPU/磁盘/请求量显著偏离均值，触发热点疏散。
3. **拓扑约束**：机架/可用区感知策略要求副本分布满足反亲和规则，成员或机架变化后需重排以满足约束。
4. **运维命令**：人工下线节点、机房迁移、硬件维护窗口内的定向搬移。

不同触发源对应不同的紧急程度：故障替换必须在短时间内完成（否则副本数不足，风险升高），而负载疏散可以慢慢来且必须限速（否则迁移本身成为新的负载高峰）。

### 五阶段流程

**① 标记迁移（Marking）。** 在路由元数据中把分区 $P$ 的状态从 `SERVING(src)` 改为 `MIGRATING(src → dst)`。此时读写路由变成「源与目标都在服务集合中」，为后续双写做准备。这一步必须写进可靠的元数据存储（通常是共识系统），以保证所有客户端与协调者看到一致的状态。

**② 快照拷贝（Snapshot & Copy）。** 源节点对分区做一致性快照并传输到目标。快照必须与一个明确的日志位置 $L_0$ 绑定（例如 LSM 的 WAL 序号、Raft 的日志索引、Kafka 的 offset），否则后续的增量同步将无从对齐。

**③ 增量追赶（Catch-up）。** 从 $L_0$ 开始，把快照期间与之后产生的新写操作持续推送到目标。追赶阶段的进度可用「落后量」度量：设源端日志位置为 $L_{src}$、目标端已应用到 $L_{dst}$，则落后量为 $L_{src} - L_{dst}$。当落后量在若干轮内持续低于可接受阈值（例如小于 1 秒的写入量）时，认为已追上。

**④ 原子切换（Cut-over）。** 在元数据中把分区归属从源改为目标，并让所有路由方（客户端、协调者、网关）原子地看到新版本。切换的原子性通常由共识系统提供（一次配置变更即生效），这是整个流程中最关键也最容易出错的一步——**切换必须是一个单点决定，不能是「各方各自逐渐切换」**。

**⑤ 清理（Cleanup）。** 源节点在确认目标已稳定服务后删除本地数据副本。清理必须延迟执行（常见做法是等待一个安全期或等待目标确认多次心跳），以应对「切换后才发现目标异常需要回滚」的情况。

### 不丢写的两条实现路径

**路径 A：双写（dual write）。** 迁移期间，任何落在 $P$ 上的写都同时应用到源与目标。优点是实现直观；缺点是写延迟翻倍、需要处理两边冲突、且要求「双写」本身是原子的（否则可能只写成功一边）。若一边失败，需要重试或记录待补偿。

**路径 B：日志转发（log shipping）。** 写只落源节点，源节点把日志持续转发给目标。目标顺序回放。优点是写路径不增加延迟与控制复杂度；缺点是源节点成为单点，若它在切换前故障，未转发的日志也随之丢失（除非日志已复制到共享存储或多数副本）。

实践中更稳的方案是把二者结合：常规写只落源并转发日志，而在切换的临界窗口（in-flight 请求可能跨两代路由）内短暂启用双写或让协调者做版本合并。

### 与共识协议的结合

若分区本身是基于 Raft/Paxos 的多副本状态机，迁移可以表达为**成员变更**而不是「数据搬移」：

- Raft 的 joint consensus（或单步成员变更）把副本集合从 $\{A, B, C\}$ 改为 $\{A, B, D\}$；新成员 $D$ 通过正常的日志复制追上进度，追上后配置变更提交，$C$ 退出。
- 这一表达的好处是迁移过程自动获得共识协议的全部保证：不丢已提交日志、切换点就是一次配置提交、失败可安全重试。
- 代价是迁移速度受共识复制带宽限制，且分区数量多时元数据开销显著。

## 三、形式化与数学基础

用路由函数描述迁移。正常情况下分区 $P$ 只有一个服务位置（或一个固定副本集合）：

$$ R: P \to 2^{Nodes}, \qquad \left| R(P) \right| = 1 \ \text{（或副本数）} $$

迁移期间扩展为多映射：

$$ R_{mig}(P) = \left\{ src,\ dst \right\}, \qquad \left| R_{mig}(P) \right| = 2 $$

读写语义随之定义。读需合并两个可能不同版本的值：

$$ \text{read}(P) = \text{merge}\left( \text{get}(src),\ \text{get}(dst) \right) $$

其中 `merge` 依据版本信息（版本号、向量时钟）选择最新值。写需覆盖两处：

$$ \text{write}(P, v) = \left( \text{put}(src, v),\ \text{put}(dst, v) \right) $$

**不丢写的正确性条件**可以形式化为：对迁移窗口内提交的任意写 $w$，切换后目标节点必须包含 $w$：

$$ \forall w \in W_{mig}: w \in dst \ \text{在 cut-over 之后} $$

充分条件是「$w$ 至少被应用到 $dst$，或 $w$ 被源节点记录在日志中且该日志在切换前被完全回放到 $dst$」。形式化地，设切换时刻源端日志位置为 $L_{co}$，则要求：

$$ L_{dst} \ge L_{co} \quad \text{在 cut-over 提交之前} $$

即**目标必须追上到切换点，才能提交切换**。这条不变式看似显然，却是实现中最常被违反的地方——常见错误是「估算差不多了就切」，导致最后一部分写丢失。

**切换的原子性**要求元数据变更是一个线性化操作：

$$ \text{route}(P) = src \ \text{或} \ dst, \qquad \text{不存在中间状态} $$

若元数据存于共识系统，线性化由协议保证；若存于本地缓存或最终一致的配置中心，则会出现「部分客户端已切、部分未切」的脑裂式路由，表现为间歇性读到旧数据。

**迁移时长**可作为规划指标。设分区数据量 $S$、可用迁移带宽 $b$、迁移期间写入速率 $w$，则：

$$ T_{copy} = \frac{S}{b}, \qquad T_{catchup} \approx \frac{w \cdot T_{copy}}{b - w} \quad (b > w) $$

当 $b \le w$ 时追赶永不收敛（写产生速度超过搬运速度），这是迁移必须限速与分批的数学原因：必须保证 $b > w$，否则该分区只能停止写入或采用停机迁移。

## 四、代码实现

迁移主流程（快照 + 增量 + 切换 + 清理），带幂等与可重入设计：

```python
def migrate_partition(p, src, dst, meta_store, catchup_every=5):
    # ① 标记迁移：写入共识元数据，使所有路由方看到 MIGRATING
    meta_store.put(p, state="MIGRATING", src=src.id, dst=dst.id)

    try:
        # ② 快照拷贝：记录一致的日志位置 L0，避免后续增量无法对齐
        L0 = src.log_position(p)
        snapshot = src.snapshot(p, upto=L0)
        dst.load_snapshot(p, snapshot, base_position=L0)

        # ③ 增量追赶：持续转发日志，直到落后量稳定在阈值内
        while True:
            Lsrc = src.log_position(p)
            Ldst = dst.applied_position(p)
            if Lsrc - Ldst <= THRESHOLD:
                break
            batch = src.read_log(p, from_pos=Ldst, limit=1000)
            if not batch:
                continue
            dst.apply_log(p, batch)          # 幂等：按位置去重
            time.sleep(catchup_every / 1000.0)

        # ④ 原子切换：在元数据中以单次线性化写入完成归属变更
        #    切换前再次确认目标已追到切换点
        assert dst.applied_position(p) >= src.log_position(p)
        meta_store.put(p, state="SERVING", owner=dst.id)

    except Exception:
        # 回滚：恢复原归属，目标侧数据保留待下次重试（幂等可重入）
        meta_store.put(p, state="SERVING", owner=src.id)
        raise

    # ⑤ 清理：延迟删除源副本，留出回滚窗口
    src.schedule_delete(p, after=SAFETY_PERIOD)
```

迁移期间的读写路由（与「迁移中读写路由」一篇互补的写入侧实现）：

```python
def route_write(p, value, routing):
    info = routing[p]
    if info.state == "MIGRATING":
        # 双写：两边都要成功，否则视为失败（由上层重试）
        ok_src = info.src.put(p, value)
        ok_dst = info.dst.put(p, value)
        if not (ok_src and ok_dst):
            raise WriteFailure(p)     # 交由上层重试；写操作需幂等
    else:
        info.owner.put(p, value)
```

以 Raft 成员变更表达迁移（伪代码，落点是「迁移即配置变更」）：

```text
# 目标：把分区 P 的副本集合从 {A,B,C} 改为 {A,B,D}
1. leader 追加配置变更日志：C_old = {A,B,C}, C_new = {A,B,D}   # joint 或单步变更
2. 新成员 D 以学习者身份接收日志复制，追赶至接近 leader
3. D 追上后，leader 提交配置变更；此后多数派为 C_new
4. 提交后 C 退出；D 正常参与选举与提交
# 关键：切换点 = 配置变更日志提交，天然线性化，失败可安全重试
```

## 五、与其他技术对比

| 维度 | 停机迁移 | 快照+增量（双写） | 日志转发（无双写） | Raft 成员变更 | 共享存储 + 元数据切换 |
| --- | --- | --- | --- | --- | --- |
| 停服时间 | 全程 | 无（仅切换瞬间抖动） | 无 | 无 | 无 |
| 不丢写保证 | 天然 | 双写原子性 | 依赖日志不丢 | 共识保证 | 依赖存储一致性 |
| 切换原子性 | 不涉及 | 需外部元数据保证 | 需外部元数据保证 | 协议内建 | 元数据系统保证 |
| 源节点负载 | 无 | 高（双倍写） | 高（转发） | 中（复制） | 低 |
| 实现复杂度 | 最低 | 高（冲突处理） | 中 | 高（需共识层） | 中 |
| 失败恢复 | 重来 | 幂等重入 | 从日志位置续传 | 自动 | 自动 |
| 适用场景 | 离线批处理 | KV/文档存储 | 消息队列、日志系统 | 强一致分片数据库 | 存算分离架构 |

关键取舍是**「谁承担切换的原子性」**：自研系统通常依赖外部的共识元数据（etcd/ZooKeeper）提供线性化点，Raft 系系统则在协议内部解决。前者灵活但需自建正确性论证，后者更稳但要求整个存储栈基于共识构建。

## 六、常见误区

- **先删源再迁。** 迁移中途失败即永久丢数据。正确顺序是「迁完、确认、切换、安全期后清理」。
- **迁移中不双写或不转发日志。** 窗口内的增量写会丢失，切换后表现为「数据回退」。
- **在估算「差不多追上了」时就切换。** 必须严格满足 $L_{dst} \ge L_{co}$，否则最后一批写会丢。这是最隐蔽也最严重的错误。
- **路由表非原子更新。** 多客户端各自轮询配置中心会导致部分读到旧、部分读到新；必须依赖线性化的元数据读取。
- **迁移不限速。** 迁移流量与线上业务争抢带宽与磁盘 IO，会把「优化」变成「事故」。必须设置速率上限与并发上限。
- **迁移任务不可重入。** 中断后从头开始会重复搬运、甚至造成重复数据；所有步骤必须幂等（按位置去重、按版本合并）。
- **忽略目标端的资源准备。** 目标磁盘空间不足、索引未建、线程池过小，都会让迁移在中途停滞，且往往在切换后才暴露。
- **回滚路径未验证。** 声称「可回滚」但没有实际演练，切换后发现异常时无从退回。

## 八、面试题

1. **迁移过程中如何保证不丢写？**
   要点：迁移期对源与目标双写，或只写源但持续转发日志；切换前必须确认目标已追到切换点（$L_{dst} \ge L_{co}$），之后才提交原子切换。

2. **为什么切换必须原子？**
   要点：若各方渐进切换，会出现部分客户端读新、部分读旧的脑裂式路由，产生间歇性陈旧读。原子切换由共识元数据或 Raft 配置变更提供线性化点。

3. **迁移流程有哪几个阶段？**
   要点：标记迁移 → 快照拷贝（绑定日志位置）→ 增量追赶 → 原子切换 → 延迟清理。每阶段都必须幂等、可重入。

4. **什么情况下追赶永不收敛？**
   要点：迁移带宽 $b$ 小于写入速率 $w$ 时，落后量单调增长。此时必须限速写入、分批迁移，或采用短时停写/停机迁移。

5. **Raft 成员变更相比自研迁移流程有什么优势？**
   要点：把迁移表达为配置变更，自动继承「不丢已提交日志」「切换点即配置提交」「失败可安全重试」三项保证，无需自建原子切换与回滚逻辑；代价是受共识复制带宽约束。

## 九、演进与趋势

迁移流程的演进方向是**减少需要搬动的字节**，而不是把搬动做得更快。存算分离架构让分区数据落在共享对象存储上，迁移退化为「改元数据指向」，几乎消除数据搬运；分层存储（热数据本地、冷数据远端）则让只有热分片需要真正迁移。

第二个方向是**把迁移纳入共识**。Multi-Raft 架构（TiKV、CockroachDB、OceanBase）把每个分区做成一个 Raft 组，迁移即成员变更；配置变更日志本身提供了线性化的切换点与自动重试，显著降低了「自研迁移流程」的出错空间。代价是分区数量受共识心跳与元数据规模约束，因此需要「大分区 + 少量热分区拆分」的混合策略。

第三个方向是**迁移的自动化与可观测化**。基于实时指标的自愈式调度器（如 Kubernetes 的 descheduler、云厂商的自动再平衡）把「何时迁、迁多少、限速多少」交给策略引擎，并暴露落后量、迁移速率、剩余时间等指标；迁移流量普遍被标记为低优先级（cgroup/io 权重、QoS 分级），保证业务流量优先。整体趋势是把迁移从「人工运维操作」变成「持续的后台平衡过程」。

## 十、小结

分区迁移的流程可归纳为「标记 → 快照 → 增量 → 原子切换 → 延迟清理」五步，其正确性依赖两条不变式：**切换前目标必须追上到切换点**（不丢写），**归属变更必须是线性化操作**（不出现脑裂式路由）。实现方式上，双写与日志转发是两种互补手段，Raft 成员变更则把整个流程纳入共识协议。

工程落地的关键在细节：所有步骤幂等可重入、迁移限速限并发、目标端资源预先就绪、清理延迟留出回滚窗口。忽略任何一条，迁移都会从「扩容优化」变成「线上事故」。
