# 分区热点与负载均衡

> 对应 DeCandia 等 2007 (Dynamo)、Kleppmann《DDIA》第 6 章与第 1 章、Cormode & Muthukrishnan 2005 (Count-Min Sketch) 与 Zipf 1949。

## 一、背景与挑战

哈希分区的均衡论证建立在一个隐含假设上：**key 的访问频次与数据量都是均匀的**。现实中的分布往往是长尾甚至幂律的：少数「名人」账号、个别爆款商品、单个时间戳对应的全量数据、某个超级租户——它们可能只占百万分之一的键数量，却承担了相当比例的请求。

这类键造成的问题称为热点（hot spot）或倾斜（skew）。它有两个独立的维度：

- **数据量倾斜**：某个键或某个分区携带的数据远多于其他（如某个用户上传了 PB 级数据、某个设备上报频率是其他设备的千倍）；
- **访问量倾斜**：数据量不大但请求极多（如「首页推荐结果」这一个键被每秒读取数百万次）。

二者的处理手段不同：数据量倾斜靠「拆数据」，访问量倾斜靠「分散请求 + 缓存」。把它们混为一谈是最常见的分析错误。

哈希分区的根本局限在于：**它保证的是「键的分布」均衡，不是「负载的分布」均衡**。只要单个键的负载超过单节点能力，无论怎么调分区数都无法解决——唯一的出路是让这个键本身可以被切开。

## 二、核心原理

### 手段一：热点键拆分（key splitting / salting）

把逻辑上的一个键拆成 $m$ 个物理键，用后缀或前缀区分：

$$ key \longrightarrow \left\{ key\#0,\ key\#1,\ \dots,\ key\#(m-1) \right\} $$

写请求按轮转或随机选择 $m$ 个子键之一，把负载分散到 $m$ 个分区；读请求需要**读全部 $m$ 个子键并合并**。于是单键的吞吐上限被提升 $m$ 倍，代价是读放大 $m$ 倍、写需要能够合并。

由此引出关键取舍：$m$ 决定吞吐提升倍数与读放大倍数，因此 $m$ 必须**按热点程度动态选择**而非固定取大值。更聪明的做法是「写分散、读收敛」：写入时轮转分布，同时在后台把子键聚合成一个汇总键（或使用缓存），读时优先读汇总，未命中才扇出。

对于**可加性**的数据（计数器、点赞数、指标聚合），子键可以独立累加，读时求和即可，无需冲突解决；对于**非可加**的数据（如某个键的最新值、列表），拆分就需要版本比较与合并策略。

### 手段二：缓存与请求合并

访问量倾斜的键是缓存的最佳候选：其访问重复度极高，缓存命中率接近 100%。三层策略：

1. **本地缓存**（进程内）：零网络开销，但多实例间可能不一致，需要 TTL 与失效通知；
2. **分布式缓存**（Redis 等）：一致性好，但要防止缓存击穿（同键并发未命中）——用**单飞（singleflight）/ 请求合并**把并发回源合并为一次；
3. **预计算 / 物化视图**：把热键的结果提前算好，读请求不再触碰原始分区。

需要强调的是**请求合并（request coalescing）**的价值：若 1 秒内有 1 万次请求命中同一个失效的键，无合并会打出 1 万次回源，足以压垮后端；合并后仅 1 次回源。

### 手段三：动态迁移与分裂

对数据量倾斜，最直接的手段是把热分区迁到空闲节点，或在范围分区系统中把热分区**分裂**成更小的分区，从而可以分散到多个节点。哈希分区无法按访问量分裂（键的归属由哈希决定），因此**处理访问量倾斜时哈希分区必须退回「键拆分 + 缓存」的组合**。

### 手段四：限流、降级与隔离

当热点强度超过系统容量时，唯一的正确动作是**主动限制**：对该键单独限流、返回降级结果、或实施批量与合并。这比让请求排队把延迟推高更有效——排队会同时拖垮同一节点上的其他（无辜的）键，造成「热点扩散」。

## 三、形式化与数学基础

设键的访问分布为 $P(k)$，节点数为 $N$。理想均衡（按访问量）要求每节点负载为：

$$ L_{ideal} = \frac{1}{N} \sum_{k} P(k) $$

哈希分区实际提供的是「键数量」意义上的均衡，即每节点分到约 $|K|/N$ 个键：
$$ L_{hash} = \sum_{k \in \text{partition}_i} P(k) $$

只要存在某个 $k^*$ 使 $P(k^*) > 1/N$，无论怎么调整哈希函数，$k^*$ 都整体落在一个分区上，该分区负载至少为 $P(k^*)$。

幂律（Zipf）分布是常见模型：

$$ P(k) \propto \frac{1}{k^{\alpha}}, \qquad \alpha \ge 1 $$

当 $\alpha = 1$ 时，排名前 1% 的键贡献的请求比例为：

$$ \frac{H_{0.01|K|}}{H_{|K|}} \approx \frac{\ln(0.01|K|)}{\ln|K|} $$

在 $|K| = 10^6$ 时约为 $0.83$——即**1% 的键承担了 83% 的请求**。这个量级解释了为什么热点问题在真实系统中如此普遍，也解释了为什么针对性优化少数的键收益极高。

**键拆分的收益与代价。** 设热点键访问量为 $P(k^*)$，拆成 $m$ 个子键后每子键负载为 $P(k^*)/m$，单分区压力下降到 $1/m$。但：

$$ C_{read}(k^*) = m \cdot \left( c_{net} + c_{proc} \right) $$

即读成本线性放大 $m$ 倍。因此最优 $m$ 由「单分区容量上限 $C$」反推：

$$ m \ge \left\lceil \frac{P(k^*)}{C} \right\rceil $$

$m$ 取到这个下界即可，再多只会增加读放大而不带来收益。

**热点的检测：精确计数不可行。** 若要在百万级键上维护精确访问计数，内存为 $O(|K|)$，不可接受。概率计数器（Count-Min Sketch）用 $d$ 个哈希函数、$w$ 个计数器，查询结果的误差满足：

$$ \hat{c}(k) \ge c(k), \qquad \hat{c}(k) \le c(k) + \varepsilon \cdot \text{total}, \qquad \text{以概率} 1 - \delta $$

其中 $w = \lceil e/\varepsilon \rceil$、$d = \lceil \ln(1/\delta) \rceil$，内存为 $O(wd)$，与键数量无关。这使它成为在线热点识别的标准工具。

## 四、代码实现

热点键拆分：写分散到 $m$ 个子键，读扇出合并。可加性数据只需求和：

```python
import random

def write_hot_counter(base: str, delta: int, store, shards: int = 16):
    """写分散：随机选一个子键累加，避免单分区写热点。"""
    i = random.randrange(shards)
    store.incr("%s#%d" % (base, i), delta)

def read_hot_counter(base: str, store, shards: int = 16) -> int:
    """读扇出：合并全部子键。可加性数据直接求和，无需版本比较。"""
    total = 0
    for i in range(shards):
        v = store.get("%s#%d" % (base, i))
        if v is not None:
            total += int(v)
    return total
```

非可加性数据（如「最新值」）必须带版本合并：

```python
def write_hot_latest(base: str, value, version: int, store, shards: int = 8):
    i = version % shards              # 按版本分片，保证同版本单调写入
    store.put("%s#%d" % (base, i), (version, value))

def read_hot_latest(base: str, store, shards: int = 8):
    best = None
    for i in range(shards):
        item = store.get("%s#%d" % (base, i))
        if item is None:
            continue
        if best is None or item[0] > best[0]:   # 用版本号选最新
            best = item
    return best[1] if best else None
```

请求合并（singleflight）防止缓存击穿把后端打垮：

```python
import threading

_locks = {}
_locks_guard = threading.Lock()

def get_with_singleflight(key, loader, cache):
    """同一 key 的并发未命中只回源一次，其余等待并复用结果。"""
    v = cache.get(key)
    if v is not None:
        return v

    with _locks_guard:
        lock = _locks.setdefault(key, threading.Lock())

    with lock:
        v = cache.get(key)          # 双重检查：可能已被前一个持锁者填充
        if v is not None:
            return v
        v = loader(key)              # 只有一次真实回源
        cache.set(key, v, ttl=60)
        return v
```

用 Count-Min Sketch 做在线热点识别（内存与键数无关）：

```python
import hashlib

class CountMinSketch:
    def __init__(self, width=2048, depth=4):
        self.w, self.d = width, depth
        self.table = [[0] * width for _ in range(depth)]

    def _idx(self, key: str, i: int) -> int:
        h = hashlib.md5(("%d:%s" % (i, key)).encode()).digest()
        return int.from_bytes(h[:4], "big") % self.w

    def add(self, key: str, n: int = 1):
        for i in range(self.d):
            self.table[i][self._idx(key, i)] += n

    def estimate(self, key: str) -> int:
        # 取各层最小值为估计：只会高估，不会低估
        return min(self.table[i][self._idx(key, i)] for i in range(self.d))

cms = CountMinSketch()
for k in ["hot:item", "hot:item", "cold:x", "hot:item"]:
    cms.add(k)
print("hot:item ≈", cms.estimate("hot:item"), " cold:x ≈", cms.estimate("cold:x"))
```

热点键的自动拆分决策（按估算值与容量反推 $m$）：

```python
def decide_shards(est_load: float, capacity_per_shard: float, cur_shards: int) -> int:
    need = int(-(-est_load // capacity_per_shard))     # 向上取整
    return max(cur_shards, min(need, 256))             # 设定上限，防止读放大失控
```

时长序列数据的建键设计（避免「按时间戳分区」造成全量热点）：

```python
def timeseries_key(device_id: str, ts_seconds: int, bucket: int = 3600) -> str:
    # 复合分区键：(device_id, 小时桶)。既避免单设备全量数据落一个分区，
    # 也避免「按天/按时间戳」导致同一时刻所有数据写入同一分区。
    return "ts:%s:%d" % (device_id, ts_seconds // bucket)
```

| 维度 | 键拆分（salting） | 缓存 + 请求合并 | 动态迁移热点分区 | 范围分区手动挪段 | 全局限流/降级 | 读副本扩容 |
| --- | --- | --- | --- | --- | --- | --- |

| 主要代价 | 读放大 $m$ 倍、需合并 | 一致性/击穿 | 迁移流量 | 运维复杂 | 牺牲部分请求 | 副本一致性延迟 |

| 适用系统 | KV、文档、计数器 | 几乎所有 | 支持调度的集群 | 范围分区系统 | 网关/入口 | 读多写少 |

组合使用的经验顺序是：**先限流保护系统（止血）→ 缓存 + 请求合并降低回源（治标）→ 键拆分提升上限（治本）→ 必要时迁移/分裂（优化分布）**。跳过前两步直接拆分，往往会因为读放大 $m$ 倍而让整体变得更糟。

## 六、常见误区

- **认为哈希分区一定均衡。** 它只对「键的数量」均衡，对「访问量」与「数据量」没有保证；单键热点哈希无能为力。
- **热点拆分后不做读的上限控制。** $m$ 越大读放大越严重，可能把热点从写侧搬到读侧，甚至让扇出请求造成更大压力。
- **仅靠加节点解决热点。** 热点键仍固定在单一分区上，加节点不会改变其归属（哈希分区下）。
- **用无界重试应对缓存击穿。** 击穿时并发回源会把后端打垮，应使用请求合并与互斥，而非重试。
- **把「数据量倾斜」与「访问量倾斜」混淆。** 前者要拆数据，后者要靠缓存与分散请求，手段不可互换。
- **忽略计数器类数据的可加性优势。** 对可加数据不做简单求和而引入复杂冲突解决，是过度设计。
- **时间序列按时间戳分区。** 会导致同一时刻的写入全部落到同一分区（写入热点），应按「实体 + 时间桶」构造复合键。
- **依赖精确计数做热点检测。** 百万级键的精确计数内存不可承受，应使用 Count-Min Sketch / Space-Saving 等概率结构。

## 八、面试题

1. **哈希分区下仍有热点怎么办？**
   要点：对热点键加随机/顺序后缀拆成 $m$ 个子键，写分散、读扇出合并；配合缓存与请求合并降低回源；必要时提升到网关级限流与降级。

2. **拆分热点键的代价是什么？**
   要点：读放大 $m$ 倍，且非可加性数据需要版本合并。因此 $m$ 应按 $m \ge \lceil P(k^*)/C \rceil$ 取下界，并在超过阈值时改用缓存/物化视图。

3. **为什么加节点解决不了单键热点？**
   要点：哈希分区中键的归属由哈希值决定，加节点不会改变该键的目标分区；只有拆分键或改用范围分区并分裂才能改变分布。

4. **缓存击穿与请求合并是什么关系？**
   要点：热点键失效瞬间会有大量并发未命中，若无合并会同时回源压垮后端；请求合并（singleflight）把同键并发合并为一次回源，是防止击穿的关键手段。

5. **如何在线检测热点键？**
   要点：用 Count-Min Sketch 或 Space-Saving 等概率计数结构，内存与键数量无关且只会高估；对估算值超过阈值的键触发拆分或限流。

## 九、演进与趋势

热点治理的演进方向是**从静态规则走向自适应闭环**。调度器持续采集每个分区的 QPS、数据量、尾延迟，用估算结构识别热点；一旦超过阈值，自动触发键拆分（对可加数据）、把热分区迁到空闲节点、或对该键单独限流。Kubernetes 生态中的自动扩缩容与云数据库的「热分区自动分裂」都在朝这个方向演进。

在数据模型层面，**冷却键设计**正成为建表规范的一部分：时间序列用 `(实体, 时间桶)` 复合分区键，多租户用 `(租户, 桶)`，社交场景对大 V 的粉丝列表做专项拆分。与其在事故中被动处理热点，不如在设计存储模型时预留拆分能力——这也是「可拆分性」作为非功能需求逐渐被显式提出的原因。

在读路径上，边缘缓存与 CDN 把热读进一步推到离用户最近的位置，使源站面对的热点强度大幅下降；物化视图与预计算（离线/流式）把「读时聚合」改为「写时聚合」，从根本上消除读放大。整体趋势是：**把热点从「必须承受的负载」转化为「可以规划的数据结构问题」**。

## 十、小结

分区均衡解决的是「键分布均衡」，而热点是「负载与数据量分布不均」，二者不是同一问题。数据量倾斜靠拆分数据（分裂分区、复合键设计），访问量倾斜靠分散请求与缓存（键拆分、请求合并、物化视图），二者手段不可互换，实际系统往往同时存在。

工程上应建立「限流止血 → 缓存与合并治标 → 拆分治本 → 调度优化分布」的处理顺序，并用 Count-Min Sketch 类概率结构在线识别热点。牢记定量关系：Zipf 分布下 1% 的键可承担 80% 以上的请求，而键拆分的收益是 $m$ 倍吞吐，代价是 $m$ 倍读放大——所有决策都应围绕这两个数展开。
