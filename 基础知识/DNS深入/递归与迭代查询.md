# 递归与迭代查询

> 对应 RFC 1034 / RFC 1035（解析算法与报文标志）；RFC 7816（QNAME Minimization）；RFC 9499（术语）。

## 一、背景与挑战
一台终端上的 stub resolver 不可能知道全网所有域名，也不可能承担全网查询。于是必须明确分工：谁负责「替我查到底」，谁只负责「给我下一步线索」。递归与迭代正是这两种协作模式的抽象，它们共同把「全球名字空间」这个超大问题拆成可缓存、可委派的子问题。

挑战在于：其一，**信任与责任边界**——递归解析器要对外承诺完整答案，因此它承受了延迟、缓存、攻击放大与合规窥探的全部压力；其二，**正确性**——CNAME 链、通配符、委派、否定应答混在一起时「查到底」并不平凡；其三，**效率**——若每个客户端都自行迭代，根与 TLD 将被海量重复查询压垮，必须靠共享缓存与少数公共解析器收敛；其四，**隐私**——完整递归意味着解析器能看到用户的全部查询，QNAME minimization 等机制正是为削减这种暴露。

## 二、核心原理
**递归查询**：客户端把 RD（Recursion Desired）置 1，要求服务器「替我问到底并把最终答案带回」。服务器要么返回答案，要么返回错误（如 SERVFAIL/REFUSED），不会返回「中间线索」。**迭代查询**：RD 置 0，服务器若不知答案，就返回「去问下一个更接近的服务器」（referral，通常表现为 NS 记录 + 胶水记录），由请求方自行继续。

典型路径因此是「客户端→本地递归解析器」用递归，而「解析器→根→TLD→权威」用迭代。响应中的 **AA（Authoritative Answer）** 标志表明答案来自权威，缓存应答通常不置 AA。公共解析器对外提供递归服务，向上游一律迭代。另一处关键机制是 **CNAME 链**：若查询的目标是别名，权威返回 CNAME 与目标名，解析器需对目标名重新发起查询（可能又跨区），每跳都可能增加一轮往返；若链条过长会被实现限制截断。

## 三、形式化与数学基础
设从根到目标权威的委派路径为 $p = (r, t_1, t_2, \dots, a)$，其中 $r$ 为根、$t_i$ 为中间区、$a$ 为权威。冷缓存下的迭代往返轮数近似
$$ R \approx |p| = 1 + k + 1 $$
其中 $k$ 为中间委派层数（常见为根 + TLD 共 2 跳）。若存在 CNAME 链 $(c_1 \to c_2 \to \dots \to c_m)$，则
$$ R_{total} \approx \sum_{j=1}^{m} R_j $$
因此限制 CNAME 链长度是防放大与防环的必要手段。设第 $i$ 层缓存的命中率为 $h_i$、TTL 为 $\tau_i$，则平均查询代价显著低于冷路径：
$$ \mathbb{E}[R] = (1-h_0)\Big(1 + (1-h_1)\big(1 + (1-h_2)\cdot 1\big)\Big) $$
这解释了为什么递归解析器的缓存命中率是它的核心 KPI。QNAME minimization 则把查询逐级「只问路径所需的标签」，使每层权威仅看到与其职责相关的前缀，形式上把每次查询暴露的名字从完整 $\mathrm{name}$ 降为 $\mathrm{suffix}_i(\mathrm{name})$。

## 四、代码实现
观察一次完整委派过程的交互序列：
```text
stub -> recursive(resolver):  Query A www.example.com  [RD=1, 递归]
recursive -> root:            Query [RD=0]   -> referral: com. 的 NS + glue
recursive -> .com TLD:        Query [RD=0]   -> referral: example.com. 的 NS + glue
recursive -> example.com NS:  Query [RD=0]   -> Answer A 93.184.216.34  [AA=1]
recursive -> stub:            Answer A 93.184.216.34  [AA=0, 来自缓存]
```

用 `dig` 显式区分递归与迭代：
```bash
# 递归：请求解析器代查（RD=1），返回最终答案
dig www.example.com A
# 迭代：向权威直接提问并关闭递归（RD=0），通常得到 referral
dig +norecurse @a.root-servers.net www.example.com A
# 从根开始逐跳展开，直观看到迭代链
dig +trace www.example.com
```

解析器侧状态机（示意，省略超时与重试）：
```python
def resolve(name, qtype, depth=0):
    if depth > MAX_DEPTH:
        raise ResolutionError("chain too long")
    zone = find_closest_zone(name)          # 本地缓存的委派表
    resp = ask(zone.authority, name, qtype, rd=False)   # 迭代
    if resp.is_answer():
        return resp.answer
    if resp.is_referral():
        return resolve(name, qtype, depth + 1)          # 换更近的权威
    if resp.has_cname():
        return resolve(resp.cname_target, qtype, depth + 1)
    return resp.negative                       # NXDOMAIN / NODATA，可负缓存
```

## 五、与其他技术对比
| 维度 | 递归查询 | 迭代查询 | 共享缓存解析器 | 直接询问权威 |
| --- | --- | --- | --- | --- |
| RD 标志 | 1 | 0 | 对外 1、对内 0 | 0 |
| 复杂度落在谁身上 | 服务器 | 请求方 | 服务器 | 请求方 |
| 是否返回中间线索 | 否 | 是（referral） | 否 | 是 |
| 缓存复用 | 高（服务多客户端） | 低 | 极高 | 无 |
| 失败面 | 解析器自身故障影响全量 | 逐跳失败需自行处理 | 单点须冗余 | 需自行处理委派 |
| 典型部署 | 客户端→本地/公共解析器 | 解析器→根/TLD/权威 | 8.8.8.8 类服务 | 排障与验证 |

## 六、常见误区
1. **「本地 DNS 总能递归」**——错。大量权威服务器 `REFUSED` 递归请求，只应答迭代；`+norecurse` 是最直观的演示。
2. **「递归一定比迭代快」**——错。单次看递归省客户端功夫，但共享缓存下迭代整体更高效；递归的价值在于把复杂度集中并可复用。
3. **「CNAME 不影响查询次数」**——错。每跳 CNAME 都可能触发新一轮求解，甚至跨区跨权威，成本与失败面都上升。
4. **「referral 就是答案」**——错。referral 只是 NS 线索（且应配合 glue），把它当答案会得到空结果或错误地址。
5. **「AA=1 才可信」**——错。缓存应答不带 AA 是正常现象；来源可信要靠 DNSSEC 验证，而不是靠 AA 标志。

## 八、面试题
1. **递归与迭代的区别？** 要点：RD 标志；递归承诺最终答案、复杂度在服务器，迭代返回线索、复杂度在请求方；实际是「客户端递归、解析器迭代」的组合。
2. **为什么根服务器只给 referral？** 要点：根只维护 TLD 委派，不给最终答案，才可能以极低状态承载全球查询量；否则无法扩展。
3. **CNAME 链如何影响成本？** 要点：每跳可能新增一次求解与往返，需限制链长并防环。
4. **QNAME minimization 解决什么问题？** 要点：避免向上层泄露完整查询名，减少隐私暴露与无效缓存污染，代价是查询次数略增。
5. **RD 置 1 却收到 referral 意味着什么？** 要点：该服务器不提供递归（或策略拒绝），客户端需改问真正的递归解析器。

## 九、演进与趋势
隐私侧，QNAME minimization 已成为主流解析器的默认行为，DoT/DoH/DoQ 把整条路径加密到解析器，DNS Cookies 降低伪造源地址带来的放大风险。性能侧，解析器普遍实现预取（prefetch）、并行查询（race 多个上游取最快）与「serve-stale」（上游不可用时先返回过期数据）来提升可用性。治理侧，公共解析器的集中化带来便利也带来「谁在看你查什么」的新问题，推动解析器本地化、企业内建解析以及 Oblivious DoH 这类「解析器也看不到查询内容」的方案。具体默认值与行为请以各家与标准的**官方最新文档**为准。

## 十、小结
递归「替你查完」、迭代「给你线索」，二者配合把全球名字空间拆成可缓存、可委派的层级查询。实践中客户端用递归、解析器用迭代，缓存命中率决定整体效率，而 CNAME 链、referral 与 RD/AA 标志是排查解析问题的关键抓手。理解这套分工，才能解释「为什么某个域名在某个网络下解析不到」以及「如何降低解析带来的隐私与性能代价」。
