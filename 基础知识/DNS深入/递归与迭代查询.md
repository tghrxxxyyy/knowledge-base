# 递归与迭代查询

> 对应 RFC 1034 / RFC 1035；RFC 9499。

## 一、背景与挑战
一台 stub resolver 不可能知道全网所有域，需要明确“谁替我查全”与“谁只给我下一步线索”。递归与迭代是两种查询模式。

## 二、核心原理
递归查询：客户端要求服务器“替我问到底并把最终答案带回”。迭代查询：服务器若不知答案，返回“去问下一个更接近的服务器”，由请求方自行继续。典型路径：客户端→本地递归解析器（递归）→根→TLD→权威（迭代）。

## 三、形式化 / 数学基础
RD 标志（Recursion Desired）置位 → 请求递归。
解析步数：最坏路径长度 ≈ 根(1) + TLD(1) + 权威(1) + 可能 CNAME 链。
响应中 AA 标志（Authoritative Answer）指示该答案是否来自权威服务器。

## 四、代码实现
```text
stub -> recursive(resolver):  Query A www.example.com  [RD=1]
recursive -> root:            Query [RD=0]  ->  referral to .com
recursive -> .com TLD:        Query [RD=0]  ->  referral to example.com NS
recursive -> example.com NS:  Query [RD=0]  ->  A 93.184.216.34
recursive -> stub:            Answer A 93.184.216.34
```

## 五、与其他技术对比
递归把复杂度集中在解析器；迭代把复杂度分散给请求方。公共解析器（8.8.8.8）对外提供递归，但向上游用迭代。

## 六、常见误区
误区一：本地 DNS 总能递归。错，很多权威服务器拒绝递归只应答迭代。误区二：递归更快。错，迭代可缓存共享，整体更高效。误区三：CNAME 不影响查询次数。错，每跳 CNAME 可能增一轮。

## 九、演进与趋势

## 十、小结
递归“替你查完”、迭代“给你线索”，二者配合构成 DNS 分层解析路径。
