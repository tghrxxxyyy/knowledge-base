# 负载均衡

> 对应 RFC 1794（DNS Support for Load Balancing）；RFC 1034（多 A 记录）；RFC 7871（EDNS Client Subnet）。

## 一、背景与挑战
单台服务器无法承载高并发，需要把流量分散到多台后端。DNS 处于请求路径最前端、且几乎所有客户端都已有解析器，因此成了最廉价、无需客户端改造的一层负载均衡与就近调度手段：权威服务器对同一域名返回多个 A/AAAA 记录，客户端自行择一。

但 DNS 层做调度有几个天然约束：其一，**无状态与缓存**——解析器会按 TTL 缓存结果，权威无法精确控制某时刻谁拿到哪个 IP；其二，**粗粒度**——只能按「区域 / 运营商 / 子网」这类宏观维度分流，感知不到后端实例的实时负载；其三，**切换慢**——摘除故障 IP 的生效时间下限是 TTL；其四，**DNS 自身可能成为瓶颈或攻击面**——短 TTL 加大查询量，形成放大与自伤。

## 二、核心原理
最基础的是**轮询（round-robin）**：权威对同一名字返回 $n$ 个地址，并按每次查询轮换顺序（或让客户端随机取）。多数解析器只会保留返回顺序或用最小 RTT 启发式选择，所以「谁最终被访问」在客户端与解析器之间被二次决策，权威只是候选提供者。

进一步地，**加权轮询**按权重分配候选出现频率，实现粗略的容量比例。**健康检查**让权威（或调度系统）周期性探测后端，故障 IP 从应答集合中摘除，恢复后加回。**GSLB（Global Server Load Balancing）**把地理位置、运营商、链路质量纳入决策：典型做法是配合 **EDNS Client Subnet（ECS）**，让递归解析器把客户端子网前缀一并上报，权威据此返回「就近」的地址集合。**Anycast** 则把同一 IP 在多地同时宣告，由 BGP 路由把用户送到最近的宣告点，是「路由级就近」而非「解析级就近」。

## 三、形式化与数学基础
设候选地址集合 $A=\{ip_1,\dots,ip_n\}$，第 $k$ 次查询返回的第一个地址为
$$ ip_{(k \bmod n)} $$
加权轮询下，地址 $ip_i$ 被选中的期望占比为
$$ p_i = \frac{w_i}{\sum_{j=1}^{n} w_j} $$
若把权重实现为「平滑加权轮询」，还需保证任意短窗口内分布不出现突刺，即最小化
$$ \mathrm{Var}\Big(\frac{c_i(t)}{N(t)} - p_i\Big) $$
其中 $c_i(t)$ 是 $[0,t]$ 内选中 $ip_i$ 的次数、$N(t)$ 为总次数。健康检查可视为对集合的过滤算子：
$$ A_{eff}(t) = \{\,ip_i \in A \mid \mathrm{healthy}(ip_i, t) = 1\,\} $$
当 $A_{eff}=\varnothing$ 时应答 SERVFAIL 或降级返回上一个已知健康集合，取决于策略。ECS 的编码把客户端子网按前缀长度 $/p$ 截断上报，$p$ 越小覆盖越广、缓存命中越高但精度越低，这是**精度与缓存命中的显式权衡**。

## 四、代码实现
最直接的观察方式与轮询验证：
```bash
# 连续查询，观察返回顺序或集合变化
for i in 1 2 3 4; do dig +short www.example.com A | tr '\n' ' '; echo; done
# 权威若启用了轮询，多行集合的排列会变化
dig +noall +answer www.example.com A
```

带健康检查与权重的极简调度器（示意）：
```python
class DNSLB:
    def __init__(self, backends):
        # backends: [(ip, weight)]
        self.backends = dict(backends)
        self.healthy = {ip: True for ip, _ in backends}
        self.cursor = 0

    def mark(self, ip, ok):
        self.healthy[ip] = ok

    def pick(self, count=2):
        pool = [ip for ip, w in self.backends.items()
                if self.healthy[ip] for _ in range(w)]
        if not pool:
            return []            # 触发降级策略
        out = []
        for _ in range(min(count, len(set(pool)))):
            self.cursor = (self.cursor + 1) % len(pool)
            out.append(pool[self.cursor])
        return list(dict.fromkeys(out))
```

## 五、与其他技术对比
| 维度 | DNS 层 LB | L4 负载均衡 | L7 负载均衡 | Anycast |
| --- | --- | --- | --- | --- |
| 决策依据 | 域名 / 区域 / 子网前缀 | 五元组 | HTTP 路径、头、Cookie | BGP 路由 |
| 粒度 | 粗（区域级） | 中（连接级） | 细（请求级） | 路由级 |
| 生效时延 | 受 TTL 制约，最慢 | 秒级 | 秒级 | BGP 收敛时间 |
| 感知后端负载 | 仅靠健康检查 | 可加权 | 可精细 | 不感知 |
| 是否需客户端改造 | 不需要 | 不需要 | 不需要 | 不需要 |
| 典型角色 | GSLB 选 region | 四层入口 | 业务入口 | 同 IP 就近入口 |

实践中三者分层组合：DNS/Anycast 负责把用户导到最近或最优 region，region 内的 L4 做连接分发，L7 再做请求级路由与灰度。

## 六、常见误区
1. **「DNS 轮询保证均匀」**——错。客户端与解析器缓存会强烈偏置：同一解析器后的大量用户可能长时间命中同一个 IP。
2. **「DNS LB 能感知后端实时负载」**——错。通常只能靠健康检查粗调，负载反馈需更强的调度层配合。
3. **「改 A 记录立即生效」**——错。生效时间上限由 TTL 决定，老旧解析器与本地缓存可能更久。
4. **「TTL 越短越好」**——错。过短会显著放大查询量、降低缓存收益，甚至让权威自身成为被压垮的一环。
5. **「Anycast 与 DNS 轮询是一回事」**——错。前者是网络层路由收敛，后者是应用层返回集合，机制与失败模式完全不同。

## 八、面试题
1. **DNS 轮询的局限是什么？** 要点：缓存偏置、TTL 决定切换速度、无法感知实时负载、可能加剧查询压力。
2. **GSLB 靠什么做就近调度？** 要点：ECS 上报的客户端子网 + 权威的地理/运营商映射表；必要时叠加 Anycast。
3. **为什么有时「换 IP 后部分用户仍访问旧机器」？** 要点：各级缓存未过期；排查应看权威 TTL 设置与实际剩余 TTL，而非只看本机 `dig`。
4. **ECS 的精度与缓存命中如何权衡？** 要点：前缀越短覆盖越广、缓存命中越高，但就近精度下降；需按业务分布调参。
5. **如何让故障 IP 尽快摘除？** 要点：缩短 TTL + 主动健康检查 + 让权威即时撤下记录，必要时在客户端侧做重试与连接失败剔除。

## 九、演进与趋势
方向之一是**更精细的就近**：ECS 与 Anycast 组合，把「解析级」与「路由级」两套就近机制叠加。方向之二是**与后端状态联动**：把 LB 后端健康与容量信息反馈到权威决策（一定程度上突破「无状态」限制）。方向之三是**协议演进**：HTTPS/SVCB 记录可携带协议参数与候选端点，使调度不再局限于 IP 集合；DoH/DoT 的普及虽削弱了运营商对 DNS 的可见性，但也让 ECS 这类信号的收集与合规使用面临新的隐私讨论。落地时需以各家权威与解析器的**官方最新文档**为准。

## 十、小结
DNS 以多 A 记录轮询、加权与健康检查实现粗粒度全局负载均衡，配合 ECS 与 Anycast 完成就近调度，是流量调度的第一道闸门。它的价值在于零客户端改造与全球覆盖，代价是缓存导致的弱控制力与 TTL 决定的慢切换。工程上正确的做法不是二选一，而是让 DNS/Anycast 做宏观引流、L4/L7 做微观分发，并为每一层设计好降级与重试路径。
