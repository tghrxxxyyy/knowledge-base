# 向量化执行引擎

> 对应 cmu-db/15445-course（Vectorization / Column-at-a-time lecture），以及 Vonng/ddia 第 3 章（列式存储与向量化背景）。

## 一、背景与挑战
火山模型逐行解释执行，函数调用与分支开销占比高，且无法利用 CPU 流水线/SIMD。向量化执行一次处理一批（如 1024 行）列式数据，把循环从解释层下沉到紧凑循环，显著提升吞吐。

## 二、核心原理
算子 `next()` 返回列式批（Column Batch / Vector），每个算子内部用紧凑循环对整批数据做相同操作，便于编译器自动向量化（SIMD）与减少虚函数调用次数。配合列式存储（数据连续、同类型）效果最佳。

## 三、形式化与数学基础
函数调用次数由每元组降为每批：
$$ calls = \frac{N}{B},\quad B = \text{batch size} $$
SIMD 加速比近似：
$$ speedup \approx \frac{w_{simd}}{w_{scalar}} $$
其中 $w$ 为寄存器位宽（如 256/512 bit / 64 bit）。

## 四、代码实现
```c
// 向量化过滤（仅示意，假设 int32 列）
void filter_batch(int32_t* col, int n, int32_t thr, int32_t* out, int* cnt) {
    int k = 0;
    for (int i = 0; i < n; i++)            // 紧凑循环，易 SIMD 化
        if (col[i] > thr) out[k++] = col[i];
    *cnt = k;
}
```

## 五、与其他技术对比
火山模型逐行、通用；向量化批处理、适合分析（OLAP）；编译执行消除解释、适合固定模式。ClickHouse/DuckDB/Velox 等均基于向量化。

## 六、常见误区
1) 认为向量化必须列式存储——行存也可批处理但收益小。
2) 误以为批越大越好——缓存与延迟权衡。
3) 忽略分支预测对向量化循环的影响。

## 九、演进与趋势
自适应批大小、向量化 + JIT 混合、GPU 向量化、与编译执行融合的统一执行层。

## 十、小结
向量化以“批处理 + 紧凑循环 + SIMD”把解释开销摊薄，是 OLAP 引擎的标配执行范式。
