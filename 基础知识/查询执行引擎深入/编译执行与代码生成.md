# 编译执行与代码生成

> 对应 cmu-db/15445-course（Code Generation / JIT lecture），以及 Kleppmann《Designing Data-Intensive Applications》第 3 章（相关执行背景）。

## 一、背景与挑战
火山/向量化仍有解释层与算子边界开销。编译执行（JIT / CodeGen，如 LLVM）把整个查询计划编译为一段专有的机器码，消除解释循环与虚函数，按数据局部性展开，极致降低每元组开销。

## 二、核心原理
优化器生成计划后，代码生成器产出针对该计划的循环（常含算子融合，如 Scan+Filter+Project 合成一个循环）。运行时直接用机器码处理原生数据，避免逐算子 materialize 与函数调用。

## 三、形式化与数学基础
解释执行每元组开销：
$$ c_{interp} = c_{call} + c_{branch} + c_{materialize} $$
编译执行摊薄后：
$$ c_{codegen} \approx c_{loop\_body} / SIMD\_width $$
当 $N$ 大时 $c_{codegen} \ll c_{interp}$。

## 四、代码实现
```python
# 伪代码：查询被“融合”成单一循环（仅示意）
def generated_scan_filter_agg(rows, thr):
    s = 0
    for r in rows:                 # 算子融合，无中间 materialize
        if r.amount > thr:
            s += r.amount
    return s
```

## 五、与其他技术对比
火山最灵活但最慢；向量化批处理快；编译执行在特定查询上最快但生成有开销、适合重复执行。Hyper/StarRocks/DuckDB 采用 JIT。

## 六、常见误区
1) 认为编译执行永远最快——生成开销对小查询不划算。
2) 忽略缓存局部性贡献——常比 JIT 本身更关键。
3) 误以为需重写引擎——多基于 LLVM。

## 十、小结
编译执行以“计划即代码”消除解释与中间物化，适合重查询；其生成成本决定适用边界。
