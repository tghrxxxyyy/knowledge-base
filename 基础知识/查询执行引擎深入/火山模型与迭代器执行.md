# 火山模型与迭代器执行

> 对应 Garcia-Molina《Database Systems: The Complete Book》第 12 章（查询处理），以及 cmu-db/15445-course（Volcano/Iterator 模型 lecture）。

## 一、背景与挑战
数据库需要将逻辑算子树（Scan/Join/Agg/Proj）高效执行为结果。火山模型（Volcano / Iterator / 拉取模型）以“一次处理一行、按需拉取”统一了所有算子的接口与流水线。

## 二、核心原理
每个算子实现 `open/next/close` 或单一 `next()` 返回下一元组。父算子调用子算子 `next()` 拉取数据，逐行处理。优点接口统一、惰性、易组合；缺点每行一次函数调用与虚函数分发，CPU 开销大，且难以利用 SIMD/缓存。

## 三、形式化与数学基础
查询代价（以元组数计）：
$$ Cost = \sum_{op} |output(op)| \cdot c_{per\_tuple} $$
火山拉取：
$$ \text{Parent.next()} \Rightarrow \text{Child.next()} \Rightarrow \dots \Rightarrow \text{Scan} $$
每元组分发开销 $c_{per\_tuple}$ 含虚函数跳转与解释开销。

## 四、代码实现
```c
// 火山模型：Scan 与 Filter 算子（仅示意）
typedef struct Op { void* st; Tuple (*next)(struct Op*); } Op;
Tuple scan_next(Op* o) { return read_row(o->st); }
Tuple filter_next(Op* o) {
    Op* child = o->st;
    Tuple t;
    while ((t = child->next(child)).valid) {
        if (predicate(t)) return t;     // 逐行拉取并过滤
    }
    return INVALID;
}
```

## 五、与其他技术对比
火山模型简单通用但逐行慢；向量化/编译执行以批处理或生成代码降低开销。Spark/Flink 早期为火山变体，现代引擎多转向批处理。

## 六、常见误区
1) 认为火山模型已过时——它仍是理解执行的基础。
2) 忽略逐行虚函数开销——在大查询中占主导。
3) 误以为拉取模型天然并行——需额外调度。

## 九、演进与趋势
向量化（批处理 next）、编译执行（消除分发）、Push 模型与 GPU/向量化融合。

## 十、小结
火山模型以统一迭代器抽象实现可组合的执行流水线，是查询引擎的“通用语言”，其逐行开销催生后续优化。
