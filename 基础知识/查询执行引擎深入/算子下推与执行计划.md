# 算子下推与执行计划

> 对应 Vonng/ddia 第 3 章（数据局部性与下推），以及 cmu-db/15445-course（query plan / pushdown lecture）。

## 一、背景与挑战
把计算尽量推到数据所在位置（存储/分片/索引）可大幅减少传输与中间结果。下推（predicate pushdown、projection pushdown、limit pushdown）是分布式与列存引擎的关键优化。

## 二、核心原理
优化器重写计划，将过滤/投影/聚合下推到扫描层或远端节点：先过滤再传输、只取所需列、尽早聚合。下推减少了被处理与网络传输的元组与属性量。

## 三、形式化与数学基础
不下推传输量：
$$ T_{no} = |R| \cdot |attrs(R)| $$
下推后：
$$ T_{push} = |R|_{filtered} \cdot |attrs_{needed}| $$
减少比：
$$ \frac{T_{push}}{T_{no}} = \frac{|R|_{filtered}}{|R|} \cdot \frac{|attrs_{needed}|}{|attrs(R)|} $$

## 四、代码实现
```python
# 逻辑计划下推过滤（仅示意）
def push_predicate(plan):
    if isinstance(plan, Filter) and isinstance(plan.child, Scan):
        plan.child.predicates.append(plan.cond)  # 把过滤下推到 Scan
        return plan.child
    return plan
```

## 五、与其他技术对比
无下推时数据先全取再过滤，浪费 IO/网络；下推贴近存储（如 PostgreSQL 索引条件下推、Spark 列式裁剪）。过度下推可能增加计划复杂度。

## 六、常见误区
1) 认为下推总是有益——某些函数无法安全下推。
2) 忽略下推对索引利用的影响。
3) 误以为所有表达式可下推——含非确定函数者不行。
