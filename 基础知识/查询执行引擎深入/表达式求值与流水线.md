# 表达式求值与流水线

> 对应 Garcia-Molina《Database Systems: The Complete Book》第 12 章（表达式与算子求值），以及 cmu-db/15445-course（expression evaluation lecture）。

## 一、背景与挑战
WHERE、JOIN 条件、投影中的表达式（算术、比较、函数）在每元组上反复求值。低效的表达式解释会成为流水线瓶颈，需权衡解释器与编译/向量化求值。

## 二、核心原理
表达式可表示为树，逐节点求值。优化手段：常量折叠、公共子表达式消除、基于栈/寄存器的字节码解释、或编译为原生代码。与执行模型结合时，表达式在批/行内紧凑求值以保持流水线。

## 三、形式化与数学基础
表达式树求值复杂度：
$$ Cost = \sum_{node} c_{op}(node) \cdot |tuples| $$
常量折叠把运行时常数提前：
$$ f(const\ a, const\ b) \to const\ c $$
流水线停顿随分支数增长：
$$ stall \propto \#branch\_mispredict $$

## 四、代码实现
```c
// 栈式表达式求值（仅示意： +, > ）
int eval(char* post, int* stk) {
    int sp = 0;
    for (; *post; post++) {
        if (isdigit(*post)) stk[sp++] = *post - '0';
        else if (*post == '+') { int b=stk[--sp],a=stk[--sp]; stk[sp++]=a+b; }
        else if (*post == '>') { int b=stk[--sp],a=stk[--sp]; stk[sp++]=a>b; }
    }
    return stk[--sp];
}
```

## 五、与其他技术对比
解释型表达式灵活但慢；编译型快但需生成；向量化按批对表达式做 SIMD。现代引擎多组合：热点表达式 JIT。

## 六、常见误区
1) 认为表达式很便宜——在宽列高频过滤时占比高。
2) 忽略类型分支开销。
3) 误以为常量折叠可解决一切——函数调用仍贵。
