# 推测执行基础

> 对应 Kocher 2019 (Spectre) 与 Böhme 2018 (Meltdown) 论文背景，及 Hennessy & Patterson 推测执行章。

## 一、背景与挑战
为掩盖分支/缓存延迟，CPU 在确认前就推测执行后续指令，结果提交前丢弃。但这种"推测副作用"（如缓存状态）不会被完全撤销，成为侧信道根源。

## 二、核心原理
推测执行沿预测路径运行，访问数据、填充缓存，若预测错误则回滚架构状态（寄存器/内存），但微架构状态（cache、TLB、BTB）常遗留。攻击者借"遗留的微架构状态"推断本不应访问的数据。

## 三、形式化与数学基础
推测窗口内可访问地址集合 $A_{spec}$ 可能超出合法集 $A_{legal}$：
$$A_{spec} \supseteq A_{legal}$$
侧信道通过测量访问 $x\in A_{spec}\setminus A_{legal}$ 的缓存命中时间泄漏信息：
$$Leak \iff AccessTime(x) < Threshold_{cold}$$

## 四、代码实现
```c
// 经典Spectre gadget: 越界推测读取
if (x < array1_size) {           // 分支被训练为taken
    int v = array1[x];           // 推测越界
    temp = array2[v * 4096];     // 把v带入cache
}
// 攻击者测array2各页访问时间, 推断v
```

## 五、与其他技术对比
正常执行无越界，推测执行"短暂越界"却留下缓存痕迹；与纯软件 bug 不同，根因在微架构而非程序逻辑。

## 六、常见误区
误以为回滚架构状态就安全：微架构状态仍泄漏。误以为只有内核受影响：用户态 Spectre V1 即可跨进程。

## 七、与开源书/权威来源对应
Kocher et al. 2019 Spectre；Böhme et al. 2018 Meltdown；量化方法推测执行。

## 八、面试题
问：为何推测执行的副作用能被观测？答：缓存等微架构状态未在回滚中清除。

## 九、演进与趋势
硬件增加推测隔离（eIBRS、自动清除），软件用安全边界（LFENCE）防御。

## 十、小结
推测执行在性能与隔离间制造裂缝，其微架构残留是熔断/幽灵类攻击的共同土壤。
