# 推测执行基础

> 对应 Kocher et al. 2019（Spectre）与 Lipp et al. 2018（Meltdown，USENIX Security）；Hennessy & Patterson 推测执行章。

## 一、背景与挑战

为掩盖分支误预测与缓存缺失带来的长延迟，现代 CPU 在「确认前」就沿预测路径推测执行后续指令，结果在架构态（寄存器/内存）提交前若预测错误则丢弃。但问题在于：推测执行产生的「微架构副作用」（如被填充的缓存行、TLB 项、BTB 条目）并不会被完全撤销，这些残留成为侧信道的根源——攻击者借此推断本不应被访问的数据。这种「性能优化」与「隔离保证」的裂缝，是所有熔断/幽灵类攻击的共同土壤。

换言之，处理器对外承诺的「架构语义」与内部实现的「微架构行为」并不一致：架构上被丢弃的推测，在微架构上留下了可被观测的痕迹。

值得强调的是，这一裂缝不是某个实现 bug，而是「乱序 + 预测 + 共享缓存」这一组合的固有属性。任何为了隐藏延迟而提前执行的设计，都会在「提前执行」与「确认」之间产生一个可被观测的窗口，因此单纯定位到某个指令级缺陷并不能消除风险面。

## 二、核心原理

推测执行沿预测路径运行，访问数据、预取、填充缓存；若预测错误则回滚架构状态（寄存器/内存），但微架构状态（cache、TLB、BTB、分支历史）常遗留。攻击者借助「遗留的微架构状态」推断原本越权/越界访问到的数据值，再通过计时测量泄漏。本质矛盾是：性能优化（推测）与隔离保证（安全）在微架构层出现了裂缝，而这一裂缝对所有带预测的处理器普遍成立，与操作系统或应用代码是否正确无关。

推测的触发源不止分支：还包括访存依赖预测（memory disambiguation，如猜测「store 不冲突」而先 load）、返回地址预测（RAS）、以及地址翻译预取。因此「消除分支推测」并不等于消除全部推测窗口，任何「猜测后确认」的机制都可能成为侧信道载体。

一旦确认失败，处理器必须回滚：恢复寄存器映射、重命名表、ROB、存队列，并把取指重定向到正确路径。回滚的代价与「推测进入多深」近似成正比，于是硬件在「推测深度」与「回滚代价」之间权衡，这个权衡值反过来决定了侧信道窗口的宽度。

## 三、形式化与数学基础

推测窗口内可访问地址集合 $A_{spec}$ 可能超出合法集 $A_{legal}$：

$$A_{spec} \supseteq A_{legal}$$

侧信道通过测量访问 $x \in A_{spec} \setminus A_{legal}$ 的缓存命中时间泄漏信息：

$$Leak \iff AccessTime(x) < Threshold_{cold}$$

即：若 $x$ 曾于推测路径被访问并缓存，则后续探测访问更快，暴露 $x$ 被读过。窗口越宽、可访问地址越多，泄漏面越大。设窗口内可越权访问地址数为 $M$，则单次推测最多泄漏 $\log_2 M$ 比特的地址信息。

若把「单次观测正确率」记为 $p$（受缓存噪声、预取、调度抖动影响），则重复 $N$ 次后通过多数表决恢复单字节的成功率上界为：

$$P_{succ} \approx 1 - (1-p)^N \cdot \text{poly}(N)$$

这解释了为什么泄漏代码里总有大循环：不是算法需要，而是为了把统计显著性从噪声中拉出来。

## 四、代码实现

```c
// 经典 Spectre gadget：越界推测读取，并把值带入缓存
if (x < array1_size) {              // 分支被训练为 taken
    int v = array1[x];              // 推测越界（x 实际超出）
    temp = array2[v * 4096];        // 把 v 带入 cache，留下痕迹
}
// 攻击者随后测 array2 各 4KB 页访问时间，命中页号即 v
// 缓解：在 if 后插入序列化屏障，或限制推测可访问范围
```

```c
// 缓解：用 LFENCE 序列化，使推测无法越过敏感边界
if (x < array1_size) {
    __builtin_ia32_lfence();
    int v = array1[x];
    temp = array2[v * 4096];
}

// 另一种软件缓解：索引掩码，让越界索引在数学上不可能成立
size_t idx = x & (array1_size - 1);   // 需 array1_size 为 2 的幂
temp = array2[array1[idx] * 4096];
```

掩码法的前提是「尺寸为 2 的幂」，否则会破坏语义；LFENCE 法的前提是编译器不会把它优化掉，故需要 atomic 或内联汇编语义保证。两者都比「依赖硬件自动防护」更可控，因此被 JIT 与内核广泛采用。

## 五、与其他技术对比

| 维度 | 正常执行 | 推测执行 | 纯软件 bug |
| --- | --- | --- | --- |
| 越界/越权 | 否（硬件拦截） | 短暂发生（推测） | 可能 |
| 副作用 | 无 | 缓存等微架构残留 | 程序态可见 |
| 根因 | — | 微架构 | 程序逻辑 |
| 可检测性 | — | 程序态不可见 | 可用工具/运行时捕获 |
| 修复方式 | — | 屏障/隔离/ISA 位 | 改代码 |

纯软件 bug 的错误发生在「程序态」（可被检测），而推测执行的越权发生在「微架构态」（程序态无感知），这正是其隐蔽性所在。

## 六、常见误区

误区一：回滚架构状态就安全。错，微架构状态仍泄漏。

误区二：只有内核受影响。错，用户态 Spectre V1 即可跨进程。

误区三：关超线程能根治。错，单线程推测执行本身即可被利用，超线程只是放大共享缓存信道。

误区四：推测只发生在分支。错，访存缺失预取、返回栈、依赖预测等也会触发推测。

误区五：常量时间代码足够。错，常量时间防时序但不防缓存状态残留，需配合隔离。

误区六：只要不把值写到内存就没事。错，连「以秘密为索引做一次访存」都足以把秘密编码到缓存状态里。

## 七、与开源书·权威来源对应

- Kocher et al. 2019《Spectre Attacks》系统阐述推测执行的侧信道利用。
- Lipp et al. 2018《Meltdown》展示权限检查晚于数据返回的变体。
- Hennessy & Patterson 在体系结构章节描述推测执行与分支预测的微架构机制（可作为背景）。
- Bernstein 2005 的缓存时序攻击提供侧信道测量基础。
- Intel SDM 卷 3 与 ARM 官方白皮书给出 LFENCE、SSBS 等屏障与推测限制指令的权威语义。

## 八、面试题

1. 为何推测执行的副作用能被观测？要点：缓存/TLB/BTB 等微架构状态未在回滚中清除，可被计时测量。
2. 推测执行与乱序执行的关系？要点：二者常被同时启用；乱序改变执行顺序，推测沿预测路径提前执行，都可能在错误路径留下痕迹。
3. 彻底消除推测副作用的代价？要点：每次回滚清缓存/TLB 性能不可接受，故需精细隔离而非全清。
4. LFENCE 与掩码两种缓解的取舍？要点：LFENCE 通用但有序列化开销；掩码零开销但要求尺寸为 2 的幂且需防止被编译器优化掉。
5. 为什么超线程会放大风险？要点：同核两线程共享 L1/L2、BTB、执行端口，侧信道信噪比更高，训练更稳定。
6. Spectre 与 Meltdown 的根本差异？要点：Meltdown 利用「权限检查晚于数据可用」，Spectre 利用「合法边界在推测下失效」；前者可由 KPTI 类隔离缓解，后者需软硬协同。

## 九、演进与趋势

硬件增加推测隔离（eIBRS、自动清除微架构状态 MD_CLEAR/VERW）、限制推测可访问范围；软件用安全边界（LFENCE）、常量时间编程、缓存分区；ISA 层提出「推测安全」语义（如 ARM SSBS、Intel 的防御位），从根上收窄推测窗口。未来可能引入按安全域隔离的推测执行，使错误路径的副作用不外泄。

另一条路线是把「安全边界」交给编译器自动化：编译器识别敏感模式（边界检查后紧跟访存）并自动插入屏障，减少对程序员纪律的依赖。长远看，ISA 级「推测安全」抽象是唯一能同时兼顾性能与安全的路径，其具体形态与可用性请以各厂商最新 ISA 文档为准。

## 十、小结

推测执行在性能与隔离之间制造了裂缝：其「虽被丢弃但未清除」的微架构残留，是熔断/幽灵类攻击的共同土壤，也推动了软硬件协同的安全边界设计。理解「架构态 vs 微架构态」的不一致，是理解这一类攻击的根本；而「推测不止来自分支」这一认识，决定了防御覆盖面是否完整。
