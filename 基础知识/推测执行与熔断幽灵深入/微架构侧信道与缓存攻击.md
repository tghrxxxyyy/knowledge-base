# 微架构侧信道与缓存攻击

> 对应 Bernstein 2005《Cache-Timing Attacks on AES》（真实来源）；Kocher/Spectre 与 Lipp/Meltdown 论文；OWASP 侧信道相关指南。

## 一、背景与挑战

除熔断/幽灵这类「推测执行 + 缓存」组合攻击外，缓存本身即是一个强大且普适的侧信道：现代 CPU 多核共享末级缓存（LLC），攻击者可通过测量对某内存/数组的访问时延，推断受害者的访问模式，进而恢复密钥或敏感数据（典型如 AES T-table 攻击）。它不依赖任何推测执行漏洞，因此对范围更广的处理器都成立，是密码实现安全的经典威胁。即便程序逻辑正确、算法安全，缓存这一「共享资源」也会成为信息泄漏的渠道。

更广义地说，任何被多主体共享且访问时延可测的微架构资源（TLB、分支预测器、执行端口）都可能成为侧信道，缓存只是其中最易利用的一种。

缓存攻击的可利用性还取决于「攻击者能否获得高精度计时」。若系统提供纳秒级计时（如 `rdtsc`）或允许高频采样，信噪比就高；相反，若强制使用低分辨率时钟、加入随机抖动、或禁止跨特权计时，攻击难度显著上升。因此「计时接口的开放程度」本身就是安全策略的一部分。

## 二、核心原理

基于时间的攻击测量某内存访问耗时：命中缓存快（数 cycle）、未命中慢（数十~数百 cycle）。两类主流手法：（1）Flush+Reload——先 `clflush` 受害者可能访问的缓存行，再测该地址是否被重新加载命中，命中即说明受害者访问过；（2）Prime+Probe——先用特定数据填充满某个缓存集（驱逐），再测该集访问时间，若变慢说明受害者曾占用该集。二者都依赖「共享缓存状态可被跨进程观测」。区别在于 Flush+Reload 需攻击者与受害者共享同一物理页，Prime+Probe 仅需共享同一缓存集。

另一种重要变体是 Evict+Reload：用「冲突访问」把目标行驱逐出缓存，而不是依赖特权指令 `clflush`，因此在虚拟机与容器中更易实施（无需共享页、也不需 flush 权限）。还有 Flush+Flush 通过「flush 自身耗时」间接判断命中，不触发实际访存，因而更难被基于访存的检测发现。

## 三、形式化与数学基础

命中/未命中时延差显著：

$$\Delta = T_{miss} - T_{hit} \gg 0$$

判决：

$$Bit = \begin{cases} 1 & T_{access} < T_{threshold} \\ 0 & \text{否则} \end{cases}$$

在 AES 中，不同 S-box 索引访问不同 T 表缓存行，反复测量可得密钥字节：

$$K_{byte} = \arg\max_j HitCount(T\ table\ row_j)$$

即通过统计每行命中频率反推被查询的 S-box 索引，逐字节恢复密钥。若缓存集映射函数为 $f(addr)$，则攻击者观测的是 $f$ 的像空间，需考虑冲突带来的噪声。

## 四、代码实现

```c
// Flush+Reload：探测受害者是否访问页偏移 o
void clflush(volatile void *p) { __builtin_ia32_clflush(p); }

int probe(volatile char *p) {
    uint64_t t = rdtsc();
    (void)*p;                       // 触发一次访问
    t = rdtsc() - t;
    return t < HIT_THRESHOLD;       // 1 = 命中（受害者曾访问该行）
}
// 攻击流程：clflush(shared+o) → 等受害者 → probe(shared+o) 返回 1 即命中
```

```c
// Prime+Probe：填充缓存集后测驱逐
void prime(char *set_base) {
    for (i = 0; i < WAYS; i++) touch(set_base + i * STRIDE);  // 占满该集
}
int probe(char *set_base) {
    uint64_t t = measure_first(set_base);
    return t > COLD_THRESHOLD;     // 变慢说明受害者曾占用该集
}

// 取多次测量的最小值，比平均值更接近「无干扰」的纯时延
uint64_t robust_time(volatile char *p, int reps) {
    uint64_t best = UINT64_MAX;
    for (int i = 0; i < reps; i++) {
        uint64_t t = time_once(p);
        if (t < best) best = t;     // 最小值滤波，抑制调度噪声
    }
    return best;
}
```

需注意：`rdtsc` 可能被乱序执行打乱，实践中需用 `lfence`/`rdtscp` 保证计时的边界，否则测量结果会掺入无关指令的延迟。

## 五、与其他技术对比

| 维度 | Flush+Reload | Prime+Probe | 熔断/幽灵 |
| --- | --- | --- | --- |
| 需共享内存 | 是（同页/同映射） | 否（按缓存集） | 否 |
| 精度 | 高（行级） | 中（集级） | 高 |
| 依赖漏洞 | 无（纯缓存） | 无 | 需微架构缺陷 |
| 需特权指令 | 需 clflush | 否 | 否 |
| 跨虚拟机可行 | 较难 | 可行 | 视实现 |

缓存侧信道是「通用基础能力」，熔断/幽灵只是在其上叠加了「越权/越界读取」作为信息源，二者可独立存在。

## 六、常见误区

误区一：常量时间代码可完全免疫。错，还需防缓存集冲突（即使时间相同，不同地址可能映射到同一缓存集）。

误区二：只在加密领域有用。错，任何数据依赖的访存（如密钥查找、权限判断分支）都可能泄漏。

误区三：关闭超线程即可防御。错，LLC 跨核共享，单核内多进程仍共享缓存。

## 七、与开源书·权威来源对应

- Bernstein 2005《Cache-Timing Attacks on AES》首次系统展示缓存时序如何恢复 AES 密钥，是常量时间编程的奠基性文献。
- Spectre/Meltdown 论文把缓存作为侧信道载体，复用 Flush+Reload 方法论。
- OWASP 在「Cryptographic Storage」「Side Channel」相关指南中强调常量时间实现。
- Hennessy & Patterson 描述缓存层次与命中/未命中时延差异，提供微架构背景。
- Intel SDM 关于 `CLFLUSH`、`RDTSC/RDTSCP` 的语义定义，是核实攻击原语可行性的权威来源。

## 八、面试题

1. 常量时间编程为何重要？要点：使执行时间/缓存访问模式不依赖秘密，消除时序侧信道。
2. Flush+Reload 与 Prime+Probe 的核心区别？要点：前者需共享内存、按行精度高；后者无需共享、按缓存集推断。
3. 为何缓存集冲突也需关注？要点：即使访问时间相同，映射到同集的地址会相互驱逐，仍暴露访问模式。
4. 为什么攻击代码常用最小值而非平均值？要点：调度与中断只会让测量变慢，取最小值更接近无干扰的纯时延，信噪比更高。
5. Evict+Reload 相比 Flush+Reload 的优势？要点：无需 `clflush` 特权指令，仅靠冲突访问驱逐，在受限环境（如虚拟化/容器）中更易实施。
6. 如何从源头消除这类攻击面？要点：让访存模式与秘密解耦（常量时间、无数据依赖查表、bitsliced 实现），而非仅靠系统层隔离。

## 九、演进与趋势

缓解包括缓存分区（CAT）、模糊时间（fuzzy time，限制高精度计时如 `clock_gettime` 分辨率）、以及软硬件协同隔离（如可信执行环境内的独立缓存域）；同时算法层普及「常量时间 + 无数据依赖查表」（如 AES 的 bitsliced 实现），从源头消除缓存依赖。硬件也引入缓存随机化与分区以增大攻击难度。

另一个方向是把「常量时间」变成可验证属性而非人工纪律：通过形式化工具或专用 DSL 生成无数据依赖的实现，并在 CI 中用统计检验验证时序分布。这类「可证明的实现」比「声称是常量时间」更可靠，尤其适合密码库与内核密钥处理路径。

## 十、小结

缓存侧信道是推测执行攻击之外的另一大片攻击面：共享缓存的命中/未命中时延差异，使任何数据依赖的访存都可能泄漏秘密。安全编码（常量时间、缓存隔离）是根本防线，硬件缓存分区是增强手段。理解 Flush+Reload 与 Prime+Probe 的区别，以及「计时质量决定可行性」这一前提，是分析与防御此类攻击的基础。
