# Spectre 变体1：边界检查绕过

> 对应 Kocher et al. 2019《Spectre Attacks: Exploiting Speculative Execution》（IEEE S&P，真实作者年份）；Google Project Zero 分析。

## 一、背景与挑战

Spectre V1（边界检查绕过，Bounds Check Bypass）利用 CPU 的分支预测：攻击者先「训练」某个条件分支（如 `x < len`）总是 taken，然后喂入一个越界输入 `x`，使 CPU 推测执行通过边界检查之后的越界访问，再把越界读到的秘密字节经由缓存侧信道（Flush+Reload）泄漏出去。它影响几乎所有带分支预测的乱序/推测执行处理器，且可在用户态跨进程、跨沙箱，是幽灵家族中利用门槛最低、覆盖面最广的变体。即便代码逻辑完全正确，推测执行也会「越界读取」，这是传统程序分析无法发现的漏洞。

更危险的是，V1 不依赖任何特权或内核漏洞，纯靠用户态代码即可构造 gadget，浏览器 JIT、解释器、eBPF 等动态生成代码的环境尤其容易成为载体。

V1 的关键前提是「攻击者能控制进入边界检查的索引」。在许多真实场景中索引并非直接来自不可信输入，而是由若干运算间接导出（如 `arr[hash(key) % n]`）；此时攻击者只需找到一个「可控输入能改变索引」的路径，V1 依然成立。因此「是否有可控索引到达敏感访存」才是风险评估的正确问题。

## 二、核心原理

攻击分三步：（1）训练条件分支为 taken，让 BTB/模式历史偏向误预测；（2）触发误预测，推测执行越界读 `array1[x]`，并用其值 `v` 索引 `array2[v*4096]`，把 `v` 带入缓存；（3）攻击者测量 `array2` 各偏移的缓存命中，命中偏移即还原出 `v`（即越界字节）。关键在于：推测执行沿错误路径读到了本无权访问的内存，且其缓存痕迹在回滚后仍然遗留，成为可观测侧信道。

三个条件缺一不可：训练使分支被误预测、越界地址在推测窗口内可被访问（不触发异常或异常晚于访存）、以及编码访问在缓存中留下可分辨的痕迹。因此缓解手段也分别对应三点——打断训练（用屏障强制顺序）、阻止越界访存（掩码）、或缩小可观测信道（缓存分区）。

还有一层细节：V1 的 gadget 并不需要「把值返回」。只要在推测路径上执行了「以秘密为索引的访存」，缓存状态就被污染；函数返回不返回、结果是否被使用都无关紧要。这解释了为什么「只读、不返回」的代码依然脆弱。

## 三、形式化与数学基础

对合法输入约束 $C(x)$（如 $x < len$），推测执行在 $\neg C(x)$ 时仍运行：

$$Exec_{spec} \models read\ array1[x],\quad x \notin [0,len)$$

泄漏量受缓存区分度与可重复训练次数限制：

$$Leak = \log_2(\text{cache sets}) \times N_{repeat}$$

即每次重复可恢复若干比特，多次叠加还原完整字节，$N_{repeat}$ 越大分辨率越高。实践中每次泄漏一个字节需数百至数千次重复测量以获得统计显著性。

把噪声考虑进来，可用「信噪比」刻画可行性：

$$SNR \approx \frac{\Delta_{hit-miss}}{\sigma_{noise}} \cdot \sqrt{N_{repeat}}$$

这解释了为什么在虚拟化、超线程或频繁中断的环境中攻击更困难（噪声 $\sigma$ 大），而在空闲的物理机上更容易（$\sigma$ 小）；也解释了为什么攻击者常通过「固定 CPU、关闭干扰线程、提高计时精度」来放大 $SNR$。

## 四、代码实现

```c
// 易受攻击的 victim 函数（x 被攻击者控制为越界值）
int victim(size_t x) {
    if (x < SECRET_LEN) {                 // 被训练为 taken
        return small_table[secret[x] * 64];
    }
    return 0;
}
// 缓解：在边界检查后用 LFENCE 阻止推测越过检查
int victim_safe(size_t x) {
    if (x < SECRET_LEN) {
        __builtin_ia32_lfence();          // 序列化，阻止越过检查的推测
        return small_table[secret[x] * 64];
    }
    return 0;
}
```

```c
// 攻击者侧：测量 array2 各页命中，还原 secret[x]
for (i = 0; i < 256; i++) clflush(&probe[i*4096]);
victim(malicious_x);                      // 推测越界，v 被带入 cache
for (i = 0; i < 256; i++)
    if (hit(&probe[i*4096])) return i;    // 命中即 secret[x] 的值

// 另一种缓解：索引掩码，使越界在算术上不可能（要求 size 为 2 的幂）
size_t idx = x & (SECRET_LEN - 1);
return small_table[secret[idx] * 64];
```

掩码法没有序列化开销，但改变了语义（等价于取模环绕），必须在业务上可接受；LFENCE 保留语义但引入流水线停顿。两者都依赖编译器不优化掉屏障，因此需用具备语义保证的内建函数或内联汇编。

## 五、与其他技术对比

| 维度 | Spectre V1 | Spectre V2 | Meltdown |
| --- | --- | --- | --- |
| 利用点 | 条件分支越界 | 间接分支目标（BTI） | 权限检查延迟 |
| 所需 | gadget + 训练 | 跨进程 BTB 投毒 | 直接越权读内核 |
| 范围 | 用户态跨进程 | 内核/跨进程 | 内核内存 |
| 训练对象 | 方向预测器 | 目标预测器 | 无需训练 |
| 典型缓解 | LFENCE/掩码 | retpoline/eIBRS | KPTI |

V1 仅靠条件分支即可，无需构造间接分支 gadget，也不依赖内核权限缺陷，因此利用面最广。

## 六、常见误区

误区一：数组边界检查能挡住 V1。错，推测执行会绕过检查执行越界读。

误区二：只在 C/C++ 存在。错，JIT/解释器（如 JS 引擎、eBPF）同样可构造 gadget。

误区三：只要不返回越界值就安全。错，秘密已被带入缓存侧信道，无需函数返回。

误区四：关闭超线程可根治。错，单线程推测本身即可被利用。

## 七、与开源书·权威来源对应

- Kocher et al. 2019《Spectre Attacks》第 4 节专门描述 V1（Bounds Check Bypass）与 PoC。
- Google Project Zero 的「Reading privileged memory with a side-channel」对 V1 给出可复现分析。
- 经典缓存攻击（Bernstein 2005）提供 Flush+Reload 方法论支撑。
- Hennessy & Patterson 体系结构章节描述分支预测微架构，可作背景。
- Intel SDM 卷 3 给出 LFENCE 的序列化语义，是核实缓解有效性的权威依据。

## 八、面试题

1. Spectre V1 的三步是什么？要点：训练分支、推测越界读、用缓存侧信道泄漏。
2. 为什么 LFENCE 能缓解 V1？要点：它序列化执行，阻止 CPU 在边界检查完成前推测越过。
3. 为什么 V1 难以纯软件根治？要点：任意条件分支后访存都可能成 gadget，需编译器插桩或 ISA 级隔离。
4. LFENCE 与索引掩码的取舍？要点：LFENCE 保语义但有停顿；掩码无开销但要求尺寸为 2 的幂且改变环绕语义。
5. 为什么「不返回越界值」也不能免于攻击？要点：泄漏发生在缓存状态上，与函数返回值无关。
6. 如何系统性排查 V1 风险？要点：找出「可控索引 → 敏感访存」的所有路径，重点检查边界检查后紧跟访存的模式，逐处插入屏障或掩码。

## 九、演进与趋势

浏览器 JIT 引入索引掩码（如 `x & (len-1)` 边界）、指针中毒防护；编译器加入 `-mlfence`/Spectre 缓解 pass；硬件层面推出自动推测隔离（如 ARM 的 SSBS、Intel 的 eIBRS 相关位）。但 V1 因根植于分支预测，仍主要靠软件防护与「无推测越界」的编程纪律。

## 十、小结

V1 揭示了「逻辑正确的边界检查」在推测执行下不再安全：推测沿错误路径读到了越权数据并留下缓存痕迹，催生了「在敏感边界插入序列化屏障」的全新安全编程范式。其本质是微架构行为与程序语义之间的契约失效，而防御的完整性问题应回到「是否存在可控索引到达敏感访存」这一最朴素的判断上。
