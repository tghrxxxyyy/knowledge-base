# Spectre 变体2：分支目标注入

> 对应 Kocher et al. 2019《Spectre Attacks》（BTI，分支目标注入，IEEE S&P）；Intel retpoline 指南；Linux IBPB 文档。

## 一、背景与挑战

Spectre V2（分支目标注入，Branch Target Injection）利用间接分支（函数指针、虚表调用、switch 跳转表）的预测器——分支目标缓冲区（BTB）。攻击者在自身地址空间执行与目标间接调用「相同（或别名）PC」的代码，把 BTB 训练成指向攻击者选中的 gadget；当受害者进程调用该间接分支时，CPU 误预测到 gadget 并推测执行，从而泄漏受害者内存。跨地址空间 BTB 共享是它得以跨进程的关键，使其比 V1 更具通用性，且缓解难度更高，因为它直接攻击控制流预测这一核心机制。

与 V1 不同，V2 不需要条件分支后的越界 gadget，而可跳转到攻击者选定的任意代码片段，因此能构造更灵活的泄漏原语。

V2 还有「同进程内跨特权的变体」（如用户态诱导内核的间接调用推测跳入用户态 gadget），以及「跨虚拟机（cloud）」场景。后者尤为严重：同一物理核上的两个租户可能通过共享 BTB 相互影响，这也是云厂商在虚拟化层追加预测器隔离的原因。

## 二、核心原理

间接分支的目标由 BTB 根据「调用点 PC」预测。BTB 多为跨进程/跨地址空间共享（为提升预测率），于是攻击者可在自己的进程里用相同 PC 反复调用某地址，把该 PC 的预测目标「投毒」为恶意 gadget 地址。受害者执行到同一 PC 的间接调用时，推测跳入 gadget，gadget 执行越权读并用缓存侧信道编码秘密，最终经 Flush+Reload 还原。投毒之所以跨进程有效，正是因为 BTB 不以地址空间为隔离维度。

完整的攻击链包含四步：定位「受害者与攻击者共享 PC 的间接分支」→ 构造同 PC 的训练循环把预测目标投毒 → 触发受害者执行并按缓存侧信道编码秘密 → 用 Flush+Reload/Evict+Reload 还原。任何一步受干扰（如预测器被刷新、gadget 被取消映射）都会让攻击失败，因此 V2 的可靠性低于 V1，但一旦成功泄漏面更大。

## 三、形式化与数学基础

BTB 以 PC 为键映射目标 $T$。投毒使：

$$T_{pred}(PC_{victim}) = PC_{gadget} \neq T_{arch}$$

推测在此错误目标上执行 $Gadget$，其内存访问 $array2[secret \times k]$ 留下缓存痕迹。泄漏量同样取决于缓存区分度与重复次数：

$$Leak \propto \log_2(\text{cache sets}) \times N_{repeat}$$

且因 gadget 可由攻击者自由布置，单次投毒可服务多次泄漏，重复次数 $N_{repeat}$ 与训练稳定性直接相关。

若攻击者能选择 gadget 中的偏移乘数 $k \ge$ 缓存行大小（通常 4096），则每次访问落在互不冲突的缓存行，$k$ 越大抗噪声越强；反之若两个不同 secret 值映射到同一缓存行，泄漏就会产生歧义。因此 gadget 的 $k$ 选择本质是在「地址空间开销」与「噪声鲁棒性」之间权衡。

## 四、代码实现

```c
// 受害者：间接调用（PC 与攻击者训练的一致）
void (*dispatch)(int) = &handler_a;
// 攻击者先执行 dispatch = evil 训练 BTB（相同 PC 地址）
// 受害者调用时推测跳 evil：
dispatch(arg);
// 缓解：retpoline 用 return 指令替代间接跳，目标由 RAS 决定
void safe_dispatch(int arg) {
    // 编译器插入 retpoline thunk，避免 BTB 参与目标选择
    __asm__ volatile ("call .Lthunk; .Lthunk: ... ret" :::);
}
```

```c
// 攻击者训练（伪）：在本进程用相同 PC 反复调用 evil
for (i = 0; i < N; i++) evil_dispatch(evil_arg);  // 把 BTB[PC] 投毒为 evil
// 随后受害者同 PC 间接调用即被诱导跳 evil

// 攻击者侧编码与还原（复用 V1 的缓存信道）
for (j = 0; j < 256; j++) flush(&probe[j * 4096]);
trigger_victim();
for (j = 0; j < 256; j++)
    if (reload_is_fast(&probe[j * 4096])) secret_byte = j;
```

注意：训练循环的 PC 必须与受害者间接调用的 PC「在 BTB 索引/标签意义上等价」，实践中常利用共享库或 ASLR 未覆盖的固定映射来满足这一条件，具体可行性以目标微架构实测为准。

## 五、与其他技术对比

| 维度 | Spectre V1 | Spectre V2 | Meltdown |
| --- | --- | --- | --- |
| 利用点 | 条件分支越界 | 间接分支目标（BTI） | 权限检查延迟 |
| 跨进程 | 需 gadget | 需 BTB 共享投毒 | 直接越权 |
| 缓解 | LFENCE | retpoline/eIBRS | KPTI |
| 训练对象 | 方向预测器 | 目标预测器（BTB/IBT） | 无需训练 |
| 可靠性 | 高（易复现） | 中（依赖投毒稳定） | 高 |

V2 把「控制流预测器」本身变成攻击向量，比 V1 更通用也更难根治，因为它利用了预测器跨进程共享这一为性能而设计的特性。

## 六、常见误区

误区一：地址空间隔离能挡 V2。错，BTB 跨进程共享，隔离无效。

误区二：只读间接调用安全。错，预测器可被训练到任意目标，调用是否「只读」不影响投毒。

误区三：retpoline 影响所有调用。错，仅间接分支需要 thunk，直接调用不受影响。

误区四：IBPB 免费。错，刷新预测器有切换开销，且过度刷新会显著降低分支预测命中率。

误区五：gadget 必须存在于受害者。错，攻击者常把 gadget 布置在自己可控的内存中，仅需受害者跳入。

误区六：单靠用户态就能完美防御。错，跨特权级投毒需 OS/微码层（IBRS/IBPB）配合，编译期缓解只是其中一环。

## 七、与开源书·权威来源对应

- Kocher et al. 2019《Spectre Attacks》第 5 节专述 V2（BTI）与跨进程投毒 PoC。
- Intel retpoline 指南给出 thunk 模板与编译器选项（`-mretpoline`）。
- Linux 内核文档描述 IBPB（Indirect Branch Prediction Barrier）在上下文切换时的使用。
- Lipp 2018《Meltdown》把 V2 列为同族威胁并对比。
- Intel SDM 卷 3 描述间接分支、IBRS/eIBRS 的行为与 MSR 控制，是核实缓解语义的权威来源。

## 八、面试题

1. retpoline 如何阻止 BTI？要点：用返回栈（RAS）替代间接跳，RAS 不易被跨进程投毒，目标不再由 BTB 决定。
2. 为何 V2 比 V1 缓解更难？要点：需改间接分支语义（retpoline）或硬件隔离 BTB（eIBRS），且涉及编译层面改动。
3. IBPB 的作用与代价？要点：切换时刷新分支预测器，防跨进程训练，但增加上下文切换延迟。
4. eIBRS 与 retpoline 的关系？要点：eIBRS 用硬件让不同特权级/地址空间不共享预测状态，可替代 retpoline 的性能开销；两者可叠加部署。
5. 为什么攻击者能在自己进程里训练受害者的分支？要点：BTB 索引基于 PC（及历史）而非地址空间 ID，共享库与固定映射让两侧 PC 等价。
6. 投毒为什么会失效？要点：上下文切换刷新、预测器容量驱逐、gadget 被取消映射或地址随机化都会打破训练。

## 九、演进与趋势

硬件 eIBRS（增强间接分支限制）从硬件隔离 BTB，使不同特权/进程不共享预测状态；IBPB 在上下文切换刷新预测器；新一代微架构引入按特权级/地址空间分区的 BTB，逐步以硬件方案取代 retpoline 的性能与维护负担。同时，编译器默认启用 retpoline 与 Spectre 缓解 pass，形成软硬协同防线。

值得注意的是，缓解本身仍在演进：单纯禁用预测的代价（每次间接调用都近似一次误预测）被称为「安全税」，因此业界更倾向「按域隔离」而非「关闭预测」。虚拟化场景还引入了每 vCPU 的预测器状态保存/恢复，进一步把隔离粒度细化到租户。

## 十、小结

V2 把「控制流预测器」本身变成攻击向量：跨进程 BTB 投毒使受害者推测跳入攻击者 gadget。它迫使硬件为预测器增加安全边界（eIBRS/IBPB），软件侧则以 retpoline 重写间接分支作为过渡防线。理解 BTB 的跨进程共享语义，是评估 V2 风险与缓解完整性的核心；具体缓解开关与 MSR 语义请以厂商最新文档为准。
