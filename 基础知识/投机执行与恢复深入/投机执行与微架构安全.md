# 投机执行与微架构安全

> 对应 Kocher et al. 2019（Spectre）、Lipp et al. 2018（Meltdown）；Saltzer & Schroeder 1975（最小权限与完全中介）。

## 一、背景与挑战

传统安全模型假设只有「架构可见」状态（寄存器、内存）影响程序，微架构状态（缓存、TLB、分支历史、BTB）被视为不可观测的实现细节。投机执行证明：被推测执行的指令虽不提交架构状态，却会修改微架构状态，进而被侧信道（计时、端口争用）观测，从而泄露本不可访问的秘密。这打破了「隔离只管架构状态」的假设，把安全边界从「程序员可见」扩展到了「硬件可见」。

这一发现的意义在于它推翻了 Saltzer & Schroeder 1975 提出的「完全中介」在硬件层面的成立前提：如果隔离机制只覆盖架构状态，而微架构状态可以被跨越隔离边界地影响与观测，那么「完全中介」在物理上就不成立。修不修复、如何修复，成为体系结构、编译器、操作系统三方共同的课题。

## 二、核心原理

攻击分两步：第一步诱导投机访问秘密（利用分支预测、乱序、间接跳转预测等让处理器沿本不该走的路径执行 load 秘密）；第二步借微架构侧信道观测痕迹（如缓存行被带入则后续访问更快）。防御须斩断「秘密 → 微架构状态 → 可测信道」这一链条：要么阻止越权投机（屏障/限制），要么消除可观测信道（缓存分区/清空），要么用恒定时间代码避免依赖秘密的分支/访存。三者分别对应「源头、痕迹、信道」三层防御。

从信息流角度看，攻击的本质是「建立了一条不被架构权限约束、但物理上存在的隐蔽信道」。任何可以被投机访问影响的微架构状态（不止缓存，还有 TLB 条目、分支预测器状态、预取器状态、内存消歧结构）都可能是信道的载体。因此「禁用缓存」只能堵住一条路，而非全部。

## 三、形式化与数学基础

信息泄漏量受信道容量约束。设攻击者观测为 $O$，秘密为 $S$，泄漏成立当且仅当存在可区分的微架构状态差异：

$$I(S; O) > 0 \iff \exists\ observable\ \delta\ state\ correlated\ with\ S$$

即投机使秘密影响了缓存/TLB 集合，计时测量 $t(addr)$ 区分命中/未命中，从而以约 $1\ bit/探测$ 恢复秘密字节。恒定时间（constant-time）实现要求 $t$ 与秘密无关，切断该相关——形式化即 $\forall s_1,s_2,\ t(s_1) = t(s_2)$。

信道容量可用香农公式粗略刻画：若每次探测能在「命中/未命中」两个状态间可靠区分，则单次探测最多传递 1 bit；对 $v$ 的 256 种取值，需 $\log_2 256 = 8$ 次探测恢复一个字节。实际中因噪声与命中率不完美，通常需多次重复取多数投票，这直接决定了攻击的耗时量级。

防御的代价也可量化：插入 `lfence` 会阻止其后的指令越过屏障投机，从而引入流水线气泡；在频繁发生的代码路径上插入，性能损失可达百分之几十。这解释了为何缓解措施通常只在「真正处理秘密的边界」处启用，而非全局插入。

## 四、代码实现

```c
// 防御：用屏障阻止越权投机跨过边界检查
void safe_access(size_t i, size_t len, uint8_t *data) {
    if (i >= len) return;                 // 真实边界检查
    asm volatile("lfence" ::: "memory");  // 阻止后续指令越过此点投机
    use(data[i]);                          // 此时投机已被串行化
}
// 恒定时间比较，避免依赖秘密的分支
int ct_eq(const uint8_t *a, const uint8_t *b, size_t n) {
    uint8_t diff = 0;
    for (size_t k = 0; k < n; k++) diff |= a[k] ^ b[k];
    return diff == 0;                      // 无分支，执行时间与秘密无关
}
```

数组边界硬化的写法（把「可能越界的下标」钳制到合法范围）：

```c
// 用无分支的方式把 i 限制在 [0, len) 内，避免依赖比较结果的分支
size_t clamp_index(size_t i, size_t len) {
    size_t mask = -(size_t)(i < len);      // i < len 时 mask 全 1，否则全 0
    return i & mask;                        // 越界时返回 0，永不越界访存
}
```

## 五、与其他技术对比

| 防御层 | 手段 | 代价 |
| --- | --- | --- |
| 架构层 | 权限位、页表 | 已存在，但不足 |
| 微架构层 | lfence/retpoline/eIBRS | 性能损失 |
| 信道层 | 缓存分区/清空 | 高，难普遍 |
| 代码层 | 恒定时间实现、边界硬化 | 需重写热点，可验证性差 |
| 调度层 | 内核页表隔离（KPTI） | 地址空间切换开销 |

纯架构层保护（权限位）不足；需微架构层缓解（lfence、retpoline、eIBRS、缓存分区），而信道层代价过高难以通用。实践中是多层叠加：架构防「越权访问」、微架构防「越权投机」、代码层防「依赖秘密的时序」。

## 六、常见误区

1. 误以为只禁用缓存即可解决：性能崩溃，且侧信道不止缓存（TLB、端口争用、分支历史都可用）。
2. 误以为用户态无法影响内核投机：Spectre 跨进程/跨沙箱均可能，恶意代码可训练共享的预测器。
3. 误以为不写内存就安全：load 秘密进缓存已足够泄露；读即写微架构状态。
4. 把 lfence 当万能：lfence 仅串行化，不修预测器状态，需配合 IBPB 等刷新。
5. 误以为编译器优化会加屏障：需显式屏障或语言级标注（如 Rust 的 `atomic`/C 的 `volatile` 不保证抗侧信道），不能依赖默认优化。
6. 以为恒定时间代码可以随手写对。编译器可能把无分支代码优化回分支形式，需检查生成的汇编并禁用相关优化。
7. 以为缓解措施可以只做一次。新的攻击变体会绕过旧缓解，需持续跟进厂商公告（以官方最新文档为准）。

## 七、与开源书·权威来源对应

- Saltzer & Schroeder 1975 提出最小权限与完全中介原则，正是「隔离须覆盖全部状态」的早期论述，今日被微架构侧信道重新激活。
- Kocher et al. 2019（Spectre）、Lipp et al. 2018（Meltdown）揭示投机执行的微架构侧信道，开启体系结构安全新方向。
- Intel/ARM 的 Speculative Side Channel 缓解指南给出 lfence/eIBRS/STIBP 用法与适用场景。
- Hennessy & Patterson《量化方法》：投机执行与精确异常的架构基础。
- 相关安全公告（CVE 系列）与厂商白皮书给出具体缓解与性能影响（以官方最新文档为准）。

## 八、面试题

1. 问：最小权限原则与投机攻击的关系？
   答：隔离必须覆盖微架构状态，否则即便架构权限正确，投机仍把秘密渗入缓存等可测信道。
2. 问：lfence 作用与局限？
   答：串行化后续指令的投机越过，阻止越权 load；但不刷新预测器历史，跨上下文需 IBPB。
3. 问：为何恒定时间代码能抗侧信道？
   答：执行时间与秘密无关，消除「秘密→计时」相关，从信道层切断泄漏。
4. 问：防御应针对哪三层？
   答：源头（阻止越权投机）、痕迹（限制微架构状态可见性）、信道（恒定时间/分区），层层兜底。
5. 问：为什么「不写内存」不足以防御？
   答：只要「读」把秘密带入缓存/TLB，就已产生可观测痕迹，读即等价于对微架构状态的写。
6. 问：恒定时间代码写完后还需要做什么？
   答：需审计生成的汇编，确认编译器未把它优化回依赖秘密的分支或变长内存访问。

## 九、演进与趋势

硬件提供推测限制指令（如 ARM FEAT_SPECRES、x86 IBPB/STIBP）、按上下文隔离预测状态；软件结合数据清洗与恒定时间库。形式化方法（如定理证明缓存行为）开始用于验证抗侧信道，把「不泄漏」从经验变成可证明属性。

一个更根本的方向是「默认安全」的硬件设计：在微架构层面为隔离域提供独立的预测器与缓存分区，使跨域影响在物理上不可能，而非依赖软件逐点插入屏障。这类设计代价高，但在多租户云环境中价值显著。

## 十、小结

投机执行的安全问题源于微架构残留可被侧信道观测，防御需架构与微架构协同。它深刻改变了安全模型：安全不再只是「谁能读写什么」，还要问「谁能在缓存/预测器里留下什么痕迹」——这是体系结构与安全融合的里程碑式课题。Spectre 之后，编译器、CPU、操作系统都不得不把微架构状态纳入威胁模型。理解「源头—痕迹—信道」三层防御框架，是评估任何缓解措施是否充分的基本方法。
