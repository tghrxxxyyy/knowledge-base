# 错误推测的回滚机制

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》；显著参考 MIPS R10000 / Intel P6 微架构的 ROB 与寄存器重命名恢复机制。

## 一、背景与挑战

投机执行一旦发生误预测（分支错、load 冲突、异常）或非法访问，必须保证架构状态（即程序员可见的寄存器/内存）不被污染，并尽快回到正确路径。回滚机制决定恢复延迟，是投机执行能否真正「无成本」的兜底保障。若恢复不彻底或太慢，投机的收益会被抵消，甚至引入正确性问题——例如误把投机写入的寄存器暴露给后续提交指令。

需要区分两类状态：架构状态（architectural state，程序员可见，必须精确恢复）与微架构状态（microarchitectural state，如缓存、TLB、分支历史，不必也不宜清空）。回滚的正确性只要求前者精确，后者残留是允许的——但这一「允许」正是侧信道攻击的立足点：攻击者可以通过缓存状态的变化推断出被回滚路径上的数据。因此回滚机制的设计必须同时回答「恢复什么」与「保留什么」两个问题。

## 二、核心原理

现代乱序处理器用 reorder buffer（ROB）与寄存器别名表（RAT）实现恢复：每条指令在 ROB 中记录目标架构寄存器与重命名后的物理寄存器。误预测点之后的 ROB 项被丢弃，物理寄存器回收；架构映射（RAT）与空闲物理寄存器表恢复到分支点的快照。为加速，常用「检查点（checkpoint / shadow RAT）」——在分支发出时保存当时的 RAT 与 freelist 快照，恢复时直接装载，免去从 ROB 顺序重建。前端从正确 PC 重新取指。内存写则在 commit 前不生效（store buffer），故回滚不影响内存。

正确性的两条不变量必须同时成立：其一，ROB 严格按程序序提交，因此任何投机指令的影响只存在于 ROB 与物理寄存器中，绝不外泄到架构寄存器或内存；其二，对同一架构寄存器，RAT 始终指向「最年轻的未提交写」所对应的物理寄存器，回滚后 RAT 指向分支点当时的映射，语义上等价于这些投机写从未发生。内存侧则靠 store buffer 延迟生效——在 commit 前 store 只写入缓冲区，其他投机 load 通过转发从缓冲区取值，从而在保证正确性的同时仍获得转发收益。

## 三、形式化与数学基础

恢复代价近似：

$$recovery\_latency = flush\_cycles + rename\_reset + refill\_frontend$$

设检查点数量为 $n$，可并行恢复的分支数为 $n$；无检查时需从 ROB 中该分支项向前重建映射，代价正比于投机深度 $D$：

$$recovery\_cost_{no\_chk} = O(D),\quad recovery\_cost_{chk} = O(1)$$

故检查点以 $O(n)$ 存储（每个分支存一份 RAT 快照）换 $O(1)$ 恢复。物理寄存器文件大小须 ≥ 所有未完成指令的目标数 + 检查点占用，否则 freelist 提前枯竭。

把期望代价写全：设误预测率为 $m$，则每指令的平均恢复开销约为 $m \times recovery\_latency$，它与预测收益共同决定投机的净收益。这解释了为何「提高预测准确率」与「加快恢复」具有同等重要性——前者降低 $m$，后者降低单次代价，二者在乘积上等价。若某方案把恢复从 100 周期降到 10 周期，其效果等同于把误预测率降为十分之一。检查点数量的约束则来自物理寄存器预算：$R \ge D + n \cdot |RAT|$ 类关系（示意，实际按寄存器数量计），因此 $n$ 越大可支持的投机深度 $D$ 越小，形成「快速恢复 vs 深投机」的直接冲突。

## 四、代码实现

```c
#define NCHK 4
typedef struct { int rat[32]; int freelist[64]; } Checkpoint;
Checkpoint chk_buf[NCHK];
int chk_head = 0;

void take_checkpoint(int br_rob, int rat[32], int *freelist) {
    // 快照必须在分支指令重命名时立即拍摄，晚一拍即无法精确恢复
    chk_buf[chk_head] = (Checkpoint){.rat = copy(rat), .freelist = copy(freelist)};
    br_checkpoint[br_rob] = chk_head;
    chk_head = (chk_head + 1) % NCHK;   // 环形复用；容量即「最大未决分支数」
}

void rollback(int branch_rob, Checkpoint chk) {
    restore_rat(chk.rat);             // 恢复架构->物理寄存器映射（关键一步）
    restore_freelist(chk.freelist);   // 回收投机期分配的物理寄存器
    rob_truncate_after(branch_rob);   // 丢弃分支点之后的全部 ROB 项
    fetch_pc = correct_target;        // 前端从正确路径重新取指
    // 注意：缓存/TLB/分支历史不清空——保证性能，但也构成侧信道面
}

void commit(int rob_head) {
    // 提交时把架构状态真正落地：RAT 的已提交部分固化、store buffer 写内存
    if (is_store(rob_head)) drain_store_buffer(rob_head);
    if (is_branch(rob_head)) release_checkpoint(rob_head);
    rat_commit(rob_head);             // 与回滚互斥：提交后该检查点不再需要
}
```

`take_checkpoint` 的时机极其关键：必须在分支指令进入重命名阶段时拍摄「它自己之前」的映射，若晚一拍，快照中已混入分支之后的投机重命名，恢复将无法回到正确映射。另一个易错点是检查点与提交的配对释放——若分支正确提交后未释放检查点，环形队列会被长期占用，最终导致新分支无法建立检查点而降级到慢速恢复。

## 五、与其他技术对比

| 策略 | 恢复速度 | 存储开销 | 对投机深度影响 | 典型实现 |
| --- | --- | --- | --- | --- |
| 无检查点（ROB 重建） | 慢，O(D) | 低 | 无额外限制 | 早期乱序核 |
| 检查点（shadow RAT） | 快，O(1) | 高（每分支一快照） | 占用寄存器预算 | MIPS R10000 / P6 |
| 混合（部分检查点） | 中 | 中 | 中 | 多数现代核 |
| 影子寄存器文件 | 快 | 高 | 中 | 研究原型 |

无检查点需从 ROB 顺序重建映射，慢；检查点以少量存储换快速恢复，但要限制检查点数量以免占用过多物理寄存器，反而限制并行度。现代设计多采用「有限数量检查点 + 超出后降级为 ROB 重建」的混合策略，在绝大多数场景享受 O(1) 恢复，仅在极端深投机时承受慢恢复。

## 六、常见误区

1. 误以为回滚仅清空流水线：架构寄存器映射（RAT）与物理寄存器空闲表也须恢复，否则后续指令用错源。
2. 误以为微架构状态全清：缓存/TLB/分支历史等微架构状态通常不清（这正是 Spectre 可利用之处）。
3. 忘记回收投机物理寄存器：不回收会耗尽 freelist，导致后续无法重命名。
4. 检查点数量无限：过量检查点会提前占满物理寄存器文件，反而限制并行与投机深度。
5. 认为 store 回滚需撤销内存：store 在 commit 前只驻 store buffer，未写内存，丢弃即可。
6. 在分支重命名之后才拍快照：快照会包含投机重命名，恢复后映射错误，属功能性 bug。
7. 忽略检查点的释放：分支正确提交后不释放检查点会耗尽槽位，令恢复路径退化为慢速模式。
8. 认为回滚代价与投机深度无关：无检查点时开销正比于 $D$，深投机下慢恢复会显著拖累平均性能。

## 七、与开源书·权威来源对应

- Hennessy & Patterson《Computer Architecture》讨论 Tomasulo/ROB 与检查点恢复延迟，给出恢复代价的量化分析（如回滚 100 项指令的周期数）。
- MIPS R10000、Intel P6 微架构用 shadow RAT 做快速恢复，是工业标准做法；相关论文量化了检查点对物理寄存器压力的影响。
- Bryant & O'Hallaron《CSAPP》第 5 章从程序员视角解释乱序执行与投机，帮助建立「架构状态 vs 微架构状态」的直觉。

## 八、面试题

1. 问：检查点 RAT 的作用？
   答：在分支发出时保存寄存器映射快照，误预测时直接装载，使恢复从 O(D) 降为 O(1)。
2. 问：回滚为何要恢复 freelist？
   答：投机期分配的物理寄存器必须回收，否则 freelist 枯竭，后续指令无法重命名而阻塞。
3. 问：为何缓存状态不清？
   答：清缓存代价过高且会破坏性能；但这正是投机副作用可被侧信道观测的根源（见微架构安全文档）。
4. 问：检查点数量如何取舍？
   答：多则恢复快但占物理寄存器、限制投机深度；少则省存储但恢复慢。实际取「允许的最大未解决分支数」量级。
5. 问：为什么快照必须在分支重命名时拍？
   答：晚拍会把分支之后的投机重命名混入快照，恢复后映射错误，无法回到正确语义状态。
6. 问：store 为何不需要回滚？
   答：提交前 store 只驻留 store buffer 未写内存，丢弃缓冲区项即等价于该写从未发生。

## 九、演进与趋势

多级检查点、按预测置信度提前部分恢复降低代价；把推测限制（speculation restriction）指令用于关键安全边界，控制回滚范围与副作用可见性。研究还探索「影子寄存器文件」以减少恢复时的拷贝。

另一方向是让回滚机制与安全需求协同：在跨越特权边界或涉及秘密数据的路径上插入屏障，限制投机深度以缩小可观测的微架构泄漏面。这类设计以少量性能换取可证明的安全边界，是当前处理器微架构设计的活跃议题。具体实现以各厂商官方最新文档为准。

## 十、小结

错误推测回滚通过 ROB 截断与映射检查点快速恢复架构一致性，是投机执行的兜底保障。其设计权衡「恢复速度 vs 检查点存储」，而「恢复了什么、没恢复什么」恰恰划定了微架构安全的攻击面——这是性能与安全的又一处交叠。理解回滚机制，就理解了为什么 CPU 能「大胆猜测、安全反悔」。

三条不变量可作为实现自检：提交严格按 ROB 顺序、架构寄存器在提交前绝不被外部可见、物理寄存器在回滚后必被回收。任何违反其一的设计都会在极端依赖链下暴露正确性或性能缺陷。
