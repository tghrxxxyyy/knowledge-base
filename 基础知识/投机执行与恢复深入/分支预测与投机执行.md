# 分支预测与投机执行

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》；Kocher et al. 2019（Spectre）。

## 一、背景与挑战

控制相关使流水线在分支结果未定时必须停顿（stall），否则取到的可能是指令流错误方向的指令。考虑一个循环内 `if (rare) A(); else B();`——每次迭代都等分支解析会浪费大量周期。分支预测器猜测方向并沿该路径投机执行（speculative execution），若猜对则省去等待、提升 IPC；猜错则必须 flush 投机部分并回滚到正确路径。预测准确率直接决定有效吞吐，而投机留下的微架构痕迹（缓存/分支历史）正是 Spectre 类漏洞的根源。

核心矛盾在于「预测越早越好、验证越晚越省」：预测必须发生在取指阶段（此时分支指令甚至还没译码完），而真实结果要到执行阶段才可知。这中间隔着数级流水与一个完整的乱序窗口，意味着预测器必须在信息极少的时刻做出决定，并承担误判后冲刷整条流水线的代价。

## 二、核心原理

预测器依据历史猜测方向：最基础的两位饱和计数器（2-bit saturating counter），更进阶的有全局历史 GShare（用分支地址 XOR 全局历史索引）、TAGE（多表不同历史长度组合）、感知机（perceptron）预测器。预测后沿目标取指执行，指令在 ROB 中保持「未完成」状态；提交（commit/retire）时核对实际方向，错误则 flush 投机部分并恢复架构状态。预测越准，flush 越少，IPC 越高。现代 CPU 还用 BTB（Branch Target Buffer）预测目标地址，二者配合才能避免取指停顿。

方向预测与目标预测必须成对工作，这一点常被低估：即使方向预测全对，若 BTB 未命中导致取不到目标地址，取指仍会停顿甚至走错路径。此外，预测器需要「训练」——初次遇到某分支时必然无信息，因此冷启动期与阶段切换期（工作集变化）会出现准确率低谷，这也是基准测试与真实负载表现差异的来源之一。

## 三、形式化与数学基础

两位饱和计数器状态机在四个状态间转移：强/弱 taken、强/弱 not-taken，仅越过中点才改变预测方向，从而抗单次噪声：

$$state \in \{SN, WN, WT, ST\},\quad state \leftarrow \begin{cases} \min(state+1, ST) & taken \\ \max(state-1, SN) & not\ taken \end{cases}$$

预测方向为 $state \ge WT$（弱以上即预测 taken）。有效 IPC 近似 $IPC \approx \frac{1}{1 - p_{hit} + p_{miss}\cdot cost}$，其中 $cost$ 为误预测惩罚周期（深流水下可达 15–40 周期）。GShare 用 $index = pc \oplus GHR$ 提升相关性。

把该式代入数值可直观看出准确率的杠杆效应：设 $cost = 20$ 周期，则准确率从 95% 提升到 99% 时，每指令平均惩罚从 $0.05 \times 20 = 1$ 周期降到 $0.2$ 周期，CPI 改善约 0.8——在基线 CPI 为 1 的处理器上，这相当于近一倍的性能差距。这解释了为什么工业界不惜用数千至上万表项、多级历史长度为代价去提升最后几个百分点。此外，误预测率还受分支「偏置程度」影响：对几乎恒 taken 的循环分支，两位计数器即可达近 100%；而对随机分支（如数据相关的比较），任何历史预测器都难以超过约 50%–75%，此时更有效的策略是「延迟解析」或谓词化。

## 四、代码实现

```c
#define N 4096
int bimodal[N];                 // 两位饱和计数器（0..3）

int predict(uint32_t pc) {
    int i = (pc >> 2) & (N - 1);         // 指令对齐：跳过低 2 位
    return (bimodal[i] >> 1) & 1;        // 最高位为方向：1 表示预测 taken
}

void update(uint32_t pc, int taken) {
    int i = (pc >> 2) & (N - 1);
    bimodal[i] += taken ? 1 : -1;          // 饱和于 [0,3]
    if (bimodal[i] < 0) bimodal[i] = 0;
    if (bimodal[i] > 3) bimodal[i] = 3;
}

// GShare：用全局历史寄存器 GHR 混合索引，区分「同地址不同上下文」
int gshare_predict(uint32_t pc, uint16_t ghr) {
    int i = ((pc >> 2) ^ ghr) & (N - 1);
    return (bimodal[i] >> 1) & 1;
}

// BTB：预测 taken 时的目标地址，与方向预测互补
typedef struct { uint32_t tag; uint32_t target; int valid; } BTBEnt;
BTBEnt btb[256];

uint32_t predict_target(uint32_t pc, int *hit) {
    int i = (pc >> 2) & 255;
    if (btb[i].valid && btb[i].tag == (pc >> 2)) { *hit = 1; return btb[i].target; }
    *hit = 0;
    return pc + 4;                        // 未命中：顺序取指，待后端纠正
}
```

`update` 中「先增减再钳位」的顺序保证状态始终落在 $[0,3]$；若把钳位写在增减之前，状态可能短暂越界并在后续计算中被误读。`predict_target` 的未命中回退到顺序取指（`pc + 4`）是常见设计：虽然可能取错，但代价等同于一次方向误预测，且不增加面积。

## 五、与其他技术对比

| 预测器 | 状态来源 | 硬件成本 | 准确率 | 训练速度 |
| --- | --- | --- | --- | --- |
| 静态（backward-taken） | 无 | 极低 | 低 | 无需 |
| 两位计数器 | 局部 | 低 | 中 | 快 |
| GShare | 全局历史 XOR PC | 中 | 高 | 中 |
| TAGE | 多表多历史长度 | 高 | 很高 | 较慢 |
| 感知机 | 历史线性组合 | 高 | 很高 | 慢 |

静态预测简单但准确率低；动态预测随历史提升，但资源与功耗更高，且高准确率预测器本身成为侧信道攻击面（见《推测执行的安全漏洞Spectre》）。TAGE 与感知机代表了两种不同思路：前者用「按需选择合适历史长度」逼近理论最优，后者用线性权重学习更复杂的模式，二者在准确率上旗鼓相当但实现风格迥异。

## 六、常见误区

1. 误以为预测错误仅损失几条指令：现代深流水误预测代价可达数十周期（刷新前端、ROB、BTB）。
2. 误以为投机无副作用：投机指令会改缓存、TLB、分支历史，留下可测微架构痕迹。
3. 用一位计数器即可：一位易被噪声翻转，需两位抗单次异常。
4. 忽略 BTB 缺失代价：目标地址预测失败同样触发 flush，甚至比方向错更贵。
5. 认为预测器越大越好：表过大增加命中延迟与功耗，边际收益递减。
6. 忽略别名冲突：不同分支映射到同一表项会互相污染，需合理哈希或更长 tag 来抑制。
7. 认为准确率提升线性带来性能提升：收益随准确率升高而饱和（已接近 100% 时提升空间极小）。
8. 忽视预测状态跨上下文残留：多进程/多线程共享预测器时，残留状态既是性能问题也是安全问题。

## 七、与开源书·权威来源对应

- Hennessy & Patterson《Computer Architecture》用整章论述分支预测器（bimodal/GShare/TAGE）与误预测代价，给出各预测器准确率实测。
- Kocher et al. 2019（Spectre）揭示投机执行的微架构副作用可被侧信道利用，把分支预测推到安全研究前沿。
- 感知机预测器见 Jiménez & Lin 2001 等工作，是工业预测器的代表。
- Bryant & O'Hallaron《CSAPP》第 5 章从程序员视角说明分支与流水线的相互影响（如条件传送优于分支）。

## 八、面试题

1. 问：两位计数器为何优于一位？
   答：抗噪声，需连续两次误预测才改变方向，避免偶发异常污染预测。
2. 问：误预测代价来自哪？
   答：flush 流水线、清空 ROB/流水线、前端重新取指与填充，深流水下可达数十周期。
3. 问：GShare 用 XOR 全局历史的意义？
   答：把分支地址与历史混合索引，区分「相同地址在不同上下文」的分支行为，提升相关性。
4. 问：BTB 与方向预测的区别？
   答：方向预测猜「taken/not-taken」，BTB 猜「taken 时的目标地址」，二者任一失误都触发取指停顿。
5. 问：如何估算准确率提升的收益？
   答：用 $IPC \approx 1/(1 - p_{hit} + p_{miss}\cdot cost)$；准确率越高，边际收益越小（趋于饱和）。
6. 问：为什么预测器残留状态是安全问题？
   答：分支历史与 BTB 可被跨上下文训练，攻击者可借此诱导受害者执行特定投机路径（Spectre 的前提）。

## 九、演进与趋势

TAGE、感知机预测器持续提升准确率；同时引入安全约束（如限制可被训练的别名、推测限制指令），在性能与抗侧信道间权衡。硬件提供 IBPB/STIBP 等刷新预测状态机制，防止跨上下文训练污染。

另一方向是把预测与「延迟解析」结合：对难以预测的分支，转而用谓词执行或条件传送消除分支本身，把控制依赖转为数据依赖，从根本上绕开误预测（其代价是可能多做无用功）。这类技术在手写优化与编译器层面都广泛使用，与预测器形成互补。

## 十、小结

分支预测驱动投机执行以提升 IPC，但误预测需经 ROB 恢复，且其微架构残留构成安全挑战。它完美体现了现代处理器「用猜测换吞吐」的哲学——而猜测的副作用，正是体系结构与安全交叉研究的核心切口。没有分支预测，现代 CPU 的 IPC 会退回数十年前；有了它，我们也要为它的副作用买单。

三条实践结论：方向与目标预测须配套（缺一即停顿）、准确率收益趋于饱和（后期要靠更大投入换更小收益）、投机副作用不可忽略（既是性能优化点也是安全攻击面）。
