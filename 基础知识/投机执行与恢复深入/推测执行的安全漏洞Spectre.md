# 推测执行的安全漏洞Spectre

> 对应 Kocher et al. 2019（Spectre: Secrets leaked in speculative execution）；Lipp et al. 2018（Meltdown）。

## 一、背景与挑战

投机执行会运行本不应执行的指令并留下微架构痕迹（主要是缓存状态）。攻击者可先「训练」分支预测器，诱导受害者沿错误路径投机执行，访问本无权访问的秘密，再把秘密编码进缓存行；随后用 cache timing 侧信道读出。Spectre 系列（含变体 1 边界检查绕过、变体 2 分支目标注入、变体 3 Meltdown 等）因根植于投机+侧信道，难以靠微码补丁彻底根治，成为体系结构安全领域影响最广的漏洞族。

Spectre 与 Meltdown 的关键区别值得厘清：Meltdown 利用「权限检查与异常处理的时序漏洞」，使越权读的结果能在异常抛出前被投机使用，本质上是硬件实现缺陷，可通过隔离页表（KPTI）与微码缓解；Spectre 利用的是「分支预测这一合法优化」本身，即使硬件实现完全正确，只要存在预测就会存在投机，因此无法靠修 bug 解决，只能限制投机的范围或影响。

## 二、核心原理

Spectre 变体 1（边界检查绕过）：构造越界读 `x = arr1[arr2[i]]`，先训练使分支预测「条件总为真」，于是 `if (i < len)` 的 false 分支被投机执行，越界读 `kernel_mem[i]` 并把 `arr1` 对应缓存行带入缓存；随后用计时测 `arr1` 各偏移的访问时间反推 `v`。整个过程中越权读未提交架构状态（异常被抑制），但其缓存痕迹持久，构成隐蔽信道。变体 2 则注入间接跳转目标，使受害者在错误地址投机执行 gadget，能力更强（可任意读受害者地址空间）。

「训练」这一步是攻击可行性的关键：攻击者需在同一物理核上反复执行相同模式的分支，使预测器形成「该分支总是 taken/not-taken」的历史。因此跨核、跨超线程的同核共享预测器都构成攻击面。防御上，除了屏障，还需在上下文切换时刷新预测器（IBPB）或在硬件上隔离预测状态（eIBRS/STIBP）。

## 三、形式化与数学基础

侧信道观测：设攻击者探测数组 `arr1` 偏移 $k$，若 $time\_access(arr1[k*256])$ 小，则该缓存行曾被投机加载，从而恢复 $v = k$：

$$v = \arg\min_k time\_access(arr1[k \times 256])$$

秘密字节经 $v \times 256$ 的偏移映射到不同缓存组（每组一个字节，避免同组干扰），逐字节泄露。每探测一次恢复 1 字节，遍历 $v \in [0,255]$ 即可定位。该过程成立的前提是缓存命中/未命中的时间差 $> $ 噪声，且 `arr1` 足够大覆盖全部 256 种可能。

为什么用 $256$ 而非 $64$（缓存行大小）作为步长？因为不同 $v$ 必须落到不同缓存行、且最好落到不同缓存「组」（set），以避免同一组内多个候选相互驱逐。取 4 KB 以上的数组并以 256 字节为步长，能保证任意两个候选落在不同页与不同组，从而让「最快的那个」唯一对应 $v$。

泄漏速率可用「每次探测恢复 $b$ 位」刻画：单字节需 8 位信息，若每次测量能在 256 个候选中唯一确定，则一次完整扫描（256 次计时）恢复一个字节。实际因噪声需多轮统计，典型速率在数十 KB/s 量级。

## 四、代码实现

```c
// 示意（不可用于攻击）：变体 1 越界读训练分支
void victim(size_t i, size_t len, uint8_t *kernel_mem) {
    if (i < len) {                     // 被误导预测为 taken
        uint8_t v = kernel_mem[i];     // 投机越界读，载入缓存
        dummy[v * 256] = 1;            // 把 v 映射到缓存行
    }
}
// 攻击者随后测 dummy[k*256] 命中情况，恢复 v
uint8_t recover(void) {
    for (int k = 0; k < 256; k++)
        if (probe(&dummy[k * 256])) return (uint8_t)k;
    return 0;
}
// 防御：在边界检查后加 lfence，阻止 false 分支被投机执行
```

变体 2（分支目标注入）的防御思路——用 retpoline 把「间接跳转」改写为「训练免疫的返回序列」：

```c
// retpoline 的核心：用 ret 代替间接 jmp，使预测器无法被注入目标
#define RETPOLINE(target) do {                       \
    asm volatile("call 1f\n"                         \
                 "1: pause; lfence; jmp 2f\n"        \
                 "2: mov %0, (%%rsp)\n"              \
                 "ret\n" : : "r"(target));           \
} while (0)
```

## 五、与其他技术对比

| 漏洞 | 利用点 | 缓解 |
| --- | --- | --- |
| Spectre V1 | 边界检查绕过 | lfence / 数组边界硬化 |
| Spectre V2 | 分支目标注入 | retpoline / eIBRS / IBPB |
| Meltdown | 权限检查与异常乱序 | KAISER/KPTI + 微码 |
| Spectre-RSB | 返回栈预测污染 | RSB 填充/清理 |
| Spectre-STL | 存储绕过（store 转发） | 屏障/数据依赖硬化 |

Meltdown 利用权限检查与异常的顺序漏洞，可被内核页表隔离（KPTI）与微码补丁缓解；Spectre 利用分支预测，更难根治，需软件屏障与硬件推测限制协同，且跨进程/跨 VM 均可能。

## 六、常见误区

1. 误以为仅内核受影响：Spectre 跨进程、跨沙箱、跨虚拟机均可能（共享预测器/BTB）。
2. 误以为禁用缓存即可：性能不可接受，且侧信道不止缓存（端口争用、TLB 也可用）。
3. 误以为不写内存就无泄漏：load 秘密进缓存已足够，读即写微架构状态。
4. 误以为编译器优化会替你加屏障：需显式 `lfence` 或语言级标注敏感边界。
5. 误以为更新微码即可根除：Spectre 根因在架构层，微码只能缓解部分变体，无法消除全部。
6. 误以为只有「读」才泄漏。投机执行的分支/地址本身也可能泄漏信息（如 Spectre 的地址依赖变体），需更广义地看待。
7. 忽略缓解措施的性能成本。全局插入屏障可能使性能下降显著，需按「敏感边界」精准启用。

## 七、与开源书·权威来源对应

- Kocher et al. 2019（Spectre）论文给出原理、变体与软件缓解（lfence/retpoline），并列出可被训练的组件（BTB、RSB 等）。
- Lipp et al. 2018（Meltdown）描述利用乱序权限检查的变体及 KPTI 缓解，与 Spectre 并列开启侧信道时代。
- Intel/ARM 安全 advisories 列出各变体对应微码与固件修复，以及 `LFENCE` 的串行化语义。
- Hennessy & Patterson《量化方法》：投机执行与分支预测的架构背景。
- Saltzer & Schroeder 1975：完全中介原则，被微架构侧信道重新审视。

## 八、面试题

1. 问：Spectre 为何难以彻底修复？
   答：根因是「投机执行 + 微架构侧信道」，二者都是性能优化所必需；只能缓解（屏障、推测限制、预测器隔离），无法在不显著损失性能下消除。
2. 问：lfence / retpoline 作用？
   答：lfence 串行化投机越界，retpoline 用训练免疫的返回序列替代间接分支，避免 V2 目标注入。
3. 问：为什么缓存痕迹能泄露未提交的读？
   答：缓存属微架构状态，不被回滚清除；虽架构上读被取消，但缓存行已载入，计时即可区分。
4. 问：为什么映射用 v*256 而非 v*1？
   答：每个字节放不同缓存组，避免相邻字节在同一 cache line 互相干扰，保证计时能精确定位 v。
5. 问：Spectre 与 Meltdown 的本质区别？
   答：Meltdown 是硬件权限检查的时序缺陷（可打补丁），Spectre 是分支预测这一合法优化的固有副作用（无法根除）。
6. 问：为什么需要 IBPB 而不只是 lfence？
   答：lfence 只串行化当前指令流，不清理预测器历史；跨上下文攻击需用 IBPB 刷新预测状态。

## 九、演进与趋势

新型缓解：eIBRS 硬件隔离预测上下文、推测限制指令、缓存分区与硬件清洗；同时出现 Spectre-RSB、Spectre-STL、Spectre-NG 等新变体，攻防持续演进。形式化验证开始用于确认关键代码路径无越权投机，编译器也引入 `-mindirect-branch` 等自动缓解。

更长远的趋势是「软硬件协同的默认安全」：硬件提供隔离的预测器分区与推测限制原语，编译器与语言运行时自动在敏感边界插入缓解，使开发者无需逐点手写屏障。这需要 ISA、编译器、语言规范三方的共同演进。

## 十、小结

Spectre 暴露投机执行的微架构副作用可被侧信道利用，是安全与体系结构交叉的重要课题。它提醒我们：性能优化引入的「不可见状态」也可能是攻击面，安全模型必须扩展到微架构层。其修复不是一次性补丁，而是软件屏障与硬件推测控制的长久协作——这或许是过去十年体系结构领域影响最深远的一次「重估」。
