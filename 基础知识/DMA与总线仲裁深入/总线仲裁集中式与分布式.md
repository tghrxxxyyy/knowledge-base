# 总线仲裁集中式与分布式

> 对应 Tanenbaum《Modern Operating Systems》与《Structured Computer Organization》中总线与仲裁的讨论、ARM AMBA 规范中的互联仲裁与 QoS 约定，以及 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》互连章节。

## 一、背景与挑战

多个主设备（CPU 簇、DMA、GPU/NPU、PCIE 控制器）需要共用一组互连资源。仲裁器（arbiter）的职责是在同一时刻只允许一个主设备使用总线（或某个具体资源），并决定下一个授权给谁。没有仲裁，多个主设备同时驱动总线会导致电气冲突与数据损坏。

挑战来自四个相互冲突的目标：一是正确性（互斥与有序），二是公平（防止饿死），三是延迟上界（实时流量需要可预测的响应），四是吞吐（尽量减少总线空闲与切换开销）。集中式与分布式是两种经典的实现风格：集中式把决策集中在一个仲裁器，实现简单、决策一致；分布式把决策分散到各主设备（或沿链路逐级传递），避免单点瓶颈、更易扩展，但需要额外的协议来达成一致。

## 二、核心原理

集中式仲裁的常见形式：

- 菊花链（daisy chain）：授权信号沿设备串行传递，离仲裁器近的设备优先。布线省、扩展容易，但优先级固定且靠前设备有优势，单点断链会阻断后续。
- 轮询（polling）：仲裁器依次询问各设备是否需要使用总线，天然公平，代价是询问开销随设备数增长。
- 独立请求（independent request）：每个设备有独立的请求线与授权线，仲裁器内部按策略选择（固定优先级、轮询、加权）。响应最快，但线数随设备数增长，仲裁器规模 $O(N)$。
- 并行优先级编码（parallel priority）：请求集中送入优先级编码器，输出授权，逻辑简单，适合中等规模。

分布式仲裁的常见形式：

- 自选择（self-selection）：每个设备把自己在优先级链路上的编号与总线上观察到的编号比较，最大（或最小）者胜出。需要解决竞争窗口内的稳定问题（需等总线信号稳定）。
- 冲突检测（如 CSMA/CD 思路）：允许同时发起，检测到冲突后随机退避重试。适合总线式共享介质，但无确定性延迟。
- 令牌传递（token passing）：令牌在设备间循环，持令牌者有权使用总线；可保证有界轮转，但令牌丢失/重复需要恢复机制。
- NoC 中的分布式仲裁：每个路由器按输出端口独立仲裁（轮询、加权或矩阵仲裁器），公平性与优先级通过网络级的虚通道与流控共同实现。

AXI 互联的仲裁通常是「集中式仲裁器 + 每端口独立仲裁」的组合：主设备在事务上携带 QoS 标注，互联在每个从端口（或每类资源）按优先级与加权轮询选择请求，并用限速防止某主设备独占。这与纯硬件的固定优先级不同：它把「策略」部分暴露给软件（QoS 字段），从而实现按业务需求调整带宽分配。

## 三、形式化与数学基础

设主设备 $i$ 的请求率为 $R_i$、平均每次授权的传输长度为 $L_i$、总带宽为 $BW$。在理想加权轮询下，主设备 $i$ 获得的带宽为：

$$BW_i = \frac{R_i w_i}{\sum_j R_j w_j} \cdot BW$$

其中 $w_i$ 为权重。若传输长度差异很大（如一个主设备发长突发、另一个发单拍事务），按「事务数」加权与按「字节数」加权会显著偏离，因此更精确的做法是按服务字节计账（赤字轮询 DRR）。

等待时间的近似模型（把仲裁器视为一个服务台）。设总到达率 $\lambda = \sum_i \lambda_i$、服务率 $\mu$，则利用率 $\rho = \lambda/\mu$，平均排队等待：

$$W_q \approx \frac{\rho}{2\mu(1-\rho)} \quad \text{（M/D/1 近似）}$$

若考虑事务长度的二阶矩 $E[L^2]$，可用 Pollaczek–Khinchine 公式：

$$W_q = \frac{\lambda E[L^2]}{2(1-\rho)}$$

这解释了为什么「少数主设备使用超长突发」会显著抬高所有主设备的平均等待——方差项直接进入公式。

公平性可用 Jain 公平指数衡量（$x_i$ 为主设备 $i$ 获得的服务量，$n$ 为设备数）：

$$J = \frac{\left(\sum_{i=1}^{n} x_i\right)^2}{n\sum_{i=1}^{n} x_i^2}, \qquad \frac{1}{n} \le J \le 1$$

对固定优先级仲裁，低优先级事务的等待上界为「所有更高优先级事务的最大突发之和」加上当前进行中事务的剩余服务时间：

$$W_{low} \le \sum_{j \in HP} B_j^{max} + t_{residual}$$

这一界是硬实时系统可调度性分析的基础；若优先级数量多且高优先级冲动频繁，该界会发散，说明纯固定优先级不足以支撑实时保证。

## 四、代码实现

```c
/* 集中式：带权重与老化的仲裁器（固定优先级 + 防止饿死）
   特点：决策集中、确定性强；输入数为 N 时逻辑规模 O(N) */
#define N 4
static const int weight[N] = {4, 2, 1, 1};
static int credits[N]       = {4, 2, 1, 1};
static int wait_ticks[N]    = {0, 0, 0, 0};

int central_arb(const int req[N]) {
    /* 1) 老化：等待过久的请求提升优先级，避免饿死 */
    for (int i = 0; i < N; i++) {
        if (req[i]) wait_ticks[i]++;
        else        wait_ticks[i] = 0;
    }
    for (int i = 0; i < N; i++) {
        if (req[i] && wait_ticks[i] > AGING_THRESHOLD) {
            wait_ticks[i] = 0;
            return i;                       /* 超时者优先 */
        }
    }
    /* 2) 加权轮询：按信用分配服务次数 */
    for (int i = 0; i < N; i++) {
        if (req[i] && credits[i] > 0) { credits[i]--; return i; }
    }
    for (int i = 0; i < N; i++) credits[i] = weight[i];    /* 新一轮 */
    for (int i = 0; i < N; i++) {
        if (req[i] && credits[i] > 0) { credits[i]--; return i; }
    }
    return -1;                              /* 无请求 */
}
```

```c
/* 分布式：自选择（self-selection），各设备比较自己在链路上的编号
   特点：无中心仲裁器、可扩展；但需要等待总线稳定，且必须有平局处理 */
static int self_select(int my_id, int *bus_priority_level, int *bus_stable) {
    if (!(*bus_stable)) return 0;                       /* 总线未稳定，不参与 */
    if (my_id >= *bus_priority_level) return 0;         /* 有更高优先级者在驱动 */
    *bus_priority_level = my_id;                        /* 抢占编号（越小越高） */
    return 1;                                           /* 本设备胜出并驱动编号 */
}

/* 令牌传递：持令牌者可用总线，用完把令牌交给下一个
   特点：轮转有界、公平性可分析；代价是令牌帧的开销与丢失恢复 */
static int token_ring_next(int cur, int active[N], int n) {
    for (int k = 1; k <= n; k++) {
        int i = (cur + k) % n;
        if (active[i]) return i;                        /* 跳过离线设备 */
    }
    return cur;
}
```

实现要点：分布式方案必须处理「稳定窗口」——只有在总线上所有请求信号都稳定后才能比较编号，否则会误判；令牌方案必须有令牌丢失检测与重生机制（否则系统整体停摆）；集中式方案的仲裁延迟与主设备数相关，规模大时可用分层仲裁（簇内 + 簇间）把组合逻辑深度压下来。

## 五、与其他技术对比

| 维度 | 菊花链 | 独立请求（集中式） | 自选择分布 | 令牌传递 | NoC 按端口仲裁 |
| --- | --- | --- | --- | --- | --- |
| 决策位置 | 集中（沿链传递） | 集中 | 分布式 | 轮转分布 | 每路由器分布 |
| 线数 | 少（$O(1)$ 级联） | 多（$O(N)$） | 中 | 少 | 链路内嵌 |
| 优先级灵活性 | 差（位置决定） | 好 | 中 | 轮转 | 好（加权/轮询） |
| 延迟上界 | 弱 | 可解析 | 需稳定窗口 | 有界轮转 | 依赖网络拥塞 |
| 容错 | 差（断链阻断） | 中 | 好 | 需令牌恢复 | 好（多路径） |
| 可扩展性 | 中 | 差 | 好 | 中 | 好 |

## 六、常见误区

1. 认为高优先级永远先得总线是「好策略」：会造成低优先级饿死，必须加入老化或保底机制。
2. 认为仲裁只影响性能不影响正确性：若一致性响应消息被长期延迟或乱序处理不当，可导致协议级活锁甚至死锁。
3. 认为分布式仲裁一定更快：自选择需要等待总线稳定窗口，且平局与竞争处理引入额外延迟。
4. 忽略事务长度的影响：按事务数分配资源在变长突发下严重偏离按字节公平，需要按字节计账。
5. 忽略令牌丢失的后果：令牌传递方案若无恢复机制，令牌丢失即整个互连停摆。
6. 认为仲裁器与 QoS 是同一件事：仲裁只决定「下一个是谁」，QoS 还包含限速、延迟上界与隔离等更强承诺。

## 八、面试题

1. 问：固定优先级仲裁的缺陷与补救？答：低优先级可能长期得不到服务而饿死；补救包括老化（等待超时提权）、保底带宽（分层仲裁中的最低配额）以及加权轮询。
2. 问：如何兼顾公平与实时性？答：用分层策略——关键流量用有延迟上界的优先级通道并限制其最大突发，非关键流量用加权轮询按比例分享剩余带宽，并用老化兜底。
3. 问：菊花链与独立请求的取舍？答：菊花链线数少、扩展成本低但优先级由位置决定且断链会阻断后续；独立请求响应快、优先级灵活但连线数随主设备数增长、仲裁器规模变大。
4. 问：分布式仲裁的主要难点是什么？答：需要总线稳定窗口来避免竞争误判，还要处理平局、冲突退避与（令牌方案下的）令牌丢失恢复，确定性与容错设计更复杂。
5. 问：为什么按事务数加权不足以实现带宽公平？答：事务长度可变，长突发会获得超额带宽；应按服务字节数记账（DRR 等）才能真正实现带宽比例公平。

## 九、演进与趋势

- 从共享总线到 NoC：集中仲裁被「按端口仲裁 + 网络流控」取代，仲裁器从全局单点变为分布在各路由器的局部部件。
- QoS 精细化与软件可编程：QoS 字段、限速与隔离从「按主设备」演进到「按进程/虚拟机」，并可与 DVFS 协同。
- 分层仲裁成为主流：簇内（低延迟）与簇间（高聚合）分离，兼顾逻辑深度与公平性。
- 可预测性与有界延迟：面向自动驾驶与工业控制，追求有界延迟而非平均性能，推动时间触发与预留带宽类机制。
- 形式化与验证：仲裁器的公平性与无饿死性质可通过模型检查与断言验证，成为 SoC 验证流程的一部分。

## 十、小结

总线仲裁在冲突中分配带宽：集中式（菊花链、轮询、独立请求、优先级编码）实现简单、确定性好，但存在单点规模与容错局限；分布式（自选择、冲突检测、令牌传递）可扩展、无单点，但需要稳定窗口与更复杂的恢复机制。无论哪种形式，正确的取舍都必须同时回答四个问题——如何保证互斥与有序、如何避免饿死、如何给出延迟上界、如何在切换开销与吞吐之间平衡。理解这四个问题，就理解了从共享总线到 NoC 一切仲裁设计的共同骨架。
