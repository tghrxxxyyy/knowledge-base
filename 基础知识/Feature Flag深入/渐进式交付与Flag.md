# 渐进式交付与Flag

> 对应 Kim et al. 2016 (Accelerate / The DevOps Handbook)。

## 一、背景与挑战
想要小步快跑又不敢全量，需要把"部署"和"发布"解耦：代码先上生产但功能对用户不可见，再逐步放量。

## 二、核心原理
渐进式交付 = 持续部署 + Flag/灰度。代码始终部署到生产，用 Flag 控制功能可见范围，从内部员工到小比例用户再到全量。

## 三、形式化与数学基础
发布进度由 Flag 目标人群比例 p 控制：p: 0 -> 0.01 -> 0.1 -> 1.0。部署频率与发布解耦，部署可每日多次而发布按需推进。

## 四、代码实现
```python
rollout = flags.rollout_percent("new-feed", user.id)
if rollout > 0 and hash(user.id) % 100 < rollout:
    return new_feed(user)   # 按比例命中
return old_feed(user)
```

## 五、与其他技术对比
相比金丝雀（按实例流量），Flag 按用户属性更精准；二者常结合使用，Flag 决定功能，灰度决定实例。

## 六、常见误区
- 部署了却长期不开 Flag，等于未发布，价值未兑现。
- Flag 判定未做哈希，同一用户时进时出。

## 七、与开源书/权威来源对应
Accelerate 证明部署频率与领先时间的高效能来自解耦的发布机制。

## 八、面试题
部署与发布解耦的好处？Flag 与灰度如何配合？

## 九、演进与趋势
渐进式交付平台把 Flag、灰度、指标分析串联成自动化决策闭环。

## 十、小结
Flag 是渐进式交付的控制开关，让"上生产"与"给用户体验"成为两件独立的事。
