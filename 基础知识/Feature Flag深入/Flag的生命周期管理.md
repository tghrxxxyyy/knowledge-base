# Flag的生命周期管理

> 对应 Martin《Clean Code》。

## 一、背景与挑战
Flag 上线后常被遗忘，代码里残留大量 if/else 死分支，既增加复杂度又制造混淆，形成"技术债"。

## 二、核心原理
Flag 应经历：创建 -> 灰度 -> 全量 -> 下线四阶段。全量稳定后必须移除对应分支与判断，并归档决策记录。

## 三、形式化与数学基础
设 Flag 状态机 S = {draft, rolling, full, removed}。转移 full -> removed 触发代码清理；未完成移除的 Flag 计入技术债度量 D。

## 四、代码实现
```python
# 全量后直接删除分支，而非保留 is_on 判断
def checkout(user):
    return new_checkout(user)   # 旧路径已移除
# 同时在配置中心删除 new-checkout 键
```

## 五、与其他技术对比
相比只增不删，规范的生命周期显著降低维护成本；相比永久开关，它要求组织纪律保障。

## 六、常见误区
- 功能全量后仍保留 is_on 判断"以防万一"。
- 多个 Flag 嵌套，分支组合爆炸难以测试。

## 七、与开源书/权威来源对应
《Clean Code》主张删除死代码、避免不必要的条件复杂度。

## 八、面试题
如何保证 Flag 被及时下线？嵌套 Flag 的测试矩阵如何收敛？

## 九、演进与趋势
工具自动检测"长期全开 Flag"并生成清理 PR，把生命周期自动化。

## 十、小结
Flag 不是免费的，生命周期管理（尤其是下线）决定其长期成本。
