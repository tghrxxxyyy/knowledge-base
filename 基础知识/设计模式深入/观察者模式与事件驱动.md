# 观察者模式与事件驱动

> 对应 Gamma, Helm, Johnson & Vlissides 1994 (GoF《Design Patterns》)。

## 一、背景与挑战
当多个模块需要响应同一状态变化（如订单支付后通知库存、积分、消息），硬编码调用会产生强耦合与爆炸式依赖。

## 二、核心原理
定义一对多依赖：主题（Subject）维护观察者列表，状态变更时广播通知；观察者实现统一更新接口，自行决定响应逻辑。

## 三、形式化与数学基础
主题 S 持有观察者集合 O = {o1..on}。状态变更事件 e 触发 notify：forall o in O: o.update(e)。复杂度 O(n)，通知顺序通常应不依赖业务结果。

## 四、代码实现
```python
class Subject:
    def __init__(self):
        self._obs = []
        self._state = None
    def attach(self, o):
        self._obs.append(o)
    def set_state(self, s):
        self._state = s
        for o in self._obs:  # 广播而非硬编码调用
            o.update(self._state)

class Logger:
    def update(self, s):
        print("state changed to", s)  # 观察者只关心自己逻辑
```

## 五、与其他技术对比
相比直接方法调用，观察者解耦但不保证执行顺序与同步性；相比消息队列，进程内观察者无持久化与跨进程能力，延迟更低。

## 六、常见误区
- 观察者中执行耗时或抛出异常的操作，阻塞主题线程。
- 忘记反注册导致内存泄漏（尤其在回调持有外部引用时）。

## 七、与开源书/权威来源对应
GoF 将观察者列为行为型模式；Vonng/ddia 在流处理章节讨论类似订阅-通知的扇出模型。

## 八、面试题
观察者模式如何避免循环通知？同步与异步通知各自的适用场景？与发布-订阅（消息总线）有何区别？

## 九、演进与趋势
演进为事件总线、响应式流（Rx、Project Reactor）与领域事件，配合 CQRS 实现最终一致性。

## 十、小结
观察者用订阅机制解耦生产者与消费者，需注意生命周期与异步化带来的复杂度。
