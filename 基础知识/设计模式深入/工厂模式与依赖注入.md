# 工厂模式与依赖注入

> 对应 Fowler 2002/2003 (Patterns of Enterprise Application Architecture)。

## 一、背景与挑战
对象创建逻辑散布在业务代码中，会导致依赖具体实现、难以替换与测试。需要把"创建什么"与"如何使用"分离。

## 二、核心原理
- 简单工厂：用一个方法按参数返回不同实现。
- 工厂方法：子类决定实例化哪个类。
- 抽象工厂：创建一组相关对象族。
- 依赖注入（DI）：由外部容器在运行时注入依赖，而非自行创建。

## 三、形式化与数学基础
设接口 I，实现集合 {C1..Ck}。工厂 f: Key -> I 隐藏构造细节；DI 将绑定关系从代码移到配置或容器：bind(I, C1)。

## 四、代码实现
```java
interface Storage { void save(String k, String v); }
class RedisStorage implements Storage {
    public void save(String k, String v) { /* ... */ }
}
// 工厂封装创建
class StorageFactory {
    static Storage create(String type) {
        if ("redis".equals(type)) return new RedisStorage();
        throw new IllegalArgumentException(type);
    }
}
```

## 五、与其他技术对比
工厂集中创建但仍需调用方获取；DI 进一步把获取也外包给容器，更利于单元测试（可注入 mock）。

## 六、常见误区
- 工厂里堆积大量 if/else，应结合注册表或反射。
- 把 DI 容器当全局服务定位器滥用，反而重新引入隐式依赖。

## 九、演进与趋势
编译期 DI（如 Dagger、Google Wire）用代码生成取代运行时反射，兼顾解耦与性能。

## 十、小结
工厂与 DI 都是解耦创建与使用的手段，DI 更适合大型应用的可测试架构。
