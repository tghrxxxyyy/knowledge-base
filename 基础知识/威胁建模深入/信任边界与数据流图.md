# 信任边界与数据流图

> 对应 Shostack《Threat Modeling: Designing for Security》中的 DFD 与信任边界方法论、Howard & LeBlanc《Writing Secure Code》中 STRIDE 的边界划分、OWASP Threat Modeling Cheat Sheet，以及 NIST SP 800-207 零信任架构。

## 一、背景与挑战
绝大多数真实攻击发生在信任关系变化的位置：数据从不可信区进入可信区、权限级别升高、跨进程或跨主机传递。若不先画出这些位置，威胁枚举只能凭直觉，容易漏掉「隐式边界」——同一进程内不同权限的线程、同一宿主上不同租户的容器。DFD 与信任边界的价值就是把「哪里需要严格校验」可视化。

## 二、核心原理
DFD 的四类元素：外部实体（人、外部系统，通常位于可信域外）、进程（执行转换的组件，信任变更最常发生处）、数据存储（数据库、文件、缓存、队列）、数据流（元素间移动的数据，标注协议与方向）。

信任边界是判定线，跨越它的数据流其信任级别发生变化。常见分层：公网→边界/DMZ→应用层→数据层；进程内：用户态→内核态；同一宿主：租户 A 容器→租户 B 容器。

跨边界流的处理原则与 STRIDE 一一对应：
- 完整性：签名、MAC、结构校验（防篡改）。
- 机密性：TLS、字段级加密、密钥隔离（防信息泄露）。
- 认证：双向证书、令牌校验（防伪装）。
- 授权：边界处策略检查与最小权限（防提权）。
- 可用性：限流、配额、体积上限（防拒绝服务）。
- 不可否认：跨边界时的可信审计记录（防抵赖）。

一个常被忽略的事实：**边界内元素并非天然可信**。若边界内某组件被攻陷，其内部流就不再可信，纵深防御要求同一逻辑边界内仍保留校验。

## 三、形式化与数学基础
设元素集合 $E$、数据流集合 $F \subseteq E \times E$，信任分区函数 $\zeta: E \to \{1,\dots,Z\}$。跨边界流集合：

$$F_B = \{\, (u, v) \in F \mid \zeta(u) \neq \zeta(v) \,\},\qquad E_{surface} = |F_B|$$

引入数据敏感度 $\sigma(f)$ 与协议强度 $\rho(f)$ 的加权暴露度：

$$R_{exposure} = \sum_{f \in F_B} \sigma(f) \cdot (1 - \rho(f))$$

缓解措施集合 $M$ 作用后的残余风险：

$$R_{resid} = \sum_{f \in F_B} \sigma(f) \cdot (1 - \rho(f)) \cdot \prod_{m \in M_f} (1 - e_m)$$

乘积形式说明两点：措施之间不是简单相加（边际收益递减），且 $e_m = 0$ 的措施对残余风险毫无贡献——「叠很多弱措施」不如「一个强措施」。

覆盖率度量与建模目标：

$$\mathrm{Cov} = \frac{|\{\, f \in F_B \mid M_f \neq \varnothing \,\}|}{|F_B|} \to 1$$

## 四、代码实现
```python
# 识别跨信任边界的流，并给出必需的缓解类别
ZONE = {"internet": 0, "dmz": 1, "app": 2, "data": 2, "kernel": 3}
FLOWS = [
    ("internet", "dmz", "https", "high"),
    ("dmz", "app", "grpc-mtls", "high"),
    ("app", "data", "postgres-tls", "high"),
    ("app", "kernel", "syscall", "medium"),
]
REQUIRED = {
    1: ["认证", "加密", "输入校验", "限流"],
    2: ["加密", "完整性校验", "审计"],
    3: ["最小权限", "系统调用过滤", "参数校验"],
}

def cross_boundary_flows(flows):
    out = []
    for src, dst, proto, sens in flows:
        dz = ZONE[dst] - ZONE[src]
        if dz != 0:
            out.append((src, dst, proto, sens, dz))
    return out

for src, dst, proto, sens, dz in cross_boundary_flows(FLOWS):
    print(f"边界流 {src} -> {dst} ({proto}, 敏感度={sens}) 需: {REQUIRED.get(abs(dz), ['复核'])}")

# 隐式边界：同进程内含多个权限域也需要标注
def find_implicit_boundaries(process_map):
    for proc, zones in process_map.items():
        if len(set(zones.values())) > 1:
            print(f"进程 {proc} 含多个权限域 {zones} -> 存在隐式信任边界")
```

## 六、常见误区
误区一：漏画隐式边界。进程内特权线程、加载的原生扩展、共享内存通信都是边界，未画出就会被系统性忽略。
误区二：默认内网可信。横向移动正是利用「内网可信」假设；零信任要求把身份而非网络位置作为信任依据。
误区三：把 DFD 画成部署图。DFD 关注数据流与信任，部署图关注机器与拓扑，用途不同但常被混用。
误区四：只在系统外部画一条边界。真实系统往往有多个嵌套边界（租户隔离、服务间、库与宿主），需分层表达。
误区五：认为跨边界检查一次就够。校验应贴近使用点，且已信任的输入进入更高权限域时仍需再校验。

## 七、与开源书·权威来源对应
- Shostack《Threat Modeling: Designing for Security》：DFD 元素定义、信任边界画法与「建模为持续活动」的方法论。
- Howard & LeBlanc《Writing Secure Code》：STRIDE 与 DFD 结合使用的原始论述，边界处威胁的分类方式。
- OWASP Threat Modeling Cheat Sheet：可操作的 DFD 绘制与边界标注清单，细节以官方最新文档为准。
- NIST SP 800-207《Zero Trust Architecture》：以身份与策略为中心取代网络边界信任，是信任边界理论的最新延伸。
- Saltzer & Schroeder 1975（CACM）：完全仲裁与最小权限，为边界处的强制性检查提供原则依据。

## 八、面试题
1. 什么是信任边界？为什么跨边界流最危险？
   要点：信任级别变化的分界线；跨边界处输入可能被完全控制，且校验缺失无法由内部逻辑弥补。
2. DFD 的四要素是什么？
   要点：外部实体、进程、数据存储、数据流；边界是附加的判定线而非元素。
3. 举例说明隐式信任边界。
   要点：进程内特权线程、容器运行时与容器内进程、JS 引擎与原生扩展、共享内存队列两端。
4. 零信任如何改变信任边界的画法？
   要点：网络位置不再赋予信任，边界转为身份与策略判定点，同一内网内也需逐次验证。
5. 缓解措施叠加为什么不是简单相加？
   要点：残余风险按 $(1-e_m)$ 连乘，边际收益递减，无效措施乘 1 不改变结果。

## 九、演进与趋势
自动化 DFD 从 IaC、服务网格配置与代码注解中提取，减少手工维护；服务网格把 mTLS 与授权策略下沉到基础设施，使许多跨边界流默认获得加密与认证。零信任持续模糊网络边界、强调身份边界，建模重点转向身份、令牌与策略的正确性。多租户隔离与供应链依赖也需作为独立边界建模。具体框架以官方最新文档为准。

## 十、小结
信任边界是威胁建模的前线，DFD 是把这条前线可视化的工具。方法上做三件事：完整枚举跨边界流集合 $F_B$（含隐式边界）、对每个 $f \in F_B$ 至少挂一项有效缓解、按残余风险公式排序优先级。边界内不等于安全，零信任进一步要求把信任依据从网络位置迁移到身份与策略。
