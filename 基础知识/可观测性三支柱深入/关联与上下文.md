# 关联与上下文

> 对应三支柱的关联：通过上下文（context propagation）打通 Metrics/Logs/Traces。

## 一、背景与挑战
单独看指标、日志、追踪各有盲区。把同一请求的三种信号通过统一上下文关联，才能从"告警"快速下钻到"根因 span"再到"相关日志"。

## 二、核心原理
- 统一上下文：trace_id 作为三者的关联键。
-  baggage/上下文传播：在进程内与跨网络传递业务属性（tenant、实验分组）。
- 语义约定：OTel 定义资源（resource）、作用域（scope）统一元数据。
- 下钻路径：Metrics 异常 → 对应 Trace 样本 → 该 trace_id 的 Logs。

## 三、形式化 / 数学基础
- 关联映射：$L \to T$ 由 $trace\_id$ 建立等值连接。
- 上下文 $C = (trace\_id, span\_id, baggage\{k:v\})$ 沿调用链传递。
- 下钻查询：$select\ logs\ where\ trace\_id = t^*$。
- 一致哈希可把同 trace 路由到同处理节点做聚合。

## 四、代码实现
```go
// 在日志中注入 trace_id，使三支柱可关联
ctx := context.WithValue(ctx, "trace_id", span.SpanContext().TraceID().String())
log.Info("handled", "trace_id", traceIDFrom(ctx), "status", 200)
// Metrics 打相同 trace 维度的 exemplar
hist.WithExemplar(exemplar{value: dt, labels: {"trace_id": tid}})
```

## 五、与其他技术对比
- 无关联：各自为政，排障靠人工拼接时间戳。
- 统一 ID：自动跳转，MTTR 大幅下降。
- 仅日志关联：缺指标趋势与链路因果。

## 六、常见误区
- 日志不打 trace_id 导致无法下钻。
- 跨线程/协程丢失上下文（需显式传递）。
- 在上下文中塞高基数 baggage 污染指标。

## 七、与开源书 / 权威来源对应

- Google SRE Book（关联排障）。

## 九、演进与趋势
Exemplars 把指标异常直接指向具体 trace；OTel 统一语义减少集成成本。

## 十、小结
关联与上下文用 trace_id 把指标、日志、追踪串成一条排障链，是可观测性价值的放大器的核心。
