# 告警

> 对应告警（Alerting）设计：有效、可行动、低噪声。

## 一、背景与挑战
告警过多导致"告警疲劳"，过少则漏故障。目标是让每条告警都可行动、指向明确 owner。

## 二、核心原理
- 基于 SLO 的告警：对错误预算燃烧率（burn rate）告警，而非单纯阈值。
- 多窗口多燃烧率：短窗口捕捉突发，长窗口捕捉持续。
- 抑制/分组/路由：避免重复、聚合相关告警。
- 静默与维护窗口：计划内变更不误报。

## 三、形式化 / 数学基础
- 错误预算 $B = 1 - SLO$（如 SLO 99.9% → 预算 0.1%）。
- 燃烧率 $R = \frac{\text{实际错误率}}{1-SLO}$；快速消耗预算时 $R$ 高。
- 多窗口：1h 窗口 $R>14.4$ 且 5m 窗口同样高 → 触发。
- 告警频率惩罚（抑制）：相同指纹在 $t$ 内仅发一次。

## 四、代码实现
```yaml
# Prometheus 燃烧率告警示例
alert: HighErrorRate
expr: |
  (sum(rate(http_errors[5m])) / sum(rate(http_requests[5m])))
  / (1 - 0.999) > 14.4
for: 5m
labels: {severity: page}
annotations: {summary: "误差预算快速燃烧"}
```

## 五、与其他技术对比
- 阈值告警：简单但易误报/漏报；SLO 燃烧率：贴合用户体验。
- 日志告警：事件级；指标告警：聚合级。
- 静态阈值 vs 动态基线：后者抗周期波动但复杂。

## 六、常见误区
- 用平均阈值告警造成疲劳。
- 告警无 runbook、无 owner。
- 同时用多窗口却不抑制导致重复。

## 十、小结
