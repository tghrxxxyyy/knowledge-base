# Raft 日志复制

> 对应 Ongaro & Ousterhout Raft 论文第 5.3 节。

## 一、背景与挑战
Leader 被选后，需把客户端命令以日志形式复制到多数派并“提交(commit)”，再应用到状态机。复制要保证所有节点日志在索引/任期上完全一致。

## 二、核心原理
- 客户端请求 -> Leader 追加日志条目 (term, index, cmd)。
- Leader 发 AppendEntries(含 prevLogIndex, prevLogTerm, entries[], leaderCommit)。
- Follower 校验 prevLog 匹配(任期与索引一致)才追加；不匹配则拒绝，Leader 回退 nextIndex 重试。
- 提交：Leader 确认某条目已复制到多数派，且当前 term 的条目被提交(带动提交更早条目)。

## 三、形式化 / 数学基础
日志匹配性质(Log Matching)：若两日志在 index i 的条目任期相同，则它们之前所有条目(1..i)完全相同。
由归纳：AppendEntries 的 prevLog 校验保证一致性；冲突时删除 Follower 冲突后缀。
提交约束：仅当 当前 term 的条目 被多数派复制后才可提交(避免 Figure 8 中旧 term 被错误提交)。

## 四、代码实现
```go
func (rf *Raft) AppendEntries(args *Args) bool {
    if args.PrevLogTerm != rf.log[args.PrevLogIndex].Term {
        return false // 不匹配，Leader 回退
    }
    // 冲突条目截断并追加新条目
    rf.log = append(rf.log[:args.PrevLogIndex+1], args.Entries...)
    if args.LeaderCommit > rf.commitIndex {
        rf.commitIndex = min(args.LeaderCommit, len(rf.log)-1)
    }
    return true
}
```

## 五、与其他技术对比
- Multi-Paxos 也复制日志，但 Raft 用强 Leader 与 prevLog 校验更直观。
- Zab 用事务 id 与队列保证有序广播。

## 六、常见误区
- 误区：复制到多数派即可提交任意条目。必须等“当前 term 条目”提交连带提交旧条目。
- 误区：Follower 可直接提交。只有 Leader 推进 commitIndex。

## 九、演进与趋势
Pipeline、批量 AppendEntries 与 ReadIndex/Lease Read 优化复制与读性能。

## 十、小结
Raft 日志复制以强 Leader、prevLog 校验与“仅当前 term 提交”约束，实现了既一致又可理解的复制协议。
