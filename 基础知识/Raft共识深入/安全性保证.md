# Raft 安全性保证

> 对应 Ongaro & Ousterhout Raft 论文第 5.4 节 Safety。

## 一、背景与挑战
选举与复制解决活性，但必须保证：任何已提交的条目永远不会丢失或被覆盖，且所有节点状态机按相同顺序应用相同命令。

## 二、核心原理
两条核心不变量：
- 选举限制(Election Restriction)：Candidate 的日志必须至少与多数派节点一样新(通过 RequestVote 的日志比较)才能当选 —— 保证 Leader 含所有已提交条目。
- 提交规则(Committing entry from current term)：只有当前 term 的条目复制到多数派后才可提交，从而连带安全提交之前 term 的条目。
由此推导出：任何被选为 Leader 的节点，其日志包含全部已提交条目(否则它无法获得多数派选票，因那些节点有更新的日志)。

## 三、形式化 / 数学基础
定理：若某条目在 term T 被提交，则所有 term > T 的 Leader 的日志中都包含该条目。
证明要点：提交需多数派 Q_T 含该条目；新 Leader 需获得多数派 Q_N 选票，Q_T ∩ Q_N ≠ ∅，故至少一个投票者含该条目且新 Leader 日志 >= 它 -> 包含该条目。
状态机安全：所有节点按相同 index 顺序应用相同命令。

## 四、代码实现
```go
// 选举时的日志新旧比较，保证安全性
func (rf *Raft) logIsAtLeastAsNew(lastTerm, lastIndex int) bool {
    myT, myI := rf.lastLogTerm(), rf.lastLogIndex()
    if lastTerm != myT {
        return lastTerm > myT
    }
    return lastIndex >= myI
}
```

## 五、与其他技术对比
- Paxos 用 chosen 值与多数派相交保证安全；Raft 用“Leader 必含已提交日志”更直观。
- 与 Zab 的“前驱提案”约束思想一致。

## 六、常见误区
- 误区：仅靠多数派复制即可安全提交。缺“当前 term”约束会导致 Figure 8 错误。
- 误区：状态机可乱序应用。必须按 index 顺序。

## 九、演进与趋势

## 十、小结
Raft 的安全性建立在选举限制与当前 term 提交规则之上，用数学归纳与多数派相交严格保证已提交日志不丢失。
