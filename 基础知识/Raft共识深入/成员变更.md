# Raft 成员变更

> 对应 Ongaro & Ousterhout Raft 论文第 6 节，及 Conf Change 实践。

## 一、背景与挑战
集群需要增删节点(扩容、故障替换)。若直接切换配置，可能出现新旧配置各自形成多数派导致“双 Leader”脑裂。

## 二、核心原理
两阶段 Joint Consensus(联合一致)：
1. Leader 提交 C_old,new(配置同时包含旧成员与新成员)。
2. 该阶段决策需 旧多数派 与 新多数派 同时同意(联合多数派)。
3. 待 C_old,new 提交后，再提交 C_new，完成切换。
简化方案：单步“C_new 直接替换”要求成员数不变或采用 leader 单飞切换，但标准安全做法是 Joint Consensus。
每条配置作为普通日志条目复制，应用后即时生效。

## 三、形式化 / 数学基础
联合多数派 Q = Q_old ∩ Q_new，其中 |Q_old| > |C_old|/2 且 |Q_new| > |C_new|/2。
任意两个配置阶段的合法决策集合必相交(因各自需新旧两多数派)，故任意时刻至多一个 Leader，避免脑裂。

## 四、代码实现
```go
// 配置作为日志条目
type Entry struct { Term, Index int; Cmd interface{} }
func (rf *Raft) applyConfig(c Conf) {
    rf.config = c // 应用后立即用新配置判断多数派
}
// 提交 C_old,new 后再提交 C_new
```

## 五、与其他技术对比
- Paxos 也用 Joint Consensus 做成员变更(同一思想)。
- etcd 早期用单步变更，后支持 Joint Consensus。

## 六、常见误区
- 误区：直接替换配置文件安全。会造成新旧两群各选 Leader。
- 误区：成员变更可绕过日志。必须作为共识条目提交。

## 九、演进与趋势
单步成员变更(Single-Server-Change)在只增删单一节点时可省略 C_old,new 中间态，简化实现。

## 十、小结
成员变更通过 Joint Consensus 的联合多数派保证切换期间仍至多一个 Leader，是 Raft 可运维性的关键。
