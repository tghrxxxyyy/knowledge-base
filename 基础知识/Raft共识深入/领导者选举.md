# Raft 领导者选举

> 对应 Ongaro & Ousterhout《In Search of an Understandable Consensus Algorithm》(USENIX 2014)。

## 一、背景与挑战
Raft 以“可理解性”为目标，把共识拆为领导选举、日志复制、安全性三部分。选举要解决：在节点崩溃后选出唯一 Leader，且 Leader 拥有最新日志。

## 二、核心原理
- 任期(term)：单调递增的逻辑时钟，每次选举 +1。
- 状态：Follower / Candidate / Leader。
- 机制：Follower 在 election timeout(随机 150–300ms)内未收心跳则转为 Candidate，投自己一票，发 RequestVote(term, lastLogIndex, lastLogTerm)。
- 获多数派选票者成为 Leader，开始发心跳维持权威。
- 选票约束：只投给日志至少与自己一样新的候选者(避免选出落后 Leader)。

## 三、形式化 / 数学基础
选举安全性：每个 term 至多一个 Leader(因需多数派选票，而任意两多数派相交)。
日志比较：候选者 (lastTerm_c, lastIndex_c) 比自己 (lastTerm_f, lastIndex_f) 新，当且仅当 lastTerm_c > lastTerm_f 或 (相等且 lastIndex_c >= lastIndex_f)。
随机超时保证：两个 Follower 同时超时概率随重试指数下降。

## 四、代码实现
```go
func (rf *Raft) startElection() {
    rf.currentTerm++
    rf.state = Candidate
    votes := 1
    for _, p := range peers {
        if p.requestVote(rf.currentTerm, rf.lastLogTerm(), rf.lastLogIndex()) {
            votes++
        }
    }
    if votes > len(peers)/2 {
        rf.becomeLeader()
    }
}
```

## 五、与其他技术对比
- Paxos：无显式选举，靠提案号抢占；Raft 选举更直观。
- Zab/ZooKeeper：类似 Leader 选举但面向事务日志。

## 六、常见误区
- 误区：超时越短越好。过短会增加无意义选举。
- 误区：选票只看 term。还需日志新旧约束保证安全性。

## 八、面试题

2. RequestVote 为何要带 lastLogIndex/Term？
3. 同一 term 如何保证只有一个 Leader？

## 九、演进与趋势
Raft 已成为 etcd、Consul、TiKV 等的事实标准共识算法；扩展出 Multi-Raft 用于分片。

## 十、小结
Raft 用任期 + 随机超时 + 日志新旧约束，把选主变得可理解且安全，是工业共识首选。
