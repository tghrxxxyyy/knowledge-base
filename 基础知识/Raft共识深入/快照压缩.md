# Raft 快照压缩

> 对应 Ongaro & Ousterhout Raft 论文第 7 节 Log Compaction。

## 一、背景与挑战
日志无限增长会耗尽存储并拖慢重启重放。需定期把已提交日志压缩为快照(snapshot)，并截断已纳入快照的日志前缀。

## 二、核心原理
- 每个节点独立对自己状态机做快照，覆盖至某个 appliedIndex。
- 快照后删除 index <= snapshotIndex 的日志条目，仅保留 snapshot 元数据(lastIncludedIndex, lastIncludedTerm)。
- InstallSnapshot RPC：当 Follower 日志落后太多(所需 prevLog 已被 Leader 截断)，Leader 直接发快照，Follower 用其覆盖本地状态。
- 快照点之前的配置/任期信息由 snapshot 携带，保证正确性。

## 三、形式化 / 数学基础
设快照覆盖至 s=(index_s, term_s)。Follower 应用快照后，其日志从 index_s+1 起与 Leader 连续；prevLog 校验改用 (index_s, term_s) 作为基线。
不变量：snapshotIndex 必须 <= commitIndex(只压缩已提交部分)，否则可能丢弃未提交但将来需的条目。

## 四、代码实现
```go
func (rf *Raft) takeSnapshot(index int, snapshot []byte) {
    if index <= rf.snapshotIndex { return }
    rf.log = rf.log[index-rf.snapshotIndex:]  // 截断
    rf.snapshotIndex = index
    rf.snapshot = snapshot
}
// InstallSnapshot: Follower 收到后用快照恢复状态机
```

## 五、与其他技术对比
- Paxos 也有快照/日志截断，但 Raft 的 InstallSnapshot RPC 标准化更清晰。
- ZooKeeper 用事务日志 + 快照文件。

## 六、常见误区
- 误区：可压缩任意位置日志。必须 <= commitIndex。
- 误区：快照要全网一致。各节点独立按自己速度做。

## 九、演进与趋势
分片快照、增量快照与写时复制(COW)降低大状态机快照开销。

## 十、小结
Raft 用节点本地快照 + InstallSnapshot 控制日志体积，兼顾存储效率与故障恢复正确性。
