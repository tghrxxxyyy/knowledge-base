# 滑动窗口与接收窗口通告

> 对应 RFC 793 §3.3/§3.4 (TCP)、RFC 7323 (窗口缩放)、Kurose & Ross《Computer Networking》第3章与 Stevens《TCP/IP Illustrated》Vol.1 第20–22章。

## 一、背景与挑战

可靠传输若采用停等（stop-and-wait）协议，发送方每发一个段就必须等待其确认，链路利用率被限制在 $\frac{L/R}{RTT}$ 量级。在带宽时延积较大的链路上，这是灾难性的低效。滑动窗口（sliding window）用「批量在途、逐个确认、连续滑动」把利用率拉回到接近 100%。

但滑动窗口天然是「发送方视角」的机制：它能填满网络，却不能感知接收方的处理能力。如果接收方应用读得慢、缓冲小，发送方的高速灌注会直接导致接收缓冲溢出与丢包。TCP 的做法是让接收方通过每个 ACK 中的窗口字段主动声明自己还能接收多少字节，即**流量控制（flow control）**。

于是发送方的实际发送窗口由两部分共同决定：接收方能力 $rwnd$ 与网络能力 $cwnd$。本文聚焦前者：窗口如何计算、如何通告、如何随确认滑动，以及通告的边界条件。

## 二、核心原理

### 接收窗口的计算

接收方维护两个游标：`LastByteRead`（应用已读走的最后字节）与 `LastByteRcvd`（已到达并排入缓冲的最后字节）。接收缓冲总容量为 $RcvBuffer$，则未被应用消费的数据量是 $LastByteRcvd - LastByteRead$，剩余空间即：

$$ rwnd = RcvBuffer - \left( LastByteRcvd - LastByteRead \right) $$

不变式是 $LastByteRcvd - LastByteRead \le RcvBuffer$，超出即表示缓冲溢出。每个 ACK 的 16 位窗口字段就是 $rwnd$ 的编码值（在窗口缩放协商后是移位前的值）。

### 发送窗口的结构

发送方为连接维护四个关键序号（RFC 793 的经典描述）：

$$ SND.UNA \le SND.NXT \le SND.UNA + W $$

其中 $SND.UNA$ 是最早未确认字节，$SND.NXT$ 是下一个要发送的字节，$W = \min(cwnd, rwnd)$ 是发送窗口。窗口内可细分为四段：已发送已确认（在窗口左侧）、已发送未确认、可发送未发送、不可发送（超出 $SND.UNA + W$）。收到 ACK 使 $SND.UNA$ 右移，窗口右侧随之推进，这就是「滑动」的含义。

接收方一侧同样维护窗口：`RCV.NXT`（期望的下一个序号）与可用空间构成接收窗口，任何超出窗口的数据段都会被丢弃（但仍回 ACK，以提示发送方当前 $SND.NXT$）。

### 窗口更新的三个陷阱

**陷阱一：窗口收缩（shrinking window）。** RFC 793 允许接收方缩小窗口但不鼓励，RFC 1122 明确禁止**向右收缩**已通告窗口的右边界（$SND.UNA + W$ 不得减小），否则发送方可能已按旧窗口发送，接收方又宣布不接受，造成不可恢复的混乱。合法做法是缩小左边界（即把已通告的窗口内容视为必须接收）。

**陷阱二：窗口更新丢失。** 窗口更新完全依赖 ACK 的不可靠传递，因此发送方必须有 persist 定时器兜底（见零窗口探测）。同时窗口字段永远伴随确认号，纯窗口更新段（不确认新数据）在实现中容易产生重复段，需要靠序号比较避免。

**陷阱三：SWS。** 逐字节通告窗口会诱导 tinygram，接收方须按 Clark 阈值抑制通告。

## 三、形式化与数学基础

发送窗口上界：

$$ W = \min(cwnd,\ rwnd) $$

发送方允许发送的新数据长度：

$$ N_{new} = \min\left( W - \left( SND.NXT - SND.UNA \right),\ L_{queued} \right) $$

即窗口内剩余空间与待发队列长度的较小者。当 $N_{new} = 0$ 且队列非空时，说明被流控或拥塞控制阻塞。

吞吐上界（受窗口限制时）：

$$ T \le \frac{W}{RTT} $$

要让 $T$ 达到带宽 $B$，必须 $W \ge B \cdot RTT = BDP$。这就把窗口大小与带宽时延积直接绑定：16 位窗口最大 65535 字节，在 $B=1\text{Gbps}$、$RTT=100\text{ms}$ 时 BDP 约 12.5MB，窗口只有 BDP 的 0.5%，吞吐被限制在约 5Mbps。这解释了窗口缩放选项的必要性。

窗口滑动的正确性不变式（接收方）：

$$ RCV.NXT = LastByteRcvd + 1 $$

$$ RCV.NXT + rwnd = LastByteRead + RcvBuffer $$

后者即「窗口右边界 = 已读位置 + 缓冲容量」，是接收方计算窗口的等价形式，实现上更常用。

## 四、代码实现

Linux 计算通告窗口的关键函数是 `tcp_select_window()`，其调用链还会叠加 SWS 与缩放处理：

```c
/* 简化示意：net/ipv4/tcp_output.c */
static u32 tcp_select_window(struct sock *sk)
{
    struct tcp_sock *tp = tcp_sk(sk);
    u32 old_win = tp->rcv_wnd;
    u32 cur_win = tcp_receive_window(tp);   /* 当前仍有效的接收窗口 */
    u32 new_win = __tcp_select_window(sk);  /* 按剩余空间计算 */

    if (new_win < cur_win) {
        /* 不允许向右收缩：最多缩到 0 或维持旧值 */
        new_win = 0;
        if (old_win < cur_win)
            new_win = old_win;
        tp->rcv_wnd = new_win;
    }
    return new_win;
}
```

接收路径上对序号做窗口检查，判断段是否落在接收窗口内：

```c
/* 简化示意：接收窗口判定的语义 */
static bool acceptable(struct tcp_sock *tp, u32 seq, unsigned int len)
{
    u32 rcv_wup = tp->rcv_wup;                 /* 窗口右边界基准 */
    u32 rcv_nxt = tp->rcv_nxt;
    u32 rcv_wnd = tp->rcv_wnd;

    if (len == 0)
        return seq == rcv_nxt ||
               (between(seq, rcv_nxt, rcv_nxt + rcv_wnd) && rcv_wnd);
    return ((seq == rcv_nxt) && (len <= rcv_wnd)) ||
           (between(seq, rcv_nxt, rcv_nxt + rcv_wnd) &&
            ((s32)(seq + len - rcv_nxt) <= (s32)rcv_wnd));
}
```

发送侧受窗口约束的核心判定（`net/ipv4/tcp_output.c`）：

```c
/* 简化示意：窗口是否允许发送更多数据 */
static inline bool tcp_snd_wnd_test(const struct tcp_sock *tp,
                                    const struct sk_buff *skb,
                                    unsigned int cur_mss)
{
    u32 end_seq = TCP_SKB_CB(skb)->end_seq;

    if (skb->len > cur_mss)
        end_seq = TCP_SKB_CB(skb)->seq + cur_mss;
    return !after(end_seq, tcp_wnd_end(tp));   /* 不越过对端窗口右边界 */
}
```

应用层可以直接观察与干预窗口行为：

```bash
# 观察收发队列、窗口与缩放因子
ss -tim 'sport = :443'
# Recv-Q 持续接近 SO_RCVBUF 说明接收窗口长期为 0
sysctl net.ipv4.tcp_rmem      # 自动调优的 min/default/max
sysctl net.ipv4.tcp_moderate_rcvbuf
```

```c
/* 显式扩大接收缓冲：内核会把窗口调到不低于 BDP 的水平 */
int bufsize = 4 * 1024 * 1024;
setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &bufsize, sizeof(bufsize));
```

## 五、与其他技术对比

| 维度 | TCP rwnd 流控 | TCP cwnd 拥塞控制 | HTTP/2 流控 | QUIC 流控 | UDP |
| --- | --- | --- | --- | --- | --- |
| 保护对象 | 接收方缓冲 | 网络瓶颈 | 应用/连接缓冲 | 接收端流与连接缓冲 | 无 |
| 粒度 | 连接级字节 | 连接级字节 | 连接级 + 流级 | 连接级 + 流级 | 无 |
| 通告方式 | 16 位窗口字段（可缩放） | 发送方本地计算 | WINDOW_UPDATE 帧 | MAX_DATA / MAX_STREAM_DATA | 无 |
| 反馈语义 | 显式、被动 | 隐式、主动探测 | 显式信用 | 显式信用 | 无 |
| 触发条件 | 接收方读得慢 | 网络丢包/时延 | 应用读得慢 | 应用读得慢 | 无 |
| 失败后果 | 窗口为 0、persist 探测 | 丢包、重传、降速 | 流挂起 | 流阻塞 | 应用层 OOM |

关键区分：$rwnd$ 是被动反映对方能力，$cwnd$ 是主动探测网络容量。二者取小，任一成为瓶颈都会限制吞吐——这正是下一节「发送窗口与拥塞窗口的协同」要展开的内容。

## 六、常见误区

- **把 $rwnd$ 与 $cwnd$ 混为一谈。** 前者保护接收方，后者保护网络；`ss -ti` 中 `rwnd_limited` 与 `cwnd_limited` 标记有明确区分。
- **认为 $rwnd = 0$ 连接就死了。** 这是正常流控状态，靠 persist 探测恢复。
- **认为调大 `net.core.rmem_max` 就够了。** 还需应用 `SO_RCVBUF` 未被 `tcp_rmem` 上限压制、窗口缩放已协商；三者任一不足，窗口都上不去。
- **忽略接收方应用不读才是主因。** 窗口长期为 0 的根因几乎总是消费者处理慢，扩大缓冲只是把问题（内存占用）推后。
- **认为窗口可以随时缩小。** RFC 1122 禁止向右收缩已通告的窗口边界，实现上只能缩左边界。

## 八、面试题

1. **接收窗口为 0 时发送方怎么办？**
   要点：停止发送应用数据，启动 persist 定时器周期发送 1 字节探测段，迫使对端回带窗口的 ACK，直到窗口重新打开。

2. **为什么发送窗口要取 $\min(cwnd, rwnd)$？**
   要点：同时满足「不压垮网络」和「不溢出接收缓冲」两个约束；任一条件不满足都会出问题，因此只能取较严者。

3. **窗口缩小有什么风险？**
   要点：若接收方把右边界向左移，发送方可能已按旧窗口发出数据，接收方却宣布不接受，造成不可恢复的状态分歧。RFC 1122 因此禁止向右收缩。

4. **接收缓冲开多大合适？**
   要点：至少覆盖 BDP（$B \times RTT$），并留出应用处理抖动的余量。过小会限制吞吐，过大会引发缓冲膨胀（bufferbloat）与内存开销。可用 `tcp_rmem` 自动调优配合 `tcp_moderate_rcvbuf`。

5. **如何判断吞吐受 $rwnd$ 还是 $cwnd$ 限制？**
   要点：`ss -ti` 查看 `rtt`、`cwnd`、`bytes_acked` 与 `rwnd_limited`/`cwnd_limited` 计数；若 `Recv-Q` 长期满、对端通告窗口接近 0，则是 $rwnd$ 受限。

## 九、演进与趋势

窗口机制本身几十年未变，但工程实现持续演进。窗口缩放（RFC 7323）把上限提到约 1GB；自动缓冲调优（`tcp_moderate_rcvbuf`）让接收方按实测 RTT 与带宽动态调整 $RcvBuffer$，避免了人工调参；`tcp_rmem` 三元组区分最小值、默认值与上限，配合 `SO_RCVBUF` 的语义变更（设置值会被内核加倍并受上限钳制）。

在协议层，HTTP/2 与 QUIC 都引入了**流级 + 连接级**的双层流控：单个流的阻塞不会独占整个连接的窗口，避免了大对象传输饿死小请求；信用制（credit-based）的显式授予比 TCP 的隐式窗口字段更易推理，也让「窗口更新丢失」问题在协议设计上消失。

在数据中心场景中，无损网络与拥塞控制（DCQCN、HPCC）把流控与拥塞控制统一到链路层的 PFC/ECN 上，但端到端 $rwnd$ 仍是最后一道保护应用缓冲的防线，不可省略。

## 十、小结

滑动窗口用「批量在途 + 连续确认」解决了停等协议的利用率问题，接收窗口通告则在此基础上叠加了端到端的流量控制。$rwnd$ 的计算依赖 $RcvBuffer$、$LastByteRcvd$、$LastByteRead$ 三个量，其通告受 SWS 阈值与「禁止向右收缩」两条规则约束，其丢失由 persist 探测兜底。

发送窗口是 $W = \min(cwnd, rwnd)$，理解这一取小关系、以及 $W \ge BDP$ 对吞吐的必要性，是排查网络性能问题的基础。
