# 零窗口探测与糊涂窗口综合征

> 对应 RFC 793 (TCP) 与 Clark 1982 论文。

## 一、背景与挑战
当接收方缓冲耗尽通告 rwnd=0，发送方须暂停。但若后续窗口重新打开的 ACK 丢失，双方可能陷入互相等待的死锁。此外若接收方每次仅腾出极小窗口（如几字节），发送方不断发送 tinygram，会造成极高协议头开销，即糊涂窗口综合征 SWS。

## 二、核心原理
零窗口探测由发送方零窗口探测定时器触发，周期性发送 1 字节报文段，迫使接收方回送带当前 rwnd 的 ACK，从而打破丢失导致的死锁。SWS 的解决分两端：接收方按 Clark 算法仅当可通告一个较大窗口（如缓冲一半或 MSS）时才更新 rwnd；发送方按 Nagle 算法累积数据到 MSS 或收到 ACK 再发。

## 三、形式化与数学基础
接收方通告条件（Clark）：
$$ rwnd_{adv} \ge \max(MSS, \frac{RcvBuffer}{2}) $$
发送方 Nagle 允许发送的条件：
$$ \text{可发} \iff (seg \ge MSS) \lor (\text{无在途未确认小段}) $$
只有二者同时满足才避免 SWS。

## 四、代码实现
Linux 零窗口探测在 `tcp_probe_timer`：
```c
if (icsk->icsk_probes_out >= ...)
    tcp_send_probe0(sk);  // 发送 1 字节探测
```
Nagle 判定在 `tcp_nagle_check`：
```c
return skb->len < mss && !tcp_skb_is_last(sk, skb);
```

## 五、与其他技术对比
SWS 是 TCP 特有于字节流小包的问题；UDP 应用自行成帧不受此限。QUIC 以流控加帧Batch 减少小包，且禁止极小窗口通告。

## 六、常见误区
误区一是禁用 Nagle（TCP_NODELAY）总能提升性能，实则对小消息高频交互会加剧小包风暴。误区二是认为零窗口探测会无限占用带宽，其探测段极小且频率受限。

## 七、与开源书/权威来源对应
RFC 793 提及窗口更新；Clark 1982「Window and Acknowledgement Strategy」提出避免 SWS；Nagle 1984 RFC 896 给出 Nagle 算法。

## 八、面试题
问：零窗口探测解决什么问题？答：解决窗口重新打开的通告 ACK 丢失导致的发送方死锁，通过定时发 1 字节探测逼迫对端 ACK 当前窗口。

## 九、演进与趋势
现代高速网络下，Nagle 与 delayed ACK 的交互仍会在某些请求-响应模式引入数十毫秒延迟，常需按场景权衡 `TCP_NODELAY`。

## 十、小结
零窗口探测打破 rwnd=0 下的通告丢失死锁，Clark 与 Nagle 协同抑制 SWS。理解二者是诊断小包与延迟异常的基础。
