# 零窗口探测与糊涂窗口综合征

> 对应 RFC 793 §3.7 (TCP)、RFC 1122 §4.2.2.17/§4.2.3、Clark 1982 (RFC 813) 与 Stevens《TCP/IP Illustrated》Vol.1 第22章。

## 一、背景与挑战

TCP 的流量控制以接收窗口 $rwnd$ 为唯一凭据。当接收方应用来不及读取、接收缓冲被填满时，接收方在 ACK 中通告 $rwnd = 0$，发送方必须停止发送应用数据。问题在于：**窗口从 0 变回非 0 的唯一通知手段是一个新的 ACK，而 ACK 本身不可靠（TCP 只对数据做重传保证）。**

如果这个「窗口已打开」的 ACK 在链路上丢失，发送方仍认为 $rwnd=0$ 而持续等待，接收方却认为已通知并等待数据——双方陷入永久死锁，连接既不报错也不前进。这就是零窗口探测（zero window probe）要解决的问题。

与之伴随的是另一个病态：若接收方每次只腾出极小空间（例如 1 字节）就立即通告，发送方会立刻发出一个 1 字节数据段，如此往复形成 tinygram 风暴。二者在 RFC 中被合称窗口管理的两端约束。

## 二、核心原理

### 零窗口探测与 persist（坚持）定时器

发送方一旦收到 $rwnd = 0$，除了停止发送数据外，还必须启动 persist 定时器。定时器到期后发送一个**零窗口探测段**：只带 1 个字节的新数据（或 1 字节旧数据的重传），序号取 $SND.UNA + 0$，由此迫使接收方无论如何都要回一个 ACK，并在 ACK 中携带当前 $rwnd$。

接收方对该探测段的处理有两条明确义务（RFC 1122 §4.2.2.17）：必须回复 ACK，并且必须携带当前窗口。接收方不得因为「该段超出窗口」就静默丢弃——这正是打破死锁的关键。

探测必须退避（backoff）：若对端持续零窗口，探测间隔按指数增长并在上限处封顶，避免为一条空闲连接持续消耗带宽。Linux 中探测次数超过 `tcp_retries2`（经退避计算）后放弃并报错，防止连接永久占用资源。

### SWS 的双侧约束

**发送方（Nagle）**：只要存在未被确认的小段在途，新的小数据先缓存，直到收到 ACK 或累积到 MSS 再发。

**接收方（Clark）**：只有当可通告窗口增长到至少 $\min(MSS, RcvBuffer/2)$ 时才更新通告；否则宁可继续通告 0，让发送方依赖 persist 探测。

二者是互补关系而非替代关系。接收方遵守 Clark 会「更频繁地通告 0」，而这恰恰放大了对 persist 定时器的依赖；如果 Nagle 缺失，一旦窗口打开，发送方会立刻用小段填充，接收方又回到小窗口状态，形成低频振荡。因此两个机制必须同时正确实现。

### 探测段与 keepalive 的区别

二者都发送「无实际语义的字节」，但目的完全不同：persist 探测是为了获取窗口信息、解决流控死锁，属数据面机制，只在不发数据时启用；keepalive 是为了探测对端存活、清理半开连接，属连接管理，由 `SO_KEEPALIVE` 显式开启。混用二者会导致空闲长连接被误杀或漏杀。

## 三、形式化与数学基础

设接收缓冲容量 $B$，已接收未读取字节数 $U = LastByteRcvd - LastByteRead$，则可用空间为：

$$ space = B - U $$

接收方通告窗口由 Clark 阈值决定：

$$ rwnd_{adv} = \begin{cases} space, & space \ge \max\!\left(MSS,\ \tfrac{B}{2}\right) \\ 0, & \text{otherwise} \end{cases} $$

发送方允许发送的条件（Nagle + 窗口）：

$$ \text{send} \iff \left( rwnd > 0 \right) \land \left( L \ge MSS \ \lor\ \text{无在途未确认小段} \right) $$

当 $rwnd = 0$ 时上式恒假，发送方唯一的动作是 persist 探测。设初始探测间隔 $t_0$、退避因子 $\alpha = 2$、上限 $t_{max}$，第 $k$ 次探测的时刻为：

$$ t_k = t_0 + \sum_{i=0}^{k-1} \min\!\left( t_0 \cdot 2^{i},\ t_{max} \right) $$

在 $n$ 次探测均无响应（对端既不回 ACK 也不消失）后，发送方判定连接失效并向上层返回错误：

$$ \text{fail} \iff k > K_{max} $$

死锁发生的充分条件可以形式化为：设窗口更新 ACK 集合为 $W$，若 $W \neq \varnothing$ 且所有 $w \in W$ 均丢失，且发送方不发送探测，则双方状态永久停滞：

$$ \left( \forall w \in W:\ \text{lost}(w) \right) \land \left( \text{no probe} \right) \implies \text{deadlock} $$

探测机制的作用就是使第二个合取项恒为假。

## 四、代码实现

Linux 的 persist 定时器处理在 `net/ipv4/tcp_timer.c` 的 `tcp_probe_timer()`，下面是结构示意：

```c
/* 简化示意：真实实现包含孤儿连接与 SYN 队列的特殊分支 */
static void tcp_probe_timer(struct sock *sk)
{
    struct inet_connection_sock *icsk = inet_csk(sk);
    struct tcp_sock *tp = tcp_sk(sk);
    int max_probes = read_tcp_retries2(sock_net(sk));

    /* 已有在途数据说明窗口已打开，探测计数清零并退出 */
    if (tp->packets_out || !tcp_send_head(sk)) {
        icsk->icsk_probes_out = 0;
        return;
    }

    if (icsk->icsk_probes_out >= max_probes) {
        tcp_write_err(sk);           /* 探测次数耗尽：向上层报错 */
        return;
    }
    tcp_send_probe0(sk);             /* 发送 1 字节探测段 */
    inet_csk_reset_xmit_timer(sk, ICSK_TIME_PROBE0,
                              min(icsk->icsk_rto, TCP_RESOURCE_PROBE_INTERVAL),
                              TCP_RTO_MAX);
}
```

发送探测段的动作本身只是把 1 字节从发送队列「重发」，同时在标志位中标记为窗口探测：

```c
/* 简化示意 */
static void tcp_send_probe0(struct sock *sk)
{
    struct tcp_sock *tp = tcp_sk(sk);
    int err = tcp_write_wakeup(sk, LINUX_MIB_TCPWINPROBE);

    if (err <= 0) {                  /* 无数据可发：改发纯 ACK 探测 */
        tp->snd_nxt = tp->snd_una;
        ...
    }
    inet_csk(sk)->icsk_probes_out++;
}
```

接收方侧对小窗口的通告抑制在 `tcp_select_window()` 中，核心逻辑是：计算真实可用空间 `space`，若小于 SWS 阈值则通告 0：

```c
/* 简化示意：SWS 避免 */
free_space = tcp_space(sk);                  /* 接收缓冲剩余 */
if (free_space < (sk->sk_rcvbuf >> 1) &&    /* 未达半个缓冲 */
    free_space < tp->mss_cache)             /* 且小于一个 MSS */
    return 0;                               /* 通告零窗口，靠 persist 恢复 */
return free_space & ~(1 << tp->rx_opt.rcv_wscale - 1); /* 按缩放粒度取整 */
```

## 五、与其他技术对比

| 维度 | TCP persist 探测 | TCP keepalive | 关闭 Nagle | QUIC 流控 | 应用层心跳 |
| --- | --- | --- | --- | --- | --- |
| 目的 | 解决窗口死锁 | 探测对端存活 | 降低延迟 | 防止接收方过载 | 探测业务可用性 |
| 触发条件 | $rwnd = 0$ 且有数据待发 | 空闲超时 | 应用显式开启 | 应用不读/读得慢 | 应用自定义 |
| 报文形态 | 1 字节数据或纯 ACK | 空 ACK 或无载荷段 | 不产生额外报文 | MAX_DATA 帧 | 业务报文 |
| 退避 | 有，指数增长封顶 | 有，默认 2 小时起 | 无 | 无 | 视实现 |
| 关闭后果 | 可能永久死锁 | 半开连接长期占用 | 小包效率下降 | 接收端 OOM | 无法感知假死 |
| 用户可调 | `tcp_retries2` | `SO_KEEPALIVE` 及三个 sysctl | `TCP_NODELAY` | 传输库参数 | 完全可控 |

与拥塞控制的交互需要特别注意：persist 探测**不改变** $cwnd$，也不被视为拥塞信号；但探测段本身占用序号空间，若对端在探测期间恢复，可能收到重复数据，由接收方的序号一致性检查（丢弃重复段并回 ACK）自然处理。

## 六、常见误区

- **认为 $rwnd = 0$ 表示连接已死。** 这是正常的流控状态，发送方进入 persist 探测等待，恢复后通信照常继续。
- **认为零窗口探测会大量占带宽。** 探测段极小且间隔退避，空闲连接的额外流量可忽略；真正的问题在接收方应用长期不读导致连接被探测耗尽而关闭。
- **认为关闭 Nagle 总能让小消息更快。** `TCP_NODELAY` 加剧 tinygram，可能在与接收方小窗口耦合时形成更严重的往返放大。
- **把 persist 与 keepalive 混用。** 关闭 keepalive 不会影响 persist，反之亦然；排查「空闲连接被断」时要区分是哪个定时器在起作用。
- **忽略窗口更新 ACK 的应用层可见性。** 接收方应用读得慢时，`rcv_wnd` 长期为 0，`netstat`/`ss` 的 `Recv-Q` 会持续接近 `SO_RCVBUF`，这才是根因。

## 八、面试题

1. **零窗口探测解决什么问题？**
   要点：解决「窗口从 0 恢复的 ACK 丢失」导致的双方永久等待。发送方在 persist 定时器到期后发 1 字节探测，强制对端回 ACK 并携带当前窗口。

2. **接收方收到超出零窗口的探测段时应如何处理？**
   要点：必须回 ACK，即使不确认探测中的字节，也要携带当前 $rwnd$；不能静默丢弃，否则死锁无法解除。

3. **为什么接收方宁可通告 0 也不通告一个很小的窗口？**
   要点：小窗口会诱导发送方填充 tinygram，头开销吞掉带宽；等空间达到 $\min(MSS, B/2)$ 再一次性通告，可让发送方每次都能发满一个段。

4. **persist 探测与 keepalive 能否互相替代？**
   要点：不能。前者解决流控死锁且只在有数据待发时工作；后者解决半开连接且只在空闲时工作。二者触发条件、报文语义、配置项都不同。

5. **长时间 $rwnd=0$ 会有什么后果？**
   要点：发送方探测次数耗尽后报错关闭连接；接收方若应用一直不读，缓冲与队列长期占用，`Recv-Q` 满、延迟持续升高，属于典型的消费者过慢问题。

## 九、演进与趋势

现代内核把 SWS 阈值与自动缓冲调优（`tcp_moderate_rcvbuf`、`tcp_rmem` 三元组）结合，接收方窗口能随 RTT 与带宽自动增长，从而大幅降低 $rwnd=0$ 的发生概率；`tcp_notsent_lowat` 则从发送侧限制未发送数据量，兼具降低延迟与抑制缓冲膨胀的作用。

在用户态传输栈中，QUIC 用显式的 MAX_DATA / MAX_STREAM_DATA 帧替代隐式窗口字段，流控信用由接收方主动授予，不存在「窗口更新通知丢失」这一类问题；gRPC 基于 HTTP/2 也以 WINDOW_UPDATE 帧显式更新，语义更接近信用制流控（credit-based flow control）。

对可观测性而言，`TCPWinProbe`、`TCPZeroWindow`、`TCPBacklogDrop` 等 MIB 计数器与 eBPF 挂钩（如 `sock_ops`、`tcp_retransmit_skb`）让零窗口事件可被精确定位到具体连接与进程，取代了过去靠 `netstat` 猜测的方式。

## 十、小结

$rwnd=0$ 本身是正常的流控状态，危险来自「窗口恢复通知不可靠」这一协议缺口；persist 定时器与零窗口探测以极小代价补上了这个缺口，同时要求接收方必须回带窗口的 ACK。糊涂窗口综合征则是同一套窗口机制的另一个失效模式，需要发送端 Nagle 与接收端 Clark 双向抑制。

掌握三者（窗口通告、探测定时器、SWS 抑制）的相互关系，是诊断「连接卡住不动」「延迟忽高忽低」「空闲连接莫名断开」这类问题的前提。
