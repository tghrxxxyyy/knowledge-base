# 发送窗口与拥塞窗口的协同

> 对应 Jacobson 1988《Congestion Avoidance and Control》、RFC 5681、RFC 7661、Kurose & Ross 第3章与 Stevens《TCP/IP Illustrated》Vol.1 第21章。

## 一、背景与挑战

TCP 必须同时避免两种资源被压垮：**接收方的缓冲**与**网络中的瓶颈链路**。前者由流量控制（接收窗口 $rwnd$）负责，后者由拥塞控制（拥塞窗口 $cwnd$）负责。这两套机制由不同年代的文献提出、由不同的内核子系统维护、用不同方式感知状态，却必须在每次发送决策时被同时满足。

它们的传感方式截然不同：$rwnd$ 是接收方在每个 ACK 中显式通告的，属于**带内显式反馈**；$cwnd$ 则由发送方根据丢包、时延等信号**自行推断**网络容量，属于隐式推测。正是这种不对称，使得同一连接在不同阶段可能被其中任意一个限制，而瓶颈是谁往往是性能排查的第一问题。

## 二、核心原理

### 两者的约束与取小

发送方维护的最核心不变式是：任一时刻，已发送但未确认的数据量（FlightSize）不得超过两者中的较小者：

$$ \text{FlightSize} \le \min(cwnd,\ rwnd) $$

$rwnd$ 是接收方对「我还能收多少」的声明，属于流控；$cwnd$ 是发送方对「网络还能容纳多少」的估计，属于拥塞控制。前者是被动遵守，后者是主动探测。

### 拥塞控制的四个阶段

**慢启动（slow start）。** 连接初始使用较小的初始窗口（RFC 5681 规定初始窗口 IW 为 2–4 个 MSS，Linux 默认 10 个 MSS 左右，以官方文档为准），每收到一个 ACK 就把 $cwnd$ 增加一个 MSS，效果是每个 RTT 翻倍，呈指数增长。

**拥塞避免（congestion avoidance）。** 当 $cwnd$ 超过慢启动阈值 $ssthresh$ 后，增速降为线性：每个 RTT 增加约 1 个 MSS。Linux 实现为「每 ACK 增加 $MSS \times MSS / cwnd$」的累积式增长（`tcp_cong_avoid_ai`），等价于每 RTT +1 MSS。

**丢包响应。** 检测到超时（RTO）时把 $ssthresh$ 设为当前 FlightSize 的一半，$cwnd$ 降回 1 个 MSS 并重新慢启动；检测到重复 ACK（快速重传）时执行快速恢复，$cwnd$ 减半而不回到起点。

**拥塞状态的维持。** $ssthresh$ 与 $cwnd$ 共同构成 AIMD（加性增、乘性减）的锯齿波，是 TCP 公平性与稳定性的基础。

### 协同的关键点：窗口受限的识别

当 $rwnd < cwnd$ 时，网络并未拥塞，$cwnd$ 的增长被 $rwnd$ 掩盖——发送方因为无数据可发而拿不到足够 ACK 来增长 $cwnd$，导致接收方一旦扩大窗口，发送方的 $cwnd$ 反而「过期」偏小。RFC 7661 专门定义了 cwnd 验证（cwnd validation）机制来处理这一情形：发送方维护一个 $cwnd$ 使用量上界，记录「$cwnd$ 限制发送」的真实用时，若某次 $cwnd$ 未实际限制发送，则按时间与 RTT 比例折减其贡献。

Linux 中的对应实现是 `tcp_is_cwnd_limited()`：它检查发送队列中是否有足够数据、是否处于应用受限（app limited）状态。若发送方根本没有数据要发，则不应让 $cwnd$ 增长，避免在空闲后被误判为可以突发。

## 三、形式化与数学基础

发送窗口上界：

$$ W = \min(cwnd,\ rwnd), \qquad \text{FlightSize} = SND.NXT - SND.UNA $$

慢启动阶段的指数增长（$t$ 以 RTT 计）：

$$ cwnd(t) = IW \cdot 2^{t} $$

拥塞避免阶段的线性增长：

$$ cwnd(t) = cwnd_0 + MSS \cdot t $$

AIMD 的稳态行为：设丢包前的峰值窗口为 $W_{max}$，乘性减半后回到 $W_{max}/2$，则平均窗口约为：

$$ \bar{W} = \frac{W_{max} + W_{max}/2}{2} = 0.75\,W_{max} $$

由此得到吞吐的近似（Mathis 公式），其中 $p$ 为丢包率、$C$ 为与 ACK 策略相关的常数：

$$ T \approx \frac{MSS}{RTT} \cdot \frac{C}{\sqrt{p}} $$

它揭示了两个重要结论：丢包率对吞吐的影响是平方根量级而非线性，且 RTT 越小的连接在同丢包率下吞吐越高——后一点正是 TCP Reno 的 RTT 不公平性。

当瓶颈在接收方（$rwnd < cwnd$）时，吞吐上界变为：

$$ T_{max} = \frac{rwnd}{RTT} $$

此时增加 $cwnd$ 毫无意义；反之若 $cwnd < rwnd$，则提高接收缓冲也不会带来任何收益。

## 四、代码实现

Linux 发送路径上的双重检查，`net/ipv4/tcp_output.c`：

```c
/* 简化示意：对端窗口约束 */
static inline bool tcp_snd_wnd_test(const struct tcp_sock *tp,
                                    const struct sk_buff *skb,
                                    unsigned int cur_mss)
{
    u32 end_seq = TCP_SKB_CB(skb)->end_seq;
    if (skb->len > cur_mss)
        end_seq = TCP_SKB_CB(skb)->seq + cur_mss;
    return !after(end_seq, tcp_wnd_end(tp));   /* 未越过对端窗口右边界 */
}

/* 简化示意：拥塞窗口约束 */
static inline bool tcp_cwnd_test(const struct tcp_sock *tp,
                                 const struct sk_buff *skb)
{
    u32 in_flight = tcp_packets_in_flight(tp);

    if (in_flight >= tp->snd_cwnd)
        return false;                          /* 已达 cwnd 上限 */
    /* 允许最后一小段补足窗口，避免小 MSS 场景浪费余量 */
    return (tcp_snd_cwnd(tp) - in_flight - 1) * tp->mss_cache >=
           skb->len - tcp_skb_pcount(skb) * tp->mss_cache;
}
```

判断当前限制来自哪一侧，`tcp_is_cwnd_limited()`：

```c
/* 简化示意：避免在应用无数据可发时虚增 cwnd */
bool tcp_is_cwnd_limited(const struct sock *sk)
{
    const struct tcp_sock *tp = tcp_sk(sk);
    u32 left;

    if (tp->is_cwnd_limited)
        return true;
    /* 应用受限（发送队列空）时不算 cwnd 受限 */
    left = tcp_packets_in_flight(tp);
    if (left >= tcp_snd_cwnd(tp))
        return true;
    return false;
}
```

拥塞避免的加性增长（`tcp_cong_avoid_ai`，等价于每 RTT +1 MSS）：

```c
/* 简化示意 */
void tcp_cong_avoid_ai(struct tcp_sock *tp, u32 w, u32 acked)
{
    /* 累积 acked 个被确认的段，凑够一个窗口就 +1 MSS */
    if (tp->snd_cwnd_cnt >= w) {
        tp->snd_cwnd_cnt = 0;
        tcp_snd_cwnd_set(tp, tcp_snd_cwnd(tp) + 1);
    }
    tp->snd_cwnd_cnt += acked;
}
```

运行时切换算法与观察：

```bash

sysctl net.ipv4.tcp_congestion_control

sysctl -w net.ipv4.tcp_congestion_control=cubic

# 观察 cwnd、rwnd、以及谁在限制发送
ss -ti 'dport = :443'
# cwnd:10, ssthresh:... 以及 rwnd_limited / cwnd_limited / app_limited 标记
```

## 五、与其他技术对比

| 维度 | 流量控制（rwnd） | 拥塞控制（cwnd） | BBR | 停等/ARQ | QUIC 流控+拥塞控制 |
| --- | --- | --- | --- | --- | --- |
| 保护对象 | 接收方缓冲 | 网络瓶颈 | 网络瓶颈与排队 | 接收方 | 接收端 + 网络 |
| 反馈来源 | ACK 中显式窗口字段 | 丢包/时延推断 | 带宽与 RTT 建模 | ACK | MAX_DATA 帧 + 丢包/时延 |
| 增长方式 | 不增长（被动跟随） | 慢启动指数 + AIMD 线性 | ProbeBW 周期探测 | 无 | 视 CC 实现 |
| 减速触发 | 无（除非缓冲紧张） | 丢包/ECN/RTO | RTT 增大、带宽下降 | 无 | 同 CC |
| 公平性 | 天然无争抢 | AIMD 保证近似公平 | 与 Reno/CUBIC 竞争时偏激进 | 无 | 类似 CC |
| 失效表现 | 窗口为 0、persist 探测 | 抖动锯齿、丢包重传 | 聚合下 RTT 公平性问题 | 利用率极低 | 流阻塞 |

BBR（Cardwell 等，2016）的关键变化是**不再把丢包当作拥塞信号**，而是持续估计瓶颈带宽 $BtlBw$ 与最小 RTT $RTprop$，以 $cwnd \approx BtlBw \times RTprop$ 为目标，并用 pacing 平滑发送。它与 $rwnd$ 依然是取小关系，因此当接收方缓冲成为瓶颈时，BBR 同样无能为力。

## 六、常见误区

- **认为调大接收缓冲就能提升吞吐。** 若 $cwnd$ 受限（丢包、RTT 大、慢启动未完成），扩大 $rwnd$ 毫无收益。必须先用 `ss -ti` 判断限制来源。
- **认为 $cwnd$ 只由丢包决定。** 它还受 $rwnd$ 截断、受应用是否持续有数据影响（app limited）。空闲连接恢复时的 $cwnd$ 往往与上一次结束状态不同。
- **把 $ssthresh$ 与 $cwnd$ 混为一谈。** $ssthresh$ 是慢启动与拥塞避免的分界点，$cwnd$ 是当前允许的在途量。
- **认为快速恢复与超时恢复等价。** 快速恢复只需减半，超时恢复要回到 1 MSS 重新慢启动，代价差一个数量级（这体现了「时间到即网络严重拥塞」的设计假设）。
- **忽略接收方限制对 $cwnd$ 增长的掩盖。** 这是 RFC 7661 要解决的问题；不了解它会在「先慢消费者、后变快」的场景中误判性能。
- **认为 BBR 不需要流量控制。** BBR 只替换拥塞控制，$rwnd$ 依然参与取小，接收端仍可能成为瓶颈。

## 七、与开源书·权威来源对应

- Jacobson 1988《Congestion Avoidance and Control》：奠定慢启动、拥塞避免与「保守估计」原则，是 $cwnd$ 思想的原典。
- RFC 5681《TCP Congestion Control》：慢启动、拥塞避免、快速重传/快速恢复的标准化描述与 IW 取值。
- RFC 7661《Updating TCP to Support Rate-Limited Traffic》：cwnd 验证机制，处理应用受限导致的窗口虚增。
- RFC 793 §3.3：窗口字段与发送序号变量，$rwnd$ 的规范定义。
- Stevens《TCP/IP Illustrated》Vol.1 第21章：慢启动、拥塞避免与快重传快恢复的逐步图解。
- Kurose & Ross《Computer Networking》第3章：$\min(cwnd, rwnd)$ 与吞吐受限的图解分析。
- Cardwell 等 2016（BBR）：基于带宽与 RTT 建模的拥塞控制，替代丢包作为信号。
- Linux `net/ipv4/tcp_output.c`、`tcp_cong.c`：`tcp_snd_wnd_test()`、`tcp_cwnd_test()`、`tcp_cong_avoid_ai()`。

## 八、面试题

1. **为什么发送窗口是两者取小？**
   要点：需同时满足「不溢出接收缓冲」与「不压垮网络」两个约束，任一不足都会成为瓶颈；取小是同时满足两个条件的唯一形式化表达。

2. **如何判断吞吐受 $cwnd$ 还是 $rwnd$ 限制？**
   要点：看 `ss -ti` 的 `cwnd`、`bytes_acked` 与 `rwnd_limited`/`cwnd_limited` 标记；若对端通告窗口接近 FlightSize 且 `Recv-Q` 长满则为 $rwnd$ 受限。

3. **慢启动为什么是指数增长，会不会太激进？**
   要点：指数增长使连接能在少量 RTT 内探测到可用带宽，起始窗口保守（IW 较小）降低了首轮冲击；配合 $ssthresh$ 与丢包响应构成「先试探、后收敛」的策略。

4. **丢包为什么可以让 $cwnd$ 减半而不必归零？**
   要点：重复 ACK 表明后续段仍在到达，网络只是轻度拥塞，快速恢复减半即可；RTO 超时说明连 ACK 都回不来，是严重拥塞，才需要回到 1 MSS。

5. **应用受限（app limited）为什么会影响拥塞控制？**
   要点：无数据可发时发送方拿不到足够 ACK 来增长 $cwnd$，而一旦应用恢复，旧的 $cwnd$ 已不代表当前网络状态。RFC 7661 的 cwnd 验证按时间折算，避免窗口虚增造成突发丢包。

## 九、演进与趋势

拥塞控制的演进主线是「寻找更好的拥塞信号」。从 Reno 的丢包，到 CUBIC 的三次函数增长（改善高 BDP 链路的收敛速度），再到 BBR 的带宽—RTT 建模，以及数据中心场景中的 DCTCP/DCQCN（以 ECN 标记比例作为信号）、HPCC（以 INT 遥测的精确链路利用率作为信号）。这些算法的共同点是仍与 $rwnd$ 取小协同，但越来越依赖更细粒度的反馈。

在部署层面，QUIC（RFC 9000）把拥塞控制放进用户态，使算法可随应用更新而不必更换内核，且天然支持按连接选择算法；这与内核态 `TCP_CONGESTION` 的可选项形成互补。同时 pacing 从 BBR 的伴随手段变成了普遍的基础设施，fq/qfq 队列规则与网卡的 per-queue 调度使其可落地。

在观测与验证方向，eBPF 让 `cwnd`、`ssthresh`、`app_limited` 等内部状态可被实时采集；RFC 7661 的 cwnd 验证也促使内核区分「拥塞受限」与「应用受限」，使自动调优与容量规划更准确。

## 十、小结

$rwnd$ 与 $cwnd$ 是同一发送决策的两个约束面：前者是接收方的显式声明，后者是发送方对网络的隐式估计，二者取小构成实际发送窗口。慢启动负责快速探测，拥塞避免负责平稳收敛，丢包响应负责退让，共同构成 AIMD 的锯齿行为。

工程上最重要的能力是**判断瓶颈归属**：先确定是 $cwnd$、$rwnd$ 还是应用（app limited）在限制发送，再决定是调拥塞算法、扩接收缓冲，还是先解决消费者过慢的问题。任何吞吐调优都应从这一步开始。
