# 窗口缩放选项与高带宽时延积

> 对应 RFC 7323 (TCP Extensions for High Performance)、RFC 1072 (Long Fat Networks)、Stevens《TCP/IP Illustrated》Vol.1 第24章与 Kurose & Ross 第3章。

## 一、背景与挑战

TCP 头中的窗口字段是 16 位无符号整数，最大通告 65535 字节。这一限制在 1981 年设计时远超当时的链路能力，但随着带宽与 RTT 同时增长，它成为吞吐的硬上限。

原因在于滑动窗口的吞吐公式 $T \le W / RTT$。要填满一条带宽 $B$ 的链路，窗口必须至少覆盖一个带宽时延积 $BDP = B \times RTT$。当 $BDP > 65535$ 时，无论网络多快、接收缓冲多大，单条 TCP 连接的吞吐都被钉死在 $65535 / RTT$。

这类「带宽高、时延大」的链路被 RFC 1072 称为长肥管道（Long Fat Network，LFN）。例如 $B = 10\text{Gbps}$、$RTT = 100\text{ms}$ 时 $BDP \approx 125\text{MB}$，是 64KB 窗口的约 1900 倍——单连接利用率不足 0.06%。窗口缩放选项（Window Scale Option，WSOPT）正是为突破这一 16 位天花板而生。

## 二、核心原理

### 选项格式与协商

WSOPT 是 TCP 选项的一种，类型 Kind = 3，长度 Length = 3，第三个字节是移位计数 $S$（shift count），取值 0–14。它只在连接建立阶段出现：

- 主动方在 SYN 中携带自己的 $S_{send}$；
- 被动方在 SYN+ACK 中携带自己的 $S_{recv}$；
- 若某方向未在 SYN 中携带该选项，则该方向的窗口**不得**缩放（RFC 7323 的强制要求），因此双方必须对称协商；
- 其他所有段（包括重传的 SYN）都不得再携带该选项。

两个方向的移位计数是**独立**的：发送方向的窗口字段按对端给的 $S_{recv}$ 解读，接收方向自己通告的窗口按本方 $S_{send}$ 编码。因此实际通告的窗口为：

$$ rwnd_{real} = rwnd_{field} \ll S_{send} $$

接收到的窗口为：

$$ rwnd_{peer} = rwnd_{field} \ll S_{recv} $$

### 为什么上限是 14

移位后的最大窗口为 $65535 \times 2^{14} = 2^{16} \times 2^{14} \approx 2^{30} \approx 1\text{GB}$。把最大值限制在 $2^{30}$ 而非更大，是为了让 32 位序号空间的窗口内比较运算保持正确：窗口内所有序号的两两差值都落在 $2^{31}$ 以内，符号比较（`(s32)(a-b) < 0`）才能无歧义地判断先后。若窗口达到 $2^{31}$，窗口本身就覆盖半个序号空间，序号回绕判定将失效。

### 与接收缓冲的关系

窗口缩放只是**编码方式**的改变，实际能通告多大仍取决于接收缓冲。Linux 中，通告窗口由 `tcp_adv_win_scale` 决定从缓冲中预留多少给协议开销：默认值为 1，即可用窗口约为 $SO\_RCVBUF / 2$。因此要让 100ms RTT、10Gbps 的链路跑满，接收缓冲需显著大于 BDP。

### 与 SYN 段的关系

SYN 段的窗口字段永不缩放（因为协商尚未完成）。这一点在抓包分析时极易误判：SYN 中的 `Win=65535` 可能对应协商后的数十 MB。

## 三、形式化与数学基础

为在带宽 $B$、往返时延 $R$ 的链路上达到完全利用，所需窗口为：

$$ W_{need} \ge B \times R = BDP $$

若 $W_{need} > 65535$，则所需移位计数为：

$$ S \ge \left\lceil \log_2 \frac{W_{need}}{65535} \right\rceil $$

且受协议上限约束 $S \le 14$。以 $B = 10\text{Gbps}$、$R = 100\text{ms}$ 为例：

$$ BDP = 10 \times 10^{9} \times 0.1 / 8 = 1.25 \times 10^{8}\ \text{字节} = 125\ \text{MB} $$

$$ S \ge \left\lceil \log_2 \frac{1.25 \times 10^{8}}{65535} \right\rceil = \left\lceil \log_2 1907 \right\rceil \approx 11 $$

考虑通告窗口还受 `tcp_adv_win_scale` 折半，实际所需 `SO_RCVBUF` 约为 $2 \times BDP = 250\text{MB}$。

链路利用率可以写成窗口与 BDP 的比值被 1 截断：

$$ \eta = \min\left(1,\ \frac{W_{real}}{BDP}\right) $$

其中 $W_{real} = \min(cwnd, rwnd_{real})$。当窗口缩放失效（$S=0$）时 $W_{real} \le 65535$，于是 $\eta \le 65535/BDP$。

一个重要的边界情况：$2^{30}$ 字节的窗口上限意味着当

$$ B \times R > 2^{30} \approx 1.07\ \text{GB} $$

时，单条 TCP 连接无论怎样配置都无法填满链路。例如 $B=100\text{Gbps}$、$R=200\text{ms}$ 时 $BDP = 2.5\text{GB} > 1\text{GB}$，必须改用多连接、更大 MSS 或应用层分片。

## 四、代码实现

内核侧解析 WSOPT 在 `tcp_parse_options()`（`net/ipv4/tcp_input.c`），协商结果保存在连接选项中：

```c
/* 简化示意：仅有 SYN 段才做缩放协商 */
case TCPOPT_WINDOW:
    if (opsize == TCPOLEN_WINDOW && th->syn &&
        !estab && sysctl_tcp_window_scaling) {
        __u8 snd_wscale = *(u8 *)ptr;
        if (snd_wscale > TCP_MAX_WSCALE)   /* 上限 14 */
            snd_wscale = TCP_MAX_WSCALE;
        opt_rx->wscale_ok = 1;
        opt_rx->snd_wscale = snd_wscale;   /* 对端给的：本方向发送时使用 */
    }
    break;
```

通告窗口的编码在发送 SYN 时写入本方缩放因子，并在计算窗口时右移：

```c
/* 简化示意：把真实窗口编码为 16 位字段 */
static inline u16 encode_window(u32 real_wnd, u8 wscale)
{
    return (u16)(real_wnd >> wscale);   /* 解码端再左移还原 */
}
```

用户态与内核参数的典型配置：

```bash
# 1) 确认窗口缩放已启用（默认开启）
sysctl net.ipv4.tcp_window_scaling         # 期望为 1

# 2) 扩大自动调优的上限，使 BDP 大的链路能拿到足够窗口
sysctl -w net.ipv4.tcp_rmem="4096 131072 268435456"
sysctl -w net.ipv4.tcp_wmem="4096 16384 268435456"
sysctl -w net.core.rmem_max=268435456
sysctl -w net.core.wmem_max=268435456

# 3) tcp_adv_win_scale 决定从缓冲中预留多少给协议开销
sysctl net.ipv4.tcp_adv_win_scale          # 默认 1 → 可用窗口约为缓冲的一半
sysctl net.ipv4.tcp_moderate_rcvbuf        # 默认 1 → 自动调优生效
```

```c
/* 显式设置接收缓冲：内核会将其翻倍并受 rmem_max 钳制 */
int want = 32 * 1024 * 1024;
setsockopt(fd, SOL_SOCKET, SO_RCVBUF, &want, sizeof(want));
/* 需要突破 rmem_max 时用 SO_RCVBUFFORCE（需 CAP_NET_ADMIN） */
```

```bash
# 验证协商结果：ss -ti 中的 wscale 即双方移位计数
ss -ti 'dport = :443' | tr ';' '\n' | grep -E 'wscale|rtt|rcv_space|bytes_acked'
# 抓包直接看 SYN 中的 option kind=3
tcpdump -i eth0 -vvv 'tcp[tcpflags] & tcp-syn != 0 and port 443' | grep -i wscale
```

## 五、与其他技术对比

| 维度 | 窗口缩放 WSOPT | 时间戳选项 TS | SACK | QUIC MAX_DATA | UDP + 应用限速 |
| --- | --- | --- | --- | --- | --- |
| 解决的问题 | 窗口上限 64KB | RTT 测量与 PAWS | 选择性重传 | 显式流控信用 | 无标准机制 |
| 协商时机 | SYN / SYN+ACK | SYN / SYN+ACK | SYN / SYN+ACK | 握手与后续帧 | 无 |
| 载荷开销 | 3 字节（仅握手） | 12 字节（每段） | 可变（丢包时） | 0（帧内） | 0 |
| 上限 | $2^{30}$ 字节 | 无 | 无 | 协议实现相关 | 无 |
| 失效后果 | 吞吐被钉在 64KB/RTT | RTT 估计粗糙、回绕误判 | 重传放大 | 流阻塞 | 应用自行控制 |
| 依赖关系 | 需接收缓冲配合 | 独立 | 常与 TS 同用 | 独立 | 独立 |

值得注意的是，三个选项（WS、TS、SACK）在 RFC 7323 中被统一定义，实践中几乎总是同时启用，且都必须出现在 SYN 中协商。若中间设备（老防火墙、负载均衡）剥离选项，会导致协商静默失败——这正是「链路明明很宽但单流很慢」的常见根因。

## 六、常见误区

- **认为改大 `net.core.rmem_max` 就够了。** 还需要应用不被 `SO_RCVBUF` 限制、`tcp_rmem` 上限足够、且 WSOPT 成功协商。四者缺一，窗口都上不去。
- **认为缩放因子可以中途改变。** RFC 7323 规定只在 SYN 中协商一次，之后全程固定；重传 SYN 也不得携带该选项。
- **混淆「通告窗口」与「字段值」。** `ss` 与抓包看到的多半是解码后的值，而原始字段是移位前的；读 SYN 的 `Win=65535` 不能直接当作实际能力。
- **忽略 SYN 段的窗口不缩放。** 在做握手阶段的窗口分析时容易得出错误结论。
- **认为窗口越大越好。** 窗口显著大于 BDP 会增加首包突发（burst）与中间队列压力，且可能触发接收方丢弃；配合 pacing 才是更优解。
- **忘记 $2^{30}$ 上限。** 超大 BDP 链路上单连接必然受限，需要多连接或应用层方案。

## 七、与开源书·权威来源对应

- RFC 7323《TCP Extensions for High Performance》：窗口缩放、时间戳、PAWS 与 SACK-permitted 的规范化定义，取代 RFC 1323。
- RFC 1072：首次提出窗口缩放与 RTTM，并定义 Long Fat Network（LFN）这一术语。
- RFC 793 §3.1：原始 16 位窗口字段的定义，是理解为何需要扩展的前提。
- Stevens《TCP/IP Illustrated》Vol.1 第24章：窗口缩放、时间戳与长肥管道的实测分析。
- Kurose & Ross《Computer Networking》第3章：吞吐与窗口、BDP 的关系推导。
- Hennessy & Patterson《Computer Architecture》：高 BDP 与内存带宽对系统吞吐的约束（体系结构视角）。
- Linux `net/ipv4/tcp_input.c`、`tcp_output.c`：`tcp_parse_options()` 与窗口编码路径。

## 八、面试题

1. **没有窗口缩放时，10Gbps、100ms 链路上的单连接为什么利用率极低？**
   要点：$BDP = 125\text{MB}$，而窗口上限 64KB，利用率约 $64\text{KB}/125\text{MB} \approx 0.05\%$；窗口是瓶颈而非带宽。

2. **窗口缩放的最大移位是多少、为什么？**
   要点：14，使最大窗口为 $2^{16} \times 2^{14} = 2^{30}$ 字节，保证序号比较在 32 位空间内无歧义（窗口不覆盖半个序号空间）。

3. **缩放因子在连接生命周期内会变吗？**
   要点：不会。只在 SYN/SYN+ACK 协商一次；不含该选项的一方不得使用缩放；重传 SYN 也不携带。

4. **`ss -ti` 里的 `wscale` 是什么？**
   要点：`wscale:7,7` 表示本端与对端各自的移位计数；真实窗口 = 字段值左移对应位数。用于确认协商是否成功。

5. **协商成功但吞吐仍然低，可能是哪些原因？**
   要点：接收缓冲不足（`SO_RCVBUF`/`tcp_rmem` 上限导致可用窗口小于 BDP）、`tcp_adv_win_scale` 折半、cwnd 受限（丢包/拥塞控制）、中间设备剥离选项、应用读得慢导致 `rwnd` 长期为 0。

## 九、演进与趋势

窗口缩放解决了 16 位天花板，但没有解决「窗口大于 BDP」带来的突发问题，也没有解决丢包恢复效率——后者由 SACK 与 FACK 承担，前者由 pacing 缓解。现代内核以自动缓冲调优（`tcp_moderate_rcvbuf`）按实测 RTT 与投递速率动态调整缓冲，使 $rwnd$ 自动逼近 BDP，大幅降低了手工调参的必要性。

在协议演进上，QUIC（RFC 9000）不再使用「窗口字段 + 移位」的编码技巧，而是用 MAX_DATA / MAX_STREAM_DATA 帧显式通告绝对字节上限，语义清晰且可动态调整，天然支持流级与连接级的双层流控；HTTP/2 的 WINDOW_UPDATE 也采用类似的显式信用模型。这代表了一种设计取向的转变：**从「用位数换范围」的紧凑编码，转向「用显式协议帧换可推理性与灵活性」。**

在数据中心内部，巨帧（jumbo frame，9000 字节 MTU）与多路径（MPTCP、RoCE）从另一维度降低了每段的协议开销，与窗口扩展互为补充。

## 十、小结

窗口缩放选项用 3 字节的握手协商，把 TCP 可用窗口从 64KB 提升到约 1GB，是让单条连接填满长肥管道的前提。其关键性质有三：只在 SYN 阶段协商一次并全程固定、双向移位计数独立、上限 14 位以保证序号比较的正确性。

有效吞吐的正确理解是 $\eta = \min(1, W_{real}/BDP)$，其中 $W_{real} = \min(cwnd, rwnd_{real})$，而 $rwnd_{real}$ 同时受缩放协商、接收缓冲大小与 `tcp_adv_win_scale` 三者约束。排查单流吞吐问题时，应按这个链条逐项确认，而不是只调一个 sysctl。
