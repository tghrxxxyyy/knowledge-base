# 窗口缩放选项与高带宽时延积

> 对应 RFC 7323 (TCP Extensions for High Performance) 与 RFC 1072。

## 一、背景与挑战
TCP 头窗口字段仅 16 位，最大通告 65535 字节。对于高带宽时延积 BDP 链路（如长肥管道），该上限使利用率极低。窗口缩放选项 WSOPT 将窗口空间向左移位，突破 64KB 限制以填满高速链路。

## 二、核心原理
WSOPT 在 SYN/SYN+ACK 中协商一个 0–14 的移位计数 $S$。真实窗口为头中字段值左移 $S$ 位：
$$ rwnd_{real} = rwnd_{field} \ll S $$
最大可支持 $65535 \times 2^{14} \approx 1\,\text{GB}$。该选项仅在三次握手交换一次，之后固定。

## 三、形式化与数学基础
为填满带宽为 $B$、RTT 为 $R$ 的链路，所需窗口：
$$ W_{need} \ge B \times R = BDP $$
若 $W_{need} > 65535$，则要求 $S \ge \lceil \log_2(W_{need} / 65535) \rceil$。例如 $B=10\,\text{Gbps}, R=100\,\text{ms}$ 时 $BDP \approx 125\,\text{MB}$，需 $S \approx 11$。

## 四、代码实现
Linux 在 `tcp_parse_options` 解析 WSOPT，应用层启用：
```c
int one = 1;
setsockopt(fd, IPPROTO_TCP, TCP_WINDOW_CLAMP, ...);
// 由内核据缓冲自动计算移位
```
查看协商窗口：
```bash
ss -ti  # 显示窗口缩放与 rto 等信息
```

## 五、与其他技术对比
UDP 无窗口概念，靠应用层自行限速；QUIC 以 MAX_DATA/MAX_STREAM_DATA 帧显式通告流控上限，类似但更灵活。

## 六、常见误区
误区一是认为改大 `net.core.rmem_max` 即可，还需应用 `SO_RCVBUF` 与 WSOPT 协商匹配。误区二是 WSOPT 可中途变更，实际握手后固定。

## 七、与开源书/权威来源对应
RFC 7323 规定窗口缩放；Hennessy & Patterson 在体系结构中讨论高 BDP 对系统的压力；xiaolincoder/hello-http 解释长肥管道。

## 八、面试题
问：为什么没有窗口缩放时 10G 长链路利用率低？答：最大窗口 64KB 远小于 BDP，管道始终未被填满，利用率约 $64KB / BDP \ll 1$。

## 九、演进与趋势
自动调优（如 `tcp_rmem` 与 BBR 配合）使现代内核默认能利用大窗口，但虚拟化与跨数据中心长链路仍需确认 WSOPT 已协商。

## 十、小结
窗口缩放选项通过移位将 TCP 窗口扩展到 GB 级，是填满高 BDP 长肥管道的前提，必须与接收缓冲配置协同才能发挥作用。
