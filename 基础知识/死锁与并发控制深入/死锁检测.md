# 死锁检测

> 对应 Silberschatz《Operating System Concepts》死锁检测章。

## 一、背景与挑战
允许死锁发生、定期检测并恢复，比严格预防有更高资源利用率。检测需判断当前是否处于死锁，并定位卷入进程/资源。

## 二、核心原理
- 单实例资源：检测资源分配图中是否存在进程环。
- 多实例资源：用类似银行家的安全算法，但用 `Request` 矩阵代替 `Need`，看能否化简到全完成。
- 检测频率权衡：过频开销大，过疏死锁持续久。

## 三、形式化 / 数学基础
多实例检测：从 `Available` 出发，反复将 $Request_i \\le Available$ 的进程 $i$ 标记为可完成并回收其 `Allocation`。剩余未标记进程集即死锁卷入者。

## 四、代码实现
等待图环检测（单实例，示意）：

```c
int detect_deadlock(int **wait, int n) {
    int *vis = calloc(n, sizeof(int)), *stk = calloc(n, sizeof(int));
    for (int s = 0; s < n; s++)
        if (dfs_cycle(wait, vis, stk, s, n)) return 1;
    return 0;
}
/* dfs: 访问中再次遇到本路径节点 => 环 */
```

## 五、与其他技术对比
检测+恢复利用率高但需恢复机制（杀进程/回滚/抢占）；预防/避免无恢复成本但限制并发。选择取决于代价模型。

## 六、常见误区
- 认为检测到就能自动解决：还需选择 victim 与回滚策略。
- 混淆等待图与资源分配图：多实例需化简算法而非单纯找环。
- 忽略检测本身的开销与锁争用。

## 八、面试题
1. 单实例与多实例死锁检测有何不同？
2. 检测到死锁后如何恢复？
3. 检测频率如何权衡？

## 九、演进与趋势
数据库用锁等待图（wait-for graph）实时检测；分布式系统用超时与向量时钟检测。

## 十、小结
死锁检测允许发生再发现：单实例看进程等待环，多实例看能否化简完全部进程；恢复靠抢占或回滚卷入者。
