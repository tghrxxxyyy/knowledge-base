# 银行家算法

> 对应 Dijkstra 银行家算法与 Silberschatz《Operating System Concepts》。

## 一、背景与挑战
死锁避免（avoidance）要求系统始终处于“安全状态”——存在某种分配序列能让所有进程完成。银行家算法在每次分配前预判安全性。

## 二、核心原理
维护：
- `Available`：各类资源可用量
- `Max`：各进程最大需求
- `Allocation`：已分配
- `Need = Max - Allocation`
分配请求 `Request` 前先试分配，若新状态“安全”才批准，否则等待。

## 三、形式化 / 数学基础
安全检测：找进程 $i$ 使 $Need_i \\le Available$，则 $Available \\gets Available + Allocation_i$，标记完成；若所有进程可完成则安全。避免的不变量：分配后仍存在安全序列。

## 四、代码实现
安全性检查（示意）：

```c
int is_safe(int *avail, int **need, int **alloc, int n, int m) {
    int *work = copy(avail), *fin = calloc(n, sizeof(int));
    for (int done = 0; done < n; done++) {
        int found = 0;
        for (int i = 0; i < n; i++) if (!fin[i] && le(need[i], work)) {
            for (int r = 0; r < m; r++) work[r] += alloc[i][r];
            fin[i] = found = 1; break;
        }
        if (!found) return 0;   /* 无法继续 */
    }
    return 1;
}
```

## 五、与其他技术对比
预防（破条件）限制资源使用、降低并发；避免（银行家）保持最大并发但需预知最大需求、且开销大；检测+恢复最灵活但可能已发生损害。

## 六、常见误区
- 认为银行家能“解决”死锁：它避免，但要求已知 Max 且保守。
- 忽略其开销随进程/资源数上升。
- 混淆安全状态与死锁状态：安全≠已分配满，是“存在完成序列”。

## 九、演进与趋势
通用 OS 很少全局运行银行家（需求难预知），但在数据库事务锁、资源控制器中有应用；更常用检测+超时回滚。

## 十、小结
银行家算法以“试分配+安全序列检查”在分配前保证系统永不离安全状态，代价是需预知最大需求且计算开销较高。
