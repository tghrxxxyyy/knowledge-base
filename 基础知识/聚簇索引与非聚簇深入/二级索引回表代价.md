# 二级索引回表代价

> 对应 MySQL InnoDB 官方文档「Clustered and Secondary Indexes」与 cmu-db/15445-course 索引章节。

## 一、背景与挑战
二级索引叶子只保存主键值，当查询需要索引列之外的字段时，必须拿主键回聚簇索引再查一次，这「回表」是二级索引查询的重要隐藏代价。

## 二、核心原理
查询走二级索引定位到若干主键值后，对每个主键再到聚簇索引做一次 B+Tree 查找取整行。回表次数等于命中的索引条目数（去重后），本质是随机 IO，可能使二级索引方案反而不如全表顺序扫。

## 三、形式化与数学基础
设二级索引命中 $k$ 个主键，回表代价：
$$ C = C_{idx\_lookup} + k \cdot C_{cluster\_lookup} $$
$k$ 大时 $k \cdot C_{cluster\_lookup}$ 占主导，可能超过顺序扫描 $N/r \cdot C_{page\_read}$。

## 四、代码实现
```sql
-- 需要 extra 列，触发回表
SELECT * FROM orders WHERE user_id = 42;
-- 若只查索引列可覆盖，避免回表
SELECT user_id FROM orders WHERE user_id = 42;
```

## 五、与其他技术对比
堆表（MyISAM）二级索引存行指针，回表一次定位物理行，但缺聚簇局部性。覆盖索引（见下篇）可彻底消除回表，是 InnoDB 重要优化。

## 六、常见误区
以为走了二级索引就很快——大范围回表可能比顺序扫还慢。认为 `SELECT *` 无害——它几乎必然触发回表。

## 七、与开源书/权威来源对应
InnoDB 文档；cmu-db/15445-course「Index」讲到回表与覆盖。

## 八、面试题
问：什么场景二级索引不如全表扫？答：选择性低、需回表列多，随机 IO 累积超过顺序扫。问：如何避免回表？答：建覆盖索引，使所需列都在索引中。

## 九、演进与趋势
索引仅存主键的设计催生「索引包含列」（INCLUDE）以兼顾覆盖与索引体积，SQL Server、PostgreSQL 均支持。

## 十、小结
回表是二级索引的随机 IO 成本核心，范围越大代价越高，需以覆盖索引化解。
