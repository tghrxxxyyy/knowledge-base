# 聚簇索引物理存储布局

> 对应 MySQL InnoDB 官方文档「Clustered and Secondary Indexes」与 Silberschatz 第11章 B+Tree 索引。

## 一、背景与挑战
InnoDB 中表数据本身就按主键 B+Tree 组织，即「索引即数据」。理解这种聚簇布局对设计主键、避免碎片化至关重要。

## 二、核心原理
聚簇索引的叶子节点直接存放整行数据（除溢出页的大字段外），非叶子节点存主键键值与子页指针。行按主键顺序物理聚拢。二级索引叶子则只存「索引列值 + 主键值」，通过主键回表取其余列。

## 三、形式化与数学基础
B+Tree 高度 $h$ 与行数 $N$、每页分支因子 $b$ 关系：
$$ N \approx b^h $$
当 $b = 100, h = 3$ 时可索引百万级行；聚簇使点查仅需 $h$ 次 IO 即取到整行。

## 四、代码实现
```sql
-- 查看 InnoDB 表聚簇结构信息
SHOW TABLE STATUS LIKE 'users';
-- 主键即聚簇键
CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(64));
```

## 五、与其他技术对比
MyISAM 为堆表，索引与数据分离，主键与二级索引叶子都存行物理地址，无回表概念但无聚簇局部性。PostgreSQL 默认堆表 + 独立索引，可建 Index-Organized 类似物（如 BRIN 用于有序数据）。

## 六、常见误区
认为二级索引也存整行——其实只存主键。认为主键可随意用 UUID——无序 UUID 会造成聚簇页分裂与碎片化。

## 七、与开源书/权威来源对应
InnoDB 官方文档「Clustered and Secondary Indexes」；Silberschatz 11.3「B+ Tree Index」。

## 八、面试题
问：为什么推荐自增主键？答：顺序插入避免页分裂，聚簇紧凑、碎片少。问：聚簇索引缺点？答：主键更新代价高、二级索引体积因含主键而变大。

## 九、演进与趋势
部分引擎支持「隐式聚簇」或可调聚簇键，以适应非主键访问模式；列式与 LSM 改写存储布局但概念仍存。

## 十、小结
聚簇索引让主键即数据地址，回表只需主键，但主键设计直接决定存储健康度。
