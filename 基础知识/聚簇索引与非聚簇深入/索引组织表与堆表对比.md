# 索引组织表与堆表对比

> 对应 Silberschatz 第11章与 PostgreSQL / MySQL 存储对比，参考 cmu-db/15445-course 存储层。

## 一、背景与挑战
数据库可按「索引即表」（IOT，聚簇）或「堆」（行按插入顺序堆放、索引指向物理地址）组织。两者在访问局部性、主键更新代价、二级索引体积上各有优劣。

## 二、核心原理
IOT（InnoDB）主键即数据位置，主键查询与点范围极快，但主键更新需移动行、二级索引含主键而偏大。堆表（PostgreSQL 默认、MyISAM）行位置稳定，主键更新只改索引指针，二级索引更紧凑，但无主键聚簇局部性。

## 三、形式化与数学基础
堆表二级索引体积约 $V_{heap\_idx} = k \cdot (idx\_cols + ptr\_size)$，聚簇表二级索引体积 $V_{clu\_idx} = k \cdot (idx\_cols + pk\_size)$，因 $pk\_size > ptr\_size$ 通常更大。

## 四、代码实现
```sql
-- PostgreSQL 堆表 + 独立主键索引
CREATE TABLE t (id INT PRIMARY KEY, v TEXT);
-- InnoDB 等价则为聚簇
```

## 五、与其他技术对比
Oracle 提供 `ORGANIZATION INDEX` 显式 IOT；SQL Server 有 clustered index 概念类似 InnoDB。堆表适合主键频繁更新或宽主键场景。

## 六、常见误区
认为聚簇一定优于堆——宽主键或频繁主键变更时堆表更稳。认为堆表没有「聚簇」优势就无法优化——可用 CLUSTER 命令或 BRIN 等获得局部性。

## 七、与开源书/权威来源对应

## 八、面试题
问：聚簇 vs 堆表二级索引差异？答：聚簇二级索引含主键、体积大但回表快；堆表含行指针、紧凑但无局部性。

## 九、演进与趋势
混合存储（如 zheap、undo 分离）缓解聚簇表 MVCC 带来的膨胀问题。

## 十、小结
IOT 与堆表是存储组织根本选择，影响主键策略、回表代价与索引体积，需按访问模式权衡。
