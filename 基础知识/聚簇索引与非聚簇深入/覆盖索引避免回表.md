# 覆盖索引避免回表

> 对应 MySQL InnoDB 官方文档「Index Covering」概念与 cmu-db/15445-course，参考 Silberschatz 第12章。

## 一、背景与挑战
前述回表代价高昂。若查询所需全部列都包含在某一个索引中，引擎可直接从索引返回，无需访问聚簇索引，这就是覆盖索引（covering index）。

## 二、核心原理
当 SELECT 列表、WHERE、ORDER BY、JOIN 键涉及的列都能由二级索引（含其隐含的主键）满足时，EXPLAIN 的 `Extra` 显示 `Using index`。InnoDB 二级索引叶子天然含主键，因此「索引列 + 主键列」可被覆盖。

## 三、形式化与数学基础
覆盖索引代价：
$$ C_{cover} = C_{idx\_scan} $$
相比需回表：
$$ C_{idx\_scan} \ll C_{idx\_scan} + k \cdot C_{cluster\_lookup} $$
当 $k$ 大时收益显著。

## 四、代码实现
```sql
-- 建联合覆盖索引
CREATE INDEX idx_cover ON orders (user_id, status, amount);
-- 下列查询可覆盖
SELECT user_id, status, amount FROM orders WHERE user_id = 42;
```

## 五、与其他技术对比
PostgreSQL 的 Index-Only Scan 类似，但需配合 visibility map 确认页内行对当前事务可见，否则仍要查堆。InnoDB 因事务信息在聚簇行，实现略有差异。

## 六、常见误区
认为建了联合索引就一定覆盖——若 SELECT 含不在索引中的列仍回表。认为覆盖索引能解决所有慢查——写入时多索引带来写放大。

## 七、与开源书/权威来源对应
Silberschatz 12.6「Covering Index」；InnoDB 文档「Using Index」。

## 八、面试题
问：如何判断查询走了覆盖索引？答：EXPLAIN 的 Extra 含 `Using index` 且无 `Using where` 回表。问：覆盖索引对写入影响？答：多维护一份索引，写入变慢、空间变大。

## 九、演进与趋势
INCLUDE 列（非键列）让覆盖索引不必把列放入键树序，减小索引宽度同时保持覆盖。

## 十、小结
覆盖索引以空间换回表 IO，是读多写少场景的核心优化手段。
