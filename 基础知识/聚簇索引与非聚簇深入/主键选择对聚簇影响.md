# 主键选择对聚簇影响

> 对应 MySQL InnoDB 官方文档「Primary Key Optimization」与 cmu-db/15445-course，参考 DDIA 第3章。

## 一、背景与挑战
InnoDB 聚簇特性使主键不仅是唯一约束，更是整张表的物理排序键。主键选择直接决定插入模式、页分裂频率与二级索引体积。

## 二、核心原理
自增整数主键使插入总是追加到 B+Tree 最右页，几乎无页分裂，存储紧凑。无序主键（如 UUID、随机散列）使插入落到树中随机位置，频繁触发页分裂与记录迁移，产生碎片并拖慢写入。

## 三、形式化与数学基础
顺序插入页分裂概率近似 0；随机主键插入时，新行落入已满页的概率约 $fill\_ratio$，导致分裂率：
$$ p_{split} \approx 1 - fill\_ratio $$
高分裂率意味更多 IO 与碎片。

## 四、代码实现
```sql
-- 推荐：自增聚簇主键
CREATE TABLE events (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...);
-- 谨慎：UUID 主键导致随机插入
CREATE TABLE events (id CHAR(36) PRIMARY KEY, ...);
```

## 五、与其他技术对比
堆表（PostgreSQL 默认）主键不影响物理顺序，UUID 主键不会造成聚簇分裂，仅二级索引偏大。LSM-tree 顺序写天然友好，无序 key 也无分裂之忧。

## 六、常见误区
认为主键只要是唯一就行，忽略顺序性。认为 UUID 主键不可用——高并发分布式场景可折中用有序 UUID（如时间前缀）兼顾。

## 八、面试题
问：为什么 UUID 主键在 InnoDB 不佳？答：无序致页分裂、碎片、二级索引膨胀。问：没显式主键会怎样？答：InnoDB 选首个唯一非空索引，否则隐式生成 6 字节 row_id，仍聚簇但不直观。

## 九、演进与趋势
有序 UUID（UUIDv7 等）兼顾分布式唯一与局部顺序，缓解聚簇分裂。

## 十、小结
InnoDB 主键即聚簇键，顺序短主键是写入与存储健康的最佳实践。
