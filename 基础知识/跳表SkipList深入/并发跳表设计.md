# 并发跳表设计

> 对应 Java `ConcurrentSkipListMap` 源码（JUC）、Pugh 论文关于并发的讨论，以及 Herlihy & Shavit《The Art of Multiprocessor Programming》中无锁数据结构章节。

## 一、背景与挑战

多线程共享一个有序映射时，最直接的做法是「一把大锁包住红黑树」。正确性好办，吞吐却很差：查找本可只读，也要排队；旋转再平衡一锁到底，写写冲突放大。平衡树的无锁化更难——一次旋转要原子地改多个指针，CAS 无法天然覆盖「多指针协同」，通常得引入事务内存或极其复杂的帮助（helping）协议。

跳表在这里显出结构性优势：插入/删除**只改局部前向指针**，查找**只读、单向前进**。于是可以做到：读路径完全无锁；写路径用 CAS 逐层发布；删除用「逻辑标记 + 物理摘除」两阶段，避免读者看到半删除结点。Java 的 `ConcurrentSkipListMap` 就是这条路线的工业标准，被广泛用于高并发有序缓存、时间线索引、任务调度堆。

挑战在于并发正确性不是「加个锁」一句话：必须定义**内存可见性**（acquire/release）、**线性化点**、**帮助机制**（一个线程能否完成另一个线程未完成的删除）、以及 **ABA 与内存回收**（Python 有 GC 相对轻松，C/C++ 要 hazard pointer/epoch）。面试里常考「如何无锁插入」「删除标记是干什么的」「读为什么不用加锁」，需要把不变量与协议讲清楚。

## 二、核心原理

### 2.1 读路径：无锁遍历

查找从 head 最高层向右再下降，全程只读指针。前提是：**读者永远能看到「结构一致的快照」**——不会看到半个结点、不会看到指向已回收内存的悬垂指针。这靠写侧的发布协议保证：

1. 新结点先完全初始化（key、value、forward 数组都写好）；
2. 再用 CAS 把前驱的 `forward[i]` 指向新结点（发布）；
3. 内存序上，初始化是 release 之前的工作，读者 acquire 到指针后能看到完整结点。

### 2.2 写路径：逐层 CAS 插入

插入与单线程相同地先找 `update[]`，然后对 $i = 0..lvl$ 执行：

```
loop:
    node.forward[i] = update[i].forward[i]
    if CAS(update[i].forward[i], 期望后继, node): 成功
    else: 重新定位 update[i]（可能别的线程插入/删除了），重试
```

可以自底向上挂（先第 0 层再高层），也可以自顶向下。关键点：**只要第 0 层挂上，结点就算存在于集合**；高层是加速指针，允许稍后补齐（或由帮助者补齐）。另一种更简单的协议是「先在私有区建好所有层，再从高到低 CAS 发布」，但失败重试更多。Java 采用自顶向下并在每层 CAS，失败则回退重新查找。

### 2.3 删除：标记 + 物理摘除

直接 `update[i].forward[i] = target.forward[i]` 有问题：读者可能正停在 target 上，或两个线程同时删 target。标准协议：

1. **标记（mark）**：把 target 最底层 `forward[0]` 的最低位标记为「已逻辑删除」（或单独 mark 位）。这一步用 CAS，保证只有一个线程标记成功。
2. **物理摘除**：从高层到低层，把各层前驱的 `forward[i]` 摘掉 target（CAS 重试）。任何线程在查找/插入中看到「已标记结点」都可以**帮助**完成摘除（helping），不必等原线程。
3. 被标记结点从查找路径上被跳过：查找时若发现后继已标记，就继续向右或 CAS 把前驱指到更后继。

标记存在的意义：**逻辑删除与物理删除分离**，使得「删除的线性化点」可以定在标记成功那一刻，物理摘除只是清理；读者在标记后仍可能短暂看到 target，但会跳过它，不破坏正确性。

### 2.4 不变量与线性化

- 每层链表关键字有序；
- 结点一旦发布，key/value 不变（改 value 需换结点或用原子引用）；
- 已标记结点最终会从所有层摘除；
- 查找的线性化点：到达第一个关键字 $\ge$ 目标的结点（或确认不存在）；插入：CAS 到第 0 层成功；删除：标记成功。

Python 中 GIL 让「指针赋值」原子性较强，但逻辑协议仍要正确，否则在多进程/去 GIL 方向会翻车。下面给出「锁分段」教学实现 + 无锁思路说明，保证可运行且体现协议要点。

## 三、形式化与数学基础

查找无锁，期望 $O(\log n)$，与单线程相同。插入/删除每层 CAS，成功概率高时期望 $O(\log n)$；高冲突下设重试上限或指数退避。

线性化证明思路（插入）：将成功 CAS 发布到第 0 层的时刻定为线性化点；此后所有查找都能看到新结点。失败重试不改变语义。

删除的线性化点是标记成功：此后任何查找都不再返回该 key；物理摘除只是让结构回到「不含已删除结点」的规范形。

内存回收（C++）：读者可能拿着旧指针，需要用 **hazard pointer** 或 **epoch-based reclamation** 延迟释放；Python/Java 有 GC，主要防的是逻辑悬垂而非 use-after-free。ABA 问题：CAS 比较指针时，内存被回收又分配出相同地址；用带版本号的指针或 hazard pointer 规避。

空间与 span（若需 rank）：并发维护 span 很难（跨层更新非原子），故 `ConcurrentSkipListMap` 不做 rank；需要并发 rank 时改用分段锁 + 树，或只读快照。

## 四、代码实现

先给一个**正确可运行的分段锁跳表**（Python，展示插入/删除/查找与标记删除思想），再给**无锁风格的 CAS 插入骨架**（教学向，Python 无真 CAS，用锁模拟 CAS 语义）。

```python
import random
import threading


class Node:
    __slots__ = ("key", "value", "forward", "marked")
    def __init__(self, key, value, level):
        self.key = key
        self.value = value
        self.forward = [None] * (level + 1)
        self.marked = False  # 逻辑删除标记


class ConcurrentSkipList:
    """细粒度锁跳表：一把大锁保护结构修改，读路径可共享（演示协议）。"""

    def __init__(self, p=0.5, max_level=16):
        self.p = p
        self.max_level = max_level
        self.head = Node(None, None, max_level)
        self.level = 0
        self.lock = threading.RLock()  # 工程可换 per-level 或 CAS
        self.size = 0

    def _random_level(self):
        lvl = 0
        while random.random() < self.p and lvl < self.max_level:
            lvl += 1
        return lvl

    def get(self, key):
        # 只读：不加写锁；Python 中指针读原子，结点初始化后不可变 key
        cur = self.head
        for i in range(self.level, -1, -1):
            while cur.forward[i] and not cur.forward[i].marked and cur.forward[i].key < key:
                cur = cur.forward[i]
        nxt = cur.forward[0]
        if nxt and not nxt.marked and nxt.key == key:
            return nxt.value
        return None

    def put(self, key, value):
        with self.lock:
            update = [None] * (self.max_level + 1)
            cur = self.head
            for i in range(self.level, -1, -1):
                while cur.forward[i] and cur.forward[i].key < key:
                    cur = cur.forward[i]
                update[i] = cur
            target = cur.forward[0]
            if target and target.key == key:
                # 已标记的结点先物理清理再插入（帮助删除）
                if target.marked:
                    self._unlink(target, update)
                else:
                    target.value = value
                    return
            lvl = self._random_level()
            if lvl > self.level:
                for i in range(self.level + 1, lvl + 1):
                    update[i] = self.head
                self.level = lvl
            node = Node(key, value, lvl)
            for i in range(lvl + 1):
                node.forward[i] = update[i].forward[i]
                update[i].forward[i] = node
            self.size += 1

    def remove(self, key):
        with self.lock:
            update = [None] * (self.max_level + 1)
            cur = self.head
            for i in range(self.level, -1, -1):
                while cur.forward[i] and cur.forward[i].key < key:
                    cur = cur.forward[i]
                update[i] = cur
            target = cur.forward[0]
            if not target or target.key != key:
                return False
            # 第一阶段：逻辑标记（线性化点）
            target.marked = True
            # 第二阶段：物理摘除
            self._unlink(target, update)
            self.size -= 1
            return True

    def _unlink(self, target, update):
        for i in range(self.level + 1):
            if update[i].forward[i] is target:
                update[i].forward[i] = target.forward[i]
        while self.level > 0 and self.head.forward[self.level] is None:
            self.level -= 1

    def keys(self):
        out = []
        cur = self.head.forward[0]
        while cur:
            if not cur.marked:
                out.append(cur.key)
            cur = cur.forward[0]
        return out


if __name__ == "__main__":
    csl = ConcurrentSkipList()
    errors = []

    def writer(start, step):
        for k in range(start, start + 200, step):
            csl.put(k, k * 2)
            if k % 3 == 0:
                csl.remove(k - 1)

    threads = [threading.Thread(target=writer, args=(i * 100, 2)) for i in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    ks = csl.keys()
    assert ks == sorted(ks), "keys must stay sorted"
    # 读路径一致性
    for k in ks:
        assert csl.get(k) == k * 2
    print("concurrent skiplist ok, size =", csl.size)
```

无锁 CAS 插入骨架（概念，展示重试与发布顺序）：

```python
# 教学骨架：真实系统用 atomic CAS（C++ atomic / Java AtomicReference）
# 步骤：1) 定位 update[]  2) 从低到高 CAS 挂接  3) 失败则重新定位
def cas_insert(head, key, value, random_level, cas_fn):
    while True:
        update, _ = find_update(head, key)
        lvl = random_level()
        node = Node(key, value, lvl)
        ok = True
        for i in range(lvl + 1):
            node.forward[i] = update[i].forward[i]
            if not cas_fn(update[i], i, update[i].forward[i], node):
                ok = False
                break  # 别的线程改了这一层，整体重试
        if ok:
            return
```

要点：CAS 期望值必须是「我们看到的旧后继」；失败说明并发修改，重新查找比盲目重试更稳。发布顺序：先初始化结点，再 CAS 指针（release/acquire）。

## 五、与其他技术对比

| 维度 | 并发跳表 | 全局锁红黑树 | 分段锁哈希 | 无锁哈希 | ConcurrentHashMap |
|------|----------|--------------|------------|----------|-------------------|
| 读路径 | 无锁 | 排队 | 段内共享 | 无锁 | 无锁读 |
| 写路径 | CAS/细锁 | 重 | 段锁 | CAS | CAS+锁 |
| 有序/范围 | 是 | 是 | 否 | 否 | 否 |
| 实现难度 | 中 | 中高 | 低 | 中 | 高 |
| 适用 | 有序并发 map | 低并发 | 高并发无序 | 高并发无序 | 高并发无序 |

需要**有序 + 并发**时，`ConcurrentSkipListMap` 几乎是 JVM 唯一标准答案；只需无序高并发则用 `ConcurrentHashMap`。数据库 memtable（LevelDB）用跳表也是为了并发写 + 顺序扫描。

## 六、常见误区

**误区一：删除直接物理摘除，不做标记。** 并发下两个线程同时删、或读者正走在目标结点上，会看到断裂链表或丢结点。标记把线性化点固定，摘除可帮助完成。

**误区二：读者也会走到已标记结点却不跳过。** 查找必须检查 `marked` 并继续向右/下降，否则返回已删数据。

**误区三：插入时先挂高层再挂第 0 层，却把高层当「已存在」。** 线性化点应是最底层发布；高层未挂好时读者可能多走一点，但不能把「只在高层」当成查找成功的依据。

**误区四：改结点 value 不加任何原子保护。** 并发读可能看到撕裂值；应原子引用或用不可变结点替换。

**误区五：C/C++ 中删除后立刻 free。** 读者可能还持有指针，必须 hazard pointer / epoch 回收，否则 use-after-free。

**误区六：以为 Python 有 GIL 就随便写。** GIL 只保证单字节码原子性，不保证「查找-插入」复合操作的事务性；协议错误仍会出现逻辑 bug。

## 八、面试题

**Q1：如何无锁实现跳表查找？**
A：查找只读指针，不加锁；写侧用 CAS 发布，并保证结点先初始化后发布（release/acquire），读者 acquire 后看到完整结点。删除用标记避免读者看到半删除状态。

**Q2：删除的标记阶段作用是什么？**
A：把删除的线性化点固定在「标记成功」；物理摘除可以被任何线程帮助完成。标记后查找跳过该结点，语义上元素已消失。

**Q3：为什么 `ConcurrentSkipListMap` 不支持 $O(\log n)$ 的 rank？**
A：span/排名统计需要跨层原子更新，并发下代价与复杂度高；该结构优先保证并发 map 语义。需要并发排名应另选结构。

**Q4：插入 CAS 失败怎么办？**
A：说明该层前驱的后继被别人改了；重新定位 `update[]` 再试，避免在过期视图上硬插。可加退避降低冲突。

## 九、演进与趋势

**JUC 无锁跳表**持续微调（索引结点、marked 位、base header）。**硬件事务内存（HTM）/ RCU** 用于读多写少场景，把读侧做到近零开销。**持久化并发跳表**用于 NVM（非易失内存），CAS 与崩溃一致性结合。**分片并发跳表**在分布式有序索引、时间线、限流中出现。语言层面，Rust 所有权 + crossbeam epoch 让安全无锁跳表成为可能。面试与工程都强调：**先明确线性化点与不变量，再谈锁粒度**。

## 十、小结

并发跳表的核心是「读无锁、写 CAS、删除标记 + 帮助摘除」：查找单向只读天然安全；插入逐层发布；删除把逻辑删除与物理清理分离。相比并发红黑树，跳表局部指针改写使其可实现、可证明、可维护，这也是 Java `ConcurrentSkipListMap` 与 LevelDB 并发 memtable 的选择逻辑。正确性依赖内存序与回收策略，细节比单线程多，但结构红利真实存在。
