# 跳表与平衡树对比

> 对应 Pugh 1990 论文中的对比讨论、Sedgewick《Algorithms》有序符号表章节，以及 Redis 设计者对 zset 选型的公开说明。

## 一、背景与挑战

「要用有序容器，选跳表还是红黑树？」这是系统设计与面试中的高频决策题。表面上二者复杂度都是 $O(\log n)$，功能都覆盖查找、插入、删除、有序遍历；真正拉开差距的是**实现复杂度、最坏行为、范围查询、并发改造、缓存行为**这五维。选错结构的代价真实存在：Redis 若用红黑树，`ZADD` 路径的旋转与并发控制会显著变复杂；C++ 标准库若用跳表，又可能在 adversarial 输入下踩到最坏退化。

平衡树一侧，AVL 严格平衡、查找略快但插入旋转多；红黑树平衡约束松、插入删除旋转少，是 `std::map`/`TreeMap` 的标准实现；B 树/B+ 树面向磁盘页，是数据库索引主流。跳表一侧，随机索引 + 链表，代码极短，天然有序扫描，天然易并发。

工程与面试都需要一张清晰的「取舍地图」：什么场景该坚持红黑树，什么场景跳表是更优解，以及为什么 Redis/LevelDB 这类系统偏爱跳表。本文从结构原理、复杂度、并发、真实系统三个层面把对比做实。

## 二、核心原理

**平衡的来源不同。** 红黑树用「着色 + 旋转」维护近似平衡：根到叶的黑高一致，最长路径不超过最短的两倍，树高 $O(\log n)$ 是**确定性**的。跳表用「随机层高」：每个结点独立晋升，高层索引密度按几何衰减，期望树高（层数）$O(\log n)$，是**概率性**的。

**有序操作的实现路径不同。** 查找：红黑树从根向下比较，左右分支；跳表从头结点最高层向右再下降，单向前进，分支少。插入/删除：红黑树要 BST 插入后再平衡（旋转/染色，情形多）；跳表只需维护每层前驱指针。范围查询：红黑树找到起点后走中序后继，指针跳跃、缓存不友好；跳表底层就是有序链表，顺序扫描极快，高层还能加速定位起点。

**最坏与平均。** 红黑树每次操作最坏 $O(\log n)$；跳表期望 $O(\log n)$，最坏（随机退化）$O(n)$，概率极低，可用 `max_level` 限制层高，使最坏层高有界，但单次查找横向仍可能较长。对实时性要求极高的系统，确定性更安心；对平均吞吐敏感的系统，跳表常数往往更好。

**并发。** 红黑树旋转会同时改动多个结点的父子指针，无锁化极难，实践中多用读写锁或分段锁。跳表插入只改局部前后继，删除可先逻辑标记，CAS 逐层发布，容易做到细粒度锁或无锁读。Java `ConcurrentSkipListMap` 就是无锁有序 map 的标杆。

**实现复杂度。** 红黑树完整实现通常数百行，且难以手写正确；跳表完整实现几十行，面试可写。这是 Pugh 论文的原始卖点：「概率性替代平衡树」。

## 三、形式化与数学基础

查找/插入/删除的复杂度对比：

| 操作 | 跳表 | 红黑树 | AVL |
|------|------|--------|-----|
| 查找 | 期望 $O(\log_{1/p} n)$ | 最坏 $O(\log n)$ | 最坏 $O(\log n)$ |
| 插入 | 期望 $O(\log_{1/p} n)$ | 最坏 $O(\log n)$ | 最坏 $O(\log n)$ |
| 删除 | 期望 $O(\log_{1/p} n)$ | 最坏 $O(\log n)$ | 最坏 $O(\log n)$ |
| 范围扫 $k$ 个 | $O(\log n + k)$ 期望 | $O(\log n + k)$ | $O(\log n + k)$ |
| 空间 | $O(n/(1-p))$ 指针 | $O(n)$ 结点（3 指针+色） | $O(n)$ |

更细的常数分析（$p = 1/2$）：

- 跳表查找期望比较次数约 $2 \log_2 n$（每层期望走 2 步）。
- 红黑树平均比较次数约 $1.0 \log_2 n$ 到 $2 \log_2 n$（取决于实现与分布），但含更多分支误预测。
- AVL 树查找最快（高度紧），插入旋转期望更多。

空间：跳表 $p = 1/2$ 时每结点期望 2 个 forward 指针，与红黑树（left/right/parent + color）相当；$p = 0.25$ 时指针更多。Redis 还要额外存 `span` 数组，空间略大，换来 `ZRank` 的 $O(\log n)$。

最坏概率：设 `max_level = L`，单次查找变慢的概率随 $n$ 指数衰减；但对手若能预测随机数（可构造坏序列），跳表可被恶意数据打穿。红黑树对输入分布免疫。对抗环境（如外部 key）应使用好的 RNG 或确定性结构。

均摊视角：红黑树旋转均摊 $O(1)$ 次/操作；跳表无再平衡，均摊就是单次期望，更平稳。

## 四、代码实现

用同一套接口实现跳表与「简化 BST + 排序数组」对照，测量有序性与范围查询；红黑树手写过长，此处用 Python `sortedcontainers` 思想的对照说明——重点是接口与调用方一致性。下面给可运行的跳表与一棵朴素 BST（作为对比基线），并演示范围扫描差异。

```python
import random
import time


# ---------- 跳表 ----------
class SkipNode:
    __slots__ = ("key", "forward")
    def __init__(self, key, level):
        self.key = key
        self.forward = [None] * (level + 1)


class SkipList:
    def __init__(self, p=0.5, max_level=16):
        self.p = p
        self.max_level = max_level
        self.head = SkipNode(None, max_level)
        self.level = 0

    def insert(self, key):
        update = [None] * (self.max_level + 1)
        cur = self.head
        for i in range(self.level, -1, -1):
            while cur.forward[i] and cur.forward[i].key < key:
                cur = cur.forward[i]
            update[i] = cur
        if cur.forward[0] and cur.forward[0].key == key:
            return
        lvl = 0
        while random.random() < self.p and lvl < self.max_level:
            lvl += 1
        if lvl > self.level:
            for i in range(self.level + 1, lvl + 1):
                update[i] = self.head
            self.level = lvl
        node = SkipNode(key, lvl)
        for i in range(lvl + 1):
            node.forward[i] = update[i].forward[i]
            update[i].forward[i] = node

    def range_query(self, lo, hi):
        cur = self.head
        for i in range(self.level, -1, -1):
            while cur.forward[i] and cur.forward[i].key < lo:
                cur = cur.forward[i]
        cur = cur.forward[0]
        out = []
        while cur and cur.key <= hi:
            out.append(cur.key)
            cur = cur.forward[0]
        return out


# ---------- 朴素 BST（对比基线，有序操作会退化） ----------
class BST:
    class N:
        __slots__ = ("key", "l", "r")
        def __init__(self, key):
            self.key = key
            self.l = self.r = None

    def __init__(self):
        self.root = None

    def insert(self, key):
        def dfs(node, key):
            if node is None:
                return self.N(key)
            if key < node.key:
                node.l = dfs(node.l, key)
            elif key > node.key:
                node.r = dfs(node.r, key)
            return node
        self.root = dfs(self.root, key)

    def range_query(self, lo, hi):
        out = []
        def dfs(node):
            if not node:
                return
            if lo < node.key:
                dfs(node.l)
            if lo <= node.key <= hi:
                out.append(node.key)
            if node.key < hi:
                dfs(node.r)
        dfs(self.root)
        return out


if __name__ == "__main__":
    n = 2000
    keys = random.sample(range(n * 10), n)
    sl, bst = SkipList(), BST()
    for k in keys:
        sl.insert(k)
        bst.insert(k)
    ks = sorted(keys)
    lo, hi = ks[n // 4], ks[3 * n // 4]
    assert sl.range_query(lo, hi) == bst.range_query(lo, hi)
    print("range query consistent, span =", len(sl.range_query(lo, hi)))
```

生产级红黑树请直接用标准库；对比实验更应关注：跳表代码量约为红黑树的十分之一，且范围扫描通过底层链表连续前进。

## 五、与其他技术对比

| 维度 | 跳表 | 红黑树 | AVL | B+ 树 | 跳表+哈希（Redis zset） |
|------|------|--------|-----|-------|------------------------|
| 查找 | 期望 $O(\log n)$ | 最坏 $O(\log n)$ | 最坏 $O(\log n)$ | $O(\log_B n)$ | 查成员 $O(1)$ |
| 范围查询 | 优秀 | 中序，缓存差 | 中序 | 优秀 | 优秀 |
| 按排名 | 需 span，$O(\log n)$ | 需 size 域，代码重 | 同左 | 叶链+计数 | span 天然 |
| 并发 | 易 | 难 | 难 | 页锁 | 易 |
| 实现难度 | 低 | 高 | 中高 | 高 | 中 |
| 最坏确定性 | 否（可截断层） | 是 | 是 | 是 | 否 |
| 典型用户 | Redis、LevelDB、Java SKL | C++ map、Java TreeMap | 语言运行时 | MySQL InnoDB | Redis zset |

**取舍总结：**

- 要**确定性最坏界**、标准库通用 map → 红黑树。
- 要**磁盘/页式**存储 → B+ 树。
- 要**内存索引 + 范围扫描 + 并发** → 跳表。
- 要**有序 + 按成员 O(1) 查** → 跳表 + 哈希（Redis zset 模式）。

## 六、常见误区

**误区一：「跳表是随机的，所以不能用于生产。」** 错。期望界 + 高概率界 + `max_level` 截断足以支撑生产；Redis、LevelDB、Java 并发库已大规模验证。真正的风险是 RNG 可预测被攻击，而非日常抖动。

**误区二：「红黑树范围查询一定比跳表快。」** 红黑树中序遍历指针跳跃，缓存局部性差；跳表底层连续扫描，常更优。当然，若范围极小而单点查找密集，二者接近。

**误区三：「跳表空间浪费。」** $p = 1/2$ 时约 2 指针/结点，与红黑树同量级。只有 $p$ 调得过大才浪费。Redis 加 `span` 是功能代价，不是结构浪费。

**误区四：「手写红黑树和跳表差不多难。」** 实际差距巨大。红黑树旋转情形多、边界多；跳表几十行可写对并测过。这也是面试常考跳表的原因——能考察指针与不变量，又不淹没在旋转分类里。

**误区五：忽略「按 rank/前驱后继」的需求。** 只比单点查找，二者都 $O(\log n)$；一旦要排名、范围、迭代器，跳表（带 span）与带 size 的树才显出设计差异。需求没想清就选型，容易返工。

## 八、面试题

**Q1：Redis zset 为什么用跳表不用红黑树？**
A：一是范围/排名操作跳表更自然（底层链表 + span）；二是跳表实现与调试远简单于红黑树，Redis 需要可审计的简单结构；三是并发与内存分配友好，跳表结点独立。红黑树理论最坏更好，但工程综合分跳表高。

**Q2：跳表最坏退化怎么办？**
A：概率极低；设 `max_level` 限制层高；对延迟敏感路径用确定性结构或定期重建；对抗输入用密码学随机数。

**Q3：需要「第 k 大」元素，选谁？**
A：都可做，但要维护子树 size（树）或 span（跳表）。Redis zset 用 span 实现 `ZRANK` $O(\log n)$；树需在旋转时维护 size，代码更繁。

**Q4：并发有序 map 选谁？**
A：Java 直接 `ConcurrentSkipListMap`；C++ 可分段锁跳表。红黑树无锁是研究级难题，工程不选。

## 九、演进与趋势

现代存储引擎常**分层组合**：内存 memtable 用跳表（LevelDB/RocksDB），磁盘用 SSTable + 稀疏索引或 B+ 树。并发方面，**无锁跳表 + RCU/HTM** 持续演进。**确定性跳表**（Munro 等）填补最坏界空白。**带持久化的跳表**用于 SSD 键值引擎。在分布式系统中，跳表还被用于**时间序列索引、限流滑动窗口、跳表作为 LSM 的可合并结构**。面试趋势上，「跳表 vs 红黑树」已从背题变成**结合真实系统（Redis/LevelDB/Java）讲取舍**的综合题。

## 十、小结

跳表与红黑树同为 $O(\log n)$ 有序结构：跳表以随机化换简单实现、范围扫描与并发优势，红黑树以旋转维护确定性最坏界。Redis zset、LevelDB memtable 证明了跳表在工程上的统治力；标准库与需要确定性时仍以红黑树/B+ 树为主。选型本质是：**在最坏确定性、实现复杂度、并发能力、范围查询之间做匹配**，而非谁「更快」。
