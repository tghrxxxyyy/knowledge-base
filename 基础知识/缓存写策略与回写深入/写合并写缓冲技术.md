# 写合并写缓冲技术

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第 2 章；Intel SDM Vol. 3A/3B 内存类型与写合并（WC）章节。

## 一、背景与挑战

即使缓存命中很快，「写」这条路依然可能成为瓶颈。写直达缓存每次 store 都要传到下级；写未命中、非临时写、写穿设备内存（MMIO）更是一次次慢速事务。若 CPU 必须等每次写被下级确认才继续，流水线会频繁停顿——store 指令本该是流水线里最便宜的操作之一，却被内存延迟拖到最慢。

朴素做法有两条死路。一是同步写穿：正确但极慢，现代核每周期可能提交 2 个 store，内存却只能每几十纳秒收一个事务。二是无限增大缓存：可写回缓存本来就能吸收写，但对必须写穿的场景（一致性要求、设备内存、非临时写）无能为力。工程上需要一个位于 CPU 与下级之间的异步队列——写缓冲（write buffer），并在其中做写合并（write merging / write coalescing），把多次小写合并成少数大事务。

写合并的价值在设备内存（framebuffer、GPU BAR）与非临时流式写上尤其明显：这些路径通常不可缓存，没有缓存行「先改后写」的合并机会，只能靠写缓冲把相邻地址的字/双字拼成一个缓存行级突发传输。面试中常问「写缓冲为什么要支持读穿透」「WC 内存类型是什么」「合并如何减少事务数」，考的是 store 提交路径的细节。

## 二、核心原理

**写缓冲（write buffer）**：一个（或多级）FIFO/可寻址队列，深度 $k$ 条。store 执行时把（地址，数据，掩码）放入缓冲即算「提交」，CPU 继续执行；后台按序（或按协议允许的序）把条目排空到 L1/内存。关键点：
- 缓冲满时反压 store（stall）。
- **读穿透（read forwarding）**：后续 load 若命中缓冲中同地址，必须转发新值，或先排空到该地址为止，绝不能读到下级旧值。
- **保序与弱序**：同地址必须先写后读可见；不同地址的可见顺序由内存模型（TSO/PSO/弱序）与 fence 约束。x86 TSO 要求 store 对其他核可见按 FIFO；ARM 允许重排但提供 STLR/DMB。

**写合并（write merging）**：当新 store 的地址与缓冲中已有条目同一合并单元（常为 64B 行或 32B/64B 合并窗口）时，把字节掩码或数据就地合并，从而一次排空覆盖多字。合并不改变程序语义（同地址顺序仍正确），但减少总线事务数与有效带宽压力。

**内存类型视角（Intel）**：WB 可缓存可合并；WC（write-combining）不可缓存但可写合并，典型用于 framebuffer、流式输出；UC（uncacheable）既不缓存也不合并，严格按序，用于 MMIO 寄存器。把设备内存设成 WC 而不是 UC，是显示驱动吞吐提升数量级的经典手段。

**不变量**：
1. 合并只发生在「无别名且无未满足依赖」的条目之间；
2. 转发后读到的必须是程序序上该地址的最新 store；
3. fence / serializing 指令必须排空相关缓冲后才继续。

## 三、形式化与数学基础

设 store 产生 $n$ 次写访问，地址分布中落入同一合并单元的连续写平均长度为 $\bar{m}$（写合并度），下级事务代价 $T_{txn}$，每次 store 独立事务代价 $T_{s}$。

无写缓冲（同步）时：

$$T_{total}^{sync} = n \cdot T_{s}$$

有写缓冲但无合并时，CPU 停顿只在缓冲满时发生，期望停顿：

$$T_{stall} \approx \max\left(0, n - k\right) \cdot \frac{T_{s}}{k} \cdot \alpha$$

其中 $\alpha$ 为反压系数。有合并时，下级事务数降为 $n/\bar{m}$：

$$T_{total}^{merge} \approx \frac{n}{\bar{m}} \cdot T_{txn} + T_{stall}$$

有效带宽：

$$B_{eff} = B_{peak} \cdot \frac{\text{有效字节}}{\text{总线字节}} \approx B_{peak} \cdot \frac{n \cdot w}{ (n/\bar{m}) \cdot B_{line} }$$

当 $w=4$B、$B_{line}=64$B、$\bar{m}=16$ 时，有效字节占比从 $4/64=6.25\%$ 提升到接近 100%。这就是 32 位像素逐点写 framebuffer 时，必须开 WC 否则带宽只有几分之一的原因。

再看缓冲深度：为隐藏延迟 $L$、写产生速率 $r$（事务/周期），由 Little 定律需要 $k \ge r \cdot L$。若 $r=2$、$L=50$，则 $k \ge 100$ 条，这解释了为何现代核的 store buffer / WC buffer 有数十到上百条目。

## 四、代码实现

下面模拟带合并的写缓冲：统计「无合并、逐条排空」与「按行合并后排空」的下级事务数，并演示读转发。

```python
"""写缓冲 + 写合并模拟器（含读转发）"""
from collections import OrderedDict

LINE = 64  # 合并单元：缓存行


class WriteBuffer:
    def __init__(self, depth: int = 16):
        self.depth = depth
        # 有序 dict: line_addr -> {byte_off: value}
        self.buf = OrderedDict()
        self.txns = 0       # 实际下级事务数
        self.stalls = 0

    def _line_addr(self, addr):
        return addr // LINE

    def store(self, addr: int, value: int, size: int = 4):
        line = self._line_addr(addr)
        bytes_now = sum(len(v) for v in self.buf.values())
        if line not in self.buf and bytes_now + size > self.depth * 8:
            self.flush_one()   # 缓冲将满：排空最老一条
            self.stalls += 1
        if line not in self.buf:
            self.buf[line] = {}
        for i in range(size):
            self.buf[line][(addr + i) % LINE] = (value >> (8 * i)) & 0xFF

    def load(self, addr: int, size: int = 4) -> int:
        """读穿透：优先从缓冲转发最新值"""
        line = self._line_addr(addr)
        if line in self.buf:
            data = self.buf[line]
            val = 0
            for i in range(size):
                off = (addr + i) % LINE
                if off in data:
                    val |= data[off] << (8 * i)
                else:
                    # 缓冲行内缺字节，需回读内存（此处简化为 0）
                    pass
            return val
        return 0  # 模拟：下级读

    def flush_one(self):
        if not self.buf:
            return
        self.buf.popitem(last=False)  # 整行合并后一次事务
        self.txns += 1

    def flush_all(self):
        while self.buf:
            self.flush_one()


def naive_txns(stores):
    """无合并：每次 store 一次 4B 事务，凑满 64B 行算 1 次行事务的朴素对照"""
    lines = set()
    for addr, _, _ in stores:
        lines.add(addr // LINE)
    return len(stores), len(lines)   # 事务数 vs 合并后行事务数


if __name__ == "__main__":
    # 顺序写一个 64B 行内的 16 个 int（像素流）
    stores = [(i * 4, 0xFF0000 + i, 4) for i in range(16)]
    raw, merged = naive_txns(stores)
    print(f"无合并事务={raw}, 按行合并事务={merged}, 压缩比={raw/merged:.1f}x")

    wb = WriteBuffer()
    for addr, val, sz in stores:
        wb.store(addr, val, sz)
    wb.flush_all()
    print("WriteBuffer 实际 txns =", wb.txns)  # 1
    assert wb.txns == 1

    # 读转发：写后立刻读同地址
    wb.store(1000, 0x12345678)
    got = wb.load(1000)
    print("read-forward got =", hex(got))
    assert got == 0x12345678
```

运行结果：16 次 4B 写被合并为 1 次 64B 行事务，压缩比 16×；写后读同地址由缓冲转发得到新值，验证了读穿透。

## 五、与其他技术对比

| 维度 | 无写缓冲同步写 | 写缓冲（不合并） | 写缓冲+写合并（WC） | 写回缓存 |
|------|---------------|-----------------|---------------------|----------|
| store 延迟 | 每次等于下级延迟 | 通常等于命中/入队 | 同左 | 等于 L1 命中 |
| 下级事务数 | n | n | n/合并度 | 脏行替换数 |
| 需要读转发 | 否 | 是 | 是 | 是（store-load） |
| 适用 | 简单核/MMIO 控制字 | 一般写穿 | framebuffer、NT store | 通用数据 |
| 顺序保证 | 最强 | FIFO 或可重排 | 合并窗口内可拼 | 行内无序，行间按协议 |

取舍：写合并降低事务数与带宽，但增加缓冲面积、转发逻辑与排序约束；UC 内存禁止合并以保证 MMIO 寄存器每个写都真实发生（例如写命令寄存器两次不能合并成一次）。

## 六、常见误区

1. **「写缓冲可以任意乱序提交」**——错。同地址必须保序；x86 TSO 下 store 对其他核按 FIFO 可见。乱序需要内存模型与 fence 明确允许，否则会出现 store-load 重排被程序观察到的 bug。
2. **「写合并会改变程序语义」**——正确实现不会。合并的是同一行内不同字节/字的写；同地址多次写保留最后值，且读转发保证及时可见。但对 MMIO 必须禁用合并，否则副作用寄存器被「合并」会出大事故。
3. **「有写缓冲就不需要管读」**——错。读穿透是写缓冲正确性的核心：load 必须查缓冲/转发，或强制排空，否则读到旧值。x86 的 store-to-load forwarding 就是硬件实现。
4. **「写合并只对非临时写有用」**——错。WB 内存的写分配与合并也在 L1/L2 行粒度发生；非临时写只是更依赖显式 WC 缓冲。
5. **「缓冲越深越好」**——深缓冲隐藏更多延迟，但增加面积、功耗、转发比较延迟，且崩溃/异常时未提交写的状态更复杂，需要精确异常支持。

## 八、面试题

**1. 写合并如何提升性能？**
答：把同一合并单元内的多次小写拼成一次大事务，减少总线事务数与有效带宽浪费。对顺序写 framebuffer 或非临时流式写，事务数可从 $n$ 降到 $n/\bar{m}$，吞吐接近峰值带宽。

**2. 写缓冲为什么必须支持读穿透（store-to-load forwarding）？**
答：因为缓冲里的写尚未到达下级/缓存，后续 load 若直接读下级会得到旧值，破坏程序语义。硬件必须把缓冲中同地址最新数据转发给 load，或先排空到该地址。

**3. UC 和 WC 内存类型的关键区别？**
答：UC 不可缓存、不可合并、严格按序，适合有副作用的 MMIO 寄存器；WC 不可缓存但可写合并，适合大块只写输出（如像素），吞吐远高于 UC。

**4. store buffer 满了会怎样？**
答：反压流水线，后续 store（以及依赖它的指令）停顿直到排空。因此缓冲深度需要匹配内存延迟与 store 速率（Little 定律 $k \ge rL$）。

## 九、演进与趋势

现代乱序核把写缓冲与 store buffer、store queue、内存顺序缓冲（MOB）融合：支持推测执行、部分写合并、跨行合并窗口，并与一致性协议联动（如 RFO 后直接在缓冲形成独占写）。非临时 store（`MOVNTDQ`、`_mm_stream_*`）显式走 WC 路径，被 glibc memcpy、BLAS、深度学习框架用作大张量落地。系统层，Linux 的 `ioremap_wc`、DPDK 的 hugepage 写合并映射、GPU/显示驱动都是 WC 的重度用户。CXL 与缓存一致性互连（CCIX、CXL.cache）把写合并与跨设备一致性结合；持久内存则要求缓冲在 fence/`sfence` 后有序持久，写缓冲语义延伸到持久域。RISC-V 的 Zicbop/Zicboz 与缓存提示指令也在标准化类似路径。

## 十、小结

写缓冲把同步写变成异步入队+后台排空，写合并再把同行小写拼成大事务，两者共同隐藏写延迟、提升有效带宽。正确性依赖读转发与保序约束，MMIO 需禁用合并。理解缓冲深度、合并度与事务数公式，就能解释从 framebuffer 到非临时写的性能差异。
