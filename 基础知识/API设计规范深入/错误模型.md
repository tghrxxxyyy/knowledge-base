# 错误模型

> 对应 Google API Design Guide、Microsoft REST API Guidelines。

## 一、背景与挑战
错误响应若不统一，客户端需针对不同格式写分支，难以自动化处理（重试、告警、降级）。

## 二、核心原理
使用恰当 HTTP 状态码（4xx 客户端错、5xx 服务端错）；响应体含机器可读 `code`、人类可读 `message`、可选 `details`；不为成功返回 200 却带 error 字段。

## 三、形式化 / 数学基础
错误响应结构 $E=\{status:int,\ code:string,\ message:string,\ requestId:string,\ details:[...]\}$。客户端以 $code$ 做条件分支，以 $requestId$ 关联日志追踪。

## 四、代码实现
```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "order 123 not found",
  "requestId": "req-abc",
  "status": 404
}
```

## 五、与其他技术对比
与"把所有错误包成 200 + 错误码"相比，语义状态码可被网关、缓存、监控直接利用。

## 六、常见误区
误区：用 200 承载业务失败，绕开 HTTP 语义。误区：泄露堆栈给客户端。

## 九、演进与趋势
Problem Details（RFC 7807，`application/problem+json`）成为标准化错误格式。

## 十、小结
状态码表意图、结构化错误体助自动化。
