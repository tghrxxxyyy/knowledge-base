# 错误模型

> 对应 Google API Design Guide「Errors」章节与 Microsoft REST API Guidelines，结合 RFC 7807。

## 一、背景与挑战

错误响应若不统一，客户端需针对不同格式写分支，难以自动化处理（重试、告警、降级、国际化）。更糟的是，许多服务把业务失败包成 HTTP 200 + 错误码，绕开了 HTTP 语义，使网关、缓存、监控无法正确识别成败，埋下运维隐患。

统一、机器可读的错误模型是 API 契约成熟度的标志：它让客户端用同一套逻辑处理所有错误，让中间件按状态码做缓存/重试策略，让可观测系统按 code 聚合问题，而不是在日志里翻字符串。

缺乏错误模型还会导致「错误信息泄露实现细节」——把堆栈、SQL 片段直接返回给客户端，既不安全也增加排障歧义。

## 二、核心原理

错误模型遵循三条原则：①用恰当的 HTTP 状态码表意图——4xx 表示客户端错误（可重试需修正），5xx 表示服务端错误；②响应体含机器可读 `code`（稳定字符串，如 ORDER_NOT_FOUND）、人类可读 `message`、可选 `details` 结构化定位信息；③附 `requestId` 关联服务端日志便于追踪。不应在成功状态码里夹带错误，也不应向客户端泄露堆栈。

从治理视角，错误还应分层：transport 层（连接失败）、协议层（4xx/5xx）、业务层（code），三者需在响应中与日志中一致映射，才能端到端定位。

关键要点：

- 错误模型三原则：恰当状态码、结构化响应体、requestId。
- 4xx 客户端错、5xx 服务端错，绝不 200 包业务失败。
- code 用稳定字符串枚举，message 人类可读，details 结构化定位。
- requestId 关联服务端日志，支撑端到端追踪。
- 错误应分层（transport/协议/业务）并一致映射。
- 错误体也需契约化与脱敏，避免 PII 外泄。

## 三、形式化与数学基础

错误响应结构化为一个元组：

$$
E = (\text{status} \in \mathbb{Z},\ \text{code} \in \Sigma^*,\ \text{message} \in \Sigma^*,\ \text{requestId} \in \Sigma^*,\ \text{details} \subseteq \mathcal{D})
$$

客户端以 code 做确定性分支，以 requestId 关联日志：

$$
\text{handle}(E): \text{action} = f(\text{code}(E)),\quad \text{trace} = \text{lookup}(\text{requestId}(E))
$$

重试决策依据状态码区间：可重试集 $R = \{408, 425, 429, 500, 502, 503, 504\}$，其余非幂等失败不自动重试。

## 五、与其他技术对比

| 方案 | 机器可读 | 网关友好 | 可重试判定 | 标准化 |
|------|----------|----------|------------|--------|
| 200 + 业务错误码 | 否 | 否 | 难 | 无 |
| 状态码 + 自定义体 | 中 | 中 | 中 | 弱 |
| RFC 7807 problem+json | 是 | 是 | 易 | 强 |
| gRPC status + details | 是 | 中 | 易 | 强 |

## 六、常见误区

误区一：用 200 承载业务失败——绕开 HTTP 语义，网关/缓存误判成功，重试与统计全乱。

误区二：泄露堆栈给客户端——暴露实现细节与潜在漏洞，且信息对调用方无意义。

误区三：code 用数字且不稳定——客户端无法做长期分支，应优先稳定字符串枚举。

误区四：message 含敏感信息——日志与错误体需脱敏，避免 PII 外泄。

误区五：只定义成功路径——错误 schema 同样要契约化，否则客户端无法预判。

## 七、与开源书·权威来源对应

Google Cloud API Design Guide「Errors」定义 code/message/details；Microsoft REST API Guidelines 的「Error condition responses」；RFC 7807 `application/problem+json` 提供标准问题详情格式；CS-Notes 汇总常见 HTTP 状态码语义。OpenAPI 3.1 强化错误响应 schema 校验，使错误契约可被机器验证。

## 九、演进与趋势

Problem Details（RFC 7807）成为跨语言标准错误格式；OpenAPI 3.1 强化错误响应 schema 校验；可观测性把 requestId 串起网关/服务/日志形成全链路追踪；错误分类向「用户可行动（actionable）」语义演进，使前端能据 code 给出精确引导而非笼统报错。

## 十、小结

状态码表意图、结构化错误体助自动化：用稳定 code 分支、用 requestId 追踪、用 RFC 7807 标准化，是 API 错误模型的成熟实践，也是契约化与可观测性的交汇点。
