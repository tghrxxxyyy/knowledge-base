# 版本管理

> 对应 Newman《Building Microservices》API 版本章，与 Fielding REST 实践及 JSON:API 规范。

## 一、背景与挑战

API 是契约，消费者众多且分布在不同版本、不同团队。破坏性变更（删字段、改语义、改类型）会令旧客户端崩溃，引发线上故障。版本管理的目标是在「持续演进」与「向后兼容」之间找到平衡：既不让接口僵化，又不破坏既有调用方。

从组织视角看，隔离策略往往由「合规等级 × 付费等级」共同决定：高合规（金融、医疗）即便付费低也倾向独占或命名空间隔离；低合规高付费可走共享池以降本。平台应把这一映射做成可配置策略，而非硬编码在路由逻辑里，以便随业务与法规变化动态调整。

## 二、核心原理

优先「向后兼容地演进」：加字段不删字段、不改字段语义、不收紧类型。必须破坏性变更时，采用显式版本化：URL 路径（`/v1/orders`）、请求头（`Accept: application/vnd.api.v2+json`）或媒体类型版本。无论哪种，都应给旧版本明确的弃用（deprecation）窗口与下线时间表，并通知消费者迁移。

从治理视角，版本还关系到「谁能改、改了通知谁」：版本变更应触发消费者影响分析，列出受影响调用方并主动沟通，而非静默发布。

关键要点：

- 优先向后兼容演进：加字段不删字段、不改语义、不收紧类型。
- 破坏性变更才显式版本化（URL 路径 / 请求头 / 媒体类型）。
- 旧版本须有弃用（deprecation）窗口与明确的下线（sunset）时间表。
- 版本变更应触发消费者影响分析并主动通知受影响调用方。
- 版本化不能替代契约测试，CI 持续校验才是防破坏的硬保障。
- 无版本 + 严格兼容 + Consumer-Driven Contracts 是新兴演进方向。

## 三、形式化与数学基础

兼容性判定：新契约 $C'$ 与旧 $C$ 向后兼容当且仅当旧客户端能解析新响应：

$$
\forall r \in C,\ \text{parse}_{old}(\text{response}_{C'}(r)) \neq \bot
$$

破坏性变更集 $B = \{c \in \Delta(C,C') \mid \neg \text{compatible}(c)\}$。触发版本号递增的充要条件是 $B \neq \varnothing$。弃用期满足：

$$
\text{deprecate}(v) \Rightarrow \exists\ \text{sunset}(v) > t_{\text{now}}
$$

## 四、代码实现

```http
GET /v1/orders          # 稳定旧版，字段最小化
GET /v2/orders          # 新版，新增字段、不改旧字段语义
Accept: application/json; version=2
```
```python
# 网关按 Accept 头路由到版本实现
def dispatch(req):
    ver = req.headers.get("Accept", "").split("version=")[-1]
    return handlers.get(ver, handlers["1"])(req)   # 默认 v1
```

| URL 路径 (/v1) | 高 | 高 | 否 | 是 |
| 请求头/媒体类型 | 低 | 低 | 是 | 中 |
| 无版本(兼容演进) | 高 | 高 | 是 | 是 |

## 六、常见误区

误区一：频繁大版本跳跃——制造迁移负担，应优先兼容演进。

误区二：只加版本不提供弃用与下线时间——消费者无从规划，易踩雷。

误区三：把版本塞进字段名（如 `name_v2`）——污染数据模型，增加理解成本。

误区四：认为版本化能替代契约测试——仍需 CI 防破坏。

误区五：旧版本无限期保留——运维与安全工作量随版本数线性增长，应按 sunset 计划回收。

补充误区：

- 误区六：媒体类型版本更易维护——手测困难且缓存键复杂，调试成本高。
- 误区七：所有字段都向后兼容——类型收紧、枚举变更同样破坏旧客户端。
- 误区八：契约测试能替代文档——二者互补，文档面向人、测试面向机。
- 误区九：版本号越高越先进——版本是兼容性信号，不代表功能优劣。

## 九、演进与趋势

Consumer-Driven Contracts（Pact）在 CI 中捕获破坏性变更，减少对显式版本的依赖；GraphQL 用 schema 演进（deprecation 标记）替代版本号；部分组织转向「无版本 + 严格向后兼容 + 契约测试」。版本管理正从「发布时贴标签」演化为「持续验证契约不被破坏」的工程能力。

## 十、小结

优先兼容演进，必要时显式版本并设弃用期；版本化只是手段，契约测试才是防止破坏式变更的硬保障，把「兼容性」交给 CI 持续守护而非依赖人工约定。
