# 版本管理

> 对应 Newman《Building Microservices》API 版本、REST 社区实践。

## 一、背景与挑战
API 是契约，消费者众多。破坏性变更会令旧客户端崩溃，需要向后兼容的演进策略。

## 二、核心原理
优先"向后兼容"地演进（加字段不删字段）。必须破坏性变更时，用 URL 路径（/v1/）、请求头（Accept: application/vnd.api.v2）或媒体类型版本化，并给弃用窗口。

## 三、形式化 / 数学基础
兼容性判定：新契约 $C'$ 与旧 $C$ 向后兼容当且仅当 $\forall request_r \in C,\ response(C',request_r)$ 能被旧客户端解析。破坏性变更集 $B$ 必须触发版本号递增。

## 四、代码实现
```http
GET /v1/orders          # 稳定旧版
GET /v2/orders          # 新版，新增字段
Accept: application/json; version=2
```

## 五、与其他技术对比
URL 版本直观易调试；媒体类型版本保持 URL 干净但难手测；无版本（仅兼容演进）最理想但难长期维持。

## 六、常见误区
误区：频繁大版本跳跃。误区：只加版本不提供弃用与下线时间。

## 七、与开源书 / 权威来源对应
Newman, S.《Building Microservices》"Versioning"；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"有哪些 API 版本化方式？如何做不破坏兼容的演进？"

## 九、演进与趋势
Consumer-Driven Contracts 在 CI 中捕获破坏性变更，减少显式版本需求。

## 十、小结
优先兼容演进，必要时显式版本并设弃用期。
