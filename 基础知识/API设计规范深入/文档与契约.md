# 文档与契约

> 对应 OpenAPI/Swagger、Consumer-Driven Contracts 实践。

## 一、背景与挑战
口头或静态文档易过时，前后端联调靠猜；API 变更缺乏机器可校验契约，破坏消费者。

## 二、核心原理
用 OpenAPI（Swagger）描述端点、参数、Schema，生成文档与客户端；用契约测试（Pact）让消费者定义期望，生产者在 CI 中验证，防止破坏式变更。

## 三、形式化 / 数学基础
契约 $K=(consumer, provider, interactions[\{request, response\}])$。验证即 $\forall i\in K,\ provider\ 能产出\ i.response$ 且匹配 schema。CI 失败即阻断合并。

## 四、代码实现
```yaml
openapi: 3.0.3
paths:
  /orders/{id}:
    get:
      responses:
        '200':
          description: ok
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
```

## 五、与其他技术对比
手写文档易腐；OpenAPI 单一事实源；契约测试把文档变为可执行断言，强于纯文档。

## 六、常见误区
误区：文档写完不更新。误区：有 OpenAPI 但不做契约测试，仍可破坏性变更。

## 七、与开源书 / 权威来源对应
OpenAPI Initiative 规范；Pact 文档；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"OpenAPI 与契约测试区别？为什么需要 Consumer-Driven Contracts？"

## 九、演进与趋势
API 网关自动从 OpenAPI 生成 mock；AsyncAPI 覆盖事件契约。

## 十、小结
机器可读契约 + 契约测试，使文档可执行、变更可防。
