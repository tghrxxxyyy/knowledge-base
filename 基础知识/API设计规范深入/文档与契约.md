# 文档与契约

> 对应 OpenAPI/Swagger 规范与 Consumer-Driven Contracts（Pact）实践，结合契约测试理念。

## 一、背景与挑战

口头或静态文档易过时，前后端联调靠猜；API 变更缺乏机器可校验契约，破坏消费者却无人知晓。当提供方与消费方团队解耦、独立发布时，问题往往在线上才暴露。文档与契约的核心诉求是：单一事实源、可机器校验、变更可防破坏。

从组织视角，契约还是「团队间信任的载体」：消费方不再需要「问提供方要字段」，提供方变更也能被自动化守护，减少跨团队扯皮与回归事故。缺乏契约的架构在微服务规模下必然走向混乱。

## 二、核心原理

用 OpenAPI（Swagger）以声明式描述端点、参数、请求/响应 schema、鉴权与错误，从而自动生成文档、客户端 SDK 与 mock server。更进一步，用契约测试（Pact）让消费者定义期望交互（请求+预期响应），提供方在 CI 中验证自己能满足这些期望，破坏式变更当场失败、阻断合并。契约把「文档」升级为「可执行断言」。

从落地视角，契约测试应区分「提供方契约」与「消费方期望」：消费方写期望、提供方跑验证，二者在 Pact Broker 中匹配，形成双向守护而非单向约束。

## 三、形式化与数学基础

契约定义为一组交互的集合：

$$
K = (c, p, \{\, (req_i, resp_i) \mid i \in I \,\})
$$

其中 $c$ 为消费者、$p$ 为提供者。验证即：

$$
\forall i \in I,\ \text{match}\big(\text{provider}(req_i),\ resp_i\big) = \text{true}
$$

再扩展为 schema 匹配（结构兼容、不缺字段）。CI 判定：

$$
\text{pass} \iff \bigwedge_i \text{match}_i
$$

任一不匹配即阻断合并，防止破坏式变更进入生产。

## 四、代码实现

```yaml
openapi: 3.0.3
paths:
  /orders/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: ok
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
```
```python
# Pact 消费者定义期望（示意）
(pact
 .upon_receiving("get order")
 .with_request("GET", "/orders/123")
 .will_respond_with(200, body={"id": "123", "status": "paid"}))
```

## 五、与其他技术对比

| 方式 | 单一事实源 | 可执行 | 防破坏 | 维护成本 |
|------|------------|--------|--------|----------|
| 手写文档 | 否 | 否 | 否 | 高 |
| OpenAPI | 是 | 弱 | 否 | 中 |
| 契约测试(Pact) | 是 | 强 | 是 | 中 |
| OpenAPI+契约测试 | 是 | 强 | 是 | 中高 |

## 六、常见误区

误区一：文档写完不更新——应随代码生成或 CI 校验，否则迅速腐化。

误区二：有 OpenAPI 但不做契约测试——提供方仍可破坏性变更，文档只是「看起来对」。

误区三：契约只覆盖成功路径——异常与错误 schema 同样要约定，否则消费方错误处理失配。

误区四：把内部字段暴露给消费者——契约应按消费方需要裁剪，遵循最小暴露原则。

误区五：只在提供方跑测试——必须由消费方定义期望，否则守护方向错。

## 七、与开源书·权威来源对应

OpenAPI Initiative 规范定义文档 schema；Pact 官方文档给出 Consumer-Driven Contracts 流程；Newman《Building Microservices》讨论契约与演进；AsyncAPI 覆盖事件/消息契约；CS-Notes 汇总 API 治理实践。API 网关可自动从 OpenAPI 生成 mock 与文档，使「文档即服务」成为可能。

## 九、演进与趋势

API 网关自动从 OpenAPI 生成 mock 与文档；AsyncAPI 覆盖事件驱动契约；契约被纳入平台工程「黄金路径」，与 CI/CD、可观测性联动形成 API 全生命周期治理。契约仓库（contract registry）逐步成为组织级资产，跨团队复用而非重复定义。

## 十、小结

机器可读契约 + 契约测试，使文档可执行、变更可防；OpenAPI 提供单一事实源，契约测试把它变为不可破坏的硬保障，是解耦团队间 API 协作的基石。
