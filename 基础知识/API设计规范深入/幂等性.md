# 幂等性

> 对应 RFC 7231 Section 4.2.2（Idempotent Methods）、REST 语义与支付系统设计实践（参考 Stripe Idempotent Requests）。

## 一、背景与挑战

网络不可靠：客户端重试、网关重发、用户重复点击都会让同一操作执行多次。在支付、下单、转账等场景，重复执行会造成重复扣款、重复发货等严重后果。幂等性正是为「安全重试」而生——让一次与多次执行效果相同，是分布式系统正确性的基石。

从治理视角，幂等还是「系统韧性」的一部分：没有幂等，任何重试策略都不敢启用，故障恢复只能靠人工介入，MTTR 被显著拉长。幂等让系统敢于自动重试，是自动化运维的前提。

## 二、核心原理

幂等操作满足「执行一次与执行多次效果相同」。HTTP 语义上 GET/PUT/DELETE 为幂等方法（可安全重试），POST 非幂等（重试可能重复创建）。对非幂等的写操作，通过「幂等键（Idempotency-Key）」使重试安全：服务端记录 `key -> 首次结果`，收到相同 key 时直接返回首次结果而非重复执行。常与分布式锁、去重表、TTL 配合。

从落地视角，幂等键应由客户端生成并持久化（如前端存于本地、支付 SDK 一次性生成），服务端以「首次写入成功」作为去重判据，配合唯一索引防止并发双写。

关键要点：

- 幂等满足「执行一次与多次效果相同」，是安全重试的前提。
- GET/PUT/DELETE 幂等，POST 非幂等需幂等键保护。
- 幂等键由客户端生成，服务端记录 key→首次结果。
- 并发同 key 需锁或原子「不存在则写入」防双写。
- 幂等键须带 TTL，避免存储无限增长与旧键复用。
- 幂等与事务互补：前者保重复执行一致，后者保部分失败回滚。

## 三、形式化与数学基础

函数 $f$ 幂等当且仅当：

$$
\forall x,\ f(f(x)) = f(x)
$$

服务端维护映射 $S: \text{key} \to \text{result}$。处理请求 $(k, op)$：

$$
\text{handle}(k, op) = \begin{cases}
S[k] & k \in \text{dom}(S) \quad \text{（已处理，返回首次结果）} \\
S[k] \leftarrow \text{exec}(op) & \text{otherwise}
\end{cases}
$$

并发安全需满足：对同一 $k$ 的并发请求仅执行一次 $\text{exec}$，即用锁或原子「不存在则写入」保证。

## 四、代码实现

```http
POST /payments
Idempotency-Key: 9f1c-4a2b-88de
Content-Type: application/json

{ "amount": 100, "currency": "CNY" }
```
```python
def pay(tenant, key, payload):
    if store.exists(key):                  # 已处理，直接返回
        return store.get(key)
    with lock(key):                        # 并发去重
        if store.exists(key):
            return store.get(key)
        result = do_pay(payload)           # 仅执行一次
        store.put(key, result, ttl=86400)  # 带 TTL，避免无限增长
        return result
```

## 五、与其他技术对比

| 去重层级 | 防重范围 | 实现位置 | 局限 |
|----------|----------|----------|------|
| 客户端禁用按钮 | 仅手抖 | 浏览器 | 防不了网络重试 |
| 网关幂等中间件 | 请求级 | 入口 | 需统一 key 规范 |
| 服务端幂等键 | 业务级 | 服务 | 需存储与 TTL |
| 数据库唯一约束 | 数据级 | DB | 仅防最终重复写 |

## 六、常见误区

误区一：仅在客户端禁用按钮——防不了网络重试与网关重发，必须服务端兜底。

误区二：幂等键未设 TTL——存储无限增长，且旧 key 可能被复用导致串结果。

误区三：把用户 ID 当幂等键——同一用户多次合法操作会互覆盖，应以「一次业务动作」为单位。

误区四：忽略并发双写——无锁时并发同 key 仍可能执行两次，需原子去重或唯一索引。

误区五：认为幂等等于事务——幂等关注「重复执行结果一致」，事务关注「部分失败回滚」，二者互补而非替代。

## 七、与开源书·权威来源对应

RFC 7231 Section 4.2.2 定义 Idempotent Methods；Stripe API「Idempotent Requests」以 Idempotency-Key 头保障重试安全；Newman《Building Microservices》讨论重试与去重；分布式事务文献给出锁/去重表模式；数据库唯一索引是最终防重复写的一道防线。

## 九、演进与趋势

网关层统一幂等中间件成为标准实践；结合分布式锁、去重表与唯一索引形成多层防护；事件溯源（Event Sourcing）以「命令幂等」原生避免重复副作用；服务网格可自动注入幂等头，使业务代码无需关心重试安全。幂等正从「手写逻辑」走向「基础设施能力」。

## 十、小结

用幂等键把非幂等写变为可安全重试的操作，并配合锁/TTL/唯一约束，是支付与下单等高后果场景不可或缺的正确性保障，也是系统敢于自动重试、实现韧性的前提。
