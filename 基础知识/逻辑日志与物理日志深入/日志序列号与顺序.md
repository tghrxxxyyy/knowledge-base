# 日志序列号与顺序

> 对应 Mohan 1992 ARIES 的 LSN 设计与 InnoDB 实现，参考 Silberschatz《OSC》第17章。

## 一、背景与挑战

崩溃恢复、回滚、复制位点，所有依赖日志的机制都需要一个「全局有序的标尺」：既能确定「这条记录该不该重放」，也能在分布式场景标记「复制到哪了」。这个标尺就是 LSN（Log Sequence Number）。

没有全序的 LSN，重放就会重复、遗漏或乱序，恢复无从谈起。LSN 还必须与页、事务、检查点三类元数据联动，才能支撑完整的恢复协议，否则恢复会卡在「该从哪开始」。

## 二、核心原理

LSN 单调递增，常见实现为单递增整数，或 `(文件号, 偏移)` 组合以便定位日志物理位置。每次写日志追加新 LSN。关键结构：

- **页头 `page_lsn`**：该页最后被哪个 LSN 修改。
- **事务 `last_lsn`**：指向该事务最近一条日志，回滚时沿链表逆序走。
- **检查点 `redo_lsn`**：最早脏页对应的 LSN，恢复可从这里开始而非日志头。

PostgreSQL 的 LSN 为 8 字节 `(时间线, 段号, 段内偏移)`，既标识顺序又定位 WAL 文件；流复制用主从 LSN 差衡量延迟。时间线（timeline）还用于区分「恢复后新分支」，避免把旧归档误用到新时间线。

## 三、形式化与数学基础

日志形成全序：

$$ LSN_1 < LSN_2 < \dots < LSN_n $$

恢复时对页 $p$ 的重放条件：

$$ LSN_{record} > page\_lsn(p) $$

即只应用比页当前更新更「新」的记录。事务回滚沿 `last_lsn` 逆序，每条 Undo 产生 CLR（补偿记录）带新 LSN，使撤销可重放而不重复。

分布式场景下，单点 LSN 被**混合逻辑时钟（HLC）**取代，以支持跨节点因果顺序：

$$ HLC = (pt, l), \quad pt \ge \text{physical\_time} $$

提供跨节点的全序或可比较偏序，解决多分片「谁先谁后」难题。

## 四、代码实现

```sql
-- InnoDB 暴露 LSN 相关状态
SHOW STATUS LIKE 'Innodb_os_log_written';   -- 已写日志字节数
SHOW ENGINE INNODB STATUS;                  -- 含 Log sequence number / Log flushed up to

-- PostgreSQL 查看复制位点
SELECT pg_current_wal_lsn();                -- 当前写位点
SELECT pg_last_wal_replay_lsn();            -- 从库已重放位点
-- 延迟 = pg_current_wal_lsn() - pg_last_wal_replay_lsn()
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), pg_last_wal_replay_lsn());
```

## 五、与其他技术对比

| 系统 | LSN 形态 | 用途 |
| --- | --- | --- |
| InnoDB | 递增整数 | 恢复重放、undo 链表 |
| PostgreSQL | 8 字节 (段, 偏移) | 崩溃恢复 + 流复制位点 |
| 分布式 | HLC / 全局事务号 | 跨节点因果顺序 |

单点 LSN 适合单机恢复；跨节点需逻辑时钟或共识序，否则无法在分片间比较「谁先谁后」，复制一致性与线性一致性读都无从保证。

## 六、常见误区

- 认为 LSN 是时间戳：它是日志位置而非墙上时间，不能当时间用。
- 认为新 LSN 一定对应新事务：同一事务会产生多个 LSN（每行修改一条）。
- 认为 LSN 全局唯一即可：还需全序以支持「大于 / 小于」比较与位点推进。
- 认为 LSN 跨时间线连续：PostgreSQL 时间线切换后 LSN 解释需结合时间线 ID。

## 八、面试题

- 如何用 LSN 避免重复重放？答：比较记录 LSN 与页 `page_lsn`，仅应用更新的。
- CLR 作用？答：标记已撤销，防恢复中断后重复 Undo。
- PostgreSQL 复制延迟怎么算？答：`pg_current_wal_lsn()` 减 `pg_last_wal_replay_lsn()`，用 `pg_wal_lsn_diff` 量化。
- 为何用 (段, 偏移) 表达 LSN？答：既保全序又能直接定位 WAL 文件与偏移，便于位点管理。

## 九、演进与趋势

物理 LSN 在分布式事务与一致性快照中被逻辑全局事务号 / HLC 取代，以支持跨分片顺序与线性一致性读；时间戳与 LSN 融合（如 LSN-by-clock）简化跨系统位点对齐，使恢复、复制、CDC 共用一套序。

在复制与一致性读场景中，LSN 还承担着「可见性边界」的角色：从库上一个事务要等到其依赖的所有 WAL 都已重放（即本地 LSN 追上所需位点）才能被读取，否则会读到陈旧数据。

PostgreSQL 的热备反馈（hot standby feedback）机制正是用从库当前可见的最老事务 LSN 回告主库，让主库推迟 vacuum 那些从库仍需要的旧版本，避免从库因旧版本被清而报「snapshot too old」。

工程上监控 LSN 应包含三项：主库写入位点、从库接收位点、从库重放位点。接收落后说明网络或主库产出快，重放落后说明从库 CPU 不足——二者成因不同，须分开排查。

最后注意，LSN 是单调递增的「逻辑位置」而非容量占用；日志文件循环复用不意味着 LSN 回绕，恢复与复制始终以 LSN 大小比较为准，这点对理解归档保留策略至关重要。

## 十、小结

LSN 提供日志全序，是重放、回滚、复制位点的统一坐标；理解其与 `page_lsn`、CLR、检查点的关系，即掌握恢复秩序的钥匙，也是排查复制延迟与恢复异常的起点。
