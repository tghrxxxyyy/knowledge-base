# 重做与撤销日志角色

> 对应 Mohan 1992 ARIES 的 Redo/Undo 与 Gray 1978 系统，参考 Silberschatz 第17章。

## 一、背景与挑战
事务的原子性与持久性需要两类相反方向的日志：Redo 保证已提交修改不丢，Undo 保证未提交修改可取消。混淆二者角色是理解恢复的常见障碍。

## 二、核心原理
Redo 日志（CLR 与更新记录）在崩溃后重放已提交（及部分未提交）修改，使数据库回到崩溃前状态。Undo 日志（及其自身的补偿记录）回滚未提交事务，释放其持有的锁与修改。ARIES 先全 Redo 再按事务逆序 Undo。

## 三、形式化与数学基础
恢复后满足：
$$ \forall committed\; T: effects(T) \text{ 全部存在 (Redo) } $$
$$ \forall uncommitted\; T: effects(T) \text{ 全部撤销 (Undo) } $$
即保证原子性（all-or-nothing）与持久性。

## 四、代码实现
```sql
-- InnoDB 中 undo 段与 redo 并存
SHOW VARIABLES LIKE 'innodb_undo%';
SHOW VARIABLES LIKE 'innodb_log_file%';  -- redo
```

## 五、与其他技术对比
LSM-tree 几乎无需传统 Undo，因写入不可变、未提交仅存内存 memtable，丢弃即可。但仍有 WAL 做 Redo。列式/分布式系统用 MVCC 替代部分 Undo 角色。

## 六、常见误区
认为 Undo 用于「回滚已提交」——Undo 只针对未提交事务。认为 Redo 只重做已提交——ARIES 先重做全部再 Undo 未提交，逻辑更稳。

## 七、与开源书/权威来源对应
Mohan 1992 ARIES 的 Redo/Undo 章节；Silberschatz 17.4「Recovery Algorithm」。

## 八、面试题
问：Redo 与 Undo 分别保证什么？答：Redo 保持久性（已提交不丢），Undo 保原子性（未提交回滚）。

## 九、演进与趋势
并行 Undo、Undo 表空间分离（如 InnoDB 独立 undo tablespace）提升大事务回滚与 purge 效率。

## 十、小结
Redo/Undo 分别守护持久性与原子性，是事务 ACID 的日志双翼。
