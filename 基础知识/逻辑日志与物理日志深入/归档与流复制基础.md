# 归档与流复制基础

> 对应 PostgreSQL 官方文档「Continuous Archiving and Point-in-Time Recovery」与「Streaming Replication」，参考 Kleppmann《DDIA》第3章。

## 一、背景与挑战

单机数据库的崩溃恢复只能保证「进程 / 机器重启后不丢已提交数据」，但无法应对两类更严重的场景：一是磁盘损坏或机房故障，需要把数据复制到异地；二是误删表或写入脏数据，需要回到过去的某个时间点。

日志归档（archiving）与流复制（streaming replication）正是分别解决「按时间点恢复（PITR）」与「跨节点高可用」的两大基石，二者都建立在「持续地把日志传输出去」之上。

缺少它们，数据库只能算「单机可恢复」，而非「生产高可用」。在合规要求（如留存 7 年审计日志）下，归档也是满足监管的必要手段。

## 二、核心原理

**归档（archive）** 指数据库把写好的 WAL/redo 段持续拷贝到外部存储（如对象存储、NFS）。配合一次「基础备份」（base backup，即对数据文件的快照），就可以做 PITR：先恢复基础备份，再顺序回放归档日志直到目标时间点或目标 LSN，从而精确到「删表前的那一秒」。

**流复制** 让一个从库（replica）通过 TCP 日志流实时追赶主库。主库每产生一段 WAL 就推送给从库，从库立即重放，因此延迟通常在毫秒到秒级。复制可配为同步（sync，提交需等从库落盘）或异步（async，主库提交即可，从库可能滞后）。

同步保证不丢已提交事务，但增加写延迟；异步反之。还可配置同步从库数量（如 `synchronous_standby_names` 要求至少 N 个确认），在可用性与性能间调档。

## 三、形式化与数学基础

PITR 可恢复性需满足：存在基础备份起点 $B$ 与连续归档日志覆盖到目标时间 $t$：

$$ backup\_start \le t \le last\_archive\_lsn\_time $$

复制延迟以 LSN 差度量：

$$ lag = LSN_{primary} - LSN_{replica} $$

同步复制的提交成功条件：

$$ LSN_{replica\_flush} \ge LSN_{commit} $$

即至少一个同步从库已刷盘该事务的日志，主库才能向客户端返回成功。当要求 $quorum$ 个从库确认时，条件变为第 $quorum$ 小的 $LSN_{replica}$ 满足上式。

```sql
ALTER SYSTEM SET archive_mode = 'on';
ALTER SYSTEM SET archive_command = 'cp %p /archive/%f';  -- %p 源路径, %f 文件名
SELECT pg_reload_conf();

-- 生成基础备份（命令行 pg_basebackup）
-- pg_basebackup -D /backup/2026 -Ft -P

-- 从库 standby：放置 standby.signal 并配置主库连接
primary_conninfo = 'host=primary port=5432 user=replicator'
primary_slot_name = 'pg_standby_1'
-- 同步复制要求至少 1 个从库确认

```

## 五、与其他技术对比

| 能力 | MySQL | PostgreSQL |
| --- | --- | --- |
| 增量备份载体 | binlog | 归档 WAL |
| 复制基础 | binlog 流 | WAL 流 |
| PITR 组合 | 全量 + binlog | 基础备份 + 归档 WAL |
| 半同步 | 半同步复制 | 同步流复制（可设 quorum） |

二者思路一致：逻辑/物理日志外流 + 重放。差异在日志类型（逻辑 binlog vs 物理 WAL）与复制协议细节。MySQL 半同步强调「至少一个 ACK」，PostgreSQL 同步复制可灵活设确认副本数。

## 六、常见误区

- 认为有副本就万无一失：异步副本存在延迟窗口，主库宕机可能丢失最近若干已提交事务。
- 认为归档可随意删除：PITR 窗口依赖「最早保留的归档段」，删太早则无法恢复到更早点。
- 混淆基础备份与归档：仅有归档没有基础备份，重放要从空库开始，不现实。
- 认为同步复制零风险：同步复制在从库全部不可用时会导致主库写阻塞（不可用而非丢数据）。

## 八、面试题

- PITR 需要什么？答：一次基础备份 + 连续的归档日志，恢复到目标 LSN/时间点。
- 同步 vs 异步复制？答：同步不丢已提交但写延迟高；异步反之，有丢数据风险窗口。
- 复制延迟怎么度量？答：对比主从 LSN 位点差，或用秒级时间差。
- 同步从库全挂会怎样？答：主库写阻塞（可用性下降）而非丢数据，这是有意为之的安全取舍。

## 九、演进与趋势

日志即服务、跨地域多副本（在 Raft/Paxos 共识之上做复制）、以及基于 WAL 的 CDC 数据管道，成为云数据库标准能力。逻辑复制让单表级订阅成为可能，进一步解耦备份与复制，使一份日志同时服务容灾、分析、审计。

在工程落地时，归档与流复制还需关注几个运维细节：归档命令必须幂等且能感知失败，否则一段日志拷贝失败会导致 PITR 链条断裂而难以察觉。

从库可分为「热备」（同步接收、可升主）与「只读副本」（承接查询、降低主库压力）两类角色，二者对延迟的容忍度不同，应分别设阈值与告警。

对于跨地域容灾，建议在异地再保留一份归档与至少一个异步副本，使「机房级故障」也可恢复；此时 RPO 由归档频率决定，RTO 由基础备份大小与重放速度决定。

备份策略上，基础备份应定期（如每周）刷新，避免恢复时需重放过长的归档；并用 `pg_verifybackup` / `mysqlbackup validate` 之类工具校验备份可用性，防止「备份成功但恢复失败」。

## 十、小结

归档与流复制把单机日志能力延伸到备份与高可用：归档支撑 PITR，流复制支撑实时容灾，是生产数据库的必备底座；二者都依赖「日志持续外流 + 顺序重放」这一统一范式，同步/异步则在一致性与延迟间权衡。
