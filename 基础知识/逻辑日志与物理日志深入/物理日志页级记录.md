# 物理日志页级记录

> 对应 MySQL InnoDB redo log（物理/生理日志）与 ARIES physiological logging，参考 InnoDB 官方文档。

## 一、背景与挑战
InnoDB 的 redo log 以页为单位记录变更，既能精准重放又不必到字节级（生理日志折中）。理解其格式对排查恢复与写入放大很重要。

## 二、核心原理
redo 记录包含表空间 ID、页号、以及页内改动的「重做动作」（如插入记录、更新某字段、分裂页）。它不依赖 SQL 语义，只描述页如何变更，因此崩溃恢复速度快、确定性强。redo 以固定大小循环文件（如 ib_logfile0/1）顺序写入。

## 三、形式化与数学基础
LSN（Log Sequence Number）单调递增标记日志位置：
$$ LSN_{current} = LSN_{prev} + record\_size $$
页头部存 `page_lsn` 表示最后修改该页的 LSN，恢复时仅重放 $LSN > page\_lsn$ 的记录，避免重复应用。

## 四、代码实现
```sql
SHOW VARIABLES LIKE 'innodb_log_file_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
-- 1 表示提交时 fsync redo，保证持久性
```

## 五、与其他技术对比
PostgreSQL WAL 也是物理（含块级前像），并支持 `FPI`（full page image）在检查点后首次修改页时记录整页，防止部分写（torn page）。InnoDB 靠 doublewrite buffer 解决部分写，而非 FPI。

## 六、常见误区
认为 redo 记录整页——多为增量动作，仅必要时（如双写/整页）记录全页。认为 redo 可无限增长——循环覆盖，受文件大小限制。

## 七、与开源书/权威来源对应
InnoDB 官方「Redo Log」文档；Mohan 1992 ARIES physiological logging。

## 八、面试题
问：LSN 在恢复中作用？答：比较记录 LSN 与页 page_lsn，只重放更新的部分。问：innodb_flush_log_at_trx_commit=2 风险？答：提交仅写 OS 缓存，宕机可能丢已提交事务。

## 九、演进与趋势
 redo 格式向压缩、并行写、与 NVMe 协同优化，降低 fsync 开销。

## 十、小结
物理/生理页级日志以精准与速度守护崩溃恢复，LSN 是其有序重放的标尺。
