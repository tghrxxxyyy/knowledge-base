# 物理日志页级记录

> 对应 MySQL InnoDB redo log（物理/生理日志）与 Mohan 1992 ARIES physiological logging，参考 InnoDB 官方文档。

## 一、背景与挑战

InnoDB 的 redo log 是崩溃恢复的核心：它必须足够「精准」以快速重放，又不能细到逐字节（那样日志会爆炸）。InnoDB 采用**生理日志（physiological logging）**——以「页」为单位描述变更：记录表空间 ID、页号、以及页内改动的「重做动作」，在「精准」与「紧凑」之间折中。

理解其格式对排查恢复、写入放大与部分写问题都很关键，也帮助理解为何某些 DDL/写入比预期更慢。某些「小更新」实际会触发页分裂、索引调整，redo 体积远超预期。

## 二、核心原理

redo 记录不依赖 SQL 语义，只描述「某页如何被修改」：例如「在页 (space_id, page_no) 偏移 off 处插入一条记录」「更新某字段为 v」「页发生分裂」。恢复时只需按页重放这些动作，无需重新执行 SQL，因此确定性强、速度快。

redo 以固定大小的循环文件（如 `ib_logfile0/1`）顺序写入；写满后覆盖最旧段。部分写（torn page，页只写了一半就断电）由 **doublewrite buffer** 解决：先写双写区再写原页。

redo 还按 Mini-Transaction（MTR）分组，保证一组页修改的原子性，避免中途崩溃留下半成品。MTR 是「物理事务」的最小单位，跨页修改要么全做要么全不做。

## 三、形式化与数学基础

LSN（Log Sequence Number）单调递增标记日志位置：

$$ LSN_{current} = LSN_{prev} + record\_size $$

每个页头部存 `page_lsn`，表示最后修改该页的 LSN。崩溃恢复时，仅重放满足：

$$ LSN_{record} > page\_lsn(p) $$

的记录，已应用的跳过，避免重复与损坏。检查点推进时将 `checkpoint_lsn` 写入日志头，恢复只需从最近检查点之后开始，缩短重放窗口。

## 四、代码实现

```sql
-- 查看 redo 配置
SHOW VARIABLES LIKE 'innodb_log_file_size';        -- 单文件大小
SHOW VARIABLES LIKE 'innodb_log_files_in_group';    -- 文件个数
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; -- 1=提交 fsync
SHOW VARIABLES LIKE 'innodb_doublewrite';          -- 双写开关

-- innodb_flush_log_at_trx_commit 取值含义：
-- 1 每次提交 fsync（最持久）；2 写 OS 缓存；0 每秒 fsync
```

## 五、与其他技术对比

| 机制 | PostgreSQL WAL | InnoDB redo |
| --- | --- | --- |
| 日志粒度 | 物理/块级 | 生理（页级动作） |
| 部分写防护 | FPI（检查点后首改记整页） | doublewrite buffer |
| 循环写 | 段回收 | 循环文件 |

二者都偏物理，但防部分写手段不同：WAL 用整页镜像（FPI），InnoDB 用双写区。FPI 会让 WAL 在检查点后首改页时体积突增，doublewrite 则额外占一份顺序写带宽。

## 六、常见误区

- 认为 redo 记录整页：多为增量动作，仅必要时（双写 / 特定场景）记录全页，否则日志过大。
- 认为 redo 可无限增长：循环覆盖，受文件总大小限制，老段被回收。
- 认为 `=2` 与 `=1` 等价：提交仅写 OS 缓存时操作系统崩溃仍可能丢已提交事务。
- 认为双写很慢：双写是顺序写且可批量，开销通常低于 FPI 带来的随机读放大。

## 八、面试题

- LSN 在恢复中的作用？答：比较记录 LSN 与页 `page_lsn`，只重放更新的部分，跳过已应用记录。
- `innodb_flush_log_at_trx_commit=2` 风险？答：提交仅写 OS 缓存，宕机可能丢已提交事务。
- 部分写怎么防？答：doublewrite buffer 先写双写区，再写原页，恢复时以双写区校正。
- 检查点为何重要？答：推进 `checkpoint_lsn` 缩短崩溃后重放窗口，是恢复速度关键。

从工程视角看，redo 的正确性最终要落在「幂等重放」上：无论崩溃中断在何处，重跑日志都能得到同一结果。这要求每条 redo 记录本身自包含（含页号、偏移、动作），不依赖前一条的执行上下文。

doublewrite 与 FPI 是两种等价的「部分写防护」哲学：前者用额外顺序写换随机读安全，后者用首改整页镜像换后续重放简单。选型时主要看 workload 是读多还是写多——读多偏向 FPI（少一次双写 IO），写多偏向 doublewrite（避免整页镜像膨胀）。

另一个常被问到的问题是「redo 与 binlog 的二阶段提交」：InnoDB 用内部 XA 先写 redo prepare，再写 binlog，最后 redo commit，保证二者最终一致；任何一步崩溃都能靠对方补齐，这也是 MySQL「双日志」能共存不乱的根基。

理解这些，才能真正读懂 `SHOW ENGINE INNODB STATUS` 里 `Log sequence number`、`Pages flushed` 与 `Last checkpoint` 三者的关系，进而判断系统是否在「追赶」还是「健康」。

## 九、演进与趋势

redo 格式向压缩、并行写、与 NVMe 协同优化演进，降低 fsync 开销；undo 与 redo 分离、日志即存储（log-structured）是新型引擎方向，进一步统一恢复与写入路径。undo 日志也可转为仅追加结构，简化崩溃后分析。

在 InnoDB 中，redo 与 undo 虽都落盘，但职责分层：redo 保崩溃后「已提交的不丢、页状态可重建」，undo 保「未提交的能回、旧版本可查」。二者通过 LSN 与事务状态机串联，构成恢复闭环。

写放大方面，redo 的循环写使磁盘写入量远小于「每修改随机写数据页」，这是 WAL 范式的核心收益；但 doublewrite 与 FPI 会带来额外顺序写，需在 `innodb_doublewrite` 与检查点频率间权衡。

线上排障时，若发现重启后恢复极慢，常见原因是检查点长期未推进导致 `checkpoint_lsn` 过旧，重放窗口过大；应检查 `innodb_checkpoint_age` 与刷脏页能力是否瓶颈。

另一个易忽视点：大事务会产生大量 undo 与 redo，不仅拖慢提交，还撑大回滚段、延缓 purge，间接影响后续所有事务的 MVCC 快照读。因此控制事务粒度本身就是对日志系统的保护。

## 十、小结

物理 / 生理页级日志以精准与速度守护崩溃恢复，LSN 是其有序重放的标尺，doublewrite 解决部分写，是 InnoDB 持久性的基石；理解 MTR 与检查点有助于解释恢复行为与写放大，并正确设置刷盘策略。
