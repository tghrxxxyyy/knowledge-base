# 逻辑日志与物理日志差异

> 对应 Mohan 1992 ARIES 的物理/生理日志与 MySQL binlog 逻辑日志对比，参考 Silberschatz《OSC》第17章。

## 一、背景与挑战

日志可以记录两种截然不同的「真相」：一是「哪个页的哪个字节改成了什么」（物理 / 生理），二是「执行了哪条 SQL / 哪行前后像变了」（逻辑）。二者在恢复粒度、复制友好性、存储开销上差异巨大，也决定了系统能否「快速自愈」与「跨节点同步」。

现代数据库几乎都同时拥有两类日志，各司其职。选择记录什么，本质是「恢复速度」与「可读可复制」之间的架构取舍，也是为什么没有一种日志能包打天下。

## 二、核心原理

**物理日志**（ARIES 称 physiological logging）记录 `页号 + 偏移 + 前后像 / 重做动作`，与高层 SQL 语义无关，恢复精准、确定、快速，适合单机崩溃恢复；缺点是不直观、难跨异构存储重放。

**逻辑日志**记录操作语义（如 `UPDATE t SET x=1 WHERE id=2`，或行的 before/after 像），跨节点复制可读、可过滤、可在不同存储结构上重放，并支撑 CDC 数据管道；缺点是需要保证幂等与确定性（语句级），或体积偏大（行级）。

MySQL 是典型「双日志」：InnoDB redo 是物理、binlog 是逻辑，binlog 负责复制与增量备份，redo 负责崩溃恢复。PostgreSQL 以物理 WAL 为主，逻辑复制靠独立的逻辑解码器输出行级变更。

## 三、形式化与数学基础

物理日志量约与改动次数成正比：

$$ L_{phys} = \sum_c (page\_id, offset, before, after) $$

逻辑日志量约与操作 / 行数成正比：

$$ L_{logical} = \sum_o (stmt, old\_row, new\_row) $$

对批量更新（如 `UPDATE` 全表 100 万行），语句级逻辑日志仅一条文本，远小于逐行物理日志；但行级逻辑日志（ROW 格式）反而可能更大。

恢复时间上，物理重放为 $O(\text{changed pages})$，逻辑重放为 $O(\text{affected rows})$ 且需解析与索引维护，故物理恢复更快。

## 四、代码实现

```sql
-- MySQL：物理 redo 与逻辑 binlog 并存
SHOW VARIABLES LIKE 'innodb_log_file_size';   -- 物理 redo
SHOW VARIABLES LIKE 'binlog_format';           -- ROW / STATEMENT / MIXED（逻辑）

-- PostgreSQL：物理 WAL 为主，逻辑复制靠发布/订阅
-- CREATE PUBLICATION pub FOR TABLE orders;
-- 从库：CREATE SUBSCRIPTION sub CONNECTION '...' PUBLICATION pub;
-- 逻辑解码插件（test_decoding / pgoutput）把 WAL 转成行级变更
```

## 五、与其他技术对比

| 维度 | 物理日志 | 逻辑日志 |
| --- | --- | --- |
| 恢复速度 | 快、精准 | 慢、依赖表结构 |
| 复制友好 | 差（异构难重放） | 好（可读可过滤） |
| 存储 | 中等 | 语句级小 / 行级大 |
| 典型用途 | 崩溃恢复 | 复制、审计、CDC |

## 六、常见误区

- 认为逻辑日志能替代物理日志做崩溃恢复：逻辑重放慢且依赖表结构，通常仍需物理 redo。
- 认为 ROW 格式一定大就不好：相比 STATEMENT 它更确定安全，常是默认首选。
- 认为两类日志冗余：二者服务不同目标（恢复 vs 复制），并存是工程最优。
- 认为逻辑日志天然幂等：行级前后像需配合主键才能安全重放，语句级还受确定性约束。

## 八、面试题

- 物理与逻辑日志各自用途？答：物理保崩溃恢复精准快速，逻辑保复制与审计可读。
- `binlog_format=STATEMENT` 风险？答：含 `NOW()`/`UUID()` 等非确定函数会导致从库不一致。
- 为何 MySQL 要双日志？答：redo 管恢复、binlog 管复制，职责分离且崩溃后仍可用 binlog 做 PITR。
- 逻辑解码做什么？答：把物理 WAL 翻译成行级变更，供逻辑复制与 CDC 消费。

从排障角度，一个高频问题是「复制延迟突增」。若是物理 WAL 流复制，延迟多半来自从库重放慢（CPU/IO 瓶颈）或网络；若是逻辑 binlog 行级复制，还可能是从库上触发器、级联外键或大事务导致单线程重放卡顿，此时应优先排查从库写入路径而非主库。

另一个易混点是「物理日志能否用于逻辑复制」：标准不行，因为物理日志绑定具体页结构与存储引擎；必须经由逻辑解码把物理变更翻译成行级语义，才能跨版本、跨引擎订阅，这也是为什么「双日志」在现代架构里难以被单一日志替代。

在云原生数据库里，物理日志还承担「存储计算分离」的底座：计算节点把 WAL 流式发给共享存储，崩溃后新节点重放同一份 WAL 即可恢复状态，日志由此从「恢复工具」升级为「状态同步总线」。

补充一句：物理与逻辑日志的边界正因「云原生」而模糊——共享存储下 WAL 既是恢复日志也是复制载体，但逻辑 binlog 仍不可替代地服务于异构订阅与审计。

## 九、演进与趋势

逻辑解码（logical decoding）与 CDC 让逻辑日志成为数据管道核心；物理日志向并行恢复、日志即存储（log-structured）演进，二者边界在云原生库中进一步融合，出现「一份日志多种视图」的统一架构。redo 与 binlog/WAL 的协同也从「双写」走向「单一日志多视图」。

在真实系统中，物理与逻辑日志往往不是二选一，而是「物理做地基、逻辑做延伸」。例如 MySQL 先靠 redo 保证崩溃后可恢复，再用 binlog 把变更导出做复制；PostgreSQL 同理以 WAL 恢复、以逻辑解码导出。

选择记录粒度时还要考虑「部分失败」：物理重放是幂等且确定的一页级操作，天然抗重放；逻辑重放（尤其语句级）需要确保可重入，行级靠主键去重、语句级靠禁止非确定函数，二者健壮性来源不同。

从可观测性角度，逻辑日志是审计与合规的天然载体——谁改了哪行、前后值是什么，一目了然；物理日志则更像是「内部实现细节」，对人和外部系统都不友好，但快且稳。

因此，设计高可用架构时应让两类日志各管一摊：物理日志守底线（不丢、能恢复），逻辑日志做外延（能复制、能审计、能接数据管道），并通过统一的位点（LSN / binlog position）把它们对齐到同一时间轴。

## 十、小结

物理日志保恢复、逻辑日志保复制，现代系统常二者并存各司其职；理解其差异与「双日志」动机，是设计高可用与数据管道、以及排查复制漂移的基础，更是读懂数据库「为什么这样记日志」的钥匙。
