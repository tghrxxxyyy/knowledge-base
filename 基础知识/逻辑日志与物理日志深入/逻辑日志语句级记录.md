# 逻辑日志语句级记录

> 对应 MySQL binlog `STATEMENT` 格式与早期复制，参考 MySQL 官方文档与 DDIA 第3章复制章节。

## 一、背景与挑战
语句级逻辑日志直接记录执行的 SQL。它紧凑、可读，但面临非确定性函数与上下文依赖，导致从库重放结果不一致。

## 二、核心原理
`binlog_format=STATEMENT` 下，主库把 `UPDATE/INSERT/DELETE` 原文写入 binlog，从库解析后重新执行。优点日志小、易审计；缺点要求重放确定性：同 SQL 在主从产生相同结果，这要求无 `UUID()`、`NOW()`、`RAND()` 等非确定调用，且依赖一致的执行环境（如隔离级别、字符集）。

## 三、形式化与数学基础
语句级日志量：
$$ L_{stmt} = \sum len(sql_i) $$
远小于行级逐行记录，对大批量更新尤其节省。但一致性要求：
$$ exec(replica, sql_i) = exec(master, sql_i) $$
必须对所有 $i$ 成立，否则复制漂移。

## 四、代码实现
```sql
SET SESSION binlog_format = 'STATEMENT';
INSERT INTO t VALUES (...);
-- binlog 中记录的是该 INSERT 语句文本
```

## 五、与其他技术对比
`ROW` 格式记录行前后像，规避确定性，但体积大；`MIXED` 由引擎自动选。PostgreSQL 逻辑复制输出行级变化（逻辑解码），非语句级。

## 六、常见误区
认为 STATEMENT 一定省空间——含大文本字段或触发器时未必。认为语句级复制简单可靠——非确定函数与负载均衡读从库易读到不一致中间态。

## 七、与开源书/权威来源对应
MySQL 官方「Binary Logging Formats」；DDIA 第3章「Replication」对语句与行复制的讨论。

## 八、面试题
问：STATEMENT 格式为何可能主从不一致？答：非确定函数、依赖上下文或触发器在主从执行结果不同。

## 九、演进与趋势
行级复制成主流，语句级仅在兼容/审计场景保留；逻辑解码让行级也能被外部消费。

## 十、小结
语句级逻辑日志紧凑但受确定性约束，现代实践多倾向行级以保一致。
