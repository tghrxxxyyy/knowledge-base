# 逻辑日志语句级记录

> 对应 MySQL binlog `STATEMENT` 格式与早期复制，参考 MySQL 官方文档与 Kleppmann《DDIA》第3章复制章节。

## 一、背景与挑战

语句级（statement-based）逻辑日志直接记录「执行了哪条 SQL」。它日志量小、人可读、便于审计，是早期 MySQL 复制的默认形态。但它的致命弱点是**确定性**：从库必须重放同一条 SQL 并得到与主库完全一致的结果，而现实里很多 SQL 并不满足这一点，于是产生主从不一致。

理解这一约束，是正确选择 binlog 格式与排查复制漂移的前提。在混合读写、读从库负载均衡的架构里，语句级复制的不一致会以「偶发脏读」形式暴露，极难定位。

## 二、核心原理

在 `binlog_format = STATEMENT` 下，主库把 `INSERT/UPDATE/DELETE` 等语句原文写入 binlog，从库的 SQL 线程解析后重新执行。优势：日志紧凑（一条 `UPDATE` 影响百万行也只占一行文本）、易审计、便于人工排查。

代价：重放必须确定性，即同 SQL 在主从产生相同结果。这要求避免 `UUID()`、`NOW()`、`RAND()`、`SLEEP()` 等非确定调用，且依赖一致的执行环境（隔离级别、字符集、`AUTO_INCREMENT` 行为、触发器定义）。

任何偏差都会让从库数据漂移到与主库不同。MySQL 在遇到不确定语句时会切换为「不安全」标记并告警，必要时回退到行格式（MIXED）。

## 三、形式化与数学基础

语句级日志体积约为语句文本之和：

$$ L_{stmt} = \sum_i len(sql_i) $$

对大批量更新尤其节省（与受影响行数无关）。但一致性要求对所有语句 $i$ 成立：

$$ exec(replica, sql_i) = exec(master, sql_i) $$

若任一 $i$ 不成立，则从库状态偏离，且偏差会随后续依赖该行的语句放大（复制漂移）。引入非确定函数 $f$ 时：

$$ exec(master, f()) \neq exec(replica, f()) $$

这是 STATEMENT 格式失败的典型代数表达，主从结果从此分叉且难自愈。

## 四、代码实现

```sql
-- 会话级切换为语句格式
SET SESSION binlog_format = 'STATEMENT';

INSERT INTO orders (user_id, amount) VALUES (7, 100);
-- binlog 中记录的即上面这条 INSERT 文本，而非行数据

-- 查看当前 binlog 格式与文件
SHOW VARIABLES LIKE 'binlog_format';
SHOW BINARY LOGS;
-- 用 mysqlbinlog 解析查看语句内容
-- mysqlbinlog mysql-bin.000001 | less
```

## 五、与其他技术对比

| 格式 | 日志量 | 确定性要求 | 适用 |
| --- | --- | --- | --- |
| STATEMENT | 小 | 高（禁非确定函数） | 审计、简单写 |
| ROW | 大（逐行前后像） | 无 | 默认、强一致 |
| MIXED | 中 | 引擎自动选 | 折中 |

PostgreSQL 的逻辑复制输出的是行级变化（逻辑解码），并非语句级重放，因此不受确定性约束，但可读性弱于语句级，审计时需解析行事件。

## 六、常见误区

- 认为 STATEMENT 一定省空间：包含大文本字段或触发器链时，行级 ROW 可能反而更优。
- 认为语句级复制简单可靠：非确定函数、`LOAD_FILE`、用户变量、从库读负载均衡易读到不一致中间态。
- 把 `binlog_format` 当全局无关：混合部署里主从格式不一致会导致复制异常。
- 认为 MIXED 永远安全：MIXED 只在检测到不安全语句时切 ROW，仍存在边界判断盲区。

## 八、面试题

- STATEMENT 为何可能主从不一致？答：非确定函数、依赖上下文或触发器在主从执行结果不同。
- 哪些函数不能用？答：`UUID()`、`NOW()`、`RAND()`、`SYSDATE()` 等；可用 `ROW` 或 `MIXED` 规避。
- 大批量更新用哪种？答：STATEMENT 日志最小，但需确认确定性；否则用 ROW 更安全。
- MIXED 何时退回 ROW？答：引擎判定语句「不安全」（含非确定函数/自增/UDF）时自动切行格式。

补充一点排障经验：当从库出现偶发不一致时，先确认 binlog 格式与 `binlog_row_image` 设置，再查是否有非确定函数或基于 Statement 的触发器；多数「诡异漂移」都能在这三层里找到根因。

## 九、演进与趋势

行级复制已成主流（MySQL 5.7+ 默认 ROW），语句级仅在兼容 / 审计场景保留；逻辑解码让行级变更也能被外部消费者（CDC）读取，兼具一致性与可读性，成为数据管道标准入口。未来复制更强调「行级 + 可过滤 + 可外部订阅」三位一体。

实际运维中，判断是否使用 STATEMENT 可遵循一条经验法则：若写入包含任何非确定函数、或依赖会话/服务器状态（如 `SQL_MODE`、时区），一律用 ROW；仅当写入是纯确定 DML 且极度关注 binlog 体积时才考虑 STATEMENT。

复制一致性校验也应纳入常规巡检：用 `pt-table-checksum` 之类工具定期比对主从数据，能在 STATEMENT 格式悄然漂移时早发现，避免「从库读到了一周前的旧值」这类隐蔽故障。

此外，STATEMENT 格式下从库的 binlog（若开启级联复制）会再次记录语句，形成多级重放，任一环的非确定都会逐级放大，故级联架构更应使用 ROW。

最后提醒：binlog 格式是会话级可变的，混合部署中务必统一主从配置，并在应用连接池初始化时显式设定，避免个别连接悄悄切换格式导致复制行为不一致。

## 十、小结

语句级逻辑日志紧凑但受确定性约束，现代实践多倾向行级以保一致；理解二者取舍是做好复制与审计的前提，binlog 格式的选择本质是在「省空间」与「强一致」间权衡，并以 MIXED 作为折中兜底。
