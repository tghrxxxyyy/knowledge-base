# 中断处理与顶半底半机制

> 对应 Corbet《Linux Device Drivers》第 10 章中断与 Bovet & Cesati《Understanding the Linux Kernel》第 4 章。

## 一、背景与挑战
硬件中断到来时内核须尽快响应以免丢失事件，但中断上下文不能睡眠、不宜做耗时工作。Linux 用"顶半部（hardirq）+ 底半部（softirq/tasklet/workqueue）"拆分：顶半快、底半延后。

## 二、核心原理
`request_irq` 注册顶半处理程序，在关中断下尽快读取状态、确认硬件、调度底半。底半 `tasklet` 在软中断上下文（仍不可睡眠但可重开中断），`workqueue` 在进程上下文（可睡眠）。网络收包即典型：顶半收 DMA 完成中断，软中断 `NET_RX` 协议处理。

## 三、形式化与数学基础
中断延迟：
$$L = L_{hw} + L_{mask} + L_{top} + L_{bottom}$$
其中 $L_{mask}$ 为关中断窗口，须最小化。吞吐受顶半占用率约束：$U_{top} < 1$ 才不丢中断。

## 四、代码实现
```c
irqreturn_t top_half(int irq, void *dev) {
    ack_hw();                 // 快速确认
    tasklet_schedule(&my_tasklet);
    return IRQ_HANDLED;
}
void bottom(struct tasklet_struct *t) {
    process_data();          // 可较长，但不可睡
}
```

## 五、与其他技术对比
tasklet 串行于同 CPU 软中断、不可睡；workqueue 可睡但延迟大；threaded irq 把底半放入内核线程兼顾二者。相较轮询，中断省 CPU 但引入延迟抖动。

## 六、常见误区
误以为中断处理里能调 `kmalloc(GFP_KERNEL)`：会睡眠，须 `GFP_ATOMIC`。误以为顶半可放任耗时：拉长关中断窗口致丢包。误以为 tasklet 跨 CPU 并行：同一 tasklet 不并行。

## 七、与开源书/权威来源对应
Corbet LDD 第 10 章 request_irq/tasklet/workqueue；Bovet & Cesati 第 4 章中断与异常。

## 八、面试题
问：顶半/底半如何分工？答：顶半确认硬件并调度，底半做重活。问：为何不能在中短线睡？

## 九、演进与趋势
threaded IRQ 成为主流，把大部分底半逻辑移入可调度线程，提升实时性（PREEMPT_RT）与可调试性。

## 十、小结
顶半底半把"必须快"的硬件确认与"可延后"的处理解耦，是中断响应与系统吞吐平衡的关键。
