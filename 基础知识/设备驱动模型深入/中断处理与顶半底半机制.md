# 中断处理与顶半底半机制

> 对应 Corbet、Rubini & Kroah-Hartman《Linux Device Drivers》（LDD3）第 10 章 Interrupt Handling 与 Bovet & Cesati《Understanding the Linux Kernel》第 4 章 Interrupts and Exceptions；并参考 Love《Linux Kernel Development》第 7 章 Interrupts and Interrupt Handlers。

## 一、背景与挑战

硬件中断到来时内核须尽快响应，以免丢失事件（如网卡收包溢出、串口 FIFO 满覆盖）。

但中断上下文不能睡眠、不宜做耗时工作（关中断窗口越长越影响系统实时性与吞吐）。

Linux 用「顶半部（hardirq）+ 底半部（softirq/tasklet/workqueue）」拆分：顶半快、底半延后，把「必须立即做」与「可以稍后做」分离。

挑战在于：正确划分边界、避免竞态、在吞吐与延迟间权衡，并适配实时内核（PREEMPT_RT）。

## 二、核心原理

`request_irq` 注册顶半处理程序，在关中断（或本地关中断）下尽快读取状态、确认硬件、调度底半。

底半 `tasklet` 在软中断上下文（仍不可睡眠但可重开中断）运行；`workqueue` 在进程上下文（可睡眠、可做重活）。

网络收包即典型：顶半收 DMA 完成中断，软中断 `NET_RX_SOFTIRQ` 做协议栈处理。

`softirq` 是静态注册的底半机制（如 `NET_TX`/`NET_RX`/`BLOCK`/`TIMER`），tasklet 是其动态封装；workqueue 提供可睡眠底半。

`IRQF_SHARED` 允许多设备共享同一条 IRQ 线，顶半须用 `dev_id` 判别是否为本设备。

## 三、形式化与数学基础

中断延迟分解：

$$L = L_{hw} + L_{mask} + L_{top} + L_{bottom}$$

其中 $L_{mask}$ 为关中断窗口，须最小化。

吞吐受顶半占用率约束：顶半占 CPU 比例 $U_{top} < 1$ 才不丢中断；超过即中断丢失或报文丢弃。

底半延迟 $L_{bottom}$ 取决于其运行上下文（softirq 立即、workqueue 受调度延迟）。

## 四、代码实现

```c
irqreturn_t top_half(int irq, void *dev_id) {
    ack_hw();                       // 快速确认，清设备中断状态
    tasklet_schedule(&my_tasklet); // 调度底半
    return IRQ_HANDLED;            // 或 IRQ_NONE（非本设备，共享线）
}

void bottom(struct tasklet_struct *t) {
    process_data();                // 可较长，但不可睡
}

// 可睡眠底半用 workqueue
static DECLARE_WORK(my_work, bottom_wq);
queue_work(system_wq, &my_work);
```

`IRQF_ONESHOT` 用于边沿触发且线程化 IRQ，确保底半完成前不再重入。

## 五、与其他技术对比

| 底半机制 | 上下文 | 可睡 | 并发 | 适用 |
| --- | --- | --- | --- | --- |
| tasklet | 软中断 | 否 | 同 CPU 串行 | 轻量延后 |
| softirq | 软中断 | 否 | 多 CPU 并行 | 高吞吐（网络） |
| workqueue | 进程 | 是 | 任意 | 重活/可阻塞 |
| threaded irq | 进程（内核线程） | 是 | 调度 | 实时/可调试 |

tasklet 串行于同 CPU 软中断、不可睡；workqueue 可睡但延迟大；threaded irq 把底半放入内核线程兼顾二者。

相较轮询，中断省 CPU 但引入延迟抖动。

## 六、常见误区

1. 误以为中断处理里能调 `kmalloc(GFP_KERNEL)`：会睡眠，须 `GFP_ATOMIC`（或移到底半 workqueue）。
2. 误以为顶半可放任耗时：拉长关中断窗口致丢包、增大延迟。
3. 误以为 tasklet 跨 CPU 并行：同一 tasklet 不并行，软中断可多 CPU 并行。
4. 误以为 `local_irq_disable` 全局关中断：它仅关本 CPU，SMP 下需 `spin_lock_irqsave` 护共享数据。
5. 误以为共享 IRQ 顶半无需判别：须用 `dev_id` 确认事件归属，否则返回 `IRQ_NONE`。

## 八、面试题

1. 顶半/底半如何分工？要点：顶半确认硬件并调度，底半做重活；前者不可睡、后者可睡。
2. 为何不能在中短线睡？要点：中断上下文属原子上下文，无进程上下文，睡眠无法被调度。
3. 共享中断怎么处理？要点：`IRQF_SHARED` + `dev_id`，顶半判别归属，非本设备返回 `IRQ_NONE`。
4. PREEMPT_RT 下中断有何变化？要点：多数硬中断线程化，底半跑在可抢占内核线程，降低延迟抖动。

## 九、演进与趋势

- threaded IRQ 成为主流，把大部分底半逻辑移入可调度线程，提升实时性（PREEMPT_RT）与可调试性。
- `irq_cpu_affinity` 把中断绑核，配合 `RPS/RFS` 把软中断负载均衡到应用所在 CPU。
- `NAPI` 在高速网卡上用「中断+轮询」混合，高吞吐下关闭每包中断，降低开销。

## 十、小结

顶半底半把「必须快」的硬件确认与「可延后」的处理解耦，是中断响应与系统吞吐平衡的关键。

现代内核进一步把底半线程化（threaded irq / NAPI），在实时性与可维护性之间持续优化。
