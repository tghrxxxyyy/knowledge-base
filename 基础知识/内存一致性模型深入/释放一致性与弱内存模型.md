# 释放一致性与弱内存模型

> 对应 Gharachorloo 等《Memory Consistency and Event Ordering in Scalable Shared-Memory Multiprocessors》（1990，释放一致性原始论文），以及 Hennessy & Patterson 量化方法弱内存章节与 ARM ARM 的 acquire/release 语义。

## 一、背景与挑战

顺序一致性（SC）禁止绝大多数硬件优化：不能有写缓冲、不能有乱序访存、每次写都要等到全局可见。为把同步成本从「每次访存」降到「只在同步点」，释放一致性（Release Consistency, RC）把访存分为普通访问与同步访问，仅对同步访问施加顺序约束。

弱内存模型（ARM、POWER、RISC-V 的 RVWMO）把这一思想做到极致：普通访存之间几乎无顺序保证，正确性完全依赖程序员在同步点显式标注 acquire/release。这带来高吞吐与低功耗，也带来两个现实困难：一是「看起来能跑」的代码可能隐藏数据竞争；二是同步语义在编译器、硬件与库三层之间都必须保持一致，任何一层的优化都可能破坏可推理性。

## 二、核心原理

RC 的基本分工：

- 普通读/写（data access）：彼此之间无跨线程顺序保证，可自由重排、流水、缓存。
- 同步操作：acquire（进入临界区/获取）、release（离开临界区/释放）。
- 约束一：某核在 release 之前的所有普通访问，必须先于该 release 生效。
- 约束二：某核在 acquire 之后的所有普通访问，必须晚于该 acquire 生效。
- 约束三：acquire/release 针对同一同步变量配对，形成跨核的传递链。

按同步操作是否强制全局定序，RC 又分为两个变体：

- RCsc（sequential consistency for synchronization）：同步操作本身具有全局顺序，因此稍强的程序语义更易推理。
- RCpc（processor consistency for synchronization）：同步操作只保证「写→读」等部分顺序，允许同步操作也被部分重排，性能更好但对推理要求更高。ARM 的 acquire/release 在部分场景下属于 RCpc 类，`lwsync` 是典型的轻量同步指令。

在硬件层面，RC 的实现依赖于三件事：非阻塞缓存（写不等待）、写缓冲与失效队列（把写完成与写可见解耦）、以及同步点上的定向栅栏（只抑制必要方向的重排）。ARMv8 用专门的指令表达：`LDAR`（acquire 加载）、`STLR`（release 存储），其顺序语义被固化在指令编码里，比通用的 `DMB` 更高效。

## 三、形式化与数学基础

RC 的约束可写成程序序蕴含（$\prec_{po}$ 为程序序，$\prec_m$ 为内存序）：

$$W_{before} \prec_{po} release \;\Rightarrow\; W_{before} \prec_m release$$

$$acquire \prec_{po} R_{after} \;\Rightarrow\; acquire \prec_m R_{after}$$

普通访问之间不做限制：

$$\neg\,\big(W_a \prec_{po} R_b \;\Rightarrow\; W_a \prec_m R_b\big) \quad \text{（无同步标注时）}$$

当 release 与 acquire 作用于同一同步变量、且 acquire 读到该 release 写入的值（或该 release 之后的值）时，建立同步：

$$release(x,v) \xrightarrow{sw} acquire(x,v') \;\Rightarrow\; release \xrightarrow{sw} acquire$$

再叠加程序序，得到跨线程的 happens-before：

$$a \prec_{po} release \xrightarrow{sw} acquire \prec_{po} b \;\Longrightarrow\; a \xrightarrow{hb} b$$

典型的「消息传递」（Message Passing）litmus 测试：写 `data=1` 再 release 写 `flag=1`，读端 acquire 读到 `flag==1` 后读 `data`，结果 `(flag=1, data=0)` 被禁止。若两端都使用 relaxed，则该结果合法——这正是弱内存下必须显式标注的直接体现。

RC 相对 SC 的性能收益可以粗略量化为：SC 下每次写都可能等待全局确认，代价 $O(2L_{coherence})$；RC 下只有同步点付费，代价约 $O(k \cdot L_{coherence})$，其中 $k$ 为同步点比例（通常远小于 1）：

$$\frac{Cost_{RC}}{Cost_{SC}} \approx k \ll 1$$

## 四、代码实现

```c
/* C11 原子实现 RC 语义的临界区（acquire 取锁，release 放锁） */
#include <stdatomic.h>

static atomic_int g_lock = 0;
static int        g_shared = 0;

static void critical_section(void) {
    /* acquire: 其后（区内）的访存不得早于获取生效 */
    while (atomic_exchange_explicit(&g_lock, 1, memory_order_acquire)) {
        /* 忙等；实际可插入 pause 或让出 CPU */
    }
    g_shared += 1;                         /* 临界区普通访问 */
    /* release: 其前（区内）的普通写必须在释放前对其他核可见 */
    atomic_store_explicit(&g_lock, 0, memory_order_release);
}
```

```c
/* 直接用 acquire/release 的"发布—订阅"，无需显式栅栏指令 */
typedef struct {
    atomic_int seq;        /* 版本号：奇数表示写入中，偶数表示稳定 */
    int        payload[16];
} seqlock_t;

static int seqlock_read(seqlock_t *s, int *out) {
    for (;;) {
        int s0 = atomic_load_explicit(&s->seq, memory_order_acquire);
        if (s0 & 1) continue;                     /* 写者正在更新 */
        for (int i = 0; i < 16; i++) out[i] = s->payload[i];
        atomic_thread_fence(memory_order_acquire); /* 防止读被提前完成 */
        int s1 = atomic_load_explicit(&s->seq, memory_order_relaxed);
        if (s0 == s1) return 0;                   /* 版本未变，读取成功 */
        /* 否则读到撕裂数据，重试 */
    }
}
```

```asm
; ARMv8 的 acquire/release 指令：把顺序语义固化在指令里，比 DMB 更轻
    stlr    w1, [x0]        ; release store：之前的普通写先于此可见
    ldar    w2, [x0]        ; acquire load：此后的普通读不早于此
    dmb ish                 ; 通用全屏障（更贵，用于复杂场景）
    lwsync                  ; POWER 的轻量同步：覆盖除 StoreLoad 外的组合
```

要点归纳：`acquire`/`release` 是「单向」的，因此成对使用才构成完整同步；用 relaxed 也能写对，但必须手工插入相应方向的栅栏，可读性与可维护性都显著下降；在循环重试型算法（如 seqlock）中，读侧重试次数与写者频率直接相关，高写入负载下必须考虑让出或退化为锁。

## 五、与其他技术对比

| 模型 | 普通访问顺序 | 同步点顺序 | 硬件示例 | 编程负担 |
| --- | --- | --- | --- | --- |
| SC | 全部保序 | 天然保序 | 无主流实现 | 最低 |
| TSO | 除 StoreLoad 外保序 | 用 MFENCE/LOCK | x86 | 低 |
| PSO | 允许写—写重排 | 用屏障 | 部分历史架构 | 中 |
| RCsc | 无要求 | 同步操作全局定序 | 多数实现可选 | 中 |
| RCpc | 无要求 | 同步操作部分定序 | ARM acquire/release 场景、POWER lwsync | 高 |
| 纯弱序 | 无要求 | 全靠显式屏障 | 早期 Alpha | 最高 |

## 六、常见误区

1. 认为 release 之后数据立刻可见：release 只保证「之前的写在该 release 之前完成」，可见性时机仍由一致性协议决定。
2. 认为普通变量在弱内存下跨线程安全：不加同步的普通访问会构成数据竞争，结果是未定义行为。
3. 只用一半同步：只有 release 没有配对的 acquire（或反之），无法建立 happens-before，顺序保证不成立。
4. 认为 acquire/release 可以替代原子性：它们提供顺序，不提供多字原子性；复合数据结构仍需锁或原子 RMW。
5. 在弱内存平台上沿用 x86 直觉：「x86 上跑通」不能证明正确，必须做跨平台与压力测试。
6. 忽视编译器的重排能力：语言级原子操作是唯一的可移植保证，依赖 `volatile` 或裸内联汇编容易被优化破坏。

## 八、面试题

1. 问：acquire/release 相比 SC 少了什么保证？答：少了普通访问之间以及所有操作之间的全局总序；只保留「release 前的写」与「acquire 后的读」这两个方向的约束。
2. 问：为什么弱内存下代码在 x86 上能跑却在 ARM 上出错？答：x86 是 TSO，隐式保证了除 StoreLoad 外的顺序；ARM 弱序允许更多重排，缺失的 acquire/release 只在弱平台上显形。
3. 问：RCsc 与 RCpc 的区别？答：RCsc 要求同步操作本身全局定序，语义更强、更易推理；RCpc 允许同步操作也被部分重排，性能更好但推理更难。
4. 问：什么时候必须用显式全屏障而不是 acquire/release？答：当需要约束不同变量之间的双向顺序、或需要跨越多个同步变量建立全局偏好顺序时，单向语义不足，需要全屏障或 seq_cst。
5. 问：seqlock 为什么在写者频繁时性能差？答：读者可能在写入窗口内反复重试，重试代价与写入频率成正比；高争用下应改用锁或其他无锁结构。

## 九、演进与趋势

- 语言级 RC 语义普及：C++/Rust 把 acquire/release 作为默认推荐，硬件提供轻量指令（LDAR/STLR）与之对应。
- 依赖序的有限利用：ARM/POWER 的地址依赖与控制依赖天然有序，语言层面尝试通过 consume 类语义利用，但工程实践普遍建议保守使用 acquire/release。
- 域限定与作用域一致性：通过 scope（如线程、设备、系统）弱化不必要的全局排序，降低同步成本。
- 持久内存引入的持久化顺序：`sfence`/`clwb` 与持久化栅栏把 RC 讨论扩展到「崩溃一致性」维度。
- 自动化验证：litmus 测试与模型检查成为验证 RC 实现的常规手段，用于发现「碰巧正确」的代码。

## 十、小结

释放一致性把「必须保序」的范围收窄到同步点：普通访问自由重排以换取吞吐，acquire/release 成对出现以建立 happens-before。它既是弱内存硬件存在的理由，也是可移植并发编程的最小充分抽象。真正掌握它的标志是：能说清什么时候需要 acquire、什么时候需要 release、什么时候两者都不够而必须用全屏障或 seq_cst，以及为什么「在 x86 上能跑」从来不是正确性的证据。
