# 拓扑排序与依赖解析

> 对应 youngyangyang04/leetcode-master 拓扑排序（依赖/编译顺序）与 Sedgewick《Algorithms》；工程侧参考 GNU Make 文档、npm/pip 依赖解析实践，以及 Kahn 1962。

## 一、背景与挑战

依赖解析是拓扑排序最"接地气"的投影：包管理器要按依赖顺序安装/构建模块，编译器要按头文件与链接关系决定翻译单元顺序，CI 流水线要按作业依赖决定执行顺序，微服务部署要按调用依赖决定启动顺序。把模块看作顶点、"A 依赖 B"看作有向边 $B \to A$（B 必须先就绪），求一个合法执行序——这就是拓扑排序。

真正的挑战不是"排一个序"，而是**依赖关系本身的脏乱**：循环依赖（A→B→C→A）使任何线性序都不存在；条件依赖（只在某个 feature 打开时依赖 C）使图随配置变化；版本约束（A 需要 B≥2.0 且 B<3.0）把问题从图排序升级为约束求解；动态依赖（运行时才加载插件）要求图可增量更新。朴素做法如"递归加载、用 visited 防死循环"只能发现"卡住了"，既给不出完整顺序，也说不清环在哪；"排序比较器"式写法（写一个 `cmp(a,b)`）在依赖非全序时直接失效。

在工程里，依赖解析器的地位是"系统的骨架"。Make 失败时最常见的一类错误就是"循环依赖"；npm/pip 的安装顺序、Cargo 的构建图、Terraform 的资源顺序、Kubernetes 控制器的 reconcile 顺序，全都是同一抽象。面试中"如何检测循环依赖并输出链路""多图如何合并""版本冲突怎么办"层层递进，考的是对"图 vs 约束"边界的理解。

## 二、核心原理

**建模**：设模块集合 $M$，依赖关系 $E = \{(need, mod) \mid mod \text{ 需要 } need\}$。边方向取"被依赖者 $\to$ 依赖者"（need 在前）。合法构建序列就是 $G=(M,E)$ 的拓扑序；不存在合法序列 $\iff$ $G$ 有环。

**核心机制**用 Kahn 或 DFS 都行，工程上 Kahn 更主流，因为可以：
1. 同时得到"哪些模块现在可以构建"（入度 0 集合）→ 天然并行；
2. 失败时在残余图上找环，输出精确依赖链；
3. 增量更新时只处理受影响的入度变化。

**循环依赖的处理策略**比单纯判环丰富：
- **严格拒绝**（最常见）：报错并打印环，让用户拆模块或引入接口层。
- **SCC 缩点容忍**：把强连通分量压成一个"簇"，簇内按约定顺序（或再编译链接）处理，簇间再拓扑。适合插件系统、单体内的双向引用。
- **延迟绑定**：依赖改为运行时查找（DI 容器、服务发现），图上的边变成弱约束，构建期不再成环。

**多图合并**：几个子系统各有局部依赖图，共享一些公共模块。做法是取边集并集、顶点取并集，再统一拓扑；关键是**公共模块只能有一个节点**，若各图对公共模块版本要求不同，要先做版本求解（SAT/约束传播），再在选定版本的图上拓扑。顺序上应先版本解析、后拓扑，不能混为一谈。

**增量与缓存**：构建系统通常给每个模块算内容哈希，拓扑序上做"若输入哈希未变则跳过"。失效传播是反向的：$B$ 变了，所有依赖 $B$ 的模块标记为 dirty。这实际上是拓扑序上的反向 BFS。

**边界条件**：空模块集返回空序；孤立模块（无依赖）合法且应出现在序中；自依赖 $A\to A$ 是环；重复边要去重或按边计数入度；节点命名冲突（同名不同路径）要先符号解析。

## 三、形式化与数学基础

**基本定理**：$G=(M,E)$ 存在合法执行序 $\iff$ $G$ 无环。证明：环 $m_1\to m_2\to\cdots\to m_k\to m_1$ 要求 $m_1$ 在 $m_k$ 前又在其后，矛盾；无环时由 Kahn 总能取完 $|M|$ 个点。

**入度不变量**：$indeg(m)$ 表示"尚未构建的直接前置数"。$indeg(m)=0$ 时 $m$ 可构建。删边维护使每个模块被构建时其前置恰已全部构建——这就是"依赖满足"的形式化。

**环报告**：设算法结束未构建集 $S\neq\varnothing$。则 $G[S]$ 中每个点入度 $\ge 1$，故含环。任取 $s\in S$ 沿"未构建前驱"走 $|S|+1$ 步必重复顶点，切片得环。复杂度 $O(V+E)$。

**版本约束边界**：当边带约束 $B \in [2.0,3.0)$，问题是 CSP：$\exists$ 版本赋值 $v: M \to \mathbb{N}$ 使得 $\forall (B,A,c),\ c(v(B))$ 成立，且依赖图在该赋值下无环（通常版本不影响边存在性，但 optional/feature 边会影响）。CSP 求解是 NP-hard 的一般情形，工业上用 MVS（Minimal Version Selection，Go modules）、SAT（PubGrub，Dart）等启发式；**纯拓扑只处理"边是否存在"，不处理"边对应哪个版本"**。

**并行层与关键路径**：按入度归零分层 $L_0, L_1, \dots$，层内可并行。层数 $T$ 是单位耗时下的工期下界；带权时 $T = $ 最长路径权和（关键路径）。设模块耗时 $d(m)$，则
$$finish(m) = d(m) + \max_{p \in pred(m)} finish(p)$$
总工期 $\max_m finish(m)$。

## 四、代码实现

```python
from collections import deque, defaultdict


def build_order(modules, deps):
    """modules: 模块名列表; deps: (mod, need) 表示 mod 依赖 need。
    返回构建顺序；循环依赖时抛 ValueError 并给出一条环链。"""
    adj = defaultdict(list)   # need -> [mod, ...]
    indeg = {m: 0 for m in modules}
    for mod, need in deps:
        if need not in indeg or mod not in indeg:
            raise KeyError(f"unknown module in {mod}->{need}")
        adj[need].append(mod)
        indeg[mod] += 1

    q = deque(m for m in modules if indeg[m] == 0)
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)

    if len(order) != len(modules):
        remain = [m for m in modules if indeg[m] > 0]
        raise ValueError(f"circular dependency: {find_cycle(remain, deps)}")
    return order


def find_cycle(remain, deps):
    """在 remain 子图上找一条环，返回模块名列表"""
    s = set(remain)
    adj = {m: [] for m in s}
    for mod, need in deps:
        if mod in s and need in s:
            adj[need].append(mod)

    color = {}
    stack = []

    def dfs(u):
        color[u] = 1
        stack.append(u)
        for v in adj[u]:
            if color.get(v, 0) == 1:
                i = stack.index(v)
                return stack[i:] + [v]
            if color.get(v, 0) == 0:
                r = dfs(v)
                if r:
                    return r
        stack.pop()
        color[u] = 2
        return None

    for m in s:
        if color.get(m, 0) == 0:
            r = dfs(m)
            if r:
                return r
    return remain


def parallel_levels(modules, deps):
    """分层构建计划：层内可并行"""
    adj = defaultdict(list)
    indeg = {m: 0 for m in modules}
    for mod, need in deps:
        adj[need].append(mod)
        indeg[mod] += 1

    q = deque(m for m in modules if indeg[m] == 0)
    levels = []
    seen = 0
    while q:
        level = list(q)
        levels.append(level)
        nxt = deque()
        for u in level:
            seen += 1
            for v in adj[u]:
                indeg[v] -= 1
                if indeg[v] == 0:
                    nxt.append(v)
        q = nxt
    if seen != len(modules):
        raise ValueError("circular dependency")
    return levels


if __name__ == "__main__":
    modules = ["app", "lib", "core", "utils"]
    # app -> lib -> core, app -> utils
    deps = [("app", "lib"), ("lib", "core"), ("app", "utils")]
    order = build_order(modules, deps)
    pos = {m: i for i, m in enumerate(order)}
    assert pos["core"] < pos["lib"] < pos["app"]
    assert pos["utils"] < pos["app"]
    assert parallel_levels(modules, deps)[0] == ["core", "utils"]

    try:
        build_order(["a", "b", "c"], [("a", "b"), ("b", "c"), ("c", "a")])
        assert False
    except ValueError as e:
        assert "circular" in str(e).lower() or "循环" in str(e) or "环" in str(e)
    print("all tests passed")
```

## 五、与其他技术对比

| 维度 | 拓扑排序（Kahn/DFS） | 约束求解（SAT/PubGrub） | 递归 + visited |
|---|---|---|---|
| 解决的问题 | 边存在时的顺序/判环 | 版本与条件约束 | 简单顺序 |
| 循环依赖 | 可检测、可报链 | 可尝试拆簇 | 只知卡住 |
| 复杂度 | $O(V+E)$ | 最坏指数 | $O(V+E)$ 但信息少 |
| 并行分层 | 直接 | 不直接 | 无 |
| 典型系统 | Make、Ninja、Bazel 内核 | npm resolver、PubGrub | 脚本玩具 |

取舍：**纯顺序/判环用拓扑**；**版本区间/feature 组合用约束求解后再拓扑**；想省事用递归但无法给出可靠错误。工业系统通常是"先版本解析，再拓扑调度"两阶段。

## 六、常见误区

1. **边方向搞反**："A 依赖 B"应建 $B\to A$（B 先）。若建成 $A\to B$，会先构建依赖者，链接直接失败。这是最常见的 bug。
2. **把版本约束塞进拓扑**：拓扑只能表达"先后"，不能表达"用 2.x 还是 3.x"。混在一起写比较器会得到既不满足版本又不稳定的序。
3. **只返回"是否成功"不返回环链**：用户看到 "circular dependency" 无从下手。应在残余图上 DFS 切片出 `a -> b -> c -> a`。
4. **多个独立分量没都入队/入栈**：只从某个入口模块开始，旁支模块被漏掉，构建结果不完整。
5. **增量更新只改局部入度忘了传播 dirty**：$B$ 改了，依赖 $B$ 的下游必须失效；只重编 $B$ 会产出新旧 ABI 混链。

## 八、面试题

**1. 如何向用户报告具体的循环依赖链？**  
Kahn 结束后在"入度仍 >0"的残余子图上 DFS，三色标记找后向边，从灰路径切片出环。输出形如 `app -> lib -> core -> app`。只说"有环"不够。

**2. 多个子系统依赖图如何合并排序？**  
顶点、边取并集（公共模块合并为同一顶点），统一跑 Kahn。若公共模块有版本冲突，先做版本求解再合并。合并后要重新判环，因为跨图新边可能引入环。

**3. 依赖带版本区间时怎么办？**  
这是约束满足，不是纯拓扑。先用 MVS/SAT/PubGrub 选出每个模块的版本，再在"选定版本展开的依赖边"上做拓扑调度。拓扑解决顺序，求解器解决选择。

**4. 如何做增量构建？**  
给每个模块记输入哈希，按拓扑序自底向上：输入哈希未变则跳过。修改模块 $m$ 后，沿反向边 BFS 标记 dirty 并重建。拓扑序保证重建时前置已是新的。

## 九、演进与趋势

现代依赖系统在拓扑之上叠了很多层：**增量图**（Bazel 的 action graph、Turborepo 的 task graph）支持改一个文件只跑受影响子图；**内容寻址缓存**（CAS）使相同输入跨机器复用；**条件/feature 图**（Cargo features、CMake options）让边随配置出现，需要"配置求解 + 拓扑"；**循环容忍**通过 SCC 簇或延迟绑定处理单体遗留代码；**调度层**在拓扑分层上再做资源约束（CPU/内存感知的并行度）。云原生里，Terraform 的 `depends_on`、Argo/Kubernetes Job 的 DAG、Airflow 的 task dependencies，都是拓扑调度的托管形态。理论侧，动态图最短路/动态拓扑、近似分层（关键路径压缩）仍是活跃方向。

## 十、小结

依赖解析 = 把模块与依赖建成 DAG，用拓扑排序产出合法顺序、用残余图定位循环、用分层得到并行机会；版本约束属于前置的求解阶段。理解"边方向、环报告、增量失效传播"三件事，就能把拓扑排序正确地落到包管理器、构建系统与工作流引擎里。
