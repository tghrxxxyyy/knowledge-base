# 自旋锁的原子实现

> 对应 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 12 章，与 Herlihy & Shavit《The Art of Multiprocessor Programming》对自旋锁、TAS 与排队锁的分析。

## 一、背景与挑战

临界区极短时，睡眠锁的代价反而不可接受：一次 futex 系统调用加两次上下文切换可能要数千周期，而临界区本身可能只有十几次内存访问。自旋锁（spinlock）让等待者在用户态原地重试，省去切换，但代价是持续消耗 CPU 与互连带宽。

正确性上，自旋锁依赖一个**原子测试并设置（Test-And-Set, TAS）**或 CAS 操作在竞争下保证互斥。必须在「没有原子原语」的前提下证明会出现两个线程同时进入临界区，这就是为什么自旋锁不能只靠普通读写实现。

此外还有三个工程问题：**公平性**（朴素 TAS 锁可能让某线程长期抢不到）、**缓存颠簸**（所有等待者反复读同一锁变量，使其在核间不断失效）、**内存序**（临界区内的写不能被重排到锁外）。

## 二、核心原理

最朴素的自旋锁是一个整型锁变量 $L$，约定 0 表示空闲、1 表示占用：

- **acquire**：原子地执行 `old = TAS(L)`，即把 $L$ 置 1 并返回旧值。若 `old == 0`，说明自己从空闲态抢到锁，进入临界区；否则原地重试。
- **release**：原子地把 $L$ 写 0（`atomic_store_release` 或 `LOCK` + `MOV`）。

优化点在于等待循环。朴素写法每轮都执行一次 `LOCK` 前缀的原子操作，会让锁变量在核间疯狂迁移。标准改进是**测试-测试-并设置（Test-and-Test-And-Set, TTAS）**：先用普通读（可共享 S 态缓存）观察 $L$，只有观察到空闲时才发一次原子 RMW。这样等待者大多停留在共享态读，抢锁时才争用，显著减少一致性流量。

公平性上，TAS/TTAS 锁都是**非公平**的：刚释放的锁可能被新到达者立刻抢走，长期等待者饥饿。解决之道是排队锁，如 ticket lock（取号-叫号）与 MCS 锁（每线程在本地节点自旋）。

## 三、形式化与数学基础

设锁状态 $L \in \{0,1\}$，TAS 的语义为：

$$\text{TAS}(L): \quad L' \leftarrow 1,\quad \text{return } L_{old}$$

acquire 成功当且仅当 $L_{old} = 0$。由此可证**互斥性**：

$$\forall h_1 \neq h_2:\; \neg\bigl(\text{hold}(h_1) \land \text{hold}(h_2) \text{ 同时成立}\bigr)$$

证明要点：两次成功 acquire 之间存在一次把 $L$ 从 1 写回 0 的 release；而 release 只能由持锁者执行，故两个临界区不可能重叠。

**进展性**：TAS 自旋锁是 **lock-free** 的——任一时刻至少有一个线程能成功获取锁并推进。但它不保证 **starvation-free**：某线程可能被无限次抢先。

TTAS 的一致性代价可用「每次原子 RMW 使该行从 S 态降级」来估算。若 $n$ 个线程在自旋，朴素锁每轮产生 $O(n)$ 次使无效；TTAS 把这一项降到「仅在释放瞬间」发生。

## 四、代码实现

```c
#include <stdatomic.h>

typedef struct { atomic_int v; } spinlock_t;

static inline void lock(spinlock_t *l) {
    for (;;) {
        /* 第一步：只读观察，允许停留在共享态 */
        if (atomic_load_explicit(&l->v, memory_order_relaxed) == 0) {
            /* 第二步：观察到空闲才做原子 RMW */
            if (atomic_exchange_explicit(&l->v, 1, memory_order_acquire) == 0)
                return;
        }
        /* 退避：pause/yield 降低争用与能耗 */
        __builtin_ia32_pause();     /* x86: PAUSE；ARM: YIELD */
    }
}

static inline void unlock(spinlock_t *l) {
    /* release：保证临界区内的写先于解锁可见 */
    atomic_store_explicit(&l->v, 0, memory_order_release);
}
```

Linux 内核的 `qspinlock` 进一步把锁变量编码为「队列尾 + 占有者」的单个 32 位字，兼顾公平与缓存友好；`CONFIG_DEBUG_SPINLOCK` 会加入持有者记录以便死锁诊断。

| --- | --- | --- | --- | --- | --- |

## 六、常见误区

- **「自旋锁总是比互斥量快」**：只在临界区短、竞争低时成立。高竞争下自旋空耗 CPU、挤占超线程资源，甚至比睡眠更慢。
- **「解锁用普通写就行」**：普通写可能被缓冲延迟，且编译器/CPU 可能把它重排到临界区之前；必须用 release 语义，否则他人长时间观察不到释放。
- **「加锁后不需要屏障」**：加锁必须带 acquire、解锁带 release，才能保证临界区内访存不被重排到锁外。
- **「重试循环里不需要 pause」**：`PAUSE`/`YIELD` 提示超线程让出执行资源，能显著降低退出自旋的流水线惩罚与能耗。
- **「自旋锁可以用于睡眠上下文」**：持锁时不可睡眠（不可触发调度、不可缺页），否则可能死锁，这是内核 `spinlock` 的基本约束。

## 八、面试题

**Q1：为什么释放必须用原子写/带 release 的写？**
要点：保证解锁对所有核可见且不被重排到临界区之前，避免等待者长时间观察不到空闲。

**Q2：TTAS 相比 TAS 好在哪里？**
要点：等待者先用普通读停留在 S 态，只在观察到空闲时才发 RMW，大幅减少缓存行使无效流量。

**Q3：自旋锁为什么会饥饿？如何解决？**
要点：TAS/TTAS 非公平；ticket 或 MCS 排队锁以 FIFO 保证有界等待。

**Q4：临界区里能调用可能睡眠的函数吗？**
要点：不能。持自旋锁时若发生调度或缺页，其它核将持续空转，可能死锁或严重退化。

**Q5：`PAUSE` 指令的作用是什么？**
要点：提示这是自旋等待，减少流水线冲刷与能耗，并在超线程上把执行资源让给同核的兄弟线程。

## 九、演进与趋势

- **排队锁成为主流**：MCS/CLH 在 NUMA 与大规模核数下把自旋局部化到每线程私有节点，缓存流量为 $O(1)$。
- **单字编码**：Linux `qspinlock` 把队列尾与锁状态压进一个 32 位字，兼顾公平与空间。
- **自适应锁**：语言运行库根据历史竞争情况在自旋与阻塞之间切换（如 Java 的偏向/自旋优化），以官方最新实现为准。
- **与内存序结合**：现代实现直接使用 acquire/release 原语而非独立屏障指令，减少不必要的 fence。
- **RCU 替代读侧加锁**：读多写少场景用 RCU/epoch 完全避免读侧原子操作。

## 十、小结

自旋锁用原子 TAS/CAS 实现互斥，是短临界区同步最轻量的手段。正确实现需要注意三点：原子获取与 release 释放、等待循环的退避与缓存友好、以及对公平性与持锁期间不可睡眠的约束。性能上它并非万能，竞争激烈时应改用排队锁或睡眠锁。
