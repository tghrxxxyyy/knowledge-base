# 火焰图常见陷阱

> 对应 Brendan Gregg 关于火焰图与采样偏差的论述（brendangregg.com/FlameGraphs），以及《Computer Systems: A Programmer's Perspective》（CSAPP）第 5 章关于性能度量的讨论。

## 一、背景与挑战
火焰图直观，但也容易被误读。错误的采集配置或想当然的解读，会把结论引向反方向。几个典型现象：

- 一个明明存在的函数，在火焰图上「消失」了，于是被误判为「没被调用」或「已被优化掉」。
- 一个耗时很长的函数看起来并不宽，于是被忽略；一个短小但高频的函数反而显得很热。
- 栈在中途断裂，深层的真实调用被错误归因到浅层函数上，制造出假的「热点」。

这些不是工具的 bug，而是采样统计与编译器优化共同作用的必然结果。只有理解偏差的来源，才能正确地读图与优化。

## 二、核心原理
造成失真的主要原因有三类。

- 编译器内联（inline）：编译器把小函数直接展开进调用者，该函数不再拥有独立的栈帧，火焰图上自然看不到它的名字，看起来像「被优化掉了」。这是「消失」的最常见原因，并非它没执行。
- 尾调用优化（tail call）：被调函数复用调用者的栈帧，中间层从栈上消失，层级被压平。
- 采样偏差与平滑效应：定时采样对极短函数命中概率低，导致短函数被系统性低估；反之，长函数被估得相对更准。
- 栈截断：缺少帧指针（FP）与 DWARF/ORC 展开信息时，栈只能展开有限层甚至完全断裂，叶函数的占用被归到错误的父级上。
- 采样与行为同步：若被测行为周期与采样周期成整数比，可能出现系统性偏斜。

理解这些机制，才能判断一张图「可信到什么程度」。

## 三、形式化与数学基础
固定频率采样对执行时长为 $T$ 的函数，命中概率近似为：

$$ P_{hit} \approx \min\left(\frac{T}{\tau},\ 1\right),\qquad \tau = \frac{1}{f} $$

当 $T \ll \tau$（如 $T = 1\mu s$、$f = 99Hz$，$\tau \approx 10ms$）时 $P_{hit} \ll 1$，短函数会被显著低估，这就是「大函数被高估、短函数被低估」的平滑效应的量化表达。

栈截断会让归因发生偏移。设真实调用链为 $f_0 \to f_1 \to \cdots \to f_k$，若展开在第 $m$ 层失败（$m < k$），则 $f_m$ 之后的占用被错误计入 $f_m$：

$$ C_{wrong}(f_m) = C_{true}(f_m) + \sum_{j>m} C_{true}(f_j) $$

这会在图上制造出一个「很宽但本不该那么宽」的假热点。内联的等价效果是把 $f_{child}$ 的采样合并进 $f_{parent}$：

$$ C_{inline}(f_{parent}) = C_{true}(f_{parent}) + C_{true}(f_{child}) $$

因此内联后父函数变宽，不代表父函数自身变慢。恢复可读性的手段包括：关闭内联（-fno-inline）以暴露真实调用、保留帧指针、使用精确事件采样（如 PEBS）。

## 四、代码实现
消除内联与栈截断的编译选项。

```bash
# 保留帧指针并关闭内联，便于观察真实调用层级
gcc -O2 -g -fno-inline -fno-omit-frame-pointer app.c -o app

# 用较高频率采样，提升短函数可见度
perf record -F 199 -g ./app
perf script | ./stackcollapse-perf.pl > app.folded
./flamegraph.pl app.folded > app.svg
```

检查栈是否被截断。

```bash
# 观察是否出现不完整的栈（顶层函数缺失、层级异常浅）
perf record -F 99 -g -p "$(pidof app)" -- sleep 10
perf script --header | head -50

# 若栈只有一两层，通常是缺帧指针或缺展开信息
```

用关闭优化的对照实验判断某函数是否被内联。

```bash
# -O0 下函数应独立出现；-O2 下若消失，说明被内联
gcc -O0 -g -fno-omit-frame-pointer app.c -o app_O0
gcc -O2 -g -fno-omit-frame-pointer app.c -o app_O2
```

## 五、与其他技术对比

| 现象/手段 | 对火焰图的影响 | 缓解方式 | 代价 |
| --- | --- | --- | --- |
| 内联 | 子函数消失，父函数变宽 | -fno-inline、读源码确认 | 性能失真，不利于发布版 |
| 尾调用 | 中间层被压平 | 关闭尾调用优化 | 可能影响递归深度 |
| 采样频率低 | 短函数被低估 | 提高频率、延长时长 | 开销上升 |
| 栈截断 | 假热点、层级错乱 | 保留 FP、带 DWARF/ORC | 体积与性能轻微下降 |
| 采样同步偏差 | 系统性偏斜 | 抖动采样、随机化间隔 | 实现更复杂 |

采样估计与插桩精确计数是两种口径；结论冲突时应以插桩校准采样，而非盲目相信任一方。

## 六、常见误区
- 把内联消失的函数当成「未被调用」，从而重复排查不存在的路径。
- 把栈截断造成的浅层假热点，当成真实瓶颈去优化。
- 用过低采样率得出结论，信噪比太差。
- 在发布版（-O2、strip）上采集却不准备符号文件，导致无法符号化。
- 只盯最顶层的框，忽略其宽度可能来自大量子孙。
- 用颜色判断热度，而颜色在默认配置下无语义。
- 比较总样本数不同的两张图，得出错误的量化结论。

## 九、演进与趋势
- 精确事件采样（如 PEBS）提升采样精度，减少短函数低估。
- 始终开启帧指针（frame pointers all the way）的实践在发行版与运行时中重新受到重视。
- ORC 等高效展开信息在内核中普及，降低对帧指针的依赖。
- 注入标记（instrumentation markers）与混合方案用于校准采样偏差。
- 工具与内核能力持续演进，具体支持以官方文档为准。

## 十、小结
火焰图的可信度取决于采集质量与对偏差的理解。内联会让函数「消失」，尾调用会压平层级，低采样率会低估短函数，栈截断会制造假热点。应对之道是：编译期保留帧指针与符号、按需关闭内联、提高采样率或延长时间，并在解读时始终追问「这个宽度是否被子孙或优化干扰过」。
