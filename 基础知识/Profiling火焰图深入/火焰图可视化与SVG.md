# 火焰图可视化与SVG

> 对应 Brendan Gregg《The Flame Graph》（Communications of the ACM, 2016）与 github.com/brendangregg/FlameGraph 工具集，性能度量背景见《CSAPP》第 5 章。

## 一、背景与挑战
剖析工具（profiler）采集到的原始产物，通常是一堆「栈 + 采样计数」的聚合文本：成千上万条调用栈，每条后面跟着它被采样到的次数。文本列表可以排序，但很难一眼看出瓶颈在哪里——因为性能问题往往藏在调用链深处，而不是排名第一的单个函数。

用树、用表格都试过，但都难以在一个视图里同时表达「调用层级」与「占用比例」。火焰图（Flame Graph）正是为解决这个可视化难题而提出：用宽度编码占用、用纵向编码调用深度，让最宽的框自然成为最值得关注的热点。

它的另一大价值是「零成本共享」：输出为 SVG，可缩放、可搜索、可嵌入网页，成为性能分析的通用语言。

## 二、核心原理
火焰图的数据来源是「折叠栈」（folded stacks）格式，一行表示一条完整调用栈及其采样数：

```
main;compute;matmul 500
main;compute;sort 120
main;io;read 80
```

含义是：栈 `main -> compute -> matmul` 被采样到 500 次，其余同理。绘制规则如下。

- 自底向上是调用链：底部是根（如 main），越往上是被它调用的函数。
- 框的宽度正比于该函数（含其所有后代）的采样占比。
- 同一层的所有框总宽等于其父框宽度，因此不会出现「父比子窄」的矛盾。
- 颜色通常无语义（默认随机色或按热度着色），不应据此判断性能，判断依据是宽度。
- 最顶层的框是叶子（当前正在执行的函数），但「最热」要看整条子树，而非仅看自己在顶部的密度。

flamegraph.pl 负责把折叠格式渲染为 SVG；stackcollapse-*.pl 系列脚本负责把 perf、eBPF、各语言 profiler 的原始输出转成折叠格式。

## 三、形式化与数学基础
设某函数 $f$（含其所有子孙调用）的采样计数为 $C_f$，全局总采样数为 $\sum_{root} C$，则其框宽为：

$$ w_f = \frac{C_f}{\sum_{root} C} \times W_{total} $$

父框与其子框满足宽度守恒：

$$ w_{parent} = \sum_{c \in children(parent)} w_c $$

因此整张图最底层的根框总宽等于画布宽度，且任意层级的框宽之和都等于总宽。函数自身的「独占」占比（self）与其子树占比不同：

$$ w_{self}(f) = w_f - \sum_{c \in children(f)} w_c $$

视觉上任一框若「很宽但子孙很少」，说明该函数自身消耗大；若「很宽但几乎全是子孙」，瓶颈在其下游。采样计数与真实 CPU 时间的关系为：

$$ T_f \approx C_f \cdot \frac{T_{total}}{\sum C} $$

这是「宽度即时间占比」的量化依据；它成立的前提是采样无偏且条件一致。分位数层面，火焰图展示的是均值口径的聚合分布，无法直接读出 P99，需要配合直方图或差分视图。

## 四、代码实现
从折叠格式到 SVG 的完整流程。

```bash
# 1) 准备折叠数据（示例：手工构造）
echo "main;compute;matmul 500" > a.folded
echo "main;compute;sort  120" >> a.folded
echo "main;io;read        80" >> a.folded

# 2) 渲染为 SVG；--title 与 --width 控制展示
./flamegraph.pl a.folded > a.svg

# 宽度比例 500 : 120 : 80，对应三层子调用的耗时占比
```

从真实采样到火焰图（以 perf 为例）。

```bash
# 采集 30 秒、99Hz 的调用栈
perf record -F 99 -g -p "$(pidof myserver)" -- sleep 30

# 展开为文本栈，再折叠
perf script | ./stackcollapse-perf.pl > out.folded

# 生成火焰图；--colors=java 等可换配色（仅观感）
./flamegraph.pl --title "MyServer CPU" out.folded > cpu.svg
```

SVG 内部的本质是一堆带 `rect` 与 `title` 的元素，框宽由脚本按上述公式算好。若要做成可搜索、可缩放的交互版本，可在 SVG 中嵌入脚本，或使用 d3-flame-graph 之类的库。

## 五、与其他技术对比

| 视图 | 横轴含义 | 适合回答的问题 | 局限 |
| --- | --- | --- | --- |
| 火焰图（flame graph） | 采样占比（聚合） | 稳定热点在哪条调用链 | 不显示时间演化 |
| 冰柱图（icicle） | 采样占比，方向相反 | 自上而下看调用 | 与火焰图等价 |
| 时序图（offcputime 等） | 时间 | 阻塞发生在何时、多久 | 不聚合，图很宽 |
| 直方图 | 取值分箱 | 延迟分布与分位数 | 无调用链信息 |
| 差分火焰图 | 变化量 | 优化前后差异 | 需同条件两份数据 |

火焰图偏「空间」（谁占了多少），时序图偏「时间」（什么时候发生），二者互补。

## 六、常见误区
- 把框的高度当时间：高度只表示调用深度，不表示耗时。
- 只看最顶层的框：顶层是叶子，真正要优化的是「宽且其子孙也宽」的路径。
- 把颜色当结论：默认配色无语义，不能凭颜色判断热度。
- 忽略采样前提：低采样率、栈截断或内联都会让图失真（详见相关章节）。
- 不加过滤地看全图：应先按进程、线程或栈深度过滤，避免噪音淹没信号。
- 直接用绝对宽度比较不同图：跨图比较必须先归一化，否则总样本数不同会让结论错位。

## 七、与开源书·权威来源对应
- Brendan Gregg《The Flame Graph》（CACM 2016）系统阐述了火焰图的设计与读法。
- github.com/brendangregg/FlameGraph 提供 flamegraph.pl 与 stackcollapse 系列脚本。
- 《Computer Systems: A Programmer's Perspective》（CSAPP）第 5 章介绍了性能优化与剖析工具的使用。
- 各语言生态的 profiler（如 perf、py-spy）通常可直接输出折叠格式。

## 九、演进与趋势
- 交互式火焰图：基于 d3 支持搜索、缩放与点击下钻。
- 差分火焰图（differential flame graph）：直接呈现优化前后的增减。
- 冰柱图（icicle）：火焰图上下颠倒，便于自上而下阅读调用。
- 持续剖析与在线火焰图：按时间窗口实时刷新，便于观察发布后的变化。

## 十、小结
火焰图用宽度量化占用、用深度展示调用层级，把成千上万条聚合栈压缩成一张可读的图，是定位热路径的视觉利器。读图的核心口诀是「看宽度、追子树、不看颜色、不数高度」。它依赖正确采样与符号化，只有数据采集无误，结论才可靠。
