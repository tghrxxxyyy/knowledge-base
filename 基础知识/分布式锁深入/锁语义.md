# 分布式锁语义

> 对应 Kleppmann《DDIA》第 8 章“分布式锁与租约”，及 Google Chubby 论文。

## 一、背景与挑战
多进程/服务需互斥访问共享资源(如写同一文件、扣库存)。单机锁(互斥量)跨进程无效，需用分布式锁协调，且必须明确其语义边界(互斥、避免死锁、容错)。

## 二、核心原理
理想分布式锁属性：
- 互斥(Mutual Exclusion)：任意时刻至多一个持有者。
- 无死锁：持有者崩溃后锁最终自动释放(靠租约 TTL)。
- 容错：少数节点故障不影响锁服务可用。
- 主动释放：持有者显式解锁。
注意：分布式锁无法保证“客户端已崩溃但仍在持锁操作”，需 fencing 等机制防范。

## 三、形式化 / 数学基础
锁作为资源 R，状态 held / free。安全：不存在 t 使 held by A 且 held by B。
租约：lock granted at t0 with TTL τ；若 holder 未在 t0+τ 前续约，则 lock 可被他人获取。
正确性依赖：τ > 最大时钟漂移 + 操作完成时间，否则出现双持锁窗口。

## 四、代码实现
```python
# 锁语义抽象
class DistributedLock:
    def acquire(self, ttl): ...   # 返回 token 或失败
    def release(self, token): ...  # 仅持对应 token 者能释放
    def renew(self, token, ttl): ...  # 续租
```

## 五、与其他技术对比
- 单机互斥量：快但不跨进程、无容错。
- 数据库唯一约束/SELECT FOR UPDATE：简单但性能与可用性受限。
- 共识型锁(etcd/Chubby)：强一致、可靠。

## 六、常见误区
- 误区：拿到锁就绝对安全。若持锁者 GC 停顿超 TTL，锁已易主，仍写数据会冲突。
- 误区：锁能防止所有并发。需配合 fencing / 版本号。

## 九、演进与趋势
fencing token + 资源端校验成为“安全锁”标准做法；租约与共识结合提升可靠。

## 十、小结
分布式锁的语义核心是互斥、无死锁与容错；但锁本身不足以保证数据安全，需 fencing 等补充。
