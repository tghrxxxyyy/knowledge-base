# 误释放防护

> 对应 Redis 官方锁文档与 Kleppmann《DDIA》第 8 章关于锁释放的警告。

## 一、背景与挑战
分布式锁最易犯的错误是“误释放”——一个客户端释放了另一个客户端持有的锁，导致互斥被破坏。必须保证释放操作只作用于自己持有的那把锁。

## 二、核心原理
防护手段：
- 唯一标识：加锁时写唯一 token/UUID，释放前校验。
- 原子释放：用 Lua / 事务保证“校验 + 删除”原子，避免校验后、删除前锁过期被他人获取而删错。
- 不依赖客户端时钟：过期由服务端判定，释放只校验归属。
- fencing：即便误释放或过期陈旧写，资源端用 token 拒绝。
此外客户端应在“业务完成”后才释放，且避免长任务超过 TTL。

## 三、形式化 / 数学基础
释放谓词：release(token) 成功 iff current_holder_token == token。
原子性要求：check-and-delete 在单步执行(服务器脚本)内完成，期间锁状态不可被并发修改。
违背则出现：A 校验通过 -> A 的锁恰过期 -> B 获锁 -> A 执行删除 -> 误删 B 的锁。

## 四、代码实现
```lua
-- Redis 原子释放
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```
```python
# ZooKeeper: 仅删除自己创建的 ephemeral 节点路径
zk.delete("/locks/r/lock-" + my_seq)
```

## 五、与其他技术对比
- Redis 锁：靠 token + Lua 防误释放。
- ZooKeeper 锁：临时节点随会话删，天然不会删他人(只要不复用会话)。

## 六、常见误区
- 误区：先 GET 判断再 DEL 即可。两步间有竞态，必须原子。
- 误区：用固定字符串当 token。并发会互相误删，必须全局唯一。

## 九、演进与趋势
锁客户端库(如 Redlock 客户端、Curator)把误释放防护固化，降低误用概率。

## 十、小结
误释放防护的核心是“唯一 token + 原子校验删除”，从根本上保证释放只影响自己持有的锁，是分布式锁正确性的底线。
