# 硬件流预取器原理

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》存储器层次设计章节；Jouppi 1990《Improving Direct-Mapped Cache Performance by the Addition of a Small Fully-Associative Cache and Prefetch Buffers》。

## 一、背景与挑战
顺序访存（数组遍历、memcpy、流式解析）具有极强空间局部性，但处理器的取数总是滞后于需求：等到 load 指令发射才发起缺失填充，内存延迟 $L_{mem}$（数百周期）完全暴露。乱序执行窗口有限，靠 OoO 掩盖数百周期延迟并不现实。

硬件流预取器的思路是：既然访问是规则的，那就提前把后续缓存行搬进来，让延迟与计算重叠。挑战在于三点：识别什么算「流」、预取多深多远、以及在预取无用或过度时如何自限。预取器必须在没有编译器信息的前提下做出这些判断，并且所有决策都在几百个周期内完成。

还有一类结构性挑战：预取器与需求访问共享同一条缺失路径。若预取不经过过滤直接进入 MSHR 与填充队列，它会与需求缺失竞争，把「隐藏延迟」变成「制造延迟」。因此现代设计几乎必然包含限流与优先级机制。

## 二、核心原理
预取器挂在 L1/L2 的缺失路径上，观察缺失地址序列。为每条活跃的访问流维护一项状态：起始行号、方向、步长、已预取深度、置信度。当连续若干次缺失满足同一规律（典型是连续的缓存行），就把该地址序列升级为流通行证，按深度 $D$ 与距离 $P$ 发出后续行的预取请求。

现代实现有几个公认的设计点。其一，预取通常发往 L2 而非 L1，避免污染一级缓存。其二，深度随流长度渐进增加（先取 1 行，稳定后加到 $D$），避免短流造成浪费。其三，预取请求进入 MSHR 与填充队列，受队列水位反馈限流。其四，跨页预取需先触发 TLB 查找，否则预取会在无映射页上被静默丢弃。

此外还有几项工程细节：预取地址用饱和加法避免越过地址空间；预取表用散列索引并允许别名，靠置信度快速淘汰错误流；部分实现区分「需求触发型预取」与「自由运行型预取」，前者每 N 次需求缺失发一批，后者独立计时，以带宽为闭环。

## 三、形式化与数学基础
设第 $k$ 次缺失地址为 $a_k$（以缓存行为单位）。单位步长流的判定条件是连续命中同一规律：
$$a_{k} - a_{k-1} = 1 \quad \text{且} \quad a_{k-1} - a_{k-2} = 1$$
满足后对流 $i$ 预取 $a_k + j\ (j = 1..D)$。能否隐藏延迟取决于提前量与迭代开销的关系：若每次迭代耗时 $T_{iter}$，预取距离为 $P$ 行，则需要
$$P \cdot T_{iter} \gtrsim L_{mem} \quad\Longrightarrow\quad P \gtrsim L_{mem} / T_{iter}$$
并行度受限于未完成缺失上限（Little 定律的硬件形态）：在飞行中的预取数约等于
$$N_{inflight} \approx B_{mem} \cdot L_{mem} / L_{line}$$
即带宽乘延迟除以行大小。若预取深度超过这个容量，多出来的请求只会排队，收益递减。收益模型可粗略写为
$$\text{Speedup} \approx \frac{T_{base}}{T_{base} - \alpha \cdot N_{miss}\cdot L_{mem} + N_{pf}\cdot c_{pf}}$$
其中 $\alpha$ 为预取准确率，$c_{pf}$ 为单次预取事务成本。

## 四、代码实现
下面是一个最小可用的流预取器模型：状态表 + 逐级加深 + 队列水位限流。
```c
#define LINE   64
#define STREAMS 32
#define MAXD    8

typedef struct { uint64_t next; int depth; int conf; int active; } stream_t;
static stream_t st[STREAMS];

/* 返回可预取的地址条数，由调用方真正发起请求 */
static int on_miss(uint64_t addr, uint64_t inflight, uint64_t limit) {
    uint64_t line = addr / LINE;
    stream_t *s = &st[(line ^ (line >> 8)) & (STREAMS - 1)];
    if (s->active && s->next == line) {           /* 命中已知流：斜率=1 */
        if (++s->conf > 2 && s->depth < MAXD) s->depth++;   /* 稳定后加深 */
        if (inflight + s->depth > limit) return 0;          /* 队列水位反馈 */
        for (int j = 1; j <= s->depth; j++)
            issue_prefetch((s->next + j) * LINE);           /* 饱和加法在内部做 */
        s->next = line + s->depth;                          /* 跳到已覆盖之后 */
        return s->depth;
    }
    s->next = line + 1; s->depth = 1; s->conf = 0; s->active = 1;
    return 0;                                     /* 首次缺失只建立状态 */
}
```
关键细节：`s->next = line + s->depth` 而不是 `line + 1`，否则同一条流会被重复预取，浪费带宽并触发自我干扰。

## 五、与其他技术对比
| 机制 | 识别的模式 | 需要软件介入 | 硬件成本 | 典型失效场景 |
| --- | --- | --- | --- | --- |
| 硬件流预取器 | 连续行 | 否 | 中（状态表 + 比较器） | 不规则步长、指针追逐 |
| 步长预取器 | 任意固定步长 | 否 | 较高（保存步长） | 随机、多流交替 |
| GHB / 相关性预取 | 历史地址序列 | 否 | 高（历史表） | 冷启动、长历史失配 |
| 空间化预取（按页/块） | 同页内多点 | 否 | 高（位图或标记） | 稀疏访问、页内局部性差 |
| 软件预取指令 | 编译器已知的模式 | 是 | 低 | 需要调参、增加指令 |
| 不预取 | — | 否 | 无 | 大数组遍历延迟全暴露 |

## 六、常见误区
- 认为预取越深越好。深度超出内存级并行上限后，请求排队、缓存被无用行挤占，净收益为负。
- 认为流预取器能处理链表或树遍历。这类指针追逐没有稳定地址差，预取器要么学不到流，要么产生大量无效请求。
- 忽视「预取与需求竞争」。预取请求先到内存控制器，会改变需求请求的调度顺序，极端情况下延迟反而变差。
- 忽略跨页/TLB 影响。预取地址落在未映射页上时被丢弃，长距离预取在页边界处出现周期性空档。
- 以为预取总能提高命中率。预取行的插入可能驱逐仍将被使用的行，命中率指标需要区分需求命中与预取命中。
- 把「预取命中率高」等同于「程序更快」。命中率高但过早或过晚都无收益，时效性（timeliness）才是关键。

## 七、与开源书·权威来源对应
- Hennessy & Patterson：存储器层次设计章节给出预取对缺失率与 AMAT 的影响框架，并讨论多级缓存的预取位置选择。
- Jouppi 1990：提出预取缓冲区与流式预取缓冲的经典结构，是「硬件预取器」这一概念的源头之一。
- Chen & Baer 1995《Effective Hardware-Based Data Prefetching for High-Performance Processors》：系统比较顺序流与步长预取器，给出准确率/覆盖率的评价方法。
- Nesbit & Smith 2004《Data Cache Prefetching Using a Global History Buffer》：GHB 用统一历史表支持多种预取策略，是流预取之外的重要分支。
- Somogyi 等 2006《Spatio-temporal Memory Streaming》：把顺序流的思路推广到「同页内多点重复模式」，解释空间化预取的动机。
- Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 6 章：以矩阵遍历说明空间局部性与访问顺序的收益差异。

## 八、面试题
1. 流预取器如何判断「这是一条流」？要点：观察连续缺失地址差，用置信度计数确认规律，再渐进加深，避免短流浪费。
2. 预取深度与距离的关系？要点：距离决定提前量能否覆盖 $L_{mem}$，深度决定覆盖行数并受在飞行请求上限约束。
3. 为什么预取通常只到 L2？要点：L1 容量小，预取行会驱逐有用行；L2 容量与带宽更适合作为暂存层，再由需求访问搬入 L1。
4. 队列水位反馈解决什么问题？要点：防止预取占满 MSHR 与填充队列，保证需求缺失的优先权。
5. 为什么预取器需要跨页处理？要点：预取地址跨行进入下一页时需 TLB 映射，未命中会导致预取静默丢弃，形成周期性性能空档。
6. 为什么 `next` 要跳过已预取区间？要点：否则后续缺失会重复预取同一批行，既浪费带宽又造成自我干扰，观测为预取命中率虚高。

## 九、演进与趋势
方向之一是多级协同：L2 预取面向流，L1 预取面向紧邻需求；方向之二是空间化：不是逐行，而是按页/按块批量搬入；方向之三是学习型：用历史表或轻量学习器预测复杂模式，并配合反馈机制在线淘汰无用策略。此外还有可编程预取（把预取策略部分放进固件或描述表）与安全限流（防止预取被用于放大侧信道）。具体能力以官方最新文档为准。

## 十、小结
硬件流预取器用极小的状态表换取大规模顺序访存延迟的隐藏，其设计核心不只是「识别流」，更是「自限」：深度、距离、目标层级与队列水位共同决定它是收益还是污染源。
