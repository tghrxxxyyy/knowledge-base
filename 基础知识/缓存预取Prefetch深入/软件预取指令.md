# 软件预取指令

> 对应 Intel SDM Vol.2 指令集参考（PREFETCHh 系列）、ARMv8-A 架构参考手册（PRFM）；Drepper《What Every Programmer Should Know About Memory》；Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 6 章。

## 一、背景与挑战
硬件预取器擅长规则流，但面对依赖数据结构的遍历会失效：链表跳转、哈希桶、稀疏矩阵的非零元、图遍历的邻接表，这些访问的地址由前一次读取的数据决定，硬件在看到地址之前无法知道下一个地址。可选办法是让程序员或编译器显式说「这块数据我很快就会用」，把提前量从硬件转移到软件。

挑战在于：软件预取必须自己判断提前多少、预取到哪一层、以及在什么前提下值得付出额外指令与寄存器压力。预取错了不仅没用，还会挤出有效数据。

## 二、核心原理
x86 提供 PREFETCHT0/T1/T2 与 PREFETCHNTA：分别提示把行取入 L1、L2、L3，或取入「非临时」路径以避免污染缓存（NTA 常用于只使用一次的流式数据）。ARMv8 提供 PRFM，操作数形如 `PLDL1KEEP`、`PLDL2STRM`、`PSTL1KEEP`，把「访问类型（PLD/PST）+ 目标层级 + 缓存策略（KEEP/STRM）」编码在提示里。

这些指令的共同语义是：非阻塞、不保证完成、不改变体系结构可见状态、可被硬件忽略。也就是说它们是提示（hint），不是命令；它们不产生异常（对未映射地址的 PREFETCH 在 x86 上不触发缺页），也不会修改寄存器或内存。

要发挥作用，预取必须与使用点之间有足够距离。距离太小则延迟未覆盖；距离太大则数据可能在真正使用前被驱逐。距离还必须是编译期可静态计算的，因此软件预取最适用于「地址可预测但硬件不擅长」的场景，例如循环中按 `a[i + d]` 的固定偏移访问。

## 三、形式化与数学基础
若数据在时刻 $\tau_u$ 被使用，预取在 $\tau_p$ 发出，则延迟被完全隐藏的条件是
$$\tau_u - \tau_p \ge L_{mem}$$
在循环中提前 $k$ 次迭代发出预取，而每次迭代耗时 $T_{iter}$，则
$$\tau_u - \tau_p \approx k \cdot T_{iter} \quad\Longrightarrow\quad k \gtrsim \frac{L_{mem}}{T_{iter}}$$
预取距离取整到缓存行粒度后，应至少覆盖 $k$ 行：
$$D = \left\lceil \frac{L_{mem}}{T_{iter}} \right\rceil \cdot L_{line}$$
收益判据（考虑无效预取的代价，其中 $\alpha$ 为准确率、$c_{pf}$ 为单次预取成本、$c_{evict}$ 为驱逐代价）：
$$\alpha \cdot L_{mem} \;>\; c_{pf} + (1-\alpha)\,(c_{evict} + c_{bandwidth})$$
实践中的循环展开系数与预取距离需联合调整：展开系数太小则预取指令占比过高（每行都摊上一次预取开销），太大则寄存器压力与 I-cache 占用上升。

## 四、代码实现
gcc/clang 的 `__builtin_prefetch` 的第二个参数是局部性：3 表示高时间局部性（对应 T0），2 为中等（T1），1 为低（T2），0 表示非临时（NTA）。
```c
#include <stddef.h>
#define DIST 16          /* 预取距离，按行数计，需按机器调优 */

double dot(const double *a, const double *b, size_t n) {
    double s = 0.0;
    for (size_t i = 0; i < n; i++) {
        __builtin_prefetch(&a[i + DIST], 0, 3);   /* 读、高局部性 -> L1 */
        __builtin_prefetch(&b[i + DIST], 0, 3);
        s += a[i] * b[i];
    }
    return s;
}
```
主动顺着指针链预取（硬件做不了，因为地址依赖）：
```c
struct node { struct node *next; long v; };
long walk(struct node *p) {
    long s = 0;
    while (p) {
        if (p->next) {
#if defined(__x86_64__)
            __asm__ __volatile__("prefetcht0 (%0)" :: "r"(p->next));
#elif defined(__aarch64__)
            __asm__ __volatile__("prfm pldl1keep, [%0]" :: "r"(p->next));
#endif
        }
        s += p->v;
        p = p->next;
    }
    return s;
}
```
注意事项：在 C 中直接写 `a[i + DIST]` 的取值是越界读取（未定义行为），必须用预取内建或内联汇编形式；同时循环边界要保证预取地址不跨入非法映射（硬件层安全，但语义上仍应避免）。

## 五、与其他技术对比
| 方案 | 可控性 | 适用模式 | 额外成本 | 失效/风险 |
| --- | --- | --- | --- | --- |
| PREFETCHT0 | 高（显式） | 即将复用的行 | 1 µop + 地址计算 | 距离不当则无效 |
| PREFETCHT1/T2 | 高 | 提前量较大 | 同上 | 到不了 L1 则收益有限 |
| PREFETCHNTA | 高 | 只用一次的流式数据 | 同上 | 策略被忽略时仍污染 |
| PRFM（ARM） | 高 | 同族语义，策略更细 | 同 PREFETCH | 需按微架构验证策略 |
| 硬件流预取 | 低（自动） | 顺序/固定步长 | 硬件面积 | 不规则模式无效 |
| 非临时存储 | 高 | 写入不再读的数据 | 绕过缓存 | 后续读该数据代价高 |

## 六、常见误区
- 认为预取指令会阻塞直到数据到达。它们是异步提示，发射后立即继续执行。
- 认为预取保证命中。提示可能被丢弃、被合并，或在到达前被驱逐。
- 距离越大越好。过远会被驱逐，还可能在别处造成污染；距离必须结合 $L_{mem}$ 与迭代开销调优。
- 用数组下标越界访问来「预取」，这是未定义行为，应改用内建函数或内联汇编。
- 忽略预取指令自身成本。每行都插入预取会在小循环中显著增加指令数，反而拖慢。
- 忽略交叉场景。多线程下预取别的核正在写的行会加剧一致性流量（见「预取对 MESI 的影响」）。

## 八、面试题
1. 软件预取与硬件预取如何分工？要点：软件预取处理地址可静态预测但硬件难以学习的模式（如固定偏移、指针链），硬件处理常规顺序流。
2. 预取距离怎么定？要点：使提前量覆盖内存延迟，即 $k \approx L_{mem}/T_{iter}$，再按基准测试微调，同时兼顾寄存器与指令开销。
3. PREFETCHNTA 解决什么问题？要点：对只用一次的流式数据避免占用缓存，减少对有用数据的驱逐。
4. 预取指令会影响程序正确性吗？要点：不会改变可见状态，可能被忽略；但在 C 中不可用越界取值来代替预取。
5. 为什么编译器自动预取不总是有效？要点：需要精确的别名/依赖分析与成本模型，且最优距离随微架构变化，编译器难以在无运行时信息时判断。

## 九、演进与趋势
编译器方向的进展包括基于循环分析的自动预取（如针对数组循环的预取 pass）与成本模型驱动的选择性预取；HPC 编译器常提供显式开关与「预取距离/层级」参数。生态方向上，IR 层（如 MLIR）逐渐把预取作为可分析的优化对象，避免在源级手工插入。安全方面，预取指令被研究用于绕过地址翻译与旁路检查，因此虚拟化与内核场景下的限制策略持续演进，具体以官方最新文档为准。

## 十、小结
软件预取把「什么时候取数据」的决策权交给程序：它以额外指令和调优成本，换取硬件预取盲区内的延迟隐藏。关键在于距离、目标层级与局部性提示三者的配合，以及在不牺牲正确性的前提下插入提示。
