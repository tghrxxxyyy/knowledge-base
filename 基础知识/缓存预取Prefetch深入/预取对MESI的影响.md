# 预取对MESI的影响

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第 2 章（存储器层次设计）与第 5 章（线程级并行），以及 Intel SDM Vol.3 缓存与内存一致性章节。

## 一、背景与挑战
预取在单核时代几乎是免费的午餐：发一个提示，命中就赚，未命中也不改变语义与正确性。进入多核后这个前提失效——预取请求本身就是一次内存读，必须走一致性协议，在其它核上产生探测（snoop）事务，可能迫使远端 M 态行写回、把共享副本降级为 S。

由此产生三类真实挑战。其一，一致性带宽（总线、环形或网格互连上的探测通道）是全局共享资源，而预取把它当私有资源使用。其二，若被预取行的相邻字段正被其它核写，预取会把「真共享」放大成「伪共享」。其三，预取未命中会占用 MSHR 与 L2/L3 填充队列，与需求缺失争夺资源，抬高真实访问的延迟。

一个容易被忽视的第四点是：预取改变了「谁拥有这行」的时序。原本由需求访问决定的共享建立时刻，被提前到预取发起时刻，导致两个核可能同时认为自己是唯一副本，触发协议末端的竞争与重试。这在环形/网状互连上表现为更长的一致性延迟尾部。

## 二、核心原理
MESI 中每行处于 M/E/S/I 之一。预取器发出的请求在协议层等价于一次读（GetS / BusRd），使本地进入 S 态而非独占：这样可避免抢占其它核副本、减少无效化。代价是若程序随后写被预取的行，需要一次额外的一致性升级事务（Upgr / BusRdX / RFO）。反之，独占预取（exclusive prefetch）可省掉这次升级，却会在其它核产生 Invalid，把一致性流量提前消耗。

Snoop 效应是理解本问题的关键：本核预取 A 行（S 态），另一核写 A 行（同缓存行不同字段）时发出 BusRdX，本核被无效化为 I；本核再次访问时又触发预取，又是一次 BusRd。访问模式持续时形成「预取—失效—再预取」颠簸环，一致性流量随核数放大。

在目录协议下还多一层成本：每次预取都要查询目录项，若发生目录项替换（recall 或驱逐），会引入额外的间接请求与更长的往返。跨核预取也会频繁触碰目录条目，压缩阴影目录的有效容量，使原本可命中的目录查询变成 miss。

## 三、形式化与数学基础
总线/目录协议下探测到读请求时的关键状态转移（$M\to S$ 伴随写回）：
$$M \xrightarrow{\text{GetS}} S\ (\text{附 Writeback}),\quad E \xrightarrow{\text{GetS}} S,\quad S \xrightarrow{\text{GetS}} S,\quad I \xrightarrow{\text{GetS}} S$$
设需求读引入的一致事务数为 $C_d$，预取请求数为 $N_{pf}$，其中最终被使用的比例为准确率 $\alpha$，则每笔有效预取分摊的事务量被放大 $1/\alpha$ 倍：
$$C_{total} = C_d + \frac{N_{pf}}{\alpha}$$
伪共享惩罚估计：$N_c$ 个核交替写同一行不同字段，每轮至少一次 BusRdX 与一次写回，
$$T_{penalty} \approx (N_c-1)\,(L_{remote} + T_{inv} + T_{wb})$$
当 $T_{penalty}$ 与循环体时间 $T_{iter}$ 同阶，预取掩盖的延迟被一致性开销完全抵消。可扩展性的判据因此是
$$\frac{N_{pf}/\alpha}{C_d} \ll N_c \quad\text{（否则加速比随核数递减）}$$

## 四、代码实现
```c
#include <stdatomic.h>
/* 同一缓存行内两个逻辑独立计数器：预取整行会互相拉扯 */
struct pair_same { atomic_long a; atomic_long b; } __attribute__((aligned(64)));
struct pair_pad  { atomic_long a; char p1[56]; atomic_long b; char p2[56]; };

void worker_same(int id) {
    atomic_long *p = id ? &pair_same.b : &pair_same.a;
    for (int i = 0; i < N; i++) __builtin_prefetch(p);   /* 取到 S 态 */
    for (int i = 0; i < N; i++) atomic_fetch_add(p, 1);  /* 每轮抢独占 */
}
```
下面的简化模拟直接计数一致性事务，说明「预取整行」如何把事务数翻倍而不是减半：
```python
# 两核交替写同一缓存行：有/无整行预取的事务计数对比
def sim(cores, steps, prefetch_row):
    state, tx = ["I"] * cores, {"BusRd": 0, "BusRdX": 0, "WB": 0}
    for k in range(steps):
        c = k % cores
        if prefetch_row:
            tx["BusRd"] += 1          # 预取取得 S 态，随后写仍需升级
            state[c] = "S"
        if state[c] != "M":
            tx["BusRdX"] += 1         # 申请独占
            if "M" in state:
                tx["WB"] += 1         # 远端 M 行写回
            state = ["I"] * cores
            state[c] = "M"
    return tx

print("no-pf ", sim(2, 1000, False))
print("with-pf", sim(2, 1000, True))
```

## 五、与其他技术对比
| 方案 | 协议请求 | 落地状态 | 对其它核影响 | 后续写代价 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 需求读 load | GetS | S/E | M 行写回、降级 | 可能需升级 | 一次性访问 |
| 共享预取 | GetS | S | 同上，且发生在使用前 | 需一次升级 | 只读数组遍历 |
| 独占预取 | GetM/RFO | E | 立即无效化远端 | 无 | 确定将要写的数据 |
| 非临时预取 | GetS + NTA | S/旁路 | 占用少量一致性资源 | 需升级 | 流式、不重复使用 |
| 读后直接写 | GetM/RFO | M | 无效化远端 | 无 | 生产者独占缓冲 |

## 六、常见误区
- 认为预取只影响本地缓存。实际每次预取都是协议事务，会在互连上产生探测流量。
- 把独占预取当万能优化。它在多核写共享数据时会制造大面积 Invalid，退化为一致性风暴。
- 用填充（padding）解决所有伪共享，却忘了预取器仍会把整行拉过来：应按访问者划分缓存行，而非只按字段划分。
- 忽略 MSHR 争用。预取占满待处理缺失队列时，需求缺失被排到后面，观测到的是「预取让延迟变高」。
- 只看平均延迟不看尾部。一致性重试与远端排队让 p99 延迟明显恶化，平均值可能仍然好看。

## 八、面试题
1. 预取为什么会引起伪共享？要点：预取以整行为单位，行内包含其它核正在写的字段时，会把该行拉入本地共享态，写入方每次都要失效本地副本。
2. 共享预取与独占预取各有什么代价？要点：共享预取省无效化但多一次升级事务；独占预取省升级但抢走所有权，写共享数据时更糟。
3. 如何量化预取带来的一致性损失？要点：计数 BusRd/BusRdX/Writeback 与无效化事件，结合准确率 $\alpha$ 估计每笔有效预取的分摊流量。
4. 为什么预取会抬高需求缺失延迟？要点：MSHR/填充队列是有限资源，预取占用后需求请求排队，延迟被推到后面。
5. 目录协议下预取为何还增加延迟？要点：目录查询与条目替换（recall/驱逐）引入额外往返，预取频繁访问会压缩阴影目录容量。

## 九、演进与趋势
协议侧的趋势是用目录与更细粒度的所有权转移降低广播成本，并把预取标记为「可投机」以便在互连拥塞时优先丢弃；CHI/CXL 一类现代互连把请求类型与缓存状态显式建模，硬件更容易抑制跨核有害预取。同时，预取状态被列入靠投机结构泄露信息的调查范围，安全模型要求限流甚至隔离。具体能力以官方最新文档为准。

## 十、小结
预取在多核下不是本地优化，而是一次必须计入一致性预算的内存事务。评估预取收益时，必须把升级事务、无效化、写回与 MSHR 占用一起算进去，否则会在可扩展性上得到与单核完全相反的结论。
