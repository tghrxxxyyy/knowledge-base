# 异步协作

> 对应 Git 工作流、Conventional Commits、开源评审文化。

## 一、背景与挑战
分布式/跨时区团队无法同步评审，PR 长时间挂起拖慢交付；沟通靠评论易误解。

## 二、核心原理
以小 PR（<400 行）、清晰描述（为什么+是什么）、约定响应 SLA、用草稿 PR（Draft）提前对齐设计。提交信息遵循 Conventional Commits 便于自动化。

## 三、形式化 / 数学基础
评审等待时间 $W = T_{review} - T_{open}$；小 PR 使 $W$ 与缺陷密度下降。PR 规模 $S$ 与评审有效性负相关，建议 $S<400$ 行。

## 四、代码实现
```text
# Conventional Commits
feat(order): add idempotency key
fix(pay): handle timeout on retry
# PR 描述：Context / Change / Risk / Test
```

## 五、与其他技术对比
与同步评审会议相比，异步可扩展、留痕；但需纪律（SLA、小 PR）防止挂起。

## 六、常见误区
误区：一个 PR 改全功能导致无人愿审。误区：无 SLA 致无限等待。

## 七、与开源书 / 权威来源对应
Git 文档、Conventional Commits 规范；Google 工程实践；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"如何优化异步代码评审？为什么 PR 要小？"

## 九、演进与趋势
PR 自动分片、AI 生成变更摘要加速评审。

## 十、小结
小 PR、清描述、设 SLA，让异步评审高效留痕。
