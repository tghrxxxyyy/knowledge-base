# 知识传递

> 对应 Bacchelli & Bird 现代评审研究、Brooks《人月神话》知识孤岛论述，与 CS-Notes: https://github.com/CyC2018/CS-Notes。

## 一、背景与挑战

软件项目的核心风险之一，是**关键知识集中在极少数人脑子里**。当某模块的「为什么这么写、踩过什么坑、边界在哪」只存在于一个人的记忆中，一旦他离职、休假或调岗，团队对该模块的理解就会断裂——这就是 Bus Factor（公交车因子）风险。

文档能部分缓解，但文档常滞后、易过时，且难以承载「决策背后的权衡」。代码评审恰恰提供了一个**低成本、高时效、双向**的知识传播渠道：它发生在代码成型的那一刻，参与者都是上下文相关的人。

## 二、核心原理

评审中的知识传递是双向的：

- **作者 → 评审者**：通过变更与描述，把某块的领域知识、设计取舍、边界条件传递给评审者，使其下次能独立维护或评审。
- **评审者 → 作者**：通过反馈指出更优写法、既有约定、潜在陷阱，作者即时吸收，避免重复踩坑。

机制上，靠**轮流评审（review rota）**与**跨模块评审**扩大每个人的认知面：不让同一模块永远由同一人审，强制不同背景的人接触不同代码，从而把「局部知识」摊薄成「团队知识」，提升知识分散度 $D$。

## 三、形式化与数学基础（含 LaTeX）

定义 Bus Factor $B$ 为使项目停滞的最小关键人数。知识分散度 $D$ 越高，$B$ 越大、单点离职风险越低：

$$
\mathrm{Risk}=f\!\left(\frac{1}{D}\right),\qquad B\propto D
$$

设评审覆盖的模块数为 $M$，人均认知广度随 $M$ 增长。对模块 $i$，其「懂的人」集合大小 $k_i$，团队整体脆弱度可写为

$$
V=\sum_i \frac{1}{\max(k_i,1)}
$$

评审轮值使每个 $k_i$ 持续上升，从而 $V$ 下降。可见**评审不是额外负担，而是降低 $V$ 的杠杆**。

## 四、代码实现（围栏配平）

```python
# 评审轮值，避免总是同一人，强制跨模块认知
REVIEW_ROTA = ["alice", "bob", "carol", "dave"]

def assign_reviewer(pr_module, last_reviewer):
    # 跨模块轮换：不选上次同一个人，尽量选未接触过该模块的人
    candidates = [r for r in REVIEW_ROTA if r != last_reviewer]
    return pick_least_familiar(candidates, pr_module)
```

## 五、与其他技术对比

- 与**写文档**相比：评审中的讨论更及时、更贴近真实决策，且不易过时；文档适合沉淀结论，评审适合传递过程。
- 与**结对编程**相比：评审更省工时，覆盖更广，但实时交互少；二者可结合。
- 与**分享会**相比：评审是「就事论事」的微观传授，密度更高、上下文更强。

## 六、常见误区

- 「只让资深审新人」——单向传递，新人永远只是被教，轮值才能双向成长。
- 「评审后不记录决策背景」——讨论中的「为什么」若不沉淀，知识仍随人走。
- 「知识传递是副作用、可省」——实证显示它常是评审最持久的价值。

## 七、与开源书·权威来源对应

- Bacchelli & Bird 的实证研究把「知识传播」列为评审主要收益之一，并给出量化证据。

## 八、面试题

- 问：代码评审如何降低 Bus Factor？答：通过轮值与跨模块评审，把局部知识摊薄成团队知识，扩大每个模块的「懂的人」，降低单点离职风险。
- 问：知识传递有哪些渠道？答：评审讨论、PR 描述、决策记录（ADR）与注释，其中评审最及时。
- 问：为何不让资深只审新人？答：那只是单向灌输，轮值才能实现双向成长与认知广度。

## 九、演进与趋势

评审评论正被沉淀为**决策记录（ADR）/ 注释 / 代码库内 Wiki**，与代码同库留存；AI 也可在评审中自动生成「这段改动涉及的知识点」摘要，加速新人 onboarding。

### 关键要点速查

- 知识传递是双向的：作者讲清 why，评审者补齐 know-how，二者都成长。
- Bus Factor $B$ 随知识分散度 $D$ 上升，评审轮值是提升 $D$ 的杠杆。
- 不让同一人永远审同一模块，强制跨模块认知，扩大「懂的人」。
- 文档会过时，评审中的讨论更及时，二者应互补而非互相替代。
- 评审后要把「为什么」沉淀为 ADR/注释/库内 Wiki，否则知识仍随人走。
- 只让资深审新人会削弱新人的表达与判断，轮值才能实现双向培养。
- 用 $V=\sum 1/k_i$ 度量团队脆弱度，评审应持续压低每个模块的 $V$。
- 把知识传递写入团队评审规范，使其成为默认动作而非偶然发生。

- 新人 onboarding 应强制参与评审，从 reviewer 与 author 双视角吸收上下文。
- 跨团队轮值能打破「模块壁垒」，让组织级知识流动起来。
- 对关键模块设置「至少两人懂」的红线，作为 Bus Factor 的硬约束。
- 评审评论中出现的设计权衡，应回流到架构文档避免重复讨论。
- 远程/异步团队更依赖评审传递知识，因其缺少非正式的Info交换。
- 用定期「模块 owner 轮换」主动制造知识再分配，防止能力板结。

## 十、小结

评审是双向知识流：用轮值与跨模块评审把个人认知转化为团队资产，是降低关键人风险、提升组织韧性的低成本杠杆。
