# 工具支撑

> 对应 GitHub / GitLab Code Review 文档、Fowler《Continuous Integration》，与 CS-Notes: https://github.com/CyC2018/CS-Notes。

## 一、背景与挑战

纯人工评审有一个结构性浪费：**机械、可自动判定的问题（格式、重复、未用变量、已知安全模式）反复消耗评审者的注意力**。当评审者把精力花在「缩进对不对、命名风格统一吗」上，就无力关注设计意图、边界权衡这些真正需要人判断的事。

工具支撑的核心思想，是**用工具分层接管可自动化项，把稀缺的人类注意力留给不可自动化项**。这不是取代评审，而是重新划分人机边界，让评审更高效、更聚焦。

## 二、核心原理

可按「是否可自动化」把评审工作分层：

- **Linter / Formatter**（如 Prettier、Black、ESLint、Ruff）：统一风格，消除格式争议。
- **SAST / 密钥扫描**（如 Semgrep、gitleaks）：在合并前发现注入、越权、硬编码密钥等安全模式。
- **测试与覆盖率门禁**：自动跑单测、集成测试，并对关键路径设覆盖率阈值。
- **架构/依赖校验**：检查循环依赖、违规 import、过期依赖。
- **CI 串联**：上述检查在 PR 阶段自动执行，结果回显到评审界面。

人工则专注三类工具做不了的事：**设计合理性、意图与需求匹配、边界权衡与可维护性判断**。

## 三、形式化与数学基础（含 LaTeX）

设评审工作中可自动化比例为 $A_{auto}\in[0,1]$，机械问题率为 $m$。工具拦截后，人工所见缺陷降为

$$
m_{human}=(1-A_{auto})\cdot m
$$

人工有效聚焦于不可自动化部分的比例为 $1-A_{auto}$。存在一个甜区：当 $A_{auto}$ 过低，人陷于机械劳动；当门禁过严（$A_{auto}$ 过高且误报多），开发者会绕过检查。最优 $A_{auto}^*$ 由误报成本与人力成本共同决定。

## 四、代码实现（围栏配平）

```yaml
# PR 检查流水线（CI 配置示意）
checks:
  - prettier / black          # 格式统一，零人工成本
  - eslint / ruff             # 静态风格与可疑模式
  - unit + coverage gate      # 覆盖率门禁，未达标阻塞
  - secret-scan / semgrep     # 密钥与常见漏洞扫描
# 上述全过才进入人工评审，人只审设计意图
```

## 五、与其他技术对比

- 与**全人工评审**相比：工具处理机械项、释放人力；但工具不能替代设计与意图判断。
- 与**纯本地检查**相比：CI 把检查标准化、强制化，避免「我本地能过」的偏差。
- 与**文档约定**相比：工具是「可执行的标准」，比口头规范更可靠。

## 六、常见误区

- 「工具报告即评审结论」——工具只管机械项，设计与意图仍需人。
- 「门禁越严越好」——过严致开发者绕过或用 `# noqa` 掩盖，反受损。
- 「上了工具就高枕无忧」——漏报与误报并存，需持续调优规则。

## 七、与开源书·权威来源对应

- GitHub / GitLab Code Review 文档给出 PR 检查、状态门禁与评审工作流的最佳实践。
- Fowler《Continuous Integration》强调把自动化检查作为集成的前置关卡。
- CS-Notes 在 CI/CD 与工程实践板块整理了相关工具链。

## 八、面试题

- 问：哪些评审工作应交由工具？答：格式、重复、已知安全模式、测试与覆盖率等可判定项。
- 问：人工应聚焦什么？答：设计合理性、意图与需求匹配、边界权衡与可维护性。
- 问：门禁过严有何后果？答：开发者绕过检查或用注释抑制告警，反而降低整体质量。

## 九、演进与趋势

AI 评审 Bot 正预读 PR，标注疑似问题、生成变更摘要与测试建议，供人确认；工具从「报错」演进到「给上下文的建议」，进一步释放人力。

### 关键要点速查

- 工具接管机械项，把稀缺的人类注意力留给设计与意图判断。
- Linter/Formatter 统一风格，SAST/密钥扫描查安全，CI 门禁跑测试。
- 人工聚焦三类工具做不了的事：设计合理性、意图匹配、边界权衡。
- 最优自动化比例 $A_{auto}^*$ 由误报成本与人力成本共同决定，非越高越好。
- 门禁过严会诱发绕过（# noqa、抑制告警），反而降低整体质量。
- 工具报告是辅助而非结论，缺陷发现仍需人确认。
- 规则需持续调优，漏报与误报并存，定期复盘告警准确率。
- AI 评审 Bot 正从「报错」演进到「给上下文建议」，进一步释放人力。

- IDE 内联检查让问题在编写时即暴露，比 PR 阶段更前置。
- 把安全规则（如 OWASP 映射）编入 SAST，使评审有安全基线。
- 覆盖率门禁应区分增量与全量，避免历史债拖累新改动。
- 用变更影响分析只跑受影响测试，缩短反馈回路。
- 对误报率高的规则设静默期，避免告警疲劳。
- 工具配置应纳入版本管理，评审策略可审计、可回滚。
- 把「人审」与「机审」结论聚合到统一视图，减少上下文切换。
- 定期清理失效规则，保持检查集精简高效。
- 给开发者提供本地等价工具，让防御左移到提交之前。

## 十、小结

工具接管机械检查、人工聚焦设计与意图，是评审提效的正解；关键在于把可自动化项坚决交给 CI，并把门禁强度调到甜区。
