# 评审目标

> 对应 Bacchelli & Bird 2013《Expectations, Outcomes, and Challenges of Modern Code Review》、Google《Engineering Practices》，与 CS-Notes: https://github.com/CyC2018/CS-Notes。

## 一、背景与挑战

很多团队把代码评审（Code Review）窄化为「上线前找 bug 的最后一关」。当目标被压缩成单一缺陷发现时，会带来一连串副作用：评审者只盯着明显错误，忽略设计意图与可读性的讨论；作者把评审当成「签字放行」的障碍，关系趋于对抗；新人失去在评审中学习的机会。

实证研究显示，缺陷发现只是代码评审诸多收益之一，甚至不是占比最大的那一项。若目标定位不清，评审既低效又伤士气，最终流于形式。明确「评审到底为了什么」，是让评审可持续、有价值的前提。

## 二、核心原理

现代代码评审是**多重目标并存的协作机制**，可拆为五个维度：

- **正确性（correctness）**：发现功能错误、边界条件、并发与安全问题，这是传统最被强调的目标。
- **知识传递（knowledge sharing）**：作者向评审者、评审者向作者双向流动上下文，降低团队关键人依赖。
- **一致性（consistency）**：统一风格、架构约定与命名，避免代码库「风格漂移」。
- **团队所有权（ownership）**：通过多人接触同一块代码，扩大「谁懂这块」的人数，减少 Bus Factor 风险。
- **新人培养（mentoring）**：资深者通过评审反馈传递工程判断力，比单纯读代码更有效。

Google 的研究指出，知识共享与团队认知的收益，常与缺陷发现同等重要，甚至更持久。

## 三、形式化与数学基础（含 LaTeX）

把评审的总收益建模为各目标加权和：

$$
B = w_1\cdot D + w_2\cdot K + w_3\cdot C + w_4\cdot O + w_5\cdot M
$$

其中 $D$ 为缺陷发现量，$K$ 为知识传递量，$C$ 为一致性提升，$O$ 为所有权扩散，$M$ 为培养成效。评审成本 $Cost$ 随变更规模 $S$ 近似线性上升（$Cost\approx c\cdot S$），且存在认知负荷上限——单 PR 过大时，评审者注意力下降，单位时间有效收益锐减。

由此可推导最优变更规模：使边际收益等于边际成本 $\frac{\partial B}{\partial S}=\frac{\partial Cost}{\partial S}$ 的 $S^*$ 即推荐上限，实践中常取 $S^*<400$ 行。

## 四、代码实现（围栏配平）

```python
# 评审目标分层清单（评委据此逐项核对）
REVIEW_GOALS = {
    "correctness":  "需求是否满足、边界与异常处理是否完备",
    "readability":  "命名清晰、结构可读、注释必要且不过度",
    "test":         "关键路径是否覆盖、失败用例是否充分",
    "architecture": "改动是否契合既有抽象与边界",
    "security":     "是否引入注入、越权、密钥泄露等风险",
}

def review_pass(goal_results):
    # 正确性/安全为阻塞项，其余为建议项
    blockers = [g for g, ok in goal_results.items() if g in ("correctness", "security") and not ok]
    return len(blockers) == 0
```

## 五、与其他技术对比

- 与**结对编程**相比：评审可异步、覆盖更广，但缺少实时交互；结对更及时但人力成本高。
- 与**QA 测试**相比：评审在编码早期以极低成本拦截问题，测试在后期验证行为，二者互补。
- 与**静态分析**相比：工具管机械项，评审管设计意图与权衡判断。

## 六、常见误区

- 「评审只挑错」——忽略意图与知识传递，易变成对抗。
- 「评审是签字放行」——把通过评审当成默认，不讨论「为什么这么改」。
- 「目标越多越好」——缺乏优先级会让评审者无所适从，应分清阻塞项与建议项。

## 七、与开源书·权威来源对应

- Bacchelli & Bird 基于对 Google、Microsoft 等团队的调查，量化了评审的多重收益，指出知识共享常被低估。
- Google《Engineering Practices》明确把「正确性、可读性、设计、复杂度、测试」列为评审关注面。
- CS-Notes 在「系统设计/工程实践」板块梳理了评审要点，适合作为入门索引。

## 八、面试题

- 问：代码评审的目标有哪些？为什么不止是找 bug？答：还包含知识传递、一致性、所有权扩散与新人培养；后者收益更持久，且能降低关键人风险。
- 问：如何防止评审变对抗？答：明确评审是对代码而非对人，分阻塞/建议两级，聚焦设计与意图。
- 问：单 PR 为何要小？答：评审收益随规模边际递减，过大导致注意力稀释、缺陷漏出。

## 九、演进与趋势

评审正向「AI 预评审」演进：自动检查风格、潜在漏洞与重复，把人从机械项解放出来，聚焦设计与意图讨论。同时目标清单被模板化进 PR 描述，让多维目标可勾选、可度量。

### 关键要点速查

- 评审目标不止找 bug，还含知识传递、一致性、所有权扩散与新人培养。
- 知识共享与团队认知的收益常比缺陷发现更持久，不应被低估。
- 用 $B=w_1D+w_2K+\dots$ 把多维目标显性化，避免只盯正确性。
- 单 PR 规模 $S$ 与评审有效性负相关，推荐控制在 400 行以内。
- 区分阻塞项（正确性/安全）与建议项（风格/偏好），减少对抗。
- 评审成本随规模近似线性上升，过大 PR 会稀释注意力、漏出缺陷。
- 把目标清单模板化进 PR 描述，让多维目标可勾选、可度量。
- 引入 AI 预评审释放人力，让人聚焦设计与意图讨论。

- 评审文化建设比工具更重要，目标共识需团队反复对齐而非一次宣贯。

## 十、小结

代码评审是兼顾缺陷、知识、一致性与培养的团队协同机制；明确多重目标并分层优先级，才能让评审既有效又不伤协作。
