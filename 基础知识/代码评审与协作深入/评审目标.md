# 评审目标

> 对应 "Modern Code Review" 研究（Bacchelli & Bird）、Google 工程实践。

## 一、背景与挑战
评审若只找 bug，会忽略知识传播与风格统一，且易变成对抗；目标不清导致效率低、关系紧张。

## 二、核心原理
评审多重目标：发现缺陷、知识传递、一致性（风格/架构）、团队ownership、新人培养。Google 研究指出缺陷发现只是收益之一，知识共享同样重要。

## 三、形式化 / 数学基础
评审收益 $B = w_1\cdot defectsFound + w_2\cdot knowledgeShared + w_3\cdot consistency$。成本 $C$ 随评审规模近似线性上升，故控制单 PR 体量。

## 五、与其他技术对比
与结对编程相比，异步评审规模更大但实时性弱；与 QA 测试互补，评审偏早期廉价发现。

## 六、常见误区
误区：评审只挑错伤士气。误区：把评审当签字放行忽视意图讨论。

## 八、面试题
"代码评审的目标有哪些？为什么不止是找 bug？"

## 九、演进与趋势
AI 预评审（自动风格/漏洞提示）让人聚焦设计与意图。

## 十、小结
评审兼顾缺陷、知识、一致性，是团队协同机制。
