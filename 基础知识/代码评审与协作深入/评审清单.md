# 评审清单

> 对应 Google《Engineering Practices》Code Review、Robert C. Martin《Clean Code》，与 CS-Notes: https://github.com/CyC2018/CS-Notes。

## 一、背景与挑战

当评审完全靠评审者「自由发挥」时，结果高度依赖个人经验：资深者关注设计，新人只敢看格式；同一类问题在不同 PR 中被反复提及或遗漏；团队对「什么叫评审通过」没有共识。这种方差会让评审既不可预期，也难复盘。

结构化清单（checklist）的价值，正是把分散在个人脑中的关注点**外显为团队共识**，让每次评审都覆盖相同的关键维度，并对高优先级项设硬门槛。但清单若设计不当，又会变成走过场。如何在「统一标准」与「保留判断」之间平衡，是清单设计的要义。

## 二、核心原理

一份实用的评审清单应分层覆盖以下维度，并按优先级（P0/P1/P2）组织：

- **设计（design）**：改动是否该做、是否放在正确边界、是否引入不必要的复杂度。
- **功能（functionality）**：需求是否满足、边界与异常是否处理、可逆性与回滚是否考虑。
- **复杂度（complexity）**：能否更简单、是否过度抽象、是否过度设计。
- **测试（testing）**：关键路径是否覆盖、失败用例是否充分、是否含回归测试。
- **可读性与命名**：命名是否表意、结构是否清晰、注释是否必要且不冗余。
- **安全与日志**：是否引入注入/越权/密钥泄露、关键路径是否有可观测日志。
- **并发与性能**：是否存在竞态、是否有明显的性能回退。

P0 为阻塞项（如安全漏洞、需求不符），未过则禁止合并；P1/P2 为建议项。

## 三、形式化与数学基础（含 LaTeX）

把清单视为目标集合 $C=\{c_1,\dots,c_n\}$，每项有优先级权重 $w_i\in\{0,1,2\}$。评审覆盖度

$$
\mathrm{Cov}=\frac{|\{c_i: \text{已核}\}|}{n}
$$

合并门禁定义为：当且仅当所有 P0 项通过，即

$$
\mathrm{Block}(PR)=\bigwedge_{c_i\in P0} \mathrm{pass}(c_i)
$$

理想状态下 $\mathrm{Cov}\to1$ 且 P0 全过；若清单过长使评审者疲劳，$\mathrm{Cov}$ 反而下降，故项数与粒度需受控。

## 四、代码实现（围栏配平）

```text
# 分层评审清单（PR 模板可勾选）
P0 阻塞项（不过不准合）:
  - 需求与实现一致
  - 无安全漏洞（注入/越权/密钥）
  - 有关键路径测试 + 回滚方案

P1 建议项:
  - 可读性 / 无多余复杂度
  - 命名清晰、结构合理
  - 关键路径有日志与监控

P2 可选:
  - 注释必要且不冗余
  - 风格统一（交由 formatter 自动）
```

## 五、与其他技术对比

- 与**自由评审**相比：清单降低方差、统一标准；但不应僵化到忽略上下文判断。
- 与**纯自动化检查**相比：工具管格式/漏洞，清单管设计与意图，互补。
- 与**过长规范文档**相比：清单精炼可勾选，更易被执行与复盘。

## 六、常见误区

- 「清单越长越全」——过长变成走过场，评审者机械打勾。
- 「只评格式不评设计」——把清单退化成 linter 的重复。
- 「清单是铁律」——对特殊上下文应允许说明理由的偏离。

## 七、与开源书·权威来源对应

- Google《Engineering Practices》「Code Review Checklist」给出设计/功能/复杂度/测试/命名等维度。
- Martin《Clean Code》强调可读性与复杂度控制，是清单可读项的理论来源。
- CS-Notes 在代码规范板块整理了可落地的评审要点清单。

## 八、面试题

- 问：你的评审清单包含哪些维度？答：设计、功能、复杂度、测试、可读性、安全、并发与性能，并按 P0/P1/P2 分级。
- 问：如何避免评审流于格式？答：把格式交给 formatter/CI，人聚焦设计与意图，且 P0 必须含功能与安全。
- 问：清单过长怎么办？答：精简到可勾选，把机械项交给工具，保留高价值判断项。

## 九、演进与趋势

清单正被模板化进 PR 描述与 Bot 自动勾选：CI 先过格式/测试，人只核设计与意图；并随团队演进持续裁剪项。

### 关键要点速查

- 清单外显团队共识，降低评审方差，但项数与粒度需受控防走过场。
- 覆盖设计、功能、复杂度、测试、可读性、安全、并发七维度。
- P0 为阻塞项（安全/需求/关键测试），未过禁止合并；P1/P2 为建议。
- 格式与风格交给 formatter/CI，人只审设计与意图，避免退化成 linter。
- 对特殊上下文允许「经说明的偏离」，清单是引导而非铁律。
- 覆盖度 $\mathrm{Cov}$ 可作为团队评审质量的度量指标之一。
- 清单应随团队演进持续裁剪，删掉长期不触发的高成本项。
- 把清单模板化进 PR，配合 Bot 自动勾选，降低执行摩擦。

## 十、小结

结构化清单统一了评审标准、聚焦高优先级，但需克制长度、与工具分工，才能既降方差又不僵化。
