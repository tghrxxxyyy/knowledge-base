# 评审清单

> 对应 Google《Engineering Practices》Code Review、Clean Code 视角。

## 一、背景与挑战
评审无结构则遗漏重点、标准不一，资深与新人关注点差异大，结果不可预期。

## 二、核心原理
用分层清单：设计（是否该改、边界）、功能（需求满足、边界条件）、复杂度（能否更简单）、测试（覆盖关键路径）、命名与可读性、安全与日志、并发与性能。

## 三、形式化 / 数学基础
清单作为集合 $Checklist=\{c_1..c_n\}$，评审覆盖度 $Cov=\frac{已核\ c_i}{n}$。每 $c_i$ 有优先级，P0 项未过则阻塞合并。

## 四、代码实现
```text
P0: 需求正确 / 无安全漏洞 / 有关键测试
P1: 可读性 / 无多余复杂度
P2: 命名 / 注释必要
```

## 五、与其他技术对比
与"自由发挥评审"相比，清单降低方差；但不应僵化到忽略上下文判断。

## 六、常见误区
误区：清单过长变成走过场。误区：只评格式不评设计。

## 七、与开源书 / 权威来源对应
Google《Engineering Practices》"Code Review Checklist"；Martin《Clean Code》；CS-Notes: https://github.com/CyC2018/CS-Notes

## 八、面试题
"你的评审清单包含哪些维度？如何避免评审流于格式？"

## 九、演进与趋势
清单模板化进 PR 模板与 Bot 自动勾选。

## 十、小结
结构化清单统一标准，分层聚焦高优先级。
