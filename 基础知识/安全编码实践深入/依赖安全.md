# 依赖安全

> 对应软件供应链与第三方依赖安全（Supply Chain Security）。

## 一、背景与挑战
现代应用大量依赖开源库，单个被投毒/含漏洞的依赖即可危及整个系统。需持续发现、评估与修复依赖风险。

## 二、核心原理
- SBOM（软件物料清单）：清点直接与传递依赖。
- 漏洞扫描：对照 CVE 数据库（如 GitHub Advisory、NVD）。
- 锁定版本 + 校验和/签名：防依赖被替换（防 typosquatting）。
- 最小依赖：移除未使用、优选维护活跃项目。

## 三、形式化 / 数学基础
- 依赖图 $G=(V,E)$，节点含版本与已知 CVE 集合 $C(v)$。
- 风险评分：$Risk = \sum_{v} severity(C(v)) \cdot reachable(v)$，可达性加权。
- 可重现构建：锁定 hash 使 $build(src, lock)=artifact$ 确定性。
- 供应链签名：SLSA 等级证明来源与完整性。

## 四、代码实现
```bash
# 生成 SBOM 与漏洞扫描
syft packages ./app -o spdx-json > sbom.json
grype sbom:sbom.json                 # 对照 CVE
# 依赖锁定（npm 示例）
npm ci                               # 用 package-lock 确定性安装
npm audit --omit=dev                 # 仅生产依赖审计
```

## 五、与其他技术对比
- 固定版本 vs 浮动（^）：固定可重现但需主动更新；浮动易引入意外。
- 扫描 vs 修复：扫描发现，修复闭环才降风险。
- 自研 vs 依赖：自研可控但有实现成本与 bug 面。

## 六、常见误区
- 从不更新依赖（漏洞累积）。
- 盲目 `npm install` 未审包名（typosquatting 攻击）。
- 忽略传递依赖的漏洞。

## 七、与开源书 / 权威来源对应
- OWASP 依赖项安全备忘单（Dependency Management）。
- CNCF/SLSA 软件供应链安全框架。

## 九、演进与趋势
SLSA 供应链等级；Sigstore 签名；可达性分析减少误报。

## 十、小结
依赖安全靠 SBOM 清点、CVE 扫描、版本锁定与签名校验，并持续修复闭环，抵御供应链攻击。
