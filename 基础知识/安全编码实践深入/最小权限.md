# 最小权限

> 对应最小权限原则（Principle of Least Privilege, PoLP）。

## 一、背景与挑战
程序/用户/服务常获得超出所需的权限，一旦被攻破，攻击面被放大。最小权限把每个主体的权限限制在必要范围内。

## 二、核心原理
- 主体（进程、用户、服务账号）仅拥有完成任务所需权限。
- 默认无权限，按需授权（default-deny）。
- 权限随时间收敛：临时提权用完即回收。
- 横向隔离：不同服务用不同身份，限制横向移动。

## 三、形式化 / 数学基础
- 权限集 $P_s$ 对主体 $s$，最小权限要求 $P_s = \text{needed}(s)$（恰好必要）。
- 越权度量：$excess(s)=|P_s \setminus needed(s)|$，目标为 0。
- 默认拒绝矩阵：$A[i][j]=1$ 仅当任务 $j$ 确需权限 $i$。
- 临时凭证有效期 $T_{tmp}$ 短，降低泄露窗口。

## 四、代码实现
```python
# 以专用低权限用户运行，而非 root
# Dockerfile
RUN useradd -m appuser
USER appuser
# 数据库：仅授权所需表的 SELECT/INSERT
GRANT SELECT, INSERT ON shop.orders TO 'app'@'%';
# 而非 GRANT ALL PRIVILEGES
```

## 五、与其他技术对比
- 最小权限 vs 方便：前者安全但需精细设计；后者易用但风险高。
- 共享超级账号 vs 每服务独立账号：后者隔离故障/入侵。
- RBAC vs 静态授权：RBAC 便于收敛与审计。

## 六、常见误区
- 生产用 root/admin 运行服务。
- 一个 DB 账号授予 ALL 用于所有功能。
- 长期有效的临时提权未回收。

## 七、与开源书 / 权威来源对应
- OWASP 安全设计原则（Least Privilege）。
- Saltzer & Schroeder《Protection of Information in Computer Systems》八大原则。

## 九、演进与趋势
零信任与短期令牌（STS）、workload identity 自动化最小权限。

## 十、小结
最小权限把主体权限收敛到恰好必要，配合默认拒绝与隔离显著限制入侵后的横向移动。
