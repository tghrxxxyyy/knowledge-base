# 密钥管理

> 对应应用中密钥/凭据的安全管理（与安全编码视角）。

## 一、背景与挑战
应用常需数据库密码、API Key、token。硬编码到源码或配置文件并入库，是泄露最高危途径。应集中管理与运行时注入。

## 二、核心原理
- 不入库：密钥禁止进入版本控制；用 secrets manager（Vault/AWS Secrets Manager/KMS）。
- 运行时注入：通过环境变量或挂载卷注入，内存中使用、用完擦除。
- 轮换与审计：定期轮换、访问留痕。
- 分级：区分构建期、运行时、第三方密钥，各自隔离。

## 三、形式化 / 数学基础
- 泄露面 $S$ = 密钥出现位置集合；目标 $|S|$ 最小（仅运行时内存）。
- 轮换窗口 $W=t_{comp}-t_{rotate}$，越短越安全。
- 访问控制矩阵：仅特定 workload 可读特定 secret（基于 identity）。
- 静态加密：secret 在存储/传输中均以 KEK 加密（见密码学密钥管理）。

## 四、代码实现
```python
# 从环境变量/密钥管理服务读取，绝不硬编码
import os
db_pwd = os.environ["DB_PASSWORD"]          # 运行时注入
# 或用 Vault 动态秘钥
resp = vault.read("database/creds/app")
db_pwd = resp["data"]["password"]
# 避免打印/日志输出
logging.info("connecting")                   # 不记录密码
```

## 五、与其他技术对比
- 硬编码 vs Secrets Manager：后者可轮换、可审计、不入库。
- 环境变量 vs 挂载文件：文件权限更可控，避免进程环境被读。
- 静态密钥 vs 动态短期密钥：动态降低泄露窗口。

## 六、常见误区
- 把密钥写进代码并提交 Git（且以为删掉历史就干净）。
- 把密钥放进前端代码（用户可见）。
- 长期不轮换、无访问审计。

## 九、演进与趋势
动态短期凭据；机密计算保护运行时密钥；Git 预提交扫描防泄露。

## 十、小结
应用侧密钥管理以不入库、运行时注入、定期轮换与最小访问为核心，杜绝硬编码泄露。
