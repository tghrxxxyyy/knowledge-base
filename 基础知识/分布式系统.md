# 分布式系统实战（Raft / 分布式锁 / 分布式 ID / 缓存策略 / 幂等设计）

> 分布式系统 =「**多节点协作 + 网络不可靠 + 节点可能宕机**」的环境下，如何保证数据一致性、可用性和性能。本篇从理论概览升级为实战指南：Raft 共识实现细节、分布式锁全方案对比、分布式 ID 选型、缓存策略与一致性、幂等设计全链路。

---

## 一、CAP 与选型决策

### 1.1 CAP 定理

```
C（Consistency）：所有节点在同一时刻看到相同数据
A（Availability）：每个请求都能收到响应（不保证最新数据）
P（Partition Tolerance）：网络分区时系统继续运行

网络分区必然发生 → 必须在 C 和 A 之间权衡

CP 系统：ZooKeeper、etcd、HBase（一致性优先）
AP 系统：Eureka、Cassandra、DynamoDB（可用性优先）
CA 系统：单机 MySQL（无网络分区）
```

### 1.2 BASE 理论

```
BA（Basically Available）：基本可用
S（Soft State）：软状态（允许中间状态）
E（Eventually Consistent）：最终一致

BASE 是 CAP 中 AP 的延伸：允许暂时不一致，但最终一致
```

### 1.3 选型决策

| 场景 | 选择 | 理由 |
|------|------|------|
| 金融交易 | CP（强一致） | 资金不能错 |
| 用户画像 | AP（高可用） | 短暂不一致可接受 |
| 库存扣减 | CP + 补偿 | 先强一致，失败后补偿 |
| 社交 Feed | AP + 最终一致 | 时效性要求不高 |
| 配置中心 | CP（强一致） | 配置不能出错 |
| 服务注册 | AP（高可用） | 挂一个节点不影响服务发现 |

## 二、Raft 共识协议（深入）

### 2.1 核心机制

```
Raft = Leader 选举 + 日志复制 + 安全性保证

角色：
  Leader：接收写请求，复制日志到 Follower
  Follower：接收 Leader 日志，投票选举
  Candidate：选举中（临时角色）

任期（Term）：单调递增的逻辑时钟，每次选举 +1
```

### 2.2 选举流程

```
1. Follower 选举超时（150~300ms 随机）
2. 转 Candidate，自增 term，给自己投票
3. 向所有节点发起 RequestVote RPC
4. 获得多数票 → 成为 Leader
5. Leader 发送心跳（AppendEntries）建立权威
6. Follower 收到心跳 → 重置选举超时 → 承认 Leader
```

### 2.3 日志复制

```
1. Client 发送写请求到 Leader
2. Leader 追加日志条目到本地日志
3. Leader 通过 AppendEntries RPC 复制到所有 Follower
4. 多数节点写入成功 → Leader 提交（apply 到状态机）
5. Leader 通知 Follower 提交

日志匹配保证：
  - 两条日志 index 相同且 term 相同 → 内容相同
  - Leader 完整性：已提交的日志一定在新 Leader 中
```

### 2.4 Raft 与 ZooKeeper ZAB 对比

| 维度 | Raft | ZAB |
|------|------|-----|
| Leader 选举 | 随机超时 + 投票 | 类似（Fast Leader Election） |
| 日志复制 | AppendEntries | Proposal/Ack/Commit |
| 状态机 | 每个节点独立 apply | 每个节点独立 apply |
| 实现复杂度 | 较低（设计目标） | 较高 |
| 使用 | etcd、TiKV、Consul | ZooKeeper |

## 三、分布式锁（全方案对比）

### 3.1 方案对比

| 方案 | 实现 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **Redis SETNX** | `SET key val NX EX ttl` | 简单高性能 | 锁过期但业务未完成 | 低竞争场景 |
| **Redlock** | 多 Redis 节点多数派 | 分布式容错 | 争议大（Martin Kleppmann 批评） | 中等可靠性 |
| **ZooKeeper** | 临时顺序节点 + Watch | 强一致、公平锁 | 性能低（ZAB 共识） | 强一致性场景 |
| **etcd** | Lease + Revision + Watch | 强一致、云原生 | 较新，生态不如 ZK | K8s/云原生 |
| **MySQL** | 唯一索引/悲观锁 | 简单 | 性能最低 | 低并发兜底 |

### 3.2 Redis 分布式锁实现

```java
// 加锁（原子操作）
String lock = redis.set("lock:order:123", requestId, "NX", "PX", 30000);

// 解锁（Lua 脚本，保证原子性）
String lua = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """;
redis.eval(lua, List.of("lock:order:123"), List.of(requestId));

// 看门狗续期（Redisson 自动实现）
// 锁过期时间 30s，每 10s 续期一次
```

### 3.3 Redlock 争议

```
Martin Kleppmann 批评 Redlock：
  1. 时钟跳跃可能导致锁失效
  2. GC 暂停可能导致锁过期
  3. 建议用 fencing token（递增令牌）保证安全

Antirez 回应：
  1. 时钟跳跃可以通过运维避免
  2. Redlock 的安全性依赖多数派
  3. fencing token 需要存储层支持

结论：Redlock 适合中等可靠性场景；强一致场景用 ZooKeeper/etcd
```

### 3.4 Fencing Token（隔离令牌）

```
Client1 获取锁（token=1）→ 写入存储 → 存储拒绝（token 太旧）
Client2 获取锁（token=2）→ 写入存储 → 成功

原理：存储层校验 token 递增，拒绝旧 token 的写入
实现：Redis INCR / ZK zxid / etcd revision
```

## 四、分布式 ID 选型

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| UUID | 无依赖 | 无序、索引碎片化 | 客户端生成/纯唯一 |
| 雪花算法 | 有序、高性能 | 时钟回拨风险 | 订单/消息主键 |
| 号段模式 | 严格递增 | 依赖 DB | 流水号 |
| Redis INCR | 严格递增 | 依赖 Redis | 计数/短 ID |
| 数据库自增 | 简单 | 单机瓶颈 | 低频场景 |

**选型关键**：趋势有序 → 雪花；严格递增 → 号段；无顺序要求 → UUID v7

## 五、分布式缓存策略

### 5.1 缓存模式

| 模式 | 流程 | 适用 |
|------|------|------|
| Cache-Aside | 先读缓存→miss 读 DB→写缓存 | 通用（最常用） |
| Read-Through | 缓存层自动加载（应用无感知） | 缓存框架支持 |
| Write-Behind | 写缓存→异步写 DB | 写多读少（有丢数据风险） |
| Write-Around | 写 DB→不更新缓存（下次读时加载） | 写多读多（一致性要求高） |

### 5.2 缓存一致性

```
问题：DB 更新了但缓存还是旧值 → 读到脏数据

解决方案：
  1. 延迟双删：更新 DB → 删缓存 → 延迟 500ms → 再删一次
  2. 订阅 binlog：Canal 监听 DB 变更 → 异步删缓存（最终一致）
  3. 消息队列：更新 DB 发 MQ → 消费者删缓存
  4. 版本号：缓存带版本号，版本不一致则重新加载
```

### 5.3 缓存三大问题

| 问题 | 说明 | 解决 |
|------|------|------|
| 缓存穿透 | 查询不存在的数据（每次都打 DB） | 布隆过滤器 / 缓存空值 |
| 缓存击穿 | 热点 key 过期瞬间大量请求打 DB | 互斥锁（setnx）/ 永不过期 |
| 缓存雪崩 | 大量 key 同时过期 | 过期时间加随机值 / 多级缓存 |

## 六、幂等设计全链路

### 6.1 为什么需要幂等

```
网络重试、用户重复点击、MQ 重复消费 → 同一操作执行多次
  → 数据重复/资损/状态错乱

幂等 = 同一操作执行一次和执行多次效果相同
```

### 6.2 幂等方案

| 方案 | 原理 | 适用 |
|------|------|------|
| 唯一索引 | 数据库唯一约束 | 创建类操作 |
| Token 机制 | 下单前获取 token，提交时校验并删除 | 表单提交 |
| 状态机 | 订单状态只能单向流转（待支付→已支付→已完成） | 状态类操作 |
| 去重表 | 操作 ID 存去重表（唯一索引） | 通用 |
| Redis SETNX | 操作 ID 作为 key（NX EX） | 高并发 |
| 乐观锁 | version 字段 CAS 更新 | 更新类操作 |

### 6.3 全链路幂等

```
入口层：Token 机制 / 验证码（防重复提交）
服务层：唯一索引 / 去重表 / 状态机（业务幂等）
数据层：乐观锁 / 事务（数据一致性）
消息层：消息 ID 去重（MQ 消费幂等）
```

## 七、分布式限流

| 方案 | 粒度 | 适用 |
|------|------|------|
| 令牌桶 | 固定速率 + 突发 | 通用限流（Guava RateLimiter） |
| 滑动窗口 | 时间窗口内计数 | API 限流（Sentinel） |
| 漏桶 | 固定速率处理 | 流量整形（Nginx） |
| 分布式限流 | Redis + Lua | 多实例统一限流 |
| 信号量 | 并发数控制 | 资源池限流（Hystrix） |
