# 分布式系统理论（总纲）

## 〇、本体介绍

**分布式系统**：多台计算机通过网络协同，对外表现为一个整体。它把「单机不可能完成的规模/可用/性能」拆解到多机，代价是**网络不可靠、时钟不同步、部分失败**带来的复杂性。

**为什么需要总纲**：CAP/BASE、共识、一致性模型这些概念散落在中间件、架构、场景设计里，但缺一篇把「理论底座」串起来的总纲。本文即为此。

**核心命题**：在「网络会延迟/丢包、节点会宕机、时钟会漂移」的前提下，如何就「共享状态」达成一致、保证正确与可用。

---

## 一、CAP 定理

- **C（一致性）**：每次读都能拿到最新写（线性一致）。
- **A（可用性）**：每个请求都有响应（不保证最新）。
- **P（分区容忍）**：网络分区（节点间失联）时系统仍能继续工作。
- **结论**：**网络分区 P 不可避免**（广域网必发生），所以实际是在 **CP（保一致弃部分可用，如 ZooKeeper/etcd）** 与 **AP（保可用弃强一致，如 Cassandra/DNS）** 间取舍。CA 仅在无分区时存在（单机或可信内网）。

---

## 二、BASE 理论（AP 的妥协）

- **BA（基本可用）**：故障时允许响应时间变长或部分功能降级。
- **S（软状态）**：允许中间状态（数据不一致）存在一段时间。
- **E（最终一致）**：经过一段时间，数据最终达成一致。
- 是 CAP 中 AP 系统的工程化指导，典型：主从异步复制、消息队列最终一致。

---

## 三、一致性模型（从强到弱）

- **线性一致（Linearizable）**：全局实时有序，最严（如 etcd、ZooKeeper 的写）。
- **顺序一致（Sequential）**：所有节点看到的操作顺序一致，但不要求实时。
- **因果一致（Causal）**：有因果关系的操作保序（如评论先于回复）。
- **最终一致（Eventual）**：无新写后最终一致（BASE）。
- **强一致 vs 弱一致**：线性/顺序属强；最终/因果属弱。

---

## 四、共识算法（Consensus）

- **Paxos**：理论基石（Basic Paxos / Multi-Paxos），难懂但严谨；选 Proposer/Acceptor/Learner 就单值达成一致。
- **Raft**（工程主流，etcd/Consul/TiKV 用）：把共识拆成**领导选举、日志复制、安全性**三块，易懂。任期(term)+心跳+日志匹配保证。
- **Zab**（ZooKeeper）：类 Raft 的原子广播。
- **Viewstamped Replication (VR)**：另一派。

> 关联：TiDB（TiKV）用 Raft 做多副本；注册中心/Nacos 用 Raft/Distro；这些在中间件与架构文档里有落地。

---

## 五、时间与时钟

- **物理时钟误差**：NTP 也有毫秒级偏差，不能直接比时间戳定全局序。
- **逻辑时钟（Lamport）**：每个事件附计数器，通信时取 max+1，给出「因果」偏序（不能区分并发）。
- **向量时钟（Vector Clock）**：每个节点一个向量，能判断事件「因果/并发」，用于检测冲突（如 DynamoDB 副本冲突）。
- **TrueTime（Spanner）**：用 GPS+原子钟给时间区间 [earliest, latest]，用「置信区间」实现全球线性一致。

---

## 六、一致性与复制

- **主从复制**：一写多读，异步复制有「读从库可能旧」问题（读写分离陷阱）。
- **多副本一致性**：Quorum（NWR）：写 W 个、读 R 个，满足 `W+R > N` 可保证读到最新（如 Dynamo/Cassandra）。
- **一致性哈希（Consistent Hashing）**：环上分桶，节点增减只影响邻近数据，减少数据迁移（缓存/分库分表/负载均衡常用）。
- **租约（Lease）**：中心给节点发「限时授权」（如缓存失效、锁），避免脑裂。
- **Gossip**：去中心化广播（如 Cassandra 成员发现），最终传播。
- **法定人数 / FLP 不可能定理**：在**异步网络 + 一个崩溃**下，不存在确定性的共识算法——解释了为何需超时/随机化（如 Paxos 用多数派）。

---

## 七、分布式事务与幂等

- **2PC（两阶段提交）**：准备→提交，强一致但**同步阻塞、单点（协调者）、数据锁定**长。
- **3PC**：引入超时与预询问，缓解阻塞，仍复杂。
- **TCC / Saga / 本地消息表 / 最大努力通知**：最终一致方案（见 中间件/分布式事务Seata.md）。
- **幂等**：网络重试下「同一操作执行多次效果等同一次」——用唯一 ID + 去重表 / 状态机 / 乐观锁。

---

## 八、经典问题与脑裂

- **脑裂（Split-Brain）**：分区后两边各选主，双写冲突。防法：Quorum（多数派才能当选）、 fencing（ fencing token 杀掉旧主 IO）、租约。
- **拜占庭容错（BFT）**：节点可能作恶（非仅崩溃），需 PBFT 等，区块链常用；常规分布式假设「崩溃型」故障。

---

## 九、与其他板块的关系

- **中间件 / 注册中心与配置中心**：CAP 取舍、Raft/Distro 在此落地。
- **中间件 / TiDB 与 NewSQL**：Raft 多副本、HTAP。
- **架构 / 系统架构**：韧性、一致性是架构权衡核心。
- **场景设计**：分布式锁、ID、缓存一致性都依赖本总纲概念。

---

## 十、速查表

| 概念 | 一句话 |
|------|--------|
| CAP | P 必选，CP/AP 二选一 |
| BASE | 基本可用 + 软状态 + 最终一致 |
| Raft | 易理解的共识（选主/日志复制/安全） |
| Quorum | W+R>N 读到最新 |
| 一致性哈希 | 节点增减只动邻近数据 |

| Gossip | 去中心化最终传播 |

## 面试高频问题（20+ 条）

1. **CAP 是什么、怎么取舍？** 一致性/可用性/分区容忍；P 必选，剩 CP 或 AP。
2. **为什么不能 CA？** 真实网络必有分区，分区下 C 与 A 冲突。
3. **CP 和 AP 例子？** CP：ZooKeeper/etcd；AP：Cassandra/DNS/主从异步。
4. **BASE 是什么？** 基本可用+软状态+最终一致，AP 的工程化。
5. **强一致到弱一致有哪些？** 线性>顺序>因果>最终。
6. **线性一致定义？** 全局实时有序，读必见最新写。
7. **Paxos 难在哪？** 角色多、活锁、难实现；Multi-Paxos 补日志流。
8. **Raft 怎么选主？** 任期+随机超时选举，获多数票者为主，心跳保活。
9. **Raft 日志复制？** 主的日志顺序广播，多数派确认才提交，保证一致。
10. **Raft 和 Paxos 区别？** Raft 更易理解工程化（拆选主/复制/安全）；Paxos 理论基。
11. **逻辑时钟解决什么？** 给事件因果偏序，不依赖物理时钟。
12. **向量时钟用途？** 判断事件因果或并发，检测副本冲突（Dynamo）。
13. **TrueTime 是什么？** Spanner 用 GPS+原子钟给时间区间，实现全球线性一致。
14. **一致性哈希解决什么？** 节点增减只迁移邻近数据，减rebalance成本。
15. **一致性哈希的虚拟节点？** 解决数据倾斜，把物理节点映射多个虚拟点。
16. **Quorum NWR？** W+R>N 保证读最新；可调强/弱一致。
17. **租约(Lease)用途？** 限时授权（锁/缓存失效），过期自动释放防脑裂。
18. **脑裂是什么、怎么防？** 分区双主；Quorum/fencing token/lease 防。
19. **2PC 缺点？** 同步阻塞、协调者单点、长事务锁资源。
20. **3PC 改进了什么？** 引入超时与预询问缓解阻塞，仍复杂少用。
21. **TCC/Saga 是什么？** 最终一致分布式事务（补偿/编排），见 Seata 文档。
22. **FLP 不可能定理？** 异步+一崩溃下无确定性共识，故需超时/随机。
23. **Gossip 是什么？** 去中心化成员/状态传播，最终一致（Cassandra）。
24. **为什么需要幂等？** 网络重试会导致重复操作，需去重保等价。
25. **拜占庭容错？** 节点可能作恶，需 PBFT，区别于崩溃型故障。
