# 指令提交与顺序提交

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第 3 章（乱序提交、精确异常）与 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 5 章。

## 一、背景与挑战

乱序执行（out-of-order execution）让后发射的指令可以因数据就绪更早完成，从而提升流水线的指令级并行（ILP）。但体系结构对外的契约是「顺序语义」：程序在任意时刻观测到的寄存器与内存状态，必须等价于指令按程序序逐条执行后的结果。问题在于，靠后的指令（如一条不依赖长延迟 load 的加法）可能已经执行完毕，而排在前面的指令（如尚未返回的 L1 miss load）还停在流水线里。如果让后面的结果先对外生效，异常、自修改代码、内存可见性都会被破坏。提交（commit / retire）级正是用来调和「内部乱序完成」与「外部顺序生效」之间的矛盾点：它在流水线的最后一级，把已经完成的指令按 ROB 中的程序序一一条生效到架构状态。

## 二、核心原理

提交级维护一个指向 ROB 头部的指针 `head`。每个周期它尝试从 `head` 开始提交最多 `C` 条指令（`C` 即提交宽度，现代宽核常取 4–8）。一条指令只有同时满足两个条件才允许提交：(1) 它在 ROB 中标记 `done`，即所有执行结果（含写回的寄存器值、store 数据、分支方向）均已就绪；(2) 它未携带未决异常或精确陷阱。提交时，架构寄存器被更新（或 store 队列项被放行写内存），该 ROB 表项被回收，其占用的物理寄存器通过自由表（freelist）归还，重命名映射表（RAT）中指向旧物理寄存器的条目被解除。一旦遇到 `head` 处一条 `done` 尚未置位或存在异常的指令，提交必须暂停——这就是「提交墙」：慢指令（长延迟、cache miss、未预测的分支）即使其后的指令全部完成，也必须等待它先提交，否则就违背了顺序语义。提交级还负责把异常「挂靠」在 ROB 边界上，使异步中断也精确。

## 三、形式化与数学基础

设 ROB 为环形缓冲，表项索引 $i\in[0,M)$，提交指针为 $head$，完成标记 $done[i]\in\{0,1\}$，异常标记 $exc[i]\in\{0,1\}$。每周期提交数 $N$ 满足：

$$ N = \min\big(C,\ \max\{n\ge 0 \mid \forall\,0\le j<n:\ done[(head+j)\bmod M]=1 \land exc[(head+j)\bmod M]=0\}\big) $$

即提交是「从头部起连续 `done` 且 `!exc` 的最长前缀」，上限为提交宽度 $C$。提交推进后 $head\leftarrow(head+N)\bmod M$。若 $done[head]=0$，则 $N=0$，其后所有已完成指令均被阻塞，吞吐被该慢指令的延迟直接截断。物理寄存器回收的节奏也由 $N$ 决定：每提交一项，freelist 增加一项可用物理寄存器。

## 四、代码实现

```c
#define COMMIT_W 6
#define ROB_M    (256 - 1)   // 环形掩码

void commit_stage(struct rob *rob, int *head, int *freelist) {
    int n = 0;
    int idx = *head;
    // 从 ROB 头部连续提交已完成的指令
    while (n < COMMIT_W && rob[idx].done && !rob[idx].exc) {
        // 1) 把结果写回架构态（或放行 store 队列）
        if (rob[idx].is_store)
            stq_commit(rob[idx].stq_id);
        else if (rob[idx].has_dst)
            arch_reg[rob[idx].arch_dst] = rob[idx].val;
        // 2) 回收该指令占用的旧物理寄存器
        free_phys(freelist, rob[idx].old_phys);
        // 3) 表项回收，指针推进
        rob[idx].valid = 0;
        idx = (idx + 1) & ROB_M;
        n++;
    }
    *head = idx;
    // 若头部指令带异常，则进入陷阱处理（提交暂停）
    if (rob[*head].exc)
        trap(rob[*head].pc, rob[*head].exc_code);
}
```

## 五、与其他技术对比

| 维度 | 顺序提交（ROB 头部） | 乱序完成（无 ROB / Tomasulo 仅完成） |
| --- | --- | --- |
| 架构可见顺序 | 严格程序序 | 完成序，非程序序 |
| 精确异常 | 天然支持 | 不支持，需额外机制 |
| 慢指令影响 | 阻塞其后所有提交（提交墙） | 不阻塞其他指令完成 |
| 推测恢复 | 截断 ROB 即可 | 需复杂机制 |
| 硬件代价 | ROB + freelist + 回收逻辑 | 较简单 |

可见顺序提交用「提交墙」换来正确性，是精确异常与推测执行的基石。对比「未来文件（future file）」方案：后者把值暂存物理寄存器堆、提交时才并入架构态，本质与 ROB 提交等价但存储组织不同。

## 六、常见误区

1. 误以为「指令执行完（写回）就等于对外生效」——未提交的写回结果对架构态不可见，只有提交那一刻才更新 `arch_reg`。
2. 误以为提交宽度等于发射/执行宽度——三者独立设计，提交级可能因分支误预测队列清空、store 队列阻塞而低于执行宽度。
3. 误以为慢指令只影响自己——它占住 ROB 头部会阻塞其后所有已完成指令的提交，造成全局停顿。
4. 忽略 store 提交与内存模型耦合：store 必须在提交时才真正写内存，否则破坏顺序与异常语义。
5. 误以为提交级不消耗资源——回收物理寄存器、更新 RAT、flush 流水线都占关键路径带宽。

## 七、与开源书·权威来源对应

- Hennessy & Patterson《Computer Architecture: A Quantitative Approach》：第 3 章系统量化乱序流水线的提交级（commit/retire stage）、精确异常与 ROB 的关系。
- Bryant & O'Hallaron《CSAPP》第 5 章：以 y86 处理器为例讲解「write-back / commit」阶段如何按序更新程序员可见状态。
- Smith & Pleszkun 1985：最早提出用重排序缓冲实现精确中断，奠定提交级概念。
- 二者一致强调：提交级是把「乱序执行结果」转换为「顺序架构语义」的唯一关卡。

## 八、面试题

1. 为什么 `head` 处指令未完成会阻塞其后已完成指令的提交？
   要点：必须按程序序生效，否则后续指令的异常/写回会早于前面指令，破坏精确异常与内存可见性。
2. 提交阶段具体做哪些事？
   要点：写回架构寄存器 / 放行 store、回收物理寄存器、推进 `head`、遇异常进入陷阱。
3. 提交宽度、发射宽度、执行宽度三者为何可以不同？
   要点：分别受提交逻辑、发射队列、执行端口约束，独立设计、互不为充分。
4. 一条长延迟 load 在 `head` 处，会对 IPC 造成什么影响？
   要点：形成提交墙，其后指令即使完成也无法提交，ROB 逐渐被占满并反压前端。
5. 提交级如何支持异步中断的精确性？
   要点：中断挂靠 ROB 提交边界，重启点精确位于已提交与未提交之间。

## 九、演进与趋势

现代高性能核在顺序提交的基本约束下做了大量优化：分区 ROB（partitioned ROB）降低大容量带来的唤醒/提交关键路径延迟；数据捕获（data capture）让提交级直接从 ROB 读寄存器值，减少写回总线路由；store 与 load 队列深度耦合以缩短内存提交路径；SMT 下多个线程共享 ROB 容量并按优先级提交。提交级仍是 ILP 挖掘的「最终闸门」，其宽度与延迟直接决定可实现的上限 IPC，并与推测侧信道防御（提交前不暴露推测性内存访问）深度耦合。

## 十、小结

顺序提交是乱序执行正确性的最终保证：所有架构态变更（寄存器、内存、异常）都必须经 ROB 头部按程序序生效。「提交墙」看似牺牲了部分并行度，但它换来了精确异常、推测执行安全与内存模型可解释性，是乱序处理器不可或缺的关卡。
