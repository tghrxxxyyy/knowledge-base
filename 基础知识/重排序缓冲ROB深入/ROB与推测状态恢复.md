# ROB与推测状态恢复

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第 3 章（推测执行与恢复）与 Böhme et al. 2018（Meltdown 揭示投机执行微架构残留）。

## 一、背景与挑战

分支预测与投机执行（speculative execution）让处理器沿着「可能错误」的路径提前运行指令，以隐藏控制依赖延迟。但一旦分支预测失败（mispredict），那些投机指令对架构状态必须「似从未执行」。难点在于：投机指令在运行期间已经修改了大量微架构状态——物理寄存器内容、store 队列、分支历史表、BTB、TLB、各级缓存。恢复机制必须保证架构态（程序员可见的寄存器与内存）被精确回滚到分支点，而恢复延迟（空转周期）又直接吞噬投机带来的收益。若恢复不彻底，还会留下可供侧信道利用的痕迹，这是现代安全研究的焦点。

## 二、核心原理

ROB 是集中式恢复的核心载体。每条投机指令在 ROB 中分配表项并标记 `speculative` 位（或等价地由分支 ROB 索引界定其所属推测区域）。当分支结果揭晓且预测错误时：
1. 从错误分支的 ROB 索引 `b` 起、其后的所有 ROB 项被丢弃（截断），流水线清空并沿正确路径重新取指。
2. 重命名映射表 RAT 恢复到分支点保存的快照（checkpoint / 影子 RAT），使后续指令重新指向分支前的物理寄存器。
3. 物理寄存器自由表恢复到分支点的状态，被投机分配的物理寄存器重新标记为空闲。
4. 分支预测器（BHT/BTB/RAS）按实际方向更新，避免下次再错。
架构态因「提交级之前都未生效」天然正确；恢复只发生在微架构层（RAT、freelist、预测器）。返回地址栈 RAS 也需随调用/返回预测恢复，否则后续取指地址错位。

## 三、形式化与数学基础

设错误分支位于 ROB 索引 $b$，提交指针 $head$，尾指针 $tail$。恢复需回滚到分支点快照 $S_b$：

$$ RAT \leftarrow RAT_{snapshot}[b] $$
$$ freelist \leftarrow freelist_{snapshot}[b] $$
$$ ROB \leftarrow ROB[head, b) \quad (\text{仅保留分支点之前的项}) $$
$$ tail \leftarrow b $$

恢复延迟 $L_{rec}$ 取决于快照粒度：若每个分支都全量保存 RAT（大小为 $R$），则 $L_{rec}=O(R)$；若用增量/影子结构可降至 $O(1)$ 到 $O(\log R)$。现代核常保留有限深度（如 4–16 个）检查点，超出则退化到更慢的 WALK 回退。检查点深度是延迟/面积的关键权衡。

## 四、代码实现

```c
// 分支提交时建立检查点；预测失败时恢复
void mispredict_recover(int b_rob, struct checkpoint *cp) {
    // 1) 用分支点的 RAT 快照覆盖当前映射
    memcpy(&RAT, &cp[b_rob].rat, sizeof(RAT));
    // 2) 恢复物理寄存器自由表（把投机分配的物理寄存器归还）
    freelist_restore(&cp[b_rob].freelist);
    // 3) 截断 ROB：丢弃 b 之后的所有表项
    tail = b_rob;
    // 4) 恢复分支预测器与 RAS
    bht_update(cp[b_rob].branch_pc, cp[b_rob].taken);
    ras_restore(cp[b_rob].ras);
    // 5) 清空相关流水级，沿正确路径重取
    flush_fetch_decode();
    set_pc(cp[b_rob].correct_target);
}
```

## 五、与其他技术对比

| 恢复策略 | 机制 | 恢复延迟 | 代价 |
| --- | --- | --- | --- |
| 集中式 ROB 截断 | 统一丢弃投机项 | 中 | 结构简单 |
| 检查点 RAT | 每个分支存 RAT 快照 | 低 | 多份 RAT 存储 |
| 影子 RAT（WALK） | 回退遍历 ROB 重建 | 高 | 存储省但慢 |
| 未来文件（future file） | 提交才并入 arch | 中 | 额外寄存器堆 |

现代核多采用「检查点 RAT + 少量影子」混合，兼顾延迟与面积。检查点过浅则深嵌套投机需 WALK 回退，过深则面积与功耗爆炸。

## 六、常见误区

1. 误以为恢复只需撤销架构寄存器——事实上 RAT、freelist、BTB/BHT、RAS 都需修正，否则后续取指/重命名错位。
2. 误以为微架构状态能完全回滚——TLB 填充、缓存行、分支预测器条目等「非精确」状态无法也不回滚，正是 Meltdown / Spectre 侧信道的根源。
3. 误以为每个分支都存全量快照最安全——面积与功耗爆炸，实际只保留有限深度检查点。
4. 忽略异常与分支误预测共用恢复路径——二者都靠 ROB 截断 + 映射恢复，区别仅在触发点是预测器还是 trap。
5. 误以为恢复延迟可忽略——深流水下恢复空转可达数十周期，直接吞噬投机收益。

## 七、与开源书·权威来源对应

- Hennessy & Patterson：详述基于 ROB 的集中恢复、检查点（checkpoint）与重命名快照，并量化恢复延迟对 IPC 的影响。
- Böhme et al. 2018（Meltdown, USENIX）：揭示即使架构态被正确回滚，缓存等微架构痕迹仍可被隐蔽信道读出，催生「推测侧信道」这一安全子领域。
- Bryant & O'Hallaron《CSAPP》：以「预测错误则 flush 流水线」直观说明投机恢复，并强调架构态不变性。
- Kocher et al. 2019（Spectre）：补充分支误预测下的侧信道利用，印证微架构残留的危害。

## 八、面试题

1. 分支预测失败如何恢复？为什么架构态天然正确？
   要点：ROB 截断 + RAT/freelist 快照恢复；提交级前指令未生效，故无需恢复架构寄存器。
2. 为什么微架构状态难以完全回滚？
   要点：缓存、TLB、预测器为性能不回滚，且这些残留可被侧信道利用（Meltdown/Spectre）。
3. 检查点 RAT 与 WALK 回退各有什么取舍？
   要点：检查点恢复快但占存储；WALK 省存储但延迟随 ROB 长度增长，仅在检查点用尽时回退。
4. RAS 为何也要恢复？
   要点：调用/返回预测错会让后续返回地址错位，导致取指路径错误，必须随分支点快照回滚。
5. 恢复延迟如何影响性能？
   要点：深流水下空转数十周期，与分支误预测率共同决定投机执行的净收益。

## 九、演进与趋势

在推测恢复之外，现代核还引入「恢复即重取指」流水线，使清空阶段与取指阶段重叠，进一步压缩空转。安全扩展要求推测期间不留下可观测的微架构痕迹，推动「推测不可见」架构。

- 分支目标缓冲（BTB）与返回地址栈（RAS）的推测更新也需随检查点回滚，否则取指路径错位。
- 针对瞬时误预测的轻量恢复（仅 flush 受影响流水级）比全 ROB 截断更快。
- 推测侧信道防御要求恢复时更激进地清空相关缓存行与 TLB，缩小残留窗口。

恢复机制与安全深度耦合：为防御推测侧信道，现代设计引入「推测隔离」（如延迟缓存填充可见性、限制推测性内存访问），误预测后更激进地清空相关缓存行。同时，更深流水线与更大 ROB 使恢复延迟成为 IPC 关键项，催生分级检查点、快速 flush 与「恢复即取指」的微体系结构优化，把恢复空转压到最小。硬件缓解（如 Speculative Store Bypass Disable）也从恢复侧补强。

## 十、小结

ROB 通过「截断投机项 + 映射快照恢复」使错误投机对架构态零影响，是推测执行可行的根基。但其微架构残留（缓存、TLB、预测器）无法回滚，反而打开推测侧信道的大门——恢复机制已从纯性能问题演变为性能与安全的双重问题，理解这一点是现代体系结构工程师的必修课。
