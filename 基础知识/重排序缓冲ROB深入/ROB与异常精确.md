# ROB与异常精确

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》第 3 章（精确异常）与 Bryant & O'Hallaron《Computer Systems: A Programmer's Perspective》第 5 章（异常与中断）。

## 一、背景与挑战

精确异常（precise exception）要求：当异常在第 $k$ 条指令发生时，所有「程序序上早于 $k$」的指令必须已完全生效，所有「晚于 $k$」的指令必须「似从未执行」。这是操作系统、调试器、信号机制正确工作的前提——若异常点前后指令状态分界不清，恢复后程序将运行在损坏的状态上。乱序执行天然破坏这种分界：靠后的指令可能早已完成。ROB 的「顺序提交」恰好提供了重建精确分界的能力，使异常点之前的指令一定已提交、之后的一定未提交。没有 ROB，乱序核无法实现可恢复的异常。

## 二、核心原理

异常指令在 ROB 中带着 `exc` 标记（异常类型与 PC）。提交指针从 `head` 顺序推进，当到达该异常项时触发陷阱（trap）：其前的所有 ROB 项已经按序提交，架构态完整保留；从异常项起、到 `tail` 为止的「未完成或已投机」项被整体丢弃（flush），流水线清空，处理器把 `PC` 设为异常指令地址、保存异常原因后陷入内核。由于提交是顺序的，异常点之前一定已全部生效、之后一定全部未生效——分界线天然精确。异步中断（外部信号、定时器）同理：它「挂靠」在 ROB 头部已提交边界上，使其中断点也精确。需特别注意：投机路径上触发的异常不能提前 trap，必须等该路径被提交（即确认非投机）才生效；若分支误预测先发生，则随 ROB 截断一起丢弃。store 异常项对应的 STQ 项在 flush 时也须作废，避免脏写。

## 三、形式化与数学基础

设异常指令位于 ROB 索引 $k$，提交指针 $head$，尾 $tail$。精确异常要求：

$$ \forall\, i\in[head,k):\ \text{已提交（架构态生效）} $$
$$ \forall\, i\in[k,tail):\ \text{丢弃，架构态不变} $$
$$ PC_{restart} = rob[k].pc,\quad cause = rob[k].exc\_code $$

恢复点即 $k$。若忽略精确性而允许乱序「完成即生效」，则 $k$ 之前可能混有未提交指令、之后可能已有已生效指令，分界失效。对异步中断，挂靠边界 $b$ 满足 $head\le b<tail$，重启点即 $b$ 对应指令，保证中断前全生效、中断后全未生效。该不变性可形式化为：

$$ \forall\,i<k:\ committed(i)=true,\quad \forall\,i\ge k:\ committed(i)=false $$

## 四、代码实现

```c
// 提交级遇到异常：精确恢复
void handle_exception(int k, int *head, int *tail) {
    // 1) 异常点之前的项已经提交，无需处理
    // 2) 从异常项起到队尾全部丢弃
    for (int i = k; i != *tail; i = (i+1)&ROB_M) {
        if (rob[i].is_store) stq_invalidate(rob[i].stq_id);
        free_phys(rob[i].old_phys);
        rob[i].valid = 0;
    }
    // 3) 设置重启现场（架构态来自已提交项）
    set_pc(rob[k].pc);
    set_cause(rob[k].exc_code);
    // 4) 清空流水级，进入内核陷阱处理
    flush_pipeline();
    enter_trap();
    *head = k;   // 异常项本身作为下一条重启指令
}
```

## 五、与其他技术对比

| 方案 | 精确性 | 实现复杂度 | 性能 |
| --- | --- | --- | --- |
| 无 ROB 乱序完成 | 不精确 | 低 | 高 |
| ROB 顺序提交 | 精确 | 中（需 ROB） | 略损（提交墙） |
| 检查点 + 选择性提交 | 精确 | 高 | 高但复杂 |
| 不精确中断（仅记录 PC） | 近似 | 低 | 高但不安全 |

ROB 以「顺序提交」这一统一机制天然获得精确异常，是工程上最简洁的正确解；不精确中断虽快，却让 OS 无法重建正确现场，难以调试与恢复。

## 六、常见误区

1. 误以为异常前「已完成」的指令都应撤销——精确异常恰恰要求它们保留（已生效）。
2. 误以为精确异常仅指缺页——算术异常、断点、非法指令、自陷（syscall）、异步中断都需精确。
3. 误以为投机指令不会触发异常——投机路径上的指令也会「记录」异常，但要在恢复时随 ROB 截断一起丢弃，不能提前 trap。
4. 混淆「异常」与「中断」：异常同步于指令、中断异步，但二者都借 ROB 边界实现精确。
5. 误以为异常项之后的 store 已写内存——store 须提交才写，异常 flush 时 STQ 中对应项被作废。
6. 以为异步中断可落在任意点——中断必须挂靠提交边界，否则重启现场不一致。

## 七、与开源书·权威来源对应

- Hennessy & Patterson 第 3 章：把 ROB 列为实现精确中断（precise interrupt）的标准手段，并对比「不精确中断」对操作系统恢复的灾难。
- Bryant & O'Hallaron《CSAPP》第 5 章：以 y86 的 `retire` 级说明异常指令之前的指令已更新程序员可见状态、之后未更新，从而恢复点精确。
- Smith & Pleszkun 1985：最早用重排序思想实现精确中断，是 ROB 异常语义的源头。
- Intel SDM 卷 3：x86 的精确异常（#PF、#GP 等）要求，与微体系结构实现对应。
- ARM ARM：AArch64 的精确异常模型与异常级别（EL）切换，约束一致。

## 八、面试题

1. 精确异常的定义是什么？ROB 如何支持它？
   要点：异常点前后指令状态分界清晰；ROB 顺序提交使「已提交=生效、未提交=丢弃」天然成立。
2. 异步中断如何实现精确？
   要点：中断挂靠 ROB 提交边界（在已提交指令之后、未提交之前插入断点），重启点精确。
3. 投机路径上触发异常怎么办？
   要点：异常随 ROB 标记，若分支误预测先恢复则丢弃；若确实提交则 trap。
4. 为什么缺页异常必须精确？
   要点：OS 需据精确 PC 与现场填充页表、重启指令，否则状态错乱导致无限缺页或数据损坏。
5. 异常 flush 为何要作废 STQ 项？
   要点：异常点之后的 store 未提交，不能写内存，否则破坏异常语义与内存一致性。

## 九、演进与趋势

精确异常还与虚拟化深度耦合：VM exit 需在 guest 指令边界精确发生，ROB 提交边界即 exit 点。调试断点（watchpoint）依赖精确异常定位触发指令，ROB 提供精确 PC。

- 事务内存（TSX）把事务 abort 建模为特殊异常，复用精确异常恢复路径。
- 异步抢占（如 SMT 的线程切换）也挂靠提交边界，保证切换点精确、现场一致。
- 推测性异常在分支误预测时廉价丢弃，降低异常路径开销，保持精确性不变。

精确异常与推测恢复的界限进一步模糊：为支持事务内存（TSX）、虚拟化退出（VM exit）与推测侧信道防御，现代核把「精确点」扩展到更丰富的事件类型；同时用「延迟提交」（deferred commit）在保持精确性的前提下掩盖提交级延迟，并引入「推测性异常」在误预测时廉价丢弃，降低异常路径开销。硬件与 OS 协同的「非精确但可恢复」异常（如某些 SIMD）也在探索中。

## 十、小结

ROB 的顺序提交让乱序执行能精确报告异常点——之前全生效、之后全丢弃，分界线由提交边界天然界定。这是异常处理、操作系统上下文切换与调试正确性的根基，也是乱序处理器「对外守约」的核心机制。理解「已提交即生效、未提交即丢弃」这一不变量，就掌握了精确异常的全部精髓。
