# 依赖注入

> 对应 Fowler《Inversion of Control Containers and the Dependency Injection pattern》；Martin《Clean Architecture》。

## 一、背景与挑战

对象若在内部自行 `new` 依赖，会把具体实现硬编码进自身：测试时无法替换为假对象，并行开发时模块相互等待，重构时牵一发动全身。这种「依赖自管」是代码僵化与难测的根源。更隐蔽的问题是，它让高层模块直接依赖低层细节，违反依赖倒置原则，导致架构层级被「向下穿透」，难以独立演进。

## 二、核心原理

依赖注入（Dependency Injection, DI）把「依赖由谁创建」与「依赖被谁使用」解耦：依赖由外部传入，而非内部构造。三种典型形式：构造器注入（最推荐，依赖不可变、必填）、Setter 注入（可选、可换）、接口注入（通过接口方法传入）。DI 常由容器（Spring、Guice）装配，但手写注入同样成立。它与依赖倒置原则（DIP）协同——高层模块依赖抽象，DI 是 DIP 的常见实现机制。构造器注入还能在对象创建期就保证不变量成立。

## 三、形式化与数学基础

设对象 $O$ 依赖抽象 $A$，传统写法 $O$ 持有 $A$ 的构造权；DI 下 $O$ 不再构造，而是：

$$O = \text{make}(A_{impl}),\quad A_{impl} \in \text{Impl}(A)$$

可测性由此取决于能否传入替身：

$$T(O) \uparrow \iff \exists\, A_{fake} \text{ 可注入}$$

即把「依赖来源」从编译期固定，变为运行期可配置的参数，从而把对象与其环境解耦。从类型论看，DI 把隐含的全局效应显式化为函数参数，使副作用可见、可控。

## 四、代码实现

```java
// 构造器注入：依赖在创建时给定，且不可变
class OrderService {
    private final Repository repo;
    OrderService(Repository repo) { this.repo = repo; }
    void ship(String id) { repo.markShipped(id); }
}

// 测试时注入内存实现，无需真实数据库
OrderService svc = new OrderService(new InMemoryRepo());
svc.ship("o1");
```

```python
# Python 风格构造器注入
class OrderService:
    def __init__(self, repo):
        self.repo = repo
svc = OrderService(InMemoryRepo())   # 测试用假实现

# Setter 注入：依赖可后续替换（适合可选依赖）
svc.repo = AnotherRepo()
```

## 五、与其他技术对比

| 机制 | 依赖可见性 | 可测性 | 耦合 | 适用 |
| --- | --- | --- | --- | --- |
| 内部 new | 隐藏 | 低 | 高 | 简单脚本 |
| Service Locator | 间接 | 中 | 中 | 遗留改造 |
| DI | 显式 | 高 | 低 | 多数场景 |
| DIP(抽象) | 显式 | 高 | 低 | 整洁架构 |

DI 相比 Service Locator 显式暴露依赖，更易读易测；与 DIP 配合最稳。

## 六、常见误区

误区一：用 Service Locator 冒充 DI——依赖被藏进全局定位器，依旧难测。误区二：注入过多依赖——暗示类职责过多，应拆分。误区三：过度依赖框架——手写注入也能获益，不必为 DI 引入重容器。误区四：构造器注入与 Setter 注入混用造成语义混乱——应明确必填用构造器、可选用 Setter。

## 九、演进与趋势

编译期 DI（如 Dagger、Rust 特质注入）消除运行时反射开销；语言级依赖作用域（如 Python 的 `contextvars`）让注入更轻量；函数式依赖注入（以显式参数传递）在纯函数架构中回归。

### 实践速查

- 选型：必填依赖用构造器注入，可选/可换依赖用 Setter 注入。
- 容器：Spring/Guice 适合大型应用，小项目手写注入同样受益。
- 抽象：依赖应声明为接口（抽象），而非具体实现类。
- 测试：注入内存实现或 Mock，无需真实基础设施即可单测。
- 反模式：Service Locator 隐藏依赖，应改用显式 DI。
- 信号：一个类注入过多依赖，往往是职责过多，应考虑拆分。

### 常见问题

- 问：构造器注入和 Setter 注入如何选？答：必填用构造器，可选用 Setter。
- 问：DI 与 DIP 关系？答：DIP 提原则，DI 是其常见实现机制。
- 问：循环依赖怎么解？答：重构抽取接口或引入事件，而非硬塞 DI。

## 十、小结

依赖由外传入，既解耦又让测试可替换，是构建可测、可维护系统的基石，也是整洁架构落地的关键手段。
