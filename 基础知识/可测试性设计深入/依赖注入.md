# 依赖注入

> 对应 Martin《Clean Architecture》、Fowler "Inversion of Control Containers and the Dependency Injection pattern"。

## 一、背景与挑战
对象自行 `new` 依赖会把具体实现硬编码，难以替换（测试时无法换假对象），也难并行开发。

## 二、核心原理
依赖注入（DI）：依赖由外部传入而非内部创建。三种形式：构造器注入、Setter 注入、接口注入。容器（如 Spring）负责装配，但手写注入也成立。

## 三、形式化 / 数学基础
对象 $O$ 依赖抽象 $A$；$O$ 不持有 $A$ 的构造权，而是 $O = make(A_{impl})$。这使得 $O$ 的可测性 $T(O)$ 取决于能否传入 $A_{fake}$。

## 四、代码实现
```java
class OrderService {
    private final Repository repo;
    OrderService(Repository repo) { this.repo = repo; } // 构造器注入
}
// 测试注入内存实现
OrderService svc = new OrderService(new InMemoryRepo());
```

## 五、与其他技术对比
与 Service Locator 相比，DI 显式暴露依赖、更易测；与 DIP 协同，DI 是 DIP 的常见实现机制。

## 六、常见误区
误区：用 Service Locator 冒充 DI（隐藏依赖）。误区：注入过多依赖暗示职责过多。

## 九、演进与趋势
编译期 DI（如 Dagger、Rust 特质注入）消除运行时反射开销。

## 十、小结
依赖由外传入，既解耦又让测试可替换。
