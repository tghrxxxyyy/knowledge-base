# 测试替身

> 对应 Meszaros《xUnit Test Patterns》「Test Double」一章；Fowler 相关论述。

## 一、背景与挑战

真实依赖（数据库、第三方服务、系统时钟、文件系统）通常慢、不稳定、且难以构造异常场景（如网络超时、并发冲突）。直接依赖它们会让单元测试缓慢、脆弱、且不可重复，违背「快而确定」的测试原则。更严重的是，某些故障路径（如「当余额不足时抛异常」）在真实环境中几乎无法稳定复现，测试只能「靠运气」触发。

## 二、核心原理

测试替身（Test Double）是用受控对象替换真实依赖的总称，Meszaros 将其分为五类：Dummy（仅占位、从不使用）、Stub（返回预设值、提供测试所需数据）、Spy（记录调用细节供断言）、Mock（预设期望并验证交互行为）、Fake（轻量但可用的实现，如内存数据库）。选型原则是「够用即可」：只验证需要的那一点，避免把测试绑死在无关细节上。错误地过度使用 Mock，是把测试耦合到实现细节的常见反模式。

## 三、形式化与数学基础

替身把真实依赖 $D$ 替换为 $D'$，满足对测试输入返回受控输出。Stub 行为：

$$\text{stub}(x_{test}) = y_{preset}$$

Mock 额外对交互做断言：在调用序列上验证

$$\text{called}(D', \text{method}, \text{args}) = \text{True}$$

Fake 则保持 $D'$ 与 $D$ 在测试范围内语义一致：$\forall x\in\mathcal{X}_{test},\ D'(x) \approx D(x)$。可见 Stub 关注「给什么数据」，Mock 关注「是否按约定交互」，Fake 关注「行为等价但更轻」。

## 四、代码实现

```python
from unittest.mock import Mock

# Stub：预设返回值提供数据
repo = Mock()
repo.find_by_id.return_value = Order("o1", total=99)
svc = OrderService(repo)
svc.ship("o1")

# Mock：验证交互行为（是否按预期调用）
repo.find_by_id.assert_called_once_with("o1")

# Spy：记录并事后检查调用次数与参数
repo.ship.assert_called_once()
print(repo.ship.call_args)

# Fake：内存实现，真实可用但不连库
class InMemoryRepo(Repository):
    def __init__(self): self._store = {}
    def save(self, o): self._store[o.id] = o
    def find_by_id(self, i): return self._store.get(i)
```

## 五、与其他技术对比

| 替身 | 提供数据 | 验证行为 | 可用实现 | 耦合度 | 适用 |
| --- | --- | --- | --- | --- | --- |
| Dummy | 否 | 否 | 否 | 最低 | 占位参数 |
| Stub | 是 | 否 | 否 | 低 | 提供状态 |
| Spy | 是 | 记录 | 否 | 中 | 观察调用 |
| Mock | 是 | 是 | 否 | 高 | 验证交互 |
| Fake | 是 | 否 | 是 | 中 | 替真实依赖 |

## 六、常见误区

误区一：Mock 一切——测试与实现细节强耦合，重构即红。误区二：Spy 与 Mock 混淆——Spy 记录、Mock 预设期望，语义不同。误区三：用 Mock 验证内部状态——应验证行为契约而非实现路径。误区四：用 Fake 替代真实依赖做集成——Fake 终究不是生产实现，关键路径仍需真依赖验证。

## 九、演进与趋势

契约测试部分替代微服务间 Mock；快照测试减少手写桩；基于属性的测试（Property-Based Testing）用生成器替代预设值，覆盖更广；AI 辅助生成替身正降低编写成本。

### 实践速查

- 选型：要数据用 Stub，要验交互用 Mock，要真可用替身用 Fake。
- 克制：只为要断言的点用 Mock，其余用 Stub/Fake，降低耦合。
- 真实路径：关键外部依赖最终要用真实集成测试覆盖，Fake 不保证等价。
- 清理：Spy 与 Mock 记得重置，避免用例间状态泄漏。
- 框架：unittest.mock 足够日常，复杂交互可用更专业的 mock 库。
- 反模式：Mock 一切导致重构即红，应面向行为契约而非实现细节。

### 常见问题

- 问：Mock 与 Stub 怎么选？答：需验证「是否调用」用 Mock，只给数据用 Stub。
- 问：Fake 能替代真实 DB 吗？答：不能，关键路径仍需真实依赖验证。
- 问：为何过度 Mock 有害？答：测试绑定实现，逻辑一改测试就失败。

## 十、小结

按需选替身：Stub 给数据、Mock 验行为、Fake 做实替、Spy 做记录——原则是「够用即止」，避免把测试绑死在实现细节上。
