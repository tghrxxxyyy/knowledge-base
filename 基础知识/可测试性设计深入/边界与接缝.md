# 边界与接缝

> 对应 Feathers《Working Effectively with Legacy Code》「Seams」一章；测试边界（test boundary）理论。

## 一、背景与挑战

不可测代码常在边界处纠缠：时间、随机数、网络、文件系统、全局配置，使测试无法在确定性环境下运行。更糟的是，这些不可控依赖往往被写进领域核心，找不到可注入点，导致「想测却无从下手」。遗留系统尤其如此——业务逻辑与 I/O 交织，任何单测都不得不触发真实副作用（发邮件、写库、调第三方）。

## 二、核心原理

Feathers 提出的「接缝（Seam）」指：程序中的某个点，其旁的行为可以不修改该点本身的代码而被替换。制造接缝，就是在不改动原有逻辑的前提下，把不可控依赖变成可传入的参数或可被继承/重写的点。边界（Boundary）指系统与外界（DB、网络、时钟、文件系统）的交界，设计上应当「薄且可替」——把不确定性推到最外层，内层保持纯逻辑。接缝与边界配合，使测试能注入假实现，把副作用隔离在测试之外。

## 三、形式化与数学基础

设接缝点 $s$ 上行为由外部实现决定，定义运行函数：

$$\text{run}(s, impl) = \text{执行 } s \text{ 之上逻辑，使用 } impl$$

则生产运行与测试运行共享同一逻辑，仅替换实现：

$$\text{run}(s, impl_{real}) \neq \text{run}(s, impl_{fake}),\quad \text{但共享 } s \text{ 之上代码}$$

理想架构把 $impl_{real/fake}$ 的切换成本降到零——即接缝「无修改即可替换」。从范畴论视角，接缝是把副作用从纯函数体内「上拉」为参数，使核心逻辑成为引用透明（referentially transparent）的纯函数。

## 四、代码实现

```python
# 领域核心不依赖具体时间来源，时间通过接缝传入
def summarize(data, now_provider):
    now = now_provider()              # 接缝点
    return f"截至{now.date()}共{len(data)}条"

# 生产：传入真实时钟
summarize(records, lambda: datetime.now())

# 测试：传入确定性时间，零修改核心逻辑
def test_summarize():
    fake = lambda: datetime(2020, 1, 1)
    assert summarize([1, 2], fake) == "截至2020-01-01共2条"

# 接缝也可通过继承/编译开关实现（示意）
class RealClock:  # 生产用
    def now(self): return datetime.now()
class FakeClock:  # 测试用
    def now(self): return datetime(2020, 1, 1)
```

## 五、与其他技术对比

| 概念 | 范围 | 实现方式 | 目的 | 侵入性 |
| --- | --- | --- | --- | --- |
| DI | 对象依赖 | 构造/Setter | 解耦与可替 | 中 |
| 接缝 | 任意替换点 | 参数/继承/编译开关 | 可测而不改码 | 低 |
| 边界 | 系统与外界 | 分层隔离 | 不确定性外推 | 设计级 |

接缝比 DI 更通用：不限于构造注入，可用函数参数、继承重写、编译期开关实现。

## 六、常见误区

误区一：把边界逻辑写进领域核心——导致无法替换、无法测试。误区二：为缝而缝——过度抽象反而增加复杂度。误区三：只在测试时打补丁（monkey patch）代替设计接缝——治标不治本。误区四：认为接缝只用于测试——它同样提升可配置性与可演进性。

## 九、演进与趋势

「函数式核心 + 命令式外壳」（functional core, imperative shell）架构将边界推到最外层；纯函数式语言天然把副作用隔离，使接缝成为类型而非技巧；依赖类型（effect systems）在编译期保证边界清晰。

### 实践速查

- 识别：先找代码中「不可控点」——时钟、随机、网络、文件系统、全局配置。
- 制造接缝：把这些点提为参数、接口或继承可重写的方法，而非内部硬编码。
- 边界外推：把 I/O 与领域逻辑分离，领域核心保持纯函数。
- 测试：测试时注入假实现（FakeClock、内存 FS），确定性复现场景。
- 渐进：遗留代码可先加窄接缝跑通单测，再逐步内推重构。
- 反模式：用 monkey patch 全局替换依赖只是临时手段，应改设计。

### 常见问题

- 问：接缝和 DI 有何不同？答：接缝更通用，可不改代码点即可替换行为。
- 问：时间依赖怎么测？答：注入时间提供方，测试传固定时间即可。
- 问：接缝会不会过度设计？答：只在确有测试/替换需求处制造，避免滥用。

## 十、小结

在边界留缝，使不可控依赖可被替换与测试，是改造遗留代码、提升可测性的核心手法，也是整洁架构的落地支点。
