# 契约测试

> 对应 Pact 文档、"Consumer-Driven Contracts" (CDC) 模式。

## 一、背景与挑战
微服务多团队并行，提供者改接口常无意破坏消费者，端到端测试反馈慢、定位难。

## 二、核心原理
消费者定义期望（请求/响应契约），在消费者侧生成并发布；提供者 CI 拉取契约验证自身，提前发现不兼容。分消费者侧（生成）与提供者侧（验证）两阶段。

## 三、形式化 / 数学基础
契约 $K=(consumer, provider, interactions[])$。验证即 $\forall i,\ provider\ 能在\ i.request\ 下产出匹配\ i.response\ schema$。任一方不符即 CI 失败。

## 四、代码实现
```python
# 消费者侧（Pact）
with pact.upon_receiving("get order").will_respond_with(200, body={"id": "o1"}):
    orders_client.get("o1")  # 记录期望
# 提供者侧：启动服务，Pact 校验每条约
```

## 五、与其他技术对比
与端到端测试相比，契约测试快、定位准、解耦团队；与单元测试不同，它验证跨进程契约而非内部逻辑。

## 六、常见误区
误区：把契约测试当集成测试用（应聚焦接口契约）。误区：消费者不更新契约导致过期保护。

## 九、演进与趋势

## 十、小结
