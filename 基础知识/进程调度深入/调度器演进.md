# 调度器演进

> 对应 Linux 调度器史：O(n) → O(1) → CFS（2.6.23）→ SCHED_DEADLINE，及 Wolf《Linux Kernel Programming》。

## 一、背景与挑战
早期调度器在多核、多任务规模下出现扩展性瓶颈或交互性抖动，推动结构反复重构。

## 二、核心原理
- O(n)：遍历全部任务选最高优，O(n) 随进程数恶化。
- O(1)：两个优先级数组 + 位图，入队/选程 O(1)，但启发式复杂。
- CFS：红黑树 + vruntime，按权重比例公平。
- SCHED_DEADLINE：EDF + 运行/周期带宽隔离，面向硬实时。

## 三、形式化 / 数学基础
CFS 公平目标：长时间窗口内每进程获得 CPU 比例 $= w_i/\\sum w_j$。SCHED_DEADLINE 以 (runtime $Q$, deadline $D$, period $P$) 三元组约束，调度性要求 $\\sum Q_i/P_i \\le 1$（EDF）。

## 四、代码实现
选择调度类（sched class）的层次调用：

```c
struct task *pick_next_task(struct rq *rq) {
    for (class = &stop_sched_class; class; class = class->next)
        if ((p = class->pick_next_task(rq))) return p;
    return NULL;
}
```

## 五、与其他技术对比
O(1) 快但调参难；CFS 自适应、交互好但无截止保证；DEADLINE 补实时短板。多调度类通过 `sched_class` 链表按优先级串联。

## 六、常见误区
- 认为“新版一定更快”：CFS 平均延迟优于 O(1) 交互，但某些基准不同。
- 忽略调度类优先级：STOP > DL > RT > FAIR > IDLE。
- 误把 CFS 当实时调度器使用。

## 九、演进与趋势
EAS 引入能耗感知、SCHED_EXT（可扩展调度类，eBPF 编写策略）让用户在态自定义调度，推动“策略可插拔”。

## 十、小结
调度器演进主线是“可扩展性 + 公平/确定性 + 可扩展策略”，从全局遍历走向按类的可插拔架构。
