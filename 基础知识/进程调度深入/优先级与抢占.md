# 优先级与抢占

> 对应 Silberschatz《Operating System Concepts》调度章与 Linux `sched_features`。

## 一、背景与挑战
优先级决定“谁先跑”，抢占决定“何时能抢”。没有抢占的优先级调度仍可能让高优任务苦等低优任务释放 CPU。

## 二、核心原理
- 静态优先级：创建时固定（如实时 FIFO）。
- 动态优先级：随运行时间/交互性调整（如 Linux 曾用 `prio = static_prio + bonus`，CFS 转为权重）。
- 抢占点：tick、唤醒更高优任务、系统调用返回用户态。

## 三、形式化 / 数学基础
可抢占条件：存在就绪任务 $j$ 满足 $prio_j > prio_{current}$ 且当前处于可抢占上下文（非持有自旋锁/中断禁用）。抢占延迟 $L_{pre} = L_{crit} + L_{sched}$，其中 $L_{crit}$ 为最长关抢占临界区。

## 四、代码实现
内核抢占检查（示意）：

```c
void check_preempt(struct rq *rq) {
    if (preempt_count()) return;          /* 处于不可抢占区 */
    if (rq->curr->prio > next_task->prio)
        set_tsk_need_resched(rq->curr);   /* 标记需重调度 */
}
```

## 五、与其他技术对比
协作式（cooperative）调度仅在点主动让出，延迟无界；抢占式有界但需临界区保护（抢占计数）。实时系统要求最小时长关抢占。

## 六、常见误区
- 以为“有优先级就有实时性”：必须配合抢占与临界区分析。
- 混淆用户抢占与内核抢占：Linux 2.6 起支持内核抢占，但仍受 `preempt_count` 约束。
- 认为提高优先级总能更快：优先级反转会反杀。

## 九、演进与趋势
`PREEMPT_RT` 将自旋锁改为可抢占互斥、中断线程化，把抢占延迟压到微秒级，逼近硬实时。

## 十、小结
优先级给出“谁该跑”，抢占给出“何时能抢”；二者结合并以抢占计数保护临界区，才能提供有界响应。
