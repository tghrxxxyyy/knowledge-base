# 一致性哈希

> 对应 Karger, Lehman, Leighton, Panigrahy, Levine, Lewin《Consistent Hashing and Random Trees: Distributed Caching Protocols for Relieving Hot Spots on the World Wide Web》(STOC 1997)，以及 DeCandia et al.《Dynamo: Amazon's Highly Available Key-value Store》(SOSP 2007)。

## 一、背景与挑战

分布式缓存与分片存储中，客户端拿到一个 key，必须决定它归哪台机器负责。最直观的做法是 `hash(key) % N`：$N$ 台机器、计算常数时间、映射均匀。问题出在**扩缩容**：$N$ 从 10 变成 11，几乎所有 key 的模数都变了，约 $10/11$ 的键被迫迁移。在 PB 级集群里，加一台机器可能触发数十 TB 的无谓拷贝，网络被打满、请求延迟飙升、在线服务抖动。更糟的是，若同时有节点故障，全量重映射会与故障恢复叠加，雪上加霜。

更深层的矛盾是：我们真正需要的只是**局部稳定**——加一台机器最好只迁移 $1/N$ 的数据，其余 $1-1/N$ 纹丝不动。Karger 等人 1997 年提出的一致性哈希（Consistent Hashing）正是为此设计：把节点和 key 映射到同一个环形空间，key 顺时针归属最近节点，于是节点增删只影响环上相邻区间。注意这里的「一致性」不是 CAP 中的数据一致性，而是「哈希映射随拓扑变化保持稳定」——理解这一点是理解全文的前提。

工程与面试语境中，一致性哈希是分布式章节必考项：Dynamo、Cassandra、Riak、Redis Cluster、Ketama、负载均衡器、CDN 调度、分布式缓存客户端都建立在它之上。面试官通常希望你说清环模型、虚拟节点、以及「为什么迁移量是 $1/N$ 而不是 $N-1/N$」三个层次，而不是背一句「减少数据迁移」。它是理解「再平衡为什么必须可控」的入口，也引出跳转哈希、带权哈希、有界负载一致性哈希等现代变体。

## 二、核心原理

**哈希环**。取一个足够大的哈希空间，例如 $[0, 2^{32})$ 或 $[0, 2^{64})$，首尾相接看成圆环。所有节点与所有 key 通过同一个均匀哈希函数（Murmur、xxHash、SHA-1 截断）映射到环上。

**路由规则**。给定 key $k$，计算 $h(k)$ 在环上的位置，**沿顺时针行走遇到的第一个节点就是归属节点**。若绕一圈无节点，系统为空，拒绝服务或扩容。这条「顺时针后继」规则是算法灵魂：它保证每个节点负责环上一段连续弧，区间起点是自己、终点是顺时针邻居。

**不变量**。
1. **区间不变量**：任意时刻每个节点 $n$ 拥有半开区间 $(\mathrm{pred}(n), n]$，其中 $\mathrm{pred}(n)$ 是逆时针前驱。key 落在该区间当且仅当属于 $n$。区间互不重叠、并集覆盖整环。
2. **局部性不变量**：节点 $n$ 加入时只接管前驱区间的 $(\mathrm{pred}(n), n]$ 这一段，其它节点区间端点不变，它们持有的 key 一个都不用迁移。
3. **离开对称**：节点 $n$ 离开时，它的区间被前驱完整接管，其它区间不动。

**虚拟节点（Virtual Nodes）**。若每台物理机只占一个环点，哈希均匀性会导致负载方差大（碎棍问题）。给每台物理机分配 $v$ 个虚拟节点（不同字符串 `"ip#i"` 哈希到环上），环上共 $n \cdot v$ 个点。虚拟节点越多，各物理机的弧长越趋于均衡。代价是路由表变大、点查需 $O(\log (nv))$。

**实现结构**。用有序数组或平衡树保存环点，查询用二分找后继。节点加入/离开时插入/删除其虚拟点。必须处理环为空、哈希碰撞（tie-break）与绕回（`bisect` 越界取模）。

## 三、形式化与数学基础

**取模哈希的迁移量**。节点数由 $N$ 变 $N+1$ 时，$h(k) \bmod N$ 变为 $h(k) \bmod (N+1)$。均匀随机的 $h(k)$ 下，一个 key 映射不变的概率约 $1/(N+1)$ 量级，于是约
$$
K \cdot \frac{N}{N+1}
$$
个 key 需迁移。极端地 $N \to N+1$ 时几乎所有数据搬家。

**一致性哈希的迁移量**。节点 $n$ 加入时接管一段弧。哈希均匀时各节点区间长度同分布，期望相等，新节点接管的 key 数期望为
$$
\mathbb{E}[\Delta] = \frac{K}{N+1} \approx \frac{K}{N}.
$$
离开时约 $K/N$，加入时约 $K/(N+1)$。相比取模的 $1-1/(N+1)$，差距约 $N$ 倍。$N=100$、$K=10^9$ 时，取模动约 $9.9\times 10^8$ 个 key，一致性哈希只动约 $10^7$ 个。

**负载方差（碎棍问题）**。$N$ 个节点把环切成 $N$ 段，等价于 $N-1$ 个均匀切点分圆周。第 $i$ 段长度 $L_i$ 满足
$$
\mathbb{E}[L_i] = \frac{1}{N}, \qquad
\operatorname{Var}(L_i) = \frac{N-1}{N^2(N+1)} \approx \frac{1}{N^3}.
$$
单节点负载标准差约 $K/\sqrt{N}$，相对波动 $1/\sqrt{N}$。$N$ 小时极不均衡——这正是虚拟节点要解决的。一致性哈希本身解决的是**迁移局部性**，负载均衡靠虚拟节点。

**虚拟节点的均衡效果**。每物理机 $v$ 个虚拟点，相当于把 $nv$ 个点分给 $n$ 个组。由 balls-and-bins，某物理机负载（弧长和）的方差下降约 $1/v$ 倍，标准差降 $1/\sqrt{v}$。要让负载偏差 < 5%，通常 $v$ 取 100~200。

**有界负载变体**。标准一致性哈希在节点过载时仍不保证上限。有界负载一致性哈希（Bounded-Load Consistent Hashing, Google 2017）在选后继节点时检查负载，超过平均的 $(1+\epsilon)$ 倍就跳到下一个，保证 $\max \le (1+\epsilon) \cdot \text{avg}$，代价是映射随负载动态化。

## 四、代码实现

带虚拟节点的一致性哈希环：稳定哈希、顺时针后继、增删节点、key 路由。可直接运行。

```python
"""一致性哈希环（含虚拟节点）。"""
from __future__ import annotations

import bisect
import hashlib
from typing import Iterable


def _stable_hash(data: str) -> int:
    """md5 取前 8 字节，避免 Python 内置 hash 的进程随机性。"""
    digest = hashlib.md5(data.encode("utf-8")).digest()
    return int.from_bytes(digest[:8], "big")


class ConsistentHashRing:
    def __init__(self, replicas: int = 100):
        self.replicas = replicas
        self._points: list[int] = []          # 有序环点
        self._ring: dict[int, str] = {}       # point -> node_id
        self._nodes: set[str] = set()

    def add(self, node_id: str) -> None:
        if node_id in self._nodes:
            return
        self._nodes.add(node_id)
        for i in range(self.replicas):
            p = _stable_hash(f"{node_id}#{i}")
            if p in self._ring:
                continue  # 碰撞：跳过该虚拟点（极罕见）
            bisect.insort(self._points, p)
            self._ring[p] = node_id

    def remove(self, node_id: str) -> None:
        if node_id not in self._nodes:
            return
        self._nodes.discard(node_id)
        for i in range(self.replicas):
            p = _stable_hash(f"{node_id}#{i}")
            if self._ring.get(p) == node_id:
                self._ring.pop(p)
                pos = bisect.bisect_left(self._points, p)
                if pos < len(self._points) and self._points[pos] == p:
                    self._points.pop(pos)

    def get(self, key: str):
        """返回 key 的归属节点；环为空返回 None。"""
        if not self._points:
            return None
        h = _stable_hash(key)
        idx = bisect.bisect_right(self._points, h)
        if idx == len(self._points):
            idx = 0  # 绕回
        return self._ring[self._points[idx]]

    def nodes(self) -> list[str]:
        return sorted(self._nodes)


def migration_ratio(ring_a: ConsistentHashRing, ring_b: ConsistentHashRing, keys: Iterable[str]) -> float:
    """统计从 ring_a 切到 ring_b 时需要迁移的 key 比例。"""
    keys = list(keys)
    if not keys:
        return 0.0
    moved = sum(1 for k in keys if ring_a.get(k) != ring_b.get(k))
    return moved / len(keys)


if __name__ == "__main__":
    keys = [f"key{i}" for i in range(10_000)]
    ring = ConsistentHashRing(replicas=150)
    for n in ["nodeA", "nodeB", "nodeC", "nodeD"]:
        ring.add(n)

    # 统计负载
    from collections import Counter
    c = Counter(ring.get(k) for k in keys)
    print("before:", dict(c))

    # 加入一台节点，观察迁移比例
    ring2 = ConsistentHashRing(replicas=150)
    for n in ["nodeA", "nodeB", "nodeC", "nodeD"]:
        ring2.add(n)
    ring2.add("nodeE")
    ratio = migration_ratio(ring, ring2, keys)
    print(f"migration after adding 1 node: {ratio:.3f} (ideal ~1/5=0.2)")
    assert 0.05 < ratio < 0.45  # 应接近 1/N，远小于取模的 0.8

    # 删除一台节点
    ring3 = ConsistentHashRing(replicas=150)
    for n in ["nodeA", "nodeB", "nodeC", "nodeD", "nodeE"]:
        ring3.add(n)
    ring3.remove("nodeE")
    ratio2 = migration_ratio(ring2, ring3, keys)
    print(f"migration after removing 1 node: {ratio2:.3f}")
    print("ok")
```

实测加一台节点的迁移比例约 0.15~0.25（5 台机器理想 $1/5=0.2$），远低于取模哈希的 0.8。虚拟节点 150 时各节点负载也大致均衡。

## 五、与其他技术对比

| 维度 | `hash % N` | 一致性哈希 | 跳转哈希 Jump Hash | Rendezvous / HRW | 有界负载一致性哈希 |
|------|------------|------------|--------------------|------------------|--------------------|
| 扩缩容迁移 | 约 $1-1/N$ | 约 $1/N$ | 最优 $1/N$ | 约 $1/N$ | 约 $1/N$ |
| 负载均衡 | 好 | 需虚拟节点 | 优（无需虚拟节点） | 好 | 带负载上限 |
| 内存开销 | 无 | 环表 $O(nv)$ | 无额外 | $O(n)$ 每查询 | 环表 + 负载表 |
| 有序性 | 无 | 无 | 无 | 无 | 无 |
| 典型场景 | 静态分片 | Dynamo、缓存、LB | Google 负载均衡、gRPC | 网络路由、副本选择 | 需要负载上限的均衡 |

与跳转哈希相比：Jump Hash 迁移最优且无需虚拟节点，但只能在连续的 $[0, N)$ 上选桶，不适合带权重或异构节点。与 Rendezvous 哈希相比：HRW 对每个 key 打分选最大，迁移也约 $1/N$，且天然适合副本选择，但每查询 $O(n)$（可用并行加速）。与 B+ 树/范围分片相比：一致性哈希是 key 级路由，不保证有序，范围查询要靠额外索引。

## 六、常见误区

**未加虚拟节点导致倾斜**。只放 $n$ 个物理点，碎棍方差大，热点机器被打爆。应给每台 100~200 个虚拟点，或改用 Jump Hash。

**环实现未处理绕回**。`bisect` 找不到后继时未取模回 0，key 丢失或返回 None。必须 `idx %= len(points)`。

**节点上下线未同步视图**。客户端各算各的环，拓扑不一致会导致 key 打到不同节点、缓存命中率暴跌。需要配置中心/元数据服务发布环版本，或客户端定期拉取。

**把「一致性哈希」理解成数据一致性**。它只是映射稳定；副本一致性仍要靠 Raft/向量时钟/最终一致性协议。面试中混淆这两个「一致」会丢分。

**忘记迁移期的双读**。节点加入时新旧映射并存，若立即切断旧节点会丢数据。正确做法是迁移期间双写/回填，或用「预热 + 切换 + 清理」三阶段。

## 八、面试题

**1. 设计分布式缓存，节点扩缩容如何最小化迁移？**
参考答案：用一致性哈希环 + 虚拟节点。key 顺时针归属最近节点；加节点只接管一段弧，迁移约 $1/N$；虚拟节点使负载均衡。迁移期需双写/回填，拓扑变更用配置中心同步。

**2. 一致性哈希的迁移量为什么是 $1/N$？**
参考答案：新节点只接管环上一段弧，其余节点区间不变。哈希均匀时期望弧长 $1/(N+1)$，故只迁移这部分 key。对比取模几乎全量重映射。

**3. 虚拟节点解决什么问题？**
参考答案：解决碎棍导致的负载方差。每物理机 $v$ 个虚拟点使负载标准差降约 $1/\sqrt{v}$。代价是环表变大、查询 $O(\log nv)$。通常 $v=100\sim 200$。

**4. 一致性哈希与跳转哈希怎么选？**
参考答案：同构、连续编号的桶且只要最小迁移，跳转哈希最优且零元数据；异构节点、带权重、需显式环管理则用一致性哈希。副本选择也可考虑 Rendezvous 哈希。

## 九、演进与趋势

**带权虚拟节点**。按机器 CPU/内存权重分配不同数量的虚拟点，实现异构集群负载均衡。

**有界负载一致性哈希**。选后继时检查负载不超过 $(1+\epsilon)$ 平均，Google SRE 与一些 RPC 路由已用。

**跳转哈希与 Rendezvous 哈希**。Jump Hash 迁移最优、实现极简；HRW 适合多副本选择。二者在 gRPC、Envoy、部分云负载均衡中出现。

**与副本、读写协议结合**。Dynamo 的偏好列表（顺时针后继 $N$ 个）+ 法定人数（Quorum）；Cassandra 的 vnode + 一致性级别。

**持久化拓扑与自动再平衡**。Kubernetes 的 StatefulSet、etcd 的成员变更、Cassandra 的 `nodetool cleanup`，都把一致性哈希的迁移流程工程化。

## 十、小结

一致性哈希用环 + 顺时针后继把扩缩容迁移从 $1-1/N$ 压到 $1/N$，用虚拟节点补足负载方差。不变量是「区间连续、增删只撕裂一段弧」；公式是碎棍方差与迁移期望；工程关键是绕回、虚拟节点与拓扑同步。它是 Dynamo 系、Redis Cluster、CDN 调度的基石，也引出跳转哈希、带权与有界负载等现代变体。掌握「为什么是 $1/N$」与「虚拟节点如何换均衡」，就能在面试与设计中把分布式路由讲清楚。
