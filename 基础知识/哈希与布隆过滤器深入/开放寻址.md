# 开放寻址

> 对应 CLRS《Introduction to Algorithms》第 11 章 Hash Tables（开放寻址与双重哈希），以及 Knuth TAOCP Vol.3 的探测序列分析。

## 一、背景与挑战

哈希表解决冲突有两条经典路线：链地址（每个桶挂链表）与开放寻址（Open Addressing，所有键值都存在表数组内）。开放寻址的动机非常工程化：链表节点是分散的小对象，一次查找可能触发多次缓存缺失甚至 GC 压力；而开放寻址把整张表摊在连续数组里，探测时是线性扫内存，对 CPU 缓存极其友好。在装载因子不高时，它的常数往往比链地址小一半以上，因此 Go 的 map（小表）、Rust 的 hashbrown、许多高性能 KV、CPU 缓存模拟器都优先采用开放寻址。

朴素的开放寻址也容易踩坑。若简单地「冲突就看下一个槽」，会形成一次聚集（primary clustering）：一旦某处出现连续占用，后来的键更易落在其尾部，簇越长越容易更长，形成热点。若删除时直接把槽位清空，后续探测链会被截断，明明存在的键会查不到。若装载因子推到 0.9 才扩容，不成功查找的期望探测数已接近 10，延迟尖刺立刻显现。这些不是理论洁癖，而是线上「偶尔超时」的常见根因。

在面试中，开放寻址是「手写哈希表」的标准答案：它考察你是否理解探测序列、墓碑（tombstone）删除、装载因子与扩容。在数据库内核里，哈希连接（hash join）的构建表、布隆过滤器的底层布局、甚至 CPU 的组相联缓存替换，都是开放寻址思想的亲戚。把这一篇读透，链地址法、布隆、缓存行预取可以串成一条线。

## 二、核心原理

**探测序列**。定义 $h(k, i)$ 为键 $k$ 第 $i$ 次探测（$i = 0, 1, \ldots, m-1$）的槽下标，要求对每个固定 $k$，当 $i$ 跑遍 $0..m-1$ 时 $h(k,i)$ 恰好遍历 $0..m-1$ 的一个排列，保证一定能找到空槽或确认不存在。三种标准形式：

1. **线性探测** $h(k,i) = (h'(k) + i) \bmod m$。实现最简单、局部性最好，但一次聚集严重。
2. **二次探测** $h(k,i) = (h'(k) + c_1 i + c_2 i^2) \bmod m$。缓解一次聚集，但同起点的键会走相同步长序列，仍有二次聚集（secondary clustering）。
3. **双重哈希** $h(k,i) = (h_1(k) + i\cdot h_2(k)) \bmod m$。步长由第二个哈希决定，不同键序列不同，聚集最弱。要求 $\gcd(h_2(k), m) = 1$，通常取 $m$ 为质数、$h_2(k)$ 落在 $[1, m-1]$ 且非零。

**插入与查找**。插入时从 $i=0$ 开始探测：遇到空槽或墓碑可写入；遇到相同键则覆盖。查找时同样探测，遇空槽即停止并判定不存在（墓碑要跳过继续探）；遇到键相等则返回。

**删除与墓碑**。开放寻址的删除**不能**简单置空，否则截断探测链。标准做法是写入特殊标记 `TOMB`（墓碑）：查找时跳过墓碑继续探；插入时可把墓碑当作空槽复用。墓碑会拉长查找路径，所以要统计墓碑比例，过高时触发重建（rehash）消除墓碑。

**装载因子与扩容**。设 $\alpha = n/m$ 为占用槽数与表长比（含墓碑则更糟）。线性探测在均匀哈希下不成功查找期望探测数约 $1/(1-\alpha)$，$\alpha=0.5$ 时约 2，$\alpha=0.8$ 时约 5，$\alpha=0.9$ 时约 10。因此工程上常把阈值定在 0.5~0.7，超过就扩到约 2 倍并重新插入。

**不变量**。(1) 对任意已存键 $k$，从 $h(k,0)$ 起沿探测序列直到找到它之前，只会经过墓碑或非 $k$ 的键，绝不会遇到空槽；(2) 删除只写墓碑、不写空槽；(3) 插入前若表中已有 $k$，必须原地更新而不是重复占用新槽。守住这三条，正确性就有保证。

## 三、形式化与数学基础

**线性探测的成功查找**。Knuth 用「占用位串」分析：表中已有 $n$ 个键、$m$ 个槽，$\alpha = n/m$。在均匀哈希假设下，一次成功查找的期望探测次数为
$$
\frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right),
$$
不成功查找为
$$
\frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right).
$$
注意不成功查找在 $\alpha$ 接近 1 时是平方发散，比 $1/(1-\alpha)$ 更悲观。直观解释：簇的平均长度随 $\alpha$ 增大而超线性增长，新键总爱接在簇尾。

**双重哈希 / 理想随机探测**。若每次探测独立均匀（近似双重哈希效果），不成功查找期望探测数为
$$
\sum_{i\ge 1} \alpha^{i-1} = \frac{1}{1-\alpha},
$$
成功查找期望约为
$$
-\frac{1}{\alpha}\ln(1-\alpha).
$$
在 $\alpha = 0.5$ 时线性探测约 2.5（成功）而理想约 1.39；$\alpha = 0.8$ 时线性约 3.0 vs 理想 2.0。可见探测策略能拉开近一倍的差距。

**二次聚集的量化**。二次探测中所有 $h'(k)$ 相同的键共享同一探测序列，若第 $j$ 次探测冲突概率为 $\alpha^{j}$，则同槽键的期望探测长度与线性探测同阶，只是不同槽序列之间不再互相拉长。双重哈希让每键独立步长，期望逼近理想值。

**墓碑对 $\alpha$ 的影响**。设真实键数 $n$、墓碑数 $t$，有效负载 $\alpha_{\text{eff}} = (n+t)/m$。查找期望探测数随 $\alpha_{\text{eff}}$ 恶化。当 $t/(n+t)$ 超过约 1/3 时应重建表，把墓碑清零，把 $m$ 扩到使 $\alpha$ 回落到 0.5 附近。

**扩容复杂度**。扩到 $m' = 2m$ 后重新插入 $n$ 个键，总代价 $O(n)$ 次插入，均摊到 $n$ 次插入上是 $O(1)$；若采用渐进式 rehash（双表并行），可把尖刺摊开，代价是查询需查两张表。

## 四、代码实现

完整开放寻址哈希表：线性探测 + 墓碑删除 + 自动扩容。可直接运行。

```python
"""开放寻址哈希表：线性探测、墓碑删除、自动扩容。"""
from __future__ import annotations

_EMPTY = object()   # 哨兵：从未使用过的槽
_TOMB = object()    # 哨兵：墓碑，曾有元素但已删除


class OpenAddressingMap:
    def __init__(self, capacity: int = 8, load_factor: float = 0.6):
        if capacity < 1:
            raise ValueError("capacity must be >= 1")
        self._cap = capacity
        self._load = load_factor
        self._table = [_EMPTY] * capacity
        self._n = 0          # 真实键值对数量
        self._tomb = 0       # 墓碑数量

    # ---------- 内部工具 ----------
    def _probe(self, key):
        """返回 (第一个空槽或可写槽下标, 是否找到键)。"""
        h = hash(key) % self._cap
        first_tomb = -1
        for i in range(self._cap):
            idx = (h + i) % self._cap
            slot = self._table[idx]
            if slot is _EMPTY:
                # 找到空槽：键不存在；写入点是第一个墓碑或该空槽
                return (first_tomb if first_tomb >= 0 else idx), False
            if slot is _TOMB:
                if first_tomb < 0:
                    first_tomb = idx
                continue
            if slot[0] == key:
                return idx, True
        if first_tomb >= 0:
            return first_tomb, False
        raise RuntimeError("table has no empty slot (corrupt load factor)")

    def _resize(self, new_cap: int) -> None:
        old = self._table
        self._cap = new_cap
        self._table = [_EMPTY] * new_cap
        self._n = 0
        self._tomb = 0
        for slot in old:
            if slot is _EMPTY or slot is _TOMB:
                continue
            k, v = slot
            idx, found = self._probe(k)
            self._table[idx] = (k, v)
            self._n += 1

    def _maybe_grow(self) -> None:
        # 墓碑也算占用，有效负载 = (n + tomb) / cap
        if (self._n + self._tomb + 1) / self._cap > self._load:
            # 优先扩容量；若墓碑比例过高，同容量重建以清墓碑
            if self._tomb > self._n:
                self._resize(self._cap)
            else:
                self._resize(self._cap * 2)

    # ---------- 对外接口 ----------
    def put(self, key, value) -> None:
        self._maybe_grow()
        idx, found = self._probe(key)
        if found:
            self._table[idx] = (key, value)
            return
        if self._table[idx] is _TOMB:
            self._tomb -= 1
        self._table[idx] = (key, value)
        self._n += 1

    def get(self, key, default=None):
        idx, found = self._probe(key)
        return self._table[idx][1] if found else default

    def pop(self, key, default=None):
        idx, found = self._probe(key)
        if not found:
            return default
        value = self._table[idx][1]
        self._table[idx] = _TOMB
        self._n -= 1
        self._tomb += 1
        return value

    def __contains__(self, key) -> bool:
        _, found = self._probe(key)
        return found

    def __len__(self) -> int:
        return self._n

    def stats(self) -> dict:
        return {
            "cap": self._cap,
            "n": self._n,
            "tomb": self._tomb,
            "load": (self._n + self._tomb) / self._cap,
        }


if __name__ == "__main__":
    m = OpenAddressingMap(capacity=4)
    for i in range(20):
        m.put(f"key{i}", i * 10)
    assert m.get("key7") == 70
    assert "key7" in m and "nope" not in m

    # 删除后必须仍能沿探测链找到未删除的键
    for i in range(0, 20, 2):
        m.pop(f"key{i}")
    assert m.get("key1") == 10
    assert m.get("key0") is None
    assert m.get("key19") == 190
    print("stats:", m.stats())

    # 重新插入被删除的键
    m.put("key0", 0)
    assert m.get("key0") == 0
    print("reopen ok, stats:", m.stats())
```

测试覆盖了插入、查找、墓碑删除后再查找、删除键重插四条关键路径。若把 `pop` 误写成「置 `_EMPTY`」，第二个断言链会立刻失败，这正是墓碑存在的原因。

## 五、与其他技术对比

| 维度 | 链地址 | 开放寻址（线性探测） | 双重哈希 | 布隆过滤器 |
|------|--------|----------------------|----------|------------|
| 内存布局 | 节点分散，指针多 | 连续数组，缓存友好 | 连续，略差于线性 | 位数组，极省 |
| 高负载表现 | 链变长，仍可接受 | $\alpha>0.8$ 后急剧变差 | 介于两者 | 误判率上升 |
| 删除 | 直接删节点 | 需墓碑 | 需墓碑 | 原生不可删 |
| 并发扩展 | 锁粒度细、易分段 | 伪共享多，难 | 同左 | 读多写少友好 |
| 典型场景 | Java HashMap（高负载） | Go map、Rust hashbrown、小表 | 理论分析 | 海量集合判存在 |

与链地址相比，开放寻址在 $\alpha < 0.7$ 时更快、内存更紧凑；链地址在高负载与频繁删除时更稳。与布隆过滤器相比，开放寻址是精确结构，无误判，但空间按元素数线性增长。

## 六、常见误区

**删除直接置空**。后续查找在探测到空槽时提前结束，导致本存在的键「消失」，插入还可能重复。必须用墓碑，并在墓碑过多时重建。

**装载因子当安全区**。把 $\alpha$ 推到 0.95 才扩容，不成功查找期望探测接近 20，p99 延迟爆炸。应按 0.5~0.7 触发扩容，并把墓碑计入有效负载。

**双重哈希的 $h_2$ 与 $m$ 不互质**。若 $m=2^p$ 且 $h_2$ 为偶数，探测只走半个表，找不到空槽就死循环。保证 $\gcd(h_2, m)=1$：要么 $m$ 取质数，要么强制 $h_2$ 为奇数。

**查找遇到墓碑就停止**。墓碑意味着「此处曾有元素」，必须跳过继续探，否则漏查。只有 `_EMPTY` 才是终止哨兵。

**线性探测不做扰动**。`hash(key)` 低位若不随机，整段表会连成一条巨簇。插入前应对哈希值做一次混合（见「哈希函数设计」篇）。

## 八、面试题

**1. 手写一个支持增删查的哈希集合。**
参考答案：数组 + 开放寻址。插入沿 $h(k,i)$ 找空槽或同键覆盖；删除写墓碑；查找遇空槽停止、遇墓碑跳过。装载因子超 0.6 时翻倍重建。注意删除不能置空、扩容要把墓碑算进负载。

**2. 线性探测 vs 双重哈希，如何选？**
参考答案：数据少、缓存敏感选线性探测（常数小、预取友好）；负载可能较高、键分布有偏时选双重哈希减少聚集。二者都要控制 $\alpha$ 与墓碑。

**3. 为什么开放寻址的删除复杂？**
参考答案：探测序列依赖「连续占用」形成查找路径。置空会截断路径；墓碑保留路径但拉长探测。正确删除 = 写墓碑 + 定期重建。

**4. $\alpha=0.7$ 时，不成功查找期望探测数大约多少？**
参考答案：线性探测约 $\frac12(1+\frac{1}{(1-0.7)^2}) \approx 6$，理想随机探测约 $1/(1-0.7)\approx 3.3$。说明高负载下探测策略差异被放大。

## 九、演进与趋势

**Robin Hood 哈希**。插入时若当前键的探测长度小于槽内键，则交换（劫富济贫），使各键探测长度方差极小，p99 更稳，且删除可用「向后挪移」避免墓碑。

**Cuckoo 哈希**。两个哈希、两个槽，插入冲突就把旧键踢走重插，最坏 $O(1)$ 查找，适合读多写少的网络设备转发表。

**SwissTable / SIMD 探测**。用 16 字节控制字存储每个槽的状态与截断哈希，一次 SSE/NEON 比较 16 个候选，把线性探测的常数再降一截。Abseil 与 Rust 标准库都采用。

**渐进式 rehash**。Redis dict 在扩容时每次操作搬迁少量桶，避免一次性停顿；查询期间新旧两张表同时存在。

**缓存感知布局**。把键放一个数组、值放另一个数组（SoA），或把热点键复制进缓存行，进一步减少缺失。

## 十、小结

开放寻址把冲突消解在连续数组内，用探测序列换取缓存友好与低常数。核心不变量是「删除写墓碑、遇空槽才停、哈希必须混合」；核心公式是不成功查找约 $1/(1-\alpha)$ 或更悲观的二次形式，决定了装载因子阈值。与链地址相比它在中低负载下更快，与布隆相比它精确可删但更耗空间。看懂探测序列、墓碑与扩容，就掌握了现代开放寻址哈希表（Go map、SwissTable）的共同骨架。
