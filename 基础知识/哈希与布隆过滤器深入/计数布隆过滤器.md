# 计数布隆过滤器

> 对应 Fan, Cao, Almeida, Broder《Summary Cache: A Scalable Wide-Area Web Cache Sharing Protocol》(SIGCOMM 1998) 中的 Counting Bloom Filter，以及后续关于压缩计数的分析论文。

## 一、背景与挑战

标准布隆过滤器有一个致命限制：**不能安全删除**。位数组的每一位可能被多个元素共享，清掉某元素对应的 $k$ 位，会把其它元素共享的位一并清 0，于是查询那些元素时出现假阴性——这是布隆的设计红线。在缓存代理、会话表、URL 去重、流式去重等场景里，元素会过期或被显式移除，只进不出的布隆会越用越满、假阳性持续上升，最终失去拦截价值。

计数布隆过滤器（Counting Bloom Filter, CBF）用**小计数器**替换每一位：插入加 1，删除减 1，查询看 $k$ 个计数器是否都大于 0。这样删除只影响属于该元素的计数，不会误伤共享位。代价是空间从 1 位/槽涨到 $c$ 位/槽（常见 4 位），并带来计数器溢出的新问题。

在工程与面试中，「布隆能不能删除、怎么删」是高频考点。RedisBloom 的 `BF.MEXISTS` 与可删除变体、Guava 的布隆、HBase 的删除路径，都需要在「空间、删除、误判、溢出」四者间做权衡。读完本篇，你应能说清 CBF 的误删/误判来源、计数器宽度的期望分析、以及与 d-left Counting Bloom、Cuckoo Filter 的取舍。

## 二、核心原理

**结构**。$m$ 个计数器 $C[0..m-1]$，每个 $c$ 位（$c=4$ 常见），初始全 0。$k$ 个哈希函数 $h_1..h_k$，映到 $[0, m)$。

**插入** $add(x)$：对 $i=1..k$，$C[h_i(x)] \mathrel{+}= 1$。若计数器已满（$2^c-1$），必须做**饱和处理**或记录溢出，否则下一次加法回绕到 0，破坏「删除只减自己」的语义。

**删除** $remove(x)$：对 $i=1..k$，$C[h_i(x)] \mathrel{-}= 1$。前提是 $x$ 确实曾被插入且未被删过。删除不存在元素会导致计数变负或下溢，后续查询假阴性。

**查询** $contains(x)$：所有 $C[h_i(x)] > 0$ 则「可能在」；任一为 0 则「必不在」。与布隆一样无假阴性（在正确维护计数的前提下）、有假阳性。

**与标准布隆的关系**。把每个计数器压成 1 位（只记录是否 >0）就退化为布隆过滤器。CBF 是「位 → 计数」的加维版本，插入/删除在群 $(\mathbb{Z}, +)$ 上可逆，因而支持删除。

**不变量**。(1) 对任意已插入未删除元素 $x$，其 $k$ 个计数器均 $\ge 1$；(2) 删除只对已插入元素做，且 $k$ 个计数器各自减 1；(3) 计数器不得回绕，溢出要饱和或触发重建；(4) 查询全 0 才判不存在，全 >0 只是可能在。

**边界条件**。计数器宽度 $c$ 太小会频繁饱和；太大浪费空间。删除从未插入的元素是最常见 bug。并发场景下加减不是原子时需要锁或原子指令（`fetch_add`）。

## 三、形式化与数学基础

**误判率**。设期望元素数 $n$、槽 $m$、计数器宽度 $c$。在无饱和、哈希均匀下，单个计数器均值 $\lambda = kn/m$。查询不存在元素时，$k$ 个计数器全非 0 的概率近似与标准布隆相同：
$$
p \approx \left(1 - e^{-kn/m}\right)^k,
$$
最优 $k^* = (m/n)\ln 2$ 时 $p \approx 0.6185^{m/n}$。也就是说**误判率与标准布隆同阶**，增加的是删除能力，不是更好的精度。

**空间放大**。标准布隆 $m$ 位；CBF 为 $cm$ 位。当 $c=4$ 时空间是 4 倍。若按同样的 $m/k$ 规划，CBF 每个元素约占 $4 \times 1.44 \ln(1/p)$ 位。例如 $p=1\%$ 时布隆约 1.44 B/元素，CBF($c=4$) 约 5.8 B/元素。仍远小于 HashSet。

**计数器饱和概率**。单个计数器在 $n$ 次插入下的增量近似 $\mathrm{Poisson}(\lambda)$，$\lambda = kn/m = k / (m/n)$。饱和概率
$$
P_{\text{sat}} = \Pr[\mathrm{Poisson}(\lambda) \ge 2^c] \approx \sum_{i \ge 2^c} e^{-\lambda}\frac{\lambda^i}{i!}.
$$
当 $c=4$（上限 15）、$k=7$、$m/n = 10$（即 $\lambda = 0.7$）时 $P_{\text{sat}}$ 可忽略；若 $m/n$ 过小（表偏紧，$\lambda$ 变大），饱和概率急剧上升。故 CBF 不能像布隆那样把 $m$ 压得过紧，通常 $m/n$ 要比布隆更宽松，或 $c$ 取 4~8。

**误删与计数共享**。删除 $x$ 时减去的计数器可能由 $x$ 与其它元素共同贡献。只要 $x$ 曾插入，减 1 后其它元素的贡献仍在，查询其它元素不会假阴性。但如果 $x$ 未插入就删除，会把共享计数减掉，制造假阴性。这与标准布隆「清位误伤」是同一问题，只是 CBF 把伤害限制在计数上。

**溢出策略的期望代价**。若饱和后永久停在 $2^c-1$，则该槽永不归零，元素删除不完整，假阳性率上升但无假阴性（偏保守）。若溢出回绕到 0，则会出现假阴性，不可接受。工程上选「饱和 + 定期重建」。

## 四、代码实现

计数布隆过滤器：双哈希、饱和计数、安全删除、溢出统计。可直接运行。

```python
"""计数布隆过滤器（Counting Bloom Filter）。"""
from __future__ import annotations

import hashlib
import math
from typing import Iterable


class CountingBloomFilter:
    def __init__(self, m: int, k: int, counter_bits: int = 4):
        if m <= 0 or k <= 0:
            raise ValueError("m and k must be positive")
        if not (1 <= counter_bits <= 8):
            raise ValueError("counter_bits must be in 1..8")
        self.m = m
        self.k = k
        self.bits = counter_bits
        self.max_count = (1 << counter_bits) - 1
        self.counters = [0] * m
        self.n_items = 0
        self.saturation = 0  # 达到饱和的次数（可监控）

    def _indexes(self, item) -> Iterable[int]:
        if not isinstance(item, (bytes, bytearray)):
            item = str(item).encode("utf-8")
        d = hashlib.md5(item).digest()
        h1 = int.from_bytes(d[:8], "big")
        h2 = int.from_bytes(d[8:16], "big") | 1
        for i in range(self.k):
            yield (h1 + i * h2) % self.m

    def add(self, item) -> None:
        for idx in self._indexes(item):
            if self.counters[idx] < self.max_count:
                self.counters[idx] += 1
            else:
                self.saturation += 1  # 已饱和，保持不变（禁止回绕）
        self.n_items += 1

    def remove(self, item) -> bool:
        """删除元素。若元素可能不存在，返回 False 且不动计数。"""
        idxs = list(self._indexes(item))
        # 先检查：若任一计数为 0，说明元素从未插入（或已被删），拒绝删除
        if any(self.counters[i] == 0 for i in idxs):
            return False
        for i in idxs:
            self.counters[i] -= 1
        self.n_items -= 1
        return True

    def might_contain(self, item) -> bool:
        return all(self.counters[i] > 0 for i in self._indexes(item))

    def estimated_fpr(self) -> float:
        # 用平均占用率近似：非零槽比例
        nonzero = sum(1 for c in self.counters if c > 0)
        ratio = nonzero / self.m
        return ratio ** self.k


def params_for(n: int, p: float, counter_bits: int = 4) -> tuple[int, int]:
    """按目标假阳性率定 m、k。CBF 空间是位布隆的 counter_bits 倍，规划时留裕量。"""
    m_bits = math.ceil(-n * math.log(p) / (math.log(2) ** 2))
    # 计数器存的是槽；m 就是槽个数，与布隆的 m 同义（布隆 m 也是槽/位数）
    m = m_bits
    k = max(1, round(m / n * math.log(2)))
    return m, k


if __name__ == "__main__":
    n, p = 50_000, 0.01
    m, k = params_for(n, p, 4)
    print(f"m={m} slots (~{m*4/8/1024:.1f} KB @4bit), k={k}")

    cbf = CountingBloomFilter(m, k, counter_bits=4)
    for i in range(n):
        cbf.add(f"sess:{i}")

    assert cbf.might_contain("sess:0")
    assert cbf.remove("sess:0")
    assert not cbf.might_contain("sess:0") or True  # 允许其它元素造成的假阳性
    assert not cbf.remove("never-inserted")

    fp = sum(1 for i in range(n, n + 20_000) if cbf.might_contain(f"sess:{i}"))
    print(f"empirical fpr: {fp/20_000:.4f}, saturation events: {cbf.saturation}")
    print("ok")
```

实现要点：删除前先验证 $k$ 个计数器全 >0，拒绝删除不存在的元素；饱和时不回绕，只计数监控。这避免了 CBF 最常见的两个 bug。

## 五、与其他技术对比

| 维度 | 标准布隆 | 计数布隆 CBF | d-left Counting Bloom | Cuckoo Filter |
|------|----------|--------------|----------------------|---------------|
| 空间 | 1 位/槽 | $c$ 位/槽（约 4×） | 略优于 CBF | 约 2~4 B/元素 |
| 删除 | 不支持 | 支持（需正确插入） | 支持 | 支持 |
| 假阳性 | 有 | 有（同阶） | 有（略优） | 有（略优） |
| 假阴性 | 无 | 无（正确实现） | 无 | 无 |
| 溢出/碰撞 | 无溢出 | 计数器溢出需处理 | 桶满需踢出 | 桶满踢出 |
| 查询代价 | $O(k)$ | $O(k)$ | $O(1)$ 探测 | $O(1)$ |
| 典型场景 | 只增集合 | 有过期/删除的去重 | 网络流去重 | 需删除的近似集合 |

与 d-left CBF 相比：d-left 把桶分成 $d$ 段，每桶存短指纹，空间利用率更高、查询更快，但实现更复杂。与 Cuckoo Filter 相比：CBF 更易增量扩展，Cuckoo 查询常数更优且支持动态删除更自然。与精确 HashSet 相比：CBF 仍省 1~2 个数量级内存，但必须容忍假阳性。

## 六、常见误区

**删除从未插入的元素**。直接减 1 会把共享计数器减到 0 甚至负值，造成假阴性。正确做法是删除前检查 $k$ 个计数器是否全 >0（近似判断），或用集合做「真值 oracle」仅在确知插入过时删除。后果是缓存/去重系统漏判，比假阳性严重得多。

**计数器溢出回绕**。4 位计数器加到 16 会变 0，把「曾插入」变成「不存在」，制造假阴性。必须饱和（停在 15）或在溢出时触发重建。后果与删除错误同级，都是正确性破坏。

**把 CBF 当精确集合用**。查询返回 True 只是可能在；下游若据此「跳过写入/跳过检查」会引入脏数据。CBF 只能做「必不在则跳过」的负向过滤。

**宽度规划过紧**。照搬布隆的 $m/n$ 却用 $c=4$，$\lambda = kn/m$ 偏大，饱和概率上升，删除不完整，假阳性率飙升。CBF 的 $m$ 应比布隆更宽松，或监控饱和率。

**并发下无锁加减**。两个线程对同一计数器 `+= 1` 可能丢更新，导致计数偏低、查询假阴性。需原子操作或分片锁。

## 八、面试题

**1. 如何给布隆过滤器加删除？有哪些坑？**
参考答案：用计数布隆，每位换成 $c$ 位计数器，插入加 1、删除减 1，查询全 >0。坑：删除不存在元素会减掉共享计数造成假阴性；计数器溢出回绕同样制造假阴性。必须饱和处理、删除前校验，或改用 Cuckoo Filter。

**2. 计数布隆的空间代价是多少？何时值得？**
参考答案：空间约为标准布隆的 $c$ 倍（$c=4$ 时 4 倍）。当元素会过期/删除、且假阴性不可接受时值得；若集合只增不减，用标准布隆更省。

**3. 为什么 CBF 仍然可能假阳性？**
参考答案：假阳性来自 $k$ 个计数器被其它元素碰巧都碰过。计数只解决删除，不解决哈希碰撞。误判率仍约 $(1-e^{-kn/m})^k$，与标准布隆同阶。

**4. 如何处理计数器溢出？**
参考答案：饱和停在 $2^c-1$（偏保守，只会略增假阳性），并在饱和率超阈值时重建过滤器（重插所有现存元素）；绝不能回绕。监控 `saturation` 指标。

## 九、演进与趋势

**压缩计数与 Spectral Bloom**。用变长编码/熵压缩存计数，只对热点桶分配宽计数；Spectral Bloom 用近似计数做「频繁元素」估计。

**d-left Counting Bloom**。桶式指纹 + 多段布局，空间与查询都优于朴素 CBF，用于网络流、DNS 缓存。

**Cuckoo / Ribbon Filter**。直接支持删除、查询一次内存访问，RocksDB、RedisBloom 等生产系统逐步采用。

**持久化与分片**。把计数器数组放持久内存或按 key 前缀分片，支持重启后继续维护删除语义；配合 LSM 的 compaction 做「过滤器重建」。

**时间衰减与滑动窗口**。计数按时间衰减（如指数衰减桶），用于「最近是否出现」这类带时效的去重。

## 十、小结

计数布隆过滤器把布隆的每一位换成 $c$ 位计数器，用约 $c$ 倍空间换取安全删除：插入加 1、删除减 1、查询看全 >0。误判率与标准布隆同阶，但多了溢出与「删不存在元素」两个正确性陷阱——饱和处理与删除前校验缺一不可。当集合有删除/过期、且假阴性不可接受时，CBF 是比标准布隆更合适的选择；若还要求更低查询代价与原生删除，可转向 Cuckoo Filter 或 d-left CBF。
