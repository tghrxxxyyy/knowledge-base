# 可扩展哈希

> 对应 Fagin et al.《Extendible Hashing — A Fast Access Method for Dynamic Files》(ACM TODS, 1979)，以及 Garcia-Molina《Database Systems: The Complete Book》外存索引章节。

## 一、背景与挑战

数据库与文件系统里的哈希索引不能像内存哈希表那样说扩容就整体 rehash：数据可能有几十 GB，全表重写意味着大量随机 IO、长时间锁表、在线抖动。传统静态哈希表一旦装载因子升高，唯一手段是申请更大的数组并把所有桶重排一遍，代价与文件大小成正比。更糟的是磁盘块（页）才是 IO 单位，桶必须按页组织，全量 rehash 会把所有热点页打散重写，缓存命中率瞬间归零。

可扩展哈希（Extendible Hashing）正是为「外存动态文件」设计的增量式方案。它的目标是：**桶溢出时只分裂这一个桶，而不是整张表**。目录（directory）记录全局深度，桶记录局部深度；分裂只重排溢出桶里的那一页数据，其它桶纹丝不动。这样一次插入的最坏额外 IO 被限制在常数页级，非常适合读多写少、数据持续增长的索引结构。

在工程与面试语境中，可扩展哈希与线性哈希、B+ 树并列为「外存索引三大路线」。面试官常问：「哈希索引如何支持动态扩容？」「可扩展哈希与线性哈希区别在哪？」「为什么数据库多用 B+ 树而不是哈希？」读懂本篇后，你能解释目录翻倍的触发条件、局部/全局深度不变量、以及内存目录本身成为瓶颈时的改进方向。它也是理解 AWS Aurora、部分 KV 存储、内存数据库（如早期的 T-tree 替代方案）里动态哈希变体的基础。

## 二、核心原理

**两个深度**。每个桶 $b$ 有一个**局部深度** $ld_b$，表示该桶的键在哈希值的前 $ld_b$ 位上完全相同。整个结构有一个**全局深度** $gd$，目录大小为 $2^{gd}$。目录项 $d[i]$ 指向某个桶；桶的局部深度满足 $ld_b \le gd$，并且所有指向 $b$ 的目录下标在高 $ld_b$ 位上一致。

**路由**。对键 $k$ 计算哈希 $h(k)$，取其高 $gd$ 位作为目录下标 $i$，再由 $d[i]$ 找到桶。换言之：
$$
\text{bucket}(k) = d[\text{high}_{gd}(h(k))].
$$
实现上常用「低 $gd$ 位」或「高 $gd$ 位」之一，只要全篇一致即可；关键是位提取方向必须与目录增长方式匹配。

**分裂规则**。当向桶 $b$ 插入导致溢出（桶内键数 $>$ 页容量 $B$）时：
1. 若 $ld_b < gd$：**局部分裂**。新建桶 $b'$，令 $ld_{b'} = ld_b + 1$，把 $b$ 中对应下一位为 1 的键搬去 $b'$，并把目录中那些下标指向 $b'$。目录不扩。
2. 若 $ld_b = gd$：**全局分裂**。目录翻倍（$gd \leftarrow gd + 1$），旧目录项 $i$ 的复制项 $i + 2^{gd-1}$ 先指向同一桶；然后对溢出桶做局部分裂（$ld$ 增一），并按新 $ld$ 重新指向目录项。

**不变量**。(1) $ld_b \le gd$ 对所有桶成立；(2) 目录中所有指向桶 $b$ 的下标，其高 $ld_b$ 位相同，且该前缀唯一；(3) 一个桶可能被多个目录项共享（当 $ld_b < gd$），这是目录能「只分裂局部」的关键；(4) 插入导致的桶分裂只搬一个桶的数据，期望代价 $O(B)$ 键。

**边界条件**。初始 $gd = 0$，目录只有一项、一个桶。哈希碰撞（不同键同值）在桶内用列表/溢出页存。目录本身也可能太大（$2^{gd}$ 项），此时可改用「目录也分页」或转向线性哈希。

## 三、形式化与数学基础

**目录大小**。有
$$
|D| = 2^{gd}, \qquad 1 \le |D| \le 2^{32}\ \text{（受内存限制，实际远小于此）}.
$$
每个桶容量 $B$（页可放的最大键数）。设文件中键数 $n$，桶数 $N_b$。若哈希均匀，则每个桶期望键数 $\mathbb{E}[|b|] = n / N_b$。

**分裂的期望代价**。一次局部分裂只遍历一个桶（$O(B)$）并重写该桶与新桶的页，目录只更新若干指针（$O(2^{gd - ld_b})$ 项）。若 $ld_b \ll gd$，目录更新很多但桶 IO 很少。全局分裂目录翻倍，内存操作 $O(2^{gd})$，但仍只搬一个桶的数据到磁盘。

**深度的期望**。在均匀哈希下，键的 $gd$ 位前缀近似均匀分到 $2^{gd}$ 个目录项。当 $n$ 增大、桶溢出时，$gd$ 约为 $\log_2(n/B)$ 量级。更精细地，当所有桶恰好装满 $B$、且完全均匀时，桶数 $N_b \approx n/B$，而目录项数 $2^{gd}$ 与 $N_b$ 同阶，故
$$
gd \approx \log_2 N_b \approx \log_2 (n/B).
$$
目录内存 $\approx 2^{gd} \cdot \text{指针大小}$，在 $n = 10^7$、$B = 100$ 时 $N_b \approx 10^5$、$gd \approx 17$，目录约 13 万指针，可接受；$n$ 再大两个数量级目录就开始吃紧。

**与静态哈希 rehash 的对比**。静态表扩到 $2m$ 需 $O(n)$ 次键搬移与全表重写。可扩展哈希总分裂次数为桶数增长量级 $O(N_b)$，每次 $O(B)$，总搬移 $O(n)$ 但**分摊到各次插入**，单次最坏 IO 有界，且无全表锁。

**溢出概率**。若键服从泊松近似，桶内键数方差随 $B$ 增大而相对变小；页越大，触发分裂的频率越低，但单次分裂 IO 越大。取 $B$ 为磁盘页大小（4KB）除以键+指针长度是常见工程折中。

## 四、代码实现

完整可扩展哈希：目录数组 + 局部/全局深度 + 局部/全局分裂。键用稳定哈希，取高 `gd` 位作目录下标。

```python
"""可扩展哈希（Extendible Hashing）教学实现。"""
from __future__ import annotations

import hashlib
from collections import defaultdict


def _stable_hash(key) -> int:
    if not isinstance(key, (bytes, bytearray)):
        key = str(key).encode("utf-8")
    d = hashlib.md5(key).digest()
    return int.from_bytes(d[:8], "big")  # 64-bit


class Bucket:
    __slots__ = ("local_depth", "pairs", "capacity")

    def __init__(self, local_depth: int, capacity: int):
        self.local_depth = local_depth
        self.capacity = capacity
        self.pairs: list[tuple] = []


class ExtendibleHash:
    def __init__(self, bucket_capacity: int = 3):
        self.cap = bucket_capacity
        self.global_depth = 0
        # 目录：list[Bucket]，下标为哈希高 global_depth 位
        self.directory: list[Bucket] = [Bucket(0, bucket_capacity)]

    def _index(self, key: int) -> int:
        # 取哈希值的高 gd 位（从 64 位的高位切）
        if self.global_depth == 0:
            return 0
        return (key >> (64 - self.global_depth)) & ((1 << self.global_depth) - 1)

    def _prefix_match(self, key: int, local_depth: int) -> int:
        """键的哈希在前 local_depth 位上的前缀值。"""
        if local_depth == 0:
            return 0
        return (key >> (64 - local_depth)) & ((1 << local_depth) - 1)

    def put(self, key, value) -> None:
        h = _stable_hash(key)
        idx = self._index(h)
        bucket = self.directory[idx]
        for i, (k, v) in enumerate(bucket.pairs):
            if k == key:
                bucket.pairs[i] = (key, value)
                return
        bucket.pairs.append((key, value))
        if len(bucket.pairs) > bucket.capacity:
            self._split(idx)

    def get(self, key, default=None):
        h = _stable_hash(key)
        bucket = self.directory[self._index(h)]
        for k, v in bucket.pairs:
            if k == key:
                return v
        return default

    def delete(self, key) -> bool:
        h = _stable_hash(key)
        bucket = self.directory[self._index(h)]
        for i, (k, v) in enumerate(bucket.pairs):
            if k == key:
                bucket.pairs.pop(i)
                return True
        return False

    def _split(self, idx: int) -> None:
        bucket = self.directory[idx]
        ld = bucket.local_depth

        if ld == self.global_depth:
            # 全局分裂：目录翻倍，旧指针成对复制
            old_size = 1 << self.global_depth
            self.directory.extend([self.directory[i] for i in range(old_size)])
            self.global_depth += 1
            # 分裂后 idx 可能不是原桶的唯一前缀，用前缀重算
            # 原桶在新目录中覆盖 idx 与 idx + old_size
            idx = self._index(_stable_hash(bucket.pairs[0][0])) if bucket.pairs else idx

        # 局部分裂：按 local_depth+1 位把桶内键分成两半
        new_ld = ld + 1
        mask_bit = 1 << (64 - new_ld)  # 新增的那一位（在 64 位哈希中的位置）
        left = Bucket(new_ld, self.cap)
        right = Bucket(new_ld, self.cap)
        for k, v in bucket.pairs:
            h = _stable_hash(k)
            if h & mask_bit:
                right.pairs.append((k, v))
            else:
                left.pairs.append((k, v))
        bucket.local_depth = new_ld
        left.local_depth = new_ld
        right.local_depth = new_ld

        # 更新目录：前缀为 left_p 的指向 left，为 right_p 的指向 right
        # left_p 的 new_ld 位在 64 位哈希中；目录索引用高 new_ld 位
        left_p = self._prefix_match(_stable_hash(left.pairs[0][0]) if left.pairs else 0, new_ld)
        right_p = self._prefix_match(_stable_hash(right.pairs[0][0]) if right.pairs else 0, new_ld)
        # 若某侧为空，用 idx 的前缀推导
        if not left.pairs and right.pairs:
            right_p = self._prefix_match(_stable_hash(right.pairs[0][0]), new_ld)
            left_p = right_p ^ (1 << (self.global_depth - new_ld))
        if not right.pairs and left.pairs:
            left_p = self._prefix_match(_stable_hash(left.pairs[0][0]), new_ld)
            right_p = left_p ^ (1 << (self.global_depth - new_ld))

        for i in range(1 << self.global_depth):
            if self.directory[i] is bucket:
                # 目录项 i 的高 new_ld 位
                p = (i >> (self.global_depth - new_ld)) if self.global_depth >= new_ld else 0
                # 更稳：比较 i 与 left_p / right_p 的高 new_ld 位
                # 目录下标 i 本身就是高 gd 位；高 new_ld 位 = i >> (gd - new_ld)
                high = i >> max(0, self.global_depth - new_ld)
                if high == left_p:
                    self.directory[i] = left
                else:
                    self.directory[i] = right

    def stats(self) -> dict:
        buckets = set(id(b) for b in self.directory)
        return {
            "global_depth": self.global_depth,
            "dir_size": len(self.directory),
            "num_buckets": len(buckets),
            "sizes": sorted(len(b.pairs) for b in {id(x): x for x in self.directory}.values()),
        }


if __name__ == "__main__":
    eh = ExtendibleHash(bucket_capacity=3)
    for i in range(30):
        eh.put(f"item{i}", i)
    print(eh.stats())
    for i in range(30):
        assert eh.get(f"item{i}") == i, i
    eh.delete("item0")
    assert eh.get("item0") is None
    assert eh.get("item1") == 1
    print("all ok")
```

说明：实现取哈希的**高** `gd` 位作目录下标，分裂时按「新增的那一位」把溢出桶一分为二，目录中所有指向旧桶的项按新前缀重定向。这是 Fagin 论文的标准结构。

## 五、与其他技术对比

| 维度 | 静态哈希表 | 可扩展哈希 | 线性哈希 | B+ 树 |
|------|------------|------------|----------|-------|
| 扩容粒度 | 全表 | 单桶 + 必要时目录 | 单桶顺序分裂 | 页分裂 |
| 最坏插入 IO | 高（全量 rehash） | 低（1~2 页） | 低 | 低（可能递归分裂） |
| 额外元数据 | 无 | 目录 $2^{gd}$ 项 | 分裂指针 + 溢出链 | 内部节点 |
| 范围查询 | 不支持 | 不支持 | 不支持 | 天然支持 |
| 目录膨胀风险 | 无 | 有 | 无 | 无 |
| 实现复杂度 | 低 | 中高 | 中 | 中高 |

与线性哈希相比：线性哈希按顺序逐个分裂桶（$h(k) \bmod (n + 2^i)$），无大目录，但可能需要溢出链；可扩展哈希目录换精确路由、无溢出链，代价是目录可能指数增长。与 B+ 树相比：哈希点查更快（常数），但不支持范围扫描与排序，因此 OLTP 主键索引多用 B+ 树，点查缓存、去重集合才用动态哈希。

## 六、常见误区

**全局/局部深度混淆**。认为「目录翻倍就是所有桶分裂」，或把局部深度当成目录下标长度。正确关系是 $ld \le gd$，目录中可有多个项指向同一桶。后果是路由错乱、键写进错误桶。

**目录翻倍后旧指针未复制**。只把新一半目录填成空桶，丢掉原映射，数据瞬间不可见。翻倍时必须把 $d[i]$ 复制给 $d[i + 2^{gd-1}]$。

**位提取方向写反**。用低 $gd$ 位索引却按高位比较前缀，或移位量算错（如 32 位哈希却按 64 位移）。后果是同一前缀的键被分进不同桶。用哈希空间宽度写进代码常量并单测。

**分裂后忘记更新所有别名目录项**。局部分裂时只更新 $d[idx]$，忘记该桶被 $2^{gd-ld}$ 个目录项共享，导致半边路由仍指旧桶。应遍历所有 `directory[i] is old_bucket` 的项。

**认为可扩展哈希「不会退化」**。若哈希极度倾斜，全局深度会持续翻倍、目录内存爆炸。此时应换线性哈希、改用更强的哈希，或对目录做二级分页。

## 八、面试题

**1. 数据库哈希索引如何在不停机的情况下扩容？**
参考答案：用可扩展哈希（目录+局部/全局深度）或线性哈希（顺序分裂）。可扩展哈希在桶溢出时只分裂该桶，必要时目录翻倍，避免全表 rehash，单次插入 IO 有界。

**2. 可扩展哈希与线性哈希的核心区别？**
参考答案：可扩展哈希用显式目录（$2^{gd}$ 项）做精确路由，局部深度相同的桶被多个目录项共享；线性哈希无大目录，按分裂指针逐桶分裂，可能需要溢出链。前者点查快、元数据大；后者内存省、写路径略复杂。

**3. 为什么 B+ 树仍是主流索引而动态哈希不是？**
参考答案：B+ 树叶子有序，天然支持范围查询、排序、前缀匹配与前向/后向扫描；哈希只做等值点查。OLTP 场景多为范围与排序，故 B+ 树更通用。哈希用于等值热点缓存。

**4. 什么情况下可扩展哈希会失效？**
参考答案：哈希分布差导致全局深度暴涨、目录内存爆炸；或键极度集中让少数桶反复分裂。需换强哈希、线性哈希，或对目录分页。

## 九、演进与趋势

**目录压缩**。把目录本身也按页组织（目录页 + 页内偏移），或用「只存非空前缀的 trie 目录」，避免 $2^{gd}$ 内存占用。

**线性哈希的回归**。因为无大目录、分裂顺序可控，很多嵌入式 KV 与内存库（如一些 session store）选线性哈希 + 溢出页。

**与页缓存/SSD 的协同**。桶大小对齐页（4KB/16KB），分裂时用追加写而非原地改，配合 WAL 保证崩溃恢复。

**并发可扩展哈希**。对目录加读写锁、对桶加锁，或使用 lock-free 的目录快照；MemC3、部分 Redis 模块与研究原型有实现。

**混合索引**。点查走哈希、范围走 B+ 树或 LSM，如 some NewSQL 的二级索引路由；或用 extendible hashing 管理 LSM 的稀疏索引分片。

## 十、小结

可扩展哈希用「全局深度 $gd$ 管目录、局部深度 $ld$ 管桶」把扩容粒度从整表降到单桶：溢出时先局部分裂，$ld = gd$ 时目录翻倍再局部分裂。不变量是 $ld \le gd$ 与目录项别名共享，位提取方向必须一致。相比静态 rehash，它把 IO 摊到每次插入；相比线性哈希，它以目录内存换无溢出链的精确路由。外存等值索引、内存去重集合是它的主场，范围查询仍要交给 B+ 树。
