# 哈希函数设计

> 对应 Knuth《The Art of Computer Programming》Vol.3 Sorting and Searching 哈希章节，以及 Austin Appleby 的 MurmurHash 设计说明与《Algorithm Design with C++ / CLRS》中的散列分析。

## 一、背景与挑战

哈希函数是把任意大小的键（字符串、对象、大整数）映射到固定范围整数的核心部件，几乎所有常数期望时间的查找结构——哈希表、布隆过滤器、一致性哈希环、分片路由——都建立在它之上。工程上对它的要求可以浓缩为三条：**确定性**（同一键永远得到同一值，否则查找会静默失效）、**均匀性**（不同键应尽量均匀落到各个槽位）、**高效性**（单次计算应接近一次内存访问或几条算术指令，不能成为热点）。差的哈希函数会让本应 $O(1)$ 的哈希表退化成 $O(n)$ 的链表扫描，线上表现为「明明只有几万条数据却慢得离谱」。

朴素做法为什么不行？若把字符串所有字符的编码直接相加再取模，那么 `"abc"`、`"bac"`、`"cba"` 会落到同一桶，Anagram 类键完全聚集。若只看字符串长度或首尾字符，分布同样灾难。Java 早期 `String.hashCode` 若不做二次扰动，高位信息在取模 $2^k$ 时被直接丢掉，短字符串在小表中严重倾斜。反过来，过度复杂的密码学哈希（SHA-256）虽然均匀，但吞吐量比非加密哈希低一个数量级，在每次 map 查找都要调用时不可接受。因此哈希函数设计的本质是：**在「分布质量」与「计算成本」之间做精确取舍**。

在面试与工程语境里，这一主题几乎必考。面试官常问「HashMap 为什么要把 hashCode 右移 16 位再异或」「为什么表大小取质数或 2 的幂」「Murmur 比取模好在哪」。答得好的人能把均匀性、雪崩效应、乘法散列的黄金分割常数串成一条线，而不是背「要选好的哈希函数」。在 Redis、Guava、Memcached、RocksDB 的源码里，你也会看到 FNV、Murmur3、xxHash、SipHash 等具体选型，理解设计动机才能正确使用与调参。

## 二、核心原理

**均匀性与雪崩效应**。好的非加密哈希要求输入哪怕只变一个比特，输出也应大约一半比特翻转，这称为雪崩效应（Avalanche Effect）。它保证相邻键（如 `"user:1001"` 与 `"user:1002"`）不会落进同一桶。实现雪崩靠的是「混合」：乘法、移位、异或的反复叠加。乘法会把低位差异扩散到高位（乘积的高位同时受乘数多个比特影响），移位再把高位搅进低位，异或做无进位的融合。

**乘法散列（Multiplicative Hashing）**。Knuth 给出的经典形式是
$$
h(k) = \big\lfloor m \cdot ((k \cdot A) \bmod 1) \big\rfloor
$$
其中 $A \in (0,1)$ 是一个无理数比例常数，常取与 $\sqrt{5}$ 有关的值 $A = (\sqrt{5}-1)/2 \approx 0.6180339887\ldots$，即黄金分割比的共轭。它与 2 的幂互质，使乘积的小数部分分布均匀。在计算机中 $A$ 写成 $s/2^w$（$w$ 为字长，$s$ 为奇数），$(k \cdot A) \bmod 1$ 等价于取乘积的高 $w$ 位中的小数部分，也就是丢掉低 $w$ 位、留下高位。这一点很重要：**乘法散列利用的是乘积高位，而不是像取模那样利用低位**。

**Fibonacci hashing**。当表大小 $m = 2^p$ 时，取 $A$ 对应的整数乘子为 $\lfloor 2^w / \varphi \rfloor$（$\varphi$ 为黄金比），则 `hash = (k * FIB) >> (w - p)` 用高 $p$ 位索引，对连续整数键分布极佳，是很多语言运行时对 identity hash 的做法。

**字符串混合：FNV / Murmur / xxHash**。FNV-1a 的骨架是「异或一字节、乘以素数」，极其紧凑。MurmurHash3 引入 32 位乘法、旋转移位、最终雪崩（`fmix32`），在质量和速度上都是工程默认选项。xxHash 进一步利用 SIMD 与多路累加，在大输入上吞吐接近内存带宽。它们共同点是：**短循环体、只用加减乘异或移位、结尾必须做一次全局混合**，否则小整数键会保留「乘积低位泄漏」。

**表大小与二次哈希**。若表大小是 2 的幂，`h & (m-1)` 只用低位，必须先做一次高位混入（Java 的 `h ^ (h >>> 16)`）。若表大小取质数且与步长互质，线性探测也能走遍全表。二者是同一问题的两面：**让最终索引比特来自哈希的高位混合结果**，而不是某个固定比特段。

## 三、形式化与数学基础

**均匀哈希假设**。理想情况下对任意 $x \ne y$，有
$$
\Pr[h(x) = h(y)] \approx \frac{1}{m}.
$$
这是简单均匀散列（Simple Uniform Hashing）假设，实际哈希无法达到完美，但好的设计使碰撞概率接近 $1/m$，从而链长期望长度为 $n/m = \alpha$（装载因子）。

**乘法散列的推导**。设 $k$ 均匀取自 $[0, 2^w)$，$A = s/2^w$ 为奇数 $s$ 形成的固定乘子。乘积 $kA$ 的小数部分 $(kA) \bmod 1$ 在 $[0,1)$ 上近似均匀（这是 $A$ 与 2 互质时的经典结论）。于是
$$
\mathbb{E}[\text{slot}] = \frac{m}{2}, \qquad
\Pr[h(k) = i] \approx \frac{1}{m}.
$$
Knuth 指出 $A = (\sqrt{5}-1)/2$ 在「用 2 的幂表、键呈算术序列」时表现最好，因为该常数的小数展开与二进制展开都足够「无理」，不易与 $2^p$ 产生共振。

**碰撞概率的量化**。若哈希近似均匀，$n$ 个键落入 $m$ 个桶，单个桶负载的期望与方差为
$$
\mathbb{E}[X_i] = \frac{n}{m}, \qquad
\operatorname{Var}(X_i) = \frac{n}{m}\left(1 - \frac{1}{m}\right).
$$
若哈希有偏，例如把键映到仅 $m/2$ 个有效桶，则有效装载因子翻倍，不成功查找期望探测数从约 $1/(1-\alpha)$ 恶化到 $1/(1-2\alpha)$，$\alpha=0.5$ 时从 2 变成发散。这解释了「分布不均直接毁掉常数时间」。

**雪崩的启发式度量**。对输入差分 $\delta$ 与输出差分 $\Delta$，好哈希应使 $\Pr[\Delta = d] \approx 2^{-w}$ 对所有非零 $d$。Murmur3 的 `fmix32`：
$$
h \mathrel{\oplus}= h \gg 16;\quad
h \mathrel{*}= 0x85ebca6b;\quad
h \mathrel{\oplus}= h \gg 13;\quad
h \mathrel{*}= 0xc2b2ae35;\quad
h \mathrel{\oplus}= h \gg 16
$$
两轮乘法+移位+异或，足以把低位信息打散到全 32 位，这是可测试的：翻转任一输入比特，输出汉明距离应集中在 $w/2$ 附近。

**Java HashMap 的扰动**。`h ^ (h >>> 16)` 把高 16 位混入低 16 位，使得 `h & (n-1)`（$n$ 为 2 的幂）同时受高位影响。扰动后单个桶命中概率近似均匀；不做扰动时，若键的哈希低位集中（例如大量偶数），偶数下标桶会显著拥挤。

## 四、代码实现

下面实现三种代表性哈希，并演示它们在哈希表中的表现差异。代码仅用标准库，可直接运行。

```python
"""哈希函数设计：FNV-1a、乘法散列、Murmur3 fmix 混合，以及简单哈希表对比。"""
from __future__ import annotations


# ---------- 1. FNV-1a（32 位） ----------
def fnv1a_32(data: bytes) -> int:
    h = 0x811C9DC5
    for b in data:
        h ^= b
        h = (h * 0x01000193) & 0xFFFFFFFF
    return h


# ---------- 2. 乘法散列（整数键 → [0, m)） ----------
def multiplicative_hash(k: int, m: int) -> int:
    """Knuth 乘法散列：A = (√5-1)/2 对应的 2^32 奇数乘子 0x9E3779B1。"""
    if m <= 0:
        raise ValueError("m must be positive")
    # 黄金分割共轭 * 2^32 取整（常用魔数）
    A = 0x9E3779B1
    product = (k * A) & 0xFFFFFFFF_FFFFFFFF  # 模拟 64 位乘积
    # 取乘积高位作为小数部分再乘 m（等价 floor(m * frac(kA)))
    frac_high = product >> 32
    return (frac_high * m) >> 32


# ---------- 3. MurmurHash3 32-bit 的核心混合 ----------
def fmix32(h: int) -> int:
    h &= 0xFFFFFFFF
    h ^= h >> 16
    h = (h * 0x85EBCA6B) & 0xFFFFFFFF
    h ^= h >> 13
    h = (h * 0xC2B2AE35) & 0xFFFFFFFF
    h ^= h >> 16
    return h


def murmur3_32(data: bytes, seed: int = 0) -> int:
    c1, c2 = 0xCC9E2D51, 0x1B873593
    h = seed & 0xFFFFFFFF
    length = len(data)
    nblocks = length // 4

    for i in range(nblocks):
        k = int.from_bytes(data[i * 4 : i * 4 + 4], "little")
        k = (k * c1) & 0xFFFFFFFF
        k = ((k << 15) | (k >> 17)) & 0xFFFFFFFF
        k = (k * c2) & 0xFFFFFFFF
        h ^= k
        h = ((h << 13) | (h >> 19)) & 0xFFFFFFFF
        h = (h * 5 + 0xE6546B64) & 0xFFFFFFFF

    tail = data[nblocks * 4 :]
    k1 = 0
    if len(tail) == 3:
        k1 ^= tail[2] << 16
    if len(tail) >= 2:
        k1 ^= tail[1] << 8
    if tail:
        k1 ^= tail[0]
        k1 = (k1 * c1) & 0xFFFFFFFF
        k1 = ((k1 << 15) | (k1 >> 17)) & 0xFFFFFFFF
        k1 = (k1 * c2) & 0xFFFFFFFF
        h ^= k1

    h ^= length
    return fmix32(h)


# ---------- 4. 用乘法散列驱动的整数哈希表 ----------
class IntHashTable:
    def __init__(self, capacity: int = 16):
        self.cap = 1 << (capacity - 1).bit_length()  # 取为 2 的幂
        self.slots = [None] * self.cap
        self.size = 0

    def _index(self, k: int) -> int:
        # 混入高位后再取低位，避免低位聚集
        mixed = (k * 0x9E3779B1) & 0xFFFFFFFF
        mixed ^= mixed >> 16
        return (mixed * self.cap) >> 32

    def put(self, k: int, v) -> None:
        i = self._index(k)
        for step in range(self.cap):
            j = (i + step) % self.cap
            slot = self.slots[j]
            if slot is None or slot[0] == "TOMB":
                self.slots[j] = (k, v)
                self.size += 1
                return
            if slot[0] == k:
                self.slots[j] = (k, v)
                return
        raise RuntimeError("table full")

    def get(self, k: int, default=None):
        i = self._index(k)
        for step in range(self.cap):
            j = (i + step) % self.cap
            slot = self.slots[j]
            if slot is None:
                return default
            if slot[0] == k:
                return slot[1]
        return default


def bucket_stats(hash_fn, keys, m: int = 16) -> dict:
    counts = [0] * m
    for k in keys:
        counts[hash_fn(k) % m] += 1
    nonzero = [c for c in counts if c]
    return {
        "empty": counts.count(0),
        "max": max(counts),
        "avg_nonzero": sum(nonzero) / len(nonzero) if nonzero else 0,
    }


if __name__ == "__main__":
    # 连续整数键：坏哈希（直接取低 4 位）vs 乘法散列
    keys = list(range(1000))
    bad = lambda k: k & 0xF
    good = lambda k: multiplicative_hash(k, 16)
    print("bad :", bucket_stats(bad, keys, 16))
    print("good:", bucket_stats(good, keys, 16))

    # 字符串键：FNV 与 Murmur 雪崩性粗测
    a = murmur3_32(b"user:1001")
    b = murmur3_32(b"user:1002")
    print(f"murmur user:1001={a:08x} 1002={b:08x} hamming={bin(a ^ b).count('1')}")
    print(f"fnv1a  hello={fnv1a_32(b'hello'):08x}")
```

运行后可以看到：`bad` 里 16 个桶中一半是空的、另一半严重拥挤；`good` 几乎每桶都有 60 多个键、无空桶。Murmur 相邻键的输出汉明距离约在 8~16 之间，接近理想雪崩。

## 五、与其他技术对比

| 维度 | 取模 / 直接取低位 | 乘法散列 | FNV-1a | Murmur3 / xxHash | SHA-256 |
|------|------------------|----------|--------|------------------|---------|
| 速度 | 极快 | 极快 | 很快 | 很快（xxHash 可 SIMD） | 慢 5~20 倍 |
| 分布质量 | 键差时很差 | 连续整数优 | 字符串尚可 | 优秀 | 密码学级 |
| 雪崩性 | 无 | 中 | 中 | 强 | 极强 |
| 适用场景 | 表大小为质数且键随机 | 整数键、2 的幂表 | 短字符串、哈希表 | 通用非加密 | 完整性校验、防碰撞攻击 |
| 显著弱点 | 低位聚集 | 不适合变长键 | 长输入质量下降 | 实现稍复杂 | 计算成本高 |

与加密哈希相比：非加密哈希不承诺抗碰撞攻击，恶意构造大量碰撞键（HashDoS）可以打垮服务，因此对外部输入做哈希表键时，SipHash（Python 3 字符串即用它）或加密哈希更安全。与简单取模相比，乘法/混合散列能在表大小为 2 的幂时仍保持均匀，从而索引用位与即可，缓存友好。

## 六、常见误区

**用可变对象做键**。键被修改后哈希值变化，再查找会找不到甚至重复插入。Python 的 list 不能做 dict 键，但自定义 `__hash__` 若依赖可变字段就会踩坑。后果是极难排查的「数据丢了一条」。

**表大小为 2 的幂却只用低比特**。`h & (m-1)` 若 `h` 低位不随机，冲突激增。正确做法是像 Java 那样先 `h ^ (h >>> 16)`，或用乘法散列取高位。后果是装载因子 0.5 时性能仍像 0.9。

**把「字符串求和」当哈希**。对 anagram 类键完全冲突，哈希表退化为 $O(n)$。后果是压测通过、上线后热点键把单桶链表拉到几千。

**忽略最终混合**。自己写的哈希只做移位异或、结尾不乘不旋，小整数键的输出保留大量线性结构，相邻键撞在一起。雪崩测试能立刻暴露。

**误以为哈希冲突会自动被「扩容」救回**。扩容只降低装载因子，若哈希本身聚集（把 $n$ 个键压进 $m/10$ 个桶），扩容十倍仍聚集。根因是哈希函数，不是表大小。

## 七、与开源书/权威来源对应

- **Knuth, TAOCP Vol.3, §6.4**：乘法散列、$A=(\sqrt{5}-1)/2$ 的经典推导与冲突统计。
- **CLRS《Introduction to Algorithms》Ch.11.3–11.4**：散列函数设计、除法/乘法散列、均匀散列假设。
- **MurmurHash（Austin Appleby）**：`fmix32` 最终混合设计，广泛用于 Guava、Redis 等。
- **FNV 算法说明（Fowler–Noll–Vo）**：`hash = (hash XOR byte) * prime` 的极简字符串哈希。

## 八、面试题

**1. 为什么 HashMap 要 `h ^ (h >>> 16)`？**
参考答案：表大小为 2 的幂时下标只用低 $\log n$ 位；原哈希高位信息被丢掉会导致低位相近的键聚集。右移 16 异或把高位混入低位，使索引同时依赖全部比特，分布更均匀。若表大小是质数，则此扰动不是必须的，但仍有益。

**2. 给定十亿个 64 位整数做分片，如何选哈希？**
参考答案：优先用乘法散列（或 murmur/xxHash 的 64 位变体）取高位，避免对 2 的幂分片数直接取模。需做雪崩测试；若输入可能被恶意构造，考虑带密钥的 SipHash。

**3. 如何测试一个哈希函数的好坏？**
参考答案：(a) 分布卡方检验或桶直方图；(b) 雪崩测试——翻转单比特看输出汉明距离；(c) 连续整数、anagram、前缀相同等难例；(d) 吞吐基准。Murmur 在这些测试上稳定优于求和哈希。

**4. 解释乘法散列为何用高比特而不是低比特。**
参考答案：$(kA) \bmod 1$ 对应乘积的高位；$A$ 取与 2 互质的常数时，小数部分均匀。取模 $2^p$ 只看低 $p$ 位，对算术序列键会产生周期性模式。故乘法散列天然适合 2 的幂表。

## 九、演进与趋势

**SIMD 与多路并行哈希**。xxHash3、wyhash、AHash 在现代 CPU 上单核吞吐可达数 GB/s，把四个 lane 的部分积同时累加，利用乱序与向量寄存器。

**硬件指令辅助**。AES-NI 指令集可做极快的密码学级混合（如 ahash 的 AES 模式），Google 的 Abseil 也探索过硬件加速。

**对抗 HashDoS**。Web 框架对外部 key 默认 SipHash 或随机种子哈希，使攻击者无法预先制造碰撞。Python 3 字符串哈希每次进程随机化 seed。

**领域定制**。一致性哈希环要求输出在大空间均匀（常用 MD5/SHA-1 截断或 64 位 murmur）；布隆过滤器要求 $k$ 个独立或双哈希独立的索引；Bloom 的「double hashing」技巧 $h_i = h_1 + i\cdot h_2$ 已被证明在实践中足够。

**测试基建**。SMHasher、PractRand 等套件成为新哈希函数的准入门槛，好的设计必须公开雪崩与碰撞统计。

## 十、小结

哈希函数设计围绕「确定、均匀、高效」三条准则：用乘法散列利用高比特、用混合轮（移位/乘法/异或）制造雪崩、用最终 `fmix` 收束分布，并在表大小取 2 的幂时通过高位扰动补救。与加密哈希相比，非加密哈希在质量足够好的前提下快一个数量级，是哈希表与布隆过滤器的默认引擎；但在面对不可信输入时仍需带密钥哈希。掌握雪崩、乘法常数与二次扰动，比背诵某个具体函数名更有价值。
