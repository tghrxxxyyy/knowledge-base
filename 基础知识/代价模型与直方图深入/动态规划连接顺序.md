# 动态规划连接顺序

> 对应 SQL Server / PostgreSQL 优化器的 join enumeration 与 System R 经典算法，参考 Garcia-Molina 第14章。

## 一、背景与挑战
N 表连接的顺序与算法组合爆炸（$O(2^N)$ 子集枚举）。优化器需在可接受时间内找出（近）最优连接顺序，动态规划是关系库经典解法。

## 二、核心原理
自底向上枚举关系子集：对每种子集计算最优子计划并记录代价（memoization）。对两子集合并时尝试嵌套循环/哈希/归并。PostgreSQL 用 `join_collapse_limit` 控制搜索深度以防爆炸。

## 三、形式化与数学基础
设 $DP(S)$ 为子集 $S$ 的最优代价，则：
$$ DP(S) = \min_{S=A \cup B} \big( DP(A) + DP(B) + cost(A \Join B) \big) $$
总复杂度约 $O(3^N)$ 子集对，配合剪枝实用化。

## 四、代码实现
```sql
-- 限制连接顺序搜索
SET join_collapse_limit = 8;
SET from_collapse_limit = 8;
EXPLAIN SELECT ... FROM a JOIN b ON ... JOIN c ON ...;
```

## 五、与其他技术对比
MySQL 早先采用贪婪启发式（有限动态规划），8.0 增强代价模型。商业库（SQL Server）用 Cascades 框架（记忆化 + 规则转换）更高效。Oracle 亦用类似 Volcano/Cascades。

## 六、常见误区
认为优化器总能找到最优——表多时受 `join_collapse_limit` 限制退化为启发式。认为加 JOIN 提示永远好——可能锁死本可更优的顺序。

## 七、与开源书/权威来源对应
Garcia-Molina 14.3「Join Order Optimization」；System R 优化器论文（Selinger 1979）。

## 八、面试题
问：为什么多表 JOIN 可能计划不优？答：搜索空间爆炸，优化器限制深度用启发式，可能错过最优。

## 九、演进与趋势
Cascades 风格优化器（如 Apache Calcite、CockroachDB、TiDB）成为开源新标准，支持更灵活的规则与并行搜索。

## 十、小结
动态规划以 memoization 枚举连接顺序，是优化器在爆炸空间中求优的基石。
