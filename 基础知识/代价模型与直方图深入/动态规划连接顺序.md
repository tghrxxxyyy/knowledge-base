# 动态规划连接顺序

> 对应 Selinger 1979 System R 优化器、Graefe 1993 Volcano/Cascades 与 Garcia-Molina《Database Systems: The Complete Book》查询优化章节。

## 一、背景与挑战
多表连接的顺序与算法组合数量随表数爆炸增长。$N$ 张表的连接树形态、左右交换、连接算法（嵌套循环、哈希、归并）相乘，空间远超可穷举范围。
优化器必须在可接受时间内找出（近）最优计划，否则规划本身就成了瓶颈。动态规划（DP）是关系数据库最经典的解法。
它的核心思想是「最优子结构 + 记忆化」：一个最优计划由最优子计划拼成，子问题结果可复用，避免重复计算。
核心挑战在于搜索空间仍然巨大：仅子集枚举就有 $2^N$ 量级，加上连接算法与物理属性（有序性、分布），实用化必须依赖剪枝与启发式。
因此现代优化器很少做「完全 DP」，而是用 DP 的变体——Cascades 风格的记忆化搜索、或对 join 数量设上限后退化为启发式。

## 二、核心原理
自底向上枚举关系子集：先求所有单表的访问路径代价，再求所有二表子集的最优连接，逐步扩展到全集。
对每个子集 $S$，优化器尝试所有二分 $S = A \cup B$，比较 $DP(A) + DP(B) + cost(A \Join B)$，保留最小者，这就是 DP 的状态转移。
记忆化保证每个子集只被完整求解一次；子集结果在后续更大子集的枚举中反复复用，是指数级节省的来源。
物理属性（如输出是否按某列有序）会被纳入状态，因为有序性影响上层归并连接与排序消除，属于「有趣序」优化。
PostgreSQL 用 `join_collapse_limit` 与 `from_collapse_limit` 限制显式 JOIN 的重排深度，超过阈值后退化为按书写顺序或有限搜索，防止规划时间失控。

## 三、形式化与数学基础
设 $DP(S)$ 为连接子集 $S$ 的最优代价，$cost(A \Join B)$ 为把两个子计划连接起来的代价，则：

$$ DP(S) = \min_{S = A \cup B,\; A \cap B = \emptyset} \Big( DP(A) + DP(B) + cost(A \Join B) \Big) $$

基例为单表子集 $DP(\{R_i\})$，取该表所有可用访问路径的最小代价。枚举所有二分对的复杂度约为：

$$ \sum_{S} \sum_{A \subset S} 1 = 3^{N} - 2^{N+1} + 1 = O(3^{N}) $$

其中 $3^N$ 来自「每个元素属于 $A$、$B$、或不属于 $S$」的三分计数。加上物理属性维度 $P$（如有序性集合），状态数为 $O(2^N \cdot |P|)$。
优化器最终取 $DP(\text{全集})$ 对应的计划。若考虑连接树形状（左深树、稠密树、布什树），搜索空间进一步扩大，故实用系统常限制为左深树以降低复杂度。
System R 的经典做法正是动态规划结合左深树与有趣的序，用较少状态换取接近最优的结果。

## 四、代码实现
```sql
-- 控制连接顺序搜索规模（PostgreSQL）
SHOW join_collapse_limit;   -- 默认 8
SHOW from_collapse_limit;   -- 默认 8
SET join_collapse_limit = 8;

-- 观察多表连接的计划与连接树形状
EXPLAIN (COSTS ON)
SELECT *
FROM a
JOIN b ON a.id = b.a_id
JOIN c ON b.id = c.b_id
JOIN d ON c.id = d.c_id
WHERE a.kind = 'x';

-- 显式指定连接顺序（等价于人为锁定搜索空间）
SET join_collapse_limit = 1;
EXPLAIN SELECT * FROM a JOIN b ON a.id = b.a_id JOIN c ON b.id = c.b_id;

-- 对比：放开搜索 vs 锁定顺序，观察代价差异
```

## 五、与其他技术对比
| 优化器风格 | 搜索方式 | 代表系统 | 特点 |
|---|---|---|---|
| System R 式 DP | 自底向上子集枚举 | 早期 DB2、PostgreSQL | 左深树、有趣序 |
| 贪心启发式 | 逐步选最小代价连接 | MySQL 早期 | 快但可能次优 |
| Cascades/Volcano | 记忆化 + 规则变换 | SQL Server、Calcite、TiDB | 灵活、支持稠密树 |
| 遗传/随机搜索 | 随机探索 | 部分研究原型 | 可控时间、无最优保证 |
| 学习型 | 模型预测顺序 | 研究阶段 | 需训练、泛化待验证 |

## 六、常见误区
- 认为优化器总能找到最优：表多时受上限约束退化为启发式，最优可能被跳过。
- 认为加 JOIN 提示总是更好：提示会锁定顺序，可能错失原本更优的重排。
- 忽视物理属性：只优化代价不看有序性，可能漏掉可消除排序的计划。
- 把 $O(3^N)$ 当成实际开销：剪枝与上限让实际远小于理论最坏值，但复杂度趋势仍成立。
- 认为左深树一定够用：某些星型/雪花模型下稠密树更优，需 Cascades 类框架支持。

## 八、面试题
1. 问：为什么多表 JOIN 可能计划不优？
   答：搜索空间爆炸，优化器限制深度改用启发式，可能错过最优顺序。
2. 问：DP 的记忆化节省从何而来？
   答：每个子集只求解一次，其最优子计划被更大子集复用，避免重复枚举。
3. 问：$O(3^N)$ 怎么来的？
   答：枚举子集的每个元素有「属 A、属 B、不在 S」三种归属，构成三分计数。
4. 问：物理属性为何要入状态？
   答：有序性影响上层归并连接与排序消除，只有带属性才能比较完整计划优劣。
5. 问：`join_collapse_limit` 的作用？
   答：限制重排深度，超过阈值后退化为有限搜索或书写顺序，控制规划时间。

## 九、演进与趋势
- Cascades 风格优化器（Apache Calcite、CockroachDB、TiDB 等）成为开源新标准，支持更灵活规则与并行搜索。
- 针对大规模连接的启发式与随机搜索被重新引入，以控制规划时间。
- 学习型连接顺序选择在研究中探索，尚未全面替代经典 DP。
- 具体实现与默认配置以各系统官方最新文档为准。

## 十、小结
动态规划以记忆化枚举连接子集，是优化器在爆炸空间中求优的基石：最优子结构与复用使其可行，物理属性让其贴近执行现实。但搜索并非无限，深度上限与启发式意味着「最优」只是近似。理解 DP 的复杂度与边界，才能解释计划为何不总是最优。
