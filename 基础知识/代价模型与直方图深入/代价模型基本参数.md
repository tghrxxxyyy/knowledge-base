# 代价模型基本参数

> 对应 PostgreSQL 文档「Planner Cost Constants」与 MySQL 优化器代价参数，参考 Garcia-Molina 第12章。

## 一、背景与挑战
优化器用统一的代价单位比较不同计划。代价模型依赖一组可调参数（顺序页读、随机页读、CPU 行处理等），参数失真会使模型偏离真实硬件。

## 二、核心原理
PostgreSQL 把代价表示为「磁盘页读取 + CPU 处理」的混合单位，关键参数：`seq_page_cost`（顺序页读，默认1）、`random_page_cost`（随机页读，默认4，SSD 应调低）、`cpu_tuple_cost`、`cpu_index_tuple_cost`、`cpu_operator_cost`。总代价为各项加权和。

## 三、形式化与数学基础
计划代价：
$$ C = N_{seq} \cdot seq\_page\_cost + N_{rand} \cdot random\_page\_cost + N_{rows} \cdot cpu\_tuple\_cost + \dots $$
优化器在所有候选计划中取 $\min C$。

## 四、代码实现
```sql
-- PostgreSQL 调整代价参数
SET random_page_cost = 1.1;   -- SSD 场景
SET seq_page_cost = 1.0;
SHOW enable_indexscan;
```

## 五、与其他技术对比
MySQL 代价模型参数较隐蔽（如 `optimizer_cost_model`，8.0 引入基于规则的 cost model），调整粒度不如 PostgreSQL 透明。商业库多提供图形化代价因子调优。

## 六、常见误区
认为默认代价参数适合所有硬件——HDD 与 SSD 下 `random_page_cost` 应显著不同。认为代价单位是秒——它只是相对比较量纲。

## 七、与开源书/权威来源对应
PostgreSQL 文档「Planner Cost Constants」；Garcia-Molina 12.2「Cost Models」。

## 八、面试题
问：SSD 为何要调低 random_page_cost？答：随机与顺序 IO 差距缩小，原默认值夸大了索引随机读代价。

## 九、演进与趋势
基于硬件实测的自动代价标定（calibration）取代手工调参，是云数据库方向。

## 十、小结
代价模型的参数必须匹配真实硬件，否则「最优」计划在现实中并不优。
