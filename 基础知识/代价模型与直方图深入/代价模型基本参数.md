# 代价模型基本参数

> 对应 PostgreSQL「Planner Cost Constants」、Garcia-Molina《Database Systems: The Complete Book》代价模型章节与 MySQL 优化器代价参数。

## 一、背景与挑战
优化器要在众多候选计划中选一个「最优」的，就必须有一把统一的尺子。代价模型就是这把尺子：它把不同计划折算成可比较的数值。
尺子的刻度由一组参数决定——读一个顺序页多少代价、随机读一个页多少代价、处理一行 CPU 多少代价。参数失真，模型就会偏离真实硬件。
最典型的例子是 `random_page_cost`：它在机械硬盘时代被设为顺序读的若干倍，但 SSD 上随机与顺序差距大幅缩小，沿用旧值会让优化器过度回避索引。
核心挑战是参数与硬件、工作负载强相关，默认值只是折中。云环境、SSD、超大内存缓存下，默认参数往往不再合适。
理解这些参数，才能解释「为什么优化器不选索引」「为什么同样的 SQL 在另一台机器上计划不同」，也才能有依据地干预。

## 二、核心原理
PostgreSQL 把总代价建模为「磁盘页读取代价 + CPU 处理代价」的加权和，所有项共享一个无量纲单位，便于比较而非表示时间。
关键参数包括：`seq_page_cost`（顺序读一页）、`random_page_cost`（随机读一页）、`cpu_tuple_cost`（处理一行的 CPU）、`cpu_index_tuple_cost`（处理一条索引项）、`cpu_operator_cost`（执行一次操作符/函数的 CPU）。
此外还有 `effective_cache_size`，它告诉规划器操作系统与共享缓冲合计可缓存多少页，间接影响索引扫描是否划算。
参数并不独立：`random_page_cost` 相对 `seq_page_cost` 的比值，直接决定「顺序扫」与「索引扫+回表」的取舍。
MySQL 的代价模型引入较晚，早期参数较隐蔽，8.0 后有专门的代价模型表可调；商业数据库多提供图形化或配置化的代价因子。

## 三、形式化与数学基础
一个计划的代价可写成各项的线性组合：

$$ C = N_{seq} \cdot c_{seq} + N_{rand} \cdot c_{rand} + N_{rows} \cdot c_{tuple} + N_{idx} \cdot c_{idx} + N_{op} \cdot c_{op} $$

其中 $c_{seq}, c_{rand}, c_{tuple}, c_{idx}, c_{op}$ 分别对应上述参数。优化器在所有候选计划中取最小代价者：

$$ \pi^{*} = \arg\min_{\pi \in \Pi} C(\pi) $$

注意 $C$ 是无量纲比较量，不是秒。参数校准的核心是让比值贴近硬件实况。例如 SSD 上随机与顺序差距缩小，理想校准应使：

$$ \frac{c_{rand}}{c_{seq}} \to 1^{+} $$

而传统机械盘下该比值常被设为约 4 甚至更高。另一个关键量是缓存命中下的有效随机读代价：

$$ c_{rand}^{\text{eff}} = h \cdot c_{seq} + (1-h) \cdot c_{rand} $$

$h$ 为命中率，命中时随机读近似顺序读代价，因此 `effective_cache_size` 越大，索引回表的有效代价越低。

## 四、代码实现
```sql
-- PostgreSQL：查看与调整代价参数
SHOW seq_page_cost;        -- 默认 1.0
SHOW random_page_cost;     -- 默认 4.0，SSD 建议调低
SHOW cpu_tuple_cost;       -- 默认 0.01
SHOW effective_cache_size; -- 依内存设置

-- 会话级调整（SSD 场景）
SET random_page_cost = 1.1;
SET seq_page_cost = 1.0;
SET effective_cache_size = '8GB';

-- 对比不同参数下的计划
EXPLAIN (COSTS ON)
SELECT * FROM t WHERE indexed_col BETWEEN 1 AND 1000;

-- 观察索引是否被选用，定位参数影响
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM t WHERE indexed_col = 42;
```

## 五、与其他技术对比
| 维度 | PostgreSQL | MySQL 8.0 | 商业数据库 |

| 校准方式 | 手工/脚本 | 手工 | 厂商适配 |

## 六、常见误区
- 认为默认参数适配所有硬件：HDD 与 SSD 下 `random_page_cost` 应显著不同。
- 把代价单位当秒：它是相对比较量纲，跨查询不可直接解读为时间。
- 只调一个参数：参数相互影响，需连同 `effective_cache_size`、`seq_page_cost` 一起校准。
- 忽略缓存：内存充足时索引回表并不昂贵，过度悲观会错失好计划。
- 认为调参数能根治慢查询：统计不准、谓词写法差时，参数调优只是治标。

## 八、面试题
1. 问：SSD 为何要调低 `random_page_cost`？
   答：SSD 随机与顺序读差距缩小，原默认值夸大了索引随机读代价，调低后优化器更愿用索引。
2. 问：`effective_cache_size` 的作用？
   答：告诉规划器可用缓存页数，影响索引回表的有效代价，进而影响扫描方式选择。
3. 问：代价单位是时间吗？
   答：不是，是无量纲相对量，只用于计划间比较，不能直接当作耗时。
4. 问：为什么调了参数计划仍不优？
   答：统计过期、列相关、谓词不可索引、搜索空间受限等会掩盖参数效果。
5. 问：CPU 代价参数为何存在？
   答：CPU 处理大量行时不可忽略，`cpu_tuple_cost` 让计划考虑行数带来的计算开销。

## 九、演进与趋势
- 基于硬件实测的自动代价标定（calibration）逐步替代手工调参，尤其在云数据库。
- 学习型代价模型尝试端到端预测计划代价，减少对手工参数的依赖。
- 硬件异构（NVMe、ZNS、分级存储）推动代价模型纳入更多维度。
- 具体参数与推荐值以各数据库官方最新文档为准。

## 十、小结
代价模型的参数必须匹配真实硬件与缓存状况，否则「最优」计划在现实中并不优。`seq/random_page_cost`、`cpu_*_cost` 与 `effective_cache_size` 共同决定扫描与连接选择，调参应成组进行，并与统计质量、谓词写法一起诊断。
