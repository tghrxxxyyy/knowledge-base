# 直方图在估算中应用

> 对应 Ioannidis 2003「The History of Histograms」、PostgreSQL histogram_bounds 与 MySQL 8.0 直方图。

## 一、背景与挑战
统计信息是优化器估计选择性的原料，而直方图是其中最重要的结构。有了直方图，优化器还要能在具体谓词上把它转成数值。
这一步是「统计」与「计划」之间的最后一公里：范围谓词、等值谓词、IN 列表、跨列条件，各自需要不同的桶定位与插值逻辑。
没有直方图时，优化器对范围查询常假设固定比例（历史实现中曾用 1/3 之类的硬编码），对倾斜数据误差可达数量级。
核心挑战在于：真实分布形态复杂，有限桶数无法完全刻画；采样本身带来误差；桶内如何插值只是启发式，可能高估或低估。
理解直方图如何被「消费」，才能解释为什么同一查询在不同统计状态下计划不同，也才能判断 ANALYZE 是否值得。

## 二、核心原理
直方图把列值域划分为若干桶。最常见的是等高直方图（equi-depth）：每个桶尽量包含相同行数，桶边界记录在元数据中。
等值谓词 $col = v$ 的估计：先定位 $v$ 落入哪个桶，用桶内平均不同值数（distinct）估算单值占比；若 $v$ 出现在 MCV（最常用值）列表则直接取精确频率。
范围谓词 $col \in [lo, hi]$ 的估计：累加完全覆盖桶的行数，两端不足整桶的部分按线性插值折算。
这依赖一个关键假设——桶内值近似均匀分布。真实数据在桶内可能高度集中，插值因此产生偏差。
PostgreSQL 在 `pg_statistic`/`pg_stats` 中暴露 `histogram_bounds` 与 MCV，MySQL 8.0 通过 `information_schema.COLUMN_STATISTICS` 提供直方图，二者思路一致。

## 三、形式化与数学基础
设总行数为 $N$，列上收集了 $B$ 个等高桶，桶边界为 $b_0 < b_1 < \dots < b_B$。桶内线性插值假设下，值 $v \in [b_{i-1}, b_i)$ 的等值选择率可近似为：

$$ \mathrm{sel}(v) \approx \frac{1}{N} \cdot \frac{\text{bucket\_rows}}{\text{distinct}_{\text{bucket}}} = \frac{1}{N} \cdot \frac{N/B}{d_{\text{bucket}}} $$

其中 $d_{\text{bucket}}$ 为该桶内估计的不同值数。范围 $[lo, hi]$ 的选择率，若跨越 $m$ 个完整桶并含两端部分桶：

$$ \mathrm{sel}([lo,hi]) \approx \frac{m \cdot (N/B)}{N} + \frac{N}{B} \cdot \frac{b_i - lo}{b_i - b_{i-1}} + \frac{N}{B} \cdot \frac{hi - b_j}{b_{j+1} - b_j} $$

估计基数即 $N \cdot \mathrm{sel}$。注意所有公式都建立在「桶内均匀」假设上；当桶内集中度高时，插值会系统性偏离真实值。

## 四、代码实现
```sql
-- PostgreSQL：查看直方图边界与 MCV
SELECT tablename, attname, n_distinct,
       most_common_vals, most_common_freqs, histogram_bounds
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'amount';

-- 触发统计收集，改变直方图精度
ANALYZE orders;
ALTER TABLE orders ALTER COLUMN amount SET STATISTICS 500;

-- MySQL 8.0：查看列直方图
SELECT SCHEMA_NAME, TABLE_NAME, COLUMN_NAME, HISTOGRAM->>'$."buckets"'
FROM information_schema.COLUMN_STATISTICS
WHERE TABLE_NAME = 'orders';

-- 验证估计是否贴合实际
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
```

## 五、与其他技术对比
| 结构 | 擅长 | 局限 | 典型实现 |
|---|---|---|---|
| 等高直方图 | 范围谓词 | 桶内均匀假设 | PostgreSQL 默认 |
| 等宽直方图 | 实现简单 | 倾斜数据桶数浪费 | MySQL 部分场景 |
| MCV 列表 | 热点值精确 | 长尾无法覆盖 | PostgreSQL、MySQL |
| 多变量统计 | 列相关 | 组合爆炸 | PostgreSQL extended stats |
| 采样近似 | 任意谓词 | 方差大、需重采样 | 部分云数据库 |

## 六、常见误区
- 认为直方图能处理所有谓词：跨列相关、函数包裹列（如 `WHERE YEAR(d)=2024`）仍难估计。
- 认为桶越多越准：边际收益递减，且增加采样误差、ANALYZE 时间与元数据存储。
- 忽略 MCV 与直方图的分工：热点值走 MCV 才精确，仅靠直方图会低估高频值。
- 忘了桶内均匀假设：数据高度集中时插值误差可能很大。
- 认为统计一成不变：数据持续变化，过期统计比没有统计更危险。
- 把直方图当成精确分布：它只是分桶近似，桶内真实形态未知，估计必然带误差。
- 忽视采样比例：大表统计基于样本，样本越小方差越大，稀有值越容易被漏掉。

## 八、面试题
1. 问：范围查询如何用直方图估算？
   答：定位两端落在哪些桶，完整桶按行数累加，两端按桶内线性插值折算占比。
2. 问：等值查询为何要用 MCV？
   答：热点值频率远超均匀假设，MCV 给出精确频率，避免直方图低估。
3. 问：桶越多越好吗？
   答：不是，边际精度提升有限，同时增加采样误差与维护成本。
4. 问：直方图在什么情况下失效？
   答：列相关、函数谓词、桶内强集中、统计过期时都会明显偏差。
5. 问：如何验证估计质量？
   答：用 `EXPLAIN ANALYZE` 对比估计行数与实际行数，偏差大则更新统计或调整策略。

## 九、演进与趋势
- 与 MCV 结合处理长尾，与扩展统计（多列、表达式）结合处理相关性，提升复杂谓词下的鲁棒性。
- 学习型基数估计用模型替代直方图，在部分基准上更准但可解释性与成本仍有争议。
- 自动统计管理（按变更率触发采样、增量维护）成为云数据库标配。
- 具体实现与参数以官方最新文档为准。

## 十、小结
直方图把分布知识转化为选择性数值，是范围与倾斜估计精确化的关键输入。它依赖桶内均匀假设，需要 MCV 补热点、扩展统计补相关，并通过 ANALYZE 保持新鲜。理解其消费逻辑，才能诊断「为何优化器估错行数」。
