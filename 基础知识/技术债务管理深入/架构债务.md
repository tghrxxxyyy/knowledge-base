# 架构债务

> 对应 Martin《Clean Architecture》稳定抽象原则（SAP）与「Architecture Debt」研究；参考 CS-Notes（CyC2018）。

## 一、背景与挑战

架构级缺陷是技术债务中代价最高的一类：错误的模块边界、循环依赖、共享内核、层违反（上层反向依赖下层）等，会系统性地拖慢全团队的吞吐，且难以局部重构——改动一处引发多处连锁破坏。其隐蔽性尤其危险：代码级 lint 无法发现架构异味，团队往往直到「改不动、加功能必出 bug」时才意识到。挑战在于架构债务需要显式决策（ADR）与跨团队共识才能偿还，成本与政治阻力都远高于代码级清理。

## 二、核心原理

架构债务的典型表现：

1. 循环依赖：模块 A→B→A，破坏可独立部署性与测试隔离。
2. 层违反（Layer Violation）：表示层直接访问数据层，绕过敏捷分层。
3. 缺失边界 / 大泥球（Big Ball of Mud）：无清晰模块职责，改动牵一发动全身。
4. 过度耦合的共享内核：公共库承载隐式契约，任何修改都成全局风险。
5. 抽象错配：本应稳定的核心过度依赖易变细节。

识别手段包括依赖矩阵、抽象度/稳定度分析（Martin 指标）与架构适应度函数（在 CI 中持续校验依赖约束）。

## 三、形式化与数学基础（含 LaTeX）

模块稳定度（Stability）$S$ 定义为外向依赖占比：

$$
S=\frac{C_e}{C_a+C_e}
$$

其中 $C_e$ 为外向依赖数（efferent），$C_a$ 为内向依赖数（afferent）。$S\to1$ 表示高度依赖他人（难改），$S\to0$ 表示被大量依赖（应稳定）。

稳定抽象原则（Stable Abstractions Principle, SAP）要求：

$$
S + A \approx 1
$$

$A$ 为抽象度（抽象类型 / 总类型数）。稳定模块应高抽象（可扩展接口），不稳定模块可低抽象。偏离 $(S+A\not\approx1)$ 即架构异味：稳定却具体（难以扩展）、抽象却不稳定（依赖动荡）。

循环依赖使部分模块的 $S$ 定义退化或不可计算，直接判定为债务。

## 四、代码实现

```text
# 依赖分析示例（结构示意）
moduleA -> moduleB
moduleB -> moduleA   # 循环依赖：架构债务

# 引入抽象打破循环
abstractB (interface)   # 由 moduleA 依赖，moduleB 实现
moduleA -> abstractB
moduleB -> abstractB    # 环被打破，依赖单向
```

```python
# 稳定度计算（结构示意）
def stability(afferent, efferent):
    total = afferent + efferent
    return efferent / total if total else 0.0
```

## 五、与其他技术对比

- 与代码债务（局部坏味道）相比：架构债务影响面广、修复成本高、需跨团队决策（ADR）。
- 与测试/文档债务相比：架构债是结构性根因，其他债务常是其症状。
- 识别工具差异：代码债靠 linter/复杂度，架构债靠依赖图与 SAP 指标，不能互相替代。

## 六、常见误区

- 「用代码 lint 替代架构审视」：lint 看不到跨模块循环依赖。
- 「放任共享库成隐式大泥球」：共享内核耦合一切，演进停滞。
- 「为解耦而过度抽象」：抽象却不稳定（SAP 偏离）反而增加债务。
- 「架构债务只能大重写」：多数可用抽象/接口增量解耦，无需推倒重来。

## 九、演进与趋势

架构适应度函数（Architectural Fitness Functions）把依赖约束、层规则写进 CI 持续校验，使架构债务在引入时即被阻断；结合依赖图可视化与「架构决策记录（ADR）」治理，把架构健康纳入工程效能仪表盘。

此外，依赖图应定期快照对比，识别「稳定度漂移」——某模块悄然变重或新出现循环依赖时能即时告警。架构债务的治理核心不是一次性重构，而是让坏结构在合入前就被适应度函数挡下。

## 十、小结

架构债务是最贵、最隐蔽的技术债务，表现为循环依赖、层违反、边界缺失等结构性缺陷。其识别依赖依赖矩阵与 Martin 的稳定抽象原则（$S+A\approx1$），偿还需 ADR 与增量解耦，并以《Clean Architecture》为权威基准，而非仅靠代码级清理。
