# 取舍与治理

> 对应 McConnell《Managing Technical Debt》、Martin 债务象限与精益权衡分析（Lean Trade-off）；参考 CS-Notes（CyC2018）。

## 一、背景与挑战

技术债务不是单纯的工程问题，而是业务与技术的联合决策：还债要占用交付产能，不还则利息侵蚀未来速度，二者永远冲突。缺乏治理机制时，债务在「没人负责」的隐形状态中累积，直到事故爆发才被看到；而治理若走向极端（一切需审批、工具自动裁决），又会僵化创新、催生绕过。挑战在于：债务的真实成本（利息）难以精确计量，且「谁该为债务负责」常在业务与技术之间踢皮球。

治理的目标，是把债务从「工程师的良心」变成「组织可对话、可决策、可追责」的显式资产。

## 二、核心原理

健康的债务治理包含四个支柱：

1. 透明（可见）：用看板/报表持续展示债务存量、分布与趋势，建立业务与技术共同的语言。
2. 决策（共担）：明确「谁在何时、为何承担某项债务」，由技术负责人与产品共同签字，而非技术单方面背锅。
3. 上限（阈值）：设定债务比率等硬上限，超线触发强制复盘与排期，防止无声失控。
4. 复盘（归因）：定期回顾债务如何产生、利息是否如预期，把经验沉淀进设计准则。

治理强调「有意的债务」可管理，「无意的债务」才危险——故要区分并分别对待。

## 三、形式化与数学基础（含 LaTeX）

候选还债项按成本收益比排序：

$$
R_j=\frac{\text{NPV}\big(\text{节省}_j\big)}{C_{\text{pay},j}}
$$

其中 $\text{NPV}$ 为未来利息节省的净现值，$C_{\text{pay}}$ 为偿还成本。仅当

$$
R_j>R_{\min}
$$

才进入排期；对整体债务比率设上限：

$$
\text{TDR}=\frac{\text{RemediationCost}}{\text{DevelopmentCost}}\le T_{\max}
$$

一旦 $\text{TDR}>T_{\max}$，触发强制治理会议与冻结新功能（或划拨专项还债预算）。该机制把定性争论转化为可计算的阈值决策。

## 四、代码实现

```text
# 治理策略配置（结构示意）
governance_policy:
  debt_ratio_limit: 0.05          # TDR 硬上限 5%
  review_if_exceed: true           # 超线触发复盘
  owner: tech-lead + pm            # 业务技术共担
  repayment_budget_pct: 0.2        # 每迭代还债工时占比
  intentional_debt_must_have: [owner, reason, due_date]
```

```python
# 治理决策（结构示意）
def should_repay(item, tdr, tdr_max=0.05, r_min=1.0):
    if item["intentional"] and not item.get("owner"):
        return False               # 无意且无人负责：必须治理
    if tdr > tdr_max:
        return True                # 超上限强制还
    return item["npv_saving"] / item["cost"] > r_min
```

## 五、与其他技术对比

- 与「技术独裁」（仅工程师决定）相比：共治让业务理解代价，避免技术闭门造车。
- 与「完全自由」（无约束）相比：设上限防失控，且让债务可追责。
- 与「纯工具自动治理」相比：工具只能呈现信号，取舍仍需人（业务+技术）拍板。

## 六、常见误区

- 「治理 = 工具自动解决」：工具只能度量，决策与担责不可替代。
- 「只在事故后才治理」：被动治理代价最高，应常态化。
- 「债务是技术的错」：多数债务是业务优先级下的有意取舍，需共担。
- 「上限设为零」：零债务不现实，会扼杀探索与交付节奏。

## 九、演进与趋势

债务作为产品待办项（backlog item）与业务优先级统一排序，进入 OKR/团队协议；组织级「债务预算」像财务预算一样被审批与追踪。结合工程效能度量（DORA 指标），把债务利息与交付速度显式关联，使治理从「道德呼吁」变为「经营仪表盘」。

## 十、小结

取舍与治理把技术债务从隐性负担变为显式、共担、可决策的组织资产：以透明、共担、设限、复盘四支柱运转，并用 TDR 上限与成本收益比量化决策。其权威基础是 McConnell 与 Martin 的债务方法论，落地关键是业务与技术的联合担责。
