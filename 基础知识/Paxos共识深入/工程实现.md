# Paxos 工程实现

> 对应 Google Chubby、Spanner 及 Diego Ongaro 对 Paxos 难点的总结。

## 一、背景与挑战
Lamport 的原始描述高度抽象，工业界落地需处理持久化、成员变更、日志压缩、性能优化等大量细节。许多系统选择 Raft 正是因为 Paxos 工程化困难。

## 二、核心原理
工程要点：
- 持久化：Acceptor 的 (minN, acceptedN, acceptedV) 与 Leader 的日志必须落盘(WAL)后才应答。
- 批处理：将多个客户端请求聚合成一个 Multi-Paxos 实例的连续 slot，提升吞吐。
- 成员变更：用 Joint Consensus(联合多数派) 平滑切换配置。
- 读优化：Leader 租约内可读本地(线性一致读)，无需走完整共识；否则需确认无更高 ballot。

## 三、形式化 / 数学基础
联合多数派：新旧配置 C_old, C_new 并存期间，决策需同时获得 Q_old ∩ Q_new 的多数(即新旧各多数派均同意)。
正确性：|Q_old| > |C_old|/2 且 |Q_new| > |C_new|/2 保证任意时刻至多一个合法多数派决策。

## 四、代码实现
```python
# 持久化 WAL 伪代码
def on_accept(a, n, v):
    if n >= a.min_n:
        write_wal(a.id, ("ACCEPT", n, v))  # 先落盘
        fsync()
        a.accepted_n, a.accepted_v = n, v
        return True
    return False
```

## 五、与其他技术对比
- Chubby 用 Multi-Paxos + 租约提供粗粒度锁与命名服务。
- Spanner 用 Paxos 组复制分片，TrueTime 提供外部一致。

## 六、常见误区
- 误区：实现 Basic Paxos 即可投产。缺持久化/成员变更则不安全。
- 误区：Paxos 性能天然差。批处理与本地读可大幅提升。

## 九、演进与趋势

## 十、小结
Paxos 理论优雅但工程沉重，持久化、成员变更、批处理与读优化是把论文变成系统的关键。
