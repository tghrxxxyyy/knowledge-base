# Paxos 角色与阶段

> 对应 Lamport《The Part-Time Parliament》(1998) 角色划分。

## 一、背景与挑战
理解 Paxos 首先要厘清三类角色与两阶段消息流。角色可任意重叠于物理节点，便于工程部署。

## 二、核心原理
角色：
- Proposer：提出提案 (n, v)，驱动协议。
- Acceptor：持久化 minN / acceptedN / acceptedV，决定接受与否；是容错核心。
- Learner：学习被选定的值，通常经 Acceptor 广播或单独的“选定”通知。
阶段：
- Phase 1a Prepare(n) -> 1b Promise(n, acceptedN, acceptedV)
- Phase 2a Accept(n, v) -> 2b Accepted(n, v)
- Learn：多数派 Accepted 同一 (n,v) 后广播 chosen。

## 三、形式化 / 数学基础
Acceptor 状态需持久化(崩溃后恢复一致)：
S(a) = (minN, acceptedN, acceptedV)
Promise 条件：n > minN；Accept 条件：n >= minN。
Quorum Q：|Q| > N/2，任意两个 Quorum 必相交(保证选定值唯一)。

## 四、代码实现
```python
def propose(acceptors, n, v):
    # phase 1
    promises = [a.prepare(n) for a in acceptors if a.prepare(n)[0]]
    if len(promises) <= len(acceptors)//2:
        return None
    # 选 v：acceptedN 最大者的值，否则自选
    v = max(promises, key=lambda p: p[1])[2] or v
    # phase 2
    accepted = sum(a.accept(n, v) for a in acceptors)
    return v if accepted > len(acceptors)//2 else None
```

## 五、与其他技术对比
- Raft 把角色显式化为 Leader/Follower/Candidate，阶段更规整。
- Paxos 角色可重叠，灵活但易混淆。

## 六、常见误区
- 误区：Learner 必须独立节点。实际常与 Acceptor 同机。
- 误区：Proposer 数量受限。可多 Proposer，但需防活锁。

## 九、演进与趋势
现代实现常把 Learner 优化为“选定即提交并异步通知”，减少消息量。

## 十、小结
Proposer/Acceptor/Learner 三类角色与两阶段消息构成 Paxos 的骨架，Acceptor 的持久化与多数派相交是不变性的根源。
