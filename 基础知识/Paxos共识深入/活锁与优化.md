# Paxos 活锁与优化

> 对应《Paxos Made Simple》(2001) 与工程实践(Google Chubby 经验)。

## 一、背景与挑战
多个 Proposer 同时用更高提案号打断彼此的 Accept，导致无限重试、永不选定 —— 即 Paxos 活锁(livelock)。需通过 Leader 与退避等机制保证进展。

## 二、核心原理
活锁成因：Proposer A 发 accept(n)，Proposer B 发 prepare(n+1) 使 A 的 accept 被拒，A 重试 prepare(n+2) 又打断 B，循环往复。
优化：
- 稳定 Leader：仅 Leader 提议，消除并发打断。
- 随机退避：被拒后随机等待再重试，降低碰撞概率。
- 选主协议：用一次 Paxos 选出唯一 Leader，其余退为只读/备用。

## 三、形式化 / 数学基础
进度条件：存在某 Proposer 在足够长时间内不被更高 n 打断，则其 accept 必被多数派接受(因 Prepare 已被承诺)。
退避期望：重试间隔 ~ Exp(λ) 使并发碰撞概率趋于 0。

## 四、代码实现
```python
import random, time
def propose_with_backoff(acceptors, v, max_retry=10):
    n = random.randint(1, 1<<20)
    for _ in range(max_retry):
        r = propose(acceptors, n, v)
        if r is not None:
            return r
        time.sleep(random.uniform(0.01, 0.1))  # 随机退避
        n += 1
```

## 五、与其他技术对比
- Raft 用任期 + 选举超时随机化天然避免活锁，更易理解。
- Paxos 需额外机制( Leader )保证活性，安全性不依赖 Leader。

## 六、常见误区
- 误区：Paxos 安全性依赖 Leader。安全性来自多数派与 P2b，Leader 只为活性。
- 误区：活锁可通过更快重试解决。反而加剧碰撞。

## 九、演进与趋势
Fast Paxos、EPaxos 以减少往返与角色数为目标进一步优化活性与延迟。

## 十、小结
Paxos 安全性不依赖 Leader，但活性需要 Leader 或退避来避免活锁；这是工程实现的关键难点。
