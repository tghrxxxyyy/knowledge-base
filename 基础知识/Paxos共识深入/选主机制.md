# Paxos 选主机制

> 对应 Basic Paxos 选主: 用 Paxos 本身选 Leader，参见 Chubby(Burrows, 2006)。

## 一、背景与挑战
为消除活锁与提高效率，需要选出唯一 Leader 来驱动 Multi-Paxos。选主本身也需容错，常用“用一次 Paxos 实例选主”或基于租约(lease)机制。

## 二、核心原理
- Paxos 选主：对“谁是 Leader”这一值运行一次 Basic Paxos，选定者即 Leader，持有递增 ballot。
- 租约选主：Leader 周期性刷新租约(带 fencing token)；租约过期未刷新则其他节点竞选。
- 优先级/时间戳：节点 ID 最大或时钟最新者优先，降低冲突。

## 三、形式化 / 数学基础
Leader 标识 L 与 epoch e。任何新 Leader 必须获得更高 e，使旧 Leader 的提案因 n<minN 被拒(fencing)。
不变式：任意时刻至多一个有效 Leader（基于租约 TTL 与时钟偏差 δ：TTL > 最大时钟漂移）。

## 四、代码实现
```python
class LeaderElection:
    def __init__(self, node_id, acceptors):
        self.id = node_id; self.acceptors = acceptors
    def try_become_leader(self, epoch):
        v = f"node-{self.id}"
        return propose(self.acceptors, epoch, v) == v
# 租约：Leader 每隔 TTL/2 续约，携带单调递增 epoch
```

## 五、与其他技术对比
- Raft 选举基于随机超时 + 任期号，天然产生唯一 Leader。
- Paxos 选主更灵活(可显式)，但需自行保证唯一性。

## 六、常见误区
- 误区：选主后 Leader 永不变。租约过期或崩溃会触发重选。
- 误区：fencing 仅用于锁。共识中也需要 epoch 防止旧 Leader 干扰。

## 九、演进与趋势
租约 + epoch 成为分布式选主主流；与 fencing 结合防止脑裂。

## 十、小结
选主把 Paxos 的并发提议收敛为单点驱动，是 Multi-Paxos 高效运行的前提；租约与 fencing 保证其安全性。
