# 寄存器堆读写冲突

> 对应 Hennessy & Patterson《Computer Architecture: A Quantitative Approach》多端口与端口争用章节、Weste & Harris《CMOS VLSI Design》SRAM 单元与位线模型，以及 Patterson & Hennessy《Computer Organization and Design》数据通路资源冲突部分。

## 一、背景与挑战

寄存器堆的端口数是硬资源：读端口数决定单周期能取多少个源操作数，写端口数决定单周期能回写多少个结果。在宽发射乱序核中，同一周期可能有 4~8 条指令要读源、2~4 条指令要写结果，而物理上无法为每个可能的并发访问各配一个端口。于是产生三类冲突：写端口争用（多个结果争用有限写端口）、读端口争用（读端口总数不足）、以及同地址读写冲突（同一周期内既读又写同一物理寄存器）。这些冲突若处理不当，轻则流水停顿、重则读到陈旧值造成静默错误。

## 二、核心原理

第一类是写端口冲突。写端口通常比发射宽度少，因为并非每条指令都写寄存器（store、分支、比较等不写），且结果产生时间不同拍。工程上用写队列缓冲待写结果，按先进先出或优先级仲裁选出一条在当拍落堆，其余排队。这要求写队列足够深以吸收突发，否则队列满时会反向背压执行级，形成新的停顿源。

第二类是读端口冲突与「多读同一格」。读同一物理寄存器多端口并行在电气上无冲突（各端口有独立位线与读出放大器），真正的问题是端口总带宽：宽发射下需要约 $2 \times$ 发射宽度个读访问。若非所有指令都需要两个源（立即数指令只需一个源、单目运算只需一个），可以靠「操作数复用」与「读端口按需分配」把平均需求压下来。这是一个统计复用问题，不是纯硬件堆端口问题。

第三类是同地址读写冲突，也是最微妙的一类。若读端口是组合读（异步），同一周期写入的值不会反映在读出数据上，读出的是旧值；若读端口是同步读（在时钟沿采样），读出的同样是写之前的值。两种实现下，消费者要拿到新值都必须依赖旁路选择写数据，而不是指望堆内读穿透。反过来，若设计者误以为「同拍写会在同拍被读出」，就会漏掉旁路逻辑，导致依赖该值的指令拿到旧数据。

第四类是跨类型与 bank 冲突。当 PRF 按数据类型拆分或按 bank 划分时，若某拍访问集中在同一 bank，就会出现 bank 冲突，需要额外拍或重新分配；分布式 PRF 还要处理跨簇（cluster）读写带来的额外延迟与唤醒偏移。

## 三、形式化与数学基础

设每周期写需求为 $D_w$、可用写端口数为 $W$、读需求为 $D_r$、可用读端口数为 $R$，可行性条件为：

$$ D_w \le W, \qquad D_r \le R $$

当 $D_w > W$ 时超额部分必须排队。若写需求到达近似泊松、单端口服务，则平均排队延迟随利用率 $\rho = D_w/W$ 迅速上升（近似 $1/(1-\rho)$），这解释了为什么写队列浅、端口少的设计在突发时容易抖动。

对 bank 化 PRF，设 $B$ 个 bank，某拍访问在 bank 上均匀分布，则无冲突概率为：

$$ P_{no\ conflict} = \frac{B!}{B^{N}\,(B-N)!} $$

其中 $N$ 为该拍的并发访问数。当 $N$ 接近 $B$ 时冲突概率急剧上升，因此 bank 数通常取并发访问数的若干倍。

同地址读写的形式化：设组合读的读出值为 $v_{read}$，同拍写入值为 $v_{write}$，寄存器旧值为 $v_{old}$，则无论组合读还是同步读都有 $v_{read} = v_{old}$，消费者必须通过旁路获得新值：

$$ \text{operand} = \begin{cases} v_{write} & \text{若同拍命中}\\ v_{read} & \text{否则} \end{cases} $$

## 四、代码实现

写端口仲裁与写队列（含背压信号），注意队列满时必须反压执行级，否则请求会静默丢失：

```systemverilog
module write_arbiter #(parameter W = 2, parameter DEPTH = 8) (
    input  logic              clk,
    input  logic [W-1:0]      req_valid,
    input  logic [W-1:0][4:0] req_addr,
    input  logic [W-1:0][63:0] req_data,
    output logic              rf_we,
    output logic [4:0]        rf_waddr,
    output logic [63:0]       rf_wdata,
    output logic              backpressure
);
    logic [4:0]  q_addr [0:DEPTH-1];
    logic [63:0] q_data [0:DEPTH-1];
    logic [3:0]  q_head, q_tail, q_cnt;
    wire push = |req_valid;
    wire pop  = (q_cnt != 0);

    always_ff @(posedge clk) begin
        if (push && (q_cnt < DEPTH))
            for (int i = 0; i < W; i++)
                if (req_valid[i]) begin
                    q_addr[q_tail] <= req_addr[i];
                    q_data[q_tail] <= req_data[i];
                    q_tail <= q_tail + 1'b1;
                end
        if (pop) begin
            rf_we    <= 1'b1;
            rf_waddr <= q_addr[q_head];
            rf_wdata <= q_data[q_head];
            q_head   <= q_head + 1'b1;
        end else
            rf_we <= 1'b0;
        q_cnt <= q_cnt + (push ? 1 : 0) - (pop ? 1 : 0);
    end
    assign backpressure = (q_cnt >= DEPTH - 1);
endmodule
```

同地址读写与旁路的配合（消费者侧）：

```verilog
// 若本拍写端口命中了源寄存器，则用写数据而非堆读数据
wire same_cycle_hit = rf_we && (rf_waddr != 5'd0) && (rf_waddr == src_arch);
assign operand = same_cycle_hit ? rf_wdata : rf_rdata;
```

注意 `same_cycle_hit` 与常规旁路的优先级关系：更年轻的在途结果（EX/MEM）通常仍应优先于本拍写端口数据，具体取决于流水级划分，写错优先级会被静默破坏。

## 五、与其他技术对比

| 方案 | 端口成本 | 冲突处理 | 延迟影响 | 适用场景 |
| --- | --- | --- | --- | --- |
| 单端口 + 时间复用 | 最低 | 分拍串行访问 | 明显增拍 | 极小核、FPGA 原型 |
| 多端口 SRAM | 高 | 基本无冲突 | 延迟随端口上升 | 通用多发射核 |
| 写队列 + 仲裁 | 低 | 排队吸收突发 | 队列满时背压 | 写少读多的常规核 |
| 分布式 PRF（按类型） | 中 | 减少单堆压力 | 跨类型访问有额外代价 | 整数/浮点分离核 |
| bank 化 + 交叉开关 | 中高 | bank 冲突需重试 | 冲突时增拍 | 宽发射、向量核 |

对比的关键维度是「面积换带宽」与「延迟换带宽」。多端口是直接的面积换带宽；bank 化是折中的带宽方案，成本低但有冲突概率；写队列是延迟换带宽，用排队替代端口；分布式 PRF 是分区换带宽，降低单点压力但引入跨区开销。

## 六、常见误区

1. 认为读操作不会冲突。读同一寄存器多端口并行确实无电气冲突，但读端口总数是有限资源，宽发射下仍需统计复用与按需分配。
2. 认为写可以无限并行。写端口数通常小于发射宽度，必须靠写队列与仲裁吸收，队列深度直接决定突发容忍度。
3. 认为同拍写会被同拍读出。组合读与同步读都不会自动穿透，消费者必须依赖旁路选择写数据。
4. 忽略队列满时的背压路径。没有背压信号时，请求会静默丢失，表现为随机数据错误而非性能下降，极难排查。
5. 认为 bank 化没有代价。bank 数不足时冲突概率急剧上升，且跨 bank 访问可能引入额外延迟与唤醒偏移。
6. 混淆「端口不足导致的停顿」与「依赖导致的停顿」。前者是结构冒险，后者是数据冒险，优化手段完全不同。

## 八、面试题

1. 写端口不足时如何处理？
   要点：用写队列缓冲并按优先级或轮转仲裁；队列满时向执行级反压；也可通过增加端口、bank 化或数据捕获减少写压力。

2. 同一周期读写同一寄存器靠什么保证正确？
   要点：靠旁路网络把写数据直接送给消费者，而不是指望寄存器堆读穿透；组合读与同步读读出均为旧值。

3. 为什么读端口冲突比写端口冲突更容易被忽视？
   要点：读访问频次更高（每指令多个源），但读冲突通常只表现为带宽不足与调度受限，不像写冲突那样直接导致排队与背压，容易被误判为依赖问题。

4. bank 化为什么不能完全消除冲突？
   要点：并发访问在 bank 上的分布具有随机性，当并发数接近 bank 数时冲突概率迅速上升；只能靠增加 bank 数或调度规避。

5. 写队列过浅会带来什么现象？
   要点：突发时队列频繁满，背压频繁触发，执行级停顿增多；表面看是性能抖动，实则端口带宽不足。

## 九、演进与趋势

冲突治理的演进主线是减少端口需求而非增加端口。具体手段包括：数据捕获（结果直接经旁路传递，减少 PRF 写端口占用）、操作数复用与读端口按需分配（立即数与单目运算只占一个读端口）、按类型与按簇的分布式 PRF（把冲突分散到多个小堆）、以及零值优化与 move elimination（减少不必要的物理项分配从而减少写活动）。在向量与矩阵扩展中，寄存器宽度从 128 位扩展到数百位，端口压力与 bank 冲突问题被显著放大，推动了分段 PRF 与更激进的调度规避策略。

## 十、小结

寄存器堆读写冲突源于端口有限与访问需求不匹配：写冲突靠队列与仲裁化解，读冲突靠统计复用与按需分配缓解，同地址读写冲突靠旁路而非读穿透解决，bank 与跨类型冲突靠分区与调度规避。任何一环的保守估计不足都会先在性能上体现为抖动，继而在极端序列下演变为静默数据错误，因此端口预算必须按最坏并发而非平均并发来规划。
