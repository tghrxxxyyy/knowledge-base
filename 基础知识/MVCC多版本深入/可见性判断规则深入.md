# 可见性判断规则深入

> 对应 Berenson et al. 1995（隔离级别可见性语义），以及 cmu-db/15445-course（MVCC 可见性 lecture）。

## 一、背景与挑战
MVCC 正确性完全取决于“某版本对某个事务是否可见”的判断。规则必须同时处理已提交/未提交、事务先后、自身修改等情形，否则出现脏读或不可重复读。

## 二、核心原理
对每个版本记录 xmin（创建事务）、xmax（删除事务）。事务 $T$ 的快照包含“已开始的事务集合”与“已提交上界”。可见性需判定：创建者是否已提交且对快照可见、删除者是否对快照不可见、以及该版本是否属于 $T$ 自身。

## 三、形式化与数学基础
对事务 $T$（快照上界 $U_T$，自身 id $T$）：
$$ \begin{aligned}
\text{created\_ok} &: xmin = T \ \text{or}\ (committed(xmin) \ \text{and}\ xmin < U_T) \\
\text{deleted\_ok} &: xmax = INF \ \text{or}\ xmax = T \ \text{or}\ \neg committed\_before(xmax, U_T)
\end{aligned} $$
可见当且仅当 created_ok 且 deleted_ok。

## 四、代码实现
```python
# 版本可见性判定（仅示意）
def visible(v, t, U, committed):
    created = (v.xmin == t) or (committed(v.xmin) and v.xmin < U)
    if v.xmax == INF or v.xmax == t:
        deleted = True
    else:
        deleted = not (committed(v.xmax) and v.xmax < U)
    return created and deleted
```

## 五、与其他技术对比
PostgreSQL 用 xmin/xmax/infomask 位表示提交状态；InnoDB 用事务 ID + undo 回滚构造旧版本并比较。规则本质一致：比较事务序与提交状态。

## 六、常见误区
1) 忽略“自身修改应可见”——导致自己读不到刚写。
2) 把 xmax=∞ 当作已删除——它是未删除标志。
3) 在可见性里漏判未提交删除。

## 九、演进与趋势
基于提交时间戳（而非 ID 比较）的可见性、硬件时钟降低可见性判断开销。

## 十、小结
可见性规则是 MVCC 正确性的“裁判”：用 xmin/xmax 与提交序精确判定每版本的可见边界。
