# 02 · 可观测性与稳定性看护（深入：SLO 看板 / Trace 采样 / 日志结构化 / 告警治理流程）

> SLO 定了，但**看不见就救不了**。可观测性（Observability）是 SRE 的"眼睛"。本篇深入拆解：SLO 看板实现、Trace 采样策略、日志结构化规范、告警治理完整流程。

---

## 一、可观测性的三件套

| 信号 | 是什么 | 特点 | 典型工具 |
|------|--------|------|----------|
| **Metrics** | 聚合数值（CPU、QPS、错误率） | 省存储、适合告警、看趋势 | Prometheus、VictoriaMetrics |
| **Logs** | 离散事件文本 | 详细但量大、难聚合 | Loki、ELK |
| **Traces** | 单次请求跨服务调用链 | 定位慢/错在哪一站 | Jaeger、Tempo、SkyWalking |

> **口诀：指标看趋势、日志看细节、链路看路径。**

---

## 二、四大黄金信号（RED / USE）

| 信号 | 含义 | 例子 |
|------|------|------|
| **延迟 Latency** | 请求耗时 | P99 响应时间 |
| **流量 Traffic** | 请求量 | QPS、并发 |
| **错误 Errors** | 失败比例 | 5xx 率、超时率 |
| **饱和度 Saturation** | 资源饱和 | CPU%、连接池占用 |

**RED（请求服务）**：Rate / Errors / Duration——适合 API 服务。
**USE（资源）**：Utilization / Saturation / Errors——适合主机/中间件。

## 三、SLO 驱动的告警（而非"能报就报"）

### 3.1 告警三原则

1. **基于 SLO 而非阈值**：不是"CPU>80% 就报"，而是"按当前燃烧率，30 分钟内会烧光预算才报"；
2. **多窗口多燃烧率**：快速燃烧（14.4 倍）立刻 Page，慢速燃烧（1 倍）仅工单；
3. **降噪**：非 SLO 相关的波动不 Page，进 dashboard 自查。

> 燃烧率 = 实际错误率 / SLO 允许错误率。>1 即在消耗预算。

### 3.2 多窗口多燃烧率配置

```
5 分钟窗口 × 14.4x burn rate → Page（突发故障）
  含义：按当前速率 5 分钟内烧光 1% 预算 → 必须立刻响应

30 分钟窗口 × 6x → Page（持续恶化）
6 小时窗口 × 1x → 工单（缓慢恶化）
  含义：1x = 整个月刚好烧完预算

配置示例：
  window: 1h, burn_rate: 14.4,  # 快速
  window: 6h, burn_rate: 6,     # 中速
  window: 3d, burn_rate: 1      # 慢速
```

## 四、SLO 看板实现

### 4.1 看板核心面板

```
顶部：SLO 达成状态（OK / WARNING / BURNING）
  每项服务一行：SLI 值 / SLO 目标 / 预算剩余

指标面板：
  错误率趋势（对比 SLO 红线）
  燃烧率趋势（多窗口）
  预算消耗曲线（本月累计）

下钻：
  点击服务 → 服务详情（黄金信号 + 最近变更）
  点击错误率 → 错误分布（按错误码/接口/地域）
  点击 Trace → 单次请求链路
```

### 4.2 Prometheus SLO 查询

```promql
# 错误率（5 分钟窗口）
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))

# 预算剩余（30 天窗口）
1 - (
  sum(rate(http_requests_total{code=~"5.."}[30d]))
  /
  sum(rate(http_requests_total[30d]))
) / 0.001  # 除以 SLO 目标（99.9%）

# 燃烧率
(
  sum(rate(http_requests_total{code=~"5.."}[5m]))
  /
  sum(rate(http_requests_total[5m]))
) / 0.001
```

## 五、Trace 采样策略

### 5.1 采样问题

```
全量采样成本高（存储/CPU）
采样率低 → 慢请求/故障漏采

权衡：质量 vs 成本
```

### 5.2 采样策略对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 头部采样（固定） | 请求开头决定 | 简单 | 可能丢异常链路 |
| 尾部采样 | 看完整再决定 | 保异常 | 需缓冲 |
| 自适应采样 | 按流量/错误率调整 | 智能 | 复杂 |
| 优先级采样 | 错误/慢请求 100%，正常 1% | 保关键 | 需标记 |

### 5.3 生产推荐

```
错误请求：100% 采样
慢请求（> 阈值）：100% 采样
正常请求：1~10%（按流量调整）
新发布/变更期间：临时提高采样率

实现：
  OTel：尾部采样处理器（tail_sampling）
  错误标记：status=ERROR → 强制保留
```

## 六、日志结构化规范

### 6.1 结构化日志格式

```json
{
  "timestamp": "2026-08-19T10:00:00.123Z",
  "level": "ERROR",
  "service": "order-service",
  "trace_id": "abc123...",
  "span_id": "def456...",
  "user_id": "u_10086",
  "order_id": "o_999",
  "message": "支付回调处理失败",
  "error_code": "PAY_TIMEOUT",
  "stack": "...",
  "duration_ms": 1520
}
```

### 6.2 日志规范要点

| 规范 | 说明 |
|------|------|
| JSON 格式 | 可解析、可检索 |
| 必带 trace_id | 与链路关联（跳转排障） |
| 关键业务 ID | user_id/order_id 等（检索维度） |
| 错误分类 | error_code（可聚合统计） |
| 禁用敏感信息 | 手机号/身份证脱敏 |
| 日志分级 | DEBUG/INFO/WARN/ERROR 使用规范 |

### 6.3 日志与指标联动

```
日志 → 指标：
  错误码计数（Promtail 解析 → 指标）
  异常类型分布

日志 → Trace：
  trace_id 关联（从日志跳链路）

指标 → 日志：
  错误率升高 → 下钻看该时段日志
```

## 七、告警治理完整流程

### 7.1 告警生命周期

```
1. 设计：告警目标（什么故障信号）+ 阈值 + 分级
2. 配置：规则 + 通知渠道 + Runbook
3. 验证：注入故障测试告警有效性
4. 运营：接收 → 响应 → 处置 → 复盘
5. 治理：噪音分析 → 优化规则
6. 迭代：季度告警审计
```

### 7.2 告警噪音治理

```
噪音来源：
  阈值不合理（太敏感）
  重复告警（同故障多条）
  无 Runbook（不知道怎么办）
  无对应动作（告警了但没意义）

治理方法：
  告警合并（同服务/同故障聚合）
  静默窗口（已知故障期间的重复告警）
  阈值调整（根据历史噪音数据）
  告警分级（Page vs 工单）
  行动率统计（能行动的告警占比）
```

### 7.3 告警指标

| 指标 | 目标 |
|------|------|
| 行动率 | 告警中可行动的占比 > 80% |
| 误报率 | < 10% |
| MTTD（发现时长） | 持续下降 |
| MTTR（恢复时长） | 持续下降 |
| 告警疲劳度 | 每人每天 Page < 3 次 |

## 八、常见陷阱

| 陷阱 | 危害 | 对策 |
|------|------|------|
| 只采集不告警 | 测到了但没人看 | 告警先行 |
| 告警阈值乱设 | 告警疲劳 | SLO 驱动 |
| 链路采样过低 | 慢请求漏采 | 尾部采样 |
| 日志打满敏感信息 | 合规风险 | 脱敏规范 |
| 指标无标签维度 | 无法下钻 | 统一标签规范 |

## 九、成熟度模型（自我评估）

| 级别 | 特征 | 表现 |
|------|------|------|
| L1 有工具 | Prometheus/Grafana 搭起来了 | 指标能看，告警靠经验拍阈值 |
| L2 有体系 | 三件套齐全、trace 贯穿 | 能定位，但告警噪音大 |
| L3 有度量 | SLO 驱动告警、燃烧率分级 | 告警可行动，预算可量化 |
| L4 有闭环 | 告警→排障→复盘→规则沉淀自动回流 | 事故率下降，演练常态化 |

> 面试回答「你们可观测性做得怎么样」时，用这个模型定位段位，并说明下一步——比空洞地说「我们用 Prometheus」强得多。

## 十、落地检查清单

**采集层**
- [ ] 所有核心服务接入统一 Trace（含入口/出口/DB/消息队列）
- [ ] 黄金信号 4 项齐全，且带维度标签（服务/接口/机房/版本）

**排障层**
- [ ] 单条链路可从 Trace 跳到日志、从日志跳到指标
- [ ] 大促/变更前后有基线对比看板

## 十、Trace 上下文传播实现细节

链路能"串起来"靠的是 **trace_id 在跨进程边界的传递**。常见传递点：

| 边界 | 传递方式 |
|------|----------|
| HTTP 入口 | 网关生成 trace_id，写入响应头 `traceparent`（W3C 标准） |
| 服务间调用 | 客户端 SDK 把 traceparent 注入下游请求头 |
| 消息队列 | trace_id 作为消息属性（header）随消息投递 |
| 异步线程 | 手动 `MDC.set("trace_id", ...)`（见 06 篇） |
| 跨线程池 | TaskDecorator / 装饰 Runnable 透传 |

```java
// Spring Cloud Sleuth / OTel 自动注入示意
@EventListener
public void onRequest(ServerHttpRequest req) {
    String tid = req.getHeaders().getFirst("traceparent");
    if (tid == null) tid = TraceIdGenerator.next();  // 入口生成
    MDC.put("trace_id", tid);
}
```

> 口诀：**入口生成、跨边界带、异步手动传、MDC 用完清**。

## 十一、指标基数（Cardinality）爆炸治理

高基数标签是 Prometheus 的"内存杀手"——一个 `user_id` 当 label 会瞬间产生百万级时间序列，直接 OOM。

| 反模式 | 后果 | 纠偏 |
|--------|------|------|
| 把 user_id/order_id 当 label | 基数爆炸、TSDB 崩溃 | 只放维度枚举（status/region） |
| 把时间戳/随机值当 label | 同上 | 禁止 |
| 标签值无限增长（每版本一个） | 存储无限涨 | 收敛枚举 + 保留策略 |

| 安全 label | 危险 label |
|-----------|-----------|
| `code=5xx/4xx` | `user_id=10086` |
| `region=bj/sh` | `order_id=...` |
| `method=GET/POST` | `trace_id=...` |

> 经验：单指标时间序列数控制在**十万级以内**，单 label 基数 < 几百。

## 十二、可观测性数据成本优化

| 信号 | 成本优化手段 |
|------|--------------|
| Metrics | Recording Rule 预聚合、降采样（5m/1h）、短保留+长保留降采样 |
| Logs | 结构化 + 采样、热 30 天冷归档、只索引关键字段 |
| Traces | 尾部采样、错误/慢请求 100%、正常 1~10%、按服务配额 |

- 成本公式：存储量 ≈ 数据点 × 保留期 × 副本；优先砍"高基数 + 长保留"；
- 黄金信号全量，细节采样——既保排障又控成本。

## 十三、真实踩坑实录

1. **trace_id 在异步线程丢失**：线程池切换后日志串不起来。
   纠偏：用 TaskDecorator 透传 MDC，或显式 `MDC.put/remove`。
2. **指标基数爆炸拖垮 Prometheus**：把 userId 当 label。
   纠偏：label 只用低基数枚举，高基数走日志。
3. **告警阈值"拍脑袋"**：CPU>80% 全量 Page，半夜被叫醒发现是正常波动。
   纠偏：告警改 SLO 燃烧率驱动，分级 Page/工单。
4. **全量 Trace 存储爆盘**：成本失控。
   纠偏：错误/慢请求 100% 采样，正常 1%。
5. **只有指标没有 Runbook**：告警响了不知道怎么办。
   纠偏：每条告警绑定 runbook 链接 + 责任人与动作。

## 十四、可观测性排障标准动作（SRE 实战）

```
收到告警 → ①看 SLO 面板（是否真越界）
         → ②看黄金信号（哪个信号异常：延迟/错误/流量/饱和）
         → ③下钻 Trace（慢/错在哪一站）
         → ④跳日志（该 trace_id 全量日志时间轴）
         → ⑤关联变更（近期发布/配置是否吻合时间线）
         → ⑥止血（回滚/降级/扩容）→ ⑦复盘
```

> 口诀：**先 SLO、再黄金、再 Trace、后日志、最后变更**——顺序错了就是瞎找。

## 十六、可观测性里的"安全视角"（跨板块联动）

可观测性不止服务于稳定性，也是安全检测与合规审计的底座。三条常被忽视的重叠线：

1. **日志脱敏是红线**：链路/访问日志里一旦落了身份证、手机号、token，可观测性系统本身就成了数据泄露源。
   落地：采集端做 PII 过滤（正则 + 结构化字段黑名单），敏感字段用盲索引而非明文（参见 [安全工程·数据安全](../安全工程/05-数据安全与密码学基础.md)）。
2. **审计日志要独立、不可篡改**：谁在什么时候改了什么配置/权限，要能事后追溯且不被运维自己改掉。
   落地：写-only 审计流，与排障日志分通道，保留周期按合规要求（如 180/365 天）。
3. **安全事件也需要 Golden Signal**：把"鉴权失败率、越权尝试数、异常出网连接数"当作一类 SLI，接进同一套 Burn Rate 告警。
   落地：安全指标与稳定性指标共用同一套多窗口告警骨架（参见 [01 SLO/Burn Rate](01-SRE理念与SLI-SLO-ErrorBudget.md)），避免安全侧另起炉灶又缺看护。

> 交叉检查：可观测性采集了哪些数据、存多久、谁能看，本身就是 [安全工程·总览](../安全工程/安全工程总览.md) 里的"数据分类分级"议题。别让"为了排查方便"突破了数据最小化原则。
