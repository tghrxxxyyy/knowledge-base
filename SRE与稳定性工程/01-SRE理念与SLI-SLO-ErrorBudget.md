# SRE 理念与 SLI/SLO/Error Budget（深入：Burn Rate 告警 / SLO 落地案例 / 自动化策略）

> SRE 不是"高级运维"，是一套**用工程方法管理稳定性**的体系。本篇深入拆解：Burn Rate 告警配置、SLO 实战落地案例、错误预算策略自动化、Toil 量化。

---

## 一、SRE 核心信条

> **用软件工程的方法解决运维问题；让开发自己承担系统的可靠性。**

关键实践：
- SRE 团队中 50%+ 时间做工程（自动化/工具），而非救火
- 开发写服务、也负责它的可靠性（You build it, you run it）
- 用 SLO 量化可靠性，用错误预算平衡迭代速度

---

## 二、SLI/SLO/SLA

### 2.1 定义

| 概念 | 含义 | 谁定 |
|------|------|------|
| SLI | 实际度量值（如可用率 99.95%） | 技术 |
| SLO | 内部目标（如月度可用率 ≥99.9%） | 技术+产品 |
| SLA | 对客户的合同承诺（含违约赔偿） | 商务 |

> SLI 是尺子，SLO 是目标，SLA 是合同（带罚则）。SLA 通常比 SLO 宽松。

### 2.2 常见 SLI 类型

| 类别 | SLI 例子 | 适用 |
|------|----------|------|
| 可用性 | 成功请求 / 总请求 | API 服务 |
| 延迟 | P50/P95/P99 响应时间 | 交互式服务 |
| 吞吐 | QPS / 每秒处理 | 消息/批处理 |
| 质量 | 错误率、数据准确性 | 数据管道 |
| 饱和度 | CPU/连接/队列深度 | 资源监控 |

### 2.3 SLO 目标参考

| 可用性 | 年停机 | 适用 |
|--------|--------|------|
| 99%（双九） | ~3.65 天 | 内部系统 |
| 99.9%（三九） | ~8.76 小时 | 多数对外服务 |
| 99.95%（3.5 九） | ~4.38 小时 | 重要服务 |
| 99.99%（四九） | ~52 分钟 | 核心金融/支付 |

> SLO 不是越高越好。四九比三九成本高一个数量级。

## 三、错误预算与 Burn Rate 告警

### 3.1 错误预算计算

```
SLO 99.9% → 月允许错误 = 0.1% × 30天 × 1440分 = 43.2 分钟
SLO 99.95% → 月允许错误 = 21.6 分钟
SLO 99.99% → 月允许错误 = 4.32 分钟
```

### 3.2 Burn Rate（燃烧速率）

```
Burn Rate = 实际错误率 / SLO 允许错误率

Burn Rate = 1x → 以 SLO 限速消耗预算（30天耗完）
Burn Rate = 2x → 15天耗完
Burn Rate = 14.4x → 2天耗完（紧急告警阈值）

多窗口告警（Google 推荐）：
  短窗口（5分钟）× Burn Rate 14.4 → 检测突发故障
  长窗口（6小时）× Burn Rate 1 → 检测缓慢恶化
```

### 3.3 Burn Rate 告警配置

```yaml
# Prometheus 告警规则
groups:
- name: slo-alerts
  rules:
  # 5分钟窗口检测突发故障（14.4x burn rate）
  - alert: HighErrorBudgetBurn_5m
    expr: |
      (
        1 - (
          sum(rate(http_requests_total{code!~"5.."}[5m]))
          /
          sum(rate(http_requests_total[5m]))
        )
      ) > 14.4 * 0.001  # 14.4x × 0.1% SLO
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "SLO 错误预算快速消耗（5min 窗口）"
      
  # 6小时窗口检测缓慢恶化（1x burn rate）
  - alert: HighErrorBudgetBurn_6h
    expr: |
      (
        1 - (
          sum(rate(http_requests_total{code!~"5.."}[6h]))
          /
          sum(rate(http_requests_total[6h]))
        )
      ) > 1 * 0.001
    for: 15m
    labels:
      severity: warning
    annotations:
      summary: "SLO 错误预算缓慢消耗（6h 窗口）"
```

### 3.4 错误预算策略自动化

```yaml
# 预算状态 → 自动动作
剩余 > 50%: 正常发布
剩余 20~50%: 重要变更加审批
剩余 < 20%: 冻结非关键发布
已耗尽: 停发功能，全员稳定性冲刺

# 与 CI/CD 联动
# ArgoCD Sync Policy 根据预算状态自动切换：
# - 预算充足 → auto-sync
# - 预算不足 → manual-sync（需审批）
```

## 四、SLO 实战落地案例

### 4.1 案例：某支付系统 SLO 落地

```
第一步：定义 SLI
  核心交易接口：成功率 = 成功交易数 / 总请求数
  SLI 度量：Prometheus 查询

第二步：定 SLO
  核心交易：99.95%（30天滚动窗口）
  商品查询：99.9%（7天窗口）
  通知服务：99%（尽力而为）

第三步：配置告警
  Burn Rate 14.4x（5min）→ PagerDuty 紧急
  Burn Rate 1x（6h）→ Slack 通知

第四步：错误预算策略
  预算剩余 > 50%: 正常发布
  预算 20~50%: 发布需 SRE 审批
  预算 < 20%: 冻结非关键发布
  预算耗尽: 全员稳定性冲刺（2周）

第五步：复盘
  月度 SLO Review 会议
  分析超预算原因（故障/变更/容量）
  输出改进 Action Items
```

### 4.2 SLI 选择最佳实践

| 服务类型 | 推荐 SLI |
|----------|----------|
| API 服务 | 可用性（成功率）+ 延迟（P99） |
| 消息队列 | 吞吐（消息处理速率）+ 延迟（端到端） |
| 数据管道 | 数据准确性 + 端到端延迟 |
| 定时任务 | 任务成功率 + 执行时长 |
| 前端页面 | 加载时间（LCP）+ 交互延迟（FID） |

## 五、Toil 量化与管理

### 5.1 Toil 定义

```
Toil = 重复性、手动的、可自动化的运维工作

特征：
  手动操作（如手动扩容）
  重复执行（如每周备份检查）
  可自动化（如日志清理）
  无持久价值（不产生新知识）
```

### 5.2 Toil 占比目标

```
Toil 占比 < 50%（Google SRE 目标）

量化方法：
  每周工时统计：工程 vs Toil vs 其他
  Toil 工时 = 手动操作工时 + 响应告警工时 + 手动变更工时
  
降低 Toil：
  自动化运维脚本 → 工具平台 → 自愈系统
  每次 Toil 事件 → 自动化 ticket → 排入工程排期
```

## 七、SLI 的"用户感知 / 系统"双层模型

稳定性不能只看"服务成功率高"。用户关心的与工程师关心的往往是两层：

```
用户感知层（对外沟通用，业务 SLO）：
  登录成功率、下单成功率、支付成功率
  首屏可交互时间(LCP)、关键操作完成率
  → 直接对应用户体验，是和业务/老板沟通的口径

系统层（对内排障用，技术 SLI）：
  API 成功率(5xx 率)、P99 延迟、MQ 堆积、线程池拒绝数
  → 支撑用户感知，是定位根因的探针

关系：用户感知 SLO 劣化 → 下钻到系统 SLI 定位根因
```

> 常见错误：只定义了一个"API 成功率"就当全局 SLO。真实系统要从**用户关键旅程**拆——每个旅程一个 SLO，组合成"用户感知可用性"。

### 7.1 多窗口多燃烧率告警的数学推导

```
燃烧率 R = 当前错误率 / SLO 允许错误率
SLO 允许错误率 = 1 - SLO（如 99.9% → 0.001）

若当前错误率 = 0.0144（=14.4 × 0.001），则 R = 14.4
含义：按此速率，月度预算在 30d/14.4 ≈ 2 天烧完

Google SRE 推荐组合（快与慢都要抓）：
  5m  × 14.4  → 2 天内烧完：紧急 Page（突发故障）
  30m × 6     → 5 天烧完：严重 Page（持续恶化）
  6h  × 1     → 30 天烧完：工单（缓慢劣化）
```

> 注意：窗口短是为了"快发现"，燃烧率高是为了"严重"。5m+14.4 不是"2 天才告警"，而是"这么猛的速率 2 天烧光，所以现在就 Page"。

### 7.2 错误预算"算谁的"要界定清楚

```
自身可控错误：代码 bug、配置错误、容量不足 → 计入本服务预算
依赖故障：下游 Redis/DB/第三方挂 → 不计入（或单列"依赖 SLO"）
用户错误：参数非法 4xx（非越权/注入）→ 通常不算

界定不清的后果：下游挂了却烧自己预算，团队背锅且无力改进
```

## 八、滚动窗口 vs 日历窗口

| 维度 | 日历窗口（Calendar Month） | 滚动窗口（Rolling 30d） |
|------|---------------------------|------------------------|
| 重置 | 每月 1 号清零 | 任意连续 30 天滑动 |
| 对齐 | 与合同/对账单一致 | 无月初月末效应 |
| 问题 | 月底预算耗尽"躺平"、月初"挥霍" | 与商务口径略难对齐 |
| 实践 | 对外 SLA 口径 | 内部运营口径 |

> 推荐：**对外用日历窗口**（SLA 对齐），**内部运营用滚动窗口**（避免月初月末抖动）。预算政策评估以滚动窗口为准。

## 九、错误预算政策自动化（含与发布系统联动）

```python
# 伪代码：错误预算策略引擎（每 5min 计算一次剩余比例）
def decide_release_policy(budget_remaining_ratio: float) -> str:
    if budget_remaining_ratio > 0.5:
        return "AUTO_SYNC"            # 预算充足 → 自动发布
    elif budget_remaining_ratio > 0.2:
        return "MANUAL_APPROVAL"      # 20~50%  → 需 SRE 审批
    elif budget_remaining_ratio > 0.0:
        return "FREEZE_NON_CRITICAL"  # <20%    → 冻结非关键发布
    else:
        return "STABILITY_SPRINT"     # 已耗尽  → 全员稳定性冲刺

# 与 ArgoCD / Flux 联动：根据策略切换 Sync 模式
#   AUTO_SYNC           → argocd app set --sync-policy automated
#   MANUAL_APPROVAL     → sync-policy none + PR 评审
#   FREEZE_NON_CRITICAL → 仅安全/紧急修复可发
```

- 预算消耗必须**可视化**：Grafana 面板显示剩余 % + 燃尽曲线；
- 政策要写进团队约定（Team Handbook），不是口头约定；
- 例外通道：紧急安全修复可破例走"紧急变更"流程（带事后复盘）。

## 十、SLI 工程实现（Prometheus Recording Rules）

```yaml
# recording rules：把 SLI 预聚合，降告警/面板查询成本
groups:
- name: slo-recording
  rules:
  - record: job:slo_errors:ratio_rate5m
    expr: |
      sum(rate(http_requests_total{code=~"5.."}[5m]))
      / sum(rate(http_requests_total[5m]))
  - record: job:slo_errors:ratio_rate30d
    expr: |
      sum(rate(http_requests_total{code=~"5.."}[30d]))
      / sum(rate(http_requests_total[30d]))
  - record: job:slo_latency:p99_5m
    expr: |
      histogram_quantile(0.99,
        sum(rate(http_request_duration_seconds_bucket[5m])) by (le))
```

- Recording Rule 让告警/面板直接读聚合指标，避免实时聚合海量数据；
- 多服务用 `by (job)` 分组，避免跨服务聚合失真。

## 十一、SRE 团队的职责边界（避免"高级运维"陷阱）

| 该做 ✅ | 不该做 ❌ |
|---------|----------|
| 写平台/自动化工具 | 手工逐个处理告警 |
| 设定 SLO / 预算政策 | 替业务定产品需求 |
| 建设可观测性 | 当"救火队员"常态 |
| 推动复盘闭环 | 替开发背锅运维 |
| 赋能开发自助排查 | 成为发布瓶颈 |

> 核心理念：**You build it, you run it**——开发对自有服务的稳定性负责，SRE 提供平台、标准与护栏，而非替开发"擦屁股"。

## 十二、真实踩坑实录

1. **预算耗尽后"躺平"**：月底预算烧光，团队停止所有发布，业务停滞。
   纠偏：用滚动窗口 + 预留"紧急变更"通道，避免月初月末效应。
2. **SLO 定 99.99% 但监控只有分钟级**：精度不够，超了也不知道。
   纠偏：SLI 采集粒度细于 SLO 判定粒度（至少 1 分钟）。
3. **下游故障算自己预算**：Redis 挂导致错误率升，烧的是自己预算。
   纠偏：错误预算按"自身可控错误"定义，下游单列依赖 SLO。
4. **只配单窗口 Burn Rate 告警**：突发 5 分钟没抓到，缓慢恶化也没抓到。
   纠偏：多窗口（5m/30m/6h）组合，突发与慢速都要覆盖。
5. **SLO 定完没人看**：形同虚设。
   纠偏：绑定错误预算政策 + 月度 Review，超预算自动冻结发布。

## 十三、面试高频追问

1. **错误预算烧完怎么办？** → 冻结非关键发布、稳定性冲刺、用数据说服业务方。
2. **Burn Rate 为什么要多窗口？** → 单窗口要么漏突发、要么误报缓慢恶化。
3. **SLO 定多高合适？** → 比 SLA 严一点，留 0.1%~1% 预算给迭代。
4. **滚动窗口 vs 日历窗口？** → 对外日历、对内滚动，避免月初月末抖动。
5. **下游故障算不算我预算？** → 不算自身可控，单列依赖 SLO。
6. **Toil 是什么、目标多少？** → 可自动化运维工作，占比 < 50%。
7. **SLI 用平均值还是分位？** → 分位（P99），长尾用户更重要。
8. **错误预算政策怎么落地？** → 剩余>50% 自动 / <20% 冻结，写进约定 + 工具联动。

## 十四、速记口诀与总结速查

> 口诀：**SLO 不是越高越好，留点预算好迭代；分位窗口要分清，燃烧速率多窗口；预算政策自动化，超了就踩刹车；Toil 过半要自动化。**

| 主题 | 一句话 |
|------|--------|
| SLI | 用户可感知指标，分位优先 |
| SLO | 比 SLA 严、留预算、按旅程拆 |
| 错误预算 | 月度允许错误 = (1-SLO)×时长 |
| Burn Rate | 实际/允许，>1 即烧预算 |
| 多窗口 | 5m 抓突发、6h 抓恶化 |
| 政策 | 剩余>50% 自动，<20% 冻结 |
| Toil | <50%，能自动别手动 |

> 一句话：**SRE = SLI（尺子）+ SLO（目标）+ 错误预算（平衡器）+ Burn Rate 告警（自动化）——预算内快速迭代，超预算修稳定；Toil < 50%，能自动别手动**。
