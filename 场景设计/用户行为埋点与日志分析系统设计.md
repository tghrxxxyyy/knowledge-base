# 用户行为埋点与日志分析系统设计

> 「埋点」是数据驱动的基础设施：谁、在什么时候、做了什么。产品看漏斗、算法要特征、风控查链路，全靠它。本篇讲「解决的问题 → 埋点方式 → 采集链路架构 → 数据质量 → 分析落地 → 面试答题框架」。

---

## 一、解决的问题与定位

**解决的问题**：
1. 采集用户行为（浏览/点击/曝光/停留/搜索/支付）；
2. 端→服务端→存储→分析全链路**低延迟、不丢不漏**；
3. 支撑漏斗分析、用户画像、A/B 实验、推荐特征、风控。

**定位一句话**：**「端上埋点 → 网关收敛 → MQ 削峰缓冲 → 实时链路(数仓/OLAP) + 离线链路(ODS) 双写 → 指标服务出分析」——本质是『事件流』系统，核心指标是『不丢、低延迟、可回溯』。」**

---

## 二、埋点方式（先讲采集）

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **代码埋点** | 开发者在按钮/曝光处显式上报 | 精确、可控、带上下文 | 侵入代码、漏埋 |
| **可视化圈选** | 后台圈元素自动生成规则 | 免发版、运营自助 | 动态元素/SPA 难覆盖 |
| **无埋点（全量采集）** | SDK 自动拦截所有交互 | 覆盖全、快 | 数据噪音大、流量成本高 |
| **服务端埋点** | 后端日志/中间件记录 | 可信、可算业务指标 | 只看得到请求级 |

> 标准答案：**代码埋点为主 + 可视化圈选兜底 + 服务端关键事件双写**（前端事件前后端各记一份，可交叉核对）。

---

## 三、采集链路架构（核心）

```
端上 SDK ──批量/压缩上报──> 埋点网关(Nginx/接入层)
                              │ 校验(字段/时间/签名) + 限流
                              ▼
                         Kafka(削峰缓冲, 主题: uv_log/click_log/...)
                       ╱            ╲
              实时链路(Flink)        离线链路(定时落 HDFS/OSS)
              │ 清洗/补齐/会话切割        │ 原始日志 ODS 分区存储
              ▼                         ▼
        实时指标(OLAP/Redis)        离线数仓(DWD/DWS)
                       ╲            ╱
                         ▼
               指标查询服务 + 分析平台(漏斗/留存/路径) + 数据订阅(算法/风控)
```

### 3.1 端上 SDK 要点

- **批量 + 压缩上报**：攒 N 条或 T 秒再发，gzip 压缩（10~100 倍流量节省）；
- **离线补发**：本地队列（IndexedDB/文件），网络恢复后补发，带 `event_id + 客户端时间戳`；
- **会话标识**：sessionId（30 分钟无操作切新会话）+ userId（登录态）+ 设备 ID 三方关联；
- 首屏性能：上报不得阻塞业务（异步、独立通道、失败静默）。

### 3.2 服务端要点

- **网关**：字段白名单校验、时间偏差过滤（客户端时钟问题）、限流丢弃（可接受丢弃率内）；
- **Kafka**：按事件类型分区，保证同用户事件有序（user_id 哈希分区）；
- **双链路**：实时（Flink，秒级指标）+ 离线（小时级全量落湖），互为兜底——**实时算漏斗，离线做深度分析**。

### 3.3 数据质量（面试加分项）

- **丢失检测**：抽样对比（前端上报数 vs 服务端埋点数 vs 网关流量），算出各层丢失率；
- **重复去重**：`event_id` 唯一，Flink 侧窗口去重；
- **脏数据治理**：非法设备/爬虫/UAT 流量打标过滤，不进指标口径。

## 四、分析落地

| 场景 | 实现 |
|------|------|
| 漏斗分析 | 事件序列匹配（Flink CEP / SQL 窗口） |
| 留存/活跃 | 明细表按天聚合，UV 用 HyperLogLog 或 Bitmap |
| 路径分析 | 会话内事件按序聚合（session 表） |
| 实时大屏 | 实时链路 → Redis/OLAP 秒级指标 |
| 算法特征 | 明细订阅 Kafka，特征工程离线/实时双路 |

- **存储选型**：明细进数仓（ODS→DWD 宽表），指标进 OLAP（Doris/ClickHouse），实时计数 Redis；
- **口径统一**：指标字典（"UV 的定义/统计窗口/去重键"）由数据团队统一定义，避免各算各的。

---

## 五、面试答题框架

1. **需求澄清**：采集什么事件？实时性？数据量级（日 UV × 人均事件数）？
2. **埋点**：代码埋点为主 + 圈选兜底 + 服务端双写；
3. **链路**：SDK 批量压缩 → 网关校验 → Kafka → Flink 实时 + 离线双链路；
4. **质量**：event_id 去重、丢包检测、脏数据过滤；
5. **分析**：漏斗/留存/路径 + OLAP 存储 + 指标口径统一。
