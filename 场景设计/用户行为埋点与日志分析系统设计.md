# 用户行为埋点与日志分析系统设计（深入：SDK 协议 / 数据质量监控 / A/B 对接）

> 埋点是数据驱动的基础设施。本篇深入拆解：埋点 SDK 协议规范、数据质量自动化监控、A/B 实验平台对接、离线分析架构。

---

## 一、定位

```
端上埋点 → 网关收敛 → MQ 削峰 → 实时链路(Flink) + 离线链路(HDFS) 双写 → 指标服务

核心指标：不丢、低延迟、可回溯
```

---

## 二、埋点方式

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 代码埋点 | 开发者显式上报 | 精确、可控 | 侵入代码 |
| 可视化圈选 | 后台圈元素 | 免发版 | 动态元素难覆盖 |
| 无埋点（全量） | SDK 自动拦截 | 覆盖全 | 噪音大 |
| 服务端埋点 | 后端日志记录 | 可信 | 只看请求级 |

> 标准答案：代码埋点为主 + 圈选兜底 + 服务端关键事件双写。

## 三、SDK 协议规范（深入）

### 3.1 事件协议

```json
{
  "event_id": "uuid-v4",
  "event_type": "button_click",
  "event_time": 1692432000000,
  "client_time": "2026-08-19T10:00:00+08:00",
  "session_id": "sess_abc123",
  "user_id": "u_10086",
  "device_id": "dev_xyz789",
  "platform": "iOS",
  "app_version": "3.2.1",
  "os_version": "17.0",
  "device_model": "iPhone 15",
  "network_type": "WiFi",
  "ip": "192.168.1.100",
  "properties": {
    "page": "home",
    "element": "buy_button",
    "position": "bottom_right"
  }
}
```

### 3.2 关键字段

| 字段 | 说明 | 必填 |
|------|------|------|
| event_id | 唯一标识（UUID） | ✅ |
| event_type | 事件类型（button_click/page_view/expose） | ✅ |
| event_time | 事件发生时间（客户端时间戳） | ✅ |
| session_id | 会话标识（30min 超时切新） | ✅ |
| user_id | 用户 ID（登录态） | 登录后 |
| device_id | 设备 ID（匿名标识） | ✅ |
| properties | 业务属性（自定义 KV） | ✅ |

### 3.3 通用事件类型

| 事件 | 说明 | 关键属性 |
|------|------|----------|
| page_view | 页面浏览 | page, referrer, duration |
| expose | 元素曝光 | page, element, duration |
| button_click | 按钮点击 | page, element, position |
| search | 搜索 | keyword, result_count |
| purchase | 支付 | order_id, amount, sku_list |

## 四、采集链路架构

```
端上 SDK（批量压缩上报）
  → 埋点网关（校验+限流）
  → Kafka（削峰缓冲，按 user_id 分区）
  → Flink（实时清洗+聚合）→ Redis/OLAP（实时指标）
  → 离线落湖（HDFS/OSS，ODS 分区存储）→ 离线数仓（DWD/DWS）
  → 指标服务 + 分析平台 + 数据订阅（算法/风控）
```

## 五、数据质量监控（深入）

### 5.1 监控指标

| 指标 | 计算方式 | 告警阈值 |
|------|----------|----------|
| 丢失率 | 前端上报数 vs 网关接收数 | > 5% |
| 重复率 | event_id 去重后数量 vs 总数量 | > 1% |
| 延迟 | 事件发生时间 vs 入库时间 | > 30s |
| 脏数据率 | 非法事件数 / 总事件数 | > 10% |
| 覆盖率 | 关键页面曝光事件数 / 页面 PV | < 80% |

### 5.2 监控大盘

```
实时大盘（Grafana）：
  各层数据量对比（前端→网关→Kafka→Flink→OLAP）
  丢失率趋势
  重复率趋势
  延迟分布

告警规则：
  丢失率 > 5% → P1 告警
  重复率 > 1% → P2 告警
  延迟 > 30s → P2 告警
  脏数据率 > 10% → P3 告警
```

### 5.3 数据质量治理

```
预防：
  SDK 校验（必填字段/类型/格式）
  网关校验（时间偏差/字段白名单/签名校验）
  Flink 校验（业务规则/去重）

检测：
  实时监控大盘
  抽样对比（前端 vs 服务端 vs 网关）
  离线数据质量报告

修复：
  脏数据打标过滤（不进指标口径）
  丢失数据补发（离线补发机制）
  重复数据去重（event_id 唯一）
```

## 六、A/B 实验平台对接

### 6.1 对接流程

```
1. 实验平台配置实验（分流规则/指标/目标）
2. 端上 SDK 获取实验分组（调实验平台 API）
3. 埋点事件携带实验分组标识（experiment_id + group_id）
4. 数据分析时按分组聚合指标
5. 实验报告（显著性检验/置信区间）
```

### 6.2 事件协议扩展

```json
{
  "experiment": {
    "experiment_id": "exp_001",
    "group_id": "control",
    "exposure_time": 1692432000000
  }
}
```

## 七、面试答题框架

1. 需求澄清：采集什么事件？实时性？数据量级？
2. 埋点：代码埋点为主 + 圈选 + 服务端双写
3. 链路：SDK 批量压缩 → 网关 → Kafka → Flink 实时 + 离线双链路
4. 质量：event_id 去重 + 丢失检测 + 脏数据过滤 + 大盘监控
5. 分析：漏斗/留存/路径 + OLAP + 指标字典 + A/B 对接
