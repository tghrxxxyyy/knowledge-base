# 短连接设计

## 方法论

1. **随机 6 位**：通过 `while` 循环判断数据库中是否已存在该短码，不存在则插入。
2. **基于数据库自增主键**：`0-9a-zA-Z` 共 62 个字符，使用 62 进制生成 6 位短码。

在方法 2 下，如果需要支持分布式，则需保证全局唯一的序号，这种方式不够优雅。可以使用 `Hash(long_url) % 64` 作为 sharding key，生成的 `short_url` 为 `Hash(long_url) % 64 + short_url`。

缺点是 sharding 的机器少于 62 台。

## 三、短码生成算法对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 随机 6 位 | 62 进制随机，查重后插入 | 实现简单 | 高并发下冲突重试多 |
| 自增主键 | DB 自增 ID → 62 进制 | 无冲突、短 | 暴露总量/顺序 |
| 发号器 | 雪花 ID / Leaf-segment 预取号段 | 分布式、高性能 | 需独立服务 |
| 哈希取模 | `hash(url) % 62^n` | 同 URL 同码、可去重 | 哈希冲突、需兜底 |

## 四、分布式发号器

- **号段模式（Leaf-segment）**：DB 预分配号段（如每次取 1000 个），内存自增，DB 压力极低。

```java
// 号段模式核心
long nextId() {
    if (cursor > segmentMax) loadSegment(); // 从 DB 取 [segmentMin, segmentMax]
    return cursor++;
}
// 短码 = Long.toString(id, 62); // 10 进制转 62 进制
```

- **雪花算法**：时间戳 + 机器ID + 序列号，天然有序唯一，转 62 进制后长度短。

## 五、跳转实现

```java
// 302 临时跳转（便于统计点击；SEO 场景可用 301）
@RequestMapping("/{code}")
public void redirect(@PathVariable String code, HttpServletResponse resp) throws IOException {
    String url = shortUrlService.get(code);
    if (url == null) { resp.sendError(404); return; }
    resp.setStatus(302);
    resp.setHeader("Location", url);
}
```

- **301 vs 302**：301 永久重定向被浏览器缓存，不利于点击统计；302 每次回源可统计，短连接通常用 302。
- **防滥用**：短码需做频次限制、恶意 URL 检测（钓鱼/涉黄）。

## 七、踩坑与权衡
- **短码长度**：6 位 62 进制 ≈ 568 亿容量，足够；过长影响体验和品牌。
- **冲突兜底**：随机方案必须有 `unique` 约束 + 重试，防止并发插入重复。
- **安全**：短码可被枚举遍历，敏感活动链接需加签名或时效。
