# 短连接设计

## 方法论

1. **随机 6 位**：通过 `while` 循环判断数据库中是否已存在该短码，不存在则插入。
2. **基于数据库自增主键**：`0-9a-zA-Z` 共 62 个字符，使用 62 进制生成 6 位短码。

在方法 2 下，如果需要支持分布式，则需保证全局唯一的序号，这种方式不够优雅。可以使用 `Hash(long_url) % 64` 作为 sharding key，生成的 `short_url` 为 `Hash(long_url) % 64 + short_url`。

缺点是 sharding 的机器少于 62 台。

## 三、短码生成算法对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 随机 6 位 | 62 进制随机，查重后插入 | 实现简单 | 高并发下冲突重试多 |
| 自增主键 | DB 自增 ID → 62 进制 | 无冲突、短 | 暴露总量/顺序 |
| 发号器 | 雪花 ID / Leaf-segment 预取号段 | 分布式、高性能 | 需独立服务 |
| 哈希取模 | `hash(url) % 62^n` | 同 URL 同码、可去重 | 哈希冲突、需兜底 |

## 四、分布式发号器

- **号段模式（Leaf-segment）**：DB 预分配号段（如每次取 1000 个），内存自增，DB 压力极低。


## 五、跳转实现

```java
// 302 临时跳转（便于统计点击；SEO 场景可用 301）
@RequestMapping("/{code}")
public void redirect(@PathVariable String code, HttpServletResponse resp) throws IOException {
    String url = shortUrlService.get(code);
```

- **301 vs 302**：301 永久重定向被浏览器缓存，不利于点击统计；302 每次回源可统计，短连接通常用 302。
- **防滥用**：短码需做频次限制、恶意 URL 检测（钓鱼/涉黄）。

## 七、踩坑与权衡
- **短码长度**：6 位 62 进制 ≈ 568 亿容量，足够；过长影响体验和品牌。
- **冲突兜底**：随机方案必须有 `unique` 约束 + 重试，防止并发插入重复。
- **安全**：短码可被枚举遍历，敏感活动链接需加签名或时效。

## 八、短码生成深入：发号器 / 雪花 / Base62 / 哈希冲突

### 8.1 Base62 编码
62 个字符 `0-9a-zA-Z`，`id → 62 进制`：
```java
static final String DICT = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
String toBase62(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) { sb.append(DICT[(int)(id % 62)]); id /= 62; }
    return sb.reverse().toString();
}
```
6 位 62 进制容量为 `62^6 ≈ 5.68e10`，足够中小规模。

### 8.2 雪花 ID + Base62
雪花 ID（41bit 时间 + 10bit 机器 + 12bit 序列）转 62 进制约 11 位，过长。优化：**去掉高位时间戳的纪元偏移、压缩机器位**，或映射为"短序号服务"发放紧凑序号。

### 8.3 哈希取模冲突处理
`short = hash(url) % 62^6`，优点同 URL 同码便于去重；缺点哈希碰撞。兜底：
1. **唯一约束 + 重试**：插入冲突则 `hash(url)+salt` 再算，或追加自增后缀。
2. **布隆去重**：先查 URL 是否已映射，避免重复生成。

## 九、高并发发号

- **号段预取（Leaf-segment）**：DB 存 `max_id`，每次取 1000 号段放内存，DB 访问降到千分之一。
- **双 buffer 号段**：当前号段用至 10% 时异步预取下一段，无取号停顿。
- **Redis INCR**：`INCR short_code_seq` 当发号器，简单但 Redis 为瓶颈且需持久化防丢失。
- **多机房发号**：不同机房用不同号段基（如机房A:0, 机房B:1e9），避免跨机房协调。

```java
// 双 buffer 号段示意
class SegmentBuffer {
    Segment current, next;
    long nextId() {
        long id = current.cursor++;
        if (current.used() > 90% && next == null) next = loadNext();
        if (current.exhausted()) { current = next; next = null; }
        return id;
    }
}
```

## 十、301 / 302 与统计

- **302（默认）**：每次回源，可统计点击、可做 A/B 与权重跳转；浏览器不缓存。
- **301（永久）**：浏览器/CDN 缓存，省流量但无法统计、无法改目标，适合稳定长期链接。
- **统计写入**：跳转时异步写 Kafka（`code, ts, ip, ua, ref`），Flink 实时聚合 PV/UV；UV 用 HLL 近似。
- **308**：RFC 严谨的永久重定向（禁止改方法），部分场景替代 301。

## 十一、防刷与安全

- **频控**：按 IP/账号限流（`rate_limit:short:{ip}`），防批量枚举。
- **恶意 URL 检测**：接入安全引擎检测钓鱼/涉黄/木马下载，生成即拦截。
- **枚举遍历**：6 位短码可被遍历，敏感活动链接加签名（`/code?sign=hmac`）或时效。
- **防盗刷跳转**：跳转目标做域名白名单，防开放重定向（open redirect）被用作钓鱼跳板。

## 十二、缓存与存储选型

| 层 | 选型 | 说明 |
|----|------|------|
| 存储 | MySQL（短码→长链）+ 唯一索引 | 持久化、防重 |
| 缓存 | Redis（code→url，TTL 长） | 扛读热点，命中率>99% |
| 布隆 | RedisBloom / Guava | 快速判断 code 是否存在 |
| 统计 | Kafka + ClickHouse/Flink | 实时与离线分析 |
| CDN | 边缘缓存 302 | 降低源站压力 |

- **读多写少**：写入走 MySQL，读几乎全命中 Redis；冷数据可降级到对象存储。
- **容量**：10 亿短码 × (code 7B + url 200B) ≈ 200GB，MySQL 单表可分库按 code 哈希。

## 十三、踩坑与权衡（深入）

- **短码长度 vs 容量**：6 位够用但易枚举，敏感场景用 8 位 + 签名。
- **301 缓存不可逆**：一旦 301，用户浏览器长期缓存，改目标需换码，慎用于活动。
- **发号器持久化**：号段未持久化前宕机丢失号段（不影响已发，但浪费），需 WAL 或定期 checkpoint。

## 十四、短码防遍历与完整服务骨架

### 防遍历增强
- **不可枚举空间**：用「随机 62 进制 + 校验位」让短码无规律，遍历无法命中有效码。
- **速率限制**：单个 IP/账号每分钟最多生成/访问 N 次，超过返回 429。
- **签名校验**：敏感活动 `/{code}?sign=hmac(url, key)`，无签名直接 404。
- **失效机制**：活动结束的短码置为失效，访问返回 410。

```go
## 十五、短链高可用与存储分库

- **高可用**：短链服务无状态，多实例 + LB；Redis 主从 + 哨兵，MySQL 主从。
- **存储分库**：按 `code` 哈希分 16 库，单库 SKU 量级可控；热点码走 Redis 抗压。
- **降级**：Redis 不可用时降级读 MySQL（RT 升高但可用）；MySQL 不可用时返回 503 并限流。
- **缓存更新**：长链变更（极少见）时删 Redis 并异步刷新，短链本质是"写少读多"。
- **容量回收**：过期/失效短码定期归档到冷存储，热表保持精简以保证查询 RT。

## 十六、短链安全审计与合规

- **生成审计**：谁在何时生成了哪个短码，留痕便于溯源恶意短链。
- **目标域名白名单**：跳转目标必须属于受信域名，防止开放重定向被用于钓鱼。
- **恶意检测**：生成时调安全引擎扫描目标 URL（病毒/钓鱼/涉黄），命中即拦截。
- **定期巡检**：扫描存量短码，发现被滥用（如指向违规站点）的批量失效。
- **合规**：营销短链带活动编号，满足广告法对"可识别推广"的要求。

## 十七、常见面试题

- **短码用尽怎么办？** 6 位 62 进制约 568 亿，常态用不完；真用尽则扩到 7-8 位或复用已失效码。
- **如何用 Redis 保证不重复？** `SET code url NX` 原子插入，冲突返回已存在，配合号段发号器几乎不冲突。
- **301 还是 302？** 统计/可变更用 302；永久固定用 301，但注意浏览器缓存不可逆。
- **高并发发号瓶颈？** 号段预取 + 双 buffer，把 DB 访问降千倍；多机房用不同号段基避免协调。
```
