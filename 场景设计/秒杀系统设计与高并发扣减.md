# 秒杀系统设计与高并发扣减

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、秒杀的核心矛盾

秒杀 = 瞬时海量请求（读多写少，但写集中在极少商品） vs 有限的库存与数据库吞吐。核心矛盾：

- 流量远超系统常态（平时 1 万 QPS，秒杀瞬间 100 万 QPS）。
- 库存有限，超卖是绝对红线。
- 大多数请求注定失败（库存 100 件，100 万人抢），要把「无效的请求」尽早拦截。

> 设计哲学：把压力层层拦在前面（CDN → 网关 → 缓存 → 异步队列），只有极少请求真正落库。

## 二、整体架构分层

```
用户 → CDN/静态页 → 网关(限流/鉴权) → 秒杀服务(缓存校验) → MQ(削峰) → 订单 Worker(落库扣减)
```

1. **静态资源-CDN**：商品详情页、图片走 CDN，不回源。
2. **网关层**：统一限流（令牌桶）、黑名单、防刷。
3. **缓存层（Redis）**：库存预热到 Redis，抢购在 Redis 原子扣减。
4. **MQ 削峰**：扣减成功才发消息，订单异步创建，平滑数据库压力。
5. **数据库**：只承接真正成单的少量写。

## 三、库存扣减方案对比

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| 数据库直接扣 | `UPDATE stock SET n=n-1 WHERE n>0` | 简单，但 DB 抗不住高并发 |
| Redis 原子扣 | `DECR` / Lua 脚本 | 高性能，需保证与 DB 一致 |
| 预扣 + 异步 | Redis 预扣，MQ 落库 | 削峰，最终一致 |

- **Redis + Lua 原子扣减**（推荐）：

```lua
-- KEYS[1]=stock_key  ARGV[1]=扣减数  ARGV[2]=用户限购标记key前缀
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -2 end
if stock >= tonumber(ARGV[1]) then
  redis.call('DECRBY', KEYS[1], ARGV[1])
  return stock - tonumber(ARGV[1])
else
  return -1   -- 库存不足
end
```

> Lua 保证「判断+扣减」原子，避免超卖。

## 四、防超卖的关键

- **Redis 预扣**：先扣 Redis，扣成功才进 MQ。
- **数据库兜底**：落库时再次 `WHERE stock>=1` 校验，双保险。
- **库存回滚**：用户下单未支付超时，定时任务把库存加回 Redis 与 DB。
- **不信任前端**：前端减库存只是展示，真正以服务端扣减为准。

## 五、流量削峰

- **答题/验证码**：增加操作成本，错峰 + 防脚本。
- **排队**：进 MQ 排队，用户看到「排队中」，而非瞬间全打进来。
- **令牌桶限流**：网关按商品维度限流，超出直接快速失败。
- **熔断**：下游（订单服务）异常时快速失败，保护整体。

### 5.1 用户维度限购（Redis 标记）

```lua
-- 同一用户只能抢一次
if redis.call('EXISTS', 'seckill:user:'..ARGV[1]) == 1 then return -3 end
redis.call('SET', 'seckill:user:'..ARGV[1], 1, 'EX', 3600)
```

## 六、热点数据处理

- **热点商品独立分片**：把爆款库存单独 Redis 实例，避免大 key 拖累。
- **本地缓存**：库存兜底读本地缓存，Redis 挂了能挡一阵。
- **库存拆分**：把 100 件拆成 10 个 10 件子库存，分散竞争。

```java
// 库存分段：将总量拆成 N 段，用户随机打到一个段，降低单 key 竞争
int segment = ThreadLocalRandom.current().nextInt(SEGMENT_COUNT);
String segKey = "seckill:stock:" + itemId + ":" + segment;
```

## 七、异步化与最终一致

```
Redis 扣减成功 → 发 MQ「创建订单」→ Worker 消费 → 落 DB → 返回用户
```

- 用户抢到后进入「待支付」，超时未付回滚库存。
- 用「预扣减 + 延时消息」实现自动关单回库存。

```java
// RocketMQ 延时消息实现关单（示意）
Message msg = new Message("seckill_order_close", orderId.getBytes());
msg.setDelayTimeLevel(16);  // 对应 30 分钟级别延时
producer.send(msg);
```

## 八、防刷与防黄牛

- 用户维度限频（同一用户 N 秒内只能抢 1 次）。
- 设备指纹 / 行为风控（异常设备、脚本特征）。
- 风控规则引擎实时拦截。

## 九、降级方案

- Redis 挂：降级到「库存文件 + 本地锁」或临时关闭秒杀。
- DB 慢：丢弃非核心请求，保核心扣减链路。
- 超卖保护：宁可少卖（少放几个），不可超卖。

## 十、容量评估

- 预估 QPS = 在线用户 × 点击率 / 活动时长。
- 压测：单接口、全链路压测，找到瓶颈点（通常是 Redis 或 DB）。
- 扩容：Redis 集群、订单服务横向扩容、MQ 堆积缓冲。

### 10.1 压测关注指标

| 指标 | 说明 |
|------|------|
| QPS / TPS | 系统吞吐上限 |
| P99 延迟 | 长尾用户体验 |
| 错误率 | 限流/超卖/超时占比 |
| Redis CPU | 单实例是否打满 |
| MQ 堆积 | 削峰是否生效 |

## 十一、常见坑

1. 直接打 DB 扣库存 → 数据库被打死。
2. 扣减非原子 → 超卖。
3. 不做限流 → 无效请求淹没有效请求。
4. 库存不回滚 → 用户不付钱，商品「消失」。
5. 前端信任 → 被脚本刷单超卖。
6. 热点 key 集中 → Redis 单点瓶颈。
7. 关单不及时 → 库存长期被占用，真实用户抢不到。

## 十二、落地清单

1. 静态化 + CDN。
2. 网关限流 + 防刷。
3. Redis 预热 + Lua 原子扣减。
4. MQ 削峰 + 异步落库。
5. DB 兜底校验。
6. 超时回滚 + 风控。
7. 全链路压测 + 降级预案。
