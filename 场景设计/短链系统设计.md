# 短链系统设计（短网址）

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、短链要解决什么

长 URL（带参数、追踪标识）不利于分享（短信、二维码、字数限制）。短链服务把长 URL 映射成短字符串（如 `t.cn/abc123`），访问时 301/302 跳转到原地址。

- 核心需求：高可用、低延迟、可统计点击、可自定义。
- 规模：亿级短链、千亿级跳转。

## 二、核心流程

```
用户访问 short.com/abc123 → 查映射 → 302 跳转原 URL（并记录点击）
生成：长 URL → 算短码 → 存映射 → 返回 short.com/短码
```

## 三、短码生成方案

| 方案 | 说明 | 优缺点 |
|------|------|--------|
| 自增 ID + Base62 | 全局发号器转 62 进制 | 短、顺序，但易猜测 |
| Hash（MD5/雪崩） | 长 URL 哈希再截断 | 可能冲突，需去重 |
| 随机串 | 随机 6~8 位 | 冲突概率低，但需查重 |
| 分布式发号（Snowflake） | 全局唯一 ID 转 Base62 | 无中心瓶颈，码较长 |

- **Base62 编码**：62 个字符（0-9a-zA-Z），6 位可表示 62^6 ≈ 568 亿，足够。

```python
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def base62(n):
    s = ""
    while n:
        s = ALPHABET[n % 62] + s
        n //= 62
    return s or "0"
```

## 四、冲突处理

- 短码已存在（Hash/随机方案）→ 重试新码或加 salt 再哈希。
- 用布隆过滤器快速判存在，再查 DB 确认。
- 自增/发号方案天然不冲突。

## 五、存储选型

- **映射表**：短码 → 长 URL + 创建时间 + 过期时间。
- **存储**：MySQL（主） + Redis（热短码缓存，扛跳转读）。
- **跳转读多写少**：Redis 缓存命中率高，DB 仅兜底。

## 六、301 vs 302

- **301 永久跳转**：浏览器缓存，省服务器流量，但点击统计难（浏览器不重复请求）。
- **302 临时跳转**：每次回源，便于统计点击，但服务器压力大。
- 统计场景用 302；纯省流量用 301。

## 七、高可用设计

- 跳转服务多机房部署，DNS 轮询。
- Redis 集群缓存热短码。
- 生成服务无状态，水平扩展。
- 降级：Redis 挂时直接查 DB（慢但可用）。

## 八、安全与风控

- 防短链钓鱼：扫描目标 URL 是否恶意，命中黑名单拒绝生成。
- 防滥用：限频（单用户生成速率）、验证码。
- 有效期：临时短链设过期，自动清理。

## 九、统计与扩展

- 点击日志 → 离线数仓 → 报表（来源、地域、设备）。
- 自定义短码（品牌词）需查重 + 付费。
- A/B 跳转：同一短码按规则跳不同落地页。

## 十、容量与性能

- 跳转延迟目标 < 50ms，靠 Redis 缓存。
- 写（生成）量远小于读（跳转），异步化统计写入。

## 十一、常见坑

1. 用 301 又想统计 → 数据缺失，改 302 或前端打点。
2. 短码可猜测 → 被遍历扫全库，加随机性。
3. 不做缓存 → 跳转打爆 DB。
4. 恶意短链 → 钓鱼传播，需 URL 安全扫描。
5. 发号器单点 → 用 Snowflake/号段避免。

## 十二、落地清单

1. 选短码方案（Base62 + 发号/随机）。
2. 存储 MySQL + Redis 缓存。
3. 跳转用 302（要统计）并异步记日志。
4. 冲突去重 + 布隆过滤。
5. URL 安全扫描防钓鱼。
6. 多机房 + 降级。
