# 短链系统设计（短网址 / Short URL）

> 板块：场景设计 　|　 返回：[README](README.md)
> 适用：营销短信、二维码、社交分享、渠道追踪、A/B 落地页等需要「长 URL 变短」的场景。

## 一、短链要解决什么

长 URL 通常带有追踪参数、会话标识、utm 字段，长度可达数百字符，直接分享会带来问题：

- **字数限制**：短信按条计费，长链接浪费字符；微博/Twitter 历史上有 140 字限制。
- **二维码密度**：URL 越长，二维码越密、越难扫。
- **可读性 & 品牌**：`t.cn/AbCdEf` 比 `https://shop.example.com/...&utm_source=...` 干净。
- **可统计**：集中跳转点天然成为点击埋点入口，可做来源/地域/设备分析。
- **可管控**：链接可随时失效、可重定向到新地址（不改对外卡片）。

短链服务的本质是 **一个高可用、低延迟、可观测的「短码 → 长 URL」映射 + 跳转 + 统计系统**。

| 维度 | 量级（典型中大型） |
|------|------|
| 已存短链数 | 亿级 |
| 日均跳转（302） | 百亿 ~ 千亿级 |
| 读:写 | 100:1 甚至 1000:1 |
| 跳转 P99 延迟目标 | < 50ms |
| 可用性目标 | 99.99% |

> 读多写少、映射关系简单、可缓存、可水平扩展 —— 这是短链系统的几个关键工程特征。

## 二、核心流程

```
【生成链路】
用户输入长 URL
  → 校验 & 安全扫描（黑名单 / 恶意站点）
  → 生成短码（算法见第三节）
  → 持久化映射（短码 → 长 URL + 元数据）
  → 返回 short.com/短码

【跳转链路】
用户访问 short.com/abc123
  → 本地/Redis 缓存查映射（命中直接跳）
  → 未命中查 DB（并回写缓存）
  → 302 跳转原 URL
  → 异步写点击日志（不阻塞跳转）
```

跳转必须 **不阻塞业务**，统计写入异步化（消息队列 / 本地缓冲落盘）。

## 三、短码生成方案（核心设计点）

短码本质是「把一个长字符串压缩成一段短、唯一、尽量不可预测的字符串」。

### 3.1 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 自增 ID + Base62 | 全局发号器生成连续 ID，转 62 进制 | 码极短、无冲突 | 顺序可猜测、易遍历 | 内部/非安全场景 |
| Hash 截断（MD5/SHA1/Murmur） | 长 URL 哈希后取前 N 位 | 无需发号、分布均匀 | 哈希冲突、需去重 | 高并发写入 |
| 随机串（纳秒+随机） | 随机 6~8 位字符 | 不可预测、冲突低 | 需查重、可能碰撞 | 对外营销 |
| Snowflake + Base62 | 分布式 ID（时间戳+机器+序列）转 62 | 无中心瓶颈、有序 | 码较长、含时间信息 | 大规模分布式 |
| 号段发号（Segment） | 每次从 DB 取一段 ID 缓存本地 | 减少 DB 压力 | 需管理号段、重启浪费 | 高吞吐生成 |

### 3.2 Base62 编码

62 个字符（`0-9a-zA-Z`），6 位可表示 `62^6 ≈ 568 亿`，7 位约 `3.5 万亿`，一般 6~7 位足够。

```python
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def base62(n: int) -> str:
    if n == 0:
        return "0"
    s = ""
    while n:
        s = ALPHABET[n % 62] + s
        n //= 62
    return s

# 62 进制反转
def base62_decode(s: str) -> int:
    n = 0
    for c in s:
        n = n * 62 + ALPHABET.index(c)
    return n
```

> 注意：标准 Base62 大小写敏感，为避免用户手输混淆，有些实现「去除易混字符」（如 0/O、1/l/I），但会减少可用字符空间，需相应加长位数。

### 3.3 哈希方案（带去重）

```java
// 用 MurmurHash3 减少 MD5 的碰撞与长度
long h = Hashing.murmur3_128().hashBytes(longUrl.getBytes(UTF_8)).asLong();
String code = base62(Math.abs(h));   // 可能需补位到固定长度
// 若 code 已存在 → 拼接 salt（如 userId 或随机数）重新哈希，直到不冲突
```

### 3.4 号段/雪花发号（推荐大规模）

```java
// 号段模式：从 DB 取 [start, end)，本地递增分配，用完再取
class IdGenerator {
    private long current, end;
    synchronized long next() {
        if (current >= end) allocateSegment();   // 从DB拿新号段
        return current++;
    }
}
// 生成短链时：code = base62(nextId())
```

## 四、冲突处理

- **哈希/随机方案**天然可能冲突：写入前用「布隆过滤器 + DB 唯一索引」双重防护。
  - 布隆过滤器快速判「大概率不存在」→ 直接写；
  - DB 唯一索引兜底，插入失败则换码重试（加 salt 或递增后缀）。
- **自增/发号方案**天然不冲突，无需去重，但短码可预测。
- 重试上限（如 5 次）后告警，避免死循环。

```sql
-- 短码唯一索引是最后防线
ALTER TABLE short_url ADD UNIQUE KEY uk_code (code);
-- 插入冲突时应用层捕获 DuplicateKeyException，换码重试
```

## 五、存储选型与表结构

### 5.1 关系模型（MySQL 主存储）

```sql
CREATE TABLE short_url (
    id          BIGINT      PRIMARY KEY AUTO_INCREMENT,
    code        VARCHAR(10) NOT NULL,          -- 短码
    long_url    VARCHAR(2048) NOT NULL,        -- 原长 URL
    creator_id  BIGINT      DEFAULT NULL,      -- 创建者（可选）
    status      TINYINT     NOT NULL DEFAULT 1,-- 1有效 2失效 3违规
    expire_at   DATETIME    DEFAULT NULL,      -- 过期时间（NULL=永久）
    created_at  DATETIME    NOT NULL,
    UNIQUE KEY uk_code (code),
    KEY idx_created (created_at)
) ENGINE=InnoDB;

CREATE TABLE click_log (
    id          BIGINT      PRIMARY KEY AUTO_INCREMENT,
    code        VARCHAR(10) NOT NULL,
    ip          VARCHAR(45),
    ua          VARCHAR(512),
    referer     VARCHAR(512),
    country     VARCHAR(16),
    created_at  DATETIME    NOT NULL,
    KEY idx_code_time (code, created_at)
) ENGINE=InnoDB;  -- 可按月分表，异步写入
```

### 5.2 缓存层级（跳转读多写少）

```
跳转请求
  → 1) 本地缓存（Caffeine/Guava，进程内，毫秒级，存热点）
  → 2) Redis 集群（分片，存全量热+温数据）
  → 3) MySQL（兜底）
```

- Redis 缓存结构：`code → long_url`（带 TTL，与过期时间对齐）。
- 本地缓存容量有限，靠 LRU 淘汰；Redis 扛主流量。
- 命中率可达 99%+，DB 几乎只承接未命中与写。

```bash
# 伪：跳转读路径
url = localCache.get(code)
if url == null:
    url = redis.get(code)
    if url == null:
        url = db.query("SELECT long_url FROM short_url WHERE code=?", code)
        redis.setex(code, 3600, url)   # 回写
    localCache.put(code, url)
return redirect(url)   # 302
```

## 六、301 vs 302（跳转语义）

| 跳转 | 语义 | 浏览器行为 | 统计影响 | 何时用 |
|------|------|-----------|---------|--------|
| 301 | 永久移动 | 浏览器/CDN 缓存，后续不再请求短链服务器 | 统计丢失（不重复回源） | 纯省流量、确定永不改 |
| 302 | 临时移动 | 每次回源短链服务器 | 统计完整 | **需要点击统计**（绝大多数场景） |
| 307/308 | 同 302/301 但禁止改方法 | 更严格 | 同 302/301 | 需保留 POST 等 |

> 实践中营销/统计场景几乎都用 **302**；若只想省流量且长 URL 永不变，用 301。也可用「首次 302 统计、确认稳定后变 301」的混合策略（少数实现）。

## 七、高可用设计

```
                  DNS 多机房
                       │
        ┌──────────────┼──────────────┐
   接入层(无状态)   接入层(无状态)   接入层(无状态)
        │                │                │
   Redis集群(分片)  Redis集群(分片)  Redis集群(分片)
        │                │                │
      MySQL主从      MySQL主从       MySQL主从
```

- **接入层无状态**：水平扩展，前面挂 LVS/SLB，DNS 轮询多机房。
- **Redis 集群**：Codis/Redis Cluster，缓存短码映射，扛跳转读。
- **DB 主从**：写主库、读从库；跳转读走从库/缓存。
- **降级**：
  - Redis 挂 → 直接查 DB（慢但可用）；
  - DB 挂 → 本地缓存仍可服务热点；
  - 生成服务挂 → 跳转不受影响（读链路独立）。
- **限流**：单 IP/单用户生成频控，防刷短链。

## 八、安全与风控

短链是「用户可控制的跳转入口」，易被用于钓鱼/诈骗，必须治理：

1. **URL 安全扫描**：生成时异步调用安全引擎（或第三方威胁情报），命中黑名单/恶意站点拒绝生成并标记。
2. **防开放重定向（Open Redirect）**：短链只跳转到已登记的长 URL，绝不接受运行期参数拼接跳转目标。
3. **防遍历**：短码不可预测（随机/哈希），避免被人 `t.cn/a00001~a99999` 扫全库。
4. **滥用防控**：生成频控 + 图形验证码 + 设备指纹；异常批量生成告警。
5. **有效期与回收**：临时活动短链设 expire_at，到期自动失效并回收码（注意回收后不可立即复用，防「码复用攻击」）。
6. **内容举报**：用户举报 → 机审+人审 → 违规短链秒级下线。

## 九、统计与扩展能力

- **点击日志**：跳转时异步写 `click_log`，经 MQ 落库/数仓。
- **实时指标**：Kafka → Flink → 实时大屏（实时点击、地域分布、渠道来源）。
- **离线报表**：按天/周聚合，输出来源、设备、地域、转化率。
- **自定义短码**：品牌词（如 `t.cn/SpringSale`），生成前查重，可付费/白名单。
- **A/B 跳转**：同一短码按权重/人群跳不同落地页，用于投放实验。
- **UTM 自动注入**：跳转时在原 URL 追加 `utm_source=short&utm_medium=...` 便于归因。
- **二维码**：短码直接生成二维码，扫码即跳转（短码让二维码更稀疏易扫）。

## 十、容量与性能

| 指标 | 目标 / 手段 |
|------|------------|
| 跳转延迟 P99 | < 50ms，靠本地缓存 + Redis |
| 缓存命中率 | > 99%，长尾未命中走 DB |
| 写吞吐 | 号段/Snowflake 发号，避免单点 |
| 存储增长 | 短链表 + 点击日志按月分表/分区 |
| 带宽 | 跳转响应极轻（仅 header），CDN 可扛 |

## 十一、真实案例参考（公开资料）

- **微博 t.cn**：早期用自增 ID + Base62，后演进为分布式发号。
- **bit.ly**：对外短链服务，强调点击分析与品牌短码。
- **百度 dwz.cn / 腾讯 url.cn**：均是高可用短链服务，跳转链路独立部署。
- 技术上无秘密，难点在「高并发跳转 + 统计不丢 + 安全治理」三者兼顾。

## 十二、常见坑

1. 用 301 又想统计 → 数据缺失，改 302 或前端打点。
2. 短码可猜测 → 被遍历扫全库，加随机性/哈希。
3. 不做缓存 → 跳转打爆 DB，必须本地 + Redis 双层缓存。
4. 恶意短链 → 钓鱼传播，需 URL 安全扫描 + 举报下线。
5. 发号器单点 → 用 Snowflake/号段避免；号段重启浪费需容忍。
6. 码回收后立即可用 → 被「旧链接复用」攻击，应延迟回收或标记。
7. 长 URL 长度未限制 → 超长 URL 撑爆字段，需截断/报错。
8. HTTPS 跳转回 HTTP → 混合内容告警，统一跳转 https。
9. 统计写入阻塞跳转 → 跳转变慢，务必异步化。
10. 跨机房缓存不一致 → 失效用主动失效（发布/删除时清缓存）。

## 十三、落地清单

1. 选短码方案（Base62 + 号段/Snowflake，或哈希+去重）。
2. 存储 MySQL + Redis 双层缓存 + 本地缓存。
3. 跳转用 302（要统计）并异步记日志。
4. 冲突去重 + 布隆过滤 + 唯一索引。
5. URL 安全扫描 + 开放重定向防护。
6. 多机房 + 分级降级 + 生成限流。
7. 点击统计链路（MQ + 数仓 + 实时）。
8. 监控：跳转延迟、命中率、缓存命中、生成失败率。
