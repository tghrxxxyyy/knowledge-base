# 延时任务与定时调度

> 板块：场景设计 　|　 返回：[README](README.md)

延时任务（30 分钟后关单）与定时调度（每天报表）是业务系统的高频需求。二者看似简单，要做到可靠、不丢、不重、可扩展却有不少坑。本文对比方案、剖析实现、给出可靠性要点与反模式。

## 一、需求分类

### 1.1 定时任务（Cron）

- 周期性触发：每天 0 点跑批、每小时统计。
- 特征：时间点已知、可预测。

### 1.2 延时任务（Delayed）

- 相对当前某段时间后触发：下单 30 分钟未支付关单、优惠券到期提醒。
- 特征：触发时间随业务事件产生，分散、动态。

很多场景二者混合：异步重试用"递增延时"重投（退避）。

## 二、定时调度方案

| 方案 | 特点 | 适用 |
|------|------|------|
| cron / 系统定时器 | 单机简单，无分布式 | 单机脚本 |
| Quartz | Java 老牌，集群模式（DB 锁） | 传统 Java 应用 |
| XXL-JOB | 分布式调度，分片、失败重试、可视化 | 企业 Java |
| Airflow / DolphinScheduler | 数据 DAG 调度，依赖编排 | 大数据/ETL |
| K8s CronJob | 云原生定时任务，天然容器化 | K8s 环境 |
| Spring @Scheduled | 轻量，单机 | 小应用 |

分布式调度的关键能力：
- **分片**：大数据任务拆分到多节点并行。
- **失败重试**：任务失败自动重跑。
- **幂等**：同一任务可能因重试被多次执行。
- **故障转移**：某节点挂了，任务漂到其他节点。

## 三、延时任务方案

### 3.1 消息队列延时

- **RocketMQ 延时消息**：内置 18 级延时级别，开箱即用；需发半消息/延迟级别。
- **RabbitMQ 死信队列（DLX）**：消息设 TTL，过期进死信队列被消费；精度取决于 TTL 粒度。
- **Kafka**：无原生延时，需外部时间轮/另起定时转发。

### 3.2 时间轮（Timing Wheel）

- 高效管理海量定时任务，复杂度 O(1) 添加与触发。
- Netty 的 `HashedWheelTimer`、Kafka 内部用到分层时间轮。
- 适合"大量短延时"场景（如连接超时、请求重试）。

### 3.3 Redis ZSet

- `score` 存触发时间戳，`ZRANGEBYSCORE 0 now` 取到期任务。
- 多 worker 用 `ZPOPMIN` / Lua 原子取走防重复。
- 简单直观，适合中小规模。

```redis
ZADD delay_queue <trigger_ts> <task_id>
# 轮询线程：
ZRANGEBYSCORE delay_queue 0 <now> LIMIT 0 100
# 取出后处理并 ZREM（建议 Lua 原子）
```

### 3.4 DB 轮询

- 任务表带 `trigger_time`，定时扫 `WHERE trigger_time <= now AND status=pending`。
- 简单、可靠，但高频扫描压力大，适合低频（每分钟级）。

### 3.5 专业定时组件

- 如基于时间轮的调度框架、Quartz 的 `SimpleTrigger` 配 `repeatInterval`。

## 四、可靠性要点

### 4.1 至少一次语义

- 任务可能重复触发 → **业务必须幂等**（见 [分布式锁与幂等设计](分布式锁与幂等设计.md)）。
- 用任务唯一 ID 去重表 / Redis SETNX。

### 4.2 失败重试与退避

- 处理失败用指数退避（1s→2s→4s...）重投更晚的延时。
- 超限进死信队列 / 人工处理，避免无限重试。

### 4.3 时钟问题

- 多机用 NTP 同步；绝对时间判断用 NTP 校准后的时钟。
- 避免用本机时钟做绝对判断；衡量"间隔"用单调时钟（如 Java `System.nanoTime()` 仅用于间隔，不可用于绝对时间）。
- 时钟回拨会导致任务提前触发或永久不触发（ZSet score 错乱）。

### 4.4 分片与扩展

- 大量任务按 `hash(task_id) % N` 分配到多 worker 分片。
- 单 worker 故障，其分片由其他 worker 接管。

### 4.5 触发延迟

- 轮询间隔决定最大延迟（如每 1s 扫一次，最坏延迟 1s）。
- 队列积压会把"延时"变"很晚"，需监控积压与处理耗时。

## 五、与业务结合

### 5.1 关单回库存

下单成功 → 发延时消息（30min）→ 消费时若**仍未支付** → 关单 + 回库存。
注意：支付成功会先取消该延时任务（若支持）或消费时校验已支付则跳过。

### 5.2 重试队列

处理失败 → 发更长延时消息（退避）→ 再试；超过阈值转死信。

### 5.3 优惠券到期

券到期前发提醒延时任务；到期发"失效"处理任务。

## 六、常见坑

1. **用 sleep 做延时** → 进程/线程重启任务丢，不可靠。
2. **单线程轮询 DB** → 量上来就慢，且无法水平扩展。
3. **不幂等** → 延时消息重投重复执行（关单两次、退款两次）。
4. **队列积压** → 任务触发严重延迟，失去"延时"意义。
5. **时钟回拨** → 任务提前触发或永久不触发。
6. **忽略失败处理** → 任务失败即丢失，无兜底。
