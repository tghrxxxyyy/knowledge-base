# 延时任务与定时调度

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、需求场景

订单 30 分钟未支付自动关单、优惠券到期提醒、异步重试退避、定时报表。两类：定时（cron）与延时（未来某刻触发）。

## 二、定时调度方案

| 方案 | 特点 |
|------|------|
| cron / 系统定时器 | 单机简单，无分布式 |
| Quartz / XXL-JOB | Java 分布式调度，分片、失败重试 |
| Airflow / DolphinScheduler | 数据 DAG 调度 |
| K8s CronJob | 云原生定时任务 |

## 三、延时任务方案

- **消息队列延时**：RocketMQ 延时消息、RabbitMQ 死信队列（TTL+DLX）、Kafka 用时间轮/外部计时。
- **时间轮（Timing Wheel）**：Netty/HashedWheelTimer，高效管理大量定时。
- **Redis ZSet**：score=触发时间戳，轮询 `ZRANGEBYSCORE` 取到期任务。
- **DB 轮询**：扫描到期行，简单但慢，适合低频。

```redis
# 用 ZSet 实现延时队列
ZADD delay_queue <trigger_ts> <task_id>
# 轮询线程：
ZRANGEBYSCORE delay_queue 0 <now> LIMIT 0 100
# 取出后处理，ZREM
```

## 四、可靠性要点

- **至少一次**：任务可能重复触发 → 业务幂等（见 [分布式锁与幂等设计](分布式锁与幂等设计.md)）。
- **失败重试**：指数退避，超限进死信/人工。
- **时钟**：多机用 NTP 同步；避免用本机时钟做绝对判断（用单调时钟衡量间隔）。
- **分片**：大量任务按分片分配到多 worker，避免单点。

## 五、与业务结合

- 关单回库存：下单成功 → 发延时消息（30min）→ 消费时若仍未支付 → 关单 + 回库存。
- 重试：处理失败 → 发更长延时消息 → 再试。

## 六、常见坑

1. 用 sleep 做延时 → 进程重启任务丢。
2. 单线程轮询 DB → 量上来就慢。
3. 不幂等 → 延时消息重投重复执行。
4. 队列积压 → 任务触发严重延迟。
5. 时钟回拨 → 任务提前/永久不触发。
