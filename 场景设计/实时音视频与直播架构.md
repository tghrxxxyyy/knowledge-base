# 实时音视频与直播架构

> 板块：场景设计 　|　 返回：[README](README.md)
> 适用：直播、音视频通话、低延迟互动、监控推流。

音视频架构区别于普通 Web：关注**低延迟、弱网对抗、海量并发下行**。核心是推流、转码、分发（CDN）、播放四段。

## 一、直播基础链路

```
主播 → 推流(RTMP/SRT) → 接入层 → 转码/混流 → 切片/HLS 或 低延迟(WebRTC/FLV)
                                              ↓
                                        CDN 分发 → 观众拉流播放
```

- **推流协议**：RTMP（成熟）、SRT（抗丢包）、WebRTC（超低延迟）。
- **播放协议**：HLS（兼容好、延迟高 3–10s）、HTTP-FLV（2–5s）、WebRTC（<1s，互动直播）。
- **转码**：一路原流转多码率，适配不同网络。

## 二、低延迟直播（LL-HLS / WebRTC）

- 传统 HLS 切片导致秒级延迟，互动场景（带货、连麦）需 <1s。
- WebRTC：UDP + ICE/STUN/TURN，端到端低延迟，但并发规模受限（适合小规模互动）。
- LL-HLS：缩短分片（如 0.5s）+ 部分分片预推，延迟降到 2s 内。

## 三、CDN 分发

- 边缘节点就近拉流，观众从最近节点获取，降低延迟与源站压力。
- 大规模直播靠 CDN 多节点扇出（一对多下行）。
- 回源策略：边缘未命中向上回源，源站做热流合并。

## 四、连麦与混流

- **连麦**：多人实时音视频，WebRTC 级联或 SFU 转发。
- **混流**：服务端把多路混成一路再分发，降低观众端复杂度（但增加服务端算力）。
- **SEI 消息**：在视频流中插入时间戳/互动指令（如点赞特效同步）。

## 五、弱网对抗

- **丢包重传（NACK）**、**前向纠错（FEC）**：丢包时恢复。
- **自适应码率（ABR）**：根据带宽动态降/升码率。
- **抖动缓冲（Jitter Buffer）**：平滑网络抖动。

## 六、监控指标

| 指标 | 说明 |
|------|------|
| 首帧时间 | 观众看到画面的延迟 |
| 卡顿率 | 播放中断比例 |
| 端到端延迟 | 主播到观众的时延 |
| 推流稳定性 | 断流/重连次数 |
| 码率/帧率 | 画质与流畅度 |

## 七、常见坑

1. **用 HLS 做互动直播** → 延迟高，连麦不同步；改用 WebRTC/LL-HLS。
2. **源站直扛下行** → 带宽/连接爆；必须 CDN 分发。
3. **不做弱网对抗** → 移动端卡顿；FEC/NACK/ABR。
4. **转码集群不足** → 推流排队；弹性扩容 + 预热。
5. **无监控** → 故障发现晚；全链路指标 + 告警。
6. **混流算力浪费** → 非必要不混流，用 SFU 转发省算力。
