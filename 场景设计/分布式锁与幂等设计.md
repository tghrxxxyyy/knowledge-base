# 分布式锁与幂等设计

> 板块：场景设计 　|　 返回：[README](README.md)

分布式系统下，多实例并发操作同一资源（扣库存、发奖励、跑定时任务），需要两类保障：**互斥**（同一时刻只有一人能操作）与**幂等**（重复执行结果一致）。二者常被混淆，但解决不同问题。本文系统拆解。

## 一、为什么需要

- 多实例部署：原来单进程的 synchronized/锁失效（跨 JVM）。
- 并发操作共享资源：库存、账户、优惠券、任务调度。
- 网络不可靠：请求可能重试、消息可能重投、用户可能重复点击。

两件事要分开想：
- **锁**：保证"互斥"，同一时刻只一人改。
- **幂等**：保证"重复无害"，多次执行不等于多次效果。

## 二、分布式锁方案

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| Redis `SET NX EX` | 单命令加锁 | 简单、快 | 主从切换可能双持锁 |
| Redlock | 多节点多数派 | 更稳 | 争议（fencing 问题） |
| ZooKeeper | 临时顺序节点 | 可靠、可重入 | 重、依赖 ZK |
| 数据库唯一约束 | 唯一索引抢行 | 简单 | 依赖 DB、性能限 |
| etcd | 租约 + 事务 | CP、可靠 | 需维护 etcd |

### 2.1 Redis 锁要点

- `SET key token NX EX seconds`：不存在才设、带过期，一步完成（避免 `SETNX` 后 `EXPIRE` 间进程挂导致死锁）。
- **value 用唯一 token**（如 UUID）：释放时校验，防误删别人的锁。
- **释放用 Lua 原子**：先 GET 比对再 DEL，否则可能删掉刚被别人拿走的锁。

```lua
-- 释放锁：仅当持有者才删
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

### 2.2 锁的风险与缓解

- **业务未完成锁已过期** → 两实例同时进临界区。
  - 缓解：看门狗自动续期（如 Redisson 的 watchdog）；或把锁过期设远大于业务最大耗时。
- **GC/网络停顿** → 客户端以为还持锁其实已过期。
  - 缓解：引入 **fencing token**（单调递增，旧操作被新操作拒绝）。
- **不可重入** → 同线程重入死锁。
  - 缓解：用重入锁（计数 + 持有者标识）或避免重入设计。

### 2.3 锁粒度

- 太粗：锁住整个方法/表，并发度低。
- 太细：漏保护（只锁 ID 却改了关联资源）。
- 建议：锁到"资源维度"（如订单号、SKU ID），而非方法维度。

## 三、幂等设计

幂等 = 同一请求（相同参数）执行一次与多次结果一致。

### 3.1 场景

- 网络重试（HTTP 超时客户端重试）。
- 消息重投（MQ at-least-once）。
- 用户重复点击（连点提交）。
- 前端防重 token 未生效。

### 3.2 实现手段

- **唯一键**：数据库唯一索引（订单号、流水号）拦截重复插入。
- **去重表**：已处理 key 记表，先查再执行；处理完写回。
- **状态机**：只有「待处理」能转「已处理」，重复事件被状态机拒绝。
- **Token 机制**：前端下单先拿一次性 token，重复提交校验已用即拒。
- **版本号/乐观锁**：`UPDATE ... WHERE version=?`，并发更新冲突重试。

### 3.3 幂等与锁的配合

- 锁解决"并发互斥"，幂等解决"重复执行"。
- 只加锁不幂等：重试仍重复（如扣款两次）。
- 只幂等不加锁：并发仍可能竞态（两个请求同时通过去重检查）。

## 四、典型组合

```
请求 → 幂等键查重(去重表) → 已处理 → 直接返回已有结果
                     ↓ 未处理
                  加分布式锁 → 执行业务 → 记结果 → 释放锁
```

## 五、与事务配合

- 锁 + 本地事务：业务失败回滚，锁释放。
- 跨服务：用 Saga / TCC，每一步都幂等且可补偿。
- 详见 [场景设计/支付系统核心设计](支付系统核心设计.md)。

## 六、常见坑

1. **锁不设过期** → 实例挂死锁，资源永久锁住。
2. **释放锁不校验持有者** → 误删别人锁，临界区被双重进入。
3. **只加锁不幂等** → 重试仍造成重复（资损）。
4. **锁粒度太粗/太细** → 性能差或漏保护。
5. **依赖时钟判断过期** → 时钟漂移出错（用 fencing/版本）。
6. **去重表与业务不在一个事务** → 查重通过但写失败，重试又查重说已处理（状态不一致）。
