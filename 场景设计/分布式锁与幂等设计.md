# 分布式锁与幂等设计

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、为什么需要

分布式下多实例并发操作同一资源（扣库存、发奖励、定时任务），需要「互斥」与「不重复执行」。两件事：锁（互斥）+ 幂等（重复无害）。

## 二、分布式锁方案

| 方案 | 实现 | 优缺点 |
|------|------|--------|
| Redis SET NX | `SET key val NX EX` | 简单、快，但主从切换可能双持锁 |
| Redlock | 多节点多数派 | 更稳，但争议（ fencing 问题） |
| ZooKeeper | 临时顺序节点 | 可靠，但重 |
| 数据库唯一约束 | 唯一索引抢行 | 简单，依赖 DB |
| etcd | 租约 + 事务 | CP，可靠 |

- **Redis 锁要点**：value 用唯一 token（释放时校验防误删）、设过期时间防死锁、用 Lua 原子释放。

```lua
-- 释放锁：仅当持有者才删
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

## 三、锁的风险

- **过期早于业务完成** → 锁失效，两实例同时进。缓解：看门狗自动续期（如 Redisson）。
- **GC/网络停顿** → 客户端以为还持锁其实已过期。需 fencing token 防旧操作。
- **不可重入** → 同线程重入死锁，需重入计数。

## 四、幂等设计

幂等 = 同一请求多次执行结果一致。场景：网络重试、消息重投、用户重复点击。

- **唯一键**：数据库唯一索引（订单号、流水号）拦截重复。
- **去重表**：已处理 key 记表，先查再执行。
- **状态机**：只有「待处理」能转「已处理」，重复事件被状态机拒绝。
- **Token 机制**：前端下单拿一次性 token，重复提交校验已用。

## 五、典型组合

```
请求 → 幂等键查重(去重表) → 未处理 → 加分布式锁 → 执行业务 → 记结果 → 释放锁
                                  ↑重复 → 直接返回已有结果
```

## 六、与事务配合

- 锁 + 本地事务：业务失败回滚，锁释放。
- 跨服务：用 Saga/TCC，每步幂等可补偿。详见 [场景设计/支付系统核心设计](支付系统核心设计.md)。

## 七、常见坑

1. 锁不设过期 → 实例挂死锁。
2. 释放锁不校验持有者 → 误删别人锁。
3. 只加锁不幂等 → 重试仍重复。
4. 锁粒度太粗 → 性能差；太细 → 漏保护。
5. 依赖时钟判断过期 → 时钟漂移出错。
