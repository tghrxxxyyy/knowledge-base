# 购物车系统设计

> 板块：场景设计 　|　 返回：[README](README.md)
> 关联：[电商交易业务模型](../业务模型/电商交易业务模型.md)、[优惠券系统与营销防刷设计](优惠券系统与营销防刷设计.md)、[缓存经典三问与一致性](缓存经典三问与一致性.md)

购物车是电商交易的"前置缓冲"，连接浏览与下单。它看似简单，实则涉及多端同步、价格时效、库存校验、优惠计算、合并结算等复杂问题。本文系统拆解。

## 一、购物车的核心职责

| 职责 | 说明 |
|------|------|
| 暂存意向 | 用户把想买的商品放一起，稍后结算 |
| 多端同步 | 手机加购、PC 结算，数据一致 |
| 价格/库存预览 | 加购时展示当前价、是否可买 |
| 优惠计算 | 购物车级满减/券的预估 |
| 结算入口 | 勾选部分商品去结算 |

> 购物车是"读多写多"且对一致性要求中等（丢一个商品可接受，但价格/库存要准）。

## 二、登录态 vs 匿名态

| 维度 | 匿名（未登录） | 登录 |
|------|--------------|------|
| 存储 | 客户端（localStorage）+ 服务端临时 | 服务端 DB/Cache |
| 合并 | 登录后合并到用户购物车 | 直接操作 |
| 容量 | 有限（客户端） | 大 |
| 风险 | 清缓存丢、换设备丢 | 依赖服务端稳定 |

- **合并策略**：登录时用 `deviceId` 关联的匿名购物车合并进用户购物车，去重（同 SKU 累加数量，或取大）。
- **合并冲突**：同一 SKU 在两端都有 → 数量相加或提示用户选择（常见相加）。

## 三、数据模型

```
Cart (用户/匿名维度)
 ├─ items: [CartItem]
CartItem:
  sku_id, quantity, checked(是否勾选), add_time, source(来源: 商详/购物车/凑单)
```

| 字段 | 说明 |
|------|------|
| sku_id | 交易核心是 SKU（见电商模型） |
| quantity | 数量（受库存上限约束） |
| checked | 是否参与结算（部分结算） |
| add_time | 用于排序/过期清理 |
| source | 来源，支撑"猜你喜欢""凑单" |

- 购物车不存价格（价格随时变），只存 SKU + 数量，**展示时实时查价**。
- 不存库存（库存随时变），结算时实时校验。

## 四、存储选型

| 方案 | 适用 | 说明 |
|------|------|------|
| Redis + MySQL | 主流 | Redis 扛读/写，MySQL 持久化兜底 |
| 纯 Redis | 轻量 | 用 RDB+AOF 持久化，可能丢极少数据 |
| 纯 DB | 低频 | 简单但延迟高 |

```
写: 更新 Redis Hash(cart:{userId}) + 异步/同步写 MySQL
读: 先读 Redis，未命中读 MySQL 回写
结算: 读 Redis 购物车 → 校验 SKU/价/库存 → 生成订单
```

```bash
# Redis 结构
HSET cart:u100 sku_001 '{"qty":2,"checked":1,"add":1690000000}'
HGETALL cart:u100
# 数量上限防滥用
if HLEN cart:u100 > 200: reject   # 单用户购物车上限
```

## 五、价格与库存的实时性

购物车展示"现价、是否可买"，但价格和库存是动态的：

- **价格**：加购时不锁价，展示时实时查 SKU 当前价（可能已变，需提示"价格已变动"）。
- **库存**：展示"仅剩 N 件"需实时/近实时查库存；结算时再次强校验（防超卖，见 [秒杀系统设计与高并发扣减](秒杀系统设计与高并发扣减.md)）。
- **失效处理**：SKU 下架/售罄 → 购物车项置灰、不可勾选、提示。

```
加购 → 存 SKU+数量
展示 → 实时聚合 [价格服务 + 库存服务 + 促销服务]
结算 → 再校验一次（价格快照 + 库存预扣）
```

## 六、优惠预估（购物车级）

- 购物车级满减（满 299 减 50）、跨店满减、店铺券需在购物车页预估"凑单还差多少"。
- 计算在展示时调用促销服务，**只预估不锁定**（结算时以最终为准）。
- 复杂优惠（跨 SKU 分摊）与下单一致，见 [电商交易业务模型](../业务模型/电商交易业务模型.md) 的价格模型。

## 七、部分结算与勾选

- 用户勾选部分商品结算 → 只把 checked=true 的项带入下单。
- 结算后从购物车移除已下单项（或标记已购）。
- 多商家购物车 → 按商家拆子订单（见电商模型订单拆分）。

## 八、异常与边界

| 场景 | 处理 |
|------|------|
| SKU 失效/下架 | 置灰、不可勾选、提示移除 |
| 库存不足 | 提示"仅剩 N"，结算拦截止 |
| 价格变动 | 提示"价格已更新"，以结算时为准 |
| 数量超限 | 单 SKU 数量上限（如 ≤ 库存、≤ 99） |
| 购物车超容量 | 单用户条目上限（如 200），拒绝添加 |
| 加购冲突 | 同一 SKU 累加，来源合并 |

## 九、高并发与性能

- **读多**：购物车列表高频访问，Redis 缓存 + 本地缓存（必要时）。
- **写并发**：同一用户并发加购 → Redis HSET 原子，无需分布式锁（单用户维度）。
- **批量查询**：展示时批量查价/库存/促销，避免 N 次 RPC（批量接口 + 并行聚合）。
- **降级**：促销服务挂 → 购物车仍可用（不展示优惠预估），核心加购/结算不受影响。

## 十、常见坑

1. **购物车存价格** → 结算时价已变，纠纷（应实时查价 + 下单快照）。
2. **不实时校验库存** → 结算时超卖或无法下单（展示+结算双校验）。
3. **匿名购物车不合并** → 登录后之前加的丢了（合并策略必备）。
4. **单 SKU 无数量上限** → 被刷/异常数据（设上限）。
5. **优惠预估与结算不一致** → 用户困惑（预估与下单用同一规则引擎）。
6. **购物车无限膨胀** → DB/Redis 压力（设条目上限 + 清理过期）。
7. **多端不同步** → 手机加 PC 看不到（服务端存储 + 登录态合并）。
8. **缓存与 DB 不一致** → 展示与结算不符（写时双写 + 读时校验）。

## 十一、关键设计 checklist

- [ ] 购物车只存 SKU + 数量，价格/库存实时查。
- [ ] 匿名 + 登录双态，登录合并去重。
- [ ] Redis + MySQL 双写，设容量与数量上限。
- [ ] 展示聚合价/库存/促销（批量并行），只预估不锁定。
- [ ] 结算再强校验价格快照 + 库存预扣。
- [ ] 失效/下架/库存不足优雅处理。
- [ ] 优惠预估与下单共用规则引擎。
