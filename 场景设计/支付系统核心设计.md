# 支付系统核心设计

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、支付的复杂性

支付不是「扣钱」一句话，而是涉及：渠道接入、订单、账务、对账、退款、风控、幂等、异步通知。任何一步错都会资损（多扣/少扣/重复扣）。

> 支付系统第一原则：钱不能错。一致性 > 性能。可审计 > 灵活。

## 二、核心实体

- **支付订单（PayOrder）**：一次支付请求，含金额、渠道、状态。
- **渠道交易（ChannelTx）**：对下游渠道（微信/支付宝/银联）的交易记录。
- **账务流水（Ledger）**：每笔资金变动的借贷记录，用于对账。
- **退款单（Refund）**：逆向交易。

## 三、支付流程

```
用户下单 → 创建支付订单 → 调渠道 SDK 下单 → 用户支付 → 渠道异步回调 → 校验签名 → 更新订单 → 通知业务 → 记账
```

- 渠道回调是**异步**且**可能重复**，必须幂等处理。
- 订单状态机：待支付 → 支付中 → 已支付 / 已关闭 / 已退款。

## 四、幂等设计（重中之重）

- 每个支付/退款请求带 `outTradeNo`（业务唯一号）。
- 渠道回调用 `outTradeNo` 做幂等键，重复通知直接返回成功。
- 数据库唯一索引防并发重复处理。

```sql
-- 用唯一索引保证同一笔只处理一次
ALTER TABLE pay_order ADD UNIQUE KEY uk_out_trade_no (out_trade_no);
-- 回调处理：INSERT 前先查，或用 ON DUPLICATE KEY 兜底
```

## 五、渠道接入与适配器

- 每个渠道一个适配器（见 [适配器模式](../../设计模式/结构型/适配器模式.md)），统一 `PaymentGateway` 接口。
- 渠道配置（商户号、密钥、证书）隔离，支持多渠道路由。
- 渠道故障 → 自动路由到其他渠道（如微信挂切支付宝）。

## 六、对账（Reconciliation）

- 每日 T+1 拉取渠道流水，与本地账务逐笔核对。
- 差异分类：长款（渠道多）、短款（渠道少）、错账。
- 差错处理：挂账、调账、人工复核。
- 对账是发现资损的最后防线，必须有。

## 七、账务与复式记账

- 每笔交易记借贷双方（用户余额、平台应收、渠道待清算）。
- 账户余额用「余额 + 流水」双写，流水不可变（只追加）。
- 用数据库事务 + 乐观锁保证余额正确。

```sql
UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?;
-- 影响行数为 0 则余额不足，回滚
```

## 八、退款与逆向

- 退款需原路退回（原卡原渠道），部分退款要记录已退金额。
- 退款也走渠道异步回调，同样幂等。
- 退款后账务做反向记账。

## 九、风控

- 实时规则：大额、异地、频繁小额测试卡。
- 限额：单笔/单日/单用户。
- 黑名单与设备指纹。
- 人工审核通道（可疑交易拦截）。

## 十、安全

- 渠道回调验签（防伪造回调）。
- 敏感信息加密（卡号脱敏、密钥托管）。
- 防篡改：金额、订单号服务端权威，不信任前端。

## 十一、常见坑

1. 回调不幂等 → 重复到账/重复发货。
2. 不做对账 → 渠道少结算才发现资损。
3. 余额更新无并发控制 → 超扣。
4. 金额信任前端 → 被篡改 0.01 元下单。
5. 退款不校验原订单 → 退了没付的钱。
6. 渠道秘钥硬编码 → 泄露资损。

## 十二、落地清单

1. 订单 + 渠道 + 账务三件套建模。
2. 全链路幂等（outTradeNo）。
3. 渠道适配器 + 路由降级。
4. 每日自动对账 + 差错处理。
5. 复式记账 + 余额并发控制。
6. 回调验签 + 风控 + 监控告警。
