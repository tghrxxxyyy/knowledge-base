# 实时推荐 Feed 流架构实战

> 本文拆解信息流（Feed）系统的架构设计：拉模型 vs 推模型、读写扩散、实时推荐插入、热点与性能优化、以及典型踩坑。内容基于公开工业实践，参数以业务为准。

## 1. Feed 流的形态

- 微博/Twitter 式：关注的人发的内容，按时间聚合。
- 抖音/小红书式：算法推荐，不纯按关注。
- 朋友圈式：半私密，强社交关系。
- 无论哪种，核心是"给用户一个有序内容列表"。

## 2. 推模型（Push / 写扩散）

- 用户发内容，立即写入其所有粉丝的收件箱（Feed 列表）。
- 读时直接取自己的收件箱，极快。
- 优点：读延迟低。
- 缺点：大 V 粉丝多，写扩散爆炸（一个明星发，千万收件箱写）。
- 适合：粉丝数普遍不大（普通社交）。

## 3. 拉模型（Pull / 读扩散）

- 用户发内容只存自己发件箱。
- 读时聚合所有关注对象的发件箱，按时间归并。
- 优点：写轻，无扩散。
- 缺点：关注多时读慢（需查很多人）。
- 适合：读少关注多，或配合缓存。

## 4. 推拉结合（Hybrid）

- 普通用户：推模型（粉丝少，扩散成本低）。
- 大 V：拉模型（粉丝多，不推，读时单独拉）。
- 读时：自己的收件箱 + 大 V 的发件箱归并。
- 这是工业界主流折中。

## 5. 存储选型

- 收件箱/发件箱：可用 Redis 有序集合（按时间 score）或宽表（Cassandra/HBase）。
- 内容主体：独立存储（对象存储/DB），Feed 只存内容 ID。
- 归并：多路归并（类似 k 路合并）。

## 6. 实时推荐插入

- 纯时间流基础上，插入推荐内容（广告/猜你喜欢）。
- 推荐服务在 Feed 生成时打分排序，插入合适位置。
- 需控制推荐占比，避免体验差。
- 与推荐系统章节呼应（召回→排序→重排）。

## 7. 分页与游标

- 用游标（cursor，如最后一条的时间戳/ID）而非 offset 分页。
- 避免 offset 大时扫描多、且新内容插入导致重复/遗漏。
- 游标需稳定唯一（时间+ID 组合）。

## 8. 热点与性能

- 大 V 发内容：推模型爆炸，用拉或限流扩散。
- 热点内容：缓存前置，避免回源。
- 读多写少：多级缓存（本地+Redis）。
- 归并计算可离线预计算 + 增量更新。

## 9. 实时性

- 推模型实时性好（写入即见）。
- 拉模型需读时聚合，可加缓存近实时。
- 实时推荐需低延迟特征（见推荐系统章节）。

## 10. 去重与过滤

- 已读过滤、重复内容去重。
- 不感兴趣/屏蔽用户过滤。
- 合规与敏感内容过滤。

## 11. 互动计数

- 点赞/评论/转发计数异步更新（MQ）。
- 计数与 Feed 解耦，避免阻塞发布。
- 最终一致即可。

## 12. 删除与失效

- 删内容：删发件箱 + 标记收件箱条目失效（懒删除/异步清理）。
- 取关：清理对应收件箱（或读时跳过）。
- 软删除优先，避免大规模物理清理。

## 13. 架构示意

```
发布服务 → 写扩散(推到粉丝收件箱) / 写发件箱(拉)
   → Feed 生成(收件箱+大V发件箱归并)
   → 推荐插入(排序重排)
   → 缓存 → 客户端(游标分页)
互动(赞/评) → MQ → 计数服务(异步)
```

## 14. 指标

- 发布到可见延迟（P99）。
- Feed 读取延迟（P99）。
- 扩散写量（大 V 场景监控）。
- 缓存命中率。

## 15. 常见踩坑

1. **纯推模型上大 V**：写扩散打垮存储；大 V 改拉。
2. **offset 分页**：新内容插入致重复/漏读；用游标。
3. **收件箱无限增长**：存储爆炸；按时间/数量截断。
4. **实时推荐占比过高**：体验差、留存降；控比例。
5. **互动同步阻塞**：发帖等计数完成，慢；异步解耦。
6. **缓存与源不一致**：清理不彻底；懒删除+异步。
7. **归并无上限**：关注极多时读超时；限制拉取范围/预计算。

## 16. 演进路径

- 起步：拉模型 + 缓存（简单）。
- 增长：推拉结合，大 V 拉。
- 实时：预计算收件箱 + 增量。
- 智能：插入推荐，重排优化体验。

## 17. 与推荐系统关系

- Feed 是推荐的载体之一。
- 推荐负责"插什么、排哪"，Feed 负责"怎么存、怎么取"。
- 二者协作：召回候选 → 排序 → Feed 重排插入。

## 18. 小结

Feed 流架构的核心是"推拉权衡"：写扩散快但怕大 V，读扩散稳但怕关注多，工业界用推拉结合（大 V 拉）平衡。设计铁律：**用游标分页而非 offset、大 V 走拉、内容 ID 与主体分离、互动异步解耦、推荐占比可控、收件箱设上限**。实时推荐是体验加分项，但需与基础 Feed 稳定性解耦演进。
