# 幂等设计深入（分布式幂等 / 消息幂等 / 补偿模式 / 状态机幂等）

> 幂等设计 = 让"重试"变得安全。本篇深入拆解：分布式幂等架构、消息幂等消费、补偿模式、状态机幂等、生产 Checklist。

---

## 一、什么是幂等

```
数学定义：f(f(x)) = f(x)
API 语义：同一条件的请求，无论调用多少次，副作用与返回结果都一致
```

| 操作 | 是否天然幂等 | 说明 |
|------|------------|------|
| GET / HEAD | 是 | 查询不改变状态 |
| PUT / DELETE | 协议定义是 | 但复杂业务仍需额外控制 |
| POST | 否 | 创建/扣减通常非幂等，必须设计 |

---

## 二、重复请求来源

| 来源 | 说明 |
|------|------|
| 网络超时重试 | 客户端/网关超时后自动重试 |
| 用户连点 | 前端按钮多次点击 |
| 前端 Retry | 浏览器自动重试 |
| MQ 至少一次投递 | 消息重复投递 |
| 微服务框架重试 | Dubbo/Feign 超时重试 |

> **只要改变业务状态的接口，都必须幂等**——尤其是资金、库存、订单、优惠券。

## 三、七大实战方案

### 1. 数据库唯一索引（最可靠兜底）

```sql
CREATE TABLE t_order (
  id int PRIMARY KEY AUTO_INCREMENT,
  code varchar(64) NOT NULL,
  UNIQUE uk_code (code)
);
```
重复插入触发 `DuplicateKeyException`，捕获后返回已有结果。适合**创建类**操作。

### 2. 乐观锁（更新类首选）

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 1;
```
并发重复时 version 已变，更新失效。适合余额扣减、库存修改。

### 3. 状态机（业务语义幂等）

```sql
UPDATE orders SET status = 'PAID' WHERE id = 123 AND status = 'CREATED';
```
状态单向流转：重复支付时状态已是 PAID，影响行数 0。

### 4. 防重表 / 流水表（通用）

```sql
CREATE TABLE deduplication (
  id int PRIMARY KEY AUTO_INCREMENT,
  processed_code varchar(64) NOT NULL,
  UNIQUE uk_code (processed_code)
);
```
处理前插入业务流水号，冲突即重复。必须与业务操作**同一事务**。

### 5. Token 令牌机制（防表单重复提交）

```java
// 1. 进入页面获取 Token，存 Redis 5 分钟
String token = UUID.randomUUID().toString();
redis.setex("submit_token:" + token, 300, "1");
// 2. 提交时校验并原子删除（Redis 6.2+ GETDEL / Lua）
Long deleted = redis.getDel("submit_token:" + token);
if (deleted == 0) return Result.fail("请勿重复提交");
// 3. 再执行业务
```

### 6. 唯一请求 ID / 业务单号

网关/客户端为每个请求生成全局 Request-ID 或业务单号，服务端查去重表。

### 7. MQ 消息去重消费

消费者以 Message-ID / 业务主键查去重表，未处理才执行。

## 四、组合拳（生产推荐）

金融/电商高并发典型组合：**Token + 唯一索引 + 状态机**。

| 场景 | 首选方案 | 原因 |
|------|---------|------|
| 创建订单/注册 | 业务唯一键 + 唯一索引 | 数据库底层保证 |
| 支付回调 | 状态机 + 去重表 + 分布式锁 | 状态防回退，流水防重复 |
| 扣余额/扣库存 | 乐观锁 / 状态机 | 防并发错乱 |
| 前端连点 | Token 机制 | 体验好，源头防重 |
| MQ 消费 | 消息ID + 唯一索引 | 去重消费 |

## 五、分布式幂等架构

### 5.1 幂等层设计

```
Client → 网关（生成 RequestId）→ 幂等层 → 业务服务
                                          ↓
                                      幂等判定
                                          ↓
                                    唯一索引/Redis

幂等层职责：
  1. 接收 RequestId
  2. 查询幂等存储（Redis/DB）
  3. 未处理 → 执行业务 + 记录结果
  4. 已处理 → 直接返回缓存结果
```

### 5.2 幂等存储选择

| 存储 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| Redis | 快、原子操作 | 可能丢数据 | 第一道快速拦截 |
| 数据库 | 可靠、事务保证 | 慢 | 最终兜底 |
| Redis + DB | 快+可靠 | 复杂 | 生产推荐 |

## 六、消息幂等消费

### 6.1 问题

```
MQ 至少一次投递 → 消费者可能收到重复消息

重复消费的危害：
  重复扣款
  重复创建订单
  重复发券
```

### 6.2 方案

| 方案 | 说明 |
|------|------|
| 消息 ID 去重 | 消费前查去重表（Redis/DB） |
| 业务唯一键 | 利用业务字段唯一索引 |
| 状态机 | 利用状态流转幂等 |
| 本地消息表 | 事务写入本地消息表 + 消费确认 |

### 6.3 本地消息表模式

```
1. 业务操作 + 消息写入同一事务
  BEGIN;
  INSERT INTO orders (...);
  INSERT INTO outbox (message_id, payload, status='PENDING');
  COMMIT;

2. 后台任务扫描 PENDING 消息，发送到 MQ
  UPDATE outbox SET status='SENT' WHERE id=...;

3. 消费者确认后更新状态
  UPDATE outbox SET status='CONFIRMED' WHERE message_id=...;

好处：
  业务 + 消息原子写入
  保证消息不丢
  消费者天然幂等（消息 ID 去重）
```

## 七、补偿模式

### 7.1 TCC（Try-Confirm-Cancel）

```
Try：冻结资源（如冻结余额）
Confirm：确认扣减（扣减冻结的余额）
Cancel：取消冻结（释放冻结的余额）

幂等保障：
  Confirm/Cancel 幂等（利用状态机）
  重复 Confirm → 状态已 CONFIRMED，返回成功
  重复 Cancel → 状态已 CANCELLED，返回成功
```

### 7.2 SAGA

```
SAGA = 一系列本地事务 + 补偿事务

正向：T1 → T2 → T3
补偿：C3 → C2 → C1（失败时反向补偿）

幂等保障：
  每个 Ti/Ci 都要幂等
  利用状态机记录执行状态
  重复执行时查状态决定是否跳过
```

## 八、状态机幂等

### 8.1 设计原则

```
状态单向流转：
  CREATED → PAID → SHIPPED → COMPLETED
  每个状态只能流转一次

SQL 幂等：
  UPDATE orders SET status = 'PAID' 
  WHERE id = 123 AND status = 'CREATED';
  
  重复执行 → status 已是 PAID → 影响行数 0
```

### 8.2 状态机实现

```java
// 状态流转表
CREATE TABLE order_status_log (
  id BIGINT PRIMARY KEY,
  order_id BIGINT,
  from_status VARCHAR(32),
  to_status VARCHAR(32),
  created_at DATETIME,
  UNIQUE uk_order_status (order_id, from_status, to_status)
);

// 幂等保障：插入状态流转记录（唯一键）
INSERT INTO order_status_log (order_id, from_status, to_status)
VALUES (123, 'CREATED', 'PAID')
ON DUPLICATE KEY UPDATE id=id;  // 重复插入忽略

// 状态更新
UPDATE orders SET status = 'PAID' 
WHERE id = 123 AND status = 'CREATED';
```

## 九、常见误区

| 误区 | 真相 |
|------|------|
| 只靠前端不够 | 按钮置灰可绕过，服务端必须兜底 |
| 幂等 ≠ 阻塞 | 重复请求应快速返回，而非让第二个请求干等 |
| 返回结果要一致 | 第一次返回成功，第二次最好也返回成功 |
| 清理机制 | Redis 去重记录务必设 TTL |

## 十、生产 Checklist

| 检查项 | 说明 |
|--------|------|
| 幂等键 | 业务唯一键 / RequestId |
| 存储 | Redis 快拦截 + DB 兜底 |
| 事务 | 去重记录与业务操作同一事务 |
| TTL | Redis 去重记录设 TTL（> 重复窗口期） |
| 降级 | Redis 挂了降级到 DB 唯一索引 |
| 监控 | 幂等命中率、重复请求量 |
| 日志 | 记录重复请求（便于排查） |
