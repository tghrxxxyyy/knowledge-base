# 推送系统设计与长连接

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、推送系统的分类

- **移动 Push**：APNs（iOS）/ FCM（Android）/ 厂商通道（小米/华为），经系统级长连接下发。
- **Web Push**：Service Worker + 浏览器推送服务。
- **站内实时消息**：App/Web 长连接（WebSocket）实时推。
- **业务通知**：短信/邮件/IM 机器人，异步投递。

## 二、长连接 vs 短轮询

| 方式 | 原理 | 优劣 |
|------|------|------|
| 短轮询 | 客户端定时拉 | 简单，但浪费流量、延迟高 |
| 长轮询 | 请求挂起直到有消息 | 准实时，但连接占用 |
| WebSocket | 全双工长连接 | 实时，需维护连接状态 |
| SSE | 服务端单向推 | 轻量，仅服务端推 |

- 实时聊天/弹幕用 WebSocket；通知类用系统 Push 通道更省电。

## 三、整体架构

```
业务系统 → 消息网关(接入层) → 长连接集群(维护连接) → 终端设备
                      ↘ 第三方通道(APNs/FCM/厂商)
```

- **接入层**：维持海量长连接（Netty/Go 原生），单机能撑数十万连接。
- **连接管理**：连接 ID ↔ 用户 ID ↔ 设备 的映射（存 Redis）。
- **投递**：查目标用户在线连接，直推；不在线走第三方通道/离线存储。

## 四、连接管理

- 每个连接分配 `connId`，注册到 `userId → [connId...]`。
- 心跳保活：客户端定时发心跳，服务端超时剔除。
- 断线重连：客户端指数退避重连，重连后拉取离线消息。

```go
// 简化：连接注册
type Hub struct { mu sync.RWMutex; users map[string]map[string]*Conn }
func (h *Hub) bind(uid, connId string, c *Conn) {
    h.mu.Lock(); defer h.mu.Unlock()
    if h.users[uid] == nil { h.users[uid] = map[string]*Conn{} }
    h.users[uid][connId] = c
}
```

## 五、消息可靠投递

- **至少一次**：消息落库（已发/已读状态），失败重试。
- **去重**：消息带 msgId，客户端去重防重复。
- **顺序**：单会话内按 seq 排序展示。
- **离线**：用户不在线，消息存离线表，上线后拉取。

## 六、海量连接优化

- **I/O 多路复用**：Netty（Java）/ epoll（Go），单线程管上万连接。
- **内存**：每连接对象尽量小，避免大缓冲。
- **水平扩展**：连接按 userId 哈希分片到多节点，配合一致性哈希。
- **网关与逻辑分离**：接入层只管连接，业务逻辑独立。

## 七、第三方通道

- 自建长连接省电差，移动端优先走系统通道（APNs/FCM/厂商）。
- 业务侧调用 channel SDK，传 token + payload；通道负责送达。
- 多通道降级：某厂商通道故障，切其他通道或自建长连接兜底。

## 八、限流与防骚扰

- 单用户推送频控（如 1 分钟最多 N 条）。
- 重要等级分级：强提醒 vs 静默。
- 用户免打扰时段（夜间不打扰）。

## 九、监控与可观测

- 在线连接数、消息投递成功率、端到端延迟。
- 通道送达回执（第三方回调）统计到达率。
- 告警：连接跌零、投递率骤降。

## 十、常见坑

1. 心跳间隔不当 → 频繁重连或连接被运营商 NAT 超时断。
2. 不做消息去重 → 用户收到重复推送。
3. 连接状态不一致 → 用户在线却推不到（映射未更新）。
4. 单节点连接过多 → 内存/文件描述符耗尽。
5. 无频控 → 用户被骚扰卸载 App。

## 十一、落地清单

1. 选连接方案（WebSocket/系统通道）。
2. 接入层分片 + 连接映射（Redis）。
3. 心跳 + 重连 + 离线存储。
4. 可靠投递（落库 + 去重 + 重试）。
5. 频控 + 免打扰。
6. 多通道降级 + 监控。
