# 推送系统设计与长连接

> 板块：场景设计 　|　 返回：[README](README.md)
> 适用：IM 实时消息、App 推送通知、弹幕、直播互动、站内信实时触达。

## 一、推送系统的分类

推送 = 「把服务端产生的内容/事件实时送达终端」。按通道与场景分：

| 类型 | 通道 | 特点 | 典型场景 |
|------|------|------|---------|
| 移动系统 Push | APNs（iOS）/ FCM（Android）/ 厂商通道（小米/华为/OPPO/vivo） | 走系统级长连接，省电，App 杀掉也能到 | 营销通知、订单提醒 |
| Web Push | Service Worker + 浏览器推送服务（VAPID） | 网页关闭也能收到 | 网页版消息提醒 |
| 站内实时消息 | 自建长连接（WebSocket / TCP） | 双向、低延迟，耗电 | IM 聊天、弹幕、协作 |
| 业务通知 | 短信 / 邮件 / 企业 IM 机器人 | 异步、可靠、慢 | 告警、验证码、审批 |

> 一句话：**移动端优先走系统通道（省电），站内实时交互走自建长连接（低延迟）**。

## 二、长连接 vs 其他模式

| 方式 | 原理 | 延迟 | 服务端开销 | 适用 |
|------|------|------|-----------|------|
| 短轮询 | 客户端定时拉 | 高（取决于间隔） | 低（无状态） | 不实时、低频 |
| 长轮询 | 请求挂起直到有消息/超时 | 中 | 中（占连接） | 兼容老客户端 |
| WebSocket | 全双工长连接 | 低 | 高（需维持连接） | 聊天/弹幕 |
| SSE | 服务端单向推（HTTP） | 低 | 中 | 通知流、行情 |
| TCP 私有协议 | 自定义二进制协议 | 极低 | 高 | 自研 IM/游戏 |

- 实时聊天、弹幕、协作编辑器用 WebSocket/TCP；
- 行情、通知流用 SSE 或 WebSocket；
- 移动后台通知用系统 Push 通道，最省电。

## 三、整体架构

```
                业务系统（订单/评论/风控…）
                        │ 发消息
                        ▼
                ┌──────────────┐
                │  消息网关/接入 │  ← 多协议适配（WS/TCP/HTTP）
                └──────┬───────┘
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   长连接集群(Conn)  离线存储(MQ/DB)  第三方通道(APNs/FCM/厂商)
  维护连接 & 推送      存储离线消息      系统级下发
```

- **接入层（Connection/Conn）**：维持海量长连接（Netty/Go netpoll），单机能撑数十万连接。
- **连接管理**：`connId ↔ userId ↔ deviceId` 的映射，存 Redis（在线状态 + 连接所在节点）。
- **投递路由**：查目标用户在线连接所在节点，直推；不在线走第三方通道或离线存储。
- **逻辑与接入分离**：接入层只管连接与字节流，业务逻辑（消息组装、过滤）独立服务。

## 四、连接管理

### 4.1 连接注册与映射

```go
// 简化：连接注册
type Hub struct {
    mu    sync.RWMutex
    users map[string]map[string]*Conn  // userId -> connId -> Conn
}
func (h *Hub) bind(uid, connId string, c *Conn) {
    h.mu.Lock(); defer h.mu.Unlock()
    if h.users[uid] == nil { h.users[uid] = map[string]*Conn{} }
    h.users[uid][connId] = c
}
func (h *Hub) unbind(uid, connId string) {
    h.mu.Lock(); defer h.mu.Unlock()
    delete(h.users[uid], connId)
    if len(h.users[uid]) == 0 { delete(h.users, uid) }
}
```

- 每个连接分配 `connId`；同一用户多端登录 → 多 `connId`。
- 在线状态写 Redis：`user:{uid} → {connId: nodeAddr, ...}`，带 TTL（心跳续期）。

### 4.2 心跳保活

- 客户端定时发心跳（如 30s/次），服务端超时（如 90s 无心跳）剔除。
- 心跳间隔权衡：太短耗电/耗带宽；太长断线发现慢、易被运营商 NAT 超时（通常 5~15 分钟）断开。
- 移动网络下建议 30~60s 心跳 + 智能心跳（根据网络自适应）。

### 4.3 断线重连

- 客户端指数退避重连（1s → 2s → 4s … 上限如 30s）。
- 重连成功后拉取离线消息（游标/seq），避免丢消息。
- 弱网切换（WiFi↔4G）触发重连，需快速感知。

## 五、消息可靠投递（至少一次 / 精确一次）

```
发送方 → 业务校验 → 落库(msgId, status=已发) → 投递在线连接
                                      ↓(失败/离线)
                              离线表 / 第三方通道 → 客户端ACK → 标记已读
                                      ↓(超时未ACK)
                                  重试(指数退避)
```

- **至少一次**：消息落库（已发/已达/已读状态机），失败重试。
- **去重**：每条消息带全局 `msgId`，客户端按 msgId 去重，防重复展示。
- **顺序**：单会话内按 `seq` 排序；跨端用服务端权威顺序。
- **离线**：用户不在线 → 消息存离线表（或按 uid 入 MQ），上线后拉取（游标）。
- **ACK 机制**：客户端收到并展示后回 ACK，服务端标记已读，停止重投。

```sql
CREATE TABLE msg (
    id        BIGINT PRIMARY KEY,
    msg_id    VARCHAR(64) NOT NULL,       -- 全局去重键
    sender    BIGINT,
    receiver  BIGINT,
    content   TEXT,
    status    TINYINT DEFAULT 0,           -- 0已发 1已达 2已读
    seq       BIGINT,                      -- 会话内顺序
    created_at DATETIME
);
CREATE UNIQUE KEY uk_msg (msg_id);
```

## 六、海量连接优化

- **I/O 多路复用**：Netty（Java NIO）/ Go netpoll / epoll，单线程管上万连接；避免每连接一线程。
- **内存控制**：每连接对象尽量小，避免大缓冲；用对象池复用；注意 Netty `ByteBuf` 泄漏。
- **水平扩展**：连接按 `userId` 一致性哈希分片到多节点；节点上下线用一致性哈希减少重连抖动。
- **网关与逻辑分离**：接入层只做字节流与连接管理；消息解析、过滤、推送逻辑独立，便于扩缩容。
- **文件描述符**：单机 `ulimit -n` 调到 100w+；内核参数（`somaxconn`、`tcp_tw_reuse`）调优。
- **协议**：用二进制紧凑协议（ProtoBuf）替代 JSON，减少带宽与解析开销。

## 七、第三方通道（移动 Push）

- 自建长连接后台耗电高，移动端优先走系统通道：
  - iOS → APNs（Apple Push Notification service）；
  - 海外 Android → FCM；
  - 国内 Android → 厂商通道（小米/华为/OPPO/vivo/荣耀），因 GMS 缺失必须走厂商。
- 业务侧调用通道 SDK/HTTP，传 `deviceToken + payload`；通道负责送达。
- **多通道降级**：某厂商通道故障 → 切其他通道，或自建长连接兜底；记录送达回执（回调）统计到达率。
- **令牌管理**：deviceToken 会变化，需上报更新；失效 token 清理，避免推送失败堆积。

## 八、限流与防骚扰

- **频控**：单用户推送频率上限（如 1 分钟 ≤ N 条），防止轰炸。
- **分级**：强提醒（订单/安全）vs 静默（营销）；用户可设置免打扰。
- **免打扰时段**：夜间（如 22:00–08:00）仅放行强提醒类。
- **聚合**：同类提醒合并（如「你有 3 条新评论」），减少打扰。
- **退订/折叠**：营销类支持退订，降低卸载率。

## 九、监控与可观测

| 指标 | 说明 | 告警阈值示例 |
|------|------|------------|
| 在线连接数 | 实时连接总量 | 跌零/骤降 30% |
| 消息投递成功率 | 已达/总发 | < 99% |
| 端到端延迟 | 发到客户端展示 | P99 > 1s |
| 通道到达率 | 第三方回执/总量 | < 90% |
| 离线消息堆积 | MQ/离线表积压 | 持续增长 |
| 心跳异常率 | 超时剔除比例 | 突增 |

- 链路追踪：msgId 贯穿发送→投递→ACK，便于排查丢消息。
- 告警：连接跌零（节点挂）、投递率骤降（通道故障）、堆积（消费慢）。

## 十、安全

- **鉴权**：长连接建立后先鉴权（token），未授权连接立即断开；`connId ↔ userId` 绑定防止越权推。
- **防伪造推送**：推送入口仅内部服务可调用，外部调用需签名。
- **内容安全**：推送内容机审（涉政/色情/诈骗），违规不下发。
- **频控防 DDoS**：单用户/单 IP 推送限流，防被当放大器。

## 十一、常见坑

1. 心跳间隔不当 → 频繁重连或连接被运营商 NAT 超时断。
2. 不做消息去重 → 用户收到重复推送（尤其重试场景）。
3. 连接状态不一致 → 用户在线却推不到（映射未更新/节点漂移）。
4. 单节点连接过多 → 内存/文件描述符耗尽，需水平分片。
5. 无频控 → 用户被骚扰卸载 App。
6. 离线消息不拉取 → 重连后丢消息，需游标拉取。
7. 第三方 token 不更新 → 推送大面积失败。
8. 推送入口无鉴权 → 被外部伪造推送（钓鱼/诈骗）。
9. 大消息体直接推 → 带宽打满，需截断/拆包。
10. 不分等级 → 营销打扰强提醒，体验崩，需分级+免打扰。

## 十二、落地清单

1. 选连接方案（WebSocket/系统通道/TCP 私有协议）。
2. 接入层分片 + 连接映射（Redis，心跳续期）。
3. 心跳 + 指数退避重连 + 离线存储 + 游标拉取。
4. 可靠投递（落库 + msgId 去重 + ACK + 重试）。
5. 第三方通道接入 + token 管理 + 多通道降级。
6. 频控 + 分级 + 免打扰 + 聚合。
7. 监控（连接数/成功率/延迟/到达率）+ 链路追踪。
8. 推送入口鉴权 + 内容安全。
