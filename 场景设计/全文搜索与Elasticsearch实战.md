# 全文搜索与 Elasticsearch 实战

> 板块：场景设计 　|　 返回：[README](README.md)

当用户需要在百万/亿级文档、商品、日志中"按关键词快速召回并排序"时，数据库的 `LIKE` 已无法满足。Elasticsearch 基于 Lucene 的倒排索引，提供近实时的全文检索、聚合与分析能力。本文从原理、概念、架构、查询、性能到坑系统讲解。

## 一、搜索要解决什么

核心三件事：
- **召回（Recall）**：从海量数据里找出相关文档。
- **排序（Rank）**：按相关性/业务权重排前面。
- **高亮与聚合**：展示命中片段、做统计 facets。

核心支撑：**倒排索引 + 相关性算分 + 高亮**。

## 二、核心概念

### 2.1 倒排索引（Inverted Index）

- 正排：文档 → 包含的词。
- 倒排：词（term） → 出现该词的文档列表（含位置、频率）。
- 查询"手机"时直接定位到包含"手机"的文档集合，远快于全表 `LIKE '%手机%'`。

### 2.2 分词（Analyzer）

- 文本经过 tokenizer + filter 拆成 term 建索引、查询时也分词。
- 中文需 IK / 结巴等分词器（"全文搜索"→"全文/搜索"），英文用 standard（按空格、小写化）。
- 索引时分词与查询时分词需一致，否则召回偏差。

### 2.3 相关性算分

- **TF-IDF**：词频高、逆文档频率高 → 得分高。
- **BM25**：TF-IDF 的改进，对词频饱和、文档长度更鲁棒（ES 默认）。
- 可通过 `boost`、function_score 注入业务权重（如销量、热度）。

### 2.4 Mapping

- 字段类型定义：text（分词、可全文）、keyword（不分词、可精确/聚合）。
- 同字段可 multi-field：text + keyword 子字段，兼顾全文与精确。
- 错误设计（如把需全文的字段设成 keyword）会导致搜不到。

## 三、ES 架构

- **Index**：逻辑库（类比数据库），内含若干 **Shard（分片）** 水平扩展。
- **Shard**：最小数据/搜索单元，可分布到不同节点并行。
- **Replica**：分片副本，提供高可用与读扩展。
- **写入流程**：进 translog（防丢失）→ refresh 成可搜 segment（默认 1s 近实时）→ 定期 merge。
- **节点角色**：master（集群管理）、data（存数据）、coordinating（协调查询）。

### 3.1 分片策略

- 分片数决定水平扩展上限，过多会有开销（cluster state 大、查询扇出多）。
- 副本数 = 高可用与读吞吐的权衡。
- 索引过大可用 rollover + ILM（生命周期）滚动。

## 四、查询类型

- **term**：精确匹配（keyword 字段），不走分词，快。
- **match**：全文分词匹配（text 字段），走算分。
- **bool**：组合 `must`（算分）/ `should`（加分）/ `must_not` / `filter`（过滤、可缓存、不算分）。
- **range / exists / wildcard / prefix / fuzzy（容错拼写）**。

```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "title": "手机" } }],
      "filter": [{ "range": { "price": { "gte": 100, "lte": 5000 } } }]
    }
  },
  "sort": [{ "sales": "desc" }],
  "from": 0, "size": 20,
  "highlight": { "fields": { "title": {} } }
}
```

### 4.1 算分与业务权重结合

- `function_score`：用销量、评分、新鲜度等做衰减/加权，避免纯文本相关性。
- `bool` 的 `should` 也可注入业务加分。

## 五、性能与一致性

### 5.1 深翻页

- `from + size` 大偏移（如 from=10000）会在每个分片取前 N 条再合并，性能差。
- 改用 **`search_after`**（基于上一页最后一个排序值游标）做深翻页。
- 或业务上限制翻页深度（只给前 N 页）。

### 5.2 聚合（aggs）

- terms/date_histogram 做 facets、趋势统计。
- 大量桶注意内存（`size`、近似聚合）。

### 5.3 与数据库最终一致

- ES 是**索引**，不是源系统（source of truth）。
- 业务表变更通过 CDC（Canal/Debezium 解析 binlog）同步到 ES，保证最终一致。
- 重建索引用 reindex / alias 切换，避免停服。

## 六、混合检索（RAG 场景）

- 向量检索（语义）+ BM25（关键词）融合（RRF / 加权）提升召回。
- 详见 [大模型/RAG/02-RAG进阶与召回优化实战](../大模型/RAG/02-RAG进阶与召回优化实战.md)。

## 七、集群与运维

- 监控：堆内存（不超过 50% 物理、CMS/G1）、段数、CPU、慢查询。
- 避免大批量单次写入阻塞；用 bulk + 限流。
- 冷热架构：热节点 SSD、冷节点大容量，降低成本。

## 八、常见坑

1. **用 keyword 做全文** → 搜不到分词结果（应 text）。
2. **深分页 from=10000** → 性能崩，改 search_after。
3. **不分片/不副本** → 单点、容量受限。
4. **Mapping 设计错** → 需 reindex（成本高、需双写切换）。
5. **把 ES 当主库** → 它是索引不是源，源丢失无法从 ES 恢复。
6. **分词不一致** → 索引分词与查询分词不同，召回异常。
7. **堆内存过大** → GC 停顿，影响稳定性。
