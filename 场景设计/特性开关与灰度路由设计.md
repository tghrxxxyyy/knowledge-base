# 特性开关与灰度路由设计

> 板块：场景设计 　|　 返回：[README](README.md)
> 适用：功能灰度发布、A/B 测试、紧急降级、多租户差异化。

特性开关（Feature Flag）让"部署"与"发布"解耦：代码先上，通过开关控制是否对用户可见。它是**安全发布与敏捷交付**的核心基础设施。

## 一、为什么需要特性开关

- **解耦部署与发布**：代码合入主干但默认关闭，随时开启。
- **灰度**：按比例/人群放量，观察后再全量。
- **紧急熔断**：出问题一键关闭，无需回滚发版。
- **A/B 测试**：不同用户走不同实现，对比效果。

## 二、开关类型

| 类型 | 生命周期 | 例子 |
|------|----------|------|
| 发布开关 | 短期，验证后删 | 新功能灰度 |
| 运维开关 | 长期 | 降级开关、限流开关 |
| 实验开关 | 中期 | A/B 测试 |
| 权限开关 | 长期 | 白名单功能 |

> 注意：发布开关是临时的，验证完必须清理，否则开关堆积成技术债。

## 三、开关架构

```
配置中心(Nacos/Apollo) → 推送变更 → 应用本地缓存开关
                                    ↓
                          开关 SDK 判断(用户/比例/标签)
                                    ↓
                          路由到不同代码分支/服务版本
```

- 开关值存配置中心，动态推送，无需重启。
- 客户端缓存，中心不可用时用本地默认值继续运行。

## 四、灰度路由策略

| 维度 | 示例 |
|------|------|
| 用户 ID 取模 | `uid % 100 < 10` → 10% 用户 |
| 白名单 | 内部员工/种子用户先开 |
| 地域/设备 | 某城市、某 App 版本 |
| 随机比例 | 1%→10%→50%→100% 渐进 |

```java
boolean enabled = flagService.isEnabled("new_checkout",
    FlagContext.of(userId).with("region","cn"));
// 内部按 userId 哈希分桶，命中比例即开启
```

## 五、与 A/B 测试关系

- 特性开关负责"开/关"，A/B 测试负责"多版本对比"。
- 同一开关可挂多个变体（A/B/C），按分流规则分配。
- 结合埋点看转化/留存，决定优胜版本。

## 六、常见坑

1. **开关堆积不清理** → 代码里上百个死开关；建"开关生命周期"制度，验证即删。
2. **默认值不安全** → 中心挂时回退默认值导致全开/全关；默认应保守（如关闭）。
3. **缓存不一致** → 推送延迟导致实例间开关状态不一；接受短暂不一致，监控差异。
4. **开关逻辑散布** → 到处 if(flag)；集中到开关 SDK + 策略。
5. **强依赖中心** → 中心挂无法决策；本地缓存兜底。
6. **灰度无监控** → 开了不知道效果；开关开启即上监控看板。
