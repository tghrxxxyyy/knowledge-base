# 限流算法与网关实践

> 板块：场景设计 　|　 返回：[README](README.md)

## 一、为什么要限流

保护系统不被突发流量/恶意请求打垮，保障核心链路可用性。限流是稳定性三板斧之一（另见 [稳定性三板斧](稳定性三板斧：限流-熔断-降级.md)）。

## 二、限流算法

| 算法 | 思路 | 优缺点 |
|------|------|--------|
| 计数器(固定窗口) | 单位时间计数 | 简单，但有临界突刺 |
| 滑动窗口 | 细分时间段计数 | 更平滑 |
| 漏桶(Leaky Bucket) | 恒定速率流出 | 平滑，但突发被削 |
| 令牌桶(Token Bucket) | 按速率发令牌，桶可攒 | 允许一定突发，最常用 |

- **令牌桶**最常用：平时攒令牌，突发可消耗存量，兼顾平滑与突发。

```go
// 简化令牌桶
type TokenBucket struct { tokens float64; rate, cap float64; last time.Time }
func (t *TokenBucket) Allow() bool {
    now := time.Now()
    t.tokens += t.rate * now.Sub(t.last).Seconds()
    if t.tokens > t.cap { t.tokens = t.cap }
    t.last = now
    if t.tokens >= 1 { t.tokens--; return true }
    return false
}
```

## 三、限流维度

- **单机限流**：本地计数器/令牌桶，简单但集群不均。
- **分布式限流**：Redis + Lua 统一计数（如 `INCR + EXPIRE` 或令牌桶 Lua）。
- **维度**：用户/IP/接口/全局；网关层统一做，业务内做细粒度。

## 四、网关层限流

- **APISIX / Kong / Sentinel / Nginx limit_req**：网关级限流，挡在最前。
- 配合熔断降级：超限快速失败（429），而非拖垮后端。

## 五、限流策略

- 拒绝策略：快速失败 vs 排队（漏桶）。
- 热点参数限流：对某个爆款商品 ID 单独限流。
- 自适应：根据系统负载动态调整阈值。

## 六、与熔断降级配合

```
请求 → 限流(超阈值拒绝) → 熔断(依赖异常则切断) → 降级(非核心关闭) → 业务
```

## 七、常见坑

1. 固定窗口临界突刺 → 改用滑动窗口/令牌桶。
2. 分布式限流用普通自增不原子 → 用 Lua/Redis 原子。
3. 阈值拍脑袋 → 基于压测与容量定。
4. 只限入口不限依赖 → 下游仍被打垮。
5. 限流后不返回友好提示 → 客户端重试雪崩。
