# 限流算法与网关实践

> 板块：场景设计 　|　 返回：[README](README.md)
> 关联：[稳定性三板斧：限流-熔断-降级](稳定性三板斧：限流-熔断-降级.md)、[秒杀系统设计与高并发扣减](秒杀系统设计与高并发扣减.md)、[SRE/故障演练与稳定性保障](../SRE/故障演练与稳定性保障.md)

限流是稳定性三板斧之首。它的目的是：**保护系统不被突发流量或恶意请求打垮**——在过载时"宁可拒绝部分请求，也不让整体雪崩"。本文对比算法、维度、网关实践与策略组合，给出可落地的配置与代码。

## 一、为什么要限流

- **突发流量**：秒杀、热点事件、营销推送带来远超容量的瞬时请求。
- **恶意请求**：爬取、刷接口、撞库、DDoS 雏形。
- **下游有上限**：DB、第三方 API、消息队列自身有吞吐天花板，上游需节制。
- **多租户公平**：防止某一用户/业务耗尽公共资源，影响其他人。
- **容量有限是事实**：任何系统都有承载力上限，限流是"承认上限、优雅降级"的工程态度。

核心思想：**有损服务**——优先保住核心链路与大部分用户体验，牺牲小部分请求（返回 429/降级页）远比整体雪崩好。

## 二、限流算法对比

| 算法 | 思路 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 固定窗口计数器 | 单位时间计数，超阈值拒绝 | 极简、O(1) | 临界突刺（窗口切换瞬间双倍） | 粗粒度、对精度不敏感 |
| 滑动窗口（计数） | 细分时间段计数 | 比固定窗口平滑 | 实现略复杂、内存随精度增长 | 需较平滑的接口级 |
| 滑动窗口（日志） | 记录每个请求时间戳，窗口内计数 | 精确 | 存储成本高 | 中小 QPS 精确限流 |
| 漏桶 Leaky Bucket | 请求进桶，恒定速率流出 | 绝对平滑、限输出速率 | 突发被削平、不攒令牌 | 需严格匀速（如短信网关） |
| 令牌桶 Token Bucket | 按速率发令牌入桶，桶可攒 | 允许一定突发、最常用 | 需维护桶状态 | 平时平稳、偶尔突发 |

### 2.1 令牌桶（最常用）

- 平时按 `rate` 往桶里放令牌，桶有上限 `capacity`。
- 请求来取走令牌：有则放行，无则拒绝/排队。
- 空闲时攒令牌 → 可应对短时突发（攒满后允许一波突发）。
- 适合"平时平稳、偶尔突发"的互联网流量。

```
时间 →
桶:  ▢▢▢▢▢      (空闲攒满 capacity)
请求: ✓✓✗✓✓     (突发时前几个消耗攒的令牌, 第3个被拒)
```

### 2.2 漏桶（匀速）

```
请求 → [桶] → (恒定速率流出) → 下游
        ↑溢出则拒绝
```

- 流入可突发，流出恒定 → 绝对平滑，保护下游不被冲。
- 缺点：无法利用闲置容量应对突发，对延迟敏感场景不友好。

### 2.3 算法选型建议

| 目标 | 选 |
|------|----|
| 防止下游被突发冲垮、要平滑 | 漏桶 |
| 允许合理突发、用户体验好 | 令牌桶 |
| 简单粗粒度、能接受临界突刺 | 固定窗口 |
| 精确限制、QPS 不高 | 滑动日志窗口 |

## 三、算法实现

### 3.1 令牌桶（Go，单机）

```go
type TokenBucket struct {
    mu     sync.Mutex
    tokens float64
    rate   float64 // 令牌/秒
    cap    float64 // 桶容量
    last   time.Time
}
func (t *TokenBucket) Allow() bool {
    t.mu.Lock(); defer t.mu.Unlock()
    now := time.Now()
    t.tokens += t.rate * now.Sub(t.last).Seconds()
    if t.tokens > t.cap { t.tokens = t.cap }
    t.last = now
    if t.tokens >= 1 { t.tokens--; return true }
    return false
}
```

### 3.2 令牌桶（Redis + Lua，分布式原子）

```lua
-- KEYS[1]=bucket_key, ARGV[1]=rate, ARGV[2]=capacity, ARGV[3]=now_ms, ARGV[4]=cost
local rate=tonumber(ARGV[1]); local cap=tonumber(ARGV[2])
local now=tonumber(ARGV[3])/1000; local cost=tonumber(ARGV[4])
local data=redis.call('HMGET',KEYS[1],'tokens','ts')
local tokens=tonumber(data[1] or cap)
local ts=tonumber(data[2] or now)
tokens=math.min(cap, tokens + rate*(now-ts))
if tokens>=cost then
  tokens=tokens-cost
  redis.call('HMSET',KEYS[1],'tokens',tokens,'ts',now)
  return 1
end
return 0
```

> 用 Lua 保证"计算+扣减"原子，避免并发下计数不准（见常见坑 2）。

### 3.3 滑动窗口（Redis，计数）

```bash
# 用 ZSET 存时间戳，窗口内数量即计数
ZADD rl:api:{key} {now_ms} {now_ms}
ZREMRANGEBYSCORE rl:api:{key} 0 {now_ms - window_ms}
count = ZCARD rl:api:{key}
if count > limit: reject
EXPIRE rl:api:{key} window_s
```

## 四、限流维度

### 4.1 单机 vs 分布式

| 维度 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 单机 | 本地计数器/令牌桶 | 无网络开销、极快 | 集群各节点不均（总量=单机×节点数） |
| 分布式 | Redis + Lua 原子计数 | 全局精确阈值 | 有网络开销、依赖 Redis 可用 |

- 单机限流适合"每实例自我保护"；分布式适合"全局配额"（如全站 1000 QPS）。
- 实践中常 **两者叠加**：网关全局限流 + 实例本地兜底限流（Redis 挂时本地仍能挡）。

### 4.2 限流对象

- 按 **用户 / 设备 / IP / 接口 / 应用 / 全局** 限流。
- **热点参数限流**：对爆款商品 ID、热点账号、特定 API 单独限流（防单点热点打垮）。
- **分级限流**：核心接口阈值高、非核心低，保护重点链路。
- 网关层做粗粒度（全局/接口/IP），业务内做细粒度（用户级/参数级），形成纵深。

## 五、网关层限流实践

网关是"第一道防线"，挡在最前面，超限快速失败（429），不拖垮后端。

### 5.1 主流方案

| 组件 | 方式 | 特点 |
|------|------|------|
| Nginx `limit_req` | 漏桶算法，原生 | 边缘层、简单、高性能 |
| APISIX | 插件（`limit-req`/`limit-count`） | 灵活、支持多维度、易配置 |
| Kong | 插件（`rate-limiting`） | 企业级、策略丰富 |
| Sentinel | 熔断限流一体 | 自适应、热点、集群限流 |
| Envoy | 本地速率限制服务 | 云原生、与 Istio 集成 |

### 5.2 Nginx 示例

```nginx
http {
  limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;
  limit_req_zone $server_name        zone=perserver:10m rate=100r/s;
  server {
    location /api/ {
      limit_req zone=perip burst=20 nodelay;  # 突发20, 不延迟
      limit_req_status 429;
      proxy_pass http://backend;
    }
  }
}
```

### 5.3 APISIX 示例

```yaml
# 路由上挂限流插件（每分钟每 IP 100 次）
plugins:
  limit-req:
    rate: 100
    burst: 50
    key: remote_addr
    rejected_code: 429
```

### 5.4 Sentinel 示例（Java）

```java
// 定义资源 + 规则
try (Entry e = SphU.entry("createOrder")) {
    // 业务
} catch (BlockException ex) {
    // 被限流：快速失败/降级
    return Result.throttled();
}
// 规则（控制台或代码配置）
List<FlowRule> rules = new ArrayList<>();
FlowRule r = new FlowRule("createOrder").setCount(100).setGrade(RuleConstant.FLOW_GRADE_QPS);
rules.add(r);
FlowRuleManager.loadRules(rules);
```

## 六、限流策略

- **拒绝策略**：
  - 快速失败（直接 429）——最常用，保护后端。
  - 排队等待（漏桶）——平滑但增加延迟，适合内部批处理。
- **友好提示**：限流后返回明确信息（如 `Retry-After` 头、提示"稍后再试"），避免客户端盲目重试（重试会加剧雪崩）。
- **自适应限流**：根据系统负载（CPU、线程池、延迟、错误率）动态调整阈值。例如 Netflix 的 **并发度自适应**（基于 Little's Law 估算系统容量）。
- **分级限流**：核心接口阈值高，非核心低，保护重点。
- **预热限流**：系统冷启动/扩容后，阈值从低逐步升到目标，避免冷机器被瞬间打满（令牌桶支持预热曲线）。

## 七、与熔断、降级配合

```
请求 → 限流(超阈值拒绝) → 熔断(依赖异常则切断) → 降级(非核心关闭) → 业务
```

- **限流**防"自己被打爆"（入口流量管控）。
- **熔断**防"依赖拖垮自己"（下游异常时切断）。
- **降级**保"核心链路"（非核心功能关闭/返回缓存）。
- 三者形成纵深防御，缺一不可。限流挡住大部分，熔断防穿透，降级保底线。

## 八、参数设定（基于容量，不拍脑袋）

| 步骤 | 做法 |
|------|------|
| 压测 | 单实例能扛多少 QPS（不同场景/数据量） |
| 定峰值 | 正常峰值、极端峰值分别评估 |
| 设阈值 | 阈值 = 实测容量 × 冗余系数（如 0.7~0.8） |
| 分维度 | 全局、接口、用户级分别设 |
| 灰度 | 先松后紧，观察拒绝率调优 |
| 监控 | 拒绝率、被限流 Top IP/用户、P99 延迟 |

- 阈值过低 → 误伤正常用户；过高 → 限流形同虚设。靠监控闭环调优。
- 区分正常峰值与极端峰值，分别设阈值与应对（极端峰值可更激进拒绝）。

## 九、真实案例启发

- **秒杀**：入口网关令牌桶（如 1 万 QPS）→ 库存校验 → 下单队列（漏桶匀速落库），防止超卖与 DB 被打爆。见 [秒杀系统设计与高并发扣减](秒杀系统设计与高并发扣减.md)。
- **短信网关**：漏桶严格匀速，避免被运营商限流/封号。
- **开放 API**：按 `appKey` 分布式令牌桶，保证多租户公平、防单租户耗尽。

## 十、常见坑

1. **固定窗口临界突刺** → 窗口切换瞬间可能放行双倍，改滑动窗口/令牌桶。
2. **分布式限流非原子** → 自增不加锁计数不准，必须用 Lua/Redis 原子操作。
3. **阈值拍脑袋** → 基于压测与容量定，否则要么误伤要么无效。
4. **只限入口不限依赖** → 下游（DB/第三方）仍被打垮，需全链路限流。
5. **限流后不友好提示** → 客户端重试雪崩，应返回 429 + Retry-After。
6. **限流误伤核心** → 未区分核心/非核心，关键链路被拒，需分级限流。
7. **Redis 挂导致限流失效** → 应本地兜底限流，避免全开。
8. **限流 key 设计过粗** → 全站一个 key 把正常流量也限了，需细分维度。
9. **突发 burst 设 0** → 正常抖动也被拒，应设合理 burst 吸收毛刺。
10. **不监控拒绝率** → 限流悄悄误伤用户，应有告警与看板。

## 十一、落地清单

1. 选算法（平时突发用令牌桶，匀速用漏桶）。
2. 定维度（全局/接口/用户/热点参数）。
3. 网关层做第一道（Nginx/APISIX/Sentinel），应用内做纵深。
4. 分布式用 Redis+Lua 原子，单机加本地兜底。
5. 阈值基于压测 + 冗余系数，灰度调优。
6. 限流后友好提示 + 监控拒绝率 + 与熔断降级联动。
