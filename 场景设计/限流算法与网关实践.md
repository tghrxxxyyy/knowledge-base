# 限流算法与网关实践

> 板块：场景设计 　|　 返回：[README](README.md)

限流是稳定性三板斧之一（另见 [稳定性三板斧：限流-熔断-降级](稳定性三板斧：限流-熔断-降级.md)）。它的目的是：**保护系统不被突发流量或恶意请求打垮**，在过载时"宁可拒绝部分请求，也不让整体雪崩"。本文对比算法、维度、网关实践与策略组合。

## 一、为什么要限流

- 突发流量（秒杀、热点事件）超出系统处理能力。
- 恶意请求（爬取、刷接口、DDoS 雏形）。
- 下游依赖自身有上限，上游需节制。
- 多租户公平：防止某一用户/业务耗尽资源。

核心思想：**有损服务**——承认容量有限，优先保住核心链路与大部分用户体验。

## 二、限流算法对比

| 算法 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口计数器 | 单位时间计数，超阈值拒绝 | 简单 | 临界突刺（窗口切换瞬间双倍） |
| 滑动窗口 | 细分时间段计数 | 更平滑，缓解突刺 | 实现略复杂 |
| 漏桶（Leaky Bucket） | 请求进桶，恒定速率流出 | 绝对平滑，限输出速率 | 突发被削平，不攒令牌 |
| 令牌桶（Token Bucket） | 按速率发令牌入桶，桶可攒 | 允许一定突发，最常用 | 需维护桶状态 |

### 2.1 令牌桶最常用

- 平时按速率往桶里放令牌，桶有上限（容量）。
- 请求来取走令牌：有则放行，无则拒绝/排队。
- 空闲时攒令牌 → 可应对短时突发（如攒满后允许一波突发）。
- 适合"平时平稳、偶尔突发"的互联网流量。

### 2.2 简化实现

```go
type TokenBucket struct {
    tokens      float64
    rate, cap   float64
    last        time.Time
}
func (t *TokenBucket) Allow() bool {
    now := time.Now()
    t.tokens += t.rate * now.Sub(t.last).Seconds()
    if t.tokens > t.cap { t.tokens = t.cap }
    t.last = now
    if t.tokens >= 1 { t.tokens--; return true }
    return false
}
```

## 三、限流维度

### 3.1 单机 vs 分布式

- **单机限流**：本地计数器/令牌桶，简单、无网络开销，但集群各节点不均（总量 = 单机×节点数）。
- **分布式限流**：用 Redis + Lua 原子操作统一计数（如 `INCR + EXPIRE`，或 Lua 实现令牌桶），保证全局阈值。

### 3.2 限流维度

- 按 **用户 / 设备 / IP / 接口 / 全局** 限流。
- 热点参数限流：对爆款商品 ID、热点账号单独限流。
- 网关层做粗粒度（全局/接口），业务内做细粒度（用户级）。

## 四、网关层限流

- **APISIX / Kong / Sentinel / Nginx limit_req**：网关/边缘层统一限流，挡在最前面。
- 配合熔断降级：超限快速失败（返回 429 Too Many Requests），而非拖垮后端。
- 网关限流是"第一道防线"，应用内限流是"纵深防御"。

## 五、限流策略

- **拒绝策略**：快速失败（直接 429） vs 排队（漏桶，平滑但增加延迟）。
- **友好提示**：限流后返回明确信息，避免客户端盲目重试（重试会加剧雪崩）。
- **自适应限流**：根据系统负载（CPU、线程池、延迟）动态调整阈值（如自适应丢弃）。
- **分级限流**：核心接口阈值高，非核心低，保护重点。

## 六、与熔断、降级配合

```
请求 → 限流(超阈值拒绝) → 熔断(依赖异常则切断) → 降级(非核心关闭) → 业务
```

- 限流防"自己被打爆"。
- 熔断防"依赖拖垮自己"。
- 降级保"核心链路"。
三者形成纵深防御，缺一不可。

## 七、参数设定

- 阈值不可拍脑袋：基于**压测**（单实例能扛多少 QPS）+ 冗余系数。
- 区分正常峰值与极端峰值，分别设阈值与应对。
- 限流后监控拒绝率，过低说明阈值松、过高说明误伤。

## 八、常见坑

1. **固定窗口临界突刺** → 改用滑动窗口/令牌桶。
2. **分布式限流非原子** → 自增不加锁导致计数不准，必须用 Lua/Redis 原子。
3. **阈值拍脑袋** → 基于压测与容量定，否则要么误伤要么无效。
4. **只限入口不限依赖** → 下游（DB/第三方）仍被打垮。
5. **限流后不友好提示** → 客户端重试雪崩。
6. **限流误伤核心** → 未区分核心/非核心，关键链路被拒。
