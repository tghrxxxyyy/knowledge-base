# 权限系统设计（RBAC / ABAC）

> 权限是几乎所有系统的地基：谁能看、谁能改、谁能删。面试必考「设计一个权限系统」——核心是**模型选择（RBAC/ABAC）+ 数据模型 + 性能与扩展**。本篇讲「解决的问题 → 三大模型 → 数据表设计 → 高性能实现 → 面试答题框架」。

---

## 一、解决的问题与定位

**解决的问题**：回答「**用户 u 对资源 r 有没有权限 p**」这个查询，并支持：
- 细粒度控制（某人只能看自己部门的数据——行级）；
- 弹性管理（新入职自动有默认角色、换部门自动失权）；
- 可审计（谁在何时做了什么）。

**定位一句话**：**「用『用户-角色-权限-资源』四要素把权限建模，用拦截器/注解统一鉴权，用缓存+位图压性能」——模型选型决定一切。**

---

## 二、三大模型（面试核心）

### 2.1 RBAC（基于角色的访问控制）——90% 系统的答案

```
用户 ──多对多──> 角色(如: 运营) ──多对多──> 权限(如: 商品上架)
权限 = 操作(create/read/update/delete) × 资源(商品/订单/用户)
```

- **核心优点**：管理粒度适中——用户数量多、角色数量少，权限挂角色而非用户，新增/离职只动关系表；
- **变体**：RBAC0（基础）、RBAC1（角色继承：子角色继承父角色权限）、RBAC2（约束：互斥角色，如"出纳"与"会计"不能同一人）、RBAC3（1+2）；
- **适用**：后台管理系统、企业应用——**绝大多数场景首选**。

### 2.2 ABAC（基于属性的访问控制）——灵活但复杂

```
规则: 允许 员工 查看 订单，当 (订单.owner == 用户.id) 或 (用户.role == "管理员")
条件 = 主体属性 + 资源属性 + 环境属性(时间/IP/设备) + 操作
```

- **优点**：**行级/数据级权限**表达力强（数据权限：只看本部门数据），无需为每个数据权限建角色；
- **缺点**：策略引擎复杂、性能开销大、规则难调试；
- **适用**：复杂业务系统（ERP/金融/医疗）、数据权限场景。

### 2.3 ACL（访问控制列表）

```
资源 -> 授权对象列表: {用户A: 读, 用户B: 读写}
```

- 直接但**管理爆炸**（资源多 × 用户多）；适用于文档协作等小规模场景。

## 三、数据模型设计（RBAC 标准五表）

```
┌────────────┐    ┌──────────────┐    ┌────────────┐
│ user       │    │ user_role    │    │ role       │
├────────────┤    ├──────────────┤    ├────────────┤
│ id,name... │◄───┤ user_id      │───►│ id,name    │
└────────────┘    │ role_id      │    └─────┬──────┘
                 └──────────────┘          │
┌────────────┐    ┌──────────────┐         │
│ permission │◄───┤ role_perm    │         │
├────────────┤    ├──────────────┤         │
│ id,code    │◄───┤ role_id      │◄────────┘
│ res,action │    │ perm_id      │
└────────────┘    └──────────────┘
```

- **五表**：user / role / permission（或 menu）/ user_role / role_perm（树形菜单可用单表 parent_id 表达角色继承与菜单层级）；
- **权限粒度**：`permission` 表存「资源 + 操作」对（如 `order:create`），**按钮级权限**= 细化操作（`order:export`）；
- **数据权限**（行级）：角色上挂数据范围（全部/本部门/本人），查询时拼 SQL 条件（`WHERE dept_id IN (...)`）；
- 扩展：加 **user_permission 直挂表**（角色外额外授权），满足「临时给某人开个权限」。

## 四、高性能与工程实现

### 4.1 鉴权链路

```
请求 → 网关/拦截器: 解析 Token(JWT) → 取用户 → 取权限列表(缓存)
     → 注解/中间件(@PreAuthorize / AOP) 校验 → 通过放行 / 403
```

### 4.2 性能要点

1. **权限缓存**：用户权限列表缓存 Redis（TTL + 变更主动失效），避免每次查库；
2. **位图加速**：权限编码为位（如 64 位整数），角色=权限位 OR 集合，校验 = `(perm & roleBits) != 0`——O(1) 判断；
3. **网关前置**：粗粒度（路径级）在网关拦截，细粒度（数据级）在业务内执行；
4. **变更一致性**：角色变更 → 广播失效缓存（用户量级小直接全量刷新）。

### 4.3 安全细节

- 权限**必须后端校验**（前端隐藏按钮只是体验）；
- 越权测试用例：改 ID 访问他人资源（IDOR）→ 数据权限兜底；
- 敏感操作（提现/删除）二次确认 + 审计日志（操作人/时间/结果入库）。

## 五、面试答题框架

1. **需求澄清**：管理端/开放平台？要数据权限吗？用户量/角色量规模？
2. **选型**：默认 RBAC（+角色继承）；行级数据权限 → 引入 ABAC 规则引擎或「数据范围」字段；
3. **数据模型**：五表关系 + 按钮级权限 + 数据权限实现；
4. **实现**：JWT → 拦截器 → 缓存权限位图 → AOP 注解校验；
5. **扩展**：权限变更即时生效、审计日志、开放平台用 OAuth2 + Scope。

## 六、速查表

| 主题 | 一句话 |
|------|--------|
| RBAC | 用户↔角色↔权限↔资源，五表模型，管理端首选 |
| ABAC | 属性规则引擎，行级/数据权限强，复杂 |
| ACL | 资源挂授权列表，小规模直给 |
| 实现 | 拦截器 + 缓存 + 位图 + 注解校验 |
| 安全 | 后端强校验、防 IDOR、审计日志 |
