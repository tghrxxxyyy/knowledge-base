# 推送系统与长连接架构进阶

> 本文在 IM 长连接（见 IM 章节）基础上，聚焦"推送系统"的架构：在线推送（长连接 Push）与离线推送（厂商通道）、推送链路、扇出与限流、到达率与保活、以及典型踩坑。内容基于公开工业实践，参数以业务为准。

## 1. 推送系统的职责

- 把服务端产生的事件（消息、通知、提醒）主动送达客户端。
- 与 IM 区别：IM 是双向聊天，推送更偏"服务端→用户"的通知。
- 核心价值：实时触达、唤醒用户、提升活跃。

## 2. 在线推送：长连接 Push

- 客户端维持长连接（TCP/WebSocket）到接入层。
- 服务端有消息，经接入层直接下发该连接。
- 低延迟、可控、不依赖系统通道。
- 与 IM 长连接架构一致（见 IM 章节）。

## 3. 离线推送：厂商通道

- App 退到后台或被杀，自有长连接断开。
- 走系统厂商推送通道（APNs/iOS、FCM/海外、各安卓厂商推送）。
- 服务端把消息发到厂商，由系统投递。
- 厂商通道有负载与格式限制（标题/正文/透传）。

## 4. 推送链路

```
业务事件 → 推送服务(构建通知) → 路由(在线/离线)
   → 在线: 接入层长连接 Push
   → 离线: 厂商通道 API
   → 客户端展示/点击
   → 上报(到达/点击) 回执
```

## 5. 用户与设备映射

- 一个用户可能多设备（手机/平板）。
- 需维护 userId ↔ deviceToken（厂商 token）/ connId（自有连接）。
- 设备 token 变更（重装/换机）需更新。
- 推送时按目标设备集合扇出。

## 6. 扇出（Fan-out）

- 单条通知可能发给海量用户（如广播）。
- 不能逐条同步发，需异步批量扇出。
- 写入任务队列，多 worker 并发推。
- 厂商通道有 QPS 限制，需限流与分批。

## 7. 限流与配额

- 厂商通道每日/每设备有推送配额。
- 自有通道需保护接入层（连接数、下行速率）。
- 重要通知优先，营销通知降级/合并。
- 避免对用户过度推送（打扰 → 卸载）。

## 8. 到达率与保活

- 在线到达率：长连接健康度决定。
- 离线到达率：厂商通道配额、分类（通知/营销）、用户设置。
- 保活：移动端长连接心跳、厂商通道合规保活。
- 监控：下发数、到达数、点击数，算转化率。

## 9. 推送内容治理

- 分类：IM 消息、系统通知、营销活动。
- 频控：同一用户单位时间内最多 N 条，避免轰炸。
- 去重：同事件不重复推。
- 静默/免打扰：用户设置与时段控制。
- 内容安全过滤。

## 10. 点击与归因

- 用户点击通知 → 上报 → 跳转对应页。
- 归因：推送带来的打开/转化。
- 用于优化推送时机与内容。
- 深链（deep link）提升体验。

## 11. 与 IM 的关系

- 二者共用长连接接入层（见 IM 章节）。
- 推送可复用 IM 的连接与路由。
- 区别：推送偏服务端发起、可走厂商通道。
- 很多系统把二者合并为统一消息平台。

## 12. 实时性要求

- IM 类消息：秒级。
- 营销通知：分钟级可接受。
- 风控/安全：即时。
- 按类型定 SLA，不必一刀切。

## 13. 多租户/多 App

- 一个推送平台服务多个 App/业务线。
- 配置隔离：证书（APNs）、厂商密钥、频控策略。
- 配额隔离：避免一业务耗尽共享通道。
- 与多租户架构（见多集群/租户章节）呼应。

## 14. 常见踩坑

1. **只走自有通道**：App 后台被杀收不到；必须接厂商通道。
2. **无频控**：轰炸用户致卸载；按用户/类型限频。
3. **token 不更新**：重装后推到旧设备；维护 token 生命周期。
4. **厂商配额耗尽**：营销占满，重要通知发不出；配额分级。
5. **无到达率监控**：以为发了就到了；建回执与监控。
6. **长连接保活不当**：被系统杀，在线转离线；合规心跳。
7. **重复推送**：同事件多触发；去重键。

## 15. 离线通道细节

- iOS：APNs，需证书/Token 认证，payload 有大小限制。
- 安卓：各厂商（华为/小米/OPPO/vivo 等）独立通道，需分别接入。
- 海外：FCM。
- 统一封装：屏蔽厂商差异，提供一致 API。

## 16. 架构演进

- 起步：单通道（自有或单一厂商）。
- 发展：在线+离线双通道，统一推送服务。
- 成熟：多 App/多租户、频控/配额/归因、监控闭环。
- 合并 IM 与推送为消息中台。

## 17. 指标看板

- 下发量、在线推送量、厂商通道量。
- 到达率（在线/离线）、点击率。
- 厂商通道失败原因分布。
- 用户投诉/退订率。

## 18. 与稳定性关系

- 推送高峰（大促/突发）需削峰（MQ）。
- 厂商通道限流需退避重试。
- 推送服务自身高可用（多实例、无状态）。
- 见容错与高并发章节。

## 19. 隐私与合规

- 推送内容不泄露敏感信息（通知栏可见）。
- 用户可关闭/退订，需尊重。
- 设备 token 属个人数据，妥善管理。
- 以当地法规为准。

## 20. 小结

推送系统是"在线长连接 Push + 离线厂商通道"的双轨架构：在线走自有连接低延迟，离线走 APNs/厂商通道兜底。设计铁律：**双通道互补、token 生命周期管理、频控防骚扰、配额分级保重要、到达率可监控、去重防重复**。与 IM 共用接入层，统一为消息平台是成熟演进方向。
