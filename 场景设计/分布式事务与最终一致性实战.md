# 分布式事务与最终一致性实战

> 本文系统梳理分布式系统中"如何保证多个服务/库的数据一致"：从刚性事务（2PC）到柔性事务（TCC、Saga、本地消息表、事务消息、最大努力通知），并给出选型决策与幂等、空回滚、防悬挂等工程细节。

## 1. 为什么分布式事务难

单体库用本地事务（ACID）即可保证原子性。拆微服务后，一个业务操作跨多个库/服务，无法用单库事务，出现"部分成功部分失败"的不一致窗口。CAP 定理告诉我们：网络分区下只能在一致性与可用性间取舍，因此多数分布式系统选择**最终一致性**而非强一致。

## 2. 一致性模型光谱

- **强一致**：读总能看到最新写（如单库事务、Raft 提交后）。
- **最终一致**：允许短暂不一致，经过一段时间后一致。
- **因果一致 / 会话一致**：稍弱于强一致，满足特定顺序保证。

实战中多数业务可接受最终一致，只要"用户最终看到正确结果"且"不出现资损"。

## 3. 两阶段提交（2PC）

### 3.1 流程

- **准备阶段（Prepare）**：协调者询问所有参与者能否提交，参与者锁资源并写 undo/redo 日志。
- **提交阶段（Commit/Rollback）**：若全部同意，协调者发提交；否则发回滚。

### 3.2 优缺点

- 优点：强一致、协议简单。
- 缺点：同步阻塞（资源锁到提交结束）、协调者单点、数据不一致风险（协调者宕机在 commit 阶段可能部分提交）。

### 3.3 适用

仅适合短事务、参与者少、对一致性要求极高且能容忍锁的场景（如传统企业内网）。互联网高并发少用。

## 4. 三阶段提交（3PC）

在 2PC 上加"预询问"与超时机制，降低阻塞，但仍复杂且未彻底解决不一致，实践中少见。

## 5. TCC（Try-Confirm-Cancel）

### 5.1 三阶段

- **Try**：预留资源（如冻结库存、预扣款），不做真正提交。
- **Confirm**：真正确认执行，需幂等。
- **Cancel**：释放预留资源，需幂等。

### 5.2 适用

对一致性要求高、有明确"预留/释放"语义的业务（下单冻库存、转账预扣）。业务侵入强（要写三套逻辑）。

### 5.3 三大坑

- **空回滚**：Try 未执行但收到 Cancel（网络丢 Try），Cancel 需识别并直接返回成功。
- **防悬挂**：Cancel 比 Try 先到（网络乱序），之后 Try 到达又执行了预留，需记录"已取消"标记拒绝后续 Try。
- **幂等**：Confirm/Cancel 可能重复触发，必须幂等。

## 6. Saga 模式

### 6.1 思路

把长事务拆成一系列本地事务，每步有对应**补偿（Compensating）**操作。出错时逆序补偿。

- **编排式（Orchestration）**：中央协调器顺序调用各服务并触发补偿。
- **协同式（Choreography）**：各服务通过事件链式触发，无中央协调。

### 6.2 适用

长流程、跨多服务（下单→扣库存→支付→物流），难以用 TCC 预留语义的场景。

### 6.3 局限

- 补偿不是"回滚"，而是反向业务操作（如取消订单而非删库）。
- 隔离性差（补偿前其他事务可能读到中间状态），需业务层处理。

## 7. 本地消息表

### 7.1 思路

利用本地事务：业务写库与"消息记录"在同一本地事务提交，保证"业务成功必有消息"。独立线程/任务轮询消息表，发送到 MQ，成功后标记。

### 7.2 优点

不依赖特殊 MQ 能力，用普通 DB + MQ 即可实现最终一致。

### 7.3 局限

消息表与业务耦合；需处理发送失败重试与幂等消费。

## 8. 事务消息（RocketMQ 等）

### 8.1 半消息机制

- 发送"半消息"（对消费者不可见）。
- 本地事务执行并回报状态（提交/回滚）。
- 提交后消息才对消费者可见；回滚则丢弃。
- MQ 有回查机制：若长时间未收到状态，回查生产者本地事务结果。

### 8.2 适用

已有支持事务消息的 MQ（如 RocketMQ），可省去自建消息表的麻烦。

## 9. 最大努力通知

最简方案：本地事务成功后，尽最大努力（多次重试）通知下游。不保证强一致，适合对一致性要求低的场景（如支付结果通知）。

## 10. 幂等是基石

无论哪种方案，消费端必须幂等，因为消息/补偿必然重复：

- **唯一键**：业务唯一号（order_id）做唯一索引，重复插入报错即跳过。
- **状态机**：已处理状态不重复处理（如订单已支付则不重复扣款）。
- **去重表**：记录已处理消息 ID。
- **Token**：下单前获取幂等 token，提交时校验。

## 11. 选型决策

| 场景 | 推荐 |
|---|---|
| 短事务、强一致、低并发 | 2PC（谨慎） |
| 有预留语义、高一致 | TCC |
| 长流程、跨多服务 | Saga |
| 有事务消息 MQ | 事务消息 |
| 无特殊 MQ、求稳 | 本地消息表 |
| 弱一致通知 | 最大努力通知 |

## 12. 一致性保障清单

1. 明确业务可接受"最终一致"还是必须"强一致"。
2. 优先选对业务侵入小的方案（消息类 > TCC > 2PC）。
3. 所有消费/补偿必须幂等。
4. 设计空回滚、防悬挂（TCC）。
5. 补偿操作要可观测、可重试、可人工介入。
6. 用对账系统兜底：定时核对各系统数据，发现不一致自动/人工修复。

## 13. 对账兜底

再完美的分布式事务方案也可能因极端故障不一致，因此**离线对账**是最后防线：

- 每日/实时核对上下游（如支付与订单、账务与流水）。
- 差异告警并进入差错处理流程。
- 差错账支持冲正、挂账、人工调账。

## 14. 常见踩坑

1. **用 2PC 扛高并发**：锁资源导致雪崩；应转最终一致。
2. **TCC 漏写幂等/空回滚**：网络异常致资损或悬挂。
3. **Saga 补偿当回滚**：补偿是反向业务，需考虑补偿期间的状态可见性。
4. **消费不幂等**：重复消息导致重复扣款/发货。
5. **无对账兜底**：相信方案 100% 可靠，极端故障无人发现。
6. **跨库事务当本地事务**：误以为 Spring @Transactional 能跨服务，实际只管单数据源。

## 15. 小结

分布式事务没有银弹。互联网实践的主流是"最终一致性 + 幂等 + 补偿 + 对账兜底"，而非强一致 2PC。选型看一致性要求、业务语义（能否预留/补偿）与团队对复杂度的承受力，并永远把幂等和对账作为底线工程。
