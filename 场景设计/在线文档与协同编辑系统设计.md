# 在线文档与协同编辑系统设计深入（Yjs 实现 / CRDT 深入 / 冲突策略 / 持久化 / 性能）

> 多人同时编辑一个文档，互不覆盖、体验丝滑——协同编辑的核心难题。本篇深入拆解：Yjs 内部实现、CRDT 细节、冲突解决策略、持久化架构、性能优化。

---

## 一、核心难点

```
用户A: 在位置3插入 "x"
用户B: 在位置5插入 "y"     ← 并发发生, 互不知晓
若都按自己的"位置"插入 → 顺序不一致 → 内容分叉
```

难点本质：**每个操作携带的位置信息，在别人并发操作后"失效"了**。两派解决方案：

| 路线 | 核心思想 | 代表 | 场景 |
|------|---------|------|------|
| **OT（操作变换）** | 并发操作**互相变换**（transform），把位置修正后再合并 | Google Docs、腾讯文档（早期） | 传统在线文档 |
| **CRDT** | 操作**天然可交换**（commutative），无论顺序如何结果一致 | Yjs（YATA）、Automerge、Figma | 现代协同、离线协同 |

## 二、Yjs 内部实现（深入）

### 2.1 YATA 算法核心

```
Yjs 使用 YATA（Yet Another Transformation Approach）算法：

每个字符带唯一 ID：(clientID, clock)
  clientID：客户端唯一标识（随机/分配）
  clock：该客户端递增计数器

插入时携带：
  左邻居 ID（origin）
  右邻居 ID（right origin）
  即：字符 = {ID, leftOrigin, rightOrigin, content}

冲突解决：
  并发插入同位置 → 比较 (clientID, clock)
  小者在前（确定性，所有节点一致）
```

### 2.2 删除标记（Tombstone）

```
删除 ≠ 物理移除，而是标记 deleted：
  {ID: (1, 5), content: "x", deleted: true}

原因：
  CRDT 需要保留删除标记来判定并发操作
  （对方插入到我刚删的位置时，要知道该字符存在过）

存储开销：
  每个删除字符保留 Tombstone
  → 长期编辑文档 Tombstone 膨胀
  → Yjs 定期 GC（仅同步状态下可清理）
```

### 2.3 更新（Update）格式

```
Yjs 更新 = 二进制的增量操作日志
  每步操作 → 编码进 Update
  同步 = 交换 Update（增量/增量补丁）

同步机制：
  连接建立 → 交换状态向量（每个客户端最新 clock）
  → 计算缺失 Update → 增量补发
  断线重连 → 状态向量对比 → 只补缺失部分

性能：
  Update 压缩（二进制编码）
  状态向量交换 O(客户端数)
  增量传输（不重传全量）
```

## 三、OT 原理（回顾）

### 3.1 三步模型

```
1. 客户端发出操作 op（如 insert(pos=3, "x")）
2. 服务端/对端收到并发 op 后, 调用 transform(opA, opB) → opA'（把位置修正）
3. 应用 opA' 后, 两端结果一致
```

### 3.2 transform 示例

- 双方插入位置不同：`insert(3,"x")` 与 `insert(5,"y")` → 修正为 `insert(4,"y")`；
- 一方插入、一方删除：插入位置在删除区间内 → 插入位置前移/后移。

### 3.3 OT 的坑

- 需要**中心化服务器**做排序与变换，离线编辑支持差；
- transform 函数按操作类型组合爆炸，实现与测试成本高；
- 文本用**位置索引**做变换，天然耦合。

## 四、冲突解决策略对比

| 策略 | 原理 | 场景 |
|------|------|------|
| Last-Write-Wins | 最后写入者胜出 | 简单字段（标题/颜色） |
| 合并（Merge） | 并发修改合并 | 列表/富文本 |
| 优先级 | 高优先级用户胜出 | 权限协作 |
| 人工解决 | 冲突标记人工处理 | 表格/复杂场景 |

```
混合策略：
  标题/元数据 → Last-Write-Wins
  正文 → CRDT 自动合并
  冲突标记 → 人工解决（评论区）
```

## 五、架构落地：在线文档系统

```
客户端(编辑器) ── WebSocket 长连接 ──> 网关/接入层
                                        │
               协同服务(房间/文档维度): 广播 + 冲突解决(CRDT状态)
                                        │
               存储: 文档快照(定期) + 操作日志(OpLog) + 光标/心跳

辅助: 权限(查看/编辑/评论)、离线队列(断网积攒操作, 重连合并)、
     版本历史(回滚=重放操作)、全文检索(异步)、CDN静态资源
```

### 5.1 关键组件

| 组件 | 职责 | 实现要点 |
|------|------|----------|
| 实时通道 | WebSocket 房间模型 | 每文档一个 room，连接数 × 文档数规划 |
| 协同引擎 | Yjs Document 状态 | 双向绑定编辑器（ProseMirror/Quill 适配器） |
| 持久化 | 快照 + 操作日志 | 重建 = 加载快照 + 重放；定期压缩 |
| 离线 | 积攒操作队列 | 恢复连接后批量提交（CRDT 天然支持） |
| 鉴权 | 权限 + 并发限制 | 每文档在线上限、只读降级、限流 |

### 5.2 房间模型

```
房间 = 一个文档的实时协作单元

服务端：
  RoomService：管理房间生命周期
  每房间一个 CRDT 状态（内存）
  房间内广播（发布订阅）

连接规划：
  在线用户 × 连接数 = 并发连接
  10 万在线 → 10 万 WebSocket 连接
  服务器：单机 ~1 万连接，10 台网关

分区：
  按文档 ID 哈希 → 分配房间到网关节点
  大文档（多人同时编辑）→ 独立节点
```

## 六、持久化架构

### 6.1 快照 + OpLog

```
写路径：
  操作到达 → 更新内存 CRDT 状态
  → 操作日志追加（OpLog，WAL 模式）
  → 定期（10s/100 操作）写快照

读路径（文档加载）：
  加载最近快照 → 重放后续操作
  → 得到最新状态

压缩：
  快照生成后 → 清理该时刻前的 OpLog
  定期 GC（Tombstone 清理）
```

### 6.2 存储选型

| 存储 | 用途 | 特点 |
|------|------|------|
| Redis | 房间状态/在线列表 | 快、易失 |
| MongoDB/MySQL | 文档快照 + OpLog | 持久、可扩展 |
| 对象存储 | 历史版本归档 | 便宜、低频 |

### 6.3 版本历史与回滚

```
版本 = 快照 + 操作时间线

回滚：
  加载目标版本快照 → 重放到目标时间点
  回滚操作可逆（新操作继续追加）

对比/差异：
  任意两版本 diff（CRDT 状态对比）
```

## 七、性能优化

### 7.1 客户端

```
编辑器性能：
  大文档（10 万字符）渲染优化：
    ProseMirror 虚拟化渲染
    懒加载（视口内渲染）
  操作合并：
    连续输入合并为一个操作（减少同步）

本地优先：
  输入即时渲染（乐观更新）
  后台同步（不阻塞输入）
```

### 7.2 服务端

```
广播优化：
  房间内广播（按房间分片）
  增量更新（只发变化部分）
  批量广播（合并同一 tick 的操作）

状态同步：
  状态向量交换（增量补发）
  连接数监控（单节点上限告警）
  大房间拆分（多人同文档 → 分片）
```

### 7.3 容量估算

```
文档状态内存：
  100 万字符 ≈ 每个字符 ~50B（ID+内容+指针）
  ≈ 50MB/文档（极端大文档）

并发连接：
  每连接 ~10KB（缓冲区）
  10 万连接 ≈ 1GB

规划：
  大文档独立节点
  连接按网关集群水平扩展
```

## 九、面试答题框架

1. **需求澄清**：并发编辑、实时性、离线支持、回滚历史、协作规模（N 人）；
2. **点破难点**：并发操作的**位置冲突** → 引出 OT/CRDT 二分；
3. **讲 OT**：transform 思想 + Google Docs 中心化架构 + 局限；
4. **讲 CRDT**：操作可交换 + YATA/RGA + Yjs/Automerge 生态 + 优点（离线/收敛性）；
5. **落地**：WebSocket 房间、快照+OpLog、权限、限流、监控。
