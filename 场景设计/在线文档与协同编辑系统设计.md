# 在线文档与协同编辑系统设计（OT / CRDT）

> 「多人同时编辑一个文档，互不覆盖、体验丝滑」是协同编辑的核心难题，也是大厂高频场景题。本篇讲「解决的问题 → 文本模型 → OT vs CRDT 两条技术路线 → 架构落地 → 面试答题框架」。

---

## 一、解决的问题与定位

**解决的问题**：多用户**并发**编辑同一文档（打字、删除、插入），保证：
1. **一致性**：所有人最终看到相同内容（converge）；
2. **即时性**：对方输入立刻可见（latency 低）；
3. **不丢失**：谁的修改都不被覆盖。

朴素方案（整文覆盖 / 最后写入胜出）会互相踩——这就是「冲突」问题。协同编辑 = 冲突处理方案。

**定位一句话**：**「用操作（Operation）而不是文档状态做同步，配合变换/合并算法保证并发操作收敛」——技术路线两派：OT（操作变换）与 CRDT（无冲突复制数据类型）。**

---

## 二、核心难点：为什么难？

```
用户A: 在位置3插入 "x"
用户B: 在位置5插入 "y"     ← 并发发生, 互不知晓
若都按自己的"位置"插入 → 顺序不一致 → 内容分叉
```

难点本质：**每个操作携带的位置信息，在别人并发操作后"失效"了**——A 的"位置3"在 B 插入后可能应该变成位置4。两派解决方案：

| 路线 | 核心思想 | 代表 | 场景 |
|------|---------|------|------|
| **OT（操作变换）** | 并发操作**互相变换**（transform），把位置修正后再合并 | Google Docs、腾讯文档（早期）、Yjs 可配 OT | 传统在线文档 |
| **CRDT** | 操作**天然可交换**（commutative），无论顺序如何结果一致，无需变换 | Yjs（YATA）、Automerge、Figma（内部） | 现代协同、离线协同 |

## 三、OT（Operational Transformation）原理

### 3.1 三步模型（经典面试必背）

```
1. 客户端发出操作 op（如 insert(pos=3, "x")）
2. 服务端/对端收到并发 op 后, 调用 transform(opA, opB) → opA'（把位置修正）
3. 应用 opA' 后, 两端结果一致
```

### 3.2 transform 示例

- 双方插入位置不同：`insert(3,"x")` 与 `insert(5,"y")` → 修正为 `insert(4,"y")`（对方先于自己）；
- 一方插入、一方删除：插入位置在删除区间内 → 插入位置前移/后移，保证引用不悬空。

### 3.3 OT 的坑

- 需要**中心化服务器做排序与变换**（Google 架构：客户端→服务器→广播），离线编辑支持差；
- transform 函数按操作类型组合爆炸（insert/delete/retain × 排列），实现与测试成本高；
- 文本用**位置索引**做变换，天然耦合——是它被 CRDT 挑战的主因。

---

## 四、CRDT 原理（现代主流）

### 4.1 核心思想

**每个操作自带元数据（作者 ID + 逻辑时钟/ID），并发操作无论以什么顺序应用，最终结果都收敛**——不需要 transform、不需要中心化排序。

### 4.2 文本 CRDT 两种代表性算法

- **YATA（Yjs 使用）**：每个字符带唯一 ID，插入时附加「左邻居/右邻居」引用——即便并发插入同位置，用 ID 排序规则决定先后，结果确定且符合直觉；
- **RGA（Automerge 使用）**：类似链表 + 版本向量，字符挂在前驱之后，并发插入按操作者优先级排列。

### 4.3 与 OT 的对比

| 维度 | OT | CRDT |
|------|----|------|
| 收敛保证 | 依赖 transform 正确性（难证） | **数学上天然收敛**（无需协调） |
| 离线/去中心化 | 弱（依赖中心排序） | **强（P2P/离线合并天然支持）** |
| 实现复杂度 | transform 矩阵复杂 | 算法简单但**内存/存储开销大**（每条字符都要元数据） |
| 服务端压力 | 中心广播，简单 | 可 P2P，服务端只存最终态 |
| 成熟产品 | Google Docs | Yjs/Automerge（2025 主流开源方案） |

> 结论：**新系统选 CRDT（Yjs 生态最成熟）；老系统/Google 系方案看 OT。面试两派都要能讲。**

## 五、架构落地：一个在线文档系统怎么搭

```
客户端(编辑器) ── WebSocket 长连接 ──> 网关/接入层
                                        │
               协同服务(房间/文档维度): 广播 + 冲突解决(CRDT状态)
                                        │
               存储: 文档快照(定期) + 操作日志(OpLog) + 光标/心跳
               
辅助: 权限(查看/编辑/评论)、离线队列(断网积攒操作, 重连合并)、
     版本历史(回滚=重放操作)、全文检索(异步)、CDN静态资源
```

### 5.1 关键组件

1. **实时通道**：WebSocket 长连接（房间模型：每文档一个 room，连接数 × 文档数规划网关）；
2. **协同引擎**：Yjs（Document 状态 + 双向绑定编辑器，如 ProseMirror/Quill 适配器）；
3. **持久化**：快照（snapshot）+ 增量操作日志，重建=加载快照+重放；定期压缩（删除历史操作）；
4. **离线与弱网**：客户端积攒操作队列，恢复连接后批量提交（CRDT 天然支持）；
5. **鉴权与并发限制**：每文档在线用户数上限、只读模式降级、频率限流防滥用。

### 5.2 扩展：从文本到结构化文档

- 表格/画布（Figma 式）→ 用**对象级 CRDT（Map/List 组合）**而非字符串；
- 富文本格式（加粗/颜色）→ 格式与内容分离建模（Yjs 的 XmlFragment 思路）。

## 六、面试答题框架（3 分钟版）

1. **需求澄清**：并发编辑、实时性、离线支持、回滚历史、协作规模（N 人）；
2. **点破难点**：并发操作的**位置冲突** → 引出 OT/CRDT 二分；
3. **讲 OT**：transform 思想 + Google Docs 中心化架构 + 局限；
4. **讲 CRDT**：操作可交换 + YATA/RGA + Yjs/Automerge 生态 + 优点（离线/收敛性）；
5. **落地**：WebSocket 房间、快照+OpLog、权限、限流、监控。

| 主题 | 一句话 |
|------|--------|
| 难点 | 并发操作的位置冲突导致内容分叉 |
| OT | 操作变换修正位置；中心化；Google Docs |

| 实时 | WebSocket 房间模型广播 |
| 选型 | 新系统 CRDT（Yjs）；老系统 OT |
