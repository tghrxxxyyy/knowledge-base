# 站内搜索联想与 Suggest 设计

> 板块：场景设计 　|　 返回：[README](README.md)
> 适用：搜索框下拉联想、商品/内容自动补全、拼音/纠错提示。

联想（Search As You Type）要求**输入即响应（<50ms）**，是搜索体验的第一道关。核心是"快速匹配前缀 + 热词排序 + 降级兜底"。

## 一、需求拆解

- **低延迟**：每次按键都要在几十毫秒内返回。
- **相关性**：高频/个性化词优先。
- **容错**：拼音、错别字、简繁也能联想。
- **防抖与限流**：避免每字符都打后端。

## 二、方案对比

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| 数据库 LIKE | `WHERE kw LIKE 'ab%'` | 简单 | 慢、全表扫 |
| Redis ZSet 热词 | 按分数排序的热词集合 | 快、易加权 | 仅适合有限热词 |
| Trie 前缀树 | 内存树匹配前缀 | 精确前缀、内存友好 | 需维护树、拼音需额外结构 |
| Elasticsearch Completion | Completion Suggester | 近实时、支持权重/上下文 | 依赖 ES |
| 倒排 + 热词缓存 | 离线算热词，缓存前缀结果 | 兼顾长尾与热门 | 实现复杂 |

## 三、Trie 前缀树方案

```java
class TrieNode {
    Map<Character, TrieNode> children = new HashMap<>();
    boolean isWord;
    double weight;  // 热度
}
// 插入：逐字符建节点；查询：沿前缀走到节点，DFS 收集 TopK 热词
```

- 前缀匹配天然契合"输入即联想"。
- 权重（搜索频次）用于排序，热词优先。
- 内存占用可控（仅词表），可全量放应用内存或 Redis。

## 四、热词与个性化

- **热词**：离线统计 TopN 查询词，写入 Redis ZSet，查询时先返回热词再补 Trie 结果。
- **个性化**：基于用户历史/地域加权（如北方用户"羽绒服"优先）。
- **拼音/纠错**：维护拼音索引（`xue→雪/学`），输入拼音也能联想；编辑距离纠错处理错别字。

## 五、性能与降级

- **前端防抖**：输入停顿 100–200ms 才请求，减少 QPS。
- **CDN/本地缓存**：常见前缀结果缓存。
- **降级**：ES/Redis 挂时，返回静态热词表或关闭联想，不影响主搜索。
- **限流**：单用户联想请求频控，防刷。

## 六、与搜索主链路关系

```
输入 → 防抖 → 联想服务(Trie/ES Completion) → 返回候选
                               ↓ 用户选中
                          主搜索(ES 全文检索)
```

## 七、常见坑

1. **每次按键都请求** → QPS 爆炸；前端防抖 + 缓存。
2. **联想慢于输入** → 体验差；Trie/缓存保证 <50ms。
3. **热词不更新** → 联想过时；离线定时刷新。
4. **拼音/错别字无兜底** → 联想率低；加拼音索引+纠错。
5. **结果无排序** → 一堆无关词；按权重+个性化。
6. **依赖主搜索 ES** → ES 抖动拖垮联想；独立服务+降级。
