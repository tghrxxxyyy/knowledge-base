# 实时风控系统设计

> 本文从业务目标出发，拆解实时风控系统的核心能力：规则引擎、特征计算、模型打分、决策流、名单库、案件调查与对抗演进，并给出典型架构与工程取舍。内容基于风控系统公开实践，具体策略参数以业务实际为准。

## 1. 风控在解决什么

风控（Risk Control）的目标是在"用户体验"与"风险损失"之间找平衡：

- 防欺诈：盗号、盗刷、薅羊毛、虚假交易。
- 防违规：内容违规、洗钱、套现。
- 防资损：重复支付、超卖、异常大额。

核心矛盾：过严则误杀正常用户（体验差、转化降），过松则资损与合规风险。因此风控追求"精准识别 + 可解释 + 可迭代"。

## 2. 风控系统的分层

```
流量入口
  │
  ▼
[实时决策引擎] ── 同步返回 通过/拒绝/人工审核
  ├─ 名单服务（黑/白/灰）
  ├─ 规则引擎（硬规则）
  ├─ 特征服务（实时+离线特征）
  ├─ 模型打分（评分卡/树模型/图模型）
  └─ 决策流（编排上述结果）
  │
  ▼
[离线层] ── 案件调查、策略回测、模型训练、标签沉淀
```

## 3. 实时决策引擎

### 3.1 同步与异步

- **同步决策**：交易/登录请求阻塞等待风控结果（毫秒级），用于强拦截场景。
- **异步决策**：先放行再事后核查，用于弱风险或批量场景。

多数支付/注册走同步，因为要在交易前阻断。

### 3.2 决策延迟要求

风控通常要求在 50–200ms 内返回，否则影响主链路。因此特征必须预计算或近实时，规则必须轻量。

### 3.3 决策结果

- **PASS（通过）**：风险低，放行。
- **REJECT（拒绝）**：高风险，阻断并提示。
- **REVIEW（人工审核）**：中等风险，进审核队列。
- **CHALLENGE（挑战）**：如短信验证、滑块、二次确认。

## 4. 规则引擎

### 4.1 规则的表达

规则是"条件 → 动作"的可配置逻辑：

```
IF 设备指纹首次出现 AND 金额 > 5000 AND 1小时内尝试3次
THEN 风险分 +40, 触发 CHALLENGE
```

### 4.2 规则类型

- **名单规则**：命中黑名单直接拒绝；命中白名单直接通过。
- **频次规则**：同一用户/IP/设备 N 时间内行为超阈值。
- **关联规则**：同设备关联多个账号、同收货地址多订单。
- **地理规则**：异地登录、常用地突变。
- **行为序列**：注册即下单、下单即退款等异常路径。

### 4.3 规则管理

- 规则需版本化、可灰度、可回滚。
- 规则改动应能在决策平台热更新，不重启服务。
- 规则冲突需有优先级与合并策略。

## 5. 特征计算

### 5.1 特征分类

- **基础特征**：用户年龄、等级、注册时长。
- **行为特征**：近 1h 登录次数、近 7d 交易额。
- **设备特征**：设备指纹、模拟器标记、Root/越狱。
- **关系特征**：一度/二度关联账号数、社群密度。
- **图特征**：社群规模、中心度、环路检测。

### 5.2 实时与离线

- **离线特征**：T+1 计算的稳定特征，入特征仓库（如用户历史坏账率）。
- **实时特征**：滑动窗口计数（近 5 分钟同 IP 下单数），用 Flink/Redis 计算。
- **特征一致性**：离线训练与在线服务要用同一套定义，避免训练-服务偏斜（training-serving skew）。

### 5.3 特征存储

- 在线：Redis / 特征存储（低延迟 KV）。
- 离线：数据仓库 / 特征平台。

## 6. 模型打分

### 6.1 模型层级

- **评分卡 / 逻辑回归**：可解释强，适合强监管场景。
- **树模型（GBDT/XGBoost）**：非线性强，常用。
- **图模型**：识别团伙欺诈（社群、环路）。
- **无监督**：异常检测、聚类发现新型风险。

### 6.2 黑白样本

- 正样本（坏用户）通常稀少且标签滞后（坏账发现晚）。
- 需解决样本不平衡（采样、代价敏感、PU learning）。
- 标签回流：从案件调查结果沉淀标签。

### 6.3 模型可解释

金融/合规场景要求"为什么拒"，需输出贡献度（如 SHAP 思路），模型不能纯黑盒。

## 7. 名单库

- **黑名名单**：确认欺诈的账号/设备/IP/卡号。
- **白名单**：高信任用户/内部测试。
- **灰名单**：待观察，加严监控。
- **时效**：名单需有有效期与复议机制，避免永久误杀。

## 8. 决策流编排

把名单、规则、特征、模型结果按策略组合：

```
score = base
score += rule_hits_weight
score += model_score * w
if score > 90: REJECT
elif score > 60: REVIEW
else: PASS
```

决策流应可视化配置，策略人员可自助调整，无需改代码。

## 9. 对抗与演进

### 9.1 攻防循环

黑产持续演进（养号、设备农场、打码平台），风控必须：

- 监控通过率/资损率/误杀率波动。
- 沉淀新型案件为规则/样本。
- A/B 验证新策略效果。

### 9.2 误杀治理

- 提供申诉/解封通道。
- 对高价值用户降阈值或白名单。
- 监控误杀率（正常用户被拒比例）。

## 10. 离线层：案件与回溯

- **案件调查**：人工/半自动核查可疑案件，沉淀标签。
- **策略回测**：新规则在历史数据上回测，估计影响与误杀。
- **模型训练**：用新标签重训，定期上线。

## 11. 典型技术栈

- 实时计算：Flink / Spark Streaming。
- 特征存储：Redis / 自研特征平台。
- 规则引擎：Drools / 自研 DSL。
- 图计算：图数据库 / GraphX。
- 模型服务：模型推理服务 + 特征对齐。
- 决策平台：可视化策略编排。

## 12. 指标与监控

- **资损率**：拦截挽回金额 / 总风险敞口。
- **通过率 / 拒绝率**：监控策略松紧。
- **误杀率**：正常用户被拒比例（核心体验指标）。
- **案件转化**：调查确认率。
- **延迟**：P99 决策耗时。

## 13. 常见踩坑

1. **规则硬编码**：改规则需发版，响应慢；应平台化配置。
2. **特征穿越**：用到了未来信息（如用还款结果算实时特征），导致离线准在线崩。
3. **训练-服务偏斜**：离线特征口径与在线不一致，模型效果打折。
4. **误杀无申诉**：用户被拒无法解封，投诉与流失。
5. **名单永久化**：误标黑名单一辈子，需有效期与复议。
6. **只看拦截率忽视误杀**：拦截高但误杀更高，体验崩盘。
7. **对抗滞后**：新黑产手法数周才进规则，需缩短反馈环。

## 14. 小结

实时风控是"规则 + 特征 + 模型 + 决策流 + 对抗演进"的闭环系统。工程上要保证低延迟决策、特征一致性、策略可配置，业务上要平衡拦截与误杀，并建立从案件到规则/样本的快反馈环。可解释与申诉通道在金融场景不可或缺。
