# 分布式锁深入（Fencing Token / 锁竞争分析 / 性能基准 / 高级模式）

> 分布式锁 = 并发安全的最后一道闸门。本篇深入拆解：Fencing Token、锁竞争分析、性能基准测试、高级模式、生产 Checklist。

---

## 一、核心要求

| 要求 | 说明 |
|------|------|
| 互斥性 | 同一时刻仅一个客户端持有锁 |
| 防死锁 | 客户端崩溃也能自动释放（过期时间） |
| 谁持有谁释放 | 释放时必须校验持有者，防误删 |
| 可重入 | 同一线程可多次获取（可选） |
| 高可用 | 避免单点，容错 |

---

## 二、Fencing Token（防脑裂）

### 2.1 问题场景

```
Client A 获锁 → GC 停顿 → 锁过期
Client B 获锁 → 写入存储
Client A 恢复 → 写入存储（覆盖 B 的数据）

Fencing Token = 单调递增的 token
  → 每次获锁 token+1
  → 存储端拒绝 token < 最新 token 的写入
```

### 2.2 实现

```
锁服务：
  Client A 获锁 → token=1
  Client B 获锁 → token=2

存储端：
  写入时带 token=2
  存储检查：token >= 最新 token？
  → 是：接受写入，更新最新 token=2
  → 否：拒绝写入（返回过期错误）

Redis 实现：
  SET key my_value NX EX 30  (value=token)
  写入时：检查 value == 当前 token
```

## 三、方案对比

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| SET NX EX | 原子、简单 | 无续期、单点 | 短期简单锁定 |
| Redisson 普通锁 | 自动续期、API 友好 | 单节点故障可能失效 | 单 Redis 节点 |
| Redisson 红锁 | 更高可用 | 开销大、实现复杂 | 金融级高要求 |
| ZooKeeper | 强一致、自动释放 | 性能较低、依赖 ZK | 强一致诉求 |
| 数据库锁 | 零组件 | 性能差、易死锁 | 不推荐作主锁 |
| etcd | 强一致、Lease | 性能中等 | 云原生/K8s 环境 |

## 四、锁竞争分析

### 4.1 竞争指标

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| 获取等待时间 | 从请求到获锁的耗时 | > 1s |
| 持有时间 | 持有锁的总时长 | > 10s |
| 获取失败率 | 获取失败的请求占比 | > 1% |
| 死锁次数 | 死锁检测发现的次数 | > 0 |
| 续期次数 | WatchDog 续期的次数 | 异常高 |

### 4.2 竞争优化

| 优化 | 说明 |
|------|------|
| 细粒度锁 | 按订单号/用户 ID 分锁，减少冲突 |
| 读写锁 | 读操作用读锁，写操作用写锁 |
| 锁超时 | 合理设置过期时间（业务最大耗时 × 2~3） |
| 重试策略 | 指数退避 + 抖动（避免惊群） |
| 本地缓存 | 热点数据本地缓存，减少锁竞争 |

### 4.3 惊群效应

```
问题：
  大量客户端同时请求锁 → 全部失败 → 全部重试 → 雪崩

解决：
  1. 指数退避重试（随机间隔）
  2. 抖动（Jitter）避免同时重试
  3. 限制重试次数（≤3 次）
  4. 快速失败（返回"处理中"而非等锁）
```

## 五、性能基准

### 5.1 测试环境

```
Redis 单节点：QPS ~10 万/秒（SET NX EX）
Redis Sentinel：QPS ~8 万/秒（故障转移开销）
Redis Cluster：QPS ~20 万/秒（分片）
ZooKeeper：QPS ~1 万/秒（写）
etcd：QPS ~2 万/秒（写）
```

### 5.2 延迟对比

| 方案 | P50 | P99 | P999 |
|------|-----|-----|------|
| Redis 单节点 | 0.1ms | 0.5ms | 1ms |
| Redis Sentinel | 0.2ms | 1ms | 2ms |
| ZooKeeper | 1ms | 5ms | 10ms |
| etcd | 0.5ms | 2ms | 5ms |

### 5.3 选型决策

```
性能优先 + 单节点可接受 → Redis 单节点
高可用 + 金融级 → Redisson 红锁 或 ZooKeeper
云原生/K8s 环境 → etcd
零组件 → 数据库锁（仅低频场景）
```

## 六、高级模式

### 6.1 公平锁

```
公平锁 = 按请求顺序获取锁（避免饥饿）

Redisson 实现：
  RLock fairLock = redisson.getFairLock("key");
  fairLock.lock();

原理：
  维护一个队列（ZSET，score=请求时间）
  按 score 顺序分配锁
```

### 6.2 读写锁

```
读写锁 = 读操作共享，写操作互斥

Redisson 实现：
  RReadWriteLock rwLock = redisson.getReadWriteLock("key");
  rwLock.readLock().lock();   // 读锁（共享）
  rwLock.writeLock().lock();  // 写锁（互斥）

适用：
  读多写少场景（如配置缓存）
  读操作可以并发，写操作需要互斥
```

### 6.3 信号量

```
信号量 = 限制并发数量（而非互斥）

Redisson 实现：
  RSemaphore semaphore = redisson.getSemaphore("permits");
  semaphore.tryAcquire(1);  // 获取 1 个许可
  semaphore.release(1);     // 释放 1 个许可

适用：
  限流（如限制同时访问某个资源的并发数）
  资源池（如数据库连接池）
```

## 七、释放锁安全性

### 7.1 误删场景

```
Client A 获锁 → GC 停顿 → 锁过期
Client B 获锁 → 执行业务
Client A 恢复 → del key（删了 B 的锁）

正确做法：
  释放时用 Lua 脚本原子校验 value 再删
```

### 7.2 Lua 脚本

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### 7.3 Redisson 自动处理

```
Redisson unlock() 内置：
  1. 校验 owner（value == 当前 value）
  2. 原子删除
  3. 释放订阅（通知等待的客户端）

不需要手动 Lua 脚本
```

## 八、生产 Checklist

| 检查项 | 说明 |
|--------|------|
| 锁 key 命名 | `业务:功能:资源ID`，粒度尽量细 |
| 过期时间 | 业务最大耗时 × 2~3；长事务用 WatchDog |
| 释放锁 | 必须校验 owner（Lua / Redisson） |
| 获取失败策略 | 返回"处理中"、查历史、或指数退避 |
| 幂等兜底 | 进入锁后仍要查业务状态 |
| 监控 | 锁等待/持有/失败/死锁 |
| 降级 | Redis 不可用时宁返回失败也不熔断 |
