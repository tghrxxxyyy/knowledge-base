# 签到系统设计深入（Bitmap 算法 / 奖励梯度 / 离线分析 / 高并发优化）

> 签到是低成本高频的用户活跃手段。本篇深入拆解：Redis Bitmap 算法细节、奖励梯度逻辑、离线数据分析、高并发优化。

---

## 一、核心矛盾

1. 签到是**高频小写**（每天一次/人），但**总量大**（DAU 级）
2. **连续签到判定**要准：漏签断签、补签卡
3. 奖励**不能重复发**（一天一次）、不能多发（并发双击）

> 核心主线：签到模型 → Redis Bitmap 存储 → 连续天数判定 → 奖励发放 → 补签

| 表 | 字段 | 说明 |
|----|------|------|
| 签到流水 | user_id, sign_date, reward_type/amount, created_at | 每用户每天最多一行，唯一键 `(user_id, sign_date)` 幂等 |

## 三、Redis Bitmap 存储

### 3.1 Key 设计

```
key = sign:{userId}:{yyyyMM}     e.g. sign:10086:202608
第 N 天签到 => SETBIT key (N-1) 1
```

### 3.2 操作命令

| 操作 | Redis 命令 | 时间复杂度 |
|------|-----------|-----------|
| 签到 | `SETBIT key (N-1) 1` | O(1) |
| 今天是否已签 | `GETBIT key (N-1)` | O(1) |
| 本月签到天数 | `BITCOUNT key` | O(1) |
| 展示月历 | `BITFIELD key GET u31 0` | O(1) |

### 3.3 空间分析

```
一个用户一年 12 个 key，每个 32 字节（8 天/字节）
千万用户一个月才 ~40MB，极省

对比：
  Redis Hash：~500 字节/用户/月
  MySQL：~200 字节/用户/月

Bitmap 节省 99%+ 存储
```

### 3.4 连续签到算法

```java
// BITFIELD 取出今天为止的位图，从末位向前数连续 1
long bits = redis.bitfield("sign:" + uid + ":" + yyyyMM)
                 .get(u(dayPos)).toLong();
int streak = 0;
while ((bits & 1) == 1) { 
    streak++; 
    bits >>>= 1; 
}
return streak;
```

### 3.5 跨月连续签到

```
问题：用户 8 月 30、31 签到，9 月 1、2 签到，连续 4 天怎么算？

方案：
  1. 先查本月连续天数（streak_current）
  2. 如果 streak_current == 本月已过天数，查上月最后连续天数
  3. 本月连续 + 上月尾部连续 = 总连续天数

Redis 命令：
  # 查上月位图
  BITFIELD sign:10086:202608 GET u31 0
  # 取尾部连续 1
```

## 四、签到流程

```
1. 用户点击签到
2. Redis SETBIT(key, 今天) → 返回 0（首次签到）
3. BITFIELD 算连续天数
4. 按连续天数给奖励（阶梯规则）
5. 发 MQ 奖励事件（幂等）
6. 异步落库流水（唯一键防重）
```

## 五、奖励梯度设计

### 5.1 阶梯奖励规则

| 连续天数 | 奖励类型 | 奖励金额 |
|----------|----------|----------|
| 1~2 天 | 积分 | 10 积分/天 |
| 3~6 天 | 积分 | 20 积分/天 |
| 7~13 天 | 优惠券 | 5 元券 |
| 14~20 天 | 优惠券 | 10 元券 |
| 21~29 天 | 优惠券 | 20 元券 |
| 30 天 | 大额券+积分 | 50 元券+100 积分 |

### 5.2 配置表设计

```sql
CREATE TABLE sign_in_reward_config (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    min_days    INT NOT NULL,
    max_days    INT NOT NULL,
    reward_type VARCHAR(32),
    reward_amount INT,
    reward_name VARCHAR(64)
);
```

### 5.3 奖励发放

```
幂等保障：
  1. Redis SETBIT 返回值判重（原子防双击）
  2. MQ 消息幂等键（业务键去重）
  3. DB 流水唯一键（user_id + sign_date）

发放链路：
  签到服务 → MQ → 积分服务（幂等入账）
  签到服务 → MQ → 优惠券服务（幂等发券）
```

## 六、补签与断签

| 场景 | 方案 |
|------|------|
| 漏签断签 | 签到接口带 `is_repair` + 补签卡库存扣减，SETBIT 历史位 |
| 补签限制 | 每月限 N 次、只能补最近 N 天 |
| 连续重算 | 补签后重新 BITFIELD 计算并刷新缓存 |

### 6.1 补签流程

```
1. 用户使用补签卡（扣减库存，幂等）
2. SETBIT 历史日期位
3. 重算连续天数
4. 如果连续天数达到新阶梯，补发奖励
```

## 七、高并发优化

### 7.1 热点问题

```
问题：签到高峰（每天 0 点）同一用户并发双击

优化：
  1. Redis SETBIT 原子操作天然防重
  2. 签到接口限流（同用户 1 秒 1 次）
  3. 客户端防抖（按钮点击后置灰 3 秒）
```

### 7.2 大用户量优化

```
问题：千万用户签到，Redis 压力大

优化：
  1. 按用户 ID 分片（分散到多个 Redis 实例）
  2. 本地缓存月历数据（减少 Redis 查询）
  3. 批量查询（BITFIELD 一次取整月位图）
```

### 7.3 落库优化

```
问题：签到流水每天百万级，MySQL 写入压力

优化：
  1. MQ 削峰（异步落库）
  2. 按月分表（sharding_key = user_id % 12）
  3. 批量写入（攒一批 INSERT）
```

## 九、面试答题框架

1. **存储选型**：Redis Bitmap（一人一月一 key，一天一位，极省内存）
2. **幂等设计**：SETBIT 返回值判重 + MQ 幂等 + DB 唯一键
3. **连续计算**：BITFIELD 取位图，尾部数连续 1（跨月查上月）
4. **奖励发放**：阶梯规则配置，MQ 异步幂等
5. **高并发**：SETBIT 原子操作 + 限流 + 防抖 + 分片
6. **离线分析**：Binlog 同步 → 数据湖 → 签到率/连续分布/成本分析
