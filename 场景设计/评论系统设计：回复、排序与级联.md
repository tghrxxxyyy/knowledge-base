# 评论系统设计：回复、排序与级联

## 〇、本体介绍

**评论系统**：内容（文章/视频/商品）下的用户互动层，包含**评论、回复、点赞、排序、后台管理（删除/审核）**。难点不在"能发评论"，而在**海量数据下的组织方式与排序体验**。

**核心矛盾**：
1. 评论量大（热帖百万级），**存储与查询的组织方式**决定性能上限；
2. 排序要兼顾**时间（最新）、热度（质量）与身份（作者置顶）**，且不可离线重算太久；
3. 删除评论后**子回复怎么处理**（级联/保留）体验与数据冲突；
4. 评论+回复的**计数与展示**在并发下要准确。

**核心主线**：存储模型（平铺 vs 树形）→ 回复设计 → 排序策略 → 删除与级联 → 计数与缓存。

---

## 一、存储模型：平铺 vs 树形

### 1.1 三种主流模型

| 模型 | 结构 | 优点 | 缺点 |
|------|------|------|------|
| **平铺 + 回复引用（楼层式）** | 评论一张表，回复记 `reply_to_comment_id`，全部按一级评论展示 | 简单、查询快、利于分页 | 回复层级少（一般只一层） |
| **树形嵌套（递归）** | `parent_id` 无限层级 | 还原对话结构 | 深度大时查询/分页复杂，需限深 |
| **混合（主流）** | 一级评论（评论表）+ 回复列表（回复表），回复挂在评论下，限制 1~2 层 | 体验好、查询可控 | 两表 |

### 1.2 推荐：混合模型

```sql
CREATE TABLE comment (
    id           BIGINT PRIMARY KEY,
    target_type  TINYINT NOT NULL,   -- 文章/视频/商品
    target_id    VARCHAR(32) NOT NULL, -- 内容ID
    user_id      BIGINT NOT NULL,
    content      VARCHAR(2000),
    like_count   INT DEFAULT 0,      -- 冗余点赞数
    reply_count  INT DEFAULT 0,      -- 冗余回复数（展示用）
    status       TINYINT,            -- 0正常 1已删除 2待审核
    is_top       TINYINT DEFAULT 0,  -- 作者置顶
    created_at   DATETIME,
    KEY idx_target (target_type, target_id, status)
) COMMENT '一级评论';

CREATE TABLE reply (
    id           BIGINT PRIMARY KEY,
    comment_id   BIGINT NOT NULL,    -- 挂在哪个一级评论下
    user_id      BIGINT,
    reply_to_uid BIGINT,             -- 回复谁（楼层 @）
    content      VARCHAR(2000),
    like_count   INT DEFAULT 0,
    status       TINYINT,
    created_at   DATETIME,
    KEY idx_comment (comment_id, created_at)
) COMMENT '回复';
```

- **一级评论只展示一层 + 回复以列表形式挂在评论下**（默认"查看全部 N 条回复"），层级体验与查询复杂度取得平衡。
- 数据量按 `target_id` 路由/分表（同「[Feed 信息流设计](Feed信息流设计.md)」的内容分表思路）。

## 二、回复设计（楼层与 @）

| 设计点 | 方案 |
|--------|------|
| 回复对象 | `reply_to_uid` 存被 @ 的人；展示为"@甲 回复 @乙" |
| 楼层号 | 评论排序后生成；新增评论可插楼，楼层仅展示不保证连续 |
| 回复引用 | 回复带上 `quote`（原文快照），原评论删除后引用仍在，展示更友好 |
| 深度限制 | 强制 2 层：回复只能在评论下，回复的回复还是挂评论下（防深递归） |

> 口诀：**"评论一层楼，回复一张表；楼层做展示，引用留快照。"**

## 三、排序策略（体验的核心）

### 3.1 排序维度（参考主流产品实践）

| 维度 | 含义 | 适用 |
|------|------|------|
| **时间正序** | 从头看剧情（弹幕式） | 小说/章节、连续剧评论区 |
| **时间倒序** | 最新在前 | 时效型内容（新闻/动态） |
| **热度排序** | 点赞/回复/停留加权 | 社区型内容（B站/抖音评论区） |
| **身份置顶** | 作者/主创的评论固定置顶（"主创说"） | 创作者需要发声的场域 |

- 主流组合：**"主创置顶 + 热度榜 + 最新榜"** 双列表或一页内分区；用户可切换"按热度/按时间"。
- 置顶由**角色判定**（作者本人/官方），不走热度算法，置顶位一般 1~3 条。

### 3.2 热度分公式（可调权重）

```
score = w1 * ln(like + a) + w2 * ln(reply + b) + w3 * (赞成-反对) - time_decay * age
```

- 取对数压缩长尾（百万赞 ≠ 百万倍热度）；`time_decay` 控制新鲜度衰减（如半衰期 24h）。
- **实时计分**：点赞/回复时更新 Redis ZSet score（增量维护），定时全量重算兜底——见「[排行榜与实时统计](排行榜与实时统计.md)」的榜单思想。

### 3.3 分页与一致性

- 热评榜按 score 分页（ZSet 天然支持）；最新榜按 id/时间分页。
- **新增评论插队导致分页漂移**：用"游标分页"（score/时间 < 上次游标）替代 offset 分页。

## 四、删除与级联（数据 vs 体验的博弈）

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **物理级联删** | 删评论连带删全部回复 | 数据干净，但损失讨论上下文、操作重 |
| **逻辑删除 + 子回复保留（主流）** | 评论置"已删除"，回复仍展示（显示"该评论已删除"）；回复可继续 | 体验好，保留了对话完整性 |
| **硬删 + 引用快照** | 物理删，回复保留但引用原文已快照 | 干净且展示完整 |

- **主流做法：一级评论删除时，其子回复不级联物理删除**，而是置顶文案"该评论已删除"（回复仍可见）。
- 被删除评论若在热度榜上：立即从 Redis ZSet 移除（实时可见）。
- 违规评论（审核）：先隐藏（status=待审核/已删除）后处理，防违规内容继续曝光——见「[SRE与稳定性工程/06-日志与告警规则库](../SRE与稳定性工程/06-日志与告警规则库.md)」的审核联动。

> 口诀：**"删评论不删回复，删榜单一键下架；逻辑删除为主，物理删除为辅。"**

## 五、计数与缓存

| 计数器 | 手段 |
|--------|------|
| 评论总数 | 内容表冗余 `comment_count`，Redis INCR/DECR + 异步落库 |
| 回复数/点赞数 | 评论表冗余字段；点赞 Redis Set 判重（见「[排行榜与实时统计](排行榜与实时统计.md)」点赞合流） |
| 热榜 | Redis ZSet（score 实时维护），DB 兜底重算 |

- **读多写少 + 峰值集中**：列表页走 Redis 缓存（分页列表缓存 + 热度 ZSet），DB 只做最终落库与兜底。
- 计数一致性：Redis 权威、DB 异步最终一致；每日对账（同账务对账思想，见「[钱包与账务系统设计](钱包与账务系统设计：账户、流水与日终对账.md)」）。

## 面试高频问题（12+ 条）

1. **评论系统难点？** 大数据量组织、排序体验、删除与回复的关系处理、计数一致性。
2. **平铺和树形怎么选？** 楼层式平铺简单高效；树形还原对话但查询分页复杂；主流用两表混合并限 2 层。
3. **回复层级为什么限 2 层？** 无界递归导致查询/展示/分页失控，2 层已满足 99% 对话需求。
4. **热评怎么排序？** ln 点赞/回复加权 + 时间衰减；主创/作者置顶不参与算法。
5. **为什么用 ln？** 压缩长尾，避免爆款评论碾压一切（百万赞 ≠ 百万倍热度）。
6. **分页漂移怎么解决？** 用 score/时间游标分页，不用 offset。
7. **删除评论后回复怎么办？** 不级联物理删，回复保留 + 评论置"已删除"文案。
8. **热榜上的评论被删了？** 实时从 ZSet 移除（下架），DB 逻辑删除，最终一致。
9. **评论数怎么维护？** 内容表冗余 + Redis INCR/DECR 异步落库，每日对账纠偏。
10. **点赞怎么防重复？** Redis Set 按用户判重（SISMEMBER/SADD），只更新一次计数。
11. **怎么防刷评论？** 入口限流 + 内容审核 + 频控（同设备/同用户维度）。
12. **评论列表性能？** 列表缓存 + 热度 ZSet 分页 + target_id 分表 + 游标分页。
13. **主创说的"置顶"怎么实现？** 身份判定（作者/官方），is_top 字段 + 排序权重最高，限量 1~3 条。
