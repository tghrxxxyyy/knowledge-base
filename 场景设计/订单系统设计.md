# 订单系统设计（状态机深入 / 分表策略 / 超时方案 / 售后退款 / 高并发下单）

> 订单系统是电商的**心脏**。本篇深入拆解：订单状态机详细设计、分库分表策略、订单号生成、超时方案对比、售后退款流程、高并发下单架构。

---

## 一、核心流程与状态机

### 1.1 下单主流程

```
用户下单 → 防重(幂等: userId+商品+session)
  → 校验(库存/价格/优惠)
  → 扣库存(Redis 预扣 / DB 乐观锁)
  → 创建订单(状态: 待支付)
  → 生成支付单
  → 调支付渠道
  → 支付回调
  → 校验签名+幂等
  → 更新库存(正式扣) + 订单(已支付)
  → MQ 异步: 出库履约/积分/通知
```

### 1.2 订单状态机（详细）

```
待支付 ──支付回调──> 已支付 ──发货──> 已发货 ──确认收货──> 已完成
   │                    │
   ├─超时取消──> 已取消    ├─退款──> 退款中 ──退款成功──> 已退款
   │                    │
   └─用户取消──> 已取消    └─售后──> 售后中(纠纷处理)

扩展状态：
  待支付 → 已锁定（风控拦截）
  已支付 → 已拆单（多仓发货）
  已发货 → 已签收（物流回传）
  已完成 → 已评价（评价后不可退款）
```

### 1.3 状态机实现

```java
// 状态枚举
public enum OrderStatus {
    PENDING_PAYMENT(0, "待支付"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货"),
    COMPLETED(3, "已完成"),
    CANCELLED(4, "已取消"),
    REFUNDING(5, "退款中"),
    REFUNDED(6, "已退款");
    
    private final int code;
    private final String desc;
}

// 状态流转校验（乐观锁更新）
public boolean updateStatus(Long orderId, OrderStatus from, OrderStatus to) {
    int rows = orderMapper.updateStatus(orderId, from.getCode(), to.getCode());
    // UPDATE orders SET status=? WHERE id=? AND status=?
    return rows > 0;
}

// 状态机规则（哪些流转合法）
private static final Map<OrderStatus, Set<OrderStatus>> VALID_TRANSITIONS = Map.of(
    PENDING_PAYMENT, Set.of(PAID, CANCELLED),
    PAID, Set.of(SHIPPED, REFUNDING),
    SHIPPED, Set.of(COMPLETED, REFUNDING),
    COMPLETED, Set.of(REFUNDING),
    REFUNDING, Set.of(REFUNDED)
);
```

## 二、订单号生成

### 2.1 设计原则

```
唯一性：全局唯一，不重复
有序性：趋势有序（支持分库分表后按 ID 范围查询）
可读性：包含业务信息（日期/渠道/用户）
不可预测：防刷单（随机后缀）
```

### 2.2 方案对比

| 方案 | 格式 | 优点 | 缺点 |
|------|------|------|------|
| 雪花算法 | 时间戳+机器ID+序列号 | 趋势有序、高性能 | 时钟回拨风险 |
| 号段模式 | DB 自增 + 预分配段 | 严格递增 | 依赖 DB |
| UUID | 36 位字符串 | 无依赖 | 无序、索引碎片化 |
| 业务规则 | 日期+渠道+序号 | 可读 | 并发冲突 |

### 2.3 雪花算法实现

```java
// 雪花 ID 结构：1位符号 + 41位时间戳 + 5位数据中心 + 5位机器 + 12位序列号
public class SnowflakeIdGenerator {
    private long datacenterId;
    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨！拒绝生成 ID");
        }
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & 4095;  // 12位序列号
            if (sequence == 0) {
                timestamp = waitNextMillis(lastTimestamp);  // 等待下一毫秒
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;
        return ((timestamp - EPOCH) << 22) | (datacenterId << 17) | (workerId << 12) | sequence;
    }
}
```

## 三、分库分表策略

### 3.1 分片键选择

| 分片键 | 查询模式 | 适用 |
|--------|----------|------|
| user_id | 查「我的订单」高效 | C 端用户查询 |
| order_id | 按订单号查询高效 | 支付回调/客服查询 |
| 双分片 | user_id + order_id 冗余 | 通用方案 |

### 3.2 分表策略

```
分表数：2^N（如 64/128/256）

路由算法：
  user_id 分表：user_id % 分表数
  order_id 分表：雪花 ID 取模 或 一致性哈希

双分片实现：
  主表：order_{user_id % 64}（按 user_id 分）
  冗余表：order_by_order_id_{order_id % 64}（按 order_id 分）

查询路由：
  查「我的订单」→ 主表
  查「订单号」→ 冗余表
```

### 3.3 跨分片查询

```
问题：分页查询（如查所有订单第 10 页）

方案一：应用层归并
  查所有分片 → 合并排序 → 截取
  缺点：分片多时性能差

方案二：搜索引擎
  订单数据同步到 ES → 复杂查询走 ES
  优点：灵活、支持全文检索

方案三：聚合表
  按维度建聚合表（如按天/按状态）
  优点：查询快，缺点：数据冗余
```

## 四、超时方案对比

### 4.1 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 延迟消息 | RocketMQ 延迟消息 | 精准触发、解耦 | 消息堆积风险 |
| Redis ZSET | ZADD score=过期时间 | 精准、轻量 | Redis 故障风险 |
| 定时任务 | 扫描待支付订单 | 简单 | 有延迟、资源消耗 |
| 时间轮 | 内存时间轮 | 精准、高性能 | 内存占用、重启丢失 |

### 4.2 组合方案（推荐）

```
延迟消息（精准触发）+ 定时任务（兜底扫描）

延迟消息：
  下单时发送延迟消息（30min）
  → 到期后检查订单状态
  → 未支付 → 取消订单 + 回滚库存

定时任务：
  每 5min 扫描「待支付超过 30min」的订单
  → 批量取消（兜底，防消息丢失）
  → 分页 + 限量（避免一次扫描太多）
```

## 五、售后退款流程

### 5.1 退款状态机

```
申请退款 → 审核中 → 审核通过 → 退款处理中 → 退款成功
                                       │
                                       └─退款失败 → 重试/人工介入

审核中 → 审核拒绝 → 退款关闭
```

### 5.2 退款核心流程

```
1. 用户申请退款（提交退款原因/金额）
2. 系统校验（是否在退款期/是否已发货/金额是否合法）
3. 自动审核（小额自动通过，大额人工审核）
4. 调用支付渠道退款 API
5. 等待退款回调（T+1~T+7 不等）
6. 退款成功 → 更新订单状态 + 回滚库存 + 退积分/优惠券
7. 退款失败 → 重试（最多 3 次）→ 人工介入
```

### 5.3 退款幂等

```
退款幂等 = 以退款单号为唯一键

处理流程：
  1. 创建退款单（状态：退款中）
  2. 调用支付渠道退款（携带退款单号）
  3. 退款回调 → 校验退款单号 → 已处理直接返回成功
  4. 未处理 → 更新退款单状态 + 订单状态 + 库存回滚

防重复退款：
  - 退款单唯一索引
  - 乐观锁更新状态（UPDATE ... WHERE status='退款中'）
```

## 六、高并发下单架构

### 6.1 架构要点

```
1. 读写分离：商品详情走缓存（多级缓存），订单写走 DB 分库分表
2. 异步化：下单只做「锁库存+建单」，履约/通知/积分全部 MQ 异步
3. 削峰：秒杀场景请求先进队列/令牌桶限流，后端固定速率处理
4. 数据一致性：本地消息表 / 事务消息保证跨系统一致
5. 热点处理：热门 SKU 库存拆分到多 Redis 实例
```

### 6.2 秒杀下单流程

```
用户点击秒杀
  → 前端限流（按钮置灰 + 验证码）
  → 网关限流（令牌桶/滑动窗口）
  → Redis 预扣库存（DECR，原子操作）
  → 校验库存 ≥ 0
  → 发送 MQ 消息（异步建单）
  → 消费者消费 → 创建订单 + 扣减 DB 库存
  → 订单创建成功 → 返回用户

关键：
  - Redis 预扣库存（毫秒级，抗高并发）
  - MQ 异步建单（削峰，后端固定速率处理）
  - 库存扣减与订单创建同事务（数据一致性）
```

6. 幂等：幂等表唯一约束 + 回调状态判断
