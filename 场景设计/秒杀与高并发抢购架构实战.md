# 秒杀与高并发抢购架构实战

秒杀是典型的"瞬时海量请求 + 极少量真实成交"场景。
核心挑战是：流量削峰、防超卖、防刷、库存一致、系统不被压垮。
本文从流量分层、库存扣减、防超卖、防刷、兜底与降级系统讲解。

## 一、秒杀的核心矛盾

### 1.1 流量特征

- 瞬时 QPS 可能是平时的千百倍。
- 绝大多数请求注定失败（库存有限）。
- 读多写少，但写集中在库存扣减。

### 1.2 目标

- 系统不宕机：保护后端数据库。
- 公平且准确：不超卖、不少卖。
- 快速失败：无效请求尽早拦截，节省资源。

## 二、流量分层拦截

### 2.1 前端层

- 按钮置灰：点击后立即禁用，防止重复提交。
- 答题/验证码：拉长请求间隔，过滤机器。
- 静态资源 CDN：页面与图片走边缘缓存。

### 2.2 网关层

- 限流：单用户、单 IP、整体 QPS 多维限流。
- 黑名单：识别异常 IP/设备。
- 请求裁剪：非法参数、缺字段直接拒绝。

### 2.3 应用层

- 本地缓存校验库存是否为 0，为 0 直接返回"已售罄"。
- 异步化：把下单转为消息，平滑写压力。
- 队列削峰：用 MQ 把瞬时写变成匀速消费。

### 2.4 数据层

- 库存扣减在数据库用行锁/乐观锁保证准确。
- 缓存库存做前置判断，数据库做最终裁决。

## 三、库存扣减与防超卖

### 3.1 扣减时机

- 下单前预占：支付失败/超时释放。
- 支付后实扣：仅支付成功才减实物。

### 3.2 数据库防超卖

```sql
UPDATE stock SET count = count - 1
WHERE sku_id = ? AND count >= 1;
```
返回影响行数 > 0 才算扣减成功。
配合行锁或乐观锁（`version`）避免并发超卖。

### 3.3 缓存库存与数据库一致

- 缓存中库存为预估值，用于快速拦截。
- 真正扣减以数据库为准，成功后回写缓存。
- 扣减失败需回补缓存，避免缓存误判售罄。

### 3.4 Redis + Lua 原子扣减

- 用 Lua 脚本在 Redis 内原子判断并扣减，避免"查-改"竞态。
- 扣减成功再异步落库或发送消息。

## 四、防刷与风控

### 4.1 用户级限流

- 同一用户 N 秒内只允许 1 次下单尝试。
- 基于用户 ID 在 Redis 计数。

### 4.2 设备/IP 风控

- 同一设备/ IP 高频请求识别为脚本。
- 行为特征（点击节奏、路径）识别机器。

### 4.3 黄牛防控

- 账号等级、实名、历史行为筛选。
- 限购（一人一件）限制获利空间。

## 五、异步化与削峰

### 5.1 下单转消息

- 前置校验通过后发送"创建订单"消息。
- 下游消费者匀速处理，数据库压力恒定。

### 5.2 排队体验

- 前端展示"排队中"，让用户感知进度。
- 用令牌桶/排队号控制进入核心链路的量。

### 5.3 支付链路

- 下单成功后给有限支付时间（如 15 分钟）。
- 超时未支付释放库存，回补可售。

## 六、降级与兜底

### 6.1 服务降级

- 非核心功能（推荐、评论）在秒杀期关闭或简化。
- 保证核心下单链路资源。

### 6.2 限流兜底

- 超出承载的请求直接返回"活动太火爆，请稍后再试"。
- 不把压力传导到数据库。

### 6.3 库存售罄快速失败

- 一旦缓存标记为 0，后续请求在网关/应用层直接拒绝。
- 避免无效请求打到数据库。

## 七、数据一致性

- 库存以数据库最终值为准。
- 缓存与数据库通过扣减回写、定时校准保持一致。
- 极端情况下允许短暂"显示有货但实际无"，用兜底提示处理。

## 八、压测与演练

- 提前做全链路压测，摸清各层拐点。
- 演练库存回补、限流触发、降级开关。
- 准备扩容预案（提前扩实例、预热缓存）。

## 九、常见坑

- 库存扣减无原子保障导致超卖（资损）。
- 没有多层拦截，流量直达数据库。
- 缓存与数据库不一致，出现"幽灵库存"。
- 售罄后未快速失败，仍打满后端。
- 支付超时未释放库存，造成少卖。

## 十、速记

- 分层拦截：前端置灰 → 网关限流 → 应用缓存预判 → 队列削峰 → DB 裁决。
- 防超卖：UPDATE ... WHERE count>=1（影响行数）或 Redis+Lua 原子扣减。
- 防刷：用户/设备/IP 限流 + 风控 + 限购。
- 削峰：下单转 MQ，匀速消费；售罄快速失败。
- 一致性：DB 为准，缓存回写+校准；超时释放库存防少卖。
