# 电商交易业务模型

> 板块：业务模型 　|　 返回：[README](README.md)

电商是互联网最成熟的业务模型之一，其复杂度在于"交易"与"履约"两条主线的协同，以及价格、库存、优惠、支付、售后多域耦合。本文从核心域、实体关系、价格/库存/订单/支付/履约模型到一致性挑战系统梳理。

## 一、电商核心域

- **商品域**：SPU/SKU、类目、价格、库存、上下架。
- **交易域**：购物车、订单、优惠、支付。
- **履约域**：仓储、物流、发货、退货。
- **用户域**：账号、地址、会员、积分。
- **营销域**：券、满减、秒杀、拼团。

## 二、关键实体与关系

```
用户 1─* 订单 *─* SKU
订单 1─* 订单项（SKU, 数量, 单价）
SKU *─1 库存（仓库维度）
订单 1─1 支付单 1─* 渠道交易
```

- **SPU vs SKU**：SPU 是商品（iPhone 15），SKU 是具体规格（256G 黑）。**交易/库存到 SKU 维度**，价格是 SKU 属性。
- **订单状态机**：待支付 → 已支付 → 已发货 → 已收货 → 已完成 / 退款中 / 已关闭。状态变更需幂等、可审计。

## 三、价格与优惠模型

- **裸价**：SKU 标价。
- **促销**：满减、折扣、券、秒杀价。
- **最终价计算**：原价 → 适用促销 → 用券 → 实付。
- **计算顺序敏感**（先满减再用券），需规则引擎或明确优先级，且可解释（用户能看到明细）。
- **优惠分摊**：多 SKU 订单的优惠按金额比例分摊到每项，便于退款核算与对账。

## 四、库存模型

- **库存类型**：可售库存、锁定（预占）库存、在途库存。
- **扣减时机**：下单锁库存（预扣），支付成功转扣减，取消/超时回滚。
- **防超卖**：Redis 预扣 + DB 兜底（见 [场景设计/秒杀系统设计与高并发扣减](../../场景设计/秒杀系统设计与高并发扣减.md)）。
- **多仓**：库存按仓库维度，下单选最近有货仓；超卖/缺货走调拨或预售。

## 五、订单拆分

- 多商家 → 拆成子订单（分别发货、开票）。
- 不同仓 → 拆发货单。
- 拆单影响优惠分摊与售后，需设计好（拆单后优惠如何归属、退款如何按比例退）。

## 六、支付与对账

- 见 [场景设计/支付系统核心设计](../../场景设计/支付系统核心设计.md)。
- 订单与支付单解耦，异步回调更新状态，**幂等关键**（回调可能重发）。
- 对账：每日与支付渠道核对交易与流水，差异（长短款）告警 + 人工处理。

## 七、履约与物流

- 下单 → 推仓 → 拣货 → 复核 → 发货 → 物流跟踪 → 签收。
- 物流用第三方（快递 100/菜鸟），状态异步回传。
- 超时未发货告警；妥投异常（拒收/丢件）走逆向流程。

## 八、售后与退款

- 退款需原路退回、优惠回退、库存回滚。
- 部分退款按分摊金额退，避免多退/少退。
- 退款与支付同样幂等（防重复退款资损）。
- 换货：退旧发新，涉及两次履约。

## 九、数据一致性挑战

- 下单同时扣库存、算优惠、创建支付 → 跨服务，用 Saga / TCC / 事务消息保证最终一致。
- 见 [场景设计/分布式事务与最终一致](../场景设计/分布式事务与最终一致.md)（如存在）/ [场景设计/支付系统核心设计](../../场景设计/支付系统核心设计.md)。

## 十、金额与精度

- **金额用整数分（或最小货币单位）存储计算**，避免浮点误差（0.1+0.2≠0.3）。
- 展示时再转元，且明确币种与精度。

## 十一、常见建模坑

1. **库存只存总数不拆仓** → 无法就近发货、无法并行履约。
2. **优惠不记录快照** → 事后纠纷无依据（下单应快照商品/价格/优惠）。
3. **退款不回退优惠** → 资损。
4. **订单状态用散落字段** → 应状态机统一管理。
5. **SKU 维度不清晰** → 库存/价格混乱。
6. **金额用浮点** → 计算误差，对账不平。

## 十二、建模要点总结

- 一切以 **SKU** 为交易核心。
- 价格/优惠**下单快照**。
- 库存**预扣 + 回滚**。
- **状态机**驱动订单生命周期。
- 跨域用**最终一致**。
- 金额**整数分**存储。
