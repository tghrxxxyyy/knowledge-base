# 企业服务 / SaaS / ERP / CRM 业务模型（深扒）

> SaaS 的核心是「**一套系统服务 N 个租户**」，技术难点在**多租户隔离、计费订阅、复杂权限、可配置化**。它不求峰值极致，但求稳定、隔离、可演进。
>
> 配套总览见「[业务模型总览](业务模型总览.md)」；权限/隔离见「[架构](../架构)」「[安全工程·认证与授权体系](../安全工程/02-认证与授权体系.md)」。

## 二、核心系统架构

### 2.1 多租户隔离（三种粒度）
- **独立库（DB per tenant）**：隔离最强、成本高，适合大客户/强合规。
- **共享库 + 租户ID 行隔离（Schema/Row）**：成本低、需严防越权，主流 SaaS 选择。
- **共享表 + tenant_id 过滤**：所有查询强制带 `tenant_id`，由中间件统一注入。

### 2.2 权限模型
- **RBAC**：角色 → 权限，简单直观；**ABAC**：基于属性（部门/数据范围）细粒度，适合复杂组织。
- 数据权限：同角色不同人可见不同数据范围（如销售只看自己客户）。

### 2.3 订阅与计费
- 套餐（按席位/功能/用量）→ 订阅周期 → 续费/升降级 → 用量计费（API 调用、存储）。
- 计量（Metering）需准确，超额提醒与封顶。

### 2.4 可配置化（低代码趋势）
- 自定义字段、自定义表单、自定义流程，靠**元数据驱动**而非改代码。

## 四、场景要点

| 场景 | 挑战 | 方案 |
|------|------|------|
| 租户数据越权 | 串数据事故 | 中间件统一注入 tenant_id + 行级过滤 |
| 某租户拖垮全局 | 噪声邻居 | 配额/限流/资源隔离 |
| 计费争议 | 用量不清 | 精确计量 + 账单明细 |
| 多版本并存 | 升级难 | 灰度 + 兼容窗口 |

## 六、深挖：核心业务机制

### 6.1 多租户隔离选型矩阵

| 方案 | 隔离性 | 成本 | 适用 |
|------|--------|------|------|
| 独立库（DB per tenant） | 最强 | 高 | 大客户、金融医疗强合规 |
| 共享库独立 Schema | 中强 | 中 | 中型客户 |
| 共享表 + tenant_id 行过滤 | 弱（靠纪律） | 低 | 中小客户，主流 |

**工程铁律**：
1. `tenant_id` 由**中间件/网关统一注入**（请求头解析 → MyBatis 拦截器自动拼 WHERE），业务代码不感知；
2. 唯一索引必须带 tenant_id（防跨租户撞键）；
3. 数据导出/备份按租户隔离，越权访问审计。

### 6.2 权限模型（RBAC + 数据范围）

```
功能权限: 用户 → 角色 → 权限点（菜单/按钮/API）
数据权限: 用户 → 数据范围规则（全部/本部门/本人/自定义）→ 查询自动追加过滤
```

| 模型 | 表达能力 | 适用 |
|------|----------|------|
| RBAC | 角色化，简单 | 大多数系统 |
| RBAC + 数据范围 | 加行级过滤 | 销售只看自己客户 |
| ABAC | 属性策略（部门=资源部门 且 时间窗） | 复杂组织/动态 |

> 落地：权限中心统一鉴权（API 网关校验 token → 权限点），数据范围在**数据层拦截器**实现。

### 6.3 计量计费（Metering）

```
订阅(套餐/席位) + 用量(API调用/存储/席位) = 账单
计量链路: 使用事件 → Kafka → 计量服务(聚合) → 账单 → 扣费/出账
```

- 计量准确性 = 收入准确性：事件幂等 + 落库 + 对账；
- 超额策略：提醒 → 限速 → 封顶（保护平台又保体验）；
- 升降级：即时生效 + 按天折算（proration）。

| 维度 | 指标 | 说明 |
|------|------|------|
| 增长 | 新签/续费率（NRR）、MRR/ARR | 北极星 |

| 计费 | 计量差异率、账单争议率 | 收入准确 |

## 八、面试与系统设计视角

1. 设计多租户 SaaS：隔离方案选型 + tenant_id 强制注入 + 资源配额。
2. 租户数据越权怎么防：统一拦截注入 + 行级过滤 + 越权审计。
3. 权限怎么设计：RBAC + 数据范围（或 ABAC），讲清两段式。
4. 订阅计费怎么做：套餐 + 计量 + 升降级折算 + 对账。
5. 一个租户拖垮全局怎么办：配额 + 限流 + 独立库分级（噪声邻居治理）。

---

## 九、SaaS 特有坑

- **忘记强制 tenant_id**：任一查询漏带 → 串租户严重事故，必须用统一拦截强制注入。
- **噪声邻居**：大租户吃满资源 → 配额 + 限流 + 独立库分级。
- **权限过于粗**：无法表达「只看自己客户」→ ABAC 数据范围。
- **计费计量不准**：超用未察觉 → 实时计量 + 告警。
- **升级破坏性**：多租户版本不一致 → 灰度 + 兼容期。

> 口诀：**"SaaS 一条线：租户隔离严，tenant_id 必带；权限分两层，计费要计量，配置靠元数据，升级走灰度。"**
