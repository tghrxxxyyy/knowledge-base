# 集成测试与 E2E 策略

> 板块：测试与代码质量 　|　 返回：[README](README.md)

## 一、集成测试定位

验证多个组件协作（服务+DB、服务+MQ）。比单测慢，但能抓到「接口/事务/序列化」层面的问题。

## 二、测试替身对比

| 类型 | 行为 | 用途 |
|------|------|------|
| Dummy | 占位 | 满足参数 |
| Stub | 返回预设 | 控制依赖输出 |
| Mock | 验证交互 | 是否调用、几次 |
| Fake | 简化实现 | 内存版 DB |
| Spy | 部分真实 | 记录调用 |

## 三、数据库集成测试

- 用 Testcontainers 起真实 DB（Docker），避免 H2 与 MySQL 行为差。
- 事务回滚或重建 schema，保证隔离。

## 四、E2E 策略

- 只覆盖核心用户旅程（下单、登录），不要全量。
- 用 Playwright/Cypress 做 Web E2E。
- 环境用类生产（数据脱敏）。

## 五、契约测试

- 消费者驱动契约（Pact）：消费者定义期望，提供者校验。
- 防接口变更破坏调用方，减少 E2E 依赖。

## 六、测试数据管理

- 用 builder/factory 造数据，避免硬编码。
- 数据隔离：每用例独立数据集。

## 七、常见坑

1. E2E 全量跑 → 慢到没人跑。
2. 集成测试依赖共享库 → 互相污染。
3. 测试环境漂移 → 本地过生产挂。
4. 不稳定测试（flaky）不修 → 团队无视红。
