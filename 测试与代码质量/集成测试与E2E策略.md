# 集成测试与 E2E 策略

> 板块：测试与代码质量 　|　 返回：[README](README.md)

测试金字塔告诉我们：单测多、集成中、E2E 少。集成测试验证"组件协作"（服务+DB、服务+MQ），E2E 验证"端到端用户旅程"。二者成本高、慢，却最能反映真实行为。本文讲清定位、测试替身、数据库/E2E 实践、契约测试与数据管理。

## 一、集成测试的定位

### 1.1 它在金字塔的位置

- 单元测试：验证函数/类（快、多、隔离）。
- 集成测试：验证**多个组件协作**（慢、中、部分真实依赖）。
- E2E 测试：验证**完整链路**（最慢、最少、最接近用户）。

### 1.2 为什么要集成测试

单测再全，也抓不到：
- 接口契约不一致（参数名错、类型不符）。
- 事务边界问题（跨表、跨服务事务）。
- 序列化/反序列化差异（JSON 字段映射错）。
- 框架配置错误（连接池、事务传播）。

这些问题只有"把组件接起来跑"才会暴露。

## 二、测试替身（Test Doubles）对比

| 类型 | 行为 | 用途 |
|------|------|------|
| Dummy | 占位，不做事 | 满足参数列表 |
| Stub | 返回预设值 | 控制依赖输出 |
| Mock | 验证交互 | 断言"是否被调用、几次、参数" |
| Fake | 简化实现 | 内存版 DB/消息队列 |
| Spy | 部分真实 + 记录 | 记录调用但不完全替代 |

选择原则：
- 验证"行为/交互"用 Mock。
- 验证"状态/结果"用 Stub/Fake。
- 不要滥用 Mock 导致测试与实现耦合过紧（一改实现就红）。

## 三、数据库集成测试

### 3.1 真实 vs 内存

- **H2/HSQL 内存库**：快，但语法/行为与 MySQL 有差异，可能"本地过生产挂"。
- **Testcontainers**：在 Docker 中起真实 DB（MySQL/Postgres），行为一致，推荐。

### 3.2 隔离策略

- 每用例独立数据集，避免互相污染。
- 事务回滚：测试跑在事务里，结束回滚（不落库）。
- 或重建 schema + 种子数据，保证可重复。
- 注意自增 ID、唯一约束导致的顺序依赖。

## 四、E2E 策略

### 4.1 只覆盖核心旅程

- 选最高价值的用户路径：登录、下单、支付、注册。
- **不要全量 E2E**：慢到没人愿意跑，最终被弃用。
- 80% 用单测+集成覆盖，E2E 只守"主干"。

### 4.2 工具

- Web：Playwright、Cypress、Selenium。
- API：基于测试框架直接调接口（更稳、更快）。
- 移动端：Appium、Espresso。

### 4.3 环境

- 用"类生产"环境（数据脱敏、配置一致）。
- 避免依赖第三方外部服务（用 mock/stub 替代不稳定依赖）。
- 测试账号、测试数据隔离，防止污染生产。

## 五、契约测试（Contract Testing）

### 5.1 消费者驱动契约（CDC）

- 消费者定义"我期望提供者返回什么"（契约）。
- 提供者 CI 校验契约，保证不破坏调用方。
- 工具：Pact。

### 5.2 价值

- 在**集成前**发现接口变更破坏，减少对脆弱 E2E 的依赖。
- 适合多团队、多服务协作（解耦发布节奏）。

## 六、测试数据管理

- 用 **Builder / Factory** 模式造数据，避免硬编码魔法值。
- 数据隔离：每用例独立数据集，可并发、可重复。
- 用随机/唯一后缀防冲突（并发跑时）。
- 清理策略：事务回滚 / 用例后清理 / 容器销毁即清。

## 七、稳定性（Flaky）治理

不稳定的测试比没有测试更糟：
- 团队会对"红色"麻木，真问题被淹没。
- 常见 flaky 原因：时间依赖、并发竞争、共享状态、外部网络。
- 治理：隔离外部依赖、固定时间/随机种子、重试一次 + 标记调查。

## 八、CI 编排

- 单测：每次提交必跑（快）。
- 集成：PR 合并前跑（中速）。
- E2E：每日/预发布跑（慢，不必每次 PR）。
- 分阶段跑，平衡"反馈速度"与"覆盖成本"。

## 九、常见坑

1. **E2E 全量跑** → 慢到没人跑，最终被关掉。
2. **集成测试依赖共享库** → 互相污染，时好时坏。
3. **测试环境漂移** → 本地过、生产挂。
4. **不稳定测试（flaky）不修** → 团队无视红，真 bug 漏过。
5. **过度 Mock** → 测试通过却没反映真实协作问题。
6. **数据未隔离** → 用例顺序依赖，难以并行。
