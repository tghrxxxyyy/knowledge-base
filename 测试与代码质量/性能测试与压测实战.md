# 性能测试与压测实战

性能测试是验证系统在不同负载下的响应时间、吞吐量与稳定性的关键手段。
压测（压力测试）通过模拟高并发访问，发现容量瓶颈与隐性缺陷。
本文讲解压测类型、指标、工具、施压模型、结果分析与稳定性保障。

## 一、性能测试的类型

### 1.1 基准测试（Benchmark）

在固定条件下测量单接口/单操作的极致性能。
用于对比优化前后、评估组件能力。

### 1.2 负载测试（Load Test）

逐步增加并发，观察系统在预期负载下的表现。
目标是验证"日常峰值"下是否满足 SLA。

### 1.3 压力测试（Stress Test）

超过预期负载继续加压，找到系统拐点与崩溃边界。
目的是知道"什么时候会挂、挂在哪里"。

### 1.4 容量测试（Capacity Test）

确定系统能承载的最大吞吐或用户数。
为容量规划与扩容决策提供依据。

### 1.5 稳定性测试（Soak/Endurance）

长时间（数小时到数天）持续施加中等负载。
用于发现内存泄漏、连接泄漏、数据堆积等慢性问题。

### 1.6 峰值测试（Spike Test）

瞬时把流量打到峰值再回落，观察系统能否快速恢复。
验证对突发流量的弹性。

## 二、核心指标

### 2.1 响应时间（RT）

从发出请求到收到响应的耗时。
常用分位值：

- P50（中位数）：一半请求快于此值。
- P95/P99：绝大多数请求的上限，最关注尾部延迟。

### 2.2 吞吐量（Throughput/QPS/TPS）

单位时间处理的请求数或事务数。
QPS（Queries Per Second）、TPS（Transactions Per Second）。

### 2.3 并发数

同时向系统施加的压力会话数。
并发不等于用户数，也不等于 QPS。

### 2.4 错误率

失败请求占总请求的比例。
压测中错误率应作为硬性达标项。

### 2.5 资源利用率

CPU、内存、IO、网络、连接数、GC 等。
用于定位瓶颈在哪个环节。

### 2.6 拐点

吞吐不再增长、RT 急剧上升的临界点。
拐点左侧是可用区间，右侧是危险区。

## 三、常见压测工具

### 3.1 命令行轻量工具

- wrk：高并发 HTTP 基准测试，基于事件循环。
- ab（Apache Bench）：简单 HTTP 压力测试。
- hey：Go 实现的轻量压测工具。

### 3.2 分布式压测平台

- JMeter：图形化、支持丰富协议，插件生态成熟。
- Gatling：基于 Scala，DSL 编写场景，报告美观。
- Locust：基于 Python，以代码定义用户行为。
- k6：现代云原生压测工具，脚本用 JS。

### 3.3 自研/全链路压测

大型系统常做全链路压测：
用真实流量或影子流量在生产环境验证容量。
需要数据隔离（影子表/影子库）避免污染真实数据。

## 四、施压模型

### 4.1 并发模式

固定并发线程数，持续发送请求。
适合模拟固定数量的连接/用户。

### 4.2 吞吐量模式（RPS 目标）

设定目标 QPS，系统尽量逼近该速率。
更能反映"流量目标"而非"连接数"。

### 4.3 阶梯加压

逐步提升并发或 QPS，观察各档位的指标变化。
便于绘制"并发—RT—QPS"曲线，找到拐点。

### 4.4 浪涌模式

短时间内拉满再回落，模拟抢购、秒杀等突发。

## 五、压测脚本设计

### 5.1 场景建模

- 明确核心链路：哪些接口、调用顺序、参数依赖。
- 参数化：用变量代替硬编码，避免所有请求完全一样。
- 关联：上一个请求的返回值作为下一个请求的输入。

### 5.2 数据准备

- 准备足量且分布合理的测试数据。
- 避免所有请求命中同一条数据（失真）。
- 压测数据应与生产分布接近（热点、长尾）。

### 5.3 思考时间（Think Time）

模拟真实用户操作间隔，避免把机器压成"无脑轰炸"。
过度密集的请求会放大系统压力，偏离真实场景。

## 六、压测执行要点

### 6.1 隔离环境

- 尽量使用与生产等配的专属环境。
- 共享环境压测会干扰他人，且结果失真。
- 全链路压测必须用影子数据与流量标记。

### 6.2 监控同步

压测同时打开监控：
应用层（RT/QPS/错误率）、中间件（缓存/DB 连接）、系统（CPU/内存/IO）。
否则只知道"慢了"却不知道"卡在哪"。

### 6.3 逐步加压

不要一上来就拉满。
从低并发起步，确认无异常后再阶梯上升。

## 七、结果分析与瓶颈定位

### 7.1 看曲线而非单点

关注 RT 随并发上升的趋势：
线性区（健康）→ 拐点（饱和）→ 崩溃区（过载）。

### 7.2 分层定位

- RT 高但 CPU 低：可能是锁竞争、外部依赖慢。
- CPU 高：计算密集或 GC 频繁。
- 内存涨不降：疑似泄漏。
- 数据库连接满：连接池不足或慢查询占连接。

### 7.3 数据库视角

- 慢查询日志：找出高耗时 SQL。
- 锁等待：行锁/表锁竞争。
- 连接池：是否打满、是否泄漏。

### 7.4 缓存视角

- 命中率是否过低导致回源。

- 是否存在大 Key/热 Key。

## 八、稳定性保障

### 8.1 限流

对入口 QPS 设上限，超出拒绝，保护后端。

### 8.2 熔断降级

依赖故障时快速失败或返回兜底，避免雪崩。

### 8.3 超时与重试

- 合理设置下游超时，避免线程堆积。
- 重试加退避，避免重试风暴。

### 8.4 容量冗余

- 按峰值 × 安全系数预留容量。
- 关键链路有冗余实例与多可用区。

## 九、常见误区

- 只在单接口压，忽略真实调用链与依赖。
- 用生产数据但不隔离，污染真实业务。
- 只关注 QPS，忽视 P99 与错误率。
- 压测环境与生产规格差异大，结论不可信。
- 压完不分析，只报一个数字。

## 十、速记

- 类型：基准/负载/压力/容量/稳定性/峰值，各有目的。
- 指标：看 P99 与错误率，不只看平均 RT 和峰值 QPS。
- 工具：wrk 轻量、JMeter 全面、Locust 灵活、k6 现代。
- 加压：阶梯找拐点，隔离环境 + 同步监控。
- 保障：限流 + 熔断 + 超时 + 冗余，压测暴露问题而非制造事故。
