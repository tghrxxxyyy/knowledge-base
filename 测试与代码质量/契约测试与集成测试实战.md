# 契约测试与集成测试实战

> 本文在测试策略总论（见测试策略章节）基础上，深入集成测试与契约测试的工程落地：Testcontainers 实战、数据库/缓存集成验证、消费者驱动契约（CDC）、Mock 与真实依赖的取舍，以及常见误区。内容基于工程实践，框架以主流为准。

## 1. 集成测试的边界

- 集成测试验证"代码 + 真实/接近真实依赖"能否协作。
- 与单测区别：单测隔离，集成测协作。
- 与 E2E 区别：E2E 走完整链路，集成聚焦模块间。
- 目标：抓单测抓不到的"接口/配置/事务"问题。

## 2. 依赖管理策略

- 真实依赖：最准，但慢、有外部依赖。
- 容器化依赖（Testcontainers）：真实且隔离，推荐。
- 内存替代品：如 H2 替代 MySQL，快但有方言差异风险。
- Mock：仅外部不可控（第三方 API）时用。

## 3. Testcontainers 实战

- 用 Docker 起真实数据库/中间件做测试。
- 每个测试类起容器，或用单例容器复用。
- 测试用真实 SQL 方言，避免 H2 方言偏差。
- 需本地/CI 有 Docker 环境。

```java
@Container
static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
    .withDatabaseName("test").withUsername("u").withPassword("p");

@Test
void shouldInsertAndQuery() {
    // 用真实 mysql 连接，验证 JPA/MyBatis 行为
}
```

## 4. 数据库集成测试

- 验证：映射、事务、锁定、分页、方言函数。
- 每个测试用独立数据，避免相互影响。
- 事务回滚或容器重建保证干净。
- 关注：索引行为、唯一约束、外键。

## 5. 缓存集成测试

- 验证：读写一致、过期、淘汰、序列化。
- 用真实 Redis 容器而非内存假实现。
- 注意：序列化兼容性（对象结构变更）。
- 验证缓存击穿/雪崩防护逻辑（见高并发缓存章节）。

## 6. 消息集成测试

- 验证：发布/消费、序列化、重试、死信。
- 用真实 MQ 容器（Kafka/RabbitMQ）。
- 验证消费幂等（见分布式事务章节）。
- 验证顺序（单分区）与重复（至少一次）。

## 7. 契约测试概念

- 解决：微服务接口变更破坏消费者，但双方独立开发。
- 消费者定义期望的接口契约（请求/响应样例）。
- 提供者 CI 中验证自己满足契约。
- 双方解耦，无需联调环境。

## 8. 消费者驱动契约（CDC）

- 消费者先写契约测试，描述"我期望怎么调你"。
- 契约发布到 broker（如 Pact 思路）。
- 提供者拉契约，验证自身实现满足。
- 任一方破坏契约，CI 即失败。

## 9. 契约 vs E2E

- 契约测试轻、快、定位准，验证接口契约。
- E2E 重、慢，验证完整业务路径。
- 二者互补：契约防接口破坏，E2E 防业务破坏。
- 不应以 E2E 替代契约（慢且脆弱）。

## 10. 契约测试适用场景

- 多团队、接口多、联调成本高的微服务。
- 提供方与消费方迭代节奏不同。
- 外部 API 被多团队消费的"平台型"服务。
- 单体应用一般不必。

## 11. Mock 的正确姿势

- 外部不可控依赖（支付网关、短信）才 Mock。
- 内部依赖尽量用真实/容器化。
- Mock 验交互易碎，应主要验行为/结果。
- 避免过度 Mock 导致测试脱离真实。

## 12. 测试数据管理

- 测试数据工厂（Factory）生成符合约束的数据。
- 每个用例独立、可重复、无副作用。
- 用事务回滚或容器重建清理。
- 避免依赖全局固定数据（易污染）。

## 13. 并行与稳定

- 集成测试慢，需并行执行提速。
- 数据隔离是并行前提（独立库/前缀/命名空间）。
- 端口/资源冲突需规避。
- 失败需可重跑（幂等）。

## 14. CI 中的定位

- 提交跑单测（快）。
- PR 跑集成 + 契约（中速）。
- 夜间跑慢集成/E2E。
- 门禁卡集成与契约，防接口破坏合入。

## 15. 覆盖率与质量

- 集成测试覆盖单测到不了的路径（事务回滚、方言）。
- 契约测试覆盖接口契约。
- 监控：集成测试通过率、契约破坏数。
- 与质量门禁（见代码质量度量章节）结合。

## 16. 常见踩坑

1. **用 H2 测 MySQL 方言**：上线 SQL 报错；用 Testcontainers 真库。
2. **集成测试共享数据**：用例互相污染，偶发失败；隔离数据。
3. **全 Mock 内部依赖**：测了桩没测真协作；用容器真依赖。
4. **用 E2E 代替契约**：慢且脆弱，接口破坏难定位；加契约。
5. **契约只消费者测**：提供者不知情；需提供者验证。
6. **测试不动清理**：容器/数据堆积，资源耗尽；回滚/重建。
7. **集成测试进单测门禁**：拖慢提交反馈；分层执行。

## 17. 落地清单

- 识别需真实依赖的集成点（DB/缓存/MQ）。
- 用 Testcontainers 起真实组件。
- 数据隔离 + 自动清理。
- 微服务接口加契约测试（消费者定义、提供者验证）。
- CI 分层：单测→集成+契约→E2E。
- 门禁卡集成与契约通过率。

## 18. 与测试策略章节呼应

- 测试金字塔：单测底座、集成中层、E2E 顶层。
- 本文聚焦中层（集成）与接口（契约）。
- 配合代码质量度量做门禁。
- 配合性能/混沌做高阶段验证。

## 19. 工具生态映射

- 容器化：Testcontainers（Java/多语言）。
- 契约：Pact 思路（消费者/提供者）。
- ORM 集成：Spring Boot Test + Testcontainers。
- 断言：AssertJ/JUnit 5。

## 20. 小结

集成与契约测试是"防协作破裂"的关键层：集成用 Testcontainers 真实依赖验证 SQL/事务/序列化，契约用消费者驱动防接口破坏。铁律：**内部依赖用真组件而非全 Mock、测试数据隔离可重跑、契约需提供者验证、用契约+E2E 互补而非替代、CI 分层执行**。它们上承接单测，下支撑 E2E，构成可信交付链。
