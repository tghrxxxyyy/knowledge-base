# 01 · 测试体系总论

> 写测试之前，先想清楚三个问题：**测什么、在哪一层测、用什么替身隔离、覆盖到什么程度**。这一篇把测试领域的"地图"画清楚，后面各篇都是这张地图的某个区域放大。

---

## 一、为什么需要一套"测试体系"

单写几个 `@Test` 很容易，难的是让整套测试**可信、快、好维护、能兜住真实缺陷**。没有体系，常见三种崩坏：

- **"测试比代码还多 bug"**：测试本身不可靠，红绿无意义；
- **"改一行跑半小时"**：E2E 当主力，反馈慢到没人跑；
- **"覆盖率 90% 还是一堆线上事故"**：覆盖的是 happy path，分支/异常没覆盖。

体系的目标：**用最小成本，获得最大的缺陷拦截置信度**。

### 1.1 一个真实改造案例：从"冰淇淋锥"到"金字塔"

某中台团队改造前（冰淇淋锥反模式）：

| 指标 | 改造前 | 改造后 |
|------|--------|--------|
| 单元测试数 | 120 | 2400 |
| E2E 用例数 | 680 | 60 |
| 全量套件耗时 | 52 分钟 | 单测 4 分钟 + E2E 12 分钟 |
| 本地能跑的占比 | 5%（只能 CI 跑） | 95% |
| 线上 P0 漏测率 | 改造前 6 起/季度 | 改造后 1 起/季度 |
| 开发者跑测试频率 | 几乎不跑 | 每次提交前必跑 |

> 关键不是"测更多"，而是"在对的层测对的量"。E2E 从 680 砍到 60，单测从 120 涨到 2400，总缺陷拦截率反而大幅提升，且反馈速度提升一个数量级。

## 二、测试金字塔（Test Pyramid）

Mike Cohn 提出的经典模型，定义了"各层测试的数量比例"。

```mermaid
graph TD
    E2E[端到端 E2E<br/>少量·慢·贵] --> INT[集成测试<br/>适量·中速]
    INT --> UNIT[单元测试<br/>海量·快·便宜]

    style UNIT fill:#c6efce,stroke:#333
    style INT fill:#ffeb9c,stroke:#333
    style E2E fill:#ffc7ce,stroke:#333
```

| 层级 | 范围 | 速度 | 数量 | 稳定性 | 典型工具 |
|------|------|------|------|--------|----------|
| 单元 Unit | 单个函数/类，隔离依赖 | 毫秒 | 海量（占 70%+） | 高 | JUnit5、pytest、Go test |
| 集成 Integration | 跨模块/真实依赖（DB、MQ） | 秒级 | 适量（20%） | 中 | Spring Boot Test、Testcontainers |
| 组件/接口 API | 单个服务对外接口 | 秒~分 | 少量 | 中 | REST Assured、Postman、Karate |
| 端到端 E2E | 跨服务全链路 | 分~十分 | 极少（<10%） | 低（Flaky 多） | Playwright、Cypress |

**反模式 · 冰淇淋锥（Ice Cream Cone）**：E2E 巨多、单测几乎没有——反馈慢、脆弱、维护灾难。很多"传统 QA 团队"正是这样。

> **口诀：金字塔别反成冰淇淋，单测是地基、E2E 是塔尖。**

### 现代修正：测试奖杯（Testing Trophy）

Kent C. Dodds 提出，对前端/组件化时代更贴切：

```mermaid
graph TD
    E[端到端 E2E 少量] --> C[组件/集成测试 中量]
    C --> U[单元测试 中量]
    U --> S[静态分析/类型检查 海量·最快]
```

强调**静态分析（类型系统、Lint）是最底层、最便宜的"测试"**，应优先用满。

### 2.1 金字塔的"数量"该怎么定

金字塔说的是**相对比例**，不是绝对数字。经验参考：

| 项目类型 | 单测:集成:契约:E2E 经验比 |
|----------|---------------------------|
| 纯算法/库 | 95:5:0:0 |
| 单体后端服务 | 70:25:0:5 |
| 微服务架构 | 60:20:15:5 |
| 重前端 SPA | 40:20:0:40（前端 E2E 占比高） |

> 不要机械套比例。核心是：**能在底层拦住的缺陷，绝不上浮到昂贵的 E2E**。

## 三、测试象限（Agile Testing Quadrants）

Brian Marick / Lisa Crispin 的象限，从"业务 vs 技术""支持团队 vs 评判产品"两个维度组织测试。

```mermaid
quadrantChart
    title 测试象限
    x-axis 支持团队 --> 评判产品
    y-axis 技术导向 --> 业务导向
    quadrant-1 Q1 技术·支持: 单元/组件
    quadrant-2 Q2 业务·支持: 功能/原型
    quadrant-3 Q3 业务·评判: E2E/探索性
    quadrant-4 Q4 技术·评判: 性能/安全/混沌
```

| 象限 | 目的 | 例子 | 自动化程度 |
|------|------|------|-----------|
| Q1 技术·支持 | 帮开发写对代码 | 单元、组件、API 测试 | 高（可全自动化） |
| Q2 业务·支持 | 帮业务确认需求 | 验收测试、原型、用例 | 中（BDD 可部分自动化） |
| Q3 业务·评判 | 评判产品体验 | E2E、探索性测试、可用性 | 低（依赖人） |
| Q4 技术·评判 | 评判非功能质量 | 性能、安全、混沌、兼容性 | 高（可编排） |

**启示**：自动化主要覆盖 Q1+Q4（确定性、可量化）；Q2/Q3 的人为判断（探索性测试）难以完全自动化，需保留人工。

## 四、测试分层（按"被测对象边界"切）

金字塔讲的是"数量比例"，分层讲的是"每一层具体测谁、用什么依赖"。

```mermaid
graph LR
    subgraph 单元层
      U1[纯函数/算法] --> U2[Service 业务逻辑+Mock依赖]
    end
    subgraph 集成层
      I1[Service+真实DB] --> I2[多服务+消息/缓存]
    end
    subgraph 端到端层
      E1[浏览器/App→网关→全链路]
    end
    U2 --> I1
    I2 --> E1
```

- **单元层**：只测"自己写的逻辑"，DB/HTTP/时间/随机数等一律替身隔离。
- **集成层**：引入**真实**依赖（Testcontainers 起的 MySQL/Redis），验证"我的代码和真实依赖接得对"。
- **端到端层**：从外部视角验证"用户能走通"，不关心内部实现。

> 关键原则：**在能定位缺陷的最小层级测**。一个算税逻辑错误，单测就该红，不必等 E2E 才发现。

## 五、测试替身（Test Doubles）

Gerard Meszaros 的经典分类——"替代真实依赖的对象"有 5 种，别再笼统叫"Mock"。

| 替身 | 干什么 | 验证什么 | 例子 |
|------|--------|----------|------|
| **Dummy** | 仅占位，从不使用 | 满足参数签名 | `null` 或空对象 |
| **Stub** | 预置返回，不验证调用 | 提供可控输入 | 返回固定用户 |
| **Spy** | 记录调用，可部分真实 | 调用是否发生+部分逻辑 | 记录发了几封邮件 |
| **Mock** | 预编程期望，验证交互 | 是否按预期被调用 | 验证 `save()` 被调一次 |
| **Fake** | 轻量但可用的实现 | 行为正确（非生产级） | 内存数据库 In-Memory DB |

```mermaid
graph LR
    D[Dummy 占位] --> S[Stub 预置返回]
    S --> SP[Spy 记录调用]
    SP --> M[Mock 期望验证]
    F[Fake 可用实现] -.独立类别.-> X
```

**最常见的误区**：把所有替身都当 Mock 用——"为了隔离而 Mock 了一切"，结果测的是"Mock 行为"而非"真实逻辑"，且过度耦合实现细节（一改内部调用就红）。

### 5.1 五种替身的 Java 代码对照

```java
// 被测服务
class NotificationService {
    void notify(User u, String msg) { /* 发邮件 */ }
}

// 1) Dummy：仅占位（满足方法签名，从不真正调用）
class DummyUser extends User { /* 空实现，仅用于通过编译 */ }

// 2) Stub：预置返回，不验证调用
class StubUserRepo implements UserRepo {
    public User find(long id) { return new User("Tom"); } // 永远返回 Tom
}

// 3) Spy：记录调用次数（如记录发了几封邮件）
class SpyMailer implements Mailer {
    int sent = 0;
    public void send(String to, String body) { sent++; }
}

// 4) Mock：预编程期望 + 验证交互（Mockito）
UserRepo repo = mock(UserRepo.class);
when(repo.find(1L)).thenReturn(new User("Tom"));
// ...调用后...
verify(repo, times(1)).find(1L);

// 5) Fake：可用但非生产级（内存实现）
class InMemoryUserRepo implements UserRepo {
    Map<Long, User> db = new HashMap<>();
    public User find(long id) { return db.get(id); }
    public void save(User u) { db.put(u.id(), u); }
}
```

> **口诀：该用 Stub 别用 Mock，测行为更要测结果；Fake 比 Mock 更接近真相。**

## 六、测试覆盖率：看什么、别迷信什么

### 6.1 三种覆盖率口径

| 口径 | 含义 | 局限 |
|------|------|------|
| **行覆盖 Line** | 每行执行过没 | 不保证分支都走 |
| **分支覆盖 Branch** | 每个 if/else 分支都走 | 不保证组合 |
| **变异覆盖 Mutation** | 故意改代码（如 `>` 改 `<`），看测试能否抓住 | 最严，但慢 |

### 6.2 覆盖率陷阱

- **"90% 覆盖 = 高质量"是错觉**：全在 happy path，边界/异常 0 覆盖，等于没测。
- **为覆盖率而写测试**：`assertEquals(true, true)` 式凑数，反而污染套件。
- **正确用法**：覆盖率用于**找盲区**（哪没测），不是 KPI。门禁设下限（如增量行覆盖 ≥80%），但更要**Code Review 看测试有没有测对**。

### 6.3 代码示意：覆盖率该测分支而非只走主路径

```java
// 被测逻辑
int discount(int price, boolean vip) {
    if (price <= 0) throw new IllegalArgumentException("price");
    int d = price > 1000 ? 100 : 0;   // 分支1
    if (vip) d += 50;                  // 分支2
    return Math.max(0, price - d);
}

// 好的测试：覆盖异常 + 三个分支组合
@Test void testBranches() {
    assertThrows(IllegalArgumentException.class, () -> discount(0, false)); // 异常
    assertEquals(1000, discount(1000, false));  // 不打折
    assertEquals(900,  discount(1000, true));   // vip+满减
    assertEquals(50,   discount(100,  true));   // 仅vip
}
```

### 6.4 JaCoCo 配置与解读（Java 实战）

```xml
<!-- pom.xml -->
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.11</version>
  <executions>
    <execution>
      <goals><goal>prepare-agent</goal></goals>
    </execution>
    <execution>
      <id>report</id>
      <phase>test</phase>
      <goals><goal>report</goal></goals>
    </execution>
    <execution>
      <id>check</id>
      <goals><goal>check</goal></goals>
      <configuration>
        <rules>
          <rule>
            <element>BUNDLE</element>
            <limits>
              <limit><counter>LINE</counter><value>COVEREDRATIO</value><minimum>0.80</minimum></limit>
              <limit><counter>BRANCH</counter><value>COVEREDRATIO</value><minimum>0.70</minimum></limit>
            </limits>
          </rule>
        </rules>
      </configuration>
    </execution>
  </executions>
</plugin>
```

> 报告解读要点：看**未覆盖行在哪**——若是核心分支逻辑，补测试；若是纯 getter/toString，可忽略。JaCoCo 还支持**增量覆盖率**（只算本次变更代码），更贴合门禁。

## 七、测试命名与组织规范

| 维度 | 推荐 | 反例 |
|------|------|------|
| 方法名 | `shouldXxxWhenYyy` / `givenX_whenY_thenZ` | `test1`、`testUser` |
| 文件组织 | 与被测类同包同名 + `Test` 后缀 | 全部塞 `TestAll.java` |
| 分组 | 按 `@Nested` 场景分组 | 平铺几十个无结构方法 |
| 数据 | 构造器/工厂，最小必要 | `new User()` 一堆 null 字段 |

```java
class PricingServiceTest {
    @Nested class VipUser {
        @Test void shouldApplyExtraDiscountWhenVipAndAmountAbove1000() { ... }
        @Test void shouldApplyOnlyVipDiscountWhenAmountBelow1000() { ... }
    }
    @Nested class NormalUser {
        @Test void shouldNotDiscountWhenBelowThreshold() { ... }
    }
}
```

## 八、测试左移（Shift-Left）与质量内建

### 8.1 缺陷修复成本曲线

```mermaid
graph LR
    R[需求] --> D[设计] --> C[编码] --> T[测试] --> P[生产]
    cost1[1x] --> cost2[5x] --> cost3[10x] --> cost4[20x] --> cost5[100x+]
```

发现越晚越贵。**左移 = 把验证动作尽量提前**：需求阶段写验收标准（BDD）、编码前想清边界、写代码同时写单测（TDD）、静态分析在保存即提示。

### 8.2 质量内建（Built-in Quality）

> W. Edwards Deming："你不能检验质量进去，它必须被建造进去。"

质量内建三件套：
1. **预防优于检测**：规范、类型、Lint 在写时就挡住低级错；
2. **每个人对质量负责**：不是 QA 兜底，开发自测、CR 互相把关；
3. **快速反馈闭环**：本地→CI→预发，每一环都能秒级/分钟级暴露问题。

## 九、测试经济学的两个关键权衡

1. **边际收益递减**：从 0→70% 覆盖很容易拦住大量缺陷；70%→95% 成本陡增、收益渐平。设合理门禁，别追 100%。
2. **脆弱性 vs 置信度**：Mock 越细，测试越脆（实现一变就红）；过度用真实依赖，测试越慢越 Flaky。按"分层"分配——单测用 Mock 求快，集成用真实求真。

## 十、团队落地路线图

### 10.1 新项目（从 0 搭体系）

| 阶段 | 动作 | 产出 |
|------|------|------|
| 第 1 周 | 定规范（Lint/格式化）、接 CI、配 JaCoCo | 提交即跑单测 |
| 第 2-4 周 | 核心逻辑补单测、关键路径加集成 | 增量覆盖 ≥80% |
| 第 1-2 月 | 接 SonarQube 门禁、写 5-10 条 E2E 主流程 | 门禁卡合入 |

### 10.2 存量项目（渐进改造）

| 阶段 | 动作 | 注意 |
|------|------|------|
| 第一步 | **只对新代码要求覆盖**（增量门禁） | 不追存量 100%，避免瘫痪 |
| 第二步 | 每修一个 bug，补一个回归测试 | 缺陷驱动补测，最划算 |
| 第三步 | 抽离核心模块补单测，逐步把 E2E 下沉为单测 | 降 E2E 占比 |
| 第四步 | 引入契约测试解耦微服务发布 | 独立发布 |

> 存量改造铁律：**增量门禁 + bug 驱动补测**，比"运动式刷存量覆盖"有效得多。

## 十一、面试高频追问（20 题 + 要点）

1. **测试金字塔是什么？反模式冰淇淋锥的危害？** → 海量单测、适量集成、少量 E2E；反模式反馈慢、脆弱。
2. **单元测试与集成测试边界？** → 单测隔离依赖测逻辑、集成引入真实依赖测对接。
3. **Mock / Stub / Fake / Spy 区别？** → 见第五节表；Mock 验交互、Stub 给数据、Fake 可用实现、Spy 记录。
4. **为什么不要 Mock 自己写的逻辑？** → 等于没测，且过度耦合实现。
5. **行覆盖和分支覆盖区别？** → 行覆盖不保证分支都走，分支覆盖更严。
6. **变异测试是什么？** → 改代码看测试能否抓到，最严但慢。
7. **覆盖率 90% 但事故频发为什么？** → 全 happy path，异常/边界 0 覆盖。
8. **测试左移含义与实践？** → 验证前移；BDD 验收、TDD、保存即 Lint。
9. **质量内建 vs 质量检验？** → 质量是设计出来的不是测出来的。
10. **Flaky 测试危害？** → 狼来了，红灯不可信，门禁失效。
11. **契约测试解决什么问题？** → 微服务接口悄悄 breaking。
12. **CDC 消费者驱动契约流程？** → 消费者定契约、提供者验证、Broker 存。
13. **为什么 E2E 要少？** → 慢、贵、Flaky 多；只测关键主流程。
14. **Testcontainers 价值？** → 真依赖又隔离，免方言差异坑。
15. **JaCoCo 增量覆盖？** → 只算本次变更代码覆盖，适合门禁。
16. **测试该不该依赖顺序？** → 不该，必须独立可重复。
17. **时间/随机数怎么测？** → 注入 Clock/Random，不依赖"现在"。
18. **如何治理 Flaky？** → 标记+限期修、禁 sleep、自动等待、数据隔离。
19. **TDD 红绿重构？** → 先失败测试、最小实现、重构不改行为。
20. **存量项目如何起步测试？** → 增量门禁 + bug 驱动补测，不追存量 100%。
