# 单元测试与测试金字塔

> 板块：测试与代码质量 　|　 返回：[README](README.md)
> 关联：[测试与代码质量总览](测试与代码质量总览.md)、[代码质量与静态分析](代码质量与静态分析.md)、[集成测试与E2E策略](集成测试与E2E策略.md)

测试金字塔是软件质量的基础模型：单元测试应占绝大多数（多、快、廉），集成与 E2E 少而精（慢、贵、覆盖关键链路）。本文讲清金字塔、FIRST 原则、AAA 结构、Mock 边界、度量与 TDD，帮助建立可持续的测试体系。

## 一、测试金字塔

```
        /\        UI / E2E（少、慢、贵、易碎）
       /  \       集成测试（中、验证协作）
      /----\      单元测试（多、快、廉、稳定）
     /------\
```

### 1.1 比例与含义

| 层级 | 占比 | 速度 | 成本 | 定位 |
|------|------|------|------|------|
| 单元测试 | ≥ 70% | 毫秒级 | 低 | 验证函数/类行为，失败易定位 |
| 集成测试 | 20% | 秒级 | 中 | 验证组件协作（DB/RPC/外部） |
| E2E | < 10% | 分钟级 | 高 | 覆盖最高价值用户旅程 |

- **单元测试**：快、稳定、可随时跑，开发者敢频繁运行。
- **集成测试**：覆盖接口/事务/外部依赖边界，不必多但关键路径要有。
- **E2E**：仅覆盖最高价值旅程（登录、下单、支付），多了会慢且脆。

### 1.2 反模式

| 反模式 | 形态 | 问题 |
|--------|------|------|
| 冰淇淋筒 | 大量 E2E、极少单测 | 跑得慢、易碎、反馈迟、维护贵 |
| 沙漏 | 单测和 E2E 多、集成少 | 组件间契约问题漏测 |
| 倒金字塔 | 全靠手动/E2E | 无回归保障 |

> 正确姿态：底宽、顶尖，金字塔形。把测试预算投在底层的单测上。

## 二、单元测试原则（FIRST）

| 字母 | 含义 | 实践 |
|------|------|------|
| **F**ast | 快 | 毫秒级，不连真实 DB/网络；开发者敢随时跑 |
| **I**solated | 独立 | 不依赖外部（DB/网络/时间），用 mock/double 隔离 |
| **R**epeatable | 可重复 | 重复跑结果一致，不依赖顺序/环境 |
| **S**elf-validating | 自验证 | 自动断言，不需要人眼看 |
| **T**imely | 及时 | 随代码写（TDD 或同步写），不事后补 |

> 不遵守 FIRST 的"测试"往往变成负担：慢、脆、没人敢跑。

## 三、AAA 结构（Arrange-Act-Assert）

```java
@Test
void should_deduct_stock_when_order_paid() {
    // Arrange：准备输入与依赖（用 builder/factory 构造）
    Order order = OrderBuilder.anOrder().withSku(SKU_A).withQty(2).build();
    // Act：执行被测行为
    order.pay();
    // Assert：验证结果（聚焦一个行为）
    assertEquals(0, stock.of(SKU_A));
    assertEquals(PAID, order.status());
}
```

好处：结构统一、意图清晰、易读易维护；新人也能照着写。

```python
def test_should_reject_when_balance_insufficient():
    # Arrange
    acc = Account(balance=10)
    # Act
    result = acc.transfer(to=other, amount=100)
    # Assert
    assert result == REJECTED
    assert acc.balance == 10  # 余额不变
```

## 四、Mock 与边界

### 4.1 何时用 Mock

- 隔离慢/不稳定依赖：数据库、RPC、第三方 API、消息队列。
- 模拟异常分支：超时、异常、空返回、限流（难以在真实环境触发）。
- 验证交互：是否调用了某依赖、次数、参数（Mock 的强项，如"发短信被调用一次"）。

```java
// Mockito：验证交互
when(userRepo.findById(1L)).thenReturn(Optional.of(user));
service.grantCoupon(1L);
verify(couponRepo, times(1)).save(any());  // 验证调用
```

### 4.2 何时不用 Mock

- 不要 mock 一切 → 测的是 mock 而非真实逻辑（假绿）。
- 纯函数/值对象可直接测，无需 mock。
- 过细 mock 会让测试与实现强耦合，一改实现就红（测试变脆弱）。

### 4.3 Mock 与真实边界

| 测什么 | 用真实还是 Mock |
|--------|----------------|
| 纯业务逻辑/算法 | 真实（无需 mock） |
| 与 DB 交互的 Repository | 集成测试用真实 DB（Testcontainers） |
| 第三方 API | Mock（或契约测试） |
| 时间/随机 | 注入 Clock/Seed，注入式可控 |

> 经验法则：测"决策逻辑"用 mock 隔离依赖；测"集成正确"用真实依赖（集成测试层）。

### 4.4 边界用例（必测）

边界最易藏 bug，必须覆盖：空、null、超长字符串、负数、0、最大值、并发、异常路径、时区、编码。

```java
// 参数化测试覆盖边界
@ParameterizedTest
@ValueSource(ints = {0, 1, -1, Integer.MAX_VALUE})
void should_handle_edge(int qty) { ... }
```

## 五、命名与可读性

- 测试方法名表达"场景+期望"：`should_xxx_when_yyy` 或 `givenX_whenY_thenZ`。
- 一个测试聚焦一个行为，断言集中、易定位失败原因。
- 用 builder/factory 构造测试数据，避免大段硬编码；用 `@Nested` 分组相关测试。
- 失败信息要有意义（自定义 `assertThat` 消息），一眼知道哪错。

## 六、度量：覆盖率之外

- **行覆盖/分支覆盖**是基础，但**不够**：高覆盖可能全是 getter/空分支。
- 看**关键路径覆盖**：核心业务逻辑、异常分支、边界是否覆盖。
- **变异测试（Mutation Testing）**：故意改代码（如把 `>` 改 `<`、删 `if`），看测试能否抓到。抓不到说明测试无效（假绿）。工具：PIT (Java)、mutmut (Python)。
- **测试有效性**：不仅"跑通"，而是"改错能被发现"。覆盖率 100% + 变异存活 = 无效测试。

| 指标 | 说明 | 陷阱 |
|------|------|------|
| 行覆盖 | 代码行被执行比例 | 可能只走 happy path |
| 分支覆盖 | if/else 各分支覆盖 | 仍可能未断言结果 |
| 变异存活率 | 变异后被测出的比例 | 越低越说明测试无效 |

## 七、稳定性（Flaky）

- 不稳定的单测比没有更糟：团队对"红"麻木，真 bug 被淹没。
- 常见原因：时间依赖（`new Date()`）、并发竞争、共享状态、外部网络、随机。
- 治理：
  - 注入时钟（`Clock`/`FixedClock`）替代 `new Date()`；
  - 固定随机种子；
  - 隔离测试数据（每测试独立 DB/事务回滚）；
  - 资源用 `@Before`/`@After` 清理；
  - 对偶发失败：重试一次 + 标记调查，但不长期容忍。

```java
// 注入时钟，避免时间依赖
Clock clock = Clock.fixed(Instant.parse("2026-01-01T00:00:00Z"), UTC);
service = new Service(clock);
```

## 八、TDD（测试驱动开发）

- **红**：写失败测试 → **绿**：最小实现通过 → **重构**：优化不改行为。
- 适合：复杂逻辑、算法、核心领域规则、边界多的代码。
- 不适合：简单 CRUD、UI 层、与外部强耦合的胶水（过度 TDD 反而拖慢）。
- 好处：先想清接口与边界、重构有安全网、设计更可测。

```
写测试(红) → 实现(绿) → 重构(保持绿) → 下一个
```

## 九、测试数据管理

- **Factory/Build**：用测试工厂构造对象，减少重复。
- **Fixture**：固定数据集（JSON/SQL）用于集成测试。
- **事务回滚**：Spring `@Transactional` 测试回滚，保持环境干净。
- **Testcontainers**：集成测试用真实 DB/Redis/Kafka 容器，贴近生产。
- 避免跨测试共享可变状态（导致顺序依赖、并行失败）。

## 十、CI 中的定位

| 阶段 | 测试类型 | 反馈 |
|------|---------|------|
| 提交前/PR | 单测（秒级） | 阻断合并（Required Check） |
| PR 合并后 | 集成测试 | 验证协作 |
| 夜间/预发 | E2E + 性能 | 全链路保障 |

- 单测：每次提交必跑，失败即阻断。
- 覆盖率趋势纳入门禁（新增代码不低于阈值，如 80%）。
- 慢测试（E2E）异步/定时跑，不阻塞开发。

## 十一、常见坑

1. **单测调真实 DB/接口** → 慢且不稳定，环境一变就红（用 mock/Testcontainers 分层）。
2. **一个测试多断言多分支** → 失败时难定位（一个测试一个行为）。
3. **只为覆盖率写无断言测试** → 假绿，毫无价值（看变异测试）。
4. **依赖执行顺序** → 并行跑就挂（测试间独立）。
5. **mock 过度** → 测的是桩，重构时大量红（只 mock 外部依赖）。
6. **从不重构测试** → 代码演进后测试腐化、越来越慢。
7. **忽略 flaky** → 团队对红麻木，真 bug 漏过。
8. **只测 happy path** → 异常/边界不覆盖，线上炸。
9. **测试数据硬编码** → 难维护，改一处崩一片（用 factory）。
10. **把集成测试当单测跑** → CI 慢，反馈迟（分层）。

## 十二、落地清单

1. 建立金字塔比例：单测为主（≥70%），集成/E2E 精简。
2. 遵守 FIRST + AAA，命名表达意图。
3. 正确用 Mock：隔离外部依赖，测决策逻辑；集成层用真实依赖。
4. 必测边界与异常路径；用参数化测试覆盖。
5. 用变异测试检验有效性，而非只看覆盖率数字。
6. 治理 flaky：注入时钟/固定种子/隔离数据。
7. CI 强制单测门禁；覆盖率趋势监控。
