# 代码质量与静态分析

> 板块：测试与代码质量 　|　 返回：[README](README.md)

代码质量决定系统的可维护性、稳定性与演进速度。静态分析在不运行代码的前提下，通过规则检查发现坏味道、漏洞与规范违例，是质量门禁的第一道关。本文讲清质量维度、工具、关键指标、门禁与工程文化。

## 一、质量的多维视角

不要只盯"能跑"。一份高质量代码应满足：

- **可读性**：命名清晰、结构合理、意图自解释。
- **可维护性**：改动局部化、依赖清晰、无"牵一发动全身"。
- **可测试性**：依赖可替换、逻辑可隔离。
- **健壮性**：边界处理、异常兜底、不静默失败。
- **安全性**：无注入、无敏感泄露、依赖无已知漏洞。
- **性能**：无明显低效（N+1、大对象、死循环）。

## 二、静态分析原理

静态分析不执行程序，而是通过：
- **词法/语法解析**：构建 AST（抽象语法树）。
- **数据流分析**：追踪变量来源与去向，发现空指针、资源未释放。
- **模式匹配**：按规则识别坏味道（如 `==` 比较字符串）。
- **依赖扫描**：检查第三方库已知 CVE。

优点：快、覆盖全、可自动化、可 CI 卡点。
缺点：有误报（false positive）与漏报（false negative），需规则调优。

### 2.1 典型规则分类

| 类别 | 示例 |
|------|------|
| 坏味道 | 过长函数、过大类、重复代码、魔法数字 |
| 潜在 Bug | 空指针解引用、资源未关闭、除零、equals 误用 |
| 安全 | SQL 注入、命令注入、硬编码密钥、XSS |
| 并发 | 非线程安全集合共享、锁未释放、双重检查锁失效 |
| 规范 | 命名、包结构、缺少注释/文档 |

## 三、主流工具

| 语言 | 格式化 | Lint/分析 | 平台 |
|------|--------|-----------|------|
| Java | Spotless | SpotBugs / PMD / Checkstyle / SonarQube | SonarQube |
| JS/TS | Prettier | ESLint | SonarQube / 自研 |
| Python | black / yapf | flake8 / pylint / ruff | SonarQube |
| Go | gofmt | go vet / golangci-lint | SonarQube |
| 通用 | - | - | SonarQube（多语言） |

### 3.1 工具分工

- **格式化（formatter）**：统一风格，消除"风格争吵"（black、gofmt、Prettier）。
- **Linter**：规则检查（未用变量、复杂表达式、潜在 bug）。
- **Bug 模式检测**：SpotBugs/FindBugs 类，基于字节码/模式找已知 bug 模式。
- **规约检查**：Checkstyle 强制命名、包结构、Javadoc 等团队规范。

## 四、SonarQube 核心指标

- **代码重复率（Duplication）**：复制粘贴是维护噩梦。
- **圈复杂度（Cyclomatic Complexity）**：独立路径数，越高越难测。
- **认知复杂度（Cognitive Complexity）**：人为理解的难度（更贴近直觉）。
- **技术债（Technical Debt）**：按规则估算修复所需时间。
- **覆盖率（Coverage）**：单测覆盖比例（但非唯一指标）。
- **安全漏洞 / 热点**：依赖与代码中的安全风险。

### 4.1 质量门禁（Quality Gate）

设定阈值，不达标**禁止合并/发布**：
- 新增代码覆盖率 ≥ 80%。
- 零新增 Blocker/Critical 问题。
- 新增重复率 ≤ 3%。
- 技术债比率（修复时间/开发时间）低于阈值。

门禁要"卡新增"而非"卡存量"，避免历史债压垮新提交。

## 五、圈复杂度与重构信号

- 方法圈复杂度 > 10：开始警惕。
- > 20：必须拆分（长函数、深嵌套、多分支）。
- 降低手段：早返回（guard clause）、提取方法、策略模式替代长 `if-else`、查表法。

### 5.1 复杂度计算示例

```java
int foo(int x, int y, int z) {
    if (x > 0) {            // +1
        if (y > 0) {        // +1
            return 1;
        }
    } else if (z > 0) {     // +1
        return 2;
    }
    return 0;
}
// 判定节点：if/else if = 3 → 圈复杂度 = 3 + 1 = 4
```

## 六、pre-commit 钩子

提交前本地自动跑：格式化、lint、单测。
- 好处：把低级问题挡在本地，不浪费 CI 与评审精力。
- 工具：husky（JS）、pre-commit（Python）、git hooks + lefthook。
- 注意：pre-commit 应快（秒级），重活交给 CI。

## 七、与 CI/CD 集成

- 每次 PR 跑静态分析，结果评论到 PR。
- 质量门禁作为合并条件（Required Check）。
- 趋势看板：监控技术债、覆盖率走势，避免劣化。
- 增量分析：只对新代码严格，存量渐进治理。

### 7.1 GitHub Actions 示例

```yaml
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: ./gradlew sonarqube -Dsonar.pullrequest.key=${{ github.event.pull_request.number }}
      - name: Block on Quality Gate
        run: ./scripts/check-quality-gate.sh   # 调用 Sonar API 判定门禁
```

## 八、Code Review 文化

- **小 PR**：单职责、易审、易回滚。
- **清单化**： reviewer 按清单检查边界/并发/安全/可测性。
- **自动化管风格，人审管逻辑**：格式/命名交给工具，人聚焦设计、边界、正确性。
- **对事不对人**：Review 是提质，不是找茬；建立"彼此提意见"的信任氛围。

## 九、技术债管理

- **可视化**：把技术债折算成"人天"，让业务方看到代价。
- **还债节奏**：每个迭代留 10–20% 额度重构，避免指数膨胀。
- **防新增**：门禁卡住新债；存量债登记到看板，按 ROI 排序偿还。
- **不要一次性还**：存量债一次性清会阻断业务，渐进式更可持续。

## 十、常见坑

1. **工具装了不接门禁** → 没人看报告，形同虚设。
2. **只看覆盖率** → 高覆盖但全是 getter/setter，坏味道依旧。
3. **门禁过严一次性卡全部存量** → 团队对抗、绕过。
4. **规则不调优** → 海量误报让真问题淹没。
5. **CR 变成风格审判** → 团队内耗，应该让工具管风格。
6. **技术债无人还** → 越积越多，重构成本指数上升。
