# 测试策略与自动化体系

> 本文梳理软件测试的完整体系：测试金字塔、各层级测试（单元/集成/端到端/契约）、测试数据管理、Mock 与 Testcontainers、CI 中的测试策略、覆盖率与质量门禁。内容基于工程实践，框架以主流为准。

## 1. 为什么需要测试体系

测试的目标不是"证明无 bug"，而是"在可控成本下尽早暴露风险"。好的测试体系让团队敢改代码、能快速交付，而非靠人工回归。

代价曲线：越早发现缺陷，修复成本越低（需求期 vs 生产期相差数十倍）。

## 2. 测试金字塔

经典金字塔（自底向上）：

- **单元测试**：量大、快、隔离，验证函数/类逻辑。
- **集成测试**：验证模块间协作（DB、缓存、外部服务）。
- **端到端测试（E2E）**：验证完整用户路径，少而慢。
- **手工/探索测试**：补自动化盲区。

反模式"冰淇淋筒"：大量 E2E、极少单测，导致反馈慢、维护贵。

## 3. 单元测试

### 3.1 原则

- **快**：毫秒级，可频繁跑。
- **独立**：不依赖外部状态、随机性可控。
- **可读**：用例名表达意图（行为驱动命名）。
- **可重复**：顺序无关、环境无关。

### 3.2 结构（AAA）

- **Arrange**：准备输入与依赖。
- **Act**：执行被测逻辑。
- **Assert**：验证结果。

### 3.3 覆盖什么

- 核心业务逻辑、边界条件、异常分支。
- 不追求 100% 行覆盖，而求"高风险路径覆盖"。
- 用参数化测试覆盖多分支。

## 4. 集成测试

### 4.1 验证协作

集成测试验证"代码 + 真实依赖"能否协作：

- 与数据库：验证 SQL、事务、映射。
- 与缓存：验证读写一致。
- 与 MQ：验证发布/消费。

### 4.2 Testcontainers

用 Docker 起真实依赖（MySQL、Redis、Kafka）做集成测试，比 Mock 更贴近真实，又比完全 E2E 轻。适合验证 SQL 方言、事务行为。

### 4.3 代价

比单测慢，需管理生命周期（启动/清理），不应过量。

## 5. 端到端测试

### 5.1 定位

模拟真实用户操作完整链路（UI / API 全流程），验证系统整体可用。

### 5.2 工具

- Web：基于浏览器的自动化（如 Playwright/Cypress 思路）。
- API：脚本化调用业务流。

### 5.3 陷阱

- 慢、脆弱（UI 变化即断）。
- 应聚焦关键路径（下单、登录），而非全覆盖。
- 需要稳定的测试环境与数据。

## 6. 契约测试

### 6.1 问题背景

微服务间接口变更易破坏消费者，但消费者与提供者由不同团队维护，集成测试难覆盖。

### 6.2 思路

- 消费者定义"我期望的接口契约"（请求/响应样例）。
- 提供者在 CI 中验证自己满足契约。
- 双方解耦，不依赖联调环境。

### 6.3 适用

多团队、接口多、联调成本高的微服务架构。

## 7. 测试数据管理

### 7.1 数据来源

- ** fixtures**：固定样例数据。
- **工厂模式（Factory）**：动态生成符合约束的数据。
- **生产脱敏数据**：真实分布但去隐私，适合性能/探索测试。

### 7.2 隔离

- 每测试用独立数据，避免相互污染。
- 事务回滚 / 容器重建保证干净。

### 7.3 一致性

- 测试假设的数据状态要显式，不依赖隐式全局状态。

## 8. Mock 与 Stub

- **Mock**：验证"是否以预期方式调用了依赖"。
- **Stub**：提供预设响应，隔离外部。
- 滥用 Mock 会使测试耦合实现细节，重构易碎；应优先测行为而非交互。

原则：对稳定依赖少 Mock，对慢/不可控依赖（第三方 API）Mock。

## 9. CI 中的测试策略

- **提交即跑**：单测 + 静态检查，秒级反馈。
- **PR 门禁**：集成测试 + 契约测试。
- **夜间/预发**：E2E + 性能测试。
- **分层执行**避免阻塞：快测试频繁，慢测试定时。

## 10. 覆盖率与质量门禁

### 10.1 覆盖率指标

- **行覆盖**：执行到的代码行比例。
- **分支覆盖**：条件分支覆盖。
- **变更覆盖**：本次改动代码的覆盖，更贴近价值。

### 10.2 门禁

- 设最低覆盖率阈值（如增量 80%），低于则拒合。
- 但避免"为覆盖而写无意义测试"，应看风险覆盖而非数字。

### 10.3 静态分析

- 代码风格、复杂度、安全漏洞扫描。
- 与测试互补，防低级错误。

## 11. 性能与混沌测试

- **性能测试**：压测验证容量（见 SRE 容量规划）。
- **混沌测试**：主动注入故障（杀节点、延迟网络）验证韧性。
- 二者是质量体系的高级组成。

## 12. 测试与可测试性

- 依赖注入使替换依赖（Mock）容易。
- 纯函数多、副作用隔离，测试简单。
- 避免全局可变状态、隐藏依赖。
- 设计时就考虑"如何测"，而非写完再补。

## 13. 常见踩坑

1. **只写 E2E 不写单测**：反馈慢、定位难、维护贵。
2. **单测狂 Mock**：测试实现细节，一改就碎；应测行为。
3. **测试数据相互污染**：用例顺序依赖，偶发失败难查。
4. **覆盖率形式主义**：追求 100% 但全是无效断言。
5. **无 CI 门禁**：测试写了不跑，等价于无。
6. **集成测试用假依赖**：以为验了 DB 其实没验。
7. **E2E 过度**：数百个 UI 测试脆且慢，关键路径即可。
8. **不带测试重构**：改完不知是否破坏，回归风险高。

## 14. 落地建议

- 新功能先写单测覆盖核心逻辑。
- 关键协作（DB、MQ）用集成测试 + Testcontainers。
- 微服务加契约测试防接口破坏。
- CI 分层跑，门禁卡增量覆盖与静态检查。
- E2E 只保关键路径，定期清理脆弱用例。

## 15. 小结

测试是"分层投入、风险导向"的工程：金字塔底的单测提供快反馈，集成/契约防协作破裂，E2E 守关键路径，CI 门禁把质量卡在合入前。核心不是覆盖率数字，而是用合理成本覆盖高风险路径，并让团队敢于持续重构。可测试性要从设计阶段考虑，而非事后补。
